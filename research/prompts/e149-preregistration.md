# E149 跑前登记：打包容器坏了靠什么补的三条补法各付什么

写于 2026-09-13 09:24 JST，装置写之前。

## 立项

D27（小数据打包容器） 未定项 1（2026-09-13 重开）逐字要求「容器坏了丢多少、靠什么补」一起答，正文列了三条补法「容器强制多副本、降低 cap、放弃打包」并逐字「都还没量」。
E114（小数据打包容器的总账） 给了每档对象大小的 cap、空间收益、写字节比与「一个容器坏了丢几个对象」；这里把三条补法在同一口径下各算成空间收益、写字节比、丢失半径与丢失概率的幂次，只报数不判输赢。

## 臂（补法）

| 臂 | 做法 |
|---|---|
| `none` | 不补：E114 的 `packbg` 形态原样（副本数 w = 2，D2（RAID 条带策略） 已定项 9） |
| `extra_copy` | 容器强制多一份副本（w = 3）：写字节 ×3/2、空间收益 ×2/3、丢失要三份同时坏 |
| `cap_2` / `cap_4` / `cap_8` | 把 cap 封顶到 2 / 4 / 8：收益与半径都等于 min(cap, 顶) |
| `no_pack` | 放弃打包：每对象一个整单元（E114 的 `pad`），收益 1、半径 1 |

对象大小五档 {512, 1024, 4096, 8192, 16384}；cap = ⌊(32768 − 107) / (size + 47)⌋（E114 口径：容器头 107、每槽自描述 47）。
空间收益 = 每单元装几个对象 = cap（packbg 整理完之后）；写字节比 = (n + ⌈n/cap⌉) / n 取 n → ∞ 的 1 + 1/cap，再乘副本数比；丢失半径 = 一个容器不可读时一起丢的对象数。

## 跑前写死的解析预测

- cap 五档 58 / 30 / 7 / 3 / 1（E114 单测钉住的数）。
- `extra_copy`：收益 38.67 / 20 / 4.67 / 2 / 0.67（16 KiB 档变成 < 1，比不打包还费），写字节比 (1 + 1/cap) × 1.5。
- `cap_8` 在 512 B 与 1 KiB 档把半径从 58 / 30 压到 8、收益从 58 / 30 压到 8；对 4 KiB 以上三档一个数不变。
- 16 KiB 档五臂里没有一臂收益 > 1（cap = 1 是硬边界，E114 逐字）。

## 判据（只报数）

1. 每档每臂：收益、写字节比（万分之）、半径、丢失概率幂次（要几份副本同时坏）。
2. 敏感点：cap 顶 8 在 512 B 档改数、在 4 KiB 档不改数。

## 失败条款

- a. 阳性对照：cap 五档必须逐字等于 E114 的 58 / 30 / 7 / 3 / 1，否则装置口径漂了，整轮作废。
- b. 16 KiB 档任何一臂收益 > 1 ⇒ 公式错，作废。
- c. 确定性模型，证据来自变异表。

**什么观测会让各条触发**：a 在容器头或槽自描述宽抄错时触发；b 在收益公式写反时触发。

## 反过来的结果我接不接受

没有输赢；这些数交给 D27（小数据打包容器） 未定项 1 / 未定项 2 定案用。

## 它答不了什么

容器坏的概率本身（设备失效率）、整理的挂钟代价（C202（打包巡回的空转开销与迟滞 K 都没有数））、覆盖面分母（C174（smallfile 那一行的三列没测））。
