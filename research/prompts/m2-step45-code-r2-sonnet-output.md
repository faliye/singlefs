### X3（影子账只住内存）——打中够得着，处置的"读法切换"半步可议

打中部分本身没有疑问：round1 原文（`m2-step45-code-r1-body.md:31`）里 S4 的原始实现是"只隔离『(txg, 实例) 大于 R_old 的可读根引用而 R_old 不引用』的槽"，且**只在 `mount_rollback` 里算一次**——这条信息只住 `PoolAllocator`（内存态），下一次挂载（`mount_writable`）重建分配器时完全没有代码路径去恢复这份隔离状态（`rebuilt_allocator` 改法之前的版本里 `mount_writable` 调用它时没有任何"读取上一次隔离结果"的输入）。这是纯粹的状态丢失，不依赖读法选择，任何读法（窄/宽/保守）都会在"只算一次、不落盘、不重算"的原实现下于下一次挂载归零。**这一步的打中是无条件成立的。**

### X4（前缀第五条是死条款）——判对，结构性证明

`recovery.rs:426-432`：

```
pub fn rollback_high_water_of_root(reader: &dyn PoolReader, root: &RootRecord) -> Option<u64> {
    instance_table_of_root(reader, root)?
        .rows
        .iter()
        .find(|row| row.instance == root.instance && row.is_rollback)
        .map(|row| row.applied_transaction_high_water)
}
```

要求：`root` 指着的实例表里，有一行 `row.instance == root.instance` 且 `row.is_rollback`。回退行是在 `establish_instance`（`mount.rs:408-519`）里写的，写入的是**新实例**（`instance = acquire_instance(...)`，`mount.rs:420`）的第一次发布（`row_publish`，`mount.rs:447-463`）所指向的实例表；而回退行本身的 `instance` 字段是**被退回的旧实例**（`target.instance`，经 `previous_row.instance`，`mount.rs:694-699` → `mount.rs:429-435`）。即：写着回退行的表，挂在"新实例"的根下面；回退行自己的 `instance` 字段却是"旧实例"的号。要让 `rollback_high_water_of_root(root)` 返回 `Some`，需要一个 `root`，它的 `instance` 字段与它自己指着的表里某一行的 `instance` 字段相等，且那一行 `is_rollback`。由于每次 `establish_instance` 写的表里，回退行 / 中间实例行的 `row_instance` 严格小于这次新取得的 `instance.0`（`mount.rs:428`：`for row_instance in first_row_instance..instance.0`），**任何一个根的表里都不含它自己实例的行**——这是构造性的、对全部可达历史成立，不是"目前测试没构造出来"。round1"任何可达历史上取不到真"的判断成立，我没能找到反例。

## 替被判出局的一方辩护

按规则要求，辩护靠查同类先例，不重新论证利弊；找不到就写找不到。

### P1（jsn 接在 R_old 自己那条记录之后）—— 找到的先例反而不利于它，如实报告

查了 `checks-owed.md` C340 的"谁打的"栏，指向"C143（inode 号水位在回退后会退回去重发） 第二轮攻方腿（H10）"——这条正是 P1/P2 这对分歧在 kb 里第一次被登记的地方。再查 C143 本身的定案（`checks-owed.md:146`），它处理的是一个**结构同构**的问题：回退之后新实例的**第一次发布 txg** 该怎么取，此前的做法是类似 P1 的"从 R_old 自己的值往下接"，2026-09-16 用户经三轮三方论证 + 定案，改成了"CJ2：max(根环里全部根记录的 txg, 环里全部自证通过的记录的 checkpoint_txg) + 1"——即改成类似 P2 的"从环里能读到的最大值往下接"（`decisions/23-journal的角色与格式.md:691` 与 `:1209` 两处逐字确认这条定案）。这是同一份代码里、同一个函数（`first_txg_of_new_instance`，`mount.rs:147-165`）里，**txg 这一维已经做过一次一模一样的选择，而且选的是 P2 的形态**，理由与 X2 打中 P1 的理由同构：都是"从 R_old 自己的值往下接"会让某个本来该被跳过的旧值被复用/覆盖。

这条先例找到了，但它是**支持 P2、不支持 P1** 的先例——我没能找到任何一处仓里现存的先例支持"从 R_old 自己的值往下接"这种模式在 jsn 或类似的单调序号上是安全的。按照"辩方靠先例，找不到就写找不到"的要求，我在这里如实报告：**没有找到能救 P1 的同类先例；找到的唯一同类先例（C143/CJ2）反而印证了 X2 的判断方向**。加上我自己在副本上的变异复现（P1 变异必红），P1 出局在证据上是双重确认的，不只是round1一次判断。

### 窄读法 —— 先例就是它自己，是现行已定条款，不需要"辩护"，需要的是指出它被违反

这一条不需要去查外部先例，因为它本身就是 2026-09-16 的用户定案（`decisions/23-journal的角色与格式.md:1209`，原文已在第六节引用）。它站得住的理由不是"利弊权衡"，是**它已经被定下来了**。round1 处置里把"每次挂载都重算"（修 X3 必要）与"换成保守读法"（不是 X3 必要）捆在一起做，导致代码现在违反这条已定规则。这里的"辩护"应当是：窄读法在结构上完全可以与"每次挂载重算"共存——`rebuilt_allocator`（`mount.rs:196-252`）已经在算 `oldest_valid_root`（有效根集合里最旧的 txg），只需要再收集"有效根集合各自的分配记录并集"，从每条被抛弃根的分配记录里减去这个并集，剩下的才隔离，就是窄读法的"每次挂载重算"版本，工程量比现在的实现只多一步集合差运算。这不是无法实现，是这一轮为了先让 X3 的测试变绿而选择了更简单的写法。

### 最新根自己的 F（回退候选集）—— 站不住，D16 已定项 1 文字无歧义

`decisions/16-发布语义.md:376`："回退候选集 | 按实例表判仍然有效 ∧ txg ≥ F_生效"，没有第二种读法的空间。这条与"两个 F"决策点里 checker 的 F 用法（`invariants.md:120`，"最新根带的回退下界 F"）不是同一件事——checker 判的是"哪些单元仍然算被有效引用、不能被判失效"，这个问题的天然参照系是"当前挂载点/最新持久状态实际生效的那个 F"，即最新根自己的 F；回退候选集判的是"哪些根允许被回退管理员选中"，这个问题的天然参照系是"考虑到所有幸存设备之后，真正确认生效的 F 下界"，即 F_生效——两者问的问题不同，用不同的 F 是有道理的设计，但"回退候选集用最新根自己的 F"具体这一处没有任何条款支持，也没找到先例，站不住。这与 checker 那半"最新根自己的 F"的合理性是两回事，不能互相佐证。

### 只用 F_生效 做回收门槛（省略"环里最旧有效根"）—— 字面站不住，但有一个可以核实的"零行为差异"记录
