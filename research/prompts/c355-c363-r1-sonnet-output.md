## 0. 结论摘要（先给结论，后面逐段给推导）

**问一（C355，checkpoint 保留池怎么扣）**：甲（今天维持，池级减一份 ckpt_cost）在**对称盘**（两盘空闲相等）上就已经系统性少扣——少扣量恰好是 `ckpt_cost / 2` 块每盘的安全边际，与「需求」读哪一种口径无关。乙（池级乘副本数）与丙（按 D28 已定项 1 的写法「挪进括号」）在两盘等量时**代数上是同一个式子**（副本数 = 2 = 设备数时，「池级减 2×ckpt_cost」与「Σ设备(...− ckpt_cost)」逐项展开后完全相同），都能在对称盘上补齐甲漏掉的一半。但**三条臂共享同一个结构性缺陷**：`可用 = Σ设备(...)` 是单个池级标量，标量求和**原理上**不可能防止「一块盘富余、另一块盘吃紧」时用富余那块的余量掩盖吃紧那块的短缺——这正是 E141 已经在切换预留（同一份 D28 已定项 1 式子里的另一项）上实测过的现象（判据 3：按设备判只读、按池级标量判可写）。⇒ **甲在两种盘型上都出局；乙与丙作为「池级标量」的两种写法在非对称盘上同样出局，不分辨彼此**；要让 checkpoint 保留池真正兑现「固定点在每块盘上都分得到」，需要一条**结构上独立于 Σ设备(...) 的按设备逐一比较**（不是把减项挪进括号那么简单），这条今天没有任何候选提出。「需求」的口径核实：全仓没有条款；从 `已分配` 的设备维增量反推，「需求」必须读成 `2u × 16384`（与 `Σ设备(已分配)` 的增量同口径），否则乙/丙在 u > 0 时也会少扣。

**问二（C363，ckpt_cost 树高从哪读）**：甲（发布开始读一次、window 内不再更新）对「窗口里的插入让根分裂」**没有任何防护**——分裂发生在读之后、下次发布之前，admission 全程用旧高。乙（内存派生、随分裂即时更新）把这个窗口收窄到「checkpoint 自己的固定点收敛过程本身导致的分裂」——这是一个结构性盲点：**任何一条臂都不可能在准入那一刻预知这次 checkpoint 自己会不会把某棵树推过分裂阈值**，因为那正是 ckpt_cost 本身要算的量（循环依赖）。丙（上一次发布的高 + 每树 1 层余量）把乙的残余窗口也盖住了，**但仅当一次窗口/一次 checkpoint 最多让一棵树多长一层**——这个「至多一层」的上界全仓没有条款、也没有实测。⇒ 三条臂都有可构造的失败序列，但窗口大小依次收窄（甲 > 乙 > 丙），丙是三者里最不容易被打中的，但它依赖一个尚未证明的假设。

**从机制反推口径**：`crates/singlefs-core/src/allocator.rs:253-265`（`PoolAllocator::record`）——每次 `record(placement, generation)` 对 `self.devices` 里**每一块设备**各推一条 `AllocationRecord`（`for device in &self.devices { self.records.push(...) }`），随后对每块设备各调一次 `mark_allocated`。写 u 个 16 KiB 单元、w=2 两盘各一份时：分配记录树里新增 `2u` 条记录（每块盘各 u 条），`crates/singlefs-core/src/transaction.rs:759-767`（`accounting_entries` 构造）显示 `STATISTIC_ALLOCATED_BYTES` 逐设备统计（`per_device(...device_map.allocated_slots() * SLOT_BYTES)`），即 `Σ设备(已分配)` 按 D5（快照 / 空间记账机制） 已定项 4（`05-快照-空间记账机制.md:756`「已分配字节...**带**设备维」）逐设备累加——写 u 个单元后 `Σ设备(已分配)` 增长 `2u × 16384` 字节（每块盘各增 `u × 16384`）。

**结论**：`可用 = Σ设备(容量 − 已分配 − ...)` 这个式子，`已分配` 本身就是「设备维统计量求和」，所以 `Σ设备(...)` 的减项已经把镜像开销算了两遍（两块盘各减一次 `u × 16384`）。要让 `可用 ≥ 需求` 在算术上自洽（两边同一个「物理字节消耗」的口径），**「需求」必须读成 `2u × 16384`**，与 `Σ设备(已分配)` 的增量同口径。若读成 `u × 16384`（逻辑字节，不计镜像），则 `可用` 的分母（Σ设备）已经是两块盘之和，而「需求」只报了单块盘的量，准入会把同一次写的真实消耗低估一半——这不是无关的选择，下面 T1 的数值例子里会看到：**两种读法都会让某一档臂出局，但读成 `u × 16384` 会让出局的档更宽**。⇒ **判定：「需求」应读成 `2u × 16384`；下面 T1/T2 两种读法都算一遍，但以 `2u × 16384` 为口径成立的判定为准**（因为它是唯一与式子里其余各项同口径的读法）。

⚠️ **这条推论本身没有走三方论证，是本轮正推腿的机制推导**，可被推翻：如果 D28（挂载期承诺量） 已定项 1 的「需求」原本设计成故意只报逻辑字节（比如为了让准入不感知冗余度、由分配器自己在扣除时乘副本数），那读法会反过来——但那样的话「可用」也必须相应改写成不含设备维求和的单一逻辑容量，而已定项 1 逐字明写「可用 = Σ设备(...)」，与「需求只报逻辑字节」的假设不自洽。**什么现象会推翻它**：如果 kb 里出现一条条款明确说「需求按逻辑字节计、可用的设备维求和已经隐含镜像开销的对账」，或者实现侧的准入代码写出来后，`2u×16384` 读法在真实回归里持续触发假性 ENOSPC 而 `u×16384` 不会，就要重新核这条判断。

## 3. 问一 T1：甲/乙/丙 的数值例子（任务项 2）

**记号**：块 = 16 KiB；ckpt_cost 取第一个事务几何的候选值 4（E148（提交固定点按两棵记录树重算） `scale=first_transaction` 各臂 `empty_publish_meta_blocks=4`，`.claude/kb/experiments/148-提交固定点按两棵记录树重算.md` 判决表）；两盘、w=2（D2（RAID 条带策略） 已定项 6 / 已定项 9）；写 u 个 16 KiB 单元，每块盘各占 u 块（`allocator.rs:253-265`）。**真实安全线**：admission 放行之后，每块盘的剩余空闲必须 ≥ ckpt_cost，即 `F_盘 − u ≥ ckpt_cost` ⇔ `F_盘 ≥ u + ckpt_cost`（每块盘各自成立，两块盘都要）。

三条臂的池级标量公式（`可用` 与 `需求` R 都是标量，`可用 ≥ R` 才放行）：

| 臂 | 可用 |
|---|---|
| 甲 | `F0 + F1 − ckpt_cost` |
| 乙 | `F0 + F1 − 2 × ckpt_cost` |
| 丙（挪进括号，逐设备减后求和）| `(F0 − ckpt_cost) + (F1 − ckpt_cost) = F0 + F1 − 2 × ckpt_cost` |

**丙与乙代数恒等**（副本数 = 2 = 设备数时）：`Σ设备(其他项 − ckpt_cost) = Σ设备(其他项) − 设备数 × ckpt_cost`，与乙的「池级减 副本数×ckpt_cost」逐项相同——**只要丙仍然是把结果加总成一个标量再跟 `需求` 比，它和乙就是同一个式子**，这一点在下面的非对称例子里是关键。

### 3.1 对称盘（F0 = F1 = F）

真实安全线：`F ≥ u + 4`。取 **u = 1**，真实边界 `F ≥ 5`。

| 池状态 F（两盘各） | 甲：`2F−4≥需求R` | 乙/丙：`2F−8≥需求R` | 真实（F≥5）|
|---|---|---|---|
| R = 2u = 2（本轮判定口径） | | | |
| F = 4 | `2(4)−4=4 ≥ 2` → **放行** | `2(4)−8=0 ≥2`？否 → **拒绝** | 放行后每盘剩 3 < 4，**不安全** |
| F = 5 | `2(5)−4=6 ≥2` → 放行 | `2(5)−8=2 ≥2` → 放行 | 放行后每盘剩 4 = 4，**恰好安全** |

⇒ **甲的放行边界是 `F ≥ 3`**（解 `2F−4≥2`），比真实边界 `F ≥ 5` 松 2 块——**任何 u 值下甲都少扣 `ckpt_cost/2 = 2` 块每盘的边际**，是结构性的（池级减一份，却要覆盖两块盘各自的需要，等于把一份 reserve 拆成两半分给两块盘）。**乙/丙的放行边界恰好是 `F ≥ 5`，与真实边界重合**——对称盘上乙/丙正确，甲出局。

若 R = u = 1（另一种「需求」读法）：甲边界 `2F−4≥1 ⇒ F≥2.5`（更松，甲更糟）；乙/丙边界 `2F−8≥1 ⇒ F≥4.5 ⇒ F≥5`（整数取整后不变，因为块数是整数——这里 u=1 时两种读法对乙/丙的边界恰好一致，但 u 更大时会分开，例如 u=10：真实边界 F≥14；乙/丙 R=2u=20 时边界 `2F−8≥20⇒F≥14`（重合）；R=u=10 时边界 `2F−8≥10⇒F≥9`（比真实松 5，**验证了「需求」必须读 2u 才自洽**，任务项 1 的结论在这里被坐实）。

**最小数值反例（T1 判据要的「最小数值例子」）**：ckpt_cost=4，两盘各 F=4，u=1，R=2（本判定口径）。甲：可用=4≥2 → **放行**；放行之后两盘各剩 3 块，下一次 checkpoint 的固定点在两块盘上都分不到它要的 4 块 → **甲在这一格出局（T1 判据字面命中）**。

### 3.2 一块盘短（F0 = 100, F1 = 4，非对称）

真实：盘 1（F1=4）已经低于真实边界 `F≥5`（哪怕 u=0！`F1−0≥4` 恰好等于 4，OK；但 u=1 时 `4−1=3<4` 不安全）——取 u=1：真实上盘 1 不该放行（放行后盘 1 只剩 3 块，< ckpt_cost=4）。

| 臂 | 可用（R=2 时的判定） |
|---|---|
| 甲 | `(100+4)−4=100 ≥ 2` → **放行**（错，盘 1 会饿死） |
| 乙 | `(100+4)−8=96 ≥ 2` → **放行**（同样错） |
| 丙（逐设备减后求和）| `(100−4)+(4−4)=96+0=96 ≥ 2` → **放行**（与乙数值相同，同样错） |

⇒ **三条臂在这一格全部放行，全部错**——这正是「结论摘要」里讲的结构性缺陷：`可用` 是把两块盘加成一个数再比较，**富余盘（100）的余量把吃紧盘（4）的短缺完全遮住**，无论 ckpt_cost 这一项按甲、乙还是丙的写法扣，都是先算出各自的「其他项」的设备维贡献、最后仍然求和成一个标量。**丙作为「挪进括号」的字面写法（仍然求和）不能解决非对称盘的问题**，它与乙给出完全相同的数字（96），因为线性求和不关心括号内外。

**要让这一格正确判定，需要一条与 `可用 ≥ 需求` 结构上独立的检查**：`∀设备 d: F_d − u_d − ckpt_cost ≥ 0`（逐设备各自比较，不求和）。这正是 E141（切换预留的挂载准入自证） 已经在**另一项**（实例切换预留）上实测出的两种判法差异（`.claude/kb/experiments/141-切换预留的挂载准入自证.md` 判据 3：「28 个取样点上『盘 0 空闲 = 份额 + 50、盘 1 = 份额 − 1』的池，被测臂全部只读、池级标量臂全部可写」）——E141 的「被测臂」用的正是**挂载时单独的逐设备判定**（`挂载判定：每块盘上 容量 − 已分配 − 不可回收 − defer 待释放 ≥ 这块盘的份额`），**不是** D28（挂载期承诺量） 已定项 1 那个 `可用 ≥ 需求` 池级式子本身。checkpoint 保留池今天**没有**这样一条独立的逐设备判定——D28（挂载期承诺量） 已定项 1（`28-挂载期承诺量.md:21`）的 `可用` 定义就是 `Σ设备(...)`，是唯一的准入通道。

**T1 判定（正推腿结论）**：甲在对称盘上出局（3.1 的最小反例）；乙与丙作为「池级标量」在非对称盘上一起出局、不分辨彼此（3.2 的反例）；三条候选都不能单独满足 T1——真正需要的是一个第四种形态（逐设备 conjunction，不是逐设备减后再求和）。

## 4. 问一 T2：假性 ENOSPC

**方向性论证**：甲/乙/丙都是「Σ设备(其他项) − k×ckpt_cost」这个形状（k=1 或 2），三者对同一个池状态的排序是 `可用_甲 ≥ 可用_乙 = 可用_丙`（甲减得少，可用值更大，更宽松）。而「真实安全线」是逐设备的合取，**任何一个满足逐设备真实安全线的池状态，也必然满足池级标量的 `≥` 判定**（因为逐设备各自非负之和必然非负，池级式子是逐设备真实约束的一个必要但不充分条件——参见 3.2 的求和展开）。⇒ **甲/乙/丙都不会把一个真实安全的池状态判成不安全**——它们的错误方向只有一种：**把不安全的池状态误判成安全（对应 T1 出局的那些格），不会把安全的池状态误判成不安全**。⇒ **T2（假性 ENOSPC）在这三条臂上都不触发**：写不出「某条臂在『放行之后固定点每块盘都分得到』的池上拒绝」这样的例子——因为标量求和只会更宽松，不会更苛刻。

⚠️ 这与前提十「保留池对普通分配是纯税，加重假性 ENOSPC」（D23（journal 的角色与格式）「死锁 2 与假性 ENOSPC 是两种故障」一节）不矛盾：那条讲的是**扣同一笔固定的 ckpt_cost 会挤占可分配空间**（值越大越容易撞上真 ENOSPC 的边界），是关于**扣多少**的成本，不是关于**扣的算法本身会不会误判**。乙/丙比甲多扣一倍，意味着乙/丙比甲提前触发拒绝（在 3.1 的边界 F=3、4 那两格），但那些格按真实安全线本来就该拒绝——是**修正了甲的漏洞**而不是「制造」假性 ENOSPC。

## 5. 问一 T3：第八项与 D16 已定项 1 的「10 + 7 c_max」是不是同一个池（任务项 3）

**逐字引两处**：

D28（挂载期承诺量） 已定项 4 的最终「形态」段（`.claude/kb/decisions/28-挂载期承诺量.md:100`）：「ckpt_cost = Σ（每棵记录树当前的高）+ 记账树每发布的节点数，每次发布按当时的树高重算；单位是 16 KiB 元数据块...归属：并进已定项 1 的『挂载期承诺量』那一项，作池级一项、不按设备求和...**D16（发布语义） 已定项 1 的推空保留池 10 + 7 c_max 与 D16（发布语义） 已定项 8 的切换预留都按同一个现算的 c_max 取。**」

D16（发布语义） 已定项 1（`.claude/kb/decisions/16-发布语义.md:415`）：「`df` = 没用过的 + 已释放的 + 活元数据 − 保留池 − 推空最坏残留 − 滞后量；**保留池 = 2 × 5 + (B − 1) × c_max = 10 + 7 c_max**，残留 = 5 + (B − 2) × c_max...」，同节（`:427` 附近）：「c_max 是声明的最坏空发布开销，口径 2026-09-13 由 D28（挂载期承诺量） 已定项 4 定为按当时结构现算...；**保留池那 10 + 7 c_max 算不算挂载期承诺量归 D28（挂载期承诺量） 已定项 4**。」

**判定：不是同一个池，是两个不同的量，共享同一个输入参数 `c_max`（= ckpt_cost）**：

1. D28（挂载期承诺量） 已定项 4 的「checkpoint 保留池」= `ckpt_cost` 本身（一次空发布/固定点的开销，第一个事务规模 4 块），是 D28（挂载期承诺量） 已定项 1 准入不等式的**第八项**，直接以块数×16384 的形式出现。
2. D16（发布语义） 已定项 1 的「保留池」= `10 + 7c_max`（B=8 次空发布上限时的推空最坏开销，一个关于 `c_max` 的**线性组合**，不是 `c_max` 本身），用在 D16（发布语义） 自己的 `df` 与「可分配 = min(可再分配+活元数据−保留池, df)」——这是前提四讲的「两道串联的闸」里**另一道闸**（D16 的闸），与 D28 已定项 1 的「Σ设备(...) ≥ 需求」是不同的检查。
3. **两者用同一个 `c_max` 值作为输入**（D28 已定项 4 逐字点名「都按同一个现算的 c_max 取」），但**加总方式不同**——一个是把 `c_max` 原样当第八项（乘 16384），另一个是 `10+7c_max`（乘 16384，D16 已定项 1 依据段有「保留池按 9 算是 73 块、按 4 算是 38 块」）。**两个数值不相等**：first-txn 几何下 ckpt_cost=4 块，`10+7×4=38` 块——差 9.5 倍。

4. **是否重复扣**是一个悬而未决的空白：D28（挂载期承诺量） 已定项 1 的正文（`28-挂载期承诺量.md:20`）只写「checkpoint 的保留池仍在 D23（journal 的角色与格式）『死锁 2 与假性 ENOSPC 是两种故障』一节，它算不算挂载期承诺量是 D28（挂载期承诺量） 已定项 4」——**这句话只提到 D23 的 `reserve≥ckpt_cost` 那个保留池，没有提 D16 已定项 1 的 `10+7c_max`**。D28（挂载期承诺量） 已定项 4 的「定案之前那一条」（历史段，`28-挂载期承诺量.md` 附录里的「原第 4 条」，任务背景材料 540-542 行引用）曾写「D16（发布语义） 已定项 1 的推空保留池 10 + 7 c_max 也是这一类量，一起判」——但**最终定案的「形态」段没有把 `10+7c_max` 并入第八项**，只并入了 `ckpt_cost` 本身。⇒ **今天的字面读法是：D28 准入式子的第八项只扣 `ckpt_cost`（如 4 块），`10+7c_max`（如 38 块）只出现在 D16 已定项 1 自己的 `df`/`可分配` 计算里，两者不是同一笔扣款、也没有互相抵消或叠加的显式条款**——这正是 C363 之外的另一处口径空白，但任务只要求我在 T3 报告判定，不要求我立新欠账（若要立，应记在 C126（切换预留的最坏量没有口径） 或 C355（checkpoint 保留池池级扣而固定点每块要落两列） 相邻的一笔新欠账，留给主 agent 判断）。

## 8. 问二 T7：一次发布的固定点会 COW 哪些树/单元；E148 漏了哪几项（任务项 4）

**按今天 `crates/` 的实现**（`transaction.rs:568-960` `publish_first_file`），一次发布实际写出的单元（第一个事务，8 个 t 单元 + mkfs/暖机不计）：t1 数据单元（用户内容，不算「元数据」）、t2 extent 树根兼叶、t3 inode 叶容器、t4 inode 树根、t5 分配记录树、t6 记账树、t7 中央映射树、t8 树表。**每个单元都会调 `allocator.allocate_*`（都会产生一条分配记录，见 `allocator.rs:253` `record()` 对每个 `Placement` 无差别调用）**；除 t7 自己、t8、以及实例表（第一个事务里没有写，只在 mkfs/切换写）之外，**其余单元都会在中央映射树里插一条条目**（`transaction.rs:835-860` `mapping_entries` 列表逐条列出：data、extent_pointer、inode_leaf_pointer、inode_root_pointer、allocation_pointer、accounting_pointer 共 6 条，**不含** mapping_pointer 自己与 tree_table_entries——代码注释原文 `transaction.rs:834`「映射树自己、树表、实例表豁免（D19（块指针的结构与宽度预算） 已定项 8 / 已定项 12）」）。

**E148（提交固定点按两棵记录树重算） 建的「两棵记录树」= 分配记录树 + 中央映射树**（premise 二、premise 八）。对照今天实现的 8 个单元，E148 的固定点循环只吃「新分配一个块 → 往两棵记录树各插一条」这条反馈；这意味着它把 t2/t3/t4（extent/inode，「用户」写入本身）算进 `user_block_count`（模型的 `U`），把 t5/t6/t7（分配记录/记账/映射树自己）当「提交内生块」（`arm.commit_blocks_are_clustered()`），**但 t8（树表）完全不在模型里**——读 `research/e7-index-bench/src/bin/e148_commit_fixpoint_two_record_trees.rs:158-180`（`publish` 函数），`pending` 只由 `user_block_count` 与 `accounting_node_count` 两路初始化，**没有第三路代表树表本身的重写**。而今天的实现每次发布都会写一个新版本的树表单元（t8），且 t8 会调 `allocate_commit_generated`（`transaction.rs` 里 `TransactionUnit::IN_BUMP_ORDER` 含 `TreeTable`，`allocator.rs` 测试 `pool.records().len(), 20` 把 t1..t8 全部计入分配记录数）——**这个块本该往分配记录树插一条记录（不进映射树，因为它享受自举豁免），这条反馈没有被 E148 建模**。

**这不是无关紧要的疏漏，但它的数值影响可能被另一处偏差抵消**：`e148_commit_fixpoint_two_record_trees.rs:20`（`ACCOUNTING_NODES_PER_PUBLISH: u64 = 2`）是一个**不随 `Scale` 调整的常量**（对照同一文件 `record_trees()` 函数，`FirstTransaction` 分支把分配/映射两棵树的叶数都改成 1，但 `main()` 里所有规模都传同一个 `ACCOUNTING_NODES_PER_PUBLISH=2`）。而**今天 first-txn 的真实字节表只写 1 个记账节点**（`.claude/kb/first-txn-layout.md` 五节「记账树节点...树 ID 14，1 个节点（t6）」）。⇒ E148 对 first-txn 规模的 `meta_blocks=4`（1 分配 + 1 映射 + 2 记账）**是把记账多算了 1、把树表漏算了 1，两处误差在这一档几何下恰好相消**（真实应为 1 分配 + 1 映射 + 1 记账 + 1 树表 = 4，与模型报的 4 数值相同，但内部构成不同）。**这个相消是这一档几何的巧合，不是公式保证的**——池规模（accounting=2 是否仍然是真实值，我没有独立核实；树表漏算的量在聚簇政策下，若树表的那 1 条分配记录落进已脏的叶就是 0 边际成本，落在叶边界就是 +1 到 +3（视分配记录树层高）——`.claude/singlefs-ai-sop/rules/test-discipline.md`「只让多条臂互相比，测不出所有臂一起错」在这里适用：E148 的三档臂（clustered / scattered / meta_clustered）都共享同一个「不含树表」的模型，臂间互比对不出这处遗漏。

**T7 结论（只报，不判输赢）**：

1. 今天实现一次发布会 COW：extent 树、inode 树（2 个节点：叶+根）、分配记录树、记账树、中央映射树、树表——**6 类结构**（premise 十二列出的 8 棵树里，livelist / 稀疏旁表 / deadlist 第一个事务不写；条带成员表第一版 `w` 恒 2、D2（RAID 条带策略） 已定项 18 钉死 `devs≤2`，不开线）。
2. E148 的公式（`ckpt_cost = Σ树高 + 记账节点数`）**只覆盖分配记录树 + 中央映射树 + 记账树（作为一个扁平常数）**，**漏了树表自身的每发布重写**（一个恒定的分配记录树反馈项，聚簇政策下常见边际成本 0 但有非零的最坏情形）；**记账节点数硬编码为 2，与 first-txn 实测的 1 个节点不符**——两处偏差在 first-txn 几何下相消，在其它几何下不保证相消。
3. E148 自陈未建模：条带成员表（D2（RAID 条带策略） 已定项 12）、livelist（D6（快照实现模型） 已定项 3）、节点分裂合并（`.claude/kb/experiments/148-提交固定点按两棵记录树重算.md`「它答不了的」第 1 条）。
4. 「记录树」这个词本身**没有条款给出外延**（C363（现算保留池时树高从哪读没有条款） 的题面原话）——E148 的「两棵」是这个实验自己的建模选择，不是任何决策文件里点名的定义；D28（挂载期承诺量） 已定项 4 的「每棵记录树当前的高」在字面上可以读成前提十二列出的全部 8 棵树（若 livelist/稀疏旁表/deadlist 有根之后也要算），也可以窄读成只有「参与固定点反馈循环」的那两三棵——**这个定义空白本身就是 C363 的一部分，我在这里只能报告它存在，不能替它定义**（定义会改变 T6 的判定，属于 T6 判据本身要用的输入）。

**什么现象会推翻它**：如果 `research/e7-index-bench` 的 E148 源码有一个我没看到的地方把树表的反馈也算进了 `pending`（比如通过某个我没追踪到的常量间接补偿），这条「遗漏」的判定要收回；我已经读了 `publish()` 函数全文（158-193 行）和 `main()` 的常量定义（1-30 行），没有找到这样的补偿路径。

## 9. 问二 T6 / T8：根分裂在窗口里 vs 固定点里；准入那一刻看不看得到（任务项 5）

**三种分裂时机，逐一对三条臂**：

**(a) 窗口里的插入让根分裂**（本次 checkpoint 开始之前，累积写入已经让某棵记录树的根超出容量、COW 出新的一层）：

- **甲**（发布开始读一次、两次发布之间沿用）：**完全没有防护**。甲的定义（洞二原句）是「两次发布之间准入用上一次发布算出的值」——按定义，从上一次发布结束到下一次 checkpoint 触发之间的整个窗口，admission 用的都是**上一次发布时的旧高**。如果窗口期间的插入把分配记录树从高 3 长到高 4（例如大量新文件的 extent/inode 记录级联出新的分配记录，压满了原来的根），admission 全程按高 3 算 ckpt_cost，但下一次 checkpoint 真实要按高 4 收敛。**T6 判据字面命中**：存在操作序列（窗口里插入 → 根分裂）使甲扣的 ckpt_cost 小于固定点实际分配的块数。
- **乙**（内存派生，随分裂即时更新）：**这一类分裂被正确捕捉**——只要分裂发生在窗口内（不是本次 checkpoint 自己的固定点循环内部），触发分裂的那次插入操作本身就会调用「即时加减」的钩子，之后的 admission 立刻用新高。**不命中**（前提是这个钩子确实挂在每一条会导致分裂的插入路径上——这是实现完整性的问题，不是设计的问题）。
- **丙**（上一次发布的高 + 每树 1 层余量）：同样不命中——固定 1 层余量本来就是为了盖住「窗口内一次分裂」这类情形（背景材料候选描述原句）。

**(b) 固定点自己的插入让根分裂**（本次 checkpoint 的固定点收敛过程本身——为了给「记账/分配记录树自己的新 COW 节点」登记分配记录——把树推过分裂阈值，这正是 E148/C83（提交固定点没人回答） 讨论的「固定点迭代」现象本身）：

- **甲**：命中（已经命中 (a)，这里更严重——甲连上一次发布之后的任何变化都不追）。
- **乙**：**这里出现一个结构性盲点**。ckpt_cost 要在 admission 那一刻（本次 checkpoint 开始之前）被拿来跟可用空间比较，而「本次 checkpoint 自己的固定点会不会导致分裂」这件事，只有在固定点**已经跑完**之后才知道——这是一个循环依赖：ckpt_cost 的值依赖于固定点会写多少块，而固定点会不会多写（因分裂）又依赖于当前树高，当前树高又是 ckpt_cost 要读的输入。乙「随分裂即时更新」这个机制能捕捉「过去已经发生」的分裂，**不能预知「即将由本次 checkpoint 自己触发」的分裂**——因为触发那次分裂的插入，正是这次 checkpoint 固定点自己要做的工作，在 admission 检查那一刻（该次 checkpoint 还没开始跑）还没有发生。**T6 判据命中**：存在场景（某棵记录树的根节点已经填到只差一条记录就要溢出，本次 checkpoint 自己的记账/分配记录反馈恰好补上那一条）使乙在 checkpoint 开始前算出的 ckpt_cost 小于该次固定点实际分配的块数。
- **丙**：如果「每棵树加 1 层余量」这句话的本意就是覆盖「本次窗口或本次 checkpoint 至多让一棵树多长一层」（背景材料候选描述里没有区分是覆盖窗口分裂还是固定点自身分裂，字面写的是「覆盖窗口里一次根分裂」），那么当「恰好只有一层」的分裂发生在固定点内部时，丙也能盖住——**但这依赖于「至多一层」这个假设**（见下）。

**(c) 新建一棵树 / 一棵根指针为零的树第一次长出根**（livelist、稀疏旁表、deadlist 从「无根」变「有根」）：三条臂的定义都只说「读有根的树」（甲：「树 = 树表里根指针非零的树 + 中央映射树」）或「挂载时从各树根节点头读一次」（乙），**都没有显式处理『这次发布让一棵此前无根的树第一次长出根』这个转变本身**——按 T7 的射程结论，这三棵树的写入不在今天 ckpt_cost 覆盖的「记录树」范围内（它们不是「记录」树），所以严格按 D28（挂载期承诺量） 已定项 4 的字面定义（`每棵记录树当前的高`），这个场景**可能根本不适用**（如果 livelist/稀疏旁表/deadlist 从来不算「记录树」）。但这恰好说明 C363 的另一半空白：「记录树」的外延没有条款，导致「新树长出根」这个场景是否要计入 ckpt_cost 是不可判定的——我把它记为 T7/T9 的射程空白，不在这里判某条臂输赢。

**「至多一层」假设没有上界**：kb 里没有任何条款限制一个窗口（两次 checkpoint 之间）能积累多少次插入，defer 窗口（D16（发布语义） 已定项 1）管的是**回退可退回的状态数**（按发布计），不是**单次窗口内插入的记录数**；分配记录树叶容量 512 条（E148（提交固定点按两棵记录树重算） 几何），若单个窗口内插入的新分配记录数超过 `512 × 扇出（256）`，理论上一次窗口就能让树跳两层。⇒ **丙的「+1」是一个未经证明的启发式上界，不是推出来的界**。

**T8（准入那一刻看不看得到）**：三条臂在**它们各自定义要读的那个量**上都是可见的——甲读「上一次发布算出的值」（已经落盘/落内存的历史数据，可见）；乙读「当下内存里的即时值」（在制品状态，系统自己维护，可见）；丙读「上一次发布的高」（同甲，可见）。**T8 本身对三条臂不构成障碍**——三条臂都不要求读一个系统看不到的量。**真正的障碍在 (b)：没有任何一条臂的输入集合里包含『本次即将发生、但还没发生的固定点自身分裂』**，这不是「看不看得到」的问题（那个分裂此刻确实还没发生，逻辑上不可能被现在的状态看到），而是 ckpt_cost 定义本身的自指性——它要预支付「一个尚未运行、且其大小依赖于自身运行结果」的过程的成本。这与 C83（提交固定点没人回答） 里「固定点收敛性与轮数上界没人证过」是同一类问题的另一面：C83 问的是「收敛不收敛、几轮」，这里问的是「收敛之后会不会多长一层」。

**T6 结论**：甲在 (a)(b) 两类场景都命中，命中面最宽（整个窗口都可能触发）；乙只在 (b) 命中，命中面收窄到「本次 checkpoint 固定点自身收敛过程」这一狭窄时间片；丙进一步收窄，只在「(b) 且单次窗口/单次固定点让某棵树多长超过 1 层」时命中——**三条臂都有可构造的失败序列，不是「三条都不中」也不是「只中一两条就让另一条免检」，而是命中面递减的三档**。按背景材料预注册的决策逻辑「T6 三条臂都中 ⇒ 不分辨臂，把『公式要加分裂项』立成新欠账，臂按 T8 / T9 判」——这条最接近本轮结论，但需要补一句：**三档命中面不同，不能因为「都中」就当成三条臂等价**；若要选一条写回，按 T8（三者可见性相同，不构成分辨依据）与 T9（连带，见下）的字面文本，丙动的已定条款最少（不像丙-问一那样直接推翻一句用户定案，问二的丙只是加一个安全余量，不推翻「每次发布按当时的树高重算」这句用户定案本身，只是把「当时」读成「上一次发布」而不是「这次发布开始」，这本身已经比甲更保守，也没有精确到乙的「即时」）。

## 10. 问二 T9：每条臂动了哪些已定条款（只报）

D28（挂载期承诺量） 已定项 4「每次发布按当时的树高重算」（`28-挂载期承诺量.md:100`）是用户定案（premise 十三；用户定案原话「按当时的结构现算」）。三条臂对「当时」的读法：

- **甲**（「发布开始」读一次，窗口内不变）：把「当时」窄读成「上一次发布完成的那一刻」，与「每次发布按当时的树高重算」这句字面有出入——它不是「这次发布时重算」，是「上一次发布时算好、这次沿用」。**动了「按当时」这半句的字面意思，但没有明说是推翻还是另一种解释**。
- **乙**（即时更新，「准入每次读当下的值」）：最贴近「按当时」的字面——每次准入决策时读的都是那一刻的真实高度。**不推翻任何已定条款字面**，是最直接的字面实现，但如 T6 (b) 所述，「当时」本身对「固定点自身尚未运行的这一部分」是不可定义的（自指）。
- **丙**（上一次发布的高 + 1 层余量）：与甲一样把「当时」读成「上一次发布」，额外加了一个不在已定条款文字里的「+1 余量」，**这是在用户定案之外新增了一条安全边际，没有条款依据**（也没有被推翻——它只是加了保守性，不改变「按当时的树高」这句话对「树高」本身的读法）。

三条臂都没有动 D28（挂载期承诺量） 已定项 1 的分界句或 D5（快照 / 空间记账机制） 已定项 4 的逐项对照表——问二的三条臂只影响 ckpt_cost **这一个数怎么算**，不影响它在准入不等式里的**归属**（那是问一的范围）。

## 11. 问二 T10：每条臂一条会红的检查（含判别力自证）

**检查落点**：同样是未来的准入/固定点模块。检查形态是「对拍」——比较「admission 那一刻算出的 ckpt_cost」与「紧接着那次固定点实际分配的块数」，蕴含：

```rust
// 对每个候选 arm ∈ {甲, 乙, 丙}：
// 构造一段操作序列（含至少一次会让某棵记录树根分裂的插入批次），
// 在序列末尾触发一次 checkpoint，断言：
//   arm_computed_ckpt_cost_at_admission_time >= actual_fixed_point_blocks_allocated
```

**判别力自证**：三个见证序列，分别命中 (a)(b)(c)：

1. **见证 (a)**（窗口分裂）：分配记录树初始高 3，窗口内插入恰好数量的记录使其分裂到高 4，随后触发 checkpoint。断言应对**甲**判红（甲的 ckpt_cost 停在高 3 算出的值）、对**乙/丙**判绿（两者都在分裂发生后立刻/在下一次发布起点前更新了高度）。
2. **见证 (b)**（固定点自身分裂）：分配记录树叶恰好差 1 条记录就会溢出分裂，窗口内不触发这次分裂，但本次 checkpoint 固定点自己新增的记账/分配记录反馈恰好补上那一条、触发分裂。断言应对**甲、乙**都判红（两者的 admission 时刻都在分裂之前，读到的都是分裂前的高），对**丙**判绿（若「+1」余量恰好覆盖这一层）。
3. **见证反例（丙的边界）**：把见证 (b) 的记录数放大成「一次窗口内插入的记录数足以让树连跳两层」（例如超过 `512×256` 条），断言此时**丙也判红**——证明「+1」余量不是万能上界，检查的判别力延伸到丙自己的失效边界，不是只测「丙比甲乙强」这一个方向。

**检查本身先证明会红**：把候选实现临时改成「甲」的读法（发布开始读一次），跑见证 1、2，两者都必须由绿转红；改回「乙」，见证 1 转绿、见证 2 仍红；改成「丙」，见证 1、2 都转绿，见证 3（放大版）转红。这一串「颜色随实现切换」的记录，就是这条检查判别力的证据。

**什么现象会推翻它**：如果实现层面证明「一次窗口内插入的记录数」有一个远小于 `512×256` 的硬上界（比如被某个尚未读到的批处理大小限制钳死），见证 3 可能构造不出来，需要重新找放大见证。

## 12. 汇总：按背景材料预注册的决策逻辑收口

**问一**（背景材料「四」的分支逻辑）：T1 显示甲在对称盘上就出局，不满足「T1 三条臂都不中 ⇒ 维持甲」；也不满足「T1 中甲而不中丙 ⇒ 甲出局，乙丙按 T1/T2 判」——因为乙丙在**非对称盘**上与甲一样出局。**最贴近的分支是「T1 三条臂都中 ⇒ 不分辨臂，病根在共用前提，先立欠账，判臂只看分辨得出臂的格」**：三条臂在对称盘上确实分辨（甲 vs 乙/丙），但在非对称盘上不分辨（三者一起错）——**病根不是「需求」口径没定（那个空白只影响出局的宽窄，不影响出不出局），而是 `可用 = Σ设备(...)` 这个准入式子本身的结构（标量求和）不能表达逐设备下限**。这件事影响的不止 checkpoint 保留池一项——D28（挂载期承诺量） 已定项 1 括号里六项（含切换预留、被抛弃根独占量）全都是「按设备求和」进同一个标量，理论上都有 3.2 那种「富余盘掩盖吃紧盘」的暴露；只是切换预留额外有 E141 建的独立逐设备挂载判定兜底（D2（RAID 条带策略） 已定项 13），checkpoint 保留池没有——这正是 C355 题面本身指出的不对称（premise 九）。⇒ 建议交用户的问题不是「甲/乙/丙选哪个」，而是「checkpoint 保留池要不要比照切换预留，也在挂载/固定点触发时加一条独立的逐设备判定，而不仅仅是准入式子里的一项系数选择」。

**问二**：T6 显示三条臂命中面递减但都有失败序列，符合背景材料「T6 三条臂都中（分裂让公式本身少算）⇒ 不分辨臂，把『公式要加分裂项』立成新欠账，臂按 T8/T9 判」这一支——按 T8（三者可见性相同，不构成分辨）与 T9（丙对已定条款字面的偏离最小，只加保守余量、不改变归属或推翻用户定案），**丙是三者里字面代价最小、命中面最窄的写回选择，但它依赖的「至多一层」假设需要单独建一个上界证明（或至少一条运行时检查兜底：固定点跑完之后，若实际分裂层数超过余量，运行时判红——即 C83（提交固定点没人回答） 式的读数检查思路，用在这里）**。这条不需要交用户改「按当时的树高重算」这句用户定案本身，是在保留量的算法细节上补一个安全边际，按 `.claude/rules/fs-design.md`「判据写不出来时，先只做一条，而且先做慢而正确的那条」的精神，比 C363 今天什么都没有更安全。

**两问共同的欠账建议**（不新建欠账条目，留给主 agent 判断是否登记）：checkpoint 保留池目前只活在 D28（挂载期承诺量） 已定项 1 的池级标量里，**没有任何一条独立于该标量的逐设备/逐时刻校验**——这是 C355 与 C363 共同的病根：C355 缺的是「空间维度」上的逐设备核验，C363 缺的是「时间维度」上的（分裂前后）核验，但两者都是同一句话的两个方向：**「池级标量 + 一次性现算」这个形态，天生无法表达「每块盘、每一刻都够」这个要求**。
