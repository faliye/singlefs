# C103（容器索引无落点）的收口候选：它就是中央映射对码 3 容器那一类的投影

## 为什么现在才问得动这一格

C103 从 2026-09-04 立到今天一直挂着「先在 D3 或 D8 开一条分项」。
2026-09-06 当天定的两条把它的条件变了：

- **D19 已定项 5**（位置权威取混合）：**中央映射是解引用与释放判定的唯一入口**，
  位置条目降为提示。⇒ 仓里第一次有了一层「身份 → 物理落点」的通用间接层。
- **D2 已定项 14**（条带表按落点排）：条带表的叶是码 3 容器，
  而容器的物理指针由容器索引持有 ⇒ **C103 从「日后要还」变成 D9 未定项 9 的唯一挡路者**。

## 候选：容器索引不是第二棵树，它就是中央映射

**主张**：码 3 打包容器**本身就是一个对象**，按与普通单元完全相同的方式进中央映射。

**key 的对应**（D18 已定项 7 定的五元组 33 字节：标签 1 + 树 ID 8 + 对象 ID 8 + 对象出生代 8 + 锚点偏移 8）：

| 五元组的段 | 容器身份的段 | 出处 |
|---|---|---|
| 单元类型标签 1 | 码 3 + **打包记录类型**（折进同一个标签字节） | D18 已定项 11 的单元类登记表 |
| 树 ID 8 | 出生树 ID | C103 逐字 |
| 对象 ID 8 | **容器号** | C103 逐字 |
| 对象出生代 8 | 容器出生代 | C103 逐字 |
| 锚点偏移 8 | 恒 0 | 容器不是某个对象内的偏移 |

**value**：位置条目 × `w`，与其他单元完全一样（D19 已定项 5）。

⇒ **零新结构**。C103 那四问一次答完：住哪（住中央映射）、key 编码（同五元组）、
它自己的更新代价（与普通单元同）、它独占的 MAC 重建时怎么重算（与普通单元同）。

**一处要注意的排序差别**：C103 逐字要求「使 (树, 类型) 下最大容器号 O(log N) 可查——
容器号分配器的下一个号 = 最大号 + 1」。按上表折进标签之后，排序是
`(类型, 树, 容器号, 出生代)` 而不是 `(树, 类型, 容器号, 出生代)`；
前缀 `(类型, 树)` 仍然连续 ⇒ 那个 max 查询仍是 O(log N)。**分组顺序变了，查询能力没变。**

## 这一轮要打的五个面

1. **「容器是一个对象」这句话站不站得住。** D18 已定项 11 逐字说容器索引是
   「打包单元物理指针（与 MAC）的**唯一持有者**，别的树按身份引用容器」——
   若容器进中央映射，那句「唯一持有者」的主语就换了人。判：这是换个说法还是推翻它？
   ⚠️ 还有一个已知例外：**类型 4（实例表）的物理指针由根记录直接持有**（D18 已定项 11 逐字），
   它进不进中央映射？不进的话中央映射就不是「唯一入口」了（D19 已定项 5 逐字）。
2. **标签字节装不装得下。** 单元类登记表今天有几个码、打包记录类型有几种、
   折进一个字节之后还剩多少空位？给算式。若装不下，这条候选当场作废。
3. **自举。** 中央映射自己也是一棵树，它的节点是不是也要进中央映射？
   在哪一层收敛？⚠️ 这正是 E106 实测过的那个形状（池刚建好时条带表落在自己描述的条带里，
   五个种子全中不可解格恒 1）——判它在这里会不会重演。
4. **扫描重建。** 中央映射按 D9 已定项 7 采用的读法是**派生态、重建源是单元自描述**。
   容器进去之后，重建要从码 3 容器的头里读出它的四元组——D18 已定项 11 的码 3 头带不带这四段？
   带不全就重建不出来。
5. **与 D2 已定项 14 的接缝。** 条带表按落点排、叶是码 3 容器；
   查一个落点要先过条带表（按落点点查）拿到容器身份，再过中央映射拿容器的物理指针
   ⇒ **两次点查**。判：这个链在分配准入那条路径上（`.claude/rules/fs-design.md` 第一格）付不付得起，
   以及它会不会绕回自己（查中央映射本身要不要先查条带表）。
