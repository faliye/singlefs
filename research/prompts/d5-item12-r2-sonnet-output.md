## 一、Q1：第一轮判决 1 复核——克隆头 7 步历史算不算按字面触发反向接受条款

### 1.1 条款前件逐字核对

第一轮反向接受条款原文（`_d5-item12-r1-background.md:50`，与判决引用一致）：

> 丙在 U1 被克隆头或跨头共享打中（纪元 txg 在克隆头上不唯一，或归属算错）⇒ 丙出局，在甲、乙之间按 U2 选。

这是一个「原因 → 结局」条款，原因分两支：(a) 克隆头 → 纪元 txg 在克隆头上不唯一；(b) 跨头共享 → 归属算错。逐字读，(a) 只要求「纪元 txg 在（某个）克隆头**上**不唯一」这个**现象**成立，没有要求这个现象的**成因**必须是克隆本身的机制（比如 origin 继承初始化那一步）。

### 1.2 核 D16 那句 permission，以及 7 步历史的机械正确性

`16-发布语义.md:85-86`（现查）：

```
（同一 checkpoint 内建两个快照是允许的：它们捕获同一状态、其间 deadlist 为空；
但 checker 里的「上一个快照」要用 `(txg, 快照 id)` 打破并列。）
```

这句允许「同一头在同一 checkpoint 内建两个快照」，且明写「其间 deadlist 为空」——这正是攻方腿 7 步历史（`d5-item12-r1-opus-output.md` 2.3 节）第 5 步之前的状态（头 13 在同一 checkpoint 内先后建出快照 14、15，中间没有任何删除）。这段历史合法，不违反任何已定条款。

我手算复核了这段历史的核心：头 13（克隆头）在同一 checkpoint 内先后建出快照 14（`prev=1`，继承自克隆初始化）、15（`prev=2`，等于 14 自己的 txg）；建完两者之后头 13 自己的 `previous_snapshot_txg` 也是 2。**丙（材料定义，点读法）的键是 `(头树ID, 纪元txg, 映射key)`**，纪元字段是「块被杀那一刻头的 `previous_snapshot_txg`」——头 13 现在的纪元与快照 15 的纪元字段值**都是 2**，两者的键前两段完全相同。销毁 14 时，「下一侧」按 `next_owner` 规则是 15，过滤 `(13, 2)` 那一段：这一段里既有本该继续受 15 保护的条目，也可能混进头当前正在累积的条目——判决无法把两者分开，触发多放。

### 1.3 我的判断：判决 1 的结局站得住，但归因需要改写

这段 7 步历史里，「涉事的头是克隆头」这件事**确实**满足条款字面（a）的现象描述——头 13 是克隆头，它自己此刻的纪元值与它名下一个快照的纪元值**不唯一**（都是 2）。按最窄的字面读法，条款触发，判决 1「丙按反向接受条款出局」站得住。

但我要指出：这不是「归因」意义上的克隆头特有问题。攻方腿自己的 2.1 节已经给出了**完全不涉及克隆**的 4 步历史（头 11，普通头，同一 checkpoint 建 S12、S13 两个快照），命中的是**同一型**故障——头当前纪元与它名下最后一个快照的纪元值相同。7 步历史只是把同一个故障**搬到了一个恰好也是克隆头的对象上**。真正的病根是「纪元 = prev 的 txg」这个**标量**在「同一头同一 checkpoint 建多个快照」时不唯一，与克隆机制（origin 继承、跨头共享）没有因果关系——攻方腿在 2.3 节末尾也自己写明了这一点（「我的判断（交主 agent）：这一击不是克隆特有的」）。

**这个重新归因不改变判决 1 的结局**（丙材料定义仍然在 U1 出局，因为即便不借条款、单看 U1 的通用判据「写出一段历史：某块被释放而仍被某个快照引用」，4 步非克隆历史已经独立满足），**但它直接决定了 Q2 该怎么判**：丙-区间、丙′ 真正要修的是「同 checkpoint 多快照共享纪元值」这个标量碰撞问题，不是什么「克隆特有」的问题——修复必须在**任意头**（克隆与否）上都成立，不能只在克隆头场景里验证。第五节的正面推导会验证这一点在普通头、克隆头两种场景下都成立。

**什么现象会推翻这个结论**：如果能找到一段历史，其故障**必须**依赖克隆本身的语义（origin 链接、跨头共享计数），且去掉克隆后该型故障就消失——那才说明条款的字面归因是对的，我的「重新归因」不成立。我没找到这样的历史；攻方腿也没有报告过这样的历史。

## 二、Q2：丙-区间算「只许收严」还是「新臂」

按 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「臂的定义也在『跑前写死』之列」那一节的三步逐条判：记一次输 / 只许收严 / 写明收严在哪。

### 2.1 记一次输

丙（材料定义，点读法）按 Q1 的结论确实在 U1 输了（4 步非克隆历史即可打中，克隆头 7 步历史是同型故障的另一个实例）。这一步没有争议，两条腿一致。

### 2.2 丙-区间在「非退化」情形下与丙逐字节一致——这是判「收严」的关键证据

丙的原定义（`_d5-item12-r2-background.md` §三，与 `d5-item12-r1-opus-output.md` 2.1 节引的材料定义一致）：「快照 S 的 deadlist = (头, `prev(S).txg`) 那一段」——这是**点匹配**：一个条目的纪元字段等于某个 S 的 `prev(S).txg` 才算它的。

丙-区间：「快照 X 的 deadlist = 纪元落在 `[prev(X).txg, X.txg)` 的全部条目」——**区间匹配**。

关键问题：在**没有同 checkpoint 姊妹快照**的正常情形下，这两种匹配规则给出的集合是否逐字节相同？我手算验证：头的 `previous_snapshot_txg` 只在「建快照」那一刻跳变（从旧值直接跳到新快照自己的 txg），跳变之间没有任何中间值——纪元字段在杀块那一刻只能取「当前 `previous_snapshot_txg`」这个**离散值**，不存在「取值恰好落在 `[prev(X), X.txg)` 内部但不等于任何端点」的条目。所以在正常情形下，`[prev(X).txg, X.txg)` 这个区间内**能出现的纪元值只有 `prev(X).txg` 一个**（因为下一次跳变直接到 X.txg，届时新条目改记到 X 名下的区间去了）——区间匹配退化为点匹配，两者给出**完全相同**的集合。

差别只出现在**退化情形**（同 checkpoint 姊妹快照，X.txg == prev(X).txg）：点匹配下这是一个「合法但有歧义」的桶（因为纪元值 == 某个已知端点，同时也可能等于紧邻的另一实体的纪元值）；区间匹配下 `[X.txg, X.txg)` 直接是空集——**不产生任何可能被误读的条目**，而不是「允许更多」。

**这正是「收严」的形态，不是「放宽」**：区间匹配对非退化情形一字不差地复刻点匹配，对退化情形把一个有歧义的非空集合收紧成空集（更少的东西可以被认领，不是更多）。反过来问「丙-区间比丙原定义少要求了什么」——我没找到：区间匹配的判定集合处处是点匹配判定集合的子集（退化处收紧、非退化处相等），从未出现区间匹配认领了点匹配不认领的条目。

### 2.3 但「做法」层面确有一处实质改变，必须单独交代——这是攻方腿自己也承认没测过的地方

丙原定义的销毁级联「按 `birth > prev(S).txg` 过滤出可释放的条目，`prev` 跟着传递」——正推腿在第一轮 §3 已经指出，这句话唯一自洽的读法是**物理改键**（把 S 自己名下的条目纪元段改写为新的边界值，使它们在「点匹配」体系下继续可被找到）。丙-区间「级联只放不改键」——级联时**完全不触碰任何条目的键**，只改「头 / 下一侧」的 `previous_snapshot_txg` 元数据本身，让区间的右端点自然位移，「自然盖住 S 原来那一段」。

这不是「点匹配规则上加一句限定」就能还原丙-区间的东西——它换了一种**维护协议**：从「物理合并」换成「边界元数据位移、条目原地不动」。这个换法本身**不影响 U1 判据**（下一节的复跑证明它在多代级联下仍然正确），但它是一处独立的、需要写进条款正文的「做法改变」，不能只用「多要求一句」来概括——我建议交用户裁决时明确说：丙-区间 = 「丙原定义在退化处收严」+「级联维护协议从物理改键换成边界元数据位移（新做法，需要独立验证，不是丙原定义『少做了一步』）」。

### 2.4 复跑验证：级联维护协议在多代连续销毁下正确

我用只读复制的 `dlmodel.py`（`BING_R` 已经实现区间读法）跑了一条自建历史：头 11 连续建 4 个快照 S12..S15，每次建之前各写一个块并立刻杀掉（依次落进 4 个不同纪元段），然后**连续销毁 S12、S13、S14 三代**（触发三次级联传递）。结果（第六节附完整 `replay` 输出）：

- 每一步 `checker=[]`（vector / i36 / c195 / decode 四道检查全程不红）、`over=[]`、`leak=[]`；
- `dl=` 那一列显示**每个存活条目的键从建立到被释放为止从未改变**——`(11, 2, ...)`、`(11, 3, ...)`、`(11, 4, ...)` 三段条目在 S12、S13 依次被销毁的过程中原样保留，只有 `ps=`（各快照记录的 `prev`）在逐代继承传递，直到条目真正满足 `birth > prev` 才被删除释放。

这与丙原定义（正推腿 §3.1 算出的「甲要重写 S 自己积累的全部历史，丙-区间连 next 桶都不用碰」）形成对照：丙-区间的销毁改写量**在三代连续销毁下始终是 0**，与第一轮 opus 模型的 U2 几何测量（G2/G5 几何下 `丙-区间` 改写恒 0）逐字节一致。

### 2.5 我的判决

**丙-区间是「只许收严」的合法收严，不是新臂**——但收严的完整表述必须同时包含 2.2 的「区间收紧退化情形」与 2.3 的「维护协议改用边界位移」两部分；只写前一半会让人误以为丙-区间只是「丙加一句限定」，掩盖了它同时也换了一种从未被验证过的维护机制这件事。**因此，虽然定性为「收严」，它仍然需要本轮的攻击面全覆盖**（第五节的 U1 正面推导覆盖了级联做到一半崩溃之外的三项；崩溃与分批交错仍是模型层零覆盖，见第五节结尾的诚实空白）。

**什么现象会推翻这个判决**：如果能找到一段（非退化）历史，区间匹配判定的集合与点匹配判定的集合不同——即区间匹配「认领」了点匹配不认领的条目，或者反过来点匹配认领的条目区间匹配漏认——那就说明 2.2 的等价性论证有洞，判决要改写成「新臂」。我在 2.4 的三代级联复跑里没有找到这样的差异。

## 四、Q4：丙′ 在杀块那一刻要「头的上一个快照的树 ID」，它从哪来、是不是 O(1)

### 4.1 材料定义的字面缺口

丙′ 的键需要「头被杀那一刻，头的上一个快照的**树 ID**」这个值（不是 txg）。树表条目（`08-核心索引结构.md:76`，已定项 8）里只有 `previous_snapshot_txg`（8 字节，一个 txg 标量），**没有任何字段存树 ID**。

### 4.2 从 `previous_snapshot_txg` 反推树 ID——我用模型验证了这条路走不通，不只是「慢」，是「歧义」

我用只读复制的 `dlmodel.py`（`BING_T` 已实现丙′，用 `pth`/`pts` 两个字典在内存里**增量**跟踪每个头 / 快照「上一个快照的树 ID」）构造了一段「同一头同 checkpoint 建两个快照」的历史（第六节附 `replay` 片段），核对模型内部状态：头 11 在同一 checkpoint 里先后建出 S12（`pts[12]=0`）、S13（`pts[13]=12`）——**两个快照的 `previous_snapshot_txg` 都是 1（同一个 txg），但它们「上一个快照的树 ID」分别是 0 和 12，彼此不同**；建完两者之后头 11 自己「上一个快照的树 ID」是 13。

这证明：**从持久化的 `previous_snapshot_txg`（值 1）出发，不可能唯一反推出「树 ID」**——txg=1 这个 checkpoint 里同一个头名下有两个快照（S12、S13），任何只按 txg 做的查询（不管是索引查找还是全表扫描）在这里都是**歧义**的，不是「慢一点」的问题。要正确反推，唯一的信息源是 D16 给的平局判别子「`(txg, 快照 id)`」——而「快照 id」本身就是树 ID，这意味着要正确解出「上一个快照的树 ID」，前提是**已经知道**这棵树的树 ID，逻辑上是循环的：你没法靠 txg 反查出你需要用来打破并列的那个东西。

即便不考虑歧义（假设从不出现同 checkpoint 双快照），单靠 `previous_snapshot_txg` 反推树 ID 也需要「按这个头的树 ID 前缀扫描树表、找 txg 匹配的那一条」，这是一次范围扫描，不是 O(1) 查找；模型里的 `pth`/`pts` 之所以是 O(1)，是因为它是一个**在内存里随每次建快照增量维护**的旁路值，而不是从持久化字段现算出来的。

### 4.3 结论：丙′ 的 O(1) 主张按字面不成立，反向接受条款触发，真实代价与乙同价

丙′ 要做到 O(1) 且不歧义，唯一出路是**把「头上一个快照的树 ID」也做成一个持久字段**——这正是本轮背景材料自己写死的反向接受条款：「丙′ 在 U2 被『杀块那一刻要按 txg 查上一个快照的树 ID、不是 O(1)』打中 ⇒ 交用户在『丙′ + 把那个树 ID 存进预留 8 字节』……与乙一样吃预留……」。按我 4.2 的复跑，这条条款**触发**，不是「可能触发」——按字面材料定义（不额外加字段）丙′ 既不 O(1) 也不无歧义；要修，必须吃预留 8 字节。

**这把丙′在 U3 的代价拉到与乙完全相同（8 字节）**——第三节的认购表里丙′不能再按「0 字节」计入，必须与乙同行：丙′ + C144 = 24，同样恰好吃满，同样挤掉 livelist 计数器、C272、C143 甲臂。**丙′相对乙唯一还剩的潜在优势只在 U1/U4**（见第五节），U3 上两者已经打平。

**额外一点，不影响本项判决但值得记一笔**：这个「树 ID 字段没有持久化」的缺口同时也是一个**崩溃重放/幂等性**风险——`KeySpace` 是集合语义，同一个键第二次插入天然折叠（不会双重计数），但这个保证的前提是「同一次逻辑上的杀块事件，在崩溃重放之后仍然算出同一个键」；如果丙′ 的树 ID 只靠内存增量维护、没有持久字段兜底，重放时重新算出的「纪元树 ID」在崩溃点落在同 checkpoint 双快照之间时**可能与原来不同**（4.2 的歧义），那么重放出的键就不是原键，集合折叠救不了它。这笔账落一条新欠账，交第五节。

**什么现象会推翻这个结论**：如果能给出一种从树表现有字段（不新增持久字段）就能在 O(1) 时间、无歧义地解出「头当前上一个快照的树 ID」的算法——比如证明「同 checkpoint 双快照」这个场景本身应该被禁止（但这与 D16:85 明文允许的条款冲突，改它是另一次重开）——那 4.3 的结论不成立。

## 五、Q5：三条臂的正面论证、检查、判别力自证、要改的 kb 正文

### 5.1 U1 正面推导——本轮要求的四个攻击面

按 §一判据表要求的四项，逐项交代（诚实标出模型能不能测）：

1. **级联做到一半崩溃**：当前 `dlmodel.py` 不模拟崩溃/journal 重放（第一轮攻方腿 §射程已自陈），我没有新工具能测这一项，**这不是「没打中」，是「测不了」**——与 D5 正文自己承认的「崩溃重放那一格仍然零覆盖」（`05-快照-空间记账机制.md:208` 附近，前提三 A3）是同一个模型层空白，三条臂共同欠着，不分辨臂。
2. **级联按意图分批（前提十六）并与另一次销毁 / 建快照 / 克隆交错**：模型里只有 `JiaBatched`（甲的拆批）实现了分批，乙 / 丙-区间 / 丙′ 都没有分批实现，我没有新写代码去测。但我可以做一个**结构性论证**：丙-区间的级联「不改任何条目的键」，只改 `prev` 元数据；如果要把「释放 K 条」这一步拆成若干批，唯一需要维护的进度状态是「已经释放到哪个 mapkey 了」——一个**单一游标**，不需要像甲拆批那样维护一份「哪些条目已经改键、哪些还没有」的待办清单（`JiaBatched.pending`）。这是因为丙-区间从不移动任何条目，中断在任何一点，**尚未处理的条目仍然停在它们本来的、正确的键上**，恢复时只要知道游标位置就能继续。乙（无论 min 还是 move）在批量合并时需要移动条目（改号），与甲同型，需要待办清单。**这是丙-区间在批处理可恢复性上比甲 / 乙更简单的正面理由**，但它没有被写成条款、也没有被测过，是本轮新发现、需要独立立项的欠账，不构成已验证的结论。
3. **克隆与给克隆建快照落在 origin 那个 checkpoint 里（`C1.txg == origin.txg`）**：我读代码论证这个历史**在当前模型 / 格式约束下不可达**——克隆操作（`C`）要求 origin 是一个已经存在的快照（`world.alive_snaps()` 里的成员），而快照只能通过 `P`/`PS`/`PSS` 这类会立即把 `world.txg` 推进到下一个值的操作产生；所以「克隆」发生时，当前开放 checkpoint 的号**已经**严格大于 origin 的 txg，之后给克隆头建的第一个快照，其 txg 只可能 ≥ origin.txg + 1，永远不可能等于 origin.txg。这个约束的机制根源是 D16 新规则 1：「快照发布点必须与 checkpoint 边界对齐」——克隆同样是结构性变更，必须挂在某次 checkpoint 关闭动作上，而 origin 必须先被关闭发布过才能被克隆，两次关闭不可能是同一次。**这不是「没测到」，是这条攻击面本身是空集**——第一轮攻方腿把它记成「没量的」（`d5-item12-r1-opus-output.md` 2.3 节），我的结论是它不需要量，因为它不可能发生。
4. **同一个头第二次杀同一块**：在没有崩溃重放的正常语义下，一个块一旦被杀（从头的活集合移出）就不可能再被同一个头杀第二次（模型 `legal_ops` 只对 `live` 集合里的块提供 `K` 操作）；唯一可能出现「同一个逻辑杀块事件被处理两次」的场景是**崩溃重放**（同一条 journal 记录被重放执行了两次）。我复核了三条臂共用的底层结构 `KeySpace.insert`（现查 `dlmodel.py` 第 85-88 行）：它是**集合语义**，同一个键第二次插入直接折叠（`self.entries[key] = None`，不产生第二条记录），**天然幂等**。三条臂的键都是「(头 / 归属, 纪元或号) + 映射 key」的确定性函数——只要重放时头当前的纪元 / 号状态与原来相同，键就相同，插入天然幂等，不会产生 D5 正文担心的「多重集相加，同一条目追加两次 ⇒ 销毁时双重释放」（该风险针对的是「多重集」实现，三条候选臂都不是多重集，是键的集合，这条风险对它们结构性不成立）。**唯一的隐患是丙′**：它的「纪元」值（树 ID）如果只靠内存增量维护、没有持久字段兜底（4.2/4.3），重放时重新算出的纪元值可能与原来不同（歧义），那时键不同，「幂等」这个保证就不成立了——这再一次印证 Q4 的结论：丙′ 没有持久字段兜底，不只是 U2 O(1) 出问题，连基本的幂等性都靠不住。
