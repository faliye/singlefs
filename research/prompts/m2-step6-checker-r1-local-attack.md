SINGLEFS SECOND TRANSACTION MILESTONE, POOL CHECKER STEP SIX, TWO NEW KNOWN BAD IMAGES FOR RECENT GENERATION INVARIANTS

Background, the pool and its root ring

Singlefs is a copy on write filesystem under design. Its on disk pool keeps a fixed size ring of root records, one slot per generation, spread across two devices, called device 0 and device 1. Each root record names a checkpoint transaction generation number, written here as txg, together with an instance generation number. A pool level checker walks the on disk image starting from these root records and reports, for a fixed list of named invariants, whether each one holds, is violated, or is not applicable to this particular image.

Each root record directly carries, as three separate fields inside that same record, a pointer to that generation's own tree table, a pointer to that generation's own instance table, and a pointer to that generation's own central mapping tree root. Nothing in a root record is shared by reference with any other root record's own copy of these three pointer fields. Publishing a new transaction writes a completely new root record. If that transaction changes what a pointer field should point to, the new root record carries the new pointer value, while any older root records that were already persisted keep whatever pointer value they were written with.

Background, the rollback candidate set

A separate value carried by every root record, written here as the rollback floor F, together with a value derived from the whole ring, written here as effective floor, together with an instance table that can mark some earlier roots as abandoned, together define a subset of the roots in the ring called the rollback candidate set. A root belongs to the rollback candidate set if and only if both of the following hold. First, it is judged valid according to the instance table: this holds if the instance table has no row at all for that root's own instance, or if it has a row for that instance whose recorded value, call it W, is greater than or equal to that root's own checkpoint_txg. Second, that root's own checkpoint_txg is greater than or equal to effective floor. Nothing in this definition singles out or excludes the newest root in the ring: if the newest root itself satisfies both of these two conditions, it is, by this wording, also a member of the rollback candidate set. Nothing in this definition states any minimum number of roots the candidate set must contain.

Definition, invariant I-7.4, near K generations blocks not reused

For every root in the rollback candidate set, every block that root references must have a physical range that has not been reallocated to any other object, and must not have had its header erased by a sweep. The phrase recent generations, in this invariant's name, refers to exactly this candidate set: under normal conditions, when the rollback floor F has not been raised, the candidate set is the whole root ring; under disk pressure, once F is raised, the candidate set narrows, down to as few as the most recent four rollback reachable states, while still always including each device's own newest persisted valid root.

Definition, invariant I-4.8, near K generations roots checksum self consistent

After any crash point replay, starting a walk from any one root in the rollback candidate set, every block's checksum must be consistent with what that block's parent pointer records. This invariant's discriminating power is to catch the case where a block that was freed within the current transaction gets reallocated and overwritten with new content: that would make an older root, one whose stored pointer still expects the old content, into a false rollback candidate, and checking only the very newest generation root would never catch this on its own.

Facts about how the checker evaluates these two invariants

The checker first finds the newest root in the ring, by comparing checkpoint_txg and then instance number, and walks only that root by itself. It records how many walk failures that single walk produced, call this list the newest walk's failures. Separately, and only using data available at that point, before anything else has been walked, it makes one judgement call naming invariant I-4.8, whose true or false value is: the newest walk's failures list is empty, and the running total of how many times invariant I-2.1 has been judged violated so far is zero. This judgement call does not name invariant I-7.4 at all. Invariant I-7.2, a different invariant meaning the newest root can be completely walked, is judged later using the same newest walk's failures list: it holds if that list is empty.

After that, the checker loops over every other root in the ring, in some fixed order, skipping the newest root itself. For each such root, it first checks two conditions using the instance table and the rollback floor: whether that root is abandoned according to the instance table's rows, and whether that root's own checkpoint_txg is below the newest root's own rollback floor F value. A root that is abandoned, or whose checkpoint_txg is below that floor, is skipped and never walked in this loop. Every other root reaches this point and is called an older candidate. For each older candidate, the checker first records the running total of I-2.1 violations and the running total length of the overall walk failures list, before walking this older candidate. It then walks this older candidate root. After that walk finishes, it compares: if the running total of I-2.1 violations has grown compared to before this candidate's walk, or if the walk failures list has grown longer compared to before this candidate's walk, it treats this as a single true or false signal meaning this candidate root's walk ran into a unit that has been reused or had its header erased. It then makes two separate judgement calls, one naming invariant I-7.4 and one naming invariant I-4.8, and both of these two calls use the exact same true or false signal, computed from the exact same before and after comparison, for the same older candidate root, in the same pass through the loop.

After the loop over all older candidates finishes, the checker counts how many roots actually reached the older candidate step inside that loop. If that count came out to zero, meaning no root other than the newest one qualified as an older candidate, the checker makes exactly one more call: it marks invariant I-7.4 as not applicable, giving as its reason that the candidate set only had the newest root in it, with no older root available to judge. It makes no similar not applicable call for invariant I-4.8 in that situation.

Facts about how a judgement's final verdict is decided

Across one full run of the checker, each named invariant accumulates a count of how many separate judgement calls named it, and, separately, whether any of those calls found the condition false. The very first call that finds the condition false has its description kept as the recorded violation detail; any later calls for the same invariant name that also find the condition false only add to a running violation count, they do not replace the first recorded detail. When the checker finishes and reports its final verdict on one invariant, it reports that invariant as violated if any call, across the whole run, ever found it false. If no call ever found it false, it reports that invariant as holding, provided at least one judgement call named that invariant during the run. If no judgement call ever named that invariant during the whole run, it is reported as not applicable, using whatever reason string, if any, was separately registered for that invariant name through the not applicable mechanism described above.

Facts about how a referenced unit's checksum is actually checked

A separate piece of code is responsible for reading any one unit that is referenced from somewhere else through a pointer. That pointer carries two location entries, one for device 0 and one for device 1, and each location entry separately carries a checksum value that was computed and stored inside that location entry at the time the location entry itself was written. For each of the two location entries, this code reads the actual bytes currently present at that device and that slot, computes a checksum over those actual bytes, and compares that freshly computed checksum against the checksum value stored inside the location entry. It makes a judgement call naming invariant I-2.1 for every one of these two comparisons, one call per location entry, regardless of whether that comparison matched or not. It returns the content of the first location entry whose freshly computed checksum matched, or returns nothing at all if neither of the two location entries' freshly computed checksums matched. This code never inspects the referenced unit's own internal header fields, and never checks whether the unit's own internally stored self checksums are self consistent; the only comparison it ever makes is between the freshly computed checksum of whatever bytes are actually present on disk right now, and the checksum value that was stored inside the referencing location entry back when that location entry was written.

Facts about the two new bad images

Both new bad images start from the same clean image and target the same single unit, a 16384 byte unit that mkfs originally wrote, called here the genesis tree table unit. A comment attached to the test code that builds these bad images states that after the first published file replaces this unit, only the two generation zero roots still reference it.

The first new bad image, meant to trigger invariant I-7.4, works as follows. It reads the current 16384 bytes of the genesis tree table unit from device 0. It changes one 8 byte field, at byte offset 42 inside that unit, to a new value. It then recomputes that unit's own internal header checksum and payload checksum fields so that the unit becomes internally self consistent with its new content: reading the unit on its own and checking only its own internal self checksums would show nothing wrong. It writes this modified, resealed content to the same slot on both device 0 and device 1, identically. It does not touch, anywhere else on the image, any location entry that points to this unit, so whatever location entries elsewhere on the image still reference this unit still carry the original checksum value that was computed and stored back when the unit held its original, unmodified content.

The second new bad image, meant to trigger invariant I-4.8, works as follows. It overwrites the entire 16384 bytes of the same genesis tree table unit with zero bytes. It does not recompute or reseal anything: the unit's own internal header fields and payload checksum fields are left as all zero, which does not match whatever internal format a genuine unit header of this kind is supposed to have. It writes these all zero bytes to the same slot on both device 0 and device 1, identically. Just as with the first bad image, it does not touch any location entry elsewhere on the image, so whatever location entries reference this unit still carry the original checksum value from before this unit was zeroed out.

The only check this project's own test suite makes on each of these two bad images is that, on that particular mutated image, the one invariant that image is meant to target is reported as violated. The test suite does not check, on the I-7.4 image, what verdict invariant I-4.8 receives. It does not check, on the I-4.8 image, what verdict invariant I-7.4 receives. It does not check what verdict either image produces for any other invariant, including I-7.2.

Facts about the specific pool this bad image test builds

This bad image test builds its clean starting image using a fixed sequence of steps, in this order: make the filesystem, acquire an instance number, warm up, publish the first file. The code describes warm up as two publishes that do not add any user visible content. Given how generation numbers are assigned in order, the two warm up publishes become the roots at checkpoint_txg 1 and checkpoint_txg 2, and the first file publish becomes the root at checkpoint_txg 3. The root at checkpoint_txg 3 is called A throughout the rest of this material. At the point where this clean image is handed to the checker, A is the newest root in the ring, and the two warm up roots, at checkpoint_txg 1 and 2, are the only two other roots present.

This entire pool only goes through what this project calls the first transaction. A separate part of this project's own records states plainly that during the first transaction, the rollback floor F carried by every root record is always zero, because at that point there are fewer than four non empty valid roots in the ring. There has been no rollback anywhere in this pool's history, so nothing in the instance table marks any root as abandoned. Given the facts above about how the older candidate loop works, this means, for this specific clean pool, that both of the two warm up roots, at checkpoint_txg 1 and 2, would reach the older candidate step in the loop described above, so the count of older candidates in this specific pool comes out to two, not zero.

Two of the questions below, questions 5 and 6, describe a different, hypothetical situation, where the rollback floor F has been raised far enough that the count of older candidates comes out to zero. That hypothetical situation is not what this specific fixed pool, as just described, actually produces; it is a separate scenario about the checker's general behavior.
