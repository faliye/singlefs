## 第 1 问：候选㈡ 与已定条款的相容性，逐条核

### 1.1 与 D2（RAID 条带策略） 已定项 16 / 17 的关系：不冲突，因为两者管的是不同的写入层

**条款原文**（`.claude/kb/decisions/02-RAID条带策略.md:65-66`，整行抄）：

```
| 16 | **不发出小于 `io_min` 的写** | **已定（2026-08-28）**：向一个设备物理映射单元里发一次更小的写，设备内部会做 read-modify-write。在 Linux 上这个量是 `io_min`，不是 `physical_block_size`；两个量不许合成一句话。正文见 D2（RAID 条带策略）「写的粒度：不发出小于设备物理映射单元的写（已定，2026-08-28）」。⚠️ **它与三条已定条款打架，冲突记在 C212（固定结构的写小于 io_min）**：根槽宽、journal 记录宽、超级块槽宽都不是按 `io_min` 定的。⚠️ **本项 2026-09-10 补编号，条款本身一个字没改**——补编号的理由是它此前住在「### 已定项」之前、没有分项号，于是按分项走的七个门禁阶段（21 / 22 / 24 / 28 / 29 / 31 / 60）对它整个是盲的（C212（固定结构的写小于 io_min） 逐字）。 **状态：已定。** |
| 17 | **不让两个生命周期不同的对象共享同一个物理映射单元** | **已定（2026-08-28）**：理由同已定项 16。正文见 D2（RAID 条带策略）「写的粒度：不发出小于设备物理映射单元的写（已定，2026-08-28）」。⚠️ **「生命周期不同」按什么判，这一条一个字没写**——那一半是 D2（RAID 条带策略） 未定项 15。⚠️ **本项 2026-09-10 补编号，条款本身一个字没改**，理由同已定项 16。 **状态：已定。** |
```

依据句（`.claude/kb/decisions/02-RAID条带策略.md:28-29`，整行抄）：

```
依据：D22（单元原子性怎么合成） 反推 C 暴露的一处——「我们不做 read-modify-write」
覆盖不到「我们不诱发设备做 read-modify-write」。
```

**判定：不冲突。**

这两条分项管的是**设备物理层的写粒度**——向一个已经持久着别的数据的
`io_min` 物理映射单元发一次更小的写，让设备内部做 RMW，从而可能损坏该单元里
**已经落盘、且不是这次写目标**的邻居字节。依据句自己把这条边界划得很清楚：
它补的是"我们不做 RMW"（逻辑层，指本工程从不原地覆写已发布的旧数据）
**覆盖不到**"不诱发设备做 RMW"（物理层）这道缝，两者本来就是两个不同的层。

候选㈡ 的"读改写"发生在**逻辑 / 树语义层**：往中央映射某个 key 的 value 里追加一个
新版本链节点，语义上要先读旧的链、算出新的完整链、再把这个新值交给树。但这棵树
（D8（核心索引结构）「结构」一节，`.claude/kb/decisions/08-核心索引结构.md:7-16`）本身是
COW + 日志结构节点：

```
| 日志结构节点 | 节点内新 key 追加不插入，内存里定期重排；写顺序、可在只读锁下回写 |
```

也就是说，无论这次是候选㈠ 的"插入一条新 key"还是候选㈡ 的"改写一条旧 key 的 value"，
落到物理层的操作都是同一件事：**COW 出一个新的整节点**（`NODE_BYTES = 16384`，
D8（核心索引结构） 已定项 2），写到一个新的物理位置，旧节点整体作废等待回收。这个新节点
**不会**去动那个正被别的、生命周期不同的对象占用的旧物理位置——旧位置上的邻居数据
根本没有被触碰，谈不上"发一次小于 `io_min` 的写把它连带损坏"。而 16 KiB 的整节点写，
在 Linux 常见的 `io_min`（多数 NVMe 在 512 B–4 KiB 量级；`io_min` 的定义与推导见
D2（RAID 条带策略）「写的粒度」一节现查 `drivers/nvme/host/core.c:2126-2143` 那段）之上有
至少 4 倍余量，本来就不落在已定项 16 管的那类写里。

**这不是候选㈡ 独有的豁免**：候选㈠ 同样要 COW 整节点。已定项 16/17 已知打架的三条
（根槽宽、journal 记录宽、超级块槽宽，登记在 C212（固定结构的写小于 io_min）——
材料未要求我复核 C212，指路不展开）都是**不走 COW 树、原地覆写固定槽位**的结构；
中央映射不属于这一类，两条候选都不属于。

⚠️ 一个真实但不属于"冲突"的代价：候选㈡ 若被采纳，值宽度非纯数字（"无上界"），
落进门禁阶段 39（`.claude/gate.d/39-field-table-sum.sh`）"表里只要有一行宽度不是纯数字…
整张表跳过并计入跳过数"那条既有豁免分支（`.claude/gate.d/39-field-table-sum.sh:15-17`）——
与"未定"字段today）同等处理，**不构成新的机械冲突**，但意味着这张字段表以后永远
排不进 C94（登记的格式常量与后来的定案对不上）要的逐字段可加总口径。这是一项
门禁覆盖率代价，不是不相容。

### 1.2 与 D8（核心索引结构） 已定项 1（记账取幂等完整值）的关系：不冲突，且候选㈡ 描述的形态本来就是它偏好的那一种

**条款原文**（`.claude/kb/decisions/08-核心索引结构.md:69`，索引行，整行抄）：

```
| 1 | **记账怎么表达成幂等完整值** | **已定（2026-08-29，用户定案）：取幂等完整值，接受 key 数量上升** | D8（核心索引结构）「已定项 1」 **状态：已定。** |
```

正文首句（`.claude/kb/decisions/08-核心索引结构.md:78-80`，整行抄）：

```
### 已定项 1（2026-08-29，用户定案）：取幂等完整值，接受 key 数量上升

**记账条目一律是「某个统计量在某一代的完整值」**，写入时整格覆盖，合并规则「后者胜」；**不用增量 Δ**。
```

**判定：不冲突。字面射程本来就不覆盖中央映射，而且候选㈡ 如果要成立，天然会落在这条偏好的那一侧。**

先看射程：条款的主语是"记账条目"（D5（快照 / 空间记账机制） 的计数器 / 统计量），
不是"中央映射条目"——这条分项 2026-08-29 定案时，D19（块指针的结构与宽度预算） 已定项 5
（中央映射是权威入口）2026-09-06 才定，D19（块指针的结构与宽度预算） 未定项 6 更是
2026-09-08 才升格出来，字面上够不着中央映射。

再看它反对的那个东西是什么：它反对的是**增量 Δ**——单条记录本身只是一次"+N"或
"-N"，checker 要重放同一套累加函数才能拿到真值，从而让 checker 与运行时共用同一段
判定代码、判别力归零（依据 E14（I-3.1 的判别力：幂等完整值 vs 增量 Δ），
`.claude/kb/experiments/14-I-3.1的判别力幂等完整值vs增量Δ.md:20-30`，实测幂等完整值形态
3/4 类真 bug 全抓、增量 Δ 形态 0/4）。候选㈡ 描述的"版本链"，按材料给的定义
（"value 存版本链，链长 = 活快照数 + 1"）**每次写入的是完整链本身**，不是"在旧链上
加一个 Δ 记录、靠运行时和 checker 各自重放同一个合并函数去拼出链"——candidate ㈡
若要立得住，写出去的 value 必须是"这一刻这个 key 完整版本链的目标态"，checker 直接
读这个值就能验证，不需要重放任何累加逻辑。这正是已定项 1 定义的"幂等完整值"那一侧，
不是它否决的"增量 Δ"那一侧。

⚠️ 这里必须把两件事分开，材料没有明确区分、容易混淆：
"写路径要不要先读旧值才能算出新值"（候选㈡ 的操作性成本，真实存在）
**不等于**"盘上存的是不是 Δ"（已定项 1 判的对象）。B-tree 本身无论插入还是修改都要
先遍历定位，候选㈠ 同样要"读"树结构才能找到插入点——差别只在候选㈠ 不需要读
**目标 key 已有的 value 内容**，候选㈡ 需要。这是一项真实的写路径依赖成本，但它不落在
已定项 1 判的"盘上是不是 Δ"这条线上；把它算作代价，应该算进"欠的账②"或另立一笔
写路径依赖成本，而不是判它违反已定项 1。

### 1.3 与 D23（journal 的角色与格式）的关系：不冲突，因为 journal 只记指针层目标态，管不到叶内条目怎么变

**条款原文**（`.claude/kb/decisions/23-journal的角色与格式.md:5-9`，整行抄）：

```
**方向已定：journal 记录承载「指针层的目标态」，不是逻辑意图，也不是全量物理重做。**
单元由 COW 写到各自最终位置并自带校验和（D22（单元原子性怎么合成） 分界线里「COW + D4（校验和位置） 够」那一类），
journal 只记「哪些子树根换到了哪个块 + 新根」。

**由此得到一条写路径的硬顺序：分配先于 journal。**
journal 记录不是「事务的全部」，是「**已经写到盘上的东西的发布指令**」。
```

**判定：不冲突。**

D23（journal 的角色与格式） 明确把 journal 的记录粒度钉在"子树根指针换到了哪个块"
这一层，**不下探到叶节点内部的条目是插入还是修改**。中央映射的叶节点无论走候选㈠
还是候选㈡，一次修改的落盘结果都是"COW 出一个新叶节点（和它往上的路径），
换一个新的子树根"——journal 只需要记这一条根指针的目标态，天然对叶内是插入还是
"读改写"语义一致，这也是材料未定项 5 正文已经写明的那条依据
（`.claude/kb/decisions/19-块指针的结构与宽度预算.md:108-131`，材料附录已整段抄，
不重复摘句；其中"中央映射 COW 一条路径 + 它自己的一个根槽"那句正是这个机制的运行时代价来源）。

顺带核了 D23（journal 的角色与格式） 表里"重放要不要分配器"与"幂等"两行
（`.claude/kb/decisions/23-journal的角色与格式.md:16-17`）：候选㈡ 落盘的 value
只要是完整链（见 1.2），重放同一条"指针层目标态"记录两次结果相同，满足
`.claude/kb/decisions/23-journal的角色与格式.md:825`"每条 journal 记录的重放必须幂等"
这条硬要求（整行抄）：

```
> **每条 journal 记录的重放必须幂等**——同一条记录被重放两次与重放一次，结果相同。
```

```
|---|---|
| 独立 keyspace | 每类数据一棵树（extent / inode / dirent / 反向索引 / 空闲空间 / 记账 …），互不干扰 |
| 日志结构节点 | 节点内新 key 追加不插入，内存里定期重排；写顺序、可在只读锁下回写 |
```

D5（快照 / 空间记账机制） 已定快照数无上界（`.claude/kb/decisions/05-快照-空间记账机制.md:406`，
本仓当前版本，整行抄——与材料附录抄录的措辞有一处出入，见文末"一处版本差异"）：

```
| 树 ID | **8** | **自由选择**。上界一条已定条款都指不到（D6（快照实现模型） 定每个可写头一棵自己的树、快照数无上界）⇒ **不许拿一个窄宽度去制造一个设计上限** |
```

**判定：结构性不相容。**

D8（核心索引结构）「结构」一节描述的是一套标准 COW B-tree：每个 key 的 value 要放进
一个 16 KiB 的节点里，节点满了走分裂。全仓查了"单条目 value 超过节点可用空间怎么办"
这类大 value / 溢出机制，只有一处提到"溢出"（`.claude/kb/decisions/08-核心索引结构.md:366,408`，
grep `溢出\|overflow` 命中 2 处，均在同一决策文件里，讲的是 inode **属性**（xattr）
要不要挂到额外 keyspace，即 C115（inode 属性的溢出路线无落点），
与"B-tree 单条目大小超过节点容量"完全是两回事；全仓 `.claude/kb/decisions/` 里
`溢出\|overflow` 合计命中 2 处，均出自这一份文件、这两行）。也就是说，
**这套 B-tree 设计里从未出现过"一个 key-value 对可以比节点还大"这种情形的处理办法**。

候选㈡ 的 value 宽度公式是"链长 = 活快照数 + 1"，而 D5（快照 / 空间记账机制） 的已定条款
明文禁止假设这个数有上界（"不许拿一个窄宽度去制造一个设计上限"）。这意味着：
**在候选㈡ 下，只要某个五元组身份被足够多的活快照引用到，它单独一条 map 条目的
value 就能超过整节点的可用空间**——而不是"变宽一点、每叶少装几条"那么温和。
这不是候选㈡ 的边缘情形，是候选㈡ 自己定义的那个公式的必然产物，D5（快照 / 空间记账机制）
的条款专门禁止我把它当作不会发生的事。

给一个量级（**仅供说明门槛落在哪个数量级，不是已定条款给出的宽度，标出假设**）：
沿用材料已引的宽度——`LOC_ENTRY = 14`（D19（块指针的结构与宽度预算） 已定项 4）、
`W = 2`（D2（RAID 条带策略） 已定项 9），若每条链节最少需要一份 `w` 份位置条目
（`14 × 2 = 28` 字节，未计版本/txg 标签，那部分宽度未定），节点可用空间取
`E109（位置权威三臂的运行时代价）` 的 `MAP_HDR = 76`（`research/e7-index-bench/src/bin/e109_position_authority.rs:58`）：
`(16384 − 76 − 33) / 28 ≈ 581` 条链节就能让**一条 key 单独占满整个节点、连自己的 key
都放不进同一个节点**（581 是这条粗算的门槛，不是精确值；若每条链节还要挂一个 8 字节
版本/txg 标签，门槛降到约 `(16308 − 33) / 36 ≈ 452`）。581 或 452 都不是不可企及的活快照数——
这正是候选㈠ 的正文自己引用的那句判据（"不许拿一个窄宽度去制造一个设计上不存在的
上界"）要防的那类判断，我在这里只是把它套用到候选㈡ 自己制造出来的这个新宽度上。

⚠️ 这条与材料点名的四条不同性质：D2（RAID 条带策略） 16/17、D8（核心索引结构） 已定项 1、D23（journal 的角色与格式）
三条我判"不冲突"，理由都是"候选㈡ 付得起代价、或者层不对口"；这一条不是"付代价"，
是**没有定义的行为**——今天的 B-tree 实现遇到一个比节点还大的 value 会怎样，
仓里没有任何条款回答。这不必然判候选㈡ 出局：候选㈡ 完全可以再补一条"链超过
某个长度时溢出到另一个结构"的子设计，但那是一笔候选㈡ 目前没有列出的新代价，
且这笔新代价本身又要过一轮 `.claude/rules/fs-design.md` 的格式分支判据——这不是
本问的范围，只记在这里，供第 2 问之外的后续判断参考。

## 第 2 问：候选㈠ 的代价清单，第五笔在哪

**未定项 6 原文列的四笔**（材料附录已整段抄，`.claude/kb/decisions/19-块指针的结构与宽度预算.md:104`）：
`MAP_ENTRY` 61 → 69、每叶 267 → 236 条、树高仍是 4、D27（小数据打包容器） 槽自描述 47 → 55。

### 2.1 第五笔（找到了）：中央映射树自身的稳态盘上占用

原文四笔里的"每叶 267 → 236 条"只是一个**比率**，未定项 6 没有把它乘回"全池要存多少条
中央映射条目"，换算出"这棵树本身在盘上永久多占多少字节"。这一步是**同一个已经列出的
数字（叶容量）的机械下一步**，不是新引入的假设。

**算法与已定项 5 自己引的那个实验完全同源**：用 E109（位置权威三臂的运行时代价） 自己的公式
与常量（`research/e7-index-bench/src/bin/e109_position_authority.rs`），

```rust
const NODE: u64 = 16384;                          // D8 已定项 2
const MAP_HDR: u64 = 76;                           // e109 自定的映射树头常量
const LOC_ENTRY: u64 = 14;                         // D19 已定项 4
const KEY_BYTES: u64 = 33;                         // D18 已定项 3
fn map_fanout(key_bytes, w) { (NODE - MAP_HDR) / (key_bytes + LOC_ENTRY * w) }
```

以及它自己取的主负载规模常量 `total_units: u64 = 483_183_820`
（`research/e7-index-bench/src/bin/e109_position_authority.rs:151`，
代码注释「16 TiB / 32768 的数据单元数量级，与 E106 / E107 同口径」，
`research/e7-index-bench/src/bin/e109_position_authority.rs:149`）：

| key_bytes | fanout（每叶容量） | 全池所需叶节点数（向上取整） | 叶层字节数 |
|---|---|---|---|
| 33（今天） | 267 | 1,809,678 | 29,649,764,352 B ≈ **27.613 GiB** |
| 41（候选㈠） | 236 | 2,047,390 | 33,544,437,760 B ≈ **31.241 GiB** |

差值：**多用 237,712 个叶节点，多占 3,894,673,408 字节 ≈ 3.627 GiB，涨幅 +13.14%**。
（算法：`fanout(33)=(16384-76)//(33+28)=267`，`fanout(41)=(16384-76)//(41+28)=236`；
叶数 `= ceil(total_units / fanout)`；叶层字节数 `= 叶数 × NODE`；这一步是对材料已引常量
做的算术，按 `.claude/singlefs-ai-sop/rules/verify-before-claiming.md`"不用现查的：
纯代码逻辑推导、算术"，不需要重新起跑实验。）

**这笔账落在哪条已定条款上**：直接落在 D8（核心索引结构） 已定项 2（`NODE_BYTES = 16384`，
`.claude/kb/decisions/08-核心索引结构.md:96-99`）与 D19（块指针的结构与宽度预算） 已定项 4
（`LOC_ENTRY = 14`）两个已冻结常量的乘积上——这两个常量本身没有争议，缺的只是
"把候选㈠ 的宽度变化代进去，报出全池维度的字节数"这一步换算，而这一步此前从未做过。
它与 D8（核心索引结构） 已定项 4（"节点大小的上限由恢复时间定"，`.claude/kb/decisions/08-核心索引结构.md:208-227`）
点名的那条轴同源但不同层：已定项 4 判的是"节点**大小**换恢复时间"，节点大小本身
两条候选都不动（仍是 16384）；我这里算的是"树**总容量**换永久占用"，是已定项 4
从未处理过的另一维——已定项 4 正文自己写着"目标线本身仍未定"
（`.claude/kb/decisions/08-核心索引结构.md:226`），说明这个方向今天没有任何数字看着它，
但"全盘扫描重建"（`.claude/rules/fs-design.md`"元数据块必须自描述"一节）要扫的正是
这棵树的全部叶节点，一棵大 13% 的树意味着一次全盘扫描重建（checker 遍历、
崩溃恢复的最后手段）要多扫 13% 的中央映射节点，这是一笔**方向确定、数字已经算出来、
但从未被计入候选比较**的代价。
