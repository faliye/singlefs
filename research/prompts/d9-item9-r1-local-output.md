The mapping layer cannot be rebuilt from unit headers because metadata unit identities are ciphertext when encryption is on, and the instance table required for current version resolution is encrypted. For example: Step 1: After encryption is enabled, a metadata unit is updated with instance ID 2 and transaction number 10. Step 2: The keyless mount attempts to rebuild the mapping layer but cannot read the encrypted instance table to determine the current version of the metadata unit. Step 3: The rebuild process picks an older version (instance ID 1, transaction number 5) instead of the current one. Rule broken: The mapping layer is supposed to be rebuildable from authoritative state, but the instance table is encrypted and inaccessible to keyless mounts. Smallest fix: Store instance table metadata (instance IDs, transaction numbers) in plaintext for keyless access during rebuilds.

2. The proposed entry shape cannot distinguish between replicas for a single logical identity. For example: Step 1: A unit has two replicas at physical locations A and B. The mapping layer has two entries: (logical ID, A) and (logical ID, B). Step 2: A keyless mount moves replica A to location C but cannot update the mapping layer because it lacks knowledge of which replica is which (no replica identifier in the entry). Step 3: After unlock, the system sees two entries for the same logical ID pointing to C and B, but cannot determine which replica was moved. Rule broken: The mapping layer entry lacks a replica identifier to track individual replicas. Smallest fix: Add a replica index field to each mapping entry to uniquely identify replicas.

Any modification to the mapping layer in the lease area would be caught by the lease area signature (since the signature covers the entire lease area content), the keyless ciphertext checksum would detect tampered data, and the checker rebuild would compare against authoritative state. For example, if an attacker alters a mapping entry, the signature check fails during unlock. If the checksum is recalculated to match, the lease area signature still fails. If the authoritative state is corrupted, AEAD decryption fails during rebuild. All three mechanisms would detect the error. The blocking step is that the lease area signature is generated after keyless writes, making post-write tampering detectable.
