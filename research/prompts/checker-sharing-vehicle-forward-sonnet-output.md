Stance: forward derivation. Answers follow the five-item task list in order.

1. Sharing rule derived from F1, F2, F5, F6 alone

The default these four facts force is prohibition. F1 states the checker must not call any deserialization or traversal code of the crate under test and must reimplement parsing, reading the raw device directly. F2 states the checker must not link any pipeline's runtime accounting or checksum code, and C12 turns this into a symbol-level rule: the function set the checker calls to rebuild accounting and the function set the runtime commit path calls must have empty intersection, with one named exception, format parsing and constants. F5 governs how that one exception may be exercised if code is actually shared: only through generation, never hand copying, and the moment a generated duplicate disagrees with its generator the relaxation is withdrawn. F6 attaches an obligation to whatever ends up inside that exception: list what is shared and ask, for each shared item, whether an error there makes both sides wrong together.

Per candidate:

1. Constants. Permitted, not required. F2 names format parsing and constants as the explicit exception to the empty-intersection rule. F1 does not mention constants at all, only deserialization, traversal and parsing. So constants sharing is open-permitted by F2, and if realized as shared code it is governed by F5's generation discipline and by F6's disclosure obligation.

2. Newtypes. Left open. None of F1, F2, F5, F6 says whether checker and core must declare the same newtype or each declare their own. F5's own newtype rule (fs-design) only requires that distinct address spaces be distinct Rust types within a crate; it says nothing about cross-crate identity of those types. F2's empty-intersection test is a test over called functions; a bare newtype with no attached encode or decode method calls no function, so it produces nothing for that test to catch. If instead the newtype carries its own serialization method, that method is parsing, and F1's requirement to reimplement parsing then forbids sharing it. So the answer bifurcates on a distinction the four facts do not draw.

3. Parsing. Forbidden for the crate-under-test's own deserialization and traversal path, with a narrow carve-out. F1 forbids the checker from calling that code and requires it to reimplement parsing. F2's exception clause names format parsing, alongside constants, as excepted specifically from the accounting-function empty-intersection rule. Read together, the live deserialization and traversal implementation is forbidden by F1, while a narrower notion of format parsing, apparently the layout knowledge itself rather than a callable decoder, is permitted to overlap for the accounting-rebuild comparison under F2. The four facts do not themselves mark where format parsing stops and deserialization or traversal code begins.

4. Checksum implementation. Forbidden. F2 names it directly: the checker must not link any pipeline's runtime checksum code.

5. Traversal. Forbidden. F1 names it directly. F1's own internal precedent reinforces this: the checker's two judging directions, root traversal and linear scan by unit header, share only format parsing with each other, not traversal logic, even inside the same crate.

6. Accounting. Forbidden. F2 states it directly and C12 operationalizes it as the empty-intersection requirement over called-function sets, again with format parsing and constants as the only exception.

2. Comparison with P1

Matches. P1 shares exactly constants, nothing else: no types, no parsing, no traversal, no checksum, no accounting. This lines up with items 1, 3, 4, 5, 6 above exactly, and resolves item 2 (newtypes) toward the forbidding side.

Where P1 is stricter than the facts require:

a. P1 shares nothing under the format-parsing half of F2's exception, only the constants half; F2 permits format-parsing code itself to overlap for the accounting-rebuild comparison, and P1 forecloses that entirely by putting parsing on its excluded list. A conservative choice, but a choice, not something F1, F2, F5, F6 force.

b. Task 1 found newtypes genuinely open under the four facts; P1 resolves the ambiguity by mandating independent newtypes in each crate, taking the stricter branch rather than leaving it open.

c. P1's rule that the generator refuses to emit a constant with no kb marker is stricter than anything in F1, F2, F5, F6, which never require that an unresolved kb gap block code generation; P1 adds this as a hard stop on its own initiative.

Where P1 is looser than the facts require, or leaves a boundary undefined:

a. P1 does not define where a constant ends and a small generated helper begins. If the generator's output ever grows past bare scalar values into a computed function, for example an offset formula mechanically derived from the field table, that function is parsing under F1's own language, and P1's text supplies no boundary that would catch such drift.

b. F6 requires that shared items be enumerated and interrogated for whether an error there makes both paths wrong together. P1 makes the sharing mechanically safe (generated, diffed, never hand-copied) but adds no mechanism that asks whether the single kb-derived value both crates converge on is itself correct. This is the exact gap explored next.

Generated-constants idea against F3, F4, F7:

Transcription errors, one crate hand-typing a width differently from the other, are caught by construction: with one generated module consumed by both and never hand-edited (F5), there is no path through which two copies of the same constant can diverge by typo.

Silent kb gaps, a field whose per-field widths were never pinned, matching F4's five-tuple (33 bytes total, no per-field breakdown anywhere in the kb), are also caught, because the generator refuses to emit an ungrounded constant. This forces the gap to be closed before code exists, which is a stronger catch than the mechanism F7 describes for the no-sharing alternative, where two independent implementers happen to invent different splits and disagree loudly after the fact.

A wrong-but-present kb value is not caught. F7 already constructs this exact scenario for a shared-constants design: JOURNAL_HDR = 78 wrong in the kb makes core and checker agree and every planned check stays green. F3 explains why extending gate 27's coverage, as P1 proposes, does not fix this: the gate only ever compares code against the registered marker's value, and that marker sits next to whichever sentence currently claims to settle it; if that sentence is stale relative to other settled increments recorded elsewhere in the same document, the marker is internally consistent and green while still wrong. F4 shows this is not hypothetical in this repository: JOURNAL_HDR is registered at 78, while other kb text says two settled-but-unlanded increments make it 91 and three make it 95. F7 further notes that forbidding sharing would not catch this particular case either, since both hand-written copies would still transcribe the same single wrong kb sentence. So for this category, P1's sharing choice is neither cause nor cure; catching it needs an orthogonal check, addressed in item 5 below.

3. Vehicle derivation from F8, F9, F10, F12, and comparison with P2

Crash-point replay (F9, D13 item 4): recording happens in userspace on the block-device abstraction, at write, flush barrier, and FUA write granularity, enumerating whole-write subsets per barrier segment and materializing images for the checker and record verifier. This requires a vehicle that issues, and can be intercepted at, raw block-device write, flush and FUA operations. Nothing in F9 calls for POSIX file semantics or a mount.

RefFS differential testing (F9, D13 item 3): the same operation sequence is driven into RefFS and the implementation and results are compared, and F9 states directly that nothing in the kb requires a mounted filesystem for that. This requires only that RefFS and the implementation expose a common operation-level API callable from a driver process.

QEMU workload (F8, F10 together): F8 states the first runnable target is correctly committing one transaction, explicitly without directories, and D7 keeps the project out of Linux mainline for years. F10 describes the already-working pattern: a statically linked musl binary given a raw device path such as /dev/vda inside a busybox initramfs, with the VM kernel's FUSE, ublk and nbd modules present in the kernel tree but not wired into the initramfs today, and the host having only the libfuse3 runtime, not the development headers needed to build a FUSE frontend. Nine existing experiment binaries already open files or devices with O_DIRECT from userspace, and one, E44, already proves fdatasync reaches the device. Nothing in F8 or F10 calls for a mount in the first version; the established and already-verified pattern is a bare binary against a raw device, matching F8's instruction to build the slow correct path first and to exclude directories from the first target.

Conclusion: none of the three tools needs a mounted filesystem in the first version. All three need the same shape of vehicle, a userspace component operating directly on a block-device abstraction (file-backed or raw device) through an operation-level API invocable from a driver process, deployable as a statically linked binary inside the existing VM harness. F12 adds a structural requirement the derivation must carry: the show-me-test gate only recognizes implementation code under crates/*/src/, and today the repository has neither a crates/ directory nor a root Cargo.toml, so a vehicle built under research/ falls only under the separate research-build gate stage, not under show-me-test's mandatory-test discipline.

Comparison with P2: P2 matches the derived shape closely. A pure userspace Rust library over a block-device trait, two backends (regular file, raw device with O_DIRECT), an operation API driven directly by all three tools, no mount in the first version, FUSE deferred until directories and the POSIX surface exist, kernel module out of scope while D7 holds. This satisfies the no-mount conclusion for all three tools and the D7 and F8 exclusion exactly.

Two gaps against the derivation:

a. F9 names three distinct block-device primitives that crash-point replay must be able to record and truncate at: write, flush barrier, FUA write. P2's stated API names two operations, write extent and publish or fsync, with publish or fsync apparently bundling flush and FUA together. P2 does not state whether the replay harness can observe or truncate at each of F9's three primitive boundaries, or only at the coarser call boundaries the stated API exposes. Concrete example in item 4 below.

b. F12's crates/ gap is not addressed. P2 describes driving the library the way today's experiment binaries drive their models, which is a research/-style pattern, while F8's own language (first runnable target is correctly committing one transaction) and CLAUDE.md describe that milestone as literal implementation, arguing for crates/ code subject to show-me-test. P2 does not say which gate governs its vehicle.

4. One concrete bug each

P1's sharing rule lets through: take F4's actual numbers. The kb's registered marker states JOURNAL_HDR = 78 bytes, while other kb text records two already-settled-but-unlanded header-field increments that would bring the true width to 91 bytes. Say those two increments are in fact correct and were simply never folded into the registered marker. P1's generator reads the registered marker and emits JOURNAL_HDR_BYTES = 78 into the one shared module. Core computes the journal payload offset as 78 plus n; the checker, reimplementing parsing independently but consuming the same generated constant, computes the identical offset. Both land 13 bytes short of where the truly settled format places the payload boundary. Every check P1 adds, gate 27 extended to cover all first-txn-layout.md widths, the generated module diffed by the gate, no stale literal reappearing, stays green, because the error is neither a transcription mismatch nor an absent value, it is one self-consistent wrong value at the single place both crates read from. A 13-byte misalignment at the header and payload boundary ships undetected.

P2's vehicle choice makes unobservable: a single data-unit write of 32768 bytes (DATA_UNIT_BYTES) plus its journal header commit could be implemented internally as two separate 16384-byte (NODE_BYTES) block writes followed by one FUA write of the journal header, all inside one call to publish or fsync. If P2's exposed API only lets the replay harness hook in at the write extent and publish or fsync call boundaries, two external events, rather than at each of the three underlying device operations F9 requires being individually truncatable, then a crash between the second 16384-byte block write and the FUA header write, a physically real crash point under F9's model, is never materialized or replayed in the first version. A recovery bug that only manifests at exactly that intra-publish boundary, for example recovery reading a torn journal header because the second data block landed but the header's FUA write did not, and misparsing it as a short valid record, would ship with a fully green crash-point-replay suite, because that suite structurally never produces the image that would trigger it.

5. What each proposal got most wrong or left out

P1's most important gap is that it makes the sharing mechanism safe, generated, diffed, never hand-copied, refusing to emit ungrounded constants, without ever checking whether the single value both crates converge on is itself correct relative to the rest of the kb, which per F4 is demonstrably false today for JOURNAL_HDR (78 registered against 91 and 95 stated elsewhere). The check that would settle it: extend gate 27 from is the registered literal used consistently to does the registered value equal the sum of every other settled increment recorded elsewhere in the kb for that same quantity. Run today against JOURNAL_HDR, this check would fail, which is itself the evidence that it belongs in the gate.

P2's most important gap is that it names an operation API, mkfs, open, write extent, publish or fsync, recover, without stating whether that API's granularity matches F9's three-primitive crash-point model, write, flush barrier, FUA write, so it is unverified whether every crash point F9's replay model requires is individually reachable or whether some are collapsed inside a single publish or fsync call. The measurement that would settle it: instrument both backends to log every underlying write or fdatasync (or equivalent O_DIRECT and FUA-marked write) syscall issued per single call to write extent and to publish or fsync, the way E44 already proves fdatasync reaches the device, and confirm the count is exactly one device-level operation per API call, or else give the replay harness a hook at each underlying operation rather than only at the API-call boundary.
