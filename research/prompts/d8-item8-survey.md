### 1.1 btrfs：种类不是字段，是树 ID 的保留区间

**「有哪些树」住在 root tree（`BTRFS_ROOT_TREE_OBJECTID = 1`，`btrfs_tree.h:38`）里，每棵树一条 `(objectid, BTRFS_ROOT_ITEM_KEY=132, offset)` 的 `btrfs_root_item`。**

`btrfs_root_item` 字段表（`btrfs_tree.h:920-963`）：

| 字段 | 宽 | 干什么 |
|---|---|---|
| `inode` (`btrfs_inode_item`) | 大 | 历史包袱，实际只用到几个位 |
| `generation` / `bytenr` / `level` | 8 / 8 / 1 | **根指针三件套**：代号 + 物理地址 + **树高** |
| `root_dirid` | 8 | 子卷根目录的 inode 号 |
| `byte_limit` / `bytes_used` | 8 / 8 | **每棵树的配额与用量** |
| `last_snapshot` | 8 | 上次快照的 txg |
| `flags` | 8 | 只读位等 |
| `refs` | 4 | 引用计数 |
| `drop_progress` + `drop_level` | 17 + 1 | **可续做删除的游标**：删一棵子卷删到哪个 key、哪一层 |
| `generation_v2` | 8 | 见下一段 |
| `uuid` / `parent_uuid` / `received_uuid` | 16 × 3 | 身份与 send/receive 的血统 |
| `ctransid` / `otransid` / `stransid` / `rtransid` | 8 × 4 | 改 / 建 / 发 / 收 各一个 txg |
| `ctime` / `otime` / `stime` / `rtime` | 4 个 timespec | 同上四个的挂钟时间 |
| **`reserved[8]`** | **64** | 逐字注释 `/* for future */` |

**树 ID 的分配与保留区间**（`btrfs_tree.h:38-120`）：`1` root tree、`2` extent tree、`3` chunk tree、`4` dev tree、`5` fs tree、`7` csum、`8` quota、`9` uuid、`10` free space、`11` block group、`12` raid stripe；**`BTRFS_FIRST_FREE_OBJECTID = 256`** 起才是动态分配的子卷；负数那一端（`-4` 到 `-12`）留给 balance / orphan / tree-log / reloc 这些内部根，`BTRFS_LAST_FREE_OBJECTID = -256ULL` 封顶。

**分配是单调不复用的，而且会耗尽**（`fs/btrfs/disk-io.c:4901-4919`）：

```
	if (unlikely(root->free_objectid >= BTRFS_LAST_FREE_OBJECTID)) {
		btrfs_warn(root->fs_info,
			   "the objectid of root %llu reaches its highest value");
		ret = -ENOSPC;
```

水位本身**不持久化，挂载时扫出来**（`fs/btrfs/disk-io.c:4863-4899`，`btrfs_init_root_free_objectid`）：拿 `BTRFS_LAST_FREE_OBJECTID` 当搜索 key 往回找最后一条，`free_objectid = max(found_key.objectid + 1, BTRFS_FIRST_FREE_OBJECTID)`。同一函数里还有一条**判别力检查**：搜到 `offset = -1` 的 key 就返回 `-EUCLEAN`，注释逐字「there would have to exist a root with such id, but this is out of valid range」。

**「树的种类」在 btrfs 里不是一个字段**，是从树 ID 反推的：`btrfs_is_fstree()`（`fs/btrfs/ctree.h:724-735`）判「≥ 256 且 qgroup level 为 0」，`btrfs_get_global_root()`（`fs/btrfs/disk-io.c:1154-1188`）对 1–12 逐个 `case` 分派，`default: return NULL`。

⚠️ **与本工程的一处已知差异**：btrfs 把每棵树的**用量与配额**（`bytes_used` / `byte_limit`）放进根条目，本工程把带树维的量放进记账树（D5（快照 / 空间记账机制） 已定项 4 第 8、9 项「每树独占 / 每树共享」）。所以 btrfs 那两个字段搬不过来——搬过来就是同一个事实的第二份权威副本，而 I-5.2（空闲统计对得上） 那条不变量的判别力恰恰要求两个数走两条不共享的加减路径（`decisions/05-快照-空间记账机制.md:317-319` 逐字）。

### 1.2 ZFS：种类是盘上一个字节，而且留了一个不进登记表的逃生口

**「有哪些对象」住在 MOS 里**：`DMU_POOL_DIRECTORY_OBJECT = 1`（`include/sys/dmu.h:372`）是一个按**名字**索引的 ZAP，`"root_dataset"`（`dmu.h:378`）等名字指向对象号；每个对象是一个 `dnode_phys_t`。

**种类是 `dnode_phys_t` 的第一个字节**（`include/sys/dnode.h:203-204`）：`uint8_t dn_type;  /* dmu_object_type_t */`。同结构里还有 `dn_nlevels`（树高）、`dn_indblkshift`、`dn_nblkptr`、`dn_maxblkid`、`dn_used`（用量）、`dn_pad3[4]`（32 字节预留，注释逐字说它受块的 MAC 保护，就是为了「protect any fields that might be added here in the future」）。

**登记表满了怎么办，ZFS 写在注释里**（`include/sys/dmu.h:228-240`）：

```
	 * Do not allocate new object types here. Doing so makes the on-disk
	 * format incompatible with any other format that uses the same object
	 * type number.
	 *
	 * When creating an object which does not have one of the above types
	 * use the DMU_OTN_* type with the correct byteswap and metadata
	 * values.
```

`DMU_OTN_*` 是把种类字节**从「名字」改成「结构描述」**：`DMU_OT(byteswap, metadata, encrypted)`（`dmu.h:105-112`）拿最高位 `DMU_OT_NEWTYPE = 0x80` 做判别子，低 5 位是字节序函数号，另两位是「是不是元数据」「加不加密」。读者遇到一个没见过的 `DMU_OTN_*` 值，**照样知道该怎么对待它**（怎么翻字节序、要不要进 metadata cache、要不要解密），只是不知道它叫什么。

**每个数据集（≈ 本工程的「一棵树」）的记录是 `dsl_dataset_phys_t`**（`include/sys/dsl_dataset.h:139-171`）：`ds_bp`（根指针，一个 `blkptr_t`）、`ds_prev_snap_obj` / `ds_prev_snap_txg`、`ds_creation_txg`、`ds_deadlist_obj`、`ds_referenced_bytes` / `ds_compressed_bytes` / `ds_uncompressed_bytes` / `ds_unique_bytes`、`ds_guid`、`ds_flags`、`ds_next_clones_obj`、以及 **`ds_pad[5]`**，注释逐字 `/* pad out to 320 bytes for good measure */`。

**对象号是复用的**：`dmu_object_alloc_impl()`（`module/zfs/dmu_object.c:38-120`）的注释逐字「Each time we polish off a L1 bp worth of dnodes (2^12 objects), move to another L1 bp that's still reasonably sparse (at most 1/4 full). **Look from the beginning at most once per txg.**」——号会绕回去 backfill 被释放的槽。保留号是**负数与零**：`DMU_META_DNODE_OBJECT = 0`、`DMU_USERUSED_OBJECT = (-1ULL)` / `GROUPUSED (-2ULL)` / `PROJECTUSED (-3ULL)`，判别子是 `DMU_OBJECT_IS_SPECIAL(obj) ((int64_t)(obj) <= 0)`（`dmu_objset.h:196-197`）。

⚠️ **与本工程的一处已知差异**：ZFS 的对象号可以复用，是因为它的块指针里没有「出生对象号」这种反向身份——生死判定只看 `blk_birth` 与 `prev_snap_txg`。本工程反过来：**树 ID 印在每一个码 1 / 码 3 单元的头里**（D18（块里携带什么信息） 已定项 11 的「出生树 ID 8」在码 3 偏移 43；五元组里也有一段树 ID 8），而且它是 AAD 的一段（D9（加密） 已定项 6）。所以「号可复用」这条在 ZFS 成立的前提，在本工程**不成立**（详见第二节第 1 问）。

### 1.3 bcachefs：种类是一个编译期属性，而树表条目只有三段

**树表不在超级块的常态路径上，在 journal 里。** 一条「某棵树的根在哪」就是一个 `jset_entry`（`fs/bcachefs/bcachefs_format.h:608-617`），type = `BCH_JSET_ENTRY_btree_root`（`bcachefs_format.h:1162`）：

```
struct jset_entry {
	__le16			u64s;
	__u8			btree_id;
	__u8			level;
	__u8			type;
	__u8			pad[3];
	struct bkey_i		start[0];
```

**整条条目就是（树 ID 1 字节，树高 1 字节，根指针一个 bkey）**，此外一个字段都没有。干净关机时同一批条目抄进超级块的 `bch_sb_field_clean`（`bcachefs_format.h:619-629`）。

**树 ID 是一张编译期登记表**（`bcachefs_format.h:1337-1418`，`BCH_BTREE_IDS()`）：21 棵树，`extents=0`……`accounting=20`，每一行还带一组 `btree_id_flags`（`BTREE_IS_extents` / `BTREE_IS_snapshots` / `BTREE_IS_snapshot_field` / `BTREE_IS_data` / `BTREE_IS_write_buffer`，`bcachefs_format.h:1329-1335`）和一张「这棵树允许出现哪些 key 类型」的位图。**这套「种类」信息一个字节都不在盘上**——它是宏展开出来的常量表。

**上界是硬的，而且理由写在源码里**（`bcachefs_format.h:1425-1430`）：

```
/*
 * Maximum number of btrees that we will _ever_ have under the current scheme,
 * where we refer to them with 64 bit bitfields - and we also need a bit for
 * the interior btree node type:
 */
#define BTREE_ID_NR_MAX		63
```

**加一棵新树走 metadata version bump**（`bcachefs_format.h:654-703`，`BCH_METADATA_VERSIONS()`）：`deleted_inodes` 是 `BCH_VERSION(1, 2)`、`rebalance_work` 是 `(1, 3)`、`btree_subvolume_children` 是 `(1, 6)`、`accounting` 那次是 `disk_accounting_v2 = (1, 9)`。

**关键一段：不认识的树 ID 不会被丢掉。** 恢复时（`fs/bcachefs/recovery.c:498-517`）先判 `entry->btree_id >= BTREE_ID_NR_MAX` 才报错，否则把 `btree_roots_extra` 这个动态数组撑到够长，把根原样收下；写回时（`fs/bcachefs/btree_update_interior.c:2765-2787`，`bch2_btree_roots_to_journal_entries`）按 `btree_id_nr_alive(c) = BTREE_ID_NR + c->btree_roots_extra.nr`（`fs/bcachefs/btree_cache.h:120-123`）**把不认识的根也一并写回去**。GC 也走同一个上界（`fs/bcachefs/btree_gc.c:591,786`）。

⚠️ **与本工程的一处已知差异，而且是这一节最值钱的一条**：bcachefs 敢让旧内核走进一棵它不认识的树，是因为**节点载荷是自描述的**——`struct bkey` 的第一个字节就是 `__u8 u64s;  /* Size of combined key and value, in u64s */`（`bcachefs_format.h` 的 `struct bkey` 定义），不认识 key 类型也跳得过去。**本工程不是这样**：D8（核心索引结构） 未定项 8 自己逐字点出「索引节点的条目宽按树不同（inode 树 93、记账树 81）**而节点头不带条目形态**」⇒ 一棵不认识的树，本工程的读者**连它的内部节点都切不开**，不是「看不见」，是「解不开」。

## 二、提案：树表条目的字段表

### 2.0 先说清算术底座

树表单元是 16 KiB 元数据单元、索引节点类头 **68**（D22（单元原子性怎么合成） 已定项 7）；E79（根记录的容量） 的模型再保守留 32 字节给单元自己的长度与保留字段（`research/e7-index-bench/src/bin/e79_root_record.rs:76` 逐字注释）⇒ **可用 16384 − 68 − 32 = 16284 字节**。

| 条目宽 | 一层装几棵 | 两层封顶 | 说明 |
|---|---|---|---|
| 61 | 266 | 70 756 | **E79（根记录的容量） 现在的数，已经过期**——它用的位置条目是 11，而 D19（块指针的结构与宽度预算） 已定项 4 定的是 14（见第四节） |
| 67 | 243 | 59 049 | 只放树 ID 8 + 根指针 59 的下限 |
| 81 | 201 | 40 401 | 提案主体，零预留 |
| **97** | **167** | **27 889** | **提案取值：主体 81 + 预留 16** |
| 113 | 144 | 20 736 | 预留 32 |
| 145 | 112 | 12 544 | 预留 64（btrfs `reserved[8]` 那个量） |

⚠️ 表里的数按头宽 **68** 算。E79（根记录的容量） 的单测钉的是「68 / 77 / 86 三档同值」这条性质，而它不是恒成立的：**97 三档同为 167**，**67 是 243 / 242 / 242**，**81 是 201 / 200 / 200** ⇒ 取 97 顺带保住了那条断言的形态。

### 第 1 问：树 ID 怎么分配与编码

**编码：8 字节，小端，与另外三处同宽。** 这一条不是选择——D5（快照 / 空间记账机制） 已定项 5 那一行虽然自陈「自由选择」，但它同时逐字写了「不许拿一个窄宽度去制造一个设计上限」，而 D18（块里携带什么信息） 已定项 11 的定案已经把 8 印进了每一个码 1 / 码 3 单元头。**收窄它今天已经是格式断裂，不再是选项。**

**保留区间（提案，形态照 D18（块里携带什么信息） 已定项 11 的登记表）**：

| 区间 | 用途 | 依据 |
|---|---|---|
| `0` | **保留：全池 / 无归属**，永不出现在树表里 | `decisions/05-快照-空间记账机制.md:309` 已经占用了它 |
| `1 – 255` | **全池唯一的系统树**，mkfs 时钉死，码用过不许回收 | 记账树、分配记录树这类不按头分的树。形态照 btrfs 的 1–12（`btrfs_tree.h:38-77`），差异见下 |
| `256 – (2⁶⁴ − 257)` | **动态分配**给按头分的树（extent、inode、dirent、反向索引…），单调递增不复用 | 起点 256 与 btrfs `BTRFS_FIRST_FREE_OBJECTID`（`btrfs_tree.h:118`）同值，取它只是为了留够系统树的余量 |
| `(2⁶⁴ − 256) – (2⁶⁴ − 1)` | **保留：永不分配** | 判别力：全 `0xFF` 的一段损坏字节不会被读成一个合法树 ID。btrfs 在 `disk-io.c:4880-4886` 对同一形态显式返回 `-EUCLEAN` |

**分配：单调不复用。论证与 D8（核心索引结构） 已定项 6 给 inode 号的那条同形，但更硬。**

D8（核心索引结构） 已定项 6 给 inode 号的论证逐字是：「`deleted_inodes` 后台回收窗口里复用会让新旧对象的 extent key 三段逐字相同」。树 ID 这一侧有**三条各自独立、任一条成立就够**的理由：

1. **树 ID 印在盘上单元的头里。** 码 3 偏移 43 是出生树 ID（D18（块里携带什么信息） 已定项 11），码 1 的五元组里也有一段。销毁一棵树之后，它的单元在清扫水位推进之前仍然躺在盘上（D5（快照 / 空间记账机制） 已定项 4 第 13 项「清扫水位」）。复用树 ID ⇒ 旧树的残留单元自称属于新树，而 I-1.3（块头树 ID 一致） 判不出来——两边逐字相同。
2. **树 ID 是 AAD 的一段**（D9（加密） 已定项 6）。复用 ⇒ 给旧树算出的 MAC 在新树的读路径上验得过。这是 ZFS 那条「对象号可复用」搬不过来的直接原因（第 1.2 节的差异）。
3. **记账行按 K 代点删**（D5（快照 / 空间记账机制） 已定项 2）。销毁一棵树之后它的 `(标签, 树 ID, 设备, 代)` 行还要活 K 代。复用 ⇒ 两棵树的账在同一个 key 上合并。

**水位放哪：提案取「记账里的一条统计量」，不取「挂载时扫树表算出来」。**

btrfs 走的是扫描路线（`btrfs_init_root_free_objectid`，`disk-io.c:4863-4899`），代价是 O(根条目数)，对本工程同样便宜（树表最多两层）。**但它在本工程会漏一格**：一次被抛弃的 checkpoint 里已经写出去、带着新树 ID 的单元仍在盘上（这正是 C113（扫描重建时多版单元的现行版本判定无输入） 定案要处理的那类暴露，`decisions/08-核心索引结构.md` 已定项 6 逐字「崩溃后 checkpoint 号会被重发」），而扫描已发布树表得到的最大值不包含它 ⇒ 下一次分配把这个号发出去，第 1 条理由那个洞当场成立。

⇒ **提案：加 D5（快照 / 空间记账机制） 已定项 4 的第 15 项「树 ID 水位」，不带设备维、不带树维（用保留树 ID 0 那一行），合并规则取最大值。** 依据完全照抄第 12 项「inode 号水位」的先例（`decisions/08-核心索引结构.md` 已定项 6 逐字：「选它而不是『后者胜』的理由是崩溃后 txg 重发那一格：同一个代段里先后出现大小两个值，取最大值给大的（浪费号、不复用号）」）。
⚠️ **这条会改 D5（快照 / 空间记账机制） 已定项 4**（十四项变十五项），所以它自己也要过一遍那条已定项的完备性口径。另一条落点是把水位放进根记录（D22（单元原子性怎么合成） 已定项 7 还剩 326 字节余量），代价是改根记录字段表；两条各有代价，**这一格提案不替用户选**。

### 第 2 问：有没有「树的种类」一段

**有，2 字节，值域是一张第二级登记表。**

**三个消费者逐字现查过，全部成立**：

| 消费者 | 逐字 | 不放会怎样 |
|---|---|---|
| checker 判 I-9（inode 树结构） 类 | `invariants.md:247`：「checker 要知道一棵树是 inode 树才能对它判这一类，而树表条目里有没有『树的种类』一段无落点」 | I-9.1（inode 树根恒码 2） 到 I-9.12（分隔 key 落在孩子区间之外） 里九条的状态列写着「未实现，前置：树的种类可识别」。第一版镜像上可由码 3 类型 2 容器头里的出生树反推，**而那条退路只在「已经有类型 2 容器」时成立**——空的 inode 树反推不出来 |
| nlink 那条门 | `invariants.md:267`：「nlink == dirent 条数的门（dirent 树存在）今天没有输入」 | 那条不变量立不起来 |
| 节点解析 | D8（核心索引结构） 未定项 8 逐字：「索引节点的条目宽按树不同（inode 树 93、记账树 81）而节点头不带条目形态」 | **一棵不认识的树连内部节点都切不开** |

第三个消费者是承重的那个，而且它**推翻了 D15（格式冻结政策） 已定项 2 依据里的一句话**：

> D15（格式冻结政策） 已定项 2 逐字：「开放列表下『新增一棵 keyspace』对旧读者只是**看不到新树**（档次 compat，优雅降级）」。

在 bcachefs 那句是真的，因为 bkey 自带 `u64s`（第 1.3 节）。在本工程它**只对「不下降到那棵树」的读者为真**：一个跑扫描重建、跑清扫、跑整理的写者要回答「这个块活没活」，而 D3（空间分配） 已定项 1 的谓词是分配记录 + deadlist、分配记录又是派生态（D21（权威态与派生态的分界） 已定项 5）⇒ 重建它就得走遍全部树。走不进一棵不认识的树，就分不清「新树的活块」与「垃圾」。

⇒ **提案把 D15（格式冻结政策） 判定表那一行拆成两行**（这一步本身需要用户定案，因为它动的是一条已定项的依据）：

| 改动 | 旧读者会怎样 | 哪档 |
|---|---|---|
| 加一棵**已登记种类**的树（第二个可写头的 inode 树、克隆…） | 条目布局不变、种类认得出、节点切得开 ⇒ 真的只是多一棵 | **compat**，D15（格式冻结政策） 已定项 2 原样成立 |
| 加一个**新种类**（节点条目形态是新的） | 条目跳得过（有长度字段），但那棵树走不下去 | **compat_ro**，且 compat_ro 读者不许跑扫描重建 / 清扫 / 整理。若那棵树的存在会改变只读答案（C115（inode 属性的溢出路线无落点） 说的属性树就是一例），降为 **incompat** |

**这个拆法不是新发明**：D15（格式冻结政策） 判定表里「新增记录类型」那一行已经是这么判的，逐字「『只读安全』与『可写安全』是两条独立保证，必须分开判」；D18（块里携带什么信息） 已定项 11 对打包记录类型也是这么定的，逐字「只有登记时能证明『跳过它不改变任何只读答案』的类型才降到 compat_ro」。

**登记表的形态（提案）**，每一行登记这几列：

| 列 | 干什么 |
|---|---|
| 码 | 2 字节；`0` 无效永不分配；**码一旦用过不许回收**（照 D18（块里携带什么信息） 已定项 11） |
| 名 | 简称 |
| 内部节点条目宽 | 今天两个值：inode 树 93、记账树 81。**这一列在就不必给每棵树各存一份条目宽**（见第 3 问） |
| 叶的单元类 | 码 2 还是码 3；码 3 的再登记它的打包记录类型（inode 树是类型 2） |
| 实例数 | 全池唯一（记账、分配记录）还是每头一棵（extent、inode、dirent） |
| 跳过它改不改变只读答案 | 定这一行的 compat 档：不改 ⇒ compat_ro，改 ⇒ incompat |

**为什么不做成一个封闭枚举**：与 D18（块里携带什么信息） 已定项 11 同一条理由——那次否掉封闭值域的依据是「一份永久契约不能有六份互不相同的正本」，而这里更直接：D15（格式冻结政策） 已定项 2 已经把「加 keyspace 是本工程明写的扩展目标」写进依据了，封闭枚举与它冲突。

⚠️ **它是不是一个独立冻结组件**：D15（格式冻结政策） 已经有两个四层之外的独立组件（打包记录单元的载荷记录格式、统计量登记表），两个都还没有 spec 文件（C119（两个冻结组件没有 spec 文件））。树的种类登记表**符合同一形态**（值 → 语义的映射，两个读者用不同映射会得出不同答案），提案立成**第三个组件**。

### 第 4 问：为未来预留多少

**先把档次判清楚。** D15（格式冻结政策） 判定表对树表相关的三种改动判得不一样：

| 改动 | 档 | 依据 |
|---|---|---|
| 树表里**加一条条目**（加一棵已登记种类的树） | **compat** | D15（格式冻结政策） 已定项 2 |
| 树表条目**加一个字段** | 取决于有没有预留区 / 长度字段。**今天的形态下是 incompat**——定长条目数组加字段改 stride，旧读者从第二条起偏移全错，落「扩大已有字段宽度」那一行 | C102（索引节点头没有预留区，加字段不是 compat） 已经在索引节点头上证过同一个形态 |
| 树表条目**改一个字段的含义** | **incompat 且弃用旧位置不复用** | 判定表明写，而 C97（改字段含义而不改宽度，全仓没有一处会红） 说这一类恰好落在门禁盲区正中 |

**提案取「长度字段 + 预留字节」两样一起上，不只取其一。**

- **长度字段 2 字节**（偏移 0）：让「加字段」这件事从「改 stride」变成「延长一条条目」，旧读者按声明长度跳过。这是三家里两家的做法：bcachefs 的 `bkey.u64s`、ZFS 的 `DMU_OTN_*` 逃生口（后者换的是「不认识也知道怎么处理」）。btrfs 走的是第三条路——`generation_v2`（`btrfs_tree.h:950`，注释逐字说它用来检测「anyone ever mounted the fs with an older kernel」并据此把新字段整段 memset 作废）——**那条路本工程不能走**：它依赖「旧内核会写坏新字段」这个可容忍前提，而本工程的树表条目住在权威态里（D21（权威态与派生态的分界）:10），写坏就是丢数据。
- **预留 16 字节**：长度字段解决的是「加字段」的兼容档，解决不了「加字段要不要 bump」——按判定表第一行，落在**预留区**里的新字段才是 compat 不 bump。16 字节能装两个 8 字节字段（例如 deadlist 的根、或第二个时间戳），比 ZFS 的 `ds_pad[5]`（40 字节）窄、比 btrfs 的 `reserved[8]`（64 字节）窄得多，但两家的条目本身也大得多。

⚠️ **预留区的语义必须显式选一侧，而这一侧与单元头相反。** D18（块里携带什么信息） 已定项 11 对共同前缀偏移 7 的 8 个 flag 位取的是「第一版恒 0，**非 0 一律拒收**」，逐字说明「本工程不给这 8 位留『忽略陌生位』的通道」。**那一侧买不到 compat**——拒收就是 incompat。树表条目的预留区要真的落在判定表第一行，语义只能是「**旧读者忽略陌生内容**」。两种语义不能同时对同一段字节成立，所以这是一次显式取舍，理由是：单元头那一侧要挡的是「拿错布局静默误读一整个单元」，而树表条目的预留区里放的是**加法字段**，忽略它的旧读者得到的是一棵少了一些属性的树，不是一棵解错的树。
⚠️ **这个取舍要立成一条会红的检查**，否则它只是一句话——见第三节。

**预留形态不取「按需加新条目类型」。** 那是 ZFS 的 `DMU_OTN_*` 与 bcachefs 的 KEY_TYPE 登记表走的路，它在**条目种类很多**时省，在**条目只有一种**时纯亏：多一个判别子、多一条解析分支、多一份 checker，而 `.claude/rules/fs-design.md` 逐字「格式上吝啬分支」，判据是「能不能把『用错了』变成『挂不上』」——加一个条目类型码买不到这个。

1. 每条条目的**种类码 ∈ 登记表**；未登记 ⇒ **拒挂**，不是忽略（照 D18（块里携带什么信息） 已定项 11 的「未登记 ⇒ 拒收」）。
2. 每条条目的根指针指向的单元，其码 2 类身份段里的**树 ID == 条目的树 ID**（I-1.3（块头树 ID 一致） 在树表这条边上的具体形态）。
3. 树 ID **严格递增、> 0、不落在保留高位区间**；无重复。
4. **flags 的可写位为真 ⟺ 该树 ID 在记账里有「inode 号水位」行。**
5. 「树 ID 水位」统计量 > 树表里最大的树 ID，且 > 全盘扫描见到的最大出生树 ID（两条独立路径，形态与 I-9.6（水位大于两处最大号） 同）。

## 五、这份提案答不了的，以及它自己的前提

| 答不了 | 为什么 |
|---|---|
| deadlist 的载体 | 形态无落点（第 3 问那一行）。它定了才知道树表条目要不要多一段 |
| 「树 ID 水位」放记账还是放根记录 | 两条各有代价（改 D5（快照 / 空间记账机制） 已定项 4 vs 改 D22（单元原子性怎么合成） 已定项 7），提案不替用户选 |
| 预留取 16 / 32 / 64 | 容量表已给（第 2.0 节），差别在可预见规模上不构成判据 ⇒ 这是一次纯取舍，没有能推出唯一答案的判据 |
| 树表单元自己的头有没有预留区 | `first-txn-layout.md:133` 标着「半定」（索引节点类，宽度未定）。E79（根记录的容量） 模型里那 32 字节是保守假设，不是定案 |
| 每棵树在树表里的**排序契约** | 提案默认按树 ID 升序（检查 B 第 3 款依赖它），但「树表条目要不要有序」全仓一处没写。按 D15（格式冻结政策） 判定表，「改变排序规则 ⇒ incompat 且不报错」 ⇒ 它得在冻结前定 |

**这份提案自己的三条前提**（推翻任一条，提案要重做）：

1. 树表条目是**定长数组**（不是变长记录流）。长度字段只在这个前提下才是「加字段的通道」；若树表本身做成打包记录单元（码 3），整套论证要照 D18（块里携带什么信息） 已定项 11 重走。
2. **树表单元是权威态**（D21（权威态与派生态的分界）:10）。所以它的载荷布局**不能**照 D8（核心索引结构） 已定项 6 给 inode 内部节点那样落 D15（格式冻结政策） 第 4 层「不永久」——那条依据逐字是「派生态，丢了从叶重建」，对树表不成立。**树表条目的字段布局落第 1 层，与超级块同格。**
3. 「不认识的树解不开它的节点」这条（第 2 问的第三个消费者）**建在 D8（核心索引结构） 未定项 8 自己那句话上**，而那句话说的是今天的形态。若日后给索引节点头加一段「条目宽」（自描述节点），这条消费者消失，第 2 问那张 compat 拆分表要重判。⚠️ 加那一段今天是 incompat（C102（索引节点头没有预留区，加字段不是 compat））。
