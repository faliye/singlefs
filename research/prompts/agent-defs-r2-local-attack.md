Background.

This is a description of a software project's own internal review process. The project defines several project specific AI assistant roles as instruction files, called role definitions. Before a candidate role definition, or a candidate fix to one, is adopted for real work, the project validates it by giving one instance of that role one small, self contained, one off task to perform, called a trial run, and then checking whether the results look correct. I will give you eleven numbered facts about this validation process, then five numbered questions. Treat every fact below as authoritative and exactly as stated. Do not assume any additional fact that is not stated here.

Fact one. Validating a candidate role definition currently means giving it one trial run: one small, self contained, one off task, invented specifically for that trial. Out of sixteen total candidate role definitions in this project, twelve have been trial run exactly once, ever, and four have been trial run twice, because a second trial run was given specifically to the four definitions that had been edited the most after their first trial run. No role definition has ever been trial run more than twice.

Fact two. A separate project mechanism, called the write scope gate, is a script that intercepts every file write made through the assistant's own built in Write tool or Edit tool. It reads a table that lists, for each role name, one or more file path patterns that role is allowed to write to. If the write's target path, after being resolved to an absolute path, matches one of that role's own registered patterns, the write is allowed. If it matches none of them, the write is rejected, and the role is told to hand the problem back instead of finding another way to write the file. This gate does not intercept writes performed through a Bash shell command, for example a command that redirects text output into a file using a greater than sign. Such Bash based writes are not blocked by anything mechanical at all; staying inside scope while using Bash depends entirely on the role choosing to follow its own written instructions.

Fact three. Exactly three roles currently have any patterns registered in this write scope table at all: one role that writes production source code, one role that writes project knowledge base documents, and one role that runs experiments. Each of these three roles has, among its own registered patterns, one blanket pattern that matches literally any path located anywhere under one specific temporary scratch directory tree, referred to here as the scratch tree. Each of these three roles keeps its own draft files and its own report file under the scratch tree. The project also places entire disposable copies of the whole repository under the scratch tree whenever it wants to trial run a candidate change safely, without touching the real repository.

Fact four. Because the blanket scratch tree pattern matches literally any path under the scratch tree, it also matches every path inside any full repository copy that happens to be placed there, including a copy's own top level project configuration file. The project directly confirmed this by testing the knowledge base writing role three times in a row: first, giving it an edit target inside a repository copy under the scratch tree, targeting an ordinary knowledge base document inside that copy, which the gate allowed. Second, giving it an edit target inside that very same repository copy under the scratch tree, but this time targeting that copy's own top level project configuration file, which is a file this role is never supposed to be allowed to edit, and the gate allowed this too. Third, giving it an edit target pointing at the real, canonical repository's own top level project configuration file, outside the scratch tree, which the gate correctly rejected. In other words, running a trial inside a full repository copy under the scratch tree can never actually exercise the write scope gate's rejection behavior for that copy's own files, because the blanket scratch tree pattern silently allows every single target inside that copy regardless of what the role's real intended scope is supposed to be.

Fact five. The one off task handed to a role for its trial run, and the criteria used afterward to decide whether the results count as a pass, are both written by the very same senior process, referred to here as the main agent, that authored the candidate role definition being tested. The main agent also personally reads and checks the trial run's resulting output itself. There is no independent party that writes the task or that grades the results.

Fact six. A documented historical incident. In an earlier round of trial runs, one candidate fix to the role definition for the experiment running role said, in effect, that a particular verification script should be run from the repository's own top level directory. This fix was checked by one trial run, judged to work, and adopted into that role's definition. Later, a second, different one off trial run of that very same role definition, doing an unrelated task, discovered that the verification script actually requires being run from one specific subdirectory of the repository instead. Running it from the top level directory does not produce any loud, clear error. Instead, an internal directory existence check inside the script happens to pass anyway, purely by coincidence, because the top level directory also happens to satisfy that same check for an unrelated reason, and the script then goes on to silently compute the wrong thing and print a misleading message blaming something else entirely for the failure. So the first trial run's judgment that the fix worked was simply wrong, and only a second, differently shaped trial run, exercising a different task, happened to expose that mistake.

Fact seven. When two competing candidate fixes to a role definition, or a candidate fix against the previously existing wording, are compared in an adversarial review, the final verdict, meaning which fix is judged correct and gets adopted into the role definition, is rendered by the very same main agent that is also the one who revises the role definitions under review. This project's own stated rule for this review process says explicitly that when independent reviewers disagree, the verdict is not decided by counting votes; the main agent alone decides, after independently checking the facts each reviewer raised.
