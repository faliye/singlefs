## 1. 一次发布多写多少字节

### 1.1 8 叶落成几条条带

按 D2 已定项 6：`w = clamp(8 + 1, 2, 4) = 4`（拿 4 个格封顶）。`w = 4` 的满条带装 `w − 1 = 3`
个数据格。8 叶 = 3 + 3 + 2（两条满条带 + 一条 2 数据格的尾条带）。

⚠️ **这里有一处第三版正文没写清楚的分叉，我显式标出来，不替它拍板**：
尾条带的 `w` 是跟着满条带一起取 4（留一列空）,还是像 D2 已定项 11 / R6 那样按自己的数据格数
重新求值（`clamp(2 + 1, 2, 4) = 3`）？R6 那句「`w = 4` 丢一列剩 3 个幸存者，新条带 `w = 3`
只装 2 个数据格」字面说的是**修复**场景，不是**首次写入切分批次**场景，不能直接照搬。
下面按**尾条带独立求值（`w = 3`）**算主线，因为这与 D2 已定项 6 的公式字面（对"这一次要写的量"求值）
更一致；用「尾条带沿用满批的 `w = 4`」算一遍作敏感性对照，写在后面。

**主线（尾条带 w=3）**：3 条条带，宽度 4/4/3。按 R3「parity 格有分配记录条目」+ R2「一条记录记
一个成员落点」⇒ 每一列（含 parity）一条记录 ⇒ 记录数 = 4+4+3 = **11 条**。
**敏感性（尾条带沿用 w=4，留一列空）**：3 条条带全 w=4 ⇒ 记录数 = 4×3 = **16 条**。

两种读法下面算出来的最终字节数**相同**（见 1.3 的说明），所以这处分叉不影响本节结论，
但它本身是一个未定的空白，落在下面第 3 节旁述里。

### 1.2 这些记录落在几个容器里

11（或 16）条记录 ≪ 583（一个容器的记录容量）。稳态下按顺序追加进当前正在写的那个容器，
**典型情形是 1 个容器**；只有当前容器恰好只剩不到 11（或 16）个空位时才会溢出到第二个容器
——按均匀分布估算，触发概率 ≈ 11/583 ≈ 1.9%（16/583 ≈ 2.7%）。
下面主线按典型情形（1 个容器）算，最后给出溢出情形（2 个容器）的敏感性数。

### 1.3 每个容器 COW 要重写多少字节（容器 + 它的树路径）

**这张条带表自己的容器索引树高**：E106 甲臂在 16 TiB / 90% / 单元 32768 的基线下，稳态容器数
= **828 789**（`.claude/kb/experiments/106-条带成员表的载体.md:41`）。按 E103 给出的容器索引
条目宽度（85 字节）与扇出（16384 字节节点、头 58 时扇出 192；头 76 时 `⌊(16384−76)/85⌋ = 191`，
本表的记录总数量级 ≈ 828 789 × 583 ≈ 4.83×10⁸，比 E103 测过的最大档 1e8 还大一档，
只能取头 76 作外推，⚠️ 这一步是外推不是实测）：

| 层 | 节点数 |
|---|---|
| 叶（容器索引最底层，每个引用 ≤ 191 个容器） | ⌈828789 / 191⌉ = 4340 |
| 中间层 | ⌈4340 / 191⌉ = 23 |
| 根 | ⌈23 / 191⌉ = 1 |

**树高 = 3。** 交叉校验（不依赖上面这个 log 公式的独立算法）：E103 在 4292 个容器时给出
「23 叶 → 1（高 2）」；828 789 / 4292 ≈ 193.1，与扇出 192 几乎相等 ⇒ **容器数正好多了一个扇出因子
的量级，多一层是自洽的**，两条算法互相印证。

⇒ 更新 1 个容器（新增记录、容器本体 COW 一份新版本）要重写：
**1 个容器（32768）+ 3 个容器索引节点（3 × 16384 = 49152）= 81920 字节**（未镜像）。

按 R1「从根记录到容器的整条链恒走 `w = 2`」，这整个 81920 字节都要镜像一份：

> **81920 × 2 = 163840 字节** —— 这是主负载一次发布里，条带表这一侧新增的字节数（典型情形，1 个容器）。

### 1.4 与「不带条带表」的基线比出倍数

基线（D25 主负载，不带条带表）总字节 = 8 × 32768（叶）+ 4 × 16384（祖先）+ 4096（journal 记录）
+ 512（根槽）= 262144 + 65536 + 4096 + 512 = **332288 字节**。

| 情形 | 条带表新增字节 | 发布总字节 | 相对基线的倍数 |
|---|---|---|---|
| 基线（不带条带表） | 0 | 332288 | 1.000 |
| **典型（1 容器，R1 镜像）** | **163840** | 496128 | **1.493×** |
| 若不做 R1 镜像（仅供对照，非提案） | 81920 | 414208 | 1.246× |
| 溢出（2 容器，朴素不共享祖先） | 327680 | 659968 | 1.986× |

⚠️ **这不是判据**（`.claude/rules/fs-design.md`「比谁省不构成任何判据」），是代价披露。

**一个值得记下来的形状**：把 8 叶换成「8 叶 + 4 祖先」共 12 个单元一起算（`w = clamp(12+1,2,4)=4`，
12 恰好整除 3，3 条满条带、12 条记录），容器 COW 的字节数**仍是 163840**——記录数从 11/16 变成
12 对最终字节数没有影响，因为 163840 字节里 616~896 字节才是记录本身，其余全部是「一个容器
COW 一次」这个固定开销。**⇒ 这笔代价的主体是「触碰一次条带表容器」这个动作本身，不是记录数**，
只要没有跨容器边界，往一次发布里塞多几条记录几乎不加钱。

## 2. R4 三段发布顺序多出来的串行等待

**R4 逐字**：「① 一条条带的全部 `w` 个格写成功（含 parity）→ ② 才写这条条带的 `w` 条记录
（容器 COW）→ ③ 才发布根。」

**对照 D16 已定项 7 的持久顺序**：`COW 单元/节点 → 屏障① → journal 记录 → 屏障② → 根槽（FUA）`，
共三个序点（两道 FLUSH + 根槽 FUA）。

**这一段落在哪两个屏障之间要看一个未定的语义分叉，我不替它拍板**：

- 若 R4 的「写成功」只要求**写请求被确认（ack）**、不要求**已经落盘持久**：条带数据/parity
  与条带记录容器都可以算作 D16 已定项 7 里同一个「单元/节点」批次的成员，都在**屏障①之前**
  一起写、一起被那一次 FLUSH 覆盖 ⇒ **R4 不新增任何硬件屏障**，只是把这一批写拆成了「先提交
  条带数据/parity、等它们的写完成回调，再提交条带记录容器」两轮 I/O 提交（一次软件层的完成
  等待，不是设备级 FLUSH）。
- 若 R4 的「写成功」要求**已经持久**（本机 E44 明写「这台盘没有掉电保护 PLP」——没有 PLP 时
  「写完成」与「已经持久」不是一回事，普通写完成并不保证掉电后数据还在）：那就必须在条带
  数据/parity 写完之后、条带记录容器写之前**插入一次额外 FLUSH**，把 D16 已定项 7 的
  「2 FLUSH + 1 FUA / 3 序点」变成「3 FLUSH + 1 FUA / 4 序点」——多出的这一道恰好夹在
  「屏障①之前」这个阶段内部，把它拆成两次子阶段各自加一道屏障。

**R3 提案原文没有回答这个分叉**（它只写了「写成功」三个字，没说是 ack 还是 durable），
这本身就是一处未答，建议记进 `.claude/kb/checks-owed.md`。

**本机有没有能拿来估屏障代价的既有实测**：**没有能直接拆出「单次加一道 FLUSH 多花多少
时间」的数**。唯一沾边的是 E44 的 `sync_8` 臂（本机中位 2715 次/秒 ≈ 368.3 微秒/次），
但它量的是**整个 fsync 操作**（ext4 自身的日志开销、一次 FLUSH 语义全部混在里面），
不是每道屏障各自的边际耗时；E44 自己写明「它测的是 ext4 的 fsync 路径，不是本工程的……
这个数是本工程 fsync 率的一个上界代理」（`experiments/44-序号位宽的本机实测与代价.md`
「它答不了的」一节）。D25 自己对屏障口径的定性也写着「这是推，不是实测」
（`decisions/25-目标负载优先级.md:88`），C26（屏障数从没量过）至今欠账
（`decisions/16-发布语义.md:225`）。

⇒ **这一格算不出绝对值，缺的输入是：① R4「写成功」的语义要先定案（ack 还是 durable），
② 本机在多队列 / O_DIRECT 下"先等一批完成再提交下一批"相对"一次性提交全部再等一次"的
额外延迟，从未被任何实验单独测过。** 不拿 E44 的整体数字去顶这个空。

## 3. 该不该做成实验：建议 E107

**判：该。** 理由两条：（a）第 1 节的字节计算虽然是纯算术推导，但按本项目纪律
（`.claude/singlefs-ai-sop/rules/test-discipline.md`「阴性结果要能和『代码没跑到』分开」、
`three-way-inference.md`）它属于「从自己的推导里得出的结论」，没有走过带变异测试的实现，
不能直接当已验证的数字用；（b）第 2 节明确缺一个真机测量，纯推导补不上。

### E107 R4 发布顺序对 D25 主负载的写放大与串行等待代价（设计，未跑，不写代码）

**它要验的是**：D2 未定项 12 第三版 R1（整条链镜像）+ R3（parity 有记录）+ R4（发布顺序）
组合，在 D25 主负载下的两笔从未量过的代价——(a) 每次发布因维护条带成员表多写的字节数，
(b) R4 的写序对串行等待/屏障次数的影响。E106 明确不答这两项（见其「它不答什么」一节：
「代价那三个数只在『所有单元都参与 w ≥ 3 条带』这个假设下成立」，且 E106 量的是稳态**空间**
ppm，不是**单次发布**的写放大）。

**被引用条款**：本文件第 0 节列的全部五条，外加 E106 的 583 条记录/容器、828 789 容器基线，
E103 的容器索引条目宽度与扇出算法。

**两条臂**：

| 臂 | 做什么 | 类型 |
|---|---|---|
| 甲（字节模型） | 仿 E103/E106 风格的纯算术实现：给定「一次发布 N 个叶」与「当前打开容器已占用槽位数 f ∈ [0, 582]」，按 D2 已定项 6 切分条带、按 R2/R3 数记录数、按容器/索引扇出算 COW 字节，扫 N ∈ {1, 8, 12, 64} 与 f 的全部取值，输出与基线的倍数；同时把第 1.1 节两种切分读法（尾条带独立求值 / 沿用满批 w）各建一个变体一起跑 | 纯算术，本机不需要设备 |
| 乙（真机延迟） | 仿 E44 方法：O_DIRECT 对临时文件，比较「一次性提交条带数据+parity+记录容器共 k 块、等一次完成」对「先提交条带数据+parity 并等完成、再提交记录容器并等完成」两种提交模式的端到端延迟差，两种"写成功"语义（ack 完成 / `fdatasync` 之后）各测一遍 | 本机实测，要设备（临时文件，不进仓库） |

**阳性对照**：

- 甲臂：仿 E103 做法，把「容器」参数强行设成与索引节点同尺寸（16384）且不计容器索引层，
  这时打包侧那一层的代价必须与「记录直接住索引叶」模型的对应层相等——不等说明两条臂没有站在
  同一把尺子上，测量分不出差别。
- 乙臂：仿 E44 做法，在"先等完成再提交"那条路径的两轮之间人为插入一个已知长度的 `sleep`
  （如 5 ms），测出来的额外延迟必须落在这个已知值的 ±10% 内——测不出说明这套测量本身不够灵敏，
  另设 `nosync`（全部写不等待完成）对照，验证不等待时确实比等待快一个数量级（仿 E44 的
  `nosync` 32.1 倍差距那条阳性对照）。

**作废条款**：

1. 甲臂阴性对照：N = 0 时两侧字节数不为 0 ⇒ 整轮作废。
2. 甲臂饱和对照：N 远大于 583（如 N = 10000）时碰到的容器数与「N / 583 向上取整」之差
   超过 0.5% ⇒ 模型错，整轮作废。
3. 乙臂：`nosync` 与「等待完成」两臂无显著差异（<10%）⇒ 说明 I/O 根本没真正落盘/没测到，
   整轮作废（仿 E44 失败条款）。
4. 乙臂：五轮之间延迟离散超过 ±20% ⇒ 报「不稳定」，不下结论，不许当作已验证数字使用。
5. 读不到 ≠ 读到 0：任一轮拿不到耗时读数，该轮作废，不许当 0 算。

**至少两条钉绝对值的断言（实际会写五条以上，跑前写死）**：

- `records_per_container_matches_e106`：`103 + 56 × 583 + 17 == 32768`（直接抄 E106 已钉的数，
  不许重新拟合）。
- `container_index_height_is_pinned`：828 789 个容器、头 76、条目 85 时算出的高必须恰为 3；
  同时钉住交叉校验用的比值 `828789 / 4292 ≈ 193`（与扇出 191/192 同量级）。
- `mirror_doubles_component_bytes_exactly`：`81920 × 2 == 163840`，逐字节钉死镜像前后条带表
  组件那一侧的代价（不是钉整个发布的比值——那个比值不是 2 倍，见下面第 4 节）。
- `baseline_total_bytes_is_pinned`：`8×32768 + 4×16384 + 4096 + 512 == 332288`。
- 乙臂 `injected_sleep_is_recovered_within_tolerance`：注入 5 ms，测得值落在 [4.5 ms, 5.5 ms]。

**它不答什么**（跑前写死）：只覆盖 D25 主负载这一个点（8 叶 / 1 脊柱），不覆盖 metaheavy /
rand / multistream；不答加密开启后「锁盘期不修复」分支的代价；不裁决 R4「写成功」到底是
ack 还是 durable——甲乙两臂各自按两种语义都跑一遍，把两个数字都摆出来，语义本身仍要走
三方论证或用户定案；不答 R1 镜像的两份副本落在不同盘对乙臂真实延迟的干扰（先只测单盘）。

## 4. 核 R1「空间翻倍」这句话在写放大这一维成不成立

**E106 原文**（`.claude/kb/experiments/106-条带成员表的载体.md:41-42`）：
「臂甲 828 789 个容器 ⇒ 少装 828 789 个数据格 = 27 157 757 952 字节 = **1544 ppm**」，
「臂甲镜 …… **3088 ppm**（恰好 2 倍）」。这两个数**都是稳态空间 ppm**（占用整块 16 TiB 盘容量
的百分比份额），不是任何一次发布的写字节数。R3 提案原文写的是「这张表占的**空间**翻倍
（1544 → 3088 ppm）」——**这句话逐字核对下来是对的，E106 的两个数确实互为 2 倍，且提案只
claim 了空间，没有 claim 写放大**。

**「空间翻倍」推不出「写放大翻倍」**，本文第 1 节的算术直接证明了这一点：

| 维度 | 未镜像 | R1 镜像后 | 倍数 |
|---|---|---|---|
| 条带表**自己**的组件字节（本文 1.3 节） | 81920 | 163840 | **恰好 2.000×** |
| **整个发布**的总字节（本文 1.4 节） | 414208 | 496128 | **1.198×**（不是 2×） |
| 相对「不带条带表」基线的写放大倍数 | 1.246× | 1.493× | 差 0.247，不是差 1.246 |

**镜像确实把条带表自己那一份组件字节和它的稳态空间占用都精确翻了倍**——这是同一个机制
（w=2 意味着每个字节物理写两份、占两份空间），所以"分量级"上「翻倍」对空间和对该分量自身的
写字节是**同一件事**，都成立。但「写放大」这个词在本项目里（见 D25 的写放大定义）指的是
**一次发布的总字节 / 用户字节**这个系统级比值，而条带表只是这个总字节里的一小块附加项
（163840 / 496128 ≈ 33%），镜像只让**这一小块**翻倍，不会让**总比值**翻倍
——1.246× 到 1.493×，涨了 20%，不是涨了 100%。

**结论**：R1 的「空间翻倍」表述本身没有错，E106 的两个数支持它；但如果有人把这句话
外推成「所以写放大也翻倍」，那一步外推**不成立**，本文第 1.4 节的算式是反例。
第三版提案 R1 原文没有做这步外推，是干净的——这里核实的是「不许有人替它做这步外推」。

## 小结：给第三版第 4 处未答的直接回答

- **一次发布多写的字节数（典型情形）：163840 字节**，相当于把这次发布的总字节从 332288
  推到 496128，**写放大从基线的 1× 变成 1.493×**（若不镜像是 1.246×）。这个数的主体是
  「触碰一次条带表容器」这个固定开销（32768 容器 + 3 层×16384 索引节点，再乘 R1 的 w=2），
  跟这次发布产生几条条带记录几乎无关，只要没跨容器边界。
- **多几次串行等待：算不出绝对值**，因为 R4「写成功」的语义（ack 还是 durable）第三版没定，
  而两种读法下屏障次数不同（3 序点不变 / 变成 4 序点），且本机没有能拆出"单次多一道屏障"
  代价的既有实测——E44 只给整体 fsync 延迟、且明写是 ext4 路径的上界代理，不能拿来顶这个空。
- 建议：把语义分叉记进 `checks-owed.md`，把 E107 建档去补这两笔账（尤其是乙臂的真机延迟测量）。
