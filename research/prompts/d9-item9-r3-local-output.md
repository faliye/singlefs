1. At lock time, stripe S has slots A and B. Signed stripe membership table states S contains A,B. During lock period, stripe S is reconfigured to contain only A (B is removed). Keyless mount moves data from A to C. It checks stripe membership table, sees C not in S (since table still lists A,B), so move proceeds. Now S has no replicas replicas. Minimum two replicas requirement is violated. Rule broken: stripe membership must maintain width floor. Smallest change: exclude stripe membership from signed tables; keyless mount operates only on lease area without stripe knowledge. Stripe membership is encrypted metadata updated only during unlock.

2. Sixteen tebibyte pool with sixteen kibibyte slots has 16*1024^4 / 16*1024 = 1 billion slots. One bit per slot: 125 megabytes. One record per slot (e.g., 8 bytes): 8 gigabytes. Signing such a table at lock time requires processing all data. For 8GB, signature computation takes seconds to minutes on modern hardware, but for large pools this delays mount significantly. Rule broken: lock time must be practical. Smallest change: use bitmap for live slots (1 bit per slot) and compress the table. Alternatively, use a Merkle tree to sign only changes, not the entire table.

3. Container index is encrypted metadata. Physical pointer for a packed record container is held only in this index. Keyless mount moves container to new slot. During lock period, container index remains encrypted and unreadable. Keyless mount updates log with move but cannot update the container index. Volume is inconsistent: container index still points to old slot, but data is moved. No entity can read the container until unlock because the index is encrypted and not updated. Rule broken: consistency during lock period. Smallest change: store container index in plaintext but signed, or have keyless mount update the index via log entries that key side verifies during unlock.
