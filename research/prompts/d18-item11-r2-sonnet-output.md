## 场景一：rm -rf 1000 个文件，每删 10 个 fsync 一次

### 前提与显式假设

D16 已定项 6（decisions/16-发布语义.md:174-178）：每次发布把 checkpoint_txg 加一，fsync 触发的发布也是发布，
没有小发布不记号的例外。D23 已定项 1（decisions/23-journal的角色与格式.md:941-946）取甲：
每次 fsync 写脏叶 + 全部祖先 + 根槽 + 一条记录，祖先不延后。这两条合起来：1000/10=100 次 fsync
就是 100 次完整发布，checkpoint_txg 从 N 涨到 N+100，每次都写根槽。

D18 已定项 10（decisions/18-块里携带什么信息.md:523-528）：对象整个删除写一条区间记录（对象 ID + 全区间）。
本节按这条字面的最小范围建模：一个单 extent 文件的 unlink 产生恰好 1 条墓碑记录，
挂在数据 extent 死亡这一条线上（树 ID = 该头的 extent 树）。dirent 树、inode 树的键删除是否也要走同一条
墓碑机制，仓里没有写清楚（见下面的判决段），本节不把它们计入物理字节，只计数据 extent 的墓碑。

### 步骤

1. 100 次 fsync，每次新增 10 条墓碑记录（56 字节/条，E83 口径，
   research/e7-index-bench/src/bin/e83_tombstone_grain.rs:16）。
2. 容器容量 583 条/单元（E102 判据 3，头 90，experiments/102-单元类登记表与打包记录单元.md 实测行）。
   1000 条总量 > 583，全程会跨 2 个容器（约第 59 次 fsync 时第一个容器写满、切到第二个）。
3. 关键点：P4「容器的 COW 重写与索引」段（_d18-item11-r2-amended.md P4）说「一个开放容器在它所属代际内
   每次要发布时都被重写（COW），每次写出的是一个新单元（新诞生代号）」。D16 已定项 7
   （decisions/16-发布语义.md:212-220）：一次发布的持久顺序恒为 COW 单元/节点 → 屏障 → journal 记录 →
   屏障 → 根槽（FUA），fsync 等根槽持久之后才返回。这意味着凡是本次 fsync 新增了墓碑记录的那个开放容器，
   必须在这次 fsync 里整单元重写一遍并持久化——不这样做，fsync 的持久性承诺就是假的。
4. 于是：100 次 fsync，每次都要重写当前打开的那个容器（32768 字节 × w=2，D2 已定六写的粒度硬要求 2，
   decisions/02-RAID条带策略.md:8,26；D2 已定项 9 第一版 2 盘恒 w=2）。物理字节 = 100 × 32768 × 2 =
   6 553 600 字节 ≈ 6.25 MiB。
5. 容器索引（P4 新提出、P7 承认无落点的那棵树）每次也要改 1 条（该容器身份对应的物理指针从旧值改成新值）——
   这是一次普通的 COW b-tree 点更新，至少再重写它自己的一个 16 KiB 叶 × w=2 = 32 KiB；
   100 次 fsync 又是约 100 × 32 KiB ≈ 3.13 MiB（不含它自己的祖先节点传播，D3 已定项 5 的聚簇优化能部分压低这一笔，
   但压不到 0）。
6. 与 E83 的口径比：E83（experiments/83-墓碑的粒度.md）算的是「一次性写完」的口径——
   1000 条墓碑记录 ceil(1000/583)=2 个容器，一次性写完只需 2 × 32768 × 2 = 131 072 字节 = 128 KiB。

### 数字对照

| 口径 | 物理字节（仅容器本身） |
|---|---|
| E83 单次批量写完（无 fsync 打断） | 128 KiB |
| 本场景：每 10 个文件 fsync 一次 | 6.25 MiB |
| 倍数 | 约 50 倍 |

再加上容器索引每次改动的约 3.13 MiB，以及 100 条 journal 记录（每条头 78~95 字节 + 点名项，
D23 已定项 12 记录尺寸 4 KiB，decisions/23-journal的角色与格式.md:1106-1111）与 100 次根槽 FUA
（127 字节，D22 已定项 7，decisions/22-单元原子性怎么合成.md:392-396）——这两笔相对小，
但同样是「E83/E84 没算」的那一类。

### 判决

打中，改成什么：E83、E84 都是纯算术、单次批量写完的模型，明写「文件操作 0 处」（E83「它答不了的」段）、
「不答打包单元在一个快照代际内被多次发布时写几次」（E102 experiments/102-单元类登记表与打包记录单元.md
「它答不了的」段）。本场景把这条留白坐实成一个具体数字：fsync 打断的现实工作负载下，
物理写比 E83 的 107 MiB/百万文件口径贵约 50 倍（仅容器本身，不含容器索引与 journal/根槽）。
提案 P5 已经用一句警示「⚠️ 开放容器每次发布重写一次...E83 的 583× 只在一次发布装满一个容器时成立」
承认了这条，但没有给出量；本场景把量算出来了，应当补进 P8 或 P5 的欠账段。
另外，dirent/inode 树的键删除是否也要走墓碑机制这件事全仓没写清楚——
如果要，上面的数字还要乘以涉及的树数，这是本场景暴露的一个格式级空白，
不是本节能替它答的（详见场景七之外，这里单独记一笔：D18 已定项 10 的字面范围只覆盖「对象整个删除」
对应的数据 extent 区间记录，没有明说 dirent 树 (parent,name)→inode 这一条键的死亡要不要另开一条墓碑）。

## 场景二：容器号分配器住哪、崩溃后与全丢重建各自怎么恢复、两头会不会撞

### 步骤

1. P4 给容器号的定义：「树内按类型单调分配，发布无关——容器被 COW 重写时不变」。
   这是一个新的逻辑计数器，不是 D3 的物理空间分配器。D3 已定项 3
   （decisions/03-空间分配.md:101-127）分配的是落点（设备身份 + 设备内偏移），
   D3 已定项 7（decisions/03-空间分配.md:197-228）给的 key 是 (设备身份 4, 16 KiB 槽号 6)——
   这两样都是物理地址，不是「给一个逻辑身份分配下一个整数」这类计数器。
2. 全仓检索「对象 ID 分配」「inode 号分配」「单调分配」：唯一命中的是
   decisions/08-核心索引结构.md:401，只说「给 inode 号的重复配了权威规则」，
   没有一处定义 inode 号本身怎么分配、崩溃后下一个号从哪来。容器号分配器是这一类问题的第二个实例，
   而第一个实例（inode 号）到今天也没答案——这不是巧合，是这个设计里一整类问题
  （单调逻辑 ID 分配器的崩溃恢复）从未被处理过。
3. 正常重启（索引/容器索引树本身没丢，只是要重放 journal）：能不能不做全表扫描就拿到「下一个容器号」，
   取决于容器索引树的 key 长什么样——而这正是 P7 自己列的欠账第①条：
   「容器索引无落点...key 必须给得出四元身份」。如果容器索引的 key 是
   (树, 类型, 容器号, 容器出生代) 这个顺序（容器号排在容器出生代前面），
   「这棵子树里最大的容器号是多少」是一次 O(log N) 的树内最右键查询，不违反
   .claude/rules/fs-design.md 第一格「运行时决策路径不许遍历」。如果顺序反过来
  （容器出生代在前），要拿到「历史上出现过的最大容器号」就得扫遍每个容器出生代分桶，
   退化成扫描。这个顺序提案一个字都没定，是本场景暴露的新空白。
4. 索引全丢，扫描重建：这时候本来就要全盘扫描来重建一切（fs-design.md 第二格「checker/审计...
   必须遍历」明确豁免），扫描过程中顺手取每个已认领码 3 容器头里的容器号字段（P4 类身份段第 3 项），
   按 (树, 类型) 分组取最大值 + 1，作为该 (树, 类型) 之后分配的起点。这条路径没有违反任何硬要求，
   是唯一在提案现有材料下站得住的恢复路径。
5. 「从扫描到的最大容器号 + 1 恢复」之后，两个头（D6 已定项 1，decisions/06-快照实现模型.md:146，
   每头一棵自己的树）各自的分配器会不会撞：不会，因为 AAD/身份四元组是
  (树 ID, 打包记录类型, 容器号, 容器出生代)，树 ID 对两个头必然不同（D9 已定项 6：
   「树 ID | D8 是多 keyspace，对象号在不同 keyspace 里各自编号、必然碰撞」，
   decisions/09-加密.md:261——这条本来就是在说不同 keyspace/不同头的树 ID 不能共用同一个编号空间），
   只要计数器按 (树 ID, 类型) 各自独立维护，两头的容器号即使数值相同也不构成身份碰撞。
6. 但即便计数器真的因为崩溃回退、重发了一个之前用过的容器号，也不必然出问题：
   身份四元组还带着「容器出生代」（分配那次发布的 checkpoint_txg），只要新分配发生在
   一个更晚的 checkpoint_txg，新旧两个容器的四元身份仍然不同（容器出生代不同）。
   真正会出事的只有一种情况：容器索引树的 key 如果没有把「容器出生代」也编进去（只用
  (树, 类型, 容器号) 三元组当 key），一次容器号重用会直接覆盖掉旧容器仍然有效的那条指针，
   把它变得不可达——这又绕回第 3 步的同一个空白：容器索引的 key 形状没有定案。

### 判决

打中，改成什么：容器号计数器的持久落点/恢复算法全仓无一字定义，这不是提案独有的问题——
inode 号分配同样没有答案，说明这是这个设计里被反复回避的一类问题。好消息是身份四元组
（含容器出生代）本身对计数器倒退是有弹性的，不会直接导致 AAD/身份碰撞；坏消息是这份弹性
完全依赖容器索引树的 key 包含全部四个字段并把容器号放在能被高效 max 查询的位置，
而这两点都是 P7 自己列出、至今没有形状的欠账。建议提案在 P7 的欠账①里明确补一句：
容器索引的 key 编码顺序必须让「(树,类型) 下最大容器号」可以用 O(log N) 查询拿到，
否则计数器恢复只能退化为扫描，撞 fs-design.md 第一格。

## 场景三：崩溃在「新版容器已写出、容器索引已更新、根还没发布」

### 步骤

1. 按 D23 已定项 1 的甲模型（每次 fsync 写脏叶+祖先+根槽+一条记录，祖先不延后），
   「容器索引已更新、根还没发布」只能理解成崩溃发生在一次 fsync 中途——单元/节点写完了，
   但 journal 记录与根槽 FUA 这两步（D16 已定项 7 的持久顺序）还没完成。
2. 子情形 A（journal 记录也没写）：没有任何持久记录点名这次写。重启后 journal 重放
  （D23 已定项 14，decisions/23-journal的角色与格式.md:1163-1180：只施加 (实例代号,checkpoint_txg)
   严格大于根水位的记录）不会碰这个事务，根仍停在旧的 checkpoint_txg=N。
   盘上同时存在旧容器（诞生代号=N 或更早，仍被有效根引用）与新容器（诞生代号=N+1，孤儿）。
3. 分配记录（D3 已定项 1，decisions/03-空间分配.md:43-61）此时怎么说：分配记录树本身也是一棵 COW 树，
   它自己的更新同样卷在这次没有发布的事务里——它的持久变更同样没有落到当前有效根，
   所以从「新版容器已分配」这个角度看，D3 已定项 5（decisions/03-空间分配.md:163-179）
   的语义是「本事务内产生的分配，事务不发布就等于没发生」：新容器占用的物理落点，
   从当前有效（旧）根的视角看仍然是未分配的。
4. I-1.2（invariants.md:21，块头代号不超当前）：新容器头里的诞生代号 N+1 > 根记录当前 checkpoint_txg N，
   这正是 D18 已定项 7「三条独立理由」第二条要防的「撕裂事务留下的孤儿单元」（decisions/18-块里携带什么信息.md:429-432）；
   E88 的「撕裂孤儿 ×9」夹具（experiments/88-冒名单元与孤儿单元的判别.md 夹具表）
   与「诞生代号 > 根 txg、无分配记录」逐字对应，判定结果是「清」（正类判别，可回收）。
   这一半机制是站得住的，不是本项新引入的洞。
5. deadlist 什么时候能回收旧版：旧容器不是死的——它仍然是当前有效根引用的那一份，
   deadlist/D5 的 birth/death 判定不适用于它。旧容器只有在后续一次成功重放/重做同一个操作、
   新事务真正发布之后才会成为「被超越的旧版本」，进入正常的 D5 kill 判定
  （birth ≤ prev_snap_txg 时进 deadlist，否则直接释放）。也就是说，本场景问的「崩溃留下的孤儿」
   与「旧容器什么时候能被回收」是两件不同的事：前者靠 I-1.2/撕裂孤儿判定当次挂载就能清；
   后者要等一次成功的后续发布才会触发，不是本场景崩溃本身的产物。
6. P4「同一身份取诞生代号高者」这条规则与 A6（AAD 期望值不来自明文侧）的关系：
   D9 已定项 6 的 A6（decisions/09-加密.md:293-300）管的是 AAD 字段的期望值来源，
   而「诞生代号」本身不在 P4 给出的 AAD 变体里（P4：AAD = (标签,树ID,打包记录类型,容器号,容器出生代)，
   诞生代号不在其中，正如数据单元的 AAD 五元组里也没有「诞生代号」这个字段，
   只有「对象出生代」这个不同的概念）。所以字面上不撞 A6——A6 管的是「AAD 字段的值从哪来」，
   诞生代号不是 AAD 字段。但这不代表「取更高者」这条规则本身没有风险：它没有显式声明
  「只在候选先通过 I-1.2（诞生代号 ≤ 根 txg）之后再比较」，如果实现者照字面理解，
   会在扫描重建阶段把本场景里那个 N+1 的孤儿容器当成「更新版本」选中——这与 I-1.2、
   与 D18 已定项 7 「三条独立理由」第二条的整个设计意图直接矛盾。
7. 另外，P4 把这条规则的出处标成「D3 已定项 1 的逐落点谓词那一格」——查
   decisions/03-空间分配.md:43-61，已定项 1 回答的是「这个落点属不属于现行版本」，
   靠的是分配记录 + deadlist 两个持久结构；而扫描重建（索引与分配记录都在被重建的过程中）
   不可能反过来先用分配记录去判定容器新旧——这是一个自举顺序上的引用错误：
   「同一身份取诞生代号高者」是扫描重建自己需要独立回答的问题，不能引用一个
   本身要靠它才能被重建出来的结构。

### 判决

打中两处，改成什么：① 「同一身份取诞生代号高者」必须显式加一个前置条件——
仅在诞生代号 ≤ 根记录当前 checkpoint_txg（即先过 I-1.2）的候选之间比较，
否则字面执行这条规则会让 I-1.2 已经拦住的撕裂孤儿在「取高者」这一步被重新捡回来，
抵消 E88 已经验过的 91 字节头 + 认领规则那套防线。② P4 对这条规则的出处引用
（D3 已定项 1 的逐落点谓词）是自举顺序上的误引，分配记录树在全丢扫描重建时本身
也在被重建，不能被引用为「谓词从哪来」；正确的写法应该是「扫描重建自己内部的一条
版本消歧规则，输入只有 I-1.2 已经筛过的候选集合」，与 D3 已定项 1 无关。
其余部分（旧容器不进 deadlist、要等下一次成功发布才触发 kill 判定）站得住。

## 场景四：代际的导出——快照表在哪、扫描重建拿不拿得到、E84 的模型改了之后还成不成立

### 步骤

1. P5 第 2 条：「代际不存字段：容器的代际 = 快照表里包含其容器出生代的那一段
  （快照表住权威态的根 / 树表，扫描重建拿得到）」。
2. 全仓检索「快照表」这个概念找不到对应的持久结构。最接近的候选是 D22 已定项 7
   的树表单元（decisions/22-单元原子性怎么合成.md:371-409）——但它的字段表只给了
   magic/fsid/flags/实例代号/checkpoint_txg/树表单元指针/自证校验和，
   「树表单元」本身装的是「每头一棵树的根指针」（decisions/22-单元原子性怎么合成.md:397：
   「树表单元：16 KiB 元数据单元，装 267 棵/层」），没有一处说它带每棵树/每个快照的
   诞生 txg 或死亡 txg 区间。
3. D5（快照/空间记账机制）自己承认这个格式要求还欠着：
   decisions/05-快照-空间记账机制.md:192「快照列表必须是可枚举的持久结构，
   见 I-3.7（活快照可枚举）」；再往上一行（decisions/05-快照-空间记账机制.md:190）
   逐字：「扫描式 checker...需要三样：birth 内联在指针里 ✓、deadlist 自身是可扫描的
   自描述树 ✓、全部根的 txg 列表 ❌——第三样是 D5 欠着的格式要求」。
   I-3.7（invariants.md:116）状态是「未实现」，且不只是 checker 未实现——
   连它该长什么样（key、value、住哪棵树）全仓一个字都没写。
4. `prev_snap_txg` 这个字段（D5 唯一提到的、与快照 txg 相关的持久量）被描述为
  「活头头部一个标量，常驻内存」（decisions/05-快照-空间记账机制.md:142），
   只给出「一个可写头当前记得的上一个快照点」，不是「这个头历史上全部快照的 txg 列表」——
   即使把它当成快照表的雏形，它也只有最近一个点，答不出「checkpoint_txg=X 落在哪一段代际里」
   这种任意历史时刻的区间归属查询。
5. P5 这句话要求扫描重建（索引全丢，包括树表单元本身如果没了也要重建）阶段就能拿到
  「快照表」，可这张表连持久形态都不存在，扫描重建更不可能凭空拿到它——这不是
  「实现细节待补」，是这句话依赖的输入对象在格式层没有任何落点。
6. E84 的验证模型（research/e7-index-bench/src/bin/e84_tombstone_pinning.rs:110）：
   `if !u.cohorts.is_empty() && u.sealed && u.cohorts.iter().all(|&c| c <= dead_upto)`——
   E84 的回收判据直接读的是模拟里显式维护的 `u.cohorts: Vec<u64>`，也就是说 E84 验证
  「按代际装载钉住恒为 0」这个结论时，模型本身假设每个单元自己记着它装的是哪个/哪些代际
  （模型里是显式字段），不是靠事后查一张外部快照表反推。这与 P5「代际不存字段」的提案
   形态是两回事：E84 验证的是「容器自己知道自己的代际」，P5 提议的是「容器自己不知道，
   靠外部表推」，而那张外部表在格式上不存在。E84 的 0% 结论不能直接搬来支持 P5 这句话——
   它验证的是另一种（有显式字段的）机制。

### 判决

打中，查不动的地方一并写明：「快照表」不是一个只差实现的空白，是一个连持久结构的形状
（住哪棵树、key 是什么、谁在什么时候写它）都没有定义过的对象——D5 自己的文本已经把它
列成欠账（「全部根的 txg 列表 ❌」），P5 却把它当成「扫描重建拿得到」的既成设施来用。
这条依赖必须先补上「快照表」本身的格式定案（大概率要落在 D5 或 D22 里另开一个分项），
否则 P5 第 2 条的「代际不存字段」这句话没有对象可以推导代际归属。在那之前，
E83/E84 已经量出的「按代际装载钉住恒为 0」这个结论也不能直接算作已经证明 P5 的可行性——
E84 验证的模型本身带着显式的每单元代际字段，与 P5 提议的「不存字段、外推」不是同一个机制，
这一段属于查不动（因为没有可查的对象），不是打中一个具体错误——但恰恰是这类查不动
最值得记，因为它说明提案在这一条上是在向一个不存在的结构借力。

## 场景五：扫描重建的解析顺序与 C99 自证样本

### 判定顺序（按 P4/P9 与已有条款拼出的完整链）

1. 头校验和（32 字节，覆盖整个头，包括共同前缀与类身份段——
   D18 已定项 7「头完整性唯一防线」decisions/18-块里携带什么信息.md:398）。
2. 类身份段解析：树 ID、打包记录类型、容器号、容器出生代、记录数、诞生代号、fsid、
   载荷校验和字段本身的结构性解出；连带 I-1.2（诞生代号 ≤ 根 txg）、I-1.3/I-1.4
  （树 ID/fsid 一致性）在这一步或紧随其后完成。
3. 记录数 × 记录宽 + 90 ≤ 声明长度（P5 第 4 条：「这是头合法性条件，在认领时判，不等到解析」）。
4. 载荷校验和（4 字节 CRC32C，覆盖记录区到单元末尾含补齐）。
5. 逐条记录解析（按记录类型登记表给出的记录宽定宽切分）。

第 3 步排在第 4 步之前，这个顺序是对的：D23 已定项 1 的 B 条（decisions/23-journal的角色与格式.md:1036）
早就给出过同一条纪律——「记录自述长度，且先边界检查再算校验和」，理由是不先做边界检查就去读
（甚至去算校验和覆盖范围）有越界读的风险。P4/P9 这条顺序与 journal 记录头的既定纪律一致。

### C99 自证样本走一遍

造样本：头好、载荷改一个字节、诞生代号 ≤ 根 txg、落点有分配记录。

| 步骤 | 判定 | 结果 |
|---|---|---|
| 1 头校验和 | 头没改，通过 | 过 |
| 2 类身份段 + I-1.2 | 字段没改，诞生代号合法，通过 | 过 |
| 3 记录数×记录宽+90≤声明长度 | 元数据字段没改，通过 | 过 |
| 4 载荷校验和 | 载荷改了一字节，CRC32C 不匹配 | 不过，整单元拒收 |
| 5 逐条记录 | 不会执行到这一步 | — |

在第 4 步被拒收，与 P4「扫描重建必须整单元拒收」的设计意图相符。

去掉载荷校验和之后：步骤 1-3 照常通过，第 4 步不存在，直接进入第 5 步逐条记录解析——
被改的那个字节落在某条记录的字节范围内，被当成该记录的合法内容原样解出，不会被任何机制拦下
（除非那条记录恰好在语义层面产生一个能被下游检测出的矛盾，这不是通用保证）。
即「从拒收变收进」，与提案自己的判决一致。

### 4 字节 CRC 对 32 KiB 载荷够不够

D19 已定项 4（decisions/19-块指针的结构与宽度预算.md:180-192）：位置条目里的密文校验和取 4 字节
（32 位），保护的正是一个最大到 32 KiB 的物理单元内容，这是本工程已经确立的先例——
同样 4 字节宽度、同样量级的载荷。D9 已定项 1（decisions/09-加密.md:52）确立了「无密钥校验和」
这一类字段普遍存在的必要性（查损坏，不查攻击）。P4 的载荷校验和取相同的 4 字节 CRC32C，
与这两条先例口径一致，不是孤立选择。E76（decisions/23-journal的角色与格式.md 已定项 13 段）
已经实测过 CRC32C 在「头落了、载荷只落了一半」这类撕裂场景下的判别力（14 单测/8 变异全抓），
虽然测的是 journal 记录（4 KiB 量级），但撕裂检测的机制（前后内容不连续导致 CRC 不匹配）
不依赖载荷具体多大，检测原理对 32 KiB 同样成立；CRC32C 不是抗攻击的密码学校验，
但这条防线在第一版（未加密）本来就只承诺查损坏，与 D9 已定项 1 的定位一致。
这一格不是新洞，是既有设计取向的延续。

### 判决

站住，一处小改：判定顺序与 D23 已定项 1 的 B 条既定纪律一致（先边界检查再算校验和），
C99 自证样本按提案设计精确在第 4 步被拒收、去掉校验和后精确在第 5 步漏进，与提案的
判决描述完全对应。4 字节 CRC32C 宽度与项目已有的 D19 已定项 4、D9 已定项 1 两条先例口径相符，
不构成新的薄弱点。唯一要补的一句话：P9 的连带修改清单应该把「先边界检查、后校验和」
这条顺序显式写成一条不变量（不能只靠 P4/P5 的行文顺序隐含），并注明它与 D23 已定项 1 的 B
条是同一条纪律的两个实例，否则将来任何一处实现都可能悄悄把顺序倒过来。

## 场景六：inode 打包路①的更新路径

### 步骤

1. inode 树叶子存什么：按 P4「容器索引（P7 那棵树）是打包单元物理指针的唯一持有者；
   别的树只按身份引用容器」，inode 树叶子存的是逻辑身份而不是物理指针：
  (树 ID 8, 打包记录类型 2, 容器号 8, 容器出生代 8) + 槽号。容器容量 233 条
  （E102 用头 90 重算的结果与 E98 的 233 一致，experiments/102-单元类登记表与打包记录单元.md
   判据 3 行；experiments/98-inode记录与inode树的几何.md「打包进共享单元」行），
   ceil(log2(233))=8 位，槽号取 1 字节足够。合计 8+2+8+8+1=27 字节。
   对比 E98 的「住索引叶」直接内联形态：140 字节/条（experiments/98-inode记录与inode树的几何.md
  「记录 140 字节」行），打包+索引形态的 inode 树叶子条目反而更窄（27 对 140），
   但代价转移到了下面几步。
2. 改 mtime：容器出生代（分配时的 checkpoint_txg）在容器被 COW 重写时不变——这是 P4 明确定义的，
   所以只要 inode 树叶子存的是这个稳定的四元身份而不是物理指针，改 mtime 造成的容器 COW 重写
  不需要触碰 inode 树叶子本身，也不需要触碰同一容器里另外 232 条 inode 记录各自的叶子引用。
   这一点提案「容器的 COW 重写与索引」段已经自己论证过，本场景核实之后认为它站得住：
   与 D14 已否的「跨文件尾部打包」（decisions/14-双轨大小文件-持久临时.md:61）
  「另一个文件的指针也得改」这个问题不同，四元身份的间接层确实吸收了这次变更，
   232 个不相关的 inode 条目不需要改写。
3. 但代价没有消失，只是转移了：改 mtime 要求整个 32 KiB 容器重写（COW，w=2）=64 KiB，
   加上容器索引里那 1 条指针更新（至少 1 个 16 KiB 叶 × w=2=32 KiB），
   合计至少 96 KiB 物理写，只为改动一个 8 字节的 mtime 字段。
4. 与 E98「住索引叶」形态比：那种形态没有容器索引这一层，改 mtime 直接 COW 那条 inode
   记录所在的 16 KiB 索引叶（116 条/叶，E98「叶扇出恒 116」），物理写 = 16 KiB × w=2=32 KiB。
   即打包+索引形态比直接内联形态贵约 3 倍（96 KiB 对 32 KiB），且多一层间接。
5. 一次 stat 要几次查找：打包形态需要 2 次树内查找（inode 树取四元身份+槽号，
   容器索引树取物理指针）再加一次 32 KiB 物理块读取（只用其中 140 字节）；
   E98 的直接内联形态只需要 1 次树内查找（inode 树叶子本身就是 16 KiB 索引节点，
   读到即拿到记录），没有第二棵树、没有多余的物理块读取。打包形态每次 stat 多一次点查。
6. 爆炸半径（C100 关注的点）：两种形态都不是 0（E98 已经量过，116 对 233，
   experiments/98-inode记录与inode树的几何.md「永久损失」表），打包形态一次容器损坏
   丢的记录数反而是直接内联形态的约 2 倍，本场景的量没有改变这个既有结论。

### 判决

不算判死，但代价被具体量出后明显劣于 E98 已经比较过的「住索引叶」形态：写放大约 3 倍
（96 KiB 对 32 KiB），读路径多一次树查找，爆炸半径仍然是直接内联形态的约 2 倍且没有改善。
提案 P7 自己承认「路①的更新代价（改一条记录=COW 32 KiB × w）未测——新欠账」，本场景把这笔账
算出来了：它足以成为 D8 未定项 6 选路时的一条实质性反对证据，不应该只停留在欠账清单里，
应该被拿回 D8 未定项 6 的候选比较表，与「权威态清单扩项（路②）」正面对比之后再定案。
提案关于「间接层避免了 D14 已否的另一半问题」这条论证本身站得住，值得保留。

## 场景七：加密开启后，不认识打包记录类型 2 的旧读者

### 步骤

1. 旧读者拿到密钥挂载：它从 inode 树 key（P7 承认的欠账①，容器索引 key 必须给得出四元身份）
   拿到 (树 ID, 打包记录类型, 容器号, 容器出生代)，其中打包记录类型码本身是个裸整数，
   不需要理解它的语义就能原样复制进 AAD 计算（P4 AAD 变体 = (标签3, 树ID, 打包记录类型,
   容器号, 容器出生代)）——按 A6（decisions/09-加密.md:293-300），期望值来自查找路径，
   旧读者能算出正确的 AAD，能过 MAC。
2. 挂只读吗：P6 给「新增打包记录类型 = compat_ro 位」，D15 判定表
  （decisions/15-格式冻结政策.md）里 compat_ro 的标准含义是「不认识就退化为只读挂载」——
   这与 D23 已定项 1 的 A 条（decisions/23-journal的角色与格式.md:1036，journal 记录类型
   未知则拒绝挂载）政策相反，但 P6 明确说这是两个不同命名空间、不同政策的选择，
   这条区分本身是合理的（journal 记录关系到能不能正确重放，打包记录类型只关系到
   能不能理解某类元数据内容）。挂只读符合 compat_ro 的常规语义。
3. 会不会把这些容器当垃圾回收：P6 原文明写「过了 MAC 之后按声明长度整体跳过，不许回收」——
   设计意图清楚，但检索全仓不变量清单（I-1 到 I-8 各类），没有一条现成的可判定不变量
   显式写着「不认识类型的打包容器不许出现在任何释放集合里」。E102 的判据 6
  （experiments/102-单元类登记表与打包记录单元.md 判据 6 行）确实在计数模型层面验过
  「m 个未登记记录类型的容器：可验恰 m、应用记录恰 0、只读、不许回收」，但这是模型自证，
   不是针对未来某个真实 GC/scrub 实现的可判定检查。
4. 哪条不变量拦它：机制上，「不回收」这件事天然靠一个消极事实成立——不认识某类型的读者
   根本不会对它的容器索引条目发出删除指令（它连这条记录活不活都判断不了），
   所以只要 GC/scrub 代码路径本身遵循「不认识的类型一律跳过写操作」这条约定，
   垃圾回收自然碰不到它。但这是一条运行时行为约定，不是一条静态可判定的不变量，
   现有的 I-x.y 清单里找不到一条能在黄金镜像上直接判红的检查来验证这件事。

### 判决

打中一处，改成什么：能只读挂载、能过 MAC，这两点站得住；「不许回收」目前只是提案正文里的
一句设计意图和 E102 模型层面的自证，没有落成一条可判定的不变量。应当在 P9 的连带不变量
清单里新增一条（可以并进 I-6.2 或者新开一条），字面要求类似：「任一未在打包记录类型登记表中
出现的码，其所属容器物理指针不得出现在任何回收/复用操作的输入集合里；违反此条的构造样本
（人为触发对未知类型容器的回收）必须能被崩溃点重放或 checker 判红」。这不是推翻提案，
是把已经说清楚的设计意图从「正文里的一句话」升级成「门禁能拦的一条检查」，
按 show-me-test 的纪律，说了不做就等于没说。

## 场景八：同一容器/跨容器的两次死亡，墓碑区间记录能不能分清

### 步骤

1. D18 已定项 8 原文（decisions/18-块里携带什么信息.md:275-277）给墓碑的原始字段集是
  「沿用已定项 3 的那五个（单元类型标签、树 ID、对象 ID、对象出生代、锚点偏移）」——
   注意这里明确包含「对象出生代」。
2. D18 已定项 10（decisions/18-块里携带什么信息.md:525-526）改写载体之后给的记录粒度描述是
  「对象整个删除写一条区间记录（对象 ID + 全区间）」——这句话字面上只提到对象 ID 和区间，
   没有再提对象出生代。P6 给打包记录类型 1（墓碑区间记录）的宽度是「56 是量级假设，
   字段表随 C84」——即字段表至今没有定案（checks-owed.md:95，C84 仍是「量化已还，
   字段表随 C84」的未完成状态）。
3. D9 已定项 6 里「对象出生代」这个字段存在的理由写得非常直接
  （decisions/09-加密.md:263）：「inode 号复用后旧文件与新文件的 (树, 对象, 偏移) 完全相同」——
   这正是本场景「K 被删、K 被重建、K 又被删」要测的那个情况：如果 K 被重建时复用了
   同一个对象 ID（这本身是不是会发生，同样属于「inode 号分配策略未定义」这个場景二已指出的空白），
   两次死亡在 (树 ID, 对象 ID) 这个坐标下无法区分，除非墓碑记录本身也带上对象出生代。
4. 若两条墓碑记录都不带对象出生代，只带 (对象 ID, 区间)：扫描重建应用第一条墓碑
  （杀死第一代 K 的数据区间）之后，如果第二代 K 已经在同一区间写入了新数据
  （复用了同样的锚点偏移范围），第一条墓碑会不会连带杀掉第二代的活数据，
   取决于应用墓碑记录时是否连带比对数据单元自己头里的「对象出生代」字段——
   数据单元本身仍然带着对象出生代（这个字段没有被这次改动影响），
   只要墓碑应用逻辑同时核对「被杀数据的对象出生代是否等于（或早于）墓碑所指的那一代」，
   就能避免误杀第二代的活数据。但这个核对逻辑需要墓碑记录本身携带对象出生代作为比较基准，
   否则「墓碑所指的那一代」这句话没有输入。
5. 换句话说：数据单元头本身的对象出生代字段能保护数据不被误杀，前提是墓碑记录里也有
   同一个字段可以比较——而 P6/D18 已定项 10 目前给出的墓碑记录字段（对象 ID + 全区间）
   里没有它。这是相对 D18 已定项 8 原始五元组的一次实质性收窄，且没有在决策历史里
   记一笔「为什么可以去掉对象出生代」。
6. 同容器或跨容器不改变这个结论：P5 第 2 条把容器绑定到单一代际，两次删除如果跨越了
   代际边界（正常情况下会，因为中间还有一次重建），两条墓碑记录自然落进不同容器；
   即使凑巧落进同一容器（同一代际内的快速创建-删除-重建-删除），字段缺失的问题
   在容器内部同样成立——这不是容器边界的问题，是记录字段表本身的问题。
7. 幂等性：P4 说「墓碑记录重复应用幂等」，这句话本身没错——同一条物理墓碑记录被
   应用两次（比如 journal 重放窗口重叠）确实是幂等的，这是集合并运算的性质。
   但幂等性回答的是「同一条记录重复应用会不会出错」，不回答本场景真正的风险
  「一条为旧一代写的墓碑记录被错误地应用到新一代的数据上」——这是两个不同的问题，
   提案的幂等性论证没有覆盖后者。

### 判决

打中，改成什么：D18 已定项 10 把墓碑记录的字段从原始五元组收窄到（对象 ID + 全区间）之后，
丢掉了「对象出生代」，而这个字段存在的理由（D9 已定项 6，防止对象 ID 复用后新旧数据混淆）
逻辑上同样适用于墓碑记录本身——否则墓碑机制在对象 ID 复用场景下无法正确区分两次死亡，
有静默误杀新一代活数据（或反过来，漏杀旧一代死数据）的风险。这不是本轮提案（第二版）
新引入的问题，是 D18 已定项 10 早先定案时就已经存在、至今仍标记为「字段表随 C84」的空白，
但第二版提案在重新梳理墓碑记录的类身份段（P4）时应该顺手把这个欠账接住，
在 P6 的记录类型 1 字段表候选里明确加入对象出生代这一项，并在 checks-owed 的 C84
里加一句「记录字段表必须包含足以区分同一对象 ID 跨代复用的字段，否则回收路径存在
误杀活数据的风险」，而不是继续只写「量级假设」。

## 综合小结（不重复各场景判决细节，只列落点）

| 场景 | 判决 |
|---|---|
| 一 rm -rf + fsync 打断 | 打中：fsync 交织写放大约 50 倍于 E83 单次批量口径，应补进 P5/P8 欠账 |
| 二 容器号分配器 | 打中：持久落点/恢复算法未定义，但四元身份对计数器倒退有一定弹性，取决于容器索引 key 顺序（P7 欠账①）|
| 三 崩溃在根发布前 | 打中两处：诞生代号取高者规则缺 I-1.2 前置条件；出处引用 D3 已定项 1 是自举顺序上的误引 |
| 四 代际的导出 | 打中：所依赖的「快照表」在格式层不存在，是比「待实现」更彻底的空白；E84 验证的是另一种（有显式字段的）机制 |
| 五 扫描解析顺序与 C99 | 站住：顺序与 D23 已定项 1 的 B 条一致，C99 样本行为与提案设计相符，4 字节 CRC 宽度有先例支持 |
| 六 inode 打包更新路径 | 不算判死，但代价量化后明显劣于 E98 已比较的替代形态（写放大 3 倍、多一次查找），应回 D8 未定项 6 重新比较 |
| 七 加密后旧读者 | 打中一处：不许回收目前只是设计意图，没有可判定的不变量兜底 |
| 八 同对象 ID 跨代死亡 | 打中：墓碑记录字段表缺对象出生代，是 D18 已定项 10 定案时就有的既有空白，第二版应顺手接住 |
