1. No, there is no reachable state where a code carried by a unit, record, or root is issued again by a later acquisition. In the described I/O error path, if the rewrite back to the old code succeeds, both devices revert to the old code and no units are written with the new code. If the rewrite back fails, the mount becomes read-only and no units are written with the new code. Thus, the new code is never used in any units. P4 does not report this legitimate state as an error because there are no units, records, or roots with the new code, satisfying both conditions of P4.

2. Yes. For example: First mount acquires code 5, writes it to slot 0 on both devices with generation 1. Publish rotates superblocks, writing slot 1 with generation 2 and code 5. Next mount acquires code 6, writes to slot 0 with generation 3. Publish rotates again, writing slot 1 with generation 4 and code 6. Now, code 5 is no longer in any superblock slot. The next acquisition reads superblocks and sees code 6, making code 5 invisible to the acquisition process, though it remains tracked via the instance table.

3. Yes, P5 opens a hole. If a rollback is started, the new code is written to superblocks, then a crash occurs before the rollback publish is confirmed. The next mount sees the new code in superblocks but acts as if no rollback occurred. However, the correct state should have the previous code, not the new code. This causes the next acquisition to use the new code + 1 instead of the correct previous code + 1, leading to inconsistent instance code assignment. The shadow ledger may prevent unit reuse, but the superblock state discrepancy remains.

4. Yes, a checker can implement P4. There are no legitimate images it would flag incorrectly. For example, if superblocks have identical instances (e.g., 5 and 5) and all units/records have instance ≤ 5, P4 does not flag it. There are no collision images it would miss; for instance, if superblocks differ (e.g., 5 and 4) and a unit has instance 5, P4(2) correctly flags it. If data is unreadable, the checker reports not-applicable, which is appropriate.

5. G1: Pool-wide highest generation +1 ensures all devices use a generation higher than their current highest, avoiding overwriting newer slots. The exclusion reason is flawed because pool-wide highest is the maximum across devices, so writing highest +1 always increases the generation per device. B2: Writing device 0 superblock, barrier, then device 1 superblock, barrier, provides better crash safety. If crash occurs after first barrier, device 0's superblock is durable and usable, reducing recovery complexity. The cost is minimal compared to the safety gain. Older invariant rewrite: Checking only when codes differ reduces overhead in common cases where codes are equal. It still catches collisions when codes differ, and the exclusion reason is incorrect because it does handle the collision case when needed. Reading only chosen slot: This simplifies reading by focusing on the most recent valid slot. Rewrite-back writes occur before units, so the chosen slot reflects the correct state. The exclusion reason is incorrect because rewrite-back is handled before units, and the chosen slot would include it.

6. Yes, P changes the bytes of the first transaction. Today's implementation writes generation 2 at acquisition, but P2 requires writing device's highest verified generation +1, which starts at 1 (initially no superblocks). Thus, first acquisition writes generation 1 instead of 2. For crash states where exactly one device received the acquisition write (no units written yet), P4 would flag zero such states because there are no units, records, or roots to check. Code changes: Superblock writes must compute device's highest verified generation +1, and acquisition must read all verified slots. Rules must update generation handling and clarify that rewrite back occurs before units, with instance code handling per P4.
