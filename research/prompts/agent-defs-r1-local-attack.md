Background.

A software project uses a review process in which several independent instances of a general purpose coding assistant, called legs, each read a short instruction file, called a role definition, and then carry out one round of work according to it. A separate process, called the main agent, decides which role definitions to dispatch, gives each leg round specific parameters (a round name, file paths, and sometimes a list of files the leg must not read, called the no read list), and later reads what each leg produced. Every leg, no matter which role it plays, also inherits one shared instruction file whose rules apply to all seven roles described below. I will give you the relevant parts of that shared file first, then a summary of each of the seven role definitions, then six numbered questions. Treat every rule described below as authoritative and exactly as written. Do not assume any additional rule that is not stated here, and do not assume that a rule stated for one role also applies to a different role unless I say so explicitly.

Shared rules that apply to every one of the seven roles, translated from the project's shared instruction file.

Rule a. The round name, output file paths, draft directory, and this round's no read list are all supplied by the main agent in one dispatch message. If any required input is missing, the leg must stop and its only reply is to state exactly what is missing, instead of guessing or proceeding with partial input.

Rule b. A leg may only write to the paths given in the dispatch message and in its own role definition's declared write scope. Writing outside that scope through the assistant's built in Write or Edit tool is mechanically blocked by a project hook. Writing outside that scope through a Bash shell command is not blocked by anything mechanical at all. Enforcement for Bash based writes depends entirely on the leg following its own written instructions, with no automated backstop.

Rule c. New files must be created exclusively, so that creating a file that already exists fails loudly instead of silently overwriting it. After a file exists, further updates append to it.

Rule d. A leg must never read any file that this round's dispatch message explicitly names in its no read list.

Rule e. A leg first writes its own report into a file. Only after that report file has been written does the leg call a special one shot handback function to deliver its result to the main agent. That handback function can be called successfully only once per leg. If the same leg tries to call it a second time, that second call is rejected. If the main agent sends a leg a follow up message while that leg is still working, meaning strictly before that leg has made its one handback call, the leg treats the follow up message as additional input for the same round of work, and must record in its report at which step the message arrived and what it changed because of it. If that follow up message contradicts the leg's role definition or its original input, the leg stops at that exact point and hands back immediately instead of continuing.

Rule f. Every conclusion in a report must state what observation would disprove it.
