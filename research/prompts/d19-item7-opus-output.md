### 2.4 我核出来的那个真缺口：不是「没有落点」，是一个已命名字段的判别力

这一条是我这轮最想留下的。② 那一半虽然有字段，**但从字段走到「祖先链」要一步解析，而那一步今天是多值的**：

## 3 第 3 问：第四条路（把两个字段放进引用它的那条条目）

### 3.1 码 1 那条边：这条路**做得到，但它逐字节等于甲**

码 1 = extent 树的叶指向数据单元。叶条目的组成逐字：

**出处 `.claude/kb/experiments/105-extent叶改码3的代价.md:9`（整行抄）**

```markdown
| D8（核心索引结构） 已定项 2 / 3 | 节点 16 KiB；extent 记录 = key 24（locality 8 + inode 8 + offset 8）+ 位置指针 59 = 83 |
```
算术（我算的，纯加法，可复核）：

| | 条目宽 | 叶扇出（分母 16284，见第 4.1 节） |
|---|---|---|
| 今天（丙） | 24 + 59 = **83** | 16284 / 83 = **196** |
| **甲**（指针头部 31 → 47 ⇒ 指针 59 → 75） | 24 + 75 = **99** | 16284 / 99 = **164** |
| **第四条路**（条目里加 出生树 8 + 出生 txg 8） | 24 + 16 + 59 = **99** | 16284 / 99 = **164** |

⇒ **两个数逐格相同。** 机制很简单：**extent 叶条目里恰好只有一条指针**，
所以「装进指针头部」与「装进条目」写的是同一块 16 字节、在同一个节点、同一次 I/O 里。

⇒ **在码 1 上，第四条路不是第四条候选，它是甲换了个说法。**
第 3 问要求「给出这条路做不到的地方，或者给出它比甲差在哪一格」——
**在码 1 上正确的答案是第三种：它跟甲没有差别**，而候选集把它当成新的一条，会让人以为码 1 上还有便宜可占。

### 3.2 它唯一的真差别，落在 inode 树的码 2 那一格

差别只在**一条指针不是「一个条目对一个被指对象」**、或者**条目里已经有闲置字段**的地方。
仓里符合后者的**只有一处**：

**出处 `.claude/kb/decisions/08-核心索引结构.md:344-348`（整行抄）**

```markdown
**内部节点条目 = 分隔 key 8 + 身份引用 26 + 子指针 59 = 93 字节**（扇出 175）。

```
⇒ 类型段 = 0（子节点是码 2 索引节点）时：**出生树 8 已经装着正确的值**，
**容器号 8 与容器出生代 8 两段恒 0**。而「容器出生代」按 D16 已定项 6「代 = checkpoint 号」，

⇒ 第四条路在这一格：**把恒 0 的容器出生代改写成子节点的出生 txg，条目宽一个字节不动。**

| | inode 树内部条目 | 扇出 |
|---|---|---|
| 今天（丙） | **93** | 175 |
| 甲（E128 `arm=jia inode_entry=109`） | **109** | 掉一档 |
| **第四条路** | **93** | **175，不动** |

⚠️ **而这一格恰恰是甲不吃亏的那一格。** E128 产物逐字：

⇒ **甲吃亏的那一格第四条路帮不上，第四条路能帮的那一格甲不吃亏。**）

### 3.3 那一格要付的价钱：一条在册不变量 + 一句已定条款

那 16 字节不是空地，它有一条在册的不变量罩着：

**出处 `.claude/kb/invariants.md:254`（整行抄）**

```markdown
| I-9.2 | 条目身份与子头相符 | inode 树内部节点的每条条目：类型段 ∈ {0, 2}；类型段 0 ⇒ 子单元偏移 6 = 2 且容器号、出生代两段为 0；类型段 2 ⇒ 子单元偏移 6 = 3，子头的 (出生树, 打包记录类型, 容器号, 容器出生代) 与条目的身份引用四段逐字相等，且子容器的打包记录类型 == 2；其余判该条目损坏。跨头共享时出生树的读法随 C110（跨头共享与加密后元数据类的块头一致性读法） | 未实现，前置同上 |
```
⇒ 逐字「类型段 0 ⇒ 子单元偏移 6 = 2 且**容器号、出生代两段为 0**；……其余判该条目损坏」。
把出生代改写成一个真 txg，**I-9.2 当场由「合法」判成「该条目损坏」**。
⇒ 第四条路要改 I-9.2 与 D8 已定项 6 的正文（checker 状态列逐字「未实现，前置同上」，所以今天改的是文本不是代码）。

**更重的一笔，是它撞在项目自己的格式判据上。** `.claude/rules/fs-design.md` 的格式分支判据是
「一条格式分支值不值得，看它能不能把『用错了』变成『挂不上』」，
而那一节标 ✗ 的形态正是「参数化布局的失败模式是**静默误读**」。
把一段**恒 0、可被 checker 白判**的字节改成一段**取值任意的 txg**：

- 旧读者按 I-9.2 读到非 0 ⇒ 判该条目损坏 ⇒ 这一半是**拒绝**，还行；
- **新读者读一条旧条目**（出生代真的是 0）⇒ 读到 birth = 0 ⇒ 按 D5 的判定 `birth > p` 恒假 ⇒
  **每一个旧内部节点指着的子节点都会被判成「追加进 deadlist」而不是「立即释放」** ⇒ **静默、方向单一、不报错**。

⇒ **这一步要么配一个 incompat 位（那就等于承认它是一套新布局），要么就是那条判据点名的静默误读形态。**
甲不碰这一格：甲把条目从 93 撑到 109，两段恒 0 原封不动，I-9.2 一个字不用改。

### 3.4 树表条目那一格，第四条路也不免——理由是 D8 自己写的那一句

有人会想：树表条目里根指针的出生树 = 这条条目自己的树 ID（已在），
于是树表条目只要加 8 字节（121 → 129）而不是甲的 16（121 → 137）。**这一步过不去，被 D8 自己那句话堵死**：

> 出生树逐条目携带，是因为克隆头（D6（快照实现模型） 已定项 1）共享 origin 的叶，同一个内部节点里会混着出生树不同的条目。

⇒ **同一条理由对根成立**：克隆头刚建出来时它的根仍是 origin 的节点 ⇒ 出生树 ≠ 条目的树 ID。
⇒ 树表条目上第四条路照样要 16 字节，**跟甲同价**（E128 `tree_entry=137`）。
根记录那两条指针（`.claude/kb/decisions/22-单元原子性怎么合成.md:483` 与 `:486`，各 59 字节）不住在任何「一个条目对一个孩子」的结构里 ⇒
第四条路对它们**无话可说**，只能照甲办（194 → 226）。

### 3.5 跟甲的差别落在哪一格：**一处定义 vs N 处定义，而 N 今天数不出来**

这是我判的、第 3 问真正的分野，与字节数无关：

| | 甲 | 第四条路 |
|---|---|---|
| 字段定义在哪 | **一处**：指针头部的字段表。指针走到哪，字段跟到哪 | **每一种「指名一个单元」的结构各定义一次** |
| 今天数得清有几处吗 | 数得清：指针只有一个格式 | **数不清**——见下 |

数不清的三条现查依据：

1. **D19 未定项 6（中央映射条目的字段表）本身未定**，而 D19 已定项 5 硬规则 1 逐字「释放一律经映射，不经提示」
   ⇒ **释放路径读的是映射条目，不是指针**。映射条目要不要自带这两个字段，**今天没有答案**。
2. **反向索引与 LRU 的 key 布局全仓空白**：D8 已定项 7 正文逐字
   「**反向索引与 LRU 的 key 布局全仓一个字都没有**」。
3. **deadlist 的盘上落点全仓没有**（C145），而 deadlist 条目正是按 birth txg 分桶的那批条目。

⇒ 甲把「谁携带这两个字段」这个问题**一次答完**；第四条路把它**拆成 ≥ 4 个未定项**，
其中 3 个今天连正文都没有。按 `.claude/rules/fs-design.md` 的「不为省空间牺牲自包含」，
以及「格式上吝啬分支」（多一套布局 = 多一份要永远维护的解析器 + checker + 崩溃点重放），
**第四条路在格式债这一轴上比甲贵，而它换来的字节收益只在一格，且那一格实测为负。**

### 3.6 第 3 问结论

- **做得到**，码 1 上没有任何机制挡着——**因为在码 1 上它就是甲**（3.1 的算术）。
- 它作为**独立候选**只在一格上成立（inode 树码 2、类型段 0 的那 16 字节恒 0）；
- 那一格的收益 **E128 已实测为负**（`ratio_median=0.9686`，5 轮同向）；
- 代价是改一条在册不变量（I-9.2）、一句已定条款（D8 已定项 6），且新旧读者的失配方向是**静默的**；
- 与甲的结构性差别是「一处定义 / N 处定义」，而 **N 今天数不出来**（未定项 6 未定、反向索引 key 全仓空白、C145 无落点）。

⇒ **我判：候选集不必增加第四条。** 但**必须在正文里写下它为什么不是第四条**——
今天那句「三条候选」把「码 2 上有 16 字节恒 0 可用」这个事实整个盖住了，
而下一个人看到 D8 已定项 6 的字段表会重新问一遍。

### 4.1 E128 的 `tree_per_level=119` 与仓里的口径差 1
