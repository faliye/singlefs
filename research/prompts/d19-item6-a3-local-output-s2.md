For H-A the birth sequence in K is used solely as a key segment and never to determine the newest version so it is not intended for telling stale copies apart. T1 specifically addresses sequence numbers rejected for the purpose of distinguishing stale copies from current ones. Since the birth sequence serves a different purpose keying it falls outside the scope of T1. Therefore K does not need to go through T1 for this use. P and R do not add any sequence numbers so they also do not interact with T1. The set of settled texts requiring change for K is empty which matches P and R. Thus K dominates P and R in terms of settled text changes.

For H-B the issue arises only if the key includes a class tag read from the unit header. P and R keys do not contain a class tag so there is no class tag to mismatch for them. The problem does not apply to P or R. For K the class tag for slot objects can be explicitly set to 1 during key construction since slot objects are code 1 data units. No formal tightening is needed as this is handled in implementation. Thus the tightening is not required and the problem does not affect all alternatives equally.

For H-C the code 1 write order is already unique per data unit as stated in T4. This ensures unique keys even when multiple code 1 units are written in a single transaction including preallocated zero units. The phrase about writing at most one data unit's user data is irrelevant because key uniqueness is guaranteed by the write order field. The tightening is unnecessary. For P and R key uniqueness is inherent in the birth location or random identifier so the same issue does not apply to them.
