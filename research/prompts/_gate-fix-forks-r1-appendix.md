```markdown
#### 已定项 5：whiteout 删除 —— 接受，但批量删除必须走 intent log

**定案**：删大目录、截断大文件会产生海量墓碑，塞进一个事务必然爆掉。**做法（bcachefs 已验证的形态）**：凡是**可能修改无界数量 extent** 的操作（truncate、collapse、删大目录），**先把意图写进 logged_ops 树，再分批推进**；崩溃后恢复时续做未完成的意图。删除中的 inode 单独进 `deleted_inodes` 树，由后台回收——用户的 `rm` 返回，不等于所有 extent 都已释放。

**硬要求**：无界规模的操作一律不许做成单个事务；意图必须**幂等**；whiteout 只在节点重写合并 bset 时清除，**不许有别的清除路径**。

意图本身就是一条普通 key，骑在同一个事务层上，断电后只有三种状态：

| 断电时机 | 恢复后看到 | 怎么收场 |
|---|---|---|
| 意图提交之前 | 没有意图 | 操作从未发生，用户那边也没返回成功 |
| 意图已提交、工作做了一半 | 意图还在 | 恢复时**续做**，已做完的部分被幂等地重跑 |
| 工作做完、意图未删 | 意图还在 | 续做一遍发现无事可做，然后删掉意图 |

不可能出现「意图没了但目标状态没达成」——**删除意图必须与最后一批工作在同一个事务里提交**。

1. **意图声明目标状态，绝不声明增量。**「把文件 X 截到 N 字节」可以重复执行，「再删 1000 个 extent」不能。
2. **续做是每次恢复都跑的常规动作，不是修复手段**（否则会出现「平时不跑、真出事时才第一次跑」的代码路径）。
3. **中间状态必须每一个都是合法的文件系统状态**——「删了一半 extent 的文件」本身就得合法。
4. **一批里每个动作施加时先核它要删的东西还在**（随 D5（快照 / 空间记账机制） 已定项 12）——幂等的字面：一批按批开始时的状态为几个意图各算一份计划、施加时不复核，两个区间重叠的级联会把同一块放两次，统计量减两次、I-3.1（已分配统计对得上） 红。

**范围重建 vs 逐项修改：两条都要有，且要有显式判据**（`.claude/rules/fs-design.md`「不追求万能方案」）：

| 走法 | 代价 | 适用 |
|---|---|---|
| 逐项修改 | K × 随机访问 | 受影响的 key 稀疏散布 |
| 范围重建 | N × 顺序访问 | 受影响的 key 在 key 序上连续 |

**真正的开关不是 K/N，是「受影响的 key 连不连续」**：连续 ⇒ 范围重建可整节点丢弃或重写；不连续 ⇒ 只能逐项。**由此得到一条布局规则：让一起死的东西在 key 序上挨在一起。**

- dirent 按 `(parent_inode, name)` 编 key → 删整个目录是范围操作
- extent 按 `(inode, offset)` 编 key → 截断是范围操作
- 同一快照的 key 带同一 snapshot 前缀 → 删快照有机会变成范围操作

**这顺带从结构上解掉了 whiteout 膨胀**：范围删除直接丢弃整个节点，不用插 N 个墓碑。

**射程**：朴素的交叉点是 `K/N > 顺序代价/随机代价`（机械盘约 1%、SSD 约 10%）。⚠️ 这两个数是**推理，不是实测**，说的是**耗时**，要靠 E4（范围重建 vs 逐项修改的交叉点） 量，那一半要 QEMU。⚠️ **第一期只取 SSD 那一档**（D12（目标介质） 已定项 5：第一条布局线是纯 SSD）。⚠️ 写放大那一半量到的交叉点，自变量是「布局」与「节点大小」而不是介质，不能拿它去证伪「机械盘约 1%、SSD 约 10%」——那说的是耗时。按 `.claude/rules/fs-design.md` 的五条要求，这个分支还欠：判据写成可计算的式子、留一个能强制走指定分支的测试开关、两条分支各自跑崩溃点重放、运行时能看出走了哪条。⚠️ **切换判据里不许出现「当前填充率」这类操作中途会变的量**——判据只能用操作期间稳定的输入。**与 D3（空间分配） 的交互（容易漏）**：意图未完成期间那些空间还没真的释放，空间统计必须把「待删除但未完成」计进去，否则会出现「我删了一大堆，`df` 却不动」。
```

```markdown
退不回去的两类，处理方式不一样：

| 类型 | 例子 | 怎么办 |
|---|---|---|
| **丢掉未提交的改动** | `git checkout <文件>`、`git restore`、`git reset --hard`、`git clean` | 先 `git stash` 或 `cp` 一份出去；只在明确要丢掉这个文件的全部未提交改动时才用 |
```

````markdown
## `pkill -f` / `killall` 一律禁用

那个模式串会出现在 wrapper 自己的命令行里，结果**把自己的 shell 也杀了**。

要停进程就先 `ps` 列出来看清楚，再用**写死的 pid** 另起一条命令去杀；
也可以交给 `scripts/proc.py stop 进程号`：它先发 TERM，过 `--grace` 秒（默认 10）还在再发 KILL，要停的是发出命令的进程自己或它的祖先时拒绝。
统计类的改用 `/proc` 里的结构化信息，并且排掉自己这一支进程树。

**同一个模式串放进等待循环里是另一种形态：不会误杀，会永远空转。**
`until ! pgrep -f "X"; do sleep 5; done` 这种等法，模式串命中的是这条循环自己所在的 shell 命令行，
````

```markdown
`rc="$(run_one ...)"` 这种写法里，`run_one` 内部给变量的赋值**在父进程里是空的**。

又一次绿着灯出错。**要传值就落到文件或者走参数，别靠变量。**

在 `set -u` 下更糟：引用的地方拿到的不是空值，是当场报「unbound variable」，
**脚本还没来得及打印诊断就被带走了**。
`howto` 一句都没打出来，而装置说谎的时候最该看的就是那几句。
写条注释提醒拦不住这种事，它是 `scripts/shell-lint.sh` 里会红的一项。

```

```markdown
## 脚本改文件之后要回读确认，警告是免费的信号

用脚本做字符串替换来改代码或文档，**匹配不上是不会报错的，它就什么都不做**。
```

```markdown
## 进程边界上的三种静默失效

`set -e`、`pipefail` 和环境变量在**跨进程**的地方一起出问题，形态都是「退出码对，判据没跑」：

| 形态 | 实测 | 怎么写 |
|---|---|---|
| `set -e` 下写 `里层; rc=$?` | 里层一判红，外层在这一行就退出，后面的清理走不到——而判红正是最要看结果的时候 | 退出码在 `if` 里取：`if 里层; then rc=0; else rc=$?; fi` |
| `export X="$(cmd)"` / `local x="$(cmd)"` | `export` 与 `local` 是命令，它们自己的退出码把命令替换的盖掉了；`cmd` 失败也当成功 | 先赋值再 `export`，两行写 |
| 握手用的环境变量漏给子进程 | 外层设给里层的变量还在环境里，里层起的第三层拿它当自己的输入——实测：门禁自检嵌套跑时反红两例 | 读完就 `unset`；起子进程时 `env -u` 清掉 |

**所以判据是「这个值跨了几层进程」**：跨一层就要问它在下一层还在不在、该不该在。

```

```markdown
## 管道里的退出码不是你想要的那个

`cmd | head` 之后取 `$?`，拿到的是 `head` 的退出码，不是 `cmd` 的。
`cmd | grep x && do_something` 也一样，判的是 `grep` 成没成功。

结果就是**失败被吞掉**：`cmd` 其实已经挂了，脚本还往下走，
后面每一步都建立在一个根本不存在的结果上。

**做法**：想判前一段成没成，用 `${PIPESTATUS[0]}`，或者干脆别接管道——
先把输出落到变量或文件里，判完退出码再处理。

```

```markdown
## 只让多条臂互相比，测不出「所有臂一起错」

**臂跟臂比出来的相等，是个很弱的判据**：它只能排除「某一条臂单独错了」，
排除不了「所有臂共用同一个公式，而那个公式是错的」。
后者在互比里跟正确一模一样——**全都相等**。

⇒ **每写一条互比断言，旁边就要有一条把绝对值钉死的断言。**
「三条臂的开销相等」不够，还得有「开销正好等于 N」，而 N 要另外算出来。


**做法**：写完一条互比断言就问自己一句「要是三条臂**一起**错了，谁会发现」。
答不上来就补一条钉绝对值的。**这条和「阳性对照必须每条臂都跑」是一件事的两面**：
那条管「每条臂都要过闸」，这条管「闸本身不能是相对的」。
```
