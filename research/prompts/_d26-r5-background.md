## 二、问法（五问，每问只有一种读法）

1. **稻草人。** E127 的节点数分组臂是不是「存组身份」这条路最有利的实现。有没有一种**只靠节点头里的组身份才做得到、从 key 算不出来**的分组形态，在同一套模型里有理由比 key 区间分组好 20% 以上而 E127 没建——例如组满时把组切成两个连续的半组（组边界随历史走、不是 key 的函数）、组按访问热度重排。举得出就说清它为什么需要盘上字段。
2. **树结构本身给不给组。** 在真实的 B 树里，同父的兄弟节点就是一个天然的「节点组」，父节点分裂时组随之分成两个连续的组；放置器重写时读父节点就知道兄弟是谁。这种组要不要在节点头里存字段？若不要，「组身份必须进格式」这条路还剩什么形态。
3. **字节判定。** 若格式部分定为「不在节点头存组身份、不动索引节点内部布局」，D26（后台整理与放置回收） 未定项 4 那句「改第一个事务的字节：是」的依据（「第一个事务要写索引节点，这一项直接改节点布局」）还站不站得住；P1 的三问各自变成什么答案。
4. **E95 的结论要不要改写。** E95 判据 5 写的是「格式臂能不能把 runs 压到政策臂一半以下」，产物 runs8 三格 `format_halves_policy=true`；E127 表明那条「格式臂」不消费盘上字段，与 key 区间分组是同一条臂。E95 正文那句「格式臂减半」是不是该改写成「按 key 分组的放置政策减半」。
5. **政策部分。** 格式部分判掉之后，剩下的政策部分（聚簇段放置、可选重写半径 R、按 key 分组重落）是不是就是 D3（空间分配） 未定项 8 与 D26（后台整理与放置回收） 已定项 1 已经在管的东西——这一项还剩什么要单独定。

## 五、倾向与「结果反过来我接不接受」

**倾向甲的理由**：E127 是按 2026-09-10 写死的判据跑的，六格没有一格过阈值，三格反而更差；节点数分组越老越偏离 key 序，而 runs 奖励的正是按 key 序相邻放；同父兄弟这种组由树结构免费给出，不需要字段。

#### 已定项 3（2026-09-09，主 agent 定案，按三方论证）：`spec_hash` 恒对 kb 字段表的完整投影求，不切到 Rust 结构体

**先定问法。** 三种读法：只问切换时机（它预设了切换一定发生）、问哈希的输入工件锚在哪一侧、
问它钉住的是字节布局还是盘上语义。**取后两种合起来的那一问**，因为切换本身不成立。

**定案**：`spec_hash` 恒对 `format-spec/<组件>.toml` 求。那份 toml 是 **kb 字段表的完整投影**——
含**行序**（盘上顺序）与**非标量的盘上语义规则**（组件 ② 的合并规则以数据形式写进去），
不是已登记的那批标量常量的集合。有代码之后新增的**不是换哈希源**，是两道检查：
① spec 与代码之间的**相等性检查**（宽度与顺序都比）；② 黄金镜像回归（正文「两条会红的检查」第 2 条）。

**四条理由**：

1. **方向**。D13（验证路线）已定项 5 逐字：「**checker 与实现之间只共享一样东西：一份由 kb 的字段表生成的常量模块**，
   生成器从 kb 读、两边都只消费，任何人不许手改」⇒ 权威在 kb，Rust 结构体是**下游消费者**。
   对结构体求哈希，是把永久契约的指纹锚在派生物上。
2. **哈希是变更探测器，不是两份工件的相等性检查。** 对结构体求哈希抓不到「结构体与 kb 不一致」，
   它只在结构体**变化**时报警。真正抓那一类错的是相等性检查，而相等性检查要求 spec 侧存在
   ⇒ 切过去不但没多买到东西，还把要比对的另一侧拆掉了。
3. **语言绑定**。D17（实现分层与第三方管道）已定项 3 逐字：「判定必须能被第三方自己复核，
   否则『合规』就退化成『我们说你合规』」。指纹锚在 Rust 源码文本上，第三方管道复算不了它。

   ⇒ 切换会被逼到与第一次真实冻结同一个提交里完成，零试跑期。

   哈希机制可以远早于第一次冻结开始生效。

⚠️ **spec 只投影标量是不够的**（2026-09-09 反推腿按跑前写死的失败条款判这条臂出局，主 agent 现查坐实）：
