VOCABULARY

A txg is the transaction-group number of a publish; each publish writes one root record carrying that txg into a ring of root slots. A mount session is an instance, with an instance number. F is the rollback floor; F_eff is its effective value as defined in FACT 2. A slot is 16384 bytes (FACT 4). A segment is 64 slots (FACT 15). A record covering a placement has a starting slot, a span in slots, a released flag, and a release generation (the txg of the publish that replaced it). The checker is a separate program that reads a pool image from disk and judges invariants. The shadow ledger is an in-memory set of isolated slots kept by the allocator (FACT 6). The words "allocated", "walk", "defer", and "isolated" below always mean the exact quantities defined in the facts.

FACTS ABOUT THE RULES

FACT 1. Invariant I-3.1, named "allocated statistic matches". Its definition: the allocated-space statistic equals the sum obtained by actually walking all references. The checker's reading: "actually walking all references" is taken as the union of the references of all valid roots in the root ring. Since 2026-09-17, a valid root means a root in the rollback candidate set: valid according to the instance table pointed to by the newest root (that table has no row for the root's instance, or it has a row (i, Ti, Wi) and the root's txg T is at most Ti), and with txg at least F_eff. The stated reason: units referenced by roots of an abandoned timeline are isolated by the shadow ledger, and released units referenced by roots below F are already reallocatable, so neither is in the current account. When the F carried by the newest root is lower than F_eff (the two differ), this check is not judged and reports "not applicable". Quarantined records: an allocated record that no root references is exempted per unit; if any copy of the unit it covers is found by the checker itself to be unreadable or to fail its checksum, that unit's records on every device are exempted; if every copy reads and matches, it is still judged a violation. Source: invariants file, row I-3.1, line 134.

FACT 2. How the checker computes F_eff: F_eff is the maximum of (a) the largest F carried by the newest durable valid root on each surviving device and (b) the F carried by the pool's self-verified system configuration slots whose fsid matches this pool. Valid here means not abandoned according to the newest root's instance table; on each device the newest one is the root with the largest (txg, instance) among the root-ring regions on that device. The F carried by roots on an abandoned timeline is not counted (a code comment says whether it should be counted is still open in decision D16, and the code takes the literal reading "valid root" and does not count it); when the newest root's instance table cannot be read, it has no rows and nothing is filtered. A root is abandoned according to that table when the table has a row for the root's instance and the root's txg is greater than that row's published txg. Source: checker walk source file, lines 5840 and 5843 through 5874; invariants file line 134 for the fsid wording.

FACT 3. Which roots the checker walks: a root is below the floor when its txg is less than F_eff. A root is walked when it is the newest root, or when it is both not abandoned and not below the floor. Source: checker walk source file, lines 5884 and 5885.

FACT 4. The ledger rows written per device: the allocated row equals the allocated slot count times the slot size; the defer row equals the deferred slot count times the slot size. A code comment on the defer row says: item 5, released ones still inside the defer window; they are still counted in allocated, because they occupy space and are referenced by valid roots in the root ring. The slot size is 16384 bytes. Source: core transaction source file, lines 6292, 6298 and 6299; format crate source file, line 14.

FACT 5. The reclaim rule. The settled rule: a placement is reallocatable exactly when it is released and its release generation is at most the maximum of F_eff and the oldest valid root in the ring. In code, reclaim picks the records that are released and whose generation is at most the floor it is given. Reclaiming a placement clears its allocated bit, subtracts its span from the allocated slot count and from the deferred slot count, adds its span to the free slot count, decrements the used count of its segment, and updates the free-run count; it clears only the allocated bit, not the isolation bit and not the hold bit. The floor handed to reclaim when F is raised is the reclaim floor: the maximum of the new F and the oldest valid root, or the new F alone when there is no valid root. The oldest valid root is the smallest txg among the ring roots that are not abandoned according to the instance table. When F is raised, reclaimed slots are put on hold until the new F takes effect, and the holds are released after the roots carrying the new F have landed on every device. At mount time, reclaim instead makes slots reusable immediately, with no hold. Source: decision D16 file line 33; core allocator source file lines 1567, 657 through 676, 1583 through 1586, 1593 and 1594; core mount source file lines 1147 through 1152, 2346 through 2350, 2367 through 2370, 1433 through 1436.

FACT 6. The shadow ledger. A note under decision D23 settled item 14: the shadow ledger and judging abandonment by the instance table are kept for the reason of crash recovery, not administrator rollback; in a history without any administrator rollback, crash recovery can land on an old root because of a temporary read error, and the instance table then abandons the newer roots; if the shadow ledger were turned off, data units referenced by the abandoned roots would be reused, and a later recovery that lands on such a root would fail to read. After tracked issue C554 option yi-config-continued (decided by the user on 2026-09-27), a newer root witnessed by the system configuration that is temporarily unreadable is no longer abandoned: a writable mount rereads once and refuses to mount writable if it is still unreadable; the reason for keeping the shadow ledger is narrowed to the form that the system configuration did not witness (that publish's system configuration rotation did not land). The code rule: slots referenced only by abandoned roots equal the slots referenced by abandoned roots, minus the slots referenced by roots in the candidate set, minus the slots still allocated (not released) in the current version's account; a candidate is a root that is readable, valid according to the instance table, and has txg at least F. The same comment adds that the user's narrow wording of 2026-09-16 was "slots still referenced by valid roots are not included", with valid judged only by the instance table, and that exempting only roots in the candidate set (the extra condition txg at least F, recomputed with the new F after a raise) is a tightening of that wording; the comment calls this provisional, a deviation from the user's wording, to be put to the user. What a root references means the placements still allocated in that root's own version's account; entries already released in its account belong to the previous version it replaced and are not counted as referenced by it. The isolation bit is independent of the allocated bit, so after the candidate set shrinks (by raising F) a recomputation only isolates more slots and never undoes any; isolation is cleared only in the publish in which the abandoned root leaves the root ring. When F is raised, the candidate set shrinks with the new F, and the slots referenced only by abandoned roots can increase (a slot previously exempted by a root below the new F); before reclaiming, the shadow ledger is recomputed with the new F. The per-device isolated slot count lives only in memory. The isolate function sets the isolation bit on each slot of the span that does not already have it and increments that segment's isolated count and the device's isolated slot count; its body does not change the allocated bit, the segment's used count, or the allocated slot count. Source: decision D23 file line 402; core mount source file lines 1209 through 1217, 1233, 1238, 1258, 2351 and 2352, 824; core allocator source file lines 576 through 591.

FACTS ABOUT THE TWO SEGMENT COUNTS (tracked issue C379)

FACT 14. Tracked issue C379, "the ledger's empty cluster segment count and the segments the allocator can open are two calibers". Its text: the ledger row "empty cluster segment count" is computed by the allocator's empty-segment counting function, which looks only at allocated bits, while the lowest-empty-segment function also requires the shadow ledger's isolation bits and the raise-F hold bits to be zero; after a whole segment is isolated, the ledger row does not change (a probe measured 3310 unchanged) while the lowest segment the allocator can open jumps from 50304 to 50368; the two calibers give different numbers for the same quantity. Those three numbers came from an earlier attack leg's copy of the code, on a different pool image from FACT 17. Source: tracked-issues file line 315; investigator report line 178.

FACT 15. The segment code. Each device's unit area is divided into segments; the number of segments is the unit-area slot count divided by 64, rounded up, so the last segment may have fewer than 64 slots. The empty-segment counting function counts every segment in that array, including a last partial one, whose used count is zero. The lowest-empty-segment function looks only at full segments (the unit-area slot count divided by 64, rounded down), finds the first one whose used count, isolated count and hold count are all zero, and returns its starting slot, which is the unit-area start slot plus the segment index times 64. The ledger row "empty cluster segment count" is written from the empty-segment counting function. A segment is 64 slots. Source: core allocator source file lines 372, 373, 386, 683 through 692, 756 through 769 (758 for the full-segment count); core transaction source file line 6301; format crate source file line 271.

FACT 16. How the isolation image was built. The same pool as the reproduction was run up to the writable remount of FACT 7 (at that point the shadow ledger had naturally isolated C's units); then, through the public entry that hands a placement to the shadow ledger, the lowest openable whole empty segment (64 slots) on each device was handed to shadow-ledger isolation; this step is injected, not natural. Then one overwrite was made so that the ledger row lands on disk, and the checker (the same investigator copy) read the ledger's empty cluster segment count from the image. F was not raised in this history. A control run did the same without the injection. Source: investigator report line 161.
