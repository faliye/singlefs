## 一、判决 3 复核：甲的四次打中是不是最弱读法，S6–S8 合不合法

### 1.1 四次打中各自是不是甲的最弱读法

甲（这一轮记作甲-S 之前的形态）在 D18（块里携带什么信息） 的候选原文（`decisions/18-块里携带什么信息.md:691-697`）只说「往这一组里加第六个字段 `locality_id`」「重建时码 1 单元从单元头读 key 首段」，**没有一句话规定重建时的版本分组规则、记录与幸存 key 冲突时谁优先、先抄后切迁移期间写路径怎么处理**。这三处空白，恰好是打中 A、C/B、B′ 分别命中的地方。逐条核实候选原文是否已经排除了被打中的那个读法：

- **打中 A（字面分组）**：`invariants.md:28`（I-1.8） 逐字「码 1 / 3 的可读已发布单元按『类身份段全部字段含写序』归并成组之后，同 key 的各组两两全序键不等」。甲把 `locality_id` 塞进类身份段（候选原文与 `decisions/09-加密.md:524` 的六元组改写一致），若不改这一句，「类身份段全部字段」按字面就含 locality——**这不是攻方腿选了一个刁钻读法，是 I-1.8 今天的字面文本，一字不改地应用到甲的字段表上，必然得到的结果**。候选原文没有一句碰过 I-1.8，所以这是候选原文的空白被 I-1.8 的既有文本自动填上了一个错误答案，是最弱读法，而且是**唯一**读法（因为没有第二句话可选）。
- **打中 C（记录优先，幸存 key 编不回记录值）**：这一击的机制是 AAD——甲把 locality 放进 AAD 规范编码之后，`decisions/09-加密.md:552`（「AAD 每个字段的期望值只许来自……」那条硬约束附近）与已定项 6 的「不许来自明文侧」机制，逼得幸存单元的 locality 只能是它自己头里解密出来的那个值，不能凭空编成别的值——这是甲把 locality 塞进 AAD 这个选择本身带出的**结构性**后果，不是某种「记录优先」策略选得刁钻。候选原文完全没有讨论「记录与幸存 key 冲突时怎么办」，甲的默认行为（记录优先，因为它是唯一现成能给出首段值的地方）撞上 AAD 硬约束，是最弱、也是当时唯一说得出的读法。
- **打中 B / B′（先抄后切）**：候选原文完全没提过迁移协议，`协议 C` 本身是这一轮为了测「后台重新聚簇」这个共同前提才建的（`decisions/08-核心索引结构.md:196` 只说「后台重新聚簇必须是增量、可中断、可续做的」，没有给出具体写法）。B′ 命中的前提是「迁移期间的写在两个 key 上各写一份」，这是「随便写」这个默认行为的自然产物，不是刻意构造的极端写法——候选原文没有任何一句禁止这种写法，所以它同样是最弱读法。

⇒ **四次打中都成立为「最弱读法」**：候选原文在这四处全部留白，而攻方腿用的是**已经在 kb 里、不需要新增任何条款就能得出**的既有文本（I-1.8 字面、AAD 硬约束、以及「无约束时写两份是合法行为」这个默认），不是曲解或选择性构造。判决 3 在这一点上站得住。

### 1.2 S6 / S7 / S8 按「记一次输 / 只许收严 / 写明收严在哪」三步核

`.claude/singlefs-ai-sop/rules/evidence-discipline.md` 那条三步规则原文（本轮现查，`evidence-discipline.md` 未编号，此处只引其规则内容，不重复摘抄整篇）：**记一次输**（按最弱读法记打中）、**只许收严**（新形态被原判据判得更严或相同，放宽一个字都不行）、**写明收严在哪**（说得出新形态比旧形态多要求了什么）。逐条核：

| 收严 | 记一次输 | 只许收严（有没有放宽别处） | 写明收严在哪 |
|---|---|---|---|
| S6：码 1 版本分组只看 (对象, 锚点偏移)，不看头里的 locality | 打中 A 按最弱读法记（1.1 已核） | **没有放宽**：分组仍然要求写序全序、仍然按写序择新，只是从「比较键」里去掉 locality 这一维；对不含 locality 的乙′、丙′、以及甲自己的其余判定（AAD、fsid、树 ID）一个字都没动 | 多要求「locality 不参与版本分组比较」这一条显式排除规则，I-1.8 原文对码 1 没有这条排除，S6 是在原文上新增一条限定语句，纯粹缩小归组的模糊空间 |
| S7：甲重建出的记录取重建出的首段集合（视图里的多值，不落盘），读者逐个试 | 打中 C、B 按最弱读法记 | **没有放宽**：它没有取消「幸存单元的 locality 必须与自己头里的值一致」这条 AAD 约束（甲的核心卖点未被削弱），只是在**读时**多给一层候选尝试，且明写「不落盘」——不触碰 D18（块里携带什么信息） 已定项 5 纪律 3（`decisions/18-块里携带什么信息.md:521`）「该状态下任何权威态结构不得由重建结果就地修复」，因为它没有写回任何东西 | 多要求「读路径在记录值失配时必须依次尝试重建出的候选集合，而不是只信任记录里那一个值」；原候选文本对此毫无规定（默认只信一个值），S7 是纯粹的增补 |

**三条都合法**。而且它们有一个共同特征值得记下来：S6/S7/S8 全部是**加约束**（对码 1 分组多一条排除、对读路径多一层尝试、对写路径少一种交错），没有一条是「换一种解释让原来的失败消失」——这正是「收严」与「诡辩」的分界线所在。

### 1.3 「甲在打包对象上结构性失效」：候选原文的问题还是读法的问题；甲-S 的补丁是不是收严

**这是候选原文的问题，不是读法问题。** D18（块里携带什么信息） 那条待定案的 ⚠️ 原文写于 2026-09-03（`decisions/18-块里携带什么信息.md:691-697`），而 D27（小数据打包容器） 直到 2026-09-07 才立项、2026-09-10 才定案「整容器一份 MAC，AAD 绑容器身份」（`decisions/27-小数据打包容器.md:230` 起「已定项 10」与已定项 7/9 那一节）。甲的候选原文写的时候，打包容器这个结构在 kb 里根本不存在，**候选原文不是选择性地没讨论打包对象，是物理上不可能讨论一个当时还没立项的结构**。第二轮辩方腿（本报告上一轮，`d18-locality-r2-sonnet-output.md`）与攻方腿都独立指出「候选原文没交代」，两条腿在这一点上没有分歧，这不是读法之争。

而且这一击**不是纯 U2 契约层面的空白，第二轮攻方腿的模型给出了真实的 U1 正确性数字**：`row pack jia_slot8_claim5 jia_key_rec 8 202 1320 1316 608 186 87 0 0 422 0 732`——608 个失败形态、186 次找不到（missing）、422 次 AAD 失配。这确认了「候选原文没写打包对象」这句话不只是文本缺口，一旦机械套用甲的规则到打包对象上，**真的会产生数据找不到的后果**，够得上 U1 的「一段正确性后果」标准，不是只在 U2 契约层面记一笔就够了的问题。

**甲-S 给出的补丁（`_d18-locality-r3-background.md` 候选原文，本轮）**：「打包对象：槽不带 locality（槽 +0），≤ 4 KiB 的对象重建时按丙′ 的规则把全部 key 编同一个值」。用三步规则核：

- **记一次输**：按最弱读法记（上一段已核，且有数字支持，比 1.1 里其余三击更硬）。
- **只许收严**：这里要小心——它不是「甲的定义域内多加一条排除规则」那种收严，而是**在 ≤4 KiB 对象这个子集上整个换成丙′ 的机制**。对未打包的码 1 单元，甲-S 的规则（S6+S7+S8 之后的甲）一个字没变，没有放宽；但对打包对象，它不再是「甲的一个特例」，而是**完全退化成丙′**——AAD 不再罩这个字段、重建规则不再是甲的规则。这在字面上满足「新形态被原判据判得更严或相同」（因为丙′ 本来就在同样的场景下 0 失败，`row pack plain bing_s1 8 202 1320 1316 0 0 0 0 0 0 0 598`），但它已经不是「收窄甲的候选空间」，而是**换了一套机制**。
- **写明收严在哪**：能写清楚——「≤4KiB 对象不再走 AAD 认证的 locality，改走丙′ 的读时重建规则」。这句话本身没有歧义。

⇒ **判定**：甲-S 的打包对象补丁在字面上通过三步检验（不放宽任何东西、能明确说出多要求了什么），但它带来一个三步规则本身没有覆盖的代价，需要单独记进 U2/U3/U4：**甲-S 已经不是一个单一机制，而是「非打包对象走甲的 AAD 路线 + 打包对象走丙′ 的读时重建路线」的复合体**。这与 `.claude/rules/fs-design.md`「行为上放开分支，格式上吝啬分支」一节的判据直接相关——甲-S 现在有两条内部分支，而分支纪律要求「每条分支必须能被测试强制进入」「每条分支单独验，包括崩溃点重放」。丙′ 和乙′ 都不需要为打包对象单独验一条分支（因为它们的规则对打包对象和非打包对象是同一套），甲-S 需要。这个代价目前哪个 kb 分项都没记，见本报告第四节的欠账登记。

## 二、判决 1 复核：S1 改判为「局部性偏好」，D21 依据站不站得住

### 2.1 先去 D21 原文核「权威态」的定义

`decisions/21-权威态与派生态的分界.md:7`（表格行）逐字：「**权威态** | **单元 + 记账 + 根** | 丢了就丢数据。参与格式冻结，是永久契约」「**派生态** | **索引（树）** | 丢了只是慢。不参与格式冻结」。这是最粗的二分表，第二轮判决 1 引的正是这张表——「记录住码 3 单元、是权威态，extent key 是派生态」。

但 D21（权威态与派生态的分界） 自己在这张表之后立刻收窄了判据，`:15` 逐字：「**态别按重算性判，不按『树』这个词判**（2026-09-05，随 D8（核心索引结构） 已定项 6 补）：判据是——这份内容能不能只从权威态重算出来」；`:24` 更进一步：「⚠️ **『能不能重算』问的是语义，不是字节**（2026-09-09 用户定案 + 三方论证）。判据的准确形式是——**重建不出这个值时，读者拿到的是保守答案还是错答案**：保守答案 ⇒ 仍是派生态；错答案 ⇒ 必须逐出该结构，或者进权威态」。

⇒ **判决 1 的理由只用了第一张粗表，没有用 D21（权威态与派生态的分界） 自己后续收窄的判据**。这不是我在挑字眼——D21 正文明确说「按字节判是被这条定案否掉的」（`:24` 之后紧接的那一段：「⚠️ 被这条定案否掉的是『按字节判』：按字节会把码 2 的身份段判成权威态（纯误报）」），也就是说 D21 本身已经预见到「一个值躺在权威态单元里就等于它享受权威态保护」这种推理方式是错的，专门写了一条来否它。

### 2.2 用 D21 收窄之后的判据重新判 locality_id

用「重算性 + 保守答案 vs 错答案」这条判据重新过一遍记录里的 `locality_id` 字段：

- **它能不能只从权威态重算？** 不能——它本身就是提示信息，没有一个「正确值」的权威来源可以重算（D8（核心索引结构） 已定项 3，`decisions/08-核心索引结构.md:196` 逐字：「它是**提示，不是正确性的一部分**——可以是错的、可以过期」）。
- **重算不出（或重算出多个候选）时，读者拿到的是保守答案还是错答案？** 这才是真正的判据，而答案取决于**读者拿它做什么**：作为文件系统扫描/放置提示，任何一个候选值都是**保守**的——用错了只是这次读多探一次目录、或者以后写入放得不够近，`.claude/kb/decisions/08-核心索引结构.md:196` 那句话本身已经把这条路堵死了对面（「它可以是错的」意味着任何取值都不构成语义错误）。这正是丙′、乙′、甲-S 三条臂在 U1 的对象次数检查里全部 0 失败（`bing_s1`/`bing_rec`/`yi_s3` 逐世界 0，第二轮已核）的根本原因——**因为 locality_id 从定义上就不是那种「取错了会有错答案」的字段**。

⇒ **D21（权威态与派生态的分界） 收窄后的判据不支持「记录里的 locality_id 享有权威态那种『不得被覆盖』的保护」**。判决 1 引的「权威态盖过派生态」这条理由，套的是 D21（权威态与派生态的分界） 已经明令否掉的「按字节/按容器类型判」，不是它现在的判据。

### 2.3 与 D18（块里携带什么信息） 已定项 5「不得由重建结果就地修复」的关系

第二轮判决 1 还隐含另一条理由：S1（幸存 key 优先）让「派生态的值盖过权威态的值」，这句话背后其实是在担心 S1 违反 `decisions/18-块里携带什么信息.md:521`「一条纪律：该状态下**任何权威态结构不得由重建结果就地修复**」（D18（块里携带什么信息） 已定项 5 纪律 3）。要判这条担心成不成立，得先核这条纪律管的是什么操作。

`:521` 那一行的出处注解写得很清楚：「它是 I-6.10（已停用·明文映射层不存在了） 逐字『差异一律判红，**不许就地修复**』扩到重建产物上，不是新机制」。I-6.10 原文（`decisions/09-加密.md`「连带要新增 / 改写的不变量与检查」一节，本轮已读过其内容，见附录段落）讲的是**checker** 拿重建出的结构与盘上明文副本逐条比对，差异要**判红报告**，不许**checker 自己动手把盘上那份改成重建出的那份**——这管的是「谁能改写权威态结构的磁盘内容」，是一条**写路径/修复路径**上的禁令。

而 S1（连同它改判之后的另一个选项「记录优先」）管的是**级 1 只读挂载状态下，一次内存里的读路径查找该先试哪个候选值**——两个选项都遵守 S7 那条「重建视图里的多值，不落盘」（`_d18-locality-r3-background.md` 候选原文与第二轮修法一致），也就是说**无论取 S1 还是记录优先，这个过程都不往盘上写任何字节**，纯粹是「读者按哪个次序去试」。

⇒ **S1 与已定项 5 纪律 3 之间不存在字面冲突**：纪律 3 禁止的是「用重建结果覆写权威态的磁盘内容」，S1/记录优先争论的是「只读挂载下内存里的查找顺序」，两者不是同一个操作。第二轮判决 1 把「S1 让重建视图里的值与盘上记录的值不一致」等同于「S1 违反了不得就地修复的纪律」，这一步推导没有站住——**视图与盘上记录不一致，本身就是级 1 只读挂载这整套机制存在的前提**（否则不需要有「只读」这个降级状态），不构成对纪律 3 的违反。

### 2.4 结论：判决 1 的理由需要改写，但不改变最终选项

上面两条核实合起来说明：第二轮判决 1 给出的**理由**（D21（权威态与派生态的分界） 的权威/派生二分、以及与已定项 5 纪律 3 的张力）在逐字核对之后**都不成立**——判决用的是 D21（权威态与派生态的分界） 已经明令否掉的粗判据，而已定项 5 纪律 3 管的是另一个操作层。

但这**不代表 S1 应该被推荐**，也不代表判决 1 的最终动作（「S1 从必要条件改判为局部性偏好，交用户时列成选项」）需要撤销——攻方腿的模型已经证明 S1 与「记录优先」在 U1 上完全等价（0 失败，仅局部性变化数字不同：`atomic` 世界 412 对 860），这个数字本身与 D21（权威态与派生态的分界） 的判据无关，站得住。真正需要改的只是**理由句**：不能再写「记录是权威态、extent key 是派生态，S1 让派生态盖过权威态」，而应该写成——**locality_id 无论存在记录里还是编在 extent key 里，都是同一等级的『提示』（D8（核心索引结构） 已定项 3 逐字），D21（权威态与派生态的分界） 的权威/派生二分不适用于这个字段；S1 与记录优先在正确性上等价（S9 之后），差别只在于哪一个更可能反映『更晚』的真实 locality——这是一个纯粹的启发式选择，不受任何已定条款约束，可以按简单原则（比如取写序更新的那个来源）定，不需要援引 D21（权威态与派生态的分界）**。

⇒ **推荐维持第二轮的动作（改判为局部性偏好、交用户选），但把理由从「D21（权威态与派生态的分界） 的权威/派生位阶」换成「locality_id 是 D8（核心索引结构） 已定项 3 定义的提示字段，两个候选值都不构成错答案，选哪个纯粹是局部性质量的经验取舍」**。这条改动要落进 kb 正文，见第四节。

## 三、共同前提复核：「找不找得到取决于分批协议，不取决于臂」站不站得住

### 3.1 先核第二轮的证据范围

第二轮攻方腿的模型（`d18-locality-r2-opus-model/model.py`）用四种协议测了「后台重新聚簇」的中间态：协议 A（一次发布做完）、协议 P（记录带双值，每次发布搬一部分）、协议 C（先抄后切，记录单值）、协议 N（记录直接换值，阳性对照）。从第二轮报告「全部结果行」（`d18-locality-r2-opus-output.md` 第 100-216 行）抄出的数据看，`plain` 家族（丙′/乙′）在 `atomic`（协议 A）、`perunit`（协议 P）、`copy`/`copy_recopy`（协议 C 两种写法）四个世界的 `bing_s1`/`bing_rec`/`yi_s3` 那几行，`missing` 列全部是 0；只有 `naive`（协议 N）那一行的 `normal_shortest` 记录显示常规读失败（`missing=1`）。协议 N 在模型口径里被明确标注为「阳性对照」（`d18-locality-r2-opus-output.md:40` 附近：「协议 N（记录直接换成 L_new、不带旧值）是阳性对照，常规读就该红」），不是候选协议之一。

⇒ 从这份数据看，判决站得住：**在三个真实候选协议（A/P/C）下，三条臂（丙′/乙′）的 plain 家族对象次数从 2512 到 1183264，missing 全部是 0；只有被明确排除在候选之外的协议 N 才会找不到**。这确认了「读不到取决于协议选择，不取决于臂」这句话——但它的准确范围是「协议 A/P/C 之间不分辨臂，协议 N 与它们分辨」，而不是「任何一种分批协议下三条臂都一样」，这个区分值得在写回时讲清楚，免得读者以为协议怎么设计都无所谓。

（续下一段）
### 3.2 一个第二轮模型没建的面：后台任务在崩溃 + 回退之后按外部进度恢复

第二轮模型的十个世界都是「线性历史」——每一步操作按顺序发生，中间没有崩溃/回退打断后台任务本身的进度记录。但 D16（发布语义） 已定项 1（`decisions/16-发布语义.md:107` 起）定的 defer 窗口允许「保留最近 4 个可退到的不同状态」，也就是说一次崩溃或一次管理员确认的回退，可以把已发布状态倒回到迁移过程中的**某个更早的发布点**，而不是最新那个。

D8（核心索引结构） 已定项 3 对后台重新聚簇的要求是「增量、可中断、可续做」（`decisions/08-核心索引结构.md:196` 附近，前提十二整句），但**没有一句话规定「续做」的进度判据必须来自盘上当前可见的状态，而不是后台任务自己维护的一份外部进度记录**。如果后台重新聚簇任务把「已经搬到第几个 key」这类进度信息存在一个不随发布回退的地方（比如一个不经过根环/记账树的内存态或独立文件），就会出现这样一条历史：

1. 任务按协议 C 迁移一个对象，已经完成「复制新 key（1..5）」「翻转记录指向新首段」，正准备执行「删除旧 key（1..5）」；
2. 在删除旧 key 之前崩溃，此时已发布的最新状态其实停在「复制完成、记录已翻转」那一步（假设这一步已经落盘发布）；
3. 但因为某个更早的检查点更符合暖机/两盘落地确认的条件（D16（发布语义） 已定项 8，`decisions/16-发布语义.md` 暖机机制），恢复选择的是**再往前一个检查点**——此时记录还没翻转，指向的仍是旧首段的 key；
4. 后台任务进程重启后，如果它按自己**外部保存的进度**认为「复制与翻转都做完了，下一步是删除旧 key」，就会执行删除——而此时盘上（回退之后）记录仍然指着旧首段，旧 key 一旦被删，**读者按记录查找会真的找不到**。

这与第二轮建的四种协议历史都不同：那四种协议里每一步都是「做完就立刻检查」，没有「任务自己认为的进度」与「盘上真实进度」脱节这一层。这个脱节的根源不是 locality_id 本身，而是**任何**增量的、可中断续做的后台写任务，如果进度判据来自外部而不是盘上状态，都会撞上同一个问题——这与 D26（后台整理与放置回收） 已定项 1/2 把「意图的目标态改成一个单调可判的谓词」（后台整理任务只信盘上可判定的谓词，不信自己记的进度）是同一类修法。

⇒ **判定**：这不是甲-S/乙′/丙′ 三条臂之间的分辨点——三条臂都要用到「后台重新聚簇」这个共同机制（甲-S、乙′ 的 locality 提示都会过期需要修，丙′干脆没有格式位但读时重建同样依赖重新聚簇把 key 编准），所以这条风险按「三条臂共同、不拿来判臂」的规则记账，不改变第二轮对丙′/乙′「没被打中」的判定，但它确实是一条第二轮模型没测到的**新洞**，应该单独记进欠账表（见第四节），并且要求「后台重新聚簇」的定案条款（前提十二那句）明确加一句：**续做的进度判据必须完全来自盘上可读状态（记录当前值 + 已存在的 key 集合），不许依赖外部/内存态进度记录**。这条不是「打中」，因为它没有具体到某个正确性反例被模型或手造历史钉死；标注为「手造推理，未穷举验证」，供第三方核实。

## 四、这一轮的正面推导：三条臂在四个新面上

### 4.1 删除 / 截断之后留在盘上的旧版（墓碑）

**场景**：对象在偏移 0 写过一次（locality=L1），随后整个文件被删除——D18（块里携带什么信息） 已定项 8（`decisions/18-块里携带什么信息.md:430` 附近）要求删除写一个墓碑单元（码 3，打包记录类型 1），原数据单元本身**不会立即擦除**，只是被判定为死亡，物理上仍留在盘上直到 K 代点删回收窗口过去。

**三条臂的重建行为**：删除之后，inode 记录本身已经不存在于 inode 树里（`deleted_inodes` 机制，`decisions/08-核心索引结构.md:379` 附近），extent 树里这个对象的 key 也应当被删除操作一并清空（D8（核心索引结构） 已定项 5 的 whiteout 删除机制）。这意味着**扫描重建的输入端本身就不会把这个对象当作「记录丢了但 extent 还在」的情形去处理**——重建版本选择靠 I-1.8（`invariants.md:28`）与 I-1.9（`invariants.md:29`）「清扫水位内无可读垃圾；其外的可读垃圾每个 key 都被更大写序的可见版本或可见墓碑压住」：**死掉的数据单元的写序天然小于压它的墓碑记录的写序**，版本归并规则（不论甲-S 的 S6 怎么改分组键，都没有改变「按写序择新」这条主规则）会正确地把这个数据单元排除在「现行版本」之外。这一层判定**完全不看 locality_id**，S6 只是把 locality 从分组比较键里去掉，没有动写序择新这条主规则。

⇒ **三条臂对这个面完全等价，都不受影响**：这不是一个能分辨甲-S / 乙′ / 丙′ 的面，是共同的既有机制（I-1.8 + I-1.9 + 墓碑压制规则）已经处理好的问题，**locality_id 放不放进 AAD、放不放进单元头、要不要现编都不改变这条链路**。唯一的边界情况是「墓碑单元自己也丢了」——这属于 D18（块里携带什么信息） 已定项 10 射程注里明写的「已定项 8 定的是『盘上留一个墓碑单元』，没有定它什么时候可以被回收」这类更基础的风险（`decisions/18-块里携带什么信息.md` 已定项 8 那一节），同样与 locality_id 无关，落在已有的 C84（墓碑单元的粒度没人定） 欠账下，不新开一笔。

**会红的检查**：手造历史——建对象、写 offset 0（locality=1）、删除（写墓碑）、损坏「extent 全丢，记录也丢」，三条臂重建都应当**不把这个已删除对象的数据单元当作任何现行对象的一部分补回去**（对照 I-9.5「删除队列里的号仍在树里」与 I-9.8「记录 inode 等于 key」两条不变量，`invariants.md` I-9 一类）。这条断言可以直接扩进已有的重建/checker 单测（`crates/singlefs-checker` 的坏镜像测试集），不需要新建装置。

（续下一段）
### 4.2 被抛弃时间线的孤儿

**场景**：实例 A 创建 inode 5（locality=10，offset 0，写出单元 U1），随后发生管理员回退或实例切换，实例代号推进到 B；U1 属于被抛弃的时间线，但物理上仍然留在盘上。inode 号水位在回退后会退回去重发（C143（inode 号水位在回退后会退回去重发），`decisions/08-核心索引结构.md:379`），所以新实例 B 完全可能**重新分配 inode 号 5** 给一个逻辑上完全不同的新文件，写出 offset 0（locality=20，单元 U2）。此时盘上同时存在 U1（inode=5, offset=0, locality=10, 实例 A）与 U2（inode=5, offset=0, locality=20, 实例 B）。

**关键问题**：甲-S 的 S6 规定码 1 版本分组只看 (对象, 锚点偏移)，不看头里的 locality——这意味着 U1 与 U2 会被分到**同一组**（都是 inode=5, offset=0），归并之后靠写序择新。这里的「写序」是 (实例代号, 事务号) 的组合，`invariants.md:22`（I-1.2） 与 `decisions/18-块里携带什么信息.md:879` 那句「作废一个 checkpoint 必须换实例代号」共同保证：**任何合法运行都不会让被抛弃的实例代号大于或等于当前实例代号**（因为实例代号只增不减，且每次可写挂载都取比现有见证到的实例代号更大的新号）。所以按写序（先比实例代号，同实例才比事务号）择新，U2（实例 B）必然胜过 U1（实例 A）——**这条择新规则完全不依赖 locality_id 放在哪里、怎么编**，是 I-1.2 已发布谓词与写序全序（I-1.8）两条既有机制共同保证的结果。

⇒ **三条臂在这个面上同样等价，不分辨臂**：无论甲-S（S6 之后）、乙′（locality 不参与版本分组，`d18-locality-r2-opus-output.md:346` 那句改写已经把这一点讲清楚）、还是丙′（S9 把全部 key 统一编到当前值），版本选择这一步用的都是同一条写序全序机制，都会正确地把 U1 排除、只认 U2 为现行版本。这是「共同前提」的又一个实例，不新开欠账。

**唯一值得单独记一笔的**，是这条安全性本身**依赖 C143（inode 号水位在回退后会退回去重发）那个欠账项自己标注的残留疑点**（`decisions/08-核心索引结构.md:379`：「『未发布的等于没发生』只对常规挂载路径成立，扫描重建看的是盘」那句读起来像是反方向的）——这个疑点如果将来被坐实成一个真正的漏洞，它影响的是**所有**依赖写序择新的机制（inode 记录本身、extent 树、树表……），不是 locality_id 独有的风险，仍然按「三条臂共同」记账，不影响本轮判臂。

**会红的检查**：手造历史——create(inode=5, 实例A) → write(5,0) → 实例切换到 B（inode 号水位回退重发）→ create(inode=5, 实例B，不同对象) → write(5,0) → 损坏「extent 全丢，记录完好（指向实例 B 那条）」。断言：重建只放回实例 B 那个单元，实例 A 的孤儿单元不出现在任何现行 key 下；I-9.10（对象出生代三处一致，`invariants.md:266`，已实现）应当能顺带抓到这类孤儿（若对象出生代也在归组键之外被正确处理）。

### 4.3 打包对象在打包之后被重编、被搬出去

这一面在第一节 1.3 已经详细核过甲-S 的补丁（打包对象整体退化为丙′ 的规则）。这里补三条臂各自在「重编之后再打包」「打包之后再搬出去」两个方向上的行为：

- **丙′**：零格式位，打包与否不影响它的重建规则——`≤4KiB` 对象的槽既不带 locality，重建时始终走「对象按 (树 ID, inode) 认、只看本头的 extent 树，把全部 key 编成同一个值」（S9）。对象被打包、被重编、被搬出打包容器，这条规则的输入（inode 记录 + 幸存 extent key）从未变化过形态，**没有额外分支**。
- **乙′**：如果选择让槽带上 8 字节提示（D19（块指针的结构与宽度预算） 已定项 6 那条收严「槽里 key 的各段逐字节取打包前那一版单元头里的值」，`decisions/19-块指针的结构与宽度预算.md:173` 那一句），每次打包/重打包都要求写路径正确刷新这个字段；这个字段的优先级本来就排在最后（S3：「key > 记录 > 头提示 > 0」），所以即便某次重打包忘了刷新，产生的是一个过期的第四优先候选，不影响正确性，只是白白携带 8 字节。第二轮已经量出这类「stale_hints」计数（`d18-locality-r2-opus-output.md:375` 附近），它属于代价范畴，不属于 U1 正确性范畴。
- **甲-S**：打包之后这个对象已经退化为丙′，「打包之后再搬出去变回独立单元」这个动作，如果写路径重新把它当作独立码 1 单元写出（D27（小数据打包容器） 已定项 1 的「搬出去」= 走未改动的独立单元写路径，`decisions/27-小数据打包容器.md:278`），此时它**又重新具备了 AAD 保护的资格**——写路径需要知道「这个对象现在的 locality 是多少」才能正确填 AAD，而这个值只能来自当时写者手上持有的、正常运行时（非重建路径）的当前 locality，与重建过程无关，这是一个**正常写路径**的问题，不是重建路径的问题，不需要额外验证重建逻辑；它需要的是「独立单元写路径在处理『刚从容器搬出来』这类对象时，同样要填对 locality 字段」这一条写路径纪律，这条今天没有专门的条款覆盖（因为整个 locality_id 提议还没定案），交第四节记一笔待补条款。

⇒ **这个面上没有新的正确性打中，但确认了甲-S 的「双机制」结构代价在这里体现得最明显**：它需要区分「对象现在是不是打包状态」来决定走哪条重建规则，而乙′/丙′ 不需要。

### 4.4 克隆之后两个头各自重编同一个共享对象

**场景**：origin 头与克隆头共享一个数据单元（D8（核心索引结构） 已定项 6 已定「两个头共享 origin 的叶、各自 COW 之后是同身份两版」）。假设两个头的后台重新聚簇任务几乎同时决定要给这个共享对象换一个新的 locality 值。

**COW 语义天然隔离了这个场景**：D6（快照实现模型） 已定项 1 定「每头一棵自己的树」，重新聚簇写一条新 key = COW 出一个新的物理单元（对甲-S）或者只改自己那棵树里的 key（对乙′/丙′），两个头各自的写入落在**各自独立的树**里，不存在「同一个物理位置被两个头同时争用」的竞争——origin 头的重新聚簇不会碰克隆头正在读或正在写的任何字节，反之亦然。这是 COW + 每头一棵树这两条既有设计（D6（快照实现模型） 已定项 1、D21（权威态与派生态的分界） 的态别判据）联合提供的安全性，与 locality_id 放在哪个位置无关——**甲-S 唯一需要额外操心的是**：如果 origin 头 COW 出的新单元与克隆头仍然引用的旧共享单元，两者的 AAD 出生树段不同（E90（树 ID 进 AAD 与跨头共享） 那一节已定的「绑出生快照」机制），这一层与 locality_id 是否作为第六个 AAD 字段完全正交——不管 locality 进不进 AAD，出生树这一段的机制都已经在处理跨头共享的 AAD 校验问题。

⇒ **这个面同样不分辨臂**，是既有的 COW + 出生树 AAD 机制已经处理好的问题。**没有找到新的正确性打中**，标注为「手造推理，未穷举验证」。
