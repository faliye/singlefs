Background (settled facts, verified by the asker):

Units are the on-disk objects. Code 1 units are data units whose header carries a five-tuple (tree id, object id, object birth generation, anchor offset) and a birth generation. Code 2 units are B-tree nodes (derived state; after a scan rebuild they are always garbage and are rewritten). Code 3 units are packed record containers whose header carries a four-tuple (birth tree, record type, container number, birth generation). Every publish increments checkpoint_txg by one. Persistent order per publish: COW units, barrier, journal records, barrier, root slot. The root ring keeps the last K root records. The journal sequence number jsn is (instance id 32 bits, counter 48 bits); recovery applies records in strictly consecutive jsn order and stops at the first gap. Each writable mount takes a fresh instance id. A crash leaves an in-flight checkpoint whose txg is reissued by the recovery instance, so two units can carry the same birth generation but belong to different timelines.

The problem C113: after losing the indexes, a full scan finds several readable units with the same logical key. Nothing in the header says which of them is the current one for a given root, and nothing says whether a unit was ever published.

The fifth version of the fix:

P1. Every unit header gets a 10 byte write sequence = (instance id 4 bytes, transaction number low 48 bits). The transaction number is per instance, from 1, carried in the journal record header; all records of one transaction share it. A transaction takes its number at the moment it is assigned into a checkpoint; that also fixes its checkpoint number, so the birth generation is known. Cutting a checkpoint only closes membership: after the cut no new transaction is assigned into it, already assigned transactions finish writing their units, the publish phase waits for all unit writes to land. A write request is split per unit into separate transactions, so one transaction writes at most one unit of user data. Failure table: (1) failure before taking a number: nothing. (2) failure after taking a number but before any unit write request has been issued to the device: the number is burned, no unit and no record written. (3) failure after at least one unit write request was issued: a single replica write failure retries on another location with the same write sequence (bounded retries); a transaction level failure writes a void row (i, n) into the instance table published with the same checkpoint, and units carrying (i, n) are judged unpublished; an unrecoverable failure ends the instance, the mount turns read-only, the next mount recovers and writes rows. W1: one transaction leaves at most one net effect per logical key; on equal write sequence that is not a replica, the tombstone wins.

P2. Instance table: a code 3 packed record container of record type 4, records of 64 bytes, kind byte first. Kind 0 row: (instance id, publish cap txg, transaction number cap). Kind 1 chain pointer, always the last record of a page, with a has-next flag. Kind 2 void row: (instance id, transaction number). The root record gets two new fields: a pointer to the instance table and the maximum applied transaction number of the instance at the time this root was published. Rows are written: after any non-clean instance end, at the next recovery, one kind 0 row for every instance in [instance of the chosen root, new instance): (i, in-flight txg, max transaction number applied by replay), or (i, in-flight txg, 0) if nothing was applied. Rollback writes (r_old, T_old, the max applied transaction number stored in the R_old root record) and (i, 0, 0) for intermediate instances. Rows are published together with the root of the same checkpoint. Published predicate, with i_now the instance of the mounted root, a unit with write sequence (i, n) and birth generation b: if (i, n) has a void row then unpublished; if i is less than i_now: no kind 0 row means published, a row (i, T, W) means published iff b is at most T and n is at most W; if i equals i_now: published iff b is at most the mounted root txg; if i is greater than i_now: corrupt. The rule no row means published holds only within one timeline. Instance id lives in the superblock; a new id = max(ids in all visible superblocks, instance ids in all root records in the ring) + 1; read-only mounts do not take an id. First release has 2 disks; losing a disk allows read-only mount only, so a diverged disk rejoining is unreachable in the first release; with 3 or more disks it is reachable and is filed as a new open item.

P3. Current version rule. Inputs: mounted root, root set = writable heads in the tree table plus snapshots, ancestry table, instance table, scanned code 1 and code 3 units, tombstones and retirement records. Code 2 does not enter the rule. Replica merge first: readable units whose whole class identity segment (including the write sequence) is equal are replicas of one logical version and are merged into one candidate; payloads must be equal (code 3 by payload checksum, code 1 by a payload CRC that this version makes a prerequisite); if it cannot be told which copy is intact the group is recorded as damaged and not chosen. Then Visible_R(u) = published(u) and u.birth is at most T_R and there is an ancestry entry (a, c) for the tree of R with u.writer tree = a and u.birth at most c. v* is the visible candidate for key k with the largest write sequence. Current_R(k) is dead if a tombstone visible to R names k with death write sequence at least v*.write sequence, else v*. Rollback is defined as an explicit recovery: the administrator picks R_old from the rollback candidate set = roots in the ring that are still valid according to the instance table, that is (i, T) is a candidate iff the table has no row for i, or has a row (i, Ti, Wi) with T at most Ti. Rollback does not apply any record after R_old, takes a new instance id, writes the rollback rows, and the first new root gets txg = max txg in the ring + 1; runtime state (defer queue, allocator cursor, accounting) is reloaded from R_old. Rollback and its first new root are published together; before that it has no persistent effect. Rollback depth is at most the ring depth.

P4. Sweep. Allocation record entries are not deleted when a location is freed; the entry is rewritten as freed plus a free generation, and stays until the location is allocated again, at which point it is overwritten. Sweep admission: entry marked freed and free generation at most the txg of the oldest root in the ring and the header readable. Orphans (no entry, not in the allocator in-flight overlay): swept iff the write sequence instance is less than the current instance and the P2 predicate says unpublished; units of the current instance are never touched. The sweep watermark advances only to the txg of the oldest root in the ring and only when a full pass completes. Images produced by scan rebuild are permanently read-only; sweep and the reclaim gates are off after a rebuild.

P5. Tombstones carry a 10 byte death write sequence. Reclaim of a tombstone requires that every snapshot referencing the dead version is gone and that the sweep watermark is at least max(death txg, txg of the last root destruction).

Measurements used for the verdict between arm A (write sequence on all three unit codes) and arm B (write sequence only on code 2 and code 3, extent tree leaves turned into code 3 containers, data reached through the rebuilt extent tree):
E104 is a counting model. Its arm wseq_meta_only gives data units only a birth generation and gives containers the write sequence; data units are judged published iff birth at most root txg and same-key versions are ordered by birth. In that arm, in the worlds crash (in-flight txg partially replayed), crash_double, crash_clean, rollback and rollback_after_crash, every abandoned data unit is resurrected (6, 7, 6, 3, 6 per seed, identical to the arm that has no instance table at all), and in the same-txg world there are 4 ambiguities and 1 resurrection; in worlds without crash, rollback or same-txg multiversion it scores 0. The model does not build code 2 nodes and does not build the path where a surviving extent leaf points at the data; it measures only what a data unit can be judged by from its own header when the extent leaf is lost.
E105 is pure arithmetic: with 83 byte extent records, 16 KiB nodes and 32 KiB containers, turning the extent leaves into code 3 containers costs 1.25 times (100 million records), 1.333 times (1 million) and 1.5 times (10 thousand) the bytes per single update and per point lookup, and 1.44 to 1.78 times for batches of 10 to 1000 updates at 1 million records.
Verdict drawn: arm A. Reason 1: arm B returns data rebuild to the pre-C113 state whenever an extent leaf is lost. Reason 2: arm B makes every update of the hottest tree 1.25 to 1.78 times more expensive.
