Two questions about the space reservation that lets a copy-on-write file system always write its commit fixed point, on a first version with two mirrored disks.

Answer in English. Do not use any markdown emphasis: no bold, no italics, no headings with asterisks. Use plain numbered answers.

Facts from the design (treat them as given; F6 and F12 are observations, not rules):

F1. Admission formula: available = sum over devices of (capacity - allocated - unreclaimable - deferred free - mount-time commitment - abandoned-root exclusive amount) - pending-delete occupancy - committed reservation - checkpoint reserve pool. The six terms inside the parentheses (including the instance-switch reservation inside the mount-time commitment, and the abandoned-root exclusive amount) are summed per device; the last three terms (pending-delete occupancy, committed reservation, checkpoint reserve pool) are not. The stated reason: the terms inside the parentheses are physical quantities, since one full disk cannot be helped by another disk; the last three are pool-wide commitments.
F2. ckpt_cost = the sum of the current height of every record tree + the number of accounting tree nodes per publish. It is recomputed at every publish from the tree heights at that time. Its unit is 16 KiB metadata blocks, multiplied by 16384 when put into the byte formula of F1. It is merged into the mount-time commitment as a pool-level term and is not summed per device. There is no constant upper bound. The user's words when deciding: compute it live, and put it into the admission inequality as a pool-level term.
F3. The warm-up half of the instance-switch reservation: the c_max blocks of each empty publish take one copy on each disk, so that half is added once per device.
F4. The first clause of the allocation admission conjunction is available >= demand. A second formula elsewhere, allocatable = min(reusable + live metadata - reserve pool, df), and the formula of F1 are two gates in series: first F1's available >= demand, then the second rule's floor-raising logic. No clause was found that says whether demand counts logical bytes or bytes on every disk.
F5. Allocated bytes = the sum of placements in the allocation record tree. Capacity in F1 = the size of the unit area of the device.
F6. Observation from the byte table: the first version runs on 2 disks; every fixed structure has one copy on each disk; in the first transaction every unit has one copy on each disk; every allocation record exists once for each disk; the accounting value allocated is kept per device, 212992 bytes on disk 0 and 212992 bytes on disk 1.
F7. Columns per write: w = clamp(batched write amount + 1, 2, 4), then clamped to the number of writable devices. w >= 2 is a hard lower bound. In the first version w is always 2.
F8. A counting model counted the metadata blocks allocated by the commit fixed point. At pool scale, with commit-generated blocks clustered, an empty publish costs 9 blocks: allocation record tree 3 levels + central mapping tree 4 levels + 2 accounting nodes. At first-transaction scale it costs 4 blocks. Node splits and merges, the stripe member table, and the livelist were not modeled.
F9. Another model checked the instance-switch reservation: on a pool where one disk is 1 block short while the two disks together have enough, the per-device judgment says read-only and the pool-level scalar judgment says writable. That model states that the checkpoint reserve pool is not part of the term it covers.
F10. The reserve pool cures the checkpoint deadlock (a checkpoint must copy-on-write new nodes, which needs allocation; if the disk is full the root cannot be published). reserve >= ckpt_cost is enough; in a model it reduced stalls from 199 to 0. For ordinary allocation the reserve pool is a pure tax, and a larger reserve pool makes false ENOSPC worse.
F11. Another decided rule sets reserve pool = 10 + 7 c_max, and the same section says that whether this 10 + 7 c_max counts as a mount-time commitment is decided by the rule in F2. It is not clear whether ckpt_cost in F2 and this 10 + 7 c_max are one pool or two.
F12. Observation from the byte table: the tree table has 7 entries. Extent, inode, allocation record and accounting trees have roots; livelist, sparse side table and deadlist have a zero root pointer. The central mapping tree's root lives in the root record, not in the tree table. A tree table entry has no level field. The header of an index node has a level field, 0 for a leaf.
F13. After implementation the number of fixed-point rounds will be recorded, and exceeding the live-computed amount will fail a check. The live-computed amount is not an upper bound.
F14. A decided rule forbids false ENOSPC: space that the file system reports as unavailable must really be unavailable.
F15. Observation from the implementation source code, which today only writes the first transaction: the pool allocator records every placement once on every disk and marks the same slot range allocated in every disk's free map, choosing the slot from disk 0's free map so both disks use the same slot number. The publish path first takes all eight placements and returns a no-space error if any of them cannot be taken. There is no admission check, no reserve pool, no ckpt_cost, and no node split yet. The level byte of each index node is hard-coded at each node build call for the first transaction (inode tree root 1, every other node 0); recovery and the checker read the level byte from the node header.

Proposals must build on the implementation in F15: describe each change as a change to that code path. Separate models are only for independent verification.

Candidates for question 1 (how the checkpoint reserve pool is subtracted):
A1. Keep today: pool-level, subtract ckpt_cost * 16384 once after the per-device sum.
B1. Pool-level times copies: still after the per-device sum, subtract copies * ckpt_cost * 16384, where copies is the lower bound of w, which is 2.
C1. Per device: move it inside the parentheses as a per-device member of the mount-time commitment; every disk subtracts ckpt_cost * 16384, the same way as F3.

Candidates for question 2 (where the tree heights in F2 come from):
A2. Read levels at publish start: at the start of each publish, for every tree that has a root, read the level field of its in-flight root node header, add 1, and sum; the trees are the tree table entries with a nonzero root pointer plus the central mapping tree; between publishes, admission uses the value computed at the last publish.
B2. In-memory derived value: read the root levels once at mount, then add or subtract immediately on every root split or merge and recompute ckpt_cost; admission always reads the current value.
C2. Last published height plus a margin: use the heights of the last published roots, plus 1 level for every tree, to cover one root split inside the window.

Questions:
1. Question 1 correctness. Let u be the number of 16 KiB units a request writes, one copy on each disk. Read demand once as u * 16384 and once as 2u * 16384. For each of A1, B1 and C1, find the smallest pool state (capacity and allocated for each disk, and one request) where the candidate admits the request but afterwards the next checkpoint's fixed point cannot get ckpt_cost blocks on some disk. Try both a balanced pool and a pool with one disk short.
2. Question 1 false ENOSPC. For each of A1, B1 and C1, find the smallest pool state where the candidate refuses the request although, had it admitted, the fixed point could still get its blocks on every disk.
3. Question 2 correctness. For each of A2, B2 and C2, find the shortest operation sequence where the ckpt_cost subtracted at admission time is smaller than the number of blocks the next fixed point actually allocates. Consider inserts in the window that split a root, the fixed point's own inserts splitting a root, and a tree with a zero root pointer getting its first root. Also list which trees or units the fixed point rewrites on every publish and which of them the formula in F2 misses.
4. For each candidate, which facts above does it change, and give one check that would fail if the design were wrong, with a way to prove that the check can fail.
5. Which candidate would you pick for each question, and what single observation would change your pick? Do not decide by which candidate reserves less; report reserved amounts only as a cost.
