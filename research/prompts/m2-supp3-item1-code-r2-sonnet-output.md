## 二、Y3：两个决定是不是同一个理由的两面

### 二.1 两处「写入进程内存」的性质不同

分配代判定读的是 `crates/singlefs-core/src/allocator.rs:651` `pub fn records(&self) -> &[AllocationRecord]`——公开方法，返回的正是 D3（空间分配） 定义要持久化的那棵分配记录树（key = 落点，value = 分配代）在内存里的镜像；`crates/singlefs-harness/src/history.rs:1472` 只在发布**成功**（`Ok(output)` 分支，`history.rs:1485-1493`）之后取它，即只在这次发布已经把这些记录写到盘上之后读。

被拒的第 0 条收窄要读的是 `allocator.rs:574` 的私有字段：`reclaimed: BTreeSet<(DeviceIdentity, SlotNumber)>`，它自己的文档注释原文（`allocator.rs:574`）是「已回收、还没被复用的落点（盘上那条记录仍写着已释放；复用时那条记录被改写）。**只住内存**。」——这个字段没有 `pub` 访问器，而且它要分辨的「已释放、还在延迟」与「已回收、还没复用」两种情况在盘上写的是**同一个**标记（`is_released = true`），任何读盘的人（checker 也好、假想中更完美的读者也好）都无法从盘面字节里把这两种情况分开。

两者虽然字面上都是「写入进程内存」，但一个（`records()`）镜像的是持久内容——盘上的分配记录树今天虽然还没有 checker 判据去核对它（这正是收口表第 44 行登记的欠账），但**原则上**可以由另一段独立代码重新解析盘面算出同一批记录去对拍；另一个（`reclaimed`）是纯运行态缓存，**没有任何持久对应物**，没有第二条独立读法可以对拍。

再看用途方向：分配代判定是拿 `records()` 与「这次发布自己的 txg」这个独立于分配器内部逻辑的外部真值比较，用来**抓**失败；而第 0 条若用 `reclaimed` 收窄，是拿被测对象自己的私有簿记去把 checker 已经报出的 I-3.1 违例**解释成**「这属于已知、无害的形态，不算新发现」——如果 `reclaimed` 本身被同一个 bug 污染，这个解释就是循环论证（拿嫌疑人自己的证词给嫌疑人开脱）。

**推翻条件**：如果能证明 `records()` 在某条路径上会与「这次发布真正落盘」的内容不同步（例如某个 `?` 提前返回、`records()` 已经更新但那次写其实没有 FUA 落盘），使得分配代判定同样是在拿一份「没有持久对应物」的内存状态去判定失败，则「持久内容镜像 vs 纯运行态缓存」这条区分线会失效，Y3-a 的判定要重新核。

### 二.2 替「用写入进程内存把第 0 条收窄」辩护

**最强理由**：同一轮里「收窄第 1 条」（P1，r1 判决第二节第 1 行）恰恰也读了实现自己的解释逻辑——`history.rs:2027-2028` 原文：「读法用的是实现的 `recovery::readable_roots` / `choose_root` / `instance_table_of_root`（代码三方第一轮攻方的 P1 就这么读）：checker 判候选集时解实例表的那一段不对外……这里没另写一份解析。」如果「用实现自己的逻辑判自己」在第 1 条上可以被接受（已被 r1 判决采纳、13.1 节已实现、被攻过零轮），同一条理由不该单独在第 0 条上被当作否决的唯一依据——这是最直接的同类先例。

**不足以反过来的理由**：P1 读的是 `image_before_raising: &MemoryPool`（`crash.rs:142`，持久字节的内存镜像——`MemoryPool` 的字段是 `devices: BTreeMap<DeviceIdentity, SparseDevice>`，即每块盘的字节内容），`readable_roots` / `choose_root` / `instance_table_of_root` 都是对这份镜像字节的解析，原则上 checker 能用另一段代码重新解出同一个答案去对拍（这正是 13.1 节自陈的「下一轮能攻的一格」——一个**已知但未闭合**的风险，而不是被否决的理由）。`reclaimed` 字段没有这种「字节层面的第二条读法」可比对，它连「能不能被独立复算」这条门槛都过不了。P1 的开放风险（实现读法与 checker 读法没有逐条对过）与第 0 条候选方案的风险（唯一读法就是实现的私有缓存，没有第二条读法可对）不是同一个量级。

**推翻条件**：如果给 `reclaimed`（或等价信息）找到一种可以从盘面独立复算的办法（例如把「defer 队列」也写进盘上某个可读结构，D5（快照 / 空间记账机制） 已定项 2 之外新增一条持久标记），使得它不再是「唯一读法是私有缓存」，则这条区分线消失，第 0 条的收窄应当重新考虑用内存实现。

### 二.3 替「不用内存判分配代」辩护

**最强理由**：分配代判定同样只在「写入进程」里核对，如果下一轮攻方能证明 `session.allocator.records()` 在某条路径上会与「这次发布真正落盘」的内容不同步（例如某个 `?` 提前返回、`records()` 已经改了但盘上那次写没有真正 commit），这条判定就会把一次「其实盘上没有代不对」的情形误判成 `HarnessJudgement` 失败——即它同样有「用进程内存代替读盘」的软肋，与第 0 条被拒的理由字面上是同一类担忧。

**够不着的理由**：代码把这条判定限定在 `Ok(output)` 分支（`history.rs:1472-1493`，发布真正成功之后才比较前后 `records()`）；「发布成功」在这套代码里意味着这次发布的效果已经落盘（否则调用不会返回 `Ok`），所以 `records()` 在这一刻**理应**与盘面一致——这与第 0 条「无论何时都没有盘面对应」的缺口不是一回事，是「此刻应当与盘面一致、只是没有另跑一次 checker 去交叉确认」的缺口，而这条缺口已经被主 agent 记账：r1 判决第二节第 3 行「盘上这一格 checker 也判不出（`.claude/kb/invariants.md` 里只有 I-3.9（释放代落在停止引用它的那一格区间里） 管释放代，没有一条管已分配记录的分配代），记进增补 2 收口表第 44 行，新立不变量等第 2 件」。「不用内存判分配代」这个被否掉的做法唯一站得住的理由（没有独立复核过 `records()` 与盘面一致），已经被这笔账兜住，不构成推翻当前决定的新理由。

**推翻条件**：如果收口表第 44 行那条「新立不变量」迟迟不做、也没有任何盘面复核路径，且下一轮攻方在 `Ok` 分支里真的构造出 `records()` 与盘面不一致的具体例子，则这条辩护失效，应当重新评估「不用内存判分配代」。

### 二.4 种子 61、81 那 2 个槽是不是别的机理

**是，且已被正确并入「② 行那一族」，不需要另开一条**。`research/prompts/m2-supp3-item1-implementer-report.md:390,393` 原文：「快档种子 [0, 96) × 30……O > U（判得了，不是第 0 条）| 2（种子 61、81）」「最后一列是**今天的代码上**就有的：种子 61、81 都是 O = 13、U = 11、N = 2。多出来的正好是只被还在环里的被抛弃根引用的 2 槽，**不是转圈留下的**。」

「还在环里但被抛弃」（未转出根环）与「根环转圈丢失追踪」是两条不同的触发路径：前者与第 43 行（F 落在回退留下的空档、根还在环里但被 F 排除出候选集）属于同一个「被抛弃根仍占记账槽而未进候选集」的家族，只是触发条件不同（第 43 行是 F 直接切出候选集；种子 61、81 是在「转过一整圈」的历史里混进了同族现象，不是纯粹的转圈丢失追踪本身）。

`.claude/kb/milestone/02-second-txn.md:311`（收口表第 ② 行）已经原文引了 implementer 这句话，并把它写成「生成器的已知红第 0 条按今天的宽度接走的失败里混着别的机理……而多算的 13 个槽里 2 个只被还在根环里的被抛弃根引用」，归入 ② 行那一族、没有当成第 43 行本身、也没有单独立项——这个处理与 r1 判决第二节第 2 行「在镜像上做不到就停下交回，写明缺哪样输入，不放宽」一致：implementer 确实「只数了槽、没核机理」（同报告第 394 行），按指示止步，没有越界下结论。

**推翻条件**：如果有人核过这 2 个槽的机理，发现它其实不是「被抛弃根仍占记账槽」这一族，而是一个全新的、与 ② 行/第 43 行都无关的问题，则应当把它从 ② 行拆出来单独立项。
