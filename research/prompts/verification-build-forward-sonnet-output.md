TASK 1. Minimum contents forced by F2 to F14

Transaction layer, minimum contents and the fact that forces each:

1. A single shared transaction state machine plus a closed CommitStep enum with an exhaustive match and no wildcard arm. Forced by F4.
2. No media or layout predicate symbol may appear in the transaction layer or the admission path. Forced by F4.
3. Serial commit execution only, no concurrency control in v1. Forced by F5 (D13 item 2).
4. Exactly 2 disks. Forced by F5 (D2 item 9).
5. Pure SSD layout only. Forced by F5 (D12 item 5).
6. No encryption logic executed in v1, only reserved format fields. Forced by F5 (D9 item 10).
7. A block interface that issues plain writes, flush barriers, and FUA writes, because the persistence order in F8 is defined in exactly those three operation kinds. Forced by F8; the exact trait shape (method names, signatures) is my inference from F8's wording, not a literal fact.
8. The publish sequence implemented exactly as: COW units/nodes, flush barrier, journal records, flush barrier, root slot with FUA; fsync must not return before the root slot is durable. Forced by F8.
9. A checkpoint_txg counter incremented by exactly 1 on every publication, fsync-triggered included, reused as the root-ring rotation key, the accounting generation, and the replay watermark. Forced by F8 (D16 item 6).
10. Recovery must validate the checksum of every named unit before applying any record. Forced by F8 and by the per-item-validation prefix condition in F9.
11. Recovery applies only records whose (instance epoch, checkpoint_txg) is strictly greater than the chosen root's, gated by four prefix conditions: jsn strictly consecutive stop at first gap, watermark above the root, commit marker present, per-item validation of named units. Forced by F9 (D23 item 14).
12. Recovery scans the whole journal ring and validates every record; it must never trust the persisted tail. Forced by F9 (D23 item 3).
13. Root-slot selection validates all candidates first, then picks the newest by checkpoint_txg, ties broken by higher instance epoch. Forced by F9 (D22 item 7).
14. Self-certifying units only (root slot, journal record header, superblock slot) depend on an atomic write width, and that width is the runtime-probed physical_block_size, never a hard-coded constant; units with a parent pointer carry no width dependency at all. Forced by F11 (D20).
15. mkfs must seed generation 0 into every region of the root ring, place superblock as one copy per disk with slot rotation, and mirror the journal ring on two disks. Forced by F7 (D22 items 2 and 8).
16. Byte-exact encode and decode for the parts of the format already settled: data unit header (91 bytes, 42-byte common plaintext prefix), pointer (31-byte head plus two 11-byte location entries), journal record (4 KiB, 78-byte header, 56 bytes per named item), root record (121 bytes), root ring geometry (R=3 regions, prime-stride placement, slot width equal to probed physical_block_size). Forced by F7.
17. Padding after the declared length inside a data unit must be all zero and covered by the checksum. Forced by F7 (invariant I-2.3 cited there).

Blocked, not yet buildable to byte-exact form in v1: superblock field table (D22 item 9), inode field table (D8 item 6), allocation record entry width and key encoding (D3 item 7), accounting key segment widths (D5 item 5) — all four named open in F6. F6's own definition of "the first transaction" (mkfs, write one small file, publish once) cannot be executed end to end until these four close, because a written file needs an inode and an allocation record, and accounting needs its key widths. Five more segments have settled shape but open width per F6 (superblock slot rotation fields, birth txg inlined in pointers, accounting node header base bytes, journal transaction boundary field, tree-table unit header) and must be built against a placeholder width that is explicitly provisional.

Nothing in this list is added beyond what F2 to F14 force; every line cites its fact.

Checker, minimum contents:

1. An independent parser plus checker realizing a unary predicate P(image) over one image; it must not call any deserialization or traversal code of the crate under test. Forced by F2 (O2).
2. Two judging directions over the same image, traversal from the root and linear scan by unit header, sharing only format parsing. Forced by F14 (D13 conflict 1).
3. I-3.1 implemented as the one accounting check allowed to traverse the whole disk, using an algorithm the runtime's own incremental accounting does not use. Forced by F14.
4. The I-6 encryption class must report "not applicable" whenever encryption is off, never silently pass. Forced by F14; directly triggered in v1 because F5 already turns encryption off.
5. Ability to run each implemented invariant against at least one known-bad image, in the same round as the real run, so a checker that stops deciding gets caught. Forced by F13.

Blocked by F6, same four gaps as the transaction layer: byte-exact checker parsing for superblock, inode, allocation record, and accounting-tree entries cannot exist yet. Only root record, journal header, pointer, unit header, and root ring geometry can be fully byte-exact today.

Crash-point replay harness, minimum contents:

1. Three tiers: tier 0 fixed-seed minimal workload, tens of writes, exhaustive, no sampling, run on any commit touching the write path; tier 1 thousands of writes with stratified sampling by commit sub-phase; tier 2 nightly, no sampling. Forced by F3.
2. The numbers C, K_max, T1 must not be hard-coded into the kb yet, so the harness cannot ship with those constants pinned. Forced by F3.
3. Block-level write recording. F3 names this directly inside its own prerequisite chain (transaction layer, block-level write recording, harness, mkfs layout switches, N checkers).
4. A two-input record verifier taking (pre-crash image, record stream, post-crash image), deliberately kept outside the O1/O2/O3 numbering. Forced by F2.
5. A crash-state model for tier 0's exhaustive enumeration: barriers cut the write stream into segments; a crash state is all earlier segments durable, plus any subset of the current segment durable, plus nothing later; each write is atomic in this baseline model. An enumerator, a recovery model, and an independent audit function sharing no code with recovery already exist for one concrete case, 6 units plus 3 records plus 1 root slot, with state counts 72 (both barriers), 79 (only unit barrier), 513 (only root barrier), 1024 (no barrier). Forced by F10.
6. The model must distinguish self-certifying units, which depend on a width, from parent-pointer units, which do not depend on any width; the width used must be the runtime-probed physical_block_size, never the raw 512-byte device-measured value, which is explicitly not to be relied on. Forced by F11.
7. Torn writes cannot be produced through dm-flakey, whose only abilities are drop_writes, error_writes, corrupt_bio_byte; some other mechanism has to manufacture torn byte patterns. Forced by F11.
8. Per crash state, run the implementation's own recovery and the checker, plus mutation injection matching every checks-owed entry that names the harness as prerequisite and prescribes a must-go-red self-test: C76 (two variants, remove the barrier before the root slot, and disable per-item validation in replay), C42 (residual record from a discarded timeline), C22 (delayed-reuse window forced to 0), C80 (accounting flush removed from the publish path), C77 (stale tail plus reused blocks), C29 (recovery that trusts the tail first), C6 (drop one FUA on real virtio-blk in QEMU). Forced by F13, which names all seven as prerequisite-on-the-harness with a must-go-red self-test, without distinguishing any subset as optional.
9. For C6 specifically, real virtio-blk under QEMU with the relevant dm modules present. Forced by F12, which also records the current gap: the VM harness initramfs today carries only busybox and the test binary, no kernel modules, even though the VM kernel ships dm-log-writes.ko, dm-flakey.ko, nbd.ko, ublk_drv.ko and has FUSE built in.

Nothing added beyond F2 to F14 in this list either. What F2 to F14 leave open, and I am not filling in, is the exact torn-write sub-model for writes larger than physical_block_size: F11 states the two categories (self-certifying depends on width, parent-pointer does not) but does not give a complete enumeration algorithm for how many torn substates a multi-block self-certifying write should produce.

TASK 2. Build order the facts force, and what needs zero settled bytes

Ordering constraints:

1. F4's state machine and CommitStep enum, F8's persistence order and checkpoint_txg counter, and F9's recovery ordering are all settled at the semantic level independent of any byte width, so their skeletons can be coded before F6's four gaps close.
2. F7 already gives byte-exact layouts for the unit header, pointer, journal record, root record, and root ring geometry. These five structures can get real (not placeholder) encode and decode code today.
3. F6's four open items (superblock field table, inode field table, allocation record, accounting key widths) block only the structures they name. They do not block the state machine, the block interface, the recorder, the checkpoint_txg counter, or the parsers for the five F7 structures.
4. F10's E77 model and its enumerator, recovery model, and audit function already exist and do not depend on F6's gaps, since the case it models (6 units, 3 records, 1 root slot) uses only F7-settled structures.
5. F11's self-certifying-versus-parent-pointer distinction can be coded today because it is a rule about which units need width tracking, not about the byte layout of any one open structure.
6. F3's block-level write recorder needs only the block interface from step 1 above; it does not depend on F6.
7. F13's self-tests split into two groups by prerequisite. C76 (both variants), C29, and C77 concern the publish and recovery machinery in general and can be exercised against an empty publication (no data units, no inode, no allocation record) once mkfs and an empty-publish path exist, so they do not need F6's gaps closed. C22 and C80 need a real allocation and a real accounting update to have something to delay-reuse or to flush, so they need at least the allocation record and accounting key widths from F6 closed. C6 needs the QEMU tier and the initramfs fix from F12, independent of F6.
8. F2's record verifier and O1/RefFS have no stated urgency: F2 explicitly marks O1's upgrade to a full RefFS as "schedule undefined," so nothing in F2 to F14 forces it early.

Resulting order:

Step A, buildable today with zero further settled bytes: the transaction state machine and CommitStep enum skeleton (F4); the block interface with write, flush barrier, FUA (F8); the write-recording wrapper (F3); the checkpoint_txg counter mechanism (F8); parsers for root record, journal header, pointer, and unit header (F7); root ring geometry and mkfs's generation-0 seeding (F7); the E77-derived crash-state enumerator, recovery model, and independent audit function (F10); the checker's two-direction skeleton over the five F7-settled structures (F2, F14).

Step B, also buildable today: mkfs plus an empty publication (no data units) exercising only F7-settled structures, and tier-0 replay of that empty publication, including the C76 (both variants), C29, and C77 self-tests, since none of those name allocation or accounting specifically.

Step C, blocked on F6's four gaps: writing one small file end to end (needs the inode field table, D8 item 6), recording its allocation (needs D3 item 7), updating accounting (needs D5 item 5), and writing a mountable superblock with a full field table (needs D22 item 9). C22 and C80 also wait here, since they need a real allocation and a real accounting flush to interfere with.

Step D, independent side track: the initramfs fix for C6 (loading dm-log-writes.ko and dm-flakey.ko, per F12) can happen in parallel with steps A through C; it is gated by tooling, not by F6.

Step E, no stated urgency per F2: the record verifier and a base O1 in-memory model do not depend on F6's gaps either (they operate on the record stream and on POSIX-visible state, not on exact byte widths), so they could start as early as step A, but nothing in F2 to F14 forces starting them before step C; F2 only explicitly defers the full-RefFS upgrade of O1, not the base model or the record verifier.

TASK 4. P3's collapse of torn sub-states for parent-pointer units

The claim in P3 is that for a unit with a parent pointer, all torn (partially persisted) sub-states collapse to "not durable," on the grounds F11 gives: the parent pointer holds the child's checksum, and the parent is published only after the child is durable, per F8's ordering (COW units and nodes durable, then a barrier, before journal records and the eventual root FUA).

Forward derivation supporting the collapse: take a 32 KiB data unit (F7's fixed unit size) against a probed physical_block_size of 4 KiB. That unit write decomposes into 8 physically atomic 4 KiB sub-writes (32 divided by 4). Under F10's segment model, a crash state lets any subset of a segment's writes be durable; for one unit that is up to 2^8 minus 1 non-full subsets, or, counted coarsely by how many of the 8 chunks landed, 9 outcomes k=0 through k=8. Because this is COW, the target physical address for this write is a freshly allocated location; no currently durable pointer (old or new) ever names it unless the write completes and the parent is subsequently published. If the crash lands at any k less than 8, the bytes at that address are a mix of new content and either uninitialized space or unrelated old content from whatever last occupied that physical location. Read back and checked against the checksum the parent pointer will eventually carry, that mix fails, for any k from 0 to 7, with the same practical outcome as k=0: the child is unreachable through any live pointer, so it never gets read on the traversal path, and its checksum, if checked at all, fails. On that ground the collapse is valid for the traversal and recovery-reachability concern F11 is answering.

Where the collapse hides a class of crash states: F10 states plainly that E77, the only existing crash-state model with real numbers, treats "each write as atomic in that model (no torn writes)." E77's 72/79/513/1024 state counts for 6 units, 3 records, 1 root slot are computed with every unit write as one indivisible event; nothing in the given facts shows a validated model that actually decomposes a single unit into physically atomic sub-writes and audits the outcome. So the reachability argument above is a plausible derivation, not yet a tested one, matching D13's own open item 4 text, which I read directly and which independently marks this exact question as "推论，要走三方论证" before settling it.

More concretely, the collapse as P3 states it operates on the crash-point replay harness's reachability question, not on the checker's own defenses. F14 requires the checker to judge in two directions, and the scan direction reads units by their self-describing header, independent of any parent pointer. Take the same 32 KiB unit and 4 KiB probed block size, and suppose the crash lands at k=1: only the first 4 KiB, which by F7's layout is exactly where the 91-byte header sits, has landed with new content (new birth txg, new logical identity fields), while the remaining 28 KiB is stale leftover from whatever previously occupied that address. Under P3's collapse, this state is bucketed with "not durable" and, if the harness only ever materializes one representative byte pattern for that bucket (say, the fully-old k=0 case), this specific header-landed-payload-stale pattern is never actually written to a test image and fed to the checker. But invariants.md defines I-1.2 specifically to catch this pattern on the scan path, by comparing the header's birth txg against the current checkpoint_txg independent of any parent pointer or checksum. P3's text does not say whether the collapsed bucket is materialized once, materialized across its full range, or skipped from image generation entirely; none of P1 to P6 names this pattern as a required entry in P5's known-bad-image mutation table either. So the risk is not that the collapse is arithmetically wrong for reachability, it is that "collapse" as a state-count simplification could be read, and implemented, as "do not generate this pattern," which would leave I-1.2's scan-side defense against exactly this class of torn header untested by tier-0 exhaustive replay, contradicting C13's requirement that the checker be run against known-bad images in the same round it runs for real.

TASK 5. Single most important gap

The most important thing the proposal got wrong is the total absence of O3, the independent specification executor written in another language, which F2 lists as one of three oracles D13's settled verification route requires, alongside O1 and O2. P1 through P6 build O2 as singlefs-check, a stand-in for O1 through a minimal RefFS at step 5, and the two-input record verifier that F2 keeps deliberately outside the O1/O2/O3 numbering — but O3 itself is never named once across all six proposal items, not even as a deferred step like O1's RefFS upgrade is. This is not a byte-level gap that D13's already-open items 4 and 5 will absorb; it is a missing pillar of the verification story the project's own decisions already committed to. The repository check that would settle it is the same one that surfaced C25 on 2026-08-29: grep the proposal text and, once crates/ exists, the actual source tree for "O3," "独立规约执行器," and "specification executor," and count the hits; C25 already recorded zero hits for O1, O2, and O3 together across checks-owed.md and experiments.md as of that date, and this review finds the same zero-hit result for O3 specifically inside P1 to P6.
