BACKGROUND. Singlefs stores several of its own internal indexes as trees built out of a fixed-size on-disk node format called format-2. One of these trees, the allocation-record tree, records which storage slots on a device are allocated; today it is implemented with only a single node, which acts as both the root and the only leaf, with no internal levels at all, and this codebase has not yet decided what an internal-node entry for this tree should look like if it grew a second level. A design decision has been made to give this tree, among others, the ability to grow additional internal levels above its leaves as the number of entries in it grows, addressing the case where a device is large enough, or free space fragmented enough, that all of its allocation records can no longer fit in one single node. This document computes node-capacity, tree-height, total-node-count, and single-publish node-rewrite-count arithmetic for the allocation-record tree, under one specific candidate internal-node entry format, given fixed already-decided numeric inputs plus that one candidate; it does not ask you to decide whether growing extra levels is the right design, or how the split and merge logic should work, or whether the candidate entry format in FACT 6 is the right one.

FACT 1. In this filesystem, an on-disk structure called a format-2 index node is always exactly 16384 bytes in total size, regardless of whether it is a leaf node or, for a tree that has one, an internal node.

FACT 2. A format-2 index node's total header size, in bytes, is computed by a formula that depends only on that node's key width in bytes, not on whether the node is a leaf node or an internal node: header size equals 86 plus 2 times the key width in bytes plus 29. Within one single tree, every node at every level uses the same key width and therefore the same header size as every other node in that same tree. The allocation-record tree's key width is 10 bytes, and applying the formula gives this tree's header size as 135 bytes; this 135-byte header size is itself a literal already-decided constant in this codebase, not merely something you need to derive; the formula is given only so you can see where it comes from.

FACT 3. The allocation-record tree's leaf-entry width, in bytes, meaning the fixed size of one data record stored in a leaf node's entry area, is 20 bytes, made up of a 10-byte key plus a 10-byte value. This 20-byte width is itself an already-decided constant in this codebase.

FACT 4. In this codebase, a pointer stored inside one format-2 index node that points at a single child node, where that child may be either another format-2 index node or a format-3 packed-record container, is always exactly 86 bytes. This 86-byte width is the same fixed value used everywhere in this codebase that a format-2 node needs to point at one child; it does not vary by tree and does not vary by level.

FACT 5. This codebase already has two examples of a decided internal-node entry format for a format-2 tree, and both examples follow the same pattern: one internal-node entry consists of exactly one separator key plus exactly one 86-byte child pointer from FACT 4, and that one entry corresponds to exactly one child; there is no additional child pointer beyond the number of entries in the node, unlike some other tree designs where an internal node with n keys has n plus 1 children. The first example is the inode tree's internal entry: an 8-byte separator key plus a 26-byte identity reference plus the 86-byte child pointer, totaling 120 bytes per entry. The second example is the extent tree's internal entry: a 24-byte key plus the 86-byte child pointer, totaling 110 bytes per entry. Neither of these two examples is the allocation-record tree; the allocation-record tree's own internal-node entry format has not been decided in this codebase as of today.

FACT 6. This document's candidate for the allocation-record tree's internal-node entry, used only in this document, consists of exactly the 86-byte child pointer from FACT 4 and nothing else: no separator key is stored in the entry at all, so the key range covered by a child would have to be recovered some other way than reading it out of the entry, for instance from the child's position among its siblings, not from a per-entry key field. Under this candidate, the allocation-record tree's internal-entry width is exactly 86 bytes. This candidate is different from the one-separator-key-plus-one-pointer pattern shown in FACT 5 for the inode tree and the extent tree; this document does not ask you to judge whether an internal entry with no stored key at all is a workable design for the allocation-record tree, or whether it is better or worse than the one-key-plus-pointer alternative; it is given to you only as a fixed input number for the arithmetic below. FACT 7. Define a tree's leaf capacity as the largest whole number of leaf entries, using that tree's leaf-entry width, that fit into the space left over inside one 16384-byte node from FACT 1 after subtracting that tree's header size from FACT 2. The formula is: leaf capacity equals the floor of ((16384 minus header size) divided by leaf-entry width), where floor means rounding down to the nearest whole number and discarding any leftover fractional entry that would not fully fit.

FACT 8. Define a tree's internal fanout as the largest whole number of internal entries, using that tree's internal-entry width from FACT 6, that fit into the space left over inside one 16384-byte node from FACT 1 after subtracting that same tree's header size from FACT 2 (the same header size as its leaves, per FACT 2's statement that header size depends only on key width and is the same at every level of one tree). The formula is: internal fanout equals the floor of ((16384 minus header size) divided by internal-entry width). Under the one-entry-per-child pattern from FACT 5, this fanout number also equals the maximum number of children one internal node of this tree can point to.
