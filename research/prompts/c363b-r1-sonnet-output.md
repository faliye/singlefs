## 一、问题 1：「准入放行 ⟹ 这次发布的固定点分配一定取得到」推不推得出

### 结论：推不出。

### 1.1 准入放行的字面构成

D3（空间分配） 已定项 12（`.claude/kb/decisions/03-空间分配.md:243`）：

> **定案**：分配准入的合取式只登记在已定项 7 那张表一处，共七条，别处一律指过去。D16（发布语义） 已定项 1 的 `可分配 = min(可再分配 + 活元数据 − 保留池, df)` 与 D28（挂载期承诺量） 已定项 1 的九项式子是两道串联的闸：先过 D28（挂载期承诺量） 的「可用 ≥ 需求」，再过 D16（发布语义） 的抬 F 逻辑。

即「准入放行」= 通过 D28 已定项1 的逐设备聚合字节不等式（闸 A）与 D16 已定项1 的抬 F 循环（闸 B）。要推出的命题是「闸 A + 闸 B 通过 ⟹ 这次发布实际要做的提交内生块分配全部成功」。

### 1.2 缺口一：ckpt_cost 自陈不覆盖分裂

D28（挂载期承诺量） 已定项4 的射程句（`.claude/kb/decisions/28-挂载期承诺量.md:98`）：

> **射程**：保留池本身（`reserve ≥ ckpt_cost`、死锁 2 与假性 ENOSPC 的区分）的权威句在 D23（journal 的角色与格式） 已定项 24，这里只定它怎么进准入。条款里不写常数：分裂合并、条带成员表、livelist 都没进 E148（提交固定点按两棵记录树重算） 的模型，它的 9 块是模型数。

这是已定项4 自己承认：ckpt_cost（闸 A 里被减去的第八项）的取值不含「分裂合并」的额外节点。而 D8（核心索引结构） 已定项11（`.claude/kb/decisions/08-核心索引结构.md:321`）确立分裂是记账树、中央映射树这类码 2 btree 的正常行为：

> **多层码 2 树怎么长、怎么收**（记账树、中央映射树，以及照已定项 14 仍用码 2 btree 的树）：① 一次发布里分裂新建的节点与别的单元落在同一段，整条根到叶的路径照常 COW，不加写序步骤、不加屏障；② 叶装不下时从中间切；③ 收缩只摘空节点，根只剩一个孩子时降高一层，不做「低于一半合并」与借条目；④ 分隔 key 跟着维护：插到最左分隔 key 之下时把它压低，条目在兄弟间挪动之后把右边那个孩子的分隔 key 改成它新的最小 key；逐层可判：分隔 key ≤ 孩子节点头的最小 key，且 > 左邻孩子节点头的最大 key（D18（块里携带什么信息） 已定项 18 的 key 区间）；⑤ 树高 = 根节点码 2 头里的层级 + 1。

分裂是「这次发布自己的写」触发的（叶装不下才切），而 ckpt_cost 按已定项4读的是「发布那一刻」（即这次发布落笔之前）从根节点头现读的层级——分裂还没发生。所以闸 A 通过时被扣掉的 ckpt_cost，不保证 ≥ 这次发布因分裂而新增的节点数。**这是逻辑缺口，不是要不要维护另一份内存值的问题**：已定项4 明确「不设常数上限」，这句只说明它是按目前结构算的一个现值，没有任何一条已定项断言这个现值是「本次发布实际提交内生块数」的上界。

### 1.3 缺口二：「记录树」清单本身没有登记，Σ 与「每次发布连带重写」的清单对不上

D16（发布语义） 已定项9（`.claude/kb/decisions/16-发布语义.md:209`）：

> **定案**：记账树存在时就写——空发布也是发布，按 D5（快照 / 空间记账机制） 已定项 2「每行每发布重写」重写记账行，连带记账树节点、分配记录、映射条目与树表单元。第一次可写挂载的暖机时树表 0 条 ⇒ 零单元；以后的空发布按 D28（挂载期承诺量） 已定项 4 现算的 c_max 块。**树表 0 条的一版上写行的那次发布写两个单元**：实例表与一片分配记录节点，分配记录树根指针住根记录（D22（单元原子性怎么合成） 已定项 7）；被换下的上一版实例表与上一片分配记录节点记成已释放，重开时从这片节点重建这一版的账。根记录那一项只有树表 0 条、写过行的那一版写非零，mkfs 的第 0 代与带文件的一版写全 0，零单元发布照抄上一版。

即每一次发布（含空发布）都要重写四类结构：记账树节点、分配记录（分配记录树）、映射条目（中央映射树）、树表单元。而已定项4 的字面只有「Σ（每棵记录树当前的高）+ 记账树每发布的节点数」两项，「记录树」是哪几棵没有清单——`.claude/kb/checks-owed.md:316`（C363，全文见文末附录 A6；单行篇幅极长，正文不整行抄，只引其中一句短语核对过 `grep -nF` 命中）自己的题面就是这句：「记录树」指哪几棵也没写，E148（提交固定点按两棵记录树重算） 只建了分配记录树与中央映射树。

已定项4 自己的依据里也确认了 E148 的模型范围（`.claude/kb/decisions/28-挂载期承诺量.md:102`）：

> - E148（提交固定点按两棵记录树重算）：聚簇提交块时固定点是与用户块数无关的常数，用户块随机或全散布时没有可用上界——所以现算、条款里不写常数。

E148 的题面把「两棵记录树」定成分配记录树与中央映射树——但已定项9 逐字要求每次发布还连带重写「树表单元」，而树表不在 E148 的两棵记录树模型里、也不在「记账树每发布的节点数」这一项里（树表与记账树是两个不同结构，D16 已定项9 的原文把「树表单元」与「记账树节点」并列，不是同一样东西）。所以：**只要 Σ 与「记账树每发布的节点数」这两项合起来没有把树表单元算进去，ckpt_cost 这个总量在数值上就至少少算已定项9 规定的一个单元**，闸 A 通过不保证这一块也留了槽位。

### 1.4 缺口三：两道闸都是聚合字节判定，不是逐槽存在性证明

D3（空间分配） 已定项5（`.claude/kb/decisions/03-空间分配.md:93`）：

> **定案**：提交自身产生的块——分配记录树、记账树等结构的 COW 新节点——必须从 key 空间上连续的聚簇段（bump 段）分配；用户数据块的落点不受此约束。段的几何与 bump 次序在已定项 10，段耗尽时的回落在已定项 8 第 2 条。

其射程句（`.claude/kb/decisions/03-空间分配.md:95`）：

> **射程**：它是**分配器政策不是格式位**——聚簇段的位置与长度是运行时选择，盘上没有任何字段声明它；违反它的实现写出的镜像完全合法，只是每次发布贵几百倍。⇒ 拦它只能靠运行时读数：提交路径记「本次发布的固定点收敛轮数」，超过声明上界判红（`.claude/rules/fs-design.md` 硬要求 4：走错分支是性能悬崖，悬崖不报错）。w ≥ 2 时各设备上的聚簇段要不要对齐（每个单元 w 份副本各整落一列 ⇒ w 个聚簇段各自推进）全仓没有条款，归这一项的实现。

这句话直接否定「存在前置保证」：唯一的把关手段是运行时读数事后判红，不是准入判定时的前置证明。闸 A、闸 B 判的是全池/全设备字节总量（可用 ≥ 需求，可分配 = min(...)），而提交内生块要从**聚簇段**这个具体的 key 空间连续区间里拿槽，还要满足 D3 已定项7 那张登记表（`.claude/kb/decisions/03-空间分配.md:115`）里的七条合取（可用≥需求之外，还要不在活让渡区、不在条带表活成员、不在整理保护期、不在任何开放聚簇段之外……）。字节总量够，不等于聚簇段里恰好存在一个同时满足全部七条的槽——两者是不同层次的保证，没有一条已定分项把它们连起来。

### 1.5 小结：缺的是哪一项

三个缺口共同指向同一个空白：**没有任何一条已定项断言「ckpt_cost（或某个修正后的量）≥ 这次发布实际要新分配的全部提交内生块数，含本次发布自身触发的树分裂新增节点、树表单元、以及聚簇段里确实存在满足七条合取的空闲槽」**。已定项4 自己写「不设常数上限、现算」，这句话的性质是「按当前结构给一个现值」，不是「给一个上界保证」；缺口一、二说明这个现值本身有会漏计的项（分裂、树表），缺口三说明即便总量算对，也没有条款把「总量够」与「存在合法候选槽」连起来。

**什么现象会推翻「推不出」这个结论**：如果日后某条已定项显式写出「ckpt_cost 的计算过程包含对本次发布分裂增量的预估，且已证明恒 ≥ 实际值」，或者把「记录树」清单显式钉死为覆盖分配记录树、记账树、中央映射树、树表四者且给出树表的常数项，并且另有一条不变量把 D3 已定项7 的七条合取与准入闸的字节总量连起来（例如：证明聚簇段耗尽只会在总量已经不够时发生），三者齐了，这个结论就要收回。

**格 0（与今天的拒绝差在哪）**：D16（发布语义） 已定项1（`.claude/kb/decisions/16-发布语义.md:39`）：

## 二、问题 2：ckpt_cost 的 Σ 该罩哪几棵

已定项4 的字面（`.claude/kb/decisions/28-挂载期承诺量.md:90` 起，见 1.2、1.3 节引文）把 ckpt_cost 写成「Σ（每棵记录树当前的高）+ 记账树每发布的节点数」——即两个加法项，Σ 只罩「记录树」，记账树单列。下面逐一给五个候选定位。

### 分配记录树——进 Σ

依据：① D3（空间分配） 已定项5（1.4 节引文）把「分配记录树、记账树等结构的 COW 新节点」并列为「提交自身产生的块」，分配记录树是提交内生块的载体之一；② 已定项4 自己的依据 E148（`.claude/kb/decisions/28-挂载期承诺量.md:102`）把「两棵记录树」明确算成常数固定点的模型对象，而 `.claude/kb/checks-owed.md:316`（C363）指认这两棵是「分配记录树与中央映射树」；③ D8（核心索引结构） 已定项14（`.claude/kb/decisions/08-核心索引结构.md:380`）：

> - 两棵树的节点照样带 D18（块里携带什么信息） 已定项 18 的码 2 头（树 ID、层级、key 区间、诞生代号），树高照 D8（核心索引结构） 已定项 11「树高 = 根节点头层级 + 1」读。

D28 已定项4 的「形态」句（`.claude/kb/decisions/28-挂载期承诺量.md:94`）：

> - **形态**：ckpt_cost = Σ（每棵记录树当前的高）+ 记账树每发布的节点数，每次发布按当时的树高重算；每棵码 2 树当前的高 = 发布那一刻从它的根节点码 2 头里现读的层级 + 1（D18（块里携带什么信息） 已定项 18 的层级字段），不用内存里另存一份；按 key 空间定形状的分配记录树与 extent 树的高怎么读，随三方 `m2-keyspace-r1`。单位是 16 KiB 元数据块，代进已定项 1 那条按字节写的式子时乘 16384（式子里的「已分配」是「已分配字节」、「容量」是单元区大小，D5（快照 / 空间记账机制） 已定项 7）；它是运行时算出的量，盘上没有字段。

分配记录树虽按 key 空间异构成形，但树高仍照已定项11 的规则从根节点头读，与这句「每棵码 2 树当前的高」的读法口径一致。**进 Σ**。

### 中央映射树——进 Σ

依据同上（E148 的「两棵记录树」之二）；另外 D8 已定项11（`.claude/kb/decisions/08-核心索引结构.md:323`）把它列为标准码 2 btree：

> **内部节点的条目 = 本树 key + 子指针 86**：记账树 22 + 86 = 108、中央映射树 27 + 86 = 113。分配记录树与 extent 树按已定项 14 另起按 key 空间寻址的结构，结构在三方 `m2-keyspace-r1` 判；照码 2 btree 做时它们的内部条目是 96 与 110（extent 110 是用户 2026-09-24 早先定的）。

中央映射树按已定项11 第 ⑤ 条「树高 = 根节点码 2 头里的层级 + 1」读，与分配记录树同一读法。**进 Σ**。

### 记账树——不进 Σ，是公式里单列的第二项

已定项4 的字面把它与「Σ（记录树）」并列写成「+记账树每发布的节点数」，不是按「高」算。理由从 1.3 节已引的 D16 已定项9 定案句能读出来：记账行是按「每行每发布重写」重写的（D5（快照 / 空间记账机制） 已定项 2），一次发布触及多少条记账行（多少个分散的叶）由这次发布实际改了多少统计行决定，与静态的树高无关——同一个树高下，一次发布可能只碰 1 个叶，也可能因为攒批的多条记账行落在不同叶而碰好几个叶，用「高」衡量会低估。**这正是「某一棵每次发布只写一个单元、没有『高』」问题的一个变体，但它不是「没有高」（记账树是码 2 btree，有高），已定项4 是刻意换成「节点数」以避免用高度低估**。

### 树表——不进 Σ，也不在「记账树节点数」项里；应作为第三个加项，取常数 1（每次发布）

依据：D16 已定项9（`.claude/kb/decisions/16-发布语义.md:209`）把「树表单元」与「记账树节点」并列，是两个不同的东西：「连带记账树节点、分配记录、映射条目与树表单元」。D16 已定项1 正文里「非空」从盘上怎么认那一段（`.claude/kb/decisions/16-发布语义.md:43`）进一步确认树表按「单元」计而不是按树的多层结构计：

> **「非空」从盘上怎么认**：一条有效根算非空 ⟺ 它的树表里用户可见的树（inode 树、extent 树）的根指针，与它前一条有效根（按 txg 排；有效 = 按实例表判仍然有效 ∧ txg ≥ 当前的 F）树表里的不同。比的是树表里这两棵树的条目、不是树表单元自己的落点——每一次发布（连空发布）都重写树表单元（`crates/singlefs-core/src/transaction.rs`），按落点比会把空发布全算成非空。

另外 D8（核心索引结构） 已定项11（`.claude/kb/decisions/08-核心索引结构.md:317`）给树 ID 的登记范围是「extent 11、inode 12、分配记录 13、记账 14、中央映射 15、livelist 16、稀疏旁表 17、deadlist 18」，**树表不在这张树 ID 表里**——它不是一棵独立编号的码 2 btree，「树表单元」的措辞（单数、不提层级）与这一点吻合：树表本身没有「高」的概念。既然 D16 已定项9 逐字要求每次发布都重写它，而它的代价不是树高、也不随条目数变化出「高」，ckpt_cost 若要覆盖它，只能作为**第三个加项，常数 1（每次发布固定写 1 个单元）**。已定项4 现在的字面公式里没有这一项——这与问题 1 缺口二指出的是同一个空白。**答：树表不进 Σ，怎么计——常数 +1（每次发布）**。

### 实例表链——不进 ckpt_cost 的任何一项，由已定项1 里另一个独立成员覆盖
