**节点缓冲这一层在模型里不去重、且靠位置定胜负**（同一份源码）：

第 244–249 行 `fn push` 是纯追加（`self.e[self.n] = (k, v); self.n += 1;`），
第 270–277 行 `fn get` 逐字 `for i in (0..self.n).rev()`——**逆序扫，最后追加的那条赢**；
第 682 行 `push_down` 的注释逐字：

以及第 706 行 `flush_node` 上方注释逐字：

> /// **内部缓冲不做压实**：清空由下刷负责，压实只属于叶。

⇒ 在这个模型里，**同一个 key 的多条消息在内部缓冲里是共存的，胜者由数组位置决定，不由存下来的 seq 决定**。

**同 key 条目能不能跨 checkpoint 共存：不能，因为代进了 key。**
`.claude/kb/decisions/05-快照-空间记账机制.md`（已定项 5 那张表）逐字给出 key 五段，

> D5（快照 / 空间记账机制） 已定项 2 的骑手条款逐字「记账条目的**跨发布合并不再可行**（代进了 key）」⇒ **同一个 key 的待去重条目必然同属一个发布窗口**

**但同一个发布窗口内会 flush 很多次。** `05-快照-空间记账机制.md:258-259`（已定项 2）逐字：

> 代价是每 checkpoint 的记账写次数从 `统计量数` 变成 `统计量数 × 2`（一写一删）。

### （c）答案

**仓里没定，而且两种读法给出相反的答案——这一问今天答不了。**

| 读法 | 同 key 两条会不会共存于盘上 | 丙成不成立 |
|---|---|---|
| flush **直落叶**（E56 `arm_logstruct_wb` 的形态，内存里已折成一条） | 不会 | 丙这一问过 |
| flush **落进节点消息缓冲区**（D11 已定项 1 / 2 给记账树留了 665 条的缓冲，而**没有第二个写者能填它**） | **会**——一个窗口内多次 flush，每次都往同一批内部节点的缓冲里追加同 key 的条目 | 丙这一问不过 |

**倾向后者，理由是排他的**：D11 已定项 1 给记账树留了 ε = 0.65 的节点缓冲，
全仓找不到第二条往那块缓冲里写东西的路径 ⇒ 填它的只能是 write buffer 的 flush。
**但这是我的推理，不是仓里的字**，按 `evidence-discipline.md` 只能记成推理。

⚠️ 还有一条加重它的已定条款：`.claude/kb/decisions/21-权威态与派生态的分界.md:17` 逐字——

> 记账是同一条判据的已定实例：离线可由遍历重算，但被问到那一刻要有答案，故取权威态。单元类码不是态别的判据——**记账树的码 2 节点是权威态**。

⇒ 记账树内部节点是**权威态**，那块缓冲里躺着的待下刷消息也就是盘上的权威内容。
把「谁覆盖谁」交给一个只活在内存里的序号，等于让一份权威内容不自描述，
撞 `.claude/rules/fs-design.md`「元数据块必须自描述」与 D21 硬约束 6
（`21-权威态与派生态的分界.md:472` 转述逐字「把一个算不出来的权威值放进一个可重建的容器里，它就事实上晋升为权威态」）。
**这一条同样是推理，不是仓里的字。**

## 四、三问之外：丙与一条已定条款直接冲突

这一条不在主 agent 列的三问里，是正推过程中撞上的，**它比三问更硬**，所以单列。

`08-核心索引结构.md:462`（D8 未定项 7，2026-09-06 用户定案 ①）逐字：

> **① 宽度取 4 字节，并把因果倒过来**——seq 宽度定死，`T_dirty` 的上界从此是**挂载时判定**（4 字节 = 32 位窗口，按 30 字节/条对应约 120 GiB）

**seq 的作用域被这条定案钉成「一个发布窗口」，不是「一次 flush 批次」。**
依据是同段的推导：4 字节 = 32 位，下界 27 位来自
「一个发布窗口最多装 **71 582 788** 条记账条目（`T_dirty` 2 GiB ÷ 30 字节）」（E99 判据 1 + 5）。

⇒ **推论**：若 seq 只在内存缓冲里存在（丙），它需要区分的就只是**一次 flush 批次内**的条目，
位宽下界由内存缓冲容量定，与 `T_dirty` 无关。
那么 2026-09-06 那条定案「把因果倒过来、`T_dirty` 的上界从此是挂载时判定」
**整条失去依据**——`T_dirty` 是发布窗口的脏字节阈值，
只有当同窗口内先后落盘的同 key 条目要靠 seq 分先后时，它才会成为 seq 宽度的约束。

**丙要成立，就得连带推翻 2026-09-06 用户定案 ① 的依据链**（宽度那个数可以留，但它的推导要换一条）。
按 `.claude/rules/format-evolution.md` 与门禁阶段 `35-user-verdict-owed.sh`，这是要记一笔未还的账的。

⚠️ **这是推论，不是仓里的字。** 我没有找到任何一处正文明说「seq 的作用域是发布窗口而非 flush 批次」，
它是从那个 27 位下界的分母（`T_dirty`）反推出来的。

## 五、判决

### 丙出局

按跑前写死的接受条款——「若丙的三问里有任何一问答不出『不需要落盘的序』，丙出局」——
**三问全部答不出**，其中两问是全仓零覆盖。

更准确的说法是：**丙不是被证伪了，是今天连评估它的前提都不在仓里。**
三问里没有一问的答案是「不需要」，也没有一问的答案是「需要」——都是「没定」。

### 丙要先补哪几条定案才谈得上

按前置顺序（后一条依赖前一条）：

| # | 要补的定案 | 落点 | 为什么它是前置 |
|---|---|---|---|
| 1 | **write buffer flush 的落点**：条目从前端 flush 进树之后，落进节点消息缓冲区还是直接落进叶 | D8 或 D11 新增分项 | 决定同 key 两条会不会共存于盘上，也就是第一问 |
| 2 | **节点消息缓冲区的盘上语义**：插入时去不去重、同缓冲内两条同 key 谁赢、跨层归并顺序（「越靠根越新」成不成立） | D15 第 4 层（索引节点内部布局），今天未冻结也未定义 | 位置能不能替代 seq，全押在这一条上 |
| 3 | **发布点的排空契约**：发布点上 write buffer 强制排空到哪一层；发布集的边界 | C80 指向 D16 新增分项 | 决定崩溃后未排空条目的去向，也就是第三问 |

⚠️ 第 2 条有一处代价要先讲清：`21-权威态与派生态的分界.md:17` 已定「记账树的码 2 节点是权威态」，
所以那块缓冲不是随便一块派生态区域，它的语义要按权威态的标准定（自描述、可重算）。

### 甲乙之间：倾向乙（seq 进 value）

**依据不是权衡，是甲与两条已定条款的字面冲突。**

**冲突一：甲不在 D5 已定项 3 的 key 定义里，而那条已定的合并规则预设 seq 不是 key 的一段。**
`05-快照-空间记账机制.md`（已定项 3 第 2 项）逐字：

> | 2 | **key = (统计量类型标签, 维度元组, 代号)；value = 该统计量在该代的完整值；合并规则按统计量分：非单调统计量「后者胜」（**后者由 seq 定**），单调统计量取最大值（今天有已定项 4 第 12、13、14 三项：inode 号水位、清扫水位、最近一次根销毁的代号）** |

这句话只有在 **seq 不是 key 的一段**时才自洽：合并发生在**同 key 的多条之间**，
而 seq 进了 key，同一统计量同一代的每条都是不同的 key，**根本不会相遇，也就无所谓合并**。
「后者由 seq 定」这半句会当场变成空话。

**冲突二：单调统计量的「取最大值」在甲之下做不成。**
`08-核心索引结构.md:376` 逐字：

> **合并规则取最大值**（幂等、交换、结合）；条目照样带 seq（D8 write buffer 硬要求 3 是格式要求，一棵 write buffer 树一套条目格式），只是**合并结果不依赖它**。

「合并结果不依赖 seq」要成立，seq 就必须**不参与 key 的同一性判定**——否则两条根本不会碰面，
取不了最大值。这三个统计量（inode 号水位、清扫水位、最近一次根销毁的代号）是 D5 已定项 4 的第 12/13/14 项，**已定**。

**冲突三：甲会打破 D5 已定项 2 那条「点删不是扫描」的判据。**
`05-快照-空间记账机制.md:255-259`（已定项 2）逐字：

> **丢弃满足 `.claude/rules/fs-design.md` 第一格**：要丢的那一代**算得出来**（当前代 − K），
> **不用找** ⇒ 是点删不是扫描；触及的 key 数 = **统计量数**，
> **与 checkpoint 数无关、与盘容量无关**。

seq 进 key 之后，一代一统计量下不再是**一条**，而是最多 2³² 条
（窗口容量 71 582 788 条是 E99 算出的实付上界）
⇒ 「触及的 key 数 = 统计量数」**当场不成立**，丢一代从点删变成前缀范围删除。
同节那张表的「保留最近 K = 8 代 ⇒ 512 条 key」也一起作废。

**乙那一侧被点名的代价，量级小得多，而且已有先例。**
乙的代价是「排序契约不再表达在 key 编码里，而 D15 第 3 层冻的正是 key 编码」。
但**合并语义本来就已经不在 key 编码里**——`05-快照-空间记账机制.md` 已定项 3 第 2 项末尾逐字
「『标签 → 合并规则』是**盘上语义**，统计量登记表立成**独立冻结组件**（D15）」，
`15-格式冻结政策.md:67` 也逐字写着这类「四层之外的独立冻结组件」。
⇒ 把 seq 放进 value、让合并函数去读它，与既有形态同构，不新开一条口子。

⚠️ **乙不是没代价，只是代价没被这三条已定条款挡住。** 它自己欠的那笔是：
value 从 8 字节变成 8 + 4，记账条目 30 → 34 字节，
`first-txn-layout.md:118` 那一行（「write buffer 要求的 `seq` 段 | 4（候选）」）要跟着从「未定」翻成已定，
而 E97 / E71 / E54 里按 30 字节算的条目数与窗口容量（含 E99 那个 71 582 788）都要重算一遍。
**这笔重算我没做**，它不影响甲乙的取舍方向，但定案时要一起还。
