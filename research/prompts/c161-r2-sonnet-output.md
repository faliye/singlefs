## 一、问题 1：第一轮判决 2 复核

判决原文（`c161-r1-main-verification.md` 第 48 行）：「甲的最弱读法按跑前第 2 条出局；收严甲-R4 在攻方腿的模型上 8 步内不中，被攻过零轮。」要答两件事：这段历史照甲的原文可不可达；甲-R4 算不算「只许收严」。

### 1.1 S1/S2 照甲的原文可不可达

甲的原文（第一轮候选定义）是「节点缓冲区只收不走前端的更新」——这句话本身只回答「进了节点缓冲区的东西从哪来」，不回答「节点缓冲区会不会真的收到东西」。判定它可不可达，要看**这三棵前端树（记账 / 反向索引 / LRU）是不是真的存在一条不走前端的写路径**。

现查 `.claude/kb/decisions/08-核心索引结构.md:73`：

```
| 5 | **whiteout 删除** | **已定（2026-08-25）：接受，但批量删除必须走 intent log** | D8（核心索引结构）「已定项 5」 **状态：已定。** |
```

以及该文件第 269–280 行（已定项 5 正文）：whiteout 删除是「意图本身就是一条普通 key，骑在同一个事务层上」——它证明本工程里「删除」这类操作本身走的是普通写路径，不是某种脱离写路径的旁路操作。这不直接证明前端树存在旁路写，但说明**本工程从不假设「写」只有一种入口**：D8 的「结构」表（`08-核心索引结构.md:7-24`）把 write buffer 前端描述成「高频小更新……批量攒起来排序去重后批量插入」——这句话本身只圈定了**前端处理哪一类写**，没有一句话说「这三棵树上不存在别的写入口」。C161 那一行（`.claude/kb/checks-owed.md:163`）自己承认「前端 flush 之后条目落进哪一层……全仓一处正文都没有」，这恰好等价于「这三棵树的全部写路径有没有被前端垄断」这件事也没有被定过。

⇒ **甲的原文「两级都可以开」不是在描述一个已被证伪的假设，是在如实反映这段空白**：既然没有任何条款说「记账 / 反向索引 / LRU 的全部写必须经过前端」，甲把这段空白读成「存在旁路写、且旁路写进节点缓冲区」，是这段空白的一个**合法读法**，不是曲解。S2（`fe_put, direct_put`，2 步）与 S1（`direct_put, fe_put, flush`，3 步，反向接受条款第 2 条点名的形状）因此都可达。我复核了第一轮正推腿（`c161-r1-sonnet-output.md` 第 52–76 行）给出的读法 A / 读法 B 二分：读法 B（节点缓冲区对这三棵树永远收不到东西）成立的唯一前提是「文档没有另开旁路写入口」，而这恰恰是 C161 本身要解决的空白，不能拿它去反证甲的读法 A 不成立——**用尚未定案的东西去否定甲的一个可能读法，逻辑上是循环的**。⇒ 采纳：读法 A 是甲原文在今天的 kb 状态下唯一站得住的读法，S1/S2 可达，判决 2 前半段成立。

### 1.2 甲-R4 算不算「只许收严」

甲-R4 = 甲的读法（前端 → 根缓冲 → … → 叶，取第一条）+ 三条写时规则：flush 清路径上比它旧的同 key 消息、落叶比同一窗口到达序、不走前端的写逐出前端里同 key 的条目。逐条核对 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「臂的定义也在『跑前写死』之列」一节要求的三步：

1. **记一次输**：甲的最弱读法（无三条新规则）在 S1（3 步）与 S2（2 步）都读到旧值，这一点第一轮已经按最弱读法原样记录，本轮复核确认没有被悄悄改写成更强的读法再宣布赢。
2. **只许收严**：三条新规则全部是**写时**行为，读算法（「找到就停」）逐字未改；三条规则各自只**新增**一个动作（flush 清路径、落叶比到达序、直写逐出前端），没有一条删除或放宽甲原有的任何一句话——尤其是「节点缓冲区只收不走前端的更新」这句话在甲-R4 下原样成立，甲-R4 没有堵死旁路写路径本身，只是让旁路写发生之后**同步**把前端里的旧副本清掉，这是加约束不是减约束。
3. **写明收严在哪**：三条规则分别封住三处旧漏洞——规则 3 封 S2（旁路写不再让前端遗留旧值挡住读），规则 1/2 封 S1/S3（flush 与落叶不再让旧消息压过新值）。我核对了 `c161-r1-opus-output.md` 第 88–98 行的九条写死形状表：甲-R3（只有规则 1、2，没有规则 3）在 S2 上仍然是**旧**，说明规则 3 确实是独立生效的、不是规则 1/2 的冗余重复——这排除了「甲-R4 表面加了三条、实际只有一条在起作用」这种隐藏收窄。

⇒ 三步都过，甲-R4 是合法收严，**判决 2 全文站得住，不需要改判**。

## 二、问题 2：第一轮判决 3 与主 agent 更正复核

主 agent 更正原文（`c161-r1-main-verification.md` 第 37 行）：「第二节那一格我判错了：我写『记账 key 带代，同一个 key 只在一次发布里写』，而 D5（快照 / 空间记账机制） 第 284–287 行定丢弃是点删（附录 A7 整行在），墓碑就是同一个 key 在第二个发布窗口里的一次写。」要答：墓碑是不是作为一条消息进同一个缓冲；D8 已定项 7 宽度依据的前件在乙之下是不是真有反例。

### 2.1 墓碑是不是一条消息，进不进同一个缓冲

现查 `.claude/kb/decisions/05-快照-空间记账机制.md:284-285`：

```
**丢弃满足 `.claude/rules/fs-design.md` 第一格**：要丢的那一代**算得出来**（当前代 − K），
**不用找** ⇒ 是点删不是扫描；触及的 key 数 = **统计量数**，
```

以及同文件 `:308-309`（已定项 3 的字段表第 2、3 行）：

```
| 2 | **key = (统计量类型标签, 维度元组, 代号)；value = 该统计量在该代的完整值；合并规则按统计量分：非单调统计量「后者胜」（后者由 seq 定），单调统计量取最大值……** | …… |
| 3 | **走 write buffer 前端，条目自带 seq** | D8（核心索引结构） 已定 write buffer 覆盖「反向索引 / LRU / 记账」三类；seq 是它的第 3 条硬要求…… |
```

已定项 3 第 3 行逐字写「走 write buffer 前端，条目自带 seq」——这句话不分「普通更新条目」与「删除条目」，是对**记账树全部写入**的统一描述。点删既然是记账树上的一次写（价值是把某个 key 标记为已死，具体载体是 whiteout，见问题 1 引的 `08-核心索引结构.md:269-280`），它就没有理由绕开「条目自带 seq、走 write buffer 前端」这条统一规则单独走别的路径——kb 里没有一句话给点删开过豁免。⇒ **墓碑必然是一条 write buffer 消息，进入与其他更新完全相同的缓冲体系**，主 agent 的更正在这一点上是对的，而且理由比第一轮报告写的更硬：不是「碰巧」墓碑会撞进缓冲，是格式上没有第二条路给它走。

再核对关键点：墓碑与被删的那一行是不是**同一个 key**。已定项 3 的 key 定义是 `(统计量类型标签, 维度元组, 代号)`，"代号" 是**原始记录写入时的那一代**，不是"删除动作发生时的那一代"。`05-快照-空间记账机制.md:284` 的「要丢的那一代算得出来（当前代 − K）」说明：在当前代 g 执行的这次丢弃，删的是代号为 `g − K` 的那一行——也就是说墓碑要写的 key 正是 `(统计量, 维度, g−K)`，与代 `g−K` 那次发布窗口里写入的原始条目**逐字段相同**。⇒ 墓碑（写于发布窗口 g）与被删的原始条目（写于发布窗口 g−K）**同 key、跨越 K 个发布窗口**——这与主 agent 更正的措辞完全一致，我复核确认成立，不是转述漂移。

### 2.2 D8 已定项 7 宽度依据的前件在乙之下是不是真有反例

现查 `.claude/kb/decisions/08-核心索引结构.md:445`（节选，前件那句）：「同一个 key 的待去重条目必然同属一个发布窗口」。这句话是 seq 4 字节宽度的依据前提。2.1 节已证明：墓碑与被删行同 key、分属两个相隔 K 个发布窗口的不同窗口——**只要这两条消息在乙的机制下有机会同时停留在同一层缓冲里、需要被去重逻辑比较谁新谁旧，前件就已经被违反**。

这是否只是「理论上」违反、实际不触发？现查根缓冲容量与记账写入频率的关系：`.claude/kb/decisions/11-索引节点要不要留消息缓冲区.md:137`（已定项 7）给出「扇出 119、缓冲 665 条」（这是 ε=0.65 的将来值，本轮讨论的正是 ε>0 那一版，取用这组数字合规）；第一个事务记账树写 15 行（`.claude/kb/decisions/05-快照-空间记账机制.md` 已定项 8 标题所指），每次 checkpoint 一写一删约 30 条 write buffer 消息——665 ÷ 30 ≈ 22 次发布，根缓冲才会溢出一次而被迫下推。**只要 K（保留代数）≤ 约 22，这个"K 代内同 key 撞车"就不是边角情形，是常态**——而 K 的定案口径（`.claude/kb/decisions/05-快照-空间记账机制.md` 已定项 2 里 「K = 根环槽总数 + 1」）给出的具体数字通常在个位数到十几（N=8 时 K=9），远小于 22。⇒ **反例不但存在，而且在乙的机制下按正常运行频率就会触发，不需要构造极端场景**。

⇒ 2.1、2.2 都确认：主 agent 的更正站得住，我在其基础上补的两点是——① 墓碑走 write buffer 是格式层面的必然，不是巧合；② 撞车不是边角情形，是 K 远小于缓冲溢出周期时的常态。第一轮判决 3 不需要改判。

### 2.3 追加发现：「乙 + seq 全池单调」没有被验证过对并行乱序 flush 免疫

判决 3 把「乙 + seq 全池单调」列为交给用户的三个选项之一（`c161-r1-main-verification.md` 第 49 行）。我核对了第一轮攻方腿模型的候选定义表（`c161-r1-opus-output.md` 第 43–57 行）：「乙 + 全池单调」这一行只改了一件事——「seq 改成全池单调」，**乙的读算法（`乙-S：……跨层按位置（越靠根越新），同一层里由 seq 定新旧`）本身没有变**。

这里的关键是：乙的读算法分两半——**跨层**靠位置（不读 seq），**同层**靠 seq。全池单调只可能修好后一半（同层内序号可比），对前一半（跨层用位置代替显式比较）不产生任何影响，因为跨层判定压根不读 seq。而第一轮攻方腿 2.4 节（并行乱序 flush）打中的正是跨层/位置这一半：「D8 已定项 10 口径的 seq 当守卫一律失效（它就是插入序本身）」——这句话说的是**任何**把 seq 当守卫、而不显式走完整路径比较的读法，在并行 flush 下都可能被插入序与逻辑序的错位坑到，与 seq 的可比范围（本地窗口还是全池）无关，因为读的时候压根没有比较 seq 的那一步。

我复核了 `c161-r1-opus-output.md` 第 112–117 行（2.4 节正文）与第 88–98 行（九条写死形状表）：表里逐字出现「乙-S、乙-D 确定读到旧值（6 步）」，而「乙-S 全池单调」这一具体变体**没有出现在并行乱序 flush 的任何一行测试记录里**——2.1 节的穷举表（第 65–82 行）里「乙-S / 乙-X 全池单调」只在 U1 的 generic / accounting 两组基础穷举下测过（结果都是「无」），2.4 节的并行 flush 攻击没有专门针对这个变体重跑。

⇒ **这是第一轮论证的一处覆盖空白，不是我构造出的新攻击**：既然乙-S（本地 seq）在并行 flush 下 6 步被打中，而全池单调只改 seq 的可比范围、不改读算法，按 `.claude/rules/mutation-sampling.md` 「换一个取样点，它还同值吗」的判据，我没有理由相信只改了一个与该攻击面无关的参数就能幸免。这不构成「反向接受条款」意义上的新一轮打中（我没有现查产物逐步重跑这个变体），但足以说明**判决 3 把它作为可选项交给用户时，应该同时告知它尚未验证对并行 flush 免疫**，除非它也采纳「同 key 区间的冻结批次按到达序进树」这条共用修法（见下节），否则不应被当成一个已经站稳的干净选项。这一点我会在第五节的正面论证里重新处理。

## 三、问题 3：D8 已定项 7 的乙骑手是不是恒真句；共用规则该写进哪条

### 3.1 乙骑手按已定项 10 的 seq 口径是不是恒真句

现查 `.claude/kb/decisions/08-核心索引结构.md:449`（节选，乙骑手那句）：「同一个 key 的跨批次插入顺序必须与 seq 同向」。再核 `08-核心索引结构.md:78`（已定项 10）：

```
| 10 | **第一版记账走不走 write buffer 前端；seq 的取值规则** | **已定……seq = 同一个 (标签, 树, 设备, 代) 在一次发布里**被写进树的第几次**（不是运行期那个统计量被改的次数），从 1 起……** |
```

seq 的定义逐字是「被写进树的第几次」——它是插入动作发生之后**由插入顺序派生出来**的一个计数器，不是插入之前就独立存在、插入顺序需要去符合它的一个约束目标。⇒ 「插入顺序必须与 seq 同向」这句话在结构上等价于「插入顺序必须与『按插入顺序算出来的计数』同向」，**它的真值不依赖任何具体的插入序列，对任意插入序列都成立**——这正是恒真句的定义。我复核了攻方腿的这条结论（`c161-r1-opus-output.md` 第 117 行），同意它成立，且这不是一个需要反例才能验证的猜测，是把两处已定条款的定义字面代入就能得出的代数事实。

⇒ 骑手这句话**今天不构成任何约束**，它想保护的东西（更新的时间序不能被打乱）没有被它实际保护住。真正携带「时间序」信息的是内存里的到达序（write buffer 收到每条消息时打的时间戳或序号），而不是盘上事后由插入动作反推出来的 seq。

### 3.2 「同 key 区间的冻结批次按到达序进树」该写进哪条条款

候选落点有两处：① 就地改写 `08:449`（乙骑手所在行）；② 写进 C161 最终定案的新分项。

我判定应该是**两处都动，但分工不同**：`08:449` 这句话今天误导读者——它看着像是在约束乙类机制，实际什么都没约束，**必须改写或删除**，否则将来还会有人拿它当"已经有一条规则挡着乱序"的依据，重蹈第一轮攻方腿在 2.4 节指出的覆辙。但改写之后应该写成什么，取决于 C161 最终选哪条候选——如果甲-R4 或丙胜出，前端到树只有一条直落叶的插入路径，"跨批次插入顺序"这个提法本身可能不再适用（甲-R4 靠"逐出"与"比到达序"两条独立规则达成同样效果，不是靠"seq 同向"）；如果乙-D 或某个改良乙胜出，才需要一条明确写着"按到达序进树"的插入协议规则。

⇒ **正确的做法是**：`08:449` 这一行先改写为一句指路（说明乙骑手按已定项 10 的 seq 口径是恒真句，已被 C161 的新分项取代），把**实质规则**写进 C161 最终产生的那条新分项里，理由是：这条规则管的是「前端 flush 时消息按什么次序进入树」，这正是 C161 自己的题面（`checks-owed.md:163`：「前端 flush 之后条目落进哪一层……全仓一处正文都没有」），不是 D8 已定项 7 的题面（已定项 7 管的是 seq 的宽度、位置、射程三件事，不管插入协议本身）。把插入协议塞进已定项 7 会让这一项承担超出它标题范围的内容，未来另一个人复核已定项 7 时会重复第一轮攻方腿踩过的坑——看到一句听起来在约束乱序的话、以为已经有人管了，实际它只是恒真句的残留。这一处改动本身也要记进 2026-09 决策变更史（因为它改写了一条已定分项的正文表述，即使真值判断不变）。

## 四、问题 4：丙要改用户定案的 D11 已定项 6 树轴（记账与反向索引两棵）——改法、代价、连带

### 4.1 冲突是不是真的

现查 `.claude/kb/decisions/11-索引节点要不要留消息缓冲区.md:254-256`：

```
**树轴（2026-09-05 增补，随 D8（核心索引结构） 已定项 6）**：布局轴的答案不动，树轴另有一条分支——分支变量是已定项 4 那条谓词：**这棵树待下刷的消息能不能只从权威态（单元 + 记账 + 墓碑单元）重算**。
能 ⇒ 留缓冲、ε = 0.65；不能 ⇒ 内部节点不留消息缓冲区、ε = 0。今天只有 inode 树落在「不能」这一边：……
extent / dirent / 反向索引按 E59（缓冲消息能不能只从单元重算）「单元 + 记账」那一行三类全 0 判能；记账树按 D21（权威态与派生态的分界）「离线可由遍历重算」判能，但 E59（缓冲消息能不能只从单元重算） 那一列是神谕、未实测（C113（扫描重建时多版单元的现行版本判定无输入））。
```

这段话逐字给记账、反向索引两棵树判「能」⇒ ε = 0.65（留缓冲），**没有给"这棵树同时走前端"这件事留任何分支或豁免**。丙的规则是"前端树 ε 恒 0、前端树上的写一律进前端"，对记账、反向索引两棵树给出 ε = 0——两条规则对同一棵树、同一个字段给出不同的值，是字面矛盾，不是可以并存的两种读法。我复核确认第一轮正推腿（`c161-r1-sonnet-output.md` 第 121–135 行）与攻方腿（`c161-r1-opus-output.md` 第 200 行注、第 273 行条款清单）对这一点的判断一致，本轮我现查原文再次坐实，没有发现哪一方在转述时把这句话读宽或读窄。

### 4.2 改法

在已定项 6 的树轴段落末尾加一条前端例外：「一棵树若已被 D8 判定走 write buffer 前端（记账 / 反向索引 / LRU），其 ε 恒为 0，不受本谓词支配，不论谓词判『能』还是『不能』。」这条例外的位置必须在树轴谓词**之前**生效（即它是一条更高优先级的短路规则，不是谓词的第三种输出），因为谓词今天已经对记账 / 反向索引给出明确的「能」，例外要做的是**覆盖**这个已有判定，不是补一个谓词没覆盖到的空档。

这属于对一条**已定**（用户定案）分项的正面修改，按 `.claude/rules/format-evolution.md`「决策变更必须记进决策变更史……含推翻依据」与 `.claude/singlefs-ai-sop/rules/kb-discipline.md` 的矛盾唯一权威记录原则，需要：① 改 `11-索引节点要不要留消息缓冲区.md` 已定项 6 正文；② 在 `.claude/kb/decisions-history/2026-09.md` 记一笔条目（改前 / 改后 / 依据）；③ 跑一遍 `.claude/gate.d/30-decision-history.sh` 确认记账落了地。这一步不能只在 C161 那一行欠账表里带过——`checks-owed.md:163` 目前的 howto 只写「D8 或 D11 开一条新分项」，没有明写这条新分项需要同时**修改**一条已定分项，这一点本身值得在 C161 最终定案时补一句，否则后来者可能以为这是一条纯新增、不知道还牵连一条已定条款的正面修改。

### 4.3 代价

D11 已定项 2（`11-索引节点要不要留消息缓冲区.md` 第 168–170 行左右，E56 的收益表）给出的 2.91–5.03× 收益是对**「无 write buffer 前端」基线**测的——这一点第一轮正推腿（`c161-r1-sonnet-output.md` 第 137–145 行）已经指出：前端本身已经用「批量攒、排序去重、批量插入」买到了节点缓冲区想买的大部分好处，丙放弃的不是全部 2.91–5.03×，是**前端已经买到的那部分之外的边际收益**，而这个边际数字至今没有任何实验量过（E7、E56 都明确写着自己的对照组不带前端）。我复核这一判断成立：E56（消息缓冲的收益 vs ε）的四组收益数据全部建立在没有前端参与竞争的场景上，不能直接拿来当"丙放弃的就是这么多"的证据，只能记成一笔待验证的欠账，不能当零代价，也不能当满额代价。

### 4.4 连带

- **D8 已定项 6（inode 树结构，`08-核心索引结构.md:74`）不受影响**：inode 树本来就不是 write buffer 前端覆盖的三棵树之一（前端覆盖「反向索引、LRU、记账」，不含 inode），已定项 6 给 inode 树的 ε=0 是走「不能重算」这条路径判出来的，丙的新例外与它是两条独立成立的规则，互不冲突，也不需要合并。
- **C52（陈旧当成合法，`checks-owed.md:62`）的暴露面收窄**：C52 要求的故障注入检出机制是针对"内部节点缓冲区里存了别处没有第二份的数据"这类风险；记账 / 反向索引两棵树在丙之下永远 ε=0、没有节点缓冲区，C52 对这两棵树不再适用，只需要继续管 extent / dirent 等仍然 ε=0.65 的树。这是丙的一个附带的正面效果，值得记进 C52 的射程注里，但不改变 C52 本身仍然欠着的状态。
- **D21（权威态与派生态的分界）不受影响**：丙不改变索引整体仍是派生态这件事，只是让记账 / 反向索引两棵树的"派生态载体"从"节点缓冲区 + 叶"收窄成"只有叶"，D21 的分类不需要跟着改。
- **对 D15（格式冻结政策）第 4 层的归属不变**：节点内部布局（含消息缓冲区的树轴规则）本来就属于第 4 层（`.claude/kb/decisions/15-格式冻结政策.md:64`），而第 4 层今天未冻结（本轮背景材料前提七已核实），所以这次修改本身不违反任何冻结约束，只是在未冻结状态下的一次正常修订。

## 五、问题 5：四条候选的正面论证

### 5.1 甲-R4

**U1（读对）**：正面论证是一个归纳论证，不只是「穷举没打中」。规则 3（不走前端的写逐出前端里同 key 的条目）保证：任一时刻，同一个 key 在「前端」与「节点缓冲区」不会同时各留一条互相冲突的消息——旁路写发生时，前端里的旧副本被立即清除；前端 flush 发生时，规则 1 清掉路径上比它旧的同 key 消息，规则 2 让落叶顺序服从到达序，这两条联合保证「沿路径找到的第一条必然是到达最晚的那条」这个 Bε-tree 读算法赖以成立的不变量在每次写操作后都被重新恢复。这是一个**保持型不变量**（write-time invariant maintenance），不是靠运气躲过了 8 步穷举——这一点也被第一轮攻方腿的阴性对照证实（76401 个状态零命中，远超其余候选的探索空间）。

**U2（崩溃）**：与丙共用同一个答案——发布前把前端强制排空到叶，这是发布协议的前置步骤，不是新的发布路径；崩溃发生在排空完成前，前端内存态直接丢弃（那次更新从未被承诺持久）；崩溃发生在排空完成后，走标准根 + journal 前缀恢复，不需要恢复时扫描或重放前端内容。

**U3（代价与格式）**：**零格式改动**——三条规则全部是运行时写路径行为，不新增字段、不改 key 编码（第 3 层）、不改节点内部布局的字段表（第 4 层）。付出的是运行时代价：每次发布要把前端树的一整条（或多条）路径写出去，按攻方腿的计数模型是乙的 2.66–10.83 倍（`c161-r1-opus-output.md` 第 166–187 行表，且这不是 E56 的重跑，只是计数模型给出的方向性线索）。

**U4（检查与判别力自证）**：会红的检查——造一份记账树镜像，key K 在叶里是前端已 flush 的新值，同一路径某内部节点缓冲区留着一条更旧的旁路写入，标准读法必须读到叶里的新值；判别力自证：把两条消息的新旧对调，检查必须由绿转红。攻方腿的变异测试（`c161-r1-opus-output.md` 第 224–236 行）里 M2（丙的前端树上有绕开前端、直落叶的写者）、M7（flush 不清路径）、M8（落叶不比到达序，只在乱序 flush 负载下敏感）、M9（不走前端的写不逐出前端）四条变异分别对应甲-R4 的三条规则，全部被抓，说明三条规则各自都是有效约束、不是摆设。

**要改的 kb 句子**：无需修改任何已定分项。只需在 C161 最终定案的新分项里写下这三条规则 + 发布前排空这一步协议。

### 5.2 乙-D

**U1**：乙-D 用「一个缓冲区里同 key 至多一条，新来的替换旧的（单调统计量取最大）」这条**结构性**规则替代 seq 比较，跨层、同层都按位置定新旧。这条规则本身是 checker 可判的静态结构约束（"同一缓冲区没有重复 key"），比甲-R4 的写时行为约束更容易在盘上核实。攻方腿的模型穷举（1905 个状态，深度 8 零命中）与阴性对照支持这一点。

**U2**：乙-D 的定义本身没有排除"发布前排空到叶"这一步——它只规定了缓冲区内部的去重规则，不规定发布协议。**这是乙-D 与乙-S/乙-X 的关键分野**：乙-S/乙-X 的卖点是"允许跨发布留存、不强制排空"，而乙-D 如果同样采纳"发布前排空到叶"，就完全继承甲-R4/丙在 U2 上的干净答案，付出的代价只是排空时机之前允许消息短暂停留在中间层（这在单次发布窗口内部是安全的，因为乙-D 的去重规则保证同一层不会有重复 key）。⇒ **正面论证是：乙-D 应该显式采纳"发布前排空到叶"这一步**，不采纳的话就继承 C80 未解的缺口（与第一轮正推腿对乙的判断一致），采纳之后 U2 与甲-R4/丙同构。

**U3**：不改 seq 的宽度或位置（乙-D 不读盘上 seq），但需要新增一条节点内部布局的结构性不变量——"同一缓冲区内同 key 至多一条"——这条不变量本身不新增字节，但它是第 4 层（节点内部布局）的一条新规则，需要在冻结前写进 spec 并配 checker。这比甲-R4（零格式改动）重，比"乙 + 全池单调"（要改 seq 宽度）轻。

**U4**：会红的检查——四种可摆出的位置对（前端+根缓冲、根缓冲+孩子缓冲、根缓冲+叶、前端+叶；同一缓冲同一发布因去重摆不出来），全绿基线、对调值后全红；判别力自证是把检测的"去重替换"逻辑关掉，同一份镜像必须由红转绿。另可加一条纯结构检查："扫描全部缓冲区，断言没有重复 key"，独立于读检查，直接验证乙-D 的核心不变量。攻方腿变异 M3/M4/M5/M10 分别对应"去重留旧丢新""下推时孩子里旧消息不被替换""先读叶再读缓冲""再开一条直进根缓冲的写路径"，全部被抓。

**要改的 kb 句子**：`05-快照-空间记账机制.md:308`「后者由 seq 定」改成「后者由位置定（乙-D 形态下）」或改写为分支表述；`08-核心索引结构.md:42-44`（硬要求 3「这是格式要求」）要补一句——乙-D 下盘上 seq 仍然按已定项 7/10 写入（字段不删），但读路径不消费它，这是一个需要显式记录的"seq 有格式位置、无运行时读者"状态，防止将来有人以为 seq 没被读就可以砍掉这个字段（它仍然服务于甲-R4 等其他候选，以及可能的将来诊断用途）。

### 5.3 乙 + seq 全池单调

**U1**：全池单调修好了「同层内 seq 可比」这一半（第 2.2 节 D8 已定项 7 前件反例问题），但按本报告第 2.3 节的分析，**没有修好「跨层用位置代替显式比较」这一半**——除非它同时采纳到达序修法。⇒ 正面论证只能给出**有条件成立**：若这条候选额外采纳「同 key 区间的冻结批次按到达序进树」（第三节结论），并且读算法从「找到就停」改成「走完整路径、显式比较 seq、取最大」（第一轮正推腿第 107–109 行已指出这个改法本身会取消 Bε-tree 提前终止的性能特性），U1 才能补全；不改读算法的话，它对并行乱序 flush 的免疫力与乙-S 一致（都没被验证过），不能当干净候选交给用户。

**U2**：与乙-D 同理，取决于是否额外采纳发布前排空——若采纳，与甲-R4/丙同构；若不采纳（这正是这条候选存在的意义所在，否则它与乙-D 没有实质区别），就继承 C80 未解的缺口，且记账树「能重算」这条判据本身还是未实测的神谕（`11-索引节点要不要留消息缓冲区.md:256`「记账树……但 E59……那一列是神谕、未实测」），意味着这条候选如果坚持跨发布留存，是把记账的崩溃一致性押在两个都没有实证支持的假设上（seq 全局单调本身没建模、「能重算」没实测）。

**U3**：代价最高，而且不完整。已定项 7 的原有依据（`08-核心索引结构.md:445-447`）要整条重开——4 字节的窗口撑不住全池单调所需的跨发布号段，要么改 8 字节（记账条目 34→38，连带 4 个实验的数要重算，落点 C162），要么给缓冲消息加一个「最长停留期」的新机制。攻方腿自己标注这是「推理，没建模」（`c161-r1-opus-output.md` 第 199 行）——**这不只是代价高，是代价本身没有被具体化到可以估算的程度**。

**U4**：这是四条候选里唯一给不出判别力自证的。判别力自证需要一个具体机制去关闭/破坏再验证检查能不能转红转绿，而「8 字节还是停留期限」这两个候选机制都还没有具体实现，没有实现就没有可以注入故障的对象。按 `.claude/rules/mutation-sampling.md` 与 `.claude/singlefs-ai-sop/rules/test-discipline.md`「变异测试证明的是断言会红，不是覆盖」的判据，这条候选目前**应该记一次「写不出判别力自证」**，不能留白当成「以后再补」，因为它连需要测什么都还没定。

**要改的 kb 句子**：`08-核心索引结构.md:445-447`（已定项 7 的宽度依据①）整条重开；若选 8 字节路径，`E97`/`E71`/`E54`/`E99` 四个实验的数按 C162 重算；若选停留期限路径，需要先建模再回到 U1–U4 重新走一遍——这条候选目前不具备与另外三条同等的可比性，交用户时应明确标注它比其他三条候选「欠一步」。

### 5.4 丙

**U1**：结构性排除，不靠算法比较——前端树只有前端一个写路径、节点缓冲区不接受任何消息，同 key 跨级共存这件事在格式层面不可能发生。攻方腿穷举 169/514 个状态、零命中，探索空间是四条候选里最小的，因为丙的状态空间本身最简单——这是它「干净」的根本原因，不是运气。

**U2**：与甲-R4 共用同一个答案（发布前排空到叶）；非前端树（ε=0.65 的树，如 extent/dirent）延用 D11 已定项 3/4 已经接受的「陈旧可检出、可从权威态重算」答案，不是新问题。

**U3**：需要问题四给出的 D11 已定项 6 修订（记账/反向索引两棵树 ε 恒 0）；不动 seq 宽度、不动 key 编码；付出运行时代价（每次发布写出的节点数比乙多 2.66–10.83 倍）。

**U4**：只有一种可摆出的位置对（前端 + 叶），是四条候选里自证形态最薄的一个——这不是缺陷，是丙状态空间小的直接推论，但意味着**读检查本身不能覆盖丙的全部安全性论据**。丙真正的安全性来自「前端树上只有前端一个写者」这句定义，而这句话不是一条读时能验证的性质，必须做成写路径上的检查。

**丙的「前端树上没有第二个写者」怎么做成会红的检查**：分两层，取更强的那层优先。① **类型层**（最强）：给记账 / 反向索引 / LRU 三棵树的插入函数设计成——除了 write buffer 的 flush 路径，代码里**没有第二个函数签名**能拿到这三棵树的「直接插入节点缓冲区」的能力；这样「没有第二个写者」从运行时不变量变成编译期不可能违反的状态（`.claude/singlefs-ai-sop/rules/code-discipline.md`「让非法状态无法表示」的直接应用）。② **运行时兜底**（若 mkfs/day-1 写入等场景需要共用同一个底层插入函数）：在插入路径上加一条 `debug_assert`，检查调用方传入的树 ID 若属于这三棵前端树、且不是来自 flush 路径，就 panic；判别力自证——在测试 harness 里构造一次「伪造的旁路直写」调用，断言这条检查必须触发（与攻方腿模型层面的 M2 变异同构，`c161-r1-opus-output.md` 第 227 行，2 步内被抓）。两层选哪层由实现阶段的具体代码结构决定，但①严格优于②，实现时应优先尝试类型层方案。

**要改的 kb 句子**：`11-索引节点要不要留消息缓冲区.md:254-256`（已定项 6 树轴）加前端例外（问题四已详述）；C161 最终新分项需要写入「前端树上没有第二个写者」这条不变量与上述检查形态。

## 结语

本轮复核的净结果：第一轮判决 2、3 与主 agent 的更正在本轮换攻击面（节点分裂合并、fsync 部分发布、多路径、K>1、陈旧检出）之后仍然站得住，没有发现需要改判的地方。本轮唯一的实质性追加发现是「乙 + seq 全池单调」这条候选的并行 flush 免疫力尚未被验证、U4 判别力自证给不出来——这两点建议在交用户定案时一并说明，不要让它看起来与甲-R4、乙-D、丙三条已经过 U1–U4 完整检验的候选处于同一个可信度层级。四条候选里甲-R4 与丙不需要动任何已定格式字段（只需要新协议规则/一条树轴例外），乙-D 需要一条新的结构性不变量（不动字段宽度），「乙 + 全池单调」代价最高且尚未建模完整——这个代价排序与第一轮的倾向（U3 里丙 / 甲的节点写入数远高于乙）方向相反，值得在最终交用户时把「运行时代价」与「格式改动代价」分开列，不要让前者的数字掩盖后者的排序。
