Q1. Clone of a clone. Head H1 cloned at txg 100. At txg 150 H1 writes block B (birth 150). Snapshot S of H1 at txg 200 (H1's prev_snap_txg becomes 200). Head H2 cloned from S at txg 250 (H2's prev_snap_txg initialized to 200). H1 destroyed at txg 300. The livelist for H1 contains ALLOC B at birth 150. Destruction When destroying H1, the release boundary is prev_snap_txg 200. Since 150 <= 200, B is not released. H2 references B from S, so no release of B occurs. However, if the boundary was incorrectly set to origin txg 100 (as per initial proposal before round one fix), then birth 150 > 100 would cause B to be released while H2 references it. But with the corrected boundary (prev_snap_txg), B is not released. This scenario is safe under the corrected boundary. However, the proposal's initial boundary was wrong, and the round one fix assumes the boundary is prev_snap_txg. But if the implementation fails to update the boundary correctly during snapshot creation (e.g., H1's prev_snap_txg remains 100 after snapshot at 200), then destroying H1 at 300 would use boundary 100, releasing B (birth 150 > 100) while H2 still references it. This is a counterexample if the prev_snap_txg update fails during snapshot creation.

Q2. Snapshot handoff. When snapshot S is taken of head H1 at txg 200, H1's livelist is kept. H H1 wrote block B at txg 150 (birth 150) before the snapshot. The livelist contains ALLOC B. After snapshot, H1's prev_snap_txg is 200. Entries with birth <= 200 (like B) can never be released when H1 is destroyed later. If the livelist is kept, these entries remain in the livelist but are never processed for release. For example, H1 destroys at txg 300: boundary is 200. ALLOC B (birth 150) is in livelist but not released. This is wasted space as the entry is stored but unused. No wrong release or leak, only wasted space. If the livelist were cleared on snapshot, the ALLOC B entry would be removed, avoiding wasted space. But the proposal does not clear the livelist, so keeping it causes wasted space.

Q3. Crash during destruction. Head H1 destroyed as intent. Livelist has ALLOC B (birth 250). Boundary is prev_snap_txg 200. Intent committed at txg 400. First batch processes ALLOC B: releases B. Before committing the batch (i.e., before updating the livelist tree to remove ALLOC B entry), system crashes at txg 401. Recovery re-runs intent. Livelist tree still contains ALLOC B entry. System reprocesses ALLOC B, releasing B again. If B was already freed, this causes double free. For example, B was a disk block marked free on first release; second release corrupts free space map. This violates idempotency because the release operation is not safe to run twice.

Q4. Counter consistency. Livelist tree's tree table entry has entry counter. Suppose H1 writes block B at txg 150: ALLOC B added to livelist. Counter incremented from 0 to 1. Before updating tree table entry to store counter=1, system crashes. Published state shows counter=0 in tree table, but livelist tree has one ALLOC entry. True count is 1, counter is 0. A check that scans the livelist tree to count actual entries and compares to stored counter would detect this inconsistency inconsistency.

Q5. Birth source. Parent pointer carries no birth txg. When freeing block B, the system needs birth txg to decide release or deadlist. If birth txg is not stored elsewhere, the system cannot determine it. For example, H1 writes block B at txg 150. When freeing B, parent pointer has no birth txg. If birth txg is not stored in block metadata or livelist, the system has no source for birth txg. During destruction, it cannot compare birth to boundary. This causes incorrect decisions: if birth txg is unknown, the system might assume birth > boundary and release a block that should be kept (leak), or assume birth <= boundary and add to deadlist a block that should be released (double free if later released again). Alternatively, if birth txg is stored in block metadata, each free operation requires a disk read to fetch it, increasing I/O cost significantly. For example, freeing a single block requires reading its metadata from disk, which could be 10x slower than if birth txg was in parent pointer.
