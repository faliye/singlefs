### 二·二 D5（快照 / 空间记账机制）里 birth 与 deadlist 那一段（`.claude/kb/decisions/05-快照-空间记账机制.md:16-36`）

> **块 b 被快照 S 引用 ⟺ `birth(b) ≤ S.txg < death(b)`**，左闭右开。

| 量 | 定义 | **不是**什么 |
|---|---|---|
| `birth(b)` | 块被**发布**的那个 checkpoint 号 | 不是写请求发出时所在的开放 txg——崩溃后该号会被重发 |
| `death(b)` | 最后一个活引用被摘掉、**且该摘除被发布**的 checkpoint 号；仍在活树里则为 ∞ | 不是 `rm` 返回的时刻（D8（核心索引结构） 走意图分批），也不是空间变得可再分配的时刻（D16（发布语义） 新规则 2） |
| `S.txg` | **S 捕获的最后一个已发布 txg** | 不是「创建操作所在的 txg」 |

⚠️ **搬迁不改 `birth`（2026-09-06 收口）**：后台整理把一个单元从一个落点搬到另一个落点，
**不是「发布一个新版本」**——逻辑内容一个字节没变，只是物理位置换了。
按 D5（快照 / 空间记账机制） 给 `birth(b)` 的定义句「块被**发布**的那个 checkpoint 号」，搬迁不产生新的发布事件
⇒ `birth` 原样跟着单元走。
**依据**：E94（搬共享落点的触碰面） 实测——若搬迁重新指派 `birth`，
「重指派的违例数恰等于被快照引用的搬动数」，即每搬一个被快照引用的单元就错一次；
`birth` 不改则违例恒 0。
⇒ 这一句是 D26（后台整理与放置回收） 未定项 5 点名要「在 D5（快照 / 空间记账机制） 那边同步记」的两笔之一，
2026-09-03 起欠着，2026-09-06 补上。**另一笔（deadlist 条目装什么）仍欠**，
它随位置权威一起定，而位置权威已由 D19（块指针的结构与宽度预算） 已定项 5 取混合
⇒ deadlist 条目要按**中央映射的 key**（逻辑身份）记，不按落点记——
按落点记会让每一次搬迁都要逐条重写 deadlist（E94（搬共享落点的触碰面） 的形态结论）。
**这一句仍是推论，没有定案，也没有实测**。

### 二·三 D5 的销毁算法（同文件 `:152-164`）


```
判定(ptr):
    birth = ptr.birth              // 指针内联字段，零次额外 I/O
    p     = head.prev_snap_txg     // 活头头部一个标量，常驻内存
    if birth > p:  立即释放 → 进 defer 队列（不是直接进空闲表，见 D16 新规则 2）
    else:          追加进 head.deadlist
```

**归约证明**：设删除发生在 checkpoint `d`，P 为此刻最新的快照。
(⇐) 若 `birth ≤ P.txg`：P 已发布 ⇒ `P.txg < d = death` ⇒ `birth ≤ P.txg < death`，∃S 引用它。
(⇒) 若 ∃S：`birth ≤ S.txg < d`，则 S 在删除时已存在 ⇒ `S.txg ≤ P.txg` ⇒ `birth ≤ P.txg`。∎

#### 2. deadlist 与 birth 怎么跟着改（D26（后台整理与放置回收）未定项 5 直接问的那两样）

- **deadlist**：条目以落点为键 ⇒ ptr_rewrite 下每批要逐条重写 11–36 条（随 K 与批次构成走）；
  central_map 下条目以逻辑身份为键 ⇒ **恒零重写**。
- **birth**：**不改**。负臂实测：重指派 birth 后，违例数在 60 个格上
  **恰等于**「被 ≥1 个快照树引用且被搬动」的版本数（中位 50–64 / 64）——
  重指派把 `birth(b) ≤ S.txg < death(b)` 的左端推过全部快照 txg，
  被共享的那部分逐个被判成「无人引用」。birth 是逻辑版本的属性，不是落点的。

### 二·七 E74（分配记录的条目数与整理开销）的轴 ②（`.claude/kb/experiments/74-分配记录的条目数与整理开销.md:52-62`）

固定 N = 4096 个落点，容量从 1 TiB 涨到 256 TiB（**256 倍**）：

| 容量 | 连续落点重写节点数 | 打散落点重写节点数 |
|---|---|---|
| 1 TiB | 13 | 4143 |
| 16 TiB | **13** | 4823 |
| 256 TiB | **19** | 8208 |

⇒ 连续那一侧容量涨 256 倍、重写节点数从 13 涨到 19，**涨的 6 个全部来自树高 3 → 4**
⇒ **没有任何一项跟着容量线性走，判据 2 成立**，整理路径里没有全扫。

#### ⚠️ 但 COW 放大差 370 倍，分水岭是落点在 key 空间里聚不聚

**COW 重写的是整个 16 KiB 节点，不是那 20 字节。** 4096 个落点、16 TiB：


| 落点分布 | 写入字节 | 相对「只写那 20 字节」 |
|---|---|---|
| **连续** | 212 992 | **2.6 倍** |
| **打散** | 79 020 032 | **964 倍** |

⇒ **370 倍的差距全在「聚不聚」这一维上**，而它由 key 的选法决定：
D3（空间分配） 已定项 3 定的 key 是**（设备身份 + 设备内偏移）**
⇒ **物理相邻的落点在 key 空间里也相邻**，而整理搬的正是物理相邻的一批
⇒ **那条 key 的选法把整理放在了 2.6 倍那一端，不是 964 倍那一端。**

⚠️ **这条不是 E74（分配记录的条目数与整理开销） 替整理策略背书**：它说的是**载体在好情形下不拦路**，
而整理策略本身（D26（后台整理与放置回收） 六个分项全开着）**没有被测**。
搬一批 key 空间上分散的落点仍然是 964 倍，那种批次存不存在由策略决定。

## 三、要被攻击的定案草案（主 agent 2026-09-07 起草，一条都还没定）

### 条款 1：搬迁不改 `birth`

搬迁把一个单元从一个落点搬到另一个落点，`birth` 原样跟着单元走。
这一条 2026-09-06 已经收口在 D5（快照 / 空间记账机制）（见二·二），
D26（后台整理与放置回收）未定项 5 这一格只做转述与指向，不是新结论。

### 条款 2：deadlist 条目按「版本身份」记，不按落点记

deadlist 一条条目 = 逻辑身份五元组（D18 已定项 3，33 字节）+ 诞生代号（8 字节）= 41 字节，
可另带一个位置**提示**（14 字节，与 D19 已定项 4 同宽，**非权威**）。
⇒ 搬迁对 deadlist 的触碰面**恒 0**（E94 实测 central_map 臂 deadlist 恒零重写；
ptr 臂每批逐条重写 11–36 条）。
销毁快照时按 `birth` 过滤只读条目自身、零额外 I/O；要拿落点去释放时经中央映射
（D19 已定项 5 硬规则 1「释放一律经映射，不经提示」）。
⚠️ deadlist 住哪棵树、树 ID 怎么挂到活头 / 快照、第一个事务建不建空的——**不在本条款内**，
那是 C145（deadlist 在盘上没有落点）。

### 条款 3：中央映射的 key 必须含诞生代号（33 → 41），本项的字节判定从「否」翻成「是」

**理由**：deadlist 与快照树引用的是**旧版本**，而 D19 已定项 5 定「中央映射是解引用与
释放判定的**唯一入口**」。key 只有五元组时，映射只指得到**现行版本**
⇒ 被快照引用的旧版本既解不出落点、也释放不掉。
E96（混合架构的一致性）的模型本来就是这么建的——见二·六源码：
`map_slot: BTreeMap<u32 /*ver*/, u32 /*slot*/>`，而 `Version { key, birth }`，
`DlEntry { ver, hint }`；也就是说 **E96 全程按「(五元组, 诞生代号) → 落点」建模**，
而 D19 已定项 5 的欠账 ① 与 `first-txn-layout.md` 三·二节写的是「key 取逻辑身份五元组 33」。
**两处对不上，而 E96 正是 D19 已定项 5 那两条硬规则的唯一依据。**
⇒ 若条款 3 成立：`first-txn-layout.md` 三·二那一行 33 → 41，
D26 未定项 5 的「改第一个事务的字节」要从「否」翻成「是」。

### 条款 4：搬一批 N 个落点对分配记录树的改写量，以及它的前提

改写量 = `⌈N/扇出⌉ 个叶 + 每层各一个内部节点`，**不随盘容量走**
（E74 轴 ②：N = 4096、容量涨 256 倍，连续落点 13 → 19 个节点，涨的 6 个全部来自树高）。

⇒ 条款 4 要补一句：**整理的目的地必须取一个连续区间**（分配器政策，不是格式位）。

| 本地（找反例） | 构造一个具体的操作序列，让四条条款里任意一条产生错误结果或不可判定的状态 |
| Sonnet（正推 + 核引文） | 逐条核这四条条款引的每一句在仓里是不是那么写的，以及结论是不是从那些句子推得出来 |
| Opus（反推） | 假设每一条条款是**错的**，本该看到什么？特别是条款 3——有没有一种读法让 33 字节的 key 也够用 |
