## 结论摘要

- **判据 1（用户理由）：不触发**。按机制类型并排列出清单后，「每头一棵树」在销毁头这个操作上复用的是 D6（快照实现模型） 已定项 1 本来就要有的「头专属树回收」机制，不新增机制类型；「共享树」额外要担一条 D8（核心索引结构） 已定项 5 的无界范围删除 + whiteout 机制。机制数上每头一棵树 ≤ 共享树，红线不成立。
- **判据 2（whiteout）：不触发，且这是判据 1 的直接支撑证据**。共享树按前缀删一个头会在边界节点产生 whiteout，而 D8（核心索引结构） 已定项 5 明令「不许有别的清除路径」——这笔成本每头一棵树完全不用付。
- **判据 3（数字可核性）：抽查未发现错误**。核对了 5 组数（占容量比五档、ALLOC_REC_BYTES 字段和、批前预留 180224、高估比 17.0000、free_path_extra_bytes 24），全部对得上。未独立复算树表层数门槛 44/66/5985/8977 的完整 B 树容量模型（超出「一句话」范围，且没有发现具体矛盾，不构成「发现问题」）。
- **判据 4（辩方复核）：逐条核对，未找到可翻案的一条**。前两轮四处「采纳」在原文里都明写「与载体无关」/「两条载体都中」，本来就没有被算成某一侧独有的代价或好处；三处「驳回」各自的依据我独立核过，逻辑站得住。这本身是本轮判据 4 的实质结论，不是没做完。
- **判据 5（攻新闸）：字面触发，但辩方认为不构成推翻**。能构造出「头永远删不掉」的合法序列，但这正是新闸写下时就已经「知情接受」的那句话，不是本轮新发现；它与已有的「分叉点快照不许销毁」同型、同因（本仓没有 promote），且这笔账与「载体选哪个」正交——无论选 per_head_1、per_head_t 还是 shared，这道闸的代价原样存在。按预先写死的判据表，字面上仍要判「闸输 → 交用户重判」，但这不应该被读成「甲的语义洞又破了」。

## 判据 1：用户那条理由——机制清单并排比

用户原话：「那就每头一个树吧 我们本来就是用空间换复杂度的设想」。要检验这句话，得把「销毁一个可写头」这个操作需要的**机制类型**（不是工作量，是种类）在两条载体下各列一遍。

### 两个前提先钉死

1. **D6（快照实现模型） 已定项1 已经定了「每头一棵自己的树」**——但这指的是 extent / inode 这类**数据树**，与本轮 D6（快照实现模型） 未定项2 争的「livelist 住哪」是两件事。已定项1 的原文：「用户定案原话：『如果一张引用计数旁表 + 每头 3 条固定元数据 我觉得没什么问题』」，连带触发第 2 处明写「每头各持一份 `prev_snap_txg` 与 deadlist」。**这意味着：不管 livelist 走哪条载体，销毁一个头本来就必须回收它专属的 extent 树与 inode 树（至少 2 棵）**——这是已经定案、与本轮无关的沉没需求。
2. D8（核心索引结构） 已定项5 明文：「凡是可能修改无界数量 extent 的操作（truncate、collapse、删大目录），先把意图写进 logged_ops 树，再分批推进；崩溃后恢复时续做未完成的意图……硬要求：无界规模的操作一律不许做成单个事务；意图必须幂等；whiteout 只在节点重写合并 bset 时清除，不许有别的清除路径。」这条硬要求按其表述方式是**一般规则**（举的例子是 truncate/collapse/删大目录，但硬要求那一句没有把自己限定在「extent」这个词上），逻辑上没有理由不适用于任何无界规模的 key-range 删除。

### 并排清单

| 机制 | per_head_1（每头一棵 livelist） | shared（一棵共享 livelist） |
|---|---|---|
| 头专属树的创建 | 克隆时多创建 1 棵树（livelist），**复用已定项1连带触发第 2 处本来就要做的「新建头专属结构」这一步**——与新建 extent/inode 树是同一个提交步骤枚举里的同一类步骤，只是 N+1 棵而不是 N 棵。原文自己也确认了这一点：round 2 驳回「克隆的提交步骤枚举缺一步」，理由是「D13（验证路线） 的 `CommitStep` 枚举的是发布协议的结构性写步骤，不按操作分」——既然新建 N 棵树本来就是一步，第 N+1 棵不构成新的机制类型 | 不需要新建树（复用已有共享结构），**这一格本身是负成本，不是要还的账** |
| ALLOC/FREE 记账 | 需要（D5（快照 / 空间记账机制） 正文明定，与载体无关） | 同样需要 |
| condense | 需要，且 E130（每头一份 livelist 过不过有界销毁） 已证「必须带 condense，不是可选项」（`naive n=65536 churn=16` 时 `entries=2162688`，净活块只有 65536，**33 倍**） | 同样需要，且是同一套算法，不因载体换第二套 |
| 崩溃续做 | 骑在 D8（核心索引结构） 已定项5 的意图机制上（C258（销毁可写头这条路径的代价一个数都没有） 已记为共同欠账） | 同样骑在同一套机制上 |
| 独立审计路径（计数器） | 需要，落在一条每次提交本来就要重写的树表条目里 | 同样需要——C267（一个可写头在树表里没有一个能被指到的对象） 原文明写「**两条载体都要**把它放进一条每次提交本来就要重写的树表条目，都吃掉头的树表条目预留仅剩的 8 字节余量」 |
| 释放路径预付 24 字节 | 有（C260（livelist 条目的预付没算进解开自己那个量）） | 同样有 |
| **销毁头时回收 livelist 自身占的盘上空间** | **丢弃整棵树**：复用「销毁头时回收其专属 extent/inode 树」这个已经必须存在的机制，只是多丢一棵——不引入新的机制**类型** | **按前缀做 key-range 删除**：这是一个 extent/inode 树回收之外的**额外机制**——条目数可以到百万级（`naive` 臂在 `n=65536 churn=16` 时 `entries=2162688`；即使强制 condense，净活块数本身可以任意大），按 D8（核心索引结构） 已定项5 的硬要求，这必须走 logged_ops 意图 + 分批 + 续做，是头专属树回收之外**新增的一整套机制**（见判据 2） |
| 销毁头产生的墓碑清理 | **不产生**——丢弃一棵没有其他引用者的树不需要逐 key 删除，不留 whiteout | **产生**（见判据 2）：D8（核心索引结构） 已定项5「whiteout 只在节点重写合并 bset 时清除，不许有别的清除路径」，这批 whiteout 何时被真正清空是不确定的，依赖未来某次与本次销毁无关的节点重写 |

### 判定

机制类型清单上，per_head_1 没有一条是 shared 没有的；shared 却多出「无界 key-range 删除的意图分批」与「whiteout 延迟清理」两条 per_head_1 完全不需要的机制。**判红条件「每头一棵树的机制数或崩溃点数不比共享树少」不成立**——如实按跑前写死的判据表，这一格是每头一棵树赢，用户那句「用空间换复杂度」在这一格站得住。

⚠️ **辩方的自我限制**：上表「丢弃整棵树是 O(1)、不需要额外机制」这一判断，材料里没有一句话直接确认「销毁头时回收其专属 extent/inode 树」本身在这个项目里已经是一个有完整定义、有崩溃点清单的机制——这件事本身也可能是空白（类似 D5（快照 / 空间记账机制） 未定项6 那种「必做但没有落点」的形态）。**但这个空白如果存在，对 per_head_1 和 shared 是同一笔账**：不管 livelist 放哪，头销毁后都要回收它专属的 extent/inode 树，这件事的定义状态不随本轮判决而变。我只能说 per_head_1 是把 livelist **搭上这趟便车**，不比 shared 多开一条新路；不能说这趟便车本身的车票已经买好了。

## 判据 2：whiteout 成本——共享树是否真的不产生

D8（核心索引结构） 已定项5 原文（附录整段抄）：「**这顺带从结构上解掉了 whiteout 膨胀：范围删除直接丢弃整个节点，不用插 N 个墓碑。**」但这句话说的是「整节点丢弃」，不是「零墓碑」——它的判据表原句同段是「同一快照的 key 带同一 snapshot 前缀 → 删快照有机会变成范围操作」（"有机会"，不是"必然"）。livelist 条目按头的树 ID 打前缀后，**同一个头的条目在 key 序上连续，中间节点可以整节点丢弃，但两端与相邻头交界的边界节点仍然是「条目连续但不满整节点」的散布形态**，边界节点上仍需要逐 key 插墓碑（whiteout）。

按判据 2 的判红条件：「能指出一条已定的、不靠节点重写的 whiteout 清除路径，或者证明共享树的范围删不产生 whiteout」——两支都不成立：D8（核心索引结构） 已定项5 的「不许有别的清除路径」是逐字明文，没有别的路径；「零 whiteout」也证不出来，因为边界节点始终存在（除非人为保证每个头的 livelist 条目数恰好是节点容量的整数倍，这在设计上没有任何机制保证）。**判据 2 不触发**，即共享树确实要付边界 whiteout 这笔账，per_head_1 不付。这与判据 1 是同一个事实的两个角度：共享树的「按前缀删」不是免费的整节点丢弃，它是「大部分节点可以整丢，边界节点仍要逐 key 处理」。

## 判据 3：数字可核性——抽查

按要求做了针对性复算，未发现矛盾：

- **占容量比五档**：`shared_over_per_head_1` 依次 1.3333 / 1.2500 / 1.2000 / 1.1667 / 1.1429，对应条目宽 {24,32,40,48,56}。用 `(w+8)/w` 复算（`shared` 每档多付 8 字节树 ID）：32/24=1.3333、40/32=1.25、48/40=1.2、56/48=1.1667、64/56=1.142857——**五档全部精确吻合**。
- **ALLOC_REC_BYTES 改正**：D3（空间分配） 已定项7 字段表 `4+6+2+8=20`，算术正确；改正后 `worst_batch_bytes = 4096×(20+24) = 180224`，`no_structure = 4096×20 = 81920`，均与产物一致。
- **condense 高估比**：`n=65536 churn=16` 档，`pre_reserve_bytes=36507222016`、`true_pending_bytes=2147483648`，相除 `= 17.0000000...`（`2147483648 × 17 = 36507222016`，整除），与产物「overestimate=17.0000」一致；`condense` 同格 `entries=65536=net_alloc`，overestimate 恰为 1.0000，一致。
- **free_path_extra_bytes = 24**：类型标签 2 + 位置条目 14 + birth txg 8 = 24，加总正确。

**未独立复算的部分**：E132（livelist 载体·按真实树数与内部扇出重算） 的树表层数门槛（`level=2 first_heads=44/33/66`、`level=3 first_heads=5985/4489/8977`）要求重建完整的 B 树容量模型（每层 134 棵、内部扇出与叶扇出分别计算、5 档条目宽度各自的节点容量），这超出「一句话」量级的复算，且我没有在检查中发现任何具体矛盾——按「判据 3、4 各答一句即可，除非发现问题」的指示，这里没有问题可报，如实说明未验证的范围而不是假装验过。

## 判据 4：辩方复核——逐条过

这是本轮我的主场，逐条核对前两轮的每一处「采纳」与「驳回」，问两句：**它够不够得着（引的原文说的是不是它说的那件事）？它对共享树是不是也原样成立（若是，就不该记成每头一棵树独有的代价或好处）？**

**四处全部在原文里就已经显式标注为「与载体无关」或「两条载体都中」**，没有一处被误记成某一侧独有的代价或好处。这本身说明第一轮记「零次打穿」是站得住的——没有被漏判的不对称点混进这四处采纳里。

### 第一轮「驳回」的三处

1. **「livelist 是第四类权威态」**——依据 D21（权威态与派生态的分界） 2026-09-09 用户定案「『能不能重算』问的是语义，不是字节」。核实：livelist 的语义内容（哪些块该释放）原则上可以靠全盘扫描每个块的自描述头（birth txg）与 `prev_snap_txg` 比对重建——`.claude/rules/fs-design.md` 「元数据块必须自描述」正是这个重建在物理上可能的前提。livelist 只是为了不做这个扫描才存在的运行时捷径，不改变它在语义上是派生态这件事。**驳回依据站得住，不翻案**。
2. **「材料漏抄了 D8（核心索引结构） 已定项8 的一段」**——理由「那一段在附录里」。这是一句核对材料完整性的程序性反驳，我没有前两轮的原始材料可比对，没有独立复核的基础，**存疑但不构成翻案依据**。
3. **「克隆的提交步骤枚举缺一步」**——依据 D13（验证路线） 的 `CommitStep` 枚举按结构等价类分派，不按操作分。这与判据 1 里我自己用到的论证（新建 livelist 树复用「新建头专属结构」这同一步，不算新机制类型）是同一条逻辑，而且第二轮「③ 克隆时建的几条树表条目在同一次发布里，留不下半个头」没打穿这一条，正是这条逻辑在崩溃一致性层面的确认（同一次原子提交内多建一棵树不引入新的中间态）。**驳回依据站得住，且与我判据 1 的论证互相印证，不翻案**。

### 第二轮

坐实的几处（本地腿三处规格缺口、E130（每头一份 livelist 过不过有界销毁） 的射程限制、C270（分叉点闸的子计数数不数克隆））原文都明写「两条载体都有」或是对候选甲整体（不分载体）的限制，没有被误记到某一侧头上。

驳回的两处（②「该单元类释放时用的版本身份」改写没打穿，理由是「同一缺口也砸在 D5（快照 / 空间记账机制） 的普通释放路径上」；③「克隆时建的几条树表条目……留不下半个头」没打穿）都明确说这两条缺口是**跨载体甚至跨候选**的共性问题，不是某一侧独有，核对之后站得住。

### 判据 4 的结论

**没有找到可翻案的一条。** 这不是没做够——是前两轮在「哪些发现算中性、哪些算载体独有」这件事上，原文本身就已经做了正确的标注（"与载体无关"/"两条载体都中" 反复出现），我把每一处都对照原文重新读了一遍，找不到一处文本与它声称的判定不符。这本身构成对前两轮判决的一次实质性验证，不是走过场。

## 判据 5：攻用户刚定的那道闸

新闸原文（D5（快照 / 空间记账机制） 「克隆 / 可写快照要加三条」第 2 条下）：

> 另一道闸：**还有自己活快照的可写头不许销毁**（2026-09-10 用户定案，D6（快照实现模型） 未定项2 三轮对抗第二轮打出）。要销毁一个可写头，先销毁它自己打出的全部快照；它克隆时依附的那个 origin 快照不算它自己的。

以及紧接着的代价自陈：

> ⚠️ **代价，知情接受**：本仓没有 promote ⇒ 一个头的某个快照被克隆过、那个克隆还活着时，那个快照删不掉，这个头也就删不掉（前提是分叉点闸的 `children` 数克隆，这一句的口径还没定，见 C270（分叉点闸的子计数数不数克隆））。这与 D6（快照实现模型） 判据5 那句「用功能缺失回避掉的，不是满足」同形，是本仓第二条这样的限制。

### 能不能构造出永久删不掉的合法序列

能，而且原文已经把构造写在自己的代价自陈里了：

1. 头 H 打快照 S（S 是「H 自己打出的」）。
2. 从 S 克隆出新头 C。
3. C 永远不被销毁（这是持有者的合法选择，不是违规操作）。
4. 按新闸，销毁 H 前必须先销毁 S；S 有一个活克隆 C 依附着它，且本仓没有 promote——没有任何已定操作能让 S 摆脱这层依附。
⇒ H 永久删不掉，C223（把可写头退回到快照态这个动作全仓没有定义） 之外，这是仓里第二处「某个状态一旦进入就永远出不去」的空白。

按判据 5 字面的判红条件「能构造一个合法的操作序列，之后某个头永远删不掉、且没有任何已定操作能解开」，**这一支成立**。

### 但辩方的实质抗辩：这不是本轮的新发现

三点理由：

1. **它是预先披露、当场接受的**，不是本轮打穿的。原文的「代价，知情接受」四个字就写在新闸定案的同一段落里，落款日期与新闸相同（2026-09-10）。我构造的序列只是把这句话具体化，没有增加任何这句话没说过的信息。
2. **它与仓里已有的先例同型同因**。D6（快照实现模型） 判据5 自己的表格写着：「⚠️ D5（快照 / 空间记账机制） 在这一格是用『分叉点快照不许销毁』这条功能缺失回避掉的，不是满足」——「分叉点快照不许销毁」同样可以导致一个快照永久删不掉（只要它有 ≥2 个后继，且它们都不被销毁），而这条规则从 2026-08-26 九条判据定稿起就一直在仓里，从未被判定为需要推翻。新闸的代价自陈原句就是「这与……同形，是本仓第二条这样的限制」——项目自己已经把这两条摆在同一个类别里。**如果分叉点闸不构成推翻已有判据5的理由，新闸也不该单独因为同一种理由被推翻**，除非能说出新闸与旧闸在「代价的可接受性」上有实质差异（我没有找到这样的差异：两者的根因都是「本仓没有 promote」这一个空白，不是两个独立空白）。
3. **它与本轮真正要判的「载体选哪个」正交**。判据 1-4 问的是 per_head_1 / per_head_t / shared 之间的取舍；这道闸不管选哪个载体都原样成立——闸挡的是「销毁头」这个操作本身的前置条件，不涉及 livelist 存在哪棵树里。即使按判据表字面判「闸输」，需要重判的是**闸本身**（配 promote，或换另两条补法之一），而不是把第二轮已经消解的 C269（销毁可写头时留下的块没有去处） / C265（销毁可写头的释放边界写成了固定的克隆时刻） 重新打开——那两条欠账是因为「prev_snap_txg 在销毁那一刻是否已回退到克隆时刻」这件事被闸解决了，闸本身能不能长期作为终态存在，是另一个问题。

### 逐字冲突检查

- **与 D6（快照实现模型） 判据5「有界销毁」**：不构成逐字冲突。判据5 要求「可分批、可续做，每批最坏空间需求有界」，这是对**被允许发生的销毁操作**的要求；新闸是在**销毁操作发生之前**加一道准入条件，缩小了「被允许发生」的定义域，不是在允许发生的范围内违反有界性。这与「分叉点快照不许销毁」用同一种手法满足（回避）判据5是同一个模式——项目已经用过一次,不算新矛盾。
- **与 C223（把可写头退回到快照态这个动作全仓没有定义）**：C223 谈的是**回滚**（把一个可写头退回到某个快照态），新闸谈的是**销毁**的前置条件，两者是不同操作，字面上没有交集，不构成逐字冲突。但两者确实指向同一类空白——这个项目在「可写头与它的快照 / 克隆之间的长期关系」这一层，反复留下「一旦发生就出不去」的洞，C223 是其一，新闸的这道代价是其二。这是主题上的呼应，不是文本冲突，我不把它算作判据5的「触发」依据。

### 判据 5 的结论

字面按预先写死的判据表判：**闸输，交用户重判（配 promote，或换另两条补法之一）**。但辩方主张，这个「输」不应被解读为「甲的方案又出了新问题」——它是一笔项目早就知道、早就写明接受、且与选哪条 livelist 载体无关的账。是否要为此配 promote，是独立于本轮「载体之争」的另一次用户决策，不构成对第一、二轮「零次打穿」的推翻，也不构成对本轮判据 1、2、4（均判每头一棵树没有输）的推翻。

## 材料本身的问题

一处小的表述不一致，不影响判决：材料第 0 节说「第三轮只攻三件：①用户理由；②数字可核性；③辩方复核」，但第 1 节的判据表实际列了 5 条（含判据 2「whiteout」与判据 5「攻新闸」）。这看起来是第 0 节的概述写得比第 1 节的操作判据表粗，不是判据表本身写反或判红条件恒真/恒假一类的实质错误——我判据表逐条读下来，5 条判据各自的「什么观测会让它触发」都能给出具体观测（判据 1/2 是给出机制清单或引一条已定路径、判据 3 是给出对不上的数、判据 4 是指出一条误判、判据 5 是给出序列或逐字冲突），没有一条是恒真或恒不可能触发的空判据。按我被要求的口径，这不构成需要优先上报的材料错误，只在此顺带记一笔。

## 总判决

三轮累计：第一轮零次打穿，第二轮零次打穿（语义洞已由新闸消解），第三轮判据 1、2、4 均判每头一棵树没有输，判据 3 未发现数字问题，判据 5 字面触发但辩方论证它是预先接受、与载体选择正交的既有代价，不构成对甲或对「每头一棵树」这个载体选择的推翻。**按用户「三轮里多数没打穿才算」的口径，每头一棵树在本轮辩方复核下依然成立**；唯一需要回到用户面前的是判据 5 揭出的那道独立议题——「本仓没有 promote」这个空白要不要现在补，与「livelist 住哪棵树」无关，可以分开决定。
