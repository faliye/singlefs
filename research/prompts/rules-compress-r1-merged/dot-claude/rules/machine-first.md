# 机器优先：实现上 AI 友好，审核上人类友好

实现面与审核面是两条轴，各自优化，不在中间折中。这个项目不默认照搬软件工程里的通行准则：每一条照「遇到一条通行准则，走这个流程」重新过判据，过不了的不要。

## 两条轴各自优化什么

| | **实现面：AI 友好** | **审核面：人类友好** |
|---|---|---|
| 谁在用 | 模型写、模型改、机器验 | 人做判断、人担责任 |
| 优化什么 | 可机检、可穷举、可强制进入、可回退 | 可判断、可信、看得出取舍 |
| 具体形态 | 显式穷举分支胜过聪明的通用路径；类型让非法状态无法表示；不变量写成断言；宁可生成重复也不手工维护 | 决策带依据；门禁失败带下一步；数字带口径；未验证的显式标出 |
| 写在哪 | 「遇到一条通行准则，走这个流程」「放宽的（人脑带宽的产物）」「留下的（与谁读代码无关）」、`.claude/singlefs-ai-sop/rules/code-discipline.md`、`.claude/rules/code-discipline-by-review.md`、`.claude/singlefs-ai-sop/rules/kb-discipline.md` 与项目自己的设计纪律 | `.claude/singlefs-ai-sop/rules/sop-first.md`「每一条拒绝都必须给出下一步」、`.claude/singlefs-ai-sop/rules/design-doc-discipline.md`、「设计文档：长度相称，该说服的就说服」「提议不因为来自谁而免检」、决策记录的依据要求 |

## AI 友好 ≠ 不可读

对模型友好的方向是更显式，不是更晦涩。放宽的只有为了让人脑装得下而做的压缩（「一个机制包打天下」「概念越少越好」这类设计统一性要求），不放宽把含义写明白。

命名、函数职责单一、路径数有限、约定一致四项不在放宽之列，按可验证性与信息量守：

| 项 | 守到什么程度 |
|---|---|
| 命名 | 语义写进名字，不省 |
| 函数职责单一 | 一个函数做一件能单独验证的事，长度按这个定，不按屏幕高度定 |
| 路径数有限 | 说得出全覆盖这段代码的控制流要多少个用例，而且有限；量的是路径数，不是嵌套层数；它是能验的必要条件，不是充分条件 |
| 约定一致 | 约定保持一致；它和「设计统一性」是两回事 |

落到代码上的写法在 `.claude/singlefs-ai-sop/rules/code-discipline.md` 与 `.claude/rules/code-discipline-by-review.md`。

## 推论：人的注意力该花在哪

人的注意力不花在读代码上，读代码交给模型；花在机器判不了的四件事上：

1. 这个测试测的是不是对的东西
2. 这条不变量本身对不对
3. 这个决策的依据成不成立
4. 要不要接受这个取舍

门禁的输出、kb 的结论、决策记录、失败信息都为人优化，让人不通读实现就判得了这四件；代码难读可以接受，这四样判断不了不行。

## 两条轴的分界线

> **Gate proves evidence requirements, not semantic correctness.**

机器证明证据够不够，人判断语义对不对（`.claude/rules/show-me-test-by-review.md`「门禁能证明什么，不能证明什么」）。

## 遇到一条通行准则，走这个流程

对现成「最佳实践」的默认态度是存疑：每一条的理由重新查一遍，不因为「大家都这么做」就接着做。

1. **问它当初要解决什么问题。** 说不出来就直接放弃。
2. **问那个问题今天还在不在。** 当初解决「人记不住」「人读不过来」「review 忙不过来」的，多半已经不在了。
3. **问它有没有跟人无关的第二个理由**（例子见「留下的（与谁读代码无关）」），有就留下。
4. **改过的理由要能落成门禁**，落不成的降为建议，不写成规矩。

代码层面审过的结果与写法在 `.claude/rules/code-discipline-by-review.md`「逐条审过的流行做法」；设计与流程层面的在「放宽的（人脑带宽的产物）」「留下的（与谁读代码无关）」。

## 判据

> **这条规则是让代码更容易被机械验证，还是只让它更容易被人眼扫过？**

- 只是让人看着舒服：可以放弃。
- 让验证更容易：留下。

## 这条姿态的前提，以及怎么推翻它

前提：上下文窗口已到 2×10⁵ ~ 10⁶ token 量级（200K / 500K / 1M 三档），指宣称的窗口上限，不是整个窗口里准确率都一样；长上下文中段记不牢从多大规模开始碍事，这个项目没量过。别家的数字不写进来。要反驳这套做法，靶子是这条前提，不是「放宽的」「留下的」两张表。

它撑起「PR 要小」「概念要少」「DRY 靠人同步」三条的放宽；撑不起「推理范围要有界」。前提失效时收回哪几条：观测到哪一行的现象，当场收回同一行的放宽。

| 观测到什么 | 收回什么 |
|---|---|
| 在这个项目的实际规模上，模型漏掉了一条已经在上下文里的约束 | 收回「PR 要小」的放宽，重新按装得下的粒度切 |
| 生成出来的重复代码和生成器对不上 | 收回「DRY」的放宽，回到不许重复 |

## 放宽的（人脑带宽的产物）

| 旧准则 | 处置 |
|---|---|
| 设计要统一、概念要少 | **放宽** |
| PR 要小 | **放宽**；能二分、能回退照保 |

放宽的是「为了让人装得下而做的压缩」，不是「把含义写明白」（「AI 友好 ≠ 不可读」）。

## 留下的（与谁读代码无关）

- 不变量
- 对外格式与协议兼容
- 测试可复现
- 故障域隔离
- 可二分、可回退
- 模块边界要有明确契约
- 推理范围要有界

文档纪律不在放宽之列：正文只写现状、历史的落点照 `.claude/singlefs-ai-sop/rules/design-doc-discipline.md`「1. 正文只写当前现状，历史一律放到文末」、`.claude/singlefs-ai-sop/rules/kb-discipline.md`「8. 正文只写现状，历史放文末的「历史版本」」与 `.claude/singlefs-ai-sop/rules/rules-discipline.md`，决策记录进 kb。

## 设计文档：长度相称，该说服的就说服

管 `.claude/singlefs-ai-sop/rules/design-doc-discipline.md` 管的那些文档（README、设计说明、`records/`）。

- 长度：判据与尺子在 `.claude/rules/writing-discipline-by-review.md`「长度要配得上改动的重量」。
- 设计文档要回答为什么该这么做、怎么上手；为这两件事写的铺垫、例子、摊开讲的取舍不算废话。判据：删掉这一段，读的人还同不同意、还上不上得了手？都还行就删，不行就留。

## 提议不因为来自谁而免检

用户提的方案和别处来的方案过同一道闸（`.claude/rules/show-me-test-by-review.md`「不按来源分类，只看证据」管提交，这一条管提议）。警告记录的格式在 `.claude/singlefs-ai-sop/rules/pushback-discipline.md`「警告写在哪：`.claude/warnings/<日期>.md`」。

### 对不上就当场说

提议和实测数据、或已核实的事实对不上时，能多早说就多早说，三样都说清：

| 说什么 | 不算说清 |
|---|---|
| 对不上的是哪一条：哪个实验、哪个数、哪条决策，带出处 | 「我觉得这样不太好」 |
| 按提议做会出什么问题，什么现象说明它出现了 | 「可能有风险」 |
| 有没有能同时满足两边的第三条路，没有就说没有 | 不说，直接照做 |

报的是哪个观测和它对不上，不是「你错了」；对方给了理由就去核（`.claude/rules/evidence-discipline.md`「陈述外部状态之前，现查一次」：别人提出的事实性更正同样要核）。

### 做完了才发现对不上，照样要说

做过的工作不是留着它的理由：做到一半发现做不到、做完了才发现前提不成立、当初调查得不够就动了手，说出来，该撤就整个撤回。「撤回要花多少」是报给对方的一条信息，不写进技术依据。

这一条只管已经做出来的工作：会静默毁掉未提交改动的命令（`git checkout`、`rm -rf` 这些）与对外的永久承诺（磁盘格式、协议、公开 API）不随手做（`.claude/singlefs-ai-sop/rules/command-safety.md`、「留下的（与谁读代码无关）」）。

### 分清「我核过」和「我印象里」

说清是「我核过，对不上」还是「我记得好像对不上」（`.claude/rules/evidence-discipline.md`「陈述外部状态之前，现查一次」：说不出靠哪条命令知道的，就写成推测）；核不动的说核不动，不把没查过的疑虑说成事实。

### 对方坚持，就照做，但要留下记录

反对过一次、对方明确重申，就是对方的决定：照做，不再劝，也不消极执行。后来跑出来的数据推翻了当初的判断，再报一次（`.claude/rules/evidence-discipline.md`）。
