R1: No counterexample found. For code 1 units, the write order (4-byte instance id + 6-byte transaction number) is unique per unit due to H2 and H3. Each instance id is unique and never reused, and each transaction number is unique within an instance for data units. Thus, no two different published or alive code 1 units can share the same key as the write order ensures uniqueness.

R2: During checkpoint 5, instance id 3, tree X. Write code 2 unit A with birth sequence 0. A failure occurs during the checkpoint (not root slot failure per H6), causing the checkpoint to restart without advancing the checkpoint number. The birth sequence counter resets to 0 in memory. Write code 2 unit B with birth sequence 0. Both units share the same scope (tree X, checkpoint 5, instance 3) and birth sequence 0. This violates R2 as the counter was reset within the same scope.

R3: No counterexample found. After an instance switch (H4), adopted units have the old instance id while redone units have a new instance id. Since the instance id is part of the key for code 2/3 units and differs between old and new instances, the keys cannot match. For code 1 units, the write order includes the instance id, which also differs, ensuring key uniqueness.

R4: Deadlist entries for code 2 units store only 24 bytes (birth tree 8, birth checkpoint 8, instance id 4, birth sequence 4). The class tag is not included in the deadlist entry. When processing the deadlist, the system must read the unit header to obtain the class tag for the full K key. This requires an extra unit read, violating R4 which states no extra unit read is needed.

R5 part 1: No counterexample found. Under the open disposition (H7 adopted), each container is written once per checkpoint. For code 2 units, the key (tree id, level, lower bound, birth checkpoint) is unique because B-tree nodes have distinct key ranges. Lower bounds cannot be identical for different nodes in the same tree and level, ensuring uniqueness.

R5 part 2: During checkpoint 5, instance id 3, tree X. Fixed point iterates: write code 2 node A (birth sequence 0) then code 2 node B (birth sequence 1). Node B is current; node A is dead. Scan rebuild does not use birth sequence to determine current version (as per H9 rejecting sequence numbers for stale copies). Scan rebuild merges units with identical birth tree, checkpoint, and instance id but ignores birth sequence. It selects node A as current. The map entry points to node A (dead), while node B (current) is not referenced. Node B's space cannot be freed as it is not in the map, but node A's space is incorrectly retained due to the map entry. This violates the claim that no map entry points to a dead version whose space cannot be freed.
