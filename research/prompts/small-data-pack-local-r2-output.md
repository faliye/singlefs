1. Slot allocation uses a container header with a free list of slot offsets and sizes. If no slot fits, the object is placed in a new unit. Crash during rewrite: the new unit is written to a new location; if power loss occurs, the old unit remains valid as the new unit's checksum fails. Deletion marks the slot as free in the container header, requiring the container to be rewritten to a new unit; if crash occurs, the old unit remains. All data structures live in the container's header.

2. Append-only design: 100k files at 1KB each fit into ~3226 containers (32KB each, 31 slots/container), using ~103MB. Overwriting 30% adds 30k new slots, requiring ~968 new containers, totaling ~134MB. Today's design uses 100k * 32KB = 3.2GB always. Append-only becomes more expensive when (1+X) > S, where S is slots per container (31). At X>30%, (1+X) >31 → X>30%. Arithmetic: (100k*(1+X))/31 *32KB > 100k*32KB → 1+X>31 → X>30%.

3. Alternating small and large objects causes containers: large objects occupy most of a container, wasting space for small files. This is a placement policy issue, not the container mechanism. Fix by separating small and large objects into distinct container pools (e.g., small files in multi-slot containers, large files in dedicated units). Cost is minimal metadata to track object size and route to appropriate pools.
