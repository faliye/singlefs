**专题：C577 加屏障之后，Z3-A 乙的三形有没有变**

C577 给 `persist_the_root_then_rotate_the_system_configuration` 加了一道池屏障，做完才返回：
快照 `crates/singlefs-core/src/transaction.rs:1208-1216`：
```
    writer.perform_commit_step(CommitStep::WriteRootRecordForceUnitAccess {
        checkpoint_txg,
        root_slot,
    })?;
    writer.perform_commit_step(CommitStep::RotateSystemConfigurationSlots {
        journal_tail,
        journal_instance,
    })?;
    writer.perform_commit_step(CommitStep::Barrier)
```
（第 1216 行 `writer.perform_commit_step(CommitStep::Barrier)`）。

**结论：没变。** 理由是调用顺序——三形各自的入口函数在调用链最外层第一步就核 `caller_inputs_agreeing_with_the_disk`（或它的等价物），核不过直接返回错误，代码根本走不到会调用 `persist_the_root_then_rotate_the_system_configuration` 的那一步，加在这个函数末尾的屏障因此对三形的判定结果无影响：
- 卸载 → `unmount`（`mount.rs:1958`）→ `raise_the_floor_through`（`mount.rs:2236`），核发生在 `mount.rs:2267`：
  `    } = caller_inputs_agreeing_with_the_disk(parameters, devices, current).map_err(|refused| {`（`crates/singlefs-core/src/mount.rs:2267`，函数为 `raise_the_floor_through`，见 `mount.rs:2236`）。
- 回退 → `roll_back_by_a_forward_publish`（`mount.rs:4893`），核发生在 `mount.rs:4912`：同一行文本、同一份函数体最前段（已在上面 Z1Q 与本节判决引过的位置）。
- 会话发布 → `MountedSession::publish_user_change` 的文档注释已经把这个次序写死：
  `crates/singlefs-core/src/mounted_session.rs:230-234`：
  「交进来的盘表先与它逐项比（实审 A1b Q2、Q3），再读每块盘的两个系统配置槽核它「可见」（Z3-A 乙），再核本盘设备号与落后支（D18（块里携带什么信息） 已定项 11「挂着之后收盘表的每个入口……核三样」：「每次发布」按「每次用户改动」读）。三样在进循环之前核一次……循环里推的每一串抬 F 在它自己的第一个写之前再核一遍三样（`mount::push_one_floor_raise_within_the_admission_budget` 经 `caller_inputs_agreeing_with_the_disk`），所以这次调用发出的每一个写之前都核过。」（`crates/singlefs-core/src/mounted_session.rs:230-234`）

这三条调用链里，核盘表这一步都严格发生在任何写（包括最终会触发 C577 屏障的 `persist_the_root_then_rotate_the_system_configuration`）之前，且是无条件的早退（`?` 或 `map_err` 直接短路）。C577 的屏障只改变「核过之后走到写路径」这条分支里发布返回前多等一次 FLUSH，不改变「核不过就直接拒、一个字节不写」这条分支——而三形攻的正是后一条分支（盘表核不过）。因此加屏障之后，三形各自「在任何写之前拒、盘上逐字节不变」的结局不会变。

**这个结论的性质**：这是对调用图（谁在谁的前面被调用、`?` 是不是无条件早退）的静态读法，不是重新编译整个工作区跑一遍三条测试拿到的新鲜绿灯（主工作区在改、禁读；本条腿的写范围与效力都不包含在快照副本上跑 `cargo test`）。**什么现象会推翻它**：若发现三形中任一形的入口函数在核盘表**之后、写任何字节之前**先构造了 `PoolWriter` 并调用过 `persist_the_root_then_rotate_the_system_configuration`（或它内部的某个提交步骤）——即核与写之间插了一段会被屏障影响的路径——这个「没变」的结论就要改判；或者若快照之外、进入主工作区之后有人把核盘表这一步挪到了写循环内部（比如只在第一次失败后才核），也会使这个结论过期。

## 七、专题：第二轮 Y1 在 3024 段单故障扫上「没打中」是不是只读了代码

**结论：不是。** Y1（连同同一批测试覆盖的 Y7）用的是一个真实构造、真实注入、真实跑出原样日志的动态测试，不是读代码判断行为。证据链：

1. **测试装置是真实的故障注入层，不是静态分析**：`research/prompts/m2-closeout-code-r2-opus-output.md:118`：
   「用例 `opus_r2_y1_y7_single_fault_ordinal_sweep.rs`（批跑脚本 `batch_sweep.sh`，两件并行，原样日志 `logs/b1-1.log`、`logs/b1-2.log`，两件退出码都是 0）。起点同 Y2（txg 5，会话开着），只建一次，之后每段从内存里那一份拷。五个入口：会话覆盖写、正常卸载、准入抬 F 到上限、管理员回退到 (1, 4)、崩了再可写挂载。每段只注入一次：整池第 n 次读、写或屏障报块设备错（自写的一层 `SweepDevice`，只那一次，之后放行）。每段之后：有冻结的发布就撤掉故障原样重发（`resend_the_frozen_publish`）；盘面跑池级 checker；再在拷贝上可写挂载一次、挂载之后再跑 checker。」
   这是一个自写的块设备包装层（`SweepDevice`）逐次注入 I/O 错误、真实驱动被测代码走一遍失败路径、再跑池级 checker 校验结果，与「读代码判断行为对不对」是完全不同的方法。

2. **原样落盘的日志是真实执行产物，不是转述**：模型目录 `research/prompts/m2-closeout-code-r2-opus-model/logs/b1-1.log` 与 `b1-2.log` 实际存在（本报告现查 `wc -l` 得 1408 与 4436 行），日志末尾是真实的测试运行器输出：
   `test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 304.67s`（`research/prompts/m2-closeout-code-r2-opus-model/logs/b1-1.log:1407`）——
   这条只可能来自一次真实的 `cargo test` 运行（`test result:` 与耗时是 Rust 测试框架的原样输出格式，不是报告作者能手写伪造成这个格式还带精确到毫秒的耗时并保持内部一致）。
3. **段数与耗时的取样过程本身说明了这是运行时观测，不是代码推理**：`m2-closeout-code-r2-opus-output.md:128` 记录了从「先跑 1 个种子测量耗时」到「按测出来的每段约 0.75 秒估算全量 82 小时、超过 40 分钟于是缩」的取样决策过程——这种「先测、再按测到的数字决定要不要缩」的叙述结构只会发生在真正执行过代码、拿到了挂钟时间之后，读代码不会产生「82 小时」这样的具体估时。
4. **结论的分辨力来自结局分布表，不是代码走读**：`m2-closeout-code-r2-opus-output.md:130-150` 的 `analyze_sweep.py` 分析产物按（入口、注入种类、结局成员、冻不冻结）分组计数，例如「`OUT ('rollback_to_1_4', 'read', 'Err:ResurrectedUnitCopyUnreadableOrMismatched', 'false') 8`」——这类计数只能来自对 3024 段逐段实测结果的汇总，不可能靠读代码推出（读代码顶多推出「理论上应该有这几种结局」，推不出「实测下来这个结局出现了 8 次」）。

**「没打中」这个判定的边界，本身也是从这份实测数据里现读出来的，不是自我宣称**：`m2-closeout-code-r2-opus-output.md:155-156`：
「读故障让入口报错、而报错之前已发过写：0 段。报错的读故障只有管理员回退那 9 段，9 段 `writes_before=0`。注入的写 / 屏障报错之后还有写：3 段，都是取号失败的回卷……」——这句直接指出了实测数据里唯一的「非零」情形（3 段），并说明了它为什么不算「写了再拒」（是全或无回卷的一部分），这正是判决措辞「没打中（一次抽样）」里「一次抽样」这个限定词的来源——判决没有说「不可能打中」，只说这一次真实执行的抽样（3024 段）没有找到反例，与 `.claude/rules/three-way-inference.md`「一条腿只抽一次样不算一次观测——否定结论尤其不算」的纪律完全对齐（第三轮 X5 ① 也据此要求换一组历史再抽一次，而不是宣布这一格已经证明安全）。

**与只读代码的对照组**：同一份报告里，攻方自己在另外两格标出了只有代码位置与推断、没有实测的形态——`research/prompts/m2-closeout-code-r2-opus-output.md` 第 222-229 行「mkfs 收不收环长不是物理块整数倍的几何」一格与第 231-233 行「读路径 panic 普查」一格，第 233 行原句是「这一条是读代码，没有造输入，不算「没打中」的观测」（`research/prompts/m2-closeout-code-r2-opus-output.md:233`）。这两处的措辞与证据形态（没有日志、没有段数、只有代码位置与推断）与 Y1/Y7 的 3024 段扫完全不同——**攻方自己在同一份报告里对「动态实测」与「只读代码」两类结论用了不同的写法与不同的证据密度，第二轮判决沿用这个区分（Y1「没打中（一次抽样）」vs Z8/Y6-c/Y6-d 之类「只读了代码」）是对原文的忠实转述，不是把两种证据强度混为一谈**。

**什么现象会推翻这个复核**：若在 `m2-closeout-code-r2-opus-model/` 里找到 `opus_r2_y1_y7_single_fault_ordinal_sweep.rs` 源码本身不含真实的 I/O 或屏障注入逻辑（例如 `SweepDevice` 只是一个空壳、从不真正触发错误分支），或 `logs/b1-1.log`／`b1-2.log` 的内容与报告转述的计数不一致，这个「不是只读代码」的结论就要改判。本报告核对了日志文件行数与末行、原始计数摘录与报告正文逐字一致，没有发现这类矛盾；但没有重新编译并重跑这个装置（重跑属于攻方腿或崩溃验证员射程，且这一格不在本轮的「重型测试」豁免范围内自行去跑）。
