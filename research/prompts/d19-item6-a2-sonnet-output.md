## 二、逐格推导

### B1：码 1 半的唯一性——四个支点逐个推

**候选定义（按类复用写序键，收严后）**：码 1 的 key = 类标签 1 + 出生树 8 + 出生 txg 8 + 写序 10（写序 = 实例代号 4 + 事务号 6）= 27。判据问的是：有没有两个内容不同、都判成已发布的码 1 单元共享同一个 (类标签, 出生树, 出生 txg, 写序)？

**支点 1：D23（journal 的角色与格式） 已定项 14「事务按单元切分」**
源文件 `.claude/kb/decisions/23-journal的角色与格式.md:681`：「同一次定案把事务按单元切分 ⇒ 崩溃原子性的单位是一个单元、不是一次写请求（仓里没有任何决策承诺过写请求级原子性，这是一次对外语义的收缩）。」
这条只确立「原子性粒度是一个单元」，它本身没有逐字说「一个事务只写一个码 1 单元」——这句话的具体化落在支点 3。它的作用是把「写路径按单元切分事务」定成结构性前提，让支点 3 那句不是孤证。

**支点 2：D23（journal 的角色与格式） 已定项 7「事务号按实例计数、从 1 起」**
源文件 `.claude/kb/decisions/23-journal的角色与格式.md:279`：「事务号按实例计数、从 1 起，同一事务的全部记录共享它，与 jsn 是两个计数；记录按事务号顺序追加，一个事务在发出单元写之后失败即实例切换、号更大的记录一条都不追加。」
这确立：在**同一个实例**内，事务号是一个严格递增、按序追加、一次性分配给唯一一个事务的计数器——同一实例内不会有两个事务拿到同一个事务号。

**支点 3：D16（发布语义）「一个事务最多写一个单元的用户数据」**
源文件 `.claude/kb/decisions/16-发布语义.md:173`：「事务切分纪律把一次写请求按单元切成若干事务各自取号，一个事务最多写一个单元的用户数据。」
这是四支点里唯一直接把「一个事务」和「一个码 1 单元」绑死的那句。⚠️ 附录 ⑤ 自己标注：「后一句所在那段在 D16 里挂着一笔用户复核，复核的对象是那一句、不是这一格」。

**支点 4：D18（块里携带什么信息） 已定项 11「作废 checkpoint 必须换实例代号」+「每次可写挂载取新代号」**
源文件 `.claude/kb/decisions/18-块里携带什么信息.md:752-876`：「**作废一个 checkpoint 必须换实例代号**：当前实例没有行，谓词对它只能问「诞生代号 ≤ 挂载根 txg」，重发同一个号一发布，诞生代号等于它的孤儿全部判已发布——这是失败表能封闭的依据」；「可写挂载的顺序：……再取新代号 = max(这次挂载独占打开成功的那个集合里各超级块的代号, 根环里全部根记录的实例代号) + 1 并写进那个集合里的每一份超级块、全或无……之后才动任何单元；只读挂载不取号；从 1 起、0 无效。」
这确立：实例代号是一个跨全池生命周期严格递增、从不回收复用的号——任何一次「变成可写」的事件（首次挂载、干净重挂、崩溃重挂、实例切换）都会先取一个比迄今出现过的一切实例代号都大的新号。

**四支点合成**：
支点 2 + 支点 4 ⇒ (实例代号, 事务号) 这一对在全池生命周期内不会重复：实例代号本身不重复（支点 4），同一实例内事务号不重复（支点 2）。这正是「写序」的全部内容——写序 = (实例代号, 事务号)。
支点 1 + 支点 3 ⇒ 每一个全局不重复的写序值，最多对应一个码 1 单元的用户数据写入。
两者合起来：写序本身（不需要 (出生树, 出生 txg) 前缀帮忙）已经足以唯一标识任何一个曾经写出的码 1 单元。(出生树, 出生 txg) 前缀在这条推理链里是冗余信息，不影响唯一性成立。

**支点塌了会怎样**：
- 支点 3（或支点 1）塌：一个事务能写多个码 1 单元时，这些单元共享同一个写序；只要它们还共享同一个 (出生树, 出生 txg)（同一事务必然发生在同一个 checkpoint，如果这几个单元又落在同一棵树上），key 就会撞——这正是判决自己标出的唯一裂缝。
- 支点 2 塌：同一实例内两个事务拿到同一个事务号，写序撞，若又落在同一 (出生树, 出生 txg) 上，key 撞。
- 支点 4 塌：实例代号被复用，旧实例「照旧」保留的单元与新实例「重做」的单元可能共享 (实例代号, 事务号)——这正是 ④ 里显式处理、并靠「每次可写挂载都取新代号」堵住的那个洞。

**我没能找到判决没写出来的新裂缝**：我尝试过的攻击角度——同一 checkpoint 内先 reflink 再覆写同一偏移（附录 ③ 已经处理，靠写序区分）、同一事务写两个不同树的码 1 单元（写序相同但出生树不同，key 不撞，因为出生树是 key 的一部分）、根槽写失败重发（这是 B2 的问题，不直接冲击码 1 半，见下）——都没能绕开四支点合起来给出的结论。判决为 B1 记「没打穿」。

### B2：码 2 / 码 3 半的计数作用域——逐个时刻推

**候选定义**：出生序号的计数作用域是 (树, checkpoint 号, 实例代号)，内存里发、从 0 起，不分类；出生序号只做 key 的一段，不拿来给固定点多版择新。判据问的是：有没有一个时刻，计数器被清零或回退，而作用域三元组没有换？

**时刻 1：根槽写失败推进一格**
源文件 `.claude/kb/decisions/23-journal的角色与格式.md:681`：「根槽写失败重发时 checkpoint_txg 推进一格再发（根环区域 = `txg mod R`，D22（单元原子性怎么合成） 已定项 2，不推进就是反复重写同一个槽、把 R 个失败域用成一个）；⚠️ 由此「同一个根槽连续失败」不再是一条判据——槽位随 txg 轮转，N_switch ≤ R 时它永远够不着，留着它读起来像一道闸、实际是空的。」

这一步与「实例切换」是两件不同的事——「实例切换」段落是紧接着的**另一句**，以「**实例切换** = 挂载内做一次恢复」另起一段定义，两者的触发条件不同（探针写「写得进去 ⇒ 瞬时失败，走实例切换；写不进去 ⇒ 持续失败，走转只读」，根槽写失败推进一格是在这两支之前的一个更局部的重试）。

推导：checkpoint_txg 是全池生命周期内严格递增、从不复用的号（D22（单元原子性怎么合成） 已定项 2「区域 = txg mod R」隐含 txg 单调；D16（发布语义） 已定项 6「发布计数、轮转键、记账代、重放水位是同一个数」）。根槽写失败推进一格只是跳过了失败那个 txg 值、换用 txg+1 重新提交根记录——它不会让任何一个 txg 值被两次用于不同的、彼此独立的 (树, checkpoint, 实例) 作用域。已经用旧 txg 写出的码 2 / 码 3 单元头（诞生代号字段一旦写入就不会因为根槽重试而被重写，因为根槽重试只重试根记录本身），它们的 (树, 出生 txg=诞生代号, 实例代号) 作用域三元组仍然是那个唯一的旧 txg 组合，没有被"复用"，也没有被"清零"——只是这批单元最终有没有被一个成功提交的根记录发布，是另一件事（这正是 C149（根槽重发之后 birth 口径松一格） 记录的既有洞：`.claude/kb/checks-owed.md:155`「D23 对根槽写失败的处置是「checkpoint_txg 推进一格再发」……⇒ 发生过根槽重发的镜像上，同一个块的 birth 说得出两个号」）。

⚠️ **这里要分清两个问题**：C149 问的是「D5（快照 / 空间记账机制） 的 birth(b)（用于快照生命周期判定）该取旧 txg 还是新 txg」，这是一个语义上「这个块算发布在哪一代」的问题；而 B2 问的是「出生序号的计数作用域三元组会不会撞车」。这两个问题的答案不同——出生序号读的是**单元自己头里的诞生代号字段**（候选定义逐字「出生 txg 取诞生代号（码 3 偏移 73；码 1、码 2 同取诞生代号）」），这个字段一旦写入就固定，不随根槽重试改变，所以出生序号的作用域三元组本身没有歧义；C149 的歧义在 D5 那条**另一个**字段（快照可见性判定用的 birth）身上，两者字面上引用的是同一个"诞生代号"概念，但被消费的方式不同。

**结论**：这一步不构成"作用域没换、计数器却被清零/回退"——没有任何计数器在这一步被重置，只是旧 txg 对应的单元可能最终成为孤儿（这另有 C149 的既有洞在管，不属于本轮判据要打的范围）。⚠️ **但**——附录 ④⑤⑨⑩ 从未显式提到"根槽写失败推进一格"这个时刻，只处理了"实例切换"与"跨崩溃"（④ 逐字只写"D23 已定项 14 的**实例切换**逐字……"）。这是我自己顺着条文推出的结论，不是判决文本里写出来的；我没能找到判决的文字覆盖这一时刻。

**时刻 2：实例切换**
源文件 `.claude/kb/decisions/23-journal的角色与格式.md:681`：「**实例切换** = 挂载内做一次恢复：取新实例代号、写行 (旧实例, 最后发布的 txg, 最后施加的事务号)、重发在飞 checkpoint，号 ≤ W 的事务照旧、号 > W 的按新写序重做……固定点单元全部按新实例重写。」
取新实例代号 ⇒ 作用域三元组里的实例代号维度换了。"号 ≤ W 的事务照旧"的单元保留旧实例代号（作用域不换，但这些单元此前也没有被计数器"回退"过，它们的出生序号在旧实例仍然是当时分配的那个值，没被重新赋值）。"号 > W 按新写序重做"与"固定点单元全部按新实例重写"的单元用新实例代号，进入一个全新的、从未被使用过的作用域，计数器从 0 开始——这是一个**新的**作用域第一次被使用，不是"同一作用域被清零"。没打穿。

**时刻 3：崩溃重挂**
就是实例切换的触发场景之一（探针写失败 ⇒ 实例切换；持续失败 ⇒ 转只读到下次挂载，下次挂载时按 D18（块里携带什么信息） 已定项 11 的可写挂载顺序取新代号）。两条路径都会先取一个新的、从未用过的实例代号。没打穿，与时刻 2 同理。

**时刻 4：干净卸载再挂载**
D18（块里携带什么信息） 已定项 11：「只读挂载不取号」「可写挂载的顺序：……再取新代号……之后才动任何单元」。只读挂载完全不触碰计数器（不写任何单元）；任何一次变成可写的挂载都先取一个新代号。干净卸载再挂载时，若重新以可写方式挂载，同样落在"取新代号"这条规则里，作用域换掉。没打穿。

**时刻 5：跨头首次 COW**
源文件 `.claude/kb/decisions/08-核心索引结构.md:327-446`（已定项 6）：「**跨头首次 COW 的重生**（C113（扫描重建时多版单元的现行版本判定无输入） 定案 P6，2026-09-05）：新身份 = (本头树 ID, 类型 2, 原容器号, 本次发布代号)——保留容器号、只换出生树与出生代……重生只对类型 2：类型 1 容器归写者树独占……从不跨头 COW。」
这条讲的是码 3 容器（打包记录类型 2，inode 记录叶）跨头首次 COW 时**身份**（(出生树, 类型, 容器号, 出生代)）怎么变——新身份的 (出生树=本头树 ID, 出生代=本次发布 checkpoint_txg) 是在**当前正在进行的** (树, checkpoint, 实例) 作用域内发生的一次普通分配事件，与树里任何别的对象在同一 checkpoint 内获得出生序号，走的是同一个计数器、同一次递增。这不是"同一作用域计数器被清零"，是"这个作用域本来就在正常递增中，这次重生只是又用掉了一个号"。没打穿。

**时刻 6：分裂 / 合并**
同一份 D8（核心索引结构） 已定项 6 原文：「插入永远落在最右的叶 ⇒ 分裂只发生在最右叶……右半容器号 = 那条新记录的 inode 号，出生代 = 本次发布的 checkpoint_txg，出生树 = 执行这次分裂的那棵树（分裂是新建，与「COW 重写身份不变」是两件事）」；「合并：只许左吸收右 / 左从右借……保留左半身份，右半退役走 COW 释放路径」。
分裂产生的右半容器是当前作用域内一次新的分配（与时刻 5 同理，不构成重置）；合并产生的是"退役记录"，D18（块里携带什么信息） 已定项 11 逐字「**3 退役记录**……记录 = 被退役的 (出生树, 类型, 容器号, 出生代) 四元组，**不带写序**」——退役记录本身不携带写序 / 出生序号，不参与这个计数器的分配，谈不上重置。没打穿。

**时刻 7：D27（小数据打包容器） 容器**
**这一档推不出**。D27（小数据打包容器） 已定项 3（`.claude/kb/decisions/27-小数据打包容器.md:306-323`）只定了"取登记表 4–15 里一个新码，不复用码 3"，紧接着写明「⚠️ **类身份段带哪些字段仍未写死**，它随已定项 7（nonce 与 MAC 载体）一起定；已定的只是「占哪个码」与「新类自己立一条合法性不变量，不套 I-1.7（打包容器合法与判定顺序）」」。既然 D27 容器的类身份段字段表还没有定案，我没有办法判断它是否会携带出生序号、按什么作用域计数——这一档没有可供推导的条文，判"推不出"，不判"没打穿"。

**时刻 8：树 ID 被重发（C274）**
`.claude/kb/checks-owed.md:266-267`（C274（重放收养的对象不推计数器水位））：「同一个形状还管每一个按计数器发号、而作用域里不带实例代号的东西（D19（块指针的结构与宽度预算） 未定项 6 第二轮的出生序号、代理号两族的原形态）；**作用域带实例代号的计数不撞在这里**——每次可写挂载都取新实例代号（D18（块里携带什么信息） 已定项 11 那一行「再取新代号 = max(……) + 1 ……之后才动任何单元」），作用域随之换掉（2026-09-11 第三轮主 agent 现查坐实）。」
C274 自己的文本已经把"出生序号"这个候选（作用域带实例代号）排除在它打中的范围之外——它打的是"作用域不带实例代号"的原始候选（出生序号的原形态、代理号）。按类复用写序键（收严后）的出生序号作用域**带**实例代号，不在 C274 打中的范围内。这与 B2 判据表自己的预期一致（"若那个时刻对七条候选都成立（例如树 ID 重发），只记共同前置"）——树 ID 重发不构成对这一候选的独有打击。没打穿。

**B2 小结**：七个测试点里，六个（实例切换、崩溃重挂、干净卸载再挂载、跨头首次 COW、分裂/合并、树 ID 重发）没打穿；D27 容器一档推不出（条文空白）；根槽写失败推进一格这一点我推出没打穿，但这是我自己的推导，判决文本没有显式覆盖它，我在此处如实标出这个覆盖缺口。

### B3：实例切换与崩溃重挂之后唯一——按 I-1.2 的谓词逐项判

I-1.2（块头写序已发布） 原文（`.claude/kb/invariants.md:15-64`）：「任一单元，其头记录的写序 (i, n)……与诞生代号 b 按……全局已发布谓词判成已发布：i < 挂载根实例且无该实例的行 ⇒ 已发布，有行 (i, T_pub, W) ⇒ 码 1 要 b ≤ T_pub ∨ n ≤ W、码 2 / 3 要 b ≤ T_pub……i == 挂载根实例 ⇒ b ≤ 挂载根的 checkpoint_txg；i > 挂载根实例 ⇒ 判损坏。」

判据问的构造是：被收养的旧单元（实例切换时"号 ≤ W 的事务照旧"）与重做 / 新写的单元（"号 > W 的按新写序重做"），是否会共享同一个 key 且都被这条谓词判成已发布？

被收养的旧单元携带旧实例代号 i_old（写序里的实例代号段，因为它们没有被重写，头里的字节原样保留）。重做 / 新写的单元携带新实例代号 i_now（i_now = max(...) + 1 > i_old，因为 D18（块里携带什么信息） 已定项 11 保证取号严格递增且从不复用）。两者的 key 里 (实例代号) 这一段天然不同，不管其余段（事务号 / 出生序号）取什么值，完整 key 都不会相同。

这与 B1 的推理链是同一件事——写序本身（含实例代号段）已经在全池生命周期内不重复；实例切换 / 崩溃重挂只是这条推理链里"实例代号严格递增"这一环节的具体触发场景，不产生新的攻击面。逐项核对 I-1.2 的四个分支（i < 挂载根实例、i == 挂载根实例、i > 挂载根实例、以及有行 (i, T_pub, W) 的判定），我没能构造出两个 key 相同、都判"已发布"、内容不同的单元。判"没打穿"。

### B4：引用侧可构造——逐条路径核

判据问的是：进映射那一刻手里有没有完整的 key，不多读一次单元、不多查一棵树？

- **解引用**：指针本身携带 (出生树, 出生 txg, 写序/出生序号) 的完整段（候选定义「指向码 1 的指针 +26、指向码 2 / 码 3 的 +24（类标签由查找路径给，不进指针）」），类标签由调用方已知的查找路径上下文给出（例如：从 extent 树叶条目下降，已知目标是码 1；从 inode 树内部节点条目下降，条目自带的"类型段"已经区分码 2 / 码 3，D8（核心索引结构） 已定项 6 逐字「类型段兼作『子节点是什么』：0 ⇒ 子节点是码 2 索引节点……2 ⇒ 子节点是码 3 容器」）。手里已经有完整 key，不需要额外读。没打穿。

- **D5（快照 / 空间记账机制） 释放判定**：这一条按判据表自己的规则「那条路径是单一引用块上的 D5（快照 / 空间记账机制） 释放判定时，它出局」——单一引用块的 kill 判定走的是 `birth(b) ≤ S.txg < death(b)` 这条比较（`.claude/kb/decisions/05-快照-空间记账机制.md:1-68`），直接读指针内联的 birth 字段，不查中央映射，本来就不在 B4 的射程内。

- **搬迁（D26（后台整理与放置回收） 的常驻整理）**：D19（块指针的结构与宽度预算） 已定项 5 硬规则 1「释放一律经映射，不经提示」加上「搬迁只改这里一条条目」——搬迁改写的是映射里已存在的那条条目（按其 key 定位），key 不变（候选集七条都要求搬迁前后 key 不变），不需要额外读一次单元或查一棵树。没打穿。

- **checker / 扫描重建**：类标签（共同前缀偏移 6）、出生树、出生 txg（诞生代号）、写序 / 出生序号，都是各单元头里已定案的字段（D18（块里携带什么信息） 已定项 7 / 11），checker 与扫描重建本来就要读单元头做别的判定（I-1.6（类标签登记且三处相等） 等），顺带就能拼出完整 key，不构成"多读一次"。没打穿。

- **deadlist / livelist 条目处理**：这一条是一个明确挂着的欠账，不是这一候选独有的失败。C266（livelist 条目的身份用了会过期的位置提示）（`.claude/kb/checks-owed.md:258`）：「E130……与 C260……都把 livelist 条目定成『类型标签 2 + 位置条目 14 + birth txg 8』……条目身份要改用中央映射的 key，而那个 key 是 D19（块指针的结构与宽度预算） 未定项 6……⇒ D6（快照实现模型） 未定项 2 的条目形态挂在 D19（块指针的结构与宽度预算） 未定项 6 上……条目 = 映射的 key 加头的树 ID 前缀 8 字节，宽度仍随 D19（块指针的结构与宽度预算） 未定项 6」。这段文字本身把"livelist 条目该用哪个 key"列成一个**等待本决策定案后才落地**的依赖，不是"按类复用写序键这一候选在这条路径上比别的候选更差"。B4 判据本身没有把这条列进要测的路径清单（B4 列的是"解引用、D5（快照 / 空间记账机制） 释放判定、deadlist / livelist 条目处理、搬迁、checker、扫描重建、模型对拍"，deadlist / livelist 确实在列），所以我仍把它记下来：**这条路径今天没有一个候选是"过"的**，因为 livelist 的字段表还没有跟着 D19（块指针的结构与宽度预算） 未定项 6 一起改写——但这不是"多读一次"的问题，是"字段表还没写"的问题，性质与 D27 容器那一档（推不出）接近，不构成对这一候选的独有打击。

### B5：「逻辑身份 + 写序键那一输随 C163 翻转」本身

**① C163（固定点各轮写序相同使平局破除落空） 的处置候选取了之后，逻辑身份 + 写序键在第 3 格真的就过了吗？**

C163 原文（`.claude/kb/checks-owed.md:174`）：「**处置候选（待用户复核，它推翻的是九轮论证的产物并动一条不变量）**：码 3 的择新键退回二元 (诞生代号, 实例代号)，并把「一个实例在一个 checkpoint 只有一个固定点、**每个容器只写出一次**」……升成显式写路径纪律 + 会失败的检查。」

这句处置候选逐字只提到"容器"（打包记录单元 / 码 3），没有一个字提到码 2（普通索引节点）。逻辑身份 + 写序键的候选定义里，**码 2 的 key = (树 ID, 层级, key 区间下界, 诞生代号)，完全不含写序**（候选表原文：「码 2：(树 ID, 层级, key 区间下界, 诞生代号)，层级与 key 区间下界由查找路径给」）。

那么问题变成：码 2 节点（普通索引节点，例如记账树 / inode 树的内部节点、extent 树的内部节点）会不会像码 3 容器一样，在同一个 checkpoint 内被物理写出不止一次？

固定点本身不是打包容器专属的机制。C163 自己引用的固定点定义（`.claude/kb/checks-owed.md:174`）：「固定点迭代按 D3（空间分配） 已定项 5 与 E81（提交的固定点） 是**发布阶段内部的收敛**（提交自身产生的块又产生分配），不产生新的用户事务」——这是在描述整个发布阶段的收敛机制（写元数据引发新的分配，分配又要记账、记账又要写，直到收敛），不是专门为打包容器设计的。记账树本身就是码 2 节点（D8（核心索引结构） 已定项 1「记账住一棵独立 keyspace 的 btree」，其内部节点走码 2 的字段表），而记账树恰恰是"提交自身产生的块又产生分配"这条反馈回路里最直接被反复触碰的结构——每次分配/释放都要更新记账，记账更新又要写节点，写节点又消耗/释放空间，又要再更新记账。如果这个收敛过程在一个 checkpoint 内需要好几轮才能稳定（这正是"固定点"这个词本身要表达的意思——不是一次写完，而是反复迭代直到不动点），那么记账树的码 2 节点完全可能在同一个 checkpoint 内被物理重写多次。

⚠️ **我要如实标出这一步的性质**：我没有找到一处条文**直接、逐字**说"普通码 2 节点会在同一 checkpoint 内被物理重写多次"——这是我从"固定点是发布阶段的通用收敛机制"（D3（空间分配） 已定项 5 / E81（提交的固定点），经 C163 转引）加上"记账树的节点就是码 2、且记账是固定点收敛回路的直接参与者"（D8（核心索引结构） 分项 1 + C163 的固定点定义）两条推出来的**推断**，不是一条现成的、逐字点名"码 2 在固定点内多写"的判决。但如果这个推断成立，逻辑身份 + 写序键的码 2 key（不含写序）就没有任何字段能区分同一 checkpoint 内先后写出的两个物理版本——这正是 I-1.8（归并后版本全序） 给码 3 配的机制（三元全序键）在码 2 上完全缺失的地方，而 C163 的处置候选没有伸手去补这个缺口。

**判：打穿**（带保留）。构造：设记账树在某个 checkpoint 的固定点收敛过程中，因为分配/释放反馈回路，同一个内部节点被物理重写了两次（第一次把某个分隔 key 更新为 A，第二次因为后续的空间分配触发的记账更新又把同一个节点重写为内容 B）；两次写出的码 2 单元的 (树 ID, 层级, key 区间下界, 诞生代号) 完全相同（同一棵树、同一层、同一个孩子的 key 区间没有变化、同一个 checkpoint 的诞生代号），而内容不同（分隔 key 或子指针不同）——按逻辑身份 + 写序键的定义，这两个单元的 key 逐字节相同，而 I-1.2 不否定第一版已发布（它在同一 checkpoint 内被后一版取代之前也曾经是"当前写出的最新版本"）。这与 C163 打中码 3 的构造是同一个形状，只是把"容器"换成"记账树的内部节点"。

**② C163 的处置候选没取时，按类复用写序键（收严后）靠出生序号给固定点两版不同的 key；那两版在扫描重建时谁是现行版本，有没有人判？**

④ 原文明确写：「出生序号只做 key 的一段，不拿来给固定点多版择新」（`.claude/kb/decisions/19-块指针的结构与宽度预算.md:104`）。这句话的作用是**主动排除**用出生序号做"哪个版本更新"的判别子——理由是这样用会落进 D18（块里携带什么信息） 已定项 1 已经否掉的用途（`.claude/kb/decisions/18-块里携带什么信息.md:129-224`：「⚠️ **射程**：定案否掉的是『为分辨陈旧副本而设的序号』」）。

那么现行版本判定还剩什么机制？I-1.8（归并后版本全序） 原文（`.claude/kb/invariants.md:15-64`）：「码 1 / 3 的可读已发布单元按……归并成组之后，同 key 的各组两两全序键不等——码 1 的键是写序，码 3 的键是 (诞生代号, 实例代号, 事务号) 三元……**码 2 不进这条**」。

对码 3：全序键落在"事务号"这一位上做平局破除，而 C163 已经证明这个事务号在固定点各轮取到的是**同一个值**（因为固定点跑在发布阶段、"该 checkpoint 的用户事务已攒完"，各轮固定点取到的是同一个已分配的最大事务号）——这条判别子本身已经失效，是 C163 记录的既有洞。C163 的处置候选（如果没被采纳）没有给出替代方案。

对码 2：I-1.8 明写"码 2 不进这条"，本来就没有全序判定；而 D18（块里携带什么信息） 已定项 12（`.claude/kb/decisions/18-块里携带什么信息.md:129-224`）把码 2 头里原本的 6 字节事务号砍掉了（改成"写序 4（只实例代号）"）——码 2 现在连"事务号"这个字段都不存在了。

所以：无论 C163 处置候选取还是不取，码 2 在固定点内多版的现行版本判定都没有任何机制；码 3 即使有 I-1.8 的三元全序键，那个全序键里唯一能做平局破除的一维（事务号）已经被 C163 证明是无效的。而出生序号被 ④ 自己排除在"择新"用途之外。

**判：打穿**。构造：某容器（码 3）在一个 checkpoint 的固定点内被写出两轮，两版的 (出生树, 出生 txg=诞生代号, 实例代号) 完全相同，出生序号不同（各自在写出那一刻从计数器领到一个新值，比如第一轮领到 41、第二轮领到 57）——这两版的 key 因为出生序号不同而**不相同**，都会各自作为独立条目进入中央映射（因为出生序号是 key 的一部分，按定义两次写出会产生两条不同的映射条目）。问题变成：这两条映射条目里，哪一条才是"现行"的，另一条对应的物理空间什么时候能被回收？扫描重建时，两个单元都能通过头校验和 / I-1.2 判成"已发布"（两者的 (实例代号, 事务号) 完全相同，事务号落在同一 checkpoint 内已施加的范围内，I-1.2 对码 3 只看 b ≤ T_pub，两者都满足），而 I-1.8 的三元全序键因为事务号相同而分不出胜负——扫描重建拿不到任何依据判定哪一版是"最终生效"的那一个。若两版内容不同（第一轮的中间态 vs 第二轮的最终态），映射里可能同时留着两条指向不同物理块的条目，或者按某个未定义的顺序（比如"先扫到哪个算哪个"）任意选中较旧的那版——这正是判据表要的构造：「按类复用写序键（收严后）的两版在扫描重建时被选错，或映射里留下一条指向已死那一版的条目、而那块空间因此放不掉」。
