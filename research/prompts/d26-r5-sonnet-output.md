## 3-1（最值钱）：E127 的节点数分组臂是不是「存组身份」这条路最有利的实现

**先确认 E127 实际测的是什么**（现查 `research/e7-index-bench/src/bin/e127_group_identity_under_split_merge.rs:431-457`）：

```rust
    fn split_at(&mut self, position: usize) -> u32 {
        ...
        let parent_group = self.node_group[identifier];
        let group = if (self.group_member_count[parent_group as usize] as usize) < self.nominal_group_size {
            parent_group
        } else {
            let fresh = self.next_group_identifier;
            self.next_group_identifier += 1;
            self.group_member_count.push(0);
            fresh
        };
        self.group_member_count[group as usize] += 1;
        self.node_group.push(group);
```

节点数分组臂的规则是：分裂出的新节点，若父组未满就跟着父组，**满了就另开一个全新组**（不是切半、不是按任何 key 或热度重排）。这与提示第 1 问要判的两种形态（组满切半、按热度重排）**都不是同一条臂**——E127 只注册了这一种组管理策略。

**候选形态一：组满切半（组边界随历史走、不是 key 的函数）**

定义：`nominal_group_size = G`；组满时不开新组，而是把这 `G` 个成员按**当前物理位置序**（不是 key）切成两个 `⌈G/2⌉` / `⌊G/2⌋` 的子组，各自延续一个组号。

① 组身份不是 key 的函数：成立（切分点取物理位置序，不取 key）。
② 需要盘上字段：成立（组号本身仍要持久，与 E127 的 `node_group_gN` 同样的理由——`step_node_count_group` 第 862-869 行读的正是 `sim.node_group[...]`，这个映射不存字段就重建不出来）。
③ 在 E127 的模型里有可核的理由比 key 区间分组好 20% 以上：**推不出来**。

推导：E127 正文自己给出的漂移机制（`.claude/kb/experiments/127-分裂合并之下组身份要不要存.md` 判决段「为什么分裂合并让两条臂分开」一节，产物同一段）是——「节点数分组的组身份跟着节点走……2000 个 checkpoint 之后组的成员在 key 序上不再连续，整组重落把 key 序上不相邻的节点放到一起」。这条漂移的根因是：组成员资格只由分裂/合并的**发生次序**决定，与当前 key 邻接关系无关。「组满切半」改的只是**溢出时怎么处理**（切半 vs 开新组），并没有改变漂移的根因——按物理位置序切半，两个子组各自的成员仍然是历史上先后被塞进这个组的节点，与它们今天的 key 邻接关系无关；相反，更频繁的组重划分（切半比开新组更早触发下一次「组内成员变化」）只会让整组重落更频繁，而不会让重落的对象在 key 序上更相邻。E127 六格里 node_group 已经在 4 格上更差（0.930 / 0.957 / 1.651 / 1.856 / 1.031，仅 0.889 一格勉强赢），且这条臂本身已经采用「组满即重置边界」（开新组）这个最直接的止损手段——切半只是止损手段的另一种形态，止损对象仍是同一个漂移机制，没有理由让结果反转 20 个百分点以上。

**候选形态二：按访问热度重排**

定义：组成员资格按「最近是否被脏过」的时间窗口重排，与 key 值无关。

① 成立（热度不是 key 的函数）。② 成立（热度分组同样要持久化组号）。③ **推不出来，且方向可能相反**。

推导：E127 的负载只有两组——`uniform`（脏 key 全域均匀随机）与 `runs8`（脏 key 按段长 8 成段选取，模型「负载」表见 `research/e7-index-bench/src/bin/e127_group_identity_under_split_merge.rs` 模型注释与判据表）。在 `uniform` 负载下，「最近脏过」这个热度标签与 key 值统计独立——按热度把它们物理聚在一起，等于把 key 序上互不相邻的对象强行放到相邻物理槽，这直接**增大** `runs`（因为 runs 按 key 序遍历时，这些被聚在一起的对象在 key 序上仍然分散，反而制造更多断点），不是减小。在 `runs8` 负载下，同一个 checkpoint 脏的 64 个对象本身就是按段长 8 成段选取的（key 序上已经局部聚集），此时「热度」恰好与 key 邻接高度相关——但这意味着按热度重排在这个负载下**退化成按 key 邻接重排**，即与 key 区间分组同源，不是一种独立地更优的机制，也谈不上凭空多出 20% 优势。

⇒ **3-1 的稻草人条款没有被打中**：两种形态都能给出定义、都确实需要盘上字段，但「在 E127 的模型里比 key 区间分组好 20% 以上」这一条给不出可核的推导，其中形态二在 uniform 负载下的推导方向反而是变差。按材料判据表的失败条款，3-1 不触发——不需要另立实验加臂重跑，本轮可以继续判「否」。

## 3-2：树结构本身给不给组（同父兄弟要不要字段）

**现查两处支撑事实**：

1. `.claude/kb/decisions/04-校验和位置.md:3`：

   ```
   **方向：内联进指向该块的指针（父节点存子节点校验和），形成 Merkle 树，自验证。**
   ```

   这条已定条款要求父节点持有子节点的校验和，前提是父节点本来就要持有指向每个子节点的指针（位置、身份）——这是标准 B 树结构本身的要求，不是为分组新加的。

2. `.claude/kb/experiments/73-节点key区间的扇出代价.md:78`：

   ```
   | 不带区间 | **答不出**（区间只在父节点的 keypointer 里，父没了就没了）|
   ```

   这条实测明确指出：一个节点自己的 key 区间信息，只有在**父节点的 keypointer 列表**里才拿得到。反过来说，父节点的 keypointer 列表本身就是「按 key 序排列的子节点指针集合」——这正是「同父兄弟」的定义：一个内部节点的全部子指针，天然按 key 序排成一行。

**推论**：在本工程的树结构里，「同父兄弟」这个组不需要新字段就读得到——放置器/整理器要重写一批节点时，本来就要走到它们的父节点去改写子指针（COW 决定了子先写、父后写，父节点必须被访问、被改写），而父节点里那份 keypointer 列表，就是这批节点的兄弟名单，且天然按 key 序排列。这与 `first-txn-layout.md:229` 已经登记的索引节点头字段——`| inode 树根（码 2） | 单元类型标签恒 = 2；类身份段 = 树 ID + 层级 + key 区间 [1, 1] + ...` ——完全一致：**节点自己的 key 区间**（本已是已定字段集合的一部分）与**父节点的子指针序列**，两者合起来就足以枚举「同父兄弟」组，不需要在节点头再加一个组身份字段。

**这也回答了第 2 问的后半句**：若「树结构给组」这条路成立（它确实成立），那「组身份必须进格式」这条路就只剩 3-1 那两种稻草人形态——而 3-1 判定推不出可核的 20% 优势。⇒ **格式部分「组身份必须进节点头」这条路，找不到第三种支撑理由**：key 区间分组不需要字段（从 key 直接算），同父兄弟分组不需要字段（从既有的父子指针结构读），3-1 的两种候选形态推不出优势。

⚠️ **这一条不构成对「同父兄弟」组本身有用与否的判断**——它只回答「读不读得到」，不回答「值不值得作为一种放置策略采用」；后者属于政策层，见 3-5 前的第 5 问，落在 D3（空间分配） 未定项 8 / D26（后台整理与放置回收） 已定项 1 的政策格里。

## 3-4：E95（老化的节点布局臂） 那句「格式臂减半」该不该改写

**现查 `.claude/kb/experiments/95-老化的节点布局臂.md:98`（2026-09-10 反推腿实测、主 agent 复跑坐实）**：

```
⇒ **被判成「格式臂」的那条臂，在这个模型里不消费任何盘上字段**（`:683` 逐字 `dirty.iter().map(|&key| key / group_size)`），
```

`key / group_size` 就是 key 区间分组的定义式——E95（老化的节点布局臂） 里赢下 runs8 三格、被登记为「格式臂」`fmt_group_gN` 的那条臂，机制上与 E127（分裂合并之下组身份要不要存） 的 `key_interval_wN` 是同一族。E127（分裂合并之下组身份要不要存） 把「按 key 区间分组」与「按节点数分组」在同一个带分裂合并的模型里分开跑之后，产物 `research/results/e127-group-identity-under-split-merge-2026-09-13.out:52-93` 的 `grid` 行显示：`key_interval` 家族在 4/6 格上明显赢过 `node_group` 家族（例如 `budget=256 load=uniform`：`key_interval_w32 runs_median=2045` 对 `node_group_g2 runs_median=3795`，budget=256/runs8：`key_interval_w8 runs_median=1123` 对 `node_group_g8 runs_median=1158`）。

**判据 3-4 的判红条件**——「说清 E95（老化的节点布局臂） 的节点组臂哪一点是 key 区间分组做不到的」——**推不出来**：E95（老化的节点布局臂） 的 `fmt_group_gN` 本身就是静态 key→对象模型下的 `key / group_size`，即 key 区间分组的一个特例；E127（分裂合并之下组身份要不要存） 把它推广到有分裂合并的模型之后，真正独立于 key 值的「节点数分组」在 4/6 格上反而更差。没有任何观测支持「E95（老化的节点布局臂） 的节点组臂能做到、key 区间分组做不到」这句话。

⇒ **该改写**。E95（老化的节点布局臂） 正文「按判据 5 的字面：能」那句结论（`.claude/kb/experiments/95-老化的节点布局臂.md:878`：「runs8 三格全中，uniform 三格全不中」）描述的实际上是**按 key 分组的放置政策**在 runs8 负载上把 runs 压到一半以下，不是「组身份进节点头」这件事本身带来的收益——E95（老化的节点布局臂） 自己的「它答不了的」第 4 条（`:931-937`）已经承认这一点（「量到的是『固定边界的整组重落 打赢 滑动窗口与轮转整理』，不是『节点头里那个组身份字段是必需的』」），E127（分裂合并之下组身份要不要存） 六格的结果进一步坐实：把「组身份」换成真正不依赖 key 的节点数分组之后，赢面从「runs8 三格全中」掉到「六格全部未过 0.8 倍阈值」。
