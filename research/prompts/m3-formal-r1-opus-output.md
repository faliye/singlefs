判据五条，都照条款文字写、不看实现的循环：R = 施加后的根等于所选根时间线上某一版（M2 字面，只看返回的根）；P = R 且那几次发布的每条记录与点名单元都在；M = P 且段长不超在飞上限；X = 落到的恰是「连续完整、不超上限」的最远一版；F = 把施加后的根当所选根再重放一次，根不动。

### 1.1 状态空间规模与界（F1「界取多大」）

原实现，合法历史域，每个状态真跑一次 `replay_journal`（`summary.txt` 表 D）：

```
base	n=4	864	viol_R=0 viol_P=0 viol_M=0 viol_X=0 viol_F=0	errors=0 panics=0 secs=0.00
base	n=5	6048	viol_R=0 viol_P=0 viol_M=0 viol_X=0 viol_F=0	errors=0 panics=0 secs=0.00
base	n=6	41472	viol_R=0 viol_P=0 viol_M=0 viol_X=0 viol_F=0	errors=0 panics=0 secs=0.01
base	n=7	279936	viol_R=0 viol_P=0 viol_M=0 viol_X=0 viol_F=0	errors=0 panics=0 secs=0.06
units	n=5	193536	viol_R=0 viol_P=0 viol_M=0 viol_X=0 viol_F=0	errors=0 panics=0 secs=0.13
units2	n=4	221184	viol_R=0 viol_P=0 viol_M=0 viol_X=0 viol_F=0	errors=0 panics=0 secs=0.13

- 每多一条记录，状态数乘 6.75 到 7（864 → 6 048 → 41 472 → 279 936）；点名单元每份多一位再乘 2。6 线程下 n=7 是 0.06 秒。照这个比率外推（推的）：n=12 约 3.9 × 10⁹ 个状态、十几分钟；默认环的在飞上限 65 536 条（事实表 (b) 循环上界表）不管哪种有界工具都够不着，只能靠「上限是入参 `ring_bytes` 算出来的」把环缩小。
- 原实现在合法历史域的全部模式上 R / P / M / X 零违例、零 panic（orig 那一段 39 行 `panics=0`；2 842 674 个状态）。全部 28 个变体里只有 m22（裸加一）在 edge 模式 panic——仓的 release 配置开着溢出检查，所以 M1「不 panic」那一格在这个域里量过是绿的。
- **最小杀伤界**（`summary.txt` 表 C）：27 条变异里 24 条能被某条判据在某个域里打红，它们的最小界是 n=1 的 12 条、n=2 的 8 条、n=3 的 2 条、n=4 的 2 条；扫描上沿是 n=5 到 7（对抗域 3），极值不在端点上。剩 3 条（m04、m09、m11）到上沿哪个域都不红。

⇒ 对「界取多大才不是摆设」的回答：**这一截代码上界取 4 条记录就把能杀的全杀了，界不是摆设与否的分界线**。分界线在下面两样：判据写在哪个对象上（1.2、1.3），输入域是合法历史还是任意自证记录（1.4、1.5）。

### 1.2 H1：M2 写在返回的根上，七·3 的必红世界不红

七·3 的验收原句：「判定改成任意一条都算末条，反例出现」（`.claude/kb/milestone/03-third-txn.md:164`）。入库变异 m07 / m08 正是这一改（`recovery.rs` 第 3200 行那一判）。在合法历史域：

```
base	mode=base n=6 shapes=243 states=41472 viol_R=0 viol_P=5148 viol_M=5148 viol_X=5616 viol_F=1512 errors=0 panics=0 applied_any=12960 applied_multi=7880 reads=12390 bytes_read=50749440 secs=0.01
base	  first_P: ks=[1, 2] commit=0 c=0 s=010 u=0 e=0 got=j=1 X期望j=0
```

六个模式到上沿 R 都不红（`results.tsv` 第 233、238、243、248、253、258 行），P 在 n=3 红。原因是写侧：一次发布的每条记录带的是同一份新根段——「每条记录都带整次发布的新根段（已定项 15），施加末条那一份。」（`crates/singlefs-core/src/recovery.rs:3209`），写侧在逐条记录的循环里填的是同一个 `plan`：「new_tree_identifier_watermark: plan.tree_identifier_watermark,」（`crates/singlefs-core/src/transaction.rs:1821`）。所以把半次发布施加上去，**返回的根逐字段等于那次发布的根**；坏的是「那次发布后几条记录点名的单元没验、可能不在盘上」，这件事不在 `replay_journal` 的返回值里。

M2 的条款原句是「不存在被前缀切开的发布」（`.claude/kb/decisions/13-验证路线.md:32`）与它前半句「重放结果等于某个整数个已发布的 checkpoint 的结果」。候选 ①②④ 若把「重放结果」取成 `replay_journal` 返回的那条根（最省事、事实表也写着施加只改内存里一条根），七·3 的必红世界就造不出反例。要它红，「结果」必须包含「那次发布的全部记录在盘上、点名单元两份都在」——也就是 spec 要带盘模型，不是一个根上的谓词。对抗域里每条记录带不同的根段时 R 在 n=1 就红（`results.tsv` 第 263 行），那是装置给的区分，合法写侧不产生。

### 1.4 H3：读者规则那几格，合法历史域看不见；放开到对抗域，手写判据与实现先对不上

表 B 第 5 类 6 条（m12、m13、m14、m17、m18、m19）是 D23 已定项 4 的读者规则与反向链那几道防线：合法写侧不写出会踩它们的记录，所以在合法历史域里它们是等价变异。要它们红，输入域得放开到「自证过、字段任取的记录」。放开之后，照条款字面写的声明式判据与**原实现**先不一致：

```
adv	mode=adv n=3 states=786432 viol_R=0 viol_P=6144 secs=1.74
adv	  first_P: n=3 锚=0 字段(txg,序号,末条,提交,事务,链对)=[(6, 1, true, true, 1, true), (7, 1, false, false, 1, true), (6, 1, false, false, 1, true)] got=施加到计数器 1
adv+PROBE_ADV_FOLLOW=monotone	mode=adv n=3 states=786432 viol_R=0 viol_P=0 secs=1.73
```

条款字面：「里带末条标志的那条之后还有记录（断在带标志的那条）」（`.claude/kb/decisions/23-journal的角色与格式.md:154`）——第 1 条带末条标志、txg 6，第 3 条又是 txg 6，照字面断在第 1 条、不施加。实现从下一个计数器起按升序看，txg 一越过就停：「.take_while(|later| later.checkpoint_txg <= record.checkpoint_txg)」（`crates/singlefs-core/src/recovery.rs:2951`），依据写在函数注释里：「同一实例里计数器与 checkpoint_txg 一起往上走」（`crates/singlefs-core/src/recovery.rs:2939`）；中间隔了一条 txg 7，它看不到第 3 条，施加了第 1 条。把判据那一句换成实现的读法，6 144 归零——这 6 144 个不一致全部出自这一句的两种读法。

这不是我报的实现缺陷：那种记录序列合法写侧写不出，读者规则本身防的就是「坏了而校验和仍对得上、或改出来的镜像」，而在那个域里「照字面」与「照单调假设」哪个对，条款没写。它是 F2 的一个实例：**spec 照文字手写、输入域一放开，第一批不一致出在条款没写清的地方，判「谁错」要回到条款去定**（D13 已定项 13 的同源性计数要的正是这种事件；这一件按原规矩该记「条款欠一句」，既不是 spec 错也不是实现错，计数器的两格里没有它的位置）。

历史：两次单记录发布；所选根那条记录读不出，第二次发布那一槽上坐着一条同实例、同计数器、同 txg、反向链相同、内容（新根段）不同的自证记录。`replay_journal` 照链首规则接上它，落到一条「这条时间线上从没发布过」的根。被判的系统看不到区分两条时间线的东西（判别子观测不到）：这一格不是实现的错，是**「M2 对任意盘成立」这句话本身为假**。射程四维里「上一条时间线的残留」正是形式化要多罩的一维（「refinement 的边际价值只在层 0 枚举取不到的那几维」（`.claude/kb/decisions/13-验证路线.md:35`））；罩它就得把这种记录放进域，放进去 M2 就要带一条前提「同一 (实例代号, 计数器) 在全部时间线上只对应一份内容」。这条前提是取号与写侧的性质（取号之前约 13 500 行、回卷写，事实表 a2、a3），不在 577 行闭包里，**五条候选没有一条的范围罩得到它**；证明里它只能当假设。

### 1.6 H5：M3 单调的字面那一句在 n=2 就假

条款：「施加的事务集」（`.claude/kb/decisions/13-验证路线.md:33`，整句是段内 `c ⊆ c'` 推 `Recover(c)` 施加的事务集包含于 `Recover(c')` 施加的）。把根槽也放进崩溃状态（每条后续根一位），两种读法各数一遍：

```
mono	mode=mono n=2 shapes=3 pairs=45 viol_applied_by_replay=3 viol_version_reached=0 secs=0.00
mono	  first_i: ks=[1, 1] A=010(c=0,j=1) ⊆ B=110(c=1,j=1)
mono	mode=mono n=5 shapes=81 pairs=151875 viol_applied_by_replay=16116 viol_version_reached=0 secs=0.00
mono+PROBE_MONO_RING_SLOTS=6	mode=mono n=5 shapes=81 pairs=151875 viol_applied_by_replay=15876 viol_version_reached=0 secs=0.00
```

- 读法 (i)「这一次重放施加上去的发布」：A = 第二次发布的记录落了、根槽没落（恢复施加 1 次）；B = A 加上那条根槽也落了（所选根已是新根，恢复施加 0 次）。A ⊆ B 而施加的集合反而变空。这一对是最普通的合法崩溃状态（记录先持久、根槽后持久，两个状态只差根槽那一次写）。
- 读法 (ii)「恢复落到的那一版所含的发布」：到 n=5（151 875 对）零违例，大环、6 槽小环都是。

⇒ M3 单调的候选原句（**只在我的模型上量过、被攻过零轮**）：
「同一条时间线上、段内两个崩溃状态 `c ⊆ c'`：`Recover(c)` 落到的版本不晚于 `Recover(c')` 落到的版本（版本按所选根时间线上的发布次序比）。」
它没罩的：跨实例切换（所选根换了时间线，「不晚于」没有定义）；`c'` 多出来的是残留或孤记录时（1.5 的域）。七·4 写「单调那一半全仓无落点，先写条款再证」（`.claude/kb/milestone/03-third-txn.md:165`），先写的那一句不能照抄 D13 第 33 行的字面。

6 槽环、在飞上限 2：所选根之上有 3 条记录（第 2 次发布 1 条、第 3 次发布 2 条）。第一次重放取前 2 条（「for record in above.into_iter().take(in_flight_limit) {」（`crates/singlefs-core/src/recovery.rs:3109`）），只施加第 2 次发布；把结果当所选根再来一次，上限从新根重新数，第 3 次发布也施加上。大环上（上限 64，n ≤ 7 够不着）F 零违例。

含义两层。① `Recover(Recover(c)) = Recover(c)` 在只读那条路上类型对不上：`recover` 不写盘（「let mut rebuilt = *root;」（`crates/singlefs-core/src/recovery.rs:3073`），返回的是一条根不是镜像），能写出来的只有这个不动点形态，而它要一条前提「所选根之上的记录不超过在飞上限」——又是写侧的性质。② I-8.4 的原句是「任一 journal 记录被重放两次与重放一次，产生的盘上状态相同」（`.claude/kb/invariants.md:87`），「盘上状态」只有可写挂载取号之后才变；那条路上第二次恢复面对的是新实例写过行、暖机发布过的盘（「恢复本身会改盘」（`.claude/kb/decisions/16-发布语义.md:116`）），实例代号都不同，字面的等号不成立，要先定义「模掉什么之后相等」。这一层是推的，没量（要起可写挂载，不在这条腿的原型里）。

### 1.8 H7：`Recover` 不是一个函数

`replay_journal` 有三处调用：`recover`（`recovery.rs` 第 4253 行）、可写挂载读阶段（`mount.rs` 第 4361 行）、只读挂载（事实表 a1、a2 没列这一处）：「let (journal, effective_root) = replay_journal(」（`crates/singlefs-core/src/mounted_read.rs:559`）。`recover` 自己还带策略：「JournalPolicy::Ignore => Ok((JournalScanReport::default(), root)),」（`crates/singlefs-core/src/recovery.rs:4261`）不重放；`ConsultWithoutNamedVerification` 把点名验证关掉（「policy == JournalPolicy::Consult,」（`crates/singlefs-core/src/recovery.rs:4258`））。后者与自造变异 v4 等价，量过：

```

### 2.1 ①：证到的是副本，而且照样有界

- 循环：取前缀主循环的上界是在飞上限，默认环 65 536 条。符号执行要把循环展开到头，调研给的线索是展开规模直接决定挂钟（「事务大小上限 k 更大」（`research/prompts/m3-formal-r1-prior-art.md:32`））。要么把环缩小（那就是有界，与 ⑥ 同一个界），要么手写归纳不变式（那就不是 Yggdrasil 形态的「只写 spec 与实现」了）。D13 已定项 14 自己写着那个一分钟口径在本工程不成立（「三层都会绑架符号执行」（`.claude/kb/decisions/13-验证路线.md:304`））。
- 绑定：被证的是 Python 副本，与 Rust 靠对拍绑——对拍就是 ⑤ 已有的那种手段，罩到的输入是跑过的那些。副本与实现在 1.4 那种「条款没写清」的格上会悄悄不同（我照字面写的判据就与实现差了 6 144 个态），而证明对副本照样过。
- 装工具：本机没有 pip（事实表 (f)），Z3 要联网装；这一格是岔路定了之后的事，只记前置。
- 能不能 1–2 天出小原型（3 条记录、1 块盘、S = 4）：能写出来，但它量不到要紧的那个数——「与 Rust 绑得多紧」。要量它，得数副本与实现在对抗域上的不一致数，那正是 ⑥ 已经在做的事。

### 2.2 ②：桩掉 CRC 之后还剩什么

- `replay_journal` 里要算 CRC 的有三处：反向链重读前一条并解析（整条 4 096 字节的头校验和加 311 字节的链值）、点名单元（16 KiB 起）。不桩，符号字节过 CRC，调研的线索是哈希一类会不终止；桩成任意值，就进了 1.4、1.5 的对抗域——**原实现自己在 M2 上红**（残留 n=2）。所以桩必须带合约：「解得出且等于扫到的那一条」「链值等于写侧放进去的那个」「同一 jsn 只有一份内容」。这几条合约合起来就是「记录来自合法写侧」，harness 得把合法历史的生成器重写一遍当 `assume`。到这一步，Kani 探的域与 ⑥ 的合法历史域是同一个，而 ⑥ 用的是真 CRC。
- 假设写错会空真（调研 3A 已知限制一行），表 B 第 5 类那 6 条读者规则在合法写侧假设下是等价变异，Kani 证出的 M2 对它们一个字都没说。
- 入参是 `BTreeMap` 加每条记录里的 `Vec`，事实表自己写着这一格「要量了才知道」（「不桩，靠把记录条数限到很小」（`research/prompts/m3-formal-r1-facts.md:201`））；调研的线索是 5 次迭代就可能撑不住（「it's not uncommon for some proofs to scale poorly even to 5 iterations」（`research/prompts/m3-formal-r1-prior-art.md:75`））。界 4 在这截代码上够杀（1.1），所以「界太小是摆设」这一攻击**不成立**，我撤掉它；成立的是「界内这件事不装工具 143 秒就做完了」。
- 它真多出来的：整数全值域。edge 模式里我只取了 txg 顶到 u64 最大值一个点（m22、m23 是因为我想到了才杀的）；计数器 48 位回绕、事务号、序号 u32 的边界我没取，Kani 不用想到就能罩。这一维不在射程四维的字面里（载荷字节、条数 / 段数 / txg 数含环回绕、残留、槽数与设备数），算不算边际价值交主 agent 判。
- 射程第四维「槽数与设备数」住在择根与扫环（3 × S 个根槽、每盘每槽），不在 `replay_journal` 里；要罩它范围得扩到 770 行并吃进 4 096 字节的真解析，CRC 的桩法要重想。小原型（只证 M2）量不到这一维的代价。

### 2.3 ③：trace 对拍罩不罩得住崩溃中间态

- `Recover` 在只读路上是镜像的纯函数，一次恢复没有中间步骤可录：trace 只有一步（输入的抽象状态、输出落到哪一版）。trace 对拍因此退化成「拿 TLA+ 写的第二份恢复函数，对实现跑过的每个镜像算一遍、比输出」——这是差分测试，不是证明。罩到的崩溃中间态恰好是 harness 枚举并喂给实现的那些，**不比 ⑤ 多一个**；调研里 trace 验证的公开案例同样只验跑过的执行（「只对已有测试（含 13 个手写场景）产生的 trace 检查，不是任意执行」（`research/prompts/m3-formal-r1-prior-art.md:170`））。
- 模型检查那一半证的是模型：模型里的恢复函数照「整次发布施加」写，M2 近乎定义成立；而 1.2 到 1.5 打中的四件事（根段相同、少施加、读者规则、残留）全在「模型与代码之间」，模型检查碰不到。最近的公开 spec 对「崩溃时只落一个前缀」自陈没建模（「etcdraft assumes atomic persisiting of states in Read action」（`research/prompts/m3-formal-r1-prior-art.md:183`））；线索，未在本项目验证，与本工程的差异是那边的对象是共识协议、这边是单机重放。
- 量级反算（推的）：把层 0 到放量的全部崩溃状态都过一遍 trace 检查，按调研里模型检查约每分钟 10⁶ 个状态算，1.66 × 10⁹ 个镜像约 28 小时；只对固定脚本那一档做则是分钟级。哪一档进门禁决定这一格差三个量级，**这一格我记不稳定**，要量的实验：数一次层 0 重放里 `replay_journal` 被调的次数与每次的抽象状态大小。
- 抽象函数（从真镜像到 TLA+ 状态）要用 Rust 写在实现旁边，或者另写一份解析；前者让 spec 侧依赖实现的解析，后者就是 F5 说的那笔。
- 按跑前条款「说不出比 ⑤ 多罩哪一维」：对**代码**，③ 说不出；对**设计**，它多罩条数与残留，但那是仓里已有的计数模型实验那一类东西换一种语言。

### 2.4 ④：唯一的无界，但代价表里少一格

- 它是五条里唯一能给无界 M2 的（循环不变式手写，调研线索里证明对代码 2.6 到 13.3 倍）。
- 少的那一格：要让 Verus 验，`replay_journal` 得改——入参的 `BTreeMap`、`&dyn PoolReader`、迭代器链（`filter` / `sort_by_key` / `take` / `range` / `take_while`）在调研的支持表里是「部分支持」或没列（线索，未核 Verus 当前版本对 `BTreeMap` 有没有规约；没查到就得换成排序切片）。改法两种：在 `crates/` 里原地改（那就动了 M2 的承重代码，提交时要重跑层 0 与放量那批重型测试，26 亿态那一档）；或抽一份纯函数核单独验（那就又是副本加绑定，回到 ① 的问题，只是同语言）。题面六项代价（另写多少行、证到哪、跑多久、哈希怎么处理、spec 从哪来、怎么绑）里没有「动不动入库实现、动了要重跑什么」。
- 无界证明照样带 1.5、1.7 的两条前提（同 jsn 一份内容、根上记录不超上限）当可信假设；可信 spec 里还有 CRC 与读者。「证到了无界 M2」要连这四样一起读。

## 四、F2、F4、F5 的反例

**F2**
- 反例一（量过，1.4）：照条款文字手写的判据与实现第一次不一致，两边都没错，错在条款欠一句。D13 已定项 13 的计数器只有「spec 错 / 不是 spec 错」两格（「同源性要被观测」（`.claude/kb/decisions/13-验证路线.md:286`）），这一类事件没处记；照它「spec 错的次数为 0 ⇒ 同源」的读法，这种事件会把计数往「同源」推。
- 反例二（推的）：M2 在合法历史域上的声明式判据（⑥ 的 P / X）与理想模型里「由记录重建」那一处（事实表 (e)：整次发布粒度、换实例就停）是同一件事的两种写法——都是「从所选根起连续完整的发布接到哪」。「spec 写成状态谓词、model 写成转移」在这一截上分不开：恢复是一步，谓词就是那一步的后条件。同源性在这一格靠表述层面区分不了，能区分的只有「谁写的、照什么写的」。
- 反例三（推的）：② 与 ④ 的 spec 住在实现同一个 crate、同一种语言里（Rust 断言 / Verus spec 函数），写的人读着 `replay_journal` 的循环写判据，最容易把实现的读法（比如 1.4 的单调扫描）抄进 spec。⑥ 的上一条腿写判据时照了字面，才量出 6 144；照实现写就是 0，什么也看不出来。

**F4**
- 三种结局之外的第四种：**空真**。假设互相矛盾或域是空的，工具报「证明」。Kani 的 `assume`、Z3 的公理都会这样（调研：「假设写错会让证明空真」（`research/prompts/m3-formal-r1-prior-art.md:84`）；哈希无碰撞公理的先例，「后者用鸽笼原理会推出矛盾」（`research/prompts/m3-formal-r1-prior-art.md:54`））。七·5 的判别力样本只列了超时、反例、证明三份，挡不住它；要加一份「域非空」的见证（每个 harness 至少一条覆盖断言能达，或像 ⑥ 那样报 `applied_any` / `applied_multi` 这种非零计数）与一张变异表（表 A 那 27 条现成可用）。
- 第五种：**界不够而不报**。Kani 默认会报展开断言失败（调研第 75 行），但可以被开关关掉；TLC 被外面杀掉时没有「完成」行，包装脚本只看退出码就可能当通过。门禁要认的是工具自己的「完成」字样，不是退出码为 0。
- ⑥ 没有超时这一格：它的结局只有过 / 红，跑多久由界定死。C5 在它上面不成立；代价是它不是证明。

**F5**
- O3 判的是「崩溃点截断后的每个磁盘状态」，要「只照 decisions 与 invariants 的文字重新推导」（`.claude/kb/decisions/13-验证路线.md:113`）。① 的 spec 住在符号盘（未解释的映射）上、③ 的住在抽象状态上，都不读真镜像；拿它当 O3，要另写一份另一种语言的格式解析（今天 checker 那份 Rust 解析是 8 337 行，`wc -l crates/singlefs-checker/src/*.rs`；O3 只要 journal 环、根环、系统配置三样，少得多，没量）。「一份两用」省的是判据那几十行，不是解析。
- 两用的同源代价：refinement 的 spec 与 O3 成了同一份，判据写错（比如把 1.4 那句读成字面）两边一起错；同一行写着 O3「必须配阳性对照才有意义」（`.claude/kb/decisions/13-验证路线.md:113`），阳性对照可以直接用表 A 的变异加 1.4、1.5 的两类对抗输入。
- ⑥ 离 O3 有多远：判据部分（P / X / 单调读法 (ii)）就是「规约允许的集合」的可执行写法，但它是 Rust 写的、调的是实现自己的类型与 `to_bytes`，两样都违反 O3 的独立性条件；它能当的是 O3 的阳性对照库与对拍对象，不是 O3。
