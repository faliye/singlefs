### 1.2 两条「逐字有据」的读法：尝试让乙′在这一格不算输

**读法 A：套「两条以上的臂在同一格一起中，不拿来判臂」这条 carve-out。**
`_c381-r1-body.md:76`：「两条以上的臂在同一格一起中，那一格不拿来判臂，另记一笔共用前提的账。」这条 carve-out 要求「**同一格**」——同一段历史（同一个失败点 + 同一串动作 + 同一个断电点）让多条臂**一起**中。检查 `c381-r1-opus-output.md:271-282` 的原样数据：在**这一段历史本身**（下标 18、无 `Remount`、不断电）上，甲是 0/3409，乙′是 774/1669——甲在同一段历史上不中。这不满足「同一格一起中」的字面（同一段历史只有乙、乙′中，不是「两条以上的臂」）。**这条读法站不住**：carve-out 管的是同一段历史被多条臂同时踩中，不是「病根形状相似」。

**读法 B：套这一轮（r2）自己扩大过的共用账条款。**
`research/prompts/_c381-r2-background.md:81`：「落在收口表第 23′ 行那一族（**记录施加出来、根没落盘的那一版的单元进 defer**、I-3.1（已分配统计对得上） 红）的红一律归那一笔共用账，不拿来判臂。」这句话比 r1 的 carve-out 更宽，不要求「两条以上的臂」，只看红的**机理**是不是「记录施加出来、根没落盘的那一版」。这是这一轮最有希望替乙′辩护的一条，但「施加」在这份 kb 里是一个专门术语，只用来描述**恢复**（重放）时的动作，不是活着重试时写入口自己的决定：
- `.claude/kb/decisions/23-journal的角色与格式.md:25`（已定项 15 标题行）：「崩在记录持久之后、根槽持久之前，**恢复**施加什么 | 由记录重建那次发布的根……」

三处「施加」全部挂在「恢复」（`recovery.rs` 的 `replay_journal`）上，指的是**崩溃之后重放时**把记录头的新根段套进根的那个动作。乙′ 在下标 18 这一格的红，走的是**没有崩溃、没有重开**的活着重试：写入口自己判定「结局不确定」、调用方原样重发、`publish_version` 直接成功（`c381-r1-opus-output.md:274-276` 的 `first: crash_at=None actions=[Retry] steps=["uncertain(txg 5)", "ok(txg 6)"]`）——这条路径里没有任何一次 `replay_journal` 被调用，C 的记录从没被「施加」过，是写入口自己把 C 的那一版当作「正常被超越」处理、把它的单元放进 defer（`c381-r1-opus-output.md` 二节「我补的」表格乙的一行：「不确定那一版的单元在重发里被正常释放进 defer 队列」）。**这条读法也站不住**：`_c381-r2-background.md:81` 那句话字面上要求红的机理是「记录施加出来」（即恢复重放出来），乙′ 下标 18 这一格没有恢复、没有重放，够不着这句话的字面。

`.claude/kb/milestone/02-second-txn.md:335`（第 23′ 行）把「c381-r1 攻方在 HEAD 版 core 副本上用一个纯断电复现同形（……可写重开之后差 4 个槽）」与「失败之后原样重发也走得到（同一报告第五节）」并排写在同一行的「去向」列里，用了「同形」这个词——这只是**记账时把两个症状相似的问题放进同一行备忘**，不是「同一格」或「记录施加出来」这两个判臂标准的字面满足；「同形」说的是「长得像同一类账目错误」，不是「机理相同」。第一轮的判词本身已经把这两条路径分开写了（`c381-r1-main-verification.md:40`：「乙多了一条不用重开就走到那里的路」），r2 材料第一节也沿用这个区分（`_c381-r2-background.md` 第一节：「病根与收口表第 23′ 行同形」——用的还是「同形」不是「同一格」）。

## 二、K4 第二问：乙′的改法要靠什么才站得住——改 checker 还是改条款，代价多大

**结论：是改 checker，不是改条款；代价不是「免费搭车」，有一处不对称需要写清楚给用户。**

**为什么是改 checker**：I-3.1 这条不变量本身的字面（`invariants.md:123` 「已分配空间统计 == 实际遍历所有引用得到的和」）没有变过，要动的是 checker 对「有效根」这个集合的**读法**——同一行后半段自己标了「⚠️ **checker 读法（2026-09-14 用户收尾弹窗定甲）**」与「**2026-09-17 起「有效根」= 回退候选集里的根**」。这两句话本身就在说：这是一条**checker 侧的操作性定义**，由「用户收尾弹窗」这种比 kb 已定项轻一级的机制定过、并且已经改过一次（2026-09-14 定甲 → 2026-09-17 收紧），不是 D5、D16、D23 任何一条已定项的正文。要让乙′在下标 18 这一格转绿，需要再把这条「读法」扩一次——`c381-r1-opus-output.md:314`（第六节判定段）已经把两条候选修法都点出来：「I-3.1 的 checker 读法（'遍历全部有效根'没把只由记录施加出来的版本算进去），或释放代口径（C380（环上有洞时释放代判不出唯一值） 同一族：施加的记录做的释放落在一个根槽没写过的 txg 上）」——**两条都是 `crates/singlefs-checker/src/walk.rs` 或分配器释放代的实现改动，不涉及改写 D16（发布语义） 已定项 4／7 或 D23（journal 的角色与格式） 已定项 14 的字面**（这三处已定项的文字在第一节引过，都不需要动）。

**代价不对称在哪**：`_c381-r2-background.md:81` 与 `.claude/kb/milestone/02-second-txn.md:335` 都表明，这个 checker 读法缺口今天**已经**是一笔要还的共用账（第 23′ 行、第 ② 行），走「记录已落盘、根没落盘」+ 可写重开这条路径每条臂都欠。但两条路径需要的**触发条件**不一样：
- 甲 / 丙 / 丁 / 戊要走到这个缺口，需要一次**真崩溃**卡在记录已落盘、根槽没落盘之间，再来一次可写重开——`c381-r1-opus-output.md:302`「HEAD 版 core 上……一次写错都不注入……只是崩在记录与根之间」；这是层 0 崩溃点重放会随机撞到的窗口，不是日常路径。
- 乙 / 乙′走到同一个账目缺口**不需要任何断电**：一次瞬时的根槽 FUA 报错（今天实现里就是 `file.sync_data()` 报错，`crates/singlefs-core/src/block_device.rs:245-246`、`:449-450`），加一次成功的原样重试，就到了同一个缺口——这是设计里**预期会发生、要求写入口正常处理**的日常失败支路，不是小概率的断电窗口。

所以如果这个 checker 读法缺口按今天收口表的口径继续挂着不修（「等增补 1」，`c381-r1-opus-output.md:314` 末句「层 0 若只在崩溃镜像上判 checker、不在重开之后再判，就看不到它」），**选乙′ 会让这个已知缺口从「小概率崩溃窗口才暴露」变成「设计要求的正常失败支路就会暴露」**，暴露频率的量级不一样，这一点要写进交用户的岔路单里，不能只写「和其他臂一样欠着同一笔账」。若主 agent 已经决定这一轮就把 checker 读法一并修掉（不管选哪条臂都要修），那么对乙′ 来说这笔代价确实是「搭车」，不构成额外成本——但目前收口表第 23′ 行的「去向」列写的是「要三方；用例按现状钉成 12 个红」（`milestone/02-second-txn.md:335`），还没有被排进这一轮要做的事，是否顺带修不是我能替主 agent 定的。

**什么现象会推翻这一节**：主 agent 决定这一轮就修 checker 的「有效根」读法（不论选哪条臂都要做），那么「代价不对称」这一段就不成立，乙′在这一项上确实免费搭车；或者找到一条决策条款把「有效根」的读法钉死在 D5（快照 / 空间记账机制）、D16（发布语义） 或 D23（journal 的角色与格式） 的已定项正文里（而不是「用户收尾弹窗」这一级），那样「改 checker 还是改条款」这一问的答案要改成「改条款」。
