## 1. R1：「头」在树表里不是一条条目，而 `per_head` 与 E131 都把它当成一条

### 1.1 正推：第一个事务里同一个头就有两条树表条目

`.claude/kb/first-txn-layout.md:343`：

> | 树表条目 | 长度 2 + 树的种类 2 + flags 2 + 树 ID 8 + 根指针 59 + `prev_snap_txg` 8 + 诞生 txg 8 + 预留 32 | 121 | 第 1 版 5 条：(extent, 1, 5123)、(inode, 2, 5128)、(分配记录, 3, 5129)、(记账, 4, 5130)、(映射, 5, 5131)，诞生 txg 1、`prev_snap_txg` 0；树的种类的码是**预想** 1..5 | D8（核心索引结构） 已定项 8 | 已定（种类码**预想**） |

inode 树是每头一棵、会被克隆的，不是全池一棵。`.claude/kb/decisions/08-核心索引结构.md:348`：

> 出生树逐条目携带，是因为克隆头（D6（快照实现模型） 已定项 1）共享 origin 的叶，同一个内部节点里会混着出生树不同的条目。

同文件 `:381`：

> 克隆头：新头的水位 = origin 那一刻的运行时水位（含还在 write buffer 里没落盘的那条），建克隆那次发布必须为新树写出这条水位行；两个头此后各自分配，号会相交，唯一性靠 (树 ID, inode)。

⇒ 一个可写头今天至少是 **extent 树 + inode 树两条条目**（`08-核心索引结构.md:414` 说 dirent 树「随 dirent 树上线时一起立」，上线后是三条），两条都各带一份 `prev_snap_txg`、各带一份 32 字节预留。

### 1.2 反推：如果「头 = 一条条目」是对的，我应该能在格式里找到把一个头的几棵树绑在一起的东西

去找了，没找到：

- 121 字节字段表（`08-核心索引结构.md:461` 逐字「条目长度 2 + 树的种类 2 + flags 2 + 树 ID 8 + 根指针 59 + `prev_snap_txg` 8 + 诞生 txg 8 + 预留 32」）里没有「所属头」一段。
- `grep -rn "头 ID\|所属头\|head_id\|头的身份\|哪几棵树\|同一个头的\|一个头由\|组成一个头" .claude/kb` 在决策、kb 正文里零处命中（只有无关的「头宽」「块头」）。

⇒ 有两个头时，树表里有两棵 extent 树、两棵 inode 树，**哪棵 inode 树跟哪棵 extent 树是同一个头，格式说不出来**。这是 D8（核心索引结构） 已定项 8 早就有的洞，但 `per_head` 踩在它上面：

| `per_head` 要的东西 | 在「头 = 两条条目、彼此不相连」下的状态 |
|---|---|
| 材料第 0 节「头通过**自己树表条目**预留里的 8 字节树 ID 找到它的 livelist」 | 「自己树表条目」有两条，写哪条没定。三种读法格式都写得出来，而且没有条款挑：① 两条都写 ⇒ 同一棵 livelist 有两个引用方；② 只写 extent 那条 ⇒ 要新立一条「按种类选主条目」的规则；③ 每棵数据树各一棵 livelist ⇒ 每头两棵 livelist |
| livelist 装哪些块 | 头被销毁时要放掉的不只是 extent 树里的数据单元，还有 inode 树的码 3 容器、两棵树自己的码 2 节点。一棵 livelist 装两棵树的出生块，还是每树一棵，没定 |

### 1.3 这让 E131 报给用户的门槛数用错了乘数

E131 源码 `research/e7-index-bench/src/bin/e131_livelist_carrier.rs:91-92`：

```
    // 每头两棵：它的数据树（D6 已定项 1 本来就要）+ 它自己的 livelist。
    let tt_entries = heads * 2;
```

`:108-109`：

```
    // 每头一棵数据树，livelist 共用一棵。
    let tt_entries = heads + 1;
```

同一个口径也出现在 `.claude/kb/experiments/79-根记录的容量.md:28`（「7 基础树 + 8 个可写头 = 15 棵」，每头按 1 棵算）。

按第一个事务那张表重算（算术，每层 16284 / 121 = 134，全池树 3 棵：分配记录、记账、映射；**先不算快照**）：

| 口径 | `per_head` 进第二层 | `shared` 进第二层 | `per_head` 进第三层 | `shared` 进第三层 |
|---|---|---|---|---|
| E131（每头 1 棵数据树、0 棵全池树） | 68 头 | 134 头 | 8979 头 | 17956 头 |
| 每头 2 棵数据树 + 3 棵全池树，每头一棵 livelist（`3H+3` 对 `2H+4`） | **44 头** | **66 头** | 5985 头 | 8977 头 |
| 同上，但每棵数据树各一棵 livelist（`4H+3`） | **33 头** | 66 头 | 4489 头 | 8977 头 |

两个方向都要写清：
- **对 `per_head` 不利**：D6（快照实现模型） 未定项 2 给倾向时逐字写的「第二层 68 头 vs 134 头」，第一个数实际约是 **44**（或 33）。
- **对 `per_head` 有利**：两臂的比值从「减半」变成约 **2/3**（44 对 66）。
- 两臂都没算快照：D8（核心索引结构） 已定项 8 ①「快照进树表（每个快照一条条目）」，而克隆必须有 origin 快照 ⇒ 只要有一个克隆，表里就至少有一条快照条目。快照一多，第二层怎么都会进，跟 livelist 取哪种载体无关。

### 1.4 为什么这一条算 `per_head` 的，而不只是 D8（核心索引结构） 的旧账

`shared` 也要回答「key 前缀里的『头的树 ID』是哪一棵的 ID」，所以洞是两臂共有的。
但 `per_head` **多要一样东西**：头的某条条目里要有一个指针槽，而「头的条目」在格式里不存在。
用户的倾向是在「每头 2 条对每头 1+1 条」这组数上给的（`06-快照实现模型.md:160`「⇒ 真取舍只剩「点查深度 + 占容量」对「树表层数门槛」，用户正是在这个前提下给的倾向」），而那组数用错了乘数。

## 2. R2：livelist 条目的身份段是一个已被降为提示的字段

### 2.1 正推

`per_head` 的条目（材料第 0 节；`.claude/kb/experiments/131-livelist的两条载体数值与代价.md:33`）：

> | `per_head` | 每头一棵自己的树，第一次克隆时随头一起建 | 类型标签 2 + 位置条目 14（D19（块指针的结构与宽度预算） 已定项 4）+ birth txg 8 = **24** |

E130 源码 `research/e7-index-bench/src/bin/e130_livelist_bounded_destroy.rs:38` 同一个形态：

> /// 一条 livelist 条目：类型标签 2 + 物理指针 14（D19 已定项 4 的位置条目宽） + birth txg 8。

而这 14 字节的地位已经改了。`.claude/kb/decisions/19-块指针的结构与宽度预算.md:119`：

> | 位置条目（D19（块指针的结构与宽度预算） 已定项 4 的 14 字节） | **降为提示**。宽度与段划分不变，变的是它的地位——读到它可以直接去那个落点试，但它可能过期 |

同文件 `:137`：

> 1. **释放一律经映射，不经提示**（E96（混合架构的一致性） 实测：按提示解落点会误放约 5000 次 / 200 轮）。

销毁一个头时，livelist 的全部用处就是告诉释放路径「放哪些块」⇒ 它交给释放路径的必须是**映射的 key**，不是提示。而映射的 key 没定。`19-块指针的结构与宽度预算.md:104`（D19（块指针的结构与宽度预算） 未定项 6）：

> **2026-09-10 走完一轮三方，判决是「候选集与分割轴都要重开」**

同一格：

> ⚠️ **两条候选都只对码 1 有定义，而已定项 5 的射程是全部指针**：I-1.1（块头自述逻辑地址） 逐字给三类单元三种身份，**索引节点没有五元组**

第一个事务那张表里的预想值（`first-txn-layout.md:201`）：

> | key：版本身份 | **未定**，**预想** 41 | **预想按候选㈠**：五元组 33（标签 1、树 ID 1、对象 ID 1、对象出生代 1、锚点偏移 0）+ 诞生代号 8（= 1） | D19（块指针的结构与宽度预算） 未定项 6 | …

### 2.2 反推：假设「位置条目够当 livelist 的身份」是对的，那一次搬迁之后 ALLOC 与 FREE 应该还配得上对

构造（各步都是已定机制，没有引入新行为）：

1. txg 20：头 H 在落点 P 写块 b ⇒ livelist 追一条 ALLOC(P, 20)。
2. 后台整理把 b 搬到 P′：按 D19（块指针的结构与宽度预算） 已定项 5「搬迁只改这里一条条目」，只改映射；P 被放掉，之后可以再分配给别的单元。
3. H 的叶被重写，提示随之刷成 P′（`19-块指针的结构与宽度预算.md:158` 逐字「③ **提示的刷新政策**只有「随重写刷新」一种被建模过」）。
4. txg 40：H 摘掉 b 的引用，按事件流形态追一条 FREE ⇒ 手上只有提示 P′ ⇒ FREE(P′, 20)。
5. condense 按身份把 ALLOC 与 FREE 抵消，而 P ≠ P′ ⇒ **抵不掉**，ALLOC(P, 20) 留到头被销毁那天。
6. 销毁 H：拿 P 去放。按规则 1 必须走映射，而 P 不是映射的 key（候选㈠ 的 key 是五元组 + 诞生代号）；想从 P 读单元头凑五元组，而 P 在第 2 步之后可能已经是别的单元 ⇒ **要么放错块，要么放不掉**。

第 6 步那两种结局，在映射 key 取什么都成立：只要 key 不是「出生时的落点」，位置条目就当不了 livelist 的身份。而候选集里没有「出生落点」这一条，`19-块指针的结构与宽度预算.md:104` 列的是㈠㈡与代理键。

### 2.3 它推倒的是哪些数

| 用到 24 的地方 | 状态 |
|---|---|
| `per_head` 描述里的「条目 24 字节」 | 身份段取错了字段。按候选㈠ 预想：条目至少是类型 2 + key 41 = 43（`per_head` 可以省掉隐含的树 ID ⇒ 35），而且码 2 / 码 3 的 key 还没定义 |
| E131 判据 4「占容量恒 4/3」 | `shared` 多出的那 8 字节是「以头的树 ID 打头」。候选㈠ 的五元组里本来就有树 ID（livelist 条目的出生树就是那个头），重排 key 顺序就能按头分组，不必再加 8 字节 ⇒ 按预想宽度比值约 43 / 35 ≈ 1.23，不是 4/3。`per_head` 仍然更省，但省得少了 |
| E130 判据 6 `free_path_extra_bytes=24`，以及 C260（livelist 条目的预付没算进解开自己那个量） | 预付量同样随身份段变宽 |

### 2.4 为什么判据表漏了这一格

D6（快照实现模型） 未定项 2 的标题是「销毁一个可写头的第二个结构：要不要，要的话住哪、**条目长什么样**」（`06-快照实现模型.md:160`）。
材料第 1 节六格全在问「住哪」，「条目长什么样」一格都没有。按 `.claude/rules/three-way-inference.md`「被判那一项自己交代过的问题，必须各占一格」，这是判据表缺了一格。

## 3. 逐个攻击面

### 3.1 预留超订（判据 1）

**正推：排队等这块头条目空间的、有逐字出处、今天没分配的需求**

| 需求 | 字节 | 逐字出处 | 自己写了别的出路吗 |

| 快照谱系嵌套区间标号 | 16 | 同段「② **快照谱系的嵌套区间标号 16 字节**」（C144） | 已算进认购的 24 |

| `prev_snap_txg` 父链要补的树 ID | 8 | `checks-owed.md:264`（C250）「要么给 `prev_snap_txg` 补上树 ID 那一半（动 D8（核心索引结构） 已定项 8 的字段表，条目 121 → 129），要么写明父链解析不走它、另有载体」 | 有：它自己写的就是加宽 |

那 32 字节就是给这类字段留的。`checks-owed.md:154`（C148）：「那 32 字节预留是**给将来未命名的字段留的**，诞生 txg 与 `prev_snap_txg` 是已命名字段、不占预留」。

合计：已点名的每头条目空间需求是 16 + 8 + 8（livelist 指针）+ 8（C143 候选一）+ 8（C250 出路一），再加 kb 正文版本的计数 8，共 **48 到 56 字节，而预留是 32**。

**反推：判据 1 要求「只能住这块预留」**。上表里每一项都有别的出路（C143 可以改 D23（journal 的角色与格式），C250 自己写的是加宽；条目本来就带长度，见 `08-核心索引结构.md:469` ④）。
⇒ **按字面，判据 1 不触发**，而且任何一项都触发不了它（见 3.6）。

实质上：`per_head` 拿走那 8 字节之后，C143 的候选一、C250 的出路一都只剩「加宽 D8（核心索引结构） 已定项 8」一条路（用户定案的 121 字节）。加宽到 129 时每层 16284 / 129 = 126 棵，到 137 时 118 棵。
**但这笔账不能记在 `per_head` 头上**：按 `06-快照实现模型.md:160`，`shared` 也要吃同样那 8 字节放它每头的计数。材料写的「触发时判谁输：`per_head` 输」与 kb 正文对不上。

另外，按 R1，每头的预留可能是**两条条目各 32**，判据 1 的前提（「头的树表条目」只有一条）本身就不成立，方向是**对 `per_head` 有利**。

### 3.2 两棵树的原子性（判据 2）

**创建的原子性：不触发。**树表只经一条根记录发布。`22-单元原子性怎么合成.md:464`：「**根记录恒走间接层：固定头 + 一条指向「树表单元」的指针，树根一律住树表单元，不平铺进根槽。**」`:586`：「**树表的权威在根记录**」。
⇒ 同一个 checkpoint 里建的头条目与 livelist 条目，要么随那一次根槽 FUA 一起可见，要么都不可见，不管树表有几层。我构造不出一个靠崩溃把两者拆开的已发布镜像。

**字面红条件：触发，但触发它的不是原子性。**判据 2 的红条件是「构造一个已发布镜像：头树在而它的 livelist 树不在（或反过来），且没有任何已定条款把它判为非法」。

- **镜像甲：mkfs 建的头。**`first-txn-layout.md:345`：「| 销毁可写头的第二个结构（livelist 一类） | 0 | **预想**：第一次克隆时惰性创建，第一个事务不写它、不占树表条目 |」。mkfs 建的那个头不是克隆出来的 ⇒ 按 `per_head` 自己的描述，从第一个事务起到第一次克隆之前的每一个镜像里，都是「头在，livelist 不在」。没有条款说这不合法，因为这正是设计本身。
- **镜像乙：快照复制了头条目。**头 H 打快照 S 时，S 的新条目若照抄 H 的条目（根指针、预留），S 的槽就也指向 L ⇒ 一棵 livelist 两个引用方。反过来，照 D5（快照 / 空间记账机制） 的 deadlist 交接形态（`05-快照-空间记账机制.md:8`「建快照时把**活头的 deadlist 整个交接给新快照**，活头换一个空的」）去做 ⇒ 只读快照拥有 livelist，与「每个可写头……一棵」对不上。「头留着 / 交给快照 / 两边都指」三种状态格式都写得出来，没有条款挑。

**这个判据恒触发，不区分载体。**「没有任何已定条款把它判为非法」对 livelist 恒真：`grep -rn livelist .claude/kb/invariants.md` 零命中，`06-快照实现模型.md:160` 立项时自己也写「`livelist` 在 checks-owed.md / first-txn-layout.md / invariants.md / verification-build.md 里各出现 0 次」。`shared` 也有对应的形态（已销毁头留下的孤儿 key 前缀）。

`per_head` 独有的，是树表条目之间的一组引用约束，今天一条都没有：槽值 ≠ 0 ⇒ 存在那个树 ID 的条目，且种类是 livelist；一棵 livelist 只有一个引用方；每棵 livelist 要么有头引用、要么有意图记录引用。

**给主 agent 的判法建议**：若判据 2 本意是问创建的原子性 ⇒ 不触发。若照字面 ⇒ 触发，但它打的是「哪些头有 livelist、从什么时候起有」这个定义缺口（R4），不是原子性。这一格我不建议记成一记干净的打穿。

### 3.3 派生态还是权威态（判据 3）：不触发，livelist 是派生态

**正推。**condense 之后，livelist 的内容就是 {头 H 可达、且出生晚于边界的块}：
- 可达性来自根，即树表条目里 H 的根指针（`21-权威态与派生态的分界.md:10`：「根」这一格含树表单元）。
- 每块的 birth 来自单元头。`19-块指针的结构与宽度预算.md:138`：「**单元头或提示必须带块 birth** —— **今天已满足**：D18（块里携带什么信息） 已定项 7 的数据单元类身份段本来就含诞生代号 8 字节」。
- 边界：取 `prev_snap_txg` 就在 H 的条目里；取建克隆的时刻，就是 livelist 树自己那条条目的「诞生 txg」（`08-核心索引结构.md:463` ① 的口径：「**快照完成（发布）那一次 checkpoint 的 txg**」）。
- 边界到底取哪个，是 C265（销毁可写头的释放边界写成了固定的克隆时刻） 的问题，本轮同一轮的正推腿已经打出来了（`checks-owed.md:279`），我不重复计。取哪个都在根里，所以不影响「可重建」这个结论。

**FREE 记录只是编码痕迹。**出生晚于边界的块被摘掉时，FREE 与对应的 ALLOC 抵消，块本身进 defer 队列，不再从 H 可达，重建结果里本来就没有它。出生不晚于边界的块被摘掉时，按 D5（快照 / 空间记账机制） 的判定进 deadlist，不进 livelist。所以不存在「只能从 livelist 自己拿到」的信息。

**反推：**假如它是权威态，丢掉 livelist 之后读者应该拿到错答案。实际上丢了之后，从 H 按边界遍历一遍就能重建，遍历属 `.claude/rules/fs-design.md` 第三格。读者拿到的是正确答案，只是慢了。

**判据 3 的红条件本身有缺陷。**它问「有没有一类信息只能来自 livelist 自己、从单元 / 记账 / 根都重建不出来 ⇒ 第四类权威态」，用的是**字节口径**，而这个口径已被用户定案否掉。`21-权威态与派生态的分界.md:24`：「⚠️ **「能不能重算」问的是语义，不是字节**（2026-09-09 用户定案 + 三方论证）」；`:34`：「⇒ **「算不回来」不等于「要进权威态」**，中间隔着「这个值今天还有没有消费者、重建不出时是答错还是保守」」；`:36`：「⚠️ **被这条定案否掉的是「按字节判」**」。
⇒ 就算有一类信息算不回来，也要先问「算不回来时读者拿到保守答案还是错答案」。保守 ⇒ 仍是派生态；错 ⇒ 要么逐出，要么进权威态。材料第 1 节写的「⇒ 第四类权威态、甲输」跳过了这一步。这就是 C263（判据表的判红条件里嵌了没核过的前提） 那一类缺陷。

派生态身份带来一条要还的义务：`21-权威态与派生态的分界.md:50` 起那一节要求派生态的损坏必须可检出。好在独立审计路径现成（遍历 H 按边界过滤，再和 livelist 比），D6（快照实现模型） 判据 2 那一半有着落。

### 3.4 第一个事务的字节（判据 4）：不触发

判据 4 的红条件是「答『不翻』而说不出第一个事务里哪个字节因 `per_head` 而不同」。我说得出：

- **未定期间，「是」仍然成立。**`06-快照实现模型.md:160` 的依据是「甲若取『自成一棵树、day-1 注册进树表』……取『第一次克隆时惰性创建』则一个字节都不写」，候选集里还同时有这两种形态，这句话就是对的。
- **定成 `per_head` + 惰性之后，能不能翻成「否」，取决于一件 `per_head` 没说的事：mkfs 建的那个头要不要 livelist。**
  - 要，理由有三条：D5（快照 / 空间记账机制） 只说克隆（`05-快照-空间记账机制.md:156`「要释放的是 `birth > origin.txg` 的那批块」），但全仓没有条款禁止销毁 mkfs 头（C265 现查过「没有「有快照的可写头不许销毁」这类条款」）；乙 已出局（`06-快照实现模型.md:160`「乙 在写意图那一刻给不出这个数……能当上界用的每树字节总量是已定项 4 第 8 / 9 项，2026-09-06 已撤回」）；所以 mkfs 头被销毁时只能靠 livelist。
  - 若它从第一个事务就有 livelist，第一个事务里会变的字节：
    ① `first-txn-layout.md:343` 树表条目 5 条 → 6 条，多 121 字节，多一条种类为 livelist 的条目；
    ② §七 的「树 ID 水位 | 8 | mkfs 1，发布后 6」→ 发布后 7；
    ③ mkfs 头某一条条目预留里那 8 字节从 0 变成 6，写 extent 1 还是 inode 2 那一条，就是 R1 那一问；
    ④ 可能还要一个空根。livelist 树的空根政策没定，唯一的先例是 inode 树「根恒为码 2……哪怕树是空的」（`08-核心索引结构.md` inode 树字段表那一行）。
  - 不要 ⇒ 这一格翻成「否」。但那需要一条今天不存在的条款，说明「非克隆头不经 livelist 销毁」，或者「不许销毁」。

外部线索（只用来提假设，不当证据；未在本项目验证）：ZFS 只给克隆建 livelist，见 `fs-refs/zfs/module/zfs/dsl_dataset.c:1333-1344`（`if (origin != NULL && spa_feature_is_enabled(dp->dp_spa, SPA_FEATURE_LIVELIST))`）；也不许销毁有自己快照的头，见 `dsl_destroy.c:717`「Can't delete a head dataset if there are snapshots of it.」。
**与本项目的已知差异**：本仓没有「有快照的头不许销毁」这条（C265），乙 也已出局，所以 ZFS 靠这两条回避掉的非克隆头、带快照头这两格，本仓都还空着。

### 3.5 deadlist 对称（判据 6）：第二个分支被逼出

**构造**：livelist 每头一棵树；deadlist 放在另一种载体，一棵共享树，key 以 deadlist 的归属打头。

1. **交接必须是 O(1)**：D6（快照实现模型） 判据 4（有界创建）要求建快照「代价不随规模增长」，而 D5（快照 / 空间记账机制） 要求建快照时把活头的 deadlist 整个交给快照。共享树若按树 ID 分组，交接就要改写全部条目的 key，是 O(deadlist)。
   ⇒ 必须用一个间接 ID，每条头条目、每条快照条目各一个槽（就是 C145 那 8 字节），交接时改槽，不动条目。
2. **快照销毁也要批前预留**：D6（快照实现模型） 未定项 2 判 乙 出局用的理由是「写意图那一刻，D3（空间分配） 的准入不等式逐字含 `− 待删占用`」，这条同样作用在销毁快照（合并 deadlist）的写意图上。
   ⇒ 写意图那一刻要有「这份 deadlist 多大」。共享树里只能按前缀范围数，这正是 E131 判据 5 给 `shared` 那条臂记的缺陷。不想范围数，就要存一个计数。
3. **计数存在哪**：deadlist 属于活头的那段时间里，计数随每次摘除递增，只能跟着头条目走；交接时再抄进快照条目。
   ⇒ 头条目要放的东西：deadlist 间接 ID 8 + 区间标号 16 + livelist 树 ID 8 + deadlist 计数 8 = **40 > 32**。
4. **在 D8（核心索引结构） 已定项 8 的 121 字节里放不下。**不加宽的出路只剩两条：把 deadlist 计数放进记账，做成带树维的统计量，这要重开 2026-09-06 撤回每树字节统计量的那次定案；或者让 deadlist 也做成每份一棵树，计数放它自己那条条目。

⇒ **判据 6 走的是第二个分支：「deadlist 必须同载体」被逼出来了**，没有打出一个根本表达不了的状态。

**这条约束与 livelist 取哪种载体无关**：`shared` 也要在头条目里放每头的 livelist 计数（`06-快照实现模型.md:160`），头条目同样是 8 + 16 + 8 + 8 = 40。所以它不判 `per_head` 输。

它的代价 E131 没算：deadlist 做成每份一棵树之后，每个头多一条 deadlist 条目，每次建快照还要给活头新建一棵空 deadlist（多一条条目）。按 R1 的口径，`per_head` 每头约 4 条（数据树 2 + livelist 1 + deadlist 1），每个快照约 3 条。「狂暴」那笔树表代价比给用户看的那组数大。

**要核的推论**：第 2 步「销毁快照写意图时要 deadlist 的规模」是我从 D6（快照实现模型） 未定项 2 判 乙 的那句理由平移过来的，没跑实验。D6（快照实现模型） 判据表第 5 行自己也写了，D5（快照 / 空间记账机制） 在有界销毁这一格是「用『分叉点快照不许销毁』这条功能缺失回避掉的，不是满足」。主 agent 核的时候要判：这条平移成立，还是销毁快照另有预留口径。

## 5. 边注：不算命中，方向对 `per_head` 有利
