## 2 Q1：谁、什么时候跑整轮清扫

先排掉推得出的出局项，再列剩下的候选。

| 候选 | 与 K1–K14 合不合 | 合法崩溃历史上的结局 | 多写 / 多判 |
|---|---|---|---|
| A 挂载开头、取号之前跑整轮并发清扫发布 | 不合。K4 取号之后才动单元，清扫发布要新实例代号（作废一个 checkpoint 必须换实例代号，`.claude/kb/decisions/18-块里携带什么信息.md:315`）；而且崩溃实例 j 的行 (j,0,0) 是本次写行才写的（「严格介于所选根的实例与新实例之间的实例写 (i, 0, 0)」，`.claude/kb/decisions/18-块里携带什么信息.md:309`），取号前表里没有 j 的行，j 的单元对所选根的表按「i > i_now ⇒ 判损坏」读（同 312 行），判不成「未发布」 | 推出：j 的单元取号前判不了，行删不掉 | — |
| B 写行发布之后、暖机之前，同在 `establish_instance` | 合。清扫发布是新实例第二次发布；它落一个根环槽，要并进暖机的覆盖计划（「新实例在本实例写成（FUA 返回）的根覆盖两块盘之前，不让任何 fsync 返回」，`.claude/kb/decisions/16-发布语义.md:199`）与取号前预演（`crates/singlefs-core/src/mount.rs:4180` 的「取号之后要发的那一串（写行一次、暖机那几次）在取号之前整串预演一遍」） | 同 C；多一处风险：暖机计划 `warm_up_publish_txgs`（`crates/singlefs-core/src/mount.rs:3340`）按 `first_txg` 往后推，插进一次清扫发布就要重算，两处各算各的是它自己注释点过的毛病 | 预演要多算一次清扫发布；改 `warm_up_publish_txgs` 与预演两处 |
| C 暖机与抬 F 之后、挂载续做之前或之后、交回之前 | 合，且有先例（K12：续做在写行与暖机之后、交回之前、不进取号前预演）。不改暖机计划，txg 接在现行那一版后面（`let mut current = row_publish.clone();`，`crates/singlefs-core/src/mount.rs:4376` 之后的 `current`） | 崩溃实例 j 的行在本次挂载写行之后表里就有 (j,0,0)，j 的单元（若没被本次挂载自己的分配盖掉）判「未发布」，同一次挂载里可抹、可删。D18 射程写的「下一次挂载取号之前删不掉……再下一次挂载才删得掉」（`.claude/kb/decisions/18-块里携带什么信息.md:326`）的两挂载延迟在 C 下缩成一次 | 挂载多一趟全池只读扫描，延迟随池容量涨；条款里没有挂载时间上限（`grep -rn '挂载时间\|挂载耗时' .claude/kb/decisions/*.md` 无命中，本报告 §Q1 末尾复跑） |
| D 会话里的显式入口（后台 / 管理员调用，不绑挂载） | 合第三格：「后台、可续做、非决策路径」（`.claude/rules/fs-design.md:25`）无戒律；删行结果不被任何即时判定需要。第一版串行提交，入口可在两次用户改动之间同步跑。K8 说进度不持久化，所以也不需要意图 | 没人调用时行只增（C597 的原题；每 369 行预留多一片，`.claude/kb/decisions/28-挂载期承诺量.md:89` 的式子里 `rows0` 随行数涨） | 需要一个新入口，抹头与分配器 overlay 的互斥（K7）要在入口里持锁 |

Q1 结论（只写推得出的）：A 出局（推得出）。B、C、D 都合得上已定落点，B 比 C 多改两处计划，C 有现成先例，D 与 K8 / 第三格最合但不自带触发。
「每次挂载都跑还是行数到阈值才跑」条款没写：整轮是全池读，频率不是 K1–K14 能推出的，**推不出**；我能给的只有数：写行每挂载一行；
根环 24 槽、暖机每挂载至少占 2 槽（「24 槽的根环 8 次挂载就整圈转完」，`.claude/kb/decisions/16-发布语义.md:207`），所以正常卸载的实例的行要等它的根全部滚出环才删得掉（K1 之外 I-3.8 的「根环里没有该实例发布的根」，`.claude/kb/invariants.md:150` 的「行只在回收条件成立后删」），
每次挂载一般能删的只有从没发布过根的崩溃实例的行。

## 3 Q2：「抹头」抹哪些落点、写什么字节、崩一半怎么认

可抹的落点集合先由 K2、K6、K7 夹出来，三条合起来是：该槽的头自证过，且判成「待删行那个实例的未发布单元」，且不被账占用（含 32 KiB 单元的第二个槽），
且不在分配器在飞的 overlay 里，且不在影子账的隔离集里（K6）。后面三个条件在抹之前、抹的那一刻各查一次（扫描到抹之间本挂载自己的写行 / 暖机发布会分配新槽，
空闲图里没有条目的孤儿槽是可分配的，所以会被盖掉；这正是 D18 射程那句「那次挂载的写行把 j 的单元全盖掉」（`.claude/kb/decisions/18-块里携带什么信息.md:326`）的机理）。

写什么字节的候选：

| 候选 | 与 K1 / K13 | 崩在一半的结局 | 写量 |
|---|---|---|---|
| 2a 只把单元起点处的头所在的一个物理块写零。用 `write_at` + `ForceUnitAccess` + 零缓冲，长度取探测到的物理块宽（≥ 512） | 合。K1 要「FUA 返回」，`write_zeroes_at` 没有 FUA 参数，其注释自述「清零永远是普通写」（`crates/singlefs-core/src/block_device.rs:133`），所以不用它。三类头都落在首个 512 字节扇区里：数据单元头 105、打包记录头 107、含预留位各加 29（`crates/singlefs-format/src/lib.rs:35`、`crates/singlefs-format/src/lib.rs:41`、`crates/singlefs-format/src/lib.rs:32`），码 2 头 86 + 2 × key 宽（`crates/singlefs-core/src/unit.rs:129`；合法 key 宽 ≤ 24，头 ≤ 163）；K13 扇区原子 ⇒ 这一写要么老头完整、要么魔数所在的扇区是零 | 每个头只有「老头」「零」两态。老头仍在 ⇒ 下一轮还判未发布、再抹（幂等）；零 ⇒ 判无头 | 每个被抹单元每份副本一个物理块；每块被抹的盘各发一道屏障（`barrier` 按块设备各发，`crates/singlefs-core/src/block_device.rs:142`；K1 的「一道屏障」是全池一道还是逐盘各一道，条款没写，我按逐盘读，推的） |
| 2b 整单元写零（16 / 32 KiB） | 要一个带 FUA 的清零变体，否则与 K1 字面冲突；K13 说屏障之间可重排，头所在扇区可能没落而后面的零落了 ⇒ 老头 + 零载荷，仍判「有头、未发布」，下一轮重抹 | 与 2a 相同的两态，没有更好 | 16–32 倍于 2a，无收益 |
| 2c 写一个「已抹」标记头（有效魔数 + 新类别或标志位） | 要在 D18 值域登记表加类（「新增单元类 ⇒ incompat」，`.claude/kb/decisions/18-块里携带什么信息.md:320`），买到的是把「已抹头」与「已被覆盖」分开；K2 明写这两种「说不出它原来属于谁」，不需要分开 | — | 格式改动，不推出需求 ⇒ 出局（无必要，不是冲突） |

「两份都抹」不是单独一句规则：K2 的「池中每一个落点」里每块盘上的每个槽是各自的落点，两份副本各判各抹。
推得出的只有 2a 与 2b 在崩溃结局上等价，2a 写得少；2c 无必要。

「已抹头」「已被覆盖」两种判定怎么从盘上读：读成功后只分两类。
头自证过（魔数 + 头校验和，`parse_packed_unit` 在 `crates/singlefs-core/src/unit.rs:461`；码 2 另有自己的解析）⇒ 有头，按行判，包括被后来的单元覆盖了的槽（那个头属于另一个单元）；
头自证不过（全零、杂物、半个头）⇒ 无头。盘上只有这两类，「抹头」与「覆盖」在盘上分不开，K2 也说不需要分。
无头里也有位腐蚀的真头，对删行没有影响：删行只会让「未发布」变「已发布」，无头的槽没有可被扫描重建认领的头。
读失败（`PoolReader::read` 返回 None）是第三种，不是无头：K2 的「读不到不等于不存在，扇区维」（`.claude/kb/decisions/18-块里携带什么信息.md:313`）要求这一轮任何行都不删。

**条款缺口（给主 agent）**：K7 的「孤儿（没有条目）」若按「起点槽键查分配记录」读，32 KiB 单元的第二个槽没有自己的键
（「一条记录记一个单元，跨度段说它覆盖几个槽」，`.claude/kb/decisions/03-空间分配.md:128`），会把活数据单元的后半槽当孤儿。
后半槽里出现魔数加过校验和的字节串并不需要恶意：把本池的镜像或快照放进池里的一个文件，内容就可能对齐成一个合法头。
所以「没有条目」必须读成「不被任何条目的跨度覆盖」（等价于分配器空闲图里该槽空闲），这一句条款没写，我推不出它的措辞，只给读法。

推翻 Q2：若盘上存在头 > 512 字节的合法单元（key 宽超 24 的码 2 节点），2a 的原子性前提不成立，要改成「先抹魔数所在扇区」并另论；若 2a 的老头在 FUA 返回后仍可被读回，说明接口没有兑现 FUA。

## 4 Q3：「读成功并按行判」比哪个字段；被账引用的落点算不算；被抛弃时间线的单元

字段（行是 (i, Ti, Wi)；单元头给写序实例 i 与诞生代号 b，码 1 另有事务号 n）：

| 候选 | 判 | 结局 |
|---|---|---|
| 3a 照 K5 逐字：码 1 判「未发布」⟺ ¬(b ≤ Ti ∨ n ≤ Wi)，码 2 / 3 ⟺ ¬(b ≤ Ti)；无行的 i < i_now 已发布；i == i_now 是当前实例，不属任何待删行；i > i_now 条款只写「判损坏」 | 合 K5、K7 | 唯一不出局的字段读法。i > i_now（池里有比挂载根更新的实例的单元）清扫怎么办条款没写：保守读法是这一轮任何行都不删并报，**推不出**条款 |
| 3b 只比 b 与 Ti，不看 W | 与 K5 的 `n ≤ W` 一支冲突 | 出局。反例：实例切换写的行 (k, k 最后发布的 txg, 被照旧事务的最大号)，「号 ≤ W 的事务照旧」（`.claude/kb/decisions/23-journal的角色与格式.md:400`）；这些事务的数据单元 b > Ti 但已发布。3b 把它们判未发布并抹头，抹掉的是被重发的 checkpoint 引用的活数据 |
| 3c 只比写序实例（行存在 ⇒ 该实例全部单元未发布） | 与 K5 的 b ≤ T_pub 冲突 | 出局。抹掉 b ≤ Ti 的已发布单元 |

被当前账引用的落点：

## 5 Q4：专用清扫发布的形状

先说一处**条款内部的张力**（给主 agent）：D18 写行一条写着「新实例的每一个根引用的实例表都已含 [max(所选根的实例, 1), 新实例) 的行」（`.claude/kb/decisions/18-块里携带什么信息.md:308`），
而 K1 的清扫发布恰是新实例的一个根、引用的表删掉了其中一些行。字面读两句不能同时成立；要么 308 行那句加「除被清扫发布删去的」，要么清扫发布不算「新实例的根」。条款怎么改是用户的事，我只标出来。

发布的形状（实现里「改什么」）：

- 记录与点名项：事务号 0、提交标记 1、不进 W、不推进实例内计数，与空发布、回退发布同形（「事务号 0 保留给不承载事务的记录，提交标记写 1」，`.claude/kb/decisions/23-journal的角色与格式.md:518`；
  「回退那次发布的记录事务号取 0、不推进实例内计数」，`.claude/kb/decisions/23-journal的角色与格式.md:386`）。点名项照写行那次发布在带文件版本上的形状：重写后的实例表链各片加固定点单元。
  不需要新记录类型或新字段：新根段已带实例表指针（`pub new_instance_table: NodePointer,`，`crates/singlefs-core/src/journal.rs:166`）。
- 改 `crates/singlefs-core/src/mount.rs`：加一个与 `instance_table_rewrite_of_the_row_publish`（1130 行）并列的函数，行集合 = 现行表的行减去待删的行（那一个函数是 `rows.extend_from_slice(rows_written);`，1135 行），
  被换下的 = 现行整条链；计划沿用写行那次发布的 `instance_table: InstanceTablePlan::Rewrite(instance_table),`（3029 行），txg 与计数器接在 `current` 后面；
  行数变少时片数 = `instance_table_pages_for_rows`（`crates/singlefs-core/src/instance_table.rs:122`），不会比旧链多。
- 准入。候选 4α 不判式子，落点那一判照判；4β 判式子。K9 的判据是性质不是名单：「没有普通分配的发布（空发布、写行、暖机、抬 F）不判」（`.claude/kb/decisions/28-挂载期承诺量.md:36`）。
  清扫发布只 COW 实例表链与固定点单元，没有普通分配，落在「不判」那一类 ⇒ 4β 与 K9 的判据冲突，出局；4α 推得出。
  落点那一判被拒（空间不够）的处置照 K12 的先例：「挂载续做走空时删除类发布被落点那一判以空间拒，同样推抬 F 再试」「推满仍放不下时挂载照样交回可写、队列留着」（都在 `.claude/kb/decisions/08-核心索引结构.md:463`）。
  对清扫而言「放弃这一轮」是安全的（行留着、已抹的留着，见 Q5），所以安全性不依赖预留够不够，只有活性依赖。
- 走哪份预留：推得出的只有两层。链重写量不超过一次切换预留里的链重写项（「副本数 × 32768 × max(1, ⌈(rows0 + N_switch) / 每片行数⌉) 字节」，`.claude/kb/decisions/28-挂载期承诺量.md:89`，行数只减不增）；
  固定点单元走 checkpoint 保留池（「它保证 checkpoint 自己的固定点写得出去」，`.claude/kb/decisions/28-挂载期承诺量.md:26`）。
  暖机项只留了 R = 3 次空发布的位置，第一版实付 2 次（`.claude/kb/decisions/16-发布语义.md:199`）：第一版两盘时每份预留多出一个 c_max 刚好够一次清扫发布；暖机用到 3 次（白推）或盘数增加时没有这个空余。
  所以「清扫发布单列一份预留」与「借暖机的空余」两个候选**推不出**取哪个，只知道后者在第一版几何下够、在别的几何下不够。
- 一次删一行还是满足条件的全部行：候选 4a 全部一次，4b 一次一行。K2 的判定对整轮做，之后对每行同样成立，两者都合。
  差别是代价：一次发布占一个根环槽并把旧根更早挤出环（「空发布占根环槽位，把旧的非空根更早挤出环」，`.claude/kb/decisions/16-发布语义.md:205`），
  每次发布整条链 COW（「每次写行 COW 重写整条链」，`.claude/kb/decisions/18-块里携带什么信息.md:308`）。4b 删 k 行多 k − 1 次发布、k − 1 个根环槽、k − 1 套固定点与链重写。
  一次发布整体施加或整体不施加（`.claude/kb/decisions/23-journal的角色与格式.md:363`），4a 的原子性不弱于 4b。⇒ 4a 推得出更省，没有它更差的崩溃结局。
- 没有可删的行时不抹头、不发清扫发布，零写。只对「行满足 K1 全部条件」的实例抹它的未发布单元（最小抹量）；对不满足条件的行的垃圾，抹不抹归 D3 的垃圾清扫（K7），这一轮不涉及，推的。

推翻 Q4：若 `publish_version` 对 `InstanceTablePlan::Rewrite` 且 `file: None` 的计划在带文件版本上拒绝或要求事务号非 0（今天只有写行发布走 `file: None` 加 `Rewrite` 这一形，3029 行；没读到拒绝，但也没有第二个调用方）；
