1. A workload writes small files repeatedly in a pattern that creates new fragments faster than defragmentation can consolidate them. Defragmentation starts when fragmentation ratio exceeds high threshold. It requests space for a batch but the pool is full due to high allocated and pending deletion from continuous writes. Defragmentation stalls due to insufficient available space. New writes continue, keeping fragmentation ratio above high threshold and empty cluster segments below low threshold. Unreclaimable bytes remain high. Defragmentation keeps attempting to run but cannot proceed, never dropping watermarks below low thresholds. User observes persistent write stalls and zero defragmentation progress despite constant background attempts.

2. The allocator may place new writes inside region R while the intent is open. No on-disk field exists to mark R as closed during intent processing. When new data is written to R after the intent record is created but before processing completes, the intent target state (clear region R) becomes impossible to achieve. The defragmentation process must now move both original and new data, but the intent’s target state requires R to be empty. Since new writes continuously fill R, the intent never completes. This violates idempotence as the target state cannot be reached due to concurrent writes.

3. A stripe width of three devices holds a partially dead stripe. To free it, the filesystem must rewrite good blocks to new space. All available space is allocated. Deletion requires rewriting but cannot allocate space. Defragmentation cannot run because it needs space to move data. The pool is stuck: deletion cannot free space, defragmentation cannot run. Permanent reserve size must equal the largest stripe size (e.g., 1MB). This reserve belongs to the "capacity" term in the admission rule, subtracted before other calculations. Smallest change: add a fixed reserved capacity value to the admission rule, ensuring space is always available for defragmentation operations.
