Deadlist entry format in a copy-on-write filesystem design with snapshots and clones, round 3.

Answer in English. Do not use any markdown emphasis: no bold, no italics, no headings with asterisks. Use plain numbered answers.

Facts from the design (treat them as given):

F1. Every block carries a birth txg: the checkpoint number in which it was published. When a writable head drops a block: if birth > the head's previous_snapshot_txg (the txg of its latest snapshot), the block is freed immediately; otherwise it is appended to the head's own deadlist. Creating a snapshot hands the head's whole deadlist to the new snapshot and gives the head an empty one. Destroying snapshot S merges S's deadlist into the next newer side and frees the entries with birth > prev(S).txg, where prev(S) is the snapshot before S. prev is inherited by the side that absorbs S; if it were not inherited, entries with small birth would never be freed. No full-disk scan.
F2. Block b is referenced by snapshot S if and only if birth(b) <= S.txg < death(b). Moving a block during background defragmentation does not change its birth.
F3. Only the destroy cascade rewrites a published snapshot's deadlist.
F4. The deadlist is one tree for the whole pool (one keyspace), registered in the tree table from day one.
F5. Entries record the version identity of a block (its central mapping key), not its location, and use the same key as the sparse side table. Birth must be available inline so the destroy filter stays O(1) per entry.
F6. Central mapping key: 27 bytes (the 25-byte forms are zero-padded to 27).
F7. Livelist precedent: one shared tree; entry key = head tree ID 8 + central mapping key 27 + event type 1 = 36 bytes; empty value; a head's entries are removed by a prefix range delete.
F8. A tree table entry has 24 reserved bytes. When the reserve was sized, two claimants were named: a deadlist location of 8 bytes and snapshot lineage nested-interval labels of 16 bytes; 8 + 16 = 24 exactly; neither was made a field. Later, 8 bytes were cut from a 32-byte reserve to store a head ID, leaving these 24.
F9. previous_snapshot_txg is one per head and lives in the tree table entry (8 bytes). A new clone's previous_snapshot_txg starts at its origin snapshot's txg. Each writable head holds one previous_snapshot_txg and one deadlist. Tree IDs strictly increase in creation order and are never reissued after a crash.
F10. A check that prev is inherited correctly during the destroy cascade is still owed.
F11. Freeing always goes through the central mapping, never through location hints.
F12. Creating two snapshots in the same checkpoint is allowed: they capture the same state and the deadlist between them is empty; to find "the previous snapshot" a checker breaks ties by (txg, snapshot id).
F13. Two design texts disagree on whether a snapshot's tree table entry carries previous_snapshot_txg: one says only the head's inode tree entry carries it and all other entries write 0; the other says it is defined for head entries and snapshot entries alike. This round assumes the second reading.
F14. Claimants for the 24 reserved bytes: deadlist location 8; lineage labels 16; a per-head livelist entry counter 8 (its text says it can only live in "the last 8 reserved bytes", written before the head ID cut); a per-head count of live snapshots for a destroy guard (no width given); an inode number watermark 8 from another open question.
F15. An invariant says: if block b is not referenced by the live head, b appears in exactly one deadlist. Its scope note excludes blocks shared across heads (sparse side table count > 1). The sparse side table is maintained at commit and is read to decide whether a cross-head shared block is dead; how the drop path reads it is not written.
F16. Bulk deletes use an intent: write the intent, then do the work in batches, resumable after a crash. While an intent is unfinished, every other invariant still holds, and the intent describes only the target state.
F17. Unbounded deletes run as an intent: write the intent, then work in batches, resumable. The structures waiting for deletion (intent keys, the pending-delete queue) count as live references, so a block's death is the checkpoint of the physical batch.
F18. Intents are idempotent and describe only the target state; after a crash there are three possible states and the intent is resumed; the intent is deleted in the same transaction as the last batch. Nothing says in which order two unfinished intents run.
F19. A snapshot with more than one child may not be destroyed; the check is an O(1) counter of children that also counts clone heads made from that snapshot. The tree table entry has no field for this counter.
F20. Filtering by "clone time" needs a fixed field; the tree table entry has none, and there is no field linking a clone head to its origin snapshot.

Rounds 1 and 2 found: the original point reading of C over-frees when two snapshots are taken in one checkpoint. C-interval over-frees when the destroy cascade runs in batches and its intent records the head's range as [S.txg, infinity): a snapshot taken, and a block dropped, while the cascade is unfinished fall into that range. With an upper bound in the intent it was not broken. B and C-prime leak when two cascades on one lineage run out of order; they are clean in order. Passing prev only at the last batch breaks all three. A head-destroy intent that runs ahead of an earlier cascade on the same head leaks in all three. C-prime needs an O(1) way to know the tree ID of the head's latest snapshot at drop time; the on-disk fields give only a txg.

Shared rules for every candidate: a destroyed snapshot stops counting as a live reference when its intent is written, and prev is passed to the next newer side in that same transaction; a head-destroy intent waits for earlier cascade intents on the same head; the invariants in F15 are checked after removing the entries an unfinished intent will free.

Candidates:
C-interval with upper bound. Key = head tree ID 8 + epoch 8 + mapping key 27 = 43 bytes, empty value; epoch = the head's previous_snapshot_txg when the block was dropped. Snapshot X's deadlist = entries with epoch in [prev(X).txg, X.txg); the head's = epochs in [prev(head), infinity). Snapshot creation only advances prev(head). Destroying S writes an intent (head, lo = S.txg, hi, P = prev(S)), where hi is the next newer snapshot's txg, or the checkpoint number in which the intent is written when the next side is the head; batches free the entries in [lo, hi) with birth > P and rewrite no key. No tree table bytes.
B with ordering. Key = deadlist number 8 + mapping key 27 = 35 bytes; the number lives in 8 reserved bytes of each head's and snapshot's entry. A head's first number is its own tree ID; the new snapshot takes the head's number and the head gets the new snapshot's tree ID. Destroying S decides in the intent-writing transaction which list moves, swaps numbers there, and records both numbers and the direction in the intent; always move S's list (worst case re-keys all of S's entries). Cascade intents on one lineage run in the order they were written.
C-prime with reserve. Key width 43; the epoch segment holds the tree ID of the head's latest snapshot when the block was dropped, and that tree ID is stored in 8 reserved bytes of the head's entry; a clone head's first segment uses 0. Snapshot X's deadlist = the segment (head, tree ID of X's previous snapshot). Destroying S frees entries in the next side's segment with birth > prev(S).txg and re-keys the rest to (head, tree ID of S's previous snapshot). Cascade intents on one lineage run in the order they were written.

Questions:

For each candidate, give a history in which a block still referenced by some snapshot is freed, or a block that should be freed never is; or list the shapes you tried.
2. Cost: bytes per entry, tree table bytes, and what each step must look up and rewrite.
3. Reserve: with F14 plus the children counter of F19 and the origin link of F20, which claimants fit in the 24 reserved bytes under each candidate.
4. For each candidate, one check that turns red when it is broken, and how you would prove the check itself can turn red.
5. Which one do you pick, and what single observation would change your pick?
