Background: this is a copy-on-write filesystem. Free-space bookkeeping is a set of independently maintained per-device statistics, refreshed on every publish (commit). A checker walks the on-disk image and cross-checks these statistics against what it finds by walking. An admission formula decides whether a write is allowed to proceed, reading the maintained statistics, not by scanning the disk.

Settled facts, do not dispute them:

F1. The admission formula (call it the "outer formula") is: Available = sum over devices of (capacity - allocated - unreclaimable - defer_pending_release - mount_period_commitment - abandoned_root_exclusive_amount) - pending_delete_occupancy - committed_reservation - checkpoint_reserve_pool. Two of its terms have a written justification: "allocated" is justified as "the object audited by invariant I-3.1 (allocated accounting matches)"; "defer_pending_release" is justified by the quoted rule "releases produced within checkpoint C must not enter the allocatable set before C is published".

F2. A separate cross-reference table pins each term of the outer formula (F1) to one maintained statistic: the formula's "allocated" term is defined to be exactly statistic item 1 ("allocated bytes"); the formula's "defer_pending_release" term is defined to be exactly statistic item 5 ("defer-queue pending-release bytes, keyed by release generation"). A written warning says: statistic item 2 ("free bytes") must be maintained independently and must never be computed as capacity minus item 1 allocated bytes; if it were, the invariant "free bytes equals total space minus allocated space" would be a tautology with zero power to catch bugs.

F3. A second, inner admission check (call it the "inner formula") is: allocatable = min(reclaimable + live_metadata - reserve_pool, df_inner). A separate rule states: the outer formula (F1) and the inner formula are two gates connected in series: first pass the outer formula's "available >= requested", then pass the inner formula's raise-the-rollback-floor logic (described in F5 below).

F4. Two hard requirements govern space availability. Requirement 1, no false ENOSPC: whenever df reports free space >= s, a write of s bytes must succeed; the filesystem may do bounded internal work first (push publishes, raise the rollback floor), and may only return ENOSPC once the disk is genuinely full, i.e. df reports free < s. Requirement 2, bounded reclaim: after deleting an s-byte object, a write of the same size must succeed within a bounded, computable number of steps, not "eventually". That bound is 3 publishes that change user-visible state; publishes the filesystem pushes on its own (to raise the rollback floor) do not count toward this bound of 3. Separately, admission itself may internally push up to B = 4 + 2*k_tol publishes (with k_tol = 2, so B = 8) while trying to raise the rollback floor, before finally returning ENOSPC.

F5. The inner formula's own rules: a released block becomes reclaimable exactly when release_generation <= max(F_effective, oldest_valid_root_in_ring). "Oldest valid root in ring" means: among every root-ring slot on disk that both self-verifies and is judged still valid by the instance table, take the minimum checkpoint-generation number; a slot whose write failed keeps its old content; an unpersisted, in-flight publish is not counted. F is an 8-byte field carried in each root record; it is normally left untouched (so the reclaim window is the whole ring); it is only raised when admission is insufficient. The upper bound when raising F is min(the newest persisted valid root on each device, the 4th-newest non-empty persisted valid root); non-empty here means a publish that changed user-visible state, excluding empty publishes pushed only to raise F. Admission (the inner formula) computes allocatable = min(reclaimable + live_metadata - reserve_pool, df_inner); if insufficient, it first pushes empty publishes to raise F (this push is skipped only before the very first publish of a brand new instance, which is called the "write-row publish"); it tries at most B = 4 + 2*k_tol publishes; only after exhausting all B attempts does it return ENOSPC. df_inner = never-used-space + released-space + live_metadata - reserve_pool - worst-case-push-residue - lag_amount. Note: df_inner's formula counts already-released space (the same bytes tracked by statistic item 5, "defer-queue pending-release bytes") as part of what is available, subject only to reserve_pool, push-residue and lag_amount deductions -- it does NOT subtract the full defer amount the way the outer formula (F1) does.

F6. Root-ring geometry: there are R=3 regions; each region holds S slots (S has a lower bound of 4); a root record for publish-generation number txg is written to region (txg mod R), slot ((txg div R) mod S). In the current first-version geometry S=8, so ring depth is R*S=24, so the root written at generation t overwrites the ring slot that used to hold the root for generation (t-24).

F7. Instance-table validity predicate, used to decide "is this root still valid, i.e. not abandoned": a root (instance i, generation T) is valid if and only if the instance table has no row for instance i, OR it has a row (i, Ti, Wi) and T <= Ti. When an administrator rolls the filesystem back to an old root R_old, a "rollback row" (i, T_old, 0) gets written for the instance that owned R_old, which makes every root produced by instance i AFTER generation T_old permanently invalid (never selectable again) under this predicate -- those are exactly the "abandoned-timeline roots".

F8. There are three candidate readings of the phrase "all valid roots" used by different rules in this system:
Reading (i): all root-ring slots that self-verify, with no instance-table filter and no F filter at all. This is what the current implementation's checker function actually computes.
Reading (ii): among self-verifying roots, only those the instance-table predicate (F7) judges still valid (drops abandoned-timeline roots), with no F filter.
Reading (iii): the "rollback candidate set" -- valid per the instance-table predicate (F7) AND generation txg >= F_effective.

F9. Rollback mechanics: when an administrator rolls back, the filesystem picks an old root R_old from the rollback candidate set (reading iii), stops applying any journal record after R_old, takes a new instance number, and writes the rollback row (F7). "The defer queue, the allocator's cursor, and the current value of every accounting statistic are reloaded from R_old's own account." Blocks referenced only by the now-abandoned-timeline roots must not be reallocated and must not have their headers erased before those abandoned roots physically leave the ring. To enforce this, the allocator additionally checks the account of every currently-readable root in the ring and isolates only the slots that are referenced exclusively by abandoned-timeline roots (a slot still referenced by any currently-valid root is never isolated). This isolated amount is tracked as a separate, in-memory-only quantity: F1's "abandoned_root_exclusive_amount" term, computed as (the abandoned root's own allocated-bytes statistic) minus (R_old's own allocated-bytes statistic), read directly from each root's own accounting-tree root without walking the tree; it is cleared to zero once the abandoned root is itself overwritten out of the ring by rotation.

F10. Invariant I-3.1 (allocated accounting matches): allocated-space statistic must equal the sum obtained by actually walking every reference. The checker's current reading of "walking every reference", decided by the project's user, is: take the union of the references reachable from every valid root currently in the ring (not just the newest root). This reading was decided at a point when the pool held only a single publish: there had been no releases yet, the root ring had never been overwritten, and F was constantly 0.

F11. Invariant I-5.2 (free accounting matches): free-space statistic + allocated-space statistic must equal the size of the unit area (device capacity area). This check is purely arithmetic over the two maintained statistics; it does not use any walked reference data.

F12. Invariant I-5.3 (reported free space is honored): if df reports s bytes free, writing s bytes must succeed; after deleting s bytes, a write of the same size must succeed within a bounded number of steps.

F13. Current source-code facts. In the allocator module: the "allocated_slots" counter is documented as "the number of occupied slots: still-allocated slots plus released-but-still-inside-the-defer-window slots"; a function that marks a slot released only increments a separate "deferred_slots" counter and does NOT decrement "allocated_slots" and does NOT touch "free_slots" at all; a function that marks a slot newly allocated increments "allocated_slots" and decrements "free_slots", and requires (by assertion) that the slot was not already marked allocated in the bitmap. There is currently no reclaim/reuse code path anywhere in the codebase (confirmed by an exhaustive source search). Each publish writes statistic item 1 (allocated bytes) directly from the "allocated_slots" counter, and statistic item 5 (defer bytes) directly from the "deferred_slots" counter. The checker's "all valid roots" function returns every ring slot that self-verifies, with no instance-table filter and no F filter (this is reading i from F8). The checker walks the newest root first (collecting referenced physical ranges), then walks every OTHER self-verifying root too, accumulating references into the SAME shared set (a true union, matching reading i / F10's decided reading). It then computes, per device: walked_sum = total size of all referenced ranges on that device; and judges I-3.1 as (allocated statistic == walked_sum), and judges I-5.2 as (free statistic + allocated statistic == capacity), using only the two statistics.

F14. Example numbers from a fixed test script: after one overwrite-publish (call it publish B) that releases 10 slots per device that were allocated by the very first publish, each device's statistics read: allocated = 23 slots, defer = 10 slots. The 10 released slots are still counted inside the 23, because the first publish's root still references them and reading (i) still includes that root's references in the union.

F15. A separate, already-settled rule about in-flight admission (not about the two persistent statistics in F1/F2): "Admission reads = published statistics minus in-flight already-approved reservations; releases produced within the current, still-open window do not create credit." This rule is about adjusting the published statistics with an in-memory, never-persisted overlay for the currently-open checkpoint window, before that checkpoint itself is published; it is a separate mechanism from the persistent, cross-publish statistic item 5 in F2.

The candidate reading under defense, C, is entirely unchanged text and unchanged code:
C1. Statistic item 1 ("allocated") counts occupied space: still-allocated slots plus released-but-still-deferred slots (matches F13's actual counter behavior).
C2. I-3.1's union range is reading (i) from F8: all self-verifying roots in the ring, unfiltered (matches F13's actual checker behavior).
C3. I-5.2 is left exactly as stated in F11, unchanged, no third term added for defer.
C4. F1's outer formula is left exactly as written, unchanged; you must find a reading of the existing wording (F1, F2) that is not self-contradictory, without changing any word of it.

Four attacks against C:

Q1, double subtraction. Under C1 and C2, "allocated" (item 1) already includes every currently-deferred slot (F13, F14: 10 of the 23 allocated slots at device level are deferred). F1's outer formula then ALSO subtracts "defer_pending_release" (item 5) separately. Since item 5's value is, by definition, the exact subset of item 1 already counted as deferred, subtracting both amounts to subtracting the same physical bytes twice, so Available under F1 is exactly item-5's byte count lower than it should be. Is there a reading of F1 and F2's exact wording, unchanged, under which "allocated" (item 1) and "defer_pending_release" (item 5) do NOT overlap, so this double subtraction does not actually happen? If you cannot find one, say so and explain precisely why F2's cross-reference table forces the overlap.

Q2, two gates and two df's. F5's inner formula's own df_inner counts released-but-deferred bytes as available (subject only to reserve_pool, residue and lag_amount), while F1's outer formula subtracts the full defer amount from Available (and, per Q1, possibly subtracts it twice). F3 says these are two gates "in series: first the outer formula's available >= requested, then the inner formula's raise-F logic". So a request that could only be satisfied by the inner formula's raise-F mechanism (F5) might get rejected by the outer formula's gate before the raise-F retry logic (F5) is ever reached, which appears to conflict with F4's requirement 2 (bounded reclaim within 3 publishes / at most B=8 admission attempts). Is there a reading of F3 and F5, unchanged, under which the outer-formula gate is NOT a dead end for such a request -- for example a reading where raising F (and later reclaiming) changes statistics that F1's outer formula actually reads, so the whole two-gate admission is retried as a single unit across the B attempts, not rejected forever at the first gate? Give the precise mechanism (which statistic changes, by how much, at which step) or say this does not hold.

Q3, ring-rotation time lag. Consider a release with release_generation g = t-23 (something released during publish t-23), and consider a later publish t (t >= 25, no generation numbers skipped), whose new root overwrites the ring slot that used to hold the root for generation t-24 (per F6, ring depth 24). While publish t is being processed, before publish t's own new root has persisted, the ring's oldest root is still generation t-24, so F5's reclaim predicate reads g=t-23 <= t-24, which is false (t-23 is greater than t-24), so these blocks are not yet reclaimable and stay counted as "allocated" in publish t's own accounting write. After publish t's new root actually persists, the ring's oldest root becomes generation t-23 (the old root for generation t-24 has been overwritten and left the ring). The root for generation t-24 was the LAST remaining root that still referenced these particular blocks (they were released starting at the root for generation t-23 itself, so root t-23 and everything after it never reference them; only roots strictly before t-23, i.e. up through t-24, still reference them). So once root t-24 leaves the ring, under C2 (reading i) NO remaining self-verifying root references these blocks anymore, so the walked union (right side of I-3.1, F10) drops by exactly these blocks' size. But per F13, nothing in the current code ever decrements the "allocated" statistic (item 1, left side of I-3.1) due to ring rotation alone; only allocation increments it, there is no decrement path at all today. So the statistic stays the same while the walked sum has shrunk, and I-3.1 goes red. This would recur every 24 generations after any release. Under C1 through C4, unchanged, can you show this does not actually happen, or find a definition already present in the given facts (F1 through F13) that ties a decrement of the "allocated" statistic to the moment a root leaves the ring purely by rotation (independent of F, independent of rollback)? If you cannot, say DOES NOT HOLD and name exactly which fact (F13's "no decrement path" or F10's chosen union reading) blocks the escape. Separately: does this same time-lag problem equally affect reading (iii) from F8 (the rollback candidate set) when F_effective is constantly 0 and no rollback has ever happened (matching F10's stated context when reading i was decided)? Explain why or why not, referencing F5's predicate and F7's validity predicate.

Q4, three readings of "valid root". Reading (i) (F8, used by C2) has no instance-table filter and no F filter, unlike readings (ii) and (iii). Two follow-on problems are claimed:
Q4a: after F is later raised and a block with release_generation <= the new F gets reclaimed and reused, an OLDER root with generation less than F may still physically exist in the ring (not yet rotated out) and may still reference that same block. Under reading (i), that older root's reference would still be included in the union, so walked_sum would count the block as still allocated even though the "allocated" statistic has already been decremented at reclaim time -- I-3.1 would go red the opposite way from Q3 (walked_sum too large this time, not too small).
Q4b: after a rollback (F9), blocks referenced only by abandoned-timeline roots are excluded from the current "allocated" statistic (F9: "in R_old's own account those blocks are free"), but the abandoned-timeline roots are still physically present and self-verifying until rotated out.
