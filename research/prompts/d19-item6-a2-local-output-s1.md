Instance id is never reused (H3) and each transaction writes at most one data unit (H2). Therefore, same instance id and transaction number implies same unit. Different units must have different instance ids or transaction numbers. No scenario found where two different code 1 units share the same key. All attempts failed because instance id and transaction number uniqueness prevents key collisions.

The system restarts the fixed point for the same checkpoint 5 and instance id 1 without changing the instance or checkpoint. The birth sequence counter resets to 0. A second code 2 unit for the same tree 10 is written with birth sequence 0. Both units have key: class tag 2 + birth tree 10 + birth checkpoint 5 + instance id 1 + birth sequence 0. This violates R2 because the counter reset in the same scope (tree 10, checkpoint 5, instance id 1). Relies on H7 (fixed point may iterate same container multiple times in one checkpoint) and the verdict's description of birth sequence being issued in memory from 0.
