## 二、D-2：为第一轮未采纳一方辩护

### G1 反面：hook 有没有不误拦插件 agent 的拒法

**够不着（找不到，不是重新论证利弊）**。

- 插件 agent 是真实机制，不是假想：`~/.claude/plugins/synced/` 目录存在（虽然当前是空的，没有任何插件装了 agent）；二进制里现查到 `plugin_load_agents`、`Loaded ${U.length} agents from plugin ${O.name} default directory`、`plugin-agents` 这几个真实字符串，证明 Claude Code 确有「从插件自己的目录加载 agent 定义」这条路径，与 `.claude/agents/` 是两处不同目录。
- 现查这个项目 2026-09-16 记录的 hook 输入键（`records/2026-09-16-subagent拆分提案.md` 第 329 行一带，74 条实测记录）：子 agent 的调用只带 `agent_id`、`agent_type` 两个额外键，没有 `plugin_name` 或任何能区分「插件来的」与「本项目定义过、后来被改名/删掉」的字段。也就是说，`agent-write-scope.sh` 现在能看到的唯一信号就是 `os.path.isfile(.claude/agents/{agent_type}.md)`，这一个信号对「真的是 Claude Code 内置 agent」「插件供的 agent」「本项目定义过又被删掉/改名的 agent」三种情形给出**同一个**答案（都是 False）。Opus 提出的「内置 agent 名单写死，名单外拒绝」这条改法，会把插件供的 agent（一旦真的装了插件）也一起拒掉——这不是过度谨慎，是能验证到的真实副作用。
- 另一条现查支持 R1 本来就标的「弱」：`.claude/agents/` 到今天仍然整个未跟踪（`git ls-files .claude/agents/` 0 个、`git log --oneline -- .claude/agents` 0 条），G1 需要的触发条件「主 agent 在一个执行员活着的时候把定义改名或删掉」从 R1 到现在一次都没有真实发生过。这不构成「问题不存在」，但确认 R1 把它标成「条件打中、弱」而不是紧急去修，到今天仍然站得住。
- 没有找到能替代的拒法，就如实报告找不到，不拿「反正插件也没装」这种利弊论证去顶替这个空白。

### 本地辩方第 2 条：bin 名对不上应按「缺输入」停下

**够不着（R1 的拒绝站得住，有直接先例）**。

- 现查 `research/scripts/mutate.sh:19-37`：退出码 6 那条分支是从 `Cargo.toml` 里按**源文件路径**（`$SRC`，主 agent/登记给定、不含糊）反查声明的 `[[bin]] name`，这是一次确定性查表，同一个 `$SRC` 只会查出唯一一个正确答案，脚本报的改法不是猜测。这与本地辩方 F10 说的「present but wrong, with a single mechanically verifiable correction」完全对得上，不需要人的判断。
- 直接先例：`mutation-triage.md` 输入一节（这份定义没有被这一轮改过）本来就写着「主 agent 给的对不上、`mutate.sh` 退出码 6 时，照它报的改法改，报告里写明」——同一个仓、同一种情形，已经有一条定义在用「自动按脚本改法走 + 报告里写明」而不是「停下」。R1 维持 experiment-runner 用同一口径，是同类先例的复用，不是重新论证利弊。

- 不替主 agent 撤销或维持判决，只交复核结果。
- 没有重新论证「该不该改」的利弊；每条命中都落在能现查的原文、脚本行为或先例上，查不到就写查不到（G1、本地攻方第 2 问）。

- 没有改任何文件；本轮只读，没有写模型目录或草稿目录。
