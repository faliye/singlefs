1a. No reachable point exists where current's instance-table content differs from a fresh choose_root read on disk. This is because every successful publish_version call writes the instance table from current to disk as part of creating the new root. After a publish completes, the disk's newest root's instance table matches current's instance-table unit. If a publish does not modify the instance table (e.g., empty publishes using Carry), current's instance-table pointer remains unchanged, so disk and current agree. This is refuted by: If a publish succeeds but fails to write the instance table to disk before returning, but the facts state publish_version writes the new root to disk before completion.

1b. The presence of a root below effective_floor in oldest_valid_root never changes reclaim_floor's output. G1 always takes the maximum of effective_floor and oldest_valid_root, so any value below effective_floor is ignored. For example, effective_floor=10, oldest_valid_root=5: reclaim_floor=10. If oldest_valid_root=15, reclaim_floor=15. A root below effective_floor has no impact. This is refuted by: If reclaim_floor returned oldest_valid_root when it was below effective_floor, but G1 explicitly states it returns the larger of the two values.

1c. Yes, effective_rollback_floor can include abandoned roots' rollback_floor values, pushing reclaim_floor higher than justified by the current timeline. For example, after a rollback, device A has an abandoned root with rollback_floor=20, device B has one with 20, and the current timeline's roots have rollback_floor=15. effective_rollback_floor=min(20,20)=20. If oldest_valid_root=10 (smallest valid root's checkpoint_txg), reclaim_floor=max(20,10)=20. reclaim_released_up_to(20) would reclaim releases up to generation 20, including those from the abandoned timeline. This is refuted by: If effective_rollback_floor filtered out abandoned roots during its computation, but G3 states it reads "every currently readable root in the ring with absolutely no filtering by abandonment."

1d. An all-abandoned readable_roots set is impossible. The newest root's own instance table row has selected_root_txg equal to its checkpoint_txg (since it is the latest), so abandoned_by_table returns false for it. Thus, readable_roots always includes at least the newest root as valid. This is refuted by: If the newest root's instance table row had selected_root_txg < its checkpoint_txg, but the facts state that for the newest root, the row's selected_root_txg matches its checkpoint_txg.

2a. No reachable sequence exists where G7 picks a non-tree-table record with generation zero. G10 confirms only the two mkfs records (instance table span two, tree table span one) have generation zero. During a rollback to mkfs root (checkpoint_txg zero), the record set contains only these original records. G7's predicate (generation zero, span one, not released) uniquely matches the tree table record. This is refuted by: If a record with generation zero and span one was created outside mkfs, but G8 and G10 state that no such record can exist after mkfs.

2c. No reachable state exists where publish_version is called with previous absent and tree-table role rewritten after the tree table is durably released. The previous-absent branch only occurs during mkfs; after mkfs, all publishes have previous present. The tree-table role check in G9 is necessary because it ensures format_time_tree_table_to_release only runs when the tree table is being rewritten (e.g., during mkfs), and it is not redundant with the is_released check. This is refuted by: If a publish after mkfs had previous absent, but the facts state previous is absent only during mkfs.

3a. It is impossible for a chosen root to both belong to instance i and carry the row describing its ending. The fact states such a row is always written into the next instance's table, not the current instance's table. Thus, the chosen root (instance i) cannot contain its own ending row. No other mechanism in the facts limits replay beyond this. This is refuted by: If the ending row for instance i was written into instance i's own table, but the given facts explicitly state it is written into the next instance's table.

3b. Adding a check for newest root's instance number being more than one step ahead of the target would wrongly reject valid targets. Example: newest root instance=3, target instance=1. The row-based check might accept the target if the high-water mark for instance 1 is below the target's checkpoint_txg. But the extra check would reject it because 3-1=2>1. This is refuted by: If the row-based check accepted a target that the extra check rejected, which occurs in the example above.

3c. No additional field distinct from transaction can be identified from the given facts to make the non-empty root test more conservative. The facts describe journal records only in terms of instance, checkpoint_txg, and transaction fields; no other fields are specified. This is refuted by: If a field like "data_size" existed in journal records and could be checked, but the facts do not describe any such field.
