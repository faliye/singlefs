1. A concrete case where jumping by unit size fails is when two data units are stored with the second unit starting within the padding of the first unit. For example, the first unit starts at offset 0 with declared length 100 bytes (so payload ends at 99), and the second unit starts at offset 100. If the scanner steps by 1 byte and uses declared length to skip, it skips 100 bytes from 0 to 100 and correctly finds the second unit at 100. If the scanner jumps by unit size (32768 bytes), it moves from 0 to 32768, skipping the second unit at 100 entirely. This causes the scanner to miss the second unit, which is a misclassification.

2. An attacker without the key can infer the following about file sizes: the total count of data units equals the number of files, since each file occupies exactly one data unit. Each file's size is between 1 and 32768 bytes because a file smaller than one unit still occupies a full unit. The physical position of units reveals no additional size information beyond the unit size, and the payload CRC is unreadable as a size indicator since it is computed over ciphertext. The unit class code confirms the unit is a data unit but does not provide size details beyond the maximum possible size.

3. Hiding the declared length does not break the keyless side's ability to detect damage. The keyless side can still check the header checksum (for the plaintext header bytes: magic, format version, flags, header checksum itself, and fsid) and the payload CRC (which covers the entire ciphertext payload). Damage in the header is detected via header checksum, and damage in the ciphertext payload is detected via payload CRC mismatch. The keyless side cannot verify the padding is zero because it cannot read the declared length, but the payload CRC already includes the padding bytes in its computation, so padding corruption is still detected.

4. A corrupt unit with a declared length set to 0 in plaintext would be rejected immediately during the declared length check today. If the declared length is moved to ciphertext, an attacker could craft the ciphertext such that decryption produces a valid declared length (e.g., 100 bytes). The unit would pass the header checksum check, decrypt to a valid declared length, and proceed to the payload checksum check. This allows the unit to advance further in the validation process than today, where it would have been rejected at the declared length stage.

5. The most likely false assumption is that units are always stored in aligned blocks such that no unit starts within the padding of another unit. This is revealed by a test where two units are deliberately stored with the second unit starting within the padding of the first (e.g., first unit at offset 0 with declared length 100, second unit at offset 100). When scanning with unit size jumps, the second unit is missed, but scanning with declared length skips correctly finds it. This shows the scanner must use declared length to avoid missing units stored within padding.
