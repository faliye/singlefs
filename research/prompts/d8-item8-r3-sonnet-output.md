## 扫过、确认没有冲突的地方（连同为什么）

### I-7.x 根环族
逐条读过 I-7.1～I-7.7（`invariants.md:44-52`）。I-7.7（超级块实例代号不低于根环） 管的是
**实例代号**，与②的**树 ID 水位**是两个不同字段、住同一个段四但各自判定，②没有改动实例代号
的判法，I-7.7 原样成立。I-7.4（近 K 代块未被复用）/I-7.3（环健康性） 依赖根环深度与实例表，
四条定案都没有动根环或实例表的语义。**没冲突，因为②③④都没有改任何 I-7.x 判据的输入**。

### D15（格式冻结政策） 分层与已定项 2
四层冻结顺序见 `15-格式冻结政策.md:47-56`，第 1 层含"树 ID"字样，但那是**块头里的树 ID 归属
字段**（I-1.3（块头树 ID 一致） 那类），不是②的"树 ID 水位"——两者字面撞了名字，语义不是同一个
东西，不构成冲突。已定项 2（`15-格式冻结政策.md:129-139`，"新增一棵 keyspace ⇒ compat"，
依据是"树数量硬编码则读不出树表；开放列表下只是看不到新树"）的前提是**旧读者能跳过不认识的
条目**——这正是④（兼容档取"树表条目自带长度"，每条目 18 字节 = 长度 2 + 预留 16）显式提供的
机制。①往树表条目里加诞生 txg 字段、③加 prev_snap_txg 字段，两者都落在④的"预留 16 字节"
或未来的扩展点内，旧读者仍能靠自带长度跳过，**不属于"扩大已有字段宽度"那一行（那一行说的是
在不改长度前缀协议的前提下静默变宽）**。**没冲突，已定项 2 的前提在①之后仍然成立**。

### D22（单元原子性怎么合成） 已定项 7 / 已定三 / 已定项 8
已定项 7 的根记录字段表（`22-单元原子性怎么合成.md:383-394`）确实没有"树 ID 水位"这一行，
但这是**已经被四条定案自己发现并在同一轮里补上的洞**（`d8-item8-r3-background.md:14-20`
"甲-2 第二路见证"），不是这次新命中，按题目要求的"已经立了账的不要报"精神一并跳过。
已定三（原地覆写结构要带整单元校验和 + 被检查的世代号）与已定项 8（超级块每盘一份、
更新走 ≥2 槽轮换）：②的"每 K 次建树写一次超级块"只是改变**写它的频率**，写的机制仍是同一套
槽轮换 + 整单元校验和 + 世代号，没有绕开或新开一条更新通道。**没冲突，②没有引入第二种
超级块更新机制**。

### D9（加密） 超级块认证与已定项 8
`09-加密.md:675-681` 的已定项 8 只对**nonce 水位**这一个字段提出"必须落在 MAC 覆盖字段、
无密钥侧不许写"的硬约束，理由是 nonce 重用在 ChaCha20 下直接泄漏明文（`09-加密.md:703-708`），
这是 nonce 特有的灾难性质，已定项 8 的定案文字没有把这条要求泛化到"任何单调水位"。
`.claude/kb/checks-owed.md:142`（C135）现查坐实"超级块"整体在 D9"方向"那句
（"除超级块与已定项 5 已定留明文的那一层外全部加密"）里是**类级别明文豁免**，不是逐字段判断——
树 ID 水位与实例代号、journal tail 一样，落在这个类豁免范围内，无密钥侧读它没有障碍。
**没冲突：②没有把树 ID 水位放进"必须 MAC 覆盖"的清单，而这清单目前只认领 nonce 水位一项，
②不违反任何已定的加密条款；"要不要比照 nonce 水位也加 MAC"是一个可以另外提的问题，
但没有已定条款要求这么做**。

### D13（验证路线） 已定项 5
`13-验证路线.md:301-334`："生成器拒绝发射没有 kb 落点的常量"+"K 是可调值不是格式常量"
（背景引用的 D16（发布语义） 已定项 5 同一句话）。checker 验证树 ID 水位不需要生成器发射 K 这个
可调值——它可以像 I-9.6（水位大于两处最大号） 验 inode 号水位一样，走**不等式**
（水位 > 树表里出现过的最大树 ID）而非等式，K 只影响水位与"最大已用树 ID"之间的差值大小，
不影响不等式判据本身能不能独立算出来。**没冲突：树 ID 水位的可判定形式不需要共享 K 这个
运行时可调值，与 D13（验证路线） 已定项 5 的边界吻合**。

### D3（空间分配） 立项原则
`03-空间分配.md:26`："COW 系统必须保证『释放空间』这个操作本身不需要申请空间。"
①给快照加了树表条目，直觉上"销毁快照时删这条条目"是一次要 COW 重写树表节点的操作，
似乎会撞这条原则。但**销毁快照被 D6（快照实现模型） 自己点名归进
`.claude/rules/fs-design.md` 三格纪律的第三格**（`06-快照实现模型.md:19`：
"销毁快照落在……三格纪律的第三格"）——后台、可续做、非决策路径，走"写意图 → 分批 → 可续做"，
不受"运行时决策路径不许现算/不许申请空间"那一档的硬约束（`fs-design.md`
"记账是事务的副产品，不是事后的遍历"节的三格表）。销毁快照本身要用的空间，与任何后台
提交内生块一样受 C139（整理停摆之后释放也发不出去） 已经登记的那类准入风险约束，不是一个
新的、专属于①的缺口。**没冲突：①没有让"释放空间需要空间"这条原则失效，只是把销毁快照的
COW 代价并入了已经被 C139 覆盖的一般性风险**。

## 结论

三方论证要求的"某条已定条款逐字要求 A，四条定案让 A 做不到"这个形状，本轮只在
**I-3.5（引用区间的精确性）** 上找到一个未被登记的真实缺口：它与 C144 共享同一个 D6 反例根因，
但作为一条独立的、在用的不变量编号，从未被①③④或 C143/C144/C145 点名，而 D8 未定项 8
定案前的正文明确把它列为诞生 txg 字段的消费者之一。其余六处逐一现查后确认没有冲突，
理由已在上面各节写明（都不是"扫到 0 项"式的空检查——每处都指出了具体是哪句已定文字、
为什么它在①-④之后仍然站得住）。
