## Q1　C871 / I-9.8（K1 分歧）

**复核结论**：第一轮判决只写「分歧进第二轮」，这一条站得住；但分歧点本身要改：两腿点名的接手者都不对，攻方的「没有不变量判」也不对。

**分辨点（这张镜像上 I-9.10、I-9.5 与别的已实现不变量红不红）的判定**：叶里 20、30、40，把 30 的偏移 0 改成 35 重封校验和。我按池级 checker 今天的联接逐条推：

- I-9.10 不红。它只拿「extent 树里数据单元的 inode 号」去查「inode 树里同号记录的对象出生代」，查不到记录就跳过：「if let Some(record_birth) = walk.inode_object_birth.get(inode) {」（`crates/singlefs-checker/src/walk.rs:20044`）。改完以后 inode 30 没有记录，该单元被跳过；inode 35 没有数据单元，没有对象。墓碑那一个等号也按号认，这张镜像上没有墓碑。
- I-9.5 不红。它的两个方向都只碰 nlink = 0 的记录：「② inode 树里 nlink = 0 的每条记录」（`crates/singlefs-checker/invariants/09-inode树结构.md:17`）；这张镜像上改号的记录 nlink ≥ 1。
- I-9.4、I-9.12、I-1.1 不红（攻方这一半对：次序 20 < 35 < 40，分隔 key 不动）。
- 红的是 I-4.7 与 I-4.6，前提是 inode 30 有数据单元（size > 0 的文件）：
  - I-4.7（删除中 inode 有账）把「处于删除中」定义成两样，第二样正是这张镜像：「extent 树里有数据单元、而 inode 树里没有 nlink ≥ 1 的记录的号」（`crates/singlefs-checker/invariants/06-事务与崩溃一致性.md:13`）。代码里 inode 30 进集合：「data_units > 0 && !records.get(inode).is_some_and(|record| record.nlink >= 1)」（`crates/singlefs-checker/src/walk.rs:13351`），号又不在 `deleted_inodes` 里，判红。
  - I-4.6 的单元数对 size 那一判逐条记录跑，记录 35 没有任何数据单元而 size > 0 时落在「没有上段叶条目」那一支：「data_units_existing == 0 && record.size_in_bytes == 0,」（`crates/singlefs-checker/src/walk.rs:13445`），size ≠ 0 判红。
- 不红的只剩 inode 30 是没有任何数据单元的空文件那一形：我在 `walk.rs` 里查了所有按 inode 号联接两棵树的地方（`inode_object_birth`、`data_units_of_each_inode`、`deleted_inodes` 三份），只有上面三处；没逐条读全部 I-1 到 I-9。

**对两腿的判定**：正推腿「区间内换号由 I-9.10、I-9.5 接」够不着（两条都不红）；攻方「没有一条不变量判」「另记新判据欠账：extent 树里每个 inode 号在同一版 inode 树里有记录」也够不着，那一条已经是 I-4.7 的第二样。两腿共同的结论「只改偏移 0、只红 I-9.8 的镜像造不出」成立。

**建议判决**：I-9.8 写成乙形（第一版格式里 key 就是偏移 0，没有第二份可比，无可判对象），不取甲。甲把「等于」换成「落在路由区间」，这是比 I-9.8 原文弱的命题，而且正推腿为它点名的接手者是错的。条文里写明实际接手：越出路由区间由 I-9.4、I-9.12 接，号在区间内被换而文件有数据单元时由 I-4.7、I-4.6 接，空文件换号判不出（记已认盲区，理由：没有第二个载体）。C871 的出口「只改偏移 0、只红 I-9.8」改成三张镜像：低于容器号 ⇒ I-9.4；跨过下一条分隔 key ⇒ I-9.12；区间内换号的带数据文件 ⇒ I-4.7 加 I-4.6，且点名 I-9.10、I-9.5 不红。不另记新判据欠账。

**什么现象会推翻它**：造出区间内换号、文件有数据单元、而 I-4.7 与 I-4.6 都绿的镜像（我没造盘面，只推；要造得起 harness 档的 cargo，本腿不起）；或找到 `walk.rs` 里另一处按 inode 号联接两棵树、会让空文件换号也红的判法。

**同类先例**：I-4.7 条款把「extent 树里有数据单元而 inode 树没有记录」当删除中处理，是同形的联接先例（上引 06:13）。

## Q2　C740 / W 的判法（K2 分歧）

**复核结论**：正推腿的三支够不着，攻方的收窄站得住。

**分辨点（三支在攻方那一对历史上各判什么）**：最小的一对：实例 1 发一次承载事务 1 的发布，记录与根槽都落了（根环里有 txg 1 的根）。
- 干净历史：挂载读得出 txg 1 的根，直接择它，一条记录都不施加，写行 (1, T=1, W=0)。
- 读故障历史：挂载时 txg 1 那一槽读坏，择到 txg 0 的种子根，重放施加 txg 1 的记录，写行 (1, T=1, W=1)。核心里 W 就是施加的记录里最大事务号：「applied_transaction_high_water: journal.maximum_applied_transaction,」（`crates/singlefs-core/src/mount.rs:8914`），取最大的循环在 `report.maximum_applied_transaction = maximum_transaction_of(`（`crates/singlefs-replay-prefix/src/lib.rs:3914`）。
- 读故障不留在盘上，两张镜像除 W 外逐字节相同。正推腿 (a) 支「T 是环里的根 ⇒ W 必为 0」在读故障那张上判红，是误红；(b) 支不到。用户把读坏一个根槽的镜像定成合法镜像：「读坏一个根槽的镜像算池级 checker 的合法镜像（用户 2026-10-04 定」（`.claude/kb/checks-owed.md:422`），所以这是合法历史上的误红，不是可接受代价。
- (b) 支也有同形误红：T 的根槽从没落、S 是环里 txg 小于 T 的最大根；挂载时 S 那一槽读坏，择到更早的 c，重放施加 (c, T]，W 取到 (c, S] 里的非 0 号，而 (b) 支只从 S 起算。模型里的例子：n = 2，事务号 (1, 0)，txg 2 的根没落，挂载时 txg 1 的根读坏，行 (2, 1)，(b) 支期望 0。

**模型**（`q2/q2_w_rule.py`，输出 `out/q2_w_rule.txt`）：一个旧实例发 n ≤ 6 次发布，事务号按 I-8.7（第一个非 0 是 1，相邻非 0 不减，同号连续）枚举，根槽落盘集合取真实形（1..n−1 全落、n 落或不落）；挂载时 ≤ k 个根读坏，重放照 D23 已定项 14（所选根 = 读得出的最大 txg，施加其后全部记录）。判器只看无故障的镜像。

| 口径 | 世界 / 历史（k ≤ 1） | 正推腿三支误红 | 攻方集合形误红 | 变异（W 改成该镜像不可达的值）红的比例 |
|---|---|---|---|---|
| 真实形 n ≤ 6，k ≤ 1 | 616 / 4190 | 253（(a) 175、(b) 78） | 0 | 集合形 2035 / 2211；最强可能（只看镜像）2211 |
| 真实形 n ≤ 6，k ≤ 2 | 616 / 13161 | 1625（(a) 1175、(b) 450） | 0 | 集合形 2035 / 2101 |
| 宽形（任意根槽落盘子集）n ≤ 5，k ≤ 1 | 3184 / 13790 | 1483 | 0 | 集合形 10795 / 11253 |
| C740 自证那一形（T 根槽没落、T 的记录事务号非 0、W 改 0），k ≤ 1 | 175 | 三条规则都红 175 / 175 | | |

集合形 = 攻方的收窄：W ∈ {0（当 T 在环里）} ∪ {对环里每条 txg 小于 T 的可读根 c：(c, T] 里记录的最大事务号}。再收一步的 k1 形（只许一个根槽读坏：T 在环里时只取最大的一条 c，T 不在环里时取最大两条）：k ≤ 1 误红 0、变异全红（2211 / 2211）；但 k ≤ 2 时有 110 / 13161 个历史误红。

**建议判决**：改。C740 的判法取集合形：W 属于「可达集合」；T 在环里时集合含 0，不再要求 W = 0；D23 注 4 的切换写者今天没实现（`.claude/kb/decisions/23-journal的角色与格式.md:374`），条文限定「本条只判挂载恢复写的行」；(c) 支（读不全报部分没判）照正推腿留。弃用 (a) 支的「必为 0」。要不要用 k1 形换回那 8% 的变异，取决于用户 2026-10-04 的定案能不能推到「同一次挂载读坏两个根槽」；本腿不替他取，先取不误红的集合形。C740 自证（W 写成 0 的坏镜像必须红）在集合形下仍成立，只在 T 的根槽从没落过的盘面上红，这正是 b35 那一形。
**模型口径**：单实例、每次发布一条记录、不模型环转圈与 F2 退回（F2 退回的行 W = 0 对应集合里的 0，躲得过），宽形是「任意落盘子集」，宽于真实写者。

**什么现象会推翻它**：一张写者可达的合法镜像上集合形红（模型里没有）；或造出 T 在环里、W 非 0、而 txg 小于 T 的每个读得出的 c 重放都给不出这个 W 的合法历史。

## Q6　C699 第四条件（K7）

**复核结论**：站得住。第四条件只会让「认作取号跳过」的集合变小，不会新增误红。

**判什么**（I-3.5 缺口条款）：认作取号跳过（gap-row）的对「照常判」，不是的对「用户可见树子树里的落点不判」，别的落点仍判 birth > R⁻.txg：「这一对照常判（gap-row）」「不是的，用户可见树子树里的落点不判」（`crates/singlefs-checker/invariants/05-空间记账.md:11`）。多加一个合取项只会把一些对从前一类挪到后一类，判得更少，不会判出新的红。

**在清扫那一版与清扫之后的版本上**：
- 清扫只删「根已全部轮出根环的实例」的行：「一个实例的根全部轮出根环之后」（`crates/singlefs-core/src/instance_table_sweep.rs:2`）。R⁻ 在环里，它的实例行不会被清扫删；中间实例 (j, 0, 0) 的行可能被删；按条文字面，缺行不是「(j, 0, 0)」，第三个条件不成立，本来就不是取号跳过（我没核代码怎么处理缺行）。
- 清扫那一版 V_s：实例表被重写，指针出生 txg = V_s.txg。V_s 与它的前一条根同实例时不是 gap-row 候选，第四条件不被问。
- 清扫之后的版本：照抄清扫那一版的指针，出生 txg 小于自己的 txg，第四条件不成立。这些版本同样只在前一条根读不出时才会成为候选，不成立正是 C698 要的结果。
- 合法的 gap-row 的 R 是新实例的第一条根，由挂载写行发布写出，指针是 `InstanceTablePlan::Rewrite(instance_table),`（`crates/singlefs-core/src/mount.rs:5267`），出生 txg = R.txg，第四条件成立，覆盖不掉。别的发布走 `InstanceTablePlan::Carry(previous.root.instance_table)`（`crates/singlefs-core/src/transaction.rs:9593` 一带）。
- 已知口子（R 是清扫那一版而它前面同实例的版本读不出）只在 R.instance = R⁻.instance + 1 时开：中间有实例号的话，中间行若被清扫删掉，第三个条件按字面已把它挡了。比正推腿写的更窄。

**建议判决**：不改，采正推腿的第四条件；动态装置的 (P1)(P2)(P3) 三句保留作验收。**什么现象会推翻它**：装置里关清扫的组出现 (P1)(P2)(P3) 违例；或一张合法的取号跳过对，R 的实例表指针出生 txg 不等于 R.txg。

## Q7　C717（K8）交用户之前要的代价数

**复核结论**：「只看根环一份镜像做不出」站得住（两腿一致，攻方模型的一对历史我读过脚本，逻辑对）。但正推腿的乙按字面写会比第一轮判决想的报得多得多，要先收窄再交用户。

**为什么要收窄**：正推腿的乙是「F 越过抬 F 那一刻环里最旧有效根 O，且窗口口径判成立 ⇒ 部分没判」。O 在一个满环里总在窗口之外（窗口锚在最新根上，只盖最后 3S 个 txg），所以凡是抬 F 的根不是最新根、F 又高过 O 的，都落进这一条，不限于「洞里留旧根 X」。攻方的 856 / 20000 是洞形（`k8_condition`）的数，不是乙按字面报的数。窗口口径的上限只有在窗口里可见的非空状态不足 4 个时才会比当时整环的高（不足 4 个时上限退到窗口里最旧的根）；够 4 个时窗口口径与当时整环口径同值，乙在那里是白报。收窄成「F > O，且窗口可见非空状态不足 4 个」（下称乙收）。

## Q8　C764（K9 ②）与 C70（K10 分歧）

### C764

**复核结论**：K9 站得住（第一轮采「只比实例代号更小的」）；读不出那一形不采攻方的丁，但正推腿的「整条部分没判」缺一个定义，要补。

**分辨点（丁的收益与它的洞）**：实现里 f_k 是 `max(根环全部根的 txg, 全部自证记录的 checkpoint_txg) + 1`：「checkpoint_txg_after_the_version(highest_ring_txg.max(highest_record_txg))」（`crates/singlefs-core/src/mount.rs:1408`）。镜像上正推腿的规则误红，要挂载时漏掉了某条实例代号更小的根或记录而镜像上读得出。最后一次发布的根占一个槽，记录在两块盘上各一份（journal 两盘各一份），一次读故障只挡一个块，所以这一形要同时读坏根槽和那条记录的两份副本，按这个读法至少三次读故障（或有一块盘不在；「两盘各一份」是我从已入库用例逐盘写同一条记录推的，没逐处核日志格式）。这是读故障流的范围，不是单个根槽读坏的合法镜像范围（C698 的定案只到一个根槽，`.claude/kb/checks-owed.md:422`）；正推腿已提「带读故障的流在登记里写明这条不判」。丁把这一形的一部分救回来（旧记录计数器小于新实例盘上最小计数器就判），但攻方自己指出它的洞：新实例第一条记录没落盘时，计数器恰等于挂载时算出的 c_new 的旧记录挂载时读不出而现在读得出，丁会拿它去比、误红。丁要崩溃加读故障两样同时才出这一洞，与它救回的那一形同样需要读故障。收益和代价在同一个量级，且都没有真盘面数；不采。

**正推腿缺的定义**：条文写「环里有读不出、不自证、落点对不上的根槽或记录槽时，整条报部分没判」。年轻的环绝大多数槽是从没写过的全零槽（journal 默认 196608 槽、根环 3S 槽），按字面「不自证」把它们算进去，这一条在几乎所有真实镜像上都是部分没判，等于没判。核心里读回全零也不算确认为空：「读回全零不算确认为空」（`crates/singlefs-core/src/allocator.rs:2824`），checker 无法区分「从没写过」与「读出来是零」。要定一句：读不出 = 读盘报错或非全零而不自证；全零槽不算，它可以是从没写过的槽（I-8.7 对「前一格读不出」的做法是同一个思路：只问应当坐着记录的那一格，`walk.rs` 的 `PredecessorDoesNotReadBack` 一支）。这是第一轮两腿都没写到的一处。

**建议判决**：K9 的条文不改，补这一句定义；丁不采，记成「读故障流里判不到的一形，要判时从丁起」。**什么现象会推翻它**：一张单根槽读坏的合法镜像上 I-8.14 红。

### C70

**复核结论**：K10 站得住，两腿对象一致，分歧只在「射程外」的理由怎么写。

**分辨点（判各自的分歧点）**：式子左边「可用(d)」是准入当时算的，不落盘；镜像上没有一个被维护的「可用」值可与右边比，攻方这一点对。攻方说「checkpoint 保留池与环窗口按条文能从镜像现算」也对：D28 写「按当时各记录树的高之和 + 记账节点现算」（`.claude/kb/decisions/28-挂载期承诺量.md:28`），D5 表把环窗口、checkpoint 保留池都标「例外」，写「只住内存、不进记账行」（`.claude/kb/decisions/05-快照-空间记账机制.md:113`）。但现算出来的只是此刻的值，准入当时用的那个数没有存下来，没有被比的一侧，比出来是恒等式。所以这四项在镜像上的状态是「没有被比的一侧」，不是「判不出」；正推腿写射程外是对的，理由写成「只住内存」是不准的。

**建议判决**：I-3.20 的 (a)(b) 条文不改；射程外那一句改写成「这四项在镜像上没有被比的一侧（准入当时的值不落盘），现算只能得到一个恒等式」，不报不适用也不报部分没判。(a) 里真正新的只有统计量 3（不可回收）那一行：空闲和已分配的和对容量早有 I-5.2；空闲是独立维护的（`crates/singlefs-core/src/transaction.rs:15123` 的注释「第 2 项独立维护」），所以和为容量这一判在 C70 要抓的「两套 += 各自没错而互相对不上」上确实有判别力。**什么现象会推翻它**：找到某个被存下来的准入读数（例如发布时把准入算出的可用写进记账或记录），则第 5 项到第 8 项里某一项有了被比的一侧，要重判。

## Q10　core：C874 那行变异与 C745 第二次抽样

### C874「只判整写不判撕裂」

**复核结论**：两腿各对一半，不矛盾：撕裂态在真实补写流上造得出，但造不出新死盘（攻方对）；枚举侧那行变异也杀得掉（正推腿对），只是它杀的不是观察者。

**分辨点（撕裂态在真实补写流上造不造得出）**：`q10_torn_states.py`（输出 `out/q10_torn_states.txt`）按取号写的结构逐态枚举：两轮，每轮每块盘一次原地覆写，轮后一道屏障（`const ACQUISITION_WRITE_ROUNDS: [AcquisitionWriteRound; 2] = [`，`crates/singlefs-core/src/transaction.rs:1251`）；D 两槽全废（基镜像上已死），L 完好；每次写落成没落 / 整写 / 撕裂。

| 流 | 状态数 | L 上新死盘的状态数 | D 没有自证槽的状态数（撕裂算没有） |
|---|---|---|---|
| 真实流（两轮之间有屏障） | 18 | 0 | 6 |
| 同上，撕裂退化成整写（正推腿的枚举侧变异，`crates/singlefs-checker-tier/src/crash.rs:2325`） | 18 | 0 | 3 |
| 去掉屏障的流（核心变异录出来的） | 81 | 9 | 36 |
| 去掉屏障且撕裂退化成整写 | 81 | 0 | 9 |

读法：真实流上新死盘数恒 0，撕裂与否都一样，所以一个「观察者只判整写」的变异在这条流上等价，杀不掉（攻方对）。观察者本身也没有地方放撕裂这个概念：它收的是逐盘自证槽数的对子（`observe_the_devices_without_a_self_verified_system_configuration_slot`，`crates/singlefs-checker-tier/src/crash_point_replay_provenance.rs:958`），撕裂的信息在判器交回槽数时已经折进数里：「撕裂域在内（判器逐状态交回逐盘槽数」（同文件 `:924`）。枚举侧那行变异会让「D 没有自证槽的状态数」从 6 掉到 3，用新流里这一数的闭式预测可以杀（正推腿对）；但它改的是枚举器，用到它的每条流和 `crash.rs` 库内单测也会红。登记完整性检查（`assert_every_state_was_seen_by_the_observers_attached_to_the_flow`，同文件 `:897`）数的是观察者看过几个状态，杀不到这一行。去掉屏障那一行核心变异倒是被观察者杀得掉（9 个新死盘态），这是观察者真正的判别力所在。

**对 C874「不手造写表」字面的影响**：杀「判槽计数把撕裂的槽数成自证」这一类，不需要手造写表，对判槽计数函数（`crates/singlefs-checker-tier/src/crash_judge_conclusions.rs:1380` 的 `self_verified_system_configuration_slots_of_each_device`）喂一个撕裂字节的槽镜像做单测就够，那是函数单测，不是流。

**建议判决**：C874 欠账行的「观察者的变异行至少四条：不判、只判整写不判撕裂、不取基镜像、判槽读法恒为「有」」（`.claude/kb/checks-owed.md:540`）里「只判整写不判撕裂」拆成两行：① 判槽计数把撕裂的槽数成自证（挂在判槽计数函数的单测上杀）；② 枚举侧撕裂退化成整写（用新流里「D 没有自证槽的状态数」闭式预测杀）。另加第五行：去掉补写两轮之间屏障的核心变异，由观察者杀（模型里 9 个新死盘态）。把「观察者自己的撕裂变异」记成等价变异，不要求流上杀。

**什么现象会推翻它**：在不注入故障录下来的补写流上找到一个撕裂态，观察者按逐盘数判出一块新死盘（则屏障或槽分配的推理错了）；或观察者与枚举器之间还有一层按撕裂与否分开计数的合并。
