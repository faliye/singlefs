## 一、这一轮要判什么

用户 2026-09-24 定（原话与经过在 `records/2026-09-24-里程碑二收尾调度.md` 第三节）：分配记录树与 extent 树按 key 空间定形状、**不分裂**；中央映射树与记账树照树分裂那一轮定的细则做（`research/prompts/m2-treesplit-r1-main-verification.md`）。同日用户选「改 D8（核心索引结构） 已定项 14，允许异构」：这两棵派生树可以另起一套按 key 空间寻址的结构，格式可以与码 2 btree 不同。前提：两棵都是派生态（`.claude/kb/decisions/21-权威态与派生态的分界.md`「#### 已定项 5」「#### 已定项 9」）——可重建、退出格式冻结、「没有换格式这个操作，只有重建」（已定项 12），而且损坏必须可检出（已定项 11）。

用户对这一块的两条嘱咐照旧有效（原话见调度表第三节）：每一种新写序都要进层 0 崩溃点；从块自描述出发设计、不照搬别家的算法——别家文件系统的做法不进正推、反推、校验任何一步。

| 格 | 题 |
|---|---|
| S1 | 分配记录树的几何：key =（设备 4, 槽号 6），一条记录罩一段槽 [槽号, 槽号 + 跨度)。叶管多宽一段槽才永远装得下（一条记录至少 1 槽）；记录按起点槽落叶，跨过叶边界的那一段怎么认；上面几层每层扇出多少、子节点的 key 区间是写在条目里还是按位置隐含；没有记录的一段是「缺席 = 全空闲」还是要写空叶；层数由什么定（设备槽数在 mkfs 时就定了） |

| S4 | 写序与层 0：一次发布里这两棵树写哪几个节点、落在哪一段（照 D16 已定项 7 的持久顺序）；长一层、摘空节点各算不算新写序；层 0 要加哪几条流 |
| S5 | 与别的结构的咬合：中央映射（两棵树的节点也经映射寻址，D19 已定项 5）、记账、准入（D28 已定项 4 的 ckpt_cost 要「当前的高」——层数固定之后怎么读）、回收、挂载怎么读 |
| S6 | 代价：每个候选每次发布写几个节点、层数随设备大小与文件大小怎么长、挂载读量、空间，与照分裂细则做（上一轮的数）并排 |

## 二、实现今天的样子（主 agent 的观测，2026-09-24 现查）

- 两棵树今天都是根兼叶的码 2 节点：分配记录树 key 宽 10、条目 20（key 10 + value 10，`crates/singlefs-format/src/lib.rs` 的 `ALLOCATION_RECORD_BYTES`），一片 812 条，装不下交回 `PublishError::AllocationRecordsExceedOneNode`（`crates/singlefs-core/src/transaction.rs`）；extent 树 key 宽 24、条目 112（key 24 + 数据指针 88），一片 144 条，多于 144 个数据单元交回 `ExtentTreeNeedsAnInternalNodeWhoseEntryFormatIsUndecided`。
- 分配记录的读写在 `crates/singlefs-core/src/allocator.rs`（`PoolAllocator`、`DeviceFreeMap`），记录态「已分配」「已释放 + 释放代」两种（D3 已定项 7）；同一次挂载里按根环表回收（实三 C518）。extent 树的写在 `crates/singlefs-core/src/transaction.rs` 的 `publish_sequential_write` 一带，读在 `crates/singlefs-core/src/mounted_read.rs`。
- 两棵树的节点今天都经中央映射寻址（码 2 条目在映射里、指针带位置提示，D19 已定项 5、12）。
- 冻结层归属：两棵树的 key 编码与节点布局都登记为派生态、退出冻结（`.claude/kb/freeze-layer-membership.md`）。

方案按 `crates/` 今天的实现来谈。

#### 已定项 3：key 布局 —— 改名与索引分开处理

**定案**：**key = `(locality_id, inode, offset)`**，`locality_id` 在创建时从父目录继承，**改名时故意不更新**。offset 段是**文件字节偏移**（这个单元第一个字节在文件里的偏移，第 n 个单元从 0 起是 n × 净荷容量 32634）。

- 命名走 dirent 树（`parent, name` → inode），改名就是删一条加一条，**O(1)**
- 数据按 inode 编 key，与名字彻底解耦
- scan 局部性来自继承的 `locality_id`，改名后**局部性缓慢退化，正确性不受影响**
- 退化由 D3（空间分配） 已承诺的常驻后台整理修复，不是新增负担

**批量改名**：`mv 大目录 别处` 在这个设计下**只改一条 dirent**。三处会把它重新变成无界操作，必须一开始就堵死：

1. **`locality_id` 永远不许被改名更新。** 它是**提示，不是正确性的一部分**——可以是错的、可以过期。
2. **改名覆盖已存在的目标 = 一次删除**，必须走已定项 5（whiteout 删除）的 intent log。
3. **后台重新聚簇必须是增量、可中断、可续做的**，且随时可以停掉不做。

**推论（可当 review 判据用）**：**任何让 rename 触及后代的设计改动，一律否决。**

**inode 记录必须存一份 `locality_id`**：它既是数据 key 的首段、又永不随改名更新，而命名树的 value 只有 inode、数据单元头的五元组里也没有它，所以盘上只有 key 自己带着它——读者打开一个改过名的文件时必须有地方拿到它，否则改名之后数据只能靠扫描才找得到。落点是已定项 6（inode 记录的盘上字段表）；这个值按本项从父目录继承，而第一版没有目录，所以「没有父目录时取什么」也要一起定——第一版取 0，登记在已定项 6 的记录字段表。扫描重建时重编出来的 key 首段按 inode 记录 > 幸存 extent key > 0 给这个对象的全部 key 编同一个首段（2026-09-16 用户定案，D18（块里携带什么信息） 已定项 3 那条加字段的提议不收）。
