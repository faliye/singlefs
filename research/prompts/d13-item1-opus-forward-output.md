## 一、先从定义推：第一个验证对象要满足哪几条（写在看候选之前）

### 1.1 把定义摊成一个证明义务

`.claude/kb/prior-art.md:493` 逐字：

> | 按钮式形式验证 | Yggdrasil（OSDI 2016，Best Paper） | **crash refinement** 正确性定义：实现能产生的磁盘状态集合（含崩溃产生的）必须是规范允许集合的子集。Z3 自动验，**无需人工标注或证明** | 实现要写成可符号执行的形态；论文称把逻辑表示与物理表示分离后验证时间降到一分钟内 |

把这句话摊开，义务的形状是：

```
∀ s ∈ 起始状态集.  ∀ c ∈ Crash( Impl(s) ).   Recover(c) ∈ Spec(s)
```

**它有五个入参，不是两个**：状态编码、`Impl`（写侧）、`Crash`（崩溃模型）、`Recover`（恢复函数）、`Spec`（允许集合）。
背景材料第二节说「这个定义有两个入参」——那是把中间三样默认掉了，而本工程恰恰在中间三样上有已定条款、
也有空白，**选题的胜负就落在中间三样上**。

### 1.2 十条判据

前四条是**门槛**（不满足 ⇒ 今天建不出模型，不是排后面），后六条是**价值排序**。

#### 门槛

| # | 判据 | 为什么它是门槛 |
|---|---|---|
| **P1** | **状态变量集对被验的操作封闭**：凡能写这些变量的操作，必须全在 `Impl` 里 | 漏掉一个写者，Z3 照样报 `unsat`——**模型不健全这件事在模型内部不可观测**。别的判据破了会看见反例，这一条破了看见的是「证明成功」。所以它排第一 |
| **P2** | **`Crash` 已经被别人定死，且它的定义与被验性质无关** | 边建模型边选崩溃模型，就永远可以把 `Crash` 削到定理成立为止。这是 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「不许先有结论再建模型」在崩溃模型上的形态 |

### 1.3 判据自己的反推

## 二、判据指向一条材料里没有的臂

把 P1 与 P9 放在一起看，**最小的封闭单元不是「择新」，也不是「一次发布」，是「一次发布 + 一次崩溃 + 一次恢复」**：

- **P1 封闭性**：根槽的写者只有三种——发布（D22（单元原子性怎么合成） 已定项 2 逐字「**区域按素数步长放置、槽序跨区轮转**」，轮转键是 txg）、mkfs 种子（D22 已定项 8 第 3 条）、实例切换 / 管理员回退（D23（journal 的角色与格式） 已定项 14）。journal 环的写者只有两种——发布（D16 已定项 7 第三步）与 tail 推进（D23 已定项 3）。**没有任何 btree 操作写它们。** 这个变量集恰好被「一次发布 + 一次恢复」封闭，一个不多一个不少。
- **P1 也说明「只验择新」是切错了地方**：D23 已定项 14 逐字「**恢复只施加 `(实例代号, checkpoint_txg)` 严格大于所选根的记录；陈旧 tail 只是「从哪开始扫环」的优化，不再决定重放集合。**」⇒ 择新的输出**就是**前缀判定的下界。把这条已定项从中间切开只验前半，等于把 bug 最爱住的那道接缝留在模型外面（C77（重放起点未定义）、C124（回退行与重放下界没有会红的检查） 两条欠账都在接缝上）。

| **D-1 全性** | `Recover` 在 D13 已定项 4 定义的**每一个**崩溃状态上有定义、终止、输出一个能过 I-7.1（根槽有效集非空） 与 I-8.3（重放前缀严格连续） 的镜像 | 脚手架，不是产出（理由见第五节） |

### 2.1 臂 D-2 的 spec 已经在仓里跑着，而且带阳性对照

`.claude/kb/experiments/42-一事务几条记录.md:42` 逐字：

> **枚举全部前缀，按状态判合法**（重放出的 map 要与某个「整数个事务已提交」的真值 map 逐条相等）：

那张表整行抄：

> |---|---|---|---|---|---|

以及它自己写下的口径（逐字，`experiments/42-一事务几条记录.md:69`）：

> **口径**：200 个事务 × 每事务 8 条幂等完整值写入（D25（目标负载优先级） 已定的粗粒度），
> 每事务切成 8 / 4 / 2 条记录三档。key 与 value 都由事务号唯一决定
> ⇒ **半个事务的状态不可能与任何已提交状态相等**，所以「非法数 = 被切开数」是可预期的等式，不是巧合。

**这段口径就是 P8 要的那个边际价值，写得比我能写的更清楚**：E42 为了让「被切开 ⇒ 非法」成为恒等式，
**故意选了一个 key 与 value 都由事务号唯一决定的载荷**。真实负载不长这样——两个事务会写同一个 key。
于是两类情形 E42 的模型**结构上看不见**：

1. 一个被切开的前缀，其结果**碰巧**等于某个已提交状态（bug 被载荷掩盖）；
2. 一个**没**被切开的前缀却非法（边界字段之外的原因）。

**把载荷符号化正好覆盖这两类**，而这是枚举做不到的：枚举必须给载荷取具体值，取哪一组值本身就是一次建模选择。
⇒ 臂 D-2 相对 E42 的增量是可说清的一句话：**E42 把载荷钉死、把 chunk 取了三个点、把事务数取了 200；
refinement 对这三维全称量化。**

⚠️ **顺带更正一处转述**：D16 已定项 7 引 E42 时写「E42（一事务几条记录）实测 87.4% 崩溃点落在事务中间」，
而 E42 正文逐字是「chunk=1 时 **1601 个前缀里 1400 个非法，占 87.4%**」，那 1400 的非法性
**只在「无边界字段」那一臂成立**；同样 1400 个被切开的前缀，在「有边界字段」臂上非法数是 **0**。
两句话说的是同一批前缀的两种命运，不是同一件事。这处不影响本轮判决，记一笔。

## 四、材料第八节的五个问题

### 第 1 问：左边那个「可符号执行的实现」在第一版不存在，意味着什么

**先分两种「不存在」，它们的处置完全相反。**

| 类型 | 例子 | 判定 |
|---|---|---|
| (i) **还没写，但确定会写** | 臂 B / C / D 的恢复路径 | **不是障碍，是时机。** `verification-build.md` 落地顺序第 2 步逐字：「自证单元的两份解析器（实现一份、checker 一份）：根记录 127 字节、journal 记录头（先按「待定案」第 7 问把 78 / 91 / 95 收成一个数）；超级块槽是第三个自证单元，等 D22（单元原子性怎么合成）未定项 9 定了字段表再补。**记录核对器的前缀判定也在这一步起手——它只消费记录流与镜像，不等数据侧的字节**」⇒ 恢复路径是第一版**必然**要写的第一段代码。把它写成可符号执行的形态是一次性的写法约束（纯函数、无 I/O、循环上界静态），**不是额外的实现** |
| (ii) **明令第一版不写** | 臂 A 的加密（D9 已定项 10） | **是障碍，形态就是 P3** |

**若硬要为臂 A 单写一份影子实现，代价有三笔：**

1. **两份实现之间的一致性没有任何 oracle。** D13 三个 oracle 的入参逐字分别是「一个镜像」（O2）、
   「POSIX 可见语义：内容、大小、目录结构」（O1）、「崩溃点截断后的每个磁盘状态是否落在规约允许的集合里」（O3）。
   **没有一个吃「两份 Rust 源码是否同语义」。** 记录核对器也不吃（它的入参逐字是
   `(崩溃前镜像, 记录流, 崩溃后镜像)`）。
2. **影子实现证的是影子。** 真实现落地时，refinement 要么重做（第一次白做），要么用「我们照着影子写的」兜底——
   而那正是 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「校验路径本身也要证明它会红」要禁的：
   **影子这条路子永远不会红。**
3. **加密写路径的规模就不小。** 它要覆盖 nonce 分配、AAD 组装（D9 已定项 6 绑五项）、
   w ≥ 2 副本共用 nonce（I-6.7）、崩溃后水位恢复。这不是「一个水位变量 + 恢复路径」——
   材料里「它触及的实现面极小」这个估计只有在**已经**替仓里选定了 nonce 分配规则之后才成立。

**⇒ 结论（这是 P3 的来源）**：不要写影子实现；要把**将来会发运的那段代码**写成可符号执行的形态。
这条把选题条件反过来了——**第一块必须落在第一版一定会写的代码上**。按 D9 已定项 10，臂 A 不是。

### 第 2 问：D13 已定项 4 那个崩溃状态集合，算不算 refinement 右边的现成规范

**不算。它是左边的一部分。**

在 `∀c ∈ Crash(Impl(s)). Recover(c) ∈ Spec(s)` 里，已定项 4 定义的是 `Crash(·)`——
也就是 prior-art 那句定义里「实现能产生的磁盘状态集合（**含崩溃产生的**）」中「含崩溃产生的」那条产生规则。
**它扩大的是左边那个被检查的集合，不是右边那个允许集合。**

已定项 4 自己的射程句逐字就是这个意思：

> ⚠️ **射程**：它定义的是模型层的枚举域。真实设备的 FLUSH / FUA 是否如宣称生效归 C6（块层语义假设写错），
> 要在 QEMU 里用真设备验；设备把一次写撕成恰好撞上校验和碰撞的形态不在模型内。

「枚举域」是**要被检查的对象集合**，不是允许集合。

**反证（做得到、这一轮做得完的观测）**：把已定项 4 当 `Spec` 会让 refinement **恒真**——
任何实现产生的崩溃状态，按定义都落在「屏障切段、段内任意整写子集」里，
包括一个把用户数据全写成零的实现。一条按字面恒真的判据，与 D13 自己点名过的那个毛病同形，逐字：

> | D23（journal 的角色与格式） 的反向判据「O2（独立解析器 + checker） 抓到而 checker + O1（内存模型对拍（HashMap 理想文件系统）） + 崩溃点重放三者都没抓到的事件数为 0」 | **按字面恒为 0，不可证伪**——D13（验证路线）里 O2（独立解析器 + checker） **就是** checker。主语改成**记录核对器** |

⇒ **材料第八节第 2 问的前半句（「臂 B 与臂 C 的规范右边已经由 D13 已定项 4 定死了」）不成立。**
三条臂的 spec 都要另建，臂 B / C 在这一维上**没有**相对臂 A 的优势。这不改变排序（臂 A 输在别处），
但若这句话进过任何一轮判决，那轮要复核。

**真正现成的是什么**：已定项 4 现成给的是 **`Crash`**，这很值钱——P2 全靠它，而且它是**用户定案 + 三方对抗**定的，
不是选题的人自己挑的。至于 `Spec`，仓里现成有两条候选，都不是从实现推出来的：
C37 那条候选不变量（臂 D-2），和 I-8.4 逐字「任一 journal 记录被重放两次与重放一次，产生的盘上状态相同」（臂 D-3a）。

### 第 4 问：排序，以及什么会让它翻转

**排序：D > C > B > A。**

⚠️ **更准确的读法**：C 与 B 不是与 D 并列的选项，是 D 的两个部件——
C 是 `Recover` 的第一步，B 是产生崩溃状态的那个 `Impl`。所以真正的建议不是「选 D 而不选 C」，
是「**按 D 的三个 milestone 排，C 与 B 各自作为 D-1 的组成部分被顺带做掉**」。

**排序的可翻转条件**（每条都写成一个能观测到的现象）：

| 观测到什么 | 排序翻转成什么 |
|---|---|
| D18 已定项 13（含 13-b 那条硬前置）与 D22 未定项 9 都定了，**并且**新开一条分项把 nonce 分配规则定成「按实例的单调计数器 + 预支水位、水位在使用前持久」 | 臂 A 从「今天建不出模型」变成可做，但仍卡在 P3——除非同时推翻 D9 已定项 10 |
| 层 0 崩溃点重放跑起来之后，C37 那条候选不变量被做成一条会红的检查，**并且在层 1 抽样里稳定复现失败** | D-2 的边际价值下降（枚举够用了），D-3 升到第一，D-2 降为 D-3 的一个用例 |
| 事务层第一版写出来之后发现恢复路径**写不成静态有界的形态**（例如全环扫描的上界要数据依赖，或实例表链长度无界） | P5 破，臂 D 整条降级，退回臂 C（择新是定长 R × S 次比较，一定有界） |
| Z3 在「环长 × 记录数」符号化之后 timeout，而且收窄到具体值之后**仍然** timeout | 臂 D 出局，退回纯枚举。⚠️ **timeout 一律判红**（C5（Z3 超时当通过） 逐字：「门禁的 crash refinement 阶段必须有**三种**结果（证明 / 反例 / timeout），timeout 一律判红」），不许当通过 |
| D13 已定项 2（先串行提交）改成并行 | **不翻转排序，反而抬高 D-2**。D13 逐字：「**并行提交下一个前缀可能同时含有完整的事务 B 与残缺的事务 A** ⇒ 要么记录里带事务分组或边界标记，要么 D16（发布语义） 那句已定的崩溃语义要改」——那正是 D-2 要回答的那一问 |
| 用户改口径说第一版不做形式验证这条腿 | 整条未定项作废，不是排序问题 |

**不会让排序翻转的**（写下来是为了拦住几条看着像理由的理由）：

- 「臂 A 防的是唯一一类静默且不可恢复的失效」——真的，但 P10 是价值判据不是门槛，压不过 P1/P3/P4。
  而且这条已经有落点：E5 那份枚举实验。
- 「nonce 水位字段 8 字节已经在超级块里预留了」——E100 逐字「| 一 的 D9（加密） 预留 | 24 | MAC 16 + nonce 水位 8（D9（加密） 已定项 8 + D15（格式冻结政策） 止损规则）|」。
  **预留一个字段不等于定了它的更新协议**，而 refinement 消费的是协议不是宽度（P4 的 ⚠️）。
- 「Yggdrasil 本来就是先写可符号执行的实现」——那句话在 prior-art 里逐字是
  「实现要写成可符号执行的形态」，说的是**形态**，不是「先写一份额外的」。见第 1 问。

### 第 5 问：对臂 D 最强的反对

**最强的一条：臂 D-2 的 spec 与「记录核对器」的实现是同一个东西。**

D13 逐字给记录核对器的定义：

> ⇒ **给它一个名字：「记录核对器」，入参 `(崩溃前镜像, 记录流, 崩溃后镜像)`。**

而臂 D-2 的 spec 正是对这三样的一个谓词。⇒ **冲突 2 在这里换了个对手**：不是与 O1 同源，是与记录核对器同源。
而记录核对器的成本是 D16 未定项 4 逐字「**记录核对器那第二份 replay 实现的成本**，以及它与 D13（验证路线）「三 oracle 合谋测试」怎么配合」——**它自己都还没定**。
如果两份由同一个人在同一周写出来，「refinement 证明了前缀语义」与「记录核对器判前缀语义」就是同一份理解跑两遍。

**能不能缓解**：能，按冲突 2 逐字的两条办法——表述层面拉开（refinement 写成「对记录流前缀的全称量化」，
记录核对器写成「逐条施加并比对」），加上逐字的「**同源性要被观测**：统计「spec 与 model 不一致」的事件数及每次判定哪一方错；
若累计 ≥ 5 次不一致而判定「spec 错」的次数为 0，说明两者实际同源，应把两条腿合并、预算移给穷举。」
⚠️ **而这条计数今天全仓零落点**（现查 `grep -rn "spec 与 model 不一致" .claude/kb/`：**1 处命中**，是 `decisions/13-验证路线.md:207` 冲突 2 自己那一句）
⇒ 采纳臂 D 的同时要立一条欠账：那个计数器住哪、谁维护。

**第二强：D-1 在层 0 上是重复劳动。** 层 0 全量枚举本来就会把每个崩溃状态跑一遍恢复，恢复卡住会当场暴露。
⇒ 这条反对**成立，而且已经被接受**：D-1 的完成判据不是「证出来了」，是「D-2 能在它上面写出来」（第三节末）。

**第三：「校验和过了」被建成布尔标志，等于把 CRC32C 的判别力当公理。**
这与 D13 已定项 4 逐字「差别只有 CRC32C 的碰撞概率（32 位，D19（块指针的结构与宽度预算）已定项 2、
D23（journal 的角色与格式）已定项 11），**知情接受**」是同一笔账，refinement 继承它。
⇒ **结论里必须写明「不许读成 refinement 验了完整性」**，与 D4 连锁逐字「**不许读成「验了 Merkle」**」同形。

**第四：形式验证这条腿今天不在任何落地计划里。** 现查 2：`verification-build.md` 第七节六步里
「形式验证 / refinement / Z3 / 符号执行」四个词零命中。⇒ 采纳臂 D 之后，
**要在那份文档的落地顺序里给它插一格**，否则这条定案会成为一条没有执行路径的定案。
建议插在第 2 步与第 3 步之间——第 2 步本来就要写自证单元的两份解析器与记录核对器的前缀判定，
那正是臂 D 的状态编码。

## 五、臂 D-2 第一个 milestone 的具体形状

**名字**：D-2.0 —— 一次发布 + D13 已定项 4 的崩溃 + 一次恢复，前缀不切事务。

### 5.1 验的谓词

设：
- `Publish(s0, [T1..Tm])` = 按 D16 已定项 7 的持久顺序发出的写流（每次发布 3 段，段间两道 FLUSH + 根槽 FUA）；
- `Crash4(W)` = D13 已定项 4 的枚举域（前若干段全持久、当前段任意**整写**子集、之后各段全不持久；镜像双写按**设备**各算一次写）；
- `Recover(c)` = D22 已定项 7 的择新 + D23 已定项 14 的五条前缀口径；
- `commit(s0, n)` = 顺序施加前 n 个**完整**事务的结果。

义务：

```
∀ s0. ∀ m. ∀ 载荷. ∀ c ∈ Crash4( Publish(s0, [T1..Tm]) ).
      ∃ n ∈ [0, m].  Recover(c)  ≃  commit(s0, n)
```

⚠️ **`≃` 要单独写下来，它是 spec 的一部分，不许默认成「逐字节相等」**：
取「已发布单元集合 + 根记录的 `(实例代号, checkpoint_txg)` + 施加到的事务号」三元相等。
补齐字节、槽位轮到哪个区域、tail 停在哪，**不进等价关系**——它们是派生态。
（这条本身是一次建模选择，要按 `.claude/rules/three-way-inference.md` 单独交叉验一次。）

### 5.2 状态变量（全部是定长位向量或有限数组，一个 uninterpreted function 都没有）

| 变量 | 类型 | 谁写它（指到已定项） |
|---|---|---|
| `root[r][s] = (valid, inst: BV32, txg: BV64)` | R × S 数组，R = 3 是常量，S 符号且有上界 | 发布（D22 已定项 2：区域 = txg mod R）；mkfs 种子（D22 已定项 8 第 3 条）；管理员回退与实例切换（D23 已定项 14） |
| `ring[j] = (valid, jsn: BV64, inst: BV32, txg: BV64, txn: BV64, commit_mark: Bool, named[])` | 环长 N 符号且有上界 | 发布（D16 已定项 7 第三步）；tail 推进（D23 已定项 3） |
| `tail : BV64` | 标量 | D23 已定项 3（只在 checkpoint 持久之后写一次，不上 fsync 路径） |
| `unit_ok[u] : Bool` | 被点名单元的校验和过没过 | 发布第一步写；崩溃可把它翻成 false。**这就是把 CRC32C 当公理的那一格** |
| `rollback[i] = (Ti, Wi)` | 实例表行 | C113 定案 P2 / D23 已定项 14 |
| `applied : BV64` | 恢复施加到的事务号 | `Recover` 的输出 |
| `persisted[w] : Bool` | 每一次**整写**落没落 | **崩溃模型的自由变量，这一维就是要被 Z3 枚举的东西** |

⚠️ **反向表是完成判据之一**：每一个变量都要指得到一条已定项，指不到的当场立成欠账
（形态照 `first-txn-layout.md` 那张「字段 → 分项」的表做）。

### 5.3 Z3 要解的约束大概长什么样

```smt2
; ---- 崩溃模型（D13 已定项 4）----
(declare-const k Int)                             ; 崩溃落在第 k 段
(assert (and (<= 0 k) (< k nseg)))
(declare-fun persisted (Int) Bool)                ; 每次整写落没落
(assert (forall ((w Int)) (=> (< (seg w) k) (persisted w))))        ; 前段全落
(assert (forall ((w Int)) (=> (> (seg w) k) (not (persisted w)))))  ; 后段全不落
; 段内不加约束 —— 这就是被枚举的那一维
; 镜像双写：按设备各算一次写（已定项 4 逐字），两份各有自己的 persisted
; 没持久的位置放旧字节（已定项 4 逐字「不是零」）

; ---- 恢复（D22 已定项 7 择新 + D23 已定项 14 五条口径）----
(define-fun valid-set () ...)                     ; 自证校验和过的根槽
(define-fun chosen ()  (argmax valid-set (txg, inst)))
(define-fun prefix ()  ...)                       ; jsn 严格连续、断号即止
                                                  ; ∧ (inst,txg) > chosen 的水位
                                                  ; ∧ commit_mark 齐全才施加
                                                  ; ∧ 施加前 unit_ok 全真
                                                  ; ∧ 有回退行则截到 W
(define-fun applied () (last-txn prefix))

; ---- 目标：取否定喂给 Z3，期待 unsat ----
(assert (not (exists ((n Int))
   (and (<= 0 n) (<= n m)
        (state-eq (recover ...) (commit s0 n))))))
(check-sat)      ; unsat = 证明；sat = 反例；timeout = 判红（C5）
```

**规模控制：先有界，再谈全称。** 第一版把 `m`（事务数）、`N`（环长）、`S`（每区槽数）取成小的具体值，
只把 `persisted` 与段内子集、以及**载荷**符号化。起步取 `m = 3, N = 8, S = 2, R = 3, w = 2`。
证出来之后逐维往上抬，抬到 timeout 为止，**把 timeout 的那一档写进 kb**——
那一档就是这条腿的射程，必须显式写出来（`.claude/singlefs-ai-sop/rules/kb-discipline.md` 第 3 条「显式记录『不知道』」）。

### 5.4 先证明它会红：三条阳性对照，缺一不可

| # | 怎么改坏 | 必须看到什么 | 依据 |
|---|---|---|---|
| 1 | 关掉 D23 已定项 14 的第三条口径（「提交标记齐全的事务才施加」） | **`sat`**，反例形态是「前缀落在事务中间、恢复施加了半个事务」 | E42 逐字：无边界字段臂 1400 / 1601 非法；有边界字段臂 **0**。**这一条不红 ⇒ 模型压根没在看事务边界，整轮作废** |
| 2 | 摘掉 D16 已定项 7 的第二道屏障（记录先于根槽） | **`sat`**，反例是「根在案而记录缺席」 | E77 那张表逐字：`\| b_ur [单元][记录+根槽] \| 79 \| **0** \| 0 \| **7** \|` ⇒ ⚠️ **数据违例是 0，记录洞才是 7** ⇒ 这条对照判的是**记录流完整性**那一支，不是数据完整性。`verification-build.md` 的三方对抗已经在这里踩过一次坑，不许重犯 |
| 3 | 关掉「施加前逐项验证点名单元」**并且**把一个被点名单元的 `unit_ok` 置 false | **`sat`**，反例是静默嫁接 | E77 逐字：`\| b_rs [单元+记录][根槽] \| 513 \| **0** \| **63** \| 0 \|`；而 `\| b_all [单元][记录][根槽] \| 72 \| **0** \| 0 \| 0 \|` ⇒ **只关验证、不改坏单元不会红** |

### 5.5 什么时候算做完（判据写在跑之前）

1. 三条阳性对照全部 `sat`，且**反例被人读懂**——读不懂等于模型不对，不算红。
2. 原样模型在 `m = 3, N = 8, S = 2, R = 3, w = 2` 上 `unsat`。
3. 逐维抬到 timeout，记录最后一个 `unsat` 的档位与那一档的挂钟。
   ⚠️ 这里的 timeout **不是 milestone 失败**——产出就是「射程到这一档为止」，那个档位要进 kb。
   （门禁阶段里的 timeout 才按 C5 判红，两件事别混。）
4. 5.2 那张表里每个状态变量都指得到一条已定项；指不到的当场立成欠账。
5. **那份可符号执行的 `Recover` 就是 `crates/` 里将来要发运的那一份**（P3）。落地形态：
   `Recover` 写成一个不含 I/O 的纯函数，入参是「镜像的解析结果」，
   由块设备后端与符号执行后端各喂它一次。
6. 与 checker 只共享那份从 kb 生成的常量模块（D13 已定项 5 逐字：
   「**checker 与实现之间只共享一样东西：一份由 kb 的字段表生成的常量模块**」）；
   择新与前缀判定**各写一份**：refinement 一份、checker 一份、记录核对器一份。
7. 同时立一条欠账：冲突 2 那个「spec 与 model 不一致」的事件计数器住哪、谁维护（现查全仓零落点）。

### 5.6 它挡在谁后面

**不挡在 D22 未定项 9（超级块字段表）后面**——这是臂 D 相对臂 A 的另一处优势。
5.2 那张表里的变量全部来自根记录（D22 已定项 7 的字段表）与 journal 记录头
（D23 已定项 4 的 78 字节 + 已定项 7 的 9 字节增量），**没有一个住超级块**。
⚠️ **不引根记录的总字节数**：同一节里合计栏写 194、它自己的改动注写 186、
`verification-build.md` 两处写 127（现查 `grep -n "合计 \*\*194\|从 127 改成 186\|根记录 127"`）。
这处三说不一与本轮判决无关——**refinement 不消费宽度**（P4 的 ⚠️）——但它进第六节。

⇒ **臂 D-2 今天就能开工**，与 `verification-build.md` 落地顺序第 2 步同批，
