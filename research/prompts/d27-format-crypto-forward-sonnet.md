## 一、把三项推成一个完整形态

### 1.1 容器占登记表哪个码

**取新码 4**，不复用码 3。理由不是"更清晰"，是**装载纪律冲突**：D18（块里携带什么信息）

### 1.3 容器怎么被引用（未定项 3/7/9 都没直接问，但推不下去这三项就填不满字段——见五、(a)）

**我推荐的形态**：**不新开一棵"容器索引"树，走中央映射（D19 已定项 5）**。

依据：D19 已定项 5 定的中央映射「key 取逻辑身份五元组…value 是 `w` 份位置条目」
（`19-块指针的结构与宽度预算.md:142`）对"这个对象现在物理上住哪"这件事本来就是通用入口，
不区分对象是独立单元还是打包容器成员。**一个容器里的 N 个对象，各自在中央映射里有一条条目，
N 条条目的 value（`w` 份位置条目）逐字节相同**（都指向同一个容器物理位置）——这是允许的冗余，
不是错误：中央映射的语义是"这个逻辑身份现在能在哪找到"，多个逻辑身份共享同一个物理落点没有
撞任何已定条款。

读路径：解引用对象 X 时，走中央映射拿到物理位置 → 读该位置的单元头 → 若偏移 6 的单元类型标签 = 1
（数据单元），整个 32768 字节就是 X 的；若 = 4（打包容器），进一步在槽目录里按 X 的五元组身份匹配，
拿到该槽的偏移+长度，再解密。**这条分支判据（读到的标签值）不依赖任何操作期间会变的输入**，
满足 `.claude/rules/fs-design.md` 分支硬要求 1 与 5。

这个选择让码 4 **不需要新增任何 D19 已定项 4/5 的字段**，只是多了一层"读到容器还要再查槽目录"的间接。

### 1.5 AAD 的规范编码

**每个槽自己的 AAD**（用于该槽的 AEAD）= `(单元类型标签=1, 树ID, 对象ID, 对象出生代, 锚点偏移)`，
**与该对象作为独立单元（码 1）时的 AAD 逐字节相同**——不随打包与否变化。这是本轮任务第 4 点的答案，
详细论证见下面第四节。

**容器自己的结构完整性**不走 AEAD/AAD 机制，走两层非密钥手段：① 头校验和（32 字节，覆盖偏移
0 到槽目录末尾，见下）；② 中央映射位置条目里的密文校验和（4 字节，覆盖整个物理单元的密文字节，
职责与码 1/码 3 相同，无需码 4 自己另开一份，见 1.2 节）。**容器本身不需要一份独立的、绑定"容器身份"
的 AAD/MAC**——这是"每槽各自加密"这条路线的直接推论：容器不再是一份被整体 AEAD 保护的对象，
它退化成"N 个独立 AEAD 密文 + 一层非密钥的结构完整性校验"的容器（字面意义上的容器）。

**头校验和覆盖范围**（I-2.4 的公式在码 4 上的具体形态）：`[0, 95 + N×75)`——覆盖公共前缀 + 类身份段 +
整个槽目录（含全部 N 个槽的 nonce/MAC/身份/写序/槽表条目），**不覆盖任何槽的密文载荷**（载荷的完整性
由各自的 AEAD MAC 负责）。⚠️ **这是 I-2.4 迄今唯一一处端点依赖"同一份头里读到的一个变长字段（槽数 N）"
计算出来的案例**——码 1/码 2/码 3 的头校验和端点都是固定常量（105/68-86/103），码 4 是第一个"公式里
带变量"的类。I-2.4 原文本来就写成公式化的话（"端点随…字段表走"），字面兼容，但这是一个新的模式，
值得在改 I-2.4 时显式点一句，免得实现者假设端点总是常量。

## 二、容量重算：三档，逐档给算式

**容器总字节 = 32768。头 = 95（1.2 节）。每槽开销 = 75（1.4 节）。**

设对象大小为 S，容器能装的对象数 N 满足：`N × (S + 75) ≤ 32768 − 95 = 32673`，即
`N ≤ ⌊32673 / (S + 75)⌋`。

| 对象大小 S | 算式 | N |
|---|---|---|
| 512 | 32673 / (512+75) = 32673 / 587 = 55.66 | **55** |
| 1024 | 32673 / (1024+75) = 32673 / 1099 = 29.73 | **29** |
| 4096 | 32673 / (4096+75) = 32673 / 4171 = 7.834 | **7** |

**与背景材料的对照**：背景材料用的是主 agent 的算式 `(32768−103)/(size+每槽开销)`——**103 是照抄码 3
的头宽度，没有为码 4 重新推导**（码 3 头 103 = 共同前缀 42 + 码 3 类身份段 61，而码 4 类身份段是 53，
少 8 字节；见 1.2 节"我从主 agent 的字段表里去掉了两样"）。用 103 算：512 档 (32768−103)/587=55.68→55，
1024 档 (32768−103)/1099=29.72→29，4096 档 (32768−103)/4171=7.833→7——**三档取整后与我用 95 重算的结果
完全相同**（55/29/7），因为 95 与 103 只差 8 字节，在这三个规模上都不足以跨过一个整数边界。

⇒ **背景材料引的容量数（55/29/7）字面正确，但推导路径有瑕疵**：主 agent 没有为码 4 独立推导头宽度，
直接借了码 3 的 103。这次巧合没有产生错误结论，但这不是可以依赖的做法——**下次容器头字段表变了
（比如 1.2 节我去掉的两个字段被人加回来），"借用码 3 的头宽度"这个习惯会在某个规模上悄悄算错，
而没有任何检查会报警**（这类"两套装置算同一个量却没有东西去对"的坑，`show-me-test.md` 点名过）。

**与 D27 已定项 2 的整容器一份 MAC 基线对照**（该基线的头是 103、每槽开销 47，来自 `27-小数据打包容器.md:52-60`）：

| 对象大小 | 基线（一份 MAC） | 本方案（每槽 MAC） | 差 |
|---|---|---|---|
| 512 B | 58 | 55 | −3 个对象，−5.17%（(58−55)/58） |
| 1 KiB | 30 | 29 | −1 个对象，−3.33%（(30−29)/30） |
| 4 KiB | 7 | 7 | 0 |

（此表数字与背景材料一致，属确认而非新结果。）

## 三、连锁清单：这个形态一旦采纳，哪些已定条款要改

逐条给「条款现在逐字说什么 → 要改成什么 → 算不算格式断裂」。

### 1. D9（加密）已定项 4——nonce 载体

**现在逐字什么**：「**指针头部为每个逻辑 extent 存一份 96 位 nonce。**」（`09-加密.md:427`）

**要改成什么**：补一条例外分支——「对被打包进小数据容器的对象，其 nonce 不住引用它的指针头部，
改住容器内该对象所在槽的槽头；宽度不变（96 位），职责不变（每逻辑 extent 恰一份）」。

**算不算格式断裂**：**是**。这条改动没有反转任何已发布字节的解释（旧的、未打包的独立单元仍按旧规则），
但它给"day-1 永久契约"的字面范围开了一个新分支（"住哪"从单值变成按物理形态分派），必须在
**加密开机之前**定死——这正是 D27 未定项 7/9 自己标注的射程（`27-小数据打包容器.md:81,93`：
「必须在加密开机之前定死」）。

### 2. D19（块指针的结构与宽度预算）已定项 3——定宽恒定占位，且明令不用类型标记省

**现在逐字什么**：「**指针按最坏情形定宽**：头部里的 MAC（128 位）与 nonce（96 位）**恒定占位**，
不加密的卷把它们留成空位，**不用类型标记省掉**。」（`19-块指针的结构与宽度预算.md:262-263`）

**这一条是本轮最硬的一处冲突，我推不下去，见第五节 (b)。** 简述矛盾：如果小对象被打包后，
其 nonce/MAC 从"指针头部"搬进了"容器内槽头"，那么引用这个对象的指针头部里，MAC128+nonce96 这两个
字段**对这个对象已经不再需要**——但已定项 3 要求"不管加不加密都占位，不用类型标记省掉"。两条路
都要付代价：(a) 继续让指针头部占位但内容作废（这些字节变成纯粹的浪费，且要在 checker 里显式豁免
"这份 MAC/nonce 不参与验证"，等于打破"占位的字段总是有意义"这条隐含假设）；(b) 引入"这个指针是否
指向打包对象"的判据来决定是否要头部里的 MAC/nonce 位——**这正是已定项 3 明确否掉的"用类型标记省掉"**。
本轮**没有第三条路**，因为 1.3 节选定"走中央映射"之后，中央映射的 value 是「w 份位置条目」
（14 字节 × w，不含头部的 31 字节），而"头部"（含 MAC/nonce）住在哪个具体结构里，仓里从来没有
明确写过（见五、(b) 与 C68 的关联）。

**算不算格式断裂**：**是，且是本轮唯一一处直接推翻一条已定论证（不只是补充射程）的连锁**。

### 3. D4（校验和位置）已定项 1——数据 extent 的校验和/MAC 覆盖 32 KiB

**现在逐字什么**：「**数据 extent 的校验和 / MAC 覆盖 32 KiB。**」（`04-校验和位置.md:60`）

**要改成什么**：加一条射程限定——「本条只管未打包的独立数据 extent；被打包进容器的对象，
其 MAC 粒度退化为槽粒度（≤4096 字节），容器物理单元级别的完整性另由头校验和 + 密文校验和承担，
不再有一份 32 KiB 的 MAC」。

**算不算格式断裂**：**是**，字面上把一条"已定"结论的适用范围从"全部数据 extent"缩窄到
"未打包的数据 extent"，需要走 decisions-history 记录（`kb-discipline.md` 第 4 条：矛盾比空白更糟，
同一事实只许一处权威记录）。不改变旧数据的解释。

### 4. D1（数据可移动性/反向索引）已定项 5——自包不可变数据带唯一一条指向

**现在逐字什么**：「**自包不可变数据带唯一一条指向**：「我属于谁」——五元组（树 ID / 对象 ID /
对象出生代 / 锚点偏移）。」（`01-数据可移动性-反向索引.md:84`）

**要改成什么**：射程扩展句——「本条对打包容器内的每个槽同样成立：槽头的五元组身份字段就是这唯一一条
指向，'新版写成即旧版断开、断开由树完成'的规则对槽内对象原样适用」。

**算不算格式断裂**：**不算**。字段的语义、宽度、判据全部原样复用，只是物理宿主从"独立单元"变成
"容器内的一个槽"——这与 D20 推论二把 I-1.x 从"元数据块"扩展到"任一单元"是同一种操作（射程扩展，
不改内容）。但仍然需要显式写一句话确认这一点，否则后续实现者可能默认 D1 已定项 5 只管码 1。

### 5. I-6.1（nonce 不重用）

**现在逐字什么**：「加密开启时，全盘任意两个**已写出**的块（不论当前是否仍被引用），其 (密钥代号, nonce)
二元组不相同」（`.claude/kb/invariants.md:187`）。

**要改成什么**：不改语义，改**检查实现的扫描范围**——checker 收集全盘 nonce 时，遇到单元类型标签=4
的容器要额外打开槽目录，把 N 个槽的 nonce 一并收进比对集合，不能只扫单元级的一份。

**算不算格式断裂**：**不算**，是检查覆盖面的扩展，不变量文字本身不用改。

### 6. I-6.2（明文头字段白名单）

**现在逐字什么**：「加密开启时，任一单元的明文头字段集合 ⊆ 它那一类的白名单，**两张，按…登记表的码分**
（码 1 数据单元类；码 2/3 元数据类…）」（`.claude/kb/invariants.md:188`）。

**要改成什么**：**开第三张白名单**（码 4 专属），而不是并进现有两张之一——因为码 4 的明文内容组合
（共同前缀 + 槽头里的 nonce/MAC/五元组/写序/槽表条目）与码 1、码 2/3 都不同：码 1 的白名单是
「共同前缀 + 五元组/诞生代号/fsid/写序/载荷CRC」，一次性、单份；码 4 的槽头字段是**逐槽重复 N 份**，
且新增了"槽表条目"这个此前任何白名单都没有过的字段类型（偏移+长度）。

⚠️ **槽表条目要不要进白名单，这里有一处此前任何决策都没审过的新泄漏**，需要在改 I-6.2 时一并交代：
**槽内偏移/长度这两个字段结构上必须是明文**，不是设计选择——它们的作用是"不解密任何东西就能定位到
第 i 个槽的密文边界"，如果这两个字段本身被加密，读者要先知道从哪解密它们才能读到它们，构成自举循环，
无解。⇒ 槽表条目是明文头字段白名单必须收的新一类，且它带来的泄漏是**逐对象的精确字节长度**——
这与 D18 已定项 3 已经知情接受的"锚点偏移直接给出文件大小与文件洞"（`18-块里携带什么信息.md:289`）
同一类（C173 待决问题的范畴），但**数量上从"一个容器一次 declared length"变成"一个容器 N 次
offset+length"**，泄漏粒度更细。这不构成新增一个泄漏"类别"，但需要在 C173 的范围里显式记一笔，
不能默认它已经被 D18 已定项 3 的知情接受覆盖了。

**算不算格式断裂**：**是**，需要新增一张白名单（不是改现有两张的内容），并把上面这条新泄漏点交代清楚。

## 四、AAD 绑对象身份时，搬运要不要重新加密——逐字段判定

任务要求：读 D9 已定项 6 的 AAD 字段表逐字，逐字段判断它在搬运前后变不变。**这次判定用的是
D9 已定项 6 正文里此前任何决策都没有引用过的一张表**（`09-加密.md:513-519`，「字段 | 为什么必须
在里面 | 谁提供期望值」），比背景材料引的"五项对快照维是瞎的"那半句更细。

AAD = `(单元类型标签, 树ID, 对象ID, 对象出生代, 锚点偏移)`（`09-加密.md:506-507`）。

| 字段 | 谁提供期望值（原文逐字） | 打包/搬运前后变不变 |
|---|---|---|
| 树 ID | 「查找路径」 | **不变**。D1 已定项 5：五元组"指的是出生所有者"，是不可变的诞生身份，与物理位置无关；D5 快照机制 2026-09-06 收口明确「搬迁不改 birth」——同一条纪律精神下，树 ID 属于逻辑出生身份，不随物理搬运改变 |
| 对象 ID | 「查找路径」 | **不变**，同上，出生身份的一部分 |
| 对象出生代 | 「密文侧」（对象出生代本身是密文侧的一个字段，但它的**值**是出生时刻钉死的） | **不变**。这是最直接的一条：D5（快照/空间记账机制）2026-09-06 明确收口——「搬迁不改 birth（2026-09-06 收口）…按 D5 给 birth(b) 的定义句「块被发布的那个 checkpoint 号」，搬迁不产生新的发布事件⇒ birth 原样跟着单元走」（`05-快照-空间记账机制.md:24-27`），并有 E94（搬共享落点的触碰面）实测背书（「重指派的违例数恰等于被快照引用的搬动数」）。**这是仓里唯一一条已经被实测验证过的字段**，其余四项目前都只是"逻辑上不该变"的论证，没有专门实验对着"打包/整理搬运"这个具体场景测过 |
| 锚点偏移 | 「查找路径 + 密文侧 extent_off」 | **不变**。锚点偏移是文件内逻辑偏移，是文件内容布局的属性，与承载它的物理形态（独立单元还是容器槽）无关 |
| **单元类型标签** | 「读者的查找路径」——**这是本轮唯一需要新论证的一项** | **不变，但依赖一个此前从未被写下过的解读**，见下 |

### 单元类型标签这一项：为什么可以判定"不变"，以及这个判定依赖什么

**问题的形状**：容器自己的物理头部把单元类型标签写成 4（登记表的码，1.2 节）。如果每个槽的 AAD
也机械地取"这个对象现在物理住在哪种单元里"，那么同一个逻辑对象在"独立成码 1 单元"与"被打包进码 4
容器"这两个物理形态之间切换时，AAD 的第一个字段会从 1 变成 4——**这意味着连"写完之后第一次被后台
整理打包进容器"这个动作本身（D27 已定项 1 定义的常规流程）都要重新加密，而不仅是背景材料讨论的
"容器间搬运"那个更窄的场景**。若这个解读成立，主 agent 依据 3（「AAD 能绑对象身份 ⇒ 后台整理搬对象
不必重新加密」）在源头上就不成立——因为 D27 已定项 1 规定"每个小对象都必然先独立写成单元、再被
后台整理打包"，这个首次打包动作就是一次物理形态切换，若标签跟着形态走，第一次打包必重新加密，
背景材料声称避免的那个代价一次都没省下来。

**我判定标签不随物理形态变**，依据是 D9 已定项 6 自己写的"期望值来源"这条最硬的规则（原文完整摘录，
`09-加密.md:550-551`）：

> **AAD 每个字段的期望值只许来自 ① 读者的查找路径，或 ② 已被上一级 MAC 认证的密文侧字段。
> 一律不许来自明文侧，也不许从指针里读回来。**

以及这条规则明确排除的一类（`09-加密.md:536`，「一定不能进 AAD 的」表格倒数第二行）：

> 「任何明文侧字段（明文头 flags / 长度 / nonce 代号、明文映射层条目、反向索引、位置条目里的
> 密文校验和）| 期望值来源判据 | **期望值由被读对象自己提供，攻击者可同时改两边，AEAD 对此零保护**」

按这条规则，容器物理头部偏移 6 那个字节（=4）是**明文侧字段**——读者不许拿它来当作某个槽的 AAD
期望值输入。真正决定期望值的是"读者的查找路径"：读者要读对象 X 的数据时，它是**通过 X 自己的
逻辑身份**（在 X 所属的文件/树里查到的一个 key）**主动发起**这次查找的，而不是"先看到一个物理位置，
再读它的标签来决定期望什么"。X 在被创建的那一刻，逻辑上就是"一份数据内容"（tag=1 这个语义），
这个语义不因为它后来被物理搬进一个容器而改变——**容器本身的 tag=4 描述的是"这个物理单元是一个打包
容器"这件事，回答的是"怎么解析这 32768 字节"，不是"里面每个对象逻辑上是什么"**。这两件事这次
被显式分开了：容器物理头部的 tag 是给"怎么找到槽目录"这一步用的解析器判据；槽内对象自己的 AAD 用
tag=1，是给"这份密文该不该解密成功"这一步用的认证判据，两者服务不同的问题，允许不同。

⇒ **在这个解读下，五项全部在打包/搬运前后不变**，包括首次打包这一步；主 agent 依据 3 成立，
且成立范围比背景材料写的更宽（不仅"容器间搬运"，"独立单元→容器"这第一步也不必重新加密）。

⚠️ **但这个解读本身，仓里没有任何一条已定条款直接写过**——D9 已定项 6 的"期望值来源"规则原本是
为了回答"读者怎么知道该期望什么，以防攻击者靠篡改明文侧来伪造期望值"这个安全问题设计的，
从没有被用来回答"同一个逻辑对象换了物理容器类型，它的 AAD 该不该跟着变"这个问题。我在上面做的
推导（"容器 tag 与槽内对象 tag 是两件不同的事"）逻辑自洽、且有 A6 规则原文支持，但它是**这次
新做的推论**，不是复述一条已有结论。这正是任务要求第 4 点点名的——"这条依据没被任何人验过"，
现在验完了，但验的结果是"需要一次新的、显式的解读判定"，不是"背景材料已经算对了"。

**结论**：**不需要重新加密**，包括首次打包与容器间搬运两种场景，条件是采纳"容器物理头部的类型标签
与槽内对象 AAD 的类型标签是两个独立判据"这条解读——这条解读目前没有被任何已定条款直接写下，
需要在这次连同未定项 9 一起定案时显式写清楚，否则将来任何人重新审视这一格时会因为找不到依据而
重新怀疑它。

## 五、推不下去的地方

### (a) 容器的引用机制：中央映射 vs 专属索引树

我在 1.3 节选了"走中央映射"（复用 D19 已定项 5，零格式改动），但仓里没有任何条款强制这个选择。
另一条路是照码 3 的先例，开一棵专属"容器索引"树（C103 那一族）。两条路都说得通：
中央映射的代价是"N 个逻辑身份共享同一份物理位置值"这种冗余（不算错误，但没有先例）；
专属索引树的代价是要重新解决 C103 至今没解决的问题（容器索引自己住哪、value 装不装得下 MAC）。
**我没有依据在两者之间强制择一**，只能说中央映射路线不新增格式字段，专属索引树路线要先趟平 C103。

### (b) D19 已定项 3 与"每槽各自 MAC/nonce"的冲突没有出路

这是本轮最硬的一处推不下去。已定项 3 明确禁止"用类型标记省掉"指针头部里 MAC/nonce 的恒定占位
（三、第 2 条已展开）。取"每槽各自 nonce/MAC"意味着被打包对象的"指针头部"（不管它具体住在哪，
这本身也是 C68 未收口的问题）不再需要一份 MAC/nonce——这与已定项 3 的字面禁令直接相撞，**而且
没有第三条路**：要么打破"不用类型标记"这条已定论证，要么让这部分空间变成纯浪费（那样的话，
"每槽独立加密不花钱"这条依据 1 的算术就要把这笔浪费也算进去，很可能不再是"不花钱"）。
这需要用户在两个选项间做一次显式取舍，我在这里给不出第三个选项。

### (c) 单元类型标签的语义歧义，虽然我在四节给出了一个自洽解读，但它是这次新造的

已经在四节详细说明：这个解读依赖 A6 规则的一次新应用，不是复述已有结论。如果这个解读不被采纳
（比如认为容器 tag 应该"传染"给槽内对象的 AAD），那么依据 3 在"首次打包"这一步就不成立，
背景材料的收益论证要收窄甚至可能推翻方向。

### (d) 槽表条目算不算新增泄漏类别，需要用户定案

三、第 6 条已经指出：槽内 offset/length 结构上必须明文，这带来"逐对象精确字节数"的泄漏，
比 D18 已定项 3 已经接受的"declared length 泄漏"更细粒度（数量从 1 次变成 N 次/容器）。
这落在 C173（明文头的泄漏面在明文侧取消后没有辩护）的范围内，但 C173 至今没有专门审过
"数量级"这个维度，我判不了它是否需要单独走一次用户定案，只能标出来交给用户。

### (e) 容器号的分配规则未定

1.2 节类身份段里的"容器号"字段宽度我沿用了码 3 的 8 字节，但**分配规则**（是否树内单调、
是否与 inode 打包路①的规则一样绑定到某个触发事件）完全没有答案——这继承自 C103 尚未解决的
"容器索引"问题，属于 D27 未定项 4 的射程，本轮 3/7/9 定案不覆盖它，但如果不定，槽目录格式
虽然字节宽度已经定了，容器号"怎么取值"仍然是空的。
