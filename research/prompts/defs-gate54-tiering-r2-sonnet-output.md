### S1–S5 是否打中「分档之前的 54 号」

分档之前（基线提交 3b60f098，2026-09-22T07:27:29+00:00）的 54 号，现查（`git show 3b60f098e97dc4c4f3ed9c6355422b607db1c34c:.claude/gate.d/54-layer0-replay.sh`）：只有两道跳过判定（`stage-must-run.sh` 树对比复用、`change-touches-crates.sh` 范围判定），跳过就退 77；不跳过就直接在**调用它的那个进程自己的根目录**下跑 `cargo test --release ... --include-ignored`（无条件全量，没有「快档」，没有标记文件，没有 worktree 转移，没有输入哈希）。

- **S1**（全量在别处跑、标记在这里核，两地对不上）：分档前「全量在哪跑」与「谁来判定」是同一次调用、同一个地方，没有跨地点的核对可言。**不打中**分档前的 54 号。
- **S3**（标记只有一格，两处各跑一次互删）：分档前没有标记文件这个产物。**不打中**。
- **S4**（工作区带别的会话的半成品、写出假的 exhaustive=false 标记，快档信它）：同上，没有「标记」也没有「快档信标记」这个环节，判定就是本次跑出的真实计数行。**不打中**。
- **S5**（跑的中途改了又改回，判定基于两头一致但中途不一致）：分档前若在共享工作区（非 `--staged`）跑，同样存在「cargo test 跑 4 小时期间源码被改了又改回」这个 TOCTOU 风险——**这个底层风险分档前也可能出现**，与分档无关。但分档前一次判定只影响**这一次** gate.sh 调用的成败，判完即弃；分档后的判定写成**标记文件持久化**，被此后所有匹配该输入哈希的快档反复重用，直到内容哈希变化为止。r1 判「分辨」的依据（`research/prompts/defs-gate54-tiering-r1-opus-output.md:257`，现查命中：「两条流编译时的内容指纹不同…标记照写，门禁判绿」）说的正是「标记被写错、此后一直误判」这个持久化效果，不是「本次判定可能出错」这个更早就有的风险。**分档前的版本会在这一次调用里给出错误答案，但不会把这个错误答案缓存下来传染给未来的调用**；分档后的设计会。这个「持久化放大」是分档特有的，S5「分辨」的判断在这个意义上站得住，但 r1 判决没有把「底层风险本来就有、分档放大了后果」这层区分写清楚——这是它论证深度上的一处「够不着」，不影响最终判断方向。

## 三、K2 与崩溃验证员定义第 1 条合起来：构造出的一条历史

**问题**：K2 让崩溃验证员默认只跑快档；崩溃验证员定义第 1 条只处理「另一个 `--full` 正在跑」这一种并发，不负责确保全量**曾经跑过**。真正会跑 `--full` 的地方只有一处：`.claude/main-agent.md:44`（现查命中，全文）：

> 暂存之后、提交之前跑门禁 | 主 agent 用 `research/scripts/stage-mine.py` 暂存 → 这一批改了门禁 54 号在 `.claude/gate.d/stage-inputs.tsv` 登记的输入，就在 HEAD + 暂存区的 worktree 里后台跑那棵树里的 `bash .claude/gate.d/54-layer0-replay.sh --full <它的根>`（层 0 全量只在这一步跑，判绿按输入哈希写全绿标记，整轮门禁的 54 号只核标记）→ `gate-triage`

这一行的触发条件（「这一批改了…登记的输入」）是**主 agent 自己用自然语言判断**的一句提示，不是代码强制。若主 agent 漏判或跳过这一步、直接派 `gate-triage`，是否有后续机制兜底？

**兜底本该在这里**：`gate-triage.md:26`（现查命中）：

> 3. 每个红阶段：抄门禁给的「✗」行与紧跟的「→」下一步原样；看它点名的文件与行在不在暂存区 diff 的块里（`git diff --cached -U0 -- <文件>`）。在块里 ⇒「这一轮」；文件在但行不在块里、或文件不在暂存区 ⇒「不是这一轮」；……

54 号快档没有标记时的红行，`.claude/gate.d/54-layer0-replay.sh:254`（现查命中）：

> echo "  ✗ 快档绿了（${quick_tier_report}），但这批输入（哈希 ${layer0_input_hash:0:16}…，${layer0_input_file_count} 个文件）没有层 0 全量的全绿标记（$full_green_marker_path）"

这一行点名的「文件」是 `$full_green_marker_path`，即 `$(git rev-parse --git-common-dir)/singlefs-layer0-full-green.<输入哈希>`——一个在 `.git/` 目录下、**从不进版本库、也不可能出现在 `git diff --cached`** 里的路径。按 gate-triage 步骤 3 的字面判法：这个路径「文件不在暂存区」⇒ 归「不是这一轮」。

gate-triage 自己承认这类盲区，`gate-triage.md:39`（现查命中）：

> 没修任何一处红；归属按暂存区 diff 的块判，块外的红即使与这一轮有关也判不出来，照写。

而这一路径的 project 内先例是 `agent-common.md:58`（现查命中）：

> 退出码 77 是「本次未跑」，不是通过。红了先看它点名的文件与行在不在这一轮的改动里；不在的不修，照写。

**拼起来的历史**：
1. 某一批暂存改了 `crates/` 下的内容（登记给 54 号的输入），主 agent 的自然语言判断没有触发 `.claude/main-agent.md:44` 那一步 --full（人/AI 判断失误，是主 agent 自身操作，不受 `.claude/agent-common.md` 子 agent 约束的任何硬闸拦——那份约束管子 agent，不管主 agent 自己）。
2. 主 agent 直接派 `gate-triage`。`gate.sh --staged` 跑 54 号快档：输入命中范围（不退 77），这批内容此前从未跑过 `--full`，无匹配哈希的标记 ⇒ 退 1，打印上面第 254 行那句 ✗，点名的是 common-dir 下的标记路径。
3. gate-triage 第 3 步按字面判法，把这个不在暂存区 diff 里的路径判成「不是这一轮」。
4. 主 agent 依循本仓一贯的「不在的不修，照写」处置（`agent-common.md:58`；gate-triage 自己的「没做什么」也是同一句式），把这一条红当作「不是这一轮」的既有问题，照常提交。
