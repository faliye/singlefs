Q1. When creating a snapshot of a file after two writes, the snapshot tree pointer contains only the five-tuple (1,2,3,4,5). During snapshot read, the system attempts to look up the map with key (1,2,3,4,5) but candidate ONE requires the birth generation. The pointer lacks the birth generation value, so the lookup fails and the physical location cannot be found. The operation sequence is: write file (1,2,3,4,5) at generation 1, overwrite to generation 2, create snapshot, then read from snapshot. The system cannot resolve the physical location because the map key must include the birth generation which is not present in the pointer.

Q2. In a system with a strict snapshot retention policy of 7 days and no more than 10 snapshots, the version chain length is capped at 11 entries. Each entry in the value is 8 bytes for the physical location, so the total value size is 88 bytes. The read-modify-write for publishing a new version occurs on a fixed-size 88-byte entry. Since the device's minimum io size is 4KB, the write operation is always for a full 4KB block. This avoids internal read-modify-write on the device because the entire block is rewritten, making the unbounded width and read-modify-write harmless.

Q3. Candidate THREE uses a key of 33 bytes (five-tuple) and a value of 8 bytes (pointer to a separate version chain structure). The version chain structure stores (generation, physical location) pairs in a log-structured append-only format. Map entry width is 8 bytes, which is smaller than candidate ONE's 61-69 bytes. Publishing a new version appends to the version chain log without modifying existing map entries, avoiding read-modify-write on the main map. This reduces map entry size and avoids main map RMW, though it adds a secondary lookup cost for the version chain.

Q4. The cost list misses snapshot creation overhead. When creating a snapshot of 10,000 files, each file requires a new map entry for its current generation. Each entry is 61-69 bytes, so 610KB to 690KB of new data is written. This cost scales with the number of files in the snapshot and is not captured by the existing publish overhead metric of 66048 bytes per publish, which only accounts for a single file update.

Q5. If candidate ONE is chosen but the block pointer header does not carry the birth generation, dereferencing fails. For example, a pointer in a snapshot tree has the five-tuple (1,2,3,4,5) but no birth generation. The system attempts to look up the map using only the five-tuple, but candidate ONE requires the full key (five-tuple + birth generation). The lookup returns no result because the key is incomplete, making it impossible to find the physical location. This forces the birth generation to be included in the pointer header, which must be an explicit design decision rather than assumed.
