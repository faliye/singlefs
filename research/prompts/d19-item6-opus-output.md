## 1. 第 3 问：候选集不完整，而且分割轴踩在错前提上

### 1.1 先把材料里能核的都核了：㈠ 的三个数**算术上对**，问题不在算术

E104 还专门跑过一条「数据单元只用诞生代号当版本维」的臂，就是 `wseq_meta_only`。

⇒ **「同 key 多版按诞生代号择新」这条规则在仓里已经被作为消融臂量过，`same_txg` 世界上歧义 4 + 复活 1。**

而仓里给码 1 定的版本全序键**根本不是诞生代号**。`.claude/kb/invariants.md:27` I-1.8（整行抄）：

```
| I-1.8 | 归并后版本全序 | 码 1 / 3 的可读已发布单元按「类身份段全部字段含写序」归并成组之后，同 key 的各组两两全序键不等——码 1 的键是写序，码 3 的键是 (诞生代号, 实例代号, 事务号) 三元——诞生代号打头（同一实例连着两个 checkpoint 都不分配新事务号时两版写序逐字节相同），事务号留在末位做同一 checkpoint 内的平局破除（固定点会迭代，同一容器在一个 checkpoint 里不保证只写一次）；同一组的成员载荷相同（码 3 由载荷校验和判、码 1 由载荷 CRC 判），不同即判损坏、不择（C113（扫描重建时多版单元的现行版本判定无输入） 定案 P3 副本归并，射程 w = 2；码 2 不进这条） | 未实现 |
```

**「码 1 的键是写序」**，而写序是 10 字节（`.claude/kb/decisions/18-块里携带什么信息.md:583` 的字段表：实例代号 4 + 事务号低 48 位）。

**这一条我要收窄自己的结论，不许外推**：歧义出在**扫描重建**那条路径上，不是自动等于映射条目会撞键。
真要撞键，得有两版同 (五元组, 诞生代号) 同时被引用；而 `.claude/kb/decisions/16-发布语义.md:78-84` 的新规则 1
（「快照发布点必须与 checkpoint 边界对齐」，理由逐字是「`birth` 的分辨率只到 checkpoint，**块无法表达『我生在本 checkpoint 里快照点之前还是之后』**」）
恰好堵住了这一支：checkpoint 内被覆写的旧版走 `birth > p` **立即释放**，不进 deadlist。

⇒ **所以真正的发现不是「㈠ 会撞键」，是「㈠ 的 key 之所以够用，全靠 D16 新规则 1 顶着，而 D19 未定项 6 与 D5:35 都没写这条依赖」。**
它是一条承重依赖：D16 新规则 1 哪天松动（比如允许 checkpoint 内的快照点），㈠ 的 key 当场不再是身份，
而**没有任何一处会红**——扫描重建那一侧有 I-1.8 顶着，映射这一侧一条不变量都没有。
按 `.claude/rules/fs-design.md` 的判据，这正是「不做成单元 / 不写下依赖 ⇒ 机制不会报警」那一类。

### 1.4 于是第三条路是现成的：**代理键**，而它在全仓零登记

**做法**：映射 key = 一个与逻辑身份无关的定宽版本号（下称「版本号」），value = `w` 份位置条目；
引用侧（指针 / 条目）携带这个版本号；单元头里也写一份，供扫描重建认领。

**它在仓里从没被提过。** 现查：

```bash
grep -rn "代理键\|surrogate\|单元号\|不透明句柄\|opaque" .claude/kb/ --include=*.md | grep -v history
```
**12 条命中，逐条读过，全部是「32 KiB / 16 KiB 物理槽号」这一类落点编码**（`19-块指针的结构与宽度预算.md:256`、
`97-记账与分配记录的条目编码.md` 的 169–228、`03-空间分配.md:213`），
**没有一条是「给每个版本发一个与逻辑身份无关的号，拿它当映射 key」。**

**它比㈠ 强在哪一格（都是机制，不是偏好）**：

| 格 | ㈠（逻辑身份 key） | 代理键 |
|---|---|---|
| **reflink** | **做不到**——见 2.2，一个单元被两个不同五元组引用时，引用侧凑不出「出生五元组」，且单元头只装得下一份 | 一个单元一个版本号，N 个引用者都拿同一个号 ⇒ 不受影响 |
| **搬迁只改一条条目**（已定项 5 的立身理由） | reflink / 打包容器下不成立（打包那一格 D27 已经写下来了，见下） | 恒一条 |
| **码 2 / 码 3** | key 无定义（1.5） | 号不看单元类 |
| **条目宽** | 41 + 28 = 69 | 8 + 28 = 36 ⇒ 每叶 `16308/36 = 453` 条（我自己算的，不是仓里的数） |

**它比㈠ 差在哪一格（必须写下来，否则我就是在推销）**：

1. **号要分配、要单调、要跨崩溃不重发**——而 `.claude/kb/checks-owed.md:264` C250 与
   `.claude/kb/decisions/08-核心索引结构.md:374` 记着仓里**已经有两个**同类分配器踩过这个坑
   （inode 号在崩溃后被重发、C143）。这是一笔真代价，不是零。
2. **key 序丢了局部性**。`.claude/kb/decisions/27-小数据打包容器.md:160` 逐字「**顺序**：打包沿中央映射 key 序遍历，**不按容器凑满序**」，
   而 `.claude/kb/experiments/120-档表取等比时公比怎么定.md:59` 逐字「若 key 以树 ID 领头，沿 key 序走一次只碰一棵树」。
   代理键的 key 序 ≈ 写入时间序，**这两处的结论都要重算**。这一笔按 E116 的回本比（key 序 0.0444）量级不小。
3. **单元头要加一个字段**（版本号 8 字节，码 1 头 105 → 113），而㈠ 一个字节都不加。

⇒ **我不主张选它**（那是正推腿的活）。我主张的是：**它是候选集里缺的一条，而且它缺席的理由从来没被写下来过。**
按 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「没有任何现役实现走 X 这条路……要走一条没人走过的路，得说清别人为什么不走」的反面——
这里是**仓里从没有人走过、也从没有人说过为什么不走**。

### 1.6 错前提丙：两条候选**只对码 1 有定义**，而已定项 5 的射程是全部指针

三类单元的身份是三样不同的东西。`.claude/kb/invariants.md:20` I-1.1（整行抄）：

```
| I-1.1 | 块头自述逻辑地址 | 任一单元，其头记录的**类内身份**与实际引用一致——数据单元的身份是五元组（锚点偏移即它的逻辑地址）；索引节点是树 ID + 层级（+ 该树已定携带的 key 区间，D18（块里携带什么信息）已定项 2 口径）；打包记录单元（码 3）是（出生树 ID, 打包记录类型, 容器号, 容器出生代）四元组，「父级」按打包记录类型分——类型 1 走容器索引的身份引用（C103（容器索引无落点）），类型 2 走 inode 树内部节点条目的身份引用（I-9.2（条目身份与子头相符）），**类型 4（实例表）走根记录的物理指针，不属于任何树、不进容器索引**。**自证单元（journal 记录 / 根槽 / 超级块槽 / 类型 4 实例表单元）显式豁免**：无父引用无树身份，自证纪律在 I-7（根环）/ I-8（journal）两类与 D22（单元原子性怎么合成）已定三 | 未实现 |
```

**索引节点（码 2）没有五元组**——它的身份是「树 ID + 层级（+ 该树已定携带的 key 区间）」，
而 key 区间**不是每棵树都带**（`.claude/kb/decisions/18-块里携带什么信息.md:136` 已定项 2：记账树带、inode 树带、**dirent 树推迟**）
⇒ 对不带区间的树，(树 ID, 层级) 下有成千上万个节点，**这个身份根本不唯一**。

而码 2 确确实实要走 D5 的判定并进 deadlist——D19 未定项 7 正文里逐字（`19-块指针的结构与宽度预算.md:106`）：

```
每个旧内部节点指着的子节点都被判进 deadlist 而不是立即释放
```

⇒ **㈠ 与㈡ 都答不了「一个索引节点的映射条目 key 是什么」，而已定项 5 逐字说映射是「解引用与释放判定的唯一入口」。**

**同一个洞在仓里被独立发现过两次，只是没人接到这一格来**：

1. `.claude/kb/decisions/09-加密.md:93`（整行抄）——2026-09-06 判逻辑键那条路塌掉时给的第一条理由：

```
| 明文映射表 | **覆盖面**：键表达不了码 2 / 码 3（它们的身份进密文），而 D9（加密） 已定项 5 的机制理由逐字说瓶颈**就是元数据**（「元数据块可以原样搬……但父指针里的地址字段仍要改，而父节点的载荷是密文」）⇒ 字段表覆盖的那类单元与立身理由覆盖的那类**不相交** |
```

## 2. 第 4 问：与未定项 7 的耦合怎么读

### 2.1 「凑得出五元组与诞生代号」——把六段说成了两段

五元组的分段是定死的。`.claude/kb/decisions/18-块里携带什么信息.md:380`（整行抄）：

```
**五个字段的宽度已定（2026-09-04，用户定案）：单元类型标签 1 + 树 ID 8 + 对象 ID 8 + 对象出生代 8 + 锚点偏移 8 = 33**（[verification-build.md](../verification-build.md) 第 8 问由此关闭；依据追溯在已定项 11）。
```

㈠ 的 key 因此是**六段**：单元类型标签、树 ID、对象 ID、对象出生代、锚点偏移、诞生代号。
未定项 7 的甲只提供其中**两段**（出生树 8 + 出生 txg 8）。逐段对一遍，以 extent 叶记录那条边为例
（`.claude/kb/decisions/08-核心索引结构.md:71`，整行抄：

```
| 3 | **key 布局** | **已定（2026-08-25）：`(locality_id, inode, offset)`，改名与索引分开处理** | D8（核心索引结构）「已定项 3」 **状态：已定。** |
```
）：

| 段 | 引用侧从哪来 | 判 |
|---|---|---|
| 单元类型标签 1 | 由上下文隐含（走的是数据 extent） | ✅ |
| 树 ID 8 | **必须是出生树**（I-1.3），当前树不算 ⇒ 只有甲给得出 | ⚠️ 要甲 |
| 对象 ID 8 | extent key 的 `inode` 段 | ✅（非 reflink 时） |
| 锚点偏移 8 | extent key 的 `offset` 段 | ✅（非 reflink 时） |
| **对象出生代 8** | **extent key 里没有**。`.claude/kb/checks-owed.md:79` C69 逐字「五元组里的「对象出生代」是 inode generation，不是块代」⇒ 要回 inode 记录读（`.claude/kb/first-txn-layout.md:96`：inode 记录偏移 8） | ⚠️ **多一次读，未定项 7 三条候选一条都不提供** |
| 诞生代号 8 | 只有甲 / 乙给得出（乙已出局） | ⚠️ 要甲 |

**对象出生代这一格我判为次要**（整个对象一次删除时它可以摊掉一次读），但它**不是零**，
而且材料与未定项 7 的耦合段里**一个字都没提**。

### 2.2 主要那一格：**reflink 下甲够不着，而 reflink 是 day-1 承诺**

`.claude/kb/decisions/04-校验和位置.md:269-271`（整段抄）：

```
三条腿把 reflink、去重、RAID 重建、journal 重放、快照销毁、重条带、墓碑打包挨个查过，
一个反例都没找到。另外有四处需要单独核实，我逐字读过原文：reflink 虽然是 day-1 承诺，
但它共享的是**整个单元**，两边偏移都是 0——那是引用共享，不是切分；
```

⇒ 一个单元被文件 A 的 (inode_A, off_A) 生出来、又被文件 B 的 (inode_B, off_B) 引用。
在 B 那条 extent 边上，㈠ 的 key 要的是**出生**身份，也就是 A 的对象 ID 与 A 的锚点偏移——
**这两段 B 的树里一个字都没有，甲也不提供**（甲只给出生树与出生 txg）。

三条推论，一条比一条硬：

1. **甲不够。** 要让㈠ 在 reflink 下能查，引用侧得携带**整段出生五元组 33 + 诞生代号 8**
   （或至少 对象 ID 8 + 对象出生代 8 + 锚点偏移 8 这三段），远超未定项 7 甲的 16 字节。
   照第四条路那种「放进引用它的那条条目」的算法，extent 叶记录 83 → 116，扇出还要再掉一档——**这笔数全仓没人算过**。
2. **扫描重建那一侧同时塌。** 已定项 5 的态别行逐字靠「映射可从单元自描述扫描重建」立身，
   而单元头只装得下**一份**五元组（I-1.1）⇒ B 那条引用对应的映射条目**扫描重建不出来**。
3. **「搬迁只改这里一条条目」在 reflink 与打包下都不成立**，而打包那一格仓里已经写下来了。
   `.claude/kb/decisions/27-小数据打包容器.md:285-286`（整段抄）：

```
  ⚠️ 代价照实记：位置条目里那 4 字节密文校验和覆盖 32 KiB 整单元（D4（校验和位置） 已定项 1）⇒
  同一容器的 N 条映射条目各存一份同值；容器一旦重写，N 条全要改。
```

⚠️ **仓里有一处张力，我不替它裁**：`.claude/kb/decisions/26-后台整理与放置回收.md:392` 里主 agent 核过
「跨树 reflink / 去重……**那类特性今天不存在**、且引入它要先重开 D5」，而 D4:270 说 reflink 是 day-1 承诺。
两句可以并存（同树内的 reflink 是 day-1，跨树的不是），**而我上面这条只需要同树内 reflink 就成立**——
两个不同的 (inode, offset)，无论是不是同一棵树，出生五元组都只有一个。
⇒ **这一条要么推翻 D4:270 那句 day-1 承诺，要么推翻㈠。今天两条同时在册。**

### 2.3 材料点名要核的那一句：「D5 的 O(1) 判定只要出生 txg，不要出生树」

**它是真的，但它的射程只有三行伪代码，不是那条代码路径。**
`.claude/kb/decisions/05-快照-空间记账机制.md:161-166`（整段抄）：

```
判定(ptr):
    birth = ptr.birth              // 指针内联字段，零次额外 I/O
    p     = head.prev_snap_txg     // 活头头部一个标量，常驻内存
    if birth > p:  立即释放 → 进 defer 队列（不是直接进空闲表，见 D16 新规则 2）
    else:          追加进 head.deadlist
```

**分支条件**只读 `birth` ⇒ 消费者 ① 说得对。**但两条出口都要完整的版本身份**：
「立即释放」要从映射里解出落点（硬规则 1「释放一律经映射，不经提示」），
「追加进 head.deadlist」要按 D5:35 的版本身份写条目。

⇒ 这句话**不松动耦合，只是把它挪了一行**。而且 D5 自己早就把更全的那句写下来了，
`.claude/kb/decisions/05-快照-空间记账机制.md:39-42`（整段抄）：

```
⚠️ **方向如此，但这一问 2026-09-08 判仍定不了**：那 33 字节里的树 ID 段是**出生树**，
而 I-1.3（块头树 ID 一致） 逐字「跨头共享时与引用树不同」⇒ 删除侧凑不出它，除非多读一次单元头，
而那就打破了 D5（快照 / 空间记账机制） 自己那条 O(1) 归约。
前置是 D18（块里携带什么信息） 已定项 11 点名的「指针带出生 (树, txg)」，今天未落地。
```

⇒ **对第 4 问的意思**：那句「只要出生 txg」若被读成「未定项 7 的耦合没那么紧」，就是把
**一条三行谓词的射程**外推成**整条删除路径的射程**。真正的形状是：
消费者 ① 与消费者 ② **是同一条代码路径的前后两行**，① 弱不代表这条路径弱。

⚠️ 还有一层：D5 的 O(1) **是一条已完成的归约证明**（`05-快照-空间记账机制.md:192` 逐字
「第一依据是……归约证明——**它是证明，不是测量**」）。
⇒ (㈠, 丙) 这个组合不是「代价大一点」，是**让一条已定条款的证明当场失效**。这是量级不同的一格。

### 2.4 判决：两个给定的读法都不对

材料问的是「两项必须一起定」还是「㈠ 的前置，可以分开定」。**我判两个都不对，第三种**：

| 读法 | 判 |
|---|---|
| 「㈠ 的前置，可以分开定」 | **假。** 先定㈠ 会让 (㈠, 丙) 成为一个可达组合，而它当场破 D5 的 O(1) 归约（2.3）。这不是「以后再补」的账 |
| 「两项必须一起定」 | **也假，而且更值得说。** 一起定的话，未定项 7 今天的候选集**没有一条满足㈠**——甲只给六段里的两段，reflink 那一格给不出（2.2）。一起定只会定出一个**仍然凑不出 key 的组合** |
| **实际形状** | ㈠ 的前置**不是**未定项 7，是**一问更上游的**：「**引用侧到底要携带多少出生身份**」。未定项 7 只是这一问在「出生 (树, txg) 那 16 字节」上的一个投影。⇒ **选㈠ 之前要先把这一问立成分项**，否则未定项 7 无论怎么定，㈠ 都还缺段 |

**方向是单向的，这一点要写明**：选甲**不**逼出㈠（甲另有两个独立消费者：D5 的 `ptr.birth` 与 E90 的 AAD 形态）；
选㈠ 逼出甲**且不止甲**。所以这两项**不是对称耦合**，把它们写成「一起定」会掩盖这个方向性。
