## 一、V1（K1）：甲出局这句话越不越位

### 1.1 「活元数据」在 kb 决策正文里没有独立定义，但在 E139 装置里有

全仓 grep（不截断，`grep -rn "活元数据" .claude/kb`）命中 8 处：`.claude/kb/decisions/16-发布语义.md:377`、`:378`（式子本身两处）、`.claude/kb/decisions/03-空间分配.md:53`、`:381`、`:430`（转述同一个式子）、`.claude/kb/experiments.md:157`、`.claude/kb/experiments-history.md:255`、`.claude/kb/decisions-history/2026-09.md:677`（三处都是复述 E139/D16 已定项 1 的同一句）。**没有一处单独给它下定义**——它只出现在式子里或转述式子的句子里。`.claude/kb/checks-owed.md`、`.claude/kb/layout/01-first-txn.md`、`.claude/kb/invariants.md`、E139/E141/E148 三份实验 kb 正文里 grep 全部 0 命中。

但 D16 已定项 1 逐字写「形态（E139（按盘回退下界的收严形态） 的臂 G2S，与装置里跑的一字不差）」（`.claude/kb/decisions/16-发布语义.md:365`），也就是说这个式子不是凭空写的，是从 `research/e7-index-bench/src/bin/e139_tightened_floor.rs` 的代码里抄出来的。那份代码里确实有这个量的实现：

```rust
// research/e7-index-bench/src/bin/e139_tightened_floor.rs:681-684
/// 收严臂：当前活着的元数据（上一个窗口的 5 块，或推空最后一次发布的 c 块）算保留池的占用——保留池正是为它留的，不从用户的空闲里扣。别的臂照 E138 不记这一笔。
fn live_metadata_credit(&self) -> u64 {
    if self.arm.is_tightened() { self.pool.metadata.len() as u64 } else { 0 }
}
```

`pool.metadata`（`PoolState` 第 253 行声明为 `Vec<usize>`）只在 `prefill()` 里写一次（第 802–809 行）：挂载之初放进 `METADATA_BLOCKS_PER_PUBLICATION` 个块、标成 `Live`、押进 `metadata` 这个账本，此后全仓再没有第二处 `.metadata.` 的读写（`grep -n "\.metadata\." e139_tightened_floor.rs` 只命中第 683、810 两行）。⇒ **它是一个常量**：当前发布已经占用、且已经算进 `BlockState::Live`（因此已经被 `df_raw()`/`reusable_count()` 排除在空闲之外）的元数据块数，加回来是为了不让保留池的扣减对同一批块**扣两次**——不是在承诺「下一次固定点在某块盘上分得到块」。

### 1.2 D16 的保留池 10 + 7 c_max 是给谁留的（逐字）

`.claude/kb/decisions/16-发布语义.md:377`：「准入 | 可分配 = min(可再分配 + 活元数据 − 保留池, `df`)；准入不够时先推空发布抬 F……**一次准入最多 B = 4 + 2 k_tol 次发布**（k_tol = 2 ⇒ 8），做满仍不够才报 ENOSPC」；:378：「`df` | ……保留池 = 2 × 5 + (B − 1) × c_max = 10 + 7 c_max」。这两句连起来读：保留池的形状是「固定 2×5 底额 + (B−1) 份 c_max」，`B−1 = 7` 恰好对上「一次准入最多推 B=8 次空发布，其中第一次不算增量、后面 7 次每次最坏吃 c_max」——它是**为『抬 F 重试循环最多跑 B 次』这件事单独留的池**，不是为「任意一次 checkpoint 的固定点」留的。这与 D28 已定项 1 第八项的保证句（`.claude/kb/decisions/28-挂载期承诺量.md:28`：「它保证 checkpoint 自己的固定点写得出去（E19（defer 窗口下的假性 ENOSPC）：预留 0 时卡死 199 次）」）在回答两个不同的问题：一个问「重试循环本身会不会把自己吃穷」，一个问「（不管重试与否）当前这次固定点本身分不分得到块」。

### 1.3 判断：甲出局不是越位，但第一轮的措辞不准确

`live_metadata_credit()` 是一个**没有设备维的标量**（`pool.metadata.len()`，池只有一份），D16 的整套 `可分配`/`df` 式子（`.claude/kb/decisions/16-发布语义.md:365-378` 那张表）从表头到表尾没有出现任何「按设备」字样——对照 D28 已定项 1 明文「括号里的六项……按设备求和」（`.claude/kb/decisions/28-挂载期承诺量.md:298`）。串上 D16 这一道闸，不会给甲凭空造出一个「盘 1 也够」的读法：D16 的量本身就不区分盘。**所以第一轮「甲出局」这个结论是对的**，但第一轮给出的理由——「它的保证不能押在另一道闸的一个没有定义的词上」（`c355-c363-r1-main-verification.md:69`）——把「没有 kb 条款定义」等同于「不存在任何定义、因此不用管它」，这一步走快了：活元数据在 E139 装置里确实有定义，只是核实之后发现这个定义**恰好也救不了甲**（常量、无设备维、语义是防止重复扣减而非承诺按盘可得）。**结论：不越位，但应该把理由换成「活元数据是无设备维的池级常量修正项，与需要按盘兑现的保证无关」，不是「它没有定义」。**

**什么现象会推翻这一节**：如果 D28 已定项 3「暖机那一半」或别的已定条款把 D16 的 `可分配`/`df` 显式改写成按设备求和（即 E139 装置之外，有第二个装置把它建成有设备维的形态），本节「D16 没有设备维」的支撑就塌了，需要重新判 K1。

## 二、K2：丙是不是被读成了它的最弱形态

### 2.1 丙的定义句自带一个限定词，第一轮没有兑现它

`_c355-c363-r1-body.md`（= `_c355-c363-r1-background.md:41-47`）第三节逐字：「**丙（按设备）**：第八项挪进括号，作挂载期承诺量里按设备的成员，每块盘各减 ckpt_cost × 16384，**与前提三暖机那一半同一取法**。」这句话没有把丙定义成「代入 Σ设备(...) 公式再求和」，它把丙的取法**外包给了前提三**（暖机那一半：D28 已定项 3「暖机那一半」）。前提三的文字本身（「空发布的 c_max 块每块盘各占一份，所以按设备各加一份」）读起来像个「按设备分摊后再加总」的记法，容易被读成跟乙一样的代数形式——**这正是第一轮踩进去的那一步**。

### 2.2 暖机那一半的真实取法（E141 的被测臂）是逐设备合取，不是求和

`.claude/kb/experiments/141-切换预留的挂载准入自证.md` 里，暖机那一半连同链重写一起，是 D28 已定项 3 的**被测对象**，装置逐字写明「挂载判定：**每块盘上** 容量 − 已分配 − 不可回收 − defer 待释放 **≥ 这块盘的份额**」，且把这条判定标成「被测」，把「两块盘空闲之和 ≥ 总预留」单独标成「池级标量（**对照**）」——两者是装置里两条不同的臂，**被测臂就是逐设备合取**。判据 3 的产物逐字：「设备维 | 28 个取样点上『盘 0 空闲 = 份额 + 50、盘 1 = 份额 − 1』的池，被测臂全部只读、池级标量臂全部可写 ⇒ 这个池分得开两条臂，不作废」；`.claude/kb/checks-owed.md:327`（C355 那一行）也整句抄了这个结论：「装置里跑的 E141……判据 3 已量出池级标量臂在……的池上判可写、按设备臂判只读」。⇒ **D28 已定项 3 暖机那一半「真实取法」不是把按设备算出的份额加总再跟池比，是要求每块盘各自过关**。

### 2.3 由此推回丙：丙按自己写的限定词，从一开始就该是逐设备合取

丙的定义句让「每块盘各减 ckpt_cost × 16384」照抄「与前提三暖机那一半同一取法」——而前提三暖机那一半的取法（2.2 节核实）是逐设备合取。把这条限定词兑现，丙应读成：**对每块盘分别要求「该盘的四项（容量、已分配、不可回收、defer 待释放）减去该盘的 ckpt_cost 份额 ≥ 0（或者说该盘仍满足自己那一份准入）」**，而不是「把 ckpt_cost 塞进 Σ设备(...) 括号里、算完还是一个求和之后再跟一个池级需求比」。第一轮正推腿的核实——「乙与丙……第一版两块盘时『挪进括号再求和』与『池级乘 2』逐项展开相同……是代数恒等：Σ_d(free_d − c) = Σ free − 2c」（`c355-c363-r1-main-verification.md:26`）——**核的是「挪进括号仍求和」这一种读法**，这一步本身没有算错，但它默认了「挪进括号」等于「代入 Σ 公式求和」，从没有检验过丙定义句里「与前提三暖机那一半同一取法」这半句要求的是逐设备合取。⇒ **第一轮判决「丙按最弱读法记一次输，它与乙逐状态相同」（`c355-c363-r1-main-verification.md:71`）确实把丙读成了它的最弱形态**——最强/按定义句该有的形态，本来就是后来被称为「丙′」、标注「被攻过零轮」的那个东西。

### 2.4 这对「丙′被攻过零轮」这句判词意味着什么，以及它没有解决的部分

`丙′` 不是两条云端腿凭空提出的新候选，是丙自己写明的限定词在被兑现之后应有的样子——**这一点上第一轮的判词有误导性**：它把丙′包装成一次「腿提的收严」（`c355-c363-r1-main-verification.md:75`：「两条腿提的收严（逐设备合取，下称丙′）……多要求的是『每块盘各自满足』，被攻过零轮」），而更准确的说法是「丙经过兑现限定词之后就是这个形态，第一轮分析时把它错判成了乙的同构」。**但这不代表丙（=丙′）已经被验证过**：K2 原文点名的两处仍然完全开着——① 池级项（待删占用、已承诺预留）在逐设备判据里怎么取，D28 已定项 1 明文这两项「不按设备求和」（`.claude/kb/decisions/28-挂载期承诺量.md:298`），逐设备合取要不要、怎么把它们摊到每块盘上，条文没写；② 三块盘以上、`w` 可变时，「每块盘各减一份」还要不要变成「只在被选中的 w 块盘上各减一份」，E141 的装置只建了两块盘（「它答不了的」第 2 条：「三块盘以上时两份副本落哪两块盘，D28（挂载期承诺量） 已定项 3 没写」），这一点对丙′同样成立、没有因为「丙′其实就是丙」而多出任何证据。**这两处仍然是被攻过零轮**——不是因为丙′是新提案，而是因为丙（无论叫不叫丙′）本来就没有人在这两个维度上核实过。

**什么现象会推翻这一节**：如果能在 D28 已定项 3 正文或 E141 装置之外找到第二处对「暖机那一半」的权威建模、且那一处是池级求和（不是逐设备合取），则「暖机那一半的真实取法是逐设备合取」这句支撑塌了，2.3、2.4 的推回随之作废，回到第一轮「丙同乙」的原判。

## 三、K3：分配记录树什么时候才会有两个叶，这一格离第一版多远

### 3.1 算叶容量：812 条记录

`.claude/kb/layout/01-first-txn.md:286`：「分配记录树节点 | 码 2 头 = 86 + 2 × 10 + 29 | **135** | 树 ID 13、层级 0、key 宽 10、条目数 20、条目宽 20」；`:71`（零节字节表 t5 行）：「t5 | 事务 | 分配记录树根兼叶（20 条记录） | 2 | **16384** | 50245 | 13 | 五」——节点（单元）大小 16384 字节，头 135 字节，每条记录 20 字节（key 10 + value 10，`:275`：「分配记录 | 落点粒度 16384；key = (设备身份 4, 16 KiB 槽号 6)；value = (跨度段 2……分配代或释放代 8) | 10 + 10」）。⇒ 一个叶能装 `⌊(16384 − 135) / 20⌋ = ⌊16249 / 20⌋ = 812` 条记录，第 813 条才会把这棵树从「根兼叶」（层级 0）推成两层（根 + 至少两个叶）。

### 3.2 第一版今天只有 20 条，离 812 条还差 792 条（≈ 396 次逻辑分配）

`.claude/kb/layout/01-first-txn.md:275` 逐字列出第一个事务的 20 条记录（10 个逻辑落点 × 每条两盘各一）。allocator.rs 里分配记录的 `sort_key`（提交 `fbae43e`，`crates/singlefs-core/src/allocator.rs:42`：`(self.device.0, self.slot.0)`）确认 key 以设备身份打头，这是回合一「分配记录树多一个叶时两块盘的记录落在不同叶上」这句话的成立前提——但**前提本身要求树已经有 ≥2 个叶**，而第一版只有 1 个叶（20 ≪ 812）。要走到「两个叶」，至少要再发生约 `(812 − 20) / 2 ≈ 396` 次两盘各写一条的逻辑分配事件（假设均匀增长；由于 key 按设备分段，也可能是单一设备先攒够 812 条自己那一段先分裂，需要的逻辑事件数量级不变）。**这在里程碑二（第二个事务）步 1–5（一次覆盖写、一次删除、一次实例切换、一次回退、一次抬 F 复用）的验收范围内不会发生**——`.claude/kb/milestone/02-second-txn.md:82-108`（步 1，已在工作区实现）与其余四步描述的都是「同一个文件几次发布」量级的操作，不是几百次独立分配。

### 3.3 但树表单元的少算不是「远」，它是今天已经在发生的

K3 原文列的四类少算——树表单元、inode 叶容器第二个槽、分配记录树多叶、映射树多路径——**不是同一个时间尺度**。树表单元每次发布都写，这是已经定案、且已经在工作区实现的行为：`.claude/kb/decisions/16-发布语义.md:192`（已定项 9）：「一次空发布写不写单元……连带记账树节点、分配记录、映射条目**与树表单元**重写」；`.claude/kb/milestone/02-second-txn.md:82-83`（步 1「现状」）：「`crates/singlefs-core` 的 `transaction` 模块……新入口 `publish_overwrite`……六个提交内生块……**与树表单元各 COW 出新版本**」——这是**第二次发布就会发生**的事，不需要等几百次分配。E148 的模型「只建了分配记录树与中央映射树」（`.claude/kb/experiments/148-提交固定点按两棵记录树重算.md` 自陈，`_c355-c363-r2-background.md:16` 前提八转述），树表单元完全没进模型 ⇒ **这一项的少算从第二个事务的第一步起就是活的、不是要等负载堆起来才暴露的**。⇒ 第一轮判决「不写回任何一条臂……公式少算另立一笔欠账」（`c355-c363-r1-main-verification.md:84`）把两种时间尺度的少算揉进了一笔账，交用户或写欠账时应该拆成「即时」（树表单元、K3 提到的 inode 叶容器第二槽——同理，只要 inode 数超过一个容器槽宽度即触发，量级远小于 812）与「远期」（分配记录树/映射树因 key 打头分裂）两笔，各自的检查形态不同：前者是「公式漏掉了一个恒定项」，后者是「公式漏掉了一个随负载才会翻转的条件项」。

**什么现象会推翻这一节**：如果第一个事务或第二个事务的验收范围内实测出现了单次发布分配 ≥ 800 条记录的场景（例如打包容器整体重写触发批量分配），812 这个门槛与「离第一版很远」的结论一起作废，需要按实测的分配批量重算。

## 四、K4：「需求」「可用」「df」有没有隐含的共同单位

### 4.1 D28 这一侧：已经有一条条款把「已分配」钉成按盘的物理字节

`.claude/kb/decisions/05-快照-空间记账机制.md:251`（已定项 7，2026-09-13 用户定案）：「『已分配字节』= 分配记录树里落点之和；准入不等式里的『容量』= 单元区大小」；:252（已定项 8）：「第一个事务写 15 行：**已分配字节（第 1 项）每盘一行**……」；:485（对照表）：「已分配字节（1） | (1, 0, 0, 3)、(1, 0, 1, 3) | **每盘 212 992**」——三处合起来确认「已分配」不是一个池级总数，是**逐盘各自维护、逐盘各自记账**的物理字节数，直接源自分配记录树（每条落点两盘各一条，`layout/01-first-txn.md:275`：「每条两盘各一」）。D28 已定项 1 的 `可用 = Σ设备(容量 − 已分配 − ……)` 因此**已经是**「对每块盘各自算出物理字节数，再求和」——这一侧不是没有单位，是单位已经被 D5 已定项 7 钉死了，只是没有人把它跟「需求」的单位显式接起来。⇒ 若 `可用` 是 Σ设备(该盘物理字节)，要让 `可用 ≥ 需求` 有意义，`需求` 只能跟着读成「这次分配会在每块盘上各占多少物理字节，再求和」——也就是正推腿说的 `2u × 16384`（`c355-c363-r1-main-verification.md:24`），但这不是正推腿凭空反推出来的读法，是 D5 已定项 7 已经定案的记账口径**唯一能兼容**的读法。

### 4.2 D16 这一侧：`df`/可分配的模型天生没有设备维，这半条鸿沟没有条款接

`research/e7-index-bench/src/bin/e139_tightened_floor.rs` 全文 `grep -n "device\|设备"` 只命中两行注释（第 1528、2222 行，说的是「新 F 要两块盘都持久」这种根槽写入语义，不是数据/元数据池的设备切分）；`PoolState`（第 250 行起）只有一份 `blocks: Vec<BlockState>`，`CAPACITY_BLOCKS` 是单一容量，不分盘。⇒ **D16 已定项 1 的 `可分配`/`df` 从建模的那一刻起就是单一标量，从没有过「这个数在哪块盘上」这个问题**。D3 已定项 12（`.claude/kb/decisions/03-空间分配.md:53`）说得很清楚这是「两道串联的闸：先过 D28 的『可用 ≥ 需求』，再过 D16 的抬 F 逻辑」——串联意味着**同一次分配请求要先后满足两个用不同单位建模的量**，而没有任何条款讲清「先过了 D28 的按盘物理字节校验之后，D16 那个不分盘的标量到底扣的是哪一份」。

### 4.3 判断

K4 的判断不是「三个词都没有单位」，是**两个词（需求、可用）已经被 D5 已定项 7 逼出了一个单位（盘字节），第三个词（df，连同它所在的整套 D16 可分配式子）从来没有单位可言（没有设备维，无所谓单位落在哪块盘）**。这比第一轮「共用前提：需求、可用、df 没有共同单位」（`c355-c363-r1-main-verification.md:70`）更精确：不是三者互相冲突，是两者已经定了、第三者从模型层面就还没资格谈这件事。交用户时应该问的不是「需求该按什么单位算」（这半句已有 D5 已定项 7 的答案），而是「D16 的可分配/df 要不要重建成有设备维的量，重建成什么样」。

**什么现象会推翻这一节**：如果能找到一条条款或实现，明确把 D16 的 `df`/`可分配` 按 D28 的设备维拆开维护（例如每块盘各报一个 `df`），本节「D16 那半没有单位」的结论作废，回到「只是没写全」而不是「模型层面缺一维」。

## 五、V5：两处实现 bug 是不是与臂无关、每条臂都要先修

### 5.1 两处 bug 的确切位置（提交 `fbae43e`）

**bug①（落点只看盘 0）**：`crates/singlefs-core/src/allocator.rs:270`：`allocate_user_data` 里 `let chosen = self.devices[0].lowest_user_data_slot(open)?;`——只用设备 0 的空闲图选槽号，之后虽然在同一函数里对全部设备重新算一遍取最小值、不一致时只递增 `policy_mismatches` 计数（不改变行为），最终 `record()`（第 253 行起）对 `for device in &mut self.devices { device.mark_allocated(placement.slot, placement.span); }`——把设备 0 选出的**同一个槽号**原样敲进每一块盘。`mark_allocated`（第 152 行）里 `assert!(end <= self.allocated.len(), "跨度越过单元区末尾")`（第 155 行）——盘 1 比盘 0 小或盘 1 那个槽已占用时，这条断言/另一条断言会炸。

### 5.2 两处 bug 违反的是已经独立定案的 D3 已定项 8，不是悬而未决的 C355/C363

`.claude/kb/decisions/03-空间分配.md:253`（已定项 8 第 1 条，2026-09-13 用户定案 + 两轮三方论证）：「设备集合由 D2（RAID 条带策略） 已定项 8 选定之后，**在每一块被选中的设备上各自取该设备内**起点槽号最小……的落点」——与 bug① 直接对立（只取设备 0）。:255（第 2 条）：「提交内生块的段耗尽时回落到该设备内槽号最小的空槽」——与 bug②直接对立（没有回落，直接失败）。这条已定项的定案日期（2026-09-13）、依据（E151（用户数据落点的到达序与容器臂） 两轮三方论证）与 C355/C363 的立项日期（2026-09-16，`.claude/kb/checks-owed.md:327`、`:338`）**是两件独立的事**：D3 已定项 8 没有引用过 C355/C363，也没有以它们的判决为前提；C355/C363 讨论的是「ckpt_cost 这个量怎么算、怎么扣」，不涉及「落点该在哪块盘上选」。

### 5.3 判断：arm 无关，且是任何一条臂都要先修的前置

因为两处 bug 独立于 C355/C363 的选择而成立，**它们对 K1/K2 的每一条候选（甲/乙/丙/丙′）与 K3 的每一条候选（甲/乙/丙）都是同一个前置**：① K2 讨论的「短盘」场景本身在 bug①存在时无法在实现里被表达——短盘会在分配阶段直接触发断言 panic（这正是第一轮攻方腿指出的「短盘在 `fbae43e` 的实现里先 panic」，`c355-c363-r1-main-verification.md:44`），不管 C355 最终选哪条臂，丙′ 想要的「按设备各自判定」在实现层面都先要求分配器真的按设备独立选槽；② K3 讨论的「固定点分得到块」在 bug② 存在时无法被 ckpt_cost 的任何一种算法真正兑现——即使准入时算对了 ckpt_cost，段耗尽没有回落会让固定点的某个提交内生块请求提前失败，这与准入扣了多少无关。⇒ **两处 bug 是「先让候选臂可测、可实现」的必要条件，不是候选臂之间要比较的差异项**。

## 六、第一轮判决里越位的句子，逐句指出
