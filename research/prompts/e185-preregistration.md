#### 已定项 3：判据取什么形式

**定案**：判据是 `CPU 16 线程耗时 ÷ (传输 + 计算 + 传回) 耗时`，小于 1 就否掉那一格。代进去的 CPU 侧数必须是**多核饱和吞吐**，不是「单核 × 核数」：线性外推与实测在 AES-GCM 上差近 4 倍（外推约 61 GB/s，实测饱和 17.4 GB/s）。GPU 侧的两个地板是**单程 56.69 GB/s**（锁页 H2D，≥64 MiB）与**来回 28.5 GB/s**（H2D + D2H，回传全部数据的场景走这一行）；CPU 侧的上限是**内存带宽墙 64.91 GB/s**。⇒ **GPU 只在「CPU 那侧的实际吞吐掉到传输地板以下」时才有机会。**

**射程**：⚠️ **「瓶颈是不是 CPU」不等价于「这个任务有没有硬件指令」**——有 AES-NI 的加密照样在 17.4 GB/s 就饱和，瓶颈仍然在 CPU 侧，**有硬件指令 ≠ 快到 GPU 追不上**。⚠️ **「CPU 够快所以 GPU 无用」这个前提在本工程不成立，不许拿它支撑任何结论**：它来自单核乘核数的线性外推，而多核实测饱和在 17.4 GB/s，差近 4 倍且方向相反——17.4 低于 GPU 的两个地板。代进去之后四个候选格各是什么：scrub（校验和 / MAC）有 AES-NI 时 CPU 侧多核饱和 17.4 GB/s（8 线程，16/32 线程 16.3/16.5；单核 3656.13 MiB/s）⇒ 按判据这一格 GPU 赢，⚠️ **两侧都没坐实，不许当已定结论用**（GPU 侧缺真的 AES-GCM 核函数）；无 AES-NI 的机器上单核 244.74 MiB/s ⇒ 16 核约 4.1 GB/s，与高端 NVMe 阵列同量级，这一档 GPU 可能有用，多核未测、饱和值只会更低；EC 重建无数据（Reed-Solomon over GF(2⁸)，重建要读全部幸存盘并算 parity，计算量随盘数 × 容量线性，这一格计算确实重）；批量压缩无数据（压缩比与吞吐的取舍，GPU 压缩库存在）。这两个数（17.4 与 244.74）来自 E6（加密算法选型），不是 D24（后台重活能不能卸给 GPU） 自己量的。⚠️ **不能读成「GPU 无用」**：计算段那一段的推论只对**带宽受限**的核函数成立，**压缩是算力受限的**，它的计算段可能远不止那一成，那一格仍然开着且仍要等 `nvcc`。⚠️ **还有一层压在上面**：三个候选场景全是盘限的后台活，盘带宽比 64.91 与 28.5 都低得多 ⇒ 整件事若是盘限的，CPU 本来就在空转，卸给 GPU 省不下任何东西——**这一层是推理不是实测**（本工程没有阵列）。⚠️ **一个未验的逃生口**：GPUDirect Storage 让 NVMe 直接 DMA 进显存、绕开主存与 PCIe 那一跳，**它会推翻「GPU 吃数据 56.69 GB/s」这个传输地板**，没测过，不许当它不存在。要定 D24（后台重活能不能卸给 GPU），先要量 EC 重建与批量压缩这两格的 CPU 上界，以及「PCIe 传输 + 核函数 + 传回」这条链路相对纯 CPU 的净收益——**数据要过一遍 PCIe，那笔搬运成本可能吃掉全部计算收益**。**本机可测**：NVIDIA RTX 5090（32 GB）+ RTX 5060 Ti（16 GB），驱动 595.84；`nvcc` 没有装（`command -v nvcc` 零命中，`/usr/local/cuda*/bin/nvcc` 也没有），那是 G24.3（计算段占比） 的前置。

**依据**：

- E21（GPU 卸载的净收益）：三条路径的吞吐（CPU 吃数据 64.91 GB/s、GPU 单程 56.69 GB/s、GPU 来回 28.5 GB/s）把判据的两个阈值钉住——GPU 光把数据搞进去就已经比 CPU 读它慢 13%，而这还没开始算；计算段用带宽受限算子给上界，显存内 1041 GB/s 而端到端（含传输）只有 50.3 GB/s ⇒ 传输占 90.3%、计算段几乎免费，对纯扫描那一格净收益 0.78×，小于 1 ⇒ GPU 输。**决定 GPU 赢不赢的是 CPU 那侧有没有对应的硬件指令，不是 GPU 有多快。**
- 用户定案（判据的正确形式是多核饱和吞吐），原话在变更史。

**欠**：无。

**入库装置**：`crates/singlefs-checker-tier/src/bin/e185_gc_batch_wall_clock_split.rs`，变异表 `scripts/experiment-apparatus/e185_gc_batch_wall_clock_split.mutations.tsv`（表的位置照执行员定义的入库装置那一支，执行员与它不一致时照执行员定义，在第十二节记一行）。理由：问题单问的就是 `crates/` 这份 GC 代码的性质（一批的挂钟、它的阶段拆分、它交给 GPU 的字节），另写一份独立模型答不了；GPU 一侧量的是 checker 档里唯一一份 GPU 代码 `GpuCard::crc32c_of_ranges`。一个二进制、四个子命令：`wall-clock`（第一段）、`stage-split`（第二段）、`gpu-submission`（第三段，`#[cfg(feature = "gpu")]`；不带特性编出来的这个子命令退 78 并报「本次未跑：没编 gpu 特性」）、`foreground-fsync`（第四段，附带）。

**装置读 `crates/` 的这些常量，执行员逐个改成本地常量、开跑先回比断言**（对不上走第十一节停机条款，不直接引）：

### 负载：池怎么造

每个取样点（f、P）造一个池：harness 默认参数 mkfs 两块盘（`parameters()`），经挂着的会话发用户改动写码 1 数据单元，按段顺序写满 ⌈P ÷ 32⌉ 段的数据单元；再对每段里按槽序每 4 个单元覆盖写其中 3 个（f = 0.25）或 1 个（f = 0.75），抬回退下限到准入上限（`raise_rollback_floor_to_the_admission_ceiling`，同整理流前缀）直到被覆盖的旧落点按记录已释放；关掉再 `mount_writable_with_compaction_switches` 可写挂载（这样造出来的段不是本次挂载开过的段，`choose_region` 资格第一条）。挂好之后、第一次 `run_compaction` 之前，装置核三样，不过就记「几何没造成」、改负载重造（第十一节，不算修订判据）：greedy 将选的那一段（活槽最少、起点最小）里未释放记录全是码 1 数据单元；活槽数 = 64 × f；`mapped_units` 条数报出来。greedy 选中的若是别的段（例如活槽更少的树节点段），先改负载（多覆盖写那几段、或让节点段的旧节点也被引用着）重造；改了三次仍造不成的，那个取样点改走登记好的后备：`forced_region` 点名一个 f 段（只供测试的开关，资格五条照判），第 1 行与甲、乙两段照常量，丙段只按重放量（`choose_region` 是纯函数，重放本来就是丙段的量法），结果行写明这个点走的是后备。

每一轮从逐字节相同的起始镜像开始：池造好之后，真盘臂把两个镜像文件拷一份做起始件，每轮开跑前从起始件拷回、核两个文件的 sha256 与起始件相同；内存臂每轮按同一串改动重造并核两块内存盘的 sha256 相同。真盘镜像放 `~/.local/share/singlefs/work/<执行员的草稿目录>/e185-images/`（不放开机清空的目录），建时整份写满零并 `fsync`（不是稀疏、不是 `fallocate` 的未写区段），开跑前用 `stat -c '%b %B %s'` 核占用块数 × 块大小 ≥ 文件字节数。

### 计时与计数怎么做（被测进程里计）

- **计时包装设备**：包住真盘或内存盘，`BlockDevice` 的每个方法（连同 trait 里带默认实现的那几个）都转给里面那块盘，每次调用前后各读一次 `Instant` 与本线程 `/proc/thread-self/schedstat` 第一个字段，按方法累计挂钟、CPU、调用次数与字节数；写还按「落在这一批计划的目的地」与「别的」分两栏累计字节（目的地取发布之后 `units_relocated_by_this_publish` 的位置）。
- **一批**：一次 `run_compaction` 调用前后读 `Instant` 与 schedstat；调用返回之后（在计时窗口外）读 `CompactionRun` 的 `batches_published`、`outcome` 与会话 `compaction.observations`，判这一次是签发、批、还是停。
- **包含自检**：每批 `挂钟 ≥ CPU + 等盘` 必须成立；`挂钟 − CPU − 等盘`（不在 CPU 上、也不在设备调用里的时间）超过挂钟 10% 的那一轮作废重跑（第十一节）。
- **阶段拆分（第二段）**：在每次 `run_compaction` 调用返回之后、计时窗口之外，装置照这一次调用的输入重放纯阶段：用调用之前那一版（`MountedSession::current` 交出的有树的一版）的 `allocation_records`、映射条目、钉住与隔离的槽，对同一个 R 调 `scan_region`，读单元的闭包从这一批计时包装设备读到的字节里取（读之前把这一批每次读的偏移与字节记下来）；`choose_region` 在签发那一步照会话的选段循环重放。三个阶段各自计时：甲 = 对每个被读单元的整单元字节调 `crc32_castagnoli`；乙 = 整个 `scan_region` 调用；丙 = 每次 `choose_region` 调用。每个阶段重放 5 次取中位（纯函数、内存里，单次观测只说明没有隐藏状态）。会话里映射条目怎么取是私有函数：装置照 `mounted_session.rs:2780-2856` 的取法另写一份，取出的条目集合与这一批 `scan_region` 判成可搬的 key 对得上才算取对（第十一节停机条款）。
- **饱和吞吐（第二段，D24 已定项 3 的形式）**：同一份重放输入，16 条线程各自重复跑同一阶段函数 2 秒，合计字节 ÷ 挂钟；另报 1 线程与 N 线程（N = 派发提示的「线程上限」，装置的线程变量 `E185_THREADS` 设成它）两点；装置核起了几条不同的线程。

### 各行的臂（对面那条臂写成支持它的人认的样子）

**第 1 行。** 整理整条路在调用线程上同步跑（第三节「线程」一行），一批的挂钟 ≈ CPU + 等盘（包含自检核这一点），所以「理想卸载把 CPU 部分全部移走能省下这一批挂钟的几成」= ρ ÷ (1 + ρ)，由做法推得出。

| 臂 | 怎么做（支持它的人怎么看这条路） | 做完会怎样 |
|---|---|---|
| 盘 | 一批要对 R 里每个活单元读整单元（`O_DIRECT`，每次一块对齐暂存区）、发布写两块盘的搬迁副本与重写的树节点，再 `fdatasync`；这些等待在消费级 NVMe 的 ext4 镜像上是毫秒级，而解头、CRC、查映射、算账都在内存里 | 真盘上一批的等盘时间大过 CPU 时间：把 CPU 部分移走只省下挂钟的小头；同一批在真盘上明显慢于内存设备 |
| CPU | CRC-32C 是软件查表、整单元都算；映射反查对全部映射条目线性找两遍（`region_scan.rs:286-289`、`309-311`），随池里的单元数涨；每次推之前对全部进映射单元在映射树里查一次（`mounted_session.rs:2780-2856`）；发布重写四棵树并封校验和；一批真正的 I/O 只有几次读写与一次 `fdatasync` | 真盘上一批的 CPU 时间大过等盘时间：把 CPU 部分移走省下挂钟的大头；同一批在真盘上与内存设备上差得不多 |

ρ 落在 0.5 与 2 之间是「两边都占」，是正当结果。

**第 2 行。** 三个候选是嵌套的（甲 ⊂ 乙 ⊂ 丙），实验量三段各自的份额与吞吐，各段增量单独判。

| 臂 | 怎么做 | 做完会怎样 |
|---|---|---|
| 甲 只算校验和 | CRC 是唯一字节密集、单元之间互不相干的一段，正合 GPU；解头与映射反查是分支与查表，交给 GPU 要把整份映射条目也传过去 | 一批 CPU 里 CRC 那一段是值得移走的一块，解头、反查与选段相比之下是小头 |
| 乙 加解头与映射反查 | 反查对全部映射条目线性找、每条记录两遍，池越大越重，它才是扫描的大头；解头顺手在同一份字节上做 | 扫描里除去 CRC 的那部分（解头、反查）也是值得移走的一块，且随池变大 |
| 丙 再加选段打分 | `choose_region` 每次调用把全部未释放记录按段数一遍、整段过滤一遍，选段循环里连调多次，盘越大越重 | 选段那部分摊到每一批之后也是值得移走的一块，且随盘变大 |

**第 3 行。** GPU 一次提交的时间按 `t(B) = a + b·B` 量（B 是这一次交的字节），一批交给 GPU 的字节 `B_批` 从第一段量出来。固定开销占比 `φ = a ÷ (a + b·B_批)`。

| 臂 | 怎么做 | 做完会怎样 |
|---|---|---|
| 甲 一批一交 | 每批扫描完把这一批的单元交一次；一次提交的固定开销（建缓冲、提交、等、回读）在一批的字节面前小 | 一批一次提交，固定开销只占这次提交时间的小头 |
| 乙 连续几批攒起来一次交 | 固定开销盖过一批的字节，几批的单元合成一次提交，合几批由显存上限定 | 一批一次提交时固定开销占大头；合几批之后固定开销摊薄，合的批数受显存上限管 |
| 丙 放宽 R | 同乙，但靠一条意图罩不止一个聚簇段让一批的字节变大 | 同乙，摊薄靠一批变大而不是合批；乙丙之间七·1 只给 n* 与每批字节，R 的语义（D26 已定项 1）与批间重扫的依赖由七·2 设计轮判 |

**第 4 行。**

| 臂 | 怎么做 | 做完会怎样 |
|---|---|---|
| 甲 按一批在真盘上的写字节与挂钟取默认值 | GC 单跑的写带宽远低于这块盘能写的，前台 fsync 撞上它的机会小，默认值直接从一批的写字节与挂钟算 | GC 单跑只占这块盘写带宽的小头，默认值从一批的写字节与挂钟算就够 |
| 乙 另跑前台负载量 GC 对前台 fsync 延迟的影响 | GC 每批一次 `fdatasync`、写两块盘，与前台 fsync 抢同一个设备队列，只看单跑的带宽看不出前台会被拖多久 | GC 并发时前台 fsync 的尾延迟被明显拖长，默认值要从并发量出来的数取 |

### 真实基线

`CompactionSwitches::PRODUCT`，只把批大小换成 `ForcedForTests(K)`：选段走产品的 greedy（`forced_region = None`）、R 排他、目的落点政策、合取 7 的 N₀、搬迁发布次序都是产品值；挂载用 `mount_writable_with_compaction_switches`。与产品一次运行的差别只有两处，照实报：发布预算压到 1（每次调用一次发布），所以每次发布之后都跑一次 discard（`run_compaction` 末尾），discard 的挂钟与 CPU 由计时包装单列；真盘是 ext4 上的镜像文件不是裸盘。

### GPU 一侧怎么量（第三段）

口径借 E21（只借口径）：每档先跑一次丢掉（编管线、建上下文），每次计时的区间就是一次 `crc32c_of_ranges` 调用的进出（它自己 `poll(Wait{submission_index})` 等这一次提交做完、映射回读之后才返回，等价于 E21 的计时前后同步），5 次取中位，钉死用哪张卡并记进结果行。不用 E21 的 torch / CUDA：七·2 的 GPU 代码栈没定，仓里现有的 GPU 代码是 wgpu（Vulkan），量它。

- 卡：经 `gpu_cards_by_priority(&[(序号, 4096)])` 一次起一张，5090 与 5060 Ti 各量一遍（序号照 `nvidia-smi` 的，结果行写型号与序号）。整条命令经 `bash scripts/crash/gpu-quiesce-run.sh -- …` 起（`.claude/rules/verification.md`「凡用 GPU 先清场，跑完不复原」），清场回读没过它退 78，本段报「本次未跑」。
- 段数 n 取 1、4、16、64、256、1024、4096、16384，每段 32768 字节（一个整数据单元，内容取第一段造池时的数据单元字节）；n 的上界再截到 `max_storage_buffer_binding_size ÷ 32768`（设备的上限，结果行写出来）。另跑 16384 字节一段（码 2 节点大小）的同一组 n：`crc32c_of_ranges` 按 32 KiB 一槽上传，节点也传 32 KiB，两组的 t 应相同（报出来，不判）。
- 每次调用交回的 CRC 与 CPU 的 `crc32_castagnoli` 逐段相同，有一段不同整张卡作废。
- 拟合：对全部 n 的中位 t 关于输入字节 B 做最小二乘，a = 截距、b = 斜率；另报 `t(n=1)` 的中位（固定开销的上界）与最大两点之差算出的斜率。
- B_批 取第一段量到的甲段字节（每个取样点、每批一个数）；φ 与 n* 按第三行的式子算，显存占用按 `bytes_crc32c_of_ranges_needs(n* × 每批单元数)` 算、与那张卡的空闲显存比。

| 第三段 `gpu-submission` | 两张卡的 a、b、物理下限与 CRC 对拍；用第一段的 B_批 算 φ 与 n*；用第二段的饱和吞吐算 Q9 | 第 3 行；第 2 行的 Q9 | 第 3 行够判；第 2 行全部够判 | 2 小时内。推的：带 `gpu` 特性另编一次约 10 分钟，清场排队不计；每张卡 2 组 × 8 档 × 6 次，最大一档 512 MiB 上传按 PCIe 下限约 9–17 ms，合计不到 1 分钟 |

四段各自预计都在 2 小时内，不写分片、续跑、多机三样。分段不是「全部做完」的计划：每段交回之后主 agent 对着问题单判续不续，一行开着的都不剩就停，后面的段不跑。

### 并行与挂钟（第十二节 12.10 加，12.11 改成全局队列）

不计时的准备进一个全局队列，计时的测量照旧在一条线程上串行；两者按批交替：跑一次准备（批内并行）、全部准备线程停下，再核本进程只剩一条线程、当场声明串行段，然后串行量；量到缺的那一份再跑下一次准备。判据、阈值、停机条款、臂、取样点、轮数、批大小一个不改（12.10、12.11）。

| 单位 | 互相独立吗 | 怎么跑 | 为什么 |
|---|---|---|---|
| 一个取样点的造池与几何核（`prepare_the_sampling_point`，含至多三次改负载重造） | 不同取样点互相独立：各自的配方、各自的两块内存盘，不读别的点的结果；同一点的几次重造前后依赖（下一次的配方取决于上一次的几何） | 每点一份准备单位，一条线程；同一点的几次重造在那条线程上按次序 | 不在任何计时窗口里；`construction_seconds` 只报不判 |
| 第 2–5 轮的内存池重造 | 互相独立：同一份配方各造一份，只依赖那一点最后的配方，不依赖哪一轮量出了什么；摘要与第一份比，不同的那一轮照旧作废 | 每轮一份准备单位，各一条线程；那一点几何核还没定时按头一次的配方推测着先造，几何核改了负载的那一点把推测造的作废、按新配方重造（作废几份报进 `name=preparation` 的 `speculative_rebuilds_voided` 与第一段 `name=pool` 的同名字段） | 同上 |
| 真盘镜像的建立（起始件与工作件写满零、写进池、核摘要） | 只读那一点造好的池，与重造互相独立 | 每点一份准备单位，那一点造好、它之前的点都量完才派；在量那一点之前建，量完删，盘上同一时刻只有正在量的那一点的镜像（每点 4 个 4 GiB 文件） | 同上；盘的空间按串行时一样只够一个点 |
| 每次 `run_compaction`（内存臂、真盘臂、阳性对照）、设备顺序写带宽 Q15、第二段的阶段重放与 2 ms 对照、丙段盘大小敏感性 | 不并行 | 一条线程，开始之前核本进程只剩一条线程（`/proc/self/status` 的 `Threads:`，不是 1 就停），再当场声明串行段 | 量的是这一条线程的 CPU、挂钟与等盘：别的线程抢 CPU、内存带宽（内存臂）与盘（真盘臂）会混进挂钟与等盘 |
| 饱和吞吐 1 / 16 / N 线程 | 它本身就是多线程的量 | 照旧；开始之前声明并行段 | 第五节「计时与计数怎么做」原文 |

- **队列与次序**：一段里全部准备单位按量的次序排：每个取样点先造池与几何核，再真盘镜像（第一段），再第 2–5 轮重造；四个取样点第一段 24 份、第二段 20 份。量的次序与产物行序照旧按取样点、轮次；准备时的行先攒着，轮到那个点量的时候照原来的位置打。
- **派几份**：这一刻能派的按次序排。最先量的那一点按次序往里加，份数不超过空着的线程数、峰值之和不超过「内存上限 − 记在账上的 − 余量」，可以只派一部分；它整点派出去了，后面的点要整点装得下（线程与内存）才派，一点装不下就停，不跳过它去派更后面的（免得后量的点占住内存；整点派是为了一点的几份一起做完，不让后量那一点只派出造池、重造留到下一次，把两次准备各拖长一遍）。什么都没在跑、要的那一份还没好时保底派一份。账：在跑的按峰值，造好没取走的按池的内存，取走或那一点量完就销账。峰值：造池与几何核 2 份池（按估的），重造 5/4 份，建镜像 1 份；一份池那一点造好之后按两块内存盘真写过的扇区 × 640 字节，没造好按估的（12.10 的估算：P = 1024 是 346030080 字节，P = 8192 是 2694840320 字节，推的）。余量：还没量完的点里最大一份池的 2 倍（之后串行测量时内存臂要拷一份池）。线程数与内存上限的取法照 12.10：线程数与饱和吞吐的 N 同一个取法（`E185_THREADS`，没设取 `SINGLEFS_THREAD_CAP`，再没设取 `.claude/heavy-thread-default` 的登记值）；内存上限取 `E185_MEMORY_CAP`，没设取本进程控制组的 `memory.max`，再没有取 28G。
- **批的切法**：量的那一侧要的那一份还没好，就跑一次准备：按「派几份」派，收回一份就再看能不能派；要的那一份好了就不再派新的，等在跑的都交回、全部线程停下才回到量的那一侧。内存装得下全部，头一次就把真盘镜像以外的全部派出去，一次做完；装不下就是几批，批内并行、批间串行量。配置行报一共几份（`preparation_units`）、按造池前的估算头一次能同时派几份（`preparation_units_started_at_once_by_the_estimates`）与由此判的 `preparation_plan_by_the_estimates=all_at_once` 或 `in_batches`；每次准备打一行 `name=preparation`（`target`、各类派了几份、推测着派的重造几份、作废几份、保底几份、`most_threads_at_once`、`distinct_threads`、`thread_limit`、`memory_cap_bytes`、`memory_headroom_bytes`、`largest_accounted_bytes`、`wall_seconds`）。按估算，28G 下头一次派 15 份（前三个取样点各五份；第四点 P = 8192、f = 0.75 那五份装不下），即分两批；64G 下 20 份一次派完。这几个数由单测 `first_start_under_twenty_eight_gibibytes_takes_fifteen_units_in_the_measurement_order_and_under_eight_takes_five` 钉住；整点派由 `later_points_start_only_when_all_of_their_units_fit` 钉住。
- **串行段声明**：环境变量 `SINGLEFS_SERIAL_DECLARATIONS` 设了（`scripts/hosts/multi-host-run.sh --peer` 设成第二台那一趟的 `.serial` 文件），每次准备开始往它指的文件追加 `<unix 秒>\t此刻并行`，每个计时窗口开始之前（核过只剩一条线程之后）追加 `<unix 秒>\t此刻串行：<理由>`，与上一条相同不重写；饱和吞吐开始之前追加并行。写法照 `scripts/hosts/core_usage.py` 文件头「声明」。三句理由：第一段「E185 计时窗口：第一段一批搬迁的挂钟、CPU 与等盘要在没有别的线程的进程里量」；Q15「E185 计时窗口：设备顺序写带宽 Q15 要在没有别的线程的进程里量」；第二段「E185 计时窗口：第二段的一批搬迁、阶段重放、2 ms 对照与盘大小敏感性要在没有别的线程的进程里量」。没设不写；设了而写不进，打一行 `name=stopped reason=serial_declaration_not_written:…`、收尾、退 3（同停机条款的退出码），不静默。
- **页缓存**：真盘臂每次测量之前（拷回、核摘要之后，计时之外）对工作件先 `fsync` 再 `POSIX_FADV_DONTNEED`，量的那一刻工作件一页都不在页缓存里，与准备阶段同时攥着几份池、内存紧不紧无关（12.10 第 3 条，12.11 不变）。
- **预计挂钟（推的）**：依据同 12.10，是第一段第一趟产物（仓外，sha256 `64749399d95512b3e63aaa176e42a5d5627b8f84e743f2b66c96c16d287e06ae`）里 20 行 `name=geometry_attempt` 与 `name=memory_rebuild` 的 `construction_seconds`：P = 8192、f = 0.25 每份 2022.6–2219.6 秒，P = 8192、f = 0.75 每份 1057.5–1107.0 秒，P = 1024 每份 9.4–20.7 秒（串行合计 16045.9 秒）。28G 下按估算分两批：头一批 15 份同时造，挂钟由 P = 8192、f = 0.25 那五份定，约 2220 秒，十几份同时造互相抢内存带宽按慢 20% 算约 2650 秒；第二批是第四点的五份，约 1110–1330 秒；第一段另有后三个点的真盘镜像各约 60 秒（12.10 的估计）。准备合计：第一段约 3500–4160 秒（1.0–1.2 小时），第二段约 3330–3980 秒（0.9–1.1 小时）。第一段再加测量约 0.5 小时，合计约 1.5–1.7 小时；第二段再加阶段重放与饱和吞吐约 0.2 小时，合计约 1.1–1.3 小时。真写过的扇区比估的少、头一次就全派出去时，准备只有一批，约 2220–2650 秒，两段各再少约 0.3 小时。两段按估算都在 2 小时内，「四段各自预计都在 2 小时内」那一句照旧（12.11）。

## 六、报哪些量与各自的判据

每个量一行、各报各的判定，不合成一个真假。判定按取样点、按轮报；5 轮判定全相同才写那个判定，不全相同写「不稳定」（真 I/O，`.claude/singlefs-ai-sop/rules/test-discipline.md`「单次观测不算数」）。阶段重放与 GPU 拟合的输入是记下的字节，确定性那一半只说明没有隐藏状态。门槛旁边写它从哪来，核过没有一个能由臂的定义直接推出：第 1 行的 0.5 与 2 是「理想卸载省下 ≤ 1/3 或 ≥ 2/3」两条边，臂的定义只说「受谁限」；10% 与 50% 是登记时定的政策线，不是臂的同义反复。

| GPU：一次调用建的缓冲字节 `bytes_crc32c_of_ranges_needs(n)` | n = 1 → 32804，n = 1024 → 33574928，n = 4096 → 134299664，n = 16384 → 537198608 |
| GPU 对 9 字节「123456789」的 CRC-32C | 0xE3069283（公开校验值，`crates/singlefs-core/src/checksum.rs` 单测用的同一个） |
| GPU 一次调用时间的物理下限 | 输入字节 ÷ 链路峰值；PCIe 5.0 x16 峰值 63015384615 B/s（128 MiB 至少 0.00213 秒），x8 31507692308 B/s（128 MiB 至少 0.00426 秒）；链路代数与宽度以 `nvidia-smi` 现查为准 |

互比断言旁边的绝对值：Q2（两臂挂钟互比）旁边是逐批读写字节的绝对值（上表）；Q4（K 与 2K 互比）旁边是搬迁副本字节翻倍的绝对值；Q13（φ）旁边是 GPU 的 CRC 校验值与物理下限。三条臂一起错（比如计时包装把读写都漏记）时，「每批读字节 = Σ 跨度 × 16384」那一条先红。

> - **线程数**：与饱和吞吐的 N 同一个取法（`E185_THREADS`，没设取 `SINGLEFS_THREAD_CAP`，再没设取 `.claude/heavy-thread-default` 的登记值）。一组装几份 = min(线程数, 内存预算 ÷ 一份峰值)，各份峰值不同时按次序累加到预算为止，至少一份。取样点只有四个、每点的重造只有四份，所以实际同时在跑的至多五条线程；再多的线程没有互相独立的单位可分。
> - **内存**：上限取 `E185_MEMORY_CAP`（`28G` 这种写法），没设取本进程控制组的 `memory.max`（`run-with-memory-cap.sh` 给的上限落在那里），再没有取 28G；产物配置行报取到的字节数与从哪取。一份池的内存：造之前按估算（两块盘 × (2P + 64) 个数据单元 × 32768 字节，元数据按同等量留，再按每写过一个 512 字节扇区 640 字节折算；P = 1024 是 346030080 字节，P = 8192 是 2694840320 字节，推的），造之后按两块内存盘真写过的扇区数 × 640 字节。峰值：准备一个取样点 2 份池（造好的与几何核的拷贝），重造一份 5/4 份，建镜像 1 份。预算 = 上限 − 已经攥着的池 − 2 份池的余量（之后串行测量时内存臂要拷一份池）。内存紧时余下的重造推到用到那一轮的开头再造一组，量的时候不造。
> - **页缓存**：真盘臂每次测量之前（拷回、核摘要之后，计时之外）对工作件先 `fsync` 再 `POSIX_FADV_DONTNEED`，量的那一刻工作件一页都不在页缓存里，与准备阶段同时攥着几份池、内存紧不紧无关（12.10 第 3 条）。
