Q1. Operation sequence: Create a file with logical identity (0,0,0,0,0), write data at offset 0 with birth generation 1, resulting in map entry key (0,0,0,0,0,1) pointing to physical block P1. Create snapshot S1. Write again to the same logical identity at offset 0 with birth generation 2, resulting in map entry key (0,0,0,0,0,2) pointing to physical block P2. When reading from S1, the snapshot tree pointer for the block is a hint containing only physical address P1. The system lacks birth generation 1 for the map lookup. Attempting to use birth generation 2 for the lookup returns P2, which is incorrect data for S1. The system cannot correctly dereference S1's data because the birth generation is missing from the hint.

Q2. Workload: System limits live snapshots to 10. Map leaf nodes are 8KB. Each version entry in the chain is 16 bytes (8 bytes birth generation, 8 bytes physical location). Publishing a new version reads the entire 8KB leaf node, modifies the chain by adding a new 16-byte entry, and writes back the full 8KB block. Device minimum IO size is 8KB. Since the write size matches the device's minimum IO size, no internal read-modify-write occurs. The chain length (11 entries) fits within 8KB, making entry width bounded in practice and RMW harmless.

Q3. Third encoding: Key is 33-byte five-tuple. Value is 8-byte pointer to a version chain storage. Each version in the chain storage is 16 bytes (birth generation 8 bytes, physical location 8 bytes). Total map entry width 41 bytes. Publish is a pure insert into the version chain storage. This beats Candidate ONE on storage efficiency: for 100 versions of the same five-tuple, Candidate ONE uses 4100 bytes in the map, while this encoding uses 41 + 1600 = 1641 bytes. It beats Candidate TWO on bounded width and no read-modify-write for map updates.

Q4. The cost list misses freeing overhead when birth generation is unknown. Mechanism: When freeing a block from a snapshot, the system must know the exact key (five-tuple plus birth generation). Since the snapshot tree pointer is a hint without birth generation, the system must scan all map entries for the five-tuple to find the correct birth generation. For a five-tuple with 1000 versions, this scan takes O(N) time per free operation, adding significant overhead not accounted for in the given cost list.

Q5. Choosing Candidate ONE forces the block pointer header to carry birth transaction group. If the header does not carry transaction group (used as birth generation), and the tree pointer hint does not store birth generation, dereferencing fails. Example: Snapshot tree pointer for block physical address X has no birth generation. Block header has no transaction group. System cannot assemble key (five-tuple plus birth generation) for map lookup. Thus, Candidate ONE requires the header to carry transaction group to provide birth generation, making the open question's answer explicit yes.
