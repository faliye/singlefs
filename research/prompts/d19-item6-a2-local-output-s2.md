R1: No counterexample exists. Code 1 units have a write order consisting of a unique instance id (H3) and a unique transaction number within that instance (H2). Each transaction writes at most one data unit, ensuring the write order is unique per unit. Thus, the K key for code 1 units (class tag + birth tree + birth checkpoint + write order) cannot be duplicated for different units.

R2: Fixed point iteration with crash and remount. Start checkpoint 5 with instance id 3. Write code 2 unit A with birth sequence 0 during the first fixed point round. Crash occurs. Remount with checkpoint 5 and instance id 3 intact. Write code 2 unit B with birth sequence 0 during the second fixed point round. Both units A and B have K key: class tag 2 + birth tree value + checkpoint 5 + instance id 3 + birth sequence 0. This violates R2 because the birth sequence counter was reset to 0 in the same scope (tree, checkpoint 5, instance id 3), as permitted by H7.

R3: No counterexample exists. After an instance switch (H4), the new instance id is unique and different from the old instance. For code 1 units, the write order includes the new instance id, so keys differ from old units. For code 2/3 units, the key includes the new instance id, so keys also differ. Published units from the old instance have instance id values that cannot match the new instance's keys, preventing shared keys.

R4: B-tree node pointers store only offset references to child units. When dereferencing a child code 2 unit, the system must read the child's header to obtain the birth sequence for the K key (class tag + birth tree + birth checkpoint + instance id + birth sequence). This requires an extra unit read, violating R4 as the full K key is not available without additional reads.

R5 part 2: Fixed point iteration without open disposition. Start checkpoint 5 with instance id 3. Write code 2 unit X with birth sequence 0. Crash occurs. Remount and rewrite unit Y in the same checkpoint 5 and instance id 3 with birth sequence 0. Units X and Y share K key: class tag 2 + birth tree value + checkpoint 5 + instance id 3 + birth sequence 0. This violates R5 part 2 because K does not produce different keys for the two versions, contradicting the claim that K ensures uniqueness at the fixed point when H7's open disposition is not adopted.
