## 条款 3：本轮最重的一条——结论对，但它写的那一步理由过强

### 一、「不经过中央映射解旧版本」这条路，仓里不存在

我按要求直接读了源码，不用材料的转述：

`research/e7-index-bench/src/bin/e96_hybrid_consistency.rs:361-371`（读路径全文）：

```rust
    /// 读：提示优先，失配回映射。返回 (读到的版本, 有没有多跳)。
    fn read(&self, root: u32, key: usize) -> (u32, bool) {
        let e = self.leaf_entry(root, key);
        if let Some(&occ) = self.occupant.get(&e.hint) {
            if self.header_matches(occ, e.ver) {
                return (occ, false);
            }
        }
        let slot = self.map_slot[&e.ver];
        (self.occupant[&slot], true)
    }
```

**`map_slot` 的 key 是 `e.ver`，不是 `key`。** 而 `ver` 是每次发布新铸的一个号
（`:245-247`：`let ver = self.versions.len() as u32; self.versions.push(Version { key: key as u32, birth: self.txg });`）
⇒ **`ver` 就是 (五元组, 诞生代号) 这个对**。同一份源码 `:338-345` 把这件事说死了：

```rust
    /// 单元头匹配：hdr_key 只比 key；hdr_birth 比 (key, birth) ⇒ 等价于同一个版本。
    fn header_matches(&self, occupant_ver: u32, wanted: u32) -> bool {
        match self.header {
            Header::Key => self.versions[occupant_ver as usize].key == self.versions[wanted as usize].key,
            Header::KeyBirth => occupant_ver == wanted,
        }
    }
```

⇒ 材料第三节说「**E96 全程按「(五元组, 诞生代号) → 落点」建模**」这句话，**源码坐实**。

**回答问的那一问**（`hdr_birth` 臂错读恒 0 是靠头里的 birth 只做检测，还是靠映射能指到旧版本）：
**两样缺一不可，而且分工是清楚的**——头里的 `birth` 只负责**让提示失配**（`header_matches` 那两行），
它自己不给出任何落点；**给出正确落点的是 `map_slot[&e.ver]` 那一行**。
`audit()`（`:421-447`）把这件事写成了守恒条件：它先把**活头根与全部快照根**可达的 `ver`、
再把全部 deadlist 的 `ver` 收进 `referenced`，然后逐个要求
`let slot = *self.map_slot.get(&v).ok_or(format!("ver {v} 无映射"))?;`
⇒ **模型明令「每一个被快照引用的旧版本，映射里都必须有它自己的一条」**。

### 二、把 key 压回 33，我实测了会发生什么

探针加了三件事，都不动模型：`key_collisions()` 数「同一个五元组名下同时活着几个版本」；
`key_map()` 造一张只有五元组的映射（每个 key 只留 `birth` 最大的那个版本，正是「33 字节 key」那种映射）；
`read_keymap()` 把读路径的回落那一行换成查这张映射。40 格全部结果一致，抄两行原样：

```
hdr alloc load seed | map_live keys max_ver_per_key | wrong_verkey wrong_keyonly | dl_release dl_misfree_keyonly
hdr_birth alloc_lowest uniform 0 | 5534 4096 4 | 0 1084 | 481 481
hdr_birth alloc_lowest adversarial 0 | 5539 4096 4 | 0 1520 | 485 485
```

口径：`map_live` = 第 200 轮末活着的映射条目数；`keys` = 不同五元组数；
`max_ver_per_key` = 同一个五元组名下同时活着的版本数的最大值；
`wrong_verkey / wrong_keyonly` = 同一趟「全部根 × 全部 key」扫描下，
回落到（按版本身份的映射 / 只有五元组的映射）的错读数；
`dl_release` = 这次销毁要释放的条目数，`dl_misfree_keyonly` = 其中按只有五元组的映射解落点会放错的条数。

三条硬事实：

1. **33 字节的 key 装不下**：40 格全部 `map_live` ≈ 5517–5554 而 `keys` 恒 4096
   ⇒ 一张以五元组为 key 的表**最多容得下 4096 条**，还有 **1421–1458 条活着的映射无处安放**；
   `max_ver_per_key` 恒 **4**。
2. **读会错**：`wrong_keyonly` 在 40 格里是 **999–1532**（`hdr_birth` 臂本来恒 0）。
   注意这是**头带 birth 的那一臂**——也就是说 E96 那条「头带块 birth 就恒 0」的结论
   **不能单独兑现**，它依赖映射按版本身份建。
3. **释放会错，而且是全错**：`dl_misfree_keyonly` 与 `dl_release` **40 格逐格相等**（474–488）
   ⇒ 按只有五元组的映射去释放 deadlist 条目，**没有一条放对**（因为 deadlist 装的恒是旧版本，
   而这张映射只指得到现行版本）。这与材料里 E96 原有的「按提示解会误放约 5000 次 / 200 轮」是两码事：
   那条打的是**提示**，这条打的是**只有五元组的映射本身**。

⇒ **条款 3 的结论方向正确**：中央映射必须能按版本身份解引用，33 字节的五元组做不到。

### 三、打中的那一步：33 → 41 是两种编码之一，而条款 3 写成了唯一解

材料第三节问了第三种读法（value 是版本链，key 仍 33）。**它存在，而且真的能解出旧版本**：
`key(33) → [(birth_1, 位置条目 × w), (birth_2, …), …]`，读路径拿 `e.ver` 里的 `birth` 在链上选一格。
条款 3 的推理链是「映射要解旧版本 ⇒ key 必须含诞生代号」，**中间那一步跳了**：
「解得出旧版本」只要求 (五元组, 诞生代号) 这 41 位身份**出现在映射里**，
不要求它们**都出现在 B 树的 key 里**。

**我去量了这条路要付什么**（探针 `run_chain`，逐轮采样，同一组 40 格）：

```
hdr alloc load seed | 全程最大链长 最多同时多版的 key 数 | 发布数 需读改写的发布数 占比%
hdr_birth alloc_lowest uniform 0 | 5 1587 | 12800 12800 100.0
hdr_birth alloc_lowest adversarial 0 | 5 1664 | 12800 12800 100.0
```

- **链长上限 = 活快照数 + 1**：这个模型 `K_SNAP = 4` ⇒ 实测全程最大链长恒 **5**，40 格无例外。
- **多版不是罕见情形**：峰值有 **1579–1665 / 4096（39–41%）** 的 key 同时挂着 ≥2 个版本。
- ⚠️ **「100%」那一列是我的取样口径造成的，不构成证据**：这个模型开局就把 4096 个 key 全填满，
  于是「发布时该 key 已有活版本」恒真。它只说明链式 value 的每次发布都是读改写，不说明比例有意义。

**而链长在本工程没有上界，这是仓里明写的**——`.claude/kb/decisions/05-快照-空间记账机制.md:391` 整行：

> | 树 ID | **8** | **自由选择**。上界一条已定条款都指不到（D6（快照实现模型） 定每个可写头一棵自己的树、快照数无上界）⇒ **不许拿一个窄宽度去制造一个设计上限** |

⇒ **快照数无上界 ⇒ 版本链长无上界 ⇒ 链式 value 是一个宽度无上界的条目。**
这是链式读法真正的代价，不是「多几个字节」。

**由此得到条款 3 该怎么改**（结论保留，理由与字节判定的依据都要换）：
