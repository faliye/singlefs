## 五、倾向与「结果反过来我接不接受」

**倾向 D′ 的理由**：① 平时与臂 A 一样守住用户的整环承诺，只在盘紧时显式、持久地作废最旧的几代，不会冒出假候选（E135 判据 3、4）；
② 近满盘上把强制发布从每窗口 8.8–47 次压到约 0.8 次（P7），而臂 A 那个量级在每次发布三个序点（D16（发布语义） 已定项 7）下就是一次吞吐悬崖；
③ 它丢掉的是可退代数，而那正是用户问「承诺带来什么收益」时判断为收益很小的那一样（P4）；④ P6 的卡死机制写得出来，收严条件就写得出来。

**反过来**：若有腿构造出臂 D 的假候选 ⇒ 取臂 A；若 D′ 的收严构造得出仍卡死 ⇒ D′ 退回 D，交用户时把卡死写进代价；
若有腿论证「平时整环、盘紧才缩」这件事本身让回退承诺没有意义（例如用户永远不知道此刻还能退几代）⇒ 这条要写进交用户的代价表，不另找理由说小。

### D16（发布语义）连带定死的两条新规则（2026-08-26，来自生命周期条件的推导）

**新规则 1：快照发布点必须与 checkpoint 边界对齐，且位置钉死在「本 checkpoint 全部数据变更之后」。**
快照不许出现在 checkpoint 中间。
理由是机制性的：`birth` 的分辨率只到 checkpoint，**块无法表达「我生在本 checkpoint 里
快照点之前还是之后」**。不钉死它，D5（快照 / 空间记账机制） 那张边界表里 `birth == S.txg` 与 `death == S.txg`
两行会同时失去确定答案——而它们一个是**数据丢失**、一个是**空间泄漏**。
（同一 checkpoint 内建两个快照是允许的：它们捕获同一状态、其间 deadlist 为空；
但 checker 里的「上一个快照」要用 `(txg, 快照 id)` 打破并列。）

**新规则 2：checkpoint C 中产生的一切释放，在 C 被发布之前不得进入可分配集合。**
两个理由，第二个是 D16（发布语义）独有且更严的：

1. 回滚：崩溃后可能回到 C−1 的根，而生于 C 之前、死于 C 的块在那时仍然活着。
2. **D16（发布语义）把 D8（核心索引结构） 的中间态语义改写成「根 + journal 任意前缀，replay 后合法」。**
   若一个块在 journal 位置 p 被释放、位置 q > p 被重新分配并写入新内容，
   那么重放到 `p < r < q` 的前缀会得到一棵指向该地址的树，
   **而盘上的字节已经是 q 的内容了**（物理写不受 journal 位置约束）。
   **这不是理论风险，是必然的错。**

ZFS 有同型机制且更保守：`include/sys/txg.h` 的
`#define TXG_DEFER_SIZE 2 /* Number of txgs worth of frees we defer adding to in-core spacemaps */`。
⚠️ **那个 2 为什么是 2，没查到一手解释**；本工程的 defer 窗口要按 D16（发布语义）的重放语义自己推，**不许照抄**。

⚠️ 新规则 2 的 defer 窗口容量与 ENOSPC 直接相关（D3（空间分配）：**释放空间这个操作本身不许申请空间**），
而 D16（发布语义）使「建了又删」在同一窗口内闭合的概率大幅上升，**defer 窗口因此落在热路径上**。

### 根环深度是块重用延迟的上界，两者不是同一个数

保留 K 代根 ⇒ **最近 K 个事务里释放的空间都不许重用**，

一条记账记录写的是「某个统计量**此刻**的完整值」，不是「增加了多少」。
于是同一个统计量会被写很多次，**key 里必须有一段把这些次分开**，那一段就是「代」。

⚠️ **「代 = checkpoint 号」的口径已由 D16（发布语义）已定项 6 收口（2026-09-02）**：
每次发布（fsync 触发的也是发布）checkpoint_txg + 1 ⇒ **代按发布走，不按 5 秒窗口走**。
两条骑手条款直接砸在这里：代段宽度 **≥ 48 位**（2785 发布/秒下 32 位 17.8 天回绕，
E71（记账 key 的条目数与宽度）的宽度算术要按此重算）；
记账条目的**跨发布合并不再可行**（代进了 key）⇒ E54（记账的「代」要保留几代）
的每代「统计量数 × 2」次写是实付值，不是上界。

**它为什么必须存在**（用户定案「需要代」的机制理由）：**根可以回退，账必须跟着回退。**
D22（单元原子性怎么合成） 的根环保留最近若干代根，恢复时可能挂上上一代的根；
若账没有「代」这一维、只有一份就地覆盖的最新值，
**挂上旧根之后账是新的、树是旧的** ⇒ I-3.1（已分配统计对得上） 当场判红，
而那不是 bug，是设计漏了这一维。

##### E54（记账的「代」要保留几代） 把原来那个二选一取消了

此前本项写作「甲（代 = checkpoint 号，不丢）／丙（只留最近 K 代）」二选一。
**实测：甲加一条增量丢弃规则与丙在 60 个格上逐格相同**
⇒ **「代取什么」与「留几代」是两个正交问题**，不是一个二选一。

| | key 数（64 个统计量、100 万 checkpoint） | 对 checkpoint 数的斜率 |
|---|---|---|
| 不丢 | **64 000 000** | **= 统计量数** |
| 保留最近 K = 8 代 | **512** | **0** |

**丢弃满足 `.claude/rules/fs-design.md` 第一格**：要丢的那一代**算得出来**（当前代 − K），
**不用找** ⇒ 是点删不是扫描；触及的 key 数 = **统计量数**，
**与 checkpoint 数无关、与盘容量无关**。代价是每 checkpoint 的记账写次数从
`统计量数` 变成 `统计量数 × 2`（一写一删）。

| 口径 | 回退深度 | K 下界 | 64 个统计量下的 key 数 |
|---|---|---|---|
| E53（丢一整块盘之后根环还挂不挂得上） **真设备实测**的最坏回退 | 1 | **2** | 128 |
| 保守：根环槽总数 N（任何幸存槽都可能被选中）| N | **N + 1** | N=8 时 576 |

⇒ **K = 根环槽总数 + 1**（保守口径）。⚠️ **N 由 D22（单元原子性怎么合成） 已定项 2 定**，

⚠️ **K 下界那张表里的 128 / 576 是按 64 个统计量算的示例，不是预测**——
