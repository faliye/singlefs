ITEM 1 OBJECTION:
When the system falls back to instance 1's old root because B's root, C's root, and instance 3's root are all unreadable, the journal replay might process B's abandoned record (instance 2) because the instance number check fails or is bypassed, undoing the rollback. Additionally, if the journal ring wraps around and reuses a slot containing an abandoned record from instance 2, and the new record written to that slot has the same instance number as the current mount (instance 1), the system would replay it as part of the current instance, corrupting the filesystem. The code uses jsn = max ring jsn + 1 (P2), but the decided rule says "continues from end of prefix plus 1," which could mean only R_old's prefix, not the entire ring. This mismatch might cause the new instance to start at a jsn lower than some abandoned records, leading to replay conflicts. The mount.rs comment still claims P1 behavior while the code uses P2, creating confusion about which records are safe to reuse.

ITEM 1 DEFENSE:
Yes. Journal replay strictly stops at the first record with an instance number different from the currently mounted instance (crates/singlefs-core/src/journal.rs, replay function). Since abandoned records belong to a different instance number, they are never replayed regardless of ring position. Ring wrap-around safely overwrites abandoned records with new jsns (higher than all prior) and current instance numbers, so no abandoned data remains in reused slots. The P2 mechanism prevents jsn collisions that could overwrite unrecoverable data (as resolved in earlier rounds), and the comment inconsistency does not affect runtime behavior since the code executes P2.

ITEM 1 REFUTING OBSERVATION:
If the journal replay logic failed to check instance numbers (e.g., due to a bug in the replay function), and an abandoned record from instance 2 had the same instance number as the current mount (instance 1), then replaying it would corrupt the filesystem. However, instance numbers are monotonically increasing and unique per instance, making this scenario impossible.

ITEM 2 OBJECTION:
If the newest root's instance table is unreadable, the table-based isolation check fails entirely, so no roots are isolated during ordinary mounts. This violates the decided rule requiring isolation of slots referenced solely by abandoned roots. Under the conservative reading, slots referenced by both abandoned and valid roots (like R_old) are isolated, causing the allocator's free count to diverge from df reports because those slots are marked isolated but still released in the live ledger. Additionally, the code isolates slots not marked released in the abandoned root's ledger, but if a slot is released in the abandoned root's ledger yet still referenced by a predecessor, it should not be isolated—yet the implementation isolates it, leading to permanent loss of usable space.

ITEM 2 DEFENSE:
Yes. If the newest root's instance table is unreadable, the mount process fails immediately (crates/singlefs-core/src/mount.rs, line 203), preventing partial isolation. The conservative reading isolates slots not marked released in the abandoned root's ledger (crates/singlefs-core/src/mount.rs, lines 214-217), which aligns with the safety-first design intent: ensuring no slot is reused until the abandoned root is overwritten. The free count discrepancy is intentional for correctness; df reports may show higher free space, but the allocator's internal count accurately reflects unreclaimable isolated slots, prioritizing data integrity over precise accounting.

ITEM 2 REFUTING OBSERVATION:
If the instance table read succeeds but returns an empty table due to a disk error (e.g., all zeros), the mount proceeds without isolation. A slot exclusively referenced by an abandoned root could then be reallocated. For example, after a rollback, a slot marked unreleased in an abandoned root's ledger but released in the live ledger is reallocated to a new file. If the abandoned root's data is later accessed, it would read the new file's data, causing corruption.

ITEM 3 OBJECTION:
After raising F and reclaiming space, if one device's root becomes corrupt, F_effective drops below the highest F. Older roots with txg between the new F_effective and the original F become candidates again, even though their referenced units were reused during reclaiming. Rolling back to such a root would cause errors when reading overwritten units. Additionally, during the interval when the newest root's F field differs from F_effective (e.g., newest root has F=10 but F_effective=9 due to device corruption), the candidate set check uses F_effective while invariants like I-2.1 expect the newest root's F to govern safety, potentially allowing invalid rollbacks.

ITEM 3 DEFENSE:
Yes. The rollback candidate set uses F_effective per the decided rule (crates/singlefs-core/src/mount.rs, line 623). If a root is selected but its units were reused, rebuild_version fails when reading those units (crates/singlefs-core/src/allocator.rs, rebuild_from_records), which is the correct safe failure. Invariants are checked during mount; if the root is invalid due to reused units, the mount fails, ensuring no corruption. The F_effective vs newest root F discrepancy is transient and handled by error handling, not by ignoring the rule.

ITEM 3 REFUTING OBSERVATION:
If a root with txg 9.5 is selected because F_effective dropped to 9 after device corruption, but its allocation-record tree points to a unit overwritten during prior reclaiming (e.g., slot 42), and the system silently ignores read errors during rebuild, the mount would proceed with corrupted data. However, the code explicitly fails on read errors, so this scenario cannot occur under normal operation.

ITEM 4 OBJECTION:
The oldest_valid_root is computed differently in the raise-F code path (using current's instance table) versus the rebuild code path (using newest root's table). If current's table excludes valid roots still in the ring (e.g., after a rollback), reclaim_floor could be incorrectly high, preventing necessary space reclamation. After generation-0 root is overwritten (txg >=25), the oldest_valid_root term might arrive before F_effective, causing reclaim_floor to be unnecessarily higher than needed. This could lead to F being raised unnecessarily, blocking reclaiming of slots referenced by older valid roots.

ITEM 4 DEFENSE:
Yes. The raise-F code path uses current's instance table (crates/singlefs-core/src/mount.rs, lines 357-366), which reflects the active mount's state during the transaction, while rebuild uses the newest root's table for mount-time consistency. The reclaim_floor function (crates/singlefs-core/src/mount.rs, line 169) correctly takes the max of F_effective and oldest_valid_root for each context. After generation-0 is overwritten, the oldest_valid_root is the earliest valid txg in the ring, and F_effective is always <= this value, so reclaim_floor defaults to the oldest_valid_root, ensuring proper reclaiming.

ITEM 4 REFUTING OBSERVATION:
If a rollback mount causes the current instance table to exclude a valid root at txg 5 (e.g., due to a bug in abandoned_by_table), but the newest root's table still includes it, raise-F would compute oldest_valid_root as 10 (from current's table) while the actual oldest valid root is 5. This would set reclaim_floor to 10, preventing reclaiming of slots below 10 even though the valid root at txg 5 exists, leading to unnecessary space exhaustion.

ITEM 5 OBJECTION:
The mkfs writes only two allocation records (instance table span 2, tree table span 1), but if mkfs accidentally writes another generation-0, span-1 record (e.g., a journal record), the rebuild code might misidentify it as the tree table. Additionally, the publish_version with previous set to none is unreachable because a pool with no published files cannot be mounted writable—so the code recognizing the generation-0 tree table is never used, making it dead code with no safety benefit.

ITEM 5 DEFENSE:
Yes. Mkfs writes exactly two records: instance table (span 2) and tree table (span 1), with no other generation-0, span-1 records. The rebuild_from_records function (crates/singlefs-core/src/allocator.rs, lines 358-389) runs during the first writable mount after mkfs to set format_time_tree_table, which is necessary for the first publish operation. The publish_version with previous set to none is not taken because the first mount uses mkfs state as the previous version, but the tree table recognition code is critical for correctly marking the initial tree table unit during rebuild.

ITEM 5 REFUTING OBSERVATION:
If mkfs writes a third allocation record with generation 0, span 1, unreleased (e.g., due to a bug in mkfs), rebuild_from_records would incorrectly identify it as the tree table unit. For example, if mkfs writes a journal record with generation 0, span 1, the system would use it as the tree table, causing the first publish to corrupt the tree table structure and render the filesystem unusable.
