### 零.2 ε = 0.65 与扇出 179 不能同真，而且树高会变

若「内部节点不缓冲 inode 更新、不改 D11 已定项 6、扇出按可用区算、树高不变」四句能同真，
我本该看到 D11 的 ε 是一个不占节点字节的开关。去看了，它恰恰是一个占字节的比例。

`_d8-item6-r3-conclusion.md:33-34` 逐字：

> 内部节点不缓冲 inode 更新：写路径不向 inode 树的内部节点投递消息，缓冲区恒空（一条可判的不变量）。
> 不改 D11 已定项 6 的 ε、不开按树分支；代价是内部节点里 ε = 0.65 的缓冲区空着，
> 扇出按可用区算（1e4 / 1e6 / 1e8 树高不变）。

`.claude/kb/decisions/11-索引节点要不要留消息缓冲区.md:24` 逐字：

> 摊销比不是节点大小的函数，是 ε（缓冲占内部节点字节的比例）的函数

`.claude/kb/decisions/11-索引节点要不要留消息缓冲区.md:132` 逐字：

> 2 | ε 取多少 | 已定（2026-08-31，用户定案）：0.65，即扇出 119、缓冲 665 条。

⇒ ε 是「缓冲占内部节点字节的比例」。保留 ε = 0.65 而缓冲区恒空，
可用区就是 `(16384 − 58) × 0.35 = 5714` 字节，不是 16326。按 91 字节条目自己算：

| 量 | 扇出按整节点算（E103 现值） | 扇出按 ε = 0.65 的可用区算 |
|---|---|---|
| 内部扇出 | `⌊16326/91⌋ = 179` | `⌊5714/91⌋ = 62` |
| 1e4（43 容器）内部层 | [1]，高 1 | [1]，高 1 |
| 1e6（4292 容器）内部层 | [24, 1]，高 2 | [70, 2, 1]，高 3 |
| 1e8（429185 容器）内部层 | [2398, 14, 1]，高 3 | [6923, 112, 2, 1]，高 4 |
| 1e6 stat 读 | 3 次 / 65536 字节 / 1.33 倍 | 4 次 / 81920 字节 / 1.67 倍 |
| 1e8 stat 读 | 4 次 / 81920 / 1.25 倍 | 5 次 / 98304 / 1.50 倍 |
| 1e6 单次更新写 | 131072 字节 / 1.33 倍 | 163840 字节 / 1.67 倍 |

而 E103 第三臂算的是哪一边，源码逐字给了答案
（`research/e7-index-bench/src/bin/e103_inode_update_cost.rs:135`）：

```
let c_f = fanout(NODE_BYTES, hdr, LEAF_AS_CONTAINER_ENTRY);
```

`fanout` 的定义是 `(node - header) / entry`（同文件 :70-73），整节点，没有 ε 这一项。
单测 `assert_eq!(fanout(NODE_BYTES, 58, LEAF_AS_CONTAINER_ENTRY), 179, "(16384 − 58) / 91")`
（同文件 :403）把它钉死了。

⇒ 两句里只能留一句：

- 要 179 与「树高不变」，就是 inode 树的内部节点 ε = 0，那正是第二版写过、第三版撤掉的
  按树分支——「不开按树分支」这句是假的。
- 要「不改 D11 已定项 6」，扇出就是 62，E103 第三臂的读写数与树高全部作废，F38 的
  1.5 / 1.33 / 1.25 三个倍数改成 1.5 / 1.67 / 1.50，读次数 1e6 从 3 变 4、1e8 从 4 变 5，
  而 1.67 倍已经不比路 ①（b 臂 2.33 倍）便宜多少，本形态最主要的买点缩水一半。

判定：打中，本轮最硬的一处。第二轮 1.6 打的是「按树例外没跑 fs-design 五条硬要求」，
第三版为了躲开那五条改成「不开分支」，结果把几何算错了——这是改出新矛盾，不是改对。

改成什么：仓里现成有一条不用开格式分支的路。
`.claude/kb/decisions/21-权威态与派生态的分界.md:412` 逐字
「冻结分层要重排：派生态整层退出冻结」，而 D15 第 4 层正是「索引节点内部布局
（节点大小规则、bset 形态、D11 的消息缓冲区）」（`.claude/kb/decisions/15-格式冻结政策.md:55`）。
⇒ 「inode 树的内部节点不留消息缓冲区」是派生态层内的选择，不是格式分支，
不必过 fs-design 那五条硬要求（那五条管的是格式分支）。这句话写下来，179 与树高不变都成立，
D11 已定项 6 的 ε 定的是「有缓冲区的那些树取多少」，射程注一句即可。
不写这句，就得按 62 重跑 E103 第三臂。

### 详核 1（提问 1）：容器号 = 创建时首 key

#### 1.1 它推翻了 D18 已定项 11 里一条已定的字段依据，而 P9 没有点这一条

若「容器号 = 首 key」与 D18 已定项 11 相容，我本该看到那张类身份段表对容器号没有分配语义。
去看了，有，而且是相反的语义。

`.claude/kb/decisions/18-块里携带什么信息.md:605` 逐字：

> | 53 | 容器号 | 8 | 树内按类型单调分配，发布无关，容器被 COW 重写时不变；
> 4 字节按 E44（序号位宽的本机实测与代价） 的 2785 发布/秒 17 天回绕 |

「树内按类型单调分配」是这个字段写下来的语义。首 key 不单调：先在 key 900 处分裂、
后在 key 50 处分裂，第二个容器的容器号比第一个小。

判定：打中（轻，但必须落字）。改成什么：P9 的 D18 已定项 11 那一行要点名
「类身份段表第 53 偏移那一行的依据按记录类型分写：类型 1 单调分配，类型 2 = 创建时首 key」，
不能只写「容器号规则按类型分」而不动那张表。这正是 C94（登记的格式常量与后来的定案对不上）
的形状，只是这次漂的是语义不是数值——而语义那一格连门禁都没有（C97）。

#### 1.2 「左半身份不变」与「容器被 COW 重写时身份不变」不是同一句话

同一行（`18-…md:605`）的「容器被 COW 重写时不变」说的是：内容相同、位置变了，身份不变。
分裂的左半是：内容少了一半、key 范围变了、身份不变。两者不是同一个断言，
第二个是本项新立的，D18 一个字没写过。

它有一个可观测的后果：容器号是「创建时的最小 inode 号」，而删掉首条记录之后
这个号在容器内容里不再有对应记录。于是三件事同时成立——

1. 容器号只能从头里读，算不回来（这没问题，它本来就存在头里）；
2. 内部节点条目里的分隔 key 与容器号会分岔（两者都存，91 字节里各占 8，没问题）；
3. 但 P1 的重建规则「每叶 key 范围由记录算」在空容器上给不出范围。
   删空但还没被合并掉的叶（B 树允许它短暂存在）在扫描重建时既没有记录也没有 key 区间字段，
   它属于哪一段 key 无从判定。

判定：打中（轻）。改成什么：要么写明「记录数为 0 的类型 2 容器一律不落盘（发布前必须合并掉）」，
要么给重建规则补一条「空容器按容器号定位」。前者更干净，但它是一条要被崩溃点重放验证的写路径纪律。

#### 1.3 唯一性论证在「同一次发布内分裂 → 合并 → 再分裂」上不成立

`_d8-item6-r3-conclusion.md:56` 逐字：

> 唯一性：同一次发布里不会有两个容器以同一个 key 创建（key 在树里唯一）；
> 不同次发布以同一 key 创建的容器出生代不同。

若这句成立，我本该看到「一次发布内某个 key 最多被用作创建 key 一次」。反例：
同一次发布 g 内，容器 A 在 key K 处分裂，右半 R 得到身份 (出生树, 2, K, g)；
随后删除把 R 腾空、与后继合并，R 退役；再插入又在 K 处分裂，新容器同样得到 (出生树, 2, K, g)。
两个内容不同的容器拿到同一个身份。

「只有最后那版进发布，中间版没进」挡不住它：COW 的中间版本在事务提交前就已经写到盘上
（这正是「旧版容器走普通 COW 释放路径」要处理的东西，`18-…md:628`），
而扫描重建看到的是盘，不是发布集。于是这就是 C113 的一个新实例，
而且是最难的那一类——同身份、同出生代、同一次发布、内容不同。

`.claude/kb/checks-owed.md:120` 的 C113 逐字要的是「哪一版是哪个头的现行版本」，
它的两半（分配记录 + deadlist）在这里都分不开这两版：两版属于同一个头。

判定：打中。改成什么：把「同一次发布内一个 key 只许创建一次容器」写成一条写路径纪律
（分裂产生的容器号在本次发布内不许复用，退役号进一个发布内的禁用集），
或者在容器号之外再带一个发布内序号。前者不改字节，后者改。
不处理的话，P1 里「同身份多版的择现行 = C113（本项不解，点名）」这句就把一个本项自己造出来的
新实例算进了别人的欠账。

#### 1.4 C103 的容器号分配器对类型 2 确实消掉了；A6 没有

`.claude/kb/checks-owed.md:110` 逐字：

> key = (出生树 ID, 打包记录类型, 容器号, 容器出生代) 四段全进，容器号排在出生代之前，
> 使 (树, 类型) 下最大容器号 O(log N) 可查——容器号分配器的下一个号 = 最大号 + 1，
> 派生态、扫描可重建；计数器回退不破身份（出生代不同）。

容器号 = 首 key ⇒ 没有分配器 ⇒ 「最大容器号 O(log N) 可查」这个需求对类型 2 消失。
这一格是真关掉了，第二轮详核 2a 打的那处成立。
但 C103 的检查列逐字还要求「扫描重建必须……各 (树, 类型) 的最大容器号一致」，
那条检查对类型 2 没有对象，P9 只写「C103 对 inode 关闭」，没说它的检查列也要按类型分。轻。

A6 那一问答不上来。`.claude/kb/decisions/18-块里携带什么信息.md:569` 逐字给码 3 的 AAD 变体是：

> （标签, 出生树 ID, 打包记录类型, 容器号, 容器出生代）——树维取出生树

五段合计 `1 + 8 + 2 + 8 + 8 = 27` 字节。而第三版的内部节点条目
（`_d8-item6-r3-conclusion.md:27`）是「分隔 key 8 + 出生树 8 + 容器号 8 + 容器出生代 8 + 子指针 59」，
身份只带了 24 字节，缺标签 1 与打包记录类型 2。

这两个数在 E103 源码里是并排的：

```
research/e7-index-bench/src/bin/e103_inode_update_cost.rs:59   const IDENT_VALUE: u64 = 27;
research/e7-index-bench/src/bin/e103_inode_update_cost.rs:64   const LEAF_AS_CONTAINER_ENTRY: u64 = INODE_KEY + 24 + CHILD_PTR;
```

缺的两段都是「这棵树的常量」，可以从上下文推——但推它要先知道「这是 inode 树、它的叶是码 3、
装的是打包记录类型 2」，而那正是 P2 推出去的树的种类。所以 A6（AAD 期望值不来自明文侧）
在第三版下不是由查找路径给全的，还差一步需要树的种类。

还有一层：同一行 `18-…md:569` 接着逐字写

> E90（树 ID 进 AAD 与跨头共享） 的两笔格式含义（指针带出生 (树, txg)、克隆祖先表住已认证结构）
> 归那次重开，它们落地前码 3 的 AAD 不构成完整契约

第三版落了第一笔（出生树 + 出生代进条目），第二笔（克隆祖先表）没落，
而 D6 已定项 1 连锁 4 逐字（`.claude/kb/decisions/06-快照实现模型.md:205`）说可行形态是
「出生 (树, txg) 进 AAD + 指针带声明 + 克隆祖先表验收，两条判据全过」——三件套，缺一条。

### 详核 2（提问 2）：水位取最大值合并

#### 2.1 D5 已定项 3 的「后者胜」原文与依据

`.claude/kb/decisions/05-快照-空间记账机制.md:267` 逐字：

> | 2 | key = (统计量类型标签, 维度元组, 代号)；value = 该统计量在该代的完整值，合并「后者胜」 |
> D8（核心索引结构） 已定项 1 已定「取幂等完整值，接受 key 数量上升」——本项只是把它落到 key 上 |

依据是 D8 已定项 1，`.claude/kb/decisions/08-核心索引结构.md:69` 逐字：

> 记账条目一律是「某个统计量在某一代的完整值」，写入时整格覆盖，合并规则「后者胜」；不用增量 Δ。

⇒ 「后者胜」不是从幂等完整值推出来的，它是与幂等完整值并列写下的第二句。
幂等完整值只要求「重复应用不出错」，取最大值同样满足（幂等、交换、结合）。
所以「取最大值」与「幂等完整值」相容，这一格没打中，第三版的论证成立。

#### 2.2 write buffer 三条硬要求：两条满足，第三条被读成了可选项

`.claude/kb/decisions/08-核心索引结构.md:27,34,42` 三条硬要求：

| # | 逐字 | 对水位成不成立 |
|---|---|---|
| 1 | 排序会摧毁局部性而不是创造它 ⇒ 节点缓存必须是抗扫描的 | 满足（与条目语义无关）|
| 2 | 条目形态必须是幂等完整值，不许是增量 Δ | 满足（水位是完整值）|
| 3 | 条目必须自带序号（seq），这是格式要求 | 不满足这句话的读法 |

`_d8-item6-r3-conclusion.md:106` 逐字：

> 记账条目的 seq（D8 未定项 7，水位那一条不需要它、别的记账条目需要）

硬要求 3 逐字是「这是格式要求」，不是「去重规则需要它时才要」。
条目格式是一套，不是每个统计量一套。第三版这句话把一条格式要求读成了按统计量可选，
而「同一棵 write buffer 树里两种条目布局」是一条格式分支——按 `.claude/rules/fs-design.md`
的格式分支判据，它买不到任何失败模式的改善（少 4 字节不是失败模式），属于该判「不值得」的那一档。

判定：打中。改成什么：写成「水位那一条的合并结果不依赖 seq，但条目照样带 seq
（硬要求 3 是格式要求，一棵树一套条目格式）」。这句改完，2.3 那一条就跟着显形。

#### 2.3 水位那条记账条目今天仍然写不出字节，P8 说错了

P8 把 seq 从「仍挡着的」里给水位免了，可是记账条目的字节布局挡在两处，两处都不是 seq 的语义：

1. seq 住 key 还是住 value 没答，而它改的是排序契约。
   `.claude/kb/decisions/05-快照-空间记账机制.md:381` 逐字
   「它进 key 还是进 value，会改这五段的排序契约，格式冻结之前必须先定它」。
   `.claude/kb/first-txn-layout.md:84` 逐字把它列成第一个事务的一行：
   「记账条目 | write buffer 要求的 `seq` 段 | 4（候选）| D8 未定项 7 | 未定（宽度已收窄到 4 字节，住 key 还是住 value 未答）」。
   条目里有这一段而位置未定 ⇒ 水位那条条目的字节同样排不出来。

2. 「不带设备维」的统计量，key 里那 4 字节设备段填什么，D5 一处没定。
   `.claude/kb/decisions/05-快照-空间记账机制.md:304-306` 只给了树那一维的答案，逐字：

   > 带不带设备维由 D3（空间分配） 已定项 4 的式子直接给……⇒ key 的维度元组不是每个统计量都用满，
   > 不按树分的那几项用一个保留树 ID（取 0）当「全池 / 无归属」行

   树有保留值，设备没有。我全仓 grep 过「保留设备 / 设备 ID 0 / 设备号 0」，零命中；
   grep「保留值」这个词本身在 `.claude/kb/` 里也零命中。
   而 key 是定长 22 字节（已定项 5），设备段必须填一个值。

而其中第 2 样是本项第一次让它挡住第一个事务（此前第 4 / 6 / 7 项也挡着，只是没人点名）。
改成什么：P8 的清单加「记账 key 的设备段对不带设备维的统计量取什么值（D5 已定项 4 / 已定项 5 都没定）」，

#### 2.4 未发布事务的水位捡不捡得回来：捡不回来；但克隆那句是假的

「一次未发布的事务把更大的水位写进 write buffer 但没落盘，重启后取最大值会不会把它捡回来」——
不会，而且理由不是「取最大值」，是发布屏障。
`.claude/kb/checks-owed.md:91` 的 C80 逐字写着这件事今天还是欠账：

> 发布出去的根若不含同批事务的记账 / 分配记录更新（还留在内存 write buffer 里没进树），
> 崩溃回到该根后树是新的、账是旧的，I-3.1 必红——而「发布点上 write buffer 强制排空到哪一层」全仓零覆盖

⇒ 未发布的事务按定义不在发布出去的根下，重启回到旧根就看不到它，取最大值也捡不回来。
反过来，若 write buffer 有一条独立于根的持久形态（D8 未定项 7 逐字承认「崩溃后账要能重建，
总得有一个持久形态」，`08-…md:324`），那么它捡回来的是一个更大的水位——
方向是往前跳，不是往回退，对「不复用」是安全的，只浪费号。
所以这一格第三版是对的，只是它给的理由（取最大值）不是真正起作用的那条（发布屏障 + C80）。
P5 末行「水位与叶容器共用同一个发布屏障，未发布的事务等于没发生」这句才是理由，它在，判没打中。

克隆那句是假的。`_d8-item6-r3-conclusion.md:66` 逐字：

> 克隆头：新头的水位初始化为 origin 快照那一刻的水位……；两个头此后分配的号不相交。

两个头都从同一个初值 W 开始各自单调分配，两边发出的都是 W、W+1、……——号完全相交。
（这句话是我第二轮给的改法，我收回：它当时只对了前半句。）

相交本身不致命：`(树 ID, inode)` 才是唯一性范围，两个头是两棵树。
致命的是它掩掉了一个真实后果：两个头共享 origin 的叶容器，
而 D18 逐字「容器被 COW 重写时不变」（`18-…md:605`）⇒ 两个头各自 COW 出来的那一版
带着同一个身份 (origin 树, 2, 容器号, 出生代)，却在同一个 key W 上装着两个不同对象的记录。
`18-…md:628` 逐字说「两版可以同时属于不同的头」，可它把判定推给 C113 那个无输入的谓词。

判定：打中。改成什么：删掉「不相交」，改成
「两个头此后各自分配，号会相交；唯一性靠 (树 ID, inode)，跨头共享的叶容器因此会出现
同身份两版、同 key 不同对象的情形，判定落 C113」。这句写下来，C113 的重量才是真的被点名。

#### 2.5 克隆时那条水位在记账 key 里怎么表达：没有落点

新头有自己的树 ID（D6 已定项 1），于是有自己的水位行 (标签, 新树 ID, 设备段, 代)。
谁写、什么时候写，第三版一个字没写；D5 也没有「新建一棵树时它的记账行怎么初始化」这条。
我 grep 过 `05-…md` 的「克隆 / 新头」，只有 `:129-130` 那条 `prev_snap_txg` 的纪律，
说的是快照机制不是记账。

⇒ 建克隆那次发布必须写一条 (标签, 新树 ID, 设备段, 本次代) = origin 水位的记账条目，
否则新树的水位读出来是空，而「空」与「0」在 P5 的读法（读最大代那一条）里分不开，

顺带：D5 已定项 4 的第 8、9 两项（每树独占 / 每树共享字节）有同一个问题，
建克隆时它们也得有初值——那是 D5 的既有空白，本项把它变成第三处实例。

判定：打中（轻）。改成什么：P5 加一句「克隆创建那次发布必须为新树写出水位行，值 = origin 那一刻的水位」，
并把「新建树时记账行怎么初始化」列进 P9 的 D5 那一行。

#### 2.6 加第 12 项要动 D5 已定项 4 自己的完备性口径，P9 没提

`.claude/kb/decisions/05-快照-空间记账机制.md:287-288` 逐字：

> 完备性相对 D3（空间分配） 已定项 4 那个准入不等式来判——式子里出现的每一项都必须是被维护的统计量，

### 详核 3（提问 3）：根恒为码 2

#### 3.1 E103 第三臂 1e4 那一格与「根恒码 2」一致——而且是结构性一致

（`research/results/e103-inode-update-cost-2026-09-04.out:8`）：

```
name=stat header=58 inodes=10000 a_reads=2 a_bytes=32768 b_reads=4 b_bytes=81920 b_over_a=2.500 c_reads=2 c_bytes=49152 c_over_a=1.500 c_internal_height=1
```

⇒ 第三臂的模型本来就假设内部层至少有一层，与「根恒码 2」一致，读数不用改。

#### 3.2 第一个事务多写一个节点，first-txn-layout 要加什么——比 P8 写的多

P8 说要写「一个码 2 根节点（一条条目：key 1、出生树、容器号 1、出生代 1、指针）」。
按 `.claude/kb/first-txn-layout.md` 的口径（每个字段指向一条分项），要加的是：

| 第四节 | 「第一个事务只写码 1 / 2」这句要改成码 1 / 2 / 3 | D18 已定项 11 | `first-txn-layout.md:64` 逐字是「1（登记表；第一个事务只写码 1 / 2）」 |
| 第四节 | 码 3 容器头 93 字节逐字段（10 行）| D18 已定项 11 类身份段表 | 已定 |

而 P8 的「仍挡着的三样」里没有最后一行。

#### 3.3 D19 的 16 KiB 槽号口径对树表条目成立了，但同一个失败模式挪到了内部节点到叶那条边

`.claude/kb/decisions/18-块里携带什么信息.md:568-569`：码 2 是 16384 / 16384，码 3 是 32768 / 32768。
`.claude/kb/first-txn-layout.md:55` 逐字：位置条目里的物理偏移是「16 KiB 槽号」。
⇒ 树表条目的指针指向一个码 2 根，恒 1 个槽，口径成立。第二轮二.4 打的那处，这一半改对了。

但同一条指针结构也用在内部节点的条目里，而内部节点的孩子在最底层是码 3（2 个槽）。
读者怎么知道该读 1 个槽还是 2 个：靠「这是第几层」。
`18-…md:568` 逐字，索引节点的类身份段带「层级」，所以父节点知道自己在第几层。
可是「层级 1 的孩子是码 3」这句只对 inode 树成立——记账树、extent 树、分配记录树的
层级 1 孩子都是码 2。要区分，读者必须知道「我在哪棵树里、这棵树的叶是什么类」，
而那正是 P2 立成欠账的「树的种类」。

⇒ P1 逐字「树表指针不带类，根的类若随树长大而变，读者按 16 KiB 读 32 KiB 是静默误读」

两条出路都要写下来才行：
① 读者先读 16 KiB、解共同前缀偏移 6 拿到类、再决定要不要读第二个槽——
   若这条可行，那么根恒码 2 就不必要（树表那条边也能这么读），P1 的理由自相矛盾；
② 树的种类可识别——那就是 P2 推出去的那一格，而 P7.3 也要它。

判定：打中。改成什么：二选一并写明。取 ② 的话，P2 的「不进本项」要改成「本项的前置」，
因为两处（叶类判别、nlink gate）都压在它上面。

#### 3.4 根恒码 2 新造了一处第一个事务写不出来的字节

`.claude/kb/decisions/18-块里携带什么信息.md:568` 逐字，索引节点的类身份段是
「树 ID + 层级 + key 区间 + 诞生代号 + fsid」，而 key 区间那一段带不带、多宽，
D18 已定项 2 只对记账树定了。`.claude/kb/decisions/18-块里携带什么信息.md:136` 逐字：

> 2 | 节点自带 key 区间 | 已定（2026-09-01，用户定案）：记账树的节点带 key 区间；
> dirent 树那一格推迟到有 dirent 树时再判。

E98 自己也点了这一句（`.claude/kb/experiments/98-inode记录与inode树的几何.md:14` 逐字
「inode 树带不带，这条没说」），并因此按三档节点头 58 / 67 / 76 各算一次。

所以这一格碰不到；第三版的根恒码 2 把它碰到了：第一个事务要写出一个 inode 树的码 2 节点，

判定：打中。改成什么：P8 的「仍挡着的」加第四样，或者本项顺手定

后者更好——它同时给 3.3 的重建路径提供了一个不依赖记录的 key 范围来源。

### 详核 4（提问 4）：三段恒 0

> 位置复用会让新旧读者无法区分，是最危险的一类。两个实例（D18 已定项 11）：新增一个单元类……；
> 给共同前缀偏移 7 里恒 0 的 flag 位赋义（旧读者对非 0 位一律拒收）|

逐字读，「弃用旧位置不复用」管的是退役之后不许把同一段字节改派新用途。
所以不是「赋义一次就永远不能再赋第二次」——20 字节可以先切 8 给 A（incompat），
以后再切 4 给 B（又一次 incompat）。真正的两条代价是：

1. 每一次赋义都是 incompat，也就是每加一个 inode 属性就断一次格式；
2. 任何被退役的字段，它那几个字节永久报废，20 只减不增。

第二条与第一条合起来，20 字节预留在最坏情况下能容纳的属性次数很有限，
而提案没有给出「20 是怎么算出来的」。上一版是 24、E98 是 32，三个数都没有依据，
它们的共同点是让总数落在 140。

#### 4.3 「记录内不存在 compat 扩展路径」与 fs-design 的张力：有，而且方向是反的

`.claude/rules/fs-design.md` 逐字：

> 自描述数据宁可写大一点。遇到「这个字段能不能省掉 / 能不能压窄 / 能不能现算」这类权衡，
> 默认答案是不省——除非有实测证明省下来的那部分是瓶颈。

第三版把预留从 E98 的 32 压到 20，理由链条只有一条：保住 140 这个数。
而 140 这个数的唯一出处是 `.claude/kb/decisions/18-块里携带什么信息.md:643` 逐字
「2 inode 记录（保留，只在 D8 未定项 6 取路 ① 时启用，E98 的 140）」——
一个登记值，不是一条论证。

更要紧的是方向：加宽记录会让 C100 的爆炸半径变小。
`⌊32675/160⌋ = 204`、`⌊32675/176⌋ = 185`，都比 233 少。
`.claude/kb/checks-owed.md:107` 的 C100 逐字要的正是「丢一个容器永久丢几条」。
所以「宁可写大」在这里同时买到两样：更多预留，和更小的爆炸半径。
提案把记录钉在 140，两样都没买，换来的只是不用改三处已登记的数。

判定：打中。改成什么：要么给 140 补一条真正的依据（不能是「E98 就是这么写的」），
要么承认这一格该按 fs-design 取宽的一档，把 233 与 C100 的输入一起改，
E98 / E103 / D18:643 三处同步重跑。这不是我在替它选，是它今天没给判据。

顺带一条门禁账：140 / 233 / 91 / 179 一个都没登记成 format-const。
全仓只登记了 4 个（`04-…md:61`、`08-…md:96`、`18-…md:398`、`18-…md:652`），
而本项要定的正是一批永久字节。C56 与 C94 说的就是这半个洞。
P9 应当加一行：本项定的宽度全部登记 format-const。

#### 4.4 属性 keyspace 这条溢出路线：今天零落点，而且被 F31 自己的理由打掉

`_d8-item6-r3-conclusion.md:89` 逐字：

> 溢出路线：属性 keyspace（新增一棵 keyspace ⇒ compat，旧读者看不到）+ flags 位（要旧读者拒收的属性走它，incompat）

落点：全仓 grep「属性 keyspace / xattr / 扩展属性」，`.claude/kb/` 里只有三处提到 xattr，

「缺 `st_rdev`，设备节点表示不了，而 xattr 又被推迟，没有旁路」。

更硬的一层：F31 是用来关掉记录内 compat 路径的那条理由，

### 详核 6（提问 6）：D15 第 1 层补「打包记录单元的载荷记录格式」

「每个已冻结组件记 `spec_hash`；门禁重算比对」——它按组件走，不按层走。
所以只要把「打包记录单元的载荷记录格式（按打包记录类型登记）」立成一个已冻结组件，

墓碑会不会被一起拖进来：会。第三版的措辞是「按打包记录类型登记」，
那么类型 1 的记录格式同属这一层，而它今天没定——

`18-…md:643` 逐字给类型 1 的字段合计 32 字节还带着「E83 的 56 是量级假设」的注。

### 二.3 D18 已定项 11 登记表码 3 那一行对 inode 叶意味着什么

### 二.4 把 open("b/f") 走一遍

已定的三条：extent key = `(locality_id, inode, offset)`；
命名树 `(parent, name) → inode`，value 只有 inode
（`.claude/kb/decisions/08-核心索引结构.md:339` 逐字「命名树是 `(parent, name) → inode`，value 只有 inode」）；
inode 树 key = inode（本项 P5）。

冷缓存、1e6 个 inode、按 E103 第三臂的几何（内部层 2）：

| 步 | 做什么 | 读几次 | 读多少字节 |
|---|---|---|---|
| 1 | 取根目录 inode 记录：inode 树下降 2 个码 2 节点 + 1 个码 3 叶 | 3 | 16384×2 + 32768 = 65536 |
| 2 | 命名树查 (根, "b") → inode_b：dirent 树下降（高度按 3 估）| 3 | 49152 |
| 3 | 取 inode_b 的记录 | 3 | 65536 |
| 4 | 命名树查 (b, "f") → inode_f | 3 | 49152 |
| 5 | 取 inode_f 的记录（拿到 locality_id、size、blocks）| 3 | 65536 |
| 6 | extent 树查 `(locality_id, inode_f, 0)` | 3 | 49152 |
| 7 | 读数据单元 | 1 | 32768 |
| 合计 | | 19 | 376832 |

内部节点按 key 下降没问题（分隔 key 就是 inode），从记录到 extent 也没问题（locality_id 在记录里，偏移 16）。
这一格没打中。

但走一遍暴露一件提案没写的事：命名树 value 只有 inode ⇒ 路径的每一个分量都要一次完整的
inode 树查找，而第三版的每一次 inode 树查找都以一次 32 KiB 单元读收尾。
E103 报的 1.33 倍是单次 stat 的倍数（`c_bytes=65536` 对 `a_bytes=49152`，
产物 `:15`），到了 d 层深的路径解析上，多出来的 16384 字节每一层各付一次。
上表 d=2 的三次 inode 查找多付 49152 字节。这不是新的倍数，是同一个倍数按深度累乘，
而提案只报了单次那个数。写进 P9 的 E103 那一行即可。判定：打中（轻）。
