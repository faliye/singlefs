1. An attacker can create a unit where the entire ciphertext section (including the 63-byte header ciphertext, 32768-byte data payload, and 16-byte tag) is set to all zeros. The plaintext header checksum is updated to match the new header (42-byte common prefix plus 63 zero bytes). The tag field is set to zero. When the rebuild path runs, it decrypts the zero ciphertext to all-zero plaintext. The AAD derived from this plaintext is all zeros. The system recomputes the tag as Poly1305(0 || 0) which equals zero. This matches the stored tag of zero, causing the system to accept the unit with all-zero identity fields (tree id 0, object id 0, etc.), which was never written by the system.

2. The attacker can infer file sizes and hole structure from the physical disk positions of data units. For example, contiguous sequences of data units on disk likely belong to the same object. The number of contiguous units multiplied by 32768 bytes gives an estimate of the file size. Gaps between unit sequences indicate holes in the file. The attacker observes physical disk positions without needing the key to decrypt object identifiers.

3. Arm B breaks the promise to detect damage and report bad blocks. The keyless side can check the header checksum (computed over the 105-byte header including plaintext and ciphertext parts) to detect header corruption. However, it cannot verify the payload CRC because the data payload is encrypted and the keyless side lacks the key to decrypt it. Thus, data payload corruption remains undetectable.

4. Arm C reintroduces the leak. The 8-byte grouping tag is a truncated key derivation of the 5-tuple. An attacker can compare grouping tags to determine which units belong to the same object. For example, units with identical grouping tags share the same object id and anchor offset. Since the grouping tag is 8 bytes, collisions are rare but object grouping is directly observable. The attacker learns the object count by counting unique grouping tags and infers object structure from tag matches.

5. The most likely flaw in Arm B is decrypting before verifying the tag, allowing trivial forgeries like the all-zero unit attack. This is revealed when the rebuild path accepts a unit with all-zero ciphertext and tag, despite no valid unit ever having all-zero identity fields. Observing such acceptance confirms the vulnerability.
