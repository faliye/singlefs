# 背景材料：D6（快照实现模型） 未定项 2 第二轮 —— 甲的形态该长什么样

## 0. 这一轮要判什么

第一轮（2026-09-10）判掉了丙与乙、重估了丁，只剩甲（每头一份 livelist）；
E130（每头一份 livelist 过不过有界销毁） 当天验完甲过 D6（快照实现模型） 判据 5。
**剩下的整格是「住哪、条目长什么样、谁维护」，也就是选定形态。**

**主 agent 手上有一个候选，这一轮就是来打它的**：

> **甲′**：一棵**独立 keyspace 的 btree**，key = `(头的树 ID 8, 设备身份 4, 16 KiB 槽号 6)`，
> 条目是**幂等完整值的集合表示**——`key 在 = 这个落点是该头自己出生的活块`，释放就是删 key，
> **不是 ALLOC/FREE 事件流**。走 write buffer，因而条目自带 `seq`。

它靠两条独立的理由推出来，而两条都要被这一轮检验：

**理由一（条款）**：D8（核心索引结构） write buffer 硬要求 2 逐字
「**条目形态必须是幂等完整值，不许是增量 Δ**」，而 D5（快照 / 空间记账机制） 给 livelist 的
形态逐字是「**ALLOC/FREE 配对**」——事件流就是 Δ。

**理由二（实测）**：E130（每头一份 livelist 过不过有界销毁） 量出 Δ 形态（`naive`）在
`n=65536 churn=16` 上条目数 `2162688` 而净活块只有 `65536`、待删占用高估 `17.0000×`；
恒 condense 形态同格逐字 `entries=65536 ... overestimate=1.0000`。
**而「恒 condense 的 livelist」就是幂等完整值的集合表示。**

**附带一条**：key 以头的树 ID 打头 ⇒ 销毁一个头变成**范围操作**，
而 D8（核心索引结构） 已定项 5 正好给了范围重建 vs 逐项修改的判据。

**一套 btree 实现 + 多个独立 keyspace + 两个前端。** 不做异构结构。

### write buffer 的三条硬要求

**1. 排序会摧毁局部性而不是创造它 ⇒ 节点缓存必须是抗扫描的**（E7（离线索引 harness），2026-08-27）。
按叶排序之后每次 flush 就是一次覆盖整个叶子空间的顺序扫描，而 **LRU 对「反复的、
大于缓存的顺序扫描」命中率恰好为 0**——D8（核心索引结构）这一侧在缓存占树 2% / 6% / 25% 三档上的
io/op **逐位相同（1.5755）**。干预证实：保持同叶聚合不变、只打乱组的处理顺序，
25% 缓存档读次数降 9.2%（下界）；100% 缓存档打乱前后完全相同（阴性对照）。
⇒ 缓存策略必须抗扫描（2Q / LRU-K 之类）。**这是硬要求，不是建议。**

**2. 条目形态必须是幂等完整值，不许是增量 Δ**（E14（I-3.1 的判别力：幂等完整值 vs 增量 Δ），2026-08-27）。

增量 Δ 形态下**抓到 0/4**，四类全部把账算错而 I-3.1（已分配统计对得上） 全绿——
机制是 Δ 形态下账本身就是权威内容，checker 只能拿同一个累加函数重放同一份 Δ 日志，**它在和自己比**。

「updates are _deltas_」）。记账那一棵咬得最紧——「释放了 4096 字节」的自然表达就是 Δ，

**3. 条目必须自带序号（seq），这是格式要求**（2026-08-27 起已知，E17（write buffer 合并上限） 逼出可判定形态）。
flush 时按 key 排序**丢弃时间序**，而去重规则是「后者胜」⇒ **「后者」必须由条目自己携带**；

且这个 sort-merge-sweep **本质单线程**，在多线程负载下它的效率是关键路径。

### 已定项 5：whiteout 删除 —— 接受，但批量删除必须走 intent log

删大目录、截断大文件会产生海量墓碑，塞进一个事务必然爆掉。
**做法（bcachefs 已验证的形态）**：凡是**可能修改无界数量 extent** 的操作（truncate、collapse、删大目录），
**先把意图写进 logged_ops 树，再分批推进**；崩溃后恢复时续做未完成的意图。
删除中的 inode 单独进 `deleted_inodes` 树，由后台回收——用户的 `rm` 返回，不等于所有 extent 都已释放。

**硬要求**：无界规模的操作一律不许做成单个事务；意图必须**幂等**；
whiteout 只在节点重写合并 bset 时清除，**不许有别的清除路径**。

意图本身就是一条普通 key，骑在同一个事务层上，断电后只有三种状态：

| 断电时机 | 恢复后看到 | 怎么收场 |
|---|---|---|
| 意图提交之前 | 没有意图 | 操作从未发生，用户那边也没返回成功 |
| 意图已提交、工作做了一半 | 意图还在 | 恢复时**续做**，已做完的部分被幂等地重跑 |
| 工作做完、意图未删 | 意图还在 | 续做一遍发现无事可做，然后删掉意图 |

不可能出现「意图没了但目标状态没达成」——**删除意图必须与最后一批工作在同一个事务里提交**。

1. **意图声明目标状态，绝不声明增量。**「把文件 X 截到 N 字节」可以重复执行，「再删 1000 个 extent」不能。
2. **续做是每次恢复都跑的常规动作，不是修复手段**（否则会出现「平时不跑、真出事时才第一次跑」的代码路径）。
3. **中间状态必须每一个都是合法的文件系统状态**——「删了一半 extent 的文件」本身就得合法。

**范围重建 vs 逐项修改：两条都要有，且要有显式判据**（`.claude/rules/fs-design.md`「不追求万能方案」）：

| 走法 | 代价 | 适用 |
|---|---|---|
| 逐项修改 | K × 随机访问 | 受影响的 key 稀疏散布 |
| 范围重建 | N × 顺序访问 | 受影响的 key 在 key 序上连续 |

朴素的交叉点是 `K/N > 顺序代价/随机代价`（机械盘约 1%、SSD 约 10%）。
⚠️ **第一期只取 SSD 那一档**（D12（目标介质） 已定项 5：第一条布局线是纯 SSD）。
⚠️ 这两个数是**推理，不是实测**，说的是**耗时**，要靠 E4（范围重建 vs 逐项修改的交叉点） 量，那一半要 QEMU。

**写放大那一半已量**（E30（交叉点的写放大那一半），2026-08-29，100 万叶、三轮字节一致）：

| 节点 | 条目连续 | 条目散布 |
|---|---|---|
| 4 KiB | **1000‰**（要全改才划算） | **10‰** |
| 16 KiB | **1000‰** | **3‰** |

⇒ **在写放大口径下，交叉点的自变量是「布局」与「节点大小」，不是介质**，两者相差两个数量级以上。
⚠️ 不能拿它去证伪「机械盘约 1%、SSD 约 10%」——那说的是耗时，E30（交叉点的写放大那一半）对介质一个字没说。

**真正的开关不是 K/N，是「受影响的 key 连不连续」**：连续 ⇒ 范围重建可整节点丢弃或重写；
不连续 ⇒ 只能逐项。**由此得到一条布局规则：让一起死的东西在 key 序上挨在一起。**

- dirent 按 `(parent_inode, name)` 编 key → 删整个目录是范围操作
- extent 按 `(inode, offset)` 编 key → 截断是范围操作
- 同一快照的 key 带同一 snapshot 前缀 → 删快照有机会变成范围操作

**这顺带从结构上解掉了 whiteout 膨胀**：范围删除直接丢弃整个节点，不用插 N 个墓碑。

按 `.claude/rules/fs-design.md` 的五条要求，这个分支还欠：判据写成可计算的式子、
留一个能强制走指定分支的测试开关、两条分支各自跑崩溃点重放、运行时能看出走了哪条。
⚠️ **切换判据里不许出现「当前填充率」这类操作中途会变的量**——判据只能用操作期间稳定的输入。
