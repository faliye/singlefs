## 攻击面一：过度外推与越位（「对拍与复用哨兵抓得到」推不推得出）

### A1 对拍自己按输入复用：判器改了，对拍不重拍

定案的抓法句：「GPU 服务只照数据算，与 CPU 参照一不一致由对拍与复用哨兵抓。」（`.claude/kb/decisions/13-验证路线.md:443`）与「判法改了对不对，靠对拍与复用哨兵抓。录入键（这一份写流录过没有）另立一组判法单元：从场景入口收闭包，只留产品代码与场景（测试代码）的单元，录制管线排出去。」（`.claude/kb/decisions/13-验证路线.md:444`）。

补丁里的对拍：

- 对拍结论入库函数的文档：「/// 对拍结论入库（「对拍结论入库」）：键只是输入摘要（两边判器与比法的代码不进键），库里有两边一致的就复用、不再判；」（补丁副本 crates/singlefs-verification/src/crash_library/pairing_inputs_and_conclusions.rs 第 371 行），复用那一支交回「PairingConclusionSource::ReusedFromTheLibrary,」（同一份第 393 行）。
- 按块对拍：「/// （`verdict_store` 文件头登记的表，不另开表、不另开键空间）：块的输入数据相同的下一趟复用，两边判器与比法的代码不进键。」（补丁副本 crates/singlefs-verification/src/crash_library/pairing_blocks.rs 第 12 行）。
- 对拍用例一处：键是「&pairing_inputs_digest(image, &tables),」（补丁副本 crates/singlefs-verification/tests/crash_judge_gpu_agrees_with_the_cpu_judge_on_the_pending_release_bound.rs 第 294 行），摘要只收基线镜像与判表（同一份第 199 行「"gpu judge deadlist pending release bound pairing inputs\nbase={}\ntables={}\n",」），断言照库里读回的那份结论字做（同一份第 315 行「let judgements = JudgementsOfBothJudgesOnAnImage::from_bytes(&conclusion)」）。主工作区同一份文件此刻还多带两把判器单元键：在 `pairing_inputs_digest(image, &tables)` 后面传 `judging_units(JudgingUnits::GpuJudge)` 与 `judging_units(JudgingUnits::JudgementOfTheGivenStates)`（主工作区该文件第 294–299 行，`sed -n 289,300p` 读的），补丁把这两把删了。
- 补丁副本 `crates/singlefs-verification/src/crash_library/` 整个目录按 `sentinel|哨兵` 不分大小写数，每份文件 0 处（`grep -rnc -i`，退 1）：对拍那几张表没有哨兵、没有强制现判。

构造（推的）：

1. 改 GPU 判器里 I-3.6 那一处（WGSL 判池级 checker 不变量的 `crash_judge_checker*.wgsl` 之一），让它在违例时也不置违例位。
2. 对拍用例 `crash_judge_gpu_agrees_with_the_cpu_judge_on_the_pending_release_bound` 那一份测试函数的复用键照「单测与变异的复用键 照旧：测试闭包引到的产品代码与测试代码」，WGSL 是测试服务代码、不进任何键（`.claude/kb/decisions/13-验证路线.md:443`）：测试函数整条复用。
3. 就算这一条被测试函数那一层的强制现判抽中、整条重跑：它照输入摘要读回库里旧的对拍结论（两边一致、复用），断言做在旧的 GPU 结论字上，照绿。
4. 崩溃块那一边：绿库里没有违例 I-3.6 的状态，强制现判那一块现判出的仍是空向量（见 C1），逐字相同，不红。
5. 结局：本该红（GPU 对一张 I-3.6 违例的镜像判绿，与 CPU 不一致），三样都不抓。只有某天产品代码改到让这张手造镜像的字节或判表变了，对拍才重拍。

为什么抓不到：对拍是「拿判器测判器」，它的输入不变、判器变了，正是它要量的那一格；把它的键缩成输入摘要，等于把判器改动排出了对拍的触发条件。这不是「两边一起改错」，是对拍根本没跑。

四句：分辨臂——分辨（旧方案的对拍键带两边判器单元键，同一改动下对拍重拍、红；新方案不重拍）；被判系统看不看得到——看不到：对拍那一刻能看到的只有输入摘要，两种情形逐条相同，这是「判别子观测不到」；满足的分句——「判法改了对不对，靠对拍与复用哨兵抓」里的「对拍」一半；正文第 2 问给的三个改法在这一格上：「改判定器代码时强制全量重判一次」只重判崩溃块、不碰对拍表，还中；「哨兵按改动过的判法加大抽样」对拍表没有哨兵，还中；「判定器改动提交前必须跑一次不复用的全量对照」要是这份对照包括对拍用例不读 `19` 表，不中，否则还中。

### A2 产品的恢复代码不在崩溃判定的键里，GPU 机上也碰不到它

定案把崩溃判定的键写成「崩溃判定的键只由块的输入数据（产品代码加场景录出来的那一块）组成」（`.claude/kb/decisions/13-验证路线.md:444`），射程里「镜像判定与给定状态判定的块键只由块的输入数据组成，不论这一块在 CPU 还是 GPU 上判的，键相同」（`.claude/kb/decisions/13-验证路线.md:466`）。括号里那句把产品代码只当成「录出块的那一方」。可 CPU 判器自己就跑产品代码：

- `crates/singlefs-verification/src/crash.rs:3`：「每个状态跑恢复、oracle、池级 checker 与记录核对器」；同一份第 18 行从产品包引「    recover, JournalPolicy, PoolReader, RecoveryOutcome, RecoveryReport,」（`crates/singlefs-verification/src/crash.rs:18`）。
- 「let consulted = recover(image, JournalPolicy::Consult);」（`crates/singlefs-verification/src/crash/state_judgement.rs:246`），所在函数是 `judge_crash_image_against_the_version_table`（同一份第 239 行），即 `crash::judge_crash_image` 往下调的那一个。
- 被调的是产品代码：「pub fn recover(reader: &dyn PoolReader, policy: JournalPolicy) -> RecoveryReport {」（`crates/singlefs-core/src/recovery.rs:514`），`singlefs-core` 在三类代码表里是产品代码（`.claude/kb/decisions/13-验证路线.md:450`）。
- 主工作区里这条路是进键的：判定定义那一组的入口登记有「"singlefs_verification::crash::judge_crash_image",」（`crates/singlefs-verification/src/judging_units_entries.rs:85`），按「函数单元从这份判定的入口沿调用与引用收」收到 `recover`（推的：组成清单是构建时现算的，我没读到编出来的那一份）。补丁里三种结论的版本只由种类定（补丁副本 crates/singlefs-verification/src/crash_identity/conclusion_kinds_and_versions.rs 第 69 行起，`b"singlefs conclusion version\nkind=crash image judgement\n"`），这一截没了。
- GPU 那一路判的是 WGSL 另写的恢复（`crates/singlefs-verification/src/crash_judge_recovery.wgsl`），不跑 Rust 的 `recover`；配了 GPU 一律走 GPU（`crates/singlefs-verification/src/crash_state_enumeration.rs:214` 那段写的「配 GPU 必用 GPU、做不到报错不降级」；结论按 GPU 判器那一处取：「Self::Gpu | Self::JudgeNotRunWithoutTheGpuFeature => JudgedBy::GpuJudge,」（`crates/singlefs-verification/src/crash_state_enumeration.rs:231`））。

构造（推的）：改 `crates/singlefs-core/src/recovery.rs` 里只在崩溃态才走到的一支（例：读 journal 时遇到撕裂的最后一条记录，原来丢弃、改成照用），录制时的场景只在新格式化的池上挂载，这一支不走，写流逐字节相同。于是：

1. 块键（写表摘要、起步镜像摘要、块起点）不变，全部复用；结论版本由种类定，也不变。
2. GPU 机上强制现判那一块由 GPU 判，跑的是 WGSL 的恢复，与改动无关，结论逐字相同。只有派到不配 GPU 的那台、强制现判又恰好抽中一个撕裂最后一条记录的块，才看得到。
3. 对拍用例的测试函数键带产品代码（测试闭包够到 CPU 参照那一侧的 `recover`），测试函数重跑；但对拍结论的键只有基线镜像与判表（A1），读回旧结论，CPU 一侧的新 `recover` 没跑。
4. 结局：本该是「恢复改了，全部崩溃态重判；CPU 新恢复与 GPU 旧 WGSL 对拍不一致，红」，实际一条都不重判、对拍不重拍，绿。`.claude/rules/verification.md:82` 那一句「**没跑过这个的写路径就不算验过。**」在恢复路径上落空。

过度外推在哪：用户原话「「因此我们说的代码指纹是 核心代码的指纹 是被检测代码的指纹 不是task-server gpu-server prune-server的指纹」」（`records/2026-11-19-判定键只算产品与测试代码.md:23`）要的是被检测代码进键；定案从「判器是黑盒，不进键」推到「判器闭包整组不进键」，把闭包里的被检测代码（恢复）一起推了出去。用户那句「「gpu对拍，是一个相等的算法。」」（`records/2026-11-19-判定键只算产品与测试代码.md:21`）说的是 GPU 判器，管不到 CPU 判器闭包里的产品恢复。

四句：分辨臂——分辨（旧方案版本键带判定定义那一组，恢复一改全部重判、对拍重拍）；看不看得到——看不到：块键与版本里没有任何东西随恢复代码变；满足的分句——「崩溃判定的键只由块的输入数据（…）组成」字面本身；三个改法：「改判定器代码时强制全量重判一次」——恢复不是判定器代码，不触发，还中；就算触发，GPU 机上全量重判跑 WGSL，仍中；「哨兵加大抽样」同理还中；「不复用的全量对照」若对照是 CPU 对 GPU、且 CPU 侧真跑，不中，代价见 D2。

### A3 「相等的算法」只罩实现等价的改动，罩不到规范改动

用户把对拍说成相等的算法：同样的输入，大于小于、位运算、减法都该得出同样的输出（`records/2026-11-19-判定键只算产品与测试代码.md:21`）。这句对「同一规范的另一种实现」成立。可本仓的规范就是池级 checker：「**「这个格式到底是什么」，答案以 checker 的源码为准，不是文档。**」（`.claude/rules/verification.md:90`）。给 checker 加一条不变量、修一处漏判，是规范变了，不是实现换了；同一份输入的正确输出本来就该变。定案「改判器不作废已判的块」对这一类改动的结局（推的）：

- 已判绿的块全部复用；新不变量只落在之后新录的块上（产品代码或场景改到、写流变了的那几条流）。
- 一条新不变量在旧数据上本该红的块数 k、这条流库里不红的块数 N，每趟这条流被强制现判抽中的概率 k/N（见 A4）。块宽是「pub const STATES_PER_BLOCK: u64 = 1 << 16;」（`crates/singlefs-verification/src/crash_amplification/crash_point_plan.rs:7`）；已定项 17 依据里有「只差名字的块各存各判 4100 块与 9679 块」的盘上数，拿它当 N 的量级，k=1 时每趟约 1/4100 到 1/9679（推的，N 没按流现量）。
- 这一格只在 GPU 也同步加了这条不变量时才有 k/N；只改了 CPU checker、WGSL 没跟的，GPU 机上强制现判跑的是 WGSL，k/N 变成 0（A2 第 2 步同一个理由）。

四句：分辨臂——分辨（旧方案判定定义那一组进版本键，checker 一改全部重判）；看不看得到——判段那一刻看得到的只有块键与版本，两种情形逐条相同；分句——「改判器不作废已判的块」；改法：「强制全量重判一次」不中（若触发得了，见 B4）；「加大抽样」每趟 m 块时概率 1-(1-k/N)^m，m 到 N 的量级才不中；「全量对照」不中。

### A4 「复用哨兵」对判器改动的判别力只剩一块强制现判

规则句：「- 每一趟真跑开跑前从键相同、库里有判定的项里随机抽几条当哨兵、再抽一条强制现判」（`.claude/rules/verification.md:41`）。实现里两样各判什么：

- 哨兵（缺省「pub const DEFAULT_REUSE_SENTINEL_COUNT: usize = 3;」，`crates/singlefs-verification/src/crash_amplification/reuse_sentinels.rs:16`）只判「键相同却被现判了」：报的那一句是「复用失灵：哨兵块 {}（点 {} 的 [{}, {})，块键 {}）键相同、库里有不红的结论，这一趟却现判了」（`crates/singlefs-verification/src/crash_amplification/reuse_sentinels.rs:604`）。它抓的是复用坏了，与判器改了无关，判别力为零。
- 真正比结论的是强制现判，每趟每条流一块：「// 强制现判照同一串数接着从剩下的里抽一块。」（`crates/singlefs-verification/src/crash_amplification/reuse_sentinels.rs:430`），比不上就报「判法依赖了键之外的输入」（`crates/singlefs-verification/src/crash_amplification/reuse_sentinels.rs:644`）。新方案下判器代码整个就是「键之外的输入」，这块强制现判是唯一的判器改动探测器。
- 候选只取库里不红的块（`plan_the_reuse_sentinels` 文档里「库里有不红结论的块」），归这台机器的才算（打印行 `candidates=` 的说明，`crates/singlefs-verification/src/crash_amplification/reuse_sentinels.rs:18`）。

所以「对拍与复用哨兵抓」在判器改动这件事上实际是「对拍（A1 让它复用）＋ 每条流每趟 1/N 的抽样」。推不出「抓得到」：要抓到一处只影响 k 块的改动，期望要跑 N/k 趟；第 1 问里「强制现判只抽一条」这一条在实现里成立。

## 攻击面二：内部矛盾与循环依赖

### B1 录入键：命中就跳过的那一段，正是被排出键的那一段

录入段的次序（`crates/singlefs-verification/src/crash_state_enumeration/flow_through_the_library.rs`）：先在场景跑完之后算流的字节「let recorded_bytes = flow_to_record.recorded_bytes();」（第 21 行），录入键在它之后算「let recording_key_of_this_run = recording_key_of_the_inputs(&inputs);」（第 37 行），键没命中才走「let manifest = flow_to_record.record_into(library, gpu_judges, &recorded_bytes)?;」（第 46 行）。输入摘要的说明：「/// 录入键的输入那一半：录进库的那一份流的字节与判表开不开」（`crates/singlefs-verification/src/crash_state_enumeration.rs:273`）；`record_into` 做的是「/// 录入段：排计划、写录入表与路径索引、把流写进库（配了 GPU 再把打包判表写进库），交回清单。」（`crates/singlefs-verification/src/crash_state_enumeration.rs:282`）。

推出两件事：

1. 产品代码与场景改了、写流跟着变的，流字节变、输入摘要就变，键自然换；写流没变的，产品与场景的指纹再变也只让一份相同的流重录一遍。录入键里「产品代码 + 场景」那一半对正确性是重复的，只多出重录。
2. 键命中时跳过的是 `record_into`：事实表、打包判表这些「从流算出来、存进库、判段照它判」的产物。主工作区录入那一组的入口登记恰是它们：「        group_name: "recording",」（`crates/singlefs-verification/src/judging_units_entries.rs:120`）下有「"singlefs_verification::crash_facts::extract_flow_facts_with_slices",」（第 123 行）、`build_judge_tables_against_the_version_table_with_slices`（第 125 行）、`PackedJudgeTables::of`（第 128 行）。`crates/singlefs-verification/src/crash_facts.rs:14` 也写着事实表按录入键存、「函数在录入那一组的入口里）」。

新录入键（「录入键在 `singlefs-unit-graph` 加按包过滤的口子」，`records/2026-11-19-判定键只算产品与测试代码.md:96`）把这几样排出去。构造（推的）：

- 改 `crates/singlefs-verification/src/crash_facts.rs` 的抽取：事实表决定「哪几次写取三态、撕裂镜像与重放接在枚举写表的哪里」（`crates/singlefs-verification/src/crash_facts.rs:5`）与「每一段展开出几个状态」（同一份第 6 行），判表照它算持久集合（`crates/singlefs-verification/src/crash_judge_tables.rs:46` 引 `persisted_writes_of_state_by_the_segment_expansions`）。修一处漏认的原地覆写（该多一态「新旧都读不出」），流字节不变 → 录入键命中 → `record_into` 不跑 → 库里旧事实表、旧打包判表照用 → 判段在旧的状态域上判 → 新多出来的状态一个都没判，绿。
- 复用哨兵碰不到：强制现判重判的是同一份旧判表上的一块；录入段没有哨兵（补丁副本 `crash_library/` 目录 0 处，见 A1）。
- 这是本该红而绿：崩溃态域漏了一类，违了共用约束「崩溃点测试准确率和正确率优先」，也违了 `.claude/rules/verification.md:82` 那一句。

与用户原话的关系：「「数据和怎么录入没有关系吧。 我怎么想都不应该产生关系。」」（`records/2026-11-19-判定键只算产品与测试代码.md:92`）对「流字节」成立（录制器怎么写，最后都在字节里）；对「从流算出来的库里产物」不成立——那几样的内容就是录制管线代码的输出。定案把两样都叫「录入」，于是一起排了出去。

同一份已定项里的矛盾：「键过窄（引用的常量、类型、宏漏收）、库放在会丢的位置、改名丢库、两份库重复判同一批，同样算违反。」（`.claude/kb/decisions/13-验证路线.md:436`）。录入键下存的事实表与判表内容依赖抽取与打包代码，而键不收它们，按这一句就是键过窄。

四句：分辨臂——分辨（主工作区的录入组收了这几样，改抽取会重录）；看不看得到——看不到：录入段判命中那一刻手里只有流字节与产品、场景指纹；分句——「录制管线排出去」；改法：「改判定器代码时强制全量重判」——重判不重录，判表仍旧，还中；「加大抽样」还中；「不复用的全量对照」若不经录入键现录，不中。

### B2 「按包过滤」分不开场景与录制管线

记录第 96 行要录入键「只留产品包与场景的单元」、把「判器、观察者、录制管线与三个测试服务 crate 的单元按包排出」。可场景之外这几样多数和场景在同一个包：录制器「pub struct RecordingBlockDevice<Inner: BlockDevice> {」在验证包的库根（`crates/singlefs-verification/src/lib.rs:381`），事实抽取 `crash_facts.rs`、判表 `crash_judge_tables.rs`、观察者、CPU 判段都在 `crates/singlefs-verification/src/`，崩溃枚举用例在同一个包的 `tests/`（53 份 `crash_enumeration_*`，`ls | grep -c` 数的）。按包只有两种切法：

- 留下 `singlefs-verification` 的库：录制管线、记录核对器、观察者整包回到键里，违「排出去」。
- 去掉它，只留用例所在的测试目标：场景用的库里脚手架（内存池、历史生成、`build_pool` 一族）也出去。因为流字节已在输入摘要里（B1 第 1 条），这一半不出错；但 B1 第 2 条那几样照样不在键里。

所以「按包过滤」要么做不到用户说的排除，要么只做到 B1 的漏洞。补丁的实现员报告自己也停在这里（设计问题 2，报告 `/home/fy5090/.local/share/singlefs/work/judging-keys-input-data-only/result.md`，转述）。

### B3 判定项标识当键，与已定项 17 自己的三句撞

记录第 96 行：「同一块上的几个观察者在结论的键里用判定项标识分开（键 = 块的输入数据 + 判定项标识），观察者的代码不进键」（`records/2026-11-19-判定键只算产品与测试代码.md:96`），并且「判定项标识照旧、不拆表（「判定项的标识根本不用改很多。以前的标识一样的用。删掉判断器的指纹相关就好了」）」（`records/2026-11-19-判定键只算产品与测试代码.md:24`）。同一份已定项里：

1. 「手写的版本常量；路径（仓根也算）、名字、种子串、行号、资源上限、限时」一律不进键（`.claude/kb/decisions/13-验证路线.md:436`）。判定项标识要么是名字（观察者名），要么是一个登记号——它要在观察者判法的意思变了时换，那就是手写的版本常量。两种都在禁列里。
2. 「改名丢库」算违反（同一行）。标识取名字时，按 `.claude/kb/term-renames.md` 改一次名，这个观察者的全部结论就丢了。
3. 不换号时（第 4 问）：观察者判法意思变了、标识没换，旧结论照复用，就是第 1 问那一类；强制现判那一块会连观察者结论一起现判、一起比（「也没被现判，强制现判那一块连这几份一起现判、一起比。」，`crates/singlefs-verification/src/crash_amplification/reuse_sentinels.rs:34`），概率同样是每趟每流 1/N。

谁判、怎么钉住：今天没有任何判据说「意思变了」；能机械判的只有「代码变了」，而代码指纹不许进键。所以「判法意思变时换号」落不成门禁，按 `.claude/rules/machine-first.md`「遇到一条通行准则，走这个流程」第 4 条只能是建议。

### B4 「改键让旧库作废不算代价」失去了它要的那个键

「改键让旧库作废不算代价：不做兼容迁移、不为旧行补签，改完重跑。」（`.claude/kb/decisions/13-验证路线.md:441`）这一句的前提是：相关的改动会改键。新定案之后，判器、观察者、录制管线的改动都不改任何键；能让旧判定作废的合规手段还剩什么？

- 代码指纹：测试服务代码「不进任何键」（`.claude/kb/decisions/13-验证路线.md:443`），CPU 判器与观察者也不进崩溃判定的键（第 444 行）。
- 按树算改动范围：「一律不进键、也不许当复用依据：按提交、HEAD 或树算的改动范围」（`.claude/kb/decisions/13-验证路线.md:436`）。正文第 2 问举的「改判定器代码时强制全量重判一次」要先知道「判定器代码改了」，只能靠这两样之一，两样都被同一条已定项禁了。
- 手动删库：已定项 17 没写这一条出路；记录第 94 行的删法是这一次换键的一次性动作。

推出：已定项 17 的新句与「改键让旧库作废」「按树算的改动范围不许当复用依据」三句放在一起，判器改动之后唯一合规的「作废」是随机抽样（A4）。这是内部矛盾，不是代价问题。

### B5 判器改动让绿结论的内容变：强制现判每趟红、没有出路（推的）

已定项：「键相同而库里记着红的，下一趟现判、不复用」（`.claude/kb/decisions/13-验证路线.md:440`）。库：「/// 同一（块键，种类，版本）下两份都不红而换一份结论（块、计数向量、恢复字任一不同）拒绝，拒了一个字都不写」（`crates/singlefs-verification/src/verdict_store/conclusion_blocks/tests.rs:324`），拒绝的那一支是 `stored_conclusion_compared_with` 交回 `DifferentConclusionUnderAStoredKeyNotDecidedInTheFirstVersion`（`crates/singlefs-verification/src/verdict_store/conclusion_blocks.rs:819`）。

构造：一处合法的判器改动让绿状态的计数向量变（例：观察者计数里多数一类挂载态）或恢复字的写法变，结论仍是绿。之后每一趟：强制现判抽中一块 → 现判出一份与库里不同的绿 → 存不进（拒）→ 这一趟红（「判定不稳…判法依赖了键之外的输入」）；库里那一块没换掉，下一趟照样是旧的；下一趟另抽一块，再红。这一类改动按新定案「不作废已判的块」，却让门禁永远红，B4 又不给作废手段。我没在副本上跑这一串（强制现判那一块存不进时判段是报错退出还是只记一句，没逐行读到底），标推的。

## 攻击面三：哪一条最脆弱

### C1 漏判类改动：库里没有阳性样本，强制现判逐字相同

一个状态的判定向量：「/// 一个状态存进库的判定向量：红项（`CrashStateJudgement::red_items` 那种写法）逐项、换行接起来的字节；绿的状态是空向量。」（`crates/singlefs-verification/src/crash_judge_conclusions.rs:36`）。门禁常年绿，库里几乎全是绿块、绿状态是空向量。把一条不变量改成永远不报（GPU 的 WGSL、CPU 的池级 checker、记录核对器、观察者任一处），在这些块上现判出的也是空向量，强制现判逐字相同、不红。见得到差别的只有三处，各自的处境：

| 有阳性样本的地方 | 新方案下 | 出处 |
|---|---|---|
| 对拍用例（手造的违例镜像） | 对拍结论按输入复用，不重拍；WGSL 改动连测试函数都不重跑 | A1 |
| 库里记着红的块 | 每趟现判；漏判之后现判出绿，「两份里有一份红的照新的换上」，红块静默变绿 | `crates/singlefs-verification/src/verdict_store/conclusion_blocks/tests.rs:324` |
| 池级 checker 自己的单测与已知坏镜像 | 测试函数键带 checker 代码，会重跑；只罩 CPU 那一侧，罩不到 WGSL | 推的，没逐条读 |

排序（最容易假绿而没人发现的在前，推的）：

1. GPU 一侧（WGSL）漏判：三处里只有第二处见得到，而它把红换成绿、不报。没人发现。
2. 产品恢复改坏（A2）：GPU 机上不跑；对拍不重拍。
3. 录制管线产物改了（B1）：事实表、判表不重算。
4. CPU checker 漏判：checker 单测还见得到一部分。
5. 规范收紧（A3）：每趟 k/N。
6. 判器改动让绿结论内容变（B5）：会红，不是假绿，是走不出去的红。

这一条最脆弱的理由：它与「两边一起改错」无关，只改一边也抓不到；它不靠抽样运气，抽中了也逐字相同。
