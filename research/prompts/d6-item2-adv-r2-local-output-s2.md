Q1. Clone of a clone. H1 cloned at txg 100. B written at txg 150. Snapshot S taken at txg 200. H2 cloned from S at txg 250. H1 destroyed at txg 300. H1's prev_snap_txg is 200. Livelist for H1 contains ALLOC B (birth 150). Destruction release boundary is 200. birth 150 <= 200 so B is not released. H2 references B which is correct. No issue. But if H1 freed B at txg 220 then livelist has ALLOC B (150) and FREE B (150). Both birth 150 <= 200 so not processed. B is already freed so no release. Correct. However if H1 allocated B at txg 150 and did not free it, then H1's destruction does not release B. H2 still references B. Correct. No problem.

Q2. Snapshot handoff. H1 allocated B at txg 100. Snapshot S taken at txg 200. H1's prev_snap_txg becomes 200. Livelist has ALLOC B (100). If livelist entries with birth <= new prev_snap_txg (200) are kept, they are never released during H1's destruction since birth <= 200. These entries are irrelevant for release as B is part of S. Keeping them causes only wasted space in livelist. No wrong release or leak.

Q3. Crash during destruction. Intent committed with current position at start. Batch 1 processes ALLOC B (birth 250) and releases B. Before committing updated position, crash occurs. Recovery restarts intent, processes ALLOC B again. If release is not idempotent, B is released twice. Example: B was a physical block on disk. First release frees it. Second release attempts to free already freed block causing corruption.

Q4. Counter consistency. Livelist tree table entry counter is 1. Actual livelist has zero entries. Published state shows counter=1 but no entries exist. This happens if counter incremented during allocation but crash occurs before writing entry to livelist tree. No check detects this as counter is stored separately from entries. Recovery might not reconcile counter with actual entries.

Q5. Birth source. Parent pointer carries no birth txg. When FREE occurs, birth txg must be read from block metadata. If block is freed before FREE entry is written to livelist, metadata may be cleared. Example: H1 allocates B at txg 150. Birth txg stored in block metadata. Crash after freeing B but before writing FREE entry to livelist. When destroying H1, livelist has ALLOC B (150) but no FREE. System tries to release B again but it is already freed. Cost: each FREE requires extra read from block metadata. Failure: double release due to missing FREE entry.
