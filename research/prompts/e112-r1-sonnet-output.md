# E112 反推腿（Sonnet，第一轮）

任务：反推 D8（核心索引结构） 未定项 8 收口清单里 2026-09-06 由 E112 定案的两条——
① 写者把不认识的记账行原样带到新代（Carry）；② 未知 flags 位按「不认识这棵树」跳过该条目（Skip）。
方法：`.claude/singlefs-ai-sop/rules/evidence-discipline.md`「假设这个结论是错的，那我本该看到什么？然后真去看一眼」。

## 反推 ① —— Carry：写者把不认识的记账行原样带到新代

### 检索点 1：仓里有没有「写者不许写它不理解的东西」的已定条款

**(a) 反推假设**：① 违反了某条已定的「不许对不理解的东西下手」的条款。

**(b) 本该看到什么**：一条明确禁止「对不透明数据做任何搬运/重写」的条款，或者
Carry 操作本身踩中它。

**(c) 现查结果**：
- D17（实现分层与第三方管道）「数据接口」一节（`decisions/17-实现分层与第三方管道.md:39-44`）逐字：
  「数据接口 = 『能安全拒绝』所需的最小字节集合……挂载 / 只读挂载 / 拒绝，三选一，
  永远不会是第四种『照着错的假设读出看起来合法的字节』」。
  这条管的是**对 value 语义下断言**（照错的假设去解释字节），Carry 恰恰不解释 value——
  它只搬运（key 结构已知、value 原样复制），**没有对 value 做任何语义假设**，
  不落在这条禁令的射程里。**这一条没打中。**
- 但同一份检索命中了一条更精确的、**已经存在、且与 ① 字面用词直接冲突**的条款：
  `checks-owed.md:81` C71（不认识的统计量标签静默忽略）——
  「D5（快照 / 空间记账机制） 已定项 3 取 btree key 形态的理由逐字是『加新统计维度不改格式』，
  而 D12（目标介质） 已定每条线可能各有统计维度 ⇒ 老读者迟早读到不认识的统计量标签。
  **它若静默忽略，自己的 ENOSPC 不等式就少一项而毫无察觉**——那不是 compat，至少是 compat_ro。」
  怎么判：「**挂载时遇到不认识的统计量标签必须按 compat_ro 拒绝可写挂载**」。
  **这与 ① 的处方（Carry：原样带到新代，允许可写挂载继续）方向相反。**

**(d) 打中程度**：对「不认识的树」这个 E112 实际建的模型——未打中，D17 的数据接口原则允许
结构层面的不透明搬运。**但对 ① 标题所写的『不认识的记账维度』这个更宽的措辞——打中**：
见检索点 3 的完整链条，C71 管的正是这个宽范围里的另一半，且给出相反的处方。

### 检索点 2：搬运本身造成陈旧值的场景

**(a) 反推假设**：Carry 会把一个已经过时的值原样带下去，而这次挂载期间该树被别的路径改了。

**(b) 本该看到什么**：一条并发/后台路径，能在 v1 把某棵树标记为「不认识、跳过」之后，
仍然改动那棵树的记账所系的物理量（比如它的 inode 水位、它占的字节数）。

**(c) 现查结果**：没找到这样的路径。
- D13（验证路线）已定项 2（`decisions/13-验证路线.md:221-227`）：**先串行提交**——同一时刻只有一个写者。
- ㊁（flags 未知位按「不认识这棵树」跳过）的语义是**整树跳过**：v1 对该树不做任何应用层 I/O
  （E112 源码 `rows_per_gen` 里 `Skip` 分支明确只维护 `H_KNOWN` 那些头的行，`H_NEW` 完全不碰）。
- 后台路径（D26（后台整理与放置回收） 的搬迁）已由 D5（快照 / 空间记账机制）
  `decisions/05-快照-空间记账机制.md:24-30` 定案「搬迁不改 birth」，且只挪物理位置，不产生新
  inode、不动水位。
- 唯一带树维的统计量（inode 号水位，第 12 项）只在「该树是可写头且有新对象被创建」时才变化，
  而 Skip 策略下 v1 完全不写入该树 ⇒ 该量在 v1 挂载期间**确实不变**，Carry 原样带下去是准的。

**(d) 打中程度**：未打中。给定「先串行 + Skip 即整树不碰」这两条已定前提，
搬运造成陈旧值的场景**构造不出来**——这与 E112 自己的阴性对照（`rows_lost == 0`）一致。

### 检索点 3（最要紧的一条）：不认识统计量标签的写者，解得出这条 key 吗

**(a) 反推假设**：写者要重写一行，得先解出它的 key（标签、维度元组、代）；
不认识那个标签就解不出 key ⇒ ① 在机制上不成立。

**(b) 本该看到什么**：key 编码依赖标签值本身（比如按标签分派不同的字段宽度/布局），
使得一个不认识标签值的写者无法定位 tree_id / device / gen 这几段字节。

**(c) 现查结果，逐字**：

D5（快照 / 空间记账机制） 已定项 5（`decisions/05-快照-空间记账机制.md:384-394`）：
`(统计量类型标签 2, 树 ID 8, 设备 4, 代 8)`，value 8 字节 ⇒ **key 22 字节，字段宽度固定**，
与标签的具体取值无关——「标签」只是这 2 字节里的一个数值，不影响后面三段的偏移。
逐字：「统计量类型标签 | 2 | 自由选择。今天十一个，1 字节就够；取 2 是留扩展余量……」
（`:390`），树 ID 段同样是固定 8 字节（`:391`）。

⇒ **狭义的「解不出 key」被现查推翻**：因为字段宽度对全体标签统一、且是这五段的公共格式
（登记进 D15（格式冻结政策） 的冻结组件，`已定项3`「标签 → 合并规则是盘上语义，
统计量登记表立成独立冻结组件」），一个不认识某个标签**取值**的写者，仍然能按固定偏移
结构性地切出 (label, tree_id, device, gen) 四段——它不需要知道 label=X 意味着什么，
只需要知道这 22 字节的**切法**，而切法与标签值正交。**所以「Carry 需要先解出 key，
而解不出」这条路径本身不成立——机制上，key 是能解出来的。**

⚠️ **但顺着这条线往下查，找到了一个真正打中、而且分量更重的事实**：
① 这个题目的**原始表述**不是「不认识的树」，是「不认识的 **(标签, 树 ID)**」——两维一起。
`research/prompts/d8-item8-r1-opus-output.md:388`（收口清单原文）逐字：

> 4 | **旧写者对不认识的记账维度怎么办**。K 代点删要求每行每发布重写，而
> 「不认识的 (标签, 树 ID) 行要原样搬下去」全仓没写；**C71（不认识的统计量标签静默忽略） 只管标签不管维度**

同一份文档 `:307-309` 更直白：

> 这条要求全仓一个字没有（我 grep 过「不认识的统计量」，只有 C71 那一格，
> `checks-owed.md:81` 逐字讲的是「老读者迟早读到不认识的统计量**标签**」，
> **不管不认识的树 ID 那一维**）。⇒ **C71 的射程要扩到维度元组，或者另立一条。**

这份 opus 调研腿明确把问题拆成两半——**标签未知**（C71 已经管，答案是「拒绝可写挂载」）与
**树 ID 未知**（当时全仓空白），并建议「扩 C71 或另立一条」。

**E112 实际只回答了后一半**：它的模型里 `T_new`/`H_new` 是「v1 不认识的树」，
但树上跑的统计量**全部是同一个已知标签**（inode 号水位，第 12 项）——E112 一次都没有建模
「标签本身未知」这种情形。也就是说 E112 隐含选了「另立一条」，而**没有去扩 C71 的射程**，
但 D8（核心索引结构） 正文写下的收口标题仍然沿用了原始的宽泛措辞
「**旧写者对不认识的记账维度**」（`decisions/08-核心索引结构.md:432`「㊀ 旧写者对不认识的记账维度」）。

⇒ **矛盾点**：`checks-owed.md:81` C71 现查仍是 2026-09-01 的原文（「2026-09-01 三方论证的
正推腿」，未被 2026-09-06 触碰过），它给「标签未知」的处方是
**「必须按 compat_ro 拒绝可写挂载」**；而 D8 正文用同一个「记账维度」标题去覆盖 ①，
① 的处方是 **Skip+Carry（继续可写挂载，只是原样带那一行）**。如果有人只读到 ① 的标题、
不去查 E112 的模型细节，会误以为「标签未知」也该套用 Carry——**这与 C71 现行的处方直接相反**。

**这个冲突的机制原因，不是「key 解不开」，而是「carry 的正确性依赖于底层量在挂载期间
不变，而这个前提只在『树未知、Skip 掉全部交互』时成立，在『标签未知』时不成立」**：
一个未知标签背后的真实量（比如某条新介质线自己的统计维度）大概率会随 v1 的**正常写入**
持续变化——而 v1 既不认识这个标签，就不知道该不该、该怎么去更新它。此时「原样搬运」
会让这个数字冻结在旧值上，而它本该随写入递增/递减，最终静默破坏它所服务的
ENOSPC 不等式（正是 C71 点名的后果）。**这与「不认识的树」那个格子的机制性质不同**：
后者里 v1 完全不写入那棵树，底层量确实不变，Carry 才是准的（检索点 2 已核实）。

**(d) 打中程度**：**部分打中，而且是最有分量的一条**。
- 字面意义上的「解不出 key」——**未打中**（key 结构固定宽度，与标签值无关，能解）。
- 但「① 的处方能不能推广到『标签本身未知』」——**打中**：
  ① 的收口标题字面覆盖「记账维度」这个更宽的范围，而这个范围里已有一条更早、独立、
  仍然有效的条款（C71）要求相反的处方（拒绝可写挂载，不是继续可写并 Carry）。
  E112 没有检验过标签未知的情形，也没有触碰或改写 C71。
- **结论**：① 应当收窄措辞为「旧写者对**不认识的树**的记账行」（标签仍认识），
  不能读成覆盖「不认识的标签」；后者仍由 C71 单独管辖，且两者答案不相容。
  这是一个**尚未还的账**，不在 checks-owed.md 现有任何编号下。

## 反推 ② —— Skip：未知 flags 位按「不认识这棵树」跳过该条目

### 检索点 1：已定条款要求旧读者必须看见全部树

**(a) 反推假设**：Skip 违反了某条要求「旧读者/checker 必须看到全部树」的已定不变量。

**(b) 本该看到什么**：一条不变量，字面要求遍历覆盖「全部」而不是「全部认识的」。

**(c) 现查结果**：
- `invariants.md:117`，I-3.1（已分配统计对得上），逐字：
  **「已分配空间统计 == 实际遍历所有引用得到的和」**——「所有引用」是全称量词，
  字面上不允许因为「不认识某棵树」而把它排除在遍历之外。
- `invariants.md:136` 补充：「I-3.1（已分配统计对得上） 是**唯一允许全盘遍历的记账检查**——
  它是 checker，不是运行时路径。」——checker 的职责就是做这趟全量遍历，
  与运行时写者「可以只维护自己认识的」不是同一件事。
- I-3.7（活快照可枚举，`invariants.md:123`）字面只管「全部**活快照**」，
  不是「全部树」，射程更窄，**不直接命中**，但方向一致（要求某类结构可被完整枚举）。

**(d) 打中程度**：**部分打中**。I-3.1 的字面表述确实要求「所有引用」的完整遍历，
与「checker 对未知 flags 树也 Skip」这个隐含推广存在张力——见检索点 2。

### 检索点 2：跳过一棵树导致已定不变量判错的场景

**(a) 反推假设**：跳过一棵不认识的树不只是「看不到」，还会让 I-3.1 判出错误结论
（而不只是盲区）。

**(b) 本该看到什么**：一个场景——checker 对未知 flags 树也执行同一套 Skip 逻辑
（D8（核心索引结构） 正文把 Skip 的纪律句写成「必须被**旧读者**看见的改动走超级块
incompat 位」，`decisions/08-核心索引结构.md:432`「㊁」条附带纪律，用词是「旧读者」，
不是「旧写者」——这暗示 Skip 是读者/写者共享的通用语义），
导致 checker 自己的遍历也漏掉这棵树，而超级块记的「已分配字节」（pool-wide，不带树维）
里却**包含**了这棵树占用的字节（因为最初创建它、往里写数据的是一个**更新版本**的写者，
按正常记账逻辑已经把这些字节计入了「已分配」）。

**(c) 现查结果**：
- 这个混合版本场景（新版本先写入、旧版本随后接手）正是 E112 与 opus 调研腿共同使用的
  标准构造（`research/prompts/d8-item8-r1-opus-output.md:286-299` 的步骤①-⑤），
  E112 自己也用同一构造来论证 Carry 的必要性——**这个场景是仓里公认会发生的**，不是我编的。
- 在这个场景下：pool-wide「已分配字节」由最初创建该树的写者正确计入，之后不会因为
  「新写者不认识」而减少（这项统计不带树维，不需要认出某棵具体的树才能维护）。
  但若 checker（O2）在自己独立的遍历式验证里，对着同一条「未知 flags ⇒ 不认识这棵树 ⇒
  跳过」的判据，**不下钻进这棵树内部去数它引用的块**，则它的
  「实际遍历所有引用得到的和」这一侧会比超级块记的「已分配字节」**少**这棵树占用的量
  ⇒ **I-3.1 判红**——而且是**假阳性**：盘本身是健康的，只是 checker 版本落后于写入内容的版本。
- 仓里没有找到任何一条已定条款去区分「checker 的 Skip」与「写者的 Skip」，
  也没有找到任何一条已定条款说「checker 允许把 I-3.1 的『所有引用』读成『所有认识的引用』」。
  `checks-owed.md` 里最接近的一条是 C156（记录编码误读没有不变量，`checks-owed.md:162`），
  但它管的是 `Ignore` 政策下「记录被按错编码解释」没有不变量去抓，**不是**
  「Skip 政策下 checker 遍历不完整导致 I-3.1 误判」这件事——两者是不同的失效模式
  （前者是误读出错值，后者是漏掉一整段引用）。

**(d) 打中程度**：**中等打中，且是一个尚未被记录的新缺口**（不在 checks-owed.md 现有
任何编号下，因此不宜断言它「已被记录」）。
- 若 checker（O2）确实沿用与写者相同的 Skip 语义（现有文本的措辞——「必须被旧读者看见
  的改动」——没有排除这个读法），则 I-3.1 在混合版本场景下会产生**假阳性**，
  这比单纯「看不到」更糟：它是一条**已定不变量给出错误判决**，不是空白。
- 这不构成对 ② 本身（写者侧该不该 Skip）的推翻——写者侧的论证（防止 `Ignore` 造成的
  4000 条记录误读）依然成立。**打中的是「Skip 这个语义要不要在 checker 侧原样复用」
  这个未被讨论过的问题**，E112 的六个格子里没有一个格子测过 checker 自己的遍历策略。

## 总结

| 检索项 | 打中程度 |
|---|---|
| ① 已定条款禁止写不理解的东西 | 未打中（一般原则）／**打中**（C71 与 ① 标题字面冲突） |
| ① 搬运造成陈旧值的并发场景 | 未打中（串行 + Skip 整树不碰，构造不出来） |
| ① key 解不解得出来 | **未打中**（key 固定宽度，与标签值无关）；但顺着这条线挖出了①的**处方越界**——原始问题是「(标签, 树 ID)」一对，E112 只答了树 ID 那一半，标签未知那一半仍归 C71 管且处方相反 |
| ② 已定条款要求全部可见 | 部分打中（I-3.1「所有引用」字面是全称量词） |
| ② 跳过导致已定不变量误判 | 中等打中（混合版本场景下 checker 若沿用 Skip，I-3.1 会假阳性——新发现，未登记） |

**最要紧的那条**（key 编码）的结论：**机制上写者能解出 key，① 在这个字面意义上不被推翻**；
但反推过程挖出的是一个**范围问题**而不是**机制问题**——① 的标题「不认识的记账维度」
比 E112 实际验证的范围（「不认识的树」）宽，多出来的那部分（「不认识的标签」）
已经有一条独立、更早、仍然生效、处方相反的条款（C71）在管，两者从未被放在一起核对过。
