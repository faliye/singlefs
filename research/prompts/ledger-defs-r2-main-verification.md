1. 第一轮的修补站不住。第一组六条两条腿没有分歧（辩方不判这一组），攻方逐条打中，主 agent 坐实其中四处：

3. 两轮合起来：「段树、先验后合」这个形态两轮都被打穿，第二轮打中的比第一轮多，其中 R8 与 R1 是修补带来的。照「三轮里多数打穿才算打穿」，这个形态算打穿，不为它开第三轮。
4. 两种做法的比较（辩方数的，主 agent 没复核数）：两批三份补丁、三条登记行的一段，段树做法比同批做法多 7 条命令、多 6 次手写登记；主工作区带着没验过的补丁，段树做法只在合入那一步中途失败时有，同批做法从写段起一直有；账本第一百九十五节那一次事故，只有段树做法挡得住（改调用方的那一批要以删了接口的树为基线写，没法同批）。攻方 R13：那一节的 ② 是工具员直接改主工作区，两种做法都挡不住。结论：两种不同序，哪一种都不是白赢。
5. 攻方提的第三种（零轮，没被攻过）：写段照旧用段树给下一批当基线；验证段不在段树上验，第 2 步改在第 1 步用 `MERGE_AND_VERIFY_KEEP_COPY=1` 留下的快照上跑。它去掉了「段树与快照两棵树各验一半」「登记行抄两遍里的一遍」「修补只进段树」三处，R4–R6（合之前核主工作区）与 R11（合到一半失败）还在。

## 三、改法

1. 「段树、先验后合」在 `.claude/main-agent.md` 里的现行写法不照做：三种去向交用户定（下一节）。在用户定之前，主 agent 派实现时照改之前的做法（补丁打进主工作区、`--skip-apply` 验），并守一条：删接口与改调用方的补丁不拆成两批先后打（量过：账本第一百九十五节那一次就是这一形）。
2. 范围闸拒绝说明里缩域的出路改成点对变量：登记的崩溃枚举用例与放量分项写放量那个变量，直接调判器的对拍写判器那个变量（零轮；改 `.claude/hooks/lib_run_scope.py`，归下一批工具改动，改之前读两处读变量的代码坐实）。
3. 缩域与变异判定的键：已问管 `scripts/mutation/crates-mutation-rows.py` 的会话（缩域变量进键，或缩过域的那一趟不入库）。它回之前，实现员定义里缩域那条路加一句「缩域证红只当开发阶段的快速反馈；这一行在提交前要在全域上证过一次（范围声明写全域理由）」（零轮）。
4. 实现员的命令模板补 `whole-run:<类名>` 与 `--check feature-gated-tests --item feature-gated:<文件名>` 两形（量过：入口脚本与 `.claude/main-agent.md` 里已有这两形的写法）。
5. 第一轮第 8 条没去向的那一处边角：不改，记一句——主 agent 结束一轮时完工清理闸照列，后果只是多列一次。
