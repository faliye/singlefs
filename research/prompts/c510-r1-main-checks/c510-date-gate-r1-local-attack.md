BACKGROUND

The project's repository just gained a new automated check. The check looks for calendar dates written as yyyy-mm-dd (four digits, a dash, two digits, a dash, two digits) and rejects the repository if it finds one that could not possibly be a real date for this project: either later than "today" or earlier than the date the project's own history began, with a small grace allowance. This round asks only one question: among things that are legitimate to have in this repository, which of them could this check wrongly reject? This round covers only one of the check's two scanning dimensions (defined in FACT 1 below): the filename dimension. Do not discuss the check's other scanning dimension (the body-text dimension), do not discuss whether the check could be tricked into missing a genuinely fabricated date, and do not discuss where in the repository's automation this check's code should live. Those are being handled by other reviewers in this same round; answering them is out of scope here.

FACTS

FACT 1. The check has two independently scanned dimensions. The filename dimension scans the path of every file tracked by the project's version control system, anywhere in the whole repository, with no directory excluded, extracts every yyyy-mm-dd occurrence found anywhere in each path string, and tests each one against the date-range rule given in FACT 2. The body dimension is restricted to only the markdown files located under one specific subdirectory of the repository (the directory that holds paired sample fixtures for other automated checks, used to prove each of those other checks correctly passes on a good case and fails on a bad case), and extracts the same kind of occurrence from the text content of those files. This round asks only about the filename dimension.

FACT 2. Two bounds. The upper bound is computed using the time zone that is furthest ahead of UTC of any time zone in active use on Earth (UTC+14), so that a date is only rejected as "later than today" once that date has already passed in literally every place on Earth, not just in the time zone of the machine running the check. The lower bound is the date of the very first commit in this repository's own git history, minus a 7 day grace allowance. A date is rejected only if it is later than the upper bound, or earlier than the lower bound.

FACT 3. As of this review, the repository's first commit is dated 2026-08-26, the repository is a full clone (not a shallow one), and the lower bound is therefore 2026-08-19. One currently tracked file in the repository, named after the real calendar date something happened in this project, is dated one day before the repository's first commit; it falls inside the 7 day grace allowance and is accepted, demonstrating that the grace allowance is already in active, needed use for a real file, not merely a theoretical margin.

FACT 4. The function that computes "the date of this repository's first commit" is written once, generically, for reuse by many separate, unrelated projects that each vendor their own copy of the same shared toolkit. That generic function returns no date at all (an empty result) in either of two situations: the repository being checked is a shallow clone (created with a truncated history, so the commit git reports as "first" is only the depth cutoff point, not the project's true beginning), or the directory being checked is not itself the top level of a git working tree. This specific check, however, does not leave the lower bound undefined when that generic function returns empty: it substitutes a different, hardcoded constant date belonging to the shared toolkit's own separate repository (the day the shared toolkit's own git history began), and computes the lower bound from that substituted date instead. Right now, that hardcoded constant happens to be the literal date 2026-08-26, the exact same date as this repository's own true first commit (FACT 3), because this repository's history began on the same day its copy of the shared toolkit was first added to it. As a result, right now, running this check against a shallow clone of this repository, or against an invocation where the checked directory is not the git top level, produces the identical lower bound (2026-08-19) as running it against the true full repository. Nothing about this equality is guaranteed to remain true if this repository's early history is ever rewritten, squashed, or rebased onto a different starting point; the hardcoded fallback constant would not move together with it, since it belongs to a separate repository entirely.

FACT 5. This repository already has five separate, currently used naming conventions that put a real calendar date, corresponding to when something actually happened inside this project, directly into a filename: a directory of dated narrative logs, a directory of dated briefing notes, a directory of dated warning notes, one file per calendar month of decision-change history (named by year and month only, for example a file named for "2026-09", not by year, month and day together), and dated experiment-output files whose names combine an experiment number, a short label, and the date the experiment was run. A repository-wide scan performed for this review finds 90 tracked paths, across the whole repository, containing at least one yyyy-mm-dd occurrence; every one of those 90 dates falls inside the current allowed window ([2026-08-19, today]), and none is rejected.

FACT 6. Elsewhere in this repository, in ordinary prose rather than in a filename, one document that surveys prior work by other, unrelated software projects cites the real publication or statement dates of that outside work: a technical manual dated 2026-04-16, a blog post dated 2019-02-08, and a public statement dated 2026-07-15, all three predating this repository's own first commit by a wide margin. A second document, recording the historical evolution of an external cryptographic standard, likewise cites, in prose, three dates from that standard's own history: 2015-08-07, 2016-11-14, and 2017-01-30. Both documents currently sit outside the body dimension's scanned scope, because the body dimension only scans the one fixtures subdirectory named in FACT 1, so neither document is rejected today. This round does not ask whether the body dimension's scope is drawn correctly; it already excludes these two documents by design, and that design choice is not being revisited here. This round only asks whether the filename dimension, which FACT 1 states has no directory restriction at all and scans the entire repository, could ever legitimately be handed a filename carrying this same kind of external, pre-repository date, the way these two documents' prose already does.

FACT 7. Numerous other automated checks in this repository ship paired sample fixtures to prove that they correctly fail on a bad case and pass on a good case. Some of these fixtures build their sample files on the fly, inside a freshly created temporary git repository, using a small setup script; that on-the-fly repository is never itself committed into this repository's own permanent history, so any date baked into a file it creates during a test run is invisible to both of this round's scanning dimensions. Other fixtures instead ship their sample files as ordinary, statically committed files, tracked directly inside this repository's own permanent history exactly like any other file in the project. As of this review, four such statically committed fixtures (belonging to four different, unrelated automated checks) each carry a real calendar date as part of a filename inside them (for example, a filename recording a simulated experiment result, and a filename recording a simulated audit record); all four of those dates currently fall inside the allowed window. The check under review, when it does reject a bad date, prints a suggestion as part of its own failure message: that any fixture needing a deliberately out-of-range date on purpose should build that file on the fly with a setup script rather than shipping it as a static file. This suggestion exists only inside that one failure message; it is not written down anywhere as a general rule for how to write a new fixture, and nothing enforces it except the check under review itself catching the mistake after the fact.

FACT 8. The shared toolkit mentioned in FACT 4 keeps its own copy of itself inside a subdirectory of this repository, and that entire subdirectory is excluded from this repository's version control tracking (listed in the repository's own ignore rules). Nothing inside that subdirectory, no matter what dates its own filenames carry, is ever seen by either of this round's two scanning dimensions.
