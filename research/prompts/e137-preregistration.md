# E137 跑前登记：映射 key 形态的性能差距——每次 fsync 写几块、每次读几次 I/O

写于 2026-09-11 23:06 JST，装置写之前。

## 为什么跑

用户看了 E136（映射 key 岔路的代价行） 给的代价行之后说「代价看不出性能差距」。E133 / E134 / E136 报的都是格式量（条目宽、扇出、层数、叶层字节），**没碰 key 的顺序**：
- 按类复用写序键（`class_reuse_tagged`）码 1 的 key 以「出生树 + 出生 txg + 写序」打头，一个 checkpoint 新写的条目在映射树里挨着；
- 逻辑身份 + 写序键（`k1_seq`）与混合路（`k1_seq_class_reuse`）码 1 的 key 以五元组打头，按「树、对象、锚点偏移」排，同一个文件的条目挨着、新旧两版挨着。

D25（目标负载优先级） 把每次 fsync 的写块数拆成「叶子数 + 各层被触到的互异节点数 + 1 根槽 + 1 记录」，原始变量是「一次 fsync 带几个叶子、落在几条互不相交的脊柱上」——key 顺序正是决定映射树那一半落在几条脊柱上的东西。这个实验把它量出来。

## 臂与配置

三条臂 × 两种映射范围（与 E136 同名、同定义）：`k1_seq`、`k1_seq_class_reuse`、`class_reuse_tagged`；`all`（全部指针进映射）与 `code1_only`（只装码 1）。
叶容量与内部扇出取 E136 的 64 / 76 口径（映射叶 206 / 296、映射内部按该配置的节点指针、extent 叶 122 / 149、extent 内部按该配置的节点指针），由一条跨装置单测钉到 E136 的留存产物。

key 的顺序（只有相对顺序参与，宽度只影响容量）：
- `k1_seq` 与混合路的码 1：(类 1, 树, 对象, 对象出生代, 锚点偏移, 诞生代号, 写序)；
- `class_reuse_tagged` 的码 1：(类 1, 出生树, 出生 txg, 实例代号, 事务号)；
- `all` 配置下 extent 树自己的节点（码 2）也进映射：`k1_seq` 取 (类 2, 树, 层级, key 区间下界, 诞生代号)，混合路与按类复用写序键取 (类 2, 出生树, 出生 txg, 实例代号, 出生序号)；映射树自己的节点不进映射（C280（中央映射装哪几类单元没有条款） 那一格的预想）。

## 模型

- 两棵有序结构：extent 树（key = (树, 对象, 偏移)，三条臂顺序相同、只是叶容量不同）与映射树。叶是有序数组，满了对半分裂，删空不合并；内部层不建实体，第 l 层的节点号 = 叶在叶序里的位置 / 内部扇出^l（同一种近似三条臂一样用）。
- 一个数据单元 = 一个码 1 单元：(对象, 锚点偏移, 诞生代号 = 写它的 checkpoint 号, 写序 = 全局递增的事务号)；一个事务写一个单元。
- **初始镜像**（每条臂各建一份，同一串操作）：4096 个文件 × 256 单元 = 1 048 576 个单元；16 条流轮流追加，每条流顺着自己名下的文件依次写满，每写 64 个单元一次 checkpoint ⇒ 一个文件的单元散在很多个 checkpoint 里、与别的流交错。物理落点 = 写入的全局顺序号（分配器按写入顺序给落点）。
- **每次 fsync 写几块** = extent 树被触到的互异叶 + 各层互异内部节点 + 映射树被触到的互异叶 + 各层互异内部节点 + 1 根槽 + 1 记录（D25 的公式；`all` 配置下被 COW 的 extent 节点各有一条映射条目要删旧插新，一并算进映射树那一半）。
- **量的负载**（每条臂从同一份初始镜像出发，同一个种子生成同一串操作）：
  1. `seq_append`：一个新文件顺序追加；
  2. `multistream_append`：16 条流轮流，各往自己当前的文件顺序追加（同 E16 的 multistream）；
  3. `rand_overwrite`：在一个已有的 256 单元文件里随机偏移覆写（数据库 / 虚机镜像的形态），旧版随即释放；
  4. `metaheavy_create`：连着建新的一单元小文件；
  - 以上四条各取批 1 与批 10（每几次写一次 fsync），各跑 20 000 次写。
  5. `file_delete`：随机删整个已有文件（256 单元），报每删一个文件映射树 COW 几个叶；
  6. `snapshot_delete`：先在镜像上建快照，再按 `rand_overwrite` 覆写 20 000 次（旧版被快照留着），然后删快照、按诞生代号的顺序放掉那些旧版，每 256 个释放一次 checkpoint，报每放一个单元映射树 COW 几个叶；
  7. `relocation`：按物理落点顺序整段搬 20 000 个单元（D26 的整理），每 256 个一次 checkpoint，报每搬一个单元映射树 COW 几个叶。
  8. `random_read`：均匀随机读已有单元 100 000 次（先热身 100 000 次不计）；每次读走 extent 树从根到叶；提示过期的那一部分（190‰ 与 370‰，E96 / E109 的区间两端）再走映射树从根到叶。缓存是 LRU、按节点计，容量取 `k1_seq` 同配置下两棵树节点总数的 10% / 30% / 60%（三条臂用同一个绝对容量）；报每次读的节点未命中数。
- 种子取 1 / 2 / 3，逐个报。

## 判据（跑前写死）

- **只报数，不判输赢**：它的数进 D19（块指针的结构与宽度预算） 未定项 6 的代价行，岔路由用户定。
- **跨装置闸**：映射叶 / 映射内部 / extent 叶 / extent 内部的容量逐格等于 E136 留存产物里对应的行；
  触发它的观测：任一格不等。
- **阳性对照**（每条臂都跑）：缓存容量 ≥ 两棵树节点总数时，热身之后每次读的未命中数为 0；缓存容量为 1 个节点时，每次读的未命中数等于它走过的节点数；
  触发的观测：任一臂偏离。
- **判别力对照**：把按类复用写序键的码 1 key 顺序换成逻辑身份 + 写序键的顺序（宽度不动），它在 `multistream_append` 与 `file_delete` 上的映射树叶数必须变；
  触发的观测：不变（⇒ 装置没在量 key 顺序）。
- **每一格计数逻辑都有钉绝对值的单测**：用手算得出的小场景（几个文件、叶容量 4）钉住分裂、互异叶计数、内部层计数、LRU 未命中。
- **结果反过来我接不接受**（写在跑之前）：哪一条臂在哪条负载上赢，都照报；若三条臂在某条负载上逐格相同，照报「这条负载分不开它们」；若差距只在批 10 或只在某一档缓存上出现，照报它的条件。

## 它答不了的

- 不算挂钟、不算 CPU；块数是 D25 认的口径，屏障次数与 key 形态无关、不报。
- 模拟的池是 1 048 576 个单元，三条臂在这个规模上树高相同；E109 池规模上多出来的那一层（E136 的区间）只在每条被触到的脊柱上多一个节点，这里不叠加。
- 只建 extent 树与映射树；记账树、分配记录树、inode 树每次发布同样要 COW，三条臂相同，不建。
- 叶删空不合并、内部层按位置近似，三条臂用同一种近似。

## 补记（2026-09-11 23:12 JST，写装置时、第一次运行之前）

- **叶的分裂**：往最右那个叶的末尾追加时不对半分，另起一个新叶、旧叶不动（D8（核心索引结构） 已定项 6 的 inode 树「插入永远落在最右的叶」同形）；其余情形对半分。一律对半分会让追加型的映射树（按类复用写序键）只有半满，那是装置的毛病、不是候选的性质。
- **覆写负载加一条**：原登记的 `rand_overwrite`（一个已有的 256 单元文件里随机覆写）保留；另加 `rand_overwrite_global`——在整个镜像里随机挑文件与偏移覆写，与 E16（journal 的角色：WAL vs 意图日志） 的 `rand`（全域随机）同尺。一个 256 单元的文件在映射树里只占一两个叶，代表不了数据库 / 虚机镜像那种散在大文件里的覆写。
- 这两条只补定义，不改任何判据、阈值与作废条款。

## 补记二（2026-09-12 00:36 JST，单测第一次跑之后、产物第一次运行之前）

- **`multistream_append` 的装置与登记不符，改装置、不改登记**：登记写「16 条流轮流，各往自己当前的文件顺序追加」，装置第一版让 16 条流各往一个**新**文件追加。
  手算的小镜像单测是按登记的读法写的（两条流各往自己已写满的那个文件末尾追加），跑出来对不上，才发现。按登记改成：每条流往初始镜像里它最后写满的那个文件的末尾追加（偏移从 256 起）。
- **`snapshot_delete` 的装置与登记不符**：登记写「再按 `rand_overwrite` 覆写 20 000 次」，即在一个已有的 256 单元文件里随机覆写；装置第一版在全镜像里随机覆写。
  按登记改回一个文件，产物行名仍是 `snapshot_delete`；另加一行 `snapshot_delete_global`（全镜像随机覆写，理由同补记一的 `rand_overwrite_global`：一个文件只留得下 256 个旧版，代表不了大文件里散着的覆写）。
- 这两条只让装置回到登记的定义、并补一行与补记一同理的负载，不改任何判据、阈值与作废条款。
