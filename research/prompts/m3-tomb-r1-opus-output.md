## 二、W5　回退（主攻面）

### 2.1 共用前提：管理员回退之后，扫盘重建按条款字面选到被回退掉的那一版（量过，副本）

条款：管理员回退「不新增实例、不取号、不写实例表行、不施加也不删除任何记录」（`.claude/kb/decisions/23-journal的角色与格式.md:376`）；已发布谓词对当前实例只问诞生代号：「i == i_now ⇒ b ≤ 挂载根的 txg」（`.claude/kb/decisions/18-块里携带什么信息.md:309`）；择版本「再在对该根可见的候选里取该类的择新键最大者」（`.claude/kb/decisions/18-块里携带什么信息.md:294`）。回退那次发布用户可见树的根指针照抄 R_old 的（实现：「root: if entry.kind == TREE_KIND_EXTENT || entry.kind == TREE_KIND_INODE {」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/mount.rs:4972`）），不重写 inode 叶。

读法：D 引用 A 的叶（诞生代号 3，size 3000）与 A 的数据单元；盘上同一身份还有 B、C 两版，都过已发布谓词（同实例、诞生代号 ≤ 6），C 那版择新键最大。扫盘重建按条款拿回的是 C 的状态（size 2500），不是 D 的。换成删除：C 若是意图那次（inode 记录 nlink = 0），扫描照样判死回退回来的对象——**不写墓碑也一样**。

- 不变量 I-1.9 第二句「其外的可读垃圾每个 key 都被更大写序的可见版本或可见墓碑压住」（`.claude/kb/invariants.md:32`）：C 的叶是被 D 释放的垃圾，写序比可见的 A 版大，这张合法镜像上这一句不成立。I-1.9 今天「未实现」，checker 不判。
- D23 已定项 14 依据里写着「它的另一半「不写回退行时被回退抛弃的单元在全规则臂上复活」撑的是回退行，回退行删了，那一半不再承重」（`.claude/kb/decisions/23-journal的角色与格式.md:417`）。上面三行是反例：回退行删掉之后，被回退掉的单元照样在全规则下被选中，只是没有任何条款再管它。

四句：
1. 分不分辨臂：**不分辨墓碑的臂**。病根是扫盘重建对「挂着时回退」没有输入，inode 叶、extent、数据单元一样中；计数模型里 inode 叶对照行（回退取 R_old、不重写）在深度 8 全枚举 3 035 783 段里 LJD 292 022 段、DJA 7 448 段（`model-output.txt`）。照「打中不分辨臂」的办法，这个前提另立一笔账先修，墓碑的臂只看下面分辨得出的几格。
2. 被判的系统看不看得到判别子：扫描时盘上有 A、B、C 三版，系统看不到「D 是回退、它的父是 A」——这一信息今天不落盘（回退不写行、根记录不带 R_old）。属「判别子观测不到」：要么盘上加一样东西（下面的谱系记录），要么回退那次发布把被回退掉的身份重写成 R_old 的内容。
3. 满足的是判据字面哪一句：跑前判据第 1 条「扫盘重建……把活对象判死 ⇒ 出局」的「活对象判死」分句（inode 叶 nlink = 0 那一版被选中时）；也满足「已删对象判活」分句（模型里 inode 叶对照行的 DJA 段：删 → 回退 → 建 → 回退到删之后一版）。
4. 跑前条款给的改法在这一格上中不中：正文第五节没有给这一格的改法。我提的两样见 2.3：谱系记录（臂 cur_lin，同一份记录让 inode 叶对照行归 0，模型量过）修得到这一格；R_old 重写（臂 old_rw）只修墓碑那一半，inode 叶要另做同样的重写、数据单元（码 1）要重写整个文件，推的。

逐臂（四句只写与 2.1 不同的那几句）：

- **cur**（H1）：建 (1, 2) → 意图那次（txg 3）写墓碑 (1, 2) → 回退到 txg 2。墓碑容器随现行那一版，(1, 2) 的墓碑留在被引用的容器里，扫描判死活对象。这是上游攻方反例二的形状，量实了。D23 已定项 14 把树表、分配记录、映射、记账都写成「按这次发布照调整之后的分配器现算」，一棵新的墓碑树若不点名，默认就落在这一臂（推的：今天的回退代码只换 extent、inode 两种，见上面 `mount.rs:4972` 那一行）。分辨臂：分辨（old_rw、cur_lin 不中）。
- **old**（H1、H4）：容器索引随 R_old，旧版容器不重写。R_old 那版容器的诞生代号小于意图那次写的那版，扫描照样选新的那版。H4：容器 #1 装满之后第三次删除开了容器 #2，回退到开 #2 之前——#2 在 R_old 的索引里不存在，没人再写它，它那一版仍是已发布的最新版。**这正是「墓碑容器随 R_old 取旧版（像 extent、inode 两棵）」那一读法**，与 inode 叶对照行同形同中。
- **cur_int**（H3）：删（txg 3）→ nop（4）→ 回退到 2（T_rb 5，写区间 (2, 5]）→ 再回退到 txg 4 那一版（同实例、仍在候选集里：候选集取「根环里按 cur 的实例表判仍然有效 ∧ txg ≥ F_生效 ∧ 带文件」，被管理员回退越过的根不被实例表抛弃）。txg 4 那一版里对象是删掉的，而区间 (2, 5] 把死亡 txg 3 作废，扫描判活。来回回退本身是合法历史：D23 已定项 14 射程第 ③ 条写着「两个状态来回回退超过根环一圈时」。**只记区间不记父子，判别子观测不到**——两次回退之后哪段算数取决于谱系，不取决于区间。
- **old_rw_unref**：回退那次给 R_old 里没有的容器写空版本，但索引照抄 R_old、空版本没有结构指着。空版本是已释放的垃圾，分配器复用它的槽而不复用更旧那版（落点取「起点最小的空槽」，哪个槽更低是布局的偶然）之后，带墓碑的旧版又是最新。模型按最坏情形去掉全部空版本：LJD 295 390 段。同时它满足跑前判据第 2 条字面「墓碑容器在某个合法镜像上没有任何结构指向它」。
- **old_rw / cur_lin**：全部取样 0。两者都需要改条款（2.3）；cur_lin 还需要 W2 带死亡 txg。

上面两处条款原文：「| 候选集 | 根环里按 cur 的实例表判仍然有效」（`.claude/kb/decisions/23-journal的角色与格式.md:380`）；「两个状态来回回退超过根环一圈时」（`.claude/kb/decisions/23-journal的角色与格式.md:406`）。

### 2.3 崩溃恢复落到旧根、号重发（量过，模型）

模型的 crash:k 让最新 k 条根（连同它们的记录）读不出，恢复落到最新可读的根、写行、新实例第一个根取环里最大 + 1，水位随所选根（号重发）。七条臂（含 inode 叶对照）在这一族上都不中：被抛弃时间线里的墓碑容器版本诞生代号大于那一行的 T_pub，P2 判未发布。最硬的一段是号与出生代一起重发（`name=named history=H6_crash_reissue_same_number_and_birth`，七臂全 0）：

```
mk(txg2 建 1) nop(3) mk(4 建 (2,4)) rm:2:4(5 写墓碑 (2,4)) crash:3(丢 3、4、5 → 落到 txg 2，实例 2，行 (1, 2)；新实例第一个根 txg 3) mk(txg 4 又建出 (2,4))
```

现查模型状态：「rows {1: 2} cur_inst 2 cur_txg 4 objs {(1, 2): 'live', (2, 4): 'live'}」，盘上那版墓碑容器是「((1, 5), 5, 1, 4, ((2, 4),))」（容器 (#1, 出生代 5)、诞生代号 5、实例 1）。活着的新 (2, 4) 与被抛弃的墓碑 (2, 4) 号与出生代逐字相同，只靠容器单元写序里的实例代号 + 行 (1, 2) 分开。

- **实例表读不出时**（推的）：条款写「表没了就一条行都没有，全部旧实例的全部单元落进「无行 ⇒ 已发布」」（`.claude/kb/decisions/18-块里携带什么信息.md:311`），这时被抛弃的墓碑 (2, 4) 判死新的 (2, 4)。要三样同时坏（被抛弃的根、它们的记录、实例表），属级 1 已声明的降级。墓碑记录若带死亡那次的 (实例代号, txg)，扫描能判「死亡 (1, 5) 早于这个对象数据单元写序里的实例 2」⇒ 这条墓碑不可能指它；4 字节，被攻过零轮。
- 顺带：C103 那句「计数器回退不破身份（出生代不同）」（`.claude/kb/checks-owed.md:98`）在这段历史上不成立——号与出生 txg 都能重发（D8 已定项 6 射程对类型 2 已写「跨崩溃不成立」，`.claude/kb/decisions/08-核心索引结构.md:203`），类型 1 的容器身份 (#1, 5) 一样能被新实例再发一次。分开它们的是写序里的实例代号与实例表行，不是出生代。不改任何臂的判定，改的是 C103 那句的理由。

### 3.2 打中的逐条

1. **D 住根记录：根槽装不下**。今天根记录「pub const ROOT_RECORD_BYTES: u64 = 457;」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-format/src/lib.rs:188`），根槽宽 = physical_block_size，mkfs 判「if u64::from(geometry.physical_block_size) < ROOT_RECORD_BYTES {」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/make_filesystem.rs:313`）就拒。加一条 86 字节指针是 543 > 512：512 字节扇区的盘上 mkfs 拒。2026-09-06 那张表写的「根槽只剩 318 字节」是根记录还没加映射树根、分配记录树根两条 86 字节指针之前的数（推的：457 − 318 不等于今天的余量，没去 git log 核当时的根记录宽）。四句：分辨臂（只打 D）；不涉及判别子；满足的不是跑前判据任何一条的字面（它是格式常量撞墙），按「要改格式常量」交主 agent；改法只有加宽根记录或要求 4 KiB 扇区，都改新池新建文件的字节。
2. **E-tt：根的类随树长大而变**。一个容器装满（1019 条，第四节）之后要第二个，根指针要么改指一个码 2 节点（根的类变了），要么另起结构。D8 已定项 6 给「根恒为码 2」的理由逐字是「树表指针指向的根若类会随树长大而变，读者按 16 KiB 读 32 KiB 是静默误读」（`.claude/kb/decisions/08-核心索引结构.md:159`）。这条理由对 E-tt 原样成立。改成「根恒为码 2」就是 A。
3. **E-chain：链指针放不进类型 1 的定宽记录**。D18 已定项 11 的装载纪律是「① 一容器一种打包记录类型」「④ 记录定宽」；链指针（86 字节节点指针）塞不进 32 或 40 字节的墓碑记录，只能照实例表那样给类型 1 也开「kind 0 / kind 1 同宽」的例外（类型 4 那条例外写在 `.claude/kb/decisions/18-块里携带什么信息.md:298`，记录宽 88 正是为装下链指针定的）。记录宽抬到 ≥ 87 就让每个容器少一半以上的条数。另有：old_rw 给回退掉的新容器写的空版本没有链指着（链头取 R_old 的），落进臂 old_rw_unref（2.2，中）。
4. **E-inode0（我提的新形态，被攻过零轮，这里自己先攻）**：inode 树随 R_old 走（今天回退只换这两种的根），所以它就是臂 old（模型 LJD 308 883 段）。要变成 old_rw，回退那次就得 COW inode 树根去指重写后的墓碑容器，撞 D23 已定项 14「新根的用户可见树……的根指针取 R_old 那一版的」与回退用例那条「"D 树表里 inode 树与 extent 树的根指针与 A 的逐字节相同"」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-harness/tests/rollback_by_a_forward_publish.rs:369`）。另要改 D8 已定项 6 类型段「其余值判条目损坏」（`.claude/kb/decisions/08-核心索引结构.md:162`）与键 0 = 无效 inode 号那一约定。出局理由比 A 多两条条款，不推荐。
5. **E-queue：最后一批之后没有结构指着**。删除本体在最后一批删掉队列条目（上游判决 U3「最后一批删记录、删队列条目、删意图同一发布」）。墓碑要活得比删除长（扫描要它），条目一删容器就没人指，跑前判据第 2 条字面出局；多个删除共用一个开放容器时归哪条条目持有也没有答案。
6. **E-map：映射是派生的，装不进「只有它指着」的东西**。发布路径的映射按这一版各树里的单元逐类装（实现里码 3 只有 inode 叶容器一类：「mapping_key_for_node(UNIT_CLASS_PACKED, container.pointer),」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/transaction.rs:6409`）），不在任何树里的单元下一次发布就掉出映射；码 3 的映射 key 里也没有打包记录类型（事实表 g4），按 key 分不出哪条是墓碑容器。

### 3.3 A 与 D19 已定项 5「唯一入口」、D18 已定项 11「唯一持有者」（推的）

- A 的条目若装 86 字节节点指针（位置条目是提示、解引用经映射），与「中央映射 | 解引用与释放判定的唯一入口」（`.claude/kb/decisions/19-块指针的结构与宽度预算.md:101`）不冲突，与 inode 树内部节点今天的做法相同。2026-09-06 写 A「正面推翻 D19 已定项 5」，只对「A 的位置条目是权威、不经映射」那一读法成立（D19 已定项 8 把这种权威只给了自举豁免三类）。A 不需要自举豁免：它的节点是普通码 2 节点，进映射。
- 「容器索引是打包单元物理指针的唯一持有者」（`.claude/kb/decisions/18-块里携带什么信息.md:294`）：今天类型 2 的叶容器已经被两处持有位置——inode 内部节点条目里的子指针，与发布路径给它写的映射条目（上面 `transaction.rs:6409`）。所以凡是进映射的候选（A、E-tt、E-chain、E-inode0）在这一句上与类型 2 处境相同，**它不分辨候选**；这句话的字面与 D19 已定项 8 + 实现已经对不上，按跑前判据第 3 条交用户：建议读成「指针头部（MAC / nonce / 算法类型）与位置提示的唯一持有者，权威位置在中央映射」。
- I-3.1 怎么数到：A、E-tt、E-chain 经树表走到新种类（checker 要认这个种类）；同时映射条目指的范围本来就并进引用集合（I-3.1 的 checker 读法）。扫盘方向的 I-1.8 已经按类标签收码 3、不看打包记录类型（事实表 h2 ③），类型 1 容器进归并组不用改；走读方向 `registered_record_width` 只认 2 与 4（「PACKED_TYPE_INSTANCE_TABLE => Some(88),」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-checker/src/walk.rs:107`）），要登记类型 1 的宽，否则走到墓碑容器就判 I-1.7 红。

## 四、W2　墓碑记录的字段表

| 字段表 | 宽 | 一个容器几条（(32768 − 136) ÷ 宽） | 在哪条 W5 臂下站得住（模型） |
|---|---|---|---|
| 对象 ID 8 + 对象出生代 8 + 区间起 8 + 区间止 8 | 32 | 1019 | old_rw（0）；照 cur 的臂下中（臂 cur） |
| 上面 + 死亡 txg 8 | 40 | 815 | cur_lin（0）、old_rw（0）；只配区间作废时中（cur_int） |
| 上面 + 死亡实例代号 4 | 44 | 741 | 同上，另把 2.3 实例表读不出那一形判对（推的） |

1. **要不要带死亡 txg，取决于 W5 选哪条臂**，不是独立的一格。old_rw 让「当前视图里同一个 (N, B) 至多一条墓碑」成立（回退把第一条连容器一起退掉），记录不带死亡 txg 也分得开；照 cur 走的臂里第一次死亡的墓碑永远留在被引用的容器里，删 → 回退 → 再删之后同一个 (N, B) 有两条，不带死亡 txg 就只能整对象判，H1 那一中（臂 cur）就是它。上游攻方反例一要的「分得出墓碑是哪一次死亡」，在 old_rw 下由容器版本承担，在 cur_lin 下由死亡 txg + 谱系承担。
2. **容量那句的数过时了**：「C84（墓碑单元的粒度没人定） 定字段表时若取 32 则 1021 条」（`.claude/kb/decisions/18-块里携带什么信息.md:296`）。⌊(32768 − 91) ÷ 32⌋ = 1021，⌊(32768 − 107) ÷ 32⌋ = 1020，⌊(32768 − 136) ÷ 32⌋ = 1019；含预留位的码 3 头是 136（同一已定项「含预留位 136」），所以 32 字节是 1019 条。583 → 582 那一处已由已定项 16 改过，这一处没跟上（C89 ⑤ 同族）。
3. **同号的两个已发布对象**（崩溃恢复后号重发）：靠对象出生代分开，模型里只要实例表可读就够（2.3）；出生代也一起重发的那一形（H6）靠容器写序里的实例代号与实例表行。字段表本身分不开它们，这不是缺字段，是 P2 的分工。
4. **整对象的区间怎么写**：取 [0, 2⁶⁴ − 1]（起 0、止全 1）当「整对象」的写法，不取 [0, 删除时的 size)。理由（推的）：意图之后到最后一批之间 size 每批都在缩（上游判决 U3 每批改 size），写 size 就要定「取哪一刻」；全 1 与以后 truncate 的分段记录同一编码、扫描一视同仁。没找到取 size 时扫描判错的历史（nlink = 0 之后写入口拒，上游判决 U3 nlink 那一格），只是多一个要定的时刻。
5. **56 字节那句**落成定值：照上表 32 或 40，取决于第 1 条。

## 五、W3、W4、W6（找反例）

### 5.1 W3　回收门（推的）

- **不按清扫开门就判活**：第一版没有快照、没有清扫，统计量 13（清扫水位）不推进。有人会把门放宽成「死亡之前的根全部离开回退候选集（滚出 24 条的根环或低于 F）就回收」。反例：建对象 (N, B) 写几个数据单元 → unlink（意图写墓碑，数据单元分批释放）→ 再发 24 次以上发布，死亡之前的根全出候选集 → 门开、墓碑回收 → 扫盘重建：(N, B) 的数据单元头还在盘上（槽释放了但没被复用：分配取「起点最小的空槽」，之后不再写新数据就不复用），已发布、没有墓碑压着 ⇒ 判活。门必须含「它指认的那些数据单元已被覆盖或清扫」这一维，第一版只有清扫能给这一维 ⇒ **第一版墓碑不回收**；统计量 13 / 14 第一版登记与否不改这个结论（14 在没有快照时也没有根销毁可记）。
- **增长**：每次 unlink 一条记录。10⁶ 次 unlink：32 字节记录 982 个容器、64 356 352 字节（61.4 MiB，两份合计），40 字节 1227 个、80 412 672 字节（76.7 MiB）。A 另有索引：每个容器一条 112 字节条目，一个 16 KiB 索引节点装 ⌊(16384 − 167) ÷ 112⌋ = 144 条（推的：码 2 头 = 115 + 2 × key 宽，key 取身份 26）⇒ 32 字节记录约 14.7 万次、40 字节约 11.7 万次 unlink 之后索引长到两层，意图那次的闭式从 2.68 × 10⁸ 变 1.07 × 10⁹（3.1 表）。
- 跑前判据「无界增长 ⇒ 记一格」：增长率 = 每次 unlink 32 或 40 字节 × 2 份 + 每 1019 / 815 次一个容器头；什么时候需要回收 = 有清扫之后。

### 5.2 W4　开放容器与写纪律

- 「开放容器在它所属代际内每次要发布时被重写」（`.claude/kb/decisions/18-块里携带什么信息.md:294`）若读成「每次发布都重写」，每次发布主段多 2 次写，所有流的每次发布闭式 ×4（覆盖写那次从 16 777 223 到 67 108 871，段形量过、加写推的）。读成「有新记录的那次发布才重写」时，我没找到扫描判错的历史：不脏的容器不重写，旧版就是最新版；D19 已定项 12「每个码 2 节点与码 3 容器，一个实例在一个 checkpoint 里只写出一次」也只管写一次、不要求每次写。建议条款写成后者。
- 第一版没有快照 ⇒「代际结束」不发生，容器只在装满时关。开放容器数 = 1 棵树 × 类型 1（加谱系记录时再 × 1 个类型）× 1 代际 × 1 头。
- old_rw 让回退那次发布也写容器：量过的回退发布段形「measured_sizes=16+2+1+2 measured_two_state_closed_form=65543」，每多重写一个容器 ×4（2.4 表）。

### 5.3 W6　预付与 checker

1. **按记录摊的预付不够写第一个容器**（推的）。D18 已定项 10 射程 ①：「预留的是记录（摊 1/583 个单元）不是整单元」（`.claude/kb/decisions/18-块里携带什么信息.md:237`）。unlink 要把开放容器整个 COW（或开一个新的），一次要 32 KiB × 2 份的新槽；旧版的槽进 defer，「窗口内产生的释放不发信用」（`.claude/kb/decisions/03-空间分配.md:108`）。池里文件数 n 时按记录摊得 n × 32 字节 × 2 份，n < 1019 时不到一个容器：满池上 unlink 写不出墓碑，D3 已定项 17 不兑现。代码里 C375 那格已按整容器算：「一个墓碑容器（码 3，每份 2 槽）」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/admission.rs:1166`）。四句：分辨候选（A 还要多一个索引节点 16 KiB × 2 份的常驻额，E-tt / E-chain / E-inode0 只要容器）；系统看得到（准入时知道开放容器有没有、满没满）；满足 D3 已定项 17 字面；改法：常驻预付「一次容器 COW（+ A 的索引路径）」，与文件数无关，加上 R3 那份按批的预付（m3-delete-r2 的事），是两份。连续几次 unlink 都在 defer 窗口里时要靠抬 F 回收旧版，我没核抬 F 那条路在这一格上够不够。
2. **新不变量「墓碑指认的对象不在 inode 树里或 nlink = 0」**：臂 cur / old 下删 → 回退的合法镜像上红（模型 LJD 那几十万段都是这种镜像）；臂 cur_lin 下要按谱系过滤（谱系外的墓碑不算），checker 要实现谱系；臂 old_rw 下照字面成立。**这条不变量的字面要等 W5 选了臂再定**。
3. **I-9.6 墓碑那一半**（水位 > 全部已发布墓碑的对象 ID）：管理员回退水位取 max，崩溃恢复抛弃的墓碑被 P2 判未发布，模型里没有反例（模型不算水位不等式，只算 DJA / LJD，推的）。
4. **I-9.10 墓碑那一半**：同号同出生代的活对象与被抛弃的墓碑（H6）只有实例表读不出时才会被拿来比，按 P2 不比。没找到反例。
5. **「每个已删完的对象都有墓碑」**：已删完的对象不在 inode 树里，checker 枚举不出「已删完的对象」，只能反过来从墓碑出发——这一句写不成会红的形态（推的）。

## 八、这条腿自己的限度

- 模型是按条款推的扫描规则，不是 crates 的实现（crates 里没有扫盘重建）：它只模拟墓碑与一片 inode 叶；数据单元（码 1）、extent 树、清扫、分配器复用都没建。「最坏情形：被释放的单元都还在盘上」是对 LJD / DJA 的上界取法；old_rw_unref 用「空版本全被覆盖」取最坏。模型里一次发布至多一个 unlink、回退不受「带文件」「F」两条候选集约束（会多出一些合法性存疑的历史，但 cur_int 的 H3、cur 与 old 的 H1 都只用了合法的候选）。
- 「回退之后被选中的是被回退掉的那一版」在 Rust 原型上只量了「覆盖写 → 回退」一段固定历史（一个文件、一个叶容器、一个数据单元），删除那一段（nlink = 0 的叶被选中）是按同一机制推的——crates 里没有删除。
- 闭式加写是推的：只把多出的单元写塞进量过的主段，没实现墓碑写路径，也没量映射树、分配记录树会不会因为多一个单元而多分裂一个节点。
- 2.4 节里「谱系记录与删掉的回退行是同一类输入，删回退行的理由是否也打到它」没查（没读 D23 变更史与 2026-09-26 那几轮判决）。
- 没读 `decisions-history.md`，C113 定案 P4 / P5 的完整原文与「死亡代号」的定义来源没核（事实表 d3 同样没找到）。
- 重型测试一个没跑；只跑了 harness 档的一个自写用例（副本里）与纯 python 模型。

## 十、什么现象会推翻这份报告的打中

- 2.1：若条款里另有一处让扫盘重建知道「挂载根是一次回退、它的父是谁」（根记录或系统配置里带 R_old、或「对该根可见」另有定义），共用前提那一中不成立——我只 grep 了「对该根可见」一处（D18 已定项 11 第 294 行），没有定义句。
- 2.2 cur_int：若候选集条款把「被管理员回退越过的根」排除出候选集（今天的候选集只按实例表与 F 判，回退不写行），H3 那段历史不合法，cur_int 的 DJA 消失；那时它与 cur_lin 不再可分。

- 5.3 ①：若「预留的是记录」那句本意是「预留量按记录算、另有一份常驻的整容器额」，那一中只是措辞。
