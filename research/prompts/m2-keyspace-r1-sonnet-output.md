## S3　节点格式与自描述

**题面要的四样**：一个节点单独捡起来要说得出——① 哪棵树、② 哪一层、③ 管哪一段 key（起点与宽度）、
④ 第几代。逐样核今天的码 2 头（D18 已定项 18）与 D18 已定项 2、D8 已定项 11：

| 要的样 | 今天的码 2 头里对应哪个字段 | 状态 |
|---|---|---|
| ① 哪棵树 | 偏移 42「树 ID」8 字节（已定项 18） | **已有，不用改** |
| ② 哪一层 | 偏移 50「层级」（已定项 18） | **已有，不用改** |
| ③ 管哪一段 key（起点与宽度） | 偏移 51「key 宽」1 字节 + 偏移 52「key 区间」2k 字节（已定项 18），即 `[min_key, max_key]` | **字段已有，语义要不要改是候选分叉——见下** |
| ④ 第几代 | 偏移 52+2k「诞生代号」8 字节（已定项 18） | **已有，不用改**；且已被 checker 消费（见 invariants.md I-1.2，本轮未点名抄入，仅指路） |

**①②④ 推得出「已有，不用改」的链路**：D18 已定项 18 逐字给出码 2 头的完整偏移表，
树 ID（42）、层级（50）、诞生代号（52+2k）三段本来就是「对全部码 2 树无条件成立」的自描述字段
（D18 已定项 2：「码 2 的头宽公式 `86 + 2 × key 宽`……因此对全部树无条件成立」）；
D8 已定项 11 补一句这条字段表的读法是「一条对全部码 2 树都成立的通用解码规则」。
分配记录树、extent 树今天就是码 2 节点（背景材料「实现今天的样子」：分配记录树 key 宽 10、
extent 树 key 宽 24，两者的码 2 头都按 `86 + 2 × key 宽 + 29` 算，135 与 163 字节，
`crates/singlefs-format/src/lib.rs` 的 `ALLOCATION_RECORD_BYTES`、`.claude/kb/layout/01-first-txn.md`
的 `EXTENT_TREE_INDEX_NODE_HEADER_BYTES` 两个 format-const）——「按 key 空间定形状、不分裂」改的是
**上面几层怎么长、扇出怎么定**（S1/S2 的题面），不改「一个码 2 节点头里有没有树 ID/层级/诞生代号
这三个自描述字段」这件事：这三段的存在不依赖树是靠分裂长大还是按 key 空间几何预先定形，
只依赖「这是一个码 2 节点」。⇒ 三样字段已经存在，推得出不用新加。

**③ 是候选分叉，不是简单的「已有/新加」二选一**：D18 已定项 2 定案的字面是
「**区间取子树覆盖区间**：`[min_key, max_key]` 是这个节点的子树里到得了的最小 key 与最大 key」——
这是一个**观测语义**（这个节点底下实际有什么内容），不是**分配语义**（这个节点在 key 空间几何里
被规定该管哪一段）。今天的 checker（`crates/singlefs-checker/src/lib.rs` 的 `check_index_node_keys`，
第 444–448 行）验的正是观测语义：

```
if let (Some(first), Some(last)) = (view.entries.first(), view.entries.last()) {
    if key_of(first) != schema.fields(&view.smallest_key)
        || key_of(last) != schema.fields(&view.largest_key)
```

即「区间贴紧首末条目」——区间必须等于**实际存在的条目**的首末 key，不是等于**几何上分给它的**
那一段。这两个语义在「每个规定的段都恰好有对应节点、没有空段」时重合；但 S1 题面自己把
「没有记录的一段是『缺席 = 全空闲』还是要写空叶」列为候选——一旦走「缺席 = 全空闲」，
一个节点声明的区间（子树覆盖区间）与它在几何里「规定管辖」的那一段就会分岔（规定的那一段更宽，
因为它把相邻的缺席段也算在自己名下，或者相反）。**这一步已定分项推不出**：
D18 已定项 2 与 D8 已定项 11 只回答了「码 2 节点头要不要带区间、怎么编码」，没有回答
「这套按 key 空间定形状的派生结构，节点自描述的区间该取哪个语义」——这正是 S1/S2 的
候选问题下游。⇒ **字段（起点 = min_key、宽度 = max_key − min_key）已经存在，够不够用
要等 S1/S2 选定「缺席段怎么处理」之后才能定，本格推不出，是候选分叉，候选见下一段。**

**checker 怎么核「它管的区间就是规定的那一段」**：今天 `check_index_node_keys` 只会核观测语义
（区间贴紧首末条目），不会核规定语义，因为它不知道「规定的那一段」是什么——那要靠一个从
mkfs 时几何（设备槽数，S1 原句「层数由什么定（设备槽数在 mkfs 时就定了）」）或文件大小
（S2 的候选）现算出来的函数，这个函数本身是 S1/S2 要交的东西，本轮推不出。
但可以推出一条**判据形状**：无论 S1/S2 怎么选，只要几何是「按 key 空间定形状」而不是
「按内容驱动分裂」，checker 就有能力**不依赖树的实际内容**、只依赖 mkfs 时系统配置里的
参数（设备槽数）与节点自己的位置（树 ID + 层级 + 它声明的起点），独立算出「这一层、这个位置
应该管哪一段」，再拿它去对照节点自述的区间字段——这与今天 `check_index_node_keys`
「只能核观测语义、核不出规定语义」的做法是两条不同的检查，且后者是**新增**的、不依赖已有 checker
代码就能推出「值得加」这件事：因为它能在**节点丢失、错位**时也报出损坏（不需要先假设树的其余
内容完好才能判断某个节点该不该存在），这是「按 key 空间定形状」相对「按内容驱动分裂」的
checker 侧优势，但具体算式仍要等 S1/S2 定几何。

**D21 已定项 11「损坏必须可检出」在这套结构上靠什么兑现**：
已定项 11 的判据落点是「一个格式选择要保住『派生态丢了只是慢』这句话，必须回答『缓冲里那条消息
能不能只从单元重算出来』——能 ⇒ 加一套可检出性机制就兜住了」。分配记录树、extent 树都已经是
派生态（freeze-layer-membership.md 第 23、25 两行：extent 树 key 编码依据 D21 已定项 9、
分配记录树 key 编码依据 D21 已定项 5），可重算性这一层不变——本轮改的是树的内部几何，
不改「这两棵树整个可以从权威态（单元 + 记账 + 根）重建出来」这件事（D21 已定项 5 定案原句
「D3 已定项 3 那棵分配记录树整个可以从权威态重建出来」，D21 已定项 9 定案原句「索引（树）……
丢了只是慢」）。⇒ **兑现「可检出」靠的不是重建本身，是「①②③④ 四样自描述字段 + checker
能独立算出预期值」这条链**：①②④ 三样已经现成（见上），③ 的具体判据要等 S1/S2 的几何函数，
但只要几何被「按 key 空间定形状」这个前提固定死，checker 侧就能做到「不遍历树内容也能算出
预期形状」，这正是已定项 11 要的「可检出」（不是「检不出的陈旧」）的一种实现路径——
**本格半推得出：机制骨架推得出，具体断言要等 S1/S2。**

**什么现象会推翻这条判断**：如果 S1/S2 最终选的几何允许「同一段 key 对应的节点位置不是
mkfs 参数的确定性函数」（比如允许运行时按负载动态调整某一层的扇出），那么 checker 就没法
不依赖树内容独立算出预期形状，「按 key 空间定形状带来的 checker 优势」这条论证失效，
D21 已定项 11 的兑现方式要退回到与树分裂结构相同的「遍历 + 内部一致性核对」（即 T1/T3 那种）。

## S5　与别的结构的咬合

逐一核五处：中央映射、记账、准入、回收、挂载怎么读。判据统一是：这条条款字面管的是什么
（指针解引用/释放判定的地位、记账的态别、准入公式的项、回收的调用时机、挂载读取策略），
它依不依赖「树靠分裂长大」这件事——不依赖 ⇒ 不动；依赖 ⇒ 改哪一句、或本轮推不出。

### 中央映射（D19 已定项 5、8、12）

**已定项 5（位置条目降为提示，中央映射是唯一入口）：不动。**
定案管的是「谁负责解引用与释放判定」——位置条目降为提示、映射是唯一入口，这条关系存在于
「指针 → 被指单元」这一层，字面完全没有涉及被指单元内部是不是分裂、几何是不是固定。
分配记录树、extent 树的码 2 节点无论按哪种候选几何，仍然是被父指针（或树表条目）引用的
物理对象，已定项 5 的机制原样适用：不动。

**已定项 8（全部指针进映射，引用侧按类携带映射 key 的各段）：不动。**
定案表按「被指的类」（码 1 / 码 2 / 码 3）分指针宽度与携带字段，不按具体是哪棵树、
树是否分裂分。分配记录树、extent 树的节点今天是码 2，按候选几何改了内部布局之后
（S1/S2 的题面）仍然是码 2 单元，指针携带的段（出生树 8 + 出生 txg 8 + 实例代号 4 + 出生序号 4，
节点指针 86 字节）不变：不动。

**已定项 12（码 2/码 3 的映射条目 day-1 写出，固定点一个 checkpoint 只写一次）：不动，
且这句话对『不分裂』的树而言天然没有触发对象。**
射程句逐字「以后放开边插边 COW，D8 已定项 13 照旧要守：同一次发布里同一个 key 只按最终态
落叶一次」——这条收严针对的是「插入触发结构改变（分裂）从而可能同一个节点在一次发布里
被 COW 多次」这类风险。分配记录树、extent 树「不分裂」意味着插入不触发结构改变，
这条收严的触发条件对它们本来就不成立（没有「边插边 COW」这件事可放开）；已定项 12 的主句
「固定点写死：每个码 2 节点与码 3 容器，一个实例在一个 checkpoint 里只写出一次」这条约束
本身管的是 COW 写入频率，与分裂与否无关，字面照旧成立：不动。

### 准入（D28 已定项 4 的 ckpt_cost）

**公式本身：不动。**
已定项 4 定案「ckpt_cost = Σ（每棵记录树当前的高）+ 记账树每发布的节点数，每次发布按
当时的树高重算」——这句话字面上不预设树是靠分裂涨高还是按 key 空间几何固定：「当前的高」
这个量对两种结构都存在、都可以被读出来。⇒ 公式这一句不用改。

**它带出的欠账 C363（树高从哪读没有条款）：本轮出现了一个新候选，但只对分配记录树成立，
对 extent 树不成立——两棵树不对称，本格半推得出。**
C363 逐字「发布那一刻『每棵记录树当前的高』从哪读——码 2 节点头里的层级字段加树表条目的
根指针，还是挂载时建、发布时维护的一份内存派生态——全仓没有条款」。S1 题面自己写
「层数由什么定（设备槽数在 mkfs 时就定了）」——若这句成立，分配记录树的层数是一个
**mkfs 时刻确定、此后永不改变**的常量：可以直接从系统配置里的设备槽数与既定的叶容量/
扇出公式现算出来，既不用读码 2 节点头的层级字段，也不用维护内存派生态，因为它根本不变。
这与 `m2-treesplit-r1-main-verification.md` T5 判决「树高从哪读交用户」（那一轮的树会
分裂涨高、层数会变）形成对照：本轮如果按 S1 候选的字面走，分配记录树这一半的 C363
出现了此前没有的候选「树高 = mkfs 参数的确定性函数，不必现读」。但 extent 树不对称：
S2 题面自己写「文件变长超出当前层数罩得住的范围时怎么长一层」——这说明 extent 树的层数
**会随文件增长而变化**（哪怕这个变化机制不叫「分裂」），因此 extent 树这一半 C363 仍然
完全开着，不能套用分配记录树那条候选。⇒ **本格只能推出「分配记录树的树高候选 = mkfs
参数的确定性函数」这一新增候选本身存在，给不出具体公式（要等 S1 定扇出/叶容量），
也不能替 extent 树给出同类候选（extent 树层数不是 mkfs 时刻定死的）——两棵树要分开
写进岔路单，不能合并成一格。**

**什么现象会推翻**：若 S1 最终候选里分配记录树的层数不是纯粹由设备槽数决定
（比如允许运行时因为空段处理策略而变化层数），上面这条「mkfs 参数确定性函数」候选
就不成立，C363 对分配记录树也退回和 extent 树一样完全开着的状态。

### 回收（D3 已定项 7、C518）

**已定项 7（分配记录条目的盘上编码，落点释放时条目不删、改写为已释放+释放代）：不动。**
定案管的是「分配记录条目本身的写语义」——找到落点对应的那条记录、原地改写 value
（打已释放标志、写释放代），这个操作在候选几何下完全一样：无论分配记录树是普通 COW 结构
还是按 key 空间定形状的固定几何结构，「改写已存在的一条记录」这件事不涉及树的整体形状。
唯一可能的差别是**定位**这一步——若几何固定，槽号可能能直接换算成确定的节点位置
（O(1) 算式），不需要像 btree 那样逐层比较查找；但这是**实现路径**的差异，不是
已定项 7 定案的字面（「落点释放时条目不删、不点删」「改写成已释放+释放代」）要改的字：
不动。

**C518（一次挂载之内环转过一圈之后不回收）：不动，与本轮判定的对象无关。**
C518 逐字「实现在一次挂载之内收不回来：`crates/singlefs-core/src/mount.rs` 只在挂载时
与抬 F 时调 `reclaim_released_up_to`，根环在一次挂载里转过一圈……要重挂才回到空闲集合」——
这是运行时**调用时机**的实现缺陷（回收函数没有在合适的时点被再次调用），与分配记录树
内部是否分裂、几何是否固定完全正交：改分配记录树的结构既不会修复它，也不会让它变得
更难修——`reclaim_released_up_to`（`crates/singlefs-core/src/allocator.rs:1182`）读的是
分配记录，不管分配记录树内部长什么样子。⇒ 不动，该修的是调用点，不在这一轮判定的射程内。

### 挂载怎么读

**推不出，是候选分叉；今天没有为分配记录树/extent 树单独定义挂载读取策略。**
D19 已定项 5 「挂载态怎么读映射」那一段管的是**中央映射树自己**怎么读（「第一版挂载态
打开池时把中央映射整片读进挂载态……映射树根不是根兼叶时拒绝打开挂载态——这是第一版的
