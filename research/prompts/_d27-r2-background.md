## 二、三处已坐实的硬伤（主 agent 逐字核过源码与条款）

### 硬伤一：E114 的 `packbg` 臂丢掉了装载纪律，而它丢的那一条正是 D27 未定项 8

**D18 已定项 11 的四条装载纪律，逐字**（`.claude/kb/decisions/18-块里携带什么信息.md:711`）：

> 四条装载纪律：① 一容器一种打包记录类型；② 一容器一个代际——把 D18 已定项 10 对墓碑定的纪律
> **推广到按代际回收的打包记录类型**（**今天只有类型 1**；类型 2 的记录逐条死亡、容器由 B 树分裂 /
> 合并回收、一片叶活很多代，D8 已定项 6）……③ 一容器一棵树；④ 记录定宽，记录数 × 记录宽 ≤ 声明长度，
> 在认领时判。

**E114 源码自陈**（`research/e7-index-bench/src/bin/e114_pack_ledger.rs:14`）：

> **四条装载纪律②「一容器一个代际」** ⇒ 容器不跨发布累积，**这是本实验的主自变量的由来**。

`pack` 臂遵守它：`containers_of(n, m, cap) = ⌊n/m⌋ × ⌈m/cap⌉ + (n mod m) 上取整`。
`packbg` 臂（第 164 行）写的是 `let containers = n.div_ceil(cap); // 与 m 无关`，
**注释只说了后果，没有一个字说它正在跨过纪律②**。

**主 agent 的判定（两半，不要把它当成一句话）**：

- **不成立的那半**：说 `packbg` 违反了 D18 已定项 11，不对。纪律② 自带射程限定
  「推广到**按代际回收的**打包记录类型」，并明文把类型 2 排除在外，理由逐字是
  「记录逐条死亡、容器由 B 树分裂 / 合并回收、一片叶活很多代」——**这正是 D27 容器的处境**。
  而且 D27 的容器占哪个码还没定（未定项 3），它今天不是码 3，D18 已定项 11 管不到它。
- **成立的那半**：`packbg` **悄悄假定了 D27 未定项 8 的答案是「数据侧一条装载纪律都不取」**，
  而未定项 8 逐字仍是「**装载纪律在数据侧取哪几条。状态：未定**」。
  ⇒ **52.33× / 28.40× / 6.91× 是有条件的数**，条件是未定项 8 那个答案；条件没写在实验里，
  也没写在定案里。若未定项 8 取纪律②，`packbg` 立刻退化成 `pack`，而 `pack` 在 m = 1 时
  收益恰好 1.0、总账为负（E114 有断言守着：`benefit_law_holds`、m=1 那格）。
  若取纪律③（一容器一棵树），容器数从 ⌈N/cap⌉ 变成 Σ_树 ⌈N_树/cap⌉。

### 硬伤二：写账里根本没有元数据写，搬迁那次中央映射覆写一个字节都没算

**E114 源码**（第 172–174 行，`pack_bg_ledger`）：

```
let write_bytes = (n + containers + overwritten) * UNIT * W;
Ledger { data_bytes, meta_bytes: map + alloc + cidx + live, write_bytes, ... }
```

`meta_bytes` 是**静态占用**（中央映射条目 + 分配记录 + 容器索引 + 活槽记账的常驻字节），
`write_bytes` **只数数据单元**。两条臂都没有把任何一条元数据的**写**计进 `write_bytes`。

E114 主判据那句「元数据两臂都算：中央映射条目、分配记录条目、容器索引条目、活槽记账条目」
说的是**条目占用**，不是**写字节**。读起来像「元数据算全了」，实际没有。

**这一漏对两条臂不对称**：`pad` 的对象写一次、中央映射条目写一次；
`packbg` 的对象写一次、**搬迁时中央映射条目要第二次覆写**——而中央映射是一棵树，
改一条要 COW 叶 + 一路到根 + 一条 journal 记录。

**主 agent 的信封背面估算（不是实验结果，量级用）**：中央映射条目 = key 33 + value 28 = 61 字节，
一个 32768 单元的叶约装 (32768 − 86) / 61 ≈ 536 条。N = 100 000 个对象：
- 整理**按映射 key 序批量**搬 ⇒ 约 ⌈100000/536⌉ ≈ 187 片叶被重写，×w=2×32768 ≈ **12 MiB**，
  相对 `pad` 数据侧 6.5 GiB 是 ~0.2%，可忽略；
- 整理**按容器凑满序**（即随机 key 序）搬 ⇒ 最坏每对象一次叶 COW = 100 000 × 32768 × 2 ≈ **6.5 GiB**，
  **等于把写字节再翻一倍**。

⇒ 这一项的量级横跨三个数量级，**取决于 D27 未定项 6（整理的触发判据与批量）**，而它未定。
E114 声称的「写字节多 1.7%–14.3%」**只是数据 payload 的落盘比**，不是事务系统的写放大。

### 硬伤三：加密转换没进模型；而它撞的是格式，不只是代价

E114 自陈的射程（`.claude/kb/experiments/114-小数据打包容器的总账.md:111`，逐字）：

> 容器内变长槽的分配与碎片、slot 的 nonce / MAC 载体、容器索引的落点，一律不建模。

而 `SLOT_FULL = 47`（五元组 33 + 写序 10 + 槽表 4）里**没有 nonce、没有 MAC**。

**I-6.1（nonce 不重用），逐字**（`.claude/kb/invariants.md:187`）：

> 加密开启时，全盘任意两个**已写出**的块（不论当前是否仍被引用），其 (密钥代号, nonce) 二元组不相同

⇒ **不论 AAD 绑谁，后台整理搬一个对象都必须重新加密**（照抄密文 + nonce 会让同一个 nonce
出现在两个已写出的块上，直接判红）。E114 把整理建模成纯字节搬运。

**加密本身的量级不大**：E6 多核饱和 17.4 GB/s，100 000 × 512 B = 51 MB ⇒ 约 3 ms。
**真正的重量在格式侧**，见第三节。

## 三、加密这一侧的硬约束（第一版材料漏引的骑手已补上）

**D9 已定项 6，逐字**（`.claude/kb/decisions/09-加密.md:57`）：

> AEAD 的关联数据里放什么 —— **已定**：绑逻辑身份五项，物理位置一律不进。
> ⚠️ **这五项对快照维是瞎的，且是静默的**——E31（AAD 缺快照维） 实测错配检出 **0 / 2**，
> 两次都读出另一个可写头的数据而 MAC 全绿；出路只剩「绑出生快照」，**字段表欠一次重开**
> （2026-08-29 记账时定「定案不改，缺口记入」）。**引用这五项时必须连这条一起引。**

五项 = (单元类型标签, 树 ID, 对象 ID, 对象出生代, 锚点偏移)。

**推论（主 agent，第一版材料漏了这一步）**：AAD 字段表**本身就欠一次重开**（要加出生快照维）。
在那次重开之前给容器定 AAD 组成，等于在一张明知要变的表上定一个 day-1 永久契约。

**D19 已定项 3，逐字**：定宽还是变长 —— **定宽，不加密时留位**。
**D19 开篇逐字**：逻辑属性（MAC、nonce、算法类型、extent 距起点偏移）在头部，**每个逻辑 extent 一份**。
**D19 已定项 4**：位置条目 14 字节（设备 4 + 物理偏移 6，**编码为 16 KiB 槽号** + 密文校验和 4）。
**D19 已定项 5**：中央映射是解引用唯一入口，key = 逻辑身份五元组 33 字节，value = w 份位置条目。

**C103（容器索引无落点）**：2026-09-06 那次收口失败，逐字的死结是
「中央映射的 value（位置条目 14）装不下 MAC 128 位 + nonce 96 位」。

## 四、用户这一轮给的两条约束（2026-09-07）

> slot 修改不能绕过 COW；不能新造一套 pointer。

**主 agent 已看出的一处直接后果，请各腿核这一步对不对**：
位置条目的物理偏移编码是 **16 KiB 槽号**（D19 已定项 4），
而容器里的槽在 32 KiB 单元内部按字节排 ⇒ **14 字节的位置条目指不到一个槽**。
于是中央映射对「已打包对象」的 value 只能是别的东西。不新造 pointer 的话，
仓里现成的只有 D18 已定项 11 的**身份引用 26 字节**（出生树 8 + 打包记录类型 2 + 容器号 8 + 容器出生代 8）。
⇒ 中央映射的 value **变成两种形态**（位置条目 / 身份引用），这本身算不算「新造一套 pointer」，
以及它撞不撞 D19 已定项 5「唯一入口」和 D19 已定项 3「定宽」，是这一轮要判的。
