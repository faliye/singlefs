# 背景：D8 未定项 8 第三轮（2026-09-06）——四条定案经第二轮修正后的现行形态

singlefs 是从零设计的 COW 文件系统，尚无代码。下面每一条主 agent 都逐字现查过原文。

## 现行的四条（含第二轮的修正）

① **快照进树表**，每个快照一条条目，带**诞生 txg 8 字节**（= 快照发布那次 checkpoint 的 txg）。
   ⚠️ 第二轮修正：它**只**给 I-3.7「盘上存在一个可枚举的持久结构，其元素恰为当前全部活快照」
   一个载体；**收不了** D5 欠的「全部根的 txg 列表」——D6:66-69 的反例
   （「主线 txg=10 建可写快照 X；在 X 里于 txg=30 写块；主线 txg=35 建快照 Y。
   按 D5 的条件 30 ≤ 35 < death → 判『Y 引用它』，而 Y 根本看不见它」）
   说明谱系成树之后要的是**嵌套区间标号**（D6:73-74），不是每根一个标量。另立 C144。

② **树 ID 水位住超级块，多副本取 max**，落 E100 段四「运行时水位」（原 12 字节，加 8）。
   ⚠️ 第二轮补上两处，挂载协议现在是：
   `base = max(这次挂载独占打开成功的那个集合里各超级块的水位, 已发布树表里的最大树 ID + 1)`；
   `新水位 = base + K` 写进那个集合里的每一份超级块、全或无、失败先回卷；
   本次挂载发的号取自 `[base, base + K)`，段内发号不碰超级块，段用完再预留下一段。
   `K` 是可调值不是格式常量。理由：水位永远先于使用落盘；崩溃烧掉整段未用完的号，
   而 D5 已定项 4 第 2 项对单调量逐字接受「浪费号、不复用号」；树表那一路只会把 max 顶上去不会拉下来。

③ **`prev_snap_txg` 每头一份，住树表条目**（8 字节）。
   ⚠️ 第二轮修正：一条条目上是**两个各自独立的 8 字节字段**（自己的诞生 txg + 前驱的 prev_snap_txg），
   不存在同段字节两义（此前记错了）。剩的那一问是**平局判别子**：
   D16:84-85 已定「同一 checkpoint 内建两个快照是允许的……但 checker 里的『上一个快照』
   要用 `(txg, 快照 id)` 打破并列」，而①③只给了 txg 那一半。
   另立 C145：D5:129「每个可写头各持一份 prev_snap_txg 与一份 deadlist」、
   D5:8「建快照时把活头的 deadlist 整个交接给新快照」——deadlist 的盘上落点全仓没有。

④ **兼容档只取「树表条目自带长度」**（每条目 18 字节 = 长度 2 + 预留 16，千棵树 18 KB），
   不取「索引节点每条目自带长度」（每条目 +2 字节、扇出掉 2.5%，今天没有消费者）。

## 第二轮同时改掉的一个陈旧数

E79 源码的位置条目停在 11，而 D19 已定项 4（2026-09-03 用户定案）定的是 **14**。重跑后：
树表单元容量 **266 → 243 棵/层**（三档节点头 243 / 242 / 242，不再逐格同值）；
512 槽平铺不带水位 7 → **6** 棵（去掉水位也装不下 7 棵）；7 棵常识树集从爆 1 字节变爆 **43** 字节；
4096 槽 65 → 59 带水位 / 60 不带。D22 已定项 7「恒走间接层」的结论方向不变、更硬了。
