Q1. Clone of a clone. Head H1 cloned at txg 100. H1 writes block B at txg 150. Snapshot S of H1 taken at txg 200. H2 cloned from S at txg 250. H1 destroyed at txg 300. H1's prev_snap_txg is 200. Block B's birth txg is 150. For H1's destruction, release boundary is birth > prev_snap_txg (150 > 200 is false). Thus B is not released. H2 references B via S which includes B. No release of B occurs. Correct behavior. However, if H1 had a block C written at txg 250 (after S), birth 250 > 200 so C is released during H1 destruction. H2 does not reference C as it was cloned from S at 200. Correct. No issue here.

Q2. Snapshot handoff. H1 cloned at txg 100. Writes block B at txg 150. Snapshot S taken at txg 200. H1's prev_snap_txg advances to 200. If H1's livelist is kept after snapshot, it contains ALLOC B (150). When H1 is destroyed later (e.g. txg 300), birth 150 <= 200 so B is not released. The ALLOC B entry remains in livelist but is never processed for release. This is wasted space. No wrong release or leak. Only wasted space.

Q3. Crash during destruction. H1 has livelist with ALLOC B (txg 150). Destruction intent started. First batch processes ALLOC B: releases B. Before removing ALLOC B from livelist tree and committing, crash occurs. Recovery re-runs intent. Livelist still contains ALLOC B. System reprocesses it: releases B again. Block B is released twice. This is invalid as releasing a block twice corrupts free space tracking.

Q4. Counter consistency. Livelist tree has two entries: ALLOC B and ALLOC C. Tree table entry counter is 1. During a batch operation, ALLOC C added to livelist but counter increment not committed. After crash recovery, published state shows counter 1 but actual entries count is 2. No check in the system would detect this inconsistency as the counter is stored separately and not validated against tree contents.

Q5. Birth source. Parent pointer carries no birth txg. When H1 frees block B written at txg 150, system needs birth txg to check against prev_snap_txg. Since parent pointer has no birth, system must read birth txg from block's metadata on disk. This requires a disk read which is not O(1). Fact 4 claims deletion is O(1) by reading only parent pointer field and prev_snap_txg. Without birth in parent pointer, O(1) guarantee fails. Cost is additional disk access per deletion operation.
