You are reviewing a design for a copy-on-write filesystem. Your stance is: find a concrete counterexample. Do not summarize, do not praise. Do not use any markdown emphasis such as bold or italics. Answer in English. Answer all three items, number them 1, 2, 3. Keep each item under 250 words.

Setting, all settled and not open for debate. Every storage unit carries a plaintext self describing header holding one pointer to its birth owner: a tuple of tree id, object id, object birth generation, and anchor offset. That header is fixed length and holds exactly one such tuple, so it names the birth owner only, never the current set of referrers. Snapshots are implemented as multiple writable heads, each head owning its own tree. Reflink is a day one promise and shares whole units, never parts of a unit. Authoritative state is exactly three things: units, accounting, and roots. Anything else is derived and must be rebuildable. A derived structure is allowed to be lost, and losing it may only make things slower, never lose data. A sparse side table already exists for blocks that have a second live reference; it was added because the release rule looks only at birth generation and would otherwise free a block that still has another referrer.

The design under review. The set of referrers of a shared unit is split in two. Referrers created by snapshots are not stored at all: they are found by walking the list of trees and doing one point lookup per tree, on the assumption that two heads referring to the same logical object use the same key. Referrers created by reflink or deduplication are stored as a list in the value of the existing sparse side table. The count of live references in that same table is authoritative, because getting it wrong frees data that is still referenced. The list of referrers in that same table is declared derived and losable: if it is lost, it is rebuilt by scanning, and the claim is that rebuilding costs on the order of the number of shared units, not the size of the pool.

Your task:

1. Attack the rebuild claim. To rebuild the list of referrers you must enumerate pointers, and pointers live inside trees, not inside units. Say what a rebuild actually has to read, give the cost in terms of what it must traverse, and construct a case where that cost is not on the order of the number of shared units. If the claim survives, say exactly why.

2. Attack the split of one table into an authoritative half and a derived half. Construct a history where the table is damaged or lost, and say what happens to each half. Then say whether the derived half can really be treated as losable when it shares storage with the authoritative half.

3. Attack the assumption that two writable heads referring to the same logical object use the same key. Construct a history where they do not, and say what the point lookup per tree returns in that case, and what the caller does with that answer when it is about to move the unit.

For each item give the history as numbered steps, say which rule text it breaks, and give the smallest change that would close it. If you cannot construct one, say so and say exactly which step blocked you.
