1. The claim that the following unit must be read is correct. The project rule forbids any runtime decision path from answering by traversal, meaning allocation decisions cannot require reading disk data. To check if the next unit is a container, the writer must read its header to inspect the class code. This violates the rule because the admission check must answer immediately without disk reads. A different data structure like a global index tracking unit classes in memory could remove this issue, but the current setup lacks such an index, making the proposal unimplementable as described. No alternative placement scheme avoids reading the next unit while respecting the rule.

2. The two encodings are indistinguishable in failure behavior. A reader unaware of containers rejects both: a zero payload length with nonzero flag fails due to nonzero flags (per version one rules), and a new registry code fails as unregistered (codes 4-15 are reserved but rejected if not explicitly registered). For a scanner rebuilding the index, both are rejected as invalid units. Encryption AD uses the class code; using class 1 with nonzero flags or a new code changes the AD, but this is irrelevant since the unit is rejected before decryption. Thus, the reviewer’s claim is decoration—no observable difference exists in failure behavior.

3. Small object size: 50 bytes. Unit capacity: 32768 bytes. Each container holds 655 small objects (655×50=32750 bytes payload). Initial 655 small objects: packed uses 32768 bytes, padded uses 655×32768=21,468,320 bytes. After deleting 99.847% (leaving 1 small object), packed uses 32768 bytes, padded uses 32768 bytes (equal). At 99.848% deletion (0 small objects), packed uses 32768 bytes (empty container), padded uses 0 bytes. Packing stops being cheaper at exactly 99.847% deletion fraction. For any deletion fraction above this, packing is more expensive; below, it is cheaper or equal.
