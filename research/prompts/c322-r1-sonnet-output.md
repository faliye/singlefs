## 一、源码现查：取号的物理写法、择超级块的实际逻辑（材料没有引到这么细，本节是本轮自己读代码得到的）

**`acquire_instance` 只发一个 `CommitStep`，两盘写在同一个 for 循环里，中间没有屏障**（`crates/singlefs-core/src/transaction.rs:181-190`）：

```rust
pub fn acquire_instance<Device: BlockDevice>(
    pool: &mut PoolWriter<'_, Device>,
    previous_instance: InstanceGeneration,
) -> Result<InstanceGeneration, BlockDeviceError> {
    let instance = InstanceGeneration(previous_instance.0 + 1);
    pool.perform(CommitStep::RotateSuperblockSlots {
        slot_generation: SUPERBLOCK_GENERATION_AT_INSTANCE_ACQUISITION,
        journal_tail: 0,
        journal_instance: instance,
    })?;
    Ok(instance)
}
```

`CommitStep::RotateSuperblockSlots` 的实现（`transaction.rs:124-146`）是 `for (identity, device) in self.devices.iter_mut() { ... device.write_at(..., WriteDurability::Plain)?; }`——两次物理写都是 `Plain`（非 FUA、非屏障），一次循环写完两块盘。`acquire_instance` 只调用这一个 `perform`，函数本身不加任何屏障。**这与 P5「取号 = 每盘各一次超级块槽写，两次写之间、之后都不另加屏障」逐字相符**——不是材料转述，是本轮直接读到的实现。

**`SUPERBLOCK_GENERATION_AT_INSTANCE_ACQUISITION` 是一个写死的常量 `2`**（`transaction.rs:49`：`pub const SUPERBLOCK_GENERATION_AT_INSTANCE_ACQUISITION: u64 = 2;`），全仓只有 `acquire_instance` 这一处用它去写盘（另外两处用它做取模计算）。⚠️ **这意味着 `acquire_instance` 目前只对「从 mkfs 世代号 1 起的第一次取号」成立**：它每次都把槽世代号写死成 2，不是「当前世代号 + 1」。如果这个函数将来被复用在「第 14 项 实例切换」或「回退」这类**不是第一次**的取号上（那时候两盘的槽世代号早已远大于 2），这个常量会把世代号往回写——但**这是里程碑范围外的推测**：第一个事务这条录制流只调用了一次 `acquire_instance`（mkfs 之后紧接着的那一次），本轮验证到的只是这一次；后续实例切换要不要复用这个函数、复用时世代号怎么算，仓里没有代码也没有条款回答，不在 C322 的判据范围内，这里只记一笔，不作为 J1–J6 的证据使用。

**`warm_up` 每一轮的第一步是 `Barrier`，紧接着才是写 journal 记录**（`transaction.rs:204-222`）：

```rust
for txg_number in 1..=WARM_UP_EMPTY_PUBLISHES {
    let txg = CheckpointTxg(txg_number);
    pool.perform(CommitStep::Barrier)?;
    let record = JournalRecord { instance, counter: txg_number, ... };
    ...
    pool.perform(CommitStep::WriteJournalRecordToEveryDevice { ... })?;
    pool.perform(CommitStep::Barrier)?;
    ...
}
```

而 `CommitStep::Barrier` 的实现是 `for (_, device) in self.devices.iter_mut() { device.barrier()?; }`（`transaction.rs:148-153`）——**对每块盘顺序调用、任一块盘的 `barrier()` 返回错误就用 `?` 整体短路**。这一点是 J1 可达性判断的关键，见第三节。

**`choose_superblock`（真正的恢复路径用它选超级块，不是 checker）对跨盘分歧完全不设防**（`crates/singlefs-core/src/recovery.rs:191-224`）：

```rust
pub fn choose_superblock(reader: &dyn PoolReader) -> Result<Superblock, RecoveryFailure> {
    ...
    for device in reader.device_identities() {
        // 先在这块盘的槽 0 / 槽 1 之间取世代号大的
        let best_on_device = ...;
        match &chosen {
            None => chosen = Some(best_on_device),
            Some(previous) => {
                if previous.filesystem_identifier != best_on_device.filesystem_identifier
                    || previous.device_count != best_on_device.device_count
                {
                    return Err(RecoveryFailure::SuperblocksDisagree);
                }
            }
        }
    }
    chosen.ok_or(RecoveryFailure::SuperblocksDisagree)
}
```

`chosen` 只在**第一块盘**（`None` 分支）时被赋值，之后各盘只核 `filesystem_identifier` 与 `device_count`——**`journal_instance`（实例代号）与 `slot_generation`（世代号）跨盘一个字都不比，函数返回的永远是第一块盘（按 `device_identities()` 的次序）的那一份**，与 P7「各盘之间只核 fsid 与设备数相同，返回第一块盘的那一份」逐字相符，也是本轮直接读到的。

**`device_identities()` 的盘序是确定的、不是随机的**：`MemoryPool` 的 `devices` 字段是 `BTreeMap<DeviceIdentity, SparseDevice>`（`crates/singlefs-harness/src/crash.rs:128`），`device_identities()` 用 `self.devices.keys().copied().collect()`（`crash.rs:199-201`）——`BTreeMap::keys()` 按键升序遍历，**恒定返回标识号小的盘在前**。这意味着：只有**标识号大的那块盘**单独拿到新实例代号、标识号小的那块盘落后时，`choose_superblock()` 会稳定地选中落后那块盘（陈旧实例代号），不是「看运气」。

**checker 的 I-7.7 判定（`walk.rs`）与恢复用的 `choose_superblock`（`recovery.rs`）是两套独立代码**，前者对跨盘分歧确实设防（见下），后者没有——这是给三条臂都要面对的一个既有缺口，与 C322 本身无关，但直接决定了甲的第二句「跨盘取世代号最大的那一份」要改在哪：**改 `recovery.rs::choose_superblock`，不能只改 `walk.rs`**（walk.rs 是审计，不是恢复决策）。

**walk.rs 里 I-7.7 目前实际做的是两次独立判定，都记在同一个不变量名下**（`crates/singlefs-checker/src/walk.rs:527-570`）：

```rust
let instances: Vec<u32> = chosen.iter().map(|(_, view, _)| view.journal_instance).collect();
root_ring_judgements.judge("I-7.7", instances.iter().all(|instance| *instance == instances[0]), ...);
...
root_ring_judgements.judge("I-7.7", instances.iter().all(|instance| *instance >= highest_root_instance), ...);
```

`Judgements::judge`（`crates/singlefs-checker/src/image.rs:48-58`）按不变量名累加——同名的两次 `judge` 调用是逻辑与（任一次不成立就记违例，只留第一处）。**第一次判定就是「各盘实例代号相等」**，恰是 J1 要打的那个点：只要两盘的 `journal_instance` 不等，这里就先红。

## 三、J1（可达）：C322 原句描述的状态本身不可达，可达的只是它的一个更弱的子情形

**J1 问两件事**：(a) 「各盘实例代号不等」的崩溃状态有几个、落在哪一段；(b) C322 原句「取号写了一盘、另一盘没到、**暖机的记录已持久**」在已定的屏障下可不可达。**(a) 材料已经答对，本轮验证了；(b) 材料没有直接推导，这是本节的主要工作，结论是「不可达」，而且是结构性不可达，不是没枚举到。**

### (a) 两个违例状态落在哪一段

段序列取自 `.claude/kb/first-txn-layout.md` 八这一节的整条流那一行（`first-txn-layout.md:390`）：

`2+2+1+2+2+1+18+2+1+2`，共 10 段，与 `first_transaction_step_seven_layer0.rs:129-132` 的断言 `vec![2, 2, 1, 2, 2, 1, 18, 2, 1, 2]` 一致。第一段（长度 2）的种类是 `[superblock_slot×2,barrier]`——**取号那两次超级块写，加上暖机第一轮开头那道屏障，三者合并成流开头这一段**（这一点 `first-txn-layout.md:390` 自己写明：「取号的 2 个超级块写与暖机第一次开头的屏障合成开头一段」）。

`crates/singlefs-harness/src/segments.rs:78-104`（`split_into_segments`）的切法确认了这一点：屏障关掉它之前那一段，**屏障本身算在被关掉的那一段里**——写号那两次写之后紧跟着的那道屏障（`warm_up` 循环的第一步）没有开一个新段，而是把自己并进了取号那一段。

`crates/singlefs-harness/src/crash.rs:594-639`（`enumerate_layer0_selecting`）的枚举规则是**前面的段全持久 + 当前段任意真子集**（doc comment 原话）：对每一段，`persisted_before`（之前所有段）恒为全部持久，当前段用 `mask` 遍历 `0..full_mask`（即除全 1 外的全部子集），之后的段完全不碰。第一段（2 个写）贡献 `2^2 − 1 = 3` 个非全持久状态：`{}`（两盘都还是旧实例 0，一致）、`{只盘 A}`、`{只盘 B}`（两种都不一致）——**恰好 2 个不一致状态，都落在第一段内部**，与 P6、与本轮现查的 262165 个状态里的计数逐字吻合。

### (b) C322 原句的字面状态结构性不可达

C322 原句要求：取号（第一段）只落了一盘 **且** 暖机的记录（第二段）已经持久。按 `enumerate_layer0_selecting` 的枚举规则，这是**两个不同段同时处于「有痕迹」状态**的组合——第一段是真子集（未完成），第二段却非空（已经有写落地）。**这种组合从来不会被枚举出来**：函数对每一段只做「之前全持久 + 本段子集」，从不会在「本段是真子集」的同时又让「后面的段有非空子集」。这不是「262165 个状态里没搜到」，是**这个闭式枚举的定义本身就不产生这种组合**——`closed_form_state_count = 1 + Σ(2^|段| − 1)`（`segments.rs:129-141`）是按段分别求和，不是按段的笛卡尔积，两个真子集不会同时出现在同一个状态里。

**这个「不可达」不是模型的人为限制，它有物理依据**：`warm_up` 循环的第一步是 `Barrier`（`transaction.rs:207`），`CommitStep::Barrier` 的实现对**每一块盘**顺序调用 `device.barrier()?`（`transaction.rs:148-153`），用 `?` 传播错误——这个 `perform(Barrier)` 调用**只有在两块盘的 `barrier()` 都成功返回之后才会返回 `Ok`**，之后代码才会往下发暖机的 journal 记录写。`barrier()`（flush）对一块盘的语义是「把这块盘此前排队的写强制落盘」，所以只要 `perform(Barrier)` 返回 `Ok`，就意味着**两块盘各自在这道屏障之前发出的写（含取号那两次超级块写）都已经各自变成持久**——不需要跨盘同步，只需要每块盘自己的屏障语义成立。反过来，如果崩溃发生在两块盘的 `barrier()` 调用之间（比如盘 A 的 `barrier()` 已返回、盘 B 的还没调用或没返回），那么 `perform(Barrier)` 根本不会返回 `Ok`，后面「写暖机记录」这一步压根不会被发出——暖机记录不可能出现在盘上。

⇒ **C322 原句描述的那个状态，在「取号 → 暖机」之间已经有的这道屏障下，物理上造不出来**：要么屏障没完全走完（两盘的取号写还没被这道屏障统一确认持久，此时暖机记录一个字节都不会被发出），要么屏障走完了（此时取号那两次写必然双盘都已持久，不再是「只落了一盘」）。这两支是穷举的，没有第三支。**这一点甲乙丙三条臂都不改变**——三条臂谁都没有提议拿掉暖机第一轮开头这道屏障，它是 D16（发布语义） 已定项 8 定下的暖机结构的一部分，不是 C322 要决定的那个屏障。

**判据 J1 的触发条款是「构造出一个可达的这种状态，或证明 P6 的 2 个不是全部」**——本节做的是后半句的反面：**证明 C322 原句那个状态不但不在 P6 的 2 个里，而且在现有屏障结构下不可能存在**，P6 的 2 个就是全部「各盘实例代号不等」的状态，其中没有一个带着「暖机记录已持久」。J1 判据不触发（没有找到可达状态，也没有推翻 P6 的 2 个），按判据表这一格是「不触发」。

**这对三条臂的实际意义**：C322 欠账行原句描述的检查对象需要重新表述——真正可达、需要恢复逻辑处理的，是**更弱的情形**：取号那两次写只完成一盘、**且这就是整个崩溃点**（后面什么都还没发出）。这正是甲的第二句、乙都要处理的那个情形，只是范围比 C322 字面写的窄。这一发现在第七节里作为对材料的一条实质性补充记录。

## 四、J2（复用）：不在这条录制流内部，但 `choose_superblock` 有一个跟 C322 独立、三条臂里只有甲显式管到的缺口

**J2 问**：各臂下有没有一个崩溃状态让下一次取号拿到一个已经有根、记录或单元落盘的实例代号。

**先说清范围**：这条录制流从 mkfs 到第一个事务结束，**只调用了一次 `acquire_instance`**（mkfs 之后紧接着那一次，实例代号 0 → 1）。262165 个状态里没有第二次取号，所以「下一次取号」不是这条流本身枚举出来的东西，**J2 问的是一个假设动作**：如果在某个崩溃状态之后真的发生了下一次取号（比如恢复判定「实例代号不一致 = 一次没做完的取号」而重新走了一遍取号，甲的第二句就是这么设计的），会不会撞上一个已经有东西落盘的号。

**在 P6 的 2 个状态内部**：由第三节 (b) 已经证明，这 2 个状态发生时暖机还完全没有开始（连 journal 记录都没发），所以「实例代号 1」名下此刻**没有任何根、记录或单元**——如果下一次取号按甲的规则取 `max(全部超级块, 根环) + 1`，在这 2 个状态里 `max` = 1（较新那块盘已经写了 1），算出新代号 = 2，**不会复用 1**，也不会撞上任何已发布的东西（1 名下本来就是空的）。**这个具体判据在这 2 个状态上不触发**（构造不出让复用发生的例子）。

**但存在一个更深的、与 C322 本身无关、独立于三条臂措辞的缺口**——本轮读代码时发现（第一节已给出源码）：`recovery::choose_superblock`（真正恢复路径用来选超级块的函数，不是审计用的 `walk.rs`）**从不跨盘比较 `journal_instance` 或 `slot_generation`，只返回第一块盘（标识号最小）的选择**。设想一个**不在这条流里、但代码结构上完全可能发生**的场景：

1. 实例代号 1 已经完整暖机、两盘一致（这一步在这条流的第四段之后已经真实发生过，不是假设）。
2. 之后某次挂载因为某种原因需要**再取一次号**（代号 1 → 2；甲的规则、乙的规则都允许「下一次取号」这个动作存在，只是各自没有把「什么时候触发下一次取号」写进这轮判据里——这是 D23（journal 的角色与格式） 已定项 14「实例切换」要管的范围，不是 C322 要定的）。这次取号只有标识号**大**的那块盘写成功（标识号小的那块盘因为 `device_identities()` 恒定排在前面、`choose_superblock` 只信它），崩溃。
3. 下一次挂载调用 `choose_superblock`：它只看标识号小的那块盘，**返回代号 1（陈旧）**，完全不知道标识号大的那块盘已经有代号 2。
4. 如果恢复流程据此认为「当前实例还是 1，可以再取一次号」，算出的新代号是 1 + 1 = **2**——**这个数字标识号大的那块盘已经有了**（第 2 步写的）。这不是巧合，是因为 `choose_superblock` 压根没有做「跨盘取最大」，任何知道「上一个代号是几」的调用点都会被那块落后的盘带偏。

**这个缺口在三条臂下的处置完全不同**：
- **甲**明确写了处置（「择超级块跨盘取世代号最大的那一份，下一次取号取 max(全部超级块, 根环) + 1」），但这句话对应的代码改动要落在 `recovery.rs::choose_superblock` 里——本轮读到的当前实现完全没有这个逻辑，是要写的新代码，不是描述已有行为。按甲的规则，第 3 步会返回代号 2（跨盘取最大），第 4 步算出 3，**不会复用 2**。
- **乙**（只是把取号那两次写从「同一循环」改成「盘 0 → 屏障 → 盘 1 → 屏障」）**完全没有触及 `choose_superblock` 的跨盘比较逻辑**——乙只改写入端的时序，不改读取端（恢复）的选择规则。上面这个缺口在乙下**原样存在**，乙的条款字面「I-7.7 字面不改」也印证了这一点：乙没有给「跨盘取最大」这件事一个位置。
- **丙**把实例代号降级为超级块之外的一次原子写（外加超级块降为提示），如果那次原子写是权威来源，「跨盘比较超级块」这个问题本身被绕开了，但材料没有给丙的具体读取规则，本轮无法进一步验证丙下这个缺口是否被别的机制封住。

**J2 判据的触发条款是「构造出这样一个状态，写出它的持久写集合」**——本节没有在**这条流枚举出的 262165 个状态**里构造出复用（第 2 步之后的场景不在这条流的范围内，是下一次挂载才会发生的事，J2 判据字面问的是「各臂下有没有一个崩溃状态」，如果严格限定在这条流内，答案是「没有」）。但本节额外指出：**这个复用缺口的真正修复点不在 C322 这一格要写的「屏障放哪」，而在 `recovery::choose_superblock` 要不要跨盘比较**——甲的措辞已经预留了这个修复（第二句），乙没有，这是甲相对乙的一个实质性优势，会在第八节的结论里作为一条独立理由列出。

## 五、J3（条款）：「全或无」在物理上不成立；乙没有换来它，只是缩小了窗口

**J3 问**：I-7.7 字面「取号写超级块全或无」在两块盘上是两次独立的设备写，物理上能不能全或无；各臂是改条款还是改机制；改条款的那一臂，新条款会不会在一个真错的镜像上判成立。

**物理上不能全或无**：两块盘是两个独立设备，各自的写路径、缓存、掉电时机互不相干，除非有一种真正跨设备的原子提交协议（本工程没有、丙也没有引入这种协议——丙只是把「代号」这一份数据挪到一次原子写，但没有说这次原子写如何跨两块盘同时生效），**任何「先写盘 0 再写盘 1」的顺序都存在崩在两次写之间的窗口**，与顺序无关。

**验证乙是否换来「全或无」**：把乙的写法（盘 0 → 屏障 → 盘 1 → 屏障）按 `segments.rs` 的切段规则重新切一遍——这会把原来 1 段 2 写切成 2 段各 1 写（盘 0 写 + 紧跟的屏障是一段，盘 1 写 + 紧跟的屏障是另一段）。按 `enumerate_layer0_selecting` 的规则（前面的段全持久 + 当前段真子集）：第一段（1 写）贡献 `2^1 − 1 = 1` 个非全持久状态——即「盘 0 还没写」，这时按前缀规则盘 1（属于第二段，在后面）当然也没写，两盘都还是旧代号，**一致，不是违例**；第二段（1 写）贡献 `2^1 − 1 = 1` 个状态——「盘 0 已经全部持久（前缀假设）+ 盘 1 没写」，这正是「盘 0=新代号、盘 1=旧代号」的**不一致状态**。

⇒ **乙把违例状态数从 2 降到 1（少了「只有盘 1 先写」那一种，因为乙的串行顺序规定盘 0 必须先写），但没有降到 0**——「盘 0 已经落盘、盘 1 还没落盘」这一种在乙下依然可达，且是乙唯一剩下的违例状态。**「全或无」在乙下依然不成立，乙只是把物理上不可避免的窗口从对称的两种缩小成非对称的一种，代价是多了一道屏障（见第六节代价）。**

**这直接回答 J3 第二问**：I-7.7 字面「全或无」这句话本身，**不管选甲还是乙都要改**——不是「甲改条款、乙不改」这么简单：乙表面上说「I-7.7 字面不改」，但乙下依然存在真实的违例状态（1 个），如果 I-7.7 字面真的不改（继续要求「各盘实例代号相等」这一条硬性判定，不留材料里甲提的那个例外句），**乙下这唯一剩下的 1 个状态会被 I-7.7 判违例，而这不是一次假警报——它是真实的、需要恢复逻辑正确处理的情形**。乙如果真的「I-7.7 字面不改」，就必须在恢复/checker 之外另外单独处理这 1 个状态（比如在挂载准入时把它当成一种要特殊对待的失败），这其实是把甲要写的那句话（「不等时怎么判」）搬到了另一个地方去写，并没有省掉这句话，只是换了搁置的位置。**乙如果不给这句处置，材料里「I-7.7 字面不改」这句就会让唯一剩下的那 1 个真实可达状态在恢复时被硬拒绝——而这个状态本身并不是数据损坏，只是取号做了一半，拒绝挂载是一个比甲更保守但更粗暴的处置，第六节会给出这两种处置各自的代价。**

**构造「新条款判成立而实际错了的镜像」（J3 触发条款）**：这一步是检验甲提出的新 I-7.7 措辞（「各超级块实例代号相等，或不等时根环与 journal 里没有任何一条带着最大那个实例代号的根或记录」）会不会被一个真正损坏的镜像骗过去而判「成立」。构造思路：让根环或 journal **确实**带着最大那个实例代号的东西，但因为**另一处独立的损坏**（比如根环某个区域所在的设备当场打不开、或那一条记录的校验和恰好因为别的原因读不出来）而在这次挂载时**读不到**——甲的新条款字面上问的是「根环与 journal 里没有任何一条带着最大那个实例代号的根或记录」，如果实现这句话的方式是「扫一遍当前能读到的根环与 journal，没找到就判定为空」，那么**「找不到」和「真的没有」在读失败发生时是分不开的**，会把「有，但读不到」误判成「没有」，从而让这条新判据在一个实际上已经发生了危险写序复用的镜像上判「相等或安全」。

⚠️ **这一步是推理，不是本轮实际构造出的镜像**——层 0 装置里目前没有「让某个区域读失败」这种故障注入手段（`.claude/kb/decisions/22-单元原子性怎么合成.md` 的「方法论标注」那一段也写明本机的 `dm-flakey` 造不出撕裂，层 0 枚举同样没有「设备读失败」这一维），按 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「一个假设要能被观测否掉，否则它不是假设」，**这一条只能记成推理，不能当结论**：如果甲被采纳，它的新 I-7.7 条款正文必须显式排除「根环/journal 读失败」这种情形（例如要求「全部设备在线且可读」作为判据的前提，参照 C113 P2「回收的量词」那一条已经用过的写法：「那次清扫里没有任何一次读失败 ∧ 全部设备在线」），不能只写「没有找到」，否则就是本节构造的那个反例的形态。这一点应该作为甲被采纳时条款正文的一项具体要求写进去，不是否决甲的理由——因为这个「读失败 vs 真的没有」的区分问题，**丙同样躲不过**（丙的一次原子写如果落在某块暂时读不到的盘上，一样会被误判为「没写」），它不是甲独有的缺陷，是任何依赖「扫描后判定」的方案的共同缺陷，只是甲的条款措辞目前没有显式排除它，而丙的措辞材料里更简略、无法评估它有没有排除。

## 六、J4（判别力）：C322 要的自证形态在这两个可达状态上确实是等价变异，换过的形态在本轮里已经现查到

**J4 问两件事**：(a) C322 要的自证（把择超级块改成只看世代号不比实例代号，检查必须由绿转红）在各臂下构造得出吗；(b) 同一池两盘的世代号在已定写法下是不是恒同步——恒同步则那条变异与原式等价，自证要换形态。

**先答 (b)，它决定 (a) 的答案**。检查对象是 P6/本轮现查的那 2 个可达状态（第三节已证明这是「各盘实例代号不等」的全部）。在这 2 个状态里，**世代号与实例代号是否恒同步，要看写它们的是同一次操作**：`acquire_instance` 的 `RotateSuperblockSlots` 调用**在同一个结构体字面量里同时填 `slot_generation`（世代号，固定值 2）与 `journal_instance`（实例代号）**（`transaction.rs:124-137`：`let superblock = Superblock { ..., slot_generation, ..., journal_instance, };`），两盘各自要么这次写落地、要么不落地——**没有落地的那块盘，世代号与实例代号都停在 mkfs 留下的旧值（世代号 1、实例代号 0）；落地的那块盘，世代号与实例代号一起跳到新值（世代号 2、实例代号 1）**。⇒ **在这 2 个可达状态上，「按世代号高低选」和「按实例代号是否相等选」给出的判断完全相同（世代号高的那块盘就是实例代号新的那块盘）**——在这两个状态的范围内，世代号与实例代号确实恒同步，**C322 原句要的自证形态（把择超级块改成只看世代号，检查必须由绿转红）在这 2 个状态上是一条等价变异，不会翻红**：任何一个只看世代号高低来挑超级块的实现，在这 2 个状态上都会选中那块世代号=2 的盘，这与选中那块实例代号=1 的盘是同一块盘，判定结果不会有分别。

**但世代号与实例代号只在「取号那一刻」同步，往后会分道扬镳**：warm_up 每一轮的 `RotateSuperblockSlots` 调用把 `slot_generation` 换成 `superblock_generation_for_publish(txg) = checkpoint_txg + 2`（`transaction.rs:172-178`，每轮 +1），但 `journal_instance` 参数原样传的还是**取号时定下的那个实例代号，不再变化**（`transaction.rs:230-235`：`journal_instance: instance,`，`instance` 是整个 `warm_up` 函数的入参，循环内不改）。⇒ **暖机第一轮之后（第四段，段序列 `2+2+1+2...` 的第 4 段），世代号会继续往上涨（2 → 3 → 4……），而实例代号在同一次挂载内保持不变**——如果这一段（暖机第一轮的超级块槽写，段长 2）只落了一块盘，会出现「两盘实例代号相同（都还是同一个数，因为落后那块盘的实例代号是上一轮就已经追上的旧值，而这一轮两盘写的实例代号字面上没有变化）、但世代号不同」的状态：这时候「按世代号高低选」和「按实例代号是否相等选」**分道扬镳**——前者能分出谁新谁旧，后者会判定「两盘相等，没有问题」，实际上却有一块盘停留在一个**过时但实例代号仍然显示正确**的槽上（该盘的其它字段，比如 `journal_tail`，是旧值）。

⇒ **构造出的换过的自证形态**：把变异挪到暖机第一轮之后的超级块槽写（段序列里长度为 2 的第 4 段或第 5 段，不是取号那一段本身），验证「只看实例代号是否相等来判定两盘是否一致」这条规则会不会漏掉「世代号不同、实例代号偶然相同」这种真实分叉——**这条变异在这些段上不是等价变异**：世代号确实在分叉（一块盘持续推进、一块盘卡在旧值），而按今天 walk.rs 的 I-7.7 第一次判定（只比较 `journal_instance`），这类分叉会被判「一致，通过」，检查在这里会放过一个真实的分叉（两盘的 `journal_tail`、`slot_generation` 不同，只是恰好都还在同一个实例代号名下）。**这正是 C322 自证要求的「必须由绿转红」，只是要在正确的段上构造，不是在取号那一段本身**——取号那一段（第三节证明的那 2 个可达状态）是 C322 要求的自证形态的一个**等价变异区间**，换到暖机之后的超级块槽写才是一个**能分辨的区间**。这一点仓里此前没有记录，本轮读代码得出，属于对 C322 判别力自证部分的一条实质性补充：**C322 的检查形态若只覆盖取号那一段，会漏掉暖机及之后每一次超级块槽写都可能出现的「世代号分叉但实例代号偶合」情形**——这是三条臂共同要面对的问题（甲的新 I-7.7 措辞如果只比较实例代号也会漏掉它，需要额外要求世代号也纳入判据），不专属于任何一条臂，但因为甲已经在改 `choose_superblock` 的跨盘比较逻辑，顺手把世代号也纳入比较（本来 `choose_superblock` 的单盘内部选择就是按世代号，改成跨盘时自然可以同时带上世代号），代价比乙或丙另开一条判据要低。

- J4：本轮确认「C322 原句给的自证形态（取号那一段）确实是等价变异」，**这句「如实写出」已经在第六节做到**，并按要求给出了换过的自证形态（暖机之后的超级块槽写段）。

**失败条款**（材料原句）：「若 P6 的实测被证明口径错了（例如那 2 个状态里有一个根环或 journal 里已有实例 1 的东西），这一轮作废，先修层 0 的计数再来。」

本轮重新跑了一遍层 0 全量（第二节），`CHECKER_FIRST` 给出第一个违例状态是 `[1, 0]`（一块盘实例代号 1、另一块盘 0），第三节 (b) 已经从屏障的物理语义证明了「暖机记录已持久」这个组合在这 2 个状态所在的第一段结构下不可能同时出现——**没有发现根环或 journal 里已有实例 1 的东西与这 2 个状态共存**，失败条款不触发，这一轮的结论可用。

## 十、结论：取甲

**理由按权重排列**：

1. **J1 证明 C322 原句描述的检查对象本身不可达**（第三节），真正需要处理的只是「取号只完成一盘、且这就是整个崩溃点」这个更窄的情形——这正是甲的第二句直接处理的对象，乙、丙都没有比甲处理得更好（乙依然剩 1 个真实可达状态需要同样的判据，第五节）。
2. **J2 揭示的 `choose_superblock` 跨盘比较缺口，甲的措辞已经覆盖（第二句「跨盘取世代号最大的那一份」），乙完全没有涉及**——乙只改写入端时序，不改恢复端的选择逻辑，这个缺口在乙下原样保留，需要另开一笔账去补，等于乙实际要做的事比材料字面写的更多。
3. **J5 代价：甲 0 道新增屏障、不改格式、不用重跑 E142 与层 0 装置；乙 +1 道屏障且要重跑一整套干跑与层 0（段结构变了）、丙要改格式（材料自己标的参照臂，代价最高）**——在 J1、J2 两条已经不利于乙丙的情况下，代价差距进一步坐实甲是唯一合理的选择。
4. **J4 提醒的等价变异问题（第六节）与 J3 提醒的「读失败误判」问题（第五节），都不专属于甲**——前者是「检查覆盖区间选错了地方」的问题，与选哪条臂无关，换到暖机之后的超级块槽写段一样能验；后者丙同样存在。这两条不能作为反对甲的理由，只能作为**甲被采纳之后，条款正文需要补的两处具体要求**：① I-7.7 新措辞里的「根环与 journal 里没有找到」要显式排除「读失败」这种情形（参照 C113 P2「回收的量词」已经用过的写法：读失败发生时判定退化到更保守的那一支，不能把「读不到」直接当「没有」）；② 判别力自证不能只在取号那一段构造，要在暖机及后续每一次超级块槽写段上都能分辨「世代号分叉、实例代号偶合」这种情形，不能只比较实例代号。

**具体要写的东西（对应甲的两句 + 本轮两条补充）**：
- D23（journal 的角色与格式） 已定项 16 补两句（甲原句）：① 取号那两次超级块写之后不另加屏障，暖机第一次空发布开头那道屏障就是持久点；② 各盘实例代号不等 = 一次没做完的取号，择超级块跨盘取世代号最大的那一份，下一次取号取 max(全部超级块, 根环) + 1，且这句「没有找到」要在实现里显式区分「读失败」与「确实没有」（本轮补充①）。
- I-7.7 改写为材料给的那句（甲原句），并在判定实现（`walk.rs`）里补一次覆盖暖机之后超级块槽写段的判别力检验（本轮补充②），不能只在取号那一段自证。
