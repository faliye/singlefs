# C68 单元头收口·反推攻击腿（opus）原样输出（2026-09-02）

I verified every quote I relied on against the repo. Findings below; F-numbers refer to the background.

Item 1 (dropping block birth). The orphan case is a reachable break, but not where F12(c) looks. D18 settled item 5 grades rebuild by witness: allocation record plus checksum equals level 2 (writable), checksum alone equals level 1 (read-only mount). A block written and never published loses its allocation record with the transaction that died, so after any crash-then-rebuild it lands at level 1, and nothing in the 47-byte header distinguishes "abandoned by a torn transaction" from "live unit whose allocation record was corrupted". Block birth compared against the root's checkpoint_txg is exactly the field that separates them. Consequence: every crash-plus-rebuild yields a read-only volume with no promotion path.

The larger break: with birth only in the parent pointer, birth for live blocks lives only in derived state. D21 settles that the index is derived and losable; D5's opening line settles the opposite reading, "每个块自带诞生代号", and only D5's kill pseudocode says ptr.birth. After an index rebuild, birth is unrecoverable for every live block, so D5's kill rule input is missing. D5's own conservative default ("输入取不到时默认进 deadlist") then leaks every block into deadlists; the naive default frees blocks that snapshots still reference, which D5's own table labels data loss. I-3.5 and I-3.6 become unjudgeable. That is authoritative accounting depending on a value stored only in derived state, which contradicts D21's split directly.

On scrub (ii): I concede the mechanism. Under COW a modified child forces its ancestors rewritten, so pruning a subtree whose pointer birth is below the watermark is sound, and the walk touches only the changed frontier. But D13's resolution of conflict 1 requires two independent checker directions, traversal and scan, judging the same invariant; without a header field the scan direction can never judge I-1.2, so the independence collapses to one direction for that invariant, and incremental scrub is impossible on any volume whose index was just rebuilt.

On (iii): E59 does not cover metadata nodes. Its Unit carries kind 1 (live) or 2 (tombstone) with D18 item 3's five-tuple; its header comment states explicitly there is no "which write is this" field. No metadata node, no crash point, no encryption, one delete model. E59 also states in its own text that reusing its numbers for other conclusions still requires three-way argument; F12(c) reuses them without one.

Item 2 (two whitelists). Mechanically unworkable as worded. The unit type tag is the first element of the five-tuple, which (e) puts into ciphertext for metadata. The scanner must choose a whitelist before parsing, and the two headers differ in length, so it cannot even locate the checksum. Second, the metadata whitelist has no header checksum, and E86's interior-probe rejection is stated as magic plus header checksum, sized at 32 bytes; so (e) removes E86's only defense for exactly the 16 KiB class that forced 16 KiB stepping. Third, keyed rebuild of metadata now requires decrypt-then-identify, because the AAD fields sit inside the ciphertext being opened; that is a new exception to A6 that was accepted for data units in D18 item 3 and never for metadata. Fourth, F12(a) reserves no bytes for nonce epoch or MAC, while D9 item 10 settles that v1 reserves encryption format fields; turning encryption on would become a layout change, and D21 requires scan-rebuild to parse every historical unit format.

Item 3. The settled root record (D22 item 7) has magic, fsid, flags, instance number, checkpoint_txg, a table pointer, and a 32-byte self checksum: no five-tuple, no self address, no tree id. Giving self-certifying units rows under I-1 leaves I-1.1 and I-1.3 with no field; exempting them contradicts invariants.md's own note that I-1 extends from any metadata block to any unit. The honest form is an explicit exemption row justified by D22's 已定三 (whole-unit checksum plus checked generation plus slot rotation). Separately, (d) over-extends: D18 item 2 settles key ranges for the accounting tree only and says explicitly not to extrapolate, and "level" is only a candidate in D9 item 6. And (a) and (d) contradict each other in bytes: one 47-byte table cannot be both the five-tuple and (tree, level, key range), and obj_id, anchor offset and object birth have no meaning in an accounting-tree node.

Item 4 (fsid). The mount check covers device-level mixing only. D18's settled "已定要带的" row quotes XFS that a misdirected write can land on a valid block number belonging to another filesystem; that is sub-device, and no mount check sees it. Concrete case: a backup or VM image of a singlefs volume stored as a file. Its interior unit headers are genuine, pass magic and any unkeyed header checksum, and sit at an allocated drop point, so D18 item 5's level-2 witness passes and scan-rebuild ingests impostor identities as promotable. fsid is the only cheap discriminator. C74's own remedy has two halves and F12(b) keeps only the mount half; the scrub half, "本卷全部单元的归属都指向本卷", is unimplementable without a per-unit volume identity. Finally the settled root record already spends 16 bytes on fsid citing I-1.4; rescoping I-1.4 orphans that citation, and the root slot is precisely the unit where a superblock-based check is circular. Note also that F4 overstates: the fsid ruling lives in a section labeled "不是定案".

Item 5 (55 to 47). D21's 108 explicitly constitutes no upper bound, so no settled conclusion rests on it directly. But E58 hard-asserts PTR_BYTES == 108, and the byte-basis crossing share 0.0823 percent derived from it is the one number D4 item 1 says survives and is unit-pinned; it becomes 0.0762 percent. E43's mount thresholds 4040 and 131016 are size minus 55 minus 1 and are cited in settled D21 item 2; they become 4048 and 131024. Independent defect found: E58's read model adds all 108 bytes to G, while E43 states that 55 of the 108 live inside the unit and are therefore already in G. The correct per-unit extra is 53 and is unaffected by this change; rescaling 108 to 100 would carry the bug forward.

Also: the 4-byte header checksum contradicts the two settled 32-byte precedents (E23 header_csum, root self checksum) and E86's stated assumption.

Reachable breaks: birth loss destroying accounting after rebuild; orphans forcing read-only; (e)'s unparseable header and missing metadata checksum; foreign-image poisoning without fsid; the (a)/(d) byte contradiction. Costs only: nonce timeline attribution, E58/E43 renumbering, checksum width.

Recommendation: adopt with riders. Riders: keep block birth in the header, or move birth into authoritative state and say where; add a unit class tag to the common plaintext prefix and a header checksum to both whitelists; make the header checksum 32 bytes; reserve nonce epoch and MAC in v1; keep fsid, or replace it with a per-unit volume binding and write down the scan-rebuild claim rule that rejects probes interior to a claimed unit; write I-1 per class with an explicit exemption row for self-certifying units; make the field table per class and recompute E43, E58 and D4 item 1.

Cheapest check that would falsify me: extend E59's counting model with two fixtures, a nested foreign image inside a data extent and an orphan unit at an unallocated drop point, and see whether the 47-byte header classifies both correctly. If it does, my fsid and birth riders fall.
