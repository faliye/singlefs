## 场景一：叶容器分裂

步骤：

1. 容器 C1 现状：出生树 = T（inode 树的树 ID）、打包记录类型 = 2、容器号 = N、容器出生代 = G0、记录数 = 233、记录宽 = 140，字段表见 `.claude/kb/decisions/18-块里携带什么信息.md:598-611`。
2. 第 234 条记录（一个新 inode）要插入。P4 定 inode 号单调递增（`_d8-item6-r2-amended.md:56-57`），意味着新对象的 key 恒大于 C1 内现有全部 233 个 key ⇒ 插入点恒在 C1 的右端，这是尾部追加型分裂，不是随机点分裂。
3. C1 已满，触发分裂。分裂产出两个新容器（无论按 117/116 均分还是按「旧容器满员不动、新记录单开一个容器」的尾部优化切）——两种切法提案都没有选，是本项对提案的第一处补充。
4. 分裂后的容器身份：已定项 11 的「容器号...被 COW 重写时不变」（`18-块里携带什么信息.md:625`）说的是同一容器内容改写、身份不变；分裂改变的是哪些记录归哪个容器，是结构变化不是内容更新，两个产物容器都不是「C1 的延续」——都要向 (树 T, 类型 2) 的容器号分配器申请新号，容器出生代 = 本次发布的 checkpoint_txg。C1 本身退役。
5. C1 的处置：`18-块里携带什么信息.md:628`「旧版容器走普通 COW 释放路径，不写墓碑」——分裂视为一次容器级 COW 释放，不写墓碑，与 C7（核心索引结构）里 inode 记录是权威态第一项、容器索引本身是普通被 COW 结构的定位一致。这一步站得住。
6. 内部节点更新：P1 里容器索引就是这棵树的内部节点（`_d8-item6-r2-amended.md:33-34`），原来指向 C1 的一条条目（分隔 key + 容器身份 + 子指针）变成两条，内部节点 COW 重写一次；内部节点本身若也满（196 扇出）则继续向上分裂，是标准 B 树传播，提案没有在这里引入任何新问题。
7. 硬骨头：D18 已定项 11 的四条装载纪律里第二条「一容器一个代际」（`18-块里携带什么信息.md:634-637`）：这条纪律是把已定项 10 对墓碑定的规则（按代际装载、代际边界关掉开放单元，`18-块里携带什么信息.md:541-542`）推广到整个码 3，字面上覆盖记录类型 2。墓碑容器是只增不改的：一个代际内只追加死亡记录，代际边界一到就永久关闭，永不再碰——这正是「按代际装载」能把钉住量压到 0 的原因（E84，`18-块里携带什么信息.md:538`）。inode 容器不是这个形状：只要文件还活着，同一个容器就会被反复 COW 重写（改 mtime、改 size），跨越任意多个代际。若第二条纪律字面套用，每逢一次快照边界，所有当前开着、装着活跃文件记录的 inode 容器都要被强制关闭——而关闭之后，容器里剩下的、还没触发下一次修改的 232 条记录何去何从？纪律本身只回答了「墓碑」那种只追加、可以整批报废的载体，没有回答「被随机点更新命中、必须继续存在」的载体。字面套用的后果是：下一次任一记录被改，找不到属于新代际、能装下该 key 的开放容器（旧容器已被强制关闭且不许再碰），要么被迫为这一条记录单开一个新容器（容器数爆炸，扇出与 F28 的读写代价模型全部作废），要么被迫把该容器持有的全部 233 个 key 重新做一次「未分裂式」COW（等价于每次快照都重写全部活跃 inode 容器，代价没有量过，且与 F28 引用的 E103 更新代价模型不是同一件事）。
8. 装载纪律②的设计初衷是给墓碑一个「代际过完就能整批回收」的边界（`18-块里携带什么信息.md:635`「只在回收判定时用，扫描重建不用」）——inode 容器没有「代际死亡」这回事，它的死亡由 `deleted_inodes`（对象整体删除）另行处理（`08-核心索引结构.md:263`），与墓碑靠代际回收是两条完全不同的生命周期。

判决：打中。四条装载纪律里的第二条对记录类型 2 不成立，或者说它服务的目的（按代际批量回收）对活跃更新的记录天然不适用。提案 F25 把「四条装载纪律」整体引给码 3（`_d8-item6-r2-amended.md:19`），P1 正文却完全没有讨论这条纪律对 inode 叶容器意味着什么——需要在 D18 已定项 11 里给记录类型 2 显式开一条例外：inode 容器不受装载纪律②约束，跨代际保持开放，直到分裂或整体删除才关闭；容器回收改走普通 COW 释放（本场景步骤 5 已确认这条本身没问题），不走「代际边界强制关闭」。这不是本项凭空提出的新问题，是提案自己援引的条款字面上打不到自己头上。

## 场景二：崩溃在「新叶容器已写、内部节点已写、根未发布」

步骤：

1. 崩溃前盘面：旧叶容器 C_old（诞生代号 g_prev ≤ 上一次成功发布的 checkpoint_txg，被当前已发布根引用）；新叶容器 C_new 与新内部节点条目 P_new（诞生代号 g_new = 本次未完成事务的 checkpoint_txg，g_new > 已发布根的 checkpoint_txg）；根槽未写，journal 记录若有也未构成一次完整事务终结。
2. I-1.2（`.claude/kb/invariants.md:21`）：任一单元诞生代号超过根记录当前 checkpoint_txg，必是未发布撕裂垃圾。C_new、P_new 的诞生代号严格大于挂载后读到的 checkpoint_txg，扫描方向据此独立判定它们是垃圾——这正是 D18 已定项 7 给诞生代号翻回头里的第二条理由（`18-块里携带什么信息.md:428-431`）。这一步和 inode 打包路是不是路①/路②无关，是通用崩溃恢复机制，提案没有破坏它。
3. 挂载恢复：D23 已定项 1 甲「每次 fsync 写脏叶 + 全部祖先 + 根槽 + 一条记录」（`23-journal的角色与格式.md:280-281`）。本场景「根未发布」意味着这次 fsync 序列没有走完，journal replay 找不到一次终结完整的事务记录，恢复后当前根仍指向发布前的旧状态——即仍指向 C_old。
4. 旧叶 C_old 的处置：它仍被当前（唯一有效的）根引用，是活对象，不进 deadlist、不被释放。释放条件（D5 deadlist / D3 已定项 1 谓词，`03-空间分配.md:43-59`）要求「该落点分出去了但不属于现行版本」，C_old 恰恰属于现行版本，不满足释放条件——这一步与 inode 打包路无关，是任何 COW 树崩溃恢复都成立的通用结论，提案没有额外开销或额外风险。
5. C_new、P_new 占用的空间怎么回收：这是本场景里 kb 没有正面回答的一处，但它是通用事务层的欠账，不是 D8 未定项 6 专属的。分配记录（D3 已定项 1）会显示这两个落点「已分配」，但它们既不在当前根的引用集合里，也没有被任何快照引用过（因为从未发布），既不满足 D3 的「属于现行版本」也不落进任何快照的 deadlist——现有决策文本里没有第三种「从未发布过就废弃」的显式回收路径描述，只在 D18 已定项 7 里确认了「怎么识别」，没有确认「识别之后谁来释放」。这个空白与本提案是否选路①或走 P1 无关，是崩溃点重放与事务层要还的账，本项不为它记打中，只记录它在这条路径上依然存在。
6. inode 号水位统计量：它是记账树的一条幂等完整值（D5 已定项 1，`05-快照-空间记账机制.md:75-82`），随同一次发布走同一个 COW 事务，即它与 C_new、P_new 共享同一个根发布屏障。若这次失败事务里曾把水位从 5 临时推进到 6（为了给新文件分配 inode 5），因为根从未发布，磁盘上仍是旧水位 5，重启后下一次成功的事务会再次分配到 5。
7. 这是否与「不复用」矛盾：不矛盾。F24/P4 的「单调不复用」管的是已发布、曾经进入过可观测历史的号；一次从未发布的失败事务，从任何外部可观测的角度看等同于从未发生，inode 5 从未真正「被分配给一个存在过的对象」——水位统计量与叶容器写入共用同一个原子发布屏障，两者一起生效或一起作废，这正是保证「重发同一个号是安全的」的机制来源，而不是巧合。这一点提案本身没有写，但它是可以从 D5 已定项 1（水位是记账树的普通条目，跟着根发布走）与 D16/D23 的发布屏障机制直接推出的，值得作为 P4 的补强正面写进去。

判决：站住，但要补一句。核心的「重发同一个 inode 号不违反不复用」这条结论是对的，依据是水位统计量与叶写入共享同一个 COW 发布屏障（D5 已定项 1 + D16 已定项 6 + D23 已定项 1 甲），提案没有把这条依据写出来，应当补一句显式论证，不能只让读者自己拼。C_new/P_new 的空间回收缺口是通用事务层欠账，不因本提案而生也不由它解决，如实记录，不计入判决。

## 场景三：扫描重建内部节点

步骤：

1. 扫描收集全部单元类型标签 = 3 且打包记录类型 = 2 的容器，每个自带（出生树、容器号、容器出生代、记录数、记录宽、诞生代号、fsid、载荷校验和）。
2. 分组键必须是（出生树, 容器号, 容器出生代），不能带诞生代号——诞生代号在已定项 11 里明确是「只记这一次写」（`18-块里携带什么信息.md:609`），同一逻辑身份每次 COW 重写诞生代号都不同，把它并入分组键会让每次物理重写都单独成组，根本找不出「同一身份的多个物理版本」，这正是接下来「择新」步骤要处理的对象。若照场景题面原样把诞生代号并进分组键，分组这一步本身就会把问题消解掉（永远只有一个候选），这是一处需要先纠正的建模错误，纠正之后才谈得上择新。
3. 同一身份出现多版物理容器的原因有二：同头内反复 COW 重写（同一逻辑容器，代际跨度可能很长，见场景一）；跨版本残留（分裂后旧容器 C1 已重新分配新号退役，不会与新容器 C2/C3 撞同一身份——因为分裂产出的都是全新容器号，见场景一步骤 4）。所以同身份多版的成因主要是「同头反复更新」，不是分裂。
4. 择新规则：已定项 11 明文「不按诞生代号择新...按『属不属于某个头的现行版本』这个谓词判（D3 已定项 1 是它的权威记录点），两版可以同时属于不同的头」（`18-块里携带什么信息.md:628-629`）。
5. 但这个谓词在扫描重建那一刻的输入是什么：C113（`.claude/kb/checks-owed.md:120`）逐字——谓词的两半是分配记录（派生态，`21-权威态与派生态的分界.md` 已定项 5）与 deadlist，而分配记录正是被重建的东西，是循环依赖；E59 乙臂的「记账」在源码里是一个 `live: bool` 神谕，不是机制。C113 是全仓已登记但未解的欠账，射程覆盖全部码 3（不只是 inode），提案 F25 把四条纪律与择新规则整体继承过来，却没有在 P1-P8 任何一处提及 C113、更没有为 inode 树给出任何补充线索。
6. Key 范围重叠的具体情形：设想一个头曾在某个快照点之前对容器做过一次分裂（旧容器 C_old 覆盖 [1,233]，分裂产出 C2 覆盖 [1,117]、C3 覆盖 [118,233+新记录]）；若那个快照点之前的版本仍被某快照引用，扫描会同时找到 C_old、C2、C3 三个不同身份（容器号不同，不是同一身份的多版本，参考步骤 3），它们的计算 key 范围确实相互重叠（C_old 与 C2、C3 的范围有交集），但这是合法的——C_old 属于旧快照头，C2/C3 属于当前头，重叠是同一段 key 空间在不同时间点分别归两个不同头所有的正常结果，不是错误。判定「这一版归哪个头」正是步骤 5 那个谓词要回答的问题，而它现在拿不到输入。
7. 内部节点本身怎么重建：P1 的说法是「内部节点丢了从叶重建（叶容器的记录里有 inode 号 ⇒ 每叶的 key 范围可算）」（`_d8-item6-r2-amended.md:36`）。这句话把「计算每叶的 key 范围」说得很轻，但重建一棵内部节点索引真正要做的不是「算出每叶的范围」，是「先分清楚哪些叶属于当前要重建的这个头，再用它们的范围拼出索引」——前一半正是 C113 卡住的地方。P1 这句话把容易的一半（key 范围怎么算）当成了整个重建故事，绕开了难的一半（先择新）。

判决：打中，但不是新问题——是 C113 这条已登记欠账的一次新实例。提案在 P1（`_d8-item6-r2-amended.md:36`）与 P8 的下游表（`_d8-item6-r2-amended.md:98`）都没有点名 C113，给读者的印象是「内部节点丢了照样能重建」，而重建能不能站住取决于一个提案没有触碰、kb 里明确写着「无输入」的谓词。建议 P1 那句话明确改成「内部节点重建依赖 C113 的择新谓词，本项不解它，与墓碑容器同一格」，并把场景题面里「按 (出生树, 容器号, 出生代, 诞生代号) 分组」的措辞连带修正为不含诞生代号。

## 场景四：克隆头

步骤：

1. D6 已定项 1（`06-快照实现模型.md:146`）：每头一棵自己的树。克隆头从 origin 复制树，物理上是 COW 共享——克隆那一刻，clone 头的 inode 树内部节点是 origin 内部节点的逻辑拷贝，两棵树（不同树 ID）的条目暂时都指向同一批物理叶容器。
2. inode 号水位是按（统计量类型, 树 ID, 设备, 代）分的记账条目（P4，`_d8-item6-r2-amended.md:58-59`）。clone 头的树 ID 是全新分配的，若这条水位记录按新树 ID 的默认初值起步（例如从 mkfs 常见的初值 2 开始），它会立刻与 clone 头已经继承自 origin 的、真实存在的 inode 号（可能已经到几十甚至几百）相撞——新建文件会尝试分配一个 clone 树里已经存在的号，直接撞 (树, inode) 唯一性。
3. 这与 D6 已定项 1 连锁触发表里第 2 条完全同构（`06-快照实现模型.md:203`）：「新克隆的 `prev_snap_txg` 必须初始化为 origin 快照的 txg（置 0 会丢数据）」。inode 号水位需要同一条纪律：克隆头的水位初值必须继承 origin 在克隆点当时的水位，不能取新树的默认起点。提案 P4 完全没有提这一步，是一处结构性遗漏，而且恰好是同一条决策（D6 已定项 1）已经点名过的同类坑,只是没人把它接到 inode 号水位这条新记账统计量上。
4. 容器出生树的问题：已定项 11 里码 3 的树维「取出生树」（`18-块里携带什么信息.md:569`），与 I-1.3（`.claude/kb/invariants.md:22`）「打包记录单元与被快照共享的数据单元头里的树 ID 是出生树，跨头共享时与引用树不同」吻合——克隆刚发生、尚未写入时，clone 头内部节点条目指向的物理容器，其头部出生树字段仍然是 origin 的树 ID，这是已知且允许的合法跨头共享形态。
5. clone 头修改一条记录时要 COW 整个容器：这是一次真正的新写，不是继承——新容器由 clone 头的事务产生，出生树字段应当写 clone 头自己的树 ID（不是 origin），容器号也要向 (clone 树 ID, 类型 2) 这个全新的（此前不存在）容器号命名空间申请全新的号，从头计数——因为容器号分配器按 (树, 类型) 独立记账（C103，`.claude/kb/checks-owed.md:110`）。提案 P1/P4/P7 都没有讨论克隆头 COW 共享容器这一步该怎么走。
6. 更硬的一处：P1 的内部节点条目结构是「分隔 key 8 + 叶容器身份（容器号 8 + 出生代 8）+ 子指针 59」（`_d8-item6-r2-amended.md:32`），没有出生树字段。克隆之后，同一个 clone 头内部节点里，有的条目指向未修改过的共享容器（出生树 = origin），有的条目指向已经被 clone 头 COW 过的新容器（出生树 = clone 自己）——若条目本身不携带「期望的出生树」这个声明，读者按 A6（AAD 期望值不来自明文侧，只能来自查找路径）取 AAD 期望值时，靠什么知道这一条该期望 origin 还是该期望 clone 自己？
7. E90（`.claude/kb/experiments/90-树ID进AAD与跨头共享.md:41,52-56`）已经实测过这个确切问题：把 AAD 期望树维取「读者当前所在的树」（`reader_tree` 臂）在合法共享读上失败 4/6；唯一两条判据全过的臂是 `ancestry_birth`——指针必须携带 (出生树, 出生 txg) 声明，读者先用克隆祖先表验收声明再据此构造 AAD 期望值。这个机制已经实测成立，但已定项 11 与 E90 自己都写明「格式含义记进正文，不当场立决策」（`90-树ID进AAD与跨头共享.md:57`）——即它还没有变成任何一条已定分项。P1 的内部节点条目结构（容器号 8 + 出生代 8，没有出生树声明字段）与这条已经验证过的机制不兼容：少了声明字段，clone 头的内部节点在跨头共享期间没有办法正确构造 AAD 期望值。

判决：打中，且是本项最硬的一处。两条具体缺口：一，inode 号水位在克隆时必须显式继承 origin 的当前值，不能按新树默认初始化，这是 D6 已定项 1 连锁 2 已经点过名的同类坑，提案没有接上。二，P1 的内部节点条目结构缺一个出生树声明字段，与 E90 已经实测验证、专门解决跨头共享 AAD 期望值问题的机制（出生 (树,txg) 进 AAD + 克隆祖先表验收）不兼容——这不是提案可以留白的地方，因为 F24（D6 已定项 1）本身就是提案自己援引的先例，克隆头必然会走到这条路径。条目结构要么显式加出生树字段，要么提案要说清楚 inode 树为什么不需要 E90 的机制（本项没看出这条路）。

## 场景五：根直接指向叶容器

步骤：

1. 第一个事务只有一片叶时，树表条目 / 根记录的指针直接指向一个码 3 单元，不经过码 2 内部节点。D19 的指针结构（`19-块指针的结构与宽度预算.md` 开头段）本身不携带目标单元的类别字段——指针的头部字段是 nonce/MAC/算法类型/extent 偏移，位置条目是设备 ID + 物理偏移 + 密文校验和，两段都不含「目标是码几」这一位。这一点提案「D19 的指针不分类」（`_d8-item6-r2-amended.md:41`）核实成立。
2. 读者拿到指针后取回目标单元，第一步永远是读共同前缀偏移 6 的单元类型标签（已定项 11，`18-块里携带什么信息.md:585`），按标签值分派解析——见到 3 就按码 3 的类身份段解，见到 2 就按码 2 解。只要遍历代码按标签分派而不是硬编码假设目标恒为码 2，这条路径没有结构性障碍，是标准 B 树「根即叶」写法的自然延伸。
3. 但 I-1.1（`.claude/kb/invariants.md:20`）的展开文字只显式写了两种情形——数据单元的类内身份是五元组，索引节点是「树 ID + 层级（+ key 区间）」——没有第三句明确码 3 打包记录单元的类内身份检查该对照什么。已定项 11 的类身份段本身给出了码 3 的身份（出生树 + 类型 + 容器号 + 容器出生代等），I-1.3（`invariants.md:22`）也明确覆盖码 3 的树 ID 一致性检查，但 I-1.1 字面没有把「父级期望的容器号+容器出生代 == 该容器自己头里声明的容器号+容器出生代」这条类内身份比对写成一条独立分句。这是文字覆盖的空隙，不是机制空隙——机制上，父项（树表条目 / 内部节点条目）本来就该拿自己记的容器身份去和读回来的容器头比对，这与 I-1.1 对码 2 的做法是同一形状，只是 I-1.1 目前的措辞没有明写第三种单元类。
4. 从一片叶长到两片叶（即场景一的分裂事件）：那次事务写出两个新叶容器 + 一个新码 2 内部节点（层级取紧邻叶的那一层，两条条目分别指向两个新叶）+ 更新树表条目的指针（从直接指向码 3，改成指向新内部节点，指针字段格式不变，只是目标物理地址与目标单元类别变了）+ 记账树多写一条被本次 COW 波及的账目更新（如果记账不受这次事务影响可以不动，视具体实现）。这与场景一步骤 3-6 是同一事件，不重复展开。

判决：部分打中。「指针不分类」「读者靠单元自身的类型标签分派」这条机制成立，站得住；但 I-1.1 的现有文字没有明确把码 3 的类内身份比对写进条文，这是随本提案（把已定项 11 的码 3 单元第一次真正用作某棵树的常规叶节点）暴露出来的一处文档缺口，应当在 I-1.1 补一句第三分支：「打包记录单元的类内身份是（出生树, 打包记录类型, 容器号, 容器出生代），与引用它的父项所持有的期望值一致」，否则 I-1.1 字面上仍只覆盖码 1/码 2，checker 实现时容易漏掉码 3 作为树叶被引用这一种情形的检查代码。

## 场景六：内部节点不缓冲消息

步骤：

1. D11 已定项 6（`11-索引节点要不要留消息缓冲区.md:237-247`）逐字「全部布局共用 ε = 0.65，不按布局分支」，依据引的是 D14 已定项 4 否掉「持久/临时」这一个候选分支变量（`.claude/kb/decisions/11-索引节点要不要留消息缓冲区.md:241-242`），从未讨论过「按树种类分支」这个轴。D11 通篇讨论的分支候选只有 D12（目标介质）的按布局分支（`11-索引节点要不要留消息缓冲区.md:110`「前置 1」）——也就是说，已定项 6 否掉的是「按布局分支」，射程是介质/格式线这一维，不是「按树」这一维。提案把「inode 树 ε=0」写成「对 D11 已定项 6 的一条按树例外」（`_d8-item6-r2-amended.md:37`），这是在一个此前从未被评估过的新维度（树种类）上开一条分支，不是对已定项 6 现有判决的局部推翻——两者不是同一件事，提案的措辞把后者读成了前者，混淆了射程。
2. 「按树种类分支」要不要过 `.claude/rules/fs-design.md` 的五条硬要求：判据显式可计算（树的角色——是不是 inode 树——是静态、mkfs 之后不变的，可计算）；能被测试强制进入（需要一个只供测试用的开关，能无视自动判据直接把某棵树的 ε 摁成 0，提案未提供）；每条分支单独验，包括崩溃点重放（提案没有单独给 inode 树的 ε=0 分支设计崩溃点重放用例，只谈了它不会丢消息这一半）；分支必须可观测（运行时能看出这个节点走的是哪个 ε，提案没有说这个观测点落在哪）；分支变量操作中途不许变（树的角色天生稳定，这条自动满足）。五条里三条提案没有走。
3. 「inode 树 ε=0」在格式上怎么表达：先要确定 ε 是不是格式层面的硬分区。E56（`11-索引节点要不要留消息缓冲区.md:154-156`）把 ε=0.65 描述为「扇出 F=119、缓冲 B=665 条，两者争同一块 16 KiB 节点字节」——这是把节点的固定字节预算按比例切成两段固定容量（entries 段与 buffer 段），是设计时定死的静态划分，不是每个节点各自声明一个可变的划分点。已定项 7 给出的码 2 类身份段字段表（树 ID + 层级 + key 区间 + 诞生代号 + fsid）里没有任何字段声明「这个节点的 buffer 边界在哪」或「这个节点用的是哪个 ε」——也就是说，节点自身不自描述这个划分点，划分点是外部（写路径策略/mkfs 常量）决定的。若 inode 树的内部节点在物理布局上用不同的 ε（entries 段与 buffer 段的字节划分点不同），而节点头里没有任何字段能告诉读者这是哪个划分，读者必须靠外部知识（这个树 ID 属于哪棵树、这棵树是不是 inode 树）才能正确切开节点的 entries 段与 buffer 段——这份外部知识在正常挂载路径下来自树表（能查到树的种类），但树表条目本身没有种类字段（提案 P2 自己承认，`_d8-item6-r2-amended.md:45-46`：「树 ID 的分配与编码规则全仓无落点」），而在扫描重建路径下（场景三）树表可能根本不在。
4. 反过来想，若 ε 不是「静态字节划分」而是「节点自己声明本节点当前放了多少条 buffer 消息，entries 段与 buffer 段的边界由节点自己的一个计数字段决定，只要不超过节点总容量即可」——这种自描述形态下，ε=0 只是「这个节点从不写入任何 buffer 消息」的运行时行为，不需要任何格式字段区分它与 ε=0.65 的节点，因为两者的字节布局解析方式完全相同（都是先读 entries、再读 buffer 计数、再读 buffer 内容，buffer 计数恰好为 0）。E56 的实验模型（`11-索引节点要不要留消息缓冲区.md:154-156`「F=119, B=665 两者争字节」）读起来更像是「设计时预算切分」，但 kb 里没有一处明确回答「这个划分在格式上是否需要显式表达」这一问，是提案没有回答、也没有查过的空白。
5. 「会不会丢」的推理：内部节点走 COW 发布，崩溃不丢，因为未发布的都被 I-1.2 判成垃圾——这条对，与 ε 取值无关，是所有已发布单元的通用保证。丢的情形只有「索引整个被丢弃、走扫描重建」——此时缓冲里的消息如果算不回来，就是硬约束 6（`21-权威态与派生态的分界.md:342-344`）禁止的形状；这正是 D11 已定项 4 判「不扩项」的依据（E59 四类重算源 `11-索引节点要不要留消息缓冲区.md:212-217`）里没有覆盖 inode 类消息，第一轮反推腿已经打中这一条（`d8-item6-r1-opus-output.md` 1.6：「一条停在 inode 树内部节点缓冲里的 inode 更新...是一个算不出来的权威值住在一个可重建容器里」）。提案用 ε=0（内部节点永不缓冲任何消息）正面回应了这条打靶——没有消息，就没有算不回来的权威值住进可重建容器这回事。这条推理本身成立，是提案对第一轮最硬两处打靶（1.6+1.7）之一给出的直接修法，逻辑闭环。

判决：部分打中。「更新直达叶容器不会丢」这条正面推理站得住，是对第一轮硬伤的有效修复。但「这是对 D11 已定项 6 的一条按树例外」这句话本身把射程从来没被评估过的一个新维度（按树分支）轻描淡写地写成了对已有判决的局部调整，且没有走 fs-design.md 分支硬要求的可测试进入、崩溃点重放、可观测这三条；更关键的是 ε=0 在格式上到底需不需要显式表达，取决于节点内部是不是自描述边界，这一点提案没有查、kb 里也没有既有答案，需要先确认这一点再谈「按树例外」的格式代价是不是零。

## 场景八：locality 对照不变量

样本与判定：

1. 样本甲：extent 树未重建、记录被单个位翻转（例如 inode 1 的 locality_id 字段中一个比特被静默改坏）。checker 走 P6 第 2 条：记录里的 locality_id 与该对象每条 extent key 首段比对——extent 树是正常派生态、未经重建，它的 key 首段是独立写入的，与被翻转的记录字段之间没有共享来源。两者不等，checker 判红。这条判别力此前已由 E98 判据 3 实测过（第一轮反推腿 6.2 引用，`d8-item6-r1-opus-output.md`「带对照臂抓 1000、静默 0」），第二版没有改变这条机制，仍然成立。
2. 样本乙：extent 树已重建（即经历过一次全盘扫描重建，重建时按 P6 第 2 条「以记录里的值为准放回数据单元」）。此时 extent key 首段是从记录里抄过去的——两侧同源。checker 再拿两侧比对，本质是拿记录跟记录自己比，任何记录本身携带的错误（哪怕从一开始就写错了 locality_id）在重建之后永远不会被这条不变量抓到，因为对照的另一侧已经变成了它自己的复制品。checker 在样本乙上不会判红，即使记录里的 locality_id 从来就是错的。
3. 提案自己在 P6 第 2 条已经写了这句话（`_d8-item6-r2-amended.md:82`「只在 extent 树未经重建时有判别力；重建后...两侧同源，不判红」），这是对第一轮反推腿 6.1/6.2 打靶的正面修正，方向正确，比第一版更诚实。
4. 「射程」写成不变量条文的具体写法：现有 P6 第 2 条的写法本身已经是叙述句而非纯提醒句——它给出了明确的判定条件（extent 树未重建时判别，重建后不判别），这一点满足「会失败的检查」的最低要求，因为「extent 树是否经历过重建」是一个可以从 map_provenance（`18-块里携带什么信息.md:326`，D18 已定项 5）读出来的持久状态，不是一句空话。但要真正落成 invariants.md 里的一条，还差两步：第一，locality 这个词目前在 invariants.md 里零命中（现查 `grep locality .claude/kb/invariants.md` 无结果），这条不变量今天完全没有在权威清单里登记，P6 第 2 条只存在于这份未定案的提案文本里；第二，射程条件要写成可执行的谓词而不是散文，例如：「若 map_provenance.rebuilt == false，则对每个对象，记录里的 locality_id 必须等于其全部 extent key 首段；若 map_provenance.rebuilt == true，本条不评估，checker 必须显式跳过并计入『不可判定』而不是『通过』」——最后一句「不可判定」与「通过」的区分是关键：如果 checker 在重建之后单纯不跑这条检查，判定结果会被外部读成「绿」，容易被误读成「这条不变量成立」，而实情是「这条不变量在这个状态下压根不构成检查」，两者对使用者的意义完全不同,必须在 checker 输出里显式区分。

判决：打中一半。P6 第 2 条本身对「重建后判别力消失」这一点的认识和写法已经站得住，是第二版相对第一版的真实改进；没做到位的是这条不变量至今没有进 `invariants.md`，且现有措辞没有把「不可判定」和「判定通过」两种结局分开写——按现在的写法直接搬进 invariants.md，容易被 checker 实现者读成「重建后自动通过」而不是「重建后这条检查应该显式跳过并标注」，两者在审计意义上是天差地别的。

## 总判决

七个场景走完，外加场景八，逐条判决：

| 场景 | 判决 |
|---|---|
| 一 叶容器分裂 | 打中：装载纪律②（一容器一个代际）对记录类型 2 不成立，需显式开例外 |
| 二 崩溃在根未发布 | 站住（重发 inode 号安全的依据要补写），但空间回收是通用事务层欠账，不计入本项 |
