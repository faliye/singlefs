## 提案一：D8（核心索引结构） 未定项 6（inode 记录的盘上字段表）

**用户裁决：取「甲」——inode 记录住进单元。**

### 它先答的是态别，不是字段

D21（权威态与派生态的分界） 已定三条边界：**权威态 = 单元 + 记账 + 根；索引是派生态；不设兼容通道**，
并写死判据：一样东西若不能只从权威态重算出来，**它已经事实上晋升为权威态，权威态必须扩项**。

而 `size / mtime / mode / uid / nlink` 从「单元 + 记账 + 根」重算不出来——
D18（块里携带什么信息） 已定项 3 的五元组是
`(单元类型标签, 树 ID, 对象 ID, 对象出生代, 锚点偏移)`，一个属性都没有。
D18（块里携带什么信息） 正文自己也写着「一旦 inode 记录丢了，扫描找到的数据单元放不回去」。

### 提案的形态

1. **inode 树的叶节点是索引节点单元**，按 D18（块里携带什么信息） 已定项 7 的索引节点类头走
   （共同明文前缀 42 字节 + 类身份段）。
2. **inode 记录是叶单元里的一条 value，不是独立单元**；类型标签、校验和、格式版本、声明长度
   四样都由**节点头**承担 ⇒ **扫描单位是节点不是记录**，这一句要明写进定案。
3. **权威态定义不扩项**：inode 树的叶单元本身就是「单元」，扫描认领得到、单独解读得出；
   树的**结构**（内部节点、排序）仍是派生态，可重建。
4. **inode 树的节点不带 key 区间**（与 D18（块里携带什么信息） 已定项 2 对记账树的处置不同），
   理由是每条记录自带身份段，放得回去，不必靠节点的区间。
5. 字段表（初值）：

```
身份段   locality_id 8 · inode 8 · 对象出生代 8          ← 与 key 重复，key 权威、记录只作对照
属性段   mode 4 · uid 4 · gid 4 · nlink 4 · size 8
         blocks 8 · rdev 8 · atime 12 · mtime 12 · ctime 12
         改动计数 8（取值 = 产生它的那次发布的 checkpoint_txg）
预留     32，配一条「不认识的 flags 位一律致命」
```

6. **inode 树的 key 里留一段「头判别位」，第一版恒 0**（多可写头下同一个 inode
   在不同头有不同的 size / mtime / nlink，而一棵按 key 索引的树对一个 key 只存一个值）。
7. **`locality_id` 要一条对照不变量**：记录里那一份与每条 extent key 的首段必须相等，
   不等判红且不许静默修复（对不上的后果是**静默读空洞**，不是 EIO）。
8. **第一版没有父目录时 `locality_id` 取什么**：取 0，作为保留值。

### 三处不是自由选择，是被已定条款逼出来的

| 字段 | 逼它出来的条款 |
|---|---|
| `locality_id` | 已定项 3：数据 key 是 `(locality_id, inode, offset)`、改名永不更新；命名树 value 只有 inode ⇒ 读者拿不到首段 |
| `blocks` | D4（校验和位置） 已定项 2 把短 extent 补齐到 32 KiB（1 KiB 文件占 32 倍）⇒ `size` 推不出占盘量，checker 分不清合法稀疏与灾难性丢失 |
| 改动计数取 `checkpoint_txg` | 它天然单调、天然带提交锚（没提交过的版本不可能有号）|

## 提案二：D8（核心索引结构） 未定项 7（write buffer 条目自带的 `seq`）

**用户裁决：`seq` 是 write buffer 那个 keyspace 的字段，不是记账条目的字段；
宽度 8 字节；取值 = 产生它的那次发布的 `checkpoint_txg` + 窗口内序号。**

三问一次答完：
- **住哪**：write buffer 的条目里。去重发生在 flush 时的排序合并，**合并完之后进记账树的是胜者，
  同 key 只有一条** ⇒ 目标树不需要这一段，D5（快照 / 空间记账机制） 已定项 5 那五段是完整的。
- **多宽**：8，与 `checkpoint_txg` 同宽同值域。
- **跨挂载单不单调**：**单调，而且是白拿的**——`checkpoint_txg` 按 D16（发布语义） 已定项 6
  每次发布加一、永不回退。挂载归零那个失败模式在这个取法下不可能发生。

绕开的两条已知代价：进 key 会把 D5（快照 / 空间记账机制） 已定项 2 的「丢一代是点删不是扫描」
变成区间删；进记账条目的 value 会让排序契约不表达在 key 编码里，而
D15（格式冻结政策） 第 3 层冻的正是 key 编码。

⚠️ **一条前置**：D8（核心索引结构） 把 seq 叫「**这是格式要求**」，这句话意味着
write buffer 的条目是**落盘**的，否则谈不上格式。仓里没有一处明写这件事。

## 提案三：D22（单元原子性怎么合成） 未定项 9（超级块的字段表）

**用户裁决：按「谁能改它」分三段。**

| 段 | 装什么 | 谁能改 |
|---|---|---|
| 一 自举头 | magic · 格式版本 · incompat / compat_ro / compat 三档位 · fsid · **本盘 dev id** · 槽世代号 · 整单元校验和 | **永不改**。定长、位置固定 |
| 二 几何 | 设备描述符表 · 节点 16384 · 单元 32768 · **落点粒度 16384** · 位置条目段宽 · journal 几何（环大小 / 最大记录字节 / 在飞上限）· 根环 R=3 与 S · 树表（开放列表）| **mkfs 定，挂载只读** |
| 三 可调值 | `T_time` · `T_dirty` · 整理的三个水位 | **随时可改，改了不改格式** |

分段判据一句话：**凡是「写死在代码里就只能重建文件系统」的量必须在段二**。
先例：D23（journal 的角色与格式） 逐字要求「journal 几何进超级块，不许是代码常量」；
D16（发布语义） 已定项 5 逐字「`T_dirty` 是可调值，不是格式常量：超级块里那个字段是格式，
字段里放什么数不是」。E97（记账与分配记录的条目编码） 刚定的**落点粒度**正是段二那一类，它今天没有落点。

两条不是自由选择：
- 超级块槽不走 D18（块里携带什么信息） 已定项 7 那张表（已定项 7 明写自证单元豁免），
  但按 D22（单元原子性怎么合成） 已定三**必须**带整单元校验和 + 被实际检查的世代号。
- **本盘 dev id 要在自举头**：D12（目标介质） 已定项 4 定 dev id 错配拒绝挂载，
  而那个判定发生在还没读到设备表之前。
