1. Moving an object into a container without re-encryption violates the nonce reuse rule. The original unit and the new slot in the container both contain the same nonce during the transition period before the original unit is freed. For example: write object X to unit A with nonce N. Then copy X’s ciphertext and N to slot S in container C. Before unit A is freed, both A and S exist on disk with nonce N. An attacker observing both units can XOR the ciphertexts to recover the XOR of the plaintexts, breaking AEAD security. This is a concrete failure, not aesthetic, as it leaks plaintext information. The invariant forbidding nonce reuse is violated during the overlap.

2. A single bit flip in the container’s directory header can corrupt all slots. For instance, flipping one bit in the 4-byte slot count field could cause the scanner to interpret an invalid number of slots (e.g., 0xFFFFFFFF), leading to out-of-bounds reads or crashes when scanning any slot. To confine this to one slot, the directory would need per-entry checksums or redundancy (e.g., CRC for each offset/length field), increasing storage overhead by ~25% for 32-bit CRCs per entry, which contradicts the "no outside input" claim by requiring extra metadata.

3. Two containers can claim identical slot identities. Suppose container C1 and C2 both hold object X with tree ID T, object ID O, birth generation G, and anchor offset A (within-container offset). If a crash occurs during compaction, both containers persist. The scanner reads both units and sees identical identity tuples (unit class, T, O, G, A) for X’s slot in each container. Since birth generation is the same, the scanner cannot determine which is current, violating the requirement to resolve ambiguity from raw disk alone. This occurs because the identity lacks container-specific uniqueness; including the container’s object ID in the slot’s identity would fix it.
