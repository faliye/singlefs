### 与条款原文逐句核对

- 「只管 `crates/*/src/`，只改文档和脚本除外」——原文 `show-me-test.md:38-39`（现查）：「**改了 `crates/*/src/` 就得带测试。** 没有例外……只改文档和脚本除外。」「只改文档和脚本除外」六字逐字相同；「只管 crates/*/src/」是对前一句触发条件的转述，与原文的适用范围一致，不冲突。
- 「新增的测试必须先证明它会红」——原文标题 `show-me-test.md:43`（现查）：`## 新增的测试必须先证明它会红`，逐字相同。
- 「这条同样管设计论证」——原文 `show-me-test.md:57`（现查）：`**这条同样管设计论证**：`，逐字相同（含标题引号内的整句）。
- **不逐字处**：implementation-workflow.md:22 把原文接下来的那句转述了，不是整段抄。原文 `show-me-test.md:57-58`（现查）：「对抗轮打中的每一条，先在模型里做成一个**必须报非 0** 的世界，再改规则。」implementation-workflow.md:22 写的是：「三方打中的每一条，先做成一个必须报非 0 的模型，再改定义。」两处不同：① 原文「在模型里做成一个……世界」，改写后丢了「在模型里」，把「世界」直接换成了「模型」——原文的「模型」与「世界」是两个不同的词（世界＝被建模的对象，模型＝建它的手段），改写后二者被合并成一个词，读的人分不清「必须报非 0 的」到底是那个被造出来的世界，还是造世界用的模型本身；② 「对抗轮」→「三方」、「规则」→「定义」是同义替换，不改变意思。
  这处改写落在 `.claude/rules/three-way-inference.md`「引 kb 里的条目要整行抄，不许摘句」管的三处射程之外——那条规则管的是「一份 kb 文件引另一份里的条款」，例句是「决策 A 的正文引决策 B 的分项」，指的是 D/E/C/I 这类编号条目的整段引用；这里是 `.claude/rules/` 引 `.claude/singlefs-ai-sop/rules/` 的一句话，不是编号条目，字面射程够不着。但改写本身确有信息丢失（「在模型里」这个限定词没了），按「英文提示里的每一句转述都要对着原文核一遍」同源的道理（该条只管给本地腿的英文提示，这里不是那个场合，不能直接套用它的判据，只能类比其风险），这是一处**值得记的转述漂移**，不构成与条款原文的「冲突」（两句话的规范性要求——「打中的每一条要先做出一个必须报非0的东西再改规则/定义」——仍然一致，只是「东西」的措辞从「世界」滑成了「模型」）。

**判定（新补段落是否与条款原文冲突）：没冲突**。三处直接引用（「只改文档和脚本除外」「新增的测试必须先证明它会红」「这条同样管设计论证」）逐字对得上；唯一的转述（「先在模型里做成一个必须报非0的世界」→「先做成一个必须报非0的模型」）丢了一个限定词、把两个不同的词合并，是转述漂移，不是规范性冲突，且这条规则字面射程够不着这里（不是 kb 编号条目的引用）。
**推翻条件**：若这句转述在后续被人当作「模型」与「世界」是同一回事去执行（例如三方腿把「造一个模型」误当成「做出一个必须报非0的东西」本身，跳过了「先在模型里跑出一个会报非0的世界」这一步的实际验证动作），会出现按新措辞执行、但按原文执行会不同的具体案例——那时候升级为冲突。

### 替正推「正文明说①③暂缺」辩

r1 判决（`gate-fix-forks-r1-main-verification.md:46`，现查）写：「正推说『①③暂缺』对①成立、对③不成立：③在定义上的取值第57行已经写着。」这句话把「取值存在于仓库某处（show-me-test.md:57）」等同于「取值已经写在 implementation-workflow.md 这个借用处」，而这正是 T2 里正推自己引用、判决自己在 T2 采纳的判据——`fs-design.md:107-111`（现查，附录已整段抄，见背景材料 269-279 行区间对应 `.claude/rules/fs-design.md` 原文）：「写借用式条款时，把被借规则的参数逐个列出来，**在 X 上各写一句它取什么**；写不出来就别借，把 X 自己的规则写全。」这条判据的字面要求是「在 X（这里是 implementation-workflow.md）上写」，不是「在仓库别处能找到」。

现查 r1 判决核实时的工作区（即 r1 三方腿写分析报告时读到的 `implementation-workflow.md`）：那时 `## 改 agent 定义与共用约束，走同一条三步` 这一节只有现在的 18、20 两行（对应「定义是工作流」与「改它们与改 crates/ 同规矩」两段），没有「三步在定义上各取什么」这一段——这一段是 r1 判决自己在这一轮才让攻方候选把它写进去的（暂定形态，见 `_gate-fix-forks-r2-background.md:353` 现查一致）。也就是说，在正推做出「①③暂缺」判断的那个时点，`implementation-workflow.md` 全文（不算 `show-me-test.md`）确实一句都没有写③的取值——判决用「第57行已经写着」来反驳正推，引的是**另一个文件**里的话，而不是 X（implementation-workflow.md）自己写的话。按 `fs-design.md:111` 的字面判据（「在 X 上各写一句」），这不满足「已经取值」，因为「取值」这件事发生的地点不对。

**判定：正推站住**。判决对③的反驳把「值存在于仓库某处」与「值写在借用处（X 自身）」混为一谈，这个区分正是 T2、T3 两格共用的同一条判据（`fs-design.md:111`）自己划出来的界线；在暂定形态落地之前，implementation-workflow.md 自身确实没有为①③取值，正推「①③暂缺」在那个时点对两条都成立。
**这一分歧不改变最终结论**：暂定形态（这一轮已落地的文本）把①②③三步的取值都显式写进了 implementation-workflow.md 自身——不论起点判断是「①③都暂缺」（正推）还是「只有①暂缺」（判决对正推的反驳），落地后的动作都是「把①③写进 X」，两种诊断殊途同归，判决最终选的形态没有因为这处诊断分歧而选错。
**推翻条件**：若日后又有一条借用式条款只引用外部文件、不在自己文件里写取值，且被判定「已取值」，可以拿这条区分（值必须写在 X 处，不是仓库某处存在即可）去核那次判断站不站得住。

## T8　替乙「读 not-numbers 当词表」辩

r1 判决（`gate-fix-forks-r1-main-verification.md:405`，现查）：「主 agent 现跑坐实：乙照正文的定义（『要剥掉的那一截与词表逐字相同就不剥』）也堵不住——被剥的是 `A256`，不是 `SHA256`。」

**现查复现这句话本身**：用 r1 时的老正则（`[A-Z]-?\d+(?:\.\d+)?`，无 `+`、无左边界——即 `.claude/scripts/gen-decision-items.py` 在丙a 落地前的形态，可从 r1 判决 `:102` 的引用还原）配 not-numbers 词表 `{"SHA256","RAID5"}`，跑 `clip("校验和算法取 SHA256 摘要", 13)`：抽出要判「在不在词表里」的那一截是 `A256`（正则 `[A-Z]` 只匹配一个字母，不是 `[A-Z]+`），`A256 not in {"SHA256","RAID5"}` → 判据不触发 → 照样剥，结果 `校验和算法取 SH`——与判决描述逐字一致，可复现。

**但这不是「乙这个词表思路本身」的缺陷，是乙被绑定的那个正则的缺陷**：把 丙a 已经落地的正则（`(?<![A-Za-z0-9._-])[A-Z]+-?\d+(?:\.\d+)*\s*$`，带 `+`、带左边界）拿来抽取候选串，再配 not-numbers 词表判「抽出来的整词在不在表里，在就不剥」，现跑（脚本内联复现 `.claude/scripts/gen-decision-items.py:44` 的正则）：

```
text = "校验和算法取 SHA256 摘要"; n = 13
丙a（现状，无词表）: clip → '校验和算法取'            # SHA256 整词丢了
乙+丙a正则（词表={"SHA256","RAID5"}）: clip → '校验和算法取 SHA256'   # 整词留住
```

对真裸引用（`"参照 D-451 号决策处理"`，各种截断点 n=6..9）「乙+丙a正则」照样在 `D-4`／`D-45`／`D-451` 都不在词表时正常剥掉，不影响原本该剥的场景（现跑核对，见上）。

⇒ **乙可以改个定义，不丢整词**：把「乙」的「剥掉的一截与词表比对」这一步，接到丙a 已经改好的正则上（先按丙a 的形状抽出整个候选词，再查表决定剥不剥），而不是接在老正则（只抠出 `A256` 这半个词）上——判决现跑坐实的失败样本，本身就是老正则的产物，不是词表机制的产物；把词表机制接到新正则上，判决自己给出的反例（`SHA256`→`A256`）不再出现。

**丙a 丢整词算不算比乙差**：丙a 自己的注释承认代价（`.claude/scripts/gen-decision-items.py` 当前正则上方注释，现查第 39-40 行）：「不带左边界时……剩下半截『SH』『RAI』；带了左边界，截断尾巴上的领域词要么整个留着、要么整个剥掉，不会剩半截」；r1 判决 `:104`（现查）也写「代价是截断尾巴上的一个领域词整个丢掉。不接 not-numbers 词表。」——这是判决自己承认的代价，不是本轮新发现。对 `kb-discipline.md:133-134`（现查，逐字：「领域术语（`RAID5`、`SHA256`）跟编号长得一样，机器分不开，得显式摘出去：`<!-- doc-lint:not-numbers RAID5 SHA256 -->`。」）已经登记过的那些词（如 `SHA256`、`RAID5`），丙a 现在的行为是**整个丢掉**，而「乙+丙a 正则」这个修法能够**整个留住**——对这个子集，「乙+丙a 正则」严格优于丙a：丙a 有代价，这个代价对登记过的领域词是可以避免的，只是判决没有测试这个组合。对没有登记进 not-numbers 的领域词（`kb-discipline.md:133` 只保证「显式摘出去」的那些词，没登记的仍然识别不了），两者一样丢——这不是乙的额外缺陷，是词表覆盖率的固有上限，`gate-fix-forks-r1-sonnet-output.md:119`（现查）已经写明这条推翻条件：「乙不会改变结果——但这不推翻选择，只说明乙的命中率上限就是标记词表覆盖到的术语」。

**判定：乙够不着丙a 的理由不成立——落选的一方（乙）在改一个字段之后其实站得住**。判决现查的那次失败（`A256` 不是 `SHA256`）可复现，但那是老正则的产物；把词表接到丙a 已经改好的正则上，`SHA256`/`RAID5` 这类已登记的领域词能整词保留，丙a 现在对它们的行为（整词丢弃）反而更差。判决没有测试「乙 + 改进正则」这个组合，「丙a 更好」这句话在「已登记领域词会不会被整词丢弃」这一点上够不着。
