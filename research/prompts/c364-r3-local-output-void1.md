A sequence where the predicate says none while one was gained is not possible under F2 and F3 because the predicate counts segments as empty regardless of allocatability; if a segment becomes allocatable, it was already counted as empty during the predicate evaluation.

For example: foreground writes continuously allocate new data into R, causing the region scan to repeatedly fail the full check. The resume point resets to the start of R each time the scan completes without meeting the target state. Rollbacks may resurrect allocations in R, forcing the scan to restart. This creates an infinite loop where the intent never reaches the target state and is never deleted.

3. For key layouts: 
   - Starting with intent kind: allows multiple live intentsints per segment (e.g., compaction and truncate for same R), violating "at most one live compaction intent per segment". 
   - Starting with R: ensures only one live compaction intent per segment (keys unique per R), but allows multiple live intents across different R (bounded by total segments). 
   - Starting with instance id: allows multiple live per segment (different instances for same R), violating the constraint. 
   For "at most one live compaction intent per segment", R-based keys are best. For "bounded number of live intents", R-based keys also work (bound by number of segments). Instance id-based keys are worse for both.

4. Choose R-based keys for both needs. The single observation that would change this is if the system requires multiple compaction intents for the same R (e.g., different priorities or types), which would require a different key layout (e.g., including intent kind and R).
