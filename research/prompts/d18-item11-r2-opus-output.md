## 二、记账 → 码 2 的收窄写法（靶子 1 第一问）

### 2.1 若这条收窄是站得住的，本该看到什么

本该看到 D9 那句禁令的射程确实只到「索引位置」，而不到「树成员身份」。

去查了，禁令的措辞不支持这个读法。`.claude/kb/decisions/09-加密.md:384-385` 逐字：

    格式必须 day-1 提供的三样（少一样 checker 就履行不了「连带要新增 / 改写的不变量与检查」那张表）：
    ① 单元类型标签在权威侧显式，不许靠「它在哪棵树里」推；

「它在哪棵树里」这七个字说的是树成员身份，不是索引位置。第二版的收窄句
（提案第 67-68 行）把它读成「即从索引位置推」，再论证「树 ID 是头里显式的字段」——
这论证的是树 ID 显式，不是标签显式。标签的那个值（记账单元）在第二版之下恰恰不显式，
它要由树 ID 反推出来，而那正是禁令的字面。

### 2.2 结论本身站不站得住：站得住，但依据要换

D9:260 自己给标签的理由逐字是「不同单元类的字段集合不同。没有域分隔时两类单元的 AAD
可序列化成同一串字节 ⇒ 类型混淆变成一次合法的 MAC 通过」。记账树节点与别的索引节点
字段集合相同（`18-块里携带什么信息.md:408` 逐字「树 ID + 层级 +
该树已定携带的 key 区间 + 诞生代号 + fsid」），域分隔在这一对上买不到东西。
所以合并的结论可以成立——但依据是「D9:260 的域分隔理由对这一对不适用」，
不是「树 ID 是显式字段」。

### 2.3 提案没接的一处：C102 已经记下这一对的态别不同

`.claude/kb/checks-owed.md:109`（C102）逐字：

    ⚠️ D21（权威态与派生态的分界） 的「索引是派生态、不参与格式冻结」这条出路至少对记账树不成立——
    first-txn-layout.md 把记账树节点头挂在索引节点类，而 D21（权威态与派生态的分界） 把记账列进权威态

`.claude/kb/decisions/21-权威态与派生态的分界.md:41` 逐字「权威态 = 单元 + 记账 + 根；索引是派生态」。
⇒ 记账树节点与别的索引节点在态别这一维上确定不同，而态别正是 I-6.2 白名单归类
（`18-块里携带什么信息.md:456` 逐字「元数据类身份字段……一律进密文（无密钥重建本来就不可能，
D21（权威态与派生态的分界）已定）」）与扩展点归属（D21 已定项 4）两处判定的依据。
若将来任何一处要按态别把它们分开，那就是给记账另开一个码——
而在第二版之下盘上已经写着 tag=2，每个记账节点的 MAC 都是按 2 算的，
按 D15 判定表这是「改变已有字段含义 ⇒ incompat，且弃用旧位置不复用」（`15-格式冻结政策.md:84`）。

判决：打中。改法三条，缺一不可：
1. 收窄依据换成 2.2 那条（域分隔理由对这一对不适用），删掉「从索引位置推」那句重读；
2. 把 C102 记的那处态别差异写进收窄段，并明写「若日后按态别分开，代价是 incompat 且码 2 不复用」；
3. decisions-history 那条要写清收窄的是 D9:385 ① 的哪一半。

同一份实验的实测表 `90-树ID进AAD与跨头共享.md:76-77`：

    | `pointer_tree`（从指针读回来） | 0 / 3 | 3 | 0 / 1 | 6 / 6 | ✗ | ✓ |
    | `ancestry_birth`（出生 (树,txg) + 祖先验收） | 3 / 3 | 0 | 1 / 1 | 6 / 6 | ✓ | ✓ |

`pointer_tree` 与 `ancestry_birth` 的唯一差别就是那道祖先表验收；少了它，三次换挂全部静默，
连伪造声明都抓不到（0 / 1）。

第二版 P4 逐字只写了「期望值来自指向它的容器索引的 key（P7）」与
「快照树里的指针照 E90 携带出生树与出生代」，一个字没提克隆祖先表。
而 E90 与 D9 都把祖先表列成格式含义。`09-加密.md:371` 逐字：

    格式含义两笔：指针要有出生 (树, txg) 两个字段的位置，克隆祖先表要住已认证结构。

登记表是这一项声称的唯一权威登记位，而这两笔格式含义在表里一处都没有。

### 5.3 「不需要 F23 那次重开」这句话与 D9:57 的必带鞍句

`.claude/kb/decisions/09-加密.md:57` 逐字（已定项 6 的索引行）：

    ⚠️ 这五项对快照维是瞎的，且是静默的——E31 实测错配检出 0 / 2……

登记表码 1 那一行的 AAD 变体逐字只写「D9 已定项 6 五项」，没有带这句鞍。

至于码 3 「不需要重开」这句：它成立的前提恰恰是码 3 已经单方面把重开的答案定了

判决：打中。改法四条：
1. 码 1 那一行补上 D9:57 的必带鞍句；
2. 码 3 那一行明写它的树维是出生树，并写一句「与码 1 那一格的语义不同，不是同一维」，
   删掉「逐位同构」这个说法或把它限定在字节布局上；
3. 把 E90 的两笔格式含义（指针带出生 (树, txg)、克隆祖先表住已认证结构）写进码 3 那一行，
   或明写「本项不定它们，码 3 的 AAD 在这两笔落地之前不构成完整契约」；
4. 「不需要 F23 那次重开」改成「本项对码 3 提前采用了 F23 唯一剩下的那条出路的形态，
   F23 对码 1 / 码 2 仍然欠着」。

### 5.4 顺带一处：码 3 的标签在密文侧没有权威副本

`.claude/kb/invariants.md:213-215` 逐字：

    ⚠️ I-6.2（明文头字段白名单） 的白名单是「允许出现在明文头」的清单，不是「可以拿来判定」的清单。

## 六、两级政策（靶子 3）

### 6.1 失败模式：旧读者遇到新码是「挂不上」，成立

`.claude/rules/fs-design.md:197` 逐字「一条格式分支值不值得，看它能不能把『用错了』变成『挂不上』」。
新增内容类占一个 incompat 位、位住超级块（`15-格式冻结政策.md:93` 逐字「三个 bitmap 各 256 位（`u64[4]`），存超级块」），
旧读者见到不认识的 incompat 位拒绝挂载 ⇒ 失败模式是挂不上，不是静默误读。这一半没打中。

顺带纠一条第一轮本地腿的说法：它说 feature bit 只有 flags 高字节 8 位、所以只能有 8 个新类。
现查 `15-格式冻结政策.md:93` 是三个 256 位 bitmap 存超级块，与 flags 无关。那条是错的，第二版没有采信，正确。

### 6.2 新读者读旧镜像要不要位：不要，但要一句话写下来

旧镜像里没有码 3 单元，也没有对应的 incompat 位；新读者照常挂。不需要任何位。
但 D15 判定表每一行都有 bump 列（`15-格式冻结政策.md:81-89`），
而 P2 / P6 一个字没提格式版本要不要 bump。这一格要补一句。

### 6.3 两条新政策没写进 D15，而判定表的权威记录点在 D15

P6 逐字「新增单元类 = incompat 位——本项定」「新增打包记录类型 = compat_ro 位——本项定，类比 D15……那行」。
两条都自陈是新开的判定，不是 D15 现成的行。而 D15 的「冻结后的改动判定表」
（`15-格式冻结政策.md:79-89`）是这类判定的唯一权威记录点。
P9 的落地清单（提案第 186-190 行）里没有 D15。
⇒ 三个月后读 D15 判定表的人会以为它是完整的，而它不提单元类与打包记录类型。
这正是 kb-discipline 第 4 条要拦的形状，而门禁没有一条阶段会红
（21 只比分项清单、22 只比状态、28 只比「说未定而已定」）。

判决：打中。改法：D15 判定表加两行（新增单元类 ⇒ incompat；新增打包记录类型 ⇒ compat_ro 且带三条限定），
D18 已定项 11 链过去，不在 D18 里第二次写判定。

### 6.4 墓碑那一类的「只读安全」按 E59 不成立

compat_ro 的语义是只读安全。D15:85 逐字「新增记录类型（新 key 类型）| 只读遍历可能误判；
整理 / 写可能误删看不懂的记录 | compat_ro」。

对墓碑这条记录类型，「跳过不认识的容器」不是误判，是给出反向的错误答案。
`.claude/kb/decisions/18-块里携带什么信息.md:286` 逐字：

    E59（缓冲消息能不能只从单元重算） 实测：只扫单元时已删的 key 全数复活，复活数恰好等于删除次数

一个 compat_ro 挂上来的旧读者做扫描重建时跳过它不认识的墓碑容器，
重建出的索引里那批已删的 key 全部复活——只读挂载给出一个包含已删文件的目录，这不是只读安全。
仓里对同一个形状已经有过一次相反的定案，`23-journal的角色与格式.md:1036` 逐字：

    | A | 记录头类型字段 + 未知类型 ⇒ 拒绝挂载，且该政策由超级块 incompat 位承载 |
    光有字段而政策是「跳过不认识的记录」，失败模式是静默漏放一条发布指令，比没有字段更糟 |

两处同形而档次相反，而第二版 P6 逐字只写了「政策相反」，没说为什么墓碑这一侧可以相反。

判决：打中。改法：把 compat_ro 的射程按记录类型分——只对「跳过它不改变任何答案」的记录类型开放；
墓碑（打包记录类型 1）不满足这个条件，它的任何后继类型只能走 incompat。
这条限定要写成第四条限定，与现有三条并列。

### 6.5 删掉记录宽让 P5 第 4 条对不认识的读者不可判，且它是免费的

P4 逐字删掉记录宽，理由「不认识记录类型的读者按声明长度跳整个容器，不需要记录宽」。
而 P5 第 4 条逐字「记录数 × 记录宽 ≤ 声明长度 − 90，这是头合法性条件，在认领时判」。
不认识类型的读者拿不到记录宽 ⇒ 判不了这条头合法性条件 ⇒ 它对恰好最需要它的那一类读者失效。
`23-journal的角色与格式.md:1037` 逐字给同一个形状留的是长度字段：

    | B | 记录自述长度，且先边界检查再算校验和 | 类型字段只说「这是什么」，不说「这有多长」。 |

而代价是零：头 90 → 92，加预留 28 是 120，`(32768−120)//56 = 583`、`//140 = 233`，一个数都不动。
按 `.claude/rules/fs-design.md`「不为省空间牺牲自包含」，一个已经论证过有用（P5 第 4 条在用它）
且代价为零的字段不该砍。

判决：打中。改法：记录宽 2 字节放回去；若同时放回 5.4 的标签 1 字节则头 93、加预留 121 > 120，
墓碑容量掉到 582，E83 / E84 的绝对值锚要重跑——两者只能选一个，或者接受重跑。这笔账要写在提案里。

## 九、容器索引与两版择新（靶子 6）

### 9.1 态别：派生态，而重建输入齐了

## 十二、头宽预算这条约束是谁定的（附加）
