1. For candidate A: During re-clustering where locality_id changes, the header's locality_id (part of associated data) becomes outdated. When decrypting, the associated data mismatch causes decryption failure, making data inaccessible. For candidate B-prime: When encryption is on and the key is unavailable during rebuild, the header's locality_id cannot be read, but rebuild uses the key prefix. However, if the key is lost entirely, data decryption fails, but the key prefix remains for rebuild. For candidate C-prime: If an extent key has a different locality_id prefix than the record's after a partial rebuild, the system may miss data because it looks under the wrong prefix. For example, one extent key uses locality_id X while another uses Y for the same (tree ID, inode), causing some data to be unreadable under X.

2. Candidate A conflicts with F5 because adding locality_id to the five fields makes it part of associated data, violating "locality_id must never be part of the associated data, because that would make a field declared 'may be wrong' load-bearing." The weight is in the phrase "field declared 'may be wrong' load-bearing" as it directly contradicts the field's intended non-critical role. Candidate B-prime does not conflict with F11 because locality_id is encrypted (part of ciphertext), so only fsid and payload CRC remain plaintext as required.

3. Candidate A: +8 bytes per unit header and per packing slot (F15 copies all five fields including locality_id); first-transaction bytes increase by 8; renames do nothing; background moves require re-encrypting units if keys change; rebuild must update header locality_id and keys. Candidate B-prime: +8 bytes per unit header but no extra bytes per packing slot (slots copy only five fields); first-transaction bytes increase by 8; renames do nothing; background moves change key prefix but do not update header locality_id; rebuild uses key prefix. Candidate C-prime: no added bytes; first-transaction bytes unchanged; renames do nothing; background moves only physically relocate data without key changes; rebuild sets record's locality_id to extent key prefix.

4. Candidate A: I-9.9 could turn red if header locality_id differs from key prefix (e.g., after re-clustering without header update). Candidate B-prime: I-9.9 could turn red if record's locality_id differs from key prefix (e.g., incomplete rebuild). Candidate C-prime: I-9.9 could turn red if record's locality_id differs from any extent key prefix (e.g., corruption during rebuild). To prove the check turns red: for any candidate, if record's locality_id does not match all extent key prefixes for an object, the check fails. For C-prime, after rebuild, the check reports undecidable by design (even if values match), as rebuild sources are unified.

5. Pick candidate C-prime. The single observation that would change the pick is if real-world performance tests show consistent, measurable slowdowns in small-cache scenarios (e.g., leaf cache of 8) where locality_id prefixing significantly improves key lookups, outweighing the minimal cost of adding the field.
