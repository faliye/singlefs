1. Yes, a later recovery can overwrite the owner row (k, 0, W_k) with (k, 0, 0) or (k, T_sel, 0) causing kept units to become unpublished. For example, after a switch where instance k has (k, 0, W_k) because it never published a root, a subsequent switch could set rows for instances between the current root and new instance. If instance k is in that range and does not own kept transactions, it would be overwritten to (k, 0, 0). This would make code-1 units with n <= W_k (which were previously published) now unpublished since W=0 requires n <=0. The owner row should receive the same protection as rollback rows to prevent this, as it directly affects publication status.

After R takes effect, the chosen root's T_pub is set to its checkpoint, and switches correctly reference this value for the owner row. 3. The instance table can grow indefinitely because unreadable root slots prevent row deletion per the extra deletion condition. Each unreadable slot keeps rows for the associated instance forever. This affects the switch reserve since the reserve is computed from the number of rows read at mount. An unbounded instance table would require an unbounded reserve, but the reserve is fixed for one more switch, leading to potential metadata overflow during switches.

For example, if kept transactions come from instance k but the system sets W to the row of instance k+1 instead of k. Proof: during switch, the instance table would reference wrong W, causing published units to be misclassified. For deletion condition: a failing check occurs when a root slot is unreadable but rows are deleted anyway. Proof: if a disk fails making a root slot unreadable, and deletion proceeds, later recovery cannot detect roots from that instance, leading to data loss or incorrect mount.
