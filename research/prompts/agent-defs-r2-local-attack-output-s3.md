1 A bad write scope table entry for the production code writing role is the pattern "/scratch/*" alone without including "/src/*". During a trial run inside a disposable repository copy under the scratch tree, the role is tasked to write to a file at /scratch/disposable/src/file. The write scope gate allows this because the path is under the scratch tree, matching the blanket pattern. The trial run passes as the write succeeds. However, when the same role definition is used against the real repository, the role attempts to write to /src/file. The write scope gate checks the patterns and finds no match for "/src/file" since only "/scratch/*" is allowed, so the write is blocked. This causes the role to fail in the real repository as it cannot complete the task. this would be refuted if the real repository write to /src/file was allowed by the pattern "/scratch/*", but the pattern only matches paths under the scratch directory, making such a scenario impossible.

2 A flaw in the role definition for the knowledge base writing role is the instruction "if the file path contains 'confidential', redact all content". However, the single trial run task only involves writing to a file named 'public_notes.txt', which does not contain 'confidential', so the condition is never triggered. A second trial run would need to include a task that requires modifying a file named 'confidential_report.txt' to exercise the condition and reveal if the role incorrectly redacts content or fails to handle it properly. this would be refuted if the second trial run with a file named 'confidential_report.txt' did not trigger the condition, but the path explicitly contains 'confidential', so the condition would be exercised.

3 The role definition for the gate triage role includes a check that says "if the user does not provide a list of changed files, assume all files are part of this trial". However, the main agent's task specification for the trial run always includes the list of changed files, so this check is never executed. Fact eleven describes such a scenario where the task specification supplied an explicit list of files for the gate triage role, causing the role's instruction that depends on the absence of such a list to never be tested during that trial. this would be refuted if the gate triage role's instruction in fact eleven was actually tested by the absence of a file list, but the task specification explicitly provided the list, so the absence case was not exercised.

4 A different bias occurs when the main agent favors a fix that simplifies error handling for readability over robustness. For example, two candidate fixes for the experiment running role: one logs detailed error messages for failed script executions, another suppresses all error messages to keep output clean. The main agent prefers the cleaner output and adopts the suppressive fix, even though it hides critical failures. During the trial run, the task only includes successful script executions, so the fix passes. However, in real use, when scripts fail, the suppressed errors prevent diagnosis. This scenario is different from fact six, which involved a directory path error. this would be refuted if the suppressive fix actually provided sufficient error details during real failures, but the fix explicitly suppresses all messages, making error diagnosis impossible.

5 One situation is a role receiving additional instructions mid-task. If the role definition does not handle concurrent messages, it might ignore them or crash. For example, the role is processing a file when the main agent sends a new instruction to stop. The role's instructions don't account for this, so it continues processing. Since all trial runs are single one-off tasks with no follow-up messages, this scenario is never tested. Another situation is a role's work being rejected and sent back for revision. If the role definition lacks instructions for handling revisions, it might create a new file instead of updating the existing one. Trials do not involve revising work, so this is never tested. A third situation is multiple roles editing the same file simultaneously. If the role definition doesn't check for file locks or conflicts, it might overwrite changes. Trials never involve multiple roles or concurrent edits, so this is never tested. For the first situation, the bug would be the role ignoring new instructions. For the second, the bug is failing to modify existing files. For the third, the bug is data corruption due to concurrent writes. this would be refuted if any trial run included mid-task messages, revisions, or concurrent edits, but all described trials are strictly single one-off tasks with no such interactions.
