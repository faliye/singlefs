## 二、丙的最强形态（先写出来）

第一轮的丙只有一个量：环里读得出的、实例 = 所选根的实例、txg ≤ T 的最大计数器，当成「所选根覆盖的最后一条」。这一轮用上的锚：

| 锚 | 出处 | 丙怎么用 |
|---|---|---|
| txg = T + 1 | D16 已定项 6「每次发布把 checkpoint_txg 加一」（`16-发布语义.md:248`）；写失败不在同一实例里重试：`23-journal的角色与格式.md:285` 逐字「一个事务在发出单元写之后失败即实例切换」，`:691` 把失败按性质分成实例切换与转只读两支，所以根 (i, T) 之后本实例的下一批记录 txg 恰是 T + 1 | 候选链首 h = 读得出的 (i, txg = T + 1) 记录里计数器最小的那条 |
| 反向链 | D23 已定项 19 ②（`23-journal的角色与格式.md:1265-1266`） | h 的前一条 p = (i, h − 1) 读得出时，要 p.txg ≤ T 且 CRC32C(p 的头) = h.反向链；h.反向链 = 0 说明 h 是本实例第一条，不可能跟在根 (i, T) 之后 ⇒ 不接 |
| 事务号、提交标记 | D23 已定项 7（`:285`：按实例计数、从 1 起、同一事务的全部记录共享、按事务号顺序追加）；空发布事务号 0（`:1263`） | p 读不出时，看前前一条 q = (i, h − 2) 与 h 的事务号，判 p 在发布 T 里还是 T + 1 里（下表） |

**T1_TX 的规则表**（`model.py` 的 `tx_rule`；p 读不出时）：

| 观测 | 判 | 理由 |
|---|---|---|
| h 的事务号 = 0 | p 在 T 里，接 | 空发布只有一条记录 |
| q 读不出 | **判不出** | — |
| q.txg < T | p 在 T 里，接 | 发布 T 至少一条记录，q 与 h 之间只有 p |
| q.txg = T 且 q 的提交标记 = 0 | p 在 T 里，接 | p 接着 q 的事务，一个事务不跨发布 |
| q.txg = T 且 q 是空发布（事务号 0） | p 在 T + 1，不接 | 空发布 T 只有 q 一条 |
| q.txg = T 且 h.事务号 = q.事务号 + 1 | p 在 T + 1，不接 | p 与 h 同一个事务 |
| q.txg = T 且 h.事务号 = q.事务号 + 2 | **判不出** | p 是一个单记录事务，在 T 的末尾还是 T + 1 的开头，记录层字段一样 |

「判不出」时 T1_TX_STRICT 不接、T1_TX_OPT 接。**这就是记录层最强的丙**；比第一轮多用了 txg 锚、反向链、事务号、提交标记、q 的 txg 五样。

**再往上两档，各多用一样东西**：

| 档 | 多用了什么 | 今天有没有 |
|---|---|---|
| FP_LAST | 约定「一次发布的固定点单元（码 2 / 码 3）只点名在这次发布的末条记录」，于是 q 点名项里有没有码 2 / 码 3 单元 = q 是不是发布 T 的末条；链尾那条同理 | **没有**：D23 已定项 17（`23-journal的角色与格式.md:696`）只写了「一项一个单元（第一个事务 8 项）」，多记录发布里固定点单元点名在哪条全仓没写。零字节，要新写一条条款 |

### 4.1 切换：最短序列

**第 1 条链尾那一型，不要任何介质故障**（`SW-mem/DING/prefix/durability_violations_truth_holds`）：mkfs → 取号 → 暖机 txg 1、2（根都落盘，fsync 已返回的是空文件）→ 发布 txg 3 = 两个事务：数据单元 d0、d1 与固定点单元 m 写出 → 屏障 → 记录 (1,3) 写出，**记录 (1,4) 写报错** → 挂载内实例切换：取号（实例 2 的超级块写与 (1,3) 同段）→ 屏障 → 重发 txg 4：号 ≤ W 的事务照旧不重写 d0、d1，固定点按新实例重写，**新固定点单元分到 m 原来的槽**（失败那次的分配不存在，`23-journal的角色与格式.md:691`）→ 新固定点单元落盘，记录与根都没落 → 崩。
再挂载：所选根 (1,2)。丁、乙、丙的记录层形态、fbae43e：(1,3) 在、(1,4) 不在、链尾没有「这次发布写完了没有」的输入 ⇒ 施加 (1,3) ⇒ 装上 txg 3 的根，它引用的 m 槽里已是实例 2 的单元 ⇒ **读不出**；而 (1,2) 那一版原样在盘上。真值 / IDXN / FP_LAST / WALK：txg 3 只到齐一条（或末条没到、或树里有没被点名的 d1、m）⇒ 整次不施加 ⇒ 读回空文件。

### 4.2 多记录发布：回退复用撕掉的末条点名的单元（`RB/DING/mount/named/cause/head_or_other`）

暖机 → 发布 txg 3 = 两个事务，(1,3) 落盘、(1,4) 没落 → 崩。挂载：丁乙丙施加 (1,3)（链尾没有输入），读回 txg 3 的根（d0、d1、m 都在盘上，读得出）。管理员回退到 (1,2)：起始计数器取这次挂载普通恢复的前缀末 + 1 = 4，隔离取 `named`（水位之上读得出的记录只有 (1,3)，只隔离 d0）→ 回退那次发布的固定点单元分到 d1 或 m 的槽 → 单元落盘、记录与根没落 → 崩。再挂载：丁乙丙照样施加 (1,3)，装上的根引用的槽被复用 ⇒ 读不出；没发起回退时读得出。

### 4.3 回绕：ringmax 的最短序列（`WRAP/ring12/acknowledged/*/ringmax`）

暖机 → 发布 txg 3 单记录 (1,3)，根落盘 → 发布 txg 4 两条记录 (1,4)、(1,5)，根 (1,4) 落盘（fsync 已返回）→ 根 (1,4) 所在的根槽从此读不出（一个故障）。之后每次挂载：恢复从根 (1,3) 重放 (1,4)(1,5)、读回 txg 4 那一版 → 取号 → 暖机第一次空发布的记录落盘、根槽之前崩。ringmax 下第 k 次挂载写计数器 5 + k，落槽 (4 + k) mod 12；第 11 次落槽 3、盖掉 (1,4) ⇒ 第 12 次恢复链从 (1,4) 接不上，读回 txg 3 那一版。`prefix` 规则每次都写计数器 6（槽 5），从不碰 (1,4)。
**缩比保留的是**：环 : 在飞 = F = 3，每轮崩溃写的记录数（1 条）与丢失前的轮数都随环线性（11 / 23 / 47 / 95 = 环 − 1）；按 196608 槽外推 196607 次；暖机连推空发布写 R 条时约 196608 / R 次（算术，没跑真几何）。**根槽不持续坏时**（`unacknowledged` 那一行，同样的数），丢的是没返回的 txg 4，条款允许，但它说明 ringmax 下「普通恢复会重放的记录」可以被一串崩溃慢慢盖掉。
