Form A scenario: A journal record's payload is corrupted but passes checksum validation due to a hash collision. This would go undetected during replay because the existing invariants do not specify that journal records must have strong checksums or that checksums must cover the entire payload. A naive inventory might assume checksums are sufficient without specifying collision resistance or payload coverage, missing this critical invariant. This adds a new invariant requirement for Form A not present in the current inventory.

Form B scenario: During replay, the block allocator allocates a new block for an ancestor node but crashes before writing the node data. The allocator's state becomes inconsistent as the allocation is recorded but the data is missing. On restart, replay may reuse the allocated block, causing corruption. This requires an invariant that allocator allocations are journaled and transactional, which is a new crash-point class specific to Form B. Form A does not need this because it never uses an allocator during replay.

Form A hidden cost: The root ring is updated 1000x faster than Form B, leading to high write amplification on storage media. This causes increased wear and performance degradation not captured by the invariants count. The inventory framing focuses on correctness but ignores the operational cost of frequent root ring writes, which requires additional maintenance for storage longevity and performance tuning.

Form A count: 10 on-disk invariants (including journal record checksums, back-chain hash verification, ring size, header alignment, sequence continuity, idempotency, tail slot validity, commit atomicity, root verification, block reuse delay) and 6 crash-point classes (crash during header write, payload write, checksum write, cursor update, root ring update, and deduplication consistency checks). 

Form B count: 14 on-disk invariants (including leaf checksums, naming record checksums, rebuilt ancestor checksums, allocator journaling, allocator block reuse delay, sequence continuity, back-chain hash verification, ring size, commit atomicity, and more) and 10 crash-point classes (crash during allocation, node write, allocator journaling, leaf read, ancestor rebuild, etc.). 

The count is not a fair proxy for maintenance cost. Form B's higher count reflects more complexity but underestimates the allocator's implementation difficulty and error-prone nature. Form A's lower count overlooks performance-related maintenance costs from high root ring write frequency, which is not addressed by correctness invariants alone. Maintenance cost depends on both the number of invariants and their implementation complexity, as well as non-correctness factors like hardware wear and performance tuning.
