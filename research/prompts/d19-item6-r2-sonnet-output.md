## 二、逐格依据

### Q1 扫描重建：只读盘上单元，能不能给每个被引用的物理版本重建出与引用侧一致的 key

**判红条件（原文抄）**：「存在一类单元（码 1 / 码 2 / 码 3 / D27（小数据打包容器） 的容器槽），重建不出 key，或重建出的 key 与引用侧的可能不同」——`_d19-item6-r2-background.md:57`。

#### K1a

码1（数据单元）：D18 已定项7 字段表逐字「五元组 | 33 | D18（块里携带什么信息）已定项3已定（明文、宁可写大）」「诞生代号（birth txg） | 8 | 三条独立理由」（`18-块里携带什么信息.md:890-891`，附录已抄）。五元组+诞生代号正是 K1a 的全部41字节，且两者都在码1头里——**过**。

码2（索引节点）：K1a 自己的定义是"（树ID,层级,key区间下界,诞生代号），要求每棵树的节点都带key区间"。现查是否每棵树都满足这个前提：

```
grep -rn "extent树.*key区间\|extent 树.*key区间" .claude/kb/     → 0 命中
grep -rn "树表.*key区间\|映射树.*key区间\|中央映射.*key区间" .claude/kb/ → 0 命中
```

D18 已定项2 正文逐字：「结论**只对记账树成立**，dirent 树那一格按本项推迟，不许外推」（`18-块里携带什么信息.md:186`，索引表见附录 D18 已定项2）。这句话本身就否定了"每棵树都带key区间"这个前提——它不但没说"每棵树都带"，还显式禁止外推。今天已定带 key 区间的只有记账树与 inode 树两棵（D18 已定项2 索引行：「记账树的节点带key区间；inode树也带……dirent树那一格推迟」）。extent 树、树表（D8 核心索引结构 的树表条目）、中央映射树自身、以及 D6 已定项3 新定的 livelist 共享树，**这四类今天全部没有 key 区间的决定**（两条 grep 均 0 命中，而 D6/D26 两个文件里出现的"key 区间"字样，经查上下文（`26-后台整理与放置回收.md:418`）说的是"结构抗老化"话题里的一个假设性比较句，不是 key 区间决定本身）。

⇒ K1a 对码2的射程今天只覆盖记账树、inode 树；extent 树、树表、映射树自身、livelist 共享树四类的索引节点**重建不出 key**——判红条件命中。**K1a 在 Q1 上不能记"全过"，只能记"部分过+缺口"。**

码3（打包记录单元）：K1a 的候选描述只给了"K1 自己要带一个码2的key"，字面没有给码3定义key形态。码3 的类身份段是「出生树ID + 打包记录类型 + 容器号 + 容器出生代」（`18-块里携带什么信息.md:800-814`，附录已抄），不含"锚点偏移"这类五元组字段——K1a 若要覆盖码3，需要重新定义一套非五元组的 key 形式，而材料没写。**按材料字面，K1a 对码3 未定义，判红条件命中（重建不出 key）。**

**若按最强形态**：假设 K1a 拥护者会补一条"码3 用（出生树ID,打包记录类型,容器号,容器出生代）四元组作 key"——码3 头里这四段全部都在（`18-块里携带什么信息.md:1027-1041`，附录已抄），可以扫描重建。这一补丁本身不违反 K1a 的精神（仍是"逻辑/出生身份"这条主线），**若按最强形态，码3 这一格可以过**，但码2 的四棵树缺口不受这条补丁影响，依然记代价。

#### K1b

码1 与 K1a 相同——过。码2/码3 明确"不进映射、走指针权威"，Q1 的判据本身是问"进映射的 key 能不能重建"，K1b 对码2/3 不试图给出映射 key，这一格对它们**不适用**（不是"重建不出"，是"根本不需要重建"，因为已经不在映射里了）。**K1b 在 Q1 上只需回答码1，判定：过。**

候选定义：「三类单元头各加8（号），扫描重建靠它」——码1/2/3 三类头里都直接写了这个代理号，扫描时逐字节读出即可，不需要任何推导或跨字段拼接。**三类全过。**

D27 容器槽：D27 已定项3 只定了"取登记表4-15里一个新码，不复用码3"，容器的"类身份段带哪些字段仍未写死，它随已定项7（nonce与MAC载体）一起定"（`27-小数据打包容器.md:306-323`，附录已抄）。槽本身的身份字段今天定的是"槽自带逻辑身份五元组"（`27-小数据打包容器.md:276-287`），K2 若要覆盖 D27 槽，需要在槽里再插一个8字节代理号字段——这是材料没写的新增字节，不是复用已有字段。**K2 对 D27 槽今天缺一处格式落点，判红条件（重建不出 key）在字面上命中，但补一个字段即可修复，不是结构性障碍。**

#### K3

候选定义已经把三段的落点讲清楚：「三类单元头各加4（出生序号）。出生树与出生txg已在头里：码1五元组的树ID段按I-1.3是出生树、另有诞生代号；码2有树ID与诞生代号；码3有出生树ID与诞生代号（I-1.1、I-1.8）」——`_d19-item6-r2-background.md:43`。

- 码2 头："树ID + 层级 + key区间 + 诞生代号 + fsid + 写序 + 载荷CRC + 预留"（`18-块里携带什么信息.md:910-916`）——树ID与诞生代号已在，**且这两段不依赖 key 区间是否带**，K3 因此不像 K1a 那样卡在"哪棵树决定带 key 区间"这个未决问题上。
- 码3 头："出生树ID | 8" 与"诞生代号 | 8"（`18-块里携带什么信息.md:1032-1038`）——同样已在。

#### K4

候选定义：「三类单元头各加10（出生落点）」——`_d19-item6-r2-background.md:44`。出生设备4+出生槽号6是新增的头字段（复用的是指针里的位置条目语义，但头里本来没有这个字段，需要新增），出生txg8同理。三类单元头补齐这10字节后，扫描重建时逐字节读出即可，与引用侧（指针里冻结的出生位置条目）一致——**过**。

⚠️ 一个需要注意的点：出生落点=出生设备+出生槽号，这是该单元**第一次被写出时**的物理位置。若单元第一次写出后从未移动，头里记的出生落点与它当前实际所在位置相同；若单元被后台整理搬迁过，头里记的出生落点与它当前物理位置**不同**——但 K4 的 key 定义本来就是"出生"落点而不是"当前"落点，所以这不构成 Q1 的问题（Q1 只问 key 能不能从头里重建出来，不问 key 指向的落点是不是当前落点，"当前落点在哪"由映射的 value 一侧回答）。**过。**

D27 容器槽：与 K2/K3 相同处境，槽今天没有为 K4 预留字段，判红条件字面命中，非结构性障碍。

### Q2 引用侧可构造：进映射那一刻手里有没有完整的 key，不多读一次单元、不多查一棵树

**判红条件（原文抄）**：「存在一条路径，进映射之前必须多读一次单元或多查一棵树才凑得出key」；**「只有那条路径是D5的释放判定时才判出局」**（F4：那条判定的注释逐字是「零次额外I/O」）——`_d19-item6-r2-background.md:58`。

F4 原文（`05-快照-空间记账机制.md:171-190`，附录已抄）：

```
判定(ptr):
    birth = ptr.birth              // 指针内联字段，零次额外 I/O
    p     = head.prev_snap_txg     // 活头头部一个标量，常驻内存
    if birth > p:  立即释放 → 进 defer 队列
    else:          追加进 head.deadlist
```

D19 已定项5 硬规则1 逐字「释放一律经映射，不经提示」（`19-块指针的结构与宽度预算.md:696`）——这意味着"释放"这个动作最终要走到映射，无论判定阶段读什么，动作阶段都要拿着映射 key 去操作映射。我把 Q2 的"D5 释放判定"理解为**判定+随后对映射的操作合起来的整条路径**，不只是判定那一步的三行伪代码，理由是：判定伪代码本身固定只读 `ptr.birth`/`head.prev_snap_txg`，四条候选都不改这两个字段的读法，若只看判定这三行，四条候选永远同分，Q2 就失去判别力；而 Q2 自己列的路径清单第一项就是"D5的释放判定"，与"解引用""deadlist处理"并列，说明它问的是这条路径在**construct mapping key** 这一步的成本，不是判定三行伪代码本身。

#### K1a

构造41字节key需要：
- 标签（查找路径给，零成本）
- 树ID=出生树（若跨头共享，需要指针携带出生树——今天指针没有这个字段，F2：「今天的指针头部31=MAC16+nonce12+算法类型1+extent偏移2，四项加满」，没有出生树的位置）
- 对象ID、锚点偏移（extent树的key给，零成本，非共享场景）
- **对象出生代（8字节）——材料原话：「④对象出生代有载体，只是不在extent树的key里……而『④从inode记录取』是一条从没被记录过的执行路径：释放一个块要先按对象查一次inode树，全仓没有任何条款写过这条路径，摊销假设也没量过」**（`_d19-item6-r2-background.md:665-666`，未定项8 正文）
- 诞生代号（8字节，今天不在指针里，同F2）

⇒ 即使假设未定项7甲落地（指针加16字节出生树+出生txg），K1a 仍然需要**对象出生代**这一段，而它的唯一已知来源是"查一次该对象的inode记录"——这是一次额外的树查找，不是零成本。**释放路径要构造 K1a 的 key，无法做到零额外 I/O，判出局。**

#### K1b

码1 的 key 定义与 K1a 完全相同（K1b 只改码2/3 的射程，不改码1 的 key 形态），因此 K1b 在码1 释放路径上与 K1a 同样需要对象出生代的额外 inode 查找——**判出局，理由与 K1a 相同**。

#### K2

候选定义给了两条路，材料原话：「D5的birth（F4）与E90的出生（树,txg）（F6）不在号里：要么指针再加16，要么D5经映射读birth（多一次查找）」（`_d19-item6-r2-background.md:42`）。

- 若走"指针再加16"（即额外携带出生树8+出生txg8，与未定项7甲字段重合）：此时 D5 判定读的 `ptr.birth` 直接对应这16字节里的出生txg，零额外I/O；K2 自己的8字节代理号也已经在指针里（候选定义「指针加8（号）」），构造 mapping key（代理号本身）同样零额外I/O。**这条路径下，K2 过。**
- 若走"D5经映射读birth"：这条路径本身就是"多一次查找"，直接撞上判红条件，且明确发生在 D5 释放判定路径上——**判出局**。

⇒ K2 的判决取决于自己选哪条路：**若坚持"8字节代理号，不额外扩指针"，则在释放路径上需要经映射读 birth，判出局；若接受指针再加16字节（与K1a的未定项7甲同等代价），则过。** 这是候选自身定义里没有排除的一个分叉，我按"候选定义给出的两条路都要评估"的原则，两条路分别记录：**默认按候选定义字面（未强制选边）判：候选给了一条会导致判出局的路径，视为该候选存在一条会触发判红的执行路径 ⇒ 判出局**；若按最强形态（指针加16），则过——这一点已在总表标注。

#### K3

候选定义：「指针加20，其中16与未定项7的甲逐字段相同」——出生树8+出生txg8+出生序号4 全部内联在指针里。构造 mapping key 需要的三段全部是指针字段的直接读取，零额外I/O，与 F4「指针内联字段，零次额外I/O」逐字吻合（K3 的 20 字节本身就是"更宽版的 ptr.birth"）。**过，且是四条候选里唯一一条不需要外部决策（未定项7）先行落地、不需要额外查找 inode 树的候选**——K1a 需要未定项7甲落地**并且**额外的 inode 查找，K2 需要在"扩指针"与"经映射查找"之间二选一，K4 需要新增出生txg 字段（见下），只有 K3 的三段从候选自身定义就已经内联齐全。

#### K4

候选定义：「指针里的位置条目冻结在出生落点、永不刷新（它同时当key的前两段用），另加出生txg8」——出生设备4+出生槽号6 复用指针里已有的位置条目字段（只是改变其更新语义：不再随重写刷新），出生txg8 是新增字段。三段全部是指针字段的直接读取，零额外I/O。**过。**

⚠️ 但这里有一个 Q2 之外、但与 Q2 同一条路径相关的重要区别，留到 Q5/Q7 展开：D19 已定项5 的"位置条目"原本语义是"随重写刷新的提示"（E96 模型「叶条目 | (版本, 落点提示)；提示只在该条目被重写时刷新，整理不改它」，`96-混合架构的一致性.md:14-32`，附录已抄）。K4 要求这个字段**从"出生后随时可能刷新"改成"出生后永不刷新"**——这是对已定项5 语义的一次收窄，构造 key 本身没有额外成本，但读到 key 之后要不要"再走一次映射跳转"的代价发生了系统性变化（详见 Q2 补充与 Q7）。

**Q2 补充：dereference（非释放）路径上的代价，四候选记法**

Q2 判据里"只有D5释放判定才判出局"，其余路径记代价。这里补记非释放路径（解引用/搬迁/checker遍历/扫描重建/模型对拍）的相对成本：

- K1a/K1b（码1）：解引用同样需要额外的对象出生代查找（除非该次解引用本来就要访问对象的 inode 记录，可摊销），**代价与释放路径相同**。
- K2：非释放路径下，只要指针/位置提示里已经带着代理号（候选定义要求），零成本；若选择不扩指针而依赖单元头，则扫描/checker路径也是零成本（头里已有代理号）。
- K3：所有路径统一零成本（头/指针双重内联）。
- K4：解引用路径上出现结构性成本——「搬过的单元提示永久过期⇒读它每次都走映射那一跳」（候选定义原文，`_d19-item6-r2-background.md:44`）。这句话说明：K4 下，**一旦某单元被后台整理搬迁过一次，它此后的每一次解引用都保证要走映射跳转**，不会像 K1/K2/K3 那样在引用它的指针/条目因其它原因被重写时"顺带"刷新回准确的当前位置。E96 已实测的提示过期率区间是 19–37%（`19-块指针的结构与宽度预算.md:688`，附录已抄，已定项5 正文），但那是在"提示随重写刷新"的假设下测出的**均值**区间；K4 的"永久过期"语义下，被搬迁过的单元的失配率会随时间单调趋向 100%，不会像今天的模型那样有机会被重写带回准确状态。**这是 K4 在非释放路径上一条持续增长、结构性的代价，我把它记在这里而不是判它出局——因为 Q2 的判出局条件明确限定在"D5释放判定"，而这里讨论的是解引用/读路径。**

### Q3 射程：候选对码1、码2、码3、D27容器槽各给不给得出一个全池唯一、且过得了第1、2格的 key

**判红条件（原文抄）**：「对某一类给不出」；「K1b例外：它主张收窄射程，那是重开D19已定项5的『唯一入口』，这一轮只记『要用户重判』，不判它出局」——`_d19-item6-r2-background.md:59`。

这一格本质是 Q1/Q2 的汇总表，这里只补两点 Q1/Q2 没展开的：唯一性、以及 D27 槽与已有决策的关系（后者展开在 Q7）。

**唯一性**：

- K1a/K1b：五元组+诞生代号 在**单个写者、单份对象生命周期内**唯一——D18 已定项7 的三条骑手理由已经论证过 fsid/树ID/诞生代号联合起来能分辨冒名与孤儿（`18-块里携带什么信息.md:929-961`，附录已抄，E88 实测「47字节的头即使开着认领规则也错分12个」，定案后头宽105/133 才不错分）。诞生代号会被崩溃重发（F5），这一点在 Q6 讨论。
- K2：全池单调号，只要水位回收正确（见 Q6/Q8），构造上就是唯一的，且不依赖任何逻辑身份字段——是四条候选里"唯一性证明最短"的一条。
- K3：出生树+出生txg 对同一 checkpoint 内的不同对象不唯一（多个对象可以在同一 (树,txg) 内诞生），因此需要出生序号这第三段来打破并列；出生序号在候选定义里是"每个(树,checkpoint)从0起的计数，在内存里发"。这一段的现场发号机制是否在崩溃重发下仍保持唯一，是 Q6 的重点，这里只指出唯一性依赖这第三段。
- K4：出生设备+出生槽号 在**单次分配**下唯一（分配器保证同一时刻一个槽只分给一个写请求），出生txg 进一步把"同一落点先后被分配给不同对象"的情形区分开（槽被释放后复用，复用时出生txg 不同）。这一组合的唯一性论证与"分配记录 + defer 窗口"的现有机制同构，材料未单独给出反例。

**D27 容器槽**：四条候选（K1/K2/K3/K4）都在这一类上遇到同一个共同空白——D27 的槽身份字段今天定的是"自带逻辑身份五元组"（`27-小数据打包容器.md:276-287`），没有为 K2/K3/K4 预留任何字段。**这不是某一条候选独有的弱点，是 D27 本身"类身份段带哪些字段仍未写死"（`27-小数据打包容器.md:306-323`）这句未定项带来的连带空白**，K1（无论a或b）恰好是唯一一条不需要新增字段就能覆盖 D27 槽的候选——这一点严格说属于 Q3 的射程判据，但它的根子在 Q7（D27 已定条款与候选的字面关系），详细论证放在 Q7，这里只标注结论：**K1a/K1b 在 D27 槽这一类上过；K2/K3/K4 在 D27 槽这一类上今天缺字段，需要新增（不是结构性做不到，是材料未定义）。**

**Q3 小结**：射程判据本质是 Q1（能重建）+ Q2（能构造）+ 唯一性的交集。K1a 在码2（四棵树缺key区间）与码3（未定义）两处不满射程要求；K1b 明确放弃码2/3 的射程（记"要用户重判"，不判出局）；K2/K3/K4 在码1/2/3 三类上射程完整，但四条候选在 D27 槽上都需要新增字段（K1 除外，因为它与 D27 已有决定同型）。

### Q4 跨头共享与 reflink：N≥2 个引用者拿不拿得到同一个 key

**判红条件（原文抄）**：「存在一个共享构造，两个引用者凑出的key不同，或有一个凑不出」——`_d19-item6-r2-background.md:60`。

`04-校验和位置.md:269-271`（附录已抄）：「reflink 虽然是 day-1 承诺，但它共享的是**整个单元**，两边偏移都是0——那是引用共享，不是切分」。这句话确认 reflink 场景下存在"同一物理单元被两个不同逻辑位置引用"的构造，且是 day-1 范围内的承诺，不能当作"以后再说"搁置。

#### K1a

**反例（机制推导，非引用材料结论）**：设文件 A 的 offset 0 首次写出一个数据单元，其五元组是 (标签1, 树ID_A, 对象A, 对象A出生代, 锚点偏移0)，这组值被写进该单元的头（D18 已定项3）。随后文件 B 对该单元执行 reflink，文件 B 的 extent 树里出现一条 key = (locality_B, 对象B, offset_100) 的条目，指向同一个物理单元。

K1a 的候选定义原文是"对象ID与锚点偏移（extent树的key给）"——若这句话按字面执行，**文件 B 侧计算 mapping key 时，会从文件 B 自己的 extent 树条目取出 (对象B, offset_100)**，而不是单元头里记录的 (对象A, 锚点偏移0)。这样一来：

- 文件 B 算出的 key ≠ 单元头本身记录的五元组（Q1 判据："重建出的key与引用侧的可能不同"）
- 文件 B 算出的 key ≠ 文件 A 侧原本算出的 key（Q4 判据的直接触发条件）

⇒ **按候选描述字面执行，K1a 在 reflink 场景下两个引用者凑出的 key 不同，判红条件命中。**

**若按最强形态**：K1a 拥护者大概率会说"这句'从extent树key给'只对首次写出成立，reflink 引用侧应当显式携带被引用单元的出生 (对象ID,出生代,锚点偏移)，不是从自己的extent树key现算"。这个修正是自洽的，但代价是：reflink 引用侧的指针需要显式携带这三段（对象ID8+对象出生代8+锚点偏移8=24字节），**加上未定项7甲已经要求的出生树+出生txg（16字节）**，reflink 场景下的指针额外开销逼近整条41字节 key 的量级，而不是候选定义暗示的"部分复用现有字段"。**若按最强形态，K1a 在 Q4 过，但代价从候选定义暗示的"零/16字节"上升到"逼近41字节"这一量级（不作为判负依据，只记代价）。**

#### K1b

码1 与 K1a 同一个反例、同一个"最强形态"修正，结论相同。

码2/码3（走指针权威）：D19 已定项5 依据表格逐字「释放一律经映射，不经提示（E96实测：按提示解落点会误放约5000次/200轮）」（`19-块指针的结构与宽度预算.md:696`，附录已抄）。这条实测是针对"跨头共享+位置条目当权威"这个组合专门测出来的——K1b 把码2/3 退回到与这条实测完全相同的处境（位置条目权威、不经映射）。**K1b 对码2/3 的跨头共享正是 E96 已经实测判负的那个组合，判红条件命中，且不是我自己的推导，是仓里已有的实测数据。**

#### K2

代理号是不透明句柄，出生时分配一次，此后不随引用者变化。COW 克隆/快照复制指针字节时，代理号字段随指针原样复制到新的引用者手里，**不需要区分"出生"与"引用"两种树身份，也不需要额外携带对象级字段**。reflink 场景下，文件 B 的新 extent 树条目直接把从别处拿到的代理号写进自己的指针（在 reflink 操作实现时，代理号是复制粘贴的对象，不是现算的），两个引用者天然拿到同一个值。**过，且是四条候选里机制最简单的一条**——它不依赖"出生树"这类需要跨头区分的概念，因为它压根不含树身份字段。

#### K3

出生树、出生txg、出生序号三段全部是**出生时刻**固定的属性，不随后续引用者变化。COW 共享把指针字节复制给新引用者时，这三段随指针原样复制。与 K1a 不同，**K3 的候选定义从一开始就把这三段放在指针里（"指针加20"），不依赖"从当前上下文现算"这种会在 reflink 场景下算错的机制**——K3 没有 K1a 那种"从extent树key给"的陷阱。**过。**

#### K4

出生设备+出生槽号+出生txg 同样是**出生时刻**固定的物理属性（首次分配的槽位），不随后续引用者/搬迁变化。COW 共享复制指针字节（含冻结的位置条目）给新引用者时，这三段原样复制。**过。**

**Q4 小结**：K2/K3/K4 三条候选的 key 组成天然是"出生时刻固定、随指针字节复制传播"的属性，对 reflink/跨头共享天然一致。K1a 按候选定义字面在 reflink 场景下会算错（两个引用者不同 key），需要补一条"显式携带出生五元组"的修正才能过，代价上升到接近整条 key 宽度；K1b 的码1 与 K1a 同病，码2/3 明确复现了 E96 已实测判负的组合。

### Q5 搬迁不变：搬迁一个单元之后，key 是否不变、引用者一个都不用改

**判红条件（原文抄）**：「搬迁后key变了，或有引用者要改」——`_d19-item6-r2-background.md:61`。

F1：「单元头随搬迁不变：指针里的校验和/MAC罩整个单元 ⇒ 搬迁只能逐字节拷贝，头里写的都是出生那一刻的值」（`invariants.md` I-2.3 + `09-加密.md:471`）。

#### K1a / K1b（码1）

五元组+诞生代号全部是单元头里"出生那一刻"写入的值，搬迁按 F1 逐字节拷贝，这些字段原样跟着搬。**过。**

#### K2

代理号住在单元头（候选定义："三类单元头各加8（号）"），搬迁逐字节拷贝头部，代理号原样跟随。**过。**

#### K3

出生树/出生txg/出生序号全部住在单元头，同理原样跟随搬迁。**过。**

#### K4

这一格是 K4 候选设计的核心目标：出生设备+出生槽号+出生txg 定义为"出生"而非"当前"物理位置，候选定义明确要求这三段"冻结、永不刷新"。搬迁改变的是单元的**实际**物理位置，但 K4 的 key 记录的是**出生**物理位置，这两者在候选定义里从一开始就是脱钩的——搬迁天然不改变"出生落点"这个历史事实。**过，且是四条候选里对这一问回答得最直接的一条：它不是"搬迁恰好不影响 key"，而是"key 的定义本身就是为了不受搬迁影响而选的"。**

**Q5 小结**：四条候选在这一格上全部通过，没有分歧。这一格不构成候选间的判别力——它只是确认"key 取逻辑/出生属性而非当前物理位置"这条大方向本身是对的，四条候选都遵循了这条大方向（K4 甚至把它做成了自己的定义核心）。真正的分歧在 Q2（构造代价）与 Q7（与 D27 的一致性），不在这一格。

### Q6 跨崩溃唯一：checkpoint 号崩溃后会被重发，候选的 key 在盘上是否仍唯一指向已发布时间线上的那个版本

**判红条件（原文抄）**：「该候选的key在回退之后同时指向两个都在盘上、内容不同、都会被认领的单元，而仓里现成的解法（C113定案的写序+实例表）罩不到它」；**「若同一个洞对四条候选都成立，这一格不是候选之间的判据（D19未定项7已经采用这条判据），只记『共同前置』」**——`_d19-item6-r2-background.md:62`。

F5：「birth是『块被发布的那个checkpoint号』，崩溃后会被重发」。

**机制推导（正推腿自己的推导，不是引用材料现成结论）**：

设 checkpoint N 的第一次尝试（实例 i）写出一个单元并崩溃（根未提交）；重试时checkpoint 号被重发为 N（还是实例 i，或递增为实例 i+1，取决于崩溃点），该重试再次写出一个**内容不同**的单元，恰好落在与前一次尝试相同的 (树, N) 坐标下。此时盘上同时存在两个单元：一个来自失败的尝试（"孤儿"），一个来自成功的重试（"活单元"）。

这个构造对**任何以 (树, checkpoint) 或 (对象, 诞生代号) 为部分 key 的候选**都成立——因为 (树, txg) 或 (五元组, 诞生代号) 本身正是"哪次 checkpoint 尝试写的"这件事的坐标，而 checkpoint 号被重发正是 F5 明写的事实。四条候选的 key 分别是：

- K1a/K1b：五元组(含诞生代号) —— 诞生代号=出生txg 是重发对象
- K2：全池单调号 —— 见下面对水位回收机制的分析
- K3：出生树+出生txg+出生序号 —— 出生txg 是重发对象，出生序号是"在内存里发"、按(树,checkpoint)从0计数，重试时同样会重新从0计数
- K4：出生设备+出生槽号+出生txg —— 出生txg 是重发对象

**四条候选的 key 里都含有一个"会被 checkpoint 重发影响"的分量，这本身是共同的。**

**现成解法能不能罩住**：仓里已有的解法是 C113 定案的"写序（实例代号+事务号）+ 实例表"（`checks-owed.md:120`，附录已抄）——每个单元头里另有一个**独立于候选key**的写序字段，记录"是哪个实例写的"，配合实例表（记录哪个实例已发布）可以判定一个单元是否"已发布"。孤儿单元（失败尝试写出的）按 I-1.2「判不成已发布者必是未发布的撕裂事务垃圾或被抛弃时间线的残留」（`invariants.md:1637`）被过滤，不会进入"已发布"集合，从而也不会被插入映射（映射只应收录已发布单元）。

这条过滤机制**不依赖候选 key 选哪一族**——它靠的是写序字段（每个单元头本来就有，与 K1/K2/K3/K4 的选择无关，见 D18 已定项7 字段表，写序10字节对码1/码2/码3 都已经存在）。只要"先用写序+实例表过滤已发布性，再构造映射key并插入映射"这个顺序被遵守，四条候选的 key 在**已发布单元集合内部**就不会再出现"内容不同但key相同"的冲突（因为已发布集合本身对每个 (树,txg) 或每个 (五元组,诞生代号) 至多保留一个胜者，这正是 I-1.8 归并规则的职责）。

⇒ **按 Q6 判据自带的分支条件（"若同一个洞对四候选都成立，只记共同前置"），我判定这一格是共同前置，不构成候选间判别力**——四条候选的 key 分量都含有会被崩溃重发的字段，但都同等依赖"写序+实例表在构造映射key之前先做已发布过滤"这道现成闸门，这道闸门本身与候选选哪一族无关。

**K3 的一个额外细节，记在这里但不改变共同前置的判定**：K3 的"出生序号"是**在内存里现场发号**，不像出生树/出生txg 是从已有字段复用——这意味着若两次 checkpoint N 的尝试（孤儿与活版）各自发了独立的出生序号计数（都从0开始），孤儿与活版可能凑出完全相同的20字节 key。但正如上面分析，孤儿本身会在"写序+实例表"这道闸门被过滤掉，不会进入映射构建阶段，所以这个细节不构成 K3 独有的判负——它只是再次印证"共同前置"这道闸门对所有候选都必需，而 K3 恰好把这个必需性摆得最明显。

**K2 的水位回收机制核对**：候选定义要求"水位照D8已定项8②的装置住根记录，取根环里全部根记录的max"。D8 已定项8② 正文对**结构完全相同**的树ID水位回收机制专门论证过"丙-2唯一盖不住的那一格，判为不是错误"（`08-核心索引结构.md:1284-1287`，附录已抄）：「某个checkpoint分配了树ID42、写出带42的单元头，根没写成就崩了⇒水位随那个根一起丢⇒下次挂载重发42，而盘上留着带42的孤儿单元。判它不构成错误的依据……决定性的一条：孤儿与活版共用五元组本来就是常态……正是C113定案P1给三类身份段统一加10字节写序要解决的东西」。K2 若采用同一套水位回收机制，会继承同一条"判为不是错误"的依据——**这进一步支持"共同前置"这个判定**：连水位回收本身重发号码这件事，仓里已有先例把它判定为"不构成错误"，理由正是写序字段能兜底，不依赖候选key本身的唯一性。

**Q6 小结**：这一格四条候选同分，都记"共同前置：依赖写序+实例表在插入映射前完成已发布过滤"。这不是我回避判别，是判据本身的分支条件（"若同一个洞对四候选都成立，只记共同前置"）字面命中——我逐条验证了四条候选的 key 分量确实都含会被重发的字段，也验证了现成解法（写序+实例表）在结构上不依赖候选选哪一族，两步都做完，共同前置的判定才站得住。
