# 背景：扩展点字节上限，去掉「省空间」这条判据之后重推

singlefs 是一个从零设计的 COW 文件系统（Rust，无代码，格式设计阶段）。

## 本轮的新前提（用户定案 2026-08-30）

**「本工程比谁省空间」不是本工程的判据。省空间从来不是目标。**

这条与本仓已有的规则同向：`.claude/rules/fs-design.md`「不为省空间牺牲自包含」逐字写着
「遇到『这个字段能不能省掉 / 能不能压窄 / 能不能现算』这类权衡，**默认答案是不省**——
除非有实测证明省下来的那部分是瓶颈」，理由是「省下来的是空间，省掉的是『一个单元单独捡起来还能不能自证』」。

## 被推翻的那一步

E44（一个已跑完的实验）曾用「D21 正文说本工程在 128 KiB 单元上比 ZFS 省」推出
扩展点上限 ≤ 19 字节（108 + N < 128）。按新前提，这条推导的**整条比较轴**不成立，
不是「循环论证所以作废」那么轻——**它引用的那个判据本工程根本不采纳**。

## 仍然成立的实测（N=5 轮逐字节一致，14 单测全绿，12 条变异全被抓）

| 量 | 值 |
|---|---|
| 下界：扩展点里放一个合法指向 | 区间 [7, 13]：落点 7（dev 1 + 物理偏移 6）／带长度 9／带密文校验和 11／都要 13 |
| 长度字段 2 字节的量程 | 65535 字节，**装不下一个 128 KiB 单元** |
| 树高上界（每个单元都带扩展点）| 2 KiB 节点在 N=865 时树高 5→6；4 KiB 档 1473、16 KiB 档 6081、64 KiB 档 55233 |
| 树高上界（只有数据单元带）| 不存在，四档全部「永不涨」 |
| 单元元数据字节数 | 本工程 2 副本 108.0 B、4+2 条带 152.0 B；ZFS 128.0 B；btrfs 4 KiB 82.5 B、128 KiB 207.3 B |

## D21 关于扩展点的已定条款

- 扩展点 = 一段空间 + 一套接口，开线方可以在里面放一个**指向**，做本工程不理解的事；
- 大小**按线在超级块里声明**（开线方自己定，可为 0），**上限由本仓定一个固定字节数**；
- 上限**取固定字节数，不按单元大小取比例**，理由是「它承载的是每对象的语义字段，与单元多大无关」；
- 五条硬约束里与本轮相关的：① 必须落在校验 / 认证覆盖之内（加密开启时是 AEAD 覆盖）；
  ③ 大小必须由格式声明，通用工具（scrub、扫描重建、救援）要能跳过它；
  ④ 指向的目标空间必须走本工程的分配与记账，从显式配额分配，配额在提交时增量维护，
  且 ENOSPC 准入要「进门前算最坏情况」；⑤ 指向不许指向核心层对象。
- 索引是**派生态**（丢了只是慢），单元 + 记账 + 根是**权威态**。

## 要被攻击的推论 Q

1. 上界 A（19 字节）不是「循环所以作废」，而是**整条比较轴不构成判据**，该连同它的理由一起删掉。
2. D21 那张与 ext2/ext4/btrfs/ZFS 的对照表，唯一合法用途是驳「我们很奢侈」这个前提，
   **不能当上界用**。
3. 剩下唯一由**功能**推出来的边界是**下界**。上界该由「核心层必须容忍的最坏情况」来定，
   而那笔代价（AEAD 要覆盖的字节、通用工具跳过它、线内几何一致性）都随 N 线性且很小
   ⇒ **没有把上限定窄的理由**，与「自描述数据宁可写大一点」同向。
4. ⇒ D21 未定项 2 该换问法：不问「上限取多少字节」，问「这个上限要保护核心层的哪一个最坏情况」。
