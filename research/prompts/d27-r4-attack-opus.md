## 一、未定项 5（活槽计数住容器索引的 value）——攻

### 1.1 主攻：这条推论**方向对、落点错**，因为同一形状的量在仓里已经有定案载体了

材料的推论只走了两步：住容器里 ⇒ 撞已定项 10 ⇒ 所以住容器索引。**第二步没有论证**，
而仓里对「一个单元有多个活引用，计数住哪」这件事**已经有 2026-09-06 的用户定案**：

```
.claude/kb/decisions/21-权威态与派生态的分界.md（已定项 6 定案表，第二行）
| **共享计数** | 「除了出生所有者，还有没有别人引用我」 | **不在本项射程内**：它是 D5（快照 / 空间记账机制） 前提 3 的问题（有第二个活引用时摘掉其中一个不构成 death），载体是 D5（快照 / 空间记账机制） 2026-08-30 已经收口的**稀疏旁表**（逐字「D5（快照 / 空间记账机制） 为主 + 稀疏旁表为辅」）。**那张表的字段表仍未定，欠在 D5（快照 / 空间记账机制） 那边** |
```

**活槽计数就是这个量的每容器聚合形态。** 一个槽「活着」的判据是「还有没有任一活头的映射条目指着它」，
逐字就是上表左列那句话；活槽计数 = 对容器里 N 个槽逐个求这个谓词再求和。
⇒ 把它塞进容器索引的 value，是**在一条用户定案已经指定过载体的量上另开第二个载体**，
撞 `.claude/singlefs-ai-sop/rules/kb-discipline.md` 第 4 条（同一事实只许一处权威记录），
并且要按门禁阶段 `.claude/gate.d/35-user-verdict-owed.sh` 记一笔未还的账。

**更硬的一条：D27（小数据打包容器） 整条压根没触发它该触发的那个重开条款。**

```
.claude/kb/decisions/05-快照-空间记账机制.md:98
⚠️ **任何引入「同一块的第二个活引用」的特性，必须先重开 D5（快照 / 空间记账机制）。**
```

一个容器就是一个被 N 条中央映射条目引用的单元 —— N 个不同的逻辑身份指同一块。
这**逐字**就是「同一块的第二个活引用」。而 D5（快照 / 空间记账机制） 在同一段里写明了不重开会怎么坏：

```
.claude/kb/decisions/05-快照-空间记账机制.md:95-96
而判据只看 `birth` 与 `prev_snap_txg`，两个引用的 birth 完全相同
⇒ 第一次摘除就判「立即释放」⇒ 另一个引用悬空 ⇒ **数据丢失**。
```

把「两个引用」换成「一个容器的 N 个槽」，这段话逐字成立：**同一个容器里 N 个对象的 `birth` 必然完全相同**
（它们是同一次写出的同一个单元），所以第一次「搬出去」就满足现行释放判据 ⇒
**容器被立即释放，另外 N−1 个对象全部悬空。** 4 KiB 档 N−1 = 6，512 B 档 N−1 = 57。

⇒ **活槽计数不是一个「顺手补上的字段」，它是在 D5（快照 / 空间记账机制） 的重开条款外面私接的一个引用计数。**
D5（快照 / 空间记账机制） 上一次被触发（D6（快照实现模型） 已定项 1 的跨头共享）时的收口不是加计数器，
逐字是「**不是把 D5（快照 / 空间记账机制）换成全域引用计数**」（`05-快照-空间记账机制.md:102`）。

**什么现象会推翻这一条**：在 D5（快照 / 空间记账机制） 或 D21（权威态与派生态的分界） 里找到一句
把「同一个单元内多个子对象」显式排除在「第二个活引用」之外的话。本腿全文读过 D5（快照 / 空间记账机制）
已定项 2 / 3 / 4 / 5 与 D21（权威态与派生态的分界） 已定项 6，没有这句；有这句就该被指出来。

### 1.3 崩溃点：题目要的那个**不存在**，而真正的分家在三处别的地方

本腿老实报告：**在正常提交语义下找不到让活槽计数与中央映射分家的崩溃点。**
理由是两者都是普通树，同一次根切换发布；而部分重放那条路按 I-1.2（块头写序已发布） 逐字只放行码 1：

```
.claude/kb/invariants.md:21（I-1.2）
…码 1 要 b ≤ T_pub ∨ n ≤ W、码 2 / 3 要 b ≤ T_pub…
```

⇒ 一次未完成的 checkpoint 里，映射叶（码 2）与容器索引节点（码 2）**一起**判未发布，不会一个过一个不过。

**但同一条谓词给出了另一个更坏的东西**：那次崩溃里，新写出的码 1 单元 `U`（搬出去的那一份）
可以凭 `n ≤ W` 判**已发布**，而映射仍指着容器 C 里那个槽。此刻盘上**同一个五元组有两份可读的已发布字节**：
`U` 是码 1，槽在码 3 里。谁是现行版本？**全仓没有规则**：

```
.claude/kb/invariants.md:27（I-1.8 归并后版本全序）
码 1 / 3 的可读已发布单元按「类身份段全部字段含写序」归并成组之后，同 key 的各组两两全序键不等——码 1 的键是写序，码 3 的键是 (诞生代号, 实例代号, 事务号) 三元…
```

I-1.8（归并后版本全序） 的「同 key」对码 1 是五元组、对码 3 是容器四元组，**两个 key 空间不相交**，
两个全序键也是不同的元组，条文里没有一句把它们放在一起比。
在 D27（小数据打包容器） 之前这不是洞：码 3 里装的是墓碑 / inode / 退役 / 实例表记录，**从来没有一条码 1 的对象身份出现在码 3 容器里**。
D27（小数据打包容器） 是**第一次**让同一个五元组同时具备码 1 与码 3 两个物理载体。
⇒ **跨类择新在全仓无输入**，而 C113（扫描重建时多版单元的现行版本判定无输入） 的定案 P3 只解了类内。
后果是扫描重建可能选中那个**死槽**，用户静默读到旧数据——这条不需要活槽计数存在就已经成立，
所以它其实是**未定项 3 / 8 的账，不是未定项 5 的账**。

真正让计数与映射分家的是三处**非崩溃**路径：

| # | 分家在哪 | 有没有已定条款检得出 |
|---|---|---|
| 1 | **多可写头**：计数只有出生树那一份，别的头的映射改了它不知道（见 1.4） | **没有**。I-1.7（打包容器合法与判定顺序） 只判容器内部、I-1.8（归并后版本全序） 只判同类同 key、I-3.1（已分配统计对得上） 判的是总量 |
| 2 | **扫描重建**：计数在盘上零输入（已定项 10 禁止它住容器），只能靠遍历重算，而映射本身也正在被重建 | **没有**。逐字：「自举收敛在「中央映射自己的节点」那一层，而那一层零条款」（`.claude/kb/decisions-history.md:869`）|
| 3 | **多算方向的泄漏**：计数偏大 ⇒ 容器永不释放 | **没有，而且泄漏量不进任何统计量**——与 C128（清扫准入对 parity 格两支都判不出） 逐字记过的同一个形状：「泄漏量不进任何统计量（D5（快照 / 空间记账机制） 已定项 4 的「不可回收字节」记的是钉住）」 |

在计数偏大时**照样平账**——容器还被引用着、字节还算在已分配里，只是永远不会被释放。

装载纪律③（一容器一棵树）里那棵树是**出生树**（`18-块里携带什么信息.md:718` 逐字「树维取**出生树**」）。
⇒ 计数只有一份，住出生树 T0 的容器索引里。类型 1 已有的先例逐字禁止跨头写它：

```

**类型 1 容器归写者树独占**（C113（扫描重建时多版单元的现行版本判定无输入） 定案 P6，2026-09-05）：…克隆不把 origin 的类型 1 容器收进自己的容器索引，回收（重写）只由写者树做…
```

**具体反例（不需要崩溃，纯正常操作）**：4 KiB 档，容器 C 住 7 个对象，出生树 T0，
建一个可写克隆 T1（D6（快照实现模型） 已定：每头一棵自己的树）。

| 0 | | | 7 | 7 |
| 1 | 覆写槽 1–4（搬出去） | | **3** | 7（T1 还引用 1–4）|
| 2 | | 覆写槽 5–7（搬出去） | **3**（T1 改不了 T0 的索引）| 4（T0 引 5–7、T1 引 1–4）|

### 1.5 「两个头各自搬出同一个容器里的不同对象」——上表第 2 步就是答案

结论：**计数变成一个既不是上界也不是下界的数**。第 2 步它读 3，真值是 4（偏小 ⇒ 早释放 ⇒ 丢数据）；
如果反过来只让写者树递减而克隆头的搬出不计，它就恒偏大（⇒ 永不释放 ⇒ 无声泄漏）。
**两个方向各有一种失败，没有一个方向是安全的**，因为单一计数器表达不了「哪些槽被哪些头引用」这张集合。

### 1.6 还有一笔材料没算的：递减发生在**前台写路径**上

已定项 1 逐字「**写路径一个字节都不改**」。但覆写一个**已被打包**的对象是前台写，
按材料的答案它现在多一棵树要 COW（容器索引）。代价数：

- 一次容器索引 COW ≈ 叶 1 + 内部 2 + 根槽，按 E109（位置权威三臂的运行时代价） 同口径
  （`19-块指针的结构与宽度预算.md:139` 逐字「映射那一份是 66 048 字节（映射树叶 1 + 内部 3 + 一个根槽）」）
  ⇒ **约 66 048 字节**。
- 覆写一个 512 B 对象本来要写：新码 1 单元 32768 × w=2 = 65 536，加映射 66 048。
  ⇒ 加上容器索引后 **197 632 字节，涨 50.0%**；相对 512 B 的用户数据是 **386 倍写放大**。

⇒ 「写路径一个字节都不改」这句话在覆写小对象这条路径上**不再成立**，而 E114（小数据打包容器的总账）
与 E116（打包容器的账·补元数据写与整理策略） 两本账都没有这一笔（E116 的 `move_write` 只有容器 / 映射 / 分配记录 / journal 四项，
`research/e7-index-bench/src/bin/e116_pack_settle.rs:141-159`）。

**替代方案（本腿给的）**：递减改成**惰性**——不在提交时维护，由整理自己在扫过容器时用
「槽的五元组去映射里点查，看还指不指着我」重算。代价是每容器 `cap` 次点查，收益是前台零改动。
但这么一改，材料给的第一格论证（「容器全空可以释放是生命周期判定，不许遍历」）就自己塌了：
**能惰性算的量，按定义不在第一格。**
⇒ **未定项 5 是个二选一，材料把两边写成了一边**：
① 提交时维护 ⇒ 前台多一棵树、已定项 1 那句话要改口径；
② 惰性重算 ⇒ 第一格论证撤回，「容器全空」不再是即时判定，释放延迟要单独给数。

## 二、未定项 6（key 序 + 整片叶批量 + 冷对象迟滞）——攻

### 2.1 ①「key 序遍历装不满容器」不是它的毛病——先把这条排除掉，省得下一轮再花一轮

材料担心「相邻 key 的对象大小差很多」。**贪心首次适应在 ≤ 4096 的界线下有一个闭式下界**：
每个合格对象占 `size + 47 ≤ 4143` 字节，所以容器只会在剩余空间 < 4143 时关闭
⇒ 已用净荷 > 32665 − 4143 = **28 522 字节**，即净荷利用率 **> 87.3%**，与对象大小的分布无关。

| 档 | `cap` | 已用净荷 | 尾部空洞 | 占单元 |
|---|---|---|---|---|
| 512 B | 58 | 32 422 | 243 | 0.74% |
| 4 KiB | 7 | 29 001 | 3 664 | 11.18% |
| 最坏（下一个是 4096 且刚好放不下）| — | — | **4 142** | **12.64%** |

⇒ **装填率不是未定项 6 的风险**。真正的风险在下面两条，而材料一条都没提。

### 2.2 ②（真正的攻击）key 序的优势是 E116（打包容器的账·补元数据写与整理策略） 的一个**建模假设**造出来的，不是顺序本身的性质

E116（打包容器的账·补元数据写与整理策略） 的 `policy 0`（key 序）逐字把映射叶数写成常数：

```rust
research/e7-index-bench/src/bin/e116_pack_settle.rs:139-145
    let map_leaves_total = n.div_ceil(map_leaf_cap());
    let map_leaves = match policy {
        0 => map_leaves_total,                                   // key 序：每片叶只 COW 一次
```

`n` 是**可搬对象数**，`map_leaves_total = n/267`。这等于假定**中央映射里只装可搬对象**。
而 D19（块指针的结构与宽度预算） 已定项 5 逐字要求「第一个事务写出的每个数据单元都要有一条映射条目」
（`.claude/kb/first-txn-layout.md:73-74`）⇒ **映射里装的是全池每一个数据单元**，
可搬的（≤ 4 KiB 且冷）只是其中一小撮。

设 ρ = 可搬对象占全部映射条目的比例。key 序保证的是「**每片叶只 COW 一次**」，
**不保证叶数少**——要凑齐 `n` 个可搬对象要扫 `n/ρ` 条条目。把 ρ 放进 E116（打包容器的账·补元数据写与整理策略）
自己的账（其余四项一字不改），回本比逐格如下（`uniform` = 可搬对象等距分布；`poisson` = 随机独立分布）：

| 档 | ρ = 1（E116 的取样点）| ρ = 10% | ρ = 3% | ρ = 1% | ρ = 0.5% | ρ = 0.375% |
|---|---|---|---|---|---|---|
| 512 B `uniform` | **0.0444** | 0.0787 | 0.1676 | 0.4217 | 0.8028 | **1.0569（不回本）** |
| 512 B `poisson` | 0.0444 | 0.0787 | 0.1676 | 0.3953 | 0.6022 | 0.6835 |
| 4 KiB `uniform` | **0.3441** | 0.3835 | 0.4854 | 0.7767 | **1.2137（不回本）** | 1.5050 |
| 4 KiB `poisson` | 0.3441 | 0.3835 | 0.4854 | 0.7465 | 0.9837 | **1.0769（不回本）** |

**回本 = 1 的临界密度**：

| 档 | `uniform` | `poisson` |
|---|---|---|
| 512 B | ρ = **0.397%**（每 252 条一个，1.06 个/叶）| ρ = **0.0445%**（每 2247 条一个，0.12 个/叶）|
| 4 KiB | ρ = **0.662%**（每 151 条一个，1.77 个/叶）| ρ = **0.476%**（每 210 条一个，1.27 个/叶）|

**这个 ρ 不是杜撰的，它就是 D25（目标负载优先级） 定的负载形状**：主负载逐字是「seq 顺序大文件」
（`25-目标负载优先级.md` 负载表，权重「主」），而 smallfile 那一行权重是「次」。
顺序大文件的每个非尾 extent 声明长度都是 32768 ⇒ **不合格**；一个文件只贡献一个可能合格的尾。
⇒ 在主负载占多数的池子里 ρ 天然是千分之几量级。

举一个能算的取样点：1 TiB 大文件数据 = 33 554 432 个单元，外加 100 000 个小对象
⇒ ρ = 0.297%，落在 512 B 那档 `uniform` 临界（0.397%）**以下**。

⇒ **结论**：「沿 key 序走」这条答案的依据（回本比 0.0444 / 0.3441）**只在 ρ = 1 时成立**，
而 ρ = 1 的意思是「池子里除了待打包的小对象什么都没有」。
**判据不是遍历顺序，是「一次事务改的映射条目集中在几片叶上」**，而集中度由 ρ 决定，不由顺序决定。

**什么现象会推翻这一条**：把 E116（打包容器的账·补元数据写与整理策略） 加一维 ρ 重跑，
若三档回本比对 ρ 不敏感（比如映射那一项在总账里本来就可以忽略），本条作废。
本腿按 E116（打包容器的账·补元数据写与整理策略） 自己的四项账算过，映射项在 ρ = 0.375% 时占总写的 **96.1%**（512 B 档），所以它敏感。

### 2.3 ②的姊妹：材料把「顺序」和「批量」当成两个独立决定，而 E116（打包容器的账·补元数据写与整理策略） 的数说它们是一个

E116（打包容器的账·补元数据写与整理策略） 结论二那张表的最后一列材料没抄：

```
.claude/kb/experiments/116-打包容器的账·补元数据写与整理策略.md（结论二表）
| 512 B | **2.0921** | 1.7692 | 0.8231 | 0.1636 | 0.0455 |
```

最后一格是 `b` = 100 000（一批干完）。**凑满序在 b = N 时是 0.0455，key 序是 0.0444，差 2.5%。**
⇒ 顺序的效应在 `b` = 1 时是 47.1 倍，在 `b` = N 时是 1.025 倍。
材料给「取 key 序」的依据逐字是「凑满序在 `b` ≤ 512 时…不回本」——
**那是在一个 `b` 的取样点上取的值，而材料同一段又规定批量按整片叶取（即大 `b`）**。
两半放在一起，「顺序」这一段就没有依据了。撞 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`
逐字「我是不是**只在一个点**上取了值」。

**建议的改法**：未定项 6 的「顺序」与「批量」合并成一条可判的量——
**「一次整理事务里被改的映射条目，落在几片叶上」**，并给它一个上界（比如 ≤ 被搬对象数 / 8）。
这条量对两种顺序都可判、可观测，且直接就是回本比的自变量。

### 2.4 ③（新的）迟滞的代价整个落在 E116（打包容器的账·补元数据写与整理策略） **不计分**的那一项上

「只搬连续 K 个 checkpoint 没被改过的对象」这个谓词**零格式代价**——
`当前 checkpoint − 诞生代号 ≥ K`，诞生代号在码 1 类身份段里已经有（`18-块里携带什么信息.md:531` 一带的字段表，
数据单元类身份段 105 = 42 + 33 + 8 + 8 + 10 + 4）。这一点材料是对的，本腿不攻。

**攻的是代价落点**：诞生代号住**单元头**，不住映射 value（`.claude/kb/first-txn-layout.md:65-70`
的映射条目字段表只有 key 33 + 位置条目 14×w）。
⇒ 整理要判一个对象冷不冷，**必须先把这个单元读回来**。
⇒ 迟滞让整理**读它不搬的那些对象**，而 E116（打包容器的账·补元数据写与整理策略） 的回本比分子是 `move_write`，
`move_read` 单列且不进回本比（`e116_pack_settle.rs:165-171`）。
若一半的候选没通过迟滞，512 B 档 `move_read` 从 3 276 800 000 涨到 6 553 600 000 字节，**回本比一个数字都不变**。

**最便宜的修法（本腿给）**：把 `声明长度`（2 字节）与 `诞生代号`（8 字节）加进映射 value。
代价可算：映射条目 61 → 71，叶扇出 267 → 229，映射叶数 ×1.166。
只加声明长度（2 字节）则 61 → 63、扇出 267 → 258、叶数 ×1.035。
这一笔归 D19（块指针的结构与宽度预算） 已定项 5 欠账 ①（「映射条目的字段表」，逐字未定）。

### 2.5 ③ 迟滞 K 的算式（材料要算式不要数）

用 E116（打包容器的账·补元数据写与整理策略） 自己的量写：设 `q(K)` = 通过迟滞被搬走、却在回本视界内又被覆写的比例，
`P` = ρ = 1 且 q = 0 时的回本比（512 B 0.0444 / 1 KiB 0.0784 / 4 KiB 0.3441），则

> **有效回本比 = `P / (1 − q(K))`，要求 ≤ 1 ⇒ `q(K) ≤ 1 − P`。**

⇒ 512 B 允许 `q` 高到 **95.6%**，4 KiB 允许 **65.6%**，8 KiB 要求 `q < −1.4%`（不可能，与已定项 2 的界线一致）。
**这个约束松到几乎不约束任何 K**：要让迟滞变成决定性的一项，`q` 得先大于六成。
⇒ **迟滞在三段里是最不重要的一段**，而材料把它与顺序、批量并列。
真正卡住符号的是 2.2 的 ρ 和 2.3 的叶集中度。

### 2.6 ③「迟滞与 D26（后台整理与放置回收） 已定项 1 的触发水位怎么合」——**合不上，两处硬冲突**

**冲突一：三个起跑水位里没有一个看得见补齐浪费。**

一个装满 512 B 小文件、每个占一个 32768 单元的池子：落点连续 ⇒ `runs` 小 ⇒ `F` 低；

`.claude/rules/fs-design.md:23` 逐字「「释放空间这个操作本身不需要申请空间」也压在同一个数上」。

**冲突二（更硬）：停机谓词与 key 序在数学上不相容。**


key 序整理释放的原单元**按落点是随机散布的**（key 序与落点序无关）。
一个聚簇段要变全空，得它里面每个单元都被释放。设段含 `s` 个单元、全池释放比例 `f`，

⇒ **停机谓词实际上永不成立** ⇒ 意图永不完成 ⇒ 按已定项 1 第 3 条

## 三、未定项 8（①③继承 / ②不取 / ④换槽目录）——攻

### 3.1 ③「一容器一棵树」的代价：算得出算式，**上界全仓没有**

**算式**：容器数从 `⌈N/cap⌉` 变成 `Σ_t ⌈N_t/cap⌉ ≤ ⌈N/cap⌉ + (T − 1)`。
收益倍数 = `N / Σ_t ⌈N_t/cap⌉`，**分界在 `N_t ≥ cap`**：

| 档 | `cap` | T = 1 | T = 16 | T = 64 | T = 1024 | `N_t` = 2 | `N_t` = 1 |
|---|---|---|---|---|---|---|---|
| 512 B | 58 | 57.97× | 57.87× | 57.87× | 48.83× | 2.00× | **1.00×** |
| 4 KiB | 7 | 7.00× | 7.00× | 6.98× | 6.98× | 2.00× | **1.00×** |

（`N` = 100 000，各树均分。）

⇒ **`N_t` = 1 那一格逐字就是 D27（小数据打包容器） 已定项 2 自己判死的那格**：
`27-小数据打包容器.md:61` 逐字「1.00×（纯亏：白写两次，一点不省）」。
**一棵树只要可打包对象少于 `cap`，纪律③ 就把它推进这一格。** 4 KiB 档 `cap` = 7 ⇒ 门槛低到「7 个小文件」。

**树的数量有没有上界或典型值——现查结果：全仓没有上界，而且有一条已定条款明令不许造上界。**

```
.claude/kb/decisions/05-快照-空间记账机制.md:391
| 树 ID | **8** | **自由选择**。上界一条已定条款都指不到（D6（快照实现模型） 定每个可写头一棵自己的树、快照数无上界）⇒ **不许拿一个窄宽度去制造一个设计上限** |
```

```
.claude/kb/checks-owed.md:113（C106 开放容器数上界）
四条装载纪律相乘：同时开着的容器数（类型 1）= 树数 × 活代际数 × 活头数…
```

C106（开放容器数上界） 本身就是一条「没有上界」的欠账，D27（小数据打包容器） 未定项 8 正文也自陈
「「一容器一棵树」的代价算不出绝对数——全仓没有「同时几个写者头」的上界」。
⇒ **本腿确认这句是对的**，并补两件材料没说的：

1. **仓里用过的取样点只有三个，都不是上界**：E59（缓冲消息能不能只从单元重算） 的负载 16 棵树；
   E97（记账与分配记录的条目编码） 的记账预算格 `1024 × 64` 与 `8192 × 64`（`05-快照-空间记账机制.md` 已定项 4 代价侧）；
   bcachefs 21 棵（`08-核心索引结构.md:18`，外部实现，按 `.claude/singlefs-ai-sop/rules/evidence-discipline.md` 只算线索）。
2. **树数不是慢慢长的，它等于快照数**。D6（快照实现模型） 已定「每头一棵自己的树」，
   而快照是用户按秒建的东西。⇒ 一个每小时一快照、留 30 天的池子有 720 棵树；
   若每棵树只继承少量自己新写的小文件，纪律③ 让它们各自开一个几乎空的容器。

**⇒ 建议**：纪律③ 在数据侧**不该照抄**。它在类型 1 / 2 上成立的理由是那两类记录**天然按树分区**
（墓碑指认本树的死者、inode 记录就是本树的 inode）；数据对象没有这个性质——
一个容器装几棵树的对象，读路径一个字节都不用改（槽自带五元组，五元组第二段就是树 ID）。
真正被③买到的东西是「容器身份里 8 字节的出生树段能当 key 前缀用」，
而那个用途在数据侧由中央映射的 key 自己提供（见第四节）。
**代价对比**：放弃③ ⇒ 收益恒 = `cap`；保留③ ⇒ 收益 = `N/Σ⌈N_t/cap⌉`，在多快照池上塌到 1.00×。
**保留③ 要付的是一个没有上界的量，而它买到的东西在数据侧有替代品。**

### 3.2 ④ 槽目录：变长碎片这个担心问错了，真正的坏情形是别的

**容器写出后不可变**（已定项 10）⇒ 槽一次性排布、之后不再插入 ⇒ **容器内部不存在传统意义的碎片**。
唯一的空洞是尾部，闭式上界 4142 字节（见 2.1），**浪费率 ≤ 12.64%**，坏情形是
「7 个 4096 排完剩 3664，第 8 个也是 4096 ⇒ 关闭」，实际浪费 3664 + 103 = 3767 字节 = **11.5%**。

**真正的坏情形是死槽**：一个槽死掉，它的 `size + 47` 字节在容器被整体重写之前**永远收不回**（已定项 10
逐字「只能**整个重写**…不许就地压紧」）。E116（打包容器的账·补元数据写与整理策略） 结论三（210 格 `pack_worse` 出现 0 次）
的前提逐字是「**全死的容器当即被释放**——回收延迟没建模」。
⇒ 部分死的容器（`0 < 死槽数 < cap`）从来没有被建模过：它既不释放、也不重写、也不压紧。
**坏情形的数**：4 KiB 档一个容器 7 槽死 6 个 ⇒ 32768 字节里只有 4096 有效 ⇒ 有效占用率 12.5%，
比不打包（4096 用户字节占一个 32768 单元 = 12.5%）**恰好持平**——
也就是说 D27（小数据打包容器） 的收益在这一格**归零**，而写字节已经付过 1.1429 倍（已定项 1 代价表）。
⇒ **净亏 14.29%。** 触发这一格只要「同一容器里 6/7 的对象被覆写过一次」。

## 四、未定项 4（容器索引）——正推

### 4.1 先答「重不重复」：**不重复，但数据侧那个消费者不存在**

C103（容器索引无落点） 给容器索引的存在理由逐字有两半：

```
.claude/kb/checks-owed.md:110（C103）
…它是打包单元物理指针（与 MAC）的唯一持有者，别的树按身份引用容器；key = (出生树 ID, 打包记录类型, 容器号, 容器出生代) 四段全进…
```

**「别的树按身份引用容器」这半在数据侧一条实例都没有。** 逐个数消费者：

| 谁 | 要「容器身份 → 落点」吗 | 依据 |
|---|---|---|
| 读一个打包对象 | **不要** | 中央映射 key 是对象五元组，value 直接给落点；读回整单元后按五元组在容器内认领（D27（小数据打包容器） 两处三方收敛的形态，`27-小数据打包容器.md:149-151`）|
| 整理重写一个容器 | **不要** | 遍历映射 key 区间就够；容器自己装着 `cap` 个五元组，反查映射不用问「谁引用我」|
| 扫描重建 | **不要** | 方向是「扫到码 3 单元 → 读头 → 写索引」，不是反过来 |
| **释放判定（活槽计数）** | **要**（若未定项 5 取「维护计数」）| 计数按容器身份存 |
| **整容器一份 MAC**（若未定项 7 取这一支）| **要，而且在读路径上** | 读者解密前要拿到 MAC，而映射的位置条目里只有密文校验和 4 字节 |

⇒ **数据侧容器索引的全部内容，就是未定项 5 与未定项 7 的答案。**
两项都未定 ⇒ **「容器索引住哪」今天是一个没有内容的问题**，
照 C103（容器索引无落点） 的形态（另开一棵树、四段 key）照抄过来，是把一个不存在的需求实例化。

⚠️ 顺带修一条 D21（权威态与派生态的分界） 已定项 6 的依据（结论不变，依据要换）：
它判「引用者清单不需要任何新结构」的理由逐字是「搬一个共享单元**只改中央映射一条条目**」。
对容器不成立——重写一个容器要改 `cap` 条（D27（小数据打包容器） 正文 `27-小数据打包容器.md:138-140` 已经记了这笔）。
**结论仍成立，但换一条依据**：容器把「谁引用我」变成「我自己装着谁」，
`cap` 个五元组都在槽里，反查映射不需要任何新结构。

### 4.2 形态（本腿的答案）：**不新开树，把容器身份编进中央映射自己的 key 空间**

容器身份 26 字节（出生树 8 + 打包记录类型 2 + 容器号 8 + 容器出生代 8）
可以**无损嵌进**中央映射那 33 字节的五元组 key（`.claude/kb/first-txn-layout.md:67`），一个新字段都不加：

| 五元组段 | 宽 | 数据单元装什么 | **容器身份条目装什么** |
|---|---|---|---|
| 单元类型标签 | 1 | 码 1 | **容器的类码**（未定项 3 分配的 4–15 之一）|
| 树 ID | 8 | 读者树 | 出生树 ID |
| 对象 ID | 8 | inode | **容器号** |
| 对象出生代 | 8 | inode generation | **容器出生代** |
| 锚点偏移 | 8 | 文件内偏移 | **打包记录类型**（右对齐，高位恒 0）|

**它一次答齐四件事**：

1. **域分隔天然到位**：标签是 key 的第一个字节，也是 AAD 规范编码的第一个字节
   （D9（加密） 已定项 6：「它是 AAD 规范编码的第一个字节」，`09-加密.md` 已定项 6 字段表首行）
   ⇒ 容器条目与对象条目在同一棵树里**永不碰撞**，且碰撞不可能靠实现 bug 制造出来。
2. **C103（容器索引无落点） 要的那条 key 序性质原样保住**：C103（容器索引无落点） 逐字要「容器号排在出生代之前，
   使 (树, 类型) 下最大容器号 O(log N) 可查」。上表里容器号（对象 ID 段）排在出生代之前 ✓。
   数据侧只有一种打包记录类型 ⇒ 类型段在这一段 keyspace 内是常量 ⇒
   「(树, 类型) 下最大容器号」= 该标签、该树 ID 前缀下最大的对象 ID，一次范围末端点查。
3. **零新树**：不加 keyspace、不加树表条目（18 字节，D8（核心索引结构） 已定项 8）、不加根槽、
   不加一棵要单独缓存的树。D15（格式冻结政策） 判定表里「新增一棵 keyspace」是 compat，
   但它要占树表一格并在 day-1 就得留位（`15-格式冻结政策.md:91`）。
4. **自举问题不变坏**：2026-09-06 那次收口失败的第二条逐字是「自举收敛在「中央映射自己的节点」那一层，
   而那一层零条款」（`.claude/kb/decisions-history.md:869`）。
   把容器索引并进中央映射**不新增**一层自举——它落在**同一层**，
   所以那条零条款的账仍然欠着，但**没有被这个方案加重**。另开一棵树则要多一层。

**条目数代价**：+`⌈N/cap⌉` 条。512 B 档 N = 100 000 ⇒ +1725 条，**映射条目数 +1.7%**；
4 KiB 档 +14 286 条，**+14.3%**。容器重写时要改 `cap + 1` 条而不是 `cap` 条
⇒ E116（打包容器的账·补元数据写与整理策略） 的映射项低估 `1/cap`（512 B 档 1.7%、4 KiB 档 14.3%），
在 2.2 的 ρ 敏感面前是二阶量。

### 4.3 value 装什么——分三种情形，两种不需要它存在

2026-09-06 那次收口失败的第一条逐字是「**栽在 value 装不下**——…MAC 128 位 + nonce 96 位住在指针头部 31 里，
而中央映射的 value（位置条目 14）只有密文校验和 4」（`.claude/kb/decisions-history.md:867-868`）。
这一条**只在未定项 7 取「整容器一份 MAC」时成立**：

| 未定项 7 取哪支 | 容器索引 value | 判定 |
|---|---|---|
| **每槽各自 nonce 与 MAC** | 每个对象的 MAC / nonce 跟着它自己的逻辑 extent 走（D19（块指针的结构与宽度预算） 分段结构原样），容器索引**不持有 MAC** ⇒ value 只剩 `w` 份位置条目 | **容器索引退化成一条普通映射条目，零特殊处理** |
| 整容器一份 MAC + AAD 绑容器身份 | value 要多 MAC 16 + nonce 12 = 28 字节 ⇒ 映射条目 61 → 89、叶扇出 267 → 183、**映射叶数 ×1.459**；或者读每个小对象都多一次点查 | **贵，且读路径变长** |
| 整容器一份 MAC + AAD 绑对象身份 | — | D9（加密） 已定项 6 已经排除：「N 个 AAD 对 1 个 MAC ⇒ N−1 个对象验不过…失配成为正常操作的必然结果 ⇒ 排除」（`09-加密.md` 已定项 6 排除表第二行同一机制）|

**⇒ 本腿的推荐：未定项 7 取「每槽各自 nonce 与 MAC」，未定项 4 随之变成「不存在」。** 代价可算：

| 档 | `SLOT_EXTRA` 47（今天）| 加 nonce 12 + MAC 16 ⇒ 75 | 回本比下界 `w/(cap−1)` |
|---|---|---|---|
| 512 B | `cap` = 58 | `cap` = **55**（−5.2%）| 0.0351 → 0.0370 |
| 1 KiB | `cap` = 30 | `cap` = **29**（−3.3%）| 0.0690 → 0.0714 |
| **4 KiB** | `cap` = 7 | `cap` = **7（不变）** | 0.3333 → 0.3333 |
| 8 KiB | `cap` = 3 | `cap` = **3（不变）** | 1.0000 → 1.0000 |

⇒ **每槽自带 nonce 与 MAC 在界线档（4 KiB）一分钱不要，在 512 B 档花 5.2% 的收益**，
换来的是：容器索引消失、AAD 绑对象身份（与码 1 同一条 day-1 契约，不用为容器发明第二种 AAD）、
搬运对象不必重新加密（未定项 9 那张表第三行逐字「自洽，且搬运不必重算」）。
**代价那一侧**（D19（块指针的结构与宽度预算） 已定项 3「MAC 与 nonce 恒定占位的定宽槽位」与
D9（加密） 已定项 4「指针头部为每个逻辑 extent 存一份」要改）**本腿核过：这两条要改的是「住哪」不是「几份」**——
每个逻辑 extent 仍然恰好一份 MAC 与一份 nonce，只是打包对象的那一份住在槽里而不是住在指针头部。
D9（加密） 已定项 4 逐字「nonce 每 extent 存，不现算」在这个形态下**原样成立**。

**⇒ 未定项 4 的定案形态（本腿给用户的三选一）**：

| 形态 | 前置 | 代价 |
|---|---|---|
| **甲：不存在**（推荐）| 未定项 7 取每槽各自 MAC ∧ 未定项 5 取惰性重算 | 512 B 档收益 −5.2%；释放延迟要给数 |
| 乙：并进中央映射（4.2 的 key 编码），value = `w` 份位置条目 + 活槽计数 | 未定项 5 取「提交时维护」| 映射条目 +1.7%（512 B）/ +14.3%（4 KiB）；前台覆写多 66 048 字节（1.6 节）；且要先答 D21（权威态与派生态的分界） 硬约束 6 |
