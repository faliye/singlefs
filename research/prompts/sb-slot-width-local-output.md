1. A filesystem created on a standalone disk with io_min 512 sets the slot width to 512. When later assembled into a RAID5 array with io_min 65536, the mount code recomputes max(physical block size, io_min) as 65536 and expects the superblock slot to be 65536 bytes wide. However, the on-disk layout has the slot width fixed at 512. During a read operation, the code reads 65536 bytes starting at the slot's fixed location, but the actual slot is only 512 bytes. This reads 65024 bytes of adjacent disk data into the superblock buffer, corrupting it. During a write, the code writes 65536 bytes, overwriting 65024 bytes of unrelated data beyond the slot, causing filesystem corruption.

2. The rule against writes smaller than io_min exists to prevent read-modify-write (RMW) overhead for bulk data operations. Superblock updates are infrequent (e.g., once per transaction) and tiny (e.g., hundreds of bytes). RMW for such small, rare writes has negligible performance impact. Applying the rule to superblocks is a category error because the rule's purpose (avoiding RMW for large writes) does not apply to metadata updates of this scale. Thus, yi's only advantage (honoring io_min across devices) is irrelevant.

3. Declaring the superblock slot as a unit would break the fixed-location requirement. Units are copy-on-write objects with dynamic locations; updating the superblock would write it to a new location and update references in metadata trees. However, the superblock must reside at a fixed disk offset (e.g., sector 0) to be locatable without metadata. Treating it as a unit would move it on each update, making it impossible to find. Additionally, the unit's integrity mechanisms (e.g., checksums) would apply, but the superblock's fixed location conflicts with unit-based storage.

4. A fifth option sets the slot width to io_min (e.g., 4096 or 65536) at creation time, with the actual superblock record occupying only a portion (e.g., 512 bytes). The cost is negligible extra space (e.g., 8KB for two slots). If the slot width is set to the maximum possible io_min (e.g., 65536) for all expected devices, it works universally: writes always match io_min, avoiding RMW issues. It breaks nothing because the extra space is unused but harmless, and checksums cover the full padded slot. If set to a device-specific io_min that later changes, problems occur, but setting it to the system's maximum io_min avoids this.

5. A wider slot spans more sectors, creating more partial write states. However, the whole-unit checksum covers the entire slot. Any partial write (e.g., due to power failure) results in a checksum mismatch, which the filesystem detects and rejects. Thus, the wider slot does not increase vulnerability; the checksum catches all corruption in the slot regardless of size. The number of sectors is irrelevant for failure detection.
