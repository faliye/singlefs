Item 4. Item 5. Observation proving this wrong would be a test where the root's journal record is unreadable, a gap exists in the journal, and the code replays non-contiguous records without error, causing data corruption.

Item 6. The strongest objection is that separate entry points for first mount (publish_first_file) and later mounts (mount_writable) could drift apart over time, leading to different on-disk results for the same conceptual operation (e.g., a bug fix in mount_writable not applied to publish_first_file), violating the design rule against duplicate transaction mechanisms. However, publish_first_file is for bootstrapping a fresh pool (creating the first version), while mount_writable is for reopening an existing pool with published data—these are distinct operations with different invariants. Fact S, T, and U confirm this split is intentional and narrow. The current split is defensible as staged rollout, not duplication. Observation proving this wrong would be a change to mount_writable that alters on-disk behavior for reopening, but the same change is not applied to publish_first_file, causing inconsistent results for the first transaction between the two paths.
