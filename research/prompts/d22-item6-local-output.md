1. For A1, a concrete failure occurs during write operations on a sequential zone device. Suppose the system attempts to write a new superblock to a sequential zone that has already reached its write pointer (full). Under A1, the system ignores the write pointer and proceeds to write to the zone without resetting it. The device rejects the write due to the zone being full, causing a write failure. This failure is not detected by any other mechanism in the design because the system does not check the write pointer to determine zone status. No other unit class or detection mechanism (e.g., checksums, generation numbers) can prevent this write error since the issue is device-level write permission, not data integrity. The seven detection mechanisms (e.g., checksum validation, generation number checks) only apply to read operations and data integrity, not write permission errors.

2. A3 fails because it requires the write pointer as input for integrity checks during recovery. However, the write pointer is device-maintained state not present in disk images. For example, if a disk image is taken for recovery analysis, the write pointer value is absent. The system cannot reproduce or validate the write pointer from the image alone, making the A3 check impossible to run on an image. This alone kills A3 because the design requires recovery to work from disk images without live device state. A1 does not have this issue since it never uses the write pointer for decisions.

3. Zone type is a branch variable that can change mid-operation. For example, when adding a new disk to a pool that mixes conventional and sequential zones, the system must branch based on zone type for each disk. If a conventional-zone disk is replaced with a sequential-zoneone during operation (e.g., during pool expansion), the zone type for that disk changes. This violates the rule that branch variables may not change during an operation because the system would need to switch branch logic while processing the pool, leading to inconsistent handling of structures (e.g., superblock placement).

4. Under B3, the bytes on disk differ between conventional-zone and sequential-only variants. Specifically, superblock locations differ: in conventional zones, superblocks are written at fixed offsets (e.g., 64KB, 1MB), while in sequential zones, superblocks are written to the start of sequential zones (e.g., offset 0 within the zone). This difference means using the wrong variant (e.g., conventional layout on a sequential-only device) causes the system to read from incorrect offsets, triggering checksum failures and mount failure. Since B3 turns using the wrong layout into mount failure, it satisfies the project's test for being worth the cost.

5. A concrete observation that falsifies A1 is that on a ZNS device with sequential zones, if a zone is full (write pointer at end), the system must reset it before reuse. Under A1, the system ignores the write pointer during write operations, leading to attempts to write to a full zone without resetting. This results in immediate device write errors (e.g., EIO from the storage driver), which are not recoverable by any other mechanism in the design. This failure occurs during normal operation and is directly caused by not using the write pointer as a decision input, proving A1 is invalid.
