## 三、候选设计（主 agent 起草，被攻过零轮）

- **P1 复用的键**：每条变异的结论挂在下面这几样上，任一样变了就重判。
  - 变异描述：文件、行列范围、替换文。
  - 被改文件的 sha256。
  - 「关联文件」的 sha256 集合（P2）。
  - 全局项：工具链 `rustc -Vv`、`Cargo.toml`、`Cargo.lock`、`.cargo/`、feature 集合、`build.rs`。全局项变了就整版重判。
- **P2 关联文件按覆盖定**：每一版在没改过的代码上跑一遍带插桩的全部测试，得到「测试 → 它执行到的源文件」与「源文件的行 → 执行到它的测试」两张表。
  - 抓到的（被测试 T 抓到）：被改文件、T 所在的测试文件、T 执行到的全部源文件，都没变才复用。
  - 没红的：被改文件没变；覆盖到那一行的每条测试，以及它们执行到的文件都没变；而且新版没有新的测试覆盖到那一行，才复用。
  - 一条测试都没覆盖到那一行的变异，直接记没红（即红，见 P5），不跑。
  - 无效（编不过）的每次重判（中位数 0.6 秒）。
- **P3 覆盖看不见的几类**：
  - 常量与 `static` 的值：编译时内联，覆盖不记。被改文件里引用到的常量，它的定义文件并进关联文件。
  - 宏在别处展开。
  - 测试运行时读的非 `.rs` 文件。
  - `include_str!` / `include_bytes!`。
  - `cfg` 与 feature。
  - 环境变量。
  - 后五样主 agent 倾向一变就整版重判，或并进关联文件。这一节是三方的重点。
- **P4 兜底**：剪枝规则自证会红。做一组「改了关联文件、结论必须重判」的样本，剪枝判成可复用就判红，进门禁；不抽样。样本至少覆盖：被改文件变了、抓到它的测试文件变了、测试执行到的另一个文件变了、常量定义文件变了、宏定义文件变了、测试读的数据文件变了、新测试覆盖到那一行、工具链变了。
- **P5 提交门禁的红**：提交时，每一条都要有这一版的结论（复用或新判）；有任何一条没红、超时或只过了第一段就红。等价变异照 `.claude/singlefs-ai-sop/rules/test-discipline.md`「变异测试证明的是断言会红」第 2 条：把等价性写成一条测试留档，再从清单里排除，排除表每一行指到那条测试。

## 四、要回答的问题

- **Q1**（正推）：P1–P5 能不能推出「复用的结论等于在这一版上重跑会得到的结论」？逐条写出依赖的前提（覆盖工具的语义、测试的确定性、执行顺序、共享状态）。推不出的地方逐个列出。另外：
  - 按今天 303 条的结局分布，复用后每次提交的耗时估多少：一次提交改 1、5、20 个文件三档，要量的写明怎么量。
  - 覆盖那一遍本身要多久。
- **Q2**（攻方）：找「关联文件都没变、而结论变了」的反例。在 `crates/` 今天的代码上造，造得出就在副本上真跑：用 cargo-mutants 对一条变异判两次，中间只改一个非关联文件，结论翻面。至少攻：
  - 常量与内联；
  - 泛型单态化与 `#[inline]` 跨 crate；
  - 宏；
  - 测试读的数据文件；
  - 测试之间的共享状态与执行顺序（nextest 每条测试一个进程，cargo test 同进程多线程）；
  - 时间与随机数；
  - panic 路径与 `should_panic`；
  - 覆盖工具对内联函数、闭包、`const fn` 的归属；
  - harness 档测试经 `#[path]` 共享的 `common` 模块；
  - checker 档测试指回 harness 的 `common`。
- **Q3**（两条腿都答）：P5「有任何没红就红」在每次提交上的代价。新代码一行没被测试覆盖到，那一行的变异就是红，提交被挡。这是用户要的效果；腿只核它是不是会被别的原因误红（覆盖工具漏记、超时的阈值、只过第一段的条怎么判）。
