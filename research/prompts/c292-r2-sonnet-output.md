## 一、判据 1：划分判不判得出（我推的，带机制论证）

### 丙′的最强辩护：分两层——「能判」层与「判不出时的默认」层

**能判的机制（我核过，D19（块指针的结构与宽度预算） 已定项 7 / 8）**：`birth(N)` 不需要读 N 自己的头才能拿到——**指向 N 的父指针本身就携带出生 (树, txg)**（D19（块指针的结构与宽度预算） 已定项 7：「指针头部在 MAC 16 + nonce 12 + 算法类型 1 + extent 偏移 2 之后再带出生树 8 与出生 txg 8」），码 2 / 码 3 的指针另外携带实例代号 4 + 出生序号 4（D19（块指针的结构与宽度预算） 已定项 8：「码 2 / 码 3 | 出生树 8 + 出生 txg 8 + 实例代号 4 + 出生序号 4 | 节点指针 83」）。**这意味着 N 的完整四段 key 可以从任何一个仍存活的、指向 N 的指针原样读出，不需要 N 自己的头。**

COW 树的物理不变量是「已发布的物理块永不就地改写」（D6（快照实现模型） 判据 4「有界创建……不触碰任何已发布块的字节」）。这条不变量的直接推论：**只要 N 曾经被某个活快照 S 的树表根 R_S 通过一条祖先链引用过，且那条祖先链此后没有再被物理覆盖，那条链原样躺在盘上，是 R1 的合法来源（R1 优先级第二档「树表根指针」、第三档「别的树里的指针」）。** 因为 COW 从不覆写旧块，S 冻结时看到的那条祖先链——无论是与活头共享的（尚未分叉）还是 S 私有的（已分叉）——只要没有被**独立的**物理损坏波及，就仍然可读。

由此，**划分判据可以重新表述为一条可操作的规则**：
> 对丢失的 N，遍历树表里全部活快照 / 克隆 origin 的根指针，尝试沿各自的祖先链下探到 N 的 key 位置；探得通（即某条链上存活的祖先节点里有一条指向 N 的指针）⇒ 判「被引用」；全部探不通 ⇒ 判「未被引用」。

**这条规则在「单点损坏」（只有 N 自己丢，祖先都在）的常见情形下总能给出正确答案**——因为祖先链只要有一个字节没被独立腐坏，就带着完整的四段 key。

### 判据 1 仍然会红：构造性反例

问题出在**共享结构下的单点故障放大**。设 N 是记账树的一个码 2 内部节点，`birth(N)=10`；快照 S1 建于 txg=20（`S1.txg=20`），此时 N 未被活头改动，S1 与活头共享**同一个物理父节点 P**（COW 未分叉）。之后活头一直未再触碰这段子树。此时若 P 因介质故障丢失（**P 是活头与 S1 唯一共享的那份物理拷贝，丢一次等于两条链同时断**），则：

- 活头自己走到 N 的位置：**探不通**（父节点 P 没了）。
- S1 走 `树表根指针 → … → P → N`：**同样探不通**（同一个 P）。
- 别的树里的指针：记账树的码 2 节点不会被别的树引用（D19（块指针的结构与宽度预算） 已定项 8 的「不进映射的三类」不含记账树的普通内部节点，映射条目本身也只是位置提示，不是身份来源——它带四段 key，但**如果 P 已经丢了，映射条目里的 key 也就是我们唯一能确认「N 曾经存在」的地方，而不是「S1 是否引用过它」**）。
- deadlist / livelist：N 从未被杀掉（仍是当前版本），不会出现在 deadlist 里。

**在这个序列里，判据 1 真实地判不出**：我们知道 N 曾经存在（若映射条目还在，能拿回 key），但**判不出「S1 的祖先链是否也经过 N」**——因为唯一能证明这一点的物理证据（P）与证明「活头也经过 N」的证据是同一份，已经一起丢了。这不是罕见的复合故障：**这正是共享结构「省空间」的代价本身**——共享意味着单点故障影响面更大，S1 与活头对这条子树的依赖点数是 1，不是 2。

⇒ **判据 1 对丙′与丁**同时**判红**（这正是判据表写「两臂都红（第一部分共用这条线）」的原因，我核实这条共用关系成立）。

### 但红了之后：保守默认把「判不出」收编成「安全的默认」

D5（快照 / 空间记账机制） 已经有过完全同构的先例：「保守默认纪律：判据的任何一个输入取不到或不确定时，默认必须是『进 deadlist』」（我核过，出自本轮附录 D5（快照 / 空间记账机制） 第 750 行附近；原句：「⚠️ 保守默认纪律：判据的任何一个输入取不到或不确定时，默认必须是『进 deadlist』。」）。**丙′可以照搬同一条纪律**：判据 1 判不出时，默认按「被引用」（part 2）处理，而不是判定失败退出。这正是判据 2 的失败条款本身写的退化路径：「丙′退化为『全部码 2 的重建产物都只读，直到……』」——**这不是矛盾，是丙′自带的降级形态**，与甲/乙/丙 那种「无论怎么补都会撞 birth 定义」的结构性矛盾不同型。

**我的判定**：判据 1 在两臂上都会红（我构造的反例是设计层的，不依赖任何实现 bug），**但丙′对红了之后怎么办有一条现成的、与 D5（快照 / 空间记账机制） 同源的保守默认可用**，所以我把这一格记成「红，但可救」，不计入「丙′整体判死」。丁在这一格与丙′处境相同（同样需要先分类才能决定新发身份的 birth 该取多少），**丁没有等价的保守退路**——它的第二部分规则本身就要求「借最小 txg 新发」，判不出「哪些快照引用」时，丁连「保守地取哪个 txg」都定义不出（见下一节）。

## 二、判据 2：R1 抄回会不会抄错（我推的，构造不出设计层反例；但有两处真实缺口）

**R1 的四段 key 由指针原样携带，不依赖 N 自己的头**（同判据 1 引的 D19（块指针的结构与宽度预算） 已定项 7 / 8）。搬迁只改位置提示、不改 key（我核过，D5（快照 / 空间记账机制） 第 710 行附近：「⚠️ 搬迁不改 `birth`（2026-09-06 收口）……`birth` 原样跟着单元走」；D19（块指针的结构与宽度预算） 已定项 8：「全部指针进映射……搬迁只改映射一条条目，被搬单元逐字节不变、birth 不变」）。所以 R1 的多个候选来源（同树父指针、树表根指针、别的树里的指针、映射条目、deadlist / livelist 条目）**在设计层面应当对同一个 N 给出相同的四段 key**——它们各自记录的都是「N 首次发布那一刻」写进去的不变值，只有物理位置（14 字节位置提示）会随搬迁漂移，而位置提示从设计上就**不被信任为身份**（D19（块指针的结构与宽度预算） 已定项 5 硬规则 1：「释放一律经映射，不经提示」）。

**我尝试构造反例但没能找到设计层的漏洞**：唯一看起来像风险点的「跨头首次 COW 的重生」机制（我核过，D8（核心索引结构） 已定项 6：「新身份 = (本头树 ID, 类型 2, 原容器号, 本次发布代号)——保留容器号、只换出生树与出生代」）**只适用于码 3 打包记录容器（type 2, inode 叶），不适用于码 2 索引节点**——码 2 节点在克隆头首次分叉时是普通 COW（产生一个全新独立身份的新节点，旧节点保持不变），不存在「同身份多版本」的重生语义，所以不会有两个持有者对同一个 key 给出不同答案的情况。

**两处未堵的真实缺口（只记，不算判红，因为没有可构造的错答案序列，只是没有检查兜底）**：
- **C289（码 2 的出生树取哪个字段没写）**：D19（块指针的结构与宽度预算） 已定项 6 的收严句只点了码 3 的「出生树取类身份段里的出生树（码 3 偏移 43）」，没点码 2 对应哪个字段（我核过，附录逐字：「出生树取类身份段里的出生树（码 3 偏移 43），出生 txg 取诞生代号（码 3 偏移 73；码 1、码 2 同取诞生代号）」——出生 txg 那半句点了码 2，出生树那半句没有）。若码 2 会跨头共享（本轮判据 1 的反例场景恰好预设了这一点），R1 抄回时「码 2 的出生树该抄哪个字段」在格式上没有权威答案，实现者可能各写各的，那时才会真正抄错——**但这是「没写清楚」的缺口，不是丙′/丁设计本身的缺陷**，两臂共同继承这个缺口。
- **C294（指针里的 key 各段与被指单元头相等没有不变量）**：即便 R1 抄对了，也没有 checker 层面的东西去验证「按抄回的 key 查映射得到的单元，头里的字段确实等于这个 key」——这意味着**如果实现有 bug 导致抄错，今天没有任何机制会报警**（我核过，附录逐字：「invariants.md 没有一条要求两边相等……checker：按指针 key 经映射取到的单元，头里对应各段逐一等于 key，不等判红」，登记状态是「无」，即尚未落地）。

**判定**：判据 2 我判「不红」——没有设计层反例；但两处缺口（C289、C294）应当在采纳丙′或丁之前一并解决，否则 R1 的正确性没有任何东西守着。

## 三、判据 3：丁的新发给不给错答案（我判：红，理由比判据表设想的更硬）

丁的规则是：抄不回时也持久化，「新发身份，诞生代号取引用它的全部快照 / 克隆 origin 里最小的那个 txg……实例代号取当前可写挂载的号，出生序号在作用域里新发」。

### 第一层问题：`birth ≤ S.txg` 满足了，不代表 S 看到的内容是对的

即使丁精确地知道「哪些快照引用 N」（这一点本身在判据 1 红的情形下也拿不到，见下），丁给新节点赋的 `birth = min(referencing snapshots' txg)` 只保证了**一个数值上的不等式**成立（D5（快照 / 空间记账机制） 引用区间判据：`birth(b) ≤ R.txg < death(b)` ⇒ S 会把这个新节点判成「我能看见」），但**这个新节点的内容是重建那一刻现有存活数据算出来的，不是 S 创建那一刻真实存在过的内容**。

**具体序列**：
1. txg=10：N 创建，`birth(N)=10`，N 覆盖 key 区间 `[K1,K2)`，此刻叶子记录 `{K1: "a", K1.5: "b"}`。
2. txg=20：快照 S1 建立（`S1.txg=20`），此时 N 未变（仍是 txg=10 那份内容），S1 与活头共享 N。
3. 崩溃 / 介质故障：N 和它的父节点 P 一并丢失（同判据 1 的反例序列）。
4. 恢复时扫描发现 `[K1,K2)` 这段 key 区间的记录目前是 `{K1: "a", K1.5: "c"}`（假设活头在 txg=15 已经通过另一层缓冲/write buffer 把 K1.5 的值改成了 "c"，只是这个变化还没来得及 COW 出对应的父节点索引，或者干脆假设这是介质故障发生后、修复之前活头继续写入产生的新叶子内容——重点不在具体怎么发生，在于**重建只能读到「当下能读到的叶子内容」，读不到「S1 创建那一刻的叶子内容」**）。
5. 丁按「引用它的全部快照里最小 txg」算出新 `birth = 20`，把当下扫描到的叶子内容 `{K1:"a", K1.5:"c"}` 打包进新节点 N₂，`N₂.birth=20`。
6. S1 读 key K1.5：按 `birth(N₂)=20 ≤ S1.txg=20 < death=∞`，判定 S1 能看到 N₂，于是 **S1 读到 "c"，而 S1 创建时（txg=20）真实存在的值是 "b"**。

这是**内容层面的错答案**，不依赖 `birth` 数值算错——即使 `min(引用它的快照 txg)` 算得完全精确，**重建出的内容本身就不是那个 txg 时刻的历史快照**，因为重建的输入只有「现在还读得到的东西」，没有时间维度。这违反的不是某一条具体的格式定义句，而是**快照本身「冻结在某一时刻」这个语义承诺**（D6（快照实现模型） 判据 3「不存在『部分可见』或『用户可见但未发布』的快照」的隐含前提——快照必须能重现它捕获那一刻的内容，这条判据没写「重建出的内容也必须是那一刻的」，但这正是快照存在的意义）。

### 第二层问题：即使只看数值层面，`min` 也算不准

判据 1 已经证明「哪些快照引用 N」在判据 1 红的场景下本身判不出。丁需要的不是一个布尔值，是一个**集合**（引用它的全部快照），且要精确到「取这个集合的最小 txg」——**这比丙′需要的信息量更大**：丙′只需要知道「是不是被至少一个快照引用」（布尔），丁需要「被哪些快照引用，取最小」（集合运算）。如果判据 1 红的原因是「S1 的祖先链和活头共享同一个已丢失的 P」，那么丁根本不知道 S1 在候选集合里，`min` 会漏掉 S1 的 txg=20，转而用一个**更大**的、来自其他侥幸存活证据的 txg（比如某个后来的快照 S2，txg=50，如果 S2 的祖先链侥幸没丢），算出 `birth=50`。这时 S1 按 `birth(N₂)=50 > S1.txg=20` 判定「N₂ 比我新，我看不到它」——**S1 那个 key 位置直接查不到任何东西**（既不是错误的旧值，是彻底的空洞/查找失败），这是比场景一更直接的违反 `birth` 定义句（D19（块指针的结构与宽度预算） 已定项 8 依据 ②：「取新 birth 违反引用区间」）。

### 第三层问题：新 key 与旧 key 不同，旧持有者的指针变成悬空引用

丁「新发身份」意味着新的四段 key（birth 变了，key 的一段就变了，D19（块指针的结构与宽度预算） 已定项 6：码 2 / 码 3 的 key = 出生树 + 出生 txg + 实例代号 + 出生序号）。**任何仍然存活、且仍然引用 N 的旧 key 的指针**（比如 S1 自己那条侥幸没丢的祖先链，如果它其实是存在的，只是这次判据 1 误判了）**查映射时用的是旧 key，映射里只有新 key 的条目，会查找失败**。这与 D19（块指针的结构与宽度预算） 已定项 8 「搬迁只改映射一条条目，被搬单元逐字节不变、birth 不变」的设计意图直接冲突——搬迁之所以只改一条映射条目还能工作，是因为**搬迁保持 key 不变，所有指向它的旧指针依然能查到**；丁的新发身份**改变了 key**，这就不再是「搬迁」，而是**引入了一个全新的、没有任何旧指针指向的孤立条目**，同时把所有指向旧 key 的存活指针都变成了悬空引用。

**判定**：判据 3 对丁**红**，且是三条独立、层层递进的理由（内容非时点一致、min 算不准、旧指针悬空），任何一条单独成立就足以否掉丁。**这比判据表原设想的「撞 key / I-1.2 误判已发布」更严重**——不是一个格式细节撞车，是**语义层面对快照不可变性的破坏**。

## 四、判据 4：第一部分的 R2 在活头里还有没有错答案（两臂共用同一条规则，同判定）

「共同的第一部分」对丙′与丁完全相同（同一段规则文字），所以这一格**不能用来区分两臂**，只能问「这条共有规则本身有没有问题」。

**我推的**（未能构造出「某个读者拿到错答案」的具体序列）：对确认为「只被活头引用」的 N，R2 新发一个全新身份的节点，此后只有活头自己的读者会经过这条路径——**没有第三方（快照）持有对旧 key 的期望**，所以不存在「旧持有者查旧 key 查不到」的问题（这正是判据 3 里丁出问题的机制，在判据 4 场景下不存在，因为按定义这里没有快照持有者）。

**真实风险是资源泄漏，不是读到错值**（呼应本轮五节点名的「永久泄漏」，第一轮三节第 5 条已指出「失败条款没预见到『永久泄漏』这一格」）：如果 N 原来的身份（旧 key）在某个记账 / 释放路径里还留着一笔「待释放」的期望（例如它曾经被写入 defer 队列但还没真正回收，或者分配记录里还留着旧落点的条目），R2 换了新身份之后，**旧身份对应的那份记账/分配记录条目永远等不到被正常路径处理**——这不是「读到错值」，是「记账账本上出现一个永远不会被回收的幽灵条目」，与 D5（快照 / 空间记账机制） 「保守默认纪律」里点名的泄漏方向同型（「泄漏可被检出、可回收、伤害有上界；丢失不可逆」——这里的差别是，**这条泄漏今天没有任何检出机制盯着，回收路径也没写**）。

**判定**：判据 4 两臂**同判定，不红**（没有错答案），但记一条尚未解决的资源泄漏欠账，两臂共同继承。

## 五、判据 5：丙′「停在只读」出不出得去（我判：出得去，但原文字面不完整）

### 逐条排除回到可写的路径

1. **「等销毁那个快照」按字面读，只处理单个快照**：丙′原文「R1 走不通……就停在只读，直到那个快照被销毁」用的是单数「那个快照」。若判据 1 判不出（不知道究竟是哪个/哪些快照可能引用 N），这句话字面上无法执行——不知道该等哪个快照被销毁。**这条路径按字面走不通。**
2. **等待期间新建快照会不会重置计时**：只要读写路径仍然对外可见「这个 key 范围目前处于降级/只读状态」，新建的快照在创建那一刻并不需要读取 N 本身（快照创建是 O(1)，只复制根指针，D6（快照实现模型） 判据 4「有界创建……不触碰任何已发布块的字节」），所以新快照的产生**不会让判据 1 的证据进一步恶化**，但也**不会让它变好**——新快照同样会在其自己的树表条目里带着「这段子树目前未确定」的状态，本质上是把不确定性原样复制了一份。这意味着：如果只按「等到某一个具体快照消失」为退出条件，而系统持续产生新快照，理论上退出窗口永远不会关闭（这正是提示材料点名的「无界只读」）。
3. **可行的修补：冻结判定时刻的快照集合，而不是等某一个快照**。在判据 1 首次判红的那一刻，把**当时全部活快照 / 克隆 origin 的树表条目**记下来（这是权威态的一部分——树表本身是根环下的结构，D21（权威态与派生态的分界） 已把「根」这一格定义为含树表单元，我核过：「『根』这一格含它的间接层……根记录 + 树表单元 + 实例表单元……三者……不是索引，丢了就丢数据」）。此后**只等这一个冻结集合里的全部成员销毁完，与冻结之后新建的快照无关**（新快照天然不可能引用一个「在它创建之前就已经确认丢失证据」的历史节点——如果 N 已经丢了，新快照根本无法通过任何存活路径读到 N，它对 N 的引用状态是确定的「不引用」，不会加入不确定集合）。集合清空之后，即可安全地对 N 执行 R2 式新发（此时不再有任何**冻结时刻已存在、可能引用 N** 的活快照，新发的身份不会撞上任何历史期望）。
4. **这条修补的代价**：需要新增一个「冻结集合」的持久化记录（哪些快照 ID 属于这次判据 1 红时的候选集合），这是**丙′原文没有的一块新格式/记账**，落在「要改的条款」清单里（见第七节）。

**判定**：判据 5 我判「**出得去，但丙′原文按字面（单数『那个快照』）是不完整的，需要补一条『冻结候选快照集合，全部销毁后才能重发』的规则**」。这不满足失败条款 3 「没有任何路径回到可写」的判红条件，所以条款 3 不触发；但这确实是丙′需要在交用户前补全的一处口径缺口，我在结论表里标「只记，交用户补充」。

## 六、判据 6：永久泄漏在两臂下还出不出现

- **丙′**：出现，形态是**可用性泄漏**（无界只读，见判据 5——如果第五节的补丁不落地，等待窗口理论上不封顶），不是空间泄漏；一旦补上「冻结候选集合」这条规则，泄漏就有界（等到冻结集合清空即可）。
- **丁**：出现，且是**双重的**——（a）空间记账泄漏：判据 3 第三层指出新 key 与旧 key 不同，旧 key 上如果还挂着未处理的记账 / 释放期望，永远不会被触发清理（与判据 4 里两臂共有的那笔泄漏同型，但丁这里是**主动制造**新旧两套身份，风险面比只有活头引用时更大，因为这里原本就有一个「快照仍然期望旧身份存在」的持有者，被新发身份直接甩开）；（b）判据 3 已经证明的错答案风险本身就是一种更严重的问题，不只是「泄漏」。

**判定**：两臂都有永久泄漏,但性质不同、不能直接比较严重度；丙′的泄漏是「效率损失」（安全但慢），丁的泄漏叠加了「正确性风险」（判据 3），这是我判丙′优于丁的核心理由之一。
