1. Create tree with id 1. Create inode 100 with birth generation 5. Write a data block at offset 0 to physical location 1000. Delete inode 100. Create a new inode 100 with birth generation 15 in the same tree. Write a data block at offset 0 to physical location 2000. When freeing the first block (physical 1000), if the object birth generation is not included in the map key, the system would use key (unit type, tree id 1, inode 100, offset 0, block birth generation 3) which matches both blocks. This causes the second block (physical 2000) to be freed instead of the first, corrupting data.

2. Data unit on disk has five-tuple (type 1, tree id 1, inode 100, birth generation 5, offset 0) and block birth generation 3 stored at physical location 1000. The map uses a surrogate key 12345. When scanning units to rebuild the map, the scanner sees the five-tuple but has no way to determine the surrogate key 12345 since it is not stored in the unit. The map cannot be rebuilt because the scanner lacks the mapping between disk units and surrogate keys.

3. In a clone scenario, a block is shared between tree id 1 (birth tree) and tree id 2 (referring tree). When dereferencing the block from tree id 2, candidate B requires inferring the birth tree id from the object's metadata. If the metadata is not cached, this requires an additional disk read. Candidate A carries the birth tree id in the pointer, avoiding the extra read. For a high number of clone references, the cumulative cost of extra disk reads for candidate B exceeds the storage cost of carrying all six segments in candidate A.

4. Candidate E: Store the map key in a separate table referenced by a handle in the pointer. When scanning units to rebuild the map, the scanner reads a data unit with a handle to the table. The table's entries contain the six segments. However, the table's location depends on the map itself. The scanner cannot find the table without the map and cannot build the map without the table, creating a circular dependency. For example, a data unit with handle 5 points to table entry 5. The scanner needs the map to find table entry 5 but the map requires table entry 5 to exist.

5. Settling how to supply the segments does not resolve the encryption issue or snapshot count limits. For encryption, even with all six segments carried in the pointer, the identity fields remain ciphertext in the data unit headers, preventing map rebuild without additional mechanisms. For snapshot count, the key supply method does not address how to track references across unlimited snapshots, leaving snapshot retention and garbage collection unresolved.
