1. The strongest objection is that the claim "instance table counts as a ninth role, written after the eight bump roles" is factually incorrect: disk write order (Fact E) shows InstanceTable is written first in the instance-table row-publish batch, sequence number assignment (Fact F) shows InstanceTable receives a lower number before TreeTable, and only the internal lookup vector construction (Fact C) matches the "ninth role" description—but that vector is unused for disk writes or sequence numbers. The claim does not hold up because it misrepresents the actual behavior; the milestone document's characterization is inaccurate. The mismatch matters for correctness only if the description is relied upon for understanding system behavior, but Fact A shows the internal order has no crash-consistency consequence. An observation proving this wrong would be if the disk write order for the instance-table row-publish batch shows InstanceTable as anything other than the first unit, or if sequence numbers for InstanceTable and TreeTable in the same publish show InstanceTable with a higher number than TreeTable.

2. The strongest objection is that dynamic computation of warm-up publishes could stop too early if the device assignment causes partial coverage (e.g., if regions map to fewer devices than expected), but the geometric upper bound of 3 and region assignment constraints (three regions, at most three distinct devices) ensure coverage of all devices within the cap. The choice holds up because it correctly handles the open decision for later mounts (Fact I) and adapts to device assignments as warned in Fact H. An observation proving this wrong would be if a pool with three devices has a region assignment where two publishes cover only one device and the loop stops early without covering all devices—but this is impossible because the loop runs until all devices are covered or reaches the cap of 3, and three devices require up to three publishes.

3. The strongest objection is that not carrying over the open segment could cause excessive fragmentationragmentation by leaving partially used segments unused, but the decision D3 settled item 7 (Fact K) confirms no disk representation exists for the open segment, and Fact L explicitly states it is purely in-memory state. The choice holds up because it the search from the free bitmap is the only safe default without a format change, and the objection is about performance, not correctness. An observation proving this wrong would be if the allocator fails to allocate space due to fragmentation after restarts despite sufficient free space, but this is a performance issue and not a correctness failure, and the system has no mechanism to avoid it without a format change.

4. The strongest objection is that skipping recovery in a marked-clean case could be unsafe if the marker write and last publish are not atomic, but the absence of a clean-shutdown marker is deliberate to avoid this risk, as confirmed by the doc comment (Fact N) and decision D18 (Fact N). The current absence is defensible for a first version because it avoids potential safety issues from a marker, and it is not a functional gap but a conscious design choice. An observation proving this wrong would be if a clean unmount followed by a crash leads to recovery failure, but the recovery path is designed to handle crashes without a marker, so no such observation exists.

5. The strongest objection is that when the chosen root's journal record is unreadable, resuming from the smallest sequence number above the water mark could apply a record that does not follow immediately after the root, violating strict contiguity (I-8.3), as in a scenario where the root's record is missing but a later record exists (e.g., jsn 3 is the next available when jsn 2 is missing). The choice does not hold up and should be an open decision point because it fails to verify contiguity. An observation proving this wrong would be if a test case with a missing root journal record (but subsequent records intact) allows recovery to apply a non-contiguous record without error.

6. The strongest objection is that separate entry points for first mount (publish_first_file) and reopening (mount_writable) could drift apart, causing inconsistent on-disk results for the same operation, but the operations are fundamentally different: publish_first_file initializes a fresh pool while mount_writable reopens an existing pool with published data. The split is defensible as a staged rollout with narrow scope boundaries, not a duplicated mechanism. An observation proving this wrong would be if a change to mount_writable produces different on-disk results for the first file publish compared to publish_first_file, but the first file publish only occurs in publish_first_file, so no such observation exists.

7. For Finding 1 (free slots counted independently), the finding still holds unweakened on the rebuild-from-disk path because rebuild_from_records calls mark_allocated, and the test cold_start_reads_the_second_content_and_the_pool_checker_stays_green catches the mutation breaking "self.free_slots -= span;". For Finding 2 (release-via-mapping), the finding still holds unweakened because the release checks are in the same release function and are exercised during normal releases, regardless of how the allocator was rebuilt. For the open item about checksum verification before release, it is a real gap not covered by the findings because rebuild_from_records does not check mapping entries' checksums before releasing, and the existing tests do not verify this. An observation proving Finding 1 wrong would be if the mutation breaking "self.free_slots -= span;" does not cause the test cold_start_reads_the_second_content_and_the_pool_checker_stays_green to fail during rebuild. For Finding 2, an observation would be if a release attempt bypasses one of the three checks during rebuild-based releases. For the open item, an observation would be if a corrupted mapping entry causes incorrect release during rebuild without checksum verification.
