# 进程与命令规范（靠 review 的那一半）

## 装置起的样本进程，放进它自己的进程组

装置、判法与复跑脚本起样本进程（真 shell、被测程序、样本命令）时，判据是：每条样本跑完，它起的进程一个不剩。

- 每条样本放进它自己的进程组：shell 里用 `setsid [--wait] <命令> &` 起（不带 `-f`），同一层紧跟着 `名字=$!`；Python 的 `subprocess` 带 `start_new_session=True`。
- 超时与结束时对整组发信号，先 TERM，过宽限再 KILL：Python 用 `os.killpg(<进程组号>, <信号>)`，shell 用 `kill -TERM -- -"$名字"`。组号只取自己用新会话起的那一个子进程的（shell 里的 `$!`、Python 里的 `<子进程>.pid`）：不对别的进程组发信号，不先挑进程再发。循环里分两种：按进程号逐个发（shell 循环里的 `kill`，对自己的组发也拒；Python 的 `os.kill(<进程号>, …)`）不许；Python 里每一轮 `os.killpg` 只停自己用新会话起的那一个子进程的组可以，钩子放行（认法写在钩子代码 `SESSION_CHILD_CALLS` 与 `OWN_GROUP_TARGET` 两段注释里）。不只停直接起的那一个。认得出的写法与照旧拒的写法以钩子 `.claude/hooks/bash-command-detector.sh` 文件头 ⑥ 与那两段注释为准。
- 跑完按进程组号在 `/proc` 里核一遍，组里没有留下进程；留下的停掉，并写进这条样本的失败信息。
- 只停直接子进程会留下孙进程：进程替换起的 `cat` 拿着管道的写端，读这根管道的一方永远等不到 EOF。

这一条还没做成检查：起的是不是样本、超时与收尾时停没停整组，脚本里认不准，靠 review。

## 起了后台任务和子 agent，就要定时复检，调度的一方不响应才终止

- **起了就要复检**：后台任务、派出去的子 agent，调度的一方看最后一次动作是多久以前、是不是停在等待循环里、同一条命令是不是反复跑而输出一模一样、它写的文件还涨不涨。主 agent 这边由看门狗复检、任务卡住由服务判（它停任务，不属于「检出和处置分开」那一条说的检出；判法在 `task-server/task_server_lib.py` 的「异常表」（常量 `ANOMALY_TABLE_TEXT`）`stalled` 一行），自己交的任务结束本轮等完成通知，不在前台干等、不轮询（`.claude/main-agent.md`「派出去之后」）。
- **检出和处置分开**：检出卡住与空转的工具（hook、看门狗脚本）只记录、只报告，不拦命令、不停进程与子 agent。结不结束、怎么处置由调度的一方看了再定；报了之后调度的一方没有响应（同一件事连报几次都没处置、也没确认），报告的人或 agent 可以终止它：进程用 `.claude/singlefs-ai-sop/scripts/proc.py stop 进程号`，子 agent 用停止它的工具，终止了要报出来。在执行前拒绝某一种危险写法的钩子不在「检出」之列。
- **提醒里的每一种处置都给能照跑的命令**，不只写「处理一下」「确认之后再跑」；出路里有「确要这样就照跑」的，同时给一条把「已决定照跑」记下来的命令，记下过的那一件不再推同一条提醒。
- **停掉子 agent 之后，当场定它的改动与它手上的活**：改到一半的文件逐份定留着、退回还是交给谁接着改，没做完的活定交给谁接手；写进记录并告诉接手的一方，不留没有主的半截改动。
- 后台任务与脚本任务的名字照与使用者对话的语言写，写明它是什么、在等哪一件；同一时间在跑的几件不许同名，只看名字说不出它在做什么的，改了名再起。
- 等日志里的一行字之前，先确认那一行真会写进那个文件。

## 遇到问题，先找有没有别的 agent 在管这一块

管干活中遇到的、自己这次任务解决不了或不归自己这次任务的问题：门禁红在不是自己改的文件上、要改的文件正被别的会话改着、要用的东西归别的任务产出、修不动或拿不准怎么修。动手修、绕开或停下干等之前，按顺序做：

1. 列出正在跑的 agent 与会话（`ListAgents`），按任务名、它在改的文件与最近的动作，判有没有哪一个在管问题所在的那一块；拿不准是不是它管的，也发消息去问。
2. 有在管的，发消息给它（`SendMessage`），不自己去改它管的那一块。消息写清：哪个文件、哪一行、什么现象、怎么复现、是不是自己这次改动带来的、要它做什么或问它什么；转述别处的做法照 `.claude/singlefs-ai-sop/rules/communication-discipline.md`「转述别处的做法，带出处或原文」。
3. 自己修不动、或缺别人手上的信息与权限，主动发消息求助，不闷头绕开，也不干等。
4. 一个在管的都没有：归自己这次任务的，自己处理；不归的，报给用户或调度的一方，写清问题在哪、建议交给谁。主 agent 自己就是调度的一方，照 `.claude/main-agent.md`「一轮怎么开、怎么收」第 15 条。
5. 发出去之后接着做手上不依赖它的活，收到回复再接那一块；对方一直不响应，报给用户或调度的一方，不擅自接手它管的那一块。

没做成检查，靠 review。

## 一个脚本里的检测项，能并行就并行

- 判据：这一批检测项互不依赖，而每一项都要起子进程干活（编译、跑测试、起虚机、起 python），就并行跑。快下来之后再看剩下的时间花在哪：故意空等的用例（验的就是「超时逻辑被破坏之后 `wait` 不返回」）并行省不掉。
- 不并行的三种：后一项要读前一项的产物；共用一份可写状态（同一个临时目录、同一个 target 目录、同一台设备），要并行就每项各给一份；每项只跑几毫秒。
- 并行度（进程数与进程内的线程数）从参数或环境变量取，不写死；没给时一律取登记的每台默认重活线程数（`.claude/heavy-thread-default`），不按 `nproc` 取。

## 别用 echo 假装命令成功

不写 `命令 2>/dev/null; echo "已完成"` 这种报成功的写法。改状态的命令都回头读一次实际状态确认：判的是读回来的内容，不是那条命令的退出码。

## 停 systemd 服务之后，回读输出判停没停

- `systemctl stop 服务名` 之后读 `systemctl is-active 服务名` 的输出，是 `inactive` 或 `failed` 才算停了；不只看 stop 的退出码，也不只看 `is-active` 的退出码（它只在 `active` 时返回 0，`activating`、`deactivating` 也返回非 0）。
- 再读它的 `cgroup.procs`（目录是 `/sys/fs/cgroup` 接上 `systemctl show -p ControlGroup --value 服务名`），读出来是空的才算进程清干净。
- 停之前判服务在不在同样看输出：`active`、`activating`、`reloading`、`deactivating` 都算在，cgroup 里有进程也算在。

## 结果抓取要有完整性闸

被测程序在最后一行报出它总共发了多少条，抓取方比对条数，对不上整轮作废。这道闸先证明会红：喂一个声称的条数比实际发出的多一条的假程序，它必须判红。

## 带闸的脚本，判完了才交出产物

脚本既产出结果、又负责判它能不能用时，结果先写临时文件，闸过了再输出；判红时 stdout 保持为空。自证要红：把脚本改回「先输出、后判」，自证必须判红。

## 脚本改文件之后要回读确认，警告是免费的信号

用脚本做字符串替换来改代码或文档：替换必须断言命中，替换数为 0 就报错退出；改完回读（grep 新内容在不在，或跑一遍看行为变没变）。编译器和 linter 的警告不许略过。

## 进程边界上的三种静默失效

| 形态 | 怎么写 |
|---|---|
| `set -e` 下写 `里层; exit_code=$?` | 在 `if` 里取：`if 里层; then exit_code=0; else exit_code=$?; fi` |
| `export 变量名="$(命令)"` / `local 变量名="$(命令)"` | 先赋值再 `export`，两行写 |
| 握手用的环境变量漏给子进程 | 读完就 `unset`；起子进程时 `env -u` 清掉 |

判据是这个值跨了几层进程：跨一层就问它在下一层还在不在、该不该在。

## 破坏性操作先看清楚再动

`mkfs`、`dd`、`dmsetup remove` 的目标设备从变量取，先 `lsblk` 打出来确认一眼，不写死 `/dev/sdX`。
