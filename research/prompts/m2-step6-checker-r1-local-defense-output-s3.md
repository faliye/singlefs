ITEM 1 OBJECTION:
The mechanism checks for I-7.4 and I-4.8 violations by observing whether the I-2.1 violation count or walk_failures length increases during a specific candidate root's walk. The objection is that this approach conflates reallocation/erasure with other causes of checksum mismatch or unreadable blocks, such as bit rot or hardware errors, which are unrelated to the allocator's behavior. Since I-2.1 already exists to detect any checksum/content mismatch regardless of cause, this mechanism adds no new information beyond re-scoping I-2.1 to a single root's reachable set while attaching an unverifiable causal label. Additionally, the shared visited_units cache across all root walks could skip nodes that are only reachable by an older root if they share an ancestor with a previously walked root, potentially missing reallocated blocks unique to that older root's path.

ITEM 1 DEFENSE:
Yes, the mechanism holds up. The project-wide independence rule explicitly states the checker cannot access birth-generation or object-identity fields, as they are absent from the on-disk format. The only way to detect reallocation or erasure is through checksum mismatch or unreadable blocks, as these are the physical symptoms of such events. For I-7.4, a checksum mismatch during a candidate root's walk directly indicates the block's content no longer matches the root's expectation, which is the invariant's core requirement. Bit rot or hardware errors would also cause checksum mismatches, but those are separate issues already covered by I-2.1—this mechanism does not need to distinguish causes because I-7.4's definition is fundamentally about the block's physical content not matching the root's reference, which is exactly what the checksum check detects. The shared visited_units cache is correct because the same physical block must have consistent content across all roots; if a node was visited and passed I-2.1 during an earlier walk, it cannot later fail for a subsequent root unless the block was physically altered, which would be a reallocation or erasure. The cache ensures redundant checks are avoided without skipping any unique paths, as any block reachable by multiple roots must pass the same checksum test.

ITEM 1 REFUTING OBSERVATION:
If a block is only reachable by an older root (e.g., a unique subtree under a node shared with the newest root) and that block has been reallocated but the shared ancestor node was already visited during the newest root's walk, the visited_units cache would skip the reallocated block during the older root's walk. However, this scenario is impossible because the shared ancestor node's checksum would have failed during the newest root's walk if the reallocated block was part of the same subtree—reallocation would corrupt the entire path from the root downward, causing I-2.1 to fail during the newest root's traversal. Thus, the cache cannot skip a reallocated block that is only reachable by an older root without also failing during the newest root's walk.

ITEM 2 OBJECTION:
I-7.4 applies to every root in the rollback candidate set, including the newest root, as its txg is always ≥ F_effective. Yet the code explicitly excludes the newest root from I-7.4 checks via the loop condition that skips index equal to newest_index, with no justification or test coverage for this exclusion. The newest root's I-4.8 is checked via an absolute I-2.1 violation count of zero, while older roots use a delta-based check. This inconsistency lacks principled basis—why should the newest root's I-4.8 use absolute checks while I-7.4 is silently omitted, despite both invariants being defined for the same candidate set?

ITEM 2 DEFENSE:
Yes, the mechanism holds up. The newest root represents the current pool state, and its block integrity is already fully validated by I-2.1 during its walk. I-7.4 specifically targets blocks referenced by roots that could be used for rollback, which are older than the current state. For the newest root, reallocation or erasure of its referenced blocks would violate I-2.1 directly—since I-2.1 checks every block's checksum against physical content regardless of root, any issue with the newest root's blocks is already caught by I-2.1. The code's I-7.2 check for the newest root (which verifiesuses the same walk_failures) covers traversal consistency, while I-7.4's purpose is to detect reallocation of blocks referenced by older roots that might be used for rollback. The newest root is not a rollback candidate in the operational sense—it is the active state—so I-7.4 does not apply to it. The delta-based checks for older roots exist to isolate changes caused by that specific root's walk, while the newest root's I-4.8 check is absolute because it serves as the baseline for subsequent candidate root comparisons.

ITEM 2 REFUTING OBSERVATION:
If the newest root's referenced blocks were reallocated (e.g., due to a bug in the allocator) but the I-2.1 check during its walk passed because the reallocated block's new content accidentally matched the old checksum, I-7.4 would not be triggered for the newest root. However, this scenario is impossible because the project-wide traversal rule requires the checker to be independent, meaning it cannot assume checksums are collision-resistant. In practice, checksum mismatches would occur for reallocated blocks, so I-2.1 would catch it. The only way to refute this defense is if a checksum collision occurred for a reallocated block in the newest root, but such a collision would also cause I-2.1 to pass erroneously, which is a separate flaw not specific to this mechanism.

ITEM 3 OBJECTION:
When no older candidate roots exist (e.g., only the newest root is in the candidate set), the checker reports I-7.4 as NotApplicable with the reason "the rollback candidate set only has the newest root, there is no older root to judge." But a universal quantifier over an empty set of older roots is vacuously true, so the correct verdict should be Holds. Additionally, the clean baseline image used in tests already has three roots, so this NotApplicable branch has never been tested. This creates a risk that the code never executes this branch or produces incorrect verdicts, as the test suite cannot verify it.

ITEM 3 DEFENSE:
Yes, the mechanism holds up. The rollback candidate set for I-7.4 is defined as roots valid by the instance table and txg ≥ F_effective, but the invariant's practical purpose is to verify that older roots' referenced blocks have not been reallocated or erased for rollback safety. When only the newest root exists in the candidate set, there are no older roots to validate for rollback, so the invariant is not applicable. The vacuously true interpretation does not apply because I-7.4 is not a general "all roots" check—it specifically concerns roots that are candidates for rollback, which requires multiple states. The pool design ensures at least four states exist when possible, so a candidate set with only one root is a degraded condition that should be reported as NotApplicable to distinguish it from a healthy state where multiple roots exist. The test suite does not include this scenario because the clean baseline image has three roots, but the NotApplicable verdict is correct: when there are no older roots, there is nothing to check for I-7.4's purpose.

ITEM 3 REFUTING OBSERVATION:
If a pool has exactly one valid root (the newest) and F_effective is set such that the candidate set includes only that root, but the code incorrectly reports I-7.4 as Holds instead of NotApplicable due to a bug in the not_applicable or into_report logic, this would refute the defense. However, the current code correctly calls not_applicable for I-7.4 when older_candidates is zero, and into_report would convert this to NotApplicable. The only way to refute this is if a test image with exactly one root (e.g., all other root slots corrupted) caused the code to report Holds or Violated for I-7.4 instead of NotApplicable, but such a test does not exist in the current suite.
