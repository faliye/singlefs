5. **什么时候起跑**：挂载就起、按周期查。每次发布之后按已定项 1 的三水位查一次；另有定时兜底，每隔一段时间再查一次，间隔是挂载参数，默认 30 秒。周期线程住在新开的运行库一层：挂载时按参数开卡、建实例、挂载、起周期线程，前台与后台经一把锁排队；核心层照旧不起线程、不读钟。定时兜底的预算照旧与用户改动共用同一份（第 6 条），挂载不再给新预算。一次整理发布要写的根槽连同它之后的余量里的根一走、根环里不同用户状态就少于 4 个时，这次整理发布不发（守 D16（发布语义） 已定项 1 的「回退候选集保留最近 4 个可退到的不同状态」）；余量取 S 槽，S 是每区根槽数（根环共 3S 槽）。只有全空聚簇段数低于底额（已定项 3）、前台已写不进时破例，每趟至少发 1 次；破例排在第 6 条的让路之前，前台有 fsync 在等也照发（前台已写不进，让路换不来什么）。删除队列不空也算起跑：这一趟只走队列、不发整理，不看水位，也不被发布预算挡。两种模式起跑规则相同。
6. **起跑之后的节奏**：GC 不在用户改动的调用线程里跑（不在用户改动返回之前跑一批），挪出之后三样照旧有保证：一趟发布预算有上限、签下一条意图那一判跨趟留着、整理批不插进用户改动的抬 F 与再判之间。签下一条意图那一判读的「上一条完成的意图」只留到下一次用户改动发成为止：每次用户改动发成就清掉它，下一趟从空起照常签新意图，预算照旧是这一次改动给的那一份；被拒、没发成的改动不清。GC 占盘写带宽有一个上限（挂载参数）；前台有 fsync 在等时不发下一批，这一判别子要 GC 挪出调用线程之后才看得到；它只约束整理批（每一批之前问调用方一次），整理开头先走的那一遍删除不是整理批，不受它约束。整理开头先走一遍删除（把盘上留着的删除意图做完）是可选的前置优化、为了效率，不是整理的一部分：删除与整理是两件事、各是各的事务，整理也可以不先删除；那一遍删除发的版不占整理一趟的发布预算。整理一批本身就是那次移动，整理判出的死空间由分配器的常规回收放掉、不交给删除；没删完的留到下一趟整理或下一次可写挂载，不因为它没删完挡住别的操作。 发布写失败冻结之后，前台 fsync 不在冻结时答成功：先重发那一次冻结的发布，发成了才答成功，没发成交回错误。重发成了照冻结那一次的种类记账：冻结的是用户改动，照一次用户改动发成办（重给预算、清掉上一条完成的意图）；冻结的是后台批，照后台批记。
7. **值不值按省下的 CPU 时间算**：GPU 模式的目的是少占主机 CPU 时间，数据量大时跑得更快只是副产物。收益是后台任务少占的主机 CPU 时间（CPU 模式下它的 CPU 时间减 GPU 模式下它的 CPU 时间，后者含准备数据、提交、等结果、两份结果的比对，以及第 8 条交 CPU 判的那几条），挂钟与 CPU 模式持平也做；D24（后台重活能不能卸给 GPU） 已定项 3 那条按挂钟比的判据不管这一项罩着的后台任务。实现之后跑一组对照：同一负载、同一池，CPU 模式与 GPU 模式各跑，报两边的 GC 挂钟、主机 CPU 时间、前台 fsync 延迟，并在几档盘容量上各跑一遍，看收益随容量怎么变。
8. **GPU 的结果怎么复核**：两份独立写的 GPU 核（不共用核函数）对同一批输入各算一次，逐条比两份的结果。两次相同的条目算确认，交 CPU：CPU 照发布路径逐条核计划与读盘核（`crates/singlefs-core/src/transaction.rs` 的 `relocation_checked_against_the_version`），再改位图，不另外抽样复核 GPU 的结果；两次不同的条目写明状态不确定，这一批不回收、不搬，留到下一轮重算。同一个条目连续 2 轮（N = 2）都不确定，交 CPU 那一份实现单独判一次，按 CPU 的判定处理；连续不确定的计数只放在内存里，重挂清零。「轮」按落点认条目：扫描里的校验和核对与区域扫描里的单元头解析与映射反查两段，一个条目是一个落点（盘、槽、跨度），选段打分一段，一个条目是一个聚簇段（盘、起点槽）；一个落点在一批里两份核的结果不同，它就不确定一轮，结果相同或已交 CPU 判过，它的计数清零；没出现在这一批里的落点，计数不动、也不清。一批放弃（GPU 出错、等超过上限）时，那一批里已经交回的段照算一轮，放弃的那一段计数不动。每一批报确认、不确定、交 CPU 判的条目各多少，运行时看得出来。只有一张卡时两份核都在这张卡上跑，有几张卡时按第 2 条分活、两份核可以分开跑；不许要求多张卡，一张与几张都要能跑、判定相同。
