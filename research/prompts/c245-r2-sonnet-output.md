### 回退那次发布的记录写在环的哪一槽，条款怎么说

### 这两种读法在 H1、H3 上给出不同结果

- **读法 A（攻方腿的真值参照，counter 推断）**：先确定"所选根覆盖到的 counter"，再要求下一条记录的 counter 恰好是它 + 1。这个 counter **没有任何格式字段直接存着**（`root_record.rs:16-25` 的字段表：`filesystem_identifier, instance, checkpoint_txg, tree_table, tree_identifier_watermark, rollback_floor, instance_table, mapping_root`，没有一个是"覆盖到的 counter"），只能靠**扫描环里"同实例、checkpoint_txg ≤ 根的水位"的记录，取其中最大 counter** 反推出来。round1 模型的 BING_STRICT、JIA_LITERAL 都是这么实现的（`c245-r1-opus-output.md` 第 36-46 行的臂定义表，JIA_LITERAL 第 39 行、BING_STRICT 第 43 行）。
- **读法 B（六条口径第二条 + 真实代码）**：直接用根记录自带的 `(instance, checkpoint_txg)` 做水位比较，"above water"集合里排序取第一条作为链首，**不要求这第一条的 counter 恰好等于"覆盖到的 counter"+1**。

**读法 A 在两种场景下会失败**：一是"覆盖到的记录"的 journal 副本本身被物理覆盖（推断源头没了），二是"覆盖到的记录"根本读不出（层 1 故障）。**读法 B 不依赖那条记录是否还能读到**——它只需要"所选根"自己的字段（这是根环里的记录，与 journal 环是两个物理结构），加上 journal 环里现存的、checkpoint_txg 比根新的记录。第三节会逐行推演，读法 B 在 round1 给出的两个具体例子上都不复现 H1/H3。

**这意味着 U3 的答案是**：攻方腿的"所选根覆盖到的计数器"是注 1 单独摘出来读时的一个忠实但不完整的读法；六条口径合起来看，还有第二种、与字面完全相容、且与真实实现对应的读法（checkpoint_txg 水位），它在 H1、H3 上的结果不同（第三节给出逐行证据）。**注 1 本身没有说"覆盖"必须靠 counter 判定**——那是攻方腿模型的实现选择，不是条款的字面要求。

**什么现象推翻本节结论**：在 D23（journal 的角色与格式） 里找到一句明确要求"链首必须验证其 counter 恰好等于所选根覆盖到的 counter + 1"（而不只是 checkpoint_txg 大于水位）；或者证明六条口径第二条与注 1 在概念上不能相容（例如同一个 checkpoint_txg 下有多条记录、且它们的 counter 不连续时，第二条自己也需要 counter 推断——第三节专门核这一格）。

```rust
        if (record.instance, record.counter) != expected_key { break; }
    }
    expected_next = Some((record.instance, record.counter + 1));
    if !record.is_commit { break; }
    let all_verified = ... // 逐项校验点名单元
    if !all_verified { report.verification_failed += 1; break; }
    report.prefix_applied += 1;
    rebuilt = RootRecord { instance: record.instance, checkpoint_txg: record.checkpoint_txg, tree_table: record.new_tree_table, ... };
}
```

**三个关键点**（逐行核对，非转述）：① `water` 直接取根记录自己的 `(instance, checkpoint_txg)`，不做任何 counter 层面的推断——对应第二节读法 B；② `above` 按 `(instance, counter)` 排序，**instance 是排序的主键**；③ `expected_next` 初值为 `None`，**第一条被取出的记录不需要验证它的 counter 是否等于"所选根覆盖到的 counter + 1"，直接接受为链首**。

### H1（回退到 mkfs 根的例子，`c245-r1-opus-output.md` 4.2 节第 1 条）

场景：instance 1 warmup 写出 (1,1)（根已持久）；管理员回退到 mkfs 根（比 (1,1) 更旧），前缀末（读法一）= mkfs 覆盖到的 0，回退写 (2,1)（instance 2, counter 1），落进 counter=1 对应的槽，物理覆盖了 (1,1) 的 journal 副本；回退自己的根未持久 → 崩。下一次挂载：root(1,1) 的**根记录**（住在根环，与 journal 环是不同的物理结构，不受 journal 槽覆盖影响）仍然自证有效，被选为所选根。

用真实算法推演：`water = (1, 1)`。`records`（journal 环扫描能读到的）里，(1,1) 已经不在（被 (2,1) 物理覆盖）；(1,2)（instance 1, counter 2, checkpoint_txg 2）还在（未被触碰）；(2,1)（instance 2, counter 1, checkpoint_txg 由 CJ2 算出，至少 3）也在。过滤 `(instance, checkpoint_txg) > (1,1)`：(1,2) 的 (1,2) > (1,1) 成立；(2,1) 的 (2, ≥3) > (1,1) 成立（instance 2 > instance 1，元组比较不看第二项）。`above` 按 `(instance, counter)` 排序：(1,2) 排在 (2,1) 前面（instance 1 < instance 2）。`expected_next = None`，直接取 (1,2) 为链首，若它自证与点名单元都验证通过，**应用 (1,2)**，然后 `expected_next = (1, 3)`；下一个候选 (2,1) 的 `(instance, counter) = (2, 1)` 不等于 `(1, 3)` → `break`。**最终只应用 (1,2)，结果与"没发起回退时"完全相同。**

⇒ **真实实现在这个具体例子上恢复出与真值相同的结果，不复现 round1 report 3.2 节描述的"丙与字面甲不施加 (1, 2)"（那是 BING_STRICT/JIA_LITERAL 靠扫描"同实例、txg ≤ 根水位"推断链首、而这条推断源头 (1,1) 恰好被物理覆盖，推断失败、判定链首失据的产物）。真实代码不需要这次推断，因为它的水位判定直接吃根记录自己的字段。**

### H3（层 1 例子，`c245-r1-opus-output.md` 4.3 节）

场景：checkpoint_txg=3 的根 (1,3) 已持久（fsync 已返回），超级块槽未落；层 1 故障：根槽 (1,3) 读不出、记录 (1,2)（journal 环里的两份副本）都读不出。择根退到 (1,2)。

用真实算法推演：`water = (1, 2)`（取自根环里 (1,2) 这条根记录**自己的**字段，与 journal 环里 (1,2) 这条记录能不能读到无关——它们是两个不同的物理位置）。`records` 里，(1,2) 的 journal 副本确实读不出（不在 `records` 里），但 **(1,3) 的 journal 副本没有被声明为不可读**（round1 只说"记录 (1,2) 两份读不出"，没说 (1,3) 不可读），所以 (1,3) 仍在 `records` 里。过滤 `(instance, checkpoint_txg) > (1, 2)`：(1,3) 的 (1, 3) > (1, 2) 成立。`above = [(1,3)]`。`expected_next = None`，直接取 (1,3) 为链首，验证通过则应用，**恢复出与真值（乙）相同的结果，读回 fsync 已确认的版本**。

⇒ **真实实现在这个具体例子上同样不复现"丙与字面甲多丢 fsync 已返回数据"。** 差别的原因与 H1 相同：BING_STRICT/JIA_LITERAL 需要先找到"覆盖到的那条记录"（即读不出的 (1,2) 本身）才能推断出链首在哪，而它读不出，推断失败；真实代码的水位直接来自"所选根"这个已经确定下来的量，不需要重新去读 journal 里那条被覆盖的记录。

### 多记录发布（U6 第三问，任务书明确要求）

**读码发现一个和 H1/H2/H3 都无关、但更直接的 bug**：D23（journal 的角色与格式） 已定项 7/19 的记录头有独立的"事务号"与"提交标记"字段（`journal.rs:85-86`，`transaction: u64, is_commit: bool`），支持一个事务跨多条记录、只有最后一条 `is_commit = true`。但 `replay_journal` 的循环体是：

```rust
expected_next = Some((record.instance, record.counter + 1));
if !record.is_commit { break; }
```

**只要当前记录 `is_commit == false`，循环立刻 `break`，永远不会走到 `for` 循环的下一轮去看这次发布里排在它后面、真正 `is_commit == true` 的那条记录**——即使那条记录已经完整持久、逐项校验都能通过。这与 D16（发布语义） 已定项 4 的字面矛盾：

**出处 `.claude/kb/checks-owed.md:265`（节选整行抄，与本问相关部分）**：

```
⚠️ **2026-09-13 用户定案（D16（发布语义） 已定项 4）：取「一次发布整体施加或整体不施加」，第二份 replay 停在句法层；条款已写，会红的检查仍欠。**
```

"整体施加或整体不施加"要求：一次**完整、全部记录都持久且逐项校验通过**的多记录发布，应当**整体施加**。而今天的代码遇到非最后一条记录（`is_commit=false`，这是设计上**必然**的，因为只有最后一条标 commit）就直接放弃，**不会去检查"这次发布是不是完整的"，而是无条件地把它当成"未完成"处理**——它确实做到了"不完整时整体不施加"（round1 report 5.1 节第二个例子就是这么触发的，只落了 (1,4) 没落 (1,3)，被跳过），但它**没有能力在"完整"的情况下走到"整体施加"**，因为它遇到第一条非 commit 记录时压根不会再往后看。

⇒ **这不属于本轮判据里 H1/H2/H3 中任何一格，是 U6"有没有别的步骤先挡掉"这一问额外读出来的一处独立缺口**：今天 milestone-1 的第一版串行提交（D23（journal 的角色与格式） 已定项 18 依据句"任一时刻只有一条记录在飞，N 恒 1"）不产生多记录发布，所以这条路径从未被 E142（第一个事务的干跑）、层 0 崩溃点重放或任何单测跑到，门禁与单测都测不出来。这是一处**静态读码发现、未构造用例实跑验证**的观察，不是本轮判据要求的对抗实测。

**什么现象推翻本节结论**：在 `crates/` 里找到一处调用 `replay_journal` 之前先把同一次发布的多条记录拼成一条"虚拟记录"再传入（这样循环体永远只看得到一条已经确认 commit 的记录，`is_commit` 分支永远不会在中间触发）；或者证明 milestone-1 的记录布局根本不会产出 `is_commit=false` 的非末记录（若"一事务几条记录"在第一版里恒为 1 条，这条发现虽然仍是代码里的隐患，但暂时够不到任何可构造的输入）。

## 四、H2"单元被复用"：影子账窄读法 + D16 已定项 1 挡不挡得住

**场景**（`c245-r1-opus-output.md` 4.2 节第 3 条）：数据发布 checkpoint_txg=3 的单元（记录 (1,3) 点名）落盘、根未落 → 崩；管理员回退到 (1,1)；分配器载入 R_old=(1,1) 的账，(1,1) 的账里那个物理槽是"空闲"（因为从 (1,1) 的视角，txg=3 那次发布根本没发生过）；回退发布把自己的实例表单元写进这个"空闲"槽，覆盖了 (1,3) 点名的单元；回退根未落 → 崩。没发起回退时 (1,3) 验证通过、可以正常应用；现在这个单元的内容已被覆盖，`replay_journal` 逐项验证点名单元时校验和对不上，`verification_failed`，断链，(1,3) 这次发布的数据彻底丢失。

**逐条核对两条候选防线**：

**① I-7.4（近 K 代块未被复用）**（`.claude/kb/invariants.md:50`，整行抄）：

```
| I-7.4 | 近 K 代块未被复用 | 回退候选集里每一个根（按实例表判仍然有效 ∧ txg ≥ F_生效，D23（journal 的角色与格式） 已定项 14）所引用的块，其物理范围均未被重新分配给其他对象、也未被清扫抹头。...被抛弃时间线的根不在候选集里，这只管回退目标的选择；它们引用的块在离开根环之前同样不许重新分配、不许抹头（2026-09-13 用户定案，C314（回退可以复用被抛弃的根引用的单元） 取影子账，D23（journal 的角色与格式） 已定项 14）。...
```

这条不变量保护的对象是**"根（回退候选集里的、或被抛弃时间线的）所引用的块"**——即已经被折进某个 ROOT 的树指针里的块。checkpoint_txg=3 的单元从未被折进任何根（它的根从未持久），所以它**不在 I-7.4 保护的对象集合里**，无论从"候选集里的根"还是"被抛弃时间线的根"哪个角度算都不在——因为它压根不属于任何一个根。

**② D16（发布语义） 已定项 1 的"可再分配"界**（`.claude/kb/decisions/16-发布语义.md:371`，整行抄，节选表格该行）：

```
| 可再分配 | 已释放 ∧ 释放代 ≤ max(F_生效, 环里最旧有效根) |
```

这条界管的是**"已经被释放（deallocate）过的块"再次可分配的时间窗**。checkpoint_txg=3 的单元从未被释放过——它是一次**全新分配**，从未进入任何账本的"已释放"集合，这条界的谓词"已释放"对它**不成立**，规则根本不适用于它。

**③ C314（回退可以复用被抛弃的根引用的单元） 的影子账窄读法**（`.claude/kb/decisions/23-journal的角色与格式.md:1209`，第一节已整行抄过）——它的保护对象是**"被抛弃时间线的根"所引用的单元**。checkpoint_txg=3 这次发布**从未持久出一个根**，所以它不构成"被抛弃时间线的根"，它引用的单元不在 C314 的保护范围内。

⇒ **三条候选防线的保护对象分别是"根引用的块""已释放的块""被抛弃根引用的块"，checkpoint_txg=3 点名的单元三者都不是——它是"从未被任何根折入过、也从未被释放过、只存在于一条水位之上自证记录里"的单元，这个类别今天没有任何一条条款提到。挡不住，是这一句漏了。**

**漏了哪一句**：D23（journal 的角色与格式） 已定项 14 回退例外那段（`:1209`）里需要补一句类似——"回退发布的分配器额外查一遍：环里水位之上、自证通过、其发布的根未持久的记录点名的单元，同样隔离到该发布的根持久（或该记录本身被环轮转覆盖）为止"。这与 C314 的隔离对象是**同一机制、不同集合**：C314 隔离"根已发布、但根属于被抛弃时间线"的单元，H2 要隔离"根未发布"的单元——两者合起来才覆盖"任何仍可能被下一次挂载重新读到的自证证据"。

**与臂无关**：这条缺口的成因是"分配器从 R_old 的账重新载入"与"影子账只查根引用的集合"，跟超级块存不存 tail 没有关系——ORACLE（真值）在 round1 模型里同样命中这一格（4.2 节："回退根落了盘的...**记录被盖 252、单元被复用 5632**...ORACLE...**5884**"），这是 round1 判决自己的结论，本节只是把"挡不住"的具体原因钉到了逐条款核对，没有推翻它。

**什么现象推翻本节结论**：在 D23（journal 的角色与格式） 或 D16（发布语义） 里找到一条专门针对"未持久根所点名单元"的隔离规则（不是 I-7.4、D16 已定项 1、C314 这三条已核过的）；或证明回退发起前必须先做一次"排空"（把水位之上的记录全部持久成一个根，或全部作废），这样进入回退流程时环里就不存在"水位之上、根未持久"的记录，H2 的前提就不成立。

## 五、U2：H3 那几格丢的数据，条款许不许丢

**D23（journal 的角色与格式） 已定项 18 断链即止代价句**（`.claude/kb/decisions/23-journal的角色与格式.md:1249-1256`，整行抄，节选代价句）：

```
**语义（2026-09-14 用户定案写死）**：这个数的含义是**一次恢复重放的前缀最多 N 条**。
读到一条校验和不过的记录时，恢复**断链即止**——停在它之前那一条，不追问它是「撕裂」还是「损坏」，也不因此拒绝挂载。
...
⚠️ 代价：一条真正的「盘中段损坏」与一条「尾部撕裂」在第一版判成同一种结局，池照常挂上、损坏那一条之后的记录全部不施加。
```

这条代价句的射程是**"journal 记录自身的校验和不过"**——它管的是环里某条记录本身坏了（不管是撕裂还是中段损坏），恢复因此停在它之前。**H3 的故障不是这一类**：H3 的故障是"根槽读不出"（层 1 对根环的破坏，不是对 journal 记录的破坏）+"记录 (1,2) 两份读不出"（这条记录的问题是**读不出**，不是**校验和不过**——round1 的层 1 故障模型明确区分"读不出"与"自证失败"两类，且这条记录本身在 H3 例子里不在重放链路径上：`water=(1,2)` 之后要应用的是 checkpoint_txg 更大的记录）。**已定项 18 这条代价句字面上够不到 H3 的故障类型**，所以按已定项 18 单独看，H3 丢的数据不在它承诺可丢的范围内。

**D16（发布语义） 已定项 7 的 fsync 返回条件注**给出了真正相关的射程句（第一节已引过，重引关键一句）：

**出处 `.claude/kb/decisions/16-发布语义.md:293`（整行抄）**

```
⚠️ **『fsync 等根槽持久之后才返回』的射程（2026-09-13，C199（实例代号递增与 jsn 断号即止互相矛盾） 两轮三方论证，2026-09-14 用户复核确认）**：返回之后这一代只由那一个根槽罩着（根槽不镜像，D22（单元原子性怎么合成） 已定项 2）。同一实例里退一代，靠 journal 重放追得上；**每个新实例（每次可写挂载、恢复、切换、回退）的第一个根在下一次发布之前是单点**——那个槽读不出或它所在的盘掉了，恢复退到上一个实例的根，重放按严格前缀停在实例边界（D23（journal 的角色与格式） 已定项 14 的注 1），这次挂载里 fsync 已返回的事务丢，一个故障就够。要不要让新实例先把根写到两块盘上再确认，是 D16（发布语义） 已定项 8。
```

这条注**明确划了两类**：① "同一实例里退一代，靠 journal 重放追得上"——这是**条款承诺守住**的一类；② "每个新实例第一个根……退到实例边界……fsync 已返回的事务丢，一个故障就够"——这是**条款自己承认会丢**的一类，但**限定在"新实例的第一个根"这个窄场景**（跨实例边界退根）。

**H3 的例子属于哪一类？** round1 例子（`c245-r1-opus-output.md` 4.3 节）：instance 1 完成了 warmup txg1、txg2、数据发布 txg3（根已持久），layer 1 故障后择根从 (1,3) 退到 (1,2)——**这是同一实例（instance 1）内部的退一代，不是跨实例边界**。按已定项 7 这条注的字面划分，**H3 落在①类（"靠 journal 重放追得上"），是条款明确承诺守住的**，不属于②类那个"一个故障就够丢"的窄场景（②类专指"新实例的第一个根"）。

⇒ **H3 丢的数据是 D16（发布语义） 已定项 7 自己承诺不许丢的那一类，不是已定项 18 断链即止代价句允许丢的那一类。** 这与第三节 U6 的推演互相印证：真实的 `replay_journal`（读法 B，checkpoint_txg 水位）在这个具体例子上确实"追得上"（应用了 (1,3)，见第三节），兑现了已定项 7 这句承诺；只有 BING_STRICT / JIA_LITERAL 这两种依赖 counter 推断（读法 A）的具体实现违反了它。

**这与"丙"这个抽象设计选择要不要为这个违反负责，是两件事**——见第六节。

**什么现象推翻本节结论**：如果 round1 或第二轮攻方腿能构造一个"跨实例边界"（新实例第一个根）的层 1 例子，且证明真实代码在那个例子上也丢数据，那么那个例子属于已定项 7 注②类，条款自己承认可丢，H3 在**那个例子**上不成立（但不影响本节对"同实例退一代"这个例子的判断）。

## 六、判决有没有越位

round1 判决原文（`c245-r1-main-verification.md` 第五节，整段抄）：

```
**结论（第一轮，挂起）**：这一问问错了量。承重的不是『超级块里的tail』，是『所选根覆盖到哪一条记录』。甲只把tail当扫描起点时它不承重；丙在所选根覆盖的记录被盖或读不出时丢链首；乙与丁把这个量绑在根上。另打中两处与臂无关的违例：回退那次发布崩在根槽之前时，D23（journal 的角色与格式） 已定项 14 显式例外里『与没发起回退时相同』不成立（记录被盖、单元被复用）。
```

**逐句核对这句话与三条腿的观测宽窄是否一致**：

- "承重的不是『超级块里的tail』，是『所选根覆盖到哪一条记录』"——**这句话本身没有越位**：它准确反映了 round1 三条腿一致同意的东西（第一轮正推腿、攻方腿都把"承重量"归到这个概念上）。
- **"丙在所选根覆盖的记录被盖或读不出时丢链首"——这一句有越位。** 它把"丢链首"说成"丙"这个**抽象设计选择**（不在超级块存 tail）本身必然带来的后果，但 round1 攻方腿模型里的"丙"（`BING_STRICT`）只是**一种具体实现**：靠扫描"同实例、txg ≤ 根水位"的记录推断链首（第二节读法 A）。本轮第三节逐行推演证明：真实代码 `replay_journal`（同样不存 tail，因此同样是"丙"这个抽象类别的一个合法成员）用**另一种实现**（六条口径第二条的 checkpoint_txg 水位，读法 B）在 round1 给出的**同样两个例子**上**不丢链首**。⇒ **"丢链首"是"丙 + 靠 counter 推断"这个具体组合的性质，不是"丙"这个抽象类别（不存 tail）本身必然的性质**。判决把"具体实现的失败"上升成"抽象设计选择的失败"，宽了一档。
- "回退那次发布崩在根槽之前时……『与没发起回退时相同』不成立（记录被盖、单元被复用）"——**这句话没有越位**，第一、四节的核对确认这两处违例确实与臂无关、且确实成立（H2 站得住，H1 的"记录被盖"在读法一下也站得住）。但**它没有提到"记录被盖"这个具体机制此前已经作为 C331 的一部分独立登记过**——这不是判决的"越位"，是"重复立项"的风险：如果第二轮 / 第三轮据此单独给 H1 开一条新账，会和 C331 产生 kb-discipline 讲的"同一个事实两处记录"，第七节给出建议写法。

**更准确的表述**（辩方建议，供交用户或写回 kb 时参考）：

> 承重的不是超级块里的 tail 字段本身，而是"能不能可靠地判定所选根之后该从哪条记录接"这件事。这件事有没有失败，取决于**具体怎么判定**：靠扫描推断"覆盖到的 counter"（BING_STRICT / JIA_LITERAL 的做法）在 round1 给出的例子上会失败；直接读根记录自己的 `(instance, checkpoint_txg)` 水位（六条口径第二条、真实 `replay_journal` 的做法）在同样的例子上不会。**乙、丁提议把这个量做成显式字段，买到的是"不需要推断"，不是"丙必然会错、只有乙丁才对"**——今天不存 tail 的真实实现恰好已经在用一种不需要推断的判定方式，只是它自己另有别的问题（第三节发现的多记录发布 bug，以及 round1 finding 5 指出的、其它场景下的过度应用问题）。

**什么现象推翻本节结论**：如果能证明六条口径第二条（checkpoint_txg 水位）在**某个** H1/H3 类场景下也需要退回到 counter 推断（例如同一 checkpoint_txg 下有多条记录、且需要确定其中哪一条是"最后一条"时），那么"丙必然要做 counter 推断"这句话对那类场景就重新成立，判决的原话在那个场景下就不算越位。
