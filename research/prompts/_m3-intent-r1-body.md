## 一、题面

用户 2026-10-01 提出（原话）：「意图记录的形态能不能装下第二个使用者（GC 那条"R 内不存在分配代 ≤ c0 且未释放的落点"）。 因为 cpu gc 肯定要做。 gpu gc只是优化项目。 同样ZNS / FTL SSD 算法 也是特性ssd的优化项。 这里需要提前设计一下，避免到时候返工」。

已定的框：

- 第一版 unlink 的意图（D8（核心索引结构） 已定项 16，用户 2026-10-01 定 K-U1「L4：只立 deleted_inodes」）：意图那次把 inode 记录写成 nlink = 0、`deleted_inodes` 加 key = N（8 字节、无 value），不立 logged_ops 树；`mount_writable` 在交回之前把队列走到空（续做挂点 M1）。
- 无界操作走意图（D8 已定项 5）：可能修改无界数量 extent 的操作先把意图写进 logged_ops 树、再分批推进；崩溃后恢复时续做。logged_ops 树的形态与字段表今天没有条款（C364（整理意图记录没有字段表））。
- 整理（GC）走同一套意图机制（D26（后台整理与放置回收） 已定项 2）：不新增 `CommitStep` 成员；意图目标态「`R` 内不存在分配代 ≤ `c0` 且未释放的落点」；`segs0` 必须以「值」写进意图记录（已定项 1 第 2 条）；触发用的三个观测量持久化进记账树与意图记录（已定项 6）；`R` 在意图期内不可作分配目的地（已定项 1 第 3 条）；整理是第三格（后台、可续做、无戒律，`.claude/rules/fs-design.md`「记账是事务的副产品」）。
- 回收分两条线（D26 已定项 7）：目前自建 GC；盘的 FTL 支持 GC 时交给盘、本工程只打标记发指令，走哪条线按 feature bit。NVMe FDP / ZNS 是「有就用的加速」（D26 已定项 11）。GPU 能不能接后台重活归 D24（后台重活能不能卸给 GPU）。
- 格式在第一个外部用户出现之前是软的（`.claude/rules/format-evolution.md`）：一处格式改动的代价只算这一次要同步的东西（字节表、不变量、checker、装置、产物重跑）；真正要慎重的是概念模型（决策正文）。

这一轮要判：第二个意图使用者（CPU 整理）落地时，今天定下的意图形态要不要返工、返工多少；现在先定哪些、留哪些。

## 三、格

### I1　整理意图记录要装什么
照 D26 已定项 1 / 2 / 6 与 C364、C91、C140、C373 逐条列出一条整理意图在盘上必须带的字段（种类、`R` 的表示、`c0`、`segs0`、触发观测量的值、进度游标？），每个字段宽度与「谁读它、什么时候读」；活意图数的上界（D26 已定项 1 第 3 条「活意图数有界」）；意图的生命周期（写入、分批推进、停机谓词判真时删不删——C373、崩溃后续做）。

### I2　载体候选与各自的返工量
至少比这几个候选（腿可以加）：
- **A 维持现状**：unlink 用 `deleted_inodes`（D8 已定项 16），logged_ops 树等整理落地时再定字段表、再注册。
- **B 现在就定 logged_ops 树**：字段表（种类码 + 目标字段）、树 ID 与种类码、day-1 零根注册现在定死，unlink 不用它（只用 `deleted_inodes`），整理落地时直接用。
- **C 合一**：unlink 的意图也写成 logged_ops 树的一条（种类 = unlink、目标 inode N），`deleted_inodes` 改成派生队列或去掉——这条推翻用户 K-U1 的 L4，要写明返工哪些已写回的条款。
每个候选答：整理落地那一天要改哪些字节（树表条目数、水位、记录格式、`layout/03-third-txn.md`）、哪些已定条款、哪些不变量与 checker、崩溃流增量；与「一个事务层，所有结构共用」（`.claude/rules/fs-design.md`）与 D13 已定项 10 封闭提交步骤枚举的关系。

### I3　续做语义两类
unlink 的续做必须在 `mount_writable` 交回之前走到空（M1，C1 的「正常挂载后没跑续做即判红」）；整理是第三格，后台、可续做、无戒律，不该挡挂载。一套意图机制装两类续做语义时：续做调度从哪读、按种类分派还是两套入口、挂载交回之前走不走整理意图、空间准入（删除类不判式子 vs 整理走常规准入 + 常驻底额 D26 已定项 3）。

### I4　与删除、回退的交互
整理搬迁一个正在删除的文件的单元（删除批释放了 `R` 里的单元、整理在同一窗口重落它）；`R` 排他与删除批的落点（删除批也要新写元数据）；管理员回退时 logged_ops 树取 R_old 还是随现行（D23 已定项 14 的表加一行），回退跨过一条整理意图之后 `c0` / `segs0` 还成不成立；搬迁不改 `birth`（D26 已定项 5）与墓碑、谱系的关系。

### I5　FTL / ZNS 与 GPU 只是优化
D26 已定项 7：盘的 FTL 支持 GC 时交给盘、本工程只打标记发指令。那一条线上有没有意图记录、长什么样；意图形态要不要预留「设备线」的种类或字段，还是由 feature bit 分流、意图记录只描述主机线；ZNS / FDP 有就用（已定项 11）对意图记录的要求；GPU（D24）只做算（选段、校验），意图记录要不要为它留什么。判据：CPU 整理是底线、必须做，另外三样是优化，意图形态不能为优化多立格式分支（`.claude/rules/fs-design.md`「格式上吝啬分支」），也不能让优化落地时返工意图格式。

### I6　现在定什么、留什么
综合 I1–I5：给出「现在必须定死的」（会让以后返工格式或概念模型的）与「可以留到整理落地时定的」两张清单，各自的理由；三·2 unlink 实现之前必须定的有哪些。
