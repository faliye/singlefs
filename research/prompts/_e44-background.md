# 背景：singlefs 的「扩展点字节上限」（D21 已定项 2）

singlefs 是一个从零设计的 COW 文件系统（Rust，尚无代码，格式设计阶段）。
下面每一条都出自本仓 kb 的正文，2026-08-29 逐字现查过；算术部分由 E43 的程序算出，
12 个单测全绿，9 条变异全部被抓（无盲区），5 轮输出逐字节一致。

## 被问的那个数

D21（权威态与派生态的分界）已定：单元里给「开线方」预留一个**扩展点**——
一段空间加一套接口，开线方可以在里面放一个**指向**，拿它去做本工程不理解的事。
已定的形态：

- 大小**按线在超级块里声明**（开线方自己定，可为 0），**上限由本仓定一个固定字节数**；
- 上限**取固定字节数，不按单元大小取比例**（理由：它承载的是每对象的语义字段，与单元多大无关）；
- **具体取多少未定案**。正文举例 128 字节，明写「未定案」。

五条硬约束（与本轮问题相关的两条）：扩展点必须落在校验/认证覆盖之内；
扩展点里的指向**只能指向它自己配额内的空间**，不许指向核心层对象。

## E43 量出来的三个边界

口径：单元元数据 = 「为了管理一个单元而多付的字节」，不含 inode、目录项、空闲空间、反向索引。
本工程 2 副本档 108.0 B（单元头 55 + 指针头部 31 + 位置条目 ×2 共 22），4+2 条带档 152.0 B。
对照行同口径：ZFS 128.0 B；btrfs 4 KiB 单元 82.5 B、128 KiB 单元 207.3 B。

| 边界 | 值 | 怎么来的 |
|---|---|---|
| 下界 | **9 字节** | 一个位置条目 dev 1 + 物理偏移 6 = 7，加上让 checker 判得了「配额范围被记为已分配」所需的长度 2 |
| 上界 A（空间对照，**计入**口径）| **19 字节** | D21 正文自己写着「本工程在 128 KiB 单元上比 ZFS 省」。108 + N < 128 ⇒ N ≤ 19 |
| 上界 B（扇出与树高，**不计入**口径）| **864 字节** | 1600 万叶、指针 40 字节、节点头 64 字节：2 KiB 节点档在 N = 865 时树高从 5 涨到 6，4 KiB 档在 1473，16 KiB 档 6081，64 KiB 档 55233。最紧的是 2 KiB 档 |

两种记法的差别是：扩展点那 N 个字节算不算「本工程的单元元数据」。
D21 的对照表没说。计入 ⇒ 区间 [9, 19]，**128 落在区间外**；
不计入 ⇒ 区间 [9, 864]，**128 落在区间内**。

## 一个顺带测出来的事实

D21 正文写着「本工程在 128 KiB 单元上比 ZFS 省、**比 btrfs 省一半**」。
按字面（本工程 × 2 ≤ btrfs）这半句在 N = 0 就不成立：108 × 2 = 216 > 207.3。
实际比值是 108 / 207.3 = **52.1%**，不是 50%。

## 两档几何都跑了

D21 正文只说「单元预留一段」，**没说索引节点这类单元带不带扩展点**。
按 D20（承重面：单元的原子性与自包含）「单元不分元数据与数据」的字面读法是都带。
- 都带（all_units）：上界 B = 864。
- 只有数据单元带（data_only）：索引节点扇出不受影响，上界 B **不存在**（树高永远不涨）。

## 要被攻击的那个推论

**推论 P**：D21 已定项 2 **不能单独定案**——它的答案完全由一个尚未定的口径决定
（扩展点字节计不计入本工程的单元元数据）。因此正确的处置是：
先定口径，再定数；并且 D21 正文「比 btrfs 省一半」那半句要按实测改写成「约为 btrfs 的 52%」。

**推论 P 的一个强形式 P′**：若取「计入」口径，则正文举例的 128 字节**必须被否掉**，
因为它是上界 19 的 6.7 倍。
