## 二、攻到达序臂：共用随机数发生器是真的，但那 +12% 不是它来的

### 2.1 混杂项确实存在，装置分不开

`research/e7-index-bench/src/bin/e151_arrival_and_container_arms.rs:602` 是
`let dirty = dirty_set(load, &mut rng, OBJECT_COUNT, DIRTY_PER_CHECKPOINT);`，
而同一个文件 `:618` 是 `let order = arrival_order(&dirty, &mut rng);`，
`arrival_order` 的实现（同文件 `:521-528`）逐字：

```rust
fn arrival_order(dirty: &[usize], rng: &mut Rng) -> Vec<usize> {
    let mut order = dirty.to_vec();
    for index in (1..order.len()).rev() {
        let other = rng.below(index + 1);
        order.swap(index, other);
    }
    order
}
```

⇒ 丙臂每个 checkpoint 从**主随机数发生器**多抽 63 次，所以从第 2 个 checkpoint 起，
丙臂看到的脏集合序列与乙臂**完全不是同一串**。装置里没有任何东西能把
「洗牌的效应」与「换了一串随机数的效应」分开：唯一盯着这件事的单测是同文件 `:1055-1060`

```rust
    fn arrival_arm_differs_from_bump_segment() {
        let bump = run_arm(Arm::BumpSegment, Load::Runs8, 0, 0, 300, 50);
        let arrival = run_arm(Arm::Arrival, Load::Runs8, 0, 0, 300, 50);
        assert_ne!(bump.runs_final, arrival.runs_final);
    }
```

它只做 `assert_ne!`，**换一串随机数照样过**——这正是 `.claude/rules/mutation-sampling.md` 与
`.claude/singlefs-ai-sop/rules/test-discipline.md`「只让多条臂互相比，测不出『所有臂一起错』」说的那个形状：
一条相对断言，没有把「到达序的效应」这个量本身钉住。

### 2.2 判据：加两条臂就分得开——我加了，混杂项不是那 12%

分开它需要两条对照，副本两条都加了，脏集合序列与主随机数发生器的消耗都写明了：

|---|---|---|
| `bump_seg_burn_rng` | 乙 + 每轮空烧 63 次抽样，**不洗牌** | 与丙（原样）同样分道 |

### 2.3 真正的毛病在臂的定义里：「到达序」被写成了「均匀置换」

`.claude/kb/experiments/151-用户数据落点的到达序与容器臂.md` 的臂表逐字给丙的括注是
「arrival（丙）｜bump 段、批内到达序」，而模型那一节逐字是
「到达序 = 对 E93（老化下的放置与碎片度） 的升序脏集合再用同一个随机数发生器**洗一次牌**」。

**均匀置换是「到达序」的一个读法，而且是反局部性那个极端的读法。** 另一个读法由已定条款给出：

`.claude/kb/decisions/16-发布语义.md:182`（已定项 5 末段，事务切分纪律，2026-09-13 用户重申）逐字：

> 取号 = 事务被分配进某个 checkpoint 那一刻，checkpoint 的切分只关闭成员资格——触发之后不再分配事务进它，已分配的事务把各自的单元写完，发布阶段等全部单元落盘（任何 COW checkpoint 都要等最慢的那次 I/O，ZFS 的 txg sync 同样等最慢的 vdev，未在本项目验证）。事务切分纪律把一次写请求按单元切成若干事务各自取号，一个事务最多写一个单元的用户数据

一次写请求被切成若干事务，每个事务写一个单元。**同一个请求的那几个单元是连着到达的**，
而 E93（老化下的放置与碎片度） / E151（用户数据落点的到达序与容器臂） 的 runs8 负载（成段重写，段长 8）建模的正是「一次请求碰 8 个连续 key」。
⇒ 按切分纪律，那 8 个单元是 8 个连着取号的事务，分配器连着拿到它们；
把它们跟别的请求的单元**均匀打散**，等于假设 checkpoint 内的事务次序与请求结构无关。

我按「请求到达顺序，请求内部按 key 升序」加了一条臂 `arrival_request_faithful`。
它与乙**共用同一串随机数、同一批脏 key**（主发生器的消耗逐字相同，只是额外记下每个请求新插进去的 key），
所以两条臂的差别只剩「批内怎么排」这一样：

```text

PROBE E arm=arrival_request_faithful load=runs8 m=0 runs_median=7334
PROBE E arm=arrival                  load=runs8 m=0 runs_median=8183
PROBE E arm=first_fit                load=runs8 m=0 runs_median=7997
PROBE E arm=bump_seg                 load=runs8 m=9 runs_median=7371
PROBE E arm=arrival_request_faithful load=runs8 m=9 runs_median=7380
PROBE E arm=arrival                  load=runs8 m=9 runs_median=8183
PROBE E arm=first_fit                load=runs8 m=9 runs_median=7995
PROBE E arm=bump_seg                 load=uniform m=9 runs_median=8186
PROBE E arm=arrival_request_faithful load=uniform m=9 runs_median=8191
PROBE E arm=arrival                  load=uniform m=9 runs_median=8191
```

**均匀随机负载上请求忠实的丙与均匀置换的丙逐格相同（8191 对 8191）**——
因为均匀负载下每个请求只有一个单元，请求结构不存在，两个读法必然重合。
这一格是内建的判别力对照：它证明 7334 不是「把丙偷偷改回乙」，而是请求结构本身给的。

⇒ **E151（用户数据落点的到达序与容器臂） 结论 1 那句「乙对甲的『97.6% vs 89.3%』优势是 key 序批带来的假象」不成立。**

## 三、判据 5-1 的判定：乙作为**用户数据**政策实现不了，但它的数不因此作废

判据 5-1 的判红条件逐字是「有腿证明真实系统里分配器拿得到 key 序批（先攒批再排序是既定机制）」。

**我证不出来，所以 5-1 按字面不打中。** 依据是同一句 D16（发布语义） 已定项 5：
「已分配的事务把各自的单元写完，发布阶段等全部单元落盘」——用户数据单元在**发布阶段之前**就各自写完了，
分配器是一个事务一个单元地被叫到，没有一个「先把这个 checkpoint 的用户数据脏集攒齐再按 key 排序」的步骤；
要造出那个步骤，就得把全部用户数据单元的落盘推迟到发布阶段，而那与「已分配的事务把各自的单元写完」这句直接冲突。

**但这一格有一条不对称，材料与 E93（老化下的放置与碎片度） 都没写，而它改变结论的读法**：

| 流 | 分配器拿到的是什么 | key 序批做不做得到 |
|---|---|---|
| **用户数据单元** | 一个事务一个单元，按事务取号次序 | **做不到**（上一段的理由） |
| **提交内生块**（分配记录树 / 记账树等的 COW 新节点） | 发布阶段一次性产生的一批树节点 | **本来就是**：树的 COW 重写按 key 序自然产生，D3（空间分配） 已定项 5 要它们从聚簇段分配正是骑在这一点上 |

⇒ E93（老化下的放置与碎片度） 的 `bump_seg` 臂（把一批脏对象按 key 升序铺进段）是**提交内生块那条流**的忠实模型，
拿它当**用户数据**政策的候选才是错位。而 E93（老化下的放置与碎片度） 自己的源码注释
`research/e7-index-bench/src/bin/e93_aging_placement.rs:400` 逐字写着
「用户批次按 D3 已定项 5 的形态顺序写进聚簇段（**时间聚簇，不保证 key 连续**）」——
**注释说的是时间聚簇，而代码里 `dirty_set` 用 `BTreeSet` 返回升序**（同文件 `:330-350`，

### 7.2 顺带打中一条：「打包喂不出空段」也是巡回预算这个取样点的产物

`research/e7-index-bench/src/bin/e151_arrival_and_container_arms.rs:39-40` 逐字：

```rust
/// 打包巡回：每 checkpoint 最多看 64 个 key（取法，不是条款）。
const PACK_SWEEP_PER_CHECKPOINT: usize = 64;
```

**这个 64 恰好等于每 checkpoint 的脏对象数 D = 64**——打包器每轮看 64 个 key，
负载每轮弄脏 64 个 key，扫完一圈 8192 个 key 要 128 轮，而这 128 轮里负载也正好把每个 key 平均弄脏一次。
⇒ 装置把打包器与负载设成了**一比一的赛跑**，而这个比值没有任何条款钉着：
D27（小数据打包容器） 已定项 6 第 5 条逐字只说「起跑：**连续巡回加限速**，不设水位」，
限速取多少逐字记在 C202（打包巡回的空转开销与迟滞 K 都没有数）（「连续巡回在**无活可干时空转读映射**的开销一次没量过」）。

把巡回预算放大（其余参数原样）：

```text

PROBE C arm=container_k16 load=runs8 m=9 sweep=256  runs_median=3018 empty_final=0 empty_max=38 packed_share_pct=63.6 write_amp=1.103
```

而同一份材料的 P3 逐字：「runs8 上甲 **7997（97.6%）**、乙 7312（89.3%）、丙 8183（99.9%）」。

⇒ **甲在成段重写负载上是 97.6%，不是 99.9%。** 7997 / 8192 = 97.62%。
倾向段与问法 3 把甲那一格抬了 2.3 个百分点，而这一格正是三条候选唯一分得开的那一档
（P3 自己下一句就是「乙比甲好的那 8 个百分点」）。
这与 E93（老化下的放置与碎片度） 那句「两组负载是端点不是分布」合在一起看更要紧：
**唯一有区分度的那一端上，倾向段报的数比产物大。**

### 9.3 「回落率 92%–94%」被当成政策的性质用，而 E93 明令它不能这么用

倾向段逐字「回落率 92% 说明第一版行为上几乎就是甲，条款却不必写两条路径」，
问法 3 逐字「丙 92% 的时间在走甲」。
而 E93（老化下的放置与碎片度）「它答不了的」第 6 条逐字（整段抄在背景材料附录里）：

> 回落率是全部分配的口径，**不能**当作提交内生块的聚簇成功率。

「第一版行为上几乎就是甲」这句话要成立，得那 92% 里**提交内生块也跟着回落**——
而那正是 E93（老化下的放置与碎片度） 明令不能从这个数里读出来的东西。
第 6.1 节实测：真按提交内生块单独看，乙′ 是 **0 次**、甲′ 是混合口径 137 488 次里的一部分（具体多少两份产物都没量）。
⇒ **「甲′ 行为上几乎就是甲」这句话把最要紧的那一半反着说了**：
在 runs 上甲′ 确实几乎就是甲，在 D3（空间分配） 已定项 5 要的那个量上，甲′ 与甲差得最远。

### 9.4 C243 要的是轨迹，E151 给的是一个端点，而欠账行按端点写下了「从来不为正」

C243（停机谓词那个量从来没有过轨迹） 的 howto 逐字：

> 给 E93（老化下的放置与碎片度） 加一个「全空聚簇段数」的直接轨迹指标（不是回落率），**逐轮报绝对值**，并给一条钉绝对值的断言（不许只做臂间互比）。判别力自证：把「`R` 在意图期内不可作分配目的地」这条保护关掉，全空段数的净增量必须塌向 0；打开必须恢复

E151（用户数据落点的到达序与容器臂） 交付的是 `empty_segments_median`——**期末那一个值**，不是逐轮的轨迹。
而 C243（停机谓词那个量从来没有过轨迹） 的欠账行 2026-09-13 据此写回：

> 40 格期末全是 0——停机谓词那个量在 E93（老化下的放置与碎片度） 几何下**从来不为正**，谓词只能靠整理喂出空段才有输入。

⇒ **「从来不为正」不成立。** 副本按 C243（停机谓词那个量从来没有过轨迹） 要的口径逐轮记了：
bump_seg / arrival 在 2000 个 checkpoint 里有 **122–159 个**读正数，峰值 32（= 初值）；
容器臂在巡回预算 ≥ 256 时峰值到 38–96，**超过初值**（第 7.2 节）。
把一个端点读成轨迹，方向恰好是「更绝望」那一边——它会让下游以为这个量根本没救，
而实测说的是「它有正读数，只是被前台吃得只剩 6%」，那是两条不同的结论，对应两条不同的修法。

⚠️ 判别力自证那一半（关掉 `R` 保护、净增量必须塌向 0）**也没做**：
E151（用户数据落点的到达序与容器臂） 被判的三条臂（bump_seg / arrival / container）里根本没有整理、没有 `R`，
那条自证没有被测对象。⇒ C243（停机谓词那个量从来没有过轨迹） 今天**不该记成已还**，
它欠的两样（逐轮轨迹、判别力自证）都还欠着。
