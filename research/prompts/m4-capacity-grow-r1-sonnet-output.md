# m4-capacity-grow-r1 正推腿报告（Sonnet）

日期：2026-11-17。背景 `research/prompts/_m4-capacity-grow-r1-background.md`。方案按 `crates/` 今天的实现谈。逐盘容量表今天在 `crates/` 里没有：`grep -rn 'capacity_table\|容量表' crates/singlefs-core/src crates/singlefs-checker/src | wc -l` 本次输出 0。所以写法建在 `research/prompts/m4-capacity-r3-main-verification.md` 已判的形态上（表追加在定长部分之后、读数出口取记录值、变小可写拒只读放行并点名），再加上「变大时怎么记」。

名字：「旧表」= 变大之前盘上的逐盘容量表，「新表」= 这次挂载要记的，「生效表」= 读者此刻当作记录的那一张，「先轮」「后轮」= 取号写两轮里覆写各盘取号前较旧槽的那一轮与覆写取号前较新槽的那一轮（代码里 `AcquisitionWriteRound` 的两个成员）。「较旧槽」「较新槽」都按取号之前的世代号说。

## 结论

1. 写的时点：新表在可写挂载的取号写两轮里写（每一次取号写都带它）；它是什么在分配器建图之前由一个纯函数定好（不读不写盘）；分配器按新表建，但第一个往盘写单元的动作排在后轮屏障之后。只读挂载不写。
2. 写的范围：每块盘两个槽，共 2n 个槽，次序与屏障就是今天取号写两轮的次序与屏障，没有多出来的写。读者认「正在改表」的条件：盘上全部自证槽（本池 fsid、这一版认得）的表两两逐项可比（成链）；成链就取最小的那张为生效表，不成链整池拒。写者每一次写都保持成链（第 2 格给证明）。
3. 生效 = 后轮屏障返回。之前盘上没有任何单元、journal 记录或根按新表分配；之后每个自证槽的表都不小于新表。
4. 跨根层级：拒记，不重建。池的根层级终身等于 mkfs 那张表的层级。夹到边界为止是另一条路，属于用户可见行为，列在「交用户的」。
5. 变大再缩回：记录只升不降，缩回 ⇒ 可写拒、只读放行并点名；在「屏障诚实」的前提下，没有落点越过缩回后的盘尾而读者看不出的历史。
6. 与 D2（RAID 条带策略） 已定项 3 的关系：算那条事务在「卷还没挂、在飞写为空」时的一个退化实例，条款要补，改句在第 6 格。
7. D22（单元原子性怎么合成） 已定项 26：归「系统运行量」，射程里「每次发布都在动」那半句要改。
8. 四种窗口：G1、G2、G4 躲开；G3 条件式躲开（不压在 C974 的结局上，压在它的成本上）；躲不开的新窗口一个，本报告叫 G5：取号完成到写行那次发布的根落盘之间，记账里的空闲 / 已分配统计还是旧容量，生效表已是新容量，I-5.2、I-3.16 一类按生效表算容量的判法在这一段崩溃态上会红。写法在第 3 格末尾。
9. 本报告的新写法（成链规则、放弃挂起的变大、拒记）都是零轮：没被攻过，也没写模型跑过。崩溃中间态表是读码加手推，没枚举。

## 第 1 格 写的时点

**写法。**

1. 在 `mount_writable_with_every_test_only_switch` 里，R3 的「每块盘探测值不小于它那一项，否则可写拒」判完、`every_device_reaches_the_unit_area_start` 之后，调一个纯函数 `capacity_to_use_in_this_mount(生效表, 盘上最大表, 各盘探测整槽数)`，交回 `in_force`（生效表）、`to_write`（这次取号写要写的表）、`growth_not_recorded`（没记的变大与原因）。不读不写盘。规则按顺序：
   - 候选 = 逐项取 max(生效表项, 探测整槽数)。候选等于生效表 ⇒ 没有变大，`to_write` = 生效表。
   - 候选不逐项大于等于「盘上最大表」（盘上有挂起的、某盘探测值又小于挂起那一项）⇒ `to_write` = 生效表，放弃挂起的变大，点名那块盘。
   - 候选的根层级（`AllocationRecordTreeGeometry::of_devices`，`crates/singlefs-core/src/allocation_record_tree.rs:97`）不等于生效表的根层级，或有一项大于 2^48 ⇒ `to_write` = 生效表，点名（第 4 格）。
   - 否则 `to_write` = 候选。
2. 分配器与分配记录树的几何按 `to_write` 建：`allocator_of_the_previous_version`（`crates/singlefs-core/src/mount.rs:3234`）里 `device.size_in_bytes()` 换成 `to_write` 项 × 16384。读数的其余出口（R3 判决里的出口清单）取生效表。两处取数不同只有这一处，且两张表的根层级相同（第 4 格），所以 `AllocationRecordTreeGeometry::of_allocator`（`crates/singlefs-core/src/transaction.rs:14006`）与 `of_reader`（`crates/singlefs-core/src/mount.rs:2759`）算出同一个几何。
3. `to_write` 经 `InstanceStart` → `PublishesPlannedAfterAcquisition` → `acquire_then_publish_until_the_continuation`（`crates/singlefs-core/src/mount.rs:8604`）→ `write_the_witnessed_expected_acquisition` 交给取号写，进 `AcquisitionWitnessedBeforeItsWrites`（`crates/singlefs-core/src/transaction.rs:1245`）。`write_system_configuration_slot` 加一个参数，形状照 F 那个：`CapacityTableOfASystemConfigurationWrite::{TheTableOnTheDisk, TheTableToRecord(&表)}`。取号写两轮的每一次传 `TheTableToRecord(to_write)`；回卷（`:800`）、发布末尾轮换（`:629`）、抬 F（`:910`）、离线出路（`:658`）传 `TheTableOnTheDisk`：抄这块盘上自证槽里世代号最大那一槽的表，本盘一槽都没有（补写之外的离线出路）抄按设备次序第一块有自证槽的盘的。`PoolWriter::new` 的签名不动。
4. 只读挂载：只择、只比、只报，不调这个函数。

**依据（为什么是取号写里，不是别处）。**

- 取号写是可写挂载的第一个写，它之前的每一步都承诺「拒了盘上逐字节不变」：「照旧在取号之前拒，盘上逐字节不变。」（`crates/singlefs-core/src/mount.rs:8080`）、「有一步要开的容器号到顶（C841）就在取号之前拒，盘上逐字节不变」（`crates/singlefs-core/src/mount.rs:7939`）、「在读根环之前拒，盘上逐字节不变。」（`crates/singlefs-core/src/mount.rs:9884`）。取号之前的读与预演只读盘：「只读盘与发那一道屏障，一个字节都不写」（`crates/singlefs-core/src/transaction.rs:1182`）。所以把写放在建图之前（用户问的第一个选项）会让这些拒绝不再是「一个字节不写」；还要自己再造一套「写前屏障、覆写较旧槽」的协议，那一套取号写已经有。
- 取号写之后到第一个单元写之前没有别的盘写：「每轮之后一道屏障，第二轮那道屏障完成才把新号交出去，于是本实例的第一个非系统配置写一定排在它之后。」（`crates/singlefs-core/src/transaction.rs:1095`）；挂载里取号返回（`crates/singlefs-core/src/mount.rs:8640`「let acquired = witnessed」）才进写行（`crates/singlefs-core/src/mount.rs:8685`「let row_publish = match &start.previous {」）。分配器在这之前建好、预演也在内存里用它，但它交给设备的字节都排在后轮屏障之后。
- 放在发布末尾的轮换里不行：根槽 FUA 先于轮换（`crates/singlefs-core/src/transaction.rs:1723` `persist_the_root_then_rotate_the_system_configuration`），那是 G1 的窗口。单独一次排在暖机之后也不行：新表生效之后到下一次发布之前的整段静止时间里，记账统计都是旧容量，G5 的窗口变成常驻。
- 预演与真发必须用同一个容量：「取号之前在分配器的拷贝上取的落点与真发起来取的逐次相同」（`crates/singlefs-core/src/mount.rs:8804`，断言）。预演若按旧表、真发按新表，分配器的偏好（空槽最多的叶、最低的全空段）可能选出不同的落点，这条断言会炸。所以分配器从建图起就按新表。

**推翻它的观测。**

- 崩溃点重放里有一个崩溃态：盘上某个根或 journal 记录点名的落点越过旧表、而该态下读者取到的生效表还是旧表。
- 在取号返回之前，挂载路径上有任何一个往盘写非系统配置字节的动作（读码与 `grep` 没找到，但没有逐条追过 `establish_instance` 的每个调用）。
- 预演与真发的断言（`crates/singlefs-core/src/mount.rs:8804`）在变大的世界里炸，说明两边容量没对齐。

**与已定条款、R3 判决的比对。** 写者那句一致：「写者：每条写系统配置槽的路抄择到的表，连 devs 一起抄（正推：`crates/singlefs-core/src/transaction.rs:723` 今天按盘表现数）；离线修复同样。盘变大时哪一步改表，归 m4-capacity-grow。」（`research/prompts/m4-capacity-r3-main-verification.md:29`）——本格就是它留给这一题的那一步。与 R3 正推腿的改句有冲突：「**逐盘容量表只在 mkfs 写。**」（`research/prompts/m4-capacity-r3-sonnet-output.md:195`）按用户后来的定案不再成立，改成「只在 mkfs 与可写挂载认出盘变大的那次取号写里写」。

## 第 2 格 写的范围、次序与中间态

### 2.1 写几块盘几个槽、次序

2n 个槽（n = 盘数，第一版 2 块盘，4 个槽），次序就是取号写两轮：

1. 取号写之前一道池屏障（已有）。
2. 先轮：盘表次序逐盘写较旧槽，每次整槽 4096 字节，带（新实例号、见证 tail、F、`to_write` 表）。池屏障。
3. 后轮：盘表次序逐盘写另一槽，同内容。池屏障。返回。

「取号写两轮」的写数、次序、屏障与今天完全相同：「for _round in ACQUISITION_WRITE_ROUNDS {」（`crates/singlefs-core/src/transaction.rs:1334`）。变大这件事没有多一次写、多一道屏障。这一点也是它躲 G3 的依据（第 3 格末）。

### 2.2 写者的不变量：盘上的表永远成链

定义：盘上全部自证槽（本池 fsid、这一版认得）带的表，两两逐项可比（一张的每一项都不大于另一张对应项），叫「成链」；成链时有最小的一张，叫生效表，有最大的一张，叫盘上最大表。

不变量：任何一次写之前盘上成链，写之后仍成链，不要求任何写的完成次序、也不要求写不被撕裂。证明按写者逐个过：

| 写者 | 写进去的表 | 为什么不破坏成链 |
|---|---|---|
| mkfs | 全部槽同一张 | 只有一张 |
| 取号写（先轮、后轮、补写盘的两槽） | `to_write` | 纯函数只给两种：生效表（盘上已有的最小那张），或逐项不小于盘上最大表的候选（上面纯函数里「不逐项大于等于盘上最大表就写生效表」与「否则取候选」两条保证），两种都与盘上的表可比 |
| 取号回卷 | 抄这块盘上自证槽里世代号最大那一槽的表 | 盘上已有的表 |
| 发布末尾轮换、抬 F | 同上 | 同上 |
| 离线出路 | 同上（本盘没有自证槽就抄别的盘的） | 同上 |
| 槽被撕裂 / 读不出 | 无 | 子集仍成链 |

由此：生效表单调不降（每个写者都只写不小于盘上现有最小表的表；删掉槽只会让最小值变大）。这是躲 G2、G4 的依据。

### 2.3 读者怎么认「正在改表」、取哪一份

条件，全部成立才认：

1. 池级字段（fsid、devs）各槽相同（今天的 `SystemConfigurationsDisagree` 那一判，`crates/singlefs-core/src/recovery.rs:1901`「|| previous.immutable.device_count != best_on_device.immutable.device_count」）。
2. 各表项数 = devs，过 R3 的值域判（每项 0 < 项 ≤ 2^48，devs ≤ 450，本盘设备号 < devs）。
3. 各表两两逐项可比（成链）。
4. 各表的根层级相同。

认了就取最小的那张当生效表，其余字段照今天：每盘取世代号最大的槽，按盘表次序留最前那块盘的那一份（`crates/singlefs-core/src/recovery.rs:1881` 起的那一段）。有一条不成立 ⇒ 整池拒，错误成员另立（`CapacityTablesDisagree`，不并进 `SystemConfigurationsDisagree`）。代码改在 `choose_system_configuration_among_the_slots_of`（`crates/singlefs-core/src/recovery.rs:1835`）：今天每盘只留一个最好的槽、两槽不比内容（「(Some(zero), Some(one)) => {」，`:1888`），改成把全部自证槽的表收齐，成链判一遍，择到的配置里的表字段换成最小那张，另在 `SystemConfigurationChoice` 加一个「挂起的表」交给挂载与只读报告。

**两句并存**。R3 判决那句：「读者：跨盘、跨槽（限本池 fsid、这一版认得的自证槽）容量表不等整池拒；每块盘探测值小于它那一项——可写挂载拒，只读挂载放行并在报告里点名（用户定）；表项为 0 整池拒。」（`research/prompts/m4-capacity-r3-main-verification.md:28`）。这里改成「不成链整池拒；成链而不全等，是变大写到一半，取最小那张」。全等是成链的特例，今天与 R3 的行为一字不变。这一改动与 R3 的 I-7.20 要同时改（I-7.20 从「逐项相同」改成「成链」）。零轮。

什么现象说明「取最小」取错：生效表大于旧表之后，盘上出现落点越过某个自证槽里的表，却没有任何一个读者看得到。成链的写者不变量保证这不会发生；它只在设备丢写（C6，块层假设写错）时才破。

### 2.4 「正在改表」的每一个崩溃中间态（两盘，按写的次序）

记号：旧 / 新 = 槽里的表；✗ = 这一槽撕裂或读不出（不自证）。「先轮槽」「后轮槽」= 取号之前较旧的槽、较新的槽（先轮覆写前者，后轮覆写后者）。每次系统配置槽写取三态（完成 / 缺失 / 撕裂），撕裂的槽新旧内容都不自证，对表集合来说撕裂等于缺失，区别只在撕裂把被覆写那一槽的旧内容也毁了。崩溃点重放对系统配置槽写本来就取这三态：「test result: ok. 2 passed」（`research/prompts/m4-capacity-r3-main-verification.md:16`，任务 18800 两条单测）。屏障已过的写一定是完成的。

二次崩溃（挂起状态之后再挂载，两次之间用户又动了盘）。第二次挂载的纯函数按下面四种给 `to_write`，每一种写进去的表都与盘上的表成链：

- 盘没再变，探测值不小于盘上最大表：写同一张新表。
- 盘又变大：写更大的候选（逐项不小于盘上最大表），盘上最多同时有旧、新、更大三张，成链；生效表在旧表还有槽时是旧，旧表一槽不剩后是新，再往后是更大。
- 盘缩回到「旧表 ≤ 探测值 < 新表」（某盘）：候选不逐项不小于盘上最大表 ⇒ 写生效表（旧），取号写两轮把旧表写满，挂起的变大作废、点名那块盘；写的过程中盘上只有旧、新两张。没有这一条会怎样：候选（小于新表）与新表不可比，先轮写完之后可以出现 {新, 候选} 而旧表一槽不剩（挂起的新表占着每盘较新的槽，第二次挂载的先轮覆写的恰是每盘较旧的、带旧表的那一槽），读者不成链整池拒。
- 盘缩到旧表之下：探测值小于生效表项 ⇒ R3：可写拒、只读放行并点名，一个字节不写。

态数（推的，没数过）：先轮屏障之前两个先轮写各三态 3 × 3 = 9 种，先轮屏障之后后轮两个写各三态 9 种，加后轮屏障之后 1 种，系统配置那一部分共约 19 种；再乘上发布段的崩溃点才是整条挂载的态数。

## 第 3 格 新容量生效与分配的先后

**怎么做。** 「生效」定义成一个读得出的盘面事件：盘上没有任何自证槽带比新表小的表（旧表的最后一槽被覆写或撕裂）、且后轮屏障已返回。次序由三件今天就有的事保证，不新增屏障：

1. 取号写两轮：先轮、屏障、后轮、屏障，屏障返回才交出新号（`crates/singlefs-core/src/transaction.rs:1334`「for _round in ACQUISITION_WRITE_ROUNDS {」、`:1095` 的注释）。
2. 取号返回之前，挂载路径上除系统配置槽以外不写盘（第 1 格依据第二条）。
3. 分配器虽然从建图起按新表，但它产出的只是内存里的落点；落点变成盘上字节要经 `persist_publish_writes`（`crates/singlefs-core/src/transaction.rs:1543` 一带），调用方都在取号返回之后。

**崩溃在哪一步之后才可能有落点越过旧容量。** 后轮屏障返回之后，并且要再过写行那次发布的单元写。证明两步：

- 甲：本次挂载里任何占着旧容量之外槽的单元、journal 记录或根，都写在后轮屏障之后（上面三条）。
- 乙：屏障之后每个自证槽的表都不小于新表（第 2 格不变量加屏障持久）；之后任何写者写的表不小于盘上最小表，删槽只抬最小值。所以这之后的任何崩溃态，读者取到的生效表都不小于新表，越过旧表的落点都在生效表之内，R3 的落点判（`crates/singlefs-core/src/recovery.rs:2868`「what: "分配记录的跨度越过单元区末尾",」，换成生效表之后）通过。

**建议加的判别力（给实现员，变异行由主 agent 登记）。** 世界：旧容量几乎写满，盘变大。弄坏项各自该让某个崩溃态红：(1) 取号写两轮都写旧表（等于不记）；(2) 把表放到发布末尾的轮换里写；(3) 后轮屏障去掉；(4) 分配器按探测值而不是 `to_write` 建。每一项红的判法是同一条：「被候选集里的根引用的落点不越过生效表」。这一条今天的落点判已经有（`recovery.rs:2868`），换出口之后自然判到。

### G5：生效表与记账统计之间的窗口（本报告新找到的，躲不开，写了代价）

记账里的空闲 / 已分配行取自分配器当时的空闲图：「PerDeviceAccountingRow::FreeBytes => device_map.free_slots() * SLOT_BYTES,」（`crates/singlefs-core/src/transaction.rs:16342`），每次发布重写固定点单元时刷新。checker 按容量判它：「judgements.judge("I-5.2", matches!((free, allocated, capacity), (Some(free), Some(allocated), Some(capacity)) if free.checked_add(allocated) == Some(capacity)), || {」（`crates/singlefs-checker/src/walk.rs:22294`），R3 把 `capacity` 的来源换成生效表。于是后轮屏障返回（生效表 = 新）到写行那次发布的根槽落盘之间，最新根的统计还是旧容量，I-5.2、I-3.20 的和与 I-3.16 的全扫重算都对不上，崩溃点重放每个崩溃态都跑 checker，这一段会红。

反方向（统计先于生效表）更糟：根上已有按新容量的统计与落点，而生效表还是旧的，就是 G1。两个结构（系统配置、根）没有单一原子点，窗口只能二选一；取「生效表先」，因为红在「统计少于容量」这一边，是安全的一边。

写法（零轮，没读 checker 里现成的「取号之后、发布之前」判法，是推的）：checker 与 GPU 判器认「取号未发布」态：盘上某个自证槽的实例代号大于最新有效根的实例代号。这个态里，I-5.2、I-3.20 的和、I-3.16 的重算改判「统计容量不大于生效表容量」，不等的那一半报「部分没判」（现成机制：`part_of_the_range_left_unjudged`，`crates/singlefs-checker/src/walk.rs:22277` 一带），统计容量大于生效表容量仍判红。这个态在没有变大的挂载里也存在（取号写之后、写行之前），那里统计容量恰等于生效表容量，判法不变。

**推翻 G5 的写法：** 崩溃点重放的盘变大世界里，取号未发布态之外还有 I-5.2 红的态；或取号未发布态里出现统计容量大于生效表的合法盘面（说明有写者先于生效表改了统计）。

**与 C974 的关系（G3 在这里收口）。** 本格的安全论证只用「后轮屏障返回之后每个自证槽带新表」这一个后置条件，不用「两轮」本身。今天它由取号写两轮给出（`crates/singlefs-core/src/transaction.rs:1313`「const ACQUISITION_WRITE_ROUNDS: [AcquisitionWriteRound; 2] = [」）。C974（取号写两轮的去留没定）判删第二轮时，变大那一次取号自己再补一轮（只在 `to_write` 不等于生效表时），后置条件不变；没变大的挂载不多一次写。所以容量不是 C974 要找的那一形（它判的是「写一轮与写两轮结局有没有差」，这里两种做法结局相同，因为后置条件相同）。C974 那一行建议只补一句：「容量表的记不依赖第二轮」。

## 第 4 格 跨分配记录树根层级边界

**怎么做：拒记，不重建。**

规则已在第 1 格的纯函数里：候选的根层级不等于生效表的根层级就不记，`to_write` 取生效表，挂载照常做成，有效容量仍是生效表，报告点名「盘 d 探测 X 槽、记录 Y 槽，变大跨过根层级边界，没记」。结果是不变量：池的根层级终身 = mkfs 那张表的层级（只有 mkfs 能定层级）。

**依据（为什么不重建）。**

- 今天读写两侧都只有一个几何。读侧每个读某一版分配记录树的地方都调一次 `AllocationRecordTreeGeometry::of_reader`：「&AllocationRecordTreeGeometry::of_reader(reader),」（`crates/singlefs-core/src/recovery.rs:2939`、`:2995`、`:4461`、`:7473`，挂载建上一版 `crates/singlefs-core/src/mount.rs:2759`），写侧 `of_allocator`（`crates/singlefs-core/src/transaction.rs:14006`「let geometry = AllocationRecordTreeGeometry::of_allocator(allocator);」）。几何只由生效表定，没有「这一版是按哪个层级写的」。读到层级对不上的根就拒：「if header.level != self.geometry.level_of(node) {」（`crates/singlefs-core/src/allocation_record_tree.rs:709`）。这就是今天跨边界会被层级错拒掉的那一处（读码推的，没有用例验过）。
- 重建意味着变大前后的版本层级不同。回退候选、被抛弃根的账、journal 里没施加的记录都要读变大之前的版本；它们用同一个（新）几何读就在 `:709` 拒。要读得动就得每一版（或每张表）自带层级，那是格式变化，不是这一题能顺手做的。`crates/` 里没有按新层级重写带文件那一版分配记录树的路径：`settle_the_allocation_record_tree`（`crates/singlefs-core/src/transaction.rs:13994`）只按 `previous_nodes` 与同一个 `geometry` 做增量；只有「树表 0 条的一版」的写行那次发布看起来是整树重写（`:1975`，推的：依据是 `transaction.rs:1500` 一带的文档注释「这一版的全部分配记录」，没逐行读函数体），而那一版之前的根（mkfs 的第 0 代）照样要被读，同样的问题。
- 拒记还保证一件事：分配器、预演、读者用的几何永远相同，第 1 格第二点的「两处取数不同」没有后果。

**推翻它的观测。** 一次真实的跨边界变大里「拒记」让用户损失的空间比「夹到边界为止」多到不可接受（用户看数据）；或找到不改格式就让旧版本读得动的办法（例如根记录里已经有层级字段，`grep` 没找，待主 agent 核根记录字段表）。

## 第 5 格 变大再缩回

**怎么做。** 记录只升不降（第 2 格不变量）。缩回后的挂载走 R3 的比对：可写拒，只读放行并点名那块盘（`research/prompts/m4-capacity-r3-main-verification.md:28`）。不为缩回另开路径，也不把记录降回去。

**有没有落点越过缩回后的盘尾而读者看不出的历史？** 在「屏障诚实」（设备守屏障，不丢写）的前提下没有，按历史的前缀逐类过：

| 变大那次挂载停在哪 | 此后用户缩到哪 | 读者 |
|---|---|---|
| 取号写之前、先轮、后轮屏障之前（生效表 = 旧） | 不小于旧表 | 放行，对的：此时盘上没有任何落点越过旧表（第 3 格甲） |
| 后轮屏障之后（生效表 = 新），无论发没发布 | 小于新表某项 | 可写拒、只读放行并点名；落点只要越过了缩回后的盘尾，生效表（新）就大于探测值，一定点名。读者「看得出」靠的是生效表不小于任何已发布落点所需（第 3 格乙） |
| 变大被拒记（跨层级、盘缩回挂起表之下） | 任意不小于生效表 | 放行，对的：分配器只用生效表，没有落点越过它 |
| 回退到变大之前的根再撤回扩容 | 小于新表 | 拒（生效表不随根回退，仍是新）。这是「用对了却挂不上」的代价，不是漏 |

价钱要写明：记录只升不降，所以「变大、什么都没写、又缩回去」也被拒（可写）。出路是把盘再放大，D2（RAID 条带策略） 已定项 3 的事务里的缩小方向第一版没有。这是用户已定的「变小可写拒」的直接后果，不是新增的代价。

只读挂载不判落点（`mounted_read.rs` 里没有分配记录的判：`grep -c 'allocation_records\|placement_lies' crates/singlefs-core/src/mounted_read.rs` 本次输出 0），所以只读挂载能不能发现「落点越过盘尾」完全靠生效表与探测值的比，不靠落点。设备丢写（块层假设写错，C6）会让一个槽留下旧表，生效表变小、只读放行：这是 C6 的类，不在这一题，可写挂载仍有落点判兜住。

**推翻它的观测。** 一个按取号写次序造出来的崩溃态，加一次「用户缩到不小于旧表」的动作，使只读挂载放行、而盘上有越过缩回后盘尾的已发布落点。

## 第 6 格 与 D2（RAID 条带策略） 已定项 3、4 的关系与改句

## 四种窗口怎么躲（对照 `research/prompts/m4-capacity-r1-opus-output.md` 的 G1–G4）

**G1「记晚于分配」**（`research/prompts/m4-capacity-r1-opus-output.md:95`）：躲开。按它的历史逐步放进这个写法：

| G1 的步骤 | 这个写法下 |
|---|---|
| 2. 「可写挂载：探测 4 GiB > 记录 ⇒ 放行；取号两轮不带新容量（「记」不在取号里）。」（`:102`） | 新表就在取号两轮里，每次取号写都带它 |
| 3. 一次发布把单元放到旧末尾之后 | 排在后轮屏障之后（第 3 格） |
| 4. 「崩溃在根 FUA 之后、系统配置轮换之前。」（`:104`） | 此时每个自证槽都带新表，生效表 = 新表；盘上落点不越过它 |
| 5. 「用户撤回扩容：把盘 1 截回 3 GiB + 33 槽。」（`:105`） | 探测值小于生效表那一项 |
| 6. 只读挂载放行（`:106`） | 放行但点名盘 1，不再静默；可写挂载拒 |

窗口在两处合上：记在分配之前（次序），生效表不随轮换回退（不变量）。

**G2「只写一槽，两槽轮换把记录退回旧值」**（`:112`）：躲开。它的历史（`:116`「- 历史：记写进盘 1 槽 a（世代 g+1，2X）；」起）要两个前提：只有一个槽带新值；轮换会盖回旧值。这里：新表在后轮屏障之前写进每块盘两槽；轮换抄盘上最新槽的表，不抄探测值也不抄旧值；读者取成链里最小的那张，丢槽只会让最小值变大。单故障（一槽读不出）下剩下的槽仍带新表。

**G3「压在没定的 C974 上」**（`:120`）：条件式躲开。它的担心是「改法 b 一旦让容量的记靠取号两轮保证两槽都带新值」（`:122`）。这里的安全论证只用后置条件「后轮屏障返回后每个自证槽带新表」，今天由取号写两轮给出，C974 判删第二轮时变大那一次自己补一轮（第 3 格末）。依赖没有消失，只是从「C974 的结局」变成「C974 若删第二轮、变大那一次多付一轮写」的成本。躲不开的只剩：这个写法今天白搭取号写两轮的车，次序上多不出一次写。

**G4「每次写都按探测值写容量」**（`:126`）：躲开。探测值进表只有一条路：挂载层的纯函数，输入是生效表与各盘探测值，输出逐项不小于生效表（候选取 max）。别的写者（回卷、轮换、抬 F、离线出路）都抄盘上的表，不读探测值：`PoolWriter::write_system_configuration_slot` 今天从内存参数现填整槽（`crates/singlefs-core/src/transaction.rs:723`），改成表这一格从盘上抄。探测值小于记录的盘在任何写之前就被 R3 的比对拒了可写，所以补写盘与离线出路都洗不白缩小。

**躲不开、要点名的：**

1. G5（第 3 格）：生效表与记账统计之间的窗口。代价写法是 checker 与 GPU 判器认「取号未发布」态、改判不等式；零轮，没读现成判法。
2. 记录只升不降的代价（第 5 格）：变大、未写、又缩回被拒可写；用户已定的「变小可写拒」的直接后果。
3. 屏障诚实这个前提：设备丢写（C6）能让一个槽留着旧表；可写挂载的落点判兜住，只读挂载不判落点、放行。不在这一题。
4. 跨层级的变大不记（第 4 格）：用户会看到「盘变大了却用不上」，要报出来。

## 交用户的

只有一条（判不出、是用户可见行为）：**变大跨过分配记录树根层级边界时，一点也不记，还是记到边界为止。**

- 候选甲（本报告取的）：拒记。整张候选表不记，生效表不动，报出来。简单：记录要么等于探测要么等于旧表。
- 候选乙：夹到边界。记「根层级不变的前提下逐盘能到的最大表」，边界之下的那一截能用。多一个夹法（多块盘时先夹哪一块要定一个次序）、记录与探测可以永远不等。
- 代价数（量的，`awk` 本次算）：两盘等大、每盘从 128 GiB 变到 256 GiB，边界每盘 175.8904 GiB；新增的 128 GiB 里用不上的部分，甲 128.0000 GiB（100%），乙 80.1096 GiB（62.6%）。两个候选在盘变大没越过边界时完全相同。
- 翻面观测：用户的池在 mkfs 时的盘大小与之后的扩容幅度——扩容幅度大多落在边界之内时两者没差，跨过边界很常见时乙才值得做。这是用户才有的信息，我没有。
- 两个候选都不动格式；真正解决跨边界要每一版（或每张表）自带层级，是格式变化，另立一题。
