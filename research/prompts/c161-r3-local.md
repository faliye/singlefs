Two-level buffering in a copy-on-write B-tree filesystem design, round 3.

Answer in English. Do not use any markdown emphasis: no bold, no italics, no headings with asterisks. Use plain numbered answers.

This round is about a future version that turns on a write buffer front end and node message buffers (epsilon > 0). The first version turns both off. Facts from the design (treat them as given):

F1. One B-tree engine with several independent keyspaces and two front ends. The write buffer front end batches high-frequency small updates (reverse index, LRU, accounting), sorts and deduplicates them, then inserts them in bulk.
F2. Write buffer requirements: the node cache must resist scans; entries are idempotent full values, never deltas; every entry carries a sequence number seq, because flushing sorts by key and loses time order, so "later wins" must be carried by the entry itself. This is a format requirement.
F3. seq is 4 bytes, stored in the value, not the key, and covers the accounting, reverse index and LRU trees. In the current definition, seq = how many times the same (tag, tree, device, generation) has been written into the tree within one publish, starting at 1. The width argument assumes that entries waiting for deduplication for the same key always belong to one publish window, and the upper bound of the dirty-byte budget is decided at mount time. A rider says: for the same key, cross-batch insertion order must follow seq. A copy of the publish number must not be added to seq, because that would copy a key segment a second time (this reasoning is stated for the accounting tree, whose key ends with the generation).
F4. Index nodes keep a message buffer (future values: epsilon 0.65, fanout 119, 665 buffered messages). The first version uses epsilon 0 for every tree; a tree of height 1 has a root that is a leaf with no buffer.
F5. Staleness is detectable, and the detection logic must not reuse the code that generates or applies messages. Buffers are purely derived state, recomputed from authoritative state. Tree axis: if a tree's pending messages can be recomputed from authoritative state, keep buffers (epsilon 0.65); otherwise epsilon 0. Today only the inode tree is on the "cannot" side; the extent, directory entry, reverse index and accounting trees are judged "can".
F6. Before any index rebuild, every buffer level must be drained; the rebuild entry point enforces it.
F7. The internal layout of index nodes, including message buffers, belongs to freeze layer 4.
F8. If a published root does not include the accounting or allocation record updates of the transactions in the same batch (still in the in-memory write buffer), a crash back to that root leaves the accounting stale. How far the write buffer is drained at a publish point is not covered anywhere. An fsync publishes only the fsynced file's dirty leaves and their ancestors, and nobody has defined which dirty state belongs to a publish.
F9. Accounting entry: (statistic, dimension tuple, generation) -> full value. Non-monotonic statistics: later wins, decided by seq. Monotonic statistics: take the maximum. Only the most recent K generations are kept; dropping one is a point delete of generation (current - K), so each checkpoint writes one entry and deletes one. Accounting goes through the write buffer front end and its entries carry seq.
F10. Applying a journal record swaps four fields of the chosen root (tree table pointer, central mapping root pointer, tree ID counter, rollback lower bound F) for the record's values. The journal design never mentions the write buffer.
F11. Fixed point: each index node and container is written at most once per instance per checkpoint, copied on write all at once at the end of the publish; the first version forbids copy-on-write during inserts.
F12. One transaction may span several journal records; the record header carries transaction boundary fields.
F13. Stale-as-valid risk: if the authoritative value of a key sits in an internal node's buffer and that node is lost, the rebuilt tree has valid headers and checksums but stale content. Detecting it needs a comparable time clue in the format.
F14. What an fsync publishes is stated three ways in the design: (a) the effect of fsync is to trigger a publish early, not a separate log format or a separate recovery logic; (b) each fsync writes the dirty leaves plus all their ancestors plus the root slot plus one record, and ancestors are not deferred; (c) the text in F8, that an fsync writes only the fsynced file's dirty leaves plus ancestors.
F15. A publish is applied as a whole or not at all. The publish counter increases by one per publish, and an fsync-triggered publish counts too; the same counter is the root slot rotation key, the accounting generation and the replay watermark. Replay applies whole publishes only.
F16. An old writer that meets accounting rows for a tree it does not know (tree ID unknown, statistic tag known) must carry those rows unchanged into the new generation (same value, new generation number).

Rounds 1 and 2 found: C was not broken by any history that distinguishes candidates. A-R4 and B-D were broken in their weakest reading by a tree collapse: when the tree gets shorter, an old message in a child buffer was treated as newly arrived and appended after a newer message in the root buffer, so reads returned the old value; the design never says how buffers are redistributed on split, collapse or rebalance. B-mono was broken in its weakest reading when its counter was not persisted: after a crash the counter restarted and two messages in one buffer had the same seq; with the counter persisted it was not broken, but no upper bound on how long a message stays in a cold buffer was seen, so 4-byte seq is not enough. For staleness detection, B-D and A-R4 need a publish number in every message, which conflicts with F3. Partial publish, a drain split across two publishes, and accounting values computed at write time broke all candidates alike; they are not used to judge candidates.

Candidates:
A-R4-T. Front-end flush goes straight to leaves, not through node buffers; node buffers take only updates that do not use the front end. A flush removes older messages for the same key on its path (the path follows the current pivots); landing in a leaf compares arrival order within the same window; a write that does not use the front end evicts the front end's entry for the same key. Reads take the first hit in the order front end, root buffer, ..., leaf. T1: when the tree gets shorter, first push the root buffer down into the children by the push-down rule, then merge the children (general form: restructuring must not change the value read for any key). T2: on rebalance, buffered messages move with their key.
B-D-T. Front-end flush goes into the root's buffer and is pushed down level by level. A buffer holds at most one message per key; a new one replaces the old (monotonic statistics take the maximum). Newer versus older is decided by position, across levels and within a level; seq is not read. Plus T1 and T2.
B-G-T. B as written (position across levels, seq within a level), with seq a pool-wide monotonic counter. T3: the number is taken when the entry enters the front end, the counter is persisted with each publish, and seq is 8 bytes (accounting entries grow from 34 to 38 bytes). Plus T2.
C-T6. A tree uses only one level: front-end trees have epsilon 0 and all their writes go through the front end; other trees follow F5. The front end is drained to leaves before each publish, and landing in a leaf compares arrival order within the same window. T6: the write path of a front-end tree exposes only the front-end entry point (type level), plus a runtime assertion that every change to a front-end tree leaf in a publish matches a front-end entry drained in that publish; the old writer of F16 also writes through the front end.
Optional T5, only for A-R4-T and B-D-T: every message carries the number of the publish that wrote it into the tree, as an on-disk clue for staleness detection; this conflicts with F3.
Shared by all, not used to judge them: a partial publish writes exactly the on-disk image plus the changes of the publish set; accounting rows are computed at publish time from the publish set, and the front end never carries a full value computed at write time; the front-end entries of the publish set are drained in the same publish, cut by transaction; frozen batches for the same key range enter the tree in arrival order. fsync is run both as a full publish and as a partial publish with these rules.

Questions:
1. Correctness under shapes rounds 1 and 2 did not try: the tightenings themselves (cascaded splits and collapses, a child buffer that overflows when the root buffer is pushed down before a collapse, a rebalance interleaved with a partial push-down, a crash after the counter is persisted); deletions in the reverse index and LRU trees (delete markers); the point delete of a monotonic statistic (F9, "take the maximum" meeting a delete marker); an administrator rollback or an instance switch back to an older root, and where the buffers and the counter go then; draining before an index rebuild (F6); trees taller than 3 and batches with more than two keys. For each candidate, give a sequence that reads a stale value or gets two answers, or that makes the accounting disagree with the chosen root after a crash; or list the shapes you tried.
2. Cost and format: what each candidate changes in node layout, in the meaning and width of seq, in persisted counters and in the tree axis of F5; write and read amplification.
3. For each candidate, one check that turns red when it is broken, and how you would prove that the check itself can turn red.
4. Which one do you pick, and what single observation would change your pick?
