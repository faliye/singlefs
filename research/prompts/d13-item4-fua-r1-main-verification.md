# 判决：D13 已定项 4 的 FUA 半句（第一轮，2026-09-20）

判的是 `.claude/kb/decisions/13-验证路线.md:71` 那句「带 FUA 的写也是段边界：**它自成一段**，它之后的写不与它同段」要不要改。正文 `_d13-item4-fua-r1-body.md`，材料 `_d13-item4-fua-r1-background.md`，开工快照 `d13-item4-fua-r1-start-snapshot.sha256`。三条腿：云端攻方（Q3、Q5）、云端正推（Q1、Q2）、本地辩方（Q4）。核查员 67 项、✓61 ✗6，核对表 `d13-item4-fua-r1-verifier-checks.md`。

这一轮**不改 `crates/`**，所以不受门禁 56 号约束。

## 一、结论

**候选甲采纳**（FUA 那种写落在当前段里、然后关掉这一段），**候选乙出局**，**攻方提的候选丁挂起**，三条的理由都不是开轮时写在正文里的那一条。

开轮时主 agent 给的理由是「FUA 只保它自己那一次写的数据，不保它之前的写，所以它不能在模型里替屏障排序」。**这条理由对本工程不成立**：本工程根本不发 `REQ_FUA`。

## 二、这一轮翻出来的、比措辞大的事实

正推腿的附带发现，主 agent 与核查员各自现查坐实：

`crates/singlefs-core/src/block_device.rs` 两份 `BlockDevice` 实现里，`WriteDurability::ForceUnitAccess`（`:245`、`:449`）与 `barrier()`（`:251`、`:455`）调的是**同一个** `file.sync_data()`。而 `write_all_at` 走 `pwrite`，不设 `REQ_FUA`。

块设备 fd 上 `sync_data` 的去向（本机 `/home/fy5090/linux-bug-fix/linux`，`git describe` 报 v7.3-rc1）：

```
block/fops.c:590   blkdev_fsync
block/fops.c:605     error = blkdev_issue_flush(bdev);
block/blk-flush.c:474  bio_init(&bio, bdev, NULL, 0, REQ_OP_WRITE | REQ_PREFLUSH);
```

零长度的 `REQ_PREFLUSH` bio，没有 `REQ_FUA`。

⇒ **本工程至今没有向任何设备发出过一次 FUA 写。** `WriteDurability::ForceUnitAccess` 这个名字名不副实，它的实际行为是「写完再整盘刷一次」，与屏障同形，比真 FUA 强——真 FUA 只保它自己那一次写，整盘刷把此前已完成的写也一起保了。

**用户 2026-09-20 定案：先按保守的走，不改成发真 `REQ_FUA`，优化以后再说。** 原话与射程在 `d13-item4-fua-r1-user-verdicts.md` 第一节。

## 三、逐条判定

### Q1（契约读对了没有）——正推腿：只支持窄读法

`Documentation/block/writeback_cache_control.rst`（6.17 树）两段原文，PREFLUSH 那段明写覆盖「previously completed write requests」，FUA 那段只说「I/O completion for this request … the data」，只字未提之前的写。virtio-blk 规范（OASIS v1.3）**全文零处出现 FUA**，命令类型清单里没有 FUA 类型——核查员独立下载原文重新 grep 坐实，与本机内核 `virtio_blk.c` 从不设 `BLK_FEAT_FUA`、以及虚机里量到的 `fua=0` 三方吻合。

NVMe Base Specification 与 SCSI SBC 的官方原文**没取到**：两处下载都落到要填姓名 / 机构 / 邮箱的访客登记闸，腿没提交个人信息，如实标「未验证」，也没有拿内核驱动代码冒充规范原文。核查员独立复核了这两个闸确实存在。**这一格留空，不算查过。**

**判定：契约读对了。但这一格对本工程的射程被第二节那条事实缩掉了**——契约说的是 `REQ_FUA` 的语义，而本工程不发它。

### Q2（改后的措辞说全了没有）——正推腿：四种形态对得上，一种说不全

屏障紧跟 FUA、流首 FUA、连续 FUA、流尾 FUA 四种，候选甲的措辞与 `crash.rs:327-366` 逐字对得上。`segments.rs:71-74` 与 `:266-274` 那份切法与 `crash.rs` 逐操作等价。

**说不全的一种**：一次写同时带 PREFLUSH 与 FUA。`RecordedOperationKind` 是封闭三元枚举（`Write` / `WriteForceUnitAccess` / `Barrier`），这种写没有编码方式，措辞对它保持沉默。**按第二节那条事实，这一格今天没有对象**：本工程发出的只有「普通写」与「写 + 整盘刷」两种，后者正是 `Write` 紧跟 `Barrier` 的合写。记进交用户表，不在这一轮补。

### Q3（枚举域会不会太宽）——攻方：问反了方向

攻方量出来（模型 `d13-item4-fua-r1-opus-model/`，核查员复跑退出码 0、sha256 逐字相同）：

- 甲、乙、丁三读法在今天登记的历史上**逐向量相同**：第一条流 262165、mkfs 34，与仓里三处独立登记的数逐字对得上（`layout/01-first-txn.md:400`、`:390`，`experiments/142-第一个事务的干跑.md:88` 的 524314）。
- 四条流上 `甲 ⊆ 丁`（丁 = 攻方建的物理可达集）**全部成立**，甲恒不宽于可达集。
- 变异表第 67 行那条流上：甲 262171、乙 262165、丁 1048609。

按甲切段，FUA 那种写永远是它那一段的最后一个写，所以甲从不造出「它之后的写已持久而它没持久」——那是唯一物理上摆不出来的形状。

**判定：Q3 的前件不成立，题面问反了。** 该问的不是「甲会不会太宽」，是「甲离可达集还差多少」——差 786438 个向量。

### Q4（替候选乙辩护）——本地辩方：辩不住

四次抽样、两份干净（s3、s4），按规矩抽到两份干净才停。四份样本都没能给出一个让「自成一段」在今天这套模型里成立的读法。

**独立的实测把乙钉死**（实现员在副本 `copy-a` 上跑的，报告第六节，主 agent 复核过）：照字面改成「自成一段」之后，有屏障与没屏障切出来的段**完全一样**（两边都是 `[记录写][根槽]`），于是变异表第 67 行判绿、里程碑 `.claude/kb/milestone/02-second-txn.md:424` 那条验收变回恒不成立。

机理在第二节那条事实下更清楚：拿掉第 553 行那道屏障之后，落盘序列是「写记录 → 写根 → 整盘刷」。刷完成之前，{记录, 根} 任意子集在介质上，**「根在而记录不在」物理上可达**。甲枚举它，乙不枚举。

**判定：乙出局。**

### Q5（取契约还是取某块盘）——攻方：今天不可证伪

`device_log.rs` 把三样东西归成同一个 `DeviceEvent::Flush`：带 FUA 标志的写（`:132-134`）、独立 FLUSH 条目（`:136-138`）、期望侧 FUA 写后无条件补的 Flush（`:168-170`）。门禁 55 号又跑在 `fua=0` 的 virtio-blk 上。两条路都分不出这两种盘。

**判定：这一格今天观测不到，属于 `evidence-discipline.md`「判别子观测不到」那一形。** 但它的重量被第二节那条事实削掉了大半：本工程不发 FUA，「取契约还是取这块盘」对今天的写流没有对象。**它变成一个条件式问题**，与「以后要不要发真 `REQ_FUA`」绑在一起，一起挂起。

## 四、采纳的措辞，与它为什么对

候选甲对，但理由要换成实现真正在做的事：

> **`ForceUnitAccess` 那种写等价于「一次普通写紧跟一道屏障」**：它落在当前段里，然后关掉这一段，它之后的写不与它同段。

推导：`write_all_at` 之后 `sync_data()`。刷完成之前，这一段里的写**一个都没被强制**；刷完成之后，**全部**被强制。这正是「段内任意子集持久、然后关段」。

⚠️ **这个模型绑在持久机制上，不绑在名字上。** 换成发真 `REQ_FUA` 之后它就不成立了：真 FUA 不刷缓存，同段前面那些普通写不会因为它而持久，那时该用的是候选丁。**所以「保守策略」这条定案与 D13 已定项 4 的措辞是一对，改一个要连着改另一个**，这笔账进交用户表。
