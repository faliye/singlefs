## 一、问题 1：塌缩打中的是不是最弱读法；T1/T2 合不合法

### 1.1 现查：D8、D11 有没有排除 fold_up 这种读法

```bash
grep -c "塌缩\|树变矮\|再平衡\|重分配" .claude/kb/decisions/08-核心索引结构.md .claude/kb/decisions/11-索引节点要不要留消息缓冲区.md
```

两个文件合计 0 次（本轮现查，与第二轮攻方腿的复核一致）。甲-R4、乙-D 的候选定义（背景材料第三节）只写了读算法与写时的三条/一条规则，没有一句提到分裂、合并、塌缩时缓冲怎么重分配。⇒ **fold_up（把孩子缓冲里的旧消息当新来的并进根缓冲）在文本层面没有被排除，是最弱读法上的一个真实、非稻草人的空白**，第二轮判决 2 的前半段站得住。

### 1.2 更硬的理由：「位置即新旧」是读算法，不是不变量本身

甲-R4、乙-D 的读法字面写的是「一个机械的搜索过程」：自上而下、第一条命中就返回。这条算法**正确**的充要条件是一个没有被写下来的不变量：

> **对同一个 key，任意时刻，浅层持有的消息在真实写入时间上不早于深层持有的同 key 消息。**

这条不变量不是「位置即新旧」的推论，是它的**前提**——没有这条不变量，「第一条命中就是最新」这句话根本不成立，读算法本身就是错的，不是「在某些输入上读到旧值」的问题。fold_up 违反的正是这条不变量：它把一条**更旧**的消息（塌缩前留在孩子缓冲里的）挪到了**更浅**的层（新根缓冲），而没有触碰任何**更新**的消息，于是浅层不再必然新。

这个框架不改变第二轮的判决（塌缩仍然是对最弱读法的一次合法打中），但回答了「T1、T2 算不算合法收严」这问题里更深的一层：**T1、T2 不是在引入一条新设计选择，是在补一句本来就该写、但没写的不变量维持义务**。这解释了两件事：

1. 为什么 T1、T2 零格式代价——它们不改变盘上任何字段，只约束「重组时怎么搬内存里的缓冲内容」；
2. 为什么它们应该被高置信度采纳——不是「这是众多修法里比较好的一种」，是「这是唯一能让『位置即新旧』这句话继续成立的做法」。**任何不满足『重组不改变任何 key 读出来的值』这条一般形式的重组实现都会破坏读算法本身，不只是破坏 fold_up 那一种具体写法。**

### 1.3 T1、T2 是否只许收严：复核三步

沿用 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「臂的定义也在『跑前写死』之列」的三步，本轮独立复核（不采信转述）：

| 记一次输 | 甲-R4 4 步 `direct_put_b, grow, direct_put_b, shrink`、乙-D 6 步 `fe_put_a, flush, fe_put_a, grow, flush, shrink`——两条路径本轮用 Model A 的算子重放，结果与第二轮攻方腿产物一致（同样的最短步数） |

## 二、问题 2：计数器不落盘是不是最弱读法；停留期外推站不站得住；8 字节是不是必要

### 2.1 「全池单调」这几个字，字面不蕴含「计数器要落盘」

候选定义（背景材料第三节）：「乙-G-T：乙字面（跨层看位置、同一层由 seq 定新旧），seq 全池单调；T3：写进前端时取号，计数器随发布落盘」。「单调」是一个**数学性质**（后发的号严格大于先发的号），这条性质单靠内存态就能维持到进程退出为止；「全池」只说明作用域不按树或按节点分段，不说明它要不要扛过掉电。⇒ **按字面，『计数器不落盘』确实是候选原文没有排除的一种实现**，第二轮判决 3 关于「打中最弱读法」这一半站得住，我在本轮没有找到理由推翻它。

但这不等于「全池单调」这四个字本身要求持久化——真正要求持久化的是一条更精确、没有被写下来的性质：

> **任何两条可能同时可达的消息，必须始终可比较；「可能同时可达」这件事不因为中间发生过一次崩溃而改变。**

一条已经进入**已发布**状态的消息（哪怕只是躺在某个盘上节点的缓冲区里，只要那个节点被某个已选中的根引用），在崩溃恢复之后仍然「可达」，仍然可能要和恢复之后新写入的消息比较新旧。这条性质，而不是「单调」本身，才是计数器必须持久化——**或者有等价替代**——的真正原因。

### 2.2 等价替代：按已有的成例重建计数器，而不是信一个字段

D8 已定项 8②（08:476） 定树 ID 水位「住根记录，取根环里全部根记录该字段的 max」；D23 已定项 16（23:695） 定实例代号「取 max(超级块, 根环) + 1」。两者共同的模式是：**遇到『一个单调量要扛过崩溃』的问题，本工程已经两次选择『挂载/切换时按可达范围重新取 max』，而不是『信一个持久化字段的原样恢复值』**——后者一旦那个字段本身的持久化时机与它想守护的写序有一点点缝隙（这正是 T3「计数器随发布落盘」字面在说的东西，一个「什么时候落」没有交代清楚的单点字段），就会重犯 D8 已定项 8②（08:476） 那条正文自己记录过的教训（「同日先定『住超级块取 max + 区段预留』，当日重比三条臂后重开」——超级块单点字段一开始就被否掉过一次）。

Model C（`model_c_rollback_counter.py`）验证了这个等价性：把乙-G-T 的计数器放进**根记录**（随根一起回退，天然复现「max(可达范围)」效果的一个特例）与放进**超级块**（不随根回退）两种落点，构造一次管理员回退（丢弃两个后发布的 checkpoint），检查回退之后新签发的 seq 会不会撞上任何仍然可达的 seq：

```bash
nice -n 19 python3 -B model_c_rollback_counter.py
```

两种落点在本场景下都**没有撞号**（见第五节附产物）：住根记录的那种，计数器随选中的根天然回退到 3，新签发 4、5、6，与 R_old 自己可达的最大 seq 3 不冲突；住超级块的那种，计数器留在 9，新签发 10、11、12，同样不冲突，只是把 4–9 这段区间永久浪费掉——这正是 D8 已定项 8②（08:476） 那句「浪费号、不复用号」已经论证过可以接受的代价，不是新问题。**这一点我要收回第二轮报告没有明确说的一个印象**：我原以为回退场景会撞号，构造之后发现，只要遵守「一次发布整体施加或整体不施加」（D16 已定项 4，16:193）这条既有原则，被抛弃时间线里没有发布成功的写从来不会进入任何被选中根的可达范围，撞号构造不出来——**这是一次没有打中的攻击尝试，如实记下**。

⇒ 真正悬空的不是「回退会不会撞号」，是**T3 没写计数器住哪、没写切换『重做』那一步对已经取过号、还没发布成功的消息是重新取号还是带着旧号走**（D23 已定项 14「实例切换」段落（23:691）只写了「固定点单元全部按新实例重写」，没有点名 write buffer 前端消息）。这是一处纯粹的规格空白，不是已证实的 bug；我尝试构造冲突未遂，如实记「没打中」。

### 2.3 停留期「没有上界」：闭式论证，不是外推

第二轮攻方腿的机理陈述是「一个缓冲区只在攒满时下推，一个节点攒满要『容量 ÷ 进它的速率』次写，停留期由这个速率定」。这句话本身就是一个**公式**：`停留期 ≈ 容量 B ÷ 该缓冲区收到写的长期速率 r`。`r` 是一个工作负载参数（这个子树在全池写流量里占的份额），**没有下界**——只要构造一个足够偏斜或者叶子足够多的负载，`r` 可以被压到任意小，`停留期` 因此可以被推到任意大。这是给定「只在攒满时下推、没有按时间/计数强制下推」这条机制之后，**直接从公式得出**的结论，不需要样本点去归纳；18 个取样点起的作用是**校准**这个公式（确认实现真的按这个公式行为），不是**证明**上界不存在的唯一依据。

Model E（`model_e_dwell_bound.py`）验证公式与第二轮实测吻合：

```bash
nice -n 19 python3 -B model_e_dwell_bound.py
```

容量 B=313（第二轮报告「今天的宽」），32768 叶下闭式给出 10 256 384 次写；第二轮攻方腿在 32768 叶、Zipf 负载、10 百万次写时实测最长停留 8 995 812 次写——同一量级，闭式公式与实测互相印证。⇒ **「没看到与总写次数无关的上界」这句话，站得住，而且比外推更硬：它是给定机制之后的必然结论，不是碰巧 18 个点都没撞到上界**。

### 2.4 8 字节是不是必要

给定 2.3 节的闭式结论，**任何有限宽度的 seq，只要下推策略仍然是纯粹「攒满才推」，都存在一个足够偏斜的负载让它溢出**——8 字节不是把停留期变成有界，是把溢出所需的偏斜程度推到当前工程判断为「不现实」的区间（Model E 的表：即便把 99.99% 的流量导去 32768 叶里的 0.01%，停留期也只有约 1.03×10¹¹ 次写，仍在 2⁶³ 之内很多个数量级）。**8 字节因此是「用宽度买安全边际」这条路上必要的那一步**，不是可选项——不加宽、也不加一个有界下推机制，4 字节在这个机制下不成立，这一点由 2.3 节的闭式公式保证，不依赖任何一次具体的采样。

⇒ 我建议 08:447 那句「4 字节、`T_dirty` 上界挂载时判定」重开时，同时给 8 字节写一条与 D19 已定项 2（密文校验和位宽，19:67）同款的「重开条件」——什么样的现场负载会让 2⁶³ 也不够用，写清楚，不要只留一个「8 字节应该够」的印象分。

## 三、问题 3：写出量口径对丙公不公平；T6 的连带

### 3.1 均匀随机 key、不含读写缓存，对丙是不是不公平

第二轮的写出量测量（U3 表，产物第 389–392 行）口径是「key 均匀随机，只数写出的节点，不含读、不含缓存」，得到丙 / 甲-R4 的排空到叶是乙的 3.4–10.7 倍。要问这个口径对丙公不公平，先问**偏离均匀随机会往哪个方向改变这个倍数**。

反向索引、LRU、记账这三棵 write buffer 前端树的真实负载都不是均匀随机 key：

- 记账树的 key 空间**很小且反复命中**——D5 已定项 4（05:326）给出的统计量数量是个位数到十几个，每个 checkpoint 都要重写（D5 已定项 2「一写一删」，05:287），这是**极端**的时间局部性，远比均匀随机偏斜。
- 反向索引、LRU 的热点由已定的目标负载给出方向：D25（目标负载优先级，25:1）已定「一次 fsync 带 8 叶、落在 1 条共享脊柱上，seq 为主」——共享脊柱意味着**同一批 fsync 反复命中相邻甚至相同的 key**。

乙的缓冲之所以能省写，机制是「多次同 key 更新只需要在缓冲区里替换一次，等真正下推才写一次盘」；负载的时间局部性越高，这个「多次更新合并成一次落盘」的比例越高，**乙省得越多**。丙没有缓冲，每次 flush 都直接落叶，**局部性对丙没有任何补偿**——无论负载多集中，丙每次落叶都要写一遍路径。⇒ **偏离均匀随机、往真实负载的局部性方向走，只会拉大乙对丙的优势，不会缩小**。均匀随机口径下测出的 3.4–10.7 倍，因此**更像是对丙有利的下界，不是夸大的上界**。

真正的不公平不在这个数字本身，在**这个数字单独拿出来评判丙**这件事：它只覆盖 U3 的「写代价」半边，丙的卖点写在「事先的倾向」里——「读的次序最短」。第二轮 U4 已经记录「丙的自证形态最薄……真正的安全性来自『前端树上只有前端一个写者』这句定义，而这句话不是一条读时能验证的性质」，但**没有任何一轮**量过前端树在四条候选下的点查代价——E56（消息缓冲的收益 vs ε）测的点查代价是 ε>0 的**一般**树，不是这三棵**前端**树按四条候选各自的层数。⇒ **U3 单独引用写代价去否定丙、或单独引用它去肯定丙，都是引用不全**；这笔账应该配一条读代价的测量，落进 C161 定案时新分项的欠账里。

### 3.2 T6（旧写者收进前端）的连带：不只是 D8:460 一句话

丙-T6 要求 D8 已定项 8 里「树 ID 不认识、统计量标签认识」的旧写者，把原样搬运的记账行改走前端（不然会撞 G3）。这条要求有一个前提没有被检查过：**D8 已定项 8 的旧写者场景，不依赖 write buffer 前端路由这一版有没有上线就已经成立**——它答的是「一个不认识某棵树种类码的旧写者，遇到那棵树的记账行该怎么办」，这件事在 **day-1**（前端对记账树还没启用，D8 已定项 10）就可能发生。

⇒ 若某个「旧」写者的代码版本**早于**「记账走 write buffer 前端」这条路由决定，它根本不知道前端协议存在——它唯一会的写法就是直接把那一行原样写回记账树（这正是已定项 8 要求它做的事，也是它**唯一物理上做得到**的事）。这不是「它没有遵守 T6」，是**它比 T6 存在得早**。若丙的 G3 被实现成「除了前端 flush 路径，代码里没有第二个函数签名能拿到这三棵树节点缓冲区的写入能力」（round-2 提议的类型层强约束），这条硬约束会把这个**已经格式合法**的兼容写法一并挡在外面，把一个合规的旧写者错判成违规写者。

这笔账不能只记「T6 与 08:460 冲突，改成前端」了事——它牵连到 D15（格式冻结政策）的 compat / incompat 分档：G3 想要的「除了前端没有第二写者」如果被当成一条**格式级**约束去强制（旧写者写了就报错、拒绝挂载或者拒绝该条目），那它其实是在**引入一条新的兼容性收紧**——把「记账走前端」从「运行时实现选择」升级成「不认识就不安全」的语义，理应走一次 compat 位判定（`.claude/rules/fs-design.md`「feature bit 分三档」），而不是只在检查代码里加一个例外分支。⇒ **T6 的完整形态应该是**：G3 的硬约束只覆盖「当前版本写者对这三棵树的写路径」，同时显式承认 D8 已定项 8 的旧写者搬运写法是一条独立、已格式合法、按内容形状可识别（值不变、只换代号、树不认识）的例外，不按「调用了哪个函数」而按「这次写的形状」去判断是不是违规。这条例外该不该单独进 D15 的 compat 分档，是留给 C161 最终定案时要一并回答的问题，不是这一轮能定死的。

## 四、问题 4：08:445 的冲突射程是不是只到记账树

现查 `.claude/kb/decisions/08-核心索引结构.md:445`（已定项 7 正文）：「⚠️ **但这个数还不能定案，三条挡着**：……③ **射程只到记账树**——反向索引与 LRU 的 key 布局仓里一个字都没有，模型对它们报『不适用』，不许外推。」——这句 ⚠️ 与「不许再放一份 txg」是同一小节的正文，本轮现查原样存在。

⇒ **答案是：射程确实只到记账树，不能把这句「不许再放一份 txg」直接套到反向索引 / LRU 头上**——它们的 key 布局全仓没定，08:445 那句话的前件（「同一个 key 的待去重条目必然同属一个发布窗口」）建立在记账 key 的「代」段之上，反向索引 / LRU 的 key 没有这一段，前件本身在那两棵树上是否成立都没有答案，遑论它的结论。

但**「不到」不等于「反向索引 / LRU 不需要一份可比对的时间线索」**——C52（`.claude/kb/checks-owed.md:62`）的前置条件写的是「需要格式层先给一个可比对的时间线索（代号 / 已应用水位线）」，这句话不分树；乙-D、甲-R4 在这两棵树上一样会遇到「同 key 多层并存，检测器只有第一版 seq 可用」的问题（第二轮陈旧检出那一节的机制对任何采用位置定新旧、盘上留多份同 key 消息的候选都成立，不特定于记账树的 key 形态）。⇒ 这一格的正确记法是：**反向索引 / LRU 上的陈旧检出线索是一个独立的、目前全仓没有答案的未定项**，不能说「08:445 挡着」（射程不到），也不能说「没问题」（C52 前置条件仍然成立）——这笔账应该单独立一条，不要挂在 08:445 底下，落点建议记进 C161 定案时新分项的欠账，写明「反向索引 / LRU 的 key 布局定案时，必须同时回答 C52 需要的时间线索从哪来」。

## 五、问题 5：四个新形状的正面论证

### 5.1 删除与墓碑（Model A）

**读写序列的形状**：一个 key 先在前端收到 `put`，flush 之后落进某一层（按候选路由规则）；随后同一个 key 收到 `del`（whiteout；D8 已定项 5「whiteout 删除——接受，但批量删除必须走 intent log」，08:73；单个 whiteout 不落进批量意图分支，是「接受」的那个基线机制，D8 已定项 5 正文 08:276「whiteout 只在节点重写合并 bset 时清除，不许有别的清除路径」——它没有另立一条写入路径）；`del` 走**与 put 完全相同的路径**——前端 in-memory 去重、flush/push 的清路径与落叶规则、重组（grow / shrink / T1 的塌缩先下推、T2 的 rebalance 随 key 搬）——**不需要为它写任何专门的分支**。

**正面论证**：Model A 把 round-2 已经验证过的 T1（塌缩先推后合）、T2（rebalance 携带缓冲）两条修法，直接套用到含 `put`/`del` 混合消息的历史上，四条候选各自穷举到深度 9：

```bash
time nice -n 19 python3 -B model_a_tombstone.py 9
```

`jia_R4: states_explored=1047683 violations=0`；`yi_D: states_explored=59395 violations=0`；`yi_G: states_explored=156859 violations=0`；`bing: states_explored=9093 violations=0`（本轮实测，53 秒）。⇒ **0 违规，四候选一致**，比第二轮只测 put 消息的历史更强一层：证明 T1/T2 不需要对删除消息做任何特殊处理，「消息」这个抽象本身（不分 put/del）已经是重组不变量该管的最小单位。

**会红的检查**：`删除的重组不变量`——造一份镜像，某 key 的权威值是「已删除」，其权威消息此刻停在某个即将参与重组（grow/shrink/rebalance）的缓冲层里；重组前后读该 key，两次都必须报「已删除」。

**判别力自证**：`MUTATE_DROP_DEL=1`——让 flush/push 写路径遇到 `del` 消息时直接丢弃（模拟「删除没有走跟 put 一样的路径」这一类实现错误）：

```bash
MUTATE_DROP_DEL=1 nice -n 19 python3 -B model_a_tombstone.py 6
```

`jia_R4: states_explored=14181 violations=7228`（最短 1 步 `direct_del_a` 就红）；`yi_D`/`yi_G`/`bing` 同样在最短 1–2 步内变红（本轮实测）。⇒ 检查有判别力：四候选在这个突变下**全部立即由绿转红**。

**要改的 kb 句子**：无需改任何已定分项——这一格没有暴露任何新的条款冲突，只需要 C161 最终定案的新分项显式写一句「删除消息（whiteout）与更新消息共用同一套位置 / seq 比较与重组搬迁规则，不单独处理」，把这条「不需要特殊处理」的结论钉下来，防止以后有人顺手给删除加一条「优化」分支（正是第二轮 N4 那类突变的另一种来源）。

### 5.2 单调统计量的点删（Model B）——这一格暴露了一个此前没建模、四候选都会中的真实 bug

D5:308（已定项 3 字段表第 2 行）「非单调统计量『后者胜』（后者由 seq 定），单调统计量取最大值」描述的是一条**与到达顺序无关的折叠**：`acc = max(acc, v)`，任意顺序应用结果相同——这正是它在崩溃重发场景下被选中的理由（D8 已定项 6 上下文：「取最大值同样幂等、交换、结合……是单调量选它而不是『后者胜』的理由」）。**这句话没有说清一件事：点删（K 代点删的墓碑，D5:284-287）在这个折叠里算什么。**

墓碑不是一个「值」，没有数值可以拿去跟别的值比大小。若实现按字面把墓碑编码成某个数值（哪怕是最保守的 0）塞进同一个 `max()` 折叠，任何非负的真实值都会赢过它——**点删被折叠吞掉，那一代记账行永远不会真的消失**，与 D5:284-287「要丢的那一代算得出来……不用找⇒是点删不是扫描」这句设计初衷正面矛盾。

**读写序列**：checkpoint g−K 内，同一个 key（某统计量, 某维度, g−K）收到多条竞争的 `put`（模拟同 checkpoint 内多写者竞争，到达顺序与数值大小故意不一致，这正是 D5 选「取最大值」而不是「后者胜」要防的那类竞态）；K 个 checkpoint 之后，同一个 key 收到唯一一条 `del`（点删墓碑）。四条候选、两种合并策略：

```bash
nice -n 19 python3 -B model_b_monotonic_delete.py
```

**朴素策略**（把 `del` 编码成数值 0 折进同一个 `max()`）：16 行测试（4 候选 × 4 条对抗序列）**全部**把点删丢掉（`naive_policy: 16 rows out of 16 silently lose the point-delete`）——这个结论跟候选是甲-R4-T、乙-D-T、乙-G-T 还是丙-T6 无关，因为它是**读/合并逻辑的问题，不是重组或位置逻辑的问题**，四条候选共用同一个折叠规则。

**T7（我在本轮提出的修法）**：读一个 key 时先按候选自己的「最新」判据（位置 / 到达序，或 yi_G 的 seq）挑出**最新的那一条消息**；若它是 `del`，直接判「死」，不参与任何数值比较；若它是 `put`，只在**它自己那一批仍处于竞争状态的 `put` 消息**之间做 `max()` 折叠。⇒ 16 行**全部**正确判「死」（`fixed_policy(T7,enabled): 0 rows lose the point-delete`）。**T7 不需要任何新格式字段**——它只是把「墓碑先判、活着的值才 max」这句话在读/合并代码里显式写出来，墓碑本身仍然是 D8 已定项 5 那条普通 whiteout 写法，Model A 已经证明它走跟 put 完全一样的位置 / seq 机制。

**判别力自证**：`MUTATE_OFF_FIX=1`（关掉 T7、退回朴素折叠）：

```bash
MUTATE_OFF_FIX=1 nice -n 19 python3 -B model_b_monotonic_delete.py
```

`fixed_policy(T7,DISABLED): 16 rows lose the point-delete`——由绿转红，检查有判别力。

**要改的 kb 句子**：`.claude/kb/decisions/05-快照-空间记账机制.md:308`（已定项 3 字段表第 2 行）要在「单调统计量取最大值」后面补一句：「点删（whiteout）不参与这个折叠——读取一个 key 时先判最新的一条是不是删除，是则判死，否则只在存活的 put 消息之间取最大值」。这不是撤销原句，是把原句里一直没写、四候选都会踩的隐含前提显式化——与第一节 T1/T2 是同一种「补上本该写但没写的不变量」的性质。这条修补建议记作 **T7**，与 T1–T6 并列，各自要改的候选一致（甲-R4-T、乙-D-T、乙-G-T、丙-T6 全部需要）。

### 5.3 管理员回退与实例切换（Model C）——尝试构造撞号未遂，残留纯规格空白

**读写序列**：正常运行发出三个 checkpoint g0（seq 1–3）、g1（seq 4–7）、g2（seq 8–9），各自发布一个根；管理员回退到 R_old = g0 的根，按 D23 已定项 14（23:691）「全部记账统计量的现行值从 R_old 那棵账重新载入」；取新实例，恢复正常写入，签发新的 seq。

**正面论证**：把乙-G-T 的计数器放进**根记录**（模拟 D8 已定项 8②（08:476） 树 ID 水位那种「随根回退」的落点），Model C 检查回退之后新签发的 seq 会不会与 R_old 自己可达范围内的任何 seq 相撞：

```bash
nice -n 19 python3 -B model_c_rollback_counter.py
```

`root placement collision: False`——计数器随选中的根回退到 3，新签发 4、5、6，与 R_old 树里可达的最大 seq 3 不冲突。**这是一次没有打中的构造尝试，如实记下**：在「一次发布整体施加或整体不施加」（D16 已定项 4，16:193）与「被抛弃时间线的单元不许复用也不许抹头，但也不会被任何选中的根引用」（C314，`.claude/kb/checks-owed.md:292`）这两条既有机制下，我找不到让回退产生 seq 碰撞的路径——被抛弃时间线里没有真正发布成功的 write buffer 消息，从来不会进入任何被选中根的可达范围，这类消息因此没有机会与「回退之后新签发的号」被放进同一次比较。

**残留的真实空白**（与既有成例连带，但今天没有答案）：T3「计数器随发布落盘」没有说清楚**落在哪**（根记录，像树 ID 水位；还是超级块，像本轮我特意构造的对照臂）；也没有说清楚 D23 已定项 14「实例切换」段落（23:691）里「号 > W 的……固定点单元全部按新实例重写」这一步，对**已经取过号、还没发布成功**的 write buffer 消息，是重新取号（新实例重新走一遍取号流程）还是带着旧号原样重写（同一批逻辑写、只换物理副本）——这两种读法今天都没有被排除，也都没有被检验过。

**会红的检查**：`计数器单调不倒退`——挂载 / 实例切换完成后，读取的计数器值必须 **≥** 从被选中根可达的整棵记账 / 反向索引 / LRU 树里出现过的任何一个 seq；不满足就是这个候选的一个真实 bug（本轮我没能构造出触发它的具体序列，但检查本身独立于这一点成立）。

**判别力自证**：Model C 里把落点从 `root` 换成 `superblock`（在场景不同、参数更极端时——例如回退发生在同一次实例切换里、超级块字段的更新时机与根槽 FUA 之间有缝——是否会让检查转红，本轮没有找到能触发的具体序列，留作欠账，不敢报「已证明恒安全」）。

**要改的 kb 句子**：D8 已定项 7（08:78 附近，本轮建议落点）补一句：「乙-G（`08:78`「第一版记账走不走 write buffer 前端」的将来值分支若采纳全池单调计数器）的计数器落点与恢复规则，照抄 D8 已定项 8②（08:476）（树 ID 水位）与 D23 已定项 16（23:695）（实例代号）的『挂载 / 切换时按可达范围重取，不信单点持久字段』模式；D23 已定项 14（23:691）『实例切换』段落要点名 write buffer 前端消息在『重做』时是否重新取号。」这两句今天都不存在，是这一格暴露出的、独立于四条候选选哪一条都要回答的欠账，落点建议记进 C161 新分项。

### 5.4 索引重建前的排空（Model D）——D11 已定项 5「各层」够不够宽

D11 已定项 5（`.claude/kb/decisions/11-索引节点要不要留消息缓冲区.md:231-235` 附近）：「任何一次索引重建（改 ε、改节点大小、损坏恢复）之前，各层缓冲必须先排空，且这一步由重建入口强制执行，不靠调用者自觉。」这句话写于 2026-08-31，**早于** C161 本身在 2026-09-06 才被发现的「write buffer 前端与节点消息缓冲区两级并存」这件事——「各层」字面上是复数，但 D11 这份文件通篇讨论的对象是**节点内部**的消息缓冲区（D11 标题本身），它没有、也不可能在写下「各层」这两个字的时候把 D8 的 write buffer 前端（一个完全不同文件定义的、纯内存的结构）算进去。

**读写序列**：某个 key 唯一的权威副本目前还停在**前端**（尚未 flush），重建入口被调用（改 ε、损坏恢复等场景）。

**正面论证 / 会红的检查**：Model D 直接对比两种「重建入口强制排空」的实现范围：

```bash
nice -n 19 python3 -B model_d_rebuild_drain.py
```

`drain_scope=node_only`（只排空节点缓冲——D11 已定项 5 字面唯一明确管辖的对象）：重建读到 `k=None`，真值是 `('put', 42)` —— **STALE/MISSING**。`drain_scope=both`（同时排空前端与节点缓冲）：重建读到正确值——**correct**。`bug_demonstrated=True fix_confirmed=True`。

**判别力自证**：Model D 的 `drain_scope` 参数本身就是判别力自证——把「排空」范围从 `both` 改回 `node_only`（模拟一个只读过 D11、没读过 D8 或没意识到两级并存的实现），同一份镜像由 `correct` 转 `STALE/MISSING`。
