BACKGROUND. Singlefs stores a rollback witness table inside a fixed-size system-configuration slot; it writes journal records of a fixed size; and it stores two of its internal indexes, called the accounting tree and the central-mapping tree, as trees built out of a fixed-size on-disk node format. Both of these two trees are being given the ability to grow additional internal levels above their leaves as the number of entries in them grows, the same way two other trees in this codebase already have been. The facts below state the already-decided sizes and formulas needed to compute node capacities for these two trees, the already-decided layout of the rollback witness table, the already-decided layout of one journal record, and one already-decided rule for how many rows the accounting tree holds for a pool with a given number of storage devices.

FACT 1. In this filesystem, an on-disk structure called a format-2 index node is always exactly 16384 bytes in total size. This is true regardless of which of several different trees the node belongs to, and regardless of whether the node is a leaf node or an internal node within its tree.

FACT 2. Two of the trees in this filesystem are called the accounting tree and the central-mapping tree. For each of these two trees, one format-2 node's total header size in bytes is a single already-decided constant that is the same value whether that node is a leaf node or an internal node: the accounting tree's header size is 159 bytes; the central-mapping tree's header size is 169 bytes. These two header sizes come from a formula that depends only on that tree's key width in bytes: header size equals 86 plus 2 times the key width in bytes plus 29. The accounting tree's key width is 22 bytes, giving 86 plus 2 times 22 plus 29 equals 159; the central-mapping tree's key width is 27 bytes, giving 86 plus 2 times 27 plus 29 equals 169. Within one single tree, every node at every level uses this same header size. The formula is given only so you can see where the two header sizes come from; both header sizes are themselves already-decided constants in this codebase, not something you need to derive yourself.

FACT 3. The already-decided leaf-entry width, meaning the fixed size in bytes of one data record stored in one leaf node's entry area, for each of these same two trees: the accounting tree's leaf entry is 34 bytes, made up of a 22-byte key plus an 8-byte value plus a 4-byte sequence number; the central-mapping tree's leaf entry is 55 bytes, made up of a 27-byte key plus two 14-byte location entries.

FACT 4. Both the accounting tree and the central-mapping tree already have a decided internal-node entry format, decided as part of giving these trees the ability to grow additional internal levels above their leaves. Each internal-node entry consists of exactly one separator key, using that tree's own key width from FACT 2, plus exactly one 86-byte pointer to one child node, and that one entry corresponds to exactly one child node; there is no additional child pointer beyond the number of entries in the node, unlike some other tree designs where an internal node with n keys has n plus 1 children. The accounting tree's internal-node entry is 22 plus 86 equals 108 bytes; the central-mapping tree's internal-node entry is 27 plus 86 equals 113 bytes.

FACT 5. For any one format-2 node of one of these two trees, define that node's entry capacity as the largest whole number of entries that fit into the space left over inside one 16384-byte node, from FACT 1, after subtracting that tree's header size, from FACT 2. The formula is: entry capacity equals the floor of ((16384 minus header size) divided by entry width), where floor means rounding down to the nearest whole number and discarding any leftover fractional entry that would not fully fit. For a leaf node, use that tree's leaf-entry width from FACT 3 as the entry width. For an internal node, use that tree's internal-entry width from FACT 4 as the entry width. The header size from FACT 2 is the same number in both cases, because FACT 2 states that header size does not depend on whether the node is a leaf node or an internal node. Under the one-entry-per-child correspondence stated in FACT 4, an internal node's entry capacity also equals the maximum number of child nodes that one internal node can point to.

FACT 6. Separately from tree node sizes, this filesystem also has an already-decided rule for how many leaf entries, meaning rows, the accounting tree holds right after a pool's very first publish, as a function of the number of storage devices D in that pool: the accounting tree holds exactly 3 plus 6 times D rows, made up of 3 pool-level rows plus 6 device-level rows for each one of the D devices. For a pool with D equals 2 devices, this is 3 plus 6 times 2 equals 15 rows. This exact case, a pool with 2 devices holding 15 rows in its accounting tree right after its first publish, is itself an already-decided, already-implemented fact in this codebase, not something you need to derive.

FACT 7. For the accounting tree, define its leaf capacity as the entry capacity from FACT 5 computed for one of its leaf nodes, and define its internal fanout as the entry capacity from FACT 5 computed for one of its internal nodes. For a given number of leaf entries N that the accounting tree needs to hold, define height(N) as the smallest whole number h, with h at least 1, such that a tree of height h can hold at least N leaf entries in total. Height 1 means a single node that is both the root and the only leaf, holding up to leaf capacity entries, with no internal levels at all. Height h for any h of 2 or more means one root, h minus 2 further levels of internal nodes below the root (zero further such levels when h equals 2), and one level of leaf nodes at the bottom; the maximum total number of leaf entries a tree of height h can hold equals leaf capacity multiplied by internal fanout raised to the power (h minus 1). Formally, height(N) is the smallest h for which leaf capacity times internal fanout to the power (h minus 1) is greater than or equal to N. FACT 8. Separately from tree nodes, this filesystem also stores a fixed-size rollback witness table inside a system-configuration slot. The table starts with a 1-byte count field. FACT 9. Separately again, this filesystem writes fixed-size journal records. One journal record is always exactly 4096 bytes in total size. The first 311 bytes of that 4096-byte record are the record's header.
