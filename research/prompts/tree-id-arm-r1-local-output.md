3. Arm A's advantage is not complete. If a mount uses up its block of K integers and attempts to reserve a second block but crashes during the superblock write, the superblock retains the original reservation. On restart, the mount hands out integers from the original block again, reusing previously allocated integers. For example, if the first block was 1-10 and all were used, a crash during writing the new block (11-20) causes the next mount to reuse 1-10.  

4. Rank: C > A > B. The deciding property is whether the counter value is derived from durable published data. Arm C uses the ring of published root records, ensuring published trees' integers are safe. Arm A relies on superblock writes that may not be updated for each allocation, risking reuse of published integers. Arm B resets the counter on rollback, directly causing reuse. For the ranking to flip, Arm A would need to update the superblock immediately after each allocation (making it durable), and Arm C would need to store the counter in a non-durable location before publishing.  

5. Arm C requires reading all root records in the ring to determine the current counter on every tree creation, which could introduce latency if the ring is large. However, the ring has only three slots, making this negligible in practice. The stronger objection is that Arm C's counter depends on the ring's integrity; if the ring is corrupted (e.g., due to disk errors), the counter could be incorrect, leading to reuse. This is a general issue but not explicitly covered in prior questions.
