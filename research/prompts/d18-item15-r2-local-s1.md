1. For A-prime: At checkpoint 5, node A [0-100] is created as a level 0 node. At checkpoint 10, parent node X (level 1) with range [0-100] is created with children A1 [0-50] and A2 [50-100]. When rebuilding X at b_X=10, the rule includes A (birth 5 <=10) because its range [0-100] intersects X's range. A covers A1 and A2, so A1 and A2 are excluded. The rule picks A as the only child, but X's true children at b_X=10 are A1 and A2.

2. For B-prime: A merge of node numbers 5 and 6 into 7 occurs. Retirement records for 5 and 6 are not written to disk before a crash. When rebuilding X at b_X after the merge, the system sees no retirement records for 5 and 6, so it includes their latest versions with birth <= b_X. However, they should have been retired. X's children are incorrectly identified as 5 and 6 instead of 7.

3. For all: A node X is written during an unpublished checkpoint. The instance table only includes published versions, so X is not considered. However, if X is written and the checkpoint is published but the root update fails, X is in the instance table but no root references it. When rebuilding, the system picks X as a child for a tree it does not belong to, causing incorrect data.

4. For B5: If a node is written twice in one checkpoint, two versions exist with identical lineage, level, identity, birth, and instance but different payloads. During rebuilding, the system cannot determine which payload is correct, leading to inconsistent data. For example, a node might have payload A in one version and payload B in another, causing checksum mismatches or incorrect subtree reconstruction.

5. For C: B6 fails when a child is relocated after b_X and the parent's pointer points to a reused location. For example, parent X at txg 10 points to child Y at location L1. At txg 20, Y is relocated to L2 and L1 is reused for another node Z. When rebuilding X at b_X=10, the system reads Z from L1, which does not match X's stored checksum. This happens whenever locations are reused before rebuilding. Narrow narrowing is possible by storing birth time in the pointer to validate against the read node's birth time.

6. For B4 clone case: An origin tree has node A created at txg 5. The clone is forked at txg F=7, but F is not stored on disk. At txg 8, the origin updates A to a new version. When rebuilding the clone, the system sees A at birth 5 and a new version at birth 8. Without F, it cannot determine if F was between 5 and 8. If F=6, only birth 5 is included; if F=9, both are included. All options cannot decide the correct child set.
