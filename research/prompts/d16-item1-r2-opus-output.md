副本（保留池 13）S = 16：c_empty = 1 时每窗口 8.79 次强制发布；**c_empty = 2 时 331296 / 7056 = 46.95 次**，c = 3..5 时 331680 / 7056 = 47.0 次，恰是 N − 1 = 47，而 E135 的推空循环上限是 N + 1 次（`e135_rollback_floor.rs:542`）。
⇒ 只要空发布开销超过 1 块，S = 16 的臂 A 在近满盘上**每个用户窗口都要把整个环推一遍**；按 D16（发布语义） 已定项 7 每次发布三个序点，一次 8 块的写带约 141 个序点。强制发布数随 S 线性涨，是结构性的，不是 c_empty = 5 那一格的偶然。
⚠️ 判据 2-3 的判红条件只写了「卡死」，所以按字面臂 A 不输这一格；**这是判据漏写了一种代价**（见第三节 M6）。

### H9　「可退代数」量的是根数，不是可退到的不同状态数；按后者，近满盘上臂 A 的承诺与臂 D 差不多，甚至更差【数我核过，折算是我推的】

空发布不改任何用户可见状态；退到一个空发布的根，与退到它之前那个非空根是同一个状态。E135 的可退代数（`avg_candidates_x100`）把推空产生的空根一起数了。
按「候选数 × 非空窗口数 / 总发布数」折成**可退到的非空窗口数**（均值近似）：

| 格 | 候选均值 | 非空窗口 / 总发布（产物字段 `checks`） | 可退到几个不同的用户状态 |
|---|---|---|---|
| S = 16，c = 1，A | 48 | 7056 / 69072 | ≈ 4.90 |
| S = 16，c = 1，D | 8.00 | 7056 / 12720 | ≈ 4.44 |
| S = 16，c = 5，A | 48 | 7056 / 338736 | ≈ 1.00 |
| S = 4，c = 1，A | 12 | 8784 / 14208 | ≈ 7.42 |
| S = 4，c = 1，D | 8.01 | 8784 / 15792 | ≈ 4.46 |

⇒ 材料倾向第 ③ 条与 E135 的「臂 A 可退代数恒 48、臂 D 付可退代数」（材料第 1270-1271 行）在 S = 16 上说反了大半：**近满盘上臂 A 的推空把环转得比臂 D 的抬 F 还快**，事故前的状态照样被推出环。S = 4 时臂 A 确实多一些。

### H10　用户承诺那一格：三条臂在「真正要回退的时刻」都守不住，而 D23（journal 的角色与格式） 已定项 14 的那半句按字面三条臂都没违反【我推的，引文我核过】

- D23（journal 的角色与格式） 已定项 14 的「回退深度 ≤ 根环深度」（`23-journal的角色与格式.md:681` 与 `:1179`）是**上界**，臂 C（≤ K）与臂 D（≤ 环里 txg ≥ F 的根数）按字面都满足。承诺实际住在另一句：「候选集 = 根环里按实例表判仍然有效的根」。**臂 C 与臂 D 改的都是这一句**（C 改成最近 K 代，D 加「∧ txg ≥ F_恢复」），臂 A 一个字不改。
- 臂 D 下，管理员**说得清**此刻能退几代（数一数 txg ≥ F_恢复 的有效根即可，可以暴露出来），所以不是「说不清」。真正的问题是：**F 由盘紧抬起，而盘紧可以由任何一个非特权写者造成**；F 持久且只增，一次盘紧之后，事故发生前的那些根永久出局。
  「有进程失控把盘写满、事后想退回事故前」正是管理员回退最可能被用上的场景，而臂 D 恰在这个场景里把它删掉。
- 但臂 A 同样守不住（H9）：近满盘上推空把环转过去，事故前的根同样被挤出环，只是换了一种方式。再加上 C215 已记的「环转得快是因为负载在写」（材料第 1439 行第 ② 条），**在任何一条臂下，这个承诺在盘紧与高负载时都接近空的**。交用户时这一格该写成「三条臂都守不住，差别只在失败怎么表现」，不该写成「臂 A 守住、臂 D 付代价」。

### H11　journal 重放窗口：没打出分臂的结果，记下【我推的】

- **对臂 D 的正推**：恢复所选根 t 之后重放 `(实例, txg) > t` 的记录，记录点名的单元写于 u > t；它们被复用要求 释放代 ≤ 生效界 ≤ F_生效 ≤ t < u ≤ 释放代，矛盾。⇒ **只要所选根 ≥ F_生效**，重放窗口不会读到被复用的块。H2 的 TWOFAIL 恰恰是所选根 < F 的情形，所以这条正推的前提在复合故障下会破。
- **各臂共有的一个洞**：若施加一条记录要重新生成祖先（C284（施加一条记录在指针层上做什么没有定义）），重放期间要分配；分配器状态从所选根载入，而记录 q 点名的单元所在的块在所选根视角里可能是空闲的，重放施加 q 之前的某条记录时就可能把它分出去 ⇒ q 的点名验证失败、前缀被截断、已返回的 fsync 丢失。这与窗口取哪条臂无关（臂 A 的界同样放出比最旧根更旧的块），**不分臂，记下**，归 C284。

### H12　实例切换：E135 的写失败世界不是实例切换，但 H1 在实例切换语义下照样成立【我推的】

E135 的根槽写失败只推进 txg、不换实例、不写行（`e135_rollback_floor.rs:482-487`）。按 D23（journal 的角色与格式） 已定项 14 索引行，瞬时写失败走实例切换：写行（旧实例，最后发布的 txg，W），重发在飞 checkpoint。
代入 H1：行是（1, c, W），区域 1 里那些旧根的 txg 都 ≤ c，仍然有效；重发的 c + 2 属新实例。F_恢复 只看幸存根所带的 F，结论不变。
若失败那一写其实落了盘（设备报错而数据写进去了），那个根带着新 F、实例表判它无效，但 F_恢复 取「全部自证合法」的根，它会把 F 救回来——**H1 需要写失败的槽不带新 F**，这与 E135 自己的世界定义「槽里留着旧根」以及 C282（环里最旧根没有定义）「写失败的槽按旧内容算」同一口径。

## 四、没做的与做不到的

- H1、H2、H6、H7、H8 都在 E135 的计数模型里：不建字节、不建 journal 记录、不建实例切换（H12 是推的）。它们能证明的是「按 E135 自己的口径，这些操作序列会让它判红」，不证明真设备上的发生率。H1 / H2 要的复合故障（盘 1 一次瞬时写失败，随后若干次发布之内盘 0 整块丢失）窗口窄，发生率本仓没有数。
- H6 的「补上元数据那一项就不卡」只在 `near_full` 一个世界、一种删建负载下扫过，不是证明。
- H9 的折算是均值近似，没有逐次回退去数不同状态。
- 副本只跑了一次；它是确定性模型，多跑几次给不出更多信息，证据强度来自对照格（无写失败 0、臂 A 0、计数口径挡住一次写失败）。
