## 1. 最强形态

### 1.1 容器身份：必须是新注册的单元类型码，不能是隐式 flag

用户原话"用一个标记来标记"——这个字面形态**被一条已定条款直接挡死**：

> `decisions/18-块里携带什么信息.md:435`："偏移 6 = 单元类型标签（已定项 11 登记表的码），偏移 7 = 8 个 flag 位、**第一版恒 0，非 0 一律拒收**（前向兼容政策）"

`decisions/18-块里携带什么信息.md:596-598` 又给了不许绕开这条闸的理由："**值域只有一处登记位**——D18 已定项 11 的这张登记表……**类的名字与码一律取自这张表**"。所以"声明长度=0 + flags 位打开"这个隐式编码，不只是"不够优雅"，而是会被**现有读者原样拒收**（非 0 flag 一律拒），也**不会被未来的兼容读者正确识别**（不是走登记表的码）——两头都错。

最强形态必须改走登记表：`decisions/18-块里携带什么信息.md:616`："| 4–15 | 保留给将来的内容类 | ... | 未登记 ⇒ 拒收；新增一类占一个 incompat 位（D15 判定表）|"。

⇒ **注册一个新的顶层单元类型码**（下文记作码 5，具体取哪个数字是留给用户定案的实现细节，不影响论证）："小数据容器"，与码 3（打包记录单元）平级，都是 `decisions/18-块里携带什么信息.md:598` 登记表的一行，但**类别标为数据类而非元数据类**（码 3 那行明确标"元数据类"，见 `decisions/18-块里携带什么信息.md:644`附近的表格第 3 行）——理由见 1.2。

**这一步不改动任何已定条款**：D18 已定项 11 本来就为这种情况预留了 4–15 号位，"新增一类占一个 incompat 位"是它自己写好的机制，不是绕开它。

### 1.2 容器结构：容器身份段 + 每槽自证身份数组，不是定长记录表

码 3 能"按记录数 × 记录宽定宽切分"（`decisions/18-块里携带什么信息.md:666`："**一容器一种定宽记录**，类型与长度在头一份就够"），前提是记录定长（inode 记录固定 140 字节）。小文件的数据天然变长——这是它与码 3 的第一处结构性差异，最强形态必须正面处理：

- **容器身份段**（仿码 3 的 61 字节段，`decisions/18-块里携带什么信息.md:644`）：出生树 ID、容器号、容器出生代、写序——回答"我是哪个容器"。
- **槽目录**（新结构，码 3 没有）：每槽一条 (对象 ID 8 + 对象出生代 8 + 槽内偏移 2 + 槽声明长度 2) ≈ 20 字节，回答"这个容器里有哪些对象、各自在哪"。这不是可选项——没有它就不满足 `decisions/01-数据可移动性-反向索引.md:27`（已定项 1）"单元数据自包含"的判据：**每一槽都必须能不靠别的槽自证"我属于谁"**，而变长布局下"我属于谁"必然需要一条独立的目录项（定长记录能把身份编码进固定偏移，变长记录不能）。
- 槽目录本身的容量是**新的账**：它挤占的字节不装用户数据，见第 4 节。

**这一步不违反 `decisions/01-数据可移动性-反向索引.md:85`（已定项 5）"唯一说的是链唯一……每一个新的数据单元都起一条唯一的链"**——因为这句话的主语按登记表是**码 1（数据单元）专属**，不是对"单元"这个概念的泛称约束（见第 0 节的核验）。D18 登记表本身已经证明"每一类单元有自己的身份段定义"这件事是允许的：码 1 的类身份段是五元组单链，码 2 的是"树 ID+层级+key 区间"，码 3 的是"出生树+类型+容器号+出生代"——三类互不相同。码 5 定义自己的"容器身份段+槽目录"是同一种操作的第四例，不是破例。

### 1.3 解引用：中央映射的一个新值变体 + 一个新的容器索引（正是 C103 的姊妹结构）

`decisions/19-块指针的结构与宽度预算.md:109`（已定项 5）："中央映射……是**解引用与释放判定的唯一入口**。搬迁只改这里一条条目，『谁引用我』根本不用知道"。中央映射今天的 value 编码只有一种：`decisions/19-块指针的结构与宽度预算.md:108`"位置条目（14 字节）……降为提示"。

要把一个小文件的数据接到码 5 容器的某个槽，中央映射的 value 需要一个**新的判别变体**："打包提示"=（容器身份 26 字节，仿码 3 的四段引用格式 + 槽序号 2 字节），代替原来的（设备 4+偏移 6+校验和 4）。

⚠️ **这是对 D19 已定项 5 的扩展，不是推翻，但必须显式记进 decisions.md，不能悄悄夹带**——按 `.claude/singlefs-ai-sop/rules/session-wrapup.md` 第 3 条"决策有没有变动"，这属于"给一条已定条款的 value 编码新增一个此前没有的分支"，即使不改变现有分支的字节，也要走一次决策记录。

但**容器本身的物理位置由谁持有**？中央映射的"打包提示"只给到"容器身份"，不给物理落点——物理落点必须再有一层持有者，这一层**目前全仓不存在，且正是 C103 已经卡住的那个洞**：

> `checks-owed.md:110`（C103）："D18 已定项 11 要求打包记录单元由一棵容器索引指向：它是打包单元物理指针（与 MAC）的唯一持有者……这棵树住哪、key 编码……全仓无落点。"

码 5 需要的"小数据容器索引"在结构上与 C103 要的容器索引是**同一类问题的第二个实例**（码 3 一个，码 5 一个），而 C103 连码 3 这个更简单的（定长记录）版本都没解决——`checks-owed.md:110` 逐字记着 2026-09-06 曾试图收口、"三腿判定不了案"。

⇒ **最强形态在这里被一个已有的、尚未解决的欠账正面挡住**：不是"数据侧要新开一笔账"，是"数据侧的解引用机制从设计的第一天就依赖一个本项目自己承认还没解出来的东西"。

### 1.4 生死判定与释放：不能沿用 D5 的 O(1) 证明，必须退到后台整理

`decisions/20-承重面单元的原子性与自包含.md:352-353`（引 D5 的话）："D5 的 O(1) 证明建立在『生死判定只用 `ptr.birth` 与 `head.prev_snap_txg`，**不查记账树**』上"。这个证明成立的前提是**一个单元只有一个所有者**，生死是它自己的 birth 与当前快照可见性的一个比较。

码 5 容器天然是**多租户**：一个容器里 N 个槽属于 N 个不同的对象，各自独立创建、独立删除。容器"能不能整体回收"不再是"birth 与 prev_snap_txg 的一次比较"，而是"**所有 N 个槽是不是都已经死了**"——这是一个跨槽的归约，不是单点判定。

⇒ 这一步**不能走 fs-design.md 记账纪律第一格**（运行时决策路径），必须退到第三格——`.claude/rules/fs-design.md`（`CLAUDE.md` 引用原文）："**后台、可续做、非决策路径**（销毁快照、整理、scrub）| **无戒律**"。具体落法：单个槽的删除只标记该槽死亡（一次原子写，容器整体 COW 重写一次，与 D4 已定项 3 的 RMW 模型一致，见 1.6）；**容器整体回收**（所有槽都死）延后给 D26 的后台整理去扫描发现——`decisions/26-后台整理与放置回收.md:50`（已定项 1）已经是"三水位起跑"的通用扫描框架，码 5 只是给它加一个新的低填充率信号源，不需要新机制，但需要**新的判据参数**（多少填充率才值得整理码 5 容器），这是新账。

### 1.5 容器搬迁与整理：可以直接复用 D26 的既有口径

`decisions/26-后台整理与放置回收.md:40`："搬迁单位是『整个对象重落一组』，不是单条条带 | D2 已定项 8 的口径，可直接复用"。码 5 容器的搬迁单位就是"整个容器"，与该口径**天然吻合**——搬完之后只需要改 1.3 里那个"小数据容器索引"的一条记录，其余对象的中央映射行不用动（因为它们存的是"容器身份+槽号"，容器身份不随搬迁改变）。**这一步不改动 D26 的任何已定条款。**

### 1.6 拆分与溢出：用户原话的"向后查询"必须整段替换，不能修补

用户原话："因为末尾的剩余的小数据 slots，我们向后查询，如果后面单元是小数据，那么这个单元就存到后面单元的 slots 头部"。

这一步**不是"效率差"，是"不安全"**，必须整段废弃，不是修一下能用：

1. **物理相邻不携带任何逻辑关系**。`decisions/02-RAID条带策略.md:39`（已定项 1）："**逐次可变**——格式侧物理位置逐个列出……不引 chunk 映射表"。本项目明确否定了"物理位置能推出结构关系"这个前提本身（这正是 `decisions/19-块指针的结构与宽度预算.md` 否定 ZFS 式几何寻址、D1 否定 bucket generation 的同一条依据）。"物理上下一个单元"可能属于别的设备（RAID 条带宽度逐次可变）、别的树、别的快照代，甚至是 parity 格——没有任何机制保证它"恰好也是小数据容器且恰好归我可写"。
2. **即使读出来确实是同类容器，直接往里面写也是跨所有权的变更**。`decisions/01-数据可移动性-反向索引.md:92-93`（已定项 5）："新版写成即旧版断开……**不去改旧单元**（它不可变，改它既撞 COW 也撞 D2『不诱发设备 RMW』那条）"。"向后查询到的单元"极可能已经被别的事务发布（甚至被某个快照根引用），往它的槽表头部追加，等价于**在别人已发布的容器上做原地修改**——直接撞上"旧单元不可变"这条硬规则，也可能撕裂一个已经被某快照根钉住的容器（正是 D1 已定项 5 "旧版不改"要防的事）。

⇒ **替换方案**：仿码 3 的"开放容器"概念——`checks-owed.md:113`（C106）已经给出现成的账本形状："同时开着的容器数（类型 1）= 树数 × 活代际数 × 活头数"。码 5 的写入目标只能是**本写者自己在当前 (树, 代际, 头) 下持有的那一个开放容器**，写不下就新建一个，**永远不查、不碰任何自己没有在写的容器**。这不是效率优化，是把一个正确性 bug 换成一个空间次优但安全的策略。

拆分本身（一个槽的数据超过界线，容器要"拆成老单元+溢出槽"）在这个替换方案下退化成："超界的那个对象改走普通 extent 路径（D4 已定项 7 的一单元一 extent），容器里对应的槽标记死亡，其余槽不动"——不需要真的物理"拆容器"，只需要该对象的中央映射条目从"打包提示"切回"位置提示"。

### 1.7 一个被 M5 命中的新增机制：跨界线迁移必须重新验证崩溃语义

`decisions/14-双轨-大小文件-持久临时.md:42-45`（E8 层 A 第 3 条）：

> "**追加写会在操作中途跨过阈值 ⇒ 阈值不是合格的分支变量**：4 KiB 文件分 8 次追加时内联臂拿到 **6.96 倍**，一次写完时恰好 **1.00**——**同一个文件大小、两个写形态，判据落在阈值两侧** ⇒ 硬要求 5 被这条分支违反，除非另设跨阈值迁移路径并**单独验它的崩溃语义**。"

小数据打包提案原文自带一个"界线"，而 `open()` 之后逐次 `write()`/`append()` 会让同一个文件在生命周期内跨过这条界线——这与 D14 里已经打过一次的坑是**同一个坑**：D14 已定项 3 当初正是因为内联阈值会被"操作中途跨越"而定为 0（不留阈值）。本提案重新引入了一个阈值，**E8 的这条约束因此重新适用**，且 D14 已定项 3 末尾原话确认了这条约束当年被内联阈值 0 消解、不是永久失效："阈值为 0 就没有『内联 → extent』这一步"（`decisions/14-双轨-大小文件-持久临时.md:203` 附近）。

⇒ 最强形态必须**独立设计并验证**"槽 → extent"迁移的崩溃语义（原来 D14 未定项 5 因为阈值取 0 而判"无对象"、"等一次清理"的那个坑，本提案会把它重新变成一个真实存在的问题）。这是一笔新账，不在 C99/C100/C103/C105/C106/C108/C116 任何一条里。

## 2. D14 已定项 3 那一关怎么过

### 2.1 码 3 凭什么过关：逐字读判据

`decisions/14-双轨-大小文件-持久临时.md:184-186`：

> "⚠️ **原子性从此是这一项的判据本身，不只是这一次的取值理由**：**今后任何抬高内联阈值的提议，都要先答『多个文件共享一个原子单位』这一关**，性能数字答不了它。"

`decisions/14-双轨-大小文件-持久临时.md:188-190`（这一关对打包记录单元的答案）：

> "这一关对打包记录单元的答案（2026-09-05，D8 已定项 6）：inode 记录打包进码 3 叶容器是 233 个对象共享一个 32 KiB 单元，形状与内联相同，答案不是性能数——D18 已定项 11 登记的打包记录单元这一类正是为『多个对象共享一个自描述单元』而立，它有自己的身份（出生树、类型、容器号、出生代）与载荷校验和，一个对象的记录不靠别的对象自证；COW 下一个对象的更新写出新版容器、旧版不动，原子性按发布，不会撕另一个对象；**文件数据仍不内联**。剩下的两笔是代价（E103 实测单次更新 1.25–1.5 倍）与爆炸半径（C100），都已立账。"

拆开看，这段话给了三根支柱：

1. **自证**——一个对象的记录不靠别的对象自证。
2. **COW 不撕**——更新一个对象只发布新版容器、旧版不动，不撕另一个对象。
3. **文件数据仍不内联**——这次打包动的是元数据（inode 记录），没有碰用户数据。

背景材料的 M2 只摘了第 1、2 支柱，**漏掉了第 3 支柱**（见第 0 节）。下面逐支柱回答"数据侧能不能照搬"。

### 2.2 支柱 1（自证）：能照搬

第 1 节已经构造出来了：容器身份段 + 槽目录，每槽携带自己的 (对象 ID, 对象出生代)，不靠别的槽自证。这一支柱数据侧**结构上可以做到**，代价是槽目录的额外字节（第 4 节量）。

### 2.3 支柱 2（COW 不撕）：能照搬，但代价是暴露了码 3 真正依赖的东西

码 3 的"不撕"能成立，根本原因不是"COW"这三个字本身（普通 COW 单元更新也会让"物理位置变了"），而是——**inode 树是唯一一棵天然拥有全部 233 条记录的树**：所有共享同一个码 3 容器的记录，本来就属于**同一棵树的同一个叶子**，只有**一个**父指针需要 COW 传播（标准 btree COW 代价，`experiments/103-inode打包路的更新代价.md:46` 实测"1.25–1.5 倍"正是这一个父指针传播的代价，不是 N 个）。

小文件数据没有这样一棵天然共享树——被打包进同一个码 5 容器的 N 个文件，只是因为写入时间接近而physically 凑在一起，各自属于**不同的 inode、不同的目录树**，彼此没有任何天然的结构关联。要让"另一个文件的指针不用改"这句话在数据侧成立，**必须人为发明一层索引**（1.3 节的"小数据容器索引"）去扮演 inode 树在码 3 场景里天然扮演的角色——而这层索引本身正是 C103 还没解出来的东西（1.3 节已论证）。

⇒ **这不是"照搬"，是"重新发明同构机制，且被发明出来的那层索引，其先决条件（C103）本项目自己都还没解决"**。这比背景材料 M2/M6 描述的"加一层容器号间接"更难——间接层不是免费的补丁，它是整个论证能否成立的必需品，而它的地基是空的。

### 2.4 支柱 3（文件数据仍不内联）：数据侧不是"没答"，是**这条支柱本身在数据侧不成立**

这是本文档最重要的发现。D14 已定项 3 判定码 3 过关时，明确把"文件数据仍不内联"作为**独立的一句**放在"不会撕另一个对象"之后（`decisions/14-双轨-大小文件-持久临时.md:190`）——顺序和措辞都表明它不是可有可无的旁注，而是这一关真正要防的东西：**用户数据本身要不要挤进一个多对象共享的原子单位**。

再往前翻一句，`decisions/14-双轨-大小文件-持久临时.md:180-182`（已定项 3 的原始判据，在讲码 3 之前）：

> "内联让**多个文件的数据挤在同一个索引节点里** ⇒ 一个文件的写牵动同节点上其他文件的原子单位。这与 E66 判出局的 `pack` 臂（**多个小文件共享一个数据单元**）**是同一个形状的耦合**，只是换了个容器。"

"只是换了个容器"这五个字是**容器无关的判据**——它明确预见了"以后会有人换个容器形态再提一次"，并且提前把结论钉死为"同一个形状"。而 E66 对 `pack` 臂的定义，逐字就是：

> `experiments/66-补齐之后小文件怎么落.md:14`："`pack` | 多个小文件共享一个 32 KiB 单元 | 空间省回来，但**生命周期耦合**：改其中一个要 RMW 整单元，删一个不释放单元"

**本提案的核心，剥掉槽表、界线、拆分这些包装之后，物理核心就是"多个小文件共享一个 32 KiB 单元"——与 E66 的 `pack` 臂是同一个东西**，只是多了一层槽表寻址和一个拆分规则。D14 已定项 3 判定码 3 过关，靠的恰恰是"码 3 打包的是 inode 记录，不是这个东西"；本提案打包的正是"这个东西"。

⇒ **支柱 3 在数据侧不是"缺一个答案"，是"直接倒下"**：码 3 能过关的必要条件之一（不碰用户数据）在数据侧从定义上就不满足，因为**碰用户数据正是这个提案存在的全部理由**。

### 2.5 这一关的耦合不是"指针传播"问题，是"写正确性"问题——第 5 节详述

支柱 2 的间接层（哪怕能建成）解决的是"更新一个对象要不要碰另一个对象的指针"；但 D14 已定项 3 真正在问的是"一个文件的写，牵不牵动同容器另一个文件的**原子单位**"。这是两个不同的问题——间接层能让"谁引用我"不用查（`decisions/19-块指针的结构与宽度预算.md:109`），但**改不了"COW 一个 32 KiB 容器时，容器里所有槽的字节都要被重新读回、重新校验、重新写出"这件事本身**。这件事的机制细节，以及它为什么无法被绕开，放到第 5 节讲。

**小结**：D14 已定项 3 的三根支柱，数据侧第 1 支柱可搬、第 2 支柱能搬但依赖一个未解的欠账、**第 3 支柱结构性不成立**。所以"照搬码 3 的论证"这个说法本身不准确——码 3 的论证之所以成立，恰恰是因为它站在"这不是文件数据"这个前提上，把这个前提换成"这就是文件数据"之后，论证不是"变难了"，是**换了一个不满足前提的命题**。

## 3. ENOSPC 重开实验怎么设计

### 3.1 判据原文

`decisions/04-校验和位置.md:257-260`（已定项 7 的重开门槛）：

> "**重开的门槛写在这里**：不许拿倍数说事（`.claude/rules/fs-design.md`『比谁省不构成任何判据』），要拿一个小文件负载量出 **ENOSPC 准入什么时候先撞墙**——已定项 2 自己写明空间放大经 D5 的记账进入准入，那是运行时决策路径。"

准入不等式原文，`decisions/03-空间分配.md:38`（已定项 4）：

> "`可用 = Σ设备(容量 − 已分配 − 不可回收 − defer 待释放) − 待删占用 − 已承诺预留`"

判据是"撞墙的时刻"，不是"空间倍数"——实验设计必须直接测这个时刻，不能算完倍数再折算。

### 3.2 实验设计

**自变量**：
- 工作负载：一个**有出处、非臆造**的小文件负载分布（例如某个真实源码树 / 邮件仓 / 包缓存的文件大小直方图——要求这个分布来自现查而不是拍脑袋，按 `.claude/singlefs-ai-sop/rules/evidence-discipline.md` "别的项目怎么做是线索不是证据"这条的姊妹要求，负载分布本身也要有可核实的出处）。
- 设备容量 `C`：固定值，选一个让 `extent` 基线负载消耗到接近 `C` 的量级，使撞墙点落在有限时间内可测（不需要 TB 级长跑）。
- **界线取值**（本提案里"多大算小数据"的那个参数）：作为第二自变量扫描，因为它同时决定槽表利用率与迁移频率（1.7 节）。
- **交错度**：负载脚本里"创建大文件 / 删除文件 / 创建小文件"的交替频率——**这是用户自己点名的弱点**，必须作为独立自变量，不能只跑一个单调追加场景。

**臂**（每条臂都要跑，按 `.claude/singlefs-ai-sop/rules/test-discipline.md` "阳性对照必须对每一条被测的臂都跑"）：

| 臂 | 作用 |
|---|---|
| `extent` 基线 | D4 已定项 2 现行模型：每个小文件补齐到 32 KiB |
| `oracle-pack` | **阳性对照**：假设的零开销打包（不含槽表、不含拆分、不含容器索引间接层的任何字节代价），只用来证明"这套测量装置分辨得出撞墙点提前"这件事本身 |
| `small-data-pack` | 第 1 节构造的最强形态，含槽目录字节开销、容器索引开销、界线迁移开销 |

**判据（跑前写死）**：每条臂在同一个 `C` 下**实际能容纳的文件数**（不是空间倍数），准入不等式（3.1 节公式）算到 ≤ 0 那一刻的文件计数。

**失败条款**：
1. **阳性对照失败**：`oracle-pack` 若不能比 `extent` 撞墙更晚，说明测量装置本身分辨不出"打包能不能延后撞墙"，整轮作废，不许往下推 `small-data-pack` 的结论。
2. **判别力对照**：`extent` 臂在文件大小 512 B 与 30 KiB 两档上，单文件占盘字节必须完全相同（都是一个单元）——不同就说明补齐没被建模，整轮作废（沿用 `experiments/66-补齐之后小文件怎么落.md:26-27` 已经验证过的同一条判别力对照）。
3. **读不到 ≠ 读到 0**：计数器读取失败按 `.claude/singlefs-ai-sop/rules/test-discipline.md` 作废重跑，不许当 0 用。

**反向接受条款（跑前写死，必须敢写）**：
- **单调增长、无删除的场景**：若 `small-data-pack` 没能比 `extent` 撞墙更晚，这是一个正当结果，如实记下——不许因为"直觉上打包应该更省"就怀疑实现有 bug。
- **交错/删除密集场景**：若 `small-data-pack` 撞墙**反而更早**（因为容器碎片化、槽目录开销、界线迁移的写放大叠加），**这同样是正当结果，必须如实记下，不许因为"这不是我们想要的答案"而重设判据**。这个方向的可能性不是凭空猜的——`experiments/103-inode打包路的更新代价.md:56`已经量出同构结构（码 3）在最坏情形下的填充率没有下界："**1e6 顺序创建再删 90% 不合并 = 9.98 倍空间放大**"。若这个数字在数据侧重演，`small-data-pack` 会比 `extent` 更快撞墙，而不是更慢。

**记账纪律的附加判据**：实验还要报告"判定某个开放容器是否还有空槽可写"这个运行时决策的代价是不是 O(1)（不随已分配容器总数增长）——这是 `.claude/rules/fs-design.md` 记账纪律第一格的硬约束，不满足就不只是"实验结果不利"，是"这个设计从格式层面就不合格，不用等 ENOSPC 撞墙"。

### 3.3 预期答案的形状

基于已有数据推断合理区间（这是推断，不是预测跑分——推断本身按 `.claude/rules/three-way-inference.md` 仍需要三方论证，这里只说形状）：

- 单调追加、无删除：`small-data-pack` 大概率能比 `extent` 撞墙更晚（这是打包省空间的本意），但空间收益会被 `checks-owed.md:112`（C105）的开放容器发布频率写放大、以及 `experiments/66-补齐之后小文件怎么落.md:69`（"`pack` 写比 `extent` 贵 1076–1106%"）的单次更新代价部分抵消——**"更晚撞墙"和"每次写更贵"是两个可能同时成立的结论，不矛盾**。
- 交错/删除密集：给定 `experiments/103-inode打包路的更新代价.md:56` 的 9.98 倍上界，`small-data-pack` 完全可能**更早**撞墙——用户自己在提案里承认这是弱点，这个实验设计的价值正在于把"承认是弱点"变成"量出弱到什么程度"。

## 4. 最强形态的代价清单

### 4.1 逐条核对 C99/C100/C103/C105/C106/C108/C116

|---|---|---|---|
| **C99** 打包共享单元里的记录扫描时发现不了 | `checks-owed.md:106` | **复制，且更重**——原句"解出一个单元头并认领之后，就按声明长度把整段载荷跳过去，载荷内部的探针不再参与认领"对码 5 同样成立；码 3 的修法是"记录由类解析器按记录数 × 记录宽枚举"（定长），码 5 是变长槽，**这个修法本身用不了**，需要额外的槽目录做扫描重建的入口（1.2 节），而槽目录自己的完整性证据全仓没有先例 |

## 5. 哪一步构造不出来

**判定：不是 C103、不是槽内分配器、不是任何"可以砸新工程量解决"的欠账——是 D14 已定项 3 的判据本身，而且这条判据的文字设计就是为了不让任何"换个容器"的重述绕过去。**

### 5.1 机制：D4 已定项 3/4 的 RMW 规则把"耦合"变成一个不需要争论的事实

`decisions/04-校验和位置.md:52`（已定项 3）："**凑不满一个单元的写怎么写**：走读—改—写。先把旧单元整个读回来并验 MAC，改完重算整单元的 MAC，再整单元写到新位置。"
`decisions/04-校验和位置.md:53`（已定项 4）："读—改—写读不回旧单元时怎么办：**该写失败并返错，不许零填充重建**。"

把这两条套在码 5 容器上：文件 A 更新自己槽里的数据，落到已定项 3 的 RMW 路径——**必须先把整个容器读回来、验完整个容器的 MAC**。这意味着：

1. **A 的写，正确性上依赖 B（同容器另一个文件）此前写入的字节仍然完整可读**——如果容器因为任何原因（一次未捕获的位翻转、一次读失败）在 MAC 校验上不过，按已定项 4，"该写失败并返错"：**A 的写失败了，尽管 A 自己的数据从头到尾没有任何问题**。
2. E66 已经量出这条 RMW 路径的真实代价：`experiments/66-补齐之后小文件怎么落.md:82`（`pack` 臂）："32768 读 + 32768 写 = 65536"，`experiments/66-补齐之后小文件怎么落.md:69`："`pack` 写比 `extent` 贵 **1076–1106%**"。这不是这次新造出来的代价，是已经测过的、`pack` 这个形状固有的代价。

这正是 `decisions/14-双轨-大小文件-持久临时.md:180`（已定项 3 原判据）说的"**一个文件的写牵动同节点上其他文件的原子单位**"的**字面**含义：不是隐喻，是"A 的写成功与否，literally 取决于容器里 B 的字节是不是完好"。

### 5.2 为什么容器索引间接层救不了这一条

第 1、2 节构造的"小数据容器索引"间接层，解决的是"更新容器后，B 的中央映射条目要不要跟着改"——答案是不用改（B 的条目只写"容器身份+槽号"，容器身份不变）。**但这个间接层完全不触碰 5.1 描述的机制**：无论中央映射怎么设计，只要 A 和 B 的数据物理上共存在同一个走 D4 已定项 3 RMW 路径的 32 KiB 容器里，A 的写就必然要经过"读回整个容器、验整个容器的 MAC"这一步——这是**单元级 RMW 与校验粒度**的规则（D4 已定项 1/3），不是**寻址/索引**的规则（D19 已定项 5 管的那一层）。间接层能优化的是"找到容器要走几步"，不能优化"容器内部的字节是不是所有槽共享同一次读—验—写"。

⇒ **这就是为什么 `decisions/14-双轨-大小文件-持久临时.md:182` 要写"只是换了个容器"**：只要判据问的是"多个文件的数据是否共享同一个 COW-RMW-MAC 的原子单位"，答案不随容器怎么寻址、怎么建索引而改变——**寻址层的进步（D19 已定项 5 的中央映射）解决的是 2026-08-31 D14 定案时还不存在的一个变量（"另一个文件的指针也得改"），但没有解决、也解决不了 2026-08-31 就已经写死的那条判据（"原子单位"）**。这是背景材料 M6 已经摸到边但没有讲透的地方：M6 说"仍消不掉，除非再加一层容器号间接"——本文档在这里给出更进一步的结论：**加了这层间接之后，消不掉的部分依然消不掉，因为间接层从来就不是被要求去解决的那个问题**。

### 5.3 唯一可能绕开它的路径，以及为什么它等于放弃提案本身

理论上有一条路能让 A 的写不依赖 B 的字节完整性：**让容器里每个槽各自独立走自己的校验和/MAC，不共享容器级的一次性 MAC**。但这条路直接撞上 `decisions/04-校验和位置.md:60`（已定项 1）："数据 extent 的校验和 / MAC 覆盖 **32 KiB**"，以及已定项 2/7 的"补齐到整单元、校验和覆盖补齐后的整单元"——**这两条已定条款本身就是这个提案想要绕开的东西**（不补齐到整单元、不用整单元校验，正是提案想省下的那部分空间的来源）。如果给每个槽单独一份校验和/MAC，等于每个槽退化成一个"迷你单元"，各自独立完整、独立校验——那样就不再是"打包共享"，而是"每个小文件仍然独立自证"，**打包省下的正是靠共享校验和/共享 RMW 才省下来的那部分开销，把它拆开来单独校验，收益就消失了，提案本身就没有存在的理由**。

⇒ **构造不出来的地方：不存在一种码 5 的具体实现，能同时满足"多个文件的数据物理共享一个单元（提案的前提）"与"一个文件的写不依赖另一个文件字节的完整性（D14 已定项 3 的判据）"。这两者互斥，不是工程量不够，是逻辑上不相容——放开前者就满足不了后者，收紧后者就取消了前者。**

### 5.4 附带的第二重障碍：即使假设 5.3 的矛盾被判据本身修改（用户明确要求放行），变长分配器仍是一个未经验证的新子系统

即使用户判断"愿意接受多文件共享原子单位这个代价"（也就是修改 D14 已定项 3 本身），第 1.2 节已指出的变长槽内分配问题仍然独立存在：码 3 靠定长记录把容器内部布局问题变得平凡（`decisions/18-块里携带什么信息.md:666`"一容器一种定宽记录"），码 5 若要真正做到"打包变长的小文件而不是把它们也削成定长块"，就需要一个新的容器内分配器（处理槽的分配、碎片、合并、拆分），这个子系统：

- 没有与之对应的已定条款可以援引（无论正推还是反推，检索全仓找不到任何一条决策讨论过"单元内部的变长分配"）。
- 自身需要独立的崩溃一致性验证（一次容器 RMW 中途崩溃，槽表的部分更新会不会产生一个自相矛盾的目录），这是**又一层**崩溃点重放需求，叠加在 1.7 节已经指出的"界线迁移崩溃语义"之上。
- 规模上与 D3（空间分配）本身是同一类问题，只是嵌套了一层（单元级分配器之内再套一个槽级分配器）——`.claude/rules/fs-design.md`"验证是组合的，不是线性的"这条硬约束在这里直接适用：多一层分配器，不是多一份工作量，是让原本"分配是否正确"这一件事变成"外层分配是否正确 × 内层分配是否正确"的叉积。

**如果为了避开这层复杂度而退回定长槽**（模仿码 3），提案就重新制造出它本来要消除的那种补齐浪费——只是把补齐粒度从 32 KiB 换成一个更小但依然固定的槽宽，量变不是质变。

## 结论摘要

1. **最强形态是可以构造出来的**（第 1 节），但它要求：注册一个新单元类型码、发明一个新的容器索引间接层（依赖尚未解决的 C103）、把生死判定退到后台整理、废弃用户原话里的"向后查询"机制、并独立验证界线迁移的崩溃语义。这些都是可以砸工程量解决的债，本文档已在第 4 节逐条与 C99/C100/C103/C105/C106/C108/C116 对表。
2. **D14 已定项 3 那一关，码 3 的论证不能被"照搬"**——它靠三根支柱过关，数据侧第 1 支柱（自证）可搬，第 2 支柱（COW 不撕）能搬但依赖未解的 C103，**第 3 支柱（文件数据仍不内联）在数据侧结构性不成立，因为不内联文件数据正是这个提案唯一的目的**。
3. **重开门槛不是空间倍数，是 ENOSPC 撞墙时刻**——第 3 节给出了具体的实验设计，包含用户自己点名的交错负载弱点作为独立自变量，以及"打包可能反而更早撞墙"这个方向的反向接受条款。
4. **真正构造不出来的地方**（第 5 节）：D4 已定项 1/3/4 的整单元 RMW + 整单元 MAC 校验，把"A 的写依赖 B 的字节完好"变成一个物理事实，这与 D14 已定项 3 的判据是同一件事的两种说法——**不存在一种实现能同时保留"多文件共享一个单元"（提案前提）和满足"一个文件的写不受另一个文件牵连"（已定判据），这是逻辑互斥，不是工程量问题**。第 5.4 节额外指出，即使这条判据被用户明确改写，变长槽内分配器仍是一个全新的、无先例可援引的子系统，规模与 D3 本身相当。
