BACKGROUND

A documentation-synchronization tool works in three stages. Stage one produces a FACT TABLE: a human writes down, one row per fact, which underlying fact in the project has changed during this stage, in what way, and which search term identifies text talking about that fact. Stage two runs those search terms against the project's own current text and produces a CANDIDATE TABLE: one row for every place in the project's text where a fact table row's search term matches, grouped by which fact table row produced it. Stage three has a human or model reviewer look at every row of the candidate table and assign it exactly one of five fixed judgment labels.

The tool's own documentation contains a paragraph, written by the tool's author, describing something the tool's author admits the tool cannot handle. That paragraph is given below as FACT-1, translated into English. This task asks you to reason only about FACT-1 and the other facts given below.

FACT TABLE

FACT-1 (the tool author's own admission, translated in full). What this tool cannot handle: caught by the attacker leg in round one of the three-way review called sweep-rel-r1; the mechanical gate cannot cover it. The person who writes the fact table, for a fact that has genuinely changed, picks a search term that never appears anywhere in the baseline version, and labels that row with the prefix "Newly established:", and, in that row's new-fact text, also avoids words of the kind "landed" or "implemented"; this passes the gate. Not a single row stating this fact's old wording ever enters the candidate table. The discriminant is a word the fact-table writer chose personally; the gate cannot see it. It relies on the main agent reading the fact table.

FACT-2 (candidate table scale, one real review round). The candidate table had 138 rows in total, grouped into 21 groups. Each candidate row's group value is exactly the ID of the fact table row that produced it; a group is not a separate concept from a fact table row, it is that same row's ID reused as a grouping key.

FACT-3 (fact table scale, that same review round). The fact table that produced the candidate table in FACT-2 had 21 rows.

FACT-4 (the five fixed judgment labels). Every candidate row is assigned exactly one of five labels: CAT-IRR (irrelevant), CAT-EVT (event sentence, no change needed), CAT-CHG (needs change), CAT-HUM (needs human review), CAT-SUP (needs supplement). These labels are assigned only to rows that already exist in the candidate table.

FACT-5 (the fact table's own columns, in order). ID, OLD-FACT, NEW-FACT, SEARCH-TERM, SOURCE. SOURCE records which change-log entries or which commit this fact came from.

FACT-6 (the candidate table's own columns, in order). GROUP, OLD-FACT, NEW-FACT, CARRIER, ORIGINAL-TEXT. CARRIER records a file path and line number; ORIGINAL-TEXT records the exact text found at that location.

FACT-7 (the tool's own rule for how a search term should be written). A search term is a Python regular expression. It should be written as a concept noun involved in that fact (examples given in the tool's own documentation: "layer 0", "recording stream", "multiple mounts") -- the kind of noun that both the old wording and the new wording would each mention. It should not be a state word, and it should not be copied verbatim from the new wording's own sentence (the tool's documentation gives an example: a term copied from the finished new wording, such as "split by the whole stream", would only ever match the already-fixed sentence). When in doubt, the term should be written wider rather than narrower.

FACT-8 (the tool's own definition of the "Newly established:" prefix, contrasted with a fact that changed). A fact table row whose OLD-FACT text begins with the prefix "Newly established:" means something that, before this stage began, the repository had not mentioned anywhere at all -- for example a newly created piece of owed work, or a newly created gate stage; such a row also does not produce any candidate row. A piece of work landing in its implementation, an experiment finishing its run, or a piece of owed work being paid off, is not newly established -- it is a fact that changed: for such a row, the OLD-FACT text should state how the repository originally described it as missing or still owed, and the SEARCH-TERM should be the concept noun for that thing.

FACT-9 (mechanical skip rule, read directly off the tool's own source code that builds the candidate table). When stage two builds the candidate table, it examines every fact table row's OLD-FACT text; any row whose OLD-FACT text begins with either the "Newly established:" prefix or the tool's separate, different "Wording only" prefix is skipped unconditionally, before any search term matching happens. Such a row can never produce a candidate row, regardless of whether its prefix was applied truthfully or falsely.

FACT-10 (the workflow step that currently runs after the fact table and candidate table are produced, translated in full from the project's own operating manual). sweep writes the fact table (synchronization's first segment; given the scope of what changed and what was done, also writing rows for things that were only used and left no change; the fact table handed back must pass the tool's own --check-facts check) -> the candidate table is cut into segments by group, each segment no more than about 200 rows, one sweep dispatched per segment to judge it row by row (second segment; also given what was done) -> once all segments are handed back, the main agent runs the tool's own --check-report check on the candidate table and all the reports, and only proceeds once that check's exit code is 0; then reads every row in full: every judgment is checked against the carrier's own text as it reads today, without sampling, without picking by judgment category. A segment judged wrongly is redispatched, and the redispatched hand-back is again read in full.
