## 5-1：丙是不是乙的忠实实现

**判据原文**：「打红条件：有腿证明真实系统里分配器拿得到 key 序批（先攒批再排序是既定机制）」，打红则「乙保留为独立候选，E151 加臂重跑」。

**正推第一步：E151 自己的代码证实乙的『批内 key 升序』来自一次排序，不是到达序**。
`research/e7-index-bench/src/bin/e151_arrival_and_container_arms.rs:498-518` 的 `dirty_set` 函数：均匀随机负载与成段负载都用 `BTreeSet` 收集脏 key，末尾 `set.into_iter().collect()`——`BTreeSet` 迭代产出的是升序序列。`Arm::BumpSegment | Arm::BumpCompact(_) | Arm::Container { .. }` 三条臂（第 611-616 行）直接遍历这个 `dirty`，即按升序放置——这就是乙「批内 key 升序」的来源。`Arm::Arrival`（第 617-623 行）额外调用 `arrival_order`（第 521-528 行，对同一个 `dirty` 做一次 Fisher–Yates 洗牌），才把顺序打散成到达序。**乙与丙的唯一差别就是这一步排序**，与 [records/2026-09-10-D3项8第一轮.md](../../../records/2026-09-10-D3项8第一轮.md) 第 41-44 行记的（针对 E93 那份代码）是同一个机制。

**正推第二步：真实系统的取号规则里没有这一步排序**。
`.claude/kb/decisions/16-发布语义.md:182` 逐字：「事务切分纪律把一次写请求按单元切成若干事务各自取号，一个事务最多写一个单元的用户数据」；同页「取号 = 事务被分配进某个 checkpoint 那一刻，checkpoint 的切分只关闭成员资格——触发之后不再分配事务进它，已分配的事务把各自的单元写完」。**取号是「被分配进 checkpoint 那一刻」，不是「checkpoint 关闭时统一排序」**——每个事务各自独立取号、独立分配落点，checkpoint 边界只管「还收不收新成员」，不管「已经收进来的按什么顺序处理」。这与 E151 的 `dirty_set` 先攒出整批脏 key 再一次性排序，是两种不同的时序模型：前者是逐笔到达即分配，后者是攒批之后再重排。

**正推第三步：仓里唯一「攒批再排序」的既定机制不覆盖用户数据/extent 树**。
`.claude/kb/decisions/08-核心索引结构.md:15` 的结构表：「**write buffer** 前端｜高频小更新（反向索引、LRU、记账）批量攒起来排序去重后批量插入」；`.claude/kb/decisions/08-核心索引结构.md:75`（已定项 7 索引表行）逐字「射程覆盖记账 / 反向索引 / LRU 三棵 write buffer 树」。**这三棵树逐字点名，extent 树（装用户数据）不在其中**。全仓 `grep -rn "攒批\|write buffer"` 现查（见下）没有第四棵树被纳入这个机制。

```bash
grep -rn "write buffer" .claude/kb/decisions/*.md | grep -v history | grep -i extent
# 现查：0 命中——没有任何一条条款说 extent 树走 write buffer 的攒批排序
```

**结论（5-1，不许补）**：我找不到一条已定条款说「真实系统里用户数据的分配器能拿到 key 序批」——唯一的攒批排序机制（write buffer）逐字排除了 extent 树，而事务切分纪律的取号时点是逐笔到达而非攒批重排。**判据 5-1 不打红**：乙（bump_seg 的「批内 key 升序」）没有对应的真实机制，它是 E151/E93 建模时 `BTreeSet` 这一步排序带来的产物，不是乙定义（「按 key 序聚簇进段」）在真实系统里能落地的形态。丙（到达序）是这一族政策里唯一忠实反映事务切分纪律的实现。

**这一条不必再核**：E151 自己的判决（`research/results/e151-arrival-and-container-arms-2026-09-13.out:36-38` 对 `:42-44`，runs8 上乙 7312/7364/7371 对丙 8183/8181/8183）已经证实按到达序放之后乙的优势消失（±11%），与我在此处独立推出的「乙的批内排序无机制支撑」是同一个结论从两条不同的路径（一条读代码 + 读条款，一条读产物数字）到达的，互相印证。

## 5-2：甲在（设备, 列）坐标里怎么写，写出来后与丙在 runs 上还打不打平

**判据原文**：「打红条件：没有腿能把甲写成（设备, 列）坐标里有指称的一句」，打红则「甲出局，候选只剩丙 / 容器」。

**正推第一步：既定坐标系是什么**。`.claude/kb/decisions/02-RAID条带策略.md:59` 已定项 8 逐字：「建对象时按最空的 g 块选一组，此后只在组内取最空的 w 块；组内有盘满了就重选」——**设备维的选取规则是「按最空」，不是「按编号」**。`.claude/kb/decisions/02-RAID条带策略.md:61` 已定项 10 逐字：「整个落在一列上，位置条目 1 条 / 副本」——**一个单元不横跨设备，落在选定的那一列（那个设备）内部**。`.claude/kb/decisions/18-块里携带什么信息.md:143` 已定项 9：「块 = 单元，一个单元一份头；扫描器按池内最小单元大小步进」——**列内的寻址单位是单元 / 槽，不是字节**。

**正推第二步：「全池编号最低的空槽」在这个坐标系里逐字没有指称**。这句话隐含一个前提——全池是一个扁平的、跨设备统一编号的地址空间，可以直接比较任意两个设备上槽号的大小。但 `.claude/kb/decisions/02-RAID条带策略.md:98` 已定项 2「各盘不必等大」与已定项 8 的「按最空的 g 块选一组」共同确定：**设备是先按『空闲程度』分组选出来的，不是按编号排出来的**；不同设备各有自己的槽号空间，没有一条条款说这些空间要拼成一个跨设备的全局序。所以「全池编号最低」这半句话在已定坐标系里没有可以代入的对象——这正是第一轮卡点 3 的原文（[records/2026-09-10-D3项8第一轮.md:18](../../../records/2026-09-10-D3项8第一轮.md)）。

**正推第三步：改写成有指称的一句**。把「甲」拆成两层，与已定项 8 已经管的层次对齐，而不是重新发明设备选取规则：

> **设备层**：沿用 D2（RAID 条带策略）已定项 8——按最空的 g 块选组、组内取最空的 w 块，组内有盘满了就重选；这一层与「甲」无关，甲不改写它。
> **列内层（甲的落点）**：在已经选定要写的那一列（设备）内部，取该设备编号最低的空槽。

这句话有指称：「该设备编号最低的空槽」是设备内部槽号的全序最小值，槽号本身由已定项 7（`.claude/kb/decisions/03-空间分配.md` 已定项 7，落点粒度 16384、按 16 KiB 槽号编码）给出，是一个可比较的整数。**这是「甲」唯一能落地的写法**：把「全池最低」收窄成「已选设备内最低」，设备的选取权原样交给已定项 8，甲不再声称自己能决定选哪个设备。

**正推第四步：写出来之后与丙在 runs 上还打不打平——这里只能推到一半，剩一半推不出来**。

能推的部分：E151/E93 的 `Sim` 结构（`e151_arrival_and_container_arms.rs:114-139`）本身**没有设备维**——它只有一个扁平的槽空间（`slot_count`），`allocate_first_fit`（第 358-367 行）就是在这个扁平空间里找最低编号的空闲槽。这恰好等价于「甲」改写之后的列内层，在**只有一个设备、或者已经选定了要写哪个设备**的情形下的行为——即改写后的甲的「列内层」子问题，E151 的 first_fit 就是它的一个合法实现。在这个子问题上，E151 的产物给出了确定的答案：

- uniform 负载：first_fit 8186（`:27`）对 arrival 8190（`:39`），差 4，占比 0.049%——打平。
- runs8 负载：first_fit 7997（`:30`）对 arrival 8183（`:42`），差 186，占比 2.33%——仍在判据 6(a) 定的 ±5% 带内，打平。

（占比用判据 6(a) 的口径 `|差| × 100 / 丙侧` 算，对照 `within_tie_band` 函数 `e151_arrival_and_container_arms.rs:750-753` 的定义方式）

推不出来的部分：改写后的甲还有「设备层」——每次写之前要先按已定项 8 重新评估「哪个设备最空」。E151/E93 的模型没有设备维，**不能告诉我这一层的存在会不会改变 runs 的统计**：如果设备切换的频率与 key 序无关（这是我能想到的最自然的假设，但它是假设，不是从条款或产物推出来的），那么列内层的结论应该近似成立；但如果设备切换恰好与写入节奏产生某种相关（比如某个设备总是恰好在到达序的某一段耗尽），runs 的表现可能不同。**这一半，E151 没有装置能回答，我也推不出来**，只能明说：判据 5-2 问的「写出来之后它与丙在 runs 上还打平吗」，在「单设备 / 已选定设备」的子问题上打平（有数），在「跨设备切换如何影响 runs」这个子问题上无法回答（E151 无设备维，条款也没有给出可以演绎的规则）。

**结论（5-2，不许补）**：甲能被写成（设备, 列）坐标里有指称的一句——设备层原样交给 D2（RAID 条带策略）已定项 8，甲只管列内层（已选设备内编号最低的空槽）。**判据 5-2 不打红**，甲不出局。它与丙在 runs 上的打平，只在列内层这个子问题上有数（两组负载都在 ±5% 带内），跨设备那一半推不出来。

## 5-3：「丙 + 回落甲」与「甲」除 runs 之外，差在哪个已定条款要的量上

**判据原文**：「打红条件：有腿证明『丙 + 回落甲』与『甲』在某个已定条款要的量上不同（不只是 runs）」，打红则「记『差在哪一格』」。

**正推第一步：先确认「丙 + 回落甲」与「甲」在代码里是不是共用同一个分配器**。`e151_arrival_and_container_arms.rs:472-482` 的 `allocate_metadata_blocks`（提交内生块的分配路径）逐字只调用 `self.allocate_bump()`（第 479 行）。`run_arm` 函数（第 597-668 行）里，`Arm::FirstFit` 分支（第 605-609 行）对用户数据调用 `sim.allocate_first_fit()`；`Arm::BumpSegment | Arm::BumpCompact(_) | Arm::Container { .. }` 分支（第 611-616 行）与 `Arm::Arrival` 分支（第 617-623 行）对用户数据调用 `sim.allocate_bump()`——**与提交内生块走的是同一个方法、同一份 `open_segment` / `bump` 状态**。这意味着：在「甲」（`Arm::FirstFit`）下，用户数据完全不碰 `allocate_bump`，提交内生块独占它；在「丙 + 回落甲」（`Arm::Arrival`，段耗尽时内部回落到 `allocate_first_fit`，见第 372-396 行 `allocate_bump` 自身的回落逻辑）下，用户数据与提交内生块共享同一个 bump 段。

**正推第二步：D3（空间分配）已定项 5 的依据本身建立在『不共享』这个假设上**。`.claude/kb/decisions/03-空间分配.md:157`（已定项 5 依据段，附录已整段抄）逐字：「只聚簇提交内生块就断链（2 轮、28 块），**用户数据全随机也不影响**」。「用户数据全随机」在 E81（提交的固定点）的建模里就是「用户数据不使用 bump/聚簇段，只在扁平空间里随机落点」——这正是「甲」的行为（不碰 `allocate_bump`），不是「丙 + 回落甲」的行为（会去碰）。**换句话说，D3（空间分配）已定项 5 那句『用户数据全随机也不影响』这句依据，量的是甲这一种用户数据策略下提交内生块的收敛情况，没有覆盖『用户数据也在竞争同一个 bump 段』这一种情形**。

**正推第三步：E151 的产物里能不能读出这个差别**。这里我只能读到一半，另一半读不出来，如实分开写。

能读到的：`grid` 一档里，`arm=first_fit` 在 `metadata_blocks=0` 与 `metadata_blocks=9` 两档下，`fallback_pct` 都是 **0.0**（`research/results/e151-arrival-and-container-arms-2026-09-13.out:27,29`（uniform）与 `:30,32`（runs8））。因为在 `Arm::FirstFit` 下用户数据从不调用 `allocate_bump`，`fallback_allocations` 这个计数器（第 391 行）唯一可能被触发的来源就是 `allocate_metadata_blocks` 自己调用 `allocate_bump` 时段已耗尽——而它两档都是 0.0%，说明在「甲」策略下，提交内生块**从未**回落到 first_fit，每次都成功从聚簇段里取到槽。这是一个**直接可读的量**：提交内生块在「甲」下的回落率恒为 0。

对照「丙 + 回落甲」（`arm=arrival`）：同样两档 `metadata_blocks=0/9` 下 `fallback_pct` 是 93.2%/94.1%（uniform，`:39,41`）与 92.3%/93.4%（runs8，`:42,44`）。但这个百分比是**用户数据与提交内生块合并计的聚合数**——`fallback_percent` 的分母是 `total_writes + metadata_blocks × checkpoint_count`（第 665 行），分子 `fallback_allocations` 不区分是哪一类调用触发的。**我读不出提交内生块单独那一份回落率**：`allocate_metadata_blocks` 在每个 checkpoint 开头先跑（第 600-601 行，先于用户数据的 `dirty_set` 与放置），只占 64 槽段里的 0/9 个，理论上不一定会被用户数据挤到回落——但产物没有把这两类分开报数，我无法从现有的 86 行里把「提交内生块自己的回落率」从聚合的 92-94% 里拆出来。**这一半明确推不出来，不许补。**

**结论（5-3，不许补）**：这一格已定条款要的量是 D3（空间分配）已定项 5 依赖的「提交内生块固定点收敛轮数」（其运行时闩落在 C83（提交固定点没人回答））。E151 证实：在「甲」下（用户数据完全不碰 bump 段），提交内生块的回落率恒为 0.0%（两档 metadata_blocks 一致）；在「丙 + 回落甲」下，用户数据与提交内生块共享同一个 bump 段，E81（提交的固定点）依据句「用户数据全随机也不影响」描述的正是「甲」这种不共享的情形，没有覆盖共享的情形。**方向上「丙 + 回落甲」比「甲」多引入了一种 E81（提交的固定点）没测过的耦合**，但耦合具体会不会、会多大程度上推高提交内生块自己的回落率（进而推高固定点收敛轮数），E151 的聚合计数回答不了——这是判据 5-3 打中的那一格，记法是「差在提交内生块回落率是否恒为 0，这个量分开测过的只有『甲』，『丙 + 回落甲』下这个量没有被单独报出来」。

## 5-4：容器档打包前的落点要不要单独一句

**判据原文**：「打红条件：有腿证明打包前的落点影响打包后的 runs 或全空聚簇段数」，打红则「单独一句」。

**正推第一步：容器臂打包前用的是哪条放置政策**。模型表（`.claude/kb/experiments/151-用户数据落点的到达序与容器臂.md:26-37`，附录已整段抄）逐字：「container_k16 / k64｜乙 + 打包（迟滞 16 / 64）｜新」——**容器臂的打包前落点，模型上定义为乙（bump_seg），不是丙（arrival）**。代码印证：`run_arm`（`e151_arrival_and_container_arms.rs:611`）把 `Arm::Container { .. }` 与 `Arm::BumpSegment` 分在同一个匹配分支，都用未经洗牌的 `dirty`（第 612-616 行），只有 `Arm::Arrival` 才调用 `arrival_order` 洗牌（第 617-623 行）——`Arm::Container` 与 `Arm::Arrival` 是两个独立分支，容器打包前的落点确实走的是乙那一支，不是丙。

**正推第二步：5-1 已经判定乙的批内排序无机制支撑**。既然乙的「批内 key 升序」不是真实系统里分配器能拿到的（判据 5-1 的结论），而容器臂的打包前落点原样继承了乙的这个建模产物，那么 `container_k16` / `container_k64` 报出来的 runs 数字，**其打包前那一段落点用的输入本身就带着乙的假象**——真实系统里如果按甲′（到达序为主）落点、再走同样的打包规则，打包前的落点会更接近丙而不是乙。

**正推第三步：这个假象会不会影响打包后的 runs——这里我能定性但定不了量**。`pack_step`（`e151_arrival_and_container_arms.rs:554-587`）判断一个 key 能不能进容器，靠的是 `key_count_at(position) == 1`（是否单对象节点）与 `checkpoint - last_write[key] >= hysteresis`（是否冷够），**两条都与这个 key 当前物理落在哪个槽无关**——即「乙 vs 丙」的落点差异不改变哪些 key 够资格被打包、不改变打包的 key 组合。但打包**之后**的 runs 统计，既取决于容器自己落到哪个槽（`sim.allocate_bump()`，`pack_step` 第 574 行，容器写入也走 bump 段），也取决于**还没被打包的那些单对象节点**当前落在哪个槽——这部分正是乙 / 丙的落点差异所在。所以：打包前的落点政策不改变「打包决策」本身，但改变「打包完成时刻整体布局的 runs」，因为未打包对象的物理槽位仍然携带乙 / 丙的差异。**E151 没有跑『丙 + 打包』或『甲 + 打包』这两条臂**（模型表只登记了「乙 + 打包」），所以这个影响到底有多大，我推不出具体数字，只能推出方向：容器 runs（`container_k16` uniform 6769、runs8 3602，`:45,48`；`container_k64` uniform 7946、runs8 4908，`:51,54`）是在乙的落点基础上测出来的，不能直接读成「到达序 + 打包」的数字。

**结论（5-4，不许补）**：**要单独一句，但不是发明一条新政策，是标注现有数字的口径**。甲′若采纳「打包前同大对象」（即打包前的落点跟随甲′本身的到达序 + 回落规则，不新设旋钮），那么它与 E151 已经跑出的 `container_k16`/`k64` 数字之间存在一个未被量过的落差——E151 测的是「乙的落点 + 打包」，不是「甲′（丙为主）的落点 + 打包」。这一句要写进条款，防止把 0.49–0.97 倍这组数字误读成「到达序 + 打包」的实测值；至于差多少，推不出来，也不该在没有新实验的情况下补一个数。
