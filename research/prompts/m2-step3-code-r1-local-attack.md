DECISIONS AND INVARIANTS THAT APPLY (this project keeps a written decision log; these are direct, faithful excerpts, not summaries)

F14. Decision document "space allocation", ruling item 7 (dated 2026-09-03) and item 11 (dated 2026-09-13). On-disk encoding of one allocation-record entry: key = (device identity, 4 bytes; 16 KiB slot number, 6 bytes) = 10 bytes total; value = (span field, 2 bytes, whose top bit is borrowed as a "released" flag; allocation-or-release generation, 8 bytes, storing a full checkpoint number) = 10 bytes total. When a placement is released, its entry is never deleted, not even by point-deletion (this follows a 2026-09-05 ruling): the entry is rewritten in place to "released + release generation" — the release generation goes into the very same 8-byte field that held the allocation generation, the released flag borrows the span field's top bit, and the entry is left exactly where it is until that same placement is reallocated in the future, at which point the entry gets overwritten by the new allocation's data. The stated reason for not deleting by generation: the tree is ordered by placement (device, slot), and the generation lives in the value; deleting all entries of a given generation would require a full scan of the tree, and the by-generation list a point-delete would need is exactly the in-memory state a crash loses. The rewrite to "released" happens in the same publish, and becomes durable atomically together with, the COW operation that produced the release, because the allocation-record tree is itself a copy-on-write tree rooted under the same root record; what a crash loses is exactly the unpublished checkpoint, so a release that never got published leaves no trace at all, and the placement's older version is still referenced by whichever root ends up selected.

Item 2: "free bytes"; consumers: admission, checker; carries a per-device dimension; does not carry a per-tree dimension. Item 5: "defer-queue bytes pending release, by generation"; consumers: the defer window, allocation, admission; carries a per-device dimension; does not carry a per-tree dimension. F20. Decision document "block pointer structure and width budget", ruling item 5 (dated 2026-09-06). This decision demotes the location entries carried inside a pointer to a hint only: reading the hint lets a reader try that placement directly, but the hint may be stale (out of date). The central mapping tree becomes the sole entry point for both dereferencing a unit and deciding whether it can be released: moving a unit only requires changing one entry in the mapping tree; nothing needs to track "who references me". F21. Decision document "verification route", ruling item 4 (dated 2026-09-03). This decision defines the exact state set that crash-point replay must enumerate: "barriers cut the recorded write-request stream into segments; a crash state is defined as: all earlier segments fully persisted, an arbitrary subset of the current segment persisted, and every later segment not persisted at all; the unit of enumeration is one whole write." It explicitly excludes tearing within a single write: "any torn state of a single write is folded into the single case 'this write did not persist'; at the position where a write 'did not persist', the crash image must contain the pre-crash old bytes, not zero bytes, and this image must actually be generated and fed to the checker, not merely counted as a number." A scope note attached to the same ruling item states, verbatim in translation: "this defines the enumeration domain at the model layer only. Whether real storage devices' FLUSH/FUA commands actually behave as this model assumes is a separate, still-open question, to be verified against real devices under a virtual machine; a device that tears one write in a way that happens to collide with a checksum by chance is not inside this model."
