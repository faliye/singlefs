1. For candidate A: A scenario where the header's locality_id is incorrect (e.g., 5) but the actual key prefix should be 3. During rebuild, the system uses the header's locality_id to reconstruct keys, storing data under (5, inode, offset) instead of (3, ...). When reading, the system looks for (5, ...), but data exists under (3, ...), causing data loss. For candidate B-prime: If the extent tree is corrupted and the inode record's locality_id is wrong (e.g., 0), but the header's locality_id is 5 (outside associated data), rebuild uses the header's value. However, the extent key prefix might be missing or corrupted, leading to incorrect key prefix (0) for data stored under (5, ...), causing data loss. For candidate C-prime: No scenario causes data loss; keys are (tree ID, inode, offset) without locality_id. Clones use (tree ID, inode) for uniqueness, and rebuild identifies objects via inode, so data is always found.

2. A conflicts with F5 because including locality_id in the five fields (associated data) makes it load-bearing, contradicting "may be wrong" declaration. The weight is in "that would make a field declared 'may be wrong' load-bearing." B-prime does not conflict with F11 because locality_id is outside the five fields and encrypted as part of the header, while F11 only specifies the five fields and birth/write order as ciphertext; additional fields outside the five fields are encrypted but not part of associated data.

3. Cost: A adds 8 bytes per unit header and per packing slot (41 bytes total), first-transaction bytes increase by 8. Rename does nothing, background moves require updating locality_id in headers during re-clustering, rebuild reads locality_id from headers. B-prime adds 8 bytes per unit header (slots remain 33 bytes), first-transaction bytes increase by 8. Rename does nothing, background moves update header locality_id during re-clustering, rebuild uses extent key prefix first. C-prime adds 0 bytes; no changes to headers, slots, or first-transaction bytes. Rename does nothing, background moves and re-clustering skip locality_id, rebuild uses (tree ID, inode) without locality_id.

4. I-9.9 check: For A, it can turn red if record's locality_id differs from extent key prefix (e.g., record=3, key prefix=5). For B-prime, same as A: red if record's locality_id ≠differs from key prefix. For C-prime, I-9.9 is undecidable because locality_id is not part of the key prefix (key is (inode, offset)), so the check cannot compare record's locality_id to a non-existent prefix; the invariant is not applicable.

5. Pick C-prime. It avoids contract changes, extra bytes, and data loss risks while maintaining correctness. A single observation that would change the pick: measurements showing >15% performance degradation in common workloads due to lack of locality_id prefix, even with large caches.
