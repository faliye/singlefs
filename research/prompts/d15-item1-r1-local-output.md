1. The precedent for reserving space for an open list of trees assumes future trees will be added as new core structures. However, the second track was explicitly rejected as a feature. Trees are fundamental to the filesystem's structure and expected to grow, while the second track was a specific rejected concept with no current or future plan. The precedent applies to necessary expansions of existing core components, not to features that were deliberately excluded. Adding trees later is a natural evolution of the design, but the second track was never intended to exist, so the justification for reserving space does not apply.

2. A reserved compatible-tier feature bit costs real resources because any future reader must always check and handle this bit, even if it is never set. For example, a version 2 reader must include code to process the bit, which adds complexity to the reader implementation. If the bit is accidentally set by a buggy tool, the version 2 reader might misinterpret the data or fail to handle it correctly, even though the bit is compatible. This creates unnecessary maintenance overhead for all future readers, as they must account for a bit that has no defined behavior and will never be used.

3. If version 2 later wants a second track and nothing was reserved, it must change the block pointer width to include the track bit. This forces all existing readers to fail to mount the filesystem because they expect a fixed-width block pointer. For example, if the block pointer was 64 bits and the new version requires 65 bits, older readers will read the wrong data for the pointer, causing corruption. This is more costly than reserving a bit in the block pointer (arm D), which would allow version 2 to set the bit without changing the width, keeping compatibility with older readers.

4. A reserved-but-unused bit prevents no misuse. Since the bit is never set, there is no scenario where it is used incorrectly. The rule requires that a format branch turns "used it wrongly" into "cannot mount", but an unused bit cannot be used wrongly in the first place. It provides no failure mode improvement.

5. Arm B is not strictly worse than arm A. Both reserve nothing on disk, and arm B explicitly documents in the checklist that version 1 does not contain the feature and version 2 would use an incompatible bit. This documentation prevents future confusion by clarifying the decision. Arm A lacks this documentation, which could lead developers to assume the feature might be added later without an incompatible bit, causing incorrect assumptions during development. The checklist entry in arm B is beneficial and does not introduce any additional cost or risk compared to arm A.

6. The assumption that the second track will never be needed is most likely false. If a critical security feature requiring a second track is discovered after the freeze—such as a need for separate checksums for encrypted data that cannot be implemented within the existing format—the observation would be that the filesystem cannot support the feature without breaking compatibility, forcing a major redesign and breaking all existing readers. This would reveal that the assumption was incorrect and the decision to not reserve space was a mistake.
