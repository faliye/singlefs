# D5（快照 / 空间记账机制） 未定项 12（deadlist 条目的形态） 第一轮：正推腿（Sonnet）报告

## 〇、结论摘要

**甲在 U2 被击穿出局**——建快照要求「逐条重写」直接违背前提一（D5（快照 / 空间记账机制） 正文，见下）自己的字面「整个交接」，且这不是可收严的缺口，是它的定义本身。
**乙在 U3 被击穿**——用掉前提八那 8 字节之后，与 C144（16 字节）、C143（inode 号水位在回退后会退回去重发） 第一轮甲臂（8 字节）三者之和 = 32 > 24，超预留 8 字节（算式见第四节）。
**丙站得住**：零树表字节、建快照 O(1)（复用既有 `previous_snapshot_txg` 字段，不新增任何格式代价）、归属键在克隆头上因头树 ID 前缀而唯一。销毁级联的改写量不是 O(deadlist(S))，而是 O(deadlist(next) 中 epoch = S.txg 那一段)——这一点甲/乙都做不到（详见第二、三节）。

**分桶取 (i)**：不另分桶，理由不止「前提六里本来就有出生 txg」，还有一条更硬的——销毁级联无论哪条臂都要把相关那一段**逐条**过一遍（第三节的改写量分析），额外的 8 字节桶号买不到跳过任何一条entry 的权利，只是把同一件事换个位置存一遍。
**value 取空**：与前提十一（释放一律经映射，不经提示）直接同构——deadlist 条目的落点/大小若带一份副本，就是位置条目降级为提示之后同一个坑的重演（旧值可能与映射不同步、且给实现留一条双重释放的路，D19（块指针的结构与宽度预算） 已定项 5 硬规则 1 明文禁止）。

**本轮发现一个不属于本项、但三条臂共享的模型缺口**：「prev(S).txg 在运行时怎么查到」全仓没有条款——已定项 9 明写 `previous_snapshot_txg` 只写在活头自己的树表条目里，快照条目该字段恒 0（见附录 `.claude/kb/decisions/08-核心索引结构.md` 已定项 9），意味着一个**已发布快照**的 prev 值不是一个可以直接读出的持久字段，得靠「在同一头的树表条目里按诞生 txg 找相邻幸存者」这类查询现算。三条臂都要用到这个值（甲用它判断要不要碰某个 tree-ID 分支的哪一段、乙/丙都要它做过滤边界），但没有任何一条 kb 条款描述这个查询的具体机制。这不是三条臂里哪一条的问题，落一笔新欠账（第五、六节展开）。

## 一、前提转述核对（失败条款自检）

逐条把前提表的转述与附录原文并排核对，**未发现转述与原文矛盾**；下面记两处措辞上需要澄清的地方（不构成失败条款触发，但影响后面的字节算术，必须先说清）。

### 1.1 前提八的「24」不是原始预留，是「16→32→24」三跳之后的当前值

前提表写「树表条目预留 24 字节……两个候选加起来正好 24」。核对 `.claude/kb/decisions/08-核心索引结构.md` 第 758 行（已定项 8 段落）：2026-09-06 那次定案时，**预留起点是 16 字节**，C145（deadlist 在盘上没有落点） 的 8 + C144（快照谱系的区间标号没有载体） 的 16 = 24 > 16（当时的预留），才把预留**加宽到 32**；随后 2026-09-14 又从 32 里切走 8 字节做「头 ID」，剩 24（`.claude/kb/decisions/08-核心索引结构.md:764`「③ 预留 32 里切 8 字节做「头 ID」，预留剩 24」）。

数字本身（8、16、24）都对，前提表没写错，但这句「两者加起来正好 24」容易让人误以为 C145+C144 是**针对今天这个 24** 精确算出来的——实际是巧合：C145 的 8 + C144 的 16 恰好等于**今天**的预留总量，而这个「今天的预留总量」已经悄悄吸收过一次「切给头 ID」的减法。**这意味着 C145（本项要解决的问题）与 C144 已经把 24 字节耗尽在假设层面，任何第三笔需求（比如 C143 的甲臂）从一开始就没有余量**——这正是第四节要算的东西。

### 1.2 前提九「previous_snapshot_txg 只写在该头 inode 树那条树表条目里，其余条目写 0」——对丙有直接影响

前提表只写「每个可写头各持一份 `previous_snapshot_txg`、住树表条目 8 字节」，附录原文（`.claude/kb/decisions/08-核心索引结构.md` 已定项 9，索引表行）更精确：「`previous_snapshot_txg` 只写在该头 inode 树那条树表条目里，**其余条目写 0 且 0 = 不适用**」。这意味着**快照自己的树表条目上，这个字段永远是 0（哨兵），不是该快照的 prev 值**——丙的机制描述「快照 S 的 deadlist = (头, prev(S).txg) 那一段」里的 `prev(S).txg`，不能从 S 自己的树表条目直接读出，必须靠查询在 S 所属那个头的树表条目集合里按诞生 txg 找 S 的相邻前驱。这就是结论摘要里提到的共享缺口，第五节详细展开，这里先标注：**前提表对前提九的转述是准确的，但它的推论（丙如何取得 prev(S).txg）需要额外一步，前提表没有点破**。

## 二、Q1：丙的归属键在克隆头上唯不唯一；C195 的 prev 传递在三条臂上各怎么落

### 2.1 唯一性：丙的键因头树 ID 前缀而唯一，克隆不构成碰撞

丙的 key = 头的树 ID 8 + 纪元 txg 8 + 映射 key 27。**头的树 ID 是全局单调递增、随创建序严格增的**（`.claude/kb/decisions/08-核心索引结构.md` 已定项 8「树 ID 水位……每次发布随根记录重写……每次发布 checkpoint 分配的树 ID 必 ≤ 根 N 里的水位」），因此不同头（包括克隆头）永远拿到不同的树 ID。给一段具体历史验证：

- txg=0：mkfs，H1（树 ID=12）。`previous_snapshot_txg(H1)=0`（哨兵）。
- txg=10：H1 写块 b1，`birth(b1)=10`。
- txg=20：建快照 S1（H1 的快照，S1.txg=20）。丙的动作：`previous_snapshot_txg(H1)` 从 0 改写为 20（单字段更新，见第三节）。
- txg=25：从 S1 克隆出 H2（树 ID=13，新分配）。按「克隆 / 可写快照要加三条」第 1 条（`.claude/kb/decisions/05-快照-空间记账机制.md:71`「新克隆的 `previous_snapshot_txg` 必须初始化为 origin 快照的 txg」），`previous_snapshot_txg(H2)` 初始化为 S1.txg=20。H2 自己的 deadlist 是全新空的。
- txg=30：H1 与 H2 都持有对 b1 的引用（H2 继承自克隆）——这是「四条前提」第 3 条被越过的场景，b1 的存活由稀疏旁表（D5（快照 / 空间记账机制） 已定项 6）计数，不是丙这条臂要管的：H1 杀掉自己那份引用，旁表计数 2→1，**不产生任何 deadlist 条目**（旁表吸收了这次 kill）。
- txg=35：H2 杀掉最后一份引用，旁表计数 1→0，落回普通 D5（快照 / 空间记账机制） 逻辑：`birth(10) ≤ previous_snapshot_txg(H2)=20` → 追加进 H2 的 deadlist，key = (头树ID=13, 纪元=20, 映射key(b1))。

这条 key 与 H1 自己链上任何一个 (12, 纪元, ...) 形态的 key **不可能碰撞**，因为 8 字节前缀就是 12 对 13，无关纪元 txg 是不是恰好都取到 20。**所以「纪元 txg 在克隆头上不唯一」这个反向接受条款设想的失败模式，本身就不成立**——纪元 txg 单独看确实可能在两个头上取到相同的数值（H2 继承 20、H1 自己后续也可能建出 txg=20 的快照？不可能，因为 txg 全局单调，H1 若在 20 之后才建自己的下一个快照，那个数必然 >20），但 key 从来不是纪元 txg 单独定义唯一性，是 **(头树ID, 纪元txg)** 一起定义，头树 ID 段天然隔离了不同头/克隆之间的命名空间。

「归属算错」这个反向接受条款设想的另一半——上面 txg=30/35 那步演示的正是「归属算对」：H1 杀自己的引用不产生条目（旁表吸收），H2 杀最后一份引用才产生条目，且条目挂在 H2 名下（谁做的最后一次删除，条目就挂谁的链）。这与 I-3.5（引用区间的精确性） 的射程注完全对应（`.claude/kb/invariants.md:123`「跨头共享的块……不由 deadlist 单独管，判据 ③/④ 对它们不适用；它们的生死由旁表计数与各头的可达性合起来判」）——丙不需要对跨头共享单独建模，这层已经被旁表挡在 deadlist 之外，丙只需要正确处理「单一头链条内部」的归属，而单一头链条内部的归属正是头树 ID 前缀保证的。

**丙在 U1 归属这一格不出局。**

### 2.2 但发现了一个丙/甲/乙都没有回答的真实缺口：克隆头自身被销毁时，它的 pre-clone deadlist 桶去哪

延续上面的历史：假设后来 H2 自己也不再需要了，要销毁 H2 这个头。D5（快照 / 空间记账机制） 给销毁头的规则是「克隆/可写快照要加三条」第 3 条：「销毁一个可写头需要第二个结构（livelist），要释放的是 `birth > origin.txg` 的那批块」（`.claude/kb/decisions/05-快照-空间记账机制.md:99`）。这条规则字面只管 `birth > origin.txg=20` 的块（H2 自己克隆之后新产生的垃圾），**没有提到 H2 自己那个 (13, 20) 桶里那些 `birth ≤ 20` 的条目**（比如 txg=35 那条 b1 的记录）该怎么处理。

这批条目此刻"归属"在 H2 名下，但 H2 即将不存在——它们逻辑上需要的是"S1 还在不在引用它们"这个判断，而不是"H2 还在不在"。这正是 U1 要求覆盖的「克隆头」场景里，材料没有明写、需要我主动指出的一处空白：**三条候选（甲/乙/丙）都只描述了「建快照」与「销毁快照」两种转移，没有一条描述「销毁一个（自己没有活跃子快照、本身是叶子）的克隆头」时，它自己链条上那些 `birth ≤ origin.txg` 的 deadlist 桶该合并到哪条链**。

这个缺口**不分辨三条臂**——甲需要把 H2 名下 tree-ID=13 的条目改键到某个目标（可能是 H1 或者 S1），乙需要把 H2 树表条目的 deadlist 号所有权转移给某个目标，丙需要把 (13, 20) 这段纪元合并进 H1 链条的相应纪元——三条臂都要多一条「头销毁时的桶转移」规则，且转移的目标（S1？还是 S1 destroy 之后继承 prev 的那条链？）都要回答同一个问题：H2 的 pre-clone deadlist 逻辑上"挂靠"在 S1 身上，但物理上存在 H2 自己的树 ID 前缀下（丙/甲）或 H2 自己的 deadlist 号下（乙）。按第五节反向接受条款的处置口径："三条臂在 U1 被同一段历史一起打中 ⇒ 打中不分辨臂，病根另记（多半在前提一的模型本身），判臂只看分辨得出臂的格"——这正是这种情形，应记成一笔新欠账（见第六节），不影响甲/乙/丙之间的取舍。

### 2.3 C195（prev 传递）在三条臂上各怎么落

C195 的检查目标（`.claude/kb/checks-owed.md:196`）是「任一 deadlist 条目，其归属快照的 `prev(S).txg` 等于它在销毁级联中继承来的那个值」。三条臂的落地方式：

- **甲**（归属=树 ID）：prev 传递体现为——销毁 S 时，S 名下 tree-ID 前缀的全部条目被**物理搬到**下一侧的 tree-ID 前缀下；这一步之后，若这条链再销毁一次（连续销毁），下一次的「下一侧」判定要看**当时**谁是链上继承者，不看任何存储的 prev 值本身（甲根本不存 prev，靠外部查询得到）。传递失败的可观测后果：条目物理挂在了错误的 tree-ID 下（比如没有转移、留在了已经不存在的 S 的树表条目名下），checker 扫描树表会发现一个不属于任何活体的 tree-ID 前缀下还有条目。
- **乙**（归属=deadlist 号）：prev 传递体现为树表条目里 8 字节 deadlist 号字段的重新赋值——销毁 S 时，S 的 deadlist 号要么被下一侧继承（下一侧的树表条目该字段改写为 S 的号），要么反过来（S 的条目被物理迁移到下一侧原有的号下）。**这个字段本身不携带任何 txg 信息**，纯粹是一个不透明标识符，所以「prev 传递」这件事在乙这里完全不体现在 deadlist 条目的字节里，只体现在树表条目那 8 字节的重新赋值上——这是一条与甲/丙完全不同性质的实现，C195 的检查落到乙身上要变成"检查树表条目的 deadlist 号字段有没有正确地跟着继承链走"，而不是"检查条目本身的某个字段"。
- **丙**（归属=(头树ID, 纪元txg)）：prev 传递**直接体现为条目 key 里纪元 txg 段的物理重写**——这是三条臂里唯一一条 C195 描述的"继承来的那个值"可以在条目本身里直接读出来对比的（甲的条目不含 txg、乙的条目也不含 txg）。销毁 S 时，S 的下一侧（epoch=S.txg 那个桶）里满足 `birth ≤ prev(S).txg` 的条目，纪元段从 S.txg 改写为 prev(S).txg；不改写的后果是它们的纪元段停留在 S.txg，之后 S 这条记录已经不存在，这批条目的纪元值再也对不上任何活体快照的 prev，正是 C195 描述的"无界泄漏"具体在盘上的样子——**丙是三条臂里唯一让这条不变量可以直接从条目内容读出来验证的**，不需要额外去查树表。

（Q1 的第四小问——三条臂各配什么会红的检查——见第四节 Q5。）

## 三、Q2：建快照与销毁级联各改写多少条；「建快照」是不是前台操作、有没有条款要求 O(1)

### 3.1 改写量公式

先说明一个贯穿三条臂的共同结构：销毁级联要处理的不是「S 自己那一段」，是**「下一侧」桶里满足 `birth > prev(S).txg` 的那批条目要释放、剩下的要并入 S 的边界**。这一点在附录原文里其实已经隐含——`.claude/kb/decisions/05-快照-空间记账机制.md:9-10`「销毁快照时把它的 deadlist 合并到下一个更新的那一侧，并按 `birth > prev(S).txg` 过滤出可释放的条目」——这句话的主语「它的 deadlist」和「过滤」放在一起读，唯一自洽的理解是：**S 自己积累的那批条目（由 I-3.6（deadlist 紧界） 定义，全部满足 `birth ≤ prev(S).txg`）不需要被过滤**（过滤条件对它们恒假，见 3.1.3），**真正需要过滤、需要移动的是"下一侧"那批条目**（详见下面按臂展开）。

**甲（归属=树 ID）**：

- 建快照：活头当前 deadlist 里的每一条，key 从 `(头树ID_H, 映射key)` 改写为 `(树ID_S, 映射key)`——**逐条重写，量 = |deadlist(活头此刻)|**，随「从上次建快照到现在删了多少东西」线性增长，不随盘容量增长但随操作历史增长，没有上界。
- 销毁：destroy S 时，S 自己名下的全部条目（tree-ID=S 前缀）要重写到下一侧的 tree-ID；**同时**下一侧原有的、满足 `birth > prev(S).txg` 的条目要被释放（删除）——这两批都要touch，量 = |deadlist(S)| + |deadlist(next) 中满足释放条件的部分|。**上界比丙/乙都高**，因为它多背了「S 自己名下那批」这一份，而这批的大小恰恰等于 S 建立时活头积累的全部历史。

**乙（归属=deadlist 号）**：

- 建快照：交换两个 8 字节标识符（新快照的树表条目写入活头当前的号，活头的树表条目写入一个新分配的号）——**零 deadlist 条目被触碰，O(1)**，与前提中「与 ZFS 换对象同形」的描述一致。
- 销毁：材料对乙的销毁只给了字面描述「销毁级联把条目改键到下一侧的号」（第三节候选段），没有说明是"总是重写被销毁一侧"还是"重写较小的一侧"（union-find 式的按秩合并）。**按字面最弱读法**（总是重写被销毁一侧），量 = |deadlist(S)|，与甲的销毁量同一个量级，只是省掉了甲销毁时还要额外扫描下一侧释放的那部分——但乙同样需要对下一侧做 `birth > prev(S).txg` 释放过滤（这是任何一条臂都逃不掉的语义要求，见 3.1.3），所以乙的销毁量实际上是 |deadlist(S)| + |deadlist(next) 需释放的部分|，与甲同阶。**乙唯一比甲省的是建快照那一步**。

**丙（归属=(头树ID, 纪元txg)）**：

- 建快照：只改写活头树表条目里 `previous_snapshot_txg` 这一个已有字段的值——**O(1)，且不是新增字段，是复用前提九已经承诺要有的字段**，这是丙相对乙的关键优势：乙的 O(1) 需要新买 8 字节（前提八点名的候选），丙的 O(1) 不需要买任何字节。
- 销毁：destroy S 时，只需要处理"下一侧"（epoch=S.txg 那个桶）：满足 `birth > prev(S).txg` 的条目释放，其余的把纪元段从 S.txg 改写为 prev(S).txg——**S 自己名下（epoch=prev(S).txg）的那批条目完全不用碰**，它们已经满足最终应有的纪元标签，不需要重写。量 = |deadlist(next) 中 epoch=S.txg 的那一段|，**不包含 |deadlist(S)| 这一份**——这是丙相对甲的关键优势：甲在销毁时要重写 S 自己积累的全部历史，丙不用。

### 3.2 为什么丙的销毁不用碰 S 自己那批（自洽性核验）

这一点值得单独验证，因为容易被误解为"少做了一步"。S 自己那批条目（epoch=prev(S).txg）由 I-3.6（deadlist 紧界） 定义为全部满足 `birth ≤ prev(S).txg`。销毁 S 时若对这批条目也套用过滤条件 `birth > prev(S).txg`，结果是空集——**这批条目里没有一条能通过这个过滤**，所以对它们做过滤是一次没有任何效果的扫描，唯一需要做的是让它们继续留在原地（纪元标签 `prev(S).txg` 本来就是它们销毁后应该归属的下一个实体的正确标签，因为 next 继承 prev(S).txg 作为自己新的有效边界）——这正是「prev 要跟着传递」那句话的字面含义：不是"S 的条目要挪去 next 名下"，是"S 的条目已经在正确的纪元标签下，next 只是把自己的边界口径改成认这批条目也是自己的"。

### 3.3 「建快照」是不是前台操作；全仓有没有条款要求 O(1)

**grep 结果（本轮现查，命令与命中数据如下）**：

```
grep -n "建快照" .claude/rules/fs-design.md      → 无命中（exit 1）
grep -rn "建快照" .claude/kb/ | wc -l              → 25 处命中，分布在 8 个文件
grep -rln "建快照" .claude/kb/                     → decisions/05, decisions/06, decisions/08,
                                                     decisions/21, checks-owed.md,
                                                     experiments-history.md, decisions-history/2026-09.md,
                                                     experiments/{12,13,90,94,129,130,137}.md
```

`.claude/rules/fs-design.md`「记账是事务的副产品」那一节（第 17-25 行）把盘上结构分三格：**运行时决策路径**（不许遍历、代价不许随盘容量涨）、**checker/审计**（必须遍历）、**后台/可续做/非决策路径**（无戒律，第 25 行明确点名「销毁快照、整理、scrub」）。**「建快照」一个字都没有出现在这三格的任何一格里**——它既不在第三格被豁免的例子中，也不在第一格被要求的例子中。**全仓没有任何一条条款用「O(1)」这三个字直接约束「建快照」**，这是本轮 grep 的确切结论，不是推测。

但有两条间接证据支持「建快照应当被当作前台/同步操作对待」：

1. **D5（快照 / 空间记账机制） 正文第 8 行自己的措辞**「建快照时把活头的 deadlist **整个交接**给新快照」——"整个交接"这个说法本身描述的是一次性、单一动作的转移，不是逐条搬运；这与"销毁快照"那一句用词不同——第 9-10 行用的是"合并……并按……过滤"，暗示要做工作，而"整个交接"没有这层意味。
2. **D5（快照 / 空间记账机制） 已定项 11 的措辞**（`.claude/kb/decisions/05-快照-空间记账机制.md:507`）在论证 deadlist 树该不该 day-1 注册时说：惰性创建"会多出一条『第一次建快照时建树』的路径，而那条路径要在提交里建一棵树、写一条树表条目、抬树 ID 水位，**全在一次发布里做完**"——这句话把"第一次建快照"里牵涉的全部格式动作都框定在**一次发布（一次 checkpoint 提交）**之内，说明"建快照"这个操作被设计者当作与一次 checkpoint 同步完成的东西，不是可以跨多个 checkpoint 分批做的后台任务。

**结论**：没有显式的 O(1) 条款，但"建快照"在设计语境里被当作前台、单次发布内完成的操作，这个定性本身没有争议（对照"销毁快照"被 fs-design.md 第三格显式豁免，两者的待遇明显不同）。**甲（逐条重写）与这个定性直接冲突**：若活头此刻积累了十万条 deadlist 条目，"建快照"这个用户触发的、预期同步完成的操作，要在同一次 checkpoint 里逐条重写十万条 B 树记录，这与"整个交接"的字面用词、以及"建快照应当是轻量操作"的设计直觉都不符。**这是甲在 U2 出局的第二重理由**（第一重是纯粹的渐进代价分析），两重理由指向同一个结论：甲不满足前提一自己定义的语义。

## 四、Q3：分桶 (i)/(ii) 与 value 空/带大小，各自的依据

### 4.1 分桶：取 (i)，不另分桶

材料给出的依据是「中央映射 key 里本来就有出生 txg（前提六），销毁级联本来就要把那一段逐条过一遍」——第三节的改写量分析证实了后半句：**不管选哪条臂，销毁级联都要对相关桶做逐条扫描**（甲要重写 S 自己的全部历史、乙同甲、丙要扫描 next 桶里 epoch=S.txg 的那一段），既然逐条扫描不可避免，一个额外的 8 字节桶号能买到的唯一东西是"用一次范围查询代替一次全量扫描"——但范围查询省下来的只是"跳过不需要碰的条目"，而销毁级联里**没有条目是不需要碰的**：需要释放的要被删，需要保留的要被重写纪元标签（丙）或重写归属标识（甲/乙），二者都是必须触碰。

反过来看分桶 (ii) 的代价：每条目多 8 字节，且这 8 字节与已经内联在映射 key 里的出生 txg 字段（码 1 的 27 字节里第 9-16 字节就是出生 txg）完全冗余——**这正是 `.claude/rules/fs-design.md`「不为省空间牺牲自包含」那条规则要挡的反面情形吗？不是**——该规则挡的是"为了省空间而砍掉本该有的自描述字段"，这里恰恰相反：分桶 (ii) 是"为了方便扫描而重复一个已经存在的字段"，属于 `code-discipline.md`"DRY，重复要生成不许手抄"一类问题的字节版本——两份 8 字节的出生 txg（一份在桶号里、一份在映射 key 里）不是由同一个生成器产生，若未来对某个类别的映射 key 编码方式做修改（比如 D19（块指针的结构与宽度预算） 已定项 6 那种"key 重新分配字段"式的收严），两处冗余字段可能分叉。**取 (i)。**

### 4.2 value：取空

前提十一「释放一律经映射，不经提示」（`.claude/kb/decisions/19-块指针的结构与宽度预算.md` 已定项 5 硬规则 1）已经对"提示类字段"给出过一次明确的负面判决——**位置条目**曾经是权威，后来被降级为"提示"，理由之一正是"提示会过期"，而"经映射"的唯一入口原则保证了释放判定永远读到最新值。deadlist 条目若在 value 里带一份大小或位置，就是重新引入一个可能过期的提示：搬迁（D26（后台整理与放置回收） 已定项 5 已定"搬迁不改 birth"，但搬迁会改变物理位置）之后，deadlist 条目里的旧提示会指向一个不再正确的地方，而**deadlist 条目本身在整个生命周期里不会因为搬迁而被更新**（搬迁触碰的是 extent/inode 树里的活引用，不触碰 deadlist——这正是 D26（后台整理与放置回收） 已定项 5 依据里 E94（搬共享落点的触碰面） 实测"按映射记 deadlist 恒零重写"这句话的含义）。value 带大小/位置，会让这份"恒零重写"的性质被破坏——搬迁如果也要去更新可能存在的 deadlist 提示，就等于重新制造了 D26（后台整理与放置回收） 已定项 5 第 ③ 条已经用 E94（搬共享落点的触碰面） 实测量出来的"按落点记每批 11-36 条重写"的代价，而这正是三条候选臂在"按什么身份记"这一层已经统一否决掉的做法（前提五："不按落点记，也不带位置提示"）。**value 空，三条臂一致，没有分歧。**

## 五、Q4：乙用掉前提八那 8 字节之后，C144 的 16 字节与 C143 第一轮甲臂要的 8 字节还放不放得下

这是一个跨两项三方论证的约束，我读了 `research/prompts/_c143-r1-body.md`（C143 第一轮的背景材料，任务书未禁止读取——它明确只禁止本轮同题的另外两条腿的产出文件 `d5-item12-r1-*-output.md`，C143 是完全独立的另一个未定项）。C143 甲臂原文（`_c143-r1-body.md` 第 29 行）：「**甲（水位进树表条目）**：树表条目预留 24 字节里切 8 字节，每个可写头的 inode 树那条条目带『inode 号水位』……改第一个事务的字节：是（inode 树那条条目这 8 字节从 0 变 2）」。

**关键的共享事实**：C143 甲臂要切的 8 字节，与 D5（快照 / 空间记账机制） 未定项 12 乙臂要切的 8 字节、以及 C144（快照谱系的区间标号没有载体） 要的 16 字节，**是同一个池——每个可写头自己的 inode 树那条树表条目**。理由：

- 乙臂原文（背景材料第三节）：「每个头/快照的树表条目带一个 deadlist 号」——对可写头而言，这个号住在头自己的 inode 树条目上（与 `previous_snapshot_txg` 同一条条目，因为按已定项 9 后者也只写在头自己的 inode 树条目上）。
- C143 甲臂：inode 号水位"每个可写头的 inode 树那条条目"——同一条条目。
- C144（快照谱系的区间标号没有载体） 的嵌套区间标号：`.claude/kb/decisions/08-核心索引结构.md:758`「树上的推广是嵌套区间标号（preorder/postorder）」——这是给**整棵谱系树上每个节点**（不止快照，包括作为谱系根/分支点的可写头本身）标号用的，一个可写头若本身是分叉点（比如上面 2.1 节历史里的 H1，它既是活头又是 S1 的谱系父节点），也需要携带这个标号——所以这 16 字节同样落在头自己的树表条目上。

**算式**：预留总量 24（今天的值，见 1.1 节）。三笔需求若同时落在同一条头的 inode 树表条目上：

```
乙（deadlist 号）  8
C144（区间标号）  16
C143 甲（inode 号水位） 8
合计              32

32 > 24，超出 8 字节，放不下。
```

即便**不算乙**（比如 D5（快照 / 空间记账机制） 未定项 12 选了丙，丙不占预留），仅 C144 的 16 + C143 甲的 8 = 24，**恰好用满、零余量**——任何第四笔需求（不管是本轮还是以后新开的哪一项）都会立刻超预留。

**丙的优势在这里量化得很清楚**：丙不占预留任何字节，把 8 字节的空间还给了"C144+C143 甲"这个组合，使这个组合从"超 8 字节"变成"零余量精确吃满"——仍然脆弱（零余量本身就是一个需要盯住的状态），但至少不是当场溢出。**乙一旦当选，则 D5（快照 / 空间记账机制） 未定项 12 与 C143（inode 号水位在回退后会退回去重发） 两项三方论证的结论会互相绑死**——只要 C143 最终选甲臂，乙就必须连带触发反向接受条款「乙 + 预留加宽」，树表条目宽度要从 148 再往上加，这是一处新的跨决策连锁，而且连锁的触发条件不在 D5（快照 / 空间记账机制） 未定项 12 自己手里，取决于另一项独立的三方论证结果。

**旁注**：C143 自己"事先的倾向"是丙（零字节，见 `_c143-r1-body.md` 第 53 行），如果 C143 最终真的落在丙或乙（回退不重载单调量），这个冲突就不会发生。但 Q4 问的是"C143 第一轮甲臂"这个具体假设下算不算得过账，按这个假设算，答案是**放不下**。

## 六、Q5：每条臂各配一条会红的检查与判别力自证

### 甲

**检查**：checker 遍历树表，对每个仍存活的 tree-ID（活头 + 未销毁快照），确认 deadlist 树里凡是以该 tree-ID 为前缀的条目，都满足"该 tree-ID 对应实体的可达性区间"（沿用 I-3.5（引用区间的精确性） 的判据 ③/④ 骨架，把"deadlist 归属区间"换成"该 tree-ID 前缀段"）；同时确认**不存在任何 tree-ID 前缀段挂在一个已经不在树表里的（已销毁）实体名下**——这是甲特有的检查，因为甲的归属直接等于物理存在的树 ID，一个残留前缀直接暴露"销毁时没有正确重写"。

**判别力自证**：在模型层把"建快照时逐条重写"的那一步故意去掉一条（模拟"改键漏了一条"），断言该检查必须由绿转红——具体地，让某条 deadlist 记录在建快照后仍然挂在旧活头的 tree-ID 下，而旧活头此刻已经把 `previous_snapshot_txg` 更新指向新快照，检查应该能发现"这条记录挂在一个已经不该再持有它的 tree-ID 下"。

### 乙

**检查**：checker 读出每个存活实体（活头/快照）树表条目里的 8 字节 deadlist 号，反查 deadlist 树里以该号为前缀的全部条目，验证它们满足对应实体的可达性区间；额外要检查**deadlist 号的唯一性**——任意时刻，不应有两个存活实体的树表条目指向同一个 deadlist 号（除非其中一个是另一个刚合并进来但尚未清空的过渡态，这需要一条明确定义的过渡态判据，目前材料未给出，是乙特有的一笔潜在欠账）。

**判别力自证**：在模型层，销毁级联时故意跳过"重新赋值树表条目里的 deadlist 号"这一步（让下一侧的树表条目仍然指向自己原来的号，而不是继承被销毁一侧的号），断言检查必须由绿转红——具体地，这会导致被销毁快照原有的条目失去任何存活实体指向它们，变成"孤儿桶"，检查应能发现"存在一个 deadlist 号不被任何存活树表条目引用，但号下仍有条目"。

### 丙

**检查**：直接对应 C195（销毁级联时 prev 传递只写在实验的模型修订记录里） 给出的判别力自证原型（`.claude/kb/checks-owed.md:196`）——「checker 判『任一 deadlist 条目，其归属快照的 `prev(S).txg` 等于它在销毁级联中继承来的那个值』」。因为丙的纪元 txg 直接内联在条目 key 里，这条检查不需要额外查树表，可以纯粹通过扫描 deadlist 树本身完成：对每个 (头树ID, 纪元txg) 前缀段，独立算出"这个纪元今天应该等于哪个存活快照/活头的边界值"（按诞生 txg 在该头链条里找相邻幸存者，即第五节要另立欠账的那个查询），与条目里实际记录的纪元段逐一比对。

**判别力自证**：把「继承那一步去掉」（每次销毁各用各的原始 prev，不做传递）——这正是 C195（销毁级联时 prev 传递只写在实验的模型修订记录里） 自己写明的自证手法，且已经在模型层被 E94（搬共享落点的触碰面） 的变异 M5b 验证过会红（`.claude/kb/decisions/05-快照-空间记账机制.md:11`）。**丙是三条臂里唯一可以直接复用这条已经验证过的模型层变异、不需要重新设计判别力自证的**——甲和乙的判别力自证都是本轮新想的，没有先例验证过它们真的会红；丙的自证路径在 E94（搬共享落点的触碰面） 里已经有一次独立实证。

### 三条臂的共同缺口

三条臂都还欠一条会红的检查覆盖 2.2 节发现的"克隆头销毁时 pre-clone deadlist 桶怎么转移"——这条缺口目前连模型层的候选做法都没有，不属于本轮能定案的范围，落第七节的欠账记录。

乙在 U3 被"挤掉 C144 的 16 字节"打中，但打中的具体形态比反向接受条款字面描述的更精确：不是乙单独就挤不下 C144（乙+C144=24，恰好吃满），是**乙加上另一项独立三方论证（C143）的甲臂**才真正溢出。按反向接受条款「乙在 U3 被『挤掉 C144 的 16 字节』打中 ⇒ 交用户在『乙 + 预留加宽』（修 U3 那一格，树表条目变宽）与丙之间选」——本轮论证认为这条款应该被触发，但需要补一句限定：**乙与 C144 单独共存时是"零余量"而非"直接溢出"，真正的溢出需要 C143 甲臂也当选**；这个精确度对"要不要现在就否决乙"这件事有影响——如果 C143 最终选了丙（C143 自己的事先倾向），乙就只面临"零余量"而非"溢出"，届时乙是否仍要被判出局，需要用户在看到 C143 结论后重新核对，而不能直接援引本轮"32>24"这个数字（那个数字的前提是 C143 选甲）。

丙在 U1、U2、U3、U4 四项判据上都未被本轮任何攻击面打中，是本轮唯一在四项判据上都站得住的候选。**丙是本轮正推腿给出的正面结论**，与主 agent 事先的倾向一致，但本轮论证是独立走到这个结论的（走过甲的"整个交接"字面冲突分析、乙的跨项字节算术、丙的克隆头历史构造），不是简单复述事先倾向。

### 本轮新发现、需要登记的欠账（不在本轮范围内定案，仅记录）

1. **prev(S).txg 在运行时怎么查到，全仓没有条款**（1.2 节、5.3 节引用处均涉及）。已定项 9 明确"该字段只写在活头自己的树表条目上，快照条目该字段恒 0"，意味着一个已发布快照的 prev 值不是持久字段可以直接读出的，需要"在同一头的树表条目集合里按诞生 txg 找相邻幸存者"这类查询——这个查询的具体算法（复杂度、要不要额外索引）全仓一处未写，且**三条臂都依赖它**（甲判断改键目标、乙判断号继承目标、丙判断纪元继承值），不是哪一条臂独有的缺口，按反向接受条款"打中不分辨臂，病根另记"的口径，不影响本轮臂选，但应该独立立项。

2. **克隆头自身被销毁时，它继承自 origin 的 pre-clone deadlist 桶去哪，没有条款**（2.2 节）。这与 D5（快照 / 空间记账机制） 已有的 livelist 机制（管 `birth > origin.txg` 那批）是互补而非重叠的关系——livelist 已经解决了"克隆头自己产生的新垃圾"，但没有解决"克隆头继承来的、且它自己后来又杀掉了的旧垃圾归属"，这批垃圾此刻记在克隆头自己名下（不管哪条臂），克隆头销毁时它们逻辑上应该回到 origin 所在的那条链，但没有任何候选臂的字面描述覆盖这一步的转移机制。这条缺口也不分辨甲/乙/丙。

以上两条按"打中不分辨臂，病根另记"处理，均不影响本轮"丙站得住"的结论，也不构成对丙的一次真正打击——它们是模型层（前提一）本身留下的空白，三条候选臂都是在这个空白之上工作的，谁也没有把这个空白填上。
