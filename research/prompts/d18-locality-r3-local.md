Self-describing data unit headers and the locality_id key prefix in a copy-on-write filesystem design, round 3.

Answer in English. Do not use any markdown emphasis: no bold, no italics, no headings with asterisks. Use plain numbered answers.

Facts from the design (treat them as given):

F1. Every data unit carries a plaintext self-describing header. Its identity fields are exactly the set that encryption binds as associated data: (unit type tag, tree ID, object ID, object birth generation, anchor offset) = 1 + 8 + 8 + 8 + 8 = 33 bytes. The design prefers writing more bytes to cutting fields for space.
F2. A proposal, open since 2026-09-03: add a sixth field, locality_id. The extent key starts with it, and on disk it has only one witness. If the inode record is lost, a scan finds the data units but cannot put them back: a unit header gives the object ID and anchor offset but not the key prefix. The field set is also the associated-data set, which is a permanent day-1 contract, so changing it is a permanent contract change.
F3. Extent key = (locality_id, inode, offset). locality_id is inherited from the parent directory at creation and deliberately not updated on rename. It is a hint, not part of correctness: it may be wrong and may be stale. The design says this allows not trusting its meaning, not dropping its bits: as the key prefix its value is exact and defining. The inode record must store a copy of locality_id.
F4. Benefit: keying by inode is 1.46 times slower than a locality_id prefix only with interleaved creates and a leaf cache of 8; when the cache holds the whole tree the effect disappears; renames decay the benefit toward 1.0.
F5. locality_id must never be part of the associated data, because that would make a field declared "may be wrong" load-bearing.
F6. In the first version locality_id is always 0. Today it has no plaintext expression on disk (the header's five fields do not include it). A rejected allocator-hint candidate that clustered data by locality was faulted, among other things, for adding the first leak of a "user object semantic category" when encryption is on; the design notes that clustering by locality moves the same signal into physical placement without adding the field.
F7. Freeze layer 3 holds the key encodings of every keyspace, including locality_id.
F8. Invariant I-9.9: the record's locality_id equals the prefix of every extent key of that object. Before any extent tree rebuild the check reports red or green; after a rebuild both sides come from the same source and it must report "undecidable", never "pass". Invariant I-9.10: the object birth generation matches in the record, in every data unit header, and in the tombstone if any.
F9. First transaction: the inode record's locality_id (offset 16) is 0; the extent leaf record key is (0, 1, 0).
F10. A project rule: "prefer writing more" governs whether a field already shown useful should be cut for space; it does not decide whether to add a field, which needs its own reason.
F11. When encryption is on, only the fsid and the payload CRC stay plaintext in a data unit's identity section; the five fields, the birth code and the write order become ciphertext in place. The user decided on 2026-09-07 that the leak is not accepted. Rebuilding with encryption on needs the key.
F12. locality_id is never updated by rename. Background re-clustering must be incremental, interruptible and resumable, and may be stopped at any time. Degradation is repaired by the resident background reorganization the design already committed to. What value to use when there is no parent directory must also be decided.
F13. Clone heads allocate inode numbers independently after the clone, so numbers overlap; uniqueness is by (tree ID, inode). Inode tree rebuild covers a single-head image only.
F14. Rebuild has three levels by witness; the level with only checksums or MACs consistent and no allocation records mounts read-only. While the superblock marks the index as rebuilt and not yet promoted, no authoritative structure may be repaired in place from the rebuild result.
F15. Objects of 4 KiB or less go into packing containers; each slot carries its own five fields; the key fields in a slot are copied byte for byte from the unit header as it was before packing; packing into a container re-encrypts anyway. A packing container has one MAC for the whole container, and its associated data binds the container identity (user decision 2026-09-10). Binding each object's identity under one container MAC is excluded by mechanism: N associated-data values against one MAC means N minus 1 objects fail verification.
F16. Background moves go through the central mapping and do not change referrers.
F17. Invariant I-1.8: readable published units of classes 1 and 3 are grouped by all fields of the class identity section including the write order; after grouping, groups with the same key must have pairwise different total-order keys; for class 1 (data units) the total-order key is the write order. Members of one group carry the same payload (class 1 judged by payload CRC); a difference is judged as damage, not a choice.
F18. On the rebuild path (index lost) the plaintext header must take part: there is no lookup path, so the associated data can only come from the unit header. Changing a single header field makes the MAC fail, but moving a whole unit (header and ciphertext together) passes verification.
F19. One transaction writes at most one unit of user data (the user restated on 2026-09-13: one unit per transaction). With the default journal ring the effective dirty-byte budget of one publish is 256 MiB.
F20. The inode record has 20 reserved bytes (always 0) at offset 120.

Rounds 1 and 2 found: C-prime and B-prime were not hit by any correctness failure. In C-prime, preferring the surviving extent key over the record turned out to be a locality preference, not a correctness requirement, because C-prime gives all of an object's keys the same prefix; preferring the record also had zero failures. Candidate A (locality_id in the associated data) was hit four ways: grouping by the literal key put back an old version from before a re-key; with the record preferred, a record rolled back to an older version could not be matched because A cannot re-key a surviving unit without breaking its associated data; a copy-then-cut re-key left the record pointing at the old segment; writing two copies during copy-then-cut left the older live copy behind a newer copy whose key had been deleted. A's associated data cannot cover packed objects (F15). Common to all candidates and not used to judge them: "background re-clustering" has no definition; if it re-keys in batches across publishes, I-9.9 turns red on legal intermediate images.

Candidates:
A-S. Put locality_id into the five fields, which also puts it into the associated data: header identity 33 -> 41 bytes; rebuild reads the key prefix of a data unit from its header. Tightenings: S6, versions of a data unit are grouped by (object, anchor offset) only, ignoring the header's locality_id (I-1.8's "same key" says so for class 1); S7, the rebuilt record takes the set of rebuilt prefixes as a multi-value in the rebuild view (not written to disk) and a reader tries each; S8, during copy-then-cut a write goes only to the primary segment and the other segment's key is dropped and copied again. Re-keying always rewrites the re-keyed units, with or without encryption. Packed objects: the slot does not carry locality_id; on rebuild an object of 4 KiB or less gets one prefix for all its keys as in C-prime. Changes F1, removes the exclusion in F5, changes I-1.8; permanent contract change; changes first-transaction bytes.
B-prime. Put locality_id into the header outside the five fields and outside the associated data (+8 bytes); when encryption is on, it becomes ciphertext together with the five fields. On rebuild, identify an object by (tree ID, inode) and look only at that head's extent tree (S2); give all of the object's extent keys one prefix, chosen in this order: surviving extent key prefix, then inode record, then header hint, then 0 (S3). I-1.8's "same key" excludes this hint field. Packing slots do not carry it. Changes first-transaction bytes.
C-prime. Do not add it. On rebuild, identify an object by (tree ID, inode) and look only at that head's extent tree (S2); give the record and all of the object's extent keys, surviving and recovered, the same prefix (S9). Two orders are both under attack: C-prime-record (inode record, then surviving extent key prefix, then 0) and C-prime-S1 (surviving extent key prefix, then inode record, then 0). A wrong value loses only locality. After a rebuild I-9.9 reports "undecidable". Zero bytes, no contract change.
Shared premise for all candidates, not used to judge them: background re-clustering is run under both definitions, moving physical placement only (no header byte changes) or re-keying; when re-keying, an object that fits one publish is done in one publish, and a larger one either keeps both old and new prefixes in the record while moving some keys per publish, or copies then cuts with a single-valued record. A protocol that replaces the record value without keeping the old one fails ordinary reads and is not a candidate. S10: I-9.9 is judged per side; when one side was derived from the other, it reports "undecidable".

Questions:
1. Rebuild correctness under shapes rounds 1 and 2 did not try: deleted or truncated data whose old units remain readable on disk (tombstones); orphans of an abandoned timeline (units published and then abandoned by an administrator rollback or an instance switch, still readable, especially when the instance table or the ancestor table cannot be read); packed objects that are re-keyed, moved out by a write, or rewritten with the whole container after packing; two clone heads that each re-key the same shared object. For each candidate (A-S, B-prime, C-prime-record, C-prime-S1), give a rebuild history in which a reader cannot find some data, one object ends up under two different key prefixes, or a reader sees data that was not at that position before the damage (an overwritten old version, a deleted version, or a version from an abandoned timeline); or list the shapes you tried.
2. Contract: does A-S conflict with F5, F15 or F17 today? Does C-prime-S1 conflict with the rule in F14?
3. Cost: bytes per unit and per packing slot, first-transaction bytes, and what rename, background moves, re-clustering and rebuild must do under each candidate.
4. Can S10 turn red on a legal image, or turn a real error into "undecidable"? What check would you give each of S6, S7 and S8 in A-S, and how would you prove each check can turn red?
5. Which one do you pick, and what single observation would change your pick?
