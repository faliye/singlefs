## 三、H3：wal_full 施加记录要不要分配器、要不要第二份固定点代码（实现侧）

**判定：实现侧没打中。** 依据全是今天的 `crates/`：

- 四样固定点每次发布都整份重建：分配记录直接从分配器全表拷（`crates/singlefs-core/src/transaction.rs` 第 1680 行 `    let mut allocation_records: Vec<AllocationRecord> = allocator.records().to_vec();`），记账行从各盘位图的计数里取，映射条目与树表条目从这一版的文件角色算。没有增量更新的代码可以「重复」。
- 已经有一条「文件角色沿用上一版、只重写固定点」的发布路径：transaction.rs 第 1637 行 `        (None, Some(carried)) => carried_file_version_units(carried),`。可写挂载的写行那次发布走的就是它：`crates/singlefs-core/src/mount.rs` 第 711 行 `/// 写行那次发布、上一版带文件：在上一版那张实例表后面接上这次写的行，重写实例表与四个固定点单元（D18（块里携带什么信息） 已定项 11；`，下一行起是第 713 行 `fn publish_rows_on_file_version<Device: BlockDevice>(`。
- 已经有一条不挑落点的登记路径：allocator.rs 第 601 行 `    pub fn rebuild_from_records(`，按盘上记录把槽标成占用、把已释放的放进 defer，不经 `allocate_*`。

所以 wal_full 的施加可以只做两件事：(i) 把每条记录点名的落点按记录登记进分配器，同 `rebuild_from_records` 的形态；被换下的旧版按 transaction.rs 第 846 行 `pub fn placements_to_release_via_mapping(` 那条路释放。(ii) 交出一份反映已施加记录的「上一版」，挂载后的写行发布照今天的路径把四样固定点重建出来。两步都不挑新落点，也不另写一份固定点代码。
模型量了「重放本身」这一段（把 `_alloc` 换成抛错，`run-len8.out` 原样）：

```
replay arm=jia allocator_calls_during_replay=0 cells_ending_on_fsync_record=0 derived_in_memory_not_on_disk=[]
replay arm=wal_K9p allocator_calls_during_replay=0 cells_ending_on_fsync_record=40456 derived_in_memory_not_on_disk=['FP']
replay arm=yi_K9p allocator_calls_during_replay=0 cells_ending_on_fsync_record=40456 derived_in_memory_not_on_disk=['FP', 'S']
```

这组数按构造成立：模型的重放函数拿不到分配器。它说明的只是「不需要」可以做到，不说明 `crates/` 里做到了。

**H3 在什么情形下会被打中**（推的，给主 agent 与后几轮看，这一轮不算打中）：

- 记录要点名这次写出的**每一个**单元，不能只点名新树根。E155 的 wal_full 记录「每棵被碰到的树点名它的新树根一项」（prereg 第 819 行）。只点名树根时，施加要从新树根往下走，走到和旧树相交为止，才找得全要登记、要进映射的新单元：实现侧的施加里多了树遍历（不挑落点，但有树语义）。
  最强形态照甲今天的记录，每个写出的单元一项（transaction.rs 第 2058 行 `    let named: Vec<NamedUnit> = written_units`）。记录定长 4096、装 67 项（D23 第 694 行，上面已抄），一次 fsync 写出的单元不超过 67 个时，记录条数与字节都不变（推的；F8A、P = 10⁸ 那一格一次 fsync 写几个单元我没算，交 H5）。
- 固定点改成增量维护之后（多层映射树与分配记录树，E148 的方向），挂载后那次发布要从「事件」推差量，而不是从全表重建。那时如果差量在 `allocate_*` 里当场产生，重放的登记路径就得另写一份：H3 的第二个分句会成立。今天的 `crates/` 不是这样。
- 读法 a（txg 按 checkpoint 走）下还撞 D19 已定项 8 的交付前置。`.claude/kb/decisions/19-块指针的结构与宽度预算.md` 第 153 行，整行：「- 固定点收敛：插映射条目会弄脏分配记录树与记账树的码 2 节点，它们又要在映射里删插；在「每个码 2 节点与码 3 容器，一个实例在一个 checkpoint 里只写出一次」下收敛，边插边 COW 下没人量（C163（固定点各轮写序相同使平局破除落空））；」。wal_full 每次 fsync 都在同一个 checkpoint 里重写一遍用户树脊柱，这个收敛前提的字面不成立。读法 b 下成立。

## 四、H6：乙有一种形态，重放不挑新落点，且与「分配先于 journal」相容

### 乙-M 的定义（被攻过零轮）

- fsync：照 E155 的乙写（prereg 第 824 行，整行：「- fsync：d 个数据单元 + extent、inode 两树第 0 层的脏节点 + ⌈脏叶数 / 67⌉ 条记录（每片脏叶一项）。次序同 wal_full。高度为 1 的树，根就是叶，照写。」）。每项带 key 各段、两盘落点、校验和，外加被换下那一版的 key。记录暂时充当父节点：`research/e7-index-bench/src/bin/e16_journal.rs` 第 72 行 `/// ⇒ **记录必须临时充当父**，否则重放时那些块没有任何完整性凭据。`（两条 WAL 臂都一样）。
- checkpoint：照 E155 的乙写，写祖先、四样固定点、记录、根槽。中间版按 K9′ 处理（见第一节）。
- 施加一条记录：把点名的叶按 key 换进所选根那棵树的内存视图，父节点在内存里改指针（叶分裂时两片叶都已点名，父节点里的分隔 key 取自叶内容）；点名的落点按记录登记进分配器，形态同 allocator.rs 第 601 行 `    pub fn rebuild_from_records(`；被换下的旧版按记录释放。祖先与四样固定点都留在内存，**由挂载后的第一次发布（写行那次）走正常发布路径分配、落盘**。
- 这正是背景材料第五节问二（第 69 行，是主 agent 写的问题，不是条款）给 wal_full 的那一招：四样固定点由施加记录的代码现推、先放内存，下一次 checkpoint 再落盘。乙-M 把同一招用到用户树的内部节点上。

## 这条腿自己的限度

- 模型只有一个实例：没有重开、实例切换、暖机、管理员回退、抬 F（F 恒 0，floor = 环里最旧的根）。第一节「套到第一版真实的镜像上」那一段是推的。
- 用户树压成一个脊柱单元 S，四样固定点压成一个单元 FP；两个文件、每个文件一个数据单元。多层树、叶分裂、多个数据单元都没建。
- 分配器对所有单元都取最低空槽。`crates/` 只对用户数据这样取，提交内生块从聚簇段 bump。第一节那段历史里被复用的槽 2 是数据单元（d0#3 → d0#8），所以只看数据单元，打中也成立（`trace.out` 第一段）。
- 故障只有单故障，没有单元撕裂、记录撕裂、环回绕。
- 「甲也中」的配对按同一串操作配、不按同名故障配，因为两臂的 txg 编号不同。
- 模型只读导入 `crates/` 的 5 个锚点，不跑 `crates/` 的代码。第三节对 `crates/` 的判断是读代码得出的，没跑。
- 第二节读法 b 的「集合层」核对器是我对最少要做什么的推断，没写过核对器。
