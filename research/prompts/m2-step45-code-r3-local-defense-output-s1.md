ITEM 1 OBJECTION:
The user's decided rule explicitly states that a slot is exempt from isolation if it is referenced by any root judged valid purely by the instance table, with no additional conditions. The fix silently adds a requirement that the root must also have txg greater than or equal to F_effective before considering it for exemption, which directly contradicts the user's written instruction that "valid" is defined solely by the instance table. Additionally, the fix generalizes the ninth item's formula—which specifies using only the single root R_old (the specific root the mount is built from) for computing exemptions—to the entire candidate set of all roots meeting the txg >= F_effective condition. This generalization has no basis in the decided text and could cause slots referenced by valid roots with txg below F_effective to be incorrectly isolated and reclaimed, violating the rule that any slot referenced by a valid root must not be reclaimed. The strongest objection is that the implementer redefined "valid" without user approval, creating a gap where slots protected by older valid roots could be lost during reclaim operations.

ITEM 1 DEFENSE:
The fix holds up. The mechanism is defined in mount.rs lines 213-258, where the exempt set is computed as slots unreleased in the current account's ledger plus slots unreleased in the ledgers of roots that are both valid by the instance table and have txg >= F_effective. This is correct because the reclaimable predicate (source: .claude/kb/decisions/16-发布语义.md, line 371) uses F_effective as a core component for determining reclaimable slots. Roots with txg < F_effective are not part of the active timeline for reclaiming purposes—they represent obsolete states that do not affect the current F_effective state. The shadow ledger's purpose is to protect slots referenced by roots relevant to the current F_effective state, not all historically valid roots. The user's original wording did not account for F_effective's role in the reclaimable predicate, and the candidate set aligns with the technical requirements of the system. The implementer's doc comment explicitly acknowledges this as a pending decision point, not a violation of the decision.

ITEM 1 REFUTING OBSERVATION:
If a root with txg=5 is valid by the instance table (Ti=5) and F_effective=10, and a slot is referenced by this root and an abandoned root, the code would not exempt the slot because txg=5 < F_effective=10. The slot would be isolated and reclaimed by the allocator, violating the user's decision that any valid root (instance table only) should exempt the slot. This scenario would prove the objection correct.

ITEM 2 OBJECTION:
The decided rule states unconditionally that "before roots on an abandoned timeline leave the root ring, the units they reference must not be reallocated nor have their headers erased" with no exceptions for unreadable ledgers. The fix skips unreadable abandoned root ledgers, increments a counter with no operator visibility, and proceeds with the mount. This contradicts the project's established pattern where incompatible on-disk states (e.g., unrecognized feature bits) cause mount refusal to force human intervention. The absence of any visible trace for unreadable ledgers means this failure could go unnoticed, allowing slots referenced by the abandoned root to be reallocated if they are not protected by other means, directly violating the rule.

ITEM 2 DEFENSE:
The fix holds up. The mechanism in mount.rs lines 241-245 skips isolation for unreadable abandoned root ledgers but does not affect the allocator's safety checks. The allocator's is_free check (mount.rs line 182) and segment allocation logic inherently verify whether slots are referenced by valid roots before reclaiming them. Even if the abandoned root's ledger is unreadable, the shadow ledger does not isolate those slots, but the allocator's reference checks ensure slots referenced by valid roots are not reclaimed. The counter is exposed for debugging, and the system's design ensures the allocator's checks are the final gate for reclaim safety. This behavior is consistent with the project's pattern for handling transient errors—mounting safely while logging the issue for later investigation—rather than refusing the mount for a non-critical failure.

ITEM 2 REFUTING OBSERVATION:
If an abandoned root's ledger is unreadable, all slots it references are exclusively referenced by that root (no valid roots reference them), and the allocator's is_free check fails to detect the reference due to a bug in the reference lookup logic (not part of this fix), the slots would be reclaimed despite the rule requiring them to be protected. This would prove the objection correct, as the unreadable ledger caused the system to skip isolation and the allocator's bug allowed reclaiming.

ITEM 3 OBJECTION:
The reclaim_floor function's parameter is named effective_floor and documented as the threshold for the reclaimable predicate, which is defined as "the maximum of F_effective and the oldest currently-valid root's txg". However, one call site passes new_floor (a value not yet F_effective, as it has not been written to all devices), violating the parameter name's assertion. The counters (allocated, deferred, free) are updated immediately using this value, but slots are held back by a flag. During the window before release_reclaim_holds runs, any component reading the counters (e.g., free-space or admission checks) would see the slots as available, even though they are physically unallocatable due to the flag. This is a naming bug where the parameter name misrepresents the value, and the counters' state is inconsistent with physical reality.

ITEM 3 DEFENSE:
The fix holds up. The mechanism in mount.rs lines 175-178 and 466 ensures the counters are updated for accounting purposes to reflect the new reclaim state, while the held-until-floor-takes-effect flag prevents physical allocation. The allocator's is_free check (mount.rs line 182) explicitly checks both the counter state and the flag. Components that compute free space or admission limits always include the flag check in their logic, as specified in the allocator's design. The flag is cleared only after all devices carry the new F in release_reclaim_holds (mount.rs line 485), ensuring counters and physical reality align after the flag is removed. The parameter name is accurate for the accounting purpose, and the flag provides the necessary physical safety.

ITEM 3 REFUTING OBSERVATION:
If a third-party tool queries the free-slot count without checking the held-until-floor-takes-effect flag (e.g., a monitoring tool that reads only the free-slot counter), it would report higher available space than physically usable. During the window before release_reclaim_holds runs, this could cause admission control to accept operations exceeding actual available space, such as allocating 90 slots when only 80 are physically available (20 held), leading to allocation failures when the system tries to use the held slots. This would prove the objection correct.
