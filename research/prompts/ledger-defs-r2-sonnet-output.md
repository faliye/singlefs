## 五、同批做法站得住的地方，与它自己的毛病

站得住（辩护）：

1. 步数少，见第六节表。段树做法里不少步骤是为修段树自己的毛病加的（核三棵树、合到一半退回、登记行抄两遍、段树寿命、修补重建段树）。
2. 同批做法没有的毛病：三棵树漂移、登记行落哪棵树、段树寿命与完工清理闸，表三前五条里的毛病它一条都没有。
3. 开着的三方轮的快照冲突早发现：补丁打进主工作区时查，「落在还没判完的三方轮的开工快照里就拒、退 2、一个字没改。」（`scripts/gate/apply-writer-patch.py:111`）；段树做法的写段打进段树时不查（「副本上不查（副本不是那一轮取快照的工作区）。」，`scripts/gate/apply-writer-patch.py:114`），要到合进主工作区那一刻、整套第 1、2 步都验完之后才发现。
4. 两份必须一起落的补丁可以并成一个补丁目录一起打，单个补丁目录是原子的（「要么整份写完、要么一个字不动」，`scripts/gate/apply-writer-patch.py:30`）。仓里手并补丁有先例：战役组补丁整份打不上，主 agent 拆开做，「补丁剔掉这一对两段另存」（`records/2026-11-05-删轻型并入重型.md:152`）。限制：没找到打之前把几份补丁目录并成一份的现成脚本；`scripts/gate/patch-of-the-current-tree.py` 能把几份补丁目录合成一份，但它的输入是「按此刻的主工作区现算」（那份脚本文件头第 4 行「按此刻的主工作区现算一份补丁目录」），补丁得已经在树上，用不到打之前。

它自己的毛病（对着 195 节事故，加上今天的脚本）：

1. 一批自洽没人核。打补丁之前的核只有变异锚点静态核（`--dry-run`，`scripts/gate/apply-writer-patch.py:62`），不编译；上表第三行就是自洽没人核的实例。
2. 有依赖的多批怎么办：前一批落地之后、后一批交回之前，主工作区就是「前一批的样子」。只有每个前缀都自洽时做法才成立；删接口这一类天然不自洽，要并批；并批又要后一批不依赖前一批的基线，而事故里的用例组恰恰依赖（上表第一行）。所以这种做法管得住的是「接口删、调用方改，两边互不依赖基线」的子集，管不住有依赖的多批，而「有依赖的」正是定义里写段第 2 条要处理的情形：「有依赖的：前一批实现员交回后，补丁只打不验」（`.claude/main-agent.md:47`）。
3. 验已打补丁的路径有摩擦：补丁已在主工作区时用 `--skip-apply` 验，倒着 `git apply --reverse` 核；补丁经三方合并打进去、或主工作区上另有别人的改动，倒不掉就退 1，出路另写（「补丁是三方合并打进去的、撤回了一半、或主工作区上另有别人的改动而倒不掉的，这两条走不通」，`scripts/gate/merge-and-verify.sh:130`），要先现算一份补丁目录再验。
4. 别的会话要起全量门禁时，主工作区带着没验过的补丁，没有「已收尾」可回：段树做法有这一句，因为补丁都在段树里（「写段的补丁都在段树里、主工作区里没有打了而没验过的补丁，直接回那个会话」，`.claude/main-agent.md:51`）。
5. 没有留底：仓里改前的老流程里 `copy-originals` 出现 0 次（`git show HEAD:.claude/main-agent.md`），某一份打坏了只能手工 `git apply -R`。

先例：同批做法在仓里的先例就是改前的老流程本身，它出了这一节的事故；除此没找到别处用同批做法并且验证过「每批自洽」的记录（找不到，不用别的理由顶替）。

**判断（辩方的，推出来的）：**

1. 「主 agent 要做几步」：同批做法更省。同一场景下不同命令 3 对 10、手写 3 对 9、修补路径 1 对 6；段树做法里不少步骤是为修它自己的毛病加的（表三前五条）。
2. 「哪几步出错会留下没验过的主工作区」：段树做法更省。它让主工作区只在一个窗口里被写，且有留底；同批做法在整个写段都让主工作区带着没验的补丁，只靠「每一批自洽」，而自洽无人核（表四第三行），有依赖的多批它管不住（第五节毛病 2）。
3. 账本给的目标句是「主工作区处在编不过或判不过的中间状态」那一种事态，账本要拦的就是它（`records/2026-10-29-subagent拆分提案.md:1059`）。以这一句为准，段树做法对事故那一批挡得住、同批做法挡不住（表四）；以步数为准，同批做法省。两者不同序，选哪一种是取舍，用户已经定了段树做法，这里只给两边的数。
4. 同批做法站得住的子集：接口删与调用方改互不依赖基线、能并成一个补丁目录一起打的，它零步数就挡住了这一类，且早发现快照冲突。现行定义对所有段一律建段树；写段第 1 条写明「没有依赖的同一条消息里同时派」（`.claude/main-agent.md:46`），无依赖的一段，补丁到合那一刻才落，段树对它只剩给第 2 步一个落脚处。线索（推的、没试）：这样的一段，第 2 步能否改在第 1 步留下的快照上起（脚本有「要留现场：MERGE_AND_VERIFY_KEEP_COPY=1，收尾不删」，`scripts/gate/merge-and-verify.sh:35`），省掉建段树、打进段树、删段树三步；需要核的是快照里门禁表与入口脚本是否齐，没核。交主 agent 判。

**什么现象会推翻这些判断：**

- 判断 1：实测按今天定义走一段，主 agent 的步骤数没有差到 3 对 10（例如批量打补丁与登记都有现成的合并脚本）。
- 判断 2：实测同批做法下几段实现，每批都自洽、主工作区从没被挡过；或实测段树做法步骤 3 的退 2 与登记手抄漏写经常发生，出错面不止 3 处。
- 判断 4 的线索：快照里缺门禁表，第 2 步起不来。

没量的：主工作区带半成品的时长、打补丁任务的排队时间、段树建树的耗时（两条腿各建过一次都退 0，合计 123.7 MiB，`research/prompts/ledger-defs-r1-sonnet-output.md:9`，那一条是它们的读数、不是我复跑的）。
