## 4. 降级之后的账：第 8/9 项改成「后台算一遍」，那一遍要算什么、代价多大

**先框定范围**：只对第 8、9 项降级，**第 12 项不降级**——它有第一格的真实消费者，必须继续
按事务提交增量维护（这本身也已经是已定项 4/E97 的现状：inode 号水位「随每次发布重写」，
`05-快照-空间记账机制.md:312`）。

**降级后台要算的东西，性质上等价于 E26（三种记账模型的查找代价与精度） 量过的那类计算**：
判定「一个块只被一个头引用（独占）还是被多个头引用（共享）」，需要对每个块核对它在多少个头/快照的
可达闭包里出现——这正是 E26 的 `refcount`/`deadlist` 查找臂在做的事，只是 E26 量的是**删除时**
单次查找次数，这里要的是**全池一次性**把每个块归类到某棵树的「独占」或「共享」桶里。

**能引用的数**（E26（三种记账模型的查找代价与精度），2026-08-29，64 快照×8 extent 玩具规模，三轮字节一致）：

| extent 总数 | 多可写头（D6 取的形态） | 精确引用计数 |
|---|---|---|
| 256 | 1 | 13 |
| 1024 | 17 | 52 |
| 4096 | 58 | 169 |
| 8192 | 213 | 379 |

log-log 斜率：多可写头 1.32，精确引用计数 0.95（`26-三种记账模型的查找代价与精度.md`）。

**这个数能证明什么、不能证明什么**：

- **能证明**：判定「独占/共享」这件事的算法复杂度量级——精确引用计数臂（最接近「后台算一遍」
  需要的语义）在这个玩具规模下**接近线性**（斜率 0.95），与做一次 I-3.1（已分配统计对得上）
  式的全盘遍历同一个量级，不是一个新的复杂度类。
- **不能证明**：真实盘上一次这样的后台扫描要多少墙钟时间——E26 正文自陈「一次反向索引查找值多少 I/O
  从未测过」「模型只跑到 8192 个 extent（真实规模的 1e-5 量级），按线性外推到 10⁸ 是外推不是实测」
  （`26-三种记账模型的查找代价与精度.md`「外推的限度」一节）。
- **不能直接搬用**：E26 量的是**删除单个块/单个快照那一刻**要付的查找次数，不是「把全池所有块的
  独占/共享状态都算一遍」这个批量操作的总代价——后者严格来说没有专门的实验量过，只能类比 I-3.1
  的全盘遍历（同样是「读一遍全部引用、按某个谓词分类」的形状），量级判定成立，绝对数字缺失。

**降级之后的调度纪律**：套 `fs-design.md` 第三格（后台、可续做、非决策路径，无戒律）的既有豁免先例——
D26 的整理、D5 自己「销毁快照落在第三格」的定案（`06-快照实现模型.md:19`）——降级只需要
「写意图 → 分批 → 可续做」这条通用要求，**不需要新开一条戒律**。代价是用户看到的「这个快照占了多少」
在两次后台扫描之间是**滞后**的，而这个滞后本身，按第 3 节的结论，需要等 pitfalls #12 那条「未决」
特性定案时一起定「滞后多久算可接受」——这是 `fs-design.md:27` 那句改动之后留下的一个新的待定项，
不是本轮能替它答的。

**缺的输入，明说**：没有任何实验量过「全池批量分类独占/共享」的绝对代价（I/O 次数或墙钟时间），
E13（D5 的四条风险路径）与 E26 都不覆盖这个操作——E13 覆盖的是 D5 机制本身的四条风险路径
（建快照边界、级联合并、崩溃重放、defer 持久化代价），不是「后台重算展示用统计量」这件事。
这是一个诚实的空白，不是能靠外推填的。

## 5. 算砍掉树维之后的收益——先纠正一处：能砍的不是整个树 ID 字段

### 5.1 假设性算式（key 真能砍掉树 ID 段时——本轮任务 5 原题，已被 0.1/2 节推翻其前提）

砍掉树 ID 段：`(标签 2, 设备 4, 代 8)` ⇒ key 14 字节、条目 22 字节。

**每条目省 8 字节，30 → 22，降 26.7%。** 这是本轮题目要的数，但如上所述，它不能实现，
因为第 12 项仍然要用满 22 字节的原 key 形态。

### 5.2 真实约束下能拿到的收益：条目数减少，条目宽度不变

**唯一能拿到的收益是「第 8、9 两项不再逐树、逐代各写一行」，条目数下降，key 宽度 22 字节不变。**

用 E71（记账 key 的条目数与宽度） 给的口径（窄读公式：带设备维 4 项 ×d + 带树维项 ×t + 无维项 ×1，
乘以代数 K），按现在 14 项统计量的分布（设备维 5 项：1/2/3/5/11；树维 3 项：8/9/12；无维 6 项：4/6/7/10/13/14）
重算一代的条目数：

```
一代条目数 = 5d + 3t + 6   （现状：8/9/12 都按树维算）
一代条目数 = 5d + 1t + 6   （降级后：8/9 移出，只剩第 12 项按树维算）
每代省下的条目数 = 2t
```

K 取 E71 示例用过的 25（`K = 根环槽总数+1`，`S=8` 时 `R×S+1=25`，`05-快照-空间记账机制.md:250-258`）：

| t（树数/快照数档位）| d=8 时现状条目数（×K=25）| 降级后条目数 | 省下的条目数 | 降幅 |
|---|---|---|---|---|
| 64 | (40+192+6)×25 = 5 950 | (40+64+6)×25 = 2 750 | 3 200 | 53.8% |
| 1 024（d=64）| (320+3072+6)×25 = 84 950 | (320+1024+6)×25 = 33 750 | 51 200 | 60.3% |
| 8 192（d=8）| (40+24576+6)×25 = 615 550 | (40+8192+6)×25 = 205 950 | 409 600 | 66.5% |

⇒ **快照/树数越多，省下的条目数占比越高**——这与本轮前提「条目数不再乘以快照数」的方向一致，
但幅度不是「全部两项归零后的理论上限」，因为第 12 项仍然按树数线性增长，降幅上限被它钉死在
「树维项从 3 降到 1」这个比例上，不是「从 3 降到 0」。

D6（快照实现模型） 已定项 1（每头一棵自己的树）与已定「快照标识不回收」（同文件已定项 2 附近，
`06-快照实现模型.md:110`）合起来意味着 **t 无上界**——这一点本轮前提写对了，
且它恰恰是「降幅随 t 变大」这张表要传达的东西：t 越没有上限，不砍这两项的代价越大。

**占容量 ppm**：E97（记账与分配记录的条目编码） 只给了**分配记录树**的 ppm（415–830 ppm 那组数，
`97-记账与分配记录的条目编码.md` 「分配记录树」一节），**没有对记账树本身算过 ppm**——
它的记账树一节只报条目数与树高，没有换算成占用比例。这是一个诚实的空白，
不许拿分配记录树的 ppm 挪用过来（口径不同：分配记录树按落点计，记账树按统计量×维度×代计）。
按 E97 判据 10（预算按脏节点算）的口径，能说的是：降级后每次 checkpoint 少写
`2 × (若该代恰好触及那两项的树数)` 个条目，对应少脏 `≤ 2t` 个 16 KiB 节点（COW 挂父指针下，
一条插入脏一整个节点，`97-记账与分配记录的条目编码.md` 判据 10），但脏节点数与条目数不是线性
一一对应（同一节点可能装多条），**这一步换算 E97 没有做过，此处不外推**。

## 6. 结论

**只在收窄口径下站得住，原题的口径站不住。**

逐条给判定：

1. **「树 ID 段只为第 8/9 两项存在」——站不住。** 05-快照-空间记账机制.md 自己的第 319 行已经
   写明 2026-09-05 之后是三项（8、9、12），第 12 项有一条已定案的运行时决策消费者
   （inode 号分配，08-核心索引结构.md:74/369，与 fs-design.md 对「运行时决策路径」的定义逐字对应）。
2. **「第 8/9 两项本身没有运行时决策消费者」——站得住**，第 2 节六条路径逐条查过，全部不要；
   且第 3 节查明它们唯一的消费者「快照用量」对应一个仍是「未决」状态的用户可见特性
   （pitfalls.md #12），不是任何已定判定。
3. **`fs-design.md:27` 总纲——该改，但改法要精确**：不是整句删掉「快照用量」，
   而是把「属于第一格」的判据从「是不是快照用量」换回它本来的定义——「有没有运行时决策消费」；
   第 12 项恰好证明了「树维统计量可以合法地属于第一格」，只是理由不是它叫快照用量，
   是它喂给了 inode 分配。这个改动是项目本地规则，改动成本低（0.2 节纠正）。
4. **key schema 缩短（22→14 字节）——不成立**：第 12 项钉住了树 ID 字段，
   D5 已定项 3/4 的「统一 key 形态、不按统计量分裂」硬约束下不能只为两项砍字段宽度。
5. **能拿到的真实收益是条目数下降，不是字段变窄**：第 8/9 两项降级为后台计算后，
   记账树每代条目数在 t=64/1024/8192 三档分别省 53.8%/60.3%/66.5%（d、K 取值见第 5 节），
   降幅随树数增长扩大，但上限被「三项砍成一项」（不是砍成零项）钉死。
6. **降级本身的代价缺一块实测**：降级后台要做的计算在复杂度量级上与 I-3.1 的全盘遍历同类
   （E26 的 refcount 臂在小规模下斜率 0.95，接近线性），但没有任何实验量过它在真实盘上的
   绝对代价（I/O 次数或墙钟时间）——这是需要另开一轮实验补的空白，不能用现有数字外推。
