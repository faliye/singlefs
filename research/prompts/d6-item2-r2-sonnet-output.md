## 1. 判据 1（枢纽）：D8 write buffer 硬要求 2 的射程罩不罩得到 livelist

**现查 `.claude/kb/decisions/08-核心索引结构.md`，射程句逐字：**

> 「层 | 做什么」表（7-16 行）：「**write buffer** 前端 | 高频小更新（反向索引、LRU、记账）批量攒起来排序去重后批量插入」

> 已定项 7（434-445 行）：「立在 D8（核心索引结构） 不立在 D5（快照 / 空间记账机制），因为 write buffer
> **覆盖「反向索引 / LRU / 记账」三类**，立在记账那边会让另外两棵树各自重问一遍。」

> 同一节 442 行：「② **射程从记账树扩到三棵 write buffer 树（记账 / 反向索引 / LRU）**，一棵树一套条目格式、三棵同宽。」

**判定：罩不到。** 这三处逐字都把 write buffer 的覆盖面写成**三个具体名字**（反向索引 / LRU / 记账），
不是"所有走 write buffer 逻辑上合适的树"，更不是"所有树"。硬要求 2、3 挂在
`### write buffer 的三条硬要求` 这个标题下——它们是**这个前端机制本身的准入条件**
（任何树选择走 write buffer 就必须满足这三条），但"livelist 走不走 write buffer"
本身是一个**还没有人做出的决定**：甲′把"走 write buffer"直接写进了候选的定义里
（材料第 13 行「走 write buffer，因而条目自带 seq」），这是把"要不要走"和
"走了之后必须怎样"这两件事合并成了一句话，读起来像是硬要求 2 直接管到了 livelist，
其实是**候选自己先做了"走"这个决定，再引用硬要求 2 来说明走了之后该长什么样**。

**这不是说甲′的结论错了**——下面会看到，E130 的实测（理由二）**独立地**、不依赖硬要求 2 的射程，
就已经把 livelist 逼成了幂等完整值形态。硬要求 2 更像是"这个形态与本工程已有的一条设计纪律吻合"的
**佐证**，不是"这个形态是硬要求 2 直接推出来的"**因果**。材料理由一的表述（"两条独立理由"）
掩盖了这一点：理由一其实不独立于"livelist 要不要走 write buffer"这个未决问题。

## 2. 判据 2：若 livelist 不走 write buffer，代价是什么

**不走的代价**：ALLOC 与 FREE 是本工程里除数据写入本身外最高频的元数据更新之一
（每次分配、每次释放各触发一次）。不走 write buffer 意味着每一次 ALLOC/FREE
都是一次**同步的、单条的树插入 / 删除**——COW 该叶与全部祖先节点、拿写锁、参与该次
发布——而不能像 write buffer 那样把一个窗口内的多条更新在内存里排序去重后**一次
flush 摊掉插入代价**。D8 的"结构"表把 write buffer 存在的理由写得很直接：
「高频小更新……批量攒起来排序去重后批量插入」，livelist 的写入模式（每个块的
ALLOC 一次、FREE 一次，且 E130 的 `churn` 参数显示同一个头短期内可能对同一批块
反复分配/释放）正是这个描述的字面例子。

**量级**：E130 的 `naive` 臂本身就是"不做任何折叠、每次操作都追加"的极端，
产物 `n=65536 churn=16` 给出 `entries=2162688`——**33 万次 ALLOC/FREE 操作对应
33 万次潜在的树写**，若都各自同步插入而不经过任何批量前端，代价与用户写路径本身
（同样高频）量级相当。D8 已定项 7/E17（write buffer 合并上限） 给出的参照：单线程
write buffer 排序合并 30.9–31.8M 条目/秒，而**不经过它、每条都单独走一次 COW 树插入**，
没有任何实验直接测过这个代价——这是材料自己承认的空白（C258（销毁可写头这条路径的代价一个数都没有）），
我在这里同样给不出实测数字，只能给出机制性论证：直接插入没有"排序去重"这一步能吃掉
churn 场景下 ALLOC 紧跟 FREE 相互抵消的那部分写（E130 的 `condense` 臂正是靠这一步
把 entries 压到 `net_alloc`），不走 write buffer 就没有这个免费的抵消，**churn 越高代价差距越大**。

## 3. 判据 3：甲′的集合表示丢不丢信息

**构造（带具体 txg 与落点）**：

- 头 H 在 `txg=100` 从 origin 分叉（`H.prev_snap_txg = 100`）。
- `txg=150`，H 写一个新块 B，落点 `(dev=2, slot=5000)`，出生代 150（150 > 100，H 自己出生的活块，
  进 H 的 livelist：`key=(H.树ID, 2, 5000)`）。
- `txg=200`，对 H 打快照 S1。按 D5（快照 / 空间记账机制） 的机制：H 的 `prev_snap_txg` 更新为 200，
  H 的 deadlist 整个交给 S1，H 换一个空 deadlist。
- `txg=250`，H 覆写 B（COW），新块 B′ 落 `(dev=2, slot=6000)`。B 现在从 H 当前视角看"死"了，
  但 **S1（`txg=200` 建，晚于 B 的出生 `txg=150`）仍然引用着 B**。

**问题**：甲′字面写的"释放就是删 key"，若在 `txg=250` 这次覆写时不加任何判断、直接
`delete key=(H.树ID,2,5000)`，就会把一个**仍被 S1 引用的块**当成"H 的私有块已死"处理——
这正是 ZFS 用 ALLOC/FREE 配对 + birth txg 分组要防的那类错误：ZFS 的 livelist 处理逻辑
在 condense/destroy 时会按 birth txg 与快照边界比对，只有"出生在上一个快照之后"的 FREE
才真正释放，否则要把这次 FREE 转成对 deadlist 的记账。**甲′的裸 key-presence 形式，
按字面定义（"key 在=活块，释放就是删 key"）没有这一步判断，会把 B 错误地当作可释放**——
这是丢信息，丢的是"这个块的出生代相对上一次快照的位置"。

**谁在消费**：写路径的 FREE 处理逻辑（决定一次释放是"真释放"还是"转入 deadlist"）；
下游是 D5 的 `I-3.1`（已分配统计对得上）与 deadlist 的正确性——错了要么提前回收了
仍被快照引用的块（破坏快照不可变性、数据损坏），要么反过来永久泄漏。

**修法不需要改字段表**：H 已经在树表条目里持有 `prev_snap_txg`（D8 已定项 8③），
被释放的块自己的出生代按 fs-design.md「元数据块必须自描述」的纪律本就写在块头里
（对象出生代 / birth txg，D8 已定项 6 的 inode 记录字段表与 D18 的单元头都有先例）。
FREE 处理只需要在删 livelist key 之前多判一句：

```
if birth_txg(块) > H.prev_snap_txg:
    delete key=(H.树ID, dev, slot)   // 真正私有，从未被任何快照看到过，可以真删
else:
    改走 deadlist 路径，不删 livelist key（或先删livelist key、同一事务里给deadlist加一条）
```

**结论**：甲′的集合表示**不必然丢信息**，但材料给出的定义句本身（"释放就是删 key"）
**低估了释放这个动作的复杂度**——它字面描述的实现是错的，正确实现需要外挂一条判据，
这条判据不改变 livelist 自己的字段表（`prev_snap_txg` 与块的出生代都已经在别处有落点），
但**必须写进 livelist 的正式定义里**，否则下一个实现的人会照字面写出一个会丢数据的版本。
这是我与甲′的第二处分歧：**甲′需要打这个补丁才算完整**。

## 4. 判据 4：key 以头的树 ID 打头，有没有反面

**好处**（材料已给）：销毁一个头变成范围操作，可整节点丢弃。

**反面**（三处，按判据表要求逐一给）：

1. **点查局部性差**：若要回答"这个具体物理落点 `(dev, slot)` 现在被哪个头的 livelist 占着"，
   treeID 打头意味着不知道头 ID 就无法直接定位，只能遍历所有头前缀或依赖块头自描述的
   出生树字段反查（后者可行，但意味着 livelist 本身不是这个问题的权威入口）。
2. **头内插入不连续**：一个头的 ALLOC 在时间上大致递增，但落点 `(dev, slot)` 由分配器
   决定、与时间无关联（不像 inode 树那样"插入永远落在最右叶"）。同一个头的 key 范围内部，
   插入位置基本随机分布，会比"槽号打头"的编码触发更多节点内重排——虽然仍被限制在该头
   自己的 key 子范围内，不会波及别的头。
3. **与物理局部性维度抢排序权**：treeID 打头之后，(dev, slot) 退化为次级排序键，
   同一物理区域的落点若分属不同头会在 key 序上分散——任何想按物理顺序做批量校验/scrub
   的操作在 livelist 这棵树上得不到局部性收益。**这与 D8 已定项 3 讨论"全路径索引 vs
   locality 前缀"是同一种权衡**：为了让"一起死的东西挨在一起"，牺牲了另一种局部性。

## 5. 判据 5：这棵树第一个事务建不建

**不建。惰性，在第一次克隆时创建。** 依据：

- livelist 只track "头自己出生、且从未被本头任何快照引用过的活块"。mkfs 出的第一个
  （也是唯一的）头没有 origin、没有分叉点，**它的"own()"集合这个概念本身不成立**
  （E130 的 `Load.own()` = `n - inherited`，`inherited` 是"从 origin 继承的块数"——
  第一个头没有 origin，谈不上继承与否）。第一个事务不产生任何需要进 livelist 的条目，
  这与 D26 未定项 5「第一个可运行目标无快照 ⇒ 逐字节相同」对**条目**成立的先例一致
  ——材料自己也引了这条先例，但同时提醒"对结构本身要不要 day-1 存在不成立"，
  这里我给出的是对**结构存在性**的独立判断：不存在的理由不是抄先例，是这棵树在
  没有克隆之前**没有东西可装**。

- **树表条目**：第一次克隆发生时，才为 livelist 分配一条 D8 已定项 8 的 121 字节
  树表条目（长度2+种类2+flags2+树ID8+根指针59+`prev_snap_txg`8+诞生txg8+预留32）。
  注意这里的"树 ID"字段指的是 livelist 这棵**共享树自己**的 ID（它作为一个独立
  keyspace 挂进树表），跟 key 里"头的树 ID"（引用被记录的那个头）是两个不同的数——
  材料把 livelist 写成"一棵独立 keyspace 的 btree"（单数），我认为这是正确读法
  （见判据 6 之前的补充说明），而不是"每头一份"字面意义上的每头一棵独立 B 树；
  后者会导致每次克隆都要新开一条树表条目、消耗 D8 已定项 8 算出的 134 棵/层配额，
  而"一棵共享树、key 里带头 ID 做前缀"只在**第一次克隆**时消耗一条树表条目，此后
  任意多个头共用同一棵树、同一条树表条目。

- **树 ID 水位**：跟任何新建的树一样，走 D8 已定项 8②"取根环里全部根记录该字段的 max"
  这条通用机制，livelist 树的 ID 在它第一次被创建（第一次克隆）那次发布中被分配、
  水位随之推进，不需要为它单独开一条特殊规则。

- **扫描重建**：livelist 的内容原则上可以从单元自描述重建——每个数据单元头部若带出生树
  字段（D8 已定项 6 的先例：inode 容器身份三元组含"出生树"），扫描全盘收集
  "出生树 = 该头的树 ID ∧ 现行版本 ∧ 出生代 > 该头 `prev_snap_txg`" 的单元即可重建
  livelist 的内容。**这意味着 livelist 本质上可以是派生态**（丢了能从单元重建，
  代价是一次全盘扫描），但运行时销毁路径**不能靠这条重建路径**——D6 判据 5 明确要求
  "有界销毁"，扫描重建只能是崩溃恢复/工具补救手段，不能是常规销毁路径。这一点材料
  没有讨论，是我在判据 5 范围内补的一条：它影响 D15（格式冻结政策） 的分层（livelist
  的载荷布局若走派生态那一层，格式冻结压力比权威态小），但不改变"第一个事务不建"
  这个结论。

## 6. 判据 6：甲′与 D5 稀疏旁表该不该是同一棵树

**不该，两者内容不相交。** 现查 D5（快照 / 空间记账机制） 未定项 6 原文（材料已整段引，
逐字核对无误）：「D5（快照 / 空间记账机制）为主 + 稀疏旁表为辅（ZFS 的 BRT 形态）……
旁表只装有 ≥2 个活引用的块，而克隆自己出生的那批块绝大多数引用计数是 1，根本不在表里。」

livelist 的成员判据是"该头自己出生的活块"，等价于"引用计数恰为 1 且引用者是这个头"；
旁表的成员判据是"活引用数 ≥ 2"。**这两个集合在正常情况下不相交**：一个块要么被
恰好一个头引用（在 livelist 里），要么被两个或更多引用（在旁表里），一个块同一时刻
不能同时满足两条判据。维护触发条件也不同——livelist 只在**这个头自己**分配/释放
自己的块时更新；旁表要在**任何**引用它的头/快照做出让它的引用计数跨越 1↔2 边界的
操作时更新（例如另一个克隆头第一次也引用了这个块，或者最后一个"多余"的引用者被销毁，
引用数从 2 降到 1，这个块从旁表移出、进入某个头的 livelist——这个移动本身值得单独记一笔，
但那是旁表与 livelist 交接协议的问题，不是"该不该合并成一棵树"的问题）。把两者塞进
同一棵树等于把两类不同判据、不同维护者、不同消费者的内容混进一个 keyspace，
正是 `.claude/rules/fs-design.md` 代码示例里标 ✗ 的"参数化布局"形态的数据版本。

## 结果反过来我接不接受

材料第 0 节写的"若甲′不成立，就要立一条 D8 硬要2 与 D5 livelist 形态互斥的新格"——
**我的结论不触发这一条**：我没有推出"甲′不成立"，我推出的是"甲′在两处需要修正

| **entry 合计（走 write buffer）** | **22** | 18 + 4 |
| **entry 合计（不走 write buffer）** | **18** | 无 seq；代价见判据 2 |

**width 校验（骑手条件是否满足）**：`T_dirty` = 2 GiB（与记账树共用同一个可调值，D16（发布语义） 已定项 5）；
livelist 条目 22 字节 ⇒ 一个 flush 周期内最多缓冲 `2×2^30 / 22 ≈ 97 620 723` 条 ⇒ 需要
`⌈log2(97620723)⌉ = 27` 位，与记账树的 27 位下界同阶（不是因为"代在 key 里"，是因为
两者的 `T_dirty`/条目宽比值恰好接近）。**4 字节（32 位）覆盖 27 位，骑手条件在数值上满足**，
但材料没有写出这一步验证——它只是"继承"了记账树的 4 字节，没有为 livelist 自己重新算一遍。
这正是已定项 7 那句"这条骑手要在它们的 key 布局定案时兑现"要求的动作，我在这里补做。

⚠️ **livelist 不含"代"字段这件事本身没有留下后遗症**：seq 的唯一职责是消解"同一个 key
在同一个未 flush 窗口内被写多次"的顺序歧义（judgment 1 已论证这与 key 是否含代无关，
只与"同一窗口内会不会重复命中同一 key"有关，而 churn 场景下会，所以 seq 仍然需要）；
一旦 flush 落盘，树的覆盖写语义本身保证"后写覆盖先写"，不需要 seq 参与跨 flush 周期的比较。

# 4. 条目数与占容量

**口径**：照 D3（空间分配） 已定项 7 的基线，16 TiB 设备、90% 填充。

2^44 字节 / 2^14 字节每槽 = 2^30 = **1 073 741 824** 个 16 KiB 槽。
90% 填充 ⇒ `1073741824 × 0.9 = 966367641.6` → **966 367 641** 个已分配槽
（与 D3（空间分配） 已定项 7 正文给"一条记一个 16 KiB 槽"候选时引用的 **966 367 641** 逐位一致，
交叉验证口径没有算错）。

**条目数上界**：livelist 的成员是"引用计数恰为 1 的活块"（判据 6 推出的等价刻画），
不同头的 livelist 之间不相交、且与 D5 稀疏旁表（引用计数 ≥2）不相交，
⇒ **全池所有头的 livelist 条目数之和 ≤ 已分配槽数**（等号只在"没有任何块被共享，
即没有克隆、或所有克隆都还没做过任何写时复制"这个极端下取到，是真正的最坏情形，
不是期望值——仓里没有任何工作负载假设能给出更紧的期望值，所以这里只报上界，
不报"典型值"）：

**条目数上界 ≤ 966 367 641**

**占容量（走 write buffer，22 字节/条）**：

```
966367641 × 22 = 21 260 088 102 字节
21 260 088 102 / (16 × 2^40) = 21 260 088 102 / 17 592 186 044 416
                              ≈ 1.2086 × 10⁻³ ⇒ 约 1209 ppm
```

**占容量（不走 write buffer，18 字节/条）**：

```
966367641 × 18 = 17 394 617 538 字节
17 394 617 538 / 17 592 186 044 416 ≈ 9.888 × 10⁻⁴ ⇒ 约 989 ppm
```

**对照**：D3（空间分配） 已定项 7 同一基线下分配记录树占 **442 ppm**（483 183 820 条、
含跨度合并）；D5（快照 / 空间记账机制） 已定项 5 的记账树在三档容量下都是同一个绝对条目数
（不随容量走）。livelist 的这两个 ppm 数字都是**极端上界**（假设全池块都是某个头的私有块），
不是期望占用；**仓里目前没有任何依据能给出比这更紧的期望值**——这本身也是一条要还的账，
留给欠账清单，我不在这里编一个负载假设。

# 5. 材料本身的错误

## 5.1（较重）：E130 的 `ALLOC_REC_BYTES` 常量与它自称依据的 D3 已定项 7 不符

`research/e7-index-bench/src/bin/e130_livelist_bounded_destroy.rs` 第 28-29 行注释写
「一条分配记录条目的盘上宽度。D3（空间分配） 已定项 7。」`const ALLOC_REC_BYTES: u64 = 30;`，
第 20-21 行头注释进一步写「分配记录条目 30 字节（D3 已定项 7 与 D5 已定项 5 同宽口径）」。

**现查 D3（空间分配） 已定项 7 的字段表**（`.claude/kb/decisions/03-空间分配.md:210-215`，逐字）：

> 设备身份 4 + 落点 6 + 跨度段（含已释放标志位）2 + 分配代/释放代 8

**逐段相加 = 4+6+2+8 = 20，不是 30。** 30 字节实际是 D5（快照 / 空间记账机制） 已定项 5
的记账 entry 宽度（`(统计量标签2, 树ID8, 设备4, 代8)` = key 22 + value 8 = **30**），
D3（空间分配） 已定项 7 从未在任何地方给出过 30 这个数。E130 自己的单测
`assert_eq!(ALLOC_REC_BYTES + 0, 22 + 8)`（源码 492-493 行）等于是在**自证它用的其实是
D5 的记账宽度**，却在注释里同时挂 D3（空间分配） 的名字、写"同宽口径"——两棵树的宽度
（20 vs 30）**并不相同**，"同宽口径"这句表述本身站不住。

**影响**：E130 判据 1 的产物 `worst_batch_bytes=221184 = 4096×(30+24)`——若按
D3（空间分配） 已定项 7 真实的 20 字节算，应为 `4096×(20+24)=180224`，与产物报的数字不同。
这不影响"甲过判据 1"这个**方向性**结论（判据 1 只要求"只随批大小走"，用哪个常数都成立），
但**具体数值不可信**，任何下游想引用 `221184` 这个字节数做进一步推算都会带着这个错误。
落点：这是 E130 装置内部的一处常量取值错误，不在 kb 决策正文里，但材料的"理由二"直接
把 E130 的产物当证据引用，继承了这个错误而没有发现——我核对宽度坐标系时才发现。

## 5.2：`LIVELIST_ENTRY_BYTES`（24 字节）与甲′的字段表不是同一个东西

E130 用 `类型标签2 + 位置条目14(含密文校验和) + birth_txg8 = 24` 字节建模 livelist 条目，
这是一个"ALLOC/FREE 事件记录"形态（需要类型标签区分 ALLOC/FREE、需要 birth txg 支持
按代分组/condense）；而材料的甲′字段是 `树ID8 + 设备4 + 槽号6`（key，不含校验和）+
可能的 seq（value），**没有类型标签、没有 birth txg、没有密文校验和**。两者结构不同、
宽度也不同（24 vs 我推出的 18/22）。**E130 的产物验证的是"idempotent/条件方向 vs Δ流
方向"这个机制选择，不是甲′这个具体字段表**——材料第二节没有点出这一层区别，
读者容易把 E130 的数字直接当成甲′的字节代价来引用（比如材料判据 6 那行的
`free_path_extra_bytes=24` 实际来自这个 24 字节的事件记录模型，不是甲′的 22 字节
key+seq 模型）。这不是错误，是一个需要显式说明的**模型-候选不对齐**，我在字段表一节
已经用仓里坐标系重新推了一遍，与 E130 的数字区分开。

## 5.3（较轻）："一棵" 与 "每头一份" 的措辞张力

D6（快照实现模型） 未定项 2 原文把甲描述为"独立 livelist（**ZFS 形态，每头一份**）"，
材料把甲′写成"**一棵**独立 keyspace 的 btree"（单数）。字面上"每头一份"更像
"每个头一棵独立的树"，材料给的具体 key 定义（`头的树ID` 作为 key 第一段）却只有
**一棵共享树**才需要这个字段——如果真是"每头一份"（每头一棵独立小树），树内部
根本不需要再存一遍"这是哪个头"，因为那本身就是这棵树的身份。材料没有显式说明
这个转写（"每头一份"→"一棵共享树、按头分区"），判据 5 我按"一棵共享树"处理并给出了理由
（避免每次克隆消耗一条树表条目），但这个转写本该在材料里写明，不该留给读的人自己猜。
