Q1. Head H1 cloned at txg 100. At txg 150 H1 writes block B with birth txg 150. At txg 200 snapshot S of H1 is taken so H1's prev_snap_txg becomes 200. At txg 250 H2 is cloned from S so H2's origin txg is 200 and prev_snap_txg is 200. H2 references B. At txg 300 H1 is destroyed. The PER HEAD LIVELIST proposal uses birth > origin txg (100) as the boundary. B's birth 150 > 100 so it is released from H1's livelist. But H2 still references B. This causes H2 to point to a freed block. The correct boundary should be prev_snap_txg (200) where 150 <= 200 so B should not be released. The proposal's use of origin txg instead of prev_snap_txg causes premature release of a block still in use by H2.

Q2. When snapshot S of H1 is taken at txg 200, H1's livelist remains with H1. Supposelease: H1 writes block B at txg 150 (birth 150). At txg 200 snapshot S is taken. H1's prev_snap_txg becomes 200. The livelist for H1 contains an alloc entry for B (birth 150). If the proposal keeps the livelist entries with birth <= prev_snap_txg (150 <= 200), destroying H1 later will check birth > prev_snap_txg (200). 150 <= 200 so B is not released. This is correct. The only issue is wasted space in the livelist tree for entries that will never be released. No wrong release or leak occurs. The entries with birth <= prev_snap_txg are harmless but occupy space in the livelist tree.

Q3. H1 is destroyed as an intent. Livelist has two entries: B1 (birth 150) and B2 (birth 200). Intent commits first batch freeing B1 but crashes before removing B1 from the livelist or marking it processed. On recovery, the intent re-runs. The livelist still shows B1 as unprocessed so it frees B1 again. This is a double-free. Fact 8 requires idempotent reprocessing but the system lacks a mechanism to track processed entries (e.g. no flag or removal from livelist during processing). Thus B1 is released twice.

Q4. H1 writes block B at txg 150. The livelist adds an alloc entry. The counter in the livelist tree's tree table entry is incremented from 0 to 1 in memory but not persisted to disk. System crashes. On restart the counter in the tree table entry is 0 but the livelist has one entry. Published state: counter=0 actual entries=1. No check detects this because the counter is only updated in memory and not validated against the livelist during normal operation. During destruction the system would process 0 entries instead of 1 causing B to leak.

Q5. Parent pointer carries no birth txg. When recording a FREE in the livelist the birth txg must be read from the block's own metadata. When destroying the head comparing birth with boundary requires reading each block's metadata to get birth txg. For example destroying H1 with 1000 blocks in livelist requires 1000 disk reads to fetch each block's birth txg. This is not O(1) per block as claimed. The proof of O(1) rests on reading only the parent pointer's field but without that field the system must read the block's data which is a disk operation per block. This causes high I/O cost during destruction.
