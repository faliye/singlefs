# 背景材料：D18 已定项 3 重开——加密开启时数据单元的身份段该放明文还是密文

**这份材料里每一条外部事实，提问者已在 2026-09-07 当天现查过一遍**（逐条标了出处）。
拿它当前提之前请注意：材料里的错误会被所有腿一起继承。

## 一、要定的那件事

singlefs 是从零设计的 COW 文件系统，还没有磁盘格式实现，格式仍是软的。
盘上每个「单元」（32768 B 数据 / 16384 B 元数据）自带一个头。

2026-09-07 用户定案：**加密开启时块头泄漏的那一面不接受，要解决。**
被点名的泄漏是数据单元（单元类登记表的码 1）明文头里的那 33 字节五元组。

## 二、今天的字段表（D18 已定项 7 逐字，105 字节）

共同明文前缀 42 字节：

| 字段 | 宽 |
|---|---|
| magic | 4 |
| 格式版本 | 2 |
| flags（偏移 6 = 单元类型标签，偏移 7 = 8 个 flag 位，第一版恒 0） | 2 |
| 声明长度 | 2 |
| 头校验和 | 32 |

数据单元的类身份段 63 字节：

| 字段 | 宽 | 干什么用 |
|---|---|---|
| 五元组 =（单元类型标签 1, 树 ID 8, 对象 ID 8, 对象出生代 8, 锚点偏移 8） | 33 | 扫描重建时认领这个单元属于谁 |
| 诞生代号（birth txg） | 8 | 三条理由：kill 规则的输入、孤儿单元判别、扫描方向独立判 I-1.2 |
| fsid | 8 | 挡错向写、挡「本卷 extent 里嵌着另一卷镜像」 |
| 写序（实例代号 4 + 事务号低 48 位） | 10 | 同 key 已发布版本定序、分辨崩溃前后时间线 |
| 载荷 CRC | 4 | CRC32C，覆盖从头末尾到单元末尾 |

**索引节点（码 2）和打包记录单元（码 3）不一样**：不变量 I-6.2 逐字——
「元数据类仅共同前缀而已（五元组 / key 区间等身份字段一律进密文）；
数据单元类另许 {五元组 / 诞生代号 / fsid / 写序 / 载荷 CRC}（D18 已定项 3 的知情泄漏面）」。
⇒ **「加密开启后身份段进密文」这套机制在本工程已经存在并已定案，只是码 1 被豁免在外。**

D18 已定项 7 同一张表逐字：头校验和「加密开启后对元数据类只罩明文部分，
类身份段的完整性转由 MAC 承担」。

## 三、泄漏了什么

加密开启、攻击者拿到裸盘、没有密钥时，从码 1 的明文头可读出：
每个数据单元属于哪棵树、哪个对象、对象的出生代、以及它在对象内的锚点偏移。
⇒ **锚点偏移直接给出文件大小与文件洞**；对象 ID 的分布给出文件数量与每文件块数。

## 四、挡在路上的那条已定条款（这是难点）

D9 已定项 6 定案：**AAD =（单元类型标签, 树 ID, 对象 ID, 对象出生代, 锚点偏移）**，
定长定序的规范编码，物理落点一律不进。**AAD 的字段组成是 day-1 永久契约，改一次就是一次格式断裂。**

同一项里那条最硬的规矩（原文称「D9 最硬的一条」，代号 A6）：

> AAD 每个字段的期望值只许来自 ① 读者的查找路径，或 ② 已被上一级 MAC 认证的密文侧字段。
> 一律不许来自明文侧，也不许从指针里读回来。

D9 自陈「这条不成立则三条命题全部崩塌」。

⇒ **五元组既是明文头里的泄漏源，又正好是 AAD 本身。** 把它挪进密文，
重建路径（索引没了、没有查找路径、没有上一级）就变成：要 AAD 才验得了 MAC，
而 AAD 只能从这个单元自己的密文里解出来——先有鸡还是先有蛋。

D18 已定项 3 自己已经登记了这个冲突（逐字）：常规读路径上明文头不参与、
不被认证；重建路径上明文头必须参与，而那与 A6 直接冲突。

## 五、两条相关的已定事实

- **D9 已定项 5（2026-09-07 用户定案改取）**：加密开启时无密钥的一侧**只读只检测**，
  不搬、不疏散、不回收；它能做到的逐字是「检测损坏、报告坏块」。
  不设明文映射层、不设明文反向索引 ⇒ **今天盘上的明文只剩超级块与单元头。**
- **E28（2026-08-29 实测，三轮字节一致）**：删掉明文映射层、只扫单元头做重建时，
  元数据侧一条不缺一条不错，**数据块侧缺口恰等于数据块总数**
  （1024 元数据 + 4096 数据块 ⇒ 重建出 1024 条、缺 4096 条）；
  阳性对照：给数据块加上自描述之后缺口归零。

## 六、一条现查过的外部事实

Linux 的 ChaCha20-Poly1305 在解密方向上**先解密、后验签**：
`/home/fy5090/kbuild/linux-om/crypto/chacha20poly1305.c` 第 99–128 行，
`chacha_decrypt()` 跑完把控制权交给第 127 行的 `poly_verify_tag()`，
后者在第 89 行才做 `crypto_memneq` 比对（2026-09-07 现查本机源码树）。
⇒ 明文在验签之前就已经在缓冲区里了；tag 覆盖的是 AAD 与密文，解密本身不吃 AAD。
⚠️ **这条只说明实现顺序如此，不构成「用未验证的明文去构造 AAD 是安全的」**——
那一步要单独论证，它正是本轮要问的。
⚠️ 别家实现怎么做是线索不是证据：本工程的判据不能是「Linux 这么做所以对」。

## 七、四条臂（跑论证之前写死，不许事后加减）

| 臂 | 形态 |
|---|---|
| **甲｜原样不动** | 保持今天的 105 字节明文头。基线对照臂，用户已判泄漏不接受 |
| **乙｜身份段进密文 + 重建先解密后验** | 码 1 的明文白名单收成 {共同前缀 + fsid + 载荷 CRC}，五元组 / 诞生代号 / 写序进密文（**位置与宽度不动，只是内容变成密文**，总宽仍 105）。重建路径改成「先解密取出候选身份 → 用它当 AAD 复算 MAC → 验过才采信」，A6 相应开第三条来源 |
| **丙｜明文留一个密钥派生的分组标签** | 五元组进密文，明文另留 8 字节 H = KDF(密钥, 五元组) 截断值。无密钥侧算不出 H，只能做等值比较 |
| **丁｜加密开启时不带身份段** | 码 1 在加密开启时不写身份段，重建接受降级（E28 量出的缺口 = 全部数据块） |

## 八、判据（跑论证之前写死）

按下列顺序字典序比较，靠前的关不许输：

1. 加密开启时，无密钥一侧还读不读得出「哪些单元属于同一个对象」「对象有多大」
2. 密钥在场时，扫描重建还能不能把数据单元认领回去（E28 的缺口是不是仍为 0）
3. 无密钥 scrub 还验不验得动（D9 已定项 5 承诺的「检测损坏、报告坏块」）
4. 动了几条已定条款，其中有没有 day-1 永久契约
5. 字段宽度变不变（变了要重算四个实验，欠账 C89）
6. 新增几个机制
