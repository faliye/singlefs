## 1. 挂载自举次序（逐步写出，每步注明需要哪些量、住在哪）

口径：本节答的是**正常挂载**（root ring 完好）。灾难恢复（root ring 整体丢失）是另一个问题，见本节末尾的范围说明。

⚠️ **范围说明（本轮不判，仅指出提问边界）**：`research/prompts/sb-treetable-local-output.md` 第 1、3 条把「根环整体损坏 / 丢失」下的离线抢救场景当成需要超级块树表指针的理由。这类场景不属于「挂载自举次序」这一问——它问的是正常挂载（root ring 完好）的读依赖顺序，上表已穷举。root ring **整体**丢失已经超出 D22（单元原子性怎么合成） 已定项 2「根环深度是块重用延迟的上界」covers 的范围，落在项目 `CLAUDE.md`「没有 oracle」与 `.claude/rules/fs-design.md`「元数据块必须自描述」（`fs-design.md:46-49`：「任何一个块单独捡起来，都要能回答『我是谁、我属于谁、我是第几代』。这是『全盘扫描重建』在物理上可能的前提」）划定的最后一道恢复手段里——即便超级块留了一份树表指针，它在「root ring 整体丢失」这种灾难下**同样可能是陈旧的**（它对应的那次 checkpoint 是否是最后一次成功发布，本身就是 root ring 要回答的问题），不能替代全盘扫描重建，这条不属于本轮四问的判据，留给主 agent 核实。

## 2. 树表的权威归属：本代 checkpoint 的状态，不是池级常量

**D22（单元原子性怎么合成） 已定项 7 逐字**（`22-单元原子性怎么合成.md:463`）：
> 根记录恒走间接层：固定头 + 一条指向「树表单元」的指针，树根一律住树表单元，不平铺进根槽。

**D21（权威态与派生态的分界） 开篇的「根」这一格定义，逐字**（`.claude/kb/decisions/21-权威态与派生态的分界.md:10`）：
> 「根」这一格含它的间接层（2026-09-05，随 C113（扫描重建时多版单元的现行版本判定无输入） 定案 P2）：根记录 + 树表单元 + 实例表单元——三者都是 I-7.2（最新根可完整遍历） 从 checkpoint 树根指针出发要走过的结构，不是索引，丢了就丢数据。

**D8（核心索引结构） 已定项 8 ② 逐字**（`08-核心索引结构.md:465`）：
> 树 ID 水位住根记录，取根环里全部根记录该字段的 max（2026-09-06 用户定案；同日先定「住超级块取 max + 区段预留」，当日重比三条臂后重开，见变更史）。逐字形态： `新水位 = max(根环里全部根记录的该字段, 本次 checkpoint 发出的最高树 ID + 1)`，**每次发布随根记录重写**。

**判据**：

1. D21 明写树表单元的入口路径是「**从 checkpoint 树根指针出发**」，且把它与根记录、实例表单元一并划进「根」这一格（权威态），不是索引（派生态）。它的权威性定义本身就绑定在「当前 checkpoint 的根记录」上，不是一个独立于 checkpoint、池级固定的对象。
2. 已定项 7 自陈机制代价「间接层的代价是**每次发布**多 COW 一个树表单元」（`22-单元原子性怎么合成.md:471`）——树表单元随每次发布（只要有树变动）产生新版本，与根记录同生命周期，不是 mkfs 写一次后不变的池级常量。
3. 紧邻的同类量——树 ID 水位——D8（核心索引结构） 已定项 8 ② 把它钉在根记录、并明写「每次发布随根记录重写」，回退语境下取「根环里全部根记录该字段的 max」。这是本工程对「随 checkpoint 变化、且要在回退时正确处理」这类量的既定处理模式，树表指针与它是同一种量（都是根记录固定头里、每次发布可能变化的字段），没有理由套用不同模式。

**结论**：树表的权威归属是**本代 checkpoint 的状态**，唯一权威路径是「根环 → 择新根记录 → 树表单元指针」。它不是池级常量。

## 3. 若超级块也带一条树表指针，会发生什么

**先答要不要跟着改**：要。已定项 7 明写树表单元「每次发布多 COW 一个」（`22-单元原子性怎么合成.md:471`），只要一次发布改动了任何一棵树（几乎每次 checkpoint 都会，见 D25（目标负载优先级） 常识负载），树表单元就有新版本；超级块若也持有指针，不跟着改就是持有一份陈旧指针。

**与 D22（单元原子性怎么合成） 已定项 8 的槽轮换互动**：

已定项 8 定的超级块更新机制（`22-单元原子性怎么合成.md:509-514`）是「每盘一份……怎么更新它按已定三办……做成槽轮换，每盘至少 2 个槽」——这与根环的槽轮换（已定项 2）是**两个独立的环**，各自的代号体系不通用（超级块自己的世代号 vs 根环的实例代号 + `checkpoint_txg`）。要让「超级块里的树表指针版本」与「当前根记录里的树表指针版本」保持一致，超级块的写必须落在与根记录发布**同一个因果链条**内，这正好命中 D16（发布语义） 描述的写放大路径，逐字（`16-发布语义.md:52-53`）：

> 目标块 → 父节点 → … → 根 → 超级块。任一块的内容改了或物理位置变了，都必须沿这条路径逐级重写到发布新根，长度 H（树高），每级 = 一次新分配 + 一次凭据重算 + 一次加密写。

把超级块纳入这条链条，等于每次发布都多走一级、多一次「新分配 + 凭据重算 + 加密写」，而且是**每次发布**（不是每 checkpoint 一次的滞后更新）。

**与已定项 3（tail 槽同样住超级块槽）的对照，说明二者不能类比**：

D23（journal 的角色与格式） 已定项 3 第 2 条逐字（`.claude/kb/decisions/23-journal的角色与格式.md:784`）：「只在 checkpoint 持久之后写一次，不上 fsync 路径……稳态开销因此是每 checkpoint 一次，不是每 fsync 一次」；第 3 条逐字（`23-journal的角色与格式.md:792`）：「tail 语义上是派生态：权威判定仍是 `jsn` 连续前缀 + `checkpoint_txg`」。tail 之所以能安全地**滞后**，是因为它是派生态——即便超级块里的 tail 陈旧，恢复算法也有独立的兜底（`23-journal的角色与格式.md:794-803`「恢复不许先信 tail 再往前走……必须先全环扫描、逐条验证，再择最长合法前缀」），陈旧 tail 的后果只是「多做功」，不是「读错」。

树表单元指针不满足这个条件：D21 已经把它划进权威态（第 2 节），没有类似「全环扫描」的独立兜底——找到它的唯一机制是根记录里那条指针（自证校验和 + 位置条目寻址，不是扫描发现）。若超级块里也放一份而允许它滞后，它在陈旧时给出的不是「保守答案」而是**读到过期的树集合**（某棵树已被删除/新建，旧树表单元的条目仍在）——按 D21 判据段逐字（`21-权威态与派生态的分界.md:25-26`）：「重建不出这个值时，读者拿到的是保守答案还是错答案：保守答案 ⇒ 仍是派生态；错答案 ⇒ 必须逐出该结构，或者进权威态」。陈旧的树表指针给的是错答案，不满足派生态条件，所以不能援引 tail 的先例把它当成「可以滞后的槽轮换字段」处理。

**结论**：若超级块也带一条树表指针，它要么（a）被迫加入每次发布的原子提交链条，把 D16 描述的写放大路径从「到根为止」延长一级到超级块，与已定项 3「tail 只在 checkpoint 之后滞后写一次」的设计初衷相反；要么（b）允许滞后，但滞后就是错答案而非保守答案，不满足 D21 对派生态的定义，也没有类似 tail 的独立兜底机制去裁决「超级块说的版本」与「根环最新根说的版本」谁更权威——这条裁决规则今天完全不存在。两条路都不是「加一个字段」那么廉价，这正是 `.claude/singlefs-ai-sop/rules/kb-discipline.md` 第 4 条「矛盾比空白更糟」的具体代价：同一个事实（当前树表单元在哪）有了两处权威记录。

## 4. 条款原文

---

**候选 T 判定（2026-09-10，三方论证正推腿）：超级块不带自己的树表单元指针**

树表单元指针不进超级块字段表。树表的权威归属是**本代 checkpoint 的状态**，唯一权威路径是「根环 → 择新根记录（D22（单元原子性怎么合成） 已定项 7）→ 树表单元指针」，该路径已被 D21（权威态与派生态的分界） 划进「根」这一格——权威态，入口定义为「从 checkpoint 树根指针出发」（`decisions/21-权威态与派生态的分界.md:10`）。

**依据一（挂载自举）**：逐步推演挂载次序（超级块槽探测 → 超级块验证择新 → 根环候选定位 → 根记录验证择新 → 读根记录字段 → 跟随树表单元指针 → 读树表单元）显示，树表单元的读取严格晚于根记录被验证选定之后，链条上不存在「读到根记录之前就需要树表」的一步。

**依据二（生命周期）**：D22（单元原子性怎么合成） 已定项 7 自陈「间接层的代价是每次发布多 COW 一个树表单元」（`decisions/22-单元原子性怎么合成.md:471`），树表单元与根记录同生命周期；紧邻的树 ID 水位（D8（核心索引结构） 已定项 8 ②）同一模式下钉在根记录、「每次发布随根记录重写」，不是超级块字段。

**依据三（重复持有的代价）**：超级块的槽轮换（已定项 8）与根环的槽轮换（已定项 2）是两个独立环、代号体系不通用。若超级块也持有树表指针，要么把它纳入每次发布的原子提交链条（D16（发布语义）「目标块 → 父节点 → … → 根 → 超级块」那条路径，每级多一次分配 + 凭据重算 + 加密写），与 D23（journal 的角色与格式） 已定项 3「tail 只在 checkpoint 之后滞后写一次」的设计初衷相反；要么允许它滞后，但树表单元已被 D21 划进权威态、没有 tail 那样的全环扫描独立兜底，滞后就是「错答案」不是「保守答案」（D21 判据段，`decisions/21-权威态与派生态的分界.md:25-26`），不满足派生态条件。两条路都要新增一条今天不存在的跨环代号裁决规则。

⚠️ **射程**：本条只回答「超级块要不要自己一条独立的树表单元指针」，不涉及超级块是否要装设备表 / journal 几何 / tail 槽 / 根环参数 / 阈值——那些字段的必要性仍由 D22（单元原子性怎么合成） 未定项 9 的其余部分继续判定。

⚠️ **对历史措辞的说明**：`first-txn-layout.md` 第 20 行与 D22（单元原子性怎么合成） 未定项 9 正文里把「树表」列进超级块要装的东西，其来源是 D15（格式冻结政策） 已定项 2（2026-08-29，`decisions/15-格式冻结政策.md:204-212`）「超级块树表 day-1 做成开放列表」一句里的旧措辞——那句定案发生在 D22（单元原子性怎么合成） 已定项 7（2026-09-02）把树表指针移入根记录间接层之前，当时逐字写「代价只是超级块里多一个表长字段加一段可变长表」。已定项 2 要保的核心政策——新增 keyspace 走 compat 档而非 incompat——由树表单元自身条目自带长度字段兑现（D8（核心索引结构） 已定项 8 ④，`decisions/08-核心索引结构.md:469`：「兼容档取『树表条目自带长度』这一层……让旧读者跳过一棵不认识的树」），不需要额外复制到超级块。已定项 2 本身不必推翻，但引用它去论证「超级块需要一条树表指针」是误用一句已被后续架构取代的措辞。
