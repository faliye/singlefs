## 二、D18（块里携带什么信息）已定项 7 / 已定项 2 与 key 区间

### 「三档节点头 58 / 67 / 76」的口径

三个数不是三种候选实现，是**同一个未定宽度的三个下界估计**。出处链：

- `D18（块里携带什么信息）已定项 7` 只给字段**集合**，不给宽度：「类身份段——索引节点：树 ID + 层级 + 该树已定携带的 key 区间…宽度随实现定」
  （`.claude/kb/decisions/18-块里携带什么信息.md:406-407`）。
- `E73（节点 key 区间的扇出代价）` 第一次把这个未定量具体成三个数：「结论不变：按 58 / 67 / 76 三个下界各重算」
  （`.claude/kb/experiments/73-节点key区间的扇出代价.md:49`）。
- 此后 E97、E98、E101、E103 全部沿用同一口径，四个实验文件里逐字重复「三档下界」这个说法
  （已核对 `experiments/97-*.md:25,70,266`、`experiments/98-*.md:40,82`、`experiments/103-*.md:18,20`）。

**inode 树的头落在哪一档**：不落在任何一档——D18 已定项 7 从未替 inode 树（或任何具体的索引节点类）定过
一个宽度数字，58/67/76 只是「如果宽度落在这个区间，扇出会怎样」的算术下界探针，不是三选一的候选值。
E103 的产物证实了这一点：`e103-inode-update-cost-2026-09-04.out` 对 58/67/76 三档都跑了一遍（`grep -c "header=58\|header=67\|header=76"` 逐档都有），
且我在几组关键行上验过第三臂的扇出在三档下**都是 175**（算术核实：`(16384−58)/93=175.5…`、
`(16384−67)/93=175.4…`、`(16384−76)/93=175.3…`，三者向下取整都是 175），
所以结论对 P1 这句「扇出 175（节点头 58/67/76 三档都是 175）」逐字核实**通过**，不是没验证过的断言。

**第一个事务的 inode 树根节点头有多少字节今天写得出来吗——不写得出来。**
`first-txn-layout.md:81` 对结构相同的记账树节点头有一行现成的先例：
「记账树节点 | 节点头的基础字节数 | 未定 | D18 已定项 7（定了字段集合，未定宽度）| 半定」。
inode 树的码 2 节点头处境完全一样：字段集合已定（树 ID + 层级 + key 区间 + 诞生代号 + fsid），
具体字节数没有任何一条决策给过。

## 三、条目类型段 0 / 2 兼作「子是什么」

### 登记表现状

`D18（块里携带什么信息）已定项 11` 的「打包记录类型」第二级登记表（`decisions/18-*.md:643`）：
「0 无效；1 墓碑区间记录；2 inode 记录（保留）；3–65535 保留」。
这张表管的是**容器自己头里那个字段**——一个真实落盘的码 3 单元，它偏移 51 处的 2 字节必须是 1 或 2（0 判无效/损坏）。

### 第四版新用法

P1 把这同一个 2 字节字段（作为「身份引用」26 字节的一部分：出生树 8 + **打包记录类型 2** + 容器号 8 + 容器出生代 8）
搬进了**码 2 内部节点的条目**里，并让它兼职：「类型段的值说明子节点是什么：0 ⇒ 子节点是码 2 索引节点
（容器号、出生代两段恒 0），2 ⇒ 子节点是码 3 容器」——这里把登记表里「无效」的 0 值，
在一个新的宿主结构（内部节点条目，不是容器头）里重新赋义为「子是索引节点」。

### 会不会冲突

**字节层面不冲突**：这 2 字节出现在两处不同的物理位置——一处是码 3 容器头偏移 51（真实的打包记录类型），
一处是码 2 节点内部条目里的「身份引用」子字段（指向别处的一个引用，不是自己的类型声明）。
`I-1.7`（`invariants.md:26`）管的正是**前者**：「打包记录类型 ∈ 第二级登记表，未登记类型的容器其物理指针
不得出现在任何回收 / 复用操作的输入集合」——它的判定对象是**容器自己的头**，管不到条目里的这个引用字段。

**登记层面冲突**：kb-discipline 第 5 条的判据是「值域只有一处登记位」，而 D18 已定项 11 明写
「值域只有一处登记位——本表」。第四版把 0 值在**新场景**下赋予了新含义，却没有回到这张表旁边写一句
「0 在容器头里判损坏；0 在 inode 树内部节点条目的身份引用里表示子是索引节点，这是同一个数值域的第二个消费场景」。
第四版唯一登记这件事的地方是 P7 新开的 `I-9.2`：「内部节点条目类型段 0 ⇒ 子单元偏移 6 = 2；类型段 2 ⇒
子单元偏移 6 = 3」——**这是第二处登记位，且没有链回 D18 已定项 11 的表**，正撞 kb-discipline 第 5 条自己举的
反例（「O2 被三份文档各自定义」）的同一个形状：值域的权威定义在 D18 已定项 11，新的消费场景却只在
I-9.2 里悄悄生效，将来有人只读 D18 已定项 11 的表会以为 0 恒等于「无效/损坏」。

**checker 会不会误判**：不会误判成红，因为 I-1.7 与 I-9.2 是两条独立的不变量，扫描器读码 2 单元走 I-9.2 的路径，
读码 3 单元走 I-1.7 的路径，代码层面不会互相踩踏——**但人读 kb 会误判**，这正是 kb-discipline 第 5 条要防的那类事故。

**判定：要拆句 + 补登记**。落地时 P9 表里 D18 已定项 11 那一行（「记录类型 2「保留」→「启用」…」）要再加一句：
「打包记录类型 0 在容器自己头里仍判无效（I-1.7 原判不变）；当这 2 字节以「身份引用」形态出现在 inode 树内部节点条目里时，
0 另表示「子是码 2 索引节点」，这是第二个消费场景，登记在 I-9.2，与容器头场景不共享判定路径」。
这句话不写，第四版现在的文本**不算落地会红**（没有门禁会抓这类语义登记缺口），但确实是「落地会矛盾」——
矛盾的不是代码，是 kb 正文本身。

   开脱——它们要么是实验状态变更与对应的决策更新被分拆进了不同提交（决策可能在更早或更晚的提交里已经更新过，
   只是不是这同一次），要么是真正意义上的「决策该更新但没更新」，**需要人工逐条核实，不能一概而论**。

### 落地判据

按提示改法直接落地会让门禁**当场从 0 红变 22 红**，而且这 22 条里至少 18 条（约 82%）是历史文档重构/重排造成的
机械误判，与 `.claude/gate.d/60-stale-open-items.sh` 已经写明并主动规避的同一类陷阱。**不能直接改这两行就提交**：
改动本身需要补一条与 60 阶段同款的「2026-08-29 拆分之前的历史不算」时间线过滤（或者对 357dbf0/c26df20 这类
纯搬迁/重排提交做特判），否则这次改动会让门禁在一次不相关的改动上突然报出一大批历史欠账，
**而『退不回去』的风险也在这——一旦把这批红当真去逐条『修复』（比如手工在决策文件里加日期凑数），
会污染 kb 的历史真实性**。

**判定：只立欠账，不是同一次落地就能安全修的门禁改法。** 建议记进 `checks-owed.md`：
「10-kb-rot 第 3 项的搜索范围只看 decisions.md 单文件，扩大范围需要同时补一条时间线过滤（与 60 阶段同款），

第 57/61 行后跑 `bash .claude/gate.d/10-kb-rot.sh .` 复现）」。E88-E91 这 4 条例外，值得单独人工核实是否为真正的漏更新
（不属于「拆分/重排」这两类可解释的假红）。

## 九、本轮独立发现：D14（双轨（大小文件 / 持久临时）） 已定项 3 的 :186 行没有被真正过关

P9 表声称：「D14 已定项 3 | 过 :186 那一关的答案：唯一引用者 + 单次更新代价已量（E103）+ 爆炸半径已立账（C100）」。

但 `decisions/14-双轨大小文件-持久临时.md:186` 原文逐字是：

> 「**今后任何抬高内联阈值的提议，都要先答『多个文件共享一个原子单位』这一关，性能数字答不了它。**」

这句话的判据主体是「多个文件（对象）共享一个原子单位」这个**耦合形状**，理由在同一小节前一句写得很清楚：
「内联让多个文件的数据挤在同一个索引节点里 ⇒ 一个文件的写牵动同节点上其他文件的原子单位。这与 E66 判出局的
`pack` 臂（多个小文件共享一个数据单元）是同一个形状的耦合，只是换了个容器」（`:180-182`）。

**第四版的码 3 打包容器（一个 32 KiB 单元装 233 条 inode 记录）正是这句话描述的同一个形状**：更新一个文件的
mtime，要 COW 整个容器，这个容器同时装着另外至多 232 个文件的记录——「换了个容器」这句话第四版又换了一次，
从「内联进索引节点」换成了「打包进码 3 单元」，耦合的形状没有变。

而 P9 给出的三条答案里，**「单次更新代价已量（E103）」和「爆炸半径已立账（C100）」都是性能/代价类的数字**，
:186 那句话原文明确写着「性能数字答不了它」。唯一不属于这一类的是「唯一引用者」，但这条论证第四版正文里
没有展开——「唯一引用者」回答的是「这份数据有没有被别的树共享指向」（防止 reflink 式的多重引用带来的耦合），
而 :186 这一关问的是「同一个原子单位里挤了几个不相关对象」，这是两个不同的问题：inode 记录打包容器不需要
被多棵树共享才会触发耦合——即使只有唯一的容器索引指向它，容器内部 233 条记录本身就已经互相耦合。

**判定：落地会矛盾。** 第四版目前给出的三条理由里有两条是 :186 那句话明确排除的证据类型，第三条没有针对
:186 的真正问题（容器内部多对象共享同一原子单位）展开论证。要么第四版需要正面回答「为什么 inode 记录打包
容器的耦合可以被接受，而 D14 讨论的内联文件数据打包不可以」（比如：inode 元数据更新频率、大小、耦合半径
与文件数据完全不同量级，需要单独论证，不能借用「已经量过代价」这条被明文排除的理由），要么需要显式承认
「D14 已定项 3 的 :186 关卡对本项不适用，理由是……」并把这条豁免写成一条新的、独立于代价数字的论证，
两者都不是「已经答了」这么简单。
