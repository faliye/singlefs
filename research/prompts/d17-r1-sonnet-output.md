## 3-2：七条写路径逐条列出用到的步骤种类

先说清工具：`RecordedOperation` 是 E142 装置里唯一真实存在的"操作分类"，定义在
`research/e7-index-bench/src/bin/e142_first_transaction_dry_run.rs:446-450`：

```rust
enum RecordedOperation {
    Write(WriteRequest),
    Barrier,
}
```

它只分 `Write` / `Barrier` 两种，`WriteRequest`（`:438-444`）里只带 `device / offset / bytes / is_fua / label`，
`label` 是一个自由文本字符串（如 "m3 第 0 代根"、"t9 journal 记录"），不是一个枚举成员。
⇒ **D13「一」那段给出的 `CommitStep` 封闭枚举（`WriteDataBlock`/`WriteStripeParity`/`WriteInternalNode`/
`CasRootPointer`/`AppendRootRecord`/`ZoneFinish`/`ZoneReset`）在 E142 源码里一次都没有出现**
（现查：`grep -n "CommitStep" research/e7-index-bench/src/bin/e142_first_transaction_dry_run.rs` 零命中）。
下面我按材料给的六个粗类（写单元 / 屏障 / 写 journal 记录 / 根槽 FUA / 原地覆盖超级块槽 / 其它）

## 3-1：「成员集合相同」这条判据够不够用

**够不用，我能现场构造出材料要的那一对序列，而且它们已经是仓里的观测，不是我编的。**

E142 的 `main()` 对同一段操作 `transaction_operations`（`publish_first_file` 产生的 21 写 2 屏障）
跑了两次 `split_into_segments`，唯一的差别是 `fua_is_boundary` 这个参数：

- `layer0`：`split_into_segments(transaction_operations, true)`（第 `:2592` 行），根槽 FUA 写自成一段，
  segments = 16+2+1+2，`closed_form = 1 + (2¹⁶−1) + (2²−1) + (2¹−1) + (2²−1) = 65543`。
- `layer0_fua_not_boundary`：`split_into_segments(transaction_operations, false)`（第 `:2601` 行），
  根槽 FUA 写并进后面 2 条超级块写的同一段，segments = 16+2+3，
  `closed_form = 1 + (2¹⁶−1) + (2²−1) + (2³−1) = 65546`。

两次调用喂的是**逐字节相同**的操作序列（同一个 `transaction_operations` 切片），
**CommitStep（或材料给的六类）成员集合因此逐字相同**——都是
{写单元×16, 屏障×2, 写 journal 记录×2, 根槽 FUA×1, 原地覆盖超级块槽×2}——
但 P7 的崩溃状态集合大小不同：65543 ≠ 65546，差 3（= (2³−1) − (2¹−1) − (2²−1) + (2²−1) 化简后就是
"根槽 FUA 是否与后面 2 条超级块写同段"这一个位造成的差额）。

这正是仓里已经登记、材料自己引过的那条缺口：**C313（FUA 写算不算崩溃段的边界）**——
`.claude/kb/checks-owed.md:299` 逐字「D13（验证路线） 已定项 4 只说『屏障把录下来的写请求流切成段』，

harness 的闭式两种都对」。

⇒ **触发观测就是这两行 E7RESULT 产物本身**（判决表整行抄：`E7RESULT name=layer0 ... states=65543
closed_form=65543 violations=0` 与 `E7RESULT name=layer0_fua_not_boundary segments=16+2+3
closed_form=65546`），不需要我另造一对假设序列。

## 3-3：D17 已定项 1 的三种合成手段各落到哪个 CommitStep 成员

引 D17（实现分层与第三方管道） 已定项 1 整句（附录已有）：「达不到的由核心层合成（读回校验 / 双写 /
补一条日志），合成代价记在核心层、按管道计费不按用户计费。」以及同项的射程注（同一决策
「失败模型是第二根轴」一节）：「⚠️ 它钉住的只是『有哪些步骤』，钉不住『每一步的失败原子性宽度』——
持久内存与对象存储改变的是后者，枚举接不住」。

- **读回校验**：不落在任何 CommitStep 成员上。它是一次读，不是一次持久化写——CommitStep
  枚举的语义射程是"提交协议里有哪些写步骤"，而射程注自己承认它"钉不住每一步的失败原子性宽度"，
  读回校验正是用来弥补"这一步到底原子到多宽"这个 CommitStep 管不到的维度，不是在往协议里加
  一种新的写步骤。⇒ 它不需要新成员，也不落在现有任何成员里，因为它根本不是 CommitStep 的
  定义域内的东西。
- **双写**：落在既有成员上，不需要新成员。D13（验证路线） 已定项 4 已经把这个模式定死：
  「镜像双写（D2（RAID 条带策略） 已定项 6 的 w ≥ 2、D22（单元原子性怎么合成） 已定项 8 的 journal
  镜像）按设备各算一次写，harness 的状态数按自己的写流另算闭式」——双写是同一个写步骤
  （写单元 / 写 journal 记录）参数化地多算一次，与 3-2 里"写单元×16 = 8 单元 × 2 设备"是同一种
  参数化，不是新增步骤种类。
- **补一条日志**：需要"写 journal 记录"这个成员，而这个成员**不是因合成手段才新增的**——3-2 已
  经指出，路径 2（今天已经在跑的基线协议）本身就需要它，而 D13「一」给出的字面 7 个成员里没有它。
  ⇒ 正确的表述是：D17 已定项 1 的这条合成手段依赖一个 D13 字面枚举本来就该有、却没写上的成员，
  不是"合成引入了一个新种类"。补齐这个成员之后，"补一条日志"复用它，不再额外新增。

## 3-4：门禁形态 ① 与 ② 哪个与 D13「一」逐字一致

**① 一致，② 矛盾。**

D13「一」那段逐字：「落地手段是一个封闭枚举 + 穷尽 match……任何布局要引入新的结构性步骤
**必须改这个共享定义** ⇒ 编译器强制所有引用处补分支 ⇒ **这个 diff** 门禁 grep 得到」——
「共享定义」是单数，「这个 diff」指向同一份定义上的一次改动。这与①（一个共享的 `CommitStep`
封闭枚举 + 每条线一个成员子集断言）逐字对应。

②（每条线一个封闭枚举）意味着 N 条线各自维护一份独立枚举。这与「共享定义」矛盾：向线 A 的
枚举加一个成员，不会牵连线 B 的任何一处 `match`，"编译器强制所有引用处补分支"这句话在②下不
成立——而这条机制正是 D12（目标介质）/D17（实现分层与第三方管道） 反复引用的 btrfs `btrfs_is_zoned`
教训（22 文件 93 处渗透）要防的东西：**渗透之所以被拦，是因为渗透的信号必须经过唯一一处共享定义**；
②把这唯一一处拆成 N 处，拦渗透的机制本身就没了。

**3-4 打中。** 按材料的失败条款处置："取①，C220（等价类仍是 2 与降级为待证互相欠着） 的门禁形态改写"；
D17（实现分层与第三方管道） 未定项 2 原文里"每条线一个封闭枚举"那句应当撤回。

这条处置本身压过"在甲乙丙里选一个当条款"——即便甲在"普通发布"这一条路径上的具体计数
（1×1=1）没有被 3-2 推翻，它作为"完整判据"来写是不够的，因为 3-1 已经现场证明"成员集合相同"

都没有、mkfs 没有被枚举装置跑过，我也推不出"丙确定不成立"，只能如实记"没有找到支持丙的证据"。
