BACKGROUND. Singlefs stores several of its own internal indexes as trees built out of a fixed-size on-disk node format called format-2. Four of these trees exist: the allocation-record tree, the accounting tree, the central-mapping tree, and the extent tree; this document only asks about the extent tree, though facts below state numbers for all four so you have the full picture. Today, the extent tree is implemented with only a single node, which acts as both the root and the only leaf, with no internal levels at all, the same as the other three trees; unlike those other three trees, the extent tree already has a decided format for what an internal-node entry would look like if it grew a second level, even though that second level does not exist in the implementation yet. A design decision has been made to give all four of these trees the ability to grow additional internal levels above their leaves as the number of entries in them grows. This document only asks you to compute node-capacity and split-count arithmetic for the extent tree under fixed, already-given numeric inputs; it does not ask you to decide whether growing extra levels is the right design, or how the split and merge logic should work.

FACT 1. In this filesystem, an on-disk structure called a format-2 index node is always exactly 16384 bytes in total size, regardless of which of the four trees in this document it belongs to, and regardless of whether it is a leaf node or, for a tree that has one, an internal node.

FACT 2. A format-2 index node's total header size, in bytes, is computed by a formula that depends only on that node's key width in bytes, not on whether the node is a leaf node or an internal node: header size equals 86 plus 2 times the key width in bytes plus 29. Within one single tree, every node at every level uses the same key width and therefore the same header size as every other node in that same tree. Applying this formula gives the following already-decided header sizes for the four trees this document covers, each stated together with that tree's key width: the allocation-record tree has key width 10 bytes and header size 135 bytes; the accounting tree has key width 22 bytes and header size 159 bytes; the central-mapping tree has key width 27 bytes and header size 169 bytes; the extent tree has key width 24 bytes and header size 163 bytes. Each of these four header sizes is itself a literal already-decided constant in this codebase, not merely something you need to derive; the formula is given only so you can see why the four header sizes differ from each other.

FACT 3. The already-decided leaf-entry width, in bytes, for each of the four trees this document covers, meaning the fixed size of one data record stored in a leaf node's entry area: the allocation-record tree's leaf entry is 20 bytes, made up of a 10-byte key plus a 10-byte value; the accounting tree's leaf entry is 34 bytes, made up of a 22-byte key plus 12 bytes of value and sequence number; the central-mapping tree's leaf entry is 55 bytes, made up of a 27-byte key plus two 14-byte location entries; the extent tree's leaf entry is 112 bytes, made up of a 24-byte key plus one 88-byte data pointer.

FACT 4. In this codebase, a pointer stored inside one format-2 index node that points at a single child node, where that child may be either another format-2 index node or a format-3 packed-record container, is always exactly 86 bytes. This 86-byte width is the same fixed value used everywhere in this codebase that a format-2 node needs to point at one child; it does not vary by tree and does not vary by level.

FACT 5. This codebase already has two examples of a decided internal-node entry format for a format-2 tree, and both examples follow the same pattern: one internal-node entry consists of exactly one separator key plus exactly one 86-byte child pointer from FACT 4, and that one entry corresponds to exactly one child; there is no additional child pointer beyond the number of entries in the node, unlike some other tree designs where an internal node with n keys has n plus 1 children. The first example is the inode tree's internal entry: an 8-byte separator key plus a 26-byte identity reference plus the 86-byte child pointer, totaling 120 bytes per entry. The second example is the extent tree's internal entry, given in FACT 6 below.

FACT 6. FACT 7. For any one of these four trees, define its leaf capacity as the largest whole number of leaf entries, using that tree's leaf-entry width from FACT 3, that fit into the space left over inside one 16384-byte node from FACT 1 after subtracting that tree's header size from FACT 2.
