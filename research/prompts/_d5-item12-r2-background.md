## 三、候选（三条臂）

- **乙（归属 = deadlist 号，住树表条目预留 8 字节）**：每个头 / 快照写在 inode 树那一条的条目带一个 deadlist 号；key = 号 8 + 中央映射 key 27 = 35，value 空。头的初始号取头自己的树 ID；建快照时新快照拿走头的号，头换新号 = 新快照的树 ID（不要新计数器）。销毁 S（下一侧 N）：N 那一份里 `birth > prev(S).txg` 的放掉，S 那一份与 N 剩下的合并，改键条数少的那一份、号跟着换（改写 min(D(S), N 剩下的条数)），N 继承 `prev(S)`。
- **丙-区间（归属 = (头的树 ID, 纪元)，纪元 = 块被杀那一刻头的 `previous_snapshot_txg`）**：key = 头的树 ID 8 + 纪元 8 + 中央映射 key 27 = 43，value 空。快照 X 的 deadlist = 纪元落在 `[prev(X).txg, X.txg)` 的全部条目，头的 = `[prev(头), ∞)`。建快照只推进头的 `previous_snapshot_txg`，不改任何条目；销毁 S（下一侧 N）：把 N 那一份里 `birth > prev(S).txg` 的放掉，不改任何条目的键，然后 N 继承 `prev(S)`，N 的区间自然盖住 S 原来那一段。同 txg 的快照那一份区间为空（前提十二）。零树表字节，级联改写 0；依赖前提十三。
- **丙′（归属 = (头的树 ID, 块被杀那一刻头的上一个快照的树 ID)）**：key 同宽 43。克隆头的第一段装 origin 快照的树 ID，没有快照装 0。快照 X 的 deadlist = (头, X 的上一个快照的树 ID) 那一段；销毁 S：N 那一段里 `birth > prev(S).txg` 的放掉，留下的改键到 (头, S 的上一个快照的树 ID)，N 继承 `prev(S)` 与 S 的上一个快照。改写 = N 剩下的条数。零树表字节是攻方腿的说法；杀块那一刻「头的上一个快照的树 ID」从哪来（树表条目里只有 txg）要各腿答。

**采用 ZFS 的 birth txg + deadlist 模型。**

- 每个块自带**诞生代号**（birth txg）。
- 删除时把块的代号与**活头记录的 `previous_snapshot_txg`**（上一个快照的代号）比：
  `birth > previous_snapshot_txg` → **直接释放**；否则 → 追加进**活头自己的 deadlist**。
- 建快照时把**活头的 deadlist 整个交接给新快照**，活头换一个空的。
- 销毁快照时把它的 deadlist **合并到下一个更新的那一侧**，并按 `birth > prev(S).txg`
  过滤出可释放的条目。不做全盘扫描。
  **`prev` 要跟着传递**：被销毁那一侧的 `prev(S).txg` 由承接的一侧继承下去。不传递则代代都拿自己原来的 `prev` 去过滤，`birth` 小的条目永远等不到 `birth > prev` 成立 ⇒ **无界泄漏**（E94（搬共享落点的触碰面） 的变异 M5b 在模型层验过这条会红；欠着的可判定形式落 C195（销毁级联时 prev 传递只写在实验的模型修订记录里））。

**核心性质：记账是增量维护出来的，不是事后遍历出来的。** 这是 D5（快照 / 空间记账机制）的全部价值。

### 引用区间的充要条件

> **块 b 被快照 S 引用 ⟺ `birth(b) ≤ S.txg < death(b)`**，左闭右开。

| 量 | 定义 | **不是**什么 |
|---|---|---|
| `birth(b)` | 块被**发布**的那个 checkpoint 号 | 不是写请求发出时所在的开放 txg——崩溃后该号会被重发 |
| `death(b)` | 最后一个活引用被摘掉、**且该摘除被发布**的 checkpoint 号；仍在活树里则为 ∞ | 不是 `rm` 返回的时刻（D8（核心索引结构） 走意图分批），也不是空间变得可再分配的时刻（D16（发布语义） 新规则 2） |
| `S.txg` | **S 捕获的最后一个已发布 txg** | 不是「创建操作所在的 txg」 |

⚠️ **搬迁不改 `birth`（2026-09-06 收口）**：后台整理把一个单元从一个落点搬到另一个落点，
**不是「发布一个新版本」**——逻辑内容一个字节没变，只是物理位置换了。
按 D5（快照 / 空间记账机制） 给 `birth(b)` 的定义句「块被**发布**的那个 checkpoint 号」，搬迁不产生新的发布事件
⇒ `birth` 原样跟着单元走。
**依据**：E94（搬共享落点的触碰面） 实测——若搬迁重新指派 `birth`，
「重指派的违例数恰等于被快照引用的搬动数」，即每搬一个被快照引用的单元就错一次；
`birth` 不改则违例恒 0。
⇒ 这一句是 D26（后台整理与放置回收） 已定项 5 点名要「在 D5（快照 / 空间记账机制） 那边同步记」的两笔之一，

它随位置权威一起定，而位置权威已由 D19（块指针的结构与宽度预算） 已定项 5 取混合
⇒ deadlist 条目要按**版本身份**（逻辑身份五元组 + 诞生代号）记，不按落点记，也不带位置提示——

取「创建操作所在 txg」会让条件随「快照点放在 checkpoint 头还是尾」在

|---|---|---|
| `birth == S.txg` | S **引用**它 | 写成 `birth < S.txg` → 判为「比快照新」→ 立即释放 → **数据丢失** |

| `birth == death` | 任何快照都不引用，可立即释放 | 记账上对，但**物理空间不许在本 checkpoint 内复用**（D16（发布语义） 新规则 2）|

⇒ 一个笔误造成两处泄漏。两种取错的失败方向确实相反（写严左边界只丢数据 1 处、
写闭右边界只泄漏 2 处，零交叉）。

⚠️ **保守默认纪律：判据的任何一个输入取不到或不确定时，默认必须是「进 deadlist」。**
泄漏可被 I-3.6（deadlist 紧界） 检出（**不是 I-3.1（已分配统计对得上）**——
[invariants.md](../invariants.md) 明写「归属错误对它不可见……总账依然平」）、可回收、伤害有上界；

### 运行时判定是 O(1)，而且这个 O(1) 要证

```
判定(ptr):
    birth = ptr.birth              // 指针内联字段，零次额外 I/O
    p     = head.previous_snapshot_txg     // 活头头部一个标量，常驻内存
    if birth > p:  立即释放 → 进 defer 队列（不是直接进空闲表，见 D16 新规则 2）
    else:          追加进 head.deadlist
```

**归约证明**：设删除发生在 checkpoint `d`，P 为此刻最新的快照。
(⇐) 若 `birth ≤ P.txg`：P 已发布 ⇒ `P.txg < d = death` ⇒ `birth ≤ P.txg < death`，∃S 引用它。
(⇒) 若 ∃S：`birth ≤ S.txg < d`，则 S 在删除时已存在 ⇒ `S.txg ≤ P.txg` ⇒ `birth ≤ P.txg`。∎

**它只用了两件事**：txg 全序，以及**判定必须发生在死亡那一刻**。
⚠️ 哪一条破了 O(1) 就没了——D6（快照实现模型） 的候选破第一条，D8（核心索引结构） 的分批删除破第二条。

**销毁快照的代价是 O(deadlist 条目数 + 桶数)，不是 O(全盘)**，
前提是 deadlist **按 birth txg 分桶、桶边界 = 快照 txg**，否则销毁时的过滤退化成全表扫描。

#### 已定项 2（2026-08-30，用户定案 + E54（记账的「代」要保留几代） 实测）：要「代」，代取 checkpoint 号，只保留最近 K 代

**「代」取什么，以及旧代什么时候可以丢 —— 已定（2026-08-30，用户定案 + E54（记账的「代」要保留几代） 实测）：
要「代」；代取 checkpoint 号，并配一条增量丢弃规则，只保留最近 K 代。**

**先说这个「代」是什么**：D8（核心索引结构） 已定项 1 已定记账条目是**幂等完整值**——
一条记账记录写的是「某个统计量**此刻**的完整值」，不是「增加了多少」。
于是同一个统计量会被写很多次，**key 里必须有一段把这些次分开**，那一段就是「代」。

⚠️ **「代 = checkpoint 号」的口径已由 D16（发布语义）已定项 6 收口（2026-09-02）**：
每次发布（fsync 触发的也是发布）checkpoint_txg + 1 ⇒ **代按发布走，不按 5 秒窗口走**。
两条骑手条款直接砸在这里：代段宽度 **≥ 48 位**（2785 发布/秒下 32 位 17.8 天回绕，
E71（记账 key 的条目数与宽度）的宽度算术要按此重算）；
记账条目的**跨发布合并不再可行**（代进了 key）⇒ E54（记账的「代」要保留几代）
的每代「统计量数 × 2」次写是实付值，不是上界。

**它为什么必须存在**（用户定案「需要代」的机制理由）：**根可以回退，账必须跟着回退。**
D22（单元原子性怎么合成） 的根环保留最近若干代根，恢复时可能挂上上一代的根；
若账没有「代」这一维、只有一份就地覆盖的最新值，
**挂上旧根之后账是新的、树是旧的** ⇒ I-3.1（已分配统计对得上） 当场判红，
而那不是 bug，是设计漏了这一维。

##### E54（记账的「代」要保留几代） 把原来那个二选一取消了

此前本项写作「甲（代 = checkpoint 号，不丢）／丙（只留最近 K 代）」二选一。
**实测：甲加一条增量丢弃规则与丙在 60 个格上逐格相同**
⇒ **「代取什么」与「留几代」是两个正交问题**，不是一个二选一。

| | key 数（64 个统计量、100 万 checkpoint） | 对 checkpoint 数的斜率 |
|---|---|---|
| 不丢 | **64 000 000** | **= 统计量数** |
| 保留最近 K = 8 代 | **512** | **0** |

**丢弃满足 `.claude/rules/fs-design.md` 第一格**：要丢的那一代**算得出来**（当前代 − K），
**不用找** ⇒ 是点删不是扫描；触及的 key 数 = **统计量数**，
**与 checkpoint 数无关、与盘容量无关**。代价是每 checkpoint 的记账写次数从
`统计量数` 变成 `统计量数 × 2`（一写一删）。

| 口径 | 回退深度 | K 下界 | 64 个统计量下的 key 数 |

### 已定项 5：whiteout 删除 —— 接受，但批量删除必须走 intent log

删大目录、截断大文件会产生海量墓碑，塞进一个事务必然爆掉。
**做法（bcachefs 已验证的形态）**：凡是**可能修改无界数量 extent** 的操作（truncate、collapse、删大目录），
**先把意图写进 logged_ops 树，再分批推进**；崩溃后恢复时续做未完成的意图。
删除中的 inode 单独进 `deleted_inodes` 树，由后台回收——用户的 `rm` 返回，不等于所有 extent 都已释放。

**硬要求**：无界规模的操作一律不许做成单个事务；意图必须**幂等**；
whiteout 只在节点重写合并 bset 时清除，**不许有别的清除路径**。

意图本身就是一条普通 key，骑在同一个事务层上，断电后只有三种状态：

| 断电时机 | 恢复后看到 | 怎么收场 |
|---|---|---|
| 意图提交之前 | 没有意图 | 操作从未发生，用户那边也没返回成功 |
| 意图已提交、工作做了一半 | 意图还在 | 恢复时**续做**，已做完的部分被幂等地重跑 |
| 工作做完、意图未删 | 意图还在 | 续做一遍发现无事可做，然后删掉意图 |

不可能出现「意图没了但目标状态没达成」——**删除意图必须与最后一批工作在同一个事务里提交**。

1. **意图声明目标状态，绝不声明增量。**「把文件 X 截到 N 字节」可以重复执行，「再删 1000 个 extent」不能。
2. **续做是每次恢复都跑的常规动作，不是修复手段**（否则会出现「平时不跑、真出事时才第一次跑」的代码路径）。
3. **中间状态必须每一个都是合法的文件系统状态**——「删了一半 extent 的文件」本身就得合法。

**范围重建 vs 逐项修改：两条都要有，且要有显式判据**（`.claude/rules/fs-design.md`「不追求万能方案」）：

| 走法 | 代价 | 适用 |
|---|---|---|
| 逐项修改 | K × 随机访问 | 受影响的 key 稀疏散布 |
| 范围重建 | N × 顺序访问 | 受影响的 key 在 key 序上连续 |

朴素的交叉点是 `K/N > 顺序代价/随机代价`（机械盘约 1%、SSD 约 10%）。
⚠️ **第一期只取 SSD 那一档**（D12（目标介质） 已定项 5：第一条布局线是纯 SSD）。
⚠️ 这两个数是**推理，不是实测**，说的是**耗时**，要靠 E4（范围重建 vs 逐项修改的交叉点） 量，那一半要 QEMU。

**写放大那一半已量**（E30（交叉点的写放大那一半），2026-08-29，100 万叶、三轮字节一致）：

| 节点 | 条目连续 | 条目散布 |
|---|---|---|
| 4 KiB | **1000‰**（要全改才划算） | **10‰** |
| 16 KiB | **1000‰** | **3‰** |

⇒ **在写放大口径下，交叉点的自变量是「布局」与「节点大小」，不是介质**，两者相差两个数量级以上。
⚠️ 不能拿它去证伪「机械盘约 1%、SSD 约 10%」——那说的是耗时，E30（交叉点的写放大那一半）对介质一个字没说。

**真正的开关不是 K/N，是「受影响的 key 连不连续」**：连续 ⇒ 范围重建可整节点丢弃或重写；
不连续 ⇒ 只能逐项。**由此得到一条布局规则：让一起死的东西在 key 序上挨在一起。**

- dirent 按 `(parent_inode, name)` 编 key → 删整个目录是范围操作
- extent 按 `(inode, offset)` 编 key → 截断是范围操作
- 同一快照的 key 带同一 snapshot 前缀 → 删快照有机会变成范围操作

**这顺带从结构上解掉了 whiteout 膨胀**：范围删除直接丢弃整个节点，不用插 N 个墓碑。

按 `.claude/rules/fs-design.md` 的五条要求，这个分支还欠：判据写成可计算的式子、
留一个能强制走指定分支的测试开关、两条分支各自跑崩溃点重放、运行时能看出走了哪条。
⚠️ **切换判据里不许出现「当前填充率」这类操作中途会变的量**——判据只能用操作期间稳定的输入。

**与 D3（空间分配） 的交互（容易漏）**：意图未完成期间那些空间还没真的释放，
空间统计必须把「待删除但未完成」计进去，否则会出现「我删了一大堆，`df` 却不动」。

### D16（发布语义）连带定死的两条新规则（2026-08-26，来自生命周期条件的推导）

**新规则 1：快照发布点必须与 checkpoint 边界对齐，且位置钉死在「本 checkpoint 全部数据变更之后」。**
快照不许出现在 checkpoint 中间。
理由是机制性的：`birth` 的分辨率只到 checkpoint，**块无法表达「我生在本 checkpoint 里
快照点之前还是之后」**。不钉死它，D5（快照 / 空间记账机制） 那张边界表里 `birth == S.txg` 与 `death == S.txg`
两行会同时失去确定答案——而它们一个是**数据丢失**、一个是**空间泄漏**。
（同一 checkpoint 内建两个快照是允许的：它们捕获同一状态、其间 deadlist 为空；
但 checker 里的「上一个快照」要用 `(txg, 快照 id)` 打破并列。）

**新规则 2：checkpoint C 中产生的一切释放，在 C 被发布之前不得进入可分配集合。**
两个理由，第二个是 D16（发布语义）独有且更严的：

1. 回滚：崩溃后可能回到 C−1 的根，而生于 C 之前、死于 C 的块在那时仍然活着。
2. **D16（发布语义）把 D8（核心索引结构） 的中间态语义改写成「根 + journal 任意前缀，replay 后合法」。**
   若一个块在 journal 位置 p 被释放、位置 q > p 被重新分配并写入新内容，
   那么重放到 `p < r < q` 的前缀会得到一棵指向该地址的树，
   **而盘上的字节已经是 q 的内容了**（物理写不受 journal 位置约束）。
   **这不是理论风险，是必然的错。**

ZFS 有同型机制且更保守：`include/sys/txg.h` 的
`#define TXG_DEFER_SIZE 2 /* Number of txgs worth of frees we defer adding to in-core spacemaps */`。
