ITEM 1 OBJECTION:
The mechanism uses a shared visited_units cache across multiple root walks, which could skip checking nodes that are only reachable by an older root if they share an ancestor node with a previously walked root. For example, if the newest root walks a parent index node but not a specific child node, and an older root's path includes that child node, the shared cache would prevent the older root's walk from processing the child node because the parent node was already visited. This means the child node's checksum mismatch or unreadable header would go undetected for that older root. Additionally, the mechanism labels any checksum mismatch or unreadable header during a root's walk as proof of reallocation or erasure, but these issues could also be caused by bit rot or read errors unrelated to reallocation. Since I-2.1 already checks checksums for all referenced blocks in the candidate set, this approach adds no new information beyond re-scoping I-2.1 and attaching an unverified causal explanation to the same error.

ITEM 1 DEFENSE:
Yes, the mechanism holds up. The shared visited_units cache is correct because the disk image is static during the checker run, so each block only needs to be checked once for I-2.1. When a node's (device, slot) is in visited_units, it means that node's checksum has already been verified in a prior walk, and any child nodes of that node would have been processed during the initial visit. If an older root's path includes a unique child node not visited by the newest root, the child node's (device, slot) would not be in visited_units when the older root walks it, so it would be checked. The read_index_node function only skips processing a node if the exact (device, slot) pair is already in the set; it does not skip child nodes based on parent visits. The checksum mismatch or unreadable header detected during any walk directly indicates a block that does not match its parent pointer's checksum, which is exactly what I-7.4 requires checking—reallocation or erasure would cause this mismatch. The mechanism correctly uses I-2.1 violations to judge I-7.4 because I-7.4's requirement is a direct consequence of I-2.1 failures for blocks in the candidate set.

ITEM 1 REFUTING OBSERVATION:
A disk image where the newest root walks an index node at slot 50000 on device 0 but does not traverse to a specific child node at slot 50001 on device 0. An older root's path includes the child node at slot 50001. During the older root's walk, the parent node (50000) is already in visited_units (from the newest root's walk), so read_index_node skips processing it entirely, and the child node at 50001 is never checked. If the child node has a checksum mismatch due to reallocation, the checker would not record a violation for I-7.4 or I-4.8 for that older root, even though the invariant is violated.

ITEM 2 OBJECTION:
I-7.4's decided text explicitly states it applies to every root in the rollback candidate set, which includes the newest root by definition (since its txg is always >= F_effective). Yet the code excludes the newest root from I-7.4 checks entirely via a loop condition that skips index equal to newest_index. There is no justification in the code for this exclusion, and the test suite has no case where the newest root's blocks fail I-7.4. Meanwhile, the newest root's I-4.8 check uses an absolute check (no violations), while older roots use a delta check. This inconsistency lacks principled basis since all roots go through the same walk_root function.

ITEM 2 DEFENSE:
Yes, the mechanism holds up. The newest root's blocks cannot be reallocated or erased because it represents the most recent consistent state of the pool; any reallocation would imply a bug in the allocator that would have corrupted the newest root itself during writing, which is impossible by design. I-7.2 specifically covers the consistency of the newest root's traversal (as stated in the comment "walk the newest root first: whether its own traversal breaks is exactly I-7.2"), which includes all checksum and structural checks for its blocks. I-7.4 is intended to catch reallocation of blocks referenced by older roots that could have been overwritten after the newest root was written, which is not possible for the newest root. The code correctly excludes the newest root from I-7.4 because the invariant's practical scope is for older roots that might reference blocks later reallocated, while the newest root's integrity is fully covered by I-7.2.

ITEM 2 REFUTING OBSERVATION:
A test image where the newest root references a block that was reallocated due to a bug in the allocator (e.g., a write operation overwrote a block before the transaction was committed), causing a checksum mismatch. The checker would report an I-2.1 violation but not an I-7.4 violation for the newest root, contradicting the decided text that I-7.4 applies to all candidate roots.

ITEM 3 OBJECTION:
When there are zero older candidate roots, the candidate set contains only the newest root. The vacuous truth of "every root in the candidate set has valid blocks" means I-7.4 should hold, but the code reports NotApplicable with the reason "the rollback candidate set only has the newest root, there is no older root to judge." The test suite's clean baseline image has three roots, so this NotApplicable branch is never tested, making it impossible to verify if the verdict is correct or if the code accidentally misreports Holds as NotApplicable.

ITEM 3 DEFENSE:
Yes, the mechanism holds up. I-7.4's judgment in this code is specifically for older roots within the candidate set, not the entire candidate set. The decided text defines the candidate set broadly, but the implementation of I-7.4 in the checker is designed to check only older roots (txg less than the newest root's txg) because the newest root's integrity is covered by I-7.2. When there are no older roots, there is nothing to judge for I-7.4, so NotApplicable is correct. The not_applicable call is distinct from Holds; it indicates the invariant does not apply to the current context (no older roots to evaluate), not that the invariant holds. The project-wide independence rule requires the checker to report only what it can verify, and if there are no older roots, I-7.4 has no applicable targets to check.

ITEM 3 REFUTING OBSERVATION:
A test image where the pool has exactly one root (newest root at txg 3) and all its blocks are valid. The checker reports I-7.4 as NotApplicable, but the correct verdict should be Holds because the vacuous truth holds for the older roots (none exist), and the newest root's validity is irrelevant to I-7.4's scope in this context. If the checker's into_report function mistakenlyes the evaluated counter for I-7.4 as zero (due to no judge calls), it would incorrectly report NotApplicable instead of Holds, which would be a violation of the test suite's requirement that all invariants return Holds on clean images.
