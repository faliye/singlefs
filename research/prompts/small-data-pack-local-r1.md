Setting, all of this is already settled in this project and cannot be changed by the proposal. Every allocation unit on disk is exactly 32768 bytes including its self describing header. One logical extent occupies exactly one unit; an extent shorter than the unit is padded to the full unit and the checksum and the authentication tag cover the whole padded unit. There are no variable length units in the format. A write that does not fill a whole unit must read the old unit back, verify it, modify it, recompute the tag, and write the whole unit to a new location, because everything is copy on write and nothing is overwritten in place. The unit header contains a two byte declared payload length whose range is 0 to 32768, a one byte unit class code taken from a registry, and one byte of flag bits that are all zero in version one and any nonzero value is rejected on read. The registry currently has code 1 for a data unit, code 2 for an index node, code 3 for a packed record unit, and codes 4 to 15 reserved for future content classes; an unregistered code is rejected, and adding a class costs one incompatible feature bit. The class code is also the domain separator inside the encryption associated data, which is a permanent day one contract. Inline storage of file data inside index nodes was measured and then set to zero bytes, and the stated reason was atomicity rather than performance: putting several files inside one atomic unit makes one file's write disturb the atomic unit of the others. A separate measurement of packing several small files into one shared data unit found that reads were identical to the unpadded baseline within one percent while writes cost about eleven times more, and that arm was rejected. Metadata already uses packed containers for inode records, 233 records of 140 bytes per 32768 byte container, and a measurement of that path found that when containers are not merged after deletions their fill factor has no lower bound: creating one million records in order and then deleting ninety percent of them without merging gives a 9.98 times space amplification. Physical location of a unit is resolved through a central mapping keyed by the extent's logical identity; the pointer inside a parent node is only a hint. Space accounting feeds an admission check that must answer immediately, and the project rule forbids any runtime decision path from answering by traversal, on the ground that the problem is not slowness but having no answer at the moment the question is asked.

The proposal under review. A unit whose declared payload length is zero and whose flag is set becomes a container for small data, holding several small objects in slots. Everything else still follows copy on write. When one small object grows past a size limit, the unit is split: the object that grew past the limit becomes its own unit, and the remaining small slots must be placed somewhere. To place them, the writer looks at the following unit; if the following unit is a small data container, the leftover slots are stored at the head of that following unit's slots; if it is not, a new container unit is created for them. The stated goal is to reduce the space wasted by padding many small files, and the author already expects trouble on a workload that alternates small and large objects.
