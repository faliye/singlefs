1. The claim that looking at the following unit is unimplementable is correct. The project rule explicitly forbids any runtime decision path from requiring traversal (e.g., reading another unit to check its class) because space accounting must answer immediately. Attempting to read the next unit’s class violates this rule. Additionally, modifying an existing container would require copy-on-write for that container, updating all its objects’ mapping entries—this is a traversal of the container’s contents, which the rule prohibits. No placement scheme can avoid both issues. A different data structure (e.g., a global container index) would still require traversal to locate a suitable container, violating the rule. Thus, the first reason blocks implementation.

2. The two encodings are distinguishable in failure behavior. A legacy reader (unaware of containers) encountering a unit with zero declared payload and nonzero flag would reject it immediately due to the rule that any nonzero flag is rejected on read. If a new registry code (e.g., code 4) is used with zero flag, the legacy reader would not reject it (code 4 is reserved, not unregistered) but would process it as an unknown class—potentially ignoring it silently. For a scanner rebuilding the index, the nonzero flag case causes rejection (safe failure), while the new code case may lead to missing data (unsafe failure). Encryption AD differs: nonzero flag includes flag bits in AD, while new code uses the class code. Thus, the claim is not decoration; the encodings have distinct failure behaviors, and the nonzero flag approach enforces safer failure.

3. Consider small objects of 1000 bytes and large objects of 32000 bytes. Padding each small object uses 32768 bytes per object. Packing them into containers (32 objects per container, 32768 bytes each) uses 32768 bytes per container. After deleting 99% of 100 small objects (1 remains), padding requires 101 × 32768 bytes (100 large + 1 small). Packing requires 101 × 32768 bytes (100 large + 1 container for smalls). For 2 small objects, padding uses 102 × 32768, packing uses 101 × 32768—packing is cheaper. For any small object count >1, packing is cheaper or equal. At 1 small object, they are equal; never does packing become more expensive. Thus, packing never stops being cheaper.
