1. No such consumer exists. The filesystem's design ensures all access to previous states is handled via snapshots or the three retained roots. Considered scenarios: garbage collection (deadlist tracks snapshot references, no need for unit-specific previous versions), repair (checksum failures trigger redundancy rebuild or snapshot fallback, not unit-specific prior versions), and transaction rollback (three retained roots provide recovery points). Snapshots already provide complete historical states, and unit-level previous versions are irrelevant since the parent pointer's checksum and birth number validate current state. No operation requires accessing a specific unit's prior version outside snapshot or root contexts.

2. A checksum collision can bypass staleness checks. Suppose unit X has birth checkpoint 1 and checksum C. Disk corruption alters X's data to Y with identical checksum C and birth checkpoint 1. Parent pointer checks pass (checksum C matches, birth 1 matches), but Y is corrupted. This violates theeness detection because the checksum and birth number are insufficient to detect data corruption when collisions occur. Changing the checksum algorithm to a stronger one (e.g., SHA-256) would mitigate this, but weak checksums inherently allow such cases.

3. Falling back to a previous version is not sensible. If the new version's checksum fails and redundancy rebuild fails, the previous version may have been freed (e.g., referenced only by a deleted snapshot). The accounting system has already updated free space records assuming the new version is live, so the old block might be reused. Accessing it would read garbage data, corrupting the filesystem further. For example, if the old block is reallocated to another file, reading it during repair would merge unrelated data. The system cannot reason about this state as it violates consistency assumptions. Recovery would require a full snapshot restore, not unit-level fallback.
