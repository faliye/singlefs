## 已定条款（逐字）

- **write buffer 硬要求 3**（`08-核心索引结构.md:42`）：「**条目必须自带序号（seq），这是格式要求**」。
  它的**理由**同段逐字：「flush 时按 key 排序**丢弃时间序**，而去重规则是「后者胜」
  ⇒ **「后者」必须由条目自己携带**；用不稳定排序时同 key 条目的相对次序未定义，去重结果因此不确定。」
- **D8 已定项 1**：记账条目取**幂等完整值**，不是增量 Δ。
- **D5 已定项 5**：记账 key = `(统计量类型标签 2, 树 ID 8, 设备 4, 代 8)`，定宽；
  末尾逐字「`seq` 落在 D8 未定项 7，仍未定——它进 key 还是进 value，会改这五段的排序契约，
  **格式冻结之前必须先定它**」。
- **D5 已定项 2**：代取 checkpoint 号，配一条增量丢弃规则，**只保留最近 K 代**（K 的值至今未定）。
- **D15**：第 3 层冻的正是各 keyspace 的 **key 编码**。
- **D11 已定**：索引节点**留消息缓冲区**（ε=0.65；inode 树 ε=0）。
  同文逐字「**关键区别不在「消息放节点内还是独立树」，在缓冲里放的是「幂等完整值」还是「增量 Δ」**」。
- **C80**（未还）：write buffer 是**内存**结构；「**发布点上 write buffer 强制排空到哪一层」全仓零覆盖**。

## 现役实现怎么做（只作机制与「该测哪条路径」用，不作正证）

本机内核树 `/home/fy5090/code/fs-refs/linux-6.17/fs/bcachefs/`：

- `btree_write_buffer_types.h:38-42`：`struct btree_write_buffered_key { enum btree_id btree:8;
  u64 journal_seq:56; __BKEY_PADDED(k, ...); }` —— **`journal_seq` 是缓冲条目自身的字段，
  不在 `bkey` 里**；落盘的只有 `k`。
- 同文件 `wb_key_ref`：排序键是 `(btree, pos, idx:24)`，`idx` 是缓冲数组下标；
  `btree_write_buffer.c:308` 逐字 `wb->sorted.data[i].idx = i;`，
  同文件注释逐字「Compare excluding idx, the low 24 bits」——**平局靠插入序，不靠存下来的序号**。
- **与本工程的一处已知差异**：bcachefs 的记账由触发器维护、是增量形态；
  本工程 D8 已定项 1 定的是**幂等完整值**，两者的去重语义不同。

## 三条候选

| | 形态 | 已知代价 |
|---|---|---|
| **甲 进 key** | key 变 `(标签, 树, 设备, 代, seq)` | 同一 `(标签,树,设备,代)` 前缀下有多行 ⇒ 动 D5 已定项 2 的「丢一代」的形态；且同 key 条目不再在 btree 层合并 |

## 丙 要成立，必须答的三问（主 agent 列，未答）

1. **落盘之后还有没有消费者**：同一个 key 的两条条目会不会**同时存在于盘上**？
   若节点消息缓冲区在插入时就按 key 去重（幂等完整值允许就地替换），就不会；
   若不去重，两条共存 ⇒ 读时要判谁新 ⇒ 必须落盘。
2. **Bε 树的「越靠根越新」够不够**：消息从根往下流 ⇒ 位置本身编码了新旧。
   这条在本工程成不成立？跨层归并、以及 write buffer 前端与节点缓冲区**两级**同时存在时呢？
3. **崩溃恢复**：未排空的缓冲条目在崩溃后从哪里恢复、按什么序重放？
   C80 逐字说「发布点上 write buffer 强制排空到哪一层」**全仓零覆盖** ⇒ 这一问今天没有答案。
