## 二、逐判据分析

### 二.1 判据 5：P15 前提的核实结果

**我核过**，方法是全仓 grep「克隆」「快照」「共享」与「码 2」「extent 树」「内部节点」的交集，以及直接读 D6（快照实现模型）、D8（核心索引结构）已定项 6、D21（权威态与派生态的分界）相关段落原文。

**找到的唯一直接先例，是 inode 树，而不是被判的对象（extent 树）**：

> 出处 `.claude/kb/decisions/08-核心索引结构.md:348`（整行抄）：
> 「出生树逐条目携带，是因为克隆头（D6（快照实现模型） 已定项 1）共享 origin 的叶，同一个内部节点里会混着出生树不同的条目。」

> 出处同文件 `:383`（整行抄）：
> 「两个头共享 origin 的叶、各自 COW 之后是同身份两版、同一个 key 装着不同对象——判定归 C113（扫描重建时多版单元的现行版本判定无输入）；跨头首次 COW 时容器身份要不要重生归 E90（树 ID 进 AAD 与跨头共享） 第二笔（C110（跨头共享与加密后元数据类的块头一致性读法））。」

inode 树的「叶」是**码 3**（打包记录单元），不是码 2。这两句话确凿地说：**克隆头之间共享的是叶（码 3），不是内部节点（码 2）**。内部节点（码 2）逐条目携带出生树字段的原因，恰恰是因为它自己**不共享**、但它指向的叶可能出生于另一棵树（origin）。

**I-1.3（块头树 ID 一致）的例外条款同样只点名码 3 与被快照共享的码 1**：

> 出处 `.claude/kb/invariants.md:21`（整行抄，已在附录中）：
> 「⚠️ 打包记录单元（码 3）与被快照共享的数据单元头里的树 ID 是出生树，跨头共享时与引用树不同，那一情形的判法随 D9（加密） 那次「绑出生快照」的重开（C110（跨头共享与加密后元数据类的块头一致性读法））。这一射程覆盖码 3 全部打包记录类型，含类型 2（inode 树的叶，D8（核心索引结构） 已定项 6）：克隆头共享 origin 的叶时，叶头的出生树是 origin」

这条不变量的例外条款**没有给码 2 留口子**——按字面读，码 2 的树 ID 就是「实际引用它的树」，隐含码 2 不会被跨头共享（否则这条不变量的字面表述在码 2 上不成立，需要同样的例外）。C289（码 2 的出生树取哪个字段没写）本身也点出这一点：

> 出处 `.claude/kb/checks-owed.md:281`（整行抄）：
> 「码 2 的类身份段里没有叫『出生树』的字段，只有树 ID；而 I-1.3（块头树 ID 一致） 把『头里的树 ID 是出生树』的例外只给了码 3 与被快照共享的码 1，按字面码 2 的树 ID 是『实际引用它的树』。码 2 节点若跨头共享，这两处读法不能同真。……⚠️ 『码 2 节点会不会跨头共享』两条云端腿都是推的，主 agent 没核」

**我的判断（推的，不是核实到的直接答案）**：从 inode 树这个先例和 I-1.3 的例外范围看，**这个仓的既有设计倾向是「码 2 索引结构本身不做跨头物理共享，只有它引用的权威态载荷（码 1 / 码 3）被共享」**——这与 D21 的核心论点一致（「树是加速结构，不是事实来源」，D21 第 320–321 行）：如果码 2 的作用只是加速指向权威态对象的路径，那么每个头维护自己一份独立的索引结构（即使内容大量重叠）比维护跨头共享的索引结构更符合「派生态可以随便重建」这条设计哲学——共享索引结构反而需要额外的引用计数/COW 追踪机制（正是 D5、D6 已经在为码 1、码 3 层面的共享而头疼的那套机制），把同样的负担再叠加到索引层，与 D19 已定项 5「树是加速结构」的取向相悖。

**但这仍然是推论，不是仓里现成的直接陈述**——extent 树（被 C292 判定所直接指向的树）从未被明确写过「内部节点/叶节点跨头共享还是不共享」。inode 树的先例是**另一棵树**，物理机制未必照搬（尤其 extent 树的「叶」本身就是码 2，不像 inode 树叶是码 3）。

⇒ **判据 5 结论：只记，不能坐实**。P15 仍然未核实，我只能提供强类比证据，指出仓里现有设计的一致倾向，但不能把它写成「已核实」。这与失败条款「先答 P15」相关：**判据 2 里依赖 P15 的那一支应当挂起**，但（见下）判据 2 还有一支不依赖 P15。

### 二.2 判据 2：每个消费者拿到什么

**场景①（依赖 P15，挂起）**：若 P15 为真（码 2 确实可被克隆头跨头共享，类比 inode 树叶那样），且被共享的码 2 节点丢失，重建方（甲）用「诞生代号取下界」重发——若"下界"取得比原节点更早（更保守），P6 的判定会走「进 deadlist」这一侧，属于 P5 定义的保守方向；但如果重建时**取的下界比原诞生代号更晚**（例如误取重建操作发生的当前 checkpoint），则可能出现「原本应被某快照引用（birth ≤ S.txg）的节点，重发后 birth 变大，判定变成 S 不引用它」——这是一个**错答案**（对应 P4 的「保守答案 vs 错答案」判据里的第三种、最危险的一种：让本该受保护的对象在快照的可见性判定里消失）。这个场景的成立**完全取决于 P15**（若码 2 不被跨头共享，就不存在"另一个头仍然引用着这个被重建节点的旧版本"这回事，重建只影响当前头，不产生这种冲突）。

**场景②（不依赖 P15，实打实站得住）**：即使码 2 完全不跨头共享（P15 为假），单个头自己的历史里，一个码 2 节点也可能已经不在活树里、但被**它自己头的某个快照**通过 deadlist/livelist 追踪。依据：

> P8（整行抄，出处 `.claude/kb/decisions/19-块指针的结构与宽度预算.md:130`，已定项 8 依据段）：
> 「① 码 2 / 码 3 的块也进 deadlist / livelist——全仓没有明句，由 I-3.5（引用区间的精确性） 管『任一块 b』、D18（块里携带什么信息） 已定项 9『块』就是单元』推出……而 D5（快照 / 空间记账机制） 定 deadlist 条目按版本身份记、经映射释放，码 2 / 码 3 不进映射就只能按落点记，整理或掉盘重建把它挪走之后会按旧落点释放（三条腿一致）。」

以及 D5（快照 / 空间记账机制）的 deadlist 版本身份记录规则：

> 出处 `.claude/kb/decisions/05-快照-空间记账机制.md:35-37`（整行抄，已在附录中）：
> 「deadlist / livelist 按映射 key 记，搬迁只改映射一条条目，被搬单元逐字节不变、birth 不变。」

**具体序列**：设某个可写头 H 在 checkpoint T1 COW 掉一个码 2 节点 N（旧版本，映射 key = K_old），旧版本 N 由于在 T1 之前还有一个已发布的只读快照 S 存在（S.txg < T1），因此按 D5「引用区间的充要条件」规则，N 满足 `birth(N) ≤ S.txg < death(N)=T1`，S 仍然引用 N；同时活头 H 已经用新版本 N' 覆盖了这个逻辑位置，旧版本 N 不再进入 H 活树，因此按 D5 的判定规则被记入了 H 的 deadlist，**deadlist 条目的 key 就是 N 的映射 key = K_old**（诞生代号=b_old、写序(实例代号)=i_old、出生序号=s_old）。此时若 N 这个物理块本身（虽然逻辑上"死"但物理字节还没被真正释放，仍躺在盘上等快照 S 销毁后才回收）发生介质损坏或被误判丢失，**重建时按甲的规则会给它重发一个全新的身份（新的诞生代号、新的写序、新的出生序号）**——但 deadlist 里记的仍然是旧 key K_old。等到快照 S 最终被销毁，D5 的销毁流程会去 deadlist 里按 `birth ≤ prev(S).txg` 过滤出可释放的条目，尝试释放 key = K_old 对应的物理空间——**但物理上那个位置现在装的是重建出的新节点（身份是 K_new），K_old 这个映射 key 在中央映射里已经查不到对应的物理位置了（因为原物理位置的单元头已经被重建过程改写成 K_new 的身份）。**

**结果分类（这正是失败条款要求判定的那一句"某腿指出 P1 的判据对这一格给不出答案"）**：这既不是 P4 定义的"保守答案"（保守答案的样子是"多压 K 代才清得掉，不会读错"——这里根本查不到，不是"多压代"的问题），也不是 P4 定义的典型"错答案"（"静默读到陈旧指针"——这里不是读到陈旧指针，而是**查找落空，永久不会被这条 deadlist 清扫逻辑处理到**，形成一笔既不会被 I-3.1 已分配统计发现（因为这块空间在分配记录里若仍标记为"已分配"就不会被当成泄漏，但它本该被释放）、也不会被 I-3.6 deadlist 紧界检出的孤儿账目）。

⇒ **这是判据 2 下一个真实的、不依赖 P15 的"甲出局或需要额外规则"的场景**：甲若要站得住，必须补一条规则——**重建一个码 2 节点之前，先检查它是否被任何 deadlist/livelist 条目引用（按落点，因为重建时映射还没建立/已经损坏），若是，重建后的新身份必须与被引用的旧身份完全一致（不能"重发"）**。这实质上把甲收窄成了"对被 deadlist/livelist 追踪的死码 2 节点，甲退化为乙（原样重造）；只对活树里的现行码 2 节点，甲可以真正重发"。这不构成甲的整体出局（判据 1-3 全红），而是甲需要打一个补丁，判据 2 记「只记，需要用户补口径」。

### 二.3 判据 3：乙依赖改写的持有者，有没有一个重建路径覆盖不到

**清单**（在材料给出的父指针、映射条目、树表根指针、deadlist/livelist 条目之外，我核实到的额外持有者）：

1. **D8（核心索引结构）已定项 6 的"身份引用"字段**（26 字节，父节点内部条目结构，与 83 字节的"子指针"是两个独立字段）。对于 inode 树内部节点里指向码 2 子节点的条目（类型段 = 0），身份引用里的出生树字段仍然有效（容器号、出生代恒 0，但出生树非零）：

> 出处 `.claude/kb/decisions/08-核心索引结构.md:349`（整行抄，已在附录中）：
> 「⚠️ 2026-09-12 用户定案（C297）：D19 已定项 7 让子指针头部也带出生树之后，身份引用里的出生树照旧保留——两份并存，加密开不开都占位、不挪作他用……两份同住父节点，不读子节点就能互证」

这是一个**独立于 83 字节子指针的第二份出生树副本**，住在同一个父节点里。若某个码 2 子节点被重建、其出生树发生变化（例如甲用"重建那一代的实例"重发写序/诞生代号，出生树理论上不变，因为出生树多半绑定的是"哪棵树创建了它"而不是"哪一代"——但若丙这条臂或某种极端重建策略连出生树都要重发，就会撞上这两份互证机制）——**这个消费者材料的臂列表没有明确点名，是一个仓里确实存在、但没在三条臂里被逐一处理的持有者**。判据 1 因此有一个小的补漏空间，但**不足以让哪一条臂整体出局**：只要甲/乙保留出生树字段不变（只重发写序、出生序号，诞生代号取下界），这个持有者就不会被打破——因为它记的是"出生树"，不是"写序"或"出生序号"。**结论：判据 1 不红（这条持有者关心的字段不在甲/乙重发的字段范围内），但值得记入六（要改的条款）里作为一条应当被明写的收严。**

2. **树表根指针**——我核实：树表条目里的根指针（D19 已定项 8 里划定的"自举豁免三类"不包括普通树，即 extent 树、inode 树、记账树、分配记录树的根指针都走正常"指向码 2 的节点指针"机制，携带映射 key 各段）。这意味着若一棵树的根节点（码 2）被重建，树表条目里的根指针也必须同步更新为新身份。

**我的判断（推的，基于对提交协议的理解，非直接引用某条明写"重建必须走正常提交协议"的条款）**：写出一个新的根节点，无论是正常 COW 还是重建后的写出，都需要父指针（这里是树表条目）跟着重写——这是 COW 树的基本机制（父指针必须指向子节点的最新物理位置），不是重建专属的特殊路径。D22（单元原子性怎么合成）已定项 7 与 D23（journal 的角色与格式）定义的提交协议本身就要求"改一个节点要沿链改写全部祖先直到根、直到超级块"（这条原则在 D8 已定项 6 表述 inode 树时也重复了一次："更新一条记录 = COW 叶 + 全部祖先"）。如果重建也是通过这套标准提交管道落盘（即，重建的产物必须先经过正常事务提交才能持久化——这正是 D18 已定项 5 划出的"级 2 才可写、级 1 只读不落盘"这条分级规则的题中之义：**只有能双证晋升为可写的重建才会真正落盘，而落盘的动作只能走标准提交协议，不存在绕过标准提交协议直接改写权威态结构的"重建专用写路径"**），那么树表这个持有者会随着标准提交自动更新，不需要"重建"这个操作额外编写一条特殊逻辑去同步它。

⇒ **判据 3 对"树表根指针"这一持有者：不红。** 但这个论证依赖一个**我没有找到直接反面证据、但也没有找到直接正面陈述**的假设——"重建产生的新版本必须走标准提交协议才能落盘"。这是仓里没有明文写清楚、但从已有分级晋升机制（D18 已定项 5）与提交协议的一般设计（D22/D23）合理推出的结论，我标注为**推的**。

3. **deadlist/livelist 条目**——按上面二.2 场景②的分析，这是乙的一个真实缺口：deadlist/livelist 记的是**历史时点上一个已死对象的身份**，它不是"当前活树的持有者"，重建（无论走不走标准提交协议）都不会、也不应该去改写一条已经记入 deadlist 的历史账目（改写历史账目本身就违反 D5 的语义——deadlist 记的是"谁曾经存在、何时死亡"这件事实，不能因为它对应的物理块被重建腾了个新身份就把账抹掉或改写）。

⇒ **判据 3 对"deadlist/livelist"这一持有者：红。乙不能通过"随重建重造"来解决这个持有者，因为重造的语义与 deadlist 记账的语义冲突**——这正好呼应二.2 场景②发现的问题，两处指向同一个洞：**乙的"逐个持有者随重建重造"这句承诺，对 deadlist/livelist 这一类"记录历史身份而非当前身份"的持有者，天然做不到**。

## 三、判据 4：「永久泄漏」算不算保守

场景②那笔账（deadlist 记的 K_old 永远找不到对应物理位置）既不能回收也不会被 I-3.6 检出，这比 P5 说的"泄漏可被 I-3.6 检出、可回收、伤害有上界"更糟——它是一笔**既不可回收、也不可检出**的账。P5 的保守默认纪律本身没有覆盖"检不出的永久泄漏"这一档（它假定的保守方向是"多压 K 代"，隐含最终能被检测/回收）。**这一格判据 4 因此确实被触发，只记，交用户补口径**：保守默认纪律需要为"deadlist 引用对象在重建中丢失原身份"这种情况单独定义一档处置，不能简单套用现有的"取不到就进 deadlist"规则（因为这里恰恰是"已经在 deadlist 里的东西，它引用的身份本身失效了"）。

## 七、结语（不客套，直说结论）

**丙不成立、不需要被认真考虑**——材料自己也只是把丙当"倾向"提出，我核实之后没有找到比甲/乙更强的理由去动 D19 已定项 8 那句已经三轮论证定案的依据。

**甲和乙都大体站得住，但都需要打一个共同的补丁**：对**仍被 deadlist/livelist（按旧映射 key）追踪的死码 2 节点**，重建不能"重发新身份"（甲的字面做法）也不能简单"随重建重造"（乙假设它能被同一次重建自动更新，但 deadlist 记的是历史身份，不该被重建改写）——真正成立的规则是：**这一类节点的物理字节如果丢失，重建必须原样恢复旧身份（映射 key 不变），而不是甲说的"重发"**；只有对**活树里当前引用的现行码 2 节点**，甲的"重发新身份+乙的持有者级联重写"才是合适的处理。这不是三选一，是**甲、乙在两类对象上分别适用**，而材料原本把它们设计成互斥的候选。

**P15 没有被坐实**，我给出的最强证据只是一个类比先例（inode 树，不是被判对象 extent 树本身），结论应挂起等待用户/正推腿补答，但**判据 2 里不依赖 P15 的那一支（deadlist/livelist 场景）现在就能判**，不必等 P15。

**「原值一个消费者都没有」这句理由确实已经不成立**——这一点材料的前提本身没有争议，我的反推没有找到任何理由让它重新站得住；本轮真正开放的是**理由重写之后，重建规则要不要为"仍被历史记账结构追踪的死码 2 节点"单独开一条子规则**，这是一个新问题，超出了 C292 原本"理由怎么写"的范围，值得单独立一条欠账。
