BACKGROUND

singlefs writes its journal into a fixed-size ring buffer on each device (the "journal ring"). The filesystem is being changed so that, on top of the ring's existing behavior, an administrator will also be able to set an explicit maximum and an explicit minimum for the ring's length, in addition to whatever default maximum and default minimum the filesystem ships with. This round only asks about the ring's length bounds and about what the on-disk configuration area stores. It does not ask about crash safety of shrinking a ring, about whether shrinking after creation should be allowed at all, about who decides "the device is out of space" or when, or about whether recording the ring's length change requires a format-compatibility bit. Do not answer any of those other questions even if they seem related; they are being handled by other reviewers in this same round.

FACTS

FACT 1. Today, the ring's length is a parameter supplied once, at filesystem-creation time ("mkfs"), with a default value of 768 MiB. Exactly one constraint is enforced on this parameter: ring length must be less than or equal to (the capacity of the smallest device in the pool, divided by 4); filesystem creation is refused outright if the supplied ring length exceeds this bound. The on-disk system configuration area stores only this one field for the ring's length (in bytes); it does not separately store the device's capacity or any ring-to-capacity ratio. There is no lower bound of any kind enforced on the ring's length today, and a repository-wide search finds no mechanism anywhere for changing the ring's length after filesystem creation.

FACT 2. The stated reason for combining "a parameter" with "an upper bound" (FACT 1) is: on a large device, the fixed default of 768 MiB ends up occupying only a small percentage of that device's capacity, while a small device gets a small ring because the administrator supplies a small parameter value at creation time; the upper bound's only job is to stop the ring from consuming the entire device.

FACT 3. A separate, already-settled design decision governs two different on-disk fields, called T_dirty and T_time, that sit inside one and the same decision item, and states explicitly that they follow two different rules from each other. For T_dirty: only the runtime effective value is reduced -- effective T_dirty = minimum(the value stored in T_dirty's on-disk field, ring length divided by a constant safety factor F) -- and the on-disk field itself is left exactly as originally stored, completely unmodified, no matter how much smaller the effective value ends up being. For T_time, by contrast: a user-supplied value outside its recommended range of 200 ms to 5 s is accepted exactly as given, overwrites the on-disk field outright, and is written back to disk as given; only a warning is produced, and no value is ever substituted for it. The already-settled text states, about these two fields sitting in the same decision item: "two fields, two rules; do not read them under the same rule."

FACT 4. A separate, already-settled invariant about the ring's geometry reads: "ring size >= F times the worst-case per-transaction journal usage, where F >= 2." The invariant's own text further specifies that both the worst-case-usage quantity and F are meant to be written into the on-disk system configuration, computed once at filesystem-creation time, and then recomputed and compared again at every mount. As of today, the automated checker meant to enforce this invariant is not implemented for this particular invariant; it exists only as written text, with nothing currently checking it.

FACT 5. An independent, already-completed check found that the specific on-disk field which is supposed to hold "worst-case per-transaction journal usage" (the quantity FACT 4's invariant multiplies by F) is not actually computed from any transaction-related quantity at all. It is instead computed purely as (ring length) divided by (the constant safety factor F). Substituting this into FACT 4's invariant produces "ring length >= F times (ring length divided by F)", which algebraically simplifies to "ring length >= ring length" -- true no matter what the ring length is, with the computed safety margin always coming out to exactly zero. As implemented today, this field carries no information distinct from the ring length itself.

FACT 6. A separate, already-completed piece of bookkeeping about a known mismatch between two design rules (about how one write gets split into journal records) states, as a directly measured fact, that the true worst-case journal usage of any single transaction, computed independently of the ring's length, is 12 KiB. (The same bookkeeping also gives a much larger number under a different reading -- the journal usage of an entire full window of buffered dirty data, rather than of one single transaction -- but that different reading is not used anywhere in this round's questions.)

FACT 7. Among the on-disk fields that this round cares about (the system configuration area also stores other fields, for other purposes, that this round does not ask about), exactly four fields relate to the ring's length and to the worst-case-usage-and-safety-factor bookkeeping from FACT 4: field W, the ring's length in bytes (the same field named in FACT 1); field X, an "in-flight record limit" stored as a whole number of records, computed at filesystem-creation time as (ring length in bytes) divided by (a fixed record size of 4096 bytes) divided by (the constant safety factor F); field Y, the same in-flight limit re-expressed in bytes, computed as field X's record count times 4096; and field Z, the constant safety factor F itself. F is a fixed compile-time constant equal to 3 everywhere in the codebase; it is not read from disk at mount time, and there is no mechanism anywhere for a user to configure it. Fields X, Y and Z are all computed purely from field W and the compile-time constant F; none of them is computed from, or capable of independently storing, any quantity that is not simply derivable from field W and F alone. A repository-wide search for any stored field representing a user-configured minimum ring length, or a user-configured maximum ring length distinct from the capacity-divided-by-4 rule in FACT 1, or any field at all named or documented as a minimum or maximum for the ring, returns zero matches anywhere in the filesystem's on-disk format or configuration source code.

QUESTIONS

G1.same-or-different: FACT 3 establishes that two fields sitting inside one and the same decision item are allowed to follow two different rules from each other. Group G2: suppose the new default minimum ring length is set to exactly F times the true worst-case per-transaction usage from FACT 6, that is, 3 times 12 KiB = 36 KiB.
