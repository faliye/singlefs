# C68 单元头收口·正推腿（sonnet）原样输出（2026-09-02）

FORWARD DERIVATION ON F12 (C68/C69 unit-header closure)

Method: for each sub-item I trace which already-settled decision or invariant text the sub-item either restates, extends, or would need to override, and classify accordingly.

(a) Field table, 47 bytes. Forced components: five-tuple 33B (D18 item 3, F2) and declared-length 2B (D4 item 6, F11) are both settled and unconditionally required — nothing optional here. Header checksum 4B is not itself settled text; D18 open-item-7's skeleton (F4) still lists "头校验和" as pending. But E85 (F8) shows the literal minimal set (five-tuple+length, 35B) cannot judge header self-integrity or support the scanner's magic probe, and E86 (F9) shows scan-rebuild's interior-probe rejection depends on a header checksum. So including it is not forced by prior text but is the only way to make (c)/(d)'s scan-rebuild claims actually work — permitted, and functionally necessary for the rest of F12 to be coherent. Verdict: adopt-with-amendment — D18 open-item-7's "待定" row for header checksum must be flipped to settled as part of this same commit, not left dangling.

(b) fsid dropped from header. This is not a new decision at all: D18 open-item-7's skeleton already records "已裁定不加" for fsid, citing D9 item 8 (KDF-based cross-volume binding) and registering the unencrypted gap as C74. F12(b) only writes this into I-1.4's wording. Verdict: adopt, forced — I-1.4's current literal text (F3) is already stale relative to settled D9/D18 text; this closes that staleness, not creates a new choice.

(c) block birth dropped from header. Forced by two already-settled pieces: F5 (D4+D5) puts both birth txg and checksum on the parent-pointer side for any reachable block, and D22's 已定一/已定二 already proved checksum-in-parent alone catches all torn-write outcomes including "全旧" without needing a self-declared generation field — that argument predates F12 and directly makes a per-unit block-birth field redundant for reachable blocks. For scan-rebuild (no parent available), F6 (D3 item 1's per-drop-point predicate, E59-measured) already answers exactly the stale-vs-current question a lineage field would have answered, and D18 item 1 already rejected the lineage-sequence candidate on that ground. "Incremental-scrub watermark walks pointers anyway" is a direct, permitted corollary of F5 (scrub walks the tree, so it has the parent's birth txg available) — not previously written down, but not contradicted by anything. Verdict: adopt — but D18 open-item-7's "待定" row for block birth generation must also be resolved (answered by existing mechanism, not by a field), matching (a)'s amendment.

(d) I-1.1 defined per unit class. For data units, five-tuple-minus-type-and-generation = (tree, object, anchor offset) is a natural, permitted reading of D18 item 3's already-settled fields; nothing forces this exact carve-out but nothing contradicts it either. For index nodes, (tree, level, key range) is directly forced by D18 item 2 (F7), whose own stated payoff — "一个节点单独捡起来能自证它该覆盖哪一段 key" — is precisely I-1.1's scan-rebuild framing. This does not, however, resolve the separate and still-open problem flagged in D9's 未定项9 (F7): with lineage_seq rejected, btree nodes still lack a defined AAD identity field; key_range is not obviously safe for that role (splits/merges change coverage) and F12(d) never claims to answer it. On the named focus question: journal records and root slots are exempt from I-1 class, not merely unaddressed by it. D21 已定项4 already classifies self-certifying units as lacking a checksummed parent pointer and explicitly states their failure mode is a crash-recovery problem, not a scan-rebuild problem — which is I-1 class's entire domain. Their self-certification is already covered, under different numbering, by I-7 (root ring) and I-8 (journal). Verdict: adopt for data/index rows; amend by adding an explicit I-1-class exemption note pointing to I-7/I-8, since invariants.md's existing "扩大到任一单元" note (written before D21 已定项4) reads as if journal/root should get I-1 rows too, which would now be wrong.

(e) Two whitelists. The metadata list (unchanged six) and the data list (five-tuple plus nonce+MAC) are each forced by prior settled text: F1 for the six-item list, F2+F1's nonce/MAC pair for the data list — this is not a new tradeoff, it is naming what was already true once F2 existed. On the flagged risk (metadata five-tuple/key-range into ciphertext vs. scan-rebuild): D21 (F10) already states keyless metadata rebuild is impossible, only scrub — so F12(e) does not newly break anything. E28's clean 0/1024 metadata-reconstruction result does not contradict this: E28 tests whether unit self-description headers suffice for rebuilding the plaintext mapping layer, and nothing in its citation (D18 item 3) says it ran with encryption on; its positive metadata result is a general/unencrypted-case demonstration, not evidence that encrypted metadata reconstructs. No genuine conflict — but I-1 class's checker behavior for encrypted metadata (I-1.1 becomes unjudgeable without keys) needs the same "report N/A, don't silently pass" treatment I-6 class already mandates for itself; that clause does not currently exist for I-1.
