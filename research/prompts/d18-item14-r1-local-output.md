1. In arm C, the whitened nonce is stored in plaintext but appears unordered. An attacker can sort all units by their physical disk offset. In a copy-on-write filesystem, newer writes typically appear at higher physical offsets due to sequential allocation. By comparing the whitened nonce values across sorted physical offsets, the attacker observes that the sequence of whitened nonces correlates with write order. For example, if unit A at offset 100 has whitened nonce X and unit B at offset 200 has whitened nonce Y, and X < Y when sorted by offset, the attacker infers unit B was written after unit A. This correlation exists because physical offset directly reflects write time regardless of whitening, making the whitening irrelevant for hiding order.

2. In arm A, the full 96-bit counter nonce is stored in plaintext. An attacker directly observes the exact counter value for every unit, allowing precise reconstruction of the entire write sequence. For example, nonce 500 is older than nonce 501. Arm C does not remove this leakage; it only obscures the nonce value itself. The physical offset of units still reveals write order, as demonstrated in part 1. Thus, arm C makes the leakage nonce harder to interpret only by requiring the attacker to sort by physical offset instead of reading the nonce directly, but the underlying information remains accessible.

3. All replicas of an extent share the same nonce. If an attacker modifies edits one replica's ciphertext to a different value while keeping the nonce unchanged, the filesystem will detect inconsistent ciphertexts across replicas during read operations. However, if the attacker also modifies the payload CRC in the corrupted replica to match the new ciphertext, the filesystem might accept the corrupted data as valid. For example, if the original payload is "hello" and the attacker changes it to "world" while adjusting the CRC to validate "world", the filesystem will use the corrupted data without error checks. This allows data tampering without triggering corruption alerts.

4. In arm B, the pointer's nonce copy is deleted, leaving only the unit's header as the nonce source. If an attacker corrupts the unit's header nonce during a partial write operation, the filesystem cannot recover the correct nonce. For example, during a system crash, only part of the unit header is written, resulting in an invalid nonce. In arm A, the pointer's copy would still provide the correct nonce for decryption. In arm B, this corruption causes permanent data loss because there is no backup nonce source, whereas arm A would use the pointer's nonce to decrypt the unit successfully.

5. The assumption that the scan rebuild path must decrypt units to identify them is most likely false. The observation that would reveal this is that the unit class code, fsid, and payload CRC are already in plaintext. These fields alone could allow the scan rebuild to reconstruct the index trees by matching units to known structures without needing to decrypt identity fields. For example, the unit class code identifies the unit type, and the payload CRC can verify data integrity during rebuild. If the scan rebuild works correctly when identity fields remain plaintext, the assumption that they must be encrypted is invalid.
