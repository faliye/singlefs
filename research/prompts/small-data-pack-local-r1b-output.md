1. The claim cannot be defeated. The first reason blocks implementation: the writer must read the next unit's header to determine its class code before placing leftover slots. This violates the project rule that space accounting must answer immediately without traversal, as reading another unit requires disk I/O. A different data structure cannot remove this because any method to locate the next container would require accessing disk data (e.g., a separate index would need to be read, which still requires traversal). The second reason also holds—modifying an existing container requires rewritingopy-on-write for all its objects, updating their mapping entries—but the first reason alone is sufficient to block the proposal.

2. The two encodings are distinguishable in failure behavior. For a reader unaware of containers: if using zero payload and nonzero flag bits, the unit is rejected due to invalid flag bits (since flags must be zero in version one). If using a new registry code, the unit is rejected due to an unregistered class code. For a scanner rebuilding the index, these produce different error messages (e.g., "invalid flags" vs. "unregistered class"). For encryption associated data, the class code is part of the domain separator; a new code changes the associated data, while using the same class code with nonzero flags causes rejection before encryption occurs, making the encryption behavior different. Thus, the reviewer's claim is valid.

3. Consider 303 small objects of 100 bytes each and 303 large objects of 32768 bytes each. Padded space: 303×32768 (small) + 303×32768 (large) = 606×32768 bytes. Container packing: 1 container unit (32768 bytes) for small objects + 303×32768 (large) = 304×32768 bytes. After deleting 99.67% of small objects, remaining small objects = 303×(1−0.9967) ≈ 1.01 → ceil(1.01/303) = 1 container. Container space = 1×32768 + 303×32768 = 304×32768. Padded space = 1×32768 + 303×32768 = 304×32768 (exact equality). For deletion fraction >99.67%, e.g., 99.7%, padded space = 303×(2−0.997)×32768 = 303×1.003×32768 ≈ 303.909×32768, while container space remains 304×32768. Thus is cheaper only up to ~99.67% deletion; beyond this, padding is cheaper.
