1. At lock time, key side signs live slot table marking slot Y as 'dead'. After locking, key side pins slot Y for a new stripe. Keyless mount reads stale live slot table (CRC32C valid), moves data from X to Y, overwriting Y's original stripe data. At unlock, key side verifies table signatures, replays move, but current state shows Y as pinned—rejects move. Y's original stripe data is lost permanently; system reads corrupted data silently. Rule broken: stale live slot table causes data loss despite CRC32C pass. Smallest fix: keyless mount must not write to destination slot until key side verifies move during unlock; move operation must be deferred to key side after verification.

2. At lock time, key side signs lease area definition page in tables. Keyless mount moves data to destination slot within lease area. At unlock, lease area definition page signature fails. Key side rejects all moves in that page but cannot identify lease area slots due to invalid definition—no party knows which slots are in lease area. Destination slots are written but unreclaimable; key side lacks lease area mapping to reclaim them. Rule broken: invalid lease area definition page makes slots unreclaimable. Smallest fix: store lease area definition in a separate, always-trusted structure not subject to table signature checks.

3. At lock time, stripe membership snapshot lists columns 1,2,3. During lock, column 3 is replaced with column 4 (authoritative membership now 1,2,4). Keyless mount rebuilds lost column using stale snapshot: computes data for column 3 from 1 and 2, writes wrong data to slot. At unlock, key side verifies move and compares rebuilt data against authoritative membership (1,2,4)—detects inconsistency. Wrongness is detectable at unlock by key side during replay verification. Rule broken: stale stripe membership causes incorrect rebuild. Smallest fix: key side must include current stripe membership in signed tables at lock time, ensuring snapshot reflects actual state.
