## 反例 1（崩溃类）：树 ID 水位的超级块写入时机未定义 —— checkpoint 已发布、水位未跟上，下次分配撞号

### (a) 事件序列

1. mkfs 一个 2 盘池，mount M1。稳态：全部超级块副本上树 ID 水位 = 300（一致）。
2. checkpoint txg=400：M1 建一棵新树（克隆或快照），分配到树 ID = 301。按 D16（发布语义）
   已定项 7 的持久顺序发布：COW 单元/节点 → 屏障 → journal 记录 → 屏障 → 根槽（FUA）。
   根槽落盘那一刻，树表条目（含树 ID=301 那一行）已经**durably** 可从新根走到。
   树 ID=301 的对象自己也写出了自描述头，头里 `树 ID` 字段 = 301
   （D18（块里携带什么信息） 33 字节五元组，见下引用）。
3. 超级块段四的树 ID 水位字段**这一步还没有被回写**——它不在上一步的持久顺序五步之内
   （下面 (d) 引用证明这一步的更新协议是独立于 checkpoint 持久顺序的另一件事）。
4. **崩溃点**：txg=400 的根槽 FUA 完成之后、超级块水位回写完成之前，断电。

### (b) 观察点

重挂 M2。

### (c) 观察到什么

全部超级块副本的树 ID 水位字段仍读到 300（陈旧，回写没来得及发生）。
按定案②「取多副本 max + 1」，M2 算出的下一个可分配树 ID = 300 + 1 = **301**——
与已经**durably** 发布、且已经在盘上写出了自描述头的树 301 **撞号**。

### (d) 违反的条款

**违反今天的定案②本身**（08-核心索引结构.md:432，节选）：
> 「② 树 ID 水位取『超级块多副本取 max』——与 D18（块里携带什么信息） 已定项 11 的实例代号同装置
> （写进独占打开成功的全部超级块、取 max + 1）。」

——这句话只定了**取值公式**，没有定**这个字段相对 checkpoint 持久顺序何时回写**。
而“同装置”那半（D18 已定项 11）明确是**挂载时一次性**写入、**在动任何单元之前**完成
（18-块里携带什么信息.md:697，节选）：
> 「……写进那个集合里的每一份超级块、全或无……之后才动任何单元；只读挂载不取号；从 1 起、0 无效。」

树 ID 水位却需要**每次建树都推进**，不是挂载时一次性——这与实例代号的更新频率
（每挂载一次）在数量级上不同。而超级块段四这整组「运行时水位」字段（journal tail +
实例代号 + 今天新加的树 ID 水位）里，**唯一已经写下更新协议的那个字段**（journal tail）
明确是**发布之后异步回写**，不在持久顺序五步之内（23-journal的角色与格式.md:777，节选）：
> 「2 | 只在 checkpoint 持久之后写一次，不上 fsync 路径 | 稳态开销因此是每 checkpoint
> 一次，不是每 fsync 一次。」

tail 的陈旧是安全的，因为它有「全环扫描 + 幂等重放」兜底（同文件 789 行：
「必须先全环扫描、逐条验证，再择最长合法前缀」）。树 ID 水位没有等价的兜底——
定案②的正文自己**明确否掉**了唯一可能的兜底（扫描树表取真实最大值）：
> 「挂载时从树表扫最大值 + 1（btrfs 那条路）同样被回退打穿——被抛弃 checkpoint 里
> 分配过的树 ID 不在已发布的树表里。」（08-核心索引结构.md:432）

于是树 ID 水位继承了 tail「异步回写、崩溃可陈旧」的更新时机，却没有继承 tail
「陈旧了也安全」的兜底机制——这个组合正是撞号的根源。

### (e) 打中哪里

**打中今天的定案②**。这不是老决策的旧洞，是②把树 ID 水位放进「E100 段四」这个
字段组时，没有连带说清楚更新时机应该照哪一个字段的先例（挂载时一次性 vs.
每 checkpoint 一次），而这两个先例的崩溃安全性并不等价。

## 反例 2（崩溃 + 回退叠加）：陈旧水位跨回退边界复用树 ID，破坏五元组身份的跨时间线唯一性

这条把反例 1 的机制接到「回退」场景上，因为②的存在理由正是「防止回退把号退回去」，
这里检验它是否真的做到了。

### (a) 事件序列

1. 承反例 1 步骤 1–4：崩溃后超级块水位陈旧在 300，而树 301 已经带着自描述头
   （`树 ID=301`）durably 存在于盘上（挂在 txg=400 那次发布之后的根链上）。
2. M2 挂载后**没有走反例 1 的路径**，而是管理员出于别的原因（例如 txg=420 时发现
   数据损坏）执行**回退**：从根环候选集里选 R_old = txg=380 的根（早于 txg=400，
   树 301 在 R_old 的树表里不存在）。
3. 按 D23（journal 的角色与格式） 已定项 14 执行回退：不施加 R_old 之后的任何记录、
   取新实例代号、写回退行，第一个新根的 checkpoint_txg = 根环里全部根记录 txg 的
   最大值 + 1（含被抛弃的 txg=400，所以新 txg 严格大于 400）。**全部记账统计量的
   现行值从 R_old 那棵账重新载入**——但树 ID 水位**不在记账里**（这正是②把它挪出
   记账的理由），所以它**不参与这次重载**，继续从超级块读，读到的还是陈旧的 300。
4. 回退发布之后，新时间线上再建一棵树：读超级块水位 max=300，取号 = **301**。

### (b) 观察点

对盘做一次全盘扫描（本工程「最后一道恢复手段」，`.claude/rules/fs-design.md`「元数据块
必须自描述」）。

### (c) 观察到什么

盘上同时存在**两个物理上不同、但自描述头里树 ID 字段都是 301** 的对象群：
一个是步骤 1 中、被回退抛弃的时间线里的树 301（其块从未被显式擦除——回退协议
只处理「记账统计量」「defer 队列」「分配器游标」，没有一条条款要求立即清除被
抛弃的未来时间线已经写下的物理块）；另一个是步骤 4 里、回退之后新时间线上刚建的树 301。

### (d) 违反的条款

违反 D18（块里携带什么信息） 已定项 11 里给数据单元定的身份五元组的隐含前提——
**同一个 (树 ID, 对象 ID, 对象出生代, 锚点偏移) 元组必须在全盘生命周期内唯一**
（否则「元数据块必须自描述」这条纪律失效，见 `.claude/rules/fs-design.md`）：
> 「五个字段的宽度已定（2026-09-04，用户定案）：单元类型标签 1 + 树 ID 8 + 对象 ID 8 +
> 对象出生代 8 + 锚点偏移 8 = 33」（18-块里携带什么信息.md:253）

也直接违反 D6（快照实现模型） 九条判据第 9 条对**任何**被采纳的快照/树标识方案的
硬要求：
> 「9 | 标识不回收 + 布局无关：快照标识单调不回收，位宽写进格式并声明生命周期内
> 创建总数上界 | 回收一个快照 ID 会让盘上遗留的旧 key 在新快照里变成可见，与
> C11（feature bit 跳号） 同型。」（06-快照实现模型.md:110）

而定案②的全部论证前提正是「取多副本 max 能防住回退把号退回去」——本反例说明
这个防护**只在超级块水位本身没有陈旧的前提下成立**，一旦反例 1 的崩溃窗口先发生，
②对回退场景的防护就是空的。

### (e) 打中哪里

**同时打中今天的定案②，和一条更早的已定条款**（D6 已定项 9、D18 已定项 11 的
33 字节身份元组）。②号称要保护后两者不被回退破坏，本反例说明它在
「崩溃缺口 + 回退」复合路径上没有真正保护住。

## 反例 3（快照删除类）：销毁快照要求「可分批」，但树表条目一删、deadlist 尾段就失锚

### (a) 事件序列

1. 建活头 H，txg=50 时建快照 S（定案①：树表条目，诞生 txg=50）。之后 H 长期运行、
   反复删除，deadlist(S) 累积到数千万条（D5（快照 / 空间记账机制） 明确允许 deadlist
   规模随运行时间无上界增长，惟一的界是「按 birth txg 分桶」带来的局部性）。
2. txg=2000：管理员发起「销毁 S」。S 不是分叉点（`children == 1`），允许销毁
   （D5（快照 / 空间记账机制） 已定项：「分叉点快照不许销毁」的判据是 `children > 1`，
   05-快照-空间记账机制.md:131）。
3. 因为 D5 的销毁算法要求「把它的 deadlist 合并到下一个更新的那一侧，并按
   `birth > prev(S).txg` 过滤出可释放的条目」（05-快照-空间记账机制.md:6-7,9），
   而 deadlist(S) 规模是 O(千万)，单个 checkpoint 内不可能把这个过滤 + 合并一次性
   做完（对比：本工程对**任何**大规模操作的既定纪律是「写意图 → 分批 → 可续做」，
   `.claude/rules/fs-design.md`：「后台、可续做、非决策路径（销毁快照、整理、scrub）
   | 无戒律 | 它们走『写意图 → 分批 → 可续做』」，fs-design.md:25）。
4. 假设实现按这条既定纪律拆批：checkpoint txg=2000 先把 S 的**树表条目移除**
   （S 不再在任何活跃枚举里出现），同时写一条「销毁意图」记录指向 S 原来的
   deadlist 根，此后若干个 checkpoint（txg=2001…2050）逐批把 deadlist(S) 的
   条目过滤、合并进 H 的 deadlist。
5. **崩溃点**：txg=2010（只处理了一小部分批次）之后断电。

### (b) 观察点

重挂之后跑 checker：枚举「全部活快照」（I-3.7 要求的那个持久结构），
再跑「deadlist 紧界」检查（I-3.6）。

### (c) 观察到什么

I-3.7 那一半是对的：S 已经不在树表里，枚举不到它——「既不多也不少」按字面成立。
但 I-3.6 那一半查不出「deadlist(S) 剩下没处理的那尾段（txg=2011 之后原计划要合并的
条目）现在挂在哪」——因为**S 的树表条目已经删了**，而 D5、以及今天的③号定案，
都没有给出「一个正在被销毁、尚未处理完的快照，它剩下的 deadlist 尾段应该挂在
哪个持久结构上」这个问题的答案。④号定案给树表条目留的「16 字节预留」明确是
**未分配**的兼容位（decisions-history.md:27：「每条 2 字节 + 16 字节预留」），
不是已经承诺要装「销毁进度游标」的字段。这尾段的条目变成**既不在任何活引用里、
也不在任何 deadlist 里**的悬空块——只会在容量记账上表现为「总账记的已分配量」
与「遍历得到的量」不一致，或者更糟，被后续分配器当成空闲空间提前复用。

### (d) 违反的条款

**违反 D6（快照实现模型） 九条采纳判据第 5 条**（本身是已定条款，不是本反例现造的）：
> 「5 | 有界销毁：可分批、可续做，每批最坏空间需求有界且可在批前预留 |
> D3（空间分配）『释放空间不需要申请空间』。⚠️ D5（快照 / 空间记账机制） 在这一格是
> 用『分叉点快照不许销毁』这条功能缺失回避掉的，不是满足」（06-快照实现模型.md:106）

这行本身已经写明「不是满足」——本反例只是把这句抽象警告变成一条能在真机上复现
的具体序列：**只要销毁一个非分叉点、大 deadlist 的快照，且实现按本工程唯一给出的
纪律（写意图 → 分批 → 可续做）去分批，第③④两个新字段都没有为『分批到一半』
这个中间态留出持久锚点**，与 I-3.6（deadlist 紧界，05-快照-空间记账机制.md 引用
经 invariants.md:120）冲突。

### (e) 打中哪里

**主要打中今天的③④两项**（它们本该、却没有借这次机会给出一个「销毁进行中」的
持久表示），间接坐实一条更早、已经在正文里被自陈「不是满足」的条款
（D6 已定项 9 判据第 5 条，06-快照实现模型.md:106）——今天关闭树表条目问题的
机会窗口过去了，而这个已知窗口没被这次定案带上。

## 反例 4（设备集合变化）：纯粹换设备集合构造不出反例；能构造出的是「与反例 1 叠加」的更强后果

### 先说结论

**只换设备集合、不叠加崩溃，构造不出反例。** 原因是过半判据本身的代数性质：
D2（RAID 条带策略） 已定项 13 定义的「过半」（devs=4 时任意两个 3-元子集，
或更一般地任意两个多数集）两两相交（02-RAID条带策略.md:388，节选）：
> 「盘数 ≤ 3 时任意两个够 w 下限的集合本来就相交，过半不多要什么；盘数 ≥ 4
> 之后两个互不相交的 2 元子集就存在了，那时过半是唯一还成立的那道闸。」

而定案②的取值公式「写进独占打开成功的**全部**设备、取 max + 1」与
D18 已定项 11 描述的「写入集合取独占打开成功的全部设备」（18-块里携带什么信息.md:697）
逐字一致——只要每次成功的写确实覆盖了那次挂载打开的**全部**设备（不是只写过半），
下一次挂载的多数集必然与上一次的写入集合相交至少一台设备，那台设备携带的水位
就不会低于上一次真正写出的值。我尝试了「M1 开 {D1,D2,D3}（D4 离线），D4 回来、
D2 掉线，M2 开 {D1,D3,D4}」这类构造，交集恒有 D1/D3 命中，水位不退。

### 但它与反例 1 叠加会更糟

反例 1 已经证明「树 ID 水位的回写不在 checkpoint 持久顺序之内，可以在崩溃时整体
缺席」——这个缺席是**对这次挂载打开的全部设备同时缺席**（因为回写还没发生，
不存在『写了一部分设备』的中间态）。这意味着设备集合切换在这里**帮不上忙**：
即使下一次挂载换了完全不同的设备子集，只要它与上一次挂载存在交集（过半保证
一定存在），那台交集设备携带的也是**同一份陈旧值**，不会因为换了挂载路径而变新鲜。
**换句话说，设备集合变化这个维度对反例 1 的暴露面没有放大，也没有缩小**——
真正的缺口仍然是反例 1 那条：水位回写没有被纳入 checkpoint 的原子发布顺序。

### 结构性的、非时序的一处不对称（不构成独立反例，但值得记录）

树 ID 水位与实例代号号称「同装置」，但取值公式**不对称**：实例代号的 max 明确取
两个独立来源——「这次挂载独占打开成功的那个集合里各超级块的代号」**与**
「根环里全部根记录的实例代号」两者的 max（18-块里携带什么信息.md:697），
后一半由 I-7.7（超级块实例代号不低于根环，invariants.md:52）钉死为不变量，
给实例代号一条独立于超级块的第二见证。树 ID 水位的取值公式**只有前一半**——
定案②原文只写「取『超级块多副本取 max』」，根记录字段表（D22（单元原子性怎么合成）
已定项 7，22-单元原子性怎么合成.md:385-394）里也确实没有树 ID 相关字段。
这是一处真实的结构差异：树 ID 水位比实例代号少一层独立见证。
但如反例 1/4 的分析所示，这处不对称目前**没有被利用出一条独立于反例 1 的
反例**——它只是让反例 1 的伤害没有第二重保险可以兜底。

### 结论对哪一类判定

**这一类（纯设备集合变化）构造不出独立反例**——过半交集的代数直接挡住。
能给出的是一个否定性结果：定案②沿用 D18 已定项 11 的「过半交集」论证时，
默认了「每次该写的设备都真的写到了」，这个默认本身在反例 1 里已经不成立，
而设备集合变化不改变这一点。

## 反例 5（多快照并发）：同一 checkpoint 内建两个快照，诞生 txg 相同，链序失去消歧键

### (a) 事件序列

1. 活头 H，当前开放的 checkpoint 窗口尚未关闭（D16（发布语义） 明确允许**同一
   checkpoint 窗口内的多批**只走一次到根：「checkpoint → 同一窗口内的 K 批只走
   约一次」，16-发布语义.md:65-66）。
2. 在同一个窗口内，用户脚本连续两次对 H 发起 `快照创建`（例如两次 `subvolume
   snapshot` 调用之间没有强制 fsync/新 checkpoint 边界）：
   - 调用 A：把 H 当前 deadlist（记为 D0）整体交接给新快照 S1，H 的 deadlist 清空，
     H.prev_snap_txg 置为**本次 checkpoint 即将拿到的 txg**（记为 T）。
   - 调用 B（紧随其后，仍在同一窗口内）：把 H 当前 deadlist（此时是空的，因为
     调用 A 刚清空）交接给新快照 S2，H.prev_snap_txg 仍置为 T（同一个值）。
   （交接算法引用 05-快照-空间记账机制.md:8：「建快照时把活头的 deadlist 整个交接给
   新快照，活头换一个空的」。）
3. checkpoint 关闭，取号 txg = T，一次性发布。按定案①，S1 与 S2 的树表条目
   **诞生 txg 都写成 T**（定案①口径：「快照发布那一次 checkpoint 的 txg」，
   08-核心索引结构.md:432：「诞生 txg 的口径按用户 2026-09-06 定：快照完成
   （发布）那一次 checkpoint 的 txg」）——S1 与 S2 的诞生 txg **相等**，
   仅有的区分是各自不同的树 ID（S1 < S2，因为②的水位单调递增，S1 先分配）。

### (b) 观察点

之后管理员销毁 S1（保留 S2）。按 D5（快照 / 空间记账机制） 的销毁算法：
「销毁快照时把它的 deadlist 合并到下一个更新的那一侧，并按 `birth > prev(S).txg`
过滤出可释放的条目」（05-快照-空间记账机制.md:9）。

### (c) 观察到什么

「下一个更新的那一侧」（S1 链上的 next）需要靠**链序**判定，而链序在现有格式里
**只能靠诞生 txg 排序**推导——今天①③两项都没有给树表条目加一个「同一 checkpoint
内的创建序号」这类消歧字段。S1、S2 诞生 txg 相等（都是 T），单靠 txg 排不出
「S2 在 S1 之后」；如果实现退而求其次改用树 ID 排序（S1 的树 ID < S2 的树 ID，
因为②保证水位单调递增、S1 先分配），这条 tie-break 规则**在正文的四条定案里
一个字都没写**——它是一个隐含假设，不是格式承诺。一旦将来任何实现选择了别的
分配顺序（例如两个创建请求并发提交、由锁的调度顺序决定谁先拿到树 ID，而
不是由「哪个逻辑上更早」决定），S1/S2 的物理链序就可能与直觉相反，
销毁 S1 时把 deadlist 错误地并给了本该在它之前的那一侧。

### (d) 违反的条款

**这正是 D5（快照 / 空间记账机制） 自己在别处点名过的同一类危险，只是这次危险
出现在「快照与快照之间的链序」上，而不是原文点名的「同一个块的两个引用」上**：
> 「前提 3 与 reflink / dedup / 块克隆机制上不相容：有第二个活引用时摘掉其中一个
> 不构成 death，而判据只看 `birth` 与 `prev_snap_txg`，**两个引用的 birth 完全
> 相同** ⇒ 第一次摘除就判『立即释放』⇒ 另一个引用悬空 ⇒ 数据丢失。」
> （05-快照-空间记账机制.md:80-82）

原文警告的是「两个引用 birth 相同」；定案①把「快照诞生 txg = checkpoint txg」
钉成格式字段之后，**同一个 checkpoint 窗口内建的多个快照，诞生 txg 必然相同**
——这是①带来的新组合，原文那条警告没有覆盖到「快照本身互相之间」这一层，
因为在①之前，快照要不要有格式级诞生 txg 字段根本还没定案。

### (e) 打中哪里

**打中今天的定案①**。它把「诞生 txg = checkpoint txg」钉成 8 字节格式字段，
却没有说清楚「同一 checkpoint 内建多个快照时，它们之间的销毁链序靠什么字段
消歧」——这不是一个已经被别处回答过的老问题，是①第一次让这个问题变得
可以被观测到（此前树表里连快照条目都不存在，链序问题无从谈起）。

| 类型 | 能否构造反例 | 打中 |
|---|---|---|
| ① 崩溃（水位写入时机） | **能**（反例 1） | 今天②本身 |
| ② 回退 | **能**（反例 2，叠加反例 1 的机制） | 今天②，及更早的 D6 判据 9 / D18 五元组 |
| ③ 快照删除 | **能**（反例 3） | 今天③④，坐实更早的 D6 判据 5（正文已自陈「不是满足」）|
