## 一、逐臂按 U1（重建）论证

**丙（不加；重建时重新编 key 首段）——U1 下不构成正确性失败，只丢局部性。**

关键机制：extent key = `(locality_id, inode, offset)`，而 **inode 号本身在一棵树内已经单调不复用**（D8（核心索引结构） 已定项 6，`.claude/kb/decisions/08-核心索引结构.md:622` 一带："已发布的 inode 号单调不复用……唯一性靠 (树 ID, inode)"）。这意味着 `(inode, offset)` 这一半已经把一个对象在一棵树内的每个数据位置唯一钉死，**`locality_id` 对唯一性的边际贡献是零**——它只改变同一批 key 在排序遍历时"挨不挨得近"（局部性），不改变"是不是同一个 key"（正确性）。这正是前提三"它是提示，不是正确性的一部分"这句话的机制根据，不是空话。

由此逐场景过 U1 四种情形：

1. **inode 记录丢了、extent 树还在**：扫该对象在 extent 树里幸存的任意一条 key，取其首段，回填进重建的 inode 记录。inode 记录与 extent key 首段由构造保证相等。无正确性风险。
2. **extent 树也要重建**：extent 树（码 2 内部节点 + 叶）整体丢失，意味着**这一棵树里所有对象**的 extent key witness 同时消失（不是只丢这一个对象的），丙的规则统一落到"没有 ⇒ 取 0"分支——**该树内每个对象的重建 key 首段全部取 0**。因为 `(inode, offset)` 早已保证跨对象唯一，全体取同一个常数 0 不产生任何 key 碰撞，只是把这棵树的局部性打到最差（等价于回到纯 inode 编 key，前提四已经量过这一档的代价：1.46× 遍历倍率，且随改名衰减到约 1.0）。这不是"丢了一个正确性后果"，是丢了它本来就承诺会丢的东西（局部性）。
3. **两者都丢**：同 2，取 0，无碰撞。
4. **多可写头 / 克隆共享同一个对象的单元**：见下段单独分析——这一格三条臂表现相同，不构成丙独有的失败。

**多头 / 克隆场景：三条臂对"哪一棵树该认领这个单元"这一问都交白卷，locality_id 的取舍不改变这一格的现状。**

`.claude/kb/decisions/08-核心索引结构.md:424`（D8（核心索引结构） 已定项 6 "重建"一节）逐字：**"射程是单头镜像……多头镜像的归属划分要克隆祖先表（E90（树 ID 进 AAD 与跨头共享） 第二笔），落地前多头镜像的 inode 树重建没有输入。"** 这句话与 `locality_id` 无关——它说的是数据单元头五元组里的"树 ID"字段本身在多头共享后就分不清"合法继承"与该归哪个头，这个问题在甲/乙/丙下都原样存在，因为甲/乙加的是"第六个字段"，不改动"树 ID"这第二个字段的语义或来源。也就是说：**这一格三条臂平局，谁都没解决它**，把它算进丙独有的失败不成立。

进一步：即使某一天有了克隆祖先表能正确判定单元归哪个头，`(locality_id, inode, offset)` 的唯一性范围也是"一条已发布历史内"（`.claude/kb/decisions/08-核心索引结构.md:616` 一带），即按树分别唯一，不跨树比较；两个头各自的 `(inode, offset)` 唯一性互不干扰，`locality_id` 仍然只影响各自树内的排布，不影响跨头判定。

⇒ **对问题 2 的直接回答**：丙在"extent 树也要重建"下能给出唯一 key 首段（取常数 0，唯一性由 inode 单调不复用担保，不依赖 locality_id 本身正确）；在"多可写头 / 克隆共享同一个对象的单元"下，丙不比甲、乙更差——三条臂都没有解决"这个单元该记进哪棵树"这个更上游的问题，它是一个独立、已经在 kb 里登记过的缺口（`.claude/kb/decisions/08-核心索引结构.md:424`），不因加不加 `locality_id` 而改变。

**丙的规则有一处欠说明，但不影响上面的结论**：候选丙原文（背景材料"三、候选"）只写了"有幸存 extent key 就取首段，没有就取 0"，没有显式说"如果 inode 记录本身没丢、只是 extent 树丢了，应当优先用 inode 记录里已经存的 `locality_id` 去重建 extent key，而不是等 extent key 幸存"。这是候选表述的疏漏，不是丙这条路线本身的缺陷——补一句"重建源优先级：inode 记录的 locality_id（若存活）> 该对象幸存 extent key 的首段（若一致）> 0"即可，唯一性结论不变（仍然只由 inode/offset 担保）。

**甲、乙在 U1 下**：甲、乙给数据单元头本身加一份 `locality_id` 的物理副本，好处是重建时多一个独立见证源（第三份，不依赖 extent 树或 inode 记录任何一方存活）；坏处是它不解决"多头/克隆归属"这一格（同上），也不改变"inode/offset 已经担保唯一性"这一机制事实——它买到的仍然是局部性的恢复速度（免得退化到全 0），不是新增的正确性。**U1 对三条臂不构成决定性判别**：甲、乙让"重建后局部性能恢复到接近原值"，丙让"重建后局部性退化到全局最差但正确性不受影响"，两者是同一个权衡的两端，不是对错之分。

## 二、问题 1：前提三与前提五是否互相顶着；D9 已定项 6 那条排除今天还成不成立

**结论：不顶着，且排除理由今天仍然成立。**

先把两句摆齐：

- 前提三（`.claude/kb/decisions/08-核心索引结构.md:207-208`）："「它是提示、可以是错的」准许的是**不信它的含义**，不是**不存它的位**：作为地址首段它的**取值精确且定义性**。"
- 前提五（`.claude/kb/decisions/09-加密.md:553`）：`locality_id` 一定不能进 AAD，理由是"让声明为「可以是错的」的字段承重"。

关键在于"取值精确且定义性"这半句在说什么。它紧跟在"命名树的 value 只有 inode，数据单元头的五元组里也没有它，所以盘上只有 key 自己带着它"（`08-核心索引结构.md:204`）之后——上下文是在论证"`locality_id` 必须**有一个确定的存放位置**（inode 记录里必须存一份），否则改名后数据连提示都找不到"，不是在论证"这个位置里存的**值必须正确**"。同一句话紧接着自己就划了界："准许的是不信它的含义"——**含义（语义正确性）仍然可以是错的**，"不是不存它的位"——**只是不允许它连一个确定的存储槽都没有**。"精确"修饰的是它作为 B 树 key 首段这个**结构角色**（一个定长 8 字节整数，参与严格的字典序比较，不能是"有时缺失""有时不定长"），不是修饰它的**内容可信度**。

前提五要挡的是另一件事：D9（加密） 已定项 6 的"期望值来源判据"（`.claude/kb/decisions/09-加密.md:568-569`）要求 AAD 每个字段的期望值只能来自"①读者的查找路径，或②已被上一级 MAC 认证的密文侧字段"，因为 AAD 失配 = MAC 校验失败，而这个失败被系统解读为"篡改或损坏"。`locality_id` 按定义会因为改名而**合法地**变得陈旧（"改名时故意不更新"，`08-核心索引结构.md:132`），如果它进 AAD，每一次改名之后，这个文件的所有数据单元在下次校验时都会**必然** MAC 失配——不是攻击，是设计内允许的正常状态，却会被系统当成"身份错配"处理（`.claude/kb/decisions/09-加密.md` I-6.9 那条新增不变量）。这与前提三讲的是两个不同的轴：**"存在性/结构确定性"（前提三）vs "内容可信度能不能被当作认证输入"（前提五）**。一个字段完全可以同时满足"永远有一个确定的 8 字节值、可比较、可排序"，又"这个值的含义可以是陈旧的、不可信的"——`locality_id` 正是这个交集。

⇒ 两句话不是矛盾，是同一条已定项里两个不同维度的判定，而且已定项 3 的作者显然预见到了会被误读成矛盾，才把"准许的是……不是……"这句消歧写进了同一段落。**D9（加密） 已定项 6 排除 `locality_id` 进 AAD 的理由（"让声明为可以是错的字段承重"）今天原样成立**：`locality_id` "可以是错的"这条性质本身没有被前提三推翻或收窄——前提三收窄的只是"可以不存位"这个从未被断言过的极端读法。

**对甲的直接后果**：甲的定义就是"把 `locality_id` 塞进五元组 = 塞进 AAD"（候选甲原文），而这正是前提五排除的对象、且排除理由未被削弱 ⇒ 按背景材料五节的反向接受条款——"甲在 U2 被前提五打中、且前提五的理由今天仍然成立 ⇒ 甲出局"——**甲出局**。

## 四、问题 4：I-9.9 在各臂下的判别力与自证

**I-9.9 逐字**（`.claude/kb/invariants.md:265`）："记录的 `locality_id` == 该对象每条 extent key 的首段；extent 树未经重建时输出红 / 绿，超级块 `map_provenance` 标 rebuilt 时两侧同源，输出「不可判定」，不许输出「通过」"。

**关键发现：I-9.9 按其字面定义，在甲、乙、丙三条臂下判别力完全相同（等价，不是三档）。**

理由：I-9.9 比较的两侧——"inode 记录的 `locality_id`"（inode 记录偏移 16，`.claude/kb/layout/01-first-txn.md:253`）与"该对象每条 extent key 的首段"（`.claude/kb/layout/01-first-txn.md:272`）——**在甲、乙、丙下都同样存在，字段位置和宽度都不因这条提议而改变**。这条提议改动的是**数据单元（码 1）头里的第三份副本**，而 I-9.9 的定义里根本没有提到"数据单元头"这个第三方。所以：

- **对已经写下来的 I-9.9，三条臂给出的判定结果集完全一样**：extent 树未重建时红/绿由 inode 记录与 extent key 是否一致决定，重建后（`map_provenance=rebuilt`）恒输出"不可判定"——这一整套行为不读、也不需要读数据单元头，甲乙加的那 8 字节对 I-9.9 而言是死信息。
- 这本身是一个值得记下的空白：**这条提议真正想解决的问题（"inode 记录和 extent 树都丢了，只剩裸数据单元扫描"）恰好是 I-9.9 覆盖不到的场景**——那种场景下两侧输入都没了，I-9.9 无从比较，只能靠 `map_provenance=rebuilt` 直接判"不可判定"，不会去看数据单元头里有没有 `locality_id` 的第三份拷贝。要让甲/乙买到的东西真正被检查覆盖，需要的是**一条新的、I-9.9 之外的不变量**（比较"数据单元头自带的 `locality_id`"与"inode 记录 / extent key 首段"三方是否一致），而不是修改 I-9.9 本身。

**自证情况**：

- I-9.9 本身（三条臂通用）：自证做法是造一个 inode 记录 `locality_id` 与其对象某条 extent key 首段不一致的坏镜像，`map_provenance` 保持非 rebuilt，断言 I-9.9 判红；再造一个同样不一致但 `map_provenance=rebuilt` 的镜像，断言输出"不可判定"而不是"通过"。**这个自证三条臂都写得出来，因为两侧字段三条臂下都存在**——不存在"写不出判别力自证的臂"，U4 反向接受条款在 I-9.9 这条不变量上不触发于任何一臂。
- **但如果要做"数据单元头 `locality_id` 副本 vs inode 记录/extent key"的新不变量**：甲、乙都写得出自证（改坏数据单元头里那 8 字节，断言新检查判红）；**丙写不出——因为丙压根没有这个字段可改坏**。这不是丙"判别力更差"，是这条新检查的定义域本身就排除了丙（U4 的"写不出判别力自证"条款字面适用于丙，但适用原因是"该检查对丙无意义"，不是"丙比别人弱"）。这一点如实记一笔：**若将来要新增这条检查，它只能在甲/乙下存在；选丙就意味着放弃这条额外的检查手段，换来零字节与零契约变更**。

## 五、结论

**按 U1–U4 逐条走完，正推腿支持维持丙（不加字段；重建时按见证者规则重新编 key 首段），与主 agent 事先的倾向一致，但推导路径是独立的：**

- U1：丙在全部四种重建场景下都不构成正确性失败（唯一性由 inode 号单调不复用担保，与 `locality_id` 取值无关）；"多头/克隆归属"这一格三条臂平局，非丙独有的短板。
- U2：甲把 `locality_id` 塞进 AAD，撞前提五，而前提五的排除理由（问题 1 的核实结果）今天依然成立 ⇒ **甲出局**（按背景材料五节反向接受条款）。
- U3：乙虽不进 AAD，但同样在盘上留下明文副本，新增"对象语义类别"这一类此前没有先例的加密泄漏 ⇒ **乙被 U3 打中**，按反向接受条款应交用户在"乙 + 加密开启时这 8 字节进密文"与丙之间选，不能直接判乙赢；且乙（与甲）要多付永久的 8 字节/单元代价与冻结分层第 3 层的改动面，丙 0 字节。
- U4：I-9.9 本身对三条臂等价，不构成判别依据；能体现甲/乙优势的是一条**尚不存在**的新不变量，且这条新不变量在丙下无从定义（不是丙的缺陷，是丙不引入这个字段的直接推论）。

⇒ 甲出局是本轮唯一一个"打中且理由仍然成立"的判定；乙落进"交用户选"的反向接受条款；丙没有被任何一条判据打中一个正确性后果。三条判据合起来指向：**维持丙**，若日后要用甲/乙买回来的额外检查手段（新不变量）或更快的局部性恢复，代价与好处需要单独摆出来交用户判断——但那已经超出这一轮 U1–U4 能裁决的范围。
