# 卡一侧的验证做成统一的常驻服务（第一轮）

方案按 `crates/` 今天的实现来谈。标「量的」的数出处在 `records/2026-11-17-崩溃判器与测试流的效率优化.md`，标「读码」的是主 agent 或调查员读源码得到的，标「推的」的没量过。

## 问题

崩溃放量与崩溃枚举用例的后半段（卡上的判）今天是「一件活持一张卡、自己一批一批发」。用户定了方向：前半段（CPU 上的录入与生成）不动；后半段改成一个统一的、不带哪一件活的状态的验证服务，批由它脉冲式地发，批大小照数据量调、不撞显存。

要推的是这个服务怎么落到今天的代码与规则上，不是要不要做。判法不变：每个状态照旧由今天这一套判器完整判，这一轮不讨论「内核与 checker 拆开、卡只比对」（那是另一轮）。

## 已定的前提（用户原话，不在这一轮里重议）

1. 「前半段还是cpu。后半段改为了gpu独立为一个统一的服务。因为后半段的gpu 是没有状态的。gpu唯一的关注的就是 一个batch根据不同的验证的数据量需要调整batchsize 不要 oom就好了。」
2. 「cpu和gpu要隔离。cpu数据装入rocksdb gpu server从rocksdb中读出来。」经网络的往返不当瓶颈看：「我们是 有线直连 速度很快 问题不大。」
3. 「这和 gc 差不多是一个道理 一个水位线，然后发一波任务。」「比如有五张卡 五张卡 每张卡能读多少batchsize。当cpu算到一定的数量 就分批次发给各个gpu 这样， 脉冲进行」
4. 对现行规则的四处，用户的答复：
   - 编译目录与二进制不跨趟共用：「这是之前的任务和gpu绑定时候的模式，如果拆分开那么gpu就是自己独立的逻辑」；
   - 判定库里只放剪枝按单元键复用时要读的键：「这里看来是要改一下 把值也写入了是吧」；
   - 一切跑项目代码的命令经统一任务服务起：「gpu独立判断不是一个task 他是一个独立的服务。和task不是一个东西」；
   - 卡由统一任务服务分、一回给一次尝试：「我们现在决定给卡设置一个公共……脉冲式……任务分配服务。这里就要改了」。
5. 没定的一处：「强制现判 需要考虑下其他的实现方式的可能性」。

## 实现今天的样子

主 agent 的观测与调查员的读码（`~/.local/share/singlefs/work/batch39-card-pulls-work/result.md`、`~/.local/share/singlefs/work/batch39-interleaved-dispatch-on-one-card/result.md`；行号是段树 `~/.local/share/singlefs/work/batch30-pieces-with-widening-rule/copy` 的，文件都在 `crates/singlefs-verification/src/`）：

**数据怎么进卡**

- 每条流一张打包的判表，录入段写进判定库、判段从库里读回再上传一次（`crash_judge_dispatch.rs:1014`）。慢流 unlink-merging-inode-leaf-containers 是 12091358 个字（量的）；读回 23–47 MiB 的判表用 0.074–0.647 秒（量的）。
- 每一批只上传四个字：第一个状态的序号、状态数、每态草稿区大小（`crash_judge_gpu.rs:1002` 的 `dispatch_words`）。状态在卡上照序号与判表现算，CPU 不逐态产出数据。
- 一批对同一组状态依次跑十几趟内核，每趟一次提交、阻塞等完，最后读回结论字（`judge_one_dispatch`，`crash_judge_dispatch.rs:1232` 起）。
- 每态草稿区是常量 `SCRATCH_WORDS = 2_009_599` 个字（`crash_judge_gpu.rs:988`），不随流变；每个进程在每张卡上另占 2560 MiB（`crash_judge_dispatch.rs:36`，调查员读的）。32G 卡一批 3843 态，16G 卡 1600 到 1730 态（量的）。
- 那把防交错的锁是每个判器一把（`crash_judge_dispatch.rs:568`、`:1080`、`:1246`）；卡池在一个进程里每张卡只起一个设备，多笔借据共用设备与编好的内核，一张卡借几笔只看显存账（`gpu_unit_checks.rs:2431`、`:2680`、`:2865`）。

**谁知道该判哪些块**

- 库里没有待判的块的清单。判段靠编进测试二进制的流程代码自己排：重算录入键（`crash_amplification.rs:20499`）、读回清单与判表（`:20561`）、排计划（`:20576`）、按份与块区间取交集（`:20674`）、`pending_blocks` 逐块问库一次（`:3728`）。结论版本取自本二进制里编进去的键（`:20585`）。
- 判段因此离不开：那份二进制、测试函数名、十几个进程级环境变量（`:20085`）、那棵树、运行目录。
- 块没有人认领：两个判段取到同一块各判一遍；写库时结论相同不写、有一份红整份换、两份都绿而不同报错（`verdict_store.rs:1861–1871`）。今天不重复靠事先按份或块区间切开。
- 判定库服务已有带租期的认领（`prune-server` 的 `protocol.rs:1129`、`committer.rs:469`、`:670`），今天只用在登记判定向量编号上（`verdict_store.rs:5437` 起）。

**一条流之内已有的分发**

- 块队列 `BlocksForTheCards`（`gpu_memory_ledger.rs:2556`），每张卡一条线程从队头取（`crash_amplification.rs:4032`），进程级卡池 `GpuCardPool`（`gpu_unit_checks.rs:2437`），同一设备上按源码摘要只编一次管线（`crash_judge_dispatch.rs:1034`）。
- 跨流的没有：每条流各建判器、各传判表（`crash_judge_dispatch.rs:1010`）、各自从窄往宽校准批的宽度（`:1649`），进程一退全丢。
- 普通流共用同一组 11 条管线；给定状态表那一路把一栏旋钮值编进扫描内核，另编 9 条（`crash_judge_gpu.rs:1154`、`:1163`）。

**判器组的键**

- 调度与批的宽度不进键（`judging_units_entries.rs` 第 29 行的说明）；块键只由内容定，在哪张卡判只进块属性。改到 `on_card_compiling_these_kernel_sources` 或 `judge_one_dispatch`（入口）才换 GPU 判器那一组的键。
- 内核一变：那一条内核在每台每种卡上冷编一次（量的：只有走读内核变 157.8 秒、缓存全空 182.6 秒、命中 1.9 秒；驱动的盘上缓存在每台的家目录下、按卡分区），这一组的键换掉、这把键下判过的块重判。

**今天每片活付的、常驻之后可能不付的（量的，22 片）**

- 起跑到拿到卡 44270 秒（62.4%），卡在判 25067 秒（35.4%），持卡而没在判 1346 秒（1.9%）。
- 每片把整个包编一遍：平均 162 秒、峰值约 9 GiB；撞内存上限合计丢 9914 秒，都撞在编译里。
- 判段里 6.4% 是卡空着等一条 CPU 线程准备与解码。
- 判定库读写：卡真在判的几趟占 0.2%（慢流）到 3.5%–8.9%（快流）；整片复用、现判 0 块的判段占 53.0%–95.1%，最重的是判段开头几次各扫一遍整条流（排哨兵 107.6 秒、另三处各约 79 秒）。

**没量的**

- 几个判器的批在一张卡上重叠时合计吞吐多还是少。调查员读图形库推的：一个设备只取一条提交队列（wgpu-hal `vulkan/adapter.rs:2881`），不同判器的提交多半一个接一个算；几条流分显存后各自变窄，合计可能掉到独占的 0.5–0.7 倍。探针已写、还没跑。
- 起设备、传判表、清场各花多少。

`crates/` 里没有的：常驻的判定进程、库里的待判清单、块的认领、判的一方与记结论的一方不是同一份二进制时的对账。`grep -rn 'pending_blocks' crates/singlefs-verification/src/` 只命中判段自己问库的那一处与它的调用。

## 判据格

每格答「成立 / 不成立 / 推不出」，并给依据（`crates/` 或 `prune-server/`、`task-server/` 的文件:行，或上面引的读数）。写改法的，写成对实现的改动：改哪个文件的哪一步、加什么。

1. **待判清单的形态**：CPU 一侧写进库、服务读出来判的那一行（或几行）是什么——流的键、判表的键、块号、结论版本要的键各从哪来；它与今天判段自己排的计划（`crash_amplification.rs:20576`、`:20674`）是不是同一个集合；这一行算不算 `.claude/rules/verification.md`「判定库只有一份」里说的另一类东西，要改那一条的哪一句。
2. **认领与不重判**：用判定库服务已有的带租期的认领够不够——两台五张卡同时取、服务中途死、租期到了别人接手，各走一遍，判定落库照旧满足 `.claude/rules/test-script-discipline.md`「判定可复用：按输入存，按前缀剪」里「一块判完才落盘，写入是原子的；被打断后重跑同一条命令就是续跑，只补没判的」。
3. **版本对账**：服务是单独编的一份二进制，它编进去的判器组键与 CPU 一侧期待的键怎么对；对不上时谁拒、清单里的行怎么处置；内核改了之后旧服务还在跑的那段时间会不会把旧判法的结论记在新键下。
4. **批大小与显存**：一张卡上同时放几条流的判表与草稿区时批大小怎么定才不撞显存——给出式子（卡的显存、每个进程固定占的、各流判表、每态草稿区），并答给定状态表那一路另编的 9 条管线怎么算；今天的「撞显存报本次未跑」那条路（`crash_judge_gpu_agrees…` 用例里的写法）在服务里对应什么。
5. **脉冲与水位线**：一波由什么触发、一波里几条流怎么排先后与分卡；在「CPU 不逐态产出数据、一条流录完全部块就都知道了」这个事实下，水位线量的是什么量。重叠着发值不值得，等探针的数，这一格只答「数出来是哪一种时各该怎么排」。
6. **强制现判与哨兵**：今天按本进程的库认强制现判（`crash_amplification.rs:3689`），判的一方换成服务之后怎么证「这一条确实被现判了、而且与库里那一条相同」；给不少于两种做法，各写它拦得住什么、拦不住什么。
7. **与统一任务服务的分工**：服务常驻之后这几件各归谁、今天在哪做——卡的清场（两台的卡平时还跑别的服务）、卡坏的发现、服务自己占的 CPU 线程与内存算谁的（任务服务的 CPU 闸让 32 核的台负载到 110，`task-server/task_server.py:994`；量到过负载一百上下时一条单线程的活三分之二的时间在排队）、服务怎么起与怎么停。
8. **多机**：两台的卡都取得到活、判出来的结果两台都读得到（`.claude/rules/verification.md`「所有任务都要多机可用」）；服务每台一个还是一共一个，各自的后果。
9. **要改的规则条文**：把前提第 4 条那四处与上面各格牵到的规则逐条列出原文与要改成什么；只列，不在这一轮里改。
10. **不换判据**：这一套改完，同一条流同一块态的判定字与今天逐态相同、判器组的键哪几组会换——逐处答，并给出主 agent 能用一块态核的办法。
