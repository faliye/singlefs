# D8 未定项 7 反例腿输出（R1，Sonnet）——三条候选各构造一条会出错的时序

**立场**：找反例，不论利弊。三条候选：甲（seq 进 key）/ 乙（seq 进 value）/ 丙（seq 不落盘）。
材料：`research/prompts/d8-item7-seq-material.md`（56 行，本轮逐字核过）。

## 反例一：针对甲（seq 进 key）——「丢一代」不再是点删，`D5（快照 / 空间记账机制） 已定项 2` 的字面被推翻

### (a) 针对候选
甲：记账 key 变成 `(标签, 树, 设备, 代, seq)`。

### (b) 事件序列
1. mkfs、挂载。checkpoint 窗口 代 = T = 100 开始。
2. 同一窗口内对同一记账四元组 `(标签=1 已分配字节, 树=7, 设备=2, 代=100)` 发生两次写：
   操作 A（分配一个块）生成 write buffer 条目，seq=42，value=V1；
   操作 B（窗口内又分配一个块，幂等完整值意味着这是「此刻的完整值」）生成条目，seq=57，value=V2。
   在甲的方案下这两条的**完整 key** 分别是 `(1,7,2,100,42)` 与 `(1,7,2,100,57)`——**不相等**。
3. write buffer 排空（D8（核心索引结构） 硬要求 3 逐字「flush 时按 key 排序丢弃时间序」，
   `.claude/kb/decisions/08-核心索引结构.md:43`）。按甲的 key 形态，这两条**不会**在 btree 层被
   同 key 覆盖折叠（材料自己的判定，`d8-item7-seq-material.md:40`：「同一 `(标签,树,设备,代)`
   前缀下有多行 ⇒ 同 key 条目不再在 btree 层合并」）——两条各自作为独立 key 落盘。
4. checkpoint T 发布（根写出，txg=100）。

### (c) 观察点
不需要崩溃即可观察：稳态运行到 checkpoint T+K+1，触发 D5（快照 / 空间记账机制） 已定项 2 的
「只保留最近 K 代」增量丢弃规则，对代 T 执行丢弃。

### (d) 观察到什么、违反哪条已定条款
`D5（快照 / 空间记账机制） 已定项 2`（`.claude/kb/decisions/05-快照-空间记账机制.md:257-259`）逐字：

> 「丢弃满足 `.claude/rules/fs-design.md` 第一格：要丢的那一代**算得出来**（当前代 − K），
> **不用找** ⇒ 是点删不是扫描；触及的 key 数 = **统计量数**，
> **与 checkpoint 数无关、与盘容量无关**。」

这句话的前提是「一个统计量在一代只有一行」。而步骤 2–3 构造出**同一个统计量、同一代、两行**
（`(1,7,2,100,42)` 与 `(1,7,2,100,57)`）。丢弃代 T 时：

- 若丢弃逻辑仍按「一个统计量一次点删」执行（例如只删 `(1,7,2,100,0)` 这种假设单行存在的动作），
  它找不到真正的两行，**留下孤儿行**——违反「触及的 key 数 = 统计量数」；
- 若要正确删净，就必须对 `(1,7,2,100,*)` 做**范围扫描**，找出这一代下所有 seq 变体再逐条删——
  这直接违反同一句话里的「**不用找**」与「是点删不是扫描」。

**两条路都与已定条款字面冲突。** 且这不是一次性的：只要同一记账 key 在同一 checkpoint 内
被写超过一次（幂等完整值形态下这是常态——一次窗口内多次分配/释放同一统计量），
每一代都会重复出现多行，丢弃逻辑每次都要面对「删几行、删之前知不知道有几行」这个
`d8-item7-seq-material.md:40` 自己点名、材料要求去想的问题。

### (e) 致命还是可补细则
**不是当场致命，但代价比表面看重**：要救回 D5（快照 / 空间记账机制） 已定项 2 的字面，
甲必须在 flush（或插入）时新增一条**跨 seq 前缀比较的强制去重**——比较时要忽略 key 的 seq 段、
只保留 max-seq 的一行再落盘。这条去重恰恰是乙（seq 进 value）靠 btree 原生同 key覆盖**免费**拿到的
效果（前提是覆盖顺序与 seq 顺序一致，见反例二）；甲需要**在此基础上再多做一步**
（按前缀而非全 key 比较）。也就是说：**甲的修复成本是乙的超集**，且甲的修复还会
反过来触碰一条已经写成「已定」的条款（D5（快照 / 空间记账机制） 已定项 2），需要在正文里
明确改写「点删」的前提条件——这是一次要走 kb 变更记录的推翻，不是免费的补丁。

## 反例二：针对乙（seq 进 value）——「后者胜」只是被写下来的意图，没有任何东西在插入时真的比较 seq

### (b) 事件序列
1. mkfs、挂载。checkpoint 窗口 代 = T = 200。
2. 对同一记账 key K = `(标签=1, 树=7, 设备=3, 代=200)` 先后发生两次写：
   W1（较早，seq=500，value=V1=1,000,000）与 W2（较晚，seq=510，value=V2=1,004,096，
   反映又多分配了一个 4 KiB 块）。两条都进入内存 write buffer。
3. buffer 在 checkpoint T 结束前触发两次独立 flush（write buffer 是有界内存结构，
   填满就要排空，不等到 checkpoint 边界）：第一批只捕获到 W1（此时 W2 还没到达），
   排序去重后生成一次树插入操作 `K → V1`（value 里带 seq=500）；
   W2 落进第二批，独立生成插入操作 `K → V2`（value 里带 seq=510）。
4. 两次插入是两次独立的 flush 批次，**不共享同一次排序去重**——D8（核心索引结构） 硬要求 3 的
   「排序去重」只保证**同一批内**同 key 条目按 seq 决出胜者，没有任何条款要求**跨批次**的
   插入必须按 seq 顺序串行执行。E17（write buffer 合并上限） 已把「按叶分区可并行」列为
   实测收益（`.claude/kb/decisions/08-核心索引结构.md:54`：「按叶分区可并行 **6.26–6.38×**
   （16 线程）」），也就是说不同 flush 批次可能被并行调度到不同 worker。
   构造：批次 2（W2，seq=510）的插入先于批次 1（W1，seq=500）的插入**物理落地**
   （例如批次 1 因为所在叶的锁竞争被延迟）。
5. 树上最终这个 key 的值是**后落地的那次插入**——批次 1（W1，seq=500）晚到，物理覆盖了
   批次 2（W2，seq=510）已经写好的行。**没有任何一步比较过 value 里的 seq 字段**——
   btree 原生的同 key 覆盖是「谁的写操作在物理/程序序上更晚，谁赢」，不是
   「谁的 seq 更大，谁赢」。这正是材料自己提的问题（`d8-item7-seq-material.md:41`）：
   「同一个 key 的两条条目在 btree 层会互相覆盖（key 相同）——那 seq 还有没有用？」——
   这里给出的答案是：**没有任何代码路径读它**。
6. checkpoint T 发布，崩溃立即发生（让这个状态持久化，排除内存态被后续操作纠正的可能）。
7. 重新挂载。

### (c) 观察点
重挂后读 K 的现行值。

### (d) 观察到什么、违反哪条已定条款
树上 K 的现行值是 V1=1,000,000（seq=500），而**真实**已分配字节（W2 之后应为 1,004,096）
已经丢失、无法从这条记账行本身看出任何异常——value 里躺着一个合法的 seq=500，
看起来就是一条正常写入的记录，不携带「本应有一条 seq=510 的行曾经存在又被物理覆盖」的痕迹。

违反的是 D8（核心索引结构） 硬要求 3 本身要保证的性质，逐字：

> 「flush 时按 key 排序**丢弃时间序**，而去重规则是「后者胜」⇒ **「后者」必须由条目自己携带**；
> 用不稳定排序时同 key 条目的相对次序未定义，去重结果因此不确定。」
> （`.claude/kb/decisions/08-核心索引结构.md:43-44`）

条目**确实携带了** seq（乙满足字面），但「携带」不等于「被使用」。硬要求 3 只规定了
**条目必须自带序号**这个格式要求，没有规定**哪个代码路径必须在插入前比较它**——
而 D8（核心索引结构） 已定项 1 自己的措辞（`.claude/kb/decisions/08-核心索引结构.md:79`）：

> 「记账条目一律是「某个统计量在某一代的完整值」，**写入时整格覆盖**，合并规则「后者胜」」

「写入时整格覆盖」这五个字，字面读法就是**盲覆盖**（无条件覆盖），不是「比较后覆盖」——
这恰好印证了反例构造的物理机制：本仓已写下的措辞本身就没有排除「谁后写谁赢」（物理序）
与「谁 seq 大谁赢」（逻辑序）不一致的可能性。

同时命中 I-3.1（已分配统计对得上）（`.claude/kb/invariants.md:117`「已分配空间统计 ==
实际遍历所有引用得到的和」）——树上记的 1,000,000 与真实已分配（可由 extent 树独立走一遍
重算出 1,004,096）对不上。**这一条最终会被 I-3.1 的全量重扫抓到**，不是永久沉默的错误，
但在下一次重扫之前，这个错误值正被 ENOSPC 准入路径实时使用
（`.claude/rules/fs-design.md` 第一格：「运行时决策路径……不许遍历，且代价不许随盘容量增长」，
准入要的是「进门前先算最坏情况」）——用一个被静默腐蚀的账去做准入判断，这本身就是一个
实时正确性缺陷，不能靠「离线 checker 最终会发现」来开脱。

### (e) 致命还是可补细则
**可补，但缺口是真实的、无人堵过**：需要新增一条明确规则——同一 accounting key 的多个
flush 批次必须按 seq 顺序**串行**落地（或者插入操作本身做成 compare-and-set：
只有新 value 的 seq 大于树上现有 seq 才覆盖）。仓内目前**没有任何条款**要求过这件事：
`13-验证路线.md:221-227`（D13（验证路线） 已定项 2）确认**事务/日志提交层**先承诺串行
（第一版），但 E17（write buffer 合并上限）测的「按叶分区可并行」是 **flush 到树的插入层**，
不是提交层，两者不是同一层，材料与决策正文都没有把「同 key 跨批次插入必须保序」
钉成规则。修这个缺口的代价可控（多数 accounting key 在一个 checkpoint 窗口内不会被
两个并行 flush 批次同时命中，只有热点统计量才会撞上），且修法（比较后覆盖 / 同 key 强制
串行）不需要改动任何已经写成「已定」的决策条款字面。

## 反例三：针对丙（seq 不落盘）——它在自己预先写下的验收条款上就已经出局

### (b) 事件序列
1. mkfs、挂载。checkpoint 窗口 代 = T = 400 开始。
2. 应用分配一个 4096 字节的 extent：其**指针层**写入（D23（journal 的角色与格式） 定义
   「记录承载指针层目标态」，`.claude/kb/decisions/23-journal的角色与格式.md:1`）走事务提交，
   随日志持久化；与此同时它的**记账**增量（`(标签=1,树=5,设备=0,代=400)` 从旧值加 4096）
   只被写进内存 write buffer——按丙的定义（`d8-item7-seq-material.md:42`「seq 只在内存缓冲
   里存在（数组下标 / journal 到达序），落盘的条目不带它」），这条 write buffer 条目本身
   （不只是它的 seq）是否有任何持久形态，仓里**没有任何条款回答过**。
3. checkpoint T 发布：根写出，指针层（extent 的分配）已经可达、已经落盘；
   记账 write buffer 里那条尚未 flush 到记账树的条目还留在内存。
4. 崩溃发生在根发布之后、write buffer 排空之前。
5. 重新挂载：D23（journal 的角色与格式） 已定项 14（`.claude/kb/decisions/23-journal的角色与格式.md:674`）
   只重放 `(实例代号, checkpoint_txg)` 严格大于所选根水位的记录——**若 write buffer 条目
   从未被记进任何这类可重放的记录**，重放没有任何东西可以恢复这条记账增量。

### (c) 观察点
重挂后独立走一遍 extent 树，与记账树的现行值比对（即 I-3.1（已分配统计对得上） 的检查方式）。

### (d) 观察到什么、违反哪条已定条款
记账树上 `(1,5,0,400)` 仍是旧值（未反映那次分配），而 extent 树上那个块已经合法可达——
**账少记了 4096 字节**。这正是本仓自己已经登记、且从未回答过的那条欠账，
`checks-owed.md:91`（C80） 逐字：

> 「**发布出去的根若不含同批事务的记账 / 分配记录更新**（还留在内存 write buffer 里没进树），
> 崩溃回到该根后树是新的、账是旧的，I-3.1（已分配统计对得上）必红——而「发布点上 write buffer
> 强制排空到哪一层」全仓零覆盖。」

现查确认这不是夸大：`grep -n "write buffer\|排空\|flush" .claude/kb/decisions/16-发布语义.md`
在发布语义正文里**零命中**——「发布」这个动作的定义里完全没有提过 write buffer 排空这件事，
也没有任何条款要求「同批事务的记账更新必须与根同一批持久」。

这个观察直接命中材料自己**跑前写好的接受条款**（`d8-item7-seq-material.md:56`）：

> 「若丙的三问里有任何一问答不出「不需要落盘的序」，丙出局，回到甲乙之争。」

丙的第三问（`d8-item7-seq-material.md:51-52`）：

> 「**崩溃恢复**：未排空的缓冲条目在崩溃后从哪里恢复、按什么序重放？
> C80 逐字说「发布点上 write buffer 强制排空到哪一层」**全仓零覆盖** ⇒ 这一问今天没有答案。」

我现查确认这句话仍然成立——不是材料写错了，是这个缺口今天确实还开着。

同时被违反的是 D5（快照 / 空间记账机制） 开篇的核心性质（`.claude/kb/decisions/05-快照-空间记账机制.md:12`）：

> 「**核心性质：记账是增量维护出来的，不是事后遍历出来的。** 这是 D5（快照 / 空间记账机制）的全部价值。」

丙在这个反例下唯一能恢复正确账目的手段是**全量重扫**（I-3.1（已分配统计对得上） 的离线
checker 路径），这正是 D5（快照 / 空间记账机制） 存在的理由要排除的东西——把「崩溃后账错了」
的恢复责任压给 checker，而不是靠增量机制自愈。

### (e) 致命
**致命，且不需要我构造额外的巧合来打穿它**——丙自己预先写好的验收条款已经判自己出局：
第三问「答不出不需要落盘的序」在今天的 kb 状态下是事实，不是假设。要救丙，
必须先把 C80 整条欠账还清（定义「发布点上 write buffer 必须排空到哪一层」，
并证明「记账更新与根发布同批持久」这条不变量成立）——而这本身是一项独立的、
尚未开始的设计工作，不是「丙 vs 甲/乙」这道题内部能补的一条细则。

## 结论：三条里哪条的反例最轻

**乙（seq 进 value）的反例最轻。**

依据（三条横向比较）：

| | 反例的性质 | 触发条件 | 修复代价 |
|---|---|---|---|
| **甲** | 破坏一条**已经写成「已定」**的条款字面（D5（快照 / 空间记账机制） 已定项 2 的「点删不是扫描」） | 常态发生——同一记账统计量在同一 checkpoint 内被写超过一次即触发（幂等完整值形态下这是常态） | 需要**跨 seq 前缀去重**这个新机制，且该机制是乙所需修复的超集，还要动一条已定条款的正文表述 |
| **乙** | 暴露一个**从未被任何条款堵过**的操作层空当（跨 flush 批次的插入顺序未与 seq 绑定） | 需要同一 key 被两个不同 flush 批次命中且物理落地顺序与 seq 顺序相反——按 E17（write buffer 合并上限） 的并行策略是「按叶分区」，同一 key 落在同一叶、大概率由同一批处理，真正撞上的只是热点统计量的边界情形 | 修法是**局部的**：给 write buffer 树的插入加一条「同 key 按 seq 比较，只在更大时覆盖」（或同 key 跨批次强制串行），不需要动任何已定条款的字面，代价只在小概率路径上 |
| **丙** | 直接撞上材料**自己跑前写死**的验收条款，且该条款今天现查仍未满足（C80 全仓零覆盖被现场复核确认） | 不需要巧合——只要证明「记账没有随根同批发布」这件事在今天的设计里**可能发生**（且没有任何条款禁止它），丙就已经出局 | 不是「补一条细则」的量级，是要先把 C80 整条独立还清 |

甲和丙的反例都指向**已经写下、但没被兑现的承诺**（甲撞已定条款的字面，丙撞验收条款本身），
而乙的反例指向的是一处**至今没人写过任何承诺**的操作细节——它不推翻任何已经定案的东西，
只是在「已定」和「可执行」之间补一块从未被要求过的板。三条候选如果要继续在甲乙之间选，
**乙需要偿还的债最小**，但反例二给出的缺口（同 key 跨批次插入的顺序保证）必须在乙定案时
一并写进决策正文，不能留作隐含假设——否则它会在未来某次给 write buffer 插入加并行度时
被重新踩中。
