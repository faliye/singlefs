BACKGROUND

singlefs verifies crash safety by exhaustively enumerating filesystem states after a simulated crash ("layer 0"). Several long write streams exist; each stream is cut into consecutive "segments" (a run of writes evaluated together), and within a segment every subset of "persisted or not" for its writes is one crash state (two states per write normally, three states for a write that overwrites data already in place, since an in-place overwrite can also be torn). A pruning method under discussion, called "P6" here, classifies states by a "key" built from what a later checking pass actually reads, and only re-runs the expensive checks once per distinct key ("class") instead of once per state; P6 has been proven exact (every state sharing a key gets the same verdict as every other state sharing that key) on the cases tested so far. A second proposed method, called "P7" here, has not been built or measured; it proposes splitting one particular checking pass (a scan over "candidate" on-disk positions) into a per-position judgement step plus a separate aggregation step, so the class key would only branch on content that actually reaches the aggregation, instead of branching on the raw candidate-position content the way P6 does today. This material does not ask you to judge whether P6 or P7 are correct or whether either is a good design; it only gives you already-established facts about them and asks you to do arithmetic. A separate part of this material concerns a proposed key-value store for saving one verdict code per crash state, and a proposed GPU offload for part of the per-state checking work; again, this material does not ask you to judge whether that store's design or the GPU offload is a good idea, only to compute byte counts and batch sizes from the facts given.

FACT TABLE 0. The two pruning methods just described, and what has actually been measured about each one so far.

0.1. P6, tested on a small artificial 8-segment prefix built to have the same segment types in the same order as a real stream's own first 8 segments (rotate-the-system-configuration-slot, write-a-record, write-the-root-slot, rotate again, write-a-record, write-the-root-slot, rotate again, then one data-unit-write segment), but with that last data-unit-write segment shrunk to 12 writes (4095 states) instead of a real stream's 24 writes, so the test would finish quickly: P6 is exact on this whole 8-segment prefix (every state inside one class gets the same verdict), and the true number of distinct verdicts among the unit segment's 4095 states is exactly 1. But the number of distinct classes P6's key actually produces for those same 4095 states is also exactly 4095, that is, zero compression: every state is its own class. The reason given is that the later checking pass rereads a "candidate" on-disk position whose content varies with exactly which writes in that segment ended up persisted, so P6's key varies from state to state even though the verdict does not.
0.2. In that same 8-segment-prefix test, the combined number of distinct classes for the whole prefix (all 8 segments together, counting torn-write states too) was still exactly 4095, the same as 0.1's unit-segment-only figure. 0.3. The source material explicitly extends facts 0.1 and 0.2, by analogy rather than by direct measurement, to much larger data-unit-write segments (as large as 2^136 or 2^300 states), stating in so many words that this extension is inferred from the same mechanism, not measured at that scale. 0.4. P7 (the per-position-judgement-plus-aggregation proposal) has no code, no measurement, and no established class-count formula anywhere in this material. FACT TABLE 1. Byte widths of the identity values as implemented in the real code today, or as a directly available replacement candidate.

1.1. A crash state's own position number within a stream (used to look up its persisted-write subset) is stored and passed around as a 64-bit unsigned integer: 8 bytes.
1.2. Today's content-deduplication key for a data unit's bytes is a 128-bit digest: 16 bytes. A previously reported test found two different 16-kilobyte data-unit contents that hash to the same 128-bit digest after about 40 seconds of search, so this digest is known to admit collisions; the same source calls for using a collision-resistant hash instead, or comparing the full content byte-for-byte whenever two keys match.
1.3. A collision-resistant hash already used twice elsewhere in the very same verdict-storage code (once for "which input produced this data" and once for "which enumeration plan produced this data") is a 256-bit digest: 32 bytes.
1.4. In the one part of the real code that stores per-state verdicts today, each state's verdict is stored as a single 1-byte code number (a "judgement-vector code"), with a hard limit of 256 distinct code numbers (one byte can express at most 256 distinct values); if more than 256 distinct verdict patterns are ever registered, that code today refuses to add a 257th.
1.5. The verdict pattern that a given 1-byte code number actually stands for (fact 1.4's "judgement vector" itself, as opposed to its 1-byte code number) is stored today as a plain variable-length byte string; there is no fixed byte width defined anywhere in the code for how large one judgement vector's own content is.

FACT TABLE 2. The real byte layout of a proposed key-value store's four tables, exactly as implemented today (this store has no callers yet; nothing computed here has been measured end to end).

2.1. Table "verdict block": key = a 1-byte table tag, followed by a "block key". A block key is: a 32-byte input fingerprint, followed by a 2-byte length field, followed by a stream-or-node name of that many bytes, followed by a 32-byte enumeration-plan hash, followed by an 8-byte block-start position number. The 2-byte length field means the name itself can be any length from 1 up to 65535 bytes.
2.2. Table "verdict block"'s value: exactly one byte per state contained in that block (fact 1.4's code number), so a block covering N states has a value of exactly N bytes; how large N is (how many states one block covers) is decided by whoever calls this store, not fixed anywhere in the store's own code.
2.3. Table "violations": key = the same block key as fact 2.1, followed by one more 8-byte field (that state's position number within its block). Value: one byte (the same 1-byte code number as fact 2.2). Only states that actually violate something are ever given an entry in this table; a state that violates nothing gets no entry at all in this table.
2.4. Table "judgement vector by content": key = a 1-byte table tag followed by the judgement vector's own variable-length bytes (fact 1.5). Value: one byte (its assigned code number).
2.5. Table "judgement vector by number": key = a 1-byte table tag followed by one byte (the code number). Value: the judgement vector's own variable-length bytes (fact 1.5).
2.6. Three real example stream-or-node names that exist in the registration data today, with their exact lengths: "layer0-first-stream" is 19 bytes; "layer0-second-stream" is 20 bytes; "layer0-multi-record-publish-stream" is 34 bytes.
