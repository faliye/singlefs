Background facts common to all seven items. This is a single-writer, two-device pool. Every "publish" writes a new root record into a fixed-size ring of root slots; each root record points to an instance table unit and other structures. A journal ("record ring") also holds one record per publish, keyed by a monotonically increasing sequence number called jsn, scoped to an "instance" number that increases every time the filesystem is (re)mounted writable or an administrator rolls back. An administrator can pick an old root R_old still present in the root ring and "roll back" to it: this abandons every newer root and every journal record after R_old, and starts a brand new instance number. The instance table records, per instance number, a row (instance, T, W) which is used at recovery time to bound how much of that instance's journal records get replayed (row's W caps replay at that transaction number). A separate mechanism raises a "rollback floor" F: F is a value stored in each root record; released disk space can only be reclaimed for reuse once its release generation is at or below F, so raising F is what actually frees space for reuse after old roots stop needing it.

ITEM 1. Where the new instance's first journal record continues from after a rollback.

Mechanism: function mount_rollback in file mount.rs reads R_old's own journal record (found by exact match on R_old's instance number and checkpoint transaction group, called txg). The code sets next_counter = R_old's own record's counter field plus 1, then that becomes the jsn of the very first record the new instance writes. Call this choice P1. An alternative choice, call it P2, would instead set the new instance's first jsn to (the end of the continuous chain of readable records, found by following jsn continuity forward) plus 1 — i.e., continue after the abandoned timeline's last surviving record instead of after R_old's own record.

Why this matters: the journal ring is fixed size and jsn is a slot index modulo the ring size (roughly). Under P1, the very next jsn slot after R_old's own record gets overwritten by the new instance's first record. But that slot, on the abandoned timeline, used to hold a record belonging to one of the abandoned instances (say instance 2's or instance 3's next record after R_old). P1 silently destroys that abandoned record by overwriting its slot. A record consistency checker used by the test harness (function record_lost in file crash.rs) is designed to distinguish "a record slot legitimately overwritten by a later, valid record" from "a genuine gap in the record stream" so that this overwrite is not flagged as data loss.

The team's own documentation admits the choice is underspecified by the general rule: the general rule for instance switching (a different scenario, not rollback) says "the journal chain continues from the last record covered by the chosen root," and in the ordinary instance-switch case, the chosen root IS the newest root in the whole system, so "the last record it covers" trivially equals "its own record" (there is nothing after it). But in the rollback case, the chosen root R_old is deliberately NOT the newest state — there IS an abandoned continuation with more records after R_old. The rollback's own specification paragraph never states explicitly which of P1 or P2 the borrowed phrase "the last record it covers" should resolve to when chosen root is not the newest. The team picked P1 as an explicit implementation decision, flagging it as still open for user sign-off, with P2 marked as the alternative that a mutation test intentionally makes fail (turning the code into P2 must break a test).

One more fact: the team could not construct, at the level of the fixed layer-0 replay script, a test in which "the rollback row governs whether the abandoned record is applied": because P1 already overwrites the slot, whatever was there before is simply gone regardless of whether the rollback row exists. The scenario "a record belonging to an abandoned instance immediately after R_old, then check that a rollback row blocks it from being replayed, then remove the rollback row and check the record IS replayed" can only be exercised by calling the row-lookup function directly in a unit test (bypassing the full replay), not through an actual sequence of disk writes, because P1 makes that record physically unrecoverable before the row is ever consulted.

Question: is P1 an acceptable resolution of the underspecified borrowed rule? Consider especially: does overwriting the abandoned record's slot destroy forensic information the system elsewhere promises to keep (self-describing units, append-only intent), and does the fact that the rollback-row front-clause becomes practically unreachable at the full-replay level (only reachable at the unit-test / function level) mean that clause is effectively dead code for this specific scenario, or is that acceptable because the row still matters for a different scenario?

ITEM 2. Why the rollback row's W field is unconditionally set to zero.

Mechanism: when a rollback happens, the new instance's first publish writes two new rows into R_old's referenced instance table: a "rollback row" (r_old, T_old, 0, rollback-flag-set) for the abandoned instance r_old, and an "intermediate instance row" (i, 0, 0) for every instance number strictly between r_old and the new instance. The rollback row's third field, W, is hardcoded to 0 in the implementation. Separately, there is a general replay rule (front-clause five of the six-clause prefix rule): if the chosen root's own instance has a rollback row in the instance table that root itself references, then that instance's records are only replayed up through jsn corresponding to transaction number W; if W is 0, none of that instance's records are replayed at all.

Given item 1's finding (P1 already overwrites the very next jsn slot after R_old, so the abandoned instance's continuation records become physically unreadable through the normal replay path before front-clause five is ever consulted), is W=0 doing any real work in the currently reachable code paths, or is it inert given P1? Consider whether there is any future or edge scenario (multiple sequential rollbacks, a later normal recovery that happens to choose R_old itself, or a different reader path such as the checker or a second independent rollback that reuses the same instance table) where a nonzero W would have mattered but was foreclosed by hardcoding zero, and whether hardcoding W=0 (rather than, say, recording the actual highest transaction number that had been applied to r_old's timeline before the rollback) throws away information without any offsetting benefit.

ITEM 3. The narrow reading of the shadow ledger used by rollback.

Mechanism: after a rollback selects R_old, every root still readable in the ring whose (txg, instance) pair is greater than R_old's must have its data slots protected from being reused — the abandoned timeline's units must not be silently reallocated or overwritten before the abandoned roots eventually leave the ring through normal rotation. This protection ("shadow ledger") is implemented in-memory only, in function isolate_abandoned in file allocator.rs, called from mount_rollback in file mount.rs. The narrow reading: for every readable root newer than R_old, the code reads that root's own allocation records (via function allocation_records_under_root in file recovery.rs), computes the set of (device, slot) pairs it references, and isolates only those slots that are NOT already referenced by R_old itself. A slot referenced by both R_old and a newer abandoned root is left alone (not isolated) since R_old still legitimately needs it. A slot referenced by two different abandoned roots is only inserted into the isolation set once (a BTreeSet naturally deduplicates). The alternative, a "wide reading," would isolate every slot referenced by ANY readable root in the entire ring, including ones referenced by currently-valid, non-abandoned roots — the team rejected the wide reading because on a small first-version ring (24 root slots) it would isolate almost everything and leave raising the rollback floor unable to reclaim anything.

Question: is the narrow reading's exact boundary correct? Note one detail about the code: the set of slots excluded from isolation because they are R_old's own ("own_slots") is built from ALL of R_old's allocation records, without checking whether each record is currently marked allocated or already marked released. So specifically: (a) if R_old itself had already released some slot X before the rollback point (X is in R_old's own records, but marked released), and an abandoned root later re-allocated that same slot number X to different content, the current code will still treat X as "R_old's own" and skip isolating it, since it only checks slot-number membership in own_slots, not each record's allocated/released state — does this leave the abandoned root's reallocation of X unprotected, and if so, is that actually dangerous (could X be reused and overwritten while the abandoned root that reallocated it is still reachable, e.g. through a second rollback)? (b) is the isolation truly held until the abandoned root is evicted from the ring by normal rotation, or is there a code path (such as raise_rollback_floor, or a second rollback) that could cause an isolated slot to be released from isolation prematurely, since the isolation set itself is described as memory-only and not persisted across a crash and remount.

ITEM 4. How the raise-floor mechanism decides which persistent roots count as "non-empty" for the purpose of computing the ceiling on how high F can be raised.

Mechanism: raising F (the rollback floor) is capped by an upper bound ("ceiling") computed as the minimum of two quantities: (a) the most recent valid root on each device, taking the maximum-per-device then the minimum across devices, and (b) the fourth most recent "non-empty" valid root. The purpose of tracking "non-empty" roots specifically is a policy decision recorded elsewhere: the rollback depth guarantee only promises to preserve the four most recent states that actually changed something the user can see — publishes that are pure "warm-up" empty publishes (used right after establishing a new instance, to make its root durable on every device before any operation is acknowledged) or pure "raise-floor" empty publishes should not count toward that "four" quota, since otherwise the guarantee could be silently eroded by internal bookkeeping publishes that carry no user content forward.

The implementation's reading of "non-empty" (function rollback_floor_ceiling in file mount.rs) is: a root counts as non-empty if there exists a journal record for that exact (instance, txg) pair whose transaction number field is not zero. Warm-up publishes and raise-floor publishes are written with transaction number hardcoded to 0 in their publish plan, which is why this reading correctly excludes them. The rollback row publish (the very first publish after a rollback, which writes the rollback row and intermediate-instance rows into the instance table) is ALSO written with transaction number 0.

This reading is explicitly marked in the team's own notes as "a guess, not yet attacked": an earlier three-way review round tried three different candidate readings of "non-empty" and found they all gave the same answer (11) on the one test scenario tried, meaning the test scenario so far has no power to distinguish between the candidate readings.

Question: is "transaction number field is not zero" the correct predicate for "changed something the user can see"? Consider specifically: could there be a publish that DOES carry user-visible content (a real file write) but whose transaction number happens to be zero for some other structural reason, or conversely a publish that carries no real user content but has a nonzero transaction number, which would make this predicate diverge from its intended meaning. Also consider: is a scenario where the fourth-newest non-empty root ends up being an intermediate warm-up-adjacent root due to a subtle counting error, plausible given the code you have been shown?

ITEM 5. The two-step raise-floor sequence: reclaim first, then push carry publishes with the new floor value, and separately, on remount the new instance's own root writes whatever floor value is "in effect" rather than necessarily the highest floor value ever announced.

Mechanism: function raise_rollback_floor in file mount.rs does, in this exact order: first it calls the allocator's reclaim_released_up_to(new_floor) — this is a purely in-memory operation that moves any allocation records with release-generation at or below new_floor from "released" state to "free" state, immediately, before any disk write happens. Only after that does the function begin pushing a sequence of "carry" publishes (same instance table, no new file, transaction number 0, but each publish's root record now carries new_floor as its declared F value) — one publish per device-region step, until every device has at least one such publish landed, or until a fixed cap (three, the number of ring regions) is reached, whichever comes first. Only once every device carries a persistent root with the new F value does the team call the new floor "in effect" ("生效").

Separately, on ANY remount (not just after a raise-floor sequence), function effective_rollback_floor in file recovery.rs computes the floor value that the new instance will treat as authoritative: for each device, take the maximum F value among all readable, valid roots on that device; then take the minimum of those per-device maximums across devices. This recomputed value is then written into the NEW instance's own root record as ITS F value — meaning the new instance's F can end up lower than a value that was previously announced as the ceiling target, if (for example) the raise-floor sequence was interrupted after covering only one device, or if a device that never received the newer F comes back into the picture.

Question: consider the window between the in-memory reclaim call (which happens immediately, before ANY of the new-F publishes reach disk) and the point where the new floor becomes disk-effective on every device (which can take up to three publishes). During that window, is it possible for the process to crash after the in-memory reclaim but before enough publishes land, such that upon remount, effective_rollback_floor recomputes a LOWER floor than new_floor (because not enough devices carry it), yet some of the reclaimed slots have, in the interim, already been handed out to a real write (not just a carry publish) because the caller of raise_rollback_floor believed reclaim had already succeeded? Look specifically at whether raise_rollback_floor's caller could interleave a real data-carrying publish in between the reclaim call and the loop of carry publishes finishing. Also: consider the loop's exit condition — it stops as soon as either every device is covered OR the count of publishes reaches the fixed cap of three (the number of ring regions), whichever happens first; is there a device-count / region-assignment configuration where the cap could be reached WITHOUT every device being covered, causing the function to return success (an "Ok" result carrying the reclaimed placements) while the new floor is, in fact, not yet in effect on every device?

ITEM 6. Recognizing a specific transaction group number as the journal chain head when the chosen root's own journal record cannot be read.

Mechanism: at recovery time, the code normally continues replaying the journal chain starting right after the record matching the chosen root's own (instance, checkpoint-txg) pair, found by reading that exact record. If that record cannot be read (both on-disk copies are corrupted, a "torn anchor"), the code does NOT simply refuse to replay anything, and does NOT simply take "whichever readable record has the lowest jsn above the root's own instance," but instead requires the very next candidate record to have its checkpoint-txg field equal to exactly (root's own txg plus 1). Only a record satisfying that exact numeric condition is accepted as the chain head; anything else, replay stops with zero records applied.

This specific choice rests on an assumption that in this version of the system, exactly one journal record is written per publish, and each publish increments the on-disk transaction-group counter (txg) by exactly one. The team's own notes flag that if a future version allows one publish to write multiple journal records, this rule and a related rule (front-clause six of the six-clause replay rule) will both need to change together.

The alternative that was rejected in a previous review round: treating a torn anchor record as "unlocatable, so replay must stop entirely and apply nothing" was found to be too conservative, because it would fail an existing acceptance test in which the chosen root's own anchor record is torn (plus a root slot is corrupted) but a fully intact record landing right after it should still be recovered rather than discarded. The txg-plus-one rule was adopted specifically to keep that test passing while still refusing to guess wrong when there is a genuine gap.

Question: is "root's own txg plus one" the right predicate, versus, for instance, "the lowest checkpoint-txg strictly greater than the root's own txg, among records belonging to the same instance"? Consider a scenario where the record whose txg equals root-txg-plus-one is present and passes checksum validation, but is not actually the correct chain continuation for some other reason (for example, it belongs to a DIFFERENT sequence of publishes that happened to reuse the same txg value due to some other code path, if such reuse is even possible in this design). Also, does accepting the exact txg-plus-one record without cross-checking against the record's own jsn counter open any window where a record that is not truly part of the intended chain gets accepted as a valid chain head, given that this rule accepts it purely by txg value and does not verify anything about jsn continuity for this first record (jsn continuity resumes being checked only from the SECOND accepted record onward)?

ITEM 7. Releasing the mkfs-time ("genesis") tree-table unit exactly once, when the first real file version is published.

Mechanism: at filesystem creation ("mkfs"), a tree-table unit is written that has no file version content in it yet (it seeds the four structural trees: extent, inode, allocation, accounting, but there is no actual file). This genesis tree-table unit's placement is recorded once, in the allocator, by a call to mark_format_time_units in file allocator.rs, and retained as long as it has not yet been released, accessible via allocator.format_time_tree_table.

The function that publishes a new version normally releases the roles (tree-table, mapping tree, etc) that get rewritten by looking up their PREVIOUS placement through a mapping-based release path, given an in-memory "previous version" state object. But the very first ever file publish (the function named publish_first_file in file transaction.rs) has no such in-memory previous-version state to work from — it is called with previous set to none, since there is no earlier real "version" to speak of, only the genesis structures. For this specific case, the code takes a different path: function format_time_tree_table_to_release in file transaction.rs checks whether the tree-table role is among the roles being rewritten in this publish, and if so, whether the allocator still has a recorded genesis tree-table placement whose allocation record has not already been marked released; if both are true, it returns that one placement to be released (added to the deferred-release queue); otherwise it returns nothing. This makes the genesis tree-table unit get released for the first and only time, at the moment the first real file version replaces it, and the guard against re-releasing it is idempotent (checking the on-disk record's released flag, not merely whether the code path was already taken).

Question: is "previous is none" the correct and only trigger condition here, or could there be a future call path (a second bootstrap, a test harness path, or some other genesis-adjacent flow) that also passes previous as none but should NOT trigger release of the genesis tree table (for example, if it is publishing something else entirely, not a genuine first file version)? There is a second, code-confirmed fact worth weighing: the function that rebuilds the allocator from on-disk records after any normal mount or remount (rebuild_from_records in file allocator.rs) never sets the in-memory format_time_tree_table field — its own comment states plainly that after a remount this field is left empty, because release on that path goes entirely through the mapping and root-record release mechanism instead. Since the genesis tree-table release path only fires when format_time_tree_table is Some, this means the release can only ever happen within the single, uninterrupted process session that both ran mkfs and then called publish_first_file — if, for any reason (a crash, a future genesis flow that spans two separate mount sessions, a test harness that mounts once for mkfs and a second time to publish the first file), the first real file version ends up being published in a DIFFERENT process session than the one that ran mkfs, the genesis tree-table unit can never be released through this mechanism, since the rebuilt allocator that session starts from already has format_time_tree_table equal to none. Is it actually guaranteed, by construction, that mkfs and the first file publish always happen in the same uninterrupted session in every code path that exists or is planned? If not, does this leave a real, reachable way for the genesis tree-table unit to become permanently unreleasable, eventually surfacing only indirectly through I-3.1 (an accounting invariant that block usage statistics must add up)?

ITEM 8 (the extra question, not one of the seven defended choices, but still to be answered).

Background: an earlier review round examined a function called mount_writable (the normal, non-rollback writable-mount path) and found that it can only succeed on a pool where SOME file version has already been published at least once in the pool's entire history; if you try to writable-mount a pool that has only ever been through mkfs (or through mkfs plus a first writable mount that only did its mandatory warm-up empty publishes but crashed or was closed before ever publishing an actual file), mount_writable fails with an error called NoPublishedVersion. The reason: mount_writable reconstructs "the previous version" by calling a shared function, rebuild_version in file recovery.rs, which explicitly checks whether the chosen root's tree-table has zero entries, and if so, returns an error meaning "there is no file version under this root yet" (the exact wording is: the tree table is empty, so there is no file version yet). The previous review round's verdict on this finding was: no code change needed, this scope limitation is intentional and matches how the system is meant to be bootstrapped (a special, separate bootstrap code path, not mount_writable, does the very first ever file publish); the finding was simply recorded as an open decision point for user sign-off, with no code change.

Now that rollback and raise-floor have been added to the code (function mount_rollback in file mount.rs, and function raise_rollback_floor in file mount.rs, both in the same source file as mount_writable), it turns out mount_rollback calls the exact same shared function, rebuild_version, on the ROLLBACK TARGET root (not on the currently newest root). This means: if an administrator tries to roll back to a root that itself predates the very first ever file publish (for example, the mkfs root itself, or one of the mandatory warm-up empty-publish roots from the very first writable mount, before any file was ever published under it), mount_rollback will also fail with the same NoPublishedVersion error, via the exact same tree-table-emptiness check, because warm-up and raise-floor publishes all carry the tree-table pointer forward unchanged (a "carry" plan, not a "rewrite" plan), so a root that predates the first file publish always has an empty tree table, and any root descended from it before the first file publish also has an empty tree table.

Question: does the previous round's verdict (this is an intentional scope limit, no code change needed, just a recorded decision point) still hold now that mount_rollback shares this exact same check? Specifically: is it correct and desirable that an administrator attempting to roll back to a pre-first-file-publish root gets refused with NoPublishedVersion, the same error as trying to writable-mount a virgin pool? Or does sharing this check between the two very different operations (initial bootstrap mounting versus administrative rollback) hide a real difference between them that should produce a different error, or different behavior, in the rollback case? Consider in particular whether an administrator might have a legitimate reason to roll back to a root that predates the first file (for instance, to prove that the state genuinely never had that file, or to reset the pool to a pristine state), and whether refusing that with the same generic error as "you tried to write to a virgin pool through the wrong entry point" is confusing or actually harmless because both cases really do mean "there is nothing to build a writable session on top of."
