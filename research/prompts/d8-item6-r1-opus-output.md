## 零、先算一遍：提案自己改了记录宽度，而它引的数全建在旧宽度上

这一节不属于任何一条 P，但它污染 P1 / P5 / P7 三条，所以放最前面。

- E98 的记录是 140 字节，字段表里没有 btime、没有 flags：
  `research/e7-index-bench/src/bin/e98_inode_record.rs:133-152` 逐条列了 14 个字段
  （locality_id / inode / obj_birth / mode / uid / gid / nlink / size / blocks / rdev /
  atime 12 / mtime 12 / ctime 12 / change_count），合计 108 + 预留 32 = 140；
  `research/e7-index-bench/src/bin/e98_inode_record.rs:346` 逐字 `assert_eq!(record_bytes(), 140);`
- P5 加了 flags 8 与 btime（秒 8 + 纳秒 4），记录变 160。

我按 160 重算（`(16384 − 头) / 160`、`(32768 − 93) / 160`，与 E98 判据 1 同一条公式）：

| 量 | E98 / E103 的值（140） | 按 P5 的 160 重算 |
|---|---|---|
| 叶扇出（头 58，不带区间） | 116 | 102 |
| 叶扇出（头 58 + 区间 16，即 P3） | 116 | 101 |
| 叶扇出（头 76 + 区间 16） | 116 | 101 |
| 打包容器装几条（头 93） | 233 | 204 |
| 内部扇出（key 8 + 子指针 59） | 243 | 243（不变） |
| 树高 1e6 / 1e8 | 3 / 4 | 3 / 4（不变） |
| 1e6 各层节点数 | 8621 / 36 / 1 | 9901 / 41 / 1 |

判定：打中。

改成什么：

1. P1 的「永久损失 116 条/叶」与 P7 的「C100 形态定了（叶，116 条）」两处数都要改成
   101（带 P3 的区间）。这不是抠字：C100 欠的正是冗余条款，条数是它的输入。
2. E103 的全部比值（1.25 / 1.33 / 1.5 / 1.65 / 1.84 / 2.25–2.5）两侧都建在 140 上
   （`research/results/e103-inode-update-cost-2026-09-04.out:1` 逐字
   `inode_rec=140 ... packed_hdr=93`）。记录改 160 之后两侧的叶数与容器数都变，
   比值要重算。提案在 F5 里原样引用这些数，同时在 P5 里把宽度改掉，两件事不能同真。
3. E98 的爆炸半径两格（116 / 233）与 E103 判据 4 同理，要重跑。

补一条：E73 逐字「基础节点头 ≥ 58 字节（42 + 8 + 8，树 ID 与层级的宽度仍随实现定）」
（`.claude/kb/experiments/73-节点key区间的扇出代价.md:47`）——也就是说 58 这个下界里
根本没算树 ID 和层级。P3 在 58 上再加 16，加的是一个已经漏了两个字段的底。
我算过：把树 ID 8 + 层级 1 补上（头 83），叶扇出仍是 101，结论方向不变，
但「三档节点头同向所以结论不依赖节点头」这句话的射程要重写。

而那一格自陈「不是慢，是在被问到的那一刻没有答案」。

inode 记录是另一类：E98 判据 2 数出 11/14 个字段任何遍历都算不回来
（`.claude/kb/experiments/98-inode记录与inode树的几何.md:61-62`）。

判定：打中，而且我认为这是 P1 最关键的一处误引。
「住在树里的权威态」这个先例真正的内容是「可用性驱动的权威态，仍有全盘扫描兜底」；
路 ② 要立的是「不可恢复的权威态，无兜底」。两者共用一个名字，但兜底那一半没跟过来，
而兜底正是 P1 论证里「抢救而不是重建」那句话本该由先例提供的东西。

改成什么：P1 的类比要么撤回，要么改写成
「记账树是先例的一半（形态：COW + 挂父指针 + 节点带 key 区间），
另一半（丢了还能全盘扫描重算）inode 树没有，因此 C100 是一笔新账不是照旧」。

### 2.2 若 D11 已定项 4 的「重算源含记账」支持这个类比，本该看到记账丢了时它还成立

去查了。不成立，而且方向相反。

`11-…md:207-208` 逐字：「它不是『只从单元』——那个更窄的问法实测答案是不能
（E59，四类里两类塌）。成立的是从权威态重算，而记账本来就在 D21 已定的权威态里，
没跟着索引一起丢。」

即：记账在那条链里是输入，不是被恢复的对象。它证明的是
「记账在，所以别的东西算得回来」，不是「记账丢了怎么办」。
拿它支撑「inode 树是住在树里的权威态」等于反着用。

判定：打中，轻（提案没有明引这条，但 F6 的整段依赖它成立的那个语境）。

### 2.3 若 D18 已定项 5 的三级见证覆盖抢救，本该看到级 2 还有见证者

去查了。级 2 的见证者已经没了。

`18-…md:353-357` 逐字：「⚠️ 那个前置已收口，而且是往坏的方向收的（2026-09-03，用户定案）：
分配记录是派生态（D21 已定项 5），而 C73 逐字写着『派生态的东西自己就要被重建，
当不了见证』⇒ 级 2 的见证者没了。级 2 要么另找一个住在权威态里的双证，
或者这一格重开；级 1 与级 0 照常可用」

⇒ 今天扫描重建的天花板是级 1（`18-…md:316` 「只有校验和 / MAC 自洽，没有分配记录：只读挂载」）。
配上 1.7 的 C104（码 2 连校验和自洽都只到头为止），
inode 树抢救出来的叶其实连级 1 都够不着——级 1 的判据是「校验和自洽」，
而码 2 的载荷没有任何校验和。

判定：打中。改成什么：P1 要写明「抢救产物落在 D18 已定项 5 的哪一级」。
按现状是级 0，而级 0 逐字是「只报告，不进映射」。

### 2.4 记账树 1e6 与 inode 树 1e8 可不可比

## 三、P2 树表条目带种类，态别由种类静态决定

### 3.1 若这个字段解决它声称要解决的问题，本该看到抢救时读得到树表

去查了。读不到——这是我对 P2 最主要的反对。

P2 的动机逐字：「树表条目只有 tree_id + 指针，扫描器无从知道哪棵树该抢救、哪棵该重建」
（`_d8-item6-path.md:59`）。

而树表住在树表单元里，树表单元由根记录的一条指针指过去
（`.claude/kb/decisions/22-单元原子性怎么合成.md:373` 「根记录恒走间接层：
固定头 + 一条指向『树表单元』的指针」）。
抢救这个动作的定义域正是「从根下不去了」。两种情形：

| 情形 | 树表在不在 | P2 的字段有没有用 |
|---|---|---|
| 根与树表都在，只是某棵子树坏了 | 在 | 有用，但这时顺着父指针下去本来就知道是哪棵树 |
| 树表也丢了（真正要抢救的情形） | 不在 | 字段跟着一起没了，一个字都读不到 |

对照：树 ID 已经在每个索引节点的头里
（`18-…md:568` 码 2 行「类身份段：树 ID + 层级 + key 区间 + 诞生代号 + fsid」），
一个孤立节点单独捡起来就能报出自己的树 ID。
所以把「种类」编进树 ID 的取值规则（例如高位段），零新增字节，且在抢救场景里活得下来；
放进树表条目则恰好在需要它的时候不在。

判定：打中。改成什么：种类进树 ID 的编码规则，不进树表条目。
顺带这条也能答掉 P2 自己那句「每头一棵树时同一种类有多棵，种类不唯一」。

### 3.2 若落点是 D22 已定项 7，本该在那条分项里看到一张树表条目字段表

去查了。没有。D22 已定项 7 定的是根记录，不是树表条目。

`22-…md:385-395` 的字段表逐行是：magic 4 / fsid 16 / flags 4 / 实例代号 4 /
checkpoint_txg 8 / 树表单元指针 59 / 自证校验和 32 = 127。
七行里没有一行是树表条目。树表条目的形态只出现在 E79 的口径段：
`.claude/kb/experiments/79-根记录的容量.md:14` 「每棵树 61 字节
（tree_id 8 + 指针头部 31 + 位置条目 11 × 2 副本）」——而这是实验的输入假设，
且那个 11 已于 2026-09-03 改成 14（`22-…md:392`），E79 正文没跟着改。

`.claude/kb/first-txn-layout.md:112` 只有「树表单元指针 59」这一行，
没有任何一行是树表条目。

判定：打中。改成什么：P2 的落点写错了。树表条目的字段表全仓不存在，
要新开一条分项（在 D22 或 D15 已定项 2 之下），不是往已定项 7 加一行。
顺带：根记录里连「树数」字段都没有（E79 的平铺头有「树数 4」，
`79-…md:11`，间接层的最终表把它去掉了），所以树表条目数今天靠什么读出来也没写。

### 3.3 加 2 字节会不会改 59 / 127

去算了。不会，但会改另一个数。

59 是根记录里那一条指向树表单元的指针（`22-…md:392`），127 是根记录总长
（`22-…md:395`）。两者都与「树表里每条条目多宽」无关。
受影响的是树表单元的容量：`22-…md:397` 「装 267 棵/层，超过再嵌一层」——
而这个 267 本身已经作废：`22-…md:398-399` 逐字
「⚠️ 267 这个数按 55 字节的单元头算出，而单元头字段表现由 D18 已定项 7 定，
⇒ 待重算（2026-09-03）……现在算不出准数」。

判定：没打中（提案没有声称会改 59/127），但要补一句：
P2 改的是一个已经算不出准数的容量，加字段之前那个数要先重算（C89 欠着）。

### 3.4 若「态别由种类静态决定」站得住，本该看不到反例

去查了。反例在 1.9 已给（dirent）。再补一条:同一种类里态别不同的情形已经存在——
`18-…md:579-580` 逐字：「记账树节点与别的索引节点类身份段字段集合相同
⇒ 域分隔在这一对上买不到东西，『记账』是树 ID 给出的角色。
两者态别不同（记账是权威态，C102 记着），态别不是 I-6.2 与扩展点的判据」。

也就是说，仓里已经明写「态别不是判据」的那一格，P2 要把它变成判据。
这不必然错，但要正面处理这句话。

判定：打中，中等。改成什么：P2 要引用并处置 `18-…md:579-580` 这句。

## 四、P4 key =(inode) 与「最大号 + 1」分配

### 4.1 若「最大号 + 1」安全，本该看到复用的号不会与未回收的旧对象撞

去查了。会撞，而且撞在 extent 树的 key 上。

- `.claude/kb/decisions/08-核心索引结构.md:263` 逐字：
  「删除中的 inode 单独进 `deleted_inodes` 树，由后台回收——用户的 `rm` 返回，
  不等于所有 extent 都已释放。」
- `08-…md:125` 逐字：「key = `(locality_id, inode, offset)`」——三段里没有对象出生代。

⇒ 删掉当前最大号 N 的文件，它离开 inode 树进 `deleted_inodes`，
`最大号 + 1` 当场把 N 发给新文件；新文件与旧文件若在同一个 locality 下
（同一个父目录，最常见的情形），两者的 extent key 逐段相同。
`对象出生代` 判别得了单元身份（它在五元组里，`18-…md:592`），
判别不了 extent 树的 key ——那三段里没有它。

判定：打中。这一条我认为是 P4 最硬的一处。改成什么，三条路选一条：
① inode 号单调不回收（那 P4 的「最大号 + 1」要改成「持久的下一号水位」，
   而水位要有落点，不能靠最右键查询）；
② extent key 加一段出生代（那是 D15 第 3 层的改动，且 D8 已定项 3 要重开）；
③ 明写「回收完成之前号不许发出去」，并给出那个「回收完成」的持久判据
（今天没有：D8 已定项 5 的意图分批是后台可续做的）。

顺带：D6 已定项 1 的判据 9 逐字「标识不回收 + 布局无关：快照标识单调不回收，
回收一个快照 ID 会让盘上遗留的旧 key 在新快照里变成可见」
（`06-…md:110`）。inode 号回收的形状与它同型，而这条戒律没被引用过来。

### 4.2 若「对象出生代兼作复用判别子」站得住，本该看到同一 checkpoint 内复用判别得出来

去查了。判别不出来，而且 E98 已经在另一个字段上测过同一件事。

- P5 逐字定义：「对象出生代 | 8 | 创建该对象那次发布的 checkpoint_txg；
  同时是 inode 号的复用判别子」（`_d8-item6-path.md:79`）。
- `.claude/kb/experiments/98-inode记录与inode树的几何.md:108-110` 逐字：
  「改动计数取 `checkpoint_txg`：同一 checkpoint 内改 8 次 ⇒ 28 对排不出先后（C(8,2)）；
  改 64 次 ⇒ 2016 对……⇒ 改动计数单靠 checkpoint_txg 排不了同窗口内的两个版本。」

同一把尺子：创建、删除、再创建同号，若发生在同一个 checkpoint 内
（窗口是 5 秒 / 2 GiB 脏数据，D16 已定项 5），两个对象的
`(树 ID, 对象 ID, 对象出生代, 锚点偏移)` 逐字段相同。
而 D9 已定项 6 给这个字段的理由逐字是
「inode 号复用后旧文件与新文件的 `(树, 对象, 偏移)` 完全相同」
（`.claude/kb/decisions/09-加密.md:263`）——也就是说，
它存在的唯一目的正好在 checkpoint 粒度下失效。这一格同时是 AAD 的一个字段
（`09-…md:251`），所以后果不止是判别不出来，是两个不同对象的 AAD 逐字节相同。

判定：打中。改成什么：对象出生代不能取 checkpoint_txg。
候选是每 inode 号一个复用计数（经典 inode generation 就是这个），
或者 (checkpoint_txg, 窗口内序号)。注意 E98 已经在改动计数那一格证明
「8 位窗口内序号在 300 次时又不够」（`98-…md:109`），这条要一起算。
另外这是对一条已定 AAD 字段的语义赋值，按 `09-…md:279` 「AAD 的字段组成是
day-1 永久契约」，要走那条流程，不能在 D8 里顺手定。

### 4.3 若「头判别位不必留」成立，本该看到 E98 的撤回理由适用于 P4 的分配规则

去查了。撤回理由成立，但它答的不是 P4 那一问。

`98-…md:99-101` 逐字：「⚠️ 头判别位撤回：D6 已定项 1 定『每头一棵自己的树』，
D8 已定项 3 的注逐字『两个头不再落进同一个 key 槽』⇒ 这一位没有对象。
两条臂都量了：带 2 字节判别位时内部扇出 236，不带是 243——白付 7 格。」

这条说的是「同一个 inode 在两个头里不会撞同一个 key 槽」，成立。
但 P4 还多说了一句「inode 号分配：树内最大号 + 1」，而 D6 已定项 1 之下
克隆头是从 origin 复制出来的（`06-…md:203` 「新克隆的 `prev_snap_txg` 必须
初始化为 origin 快照的 txg」）⇒ 两个头看到同一个「树内最大号」，
各自 +1 得到同一个号，生成两个不同的对象。

这本身不撞 key（不同树），但它撞另一处：D6 已定项 1 的连锁 1 逐字
「② 的跨头共享正是第二个活引用」（`06-…md:202`），跨头共享的块的 AAD 取出生树
（`18-…md:569` 「树维取出生树」）。共享成立时两个头对同一个块用同一个 (出生树, 对象 ID)，
而两个头各自新建的同号对象用的是各自的树 ID ——这一组关系仓里没有一处写全过。

判定：部分打中。「同号」本身不是 bug，但 P4 说「复用由对象出生代判别」，
而在克隆场景里两个头的同号对象连出生代都可能相同（同一次发布创建）。
改成什么：P4 要写明 inode 号的唯一性范围是「(树 ID, inode)」而不是「inode」，
并且要说清跨头共享时读者拿哪一个树 ID 当身份。

### 4.4 D5 / D8 已定项 3 对 inode 号还说了什么

去查了。D5 的记账 key 里没有 inode（`05-…md:208`
「`(统计量标签 2, 树 ID 8, 设备 4, 代 8)`」），所以记账不受影响。
D8 已定项 3 只说 extent key 与命名树 value（`08-…md:125-127`），
没有对 inode 号的分配说过一个字。

判定：没打中（提案没有对这两处做出可核的断言）。
但要记一句：inode 号的分配规则全仓零命中，P4 是第一处，
所以它要自带论证，不能引任何先例。

### 5.2 改动计数取 checkpoint_txg，提交锚 = 叶节点头的诞生代号

### 5.3 flags 恒 0、非 0 判损坏，与预留 32 互相打架

P5 同时写了两件事：

- flags：「第一版恒 0，非 0 ⇒ 该记录判损坏（EIO）……属性 keyspace 的存在位
  日后也走这条」（`_d8-item6-path.md:85`）
- 预留：「预留 32 | 全零；非 0 判损坏」（`_d8-item6-path.md:89`）

去核 D15 判定表第一行：`.claude/kb/decisions/15-格式冻结政策.md:81` 逐字
「新增字段在预留区 / TLV 尾部 | 忽略，继续正常工作 | compat | 否 |
没有语义依赖的纯加法，『忽略陌生字段』这条安全网够用」。

那一行成立的机制是「旧读者忽略」。P5 把预留区定成「非 0 判损坏」，
也就是旧读者拒收 ⇒ 这块预留区在 D15 判定表下不落第一行，落的是 incompat 那几行。
⇒ 32 字节预留买到的只有「偏移稳定」，买不到任何 compat 扩展路径。

而第一轮论证里预留从 16 放大到 32 的理由逐字是
「预留 16 字节不够：上面两个字段就吃掉 16，冻结时零扩展路径」
（`08-…md:363`）——要的正是扩展路径。P5 把字节给了，把路径关了。

这与 C102 是同一个形状：`checks-owed.md:109` 逐字
「⚠️ D18 已定项 11 把共同前缀偏移 7 定成 8 个 flag 位（第一版恒 0、非 0 判损坏、
赋义要 incompat）——它不是本条意义上的预留区（装不下字段），
这条门禁不许把它当预留区指到」。

判定：打中。改成什么：预留区与 flags 位要分开定政策。
预留区取「忽略陌生内容」才买得到 compat；要「非 0 判损坏」就别叫预留，
叫「必须为零的填充」，并另外给一条真的扩展路线（第一轮判决逐字要的是
「一条定下来的溢出路线」，`08-…md:374`）。

### 5.4 flags 那个两难，本项解了吗

## 六、P6 三条不变量

### 6.1 若「locality 对照两侧都在权威态」是对的，本该看到 extent key 在权威态

去查了。不在。这句话是 P6 里唯一一处可以逐字判假的断言。

- P6 逐字：「这是 F12 说的那条『三方对照』，两侧都在权威态里。」（`_d8-item6-path.md:97`）
- 而对照的另一侧是 extent 树的 key，extent 树按 D21 是派生态
  （`21-…md:8` 「派生态 | 索引（树） | 丢了只是慢」），P1 也没有把 extent 树扩进权威态。

⇒ 两侧不是都在权威态，一侧在（记录），一侧不在（extent key）。

### 6.2 那么扫描重建之后这条不变量还判不判得红

去查了。判不红了，而且 P6 自己写出了原因。

- P6 逐字：「扫描重建时以记录里的值为准放回数据单元（单元头给 (对象 ID, 锚点偏移)，
  记录给首段）」（`_d8-item6-path.md:97`）
- 数据单元头确实没有 locality_id：`18-…md:592` 五元组 =
  「标签 1 + 树 ID 8 + 对象 ID 8 + 对象出生代 8 + 锚点偏移 8」；
  `08-…md:340` 也逐字确认「数据单元头的五元组……没有 `locality_id`」。

⇒ 重建之后 extent key 的首段是从记录里抄过去的，两侧同源。
checker 再拿两侧对照，等于拿记录跟记录自己比。
这正是 `.claude/rules/fs-design.md` 那条「审计与被审计用同一段代码」要禁的形状，
也是 D8 已定项 1 判增量 Δ 时用的同一句话：`08-…md:37` 逐字
「checker 只能拿同一个累加函数重放同一份 Δ 日志，它在和自己比」。

E98 判据 3 量出的判别力（`98-…md:105-106` 「带对照臂抓 1000、静默 0；
不带对照臂抓 0、静默读空洞 1000」）是在「extent key 独立给定」的模型里数的，
不覆盖重建之后那一态。

判定：打中。改成什么：这条不变量要写明射程——
「只在 extent 树未经重建时有判别力；重建之后两侧同源，不判红」。
要让它在重建之后仍然有判别力，唯一的办法是让 locality_id 在权威侧另有一处见证，
而那正是第二轮反推腿给的修法（`08-…md:412-414` 把 locality_id 加进单元身份），
它被判为「要动已定条款，因此必须由用户定」，且 `09-…md:280` 逐字把 locality_id
排除在 AAD 之外，理由是「让声明为『可以是错的』的字段承重」。

### 6.3 D9 已定项 6 那条排除理由，本项把它的前提打掉了却没修订

`09-…md:280` 逐字：「`locality_id` | D8 已定项 3 逐字：『locality_id 是提示，
不是正确性的一部分——它可以是错的、可以过期』| 让声明为『可以是错的』的字段承重」

而 D8 已定项 3 现在逐字写着相反的话：`08-…md:200-201`
「⚠️『它是提示、可以是错的』准许的是不信它的含义，不是不存它的位：
作为地址首段它的取值精确且定义性。」

⇒ D9 已定项 6 排除 locality_id 的那条理由，其引用的原文已经被改掉了。
第二轮论证已经点过这一处（`08-…md:409-410` 逐字
「这句话在新形态下变成了数据丢失许可证，而提案没有修订它、也没有标注这次提升」），
P5 / P6 仍然没有修订它，也没有标注。

判定：打中，且是第二轮同一处的复发。
改成什么：P6 要么附一条「D9 已定项 6 那行的排除理由要重写（不改结论）」，
要么明说本项不处置并把它挂成欠账。不能第三轮还是当它不存在。

### 6.4 nlink 的 gate 与「位不回收」

P6 逐字：「超级块一个单调 feature 位『dirent 树已上线』；位未置时 checker 不评估
『nlink == dirent 条数』，置了之后零豁免」（`_d8-item6-path.md:98`）。

去查了三处：

1. `15-…md:99-104` 逐字「位一旦用过不许回收……feature bit 是磁盘上真实存在过的物理位。
   回收后重新分配给新特性，一个旧镜像挂到新代码上，这一位会被误读成
   『新特性 X 已启用』——文件系统会真的做错事」
   ⇒ 这个位是永久的。它是一根只在第一版到目录上线之间有用的脚手架，
   但格式里要永远留着。P6 没有写这笔代价。
2. `15-…md:93` 逐字「位数：三个 bitmap 各 256 位（`u64[4]`），存超级块」——
   compat / compat_ro / incompat 三张。P6 没说这个位进哪一张。
   它既不是能力声明也不是兼容开关，是一个状态位，三张表都不太像它的家。
3. 第二轮反推腿打中的那半，P6 没答：`08-…md:395` 逐字
   「而且那个开关是盘上可被同一次损坏翻掉的状态」。
   P6 只写「单调」，而单调是一条政策，盘上没有任何东西执行它。
   对照同一形状的另一处，仓里是怎么处理的：`18-…md:344` 逐字
   「级 1 → 级 2 的晋升必须留痕，不许原地把标志位改回正常……
   留痕内容：依据哪一批双证、何时晋升；那条记录自己也要能被 checker 复核」。
   P6 没有对应的留痕要求。

另外我 grep 过 `.claude/kb/invariants.md`，「nlink」零命中——
这条 gate 门着的那条不变量今天在不变量清单里不存在。

判定：打中。改成什么：① 补留痕要求（照 D18 已定项 5 要求 2 的形状）；
② 说明位进三张 bitmap 的哪一张、以及它是永久的；
③ 先把「nlink == dirent 条数」立成 invariants.md 的一条（现在没有），
   否则 gate 门的是一条不存在的规则。

### 6.5 身份对照（不变量 1）

记录里的 inode 必须等于 key，不等判红。这一条我找不到反例：
key 与记录是两处独立写入，对照有判别力，且不依赖重建。

判定：没打中。
