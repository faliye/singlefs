# D18 未定项 12 第二轮 · 攻方腿（Sonnet）输出

立场：攻三步推理链与五条臂。全部引文整行抄原文并给文件路径 + 行号；构造不出反例的地方明说，不假装打中。

## 一、攻步骤 1（遍历重算不出水位）

### 1.1 步骤 1 原文的字面陈述为假：删除的号在回收窗口内仍在树里

`.claude/kb/decisions/08-核心索引结构.md:375`：

> **inode 记录在回收完成前留在 inode 树里（nlink = 0），`deleted_inodes` 只存号**

配套不变量 `.claude/kb/invariants.md:257`（I-9.5）：

> `deleted_inodes` 里的每个 inode 号在同一棵树的 inode 树里存在且记录的 nlink = 0（记录在回收完成前留在 inode 树里，`deleted_inodes` 只存号）

这两条一起说明：**一个号被 `rm` 之后，在后台回收窗口关闭之前，它的记录物理上仍然躺在 inode 树里、可以被遍历读到**（只是 nlink = 0）。
背景材料步骤 1 的原句是「numbers that were issued and then deleted are not among them」——按字面，这句话对回收窗口内的号是**假**的：它们恰恰还在「现存对象」（现存记录）之列，遍历遇到它们不会漏号。

### 1.2 但收窄后，结论方向仍然大概率成立——缺口比步骤 1 说的窄

真正的缺口只在**完全回收之后**：`.claude/kb/decisions/08-核心索引结构.md:333` 明写打包记录类型 2（inode 记录）
「死亡不写墓碑，死亡由现行叶版本体现」——记录被回收时不留墓碑，直接从叶里消失，物理上不留痕迹。
一旦某个号是「历史最大已发号」且已经完全回收（没有更大号后续发出），遍历得到的树内最大 key 就会**低于**真实水位。

所以攻击结论：**步骤 1 的推理成立，但它给出的原因写错了**——不是「删除的号立刻从盘上消失」，
而是「删除的号在**回收完成**之后才从盘上消失，且没有墓碑兜底」。这个区别不是文字游戏：
它直接决定步骤 3 的规模——真正需要额外机制兜住的，只是「历史最大号被删并完全回收」这一类狭窄场景，
不是背景材料暗示的「任何删除」。

### 1.3 反推：I-9.6 里出现的第二个来源，没有解决问题

`.claude/kb/invariants.md:258`（I-9.6）：

> 每个可写头的「inode 号水位」统计量 > 该树 inode 树内最大 key，> **该树全部墓碑记录的对象 ID**；checker 遍历侧算出的最大值与记账里的水位是两条独立路径

这条不变量字面上还引用了「该树全部墓碑记录的对象 ID」作为第二个下界来源。但按 1.2 引的原文，
**打包记录类型 2（inode 记录）死亡不写墓碑**——这个来源对 inode 树是空集，I-9.6 这半句字面上够不到 inode 号水位。
这是仓里自己的一处内部不一致（I-9.6 的措辞疑似照抄了别处「水位族」模板，未按 inode 树的实际墓碑策略收窄），
不构成能推翻步骤 1 的证据，但值得记一笔：**遍历侧目前没有任何盘上残留能补上完全回收之后的缺口**。

**判定：步骤 1 的字面推理有缺陷（过强），但收窄后的版本站得住，我找不到能推翻收窄版本的反例。**

## 二、攻步骤 2（P3 对这一行的排除理由为假）

步骤 2 是纯逻辑推导：若步骤 1（收窄版）成立，则「它离线可由遍历重算」这句理由对这一行为假。
这一步本身不需要攻——它是条件句，条件(步骤1)已经在收窄意义上站住，结论随之成立。

但我核实了 P3 原文的确切措辞，发现一个此前背景材料没有引到的细节，值得放进讨论。

`.claude/kb/decisions/18-块里携带什么信息.md:718`：

> **码 2 不进扫描重建的择版本规则**：它离线可由遍历重算，**重建按派生量那一段整个重写它**（理由取「可重算」，不取「它是派生态」——D21（权威态与派生态的分界） 明写单元类码不是态别的判据、记账树的码 2 节点就是权威态）。

`.claude/kb/decisions/21-权威态与派生态的分界.md:17`：

> 记账是同一条判据的已定实例：离线可由遍历重算，但被问到那一刻要有答案，故取权威态。单元类码不是态别的判据——记账树的码 2 节点是权威态。

关键词是「**重建按派生量那一段整个重写它**」——P3 对码 2 设计的机制从来不是「在多个物理副本里挑一个现行版本读出来」，
而是「**整个重算重写**」（类似 inode 树内部节点：丢了就从叶重新生成，见 `.claude/kb/decisions/08-核心索引结构.md:413`
「内部节点丢了，收集打包记录类型 2 的容器…内部节点的 key 区间由叶算」）。

⇒ 这条线索直接喂给第三步的攻击：**P3 从未设想过「给码 2 留事务号做容器级版本选择」这条路**，
它设想的唯一路是「recompute」。步骤 1 打掉的是 recompute 这条路，但**打掉一条路不等于剩下的路只有「容器级版本选择」一条**——
见下面第三节。

## 三、攻步骤 3（因此需要单元头的事务号）——这是最关键的一节

步骤 3 的论证形状是：recompute 不行 ⇒ 必须择版本 ⇒ 择版本必须用事务号做同 checkpoint 内平局破除。
第一个箭头（recompute 不行 ⇒ 必须择版本）是一次**未经检验的跳步**：它假定除了「recompute」和
「容器级版本选择 + 事务号」之外没有第三条路。我找到至少两条路，外加一条部分验证的第三路，都不需要动码 2 的字节。

### 3.1 第一条路：消息自带的 seq 已经解决了「同一 checkpoint 内重复写同 key」这个问题——而且是已经跑过、已经钉死绝对值的实验

背景材料的问题原句是：「记账条目取『幂等完整值』（D8 已定项 1），合并规则是『后者胜』且『后者由 seq 定』（D5 已定项 2）。
既然记账条目自带 seq 用来去重，那扫描重建择版本用得着单元头的事务号吗？」——这个问题问得对，答案是**用不着**，而且不是我推的，是仓里已有实验直接测过。

`.claude/kb/decisions/05-快照-空间记账机制.md:281`（已定项 2）：

> key = (统计量类型标签, 维度元组, 代号)；value = 该统计量在该代的完整值；合并规则按统计量分：**非单调统计量「后者胜」（后者由 seq 定）**，**单调统计量取最大值**（今天有已定项 4 第 12、13、14 三项：inode 号水位、清扫水位、最近一次根销毁的代号）

注意：**inode 号水位是单调统计量**，走的是「取最大值」，根本不是「后者胜」——这条分支从设计上就是**幂等、交换、结合**的（原文明写，见下）。

`.claude/kb/decisions/08-核心索引结构.md:379`：

> **合并规则取最大值**（幂等、交换、结合）；条目照样带 seq（D8（核心索引结构） write buffer 硬要求 3 是格式要求，一棵 write buffer 树一套条目格式），**只是合并结果不依赖它**。

也就是说：对 inode 号水位这一条统计量，「谁是最后写的」根本不重要，**任意顺序、任意重复读取所有物理副本里的消息，取最大值都能得到正确答案**——
这比背景材料设想的「先选出唯一 current version 再读」宽松得多。

再看 `seq` 本身是不是已经被验证能在「同一 checkpoint 窗口内同 key 被写多次、到达顺序被打乱」这个确切场景下工作：

`.claude/kb/experiments/99-writebuffer条目与seq的去重.md:58-89`（E99，已跑，12 单测 / 10 条变异全抓）：

> 判据 6：记账树的 key 里**已经有代**，seq 不必重复携带 txg……⇒ 同一个 key 的待去重条目必然同属一个发布窗口 ⇒ seq 只需要窗口内序号……记账树（key 含代）：**4 字节**
>
> 判据 2 + 3：1000 个 key、每个 8 次更新、按 key 排序之后**到达顺序被丢掉**：
>
> | 臂 | 不插挂载（选错 / 未定义）| 插一次挂载（选错 / 未定义）|
> |---|---|---|
> | 无 seq | 0 / 1000 | 0 / 1000 |
> | `txg + 窗口序号` | **0 / 0** | **0 / 0** |

这个实验测的场景——「同一个 key 的多条消息、到达顺序被打乱、要正确去重/排序」——**正是步骤 3 所说的
『固定点迭代导致同一容器一个 checkpoint 内被写多次』在消息粒度上的等价物**。E99 已经证明：
只要每条消息自带 4 字节窗口内 seq，去重 100% 正确，**完全不需要知道消息物理上落在哪一个码 2 容器副本里**。

⇒ 换句话说：即便扫描重建**同时看到同一个码 2 节点的两个物理版本**，它也不需要判断「哪个是 current」——
它可以把两个版本里能读到的全部消息**收集到一起**，凭消息自己的 (key, seq) 去重、按 D5 已定项 2 的规则合并
（单调取最大 / 非单调后者胜由 seq 定），得到的答案与「先选出唯一 current 版本再读」是同一个答案，
**前提是消息集合在一个 checkpoint 内只增不减**（见 3.3 的保留意见）。

**这直接推翻步骤 3「必须择版本」的必然性**：择版本只是解法之一，不是唯一解法。

### 3.2 第二条路：C143 自己登记的候选修复方案里，没有一条是「码 2 容器加事务号版本选择」

`.claude/kb/checks-owed.md:150`（C143，仍欠着）载体候选逐字是：

> 载体定案（要用户定案）：候选是**树表条目里每头一个字段**（与 2026-09-06 刚定的诞生 txg / `prev_snap_txg` 同处），或**让记账里的单调量在回退时豁免重载**（改 D23（journal 的角色与格式） 已定项 14）；两条都是格式级

这两条候选**都不是**「保留 inode 水位住在记账树的码 2 节点里，靠单元头事务号做版本选择」——
候选①是把水位整体搬出记账树，挪进树表条目（一个头一个定长字段，天然不会被固定点迭代多次重写出多副本，
因为它的载体是树表这类单元，不是记账那种 write-buffer 缓冲结构）；候选②是给回退重载开个例外，
让水位不必每次都从 R_old 的账重新载入。

而且候选①有一个**刚刚发生过的同类先例**：背景材料自己的「A counter-consideration」部分写道
「2026-09-06 a user ruled that the tree id watermark moves out of accounting into the root record」——
树 ID 水位这条**同样带树维、同样是单调统计量**的量，就在两天前刚被从记账树整个搬走了。
如果 inode 号水位比照办理（这是 C143 候选①的方向），那么此刻讨论的这整条统计量根本不会再落在
「会被固定点多次重写的码 2 记账节点」里——步骤 3 的物理前提（同一 checkpoint 内该码 2 节点有多个物理版本、
需要在其中选出装着这行统计量的那一个）就不存在了。

⇒ **步骤 3 的结论建立在一个尚未定案、且最可能的两条候选修复都会使其前提消失的开放问题（C143）之上**。
在 C143 定案之前，把「给码 2 留 6 字节事务号」当成步骤 1/2 的必然推论，属于**在未决问题上抢先做格式承诺**。

### 3.3 第三条路（部分验证，标为待证）：即使不管容器版本，直接对该 key 范围做「全副本消息并集」

3.1 已经论证：只要消息集合是「只增不减」，merge-all-versions 就能给出正确答案，不需要择版本。
唯一没有把握的地方是：**同一 checkpoint 内，码 2 容器的一次重写，会不会伴随「把部分消息 flush 给子节点、并从本容器的缓冲区里移除」**？
若会，则一个较早的物理副本可能包含一条「已经被 flush 走」的消息，merge-all 会把它错误地并回来。

我在仓里搜索不到任何一处正面回答「同一个 checkpoint 窗口内，write buffer 是否会发生部分 flush」——
`.claude/kb/decisions/08-核心索引结构.md` 与 `.claude/kb/decisions/05-快照-空间记账机制.md` 里没有 flush 与
「同一 checkpoint / 一次发布内」搭配出现的条款。**这是全仓的一处空白，不是我能现查现核的事实**，
按 `verify-before-claiming.md` 只能标记为待证，不能替它下结论。

**判定：步骤 3「因此需要单元头事务号」这个结论没有必然性**——3.1 与 3.2 已经指出两条不需要动码 2 字节、
且分别有实测数据（E99）与在飞先例（树 ID 水位搬迁）支持的路；3.3 的第三条路缺一块尚未验证的前提，但它即便不成立，
也不影响 3.1/3.2 已经打开的缺口。三步链条最多能站到步骤 2（P3 排除码 2 的理由对这一行不成立），
**站不到步骤 3 的最终结论**。

## 四、攻臂 D

### 4.1 载荷 CRC 对码 2 到底买不买得到东西——找不到已证实的消费路径，且有反例证据

C104 的判别力自证只覆盖了码 1（数据单元）那一半：

`.claude/kb/checks-owed.md:111`（C104）：

> **已还一半（2026-09-05…）**：码 1 的类身份段加 4 字节载荷 CRC（头 105），副本归并判「载荷逐字节相同」时有据可查。**码 2 那一半仍欠着**：候选「把 CRC 挪进共同前缀一次关全部类」没有采纳，码 2 的载荷完整性证据仍是空的……判别力自证：造「头好、载荷改一字节、诞生代号 ≤ 根 txg、有分配记录」的数据单元样本，扫描重建级 2 收进即红；补上载荷 CRC 后必须拒收。

这条判别力自证的样本是**数据单元**（码 1），**不是**码 2——C104 从来没有为码 2 造过一个「载荷改一字节、必须被 CRC 抓到」的样本。
也就是说：**码 2 的载荷 CRC 目前没有任何一条被验证过的读取路径会去消费它**。

反例证据（inode 树内部节点，本身也是码 2）：`.claude/kb/decisions/08-核心索引结构.md:413`

> **重建**：内部节点丢了，收集打包记录类型 2 的容器，按 (出生树, 容器号, 容器出生代) 分组，同身份多版的择现行 = C113；每叶 key 范围由记录算，**内部节点的 key 区间由叶算**

这条路径**完全不读旧码 2 节点本身的字节**——它把内部节点当作丢失的东西，从叶重新生成。inode 树内部节点上如果挂了载荷 CRC，
在这条重建路径上永远不会被校验，因为压根不会去读旧内容。

⇒ 载荷 CRC 对码 2 是否有价值，**取决于第三节的三步链条本身站不站得住**：
只有当（a）步骤 1/2 成立（这条统计量确实不能被 recompute）**且**（b）最终选择的修复路径确实是
「靠扫描直接读记账码 2 节点里残留的消息」（而不是 3.2 里 C143 候选①那种把水位搬出记账树），
载荷 CRC 才会有一个真实的消费者。这是一个**窄且有条件**的收益，不是「码 2 普遍地补上了载荷完整性证据」——
把它写成后一种说法是对收益范围的夸大。

### 4.2 「预留 2」算不算 C102 意义上的「预留字段」——字面上大概率过关，但买不到 C102 真正想要的东西

C102 的判别力自证专门排除了 flag 位：

`.claude/kb/checks-owed.md:109`（C102）：

> 判别力自证：给索引节点头加一个预留字段必须转绿，删掉必须红。⚠️ D18（块里携带什么信息） 已定项 11 把共同前缀偏移 7 定成 8 个 flag 位（第一版恒 0、非 0 判损坏、赋义要 incompat）——**它不是本条意义上的预留区（装不下字段）**，这条门禁不许把它当预留区指到

排除 flag 位的理由是「装不下字段」——这是**粒度**判据（位 vs 字节），不是宽度判据。2 字节是字节寻址的、
可以被单独取出来赋值的区域，粒度上不是 flag 位那一类，字面上应当能通过「指到一个真实存在的预留区」这条测。

但有两处理由让我认为这个「过关」是**形式性**的，买不到 C102 真正要的东西：

1. **这 2 字节的宽度不是为将来的字段设计出来的，是凑出来的余数**——arm D 的原话是「6 字节」减去「payload CRC 需要的 4 字节」剩下 2。
   对比仓里唯一的同类先例，D18 已定项 7 的 nonce 代号 / MAC 预留位，其宽度是按 D9（加密）实际要用的密钥学尺寸倒推出来的
   （`.claude/kb/decisions/19-块指针的结构与宽度预算.md:260-266`：MAC 128 位 + nonce 96 位，指针里恒定占位）——
   是「已知将来要装什么、按那个东西的尺寸留位」，不是「剩多少留多少」。
2. **2 字节相对本仓其他预留区显得极窄**。D8（核心索引结构） 已定项 6 的 inode 记录字段表（`.claude/kb/decisions/08-核心索引结构.md`
   「预留（恒 0）| 20」）为同类用途留了 20 字节。2 字节大约只够装一个小版本号或者一个小枚举，
   下一次真的要加字段时，大概率仍然不够，等于把「加字段要不要 incompat」这个问题往后挪了一小步，
   而不是真正解决。

**判定**：2 字节大概率能在字面上通过 C102 现有的门禁判据（这本身是 C102 判据的一个盲点：只挡了「太窄的 flag 位」，
没挡「凑出来的、宽度与任何已知未来字段都不对齐的窄预留区」），但**不构成 C102 真正想买的那种「以后加字段不必 incompat」的实质保障**。
这不是否定臂 D 的理由（2 字节总比 0 字节强），但引用它作为「还清了 C102」的证据时，应该说清这层保留。

## 五、第六条臂

**F. 砍到 4 字节（省下臂 A 的全部空间），不给码 2 留任何事务号字段；把「同一 checkpoint 内该记账码 2 节点被固定点多次重写」这件事，
从『容器级选出 current version』改造成『消息级合并全部可读副本』**——扫描重建遇到同一个 (树, 层级, key 区间, 诞生代号) 的多个物理副本时，
不判定谁是「现行版本」，而是把每个可读副本里的消息**全部收集起来**，按各消息自带的 (key, seq)（D8 已定项 7）
与 D5 已定项 2 的合并规则（单调统计量取最大值、非单调统计量按 seq 后者胜）统一 merge，得到的结果与
「先选出一个 current 容器再读」在 3.1 论证的前提下是同一个答案。

这条臂与臂 E 的核心差别：臂 E 仍然是**容器级机制**（给码 2 塞一个新语义的写序字段，纳入 I-1.8 的容器级归并规则）；
臂 F 是**放弃容器级版本选择**，把问题整个降到消息级解决，字节代价为 0（连臂 A 都不用改，因为它天然只需要 4 字节实例代号）。

臂 F 不是凭空提的：它直接对应第三节 3.1 已经用 E99 的实测数据支持过的那条路径，
以及 D8 已定项 1「取幂等完整值，接受 key 数量上升」（`.claude/kb/decisions/08-核心索引结构.md:69`）本身的设计初衷——
幂等值本来就是为了让「乱序、重复也能安全合并」这件事成立，臂 F 只是把这个初衷用到扫描重建的场景里，而不是像
背景材料默认的那样，遇到多副本第一反应是「选一个赢家」。

**臂 F 的已知风险**（第三节 3.3 已经指出，不重复展开）：如果同一 checkpoint 窗口内会发生部分 flush
（消息从码 2 缓冲区移出、推给子节点），merge-all 可能错误复活已经 flush 的消息。这是仓里一处真实的空白
（`.claude/kb/decisions/08-核心索引结构.md` 与 `.claude/kb/decisions/05-快照-空间记账机制.md` 均未回答「一个 checkpoint 内
write buffer 是否会部分 flush」），应该在采纳臂 F 之前先把这个问题问清楚——这本身构不成否定臂 F 的理由，
只是列出臂 F 需要先还上的一笔账。

## 六、结论摘要

| 步骤/臂 | 判定 |
|---|---|
| 步骤 1 | 字面陈述过强（回收窗口内的删除号仍可被遍历发现，I-9.5），但收窄到「完全回收后的号」仍然成立，找不到反例 |
| 步骤 2 | 纯逻辑推导，条件满足则结论成立；额外找到 P3 原文「重建按派生量那一段整个重写它」，说明 P3 设想的路本来就不是「容器级择版本」 |
| 步骤 3 | **不成立**——至少两条不动码 2 字节的路（消息级 seq 合并，已用 E99 实测验证；C143 候选①「水位搬出记账树」，有树 ID 水位先例）没有被排除，第三条（全副本消息并集）部分验证、缺一块关于「checkpoint 内是否部分 flush」的空白 |
| 臂 D 收益 #1（C104） | 条件性、范围窄：只在步骤 1-3 全部成立且最终未采用「搬出记账树」这类修复时才兑现；且没有任何已验证的消费路径，inode 树内部节点重建路径（同为码 2）反例显示「码 2 payload 常被整体重算、从不被读」 |
| 臂 D 收益 #2（C102） | 字面上大概率能过门禁的现有判据，但 2 字节是凑出来的余数，不是按未来字段尺寸设计的，买不到 C102 真正要的「以后加字段不必 incompat」的实质保障 |
| 新增臂 F | 砍到 4 字节 + 消息级合并全部可读副本，绕开步骤 3 的必要性；已知风险是「checkpoint 内部分 flush」这一未验证前提 |

**最重的一条**：第三节 3.1——E99 已经用实测数据（12 单测、10 条变异全抓、跨挂载/回绕绝对值钉死）证明
「同一 key 在同一 checkpoint 窗口内被多次写、到达顺序被打乱」这个问题，靠消息自带的 4 字节 seq 就能 100% 正确去重，
根本不需要知道消息躺在哪一个物理码 2 容器版本里。步骤 3 从「recompute 不行」跳到「必须容器级择版本、必须用事务号」，
跳过了这条已经验证过的更便宜的路，这个跳步没有论证支撑。
