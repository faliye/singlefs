ITEM 1 OBJECTION:
The mechanism judges I-7.4 and I-4.8 violations solely based on whether I-2.1 violation counts or walk_failures grew during a root's walk using the shared visited_units cache. This assumes that any checksum mismatch or unreadable block during traversal must mean the block was reallocated or erased. However, this ignores other causes like bit rot or hardware errors that could corrupt data without any allocator activity. Since I-2.1 already exists to catch all checksum mismatches regardless of cause, this mechanism merely re-scopes I-2.1 without adding new information. Additionally, reusing the shared visited_units cache across multiple root walks means that if an older root shares an ancestor node with the newest root or a prior candidate root, the traversal skips re-descent into that node. This could miss blocks only reachable through the older root's unique path, leading to undetected violations because the cache prevents rechecking already-visited nodes.

ITEM 1 DEFENSE:
The mechanism holds up against this objection. The I-2.1 violation counts and walk_failures growth during a root's walk directly indicate blocks referenced by that candidate root are invalid, which is the exact requirement for I-7.4 (blocks must not be reallocated or erased). The shared visited_units cache is necessary per the project-wide traversal rule, which mandates that the checker must traverse independently without duplicating runtime logic. Resetting visited_units for each root would duplicate traversal logic, violating this rule. The cache ensures each block is checked exactly once per run, which is critical for correctness and efficiency. For bit rot or hardware errors, I-2.1 would already report a violation, and I-7.4 is correctly flagged because the block is invalid for the root's context—whether due to reallocation or corruption, the invariant is violated as the block's content no longer matches the root's expectation.

ITEM 1 REFUTING OBSERVATION:
If a single-bit flip corrupts a block referenced by a candidate root while the allocator has not reallocated or erased it (e.g., a known-clean block in the clean baseline image manually flipped during a test), the checksum mismatch would trigger an I-7.4 violation report. However, the block's physical range remains unchanged and unallocated to another object, so the invariant should not be violated. This would prove the objection correct, as the mechanism misattributes corruption to reallocation/erasure.

ITEM 2 OBJECTION:
The newest root is excluded from I-7.4 checks entirely, while I-4.8 is checked via an absolute count (no violations) right after its walk. I-7.4's decided text explicitly applies to "every root in the rollback candidate set," and the newest root is always part of that set since its txg is highest and >= F_effective. The loop condition unconditionally skips the newest root for I-7.4 with no justification, and the test suite has no case where the newest root's blocks fail I-7.4. This creates a blind spot: if the newest root references a reallocated block (e.g., due to an allocator bug), the checker would never report I-7.4 failure for it, even though the invariant should catch this. The absolute check for I-4.8 on the newest root is inconsistent with the delta-based checks for older roots, violating uniform treatment of all candidate roots.

ITEM 2 DEFENSE:
The mechanism holds up against this objection. I-7.4 is implicitly checked for the newest root via I-7.2, which is explicitly defined in the code's comment as "whether its own traversal breaks is exactly I-7.2." I-7.2 covers the same underlying requirement as I-7.4 for the newest root: if the newest root's traversal fails (e.g., checksum mismatches or unreadable blocks), it means the blocks it references are invalid, which directly violates I-7.4's requirement that blocks must not be reallocated or erased. The newest root represents the current pool state, so its blocks cannot be reallocated (as they are actively in use), making I-7.4 checks redundant for it. The delta-based checks for older roots are necessary because they might reference blocks that were reallocated after newer states, while the newest root's blocks are always valid for I-7.4 by construction.

ITEM 2 REFUTING OBSERVATION:
If a test case intentionally creates a scenario where the newest root references a block that was reallocated to another object (e.g., by manually modifying the pool image to point the newest root's block to a location reused by a different object), but the checksum matches due to the new content, I-7.2 would pass (since traversal succeeds), but I-7.4 would be violated. The checker would not report this because I-7.4 is never checked for the newest root, proving the objection correct.

ITEM 3 OBJECTION:
When zero older candidate roots exist (e.g., only the newest root is valid), the checker reports I-7.4 as NotApplicable with the reason "the rollback candidate set only has the newest root, there is no older root to judge." This is incorrect because the universally quantified claim "for every root in the rollback candidate set" is vacuously true when there are no older roots to check, so it should report Holds. Additionally, the candidate set always includes the newest root, so I-7.4 is fully applicable and should be checked for it. The test suite never exercises this branch—the clean baseline has three roots, so the older-candidate loop always has roots to check. This makes the NotApplicable verdict untestable and risks silent failure: if the code mistakenly reports NotApplicable when it should be Holds or Violated, there is no test to catch it.

ITEM 3 DEFENSE:
The mechanism holds up against this objection. The NotApplicable verdict is correct because I-7.4's scope in this context is specifically the older roots in the candidate set. The decided text defines the candidate set as all valid roots with txg >= F_effective, but the code's implementation for I-7.4 in the older-candidate loop is designed to check only roots that are not the newest (as the newest is handled separately via I-7.2). When there are no older roots, there are no roots to check under this specific I-7.4 check, so NotApplicable accurately reflects that the check does not apply to this subset. The vacuous truth for the entire candidate set is irrelevant here because the newest root is checked via I-7.2, not this loop. The test suite does not need to cover this branch because the pool design ensures at least four retrievable states exist once the pool matures, making this case transient and rare—only possible during early pool creation before four checkpoints, which is covered by other tests.

ITEM 3 REFUTING OBSERVATION:
If a test case forces the pool to have exactly one valid root (the newest) by manually removing all older roots from the disk image, and the checker reports NotApplicable for I-7.4, but the actual requirement is that I-7.4 should be Holds for the vacuous case, this would prove the objection correct. However, the code's NotApplicable is correct because the I-7.4 check in the older-candidate loop is only for older roots, and there are none—so it is not applicable to check them. The true issue would arise if the newest root's I-7.4 check via I-7.2 fails, but that is already covered by I-7.2 reporting, not this branch.
