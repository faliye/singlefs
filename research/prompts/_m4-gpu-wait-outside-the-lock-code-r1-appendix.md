5. **什么时候起跑**：挂载就起、按周期查。每次发布之后按已定项 1 的三水位查一次；另有定时兜底，每隔一段时间再查一次，间隔是挂载参数，默认 30 秒。周期线程住在新开的运行库一层：挂载时按参数开卡、建实例、挂载、起周期线程，前台与后台经一把锁排队；核心层照旧不起线程、不读钟。后台整理的一批分三段：会话锁里取输入（问让路、排空待发、读一次后台计算设置、现行那一版只拷指针），锁外算（GPU 与 CPU 两条路径都走；选段循环每一圈要读盘上的一段时回会话锁里读那一段再放锁），回会话锁里发布。锁外那一段算完先放 GPU 实现那把锁再回会话锁。回锁里出错先于一切；不作废：先排空待发、重取隔离集，有活意图时比起点在 R 里的未释放记录的整条记录与集合相等，变了的单元从计划里剔掉，其余在现行那一版上发布，剔完一个不剩就不发；签发时对选中的段在现行那一版上重判资格与签发前那一判，各个量取现行那一版的；回锁那一次发布同样过回退候选集那道门；回锁时有冻结的发布就丢掉这一批、记单独的停因。会话上记有一批在锁外，这时再取输入被拒。定时兜底的预算照旧与用户改动共用同一份（第 6 条），挂载不再给新预算。一次整理发布要写的根槽连同它之后的余量里的根一走、根环里不同用户状态就少于 4 个时，这次整理发布不发（守 D16（发布语义） 已定项 1 的「回退候选集保留最近 4 个可退到的不同状态」）；余量取 S 槽，S 是每区根槽数（根环共 3S 槽）。只有全空聚簇段数低于底额（已定项 3）、前台已写不进时破例，每趟至少发 1 次；破例排在第 6 条的让路之前，前台有入口在等也照发（前台已写不进，让路换不来什么）。停着时那一次只删意图的发布（第 4 条）同样过这道门：门关就不发，意图与 `R` 排他留到门开；破例的条件（全空聚簇段数低于底额、前台已写不进）成立时，这一次也照发。删除队列不空也算起跑：这一趟只走队列、不发整理，不看水位，也不被发布预算挡。两种模式起跑规则相同。
6. **起跑之后的节奏**：GC 不在用户改动的调用线程里跑（不在用户改动返回之前跑一批），挪出之后三样照旧有保证：一趟发布预算有上限、签下一条意图那一判跨趟留着、整理批不插进用户改动的抬 F 与再判之间。签下一条意图那一判读的「上一条完成的意图」只留到下一次用户改动发成为止：每次用户改动发成就清掉它，下一趟从空起照常签新意图，预算照旧是这一次改动给的那一份；被拒、没发成的改动不清。GC 占盘写带宽有一个上限（挂载参数）；前台有任何入口在等会话锁（fsync、收下改动、单发改动、读、切换后台计算）时不发下一批，这一判别子要 GC 挪出调用线程之后才看得到；它只约束整理批（每一批取输入之前问调用方一次，回会话锁里发布那一刻不再问）；前台入口不断时有下限：连着让路 N 次或让路累计 T 毫秒，哪一个先到下一批就不让，一批发成两个都清零，N 与 T 是挂载参数；全空聚簇段数低于底额、前台已写不进时的破例批仍旧不让，整理开头先走的那一遍删除不是整理批，不受它约束。整理开头先走一遍删除（把盘上留着的删除意图做完）是可选的前置优化、为了效率，不是整理的一部分：删除与整理是两件事、各是各的事务，整理也可以不先删除；那一遍删除发的版不占整理一趟的发布预算。整理一批本身就是那次移动，整理判出的死空间由分配器的常规回收放掉、不交给删除；没删完的留到下一趟整理或下一次可写挂载，不因为它没删完挡住别的操作。 发布写失败冻结之后，前台 fsync 不在冻结时答成功：先重发那一次冻结的发布，发成了才答成功，没发成交回错误。重发成了照冻结那一次的种类记账：冻结的是用户改动，照一次用户改动发成办（重给预算、清掉上一条完成的意图）；冻结的是后台批，照后台批记。
7. **值不值按省下的 CPU 时间算**：GPU 模式的目的是少占主机 CPU 时间，数据量大时跑得更快只是副产物。收益是后台任务少占的主机 CPU 时间（CPU 模式下它的 CPU 时间减 GPU 模式下它的 CPU 时间，后者含准备数据、提交、等结果、两份结果的比对，以及第 8 条交 CPU 判的那几条），挂钟与 CPU 模式持平也做；D24（后台重活能不能卸给 GPU） 已定项 3 那条按挂钟比的判据不管这一项罩着的后台任务。实现之后跑一组对照：同一负载、同一池，CPU 模式与 GPU 模式各跑，报两边的 GC 挂钟、主机 CPU 时间、前台 fsync 延迟，并在几档盘容量上各跑一遍，看收益随容量怎么变。
8. **GPU 的结果怎么复核**：两份独立写的 GPU 核（不共用核函数）对同一批输入各算一次，逐条比两份的结果。两次相同的条目算确认，交 CPU：CPU 照发布路径逐条核计划与读盘核（`crates/singlefs-core/src/transaction.rs` 的 `relocation_checked_against_the_version`），再改位图，不另外抽样复核 GPU 的结果；两次不同的条目写明状态不确定，这一批不回收、不搬，留到下一轮重算。同一个条目连续 2 轮（N = 2）都不确定，交 CPU 那一份实现单独判一次，按 CPU 的判定处理；连续不确定的计数只放在内存里，重挂清零。「轮」按落点认条目：扫描里的校验和核对与区域扫描里的单元头解析与映射反查两段，一个条目是一个落点（盘、槽、跨度），选段打分一段，一个条目是一个聚簇段（盘、起点槽）；一个落点在一批里两份核的结果不同，它就不确定一轮，结果相同或已交 CPU 判过，它的计数清零；没出现在这一批里的落点，计数不动、也不清。一批放弃（GPU 出错、等超过上限）时，那一批里已经交回的段照算一轮，放弃的那一段计数不动。一批里同一个条目键出现两次（两份核比对之前整批查出），这一批作废，重复的那一段连续不确定的计数一条不动、也不交 CPU 那一份判；核心层收到一种不归哪张卡的出错（`SameEntryKeyTwiceInOneBatch`），后台任务不停、不报警，下一批照常算；那一批的意图照第 4 条一批出错放弃的规矩删（有活意图就单发一次只删意图的发布）。重复键在交卡之前就查，重复就这一段一片都不交给卡，所以同一批里卡出错与重复键不会同时出现；同一批里别的段已交回的照算一轮。重复键每一批都出现时照旧不停、不报警，也不在 CPU 上补跑。每一批报确认、不确定、交 CPU 判的条目各多少，运行时看得出来。只有一张卡时两份核都在这张卡上跑，有几张卡时按第 2 条分活、两份核可以分开跑；不许要求多张卡，一张与几张都要能跑、判定相同。

#### 已定项 3：判据取什么形式

**定案**：判据是 `CPU 16 线程耗时 ÷ (传输 + 计算 + 传回) 耗时`，小于 1 就否掉那一格。代进去的 CPU 侧数必须是**多核饱和吞吐**，不是「单核 × 核数」：线性外推与实测在 AES-GCM 上差近 4 倍（外推约 61 GB/s，实测饱和 17.4 GB/s）。GPU 侧的两个地板是**单程 56.69 GB/s**（锁页 H2D，≥64 MiB）与**来回 28.5 GB/s**（H2D + D2H，回传全部数据的场景走这一行）；CPU 侧的上限是**内存带宽墙 64.91 GB/s**。⇒ **GPU 只在「CPU 那侧的实际吞吐掉到传输地板以下」时才有机会。**

**射程**：⚠️ **「瓶颈是不是 CPU」不等价于「这个任务有没有硬件指令」**——有 AES-NI 的加密照样在 17.4 GB/s 就饱和，瓶颈仍然在 CPU 侧，**有硬件指令 ≠ 快到 GPU 追不上**。⚠️ **「CPU 够快所以 GPU 无用」这个前提在本工程不成立，不许拿它支撑任何结论**：它来自单核乘核数的线性外推，而多核实测饱和在 17.4 GB/s，差近 4 倍且方向相反——17.4 低于 GPU 的两个地板。代进去之后四个候选格各是什么：scrub（校验和 / MAC）有 AES-NI 时 CPU 侧多核饱和 17.4 GB/s（8 线程，16/32 线程 16.3/16.5；单核 3656.13 MiB/s）⇒ 按判据这一格 GPU 赢，⚠️ **两侧都没坐实，不许当已定结论用**（GPU 侧缺真的 AES-GCM 核函数）；无 AES-NI 的机器上单核 244.74 MiB/s ⇒ 16 核约 4.1 GB/s，与高端 NVMe 阵列同量级，这一档 GPU 可能有用，多核未测、饱和值只会更低；EC 重建无数据（Reed-Solomon over GF(2⁸)，重建要读全部幸存盘并算 parity，计算量随盘数 × 容量线性，这一格计算确实重）；批量压缩无数据（压缩比与吞吐的取舍，GPU 压缩库存在）。这两个数（17.4 与 244.74）来自 E6（加密算法选型），不是 D24（后台重活能不能卸给 GPU） 自己量的。⚠️ **不能读成「GPU 无用」**：计算段那一段的推论只对**带宽受限**的核函数成立，**压缩是算力受限的**，它的计算段可能远不止那一成，那一格仍然开着且仍要等 `nvcc`。⚠️ **还有一层压在上面**：三个候选场景全是盘限的后台活，盘带宽比 64.91 与 28.5 都低得多 ⇒ 整件事若是盘限的，CPU 本来就在空转，卸给 GPU 省不下任何东西——**这一层是推理不是实测**（本工程没有阵列）。⚠️ **一个未验的逃生口**：GPUDirect Storage 让 NVMe 直接 DMA 进显存、绕开主存与 PCIe 那一跳，**它会推翻「GPU 吃数据 56.69 GB/s」这个传输地板**，没测过，不许当它不存在。要定 D24（后台重活能不能卸给 GPU），先要量 EC 重建与批量压缩这两格的 CPU 上界，以及「PCIe 传输 + 核函数 + 传回」这条链路相对纯 CPU 的净收益——**数据要过一遍 PCIe，那笔搬运成本可能吃掉全部计算收益**。**本机可测**：NVIDIA RTX 5090（32 GB）+ RTX 5060 Ti（16 GB），驱动 595.84；`nvcc` 没有装（`command -v nvcc` 零命中，`/usr/local/cuda*/bin/nvcc` 也没有），那是 G24.3（计算段占比） 的前置。
