# C163 正推腿输出（Sonnet，第一轮）

## 0. 结论先行

枢纽问题的答案：**E81 的「轮」是纯内存迭代，不是写盘次数。它的计数模型里，
一个容器（树节点）在一次发布里最多贡献 1 个块——`meta_blocks` 就是"新脏节点数"，
不是"写操作数"。28 块是 28 个不同的节点，不含同一节点的多个版本。**
这个模型选择是显式写在源码注释里的，不是我推出来的：见下面第 1 节的行号引用。

推荐臂：**C**，判据在第 4 节。

## 1. 枢纽问题：E81 的"轮"是内存迭代还是写盘次数

### 1.1 源码证据

`research/e7-index-bench/src/bin/e81_commit_fixpoint.rs`：

- 第 141 行：`let mut dirty: Vec<Vec<bool>> = geo.levels.iter().map(|&n| vec![false; n as usize]).collect();`
  ——这个 `dirty` 数组在整个 `publish()` 函数调用期间（即一次 checkpoint 发布期间）只声明一次，
  **贯穿所有轮次，从不重置**。
- 第 178–190 行，每轮的核心逻辑：
  ```
  for &off in &pending {
      records_inserted += 1;
      let mut id = off / geo.leaf_cap;
      for level in dirty.iter_mut() {
          if !level[id as usize] {
              level[id as usize] = true;
              newly += 1;
          }
          id /= fanout;
      }
  }
  tree_dirty += newly;
  ```
  一个节点第一次被标记为 `true` 时才计入 `newly`；此后同一节点再被同一轮或后续轮的记录
  命中，`level[id]` 已经是 `true`，**不再计数，也不再产生新的 pending（不再分配新块）**。
- 第 210 行：`meta_blocks: tree_dirty + acc` ——每个发布周期的元数据块数，直接等于
  "本次发布中变脏的节点数"（加记账树固定的 2 个节点），**不是"轮数 × 每轮写的节点数"**，
  也不是"记录插入次数"。
- 源码头部注释第 18 行明写："**已脏节点本次发布只 COW 一次，再插新记录不再多付**"。
- 文件头注释第 49 行："『已脏节点再插不多付』假设发布末尾一次性 COW——若实现边插边 COW，
  放大更大，本模型给的是下界。"
- `.claude/kb/experiments/81-提交的固定点.md` 第 38–39 行原文："**该规则已定案
  （2026-09-02）：D3（空间分配）已定项 5**……模型给的是下界（假设发布末尾一次性 COW，
  已脏节点再插不多付；边插边 COW 的实现更贵）。"

### 1.2 这直接回答枢纽问题

E81 的计数模型里，"2 轮、28 块"中的**28 是 28 个不同的容器（树节点），每个恰好被计入一次**。
模型结构上不可能让同一个节点贡献 2 个块——`dirty[id]` 一旦置 true 就不会再触发
`blocks_allocated += 1`（第 193–204 行的 `pending` 只由 `newly`，即本轮新变脏的节点数生成）。

"轮"（`rounds`，第 170–205 行的 `while` 循环计数）衡量的是：**要发现全部被自指循环
传递波及的脏节点，需要迭代几趟**——这是一个纯粹的图遍历/传播深度概念，与"这个节点的块
被物理写出几次"是两个不同的量，模型里根本没有后者的计数器。

**这意味着 E81 自己的建模假设，就是背景材料里"四条臂"的臂 C**（"the fixed point
converges in memory and each container is written out at most once per checkpoint"）。
E81 不是在两种可能之间保持中立后来才被拿去支持某一臂——它从一开始就是按臂 C 的语义
建的模型，只是没有人把这一点显式挑出来对上 C163 的矛盾。

⚠️ 这也精确定位了矛盾的来源：D3（空间分配）已定项 5 的定案文本（`decisions/03-空间分配.md`
第 186 行）已经用大写警告写明"**E81 给的是下界（假设发布末尾一次性 COW），边插边 COW
的实现更贵**"——"更贵"这个词当时被理解为纯粹的性能账（多写几百倍的块）。但没有人在当时
指出："边插边 COW"这个被排除的替代实现方式，除了更贵之外，**还会让 I-1.8 描述的场景
（同一容器在一个 checkpoint 内被写出多个版本）成为现实**。C163 的矛盾本质上是：
I-1.8 / D18 已定项 7 是按"边插边 COW"这个已被 E81 隐式排除、且从未被正式判否的场景写的，
而 D3 已定项 5 采纳的却是"一次性 COW 到底"这个场景下量出的数字。两条已定条款各自假设了
不同的写盘模型，谁都没有把这个假设显式钉死。

链：见第 1.2 节——**E81 自己的模型就是按这个语义建的**，且 D3 已定项 5 已经采纳了

## 3. 重点评估臂 C

### 3.1 与 D3 已定项 5 相容吗

**相容，而且不只是相容——臂 C 是 D3 已定项 5 采纳的数字（2 轮、28 块）成立的必要条件，
不是可有可无的旁注。**

D3 已定项 5 的决策依据完全来自 E81 的计数模型，而 E81 的计数模型（第 1.1 节已证）
在结构上就是"一个节点在一次发布中最多贡献一个块"。如果实现违反臂 C——也就是采用
"边插边 COW"，某个节点在轮 1 因为部分记录到位而被写出一次，轮 2 又因为新记录追加
而不得不再写一次——那么：

1. D3 已定项 5 引用的"28 块"这个数字就不再是真实块分配数的准确值，而只是它的**下界**
   （这一点 E81 自己已经用大写警告写明，见 1.2 节引用）。真实块分配数会更高，
   因为同一逻辑节点可能贡献不止一个物理块。
2. 更关键的是：违反臂 C 恰好就是制造 I-1.8 想要防的那个场景——同一容器同一 checkpoint
   内出现多个物理写出的版本。

所以臂 C 与 D3 已定项 5 不是两件独立的事，是同一个建模假设的两种表述：
"发布末尾一次性 COW" = "每容器每 checkpoint 至多写一次"。D3 已定项 5 已经用户定案
采纳了前者的数字，等于已经默认了后者——只是没有人把这个默认显式写成一条决策条款或
一条检查。

### 3.2 会失败的检查该是什么形态

`.claude/kb/checks-owed.md` C83 的"仍欠"栏（第 94 行）原文已经写了一半："**仍欠：
实现后提交路径记「固定点收敛轮数」、超声明上界判红（政策不是格式位，违反只表现为
几百倍的性能悬崖，唯一拦法是这条读数）**"——但这只挡"轮数发散"（性能悬崖），
不挡"同一容器被物理写出多次"（C163 要的这一条）。两者是独立的读数，缺一不可。

提议的检查是对 C83 现有读数的补充，不是替代：

**在提交/发布路径的固定点实现里，维护两个计数器，在每次 checkpoint 发布结束时断言相等：**

```
distinct_dirty_containers  ——本次发布中"逻辑上变脏"的容器（树节点）去重后的数量
                              （对应 E81 模型里的 tree_dirty + acc）
physical_write_issued      ——本次发布中，对分配记录树 / 记账树发起的实际物理写 I/O 次数
断言：physical_write_issued == distinct_dirty_containers
```

若 `physical_write_issued > distinct_dirty_containers`，说明至少有一个容器在本次发布中
被物理写出了不止一次——这正是 I-1.8 那句"a container is not guaranteed to be written only
once per checkpoint"描述的场景真的发生了，此时应当**当场拒绝提交（panic / 返回硬错误）**，
不是记日志。

**这条检查必须先证明自己会红**（`show-me-test.md` 硬性要求）：构造一个"急切 COW"变异——
让某个节点在它第一次变脏的那一轮就立刻发起物理写，然后在后续轮次因为新记录追加而
被迫再次变更并再次物理写——用这个变异去跑上面的断言，必须观察到它变红。这个变异形态
与 E81 自己的变异表（`research/mutations/e81_commit_fixpoint.tsv`）里 M7（"没收敛也当收敛"）
的精神一致，但测的是一个新维度（写入次数而非收敛判定），需要单独建一张变异表，
不能复用 E81 现成的那张——E81 的计数模型里根本没有"物理写发起次数"这个量可供变异
（它只有 `blocks_allocated`，混合了"逻辑分配"与"物理写"两个在臂 C 下应该相等、
在违反臂 C 时会分道的概念）。

**类型层面的配套**（呼应 `.claude/singlefs-ai-sop/rules/machine-first.md` 的"用类型让非法
状态无法表示"）：把"逻辑上已确定的新版本，尚未物理落盘"与"已物理落盘的版本"做成两个
不同的 Rust 类型（例如 `PendingNode` vs `WrittenNode`），`PendingNode` 只能通过"固定点已
收敛"这一步转换成 `WrittenNode`，转换函数内部才允许调用物理写 I/O。这样"对同一逻辑节点
调用两次物理写"在类型层面就没有入口——除非显式地把已经是 `WrittenNode` 的东西降级回
`PendingNode` 再升级一次，而这种降级操作本身就可以在 review 里被一眼看见、并在测试里
被专门盯防。

### 3.3 与崩溃语义相容吗

**相容，且不需要新的崩溃处理分支——它精确落在"这个 checkpoint 没发布成功"这条已有的
恢复路径里，不是一个新场景。**

论证链：

1. D16 已定的语义（`decisions/16-发布语义.md` 第 3 行）是"攒够一批脏节点再发布一次根"；
   同文件第 27–28 行把中间态语义改写为"**根 + journal 任意前缀，replay 之后合法**"——
   合法状态的判据从来就是"根"这个终点，不是发布过程中任何一个中间时刻的内存状态。
2. 按背景材料条款 4 引用的推论、以及 `decisions/18-块里携带什么信息.md` 第 269–270 行
   的原文，固定点"**发布阶段内部的收敛、不产生新 journal 记录**"——也就是说，固定点
   迭代期间发生的一切（哪个节点在哪一轮变脏、变脏几次、最终内容是什么）在崩溃前都只存在
   于内存里，**journal 里没有任何记录指向这些中间状态**，因为 journal 记录本来就是
   "指针层的目标态"（D23 决策正文第 5–7 行），而"目标态"要到固定点收敛、内容确定之后
   才存在。
3. 因此，若崩溃发生在固定点收敛完成、物理写发起之前：内存里的一切丢失，但盘上什么都
   没变——上一个已发布的根仍然是唯一权威状态。这与"这个 checkpoint 从未开始过"在盘上
   是**同一种状态**，没有产生任何需要被恢复逻辑特殊处理的半成品。
4. 若崩溃发生在固定点已收敛、物理写已经发起一部分之后：按"分配先于 journal"的顺序
   （D23 决策正文第 9 行），这些已经物理写出的块此刻还没有任何 journal 记录或根指针指向
   它们——它们是孤儿块，不影响任何已发布状态的可读性，只是需要被将来的垃圾回收路径
   认出来（这是空间记账的问题，不是崩溃一致性的问题；`.claude/rules/fs-design.md`
   "记账是事务的副产品"一节把"后台、可续做、非决策路径"的空间回收单独归到"无戒律"一格，
   不在本任务射程内）。
5. 被抛弃的这次 checkpoint 尝试所积攒的用户事务（D16 batch 阶段已经写入 journal 的那些
   记录）不会丢失：按 D23 已定项 14（`decisions/23-journal的角色与格式.md` 第 674 行）
   "只施加 (实例代号, checkpoint_txg) 严格大于根的记录"，下次挂载会把这批 journal 记录
   重新施加、重新走一遍发布流程（包括重新算一遍固定点）——**这正是"那个 checkpoint 没
   发布成功"的标准处置，不是为臂 C 新开的路径**。

所以任务里问的"发布中途崩溃、内存里没写出的东西丢了，是不是正好等于『那个 checkpoint
没发布成功』"——是。而且这个等价关系不是臂 C 带来的新性质，是 D16 本来就有的
"根是递归终点"模型的直接推论；臂 C 只是恰好落在这条已有的安全线以内，没有在它之外
再造一个需要单独验证的新分支。

## 4. 推荐臂与可失败判据

**推荐臂 C。**

理由收束：

- 第 1 节已证：E81 的模型本来就是按臂 C 的语义建的，D3 已定项 5 采纳的数字建立在
  这个假设上——选臂 C 不是引入新约束，是把一个已经被事实上依赖、却从未被写成决策条款
  的假设显式钉死。
- 零格式代价（臂 A 要重开两条已定案条款的语义，臂 B 要在冻结的第 1 层挤字段）。
- 第 3.3 节已证：它不产生新的崩溃处理场景，落在 D16 已有的"根是递归终点"模型内。
- 相比臂 D：臂 D 需要正面回答"重建挑错版本会造成什么后果、现在有什么挡着"，而背景材料
  第 88–92 行已经指出 I-1.2 的已发布谓词**不会**把同 checkpoint 的中间版本过滤掉——
  它们全部进入候选集，此时若 I-1.8 的判别子失效，`.claude/kb/decisions/18-块里携带什么
  信息.md` 第 750 行 C113 定案的择新键规则会在"载荷相同即判损坏、不择"（I-1.8 原文）
  这条兜底之外，退化为**任选其一**当作现行版本——如果两个中间版本因为固定点收敛
  路径不同而实际内容不同（比如轮 1 的部分状态 vs 轮 2 的完整状态），选错一个就是
  静默读到一个逻辑上不完整的容器版本，且没有任何校验和会报警（两版各自的载荷校验和
