### 打中的是条款里的哪一句

`.claude/kb/decisions/03-空间分配.md:126` 整段里的这一句（整句抄）：

> 崩溃丢掉的是没发布的那个 checkpoint，它里面的释放一条都不留痕、对应的旧版本仍被所选根引用。

**甲下这句是真**：丢掉的那次发布里，中间版的记录与根一起没生效，中间版从来没被登记过，「对应的旧版本」（s1 的前一版）确实还被所选根引用着，账自洽。
**W1 / W2 / L1 下这句是假**：中间版的记录**活着**（它在重放前缀里、第 6 步刚被施加），而 s1 的「对应的旧版本」是谁？s1 自己就是间隔里新分配的、任何根都没引用过它。
⇒ s1 被登记成已分配、不被任何树引用、也永远进不了「已释放」，第一版没有整理（D3 已定项 7 合取 7：`N₀` 第一版取 0、整理未实现）也没有 fsck ⇒ **永久泄漏**。

### 量级（E155 第二次跑的产物数，整行抄自背景材料第四节）

> K9′ 下 wal_full 一个间隔（N=16）的中间版 60，分配记录树长到 `[5, 1]`（K9 下仍 `[1]`，402 条）；乙-M-K9′ 中间版 45、分配记录树 `[4, 1]`。

给出一条路径，让那条已释放的分配记录在**间隔里**就落盘，而不违反「分配记录是根下的 COW 树、条目与根同一次发布」（`03-空间分配.md:126`）。

## I3-B（打中）：`df` 少报的量比甲0 多多少——「发布」这个单位在 WAL 类下悄悄放大了 N 倍

界 3 与谓词都是拿**发布**当单位写的。两条原文（现查，整句抄）：

- `.claude/kb/decisions/03-空间分配.md:180`：
  > 2. **删掉的空间在有界步数内可用**：删掉一个 s 字节的对象之后，同样大小的写必须在有界步数内成功。这个界要写成算得出的数，不许是「最终会」。**界是 3 次改变用户可见状态的发布**：删掉的块被最近 4 个状态里更旧的 3 个钉着，要再发生 3 次这样的发布才回可分配集合；在那之前 `df` 不把它算空闲，写它按 `df` 是真 ENOSPC，第 1 条不破。文件系统自己推的空发布不算这 3 次（空发布不改用户可见状态）。
- `.claude/kb/decisions/16-发布语义.md:39`（表里那一行）：
  > | `df` | 没用过的 + 已释放的 + 活元数据 − 保留池 − 推空最坏残留 − 滞后量；保留池 = 2 × 5 + (B − 1) × c_max = 10 + 7 c_max，残留 = 5 + (B − 2) × c_max = 5 + 6 c_max；滞后量 = 释放代 > max(第 4 新的非空有效根, 环里最旧有效根) 且不是空发布放掉的已释放块 |

**按字面，界 3 在 W1 / L1 下仍然成立**——它数的是发布，不是 fsync，我不把这一条报成违反。
被打中的是**它旁边那个用户知情接受过的代价数**。`16-发布语义.md:52`（整句抄）：

> - **用户知情接受的代价三条**：删掉的空间要再发生 3 次改变用户可见状态的发布才回可分配集合，在那之前 `df` 不把它算空闲、按 `df` 写它是真 ENOSPC；`df` 少报 = 保留池 + 残留 = 15 + 13 c_max（c_max = 5 / 10 时 80 / 145 块）再加滞后量，而滞后量 = 4 × 最近四个窗口的释放量、**没有上界**（一窗删一个 8 块对象时平均约 34 块、最大 44 / 52，一窗删 32 个时 1044 块），删掉 s 字节 `df` 一个字节都不涨；c_max 按现算取，第一版池规模 9 块 ⇒ 保留池 73 块。

「最近四个窗口」的**窗口 = 一次发布**。甲下一次发布 = 一次 fsync；W1 / L1 下一次发布 = 一个 checkpoint 间隔 = N 次 fsync。

## I4-B（打中）：树表 0 条那道拒绝，在 L1 下把窗口从「一次发布」撑成「一整个间隔」

`crates/singlefs-core/src/mount.rs:803-804` 的注释（整句抄）：

> /// 所选根的树表 0 条而这次要写的行区间 [max(所选根的实例, 1), 要取的号) 不为空：在取号之前拒绝（写行要重写实例表，没有文件版本的一版上
> /// 它的落点记在哪没有条款）。不靠坏盘就走得到：第一个事务暖机之后、第一个文件版本之前崩溃，重开时所选根 (1, 2)、要写 (1, 2, 0)。

甲下这个窗口只有「第一个文件版本那一次发布」那么宽，而且窗口里没有任何已向用户返回的 fsync。
**L1 下这个窗口就是第一个 checkpoint 间隔的全长**：树表是四样固定点之一、L1 把它延到 checkpoint，
所以从第一个文件被 fsync 起，一直到第一次 checkpoint 为止，盘上所选根的树表恒 0 条，而这中间每一次 fsync 都已经返回给用户了。

可达历史：mkfs → 第一次可写挂载（实例 1，写行零单元 txg 1、暖机 txg 2，树表 0 条）→ 用户建文件并做 N 次 L1 形态的 fsync（不发根、树表不落盘）→ 崩 →
重挂载：所选根 (1, 2)、`rebuild_previous_version`（`mount.rs:224`）交回 `PreviousVersion::WithoutFile` ⇒
`refuse_instance_rows_on_version_without_file`（`mount.rs:805`）判 `first_row_instance = 1 < instance_to_acquire = 2` ⇒
**`MountError::InstanceRowsOnVersionWithoutFileUnsupported`，一个字节都不写，池挂不上可写**，那 N 次已确认的 fsync 留在环里谁都够不着。

回退那条路上同一件事再出一次。`mount.rs:1236-1238`（整句抄）：

> // 回退到树表 0 条的根（例如第一个事务里 txg 1、2 的暖机根）：走到这里它已经在回退候选集里，但回退行要重写实例表，没有文件版本的一版上
> // 它的落点记在哪、换下的 mkfs 实例表与候选根引用的单元谁护着都没有条款（D16（发布语义） 已定项 9 只定了树表 0 条时空发布写零个单元）——
> // 在任何写之前拒绝，报「第一版不支持」，不报候选排除。

⇒ `mount.rs:1240` `MountError::RollbackToVersionWithoutFileUnsupported`。L1 下这些树表 0 条的根在回退候选集里的占比按 N 放大。

## I4-C（没打中，但要记一笔）：取号之前那道准入算的是两个常量形状，L1 下它算的不是要发的那次

                plan.shape(),
                PublishShape::EMPTY_PUBLISH,
                "暖机这次空发布的形状与取号之前算准入用的那一个相同（不写文件版本、实例表照抄）"

> **定案**：预留 = (N_switch + 1) × 一次切换的最坏量，按设备算；一次切换的最坏量 = 实例表链重写 + 暖机空发布。

这个式子里**没有任何一项对应「重放出来的那批叶的祖先」**。L1 要接上，这条已定项要加第三项，而那一项的上界是 N（间隔长度），
也就是第三节那个不受任何条款约束的量。

# 三、I7：周期取大取小在 WAL 类形态下各付什么

## 3.1 式子

记 `P` = 周期（秒，= 本次挂载生效的 `T_time`）、`λ` = fsync 到达率（fsync/秒）、`d` = 每次 fsync 的脏叶数、`R(d)` = 每次 fsync 写出的记录条数。

**一次 checkpoint 的最坏 journal 占用**

```
J(P, λ, d) = λ · P · R(d) · 4096 字节
```

三个因子各自的依据：

| 因子 | 取值与出处 |
|---|---|
| `λ · P` | 一个间隔里的 fsync 次数。间隔的上界是 `T_time`：`.claude/kb/decisions/16-发布语义.md:121`「**`T_time` 用户可设，不限制**：挂载时传的值覆盖盘上的字段并回写；超出 [200 ms, 5 s] 不拒绝，只给警告（用户 2026-09-20）」 |
| `R(d)` | `.claude/kb/decisions/16-发布语义.md:130`「按六个负载点算，每次 fsync 的记录数等于数据单元数（seq 批 1 是 8 条、批 10 是 80 条）」⇒ 主负载 seq 批 1 取 `R = 8`。脏叶数 `d = 8`（`.claude/kb/decisions/25-目标负载优先级.md:20`「一次 fsync 带 8 个叶子，落在 1 条共享脊柱上」），两者在 seq 这一档同值 |
| `4096` | `.claude/kb/decisions/16-发布语义.md:130` 那一句里的「4 KiB 定长记录」，实现侧 `crates/singlefs-format/src/lib.rs:139` 的 `JOURNAL_RECORD_BYTES: u64 = 4096` |
| 为什么整个间隔都得留在环里 | `.claude/kb/decisions/16-发布语义.md:169`「**系统配置槽在根槽持久之后再更新，每个 checkpoint 一次**，它是发布序列的最后一步」——tail 住系统配置槽 ⇒ WAL 类形态下 tail 每个间隔只推进一次 ⇒ 间隔里的记录一条也放不掉 |

**甲0 / 甲B 的同一式子**：甲每次 fsync 发一次根、系统配置槽每次发布都更新 ⇒ `P = 1/λ` ⇒ `J = R·4096 = 32 KiB`，与 `λ`、`P` 都无关。

## 3.2 与 D23 已定项 23 / I-8.1 能不能同真：**不能，而且今天的条款根本没在管它**

两条原文已抄在报告开头（`23-journal的角色与格式.md:534` 的「任一操作」、`invariants.md:76` 的「任一事务」）。
**第一个结论是口径上的**：这两条的主语是「操作 / 事务」。甲下一次 fsync = 一个事务组 = 一次发布 = 一个 checkpoint，四者同外延，所以这两条顺带也罩住了 checkpoint。
WAL 类形态下一个 checkpoint 跨 `λ·P` 个事务，**这两条一条都罩不住间隔**——它们只要求单个事务装得进 `环÷F`，而单个事务在 W1 / L1 下只有一条记录。
⇒ 要让 WAL 类形态成立，得**新加**一条不变量（形如「一个 checkpoint 间隔的最坏 journal 占用 ≤ 环大小 ÷ F」），今天的 I-8 类里没有。

**第二个结论是数上的**：就算把这条新不变量按材料第二节的转述加上去，默认参数下它直接不成立（模型 I7 表 1，原样输出）：

```
## I7 表 1：一个 checkpoint 间隔的 journal 占用 vs 环÷F（环 768 MiB）
  周期 s | WAL 类间隔占用 MiB | 甲一次发布占用 KiB | 环÷F=2 MiB | 环÷F=3 MiB | F=2 过不过 | F=3 过不过
  0.2 | 17.41 | 32.0 | 384.0 | 256.0 | 过 | 过
  1.0 | 87.03 | 32.0 | 384.0 | 256.0 | 过 | 过
  2.941 | 255.96 | 32.0 | 384.0 | 256.0 | 过 | 过
  4.412 | 383.98 | 32.0 | 384.0 | 256.0 | 过 | 不过
  5.0 | 435.16 | 32.0 | 384.0 | 256.0 | 不过 | 不过
  30.0 | 2610.94 | 32.0 | 384.0 | 256.0 | 不过 | 不过
  300.0 | 26109.38 | 32.0 | 384.0 | 256.0 | 不过 | 不过
```

`λ = 2785` 取自 `.claude/kb/decisions/16-发布语义.md:138`「本机 2785 fsync/秒」（E44 本机实测）；
环 768 MiB 与 F 的取法取自 `16-发布语义.md:121`（默认环 768 MiB，默认有效 `T_dirty` 256 MiB ⇒ 那一句用的 `F` 是 3）。

⇒ **`T_time` 取它自己的默认值 5 s，WAL 类形态在本机实测的 fsync 速率上就已经越界**：F = 3 时在 2.94 s 越界，F = 2 时在 4.41 s 越界。
换句话说，WAL 类形态下**周期的可用上端不是 `T_time` 的默认值 5 s，是 2.9 s**——而 `T_time` 那条已定项明写「用户可设，不限制，越界只给警告」。

## 3.3 与 `T_dirty` 夹取能不能同真：**夹取那一支在 WAL 类形态下不触发**

`.claude/kb/decisions/16-发布语义.md:132`（整句抄）：

> - **`T_dirty` 与 `T_time` 是两种规则**：`T_dirty` 走夹取——有效值 = min(字段, 环长 ÷ F)，不动；`T_time` 走警告——越界不拒绝，只给警告。同一段里两个字段两种规则，不按同一规则读。

夹取那一支之所以能替环账兜底，靠的是同一句里这半句（`16-发布语义.md:121`，整句抄）：

> 所以「环装不装得下 `F ×` 最坏占用」不由一条 mkfs 时的下界保证，改成挂载时把脏字节预算压下去

**这一步只在甲下成立**：甲的脏字节要等到 checkpoint 才落盘，压住脏字节就压住了这一轮要写的量、也就压住了记录条数。
`T_dirty` 的定义是量纲上的内存量——同一句里写着（`16-发布语义.md:121`，整句抄）「`T_dirty` 管的是**量**，它就是脏页内存预算本身」。
而 W1 与 L1 的臂定义第一句都是「每次 fsync **写**脏数据单元、脏叶」：这些字节在 fsync 返回那一刻**已经在盘上**，不是脏页。
⇒ **W1 / L1 下脏页量 ≈ 0（L1 只剩内存里的祖先），夹取那一支永不触发，间隔只由 `T_time` 收**（模型 I7 表 3 的「读法 A 触发时刻 s: None」）。

就算退一步、按对 WAL 最有利的读法 B（`T_dirty` 改数「这个间隔里写出去、还没被根罩住的用户数据字节」），得到的是另一个坏结果（模型 I7 表 3 原样输出）：

```
## I7 表 3：T_dirty 夹取那一支什么时候先触发
  有效 T_dirty MiB: 256.0
  读法 A 触发时刻 s: None
  读法 B 触发时刻 s: 0.3677
  读法 B 下的间隔 journal 占用 MiB: 32.0
```

⇒ 读法 B 下环账过了，但**间隔被夹到 0.368 秒**。用户 2026-09-20 要的「这个频率应该可以配置」在这一读法下只剩
「配 0.368 秒以下才有效，往上调一个字节都不生效」——配置那一半在 WAL 类形态下**买不到周期**。

**两个读法都不能与另外两条同真**：读法 A 下夹取不触发、环账在默认 `T_time` 上就破；读法 B 下环账过了、但 `T_time` 可配置这条已定项变成空文。

## 3.4 哪一条要先收严（判据 I7 要求写清）

按最弱读法，要先收严的是**一条，不是三条**：

**`T_time` 的「用户可设，不限制，越界只给警告」（`16-发布语义.md:121`，2026-09-20 用户定案）在 WAL 类形态下必须改成夹取**，
有效周期 = min(字段, (环大小 ÷ F) ÷ (λ · R · 4096))。代价是这个夹取的分母里有 `λ`（运行时才知道的到达率），
而 `T_dirty` 的夹取分母全是 mkfs 参数——**新夹取是个运行时量，挂载时算不出来**，只能做成「journal 占用到 环÷F 就强制 checkpoint」的第三条触发条件，
也就是给 `∨` 规则（`T_time ∨ T_dirty`）加第三支。加这一支就等于承认：**WAL 类形态下周期不是用户能配的，是环几何说了算的。**

次一条：D23 已定项 23 死锁 3 与 I-8.1 的主语要从「任一事务 / 任一操作」改成「任一 checkpoint 间隔」，否则死锁 3 在 WAL 类形态下无人把守。
这一改牵连 `invariants.md:76` 那条口径注（ckpt_cost 挂载期内会长）与 C28（环几何不变量未实现）。

甲0 / 甲B 不受这一节任何一条影响：甲的间隔恒为一次发布，`J = 32 KiB`，`λ`、`P` 怎么变都罩得住。
