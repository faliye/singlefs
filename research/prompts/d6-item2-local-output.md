Q1. Yes, candidate B can leak space and violate fact 7. Scenario: transaction group 1 creates an origin snapshot. Transaction group 2 creates a writable head from the origin. Transaction group 3 allocates a block with birth transaction group 3. Destroying the writable head begins: the process reads the root block, requiring allocation of a 4KB buffer for the block data. Immediately after this allocation, a crash occurs. The 4KB buffer is leaked (space leak), the block with birth 3 remains allocated (space leak), and fact 7 is violated because releasing space required allocating space for the buffer.

Q2. For candidate B to be resumable, the resume progress must be persisted in a persistent structure (e.g., a metadata area storing the current traversal state). Scenario: transaction group 1 creates an origin snapshot. Transaction group 2 creates a writable head. Transaction group 3 allocates block X with birth 3. Destroying the head begins: block X is freed, but before persisting the resume state (e.g., "X freed, next to free block Y"), a crash occurs. On restart, the system reprocesses from the beginning and frees block X again (double-free), corrupting the space map. Thus, resume progress must be persisted, and this requirement means candidate B also needs a persistent structure for resume state, differing from candidate A only in the shape of the structure (livelist vs. resume state metadata), not in whether a persistent structure exists.
