ITEM 1 OBJECTION:
The mechanism judges a candidate root's blocks as reused or erased solely by whether the I-2.1 violation count or walk_failures length increases during that root's walk using the shared visited_units cache. But I-2.1 already checks all checksum mismatches for any reason, including bit rot or read errors unrelated to reallocation. This approach simply repackages I-2.1 results with a causal label that isn't verifiable. Additionally, since visited_units is shared across all root walks without reset, if an older root shares an ancestor node with the newest root or another candidate root, the traversal skips reprocessing that node. This could miss blocks only reachable through the older root's unique path because the shared cache prevents re-descent into subtrees that weren't visited during the newest root's walk, leading to undetected violations.

ITEM 1 DEFENSE:
Yes, the mechanism holds up. The delta in I-2.1 violations and walk_failures during a specific root's walk directly captures new checksum mismatches or unreadable blocks encountered while traversing that root's unique reference chain. The shared visited_units cache is essential for avoiding infinite loops and redundant checks in a static disk image. Since the image doesn't change during the checker run, any node already processed by an earlier walk has a known state. If a node was valid during the newest root's walk, it remains valid for subsequent roots. If a node was reallocated or erased, the checksum mismatch would have been caught during the first traversal of that node (e.g., by the newest root or an earlier candidate root), so the delta for later roots wouldn't increase. The shared cache ensures each node is checked exactly once, which is correct for a static image. The mechanism correctly identifies new issues during a root's walk, and the cache behavior is intentional and necessary for correctness.

ITEM 1 REFUTING OBSERVATION:
If a block referenced only by an older root has identical data to a reallocated block from another object (causing a checksum collision), the checksum match would not trigger a violation. The shared visited_units cache would process this block during the older root's walk (since the newest root didn't reference it), but the checksum match would pass I-2.1, so the violation count wouldn't increase. The mechanism would fail to detect the reallocation, proving the objection right. This scenario would occur in a test image where the oldest root references a block overwritten with the same data as a different object, but the checksum matches.
