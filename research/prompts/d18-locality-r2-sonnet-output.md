## 一、问题 1：判决 2 复核——甲的跑前条款前件「前提五的理由今天仍然成立」怎么读

### D9 排除逐字写的理由是什么

`.claude/kb/decisions/09-加密.md:553`（「一定不能进 AAD 的」表，locality_id 那一行）整行：

这是表面理由：D8 已定项 3 说 locality_id「可以是错的」，所以不能承重（不能当 AAD 的输入，因为 AAD 失配 = 身份错配，见 I-6.9）。

但这句表面理由要落地，得挂在 D9 已定项 6 更深一层的机制判据上——`.claude/kb/decisions/09-加密.md:568-569` 整段：

> **AAD 每个字段的期望值只许来自 ① 读者的查找路径，或 ② 已被上一级 MAC 认证的密文侧字段。
> 一律不许来自明文侧，也不许从指针里读回来。**

正推腿（round 1）在「问题 1」一节把这句消歧成「前提三管存在性/结构确定性，前提五管内容可信度」，这个二分我核过，成立（`.claude/kb/decisions/08-核心索引结构.md:208` 与 `.claude/kb/decisions/09-加密.md:553` 原文确实是两个不同的轴，我不推翻这一点）。但"不冲突"是一回事，"今天仍然成立、足以让甲出局"是另一回事——中间还差一步：**locality_id 的『可以是错的』这条性质，会不会在『甲已经把它塞进 AAD』这个新状态下，真的产生一次合法却被系统误判的 AAD 失配？** 这一步是经验/机制问题，不是文本消歧能回答的，而攻方腿（Opus）的模型恰恰是在这一步上给出了正面的、可复跑的证据（阳性对照 B：不重写就重新聚簇，MAC 败 2 次；`research/prompts/d18-locality-r1-opus-output.md` 第 175 行「手造 B 阳性对照：2 次」）。

### 「后台重新聚簇」全仓有没有定义、它重不重编 key

**全仓没有操作性定义。** 现查（本轮，非背景材料转述）：

```
$ grep -n "重新聚簇" .claude/kb/decisions/08-核心索引结构.md .claude/kb/decisions/26-后台整理与放置回收.md
08-核心索引结构.md:137:- 退化由 D3（空间分配） 已承诺的常驻后台整理修复，不是新增负担
08-核心索引结构.md:198:3. **后台重新聚簇必须是增量、可中断、可续做的**，且随时可以停掉不做。
```

D8 已定项 3 只在 198 行给了一句**约束**（增量/可中断/可续做/随时可停），没有一处给出**它具体做什么**——是重写 extent key 首段（改变逻辑排序），还是只搬物理位置（D26 的整理机制），还是两者都做。D26（后台整理与放置回收） 已定项 4（`.claude/kb/decisions/26-后台整理与放置回收.md:213`）逐字「格式部分——不在节点头存组身份、不动索引节点内部布局；放置的组只从 key 算（key 区间分组）」，而 D26 的搬迁本身是「走映射、不改引用者」（`.claude/kb/decisions/26-后台整理与放置回收.md:218` 附近的「结构抗老化不进格式」小节标题下，及第二节里 Opus 已引「26-后台整理与放置回收.md:218」为长行指路）——这条搬迁只挪物理落点，不碰 key，所以**它不是「后台重新聚簇」的候选实现**：D8 已定项 3 把「按 locality 排序的遍历局部性」列为收益来源（前提四），而遍历局部性是 B 树按 key 序扫描的性质，只搬物理位置不改 key 不可能恢复它。

⇒ 这给出一个**推理**（非已定，我标出）：「后台重新聚簇」若要真的买到它名字里承诺的东西（恢复因改名而退化的 key 序局部性），机制上**几乎必须**触及 extent key 首段本身，即某种形式的重编。但它是否连带重写受影响的数据单元本体（从而让甲的 AAD 副本保持同步），全仓一个字都没说——这正是它「全仓没有定义」的确切含义：不是「有没有这个动作」没定义，是「这个动作的具体形状」没定义。

### 没有这个动作时甲还剩什么代价

若把「后台重新聚簇」整个从范围里摘掉（假设第一版根本不实现它，这个动作对本轮判据不生效），甲仍然要付：

1. **格式代价**：单元头 134 → 142（+8，`.claude/kb/decisions/18-块里携带什么信息.md:150` 现查今天码 1 头是 134），AAD 规范编码 33 → 41（六字段），第一个事务两盘各 +8（`.claude/kb/layout/01-first-txn.md:245` 一带的偏移表要整体后移）。
2. **永久契约代价**：AAD 字段集合是 day-1 永久契约（前提二逐字「这一组同时是 D9（加密） 已定项 6 的 AAD 字段集……动它是一次永久契约变更」），甲要把这条契约在**取值规则还没写**的时候冻进第 1 层——`.claude/kb/decisions/08-核心索引结构.md:209` 整行「⚠️ 连带：第一版没有目录，而这个值按本项从父目录继承 ⇒ **没有父目录时取什么，也要一起定**。」——继承的是父目录的哪个字段也没写（`grep -n "从父目录继承" 08-核心索引结构.md` 只命中 132、209 两行，都没给出具体取值算法）。这是把一个未完工的字段永久冻结，风险不随「后台重新聚簇」存不存在而消失。
3. **U3 泄漏**：与乙′同一档（新增「对象语义类别」这一类泄漏，详见第三节问题 3 与第四节）。

⇒ 我的判断：**即使假设「后台重新聚簇」永远不实现（第 3 种读法，见下），甲仍然背着 1、2、3 三项代价**，这些代价本身不足以让甲在 U2 出局（它们是「贵」，不是「撞已定条款」）。真正让 U2 判据可能触发的，只有「后台重新聚簇 = 重编 key 且不必然重写单元」这一具体读法。而这个读法今天既不能证实也不能证伪（无操作性定义）。

### 我的复核结论

正推腿的判法（「前提五的理由今天仍然成立 ⇒ 甲按条款出局」，无条件）**读得太松**：它把「不冲突」直接当成「理由今天仍然成立」，跳过了「有没有一个真实存在的、合法的、不重写单元的改值路径」这一步经验问题。攻方腿的判法（条件式，「后台重新聚簇 = 重编 key」这个前件未定义）**更贴合证据**，但我认为可以走得更远：**这不是「甲出局的条件不满足所以甲暂时不出局」，而是「甲出局与否本身就系于一个尚未做出的格式决策，而那个决策不管往哪边走都会伤到甲**：

- 若「后台重新聚簇」定义为**必须连带重写受影响单元**（S4 类的收严——注意这是我在第三节要点名要求乙′/甲都需要的一种收严）：甲不再撞 MAC 失配，但要付攻方腿模型量出的重写代价（`research/prompts/d18-locality-r1-opus-output.md` 手造 A：2 个单元强制重写、2 个被拆开的克隆共享），且代价「随数据量涨，不随 extent 数涨」（同报告第 210 行）——这是一笔开放式的、无上界的运行时代价，还额外撞克隆共享（把 origin 与克隆头本共享的单元拆开重写）。
- 若定义为**只重编 key、不连带重写**（最省事的实现）：甲面对合法却被系统当成攻击的 MAC 失配（阳性对照 B：2 次），这正是 I-6.9（`.claude/kb/invariants.md:199`）要挡的那类误判——I-6.9 逐字「加密开启且密钥在场时，任一被引用的块，若**密文校验和通过而 MAC 失配**，判红并归类为「身份错配」——**不许归类为介质损坏，不许触发副本修复或投毒**」——甲会让这条不变量在**正常操作**（合法重新聚簇之后没赶上重写的旧单元）下频繁触发，而 I-6.9 本身要求「不许归类为损坏」，等于把一批合法陈旧单元永久钉在「身份错配」这个不上不下的状态里，没有出路。

⇒ **我的复核结论：判决 2 应该改写，不是简单地在「Sonnet 无条件出局」和「Opus 条件式出局」之间选一个，而是给出第三个、更强的结论——甲在两种可能的「后台重新聚簇」定义下都要付出真实代价，没有一种定义能让甲免费。** 这本身构成一条比原判决 2 更硬的理由：**甲不该等「后台重新聚簇」定义清楚才判，因为不管往哪边定义，甲都要么付无界重写代价、要么制造永久性的误判死结。** 这条结论我会在第四节甲的正面论证里再展开一次，并配一条会红的检查。
## 二、问题 2：判决 4 复核——前提六作废的范围

### 失败条款的字面

背景材料第五节逐字：「**失败条款**：前提表一至十六的转述与附录原文对不上 ⇒ **这一轮的前提作废**。」这句話字面上是「这一轮的前提」（没有限定词），可以读成「全部十六条前提一起作废」，也可以读成「（触发的那一条）前提作废」。第一轮判决 4 按更窄的口径处理：「本地腿、正推腿在 U3 泄漏那一格作废，第二轮改正前提六重判」——只废了**依赖前提六错误读法得出的那两格结论**，不是前提六本身，更不是全部十六条。

### 我的复核：窄口径是对的，理由不靠"先例"，靠这条失败条款本身要防的是什么

先说我核过的事实：前提六错在哪。攻方腿（round 1）指出 `.claude/kb/decisions/14-双轨大小文件-持久临时.md:291` 整行「② **加密开启时它新增第一处「用户对象语义类别」的泄漏**——D18（块里携带什么信息） 已定项 14 那一轮列的」，这句的主语「它」按同文件上下文指的是同页 280–281 行那条被判掉的**分配器提示候选**（按 locality 聚簇），不是 locality_id 字段本身；前提表把这句的主语挪到了字段上。我现查确认这处主语确实容易读岔（该行单独摘出来时代词「它」找不到先行词）。

但同一文件里还有一段**没有代词歧义、可以独立支撑同一个结论**的原文，`.claude/kb/decisions/14-双轨大小文件-持久临时.md:295-297` 整段：

> ⚠️ 而 `locality_id` 至今**没有**盘上的明文表达（D18（块里携带什么信息） 已定项 3 的自描述头五元组不含它，
> 加它的提议 2026-09-03 起待用户定案且逐字「动它是一次永久契约变更」）
> ⇒ 按 locality 聚簇等于不加那个字段就把同一个信号搬进物理排布。

这段的逻辑是：locality_id 今天没有任何盘上明文表达 ⇒ 「按 locality 聚簇」这条候选相当于**间接地**把这个信号写上盘（不用显式加字段，靠物理排布就泄漏了同一类信息）。反过来读：**如果直接加字段（甲/乙′），那就是比"按 locality 聚簇"更直接的同一类泄漏**——这个推论不依赖 291 行那句有歧义的话，只依赖 295-297 这段无歧义的话。也就是说：**判决 2 所说"本地腿、正推腿在 U3 泄漏那一格"这个结论，就算把前提六的错误读法完全剔除，仍然可以从同一份来源文件里另一处正确无误的文本重新推出来**——它不是"建在沙子上"，只是"引用的门牌号写错了"。

### 为什么不该整轮作废

三条理由：

1. **失败条款检查的对象是逐条前提**，不是整份材料的一次性表决。第一轮两条腿（正推与攻方）各自逐条核对了前提一到十六，我在本轮开工前也逐条核对过附录与前提表（见第〇节，未展开是因为与两条腿一致，此处不重复贴）——十六条里**只有前提六的主语被换了、前提一漏引已定项 13（攻方腿指出，不算"对不上"，是"没写全"）**，其余十四条逐字命中附录。如果字面上"一条错⇒全部作废"，那么这份失败条款在任何一轮长度的材料里都会**近乎必然触发**（十六条转述里出一个代词歧义的概率不低），触发之后又不区分对错地把没问题的十四条一起判死——这样的判据丧失了区分能力，等价于`.claude/singlefs-ai-sop/rules/evidence-discipline.md`「判别子观测不到」那一类失效判据：它对"材料整体有没有转述错"这件事给不出有信息量的答案，因为它几乎总是为真。

2. **`.claude/singlefs-ai-sop/rules/evidence-discipline.md`「新立一条判据，当场拿它回扫已有的条目」的反面同样适用**：这条失败条款要防的是"一个被曲解的前提，悄悄支撑了一个本不成立的结论"。它的正确射程是"结论 ← 依赖 ← 被曲解的那句话"这条链，不是"结论所在的那份材料"。把射程扩大到"整份材料"，防住的东西不多（因为其余十四条前提本来就没有问题，不会真的支撑出错误结论），但代价是把两条腿花了工夫、且经过主 agent 现查坐实的**正确**结论（例如正推腿对丙在 U1 下不构成正确性失败的完整论证、攻方腿对丙收严读法零失败的模型复跑结果）全部作废重来——这是拿一个代词歧义的成本，换一整轮已验证工作的报废，不成比例。

3. **判决 4 本身已经预留了"重判"这一步**（"第二轮改正前提六重判"），意味着主 agent 当时也认为前提六的错误不足以让结论必然错，只是需要按正确读法重新走一遍——这与我现在做的事（用 295-297 重新推导，得到同一个结论）是同一件事的完成。如果当初真认为要整轮作废，判决 4 就不会写"重判"而会写"整轮重跑"。

### 复核结论：不推翻判决 4 的范围限定，但把"重判"这一步做完并收紧一处

我**维持**判决 4 对前提六错误的**处置范围**（只废依赖它的那两格，不废整轮），但补上判决 4 自己留下的尾巴——"重判"的结果：**按 295-297 重新推导，U3 泄漏那一格的结论不变**（甲/乙′都新增"对象语义类别"这一类此前没有先例的泄漏），应当**原样恢复**，不需要留空等第三轮。

同时我要指出一处判决 4 没有覆盖到、但同样属于"前提转述"范畴的遗留问题：前提七的出处误标（`.claude/kb/decisions/15-格式冻结政策.md:62` 只有"第 3 层：各 keyspace 的 key 编码"这半句，"今天一层都没冻"那半句实际在 `.claude/kb/decisions/14-双轨大小文件-持久临时.md:283`）——正推腿已经现查确认**内容本身成立**（D15 全文确实没有任何一处宣称某层已冻结），只是来源标注挪错了文件。这处误标比前提六更轻（不涉及主语指代，只是引用挪错了地方），round 1 判决 4 已经"照实记"但没有要求任何重判——我核过这个处理是对的：这处误标从未被用来支撑任何一格 U1–U4 的判定（它只是给"冻结分层第 3 层含 locality_id"这个背景事实提供出处），不构成第 4 类判决需要处理的对象。
## 三、问题 3：丙′「幸存 extent key > inode 记录 > 0」与乙′「幸存 key > 记录 > 头提示 > 0」

三个场景逐个过：克隆、D27 打包容器、加密开启时的重建。

### 3.1 克隆

D8（核心索引结构） 已定项 6，`.claude/kb/decisions/08-核心索引结构.md:386` 整行：

> 克隆头：新头的水位 = origin 那一刻的运行时水位（含还在 write buffer 里没落盘的那条），建克隆那次发布必须为新树写出这条水位行；两个头此后各自分配，号会相交，唯一性靠 (树 ID, inode)。

丙′的 S2 collar（「对象按 (树 ID, inode) 认、只看本头的 extent 树」）与这句的唯一性范围逐字相符——克隆之后两个头会分配出相同的 inode 号，唯一性只在加了树 ID 之后才成立，S2 把"对象"的识别单位收紧到 (树 ID, inode)，正是这句话要求的最小识别单位。round 1 攻方腿的"打中 2"（`d18-locality-r1-opus-output.md:114`，最弱读法"这个对象"按 inode 号单独认，两个头各建一个同号对象时取错首段）已经用 S2 堵上：`bing_inode_only` 在有 S2 之后退化成 `bing`，round 1 复跑数据里 `bing keys_first` 在 `rekey_on`/`rekey_off`/`v1_all_zero` 三个世界深度 6/6/7 全 0（`d18-locality-r1-opus-output.md:67-90` 那批 row 行）。**我核过这一点在 round 1 已经坐实，round 2 沿用不需要重跑。**

但 S2 本身有一个**没有解决、也不打算解决**的上游缺口：`.claude/kb/decisions/08-核心索引结构.md:424` 整句：

> **射程是单头镜像**：有克隆头时共享叶头里的出生树是 origin（I-1.3（块头树 ID 一致） 的 C110（跨头共享与加密后元数据类的块头一致性读法） 那一格），按出生树认领会把克隆头的树认残——多头镜像的归属划分要克隆祖先表（E90（树 ID 进 AAD 与跨头共享） 第二笔），落地前多头镜像的 inode 树重建没有输入。

即：S2 假设"这个数据单元属于哪棵树"这个更上游的问题**已经解决**（本头 extent 树能正确圈定属于自己的对象），而这个假设在多头共享的镜像上今天不成立（克隆祖先表没有落地）。正推腿 round 1 已经指出这一点对三条臂**平局**（`d18-locality-r1-sonnet-output.md:34-40`）——三条臂谁都没有解决"单元该记进哪棵树"，这个缺口不因加不加 locality_id 而改变。**我复核这个判断成立，且它同样适用于乙′**：乙′的重建次序同样需要先圈定"这个对象"（S2）才能去问"幸存的 extent key 是什么"，上游缺口对乙′一样存在、一样不由这次决策解决。

⇒ **克隆场景下的结论**：丙′、乙′的次序在**已知树归属**这个前提下都成立（S2 收严过的读法零失败）；两者都不解决、也不需要解决"归哪棵树"这个上游问题——那是 D8 已定项 6 自己标出来的、独立于本决策的缺口（落点仍是 E90（树 ID 进 AAD 与跨头共享） 第二笔与克隆祖先表，不在本轮射程内）。

### 3.2 D27 打包容器（≤4 KiB 对象）

前提十五：`.claude/kb/decisions/27-小数据打包容器.md:281` 整行「- **解引用不需要新 pointer**：槽自带逻辑身份五元组（D1（数据可移动性 / 反向索引） 已定项 5 要求自包不可变数据带唯一一条指向），」；`.claude/kb/decisions/19-块指针的结构与宽度预算.md:173` 整行「- 类标签取被命名对象在 D18（块里携带什么信息） 已定项 11 登记表里的码，D27（小数据打包容器） 槽里的对象恒为码 1；打包与整容器重写时，槽里 key 的各段逐字节取打包前那一版单元头里的值（⑩㈠）。」——这两句只覆盖"五元组"，**没有把 locality_id（无论甲还是乙′的形态）算进"槽里 key 的各段"**。如果甲/乙′采纳而不同步改这两处，一旦对象被打包，locality_id 这个字段会随打包**静默消失**（槽格式不携带它），该对象退化成丙′行为（0 提示）而没有任何地方记录这一点——这正是`.claude/rules/fs-design.md`「不是单元的盘上空间，核心层对它零覆盖」一节要挡的那类"静默丢失"。

⇒ **这是甲、乙′都要付的一笔格式代价**：D27 槽格式必须同步扩 8 字节，逐字节取打包前单元头里的 locality_id 值（与五元组的取法完全同构，属于同一条已有机制的直接延伸，不是新发明）。**加了这一笔之后，乙′的次序在打包场景下不产生新问题**——打包后的槽里那份提示与打包前单元头里那份是同一个值（COW 语义下静态复制），对"幸存 key > 记录 > 头提示 > 0"这条次序而言，槽里的提示就是"头提示"的一个等价来源，优先级不变。

**但甲有一个结构性的、乙′没有的问题**：D27 已定项 7 / 9，`.claude/kb/decisions/27-小数据打包容器.md:364` 起，用户定案原话（同文件 :5）「不接受新增语义，就在一套 COW 下面走」，落地是「**整容器一份 MAC，AAD 绑容器身份**」；同文件 :379 整行「AAD 绑**对象**身份 + 整容器一份 MAC | **机制性排除**：N 个 AAD 对 1 个 MAC ⇒ N−1 个对象验不过。这正是 D9（加密） 已定项 6 排除 extent 切分时用的那条机制，逐字「失配成为正常操作的必然结果 ⇒ 排除」」——这条已定条款**明确排除了"按对象身份绑 AAD"这条路**，改用容器级 AAD。甲的核心机制恰恰是"locality_id 进对象的六元组 AAD"，而一旦对象被打包进 D27 容器，**这个对象层面的 AAD 根本不存在了**——AAD 换成了容器身份 (出生树, 打包记录类型, 容器号, 容器出生代)，不含 locality_id，也不含任何对象专属字段。

⇒ 甲对打包对象是**结构性失效**，不是"多付一点代价"：它宣称的机制（"locality_id 成为第六个 AAD 字段"）对 ≤4 KiB 对象根本无法实施，而 D27 已定项 1（`.claude/kb/decisions/27-小数据打包容器.md:5-8`）的存在理由就是覆盖这一档对象——按 D25（目标负载优先级） 的 smallfile 权重，这不是一个可以忽略的小众场景。**甲的候选原文（背景材料第三节）没有交代打包之后怎么办，这是一处未定义的缺口，我把它记进第四节甲的正面论证需要补的条款里**：甲若要自洽，要么承诺打包对象上退化为乙′式（进容器密文、不进 AAD）的形态（意味着甲事实上分裂成两套机制，各自按对象大小选择），要么放弃"进 AAD"这条核心主张、直接并入乙′。乙′完全没有这个问题，因为它从一开始就不依赖 AAD 绑定。

### 3.3 加密开启时的重建

（这里的"臂乙′"是 D18 已定项 13 自己内部的臂名，与本轮候选"乙′"同名但不同指，容易混淆，下面我一律用"D18-13-乙′"指代前者，避免与本轮乙′混淆。）加密开启时，五元组/诞生代号/写序就地变密文，重建路径本来就需要密钥才能解出身份（前提十一）。甲、乙′的字段都住在同一个类身份段区域（甲：并入六元组，同样"就地变密文"；乙′：候选原文自己写"加密开启时与五元组一起就地变密文"）——两者在这一点上**待遇相同**：都需要密钥才能在加密开启时被读出，都不比五元组本身更难重建。丙′没有这个字段，它的"幸存 extent key"来源是 extent 树（码 2 索引节点），而索引节点的类身份字段（树 ID + key 区间等）在加密开启时**同样**要进密文（`.claude/kb/decisions/18-块里携带什么信息.md:950` 一带"元数据类身份字段（五元组 / key 区间）一律进密文"）——所以丙′的主路径同样需要密钥。

## 四、问题 4：三条臂正面论证（U1–U4）+ 检查 + kb 改动

### 4.0 分批重新聚簇中间态：不分辨臂，且不构成正确性失败（分析性结论，非新模型）

D8（核心索引结构） 已定项 3 第 3 条（`.claude/kb/decisions/08-核心索引结构.md:198`）要求重新聚簇"增量、可中断、可续做"——即一个 extent 很多的大对象，重编可能跨多个事务分批完成。round 1 攻方腿已指出（`d18-locality-r1-opus-output.md:164-166`，标"推理，模型没建"）：中途某次发布落盘时，这个对象的部分 extent key 已经换了新首段、另一部分还是旧首段，此时 I-9.9（记录==每条 key 首段）在合法镜像上会判红，三条臂共同撞上。

我的分析（不需要新模型，是从已有定义直接推出）：这个"合法却判红"的风险**不是新的**——I-9.9 已经用"重建后一律不可判定"这一整块处理了"记录与 key 不能保证同源"的场景（`.claude/kb/invariants.md:265` 整行「记录的 `locality_id` == 该对象每条 extent key 的首段；extent 树未经重建时输出红 / 绿，超级块 `map_provenance` 标 rebuilt 时两侧同源，输出「不可判定」，不许输出「通过」」）。分批重新聚簇造成的"一个对象内部多个首段并存"，与"重建之后记录/key 不同源"是**同一种不确定性**（都是"这个字段允许暂时不一致"），只是触发条件不同（一个是崩溃重建，一个是正常运行中的多步操作）。这提示一个缺口不在本轮射程但要记下来：**I-9.9 的"不可判定"目前只挂在 `map_provenance=rebuilt` 这一个开关上，没有覆盖"重新聚簇进行中"这第二种合法不一致的窗口**——这是 D8 已定项 3 第 3 条自己欠下的账，不因本轮选甲/乙′/丙′而改变，我把它记为一条新欠账（见文末改动清单）。

对**数据可找到性**（U1 的字面判据）：分批重编不改变 (inode, offset) 的唯一性（丙′/乙′/甲论证过的同一条机制，第三节已重复确认），所以中间态下**没有任何一段数据变得找不到**——最坏情况是重建时对同一个对象的不同 extent 选出了不完全一致的 locality（首段），这只影响排布，不影响能不能读到。**这与第三节的克隆分析同构**：一个共同前提上的洞，三臂一起顶着，不分辨臂，不拿它去打倒任何一条候选。

> 重建时若某对象的 inode 记录与全部 extent key 均丢失、单元头提示存活：重建后该对象的 locality 取单元头提示值（不取 0），且该对象在重建报告里标记「provenance=hint」，checker 不许把这个标记与 I-9.9 的"通过"混同输出；`provenance=hint` 的对象即使数值上与其他幸存证据一致，也不进入 I-9.9 的"通过"判定，只能是"不可判定"的一种（与 `map_provenance=rebuilt` 同一档，理由相同：两侧不同源）。
