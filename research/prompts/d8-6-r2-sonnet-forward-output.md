# D8 未定项 6 第二轮·sonnet-forward 原样输出（2026-09-03）

## Verdict: SURVIVES WITH AMENDMENT

F23's shape (fixed 160-byte record, `locality_id` restored per F14, key `(inode)` alone, an authority-and-mismatch rule per F22, explicit gating on F9) is structurally sound and reuses the project's own patterns correctly. But three of the six scrutiny points expose gaps that would leave the record either unfalsifiable (d) or under-specified in a way that reopens the exact hole it claims to close (e), and one (b) risks a freeze the project can't undo (F12). None require reshaping the field list — all are fixable by adding stated rules.

## (a) locality_id: hole closed, but a second identity relation goes unstated

Storing `locality_id` in the record literally satisfies F14's demand ("the inode record MUST store locality_id"), and because F1 fixes it at creation and forbids updating it on rename, the record's copy cannot drift from what's already baked into existing extent-tree keys **provided** nothing ever rewrites it later. F23(d) correctly keeps `locality_id` out of the inode-tree's own key, so it never collides with (f)'s inode-number cross-check — (f) as written only covers the inode-number duplication, not this one. That's the gap: F23 states no immutability rule for the record's `locality_id` field itself (F1 bars updates "by rename" specifically, leaving other paths undiscussed), and states no checker invariant tying the record's `locality_id` to the locality prefixes actually found in the extent tree for that inode. Without both, a future "migrate locality" operation could silently reopen F14 in a new form: record says L_b, real data still keyed under L_a.

## (b) `(inode)` alone: right for now, unsafe to freeze as-is

Nothing in F1–F22 implies the inode tree is scanned by locality — directory listing goes through the dirent tree (F1), and full rebuild relies on per-block self-description (F10a), not key-order scanning — so the extent tree's scan-locality argument for carrying `locality_id` does not transfer to the inode tree. `(inode)` alone is defensible. But F9 is explicitly unsettled and speaks of snapshot bits "competing for key space" in *the* key — scope unspecified. F23(g) gates the record's reserved bytes on F9 but does **not** gate the inode-tree key SHAPE on F9. If F9 resolves to "every tree's key carries snapshot bits," freezing `(inode)` now (F12) forecloses that without the reformat F12 says becomes impossible post-freeze.

## (c) attribute-presence bit: cashable now, but two things aren't nailed down

The refuse-if-unset-and-set semantics in F23(a) doesn't need the attribute keyspace's internal design to be meaningful — it's the incompat-bit pattern (F4-style "reserve, don't grow later") applied per-object, and it's a legitimate now-decidable contract. Two gaps: (1) F23(b) gives `flags` only 8 bits with none of them named — which bit is the presence bit, and are the rest reserved-zero, is unstated; (2) "does not understand the attribute keyspace" is all-or-nothing — it doesn't address a reader that understands the keyspace format but not one specific attribute type inside it, which just recreates the incompat/compat_ro/compat three-tier problem one level down, unresolved. Neither is fatal since v1 never sets the bit (xattrs/ACLs are deferred per F19), but that v1-inert state must be said explicitly or the freeze (F12) is ambiguous about what's actually settled.

## (d) `nlink = 1` survives; the invariant wording does not

The *value* `nlink = 1` is defensible on grounds F23 already gives (F21: it doesn't trip an `nlink==0`-triggers-reclaim scanner) — this is a correctness argument, not a space one, so F10 doesn't bar it. The *invariant* — "nlink equals dirent count, ... exempt until the dirent tree exists" — is broken both ways: if "dirent tree exists" means the tree structurally exists (F20: it's one of D8's six trees, presumably present from mkfs), the exemption never fires and the conflict F21 identified stands unresolved on the very first image. If it instead means "this object has zero dirent entries," the exemption swallows exactly the case it's meant to justify, making the invariant true by construction — unfalsifiable, and it erases the checker's ability to ever distinguish "not yet linked" from "orphaned" (the exact distinction F16's recoverability argument needs elsewhere). Given v1's stated milestone has no directories at all, this isn't a transient corner case — it is the permanent state of v1's only durable image, so a "post-commit only" carve-out doesn't save it either.

## (e) change_counter orders same-lineage records; it does not order across inode-number reuse

Within one continuous object lifetime, a monotone per-record-rewrite counter correctly answers F17 ("which of two scan-found copies is current") — the higher counter wins, since every COW of the record increments it and old copies keep their old value forever. But F18 flags exactly the failure mode F23 doesn't guard against: after inode-number reuse, an old deleted object's un-GC'd record and a new object's fresh record can both carry inode=42, and the old (dead) object's `change_counter` can be numerically *higher* — a bare counter comparison picks the wrong one. The tie-break must be lexicographic: `inode_reuse_gen` first (unconditional), `change_counter` second (within the same reuse epoch). F23(b) lists both fields but states no ordering between them. Wrap at 64 bits is not a practical concern and needs only a one-line "undefined; bump reuse_gen first" note.

## (f) still missing for the first transaction

Beyond (a)/(b)/(d)/(e)'s fixes: (1) no stated write-path rule that a data write must *read* the target inode's record to obtain `locality_id` before constructing the extent key — F23 only established that the record makes this *readable*, not that the write path is required to source it from there rather than some other in-memory state; (2) no stated initial values for `inode_reuse_gen` and `change_counter` at creation (0 and 1, presumably, but unstated); (3) (f)'s mismatch rule is read/checker-time only — no write-time assertion that `record.inode_number` equals the key it's filed under before commit, which catches a writer bug before it becomes an irreversible durable EIO.

## Required amendments (exact wording)

1. **(a) immutability + second invariant.** Add to F23(f)/(g): *"The record's `locality_id` is write-once: set at creation from F1, never modified by any code path thereafter (rename, migration, defrag) without a full, same-transaction rewrite of that inode's entire extent-tree key range — no such path exists in v1. Checker invariant: every extent-tree entry `(L, I, *)` must have `L == inode_record(I).locality_id`; violation is CORRUPT, kernel returns EIO for that range, never auto-repaired."* Add a write-path rule: *"Any data write reads `locality_id` from the target inode's record before constructing its extent key; it is never sourced from path-walk context."*

2. **(b) gate the inode-tree key shape.** Add to F23(d): *"`(inode)` alone is provisional, gated on F9: if F9 resolves to snapshot bits carried in tree keys generally, the inode tree key becomes `(inode, snapshot_bits)` with those bits reserved-zero now, matching F4's reserve-don't-grow-later posture — this item is not eligible for freeze under F12 until F9 states whether it applies to this tree."*

3. **(c) name the bit and scope v1.** *"`flags` bit 0 = attribute-presence bit; bits 1–7 reserved-zero. In v1 this bit is always 0; the attribute keyspace is out of v1 scope (cf. F19). Its later introduction is additive only — no migration of existing records required, since the bit was already reserved-zero."* Flag as an open dependent (alongside F9) that the attribute keyspace itself will need its own compat-tier scheme per attribute type, not decided now.

4. **(d) replace the exemption with a gate.** Delete the "exempt until dirent tree exists" clause. Replace with: *"The invariant `nlink == dirent_count` is GATED on directories shipping (same mechanism as F23(g)'s gate on F9); the checker does not evaluate it in v1. Once directories ship, it applies with zero exemptions to every durable image."*

5. **(e) state the composite order and the trigger.** *"Two records for the same inode number are ordered by `(inode_reuse_gen, change_counter)` lexicographically, `inode_reuse_gen` dominant. `change_counter` increments on every durable rewrite of the record (including size/mtime changes from data writes, not only explicit metadata syscalls). Wrap is undefined; `inode_reuse_gen` must be bumped before it could occur."*

6. **(f) initial values and write-time check.** State `inode_reuse_gen = 0`, `change_counter = 1` at creation. Add to F23(f): *"The writer asserts `record.inode_number` equals the inode-tree key it is filed under before commit; the checker's EIO rule is a second, independent check, not the only one."*
