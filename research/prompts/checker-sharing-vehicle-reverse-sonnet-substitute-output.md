1. Attack on P1's generated constants module

The concrete kb entry already exists in this repository today, it is not hypothetical. F4 states it directly: the journal header is registered as JOURNAL_HDR = 78 bytes, but the kb's own prose elsewhere says two settled-but-unlanded increments make it 91, and three make it 95. F7 already showed, in the prior adversarial round on the build plan, that this exact number produces a shared-file failure: with JOURNAL_HDR = 78 wrong, core and checker agree and every planned check stays green.

P1 does not close this gap, it inherits it unchanged. Walk the mechanism precisely, using the gate 27 script as it is actually written (.claude/gate.d/27-format-constants.sh), which is the only existing machinery P1's generator would sit beside:

Kb entry: a single format-const marker exists, "format-const: JOURNAL_HDR = 78 stale=...", attached to the settled item that first fixed the header at 78 bytes. Two later settled items (D23's item 7, adding a transaction-boundary field to the header, and item 13, requiring the payload checksum to live inside the header and be covered by header_csum) changed what the header should contain, but those items never got a second format-const marker, because kb-discipline and the gate 27 script both enforce that a name may be registered in exactly one place (the script's own duplicate-detection code rejects a second marker for the same NAME).

Generator behavior: P1 says the generator "refuses to emit a constant that has no kb marker." JOURNAL_HDR has a marker, so the generator emits it without complaint: pub const JOURNAL_HDR: u64 = 78. The generator has no instruction to reconcile a registered marker against unmarked prose elsewhere in the same file describing later increments, because those increments were never expressed as a second marker (the registration rule forbids that), and nothing in P1's description asks the generator to scan decision prose for phrases like "settled but unlanded" near a constant's name.

Resulting bug: both core's serializer and the checker's parser consume the same generated value. Core lays out the record with header_csum covering bytes 0 to 78 and starts writing named items at byte 78. When core implements the settled item 7 and item 13 fields, it has only two options given the shared 78: either it never actually adds those fields (silently non-compliant with its own settled decisions, but self-consistent, since checker uses the identical boundary), or it writes them starting at byte 78, which both sides now agree is payload territory, not header territory. In the second case, the transaction-boundary field and the payload checksum end up outside header_csum's coverage, which is precisely the gap D23's item 13 exists to close ("载荷校验和住头内罩点名项数组"). A single flipped byte in that region would go undetected by any header-level checksum check, and would only be caught, if at all, by whatever weaker protection ordinary payload bytes get. Gate 27 stays green because 78 equals 78 in both source and marker. Every planned invariant check stays green because I-8.2 (record header does not cross the physical atomic unit) and the I-2 checksum checks are defined and evaluated relative to the same wrong 78-byte boundary on both the writing side and the checking side.

Would forbidding sharing (two hand-written constant sets) have caught it? No, for this specific instance, and F7 already establishes why: both hand-written copies would be transcribed from the same kb marker or the same kb sentence, so both authors write 78. The cost of trying it anyway is not merely wasted effort, it is disallowed outright: F5's machine-first rule states duplicated code is permitted only if generated, never hand-copied. Proposing two hand-written constant sets as the alternative is itself a violation of a settled project rule, not a safer fallback.

The answer is different for F4's other open defect, the five-tuple that totals 33 bytes with no per-field widths anywhere in the kb. There, F7 already showed that two independent inventions of the split disagree loudly, so hand-writing would catch that one. P1's own rule (refuse to emit an unmarked constant) forces this specific gap to be pinned before generation, which is a genuine improvement over silence. But that same refusal rule creates a second, distinct risk: it puts pressure to add a marker just to unblock a red gate, before the actual split has gone through the decision process. Nothing in gate 27 (I read its full source) checks that a marker's value is backed by a settled decision at the same authority level as the surrounding prose, it only checks that a marker exists and that source matches it. A quick, ad hoc marker added purely to silence the generator's refusal would pass gate 27 exactly as well as one that reflects real consensus.

2. Attack on P1's independence claims

Separate newtypes. This defends against exactly one class of bug, per F5's rule: confusing logical address, physical address, device offset, generation and inode number with each other, which is a mixing-of-kinds problem. It does nothing for the class of bug in task 1, because a newtype wraps a numeric value, it does not validate that value against the decisions. Both crates' newtypes get instantiated from the same numeric literal, generated by the same script from the same kb sentence. The independence here is real for what it targets and irrelevant to what F6 and C48 are actually worried about, which is a shared wrong premise, not a mixed address space. This is nominal independence along the axis that matters for this review, not a false claim along the axis it was designed for.

Independent CRC32C implementation. This defends against one implementation having a coding bug the other does not share, for example an off-by-one in the polynomial table. It does not defend against a wrong field boundary, because both CRC32C implementations, however differently coded, are told where the header ends by the same generated constant. If that boundary is wrong (as in task 1), both independently-coded checksums are computed over the same wrong byte range and agree with each other, which is exactly C12's cited bcachefs failure mode (this_cpu_add shared between runtime and GC reconstruction, differing only by a gc index) reproduced one layer up, at the constants level rather than the code level.

There is also a way this can go the other direction and produce a false red on a healthy image. CRC32C is not one fixed byte-for-byte specification once you leave the polynomial choice; concrete implementations differ in initial value, input/output reflection and final xor unless every parameter is pinned identically. If P1's "a different crate" is adopted without pinning it to the exact same parameter set core uses (poly, refin, refout, xorout, init), the two computed values will disagree on every single image, healthy or not, purely from a convention mismatch, not from any real corruption. That failure mode is worse than it looks: once it fires on every image, the practical fix under time pressure is to make the two crates agree on parameters, which puts the two implementations right back to being effectively the same computation, undoing the independence P1 is trying to buy.

Independent parser. F1 records that D13's compromise, "share only format parsing," was scoped narrowly to the checker's own two internal directions, root traversal and linear scan. P1 extends sharing of format-relevant material (the constants module) to a third party, core itself. F2's C12 exception ("format parsing and constants excepted") does authorize this at the decision level, so this is not a contradiction, but it does mean the shared premise now sits under three surfaces instead of two: root traversal, linear scan, and core's own serializer. An independently written parser that consumes the same wrong width from the shared module will misparse in exactly the way core wrote it, because the round trip is self-consistent by construction. So "independent parser" protects against bugs in parsing logic, wrong loop bounds, wrong endianness handling, and does not protect against a wrong constant that all three surfaces agree to trust.

Checker probes physical_block_size itself. P1's stated fallback for a file-backed image, report the geometry as "declared, not probed," is the honest and correct thing to do when there is genuinely nothing to probe; it is not a lie, so it is not itself a false red. The break is about volume, not correctness of the fallback. F9 describes crash-point replay as materializing images and running the checker against each one; D13's own layer description (layer 0, tens of writes, not sampled, run on every write-path submission; layer 1, thousands of writes, run every commit) puts the number of materialized states at, in the kb's own words, the low hundreds even for the first transaction (verification-build.md, section three). Materializing that many states as live, geometry-bearing block devices, one loop device or device-mapper node per state, on every commit, is not a practical design: it multiplies setup and teardown by the state count and typically needs elevated privileges, which is exactly why the kb reserves real raw-device testing (dm-log-writes, C6) for a separate, slower tier and keeps layer 0 and layer 1 fast. The practical, and almost certainly the intended, choice for the high-frequency tier is plain files. That means the checker runs in "declared, not probed" mode for the overwhelming majority of its actual invocations, the crash-point-replay tier, which is also the tier I-7.5 and I-8.2 are supposed to be exercised against. P1's independent-probe mechanism is real for the raw-device path and largely inert for the path that runs most often.

A second, sharper break in the same mechanism: P1 says the checker "probes the device itself," singular. D22's settled item 2 says mkfs divides by the pool's max physical_block_size across all devices, and mount recomputes per device and refuses on mismatch. Heterogeneous device geometry inside one pool is an already-flagged risk area (C17). If the checker's probing code queries one arbitrary device rather than reproducing mkfs's exact pool-max aggregation across every device, a perfectly healthy image on a heterogeneous pool will make the checker disagree with the superblock's recorded value and report a false red, purely from a methodology mismatch between how mkfs computed the number and how the checker re-derives it. P1's text does not specify that the probing step must reproduce the pool-wide max, only that it "probes the device," so this gap is open as written.

4. Attack on P2's claim that the vehicle changes no on-disk byte

The claim is defensible for the raw byte values the kb has settled: DATA_UNIT_BYTES = 32768 and NODE_BYTES = 16384 (F3, registered) do not change their numeric value depending on whether the code driving the write is a library call, a FUSE daemon, or a kernel module. But I checked what a kernel-module vehicle would actually require to write those unit sizes through the standard Linux mechanism a kernel filesystem uses, and it is not neutral.

I read block/bdev.c in the kernel tree at /home/fy5090/linux-bug-fix/linux, which is the same 6.17 line as the host kernel per F10. sb_set_blocksize (lines 234 to 244) refuses any block size above PAGE_SIZE unless the filesystem type declares the FS_LBS flag and CONFIG_TRANSPARENT_HUGEPAGE is enabled; otherwise it prints "block size(%d) > page size(%lu) not supported by filesystem" and returns 0, meaning failure. sb_min_blocksize, which most in-tree filesystems call at mount time, floors the requested size at the device's logical block size and then calls sb_set_blocksize, inheriting the same PAGE_SIZE ceiling. I also checked this machine directly: getconf PAGE_SIZE returns 4096 on this x86_64 host. Both 32768 and 16384 exceed that.

This means a kernel-module vehicle for singlefs cannot represent a 32 KiB unit or a 16 KiB node as a single buffer-head-managed block through the ordinary VFS path without either opting into FS_LBS, a comparatively recent, narrowly supported kernel feature gated on transparent huge pages being enabled, or managing its own buffering above 4 KiB blocks entirely inside the module, the way btrfs and XFS manage nodesize independently of the VFS blocksize. Neither the userspace library backend nor the later FUSE adapter faces this constraint at all: userspace I/O only needs O_DIRECT alignment to the device's own logical block size, which has no tie to the host's PAGE_SIZE. So while the settled byte values (32768, 16384) do not change across vehicles, the achievable semantics do: a kernel-module vehicle is forced into an extra structural choice, either a kernel config dependency the other two vehicles never need, or a private multi-block buffering layer, and either path opens a state the block-device-abstraction crash model in F9 does not model at all, a unit whose constituent 4 KiB buffer heads can be dirtied independently of one another by the VFS's own writeback machinery, something that cannot happen in the O_DIRECT library or FUSE-over-library path where the whole 32 KiB unit is always issued as one explicit write by singlefs's own code.

P2's proposal defers the kernel-module vehicle indefinitely, so this is not an active break today, it is a cost that P2's "changes no on-disk byte" sentence understates: the sentence is true about the byte values and silent about the fact that one of the three vehicles it names cannot honor those byte values through the kernel's standard path without an additional, vehicle-specific engineering decision that the other two never have to make.

6. Closing

The one finding in this review that is a reachable break today, not merely a cost or a future risk, is the first one: P1's generated constants module, run exactly as specified against the kb's current, live state, reproduces the JOURNAL_HDR = 78 versus 91 versus 95 defect that F4 and F7 already document as an existing, unresolved inconsistency, not a hypothetical one. Nothing in P1's design adds a check that catches it, because gate 27, as actually written, only compares a registered marker's value against source literals; it has no mechanism to notice that the registered marker is stale relative to later settled prose about the same field. Every mechanism P1 proposes, the generator, gate 27's extension, the independent CRC32C, would run green on this exact input today. The kernel-module and checker-probing findings in attacks 2 through 4 are real but are either explicitly deferred by the proposal (the kernel module) or already partially acknowledged by the proposal's own hedge ("declared, not probed"), which makes them costs and open risks rather than silent breaks.

The one check that would most change this answer is a gate stage that does not yet exist: something that cross-checks each registered format-const marker's value against every settled decision item that discusses a width contributing to that same field, and turns red when a marker's value is older, by decision-item date, than a settled item that changed the field's implied width. Verification-build.md's own "待定案" section, question seven, already names the underlying problem, collapsing the 78, 91 and 95 readings of the journal header into one number, as unresolved and reported to the user. Until that check exists, P1's generator is only as trustworthy as the currently registered marker, and today that marker is already known to be wrong.
