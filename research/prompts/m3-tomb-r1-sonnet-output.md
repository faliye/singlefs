## 2　W1　墓碑容器从哪可达（C103 在类型 1 上的那一半）

### 2.1　条款与实现各说了什么（推导起点）

1. 条款要求墓碑容器有一个容器索引指向：「容器索引是打包单元物理指针的唯一持有者」（`.claude/kb/decisions/18-块里携带什么信息.md:294`），类型 1 的更新代价写成「类型 1（墓碑）= COW 它 + 改容器索引一条」（`.claude/kb/decisions/18-块里携带什么信息.md:294`）；容器号「类型 1（墓碑）树内单调分配」（`.claude/kb/decisions/18-块里携带什么信息.md:279`）。
2. 中央映射才是落点的唯一入口，且装全部码 3 容器：「释放一律经映射，不经提示」（`.claude/kb/decisions/19-块指针的结构与宽度预算.md:106`）；「中央映射装码 1、码 2、码 3 三类单元」（`.claude/kb/decisions/19-块指针的结构与宽度预算.md:175`）；豁免映射的只有三类：「不进映射的三类（自举豁免）」（`.claude/kb/decisions/19-块指针的结构与宽度预算.md:182`）——映射树自己的节点、树表单元、实例表单元。
3. 所以 inode 叶容器今天的形态是「父内部节点持 86 字节指针（提示）+ 容器进映射（权威）」（第 0.5 行）；MAC / nonce 住这条 86 字节指针的头部，第一版恒 0、读者遇到非 0 判损坏：「加密关着时 MAC 16、nonce 12 恒 0，读者遇到非 0 判该指针所在的结构损坏」（`.claude/kb/decisions/19-块指针的结构与宽度预算.md:64`）。位照留由这条指针头部承担，不需要映射 value 装 MAC。
4. 2026-09-06 那次「容器索引就是中央映射」栽在 value 装不下 MAC / nonce。今天的代码上再看两点：(i) 映射 key 是 (类标签, 出生树, 出生 txg, 实例代号, 出生序号) 补零，不含打包记录类型与容器号（「pub fn mapping_key_for_node(unit_class: u8, pointer: NodePointer) -> Vec<u8> {」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/records.rs:202`）），所以「(树, 类型) 下最大容器号」从映射里读不出来，类型 1 与类型 2 的容器在映射里分不开；(ii) 映射条目答的是「这个单元落在哪」，不是「哪个根引用了它」，I-3.1 数引用沿树走（第 0.4 行），映射里有一条只说明它被映射着。（我先前想用「回退取不回」当第三条理由，读 `mount.rs:4946` 之后撤回：用户可见角色的映射条目是随目标版本带回来的。）
5. T1 要在意图那次发布写墓碑，所以必须有一个新的挂点；day-1 注册一棵零根空树、之后第一次写才有根，是 livelist / 稀疏旁表 / deadlist 的现成先例（第 0.1 行）。回退按种类找 R_old 条目用 `expect`（第 0.8 行），惰性注册会让回退到「注册之前」的一版 panic，所以 day-1 注册是这条路上的唯一稳妥时机（推的；与 m3-delete-r1 对 `deleted_inodes` 的结论同向）。

### 3.2　要不要带死亡那次的 txg 或写序：不带

1. **记录字段分不开「哪一次死亡」**：同一个 (对象 ID, 对象出生代) 在一条时间线上只会死一次；管理员回退把对象带回来之后再删，第二条墓碑与第一条逐字节相同，加一个 txg 字段只会让两条「不同」，而不同并不告诉扫描重建该信哪一条。能分开的是它们**住在哪个容器的哪一版**（见 W5：R_old 取旧版 + 重写 + 退役记录，判活靠容器身份与诞生代号，不靠记录字段）。
2. **回收门不需要它**：回收粒度是单元（「回收粒度 = 单元」（`.claude/kb/decisions/18-块里携带什么信息.md:237`）），一个容器要整个过门才能回收，过门要看的是它里面最晚的那次死亡；容器关闭那一版的诞生代号（码 3 头偏移 73，「只记这一次写」（`.claude/kb/decisions/18-块里携带什么信息.md:283`））恒不早于里面每一条的死亡（见 W3），是现成的上界，保守不误放。
3. **代价**：带 txg 是 40 B、815 条（容量 −20%）；带写序 10 B 是 42 B。买到的只有记录级的门，而记录级的门在单元级回收下没有消费者。
4. **会推翻它的现象**：出现一条扫描重建规则要比较「墓碑的死亡顺序」与「同一个 key 之后又被写的数据版本」——那是部分删除（truncate / punch 后重写）的世界，第一版没有；那时记录是新形态（新类型或改宽，incompat），冻结前零代价。E104 把「死亡写序」列为六样输入之一（`.claude/kb/decisions/11-索引节点要不要留消息缓冲区.md:61`），但它在活跃 kb 里没有字段定义（事实表 d3 节）；整对象墓碑上它等于容器的 (诞生代号, 实例代号, 事务号) 三元（D18:286 / I-1.8），推的。

### 3.3　同号的两个已发布对象靠哪个字段分开

靠**对象出生代**（记录偏移 8）：D8 只保证已发布的 (inode 号, 对象出生代) 不复用，崩溃恢复落到较旧的根后同一个号可以被重发（「号在崩溃恢复落到较旧的根之后可以重发」（`.claude/kb/decisions/08-核心索引结构.md:203`）），重发的新对象出生代大于环里读得出的每一条根的 txg。

**字面冲突（两边整行并排）**：
- 左 `.claude/kb/decisions/18-块里携带什么信息.md:232`：「D8（核心索引结构） 已定项 6 只保证已发布的 (inode 号, 对象出生代) 不复用，回退之后号会被重发」。
- 右 `.claude/kb/decisions/08-核心索引结构.md:171`：「管理员回退是挂着时的一次向前发布，那次发布的 inode 号水位取 max」，接着「已发过的号不重发」。

2. **统计量 13、14 不登记**：不加标签常量、不写记账行、不改 `NEW_POOL_FILE_CREATION_ACCOUNTING_ROWS`（15）；「空」读成「从未推进」，门读不到 13 就判关。初值 0 与「空」在门上等价（所有 txg ≥ 1），但写 0 要多两行并随发布重写，与 D5:134 的「有过一次推进之后才随每次发布重写」冲突。
3. **「死亡代号」定义成容器的一个字段**：该容器**关闭那一版**的诞生代号（码 3 头偏移 73）。开放容器没有死亡代号（门对它无定义、不回收）；一个已关闭的容器不再重写，所以这个值固定。它是容器内每条记录真实死亡 txg 的上界：容器只在新记录进来时才重写（W4），每次重写的诞生代号 = 那次发布的 txg ≥ 刚加进去那条的死亡 txg。取上界只会让门晚开、不会早开。回退发布重写 R_old 那个容器时（W5）诞生代号变成回退发布的 txg，只会更晚，同向保守。

| 10^9 | 981 355 | 64 314 081 280（61 334.69 MiB ≈ 59.9 GiB） |

- 摊到每次删除约 64.3 B（两副本）。树的根一层装 135 个容器（`(16384 − 131) ÷ 120`），一层树装到 135 × 1019 = 137 565 条墓碑；再往后要多层码 2（见 2.3 第 3 条，v1 走不到）。
- 「第一版单文件下有多大」：一次 unlink 一条记录，第一版没有目录、删完只能建 size 0 的新 inode（K-U5 已定 X1），能产生多少条墓碑由用户能做多少次建删决定，增长与时间无关；上表是上界，不是预测。要不要回收的触发点在第一版不存在（没有清扫），需要它的时刻 = 清扫落地之后第一次要摊薄这笔增长，或树要长到多层之前。
- 这是「墓碑容器在第一版的合法历史上无界增长」那一格（跑前判据第 4 条）：记一格，增长率如上、需要回收的时刻写在上一条。

## 5　W4　开放容器与写纪律

1. **一个开放容器，满了才关**：第一版没有快照，`.claude/kb/decisions/18-块里携带什么信息.md:234`：「墓碑单元按代际装——一个代际结束就把当时开着的单元关掉，不让不同代际的记录混进同一个单元」，与 `.claude/kb/decisions/18-块里携带什么信息.md:295`：「快照发布之前必须先关闭并写出当前开放容器」，在第一版都不触发；容器在记录数到 1019 时「关」。关闭不写任何东西：满的那一版就是它最后一次被重写的那一版，下一条墓碑进新容器（容器号 + 1、新出生代），旧容器此后只被照抄。
2. **不删除的发布不重写它**：每次发布装全部角色的单元，重写的是这次装的、照抄的从上一版拷（「这一版全部角色的单元：重写的是这次装的，照抄的从上一版拷」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/transaction.rs:6556`）），照抄机制是 `fn carried_unit(previous: &TransactionOutput, identity: TransactionUnit) -> PublishedUnit {`（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/transaction.rs:5435`），墓碑树的容器与根在没有新记录的发布里走这一支，+0 单元。
3. **D18 那句有两种读法，我取第一种**：「开放容器在它所属代际内每次要发布时被重写，新单元、新诞生代号、身份不变」（`.claude/kb/decisions/18-块里携带什么信息.md:294`）——读法一：每次发布里有新记录要进这个容器时重写；读法二：开放期间每次发布都重写。D18:323 的账「1000 文件每 10 个 fsync 一次 ≈ 6.25 MiB」（`.claude/kb/decisions/18-块里携带什么信息.md:323`）= 100 次发布 × 64 KiB，数的是「有删除的发布」，读法一。读法二会让第一次删除之后的每一次发布都 +2 单元、×16，包括纯写与空发布，与发布结构里照抄没重写的角色那一支也不合。**请主 agent 核这句的原意**（条款没有明写）。
4. **对每次发布的影响**（推的，单位：单元；一个单元两次整写；崩溃状态倍数按那一段整写数取 2 的幂）：

| 发布 | 墓碑相关单元 | 该段倍数 |
|---|---|---|
| 普通发布 / 空发布 / 删除的各批（含最后一批：墓碑只在意图那次写） | +0 | ×1 |
| unlink 意图发布（含「满了开新容器」那一次） | +2（容器 + 根） | ×16 |
| 回退发布 | +0 / +2 / +3（W5） | ×1 / ×16 / ×64 |

   D18:323 那笔账在 P 下变成 100 × (32 KiB + 16 KiB) × 2 = 9.375 MiB（多一个 16 KiB 根），比条款口径多 50%（算术，推的）。
5. **关闭路径要能被测试强制进入**（`.claude/rules/fs-design.md` 五条硬要求第 2、4 条）：加一个只供测试的容量旋钮，形态照 `CodeTwoTreeNodeCapacities::CappedForTests`（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/transaction.rs:2126`），把每容器记录数从 1019 压到 2，固定脚本的删除段才走得到「满 → 开新容器 → 根多一条」；运行时报出「开放容器记录数 / 容器总数 / 走的哪一条」（硬要求 4）。第一版单文件一次 unlink 一条记录，不加旋钮这条分支永远走不到。

## 6　W5　回退（以及崩溃恢复落到较旧的根）

### 6.1　条款

- 回退是一次向前发布：「管理员回退是挂着时的一次向前发布」（`.claude/kb/decisions/23-journal的角色与格式.md:376`），新根的用户可见树取 R_old 的，「不新增实例、不取号、不写实例表行、不施加也不删除任何记录」（`.claude/kb/decisions/23-journal的角色与格式.md:376`）；实例表那边也写着「管理员回退是挂着时的一次向前发布，不写行」（`.claude/kb/decisions/18-块里携带什么信息.md:305`）。
- `deleted_inodes` 已经被点名取 R_old：「`deleted_inodes` 也取 R_old 那一版的」（`.claude/kb/decisions/08-核心索引结构.md:171`）；理由是否则 R_old 之后删掉、随 R_old 的 inode 树回来的对象会被再收一次。墓碑树是同一类「随删除状态走」的结构，要么与它同取 R_old，要么说清为什么不同。
- 崩溃恢复：已发布谓词对码 2 / 3 判「b ≤ T_pub」（「码 2 / 3 ⇒ b ≤ T_pub」（`.claude/kb/decisions/18-块里携带什么信息.md:309`）），被抛弃时间线上之后写的固定点单元一律未发布。

### 6.2　三种形态

| 形态 | 做什么 | 判 |
|---|---|---|
| R-K 墓碑树取现行 | 回退发布不动墓碑树 | **出局**（跑前判据 1）：回退把对象带回来，墓碑仍指着它；新不变量 N3（墓碑指认的对象若在 inode 树里则 nlink = 0，见 7.2）在回退后的镜像上直接红，扫描读它时活对象判死——正是第一轮攻方反例二 |
| R-A 取 R_old（像 extent、inode） | 回退发布里墓碑树的树表条目根指针换成 R_old 那一版的；墓碑树的根与容器记成用户可见单元 | 活的树自洽，回退发布 **+0 单元**。改动：`root: if entry.kind == TREE_KIND_EXTENT`（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/mount.rs:4972`）那个条件加上墓碑树的种类，`is_a_user_visible_unit`（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/mount.rs:4651`）给新角色表态为 true。**但留一个扫描洞，见 6.3** |

### 6.3　为什么 R-A 单独不够：玩具里的三个世界（`tomb_model.py` 第二部分，run-1.txt `scan` 行）

玩具规则（取自 E104 摘要与 D18:294 / I-1.8，不是 E104 的复跑）：只看已发布的版本；每个容器身份取 (诞生代号, 实例代号, 事务号) 最大的一版；类型 3 容器里列出的身份整身份作废；墓碑 = 剩下的类型 1 容器里全部记录之并。真值 = R_old 那一版的死者，加回退之后用户又删掉的。世界（A、B、C 三个对象，容器号与 txg 见 `world()`）：w1 两次删除之间回退；w2 回退到任何删除之前、再删一次 A；w3 每容器两条、回退到第一次删除之后。

| 形态 | w1 活对象判死 / 死对象判活 | w2 | w3 |
|---|---|---|---|
| R-A（只取 R_old） | 1 / 0（B 判死） | 1 / 0（B 判死） | 2 / 0（B、C 判死） |
| R-B（重写 + 退役） | 0 / 0 | 0 / 0 | 0 / 0 |
| R-B 消融：退役记录不带容器出生代 | 0 / 0 | 0 / **1**（回退之后新删的 A 被旧退役记录误杀，判活） | 0 / 0 |

读法（推的，玩具只有一条择新规则）：R-A 之所以错，是回退之后盘上仍有「诞生代号更大」的陈旧容器版本，扫描择新会选它；重写一遍 R_old 的内容，让重写那一版的诞生代号（= 回退发布的 txg）压过陈旧版本；R_old 之后才出生的容器身份在 R_old 里没有对应，只能整身份作废。消融行说明退役记录的**出生代那一段承重**（D18:296 的四元组写对了），去掉它回退之后同号新容器会被旧退役误杀。

不对称：陈旧的**数据**单元被扫描择新，最坏多出一些文件（复活）；陈旧的**墓碑**被择新，是把活对象判死——给的是错答案而不是保守答案，所以墓碑这一类值得为回退多写。**这个洞不是墓碑独有**：回退不写行，所有类的陈旧已发布版本对扫描都可见；条款没有回答别的类（inode 叶、extent 节点）怎么办（E104 的 rollback 世界：「不写回退行时全规则臂也复活 3」（`.claude/kb/experiments/104-扫描重建的现行版本判定.md:76`）；而 D23 已定项 14 的依据一节说那一半「回退行删了，那一半不再承重」（`.claude/kb/decisions/23-journal的角色与格式.md:417`））；这一轮只对墓碑给答案，别的类交 C113 / 扫描重建那一轮，我没有查它们。

### 6.4　回退那次发布多几个单元（推的，单位：单元；该段倍数 = 4^单元数）

| R_old 之后墓碑树发生了什么 | 回退发布墓碑相关单元 | 该段倍数 |
|---|---|---|
| 一次都没动（R_old 之后没有 unlink 意图） | 0 | ×1 |
| 只往 R_old 的那个开放容器里加过记录 | 重写那个容器 + 根 = 2 | ×16 |
| R_old 之后又开过新容器（≥ 1 个）；R_old 的开放容器可能也动过 | 退役记录容器 1 + 根 1，若开放容器动过再加重写 1 = 2 或 3 | ×16 / ×64 |

- 退役记录容器：类型 3、记录宽 26、一容器 1255 条，容器号与类型 1 共用同一个单调序列（D18:296 写「容器号按类型 1 那套单调分配」（`.claude/kb/decisions/18-块里携带什么信息.md:296`），是否共用一个计数条款没写，我取共用，推的）；它自己也是墓碑树里的一个孩子，条目身份引用的类型段 = 3。
- 回退发布也是「一次发布」，崩在其中任何一点恢复落到的与普通发布没成时相同（「崩在回退那次发布的任何一点，恢复落到的与任何一次普通发布没成时相同」（`.claude/kb/decisions/23-journal的角色与格式.md:387`）），所以重写与退役必须与根指针换成 R_old 同在这一次发布里，不拆。
- 重写那个容器的内容与 R_old 逐字节同，只有诞生代号、写序是新的；它是 R_old 引用的容器的一份新拷贝，R_old 原来那份不再被新根引用，由发布路径照常释放（回退本来就如此：「释放：cur 引用、新根不引用的用户可见单元」（`/tmp/claude-1000/m3-delete-r2/tree/crates/singlefs-core/src/mount.rs:5034`））；回退的复活逻辑只对 R-A 那一支（没重写的容器）起作用。

### 6.5　扫盘重建看到「墓碑 + 回退之后又活着的对象」时靠哪个字段判活

靠**容器身份加诞生代号**（码 3 头的出生树 43、类型 51、容器号 53、容器出生代 61、诞生代号 73、写序 93），**不靠记录里的字段**：记录里的 (对象 ID, 对象出生代) 只指认对象，同一个对象回退前后的墓碑逐字节相同（3.2 第 1 条）。判活的次序（推的，按 P2 / P3）：① 按实例表行滤掉未发布版本；② 每个容器身份取 (诞生代号, 实例代号, 事务号) 最大者；③ 类型 3 里列出的身份整身份作废；④ 余下类型 1 容器里的记录之并是死者。①–④ 里 ① 是崩溃恢复管的，②③ 是回退管的。

### 6.6　崩溃恢复落到较旧的根（被抛弃时间线里写过墓碑）

不需要任何墓碑专用动作（推的）：被抛弃时间线上写的容器版本与根都是 b > T_pub，判未发布（6.1 第三条）；恢复之后新实例的每个 txg 都大于环里读得出的每一条根与记录的 txg（「恢复之后新实例的每一个 txg 都大于环里读得出的每一条根与记录的 txg」（`.claude/kb/decisions/08-核心索引结构.md:203`）），所以新实例里重写同一个容器身份的那一版诞生代号一定压过被抛弃的版本；新容器号 = 所选根的墓碑树最右条目 + 1，与被抛弃时间线里同号的容器靠出生代分开（D18:279 容器号行）。第 13 / 14 项与 I-9.6 照旧：被抛弃时间线的墓碑不进水位算式（`.claude/kb/invariants.md:280`）。
