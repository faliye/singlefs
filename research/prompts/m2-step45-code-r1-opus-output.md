## X2　P1 把一条已提交的发布在「与没发起回退时相同」的窗口里抹掉

### 被判的那一句

`.claude/kb/decisions/23-journal的角色与格式.md:1209`（整行抄，附录一同句）：

> 回退与它的第一个新根同一次发布：回退行、那次发布的单元与回退根在那次发布之前都不生效，崩了就重做——崩在它之前，下一次挂载选的根、施加的记录、已发布谓词的判定都与没发起回退时相同；

许可 P1 的是代码，不是条款：`crates/singlefs-core/src/mount.rs:570` `let next_counter = own_record.counter + 1;`，注释在 `mount.rs:44` 与 `mount.rs:518`（「C340（回退之后记录链从哪条之后接没有定义） 取 P1，预想、等用户定」）。记录落在哪个槽只看 jsn：`crates/singlefs-core/src/journal.rs:109-113`

```rust
pub fn record_offset(counter: u64, ring_bytes: u64) -> DeviceOffsetInBytes {
    let ring_slots = ring_bytes / JOURNAL_RECORD_BYTES;
    DeviceOffsetInBytes(
        JOURNAL_RING_START_SLOT * SLOT_BYTES + ((counter - 1) % ring_slots) * JOURNAL_RECORD_BYTES,
    )
}
```

### 可达的历史（两个崩溃点，零故障）

发布顺序是单元 → 记录 → 根（D16（发布语义） 已定项 7）。

1. mkfs、取号 1、暖机 txg 1/2、A = 第一个事务 txg 3（jsn 3，根已落盘）。
2. B = 一次覆盖写 txg 4（jsn 4）。**崩溃点 ①**：B 的记录写已落盘（提交标记齐全）、B 的根写还没落盘。
3. 管理员重开，带外发起回退到 A `(1, 3)`——A 是这时的最新根，按每种读法都在候选集里。
4. `mount_rollback` 算出 `next_counter = R_old 的 jsn 3 + 1 = 4`，回退那次发布的记录写进 jsn 4 那个槽，**盖掉 B 那条**。**崩溃点 ②**：这条记录已落盘、回退那次发布的根还没落盘（正是条款说「都不生效」的那个窗口）。

副本上的两条流（`x2_the_p1_record_slot_overwrite_destroys_a_committed_publish_in_the_window_the_clause_calls_equivalent`，原样输出）：

```
甲 记录键 [(InstanceGeneration(1), 1), (InstanceGeneration(1), 2), (InstanceGeneration(1), 3), (InstanceGeneration(1), 4)]
甲 恢复 Some((1, 4)) / JournalScanReport { valid_records: 4, above_water: 1, prefix_applied: 1, verification_passed: 1, verification_failed: 0, maximum_applied_transaction: 2 }
乙 回退那次发布 txg [5, 6, 7]，jsn 4
乙 记录键 [(InstanceGeneration(1), 1), (InstanceGeneration(1), 2), (InstanceGeneration(1), 3), (InstanceGeneration(2), 4), (InstanceGeneration(2), 5), (InstanceGeneration(2), 6)]
乙 恢复 Some((1, 3)) / JournalScanReport { valid_records: 6, above_water: 0, prefix_applied: 0, verification_passed: 0, verification_failed: 0, maximum_applied_transaction: 0 }
```

甲 = 不发起回退：恢复择 A 的根、施加 B 那条、施加之后的根是 `(1, 4)`，读回 B 的内容。
乙 = 同一个前缀上发起回退再崩在窗口里：`(1, 4)` 那条记录在盘上已经不存在，`above_water = 0`、`prefix_applied = 0`，读回的是 A 的内容。**施加的记录不同，已发布谓词的判定也不同**——条款那一句在这条历史上是假的。

副本上的实现细节：崩溃点 ① 我用「把 txg 4 的根槽翻一个字节」实现，与「那次根写没落盘」在 `choose_root` / `readable_roots` 看到的字节上等价（`RootRecord::parse_slot` 不通过即跳过）；崩溃点 ② 我让回退那次发布的三条根（txg 5、6、7）都读不出。真正的崩溃点比这更早、更便宜：**只要 D 的记录写落了盘、D 的根写没落**，B 那条记录就已经没了，后面两次暖机的记录写还没发生。多出来的那两条记录只会让乙这一格更接近合法，不会让它更坏。

### 为什么不是「管理员本来就要丢掉 B」

管理员发的是「回退到 A」，而那次回退**没有生效**：它的根一条都没落盘，条款逐字说这时候一切与没发起回退时相同，D16（发布语义） 已定项 8 的暖机也规定本实例的根覆盖两块盘之前不向管理员确认回退。所以下一次挂载应当把 B 恢复出来、由管理员重新决定；实现给出的是「回退没确认，但 B 已经永久没了」——一次没生效的操作留下了不可逆的效果，这正是那一句要排除的东西。B 的记录带提交标记、已落盘，按 D23（journal 的角色与格式） 已定项 14 的重放规则它是一次已完成的发布。

## X4　前缀第五条的谓词在任何可达历史上都取不到真

### 被判的那一句

`.claude/kb/decisions/23-journal的角色与格式.md:1225-1226`（整行抄）：

> **所选根的实例在实例表里有回退行时，该实例的记录只施加到回退行的 W 为止**（C113（扫描重建时多版单元的现行版本判定无输入） 定案 P2，2026-09-05：

```rust
        .rows
        .iter()
        .find(|row| row.instance == root.instance && row.is_rollback)
        .map(|row| row.applied_transaction_high_water)

```

唯一的调用点是 `crates/singlefs-core/src/mount.rs:465`（`mount_writable` 里那一句 `rollback_high_water_of_root(&*devices, &chosen_root)`）；`mount_rollback` 自己不调它（它把 `JournalScanReport` 直接写成一条不施加，`mount.rs:576-584`）。全仓只有这一处：

### 为什么取不到真

谓词要求同一条根上两件事同时成立：`row.is_rollback` 且 `row.instance == root.instance`。而回退行写的是**被退回的那个实例** r_old 那一行（`mount.rs:356-362` 用 `start.previous_row`，回退时 `previous_row.instance = target.instance`、`is_rollback = true`，`mount.rs:613-618`），这张表由**新实例**的第一次发布重写（`InstanceTablePlan::Rewrite`，`mount.rs:384`），所以带回退行的表只挂在实例号 > r_old 的根下面。实例号只增不减（`acquire_instance`），r_old 那个实例此后一条根都不会再写。两件事因此互斥。

带回退行 `(1, 3, 0, true)` 的两条根都是实例 3 的，而 C113 P2 要保护的那次恢复正是**落在 R_old（实例 1 的 (1, 3)）上**的——它自己那张表是回退之前的，一行都没有。

### 条款字面「所选根的实例在实例表里有回退行时」指哪张表

三种读法，逐个走一遍：

| 读法 | 这一轮的判定 |
|---|---|
| 甲：所选根自己指着的那张（代码取的） | 谓词恒假，第五条是死条款 |
| 乙：最新根指着的那张（与候选集 `mount.rs:545` 同一个读法） | 第五条要用的时候恰好用不上——恢复落到 R_old 上，正是因为带回退行的那些根都读不出，那时最新根就是 R_old 自己或某条被抛弃的根，表里同样没有回退行 |
| 丙：环里任一可读根指着的表的并 | 唯一能让第五条活起来的读法，代价是恢复要多读若干个实例表单元，且要定「两张表说不同的话时听谁的」 |

⇒ 条款这一句在实现层面还没有落点，`.claude/kb/checks-owed.md` C124（回退行与重放下界没有会红的检查） 那一笔按现在的实现**永远不会被还清**：无论怎么写检查，被检的谓词都取不到真。要么按丙改实现并改条款，要么承认第五条已经被别的机制（前缀不跨实例边界 + P1 盖槽）替代，把它从六条口径里撤掉——那是一次条款修订，不是实现修订。

### 今天真正在拦「把被抛弃的时间线整段重放回来」的是谁

不是第五条，是两样：

1. `crates/singlefs-core/src/recovery.rs:726-731`：候选记录先按 `record.instance == root.instance` 过滤（前缀不跨实例边界）——落在 R_old 上时只可能重放 r_old 自己的记录。
2. P1 盖掉 `R_old.jsn + 1` 那个槽（X2 那一节）——这正好是 r_old 时间线上紧接 R_old 的那条，链首一断，断号即止接管。

第 2 条是**副作用**，不是设计；它成立的条件是「回退那次发布的记录写落了盘」。回退崩在记录写之前时它不成立，但那时回退行也没落盘，重放 B 是对的，所以不出事。X8 那一节给出它不成立的另一种形态。

## X8　P1 让「所选根自己那条记录读不出」零故障发生，无锚点规则接着把被抛弃的时间线重放回来

### 被判的那一段（上一轮 X1 的改法，这一轮的 S12）

### 打中：回退之后，没有任何故障，两条根一起失去锚点

P1 把 `R_old.jsn + 1` 起的槽让给新实例，被盖掉的那几条记录，正是某些**还留在根环里的根自己那条**。副本实测（`x8_...`，固定脚本到 D，零故障，原样输出）：

```

零故障就没有锚点的根 [(0, 0), (1, 4), (2, 5)]
从 (2, 5) 重放：第五条的 W = None，施加 3 条，施加之后的根 (实例 2, txg 8)
```

`(1, 4)`（B 的根）与 `(2, 5)`（实例 2 写行那次发布的根）都还在环里、都读得出，而它们自己那条记录已经被实例 3 的 jsn 4 / jsn 5 盖掉。`(0, 0)` 是 mkfs 的根，本来就没有记录，不算新增。

选到 `(2, 5)` 之后，无锚点规则认 `checkpoint_txg = 5 + 1 = 6` 那条，于是 jsn 6/7/8 三条**被抛弃的实例 2 的记录**顺链全部施加，施加之后的根是 `(2, 8)` —— 被回退抛弃的那段时间线整段重放回来，而 `rollback_high_water_of_root` 给的是 `None`（X4：它给不出别的）。这正是 `.claude/kb/decisions/23-journal的角色与格式.md:1225-1226` 写下第五条要拦的那件事，逐字是「管理员的回退被静默撤销」。

**代价**：要让恢复择到 `(2, 5)`，比它新的五条根 `(2, 6)`、`(2, 7)`、`(2, 8)`、`(3, 9)`、`(3, 10)` 都得读不出（五个根槽）。这比步 4 用例自己那条必红（四个根槽改坏就退到 C）贵，所以它不是最省的那条路；它值钱的地方在于说明**无锚点这条分支的入口变了**：从「一次两份都撕的故障」变成「任何一次回退都会造出两条没有锚点的根」，而这个入口既没有用例、也没有变异行盯着。`crates/mutations.tsv` 第 45 行（步 3 三方第一轮那条改法的变异）必红的测试是 `torn_anchor_record_lets_the_chain_start_only_at_the_next_checkpoint_txg`——撕掉记录那一格；第 36 行（步 4：前缀第五条不判）必红的是 `the_rollback_row_caps_the_prefix_of_the_chosen_roots_instance_at_its_high_water`，而那条用例是**直接把 W 喂给 `replay_journal`** 的（`second_transaction_step_four_rollback.rs:381-388`），一次都没走 `rollback_high_water_of_root`。⇒ 「记录被盖 ⇒ 无锚点」与「谓词取不到真」这两格，四十五行变异表里一条都没有。

### 顺带答 X8 提示里的两问

- 「所选根 (1, 4)（B）自己那条 jsn 4 已被实例 3 的 jsn 4 盖掉 ⇒ 无锚点 ⇒ 认 txg 5 的记录——实例 2 的 txg 5 记录（写行）实例不同、被候选过滤掉了」：**是这样**，`recovery.rs:726-731` 的 `record.instance == root.instance` 先把它滤掉了，所以 `(1, 4)` 这条无锚点的根什么都接不上。危险的是 `(2, 5)` 那条——同实例、txg 连续，一接就是三条。
- 「有没有同实例、txg = 根 + 1、但不是紧接着那条的形态」：第一版没有。一次发布一条记录、txg 与 jsn 在一个实例内同步加一（`transaction.rs` 的 `PublishPlan { txg, counter }` 由调用方逐次加一给出），所以同实例里「txg 最小的那条」就是「jsn 最小的那条」。⇒ 这条规则今天等价于「txg 不许有洞」。**D23（journal 的角色与格式） 已定项 14 第六条口径（一次发布多条记录）落地那天它就不等价了**：那时同一次发布的几条记录 txg 相同，`chain_start_txg_without_anchor` 会同时匹配其中任意一条，而 `above` 按 `(instance, counter)` 排序取第一条——要么改成「txg = 根 + 1 且 jsn 是这一批里最小的」，要么给记录加一个「这次发布的第几条」的字段。这一条现在没有欠账行盯着。

## X1　候选集与回退目标：两处打中

### 甲　最新根自己是被抛弃时间线的根时，候选集按那张旧表判，被抛弃的根被接受

被判的那一句（`.claude/kb/decisions/23-journal的角色与格式.md:1209`，整行抄）：

> 候选集 = 根环里按实例表判仍然有效、且 txg ≥ F_生效（2026-09-13，D16（发布语义） 已定项 1）的根，(i, T) 可选 ⟺ 实例表无 i 的行，或有行 (i, Ti, Wi) 且 T ≤ Ti（被抛弃时间线的根一条都选不中）

实现取的是**最新根**指着的那张表（`crates/singlefs-core/src/mount.rs:545-546`）：

```rust
    let newest_table = instance_table_of_root(&*devices, &newest_root)
        .ok_or(MountError::InstanceTableMalformed)?;
```

而 `newest_root` 是 `choose_root`（`mount.rs:529`），按 `(checkpoint_txg, instance)` 取最大（`recovery.rs:295-296`）——它**不看实例表**。于是回退实例的根全读不出时，最新根就是一条被抛弃的根，它指着回退之前那张表。

历史：固定脚本到 C，回退到 A `(1, 3)` ⇒ 实例 3 的两条根 txg 9、10；这两条根都读不出（步 4 那条必红用例自己造的正是这个状态，`second_transaction_step_four_rollback.rs:326-329` 改坏 txg 9/10/11/12 四个根槽）。副本实测（`x1_with_the_rollback_instances_roots_unreadable_the_candidate_set_accepts_abandoned_roots`，原样输出）：

```
回退实例的根 [9, 10] 都读不出之后，最新根 = (实例 2, txg 8)
退到被抛弃的根 (实例 1, txg 4) 被拒：RollbackRecordUnreadable(RollbackTarget { instance: InstanceGeneration(1), checkpoint_txg: CheckpointTxg(4) })（不是候选集拒的）
退到被抛弃的根 (实例 2, txg 6) 被接受：新实例 4，第一个新根 txg 11，读回的版本 (实例 2, txg 6)
退到被抛弃的根 (实例 2, txg 7) 被拒：RollbackTargetNotACandidate { …reason: "实例表里那个实例的行 T 更小：这是被抛弃时间线的根" }（不是候选集拒的）
退到被抛弃的根 (实例 2, txg 8) 被拒：RollbackTargetNotACandidate { …reason: "实例表里那个实例的行 T 更小：这是被抛弃时间线的根" }（不是候选集拒的）
```

读法：`(2, 6)` 被接受，恢复出来的版本就是被回退抛弃的实例 2 那一版 —— 一次已确认的回退（暖机已让实例 3 的根覆盖两块盘）被第二次回退原路撤销，而条款逐字说被抛弃时间线的根一条都选不中。`(1, 4)` 是被 `RollbackRecordUnreadable` 拒的（X2 那一节：它的记录被 P1 盖了），候选集这一关它过了。`(2, 7)`、`(2, 8)` 那两行是我这条用例的副作用：同一个 `pool` 上 `(2, 6)` 那次回退已经落盘，新表里写了 `(2, 6, 0, 回退位)`，所以后两个目标被**新的**回退行拒——不是候选集在第一时间拒的。要单独复现那两格，把用例里的循环拆成各自新建一个 pool 即可（我没跑，时间）。

代价：两个根槽读不出。**这不是新增的故障假设**——步 4 自己那条必红用例已经把四个根槽改坏了，X1 甲 只是在那个状态上再发一条管理员命令。

### 乙　最新根的实例表单元读不出时，一条按每种读法都在候选集里的目标也被拒，而这时回退是唯一的退路

`mount.rs:545-546` 那个 `.ok_or(MountError::InstanceTableMalformed)?` 在候选集判定**之前**、在读目标根自己那张表之前。副本实测（`x1_an_unreadable_newest_instance_table_refuses_a_target_that_is_in_the_candidate_set`，原样输出）：

```
改坏的实例表落点 [(0, 50304), (1, 50304)]
回退到 (1, 3) 的结果：Some(InstanceTableMalformed)
同一个镜像上普通可写挂载的结果：Some(Recovery(UnitUnreadable { slot: SlotNumber(50304) }))
```

目标 `(1, 3)` 是 A 的根：它在环里、txg 3 ≥ F = 0、按回退之前那张表也没有 i 的行；它自己指着的实例表单元完好（那是 mkfs 那片，落点不同）。两份副本都坏的是**最新根**那一版的实例表。结果是：正常挂载走不通（本来就该走不通），而**为这种局面准备的回退也走不通**。D23（journal 的角色与格式） 那一段把回退定义成「回退 = 一次恢复」，恢复要能绕开坏掉的最新版本才有意义；实现把最新根那一版的一个单元变成了回退的前置条件。

判据表 X1 的触发观测逐字是「一段历史让不该退到的根被退到，或该退到的被拒」——甲是前半句，乙是后半句。

改法（**只在我的模型上量过、被攻过零轮**）：候选集判定改读**目标根自己指着的那张表**加上「环里比目标新的每条可读根的表」的并；退一步的最小改动是把 `instance_table_of_root(newest_root)` 读不出时**降级**成「按目标根自己的表判，并在返回值里标明候选集是降级判的」，而不是整条路拒掉。两种都要先答 X4 那一节列的「指哪张表」。

## X3　影子账只住内存、只在回退那一次挂载里算：普通重开一次，隔离整批消失

### 被判的那一句

`.claude/kb/decisions/23-journal的角色与格式.md:1209`（整行抄）：

> **被抛弃时间线的根离开根环之前，它们引用的单元不许重新分配也不许抹头——分配器多查环里每一个可读根的账、只隔离其中**只被被抛弃根引用**的槽——查账的集合 2026-09-16 用户定案取窄读法：按主语「被抛弃时间线的根」读，仍被有效根引用的槽不在其内；

两句要分开读：**「不许重新分配」的期限是「离开根环之前」**；**「分配器多查环里每一个可读根的账」是机制**，条款没有把它限定在回退那一次挂载里。

实现把隔离整个放在 `mount_rollback` 里（`crates/singlefs-core/src/mount.rs:589-612`），`mount_writable` 一次都不查别的根的账（`mount.rs:452-513` 里没有 `allocation_records_under_root`）。隔离位图只住内存（`allocator.rs` 的 `isolated`，不进已分配 / defer / 空闲），`MountOutput.isolated_slots_per_device` 的文档注释自己写着「可写挂载恒 0」（`mount.rs:95-96`）。

### 后果落在哪

这一格的后果与 `.claude/kb/checks-owed.md` C314（回退可以复用被抛弃的根引用的单元） 的第二格同形：`choose_root` 不看候选集，回退实例与之后各实例的根都读不出时它会挑中 `(2, 8)`，而 `(2, 8)` 引用的数据单元已经被覆盖。步 4 那条 `ShadowLedger::Off` 的必红用例造的正是这个（它靠一个只供测试的开关强制进入），而重开这条路**不需要那个开关**，产品路径上就走得到。

### 顺带答 X3 提示里的几问

- 「被抛弃根引用而 R_old 也引用的槽（不隔离，对吗）」：按 2026-09-16 用户定案的窄读法，不隔离是对的；`mount.rs:590-602` 用 `own_slots`（R_old 的账）做差，与那句话逐字相符。但窄读法的射程只到「仍被**有效根**引用」，而代码写的是「仍被 **R_old** 引用」——比 R_old 更老的有效根（`(1, 1)`、`(1, 2)`、mkfs 的 `(0, 0)`，它们都在候选集里）引用而 R_old 不引用的槽，会被当成被抛弃根独占量隔离掉。方向是偏保守（多隔离），不会让槽被发出去，所以我不记它为打中，只记成口径与条款差半格。
- 「被抛弃根之间共享的槽只隔离一次」：`mount.rs:602` 的 `!isolated.insert(key)` 去重，跨度按第一条记录的 `span_slots` 算。**同一个槽在两条被抛弃根的账里跨度不同时**（一条记 2 槽、一条记 1 槽），只按先遇到的那条隔离，另一条多出来的那一槽不隔离。这条几何上造不出（覆盖写整片换、跨度不变），我没打中，列进「没打中的形状」。
- 「已释放但仍在被抛弃根 defer 队列里的槽算不算引用」：`allocation_records_under_root`（`recovery.rs:405-409`）把分配记录树根节点里的条目**全部**返回，不看 `is_released`，所以已释放的也算引用、也被隔离。方向同样偏保守。
- 「`ShadowLedger::Off` 两格里另一格（回退那次发布崩在单元写完之后、记录之前，恢复挂上 C 的根）」：**我没打中，也没跑**。步 4 那条用例只钉了回退之后第四、五次发布的数据落点（50182 / 50184），没钉 D 自己那几个提交内生块落在哪；我时间不够去算 D 的开放段 bump 落点。列进「没打中的形状」。

## 这条腿自己的限度

1. **我造的崩溃点是用「把根槽翻一个字节」实现的，不是把写流截断。** 两者在 `RootRecord::parse_slot` / `choose_root` / `readable_roots` 看到的字节上等价（都不通过自证），但它们在**录制流**里不等价：真崩溃点上那几次写根本不存在，我这里是写了再改坏。X2 那一格的结论只用到「这几条根读不出」，不用到录制流，所以我认为它站得住；X1 甲 同理。要把它做成入库的检查，得走层 0 的崩溃点枚举，不是我这种手工镜像。

3. **X1 甲 那条用例是有状态的**：同一个 `pool` 上连着试四个目标，第一次成功之后的三次看到的是新状态。`(2, 6)` 那一行不受影响（它是第一个成功的），后三行的理由我在正文里标了。
4. **我没跑门禁的任何阶段**，也没在原仓编译过。原仓只读：我只新建了报告与模型目录两处，`crates/` 一个字节没动。
5. **X5、X6、X7、X9、X10 我一格都没判。** X6 那一格我在「没打中的形状」里记了一处看到的东西（`newest_root.rollback_floor` 与 `effective_rollback_floor` 两个 F），那是线索不是判决，归本地攻方与主 agent。
