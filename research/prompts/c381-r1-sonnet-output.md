# c381-r1 云端辩方（Sonnet）报告：K6——甲「一律退回」能不能读成不矛盾

任务范围：只答 K6，不判 K1–K5，不替攻方找反例。K6 原文：「今天的『一律退回』能不能读成不矛盾：有没有一种逐字有据的读法，按它攻方 Z2-c 那段历史不是缺陷（例如条款允许失败之后不许在同一次挂载里接着发布，而调用方违反了它）」。

方法：先现查代码与 kb 原文的行号（`grep -nF`，命中才写引文），构造最强的反对（甲确有矛盾），再逐条试辩护，辩不住就写清楚在哪一步垮。

## 一、最强的反对（steelman，站在攻方一边）

四件已核实的事实拼在一起：

1. `crates/singlefs-core/src/transaction.rs:1259-1260`：`if outcome.is_err() { *allocator = allocator_before_this_publish; }`——失败（含 S3：根槽 FUA 成功之后、超级块槽轮换失败）时把整个分配器换回发布前的克隆，不分失败落在哪一步。docstring（1223 行）原文「准入之后任何一步失败，分配器退回到进来时的样子——这次发布没有成立」把 S3 也一并收进「没有成立」。
2. `.claude/kb/invariants.md:53`（I-7.4）原文：「回退候选集里每一个根（按实例表判仍然有效 ∧ txg ≥ F_生效，D23（journal 的角色与格式） 已定项 14）所引用的块，其物理范围均未被重新分配给其他对象、也未被清扫抹头。」候选集成员资格只看「实例表判仍然有效」与「txg ≥ F_生效」，不看「调用方内存里怎么认为这次发布」。C 的根（txg 5）在 Z2-c 历史里满足这两条（同一实例、无回退行、F 未抬），字面上就在候选集里。I-7.4 已实现且被 checker 判定为不变量（`.claude/kb/invariants.md:12` 「已实现（2026-09-17……层 0 每个崩溃状态都判）」），不是设计文档里的意向句，是可执行、可判红的量。
3. `.claude/kb/decisions/22-单元原子性怎么合成.md:233`（已定项 16）原文：超级块槽「每盘恒 2 个槽……择槽取校验和过且世代号最大的」——按盘独立择槽、自证世代号，本来就设计成允许两盘状态不一致（否则不需要每盘自己的世代号）。`crates/singlefs-core/src/transaction.rs:172-174` 的 `RotateSuperblockSlots` 逐盘调用 `write_superblock_slot`，盘 0 成功、盘 1 失败时函数仍然整体返回 `Err`——把一个格式本身容忍的「盘间暂时不一致」翻译成「这次发布整体没有发生」。
4. 把 1–3 接起来：分配器换回克隆 ⇒ C 占用的块在内存里立刻重新可分配；调用方「写入口照旧」⇒ 立刻能发下一次；下一次分配器从同一个游标起步 ⇒ 落到 C 刚用过的槽（Z2-c 历史里是 50257）；C 的根仍在候选集里、仍被 checker 认定为有效——I-7.4 在这一步被现实违反，`z2.log` 的 checker 输出五条红、重开报 `Recovery(UnitUnreadable)` 就是这条违反的具体后果。

这条链子里没有一步依赖对「这次发布算不算成立」的主观解读——I-7.4 的候选集定义、超级块每盘独立择槽的机制、分配器换回的代码逻辑，三者都是可以逐字核对的既有条款/既有代码，接起来就是现实违反。

## 二、逐条试辩护

**辩护 A——「『没有成立』只是分配器记账口径，不涉及恢复选根，两边各管各的，字面不矛盾」。**
现查：I-7.4（`invariants.md:53`）与「有效」的定义（C113 定案 P3，同一行内引用）都只看盘上的实例表与 txg，不引用「调用方内存里的分配器状态」这个量。如果 I-7.4 的保护范围与调用方的记账口径真的互不相干，那么分配器把 C 占用的块标回「空闲」这个动作本身就必须不会导致这些块被写——但 Z2-c 历史里它确实导致了（E 落到了 50257）。「两边各管各的」只有在分配器换回之后这些块**事实上不会被写**时才成立；一旦「写入口照旧」允许立即再发布，两边就会在同一批物理块上打架。**站不住**：这条辩护要求同时接受「分配器可以认为这些块空闲」与「这些块仍然是不变量保护对象」，而不许把前者转成对后者的破坏——代码里没有任何东西在两者之间设一道闸（没有扣住、没有另编号），辩护等于要求一个在代码里不存在的隔离层。

**辩护 B——「调用方在同一次挂载里换一条路重新发布，违反了某条已定的『失败之后不许接着发布』的条款，缺陷该记在调用方，不记在甲」。**
现查：`grep -rn "不许再发布\|不许接着发布\|不许继续发布\|此后不许发布\|失败之后.*不许.*发布\|发布失败.*不许" .claude/kb/` 全仓唯一命中是 C381 自己那一行（`checks-owed.md:355`），而它原文把这一点写成**尚未回答的问题**：「失败之后这个写入口还许不许接着发布」——这正是本轮要定的东西，不是已有条款。`.claude/kb/decisions/23-journal的角色与格式.md:691`（已定项 14）里唯一与「失败之后怎么走」相关的既有规则是**根槽写失败**（S2）的处置（探针写 ⇒ 实例切换或转只读、「根槽写失败重发时 checkpoint_txg 推进一格再发」），管的是根槽本身没写成的情形，字面不覆盖「根槽已经 FUA、只有超级块槽后续失败」这一格（S3）。**站不住**：仓里没有这条禁令，K6 给的例句本身在字面上找不到出处；此外 C381 行原文把这一问列为「待定」，说明连主 agent 自己此前也确认了它没有既定答案。

**辩护 C——「真正的缺陷在恢复选根逻辑：不该选中一个超级块两盘不一致的根，选错的是恢复，不是甲的分配器退回」。**
现查：根的选择依据 I-7.2（`invariants.md:51`）「S 中代号最大者……递归校验，能走完全部权威态……无一处失配」与根环放置公式（D22 已定项 16，「区域内槽位 = (txg div R) mod S，无状态，只由 txg 与 (R,S) 决定」），两处都没有把「超级块两盘是否一致」列为根有效性的判据；超级块本身是按盘独立、自证世代号的旁路结构（已定项 16 原文见上）。也就是说，恢复选中 C 的根（txg 5）是**按已定条款正常运作**的结果，不是恢复逻辑的漏判。**站不住**：把缺陷推给恢复选根，需要一条「根有效性依赖超级块跨盘一致」的条款，仓里没有这条，现查结果是恢复做的正是条款要求它做的事。

**辩护 D——「乙/丙/丁在 S3 也一样会踩这个坑，所以这不是甲独有的矛盾，只是这一格本来就难」（是否『同样打中别的臂』）。**
现查候选表（背景材料第 50–56 行）：乙 S3「不退回；这次发布已成立，调用方拿到这次的版本，超级块槽下一次发布时再转」——分配器不换回，C 占用的块继续标记为已分配，E 的游标不会落到 50257，I-7.4 不会被这条路径破坏。丙 S3「同 S2」＝「写入口作废：这次挂载里不许再发布，调用方要重开」——挡住的正是「同一个写入口立刻发下一次」这一步，Z2-c 历史里的第 2 步在丙下不会发生。丁 S3「同 S2」＝「退回，但这次占过的槽扣住（不许分配），直到一个 txg 更大的根落盘」——分配器虽然换回，但 C 占过的槽被单独扣住，E 的游标不会分到 50257。**站不住**：三条替代臂各用不同机制（不退回 / 挡住写入口 / 扣槽）避开了这条具体路径，Z2-c 打中的正是「分配器整体退回 + 写入口毫无阻拦地照旧」这个**组合**，而这个组合是甲独有的（其余三臂都在这两者之一上做了区隔）。这不是「这一格本来就没人能躲开」，是甲在这一格没有设防。

## 四、什么现象会推翻以上判定

- 若在仓里找到一条已定条款，明文规定「超级块槽任一盘写失败即整次发布视为未持久，含根槽已 FUA 的情形」（即显式把超级块跨盘一致性并入根有效性判据），辩护 C 成立，缺陷会转移到恢复选根逻辑（它没有去检查这条新条款）。目前 grep 与已读的 D22 已定项 2 / 16、I-7.2 全文都没有这一句。
- 若在仓里找到一条已定条款明文禁止调用方在一次发布失败之后于同一次挂载里继续发布，辩护 B 成立。目前 checks-owed C381 自己把这一点列为待定，未找到反例。
- 若能证明分配器换回之后、下一次发布的落点分配存在某种未被我看到的「避让上一次失败发布所占槽位」的机制（使得 E 实际上不会分到 50257），辩护 A 的具体后果不成立；但攻方 Z2-c 的 checker 输出（`z2.log`，五条红、`Recovery(UnitUnreadable { slot: SlotNumber(50257) })`）已是现查到的实测结果，要推翻它需要一份能复现的反例记录，不是推理。
