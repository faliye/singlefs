1a. The attack claims that under SERIAL, a write request that requires raising F to succeed is rejected at gate 1 because gate 1's available calculation includes defer_pending_release unconditionally, and gate 2 (raise F path) is never entered for such requests. The fact that gate 1 subtracts defer_pending_release unconditionally is established by F2 (available includes defer_pending_release as a term) and F3 (defer_pending_release is defined as maintained statistic item 5, consumed by allocation and admission). The ordering of gates (gate 1 first, then gate 2) is established by F1 ("two gates connected in series: first pass D28's available >= requested, then pass D16's raise the floor logic") and the SERIAL definition ("if the first gate does not pass, the request is rejected outright and gate 2 is never entered for that attempt"). Refuted if: F1 does not describe the gates as connected in series with gate 1 preceding gate 2, or F2 does not include defer_pending_release in the available calculation.

1b. Under SERIAL, user visible df equals F2's full available quantity. F5 states "df reports available (per D3 item 9 clause 1)" and the probe testing shows that subtracting mount_period_commitment (part of F2's formula) eliminates false ENOSPC, confirming df = F2's available. F6 clause 1 says "whenever df reports free space >= s, writing s bytes must succeed", meaning if df < s, ENOSPC is permitted. For a request needing F raise, gate 1 fails (F2's available < s), so df < s, and ENOSPC is allowed per F6 clause 1. This chain is: F2 defines available, F5 equates df to F2's available, F6 clause 1 permits ENOSPC when df < s. Refuted if: df does not equal F2's full available quantity, or F5's "df reports available" is interpreted as df excluding mount_period_commitment.

1c. Yes, there is a mechanism. A different admission attempt (that passes gate 1) can trigger gate 2 (F4's admission row), which pushes empty publishes to raise F. F8 shows reclaim_floor is called when F is raised (line 367), and reclaim_released_up_to reclaims records, which decrements defer_pending_release (via mark_reclaimed, F8 lines 212-233). Since F3 states defer_pending_release is part of gate 1's available calculation, this reduces defer_pending_release, increasing available for subsequent requests. This mechanism does not assume gate 1 is rejudged within the same admission attempt's retry loop (which would be SERIAL_RECHECK), but relies on other requests triggering gate 2. Refuted if: raising F does not reduce defer_pending_release, or gate 2 cannot be triggered by other admission attempts that pass gate 1.

1d. The E139 excess in F6's warning does not change the answer to 1c. F6 states E139 "exceeds the bound of 3" under the adopted mechanism (D16 item 1), which includes its own raise F logic. F4's skip of raise F push for write row publish only affects the first publish of a new instance, but E139's failures occur across multiple windows (up to window 6), showing the bound is violated regardless of SERIAL or other readings. This fact confirms the requirement fails in practice for the adopted mechanism, so SERIAL's potential failure is not uniquely worse. Refuted if: E139's failures are specific to SERIAL and not the adopted mechanism, or F4's skip of raise F push prevents the mechanism described in 1c.
