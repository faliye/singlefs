## D17 (実装階層とサードパーティパイプライン) —— 確定

[中文](17-实现分层与第三方管道.md) · [English](17-implementation-layering-third-party-pipeline.en.md) · **日本語**

D17 (実装階層とサードパーティパイプライン) は本プロジェクトとサードパーティパイプラインの間の境界を管轄する：ウエストラインをどこに引くか、どちら側が本プロジェクトの独占となるか、「データインタフェース」とはどのバイト区間か、障害モデルの軸は誰が決定権を持つか、構造等価類をどう数えるか、ならびに第1版の実行媒体と1つのパイプラインが返済すべき債務。対象外とする事項：メディア系統の分岐数、誰が開設した系統を誰が保守するかは D12 (対象メディア)；クラッシュ状態集合と `CommitStep` の列挙は D13 (検証ルート)；ユニット原子性の合成手法は D20 (荷重受け面: ユニットの原子性と自己完結性) および D22 (ユニット原子性の合成手法)；フォーマット凍結の階層分けは D15 (フォーマット凍結ポリシー) に属する。

#### 確定項目 1：単一障害モデル、コア層による合成

**確定内容**：コア層が単一の障害モデルを規定——セクタ 512 バイト原子性、書き込みはセクタ単位まで断裂可能、バリア間は並べ替え可能（D20 (荷重受け面: ユニットの原子性と自己完結性) 系3の実測計測条件「デバイス側原子幅 512 かつ依存不可」に基づく）、読み出しは位置がずれうる（別の場所にある自己証明の通る内容を読み戻す：ルートリングスロットから読んだルートで、その txg が配置先公式上そのスロットに住むはずのないものは、ルートリングを読むすべての箇所で自己証明不合格として扱う；第 0 世代ルートは mkfs がルートを置くスロットで別に認め、I-7.17 (ルートスロットの位置は txg から算出した位置に等しい) と同じ例外）；パイプライン側による例外宣言を禁止；未達の機能はコア層が合成（読み戻し検証 / 二重書き込み / ログ補填）、合成コストはコア層が負担し、ユーザー課金ではなくパイプライン単位で計上。`REQ_PREFLUSH` / `REQ_FUA` の「バックエンドによる拒否を禁止しブロック層が自前合成する」設計と同形である。

**射程**：この軸の基数は恒常的に 1 であり、等価類数の乗算には関与しない（確定項目 2）。D17 (実装階層とサードパーティパイプライン) 確定項目 1 が定めるのは契約の形態であり、最初のサードパーティパイプラインが現れるまでバイト列は固定されず、C16 (パイプラインが障害モデルの例外を宣言) の前提条件はこれに伴い充足される。「障害原子性幅 / 断裂 / 並べ替え」の既存カバレッジは D13 (検証ルート) 確定項目 4（クラッシュ状態集合）および D20 (荷重受け面: ユニットの原子性と自己完結性) / D22 (ユニット原子性の合成手法) に記載；C6 (ブロック層セマンティクス仮定の記述誤り) が問うのは「本プロジェクトの仮定が正しいか否か」であり、「あるパイプラインの障害モデルが何か」を問うものではなく、両者は異なるセルに属する。否決された候補乙（パイプラインがより強力なモデルを宣言することを許容し宣言ごとにリプレイをディスパッチ）は `CommitStep` 外に軸が1つ増え、ヘビー層のリプレイを宣言ごとにディスパッチするコストを伴う。

**根拠**：

- E129 (io_min 未満の書き込みの実デバイス上での障害形態)：位置確定的な断裂は実デバイス上で再現可能であり、陽性・陰性対照とも明白——「書き込みはセクタ単位まで断裂可能」は防壁を設けるべき現実の挙動であり、単なる演繹ではない。
- 現役の対照群：バックエンドが `-EOPNOTSUPP` を返すことを許容した `REQ_HARDBARRIER` は Linux 2.6.37 で廃止され、バックエンドの拒絶を許さずブロック層自身が合成する `REQ_PREFLUSH` / `REQ_FUA` へ移行し、現在に至るまで 15 年間不変；両者の唯一の差異はバックエンドが「非対応」と表明できるか否かである。
- ユーザー決定（2026-09-13 甲を選択）、原文は変更履歴に記録。
- 読み出しは位置がずれうる：ルートリング三方 3 ラウンドの判定 `research/prompts/m3-close-rootring-r1-main-verification.md` 第 2 節 X1（裸の公式が第 0 世代ルートに突かれ、例外を補った）、`research/prompts/m3-close-rootring-r2-main-verification.md` 第 2 節 Y1（例外を補った後はヒットせず）、`research/prompts/m3-close-rootring-r3-main-verification.md` 第 2 節 C743 (アロケータ再構築が新しい類を記録するとき、ルートがそのスロットに属するかを確かめない) のセル（維持）；ユーザー決定 2026-10-20「ルートリングを読むすべての箇所で受ける」、原文は変更履歴に記録。実験なし：数値は三方レグのレプリカで計測、実験番号なし。

**未済の検査**：C16 (パイプラインが障害モデルの例外を宣言)。

#### 確定項目 2：構造等価類はセグメントシーケンスに基づき分類、現在値 1

**確定内容**：

1. 構造等価類は記録ストリームのセグメントシーケンスに基づき分類する：2つのレイアウト系統が同類 <=> 各ルートスロット書き込みパス（パブリッシュ、空パブリッシュ、mkfs シード、インスタンス切り替え / 管理者ロールバック——D13 (検証ルート) 確定項目 1 に列挙された3種の書き込み者役割 + 空パブリッシュ）について、両系統の記録ストリームのセグメントシーケンスが同型：セグメント境界（バリアおよび FUA 書き込みにより区切られたセグメント、D13 (検証ルート) 確定項目 4）の位置が一致し、各セグメントに出現するステップ種別の**集合**が一致（セグメント全体ゼロクリア / discard / ユニット書き込み / journal レコード書き込み / ルートスロット FUA 書き込み / システム構成スロットその場上書き / バリアの**7種**、標準順序はこの宣言順であり、`crates/singlefs-harness/src/segments.rs` 的 `StepKind` と個別に対応）；ステップごとの反復回数（デバイス数、ユニット数、レプリカ数）はパラメータであり判定基準に含めない（D13 (検証ルート) 確定項目 10）。比較は同一パス役割・系統間でのみ行い、1系統内部の各パス間で相互比較や計数は行わない。種別は「今回がどの I/O 動作か」に基づき分類し、「今回の書き込みがディスクのどの領域に配置されるか」では分類しない：配置先で分類すると「journal リングの全体ゼロクリア」と「journal リングへの順次レコード書き込み」が同一類に分類されてしまい、等価類が判定対象とするセグメント内ステップ種別集合においてこれら2つのコミットプロトコルを区別できなくなるためである。
2. **等価類数 = 開設済み系統の構造等価類数 × 障害モデル数、現在値 1 × 1 = 1、1系統開設ごとに再計算**：障害モデル数は恒常的に 1（確定項目 1、合成が追加するのは順序付けポイントでありステップ種別ではない）、開設済み系統は純 SSD の1系統のみ（D12 (対象メディア) 確定項目 5）。これは D12 (対象メディア) の返済すべき債務第 2 / 3 項（各類ごとにクラッシュポイント再生を1回実行、ゲート壁時計時間が等価類数の倍率で増加）に乗算される。
3. 登録箇所は1箇所のみ：[layout/01-first-txn.md](../layout/01-first-txn.md) VIII；表中のセグメントシーケンスは E142 (新規プールでのファイル作成のドライラン) 成果物の `name=segments` 行から一字一句正確に取得し、**本書ではそれらの数値列を重複記載しない**（重複記載すると第2の登録箇所となってしまい、ゲート doc-registries の segment-registry セルは layout/01-first-txn VIII と成果物のみを突合するため、重複記載された側を一切検証できない）；インスタンス切り替え / 管理者ロールバック（その後のウォームアップを含む）および F 引き上げの空パブリッシュはバイト列化前に予想値を標記し、バイト列化時に同一手法で再検証する。
4. 系統を1つ開設するごとに：当該系統の各ルートスロット書き込みパスを実行し、その `name=segments` 行を当該系統のバイト表に登録、既存の各類とパスごとに比較し、非同型であれば +1。zoned 系統開設時は本書に従って計数し、D22 (ユニット原子性の合成手法) 未定項目 6 乙の回答数には従わない。
5. ゲート = 登録表 + 成果物内の `name=segments` 行（`replay.sh` exact で固定）+ E142 (新規プールでのファイル作成のドライラン) 単体テスト `registered_segment_sequences_match_every_recorded_path`（いずれかのパスにおけるバリアまたは FUA の位置を変更すると赤判定、mkfs 行も含む）。

**射程**：mkfs 自身のクラッシュ状態はクラッシュポイント再生の中に 1 本のストリームしかない：使用済みのディスク上で mkfs をやり直し、mkfs が記録した 27 ステップを列挙する（`.claude/gate.d/stage-inputs.tsv` の `crash-case:make-filesystem-over-a-used-pool-stream`）；それ以外の初期ディスク面とデバイスセマンティクス上の mkfs クラッシュ状態は列挙対象外で（E142 (新規プールでのファイル作成のドライラン) G19）、その側で固定されるのはそのセグメントシーケンスのみ；「現在値 1」は単元集合上の恒等式であり、いかなる判定基準でも 1 となるが、条項の重要性は第 1、4、5 項にある。

**根拠**：

- E142 (新規プールでのファイル作成のドライラン)：`name=segments` の4行が各ルートスロット書き込みパスのセグメント境界とステップ種別をバイト列化し、いずれかのパスでバリアや FUA の位置を変更すると単体テストが赤判定——判定基準が実装に落ちており、登録箇所に出典の唯一性が担保されている。
- 三者判定：第1ラウンド `research/prompts/d17-r1-main-verification.md`（3脚一致で「`CommitStep` メンバー集合による分類」は粗すぎると判定）、第2ラウンド `research/prompts/d17-r2-main-verification.md`（3脚とも候補判定基準下で第2系統を計数できず、指摘された文言とゲートの隙間をすべて確定内容の5項目へ統合）。
- メイン agent 確定（2026-09-13、2ラウンドの三者論証に基づく）、ユーザーの方向付け原文は変更履歴に記録。

**未済の検査**：C8 (ゲート範囲が判定不能)：ゲート壁時計時間に乗算されるのがまさにこの数値であり、その増大を抑止する機構が存在しない。

#### 確定項目 3：適合性テストスイートはソースコード + 判定プログラムを配布

**確定内容**：2種類の要素を配布する：スイートのソースコード、および1つの判定プログラム。コンテナは配布せず、イメージコーパス単体の配布も行わない。サードパーティパイプラインが自己の適合性を証明するには、**同一の判定プログラム**を実行する必要があり、その判定ロジックはブラックボックスではなく**可読なソースコード**とする——これは D13 (検証ルート) 確定項目 7「O2 (独立パーサー + checker) は単項述語であり、単一イメージのみを判定する」と同型である：判定がサードパーティ自身によって再検証可能でなければならず、そうでなければ「適合」が「当方が適合と宣言したから適合」へと形骸化するためである。

**射程**：「判定プログラムと本リポジトリの checker が同一コードか2つの別個のコードか」には回答していない——仮に同一コードとする場合、`.claude/rules/fs-design.md` の「監査側と被監査側で同一コードを使用してはならない」という原則についてここで再度判定を行う必要がある：サードパーティが被監査側、本プロジェクトが監査側であり、checker / ランタイムのペアとは同一の関係性ではないため、結論を単純に借用することはできない；帰属先は確定項目 2 および C8 (ゲート範囲が判定不能) である。イメージコーパスを配布物に含めないのは意図的な選択であり、見落としではない：コーパスはフォーマットの進化に伴い陳腐化するが、ソース + 判定プログラムはバージョンに追従可能であるためである；凍結時点のコーパスを別途配布するか否かは D15 (フォーマット凍結ポリシー) に従って決定する。

**根拠**：

- 実験なし：何をいくつ配布するかは対外コミットメントの形態であり、計測可能な物理量を持たない；それがもたらす成果（判定がサードパーティによって再検証可能であること）は最初のサードパーティパイプラインが現れて初めて計測可能となる。
- ユーザー決定（2026-08-31）、原文は変更履歴に記録。

**未済の検査**：C8 (ゲート範囲が判定不能)。

#### 確定項目 4：エントリポイント = RefFS の操作面

**確定内容**：「エントリポイント」の実行可能な定義は RefFS が提供する——D13 (検証ルート) 確定項目 3「極限まで作り込み、自前で永続化とクラッシュセマンティクスを処理する」に従い、RefFS が fsync の永続性コミットメントを定義する；RefFS は独立したセマンティクス水準の実装とする（kb 条文のみに従って記述し、O1 (インメモリモデル突き合わせ / HashMap 理想ファイルシステム) から拡張せず、実装とクラッシュポイント列挙コードを共有しない）；別途 O3 (独立仕様実行器) は設けない。RefFS は呼び出し側からホワイトリストに登録された入力のみを受領する：各操作の結末（成功、いかなる書き込み前の拒否、書き込み後のエラー報告、同一再送）、クラッシュが何番目の操作内で発生したかとその帰属規則、ロールバック対象が何回目の確認済みパブリッシュか、各リカバリで読み出された内容、明示的パブリッシュポイント。

**射程**：コストとしてセマンティクス水準の RefFS を要する（D13 (検証ルート) 確定項目 3：ディスク上フォーマットを持たず、ユーザーが 2026-10-02 に当該確定項目の解釈を改め、「開発工数がファイルシステムをもう1つ書くのに近い」水準ではなくなった）。否決された候補乙（別途 O3 (独立仕様実行器) を設けて fsync のコミットメント1件のみを定義し、残りを O1 (インメモリモデル突き合わせ / HashMap 理想ファイルシステム) に委ねる案）は D13 (検証ルート) 確定項目 3 の再開設を必要とする。

**根拠**：

- 実験なし：このセルが定めるのは2つの oracle の境界の配置先であり、検証側に位置しディスク上のバイト列を一切変更しないため、計測可能な物理量を持たない。
- ユーザー決定（2026-09-13）、2026-09-08 に再確認された「確定項目 3 の解釈はすでにモデル拡張に当たる」旨をユーザーが条項として確定；原文は変更履歴に記録。
- ユーザー決定（2026-10-02）：RefFS をセマンティクス水準とし、kb に基づき独立実装、単独クレートに分離、ロールバック対象を入力とする方針を確定、原文は変更履歴に記録；「O1 (インメモリモデル突き合わせ / HashMap 理想ファイルシステム) から拡張」の記述をこれに伴い修正。

#### 確定項目 5：第1版は純粋ユーザー空間ライブラリ、マウントせず

**確定内容**：第1版は純粋なユーザー空間 Rust ライブラリであり、ブロックデバイス抽象のみに対してプログラミングを行い、2つのバックエンドを持つ：通常ファイルおよび `O_DIRECT` でオープンした raw デバイス。外部に対しては一連の操作（mkfs、オープン、extent 書き込み、パブリッシュ / fsync、リカバリ）を提供し、クラッシュポイント再生 harness、RefFS 突き合わせ、QEMU 層の負荷バイナリはいずれもこの操作群を直接駆動する。第1版にはマウント機能が存在しない：FUSE は後から追加される薄いアダプタ層であり、ディレクトリと POSIX 面が登場した後に実装する；カーネルモジュールは予見可能な数年間は着手しない。

3種の検証手段はいずれもマウントを必要としない：クラッシュポイント再生が必要とするのはブロックデバイスの3つの基本プリミティブ（書き込み、バリア、FUA 書き込み）を捕捉できることであり、D13 (検証ルート) 確定項目 4 が定めた記録はその層に位置する；RefFS 突き合わせが必要とするのは同一の一連の操作を両側に供給して結果を比較できることであり、ディスクには触れない；QEMU 層が実行するのは `/dev/vda` を消費する静的バイナリである：実験バイナリは musl 静的バイナリ、RocksDB を備えた checker 層の実デバイスバイナリは `x86_64-unknown-linux-gnu` に `+crt-static` を付与して static-pie としてビルドする（[vm-harness.md](../vm-harness.md)）。

**射程**：3箇所の既知の境界条件が存在する。① 記録フックはブロックデバイスインタフェースに配置し、操作 API には配置しない：1回の「パブリッシュ / fsync」内部で複数回のユニット書き込み、2重のバリア、1回の FUA 書き込みが発行されるため、フックを API 層に置くとこれらの中間クラッシュポイントをすべて隠蔽してしまい、D13 (検証ルート) 確定項目 4 の列挙領域はまさにそれら基本プリミティブである => 実装は「1回の API 呼び出しで何回のデバイス水準操作が発行されたか」の読み取り値を提供し、harness が記録件数と照合、不一致時は実行全体を無効化する。② ライブラリは `crates/` 配下に配置すること：ゲートの「Show me test」は `crates/*/src/` 内の実装コードのみを対象とする。③ ディスク上のバイト列は一切変更しないが、媒体の選定にはコストが伴う——カーネル `block/bdev.c` の `system_configuration_set_blocksize` は `PAGE_SIZE` を超えるブロックサイズに対してファイルシステムが `FS_LBS` フラグを保持し、かつカーネルで `CONFIG_TRANSPARENT_HUGEPAGE` が有効であることを要求する；本プロジェクトのユニット 32,768、ノード 16,384 はいずれもマシンの 4,096 を超えるため、カーネルモジュール方式は当該カーネル機能に依存するか、内部でページ未満のバッファリングを自前で行う必要がある；ライブラリおよび FUSE 方式はこの制約を受けない。カーネルモジュールを延期する根拠は D7 (Linux メインラインへのマージ是非) ではない——同条項はメインラインへ投稿しないと述べているのみで、ツリー外モジュールの作成を禁じているわけではない——真の根拠は `.claude/rules/fs-design.md`「まず低速だが正しい経路を作成せよ」であり、大ブロック `system_configuration_set_blocksize` に伴うカーネル制約が加わる。

**根拠**：

- E142 (新規プールでのファイル作成のドライラン)：新規プールでのファイル作成における全固定構造のバイト列は、ブロックデバイス抽象のみに対してプログラミングされたバイナリによって書き出され、`crates/` の実装と領域ごとに完全一致が確認された——マウントせずとも「トランザクションを正しくコミットする」ことが達成可能である。
- 三者対抗（2026-09-03）：順推レッグが確定条項から同一の媒体を演繹し記録フックと `crates/` の2項目を指摘、代替逆推レッグは反例を発見できず、稼働中のカーネル 6.17 ソースを調査して `system_configuration_set_blocksize` の制約を明示；ユーザー決定（2026-09-03）、原文は変更履歴に記録。

**未済の検査**：C8 (ゲート範囲が判定不能)。

#### 確定項目 6：ウエストラインをコミットプロトコル直下に画定

**確定内容**：ウエストラインをコミットプロトコルの直下に引く。メディア種別ごとに独立したパイプラインを1本ずつ保持し（割り当て、配置、レイアウト、インデックスチューニング、ノードサイズ、キャッシュ、デバイス処理をすべて個別に実装し、サードパーティが独自に持ち込むことも許容）；一方で**トランザクションの抽象状態遷移機械、コミットステップ集合、クラッシュセマンティクスはウエストライン以上に残し、本プロジェクトが独占する**。

**プロトコルは本プロジェクトに帰属する**：あるパイプラインが新規の構造的コミットステップを導入する場合、本リポジトリの共有列挙型（D13 (検証ルート) 確定項目 10 の `CommitStep`）に対して diff を提出しなければならず、自己のブラックボックス内で独自に考案することは禁止する。

**射程**：ウエストラインが拘束するのは構造であり、「バイト列が完全に一致するディスク書き込みコード」ではない——メディアごとに別個の実装パイプラインを保持することは許容されるが、状態機械を迂回する第2のパブリッシュパスは許容されない（`.claude/rules/fs-design.md`「単一のトランザクション層、全構造で共有」）。現役のテンプレートを踏襲しても境界が自律的に維持されるわけではない：規律ある設計の `iomap` であっても、`iomap.h` 内の `validity_cookie` は共有層がバックエンドのトランザクションによるマッピング無効化時点を感知できないため、ファイルシステムに構造体へのシーケンス番号埋め込みを要求せざるを得なかった。ウエストライン以上のバイト区間は凍結第1層に属し、他の層よりも厳格に保持される（確定項目 7）。

**根拠**：

- 実験なし：ウエストラインをどこに引くかは分業の形態であり、計測可能な物理量を持たない；その観測可能なコスト（パイプライン数と等価類数）は確定項目 2 で計数され、浸透防止効果は最初のサードパーティパイプラインが現れて初めて計測可能となる。
- 三者論証（2026-08-27、3脚一致）：逆推レッグがカーネル 6.17 ツリーおよび OpenZFS master を調査したところ、「サードパーティが独自バックエンドを保持 + 契約にクラッシュ整合性セマンティクスを含む + 契約が形骸化していない」を満たす事例は皆無（未発見であり不存在の証明ではないため陰性結論として扱うことは禁止）；プラグイン可能なバックエンドを実現した唯一の商用 COW ファイルシステムは ZFS であるが、そのバックエンドシグネチャにはトランザクショングループ番号が含まれ（`include/sys/vdev_impl.h` の `vdev_asize_func_t`）、バックエンド自身が3本の per-txg ダーティリストを保持し、`vdev_ops` 内の4つのメソッドが「データ移動のみ」の境界線を越脱している；順推レッグは同一のウエストラインを独自に演繹し、より浅い2箇所では zoned の「ルートポインタはその場上書き不可」という構造的事実を収容できず、より深い2箇所では D12 (対象メディア) の既購入事項「サイレントな誤読ではなくマウント拒否」を放棄するか、究極まで推し進めた結果として本ウエストラインへ収束する。
- 現役事例（カーネル 6.17 現地調査）：btrfs の zoned 対応は独立した `zoned.c` モジュールにとどまらず、`btrfs_is_zoned` が 22 ファイル 93 箇所に散在し、うち 5 箇所が `tree-log.c`（トランザクションログパス）、6 箇所が `space-info.c`（ENOSPC 受入）——メディア分岐に境界線を設けない場合、トランザクション層や ENOSPC 受入へ自然に浸透してしまう。

**未済の検査**：C19 (媒体の判定がトランザクション層に漏れ込む)。

#### 確定項目 7：「データインタフェース」= 安全な拒絶に必要な最小バイト集合

**確定内容**：「データインタフェース」とは「同一のバイト列」ではない——D12 (対象メディア) がメディアごとに別個のレイアウトを定めており、ディスク上のバイト列は設計上異なるものである。データインタフェース = **安全な拒絶に必要な最小バイト集合**：見知らぬリーダーが常に確定的な判定（マウント / 読み取り専用マウント / 拒絶の3択）を下すのに十分なフォーマット区間であり、**「誤った前提に基づき適法に見えるバイト列を読み出してしまう」という第4の状態を決して発生させない**こと。

機械検証可能な形態：**パイプラインコードを一切リンクしないプレーンヘッダパーサー**であり、singlefs を自称する任意のバイト列に対して実行し、I-1.1 (ブロックヘッダは論理アドレスを自己記述する) および I-1.4 (ブロックヘッダの fsid が一致) が抽出可能かつ整合的であること + feature bit のエンコーディング + ポインタ内のチェックサム / MAC フィールドの位置と幅をアサートする。

**射程**：I-1.2 (ブロックヘッダ書き込みシーケンスパブリッシュ済み) および I-1.3 (ブロックヘッダのツリー ID が一致) はプレーンヘッダパーサーの射程外とする——I-1.3 は文言通り「それを実際に参照しているツリーと一致すること」を要求し、それを参照する親ノードを先行して特定する必要がある；I-1.2 は文言通り C113 (スキャン再構築時に複数版ユニットの現行バージョン判定に入力がない) 確定方針 P2 の大域発行済み述語に従って判定する必要があり、入力としてインスタンス表の当該行 (i, T_pub, W) とリカバリ選択ルートの txg を必要とする；両者とも第2の入力を必要とし、「任意のバイト列に対して実行する」単項ヘッダ述語には該当しない => O2 (独立パーサー + checker) に帰属し、データインタフェースには含めない。

**根拠**：

- 実験なし：このセルが定めるのは「どのバイト区間を契約とみなすか」であり、判定基準は障害モード（サイレントな誤読ではなく拒絶）であって数値の大小比較ではない；プレーンヘッダパーサーの実装完了後に初めて、任意のバイト列に対する判定率が計測可能となる。
- `.claude/rules/fs-design.md`「『誤用』を『マウント不能』に変換できるか」が本確定内容の判定基準の出典；三者論証（2026-08-27）および 2026-09-14 の絞り込み（I-1.2 および I-1.3 を射程外へ除外）の原文は変更履歴に記録。

**未済の検査**：なし。C446 (未実装の不変条件に事前登録も期限もない) は清算済みで、判定はゲート doc-registries の invariant-prerequisites セルが行う。

#### 確定項目 8：サードパーティパイプラインが返済すべき5つの債務

**確定内容**：

| # | 未済の内容 | なぜ回避不能か |
|---|---|---|
| 1 | **3つの oracle を内部テストから外部公開の適合性テストスイートへ移行** | 「ユーザーが採用するか否かはユーザーの自由」が成立する前提は、**ユーザーが自前で実行可能なツールが存在すること**である。これは明確なスコープ増分である |
| 2 | **適合性判定には本プロジェクトの oracle を採用し、パイプライン独自の検証コードは使用しない** | `.claude/singlefs-ai-sop/rules/show-me-test.md`「出所による差別的扱いの禁止」がそのまま適用される：判定基準は根拠であり、自己証明レポートではないためである |
| 3 | **システム構成に初日から書き込み者識別子を記録** | 影響半径を帰属可能とすること。壊れたイメージが持ち込まれた際、checker は単に corrupt と述べるだけでなく「パイプライン X v2.3 による書き込み」と特定できなければならない。後付けは不可能である |
| 4 | **未知の `compat_ro` ビットの縮退動作にはクラッシュテストのセーフティネットが必要** | [pitfalls.md](../pitfalls.md) 第 9 項：btrfs の degraded マウントは修復を試みるほど悪化し、根本原因は縮退セマンティクスが未設計であったことにある |
| 5 | **checker はいかなるパイプラインのランタイム会計 / 検証コードもリンクしてはならない** | 「監査側と被監査側で同一コードを使用してはならない」。サードパーティに対しては内部よりもさらに重要である——ここには信頼が存在しないためである |

**射程**：第3の債務の条項は策定済みだが検査は依然未済：システム構成のブートストラップヘッダには「書き込み者識別子 20」= 16 バイトの ASCII 実装識別子ゼロパディング + 4 バイト u32 バージョンが規定され、第1版では `singlefs-rs` / 1 を書き込み（D22 (ユニット原子性の合成手法) 確定項目 9）、不変条件 I-1.5 (システム構成がパイプライン識別を記録する) として策定済みだが、checker 側では未実装。第1の債務の配布形態は確定項目 3 が定め、判定プログラムと本リポジトリの checker が同一コードか否かは依然未確定。5つの債務はいずれも最初のサードパーティパイプラインが現れるまでバイト列化されない。

**根拠**：

- 実験なし：5つの債務は「パイプラインが登場した際に満たすべき要件」を述べており、サードパーティパイプラインが存在しない現段階では計測可能な物理量を持たない；第3の債務はすでにディスク上フィールドおよび不変条件として定着しており、それを検証するのは実験ではなく checker である。
- [pitfalls.md](../pitfalls.md) 第 9 項（btrfs の degraded マウント）が第4の債務の出典；第 2、5 の債務は `.claude/singlefs-ai-sop/rules/show-me-test.md` および `.claude/rules/fs-design.md` の2つの既存規律に由来；第3の債務のフィールドはユーザー決定（2026-09-14）、原文は変更履歴に記録。

**未済の検査**：C445 (モデル突き合わせのサンプリング点が書き込みパス伸長に伴い増加しない)；C447 (仕様実行器がクラッシュポイント再生と RefFS 突き合わせに未接続)；C8 (ゲート範囲が判定不能)。3つの後継債務（C445 (モデル突き合わせのサンプリング点が書き込みパス伸長に伴い増加しない)、C446 (未実装の不変条件に事前登録も期限もない)、C447 (仕様実行器がクラッシュポイント再生と RefFS 突き合わせに未接続)；そのうち C446 (未実装の不変条件に事前登録も期限もない) は清算済みで、判定はゲート doc-registries の invariant-prerequisites セル）は各検証ルート自身の欠落をカバーしているが、第1の債務が要求する「oracle を対外公開の適合性テストスイートとする」要件はこれらよりも広範である——**そのセルには対応する追跡番号が存在しない**。
