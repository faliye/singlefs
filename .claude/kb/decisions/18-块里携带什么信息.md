## D18 块里携带什么信息 —— 半定（判据已定，清单三项已定、四项未定）

**判据已定，三条叠加，缺一不可。** 一个字段值不值得带进块里：

| # | 问什么 | 不满足的后果 |
|---|---|---|
| **1（必要）** | **它的更新周期与内容变化周期绑定吗？** 绑定 = 内容变它才变 | 解耦的字段每次变都独立触发一次 H 级全链 COW（COW 下地址反正要改、要重写到根，这是免费便车；解耦的字段搭不上） |
| **2（必要）** | **缺了它，哪一个具体的恢复/判定会从「可判」变成「不可判」？** 答不上来就是永久格式债 | 见本决策「反面样本：一个没买到失败模式改善的字段」 |
| **3（必要）** | **相对已有机制净增了多少？对哪一侧可恢复？** | 与已有机制重叠的字段边际收益趋近零；「有密钥才可恢复」和「无密钥也可恢复」是两回事，不许笼统写「能重建」 |

⚠️ **判据 2 不是 `.claude/rules/fs-design.md` 那条「能不能把用错了变成挂不上」。**
那条是为**格式分支**设计的挂载期二元判断；携带信息是运行期对单个对象的判断，
两条判据射程不同，不许互相替代。

### 成本在哪：不在块头，在每条记录

现役实测（2026-08-28 现查 Linux 6.17，字节数由字段相加得出）：

| 层面 | 开销 | 判 |
|---|---|---|
| **块头** | btrfs `btrfs_header` **101 B / 16 KiB = 0.616%**；bcachefs `btree_node` **160 B / 256 KiB = 0.061%** | **免费** |
| **每条记录** | bcachefs 的 bkey 头多 **1 字节** ⇒ extent key 从 8 字节变 16 字节 = **2 倍** | **每字节都要抠** |

Kent 本人的原话（`fs/bcachefs/bcachefs_format.h:238-243`）：
「I wanted the header to be no bigger than necessary so that bkey_packed could use the rest.
That means that **decently often extent keys will fit into only 8 bytes, instead of spilling over to 16.**」

⇒ **约束不在「头 / 节点」这个比值上，在「每条记录都要再付一遍」这件事上。**

**而块头这一层现役实现根本没用完**（2026-08-29 现查 OpenZFS master `58d73c9`
`include/sys/spa.h:366-374`，源码固定在 `/home/fy5090/code/fs-refs/zfs/`）：
128 字节的 `blkptr_t` 里，预留区是 `blk_prop2` + `blk_pad`，各 8 字节；
`BP_GET_REWRITE` 用掉的是 **`blk_prop2` 的最高位**（`spa.h:532-538`），
**`blk_pad` 那 8 字节至今整字全空**。
⚠️ **此前这里写的是「`blk_pad` 是 16 字节……第二个字至今全空」**——
16 字节是历史形态（当年是 `blk_pad[2]`），其中一个字已改名 `blk_prop2` 并被用掉一位。
**方向不变**（预留区确实几乎没用完），错的是字段名与宽度。

### 已定要带的（判据三条全过）

| 字段 | 缺了它哪个判定不可判 | 证据 |
|---|---|---|
| **自身逻辑地址 + fsid** | 错向写（ghost write）**无法检测**。btrfs 第一方原话：「the measures have to be done ahead of time」。XFS 补一句：只有块号不够，错向写可能落到**另一个文件系统的正确块号上**，所以位置信息**必须含文件系统标识** | I-1.1（块头自述逻辑地址） / I-1.4（块头 fsid 一致） 已有 |
| **generation（出生代）** | **丢写留下的旧块是自洽的**——旧内容配旧校验和，校验和永远不报警。btrfs 的机制原话（`fs/btrfs/disk-io.c:113-118`）：「we can't consider a given block up to date unless the transid of the block matches the transid in the parent node's pointer. **This is how we detect blocks that either didn't get written at all or got written in the wrong place.**」 | I-1.2（块头代号不超当前） 已有 |
| **所属树 ID（出生树）** | 孤儿块**连损坏范围都判不出来**。XFS 第一方原话：「the corruption could mean that no owner can be found (i.e. it's an orphan block), and so **without an owner field in the metadata we have no idea of the scope of the corruption**」 | I-1.3（块头树 ID 一致） 已有 |

### ⚠️ 自包含的物理上限：丢失写，块里带什么都抓不到

**这条是本决策的边界，不写清楚会让「块尽量自包含」被推到它做不到的地方。**

**丢失写（lost write / phantom write）**——设备回报写成功但实际没写——留下的旧块
**在块内层面完全自洽**：旧内容、旧校验和、正确的自身逻辑地址、正确的 fsid，逐项匹配。

**这条不依赖任何引文，可以自己证**：检测丢失写 = 判断「盘上这块是不是它**应该**是的那个版本」，
而一个合法的旧版本与一个合法的新版本**在块内层面同构**——两者都是「某次成功写入的完整结果」。
三条反例路径全部失败：① 带墙钟时间戳——旧块**合法地**带旧时间戳；
② 每写一次就递增存在本地的计数器——「期望计数」是外部信息；
③ 带自身版本历史的哈希链——「期望链长」是外部信息。
⇒ **任何「这是上一版」的判定都需要外部见证者。这是定义性的，不是工程限制。**

同结论的成文出处（2026-08-28 本机下载 PDF 抽取复核，逐字）——OSTEP 第 45 章 §45.6：
「do any of our checksumming strategies from above (e.g., basic checksums, or **physical identity**)
help to detect lost writes? **Unfortunately, the answer is no: the old block likely has a matching
checksum, and the physical ID used above (disk number and block offset) will also be correct.**」

**推论：见证者必须在不同的失败域上。** 父节点若在同一次事件里也没写成，就要祖父，递归到根。
⇒ **根 / 超级块是最终见证者**——这解释了 ZFS 为什么要 4 个 label × 128 KiB 的 uberblock 环，
也解释了 D16（发布语义） 的 checkpoint 为什么是特殊的那一层。**这条是 D16（发布语义） 的一条独立理由。**

⇒ **抓它的信息必须在块外。** 唯一的办法是**父节点持有子块的校验和/代号**——
即 D4（校验和位置） 已定的「校验和内联进指向该块的指针，形成 Merkle 树」。
btrfs 的机制注释说的是同一件事（`fs/btrfs/disk-io.c:113-118`）：
transid 必须与**父节点指针里的** transid 匹配。

**现场数据**：NetApp FAST'20（SSD 换盘原因统计）里 **lost write 占 13.54%**，
而它是靠 WAFL 的**块签名（身份 + 版本号）**发现的，不是 SSD 的 ECC。

⇒ **自描述的射程是「错向写 / 拿错块」，不是「丢失写」。两者不许混为一谈。**

⚠️ **一处源头冲突，已判**：XFS 的 `xfs-online-fsck-design.rst:945-946` 声称
块里记的 ondisk address「enables the filesystem to detect lost writes」，
**与 OSTEP §45.6 直接矛盾**。判 OSTEP 对，XFS 那句按字面不成立，按情形分：

| 情形 | 旧内容记的地址 | 地址校验 |
|---|---|---|
| 地址 A 上原本是**同一个对象的旧版本** | = A，正确 | **通过，抓不到** |
| A 上原本是别的对象 / 从没写过 | ≠ A 或垃圾 | 失败，抓得到 |

XFS 是原地更新文件系统，第一种是它元数据更新的**常态**，所以那句话在它自己的语境里就是错的。

**而 COW 把这件事的形态换了，本工程要按新形态理解**：
COW 每次写都去**新分配的地址**，所以「同一对象的旧版本占着同一个地址」在块这一层**不可能发生**。
丢失写在 COW 里的形态是：**新块写好了，父节点的更新丢了** ⇒
父仍指向旧子块，而旧子块完全合法、自洽、地址正确，**整棵子树静默回退到上一版**。

⇒ 抓它的**不是块自己记的地址，是父指针里记的期望代号**。
**D4（校验和位置） 的 Merkle 不是「因为块自己抓不到」，而是因为「期望值」按定义只能存在于提问方那一侧。**

### 设备 ECC 的作用域：不是「不够强」，是「不在讨论范围内」

两篇闪存可靠性权威综述（arXiv:1706.08642、arXiv:1711.11427）的全文逐词计数：
`misdirect*`、`lost write`、`phantom`、`wrong LBA`、`silent data`、`firmware bug`
—— **六个词在两篇里全部 0 命中**。

设备 ECC 的作用域是**单个 codeword 内部的位是否自洽**，失败模式是**报错**
（latent sector error / uncorrectable），不是静默。
而错向写与丢失写的共同结构是：**盘上的位完全合法、ECC 完美通过**，
错的是「这些位属于谁」和「这些位是第几代」。

### 由「现役修复工具修不了什么」倒推出的缺失项

**这一节的每一条都绑着一个真实的、有公开记录的恢复失败。**

| # | 候选 | 绑着哪个失败 | 状态 |
|---|---|---|---|
| **1** | **谱系重写序号**（沿谱系单调增，与事务号正交） | btrfs-rec 遇到「同 owner、同 generation、覆盖同一 key 区间」的两个节点时**直接 panic**，格式里没有任何字段能判谁覆盖谁。⚠️ **该 panic 出自 btrfs-rec 作者的设计博客，我未独立复核其源码**；但「btrfs 的 key 区间上界只存在于父节点的下一个 keypointer 里」这一半是从 `include/uapi/linux/btrfs_tree.h:570-574` 的 `btrfs_key_ptr` 字段表直接读出的，成立。bcachefs 的 `BTREE_NODE_SEQ` 一行解决（`fs/bcachefs/btree_gc.c:266` `if (prev && BTREE_NODE_SEQ(cur->data) > BTREE_NODE_SEQ(prev->data)) /* cur overwrites prev */`）。⚠️ **事务号做不到**：同一次事务里 split 出的两个节点事务号相同 | **未定，强候选** |
| **2** | **节点自带 key 区间 `[min_key, max_key]`** | btrfs 的 max key 只存在于**父节点的下一个 keypointer** 里，父没了区间就没了，btrfs-rec 必须做动态规划去推。bcachefs 存在节点头里，于是能**发现 key 空间的洞并从扫描结果补一个节点进去**（`btree_gc.c:248-286`） | **未定，强候选** |
| **3** | **数据块的自描述**（本工程当前为零，见本决策「本工程当前最大的自恢复盲区：数据块零自描述」） | btrfs 恢复数据 chunk 只能拿 csum 树做 KMP + 模糊匹配（`best>50% && second<50%` 才敢采信）；`btrfs restore` 捞出来的数据**无法验证**——「Since either way data checksum verification is no longer in place」，因为 csum 树按**逻辑地址**索引，而逻辑地址正是丢掉的那样东西 | **未定，且与 D9（加密）冲突** |
| **4** | **提交点身份 =（计数, 提交点 hash）**，不只是计数 | **单调计数在回滚 / fsck 之后会重复**，重复之后上一条时间线的残留块会冒充合法块。f2fs 的处置是把 checkpoint 的 CRC 塞进 `cp_ver` 高 32 位（`fs/f2fs/node.h:326` `cp_ver \|= (cur_cp_crc(ckpt) << 32)`）。UBI 的 `image_seq` 解决同类问题 | **未定** |
| **5** | **「我是搬迁副本」标记 + 副本专属数据 CRC** | UBI 第一方承认：两个 PEB 对应同一个 LEB 时**光看序号不够**，较新的那个可能是搬到一半掉电的——「this is just a guess, which might be wrong」。它的解法是 `copy_flag` + 只有副本才付的 `data_crc` | **未定**，与 D3（空间分配） 的常驻整理、设备替换直接相关 |

### 本工程当前最大的自恢复盲区：数据块零自描述

⚠️ **[invariants.md](../invariants.md) 的 I-1.1（块头自述逻辑地址） ~ I-1.4（块头 fsid 一致） 四条全部写的是「任一元数据块」**，
全清单里「数据块」只在 I-6.4（无未加密块）出现过一次。
⇒ **extent 树与 inode 树同时丢失时，数据块是匿名字节**——校验和正确、内容完好，
但没有任何字段说它属于谁。

而 `.claude/rules/fs-design.md` 那条铁律的理由写着「这是**全盘扫描重建**在物理上可能的前提」。
**那个前提目前只兑现了一半**：能重建树结构，重建不出文件内容的归属。

⚠️ **但补它有硬约束**：把 `(inode, 逻辑偏移)` 明文放进数据 extent，
就是 D9（加密）未定项 5 已经权衡过并**选择性拒绝**的那条路（明文物理映射泄漏布局与引用关系）；
放进 AEAD 覆盖范围则**对无密钥侧无效**。
⇒ 这条收益**有条件**：只在「索引树丢了但密钥还在」这个更窄的场景成立。

### 显式字段 vs 折进校验和种子：不等价，且这条把每一项分成两档

ext4 把 `(fs uuid, i_ino, i_generation)` 折进校验和种子（`fs/ext4/ialloc.c:1289-1293`），零额外字节；
dm-integrity 把扇区号混进 mac。**代价是只能验证一个猜测，不能反解身份**——
拿一个孤儿块问「你属于谁」，折进种子的方案答不出来。

⇒ **凡是要支持「扫盘重建」的信息必须显式写下来；只有「只需检出误用、不需重建」的才可以折进种子。**

### 否决清单

| 候选 | 否决理由 |
|---|---|
| **子块记录「当前」父节点物理地址** | **时序上不可能**。COW 是子先写、父后写——子块下笔那一刻，父节点还没被重写到反映这次变更的状态，**它想记的东西那时还不存在**。改成回填就违反「一次写完不回写」。这是逻辑矛盾不是工程麻烦 |
| **checkpoint 内联「本次共 N 块」** | **同类时序死锁**：N 只有 checkpoint 收尾才知道，而字段要嵌进期间写的每一个块。要求集合还没封闭就知道集合大小 |
| **COW 前驱地址（版本链）** | **净值为负**。① 与 D5（快照 / 空间记账机制） 的 birth txg + deadlist 功能重叠，边际收益趋近零；② 前驱块被物理复用后那个指针变成**误导指针**——沿它去看「历史版本」看到的是**别的对象的当前内容**；③ 它要求新增一条不变量去防它自己制造的坑 |
| **块内纠错码（ECC）** | **否决，理由是「两头都不划算，中间没有甜点区」**（⚠️ 不是「太贵」——最便宜那档很便宜）。① 便宜档：Hamming 16 位校验纠 1 比特，4 KiB 块上开销 **0.05%**，**但它只修设备 ECC 已经修好的那类**（散落位翻转）；贵档：RS 修整个 512 字节扇区要 12.5%、修撕裂写丢的半块要 50%。而设备 ECC 覆盖不了的两类里，**撕裂写要 50% parity、错向写整块都是别人的数据没有任何冗余可用**。② **全场唯一实例是 OCFS2 `metaecc`**（`fs/ocfs2/ocfs2_fs.h:408` 32 位 CRC32 + 16 位 Hamming，`blockcheck.c:405` 纠 1 bit 后重验 CRC），**只纠单比特、默认关闭**，且其设计文档自陈动机是「OCFS2 is already out in the wild... Modifying it to this level of safety isn't really possible **without creating an entirely new filesystem**」——**这个动机对从零设计的本工程不成立**。③ 另查 13 个系统（含 IRON、CrookFS、NOVA-Fortis、EnvyFS 等研究系统），**块内 ECC 零命中**；NOVA-Fortis 更是显式评估过 ECC 然后拒绝 |
| **每块存墙钟时间** | 四家块头逐字段查过，**一个都没有**。全是 `generation` / `txg`——单调、可比、COW 提交有天然定义点。墙钟只在 ZFS 的 uberblock 出现一次，**全池一份** |

### 反面样本：一个没买到失败模式改善的字段

**btrfs 的 `chunk_tree_uuid`，16 字节/块**。现查：一处写、一处 scrub 验（`fs/btrfs/scrub.c:736`）、
一处挂载时**自指**读取期望值（`disk-io.c:3453`，从 chunk root 自己的块头里读）；
**常规读路径 `btrfs_validate_extent_buffer` 对它 0 命中**。

⇒ **字段的判据不是「多一份身份信息更保险」，而是「缺了它，哪一个具体的判定会从可判变成不可判」。**
答不上来的字段，就是每块 16 字节的永久格式债。

### 与其他决策的连锁

| 决策 | 连锁点 |
|---|---|
| D9（加密）| 数据块自描述与 D9（加密）未定项 5 的泄漏面权衡直接冲突，见本决策「本工程当前最大的自恢复盲区：数据块零自描述」 |

| D8（核心索引结构） | 携带的信息若落在**每条记录**上而非块头上，成本按记录数乘，见本决策「成本在哪：不在块头，在每条记录」里 Kent 的原话 |

### 未定项

1. **谱系重写序号**要不要做，宽度多少，与 D16（发布语义） 的 checkpoint 序号怎么共存。
2. **节点自带 key 区间**要不要做。⚠️ 对 dirent 树要小心——它的分隔 key 就是文件名，
   D9（加密）已认定那是敏感信息，明文 key 区间等于暴露「这个子树覆盖的文件名范围」。
3. **数据块自描述**做到什么程度，明文还是进 AEAD（硬约束见本决策「本工程当前最大的自恢复盲区：数据块零自描述」）。
   ⚠️ **阻塞第一行事务层代码**：第一个事务写的就是数据块，而本项决定**载荷从第 0 字节开始还是从块头之后开始**，
   且「明文还是进 AEAD」直接改变密文边界与 MAC 覆盖范围。
   ⚠️ **它没有「先按 0 条写」这种中间态**——这一点与 D21（权威态与派生态的分界） 未定项 1 不同，
   后者是另一个结构、条目数可以为 0（对抗验证 2026-08-29 分辨过这两者）。

   ⚠️ **这个洞的大小已量**（[experiments.md](../experiments.md)
   E29（明文映射层能不能只靠单元自描述重建），2026-08-29，三轮字节一致）：
   删掉明文映射层、只扫单元头重建时，**元数据侧一条不缺一条不错，数据块侧缺口恰等于数据块总数**
   （1024 元数据 + 4096 数据块 ⇒ 重建出 1024 条、缺 4096 条）。
   **阳性对照**：给数据块加上自描述之后缺口归零 ⇒ 缺的是自描述本身，不是重建路径坏了。
   ⇒ D9（加密）未定项 7 的定案「明文映射层是派生态、重建源是单元自描述」
   **对元数据成立，对本项欠着**。
4. **单盘自恢复的形态**：主流答案是**元数据多副本 + 分散放置**，不是块内纠错。
   ZFS 的 ditto blocks 形态：用户数据 1 份、数据集元数据 2 份、全池元数据 3 份，
   **单盘上也有意义**——「we spread the blocks physically across the disk.
   Our policy aims to place the blocks **at least 1/8 of the disk apart**」；
   总开销约 **2%**，因为元数据本来只占全部数据的 1.5–2%。
   作者本人的破坏性验证：抹掉分区前 1 GB 后「**I could still navigate the entire filesystem,
   typing "ls", "rm" and creating new files as much as I wanted**」。
   ⚠️ 本工程的 D2（RAID 条带策略） 已定变宽全条带（需 ≥2 盘），**单盘这一格目前空着**，
   ditto blocks 形态是候选，未定。
