## D20 承重面：单元的原子性与自包含 —— 已定

D20（承重面：单元的原子性与自包含） 定本工程的承重面在哪一层，以及那一层要满足什么：单元的**原子性**与**自包含**。管的是这两根轴的地位、原子宽度按什么分、谁来保证、被违反时怎么发现。不管的：具体字段带什么、宽多少归 D18（块里携带什么信息）；怎么合成原子性的两条轴归 D22（单元原子性怎么合成）；校验和住哪归 D4（校验和位置）；发布次序归 D16（发布语义）。上层结构——索引形态、快照模型、分流策略、介质布局——都可以换，承重面不能。

### 已定项

D20（承重面：单元的原子性与自包含）的分项只有一套编号，不重排。

| # | 分项 | 定案 |
|---|---|---|
| 1 | **承重面划在哪一层** | 划在「单元」这一层：它的原子性与它的自包含；上层怎么变都无所谓 **状态：已定。** |
| 2 | **自描述要不要罩住数据块** | 要：I-1（块自描述） 那几条从「任一元数据块」扩到「任一单元」，做到什么程度由 D18（块里携带什么信息） 已定项 3 定 **状态：已定。** |
| 3 | **「原子性」怎么写成可判定的** | 写成三问：原子宽度是多少、谁保证、被违反时怎么发现；缺一条就还没落地 **状态：已定。** |

#### 已定项 1：承重面划在「单元」这一层

**定案**：本工程的承重面是**单元**这一层——它的**原子性**，和它的**自包含**。上层结构（索引形态、快照模型、分流策略、介质布局）都可以换，承重面不能。

两条各自独立的理由：

- **可外推性**：格式要活很久，而活得久的部分不是当时选对了哪棵树，是**最小单元的语义有没有留下歧义**。
- **机制**（不依赖上一条）：一个既自包含又原子的单元，使「全盘扫描重建」在物理上可能——捡起任意一个单元都能回答「我是谁、我属于谁、我是第几代」，且它要么是完整的旧版要么是完整的新版，没有第三种状态。**重建能力是所有上层结构的共同后备**：上层换成什么，这条后备都还在。它是 `.claude/rules/fs-design.md`「元数据块必须自描述」的推广——从「元数据块」推广到「单元」，并加上原子性这根轴。

**射程**：定的是哪一层承重与那一层要满足什么，不定任何一个字段、任何一条合成机制。「单元」这个形态本身的射程在 `.claude/rules/fs-design.md`「不是单元的盘上空间，核心层对它零覆盖」：不做成单元的盘上空间自动落在校验和、扫描重建认领、checker 遍历、不变量这几样之外。

**依据**：无实验：定的是承重面划在哪一层，没有可量的量；两条理由一条是可外推性判断、一条是机制推导（重建能力要的正是自包含加原子性这两样）。用户定案，原话在变更史。

**欠**：无。

#### 已定项 2：自描述要罩住数据块，不只元数据块

**定案**：[invariants.md](../invariants.md) 的 I-1（块自描述） 那几条说的是「任一**单元**」，不是「任一元数据块」——按已定项 1，「单元」不分元数据与数据。数据块做到什么程度由 D18（块里携带什么信息） 已定项 3 定（明文，且宁可写大一点：每个数据单元带明文自描述头，五元组共 33 字节；不加 `locality_id`）。

**射程**：这一项只要求「数据单元也要自证身份」，不定字段集合与宽度——那在 D18（块里携带什么信息） 已定项 3 / 7。自证单元（journal 记录 / 根槽 / 系统配置槽 / 类型 4 实例表单元）对 I-1.1（块头自述逻辑地址） 与 I-1.3（块头树 ID 一致） 显式豁免，它们的自证纪律另有落点。

**依据**：无实验：这一项只把已定项 1 的「不分元数据与数据」落到不变量的主语上，量在 D18（块里携带什么信息） 已定项 3 那一侧。主 agent 与用户定案，原话在变更史。

**欠**：无。

#### 已定项 4：原子宽度按单元类分开给，合成一句就会错

**定案**：两问的答案必须按单元类分开给。

| 单元类 | 第 1 问：原子宽度是多少 | 第 2 问：谁保证 |
|---|---|---|
| **有父指针的单元**（多数） | **不依赖任何宽度。** 撕裂粒度是 512、4 KiB 还是整块，对父指针校验和这条论证毫无影响（D22（单元原子性怎么合成） 已定项 19 / 已定项 20） | 核心层，用 D4（校验和位置） 的父指针内嵌校验和 + D16（发布语义） 的发布次序 |
| **自证单元**（根槽、journal 记录头、**系统配置槽**） | **等于运行时探测到的 `physical_block_size`，不许硬编码。** 这一句说的是**撕裂判定的分辨率**，不是结构尺寸。见 D23（journal 的角色与格式） 已定项 4 的明文禁令 | 核心层合成（整单元校验和 + 代号 + 槽轮换，见 D22（单元原子性怎么合成） 已定项 21）；设备声明只做上界参数 |

**「原子宽度是一个格式常量」这个说法是错的**，它把两格压成一句：多数单元根本不需要知道宽度；需要知道的那一小格又明令不许把数字焊进格式。

**设备声明可不可用，分两种情形，不是一句话**（现查 `drivers/nvme/host/core.c` 的 `nvme_configure_atomic_write()`）：

```c
if ((id->nsfeat & NVME_NS_FEAT_ATOMICS) && id->nawupf) {
        atomic_bs = (1 + le16_to_cpu(id->nawupf)) * bs;
```

| 情形 | 可不可区分 | 能不能用 |
|---|---|---|
| 没有 ATOMICS 特性位，或 `nawupf == 0` | **不可区分**——`atomic_bs` 落到逻辑块，与「什么也没声明」同形 | 不能 |
| 有 ATOMICS 位且 `nawupf > 0` | **严格可区分**，`atomic_bs = (1+nawupf) × bs > bs` | 可以，但**只做上界参数** |

**射程**：自证单元那一行说的是**撕裂判定的分辨率**，不是**结构尺寸**——系统配置槽的结构尺寸是格式常量 4096（登记名 `SUPERBLOCK_SLOT_BYTES`，D22（单元原子性怎么合成） 已定项 2），根槽宽才是「等于挂载时探测的 `physical_block_size`」。拿到一个可信的上界也买不到新的安全性：检测机制本身不依赖宽度，它只影响自证单元那一格的对齐代价。⚠️ 它不解 C212（固定结构的写小于 io_min）：在 `io_min` 大于 `physical_block_size` 的设备上，一次系统配置槽写仍然是一次小于 `io_min` 的写，与 D2（RAID 条带策略） 已定项 16 的冲突原样还在。

**依据**：无实验：两问的答案是从「父指针校验和这条论证要不要知道宽度」推出来的，没有可量的量；设备声明那两种情形逐行现查内核源码坐实，出处是 `drivers/nvme/host/core.c` 的 `nvme_configure_atomic_write()`，未在本项目验证。系统配置槽进这一格的枚举是用户定案（规则本身一个字没改），原话在变更史。

**欠**：C212（固定结构的写小于 io_min）。

#### 已定项 5：核心层合成什么——七个机制，各自的盲区写明

**定案**：

| 机制 | 能检测 | 检测不到 |
|---|---|---|
| 父指针内嵌校验和（D4（校验和位置））+ 发布次序（D16（发布语义）） | 任意粒度撕裂、错向写、位翻转、子块丢写 | 父自己丢写（递归到祖父）；根 |
| 整单元校验和 | 单元字节不自洽 | **完整的陈旧单元**；按位宽漏检 |
| 世代号 / `jsn` 且被实际检查 | 完整的陈旧单元；序列空洞 | **头落尾没落**——头里的号是新的 |
| 槽轮换 + 先全验后择新 | 唯一副本被撕裂即失去见证者 | 回退深度（受块重用延迟 K 限） |
| per-sector 盖章（D22（单元原子性怎么合成） 轴 ②，现判不做） | 陈旧扇区**确定**检出；撕裂**位置** | 扇区内容损坏；整条都旧 |
| 在飞记录数上限 | 把窗口外的校验失败判为损坏而非撕裂 | —— |
| 写侧不发小于映射单元的写 | 它**预防**设备内部 RMW 损坏邻居，不检测任何东西 | —— |

⚠️ **整单元校验和与世代号单独都不封闭，必须成对**：前者漏掉陈旧，后者漏掉头尾不齐。

**射程**：这张表列机制与盲区，不判哪一个该做——per-sector 盖章做不做在 D22（单元原子性怎么合成） 已定项 21（现判不做）。D22（单元原子性怎么合成） 否掉它时只比了漏检率一个维度，而盖章还买到**免对齐**（判定分辨率是扇区时，多条记录挤同一个原子单元照样判得了撕裂，而整单元校验和下除第一条外都判不了）；那条否决理由的比较集不完整这件事已记在 D22（单元原子性怎么合成） 已定项 21，重开与否归 D22（单元原子性怎么合成），这一项只记账。

**依据**：

- E23（journal 几何）：per-sector 盖章买到的第三样是免对齐，那笔对齐代价在 4Kn 上是 29.3 倍——七个机制表里那一行的收益不止漏检率一个维度。
- 三方论证：正推腿把「原子宽度」拆成设备声明的宽度与判定宽度并给出七个机制的盲区表，两条非正推腿在设备声明那一处独立收敛，主 agent 逐行现查内核源码后采纳并收窄；经过在变更史。

**欠**：C16（管道声明失败模型例外）。

#### 已定项 6：被违反时怎么发现——崩溃点重放 + checker

**定案**：第 3 问的落点是**崩溃点重放 + checker**。两样都有了（门禁 54 号、`crates/singlefs-checker`），但层 0 只录本工程自己这一条管道、按整写枚举、撕裂并进「没持久」（D13（验证路线） 已定项 4）⇒「失败原子性宽度 / 撕裂 / 重排序」按管道声明的那一类仍**零覆盖**。

**射程**：本机也造不出撕裂（`dm-flakey` 只有 `drop_writes` / `error_writes` / `corrupt_bio_byte`）⇒ 这一问要等第二条管道与撕裂注入才验得了。「落点定了」不等于「已经验过」。

**依据**：无实验：定的是这一问交给哪两样装置，没有可量的量；两样装置各自的判别力在 D13（验证路线） 那一侧，撕裂那一类的注入手段今天不存在。主 agent 定案。

**欠**：C16（管道声明失败模型例外）。

#### 已定项 7：设备侧的原子宽度是 512，且不可依赖

**定案**：**本工程不能假设大于 512 字节的原子性，且连 512 也只能当作「大概率成立」。单元原子性必须自己合成。**

逐字现查坐实的五条事实：

| # | 事实 | 出处 |
|---|---|---|
| 1 | 本机 NVMe：`atomic_write_unit_min = atomic_write_unit_max = logical_block_size = physical_block_size = 512` | `/sys/block/nvme0n1/queue/` 现读 |
| 2 | **Linux 上 `physical_block_size` 已经就是「设备承诺的掉电原子宽度」** | `drivers/nvme/host/core.c`：`lim->physical_block_size = min(phys_bs, atomic_bs);` 上方注释原文「Linux filesystems assume writing a single physical block is an atomic operation. Hence limit the physical block size to the value of the Atomic Write Unit **Power Fail** parameter.」 |
| 3 | 内核只认 Power Fail 变体（`AWUPF`/`NAWUPF`），对 `AWUN`/`NAWUN` **零引用** | `nvme_configure_atomic_write()` |
| 4 | **「设备声明 1 块」与「设备什么也没声明」不可区分** | `drivers/nvme/host/core.c` 的 `nvme_configure_atomic_write()`：设备不声明时走 `atomic_bs = (1 + ns->ctrl->subsys->awupf) * bs`，`awupf == 0` ⇒ `atomic_bs = bs`，且 `lim->features \|= BLK_FEAT_ATOMIC_WRITES` **无条件执行**，没有「未声明就不置该 feature」的分支 |
| 5 | **块层从未承诺「一个 bio 不会被撕裂」** | `Documentation/ABI/stable/sysfs-block` 的四个 `atomic_write_*` 条目**没有一处**出现 crash / power loss；`Documentation/block/writeback_cache_control.rst`（95 行）**全文没有 atomic / torn / tear**——`REQ_PREFLUSH`/`REQ_FUA` 管的是持久化时序 |

**现役实现的反证——全部自己合成撕裂检测，没有一家靠设备**（外部实现只当反证与机制，未在本项目验证）：

| 实现 | 机制 |
|---|---|
| **ZFS 根** | 4 label × 128K uberblock 环；槽号 = `ub_txg % (VDEV_UBERBLOCK_COUNT − m)`（**轮换，不覆写上一代**；`m` 是多主机保护 MMP 占掉的槽数）；SHA-256 **内嵌块尾**、verifier 是该块自己的物理偏移；读时全扫所有槽按 `txg → timestamp` 择新；偶数 label → uberblock → 奇数 label 三阶段带 flush |
| **ZFS 普通块** | 校验和在父指针里；撕裂 ⇒ 失配 ⇒ 靠副本修 |
| **btrfs 节点** | `csum` 覆盖 `[32, nodesize)`；**第二道独立闸**：父指针的 transid 与节点头 generation 对拍；本事务内释放的块 **pin 住不重用** |
| **XFS log** | `xlog_pack_data()`：**每 512 字节格的首个 `__be32` 覆写成 cycle_lsn，原值存进 record 头的 `h_cycle_data[i]`**，恢复时换回；另有整条 record 的 CRC。自述原文：「Storage without sector atomicity guarantees can result in torn writes… **Our only means to detect this scenario is via CRC verification.**」 |
| **jbd2** | commit block 整块 csum + `REQ_PREFLUSH\|REQ_FUA` 定序；另有一条接受「只有头部有效、其余为零」的 `verify_partial` |

两处例外，方向都指向同一个结论：唯一明文声称依赖设备的是 ZFS `vdev_label.c` 那句「the disk does not do single-sector overwrites atomically (**even though it is required to**)」——量级是**单扇区 512**，而且 ZFS 仍然靠**换槽**绕开它；唯一真正吃设备 >512 原子保证的是 XFS 的 `RWF_ATOMIC` **用户数据**直写，且配一条纯软件 COW 回退（`-ENOPROTOOPT` ⇒ 换 COW 路径），**XFS 自己的日志与元数据一个字节都不走这条路**。

**射程**：⚠️ **「设备新」不等于「原子写宽度更大」。** NVMe 的原子写单元要看设备自己声明的 `AWUN` / `NAWUPF`，不声明就是没有。放弃兼容旧设备能换到的是「可假设 4 KiB 物理扇区」「可假设 FLUSH/FUA 由块层合成」「可假设并发提交」——**换不到原子写宽度**。ZFS `vdev_label.c` 那句是 D20（承重面：单元的原子性与自包含） 早先记录的引文，本机无 OpenZFS 源码、不可独立核实。

**依据**：无实验：五条事实是逐字现查内核源码与 sysfs 得到的观测，不是本工程跑出来的量；现役实现那张表按 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「别的项目怎么做，是线索不是证据」只当反证与机制——它把举证责任压到「靠设备」那一边，不构成正证。主 agent 定案，两条独立路径加自核，经过在变更史。

**欠**：C16（管道声明失败模型例外）。
