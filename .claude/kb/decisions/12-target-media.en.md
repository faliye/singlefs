## D12 Target Media —— Settled

[中文](12-目标介质.md) · **English** · [日本語](12-対象メディア.ja.md)

D12 (Target Media) governs the media dimension: how many sets of disk layouts can exist in total, what must be shared across layouts, where device-level geometric quantities reside, which items are compared at mount time, which layout is implemented first, and what debts must be paid when opening a layout branch. What it does not govern: internal node layout and stripe geometry within a layout belong to their respective layout lines; whether block pointers carry device identity belongs to D19 (Block Pointer Structure & Width Budget) Settled Item 1; number of commit protocol structural equivalence classes belongs to D17 (Implementation Layering & Third-Party Pipeline) Settled Item 2; freeze hierarchy and feature bit numbering discipline belong to D15 (Format Freeze Policy).

### Settled Items

**D12 (Target Media) sub-items maintain a single numbering scheme**, continuous with the "Unsettled Items" section without renumbering.

| # | Item | Decision |
|---|---|---|
| 1 | **How many sets** | No cap in advance; each media class can have its own layout; prerequisite is that each layout occupies one incompat bit **Status: Settled.** **Progress: Implemented.** |
| 2 | **How much is shared** | Governs format-layer sharing only; derived state sharing excluded; bucket criteria take "failure mode under inconsistency", divided into three buckets: must share / may differ / must not share **Status: Settled.** **Progress: No code object.** |
| 3 | **Where device-level geometric quantities reside** | Reside in device descriptor table in system configuration, not in block headers—reading block headers requires addressing, and addressing requires knowing device geometry **Status: Settled.** **Progress: Implemented.** |
| 4 | **Which device-level geometric quantities to check** | Any geometric quantity entering address arithmetic is compared per device; others not compared; dispositions for four compared items hardcoded **Status: Settled.** **Progress: Implemented.** |
| 5 | **Which layout is implemented in the first version** | Only standard SSD layout implemented, not requiring FDP / ZNS; ultimate goal remains multi-media without changing a word **Status: Settled.** **Progress: Implemented.** |
| 6 | **Branch by media or single layout with parameters** | Multiple media each first-class with dedicated disk layout; no "single layout + parameters derived per media" **Status: Settled.** **Progress: No code object.** |
| 7 | **Debts to pay when opening a layout branch** | Eight items, none can be defaulted: checker, crash-point replay, gate wallclock, test-forced entry, observability, permanence, golden images, periodic full run **Status: Settled.** **Progress: No code object.** |

#### Settled Item 1: How many sets

**Settled**: **No cap in advance.** Every media class can have its own disk layout, and the format reserves the capability to branch for future media; **extensibility takes priority over minimizing set count**. ⚠️ **A foundational prerequisite, not an optional recommendation: each layout must occupy one incompat bit.** **A media branch without an incompat bit buys nothing and must not be opened.** **Layout line ownership: whoever opens a line maintains it.** This repository maintains a small number of lines in-house (order of 4–5), while the rest are maintained by their opening parties.

**Scope**: The rationale is that multiple branches do not interfere with each other and new media can plug in directly without disturbing existing layouts, while the constraint "a single maintainer must hold N sets in mind" no longer applies; basis for the incompat bit prerequisite is .claude/rules/fs-design.md "whether a format branch is worthwhile depends on whether it turns 'wrongly used' into 'cannot mount'". The number of commit protocol structural equivalence classes is a different metric (D17 (Implementation Layering & Third-Party Pipeline) Settled Item 2), not overlapping with layout count: layout count N multiplies checker / golden images / crash-point replay, while equivalence class count multiplies commit step enums. **The greatest risk lies not in set count, but in waistline penetration**—.claude/rules/fs-design.md settled "index structures can be diverse, but **transaction layers must not be diverse**"; if a new media class requires new structural commit steps, it modifies the shared `CommitStep` enum, triggering crash-point replay re-runs across all existing layouts => **the cost of onboarding the (N+1)-th line is O(N) upon touching the waistline, not O(1)**; an active demonstration is btrfs's `btrfs_is_zoned` scattered across 22 files and 93 sites, including 5 in transaction log paths and 6 in ENOSPC admission. Open N in itself does not pose wallclock issues: touching one branch at a time costs O(1), waiting for results is asynchronous; what must be prevented is "thinking only one branch was touched while actually altering shared code". "Whoever opens maintains" transforms three things from optional to mandatory: conformance suite must be publishable (D17 (Implementation Layering & Third-Party Pipeline) Settled Item 3, without which "whoever opens maintains" equals "whoever opens decides"), waistline enforcement must be mechanical (this repository cannot review all code from line creators; same rationale repaid C12 (shared delta semantics) on repository side per owed check resolved table: checker-implementation-disjoint cell of gate checker-independence-and-sync enforces that dependency closure intersection of `singlefs-checker` and `singlefs-core` contains only constants modules, checker forbidden from linking runtime code of core; what remains uncovered is third-party pipeline side—its own `Cargo.toml` is outside this repository's dependency graph, requiring real `cargo tree` runs), and a "layout retirement" channel must exist. **Retirement channel does not yet exist**: D15 (Format Freeze Policy) has freeze layering, mutation table, and feature bit numbering discipline (retired bits cannot receive new semantics, C11 (Feature Bit Number Skip)), but lacks the process for "how a layout transitions from supported to read-only, and then to mount rejection", needing to answer whether old images mount after retirement, who determines a line is unmaintained, and whether retirement verdicts enter incompat bits. **Acceptance criteria do not change with ownership** (.claude/singlefs-ai-sop/rules/show-me-test.md: distinguishing only evidence-backed from unbacked), external layout lines pass through the exact same gate as repository layouts.

**Basis**:

- User settlement twice (no cap in advance, whoever opens maintains), original words in changelog.
- External facts (checked on Linux 7.2.0 on 2026-08-28, unverified in this project): `BTRFS_FEATURE_INCOMPAT_ZONED` (defined in `include/uapi/linux/btrfs.h`) and `XFS_SB_FEAT_INCOMPAT_ZONED` (defined in `fs/xfs/libxfs/xfs_format.h`) are both incompat bits named after media, but **no file system branches its entire layout by media**; coupled with "f2fs designed for flash having zero references to rotational checks" and "bcachefs removing `TIER` from on-disk format"—these prove others did not venture to this project's point, not that doing so is incorrect; per .claude/singlefs-ai-sop/rules/evidence-discipline.md they do not serve as positive evidence.
- No experiments: capping set count has no measurable quantities; load-bearing elements are the incompat bit format criterion and waistline enforcement.

**Owed**: C19 (Media Verdict Leaking into Transaction Layer), C183 (one incompat bit per layout while on-disk bytes show no difference).

#### Settled Item 2: How much is shared

**Settled**: First split "sharing" into two classes: only **format-layer sharing** (immutable, permanent contract, directly offsetting debt items 1 and 2) enters D12 (Target Media) Settled Item 2; **derived state sharing** (reversible, modification merely requires rebuild) does not enter. Then sort into three buckets based on "failure mode under inconsistency":

| Bucket | Criterion: What happens if two layouts diverge on this item | What goes in |
|---|---|---|
| **Must share** | **Reading bytes that appear legal** (silent misinterpretation) | System configuration skeleton, feature bit encoding, **"device -> layout" table**, KDF identifier / master key slot / encryption type in system configuration (D9 (Encryption) Settled Item 12 Item 3), MAC + nonce space in pointers (Item 1), extent offset from original start (Item 2) |
| **May differ** | **Intra-volume self-localization**: holding an object suffices to explain which rules decode it—either self-declaring or deduced from already held information | Node layout and stripe geometry of each layout, per-write algorithm type field (D9 (Encryption) Settled Item 12 Item 4) |
| **Must not share** | Discriminative power of checker collapses | Verdict paths for "whether a given accounting fact holds" |

**Scope**: ε, buffer geometry, index topology (single layout-axis value in D11 (Message Buffers in Index Nodes) Settled Item 6; tree-axis inode tree ε = 0 exception based on recomputation predicate, not media) fall outside D12 (Target Media) Settled Item 2—they are indeed identical across layouts, but that is not a format contract, and sharing them does not reduce debts. **System configuration cell relies not on failure modes, but on starting point of chain**: parsing rules must be in hand before reading that layer, and system configuration has no prior layer—reading it requires knowing layout, while knowing layout requires reading it; feature bit encoding and D9 (Encryption) Settled Item 12 Item 3 reside here for the same reason. Deeper layers may differ, **but rules must be written explicitly in the layer above**; relying on implicit implementation conventions is the source of silent misinterpretation. Rationale for putting D9 (Encryption) Settled Item 12 Items 1 and 2 into "must share" is heterogeneous pools: when extents of two layouts coexist within one volume, inconsistent nonce width and AAD measurement basis lead to **nonce reuse and false MAC verification, neither reporting errors**—D9 (Encryption) Settled Item 13 Hard Requirement 1 settles nonces tracking logical identity, and D9 (Encryption) Settled Item 4 settles storing per extent; after reuse no checks alarm. Item 4 (per-write algorithm type field) is opposite: old data decoded per respective field, encountering unrecognized algorithm types **can only fail explicitly**, cited by .claude/rules/fs-design.md as the cleanest format branch example in this project. Block header self-describing fields need no further decision in D12 (Target Media) Settled Item 2, as D18 (Information Carried in a Block) Settled Item 3 / 6 already provided field sets, categorized by unit class in Settled Item 7. ⚠️ **Criterion for bucket 2 is not "mount failure", which is hollowed out by heterogeneous pools**: "unrecognized means mount failure" holds only when a volume has one layout, whereas heterogeneous pools must be supported => a volume declares incompat bits for multiple layouts simultaneously; an implementation recognizing all layouts mounts normally, whereupon two sets of rules coexist; "inconsistency" becomes the norm rather than failure, and the safety net never triggers => admission requires **intra-volume self-localization**, with "mount failure" demoted to safety net against implementations unaware of this layout. How two members self-localize: per-write algorithm type field is **deduced** (in hand upon following pointer, residing in pointer header, one per logical extent; self-proving units lack parent pointers with checksums and carry their own—D23 (Journal Role & Format) Settled Item 4 record header has 1 byte algorithm type among ten fields); node layouts and stripe geometry of each layout are also **deduced** (device identity in pointer -> "device -> layout" table -> layout, landing in device descriptor table of Settled Item 3) => **"device -> layout" table enters bucket 1**: it is a meta-rule explaining others, read early during mount; scan rebuild also relies on it—block headers per D18 (Information Carried in a Block) Settled Item 3 forbidden list must not carry device IDs, but scanners know which device they read (observation), looking up table by device identity, provided that table is identical across all layouts. ⚠️ **Bucket 3 is not an amplified bucket 2, nor is criterion failure mode**; it is an independent line: if checkers for two layouts link the same parameterized reconciliation framework, merely disabling plugins at call time, independence degrades from "code does not exist" to "this invocation did not use this code"—the exact criterion used by D11 (Message Buffers in Index Nodes) in rejecting "messages as independent tree".

**Basis**:

- User settlement (two classes, three-bucket classification, heterogeneous pools must be supported), original words in changelog.
- No experiments: bucket criteria are definitional derivations based on failure modes, carrying no measurable quantities.

**Owed**: C181 (in-pool heterogeneity criterion missed bitwise XOR stripe axis).

#### Settled Item 3: Device-level geometric quantities reside in device descriptor table of system configuration

**Settled**: Device-level geometric quantities reside in **device descriptor table in system configuration**, **not in block headers**. Criterion: **whether a geometric quantity can be heterogeneous in a pool depends on whether address arithmetic using it carries device identity**—carries => can vary per device; does not carry => must be uniform across pool, rejecting mount on mismatch. **Heterogeneous pools must be supported**: a volume can contain multiple layouts simultaneously.

**Scope**: Between the two candidates, "residing in block headers" is excluded by circularity, not a tradeoff—**reading block headers requires addressing, and addressing requires knowing device geometry** => storing geometry in block headers requires reading block headers before reading block headers, identical to D18 (Information Carried in a Block) Settled Item 6 header placement criterion ("scanner must predict location without prior knowledge"). User instruction: land in this form first, adjust when coding. Unlocks bucket 2 chain in Settled Item 2—device identity -> "device -> layout" table -> layout, where the table's landing site is this cell, rendering the two members unconditionally valid. ε and buffer geometry are not device-level quantities: they do not enter address arithmetic, and the index is derived state (D21 (Boundary Between Authoritative and Derived States)) => criterion "whether address arithmetic carries device identity" does not apply. Four-way verification of criterion (checked on Linux 6.17 and OpenZFS master on 2026-08-27, unverified in this project): bcachefs `bucket_size` **carries** device identity (`bch_extent_ptr` is `{offset:44, dev:8, gen:8}` in `extents_format.h`; addressing written as `div_u64(s, ca->mi.bucket_size)` in `buckets.h`, device `ca` is explicit parameter) => true per-device geometry, not even requiring power of 2; btrfs capacity **carries** (`btrfs_stripe` specifies `devid` and `offset`) => capacity heterogeneity fully supported; btrfs `zone_size` **does not carry** (`fs_info->zone_size` is fs-level scalar, entering `round_down(physical, fs_info->zone_size)`) => differing zone sizes across devices rejects mount with `-EINVAL` (`fs/btrfs/zoned.c` line containing "zone_size != zone_size"); **md/raid0 capacity does not carry** (addressing across multi-zone layout failed to carry device identity) => silent data corruption spanning 5 years—comment in `drivers/md/raid0.h` mentioning "Linux 3.14", where multi-zone (differing disk sizes) RAID0 layout changed accidentally, retaining data but chunk placements differed across devices; upstream fix (`c84a1372df92`, v5.4, cc:stable 3.14+) admitted "It is not possible to determine what layout to use", resolved by adding feature bit (`MD_FEATURE_RAID0_LAYOUT`) and refusing assembly when unparameterized (`raid0.c` "cannot assemble multi-zone" -> `-EOPNOTSUPP`); ⚠️ when disks are equal in size, both layouts coincide without issues (`raid0.c` "nr_strip_zones == 1")—**heterogeneity itself was the trigger condition**. Negative examples also noted: btrfs `btrfs_dev_item` has `sector_size` / `io_align` / `io_width` slots, but writes copies of fs-level constants (`fs/btrfs/volumes.c` lines with "io_width = fs_info->sectorsize"), with no checks reading them—**reserving slots does not equal supporting heterogeneity**. Consequence for this project: whether this criterion applies depends on whether pointer format carries device identity; D19 (Block Pointer Structure & Width Budget) Settled Item 1 settled "position entry carries dev", and D2 (RAID Stripe Policy) Settled Item 2 settled "disks need not be equal in capacity" (confined to addressing correctness). **Testable**: local host lacks zoned/4Kn/rotational disks, but E15 (Validity of Heterogeneous Device Geometry Simulation) proved QEMU can create heterogeneous geometry distinguishable by guests (including negative controls), so fault injection self-test for C17 (Device Geometry as Global Parameter) need not await hardware. E72 (Mount-Time Recalculation of Device Descriptor Table) milliseconds reflect harness `sudo` process overhead rather than mount latency predictions, holding linearly without extrapolating absolute values; entry widths computed across 24 / 40 / 64 bytes are assumptions unsettled in repository; heterogeneity only tested `physical_block_size` dimension (`losetup --sector-size` creating 512/4096 mixed), while media types, stripe geometries, and layouts require QEMU and remain owed.

**Basis**:

- E72 (Mount-Time Recalculation of Device Descriptor Table): On real heterogeneous loop pools, table byte size is exactly `device count * entry width` (2/4/8 devices across three candidate widths all hold), recomputation time linear with device count without quadratic terms => tracking geometry per device in a single table is computationally viable.
- User settlement, original words in changelog.

**Owed**: C17 (Device Geometry as Global Parameter).

#### Settled Item 4: Which items to compare at mount time

**Settled**: **Any geometric quantity entering address arithmetic must be compared per device; quantities outside address arithmetic are not compared.** This is the mount-side dual to Settled Item 3 criterion—**heterogeneous quantities must be tracked and compared per device; non-heterogeneous quantities must be equal pool-wide, rejecting mount on mismatch**.

| Comparison Item | On Mismatch | Why in List |
|---|---|---|
| `physical_block_size` | **Reject writable mount** | Root slot width carved per this value (D22 (Synthesizing Unit Atomicity) Settled Item 2 + I-7.5 (root slots aligned to the judged width)); C47 (Root Slots Not Aligned to the Judged Width) requires verbatim "mkfs carves per pool `max`, mount recomputes and compares per device" |
| Device capacity | Smaller => **reject**; larger => allow and note | Shrinking implies allocated placements may fall outside device, while allocation records cannot judge per placement (D3 (Space Allocation) Settled Item 1) whether placement remains on disk |
| Device identity (dev ID in table <-> physical device) | **Reject mount** | Position entry carries dev (D19 (Block Pointer Structure & Width Budget) Settled Item 1), mismatch => all addressing targets wrong disk, matching md/raid0 5-year silent corruption in Settled Item 3 |
| Which layout device uses (incompat bit) | **Reject mount** | Settled Item 1: unrecognized layout must not mount |

**Scope**: **Not in list**: rotational speed, queue depth, `io_opt`, discard support—they do not enter address arithmetic; changes affect performance only, and comparing them produces false mount rejections. ⚠️ Each item must be test-forced into the "mismatch" branch (.claude/rules/fs-design.md Hard Requirement 2)—a check that never fires looks identical to an absent check in mount logs. `io_min` enters this list per D2 (RAID Stripe Policy) Settled Item 19, with its two mount gates setting only (a) in first version (C82 (io_min not on the mount comparison list)). First version has two homogeneous disks without writing device descriptor table; capacity and layout bit checks degenerate to cross-disk comparison (Settled Item 5).

**Basis**:

- E72 (Mount-Time Recalculation of Device Descriptor Table): On real heterogeneous pools, four comparison items were forced red individually (disk 1 `--sector-size` 4096 -> 512 remount judged `refuse_rw`, `truncate` to half judged `refuse`, `truncate` to double judged `allow_and_note`, swapping two disks judged `refuse`, changing layout bit to 2 judged `refuse`), **each time only the corrupted item turned red**—isolation demonstrates they judge distinct quantities; the "do not compare" rule was also verified, as `blockdev --setra` altering read-ahead allowed recomputation to pass => non-table quantities do not cause false alarms.
- User settlement, original words in changelog.

**Owed**: C82 (io_min not on the mount comparison list).

#### Settled Item 5: First version implements only standard SSD layout

**Settled**: The first layout line is a pure SSD branch; HDDs do not enter Phase 1. **Measurement basis for "standard SSD": no requirement for FDP / ZNS or special device interfaces.** **Device descriptor table**: first line uses two homogeneous disks and is not written in Phase 1; must be written before adding second layout. Capacity / layout bit / `physical_block_size` checks in Settled Item 4 degenerate to cross-disk comparison in Phase 1; `physical_block_size` is no longer merely cross-comparison—system configuration geometry section added 4-byte "mkfs `physical_block_size`" (D22 (Synthesizing Unit Atomicity) Settled Item 9, 512 in Phase 1), compared against probed value at mount time, providing a second independent input in Phase 1.

**Scope**: Settles "which layout in Phase 1", not "how many layouts in total"—ultimate goal remains multi-media without altering Settled Item 1, with no conflict between the two. Basis for "no FDP / ZNS required" is D26 (Background Compaction and Placement Reclamation) settled on same date demoting device interfaces to "use-if-available acceleration"; requiring FDP in Phase 1 would contradict it. **What it buys**: multiplier for all eight debts in Settled Item 7 is 1 in current phase—each layout writes one checker, runs crash-point replay once, maintains one set of golden images, with gate wallclock scaling by layout count; in Phase 1 N = 1, counted as single copy, which is Settled Item 5's sole, tangible gain. **What must not be skipped**: ⚠️ layout identity still enters format, incompat bits still allocated, "device -> layout" table still retained—"only one set, so no need to mark" is the easiest mistake induced by this settlement, buying negative value: skipping markings causes old implementations reading new images to silently misinterpret upon onboarding a second layout, exactly what Settled Item 6 basis eliminates; Settled Item 2 assigned that table to bucket 1 "must share" because of chain starting point, and having one layout in Phase 1 does not alter that cycle. **Scope contractions (conclusions unchanged, support thinner)**: D8 (Core Index Structure) Settled Item 2 (16 KiB nodes) originally had support from both byte-dominated and seek-dominated regimes rejecting 128K–256K => Phase 1 retains only byte-dominated regime in scope, leaving conclusion unchanged with support reduced from two sides to one; D8 (Core Index Structure) crossover point `K/N > sequential cost / random cost` originally cited "rotational ~1%, SSD ~10%" => Phase 1 takes only SSD tier; heterogeneous pool test objects in Phase 1 reduce to capacity and block size differences among SSDs, while E15 (Validity of Heterogeneous Device Geometry Simulation) proved QEMU generates distinguishable geometry, keeping path unaffected. **What remains entirely unchanged**: D13 (Verification Route) Settled Item 10 explicitly states "rotational vs SSD lands in **device layer**, not transaction layer protocol" => commit protocol, crash semantics, and equivalence class count (D17 (Implementation Layering & Third-Party Pipeline) Settled Item 2) remain untouched; Settled Item 5 does not touch transaction layer or Settled Item 2 three buckets. **Linkage with D26 (Background Compaction and Placement Reclamation)**: standard SSD is where D10 (True Answer to Random Writes / Fragmentation) originally had its gap => D26 (Background Compaction and Placement Reclamation) Leg 1 shifts from "pluggable later" to primary battlefield of Phase 1; without FDP / ZNS on target media, fragmentation must be borne by in-house layer; ⚠️ yet it still does not alter new-pool file creation bytes—D26 (Background Compaction and Placement Reclamation) items remain unaffected by Settled Item 5, compaction remains background, unrun in first runnable milestone. ⚠️ D26 (Background Compaction and Placement Reclamation) Settled Item 7 settles reclamation dividing into two tracks, delegating to disk when disk FTL is adequate without building software FTL; where standard SSDs land depends on switching criteria in D26 (Background Compaction and Placement Reclamation) Unsettled Item 8, before which "fragmentation must be borne by in-house layer" holds only if landing on in-house track; which track reclamation takes is handled via feature bits in system configuration per disk, with tier (incompat / compat_ro / compat) unsettled, and whether it occupies a separate bit or follows Settled Item 1 layout bit unsettled (D26 (Background Compaction and Placement Reclamation) Unsettled Item 10). **What reopens this item**: supporting HDD or ZNS within Phase 1; or freezing second layout before Phase 1 ends (whereupon D15 (Format Freeze Policy) freeze layers must answer "whether freezing one layout counts as freeze").

**Basis**:

- User settlement twice (Phase 1 implements only standard SSD; device descriptor table unwritten in Phase 1, modified alongside D22 (Synthesizing Unit Atomicity) Settled Item 15), original words in changelog.
- No experiments: Phase 1 layout selection is scheduling, not a measurable quantity; "debt multiplier = 1" is arithmetic of Settled Item 7 eight items.

**Owed**: None. C635 (No machine-readable marker for the last full run) (merged from C20 (Rare Layouts Nobody Runs)) is resolved; it is judged by the last-full-judgement cell of gate checker-tier-crash-point-replay (when the current pass has not run a full run, it may still exit 77 as before).

#### Settled Item 6: Branch by media, no single layout with parameters

**Settled**: **Multiple media each first-class, with dedicated disk layout.** **No "single layout + parameters derived per media".**

**Scope**: Two rationales, second independent of model assumptions—**explicit branches are more reliable than clever generalized paths, reducing misread/miswrite probability** (.claude/singlefs-ai-sop/rules/machine-first.md corollary 1, extended by D12 (Target Media) from code to format); **mechanically harder rationale**: with single layout + parameters, reading an image under wrong media assumptions causes **silent misinterpretation**; with dedicated layouts + `incompat` feature bits, unrecognized layouts **reject mount**. Settled Item 6 governs branching style; whether set count is capped belongs to Settled Item 1, along with prerequisite that each layout occupies one incompat bit.

**Basis**:

- User settlement, original words in changelog.
- No experiments: two failure modes (silent misinterpretation vs mount rejection) represent format-layer mechanism comparisons carrying no measurable quantities; .claude/rules/fs-design.md "whether a format branch is worthwhile depends on whether it turns 'wrongly used' into 'cannot mount'" established this as criterion.

**Owed**: C183 (one incompat bit per layout while on-disk bytes show no difference).

#### Settled Item 7: Debts to pay when opening a layout branch

**Settled**: Eight items, none can be defaulted—

| # | What is Owed | Why Unavoidable |
|---|---|---|
| 1 | **Write a checker for each layout** | "Checker is specification", N layouts mean N executable forms of specifications. Landing in [checks-owed.md](../checks-owed.md) C13 (Checker Judgment Ineffective) / C14 (format changed but checker did not follow) |
| 2 | **Run crash-point replay for each commit protocol structural equivalence class** | Hard Requirement 3: crash semantics may differ. ⚠️ **Multiplies equivalence class count, not layout count**—domain of crash points is transaction layer state machine, and layouts modifying parameters only add no state machine paths. Measurement basis in D13 (Verification Route) Settled Item 10 "the N that must truly multiply" |
| 3 | **Gate wallclock scales by equivalence class count** | C8 (Gate Scope Cannot Be Determined) has nothing checking this inflation ⚠️ Equivalence class count provided by D17 (Implementation Layering & Third-Party Pipeline) Settled Item 2: current value 1, recomputed per segment sequence registry when opening lines |
| 4 | **Each layout must be test-forced into entry** | Hard Requirement 2: provide mkfs toggle overriding automatic criteria to specify layout directly. Inability to enter equals unverified |
| 5 | **Runtime observability of active layout** | Hard Requirement 4: wrong branch causes performance cliff, and cliffs do not alarm |
| 6 | **Layout branches are permanent** | Code branches can be deleted; disk layout branches cannot. **Current cost is zero (no bytes yet, no external users), becoming infinite post-freeze => true cost of D12 (Target Media) determined by D15 (Format Freeze Policy)** |
| 7 | **One set of golden images per layout** | C10 (Historical unit formats unreadable) |
| 8 | **Rare layouts periodically run in full** | C635 (No machine-readable marker for the last full run) (merged from C20 (Rare Layouts Nobody Runs)). Scoping runs by diff leaves unedited layouts unrun forever, allowing rare branches to rot |

**Scope**: These eight items form the acceptance checklist for opening layout lines, not tasks for the first version—in Phase 1 N = 1, current multiplier is 1 (Settled Item 5). Test-forced entry for item 4 is constructible locally: E15 (Validity of Heterogeneous Device Geometry Simulation) proved QEMU creates guest-distinguishable geometry, including negative controls. Nothing prevents inflation of item 3, with criterion being whether "which lines this diff actually touched" can be judged.

**Basis**:

- Five hard requirements of `.claude/rules/fs-design.md` (explicit computable switching criteria, test-forced entry per branch, individual verification including crash-point replay, observable branches, branching variables immutable mid-operation) unfolded item by item at format layer; "permanence" of debt item 6 priced by D15 (Format Freeze Policy) freeze layers.
- No experiments: debt table is an acceptance checklist, with individual costs registered in cited owed checks, carrying no measurable quantities.

**Owed**: C8 (Gate Scope Cannot Be Determined), C10 (Historical unit formats unreadable), C13 (Checker Judgment Ineffective), C19 (Media Verdict Leaking into Transaction Layer).
