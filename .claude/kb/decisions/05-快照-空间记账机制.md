## D5 快照 / 空间记账机制 —— 已定（5 个分项全定；正确性成立；**O(1) 性质已因 D6（快照实现模型） 取多可写头而失效**，退化为每删快照 O(N) 次反向索引查找）

**采用 ZFS 的 birth txg + deadlist 模型。**

- 每个块自带**诞生代号**（birth txg）。
- 删除时把块的代号与**活头记录的 `prev_snap_txg`**（上一个快照的代号）比：
  `birth > prev_snap_txg` → **直接释放**；否则 → 追加进**活头自己的 deadlist**。
- 建快照时把**活头的 deadlist 整个交接给新快照**，活头换一个空的。
- 销毁快照时把它的 deadlist **合并到下一个更新的那一侧**，并按 `birth > prev(S).txg`
  过滤出可释放的条目。不做全盘扫描。

**核心性质：记账是增量维护出来的，不是事后遍历出来的。** 这是 D5（快照 / 空间记账机制）的全部价值。

### 引用区间的充要条件

> **块 b 被快照 S 引用 ⟺ `birth(b) ≤ S.txg < death(b)`**，左闭右开。

| 量 | 定义 | **不是**什么 |
|---|---|---|
| `birth(b)` | 块被**发布**的那个 checkpoint 号 | 不是写请求发出时所在的开放 txg——崩溃后该号会被重发 |
| `death(b)` | 最后一个活引用被摘掉、**且该摘除被发布**的 checkpoint 号；仍在活树里则为 ∞ | 不是 `rm` 返回的时刻（D8（核心索引结构） 走意图分批），也不是空间变得可再分配的时刻（D16（发布语义） 新规则 2） |
| `S.txg` | **S 捕获的最后一个已发布 txg** | 不是「创建操作所在的 txg」 |

⚠️ **「某个落点此刻属不属于现行版本」这个谓词不在 D5（快照 / 空间记账机制） 记**——
它的权威记录点是 D3（空间分配） 已定项 1（分配记录逐落点答得出）。
D5（快照 / 空间记账机制） 出的是其中一半：进了 deadlist 的落点只被快照引用，不在活树里。

`S.txg` 取第二种定义的理由是机制性的：`birth` 的分辨率只到 checkpoint，
取「创建操作所在 txg」会让条件随「快照点放在 checkpoint 头还是尾」在
`birth ≤ S.txg` 与 `birth < S.txg` 之间跳。**定义要选让不变量不随实现位置摆动的那个。**

| 边界 | 判定 | 取错的后果 |
|---|---|---|
| `birth == S.txg` | S **引用**它 | 写成 `birth < S.txg` → 判为「比快照新」→ 立即释放 → **数据丢失** |
| `death == S.txg` | S **不引用** | 写成 `S.txg ≤ death` → 挂在不需要它的快照上 → **空间泄漏 + 归属错** |
| `birth == death` | 任何快照都不引用，可立即释放 | 记账上对，但**物理空间不许在本 checkpoint 内复用**（D16（发布语义） 新规则 2）|

⚠️ **这三行不是三处独立的笔误**（E27（D5 三条可建模的风险路径） 实测，2026-08-29）：
右边界写成 `S.txg ≤ death` **同时命中两行**（`death == S.txg` 与 `birth == death` 都被判成「引用」）
⇒ 一个笔误造成两处泄漏。两种取错的失败方向确实相反（写严左边界只丢数据 1 处、
写闭右边界只泄漏 2 处，零交叉）。

⚠️ **保守默认纪律：判据的任何一个输入取不到或不确定时，默认必须是「进 deadlist」。**
泄漏可被 I-3.6（deadlist 紧界） 检出（**不是 I-3.1（已分配统计对得上）**——
[invariants.md](../invariants.md) 明写「归属错误对它不可见……总账依然平」）、可回收、伤害有上界；
丢失不可逆，且一旦空间被复用就退化成「校验和不匹配、原因不明」，连归因都没了。

### 那个条件是 O(1) 条件，不是正确性条件（E18（D5 在多分叉 / 多可写头下是否报废），2026-08-28 第二轮）

`birth(b) ≤ R.txg < death(b)` **只在 txg 全序（单向线性历史）时等价于可达性**。

| 历史形状 | 判死实活（数据丢失） | 判活实死（泄漏） | 「永不记 death」的泄漏 |
|---|---|---|---|
| 线性（阳性对照） | **0** | **0** | — |
| 一次分叉 | **0** | 8.19% | 8.44% |
| 8 个可写头 | **0** | **29.40%** | **29.40%（逐位相同）** |

按 D5（快照 / 空间记账机制）的 `death` 定义，分叉下判死实活恒为零，**这是可证的**：truth 为真 ⇒ 块在该根的链上没死
⇒ 不满足「所有分支都删过」⇒ `death = ∞` ⇒ 区间判定必为真。
⚠️ **代价是回收能力归零**：8 个可写头档，正确规则与「根本不记 death」逐位相同（均 29.40%），
它用「一块都不回收」换零数据丢失；而维护「是不是最后一个活引用」需要的正是每块的分支覆盖信息
= **引用计数**，正是 D5（快照 / 空间记账机制）想省掉的东西。
⇒ D6（快照实现模型） 取多可写头后，D5（快照 / 空间记账机制）的失效形态是**无界泄漏 + 记账退化到引用计数**。

### 级联方向：并到更新的那一侧（约定 B）

两种约定的差别是**改写已发布快照 deadlist 的频率**，不是改不改写：
另一种约定每一次 kill 都要往一个已发布快照的 deadlist 里追加；约定 B 只在销毁级联时改写一次。
⚠️ 约定 B **不是**「快照的 deadlist 永不改写」——销毁级联的目标
`dsl_deadlist_merge(&ds_next->ds_deadlist, ...)` 里 `ds_next` 本身就是快照。
取它的理由是例外少一个数量级，不是没有例外。
ZFS 实现的就是约定 B（2026-08-26 现查 `module/zfs/dsl_destroy.c`：
`/* Merge our deadlist into next's and free it. */`）。

### 四条前提，越过任何一条它就失效

1. **线性历史**（无分叉）；2. **单一可写头**；3. **每个块在活树里至多一个活引用**；
4. **快照点与 checkpoint 边界对齐**（D16（发布语义） 新规则 1）。

**前提 3 与 reflink / dedup / 块克隆机制上不相容**：有第二个活引用时摘掉其中一个不构成 death，
而判据只看 `birth` 与 `prev_snap_txg`，两个引用的 birth 完全相同
⇒ 第一次摘除就判「立即释放」⇒ 另一个引用悬空 ⇒ **数据丢失**。
ZFS 二十年没有 reflink，2023 年的 block cloning 补的方式是**另加一张带引用计数的表**，
不是扩展 birth/death。⚠️ **任何引入「同一块的第二个活引用」的特性，必须先重开 D5（快照 / 空间记账机制）。**

⚠️ **这条重开条款已经被触发过一次，并已收口（2026-08-30）**：D6（快照实现模型） 已定项 1 定案取「每头一棵自己的树」，而跨头共享的块**就是第二个活引用**。
⇒ 按 D5（快照 / 空间记账机制）自己给出的正确形态收口：**D5（快照 / 空间记账机制）为主 + 稀疏旁表为辅（ZFS 的 BRT 形态）**——
不是把 D5（快照 / 空间记账机制）换成全域引用计数。旁表规模由 E52（两种多可写头机制的运营代价） 量出
（共享 100‰ / 每头 1 万条时 1 000 条；8 头 / 10 万条 / 500‰ 时 50 000 条），
其代价由 E12（攒批的顺序追加 vs 不攒批的随机页读改写） 量出（**装得进缓存几乎免费，装不下时每次删除约 1 次设备 I/O**）。
⇒ **「克隆 / 可写快照要加三条」那一节从备查变成必做。**

**但重开不等于推翻**（E12（攒批的顺序追加 vs 不攒批的随机页读改写），N=5 轮、五种子、每档 200000 次删除）：

**20 万次删除一共触发多少次设备 I/O（中位）**

| | 计数器表装得进缓存 | 2× 缓存 | 8× 缓存 |
|---|---|---|---|
| **D5（快照 / 空间记账机制）（时间序推导）** | **2** | **2** | **2** |
| **全域引用计数** | 512 | ~200,208 | ~350,042 |
| **D5（快照 / 空间记账机制） + 稀疏旁表**（clone 率 1‰） | 508 | ~1,956 | ~3,466 |

块层独立校验：每臂前后读一次虚机内 `/sys/block/vda/stat`（内核自己数的，与被测程序不共享代码、
采样或工具），**九个格子比值全部 1.00**；摘掉 `O_DIRECT` 后块层读数归零而程序计数器不变
⇒ 这条校验路径有判别力，不是摆设。

1. **转折是陡的**：计数器表一旦装不下缓存，引用计数从几乎免费跳到约 1 次设备 I/O 每删除，
   而 D5（快照 / 空间记账机制）这一侧完全不动——它没有计数器可查。
2. **装得下时引用计数几乎免费**（那 256 次读写是一次性冷启动填充）。这是合法结果，不是实现 bug：
   D5（快照 / 空间记账机制）的优势条件是「计数器表装不下缓存」，不是无条件成立。
3. **正确形态是「D5（快照 / 空间记账机制）为主 + 稀疏旁表为辅」**（ZFS 的 BRT 形态）：1‰ clone 率下稀疏旁表
   把代价压回 0.0172，约 100 倍。
   ⚠️ **这条结论的唯一来源是 E12（攒批的顺序追加 vs 不攒批的随机页读改写） 的臂 C，而那条臂
   没有失败条款、也没有阳性对照**（E12（攒批的顺序追加 vs 不攒批的随机页读改写） 正文自陈，标着「未修」）⇒ **没有任何东西证明它的度量有判别力**：
   臂 A / 臂 B 那套块层独立校验与故障注入自检**没有对臂 C 做过**。
   ⇒ 「约 100 倍」只能当**待验的量级指示**，不许当作已验证的收益写进任何判据；
   要用它先补臂 C 的失败条款与阳性对照，然后重跑。

⚠️ **外推边界**：E12（攒批的顺序追加 vs 不攒批的随机页读改写） 的探测用内存全域位图、每块 1 bit
（真实文件系统上 ≈ 128 MB/TB）⇒ **高估了旁表在大盘上的表现，换成真正的稀疏结构必须重测**。
⚠️ **局部性已量出**：删除序列从均匀随机换成顺序，引用计数 8× 档从 174,998 次 I/O 掉到
**391 次（448 倍）** ⇒ 真实负载有局部性时 D5（快照 / 空间记账机制）的优势显著小于主表那个数量级，**必须与主结论一起引用**。
⚠️ E12（攒批的顺序追加 vs 不攒批的随机页读改写） **不回答** checker 代价与崩溃一致性，
也不是 D5（快照 / 空间记账机制）自己的实现（它的臂 A 无快照、无 defer 队列，判据换成掷硬币结果一样）。
⚠️ [checks-owed.md](../checks-owed.md) C12（增量语义共用） 对 D5（快照 / 空间记账机制）同样成立：D5（快照 / 空间记账机制）的记账也是靠一串 `+=` 维护出来的，与生命周期判定用 birth txg 还是引用计数无关。

**克隆 / 可写快照要加三条**（前提 1、2 被越过时；**D6（快照实现模型） 2026-08-30 定案取每头一棵树之后，这三条是必做，不是备查**）：

1. 每个可写头各持一份 `prev_snap_txg` 与一份 deadlist，**新克隆的 `prev_snap_txg`
   必须初始化为 origin 快照的 txg**——置 0 则克隆里删一个继承来的老块会算出「立即释放」，**数据丢失**。
2. **分叉点快照不许销毁**（约定 B 在分叉点没有唯一的 next）。判据是 O(1) 子计数 `children > 1` → 拒绝；
   ZFS 同（`dsl_destroy_snapshot_check_impl`：`/* Can't delete a branch point. */`）。
3. **销毁一个可写头需要第二个结构**（ZFS 的 livelist 形态：ALLOC/FREE 配对、按 birth txg 分组、
   可增量、可 condense）。不承认它，「永不事后遍历」在这条路径上就是假的——
   要释放的是 `birth > origin.txg` 的那批块，散落全树。

### 运行时判定是 O(1)，而且这个 O(1) 要证

```
判定(ptr):
    birth = ptr.birth              // 指针内联字段，零次额外 I/O
    p     = head.prev_snap_txg     // 活头头部一个标量，常驻内存
    if birth > p:  立即释放 → 进 defer 队列（不是直接进空闲表，见 D16 新规则 2）
    else:          追加进 head.deadlist
```

**归约证明**：设删除发生在 checkpoint `d`，P 为此刻最新的快照。
(⇐) 若 `birth ≤ P.txg`：P 已发布 ⇒ `P.txg < d = death` ⇒ `birth ≤ P.txg < death`，∃S 引用它。
(⇒) 若 ∃S：`birth ≤ S.txg < d`，则 S 在删除时已存在 ⇒ `S.txg ≤ P.txg` ⇒ `birth ≤ P.txg`。∎

**它只用了两件事**：txg 全序，以及**判定必须发生在死亡那一刻**。
⚠️ 哪一条破了 O(1) 就没了——D6（快照实现模型） 的候选破第一条，D8（核心索引结构） 的分批删除破第二条。

**销毁快照的代价是 O(deadlist 条目数 + 桶数)，不是 O(全盘)**，
前提是 deadlist **按 birth txg 分桶、桶边界 = 快照 txg**，否则销毁时的过滤退化成全表扫描。

### 与 D8（核心索引结构） 分批删除的交互：待删除结构算作活引用

D8（核心索引结构） 已定无界删除走「写意图 → 分批 → 可续做」，判定因此发生在物理批次那一刻，
而逻辑死亡早得多——归约的第二个前提被破。**D5（快照 / 空间记账机制）取的处置：待删除结构（意图 key、删除中队列）
算作活引用**，于是 `death` = 物理批次的 checkpoint，判定天然发生在死亡那一刻，
**O(1) 保住，且不需要新增任何不变量**。

代价是一个用户可见现象：`rm` 返回之后建的快照会**钉住**那批尚未释放的 extent，
`df` 要等快照死了才回来。已被 I-3.4（可用空间扣待删占用） 与 I-4.7（删除中 inode 有账） 部分覆盖。
**另一条路（把待删除结构算作已死）会破坏 O(1)**：正确的 deadlist 属于「逻辑死亡之后建的第一个快照」，
而那个快照在写意图时还不存在，只能在批次执行时查快照列表。

### 依据：机制推导，D5（快照 / 空间记账机制）自己的实测仍然欠着

第一依据是「运行时判定是 O(1)，而且这个 O(1) 要证」一节的归约证明——**它是证明，不是测量**。

**欠的那次实测现在只剩一格**（E13（D5 的四条风险路径） 四条路径里，建快照边界 / 按 birth 分桶 / defer 队列
已由 E27（D5 三条可建模的风险路径） 还清）：**崩溃重放那一格仍然零覆盖**。稳态 kill 路径不在其中——那条路径没人怀疑。
⚠️ **零覆盖的恰是四条里最危险的一条**：E13（D5 的四条风险路径） 逐字自陈「deadlist 的追加与级联合并**不幂等**
（多重集相加，同一条目追加两次 ⇒ **销毁时双重释放**），这一条是最该红的地方」。
**双重释放是数据丢失方向**，而 D5（快照 / 空间记账机制） 已证的「数据丢失方向结构性为零」只覆盖
稳态下的 death 规则取值，覆盖不了崩溃重放把同一条 deadlist 条目追加两次这一类。
⇒ **前置是块层写记录 + checker + 崩溃点重放 harness，三样都不存在**；
在它跑起来之前，不许说 D5（快照 / 空间记账机制） 的风险路径「验过了」。

**第二依据（别家记录，口径要看清）**：btrfs qgroup 走 extent refcount + 反向索引遍历，
代价是提交时间 +76%、事务等待 +1347%、写吞吐 −25%（btrfs 官方数据，见 [prior-art.md](../prior-art.md)）。
⚠️ 口径是「qgroup 走反向索引」，不是「纯引用计数」，**只能作为旁证**。

**独立印证（2026-08-26）**：bcachefs 的记账由触发器在 key 提交时维护、不靠遍历 btree，
而 `check_allocations` 用全量遍历重建记账——与 I-3.1（已分配统计对得上） 同一个设计。
⚠️ 印证成立的层次是「增量维护 + 遍历校验」这个模式，**不是「birth txg + deadlist」这个机制**
（bcachefs 没有 deadlist）。⚠️ 它那套遍历校验**与运行时共用同一段加减代码**，
因此抓不到「语义本身写错」（[prior-art.md](../prior-art.md) 7.11），本工程不许照搬那个形态。

**格式要求已落地**：**快照列表必须是可枚举的持久结构**，见 I-3.7（活快照可枚举）（checker 未实现）。
扫描式 checker（D13（验证路线） 要求的第二个方向）要判归属需要三样：`birth` 内联在指针里 ✓、
deadlist 自身是可扫描的自描述树 ✓、**全部根的 txg 列表** ❌——第三样是 D5（快照 / 空间记账机制）欠着的格式要求。

**与 D9（加密） 的连锁**：birth txg **不能**当加密 nonce——同一事务里的块共享它，nonce 会重复。

#### 已定项 2（2026-08-30，用户定案 + E54（记账的「代」要保留几代） 实测）：要「代」，代取 checkpoint 号，只保留最近 K 代

**「代」取什么，以及旧代什么时候可以丢 —— 已定（2026-08-30，用户定案 + E54（记账的「代」要保留几代） 实测）：
要「代」；代取 checkpoint 号，并配一条增量丢弃规则，只保留最近 K 代。**

**先说这个「代」是什么**：D8（核心索引结构） 已定项 1 已定记账条目是**幂等完整值**——
一条记账记录写的是「某个统计量**此刻**的完整值」，不是「增加了多少」。
于是同一个统计量会被写很多次，**key 里必须有一段把这些次分开**，那一段就是「代」。

⚠️ **「代 = checkpoint 号」的口径已由 D16（发布语义）已定项 6 收口（2026-09-02）**：
每次发布（fsync 触发的也是发布）checkpoint_txg + 1 ⇒ **代按发布走，不按 5 秒窗口走**。
两条骑手条款直接砸在这里：代段宽度 **≥ 48 位**（2785 发布/秒下 32 位 17.8 天回绕，
E71（记账 key 的条目数与宽度）的宽度算术要按此重算）；
记账条目的**跨发布合并不再可行**（代进了 key）⇒ E54（记账的「代」要保留几代）
的每代「统计量数 × 2」次写是实付值，不是上界。

**它为什么必须存在**（用户定案「需要代」的机制理由）：**根可以回退，账必须跟着回退。**
D22（单元原子性怎么合成） 的根环保留最近若干代根，恢复时可能挂上上一代的根；
若账没有「代」这一维、只有一份就地覆盖的最新值，
**挂上旧根之后账是新的、树是旧的** ⇒ I-3.1（已分配统计对得上） 当场判红，
而那不是 bug，是设计漏了这一维。

##### E54（记账的「代」要保留几代） 把原来那个二选一取消了

此前本项写作「甲（代 = checkpoint 号，不丢）／丙（只留最近 K 代）」二选一。
**实测：甲加一条增量丢弃规则与丙在 60 个格上逐格相同**
⇒ **「代取什么」与「留几代」是两个正交问题**，不是一个二选一。

| | key 数（64 个统计量、100 万 checkpoint） | 对 checkpoint 数的斜率 |
|---|---|---|
| 不丢 | **64 000 000** | **= 统计量数** |
| 保留最近 K = 8 代 | **512** | **0** |

**丢弃满足 `.claude/rules/fs-design.md` 第一格**：要丢的那一代**算得出来**（当前代 − K），
**不用找** ⇒ 是点删不是扫描；触及的 key 数 = **统计量数**，
**与 checkpoint 数无关、与盘容量无关**。代价是每 checkpoint 的记账写次数从
`统计量数` 变成 `统计量数 × 2`（一写一删）。

##### K 取多少 —— 绑在「根最多能回退几代」上，不是一个新的自由参数

| 口径 | 回退深度 | K 下界 | 64 个统计量下的 key 数 |
|---|---|---|---|
| E53（丢一整块盘之后根环还挂不挂得上） **真设备实测**的最坏回退 | 1 | **2** | 128 |
| 保守：根环槽总数 N（任何幸存槽都可能被选中）| N | **N + 1** | N=8 时 576 |

⇒ **K = 根环槽总数 + 1**（保守口径）。⚠️ **N 由 D22（单元原子性怎么合成） 已定项 2 定**，
而那一项只差一个数（要容忍几个失败域 F）⇒ **本项不再是独立的未定项，它跟着 N 走。**
⚠️ **K 下界那张表里的 128 / 576 是按 64 个统计量算的示例，不是预测**——
它写在 D5（快照 / 空间记账机制） 已定项 4 定案之前。按已定项 4 的十一个统计量重算，
同两行是 `11 × 2 = 22` 与 `11 × (N+1)`（N=8 时 99）。**示例保留，是因为它论证的是
「K 跟着根环槽数走」这件事，与统计量个数无关。**

#### 已定项 3：记账的载体形态 —— 记账住一棵独立 keyspace 的 btree，条目是「(统计量, 维度元组, 代) → 完整值」

| # | 定的是什么 | 依据 |
|---|---|---|
| 1 | **载体是 btree 里的 key，不是超级块里的一组标量、也不是盘上一块定长区域** | 定长区域把「有哪些统计量」焊进格式，而 D12（目标介质） 已定按介质开放布局分支、每条线可能各有统计维度。btree key 形态下**加新统计维度不改格式**（bcachefs 2024 年把计数器做成 btree key 的那个形态） |
| 2 | **key = (统计量类型标签, 维度元组, 代号)；value = 该统计量在该代的完整值；合并规则按统计量分：非单调统计量「后者胜」（后者由 seq 定），单调统计量取最大值（今天有已定项 4 第 12、13、14 三项：inode 号水位、清扫水位、最近一次根销毁的代号）** | D8（核心索引结构） 已定项 1 已定「取幂等完整值，接受 key 数量上升」——本项只是把它落到 key 上；取最大值同样幂等、交换、结合，在崩溃后 txg 重发那一格给出更大的水位（浪费号、不复用号），是单调量选它而不是「后者胜」的理由（2026-09-05，D8（核心索引结构） 已定项 6）。「标签 → 合并规则」是盘上语义，统计量登记表立成独立冻结组件（D15（格式冻结政策）） |
| 3 | **走 write buffer 前端，条目自带 seq** | D8（核心索引结构） 已定 write buffer 覆盖「反向索引 / LRU / 记账」三类；seq 是它的第 3 条硬要求（排序丢弃时间序 ⇒「后者」必须由条目自己携带）|
| 4 | **整棵记账树按 COW 挂在根下** | D22（单元原子性怎么合成） 已定项 3 已定「记账结构取 COW，挂父指针下」；最硬的那条依据是 mkfs 预留量——原地形态要预留 32.5 MiB–128.5 GiB，COW 恒为 0 |

**依据（用户定案）**：本项的三个前置全部已定，定案是它们的合取，不是一次新的权衡——
幂等完整值（D8（核心索引结构） 已定项 1）定了 value 的语义；COW 挂父指针下（D22（单元原子性怎么合成） 已定项 3）定了落盘方式；
「权威态 = 单元 + 记账 + 根」（D21（权威态与派生态的分界））定了它必须被根覆盖、且参与格式冻结；
`.claude/rules/fs-design.md` 第一格定了它在**事务提交路径上增量维护**，不在后台扫。

| 买到 | 付出 |
|---|---|
| 加统计维度不改格式；I-3.1（已分配统计对得上） 保住判别力（E14（I-3.1 的判别力：幂等完整值 vs 增量 Δ） 实测幂等 3/3、增量 Δ 0/4）；checker 的扫描式方向能独立重算——value 是完整值，不必重放 Δ 日志 | **key 数量上升**（每个统计量 × 每一代各占一条）。⚠️ **倍数未测**，D8（核心索引结构） 明写量出来之前不许拿它推「记账占多少空间」 |

⚠️ **兜底不变**：若某一类账确实做不到幂等，那一类必须另有一条与运行时**不共享判定代码**的独立重算路径
（[checks-owed.md](../checks-owed.md) C12（增量语义共用））。

   `T_dirty` 的 1%（21 474 836 字节）在 `t × d ≳ 65536` 时被上界臂突破
   （两个过界格 1024×64 与 8192×8 的字节数逐字相同）；按分项计维那条臂在扫过的范围内一格都没过界。
   ⚠️ **K 不进这个条件**——它只线性放大树的总条目数，不放大单次 checkpoint 的写。

⚠️ **「哪几个统计量带树维」D5（快照 / 空间记账机制） 已定项 4 那张表没有列**（它只列了带不带设备维），
E71（记账 key 的条目数与宽度） 按窄读与宽读各跑一臂、**没有替它选一个**：两个读法在同一格差 **14.5 倍**。
⇒ 要拿条目数做任何容量判断之前，这一维先定下来。
⚠️ **key 各段的字节宽度仓里一处都没定过**（已定项 3 只定了形态）
⇒ E71（记账 key 的条目数与宽度） 的字节数按三档宽度各算一次，那是假设不是结论。


### 已定项 5（2026-09-03，用户定案 + E97（记账与分配记录的条目编码））：记账 key 各段的宽度

**`(统计量类型标签 2, 树 ID 8, 设备 4, 代 8)`，value = 完整值 8 字节 ⇒ key 22 字节、条目 30 字节。**

| 段 | 宽 | 依据的等级 |
|---|---|---|
| 统计量类型标签 | **2** | **自由选择**。今天十一个，1 字节就够；取 2 是留扩展余量（已定项 4 自陈清单不封闭、D12（目标介质） 不封顶介质套数），而 E97（记账与分配记录的条目编码） 实测四档 key（7 / 14 / 19 / 22 字节）的树高**恒为 2**，代价曲线是平的 |
| 树 ID | **8** | **自由选择**。上界一条已定条款都指不到（D6（快照实现模型） 定每个可写头一棵自己的树、快照数无上界）⇒ **不许拿一个窄宽度去制造一个设计上限** |
| 设备 | **4** | **随 D19（块指针的结构与宽度预算） 已定项 4**，同一个坐标系 |
| 代 | **8** | **已定条款直接给的**：已定项 2 的骑手条款逐字「代按发布走，不按 5 秒窗口走……代段宽度 **≥ 48 位**」，而 D22（单元原子性怎么合成） 已定项 7 的 `checkpoint_txg` 就是 8 字节 |
| value（完整值）| **8** | 统计量是字节计数，256 TiB 也只用到 48 位 |

**E97（记账与分配记录的条目编码） 给代段配了第一份可执行断言**：模 2³² 的回绕期算出来 **17 天**
（骑手条款写 17.8 天）、模 2⁴⁸ **3204 年**（E44（序号位宽的本机实测与代价） 写 48 位撑 3202 年）；
并实测**任何有限模都只是把破 key 序推迟到回绕那一刻**——模 256 在 257 代出 255 个逆序对、
512 代出 32 640 个，而它 **91 毫秒**就绕完一圈。⇒ **存完整 checkpoint 号，不许取模。**

**用户定案**：先按这个形态落地，写代码时再调整。

⚠️ **这五段还不是一个定得下合并结果的 key。** D8（核心索引结构） write buffer 硬要求 3 逐字
「**条目必须自带序号（seq），这是格式要求**」，而记账条目是幂等完整值、同一个统计量在
**同一个 checkpoint 内会被写很多次** ⇒ `(标签, 树, 设备, 代)` 在一个 checkpoint 内**不唯一**，
去重规则「后者胜」的「后者」要靠 `seq` 定。**`seq` 落在 D8（核心索引结构） 未定项 7，仍未定**——
它进 key 还是进 value，会改这五段的排序契约，**格式冻结之前必须先定它**。

⚠️ **E73（节点 key 区间的扇出代价） 与 E71（记账 key 的条目数与宽度） 当年假设的 22 字节，
与本项定的 22 字节数值相同但拆法此前没人写过**；E73（节点 key 区间的扇出代价） 的扇出结论
按本项重算仍成立（树高恒为 2）。
