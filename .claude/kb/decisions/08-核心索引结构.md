## D8 核心索引结构 —— 半定

**不预设 B-tree。** 调查见 [prior-art.md](../prior-art.md) 第五节。

**方向已定，两处细节待实验取值。**

### 结构

**一套 btree 实现 + 多个独立 keyspace + 两个前端。** 不做异构结构。

| 层 | 做什么 |
|---|---|
| 独立 keyspace | 每类数据一棵树（extent / inode / dirent / 反向索引 / 空闲空间 / 记账 …），互不干扰 |
| 日志结构节点 | 节点内新 key 追加不插入，内存里定期重排；写顺序、可在只读锁下回写 |
| **write buffer** 前端 | 高频小更新（反向索引、LRU、记账）批量攒起来排序去重后批量插入。⚠️ **排序对缓存策略提出要求，见本决策「write buffer 若排序，节点缓存必须是抗扫描的」一条** |
| **key cache** 前端 | 同一批 key 反复读写的（分配信息）走哈希表，不做全树查找 |

依据：bcachefs 用**一套 btree 实现 + 21 棵树**，其中 **5 棵**走 write buffer
（`lru` / `backpointers` / `deleted_inodes` / `rebalance_work` / `accounting`）。
口径：2026-08-29 现查 `linux-6.17/fs/bcachefs/bcachefs_format.h` 的 `BCH_BTREE_IDS()` 宏，
数 `x(` 行与带 `BTREE_IS_write_buffer` 的行；源码固定在 `/home/fy5090/code/fs-refs/`。
⚠️ **此前这里写的是「28 棵树、write buffer 覆盖 10 棵」，两个数都不对，且原文没有口径没有日期。**
本决策的方向不因此改变——「只有一套结构要调对」这条依据不依赖树的具体条数。
这比「按访问模式选不同结构」好在**只有一套结构要调对**——
异构方案意味着 N 套实现、N 套崩溃一致性 bug、N 套 checker。

⚠️ **write buffer 若排序，节点缓存必须是抗扫描的（2026-08-27 实测）。**
[experiments.md](../experiments.md) E7（离线索引 harness） 量到：按叶排序之后，每次 flush 就是一次
**覆盖整个叶子空间的顺序扫描**，而 **LRU 对「反复的、大于缓存的顺序扫描」命中率恰好为 0**——
本决策这一侧在缓存占树 2% / 6% / 25% 三档上的 io/op **逐位相同（1.5755）**，缓存完全不起作用。
干预证实：保持同叶聚合不变、只打乱组的处理顺序，25% 缓存档的读次数降 9.2%（下界）；
而 100% 缓存档打乱前后完全相同（阴性对照）。

⇒ **排序会摧毁局部性而不是创造它，除非缓存策略抗扫描（2Q / LRU-K 之类）。**
**这是本决策对缓存策略的硬要求，不是建议。**

⚠️ **write buffer 里的条目形态必须是幂等完整值，不许是增量 Δ（2026-08-27 实测）。**
[experiments.md](../experiments.md) E14（I-3.1 的判别力：幂等完整值 vs 增量 Δ） 量到：同一棵树同一负载，注入四类语义 bug，
幂等完整值形态下 I-3.1（已分配统计对得上） 抓到 3/3 真 bug、盲区 0 格；增量 Δ 形态下**抓到 0/4，
四类全部把账算错而 I-3.1（已分配统计对得上） 全绿**。机制是增量 Δ 形态下账本身就是权威内容，
checker 只能拿同一个累加函数重放同一份 Δ 日志，**它在和自己比**。
本工程因此与 bcachefs 在这一格上分道：其 accounting 树是 delta 形态
（`disk_accounting_format.h` 原文「updates are _deltas_」）。

**这条约束咬得最紧的是记账那一棵**——「释放了 4096 字节」的自然表达就是 Δ。
**尚未解决**：记账怎么表达成幂等完整值。已知的方向是把 key 细分到
「某个统计量在某一代的完整值」（写入时整格覆盖，合并 = 后者胜），
代价是 key 数量上升。**这是 D8（核心索引结构） 的一个未定项，不是已定项。**
若某一类账最终确实做不到幂等，那一类必须另外具备一条与运行时**不共享判定代码**的
独立重算路径——[checks-owed.md](../checks-owed.md) C12（增量语义共用） 是它的门禁形态。

⚠️ **write buffer 的条目必须自带序号（seq），这是格式要求（2026-08-27 起已知，2026-08-28 由 E17（write buffer 合并上限） 逼出可判定形态）。**
flush 时按 key 排序**丢弃时间序**，而去重规则是「后者胜」——
**排序之后「后者」这个概念必须由条目自己携带**。用不稳定排序时同 key 条目的相对次序未定义，
**去重结果因此不确定**。
⚠️ 它与「条目必须是幂等完整值」是**两条不同的要求**：
幂等管「重复应用不出错」，序号管「谁覆盖谁是确定的」。
发现经过：[experiments.md](../experiments.md) E17（write buffer 合并上限） 第一版漏了 seq，两条臂与真值当场对不上。

**已知代价**（原文明写）：write buffer 的更新无序且最终一致，
flush 时按 key 排序丢弃时间序，且这个 sort-merge-sweep **本质单线程**，
在多线程负载下它的效率是关键路径。

⚠️ **「单线程是关键路径」这句有两种读法，实测结果相反，必须分开写（2026-08-28 第二轮）。**

| 读法 | 判定 | 依据 |
|---|---|---|
| **线程读法**：合并的 CPU 吞吐撑不住多线程负载 | **不成立** | E17（write buffer 合并上限）：单线程 30.9–31.6M 条目/秒，且按叶分区可并行 6.38×（16 线程） |
| **I/O 读法**：flush 的树插入 I/O 是关键路径 | **成立，而且它是三项里最大的一项** | E7（离线索引 harness） 实测 `logstruct_wb` io/op = 1.5755；按每 4 KiB 用户写 3 条条目折算约 **4.65 µs**，对比加密 1.0 µs、合并 0.13 µs |

⇒ **本条批注只限定于线程那一侧。** 详见 [experiments.md](../experiments.md) E17（write buffer 合并上限） 的数与它的边界。
单线程 sort-merge-sweep 做到 **30.9–31.6M 条目/秒（707–724 MiB/s，两轮独立运行）**——
按每 4 KiB 用户写产生 3 条缓冲条目算，单线程能撑 **42.2 GB/s** 用户写带宽；
即使每 4 KiB 产生 10 条也能撑 12.6 GB/s。
而 E6（加密算法选型） 实测加密单核是 4.1 GB/s（有 AES-NI）/ 0.28 GB/s（无 AES-NI）。
⇒ **关键路径上真正卡住的是 D9（加密）的加密，不是本节的合并。**
且**按叶分区的无锁并行现成可用**：16 线程 **6.38×**、32 线程 **6.96×**（N=5 取中位），
阳性对照同档 **11.91×**——散射那趟吃掉 46%（16 线程）到 55%（32 线程）的加速，但没把收益吃光。
⚠️ E17（write buffer 合并上限） 只量了合并这一段，不含树插入与 I/O，给的是**合并步骤的上界**。

### 已定项（2026-08-26）

**1. key 布局：改名与索引分开处理 —— 采纳，方向已定**

原来的问法「按 inode 还是按路径」是个假二选一。**scan 局部性不一定要住在 key 序里**，
它可以住在四个不同的地方：

| 局部性放在哪 | scan | 改名 | 代表 |
|---|---|---|---|
| key 序（全路径索引） | 最好 | **O(子树深度)**（BetrFS 0.4 的 lifted Bε-tree，FAST 2018，本项正文有修正说明） | BetrFS 0.4 |
| 分配器（把子目录的数据放到父目录附近） | 好 | 免费 | ext4 Orlov 分配器：遍历内核树快 30%。⚠️ **未核实**——kb 内无出处、无口径（谁测的、什么数据集），要用先补 |
| 第二索引 | 好 | 仍然贵 | —— 且要多维护一份一致性 |
| **出生时继承、改名不更新的 locality 前缀** | 较好 | 免费 | 本工程方向 |

**⚠️ 这张表的第一行在 2026-08-26（其四）被修正，采纳结论因此需要重新权衡。**

BetrFS 0.4（FAST 2018）的 lifted Bε-tree 把全路径索引的改名代价
**从「子树大小」降到「子树深度」**——论文复杂度一节明写：tree surgery 里被切分或合并的
节点数「at most proportional to the height of the tree」。
机制与论文自陈的代价见 [prior-art.md](../prior-art.md) 5.6。
换言之，「全路径索引改名代价爆炸」这条前提**对 2018 年之后的实现不再成立**。

**但采纳结论不因此自动翻转，因为全路径索引在本工程还有三条 BetrFS 不必付的代价：**

1. **与 D9（加密）加密直接冲突。** 全路径索引意味着 btree 内部节点的分隔 key 就是路径，
   而 D9（加密）未定项 5 已经认定「dirent 树的分隔 key 就是文件名」是敏感信息。
   全路径索引把这个泄漏面从 dirent 一棵树扩大到**所有按路径编 key 的树**。
2. **与 D1（数据可移动性 / 反向索引） 反向索引的稳定性冲突。** 反向索引要回答「这个物理块被谁引用」，
   引用方的身份如果是路径，改名就会让所有反向索引条目失效；按 inode 编 key 则不会。
3. **lifting 对 key 编码提出的额外要求还没有和 D9（加密）的 nonce 载体、D6（快照实现模型） 的快照 ID 位置对过账**，
   三者抢的是同一段 key 空间。

**结论：维持采纳第四种（继承式 locality 前缀 + dirent 树），但理由改写。**
理由不再是「全路径索引改名代价爆炸」（该前提已被修正），
而是**「全路径索引与 D9（加密）加密的泄漏面、D1（数据可移动性 / 反向索引） 反向索引的稳定性冲突」**。
两条路的定量差距由 [experiments.md](../experiments.md) E9（key 编码对遍历局部性的影响） 量。

**采纳第四种**：key = `(locality_id, inode, offset)`。
`locality_id` 在创建时从父目录继承，**改名时故意不更新**。

- 命名走 dirent 树（`parent, name` → inode），改名就是删一条加一条，**O(1)**
- 数据按 inode 编 key，与名字彻底解耦
- scan 局部性来自继承的 `locality_id`，改名后**局部性缓慢退化，正确性不受影响**
- 退化由常驻后台整理修复——**D3（空间分配） 已经承诺了常驻后台整理，这里是复用，不是新增负担**

这条把改名代价换成了「局部性慢慢变差」，而后者是可以在后台慢慢还的债。

**批量改名（2026-08-26 补）**：`mv 大目录 别处` 在这个设计下**只改一条 dirent**——
子项按 inode 编 key，key 里没有路径，改名碰不到任何后代。这正是选它的理由。

但有三处会把改名重新变成无界操作，**必须一开始就堵死**：

1. **`locality_id` 永远不许被改名更新。** 一旦「改名后重新聚簇后代」进了同步路径，
   改一个大目录就要动几百万个 key。`locality_id` 是**提示，不是正确性的一部分**——
   它可以是错的、可以过期，不影响任何语义。
2. **改名覆盖已存在的目标 = 一次删除**，若目标是大文件/大目录，
   这条路径必须走本节第 3 项「whiteout 删除」定的 intent log，不能因为「这是改名」就绕过。
3. **后台重新聚簇必须是增量、可中断、可续做的**，且随时可以停掉不做。
   它是优化，不是义务。

**推论（可当 review 判据用）**：**任何让 rename 触及后代的设计改动，一律否决。**

**已验证**（[experiments.md](../experiments.md) E9（key 编码对遍历局部性的影响），2026-08-28 复跑定稿，5 种子取中位）：
按 inode 编 key 时递归遍历比 `locality_id` 前缀慢 **1.46×**（全新树），
**⇒ `locality_id` 值得做**——差距远超测量噪声（极差 3.0%）。

⚠️ **这个数只在一个特定口径下成立，引用它必须连口径一起引**：
必须是**交错创建**（`interleave`，老化的代理）**加上 `cache_leaves = 8`**。

- **depth-first 创建时三条真实臂逐位相同**：每个目录的 24 个文件拿到连续 inode，
  而 `locality` 是 `path[0]`、在深度优先创建下是 inode 的单调函数 ⇒ 两条臂排序完全一致。
- **比值随节点缓存从 1.00 摆到 8.60**：`cache_leaves` 取 4/8/16/32/64/128 时
  分别是 1.18 / **1.46** / 3.01 / 8.60 / 6.05 / 1.00。
  **缓存装得下整棵树时四条臂全部相等，效应消失。**

⇒ **报「1.46 倍」而不报缓存档，等于报了一条曲线上的一个点。**
⚠️ **收益随改名衰减，量出来的曲线是**：

| 改名次数 | locality 相对纯 inode 省 |
|---|---|
| 0 | **1.462×** |
| 500 | 1.081× |
| 2000 | 1.021×（已落到噪声量级） |
| 5000 | **0.996×**（略微反超） |
| 20000 | 1.002× |

⇒ 「改名后局部性缓慢退化」成立，而且**衰减到基本不值钱**。
`locality_id` 的收益是**新树的收益**，不是稳态收益。
⚠️ 改名强度的现实性未校准——曲线可用，绝对刻度不可用。
⚠️ **复跑把衰减推得更远**：改名 2000 次后降到 **1.021×**，5000 次后 **0.996×**（略微反超）。
⇒ 「衰减到基本不值钱」这句成立，而且比原表更彻底。

**全路径索引的遍历优势也量出来了：相对 locality 前缀 7.38×、相对纯 inode 10.80×**
（`interleave` + `cache_leaves=8`，与本节改名衰减表同一口径；2026-08-28 复跑值，
此前记的 7.34× / 10.78× 是同一实验早前一轮）。
⚠️ **「每次改名平均重写约 2700 个 key」这个数缺口径**：查不到它是哪一档改名、哪个种子算出来的，
按 `.claude/singlefs-ai-sop/rules/kb-discipline.md` 第 2 条标为**未核实**，
要用它先复跑一遍。
⚠️ **这个数不推翻本决策**——维持采纳 locality 前缀的理由是 D9（加密）泄漏面与 D1（数据可移动性 / 反向索引） 反向索引稳定性，
E9（key 编码对遍历局部性的影响） 对那两样一个字都没说，不许拿遍历优势去替它们做判断。
见 [experiments.md](../experiments.md) E9（key 编码对遍历局部性的影响）。⚠️ 此处此前误引 E2（key 布局对递归遍历的影响），而 E2（key 布局对递归遍历的影响） 至今未跑。

**2. 节点大小 —— 上限由可恢复性定，靠实验取值**

大节点省 seek、树更浅，但**一个坏节点的爆炸半径随节点大小线性放大**，
与本工程的可重建性目标直接冲突。所以**不照抄 128K–256K**。

⚠️ **「爆炸半径」这个说法已被实测纠正**（[experiments.md](../experiments.md)
E30（坏一个节点的爆炸半径），2026-08-29，三轮字节一致）：

| | 与节点大小的关系 |
|---|---|
| **索引坏的永久损失** | **恒为 0**——D21（权威态与派生态的分界）已定索引是派生态、「丢了只是慢」 |
| **数据单元坏的损失** | **与节点大小无关**（单元就是单元） |
| **重扫代价** | **随节点大小线性放大**：第 1 层节点的重扫量恰等于扇出，2 KiB 的 49 到 64 KiB 的 1636 |

⇒ **节点大小换的是「恢复时间」，不是「数据安全」。**
本项的目标线该定在恢复时间上，不是「重建成功率」上。
⚠️ 这条推理有一个前置：索引可从单元自描述重建——
E29（明文映射层能不能只靠单元自描述重建）实测**元数据侧成立、数据块侧今天不成立**
（欠 D18（块里携带什么信息）未定项 3）。

取值靠实验定，判据与失败条件见 [experiments.md](../experiments.md) E1（节点大小 vs 可恢复性）：
在「全盘扫描重建成功率 ≥ 目标线」的前提下取查找代价最低的那档。

**按设备特性动态选取（2026-08-26 补）—— 采纳，但有三条约束**

节点大小写进超级块，**mkfs 时按设备特性自动选取**，可显式覆盖。
参考量：旋转介质 vs SSD（seek 代价差一个量级）、设备容量、
以及 flash/zoned 设备的擦除块或 zone 大小。

**2026-08-27 有数了**（[experiments.md](../experiments.md) E7（离线索引 harness） 节点大小扫描，
3 档 × 5 种子，**固定约 1 MB 缓存预算**）：

| 节点 | 缓存占树 | Bε 的 io/op | Bε 的字节/次 | 点查读/次 |
|---|---|---|---|---|
| 4 KiB | 25% | 0.3176 | 1,301 | 0.777 |
| 16 KiB | 6% | 0.3994 | 6,544 | 1.225 |
| 64 KiB | 2% | 0.6384 | 41,841 | 1.779 |

**固定内存预算下，大节点在三个轴上全都更差**——机制是**节点越大，
同样的内存装得下的节点越少，命中率掉得比「每次读更多」赚回来的更快**。

**两端都测过了，方向同向**（[experiments.md](../experiments.md) E7（离线索引 harness） 寻道主导档，2026-08-27）：
在「每次 I/O 代价相同、与请求大小无关」这个寻道主导的极端上，大节点仍差 **13.8%**
（无批量对照，87.13 → 99.18 s）与 **100.7%**（Bε，15.90 → 31.91 s），本决策方向持平。

⚠️ **上面两端量的都是设备 I/O，而第三条轴方向相反**：
[experiments.md](../experiments.md) E20（指针变宽的 CPU 缓存代价） 实测 CPU 缓存那一侧——同样 40 字节的指针头部，
**4 KiB 节点付 +98%，16 KiB 节点只付 +14%**，即**大节点吸收指针变宽**。
⇒ 「两端都得到支持」这句话只对设备 I/O 成立；节点大小的自动选取判据里
**必须含指针宽度这一项**，此前没有。
⇒ **「不照抄 128K–256K」在字节主导与寻道主导两端都得到支持。**

⚠️ **「按设备特性选取节点大小」这条没有本工程自己的实测支撑。**
两端的最优方向相同，都偏小。节点大小仍是 mkfs 参数，
但**「按介质取相反方向」这个理由不成立**。要保留按介质调档，需要另找依据。

约束：

1. **它是 mkfs 时的格式参数，不是挂载参数。** 建完就固定，
   自动选取只发生在 mkfs 一次。

   ⚠️ **「改它等于重建文件系统」这半句已被 D21（权威态与派生态的分界） 取消（2026-08-29 审计）。**
   D21（权威态与派生态的分界） 已定索引是**派生态**，逐字：「派生态的格式**随便变**，因为它整个可以从单元重建出来」，
   且冻结第 2 层「降级为**本地缓存格式**」。⇒ 改节点大小 = **重建索引**，不是重建文件系统。
   ⚠️ **取消的是「等于重建文件系统」这个定性，不是「代价很小」。**
   E30（坏一个节点的爆炸半径） 自己的数就在旁边：坏根要重扫**全部 16777216 个单元**，即全盘扫描。
   而改一个全局的节点大小参数会让**整棵树**按新尺寸重建，规模与坏根同一量级。
   ⇒ **它是一次满量级的全盘 I/O，只是不丢数据**——范畴变了（数据幸存 vs 数据丢失），
   代价没变小。把「不是重建文件系统」读成「随时可以改」是误读。

   ⚠️ **而且这个取消有一个未满足的前置**：E29（明文映射层能不能只靠单元自描述重建） 实测
   重建在**元数据侧成立、数据块侧今天不成立**（缺口恰等于数据块总数），欠 D18（块里携带什么信息） 未定项 3。
   ⇒ **补上数据块自描述之前，这半句在数据块那一侧仍然成立。**

   ⚠️ **这里有一步桥接，本决策把它写明，因为它此前是被默认的**：
   E29（明文映射层能不能只靠单元自描述重建） 测的对象是**明文映射层**（逻辑身份 → 物理地址那张扁平表），
   而本节说的是**索引树**的重建——**两者不是同一个东西**。
   桥接的依据是它们**读同一份输入**：D21（权威态与派生态的分界） 逐字「扫一遍全盘就能把内容取出来」，
   靠的是每个单元自带「我是谁、我属于谁」；E29（明文映射层能不能只靠单元自描述重建） 量的正是这份自描述够不够。
   ⇒ 数据块自描述为零 ⇒ **两种重建在数据块那一侧同时不成立。**
   ⚠️ **这是推理，不是实测**——E29（明文映射层能不能只靠单元自描述重建） 只测了明文映射层那一个实例，
   索引树的重建从未被单独量过。按 `.claude/singlefs-ai-sop/rules/evidence-discipline.md` 标明。
   连锁：D11（索引节点要不要留消息缓冲区） 「不能拖」的**全部理由**就是这半句，见该决策。
2. **默认策略必须是确定性的、可查的。** 同样的设备特性必须得到同样的取值，
   并且 mkfs 要把「为什么选了这个值」打出来。
3. **测试钉死的是「模拟设备的参数」，不是节点大小本身。**
   QEMU 可以模拟旋转标志、容量、块大小、discard 粒度，
   所以测试环境固定一组设备档位，让自动规则照常跑——
   这样**连选取规则本身也一起被测了**，比绕过它更好。
   要求只有一条：**同一档位必须得到同一取值**，否则
   `test-discipline.md` 的「N≥5 轮全通过」和镜像差分比对会一起失效。

**3. whiteout 删除 —— 接受，但批量删除必须走 intent log**

接受日志结构节点带来的 whiteout 删除。但**批量删除是这个设计最危险的地方**：
删大目录、截断大文件会产生海量墓碑，想塞进一个事务必然爆掉。

**做法（bcachefs 已验证的形态）**：
凡是**可能修改无界数量 extent** 的操作（truncate、collapse、删大目录），
不做成一个大事务，而是**先把意图写进 logged_ops 树，再分批推进**；
崩溃后恢复时续做未完成的意图。删除中的 inode 单独进 `deleted_inodes` 树，
由后台回收——用户的 `rm` 返回，不等于所有 extent 都已释放。

**硬要求**：
- 无界规模的操作**一律不许做成单个事务**，必须是「写意图 → 分批 → 可续做」
- 意图必须**幂等**：续做时重复执行已完成的部分不能出错
- whiteout 在节点重写合并 bset 时清除，**不许有别的清除路径**

**断电之后怎么办（2026-08-26 补）**

意图本身就是一条普通 key，**骑在同一个事务层上**（`.claude/rules/fs-design.md` 第 6 条），
所以它和别的元数据一样受崩溃保护。断电后只可能落在三种状态，每种都有确定的出路：

| 断电时机 | 恢复后看到 | 怎么收场 |
|---|---|---|
| 意图提交之前 | 没有意图 | 操作从未发生，用户那边也没返回成功 |
| 意图已提交、工作做了一半 | 意图还在 | 恢复时**续做**；已做完的部分被幂等地重跑一遍 |
| 工作做完、意图未删 | 意图还在 | 续做一遍发现无事可做，然后删掉意图 |

不可能出现「意图没了但目标状态没达成」——因为**删除意图必须与最后一批工作在同一个事务里提交**。

由此得到三条设计规则：

1. **意图声明目标状态，绝不声明增量。**
   「把文件 X 截到 N 字节」可以重复执行，「再删 1000 个 extent」不能。
   任何写成 delta 的意图都是错的。
2. **续做是每次恢复都跑的常规动作，不是修复手段。**
   把它做成可选的修复通道，就会出现「平时不跑、真出事时才第一次跑」的代码路径。
3. **中间状态必须每一个都是合法的文件系统状态。**
   分批推进意味着任何一批之间都可能断电，
   所以「删了一半 extent 的文件」本身就得是合法的。

**范围重建 vs 逐项修改：切换判据（2026-08-26 补）**

无界操作有两条实现，**都要有，并且要有显式判据决定走哪条**
（`.claude/rules/fs-design.md`「不追求万能方案」）：

| 走法 | 代价 | 适用 |
|---|---|---|
| 逐项修改 | K × 随机访问 | 受影响的 key 稀疏散布 |
| 范围重建 | N × 顺序访问（读一遍写一遍） | 受影响的 key 在 key 序上连续 |

朴素的交叉点是 `K/N > 顺序代价/随机代价`——机械盘上这个比大约 1/100，
SSD 上大约 1/10，即**机械盘碰超过约 1% 就该重建，SSD 要碰到约 10%**。
⚠️ 这两个数是**推理，不是实测**，要靠 [experiments.md](../experiments.md) E4（范围重建 vs 逐项修改的交叉点） 量。
**它们说的是耗时的交叉点，至今仍未实测**——介质影响时间，那一半要 QEMU。

**写放大那一半已量**（[experiments.md](../experiments.md) E31（交叉点的写放大那一半），
2026-08-29，100 万叶、三轮字节一致）：

| 节点 | 条目连续 | 条目散布 |
|---|---|---|
| 4 KiB | **1000‰**（要全改才划算） | **10‰** |
| 16 KiB | **1000‰** | **3‰** |

⇒ **在写放大口径下，交叉点的自变量是「布局」与「节点大小」，不是介质**，
两者相差两个数量级以上。这与本节「真正的开关不是 K/N，是受影响的 key 连不连续」那句
**是同一个结论的两种说法**——本决策先推出来，实验后来量到了。
⚠️ **不能拿它去证伪「机械盘约 1%、SSD 约 10%」那两个数**：那说的是耗时，本实验对介质一个字没说。

**但真正的开关不是 K/N，是「受影响的 key 连不连续」**：

- 连续 → 范围重建可以**整节点丢弃或整节点重写**，是顺序操作
- 不连续 → 只能逐项，重建也快不起来

**由此得到一条布局规则：让一起死的东西在 key 序上挨在一起。**

- dirent 按 `(parent_inode, name)` 编 key → 删整个目录是范围操作
- extent 按 `(inode, offset)` 编 key → 截断是范围操作
- 同一快照的 key 带同一 snapshot 前缀 → 删快照有机会变成范围操作

**这顺带从结构上解掉了 whiteout 膨胀**：范围删除直接丢弃整个节点，
根本不用插 N 个墓碑。墓碑只在「稀疏删除」这一条分支上产生，而那条分支本来量就小。

按 `.claude/rules/fs-design.md` 的五条要求，这个分支还欠：判据写成可计算的式子、
留一个能强制走指定分支的测试开关、两条分支各自跑崩溃点重放、
运行时能看出走了哪条。

⚠️ **切换判据里不许出现「当前填充率」这类操作中途会变的量**——
一个无界操作跑到一半判据翻转，恢复时走了另一条分支，要验的就是叉积。
判据只能用操作期间稳定的输入（介质类型、受影响 key 是否连续、操作开始时的规模估计）。

**与 D3（空间分配） 的交互（容易漏）**：意图未完成期间，那些空间**还没真的释放**。
空间统计必须把「待删除但未完成」计进去，否则会出现
「我删了一大堆，`df` 却不动」——那正是避坑清单里 btrfs 被抱怨的那类现象。
