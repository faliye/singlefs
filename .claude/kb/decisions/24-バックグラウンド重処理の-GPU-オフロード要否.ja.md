## D24 バックグラウンド重処理の GPU オフロード要否 —— 確定

[中文](24-后台重活能不能卸给GPU.md) · [English](24-offloading-heavy-background-work-to-gpu.en.md) · **日本語**

D24 (バックグラウンド重処理の GPU オフロード要否) は一つの事項を管轄する：三つのバックグラウンド重処理（バッチ圧縮、全ディスク scrub、大規模消失訂正符号再構築）を GPU へオフロードすべきかどうか。バックグラウンド整理（GC 移動とパッキング移転）の計算を GPU に置くことはこの三つに含まれない：ユーザーが実施を決定し、スイッチと運用ポリシーは D26 (バックグラウンド整理と配置回収) 確定項目 13 にあり、一組のパラメータが全バックグラウンドタスクを管轄し、確定項目 2 の三つのハード制約は同様にそれを管轄する。管轄外：CPU 側のアルゴリズム選択は D9 (暗号化) 確定項目 3；scrub 本体の形態は D9 (暗号化) 確定項目 5；バックグラウンド整理と回収のキューと予算は D26 (バックグラウンド整理と配置回収)；三区分自体は `.claude/rules/fs-design.md` の会計規律であり、D24 (バックグラウンド重処理の GPU オフロード要否) はそれを引用するのみである。

### 確定項目

| # | 項目 | 決定事項 |
|---|---|---|
| 1 | **実装の要否** | 延期、スケジューリング外；延期は否決と同義ではなく、計算能力制約セルは維持、GPU 系列の計測は継続しない **状態: 確定。** **進捗: 未実装。** |
| 2 | **3つのハード制約** | 決して必須としない（フォーマットに1ビットも持ち込まない）、フォアグラウンドパスへの混入禁止、オフロード結果は必ず再検査、GPU と CPU は二つの実装 **状態: 確定。** **進捗: 対象なし。** |
| 3 | **判定基準の形式** | CPU 側のマルチコア飽和スループットを GPU の2つの転送下限値と比較する形式とし、「単一コア × コア数」や「ハードウェア命令の有無」には依拠しない **状態: 確定。** **進捗: 対象なし。** |

#### 確定項目 1: 延期、実施しない

**決定事項**: **延期、実施しない**——3つの候補シナリオ（バッチ圧縮、全ディスク scrub、大規模消失訂正符号再構築）はいずれもスケジューリング外とする。**延期は否決と同義ではない**：計算能力制約枠（バッチ圧縮）は開いたままであり、単にスケジューリングしないだけである。**GPU 系列の計測はこれ以上継続しない**とし、D24 (バックグラウンド重処理の GPU オフロード要否) は「方向性に疑問があり、両側とも確証が得られていない」状態で停止する——GPU 側には依然として真の AES-GCM カーネル関数（`nvcc` が必要）が不足している。**「GPU の勝利」を確定結論として他の決定を支えるために用いてはならない。**

**適用範囲**: 荷重を受けるのは「非必須」の1点のみである——3つの候補シナリオはいずれも `.claude/rules/fs-design.md` の第3枠（バックグラウンド、再開可能、非決定パス）にあり、それを実施しなくてもいかなるハードな約束にも影響しない。D1 (データ移動性 / 逆インデックス) の縮小や、D3 (領域割り当て) の常駐整理のように公約された能力とは異なる。**実測された枠は候補リストに含まれていない**：判定によって排除されたのは「純粋スキャン」であり、3つの候補の CPU 側はいずれもスキャン上でさらなる計算を行う。したがってタイトル中の「1枠は実測で負の利益」という記述は「候補とは無関係な1枠」と解釈すべきであり、「候補が実測で負と判定された」のではない——その枠の数値と判定法は確定項目 3 にある。

**根拠**:

- ユーザー決定が2回（本件は非必須；GPU 系列はこれ以上計測しない）、原文は変更履歴にある。
- 実験なし: この延期が荷重を受けるのはユーザー決定のみであり、実測で判定排除された枠は純粋スキャンであり候補リストに含まれない（その枠は確定項目 3 に記録）；候補3枠のうち2枠にはデータがなく（消失訂正符号再構築とバッチ圧縮）、測定可能な量が存在しない。

**未済**: なし。

#### 確定項目 2: 3つのハード制約

**決定事項**: 3項目とし、満たされなければ実施を許容しない——

1. **決して必須としてはならない。** ファイルシステムは GPU が存在しない場合でも完全に機能し、かつセマンティクスが完全に同一でなければならない。⇒ **GPU は任意のアクセラレータであり、フォーマットに1ビットも入れてはならない。**
2. **フォアグラウンドパスへの混入を禁じる。** PCIe の往復は数十マイクロ秒のオーダーであり、フォアグラウンドの読み書き遅延はこのコストを許容できない；すでにバッチ化されたバックグラウンド重処理のみに供される。
3. **これは新たな障害ドメインであり、オフロードされた結果は必ず再検査しなければならない。** GPU の計算誤り（ドライバのバグ、VRAM の ECC 欠如、アルゴリズム実装の相違）がサイレントなデータ破損になってはならない ⇒ `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「検証の2つのパスは同一コードを共有してはならない」と同型である：**GPU パスと CPU パスは2つの独立した実装でなければならず**、二つはテストで突き合わせる。実行時にどう再検査するかは GPU を使う側の決定が定める：バックグラウンドタスクは D26 (バックグラウンド整理と配置回収) 確定項目 13 第8項に従い、二つの独立した GPU カーネルがそれぞれ一回計算して比較し、確認されたエントリは CPU に渡してビットマップを更新し、連続数ラウンド不確定のエントリは CPU 側の実装に判定させる。

**適用範囲**: 第1項はフォーマットを、第2項はパスを、第3項は検証を管轄し、3項はそれぞれ独立しており、いずれか1つでも満たせなければ実施を禁ずる。これらは「実施する価値があるか」を定めるものではなく、それは確定項目 1 および確定項目 3 の管轄である。第3項が求める2つの実装はいずれも存在しない（D24 (バックグラウンド重処理の GPU オフロード要否) は延期され、スケジューリング外）。第2項の「PCIe の往復は数十マイクロ秒のオーダー」は本プロジェクトの実測と約 100 倍ずれる：E185 (GC 1バッチ移行のウォールクロック内訳) 第 4 回再実行で一回の GPU 投入の壁時計は約 5.3 ms（`research/prompts/m4-gpugc-design-r3-main-verification.md` 第二節の「今天的形态进前台路径」（今日の形態はフォアグラウンドパスに入る）の欄）；測ったのはカーネルを含む投入全体で、純粋な PCIe 往復ではなく、方向は「フォアグラウンドパスへの混入を禁じる」と一致する（なおさら許容できない）ため、条項の判定基準は変えない。

**根拠**:

- ユーザー決定（GPU は任意のアクセラレータ；2026-10-21 に実行時の再検査を、二つの独立した GPU カーネルがそれぞれ一回計算して比較し、連続して不確定のエントリは CPU に判定させる形に変更）、原文は変更履歴にある。
- 実験なし: 3項ともポリシーおよび検証規律からの直接の推論であり、測定可能な量はない；第2項が引く PCIe 往復のオーダーは公開の共通知識であり、本プロジェクトはフォアグラウンドパス上の GPU 往復を測定していない。

**未済**: なし。

#### 確定項目 3: 判定基準の形式

**決定事項**: 判定基準は `CPU 16スレッド所要時間 ÷ (転送 + 計算 + 転送返却) 所要時間` であり、1未満であればその枠を排除する。代入される CPU 側の数値は**マルチコア飽和スループット**でなければならず、「単一コア × コア数」ではない：線形外挿と実測は AES-GCM において約4倍乖離する（外挿約 61 GB/s、実測飽和 17.4 GB/s）。GPU 側の2つの下限値は**片道 56.69 GB/s**（ページロック H2D、≥64 MiB）および**往復 28.5 GB/s**（H2D + D2H、全データを送り返すシナリオはこの行）；CPU 側の上限は**メモリ帯域幅の壁 64.91 GB/s** である。⇒ **GPU は「CPU 側の実際のスループットが転送下限値を下回る」場合にのみ勝機が存在する。**

**適用範囲**: ⚠️ **「ボトルネックが CPU か否か」は「このタスクにハードウェア命令があるか否か」と等価ではない**——AES-NI を有する暗号化でも同様に 17.4 GB/s で飽和し、ボトルネックは依然として CPU 側にある。**ハードウェア命令の存在 ≠ GPU が追いつけないほど高速**。⚠️ **「CPU は十分高速だから GPU は不要」という前提は本プロジェクトでは成立せず、いかなる結論の支えとしてもならない**：それは単一コアにコア数を掛けた線形外挿に由来し、マルチコア実測飽和値 17.4 GB/s とは4倍近く乖離し向きも逆である——17.4 は GPU の2つの下限値より低い。代入後の4つの候補枠の現況：scrub（チェックサム / MAC）は AES-NI がある場合 CPU 側マルチコア飽和 17.4 GB/s（8スレッド、16/32スレッドは 16.3/16.5；単一コア 3656.13 MiB/s）⇒ 判定基準によればこの枠は GPU の勝ちだが、⚠️ **両側とも確証がなく、確定結論として用いてはならない**（GPU 側に真の AES-GCM カーネル関数が不足）；AES-NI のないマシンでは単一コア 244.74 MiB/s ⇒ 16コアで約 4.1 GB/s、ハイエンド NVMe アレイと同オーダーであり、この層では GPU が有用である可能性があり、マルチコアは未測定で飽和値はさらに低下する；EC 再構築はデータなし（Reed-Solomon over GF(2⁸)、再構築は全残存ディスクを読み取りパリティを計算、計算量はディスク数 × 容量に比例し、この枠の計算は確かに重い）；バッチ圧縮はデータなし（圧縮率とスループットのトレードオフ、GPU 圧縮ライブラリは存在）。この2つの数値（17.4 と 244.74）は E6 (暗号化アルゴリズム選定) に由来し、D24 (バックグラウンド重処理の GPU オフロード要否) 自身が測定したものではない。⚠️ **「GPU は無用」と読んではならない**：計算段に関する推論は**帯域制約型**のカーネル関数にのみ成立し、**圧縮は計算能力制約型**であり、その計算段は1割をはるかに超える可能性があり、その枠は依然として開かれており `nvcc` を待つ必要がある。⚠️ **さらに上位の制約が存在する**：3つの候補シナリオはいずれもディスク律速のバックグラウンド処理であり、ディスク帯域は 64.91 や 28.5 よりもはるかに低い ⇒ 全体がディスク律速であれば、CPU は元より空転しており、GPU へオフロードしても何も節約できない——**この層は推論であり実測ではない**（本プロジェクトにアレイはない）。⚠️ **未検証のエスケープハッチ**：GPUDirect Storage は NVMe から VRAM への直接 DMA を可能にし、主記憶と PCIe のホップを迂回する。**これは「GPU データ受入 56.69 GB/s」という転送下限値を覆すことになる**。未検証であり、存在しないものと見なしてはならない。D24 (バックグラウンド重処理の GPU オフロード要否) を確定するには、まず EC 再構築とバッチ圧縮の2枠における CPU 上限、および「PCIe 転送 + カーネル関数 + 転送返却」リンクの純粋 CPU に対する正味利益を測定する必要がある——**データは PCIe を一度通過しなければならず、その搬送コストがすべての計算利益を消費する可能性がある**。**実機で測定可能**：NVIDIA RTX 5090 (32 GB) + RTX 5060 Ti (16 GB)、ドライバ 595.84；`nvcc` はインストールされていない（`command -v nvcc` はヒット0、`/usr/local/cuda*/bin/nvcc` もなし）、これは G24.3（計算段の比率）の前提条件である。

**根拠**:

- E21 (GPUオフロードの純収支): 3つのパスのスループット（CPU データ受入 64.91 GB/s、GPU 片道 56.69 GB/s、GPU 往復 28.5 GB/s）が判定基準の2つの閾値を固定する——GPU はデータを投入するだけで既に CPU が読み出すより 13% 遅く、計算はまだ開始していない；計算段は帯域制約型演算子で上限を与え、VRAM 内 1041 GB/s に対しエンドツーエンド（転送込み）は 50.3 GB/s にすぎない ⇒ 転送が 90.3% を占め、計算段はほぼ無料、純粋スキャンの枠に対する正味利益は 0.78× で 1 未満 ⇒ GPU の負け。**GPU が勝つか否かを決定するのは CPU 側に対応するハードウェア命令があるか否かであり、GPU がどれほど高速であるかではない。**
- ユーザー決定（判定基準の正しい形式はマルチコア飽和スループット）、原文は変更履歴にある。

**未済**: なし。

#### 確定項目 4: 再開判定基準

**決定事項**: いかなる現象が再開をもたらすかを明言できなければ、「延期」とは無期限の棚上げである。4つのゲート——

<!-- doc-lint:registry name-col=2 -->

| ゲート | 略称 | 判定内容 | 測定可否 |
|---|---|---|---|
| G24.1 | ハードウェア命令欠如 | 対象プラットフォームの CPU が対応ハードウェア命令を**欠致**し、当該タスクの CPU 側スループットが **50.3 GB/s**（片道シナリオ）または **28.5 GB/s**（送り返しが必要なシナリオ）を下回る | 可能、対象 CPU 上で当該タスクのスループットを測定するのみ |
| G24.2 | ディスク律速でない | 当該タスクが**ディスク律速でない**こと——すなわち CPU 側スループットがディスク帯域を下回り、CPU が真のボトルネックとなっている | アレイが必要、本プロジェクトにはなし |
| G24.3 | 計算段の比率 | 圧縮セル：真のカーネル関数の計算段比率 | **不可**、実機に `nvcc` なし、前提条件は CUDA ツールチェーン |
| G24.4 | GPUDirect 利用可能 | GPUDirect Storage が利用可能——主記憶と PCIe のホップを迂回し、「GPU データ受入 56.69 GB/s」という転送下限値を覆す | 未検証 |

⚠️ **G24.1 (ハードウェア命令欠如) と G24.2 (ディスク律速でない) は同時に成立しなければならない。** G24.1 (ハードウェア命令欠如) のみを満たし（CPU に命令がなく低速）、G24.2 (ディスク律速でない) が不成立（全体がディスク律速）である場合、CPU が遅くとも問題ない——元よりディスクを待っているからである。

**適用範囲**: 4つのゲートは再開の十分条件であり、スケジューリングの判定基準ではない；G24.3 (計算段の比率) と G24.4 (GPUDirect 利用可能) は測定不能であり、前提条件はそれぞれ CUDA ツールチェーンと GPUDirect Storage である。G24.2 (ディスク律速でない) はアレイが必要。確定項目 4 が定めるのは「いかなる現象が再開をもたらすか」であり、再開後にいかなる順序で進めるかは規定しない。

**根拠**:

- E21 (GPUオフロードの純収支): G24.1 (ハードウェア命令欠如) の2つの閾値（50.3 GB/s 片道、28.5 GB/s 往復）および G24.4 (GPUDirect 利用可能) が覆すべき下限値（56.69 GB/s）はいずれも本実験で測定された；判定基準 1 の形式もここから導出された。
- ユーザー決定（いかなる現象が再開をもたらすか明言できなければ、延期とは無期限の棚上げである）、原文は変更履歴にある。

**未済**: なし。

#### 確定項目 5: 正当性の源泉

**決定事項**: 3つの候補シナリオはいずれも `.claude/rules/fs-design.md` 会計規律の**第3枠**（バックグラウンド、再開可能、非決定パス、明示的に「戒律なし」と記述）に属する ⇒ GPU の導入はいかなる確定済みの規律とも衝突しない。**3区分は D24 (バックグラウンド重処理の GPU オフロード要否) の正当性のすべての根拠である——あるシナリオが第1枠（実行時決定パス）へ移行した瞬間、D24 (バックグラウンド重処理の GPU オフロード要否) はそれに対して直ちに失効する。**

**適用範囲**: 他の決定との連鎖は3つ：D2 (RAID ストライプ方針) 側では、EC 再構築が D24 (バックグラウンド重処理の GPU オフロード要否) で最も利益を得られる可能性が高い枠である；D3 (領域割り当て) 側では、常駐バックグラウンド整理が第3枠に属し、GPU の正当な適用範囲である；D9 (暗号化) 側では、scrub のチェックサムおよび MAC 計算量がそれによって決定され、**AES-NI のない層が GPU にとって明確なデータ支持を持つ唯一の入口である**。確定項目 5 はこれら3枠を実施する価値があるかを判定するものではなく、それは確定項目 1 および確定項目 3 の管轄である。

**根拠**:

- `.claude/rules/fs-design.md`「会計はトランザクションの副産物であり、事後の走査ではない」の3枠表：第3枠は逐字で「バックグラウンド、再開可能、非決定パス（スナップショット破棄、整理、scrub）」であり、明示的に「戒律なし」と記述。
- 実験なし: シナリオがどの枠に属するかはその規律自体の判定基準に従って判定され（「問われた瞬間に回答があるか」）、測定可能な量はない。

**未済**: なし。
