## D16 发布语义 —— 已定：checkpoint（两项未定）

**攒够一批脏节点（或到时间）再发布一次根，不是每个事务发一次。**

依据（2026-08-26 用户定案）：它与 D5（快照 / 空间记账机制） 已定的 ZFS birth txg 模型天然相容——
**ZFS 的 txg 本身就是 checkpoint**（`zfs_txg_timeout` 默认 5 秒，或攒够一定脏数据量），
一个 txg 批量大量操作、txg 结束才更新一次 uberblock。
采纳 checkpoint 之后 birth txg 的号粒度问题**自动消失**：一个 txg 一个号，
deadlist 的比较粒度就是 checkpoint 粒度，不必重算。

**一条独立的理由（2026-08-28 补）**：**根是丢失写的最终见证者。**
检测「盘上这块是不是它应该是的那个版本」需要一个外部见证者——
块自身办不到，因为合法的旧版本与合法的新版本在块内层面同构（D18（块里携带什么信息） 有完整论证）。
而见证者必须在**不同的失败域**上：父节点若在同一次事件里也没写成，就要祖父，递归到根。
⇒ **checkpoint 发布的那个根是这条递归的终点**，它的持久化必须比任何单个块更可靠。
ZFS 的形态是 4 个 label × 每个 128 KiB 的 uberblock 环、且偶数与奇数 label 分两阶段写。
根自身的冗余形态由 D22（单元原子性怎么合成） 已定项 2 定：R=3、素数步长放置、跨区轮转槽序、槽宽 = 探测到的 `physical_block_size`。

**连带定死的三条**（不写死就会退化成「为某个路径开第二套事务机制」）：

1. **没有任何操作可以绕过 journal 直接发根。** 所有结构、所有操作先进同一个 journal、
   共用同一个 checkpoint 节奏。fsync 的效果是「提前触发一次发布」，
   **不是另开一条日志格式、另一套恢复逻辑**。
   判据是：**journal 是所有提交的必经之路，还是某些路径的旁路**——
   前者是一套机制、持久化分两级，合规；只有 fsync（或只有元数据、只有小写）走 journal、
   别的直接发根，就是 `.claude/rules/fs-design.md` 点名的「为 fsync 单开一套日志树」。
2. **D8（核心索引结构）「中间状态必须每一个都是合法的文件系统状态」改写为**：
   「**根 + journal 任意前缀，replay 之后合法**」。
3. **这份 journal replay 归「记录核对器」，不归 O2（独立解析器 + checker）**（D13（验证路线） 已定 O2（独立解析器 + checker） 是一元谓词、只判单个镜像）。⚠️ 且 D23（journal 的角色与格式） 轴一定甲之后「redo 为空」，D16（发布语义）自称「最贵的一笔」的大头随之消失，只剩前缀判定 + 择根 + 续做。
   那是第二次实现 replay，而 replay 正是崩溃语义最容易出**共同误解**的地方——
   D13（验证路线） 的「三 oracle 合谋测试」要防的就是这个。**这是 D16（发布语义）最贵的一笔。**

### 这条定案改变了什么

**它同时钉死了 [experiments.md](../experiments.md) E7（离线索引 harness） 的对照组。**
checkpoint 与 D11（索引节点要不要留消息缓冲区） 的消息缓冲区买的是同一样东西，差别只在**摊销窗口住在哪**：
checkpoint 的窗口住**内存**、不进格式；消息缓冲的窗口住**盘**、必须进格式。
⇒ **D11（索引节点要不要留消息缓冲区） 的边际收益 = 「跨 checkpoint 的摊销」减去「checkpoint 内摊销」**，
而 BetrFS 那组数字里这两块从没被拆开过（它同时有 4 MiB 节点的消息缓冲**和** 5 秒 checkpoint）。
**E7（离线索引 harness） 的对照组必须是「有 checkpoint、无消息缓冲」。**

**对 C 类问题（分批大删除的元数据写放大）**：同一 checkpoint 窗口内的 K 批只走约一次
到根的路径，各批只留一条 journal 记录（小、顺序写），写放大从 `K × M × H` 降为
`checkpoint 数 × M × H`。

### 为什么发布频率是枢纽

D16（发布语义）回答的是**一次事务提交就发布一个新根，还是攒够一批脏节点再发布一次根**。
发布频率只由 D16（发布语义）定：`litmus/commit-publish.litmus` 钉的是一次发布事件**内部**的顺序
（写块内容 → `smp_wmb` → 写 generation），**对频率一字未提**（2026-08-26 逐文件核实）。

它是枢纽，因为有一条路径被三条决策共同压着——**引用改写路径**：
`目标块 → 父节点 → … → 根 → 超级块`。
任一块的内容改了或物理位置变了，都必须沿这条路径逐级重写到发布新根，
长度 H（树高），每级 = 一次新分配 + 一次凭据重算 + 一次加密写。

| 来源 | 它往这条路径上加了什么 |
|---|---|
| COW（项目前提，不是某条决策） | 块不原地改 → 新块新地址 → 父指针的**地址字段**必改。**单这一条就足以产生「到根」** |
| D4（校验和位置） 校验和内联进父指针 | 父指针除地址外还是子块的完整性凭据。**在 COW 下它对写放大的边际贡献是零**（地址反正要改） |
| D9（加密）整卷 AEAD | 那个凭据在加密开启时是 MAC，且路径上每级节点的载荷是密文 → **这条路径需要密钥** |
| D3（空间分配） 全局分配器 + 常驻整理 | 制造「必须主动走这条路径」的需求（搬块） |
| D8（核心索引结构） 无界操作分批 + 意图 | 制造「反复走这条路径」的需求（K 批） |

- **发布语义决定「走几次」**：每事务发根 → K 批走 K 次；
  checkpoint → 同一窗口内的 K 批只走约一次，各批只留一条 journal 记录（小、顺序写）。
- **它同时钉死 D11（索引节点要不要留消息缓冲区） 的对照组**，见 D16（发布语义）「这条定案改变了什么」一节。

### 净代价分布

**格式侧几乎为零**（journal 本来就要有），**验证侧一大笔**：
连带定死的第 2 条（中间态语义改写成「根 + journal 任意前缀」）与第 3 条
（journal replay 的第二份实现，归记录核对器而不归 O2（独立解析器 + checker），D16（发布语义） 连带定死的第 3 条已写明）都落在验证上，再加一条——
**D13（验证路线） 的「Merkle 根链差分」粒度变粗**：一代根里塞了 K 个事务的改动，
定位精度从「哪个事务」降到「哪个 checkpoint」，而 D13（验证路线） 已写明夜间档的真代价是定位成本。

### D16（发布语义）连带定死的两条新规则（2026-08-26，来自生命周期条件的推导）

**新规则 1：快照发布点必须与 checkpoint 边界对齐，且位置钉死在「本 checkpoint 全部数据变更之后」。**
快照不许出现在 checkpoint 中间。
理由是机制性的：`birth` 的分辨率只到 checkpoint，**块无法表达「我生在本 checkpoint 里
快照点之前还是之后」**。不钉死它，D5（快照 / 空间记账机制） 那张边界表里 `birth == S.txg` 与 `death == S.txg`
两行会同时失去确定答案——而它们一个是**数据丢失**、一个是**空间泄漏**。
（同一 checkpoint 内建两个快照是允许的：它们捕获同一状态、其间 deadlist 为空；
但 checker 里的「上一个快照」要用 `(txg, 快照 id)` 打破并列。）

**新规则 2：checkpoint C 中产生的一切释放，在 C 被发布之前不得进入可分配集合。**
两个理由，第二个是 D16（发布语义）独有且更严的：

1. 回滚：崩溃后可能回到 C−1 的根，而生于 C 之前、死于 C 的块在那时仍然活着。
2. **D16（发布语义）把 D8（核心索引结构） 的中间态语义改写成「根 + journal 任意前缀，replay 后合法」。**
   若一个块在 journal 位置 p 被释放、位置 q > p 被重新分配并写入新内容，
   那么重放到 `p < r < q` 的前缀会得到一棵指向该地址的树，
   **而盘上的字节已经是 q 的内容了**（物理写不受 journal 位置约束）。
   **这不是理论风险，是必然的错。**

ZFS 有同型机制且更保守：`include/sys/txg.h` 的
`#define TXG_DEFER_SIZE 2 /* Number of txgs worth of frees we defer adding to in-core spacemaps */`。
⚠️ **那个 2 为什么是 2，没查到一手解释**；本工程的 defer 窗口要按 D16（发布语义）的重放语义自己推，**不许照抄**。

⚠️ 新规则 2 的 defer 窗口容量与 ENOSPC 直接相关（D3（空间分配）：**释放空间这个操作本身不许申请空间**），
而 D16（发布语义）使「建了又删」在同一窗口内闭合的概率大幅上升，**defer 窗口因此落在热路径上**。

2. **checkpoint 的触发判据：时间与脏数据量，两者取先到。** **状态：已定。**（2026-08-31 用户定案）

   逐字形态：`触发 ⟺ (now − 上次 checkpoint 的时刻 ≥ T_time) ∨ (脏字节数 ≥ T_dirty)`。

   **为什么这个形态满足两条硬要求**（`.claude/rules/fs-design.md`）：

   | 要求 | 满足在哪 |
   |---|---|
   | 硬要求 1：判据显式、可计算、写下来 | 那个 `∨` 式子就是全部，没有魔数以外的自由度；两个阈值是**超级块声明值**，挂载时求值一次（形态与 D21（权威态与派生态的分界）「单元几何挂载时求值一次」同型） |
   | 硬要求 5：分支变量不许在操作中途改变 | **被触发的量会变，阈值不会**。`now` 与脏字节数是被比较的量，不是分支变量；分支变量是那两个阈值，它们在挂载期间恒定 |

   **单取一样都不够，这是取先到的理由**：只按脏数据量，空闲系统上最后一批写可以无限期不落
   ⇒ 崩溃丢窗口无界；只按时间，突发写会把一个 checkpoint 的 journal 占用撑过环几何
   （I-8.1（环几何够大） 要的是「任一事务的最坏 journal 占用」有界）。**两条各自堵住对方的失败模式。**

   两个阈值的取值见 D16（发布语义）「已定项 5」。

5. **`T_time` 与 `T_dirty` 取多少：`T_time` = 5 s，`T_dirty` = 2 GiB。** ⚠️ 2026-09-05 C113（扫描重建时多版单元的现行版本判定无输入） 定案把丢失窗口的口径改成「T_time + T_retry（单元写的重试预算）」，待用户复核（正文末段）。 **状态：已定。**（2026-08-31 用户定案）
   **`T_time` 取可行区间的上端 5 s**：丢失窗口既然是 5 秒，取更小只减少摊销、不多买任何东西——
   拦住丢失的是那 5 秒本身。**`T_dirty` = 2 GiB**（初值，写代码时再调）。

   **两条耦合已由 E70（checkpoint 两个阈值的可行域）（2026-08-31）算过，结果改了其中一条的分量**：

   | 量 | 算出来是什么 |
   |---|---|
   | `T_dirty` | 环几何给的上界 = `(环/F − 78) × 512`——一个脏节点 16 KiB 在 journal 里只占一个 32 B 位置条目 ⇒ **64 MiB 环就允许 16 GiB 脏数据**。⇒ **「上界绑环几何」方向没错但不承重**；实际卡住它的是脏页内存与崩溃丢失窗口——**这张表列的是定案前的推导状态，两个阈值的定案值见同一已定项后文** |
   | `T_time` | 下界由摊销预算反解：multistream 负载要 **94 ms（预算 0.2）／197 ms（0.1）**；**seq 负载一点下界都不需要**（ckpt=100 就已满足）⇒ 占位的 8 秒**远在下界之上**，不与它冲突 |

   ⇒ **这一步已定（2026-08-31 用户定案）：按最差负载 multistream 定，不按主负载 seq 定。**
   取摊销预算 `B = 0.1` 块/操作 ⇒ 反解 547 次操作 ⇒ 按 E44（序号位宽的本机实测与代价） 的 2785 fsync/秒
   得 **`T_time` 下界 ≈ 197 ms，向上取整记 200 ms**。
   ⚠️ **「向上取整到 200 ms」与「预算取 0.1」都是选的，不是算出来的**：
   0.2 给 94 ms、0.05 给 410 ms（外推）。**下界随预算线性挪，改预算就要重算。**

   **上界也定了（2026-08-31 用户定案）：崩溃最多允许丢 5 秒的写。**
   `∨` 规则里时间那一支就是丢失窗口的执行者 ⇒ **`T_time` ≤ 5 s**。
   合上下界 ⇒ **`T_time` 的可行区间是 [200 ms, 5 s]**，本分项取区间上端 5 s。

   ⚠️ **此前的占位值 8 秒作废**：它在 5 秒窗口之外，落在可行区间以外。

   **`T_dirty` = 2 GiB（2026-08-31 用户定案，明说是初值、写代码时再调）。**
   `T_dirty` 不由丢失窗口定——`∨` 规则下时间那一支已经保证了窗口，`T_dirty` 管的是**量**，
   它就是脏页内存预算本身。

   **由它推出的两个数**（用 E70（checkpoint 两个阈值的可行域） 的式子，放大倍数 `节点/条目 = 512`）：

   | 量 | 值 |
   |---|---|
   | 每个 checkpoint 的 journal 占用 | `2 GiB / 512` = **4 MiB** |
   | I-8.1（环几何够大） 要求的**环大小下界** | F=2 时 **8.00 MiB**，F=3 时 **12.00 MiB** |

   ⇒ **这是 I-8.1（环几何够大） 第一次拿到一个具体的数**；环大小本身仍未定，但它的下界不再悬空。
   ⚠️ **射程注（2026-09-03，E91（已定格式下的环账与准入账）实测）**：「由它推出的两个数」那张表的放大倍数 512 用的是
   32 B/条目旧口径；按更晚定的 D23（journal 的角色与格式）已定项 12（4 KiB 定长记录、
   头 78 B、每项 56 B、71 项/条）重算，同一个 T_dirty 满窗是 1847 条记录、
   占用 **7388 KiB**，I-8.1（环几何够大）的环下界 F=2 时 **14776 KiB**、F=3 时 **22164 KiB**——
   旧口径少算 1.80 倍。T_dirty / T_time 的定案值不变，变的只是这两个派生数的口径。
   ⚠️ **`T_dirty` 是可调值，不是格式常量**：超级块里那个字段是格式，字段里放什么数不是。
   ⚠️ **本机持续写带宽没有实测**（E58（校验和粒度的端到端代价） 那个 2045 MiB/s 是校验和实验里的顺序口径，
   不是写带宽，不许拿来换算），所以「5 秒能写多少字节」现在也算不出来。

   **丢失窗口的口径改写（2026-09-05，随 C113（扫描重建时多版单元的现行版本判定无输入） 定案 P1；⚠️ 待用户复核，动的是 2026-08-31 的定案句）**：取号 = 事务被分配进某个 checkpoint 那一刻，checkpoint 的切分只关闭成员资格——触发之后不再分配事务进它，已分配的事务把各自的单元写完，发布阶段等全部单元落盘（任何 COW checkpoint 都要等最慢的那次 I/O，ZFS 的 txg sync 同样等最慢的 vdev，未在本项目验证）。事务切分纪律把一次写请求按单元切成若干事务各自取号，一个事务最多写一个单元的用户数据；单元写的重试预算是墙钟 T_retry（具名可调参数，不是格式常量；用尽即按失败的性质走实例切换或转只读，D23（journal 的角色与格式） 已定项 14——它同时是丢失窗口的加项、挂载内实例切换的判据、以及连续切换计数的时间基准，三个用途一起送复核）。**由此崩溃最多丢的是 T_time + N_switch × (T_retry + T_redo)，不再恰是 5 秒**——一次挂载允许 N_switch 次实例切换（D23（journal 的角色与格式） 已定项 14），每次都要熬完 T_retry 再把在飞 checkpoint 重做一遍（T_redo），而重做期间开放的那个 checkpoint 发布不了、只能一直攒（第八轮反推腿 5.1）。**「上次 checkpoint 的时刻」在重发时取重发那一刻**（取原来那一刻的话，切换期间触发条件一直成立而在飞深度只有两个，触发只能空转）；E70（checkpoint 两个阈值的可行域） 给的下界不受影响；在飞 checkpoint 深度 = 开放 + 发布中两个；并发 fsync 的返回时刻被同 checkpoint 的其他事务拖住是组提交固有的代价。这是新规则 1「快照发布点钉在这个 checkpoint 全部数据变更之后」的可执行形态。


### 已定项 6（2026-09-02，用户定案，先过对抗测试）：发布计数器

**每次发布把 checkpoint_txg 加一——fsync 触发的发布也是发布，没有「小发布不记号」的例外；
根槽的轮转键（D22（单元原子性怎么合成）已定项 2 的「区域 = txg mod R」里那个 txg）、
记账的代（D5（快照 / 空间记账机制）已定项 2）、恢复重放的水位（D23（journal 的角色与格式）已定项 14）
都是这同一个计数。不另设「发布代号」字段——它与 checkpoint_txg 是同一个东西。**

   前缀五条口径按事务施加，前缀可以落在同一次发布的两个事务之间（E42（一事务几条记录） 那种切法）；
   而「施加一条记录」在指针层上具体做什么——换哪个指针、祖先谁来 COW、落点谁分配——全仓没有定义，
   D23（journal 的角色与格式） 开篇「重放不要分配器」与「只施加一部分事务就要重新生成祖先」互相顶着。
   D13（验证路线） 那句「核对一条记录只需格式解析 + 校验和 + 根环择新」管的是**验记录**，不是算期望态（反推腿 4-A）。
   落 C284（施加一条记录在指针层上做什么没有定义）。成本量级由这一问决定：定成「一次发布整体施加或整体不施加」，
   第二份实现停在句法层；允许部分施加，它就要自己实现树语义。
