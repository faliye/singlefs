## D17 实现分层与第三方管道 —— 已定

D17（实现分层与第三方管道） 管本工程与第三方管道之间那条线：腰线划在哪、哪一侧归本工程独占、「数据接口」是哪一截字节、失败模型这根轴谁说了算、结构等价类怎么数，以及第一版的运行载体与一条管道要还的债。不管的：介质分几条线、谁开的线谁维护在 D12（目标介质）；崩溃状态集合与 `CommitStep` 的枚举在 D13（验证路线）；单元原子性怎么合成在 D20（承重面：单元的原子性与自包含） 与 D22（单元原子性怎么合成）；格式冻结分层在 D15（格式冻结政策）。

#### 已定项 1：单一失败模型，核心层合成

**定案**：核心层规定一个失败模型——扇区 512 原子、写可撕裂到扇区、屏障之间可重排（D20（承重面：单元的原子性与自包含） 推论三的实测口径「设备侧原子宽度 512 且不可依赖」）；管道不许声明例外；达不到的由核心层合成（读回校验 / 双写 / 补一条日志），合成代价记在核心层、按管道计费不按用户计费。与 `REQ_PREFLUSH` / `REQ_FUA`「后端不许拒绝、块层自己合成」同形。

**射程**：这根轴的基数恒为 1，它不参与等价类数相乘（已定项 2）。本项定的是契约的形态，第一条第三方管道出现前不落字节，C16（管道声明失败模型例外） 的前置随之满足。「失败原子性宽度 / 撕裂 / 重排序」今天的覆盖在 D13（验证路线） 已定项 4（崩溃状态集合）与 D20（承重面：单元的原子性与自包含） / D22（单元原子性怎么合成） 里；C6（块层语义假设写错） 问的是「本工程的假设对不对」，不是「一条管道的失败模型是什么」，两者不同格。被否掉的乙（允许管道声明更强模型、按声明分派重放）在 `CommitStep` 之外多一根轴，代价是层 2 重放要按声明分派。

**依据**：

- E129（小于 io_min 的写在真设备上怎么出事）：位置确定的撕裂在真设备上造得出，阳性与阴性对照各自干净——「写可撕裂到扇区」是要兜住的真实形态，不是推导。
- 现役对照组：允许后端返回 `-EOPNOTSUPP` 的 `REQ_HARDBARRIER` 在 2.6.37 被砍，换成不许后端拒绝、块层自己合成的 `REQ_PREFLUSH` / `REQ_FUA`，至今 15 年未变；两者唯一的差别就是允不允许后端说「我不支持」。
- 用户定案（2026-09-13 取甲），原话在变更史。

**欠**：C16（管道声明失败模型例外）。

#### 已定项 2：结构等价类按段序列分，今天 1

**定案**：

1. 结构等价类按录制流的段序列分：两条布局线同类 ⟺ 对每一条根槽写路径（发布、空发布、mkfs 种子、实例切换 / 管理员回退——D13（验证路线） 已定项 1 列的三种写者加空发布），两条线录制流的段序列同构：段边界（屏障与 FUA 写切出的段，D13（验证路线） 已定项 4）的位置相同、每段里出现的步骤种类**集合**相同（写单元 / 写 journal 记录 / 根槽 FUA 写 / 超级块槽原地覆写 / 屏障五种）；一步重复几次（设备数、单元数、副本数）是参数不进判据（D13（验证路线） 已定项 10）。比较只在同一路径角色、跨线之间做，一条线内部各路径不互比、不计数。

#### 已定项 3：一致性套件发源码 + 判定程序

**定案**：发两样：套件的源码，以及一个判定程序。不发容器，也不只发镜像语料。第三方管道要证明自己合规，跑的是**同一份判定程序**，而判定逻辑是**可读的源码**、不是黑盒——这与 D13（验证路线） 已定项 7「O2（独立解析器 + checker） 是一元谓词、只判单个镜像」同型：判定必须能被第三方自己复核，否则「合规」就退化成「我们说你合规」。

**射程**：它没答「判定程序与本仓 checker 是同一份代码还是两份」——若同一份，`.claude/rules/fs-design.md` 那条「审计与被审计不许用同一段代码」在这里要重新判一次：第三方是被审计方、本工程是审计方，这与 checker / 运行时那一对不是同一种关系，不能直接照搬结论；落点是已定项 2 与 C8（门禁范围判不出来）。镜像语料不在发布物里是一个选择而不是遗漏：语料会随格式演进而过期，而源码 + 判定程序可以随版本走；要不要另外发一份冻结时刻的语料，跟着 D15（格式冻结政策） 定。

**依据**：

- 无实验：发什么、发几样是对外承诺的形态，没有可量的量；它买到的那件事（判定能被第三方复核）只有等第一条第三方管道出现才量得到。
- 用户定案（2026-08-31），原话在变更史。

**欠**：C8（门禁范围判不出来）。

#### 已定项 4：入口 = RefFS 的操作面

**定案**：「入口」的可执行定义由 RefFS 给——按 D13（验证路线） 已定项 3「做到极致、自己处理持久化与崩溃语义」，O1（内存模型对拍（HashMap 理想文件系统）） 扩成的 RefFS 定义 fsync 的持久性承诺；不另起 O3（独立规约执行器）。

**射程**：代价是 D13（验证路线） 已定项 3 逐字「工程量接近再写一个文件系统」。被否掉的乙（另起 O3（独立规约执行器） 只定义 fsync 一条承诺、其余交 O1（内存模型对拍（HashMap 理想文件系统）））要重开 D13（验证路线） 已定项 3。

**依据**：

- 无实验：这一格定的是两个 oracle 的边界住在哪，落在验证侧、不改任何一个盘上字节，没有可量的量；RefFS 的工程量要等它写出来才量得到。
- 用户定案（2026-09-13），2026-09-08 复核那句「按已定项 3 读已经是扩模型」由用户落成条款；原话在变更史。

**欠**：C25（三个 oracle 零代码）。

#### 已定项 5：第一版是纯用户态库，不挂载

**定案**：第一版是一个纯用户态 Rust 库，只对块设备抽象编程，两个后端：普通文件与 `O_DIRECT` 打开的裸设备。它对外是一组操作（mkfs、打开、写 extent、发布 / fsync、恢复），崩溃点重放 harness、RefFS 对拍、QEMU 档的负载二进制都直接驱动这组操作。第一版没有挂载：FUSE 是后来的一层薄适配，等目录与 POSIX 面出现之后再加；内核模块在可预见的几年里不做。

三样验证手段都不需要挂载：崩溃点重放要的是能拦住块设备那三个原语（写、屏障、FUA 写），D13（验证路线） 已定项 4 定的录制就在那一层；RefFS 对拍要的是同一串操作能喂给两边、比结果，不碰盘；QEMU 档跑的就是静态 musl 二进制吃 `/dev/vda`（[vm-harness.md](../vm-harness.md)）。

**射程**：三处已知边角。① 录制钩子挂在块设备接口上，不是挂在操作 API 上：一次「发布 / fsync」内部会发出多次单元写、两道屏障与一次 FUA 写，钩子挂在 API 层就把那些中间崩溃点整个吞掉，而 D13（验证路线） 已定项 4 的枚举域正是那些原语 ⇒ 实现要给出「一次 API 调用发了几个设备级操作」的读数，harness 拿它比对录到的条数，对不上整轮作废。② 库要落在 `crates/` 下面：门禁的「Show me test」只认 `crates/*/src/` 里的实现代码。③ 它不改任何盘上字节，但载体不是零成本的——内核 `block/bdev.c` 的 `sb_set_blocksize` 对大于 `PAGE_SIZE` 的块大小要求文件系统带 `FS_LBS` 标志且内核开了 `CONFIG_TRANSPARENT_HUGEPAGE`，而本工程的单元 32768、节点 16384 都大于本机的 4096，所以内核模块那条路要么依赖那个内核特性、要么自己在内部做小于页的缓冲；库与 FUSE 两条路不碰这个约束。推迟内核模块的依据不是 D7（是否进 Linux 主线）——那条只说不往主线投，没说不许做树外模块——真正的依据是 `.claude/rules/fs-design.md`「先做慢而正确的那条」，加上大块 `sb_set_blocksize` 那笔内核账。

**依据**：

- E142（第一个事务的干跑）：第一个事务的全部固定结构字节由一个只对块设备抽象编程的二进制写出来，并与 `crates/` 实装逐区域比对全等——不挂载也走得到「正确提交一个事务」。
- 三方对抗（2026-09-03）：正推腿从已定条款推出同一处载体并指出录制钩子与 `crates/` 两条，替代反推腿找不到反例、现查本机内核 6.17 源码给出 `sb_set_blocksize` 那笔账；用户定案（2026-09-03），原话在变更史。

**欠**：C8（门禁范围判不出来）。

#### 已定项 6：腰线划在提交协议之下

**定案**：腰线划在提交协议之下。每种介质各自一条独立管道（分配、放置、布局、索引调优、节点大小、缓存、设备处理全部各自实现，且第三方可以自带一条）；而**事务的抽象状态机、提交步骤集合、崩溃语义留在腰线以上，由本工程独占**。

**协议是本工程的**：一条管道要引入新的结构性提交步骤，必须往本仓的共享枚举（D13（验证路线） 已定项 10 的 `CommitStep`）发一个 diff，不许在自己的黑盒里发明。

**射程**：腰线约束的是结构，不是「字节完全相同的落盘代码」——介质各自一条实现管道是允许的，绕开状态机的第二条发布路径不允许（`.claude/rules/fs-design.md`「一个事务层，所有结构共用」）。照抄现役模板不等于边界自动守得住：即使克制如 `iomap`，`iomap.h:114` 的 `validity_cookie` 也是因为共享层不知道后端的事务何时让映射失效，只能让文件系统往结构里塞一个序列号。腰线以上那一截字节属于冻结第 1 层，且比其余各层更硬（已定项 7）。

**依据**：

- 无实验：腰线划在哪是分工的形态，没有可量的量；它的可观测代价（管道数与等价类数）由已定项 2 数，防渗透效果要等第一条第三方管道出现才量得到。
- 三方论证（2026-08-27，三条腿一致）：反推腿查内核 6.17 树与 OpenZFS master，查不到任何一个案例同时满足「第三方自带后端 + 契约里含崩溃一致性语义 + 契约没被架空」（这是查不到，不是不存在，不许当阴性结论用）；唯一做出可插拔后端的生产 COW 文件系统是 ZFS，而它的后端签名里带事务组号（`include/sys/vdev_impl.h:62`）、后端自己持有三条 per-txg 脏链表、`vdev_ops` 里四个方法越过了「只搬数据」那条线；正推腿独立推出同一处腰线，更浅的两处装不下 zoned「根指针不能原地覆盖」这条结构性事实，更深的两处要么放弃 D12（目标介质） 已买单的「拒绝挂载而非静默误读」、要么被推到底之后收缩回本腰线。
- 现役演示（现查内核 6.17）：btrfs 的 zoned 不是一个 `zoned.c` 模块，`btrfs_is_zoned` 散在 22 个文件 93 处，其中 5 处在 `tree-log.c`（事务日志路径）、6 处在 `space-info.c`（ENOSPC 准入）——介质分支不划线就会自己渗进事务层与 ENOSPC 准入。

**欠**：C19（介质判定渗进事务层）。

#### 已定项 7：「数据接口」= 能安全拒绝所需的最小字节集合

**定案**：「数据接口」不是「同一份字节」——D12（目标介质） 已定各介质各自一套布局，盘上字节按设计就是不同的。数据接口 = **能安全拒绝所需的最小字节集合**：格式里足够让一个陌生读者总能得出确定判决的那一截——挂载 / 只读挂载 / 拒绝，三选一，**永远不会是第四种「照着错的假设读出看起来合法的字节」**。

可机检形态：**一个不链接任何管道代码的裸头部解析器**，对任意声称是 singlefs 的字节串跑，断言 I-1.1（块头自述逻辑地址） 与 I-1.4（块头 fsid 一致） 抽得出且自洽 + feature bit 编码 + 指针里校验和 / MAC 字段的位置与宽度。

**射程**：I-1.2（块头写序已发布） 与 I-1.3（块头树 ID 一致） 不在裸头部解析器的射程里——I-1.3（块头树 ID 一致） 逐字要「与实际引用它的树一致」，得先找到引用它的父节点；I-1.2（块头写序已发布） 逐字要按 C113（扫描重建时多版单元的现行版本判定无输入） 定案 P2 的全局已发布谓词判，输入是实例表里那一行 (i, T_pub, W) 与恢复所选根的 txg；两条都要第二个输入，不是「对任意字节串跑」的一元头部谓词 ⇒ 归 O2（独立解析器 + checker），不进数据接口。

**依据**：

- 无实验：这一格定的是「哪一截字节算契约」，判据是失败模式（拒绝而不是静默误读），不是一个可比大小的数；裸头部解析器写出来之后，它对任意字节串的判决率才量得到。
- `.claude/rules/fs-design.md`「能不能把『用错了』变成『挂不上』」是这条定案的判据来源；三方论证（2026-08-27）与 2026-09-14 的收窄（把 I-1.2（块头写序已发布） / I-1.3（块头树 ID 一致） 移出射程）原话在变更史。

**欠**：C25（三个 oracle 零代码）。

#### 已定项 8：一条第三方管道要还的五笔债

**定案**：

| # | 欠什么 | 为什么躲不掉 |
|---|---|---|
| 1 | **三个 oracle 要从内部测试变成对外发布的一致性套件** | 「用户用不用是用户的事」成立的前提是**用户有东西可以自己跑**。这是明确的范围增量 |
| 2 | **合规判定用本工程的 oracle，不用管道自带的验证代码** | `.claude/singlefs-ai-sop/rules/show-me-test.md`「不按来源区别对待」原样适用：判据是证据，不是自证报告 |
| 3 | **超级块 day-1 记录写入者身份** | 爆炸半径要可归因。坏镜像送来时 checker 要说得出「这是管道 X v2.3 写的」，不能只说 corrupt。事后加不进去 |
| 4 | **未知 `compat_ro` 位的降级行为要有崩溃测试兜底** | [pitfalls.md](../pitfalls.md) 第 9 条：btrfs 的 degraded 挂载越救越糟，根因就是降级语义没设计 |
| 5 | **checker 不许链接任何管道的运行时记账 / 校验代码** | 「审计与被审计不许用同一段代码」。对第三方比对内部更要紧——这里没有信任 |

**射程**：第 3 笔的条款已写、检查仍欠：超级块自举头段有「写入者身份 20」= 实现标识 16 字节 ASCII 零补齐 + 版本 4 字节 u32，第一版写 `singlefs-rs` / 1（D22（单元原子性怎么合成） 已定项 9），落成不变量 I-1.5（超级块记管道身份），checker 侧还没实现。第 1 笔的发布形态由已定项 3 定，判定程序与本仓 checker 是不是同一份代码仍开着。五笔都在第一条第三方管道出现之前不落字节。

**依据**：

- 无实验：五笔说的是「一条管道来了要满足什么」，今天一条第三方管道都没有，没有可量的量；第 3 笔已经落成盘上字段与不变量，量它的是 checker 而不是实验。
- [pitfalls.md](../pitfalls.md) 第 9 条（btrfs 的 degraded 挂载）是第 4 笔的来源；第 2、5 笔来自 `.claude/singlefs-ai-sop/rules/show-me-test.md` 与 `.claude/rules/fs-design.md` 的两条既有纪律；第 3 笔的字段由用户定案（2026-09-14），原话在变更史。

**欠**：C25（三个 oracle 零代码）；C8（门禁范围判不出来）。
