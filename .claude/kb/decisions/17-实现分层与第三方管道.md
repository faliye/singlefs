## D17 实现分层与第三方管道 —— 半定（腰线已定，一条未定：等价类数待三方）

**腰线划在提交协议之下。** 每种介质各自一条独立管道（分配、放置、布局、索引调优、
节点大小、缓存、设备处理全部各自实现，且第三方可以自带一条）；
**而事务的抽象状态机、提交步骤集合、崩溃语义留在腰线以上，由本工程独占。**

**协议是本工程的。** 一条管道要引入新的结构性提交步骤，必须往本仓的共享枚举
（D13（验证路线） 的 `CommitStep`）发一个 diff，不许在自己的黑盒里发明。

依据（2026-08-27 三方论证，三条腿一致）：

1. **反推腿（Opus，查内核 6.17 树 + OpenZFS master，逐条现查复核过）**：
   **没有查到任何一个案例同时满足三条**——第三方自带后端 + 契约里含崩溃一致性语义 +
   契约没被架空。查到的成立案例只走两条路之一：契约里根本不含崩溃语义
   （FUSE / SPDK bdev / dm `target_type`，三者头文件与文档均逐条核实无该类规范文字），
   或者后端不许拒绝、中间层合成（`REQ_PREFLUSH`/`REQ_FUA`）。
   ⚠️ 这是**查不到**，不是「不存在」——不许当成阴性结论用。
2. **唯一一个真做出可插拔后端的生产 COW 文件系统是 ZFS，而它的后端签名里带事务组号。**
   现查 OpenZFS master `include/sys/vdev_impl.h`：
   `:62 typedef uint64_t vdev_asize_func_t(vdev_t *vd, uint64_t psize, uint64_t txg);`，
   `:252-254` 后端自己持有三条 per-txg 脏链表（`vdev_ms_list` / `vdev_dtl_list` / `vdev_txg_node`），
   `vdev_ops` 里 `vdev_op_metaslab_init` / `vdev_op_config_generate` / `vdev_op_nparity` /
   `vdev_op_min_alloc` 四个越过了「只搬数据」那条线。
   ⇒ **「一个事务层，所有结构共用」与「后端第三方自带」在现役实现里从没共存过。**
3. **正推腿（Sonnet）独立推出同一处腰线**：更浅的两处（设备驱动之下 / 分配放置之下）
   装不下 zoned「根指针不能原地覆盖」这条结构性事实——它天然属于提交协议层，
   划在更浅处会渗透穿过腰线改变上侧共用的状态机；更深的两处（索引之上 / POSIX 之上）
   要么放弃 D12（目标介质） 已买单的「拒绝挂载而非静默误读」，要么被推到底之后事实上收缩回本腰线。
4. **不主动划线的后果有现役演示**（现查内核 6.17）：btrfs 的 zoned 不是一个 `zoned.c` 模块，
   `btrfs_is_zoned` 散在 **22 个文件 93 处**，其中 **5 处在 `tree-log.c`**（事务日志路径）、
   **6 处在 `space-info.c`**（ENOSPC 准入）。
   ⇒ **介质分支不划线的话会自己渗进 `.claude/rules/fs-design.md` 第一格与事务层**，
   而那正是「唯一不许多样化」的地方。**强解耦不是可选项，是防渗透的手段。**

### 「数据接口」的精确含义

**不是「同一份字节」**——D12（目标介质） 已定各介质各自一套布局，盘上字节按设计就是不同的。

**数据接口 = 「能安全拒绝」所需的最小字节集合。** 即：格式里足够让一个陌生读者
总能得出确定判决的那一截——挂载 / 只读挂载 / 拒绝，三选一，
**永远不会是第四种「照着错的假设读出看起来合法的字节」**。

可机检形态：**一个不链接任何管道代码的裸头部解析器**，对任意声称是 singlefs 的字节串跑，
断言 I-1.1（块头自述逻辑地址）~I-1.4（块头 fsid 一致） 四个字段都抽得出且自洽 + feature bit 编码 + 指针里校验和/MAC 字段的位置与宽度。

### 失败模型是第二根轴，且它不许由管道声明

**崩溃点的定义域是「步骤集合 × 每步的失败原子性宽度」，而 D13（验证路线） 的 `CommitStep` 枚举
只钉住了第一项。** 持久内存（失败原子性从块掉到 8 字节）与对象存储（PUT 之间无序、无 fsync）
都不新增步骤，它们**改变每一个已有步骤的失败模型**，枚举接不住。

**补法是核心层规定一个失败模型、管道不许声明例外；达不到的由核心层合成**
（读回校验 / 双写 / 补一条日志）。
依据是现役对照组：允许后端返回 `-EOPNOTSUPP` 的 `REQ_HARDBARRIER` 在 2.6.37 被砍，
换成不许后端拒绝、块层自己合成的 `REQ_PREFLUSH`/`REQ_FUA`，至今 15 年未变；
**两者唯一的差别就是允不允许后端说「我不支持」**。

⚠️ 「失败原子性宽度 / 撕裂 / 重排序」今天的覆盖在 D13（验证路线） 已定项 4（崩溃状态集合）与 D20（承重面：单元的原子性与自包含） / D22（单元原子性怎么合成） 里；2026-08-27 立本项时全 kb 零覆盖。
最接近的是 [checks-owed.md](../checks-owed.md) C6（块层语义假设写错），但那问的是「本工程的假设对不对」，
不是「一条管道的失败模型是什么」。

### 两个可以照抄的成功模板（现查内核 6.17 核实）

| 模板 | 规模 | 它靠什么活下来 |
|---|---|---|
| `iomap` | 正好 2 个方法（`iomap_begin`/`iomap_end`），12 个文件系统在用 | **契约里刻意不含事务概念**——`include/linux/iomap.h` grep `journal\|transaction\|trans` **0 命中**。共享层只拿走页缓存迭代，崩溃语义整体留在文件系统里 |
| `REQ_PREFLUSH` / `REQ_FUA` | 2 个 bit，15 年未变 | **后端不许拒绝**，设备不支持时块层自己合成 |

⚠️ **即使克制如 `iomap`，边界仍在渗**：`iomap.h:114` 的 `validity_cookie` 是因为
共享层不知道后端的事务何时让映射失效，只能让文件系统往结构里塞一个序列号。
**照抄模板不等于边界自动守得住。**

#### 已定项 3（2026-08-31）：一致性套件发源码 + 判定程序

**发两样：套件的源码，以及一个判定程序。** 不发容器，也不只发镜像语料。

**它买到什么**：第三方管道要证明自己合规，跑的是**同一份判定程序**，
而判定逻辑是**可读的源码**、不是黑盒——这与 D13（验证路线） 已定
「O2（独立解析器 + checker） 是一元谓词、只判单个镜像」同型：判定必须能被第三方自己复核，
否则「合规」就退化成「我们说你合规」。

⚠️ **它没答的**：判定程序与本仓 checker 是同一份代码还是两份。
若同一份，`.claude/rules/fs-design.md` 那条「审计与被审计不许用同一段代码」在这里要重新判一次——
第三方是被审计方，本工程是审计方，**这与 checker / 运行时那一对不是同一种关系**，不能直接照搬结论。
落点：D17（实现分层与第三方管道） 未定项 2（结构等价类数）与 [checks-owed.md](../checks-owed.md) C8（门禁范围判不出来）。

⚠️ **镜像语料不在发布物里，是一个选择而不是遗漏**：语料会随格式演进而过期，
而源码 + 判定程序可以随版本走。要不要另外发一份**冻结时刻的**语料，跟着 D15（格式冻结政策） 定。

#### 已定项 5（2026-09-03，用户定案，按三方对抗定）：第一版是纯用户态库，不挂载

**第一版是一个纯用户态 Rust 库，只对块设备抽象编程，两个后端：普通文件与 `O_DIRECT` 打开的裸设备。**
它对外是一组操作（mkfs、打开、写 extent、发布 / fsync、恢复），崩溃点重放 harness、
RefFS 对拍、QEMU 档的负载二进制都直接驱动这组操作，形态照 `research/` 下那批实验二进制。
**第一版没有挂载**：FUSE 是后来的一层薄适配，等目录与 POSIX 面出现之后再加；
内核模块在可预见的几年里不做。

**三样验证手段都不需要挂载**（2026-09-03 三方对抗，正推腿从已定条款推、替代反推腿找不到反例）：
崩溃点重放要的是能拦住块设备那三个原语（写、屏障、FUA 写），D13（验证路线）已定项 4 定的录制就在那一层；
RefFS 对拍要的是同一串操作能喂给两边、比结果，不碰盘；QEMU 档现在跑的就是静态 musl 二进制吃 `/dev/vda`
（[vm-harness.md](../vm-harness.md)），本机已经这么跑过九个实验。

⚠️ **录制钩子挂在块设备接口上，不是挂在操作 API 上**（正推腿指出）：一次「发布 / fsync」内部会发出
多次单元写、两道屏障与一次 FUA 写，钩子挂在 API 层就把那些中间崩溃点整个吞掉，
而 D13（验证路线）已定项 4 的枚举域正是那些原语。**实现要给出「一次 API 调用发了几个设备级操作」的读数**，
harness 拿它比对录到的条数，对不上整轮作废——形态照 [vm-harness.md](../vm-harness.md) 那道完整性闸。

⚠️ **库要落在 `crates/` 下面**（正推腿指出）：门禁的「Show me test」只认 `crates/*/src/` 里的实现代码，
放在 `research/` 下等于第一个可运行目标不受那条准入铁律管。

⚠️ **它确实不改任何盘上字节，但载体不是零成本的**（替代反推腿现查本机内核 6.17 源码
`block/bdev.c` 的 `sb_validate_large_blocksize`，主 agent 逐行复核）：`sb_set_blocksize` 对
大于 `PAGE_SIZE` 的块大小要求文件系统带 `FS_LBS` 标志且内核开了 `CONFIG_TRANSPARENT_HUGEPAGE`，
而本工程的单元 32768、节点 16384 都大于本机的 4096，所以**内核模块那条路要么依赖那个内核特性、
要么自己在内部做小于页的缓冲**。库与 FUSE 两条路不碰这个约束。这不改字节，但它是选内核模块要先付的账。
⚠️ **一处措辞要准**：推迟内核模块的依据不是 D7（是否进 Linux 主线）——那条只说不往主线投，
没说不许做树外模块。真正的依据是 `.claude/rules/fs-design.md`「先做慢而正确的那条」，加上大块 `sb_set_blocksize` 那笔内核账。
