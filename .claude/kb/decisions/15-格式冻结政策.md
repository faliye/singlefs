## D15 格式冻结政策 —— 已定（机制与三条分项全定）

回答两个问题：**什么时候允许说「format v1 frozen」**，以及**冻结之后新增东西走什么通道**。
它是 D11（索引节点要不要留消息缓冲区） / D12（目标介质） / D14（双轨（大小文件 / 持久临时）） 的共同前置——「格式分支永久」这条成本的**当期值为零、冻结后为无穷**，
所以那几条决策的真实代价由 D15（格式冻结政策）定义。

### 冻结是一次受门禁仲裁的提交，不是一句话

**动作**：冻结 = 向仓库提交 `.claude/kb/format-frozen/<组件>.toml`
（内容含 `version`、`frozen_at_commit`、`spec_hash`）。

**谁判**：不是人「觉得可以了」就生效。门禁一旦发现本次 diff 触碰了这个目录，
自动切换到一套更严的前置检查，全部满足才允许该 commit 通过。
**人只决定「现在要不要发起冻结」，机器决定「这次冻结请求成不成立」**——
与 `.claude/singlefs-ai-sop/rules/show-me-test.md`「不按来源区分，只按证据区分」同构。

该阶段平时不跑（形态同 `GATE_QEMU`），因此现在挂上去也不拖慢日常提交。
**它注定常年触发 0 次，这不是缺陷，是正确状态**——与门禁显式列出未实现阶段是同一种诚实。

### 冻结前必须完成的清单

| # | 项 | 不做它冻结会怎样 |

**实测已经发生过一次**（2026-08-31）：第 7 项对 D14（双轨（大小文件 / 持久临时）） 的复核写着

### 冻结分四层，有严格依赖顺序

```
第 1 层：超级块 + 块头（自身地址 / generation / 树 ID / fsid / magic）
    ↓
第 2 层：指针字段布局（D4 校验和 + D9 的 MAC / nonce / 密文校验和）
    ↓
第 3 层：各 keyspace 的 key 编码（D8 的 locality_id / inode / offset）
    ↓
第 4 层：索引节点内部布局（节点大小规则、bset 形态、D11 的消息缓冲区）
```

依赖方向的理由：第 1 层是「元数据块必须自描述」的物理前提，后面所有层都建在它之上；
第 2 层被 D9（加密）的 MAC / nonce / 密文校验和「事后加不进去」钉死，必须先于依赖它的树结构；
第 3 层的 key 编码定了，节点内部怎么组织这些 key 才有讨论基础。

⚠️ **分批冻结的风险必须显式接受**：早冻的层若漏留字段，后面只能走 incompat 打补丁，
等价于提前烧掉一次本该整体设计时留的余量。
止损规则只有一条：**第 1、2 层冻结前必须已包含 D9（加密）全部四项预留**，
因为它们恰好是「已知迟早要用」的字段，不能指望第 3、4 层再补。

**四层之外的独立冻结组件**（2026-09-05，随 D8（核心索引结构） 已定项 6 立；③ 2026-09-11 随 D16（发布语义） 已定项 3 加）：有三样永久字节不属于四层里的任何一层，各立成一个组件，C9（冻结后偷改格式） 的 `spec_hash` 按组件记，四层不动——
③ journal 记录格式（记录头、点名项、载荷校验和的覆盖范围、事务边界）：冻结前置不早于第 2 层与落点粒度那一格，冻结时刻是提交它那份 toml 的 commit，新记录格式走「新记录类型 + 超级块 log-incompat 位」，全文在 D16（发布语义） 已定项 3；
① 打包记录单元的载荷记录格式，按打包记录类型登记：类型 2 的 140 字节 inode 记录表（D8（核心索引结构） 已定项 6），冻结时刻是第一个写出类型 2 容器的镜像；类型 1 的随 C84（墓碑单元的粒度没人定） 各自独立，不因类型 2 一起冻结；
② 统计量登记表（标签值 + 维度 + 合并规则，D5（快照 / 空间记账机制） 已定项 3 / 4）——合并规则是盘上语义，两个读者对同一批字节用不同规则会算出不同的值，C71（不认识的统计量标签静默忽略） 只罩「不认识的标签」，罩不到「认识标签但用错规则」。
两个组件的 spec 文件今天都不存在（C119（两个冻结组件没有 spec 文件））。

### 冻结之后失去哪些自由

| 软格式期的自由 | 冻结后变成什么 |
|---|---|
| 结构「拆了重做」 | 已冻结字段的宽度 / 存在性 / 含义不能再改；只能新增，退役字段走「保留读支持、停止写」 |
| 发现设计错了直接改正文不留兼容 | 决策记录层面仍可推翻，但**盘上字节层面从 0 兼容成本变成非零** |
| mkfs 自动选取规则可随时换算法 | 已冻结组件的选取规则本身也被钉死；换算法会让新旧镜像默认值不同，必须体现在新格式版本号下 |
| 实验结果不理想就直接改格式重定 | 只能通过新 feature bit 引入新策略，并保留旧值的解释能力 |
| checker 可以跟着格式自由改 | **对已冻结部分，checker 的判断变成事实上的兼容性契约**——悄悄改 checker 对冻结字段的解释，和悄悄改格式一样危险 |

### 冻结后的改动判定表

| 改动类型 | 旧读者会怎样 | 哪档 | bump | 理由 |
|---|---|---|---|---|
| 新增字段在预留区 / TLV 尾部 | 忽略，继续正常工作 | compat | 否 | 没有语义依赖的纯加法，「忽略陌生字段」这条安全网够用 |
| 新增字段，缺了会让旧读者对**另一个已有字段**算错 | **算错，可能损坏数据** | incompat | 是 | 语义一旦耦合，安全网失效 |
| 扩大已有字段宽度 | 按旧宽度解析，越界读 / 错位 | incompat | 是 | 宽度是布局的一部分，旧代码的偏移计算全错 |
| 改变已有字段含义 | 按旧含义解读，**不报错**地产生错误行为 | incompat，且**弃用旧位置不复用** | 是 | 位置复用会让新旧读者无法区分，是最危险的一类。两个实例（D18（块里携带什么信息） 已定项 11）：新增一个单元类（登记表码 4–15）改的是类身份段的解析口径；给共同前缀偏移 7 里恒 0 的 flag 位赋义（旧读者对非 0 位一律拒收） |
| 新增记录类型（新 key 类型） | 只读遍历可能误判；整理 / 写可能误删看不懂的记录 | compat_ro | 是 | **「只读安全」与「可写安全」是两条独立保证**，必须分开判。⚠️ 打包记录单元内的打包记录类型**不走这一行**（D18（块里携带什么信息） 已定项 11）：跳过一个墓碑类或 inode 类记录会改变只读答案（E59（缓冲消息能不能只从单元重算）），默认档是 incompat；只有登记时能证明「跳过它不改变任何只读答案」的类型才降到 compat_ro，且 compat_ro 读者不许跑扫描重建 |
| 新增一棵 keyspace | 若超级块的树表 day-1 就是开放列表：只是看不到新树；若树数量硬编码：读不出树表 | **compat**（已定：树表 day-1 做成开放列表，见已定项 2）。留了开放树表 → compat；没留 → incompat | 是 | **「树表是否可扩展」必须在冻结时决定**，不能等要加树才发现没留 |
| 改变排序规则 | 二分查找 / 遍历结果错，**不报错** | incompat | 是 | 排序规则是索引本体，日志结构节点的重排直接依赖它不变 |
| 改变校验和 / MAC 算法 | D9（加密）的算法类型字段已留 → 遇到不认识的类型只能显式失败 | 已留 → compat_ro；未留 → incompat | 是 | D9（加密）day-1 预留字段第 4 项正是为这类改动准备的通道 |
| 退役一个字段 | 不受影响，旧读者继续按旧方式解释 | compat，且**永久保留解析代码** | 否 | 落过盘的字段，只要还有一份旧镜像存在就必须一直能被解释 |

### feature bit 补成可实现的形态

- **位数**：三个 bitmap 各 **256 位**（`u64[4]`），存超级块。
  位比字段宽度便宜得多（3×32 字节对超级块可忽略），**预留要往宽了留**。
- **记账**：新建 `.claude/kb/feature-bits.md`，列
  `位号 | 类别 | 名称 | 引入版本 | 引入 commit | 状态 | 语义一句话`。
- **分配权是「谁先合并谁先占」，不是审批制**。门禁强制：位号严格递增、不许跳号占位、
  不许有代码引用了表里不存在的位号——机械仲裁。
- **位一旦用过不许回收。** 理由比 `invariants.md` 编号不回收**更硬**：
  编号是检索键，回收误导的是「读文档的人或模型」；
  **feature bit 是磁盘上真实存在过的物理位**。回收后重新分配给新特性，
  一个旧镜像挂到新代码上，这一位会被误读成「新特性 X 已启用」——
  **文件系统会真的做错事**（例如把不存在的加密特征当存在，去找不存在的密钥）。
  退役的位标为「含义永久锁定为退役前最后一次使用的语义」，不许赋予新特性。

### 两条会红的检查（已记进 [checks-owed.md](../checks-owed.md)）

1. **格式冻结契约**：每个已冻结组件记 `spec_hash`；门禁重算并比对，
   不同则要求本次 diff **同时**满足「`feature-bits.md` 有新增行或 `version` 被显式改动」
   与「`decisions.md` 对应条目在同一 commit 里被改动」。缺一判红。
2. **向后兼容回归（黄金镜像）**：每次某组件版本变化时用**当时的代码**生成一份镜像并归档，
   门禁用**当前代码**去读全部历史镜像、跑 checker、比对期望内容摘要。
   ⚠️ 镜像本体**不进 git**（`command-safety.md`：测试镜像不许放仓库内），
   仓库只提交清单 `.claude/kb/golden-images.toml`；镜像放
   `${SINGLEFS_GOLDEN_DIR:-$HOME/.cache/singlefs-golden}`。
   清单**只增不删**——删掉某版本的回归等于悄悄放弃对它的兼容承诺，必须走决策记录。

#### 已定项 1（2026-09-09，主 agent 定案，按三方论证）：第 7 项的对象是未定分项，不是决策名单

**先定问法。** 「第 7 项的具体处置」有三种读法，答案不一样，所以先定读法
（`.claude/singlefs-ai-sop/skills/decide/SKILL.md` 硬要求 7：待定项的问法必须只有一种读法）：

| 读法 | 它在问什么 | 判 |
|---|---|---|
| 逐条钉死六格的取值 | 现在就替那六条决策各自答一句 | **不取**：每一格的内容住在各自那条决策里，D15（格式冻结政策）复制一份就是同一事实两处记录 |
| 定第 7 项的判定规则 | 对象是谁、状态从哪儿取、留白宽度默认多少 | **取它** |
| 第 7 项是一次性的门还是逐次冻结重判 | 冻第 k 个组件时要不要重跑一遍 | **逐次重判**：清单是 commit 触发的前置检查（正文「谁判」那一段逐字「门禁一旦发现本次 diff 触碰了这个目录，自动切换到一套更严的前置检查」），每一次冻结请求都跑一遍 |

**定三条**：

1. **对象是全仓每一条仍未定的分项，不是一份决策名单。** 每条未定分项要带一句判定——
   **动不动格式**：它的答案会不会改动任何盘上字节，或改动已有字节的**解释口径**
   （口径这半是 C97（改字段含义而不改宽度，全仓没有一处会红）的形态：宽度一个字节不变而含义变了）。
   三个取值：**动 / 不动 / 界不定（视同动）**；**没写过视同动**。
2. **判定**：冻结请求发起时，凡判「动」或没判过的，判红。要分批冻结就在请求里**逐条列名并显式接受风险**
   （形态照正文「分批冻结的风险必须显式接受」那一段），**列漏一条判红**。
3. **留白宽度默认 0**，举证责任在要留非零宽度的一方，必须过 `.claude/rules/fs-design.md` 的格式分支判据
   （逐字：「一条格式分支值不值得，看它能不能把『用错了』变成『挂不上』」）。

**为什么谓词不按层切**（2026-09-09 反推腿打中，主 agent 现查坐实）：四层图今天①挂着
C45（冻结分层重排挂了单没做）的单要重排；②成员不齐——正文「四层之外的独立冻结组件」那一段逐字说有三样永久字节
「不属于四层里的任何一层」；③至少一个成员的归属当时**本身就是未定项**：D16（发布语义）已定项 3 当时逐字问的正是

#### 已定项 3（2026-09-09，主 agent 定案，按三方论证）：`spec_hash` 恒对 kb 字段表的完整投影求，不切到 Rust 结构体

**先定问法。** 三种读法：只问切换时机（它预设了切换一定发生）、问哈希的输入工件锚在哪一侧、
问它钉住的是字节布局还是盘上语义。**取后两种合起来的那一问**，因为切换本身不成立。

**定案**：`spec_hash` 恒对 `format-spec/<组件>.toml` 求。那份 toml 是 **kb 字段表的完整投影**——
含**行序**（盘上顺序）与**非标量的盘上语义规则**（组件 ② 的合并规则以数据形式写进去），
不是已登记的那批标量常量的集合。有代码之后新增的**不是换哈希源**，是两道检查：
① spec 与代码之间的**相等性检查**（宽度与顺序都比）；② 黄金镜像回归（正文「两条会红的检查」第 2 条）。

**四条理由**：

1. **方向**。D13（验证路线）已定项 5 逐字：「**checker 与实现之间只共享一样东西：一份由 kb 的字段表生成的常量模块**，
   生成器从 kb 读、两边都只消费，任何人不许手改」⇒ 权威在 kb，Rust 结构体是**下游消费者**。
   对结构体求哈希，是把永久契约的指纹锚在派生物上。
2. **哈希是变更探测器，不是两份工件的相等性检查。** 对结构体求哈希抓不到「结构体与 kb 不一致」，
   它只在结构体**变化**时报警。真正抓那一类错的是相等性检查，而相等性检查要求 spec 侧存在
   ⇒ 切过去不但没多买到东西，还把要比对的另一侧拆掉了。
3. **语言绑定**。D17（实现分层与第三方管道）已定项 3 逐字：「判定必须能被第三方自己复核，
   否则『合规』就退化成『我们说你合规』」。指纹锚在 Rust 源码文本上，第三方管道复算不了它。
4. **落地**。2026-09-09 现查 `crates/` 不存在，全仓零行实现代码 ⇒ 切换那条路在整个设计阶段没有输入；
   而正文「四层之外的独立冻结组件」那一段逐字说组件 ① 的「冻结时刻是第一个写出类型 2 容器的镜像」
   ⇒ 切换会被逼到与第一次真实冻结同一个提交里完成，零试跑期。
   反过来，两个组件的 spec 文件今天就写得出来（C119（两个冻结组件没有 spec 文件）自己给的下一步），
   哈希机制可以远早于第一次冻结开始生效。

⚠️ **spec 只投影标量是不够的**（2026-09-09 反推腿按跑前写死的失败条款判这条臂出局，主 agent 现查坐实）：
**按最弱读法这条臂输了一次**——若 spec 就是那批已登记的标量常量，字段顺序那条假绿它罩不住，而
「对 Rust 结构体求哈希」「双哈希」「锚在黄金镜像字节上」三条臂都会红。定案取的是**收严后的形态**
（spec 必须含行序），新形态比旧形态多要求一样东西、没少要求任何东西
（`.claude/singlefs-ai-sop/rules/evidence-discipline.md`「臂的定义也在『跑前写死』之列」那三步）。
[first-txn-layout.md](../first-txn-layout.md) 的单元头逐行列着**六个宽度都是 8 的相邻字段**
（五元组的树 ID / 对象 ID / 对象出生代 / 锚点偏移，以及诞生代号、fsid）。
把序列化时任意两个对调，所有标量与 `UNIT_HDR_DATA = 105` 一个都不变、盘上字节全错位，
落进正文改动判定表「改变已有字段含义」那一行（incompat，且弃用旧位置不复用）。
⇒ **spec 必须含行序**，相等性检查也要比顺序。
⚠️ 有人会拿 D13（验证路线）已定项 5 那条边界来反对，它逐字是：「**一条边界要守住**：生成器只发射标量值。
它一旦开始发射『按字段表算出来的偏移函数』，那就是 D13（验证路线） 明令不许共享的格式解析，而不再是常量。
判据是发射物里有没有分支与算术。」**它管的是 checker 与实现之间的共享物**，理由是不许共享格式解析；
`format-spec/<组件>.toml` 是**门禁工件**，运行期一个消费者都没有 ⇒ 不在那条边界的射程里。
而且按它自己的判据，一张带行序的字段表**既没有分支也没有算术**。

**抓不到的，明说**：spec 与实际写出的字节之间，哈希**不构成绑定**。
第一份黄金镜像若本身就是错代码写出来的，回归会把错的那份当基准（本地腿构造，主 agent 采纳）。
堵它的是 checker 这个独立解析器与一致性套件的判定程序，不是 `spec_hash`。
落点 C227（黄金镜像的基准是它自己那份代码写的）。
同理，spec 今天注定手写——没有任何从 kb 字段表投影到 toml 的机制，手改脱节与
C94（登记的格式常量与后来的定案对不上）是同一个形状，落点 C226（spec 是手抄的，没有从字段表生成）。

⚠️ **给不出可判定形式的一处**：分批冻结「早冻层漏留字段」的**风险大小**
（具体浪费多少格式余量）给不出量化形式——它依赖尚不存在的 D8（核心索引结构） / D11（索引节点要不要留消息缓冲区） 具体布局。
