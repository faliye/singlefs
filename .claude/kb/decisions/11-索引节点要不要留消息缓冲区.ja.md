## D11 インデックスノード内のメッセージバッファ要否 —— 確定

[中文](11-索引节点要不要留消息缓冲区.md) · [English](11-索引节点要不要留消息缓冲区.en.md) · **日本語**

D11 (インデックスノード内のメッセージバッファ要否) はインデックスノードのディスクフォーマット内にメッセージバッファ領域を保持し、毎回の書き込みで葉を変更するのではなく小書き込みを内部ノードに蓄積してバッチでフラッシュするか（Bε-tree 形態）、すなわち D10 (ランダム書き込み / 断片化の真の回答) 候補 A の具体的形態を管轄する。その実質は「キーの権威値が、一時的に最終位置に存在しないことを許容するか否か」であり、「空間をどう会計するか」と同次元のメンタルモデルである（.claude/rules/format-evolution.md「概念モデルの変更は慎重に」）。バッファを保持するか否か、ε の設定値、分岐基準、陳腐化の検出方法、バッファの再計算可能性、再構築前の排空を管轄する。管轄外：ノードサイズは D8 (コアインデックス構造) 確定項目 2；write buffer フロントエンドとノードメッセージバッファの連携は D8 (コアインデックス構造) 確定項目 12；メッセージバッファの凍結方針上の位置づけは D15 (フォーマット凍結ポリシー) 第4層（インデックスノード内部レイアウト）に属する。第1版では全ツリーで ε = 0 とする（確定項目 7）。

### 確定項目

D11 (インデックスノード内のメッセージバッファ要否) の分項番号体系は単一であり、再採番は行わない。

| # | 項目 | 決定 |

| 2 | **ε の設定値** | 将来値は 0.65（ファンアウト 119、バッファ 665 件）、第1版では無効；有効化前に現行の pivot とメッセージ幅で E56 (メッセージバッファのゲイン vs イプシロン) を再実行 **状態：確定。** **進捗：未実装。** |
| 3 | **陳腐化の検出メカニズム** | 検出可能、確定項目 4 の2つの再計算ソースに依拠；検出ロジックはメッセージ生成または適用のコードを再利用してはならない **状態：確定。** **進捗：未実装。** |
| 4 | **バッファ内メッセージはユニットのみから再計算可能か** | 権威態から再計算可能、ソースはユニット（書き込み順付き）+ インスタンス表 + 祖先表 + 墓石ユニット；バッファは純粋な派生態にとどまり、権威態は拡張しない **状態：確定。** **進捗：対象なし。** |

#### 確定項目 1：メッセージバッファを保持するか否か

**定案**：保持する。インデックスノードのディスクフォーマットにメッセージバッファ領域を確保し、内部ノード内にバッファを常駐させる；メッセージを独立したツリー（`pending_ops`）とする代替案は却下された。第1版では全ツリーで ε = 0 とし、有効化しない（確定項目 7）。

**射程**：本決定は2つの既知の未決事項を踏まえて下された裁定であり、それらが解消されたわけではない：コスト 2（再構築性が「検出可能な到達不能」から「検出不可能な陳腐化」へ退行する）は依然として推論であり定量化されていない；.claude/rules/fs-design.md のフォーマット分岐判定基準はこれを負の改善と判定する——メッセージバッファは「誤用→マウント不能」を買うことができず、同一規則は「判定基準に『この方が速い』を含めてはならない」と明記している ⇒ 性能上の利益は同基準における合格理由とはならない。これは [pitfalls.md](../pitfalls.md) 第 10 項の根本原因（再構築性が設計目標になっていない）へ一歩近づくものであるため、確定項目 3（陳腐化の検出メカニズム）は選択肢ではなく必須である。コスト 1（チェッカーの増分 Δ 形態に対する識別力がゼロになる）は、D8 (コアインデックス構造) 確定項目 1 でべき等完全値を採用したため本プロジェクトには当てはまらない；ある種の会計がべき等にできない場合、その種別はランタイムと判定コードを共有しない独立した再計算パスを持たなければならない（C12 (増分セマンティクス共用)）。

**根拠**：

- E56 (メッセージバッファのゲイン vs イプシロン)：16 KiB ノードにおいて利益は ε の強い関数であり、4つのツリー規模すべてで顕著である；ノードサイズは ε の分解能を決定するだけであり、利益の有無を決定するわけではない。
- E14 (I-3.1の判別力：冪等完全値 vs 増分Δ)：コスト 1 は増分 Δ 形態においてのみ成立し、べき等完全値形態ではチェッカーの独立再計算によりセマンティクス記述ミスを捕捉できる——べき等完全値の採用後は「保持」を妨げない。
- ユーザー決定、日付と経緯は変更履歴にある；「メッセージの独立ツリー化」が却下された論証も変更履歴にある。

**未済の検査**：C52 (陳腐化を正当とみなす)：コスト 2 のセーフティネット検査；C349 (再構成時にノードメッセージバッファをどう移行するかの条項がない)：収縮・再平衡時にノードバッファ内のメッセージをどう移行するか。

#### 確定項目 2：ε の設定値

**定案**：ε = 0.65 は将来値であり、第1版の設定値ではない（確定項目 7）：ファンアウト F = 119、バッファ B = 665 件であり、双方が同一の 16 KiB ノードバイトを競合する。有効化するか否か、どの程度にするかは、現行の pivot とメッセージ幅で E56 (メッセージバッファのゲイン vs イプシロン) を再実行した後に決定する。

**射程**：ε は可逆的であり、「保持するか否か」は不可逆的である：D21 (権威態と派生態の境界) によりインデックスは派生態である ⇒ ε の変更 = インデックス再構築であり、フォーマット変更を伴わない。そのため確定項目 2 は将来的に確定項目 3（陳腐化の検出メカニズム）の結果に基づき上下調整可能であるが、確定項目 1 は不可能である。ε を押し下げる唯一の力はコスト 2 の露出面であるが、数値が存在しない。将来値 0.65、ファンアウト 119、バッファ 665 件は E56 (メッセージバッファのゲイン vs イプシロン) の pivot 48 およびメッセージ幅 16 に由来し、これら2つの入力はいずれも無効化されている（C351 (ε 0.65 の2入力が無効化されたのに数値が本文に残存)）。

**根拠**：

- E56 (メッセージバッファのゲイン vs イプシロン)：ε = 0.65 は4つのツリー規模すべてで ε = 0.5 を一貫して上回り、ポイントルックアップのコスト増加は数パーセントにとどまる；ツリーの高さは (葉の数, ファンアウト) の従属変数であり、1層余分に支払うことに決定的なコストペナルティはない。
- ユーザー決定、日付と経緯は変更履歴にある。

**未済の検査**：C351 (ε 0.65 の2入力が無効化されたのに数値が本文に残存)：現行の pivot とメッセージ幅で E56 (メッセージバッファのゲイン vs イプシロン) を再実行する。再実行前は本文中の 0.65 / 119 / 665 に一律「将来値」を付記する。

#### 確定項目 3：陳腐化の検出メカニズム

**定案**：コスト 2（再構築性が「検出可能な到達不能」から「検出不可能な陳腐化」へ退行する）にはセーフティネットが存在し、解決不能ではない。検出メカニズムは確定項目 4 の2つの再計算ソースに依拠し、第3の要素を必要としない：

| 問い | 回答元 |
|---|---|
| この配置先が現行バージョンであるか否か | **ユニット自身の書き込み順 + インスタンス表 + 祖先表**（C113 (スキャン再構築時における複数版ユニットの現行バージョン判定に入力がない) 定案 P2 / P3：書き込み順 (インスタンス代号, トランザクション番号) とインスタンス表を組み合わせて「パブリッシュされたか否か」を判定し、祖先表により「このツリーから可視か」を判定、可視候補の中で書き込み順が最大のものが現行バージョンである） |
| この key がすでに死亡しているか否か | **墓石ユニット**（削除時にユニットを書き込むと決定済み） |

**検出ロジックはメッセージ生成または適用のコードを再利用してはならない。** さもなくば bcachefs と同一の形状を再犯し、適用プロセスの偏差は捕捉できても、セマンティクス自体の記述ミスを捕捉できなくなる。

**射程**：定めたのは「検出可能であること」であり、未済の検査は「検出可能であることの証明」である。空間会計は配置先ごとに「この配置先が生存しているか」を答えることができず（D3 (領域割り当て) 確定項目 1 に会計ツリーは個々の配置先には答えられないと明記）、そのため現行バージョン判定の問いは会計に委ねない。

**根拠**：

- E104 (スキャン再構築における現行バージョンの判定)：書き込み順、インスタンス表の行、祖先表、死亡書き込み順、コンテナ退役レコード、クリーンアップゲートがすべて揃った場合、全規則アームはすべての世界とシードにおいて現行バージョンを正しく判定し、削除済み key を復活させない。いずれの要素を削ってもターゲット世界で誤判定となる——この入力セットは十分であり、各要素が荷重を分担している。
- E14 (I-3.1の判別力：冪等完全値 vs 増分Δ)：チェッカーがランタイムの累積関数を用いて再生を行う場合、自己比較となってセマンティクス記述ミスを1つも捕捉できない——検出ロジックはそのコードを再利用してはならない。
- ユーザー決定、日付と経緯は変更履歴にある。

**未済の検査**：C52 (陳腐化を正当とみなす)：「バッファメッセージが消失し、対応する葉に古い値が残る」イメージを作成し、N 回の故障注入に対して必ず N 回捕捉しなければならない（判定基準はサンプリング通過率ではなく故障注入率を見る）；検出メカニズムをオフにした場合、同一イメージが赤から緑に転じなければならない。

#### 確定項目 4：バッファ内メッセージはユニットのみから再計算可能か

**定案**：可能である。ソースは「ユニット（書き込み順付き）+ インスタンス表 + 祖先表 + 墓石ユニット」⇒ **バッファは依然として純粋な派生態にとどまり、D21 (権威態と派生態の境界) の「権威態 = ユニット + 会計 + ルート」は拡張しない**（インスタンス表ユニットはツリーテーブルユニットと同様にルートの間接層であり、権威態の項目は増えない）。ユニット自身の書き込み順でパブリッシュ可能性を判定し（インスタンス表が上限を提供）、祖先表でツリー軸の可視性を判定し、墓石ユニットで key の死亡を判定する。

**射程**：「ユニットのみから」ではない——その狭い問いに対する答えは不可能である；成立するのは**権威態**からの再計算である。会計は配置先ごとに生存を判定できず（D3 (領域割り当て) 确定項目 1）、この半分は書き込み順、インスタンス表、祖先表のメカニズムによって代替される（C113 (スキャン再構築時における複数版ユニットの現行バージョン判定に入力がない) 定案）。

**根拠**：

- E59 (バッファメッセージはユニットのみから再計算可能か)：ユニットのみから再計算した場合、上書き時に現行値を識別できず、削除が復活し、会計も連動して誤る；ユニット + 会計、シーケンス番号 + 墓石ユニットの2つのアームは4カテゴリすべてで正しく判定——「ユニットのみから」は成立せず、権威態からは成立する。
- E104 (スキャン再構築における現行バージョンの判定)：E59 (バッファメッセージはユニットのみから再計算可能か) 乙アームでオラクルとして用いた会計を書き込み順 + インスタンス表 + 祖先表のメカニズムに置き換えた後もすべて正しく判定された——ソース内の会計はこの一連のメカニズムで代替可能である。
- ユーザー決定、日付と経緯は変更履歴にある。

**未済の検査**：なし。

#### 確定項目 5：インデックス再構築前の排空契約

**定案**：**いかなるインデックス再構築（ε の変更、ノードサイズの変更、破損復旧）の前にも、各層のバッファ（ノード内のメッセージバッファ；write buffer フロントエンドはメモリ内構造であり再構築でクリアされず、読み出し順序では依然としてツリーの前段に配置される、C161 (2段バッファ共存で連携が未定) 第3ラウンドで明記）は必ず事前に排空されなければならず、この手順は再構築エントリポイントにより強制され、呼び出し側の規律に依存しない。**

**射程**：再構築エントリポイントのみを管轄する；write buffer フロントエンドは「各層のバッファ」に含まれず、再構築によってクリアされない。

**根拠**：

- E56 (メッセージバッファのゲイン vs イプシロン)：排空後の更新優位性は排空しない場合よりわずかに劣る程度である——排空自体は非常に低コストである；高コストなのは「排空忘れ」に対していかなる警告も出ない点であり、したがって判定基準は「忘れずに排空する」ではなく「誰が強制するか」に置かれる。
- ユーザー決定、日付と経緯は変更履歴にある。

**未済の検査**：C390 (インデックス再構築エントリポイントで強制排空しない)：赤となる検査は再構築パスとチェッカーの存在を前提とするため、現時点では記述できない。

#### 確定項目 6：ε は単一値かレイアウトにより分岐するか

**定案**：**レイアウト軸は分岐せず、全レイアウトで同一の ε を共有する**（将来値 0.65、E56 (メッセージバッファのゲイン vs イプシロン) を現行の幅で再実行するまでは未定、確定項目 2 参照；第1版は ε = 0、確定項目 7）。ツリー軸には別途分岐が存在し、分岐変数は確定項目 4 の述語である：**このツリーのフラッシュ待ちメッセージが権威態（ユニット + 会計 + 墓石ユニット）のみから再計算可能か否か**——可能 ⇒ バッファを保持し、ε は確定項目 2 の将来値 0.65 を採用；不可能 ⇒ 内部ノードにメッセージバッファを保持せず、ε = 0。write buffer フロントエンドを経由するツリー（会計 / 逆インデックス / LRU）は別の分岐変数である：ε は常に 0、ノードバッファは保持せず、フロントエンドはパブリッシュ前に葉へ直接排空する（D8 (コアインデックス構造) 確定項目 12）。

**射程**：inode ツリーのみが「不可能」側に属する：inode 属性の更新は葉（Code 3 パック記録ユニット）に到達するまで権威態の担持体を持たず、派生態ノードにバッファリングすると D21 (権威態と派生態の境界) 確定項目 4 のハード制約 6 に抵触する。extent / dirent / 逆インデックスは「可能」と判定される；会計ツリーは D21 (権威態と派生態の境界) 確定項目 10「オフラインで走査により再計算可能」に基づき「可能」と判定されるが、E59 (バッファメッセージはユニットのみから再計算可能か) のその列はオラクルであり実機検証されていない（C113 (スキャン再構築時における複数版ユニットの現行バージョン判定に入力がない)）。分岐変数はツリーごとに恒常であり、.claude/rules/fs-design.md の5つのハード要件（明示的判定基準、inode ツリー作成時にこの分岐上にあること、E103 (inodeパッキング経路1の更新コスト) とクラッシュポイント再生の個別検証、観測可能なノードレイアウト、操作途中で不変）を満たす；これは D15 (フォーマット凍結ポリシー) 第4層（派生態）に位置づけられ、フォーマット分岐ではない。将来的にレイアウトごとに分岐させる場合は、まず適格な分岐変数（明示的、計算可能、操作途中で不変）を提示し、次いで .claude/rules/fs-design.md の5つのハード要件を1つずつ満たさなければならない。

**根拠**：

- D14 (大小ファイル・永続/一時デュアルトラック) 確定項目 4 は、唯一の候補レイアウト分岐変数（永続 / 一時）を不成立と判定済みであり（`linkat` / `fsync` / スナップショットにより操作スコープ外から反転され、.claude/rules/fs-design.md ハード要件 5 に抵触）、同一規則には判定基準が書けない場合はまず1系統のみ実装すると規定されている；本件は可逆的（ε 変更 = インデックス再構築、フォーマット変更なし）であるため低コストである。
- E98 (inodeレコードとinodeツリーの幾何)：inode レコードのフィールドの多くは権威態のみからは再計算できない——inode ツリーは「不可能」側に属する。
- E59 (バッファメッセージはユニットのみから再計算可能か)：ユニット + 会計のアームはマッピング、逆インデックス、墓石の3種すべてで完全に正しい——extent / dirent / 逆インデックスは「可能」側に属する。
- ユーザー決定、日付と経緯は変更履歴にある。

**未済の検査**：なし。

#### 確定項目 7：他4ツリーおよびツリーテーブルユニットの ε；高さ 1 のツリー；第1版で全ツリー ε = 0 とするか否か

**定案**：第1版は全ツリーで ε = 0（extent および会計を含む）、高さ 1 のツリーはルートが葉でありバッファを持たない；D8 (コアインデックス構造) 確定項目 6「ルートは常に Code 2」は inode ツリーのみに適用される。確定項目 2 の 0.65 は将来値として維持する：E56 (メッセージバッファのゲイン vs イプシロン) を現行の pivot（105–117）とメッセージ幅（34–109）で再実行した後に、有効化するか否か、どの程度にするかを決定する。

**射程**：確定項目 1 は変更しない——「保持するか否か」は不可逆であり、ε は可逆である。D11 (インデックスノード内のメッセージバッファ要否) 確定項目 1 / 確定項目 2 / 確定項目 6 における 0.65、ファンアウト 119、バッファ 665 件は write buffer フロントエンド有効化後の将来値であり、第1版の設定値ではない；有効化するか否か、どの程度にするかは E56 (メッセージバッファのゲイン vs イプシロン) の再実行を待つ。

**根拠**：実験なし：第1版でバッファを有効化しないことは取捨選択であり、測定可能な量ではない——その将来値には裏付けとなる数値がなく（2つの入力が無効化済み、C351 (ε 0.65 の2入力が無効化されたのに数値が本文に残存)）、ε は可逆的であるが「保持するか否か」は不可逆であるため、まず ε = 0 として確定項目 1 には手を付けない。コーディング前の総監査（`records/2026-09-13-总审核.md` の D11 (インデックスノード内のメッセージバッファ要否) の2節）はこのアームを推奨し、ユーザー決定、日付と経緯は変更履歴にある。

**未済の検査**：C351 (ε 0.65 の2入力が無効化されたのに数値が本文に残存)。
