## D11 索引节点要不要留消息缓冲区 —— 待定（不能拖，前置是 D12（目标介质））

即 D10（随机写 / 碎片化的真答案） 候选 A 的具体形态：索引节点的磁盘格式里留不留一块「消息缓冲区」，
让小写先攒在内部节点里、批量下刷，而不是每次都改到叶子（Bε-tree 形态）。

**它的实质不是「节点里留不留一块区域」，是**
**「一个 key 的权威值，允不允许暂时不在它的最终位置上」。**
这是心智模型，与「空间怎么记账」同级——
`.claude/rules/format-evolution.md` 的「概念模型要慢」管的正是这一类，
而不是它前半句「字节随时可拆」管的那一类。

### 为什么不能拖：它与 E1（节点大小 vs 可恢复性） 的节点大小互相定义

⚠️ **这条理由的地基已经塌了一半（2026-08-29 审计，三方论证的正推腿擦到边、主 agent 推到根）。**
本节的链条整个压在 D8（核心索引结构） 约束 1 那句「改它等于重建文件系统」上，
而 **D21（权威态与派生态的分界）（2026-08-28 已定）已经取消了那句话**——索引是派生态，
「派生态的格式随便变，因为它整个可以从单元重建出来」。
⇒ 改节点大小 = 重建索引，不是重建文件系统 ⇒ **「先定任何一个等于替另一个做主」这个死结不再成立。**

⚠️ **塌的是「死结」，不是「代价」。** E30（坏一个节点的爆炸半径） 的数就在旁边：
改全局节点大小要让整棵树按新尺寸重建，规模与「坏根」同一量级（全盘扫描）。
⇒ 它变的是**范畴**（数据幸存，不是数据丢失），不是**代价**。

⚠️ **塌的也只是一半**：E29（明文映射层能不能只靠单元自描述重建） 实测重建在**数据块侧今天不成立**
（缺口恰等于数据块总数），欠 D18（块里携带什么信息） 未定项 3。
⚠️ 且 E29（明文映射层能不能只靠单元自描述重建） 测的是**明文映射层**而不是**索引树**，
两者靠「读同一份单元自描述」桥接——**那一步是推理不是实测**，依据写在 D8（核心索引结构） 约束 1 的批注里。
⇒ **本决策的紧迫性现在条件于 D18（块里携带什么信息） 未定项 3**：那一条补上之后，本决策可以拖；
在那之前它仍然卡着。**紧迫性的来源变了，不是消失了。**

原链条（保留，因为上面的收窄是对着它做的）：
Q13 悬着 → [experiments.md](../experiments.md) E1（节点大小 vs 可恢复性） 按「内部节点是纯路由」的重建语义定目标线 →
跑出一个节点大小 → 而 D8（核心索引结构） 约束 1 明写**节点大小是 mkfs 时的格式参数，建完就固定**。

方向还是单向的：E1（节点大小 vs 可恢复性） 的爆炸半径判据把节点往**小**推（D8（核心索引结构） 明写「不照抄 128K–256K」），
而摊销比是节点容量的函数——BetrFS 0.4 用 **4 MiB** 节点
（见 [prior-art.md](../prior-art.md) 7.1）。本工程若取到 16K–32K，
一次下刷能携带的消息条数接近 1，**消息缓冲的收益机制在那个节点大小下自然消失**。

**先定任何一个，等于替另一个做主。** 反方向同样成立：
若定为「要做」，节点大小下界被摊销要求顶起来，与爆炸半径判据直接对撞。

### 代价 1 的适用范围要改写：它是一条横跨 D8（核心索引结构） 与 D11（索引节点要不要留消息缓冲区） 的线

**关键区别不在「消息放节点内还是独立树」，在缓冲里放的是「幂等完整值」还是「增量」：**

| 缓冲内容形态 | 合并规则 | checker 要不要理解 value 语义 | 构不构成 D11（索引节点要不要留消息缓冲区） 代价 1 |
|---|---|---|---|
| **幂等完整值**（含 tombstone） | 「后者胜」覆盖 | **不要**——那是十几行可以独立重新实现的代码 | **不构成**。`evidence-discipline` 说的「共享同一段代码」够不着它 |
| **增量 Δ**（「减 1」「再释放 N 个」） | 依赖 value 语义 | **要** | **这才是代价 1 的成立条件** |

⚠️ **而 D8（核心索引结构） 已定的 write buffer 前端覆盖「反向索引、LRU、记账」三类。
记账那一棵在 bcachefs 里确实是 delta 形态——已核实（Linux v6.17 源码，逐字比对）：**

| 事实 | 源码 |
|---|---|
| accounting 树**格式级**绑定 write buffer | `bcachefs_format.h:1415` `x(accounting, 20, BTREE_IS_snapshot_field\|BTREE_IS_write_buffer, ...)` |
| 缓冲里放的是增量，不是完整值 | `disk_accounting_format.h` 原文：「Unlike with other key types, **updates are _deltas_**, and the deltas are not resolved until the update to the underlying btree, done by btree write buffer flush or journal replay」 |
| 合并是加法不是「后者胜」 | `disk_accounting.h:33` `bch2_accounting_accumulate()`：`dst->v.d[i] += src.v->d[i]` |
| write buffer 对 accounting 与普通 key **三处显式分叉** | 入 buffer（两个不同容器）、flush 去重（普通是后者胜、accounting 是先加进后者）、落 btree（accounting 要先读现值加进 Δ） |
| 非幂等派生出的额外成本 | 必须另造一套 **bversion 全序**来判断某条 Δ 有没有被应用过；journal replay 未完成时 accounting key **一律不许 flush** |

**⇒ 代价 1 的一部分，D8（核心索引结构） 已经在付了。**

### 而 bcachefs 的 checker 在这一格上是被自己绊倒的（本工程必须避开）

它的 `bch2_check_allocations()` 用全量遍历重建记账再 `memcmp` 比对——形态与本工程 I-3.1（已分配统计对得上） 相同。
**但重建那一侧用的是同一段加减代码**，已核实：

```c
this_cpu_add(e->v[gc][i], a.v->d[i]);        // disk_accounting.h:208
```

**运行时与 GC 重建走的是这同一行，只差 `gc` 这个下标**；
上游的 `__trigger_extent()` 也只靠一个 `bool gc = flags & BTREE_TRIGGER_gc;` 分流。
`btree_gc.c` 自己的注释还写明重建侧「is not idempotant; we'll calculate the
wrong result if we run it multiple times」——**重建侧本身就是一串 `+=`**。

**后果**：它的 checker 能抓「增量应用过程出了偏差」（漏一次更新、并发丢失、崩溃后未重放），
**抓不到「加减语义本身写错了」**——某个分支符号搞反，运行时与重建会一起错到同一个值上，
`memcmp` 全绿。

**这正是 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「校验的两条路径不许共享同一段代码」
要拦的那个失效，而它在一个真实文件系统里已经发生。**
本工程若照搬这个形态，I-3.1（已分配统计对得上） 会**在最需要它的那一类错误上失去判别力**，且门禁全绿。
处置见 [checks-owed.md](../checks-owed.md) C12（增量语义共用）。

**推论：这条代价的适用范围应当从「D11（索引节点要不要留消息缓冲区） 要不要做」改写成
「索引里任何一层缓冲允不允许出现非幂等增量」——那条线横跨 D8（核心索引结构） 和 D11（索引节点要不要留消息缓冲区），
而目前只有 D11（索引节点要不要留消息缓冲区） 被它拦着。**

### 已知的两条代价：代价 1 已量化，代价 2 仍未量化

1. **checker 的 I-3.1（已分配统计对得上） 在增量 Δ 形态下判别力归零——实测，不是推理。**
   [experiments.md](../experiments.md) E14（I-3.1 的判别力：幂等完整值 vs 增量 Δ）（2026-08-27，5 种子全一致）：
   同一棵树同一负载，注入四类语义 bug，

   | 缓冲条目形态 | I-3.1（已分配统计对得上） 抓到 | 账算错但 I-3.1（已分配统计对得上） 绿 |
   |---|---|---|
   | 幂等完整值 | **3/3 真 bug**（第四类「重复应用」在幂等下不是 bug，账仍等于真值） | **0** |
   | 增量 Δ | **0/4** | **4/4** |

   机制：checker 能独立重算的前提是**存在一份不经过累加逻辑的权威内容**。
   幂等完整值形态里权威是内容、账只是缓存，两条路径不共享代码；
   增量 Δ 形态里账本身就是权威内容，checker 唯一的重算办法是拿同一个累加函数
   重放同一份 Δ 日志——**它在和自己比**，连「下刷时丢一条消息」都抓不到。
   ⚠️ **「丢一条消息 / 重复应用属于应用过程偏差、增量形态仍抓得到」这个说法不成立**，
   E14（I-3.1 的判别力：幂等完整值 vs 增量 Δ） 实测两类都是 0/5，依据见 experiments.md E14（I-3.1 的判别力：幂等完整值 vs 增量 Δ） 的机制一节。
   （`.claude/singlefs-ai-sop/rules/evidence-discipline.md`：校验的两条路径不许共享同一段代码。）
   ⚠️ **记账正确性的判据不是「必须是 I-3.1（已分配统计对得上）」，是「至少存在一条与运行时不共享判定代码的独立重算路径」。**
   [invariants.md](../invariants.md) 的 I-3.5（引用区间的精确性） 注明写着「I-3.5（引用区间的精确性） 与 I-3.1（已分配统计对得上） 正交，**两条都必须有**」，
   且归属错误对 I-3.1（已分配统计对得上） **构造上不可见**；而 [checks-owed.md](../checks-owed.md) C12（增量语义共用） 记的正是 I-3.1（已分配统计对得上） 的已知盲区。
   **一个有已知盲区的检查在定义上不可能是唯一手段。** 用什么机制（标量总账 / 按快照分箱的向量等式 /
   扫描式重建）是自由的。
2. **可重建性从「可检出的不可达」退化成「检不出的陈旧」——仍是推理，未量化。**
   内部节点一旦存了别处没有第二份的数据，单节点损坏后全盘扫描重建出的树可以
   块头对、校验和对、Merkle 链对，**而内容是旧的**——
   [invariants.md](../invariants.md) 现有条目无一能检出这一类。

### 「消息做成独立的树」这条出路：已被复核否掉

该形态把消息放进一棵独立的 `pending_ops` keyspace，主张 D11（索引节点要不要留消息缓冲区） 因此不是格式级决定。
**不成立，三条依据**：

1. **对第 1 条代价零改善。** I-3.1（已分配统计对得上） 要不要把「释放 extent X」这条未下刷消息算进统计，
   与消息放在哪毫无关系——要回答就得解析消息语义。
2. **把第 2 条代价加重。** 消息块的块头说「我属于 pending_ops 树」，
   它与目标树的关联只存在于 key 编码里、没有第二份；
   丢一个 pending_ops 叶子，目标树 I-1（块自描述）.x / I-2（校验和）.x 全绿而内容是旧的，
   且**损坏发生在 A 树、症状出现在 B 树**。
   更硬的一条：I-1.3（块头树 ID 一致）在语义上被劈成两个答案——
   物理上属于 pending_ops，语义上承载别人的数据，而格式里只有一个字段。
3. **读路径从 H 变成 H + H′**，且「空树快速跳过」需要一个存在性判据；
   **那个判据一旦要持久化，D11（索引节点要不要留消息缓冲区） 就又变回格式级决定，只是换了个地方**。
