#### 確定項目 1: 整理のトリガー基準

**決定事項**: 3項目。

1. **開始: 3つの水位のいずれかを超過した時点で開始。** 完全空クラスタセグメント数（物理量、デバイス次元付き）、断片化度 `F = runs / L`（runs の現行計測条件はユニット領域空きスロットの連続ラン数、物理量、デバイス次元付き、D5 (スナップショット / 空間会計メカニズム) 確定項目 4 第10項）、回収不能バイト数（デバイス次元付き）。完全空クラスタセグメント数はレコード基準（セグメント内 64 スロットすべてに未解放の割り当てレコードが存在しない）；コードの現在の `empty_segments` は占有基準であり、レコード基準へ改訂が必要（C372 (完全空クラスタセグメント数の相反する2重定義)）、D3 (領域割り当て) 確定項目 10 ① と同文。3つの測定量はいずれも確定項目 6 により永続化が決定されており、マウント直後から読み出し可能。
2. **停止: 意図削除時点で `R` がレコード基準で全空**（`R` ローカル述語）；発行前に `R` 外の非全空セグメント（コミット内生ブロックのみを収容するセグメントは非全空とみなさない）の空洞数 ≥ `R` 内の移動対象ユニット数を判定し、不足なら発行しない；1つの意図が完了しても全体差分 `完全空クラスタセグメント数(現在) − segs0 ≥ 1` が偽であれば次を発行しない；`segs0` は意図レコードに値として書き込まれるが、観測量としてのみ機能する。
3. **`R` は意図期間中に割り当て配置先として使用不可**（フォールバックポリシーの第1項）。代償として割り当てパスに連言節「候補配置先がいかなるアクティブな整理意図の `R` 内にも含まれない」が1つ追加される；アクティブな意図数は有界（整理は一度に1バッチずつ進める）⇒ これは O(アクティブ意図数) のポイント検索であり走査ではない；意図自体は logged_ops ツリーに存在し（D8 (コアインデックス構造) 確定項目 5）、アロケータから読み取り可能。

**閾値数値はフォーマットに導入しない**: E10 (老朽化：構造的耐老朽化 vs 事後整理) を待つ；それまでは保守的なデフォルト値を取りマウント時調整可能とする。新規プールでのファイル作成のバイト列変更: 否 —— 3つの量は確定項目 6 により会計ツリー内の統計量として定められており、新規プールでのファイル作成は既にこれらを書き込んでいる；開始と停止は判定の形式であり、`segs0` は意図レコードに格納されるが新規プールでのファイル作成には整理意図が含まれない。

**射程**: 開始および停止の形式、ならびに `R` の排他性を管轄し、閾値の具体値は管轄外。意図達成後の成果の有無は第2項の `R` ローカル述語が判定し、大域差分は次を発行するか否かのみを決定する；「N 個の意図完了ごとに完全空セグメント数が厳密に増加する」検査は C140 (意図完了が空セグメントの明け渡しを意味しない) の未済に属する。`R` の外に空セグメントがない場合の割り当て配置先はリポジトリ内にいまだ条項が存在しない。「`R` を割り当て配置先として使用不可」という状態はディスク上に独立した配置先を持たず、アクティブな意図の読み取りから導出される —— C127 (ピン留め状態が割り当てレコード内に配置先を持たない) と同形であるが、本項目には入力が存在する（意図レコードがディスク上にある）。限界収益（`Δ断片化度 ÷ Δ書き込みバイト数`）という停止形態は使用不可: 分子に大域 `runs` を取ると実験軌跡上で符号がすべて不適となり、分母に「この整理バッチで書き込み済みのバイト数」を取ると履歴の関数となりディスク状態から逆算不能となり、意図レコードに書き込めば「増分の宣言」となって D8 (コアインデックス構造) 確定項目 5 の硬的要件1の逐字「意図は目標状態を宣言し、増分は決して宣言しない」に抵触する。

**根拠**:

- E93 (老朽化下での配置と断片化度): 断片化度は O(1) で増分維持可能；クラスタセグメントポリシーは整理による空セグメント供給がなければ自立不能；最大予算の整理アームにおける `runs` 軌跡は単調増加 —— したがって限界収益停止判定基準の分子はすべてのサンプリング点で符号が不適。
- 三方論証第3ラウンド（出力原文 `research/prompts/d26-r3-{sonnet,opus,local}-output.md`）: 停止判定基準の形態変更、フォールバックポリシーへの1項追加。
- ユーザー決定（3水位、成果述語、`R` 排他）、原文は変更履歴にある。
- 判定 `research/prompts/m4-gc-r1-main-verification.md` 第3節 G4: 停止を `R` ローカル述語に変更、発行前の空洞判定、成果がなければ次を発行停止（攻撃側モデルにおいて発行前判定により4つの幾何学的ライブロックが0、無成果時停止によりすべての幾何学的ライブロックが0）；C372 (完全空クラスタセグメント数の相反する2重定義) をレコード基準で決着。第7節ユーザー決定「再開: R ローカル述語 + 発行前判定 + 無成果時停止」、原文は変更履歴にある。

**未済**: C140 (意図完了が空セグメントの明け渡しを意味しない)；C146 (空セグメント不在時のフォールバックポリシーがリポジトリ全域で未定義)；C243 (停止述語の測定量に軌跡が存在したことがない)；C364 (整理意図レコードにフィールド表がない)；C372 (完全空クラスタセグメント数の相反する2重定義)；C373 (停止述語が真と判定された際のアクティブ意図削除要否の条項がない)。

#### 確定項目 3: 整理自身による空間要求の要否

**決定事項**: 3文。

1. **「空間を解放する操作自体は空間を要求しない」という要件はそのまま成立**し、D3 (領域割り当て) の原則は**再開しない** —— これを再開すればプロジェクト立ち上げ時に btrfs の病根を名指しした規律までも解体してしまう。成立しないのは「D3 (領域割り当て) 確定項目 2 + 確定項目 4 が**すでにこれを履行した**」という文であり、再開を要するのは D3 (領域割り当て) 確定項目 2 の「自身を解くためにどれだけ必要か」というアルゴリズムである。
2. **整理は解放パスではなく、通常の受入を通過する**；バッチの最悪占有量は「コミット済み予約」に算入される。
3. **第1版から常駐下限枠を確保する**；形態は受入の**第2連言節** `(利用可能 ≥ 要求) ∧ (完全空クラスタセグメント数 ≥ N₀)` とする。**下限枠は不等式のいずれの項にも算入できない** —— スカラーではなく**形状**を制約するためである。`N₀` は**ラチェットを発散させない最小値**を取り、判定基準は「十分であればよい」ではなく「小さければ小さいほどよい」とする（理由は D3 (領域割り当て) 確定項目 13 が data / metadata の2種空間を分離せず大域統一アロケータを持つため ⇒ 「解放が空間を要求する」ことはここでは btrfs ほど致命的ではない）；数値は E10 (老朽化：構造的耐老朽化 vs 事後整理) を待つ。

新規プールでのファイル作成のバイト列変更: 否 —— 完全空クラスタセグメント数は確定項目 6 により会計ツリー内の統計量と定められており、新規プールでのファイル作成は既にこれを書き込んでいる；連言節の追加は受入判定の形式であり、書き出されるバイト列を変更しない。

**射程**: 回収の系列分離要否および選定メカニズムを管轄し、ディスク FTL のテスト方法（未確定項目 8）、ディスク委譲系列移行時に脚1のどの作業を停止するか（未確定項目 9）、feature bit の階層およびディスク発行コマンド（未確定項目 10）は管轄外。**D10 (ランダム書き込み / 断片化の真の回答) の候補 C とは無関係**: 候補 C は逐字で「NVMe FDP / ZNS がデータ配置と GC 責任をホストに委譲する」であり、確定項目 7 の「ディスクに委譲」は方向が逆 —— 回収はディスク自身の FTL に留まり、ホストは行わない；FDP / ZNS は「存在すれば利用する加速」のままであり一字も変更しない。ディスク委譲系列は `crates/` 内に存在しない；自前系列には計算のみを行う3つのモジュール（`crates/singlefs-core/src/logged_operations.rs` 意図エントリフォーマット、`region_scan.rs` 領域スキャン、`compaction_plan.rs` セグメント選定と計画）が存在するのみで、整理のトリガー、パブリッシュエントリポイント、データ移動コードは存在しない。`grep -rln "整理" crates --include=*.rs` は 11 ファイルにヒットし、上記3モジュールとそのテストケース2件、`block_device.rs` のコメント1行、`crates/singlefs-format/src/lib.rs` の logged_ops 定数ドキュメント4件を除くと: `crates/singlefs-core/src/system_configuration.rs` の水位定数 `COMPACTION_WATERMARK_COUNT`、`COMPACTION_WATERMARK_BUILT_IN_DEFAULT`（「整理低水位 / 高水位 / 停止線の3本」、第1版は常に 0 = 組み込みデフォルト使用、24 バイトの 0 を書き込み）およびフィールド表コメント、`crates/singlefs-core/src/recovery.rs` のコメント1行、`crates/singlefs-harness/src/mount_transparency.rs` および `crates/singlefs-harness/tests/mount_transparency_judged_field_by_field_after_a_writable_mount.rs` が水位の組み込みデフォルト 0 を検査するのみ、`crates/singlefs-core/src/allocator.rs` の `reclaim_released_up_to` は解放済み配置先を再割り当て可能となった後に空きプールに戻すのみで生存データを移動しない、ブロックデバイストレイトに `discard_at` があるが（`crates/singlefs-core/src/block_device.rs`）プロダクトパスからの呼び出し元は不在（`discard_at(` は `block_device.rs` 単体テスト、harness のレコーダおよび故障注入デバイス転送でのみヒット）；discard 発行タイミングは未確定項目 9「discard のタイミング」節を参照。

#### 確定項目 11: 断片化の回答の所在 —— 2本の脚の重畳、デバイスインターフェースは加速へ格下げ

**決定事項**: **長期運用で蓄積する断片化は本プロジェクト自身が解決し、デバイスインターフェースに賭けない。** 2本の脚は**重畳**であり、二者択一ではない:

| 脚 | 正体 | フォーマット級か？ |
|---|---|---|
| **一: 事後整理** | 常駐・自動・ユーザーが意識不要のバックグラウンド整理、および本プロジェクト独自の配置・回収層；回収側は2系列に分岐（確定項目 7） | 否 —— `.claude/rules/fs-design.md` スロット3（バックグラウンド、再開可能、非決定パス、戒律なし）に属する |
| **二: 構造的耐老朽化** | インデックス構造自体が老朽化後も走査局所性を維持し、根本から断片化発生を抑制 | フォーマットに導入しないと決定（確定項目 4）⇒ D8 (コアインデックス構造) のノードフォーマット凍結を阻止しない |

**NVMe FDP / ZNS は「存在すれば利用する加速」に格下げし、回答そのものとはしない**: 断片化の回答をデバイスインターフェースに賭けるのは信頼性に欠ける —— FDP / ZNS 非対応デバイス上では回答が存在しないことと同義であり、D12 (ターゲットメディア) はメディア種類の事前上限設定を否定済み ⇒ それらはコーナーケースではなく主流メディアである。**重畳は現行の決定事項であり最終形態ではない**: 2本の脚のうち1本が格下げされる可能性はあるが、判定基準は E10 (老朽化：構造的耐老朽化 vs 事後整理) が規定する基準（「③ ②のレベルに達した場合、常駐バックグラウンド整理はコミットメントから最適化へ格下げ可能」）のみを用い、**別基準の設立は認めない**；それまでは両方を実施する。新規プールでのファイル作成のバイト列変更: 否 —— 2本の脚はいずれもバックグラウンドおよび配置ポリシーであり、新規プールでのファイル作成はこれらを実行しない。

**根拠**:

#### 確定項目 12: 脚1の形態は3つの確定済み規律により拘束

**決定事項**: 脚1の形態はオープンな問題ではなく、3つの確定済み規律を合わせることで完全に定まる:

| 制約 | 出典 |
|---|---|
| 整理はスロット3に属し、**戒律なし** —— 走査可能、遅延許容、即時判定に一切関与しない | `.claude/rules/fs-design.md` 3スロット規律、逐字で「スナップショット破棄、整理、scrub」を指定 |
| 非有界重労働は「意図書き込み → バッチ分割 → 再開可能」に従う | 同一スロット；C2 (非有界操作の単一トランザクション化) が担保 |
| 移動ユニットは「オブジェクト全体のグループ再配置」であり、単一ストライプではない | D2 (RAID ストライピングポリシー) 確定項目 8 の計測条件を直接再利用可能 |

**整理とリバランスは別作業であり統合しない**: 整理は断片化を管理し、リバランスはディスク間平準化を管理する（D2 (RAID ストライピングポリシー) に明記）。新規プールでのファイル作成のバイト列変更: 否 —— 3項目はいずれも既存規律の再利用であり、ディスク上の新規フィールドを追加しない。

**射程**: 脚1全体の形態枠組みを管轄し、各スロットの具体条項は管轄外 —— トリガーは確定項目 1、トランザクション形態は確定項目 2、受入は確定項目 3、会計相互作用および領域スキャン・セグメント選定解釈は確定項目 5、観測点は確定項目 6、回収系列分離は確定項目 7。スロット3の戒律なしは整理というバックグラウンドパスのみをカバーする；ある測定量が実行時決定パスへ引きずり込まれた場合（確定項目 3 が完全空クラスタセグメント数を引きずり込んだのが一例）、本免除は享受できなくなる。

**根拠**:

- E74 (割り当てレコードのエントリ数と整理コスト): 整理コストはディスク容量に連動しないが、コピーオンライト増幅率は配置先クラスタリング次第で370倍の差 —— 「移動ユニットはオブジェクト全体のグループ再配置」という再利用計測条件がこのスロットを支える。
- E93 (老朽化下での配置と断片化度): 整理は予算に伴い継続的に低下し飽和しないことから、一回限りのツールではなく常駐バックグラウンドタスクとしての実装を支持。
- ユーザー決定（脚1の形態は再決定不要）、原文は変更履歴にある。

**未済**: C2 (非有界操作の単一トランザクション化)。

#### 確定項目 13: バックグラウンドタスク計算の配置場所・有効化方法・リズム

**決定事項**: 7項目。

1. **計算の配置場所**: デフォルトは CPU。マウントパラメータ `background_compute`（`cpu` または `gpu`、デフォルト `cpu`；CLI では `--background-compute=gpu`）で GPU を選択。このマウントパラメータ一組（本項と第2・3項）は一つだけで全バックグラウンドタスクを管轄し、タスクごとには設けない：`gpu` にすると GPU パスを持つバックグラウンドタスク（GC 移動、パッキング移転、今後 GPU パスを持つ他のバックグラウンドタスク）はすべて GPU で計算し、GPU パスを持たないものは従来どおり CPU で計算する。メモリ内でのみ生存: システム構成に書き込まず、feature bit を消費せず（D24 (バックグラウンド重負荷の GPU オフロード可否) 確定項目 2 第1項）、マウントごとに個別に指定。マウントセッションの制御インターフェース経由でマウント中も切り替え可能（一度に全バックグラウンドタスクを切り替える）、次バッチから適用；1バッチの途中で変更しない（`.claude/rules/fs-design.md`「分岐変数は操作途中で変更不可」）。
2. **使用するカード**: マウントパラメータ `background_gpu_devices` はカードのリスト（複数指定可）；未指定時はホスト上の全 GPU カードを使用。
3. **VRAM 上限**: マウントパラメータ `background_gpu_memory_limit` は単位付きバイト数値のリストであり、順序どおりカード1枚に1つ割り当て、参加するカードと1対1に対応させる（`background_gpu_devices` 指定時はそのリストに対応、未指定時はホスト全カードリストに対応）、パディングなし: `background_gpu_devices` で3枚指定した場合、`background_gpu_memory_limit` は未指定とするか正確に3個与える必要があり、1個のみではエラー；GPU モード時、全バックグラウンドタスクがそのカードで合わせて占有する VRAM は指定値を超えない。未指定時は上限なし、バックグラウンドタスク実行時にカード上で利用可能な全容量を使用。GPU モードは連続複数バッチの計算をまとめて GPU に委託し、まとめる規模は本設定に従う。
4. **設定不備および GPU 使用不能時はエラー、フォールバックなし**: マウントまたは切り替え時点において、`background_gpu_memory_limit` の個数が参加カード数と不一致、いずれかの数値がカードの VRAM 総量を超過、GPU 不在、ドライバ不一致、指定カードが存在しない場合はマウント（または切り替え）を拒否しエラー；マウント中に GPU エラーが発生した場合、計算中のバッチは破棄（意図はディスク上に残留、目標状態は単調、確定項目 2）、そのバックグラウンドタスクは停止しエラーを報告し CPU に戻さない；復旧には手動で `cpu` に切り替えるか GPU 修復後に再切り替えが必要。
5. **開始タイミング**: パブリッシュごとに確定項目 1 の3水位を検査；さらに定期フォールバックタイマーにより一定時間ごとに再検査、間隔はマウントパラメータ。両モードで同一の開始規則に従う。
6. **開始後のリズム**: GC が占有するディスク書き込み帯域に上限を設ける（マウントパラメータ）；フォアグラウンドで待機中の fsync が存在する場合は次バッチを発行しない。
7. **採算性は節約された CPU 時間で評価**: GPU モードの目的はホスト CPU 時間の占有を減らすことであり、データ量が大きいときに速くなるのは副産物にすぎない。収益はバックグラウンドタスクがホスト CPU 時間を節約できた量（CPU モードでのその CPU 時間から GPU モードでのその CPU 時間を差し引いたもの、後者にはデータ準備・投入・結果待機・サンプリング照合を含む）；壁時計時間が CPU モードと同等であっても実施；D24 (バックグラウンド重負荷の GPU オフロード可否) 確定項目 3 の壁時計比率判定基準は本項目が管轄するバックグラウンドタスクには適用しない。実装後に比較実験を実施: 同一ワークロード・同一プールで CPU モードと GPU モードを走行させ、双方の GC 壁時計時間、ホスト CPU 時間、フォアグラウンド fsync レイテンシを報告し、複数ディスク容量階層で実行して容量に応じた収益変化を検証。

GPU パスと CPU パスは2つの実装に分かれ、GPU の結果はサンプリングして CPU で照合（D24 (バックグラウンド重負荷の GPU オフロード可否) 確定項目 2 第3項）。GPU パスはデフォルトで WGSL として記述し `wgpu` 経由で起動（checker 層のクラッシュ判定器ですでに使用実績あり、`Cargo.lock` には `wgpu 30.0.1` が含まれ追加の CUDA ツールチェーンは不要）；より優れた手法があれば設計ラウンドでの比較後に交換可能。新規プールでのファイル作成のバイト列変更: 否 —— 7項目はすべてマウントパラメータおよびバックグラウンド動作であり、ディスクには書き込まない。

**射程**: スイッチ、カード選定、VRAM、エラー処理、開始およびリズムの形式を管轄。第1〜4項と第7項は GPU パスを持つ全バックグラウンドタスクを管轄し、現時点では GC 移動とパッキング移転；第5・6項は GC のみを管轄し、パッキングの開始と速度制限は D27 (小データパッキングコンテナ) 確定項目 6 にある。D24 (バックグラウンド重負荷の GPU オフロード可否) の三候補は引き続き保留（D24 (バックグラウンド重負荷の GPU オフロード可否) 確定項目 1）で、再開して GPU パスを持ったときは同じスイッチに入り、採算をどの判定基準で判じるかは再開時に決める。以下は管轄外: GPU 上で GC のどのフェーズを計算するか（マイルストーン4設計ラウンドで決定）、パッキングのどのフェーズを計算するか（マイルストーン7設計ラウンドで決定）；定期フォールバック間隔、書き込み帯域上限のデフォルト値（C412 (整理の壁時計コスト未測定) および E10 (老朽化：構造的耐老朽化 vs 事後整理) を待つ）。⚠️ 第4項の稼働中エラーによる GC 停止: 停止中は空間が減少するのみで増加しないが、D3 (領域割り当て) 確定項目 14「バックグラウンド整理は常駐・自動」との整合的な解釈は、これがユーザーが明示的に GPU を有効化した場合にのみ発生し、デフォルトの `cpu` は影響を受けないという点にある。

**根拠**: 実験なし: 本項目はスイッチおよび運用ポリシーに関するユーザー決定であり、数値はここには含まれない（C412 (整理の壁時計コスト未測定) および E10 (老朽化：構造的耐老朽化 vs 事後整理) を待つ）。ユーザー決定（2026-10-19 ポップアップ4問および追加の回答；2026-10-20 パラメータを全バックグラウンドタスクで統一、収益の口径を全バックグラウンドタスクに拡張）、原文は変更履歴にある。

**未済**: C412 (整理の壁時計コスト未測定)。

#### 未確定項目 8: 回収の2系列間の切り替え判定基準

**設問**: ディスク FTL の GC サポートのテスト方法、mkfs 時かマウント時か、テスト結果をディスクに保存するか否か。ユーザーの回答における判定基準入力は「テストでディスクのftlがgcをサポートしていると判明した場合」であり、何をいつテストするかは未指定、当面論証しないと決定（原文と全回答は変更履歴にある）。

**本分岐は `.claude/rules/fs-design.md`「5つの硬的要件」に準拠**: 当該節の要件は順に、切り替え判定基準は明示的・計算可能・文書化必須；各分岐はテストで強制突入可能必須；各分岐はクラッシュポイント再生を含め単独検証必須；分岐は観測可能必須；分岐変数は操作途中で変更不可。⇒「ディスク FTL の GC サポート有無」というテスト結果は1回の操作途中で変化してはならない。

**先行実装系列は確定済み**: 自前系列を先行させ、ディスク委譲系列は後から追加（確定項目 7）；本項目はディスク委譲系列が接続される前に回答を要する。

**第1期**: D12 (ターゲットメディア) 確定項目 5 は最初のレイアウト系列を標準 SSD と定め、計測条件は逐字で「FDP / ZNS / 特殊なデバイスインターフェースを要求しない」；標準 SSD がどちらの系列に属するかは本項目に依存する。

#### 未確定項目 9: 回収の2系列の射程

#### 未確定項目 10: 回収系列の feature bit レベルおよびデバイスへの発行コマンド

**設问**: 回収系列の feature bit に incompat（非認識時マウント拒絶）、compat_ro（非認識時リードオンリーマウント）、compat（非認識時自由マウント）のどの階層を用いるか、別ビットを確保するか D12 (ターゲットメディア) 確定項目 1 のレイアウトビットに追従するか；ディスクに発行するコマンドは何か。ユーザーは当面論証しないと決定。

**階層の判定方法**: `.claude/rules/fs-design.md`「フォーマット分岐の価値は『誤用』を『マウント不可』に変えられるかにある」。メイン agent が提起した異議（ユーザーはこれに基づき「feature bit、階層は未定のまま保留」を選択）: 両系列がディスク上に書き出すバイト列が同一でホストによるデータ移動と discard 発行の有無のみが異なる場合、本ビットを認識しない実装も本来そのディスクを正常に読み書き可能であり、incompat でブロックしても安全性向上は得られず compat を用いるべきである；ディスク委譲系列により自前系列が依存する前提条件（例えば確定項目 3 の受入に必要な完全空クラスタセグメント）が欠落する場合、本ビットを認識しない実装が自前系列の前提で書き込むと障害を招くため compat_ro または incompat の出番となる。⇒ 階層は未確定項目 9 の回答に追従する。feature bit は mkfs 時に固定され、未確定項目 8 で引用した「分岐変数は操作途中で変更不可」を満たす。

**実装の形態**: システム構成ブートストラップヘッダには incompat / compat_ro / compat の3つのビットマップが各 256 ビット存在し（[layout/01-first-txn.md](../layout/01-first-txn.md)「一、mkfs が既に植え付けたもの」）、第1版は incompat ビット 0 = 1（最初の純 SSD レイアウト系列）のみ；`crates/singlefs-core/src/system_configuration.rs` は incompat ビットマップのみを検査（`incompat_bits_are_mountable`）、`grep -rn "compat_ro" crates --include=*.rs` はゼロヒット。メイン agent の解釈（ユーザー未指定、決定事項ではない）: ディスク発行コマンドには少なくとも discard が含まれる、理由は未確定項目 9「discard のタイミング」節を参照。
