## D9 暗号化 —— 確定

[中文](09-加密.md) · [English](09-encryption.en.md) · **日本語**

D9 (暗号化) は本プロジェクトの暗号化を管轄する：ボリューム全体 AEAD の方針と平文免責範囲、暗号化のために day-1 で予約すべきフォーマット上のビット、MAC / nonce / アルゴリズム / AAD の形態、選定に依存しない 3 つの必須要件、鍵を持たない側ができること、システム構成とルートの認証およびロールバック保護、暗号化を最初の実行可能バージョンに含めるかどうか。暗号化はオプションの演算であり、オプションのフォーマットではない（`.claude/rules/fs-design.md`「暗号化はオプションの演算であり、オプションのフォーマットではない」）：暗号化が無効な場合、MAC と AAD は計算されず、暗号化のために予約されたビットはすべてのボリュームでそのまま保持され、全ゼロとされ、他のフィールドに流用されることはない。管轄外の事項：各フィールドの幅とオフセット——ポインタは D19 (ブロックポインタ構造と幅予算) 確定項目 11 に属し、ルートレコードは D22 (ユニット原子性の合成手法) 確定項目 7 に属し、システム構成は D22 (ユニット原子性の合成手法) 確定項目 9 に属し、journal レコードヘッダは D23 (ジャーナルの役割と形式) 確定項目 4 に属し、ユニットヘッダ内の nonce / MAC / アルゴリズムタイプの予約ビットは D18 (ブロックに含める情報) 確定項目 14 / 確定項目 16 に属する；ユニットタイプタグの定義域は D18 (ブロックに含める情報) 確定項目 11 の登録表に属する。調査は [prior-art.md](../prior-art.md) 第 6 節を参照。現在 AEAD の暗号化・復号演算はない。書き込み経路は非暗号化形式で予約フィールドを書き、読み取り経路はその合法値を検査し、暗号化有効の構成を拒否する。予約フィールドと値の検査は暗号化の実装を意味しない。

#### 確定項目 1：ポインタに追加の暗号文非鍵チェックサムを保持するか

**決定**：ポインタには 2 つの完全性フィールドを設ける：MAC（鍵が必要、認証）+ 暗号文チェックサム（鍵不要、破損検査）。すべての読み出しパスで暗号文チェックサムを使用し、scrub だけが使用するのではない。

**射程**：鍵なし側は検出のみを行い、どれが良いコピーかの判定は行わない——攻撃者は自己整合的なチェックサムを持つブロックを作成して鍵を持たない側を騙すことができる（確定項目 6 の命題 1 が鍵なし scrub において成立しないのは、同じ事象である）。代償としてポインタが肥大化する。暗号文チェックサムの配置先と幅は D19 (ブロックポインタ構造と幅予算) 確定項目 4（位置エントリ内の 4 バイト）に属する；その判定可能な形式は I-6.8 (暗号文チェックサム一致) であり、鍵は不要である。

**根拠**：

- 実験なし：このフィールドを設けるかどうかは能力のトレードオフであり、測定可能なコストはない——鍵を持たない側は scrub のみを行い（確定項目 5）、破損の検出と不正ブロックの報告は完全にこの鍵不要フィールドに依存している；それがなければアンロック前は完全にブラインドとなる。
- ZFS と同一の形態：MAC はチェックサム空間の半分を占め、もう半分は鍵がロードされているかどうかにかかわらずディスク上の破損検査に使用される（`include/sys/spa.h` の「MAC occupies half」のコメント、原文は変更履歴にある）。

**未済の検査**：なし（I-6.8 (暗号文チェックサム一致) の checker 状態は [invariants/08-加密不变量.md](../../../crates/singlefs-checker/invariants/08-加密不变量.md) に記載、暗号化は第 1 バージョンには含めない）。

#### 確定項目 2：MAC 長：80 ビット切り捨て vs 128 ビット

**決定**：切り捨てず、128 ビット（16 バイト）を完全に確保する。

**射程**：MAC の責任は認証のみとなる——鍵なしでの破損検出は確定項目 1 の暗号文チェックサムが独立して担っており、切り捨てによって節約される 8 バイトは何の検出能力ももたらさない。すべてのポインタ内の MAC および自己証明ユニット自身の MAC（確定項目 12 第 1 項）を管轄する。確定項目 13 必須要件 3（MAC 切り捨て時に読み出し再試行上限をハードコードする）はしたがって荷重を負わない；「MAC 長は読み出し再試行上限に依存する」という判定基準は成立せず、C3 (読み出し再試行にハード上限なし) は消し込み済みであり、その理由は前提の計測条件が誤っていたためであり、阻止されたからではない。切り捨ての危険性を引用する際に Ferguson 2005 の短いタグの惨劇を Poly1305 へ外挿することは禁止される：その攻撃の根本原因は GF(2¹²⁸) 上の GHASH の線形構造にあり、Poly1305 は素体 2¹³⁰−5 上にあり、マスクは XOR ではなく加算剰余であるため、その bit-forcing パスに対応するものはない（この記述自体は推論であり、免疫があると明記された権威ある情報源は見当たらない）。

**根拠**：

- 実験なし：値は標準規格とカーネルインターフェースのハードな制約によって決まり、比較すべき測定可能なコストは存在しない。
- 三者検証の一致（経緯は変更履歴にある）。
- SP 800-38D §5.2.1.2 の逐語「t may be any one of the following five values: 128, 120, 112, 104, or 96」、80 はその中にない；Linux の `chachapoly_setauthsize` は authsize がちょうど 16 バイトであることを要求し、`crypto_gcm_check_authsize` は 10 バイトを拒絶する（[prior-art.md](../prior-art.md) 6.7）。
- RFC 8439 §4「Tag truncation MUST NOT be done.」：分析を欠く保守的な禁止であり、広く施行されているわけではない（BoringSSL、OpenSSL は 1 バイトまで許可）ため、中程度の強度の傍証としてのみ扱う；経緯は変更履歴にある。
- 要求をまたぐ偽造試行上限を固定している現役の実装は皆無（dm-integrity、dm-verity、bcachefs を現時点で調査、カーネル全体で `MaxInvalids` のヒットは 0）；`MaxInvalids` は SP 800-38B に由来し、38D 付録 C のその列はすべての復号呼び出しをカウントしている。
- 80 ビットを支持する唯一の現役データポイントは bcachefs の既定値である：それは `bch_extent_crc64` ビットフィールドから絞り出された余白であり、カーネル AEAD インターフェースを迂回して手動で切り捨てることで実現されているが、それ自身のメタデータは恒常的に 128 ビットを使用している。
- Poly1305 を切り捨てる危険性は RFC の禁止条項とは独立している：Wegman-Carter 型 MAC の偽造境界は `fℓ/2^τ` である；Poly1305 において 1 回の偽造が成功すると同様に r が暴露される（DJB *Cryptography in NaCl* §9 逐語）；安全な切り捨てには 2 段階のハッシュまたは追加のサブキーが必要だが、Poly1305 にはそのどちらもない。
- OpenZFS は同じ衝突に直面して完全な 128 ビット MAC を保持し（`include/sys/zio.h` の `ZIO_DATA_MAC_LEN 16`）、「暗号化ブロックは最大 2 レプリカ」という代償を進んで支払っている。

**未済の検査**：なし。

#### 確定項目 3：CPU 機能に基づき実行時に選択、フォーマットには固定しない

**決定**：ディスク上にアルゴリズムタイプを記録し、実行時に AES-NI の有無に応じて既定値を選択する。ChaCha20-Poly1305 と AES-256-GCM の両方のアルゴリズムを必ず実装する。アルゴリズムタイプフィールドの登録表：0 未暗号化、1 ChaCha20-Poly1305、2 AES-256-GCM；新しいアルゴリズムはコードを再利用せず追記のみとし、読者が未登録のコードに遭遇した場合は明示的に失敗させ、他のアルゴリズムでの検証は行わない（`.claude/rules/fs-design.md`「各書き込みのアルゴリズムタイプフィールド」のセル；D22 (ユニット原子性の合成手法) 確定項目 17 が登録場所をここに向けている）。暗号化パスは並列化可能でなければならない。

**射程**：決定したのは既定値の選択方法であり、フォーマット側の新規追加はない。並列化の条項について：AES-NI がない場合、AES-256-GCM のシングルコアスループットは 244.74 MiB/s にすぎず、現代のいかなる NVMe のシーケンシャル帯域幅よりも低い（ローカル nvme0n1 3.6 T、そのシーケンシャル帯域幅は個別実測していない——このステップはメディアカテゴリから推定）。シングルコア暗号化は flush のクリティカルパスではなく、クリティカルパスは flush 時のツリー挿入 I/O である（E17 (ライトバッファマージ上限) 末尾の比較セット修正）。暗号化パスの並列化と D13 (検証ルート) 確定項目 2（まず直列コミット）をどう重ね合わせるかは評価されていない。`crates/` の読み出しパスはアルゴリズムタイプの 1 バイトをスキップしており（`PointerHead::read_from`、`JournalRecord::parse`、`RootRecord::parse_slot`）、「未登録のコードは明示的に失敗する」を判定するコードは存在しない。

**根拠**：

- E6 (暗号化アルゴリズム選定)：2 つの CPU 機能階層において AES と ChaCha の速度逆転があり、8 セル全走査でいずれも数倍の開きがある——一方を選んでフォーマットに固定すると、別の種類のマシンで必ず誤った選択となる；AES-NI をマスクした場合、AES のシングルコアスループットは NVMe シーケンシャル帯域幅を下回るため、暗号化パスは並列化可能でなければならない。
- 登録表：ユーザー決定、原文は変更履歴にある。

**未済の検査**：C405 (暗号化の並列化要求と直列先行コミットを誰も突き合わせていない)：並列化と直列コミット優先の重ね合わせ；C406 (読み取り側がアルゴリズム種別と圧縮の 3 バイトを判定しない)：ポインタ先頭の 3 つの判定はすでに `crates/singlefs-core/src/pointer.rs` の `PointerHeadAsRead::judged` に反映済み；journal レコードヘッダおよびルートレコードのオフセット 437 の 2 箇所のアルゴリズムタイプバイトにおける「未登録コードの明示的失敗」の判定が依然として未済。

#### 確定項目 4：nonce はエクステントごとに保持し、オンザフライ計算しない

**決定**：ポインタ先頭に論理エクステントごとに 96 ビットの nonce を 1 つ保持する。`bversion` からオンザフライ計算する bcachefs のような形態は採用しない。

**射程**：

- 獲得するもの：① 復号が**他のいかなる場所**のフィールドが正しいままであることにも依存しない ⇒ ユニットの自己完結性（D20 (荷重受け面: ユニットの原子性と自己完結性)）が暗号化が有効な場合にも成立する——この記述は D18 (ブロックに含める情報) 確定項目 14 により文字通りに成立する：完全な 96 ビット nonce のもう 1 つのコピーがユニット平文ヘッダに存在し、ポインタ内のコピーも保持される；② I-6.1 (nonce 再利用なし) が**イメージに対して判定可能**な性質となる——すべてのポインタ先頭を 1 回走査すれば十分である。支払う代償：**12 バイト / 論理エクステント**；暗号化が無効な場合は予約ビットとなる（D19 (ブロックポインタ構造と幅予算) 確定項目 3）。
- エクステント分割のセルは解決していない：確定項目 12 第 2 項は依然として必須である——**もし**分割が有効化された場合、分割後の N 個のサブエクステントは**同一の暗号文、同一の nonce、同一の MAC を共有**し、保持された nonce は「元のエクステントのもの」であり、サブエクステントはオフセットによってそれを取り戻す。**nonce を保持することは各サブエクステントがそれぞれ 1 つずつ保持することを意味しない。**第 1 バージョンにはこのセルはない：分割は予約機能であり第 1 バージョンでは無効化され、`extent_off` は恒常的に 0、各ユニットは恒常的に 1 つの nonce と MAC を持つ（D4 (チェックサム配置位置) 確定項目 7）。

**根拠**：

- 実験なし：保持するか計算するかは自己完結性のポリシーであり、測定可能なコストはない——nonce は書き出された瞬間に固定されるべきものである；オンザフライ計算は「この暗号文にどの nonce を対応させるべきか」を推論に変え、推論の各入力（bversion、per-crc オフセット、エクステント分割履歴）はいずれも後から変更されうる値であるが、保持しておけば 1 回の書き込み以降は読み取り専用となる。並列する第 2 の根拠は `.claude/rules/fs-design.md` の**領域節約のために自己完結性を犠牲にしない**原則である。
- ユーザー決定、原文は変更履歴にある。

**未済の検査**：C184 (再構築パスが完全な nonce を取得できない)：スキャン再構築パスにおいて nonce 取得元にアクセス可能であることのゲート比較。

#### 確定項目 5：鍵なしメンテナスは scrub のみ実施、安全性を優先

**決定**：**暗号化が有効な場合、鍵を持たない側は読み取り専用・検出専用とし、移動、退避、回収は行わない。**「ブロックの物理アドレスの権威ある記録場所」は**暗号化構造内に残す**（ポインタ内の位置エントリ、D19 (ブロックポインタ構造と幅予算) 確定項目 4）。平文マッピング層は設行せず、平文逆引きインデックスも設けない。鍵を持たない側ができることは破損の検出と不正ブロックの報告である；何も移動させることはできず、断片化解消と障害ディスクからの退避には依然として鍵が必要である。

**射程**：

- **認識した上で受容する代償**：D3 (領域割り当て) の「常駐・自動・ユーザーが意識する必要のないバックグラウンド整理」という確約は**暗号化が有効な場合には成立しない**。ディスクロック中は整理と退避がすべて停止し、ほぼ満杯のボリュームでのディスク交換や縮小は行えない。
- 他の 2 つの候補は不採用：「インデックス内部ノードを平文で残す」（移動・退避は可能だが、内部ノードは区切りキーを持ち、dirent ツリーの区切りキーはファイル名そのものである——漏洩面は ZFS よりはるかに大きい。ZFS の間接ブロックは純粋なポインタ配列でありキーを持たない）、「逆引きインデックス + bucket コードを平文で残す」（移動は可能だが、物理レイアウトと参照関係が漏洩する）。撤回前に採用されていた第 3 の候補とその経緯は変更履歴にある。
- 鍵なし scrub がどの構造を読み出すべきかについて、リポジトリ全体に目録が存在しない（C303 (D2 境界 ③ の根拠が D9 確定項目 7 の撤回で失効した)）。

**根拠**：

- 実験なし：トレードオフの好みが変わったのではなく、**「移動可能」とする側が到達不能であると証明された**ためであり、比較すべき測定可能なコストはない。4 つの確定条項が同時に真となることはできない：1 つのユニットを移動することは新しいストライプを発行することであり（D2 (RAID ストライプ方針) 確定項目 6 逐語「`w ≥ 2` はハードな下限（冗長性ゼロのストライプの発行は禁止）」）、新しいストライプの各セルにはメンバーレコードが必要であり（D2 (RAID ストライプ方針) 確定項目 12）、メンバー表は逐語「**ユニットのペイロード内に存在しなければならない**」とされ、ペイロードは暗号文である ⇒ **鍵なし側はメンバー表を書き込めない** ⇒ 移動は不可能；`w ≥ 2` はハードな下限である ⇒ **任意の**プールに対して成立する。平文マッピング層は「移動可能」のために支払う代償であり（D3 (領域割り当て) 確定項目 16）、目的が失われた以上、代償を支払う必要はない。
- ボトルネックの正確な位置は MAC の位置ではなく、**「ブロックの物理アドレスの権威ある記録場所が暗号文の中にあるかどうか」**である：MAC をブロック自身の平文ヘッダへ移動しても（bcachefs が btree ノードに対して行っていること、`extents_format.h` のコメント行で直截に `/* Btree pointers don't carry around checksums: */` と記述）、1 セル緩むだけにすぎない——メタデータブロックはそのまま移動できる（MAC がブロック自身のバイトをカバーし、nonce が物理位置から導出されないため）が、親ポインタ内の**アドレスフィールド**は依然として変更する必要があり、親ノードのペイロードは暗号文である。
- 三者論証：確定項目 9 の 6 ラウンドにわたる三者論証が「移動可能」側の形態を一つずつ論破した（`research/prompts/d9-item9-r1-*` から `d9-item9-r6-*`、`records/2026-09-06-D9项9三轮对抗.md`）；ユーザー決定、原文は変更履歴にある。
- bcachefs の「鍵なしバックグラウンド整理の麻痺」は推論であり、引用ではない：一次資料に散文で明言されたものはなく、推論は 5 つの検証可能な事実に基づいている（検索範囲と 5 つの事実は変更履歴にある）。

**未済の検査**：C303 (D2 境界 ③ の根拠が D9 確定項目 7 の撤回で失効した)：鍵なし scrub が読み出すべき全構造のリストアップ；C23 (鍵なし scrub が生きたスロットと古いスロットを区別できない)：整合性のあるユニットを走査した際にアクティブかどうか判定できない；C32 (鍵なし側がバイトを書き出せるかにゲートがない)：「読み取り専用」に何らゲートがない；C33 (scrub が検出した後の処理に条項がない)：報告がどこに記録され、アンロック後に誰が消費するか；C134 (scrub 水位自身に配置先も保護もない)；C136 (鍵なしでどの不変条件を検証できるか誰も標示していない)；C166 (平文側撤廃後にフォーマット予約領域も回収すべきか否か)；C167 (平文マッピング層参照の全リポジトリリスキャンが未実施)。

#### 確定項目 6：AEAD の関連データは論理 ID に紐付け、物理位置は一切含めない

**実装範囲**：`crates/singlefs-core/src/unit.rs` は論理同一性の五項目をフォーマット準備として符号化するが、AEAD/AAD 認証計算はない。`crates/singlefs-core/src/recovery.rs` は暗号化有効のシステム構成を拒否する。暗号化無効時には AAD を計算しないため、同一性フィールドや CRC 検査の存在を五項目の MAC 認証済みと記述してはならない。初版の範囲は確定項目 10 のフォーマット予約のみ。

**決定**：**AAD = `(ユニットタイプタグ, ツリー ID, オブジェクト ID, オブジェクト出生世代, アンカーオフセット)` の固定長・固定順序の標準エンコーディングとする。物理配置先、デバイス ID、およびいかなる平文側フィールドも一切含めない。**AAD は暗号化が有効な場合にのみ計算される演算であり、暗号化が無効な場合は計算されない（`.claude/rules/fs-design.md`「暗号化はオプションの演算であり、オプションのフォーマットではない」）。各フィールドの期待値がどこから来るかは確定項目 16 に属する。

| フィールド | なぜ含めなければならないか | 誰が期待値を提供するか |
|---|---|---|
| **ユニットタイプタグ**（値域は D18 (ブロックに含める情報) 確定項目 11 の登録表——データエクステント = コード 1、btree ノードおよび会計ツリーノード = コード 2、パッキングレコードユニット = コード 3、ルートレコード = コード 16；AAD 標準エンコーディングの第 1 バイトとなる） | ユニットクラスごとにフィールドセットが異なる。ドメイン分離がない場合、2 種類のユニットの AAD が同一のバイト列にシリアライズされうる ⇒ **型の混同が正当な MAC 通過となってしまう** | 読者の探索パス |
| **ツリー ID** | D8 (コアインデックス構造) はマルチキー空間であり、オブジェクト番号は異なるキー空間で個別に番号付けされ、**必ず衝突する** | 探索パス |
| **オブジェクト ID (inode)** | 同一ツリー内のファイル A の offset 0 とファイル B の offset 0 はオブジェクト番号を除いて完全に同一。ポインタを誤ったオブジェクトにぶら下げると ⇒ A を読んで B が得られる | 探索パス |
| **オブジェクト出生世代 (inode generation)** | 5 つ組 / AAD の day-1 契約に従って保持される（D18 (ブロックに含める情報) 確定項目 3 / 確定項目 11）。これは深層防御ではなく、一意性そのものである：D8 (コアインデックス構造) 確定項目 6 は「パブリッシュ済みの (inode 番号, オブジェクト出生世代) は再利用しない」と定めており、番号はロールバック後に設計上再発行され、AAD / nonce の 2 層で同一番号の新旧オブジェクトを分離するのはまさにこの部分である；同時にこれは I-6.1 (nonce 再利用なし) が失効した際（クラッシュウィンドウ / nonce 水位ロールバック）の第 2 のゲートでもある | 暗号文側 |
| **アンカーオフセット** = そのエクステントが最初に書き出された際のオブジェクト内開始オフセット、読者は `key.offset − ptr.extent_off` をオンザフライ計算 | 同一ファイル内の 2 つのエクステントの入れ替えは、データベースファイルや VM イメージにとって実質的な破壊となる | 探索パス + 暗号文側の `extent_off` |

AAD に絶対に含めてはならないもの、およびそれぞれがどの条項に抵触するか：

| フィールド | どの条項に抵触するか | メカニズム |
|---|---|---|
| **物理配置先 / デバイス ID** | **A7 (意味調査中) + D19 (ブロックポインタ構造と幅予算)** | D2 (RAID ストライプ方針) は「N 個のレプリカは同一の暗号文を N 回書き込み、1 つの nonce を共有する」と決定し、D19 (ブロックポインタ構造と幅予算) は「MAC は論理エクステントごとに 1 つ、配置先は物理位置ごとに 1 つ」と決定している ⇒ 配置先が AAD に入ると ⇒ N 個のレプリカで N 個の AAD になる ⇒ N 個の MAC が必要となる ⇒ D19 (ブロックポインタ構造と幅予算) のセグメント構造をその場で覆すことになる |
| **元の起点からのエクステントオフセット** | **確定項目 12 第 2 項** | **AAD のフィールド構成は day-1 の恒久的契約である**：暗号化の運用開始前に確定されなければならず、以降の変更はフォーマット破断を意味する ⇒ 判定基準は「このフィールドが将来ポインタごとに異なりうるか」によってのみ定められ、「現在どんな値であるか」で定めてはならない。そして**もし**分割が有効化された場合、N 個のサブエクステントは同一の暗号文、nonce、MAC を共有しながらこのフィールドはポインタごとに異なる ⇒ 1 つの MAC に対して N 個の AAD となる ⇒ **N−1 個のサブエクステントがすべて検証失敗する**、不一致が正常な操作の必然的結果となる ⇒ 排除。⚠️ **「第 1 バージョンでは恒常的に 0 であるため含めても無害」という再論証は禁止**（逆推レッグが名指しした罠）：恒常的に 0 であることは第 1 バージョンの実行時の事実にすぎず、フォーマット契約ではない；その理由で AAD に戻せば、分割が有効化された瞬間に即座に破綻する |
| **`locality_id`** | **D8 (コアインデックス構造) 確定項目 3 逐語**：「ヒントであり、正当性の一部ではない——誤っていてもよく、期限切れでもよい」 | 「誤っていてもよい」と宣言されたフィールドに荷重を負わせることになる；D18 (ブロックに含める情報) 確定項目 3 のブロックヘッダに `locality_id` を追加する提案をユーザー決定で却下したため、この行を維持する |
| **任意の平文側フィールド**（平文ヘッダの flags / 長さ / nonce コード、位置エントリ内の暗号文チェックサム）| 期待値ソース判定基準（確定項目 16） | 期待値が読み出される対象自身によって提供されるため、攻撃者が両側を同時に改ざん可能であり、AEAD はこれに対して保護ゼロである |
| **読者が現在位置するスナップショット ID** | COW 共有 | 1 つのブロックに N 個のスナップショットからアクセス可能な場合、読者側のスナップショットに紐付けると ⇒ そのブロックは 1 つのスナップショットでしか検証に通らなくなる（この排除自体は成立するが、スナップショット次元の欠落については射程「AAD にスナップショット次元が欠落」を参照） |
| **参照カウント / 会計量 / deadlist 所属 / 現在の txg** | D5 (スナップショット / 空間会計メカニズム) | すべて集合の属性であり、ブロックが書き直されなくても変化する ⇒ 変化するたびに再暗号化が必要となる |
| **親ノードの物理アドレス** | D18 (ブロックに含める情報) 確定項目 23 | 時系列上不可能：COW は子が先で親が後であり、子ブロックを書き込む時点ではその値はまだ存在しない |

フォーマットが day-1 で提供必須の 3 項目（1 つでも欠けると、checker は I-6.3 (MAC と暗号文の一致) および I-6.9 (暗号文一致かつ MAC 失敗時は ID 不一致と判定) を判定できない）：
① **ユニットタイプタグが権威側で明示的であること**、「どのツリーにあるか」から推論することは禁止；
② **逆引きインデックスエントリの ID 計測条件 == AAD 計測条件 == 権威ツリー key 計測条件、同一の定義であること**（3 つの計測条件は 3 つの定義を意味する）；
③ **btree ノードの論理 ID が定義されていること**——AAD のフィールド目録はデータエクステントのみをカバーしている；D18 (ブロックに含める情報) 確定項目 1 で系譜書き換え連番を行わないと定めたため、インデックスノードの AAD フィールドセットはコード 2 クラスの ID セグメント（ツリー ID + 階層 + key 区間）と揃える必要があり、C107 (インデックスノードの AAD 同一性に配置先がない) として未済。

**射程**：

- fsid は AAD には含まれず、鍵導出の入力である（確定項目 8）：ボリュームをまたぐバインドは鍵層で発生し、別のボリュームの暗号文は自ボリュームの導出鍵の下では**まったく復号できない**ため、AAD でユニットごとに不一致となるよりも早く、徹底的である；**フィールドではないため、A6 (AAD 期待値は平文側から来ない) の制約を受けない**。
- 不要だがゼロコストの 2 項目：アルゴリズムタイプ、鍵コード。含めてもよいが、「コストのない冗長性」として記録されなければならない：それらは暗号文側に存在し、攻撃者が改ざんすることはできず、誤って使用すれば必ず不一致となる。アルゴリズムタイプは最も危険なセルには届かない：フィールドが「未暗号化」とマークされている場合、読者はそもそも MAC を実行せず、AAD は MAC の内部のものである；そのセルの防衛線は I-6.4 (未暗号化ブロックなし) とシステム構成の暗号化宣言である。ユニット長は AAD に含める必要はない：AEAD 構造がすでに暗黙的にそれを認証している（`crypto/chacha20poly1305.c` の末尾で `tail.assoclen` / `tail.cryptlen` を投入）。
- **AAD にスナップショット次元が欠落**：この 5 項目はスナップショット次元に対してブラインドであり、かつ無口である——スナップショット key が不一致の際に別の書き込み可能ヘッドのデータを読み出しても MAC はすべてグリーンとなり、「スナップショット key の改ざん」はまさにチェーン B が名指しした 3 種類の実装バグの 1 つである。「読者が現在位置するスナップショット ID」を排除する根拠自体は成立する；崩れたのは「読者側スナップショットを排除 ⇒ スナップショット次元全体を AAD に含めない」という論理の飛躍である。解決策は出生スナップショットに紐付けることだけである——スナップショット次元をオンザフライ計算の nonce に畳み込むことは確定項目 4 の別の選択肢であったが、確定項目 4 はすでに「エクステントごとに保持し、オンザフライ計算しない」と決定している。対処は「決定は変更せず、欠落を記録する」とし、フィールド表は 1 回の再開の宿題を抱える（C63 (確定済み AAD がスナップショット次元に対して盲目)）。ヘッドごとに 1 つのツリーがある場合の実行可能な形態：出生 (ツリー, txg) を AAD に含め、ポインタに宣言を持たせ、読者はまず**クローン祖先表**で受入検査を行い（宣言されたツリーが祖先チェーン上にあり、かつ出生 txg ≤ 対応するクローン分岐点）、その後 MAC に進む；ポインタ内のこれら 2 つのフィールドの位置は D19 (ブロックポインタ構造と幅予算) 確定項目 7 で与えられており（出生ツリー 8 + 出生 txg 8）、クローン祖先表は認証済み構造に存在し、読者がアクセス可能でなければならない（C110 (ヘッド間共有と暗号化後のメタデータ類のブロックヘッダ整合性の読み方)）；祖先受入区間内でのバージョン相互入れ替えは未テストである。**この 5 項目を引用する際は必ずこの条項も併せて引用すること。**
- AAD が真に獲得するリンクはどこか——「MAC が不一致になる」ことではない：

```
論理 ID q  ──チェーン B──  ポインタ（先頭部：nonce / MAC）  ──チェーン A──  ディスク上の暗号文 C
```

| チェーン | 何によって保証されるか | 主な脅威は何か |
|---|---|---|
| **チェーン A：ポインタ ↔ 暗号文ブロック** | **nonce**（暗号文側のポインタ先頭にあり、I-6.1 (nonce 再利用なし) によりディスク全体で一意；tag は nonce の関数）⇒ **AAD は不要** | 攻撃者 |
| **チェーン B：論理 ID ↔ ポインタ** | **AAD のみ**。nonce は「このブロックはこのポインタに対応する」と言うだけで、「このポインタがどの key にぶら下がるべきか」は言わない | **本プロジェクト自身の実装バグ**——btree の split/merge、write buffer の seq 重複排除、スナップショット key の書き換え |

「MAC が不一致になる」はチェーン A に答えただけにすぎない；AAD の価値はほぼすべてチェーン B にあり、チェーン B の主な脅威は自前のコードである（E17 (ライトバッファマージ上限) の実測で `seq` を漏らしたのがまさにこの類である）。

- 3 つの命題の適用範囲：

| 命題 | 判決 | どの範囲に狭められるか |
|---|---|---|
| 1 checker を騙せない | **鍵を持つ checker に対して成立** | **鍵なし scrub に対しては完全に不成立**：暗号文チェックサムは平文側にあり、攻撃者がブロックを移動する際にチェックサムも一緒に自己整合的に改ざんすればよい。これは確定項目 1 で文字通り受容された範囲である |
| 2 特権昇格できない | **2 つのケースが個別に閉じられた後にのみ成立** | ①「至近修復」：暗号文チェックサムが合格し MAC が失敗した場合に破損と見なしてレプリカ修復に進むと、攻撃がデータ破棄へと転化する——I-6.9 (暗号文一致かつ MAC 失敗時は ID 不一致と判定) により閉鎖；② **平文システム構成内の nonce 水位がロールバック可能**（A2 (システム構成は平文)）⇒ 書き込み者が nonce を再利用 ⇒ ChaCha20 において 2 つの平文が直接 XOR され、**AAD はこれに対して効果ゼロ**——確定項目 8 サブ問題 2 により閉鎖 |
| 3 他者の古いデータを読み出せない | **単一ボリューム、ルート全体ロールバックなし、ブロックレベルクローンなしの範囲で成立** | 並べ替えを阻止する主力は**暗号文側の nonce であり、AAD ではない**；AAD の純増分は I-6.1 (nonce 再利用なし) が失効した際の縮退保護とチェーン B の実装バグ検出のみである。ボリュームまたぎのセルはすでに鍵導出層に移管されている（確定項目 8）|

**AAD では補えない 2 つのセル**：**ルート全体のロールバック**（ロールバックされた古いルートの各 (nonce, AAD, 暗号文) の 3 つ組はすべて本物である——「これが前の版である」という判定には AEAD 以外の証人が必要となる）；**ブロックレベルクローン**（クローンボリュームと元ボリュームは fsid が同一、鍵が同一、nonce 空間が同一地点から分岐 ⇒ 分岐後に両ボリュームが異なる内容に対して同一の nonce を発行する可能性があり、**これは nonce 再利用イベントであり、AAD に何を置いても修正できない**。修正するには mkfs / クローン時に鍵ドメインを変更するしかない）。「ボリューム全体のロールバックを防げない」ことは本プロジェクト固有の弱点ではないが、fscrypt や dm-verity と同様に表立って明記しなければならない。

- 対応する不変条件はすべて [invariants/08-加密不变量.md](../../../crates/singlefs-checker/invariants/08-加密不变量.md) に記載済みで、checker の状態はいずれも未実装である：I-6.3 (MAC と暗号文の一致) の関連データ各フィールドは checker が権威ツリーの key からオンザフライ計算し、ポインタや平文側から読み戻すことは禁止；I-6.9 (暗号文一致かつ MAC 失敗時は ID 不一致と判定) は破損に分類してはならず、レプリカ修復やポイズニングをトリガーしてはならない；I-6.2 (平文ヘッダフィールドのホワイトリスト) のホワイトリストは「平文ヘッダへの出現が許可される」という意味であり、「判定に用いてよい」ではない；I-6.1 (nonce 再利用なし) は対バグ検査であり、対攻撃検査ではない。

**根拠**：

- E31 (AADのスナップショット次元不足)：5 項目の AAD はスナップショット key 不一致を静かに素通しし、読者側スナップショットへの紐付けは共有読み取りを破壊し、出生スナップショットへの紐付けとオンザフライ計算 nonce への畳み込みの 2 つの判定基準はすべて合格——読者側スナップショットの排除が成立し、欠落と解決策がこれによって示された。
- E90 (ツリーIDのAAD格納とヘッド間共有)：ヘッドごとに 1 つのツリーがある場合、読者が探索パスに従ってツリー次元を取得すると正当な継承読み取りも一括して拒否してしまうが、出生 (ツリー, txg) の AAD 投入とクローン祖先受入の 2 つの判定基準はすべて合格——出生スナップショットに紐付ける実行可能な形態。
- 三者論証：3 本の脚が提案の下で 3 つの命題が成立すると一致して判定し、絞り込み条件は 2 つのクラウド脚から提供された；順推レッグが元の起点からのエクステントオフセットは AAD に含められないことを発見した（資料 `_d9q6-background.md`、脚の状況とメイン agent が自己検証した 4 つの外部事実は変更履歴にある）。
- ext4 の inode チェックサムシードは (fsid, オブジェクト ID, オブジェクト出生世代) の 3 点セットであるが、3 項目が入る階層は異なる（[prior-art.md](../prior-art.md) 6.5）：重複点は「どの 3 項目か」であり、階層ごとに読むと確定項目 8 の形状を支持する；シードに畳み込む形態は推測を検証できるだけであり ID を逆算できず、D20 (荷重受け面: ユニットの原子性と自己完結性) の荷重支持面の穴を埋められない（データブロックの自己記述性は D18 (ブロックに含める情報) 確定項目 3 の明示的フィールドに依存する）。
- fscrypt はオフライン改ざん後の機密性と認証を保証しないと明記している（[prior-art.md](../prior-art.md) 6.1）。

**未済の検査**：C63 (確定済み AAD がスナップショット次元に対して盲目)：AAD フィールド表の 1 回の再開（出生スナップショットへの紐付け）と checker 側の不一致判定；C107 (インデックスノードの AAD 同一性に配置先がない)；C110 (ヘッド間共有と暗号化後のメタデータ類のブロックヘッダ整合性の読み方)：クローン祖先表の配置先。

#### 確定項目 8：fsid は KDF へ、システム構成は nonce 水位により認証必須、ボリューム全体のロールバックは保護しないと宣言

**決定**：

| サブ問題 | 決定 |
|---|---|
| 1 システム構成は認証されるか | **認証されるが、理由は fsid ではない。** fsid を KDF に移した後、それと A6 (AAD 期待値は平文側から来ない) との矛盾は自然消滅する；認証の必要性を強いるのは nonce 水位である |
| 2 nonce 水位はどこに存在するか | **素の平文システム構成内に存在することは禁止**、マスター鍵から導出された MAC でカバーされるフィールド上に配置しなければならない——鍵なし側がそれを書き込むことは禁止 |
| 3 ボリューム全体のロールバック | **既知の保護対象外の範囲として宣言**、fscrypt と同一の計測条件。これを防ぐには AEAD 以外の証人が必要であり、本プロジェクトでは導入しない |

**射程**：

- サブ問題 1 の解決策は、システム構成に認証を加えて fsid を救うことではなく、fsid を AAD から外すことである：別のボリュームの暗号文を自ボリュームに持ち込む ⇒ 導出鍵が異なる ⇒ **復号できない**；攻撃者が平文の fsid を改ざんする ⇒ ボリューム全体が復号できなくなるが、これは機密性の侵害ではなくサービス拒否であり、かつ**即座に顕在化する**。KDF は暗号化が有効な場合にのみ存在し、第 1 バージョンにはこのボリューム間防衛線はない（C74 (暗号化なしの期間にボリュームをまたぐ誤方向書き込みへの防御がない)）。
- サブ問題 2：I-6.5 (nonce 水位単調) の水位が素の平文システム構成内に存在する場合、それをロールバックすることは**鍵のバイパス**を意味する（書き込み者が nonce を再利用し、ChaCha20 において 2 つの平文が直接 XOR され、AAD に何を置いても修正不能となる）。
- サブ問題 3：D22 (ユニット原子性の合成手法) にすでに「『これが前の版である』といういかなる判定も外部の証人を必要とし、これは定義的なものであり、工学的制約ではない」と記されている；ここではそれをシステム構成に対する形態として明記するにすぎない：**MAC は完全性を提供するが、新鮮性は提供しない**——再生された本物の古いシステム構成のすべてのビットは正当であり、署名検証は必ず合格する。
- システム構成の MAC が具体的にどのフィールドをカバーし、アルゴリズムと鍵をどう定めるかはフォーマットの詳細に属し、配置先は D22 (ユニット原子性の合成手法) 確定項目 9（システム構成のフィールド表）である：表にはすでにシステム構成自身の MAC 16、nonce 水位 12、KDF 識別子 4、暗号化タイプ 1、MAC 長宣言 1、マスター鍵スロット 80（インライン）が存在する；カバー範囲の条項はまだ記載されていない。

**根拠**：

- 実験なし：3 つのサブ問題はいずれも脅威モデルと確定条項からの推導であり、測定可能なコストはない。
- 現役の先例：ext4 は `s_uuid` を `s_csum_seed` に畳み込み（マウント時に 1 回計算）、オブジェクトごとの検証には `inum` と `gen` のみを投入する——「ボリューム ID は導出層へ、オブジェクト ID はユニットごと層へ」は現役のプラクティスである（[prior-art.md](../prior-art.md) 6.5）；dm-integrity の `recalc_sector` は平文システム構成に存在し、ロールバック即バイパスとなるため、上流が鍵を保持する場合は既定でそのパスを無効化する（`drivers/md/dm-integrity.c` の `dm_integrity_disable_recalculate`、[prior-art.md](../prior-art.md) 6.6）——本プロジェクトも同一の形状を採用する。
- 三者論証：3 本の脚が 3 つの異なる答えを出し、ローカル脚のみが「fsid は AAD ではなく KDF に入るべき」とした；意見の不一致は投票ではなく、ext4 が uuid をどの階層に置いているかを調べることで解決した（資料 `_d9q8-background.md`、脚の状況と 4 ラウンドで無効化されたローカル脚は変更履歴にある）。

**未済の検査**：C74 (暗号化なしの期間にボリュームをまたぐ誤方向書き込みへの防御がない)。

#### 確定項目 10：暗号化は最初の実行可能バージョンには含めず、フォーマットフィールドの予約のみ行う

**決定**：暗号化は最初の実行可能バージョンには含めず、フォーマットフィールドの予約のみを行う。実装はトランザクション層と checker が開通した後に接続する（`.claude/rules/fs-design.md`：機能からではなくトランザクションから始める）。

**射程**：予約するのは確定項目 12 の 4 項目であり、暗号化が無効な場合は全ゼロとされ、すべてのボリュームでそのまま保持され、他用途には流用されない（D19 (ブロックポインタ構造と幅予算) 確定項目 3）。`crates/` には暗号化コードは存在しない：書き込みパスはこれらのビットに 0 を書き込み（`PointerHead::write_to`、`RootRecord` と `JournalRecord` の書き出し、`SystemConfiguration::to_slot`、ユニットヘッダの 29 バイト予約）、core の読み出しパスはユニットヘッダの 29 バイトが全ゼロであること（I-2.4 (ヘッダチェックサムの対象範囲)）、システム構成の暗号化タイプが恒常的に 0 であること、2 箇所の読者（多層コード 2 ツリー内部エントリ、journal 新ルートセグメントポインタ）のポインタ先頭の MAC / nonce が恒常的に 0 であることを判定し、非ゼロは一律に破損と判定する（実審 A3a）；これら 2 箇所の読者以外でまだ切り替えられていないポインタ読者、システム構成のその他の構造定数、journal レコード自身のアルゴリズムタイプ / nonce / MAC 予約は、読み出しパスでは依然としてスキップされる。プールレベル checker は 3 種のコードのユニットヘッダ 29 バイトが全ゼロであることとフォーマットバージョンが認識可能であること、および追跡走査するポインタ先頭の MAC / nonce が全ゼロであることを判定し、いずれも I-2.4 (ヘッダチェックサムの対象範囲) に属する；システム構成のフォーマットバージョン、暗号化タイプがこのバージョンの読者の許容範囲を超える場合は、新設された I-7.13 (システム構成のプールレベルフィールドがリーダーの受け入れ範囲内にある) に属する。

**根拠**：

- 実験なし：順序は `.claude/rules/fs-design.md`「機能からではなくトランザクションから始める」の直接的な適用であり、測定可能な量はない。

**未済の検査**：C166 (平文側撤廃後にフォーマット予約領域も回収すべきか否か)：取り消された平文マッピング層 / 平文逆引きインデックスのために予約されたビットを回収するか残すか。

#### 確定項目 11：方針はボリューム全体 AEAD、暗号化境界とチェックサム境界を一致させる

**決定**：**ボリューム全体 AEAD、暗号化境界とチェックサム境界を一致させる：D4 (チェックサム配置位置) のポインタにインライン化されたフィールドは、暗号化が有効な場合は MAC そのものとなる。システム構成を除きすべて暗号化し、メタデータには最小限の平文ヘッダを残す。**この文言に例外項目はない：journal、会計ツリー、割り当てレコード、ストライプメンバー表は**一律に暗号文側にある**ため、個別に再度確認する必要はない。ディレクトリ単位 / サブボリューム単位の暗号化は行わない；「鍵なしでもバックグラウンドメンテナンスを行える」ためにメタデータを平文へ移動させることはしない。

**射程**：平文ヘッダ内に出現が許されるフィールドはユニットクラスごとに 2 つのホワイトリストに分かれる（I-6.2 (平文ヘッダフィールドのホワイトリスト)；D18 (ブロックに含める情報) 確定項目 13 はコード 1 の ID セグメントと宣言長さを暗号文に収容）；システム構成は暗号化されないが認証が必要である（確定項目 8）。暗号化が有効な場合、残された平文漏洩面には対照表が存在し（D18 (ブロックに含める情報) 確定項目 13 の「平文に残るもの／何が漏洩するか／逐語的根拠」）、ゲート比較は依然として未済である（C173 (平文側を取り消した後、平文ヘッダの漏洩面に弁護がない)）。

**根拠**：

- 実験なし：暗号化境界をどこに置くかは脅威モデルとフォーマットのトレードオフであり、測定可能なコストはない。
- AEAD の場所は D4 (チェックサム配置位置) によってすでに確保されている：ブロック層暗号化（LUKS）が認証を行えないのは、ブロックアライメントを崩さずに MAC と nonce を配置する場所がないためである；fscrypt が認証を行わない理由として挙げているのも暗号文の肥大化である。
- ディレクトリ単位 / サブボリューム単位の暗号化は行わない：bcachefs がそれを拒絶する理由は本プロジェクトにおいてさらに重みを持つ——fsck はファイルサイズを必要とする ⇒ サイズは平文でなければならない；一方、本プロジェクトの checker はディスク全体の走査によって会計を検証する必要があり（I-3.1 (割り当て済み統計が一致する)）、一部のサブボリュームがロックされていれば、その部分の会計が検証できないことを意味する。
- 鍵なしバックグラウンドメンテナンスのためにメタデータを平文に移動しない：ZFS はその道を選んだが、その代償として間接ブロックがすべて平文となり（プール構造、ファイルサイズ、ファイルホール、スナップショット構造がすべて漏洩）、認証は MAC ツリーではなく SHA512 集約へと縮退し、objset 層で portable / local の 2 つのルート MAC を維持する必要が生じた——[prior-art.md](../prior-art.md) 6.4 に記録された一連の send/recv 破損バグはこの複雑さの上に発生している。この条項は同時に確定項目 5 の第 2 の候補（インデックス内部ノードを平文で残す）を抑え込んでいる：それは同じ道であり、本プロジェクトではさらに悪い。なぜなら内部ノードの区切りキーがセマンティクスを持つからである。

**未済の検査**：C173 (平文側を取り消した後、平文ヘッダの漏洩面に弁護がない)：平文フィールド表と D18 (ブロックに含める情報) 確定項目 13 の漏洩目録のゲート比較、1 項目でも多ければ赤と判定。

#### 確定項目 12：フォーマットが day-1 で予約必須の 4 項目

**決定**：

| # | フィールド | 予約しないとどうなるか |
|---|---|---|
| 1 | ポインタ内の MAC + nonce 空間；**自己証明ユニット自身の MAC + nonce + アルゴリズムタイプ** | 事後に追加することはポインタ幅を変更することになり、フォーマット全体を一からやり直すことになる。**自己証明ユニット（ルートレコード、journal レコードヘッダ、システム構成スロット）には親ポインタが存在しない**ため、それらの MAC / nonce / アルゴリズムタイプは自身の上に配置するしかない：ルートレコード末尾にアルゴリズムタイプ 1 + nonce 12 + MAC 16（D22 (ユニット原子性の合成手法) 確定項目 7）、journal レコードヘッダの MAC 16 は fsid の後ろに並び、nonce 12 とアルゴリズムタイプ 1 は 10 個のフィールドの中にある（D23 (ジャーナルの役割と形式) 確定項目 4）、システム構成の MAC 16 / nonce 水位 12 / 暗号化タイプ 1 はフィールド表内にある（D22 (ユニット原子性の合成手法) 確定項目 9）。⚠️ **これら 3 つは I-6 (暗号化不変条件) には入らない**：ビットを予約しない場合、暗号化を有効化する日には 2 つの道しか残らない——全体を平文免責とするか（ルートレコードは `checkpoint_txg`、ツリーテーブルポインタ、マッピングルートポインタ、ツリー ID 水位を漏洩；journal レコードヘッダは `checkpoint_txg`、新規ルートセグメントの 2 本のポインタと名指し項目位置を漏洩）、またはレイアウト変更を行うかである。 |
| 2 | エクステントの「元のエクステント起点からのオフセット」 | **もし**分割が有効化された場合、分割されたエクステントを書き直す際に nonce の再利用も再計算も行わないことが不可能となる（[prior-art.md](../prior-art.md) 6.3） ⇒ day-1 でビットを予約しなければならない。⚠️ **分割は予約機能であり、第 1 バージョンでは無効化され、このフィールドは第 1 バージョンでは恒常的に 0 である**（D4 (チェックサム配置位置) 確定項目 7）——予約の理由は D19 (ブロックポインタ構造と幅予算) 確定項目 3 の固定幅であり、暗号化が無効な場合でもビットを予約するというポリシーによるものであり、「第 1 バージョンで使用される」からではない。幅：値域は**最大エクステントサイズ**によってキャップされ、ファイルサイズによってはキャップされない（エクステントは恒常的に = ユニット 32768 ⇒ 15 ビットで十分）、D19 (ブロックポインタ構造と幅予算) 確定項目 11 のオフセット表はこれに **2 バイト**（オフセット 32）を割り当てている |
| 3 | システム構成の KDF 識別子 + マスター鍵スロット + 暗号化タイプ | KDF を変更できず、既存のファイルシステム上で暗号化を有効化することもできなくなる。配置先は D22 (ユニット原子性の合成手法) 確定項目 9：KDF 識別子 4 バイト、マスター鍵スロットはシステム構成スロットにインラインで 80 バイト、暗号化タイプ 1 バイト、暗号化が無効な場合は全ゼロ；マスター鍵スロットの内部構成は暗号化有効化時に決定する |
| 4 | 各データ/メタデータ書き込みのアルゴリズムタイプフィールド | アルゴリズムを変更できなくなる；bcachefs は暗号化を一種のチェックサムタイプとして実装し、新しいデータは新しいアルゴリズムを使用し、古いデータはそれぞれのフィールドに従って復号する |

**射程**：これら 4 項目がマルチレイアウト下で共有されるかどうかについて、権威ある記録は D12 (対象メディア) 確定項目 2 にある：第 1、2、3 項は**全レイアウトで共有必須**、第 4 項は**レイアウトごとに異なってよい**。D9 (暗号化) に 2 つ目の記録は作らない。暗号化が無効な場合、これらのビットはすべてのボリュームでそのまま保持され、全ゼロとされ、他のフィールドに流用されない（`.claude/rules/fs-design.md`「暗号化はオプションの演算であり、オプションのフォーマットではない」）；journal レコードヘッダのアルゴリズムタイプの 1 バイトは第 1 項（自己証明ユニット自身の上にある分）に属する。

**根拠**：

- 実験なし：どの項目を予約すべきかは「事後に追加できない」というフォーマット上の判断であり、測定可能なコストはない；第 1 項の射程を自己証明ユニットに拡張したのはユーザー決定であり、原文は変更履歴にある。

**未済の検査**：なし（C360 (バイト表の journal 行のアルゴリズム種別が誤った予約項目を指している) は返済済み、未済の検査表の返済済み表を参照）。

#### 確定項目 13：最終選定に依存しない 3 つの必須要件

**決定**：

1. **nonce は物理位置から導出してはならない**。そうでなければ balance / copygc でブロックを 1 つ移動するたびに再暗号化が必要となり（MAC の変更が必要、鍵が必要）、マルチレプリカでもバイト列が異なってしまい、D2 (RAID ストライプ方針) のパリティ計算が直接成立しなくなる。**nonce は論理 ID に従い、ポインタ内に保持される。**
2. **順序は 圧縮 → 暗号化 → MAC に固定する。** 逆は不可能である（暗号文は圧縮できない）。これにより暗号文の長さが平文の圧縮性を漏洩する（Kelsey, FSE 2002）が、既知の漏洩目録に記載し、存在しないふりはしない。フォーマットキャリア：ポインタ先頭はアルゴリズムタイプ（オフセット 28）の後ろに **圧縮アルゴリズムコード 1 バイト（オフセット 29）+ 圧縮後長 2 バイト（オフセット 30）** を持つ（D19 (ブロックポインタ構造と幅予算) 確定項目 7 / 確定項目 11）、圧縮アルゴリズムコードの登録表は確定項目 14 にある。
3. **切り捨てられた MAC を採用する場合、読み出し再試行回数の上限はハードコードされた小さな定数でなければならず、かつ検査を備えなければならない。** bcachefs の 80 ビット MAC の安全性論証は完全に「MAC が一致しなければデバイス障害と判定し、速やかに使用を停止する」ことに賭けている——**それは実装の振る舞いであり、暗号学的性質ではない。**（確定項目 2 で完全な 128 ビットを採用したため、本条項は荷重を負わない。）

**射程**：3 項目とも最終選定とは無関係である。漏洩目録はすでに D18 (ブロックに含める情報) 確定項目 13（「平文に残るもの／何が漏洩するか／逐語的根拠」の 3 列）に記載されており、C173 (平文側を取り消した後、平文ヘッダの漏洩面に弁護がない) は依然としてゲート比較が未済である。圧縮に関する一連のフィールドは第 1 バージョンでは 0 を書き込む（確定項目 14）。

**根拠**：

- 実験なし：3 項目とも移動、暗号学の順序、および確定項目 2 から導出された制約であり、測定可能な量はない。
- 圧縮に関するフィールド群：ユーザー決定で残すことを選択（メイン agent の推奨は残さないことであった。圧縮はオプションの演算であり、`.claude/rules/fs-design.md` はフォーマット上の分岐を極力抑えることを求めており、「暗号化のために予約されたビットはすべてのボリュームで保持する」という原則は暗号化のみを管轄し、圧縮は管轄しないため）、原文は変更履歴にある；三者論証を経ておらず、覆す余地がある。

**未済の検査**：C173 (平文側を取り消した後、平文ヘッダの漏洩面に弁護がない)：漏洩目録のゲート比較（表は D18 (ブロックに含める情報) 確定項目 13 にある）。

#### 確定項目 14：圧縮アルゴリズムコードの登録表

**決定**：

| コード | アルゴリズム | 第 1 バージョン |
|---|---|---|
| 0 | 非圧縮 | **0 を書き込み**、圧縮後長も同時に 0 を書き込む |

新しいアルゴリズムはコードを再利用せず追記のみとする；読者が未知のコードに遭遇した場合は一律にそのポインタの参照解決不能と判定する（アルゴリズムタイプのフィールドと同一のポリシー、D22 (ユニット原子性の合成手法) 確定項目 17）。**圧縮後長**は 2 バイトを取り、`[0, 32768)` を表現するのに十分である（D4 (チェックサム配置位置) 確定項目 7 はエクステントのディスク占有を恒常的に = ユニット = 32768 と定めている）；コード 0 の場合、これは恒常的に 0 であり、非ゼロはそのポインタの破損と判定する。

**射程**：唯一の登録場所はここにある（D19 (ブロックポインタ構造と幅予算) 確定項目 7 の圧縮の 3 バイトはここを指している）。これはコードと圧縮後長の値の範囲を管轄し、書き込みパスで圧縮がいつ行われるかは管轄しない（順序は確定項目 13 必須要件 2 に属する）。`crates/` は 0 を書き込み（`PointerHead::write_to`）、読み出し側の「未知のコードは参照解決不能と判定」「コード 0 で圧縮後長が非ゼロの場合は破損と判定」の 2 つはすでに `PointerHeadAsRead::judged`（`crates/singlefs-core/src/pointer.rs`）に反映されている；journal レコードヘッダおよびルートレコードのオフセット 437 のアルゴリズムタイプバイトは依然として判定者がいない（C406 (読み取り側がアルゴリズム種別と圧縮の 3 バイトを判定しない)）。

**根拠**：

- 実験なし：登録表は取り決めであり、測定可能な量はない；ユーザー決定、原文は変更履歴にある。

**未済の検査**：C406 (読み取り側がアルゴリズム種別と圧縮の 3 バイトを判定しない)：読み出し側の圧縮アルゴリズムコードと圧縮後長の 2 つの判定はすでに `crates/singlefs-core/src/pointer.rs` の `PointerHeadAsRead::judged` に反映済み；journal レコードヘッダおよびルートレコードのオフセット 437 の 2 箇所のアルゴリズムタイプバイトの判定が依然として未済。

#### 確定項目 16：AAD 各フィールドの期待値は探索パスまたは認証済み暗号文側からのみ取得を許可

**決定**：

> **AAD の各フィールドの期待値は、① 読者の探索パス、または ② 上位の MAC で認証された暗号文側フィールドからのみ取得を許可する。
> 平文側からの取得、およびポインタからの読み戻しは一律に禁止する。**

メカニズム：平文側から期待値を取得する ⇒ 攻撃者が AAD の入力を制御し、AAD が防衛線から自由変数へと転化する；ポインタから読み戻す ⇒ checker は「ポインタの自己整合性」を検証しているにすぎず、**論理 ID ↔ ポインタ**のリンクはまったく検査されない。

**射程**：確定項目 6 の AAD の各セグメントを管轄する；fsid は AAD フィールドではないため（確定項目 8）、この制約を受けない。その判定可能な形式は I-6.3 (MAC と暗号文の一致) である：関連データの各フィールドは checker が権威ツリーの key からオンザフライ計算し、ポインタや平文側から読み戻すことは禁止される。条項のないコーナーケースが 2 箇所ある：ポインタ内の key セグメント（D19 (ブロックポインタ構造と幅予算) 確定項目 7 の後、ポインタは出生 (ツリー, txg) を保持する）が「探索パス」と見なされるか「ポインタからの読み戻し」と見なされるか（C295 (ポインタ内のキーセグメントが AAD の探索パスに含まれるか否か)）；ファイル間 reflink 後にオブジェクト ID とアンカーオフセットの期待値取得元が存在しないこと（C275 (ファイル間 reflink 下で AAD の2セグメントに期待値の供給元がない)）。

**根拠**：

- E90 (ツリーIDのAAD格納とヘッド間共有)：ツリー次元をポインタから読み戻すアームは 3 回の付け替えがいずれもサイレントであり、偽造された出生 txg さえ見落とす——期待値ソース判定基準（ポインタからの読み戻し禁止）の実行可能な証明。
- 三者論証：2 本の脚が異なる方向からそれぞれこれに衝突し、いずれも「この条項が成立しなければ 3 つの命題はすべて崩壊する」と判定した（確定項目 6 のそのラウンド、資料 `_d9q6-background.md`）。

**未済の検査**：C295 (ポインタ内のキーセグメントが AAD の探索パスに含まれるか否か)；C275 (ファイル間 reflink 下で AAD の2セグメントに期待値の供給元がない)。

#### 確定項目 17：他の決定との連動

**決定**：

| 決定 | 連動ポイント |
|---|---|
| D1 (データ移動性 / 逆インデックス) | データの移動可能性はハードな要件 → nonce は物理位置に紐付けてはならない（確定項目 13 必須要件 1）。**bucket generation は無効化のみを管轄し、移動は管轄しない** |
| D2 (RAID ストライプ方針) | パリティは**暗号文**に対して計算する；マルチレプリカはバイト列が同一でなければならず、同一の暗号文を N 回書き込むのであり、N 回暗号化するのではない |
| D3 (領域割り当て) | 鍵なし側は検証可能だが移動不可：scrub は実行可能、移動にはインデックスの読み書きが必要、確定項目 5 を参照 |
| D4 (チェックサム配置位置) | 暗号化が有効な場合、このフィールドは MAC そのものであり、両者は同一フィールドの 2 つの値である |
| D5 (スナップショット / 空間会計メカニズム) | **birth txg は nonce として使用不可**——同一トランザクション内のブロックがそれを共有し、nonce が重複する |
| D8 (コアインデックス構造) | extent key は version number とオフセットフィールドを予約する必要がある；btree ノード平文ヘッダのフィールドセットは一緒に決定しなければならない |
| D10 (ランダム書き込み / 断片化の真の回答) | COW をバイパスするいかなる高速パスも**暗号化をバイパスしてはならない**；インプレース上書きは直接 nonce 再利用を引き起こす |

**射程**：D9 (暗号化) が他の決定に課す制約のみを列挙する；相手側でどう実現されるかは各決定に属する。D8 (コアインデックス構造) の行の version number は D8 (コアインデックス構造) の extent key には存在せず（その確定項目 3 は `(locality_id, inode, offset)`）、確定項目 4 で nonce はエクステントごとに保持し key からオンザフライ計算しないと決定されたため、この行を残すべきかどうかは誰も判定していない。

**根拠**：

- 実験なし：各行はすべて D9 (暗号化) の確定項目（nonce は論理 ID に従う、MAC とチェックサムは同一フィールド、scrub のみ実施）から導出されており、測定可能な量はない。

**未済の検査**：なし。
