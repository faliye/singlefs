## D18 (Information Carried in a Block) —— Settled

[中文](18-块里携带什么信息.md) · **English** · [日本語](18-ブロックに含める情報.ja.md)

D18 (Information Carried in a Block) governs what information is carried inside a unit (block): criteria for whether a field is worth carrying into a block (settled item 19), fields settled to be carried and rejected fields (settled item 20, settled item 23), field tables and offsets for each class of unit headers, the value range of unit type tags and the registry for packed record types (including the instance table), the header checksum algorithm and reserved bits for nonce / MAC / algorithm type, and what level of scan rebuild can achieve relying solely on block headers. Out of scope: "Is this block still alive?" is a **question about sets**, which a block can never answer—this is not a defect in format design, but rather D5 (Snapshot / Space Accounting Mechanism) has settled that it is a global attribute, and that is precisely the origin of O(1); the field composition of AAD belongs to D9 (Encryption) settled item 6. Interlocks with other decisions: data unit self-describing is directly related to the leakage surface trade-off in D9 (Encryption) settled item 5 (settled item 3, settled item 13); intra-node parity partially overlaps with the variable-width full stripes of D2 (RAID Stripe Policy) across multiple disks, but **a single disk is where D2 (RAID Stripe Policy) cannot reach** (settled item 4); if carried information falls on **each record** rather than on block headers, the cost multiplies by record count (D8 (Core Index Structure), settled item 19); inlining "last verification time" would turn **scrub from a read-only into a write operation**, creating new blocks on each sweep, condemning old blocks to death and feeding them into deadlists, **working in direct opposition to the goal of resident compaction in D3 (Space Allocation)** (settled item 19 criterion 1).

#### Settled Item 1: Lineage Rewrite Sequence Number Not Adopted

**Settlement**: Lineage rewrite sequence numbers (monotonically increasing along lineages, orthogonal to transaction numbers) are not implemented. **What it aims to purchase has already been purchased by something else**: the purpose of a lineage rewrite sequence number is "distinguishing stale replicas from active replicas", whereas the per-placement predicate of D3 (Space Allocation) settled item 1 is precisely the authoritative recording point for that capability ⇒ adding another sequence number purchases nothing new, only adding a permanent format field.

**Scope**: What is rejected is "a sequence number established to distinguish stale replicas". If another use arises in the future (for instance, if the question of how to coexist with the checkpoint sequence numbers settled in D16 (Publish Semantics) genuinely stands independently), it can be reopened when needed, **but whoever reopens it must first demonstrate that it does not buy what has already been bought**. The unit header's write sequence (instance generation, transaction number) (settled item 7) is not within the scope of rejection: it purchases "whether this unit has been published, and which timeline it belongs to"; ordering of published versions of the same key relies sufficiently on birth generation + one net effect per transaction per key; write sequence only incidentally provides ordering when modifying the same key across transactions in the same txg. Settled item 11 once planned to use birth generation to select the newest among multi-version packed containers of the same identity, which is precisely the use rejected here; having shifted to judgment via the predicate of D3 (Space Allocation) settled item 1, settled item 1 will not reopen.

**Basis**:

- E59 (Can Buffered Messages Recompute Solely from Units): When scanning only units, multiple readable replicas of the same key cannot distinguish the active value; after adding the per-placement predicate, divergence across all four categories of messages falls to zero—a sequence number only purchases the overwrite slot; adding another purchases nothing new.
- User settlement, recorded in change history; the scope note on write sequence was added following the settlement of C113 (No Input to Current-Version Determination of Multi-Version Units in Scan Rebuild).

**Owed checks**: C288 (collateral changes from mapped key settlement did not land in other decisions) item 6: add note in scope that "birth sequence number only serves as one segment of key, not used to select newest".

#### Settled Item 2: All Code 2 Nodes Unconditionally Carry Key Ranges

**Settlement**: **Every code 2 index node carries `[min_key, max_key]`, not split by tree, without toggle.** The code 2 header width formula `86 + 2 × key width` (settled item 18) therefore holds unconditionally for all trees; decoding a code 2 node during scanning does not require first checking "whether this tree carries it". What it purchases is: a node picked up in isolation can self-prove which range of keys it ought to cover, aligning with `.claude/rules/fs-design.md` "do not sacrifice self-containment to save space". **The width of the range is two key widths**: the accounting tree key is 22 wide (D5 (Snapshot / Space Accounting Mechanism) settled item 5), so the range a node carries is 44 bytes, exactly the `2 × 22` in the header width `86 + 2 × 22`. **Range takes the subtree coverage range**: `[min_key, max_key]` is the minimum and maximum key reachable within this node's subtree—on leaf-level code 2 nodes it is the keys of the first and last entries; on internal nodes whose children are code 3 containers, max_key is the key of the last record in that final container, not the separator key of the last entry. Modifies bytes of new-pool file creation: No—the ranges were already present in the bytes written out by the six code 2 trees; both interpretations yield the same value for new-pool file creation (inode tree root [1, 1]).

**Scope**: What is extrapolated is the judgment "whether to carry", not the cost numbers of E73 (Fanout Cost of Node Key Interval)—how many slots fanout drops for each tree still requires individual measurement. **The dirent tree slot is closed accordingly**: when a dirent tree exists it still carries key ranges; what needs remeasuring then is fanout cost, not this judgment. Key ranges reside in block headers (D15 (Format Freeze Policy) tier 1), sharing the same slot as accounting tree node headers (C102 (no reserved area in index node headers; adding fields is not compat)). Internal nodes whose children are code 3 containers (inode tree, tombstone tree, lineage tree, retirement tree) carry the subtree coverage range: the inode tree root writes [smallest record number of the leftmost leaf container, largest record number of the rightmost leaf container], and container trees fit tightly to the container numbers of the first and last entries at level 1 and write [leftmost container number of the first child's branch, rightmost container number of the last child's branch] at level ≥ 2. Implementation: writer `crates/singlefs-core/src/transaction.rs`, reader `crates/singlefs-core/src/recovery.rs`, pool-level checker `crates/singlefs-checker/src/lib.rs` and `crates/singlefs-checker/src/walk.rs` (the range of an internal node is judged only after its children are read back; the node-reading step judges only that separator keys strictly increase); bad images with the range written as the entry key range have test cases in `crates/singlefs-harness/tests/key_range_of_code_two_nodes_over_containers_is_the_subtree_coverage.rs` and `crates/singlefs-harness/tests/pool_checker_judges_the_key_range_of_code_two_nodes_over_containers_against_the_subtree.rs`. For position-addressed trees (allocation record tree, extent tree, D8 (Core Index Structure) settled item 14), the key range in the node header writes the span governed by position regulations for that node, which is identical to the "subtree coverage range" on such trees; checker independently computes the span each node ought to cover based on position and verifies node by node.

**Basis**:

- E142 (New-Pool File Creation Dry Run): All six code 2 trees written out in run 6 carry key ranges; without them, no tree header width can be calculated; the per-tree carrying approach would require adding a "carry or not" flag bit in the code 2 header, whereas the scan rebuild path has no tree table, creating a cycle where one must know header length before reading the flag.
- E73 (Fanout Cost of Node Key Interval): Carrying ranges drops fanout by at most 1 slot without increasing tree height; 16 KiB in D8 (Core Index Structure) settled item 2 does not need reopening; isolated node coverage range judgment cannot be resolved by the arm without ranges.
- User settlement (modal prompt, did not go through three-way argument, overturnable; main agent recommended this tier too), verbatim text in change history.
- User settlement 2026-09-23: Range takes subtree coverage range, verbatim text in change history.

**Owed checks**: C909 (only core checks that a level-1 separator key in a container tree equals the container number).

#### Settled Item 3: Data Blocks Carry Plaintext Self-Describing Header

**Settlement**: Each data unit carries a plaintext self-describing header, taking the fields settled in D9 (Encryption) settled item 6: `(unit type tag, tree ID, object ID, object birth generation, anchor offset)`. **Preferably sized generously, not trimming fields to save space.** Width of the five fields: **unit type tag 1 + tree ID 8 + object ID 8 + object birth generation 8 + anchor offset 8 = 33** (question 8 of [verification-build.md](../verification-build.md) closed hereby; basis traced back in settled item 11).

- **Boundary with D1 (Data Mobility / Reverse Index)**: **Criteria reside in D1 (Data Mobility / Reverse Index)** (what enters self-contained segments, what enters extension points; see its settled items 1 / 3 / 4); **field tables reside here** (which fields actually entered, how wide each is, how partitioned by unit class). If criteria change, this table changes accordingly; table formatting does not reverse criteria.
- **Do not add sixth field `locality_id`**: `locality_id` is a hint (D8 (Core Index Structure) settled item 3); during rebuild, objects are identified by (tree ID, inode), inspecting only the extent tree of the current header, assigning the same initial segment to all extent keys (surviving and recovered) for this object, taking value inode record > surviving extent key > 0; incorrect assignment merely loses locality; rebuild artifacts are inherently read-only (settled item 5). Rebuild rules text resides in D8 (Core Index Structure) settled item 6 "Rebuild" paragraph.
- **Two lines that must be held**:

| Forbidden to Place | Why |
|---|---|
| **Physical placement / device ID** | D9 (Encryption) settled item 6 settled that "physical locations never enter AAD" ⇒ placing it in block headers creates an **unauthenticated, silently tamperable** field. Authoritative recording points for physical addresses remain in encrypted structures per D9 (Encryption) settled item 5 (scrub only); the non-key-holding side cannot read it anyway |
| **File name / separator key / any path info** | D9 (Encryption) settled item 5 settlement states verbatim that its **entire** difference from the ZFS path is scope—"not exposing separator keys of btree internal nodes", whereas the separator key of the dirent tree is the file name. **Failing to hold this equals taking the ZFS path** |

- **Why physical pointers in extension points do not hit these two lines: reason is "cannot create silent misreads", not "it is authenticated"**: These two lines guard against **silent misreads**—a forged physical placement in a block header would make a reader read the wrong block while believing it read correctly. But pointers in extension points **cannot enter any decision path** (D1 (Data Mobility / Reverse Index) settled item 5 verbatim: it does not constitute a reference); every dereference must pass target birth generation comparison against target unit's own header checksum ⇒ forging it at most makes a clue point into empty space, **incapable of creating "reading wrong while believing read right"**. This belongs to the same category already knowingly accepted in D9 (Encryption) settled item 5 (plaintext side may be reordered, generation may be forged), introducing no new category. **Must not cite "extension point is within checksum / authentication coverage of whole unit" as reason**; reason remains "cannot create silent misreads", which does not depend on whether MAC covers extension point; switching back to "extension point is authenticated" requires renewed defense, which has not been done.

**Scope**: What it purchases is "rebuildable when index is lost", **not "tamper-evident when attacker modifies"**—the latter relies on AAD mismatch and the Merkle tree of D4 (Checksum Location). **Plaintext readability of block headers does not constitute authentication**: during normal reads (indices present), plaintext headers do not participate; AAD expected values come from lookup path per A6 (AAD expected values do not come from plaintext side); rebuild (indices lost) must participate; individually modifying fields causes MAC mismatch, but whole-unit relocation (header + ciphertext moved together) passes verification completely, which is precisely the "block-level reordering" A6 (AAD expected values do not come from plaintext side) guards against—this slot is handled per degraded semantics of settled item 5. The two lines govern self-contained immutable data, not extension points: **physical placement is mutable** (blocks get moved, and the raison d'être of D1 (Data Mobility / Reverse Index) is precisely mobility); by "changes across versions or not", it inherently cannot enter self-contained segments; extension points are for mutable data (D1 (Data Mobility / Reverse Index) settled item 3: either empty or a pointer). When encryption is enabled, this tuple in the block header is its **sole** plaintext expression on disk (D9 (Encryption) settled item 5 establishes no plaintext mapping layer and no plaintext reverse index); anchor offset directly reveals file size and file holes; this leakage is not accepted, handled under settled item 13; settled item 3 itself remains unchanged—data units still carry self-describing headers, field set and widths untouched; settled item 13 merely changes "whether these fields are plaintext or ciphertext on disk when encryption enabled"; primary basis (existing for fast retrieval, not sacrificing self-containment for space) does not depend on the leakage surface slot. This group is simultaneously the AAD field set of D9 (Encryption) settled item 6, and the C72 (nobody answers how extents relate to units) round established that "AAD field composition is a day-1 permanent contract" ⇒ modifying it is a permanent contract alteration. Three slots derived from settled item 3 form formal items: settled item 5, settled item 6, settled item 7.

**Basis**:

- E28 (Can Plaintext Mapping Rebuild Solely from Self-Describing Units): When removing plaintext mapping layer and scanning only unit headers for rebuild, metadata side has zero missing and zero incorrect entries; data block side deficit exactly equals total data block count; positive control adding self-description to data blocks drops deficit to zero—this is the hole it purchases.

#### Settled Item 4: Form Takes Metadata Multi-Copy + Dispersed Placement, Chain Arm Rejected, Single-Disk Layout Line Not Opened Yet

**Settlement**: Form of single-disk self-recovery takes "metadata multi-copy + dispersed placement" (ditto); chain arm formally rejected; but **single-device layout line is not opened yet**. ditto takes ZFS's real form: user data 1 copy, dataset metadata 2 copies, whole-pool metadata 3 copies, copies placed dispersedly. **Mandatory clause when adopting ditto**: placement offset **must not take powers of 2**—resonating with failures of any power-of-2 periodicity causes all three copies to share congruences and perish together. Modifies bytes of new-pool file creation: **No** (ditto is copy count and placement policy, modifying no field tables; single-disk layout line unopened ⇒ bytes written by new-pool file creation remain unchanged).

**Scope**: **Settled item 3 does not diminish settled item 4**: data block self-description guards against "**index lost**"; settled item 4 guards against "**block itself lost**"—self-description cannot read a block no longer on disk; the two have different scopes. Reason for not opening single-disk line: single-disk line is an **entirely different layout**, not "a 2-disk line with one disk pulled"—D2 (RAID Stripe Policy) settled item 6 `w ≥ 2` is mutually exclusive with single device (D2 (RAID Stripe Policy) settled item 9); D12 (Target Media) also requires an incompat bit for it, making it a permanent format branch; per branch criteria in `.claude/rules/fs-design.md`, it must be justified independently; opening the line requires standalone crash-point replay verification, and requires test-only switches to force entry. Multi-disk and single-disk are not equivalent: `w ≥ 2` and zero-redundancy stripes forbidden to issue ⇒ every stripe in a ≥2 disk pool naturally carries parity, losing 1 column can be rebuilt from remaining columns (the claim that "one unit landing on one column in its entirety (D2 (RAID Stripe Policy) settled item 10) ⇒ losing one disk equals losing the entire unit ⇒ multi-disk equals single-disk" **does not hold**); **single disk lacks this mechanism**. If chain takes version chain (prev/next = COW predecessor and successor of this unit), it hits two rejection list items (settled item 23: "child block recording current parent node physical address" judged "temporally impossible", "COW predecessor address (version chain)" judged "negative net value"), leaving only same-batch chain for comparison.

**Basis**:

- E118 (Three Arms of Single-Disk Self-Recovery): Pre-run hardcoded failure clauses triggered literally—recovered count for same-batch chain on **all** failure points equaled zero-redundancy arm; what it purchases is **detection**, and detection can already be answered by allocation records of D3 (Space Allocation) settled item 3 ⇒ net gain ≈ 0; ditto is the only arm among the three that purchases recovery capability; the offset of "at least 1/8 disk away" in the model was a power of 2, resonating with power-of-2 periodic faults. The six evidentiary burdens prior to line opening are discharged at once by this.
- Six line-opening evidentiary burdens, red-verdict conditions, and user settlements resulting from three-way argument are all in change history.

**Owed checks**: C201 (ditto placement offset forbidden from power of 2).

#### Settled Item 5: Rebuild Is a Degraded Path, Graded into Three Levels by Available Witnesses

**Settlement**: Acknowledging rebuild as a degraded path, but the form is not a mere statement, but graded by available witnesses:

| Level | What Witness Obtained | Disposition |
|---|---|---|
| 2 | Allocation record (D3 (Space Allocation) settled item 3) + checksum / MAC dual-witness | Writable, normal promotion; ⚠️ Unreachable—allocation records are derived state (D21 (Boundary Between Authoritative and Derived States) settled item 5); derived state cannot serve as a witness; level 2 witness does not exist |
| 1 | Only checksum / MAC self-consistent, no allocation record | **Read-only mount** |
| 0 | Cannot even verify checksum | Report only, do not enter mapping |

**Grading criteria are computable, and inputs remain constant during operation**, satisfying `.claude/rules/fs-design.md` hard requirements 1 and 5 for branching. **All three must be implemented; lacking any one leaves it as a mere reminder** (`.claude/singlefs-ai-sop/rules/show-me-test.md` verbatim prohibits writing past pitfalls as reminder sentences):

|---|---|---|

It must fall on authenticated fields (D9 (Encryption) settled item 8 settled that system configuration must be authenticated due to nonce watermark) |
| 2 | `map_provenance = rebuilt` and unpromoted ⇒ **read-only mount** | The `compat_ro` form of `.claude/rules/fs-design.md` "turning misuse into unmountable": mountable, unwritable, explicit failure mode |
| 3 | One discipline: under this state, **no authoritative state structure may be repaired in-place by rebuild results** | It extends I-6.10 (deactivated · the plaintext mapping layer no longer exists) verbatim "any discrepancy is judged red, **in-place repair forbidden**" to rebuild artifacts, not a new mechanism |

Three format-level requirements for `map_provenance`:

| # | Requirement | Why |
|---|---|---|
| 1 | Resides in system configuration, **and must not reside in a position where it can be rewritten without trace** | A gate that can be bypassed by modifying a single byte is equivalent to having no gate at all. Its protection strength varies with encryption toggle (Scope) |
| 2 | **Promotion from Level 1 → Level 2 must leave traces**, in-place modification of flag bit back to normal forbidden | Promotion is "legitimately clearing rebuilt"—**it is itself the shape of a bypass path**. | 3 | Subsequent normal write paths **must not overwrite it** | Amnesia shape: declare once, never inspected again, subsequent mounts all display normal. **Good-faith operation will also lead there** |

**The half-sentence "requiring human confirmation" is not adopted**: administrators hold no original index or reference data to compare against, **unable to judge whether files have been moved** ⇒ that requirement in practice forces humans to trust rebuild processes without verifiable data, **which directly violates the purpose of authentication**. #### Settled Item 6: Data Block Self-Describing Header Placed at Low Offset, Payload Starts After Header

**Settlement**: Each block's **byte 0 onwards is the self-describing header**, immediately followed by payload. **The half-question "whether header attaches at block level or unit (extent) level" is settled as block-level**: placing at low offset means the scanner hits it by stepping per block, whereas unit-level requires scanner to know unit boundaries beforehand—**which is precisely what it needs to rebuild** (cyclical).

**Scope**: Once block = unit (settled item 9) and extents do not span multiple units (D4 (Checksum Location) settled item 7), "block-level" and "unit-level" coincide under this value; the amortized cost N for "a large extent spanning N blocks paying N copies of headers" originally owed by block-level is constantly 1, removing the target.

**Basis**:

- No experiments: Criterion is "whole-disk scanning during recovery must find these headers **without indices**" ⇒ headers must fall at positions the scanner can **predict**, and block start is the sole position computable without any prior knowledge.
- User settlement, recorded in change history.

**Owed checks**: None.

#### Settled Item 21: Scope of Self-Description Is Misdirected Writes, Not Lost Writes

**Settlement**: A **lost write / phantom write**—the device reports success without actually writing—leaves an old block that is **fully consistent internally**: old contents, old checksum, correct own logical address and correct fsid all match. ⇒ **Any judgment that "this is the preceding version" requires an external witness. This follows from the definition, not an engineering limitation.** **The witness must be in a different failure domain**: if the parent also failed to write in the same event, a grandparent is needed, recursively up to the root. ⇒ **Root / system configuration is the final witness**, also an independent reason for D16 (Publish Semantics). ⇒ **Detection information must reside outside the block**; the only method is for the parent to hold the child's checksum / generation, the Merkle tree settled in D4 (Checksum Location). **Self-description covers misdirected writes / fetching the wrong block; it does not cover lost writes. Do not conflate them.** Under COW, a lost write can mean **the new block was written but its parent's update was lost**. The parent still points to an entirely legal old child, so **the whole subtree silently rolls back to the preceding version**. Detection uses **the expected generation stored in the parent pointer, not the address stored by the block itself**. D4's Merkle construction is required because the expected value can, by definition, reside only on the asking side, rather than merely because a block cannot detect the problem itself.

**Scope**: **Device ECC is outside the scope being discussed, rather than insufficiently strong.** It judges bit consistency within an individual codeword, with an error-reporting failure mode rather than a silent one. Misdirected writes and lost writes share a different structure: **the on-disk bits are entirely legal and pass ECC perfectly**; what is wrong is whose bits they are and which generation they belong to.

**Basis**:

- No experiments: Definitional—valid old versions and valid new versions are **isomorphic at the intra-block level**; three counterexample paths all fail: wall-clock timestamps (old blocks **legitimately** carry old timestamps), incrementing local counters, and version history hash chains ("expected count", "expected chain length", and "expected hash" all reside outside the block).
- OSTEP §45.6 verbatim (local PDF extraction recheck): "Unfortunately, the answer is no: the old block likely has a matching checksum... Thus, checksums alone are not enough to detect lost writes; the file system needs additional machinery...".
- XFS `xfs-online-fsck-design.rst:945-946` claims that recording the ondisk address in a block "enables the filesystem to detect lost writes", directly contradicting OSTEP §45.6. OSTEP is judged correct: XFS updates in place, and an address check passes when the address already holds an older version of the same object. Word-by-word counts in two flash reliability surveys (arXiv:1706.08642, arXiv:1711.11427) find zero hits for all six terms related to misdirected / lost writes. The original text and cell-by-cell comparison are in the change history.

**Owed checks**: C7 (no check for stale blocks).

#### Settled Item 23: Rejection List

**Settlement**: The following candidates are not carried into blocks:

| Candidate | Rejection Reason |
|---|---|
| **Child block recording "current" parent node physical address** | **Temporally impossible**: COW writes child first, parent second—the moment child block writes, what it wants to record does not exist yet. | **Checkpoint inlining "N blocks in this checkpoint"** | **Same temporal deadlock**: N is known only when checkpoint concludes, whereas the field must embed into every block written during the period |

| **Intra-block error correction code (ECC)** | **Rejected, reason being "neither end economical, no sweet spot in between"** (not "too expensive"). ① Cheap tier: Hamming 16-bit corrects 1 bit, overhead on 4 KiB block is **0.05%**, **but it only corrects the class already fixed by device ECC**; expensive tier: RS correcting an entire 512-byte sector takes 12.5%, correcting a half-block lost to torn write takes 50%; whereas in the two classes device ECC cannot cover, torn write takes 50% parity, and **misdirected write means the entire block is someone else's data with zero redundancy available**. ② **The sole instance across all examined systems is OCFS2 `metaecc`** (`struct ocfs2_block_check` in `fs/ocfs2/ocfs2_fs.h`: 32-bit CRC32 + 16-bit Hamming, `ocfs2_hamming_fix_block` in `blockcheck.c` correcting 1 bit before reverifying CRC), **correcting only single-bit errors and disabled by default**, with its design doc explaining the motivation as "Modifying it to this level of safety isn't really possible **without creating an entirely new filesystem**"—**this motivation does not hold for this project designed from scratch**. ③ Checking 13 other systems (including IRON, CrookFS, NOVA-Fortis, EnvyFS), **intra-block ECC has zero hits**; NOVA-Fortis explicitly evaluated ECC and then rejected it |
| **Per-block wall-clock time** | Checked across four block header implementations, **none carry it**, all using `generation` / `txg`—monotonic, comparable, naturally defined commit points under COW. Wall-clock appears once in ZFS uberblock, **one copy per pool** |
