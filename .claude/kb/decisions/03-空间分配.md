## D3 空间分配 —— 已定（7 个分项全定）

**1. 不分 data / metadata 两类空间。** 全局统一分配器。

依据：btrfs 的两级分配 + chunk 分类僵化是 ENOSPC 病根
（"`df` 还有几十 G，写文件报没空间"、"删文件也报没空间"）。

**2. 连带承诺：后台整理必须是常驻的、自动的、用户无需知道的。**
不分类意味着碎片化压力全压在一个分配器上，btrfs 靠人手动跑 `balance` 来救，
这是它最大的运维恶名之一。选了不分类就等于承诺自动整理。
**这个承诺的承接方是 D26（后台整理与放置回收） 腿一**——机制、触发判据与未定项都在那条正文里。

**3. 空间预留用准入控制形态，量要小。**
预留不是"划一块地不给用"，而是：任何增加空间占用的操作，进门前先算
"最坏情况下解开自己需要多少"，算不过就拒绝。这样预留量动态贴着实际需求，不白占。

**4. 与 D9（加密）的连锁**：加密开启时，无密钥的一侧**能搬，不能回收**。

- **能搬**：D9（加密）已定项 5 已定（2026-08-26）——把「一个块的物理地址的权威记录点」
  移出加密结构，改为明文的「逻辑身份 → 物理地址」映射层 + 明文反向索引。
  这一条正是为 D3（空间分配）的「常驻、自动、用户无需知道的后台整理」这个硬承诺付的代价。
- **不能回收**：记账是权威态（D21（权威态与派生态的分界））且加密，无密钥侧写不了它。
  ⇒ 「把空间标记为可分配」在锁盘期做不到，见 D9（加密）已定项 7。
- 检测始终可做（指针里有不要密钥的密文校验和）。

**原则**：COW 系统必须保证「释放空间」这个操作本身不需要申请空间。
btrfs 没在设计层保证这点，靠一堆启发式补了十几年还在出问题。

#### 已定项 1（2026-08-31，用户定案）：分配记录逐落点答得出「属不属于现行版本」

**这是「某个落点此刻属不属于现行版本」这个谓词的权威记录点**，
不是聚合量——D5（快照 / 空间记账机制） 已定项 3 那棵记账树装的是
「(统计量, 维度元组, 代) → 完整值」，它答不了单个落点。

谓词由两半合成，两半都已定：

| 半 | 谁给 | 说的是 |
|---|---|---|
| 这个落点分配出去了吗 | **D3（空间分配）** 的分配记录 | 空闲的落点不属于任何版本 |
| 分出去的属不属于**现行**版本 | **D5（快照 / 空间记账机制）** 的 deadlist | 进了 deadlist 的落点只被快照引用，不在活树里 |

⚠️ **「权威记录点」是运行时口径，不是态别**（2026-09-03 用户定案收口 C73（分配记录的态别没定））：
分配记录**是派生态**，整棵树可从单元 + 记账 + 根重建，权威态仍是那三样、不扩项。
运行时判这个谓词只许问它、不许现扫；而它自己丢了能重建。权威记录在
D21（权威态与派生态的分界）已定项 5。

**它买到什么**：索引整个丢掉之后，扫盘重建**分得清陈旧副本与现行副本**。
E59（缓冲消息能不能只从单元重算） 实测：只扫单元时同一个 key 的多份可读副本分不出现行值
（分不出的数恰好等于覆写次数），加上这个谓词之后四类消息的分歧**全部归零**。
D11（索引节点要不要留消息缓冲区） 已定项 4「缓冲仍是纯派生态」整个压在这一条上。

**E74（分配记录的条目数与整理开销） 已量（2026-09-01，9 单测 / 8 条变异全抓）**：
逐落点确实随容量走——32 KiB 落点、90% 填充下，**这棵树自己吃掉约 0.055% 的容量**
（16 TiB 盘上 4.83 亿条目、树高 3、占 9.0 GiB；256 TiB 上 77 亿条目、树高 4、占 145 GiB）。
与记账树的量纲**确实不同**（记账树在三档容量上都是同一个数），两棵树都没建错。

**与后台整理的交互也量了结构那一半**：固定 4096 个落点、容量涨 256 倍，
重写的节点数只从 13 涨到 19，涨的全部来自树高
⇒ **整理路径里没有随盘容量走的项**（`.claude/rules/fs-design.md` 第一格）。
⚠️ **但 COW 重写的是整个 16 KiB 节点，不是那 20 字节**：
落点在 key 空间里**连续**时放大 2.6 倍，**打散**时 **964 倍**，差 370 倍。
**已定项 3 那条 key（设备身份 + 设备内偏移）把整理放在了好的那一端**——
物理相邻的落点在 key 空间里也相邻，而整理搬的正是物理相邻的一批。
⚠️ **挂钟那一问仍欠实现**，且整理**策略**本身没被测（D26（后台整理与放置回收） 六个分项全开着）
⇒ 量的是载体强制付出多少，不是某个策略的代价。

#### 已定项 2（2026-08-31，用户定案）：墓碑那一笔由准入控制算进最坏情况

D18（块里携带什么信息） 已定项 8 已定「删除要写墓碑单元」⇒ **删除这个操作本身要写盘**，
而 D3（空间分配） 的原则逐字写着「COW 系统必须保证『释放空间』这个操作本身不需要申请空间」。

**解法不是给删除路径开口子，是把那一笔提前到写入那一刻收掉**：
D3（空间分配） 第 3 条的准入控制本来就要求「任何增加空间占用的操作，进门前先算
**最坏情况下解开自己需要多少**」——**墓碑就是「解开自己」的一部分**，计入那个量。

⇒ **删除路径仍然不申请空间**：它要写的那个墓碑，空间在对象写进来的时候就已经算过并留住了。
原则一个字不改，改的是「解开自己需要多少」这个量的算法——它现在含墓碑那一项。

⚠️ **量还没算**：一次删除写几个墓碑、能不能批量摊、盘满时删得动删不动，一个数都没有。
定案定的是**这笔账归谁付**（准入控制，写入时付），不是**这笔账是多少**。
后者要等分配器与准入控制有实现才算得出来。

⚠️ **它把一条现有的坑变紧了**：预留量现在与「将来会不会被删」绑在一起，
而 D3（空间分配） 第 3 条的原意是「预留量动态贴着实际需求，不白占」。
墓碑那一项对**永不删除**的对象是纯浪费——浪费多少，同样没量。

#### 已定项 3（2026-09-01，用户定案）：分配记录住一棵独立 keyspace 的 btree

**已定项 1 定的是谓词（逐落点答得出属不属于现行版本），没定它住哪。** 这一项补上载体：
**独立 keyspace 的 btree，key = 落点（设备身份 + 设备内偏移），value = 分配代。**

**依据**：

- key 用落点是已定项 1「逐落点」的直接后果，`(dev, 偏移)` 与 D19（块指针的结构与宽度预算）

- 加一棵 keyspace 不是 incompat 改动——D15（格式冻结政策） 已定超级块树表 day-1 做成开放列表，
  判定表把「新增一棵 keyspace」钉死为 **compat**。

**用户口径**：先按这个形态落地，写代码时再调整。

⚠️ **欠一次测量，已立 E74（分配记录的条目数与整理开销）**：已定项 1 自陈

⚠️ **一条实验发现的候选规则（2026-09-02，E81（提交的固定点））——写下来时还没定案，同日已定，权威记录在 D3（空间分配） 已定项 5**：

#### 已定项 4（2026-09-01，用户定案）：准入不等式的权威形式

```
可用 = Σ设备( 容量 − 已分配 − 不可回收 − defer 待释放 ) − 待删占用 − 已承诺预留
```

**它是「任何增加空间占用的操作，进门前先算最坏情况下解开自己需要多少」（D3（空间分配） 第 3 条）的可执行形式。**
此前全仓没有一处把它写全——I-3.4（可用空间扣待删占用） 只说「可用空间统计已扣除待删占用」，
第 3 条只说「先算最坏情况」。

**六项逐项有出处，不是凑出来的**：

| 项 | 为什么在式子里 |
|---|---|
| 容量、**已分配** | I-3.1（已分配统计对得上） 的被审计对象 |
| **不可回收** | zoned 上一个活快照钉住的物理空间是 zone 粒度而引用的块数是块粒度，[invariants.md](../invariants.md) 逐字要求「另立一个不可回收量」 |
| **defer 待释放** | D16（发布语义）：checkpoint C 中产生的释放在 C 发布之前不得进入可分配集合 |
| **待删占用** | I-3.4（可用空间扣待删占用）；D5（快照 / 空间记账机制） 与 D8（核心索引结构） 分批删除定「待删除结构算作活引用」 |
| **已承诺预留** | D3（空间分配） 第 3 条；已定项 2 逐字「墓碑就是解开自己的一部分，计入那个量」 |

⚠️ **前三项按设备求和，后两项不按**——前三项是物理量（一块盘满了不能靠别的盘补），
后两项是全池的承诺量。**这个分界直接决定 D5（快照 / 空间记账机制） 已定项 4 里哪几个统计量要带设备维。**

⚠️ **它解锁了两样**：D5（快照 / 空间记账机制） 已定项 4（统计量有哪几个）的完备性现在可判了——
清单相对这个式子完备即可；[checks-owed.md](../checks-owed.md) C70（跨统计量的和没人盯） 的那条向量等式现在写得出来了。

⚠️ **式子的六项都是已发布统计量，准入却发生在窗口中间——在飞合成已由 E82（准入的在飞合成）
建模（2026-09-02）**：只读已发布值 ⇒ 同窗并发超卖（实测 80/120 格）；把窗口内释放记成可用
⇒ 20 格吃进 defer 该扣住的块（D16（发布语义）新规则 2 被静默绕过）；忘了把墓碑计入「解开自己」
⇒ 盘满后删除全数死锁。**正确形态已定案（2026-09-02），权威记录在 D3（空间分配）已定项 6**；
实现侧的测试开关（overlay 可强制清零，双向证）仍欠，见 [checks-owed.md](../checks-owed.md)
C87（准入读的合成值无定义）。


#### 已定项 5（2026-09-02，用户定案 + E81（提交的固定点））：提交内生块从聚簇段分配

**提交自身产生的块——分配记录树 / 记账树等结构的 COW 新节点——必须从 key 空间上
连续的聚簇段（bump 段）分配；用户数据块的落点不受此约束。**

**依据（E81（提交的固定点），计数模型）**：全部记账结构都是 COW 树
⇒ 给它们写节点又产生分配，固定点循环的放大由「提交内生块聚不聚簇」决定——
全散布时一次 12 单元的 fsync 拖出 **5909 个元数据块**（65 轮，journal 点名项 5921，
I-8.1（环几何够大）的「最坏事务占用」在该政策下没有可用上界）；
**只聚簇提交内生块就断链**（2 轮、28 块），用户数据全随机也不影响。

⚠️ **口径**：它是**分配器政策不是格式位**——聚簇段的位置与长度是运行时选择，
盘上没有任何字段声明它；违反它的实现写出的镜像完全合法，只是每次发布贵几百倍。
⇒ 拦它只能靠运行时读数：**提交路径记「本次发布的固定点收敛轮数」，超过声明上界判红**
（`.claude/rules/fs-design.md` 硬要求 4：走错分支是性能悬崖，悬崖不报错），
落点 [checks-owed.md](../checks-owed.md) C83（提交固定点没人回答）。
⚠️ E81（提交的固定点）给的是下界（假设发布末尾一次性 COW），边插边 COW 的实现更贵。

#### 已定项 6（2026-09-02，用户定案 + E82（准入的在飞合成））：准入的在飞合成

**准入读数 = 已发布统计量 − 在飞已批准的预留；窗口内产生的释放不发信用
（D16（发布语义）新规则 2 的准入侧形态）；「最坏情况下解开自己需要多少」含墓碑那一笔
（已定项 2 的可执行读法）。**

**依据（E82（准入的在飞合成），三个 bug 形态各配一个可数违例）**：
只读已发布值 ⇒ 同窗并发超卖（80/120 格，分配中途才失败）；
把窗口内释放记成可用 ⇒ 20 格吃进 defer 该扣住的块（崩溃回滚后旧根还引用它们）；
忘了墓碑 ⇒ 盘满后删除全数死锁。三个红样例照抄进准入路径的单测与崩溃点重放。

⚠️ **在飞 overlay 是纯内存派生态**：崩溃后按定义清零（在飞事务全部作废），
不落盘、零格式位。⚠️ 实现侧仍欠：overlay 做成可强制清零的测试开关（清零后并发准入
必须超卖、检查必须抓到——双向证），见 [checks-owed.md](../checks-owed.md)
C87（准入读的合成值无定义）。

#### 已定项 7（2026-09-03，用户定案 + E97（记账与分配记录的条目编码））：分配记录条目的盘上编码

**落点粒度取 16384 字节（一个 16 KiB 槽）；key = (设备身份 4 字节, 16 KiB 槽号 6 字节)；
一条记录记一个存储单元，另带一个跨度段；value = 分配代或释放代 8 字节，存完整 checkpoint 号。**
**落点释放时条目不删、不点删**（C113（扫描重建时多版单元的现行版本判定无输入） 定案 P4，2026-09-05）：改写成「已释放 + 释放代」——释放代仍写进那 8 字节，已释放标志位借跨度段的最高位，条目留到该落点被重新分配时覆盖。不点删的理由：树按落点排序、代住 value，按代点删要扫全树，而点删所需的按代清单正是崩溃会丢的那份内存态；条目改写与产生这次释放的 COW 在同一次发布里原子生效——分配记录是根下的 COW 树（D22（单元原子性怎么合成） 已定项 3），条目与根同一次发布，释放代 = 那次发布的 checkpoint_txg；崩溃丢掉的是没发布的那个 checkpoint，它里面的释放一条都不留痕、对应的旧版本仍被所选根引用。崩溃后 defer 队列的内存态丢失，接手的是「释放代 ≤ 环里最旧根 txg」这条闸（I-7.4（近 K 代块未被复用） 的注）。「释放」的口径 = 分配器把落点放进 defer 队列那一刻 = 没有任何根（含快照）引用它，被快照引用的落点按 D5（快照 / 空间记账机制） 的 deadlist 纪律进 deadlist 不进 defer、快照销毁时才释放 ⇒ 释放代晚于最后一个引用它的根被销毁的那次发布。清扫准入两支共有的合取 = 不在分配器在飞 overlay 里 ∧ 头可读；有条目的再要求已释放 ∧ 释放代 ≤ 根环最旧根的 checkpoint_txg（由释放的口径，此时环里没有根还引用它；单元属于哪个实例无关，当前实例自己释放的落点也要能清）；孤儿（没有条目）要求头里的写序实例 < 当前实例 ∧ 按实例表的已发布谓词判未发布（当前实例没有行，它的孤儿只能是在飞的写，交给 overlay 那一条）。条目数上界由此从「已分配落点数」变成「曾分配过、尚未被覆盖的落点数」，仍以容量 / 16 KiB 为界；E74（分配记录的条目数与整理开销） 判据 1「条目数恰好等于已分配落点数」在新口径下按定义为假，改成「条目数 == 曾分配过、尚未被覆盖的落点数」后与 E97（记账与分配记录的条目编码） 一起重跑取新的绝对值，今天未跑（C122（分配记录不点删之后的条目数口径））。

| 段 | 宽 | 依据 |
|---|---|---|
| 设备身份 | **4** | D19（块指针的结构与宽度预算） 已定项 4。**同一个坐标系**，不许各定各的（已定项 3 依据第 2 条逐字）|
| 落点 | **6**，编码为 **16 KiB 槽号** | 粒度由 D18（块里携带什么信息） 已定项 9 逼出来（索引节点对齐 16384、大小就是 16 KiB）；E97（记账与分配记录的条目编码） 判据 7 实测：按 32 KiB 单元号编码时 4096 个槽里 **2048 个表达不了**，按 16384 编码时 **0 个**。6 字节槽号寻址 **4 EiB / 设备** |
| 跨度段（含已释放标志位） | **2（初值）** | 一条记录记一个单元，跨度段说它覆盖几个槽。宽度按 D19（块指针的结构与宽度预算） 已定项 3 的「定宽留位」政策取，**理由是政策不是用量**——第一版恒为 1 或 2；**最高位借作已释放标志**（0 = 仍分配、1 = 已释放，2026-09-05 随 C113（扫描重建时多版单元的现行版本判定无输入） 定案），不占表达跨度值的位 |
| 分配代 / 释放代 | **8** | 与 D22（单元原子性怎么合成） 已定项 7 的 `checkpoint_txg` 同宽同值域，语义按跨度段的标志位取其一。E97（记账与分配记录的条目编码） 判据 3 / 8 实测：任何有限模都只是把破 key 序推迟到回绕那一刻，而 1 字节的代按 E44（序号位宽的本机实测与代价） 的 2785 发布/秒 **91 毫秒**就绕完一圈 |

**代价（E97（记账与分配记录的条目编码） 实测，16 TiB / 90% 填充 / 头 58）**：
条目数 **483 183 820**、树高 **4**、这棵树自己占 **442 ppm**。
对照「一条记一个 16 KiB 槽」那条候选：条目数与占容量都是它的 **1.88 倍**（966 367 641 条、830 ppm）。

**用户定案**：先按这个形态落地，写代码时再调整。

⚠️ **占容量那 1.88 倍不是本项的判据**——`.claude/rules/fs-design.md` 明令
「**比谁省不构成任何判据**」。E97（记账与分配记录的条目编码） 把两条候选压到只剩这一个差别，
**它自己判不出高下**，这一格是用户定的。

⚠️ **「一条记录恰好覆盖一个单元」是分配器的不变量，不是编码强制的。**
E97（记账与分配记录的条目编码） 实测证明**「表达得了全部合法起点」与「让半个数据单元不可表示」不可兼得**：
跨度 1 必须永远合法（索引节点就是一个 16 KiB 槽），所以 `(偶数槽, 跨度 1)` 这条记录永远写得出来。
⇒ **欠一条会红的检查**：checker 要判「每条分配记录覆盖的槽数与它所记单元的类别相符」，
落点 [checks-owed.md](../checks-owed.md)。

⚠️ **落点粒度这个数同时进两层冻结**：位置条目在 D15（格式冻结政策） 第 2 层、
分配 keyspace 的 key 在第 3 层，而 D15（格式冻结政策） 逐字要求第 2 层先于第 3 层冻
⇒ **它要当第 2 层的问题看**。异构池（D12（目标介质） 已定项 3）让它不能挂在某一条布局线的
incompat 位上——一个布局 A 的节点里的位置条目会指向布局 B 的设备。**这一格仍欠处置。**
