## D3 空间分配 —— 已定（4 个分项全定）

**1. 不分 data / metadata 两类空间。** 全局统一分配器。

依据：btrfs 的两级分配 + chunk 分类僵化是 ENOSPC 病根
（"`df` 还有几十 G，写文件报没空间"、"删文件也报没空间"）。

**2. 连带承诺：后台整理必须是常驻的、自动的、用户无需知道的。**
不分类意味着碎片化压力全压在一个分配器上，btrfs 靠人手动跑 `balance` 来救，
这是它最大的运维恶名之一。选了不分类就等于承诺自动整理。

**3. 空间预留用准入控制形态，量要小。**
预留不是"划一块地不给用"，而是：任何增加空间占用的操作，进门前先算
"最坏情况下解开自己需要多少"，算不过就拒绝。这样预留量动态贴着实际需求，不白占。

**4. 与 D9（加密）的连锁**：加密开启时，无密钥的一侧**能搬，不能回收**。

- **能搬**：D9（加密）已定项 5 已定（2026-08-26）——把「一个块的物理地址的权威记录点」
  移出加密结构，改为明文的「逻辑身份 → 物理地址」映射层 + 明文反向索引。
  这一条正是为 D3（空间分配）的「常驻、自动、用户无需知道的后台整理」这个硬承诺付的代价。
- **不能回收**：记账是权威态（D21（权威态与派生态的分界））且加密，无密钥侧写不了它。
  ⇒ 「把空间标记为可分配」在锁盘期做不到，见 D9（加密）已定项 7。
- 检测始终可做（指针里有不要密钥的密文校验和）。

**原则**：COW 系统必须保证「释放空间」这个操作本身不需要申请空间。
btrfs 没在设计层保证这点，靠一堆启发式补了十几年还在出问题。

#### 已定项 1（2026-08-31，用户定案）：分配记录逐落点答得出「属不属于现行版本」

**这是「某个落点此刻属不属于现行版本」这个谓词的权威记录点**，
不是聚合量——D5（快照 / 空间记账机制） 已定项 3 那棵记账树装的是
「(统计量, 维度元组, 代) → 完整值」，它答不了单个落点。

谓词由两半合成，两半都已定：

| 半 | 谁给 | 说的是 |
|---|---|---|
| 这个落点分配出去了吗 | **D3（空间分配）** 的分配记录 | 空闲的落点不属于任何版本 |
| 分出去的属不属于**现行**版本 | **D5（快照 / 空间记账机制）** 的 deadlist | 进了 deadlist 的落点只被快照引用，不在活树里 |

**它买到什么**：索引整个丢掉之后，扫盘重建**分得清陈旧副本与现行副本**。
E59（缓冲消息能不能只从单元重算） 实测：只扫单元时同一个 key 的多份可读副本分不出现行值
（分不出的数恰好等于覆写次数），加上这个谓词之后四类消息的分歧**全部归零**。
D11（索引节点要不要留消息缓冲区） 已定项 4「缓冲仍是纯派生态」整个压在这一条上。

⚠️ **代价没有量**：逐落点意味着分配记录的条目数随容量走，而不是随统计维度走。
它与 D3（空间分配）「后台整理常驻」的交互（整理会大批改写落点归属）没有实测。

#### 已定项 2（2026-08-31，用户定案）：墓碑那一笔由准入控制算进最坏情况

D18（块里携带什么信息） 已定项 8 已定「删除要写墓碑单元」⇒ **删除这个操作本身要写盘**，
而 D3（空间分配） 的原则逐字写着「COW 系统必须保证『释放空间』这个操作本身不需要申请空间」。

**解法不是给删除路径开口子，是把那一笔提前到写入那一刻收掉**：
D3（空间分配） 第 3 条的准入控制本来就要求「任何增加空间占用的操作，进门前先算
**最坏情况下解开自己需要多少**」——**墓碑就是「解开自己」的一部分**，计入那个量。

⇒ **删除路径仍然不申请空间**：它要写的那个墓碑，空间在对象写进来的时候就已经算过并留住了。
原则一个字不改，改的是「解开自己需要多少」这个量的算法——它现在含墓碑那一项。

⚠️ **量还没算**：一次删除写几个墓碑、能不能批量摊、盘满时删得动删不动，一个数都没有。
定案定的是**这笔账归谁付**（准入控制，写入时付），不是**这笔账是多少**。
后者要等分配器与准入控制有实现才算得出来。

⚠️ **它把一条现有的坑变紧了**：预留量现在与「将来会不会被删」绑在一起，
而 D3（空间分配） 第 3 条的原意是「预留量动态贴着实际需求，不白占」。
墓碑那一项对**永不删除**的对象是纯浪费——浪费多少，同样没量。

#### 已定项 3（2026-09-01，用户定案）：分配记录住一棵独立 keyspace 的 btree

**已定项 1 定的是谓词（逐落点答得出属不属于现行版本），没定它住哪。** 这一项补上载体：
**独立 keyspace 的 btree，key = 落点（设备身份 + 设备内偏移），value = 分配代。**

**依据**：
- 形态照 D5（快照 / 空间记账机制） 已定项 3 的记账树——同一套 btree 机制，不新开第二种结构；
- key 用落点是已定项 1「逐落点」的直接后果，`(dev, 偏移)` 与 D19（块指针的结构与宽度预算）
  已定项 1 的位置条目同一个坐标系，查一个落点是点查不是扫描；
- 加一棵 keyspace 不是 incompat 改动——D15（格式冻结政策） 已定超级块树表 day-1 做成开放列表，
  判定表把「新增一棵 keyspace」钉死为 **compat**。

**用户口径**：先按这个形态落地，写代码时再调整。

⚠️ **欠一次测量，已立 E74（分配记录的条目数与整理开销）**：已定项 1 自陈
「代价没有量：逐落点意味着分配记录的条目数随容量走，而不是随统计维度走」，
且它与「后台整理常驻」的交互（整理会大批改写落点归属）没有实测。
**载体定了不等于代价知道了**——量出来若不可接受，重开的是已定项 1 的粒度，不是这一项的载体。


### 已定项 4（2026-09-01，用户定案）：准入不等式的权威形式

```
可用 = Σ设备( 容量 − 已分配 − 不可回收 − defer 待释放 ) − 待删占用 − 已承诺预留
```

**它是「任何增加空间占用的操作，进门前先算最坏情况下解开自己需要多少」（D3（空间分配） 第 3 条）的可执行形式。**
此前全仓没有一处把它写全——I-3.4（可用空间扣待删占用） 只说「可用空间统计已扣除待删占用」，
第 3 条只说「先算最坏情况」。

**六项逐项有出处，不是凑出来的**：

| 项 | 为什么在式子里 |
|---|---|
| 容量、**已分配** | I-3.1（已分配统计对得上） 的被审计对象 |
| **不可回收** | zoned 上一个活快照钉住的物理空间是 zone 粒度而引用的块数是块粒度，[invariants.md](../invariants.md) 逐字要求「另立一个不可回收量」 |
| **defer 待释放** | D16（发布语义）：checkpoint C 中产生的释放在 C 发布之前不得进入可分配集合 |
| **待删占用** | I-3.4（可用空间扣待删占用）；D5（快照 / 空间记账机制） 与 D8（核心索引结构） 分批删除定「待删除结构算作活引用」 |
| **已承诺预留** | D3（空间分配） 第 3 条；已定项 2 逐字「墓碑就是解开自己的一部分，计入那个量」 |

⚠️ **前三项按设备求和，后两项不按**——前三项是物理量（一块盘满了不能靠别的盘补），
后两项是全池的承诺量。**这个分界直接决定 D5（快照 / 空间记账机制） 已定项 4 里哪几个统计量要带设备维。**

⚠️ **它解锁了两样**：D5（快照 / 空间记账机制） 已定项 4（统计量有哪几个）的完备性现在可判了——
清单相对这个式子完备即可；[checks-owed.md](../checks-owed.md) C70（跨统计量的和没人盯） 的那条向量等式现在写得出来了。
