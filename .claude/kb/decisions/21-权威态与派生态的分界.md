## D21 权威态与派生态的分界 —— 已定（三条边界已定，两项未定）

**盘上的东西分两类：权威态与派生态。**

| 类 | 有什么 | 性质 |
|---|---|---|
| **权威态** | **单元 + 记账 + 根** | 丢了就丢数据。参与格式冻结，是永久契约 |
| **派生态** | **索引（树）** | 丢了只是慢。**不参与格式冻结** |

依据（2026-08-28 用户定案）：**树是为了快查，而每个单元自带自包含信息**——
所以树是加速结构，不是事实来源。

**这条买到的东西**：

| 现状 | 分界之后 |
|---|---|
| D15（格式冻结政策） 冻结第 2 层（指针字段布局）是永久契约 | 降级为**本地缓存格式**，换一棵完全不同的树不需要兼容 |
| D12（目标介质） 的 N 条线共享一棵树、各自一套布局 | N 条线**各用各的索引结构**，只共享单元格式 |

⇒ **D12（目标介质）「针对某个介质极致优化」落在派生态这一侧比落在布局这一侧干净得多。**

### 派生态没有「换格式」这个操作，只有「重建」

**已定（2026-08-28）：不为索引格式设兼容通道，也不写转换器。**

推导：**权威态的格式按 D20（承重面：单元的原子性与自包含） 就是不该变的那一层**——它变了才叫换格式，而那正是要避免的；
**派生态的格式随便变**，因为它整个可以从单元重建出来。
两侧各自的结论合起来就是：**没有一个「旧格式 → 新格式」的转换问题存在。**

⇒ **「转换器」这个东西不该被造出来。** 造了它就要证明转换的正确性，
而重建只需要证明「从单元能重建出来」和「重建是幂等的」——**后者严格更弱，也更容易验。**

### 救援与迁移是同一条路径，而且可以落到另一条线上

单元自包含 ⇒ 扫一遍全盘就能把内容取出来，**按什么形状重建索引是重建方决定的**。
所以下面三件事在实现上是同一条代码路径：

| 场景 | 做什么 |
|---|---|
| 索引损坏后的救援 | 扫描 → 按本线规则重建索引 |
| 换一棵完全不同的树 | 扫描 → 按新规则重建索引 |
| **迁移到另一条线（另一种介质布局）** | 扫描 → **按目标线的规则重建**（可能连数据布局一起重排） |

⇒ 这条路径是本工程唯一需要向后兼容的地方，而它的兼容面很窄：
**扫描重建路径必须认识历史上出现过的所有单元格式**，仅此一条。
文件系统的正常读写路径**不必**读旧镜像。
**而「认识 N 种单元格式」的成本是 N 个解析器，不是 N 条读路径**——
单元自描述意味着扫描不需要任何锚点：线性扫过去，每个单元自己说明自己是什么。

⚠️ **两条限制，不写下来会被当成「重建万能」**：

1. **扫描能重建索引，重建不出「哪个一致点」。** 扫描找到的是盘上**现存且未被覆盖**的
   全部单元，其中含中断事务留下的那些。挑出「最新且一致的那一组」要靠根
   （D16（发布语义） 的 checkpoint）——**树可以丢，根不能丢。**
2. **加密开启时，自描述住在密文里。** [invariants.md](../invariants.md) I-6.2（明文头字段白名单） 的明文头白名单是
   magic / 格式版本 / flags / nonce 代号 / 长度 / MAC，**不含**自身逻辑地址、generation、
   树 ID、所属对象——而那几样正是扫描重建要读的。
   ⇒ **无密钥不能重建，只能 scrub。** 这与 D9（加密）已定的取舍一致（宁可泄漏面小，
   不把元数据挪到明文），本条把那个取舍落到重建路径上。

**连锁：[checks-owed.md](../checks-owed.md) C10（历史单元格式读不了） 的回归对象要改写。**
C10（历史单元格式读不了） 拦的是「新代码读不了旧镜像却没人发现」——按本条，
要回归的是**扫描重建路径**读得了历史单元格式，并重建出内容摘要一致的结果。

### 单元是可扩展的对象，含开线方的扩展点

**已定（2026-08-28 用户定案）：不追求单元绝对简洁。**
单元预留一段供开线方使用的空间**与一套接口**——形态不是「一段不透明字节」，
而是**扩展点**：开线方可以在里面放一个**指向**，再拿这个 key 去做本工程不理解的事
（例如为自家介质做更快的定位）。本工程允许，并为此预留空间与接口。

依据：存储是当前最便宜的资源，用空间换性能与安全划算；
且这是 D12（目标介质）「谁开的线谁维护」在单元格式里的形态。

**已定（2026-08-28）：扩展点的大小按线声明，不按单元变长。**
每条线在超级块里声明一个值（开线方自己定，可以定 0），上限由本仓定。

三档里取中间那一档的理由：

| 形态 | 开线方 | 代价 |
|---|---|---|
| 全局固定值 | 他要 200 字节而本仓定了 128，只能忍 | 无 |
| **每条线声明一个值** | **他自己定** | 几乎无：线内几何仍然一致 |
| 每个单元各自变长 | 最灵活 | 每单元多一个长度字段；**几何不再一致**，扫描重建与记账都要按单元算 |

⇒ 中间那档从开线方看是可伸缩的，从格式几何看是固定的。
第三档只在「同一条线里不同单元需要不同大小」时才有意义，**那个需求目前不存在**。

**已定：上限取固定字节数，不按单元大小取比例。**
理由是语义——它承载的是**每对象的语义字段，与单元多大无关**。
按比例定会在大单元上失控：1% 在 128 KiB 单元上是 **1310 字节**，
是本工程自己全部单元元数据（108 字节）的 **12 倍**。
固定 128 字节则是 4 KiB 单元上 3.1%、128 KiB 单元上 0.098%——
而 4 KiB 上占比高是「4 KiB 单元对谁都贵」的表现（见本决策「单元元数据的记账：本工程与三个年代逐字节对照」），不是这一项的问题。
**具体取多少仍未定**，见未定项 2。

**五条硬约束。** 前三条对「不透明字节」就成立；
**后两条是「里面可以放指向」这个形态独有的，缺了它们扩展点会直接破坏记账与生命周期**：

1. **必须落在校验 / 认证覆盖范围之内。** 落在外面 ⇒ 那一段是损坏盲区，
   且加密开启时是未认证字节，直接是攻击面（D9（加密）的 AEAD 边界不许开洞）。
2. **checker 不许对它的内容有任何判定。** 它对本工程是不透明的。
3. **大小必须由格式声明**（按本节已定：在该线的超级块里）。
   通用工具（scrub、扫描重建、救援）要能跳过它。
4. **扩展点里的指向，其目标空间必须走本工程的分配与记账。**
   开线方不许自己划一块盘外空间——`.claude/rules/fs-design.md` 第一格已定
   「运行时决策路径不许遍历」，ENOSPC 准入要在进门前算最坏情况，
   **一块不在记账里的空间会让那个数直接失效**。
   ⇒ 目标空间从一个**显式配额**分配，配额在提交时增量维护；
   checker 要能验「扩展点指向的范围确实被记为已分配」，**即使它不理解内容**。
5. **扩展点里的指向不许指向核心层的对象。** 只能指向该扩展点自己配额内的空间。
   ⚠️ **这条最硬**：允许指向核心对象 ⇒ 那个对象多了一条核心层不知道的引用 ⇒
   D5（快照 / 空间记账机制） 的 `birth`/`death` 记账当场失效（它算的是「从根可达」，而这条引用不在任何根下）。
   **⇒ 扩展点是一个封闭的子图，不是一条通用引用。**

⚠️ **生命周期绑定宿主单元**：宿主单元死 ⇒ 其扩展点配额内的空间随之释放。
不绑定则核心层无从知道何时该回收，那就是确定的泄漏。

### 单元元数据的记账：本工程与三个年代逐字节对照

**口径**：只算「为了管理一个单元而多付的字节」——不含 inode、目录项、空闲空间、反向索引。
常量全部现查逐字核实（2026-08-28）：
`btrfs_header` = 32+16+8+8+16+8+8+4+1 = **101**（`BTRFS_CSUM_SIZE 32`、`BTRFS_FSID_SIZE 16`
分别在 `include/uapi/linux/btrfs_tree.h:376` 与 `include/uapi/linux/btrfs.h:62`）；
`btrfs_file_extent_item` = 53；`btrfs_item` = 25；`SPA_BLKPTRSHIFT 7` ⇒ ZFS blkptr **128 字节**；
`EXT4_GOOD_OLD_INODE_SIZE 128`。本工程那一行是**提议值，尚未定案**。

| 系统 | 4 KiB 单元 | 128 KiB 单元 |
|---|---|---|
| ext2/ext3（2001） | 4.1 B（0.101%） | 132.0 B（0.101%） |
| ext4（2008，有 extent） | 12.1 B（0.296%） | 16.0 B（0.012%） |
| btrfs（2007） | 82.5 B（2.014%） | 207.3 B（0.158%） |
| ZFS（2005） | 128.0 B（3.125%） | 128.0 B（0.098%） |
| **本工程（2 副本）** | 108.0 B（2.637%） | **108.0 B（0.082%）** |
| 本工程（4+2 条带） | 152.0 B（3.711%） | 152.0 B（0.116%） |

**本工程那 108 字节的去向**：单元头（自描述）55 + 指针头部（MAC 16 + nonce 12 +
算法类型 1 + extent 偏移 2）31 + 位置条目 ×2（dev 1 + 物理偏移 6 + 密文校验和 4）22。

**三条结论**：

1. **「早期文件系统更节省」不成立。** ext2 省的是自描述（数据块 0 字节），
   但它**没有 extent**，128 KiB 要 32 个 4 字节块号 = 132 字节——
   **比本工程带全套完整性与加密的 108 字节还多。**
   ⇒ 拉开差距的从来不是「放不放维护数据」，是**引用的粒度**。
   而 ext2 那 0.101% 买到的是零校验和、零自描述、无 COW、无快照、无认证。
2. **真正的分水岭是单元大小，不是年代。** 所有带校验和的方案在 4 KiB 单元上是 2.0–3.7%，
   在 128 KiB 单元上是 0.07–0.16%，**差 30 倍**。
   ⚠️ 与 [experiments.md](../experiments.md) E6（加密算法选型） 是两条独立理由指向同一结论：
   E6（加密算法选型） 从吞吐侧量到加密/校验单元的增益在 16 KiB 之后饱和。
3. **本工程在 128 KiB 单元上比 ZFS 省、比 btrfs 省一半。**
   「我们很奢侈」这个前提在数字上不成立。

### 自包含把反向映射的一半变成 O(1)

单元自带「我属于谁」⇒ **「这个物理位置上是哪个对象」只需读那一个单元，不需要一棵反向索引树。**

⚠️ **但只有一半。** 共享（快照 / reflink / 去重）之下，一个单元可以有**多个**引用者，
而定长的单元头列不下。**⇒ 反向索引仍然要，但它的职责收窄了**：
从「回答所有反向查询」收窄到「回答被共享的那部分」。
这对 D1（数据可移动性 / 反向索引） 是一次减负，具体形态未定。

### 未定项

1. **反向索引在权威态还是派生态。** 若派生 ⇒ balance / GC 在索引重建完之前不能跑；
   若权威 ⇒ 要跟着提交增量维护。

   ⚠️ **本项不阻塞第一行事务层代码（2026-08-29 对抗验证判定）**，依据是本决策自己那一节
   「自包含把反向映射的一半变成 O(1)」：反向索引的**全部剩余职责**是「回答被共享的那部分」。
   而 CLAUDE.md 定义的第一个可运行目标是「只能分配块、写入、提交，**没有目录、没有树**」
   ⇒ 无快照、无 reflink、无去重 ⇒ **一个共享单元都不存在** ⇒ 第一个事务写入的反向索引条目数为 **0**
   ⇒ 两个答案写出的字节逐字节相同（权威要增量维护的是空集，派生要重建的也是空集）。
   ⚠️ **「若权威则要参与格式冻结、mkfs 就得造出这棵树」这条反驳不成立**：
   D15（格式冻结政策） 已定超级块树表 day-1 做成开放列表，其判定表把「新增一棵 keyspace」钉死为 **compat**。
   ⇒ **本项阻塞的是第一个共享引用（第一个快照 / reflink），不是第一个事务。**⚠️ 与 `.claude/rules/fs-design.md` 第一格直接相关：
   记账**已定**是权威态（「不是慢，是在被问到的那一刻没有答案」），反向索引这一格没有答案。
2. **自定义空间的固定字节上限取多少**（正文举例 128 字节，未定案）。
   ⚠️ 此前这一项写作「**比例**上限取多少，以及每单元一份还是每线一份」，
   而本决策正文已定「扩展点大小**按线在超级块里声明**」与「上限取**固定字节数**，
   不按单元大小取比例」——那两问都已答，只剩取值。
