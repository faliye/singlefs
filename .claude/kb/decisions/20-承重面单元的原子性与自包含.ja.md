## D20 (荷重受け面: ユニットの原子性と自己完結性) — 確定

[中文](20-承重面单元的原子性与自包含.md) · [English](20-承重面单元的原子性与自包含.en.md) · **日本語**

D20 (荷重受け面: ユニットの原子性と自己完結性) は本プロジェクトの荷重受け面がどの層にあり、その層が何を満たすべきかを定める：ユニットの**原子性**と**自己完結性**である。管轄するのはこれら2本の軸の位置づけ、原子幅をどう分類するか、誰が保証するか、違反時にどう検出するか。対象外とする事項：具体的なフィールドに何を含めるか・幅はいくらかは D18 (ブロックに含める情報)；原子性を合成する2つの軸の手法は D22 (ユニット原子性の合成手法)；チェックサムの配置位置は D4 (チェックサム位置)；発行順序は D16 (パブリッシュセマンティクス) に属する。上位構造——インデックス形態、スナップショットモデル、振り分け戦略、メディアレイアウト——はすべて変更可能であるが、荷重受け面は変更できない。

### 確定項目

#### 確定項目 1：荷重受け面を「ユニット」層に設定

**確定内容**：本プロジェクトの荷重受け面は**ユニット**層である——その**原子性**、およびその**自己完結性**。上位構造（インデックス形態、スナップショットモデル、振り分け戦略、メディアレイアウト）はすべて変更可能であるが、荷重受け面は変更できない。

独立した2つの理由：

- **外挿可能性**：フォーマットは長期にわたり存続する必要があり、長期存続する部分は当時どのツリーを選択したかではなく、**最小ユニットのセマンティクスに曖昧さを残さなかったか否か**である。
- **メカニズム**（前項に依存しない）：自己完結性と原子性を兼ね備えたユニットにより、「全ディスクスキャン再構築」が物理的に可能となる——任意のユニットを拾い上げるだけで「私は誰か、誰に属しているか、何世代目か」に回答でき、かつ完全な旧版か完全な新版のいずれかであって、第3の状態は存在しない。**再構築能力はすべての上位構造に共通する最終防衛線である**：上位層が何に置き換わろうとも、この防衛線は維持される。これは `.claude/rules/fs-design.md` の「メタデータブロックは自己記述的でなければならない」の拡張であり、「メタデータブロック」から「ユニット」へと拡張し、原子性の軸を追加したものである。

**射程**：どの層が荷重を受け、その層が何を満たすべきかを定めるものであり、個々のフィールドや合成メカニズムを定めるものではない。「ユニット」という形態自体の射程は `.claude/rules/fs-design.md` の「ユニットでないディスク上空間に対し、コア層はゼロカバレッジである」に規定されている：ユニットとして構成されないディスク上空間は、チェックサム、スキャン再構築の領有判定、checker の巡回走査、不変条件の対象外に自動的から外れる。

**根拠**：実験なし：荷重受け面をどの層に設定するかを定めるものであり、定量可能な数値は存在しない；2つの理由のうち一方は外挿可能性の判断、もう一方はメカニズムの演繹（再構築能力が求めるものがまさに自己完結性と原子性の2つである）である。ユーザー確定、原文は変更履歴に記録。

**未済の検査**：なし。

#### 確定項目 2：自己記述はメタデータブロックだけでなくデータブロックも対象とする

**確定内容**：[invariants/01-块自描述.md](../../../crates/singlefs-checker/invariants/01-块自描述.md) の I-1 (ブロック自己記述) 各条項が対象とするのは「任意の**ユニット**」であり、「任意のメタデータブロック」ではない——確定項目 1 に従い、「ユニット」はメタデータとデータを区別しない。データブロックがどの程度まで満たすべきかは D18 (ブロックに含める情報) 確定項目 3 が決定（平文、かつむしろ大きめに記述：各データユニットは平文の自己記述ヘッダを保持、5つ組で計 33 バイト；`locality_id` は追加しない）。

**射程**：本項目は「データユニットも自己の同一性を証明しなければならない」ことのみを要求し、フィールド集合や幅は規定しない——それらは D18 (ブロックに含める情報) 確定項目 3 / 7 に属する。自己証明ユニット（journal レコード / ルートスロット / システム構成スロット / タイプ 4 インスタンス表ユニット）は I-1.1 (ブロックヘッダ自己記述論理アドレス) および I-1.3 (ブロックヘッダツリー ID 一致) の明示的な免除対象であり、それらの自己証明規律には別途着地点がある。

**根拠**：実験なし：本項目は確定項目 1 の「メタデータとデータを区別しない」を不変条件の主語に反映させたものに過ぎず、計量は D18 (ブロックに含める情報) 確定項目 3 側にある。メイン agent およびユーザー確定、原文は変更履歴に記録。

**未済の検査**：なし。

#### 確定項目 3：「原子性」は判定可能な3つの問いとして記述されなければならない

**確定内容**：「原子性」を形容詞として用いることは禁じられ、少なくとも3つの問いに答えなければならない。1つでも欠ければ D20 (荷重受け面: ユニットの原子性と自己完結性) はまだ着地していない：

| 問い | どこで答えるか |
|---|---|
| 1. 原子幅はいくらか | 確定項目 4（ユニット種別ごとに個別に規定）および確定項目 7（デバイス側は 512 であり依存不可） |
| 2. 誰が保証するか | 確定項目 4（親ポインタを持つユニットは親ポインタチェックサム + 発行順序に依存；自己証明ユニットはコア層が合成） |
| 3. 違反時にどう検出するか | 確定項目 6（クラッシュポイント再生 + checker） |

**射程**：3つの問いは D20 (荷重受け面: ユニットの原子性と自己完結性) 自身の着地チェックリストであり、第3の問いの検査はまだ対象コードが存在しない（確定項目 6）；3つの問いに答えたことは、3つの問いを検証済みであることを意味しない；「いかに合成するか」はここでは回答せず、直交する2軸は D22 (ユニット原子性の合成手法) 確定項目 19 / 20 / 21 に属する。

**根拠**：実験なし：D20 (荷重受け面: ユニットの原子性と自己完結性) がどの問いに答えるべきかを定めるものであり、定量可能な数値は存在しない；「形容詞で判定基準を代用してはならない」という規律の荷重受け面における形態である。メイン agent 確定。

**未済の検査**：C16 (パイプラインが障害モデル例外を宣言)。

#### 確定項目 4：原子幅はユニット種別ごとに個別に規定、1文にまとめると誤りとなる

**確定内容**：2つの問いへの回答はユニット種別ごとに個別に与えられなければならない。

| ユニット種別 | 第1の問い：原子幅はいくらか | 第2の問い：誰が保証するか |
|---|---|---|
| **親ポインタを持つユニット**（多数派） | **いかなる幅にも依存しない。** 断裂粒度が 512、4 KiB、またはブロック全体であるかは、親ポインタチェックサムの論証に何の影響も与えない（D22 (ユニット原子性の合成手法) 確定項目 19 / 確定項目 20） | コア層、D4 (チェックサム位置) の親ポインタ内蔵チェックサム + D16 (パブリッシュセマンティクス) の発行順序を使用 |
| **自己証明ユニット**（ルートスロット、journal レコードヘッダ、**システム構成スロット**） | **実行時にプローブされた `physical_block_size` に等しく、ハードコードは禁止。** この規定は**断裂判定の分解能**を述べており、構造サイズではない。D23 (ジャーナルの役割と形式) 確定項目 4 の明文禁止規定を参照 | コア層が合成（ユニット全体チェックサム + 世代番号 + スロットローテーション、D22 (ユニット原子性の合成手法) 確定項目 21 参照）；デバイス宣言は上限パラメータとしてのみ機能 |

**「原子幅はフォーマット定数である」という言説は誤りであり**、2つのセルを1文に圧縮している：多数派のユニットは幅を知る必要すら全くない；知る必要がある小数のセルも、数値をフォーマットに溶接することを明確に禁じられている。

**デバイス宣言が利用可能か否かは2つのケースに分かれ、単純な1文では済まない**（`drivers/nvme/host/core.c` の `nvme_configure_atomic_write()` を実地確認）：

```c
if ((id->nsfeat & NVME_NS_FEAT_ATOMICS) && id->nawupf) {
        atomic_bs = (1 + le16_to_cpu(id->nawupf)) * bs;
```

| ケース | 識別可能か | 利用可能か |
|---|---|---|
| ATOMICS 機能ビットがない、または `nawupf == 0` | **識別不能**——`atomic_bs` は論理ブロックに帰着し、「何も宣言されていない」と同形 | 不可 |
| ATOMICS ビットがあり、かつ `nawupf > 0` | **厳密に識別可能**、`atomic_bs = (1+nawupf) × bs > bs` | 可能、ただし**上限パラメータとしてのみ** |

**射程**：自己証明ユニットの行が規定しているのは**断裂判定の分解能**であり、**構造サイズ**ではない——システム構成スロットの構造サイズはフォーマット定数 4096（登録名 `SYSTEM_CONFIGURATION_SLOT_BYTES`、D22 (ユニット原子性の合成手法) 確定項目 2）であり、ルートスロット幅こそが「マウント時にプローブされた `physical_block_size` に等しい」とされる。信頼できる上限を得たとしても新たな安全性が得られるわけではない：検出メカニズム自体は幅に依存せず、自己証明ユニットにおけるアライメントコストにのみ影響する。⚠️ 本項は C212 (固定構造の書き込みが io_min 未満) を解決しない：`io_min` が `physical_block_size` を超えるデバイスでは、システム構成スロットの書き込みは依然として `io_min` 未満の書き込みであり、D2 (RAID ストライプポリシー) 確定項目 16 との衝突は従前のまま残る。

**根拠**：実験なし：2つの問いへの回答は「親ポインタチェックサムの論証が幅を知る必要があるか否か」から演繹されたものであり、定量可能な数値は存在しない；デバイス宣言の2つのケースはカーネルソースコードの行ごと実地確認により確認、出所は `drivers/nvme/host/core.c` の `nvme_configure_atomic_write()`、本プロジェクトでの検証は未実施。システム構成スロットがこのセルに含まれる列挙はユーザー確定（規則自体は1文字も変更なし）、原文は変更履歴に記録。

**未済の検査**：C212 (固定構造の書き込みが io_min 未満)。

#### 確定項目 5：コア層が何を合成するか——7つのメカニズム、それぞれの死角を明記

**確定内容**：

| メカニズム | 検出可能 | 検出不能 |
|---|---|---|
| 親ポインタ内蔵チェックサム（D4 (チェックサム位置)）+ 発行順序（D16 (パブリッシュセマンティクス)） | 任意粒度の断裂、ゴースト書き込み、ビット反転、子ブロックの書き込み消失 | 親自身の書き込み消失（祖父母へ再帰）；ルート |
| ユニット全体チェックサム | ユニットのバイト列不整合 | **完全な陳腐化ユニット**；ビット幅に応じた検出漏れ |
| 世代番号 / `jsn` かつ実際に検査 | 完全な陳腐化ユニット；シーケンスの欠落 | **先頭が書き込まれ末尾が未書き込み**——ヘッダ内の番号は新しい |
| スロットローテーション + 全検証後の最新選択 | 唯一のレプリカが断裂した場合の証拠喪失 | ロールバック深度（ブロック再利用遅延 K により制限） |
| per-sector 刻印（D22 (ユニット原子性の合成手法) 軸 ②、現行では不採用） | 陳腐化セクタの**確定的**検出；断裂**位置** | セクタ内容の破損；全レコードが陳腐化 |
| 処理中レコード数の上限 | ウィンドウ外の検証失敗を断裂ではなく破損と判定 | —— |
| 書き込み側がマッピングユニット未満の書き込みを発行しない | デバイス内部の RMW による隣接領域破損を**予防**、何も検出しない | —— |

⚠️ **ユニット全体チェックサムと世代番号は単独では完結せず、対にしなければならない**：前者は陳腐化を見落とし、後者は頭尾の不揃いを見落とす。

**射程**：本表はメカニズムと死角を列挙するものであり、どれを採用すべきかを判定するものではない——per-sector 刻印を採用するか否かは D22 (ユニット原子性の合成手法) 確定項目 21 に属する（現行では不採用）。D22 (ユニット原子性の合成手法) がこれを否決した際は検出漏れ率という単一の次元のみを比較したが、刻印は**アライメント免除**ももたらす（判定分解能がセクタ単位であれば、複数レコードが同一の原子ユニットに詰め込まれても断裂を判定可能であるが、ユニット全体チェックサムでは先頭以外判定できない）；その否決理由の比較対象が不完全であった事実は既に D22 (ユニット原子性の合成手法) 確定項目 21 に記録されており、再開の可否は D22 (ユニット原子性の合成手法) に属し、本項目は記録にとどめる。

**根拠**：

- E23 (journal 幾何)：per-sector 刻印がもたらす第3の利点はアライメント免除であり、そのアライメントコストは 4Kn 上で 29.3 倍である——7つのメカニズム表における該当行の利得は検出漏れ率の1次元にとどまらない。
- 三者論証：順推論側の担当が「原子幅」をデバイス宣言幅と判定幅に分解し7つのメカニズムの死角表を提示、2つの非順推論側の担当がデバイス宣言に関して独立に収束、メイン agent がカーネルソースを精査した上で採用・絞り込み；経緯は変更履歴に記録。

**未済の検査**：C16 (パイプラインが障害モデル例外を宣言)。

#### 確定項目 6：違反時にどう検出するか——クラッシュポイント再生 + checker

**確定内容**：第3の問いの着地点は**クラッシュポイント再生 + checker** である。両者とも整備済み（ゲート checker-tier-crash-point-replay、`crates/singlefs-checker`）であるが、クラッシュポイント再生は本プロジェクト自身の単一パイプラインのみを記録し、完全書き込み単位で列挙、断裂は「未永続化」に統合されている（D13 (検証ルート) 確定項目 4）=> パイプラインが宣言する種類の「障害原子性幅 / 断裂 / 並べ替え」は依然として**ゼロカバレッジ**である。

**射程**：ローカルホスト上でも断裂を再現できない（`dm-flakey` は `drop_writes` / `error_writes` / `corrupt_bio_byte` のみ）=> この問いは第2のパイプラインと断裂注入が整うまで検証できない。「着地点が定まった」ことは「検証済みである」ことを意味しない。

**根拠**：実験なし：この問いをどの2つのハーネスに委ねるかを定めるものであり、定量可能な数値は存在しない；両ハーネスそれぞれの識別力は D13 (検証ルート) 側にあり、断裂類型の注入手段はまだ存在しない。メイン agent 確定。

**未済の検査**：C16 (パイプラインが障害モデル例外を宣言)。

#### 確定項目 7：デバイス側の原子幅は 512 であり、依存不可

**確定内容**：**本プロジェクトは 512 バイトを超える原子性を仮定できず、512 すら「高確率で成立する」とみなすにとどまる。ユニットの原子性は自前で合成しなければならない。**

字句ごとの実地確認により確認された5つの事実：

| # | 事実 | 出所 |
|---|---|---|
| 1 | ローカル NVMe：`atomic_write_unit_min = atomic_write_unit_max = logical_block_size = physical_block_size = 512` | `/sys/block/nvme0n1/queue/` 実地読み取り |
| 2 | **Linux 上で `physical_block_size` は既に「デバイスが約束する停電時原子幅」である** | `drivers/nvme/host/core.c`：`lim->physical_block_size = min(phys_bs, atomic_bs);` 直前のコメント原文「Linux filesystems assume writing a single physical block is an atomic operation. Hence limit the physical block size to the value of the Atomic Write Unit **Power Fail** parameter.」 |
| 3 | カーネルは Power Fail 変種（`AWUPF`/`NAWUPF`）のみを認識し、`AWUN`/`NAWUN` への**参照はゼロ** | `nvme_configure_atomic_write()` |
| 4 | **「デバイスが 1 ブロックを宣言」と「デバイスが何も宣言しない」は区別不能** | `drivers/nvme/host/core.c` の `nvme_configure_atomic_write()`：デバイスが未宣言の場合 `atomic_bs = (1 + ns->ctrl->subsys->awupf) * bs` を通り、`awupf == 0` => `atomic_bs = bs`、かつ `lim->features \|= BLK_FEAT_ATOMIC_WRITES` が**無条件実行**され、「未宣言なら該当 feature を立てない」分岐は存在しない |
| 5 | **ブロック層は「bio が断裂しない」と約束したことはない** | `Documentation/ABI/stable/sysfs-block` の4つの `atomic_write_*` エントリに crash / power loss は**1箇所も出現しない**；`Documentation/block/writeback_cache_control.rst`（95 行）の**全文に atomic / torn / tear は存在しない**——`REQ_PREFLUSH`/`REQ_FUA` が管轄するのは永続化の時系列順序である |

**現役実装の反証——すべて自前で断裂検出を合成しており、デバイスに依存する実装は皆無**（外部実装は反証およびメカニズムの提示にすぎず、本プロジェクトでの検証は未実施）：

| 実装 | メカニズム |
|---|---|
| **ZFS ルート** | 4 ラベル × 128K uberblock リング；スロット番号 = `ub_txg % (VDEV_UBERBLOCK_COUNT − m)`（**ローテーション、前世代を上書きしない**；`m` は複数ホスト保護 MMP が消費するスロット数）；SHA-256 は**ブロック末尾に内蔵**、verifier は当該ブロック自身の物理オフセット；読み取り時は全スロットを走査し `txg → timestamp` で最新を選択；偶数ラベル → uberblock → 奇数ラベルの3段階フラッシュ |
| **ZFS 通常ブロック** | 親ポインタ内にチェックサム；断裂 => 不一致 => レプリカにより修復 |
| **btrfs ノード** | `csum` が `[32, nodesize)` をカバー；**第2の独立ゲート**：親ポインタの transid とノードヘッダの generation を突き合わせ；現行トランザクション内で解放されたブロックは**ピン留めされ再利用されない** |
| **XFS ログ** | `xlog_pack_data()`：**各 512 バイトスロットの最初の `__be32` を cycle_lsn で上書きし、元の値はレコードヘッダの `h_cycle_data[i]` に保存**、リカバリ時に復元；別途レコード全体の CRC あり。記述原文：「Storage without sector atomicity guarantees can result in torn writes… **Our only means to detect this scenario is via CRC verification.**」 |
| **jbd2** | commit block ブロック全体の csum + `REQ_PREFLUSH\|REQ_FUA` による順序付け；別途「ヘッダのみ有効、残余はゼロ」を許容する `verify_partial` あり |

2つの例外はいずれも同一の結論を指し示している：唯一明文でデバイス依存を主張する ZFS `vdev_label.c` の記述「the disk does not do single-sector overwrites atomically (**even though it is required to**)」は——規模が**単一セクタ 512** であり、かつ ZFS は依然として**スロット切り替え**によりこれを回避している；唯一真にデバイスの >512 原子性保証を享受しているのは XFS の `RWF_ATOMIC` による**ユーザーデータ**直接書き込みであり、かつ純ソフトウェアのコピーオンライトフォールバック（`-ENOPROTOOPT` => COW パスへ切り替え）を備えており、**XFS 自身のログとメタデータはこのパスを1バイトも通らない**。

**射程**：⚠️ **「デバイスが新しい」ことは「原子書き込み幅が大きい」ことを意味しない。** NVMe の原子書き込みユニットはデバイス自身が宣言する `AWUN` / `NAWUPF` に依存し、未宣言であれば存在しないのと同義である。旧デバイスとの互換性を放棄して得られるのは「4 KiB 物理セクタを仮定可能」「FLUSH/FUA がブロック層で合成されると仮定可能」「並行コミットを仮定可能」であり——**原子書き込み幅は得られない**。ZFS `vdev_label.c` の記述は D20 (荷重受け面: ユニットの原子性と自己完結性) の以前の記録からの引用であり、ローカルホスト上に OpenZFS ソースがなく、独立した検証は不可。

**根拠**：実験なし：5つの事実はカーネルソースコードと sysfs の字句通りの実地確認から得られた観察であり、本プロジェクトで計測された数値ではない；現役実装の表は `.claude/singlefs-ai-sop/rules/evidence-discipline.md` の「他プロジェクトの手法は手がかりであり根拠ではない」に従い、反証およびメカニズムとしてのみ扱う——立証責任を「デバイス依存」側に課すものであり、積極的証拠を構成するものではない。メイン agent 確定、2つの独立経路 + 自己検証、経緯は変更履歴に記録。

**未済の検査**：C16 (パイプラインが障害モデル例外を宣言)。
