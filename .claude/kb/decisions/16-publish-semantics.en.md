## D16 (Publish Semantics) —— Settled

[中文](16-发布语义.md) · **English** · [日本語](16-パブリッシュセマンティクス.ja.md)

D16 (Publish Semantics) governs the publish slot: when a new root is published, in what persistence ordering a publish lands on disk, which number the publication counter is, when this batch of releases returns to the allocatable set, how the first root of a new instance first covers two disks, whether an empty publish writes units, and what the journal record format counts as in the D15 (Format Freeze Policy) freeze layering. Out of scope: journal record fields, ring geometry, and replay prefixes are in D23 (Journal Role & Format); root ring parameters, root record, and system configuration field tables are in D22 (Synthesizing Unit Atomicity); snapshot accounting model and lifetime boundary tables are in D5 (Snapshot / Space Accounting Mechanism) and D6 (Snapshot Implementation Model); acceptance inequalities and mount commitment bounds are in D3 (Space Allocation) and D28 (Mount-Time Commitments); memory ordering within a publish event is in `litmus/commit-publish.litmus`, which nails down write block content -> `smp_wmb` -> write generation, making no mention of frequency.

**How "non-empty" is recognized on disk**: A valid root is non-empty <=> root pointers of user-visible trees in its tree table (inode tree, extent tree, and all snapshot trees: Code 14 snapshot inode root, Code 15 snapshot extent root, D8 (Core Index Structure) settled item 9) differ from those in the tree table of its preceding valid root (sorted by txg; valid = valid per instance table /\ txg >= current F); publishes creating snapshots count as non-empty. Comparison targets entries of these types in tree tables, not placements of tree table units themselves — every publish (including empty publishes) rewrites tree table units (`crates/singlefs-core/src/transaction.rs`), so comparing placements would treat all empty publishes as non-empty. **Deduplication when counting "Nth newest non-empty valid root" and "4 distinct states"**: Counting from newest to oldest, a non-empty root is counted only when its (inode tree root pointer, extent tree root pointer, all snapshot tree root pointers) differs from every newer root already counted — new roots issued by administrator rollback differ from their immediate predecessor root, counting as non-empty per "How 'non-empty' is recognized on disk", but share state with an earlier root; without deduplication, identical states would be counted twice (Round 2 X7: after bouncing rollbacks, only 2 distinct states remained by content). Reverse direction merely holds F until the 4th state's root departs the root ring.

**Modifies new-pool file creation bytes: Yes**: Root record adds F 8 bytes; in new-pool file creation, F is always 0 (fewer than 4 non-empty valid roots at mkfs and first publish, ceiling takes oldest valid root txg 0). System configuration adds F 8 bytes, written as 0 in new-pool file creation (D22 (Synthesizing Unit Atomicity) settled item 9).

#### Settled Item 5: Values for `T_time` and `T_dirty`, Loss Window Measurement Basis

**Implementation boundary**: fields encode the defaults of 5000 ms and 2 GiB. Runtime configuration has no mount-time setting entry point, and parsing does not restore this adjustable state; threshold-driven publication, effective-value clamping and out-of-range warnings are not connected. The loss-window formula is a design commitment conditional on those mechanisms and their prerequisites, not a verified runtime guarantee of the current synchronous API.

**Settlement**: `T_time` defaults to 5 s, taking upper bound of feasible interval [200 ms, 5 s] — default loss window is 5 seconds; smaller values merely diminish amortization without buying extra safety, as the 5 seconds itself bounds data loss. **`T_time` is user-configurable without restriction**: mount-time value overrides and writes back to on-disk field; exceeding [200 ms, 5 s] produces warnings without rejection (user 2026-09-20). `T_dirty` = 2 GiB (initial value, tuned during coding); independent of loss window — under `\/` rule, time branch guarantees window, while `T_dirty` governs **volume**: the dirty byte count is the journal bytes that the pending changes will write (user settlement 2026-10-26), the same dimension as min(field, ring_length / F); changes touching only metadata count too, and K overwrites of one unit within a batch count the records of every change, K times, without folding. **`T_dirty` is tunable, not format constant**: field in system configuration is format, value inside is not. **Clamped again at mount**: effective `T_dirty` = min(system configuration field, ring_length / F); ring length is mkfs parameter (default 768 MiB, constrained to ring <= device capacity / 4), so "whether ring accommodates `F *` worst-case consumption" is guaranteed by depressing dirty budget at mount rather than mkfs lower bounds; under default ring, effective value = min(2 GiB, 256 MiB) = **256 MiB**, system configuration field remaining 2 GiB untouched.

**Loss window measurement basis**: Taking number = moment transaction assigned to a checkpoint; checkpoint slicing closes membership only — post-trigger transactions are excluded, assigned transactions write respective units, publish phase waits for all units to land (any COW checkpoint waits for slowest I/O, ZFS txg sync waiting for slowest vdev, unverified in this project). Transaction slicing discipline is one transaction per unit. For number acquisition, write requests slice by unit into transactions taking numbers individually; a transaction writes at most one data unit of user data; **transactions sliced from same request take numbers in ascending order of unit keys** (commit path records "inversions between number order and key order within same request", non-zero flagging red). Unit write retry budget is wall-clock T_retry (named tunable parameter, not format constant; exhaustion triggers instance switch or read-only transition per failure nature, D23 (Journal Role & Format) settled item 14 — simultaneously loss window increment, mount-time switch predicate, and time baseline for consecutive switch counting). **Thus crash loss is at most T_time + P + d + queueing time + N_switch * (T_retry + T_redo), not exactly 5 seconds** — P is the period at which the caller polls `publish_when_due`, d is the duration of one publish, and the queueing time is the duration of the call queued before this check on the caller's thread (verdict `research/prompts/m4-publish-trigger-r1-main-verification.md` Section 2, cell "the time branch"); in milestone four the polling period P and the queueing time are the caller's responsibility, and the clause only names them; single mount permits N_switch switches, each waiting out T_retry before redoing in-flight checkpoint (T_redo), while checkpoint open during redo cannot publish, accumulating writes. #### Settled Item 10: Publish Granularity Batches Writes, Not Once Per Transaction

**Implementation boundary**: a sequential-write request can already be split into per-unit transactions handled in one publication; the session still publishes synchronously for each user change. Batching within one request does not implement dirty-node accumulation across requests or timed publication, and does not imply that every transaction publishes its own root.

**Settlement**: Batches dirty nodes (or reaches timeout) before publishing a root, rather than publishing once per transaction. Session entry points: `accept` takes one change into the pending set; `publish_when_due(now)` is called periodically by the caller and publishes once the trigger holds; `publish_pending_now` drains immediately; the original `publish_user_change` keeps its meaning and drains the pending set before doing its own change. Data writes can be merged: writes to the same inode fold and inode creations add up; unlink, truncation, snapshot creation and deletion, compaction, rollback and unmount are barriers that drain the pending set on entry and publish alone. On entry `accept` first runs the combined acceptance and record-count pre-check for the batch, and if it fails refuses before any read or write, never after returning success; after a publish write fails and the session freezes, `accept` refuses before any read or write.

**Scope**: Settles frequency, not ordering within publish event — governed by `litmus/commit-publish.litmus`, which nails down write block content -> `smp_wmb` -> write generation, making no mention of frequency. Two known corner cases:

- **Net cost distribution**: Format side virtually zero (journal required regardless), verification side substantial — intermediate state semantics rewrite (settled item 12), second replay implementation (settled items 4 and 13), plus coarsened D13 (Verification Route) "Merkle root chain differential": one generation root packs mutations from K transactions, degrading localization precision from "which transaction" to "which checkpoint", with D13 (Verification Route) specifying localization cost as genuine cost of full run tier.
- **Publish semantics govern traversal counts**: Per-transaction root publish => K batches traverse K times; checkpoint => K batches in same window traverse roughly once, each batch leaving small sequential journal record => metadata write amplification for batched large deletions drops from `K * M * H` to `checkpoint_count * M * H`.

**Evidence**:

- No experiment: Settlement rests on two independent rationales, lacking quantifiable metrics at the time. (1) Naturally compatible with D5 (Snapshot / Space Accounting Mechanism) ZFS birth txg model — ZFS txg is inherently a checkpoint (`zfs_txg_timeout` default 5 seconds, or accumulating dirty volume), batching operations and updating uberblock once at txg close; adopting checkpoint eliminates birth txg numbering granularity issues, matching deadlist comparison granularity without recalculation (unverified in this project). (2) **Root is ultimate witness of lost writes**: detecting "whether this on-disk block is the expected version" requires external witness, unobtainable within block itself (legal old and new versions isomorphic at block level, fully argued in D18 (Information Carried in a Block)); witness must reside in distinct failure domain — if parent fails to write in same event, requires grandparent, recursing to root => checkpoint-published root is termination of this recursion, its persistence requiring higher reliability than individual blocks (ZFS uses 4 labels * 128 KiB uberblock rings, writing even and odd labels in two phases; project root redundancy governed by D22 (Synthesizing Unit Atomicity) settled item 2). Quantifiable costs (feasible region of two thresholds) in settled item 5.
- Verdict `research/prompts/m4-publish-trigger-r1-main-verification.md` Section 2, cells "what one publish batches", "return means on disk" and "what does not arise under serial execution": barrier classification, entry pre-check of acceptance and record count, refusal after freezing, the three entry points (both legs combined, attacked zero rounds); user settlement 2026-10-26: scope "time and dirty-volume triggers under serial execution" (original wording in history).
- User settlement, verbatim in decisions history.

**Owed checks**: None.

#### Settled Item 15: Releases in Checkpoint C Forbidden from Entering Allocatable Set Before C Publishes

**Settlement**: All releases generated in checkpoint C are forbidden from entering the allocatable set before C is published. Two rationales, the second unique to D16 (Publish Semantics) and stricter:

1. **Rollback**: Crash may return to C-1 root, where blocks born before C and dying in C remain alive.
2. **Settled item 12 rewrites D8 (Core Index Structure) intermediate semantics to "root + arbitrary journal prefix, valid after replay"**: If block released at journal position p is reallocated and written with new content at position q > p, replaying prefix `p < r < q` yields tree pointing to that address **while on-disk bytes already reflect q content** (physical writes unconstrained by journal position). **This is an inevitable defect, not theoretical risk.**

**Scope**: Settles lower bound for returning to allocatable set, not window size (settled item 1). Three known corner cases:

- **Second rationale formulated by journal position** => true constraint is entire journal replay window, not checkpoint boundary; D22 (Synthesizing Unit Atomicity) settled item 4 closes in that form, failure mode without it being "detectable (parent pointer checksum mismatch), unrecoverable".
- **Window capacity correlates directly with ENOSPC** (D3 (Space Allocation): releasing space cannot allocate space), while batching increases probability of create-and-delete closing within same window => **defer window resides on hot path**.
- **External reference**: ZFS features isomorphic conservative mechanism, `include/sys/txg.h` defining `#define TXG_DEFER_SIZE 2 /* Number of txgs worth of frees we defer adding to in-core spacemaps */`, **unverified in this project**; ⚠️ why that value is 2 lacks primary explanation; project defer window must derive from own replay semantics, **copying forbidden**.

**Evidence**:

- E82 (In-Flight Synthesis for Admission): Arm treating intra-window releases as available consumed defer-held blocks across 20 cells — phenomenon of silently bypassing this rule is quantifiable, acceptance form incorporated into D28 (Mount-Time Commitments) settled item 2.
- User settlement, verbatim in decisions history.

**Owed checks**: None (block reuse check handled by I-7.4 (Blocks in Recent K Generations Not Reused), owed checks listed in settled item 1).

#### Settled Item 17: What Callers May Assume After fsync Errors

**Settlement**:

**Scope**:
