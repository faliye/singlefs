## D24 后台重活能不能卸给 GPU —— 已定：**暂缓，非必需**（一格实测为负收益，一格仍开着）

**候选场景三个**：批量压缩、全盘 scrub、大规模纠删码（EC）重建。

**它们落在哪一格，决定了引入 GPU 违不违反已定纪律。**
`.claude/rules/fs-design.md` 的记账纪律把路径分三格，第三格是
「**后台、可续做、非决策路径**（销毁快照、整理、scrub）」，明写「**无戒律**」。
⇒ **三个候选全部落在第三格，引入 GPU 不与任何已定纪律冲突。**

### 三条硬约束（不满足就不许做）

1. **绝不能成为必需。** 文件系统必须在没有 GPU 时完整工作、且语义完全相同。
   ⇒ **GPU 是可选加速器，一个比特都不许进格式。**
2. **不许进前台路径。** PCIe 往返是几十微秒量级，前台读写延迟吃不起这个。
   它只能服务已经攒批的后台重活。
3. **它是一个新的失败域，卸出去的结果必须能被 CPU 独立复核。**
   GPU 算错（驱动 bug、显存 ECC 缺失、算法实现分歧）不能变成静默的数据损坏。
   ⇒ 与 `.claude/singlefs-ai-sop/rules/evidence-discipline.md`「校验的两条路径不许共享同一段代码」同构：
   **GPU 路径与 CPU 路径必须是两份实现**，抽样复核。

### 判据：这一格的瓶颈是不是 CPU

**目前只有一个数据点**（[experiments.md](../experiments.md) E6（加密算法选型））：

| 场景 | 现有数据 | 推断 |
|---|---|---|
| **scrub（校验和 / MAC）** | 有 AES-NI 单核 **3888 MiB/s** ⇒ 16 核约 **62 GB/s** | **高于任何单设备带宽**，瓶颈大概率在设备不在 CPU ⇒ **GPU 无用** |
| **scrub，无 AES-NI 的机器上** | 单核 **267.55 MiB/s** ⇒ 16 核约 **4.3 GB/s** | 与高端 NVMe 阵列同量级 ⇒ **这一档 GPU 可能有用** |
| **EC 重建** | **无数据** | Reed-Solomon over GF(2⁸)，重建要读全部幸存盘并算 parity，计算量随盘数 × 容量线性。这一格计算确实重 |
| **批量压缩** | **无数据** | 压缩比与吞吐的取舍；GPU 压缩库存在 |

⇒ **要定它，先要量 EC 重建与批量压缩这两格的 CPU 上界**，
以及「PCIe 传输 + 核函数 + 传回」这条链路相对纯 CPU 的净收益——
**数据要过一遍 PCIe，那笔搬运成本可能吃掉全部计算收益**，这一条必须先量。

**本机可测**（2026-08-28 现查）：NVIDIA RTX 5090（32 GB）+ RTX 5060 Ti（16 GB），驱动 595.84。
⇒ 这条不是纸面设计题，是可以出数的。见 [experiments.md](../experiments.md) E21（GPU 卸载的净收益）。

### 定案（2026-08-28）：暂缓，不做

**两条依据，互相独立：**

1. **实测：带宽受限那一格是负收益。** GPU 端到端 50.3 GB/s vs CPU 64.91 GB/s，
   净收益 **0.78×**，按 [experiments.md](../experiments.md) **E21（GPU 卸载的净收益） 的判据 1**「小于 1 就否掉那一格」（本决策自身没有编号判据），那一格已判。

   ⚠️ **这条依据只覆盖「纯扫描」那一格，覆盖不了本决策的三个候选场景（2026-08-29 审计）。**
   本决策后文自己写着：三个候选（scrub 的校验和 / EC 重建 / 批量压缩）的 CPU 侧都要**在扫描之上再算**，
   而加密那一格实测只有 **17.4 GB/s** ⇒ 远低于 GPU 的两个地板 ⇒ **那几格 GPU 赢**。
   ⇒ **依据 1 与本决策的结论方向相反**，它判掉的是一个不在候选清单里的场景。
   **本定案实际只剩依据 2（用户定案「非必需」）在承重**，标题里那句「一格实测为负收益」
   要读成「一个与候选无关的格」，不是「候选被实测判负」。
2. **用户定案：这件事非必需。** 三个候选场景全在
   `.claude/rules/fs-design.md` 第三格（后台、可续做、非决策路径），
   **不做它不影响任何硬承诺**——不像 D1（数据可移动性 / 反向索引） 的缩容、D3（空间分配） 的常驻整理那样是承诺过的能力。

⇒ **暂缓不等于否掉**：算力受限那一格（批量压缩）仍然开着，只是不排期。

⚠️ **2026-08-29 用户定案：GPU 这条线不再继续测。**
E6（加密算法选型） 多核档已经把「有 AES-NI ⇒ GPU 输」翻成了反面（CPU 侧饱和 17.4 GB/s < GPU 的两个地板），
**但那个反面同样没被坐实**——GPU 侧还缺一个真的 AES-GCM 核函数（要 `nvcc`）。
⇒ **本决策就停在「方向存疑、两侧都没坐实」这个状态**，重开判据见下节。
**不要把「GPU 赢」当成已定结论去支撑别的决策。**

### 重开判据（说不出什么现象会让它重开，「暂缓」就是无限期搁置）

<!-- doc-lint:registry name-col=2 -->

| 闸 | 简称 | 判什么 | 现在测得了吗 |
|---|---|---|---|
| G24.1 | 缺硬件指令 | 目标平台的 CPU **缺**对应硬件指令，使该任务的 CPU 侧吞吐低于 **50.3 GB/s**（单程场景）或 **28.5 GB/s**（要回传的场景） | 能，量一下那个任务在目标 CPU 上的吞吐即可 |
| G24.2 | 不是盘限 | 该任务**不是盘限**的——即 CPU 侧吞吐低于盘带宽，CPU 真的成了瓶颈 | 需要阵列，本工程没有 |
| G24.3 | 计算段占比 | 压缩那一格：真核函数的计算段占比 | **不能**，本机无 `nvcc`，前置是 CUDA 工具链 |
| G24.4 | GPUDirect 可用 | GPUDirect Storage 可用——它绕开主存与 PCIe 那一跳，会推翻「GPU 吃数据 56.69 GB/s」这个传输地板 | 未验 |

⚠️ **G1 与 G2 必须同时成立。** 只满足 G1（CPU 没指令所以慢）而 G2 不成立（整件事是盘限的），
那 CPU 慢也无所谓——它本来就在等盘。

### 传输段与 CPU 基线已实测，判掉了一半（2026-08-28）

**结论一句话：决定 GPU 赢不赢的是 CPU 那侧有没有对应的硬件指令，不是 GPU 有多快。**

| 路径 | 吞吐 | 性质 |
|---|---|---|
| CPU 吃数据（内存带宽墙） | **64.91 GB/s** | CPU 侧上限 |
| GPU 吃数据（锁页 H2D，≥64 MiB） | 56.69 GB/s | 传输**地板**，核函数再快也绕不过 |
| GPU 来回（H2D + D2H） | **28.5 GB/s** | 传输地板，回传全部数据的场景走这一行 |

**GPU 光把数据搞进去就已经比 CPU 读它慢 13%**，而这还没开始算。
⇒ GPU 只在「CPU 那侧的实际吞吐掉到传输地板以下」时才有机会。
代入 [experiments.md](../experiments.md) E6（加密算法选型） 已测的加密吞吐：

| CPU 侧 | **多核饱和实测** | 判 |
|---|---|---|
| **有 AES-NI** | **17.4 GB/s**（8 线程饱和，16/32 线程 16.3/16.5） | **< 28.5 < 50.3 ⇒ GPU 赢** |
| 无 AES-NI | 多核未测；单核 267.55 MiB/s，饱和值只会更低 | **< 28.5 ⇒ GPU 大幅赢** |

⚠️ **判据的正确形式是「CPU 侧的多核饱和吞吐」，不是「单核 × 核数」。**
线性外推与实测在 AES-GCM 上差近 4 倍（外推 ≈65 GB/s，实测饱和 17.4 GB/s）。

⚠️ **「瓶颈是不是 CPU」不等价于「这个任务有没有硬件指令」**：
有 AES-NI 的加密照样在 17.4 GB/s 就饱和，瓶颈仍然在 CPU 侧。
**有硬件指令 ≠ 快到 GPU 追不上。**

⚠️ **还有一层压在上面**：三个候选场景全是盘限的后台活，
盘带宽比 64.91 与 28.5 都低得多 ⇒ 整件事若是盘限的，CPU 本来就在空转，
卸给 GPU 省不下任何东西。**这一层是推理不是实测**（本工程没有阵列）。

**计算段也测了**（用带宽受限算子给上界，不需要 `nvcc`）：显存内 **1041 GB/s**，
而端到端（含传输）只有 **50.3 GB/s** ⇒ **传输占 90.3%，计算段几乎免费**。
⇒ 对**纯扫描**（CPU 侧 64.91 GB/s）这一格，E21（GPU 卸载的净收益） 判据 1 的净收益 = **0.78×**，小于 1 ⇒ GPU 输。

⚠️ **但「纯扫描」不是本决策的三个候选场景中的任何一个。**
三个场景（scrub 的校验和、EC 重建、批量压缩）的 CPU 侧都要**在扫描之上再算**，
而加密那一格实测只有 **17.4 GB/s** ⇒ **远低于 GPU 的两个地板，GPU 赢。**
⇒ **阈值仍然成立**（CPU 侧低于 50.3 GB/s 单程 / 28.5 GB/s 来回时 GPU 赢），
**变的是代进去的那个数**。

⚠️ **不能读成「GPU 无用」**：上面的推论只对**带宽受限**的核函数成立。
**压缩是算力受限的**，它的计算段可能远不止 9.7%，**那一格仍然开着且仍要等 `nvcc`**。
⚠️ **一个未验的逃生口**：GPUDirect Storage 让 NVMe 直接 DMA 进显存、
绕开主存与 PCIe 那一跳，**它会推翻「GPU 吃数据 56.69 GB/s」这个传输地板**。没测过，不许当它不存在。
