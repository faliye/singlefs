# 三样验证手段怎么落地：checker、事务层、崩溃点重放

**口径**：2026-09-03 调研。三样东西在仓里的现状是零代码——`crates/` 不存在，仓库根没有 `Cargo.toml`，
`research/` 下 90 多个实验二进制全是模型与算术，没有一行是文件系统实现（现查 `git ls-files`）。
门禁每次打印的三条未实现阶段（模型对拍、崩溃点重放、QEMU 真实负载）压在同一条链上：
**没有事务层就没有被测对象，没有 checker 就没有判决，两者都没有就没法做崩溃点重放。**
这份调研把每一样要消费哪些已定条款、被哪些未定项挡着、能从仓里复用什么、第一版最小该做到哪，
逐条列出来；末尾是挡在代码前面、只有用户能定的几个问题。

⚠️ **「推荐的落地顺序」一节是推论**，2026-09-03 走过一轮三方对抗（腿况与判决在同一节里），
其余各节是现查事实。

## 一、三样各自是什么

| 手段 | 门禁里的阶段 | 输入 | 输出 | 权威定义 |
|---|---|---|---|---|
| **事务层**（被测对象） | 没有单独阶段；模型对拍、崩溃点重放、QEMU 负载三条都以它为前置 | mkfs 参数、一串操作、一个块设备 | 镜像，以及一条写请求流（给崩溃点重放用） | 项目 `CLAUDE.md`「第一个可运行目标是正确提交一个事务」；结构约束在 D13（验证路线）的 `CommitStep` 封闭枚举与 D17（实现分层与第三方管道）的腰线 |
| **checker** | 是模型对拍与崩溃点重放两条阶段共同的判决器，本身对应 O2（独立解析器 + checker） | **一个**镜像 | 每条不变量的成立 / 不成立 / 不适用 | D13（验证路线）已定：一元谓词，只判单个镜像，不许调用被测 crate 的任何反序列化或遍历代码；[invariants.md](invariants.md) 是它的规格 |
| **崩溃点重放** | 「崩溃点重放」阶段 | 写请求流（含屏障）+ 崩溃前镜像 | 每个崩溃状态上「恢复 → checker → 记录核对器」的结果 | `.claude/singlefs-ai-sop/rules/test-discipline.md`「崩溃一致性只能靠崩溃点重放验证」；分层与抽样在 D13（验证路线）「崩溃点重放要分三层」 |

模型对拍（O1（内存模型对拍（HashMap 理想文件系统））与 D13（验证路线）已定项 3 的 RefFS）
不在用户点名的三样里，但它是第四条前置链：它要 checker 判镜像、要事务层当被测对象。
O3（独立规约执行器）（用另一种语言、只照 decisions 与 invariants 的文字重新推导的规约执行器）
也不在三样里，它是 D13（验证路线）三个 oracle 里离代码最远的一个，落地顺序放在最后一步。
记录核对器（入参 `(崩溃前镜像, 记录流, 崩溃后镜像)`，D13（验证路线）故意不给编号）
同样不在三样里，却是崩溃点重放的第二个判决器——没有它，「根在案而记录缺席」那 7 类状态
（E77（发布的持久顺序））只能靠 checker 的单镜像判据间接发现。

## 二、依赖顺序：谁挡着谁

```
格式字节的 4 处空白 ──▶ mkfs + 事务层 ──▶ 写请求流 ──▶ 崩溃点重放
                     └─▶ checker ────────────────────┘
                                                      └─▶ 记录核对器 / 模型对拍
```

**挡在第一行事务层代码前面的，是 [first-txn-layout.md](first-txn-layout.md) 里判了「改第一个事务的字节：是」的四个未定项**（2026-09-03 现查）：

| 未定项 | 挡住什么 |
|---|---|
| D22（单元原子性怎么合成）未定项 9：超级块的字段表 | mkfs 写的第一批字节 |
| D8（核心索引结构）未定项 6：inode 记录的盘上字段表 | 第一个事务要写一个文件的元数据 |
| D3（空间分配）已定项 7：分配记录的条目宽度与 key 编码 | 写完数据单元就要写它的分配记录 |
| D5（快照 / 空间记账机制）已定项 5：记账 key 各段的宽度 | 记账树节点的内容 |

另有五处只定了形态没定宽度（超级块槽轮换字段、指针内联的诞生 txg、记账树节点头基础字节、
journal 事务边界字段、树表单元自己的头），[first-txn-layout.md](first-txn-layout.md) 标为半定。
写代码时按「初值」取，取了要回写那张表。

**不被这四处挡住、今天就能写的**：块设备抽象与写请求录制器、崩溃状态枚举器、checker 的两方向骨架与
已知坏镜像机制、自证单元（根记录 127 字节、journal 记录头 78 字节）的独立解析器。
它们消费的条款都已定（D22（单元原子性怎么合成）已定项 7、D23（journal 的角色与格式）已定项 4）。

## 三、每一样的第一版范围

### 事务层第一版：mkfs、一个事务、一次发布、一次恢复

第一个事务的定义在 [first-txn-layout.md](first-txn-layout.md)：mkfs 之后写一个小文件并发布一次，
不含目录、快照、reflink、加密（D9（加密）已定项 10）、压缩。第一版实现的是纯 SSD 布局
（D12（目标介质）已定项 5）、2 块盘（D2（RAID 条带策略）已定项 9）、串行提交（D13（验证路线）已定项 2）。

它必须逐字遵守的已定条款：

| 步骤 | 条款 |
|---|---|
| mkfs | 超级块每盘一份、更新走 ≥2 槽轮换；journal 环两盘镜像；第 0 代根种进全部根环区域（D22（单元原子性怎么合成）已定项 8）；根环 R=3、素数步长放置、槽宽 = 探测到的 `physical_block_size`（D22（单元原子性怎么合成）已定项 2） |
| 分配 | 逐落点谓词（D3（空间分配）已定项 1），住独立 keyspace 的 btree（D3（空间分配）已定项 3）；提交内生块从聚簇段分配（D3（空间分配）已定项 5）；准入读数 = 已发布 − 在飞已批（D3（空间分配）已定项 6） |
| 写单元 | 数据单元恒 32 KiB 含头（D4（校验和位置）已定项 5 / 已定项 7）；单元头 91 字节字段表（D18（块里携带什么信息）已定项 7）；补齐恒为 0 且参与校验和（I-2.3（补齐字节为零且参与校验和）） |
| 写指针 | 指针头部 31 + 位置条目 11 × 2 副本（D19（块指针的结构与宽度预算）已定项 1 / 已定项 2 / 已定项 3）；校验和内联进父指针（D4（校验和位置）已定项 1） |
| 写记录 | 4 KiB 定长记录、头 78 字节、每项 56 字节（D23（journal 的角色与格式）已定项 4 / 已定项 12）；一个事务可跨多条、头带事务边界（已定项 7）；反向链 CRC32C（已定项 8 / 已定项 11）；载荷校验和（已定项 13）；jsn 与实例代号的位宽划分（已定项 9） |
| 发布 | 持久顺序恒为「单元/节点 → 屏障 → journal 记录 → 屏障 → 根槽（FUA）」（D16（发布语义）已定项 7）；每次发布 checkpoint_txg + 1（D16（发布语义）已定项 6）；根记录 127 字节、恒走树表单元间接层（D22（单元原子性怎么合成）已定项 7） |
| 恢复 | 先逐个验证全部根槽候选再择新，平局按实例代号（D22（单元原子性怎么合成）已定项 7）；全环扫描、不许先信 tail（D23（journal 的角色与格式）已定项 3）；前缀四条口径——jsn 严格连续、`(实例代号, checkpoint_txg)` 大于根的水位、提交标记齐全、施加前逐项验证点名单元（D23（journal 的角色与格式）已定项 14） |

**结构上的硬要求**：一个共享的事务抽象状态机加一个封闭的 `CommitStep` 枚举，穷尽 `match`、没有通配臂
（D13（验证路线）「落地手段是一个封闭枚举 + 穷尽 match」）；提交路径与准入路径里不许出现介质判定符号
（C19（介质判定渗进事务层））；块设备接口只暴露「写、屏障、FUA 写」，不暴露「介质是什么」。

⚠️ **第一版明确不做的**：并行提交（D13（验证路线）已定项 2 明写「越过交点再开并行」）、
zoned 布局（D22（单元原子性怎么合成）未定项 6 未答）、无界操作的意图日志（D8（核心索引结构）已定项 5 的
批量删除路径，第一个事务用不到）、defer 窗口的取值（D16（发布语义）未定项 1，占位 8 秒）。

### checker 第一版：两个方向、一份已知坏镜像语料、每条不变量三态

**它能判什么，由 [invariants.md](invariants.md) 与第一个事务的镜像共同决定**（2026-09-03 逐条对过）：

| I-8（journal） | I-8.1（环几何够大）到 I-8.5（tail 槽有效集非空）五条全部 | —— |

**两个方向**：遍历式从根槽走下去，扫描式按 D18（块里携带什么信息）已定项 9 的步进线性扫全盘、靠
91 字节单元头认领（E86（扫描步进与两种单元大小）的探针、E88（冒名单元与孤儿单元的判别）的认领规则）。
两者对同一条不变量各判一次，共享的只有格式解析（D13（验证路线）「冲突 1」的折中）。
I-1.2（块头代号不超当前）是扫描方向独立于遍历方向的判据，也是把撕裂事务垃圾从活单元里分出来的唯一判据。

**判定宽度要自己探，不许从 harness 或实现拿**：I-7.5（根槽按判定宽度对齐）与 I-8.2（记录头不跨原子单元）的判据是挂载时探测的 `physical_block_size`，
它不在镜像里；checker 直接读裸设备（O2（独立解析器 + checker）的口径），就该自己探一次，再与超级块记录的 mkfs 时取值比对
（D22（单元原子性怎么合成）已定项 2「挂载时逐设备复算比对」的 checker 侧形态；超级块要记这个值，归 D22（单元原子性怎么合成）未定项 9）。
文件当设备时探不到，checker 要把几何报成「来自参数」而不是当成探到的（反推腿指出）。

**独立性是硬约束，不是风格**：checker 是单独的 crate，不依赖实现 crate；
不许链接实现的记账与校验代码（D17（实现分层与第三方管道）债表第 5 项、C12（增量语义共用））。
它与实现之间允许共享的最小集合还没定，见「待定案」一节。

**它自己要先证明会红**：每条已实现的不变量配至少一份「改坏了正好触发它」的镜像，
做成与 `research/mutations/` 同型的变异表，由门禁复跑（C13（checker 判定失效）要的正是这个：
跑了、全绿、但已经不做事，与没跑长得一样）。C88（根环的时间线判别未实现）的双根镜像、
C47（根槽没按判定宽度对齐）的偏移半个槽镜像，是这份语料最早的两条。

### 崩溃点重放第一版：用户态录制、全量枚举、三个判决器

**录制在用户态做，不在内核做。** 实现是一个 Rust 库，所有 I/O 都过同一个块设备抽象；
在那个抽象上套一层录制器，就能拿到带屏障与 FUA 标记的完整写请求流。
`dm-log-writes` 留给 C6（块层语义假设写错）那一格——它问的是「真实块层的 FLUSH / FUA 语义是不是我们假设的那样」，
只有真设备答得了；本机与虚机内核都带这个模块（见「环境现查」）。

**枚举照 E77（发布的持久顺序）的模型**（撕裂子集不枚举，D13（验证路线）已定项 4 已定；⚠️ 撕裂态并进「未持久」来计数，那些撕裂字节样式也必须真的写成镜像喂给 checker 的扫描方向——头落了、载荷没落的那一格正是 I-1.2（块头代号不超当前）要抓的，「并进一格计数」不许被读成「不生成这种镜像」）：屏障把写请求流切成段，崩溃状态 = 前若干段全持久 + 当前段任意子集持久 + 之后段全没持久。
D16（发布语义）已定项 7 的两道屏障加根槽 FUA 把一次发布切成三段，第一个事务的状态数在百的量级，
**层 0 不抽样、全量枚举**。E77（发布的持久顺序）已有可直接抬进来的三段代码：枚举器 `crash_states`、
恢复模型 `recover`、以及**不共享恢复代码**的审计 `audit`——审计与被审计分开这条纪律在那里已经踩过一次坑
（不验证的重放自称成功，被变异测试当场抓到）。

**录制按设备录，不按池录**：第一版两块盘、任何写都 w ≥ 2（D2（RAID 条带策略）已定项 6），journal 环两盘镜像（D22（单元原子性怎么合成）已定项 8），
每个单元与每条记录都是两次可以各自持久的物理写，屏障也是两次设备 FLUSH。所以 E77（发布的持久顺序）的 72 / 79 / 513 / 1024 不能搬来当 harness 的状态数断言，
harness 要按自己的写流另算闭式（反推腿指出）。

**每个崩溃状态跑三件事**：实现自己的恢复 → checker（一元判决）→ 记录核对器（二元判决，
对拍崩溃前镜像、记录流、崩溃后镜像）。三者各自独立，缺一样就有一类错误没人看。

**harness 自己要证明会红的用例，仓里已经点名了七条**（[checks-owed.md](checks-owed.md) 把它们的前置都写成崩溃点重放 harness，没有哪一条是可选的）：

| 用例 | 必须红在哪 | 出处 |
|---|---|---|
| 摘掉根槽前的屏障 | **记录核对器**判「根在案而记录缺席」，E77（发布的持久顺序）b_ur 臂 79 个状态里 7 处；checker 在这里不会红（数据违例 0），摘掉两道屏障才是 b_none 臂的 504 处 | C76（发布时序没有权威落点）；2026-09-03 复跑 E77（发布的持久顺序）核实 |
| 关掉重放施加前的点名单元验证，**并把一个被点名的单元改坏** | 关掉验证 ⇒ 坏单元被嫁接，I-2.1（校验和与内容匹配）红；不关 ⇒ 那个事务被丢弃、回旧态且绿。不改坏单元的话，已定的两道屏障下验证是死代码（E77（发布的持久顺序）b_all 臂 naive 与 validating 都是 0 / 72） | C76（发布时序没有权威落点）；E77（发布的持久顺序）b_rs 臂 63 处 |
| 空洞 → 恢复 → 少量续写 → 再崩 | 重放出属于已丢弃时间线的记录 | C42（残留记录冒充合法前缀）；E32（上一条时间线的残留） |
| 把延迟重用窗口改成 0 | I-4.8（近 K 代根校验和自洽）必须红 | C22（刚释放的块立即重分配） |
| 把记账排空从发布路径摘掉 | 每个发布点后的 I-3.1（已分配统计对得上）必须红 | C80（记账更新必须原子地随根发布） |
| 陈旧 tail + 已复用的块 | 恢复必须完成，且终态与真值逐格相等；失配即中止的形态必须被抓 | C77（重放起点未定义）；E78（重放的起点） |
| 先信 tail 再往前走的恢复 | 窗口内的记录必须全漏，漏数等于写入数 | C29（恢复先信 tail 会丢数据）；E24（恢复算法：先信 tail 会不会丢记录） |

⚠️ **层 0 的负载不能只是「第一个事务」**：mkfs 之后写一个文件并发布一次，数据侧一个块都不释放，
C22（刚释放的块立即重分配）与 C80（记账更新必须原子地随根发布）两条用例没有东西可抓
（三方对抗里本地腿与正推腿各自指出）。层 0 的固定负载要含第二个事务——覆盖写同一个文件，
造出一次释放、一次延迟重用与一次记账变更；C42（残留记录冒充合法前缀）还要「崩溃 → 恢复 → 少量续写 → 再崩」，
所以层 0 的固定脚本是三次发布夹一次恢复：mkfs、发布 A（写文件）、发布 B（覆盖写）、在 B 的每个崩溃点恢复、再发布 C（短）、在 C 的每个崩溃点恢复。
**基镜像要能预置**（反推腿指出）：录制器只录本次跑的写，环里「上一条时间线的残留」不会自己出现，harness 得能把一条残留记录种进基镜像。
屏障与空发布相关的用例在只有 mkfs 与空发布时就能跑，释放、重用、残留三类要等到发布 B 与 C。

**它答不了、要交给 QEMU 那一档的**：C6（块层语义假设写错）（真实 FLUSH / FUA）、
C26（屏障数从没量过）（真机屏障计数）、C16（管道声明失败模型例外）与 D20（承重面：单元的原子性与自包含）
推论三第 3 问要的撕裂注入——`dm-flakey` 造不出撕裂，用户态录制器倒是能按 `physical_block_size` 粒度造，
但那是模型不是设备。
