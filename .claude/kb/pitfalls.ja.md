# 避坑リスト

[中文](pitfalls.md) · [English](pitfalls.en.md) · **日本語**

**既存の COW ファイルシステムで既に確認された設計上の過ち。使用方法: 設計の決定を行うたびに、この表に戻って確認する。**

項目は主に btrfs から抽出した——批判を目的とするのではなく、その失敗パターンが最も完全に記録され、
コミュニティの議論が最もオープンで検証可能だからである。他の実装の同様の教訓も同様に収集している。

過ちの説明は公開資料およびそれぞれの公式ドキュメントに基づいており、**本プロジェクトでは未検証**である。
「対策」列は [decisions.md](decisions.md) の対応する決定にリンクしている。

| # | 陥穽 | 根本原因 | 対策 |
|---|---|---|---|
| 1 | ENOSPC の不条理（`df` に空き領域があるのに書き込めない、ファイル削除時にも領域不足エラー） | 二段階割り当て + chunk 分類の硬直化 | ✅ D3 (領域割り当て) で分類しない；✅ 偽の ENOSPC を禁止し、削除された領域は有界ステップ数内で利用可能とする（D3 (領域割り当て) 確定項目 9、2026-09-11 ユーザー決定）、着地形態は D16 (パブリッシュセマンティクス) 確定項目 1 に従う |
| 2 | RAID5/6 write hole、本番環境での使用非推奨 | 固定幅ストライプに read-modify-write が必要 | ✅ D2 (RAID ストライプ方針) 可変幅フルストライプ |
| 3 | extent tree + backref は複雑さのブラックホールかつバグ頻発域 | 逆インデックスが後から増殖したものであり、設計されたものではない | ✅ D1 (データ移動性 / 逆インデックス) day-1 設計 |
| 4 | fsync が特例化された log tree を経由し、独立したバグの温床となる | 第二のトランザクション機構 | ✅ 統一トランザクション層（.claude/rules/fs-design.md） |
| 5 | 全データが同一ツリー、同一 key 空間、同一ロックに押し込められる | 単一インデックス構造 | ✅ D8 (コアインデックス構造) 確定: 一つの btree 実装 + 複数の独立 keyspace + write buffer / key cache 二つのフロントエンド |
| 6 | RAID レベルがディスク全体でしか設定できず、ファイルごとに設定できない | profile が chunk に紐付いている | ⏸ 候補: ポインタインライン複数レプリカ |
| 7 | qgroup が低速かつ慢性的に誤計上（+76% コミット時間 / +1347% トランザクション待ち / −25% 書き込みスループット） | 会計が後付けで、逆インデックス走査に依存 | ✅ D5 (スナップショット / 空間会計メカニズム) birth txg 増分会計 |
| 8 | `nodatacow` は脱出ハッチであり解決策ではない（COW を切る = チェックサムとスナップショット整合性を同時に失う） | ランダム書き込みの断片化に対する真の答えがない | ✅ D26 (バックグラウンド整理と配置回収) 常駐整理 + 構造の抗老化スタック、デバイスに依存せず自前で解決 |
| 9 | degraded マウントで単一レプリカ chunk が書き出され、事態が悪化する | 縮退動作が設計されていない | ⏸ 未決: 縮退セマンティクスの明示的定義が必要 |
| 10 | `btrfs check --repair` コミュニティ自体が使用を控えるよう勧告 | 再構築可能性が設計目標ではない | ✅ 自己記述ブロック + checker day-1 |
| 11 | ネイティブ暗号化がない | フォーマットに入ったことがなく、後からねじ込めない | ✅ D9 (暗号化) 確定: ボリューム全体 AEAD、ポインタ内に MAC / nonce / アルゴリズムタイプ / extent オフセットを day-1 で予約、暗号化自体は初版に入れない（確定項目 10） |
| 12 | `df` の出力がユーザーにとって無意味 | 実装の詳細がユーザーに漏洩している | ⏸ 未決: 領域セマンティクスはユーザー向けに設計する必要がある |
| 13 | ネイティブ暗号化と send/recv 複製パスが長期にわたり互いに干渉（openzfs/zfs#12014 は 2021-05 からオープン、2025 年時点でも修正中） | raw send のために認証構造が変形: MAC を Merkle ツリーにできず、集約 MAC + objset 層の二重ルートを採用 | ⏸ 管理する条項なし（D9 (暗号化) はすべて確定、暗号文複製 / raw send は項目未立案）: 暗号文複製のセマンティクスはフォーマット層で確定すべきであり、後付け機能にしない |
| 14 | nonce が物理位置に紐付け → 1 ブロック移動するだけで再暗号化が必要、バックグラウンド整理に鍵が必須、複数レプリカでバイト列が異なる | 暗号化とデータ移動性が一緒に設計されていない | ✅ D9 (暗号化) 確定項目 13 ハード要件 1: nonce は論理アイデンティティに従い、ポインタ内に保存 |
| 15 | ディレクトリごとの暗号化によりファイルサイズを平文で残すことを強制され（fsck が使用）、filenames / xattr / inline extent にそれぞれ多くの隙間が残る | 暗号化の粒度が検証の粒度より細かい | ✅ D9 (暗号化): ボリューム全体暗号化、ディレクトリごとの暗号化は行わない |
| 16 | ユーザー鍵を変更しても古いラップされたマスターキーが無効化されず、フォレンジック復元が可能 | 鍵更新時にマスターキーを再ラップするだけで、データを再暗号化しない | ⏸ 管理する条項なし（D9 (暗号化) はすべて確定、鍵更新は項目未立案）: 鍵更新が何を保証するかをユーザーに示す必要があり、再暗号化と同等と誤解させてはならない |

## 利点

**同様に既存の実装から得られたものだが、これらは有効性が検証されており、直接踏襲する価値がある。**

| 項目 | 説明 |
|---|---|
| メタデータノードヘッダの自己記述 | ノードヘッダに自身の論理アドレス、generation、level、所属ツリー、fsid を保持。ツリー全体が破損した際に btrfs-rec が全ディスクのスキャン再構築で復旧できる唯一の理由 |
| 3 段階の feature bit | `incompat` / `compat_ro` / `compat`、進化経路が正しく設計されている |
| 単一デバイスと複数デバイスで同一のコードパス | 単一ディスク用の特例を設けず、複数ディスク下でのみ顕在化するバグのクラス全体を削減 |
