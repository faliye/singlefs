# 待議の規矩

[中文](pending-rules.md) · [English](pending-rules.en.md) · **日本語**

違反時に赤になる検査にできず規則に入れられない条項は、pending-rules.md に待議として置く（`.claude/singlefs-ai-sop/rules/sop-first.md`「境界」：検査にできないものはまず kb に待議として残し、規矩にしない）。
各項目には原文、元どこにあったか、なぜ撤回したか、規則にするために何が不足しているかを書く。原文は撤回時のテキストをコードブロック内に一字一句そのまま保存する。各コードブロックでは、原文の後に同じブロック内で日本語訳を続ける。

## 検証装置またはテスト入口を新設する前に既存のものを探す —— 待議

| 項 | 内容 |
|---|---|
| 元どこにあったか | 共有 SOP `rules/sop-first.md` の小節「検証装置またはテスト入口を新設する前に、同様にまず既存のものを探す」、0.0.64 以降（2026-10-11 リリース） |
| 撤回 | 2026-10-16、ユーザー決定「検査にできず review にのみ依存する条項はすべて kb 待議に撤回する」 |
| 状態 | 待議：規則ではなく、実行を拘束しない |
| 規則にするため不足しているもの | 一道の赤になる検査：新しい入口スクリプトのファイルヘッダに `# gate-similar:` がなければ赤とし、指名された装置が存在するか検証する。「二つの装置が同一の事項を判定しているか」は依然として判定不能 |

```text
## 立验证装置或测试入口之前，同样先找已有的

射程：验证装置（枚举、对拍、跑真设备或外部工具的那一套代码）、测试入口（`test-script-discipline.md` 说的入口脚本），以及跑它们的门禁阶段与快慢两档。

1. 先列已有的装置与入口各判什么：判哪件事、哪一批对象（哪几条流、哪个枚举域）、用哪个判法、在哪个阶段跑。
2. 有判同一件事、同一批对象的，新的并进已有的那一套：换一种算法、换到加速硬件、加一条流、加一个域，都写成它的加速路径或新项，用它的名字、它的入口、它的阶段与它的快慢两档，不另起名字、不另立阶段、不另分一套快档与全量。加速路径留参照路径、两边对拍，照 `test-script-discipline.md`「用上现有的硬件加速」。
3. 只有一部分重叠（几条流、一段域相同）的，重叠的那一部分并进去，其余作为同一套里的新项。
4. 仓里已经并存两套判同一件事的，先合成一套，再跑它的剪枝跑或全量；合之前不跑两套各自的全量。
5. 非单独立不可，在新入口的文件头写 `# gate-similar: <已有的装置或入口> <为什么不并进它>`；一个像的都没有，写 `# gate-similar: 无 <查过哪些>`。

「立验证装置或测试入口之前，同样先找已有的」门禁还不判：新入口的文件头写没写 `gate-similar`、两套装置判的是不是同一件事，都靠 review。

日本語訳：

## 検証装置またはテスト入口を新設する前に既存のものを探す

射程：検証装置（列挙、突き合わせ、実デバイスや外部ツールを動かす一式のコード）、テスト入口（`test-script-discipline.md` の言う入口スクリプト）、およびそれらを実行するゲートのステージとクイック層・スロー層の二層。

1. まず既存の装置と入口がそれぞれ何を判定しているかを列挙する：どの事項を、どの対象群（どのストリーム、どの列挙ドメイン）について、どの判定法で、どのステージで実行するか。
2. 同じ事項・同じ対象群を判定しているものがあれば、新しいものは既存の一式に統合する：アルゴリズムの差し替え、高速化ハードウェアへの移行、ストリームの追加、ドメインの追加は、いずれもその一式の高速化経路または新しい項目として書き、その名前・入口・ステージ・クイック層とスロー層を使う。別の名前を立てず、別のステージを立てず、クイック層とフル実行を別に分けない。高速化経路は参照経路を残して両者を突き合わせる（`test-script-discipline.md`「既存のハードウェア高速化を使う」に従う）。
3. 一部だけ重なる（いくつかのストリームやドメインの一部が同じ）ものは、重なる部分を統合し、残りは同じ一式の新しい項目にする。
4. リポジトリに同じ事項を判定する二式が既に並存している場合は、先に一式に統合してから、その枝刈り実行またはフル実行を行う。統合する前に二式それぞれのフル実行は行わない。
5. どうしても単独で立てる必要がある場合は、新しい入口のファイルヘッダに `# gate-similar: <既存の装置または入口> <統合しない理由>` と書く。似たものが一つもない場合は `# gate-similar: 无 <調べた対象>` と書く。

「検証装置またはテスト入口を新設する前に既存のものを探す」はゲートがまだ判定しない：新しい入口のファイルヘッダに `gate-similar` が書かれているか、二つの装置が同じ事項を判定しているかは、いずれも review に頼る。
```

## バグを修正したときは全リポジトリで論理とコードが類似する箇所を厳密に調査する —— 待議

| 項 | 内容 |
|---|---|
| 元どこにあったか | 共有 SOP `rules/code-discipline.md` の小節「バグを修正したときは、全リポジトリで論理とコードが類似する箇所を厳密に調査する」、0.0.66 以降（2026-10-15 リリース） |
| 撤回 | 2026-10-16、「検証装置またはテスト入口を新設する前に既存のものを探す」の撤回決定と同じ |
| 状態 | 待議：規則ではなく、実行を拘束しない |
| 規則にするため不足しているもの | 一道の赤になる検査：バグ修正コミットメッセージに「何を検索したか、何箇所ヒットしたか、何箇所修正したか」の三点がなければ赤とする。検索が網羅的か、判定が正しいかは依然として判定不能 |

```text
## 修了 bug，要严查全库里逻辑和代码相似的地方

射程：改了一处缺陷，不分代码、脚本、门禁、文档，也不分语言版本。

**判据：修完之后，说得出全库里还有哪几处和它是同一个模式，每一处是改了，还是查过确认没有这个缺陷。**

1. 把缺陷拆成两种形态：**代码形态**（同样的写法、同一个函数或正则、抄过的同一段）和**逻辑形态**（同样的假设、同样的边界、同一个口径，写法不同也算）。
2. 两种形态都全库搜。代码形态按写法 grep；逻辑形态按「谁在做同一件事」找：同一个概念的别的实现、同一类输入的别的处理、判同一条判据的别的检查，含测试、示例、各语言版本。输出不截断，先数再看（`verify-before-claiming.md`「截断过的输出也是窄的那一句」）。
3. 每个命中逐个判。有同一缺陷的，在同一次改动里一起改；没有的，写明为什么不受影响。
4. 每个顺带修掉的相似处，各配一条先证明会红的测试（`show-me-test.md`）。
5. 提交信息写：搜了什么（关键字或命令）、命中几处、改了几处、没改的几处各自的原因。搜不到别的相似处，写「搜了 <什么>，0 处」，不写「没有」。

缺陷在口径层（同一个量在两套装置里算法不同）的，相似处就是另一套装置，照 `show-me-test.md`「装置里，还是口径上」立跨装置的检查。

日本語訳：

## バグを修正したときは全リポジトリで論理とコードが類似する箇所を厳密に調査する

射程：欠陥を一箇所修正したすべての場合。コード、スクリプト、ゲート、文書を問わず、言語版も問わない。

**判定基準：修正後に、全リポジトリで同じパターンの箇所がほかにどこにあるか、そのそれぞれを修正したのか、調べてこの欠陥がないと確認したのかを言えること。**

1. 欠陥を二つの形態に分ける：**コード形態**（同じ書き方、同じ関数や正規表現、コピーされた同じ一節）と**論理形態**（同じ仮定、同じ境界、同じ計測条件。書き方が違っても含む）。
2. 二つの形態をどちらも全リポジトリで検索する。コード形態は書き方で grep する。論理形態は「誰が同じことをしているか」で探す：同じ概念の別の実装、同じ種類の入力の別の処理、同じ判定基準を判定する別の検査。テスト、例、各言語版を含む。出力は切り詰めず、先に数えてから見る（`verify-before-claiming.md`「切り詰めた出力も狭い主張である」）。
3. ヒットを一つずつ判定する。同じ欠陥があるものは同じ変更でまとめて修正し、ないものは影響を受けない理由を書く。
4. ついでに修正した類似箇所のそれぞれに、先に赤になることを示したテストを一つずつ付ける（`show-me-test.md`）。
5. コミットメッセージには、何を検索したか（キーワードまたはコマンド）、何箇所ヒットしたか、何箇所修正したか、修正しなかった箇所それぞれの理由を書く。ほかに類似箇所が見つからなければ「<何> を検索して 0 箇所」と書き、「なし」とは書かない。

欠陥が計測条件の層にある（同じ量を二つの装置で異なるアルゴリズムで計算している）場合は、類似箇所はもう一方の装置であり、`show-me-test.md`「装置の中か、計測条件の上か」に従って装置をまたぐ検査を立てる。
```

## 発見された問題は徹底的に修正しサンクコストを理由にしない —— 待議

| 項 | 内容 |
|---|---|
| 元どこにあったか | 共有 SOP `rules/code-discipline.md` の小節「発見された問題は徹底的に修正し、サンクコストを理由にしない」、2026-10-16 に上流作業ツリーに追加、未リリース |
| 撤回 | 2026-10-16、「検証装置或者テスト入口を新設する前に既存のものを探す」の撤回決定と同じ |
| 状態 | 待議：規則ではなく、実行を拘束しない |
| 規則にするため不足しているもの | 赤になる検査は文字通りの一部にしか及ばない：共有スクリプトの引数や出力規約を変更し、利用側プロジェクトに旧規約に従う呼び出し元が残っていれば赤とする。「修正が完了したか」「リファクタリングすべきか」は判定不能 |

```text
## 查出来的问题要彻底修，不拿沉没成本当理由

射程：review、门禁、自证、别人报来的问题，核实成立的每一条。

- **核实成立就修，在这一次改动里修完。** 不写「没在这一次动」「下次再说」「先这样」。修不了的（要使用者定的、要别的仓改的）明说卡在哪、交给谁，不默认放着。
- **判据是怎么改才对，不是已经写了多少。** 已经写好的代码、已经发出去的版本、改动面大，都不是不改或只打补丁的理由；结构错了就重构，不在错的结构上加绕过的分支。
- **不走捷径。** 不放宽检查、不加豁免、不改用例的预期让它变绿、不把报错吞掉；改的是出错的原因，不是它露出来的症状；修完照「修了 bug，要严查全库里逻辑和代码相似的地方」查相似处。
- **改了共享的东西，同一次改动里把用它的地方一起改。** 脚本的参数、输出、文件名与目录约定变了，本仓的调用方、各语言版本、使用者项目里的调用方与样本一起改到位，再发版；只改上游、下游还按旧约定跑的，算没改完。
- 修的是缺陷本身，当场修；为防它再犯而新立的门禁，立的时机照 `sop-first.md`「边界」一节。

日本語訳：

## 発見された問題は徹底的に修正しサンクコストを理由にしない

射程：review、ゲート、自己検証、他者からの報告で、成立すると確認された問題のすべて。

- **成立を確認したら修正し、今回の変更で修正を終える。** 「今回は触らない」「次回に」「ひとまずこのまま」とは書かない。修正できないもの（使用者の決定が要る、別のリポジトリの変更が要る）は、どこで止まっているか、誰に渡すかを明言し、黙って放置しない。
- **判定基準はどう直せば正しいかであり、すでにどれだけ書いたかではない。** 書き終えたコード、すでに出したバージョン、変更範囲の大きさは、直さない理由にも継ぎはぎで済ませる理由にもならない。構造が間違っていれば作り直し、間違った構造の上に回避の分岐を足さない。
- **近道をしない。** 検査を緩めない、免除を足さない、テストの期待値を変えて緑にしない、エラーを握りつぶさない。直すのはエラーの原因であり、表に出た症状ではない。修正後は「バグを修正したときは全リポジトリで論理とコードが類似する箇所を厳密に調査する」に従って類似箇所を調べる。
- **共有のものを変えたら、同じ変更でそれを使う箇所もまとめて変える。** スクリプトの引数、出力、ファイル名やディレクトリの約束が変わったら、このリポジトリの呼び出し側、各言語版、使用者プロジェクトの呼び出し側とサンプルをまとめて揃えてからリリースする。上流だけ変えて下流が古い約束のまま動いているものは、変え終えていないとみなす。
- 直すのは欠陥そのものであり、その場で直す。再発を防ぐために新しく立てるゲートは、立てる時期を `sop-first.md`「境界」節に従う。
```

## ポジティブコントロールはユニットごとに固定し三箇所の正式実行を一致させる —— 待議

| 項 | 内容 |
|---|---|
| 元どこにあったか | 共有 SOP `rules/test-discipline.md` の小節「ポジティブコントロールは**すべての**被試験アームに対して実行しなければならない」内の 3 条項、0.0.64 以降（2026-10-11 リリース） |
| 撤回 | 2026-10-16、「検証装置またはテスト入口を新設する前に既存のものを探す」の撤回決定と同じ |
| 状態 | 待議：規則ではなく、実行を拘束しない |
| 規則にするため不足しているもの | 一道の赤になる検査：実行前登録、ユニットテストのユニット表、再実行登録の 3 箇所の正式実行リストを項目ごとに比較し、1 箇所でも欠けていれば赤とする。各セルのコントロール測定値が十分であるかは依然として判定不能 |

```text
- **对照按单元钉，不并起来判。** 正式跑切成几格（档、族、域这类）的，每一格判了哪几条判据，那一格自己的正式跑里就要有那几条判据的对照读数；单元测试按格写死各格的期望集，不拿几格的读数取并集去判。
- **登记时逐格写出对照由哪一跑担。** 跑前登记写判据集合时，按格列出每条判据的对照落在哪一条正式跑；某一格没有一条正式跑担得起，就补一跑，或者那一格不判那条判据。
- **登记、单元测试、复跑三处的正式跑逐条对得上。** 登记里的每条正式跑，在单元测试的单元表与复跑登记里都找得到；少一处就是那一格没人对照。

日本語訳：

- **対照はユニットごとに固定し、合算して判定しない。** 正式実行をいくつかのマス（層、族、ドメインなど）に分けた場合、各マスが判定する判定基準の対照の読み値は、そのマス自身の正式実行に含まれていなければならない。単体テストはマスごとに各マスの期待集合を固定し、複数マスの読み値の和集合で判定しない。
- **登録時に、対照をどの実行が担うかをマスごとに書く。** 事前登録で判定基準の集合を書くとき、各判定基準の対照がどの正式実行に載るかをマスごとに列挙する。あるマスで担える正式実行がなければ、実行を一つ足すか、そのマスではその判定基準を判定しない。
- **登録、単体テスト、再実行の三箇所の正式実行が一件ずつ一致する。** 登録にある各正式実行が、単体テストのユニット表と再実行登録の両方に見つかる。一箇所でも欠ければ、そのマスは誰も対照していない。
```
