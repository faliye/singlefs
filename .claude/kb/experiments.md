# 待做实验

**每条实验在开跑之前必须先写清三样：测什么、判据是什么、怎样才算失败。**
判据写不出来的，说明问题还没想清楚，不许开跑——跑完再定判据等于自己给自己发证书。

遵守 `singlefs-ai-sop/rules/test-discipline.md`：N≥5 轮，
判「通过」要全通过、判「失败」要全失败，两侧都不满足就报「不稳定」。

## E1 节点大小 vs 可恢复性 —— 未跑（依赖 D8 定案与 checker）

**背景**：大节点省 seek、树更浅（bcachefs 用 128K–256K），
但**一个坏节点损失的范围随节点大小线性放大**，与本工程的可重建性目标直接冲突。
两边都要量，不能只挑一边说话。

**自变量**：节点大小 16K / 32K / 64K / 128K / 256K。

**测什么**

| 指标 | 口径 |
|---|---|
| 单节点损坏的爆炸半径 | 随机破坏 1 个元数据块后，**变得不可达的 key 数**（不是字节数——字节数会被节点大小本身带偏） |
| 全盘扫描重建的成功率 | 破坏 K 个节点后，靠自描述块头全盘扫描能重建出的 key 占比 |
| **可达但值陈旧或错误的 key 数** | 把重建出的 keyspace 与模型（那个理想文件系统 HashMap）逐 key 比对，**与「不可达」分开报两个数** |
| 查找代价 | 一次点查平均读多少个块；树高 |
| 元数据总量 | 同一份数据集下的元数据字节数 |

**判据**：在「全盘扫描重建成功率 ≥ 目标线」的前提下，取查找代价最低的那个节点大小。
目标线本身要先定——**这一步不能等实验结果出来再定**。

**怎样才算失败**：如果各档之间爆炸半径没有可分辨的差异，
说明破坏注入的方式不对（比如只破坏了叶子、或者破坏点没落在被引用的节点上），
**整轮作废重做**，不许拿「看起来差不多」当结论。

⚠️ **「可达但值陈旧」这一列不是锦上添花，是这个实验的判别力缺口。**
纯路由的内部节点丢了，损失的只是路由，叶子自带块头，扫描重建是**幂等**的；
而一旦内部节点里存了别处没有第二份的数据（例如消息缓冲区里还没下刷的更新），
丢了它损失的就是**数据**，重建出来的树可以块头对、校验和对、Merkle 链对——
**I-1.x 与 I-2.x 全绿，内容却是旧的**。
[invariants.md](invariants.md) 里现有的不变量没有一条能检出这一类。
不加这一列，E1 会对「内部节点存数据」这类设计报出一个漂亮的重建成功率，
而那个数字什么也没保证。

**前置**：D8 定案、mkfs、checker、以及一个能定点破坏镜像的工具。

**顺带要产出的**：一条 mkfs 用的确定性选取规则——
输入设备特性（旋转 vs SSD、容量、擦除块/zone 大小），输出节点大小。
同样输入必须得到同样输出，且 mkfs 要打印出选取理由。
**测试一律显式钉死取值，不许用自动值**（见 decisions.md D8）。

## E2 key 布局对递归遍历的影响 —— 未跑（依赖 D8 定案）

**背景**：见 [decisions.md](decisions.md) D8「key 布局」。
按 inode 编 key 时 scan 到底慢多少，决定要不要引入 locality 机制。

**判据**：在同一数据集上比较递归遍历耗时——
按 inode 编 key、按 inode + locality 前缀编 key、（可选）按全路径编 key。
若前两者差距小于测量噪声，locality 机制就不必做。

**怎样才算失败**：三档全都跑不出差异，多半是数据集太小或缓存全命中，
换更大数据集并清缓存后重做。

## E3 意图日志的断电语义 —— 未跑（依赖事务层与 checker）

**背景**：无界操作走「写意图 → 分批 → 可续做」，
其正确性全押在「续做是幂等的」和「中间状态都合法」这两条上。
见 [decisions.md](decisions.md) D8「断电之后怎么办」，对应不变量 I-4.4 / I-4.6 / I-4.7。
**「续做幂等」不在不变量清单里**——它要比对两个镜像，单镜像判不了；
本实验的判据③就是这条性质的唯一权威表述。

**做法**：对一个含大文件/大目录的镜像发起无界操作（truncate 大文件、删大目录），
用块层写记录在**每一个**可能的崩溃点截断、重放、跑 checker，
然后续做至完成，再跑一次 checker。

**判据**：全部崩溃点上——
① checker 无报错；② 续做后达成目标状态；③ 对同一意图重复续做两次，结果不变。

**怎样才算失败**：如果所有崩溃点都「恰好」落在批与批之间，
说明截断粒度太粗，**没有真正测到批内断电**——整轮作废，把粒度降到单次写请求。
这是本实验最容易骗过自己的地方。

## E4 范围重建 vs 逐项修改的交叉点 —— 未跑（依赖 D8 实现）

**背景**：无界操作两条实现的切换判据，见 [decisions.md](decisions.md) D8。
现在写在文档里的「机械盘约 1%、SSD 约 10%」是**推理，不是实测**，必须量出来。

**自变量**：受影响比例 K/N（0.1% / 1% / 5% / 10% / 30% / 100%）×
介质（QEMU 模拟旋转盘 / SSD）× key 连续与否（连续范围 / 随机散布）。

**测什么**：完成同一操作的耗时与写放大，两条实现各跑一遍。

**判据**：找出每种「介质 × 连续性」组合下两条曲线的交叉点，
写成一个可计算的式子放进代码，不是放进注释。

**怎样才算失败**：
- 若「连续」和「随机散布」两组的交叉点没有明显差异，
  说明范围重建其实没走到整节点丢弃那条路径，**实现有问题，整轮作废**。
  这是本实验的判别力所在——两组必须分得开。
- 若两条曲线在全区间不相交，说明有一条实现从头到尾都更差，
  那就别做分支，直接删掉差的那条（`.claude/rules/fs-design.md`：判据写不出来就只做一条）。

## E5 nonce 唯一性 × 崩溃点重放 —— 未跑（依赖事务层、加密实现与 checker）

**背景**：[invariants.md](invariants.md) I-6.1 与 I-6.5。
nonce 重用在 ChaCha20 这类流密码下**直接泄漏明文**，而它不产生任何读写错误、
不触发任何校验失败——不主动去查就永远不会被发现。
危险窗口在崩溃之后：数据先用某个 nonce 写盘，之后才把指针插进树，
所以不干净关机后存在「用过但树里查不到」的 nonce
（bcachefs 的同类问题记在 [prior-art.md](prior-art.md) 6.3）。

**做法**：对开了加密的镜像跑随机写 + 覆盖写 + 截断负载，块层记录全部写请求；
在**每一个**崩溃点截断、重放、恢复，恢复后继续写一段新数据；
全程收集每个块的 (密钥代号, nonce) 二元组。

**判据**（三条全中才算通过，N≥5 轮全通过）：

1. 全部崩溃点上，二元组无重复。
2. 恢复后新分配的 nonce 严格大于记录在案的水位。
3. 崩溃前已写盘但未进树的那些 nonce，**确实出现在收集结果里**——
   否则第 1 条的「无重复」什么也没证明。

**怎样才算失败**：把水位机制关掉之后这个检查**仍然全绿**，
说明扫描根本没看到崩溃前写出去的那些 nonce，**检查没有判别力，整轮作废**。
这一步必须先做：先让它红，再让它绿。

**前置**：事务层、加密实现、块层写记录、checker 的 I-6.1 / I-6.5 检查。

## E6 加密算法选型 —— 已跑（2026-08-27，两档 CPU 特性）

**结论**：**没有单一赢家，快慢随 AES-NI 反转，且幅度很大。**
有 AES-NI 时 AES-256-GCM 快 1.5–3.2 倍；屏蔽 AES-NI 后 ChaCha20-Poly1305 快 3.7–4.4 倍。
⇒ [decisions.md](decisions.md) D9 未答项 3 的答案是**运行时按 CPU 特性选**，不是格式里钉死一个。

**口径**：QEMU 8.2.2 + KVM，宿主 CPU 暴露 `aes`；来宾侧用 `-cpu host` 与 `-cpu host,-aes` 两档。
每档每种算法每个单元大小各加密 256 MiB。单核，**原地加密（`encrypt_in_place_detached`）、
缓冲预分配**，循环内不分配——否则测到的是 allocator 不是算法。
`RustCrypto` 的 `aes-gcm` 0.11.1 与 `chacha20poly1305` 0.11.0。
复跑：`VM_CPU="host,-aes" bash research/scripts/vm-bench.sh <musl 二进制>`。

### 实测（单核吞吐，MiB/s，原地加密、缓冲预分配）

| 单元 | AES 有 NI | AES 屏蔽 | ChaCha 有 NI | ChaCha 屏蔽 |
|---|---|---|---|---|
| 4 KiB | **3888.51** | **267.55** | 1192.00 | 1192.59 |
| 16 KiB | 4097.12 | 271.74 | 1489.67 | 1498.21 |
| 64 KiB | 4126.31 | 273.08 | 1589.36 | 1598.56 |
| 256 KiB | 4136.52 | 273.15 | 1616.59 | 1625.09 |

**赢家**：有 AES-NI → AES 快 2.6 倍（64K）到 3.3 倍（4K）；
无 AES-NI → **ChaCha 快 4.5 倍（4K）到 5.9 倍（256K）**。

### 单元大小：增益在 16 KiB 之后基本饱和

从 4 KiB 放大到 64 KiB，吞吐只多 **6.1%（AES）/ 33.3%（ChaCha）**；
再放大到 256 KiB 只多 0.2% / 1.7%。

⚠️ **这条直接答 [decisions.md](decisions.md) D4 的未定项**（校验和粒度与随机小读的张力）：
加密/校验单元从 4 KiB 放大到 64 KiB **买到的吞吐是个位数到三成**，
而随机小读被迫读取并校验的量是 **16 倍**。⇒ **单元不该大。**

### 阴性对照贯穿整条扫描，不是只在一个点上成立

ChaCha20-Poly1305 在四个单元档上受屏蔽的影响分别是 **+0.05% / +0.57% / +0.58% / +0.53%**。
它不使用 AES-NI，所以它必须不受影响——四档全中说明那个 CPU flag 只作用在该作用的地方。

**另一个未经安排的对照**：两档之间 `tagchk`（认证标签首字节之和）**逐位相同**
（AES 8341413 / 2090216 / 516605 / 131087，ChaCha 同理）
⇒ 两档跑的是同一份计算，差别只在快慢。

### 失败条款的判定：通过，且带一个自带的阴性对照

E6 的失败条款是「屏蔽 AES-NI 对 AES-GCM 的数字没有可分辨影响 ⇒ CPU flag 没真生效，整轮作废」。
实测 AES-GCM 掉了 **14.3 倍**，远超任何噪声。

**而 ChaCha20-Poly1305 在两档之间纹丝不动（4K 档差 0.01%）**——它不使用 AES-NI，
所以它**必须**不受影响。这是一个未经安排却成立的阴性对照：
它证明那个 CPU flag 不但生效了，而且**只作用在该作用的地方**，不是整机变慢。

### 触发了第二条判据：加密必须能并行化

E6 立项时写明「若两者的单核吞吐都低于单盘顺序带宽，则加密必须并行化——
那会改变写路径的结构，属于会改变第一段代码长什么样的结果，必须回写 D9」。

**无 AES-NI 时 AES-GCM 只有 267.55 MiB/s（4 KiB 单元）**，而任何现代 NVMe 的顺序带宽都在 1 GB/s 以上
（本机 nvme0n1 3.6 T，未单独实测其顺序带宽——这一句是按介质类别推的，不是量的）。
⇒ **在没有 AES-NI 的机器上，单核加密是瓶颈，加密路径必须支持并行。**

### 本实验证明不了什么

- **不是多核扩展比。** E6 立项时列的「多核扩展比」与「门禁挂钟增量」两项本轮未测。
- **不覆盖解密与鉴权失败路径。**

**前置**：无（已跑完）。

## E7 离线索引 harness —— 首轮已跑（2026-08-27）

**背景**：E1 / E2 / E4 都写着「依赖 D8 定案与 checker」，而 D8 的取值又要等这些实验，
形成死锁。破法是承认一件事：**索引结构的选型不需要一个完整的文件系统**，
只需要一个能在真实块设备上跑的独立索引引擎与一套负载回放器。

**做什么**：写一个不含 VFS、不含 POSIX 语义、不含崩溃恢复的**索引 harness**——
只有「在块设备上维护一棵树 / 一个 KV，支持 insert / point query / range scan / 范围删除」。
在它上面把候选结构各实现一份，用同一组负载回放对比。

**候选结构**（依据 [prior-art.md](prior-art.md) 7.3）：

| 候选 | 要量的东西 |
|---|---|
| B+tree（基线） | 点查最优时的读代价上限 |
| 日志结构节点的 B+tree（D8 现方向） | 节点内追加 + 定期重排的实际收益与重排代价 |
| Bε-tree（内部节点带消息缓冲） | 小写吸收能力、点查退化多少 |
| Bε-tree + size-tiering + 过滤器（SplinterDB 形态） | 相对纯 Bε-tree 的写放大与点查差异 |
| 上述任一 + key-value 分离（WiscKey 形态） | 大 value 移出索引后，compaction / 重排代价降多少，range scan 退化多少 |

**测什么**：写放大、读放大、点查延迟分布、range scan 带宽、空间放大、CPU 占用。
**每项都要分「冷缓存」和「热缓存」两组**——热缓存下所有结构都会看起来差不多。

**判据**：得到一张「负载形态 × 结构」的表，每格是上述六个指标。
**这张表本身就是产出**，不需要它选出唯一赢家——D8 要的是「参数怎么取」，不是「选哪棵树」。

**基线必须是 D8 现方向，不是教科书 B+tree。**
D8 已定的形态是「日志结构节点 + write buffer 前端」，**它本身就是一个吸收小写的机制**。
拿排序节点的朴素 B+tree 当基线，测出来的是「有没有批量」，不是「消息缓冲比 write buffer 多买到什么」。
文献里的数字全部相对朴素基线：BetrFS 对的是 ext4/btrfs/XFS/ZFS，SplinterDB 对的是 RocksDB，
**没有一个对照组带 write buffer 前端**——消息缓冲相对 D8 现方向的边际收益，现有文献一个数字都没给。

**怎样才算失败**（分两类，不许混）：

| 现象 | 判定 | 理由 |
|---|---|---|
| 各候选在所有负载上差异都小于测量噪声 | **整轮作废**，加大数据集并清缓存重做 | 多半是数据集小到全进了页缓存 |
| Bε 在**无批量对照组**（朴素排序节点 B+tree）上没有显著优于对照 | **实现有问题，整轮作废** | 这是阳性对照：效应在文献里确凿存在，测不出来就是实现错了（缓冲比例设成 0、每次插入都触发下刷之类） |
| Bε 相对 **D8 现方向基线**没有优势 | **这是合法结果，如实记录** | 它说明消息缓冲没买到 write buffer 还没买到的东西——这正是本实验要回答的问题 |

⚠️ **必须保留那个无批量对照组**，否则「没有优势」分不清是「结论如此」还是「实现坏了」。
两个对照组一起跑，才同时具备判别力和可证伪性。

### 首轮结果（2026-08-27，N=5 轮、五个不同种子、带块层独立读数）

**更新路径的设备 I/O（每次操作）与点查的读次数**

| 臂 | 更新 io/op（中位） | 极差/中位 | 点查 读/次 |
|---|---|---|---|
| **sorted_bplus**（无批量对照，阳性对照） | 1.9378 | 0.0% | 1.241 |
| **logstruct_wb**（D8 现方向：日志结构节点 + write buffer 前端） | 1.5755 | 0.2% | 1.241 |
| **betree**（内部节点带消息缓冲） | **0.4900** | 0.9% | **1.178** |

> **Bε 相对 D8 现方向：3.22 倍**（更新路径）
> **D8 现方向相对无批量对照：只有 1.23 倍**

**这就是 [decisions.md](decisions.md) D11 前置 2 要的那个数。**
此前文献里一个都没有——BetrFS 对的是 ext4/btrfs/XFS/ZFS，SplinterDB 对的是 RocksDB，
**没有一个对照组带 write buffer 前端**。

#### 三条硬要求逐条判定

| 要求 | 观测 | 判定 |
|---|---|---|
| 1. 每条臂真的实现它声称的结构 | 把两条攒批臂的核心判据换成常量（缓冲=1）：logstruct_wb 0.866 → **1.502**（+73%），betree 0.171 → **1.702**（+897%）；sorted_bplus 不变（它本来就没缓冲） | **通过**。结构真的在参与 |
| 2. 摊销架构对称 | logstruct_wb 与 betree 共用同一个节点缓存、同一个 checkpoint 节奏（每 4096 次操作）。sorted_bplus 故意写穿——**它是无批量对照，不参与对称性要求** | **通过** |
| 3. 块层独立读数 + 该校验路径本身有判别力 | 五轮九格程序计数器与 `/sys/block/vda/stat` **逐轮相符**；摘掉 `O_DIRECT` 后块层读数全部归零而程序计数器不变，挂钟掉 73 倍 | **通过** |

#### 两条解析对照（第三条独立路径）

- `sorted_bplus`：每次 1 写 + `(1 − 64/1024)` 读 = **1.9375**，实测 **1.9378**。
- `logstruct_wb`：512 个随机 key 落到约 400 个不同叶子、每叶一读一写 ⇒ 约 **1.56**，实测 **1.5755**。

⚠️ **低极差不是确定性假象**：五轮种子各不相同（101/202/303/404/505），
另两条臂的极差是 0.2% 与 0.9%。`sorted_bplus` 的 0.0% 来自它每次操作恰好一次写、
读次数是 20 万次采样上的缺页率平均。

| 64 | 6% | 1.9378 | 1.5755 | 0.4900 | **3.22×** | 1.23× |
| 264 | 25% | 1.7437 | 1.5755 | 0.3176 | **4.96×** | 1.11× |
| 1057 | **100%** | 1.0051 | **0.2515** | 0.1678 | **1.50×** | **4.00×** |

**点查 读/次（中位）**：三臂在每一档上几乎相同（2% 档 1.78/1.78/1.72，
100% 档全为 0.053），**Bε 略优而非略劣**——原因见外推边界那一节。

块层与程序计数器：**60/60 格相符**。

#### 两条结论

**1. `Bε / D8` 不是单调的，峰值在中间。**
2% → 25% 一路升到 4.96×，而缓存装得下整棵树时**骤降到 1.50×**。
⇒ **Bε 的优势条件是「树装不下缓存」**——与 E12 里 D5 的优势条件
（「计数器表装不下缓存」）同构：两者都是「把随机查找换成顺序/批量」，
而那件事只在装不下时才值钱。

**2. D8 现方向在 2% / 6% / 25% 三档的 io/op 逐位相同（1.5755）——缓存对它完全不起作用。**
机制：**write buffer 按叶排序之后，每次 flush 就是一次覆盖整个叶子空间的顺序扫描，
而 LRU 对「反复的、大于缓存的顺序扫描」命中率恰好为 0。**

干预证实（保持同叶聚合不变，只打乱**组的处理顺序**）：

| 缓存档 | 排序 flush | 打乱组顺序 | |
|---|---|---|---|
| 25% | 157,739 读 | **143,251 读（−9.2%）** | 顺序确是驱动量 |
| 100% | 1,024 读 | **1,024 读（完全相同）** | **阴性对照**：全装得下时顺序无关 |

⚠️ 那 9.2% 是**下界**：洗牌种子按组数派生，组数相同就得到相同排列，
跨 flush 有相关性，削弱了效果。**方向与阴性对照都成立，量级偏保守。**

> **由此得到一条设计要求：如果 write buffer 要排序，节点缓存必须是抗扫描的
> （2Q / LRU-K 之类），否则排序摧毁局部性而不是创造它。**
> 这一条对 [decisions.md](decisions.md) D8 有直接影响，而 D8 正文目前只写了
> 「write buffer 批量攒起来排序去重后批量插入」，**没有对缓存策略提任何要求**。

### 节点大小扫描（2026-08-27，3 档 × 5 种子 = 15 轮，**固定约 1 MB 缓存预算**）

**口径的要害：内存预算固定，节点越大，装得下的节点越少。** 这才是真实的取舍。

| 节点 | 缓存节点数 | 占树 | | 无批量对照 | D8 现方向 | Bε |
|---|---|---|---|---|---|---|
| **4 KiB** | 264 | 25% | io/op | 1.7437 | 1.5755 | **0.3176** |
| | | | 字节/次 | 7,142 | 6,453 | **1,301** |
| | | | 点查读/次 | 0.7766 | 0.7766 | 0.7361 |
| **16 KiB** | 66 | 6% | io/op | 1.9359 | 1.5755 | **0.3994** |
| | | | 字节/次 | 31,718 | 25,812 | **6,544** |
| | | | 点查读/次 | 1.2249 | 1.2249 | 1.1624 |
| **64 KiB** | 16 | 2% | io/op | 1.9844 | 1.5755 | **0.6384** |
| | | | 字节/次 | 130,050 | 103,249 | **41,841** |
| | | | 点查读/次 | 1.7792 | 1.7792 | 1.7175 |

块层与程序计数器：**45/45 格相符**。

#### 结论：固定内存预算下，大节点在三个轴上全都更差

I/O 次数翻倍（Bε 0.318 → 0.638）、字节数 **32 倍**（1,301 → 41,841）、点查读次数翻倍。
机制：**节点越大，同样的内存装得下的节点越少，命中率掉得比「每次读更多」赚回来的更快。**

`logstruct_wb` 的 io/op 在三档**逐位相同（1.5755）**——同一个原因（排序 flush ⇒ 顺序扫描 ⇒ 命中率 0），
节点大小不改变它触到的节点个数；但它的字节数涨了 **16 倍**。

⚠️ **它撑不起「按介质分层布局」**：[decisions.md](decisions.md) D8 约束 1 已定节点大小是
mkfs 时写进超级块的格式参数——**参数就够，不需要为此多开一套布局**
（D12 未定项 1 已按此定案为 2 套）。
本实验把「一次节点读」记为 1 次设备 I/O，**不论节点多大**；
在虚机 + 宿主文件（近似 SSD）上**字节主导**，所以大节点是净亏。

**寻道主导的一侧已实测（见下方「寻道主导档」），结论同向而非相反**：
在「每次 I/O 代价相同、与大小无关」这个极端上，大节点仍然不赢。
⇒ **小节点在字节主导与寻道主导两端都赢**，节点大小不必按介质取相反方向。

⇒ 对 [decisions.md](decisions.md) D8「不照抄 128K–256K」这条：**两端都得到支持**。

### 寻道主导档（2026-08-27，QEMU 限流 4000 IOPS，**2 档 × 5 种子 = 10 轮**，两端对比）

**N=5**：两个配置各 5 个种子（11/22/33/44/55），10 轮全部有完成标记，无作废轮。

**口径**：本机没有旋转盘（`lsblk` 确认只有 nvme0n1，ROTA=0），所以这是
**模型化设备上的实测，不是旋转盘实测**。模型 = QEMU `throttle-group x-iops-total=4000`，
不设 `x-iops-size` ⇒ **每次 I/O 代价相同、与请求大小无关**，即寻道主导的极端。
复跑：`VM_IOPS=4000 bash research/scripts/vm-bench.sh <musl 二进制> 11 none <cache> <node_pages>`。

**限流路径自证会红**：同样 300 次直接读，不限流 0.18 s；限流 100 IOPS 用 2.89 s
（≈ 300/100 = 3 s）。不做这一步就分不清「没测出差异」和「限流根本没生效」。

**模型自证**：挂钟与「I/O 次数 ÷ 限流值」的吻合度（中位数，N=5）

| 档 | 臂 | io/op 中位 | 预测挂钟 | 实测挂钟中位 | 误差 |
|---|---|---|---|---|---|
| 4 KiB | 无批量对照 | 1.742435 | 87.12 s | 87.13 s | 0.01% |
| 64 KiB | 无批量对照 | 1.984590 | 99.23 s | 99.18 s | 0.05% |
| 4 KiB | Bε | 0.317940 | 15.90 s | 15.90 s | 0.00% |
| 64 KiB | Bε | 0.639135 | 31.96 s | 31.91 s | 0.15% |
| 4 KiB | D8 现方向 | 1.574990 | 78.75 s | 78.76 s | 0.01% |
| 64 KiB | D8 现方向 | 1.574990 | 78.75 s | 78.65 s | 0.13% |

⇒ **字节数在这个设备上完全不计价**：64 KiB 档每次操作读 130,041 字节、4 KiB 档 7,137 字节
（**18 倍**），而挂钟只由 I/O 次数决定。模型如实做到了它声称的事。

**块层校验仍然成立**：限流是在 QEMU 栈里插了一层 `throttle` 块驱动
（`-blockdev driver=throttle` 取代原来的 `-drive`），I/O 路径变了，
所以块层对照不能默认还成立。实测 **12/12 格逐位相符**（两个配置 × 三条臂 × update/query，
程序自数的 reads/writes 与来宾 `/sys/block` 的 `blk_r`/`blk_w` 完全一致）。
该校验路径此前已自证会红——摘掉直接 I/O 后块层计数归零而程序计数纹丝不动。

**结果**

| 臂 | 4 KiB 挂钟中位 | 64 KiB 挂钟中位 | 大节点 | 各自极差 |
|---|---|---|---|---|
| 无批量对照 | 87.13 s | 99.18 s | **差 13.8%** | 0.06% / 0.32% |
| D8 现方向 | 78.76 s | 78.65 s | 持平（−0.14%） | 0.09% / 0.06% |
| Bε | **15.90 s** | 31.91 s | **差 100.7%** | 0.72% / 0.33% |

**极差 ≤0.72% 不是可疑，是机制性的**：挂钟 = I/O 次数 ÷ 限流值，
而 I/O 次数在五个种子间只差 0.06%（4 KiB 无批量对照档：1.742510 / 1.741970 /
1.742720 / 1.742435 / 1.741695）。**种子确实在变**——五个值各不相同，
只是这个负载的结构是确定的，变的只有 key 序列。
极差之小反过来又确认了「限流确实主导挂钟」。

**⇒ 寻道主导的极端上大节点仍然不赢，没有反转。**

原因：自变量是**固定内存预算**，节点越大装得下的越少、缺失率上去，
**节点读次数反而更多**——这个效应压过了「一次读更多」。

### 寻道主导档证明不了什么

- **不是旋转盘实测。** 是模型化设备。
- **模型不含顺序合并。** 真实机械盘上相邻的小 I/O 会被合并成一次寻道，
  而 QEMU 的 IOPS 限流逐个计费 ⇒ **本模型高估了小节点的代价**。
  小节点在被高估的情况下仍然赢，**所以这条局限让结论更稳，不是更弱**。
- **只测了两端（4 KiB 与 64 KiB），没测 16 KiB 中间档。** 单调性未验证。

### 这组数字不能证明什么

- ⚠️ **树很小**：1024 个叶子 + 32 个内部 + 1 个根 = 1057 节点（约 4.3 MB），缓存 64 页（**6%**）。
  真实的树大得多，而**缓存/树比正是驱动量**——这个比一变，三条臂的差距都会变。
- ⚠️ **负载是对已存在 key 空间的随机更新，没有分裂/合并**。
  分裂行为不在射程内，而 BetrFS 自陈相对更差的情形正是「节点切分与合并落在关键路径上」。
- ⚠️ **点查那一列反直觉，原因是配置带来的**：查询用的是与更新**同一个均匀随机分布**，
  于是最近更新过的 key 有很大机会还在缓存住的根/内部缓冲里，省掉一次叶子读。
  **对冷 key 的查询会得到相反结果**——这条要单独量，目前没量。
- ⚠️ 节点固定 4 KiB、值固定 8 字节。D8 已定节点大小是**每套布局的格式参数**，属 E1 射程。

**口径**：`e7-index`，musl 静态，xorshift64\*；扇出 32、1024 叶、每叶 64 key、
key 空间 65536；节点 4 KiB、每节点 255 槽；缓存 64 页、write buffer 512 条、
Bε 缓冲 200 条、checkpoint 每 4096 次操作；每轮 20 万次更新 + 2 万次点查。
虚机 2048M / 4 vCPU / 64 MiB virtio 盘，`cache=none,aio=native`；宿主 32 核 / 60 GiB；QEMU 8.2.2 + KVM。

### 三条从 E12 学来的硬要求（不满足就别开跑）

E12 的教训是具体的：它的一条臂声称实现某个机制，实际是一个 stub，
而两臂的摊销架构还不对称——**结果那个 17 万倍里，机制与攒批各贡献多少拆不开**。
本实验不许重犯：

1. **每条臂必须真的实现它声称的结构。**
   臂的名字叫什么，代码里就得有那个东西。
   ⚠️ **自检方式**：把该臂的核心判据换成一个恒真/恒假的常量，结果**必须显著变化**；
   没变化说明那个结构根本没参与，**整轮作废**。
   （E12 的臂 A 判据换成掷硬币结果一样——那就是这条自检会红的形态。）
2. **所有臂的摊销架构必须对称**：同一个批量窗口、同一个刷盘时机、同一套发布语义。
   [decisions.md](decisions.md) D16 已定 checkpoint，**所有臂都在同一个 checkpoint 节奏下跑**。
   否则量到的是「谁攒批」，不是「谁的结构好」。
3. **设备 I/O 必须有块层独立读数**（虚机内 `/sys/block/*/stat`），逐格与程序内计数器比对；
   且**这条校验路径本身要用故障注入证明有判别力**（摘掉 `O_DIRECT`，块层读数必须归零）。
   `singlefs-ai-sop/rules/evidence-discipline.md`：校验路径本身也要证明它会红。

### 另加一个自变量：缓冲里放幂等完整值还是增量

[decisions.md](decisions.md) D11 的代价判据已被改写为「缓冲里放的是**幂等完整值**（合并=后者胜，
checker 不需要理解 value 语义）还是**增量 Δ**（合并依赖 value 语义）」。
**这一条要作为自变量量出来**：同一条臂在两种条目形态下的写放大与合并代价各是多少。
它决定 D11 的代价 1 成不成立，而那条判据横跨 D8 与 D11。

**前置**：块设备、一个负载回放器、Rust 工具链。**不需要文件系统、不需要 checker、不需要 D8 定案。**

**它解掉什么**：E1 的节点大小、E2 的 key 布局、E4 的范围重建交叉点、
E8 的大小文件分流、E9 的全路径 vs inode 索引——五个实验的主体部分都可以在这个 harness 上先跑一遍，
只把「需要真实 POSIX 语义与崩溃恢复」的那部分留到文件系统存在之后。

## E8 大文件与小文件是否该走不同写路径 —— 层 A 已跑（2026-08-28），层 B 未跑

**结论**：

1. **交叉点不是文件大小的某个自然刻度，就是内联阈值本身。**
   收益全部集中在 ≤ 阈值（本轮取 3584 B）的档位：64 B 与 1 KiB 上分流相对不分流
   省 2.9–94.6 倍写放大；**4 KiB 及以上四条臂逐格相同（1.00）**，一档收益都没有。
2. **交叉点对指针宽度不敏感。** 指针从 256 位加宽到 320 位，
   四种写形态 × 七档大小上的交叉点位移全部在 **±0.5% 以内**（最大 −0.48%）。
   ⇒ **E8 的分流判据不必等 [decisions.md](decisions.md) D19 定案。**
3. **追加写会在操作中途跨过阈值，因此阈值不是合格的分支变量。**
   4 KiB 文件分 8 次追加时，前 7 次的累计大小都在阈值以下，
   内联臂因此仍拿到 6.96 倍收益——而同样的 4 KiB 文件一次写完时收益恰好是 1.00。
   **同一个文件大小，两个写形态，判据落在阈值两侧。**
   ⇒ 直接答掉本实验判据 3：`.claude/rules/fs-design.md` 硬要求 5
   「分支变量不许在操作中途改变」**被这条分支违反**，除非另设跨阈值迁移路径并单独验崩溃语义。
4. **内联的代价在读侧，而且很大。** 1 KiB 档内联把每条 inode 记录撑到约 1152 字节，
   每叶装得下的记录数塌下来，叶子数量暴涨：设备读次数从 47 涨到 **293（6.2 倍）**，
   每文件元数据字节从 692 涨到 1644。
   ⇒ **写放大与读次数在这一档上方向相反**，只看写放大会选错。
5. **消息层臂在写侧一律劣于内联臂**，因为每条消息在落到叶之前要在每一层被重写一次：
   下推字节占其元数据总量的 20.6%（一次写完 64 B）到 **91.0%**（随机小写 1 KiB）。
   4 KiB 追加档它甚至比不分流还差（0.98 倍）。

**口径**：纯记账实验，无设备、无虚机、无文件系统。四条臂**共用同一个记账器与同一棵索引树**，
差别只在「数据放哪、插什么记录」。节点 16 KiB / 块 4 KiB / key 16 B /
内联阈值 3584 B / checkpoint 攒批 64 / 节点缓存 256。确定性，无随机种子依赖
（随机小写用固定种子 7）。代码 `research/e7-index-bench/src/bin/e8_split.rs`，
`cargo run --release --bin e8-split`。

**为什么不放进虚机**：写放大与每文件元数据字节数是格式上的算术，
放进虚机只会给确定性的数字掺上噪声。端到端吞吐/延迟是层 B 的事。

### 两个对照，两个都自证过会红

| 对照 | 断言 | 自证 |
|---|---|---|
| **阳性** | 4096 个 64 B 文件在不分流臂上数据字节 == 4096 × 4096（整块分配的钱真的付了），内联臂数据字节 == 0 | 把整块取整改成按字节计，`pos_ok` 立即变 false 且整轮作废退出（实测） |
| **阴性** | 1 GiB 文件上内联阈值够不着，内联臂与不分流臂的 `dev_bytes` / `read_ops` / `node_writes` **逐位相同** | 把阈值判定改成恒真，该断言变红（实测） |

⚠️ **阳性对照只断言机制，不断言「内联赢多少倍」。**
那个倍数随 checkpoint 攒批大小变（batch=1 时跌破 2 倍），
把它写进对照会让一个合法结果被误判成模型坏了。

五条单测全部经过定向破坏证明会红：改坏整块取整 / 扇出不看指针宽度 / 阈值判定失灵 /
记账器多一条出口，各自击红对应的测试。

### 本轮修掉的一个建模缺陷

首轮 `inline` 与 `msgbuf` 两列**逐格完全相同**——消息层在模型里没有任何区别于内联的行为，
那不是发现，是缺陷。修法：消息插入不碰目标叶（这是消息层买到的东西），
checkpoint 时按 key 排序后下推，并按 `payload × 树深` 记下推重写的字节（这是它付的钱）。
**收益与代价成对建模，缺一条就是偏袒。**

### 层 A 测不出来的一格

**消息层在读侧的收益本实验没能测出来。** 它的 `read_ops` 在缓存 4–512 节点、
攒批 1–64 的全部组合上都 ≥ 内联臂（cache=4 时是 621 对 293）。
机制是本模型按「排序位次 / 每叶记录数」定叶归属，消息成批落地时叶映射会整体位移——
**这是建模伪影，不是消息层的性质**。
⇒ 这一列的读数不算数，消息层的读侧收益留给层 B。

### 层 B（未跑）

只对层 A 判出有交叉的那几档（≤ 4 KiB）做端到端 I/O 计数，两种介质。
**前置**：`research/scripts/vm-bench.sh` 已有；跨阈值迁移那条要等文件系统与崩溃点重放。

## E9 key 编码对遍历局部性的影响 —— 已跑（2026-08-28 复跑定稿）

**背景**：[decisions.md](decisions.md) D8 已定 key = `(locality_id, inode, offset)`，
且 `locality_id` **创建时从父目录继承、改名时故意不更新**。本实验量的是这个选择买到多少。

**测什么**：一次递归遍历要发出多少次设备读。四条臂共用同一棵目录树与同一个 LRU：
`FullPath`（按路径分量逐层打包）/ `Inode`（纯创建顺序）/
`Locality`（`(locality << 40) | inode`）/ `Hashed`（**阳性对照**，哈希打散）。

### 结论

**1. 三条真实臂只在「交错创建 + 小节点缓存」下才分得开。**
depth-first 创建（解压 tar 的形态）时 `Inode` 与 `Locality` **逐位相同**——
每个目录的 24 个文件拿到连续的 inode，而 `locality` 是 `path[0]`，
在深度优先创建下是 inode 的单调函数，**两条臂的排序完全一致**。
⇒ 要测出差别必须 `interleave`（目录创建顺序打散，老化的代理）。

**2. 比值强烈依赖节点缓存大小，不是一个常数**（`interleave`，改名 0 次，5 种子取中位）：

| `cache_leaves` | FullPath | Inode | Locality | Hashed | Inode/Locality |
|---|---|---|---|---|---|
| 4 | 122 | 1364 | 1158 | 28367 | 1.178 |
| **8** | 122 | 1317 | 901 | 28367 | **1.462** |
| 16 | 122 | 1231 | 409 | 28267 | 3.010 |
| 32 | 122 | 1058 | 123 | 23265 | **8.602** |
| 64 | 122 | 738 | 122 | 15073 | 6.049 |
| 128 / 256 | 122 | 122 | 122 | 122 | **1.000** |

⇒ **缓存装得下整棵树时四条臂全部相等（122）**，效应消失。
**报「1.46 倍」而不报缓存档，等于报了一条曲线上的一个点。**

**3. `locality_id` 的收益是新树的收益，改名会把它吃光**（`cache_leaves=8`，5 种子取中位）：

| 改名次数 | FullPath | Inode | Locality | Hashed | Inode/Locality | 极差 |
|---|---|---|---|---|---|---|
| 0 | 122 | 1317 | 901 | 28367 | **1.462** | 3.0% |
| 500 | 122 | 1316 | 1217 | 28367 | 1.081 | 2.8% |
| 2000 | 122 | 1315 | 1288 | 28367 | 1.021 | 0.9% |
| 5000 | 122 | 1311 | 1316 | 28367 | **0.996** | 2.5% |
| 20000 | 122 | 1315 | 1312 | 28367 | 1.002 | 1.9% |

⇒ **2000 次子树改名之后优势基本归零，5000 次之后略微反超。**
这给 D8 已经写下的那句「`locality_id` 的收益是新树的收益，不是稳态收益」补上了数——
此前那句话没有任何数支撑。

**4. `FullPath` 在所有档位上恒为 122**，即「一次遍历只读该子树的那几个叶」。
它是遍历局部性的上界。⚠️ 但 D8 已定不采纳全路径 key，理由是改名要重写所有后代的 key——
**本实验不测那笔代价**，只测遍历侧。拿本表去论证「全路径更好」是误用。

### 阳性对照

`Hashed` 在每一格都远差于三条真实臂（28367 vs 122–1364，最大 232 倍）。
⇒ 度量确实在测遍历局部性。**若它测不出哈希打散与其余三条的差别，前三条结论一并作废。**

⚠️ **阳性对照在 `cache_leaves ≥ 128` 那两档失效**（四条臂全部 122）——
那不是「哈希也很好」，是**整棵树装进了缓存，这个度量在那一档没有判别力**。
按 `singlefs-ai-sop/rules/test-discipline.md`「阴性结果要能和『代码没跑到』分开」，
那两档只能读成「测不了」，不能读成「无差别」。

5 个种子（3/7/11/13/17）取中位数。

## E16 journal 的角色：WAL vs 意图日志 —— 记账模型这一半已跑（2026-08-28），延迟那一半未跑

**背景**：[decisions.md](decisions.md) D23 未定项 1，它自陈「**必须先定角色，才能定大小**」。

### 建模时先撞上的一件事：WAL 这一侧其实是两条臂

D23 已定「**分配先于 journal**：journal 记录是**已经写到盘上的东西的发布指令**」。
⇒ **「WAL 的 fsync = 追加一条记录」在本工程不可实现**——记录里点名的块必须已经在盘上。
于是 WAL 裂成两条本质不同的臂，差别不在快慢，在**重放要不要分配器**：

| 臂 | fsync 时写什么 | 重放要不要分配器 | 与 D23 已定项 |
|---|---|---|---|
| `intent` 意图日志 | 脏叶 + 全部祖先 + 根槽 + 一条游标记录 | 不要 | 相容 |
| `wal_full` WAL / 记录点名到根下一层 | 脏叶 + 全部祖先 + 一条记录（**不发根**） | 不要 | 相容 |
| `wal_leaf` WAL / 记录只点名叶 | **只写脏叶** + 一条记录；祖先延到 checkpoint | **要** | **冲突** |

### 实测（20 万次操作 × 3 负载 × 3 档 fsync × 2 档 checkpoint 间隔 = 18 格 × 3 臂）

写放大 = 设备写块数 / 用户写次数；下表取 checkpoint 间隔 1000。
「fsync 块」是 p50，**单位是块，不是时间**。

| 负载 | fsync | intent WA | wal_full WA | wal_leaf WA | intent 环 | wal_full 环 | wal_leaf 环 | intent fsync 块 | wal_leaf fsync 块 | intent 发根 | WAL 臂发根 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| rand | 每次 | 7.000 | 6.002 | **4.101** | 48 B | 104048 B | 107120 B | 7 | **2** | 200000 | 200 |
| rand | 每 10 次 | 4.265 | 4.167 | **3.201** | 48 B | 59728 B | 63920 B | 43 | **11** | 20000 | 200 |
| rand | 不 fsync | 3.101 | 3.101 | 3.101 | 48 B | 3120 B | 3120 B | 0 | 0 | 200 | 200 |
| metaheavy | 每次 | 4.968 | 4.469 | **2.149** | 48 B | 104048 B | 160072 B | 10 | **3** | 200000 | 200 |
| metaheavy | 每 10 次 | 2.776 | 2.727 | **1.698** | 48 B | 10448 B | 116872 B | 56 | **21** | 20000 | 200 |
| seq | 每次 | 1.750 | 1.625 | **1.134** | 48 B | 104048 B | 496072 B | 14 | **9** | 200000 | 200 |

整网格最大臂间总写块数比 **2.31×**。

### 这一轮判决性的四个数

1. **不 fsync 时三条臂写放大逐格完全相等**（阳性对照 1）。⇒ **WAL 的边际收益恰为 0**——
   它买的东西只在组提交拿不到的地方存在。
2. **`wal_leaf` 是唯一买到实质写放大收益的形态**：每次 fsync 的块数降到 1/3.5（rand 7→2）、
   1/3.3（metaheavy 10→3），写放大降 **35–57%**。
3. **环大小差 3 个数量级**：`intent` 恒 48 字节（与吞吐、负载、间隔全部无关），
   两条 WAL 臂 10⁴–10⁵ 字节，且**下限正比于 fsync 率（`wal_full`）或吞吐（`wal_leaf`）**。
4. **根环槽消耗速率差 1000 倍**：`intent` 每次 fsync 发一次根（200000 次），
   WAL 臂只在 checkpoint 发（200 次）。根环槽数有限（D22 未定），这是一项资源速率差，
   不只是写块数差。

### 前两版的三处建模错误，全部由三方论证的另外两条腿抓出来

**这一轮最该记住的不是上面的数，是这三条错误的形状。**

| # | 错误 | 后果 | 谁抓到 |
|---|---|---|---|
| 1 | `wal_full` 的记录按**脏叶**计费，而 D23 明写记录点名**子树根**（条数被扇出封顶 ≤128） | 环峰值虚报最多 **47 倍**，而环大小正是本实验要产出的那个数 | 两条云端腿**各自独立**抓到 |
| 2 | `wal_full` 的 fsync 清空 dirty 之后，区间 checkpoint 的触发条件只看 dirty | **20 万次操作里一次根都没发**（`root=0 ckpts=0`），而守恒检查、三臂互比、单测全部看不见 | 正推腿 |
| 3 | 不发根却把环清零 | `wal_full` 的环峰值虚报低 **4–5 个数量级** | 正推腿 |

⇒ **三条的共同形状：检查只让三条臂互相比，没有把绝对值钉死。** 三条臂一起错时，
互比仍然相等。补救是往守恒检查里加「每条臂必须至少每 `ckpt_interval` 次操作发一次根」，
以及把记录计费、环截断规则各写成一条独立单测。

### 这一轮逼出来的一条格式要求

> ⚠️ **fsync 记录点名的每一项必须自带校验和。**

D4 已定校验和内联进**父指针**，而 fsync 记录点名的东西**其父此刻还没写到盘上**——
`wal_full` 点名子树根、父是尚未发出的根；`wal_leaf` 点名叶、父是尚未写的内部节点。
⇒ **记录必须临时充当父**，否则重放时那些块没有任何完整性凭据。
每项因此从 24 字节涨到 56 字节。**checkpoint 记录不需要**：根在同一次 checkpoint 里发出。
⇒ **这是 WAL 逼进格式的一项开销，此前没有任何地方写过。**

### 口径与已知局限（不许无视）

- 量的是**设备写块数，不是时间**。真实 fsync 延迟还含 FUA 往返与队列排队，**本实验够不着**——
  那一半仍要等 E12 harness 与事务层。**拿本实验的数去谈延迟是误用。**
- 一条记录按「至少占一个块」计（同步发布指令不与后续记录合并）。
- ⚠️ **环的「峰值占用」不等于「环该开多大」。** 本实验量的是占用；而环的**下限**另有来源：
  [decisions.md](decisions.md) D23 死锁 3 要求「任一操作的最坏 journal 占用 ≤ 环大小 / F，F ≥ 2」，
  C6 还要求一个显式的在飞记录数上限（XFS 的对应物是 `XLOG_MAX_ICLOGS 8`，
  2026-08-28 现查 `fs/xfs/libxfs/xfs_log_format.h:25`）。
  ⇒ **`intent` 那个 48 字节是占用，不是它可以只开 48 字节。**
- 几何：完全 128 叉树、内部 4 层、块 4 KiB、根环槽 1 块；记录 `48 + 每项(24 或 24+32)` 字节；
  意图日志记录定长 48 字节。叶=用户数据块，一次操作弄脏 1（rand）/ 2（metaheavy）/ 8（seq）个叶。
  **树高、扇出、记录字段宽度都是模型参数，不是实测值。**
- **记账块自身的 COW 代价完全没建模**（D22 未定）。若它按 checkpoint 次数缩放，
  checkpoint 次数最多的 `intent` 会被进一步拉开劣势。

### 这一轮的实验纪律

- 三臂**共用同一份操作流**，指纹相同才算数（不同即整轮作废，exit 4）。
- **阳性对照 1 对每一条臂都跑**：不 fsync 时三臂的 COW 写与根槽写必须逐格相等。
- **故障注入对每一条臂都做**：注入「不写 journal」后守恒检查必须判红，三臂全部判红。
- **18 个单测全部用变异测试证明会红**，14 条变异逐条命中，脚本 `research/scripts/mutate.sh`。
  ⚠️ 变异跑了三轮，每轮都有「一个测试都没红」的条目，暴露的都是同一种盲区（只互比、不钉绝对值）。
- 两轮运行**逐字节相同**；完整性闸 `emitted=60` == 抓到 60 行。

代码 `research/e7-index-bench/src/bin/e16_journal.rs`，`cargo run --release --bin e16-journal`；
输出 `research/results/e16-journal-2026-08-28.out`。

### 还没做的那一半

- **fsync 延迟分布**（p50/p99，真实时间）：要设备、要事务层。
- **维护代价**（E16 注册时写下的判据 3：两种形态各需多少条不变量、多少个崩溃点类别）：
  这是**推论**不是观测，按 `.claude/rules/three-way-inference.md` 要走三方。

## E17 write buffer 合并的单线程上限与无锁并行 —— 已跑（2026-08-28）

**结论**：

1. **合并本身撑得住，它不是关键路径的瓶颈。** 单线程 sort-merge-sweep 做到
   **30.9–31.6M 条目/秒（707–724 MiB/s，两轮独立运行）**。
   ⚠️ **但由此推出「加密才是瓶颈」不成立**，见本条末尾的比较集更正。换成用户写带宽：按每 4 KiB 用户写产生 3 条缓冲条目算，
   单线程能撑 **42.2 GB/s**；即使每 4 KiB 产生 10 条，也能撑 12.6 GB/s。
   而 [experiments.md](experiments.md) E6 实测加密单核是 4.1 GB/s（有 AES-NI）/
   0.28 GB/s（无 AES-NI）。
   ⇒ **[decisions.md](decisions.md) D8「sort-merge-sweep 本质单线程」这条在
   **线程**含义上不成立**——单线程合并比单核加密快一个数量级，且可并行。
   ⚠️ D8 原句的 **I/O 含义仍然成立**，见本条末尾。
2. **按叶分区的无锁并行可用**（N=5 轮取中位）：

   | 线程 | 合并臂加速 | 阳性对照加速 | 散射吃掉 |
   |---|---|---|---|
   | 16 | **6.38×** | 11.91× | 46% |
   | 32 | **6.96×** | 15.60× | 55% |

   **32 线程 5/5 轮都高于 16 线程**，超线程在这个负载上仍有收益（约 +9%），
   但边际递减——散射那趟 O(n) 吃掉的比例从 46% 涨到 55%。
   ⇒ **按叶分区的散射没把收益吃光，但它是并行度的天花板所在。**

**这一轮最值钱的产出是一条格式要求，不是上面的数**：

> ⚠️ **write buffer 的条目必须自带序号（seq）。**

D8 正文明写「flush 时按 key 排序**丢弃时间序**」，而去重规则是「后者胜」——
**排序之后「后者」这个概念必须由条目自己携带**。用不稳定排序时同 key 条目的相对次序未定义，
**去重结果因此不确定**。本实验第一版漏了它，两条臂与真值当场对不上。
⚠️ 它与 E14 已定的「条目必须是幂等完整值」是**两条不同的要求**：
幂等管「重复应用不出错」，序号管「谁覆盖谁是确定的」。

**口径**：纯 CPU/内存实验，无设备、无虚机。400 万条目 / 4096 个目标叶 /
key 空间为叶数的 64 倍（保证有重复可去）/ 条目 24 字节（key + seq + value）/
每档取 5 轮最好值。机器：AMD Ryzen 9 9950X，16 核 32 线程。
代码 `research/e7-index-bench/src/bin/e17_merge.rs`，`cargo run --release --bin e17-merge`。

**非平凡性保证**：两条臂**共用同一份输入**，且**输出必须与真值逐位相同**，不同即整轮作废。
真值用 BTreeMap 按到达顺序独立算，**与两条臂不共享任何合并代码**。
三条单测经定向破坏证明会红：把排序键里的 `seq` 去掉，
`arms_agree_with_truth` 与 `partition_count_does_not_change_result` 立即变红。

⚠️ **本实验只量了合并这一段**：不含树插入、不含 I/O、不含分配。

⚠️ **由此推出的「加密才是瓶颈」那句话不成立——比较集少了一项，而少掉的那项最大。**
真实 flush 的树插入 I/O 由 [experiments.md](experiments.md) E7 量过：
`logstruct_wb` 的 io/op = **1.5755**，口径是「512 个随机 key 落到约 400 个不同叶子、
每叶一读一写」⇒ **条目/叶 ≈ 1.28**。
而本实验把 400 万条目塞进 4096 个叶，**条目/叶 = 976.6**——
**树插入 I/O 被摊薄了约 1000 倍**。

按每 4 KiB 用户写 3 条条目、E7 的 io/op 折算，三项预算：

| 项 | 每 4 KiB 用户写 | 来源 |
|---|---|---|
| 合并 CPU | **0.13 µs** | 本实验 |
| 加密（单核，有 AES-NI） | **1.0 µs** | E6 的 4.1 GB/s |
| **flush 的树插入 I/O** | **≈ 4.65 µs** | E7 的 io/op 1.5755 |

⇒ **真正的关键路径是 flush 的树插入 I/O**，比加密约 4.6 倍、比合并约 36 倍。
而这笔钱正是**排序本身**造成的（E7 的干预对照：打乱组顺序 −9.2%，
100% 缓存档完全相同作阴性对照）。

⚠️ **这一条唯一待验的假设**：「条目/叶 ≈ 1」依赖「叶数 ≫ 一次 flush 的条目数」。
若真实缓冲区大到能覆盖热叶集，本实验的配比才是对的，flush I/O 项会塌下去。
**这一点现在没有数。**

所以本实验给的是**合并步骤的上界**，不是 flush 的总代价，更不是关键路径的判定。

## E18 D5 在多分叉 / 多可写头下是否报废 —— 已跑（2026-08-28，第二轮修正后）

**结论：D5 在多可写头下失效，但失效形态是「无界泄漏 + 回收率归零」，不是数据丢失。**

按 [decisions.md](decisions.md) D5 正文真正定义的那条 `death` 规则
（「**最后一个活引用被摘掉**、且该摘除被发布的 checkpoint 号；仍在活树里则为 ∞」）：

| 历史形状 | 判死实活（数据丢失） | 判活实死（泄漏） | 「永不记 death」的泄漏 |
|---|---|---|---|
| 线性（阳性对照） | **0** | **0** | — |
| 一次分叉 | **0** | 8.19% | 8.44% |
| 8 个可写头 | **0** | **29.40%** | **29.40%（逐位相同）** |

**两条结论**：

1. **数据丢失方向结构性为零。** truth 为真 ⇒ 块在该根的链上没死 ⇒ 不满足「所有分支都删过」
   ⇒ `death = ∞` ⇒ 区间判定必为真。**这不只是实测，是可证的。**
2. **代价是回收能力归零。** 8 个可写头档，正确的规则与「**根本不记 death**」
   **逐位相同**（fp 均为 29.40%）——它用「一块都不回收」换来零数据丢失。
   而要维护「是不是最后一个活引用」，需要的正是每块的分支覆盖信息 = **引用计数**，
   **正是 D5 想省掉的那个东西**。

⇒ **D5 在分叉下破的是 O(1) 性质，不是正确性。**

### 这一轮推翻了本实验第一轮的结论

第一轮报「一次分叉 1.73%、8 个可写头 5.80% 的**数据丢失**」，那个结论**不成立**，
两个成因都在本实验自己身上：

| # | 错在哪 | 后果 |
|---|---|---|
| 1 | **测的两条 `death` 规则（最早 / 最晚）都不是 D5 正文定义的那条。** D5 第 206 行写着「最后一个活引用被摘掉」，分叉下完全确定 | 数据丢失那一列整列是假的 |
| 2 | **阳性对照只对 `earliest` 一条臂跑了。** 产出「5.80 → 4.00」的 `latest` 臂**从没过闸**——补跑后它在线性历史上 fp=8 | 按本实验自己的作废条款，那条臂当时就该整轮作废 |
| 3 | 生成器允许**同一条分支上把同一个块删两次**（真实文件系统里不存在），正是 fp=8 的成因 | 修掉之后三条规则的线性阳性对照全部 0/0 |

⚠️ **教训写进纪律**：**阳性对照必须对每一条被测的臂都跑。**
只跑一条等于另一条从没过闸，而它偏偏就是产出结论的那一条。

### 口径与对照

**口径**：纯逻辑实验，无设备。共同前缀 40 个 txg，每分支 20 个 txg，
每 txg 造 3 个块、删 1 个前缀块（且**同一分支上不重复删**）。每个 txg 都是保留的根。
代码 `research/e7-index-bench/src/bin/e18_branch.rs`，
原始输出 `research/results/e18-branch-2026-08-28.out`。

| 对照 | 断言 | 结果 |
|---|---|---|
| **阳性** | 线性历史上**三条规则**都必须零错误 | earliest / latest / conservative 全部 fp=0 fn=0 ✓ |
| **判别力** | 分叉档必须真的构造出跨分支引用 | 7860–24420，非零 ✓ |
| **退化下界** | 加一条「永不记 death」臂。若正确规则与它逐位相同，说明它什么也没回收 | heads8 档**逐位相同**——这一条正是本轮最重的发现 |

⚠️ **fp 的具体数值依赖根密度与删除模式**，换模式会变。
不依赖模式的是两条定性结论：**fn ≡ 0（可证）**、**conservative 在多头下退化到 never**。

### 这对 D5 / D6 意味着什么

D5 标着「已定（**条件于**历史是单向线性）」。本实验把那个条件的**性质**定清楚了：
**不是正确性条件，是 O(1) 条件。**
⇒ D6 若取多可写头候选，D5 的失效形态是**无界泄漏 + 记账退化到引用计数**。
**泄漏可被 [invariants.md](invariants.md) I-3.1 检出、可回收、伤害有上界；数据丢失不可逆**——
两者在 D6 的候选评估里权重差一个量级，**这个改写很要紧**。

## E19 defer 窗口下的假性 ENOSPC —— 建模层已跑（2026-08-28），真机压测未跑

**结论**：

1. **判据是可计算的，而且实测 36/36 命中**：

   > **假性 ENOSPC 与 checkpoint 卡死出现 ⟺
   > 剩余空间 ≤ 每 checkpoint 搅动量 × (延迟代数 + 1) + 一次 checkpoint 的开销**

   跨 6 档填充率（0.90–0.999）× 6 档延迟（1–32）共 36 格，预测与实测**逐格一致**。
   这条预测**只用负载参数**，不读被测模型的任何字段。

2. **90% / 95% 填充下全部为 0**——这个问题只在盘很满时存在，不是常态。

   | 填充率 | 剩余空间 | 出问题的最小延迟 |
   |---|---|---|
   | 99% | 10000 块 | **16**（延迟 8 无事） |
   | 99.5% | 5000 块 | **8** |
   | 99.9% | 1000 块 | **1**（最小延迟就出问题） |

3. **99.9% 填充下的假性 ENOSPC 率**：延迟 1 → 0.375%；延迟 8 → 3.875%；延迟 16 → **7.875%**。

4. **两种故障模式要分治，不能并成一句话。**

   | 故障 | 谁治得了 | 数字 |
   |---|---|---|
   | **checkpoint 卡死** | **保留池**，且 `reserve ≥ ckpt_cost` 就够 | 预留 **64 块**（恰等于 `ckpt_cost`）把 `ckpt_stall` 从 **199 打到 0** |
   | **假性 ENOSPC** | **只有准入**。保留池反而加重它 | 预留 0 → 16384 块，假性 ENOSPC 从 3150 涨到 **7246**，每档增量恰为 `reserve / file_blocks` |

   **机制**：保留池是给 checkpoint 开的一道地板，对**普通分配**是纯税。
   而假性 ENOSPC 的成因是「defer/K 扣住的量超过剩余空间」，那不在保留池的射程内。
   ⇒ 准入规则治后者：不许把盘填到
   `容量 − 搅动量 × (延迟+1) − checkpoint 开销` 以上。

**口径**：纯逻辑建模，无设备、无文件系统。容量 100 万块（4 KiB/块 ≈ 3.8 GiB），
每个临时文件 4 块，每 checkpoint 窗口 200 次「删一个 + 建一个」，跑 200 个 checkpoint，
一次 checkpoint 自己写 64 块。代码 `research/e7-index-bench/src/bin/e19_defer.rs`。
原始输出 `research/results/e19-defer-2026-08-28.out`。

**两个数分开算，不是同一个公式导出**：
`df_free = 容量 − 活引用`（用户看到的）；
`allocatable = 容量 − 活引用 − 被扣住的 − 保留池`（分配器看到的）。
「被扣住的」由**逐 checkpoint 的记账队列**算出来。

### 本轮抓出自己两个建模 bug

| bug | 症状 | 后果 |
|---|---|---|
| `allocatable()` 用 `u64` 直接相减 | 被扣量超过剩余空间时**下溢成天文数字** | 分配反而总是成功，整张表是假的 |
| 保留池实现成「缩小容量」，而填充率又按缩小后的容量算 | 预留从 0 到 16384 **完全没有区别** | 那不是发现，是没实现 |
| **卡死判据读了错的视图**：写成 `allocatable()`（**减掉了保留池**）而不是 `allocatable_ckpt()` | `allocatable_ckpt()` 成了死代码，编译器一直在报 `never used` | **「保留池救不了」这个结论完全由这一行造成。** 接对之后 `reserve=64` 就把卡死从 199 打到 0 |

**第二个 bug 是被结果的「太整齐」暴露的**——六档预留给出完全相同的数，
本身就是「这个自变量没接上」的信号。
**第三个 bug 是三方论证的反推腿抓到的**：它去读代码，发现那个方法从没被调用过。
⚠️ 成因是一次 `str.replace` 因缩进不匹配**静默没生效**，而我没回读确认。

### 一条要标明的判别力缺口

`analytic_held`（公式估算）与逐项记账**逐格完全相等**（800/800 … 12800/12800）。
⚠️ **那个「一致」没有判别力**：本实验的负载完全规则（每 checkpoint 恰好 200 次 × 4 块），
两条路算的是同一道算术。**有判别力的是准入那一条**——它预测的是 trouble / no-trouble 这个二值，
且跨 36 格全中。要让 `analytic_held` 也有判别力，负载必须不规则（变长文件、变速率）。

### 真机压测（未跑）

**前置**：事务层与分配器。建模层已经给出准入规则的形式，真机要验的是
「搅动量」这个量在真实负载下怎么估——本实验把它当成常数，真实负载里它是变量。

## E20 指针变宽的 CPU 缓存代价 —— 已跑（2026-08-28）

**背景**：[decisions.md](decisions.md) D19 此前只量了两样——内部节点的**常驻内存容量**
（10.6 → 68.8 GB/PiB）与**树深**，两样都算出「代价很小」。
**但没量过一次点查的 CPU 时间**：条目变宽 ⇒ 一个缓存行里装得下的 key 变少 ⇒
每次节点内查找碰更多缓存行，工作集也整体变大。消耗的是 L1/L2/L3 与 DRAM，不是廉价磁盘。

**结论**：

1. **代价只在工作集超出 L3 时出现**（本机 L3 32 MiB），一次点查的 ns：

   | 工作集 | 4 KiB 节点 16B → 111B | 16 KiB 节点 16B → 111B |
   |---|---|---|
   | 40 K（L1 内） | 59 → 59（**1.00×**） | 63 → 56（0.89×） |
   | 528 K（L2 内） | 74 → 76（1.02×） | 74 → 84（1.13×） |
   | 8.3 M（L3 内） | 108 → 122（1.12×） | 98 → 122（1.24×） |
   | **134 M（超 L3）** | 179 → 467（**2.61×**） | 206 → 541（**2.62×**） |

2. **节点大小决定代价从哪一档开始**——这是最有用的一条：

   | 条目宽 | 4 KiB 节点 | 16 KiB 节点 |
   |---|---|---|
   | 40 B（本工程指针头部） | **1.98×**（树深 3→4） | **1.14×**（树深仍 3） |
   | 67 B | 2.26× | 2.22× |
   | 111 B | 2.61×（深 5） | 2.62×（深 4） |

   ⇒ **大节点吸收指针变宽。** 同样 40 字节，4 KiB 节点付 +98%，16 KiB 节点只付 +14%。

3. ⚠️ **本实验与 [experiments.md](experiments.md) E7 指向相反的方向，但两者不矛盾。**
   E7 量**设备 I/O**，得出「小节点在两端都赢」；本实验量 **CPU 缓存**，
   得出「指针宽时大节点明显更好」。**它们量的是两种不同的资源。**
   ⇒ D4 记着的那笔债（E7 要用最终指针宽度复跑）**现在有第二个理由**：
   不只是扇出影响设备 I/O，还因为节点大小与指针宽度在缓存这一侧是耦合的。

**口径**：纯 CPU/内存实验。按数组铺开的隐式 B 树，节点内二分，条目按 `entry_bytes` 跨步，
条目第二个 8 字节存子节点号（形成依赖式载入链）。**固定 key 数、不固定工作集**——
条目变宽 ⇒ 工作集变大 ⇒ 被挤出缓存，这才是要问的。
本机每核 L1d 48 KiB、L2 1 MiB、L3 32 MiB、缓存行 64 字节。
代码 `research/e7-index-bench/src/bin/e20_fanout.rs`，
原始输出 `research/results/e20-fanout-2026-08-28.out`。

### 阳性对照拦下了三版，其中两版是建模错

**对照**：同一条目宽度下，L1 能装下的工作集必须显著快于超出 L3 的（比值 ≥ 2）。

| 版本 | 比值 | 病因 |
|---|---|---|
| 第一版 | 1.01 | 随机数与取模淹没了树下降本身（计时区里做 RNG 与 u64 取模） |
| 第二版 | 0.99 | 各次查找互相独立，**乱序执行把几十个缓存缺失并行掉了**——量到的是带宽不是延迟 |
| 第三版 | 0.99 | **数据布局错**：节点 0 的 key 是 0..251 而查找 key 均匀分布在全域，99.99% 的查找在第一层就落到最右端，每次走同样几个节点、全在 L1 |
| 第四版 | **3.03** ✓ | 修法：计时区外预生成 key、查找之间串行依赖、每个节点同值域按层取 key 位段 |

⚠️ **没有这个对照，前三版的表会被当成「指针变宽没有代价」发出去。**
四条单测经定向破坏证明会红，其中 `lookups_spread_across_nodes` 专门抓第三版那个布局错。

## E21 GPU 卸载的净收益 —— 未跑（本机可测，无前置）

**背景**：[decisions.md](decisions.md) D24。三个候选场景（批量压缩、全盘 scrub、EC 重建）
全部落在 `.claude/rules/fs-design.md` 第三格（后台、可续做、非决策路径，无戒律），
所以引入 GPU 不违反已定纪律；但**收益一个数都没有**。

**自变量**：任务（校验和 / AEAD / Reed-Solomon 编解码 / 压缩）× 批大小（1 MiB … 4 GiB）
× 执行位置（CPU 单核 / CPU 16 线程 / GPU）× 数据是否已在显存。

**测什么**（**三段必须分开报，合并成一个「GPU 快 N 倍」就没意义了**）：

| 段 | 口径 |
|---|---|
| **传输**：主机 → 显存 | GB/s，含固定开销 |
| **计算**：核函数本身 | GB/s |
| **传回**：显存 → 主机 | GB/s（scrub 只回一个结论，EC 重建要回全部重建数据，两者差别巨大） |

**判据**：

1. **端到端净收益**：`CPU 16 线程耗时 ÷ (传输 + 计算 + 传回) 耗时`。
   **小于 1 就是负收益**，那一格直接否掉。
2. **收益随批大小的曲线在哪里过 1**——那个批大小就是启用 GPU 的阈值，
   必须是显式可计算的（`.claude/rules/fs-design.md` 硬要求 1）。
3. **回传量的影响**：scrub 只回一个判定，EC 重建要回整批数据。
   两者的曲线形状预期完全不同，**要分开报，不许用一个数概括**。

**怎样才算失败**：
- 若 GPU 计算段本身都不比 CPU 16 线程快，**不必再看传输段**，该任务直接否掉。
- 若各批大小下净收益都在 ±10% 内，检查是不是被 PCIe 带宽钉死了，
  **那说明这类任务不适合卸载，是合法结果，如实记录**。
- ⚠️ **阳性对照**：拿一个已知极度适合 GPU 的任务（例如大矩阵乘）跑同一条链路，
  它必须显示出显著加速。测不出来 ⇒ 环境或 harness 有问题，**整轮作废**——
  不许把「没加速」记成任务的结论。

**本机**（2026-08-28 现查）：NVIDIA RTX 5090（32 GB）+ RTX 5060 Ti（16 GB），驱动 595.84。
⚠️ **两块卡型号不同，跑分要钉死用哪一块并记进口径。**

**前置**：无。但需要 CUDA 工具链，`research/scripts/env.sh` 尚未检查它。

## E11 双轨：收益与翻转代价，自己量 —— 未跑（依赖事务层与两条轨的实现）

**背景**：[decisions.md](decisions.md) D14 已改为「不许拿文献或别家结局当依据，自己推导、自己验证」。
推导那一半（穷举翻转入口、六样逐样重判）不需要实验；本实验负责另一半。

### 第一组：收益侧——每一样「少做」单独量，不许打包

**自变量**：分轨要少做的六样，各自独立开关（快照可见性、deadlist 记账、
Merkle 链、加密与 nonce、恢复承诺、反向索引）。

**测什么**：每样单独关掉时的写路径耗时、写放大、每对象元数据字节数、
以及 checker 跑一遍的挂钟。

**判据**：得到一张「关掉哪一样 → 省了多少」的表。
**打包量是这个实验最容易骗自己的地方**——六样一起关当然快，
但那个数字不能回答「哪一样值得为它开一条格式分支」。

**怎样才算失败**：
- 六样一起量、分不出各自贡献 → **整轮作废**。
- 某一样关掉之后省下的挂钟**小于测量噪声** → 那一样**不值得进格式**，如实记录；
  这是合法结果，不是实现 bug（`singlefs-ai-sop/rules/test-discipline.md`：
  实验的失败条款不许让结论不可证伪）。

### 第二组：代价侧——翻转迁移的斜率

**背景**：一个对象从一条轨迁到另一条轨，代价随对象规模怎么变，决定了它是不是无界操作。
D8 硬要求：**无界规模的操作一律不许做成单个事务**。

**做法**：对每一个翻转入口（推导 D-1 那张穷举表里的每一行），
在对象规模 4KB / 1MB / 64MB / 4GB 上各触发一次，量迁移耗时与写入量。

**判据**：**斜率**。
- 耗时/写入量**不随对象规模增长** → 该入口是有界的，可以做成单个事务。
- **随规模线性增长** → 它是无界操作，必须走「写意图 → 分批 → 可续做」，
  于是该入口所承诺的原子性（`linkat`、`rename` 本来是 O(1) 或原子的）**当场作废**，
  这一条要写进 D14。

**怎样才算失败**：
- 全部档位都测不出斜率差异 → 多半是最大档还不够大，或者迁移被后台异步做掉了没算进来。
  **整轮作废**，加大规模并确认计时覆盖到迁移真正完成。
- 若某个入口在测试里**根本没触发迁移**，先确认它是不是被实现悄悄跳过了——
  「没测出代价」和「代码没跑到」必须分开
  （`singlefs-ai-sop/rules/evidence-discipline.md`）。

### 强制进入两条轨的开关（硬要求 2）

两条轨都必须能被测试**无视自动判据直接指定**，否则「进不去就等于没测」。
开关形态与 D12 的「强制指定布局」那个 mkfs 开关同源，应当复用同一套机制。

**前置**：事务层、两条轨的实现、块层写记录、checker。
**注意**：本实验的第二组与 [invariants.md](invariants.md) I-4.6（存在未完成意图的镜像上
其余不变量仍然成立）叉乘——翻转到一半的镜像是一类**新的合法中间态**，
它要单独跑崩溃点重放，不能算在既有类别里。

## E12 攒批的顺序追加 vs 不攒批的随机页读改写 —— 已跑（2026-08-26）

**背景**：[decisions.md](decisions.md) D5 用「birth txg + 时间序」推导块的生命周期，
删除判定读两个标量、**零次额外设备 I/O**；代价是它排除 reflink / dedup
（前提之一是「每个块在活树里至多一个活引用」）。
另一条路是**每块一个引用计数**，能支持任意多活引用，代价是每次解引用要读-改-写一个计数器。

D5 立项时引的是 btrfs qgroup 的数字（提交时间 +76%、事务等待 +1347%、写吞吐 −25%）。
⚠️ **那个口径测的是 qgroup 走反向索引，不是纯引用计数**，拿它回答本题会夸大。
**本实验自己量。**

### 口径：唯一会让两者分开的自变量是「计数器表工作集 vs 缓存预算」

- **计数器表装得进缓存**时，引用计数的读-改-写全在内存，设备 I/O 接近 0
  ——两者可能没有可分辨差异，**而那是一个合法结果**。
- **装不进**时，每次删除都可能触发一次随机读（4 KiB 页）+ 一次回写。
  **D5 这一侧不随工作集变化**，因为它根本没有计数器。

### 三条被测路径

| 臂 | 删除一个引用时做什么 | 预期设备 I/O |
|---|---|---|
| **A：D5（时间序）** | 比较两个标量（`ptr.birth` 手上就有、`prev_snap_txg` 常驻内存）→ 追加一条定长记录进 deadlist 缓冲，满 1 MiB 顺序刷 | **只有顺序写**，无随机读 |
| **B：引用计数** | 定位计数器页（`blk / 每页条目数`）→ 不在缓存则 O_DIRECT 读 4 KiB（按 LRU 逐出，脏页回写）→ 减一 → 标脏 | 随机读 + 随机写，随工作集/缓存比增长 |
| **C：D5 + 稀疏旁表（ZFS BRT 形态）** | 先探一次稀疏表确认「这块没被 clone 过」；未命中走 A，命中走 B | 取决于**探测能不能不碰设备** |

### 自变量

计数器表条目数，取三档：**装得进缓存 / 2× 缓存 / 8× 缓存**。
缓存预算固定（页数写死），随机删除序列用**固定种子**（可复现是硬要求）。
每档 N≥5 轮。

### 判据

1. **主判据**：臂 B 的「每次删除的设备 I/O 次数」随工作集/缓存比怎么变，臂 A 是不是**平的**。
2. **臂 C 的关键一问**：**未被 clone 的块，探测能不能做到真的零设备 I/O**。
   做不到，则「D5 为主 + 稀疏旁表为辅」这个组合的全部卖点消失。
3. 报**设备 I/O 次数与字节数**，不只报挂钟——挂钟受虚机与宿主影响，I/O 计数是结构性的量。

### 怎样才算失败（两个对照组，分开判）

| 现象 | 判定 | 理由 |
|---|---|---|
| 在「8× 缓存」档，臂 B 相对臂 A **没有可分辨的额外 I/O** | **实现有问题，整轮作废** | 这是**阳性对照**：工作集是缓存的 8 倍还不产生随机读，说明缓存边界没生效或访问序列不够随机 |
| 在「装得进缓存」档，臂 B 与臂 A 无可分辨差异 | **合法结果，如实记录** | 它正说明「计数器装得下时引用计数几乎免费」，是本实验要回答的问题之一，**不是 bug** |
| 三档之间臂 A 有可分辨差异 | **实现有问题，整轮作废** | 臂 A 不含计数器，不该随计数器表大小变化 |

⚠️ 保留阳性对照是硬要求（`singlefs-ai-sop/rules/test-discipline.md`：
实验的失败条款不许让结论不可证伪）——**没有它，「没有差异」分不清是结论如此还是实现坏了。**

### 这个实验不回答什么

- **不回答**「reflink 值不值得做」——那是特性取舍，不是性能数字能决定的。
- **不回答**崩溃一致性与 checker 代价。引用计数是 delta 形态，
  其 checker 验证有一类盲区（见 [checks-owed.md](checks-owed.md) C12），
  **那笔账不在本实验射程内，不许拿本实验的数字去覆盖它**。
- **不回答**真实负载下的分布。本实验的删除序列是均匀随机的，
  真实负载有局部性，会让臂 B 好看。**外推要说明这一点。**

**前置**：E7 的虚机 harness（**已就绪并自检通过**）、块设备、Rust 工具链。**不需要文件系统。**

### 本实验测的是什么（读结果之前必须先读这一段）

**它测的是「攒批的顺序追加」与「不攒批的随机页读-改-写」的 I/O 对比，
外加一次测量装置自检。它不是「D5 与其对手」的机制比较。**

臂 A 的实际内容：`prev_snap_txg` 是硬编码常量（**运行期间没有建过、也没有销毁过任何快照**）；
`birth` 是现造的随机数，不从任何指针读；记录声明 16 字节而只写 8 字节，**块指针不在其中**；
**全段零次读**。⇒ **判据换成掷硬币，结果一模一样。**
那个「2」= ⌈1.6 MB / 1 MiB⌉ + 收尾刷，**与 birth txg、与 deadlist 语义、与快照都无关**。

臂 B **完全不攒批**：每次操作一次随机页读-改-写。
⇒ **两臂摊销架构不对称，机制与攒批各贡献多少，本实验拆不开。**
本实验自己的 `sequential` 注入给出了量级：174,998 → **391**，
**攒批 + 排序独自吃掉三个数量级中的两个半。**

约 10 万次判「立即释放」的在臂 A 里零成本跳过，
而 [decisions.md](decisions.md) D5 的伪代码要求它们**进 defer 队列**——
那是第二条必须持久化的追加日志，本实验未量。

**D5 的四条前提本实验零覆盖**：无快照、无克隆、无 reflink、无崩溃、无一次 flush。
而 D5 的风险不在稳态 kill 路径上，在**建快照的边界**（`birth == S.txg` 取错是数据丢失）、
**销毁快照的级联合并**（按 birth 分桶的开销本实验未量）、以及**崩溃重放**。

### 本实验能支撑的三条结论

1. **拐点的解析式**：`io/op = 2×(1−缓存/表)`，实测 0.998 vs 解析 1.000、1.751 vs 1.750。
2. **`nodirect` 那一行**：证明这套**测量装置**有判别力——与 D5 无关，但对以后所有块层实验有效。
3. **`bigcache` / `sequential` 两行**：量出臂 B 两个驱动变量各自的权重（85×、448×）。
   **这两行是本实验信息量最大的部分，而它们量的是「臂 B 的模型有多脆」。**

### 要让它成为一次机制比较，至少要改三处

臂 A 真的实现 D5（含建快照交接、销毁快照级联、defer 队列）；
臂 B 与臂 A 摊销架构对称（都攒批）；
把真正的对手（D6 的「快照 ID 进 key」+ D8 的 write buffer 形态）放上场。

### 结果（2026-08-26，N=5 轮、**五个不同种子**、带块层独立读数）

**20 万次删除一共触发多少次设备 I/O（中位）**

| 臂 | 装得进缓存 | 2× 缓存 | 8× 缓存 |
|---|---|---|---|
| **A：D5 时间序** | **2** | **2** | **2** |
| **B：引用计数** | 512 | ~200,208 | ~350,042 |
| **C：D5 + 稀疏旁表**（clone 率 1‰） | 508 | ~1,956 | ~3,466 |

**中位挂钟（毫秒）**：A 约 1.7–2.3；B 为 53 / 15398 / 26982；C 为 40 / 150 / 271。

#### 校验：块层独立读数与程序内计数器逐格相符，比值 1.00

每一臂前后各读一次 `/sys/block/vda/stat`（**内核的块层自己数的**，
与本程序的计数器不共享任何代码、采样或工具，满足
`singlefs-ai-sop/rules/evidence-discipline.md` 的校验要求）。
**九个格子全部比值 1.00。**

这条独立路径证明了三件此前只是假设的事：
**O_DIRECT 真的绕过了缓存**（没有多余的读）、**块层没有合并或拆分请求**、**没有预读**。

#### 换种子之后离散度是真的

| 臂 · 工作集 | 五个种子下的实际取值 |
|---|---|
| refcount · 2× | 199894 / 200118 / 200208 / 200214 / 200632 |
| refcount · 8× | 349930 / 349980 / 350042 / 350084 / 350156 |
| hybrid · 8× | 3396 / 3420 / 3466 / 3500 / 3522 |

离散度 0.4%–4%。**而 D5 恒为 2——那个不变是结构性的（它根本不查计数器），不是种子造成的。**

⚠️ `d5 · x8` 的块层极差显示 50%，是因为**绝对值只有 2**，一轮差 1 就是 50%。
**小基数上的百分比没有意义，不要读它。**

### 三条失败条款逐条判定

| 条款 | 观测 | 判定 |
|---|---|---|
| 8× 档臂 B 无可分辨额外 I/O → 实现有问题 | 350042 vs 2 | **不触发**，阳性对照有判别力 |
| 装得进缓存档无差异 → 合法结果 | 512 vs 2，绝对值都极小（512 = 一次性冷启动填满 256 页的读+写） | **触发，如实记录**：计数器表装得下时，引用计数几乎免费 |
| 臂 A 三档之间有差异 → 实现有问题 | 三档**都是 2** | **不触发** |

### 结论

1. **转折是陡的，不是渐变的。** 计数器表一旦装不下缓存，引用计数从 512 次跳到约 20 万次
   （≈ 每次删除 1 次设备 I/O），8× 时到 35 万。**而 D5 恒为 2**——它没有计数器可查。
2. **稀疏旁表把大部分优势拿回来。** 1‰ clone 率下 8× 档是 3466，
   对比纯引用计数的 350042，**约 100 倍**。
3. **所以不是二选一。** 数据支持「**D5 为主 + 稀疏旁表为辅**」（ZFS BRT 形态）。

### 机制：为什么 D5 恰好是 2，而引用计数随工作集爆炸

**说不出机制的数字只是观测，不是理解。** 两侧都能从第一性原理推出来，
并且**推算与实测吻合到三位有效数字**——这构成第三条独立校验路径
（另两条是块层读数、以及实测本身）。

#### 臂 A 为什么是 2

判定的输入只有两个，**都不需要查任何东西**：
`ptr.birth`（这条指针本来就要读，零额外 I/O）与 `head.prev_snap_txg`（常驻内存的一个标量）。
于是唯一的设备 I/O 是把 deadlist 记录**顺序追加**出去：

- 20 万次删除里，`birth ≤ prev_snap_txg` 的约 10 万条要进 deadlist（另一半直接释放，连写都不写）
- 每条 16 字节 ⇒ 约 1.6 MB ⇒ **1.53 个 1 MiB 缓冲**
- ⇒ 满缓冲刷 1 次 + 收尾刷 1 次 = **2 次写，0 次读**

推算 1,600,000 字节 vs 实测 `bytes_w=1597440`，差 0.16%（PRNG 分布不是精确对半）。

> **它的 I/O 次数 = ⌈进 deadlist 的总字节 / 缓冲区⌉，正比于「删除的量」，与地址空间大小无关。**

#### 臂 B 为什么爆炸

它必须**按块的身份去查一张表**，而表的大小正比于地址空间。均匀随机访问 + LRU 下：

```
缺页率 = 1 − 缓存页数 / 表页数
每次缺页 = 一次随机读 + 一次逐出脏页回写 = 2 次 I/O
⇒ io_per_op = 2 × (1 − 缓存页数 / 表页数)
```

| 档 | 表页数 | 缓存/表 | 缺页率 | **解析 io/op** | **实测 io/op** |
|---|---|---|---|---|---|
| fits | 256 | 1.000 | 0.000 | 0.000 | 0.003（一次性冷启动填满 256 页） |
| 2× | 512 | 0.500 | 0.500 | **1.000** | **0.998** |
| 8× | 2048 | 0.125 | 0.875 | **1.750** | **1.751** |

> **它的 I/O 次数正比于「地址空间与缓存的比」，与删除的量无关——每次删除都付。**

#### 一句话的结构差异

**D5 把随机查找换成了顺序追加；引用计数没有这个选项**，
因为「这个块的计数器在哪」由**块的身份**决定，而身份是随机的。
这与 LSM 相对 B-tree 是同一个形状，只是发生在**记账层**。

#### ⚠️ 这个「2」有一个前提，而它正好是 D16

**那 2 次写成立的前提是「追加可以攒起来批量刷」。**
若每次删除都必须立即持久化（例如每删一条就 fsync），缓冲区攒不起来，
**2 会退化到约 10 万**（每条记录各自一次持久化）——**这一条是推理，未实测**。

⇒ **[decisions.md](decisions.md) D16 定为 checkpoint，正是 D5 这个「2」的前提。**
若发布语义改回「每事务发新根」，本实验的 A 臂结果不再成立，必须重测。

### 对测量本身做故障注入：证明这套测量有判别力

**「比值 1.00」可能意味着「一切正确」，也可能意味着「校验路径是摆设」——不注入故障就分不开。**
`singlefs-ai-sop/rules/test-discipline.md`：写完一个检查，问「如果被测对象真的坏了，它会不会红」。

四个用例（种子 77777，只看 refcount 的 8× 档）：

| 注入 | 改了什么 | 我数的 I/O | **块层数的** | 挂钟 | 判定 |
|---|---|---|---|---|---|
| **none**（基线） | —— | 174,998 | 174,998 | 27.2 s | 比值 1.00 |
| **nodirect** | 打开设备时摘掉 `O_DIRECT` | 174,998 | **0** | 0.36 s | **块层校验有判别力** |
| **bigcache** | LRU 容量放大到装得下整张表（表大小不变） | **2,048** | 2,048 | 0.36 s | **工作集/缓存比确是驱动量** |
| **sequential** | 访问序列改成顺序而非随机 | **391** | 391 | 0.056 s | **随机性确是驱动量** |

**最要紧的是 `nodirect` 这一行。** 摘掉 O_DIRECT 之后，程序内的计数器**纹丝不动**
（它数的是自己发的系统调用），而**块层读数归零**——页缓存全吸收了，挂钟掉了 75 倍。

> **⇒ 若 O_DIRECT 哪天悄悄失效，比值会掉到 0，不会停在 1.00。那个 1.00 是有意义的。**

`bigcache` 与 `sequential` 分别证明结论的两个前提是真的驱动量，而不是碰巧：
缓存装得下整表则 174,998 → 2,048（**85 倍**）；顺序访问则 174,998 → 391（**448 倍**）。

⚠️ **`sequential` 那一行把外推边界从「标注」变成了「量出来的数」**：
本实验的删除序列是均匀随机的，而**真实负载有局部性**——
顺序极端下引用计数只要 391 次 I/O，与 D5 的 2 次差 195 倍而不是 87499 倍。
**引用计数的代价高度依赖访问局部性，这一条必须与主结论一起引用。**

#### 注入故障时我自己先写错了一个

`bigcache` 第一版把缓存放大到 2048 页，**而档位是相对缓存定义的，于是表也跟着放大 8 倍**，
比值不变、结果原样（1.74992）——**什么也没测到**。
是配置行里的 `counters=8388608` 暴露的。已改为「档位按基准缓存 256 页定义，不随故障变」。

**教训：把全部参数打进结果行是这次能发现它的唯一原因。**
若只打结果不打配置，那一轮会被当成「bigcache 没影响」这个错误结论收下。

### 这些数字不能证明什么（外推边界，必须一起引用）

- ⚠️ **臂 C 的探测用内存全域位图、每块 1 bit，是理想化。** 真实文件系统上 ≈ 128 MB/TB，
  **本实验高估了旁表在大盘上的表现**。ZFS 的 BRT 是**稀疏结构**，换成它必须重测。
- ⚠️ **删除序列均匀随机**，真实负载有局部性，**会让引用计数好看**。
- ⚠️ **不回答 checker 代价**（引用计数是 delta 形态，有 [checks-owed.md](checks-owed.md) C12 那类盲区），
  **也不回答崩溃一致性**，更不回答「reflink 值不值得做」。

**口径**：`e12-lifecycle`，musl 静态，xorshift64\* 随机序列，
五轮种子 11111 / 22222 / 33333 / 44444 / 55555（同一轮内三臂共用同一种子）；
缓存预算 256 页（1 MiB），每档 200000 次删除，计数器每页 512 个；
虚机 2048M / 4 vCPU / 2 GiB virtio 盘，`cache=none,aio=native`，
宿主 32 核 / 60 GiB；QEMU 8.2.2 + KVM。块层读数取自虚机内 `/sys/block/vda/stat`。

## E13 D5 的四条风险路径 —— 未跑（[decisions.md](decisions.md) D5 欠的那次实测）

**背景**：D5 的依据目前是 O(1) 归约证明（是证明，不是测量）。
[E12](#) 测的是「攒批的顺序追加 vs 不攒批的随机页读改写」，**它的臂 A 不是 D5 的实现**，
不能用来支撑 D5。本实验补那一次。

**为什么不测稳态 kill 路径**：那条路径本来就没人怀疑，而 D5 的风险不在那里。

### 要覆盖的四条路径，各自的判据

| # | 路径 | 测什么 | 判据 |
|---|---|---|---|
| 1 | **建快照的边界** | 在 `birth == S.txg`、`death == S.txg`、`birth == death` 三个边界上各构造一个块，建快照后检查它在不在快照里 | 与 D5 那张边界表逐格一致。**任一格不一致即判红**——`birth == S.txg` 取错是**数据丢失**，`death == S.txg` 取错是**空间泄漏** |
| 2 | **销毁快照的级联合并** | 合并耗时与写入量随 deadlist 条目数、以及随「按 birth 分桶」有无的变化 | D5 声称是 `O(deadlist 条目数 + 桶数)`。**不分桶时若退化成全表扫描，说明分桶是必需的格式要求，要写进 D5** |
| 3 | **崩溃重放** | 在级联合并的每一个崩溃点截断、重放、跑 checker；重复续做两次 | ① checker 无报错；② 达成目标状态；③ **重复续做结果不变**。⚠️ deadlist 的追加与级联合并**不幂等**（多重集相加，同一条目追加两次 ⇒ 销毁时双重释放），这一条是本实验最该红的地方 |
| 4 | **defer 队列的持久化代价** | 「立即释放」那一半进 defer 队列的写入量与 I/O 次数 | D16 新规则 2 要求 checkpoint 内的释放在发布前不得进入可分配集合。**E12 把这一半按零成本处理，实际它是第二条必须持久化的追加日志** |

### 怎样才算失败

| 现象 | 判定 |
|---|---|
| 三个边界全部一致，但**没有一个是构造出来的**（负载里根本没出现那些边界） | **整轮作废**——「没测出问题」与「没测到」必须分开 |

## E14 I-3.1 的判别力：幂等完整值 vs 增量 Δ —— 已跑（2026-08-27，5 种子全一致）

**结论**：`I-3.1`（增量记账 vs 遍历重算）**对增量 Δ 形态的判别力是零**——
注入的四类语义 bug 一条都抓不到，而四类**全都把账算错了**。
同样四类注入在幂等完整值形态上：三类真 bug 全抓到，第四类根本不是 bug。
**因此 D11 代价 1 成立**：在增量 Δ 形态下 I-3.1 不是判别力下降，是归零。

**口径**：纯逻辑实验，无设备、无虚机、无文件系统。20000 次操作 / 512 个键 /
批大小 64 / 5 个种子（11 22 33 44 55），5 个种子结论完全一致（`test-discipline` 的
「判通过要全通过、判失败要全失败」两侧都满足）。
复跑：`research/e7-index-bench/src/bin/e14_discrimination.rs`（不入库，见 D15 口径）。

### 实测

| 形态 | 注入的 bug | I-3.1 红 | 运行时账 = 真值 | 落盘条目数 |
|---|---|---|---|---|
| 幂等完整值 | 无（基线） | 0/5 | 5/5 | 20000 |
| 幂等完整值 | 合并规则反了（取先者胜） | **5/5** | 5/5 | 20000 |
| 幂等完整值 | 墓碑当普通值 | **5/5** | 5/5 | 20000 |
| 幂等完整值 | 下刷时丢一条消息 | **5/5** | 5/5 | 19687 |
| 幂等完整值 | 同一条消息应用两次 | 0/5 | 5/5 | 40000 |
| 增量 Δ | 无（基线） | 0/5 | 5/5 | 20000 |
| 增量 Δ | 合并规则反了（符号取反） | 0/5 | **0/5** | 20000 |
| 增量 Δ | 墓碑当普通值（删除不产生负 Δ） | 0/5 | **0/5** | 20000 |
| 增量 Δ | 下刷时丢一条消息 | 0/5 | **0/5** | 19687 |
| 增量 Δ | 同一条消息应用两次 | 0/5 | **0/5** | 40000 |

**「运行时账 = 真值」这一列是第三方读数，不是 I-3.1 的一部分。**
I-3.1 只比「运行时计数器」和「checker 遍历重算」；真值由操作日志直接重放算出，
用来分辨「两边一起错」。**盲区就是「I-3.1 绿 且 账 ≠ 真值」那四格，全在增量 Δ 一侧。**

### 两条阴性结果各自的解释（这一步不做就分不清「没问题」和「没跑到」）

| 阴性格 | 它是什么 | 凭什么这么说 |
|---|---|---|
| 幂等完整值 / 应用两次：I-3.1 绿 | **那一格根本不是 bug** | 落盘条目数 40000（正好 2×）证明注入生效了，而账仍等于真值 5/5——幂等把它吸收了。这正是选幂等完整值买到的东西 |
| 增量 Δ / 四类全绿 | **判别力归零，不是注入没生效** | 落盘条目数：应用两次 40000、丢消息 19687（= 20000 − 313 批，每批丢 1）；且四类的账全部 0/5 不等于真值。注入既改了盘上条目数，又改了结果，而 I-3.1 纹丝不动 |

### 机制：为什么增量 Δ 一侧连「丢一条消息」都抓不到

**checker 能独立重算的前提是存在一份不经过累加逻辑的权威内容。**

- 幂等完整值形态：权威是内容（键 → 值）。账是它的缓存。
  checker 遍历内容求和，与运行时那条「入缓冲时增量维护」的代码**不共享任何东西**——
  两条路径独立，所以下刷侧的任何语义错都会让它们分叉。
- 增量 Δ 形态：**账本身就是权威内容**，没有别的可遍历。
  checker 唯一的重算办法是拿同一个累加函数重放同一份已持久化的 Δ 日志。
  日志少了一条，两边都少那一条；符号反了，两边都反——**它在和自己比**。
  这与 bcachefs `disk_accounting.h:208` 的形态一致：
  `this_cpu_add(e->v[gc][i], a.v->d[i])`，运行时与 GC 重建只差一个下标。

### 建模上的要害（复跑时不照这个建就测不出东西）

**运行时的账必须在条目入缓冲时增量维护，树必须在下刷合并时更新——两个时刻、两段代码。**
这是 [rules/fs-design.md](../rules/fs-design.md)「记账是事务的副产品」的直接形态。
若把账也从合并结果导出，I-3.1 就退化成恒等式，四类注入在两种形态上都是 0/5，
整个实验什么都测不到。

### 本实验证明不了什么

- **不覆盖崩溃。** 全程无崩溃点、无重放，说的只是「稳态下 I-3.1 能不能抓到语义写错」。
- **不覆盖 D11 的收益侧。** 收益是 E7 的 1.50×–4.96×，这里一个字都没测。
- **注入的四类不是穷举。** 是四类「语义写错」的代表，不是「所有可能的 bug」。
  抓到率 3/3 与 0/4 是对这四类而言的，外推到别的 bug 类需要另外的论证。

**前置**：无（已跑完）。

## E15 异构设备几何的模拟是否成立 —— 已跑（2026-08-27，异构档 + 阴性对照双向通过）

**结论**：**成立。** 本机没有 zoned 盘、没有 4Kn 盘、没有旋转盘，但 QEMU 能造出来宾**确实能分辨**的
异构几何，因此 [decisions.md](decisions.md) D12 未定项 3 与 [checks-owed.md](checks-owed.md) C17
不必等真硬件。

**口径**：QEMU 8.2.2 + 内核 6.17.0-lockdep，`nvme` 走 initramfs 里 insmod 的模块。
被测的是**来宾内核读出来的几何**（`/sys/block/*/queue/`），不是 QEMU 的命令行参数。
复跑：`research/scripts/vm-geom.sh`（不入库）。

### 实测

**异构档**（三个命名空间几何各不相同）：

| 设备 | 逻辑/物理扇区 | zoned | chunk_sectors | zone 数 | 字节 |
|---|---|---|---|---|---|
| nvme0n1 | 4096 / 4096 | host-managed | 131072 | 8 | 536870912 |
| nvme0n2 | 4096 / 4096 | host-managed | **262144** | **4** | 536870912 |
| nvme0n3 | **512 / 512** | **none** | 0 | 0 | 536870912 |

⇒ 来宾看到 **3 种**不同几何。数字自洽：131072 扇区 × 512 B = 64 MiB、262144 × 512 = 128 MiB；
512 MiB ÷ 64 MiB = 8 个 zone、÷ 128 MiB = 4 个。

**阴性对照**（三个命名空间几何完全相同）：来宾看到 **1 种**几何。
⇒ **读取路径有判别力**，异构档那个「3 种」不是在回声命令行参数。

### 一条命令能造出的三样

**异构 zoned 池**（zone 大小 64M vs 128M）、**512e 与 4Kn 混用**、**zoned 与常规混用**。
`zoned.zone_size` 与 `logical_block_size` 挂在 `nvme-ns`（命名空间）上而非控制器上，
所以同一个控制器下的多个命名空间可以各不相同。

### 建这套东西时撞出来的四个坑（都会静默失败）

| 坑 | 表现 | 判据 |
|---|---|---|
| `logical_block_size` 不配 `physical_block_size` | QEMU 直接拒绝：`logical_block_size > physical_block_size not supported` | 会报错，不静默 |
| **完整性闸放过 `0/0`** | 来宾一个设备都没看到，闸判「0 条 == 声称 0 条」通过，结论变成「只看到 1 种几何 ⇒ 模拟不成立」 | **必须显式拦 `n < 1`**——读不到 ≠ 读到 0 |
| **内核与模块树不同版本** | `/boot` 里 4 个内核多数不可读，「第一个可读的」未必有配套模块树；vermagic 不符 ⇒ 四个 insmod 全失败 ⇒ 来宾零设备 | 挑内核时必须同时要求 `/lib/modules/$v` 存在 |
| 模块树压缩格式不一 | 本机 `-oem` 树是 `.ko.zst`、`lockdep` 树是裸 `.ko`，写死一种在另一种上失败 | 两种都认 |

⚠️ **前两个坑叠在一起会给出一个「看起来是阴性结果」的假结论**：模拟明明没跑起来，
输出却是「来宾只看到 1 种几何」——与「几何模拟不成立」外观完全一样。

### 本实验证明不了什么

- **不证明旋转盘。** 本机一块旋转盘都没有，QEMU 的 `rotation_rate` 只改声明不改延迟。
  旋转介质只能靠 `dm-delay` 之类的**模型化设备**，那是另一回事，口径必须分开写。
- **不证明文件系统在异构池上是对的。** 它只证明「来宾能分辨不同几何」这一步成立。

**前置**：无（已跑完）。

## E22 journal 记录点名祖先落点能不能免掉重放分配 —— 未跑，且**已被 D23 轴一排除，只在轴一重开时才有意义**

⚠️ **本实验的地位在 2026-08-28 变了。** D23 未定项 1 已定：延后祖先 ⇒ 新根不可能自洽
⇒ 发不出反映本次 fsync 的根，与已定的「每次 fsync 发根」直接冲突。
**丙同样不写祖先内容，因此同样被排除。** 本实验只在轴一被重开时才有意义，
它不再是「轴二的第三个候选」。下面的设计原样保留，供那时直接用。

**背景**：[decisions.md](decisions.md) D23 未定项 1 的**轴二候选丙**。
它是 2026-08-28 那轮三方论证逼出来的：C3② 的判据被写成了「重放跑不跑分配器」，
而真正的判据是「**记录 + 格式能不能唯一确定落点**」。
D23 的 C2 已定「分配先于 journal」⇒ **祖先的落点在 fsync 时刻就是已知的**，只是没进记录。

**要测的形态**：fsync 只写脏叶 + 一条记录，记录里带**整条祖先链的落点与校验和**，
祖先内容不写。重放：读旧祖先 → 打上变更 → 写到记录点名的地址。
⇒ 不挑任何空闲块，且确定性。

**自变量**：负载 × fsync 频率 × checkpoint 间隔 × 树高（记录大小正比于它）。

**测什么**：
1. **记录大小**：每条 ≈ `48 + (路径长度 + 1) × (落点 + 校验和)` 字节，
   与候选乙（点名叶）和候选甲（不延后）逐格对比。
2. **同一祖先在一个窗口内被反复触碰时的落点消耗**：是每次一个新落点，还是可以复用。
   **这一项是丙成不成立的关键**——若每次触碰都要一个新落点，
   一个热点目录会在一个 checkpoint 窗口内吃掉大量落点。
3. **「已分配未写」的落点在崩溃后靠什么不被重复分配**：
   若答案是「重放读记录即可重建那个集合」⇒ 不需要额外持久结构；
   若不是 ⇒ 丙退回候选乙那一侧，本实验的结论就是「丙不成立」。

**阳性对照**：把候选甲与乙用同一份 harness 跑出来，必须复现
[experiments.md](experiments.md) E16 已有的数（rand/每次 fsync：甲 7 块、乙 2 块）。
复现不了说明 harness 有问题，**整轮作废**——不许把「丙没优势」记成结论。
⚠️ **对照要对三条臂各跑一遍**，不是只跑第一条。

**怎样才算失败**：若丙的记录大小使 fsync 块数追平候选甲，则丙买不到东西，如实记「丙不成立」。

**前置**：无。E16 的 harness（`research/e7-index-bench/src/bin/e16_journal.rs`）加一条臂即可。
