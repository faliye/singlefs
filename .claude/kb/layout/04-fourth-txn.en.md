# Bytes Written by Sharing and Reclamation (On-Disk Forms Newly Appearing After New-Pool File Creation, Overwrite and Deletion)

[中文](04-fourth-txn.md) · **English** · [日本語](04-fourth-txn.ja.md)

**Registry table for steps I.3 and VI.3 of milestone "Sharing and Reclamation"** ([04-fourth-txn.md](../milestone/04-fourth-txn.md)), established 2026-10-26. Each byte segment of new-pool file creation is in [layout/01-first-txn.md](01-first-txn.md), the forms newly written by overwrite, release, rollback and reuse are in [layout/02-second-txn.md](02-second-txn.md), and the forms newly written by deletion and by the lineage records of administrator rollback are in [layout/03-third-txn.md](03-third-txn.md); here we only register the forms newly written in milestone four: read-only snapshots (creating a snapshot, overwriting and deleting files under a snapshot, deleting a snapshot), compaction (intent and relocation batches), truncation and extension, partial writes, extent upper leaf tag 0, and the on-disk quarantine mark. Widths and placements of the same field follow layout/01-first-txn.md and are not copied again. Each row points to a decision item; rows that point to no item are written as "format-level blank" with their source, collected in section "8. Format-Level Blanks and Not Found". Line numbers of code sources were looked up in the working tree on 2026-10-26 (including changes other sessions have not yet committed); this table cites no dry-run artifact, and the bytes follow the read and write functions named in `crates/`.

## 5. Truncation Fields of the inode Record and incompat Bit 2

The other fields of the 140-byte inode record follow section "IV. File Metadata (inode)" of [layout/01-first-txn.md](01-first-txn.md); row "inode record (offset 108 / 112 / 120 / 128 / 136)" of that section lists the two truncation fields from offset 120 and the 4 reserved bytes from 136; their values and write rules are in this section. The bytes are written at `crates/singlefs-core/src/records.rs:163`–`:165`.

| Offset | Field | Width | Value | Points To |
|---|---|---|---|---|
| 120 | Truncation field T | 8 | The txg of the most recent truncation intent publish that released units; 0 if there never was one | D8 (Core Index Structure) settled item 6 |
| 128 | Truncation field N_w | 8 | The target byte count of that truncation; must be 0 when T = 0 | D8 (Core Index Structure) settled item 6 |
| 136 | Reserved | 4 | Always 0 | D8 (Core Index Structure) settled item 6 |

Write rules: in the truncation intent publish, when the units existing before it outnumber ⌈N ÷ payload⌉ (at least 1), the fields are written as (this txg, N); a truncation that releases no unit copies the previous version (`truncation_field_after_the_truncation_intent` at `crates/singlefs-core/src/truncate.rs:116`); batches, the final batch, extension, same-size requests and unlink copy it; whole-content writes (sequential write, overwrite) clear it; a newly created inode writes 0; rollback restores the value of the target version (paragraph "compatibility and writing of the truncation fields" of D8 (Core Index Structure) settled item 6). Readers: T = 0 with N_w ≠ 0 makes the record unusable (`crates/singlefs-core/src/records.rs:91`); on a pool without incompat bit 2, offsets 120–135 must be all zero, and a record where they are not is EIO (I-9.7 (three record segments always zero)).

| Segment | Field | Width | Value | Points To |
|---|---|---|---|---|
| System configuration | First byte of the incompat bitmap in the feature bits (slot offset 6) | 1 | 0x06 (bit 1 layout identity plus bit 2 truncation fields); readers accept both 0x02 and 0x06 and refuse bit 2 without bit 1; on a pool without bit 2, inode record offsets 120–135 must be all zero | D15 (Format Freeze Policy) settled item 4 |

The writer writes bit 2 on every system configuration write (`INCOMPAT_INODE_RECORD_TRUNCATION_FIELDS_BIT` at `crates/singlefs-core/src/system_configuration.rs:35`; the system configuration write is at `crates/singlefs-core/src/transaction.rs:627`), and mkfs writes it too (`crates/singlefs-core/src/make_filesystem.rs:791`), so the first incompat byte of the system configuration in new-pool file creation is also 0x06 (the same value that the feature bits row of the system configuration field table in section "I. ## 7. On-Disk Quarantine Mark

The form of an allocation record follows section "V. Space Accounting and Allocation" of [layout/01-first-txn.md](01-first-txn.md): value = span field 2 (little-endian) + allocation or release generation 8.

| Segment | Field | Width | Value | Points To |
|---|---|---|---|---|
| Allocation record value | Highest bit 0x8000 of the span field | 1 bit | Released flag | D3 (Space Allocation) settled item 7 |
| Allocation record value | Second-highest bit 0x4000 of the span field | 1 bit | Quarantine mark: the quarantining publish sets it in that record on both disks, the record stays allocated and its allocation generation unchanged; the revival publish of a rollback clears it in the same publish; releasing a quarantined record rewrites it as released and clears the mark with it | D19 (Block Pointer Structure & Width Budget) settled item 5 "on-disk quarantine mark" |
| Allocation record value | Remaining 14 bits of the span field | 14 bits | Span value (1 or 2); marked records read as spans 1, 2 | D3 (Space Allocation) settled item 7; D19 (Block Pointer Structure & Width Budget) settled item 5 |
| Allocation record value | 0x4000 and 0x8000 both set | — | A bad record; the reader refuses it (`QuarantineMarkOnAReleasedRecord` at `crates/singlefs-core/src/allocator.rs:57`) | D19 (Block Pointer Structure & Width Budget) settled item 5 |

The mark constant is at `crates/singlefs-core/src/allocator.rs:37` and it is written by `release_leaving_the_record_allocated_on` at `crates/singlefs-core/src/allocator.rs:2206`; when any copy of a unit fails the check, both copies are returned together and both disks keep the record (`crates/singlefs-core/src/transaction.rs:5122`). Old readers that do not know the mark read 0x4001, 0x4002 and refuse the whole allocation record tree (E187 (Cost of Persisting Quarantine Marks) segment one). The pool-level checker only trusts the mark: an unreleased record marked on both disks is not judged a violation of I-3.15 (Unit Covered by an Unreleased Record Is Pointed to by the Mapping at This Slot) (D19 (Block Pointer Structure & Width Budget) settled item 5); asymmetry between the two disks has no verdict yet (C873 (nobody judges asymmetric quarantine records across two disks)).
