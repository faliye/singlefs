## D1 数据可移动性 / 反向索引 —— 已定

**要。且 day-1 就设计进格式，不许后补。**

支持 balance / defrag / 缩容 / 移除设备 / 纠删码，都要求能回答"这个物理块被谁引用"。

依据：btrfs 选了要但是**后长出来的**，成了它最复杂、bug 最多的部分；
ZFS 选了不要，换来简单，代价是二十年不能缩容不能碎片整理。
本工程要"解决痛点"，缩容和整理是刚需，所以选要——但必须是设计出来的，不是补出来的。

**bucket generation 已调查（2026-08-26，Linux v6.17 `fs/bcachefs/` 源码核实）——对本决策减负有限，
不能指望它替代反向索引：**

- **它只对缓存副本成立。** `buckets.c` 里 `!p.ptr.cached && gen_cmp(p.ptr.gen, g->gen) < 0`
  直接判 `stale_dirty_ptr`（fsck 级不一致）；读路径上撞到就 `bch2_fs_inconsistent()`。
  理由是机制性的：**bump gen 的语义是「这份数据没了」**——对缓存副本合法（回源重读），
  对唯一副本就是丢数据。
- **它只管「失效」，不管「搬运」。** 搬 = 数据还在、换了地方 = 引用必须指向新地方；
  失效 = 数据没了 = 引用可以懒惰作废。**gen 把「回收」的代价从 O(引用数) 降到 O(1)，
  一点也不减「搬运」的代价。**
- **它的绕回处理是一次全索引遍历**（`BUCKET_GC_GEN_MAX = 96`，超限靠 `bch2_gc_gens()` 恢复，
  该函数遍历每一棵带指针的树的每一个 key）——**正是 `.claude/rules/fs-design.md`
  记账纪律点名否决的「事后扫一遍」形态**。
- **bcachefs 自己在往回走，而且已经走完了。** 它的 Principles of Operation
  （Rev 1.39.2+2202696，2026-08-25）在 bucket 状态清单里把 `need_gc_gens` 标为
  **「Legacy state, retained for compatibility. Previously used to prevent generation number
  wraparound; now effectively unused since the invalidate worker uses backpointers
  instead of generation bumping.」**
  对应的 commit 原话两次点名同一理由：`gc_gens` "requires a full metadata scan" /
  "this gets rid of another scalability limit"。**那个方向恰好是 D1 已经选的路。**
- **它的设计文档对适用范围写得同样明确**（§1.5 原文）：
  「we can reuse a bucket with **cached data** in it without finding and deleting all the
  data pointers by incrementing the generation number」——**限定词是 cached。**

**结论：维持本决策（反向索引 day-1 设计进格式）。** bucket generation 可作为
「缓存副本回收」的优化并入，但它对 [decisions.md](decisions.md) D9 未答项 5 的
「无密钥能不能搬」**无效**。

## D2 RAID 条带策略 —— 已定

**条带宽度可变，每次写都是全条带写，永不 read-modify-write。**

write hole 不是被修好的，是被设计成不存在。ZFS RAID-Z 已验证此路可行。

代价：空间效率略降，小写有浪费。接受。

**存在第二个已知好答案（2026-08-26 调查补充，未采纳，备查）**：
bcachefs 在**后台对整个 bucket 做纠删码**，而不是把前台写切成条带——
前台正常多副本写，后台攒够候选 bucket 再算一次 parity，然后原子更新所有指针。
parity 只对不可变数据算一次，因此同样不存在 write hole。
代价是 stripe 里只要还有活数据，其中的 bucket 就不能复用。
两条路都成立，本决策维持变宽全条带；若将来 D8 采用 bucket 模型，此项应重新权衡。

**与 D9 的连锁**：parity 对密文算，多副本是同一份密文写 N 遍——加密 N 次会得到 N 份不同的字节。

## D3 空间分配 —— 已定

**1. 不分 data / metadata 两类空间。** 全局统一分配器。

依据：btrfs 的两级分配 + chunk 分类僵化是 ENOSPC 病根
（"`df` 还有几十 G，写文件报没空间"、"删文件也报没空间"）。

**2. 连带承诺：后台整理必须是常驻的、自动的、用户无需知道的。**
不分类意味着碎片化压力全压在一个分配器上，btrfs 靠人手动跑 `balance` 来救，
这是它最大的运维恶名之一。选了不分类就等于承诺自动整理。

**3. 空间预留用准入控制形态，量要小。**
预留不是"划一块地不给用"，而是：任何增加空间占用的操作，进门前先算
"最坏情况下解开自己需要多少"，算不过就拒绝。这样预留量动态贴着实际需求，不白占。

**4. 与 D9 的连锁**：加密开启时，无密钥的一侧只能**检测**（指针里有密文校验和），
**搬不动**——搬块要更新引用，那要读写加密的索引树。
「未解锁也能整理」到哪一步是 D9 未答项 5。

**原则**：COW 系统必须保证「释放空间」这个操作本身不需要申请空间。
btrfs 没在设计层保证这点，靠一堆启发式补了十几年还在出问题。

## D4 校验和位置 —— 半定

**方向：内联进指向该块的指针（父节点存子节点校验和），形成 Merkle 树，自验证。**

收益：整棵树自验证，能检测"读到了正确但过期的块"；
而且 btrfs 那棵庞大的独立 csum tree **直接消失**。ZFS 与 bcachefs 都是这个形态。

**与 D9 的连锁**：加密开启时这个字段存的就是 MAC，两者是同一个字段的两种取值。
校验和粒度因此也是 MAC 粒度，加密不另开一层。

**未定**：校验和粒度与随机小读的张力。
内联会让校验和粒度和 extent 粒度耦合，大 extent 的随机小读被迫读取并校验一大块。
bcachefs 存在这个问题。需要单独设计。

## D5 快照 / 空间记账机制 —— 已定

**采用 ZFS 的 birth txg + deadlist 模型。**

- 每个块自带**诞生代号**（birth txg）。
- 删除时，把块的代号和"下一个更老的快照"的代号比：
  块更新 → 直接释放；块更旧 → 进那个快照的 deadlist。
- 销毁快照时，遍历它的 deadlist 级联合并到下一个更老的快照，不做全盘扫描。

**核心性质：记账是增量维护出来的，不是事后遍历出来的。** 这是本决策的全部价值。

**独立印证（2026-08-26）**：bcachefs 的记账「由触发器在 key 提交时维护，
不靠遍历 btree」，而其 `check_allocations` 用全量遍历重建记账，
以此分辨「计数器过期」和「key 真的还在」。
这与 [invariants.md](invariants.md) 的 I-3.1 是同一个设计。

依据（实测数据来自 btrfs 官方，见 prior-art.md）：btrfs qgroup 走 extent refcount +
反向索引遍历，代价是提交时间 +76%、事务等待 +1347%、写吞吐 −25%。
btrfs 自己已经投降，另出了 squota（不算全局 refcount，只归属原创建者）。
**这条路走不通已经不需要本工程再验证一遍。**

**与 D9 的连锁**：birth txg **不能**当加密 nonce——同一事务里的块共享它，nonce 会重复。

**未定**：计数器的**载体形态**。bcachefs 2024 年把计数器做成 btree 里的 key
（tagged union，加新统计维度不用改格式），是个值得采用的形态，但与 D8 耦合，等 D8 定。

## D6 快照实现模型 —— 待定（低优先）

候选之一是 bcachefs 的「快照 ID 进 key 低位」：快照 ID 自成一棵树，
查找时按祖先关系过滤，不 clone 任何树，创建 O(1)，可有百万级快照。

代价：删快照要遍历所有带快照的 btree；读路径有恒定的祖先过滤开销；
写路径要处理 whiteout 和跨快照的部分覆盖分片。

**注意它和 D-写路径优先的耦合**：这个选择会显著改变提交路径的复杂度，
即"第一段代码长什么样"。真要采用就得早定；不采用则可以一直拖。

现状：**不作为默认方案，仅作候选。**

## D8 核心索引结构 —— 半定

**不预设 B-tree。** 调查见 [prior-art.md](prior-art.md) 第五节。

**方向已定，两处细节待实验取值。**

### 结构

**一套 btree 实现 + 多个独立 keyspace + 两个前端。** 不做异构结构。

| 层 | 做什么 |
|---|---|
| 独立 keyspace | 每类数据一棵树（extent / inode / dirent / 反向索引 / 空闲空间 / 记账 …），互不干扰 |
| 日志结构节点 | 节点内新 key 追加不插入，内存里定期重排；写顺序、可在只读锁下回写 |
| **write buffer** 前端 | 高频小更新（反向索引、LRU、记账）批量攒起来排序去重后批量插入 |
| **key cache** 前端 | 同一批 key 反复读写的（分配信息）走哈希表，不做全树查找 |

依据：bcachefs 用 28 棵树 + 一套 btree 实现，write buffer 覆盖其中 10 棵。
这比「按访问模式选不同结构」好在**只有一套结构要调对**——
异构方案意味着 N 套实现、N 套崩溃一致性 bug、N 套 checker。

**已知代价**（原文明写）：write buffer 的更新无序且最终一致，
flush 时按 key 排序**丢弃时间序**，且这个 sort-merge-sweep **本质单线程**，
在多线程负载下它的效率是关键路径。这是采用前必须接受的一条。

### 已答的三个未定项（2026-08-26）

**1. key 布局：改名与索引分开处理 —— 采纳，方向已定**

原来的问法「按 inode 还是按路径」是个假二选一。**scan 局部性不一定要住在 key 序里**，
它可以住在四个不同的地方：

| 局部性放在哪 | scan | 改名 | 代表 |
|---|---|---|---|
| key 序（全路径索引） | 最好 | **O(子树深度)**，见下方修正 | BetrFS 0.4 |
| 分配器（把子目录的数据放到父目录附近） | 好 | 免费 | ext4 Orlov 分配器：遍历内核树快 30% |
| 第二索引 | 好 | 仍然贵 | —— 且要多维护一份一致性 |
| **出生时继承、改名不更新的 locality 前缀** | 较好 | 免费 | 本工程方向 |

**⚠️ 这张表的第一行在 2026-08-26（其四）被修正，采纳结论因此需要重新权衡。**

BetrFS 0.4（FAST 2018）的 lifted Bε-tree 把全路径索引的改名代价
**从「子树大小」降到「子树深度」**——论文复杂度一节明写：tree surgery 里被切分或合并的
节点数「at most proportional to the height of the tree」。
机制与论文自陈的代价见 [prior-art.md](prior-art.md) 5.6。
换言之，「全路径索引改名代价爆炸」这条前提**对 2018 年之后的实现不再成立**。

**但采纳结论不因此自动翻转，因为全路径索引在本工程还有三条 BetrFS 不必付的代价：**

1. **与 D9 加密直接冲突。** 全路径索引意味着 btree 内部节点的分隔 key 就是路径，
   而 D9 未答项 5 已经认定「dirent 树的分隔 key 就是文件名」是敏感信息。
   全路径索引把这个泄漏面从 dirent 一棵树扩大到**所有按路径编 key 的树**。
2. **与 D1 反向索引的稳定性冲突。** 反向索引要回答「这个物理块被谁引用」，
   引用方的身份如果是路径，改名就会让所有反向索引条目失效；按 inode 编 key 则不会。
3. **lifting 对 key 编码提出的额外要求还没有和 D9 的 nonce 载体、D6 的快照 ID 位置对过账**，
   三者抢的是同一段 key 空间。

**结论：维持采纳第四种（继承式 locality 前缀 + dirent 树），但理由改写。**
理由不再是「全路径索引改名代价爆炸」（该前提已被修正），
而是**「全路径索引与 D9 加密的泄漏面、D1 反向索引的稳定性冲突」**。
两条路的定量差距由 [experiments.md](experiments.md) E9 量。

**采纳第四种**：key = `(locality_id, inode, offset)`。
`locality_id` 在创建时从父目录继承，**改名时故意不更新**。

- 命名走 dirent 树（`parent, name` → inode），改名就是删一条加一条，**O(1)**
- 数据按 inode 编 key，与名字彻底解耦
- scan 局部性来自继承的 `locality_id`，改名后**局部性缓慢退化，正确性不受影响**
- 退化由常驻后台整理修复——**D3 已经承诺了常驻后台整理，这里是复用，不是新增负担**

这条把改名代价换成了「局部性慢慢变差」，而后者是可以在后台慢慢还的债。

**批量改名（2026-08-26 补）**：`mv 大目录 别处` 在这个设计下**只改一条 dirent**——
子项按 inode 编 key，key 里没有路径，改名碰不到任何后代。这正是选它的理由。

但有三处会把改名重新变成无界操作，**必须一开始就堵死**：

1. **`locality_id` 永远不许被改名更新。** 一旦「改名后重新聚簇后代」进了同步路径，
   改一个大目录就要动几百万个 key。`locality_id` 是**提示，不是正确性的一部分**——
   它可以是错的、可以过期，不影响任何语义。
2. **改名覆盖已存在的目标 = 一次删除**，若目标是大文件/大目录，
   这条路径必须走下面第 3 条的 intent log，不能因为「这是改名」就绕过。
3. **后台重新聚簇必须是增量、可中断、可续做的**，且随时可以停掉不做。
   它是优化，不是义务。

**推论（可当 review 判据用）**：**任何让 rename 触及后代的设计改动，一律否决。**

**待验证**：按 inode 编 key 时递归遍历到底慢多少，决定 `locality_id` 值不值得做。
见 [experiments.md](experiments.md) E2。

**2. 节点大小 —— 上限由可恢复性定，靠实验取值**

大节点省 seek、树更浅，但**一个坏节点的爆炸半径随节点大小线性放大**，
与本工程的可重建性目标直接冲突。所以**不照抄 128K–256K**。

取值靠实验定，判据与失败条件见 [experiments.md](experiments.md) E1：
在「全盘扫描重建成功率 ≥ 目标线」的前提下取查找代价最低的那档。

**按设备特性动态选取（2026-08-26 补）—— 采纳，但有三条约束**

节点大小写进超级块，**mkfs 时按设备特性自动选取**，可显式覆盖。
参考量：旋转介质 vs SSD（seek 代价差一个量级）、设备容量、
以及 flash/zoned 设备的擦除块或 zone 大小。

约束：

1. **它是 mkfs 时的格式参数，不是挂载参数。** 建完就固定，
   改它等于重建文件系统。自动选取只发生在 mkfs 一次。
2. **默认策略必须是确定性的、可查的。** 同样的设备特性必须得到同样的取值，
   并且 mkfs 要把「为什么选了这个值」打出来。
3. **测试钉死的是「模拟设备的参数」，不是节点大小本身。**
   QEMU 可以模拟旋转标志、容量、块大小、discard 粒度，
   所以测试环境固定一组设备档位，让自动规则照常跑——
   这样**连选取规则本身也一起被测了**，比绕过它更好。
   要求只有一条：**同一档位必须得到同一取值**，否则
   `test-discipline.md` 的「N≥5 轮全通过」和镜像差分比对会一起失效。

**3. whiteout 删除 —— 接受，但批量删除必须走 intent log**

接受日志结构节点带来的 whiteout 删除。但**批量删除是这个设计最危险的地方**：
删大目录、截断大文件会产生海量墓碑，想塞进一个事务必然爆掉。

**做法（bcachefs 已验证的形态）**：
凡是**可能修改无界数量 extent** 的操作（truncate、collapse、删大目录），
不做成一个大事务，而是**先把意图写进 logged_ops 树，再分批推进**；
崩溃后恢复时续做未完成的意图。删除中的 inode 单独进 `deleted_inodes` 树，
由后台回收——用户的 `rm` 返回，不等于所有 extent 都已释放。

**硬要求**：
- 无界规模的操作**一律不许做成单个事务**，必须是「写意图 → 分批 → 可续做」
- 意图必须**幂等**：续做时重复执行已完成的部分不能出错
- whiteout 在节点重写合并 bset 时清除，**不许有别的清除路径**

**断电之后怎么办（2026-08-26 补）**

意图本身就是一条普通 key，**骑在同一个事务层上**（`.claude/rules/fs-design.md` 第 6 条），
所以它和别的元数据一样受崩溃保护。断电后只可能落在三种状态，每种都有确定的出路：

| 断电时机 | 恢复后看到 | 怎么收场 |
|---|---|---|
| 意图提交之前 | 没有意图 | 操作从未发生，用户那边也没返回成功 |
| 意图已提交、工作做了一半 | 意图还在 | 恢复时**续做**；已做完的部分被幂等地重跑一遍 |
| 工作做完、意图未删 | 意图还在 | 续做一遍发现无事可做，然后删掉意图 |

不可能出现「意图没了但目标状态没达成」——因为**删除意图必须与最后一批工作在同一个事务里提交**。

由此得到三条设计规则：

1. **意图声明目标状态，绝不声明增量。**
   「把文件 X 截到 N 字节」可以重复执行，「再删 1000 个 extent」不能。
   任何写成 delta 的意图都是错的。
2. **续做是每次恢复都跑的常规动作，不是修复手段。**
   把它做成可选的修复通道，就会出现「平时不跑、真出事时才第一次跑」的代码路径。
3. **中间状态必须每一个都是合法的文件系统状态。**
   分批推进意味着任何一批之间都可能断电，
   所以「删了一半 extent 的文件」本身就得是合法的。

**范围重建 vs 逐项修改：切换判据（2026-08-26 补）**

无界操作有两条实现，**都要有，并且要有显式判据决定走哪条**
（`.claude/rules/fs-design.md`「不追求万能方案」）：

| 走法 | 代价 | 适用 |
|---|---|---|
| 逐项修改 | K × 随机访问 | 受影响的 key 稀疏散布 |
| 范围重建 | N × 顺序访问（读一遍写一遍） | 受影响的 key 在 key 序上连续 |

朴素的交叉点是 `K/N > 顺序代价/随机代价`——机械盘上这个比大约 1/100，
SSD 上大约 1/10，即**机械盘碰超过约 1% 就该重建，SSD 要碰到约 10%**。
⚠️ 这两个数是**推理，不是实测**，要靠 [experiments.md](experiments.md) E4 量。

**但真正的开关不是 K/N，是「受影响的 key 连不连续」**：

- 连续 → 范围重建可以**整节点丢弃或整节点重写**，是顺序操作
- 不连续 → 只能逐项，重建也快不起来

**由此得到一条布局规则：让一起死的东西在 key 序上挨在一起。**

- dirent 按 `(parent_inode, name)` 编 key → 删整个目录是范围操作
- extent 按 `(inode, offset)` 编 key → 截断是范围操作
- 同一快照的 key 带同一 snapshot 前缀 → 删快照有机会变成范围操作

**这顺带从结构上解掉了 whiteout 膨胀**：范围删除直接丢弃整个节点，
根本不用插 N 个墓碑。墓碑只在「稀疏删除」这一条分支上产生，而那条分支本来量就小。

按 `.claude/rules/fs-design.md` 的五条要求，这个分支还欠：判据写成可计算的式子、
留一个能强制走指定分支的测试开关、两条分支各自跑崩溃点重放、
运行时能看出走了哪条。

⚠️ **切换判据里不许出现「当前填充率」这类操作中途会变的量**——
一个无界操作跑到一半判据翻转，恢复时走了另一条分支，要验的就是叉积。
判据只能用操作期间稳定的输入（介质类型、受影响 key 是否连续、操作开始时的规模估计）。

**与 D3 的交互（容易漏）**：意图未完成期间，那些空间**还没真的释放**。
空间统计必须把「待删除但未完成」计进去，否则会出现
「我删了一大堆，`df` 却不动」——那正是避坑清单里 btrfs 被抱怨的那类现象。

## D9 加密 —— 半定（方向已定，四条细节未定）

调查见 [prior-art.md](prior-art.md) 第六节。

### 方向

**整卷 AEAD，加密边界与校验和边界重合：D4 那个内联进指针的字段，
在加密开启时就是 MAC。除超级块外全部加密，元数据留最小明文头。**

依据：

1. **AEAD 的位置已经由 D4 腾出来了。** 块层加密（LUKS）做不了认证，
   是因为它没地方放 MAC 和 nonce 而不破坏块对齐；fscrypt 不认证，
   给的理由也是密文膨胀。校验和跟着指针走的 COW 文件系统没有这个约束。
2. **不做 per-directory / per-subvolume 加密。** bcachefs 拒绝它的理由在本工程更重：
   fsck 需要文件大小，大小就得明文；而本工程的 checker 要靠全盘遍历验记账
   （[invariants.md](invariants.md) I-3.1），有一部分子卷锁着就等于那部分记账验不了。
3. **不为「无 key 也能后台维护」把元数据挪到明文。** ZFS 选了那条路，
   代价是间接块全明文（池结构、文件大小、文件洞、快照结构都泄漏），
   认证退化成 SHA512 聚合而不是 MAC 树，并且要在 objset 层维护 portable / local
   两个根 MAC——[prior-art.md](prior-art.md) 6.4 记的那串 send/recv 损坏 bug
   就长在这套复杂度上。
   **这条同时压住未答项 5 的第二个候选**（索引内部节点留明文）：那是同一条路，
   在本工程还更糟，因为内部节点的分隔 key 带语义。

### 已答（2026-08-26）

**1. 指针里额外存一份密文的非密钥校验和 —— 要。**

即指针里有两个完整性字段：MAC（要密钥，认证）+ 密文校验和（不要密钥，查损坏）。
ZFS 是同一个形态，它把 `blk_cksum` 前 128 位留给密文的截断校验和专供 scrub。

依据：本工程的可重建性与常驻后台整理是硬承诺（D1、D3），
而「未解锁就完全瞎」会让这两条在最需要的时候（盘开始坏、人不在）失效。
代价是指针变大，且无密钥时的「修复」判据只有校验和，
攻击者能造出校验和自洽的块骗过无密钥的一侧——**无密钥只做检测与搬运，不做判定谁是好副本**。

**2. 加密不进第一个可运行版本 —— 只预留格式字段。**

实现等事务层与 checker 跑通之后再接（`.claude/rules/fs-design.md`：从事务开始，不从功能开始）。
预留的四样见下表，**一样都不能少**——它们事后加不进去，加密实现却可以随时接。

### 这个答案打开的新缺口：无密钥能「验」，不等于能「搬」

**存了密文校验和只解决了检测。** scrub 读一遍、比一遍校验和，无密钥可做。
但 copygc / balance 要搬块，搬完必须**更新引用**——那要读写索引树，
索引树是加密的就读不了。所以「无密钥维护」到底到哪一步，是新的未答项 5。

三个候选，各自的代价已知：

| 候选 | 无密钥能做到 | 代价 |
|---|---|---|
| 只做 scrub | 检测损坏、报告坏块 | 搬不动任何东西，碎片和坏盘疏散仍要密钥 |
| 索引内部节点留明文 | 能搬、能疏散 | **内部节点带分隔 key，dirent 树的分隔 key 就是文件名**——泄漏面比 ZFS 大得多（ZFS 的间接块是纯指针数组，没有 key） |
| 反向索引 + bucket 代号留明文 | 能搬（靠代号失效，不必逐条改引用） | 依赖 D1 待调查的 bucket generation 机制；泄漏物理布局与引用关系 |

**第二个候选在本工程比在 ZFS 危险得多**，因为本工程的索引是 key 有序的
（D8），而 ZFS 的间接块按偏移索引、不含语义。**这条差异要在选之前想清楚。**

### 三条现在就能定死的硬要求（与最终选型无关）

1. **nonce 不许由物理位置派生。** 派生自物理位置的话，balance / copygc 搬一个块
   就要重新加密（D1、D3 要求数据可移动），而重新加密要改 MAC、要改指针、要 key；
   多副本还会因此字节不同，D2 的 parity 直接算不成。
   **nonce 必须跟逻辑身份走并存在指针里。**
2. **顺序固定为 压缩 → 加密 → MAC。** 反过来不可能（密文压不动）。
   由此密文长度泄漏明文可压缩性（Kelsey, FSE 2002），
   这个泄漏是选了压缩就必须接受的，写进已知泄漏清单，不装作没有。
3. **若采用截断 MAC，读重试次数上限必须是写死的小常数，并且有检查。**
   bcachefs 的 80 位 MAC 安全论证整个押在「MAC 对不上就判设备坏、很快停用」上
   （约 10 次伪造机会）。**那是一条实现行为，不是密码学性质**——
   不把它钉死，论证不成立。

### 格式必须 day-1 预留的四样

**这是「D9 必须早定」的具体内容。** 即使第一版不实现加密，这四样也必须在格式里：

| # | 字段 | 不留会怎样 |
|---|---|---|
| 1 | 指针里的 MAC + nonce 空间 | 事后加等于改指针宽度，全格式重来 |
| 2 | extent 的「距原始 extent 起点偏移」 | extent 被切分后重写时无法既不重用 nonce 又不重算，见 [prior-art.md](prior-art.md) 6.3 |
| 3 | 超级块的 KDF 标识 + 主密钥槽 + 加密类型 | 换不了 KDF，也没法在既有文件系统上开加密 |
| 4 | 每个数据/元数据写的算法类型字段 | 换不了算法；bcachefs 把加密做成一种校验和类型，新数据用新算法、老数据按各自字段解 |

### 未答项 5 —— 已定（2026-08-26）：取第三个候选，性能优先

**把「一个块的物理地址的权威记录点」移出加密结构**，让无密钥的一侧能搬块。
即采用三个候选里的第三个（明文的逻辑身份 → 物理地址映射层 + 明文反向索引）。

**依据（用户定案）**：这是一笔**互斥取舍**，不是可以设计掉的东西——
无密钥搬运要求「位置」能在无密钥下被改写，而「被 MAC 覆盖」要求它不能。
两者不可兼得时**性能优先**，因为 D3 的「常驻、自动、用户无需知道的后台整理」是硬承诺，
而锁盘状态下整理瘫痪会让 D1（缩容、移除设备）与 D3（碎片）在最需要的时候一起失效。

**明确失去什么，不许含糊**：

| 失去 | 具体是什么 |
|---|---|
| 「哪个块该出现在这个位置」的密钥保护 | 位置信息移出 MAC 覆盖范围后，攻击者可以重排块。**块内容仍被 MAC 认证**（改内容仍会被发现），但**换位置不会** |
| D4 「检测读到正确但过期的块」的抗篡改性 | 可以用父指针里的明文期望代号补回**检测**能力（形态同 bcachefs `bch_btree_ptr_v2` 的 `seq`，纯整数比较、不需要密钥），但代号是明文，**攻击者可以连块头带代号一起伪造** |

⚠️ **这条使本决策正文拒绝 ZFS 那条路的理由被部分推翻**：
本决策正文以「认证退化成聚合而不是 MAC 树」为由拒绝了「把元数据整体挪到明文」。
现在本工程也接受了一个明文间接层——**差别在于范围**：
ZFS 是整个间接块明文（池结构、文件大小、文件洞、快照结构全泄漏），
本工程只把**逻辑身份 → 物理地址**这一层扁平映射放明文，
**不暴露 btree 内部节点的分隔 key**（D9 已认定 dirent 的分隔 key 就是文件名，属敏感）。
这个范围差异是本条成立的全部依据，**必须在实现时守住，守不住就等于走了 ZFS 那条路**。

**尚未定的细节**：明文映射层的最小字段集合、它自身的完整性怎么保
（它不参与 MAC 认证，但仍需防静默损坏——候选是不要密钥的密文校验和，同已答项 1）。

### 未答项 5 的瓶颈在哪（2026-08-26 源码核实后定位）

**瓶颈不是 MAC 的位置，是「一个块的物理地址的权威记录点在不在密文里」。**

把 MAC 从父指针挪到块自己的明文头（bcachefs 对 btree 节点就是这么做的——
`extents_format.h` 有一行注释直说 `/* Btree pointers don't carry around checksums: */`），
**只松一格，门还锁着**：

- 松的那一格：元数据块可以**原样搬**——MAC 覆盖块自己的字节，nonce 不由物理位置派生
  （本决策硬要求 1 已经这么定），所以搬 = 把密文逐字节复制到新地址，不用重算 MAC、不需要密钥。
  bcachefs 已经把这条做到数据侧：`extent_nonce()` 只用 `bversion` + `crc.nonce`、与物理位置无关，
  无需裁剪/重压缩时加密 extent 被逐字节原样搬走，全程不解密。
- **还锁着的那一格**：父指针里的**地址字段**仍要改，而父节点的载荷是密文
  （bcachefs 连「这是哪棵树、哪一层」都在密文里）。**无密钥后台整理仍然瘫痪。**

⚠️ **「无密钥后台整理瘫痪」这一句是推理，不是引文。** 2026-08-26 的专项检索
（Principles of Operation 全文、bcachefs.org 的 Encryption 与 FAQ、`bcachefs.5` 手册源码、
Kent 的历次公告）**没有找到任何一手材料用散文明说 copygc / rebalance / scrub / fsck
在无密钥时不能跑**。找得到的是这五条，推论建立在它们之上：
① 除超级块外全部加密且全部认证；② 主密钥在挂载时解密并在内核内存中缓存至卸载；
③ 未解锁时挂载直接失败（`Required key not available`）；
④ 离线 `bcachefs dump` 必须先 `remove-passphrase`；
⑤ 拒绝 per-directory 加密的理由之一是「fsck 需要文件大小，所以大小得明文，
否则要复杂地把那部分 fsck 推迟到密钥提供之后」。
**推论是准确的，但它是推论——按 `singlefs-ai-sop/rules/evidence-discipline.md` 标明。**

**推论：三个候选里真正在动瓶颈的只有第三个**（把物理地址的权威记录点移出加密结构）。

⚠️ **这是一笔必须显式做的取舍，不是可以设计掉的东西**：
无密钥搬运要求「位置」能在无密钥下被改写，而「被 MAC 覆盖」要求它不能——两者互斥。
若把父指针里的 MAC 换成一个明文的期望代号（bcachefs `bch_btree_ptr_v2` 的 `seq` 就是这个形态，
读到子节点后比 `b->data->keys.seq != bp->seq`，纯整数比较、不需要密钥），
能补回 D4「检测读到正确但过期的块」那条收益，**但补不回抗篡改**——
代号是明文，攻击者可以连块头带代号一起伪造。那会退化成本决策正文已经点名拒绝的
ZFS 那种「明文间接层 + 认证靠聚合」形态。

### 与其他决策的连锁

| 决策 | 连锁点 |
|---|---|
| D1 反向索引 | 数据可移动是硬需求 → nonce 不许绑物理位置。**bucket generation 只管失效不管搬运，对本未答项无效**（D1 已核实） |
| D2 纠删码 | parity 对**密文**算；多副本必须字节相同，即同一份密文写 N 遍，不是加密 N 次 |
| D3 后台整理 | 无密钥能验不能搬：scrub 可做，搬运要读写索引，见未答项 5 |
| D4 校验和内联 | 加密开启时该字段就是 MAC，两者是同一个字段的两种取值 |
| D5 birth txg | **birth txg 不能当 nonce**——同一个事务里的块共享它，nonce 会重复 |
| D8 索引结构 | extent key 要留 version number 与偏移字段；btree 节点明文头的字段集合要一起定 |
| D10 随机写 | 任何绕过 COW 的快路径**不许绕过加密**；原地覆盖写会直接造成 nonce 重用 |

## D10 随机写 / 碎片化的真答案 —— 待定（三条候选已立，判层未做）

数据库和虚拟机镜像上的随机写是 COW 文件系统的共同软肋。
btrfs 的答案是 `nodatacow`——关掉 COW，代价是同时失去校验和与快照一致性。
这是个烂交易，本工程不接受用开关糊弄。

**2026-08-26 文献扫描给出三条候选**，调查见 [prior-art.md](prior-art.md) 7.1 与 7.2：

| 候选 | 机制 | 现有证据 | 未知 |
|---|---|---|---|
| **A. 把小写吸收进索引的消息层** | Bε-tree 的内部节点消息缓冲：小写不落到数据块上，先攒在树里批量下刷 | BetrFS 0.4 在 256K 次 4 字节随机写上比 btrfs / ext4 / xfs / zfs 快 400–670 倍（FAST 2018 Table 2，合计仅 1 MiB 写入的极端微基准） | 这个收益在**真实数据库 / 虚拟机负载**上还剩多少；与 D2 全条带写、D5 birth txg 记账怎么共存 |
| **B. 结构上抗老化** | 让索引本身在老化后仍保持 scan 局部性，减少「事后整理」的负担 | FAST 2017 测出老化后的 BetrFS 胜过其余文件系统未老化时的表现（btrfs 除外） | 与 D3 已承诺的常驻后台整理是替代关系还是叠加关系 |
| **C. 交给设备** | NVMe FDP / ZNS 把数据放置与 GC 责任交给主机，减少设备侧写放大 | NVM Express 与 SNIA 公开材料；FDP 不强制顺序写、向后兼容 | 与 COW 自己管分配**职责重叠**，重叠部分是收益还是双重管理的代价 |

**定它需要先回答**：D10 是不是格式级的。

- 候选 A **是格式级的**——「小写住在消息里」要求索引节点格式留出消息缓冲区，
  而节点格式是 D8 的一部分，事后加不进去。
- 候选 B 大部分落在 D8 的结构选择上，也是格式级的。
- 候选 C 主要是分配器与设备抽象，**不是格式级的**，可以后接。

**推论：A 与 B 必须在 D8 的节点格式冻结之前判完，不能拖。**
判据靠 [experiments.md](experiments.md) E7（离线索引 harness 对拍）与 E10（老化实验）。

候选 A 的具体形态与它为什么不能拖，见 D11。候选 A 的收益上界由 D12 决定，D12 是它的前置。

## D11 索引节点要不要留消息缓冲区 —— 待定（不能拖，前置是 D12）

即 D10 候选 A 的具体形态：索引节点的磁盘格式里留不留一块「消息缓冲区」，
让小写先攒在内部节点里、批量下刷，而不是每次都改到叶子（Bε-tree 形态）。

**它的实质不是「节点里留不留一块区域」，是**
**「一个 key 的权威值，允不允许暂时不在它的最终位置上」。**
这是心智模型，与「空间怎么记账」同级——
`.claude/rules/format-evolution.md` 的「概念模型要慢」管的正是这一类，
而不是它前半句「字节随时可拆」管的那一类。

### 为什么不能拖：它与 E1 的节点大小互相定义

链条不需要一行代码就能走通：
Q13 悬着 → [experiments.md](experiments.md) E1 按「内部节点是纯路由」的重建语义定目标线 →
跑出一个节点大小 → 而 D8 约束 1 明写**节点大小是 mkfs 时的格式参数，建完就固定**。

方向还是单向的：E1 的爆炸半径判据把节点往**小**推（D8 明写「不照抄 128K–256K」），
而摊销比是节点容量的函数——BetrFS 0.4 用 **4 MiB** 节点
（见 [prior-art.md](prior-art.md) 7.1）。本工程若取到 16K–32K，
一次下刷能携带的消息条数接近 1，**消息缓冲的收益机制在那个节点大小下自然消失**。

**先定任何一个，等于替另一个做主。** 反方向同样成立：
若定为「要做」，节点大小下界被摊销要求顶起来，与爆炸半径判据直接对撞。

### 代价 1 的适用范围要改写：它是一条横跨 D8 与 D11 的线

**关键区别不在「消息放节点内还是独立树」，在缓冲里放的是「幂等完整值」还是「增量」：**

| 缓冲内容形态 | 合并规则 | checker 要不要理解 value 语义 | 构不构成 D11 代价 1 |
|---|---|---|---|
| **幂等完整值**（含 tombstone） | 「后者胜」覆盖 | **不要**——那是十几行可以独立重新实现的代码 | **不构成**。`evidence-discipline` 说的「共享同一段代码」够不着它 |
| **增量 Δ**（「减 1」「再释放 N 个」） | 依赖 value 语义 | **要** | **这才是代价 1 的成立条件** |

⚠️ **而 D8 已定的 write buffer 前端覆盖「反向索引、LRU、记账」三类，
若其中记账那一棵是 delta 形态，那么代价 1 的一部分 D8 已经在付了，只是没人记账。**
（bcachefs 的 accounting 走 write buffer 且疑为加减形态——**本条未核实**，
2026-08-26 的源码摘录里没有 `disk_accounting.c`，不许当成已知事实用。）

**推论：这条代价的适用范围应当从「D11 要不要做」改写成
「索引里任何一层缓冲允不允许出现非幂等增量」——那条线横跨 D8 和 D11，
而目前只有 D11 被它拦着。**

### 已知的两条推不翻的代价

1. **checker 的 I-3.1 会失去判别力。** 镜像里有未下刷的删除消息时，
   checker 要判「已分配空间统计 == 遍历所有引用得到的和」就必须**解析消息语义**；
   若与运行时共用同一段解析代码，I-3.1 就不再是独立对照
   （`singlefs-ai-sop/rules/evidence-discipline.md`：校验的两条路径不许共享同一段代码），
   它会对着同一个 bug 全绿。而 I-3.1 是本工程记账正确性的唯一手段。
2. **可重建性从「可检出的不可达」退化成「检不出的陈旧」。**
   内部节点一旦存了别处没有第二份的数据，单节点损坏后全盘扫描重建出的树可以
   块头对、校验和对、Merkle 链对，**而内容是旧的**——
   [invariants.md](invariants.md) 现有条目无一能检出这一类。

### 「消息做成独立的树」这条出路：已被复核否掉

该形态把消息放进一棵独立的 `pending_ops` keyspace，主张 D11 因此不是格式级决定。
**不成立，三条依据**：

1. **对第 1 条代价零改善。** I-3.1 要不要把「释放 extent X」这条未下刷消息算进统计，
   与消息放在哪毫无关系——要回答就得解析消息语义。
2. **把第 2 条代价加重。** 消息块的块头说「我属于 pending_ops 树」，
   它与目标树的关联只存在于 key 编码里、没有第二份；
   丢一个 pending_ops 叶子，目标树 I-1.x / I-2.x 全绿而内容是旧的，
   且**损坏发生在 A 树、症状出现在 B 树**。
   更硬的一条：I-1.3（块头记录的所属树 ID 与实际引用它的树一致）在语义上被劈成两个答案——
   物理上属于 pending_ops，语义上承载别人的数据，而格式里只有一个字段。
3. **读路径从 H 变成 H + H′**，且「空树快速跳过」需要一个存在性判据；
   **那个判据一旦要持久化，D11 就又变回格式级决定，只是换了个地方**。

## D12 目标介质 —— 已定

**多种介质各自一等，且各自一套磁盘布局。** 不做「一套布局 + 参数按介质推导」。

依据（2026-08-26 用户定案）：**显式分支比聪明的通用路径更可靠，减少误读写概率。**
这与 `singlefs-ai-sop/rules/machine-first.md` 的推论第一条同源——
「宁可写穷举的显式分支，不写聪明的通用路径——**穷尽性是可机检的**」；
该条原本只写给代码，本决策把它延伸到格式。

**机制上更硬的那一条**（比认知论证硬，因为它不依赖任何关于模型的假设）：
一套布局 + 参数时，拿错介质假设去读一个镜像是**静默误读**；
各一套布局 + `incompat` feature bit 时，不认识那套布局就**拒绝挂载**。
后者是 `machine-first.md` 第二条「用类型让非法状态无法表示」在格式层的形态。

### 这条决策要还的债（一样都不许赖）

按 `.claude/rules/fs-design.md`「不追求万能方案」的五条硬要求与四样未解除的成本：

| # | 欠什么 | 为什么躲不掉 |
|---|---|---|
| 1 | **每套布局各写一份 checker** | 「checker 即规范」，N 套布局就是 N 份规范的可执行形式 |
| 2 | **每套布局各跑一遍崩溃点重放** | 硬要求 3：分支的意义就是行为不同，那崩溃语义也可能不同 |
| 3 | **门禁挂钟按 N 倍算** | 成本 3：门禁运行时长本身是设计约束。[checks-owed.md](checks-owed.md) 的 C8 现在没有任何东西在拦这个膨胀 |
| 4 | **每套布局都要能被测试强制进入** | 硬要求 2：留一个无视自动判据、直接指定布局的 mkfs 开关。进不去等于没测 |
| 5 | **运行时能看出用的是哪套布局** | 硬要求 4：走错分支是性能悬崖，而悬崖不报错 |
| 6 | **布局分支永久** | 成本 2：代码分支可以删，磁盘布局分支不能。**这条的当期成本为零（还没有字节、没有外部用户），但它在冻结之后变为无穷——因此本决策的真实代价由 D15 格式冻结政策决定** |

### 未定

1. **分几套，判据是什么。** 候选轴：旋转 vs 固态、zoned（ZNS 强制顺序写）vs 常规、
   有无 NVMe FDP。判据必须显式、可计算、写进 mkfs（硬要求 1）。
   ⚠️ 每多一套布局，上表六项债各乘一次——**套数是成本的乘数，不是加数**。
2. **共用多少。** 布局不同不等于全部不同：块头自描述字段、feature bit 编码、
   超级块骨架、指针里 D9 预留的四样，这些能不能强制所有布局一致？
   共用的部分越多，第 1、2 项债越小。

   ⚠️ **但共用有一条不许越过的线：checker 里与 I-3.1 判别力相关的那部分代码不许跨布局共用。**
   本条与上面债表第 1 项「每套布局各写一份 checker」存在张力，张力的解法不是折中，是划线：
   **格式常量、块头解析、feature bit 编码可以共用；「某条记账事实成不成立」的判定路径不许共用。**

   理由：若两套布局的 checker 链接同一套参数化对账框架、只是调用时不启用某个插件，
   独立性就从「这段代码不存在」降级成「这次调用没用到这段代码」——
   **而后者正是 D11 否掉「消息独立成树」时用的同一条判据**
   （`singlefs-ai-sop/rules/evidence-discipline.md`：校验的两条路径不许共享同一段代码）。
   把 D11 的代价并进 D12 已认的债是合法的**账目合并**；
   但若共用到判定路径上，那就不是合并，是代价原样搬到另一根轴上。
3. **对 D11 的影响需要重算。** D12 定成各自布局之后，
   消息缓冲区可以只存在于某一套布局里（例如只在机械盘布局，因为 D11 的收益
   正比于随机/顺序代价比，D8 给的量级是机械盘约 1/100、SSD 约 1/10）。
   ⚠️ **这只是一个推论，未经三方论证，也未验证**——
   它不减轻 D11 那两条代价，只是把它们限制在一套布局内，而这正是 D14 被否掉的
   「消息独立成树」用过的同一种论证形态（缩小作用域 ≠ 消除代价），要小心。

### 它解锁了什么

D10 候选 A/B 的收益上界、D11 的前置 1、E1 的节点大小取值——
三者此前都卡在「目标介质未定」上，现在可以按每套布局各自取值。

## D13 验证路线 —— 半定（三类都做已定，分工与两处冲突未定）

**三类现成办法全做**：自写参照实现做差分对拍、有界穷举崩溃测试、crash refinement 形式验证。
调查见 [prior-art.md](prior-art.md) 7.4。

**并且不照抄**——针对本工程特有的四样（COW 每事务发新根、Merkle 自验证、
整卷 AEAD 的 nonce 唯一性、没有参照实现）自己设计验证手段。

### 三个互相独立的 oracle

| # | oracle | 判什么 | 独立性来自哪里 | 验不到什么 |
|---|---|---|---|---|
| O1 | 内存模型对拍（HashMap 理想文件系统） | POSIX 可见语义：内容、大小、目录结构 | 不碰盘、不解析磁盘格式 | 磁盘结构是否自洽；崩溃语义；**两份实现对同一条 POSIX 语义的共同误解** |
| O2 | 独立格式解析器 + checker | 磁盘字节是否满足 I-1~I-6 | **checker 不得调用被测 crate 的任何反序列化/遍历代码**，必须重新实现一份解析，直接读裸设备 | 只判结构自洽：一个块被覆盖成另一份**合法**内容，Merkle 链照样自洽、记账照样对 |
| O3 | 独立规约执行器 | 崩溃点截断后的每个磁盘状态是否落在规约允许的集合里 | **用另一种语言写**（不用 Rust），且不参照实现代码，只照 decisions.md 与 invariants.md 的文字重新推导 | 规约本身可能写错——**必须配阳性对照才有意义** |

**独立性要被验证，不许自称**：设计一个「三 oracle 合谋测试」——
拿一个精心构造的坏实现（例如 nonce 永远为 0）去过三关，
若三者全部放行，说明存在共同盲区，回头补 oracle。

### 自研的两样（现成工具没有）

**1. Merkle 根链差分（root-chain diff）—— COW + 每事务发新根独有的杠杆**

历史根在被回收前物理存在过，构成一条可回放的链。
对相邻两代根递归比较「子树指针 + 校验和/MAC」，**指针没变的地方直接跳过不下钻**，
复杂度只正比于两代之间实际改动的部分。

它能检出常规遍历式 checker 检不出的一类错误：**同步篡改后自洽的原地写**。
若某次写绕过了 COW、原地改了块内容**并同步更新了校验和**，
单点看这个块是自洽的（I-2.1 全绿）；
但根链差分会发现矛盾——**没走 COW 就不该有新分配，父指针理应没变，校验和却变了**。
这个矛盾只有对比两代根才看得出来。

⚠️ **必须配阴性对照**：正常 COW 提交后跑同一检查必须全绿，
否则它会把每次正常更新都当成篡改。

**2. 代际增量 scrub**

靠 I-1.2（块头 generation ≤ 当前 generation）与 D5 的 birth txg，
维护一个「上次 scrub 扫到的 generation 水位」，
只遍历 `birth generation > 水位` 的块——老子树的校验和链没变就必然还自洽。
**它让「每次提交都全量验证本次改动」在挂钟上可行，不必抽样。**

### 崩溃点重放要分三层，否则挂钟必炸

| 层 | 范围 | 抽样 | 触发 |
|---|---|---|---|
| 层 0 冒烟 | 固定种子的最小复现负载（写请求数两位数） | **不抽样，全量** | 任何触碰写路径的提交 |
| 层 1 常规 | 中等规模负载（写请求数上千） | 项目级固定种子 + **按崩溃点所在子阶段分桶抽样**（意图写入 / 分批推进 / 意图删除 / 纯数据写） | 每次提交 |
| 层 2 全量 | 层 1 负载 + 大规模负载 + 多设备档位交叉，N≥5 轮 | 不抽样 | 夜间 / 发布前 |

**分桶而不是均匀随机**：均匀随机可能把点全抽到同一个子阶段，
那正是 [experiments.md](experiments.md) E3 点名的自欺情形（崩溃点全落在批与批之间）。

**抽样之后敢说什么**：敢说「层 0 负载在全部崩溃点上通过」「层 1 抽到的这 N 个点通过」；
**不敢说**「崩溃一致性在所有可能的崩溃点上成立」，也不敢说「层 1 连续通过等价于层 2 会通过」。

**「只能夜间跑的还算不算准入判据」——算，但只能是异步准入判据。**
`singlefs-ai-sop/rules/show-me-test.md` 写的「最终判据是 QEMU 跑真实负载 + 崩溃注入」
本来就不是提交前跑得完的，本工程从一开始就隐含两段判决，现在写明：
**提交前 = 快速档全绿（必要条件）；合并前 = 夜间档全绿（准入条件）。**
夜间档红了，处置不是回退，是「之后所有提交都带着一个未结的红」直到修掉。

⚠️ **真代价不是跑得慢，是定位成本**：夜间档一天一次、一天进 N 个提交，
红了要在 N 个里二分，每次二分跑一天 → 修一个夜间档 bug 的挂钟 ≈ `log2(N) × 一天`。
由此得一条纪律：**夜间档必须优先保证「失败可复现」而不是「覆盖率最大」——
一个不可复现的夜间失败价值接近 0，甚至为负，它训练人忽略红灯。**

### 两处必须由人裁决的冲突

**冲突 1：`checker 即规范` 与 `校验的两条路径不许共享工具` 直接打架。**

`singlefs-ai-sop/rules/test-discipline.md` 写「这个格式是什么的权威答案是 checker 的源码」，
`invariants.md` 写「checker 是本文件的可执行形式」；
而 `singlefs-ai-sop/rules/evidence-discipline.md` 写「校验的两条路径不共享同一段代码、
同一次采样、同一个工具」。26 条不变量若既是 checker 源码又是形式验证的 spec，就成了单点。

**可行的折中，而且本工程已经付过这笔钱**：checker 做两个方向——
**遍历式**（从超级块走下去）与**扫描式**（全盘扫，靠「元数据块必须自描述」的块头重建），
两者对同一条不变量独立判断，共享的只有格式解析。I-3.1 已经是这个形态的一半。

**冲突 2：crash refinement 的 spec 与模型对拍的 model 是同一个东西的两种写法。**

合并成一份 → 省一半工作量，但**直接违反独立性要求**，规范写错时两条腿一起绿。
各写一份 → 名义独立，但通常是同一个人同一周写的。
缓解（只降低相关性、不消除）：让两份**在表述层面就不同**——
spec 写成「对镜像的状态谓词」，model 写成「op → 状态转移」，
不一致时至少能互相定位。

**同源性要被观测**：统计「spec 与 model 不一致」的事件数及每次判定哪一方错；
若累计 ≥ 5 次不一致而判定「spec 错」的次数为 0，说明两者实际同源，
独立性只是名义上的，应把两条腿合并、预算移给穷举。

| 决策 | 连锁点 |

| D4 Merkle | 根链差分把 Merkle 从「要付的代价」翻转成验证杠杆；但形式验证里哈希是 uninterpreted function，**碰撞抗性完全在验证范围之外，不许读成「验了 Merkle」** |
| D8 索引结构 | 日志结构节点、write buffer、key cache 三层都会绑架符号执行（循环上界、滞后窗口、缓存一致性），使「Yggdrasil 一分钟内」的口径在本工程不成立 |
| D9 加密 | AEAD 在 SMT 里不可解，只能建模成 uninterpreted function，**「nonce 重用泄漏明文」这个后果验不出来**，只剩「nonce 不重复」这条纯组合性质——而后者恰是这条腿最值钱的产出 |
| D11 消息缓冲区 | 若采用，checker 的 I-3.1 要解析消息语义，**冲突 1 会从「可折中」变成「无解」** |

### 拆成两半：可穷举的推导 + 要自己量的实验

**推导这一半不需要任何文献，而且它是可机检的**（`singlefs-ai-sop/rules/machine-first.md`：
「穷尽性是可机检的」）：

**推导 D-1：穷举所有能改变「对象 → 轨道」映射的入口。**
判据来自 `.claude/rules/fs-design.md` 硬要求 5——分支变量不许在操作中途改变。
要产出的是一张**穷举表**：每一个能改变该映射的系统调用 / 内部事件各一行，
每行写清：它改的是什么、改动是否原子、正在进行的操作怎么收场、以及**能不能禁掉它**。
已知至少有这些入口，但**这张表必须自己推完并证明穷尽，不许照抄**：
`linkat` / `rename` / `fsync` / 快照捕获 / 硬链接 / mmap 脏页回写 / 配额结算 / `truncate` / `fallocate`。

**推导 D-2：六样「少做」逐样推「能不能只看一个镜像判出来」。**
这是定义推导，不需要历史。判不出来 ⇒ 必须有盘上事实 ⇒ 落进 D12 已经接受的格式分支预算里，
而不是新开一笔债——**这一步是 D12 定案之后必须重算的核心**。

**验证这一半见 [experiments.md](experiments.md) E11。**

### 推导 D-3：day-1 多轨兼容的可判据（不依赖任何历史归纳）

**问题**：如果 day-1 就把多轨设计进格式（per-extent 轨道字段、混合态天生合法、
feature bit 预留够），那六样的账要重算成什么样？

**最强形态是「轨道只减承诺、不改编码」**：轨道字段只降低耐久性承诺，
绝不改变任何字节布局。可判定形式（若采纳，届时在 [invariants.md](invariants.md) 新开一条，编号按「只往上加」的规矩现取）：
**把任一指针的 track 字段抹成 0 之后，它必须仍能被单轨解析器逐字节解析，
且校验和 / MAC / nonce / birth txg / 反向索引语义一字不变。**

在这个形态下，inode 的轨道**不存**，是其全部 extent 轨道算出来的下确界——
于是混合态天生合法，「迁移」退化成翻两个位，与那次本来就要重写指针的事务合并，
**没有数据搬运、没有重新编码、没有重算 MAC**。

**重算结果**：六样里真正变便宜的只有 **deadlist 一样**（I-3.1 从标量等式变成
「按轨道分箱的向量等式 + 标量收缩」，判别力**净增**，能检出「总数对但归类错」这一整类）。
另外两样是「省 0 字节但否决权消失」（反向索引：等宽等语义则临时块照常进反向索引，
与 D1 的冲突消失）与「小幅变便宜」（恢复承诺可降为既有 keyspace 的新 key 变体）。
**其余三样（快照可见性、Merkle、nonce）净省为 0。**

⚠️ **使前三样成立的机制，恰恰是「让临时轨什么也不省」——这个设计用删掉收益的方式消掉了成本。**

**四条判据（全部是设计期常量，无一是操作期间会变的量）**：

| # | 判据 | 怎么判 |
|---|---|---|
| 1 | **轨道字段只减承诺、不改编码** | 抹成 0 后仍可被单轨解析器逐字节解析。写成不变量，checker 可判，且能证明会红（构造一个两轨不等宽的镜像） |
| 2 | **每一条被减掉的承诺，都能写成只读该指针自身字段的谓词** | 把谓词实现签名钉成 `fn(&Pointer) -> bool`，多一个入参即判红 |
| 3 | **轨道在对象创建时确定，此后永不改变** | 枚举全部能改变轨道的入口，集合必须为空 |
| 4 | **D12 与 D6 已定** | track 要与 nonce 载体、快照 ID、locality_id 抢**同一段排序权**；在它们定型前给 track 分配排序权，等于替它们做主 |

**判据 3 是可判定性的全部重量所在，也是它自洽的地方：**
一条「出生即定、此后不变」的耐久性轨道，就是不可撤销的声明。
**判据 3 自动把持久/临时轴判出局，而不是靠历史归纳。**

**这条判据不是空的——本工程已经有一条满足全部四条的 day-1 多轨：
D9 预留的「每个数据/元数据写的算法类型字段」。**
它只减承诺不改编码（老数据按各自字段解）、谓词只读该写自身、
**写下去那一刻就定死、此后永不改变**、且已随 D9 定案。
**它成立正是因为满足判据 3；而耐久性轴无法满足。**

**由此得到一条不对称结论**：day-1 多轨对**大/小轴**帮助显著
（翻转由操作自己引起，可以并进同一个事务），对**持久/临时轴**帮助为零（翻转来自操作范围之外）。
而大/小轴本决策**已经采纳**（有界内联 + 分配器提示）。

**day-1 买到的准确表述是：格式能在翻转中存活，操作不能。**
`linkat` 在 POSIX 下是 O(1)；一个带 1 TB 临时 extent 的对象被 `linkat` 挂进目录树，
三条出路各自的结局是：急切重标 = O(N) 元数据重写、**O(1) 承诺照样作废**；
惰性重标 = 引入「尚未重标」这个在途派生状态，**正是 D11 被否掉的那个东西换了个地方**；
意图日志重标 = `linkat` 变成发起一个无界操作，**崩溃落在返回之后、重标完成之前
⇒ 恢复丢弃一个已被成功 link 的文件的数据**。

⚠️ **最后这条的形状与 D14 参考里那条 btrfs 内核 commit 逐字相同
（`write()` 返回成功之后数据丢失）——从零设计、格式全新，走到了同一个坑。
因为病根不在 retrofit，在「承诺翻转来自操作范围之外」。**
这是用自己的推导得到的结论，不是照抄别家结局。

### 采纳的两层

| 层 | 做什么 | 为什么它不欠债 |
|---|---|---|
| **分配器提示** | 把小文件的块放到一起；把疑似短命的数据放进预期会整片释放的区域 | 不落盘、猜错只损失局部性、每次分配都可以重新判、**零格式位**。F2FS 的冷热分离就活在这一层：判据是 superblock 里一张文件名后缀表（`mkfs.f2fs -e/-E`），它只决定块进哪个 log，不改格式、不改校验、不改恢复语义 |
| **小文件内联进 inode** | 小到能塞进 inode 剩余空间的数据直接内联 | **迁移规模按构造有界**（≤ inode 剩余空间），「内联 → extent」是**一个有界事务**，不触发 D8 的意图日志，不产生混合态 inode，per-inode 一个位就够 |

### 不采纳格式级第二轨的依据

**参考一（待自推验证）：两条轴上都不存在「操作期间稳定的分支变量」。**

`.claude/rules/fs-design.md` 硬要求 5 要求分支变量在操作期间不变，
D8 已经列举过合格的输入：介质类型、受影响 key 是否连续、操作开始时的规模估计——
共同性质是「在操作外部，且操作本身不改变它」。

- **大/小轴**：`open(O_CREAT)` 时 size=0，**每个文件出生都是小文件**，判据在做决定的那一刻永远返回同一个答案；
  `truncate` 让阈值**双向可穿**；「大小」还是 `i_size` / 已分配块数 / extent 条数三个互相矛盾的候选
  （`ftruncate(fd, 1TB)` 后是「i_size 大、分配 0」，`PUNCH_HOLE` 后反向）。
- **持久/临时轴**：它比「中途改变」更糟——分支变量会被**操作范围之外的第三方异步翻转**。
  已枚举的入口：`linkat`（O_TMPFILE 挂进目录树）、`fsync`、**快照捕获**（一次操作把整个子卷内每个文件的分类同时翻转）、
  `rename` 到持久路径、硬链接把持久文件挂进临时目录、mmap 脏页在翻转后回写、配额。
  **每一个入口都是 POSIX 已经承诺为 O(1) 或原子的操作**，把轨道迁移挂上去等于把这些承诺作废。

**依据二：唯二不可撤销的声明，是靠禁掉翻转入口换来的，不是设计出了稳定的变量。**

| 声明 | 为什么不可撤销 | 代价 |
|---|---|---|
| `O_TMPFILE \| O_EXCL` | `man 2 open` 原文：「Specifying O_EXCL in conjunction with O_TMPFILE **prevents a temporary file from being linked into the filesystem**」 | 这个文件**永远不能有名字**，只能靠 fd 传递 |
| 独立子卷 / 挂载点 | 跨边界 `rename` 返回 `EXDEV`，内核替你拒绝翻转 | **不是 per-file 的**，而且它就是 tmpfs 已经是的东西 |

围起来之后，「临时文件透明地走快路径」这个最初的诉求已经不在了。
另外 `man 2 open` 明写 O_TMPFILE 的两个主要用途之一就是**变成永久文件**
（写好后用 `linkat` 原子地挂进文件系统）——**它表达的是「这个名字还不存在」，不是「这份数据是临时的」。**

**参考三（D12 定案后必须重算）：要少做的六样，零样落在纯行为分支里。**

判定标准是「这件事能不能只看一个镜像判出来」，判不出来就必须有盘上事实。

⚠️ **本表的判定基于「不为多轨预留格式字段」这个前提，该前提正在被重新审视**——
若 day-1 就把多轨设计进格式（per-extent 轨道字段、混合态 inode 天生合法、
feature bit 预留够），这张表要重算。重算的前置是格式冻结政策（见 D15）。

| 要少做的 | 判定（在「不预留」前提下） | 机制 |
|---|---|---|
| 快照可见性 | 格式 | 挂载时必须知道哪些对象不被快照捕获，这知识只能来自盘 |
| deadlist 记账 | 格式 | 释放块时判「进不进 deadlist」，判据必须来自块自己（D5 就是这么设计的）。若临时块单开一本账，I-3.1 就从**一条对照**退化成两条各自对账，**唯一那条独立对照消失**——与 D11 否掉「消息独立成树」是同一个论证 |
| Merkle 链 | 格式或白省 | 只有两种实现：指针宽度不同 = 两种指针格式 = 永久分支；宽度相同、字段标为无效 = **一个字节都没省**，只省 CPU |
| nonce | **绝对少不了** | I-6.1 的 checker 阶段 ② 要全盘扫描已分配区间、靠明文头识别「这是不是一个 singlefs 块」。一个不带标准明文头的临时块，会让阶段 ② **分辨不出它是不是本文件系统的块**——检查全绿而判别力为零 |
| 恢复承诺 | 格式 | 挂载时要知道哪些 inode 可以直接丢，而 `.claude/rules/fs-design.md` 明写「任何要事后扫一遍才能算出来的记账设计一律否决」⇒ 必须有一棵持久的临时对象树 ⇒ 新 keyspace ⇒ 进格式 |
| 反向索引 | 格式，且违反 D1 | 临时块不进反向索引 ⇒ balance / copygc **搬不动它** ⇒ 它是永久碎片源，缩容与移除设备会卡在它上面 |

**参考四（D12 定案后必须重算）：验证叉积 16 倍。**

已在册的配置维度：D8 范围重建/逐项修改（2）× D2 条带宽度（3）× D12 若定成两者都一等（2）× D9 加密开关（2）= **24**。
加双轨（迁移路径本身也是分支）：大/小 4 档 + 持久/临时 4 档 → **24 × 4 × 4 = 384，16 倍**。
⚠️ 这个比值是纯组合推算；具体挂钟依赖尚不存在的实现，无法量。
而 [checks-owed.md](checks-owed.md) 的 C8（拦门禁挂钟膨胀）状态是「零前置的纯欠工」——**现在没有任何东西在拦这个膨胀**。

**参考（不作依据）：历史上没有任何文件系统成功发布过格式级临时轨。**

⚠️ **这一条是「无证据」，不是「有反证」，因此列为参考而非依据。**
下表每一个案例都是**往既有格式上补**的：btrfs 的 nodatacow 是补的、
XFS realtime 的 reflink 与 rmap 是后来才加的、ZFS 的 `special_small_blocks`
是 2019 年加进 2005 年定的格式、ext4 的 `data=writeback` 继承自 ext3。
**它们承载的结论是「retrofit 很贵」，不是「从零设计也不行」。**

| 实现 | 原文与结局 |
|---|---|
| btrfs `chattr +C` | 跨阈值迁移的历史答案是**宣布为未定义**：`chattr(1)` 原文「If it is set on a file which already has data blocks, **it is undefined when the blocks assigned to the file will be fully stable**」 |
| btrfs `nodatacow` | 第二轨要付的是丢掉校验和：`man 5 btrfs` 原文「**Nodatacow implies nodatasum, and disables compression**」。且它被快照压倒——NOCOW 文件只要引用数 > 1，写它仍然 CoW；社区的规避办法是「放进单独子卷并且不对它做快照」 |
| btrfs NOCOW 的数据丢失 bug | 内核 commit「fix unexpected failure of nocow buffered writes after snapshotting when low on space」（backport 到 4.14 / 4.18 stable）：空间不足时 nocow 写**不预留空间**就返回成功，建快照强制此前的写回退到 COW，回退因无预留而 ENOSPC ⇒ **`write()` 返回成功之后数据丢失**。修法不是「处理翻转」，是新增 `snapshot_force_cow` 让已开始的写按旧轨走完、新的写提前失败——正是硬要求 5 的内容，用一个 stable backport 学回来 |
| ext4 `data=writeback` | `man 5 ext4` 原文：收益是「This is **rumoured** to be the highest-throughput option」，代价是「**can allow old data to appear in files after a crash**」。**内核手册无法把收益写成事实，却把代价写成事实**；且它是挂载全局的，ext4 二十年没能把 data 模式做成 per-file |
| XFS realtime subvolume | 格式级第二轨的三十年账单：**quota 从来不支持带 realtime volume 的文件系统**（即使一个 realtime 文件都没有）；reflink 与 rmap 直到 Linux 6.13 / 6.14（2025）才落到 realtime 设备。**它缺的恰好是 D1 反向索引与 D5/D6 快照，两条都是本工程 day-1 硬承诺** |
| ZFS `special_small_blocks` | 按大小分轨的现役实现，三个毛病：改阈值**不追溯**（盘上同时躺着按每一个历史阈值放置的数据且无法分辨）；special vdev 写满后**静默回落**（硬要求 4「走错分支是性能悬崖，而悬崖不报错」的现役实例）；判据是**压缩后**大小，与 `recordsize` 耦合 |
| Windows `FILE_ATTRIBUTE_TEMPORARY` | **唯一一个主流的 per-file 临时声明**，而它整个关在页缓存层（「a hint to the **cache manager**」），**一个字节的盘上格式都没动**，并要求应用配上不可撤销的 `FILE_FLAG_DELETE_ON_CLOSE` |

口径：man page 为本机 2026-08-26 现查并逐字核对；其余为公开记录，**未在本工程验证**。

1. **分配器提示的判据写成什么。** F2FS 用 superblock 里的后缀表，本工程用什么？
   判据必须显式、可计算、写下来（硬要求 1），且要能被测试强制进入（硬要求 2）。
2. **内联阈值取多少**，以及内联 → extent 那个有界事务的崩溃语义。
3. **「持久/临时」是不是 D11 缺的那个判据** —— 一度被提出，**现判为不成立**：
   该判据会被 `linkat` / `fsync` / 快照 / `rename` 从操作范围之外异步翻转（依据一）。
   D11 仍然缺一个合格的分支变量。

## D15 格式冻结政策 —— 半定（机制已定，清单待逐项确认）

回答两个问题：**什么时候允许说「format v1 frozen」**，以及**冻结之后新增东西走什么通道**。
它是 D11 / D12 / D14 的共同前置——「格式分支永久」这条成本的**当期值为零、冻结后为无穷**，
所以那几条决策的真实代价由本决策定义。

### 冻结是一次受门禁仲裁的提交，不是一句话

**动作**：冻结 = 向仓库提交 `.claude/kb/format-frozen/<组件>.toml`
（内容含 `version`、`frozen_at_commit`、`spec_hash`）。

**谁判**：不是人「觉得可以了」就生效。门禁一旦发现本次 diff 触碰了这个目录，
自动切换到一套更严的前置检查，全部满足才允许该 commit 通过。
**人只决定「现在要不要发起冻结」，机器决定「这次冻结请求成不成立」**——
与 `singlefs-ai-sop/rules/show-me-test.md`「不按来源区分，只按证据区分」同构。

该阶段平时不跑（形态同 `GATE_QEMU`），因此现在挂上去也不拖慢日常提交。
**它注定常年触发 0 次，这不是缺陷，是正确状态**——与门禁显式列出未实现阶段是同一种诚实。

### 冻结分四层，有严格依赖顺序

```
第 1 层：超级块 + 块头（自身地址 / generation / 树 ID / fsid / magic）
    ↓
第 2 层：指针字段布局（D4 校验和 + D9 的 MAC / nonce / 密文校验和）
    ↓
第 3 层：各 keyspace 的 key 编码（D8 的 locality_id / inode / offset）
    ↓
第 4 层：索引节点内部布局（节点大小规则、bset 形态、D11 的消息缓冲区）
```

依赖方向的理由：第 1 层是「元数据块必须自描述」的物理前提，后面所有层都建在它之上；
第 2 层被 D9「事后加不进去」钉死，必须先于依赖它的树结构；
第 3 层的 key 编码定了，节点内部怎么组织这些 key 才有讨论基础。

⚠️ **分批冻结的风险必须显式接受**：早冻的层若漏留字段，后面只能走 incompat 打补丁，
等价于提前烧掉一次本该整体设计时留的余量。
止损规则只有一条：**第 1、2 层冻结前必须已包含 D9 全部四项预留**，
因为它们恰好是「已知迟早要用」的字段，不能指望第 3、4 层再补。

### 冻结之后失去哪些自由

| 软格式期的自由 | 冻结后变成什么 |
|---|---|
| 结构「拆了重做」 | 已冻结字段的宽度 / 存在性 / 含义不能再改；只能新增，退役字段走「保留读支持、停止写」 |
| 发现设计错了直接改正文不留兼容 | 决策记录层面仍可推翻，但**盘上字节层面从 0 兼容成本变成非零** |
| mkfs 自动选取规则可随时换算法 | 已冻结组件的选取规则本身也被钉死；换算法会让新旧镜像默认值不同，必须体现在新格式版本号下 |
| 实验结果不理想就直接改格式重定 | 只能通过新 feature bit 引入新策略，并保留旧值的解释能力 |
| checker 可以跟着格式自由改 | **对已冻结部分，checker 的判断变成事实上的兼容性契约**——悄悄改 checker 对冻结字段的解释，和悄悄改格式一样危险 |

### 冻结后的改动判定表

| 改动类型 | 旧读者会怎样 | 哪档 | bump | 理由 |
|---|---|---|---|---|
| 新增字段在预留区 / TLV 尾部 | 忽略，继续正常工作 | compat | 否 | 没有语义依赖的纯加法，「忽略陌生字段」这条安全网够用 |
| 新增字段，缺了会让旧读者对**另一个已有字段**算错 | **算错，可能损坏数据** | incompat | 是 | 语义一旦耦合，安全网失效 |
| 扩大已有字段宽度 | 按旧宽度解析，越界读 / 错位 | incompat | 是 | 宽度是布局的一部分，旧代码的偏移计算全错 |
| 改变已有字段含义 | 按旧含义解读，**不报错**地产生错误行为 | incompat，且**弃用旧位置不复用** | 是 | 位置复用会让新旧读者无法区分，是最危险的一类 |
| 新增记录类型（新 key 类型） | 只读遍历可能误判；整理 / 写可能误删看不懂的记录 | compat_ro | 是 | **「只读安全」与「可写安全」是两条独立保证**，必须分开判 |
| 新增一棵 keyspace | 若超级块的树表 day-1 就是开放列表：只是看不到新树；若树数量硬编码：读不出树表 | 留了开放树表 → compat；没留 → incompat | 是 | **「树表是否可扩展」必须在冻结时决定**，不能等要加树才发现没留 |
| 改变排序规则 | 二分查找 / 遍历结果错，**不报错** | incompat | 是 | 排序规则是索引本体，日志结构节点的重排直接依赖它不变 |
| 改变校验和 / MAC 算法 | D9 的算法类型字段已留 → 遇到不认识的类型只能显式失败 | 已留 → compat_ro；未留 → incompat | 是 | D9 day-1 预留字段第 4 项正是为这类改动准备的通道 |
| 退役一个字段 | 不受影响，旧读者继续按旧方式解释 | compat，且**永久保留解析代码** | 否 | 落过盘的字段，只要还有一份旧镜像存在就必须一直能被解释 |

### feature bit 补成可实现的形态

- **位数**：三个 bitmap 各 **256 位**（`u64[4]`），存超级块。
  位比字段宽度便宜得多（3×32 字节对超级块可忽略），**预留要往宽了留**。
- **记账**：新建 `.claude/kb/feature-bits.md`，列
  `位号 | 类别 | 名称 | 引入版本 | 引入 commit | 状态 | 语义一句话`。
- **分配权是「谁先合并谁先占」，不是审批制**。门禁强制：位号严格递增、不许跳号占位、
  不许有代码引用了表里不存在的位号——机械仲裁。
- **位一旦用过不许回收。** 理由比 `invariants.md` 编号不回收**更硬**：
  编号是检索键，回收误导的是「读文档的人或模型」；
  **feature bit 是磁盘上真实存在过的物理位**。回收后重新分配给新特性，
  一个旧镜像挂到新代码上，这一位会被误读成「新特性 X 已启用」——
  **文件系统会真的做错事**（例如把不存在的加密特征当存在，去找不存在的密钥）。
  退役的位标为「含义永久锁定为退役前最后一次使用的语义」，不许赋予新特性。

### 两条会红的检查（已记进 [checks-owed.md](checks-owed.md)）

1. **格式冻结契约**：每个已冻结组件记 `spec_hash`；门禁重算并比对，
   不同则要求本次 diff **同时**满足「`feature-bits.md` 有新增行或 `version` 被显式改动」
   与「`decisions.md` 对应条目在同一 commit 里被改动」。缺一判红。
2. **向后兼容回归（黄金镜像）**：每次某组件版本变化时用**当时的代码**生成一份镜像并归档，
   门禁用**当前代码**去读全部历史镜像、跑 checker、比对期望内容摘要。
   ⚠️ 镜像本体**不进 git**（`command-safety.md`：测试镜像不许放仓库内），
   仓库只提交清单 `.claude/kb/golden-images.toml`；镜像放
   `${SINGLEFS_GOLDEN_DIR:-$HOME/.cache/singlefs-golden}`。
   清单**只增不删**——删掉某版本的回归等于悄悄放弃对它的兼容承诺，必须走决策记录。

### 未定

## D16 发布语义 —— 已定：checkpoint

**攒够一批脏节点（或到时间）再发布一次根，不是每个事务发一次。**

依据（2026-08-26 用户定案）：它与 D5 已定的 ZFS birth txg 模型天然相容——
**ZFS 的 txg 本身就是 checkpoint**（`zfs_txg_timeout` 默认 5 秒，或攒够一定脏数据量），
一个 txg 批量大量操作、txg 结束才更新一次 uberblock。
采纳 checkpoint 之后 birth txg 的号粒度问题**自动消失**：一个 txg 一个号，
deadlist 的比较粒度就是 checkpoint 粒度，不必重算。

**连带定死的三条**（不写死就会退化成「为某个路径开第二套事务机制」）：

1. **没有任何操作可以绕过 journal 直接发根。** 所有结构、所有操作先进同一个 journal、
   共用同一个 checkpoint 节奏。fsync 的效果是「提前触发一次发布」，
   **不是另开一条日志格式、另一套恢复逻辑**。
2. **D8「中间状态必须每一个都是合法的文件系统状态」改写为**：
   「**根 + journal 任意前缀，replay 之后合法**」。
3. **[decisions.md](decisions.md) D13 的 O2（独立格式解析器）必须自己实现一遍 journal replay。**
   那是第二次实现 replay，而 replay 正是崩溃语义最容易出**共同误解**的地方——
   D13 的「三 oracle 合谋测试」要防的就是这个。**这是本决策最贵的一笔。**

### 这条定案改变了什么

**它同时钉死了 [experiments.md](experiments.md) E7 的对照组。**
checkpoint 与 D11 的消息缓冲区买的是同一样东西，差别只在**摊销窗口住在哪**：
checkpoint 的窗口住**内存**、不进格式；消息缓冲的窗口住**盘**、必须进格式。
⇒ **D11 的边际收益 = 「跨 checkpoint 的摊销」减去「checkpoint 内摊销」**，
而 BetrFS 那组数字里这两块从没被拆开过（它同时有 4 MiB 节点的消息缓冲**和** 5 秒 checkpoint）。
**E7 的对照组必须是「有 checkpoint、无消息缓冲」。**

**对 C 类问题（分批大删除的元数据写放大）**：同一 checkpoint 窗口内的 K 批只走约一次
到根的路径，各批只留一条 journal 记录（小、顺序写），写放大从 `K × M × H` 降为
`checkpoint 数 × M × H`。

### 背景：那条被共同压着的路径



**一次事务提交就发布一个新根，还是攒够一批脏节点再发布一次根（checkpoint）？**

**本工程从未决定过这件事**（2026-08-26 逐文件核实）：
`litmus/commit-publish.litmus` 只钉一次发布事件**内部**的顺序
（写块内容 → `smp_wmb` → 写 generation），对发布频率一字未提；
`decisions.md` / [CLAUDE.md](../../CLAUDE.md) / `.claude/rules/fs-design.md` 全文均无此表述。

### 为什么它是枢纽

有一条路径被三条决策共同压着——**引用改写路径**：
`目标块 → 父节点 → … → 根 → 超级块`。
任一块的内容改了或物理位置变了，都必须沿这条路径逐级重写到发布新根，
长度 H（树高），每级 = 一次新分配 + 一次凭据重算 + 一次加密写。

| 来源 | 它往这条路径上加了什么 |
|---|---|
| COW（项目前提，不是某条决策） | 块不原地改 → 新块新地址 → 父指针的**地址字段**必改。**单这一条就足以产生「到根」** |
| D4 校验和内联进父指针 | 父指针除地址外还是子块的完整性凭据。**在 COW 下它对写放大的边际贡献是零**（地址反正要改） |
| D9 整卷 AEAD | 那个凭据在加密开启时是 MAC，且路径上每级节点的载荷是密文 → **这条路径需要密钥** |
| D3 全局分配器 + 常驻整理 | 制造「必须主动走这条路径」的需求（搬块） |
| D8 无界操作分批 + 意图 | 制造「反复走这条路径」的需求（K 批） |

- **发布语义决定「走几次」**：每事务发根 → K 批走 K 次；
  checkpoint → 同一窗口内的 K 批只走约一次，各批只留一条 journal 记录（小、顺序写）。
- **它同时钉死 D11 的对照组**：checkpoint 与消息缓冲区买的是同一样东西，差别只在**摊销窗口住在哪**——
  checkpoint 的窗口住在**内存**、不进格式；消息缓冲的窗口住在**盘**、必须进格式。
  **所以 D11 的边际收益 = 「跨 checkpoint 的摊销」减去「checkpoint 内摊销」**，
  而 BetrFS 那组数字里这两块从没被拆开过（它同时有 4 MiB 节点的消息缓冲**和** 5 秒 checkpoint）。
  ⇒ [experiments.md](experiments.md) E7 的对照组必须是「**有 checkpoint、无消息缓冲**」。

### 采用 checkpoint 会撞什么

1. **`.claude/rules/fs-design.md`「不许为某个路径开第二套事务机制」——不撞，但判据要当场写死。**
   判据是：**journal 是所有提交的必经之路，还是某些路径的旁路。**
   所有结构、所有操作先进同一个 journal、共用同一个 checkpoint 节奏 → 一套机制，持久化分两级，合规。
   只有 fsync（或只有元数据、只有小写）走 journal、别的直接发根 → **那就是第二套**，
   正是该规则点名的「为 fsync 单开一套日志树」。
   **引入 checkpoint 必须同时写死：没有任何操作可以绕过 journal 直接发根。**
2. **D8「中间状态必须每一个都是合法的文件系统状态」语义要改写，代价落在 checker 上。**
   这条不再能读成「盘上可见的每个根都合法」，只能读成「**根 + journal 任意前缀，replay 后合法**」。
   ⇒ **D13 的 O2（独立格式解析器，不许调用被测 crate 任何代码）必须自己实现一遍 journal replay**。
   那是第二次实现 replay，而 replay 正是崩溃语义最容易出**共同误解**的地方——
   D13「三 oracle 合谋测试」要防的就是这个。**这是这条出路最贵的一笔。**
3. **D13 的「Merkle 根链差分」粒度变粗**：一代根里塞了 K 个事务的改动，
   定位精度从「哪个事务」降到「哪个 checkpoint」，而 D13 已写明夜间档的真代价是定位成本。

### 反方向：checkpoint 其实是 D5 已经隐含接受的

D5 已定采纳 ZFS 的 birth txg。**而 ZFS 的 txg 本身就是 checkpoint**——
`zfs_txg_timeout` 默认 5 秒（或攒够一定脏数据量），一个 txg 批量大量操作，txg 结束才更新一次 uberblock。

**推论：「每事务发布一次新根」不只是从未被决定过，它与 D5 已定的模型之间还有张力。**
若真采用每事务发根，就要回答「birth txg 里的 txg 到底是什么」——
每事务一个号的话，deadlist 的比较粒度与号空间消耗都要重算。

### 净代价分布

**格式侧几乎为零**（journal 本来就要有），**验证侧一大笔**（上面第 2、3 条）。

### 未定

1. **checkpoint 的触发判据**：时间、脏数据量、还是两者取先到。
   判据必须显式可计算（`.claude/rules/fs-design.md` 硬要求 1），
   且**不许是操作期间会变的量做分支变量**。
2. **journal 的格式**——它现在是格式的一部分了，要进 D15 的冻结分层
   （它属于第 1 层还是单独一层）。
3. **O2 那第二份 replay 实现的成本**，以及它与 D13「三 oracle 合谋测试」怎么配合。

## 待议：记账与反向索引的隔离纪律

曾提议作为硬纪律：**反向索引只服务 GC / balance / scrub，
任何记账、配额、空间统计一律不许依赖它。**

理由是 btrfs qgroup 慢的直接原因就是记账要走反向索引。

**状态：标为再考虑**（2026-08-25，用户要求）。未纳入 CLAUDE.md 硬规范。
