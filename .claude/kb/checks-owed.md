# 欠的检查清单

**本文件放「已经知道要拦什么、但现在还拦不了」的检查。**

与 [invariants.md](invariants.md) 的分界：不变量是**对着一个镜像**可判定的性质，
checker 是它的可执行形式；本文件放的是**代码路径的要求**——
它们对着镜像判不出来，只能由门禁在跑的时候拦。

**写进来的门槛**：说得出「拦什么」「怎么拦会红」「现在缺什么前置」。
三样缺一样就是还没想清楚，先别写
（`singlefs-ai-sop/rules/sop-first.md`：写不出下一步就别加那条检查）。

| # | 要拦什么 | 怎么拦（会红的形态） | 前置 | 出处 |
|---|---|---|---|---|
| C1 | 把「续做未完成的意图」做成可选的修复通道，而不是每次恢复都跑的常规路径 | 崩溃点重放里，任一含未完成意图的镜像正常挂载后没跑续做即判红；恢复路径里不许存在「跳过续做」的分支 | 事务层、意图日志、崩溃点重放 harness | [decisions.md](decisions.md) D8 规则 2 |
| C2 | 无界操作被做成单个事务 | 对 truncate 大文件 / 删大目录量一遍「单个事务的写入量 vs 对象规模」，斜率不为 0 判红 | 事务层、块层写记录 | [decisions.md](decisions.md) D8 硬要求 |
| C3 | 读重试次数没有小的硬上限 | 加密开启且用截断 MAC 时，读路径的重试上限必须是编译期常量且不超过约定值；取不到该常量或超限判红 | 加密实现、读路径 | [decisions.md](decisions.md) D9 硬要求 3 |
| C5 | 形式验证的 `Z3 timeout` 被当成通过 | 门禁的 crash refinement 阶段必须有**三种**结果（证明 / 反例 / timeout），timeout 一律判红。现在 `gate.sh` 的 `record` 只有 PASS/FAIL 两态 | crash refinement 阶段存在 | 读 `singlefs-ai-sop/scripts/gate.sh` 确认只有两态；`show-me-test.md`「门禁不许假装通过」 |
| C6 | 块层重排 / FLUSH / FUA 的语义假设本身写错 | 在 QEMU 里用真实 virtio-blk + 写缓存策略跑，**故意去掉一次 FUA**，崩溃测试必须变红；不红说明重排模型没判别力 | QEMU 负载、崩溃点重放 | 三类验证路线共享这份假设，共享的东西没有第二条路径能查 |
| C7 | 「返回正确但过期的块」这一类错误没有任何检查 | 需要一个**会返回该地址历史版本**的设备模型（不是随机损坏），在它上面 D4 的 Merkle 必须报错 | 设备模型（现成工具没有，必须自造）、checker | D4 正文把「能检测读到正确但过期的块」列为 Merkle 的首要收益，而目前无手段验证它 |
| C8 | **一次改动的门禁范围判不出来，于是要么全跑（挂钟炸）要么少跑（有布局没被验）** | 门禁按 diff 计算**受影响的布局集合**并打印：diff 只碰某一条布局的专属路径 ⇒ 只跑那一条；碰到共享代码（事务层、`CommitStep`、格式常量、checker 框架）⇒ **强制全跑**。取不到这个集合、或集合为空而 diff 非空，即判红。故障注入自证：造一个只改共享枚举的 diff，门禁必须判为全跑；造一个只改单布局的 diff，必须判为只跑那一条 | 布局清单文件（同 C14）、布局专属路径与共享路径的目录约定、事务层存在 | **判据从「总时长」改成「范围可判定」（2026-08-28 用户定案）**：单次改动只动一条分支时代价是 O(1)，语料总量大不构成成本——人只是异步等结果，等的时候在做别的事。⚠️ 但「只动了一条」是**需要被证明的断言，不是事实**：btrfs 的 `btrfs_is_zoned` 散到 93 处，正是一次次「我只是加个 zoned 支持」累积出来的，每一次都以为自己只动了一条。⇒ **让 O(1) 成立的东西是这条检查，不是跑得快。** 与 C19 成对：C19 拦渗透，本条拦「渗透了但门禁没扩范围」 |
| C20 | 罕见布局的整条验证链长期没人跑过，静默腐坏 | 定期全量扫（不挂在提交上）：每套布局的 checker + 崩溃点重放 + 黄金镜像至少每 N 天被完整跑过一次，最久未跑的那套超期即判红。**必须记录每套布局的「上次完整跑过」时间戳并纳入门禁读数** | 每套布局的 checker、崩溃点重放 harness、布局清单文件 | C8 改判据之后打开的缺口：**按 diff 决定范围 ⇒ 没人改的布局就永远不被跑**。而 `.claude/rules/fs-design.md` 已定「罕见分支会腐坏：千分之一才走到的分支，它的 bug 只在生产里出现」。异步等待解除的是人的注意力成本，**没有解除「从来没跑过」**。这条不需要人守着，定时跑即可 |
| C13 | 某套布局的 checker 判定逻辑失效（跑了、全绿，但已经不做事） | 该布局被跑到的**同一轮**里，额外对一份「已知坏的镜像」跑它自己的 checker，**不报错即判红**。已知坏镜像随格式版本一起归档（同 C10 的黄金镜像机制） | 层 1 harness、每套布局的 checker | 覆盖记录只证明「被执行」，完全不证明「有判别力」；而判定逻辑失效的 checker **跑得更快**，在按耗时填切片的调度下反而更容易被选中 |
| C14 | 某套布局的格式变了、它的 checker 判定路径没跟 | 该布局的 `spec_hash` 变化时，同一次 diff 里该布局的 checker 判定路径必须也被改动，否则判红。形态同 C9，但键是「布局」而不是「组件」 | 一份布局清单文件（**不需要一行 Rust，现在就能做**） | 它抓的正是 C13 那类腐坏最常见的成因，而且是唯一现在就能落地的一条 |
| C12 | 记账的「增量语义」实现被 checker 与运行时共用，使 I-3.1 抓不到「加减语义本身写错」 | 门禁做**符号级**检查：checker 侧重建记账所调用的函数集合，与运行时提交路径所调用的函数集合，**交集必须为空**（格式解析、常量除外）。取不到调用图、或交集非空即判红。另配一条故障注入自证：把运行时某条记账分支的符号取反，I-3.1 必须变红——不红说明两侧同源 | 事务层、记账实现、checker | 已核实 bcachefs 在这一格上被自己绊倒：`disk_accounting.h:208` 的 `this_cpu_add(e->v[gc][i], a.v->d[i])` 是运行时与 GC 重建**共用的同一行**，只差 `gc` 下标；其 checker 因此只能抓「增量应用过程出偏差」，抓不到「语义写错」。⚠️ **第三方管道存在时这条收紧**（[decisions.md](decisions.md) D17 债表第 5 项）：checker 不许链接**任何**管道的运行时记账/校验代码——对第三方比对内部更要紧，因为这里没有信任。⚠️ **「增量形态至少还抓得到应用过程偏差」这一条经 E14 实测不成立**：增量 Δ 形态下「下刷时丢一条消息」「同一条消息应用两次」两类的 I-3.1 也是 0/5，见 [experiments.md](experiments.md) E14 |
| C15 | write buffer 里混进了增量 Δ 形态的条目，使 I-3.1 对那一棵树判别力归零而门禁全绿 | 缓冲条目类型在 Rust 侧强制成幂等形态：条目 value 只有「完整值」和「墓碑」两个构造子，**没有承载 Δ 的构造子**，写不出增量条目（machine-first「用类型让非法状态无法表示」）。另配故障注入自证：临时加一个 Δ 构造子并注入符号取反，I-3.1 必须变红 | write buffer 实现、记账实现、checker | 依据是实测：[experiments.md](experiments.md) E14 量到增量 Δ 形态下四类语义 bug 的 I-3.1 抓到率 0/4、盲区 4/4，幂等完整值形态 3/3、盲区 0。⚠️ **这条检查落不了地，除非先解决「记账怎么表达成幂等完整值」**——那是 decisions.md D8 的未答项，也是本条的真前置 |
| C16 | 一条管道声明了自己的失败模型例外（「我这儿不保证块原子」），核心层没有为它合成，于是那一类撕裂从来没被任何崩溃测试覆盖过 | 契约里**没有**「后端声明能力」这个入口——核心层规定唯一的失败模型，管道无处声明例外。门禁形态：故障注入自证，往被测管道注入一个核心层声明的失败模型**允许**的故障（例如按声明宽度撕裂一个块），崩溃测试必须变红；不红说明合成没做或没生效 | 崩溃点重放 harness、至少两条管道、失败模型这根轴先定下来（[decisions.md](decisions.md) D17 未定项 1）。⚠️ **撕裂注入不能靠 dm-flakey**（2026-08-28 现查 `Documentation/admin-guide/device-mapper/dm-flakey.rst`）：它的全部能力是 `error_reads` / `drop_writes` / `error_writes` / `corrupt_bio_byte <第N字节>` / `random_{read,write}_corrupt`——**丢整个 bio 或改一个字节，没有「前半落盘后半没落」**。撕裂只能在崩溃点重放 harness 里造（截断一条记录下来的写请求） | 依据是现役对照组（2026-08-27 现查 Linux 6.17）：允许后端返回 `-EOPNOTSUPP` 的 `REQ_HARDBARRIER` 在 2.6.37 被砍，换成不许后端拒绝、块层自己合成的 `REQ_PREFLUSH`/`REQ_FUA`，至今 15 年未变。⚠️ 本仓对「失败原子性宽度 / 撕裂 / 重排序」目前零覆盖，C6 问的是本工程的假设对不对，不是管道的失败模型是什么 |
| C17 | 设备级几何量（`zone_size`、擦除块对齐）被当成文件系统级单值参数，异构设备池上算出「看起来合法、但不在该设备写指针位置」的地址，错误到提交路径很晚才暴露 | 挂载时逐设备读回各自声明的几何量，与条带宽度做整除性/一致性校验，**不满足就拒绝挂载**（把「用错了」变成「挂不上」）。故障注入自证：造一个各设备 zone 大小不一致的池，挂载必须失败；不失败说明校验没生效 | 多设备支持、zoned 布局、mkfs 的设备描述符结构。⚠️ **不再需要真硬件**：[experiments.md](experiments.md) E15 已证明 QEMU 能造出来宾确实能分辨的异构几何（含阴性对照），复跑 `research/scripts/vm-geom.sh` | 依据（2026-08-27 现查 Linux 6.17）：`zone_sectors` 挂在 `disk->queue->limits`，是**设备级**量；btrfs 撞到同一堵墙，`fs/btrfs/zoned.c:711` 检出各设备 zone 大小不一致后 `return -EINVAL` 拒绝挂载。⚠️ 失败模式不对称：擦除块对齐设错只是变慢（按 D12 判据不算数），条带宽度 × `zone_size` 不整除才是本条要拦的。本条的前置是 [decisions.md](decisions.md) D12 未定项 3 |
| C18 | 块里带了一个「更新周期与内容变化解耦」的字段，于是某个本该只读的维护操作（scrub / 统计）静默变成写操作，每跑一遍造一批新块并把旧块灌进 deadlist | 门禁形态：跑一轮全盘 scrub 前后比对**设备写次数与 deadlist 条目数**，两者都必须**逐位不变**；任一增长即判红。自证会红：临时给块头加一个「上次校验时间」并在 scrub 时写回，该检查必须变红 | 事务层、deadlist、scrub、块层写记录 | 依据：[decisions.md](decisions.md) D18 判据 1。这类字段的危害不是「贵一点」而是方向相反——维护操作反过来制造它本该消灭的碎片与死块。⚠️ 光靠 review 拦不住：一个字段是不是「解耦」要看它的**更新时机**，而那在格式定义里看不出来 |
| C19 | 介质判定渗进事务层或 ENOSPC 准入路径，使「事务层不许多样」这条腰线在代码里失效 | 门禁做符号级检查：事务层与准入路径所在的模块，其调用图/符号引用里**不许出现任何介质或布局判定符号**（布局标识、`is_zoned` 一类），出现即判红。故障注入自证：临时在提交路径插一条介质判定，该检查必须变红 | 事务层存在、布局标识的符号命名约定定下来 | 现役演示（`.claude/rules/fs-design.md` 已记，2026-08-27 现查 Linux 6.17）：btrfs 的 `btrfs_is_zoned` 散在 20 个文件 **93 处**，其中 **5 处在 `tree-log.c`**（事务日志）、**6 处在 `space-info.c`**（ENOSPC 准入）。⚠️ **[decisions.md](decisions.md) D12 把布局数改成开放的 N 之后，这条风险线性增长**，而 D12 「无脑接入新介质」这个收益**恰恰依赖腰线不被渗透**——腰线一破，接入第 N+1 条的代价从 O(1) 变成 O(N)（要重跑所有已有布局的崩溃点重放） |
