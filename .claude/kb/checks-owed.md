# 欠的检查清单

**本文件放「已经知道要拦什么、但现在还拦不了」的检查。**

与 [invariants.md](invariants.md) 的分界：不变量是**对着一个镜像**可判定的性质，
checker 是它的可执行形式；本文件放的是**代码路径的要求**——
它们对着镜像判不出来，只能由门禁在跑的时候拦。

**写进来的门槛**：说得出「拦什么」「怎么拦会红」「现在缺什么前置」。
三样缺一样就是还没想清楚，先别写
（`singlefs-ai-sop/rules/sop-first.md`：写不出下一步就别加那条检查）。

| # | 要拦什么 | 怎么拦（会红的形态） | 前置 | 出处 |
|---|---|---|---|---|
| C1 | 把「续做未完成的意图」做成可选的修复通道，而不是每次恢复都跑的常规路径 | 崩溃点重放里，任一含未完成意图的镜像正常挂载后没跑续做即判红；恢复路径里不许存在「跳过续做」的分支 | 事务层、意图日志、崩溃点重放 harness | [decisions.md](decisions.md) D8 规则 2 |
| C2 | 无界操作被做成单个事务 | 对 truncate 大文件 / 删大目录量一遍「单个事务的写入量 vs 对象规模」，斜率不为 0 判红 | 事务层、块层写记录 | [decisions.md](decisions.md) D8 硬要求 |
| C3 | 读重试次数没有小的硬上限 | 加密开启且用截断 MAC 时，读路径的重试上限必须是编译期常量且不超过约定值；取不到该常量或超限判红 | 加密实现、读路径 | [decisions.md](decisions.md) D9 硬要求 3 |
| C5 | 形式验证的 `Z3 timeout` 被当成通过 | 门禁的 crash refinement 阶段必须有**三种**结果（证明 / 反例 / timeout），timeout 一律判红。现在 `gate.sh` 的 `record` 只有 PASS/FAIL 两态 | crash refinement 阶段存在 | 读 `singlefs-ai-sop/scripts/gate.sh` 确认只有两态；`show-me-test.md`「门禁不许假装通过」 |
| C6 | 块层重排 / FLUSH / FUA 的语义假设本身写错 | 在 QEMU 里用真实 virtio-blk + 写缓存策略跑，**故意去掉一次 FUA**，崩溃测试必须变红；不红说明重排模型没判别力 | QEMU 负载、崩溃点重放 | 三类验证路线共享这份假设，共享的东西没有第二条路径能查 |
| C7 | 「返回正确但过期的块」这一类错误没有任何检查 | 需要一个**会返回该地址历史版本**的设备模型（不是随机损坏），在它上面 D4 的 Merkle 必须报错 | 设备模型（现成工具没有，必须自造）、checker | D4 正文把「能检测读到正确但过期的块」列为 Merkle 的首要收益，而目前无手段验证它 |
| C8 | 门禁挂钟悄悄膨胀到没人愿意本地跑 | `gate.sh` 打印每阶段耗时并把总时长做成可回归的数，中位数超阈值判红；同时统计带跳过标记的提交比例 | 无（纯欠工）。⚠️ **但它量不出层 1 的每格耗时**——今天的 gate.sh 里没有「崩溃点重放」这个阶段，见 [decisions.md](decisions.md) D13 | `.claude/rules/fs-design.md`：门禁运行时长本身是设计约束，而「本地先跑一遍」是整套设计的支点 |
| C13 | 某套布局的 checker 判定逻辑失效（跑了、全绿，但已经不做事） | 该布局被跑到的**同一轮**里，额外对一份「已知坏的镜像」跑它自己的 checker，**不报错即判红**。已知坏镜像随格式版本一起归档（同 C10 的黄金镜像机制） | 层 1 harness、每套布局的 checker | 覆盖记录只证明「被执行」，完全不证明「有判别力」；而判定逻辑失效的 checker **跑得更快**，在按耗时填切片的调度下反而更容易被选中 |
| C14 | 某套布局的格式变了、它的 checker 判定路径没跟 | 该布局的 `spec_hash` 变化时，同一次 diff 里该布局的 checker 判定路径必须也被改动，否则判红。形态同 C9，但键是「布局」而不是「组件」 | 一份布局清单文件（**不需要一行 Rust，现在就能做**） | 它抓的正是 C13 那类腐坏最常见的成因，而且是唯一现在就能落地的一条 |
| C12 | 记账的「增量语义」实现被 checker 与运行时共用，使 I-3.1 抓不到「加减语义本身写错」 | 门禁做**符号级**检查：checker 侧重建记账所调用的函数集合，与运行时提交路径所调用的函数集合，**交集必须为空**（格式解析、常量除外）。取不到调用图、或交集非空即判红。另配一条故障注入自证：把运行时某条记账分支的符号取反，I-3.1 必须变红——不红说明两侧同源 | 事务层、记账实现、checker | 已核实 bcachefs 在这一格上被自己绊倒：`disk_accounting.h:208` 的 `this_cpu_add(e->v[gc][i], a.v->d[i])` 是运行时与 GC 重建**共用的同一行**，只差 `gc` 下标；其 checker 因此只能抓「增量应用过程出偏差」，抓不到「语义写错」 |
| C9 | 冻结后偷偷改了格式却没走演进通道 | 每个已冻结组件记 `spec_hash`；门禁重算比对，不同则要求本次 diff 同时有「`feature-bits.md` 新增行或 `version` 被显式改动」与「`decisions.md` 对应条目被改动」，缺一判红 | 第一次冻结发生（[decisions.md](decisions.md) D15） | D15 |
| C10 | 新代码读不了旧镜像却没人发现 | 黄金镜像回归：用当前代码去读全部历史版本的归档镜像、跑 checker、比对期望内容摘要，任一不过判红。镜像本体不进仓库，只提交清单，清单**只增不删** | 第一次冻结发生、mkfs、checker | D15 |
| C11 | feature bit 位号被跳号占位或被回收再分配 | 门禁扫 `feature-bits.md`：位号必须严格递增、不许跳号、不许有代码引用表里不存在的位号、退役位不许被赋予新语义 | `feature-bits.md` 存在（可先于格式建立） | D15。回收一个位会让旧镜像那一位被误读成「新特性已启用」，文件系统会真的做错事 |
| C4 | 项目本地规则（`.claude/rules/*.md`）与项目 `CLAUDE.md` 的引用清单不一致 | 门禁比对 `.claude/rules/` 下的文件集合与 CLAUDE.md 里 `@.claude/rules/` 引用集合，任一侧多出一项即判红 | 无（现在就能做，只是还没做） | 实测：`manifest.sh` 只覆盖 SOP 包自己的 `CLAUDE.md + rules/`，项目本地那一份没有任何检查在看 |

> ⚠️ C3 不是强化项。截断 MAC 的安全论证整个押在「伪造尝试次数有界」上，
> 而那个界来自读重试上限——上限没钉死，80 位 MAC 的论证不成立。
