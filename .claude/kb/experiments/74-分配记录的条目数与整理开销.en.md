## E74 Allocation Record Entry Count and Compaction Cost — Structural Half of Axis 1 and Axis 2 Run (2026-09-01, 9 Unit Tests / All 8 Mutations Caught): **Compaction Cost Does Not Scale with Disk Capacity, but COW Amplification Varies 370×, Depending Entirely on Placement Clustering**

[中文](74-分配记录的条目数与整理开销.md) · **English** · [日本語](74-分配记录的条目数与整理开销.ja.md)

D3 (Space Allocation) settled item 1 self-acknowledged "**cost has not been measured**: per-placement implies allocation record entry count scales with capacity,
rather than with statistical dimensions", and its interaction with "resident background compaction" had no empirical test.
D3 (Space Allocation) settled item 3 settled the carrier (btree in an independent keyspace, key = placement, value = allocation generation) —
**settling the carrier does not mean cost is known.**

### Criteria (Hardcoded Before Run, Unchanged After Run)

1. **Absolute value assertion**: Entry count must exactly equal allocated placement count, forbidden to merely observe that it "roughly scales with capacity".
2. Compacting a batch of N placements, write bytes must be `O(N × entry_width + tree_height × node_size)`;
   items growing with **disk capacity** rather than N judged as "full scan crept into compaction path".
3. Contrast against accounting tree of D5 (Snapshot / Space Accounting Mechanism): entry count dimensions of both trees must differ; identical dimensions indicates one was built incorrectly.

### Measurement

#### Axis 1: Entry Count and Tree Height Scale Linearly with Capacity (Criterion 1)

Placement granularity taken as 32 KiB (unit size of D4 (Checksum Position)), 90% fill rate, 16 KiB node, 20-byte entry ⇒ fanout **816**:

⚠️ **Range Note (2026-09-03, E97 (Entry Encoding of Accounting and Allocation Records) review): Tree height column was one level too low.**
E74 (Allocation Record Entry Count and Compaction Cost) multiplied all the way up using **leaf** fanout 816 across entire tree, whereas interior nodes must each carry an extra
child pointer — calculating per actual width of 53 bytes for tree table unit pointer from D22 (How to Synthesize Unit Atomicity) settled item 7,
interior fanout is only **251**. E97 (Entry Encoding of Accounting and Allocation Records) recalculated using two-tier fanout: on 16 TiB it is
**4 levels, not 3 levels**, and this tree itself consumes 9 740 435 456 bytes (553 ppm) rather than 9.0 GiB (approx 512 ppm).
⚠️ **Axis 2 conclusion unaffected** — "no item scales linearly with capacity" relies on those 6 increments in 13 → 19 originating entirely from tree height;
under two-tier fanout, tree height still grows only one level with capacity. **Not a word in entry count column needs changing.**

| Capacity | Entry Count | Tree Height | This Tree Consumes |
|---|---|---|---|
| 1 TiB | 30 198 988 | 3 | 578 MiB |
| 16 TiB | 483 183 820 | 3 | **9.0 GiB** |
| 64 TiB | 1 932 735 283 | 4 | 36 GiB |
| 256 TiB | 7 730 941 132 | 4 | **145 GiB** |

⇒ **Allocation record tree itself consumes approx 0.055% of capacity**, scaling linearly and synchronously with capacity.
This is precisely the number D3 (Space Allocation) settled item 1 described as "not measured"; E74 (Allocation Record Entry Count and Compaction Cost) measured it.

#### Axis 2: Compaction Cost Does Not Scale with Disk Capacity (Criterion 2 Holds)

Fixed N = 4096 placements, capacity scaled from 1 TiB to 256 TiB (**256×**):

| Capacity | Rewritten Nodes for Contiguous Placements | Rewritten Nodes for Scattered Placements |
|---|---|---|
| 1 TiB | 13 | 4143 |
| 16 TiB | **13** | 4823 |
| 256 TiB | **19** | 8208 |

⇒ On contiguous side, capacity grew 256× while rewritten nodes grew from 13 to 19; **all 6 added nodes came from tree height 3 → 4**
⇒ **Not a single term scales linearly with capacity, Criterion 2 holds**, no full scan exists in compaction path.

#### ⚠️ But COW Amplification Varies 370×; Watershed Is Placement Clustering in Key Space

**COW rewrites entire 16 KiB node, not merely those 20 bytes.** 4096 placements, 16 TiB:

| Placement Distribution | Bytes Written | Relative to "Writing Only Those 20 Bytes" |
|---|---|---|
| **Contiguous** | 212 992 | **2.6×** |
| **Scattered** | 79 020 032 | **964×** |

⇒ **The 370× disparity lies entirely on the "clustered or not" dimension**, which is governed by key choice:
Key settled in D3 (Space Allocation) settled item 3 is **(device identity + in-device offset)**
⇒ **Physically adjacent placements are adjacent in key space as well**, while compaction relocates physically adjacent batches
⇒ **That key choice places compaction on the 2.6× side, not the 964× side.**

⚠️ **This is not E74 (Allocation Record Entry Count and Compaction Cost) endorsing compaction policy**: it states that **carrier does not obstruct under favorable conditions**,
whereas compaction policy itself **was unmeasured** — D26 (Background Compaction and Placement Reclamation) settled items 1 / 2 / 3 / 12 settled trigger, transaction form, acceptance, and framework, while threshold values await E10 (Aging: Structural Anti-Aging vs Post-Hoc Compaction), none of which are in the model of E74 (Allocation Record Entry Count and Compaction Cost).
Relocating a batch of placements scattered across key space remains 964×; whether such batches occur is governed by policy.

#### Criterion 3: Two Trees Have Different Dimensions ✅

| Capacity | Allocation Record Entry Count | Accounting Tree Entry Count (E71 (Entry Count and Width of Accounting Keys) Upper Bound Arm) | Ratio |
|---|---|---|---|
| 1 TiB | 30 198 988 | **115 200** | 262 |
| 16 TiB | 483 183 820 | **115 200** | 4194 |
| 256 TiB | 7 730 941 132 | **115 200** | 67 108 |

⇒ Allocation records scale linearly with capacity; accounting tree **is identical number across all three tiers** (scaling with statistical dimensions)
⇒ **Dimensions indeed differ, Criterion 3 holds**, neither tree was built incorrectly.

### What It Cannot Answer

1. Pure arithmetic + btree structure model: no allocator implementation, no background compaction, no write buffer, 0 file operations.
2. **Axis 2 has two questions, answers only one**: "how many bytes this tree writes" is a structural quantity, calculable;
   **"how long it runs" is wall clock, requiring implementation to exist**.
3. **Background compaction policy not in model** (none of triggers, transaction forms, acceptance, and frameworks from D26 (Background Compaction and Placement Reclamation) settled items 1 / 2 / 3 / 12 modeled)
   ⇒ Measures "**what btree carrier forcibly pays under batch rewrites**",
   **not** cost of a specific compaction policy. Carrier is settled; policy is not.
4. **Placement granularity unsettled in repo** — 32 KiB settled in D4 (Checksum Position) is **unit**, not definition of "placement".
   Primary tier uses 32 KiB, additionally scanning 4 KiB and 1 MiB tiers; entry counts scale inversely with granularity.
5. **Key segment widths and node header base bytes likewise unsettled** (same owed check as E71 (Entry Count and Width of Accounting Keys) / E73 (Fanout Cost of Node Key Interval)).
6. **"Contiguous" and "scattered" are two endpoints, not distribution**: no basis for where real compaction batches land;
   E74 (Allocation Record Entry Count and Compaction Cost) provides values for these two extremes only.
