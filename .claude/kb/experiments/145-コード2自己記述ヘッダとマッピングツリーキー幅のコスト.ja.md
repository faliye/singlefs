## E145 コード2自己記述ヘッダとマッピングツリーキー幅のコスト —— 実行済み（2026-09-13、カウントモデル、9単体テスト / 11件ミューテーション全検出）

[中文](145-码2自描述头与映射树key宽的代价.md) · [English](145-cost-of-code-2-self-describing-header-and-mapping-tree-key-width.en.md) · **日本語**

**問うているのは C306 (コード 2 ヘッダが key 幅を自己記述しない)と C307 (マッピングツリーの2つのキー幅を固定幅キーのツリーに収める方法)それぞれのコストである。** ユーザーは「コード2は自己記述でよい」と指示した。
**六つの判定基準がすべて通過**：自己記述ヘッダ（B アーム）はノードあたり5バイト多いだけで、五本のツリーのファンアウトは一つも落ちず、ツリー高は 10 TB プールで全く変わらない；
スキャン時にツリーテーブルがない場合、A アームのヘッダは登録済みの幅を一つずつ試すことで、登録済み五本のツリーの 1000 ノードをすべて解けるが、未登録のツリーの 200 ノードは一つも解けず、自己記述ヘッダは 1200 個すべてを解く；
マッピングツリーの三通りの収め方は、10 TB プールでいずれもツリー高が 4 で、27 へのゼロ埋めと二本のツリーはリーフファンアウト 294 / 306、自己記述エントリは 284 である。数値だけを報告し、形態は決定が定める。

### これはカウントモデルであり、測定ではない

I/O なし、乱数源なし（スキャンのシミュレーションは固定シードを使う）⇒ N 回走らせてもバイト単位で一致する。根拠の強さは、9個の単体テストで固定した絶対値 + 11件のミューテーション全検出から来る：
ヘッダ基数を80に変更、自己記述で増えるバイトを4に変更、固定幅区間を16に変更、A アームがペイロード内のエントリ数フィールドを引き忘れる、ツリー高を0から数える、登録幅の表が27を落とす、A アームが先頭の四つの幅しか試さない、
自己記述スキャナがヘッダ内の key 幅をチェックサム検証せずに信じる、ゼロ埋めアームのエントリを53に変更、二本のツリーがツリーテーブルのエントリを一つしか登録しない、自己記述エントリがオフセット表を加えない、のそれぞれでテストが赤になる。
⚠️ 等価ミューテーションが一件記録されている：A アームの「ちょうど一つの幅がチェックサムを通る」と「最初に通った幅を採る」は32バイトのチェックサムの下では同じ挙動になり（カバー範囲の異なる二つのダイジェストが同じフィールドに同時に等しくなることはない）、単体テストが「各ノードで通る幅は多くても一つ」を固定している。

### 被験対象とアーム

コード2ヘッダ（C306 (コード 2 ヘッダが key 幅を自己記述しない)）、ヘッダ幅は E142 (新規プールでのファイル作成のドライラン) の 81 + 2 × key 幅に従う：

| アーム | ヘッダ | スキャン時の解き方 |
|---|---|---|
| A 現状 | 81 + 2 × key 幅 | ツリーテーブルがないと key 幅が分からない：登録済みの五つの幅を一つずつ試し、ちょうど一つの幅がヘッダチェックサムを通ったときだけ解けたとする；未登録のツリーは解けない |
| B 自己記述 | A + key 幅 1 + エントリ数 2 + エントリ幅 2 | ヘッダ内の key 幅を読み、それからヘッダチェックサムを検証する |
| C 固定幅区間 | 81 + 2 × 32 + 5 = 150 | ヘッダ幅は固定、key 幅フィールドが区間内で有効な先頭何バイトかを示す |

マッピングツリー（C307 (マッピングツリーの2つのキー幅を固定幅キーのツリーに収める方法)）：a 27 へのゼロ埋め（エントリ 55）、b 二本のツリー（コード1のツリー 55、コード2 / コード3 のツリー 53、ツリーテーブルに 200 バイトのエントリが一つ増える）、c 自己記述エントリ（1バイトの key 長 + key + 28 + ノード内2バイトのオフセット表 ⇒ 58 / 56）。
規模：10 TB ÷ 32 KiB = 335 544 320 個のデータユニット、コード2 / コード3 はその 1/8 で数える；ツリー高は満杯充填で計算し、内部ノードのエントリ = key + 83 のポインタ。

### これらの数値が示すもの

1. **自己記述はほぼ無料**：B は A よりノードあたり1バイト多いだけで（エントリ数とエントリ幅は A も入れる必要があり、ペイロードに入れているだけ）、ファンアウトとツリー高は欄ごとに同一である。C の固定幅区間は21〜53バイト多く、割り当てツリーでファンアウトが2落ち、買えるのは「ヘッダ幅が一定」だけである。
2. **A アームは完全に解けないのではなく、未登録のツリーが解けない**：登録済みの五つの幅を一つずつ試してちょうど一つが通ることを要求すれば、32バイトのヘッダチェックサムの下で曖昧さはない；D15 (フォーマット凍結ポリシー) 確定項目 2 はツリーテーブルを初日からオープンリストと定めており、将来のツリーは旧スキャナの目には解けない200ノードそのものである。
   ⇒ C306 (コード 2 ヘッダが key 幅を自己記述しない)の深刻さは「オープンリストの下で新しいツリーが解けない」であり、「何も解けない」ではない。
3. **マッピングツリーの三通りの収め方はツリー高で区別できない**：a と b のリーフファンアウト 294 / 306 は 10 TB プールでいずれも4層；b はツリーテーブルのエントリが一つ増え、読むべきツリールートも一つ増える；c はエントリあたり3バイト多く、ファンアウトが10落ち、ノード内の固定幅二分探索も失う。
   ⇒ コストで見れば C307 (マッピングツリーの2つのキー幅を固定幅キーのツリーに収める方法)は a と b が互角で、差は条項にある：a は D19 (ブロックポインタ構造と幅予算) 確定項目 6 に「コード2 / コード3 の key は二バイトのゼロを補って27にする」と明記する必要があり、b はツリーを一本加える必要がある。

### 答えられないこと

1. カウントモデル：時間は測らない；ツリー高は満杯充填で計算しており、実際の充填率はより低くツリーはより高いが、三つのアームは一緒に変わる。
2. スキャンでのヘッダ解読はユニットヘッダだけを作り、実在のプールは作らない；未登録のツリーは key 幅 16 で「将来のツリー」を代表させる。
3. D15 (フォーマット凍結ポリシー) の層は答えない：自己記述フィールドを第1層に入れるか第4層に入れるかは、決定が定める。
4. 決定性：N 回走らせても同じ。
