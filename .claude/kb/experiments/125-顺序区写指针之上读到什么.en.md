`zone_capacity` / `zone_nr_conv` / `zone_max_open` / `zone_full`), and `/usr/sbin/blkzone` is present.
E125 (What is Read Above Write Pointer in Sequential Zone) went to obtain those observations.

### Criteria (Hardcoded Before Run, Never Modified After)

1. **What is read above WP.** Append N records of root slot width into an empty sequential zone, then read `[wp, zone_end)`.
   Result can only be one of three, **consequences for tested arm hardcoded before run**:

   | Observation | Consequence for "Addressing Hint Only" Arm |
   |---|---|
   | ① Read succeeds and **all zeros** | Scanning whole zone **can read bytes**. ⚠️ Still requires a separate rule distinguishing "all zeros" from "corruption", but input to that rule can be zero value itself, not necessarily WP ⇒ this half of arm **stands** |
   | ② Read succeeds and **non-zero** | Exit must pay a new rule distinguishing non-zero garbage from corruption, and **E125 (What is Read Above Write Pointer in Sequential Zone) must report offset and value of first non-zero byte**, determining whether input to that rule can only be WP |
   | ③ **Read fails** | Exit **does not hold** (report errno absolute value) ⇒ without WP on sequential zone "all candidates" cannot be bounded ⇒ that arm **eliminated** |

2. **What is read after zone reset, and whether written bytes remain.** Re-read entire zone after `BLKRESETZONE`, similarly triaged per criterion 1;
   **additionally report whether signature bytes of those N records written prior to reset are still found** —— this answers
   "after resetting a zone, whether any trace of its former existence remains in bytes written by this project".
3. **Whether `zone_full` can construct "WP leading our recognized commit point".** Spin up a null_blk with `zone_full=1`,
   reporting relationship between `wp` and `start + capacity` for each zone in `blkzone report`, in **absolute values**.
4. **Zone boundary alignment (cross-apparatus reconciliation).** Report absolute value of `zone_size`, and calculate `8191 × chunk mod zone_size`,
   with chunk taking three tiers swept by E48 (Feasible Points of Root Ring Geometry). **Result must match the nine cells recomputed by main agent in 2026-09-09 round cell by cell**
   (none divisible across all nine cells). Mismatch judged red —— indicating two places calculated different numbers for the same quantity.
5. **Conventional zones.** When `zone_nr_conv=k`, report `type` of first k zones and `type` of remaining zones, in **absolute values**,
   and report total bytes of conventional zones —— determining whether "always place in conventional zone" arm requirement of
   "conventional zone covering three points `{0, P·chunk, 2P·chunk}`" is feasible.

### What It Cannot Answer

**Does not answer behavior of real ZNS disks** —— machine has no real zoned disks.
**Does not answer crash semantics**: `zone_full` creates a static "WP already at end" state,
not "crashing mid-write" —— "crashing mid-write" still requires a crash-point replay harness.
**Nor does it answer whether "always place in conventional zone" arm holds**: criterion 5 only reports size of conventional zones,
whether "this size suffices to cover those three points" is a deduction requiring tripartite review.

### Two Findings Outside Criteria, Originating from Kernel Documentation Rather Than Apparatus

Inspecting local `~/code/fs-refs/linux-6.17/Documentation/filesystems/zonefs.rst` after run,
two sentences directly relevant to D22 (Synthesizing Unit Atomicity) unsettled item 6, copied verbatim (**external documentation, unverified in this project**):

1. Lines 236–242: "the partial failure of a multi-BIO large write operation will cause the zone
   write pointer to advance partially, even though the entire write operation will be reported as
   failed to the user" ⇒ **WP leading commit point does not require a crash**, a single large write reported as failure suffices.
2. Lines 330–332: "the write pointer of read-only zones is defined as invalib by the ZBC and ZAC
   standards, making it impossible to discover the amount of data that has been written to the zone"
   (`invalib` is spelling in upstream original, copied as-is) ⇒ **once a zone transitions to read-only, WP is invalid by standard**.

⚠️ **The external standard point was investigated once more**: checking public NVMe ZNS materials on 2026-09-09,
"reading in this area is handled the same way as when reading unwritten blocks",
where unwritten block read behavior is chosen by Identify Namespace `DLFEAT` (all 0 / all 1 / not reported),
and when a bit in `NSFEAT` is set controller **can directly return an error for reading unwritten blocks** (Deallocated or Unwritten Logical Block error).
⇒ **"Reading above WP definitely succeeds and definitely returns 0xff" does not hold**, that is behavior of this apparatus, not a guarantee of standards.
Source: ZNS Command Set specification from nvmexpress.org and zonedstorage.io, **unverified in this project**.

**6 mutations each proven to turn red** (baseline green):
`slot_width_not_4096` (changing expected slot width to 512), `crit4_unexpected_divides` (replacing P with power of 2 8192,
cross-apparatus reconciliation turns red immediately), `neg_control_cond_not_empty`, `zone_bytes_not_64MiB`,
`pos_control_wp_absolute` (changing M from 8 to 7), `slot_width_not_4096:512` (slot width not taking pbs).

⚠️ **One of them was a true defect forced out by mutation testing, recorded faithfully**: positive control originally had only
the mutual comparison assertion `WPB == M × SLOT`, where `M` drove both write and expected value ⇒ changing `M` from 8 to 7
**remained completely silent**. Per `.claude/singlefs-ai-sop/rules/test-discipline.md` "For every mutual comparison assertion written,
there must be an assertion beside it pinning absolute values", supplemented two absolute value assertions `WPB == 32768` and `ZBYTES − WPB == 67076096`,
and the mutation was caught on the spot. **This is precisely the failure pattern that rule guards against, and it truly happened once in E125 (What is Read Above Write Pointer in Sequential Zone) 2026-09-09 run.**
