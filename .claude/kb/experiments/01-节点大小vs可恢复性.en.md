## E1 Node Size vs Recoverability —— Partially Run (The blast radius half is cleared by E29 (Blast Radius of a Single Failed Node), and its criteria were corrected by it; the recovery time half has not been run, checker already exists)

[中文](01-节点大小vs可恢复性.md) · **English** · [日本語](01-节点大小vs可恢复性.ja.md)

**Artifacts**: The raw output of the blast radius half is in `e29-blast-radius-2026-08-29.out`,
rerun `cargo run --release --bin e29_blast_radius` (body text in E29 (Blast Radius of a Single Failed Node)).
⚠️ **The recovery time half has no artifacts, because it has never been run**—prerequisites are mkfs, checker, and a targeted corruption tool.


**Background**: Large nodes save seeks and yield a shallower tree (bcachefs uses 128K–256K),
but **the rescanning cost of a corrupted node is linearly amplified by node size** (measured in E29 (Blast Radius of a Single Failed Node): the rescan volume of a level-1 node equals fanout exactly,
from 49 for 2 KiB to 1636 for 64 KiB), directly conflicting with the project's rebuildability goal.
⚠️ **What is amplified is recovery time, not permanent data loss**—index is derived state (D21 (Boundary Between Authoritative and Derived States)), so corruption only causes slowness.
Both sides must be measured; one cannot cherry-pick only one side.

**Independent Variable**: Node size 16K / 32K / 64K / 128K / 256K.

**What to Measure**

| Metric | Measurement Basis |
|---|---|
| Blast radius of single-node corruption | After randomly corrupting 1 metadata block, **the number of unreachable keys** (not bytes—bytes would be biased by node size itself). The arithmetic version is already given by E29 (Blast Radius of a Single Failed Node); here what is wanted is reproduction on real images |
| **Rescan cost of full-disk scan rebuild** | After corrupting K nodes, how many units must be scanned to rebuild them. **Do not measure "success rate"**—E29 (Blast Radius of a Single Failed Node) measured permanent loss on index side as constantly 0, so success rate has no discriminative power |
| **Number of reachable keys with stale or incorrect values** | Compare rebuilt keyspace key-by-key against the model (the ideal file system HashMap), **reporting two separate numbers from "unreachable"** |
| Lookup cost | Average blocks read per point lookup; tree height |
| Total metadata volume | Metadata bytes under the same dataset |

**Criterion**: Under the premise that "**rescan cost ≤ target threshold**", select the node size with the lowest lookup cost
(settled by user on 2026-09-06, simultaneously with the measurement basis rewrite of D8 (Core Index Structure) settled item 4).
The target threshold is a recovery time budget, **which must be fixed beforehand**—this step cannot wait until experiment results are out.
⚠️ **The criterion is not "full-disk scan rebuild success rate ≥ target threshold"**: E29 (Blast Radius of a Single Failed Node) measured
permanent loss from index corruption as constantly 0 ⇒ success rate is independent of node size, using it as criterion cannot bound an upper limit.

**What Counts as Failure**: If there is no distinguishable difference in blast radius across tiers,
it indicates that the corruption injection method was improper (e.g., only leaves were corrupted, or corruption points did not fall on referenced nodes).
**The entire round is invalidated and must be rerun**; "looking roughly similar" must not be taken as a conclusion.

⚠️ **The "reachable but value stale" column is not a bonus, but a discriminative power gap in E1 (Node Size vs Recoverability).**
If a pure routing internal node is lost, only routing is lost; leaves carry block headers, and scan rebuild is **idempotent**;
however, once an internal node holds data that has no secondary copy elsewhere (e.g. pending unflushed updates in message buffers),
losing it means losing **data**. The rebuilt tree can have correct block headers, checksums, and Merkle chains—
**I-1 (Block Self-Describing).x and I-2 (Checksum).x are all green, yet content is stale**.
None of the existing invariants in [invariants/README.md](../../../crates/singlefs-checker/invariants/README.md) can detect this category.
Without adding this column, E1 (Node Size vs Recoverability) would report an attractively high rebuild success rate for designs storing data in internal nodes,
whereas that number guarantees nothing.

**Prerequisites**: D8 (Core Index Structure) settled, mkfs, checker, and a tool capable of targeted image corruption.

⚠️ **Does not produce a selection rule for "calculating node size based on device characteristics"**: D8 (Core Index Structure) settled item 2 has
pinned 16 KiB **as a constant**—"it is a constant in the format, not a formula", based on the fact that on the curve of E20 (CPU Cache Cost of Widening Pointers),
the anomaly at 8 KiB remained stable across six rounds with nobody able to explain it.
⇒ What E1 (Node Size vs Recoverability) must produce is **the upper-bound verification of that constant**: whether 16 KiB holds under the recovery time target threshold,
rather than a formula calculating node size by device. **Tests must uniformly pin values explicitly; automatic values are forbidden.**
