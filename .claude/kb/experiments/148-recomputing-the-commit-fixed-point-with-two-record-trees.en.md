### This is a counting model, not an implementation

The `scattered` arm uses deterministic pseudorandomness (5 seeds, multiplicative mixing, not `seed | 1`); the other two arms are deterministic ⇒ N runs are byte-identical. Evidence comes from 9 unit tests and all 10 mutations caught: two hand-calculated anchors (two small trees with 8 leaves each: 4 rounds / 10 dirty / 11 blocks / 22 records; one tree: 2 rounds / 3 dirty / 4 blocks), positive controls from E81 (Fixed Point of Commits) (2 rounds and 5 blocks, scattered ≥ 5 times as many), two trees at pool scale in 2 rounds and 9 blocks, 4 blocks at new-pool file creation scale, ordering of the three arms (commit-block-only clustering strictly between fully clustered and fully scattered), conservation, a cursor starting in the middle of key space, and mapping-tree geometry. The first mutation round missed “cluster user blocks as well in the commit-block-only arm” and “start cursor at 0”: the former lacked an assertion distinguishing the arm, while the latter had insensitive sample points (the small tree dirtied the same number of nodes from 0). Adding one assertion for each caught both.

### Arms and measurement basis

- The three placement policies are identical to E81 (Fixed Point of Commits): `clustered` (both user blocks and blocks generated by commit land sequentially in a clustered segment), `scattered` (all random), and `meta_clustered` (only blocks generated by commit are clustered). Policies act on both trees' key spaces: allocation record tree keys are placements (clustered ⇒ contiguous); mapping tree keys are “class tag + birth tree + birth txg + write sequence” under D19 (Block Pointer Structure & Width Budget) settled item 6. Entries for the same birth tree in one publish are contiguous in write sequence ⇒ clustered keys are contiguous in both trees.
- The allocation record tree matches E81 (Fixed Point of Commits): 512 entries per leaf, fanout 256, 65,536 leaves (≈ 1 TiB pool / 32 KiB). The mapping tree has 296 entries per leaf (mapping-leaf fanout from D19 (Block Pointer Structure & Width Budget) settled item 6), internal fanout 147 (⌊16205 / (27 + 83)⌋), and ⌈33,554,432 / 296⌉ = 113,360 leaves ⇒ 4 levels. At new-pool file creation scale each tree has one leaf (splits are not modeled; U = 1024 does not fit in one leaf, so 0 / 1 / 12 / 128 are run).
- The accounting tree publishes 2 nodes per publish (E81 (Fixed Point of Commits)). Each block to allocate inserts one record in each record tree. Conservation: inserted records = allocated blocks × number of trees.
- U ∈ {0, 1, 12, 128, 1024}; 0 is an empty publish. The clustering cursor starts in the middle of key space (the measurement basis of E81 (Fixed Point of Commits)).
- All 10 mutations caught: change mapping-leaf fanout to 512; change mapping internal fanout to 256; build only one tree; change accounting nodes to 0; do not accumulate dirty counts; omit accounting when adding metadata blocks; cluster user blocks as well in the commit-block-only arm; start cursor at 0; stop allocating new dirty nodes; count one level too few.

### What these numbers mean

1. **The second record tree raises the clustered fixed point from 5 to 9 blocks**: the extra four are exactly the mapping tree's four levels; convergence takes two rounds—one node per level, one record per node, all landing in already-dirty leaves in the next round. This 9 is independent of U (0 / 12 / 128 all give 9; 1024 gives 14) and is a **constant upper bound** under the clustering policy.
2. **There is a candidate measurement basis for c_max**: empty publish = 2 accounting blocks + 3 allocation record tree levels + 4 mapping tree levels = 9 blocks at pool scale; 4 at new-pool file creation scale. The drain reserve pool 10 + 7 c_max in D16 (Publish Semantics) settled item 1 is 73 blocks using 9, or 38 using 4. Arm 戊 of D16 (Publish Semantics) settled item 8, “at most R = 3 empty publishes per switch,” costs 27 blocks using 9. **These are model numbers; before entering a clause the user must decide whether they are an upper bound** (splits and merges, the stripe membership table and livelist are outside the model; see “What it cannot answer”).
3. **Scattered user blocks remain expensive when only commit blocks are clustered**: 59 / 487 / 2879 blocks (roughly 28 / 231 / 1273 with one tree). Two trees roughly double the cost of random user-block placements. D3 (Space Allocation) settled item 5 requires clustering commit blocks; this cell shows that the user-block placement policy (D3 (Space Allocation) settled item 8) also materially affects ckpt_cost.
4. **Fully scattered allocation costs 138,000 blocks with two trees** (5909 with one): the mapping tree's 113,360 leaves are touched randomly. The conclusion is the same as E81 (Fixed Point of Commits): under scattered allocation I-8.1 (Ring Geometry Sufficiently Large) has no usable upper bound.
5. `trees=1` reproduces E81 (Fixed Point of Commits) cell by cell: the apparatus has not drifted.

### What it cannot answer

1. Whether the stripe membership table (D2 (RAID Stripe Policy) settled item 12) and livelist (D6 (Snapshot Implementation Model) settled item 3) also enter the fixed point is not modeled; node splits and merges are not modeled either (when a leaf fills to capacity the next leaf is dirtied).
2. Actual I/O counts and crash semantics; at new-pool file creation scale the run reaches only U = 128.
3. Whether 9 blocks is an “upper bound”: the 2026-09-13 user settlement in D28 (Mount-Time Commitments) settled item 4 sets no constant ceiling and calculates from the current structure instead. Nine is a model number, not an upper bound.
