## E66 How Small Files Land After Padding — Run (2026-08-31, N=5)

[中文](66-补齐之后小文件怎么落.md) · **English** · [日本語](66-补齐之后小文件怎么落.ja.md)

**The question asked**: After D4 (Checksum Location) settled item 2 (extents smaller than a unit are padded to 32 KiB) was settled,
which landing strategy small files should follow. **The inlining conclusion of E8 (Different Write Paths for Large vs Small Files) was measured under the premise of no padding**—
it computed at the time that "inlining saves one I/O", whereas after padding an additional item appeared: "not inlining occupies an entire 32 KiB unit".
**That item simply did not exist in the model of E8 (Different Write Paths for Large vs Small Files)**, so its crossover point cannot be directly applied.

### Three Landing Strategies

| Arm | Where Small Files Live | Its Cost |
|---|---|---|
| `extent` | Independent data extent, **padded to 32 KiB** | Space: 1 KiB file occupies 32×; Read: one 32 KiB read |
| `inline` | Inlined into index node (16 KiB node of D8 (Core Index Structure) settled item 2) | Squeezes node bytes ⇒ fanout drops, tree height grows; read along when reading large files |
| `pack` | Multiple small files share one 32 KiB unit | Space reclaimed, but **lifecycles coupled**: modifying one requires RMW on entire unit, deleting one does not release unit |

### What to Measure

Independent variable = file size (512 B, 1 K, 2 K, 4 K, 8 K, 16 K, 32 K, 64 K), measuring across three arms for each tier:
**space footprint bytes**, **device bytes and time to read a small file**, **device bytes and time to write a small file**.

### Criteria and Failure Clauses Hardcoded Before Run

1. **Main criterion**: Provide pairwise **crossover file sizes** among the three arms, and clarify where the crossover point of E8 (Different Write Paths for Large vs Small Files) shifts once padding is taken into account.
2. **Positive control, run arm by arm**: Kernel `/proc/self/io` byte delta matches claimed device bytes of each arm (±2%).
3. **Discriminative power control**: Space footprint of `extent` arm across 512 B and 16 KiB tiers **must be completely identical** (both occupy one unit)—differing indicates padding was not modeled, entire round aborted.
4. **Cannot read ≠ read 0**: Zero timing or unobtainable count uniformly aborts the entire round.
5. N=5 rounds; judging "passed" requires passing all 5 rounds.
6. **Acceptance of reverse outcome** (written before run): If `inline` is not superior to `extent` across **all** tiers, write "padding did not change the conclusion of E8 (Different Write Paths for Large vs Small Files)"; **forbidden to assert inlining is better merely because space multiple of padding is huge**—space is not a criterion of this project (`.claude/rules/fs-design.md`), winning must be won on I/O or latency.

⚠️ **Lifecycle coupling of the `pack` arm is not modeled in E66 (How Small Files Land After Padding)**; only its space and I/O upper bounds are measured;
the cost of coupling requires a separate experiment.

### Verdict for Two Controls: All Passed

| Control | Criterion | Actual Measurement |
|---|---|---|
| Positive | Kernel recorded bytes ÷ claimed device bytes of each arm ≈ 1 | **200/200 cells** within ±2% |
| Discriminative power | `extent` space footprint identical at 512 B and 16 KiB | Value set of `space_bytes` across **all tiers ≤ 32 KiB is precisely {32768}** |

### Actual Measurement (N=5, **Device Side** = Total Time Minus Separately Counted Checksum Time, Taking **Median**)

⚠️ **Two harness defects were remedied before this dataset was obtained**, both struck by three-way argumentation:
① Checksum verification time must be counted separately—E65 (Write-Side Cost of Checksum Granularity) round 1 failed to split it, where 11 percentage points of `full` arm's 25.92% were AES;
② **Warm-up must be discarded**—added 64 discarded warm-up runs (`const WARMUP`, pinned by unit test, proven to turn red by one mutation).
⚠️ **Chose adding warm-up rather than discarding that round post-hoc**: "looking at numbers before deciding which round to drop" is precisely the pattern that `.claude/singlefs-ai-sop/rules/test-discipline.md` aims to prevent.

⚠️ **Taking median instead of mean, because one round was pushed high overall by external activity**: in seed=2 round, there appeared `extent` read 569805, `pack` read 464044, `pack` write 704808 (other four rounds in same tier were on the order of 255–305 μs).
This machine had other sessions running experiments concurrently on the same NVMe ⇒ **absolute latency can be polluted by neighbors**.
Mean and median measurement basis yield **completely identical direction and order of magnitude** for conclusions (point-read advantage 16.5–16.7% vs 16.2–18.0%), with differences only in the two cells struck by that round.

| File Size | `extent` Read / Write | `inline` Read / Write | `pack` Read / Write |
|---|---|---|---|
| 4 KiB (Representative tier) | 255923 / **25018** | **212612** / 247842 | 256198 / 299190 |

**Three ratios across tiers (median measurement basis, five tiers from 512 B to 8 KiB)**:

| Metric | Range |
|---|---|
| `inline` point read faster than `extent` | **16.23 – 18.01%** |
| `inline` write more expensive than `extent` | **861 – 906%** |
| `pack` write more expensive than `extent` | **1076 – 1106%** |
| Difference between `pack` read and `extent` read | **±1.06%** (identical quantity) |

**Three conclusions**:

1. **`pack` is eliminated.** Read is cell-by-cell identical to `extent` (difference ±1.06%), while write is approximately **11× more expensive**.
   ⇒ **Purely inferior** on I/O, purchasing only space, and space is not a criterion of this project (`.claude/rules/fs-design.md`).
2. **The write-side advantage of `extent` originates from "first write does not need RMW", independent of byte count—strictly independent when calculated by total I/O bytes.**

   | Arm | Total Device I/O Bytes for One Write | Write Device Side ns (4 KiB Tier Median) |
   |---|---|---|
   | `extent` | 32768 (pure write) | **25018** |
   | `inline` | 16384 read + 16384 write = **32768** | 247842 |
   | `pack` | 32768 read + 32768 write = 65536 | 299190 |

   ⇒ **`inline` and `extent` transfer completely equal total bytes, yet elapsed time differs by 10×**—
   **a 0× byte gap cannot explain a 10× time gap.**
   The differentiating item is **one additional device round-trip**, not those bytes.
   ⚠️ This finding was pointed out by the forward leg of 2026-08-31 three-way argumentation, adopted after main agent confirmed by inspecting `read_bytes_of` / `write_bytes_of` functions.
3. **`inline` wins on point read, but this dataset does not have the final say on how much it wins**—whether it is 16.6%, 54.5%, or 100% under accounting measurement basis, see section "Asymmetry in Point Read Accounting".

### Asymmetry in Point Read Accounting: `extent` Index Leaf Read Not Accounted, While `inline` Was Accounted

⚠️ **Struck by counter-argument leg, confirmed by main agent: this is a modeling error, not noise.**
`read_bytes_of` accounts 16 KiB for `inline`—which is precisely the index leaf node; for `extent`, it accounts only 32 KiB data unit.
Yet for `extent` to obtain that extent pointer, **it must also first read the same 16 KiB index leaf**
(D4 (Checksum Location) settled item 1: metadata side 16 KiB, data side 32 KiB).
**For the same index read, one arm accounts for it while the other does not.**

After symmetrizing it, three accounting methods differ by an order of magnitude:

| Accounting Method | `extent` Point Read | `inline` Point Read | `inline` Advantage |
|---|---|---|---|
| Leaf constant miss (Symmetric) | 214.1 + 256.7 = 470.8 μs | 214.1 μs | **54.5%** |
| Leaf constant hit (Symmetric) | 256.7 μs | 0 (no device I/O) | **100%** |
| **Used in E66 (How Small Files Land After Padding) actual measurement (Asymmetric)** | 256.7 μs | 214.1 μs | 16.6% |

⇒ **The 16.6% in the asymmetric column cannot be treated as the read-side advantage of inlining**: symmetric accounting gives 54.5%–100%,
**inlining wins on point read by far more than shown by asymmetric accounting.**
⚠️ **This does not change the settlement of D14 (Dual-Track: Large/Small Files & Persistent/Transient) settled item 3**—its criterion is **atomicity**, explicitly stating "performance numbers cannot answer it". Asymmetric accounting affects the magnitude in the "cost" column, not the evidence for that settlement.

### That Percentage Also Drifts with Device State, Spanning 2.4×

Counter-argument leg used fio 3.36 on four 8 GiB direct-access files to measure the identical axis (16k vs 32k random reads, `iodepth=1`):

| File | `inline` Advantage |
|---|---|
| `e58.img` | 11.5 / 11.7 / 11.5% |
| `e61.img` | 10.8 / 10.8% |
| `e66.img` (used by E66 (How Small Files Land After Padding)) | **16.5 / 16.6%** |
| Fresh file just sequentially written full | **7.0 / 6.8%** |

**Granularity unchanged, advantage wanders between 6.8% and 16.6%.** The tier recorded by E66 (How Small Files Land After Padding) was the most favorable to inlining among the four files.
⚠️ **A conflicting independent figure already resided in kb**: the device-side split table of E58 (End-to-End Cost of Checksum Granularity)
(same axis, same disk, same date) gave 149444 / 162321 ns ⇒ **7.9%**.
Both recorded "device side", differing by over 2× — **the discrepancy is device state, not granularity.**
Three alternative explanations were all refuted by counter-argument leg: harness (rerun matches fio to 0.1 pp),
arm ordering and write burst (files untouched by write arms also showed only 10.8–11.7%), and ext4 fragmentation
(`filefrag` gave e58=26, e61=12, e66=8 extents; the least fragmented file had the highest penalty, hypothesis refuted).

### Break-Even Read-to-Write Ratio: Steady Direction, Unsteady Magnitude, Forbidden to Cite to Decimal Places

Device-side break-even read-to-write ratio (how many reads per write are needed for inlining to break even): five-tier median is 4.84 : 1 ~ 5.42 : 1,
**but that is merely one single point: "state of this disk when tested on 2026-08-31 + leaf constant miss + no node cache".**

| Variable | Break-Even Ratio |
|---|---|
| Fresh file just written full (fio today) | **13.5 : 1** |
| Aged `e66.img` (harness today) | **5.2 : 1** |
| Adding index node cache hit rate 0.9 (accounting of E8 (Different Write Paths for Large vs Small Files) had 256-node cache, E66 (How Small Files Land After Padding) dropped it entirely) | **0.42 : 1** |
| Cache hit rate 1.0 | **Inlining even cheaper than `extent`**, Conclusion 2 and break-even ratio fail together |

⇒ **Locally observable interval is 5:1 ~ 13.5:1**; stacking cache dimension drops lower bound to **0.42:1**.
⚠️ **Constant miss for data units can be defended; constant miss for index leaves cannot be defended**—without reading that leaf, one cannot find the file.

**The reason for drift was found by counter-argument leg: entirely on device side, zero from harness**: same fio, same file, same machine,
measured 4 KiB at 67.8 μs initially, then 142.3 μs subsequently (2.1×); the entire curve is an **additive shift of +70–80 μs**.
Not transient GC (continuous runs of 6×10 s stabilized at 257–265 μs), not temperature (36–55 ℃), not neighbors (block-layer read completions 0 within 5 s).
**A fresh file just sequentially filled returned to the "old" level** (16k 156.5–164.4 μs), while writing 24 GiB elsewhere left it completely unchanged
⇒ difference lies in "whether this data was written hours ago or just written".
⚠️ **Mechanism was not verified**: SLC folding and L2P mapping cache can both explain this shift, indistinguishable in the 2026-08-31 round.
Following the precedent of E65 (Write-Side Cost of Checksum Granularity), **forbidden to write SLC as explanation**.

⚠️ **Ran four times on the same day, ratio shifted 8.4–9.7 → 5.1–6.4 → 5.2–5.4 → 4.8–5.4**:
first time did not split checksum time; second time split but did not drop warm-up; third time remedied both; fourth time rerun with same measurement basis.
Interleaved with approximately 12 GiB of unrelated writes and activities of other sessions on the same disk,
absolute latency shifted upward overall (`extent` point read 174 μs → 256 μs).
⇒ **Break-even read-to-write ratio is not a number that can be cited to decimal places**. What can be cited is direction and magnitude:
**inlining wins by 15–20% on point read, pays an order of magnitude on write, with break-even point hovering around read-to-write ratio 5:1.**
⚠️ Same lesson as critical proportion in E58 (End-to-End Cost of Checksum Granularity): **a ratio obtained by subtracting two large numbers is extremely sensitive to device state, neighbor activity, and harness defects**.

### Not Contradicting E8 (Different Write Paths for Large vs Small Files), Both Measure Different Reads

⚠️ **E8 (Different Write Paths for Large vs Small Files) stated "cost of inlining lies on read side, device read count 47 → 293 (6.2×)",
whereas E66 (How Small Files Land After Padding) stated inline point read is 10% faster—both are correct because they do not read the same thing.**

| Who | Measured Read | Inlining in This Cell |
|---|---|---|
| E66 (How Small Files Land After Padding) | **Point-reading a small file**: reading one 16 KiB node vs one 32 KiB unit | **Device side 16–18% faster** |
| E8 (Different Write Paths for Large vs Small Files) | **Scanning a batch of files**: inlining bloats inode records to ~1152 bytes ⇒ records accommodated per leaf collapse ⇒ leaf count skyrockets | **6.2× slower** |

⇒ **E66 (How Small Files Land After Padding) alone is insufficient to overturn E8 (Different Write Paths for Large vs Small Files)**:
its `inline` arm **does not model fanout degradation**, reading only one node to finish, hence **systematically underestimates the cost of inlining**.
Read together, the combined interpretation is: inlining buys a tenth or so on point read, pays an order of magnitude on write, and pays 6.2× on scan.

⇒ **Padding did not change the conclusion of E8 (Different Write Paths for Large vs Small Files).**
Per Criterion 6 hardcoded before run, it must be stated truthfully here: `inline` **is not inferior across all tiers**—
it is 15% superior in the point read cell. But that cell is overwhelmed by an order of magnitude on the write side and 6.2× on scan,
and **the space it buys is not a criterion**.

⚠️ **The final settlement was not determined by this dataset**: D14 (Dual-Track: Large/Small Files & Persistent/Transient) settled item 3
(settled by user on 2026-08-31) set inline threshold to 0; **the criterion is atomicity, not performance**—
inlining crowds data of multiple files into the same index node, which is coupling of the identical shape as `pack`.
Figures of E66 (How Small Files Land After Padding) only show that "settling this way does not pay a large performance penalty", and **are not evidence for that settlement**.

### A Cross-Experiment Harness Defect: N=5 Actually Has Only 3 Seeds

Initial value of random state initialized with `seed | 1` (called `random_state` in `e66_small_files.rs` and `e65_write_grain.rs`, called `st` in `e58_csum_grain.rs`)
⇒ **seed 2 and 3 fold into the same state, seed 4 and 5 fold into the same state**.
Main agent confirmed by recalculating 1024 offsets for each of 5 seeds: **sequences for seed2 and seed3 are item-by-item identical, as are seed4 and seed5**.
⇒ The so-called N=5 is actually **3 access patterns × (1,2,2) repetitions**, **inter-round variation is therefore systematically depressed**.
Placement in [checks-owed.md](../checks-owed.md) C59 (Seeds Folding into the Same State).
⚠️ **It affects more than E66 (How Small Files Land After Padding)**: E58 (End-to-End Cost of Checksum Granularity) and
E65 (Write-Side Cost of Checksum Granularity) share the identical code pattern, and recorded "5-round variances" in both are likewise depressed.

### What It Cannot Answer

**`inline` arm does not model fanout degradation and tree height changes** (precisely what E8 (Different Write Paths for Large vs Small Files) measured)
⇒ it provides a **lower bound** of inlining cost;
**`extent` point read also omitted the hop on the index side**—`read_bytes_of` counts only the 32 KiB of the data unit,
whereas the 16 KiB node read of `inline` **serves both lookup and data retrieval simultaneously**
⇒ this item conversely flatters `extent`, pointing in opposite direction to previous item, neither measured;
**no transaction merging**: local leg pointed out that when `pack` "writes multiple small files on same unit in one transaction"
it performs RMW on only one unit while `extent` must write multiple units; E66 (How Small Files Land After Padding) has zero numbers for that cell
⇒ **conclusion "`pack` is purely inferior" holds only under single-operation measurement basis**;
`pack` arm does not model lifecycle coupling (deleting one does not release unit, modifying one affects others on same unit);
does not include transaction amortization, concurrency, or crash-point replay; changing devices requires rerun;
⚠️ **Local machine is shared**—other sessions running experiments on the same NVMe push absolute latency upward
(seed=2 round measured up to 2.3×); check whether neighbors are running before citing absolute values.
