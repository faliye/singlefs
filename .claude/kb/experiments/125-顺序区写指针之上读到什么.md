### 判据（跑前写死，跑完不许改）

1. **WP 之上读到什么。** 在一个空的顺序区里追加 N 条根槽宽的记录，再读 `[wp, zone_end)`。
   结果只可能是三种之一，**每种对被测臂的后果跑前写死**：

   | 观测 | 对「只做寻址提示」臂的后果 |
   |---|---|
   | ① 读成功且**全零** | 扫全区这条出路**读得到字节**。⚠️ 仍要另立一条规则把「全零」与「损坏」分开，但那条规则的输入可以只是零值本身，不必是 WP ⇒ 该臂**这一半站得住** |
   | ② 读成功且**非零** | 出路要付一条新规则把非零垃圾与损坏分开，而**E125（顺序区写指针之上读到什么） 要报出第一个非零字节的偏移与值**，由它判那条规则的输入是不是只能取 WP |
   | ③ **读失败** | 出路**不成立**（报 errno 绝对值）⇒ 顺序区上没有 WP 就界定不了「全部候选」⇒ 该臂**出局** |

2. **区重置之后读到什么，以及写进去的字节还在不在。** `BLKRESETZONE` 之后重读整个区，同样按判据 1 三分；
   **另报「重置前写下的那 N 条记录的特征字节还找不找得到」**——这答的是
   「重置一个区之后，本工程写下的字节里还有没有它曾经存在过的痕迹」。
3. **`zone_full` 造不造得出「WP 领先于我们认定的提交点」。** 用 `zone_full=1` 起一台 null_blk，
   报 `blkzone report` 里每个区的 `wp` 与 `start + capacity` 的关系，**绝对值**。
4. **区边界对齐（跨装置对账）。** 报 `zone_size` 的绝对值，并算 `8191 × chunk mod zone_size`，
   chunk 取 E48（根环几何的可行点） 扫过的三档。**结果必须与 2026-09-09 那一轮主 agent 复算的九格逐格一致**
   （九格全部不整除）。对不上判红——那说明两处对同一个量算出了不同的数。
5. **常规区。** `zone_nr_conv=k` 时报前 k 个区的 `type` 与其余区的 `type`，**绝对值**，
   并报常规区总字节数——它决定「一律落常规区」臂要求的
   「常规区覆不覆盖 `{0, P·chunk, 2P·chunk}` 这三个点」做不做得到。

### 失败条款（跑前写死）

| 条款 | 触发时怎么判 |
|---|---|
| **阳性对照**：往空区写 M 条之后，`blkzone report` 报的 `wp` 必须等于 `start + M × 记录宽` | 不等 ⇒ **观测装置本身错了，整轮作废**（分不清「WP 语义与我以为的不同」和「我写错了」）|
| **阴性对照**：空区的 `wp` 必须等于 `start`，`cond` 必须是 EMPTY | 不成立 ⇒ 整轮作废 |
| **反向接受条款**：若判据 1 得到 ①（全零） | 如实写「扫全区这条出路读得到字节」，**不许因为它对被测臂有利就跳过判据 2**——重置之后那一格才是更难的那半 |
| **反向接受条款二**：若判据 3 造不出「WP 领先」 | 如实写「`zone_full` 造不出这个状态」，并把「那个状态怎么造」重新立成空白，**不许改口径把别的状态说成它** |
| null_blk 的行为与真 ZNS 盘不同 | **E125（顺序区写指针之上读到什么） 只回答 null_blk 的行为**，正文每个数都要带 [tooling.md](../tooling.md) 那句口径。⚠️ **不许把它写成「zoned 设备上就是这样」** |

### 怎么跑（要 root，2026-09-09 那一轮拿不到）

```bash
# 判据 1/2/4/5：一台 4 个区、每区 64 MiB、前 1 个常规区的 null_blk
sudo modprobe null_blk nr_devices=0
# 其余几何走 configfs（模块参数是全局的，每设备各自的几何要走 configfs）
# 判据 3：另起一台，zone_full=1
sudo modprobe null_blk zoned=1 zone_size=64 zone_full=1 nr_devices=1
sudo blkzone report /dev/nullb0
```

⚠️ **目标设备一律从变量取并先 `lsblk` 确认**（`.claude/singlefs-ai-sop/rules/command-safety.md`），
**本机唯一的真实块设备 `nvme0n1` 一个字节都不许碰**。

### 它答不了的

**不答真 ZNS 盘的行为**——本机没有真 zoned 盘。
**不答崩溃语义**：`zone_full` 造的是一个静态的「WP 已经在末尾」状态，
不是「崩在写到一半」——后者仍要崩溃点重放 harness。
**也不答「一律落常规区」臂成不成立**：判据 5 只报常规区有多大，
「这么大够不够覆盖那三个点」是一条推论，要另走三方。

### 实测结果（2026-09-09）

装置：`null_blk` 内存后端的 host-managed zoned 设备，4 个区 × 64 MiB，区 0 常规区、区 1–3 顺序区，
`physical_block_size` = `logical_block_size` = 4096（⇒ D22（单元原子性怎么合成） 已定项 2 的槽宽在本装置上是 4096）。
**5 轮逐字节一致**，两条对照都过：阳性对照 `wp_bytes=32768 expect_bytes=32768`，
阴性对照 `wptr=0x000000 zcond=1`。

| 判据 | 实测 | 落在跑前写死的哪一格 |
|---|---|---|
| 1 WP 之上读到什么 | `outcome=read_ok rc=0 bytes_got=67076096 distinct=1 uniform_byte=0xff first_nonzero_off=0 first_nonzero_val=0xff` | **②（读成功且非零）** |
| 2 区重置之后 | `wp_bytes=0 zcond=1 uniform_byte=0xff marker_found_at=-1` | 重置把区退回 EMPTY，**特征字节一个都找不回来** |
| 3 `zone_full` 造不造得出 WP 领先 | `committed_bytes=0 wp_bytes=67108864 lead_constructed=yes`（四个区全部 `wp_eq_cap=yes zcond=14`） | **造得出** |
| 4 区边界对齐（跨装置对账） | 九格 `divides=no`，商 7.999023 / 3.999512 / 1.999756 / 63.992188 / 31.996094 / 15.998047 / 511.937500 / 255.968750 / 127.984375 | **与 D22（单元原子性怎么合成） 正文那张表逐格一致** |
| 5 常规区 | `types=1222 conv_zones=1 conv_bytes=67108864`；三档 chunk 的 `p1_inside=no p2_inside=no` | 常规区 64 MiB，够不到 `{P·chunk, 2P·chunk}` |

**判据 1 落在 ② 上，而 ② 那一格跑前写死的后果是**：「出路要付一条新规则把非零垃圾与损坏分开，
而 E125（顺序区写指针之上读到什么） 要报出第一个非零字节的偏移与值，由它判那条规则的输入是不是只能取 WP」。
报出来的是：偏移 0、值 `0xff`，且 WP 之上 67 076 096 字节 `distinct=1`（只有这一种字节值）。

⚠️ **判据 1 之外最值钱的一格是判据 5 顺带撞出来的对照**：
**同一台设备上，未写过的常规区读到的是全 `0x00`，而未写过的顺序区读到的是全 `0xff`**
（`crit5_conv_unwritten distinct=1 uniform_byte=0x00`）。
⇒ 「未写图样」在**一台设备内部**就不是同一个常量。

### 判据之外的两处，来自内核文档而不是本装置

跑完之后现查本机 `/home/fy5090/code/fs-refs/linux-6.17/Documentation/filesystems/zonefs.rst`，
两句与 D22（单元原子性怎么合成） 未定项 6 直接相干，逐字抄（**外部文档，未在本项目验证**）：

1. 第 236–242 行：「the partial failure of a multi-BIO large write operation will cause the zone
   write pointer to advance partially, even though the entire write operation will be reported as
   failed to the user」⇒ **WP 领先于提交点不必等崩溃**，一次被报为失败的大写就够。
2. 第 330–332 行：「the write pointer of read-only zones is defined as invalib by the ZBC and ZAC
   standards, making it impossible to discover the amount of data that has been written to the zone」
   （`invalib` 是上游原文的拼写，原样抄）⇒ **区一旦转成只读，WP 按标准就是无效的**。

⚠️ **外部标准那一条另查过一次**：2026-09-09 现查 NVMe ZNS 公开资料，
「reading in this area is handled the same way as when reading unwritten blocks」，
而读未写块的行为由 Identify Namespace 的 `DLFEAT` 选（全 0 / 全 1 / 不报告），
且 `NSFEAT` 有一位打开时控制器**可以对读未写块直接报错**（Deallocated or Unwritten Logical Block error）。
⇒ **「读 WP 之上一定成功、一定返回 0xff」不成立**，那是本装置的行为，不是标准的保证。
来源：nvmexpress.org 的 ZNS Command Set 规范与 zonedstorage.io，**未在本项目验证**。
