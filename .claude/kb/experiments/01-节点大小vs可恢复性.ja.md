## E1 ノードサイズ vs 回復性 —— 一部実行済み（爆発半径側は E29 (1ノード破損の爆発半径) で清算され、判定基準も同実験で是正；リカバリ時間側は未実行、checker は存在）

[中文](01-节点大小vs可恢复性.md) · [English](01-节点大小vs可恢复性.en.md) · **日本語**

**成果物**：爆発半径側の生出力は `e29-blast-radius-2026-08-29.out`、
再実行は `cargo run --release --bin e29_blast_radius`（本文は E29 (1ノード破損の爆発半径)）。
⚠️ **リカバリ時間側には成果物がない。一度も実行されていないためである**——前提条件は mkfs、checker、ピンポイント破壊ツール。


**背景**：大ノードは seek を節約し、ツリーをより浅くする（bcachefs は 128K–256K を使用）。
しかし、**破損ノード1つの再スキャンコストはノードサイズに比例して線形に拡大する**（E29 (1ノード破損の爆発半径) の実測：第1層ノードの再スキャン量はファンアウトに厳密に等しく、
2 KiB の 49 から 64 KiB の 1636 へ）、これは本プロジェクトの再構築性目標と直接衝突する。
⚠️ **拡大するのはリカバリ時間であり、永久損失ではない**——インデックスは派生態（D21 (権威態と派生態の境界)）であり、壊れても遅くなるだけである。
両面を計測しなければならず、片側だけを選んで論じてはならない。

**独立変数**：ノードサイズ 16K / 32K / 64K / 128K / 256K。

**何を測定するか**

| 指標 | 計測条件 |
|---|---|
| 単一ノード破損の爆発半径 | メタデータブロックをランダムに1つ破壊した後、**到達不能となったキー数**（バイト数ではない——バイト数はノードサイズ自体によって偏る）。算術版は既に E29 (1ノード破損の爆発半径) で提示されており、ここで求めるのは実イメージ上での再現である |
| **全ディスクスキャン再構築の再スキャンコスト** | K 個のノードを破壊した後、それらを再構築するためにスキャンしなければならないユニット数。**「成功率」は測定しない**——E29 (1ノード破損の爆発半径) の実測でインデックス側の永久損失は常に0であり、成功率の次元には判別力がない |
| **到達可能だが値が古いまたは誤っているキー数** | 再構築された keyspace をモデル（理想ファイルシステムの HashMap）とキーごとに照合し、**「到達不能」とは分けて2つの数値を報告する** |
| 検索コスト | 1回のポイント検索で読み出す平均ブロック数；ツリー高 |
| メタデータ総量 | 同一データセット下でのメタデータバイト数 |

**判定基準**：「**再スキャンコスト ≤ 目標ライン**」を前提として、検索コストが最も低いノードサイズを採用する
（2026-09-06 ユーザー決定、D8 (コアインデックス構造) 確定項目 4 の計測条件書き換えと同回）。
目標ラインはリカバリ時間予算であり、**事前に確定しておく必要がある**——この手順は実験結果が出るのを待って決定してはならない。
⚠️ **判定基準は「全ディスクスキャン再構築成功率 ≥ 目標ライン」ではない**：E29 (1ノード破損の爆発半径) の実測により
インデックス破損の永久損失は常に0 ⇒ 成功率はノードサイズに依存せず、これを判定基準としても上限を絞り込めない。

**何をもって失敗とするか**：各段階間で爆発半径に識別可能な差異がない場合、
破壊注入の方法が不適切であったことを意味する（例えばリーフのみを破壊した、または破壊箇所が参照されているノードに当たらなかったなど）。
**そのラウンド全体を無効としてやり直す**。「大体同じに見える」を結論にしてはならない。

⚠️ **「到達可能だが値が古い」列は飾りではなく、E1 (ノードサイズ vs 回復性) の判別力の欠落部である。**
純粋なルーティング用内部ノードを失った場合、失われるのはルーティングのみであり、リーフ自体がブロックヘッダを保持しているためスキャン再構築は**冪等**である；
しかし内部ノード内に他にコピーが存在しないデータ（例えばメッセージバッファ内の未フラッシュ更新など）が保存されていた場合、
それを失うことは**データ**の喪失を意味する。再構築されたツリーはブロックヘッダ、チェックサム、Merkle チェーンが整合し得て——
**I-1 (ブロック自己記述).x と I-2 (チェックサム).x は全緑であるにもかかわらず、内容は古いままとなる**。
[invariants/README.md](../../../crates/singlefs-checker/invariants/README.md) 内の既存の不変条件には、これを検出できるものは一つもない。
この列を追加しなければ、E1 (ノードサイズ vs 回復性) は「内部ノードにデータを保存する」類いの設計に対して見かけ上美しい再構築成功率を報告してしまい、
その数値は何の保証にもならない。

**前提条件**：D8 (コアインデックス構造) の確定、mkfs、checker、およびイメージをピンポイント破壊可能なツール。

⚠️ **「デバイス特性に応じてノードサイズを計算する」選択規則は出力しない**：D8 (コアインデックス構造) 確定項目 2 により
16 KiB は**定数として固定されている**——「フォーマット内では定数であり、数式ではない」。根拠は E20 (ポインタ肥大化によるCPUキャッシュコスト)
の曲線上で 8 KiB の異常値が6ラウンドにわたり安定しており誰も説明できなかったことである。
⇒ E1 (ノードサイズ vs 回復性) が出力すべきなのは**その定数の上限検証**である：リカバリ時間目標ラインの下で 16 KiB が成立するか否かであり、
デバイスからノードサイズを算出する計算式ではない。**テストでは例外なく値を明示的に固定し、自動値を使用してはならない。**
