### 要测什么、判据、失败条款

- **测什么**（三段，都不需要文件系统，纯算术与计数模型）：
  1. **上界之一，空间对照**：扫 `N ∈ {0, 16, 32, 64, 128, 256, 512}` × 单元 ∈ {4, 16, 64, 128} KiB，
     算每单元元数据字节数与占比，与 ext2 / ext4 / btrfs / ZFS 四行同口径对照。
     ⚠️ **两种记法都要报**：把扩展点**计入**「为管理一个单元而多付的字节」，和**不计入**（记为开线方净荷）。
  2. **上界之二，扇出与树高**：扩展点吃掉节点可用字节 ⇒ 扇出下降。
     按 E29（坏一个节点的爆炸半径） 的口径（1600 万叶、指针 40 字节）算每个 `N` 下的扇出与树高。
  3. **下界**：扩展点至少要放得下**一个合法指向 + 它的配额边界**，
     位置条目宽度由 D19（块指针的结构与宽度预算） 已定的字段独立算出（dev 1 + 物理偏移 6，加长度与边界描述）。
     小于这个值的 `N` ⇒ 扩展点在结构上放不下任何指向 ⇒ **该功能等于不存在**，而 D21（权威态与派生态的分界） 已定它的形态就是「放一个指向」。
- **判据**：三段各给一个边界，取**交集**。
  - **对照翻转点**：`N` 使本工程在 128 KiB 单元上的每单元元数据字节数超过 ZFS 的 128.0 B 或 btrfs 的 207.3 B ⇒
    D21（权威态与派生态的分界） 正文「本工程在 128 KiB 单元上比 ZFS 省、比 btrfs 省一半」那句话**不再成立**。
    ⇒ 要么把 `N` 收窄到翻转点以内，要么改写那句话并写明改的是哪种记法。
  - **树高**：`N` 不得使任一单元档的树高比 `N = 0` 时**多一层**。
  - **下界**：`N ≥` 第 3 段算出的最小可用值。
  - 三段的上界互相矛盾时**取最紧的那个**，并写明是哪一段在约束，**不许平均、不许挑宽的那个**。
- **阳性对照**（**四个单元档各跑一次，不是只跑第一档**）：每一档都把 `N` 抬到该档单元大小的一半，
  占比与扇出必须显著变化且等于独立算出的值——否则模型根本没在把扩展点算进去，**整轮作废**。
- **失败条款**：
  - 阳性对照测不出变化 ⇒ **实现有问题，整轮作废**。
  - 三段的交集为空 ⇒ **合法结果，如实记录**：结论是「这个数在现有口径下定不了」，
    要改的是口径或 D21（权威态与派生态的分界） 那句对照结论，**不许换一种记法把 128 坐实**。
  - 「全单元带」与「仅数据单元带」两档结论不同 ⇒ 如实记录两个，并把那个岔路退回 D21（权威态与派生态的分界）。
- ⚠️ **必须带绝对值断言**（这三段全是臂间比较，只互比测不出四条臂一起错）：
  - `N = 0` 档必须逐字复现 D21（权威态与派生态的分界） 对照表：158.0 B、4 KiB 3.857%、128 KiB 0.121%、4+2 条带 202.0 B（数值随对照表的现行口径走）。
  - `N = 0` 档的扇出必须等于 E29（坏一个节点的爆炸半径） 的 49 / 100 / 408 / 1636，树高必须等于 5 / 4 / 3 / 3。
  - 每个 `N` 的占比由 `(158 + N) / 单元字节数` 独立算出，**不许从被测代码读回来**。

### ⚠️ 它答不了的那一半

**「开线方到底需要多少字节」没有本机来源**——本工程今天一条开线方的线都没有。
E43（扩展点字节上限）只回答两件事：给定 `N`，代价是多少；`N` 至少要多大才不是摆设。
它**不回答**「`N` 够不够用」。⇒ 结论必须写成区间与条件式，
拿它去给 D21（权威态与派生态的分界） 已定项 2 定案时，那个条件要一起引用。
与 E40（密文校验和位宽） 同一形状：那里缺的是损坏率，这里缺的是需求。

### 实测（2026-08-30）

**判据换过一次。** 立项时E43（扩展点字节上限）拿「本工程比 ZFS / btrfs 省」当上界的来源，
而**「比谁省」不是本工程的判据**（用户定案 2026-08-30；
`.claude/rules/fs-design.md`「不为省空间牺牲自包含」同向，默认答案是不省）。
⇒ 由那条比较轴推出的上界（19 字节）**连同它的理由一起删**——
不是「循环论证所以作废」那么轻，**它引用的判据本工程根本不采纳**。

**剩下的边界，全部与省空间无关**：

| 边界 | 值 | 它把什么变成「挂不上」 |
|---|---|---|
| **结构上界**：净荷被挤成 0 | 4 KiB 单元 **3990**、128 KiB 单元 **130966**（2026-09-06 起按 105 字节单元头计）；索引节点还要留得下一个指针 ⇒ 2 KiB 节点 **1944**、64 KiB 节点 **65432** | 「放不下」，不是「浪费」 |
| **自证单元上界**：根槽与 journal 记录头没有带校验和的父指针，原子宽度 = 运行时探测的 `physical_block_size`（D20（承重面：单元的原子性与自包含） 推论三）| journal 记录头 311 字节落进 512 扇区后余 **201**（与 D23（journal 的角色与格式） 已定项 4 逐字相符；产物 `hdr=311 atomic=512 room=201`）；根槽那一档**给不出与机器无关的常数**（按候选槽宽 256 算出的 255 已作废，见E43（扩展点字节上限）局限） | 头顶不住一个原子宽度 ⇒ 撕裂判不了 |
| **撕裂隔离**：一个原子单元里只许有一个槽 | 候选槽宽 256 + 原子宽度 512 ⇒ 挤 **2** 个，4096 上挤 **16** 个；阳性对照把槽宽抬到 512 ⇒ 降到 **1** | 写一个槽可能撕裂邻槽（E34（根环槽几何） 主张一）|

⇒ **若自证单元也带扩展点，最紧的那条落在 journal 记录头上，而不是索引节点的 864**——
紧 4.3 倍（864 ÷ 201），理由与省空间无关。
⚠️ **E43（扩展点字节上限）第一轮对这一档零覆盖**：那一档建的是索引节点，不是根槽与 journal 记录头。

### 挂载时求值一次

**已定（2026-08-30，用户定案）：单元几何动态计算，但挂载时算一次，运行时只查不算。**

E43（扩展点字节上限）把「剩下的边界」表里结构上界、自证单元上界、撕裂隔离三条做成一个挂载时的判定函数，它**返回「挂得上 / 挂不上」，不返回「慢一点」**——
这是 `.claude/rules/fs-design.md`「能不能把『用错了』变成『挂不上』」在本项上的形态。
输入全部是**操作期间不会变的量**（系统配置里声明的 N、格式里的单元与节点大小、
探测到的 `physical_block_size`），满足同一份规则「分支变量不许在操作中途改变」。
实测四条拒绝理由**都够得到**：净荷为 0 ／ 节点放不下一个指针 ／
一个原子单元里不止一个槽 ／ 自证单元的头顶不住一个原子宽度。

⚠️ **它的代价要写下来**：同一份声明（槽宽 512）在 512 字节原子宽度的设备上判 `ok`，
在 4Kn 设备上判 `reject_slot_shares_atomic`。
⇒ **镜像的可挂载性依赖它当前插在哪台机器上。** 这不是缺陷——拒绝挂载正是安全的失败模式——
但必须写下来，因为「换台机器就挂不上」在现场看起来像故障。
