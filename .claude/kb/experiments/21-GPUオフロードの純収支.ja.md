## E21 GPUオフロードの純収支 —— 3段すべて測定済み (2026-08-28)；純スキャンセルは負の収支と判定、候補3セルは保留とし計画見送り

[中文](21-GPU卸载的净收益.md) · [English](21-net-benefit-of-gpu-offloading.en.md) · **日本語**

### 実行済みの2段階、およびそれら単独で何を判定排除できるか

**判定基準 1 は `CPU 16スレッド所要時間 ÷ (転送 + 計算 + 転送戻し) 所要時間` であり、1 未満であればそのセルを否決する。**
⇒ **たとえカーネル実行時間がゼロであったとしても**、GPU パスは最低限転送コストを支払わなければならない。その区間が GPU 側の**下限**であり、
CPU のメモリ帯域幅が CPU 側の**上限**となる。両者を比較することで、カーネルを書き上げる前であっても一部を判定・排除できる。

| パス | スループット | 性質 |
|---|---|---|
| CPU スキャン (XOR 畳み込み、2 GiB、5ラウンドの最良値) | **64.91 GB/s** | メモリ帯域の壁、CPU 側の**上限** |
| GPU 片道 (ページロック H2D、≥64 MiB) | 56.69 GB/s | 転送の**下限** |
| GPU 往復 (H2D + D2H 直列) | **28.5 GB/s** | 転送の**下限** |

**⇒ 判定基準：GPU は「CPU 側の実際のスループットが GPU の転送下限を下回る」場合にのみ勝利し得る。**

| シナリオ | 返却データ | GPU 下限 | CPU 側がどの程度遅ければ GPU に勝機があるか |
|---|---|---|---|
| 全ディスク scrub | 1つの結論のみ返却 | 56.7 GB/s | < 56.7 GB/s |
| バッチ圧縮 | 圧縮後データ (入力より小さい) | 40.6 GB/s (圧縮比 0.5) / 47.6 (0.25) | < その数値 |
| **EC 再構築** | **再構築データ全体** | **28.5 GB/s** | **< 28.5 GB/s** |

**[experiments.md](../experiments.md) E6 (暗号化アルゴリズム選定) のマルチコア飽和実測値を代入**：AES-NI 有効時、
**8スレッドで 17.4 GB/s に飽和** (16 / 32スレッドで 16.3 / 16.5、E6 (暗号化アルゴリズム選定) 2026-08-28 マルチコア層)
⇒ **GPU の2つの下限 (往復 28.5、片道 50.3) を下回り、GPU の勝利**；
AES-NI なし時はマルチコア未測定、単一コア 0.257 GB/s (244.74 MiB/s、2026-08-31 再測定)、飽和値はさらに低下するのみ
⇒ **28.5 GB/s を大幅に下回り、GPU の大勝**。

⚠️ **代入する数値はマルチコア飽和実測値でなければならず、「単一コア × コア数」を用いてはならない。** 同一の測定量において、線形外挿は ≈61 GB/s
(3.83 GB/s × 16) を与えるが、実測飽和値は **17.4 GB/s** である——約4倍の乖離があり**しかも方向が逆**である：外挿では「AES-NI あり ⇒ GPU 敗北」と導かれるが、
実測では GPU の勝利となる。

⇒ **判定基準となるのは CPU 側のマルチコア飽和スループット**であり、GPU がどれほど高速であるかにも、CPU に対処するハードウェア命令が存在するか否かにも依存しない：
AES-NI を備えた AES-GCM であっても 17.4 GB/s で飽和し、**ハードウェア命令の存在 ≠ GPU が追いつけないほど高速**、である。
実機で GPU 下限を上回ることが実測された唯一の処理は**純スキャン** (XOR 畳み込み 64.91 GB/s、メモリ帯域の壁に衝突) のみである。

⚠️ **「実行済みの2段階、およびそれら単独で何を判定排除できるか」は単独では必要条件にすぎない。** 計算段とエンドツーエンドについては「計算段」および「判定基準 1 の回答」の2節を参照。

### 計算段：nvcc なしでも上界の測定が可能であり、ほぼ無料

scrub / EC / 圧縮の内側ループはいずれも**帯域律速**であり、帯域律速カーネルの天井は VRAM 帯域幅である——
そしてそれは既存のビット演算子を用いて測定可能である。測定されるのは**カーネルの上界**である (実カーネルはこれより遅くなるのみ)。

| 区間 | スループット | エンドツーエンドに占める割合 |
|---|---|---|
| 計算 (VRAM 内排他的論理和畳み込み、読み取り＋書き込み各1回) | **1041.3 GB/s** | 9.7% |
| **エンドツーエンド (ページロック主メモリ → VRAM → 計算、転送戻しなし)** | **50.3 GB/s** | — |
| うち転送 | — | **90.3%** |

陽性対照：転送込みは純計算より大幅に遅くなければならない (要件 >3×)、実測 **10.3×**、合格。
⚠️ この差異が測定されない場合はほぼ確実に**同期漏れ**である——`torch.cuda.synchronize()` が抜けている場合、
測定されるのは非同期起動となり、数値が1桁過大に良くなってしまう。

⇒ **GPU パスのコストは転送であり、計算段はほぼ無料である。**

### 判定基準 1 の回答：純スキャンセルは負の収支であり、直ちに否決

E21 (GPUオフロードの純収支) の判定基準 1 は `CPU 16スレッド所要時間 ÷ (転送 + 計算 + 転送戻し) 所要時間` であり、**1 未満であればそのセルを否決する**。

| | スループット | 純収支 |
|---|---|---|
| CPU (メモリ帯域の壁) | 64.91 GB/s | — |
| GPU エンドツーエンド (片道、実測) | **50.3 GB/s** | **0.78×** |

⇒ **CPU 側がメモリ帯域の壁に衝突するセル (純スキャン、64.91 GB/s) において、GPU オフロードは負の収支であり、否決する。**
これはもはや推論ではない——エンドツーエンドの双方の数値が実測されている。

⚠️ **純スキャンは [decisions.md](../decisions.md) D24 (バックグラウンド重処理の GPU オフロード要否) の3つの候補シナリオのいずれでもない**：
scrub のチェックサム / EC 再構築 / バッチ圧縮の CPU 側はいずれもスキャンの上に追加の計算を要し、実測された暗号化セルは 17.4 GB/s にすぎず
⇒ 2つの下限を下回る。**0.78× という負の収支が排除したのは、候補リストに含まれていないシナリオである。**

**⇒ 閾値もこれに伴い明確化された：CPU 側のスループットが 50.3 GB/s (片道シナリオ) を下回る場合に初めて GPU が勝ち始める。**
[experiments.md](../experiments.md) E6 (暗号化アルゴリズム選定) のマルチコア飽和実測値を代入：AES-NI ありで **17.4 GB/s** ⇒ 勝利；
AES-NI なし時はマルチコア未測定、単一コア 0.257 GB/s であり飽和値は下がるのみ ⇒ 勝利、その差は1桁に達する。

### GPU は確かに動作している：3つの独立した根拠 (2026-08-28 補足根拠)

**発端は妥当な疑問であった**：傍らで `nvidia-smi` を監視したところ、5090 が **11 W** と表示され、「GPU カードが全く動いていない」と判定された。
疑問は成立するが結論は成立しない——双方の事実はともに真である：

| 時点 | 消費電力 | 使用率 | SM クロック |
|---|---|---|---|
| ベンチマーク間の待機時 | **11.67 W** | 0% | 195 MHz |
| **10秒間の連続実行** (35回サンプリング) | **352 W** (ピーク 353) | **100%** | **2857 MHz** |
| 実行直後 | 74.5 W | 0% | 570 MHz |

3つの独立した根拠があり、いずれか1つ単独でも十分である：

1. **使用率の対照**：無負荷2秒間の中央値 **0%**、全負荷6秒間の中央値 **100%**。
2. **消費電力**：11.67 W → **352 W**。
3. **物理的不可能性**：同一の `bitwise_xor` が CPU 上で **35.6 GB/s**、GPU 上で **1037.3 GB/s**、
   **29.1×**。実機メモリ帯域幅の実測上限は **64.91 GB/s** であり——CPU が 1037 を出すことは不可能。

⚠️ **この教訓は数値よりも重要である：ミリ秒単位でしか走行しないベンチマークは、外部から走行の有無を判別できない。**
E21 (GPUオフロードの純収支) の以前の測定では、GPU が稼働していたのはそれぞれ 2.06 ms (計算段) から 21.3 ms (転送込み) にすぎず、各5ラウンドで、
合計しても 0.2 秒未満であった；一方で `nvidia-smi` は秒単位サンプリングであり、消費電力にも遅延が存在する
⇒ **どの瞬間に確認しても、ほぼ必然的に無負荷に見える**。
これは `.claude/singlefs-ai-sop/rules/test-discipline.md` の
「陰性結果は『コードが走行しなかった』ことと明確に区別できなければならない」に直結する——**「このパスを実行した」と主張するためには、実際に実行されたことを証明する測定値が必要であり**、
ミリ秒級のベンチマーク単独ではその測定値を提供できない。
⇒ **対策**：GPU 系のベンチマークは、使用率・消費電力を同時に採取するか、実在の証明として十分な長さの連続負荷を別途実行する。
スクリプト `scripts/experiment-apparatus/e21-prove-gpu.py`。

### さらに上位の制約：これら3シナリオはいずれもディスク律速

3つの候補シナリオ (scrub / EC 再構築 / バッチ圧縮) はいずれも**全ディスク I/O 集中型のバックグラウンド処理**である。
データはまずディスクから読み出さねばならず、ディスク帯域幅は 64.91 (CPU メモリ帯域幅) や 28.5 (GPU 往復) よりはるかに低い。
⇒ **処理全体がディスク律速であるならば、CPU は元々遊休状態にあり、計算を GPU にオフロードしても何も節約できない**——
CPU がディスクよりも遅いほど極端に遅い場合を除き、そしてそれは「ハードウェア命令の有無」という論点に戻る。

⚠️ **この層は推論であり実測ではない**：本プロジェクトにはディスクアレイ環境がなく、ディスク帯域幅は測定されていない。
⚠️ **未検証の抜け穴がもう1つ存在する**：GPUDirect Storage により NVMe から VRAM へ直接 DMA を行い、
ホストメモリと PCIe ホップを回避する場合、**「GPU のデータ取り込み 56.69 GB/s」という転送下限は覆される**。未測定であり、存在しないものとして扱ってはならない。

### 実カーネルは未作成だが、本セルの判定にはもはや影響しない

**実機には2枚の GPU カード (RTX 5090 32 GiB / RTX 5060 Ti 16 GiB、ドライバ 595.84) があるが、`nvcc` が存在しない。**
⇒ 実カーネルをコンパイルできない。しかし帯域律速演算子による**上界**は計算段が 9.7% しか占めないことを既に示しており、
⇒ 実カーネルがどれほど遅くとも GPU 側をさらに悪化させるのみであり、**判定が覆ることはない**。
⚠️ この推論は**帯域律速**のカーネルにのみ成立する。圧縮のような**計算力律速**のカーネルはこの限りではなく、
その計算段は 9.7% をはるかに超える可能性があり、**そのセルは依然としてツールチェーン待ちである**。
⚠️ **E21 (GPUオフロードの純収支) で 2026-08-28 以前に記録されていた「前提条件なし」は誤りであり**、圧縮セルの前提条件こそがこのツールチェーンである。

⚠️ 5060 Ti は当時約 1 GiB の空きしか残っておらず (ローカル推論サービスが占有)、**08-28 のラウンドでは 5090 のみを使用**、
スクリプトは空き VRAM が 3 GiB 未満の場合に直ちに実行を拒絶する——他者のサービスを圧迫する価値はない。

### 2つの陽性対照、および第2の対照が2度の修正を経て成立した経緯

| 対照 | アサーション | 結果 |
|---|---|---|
| GPU 転送 | ページロックメモリはページ可能メモリより明らかに高速でなければならない (ページ可能はステージングコピーが1回余分に必要) | **2.05×** (56.69 vs 27.63)、合格 |
| CPU スキャン | **計算力律速のアームを別途設け**、16スレッドでほぼ線形にスケールしなければならない | **15.30×**、合格 |

⚠️ **CPU 側の対照は2回誤って記述されたが、2回とも対照自体の誤りであり実機の問題ではない**：

1. 初版では**被測定アーム自身**を対照とし、「16スレッドで2倍高速」を要求した。しかし XOR 畳み込みは**帯域律速**であり、
   単一スレッドですでに 54.12 GB/s に達し2スレッドで壁に衝突するため、**そもそも線形スケールするはずがない**。
   実測 1.16× ⇒ 正当な結果が harness の破損と誤判定された。
   **`.claude/singlefs-ai-sop/rules/test-discipline.md` に明記されている通り、陽性対照には「効果が確実に存在するベースライン」を用いるべきであり**、
   被測定アーム自身を用いてはならない。
2. 第2版では計算力律速アームを別途設けたが、**各**スレッドに同数の反復を実行させた ⇒ 総仕事量がスレッド数に伴って増加し、
   それはウィークスケーリングであり完全並列時に所要時間は同等、比率 ≈ 1 となり、実測 0.96 で再び並列化失敗と誤判定された。
   **総仕事量を固定しスレッド間で均等配分**するように改修した後、15.30× となった。

⇒ **教訓：陽性対照の失敗に遭遇した場合、まず対照の仕様を疑い、次に実機を疑うこと。** 2回とも仕様の誤りであった。

### ⚠️ 言語間比較の単位を以前は何も固定していなかった (2026-08-29 対抗検証による補完)

E21 (GPUオフロードの純収支) の判定は**言語間の比率**である：CPU 側の 64.91 GB/s は Rust (`e21_cpu.rs`) 由来、
GPU 側の 50.3 / 56.69 / 28.5 GB/s は Python (`e21-transfer.py`) 由来である。
**双方はともに10進数 1e9 を使用している** (Rust `bytes / ns`、Python `gb = n / 1e9`)——
確認の結果整合していることが判明したが、**それまでこの事実を固定するアサーションは存在しなかった**。
⇒ いずれか片方を GiB (2³⁰) に変更すると比率が **7.4%** ずれ、
[decisions.md](../decisions.md) D24 (バックグラウンド重処理の GPU オフロード要否) の判定はまさにこのオーダーに乗っている
(0.78× という純収支は 1.0 からわずか 22% しか離れていない)。

⚠️ **これは「相互比較だけでは共倒れの誤りを検出できない」複数実験横断の形態である**：両側の単位を同時に変更しても比率は依然として「成立」してしまう。
E21 (GPUオフロードの純収支) の2つの単体テストが固定しているのは「畳み込みと順序が無関係であること」「チャンキングが完全な分割であること」であり、**いずれも構造的性質である**。

絶対値アサーション `throughput_unit_is_decimal_gigabytes_per_second` を追加：
`decimal_gigabytes_per_second(10⁹ バイト, 10⁹ ナノ秒) == 1.0` であり、`2 GiB / 1 s` は 2.0 ではなく **2.147…** と算出されなければならない。
ミューテーション表は `scripts/mutation/tables/e21_cpu.tsv` に保存され、3つのミューテーション (GiB 計測条件への変更、floor チャンキング、末尾チャンク切り捨て漏れ) はすべて検出・殺傷された。

### 計測条件とコード

GPU 転送段：`scripts/experiment-apparatus/e21-transfer.py` (torch 2.11.0+cu130)、各段階で初回破棄ラウンドを実行 (CUDA コンテキスト構築)、
**各計測の前後に `torch.cuda.synchronize()` を実施**——非同期の測定は転送ではなく非同期起動を測定してしまい、数値が1桁過大に良くなってしまう。
N=5 の中央値を取得。
CPU：`scripts/experiment-apparatus/e21_cpu.rs`、`cargo run --release --bin e21-cpu -- 2048 5`、
2 GiB バッファ、5ラウンドの最良値；4つの単体テスト、3つのミューテーションが赤になることを1つずつ実証
(うち1つのミューテーションにより、単体テストが**プロダクションパスを通らずにチャンキングロジックを独自再実装していた**ことが判明、共通関数へ抽出済み)。
出力 `e21-cpu-2026-08-28.out`。
GPU 計算段：`scripts/experiment-apparatus/e21-compute.py` (VRAM 内排他的論理和畳み込み ＋ 転送込み同一演算子 ＋ 陽性対照)、
「計算段」節の 1041.3 GB/s、50.3 GB/s、9.7%、および陽性対照 10.3× はすべてこれによる；
⚠️ **その生出力は保存されておらず**、これらの数値は本スクリプトの再実行によってのみ再確認可能 (実機に CUDA と ≥ 4 GiB の空き VRAM が必要であり、スクリプト自身が条件不適合のマシンを拒否する)。

**背景**：[decisions.md](../decisions.md) D24 (バックグラウンド重処理の GPU オフロード要否)。3つの候補シナリオ (バッチ圧縮、全ディスク scrub、EC 再構築) は
すべて `.claude/rules/fs-design.md` 第3セル (バックグラウンド、再開可能、非決定パス、戒律なし) に属し、
したがって GPU の導入は確定済みの規律に違反しない；しかし**利益に関する数値は皆無であった**。

**独立変数**：タスク (チェックサム / AEAD / Reed-Solomon 符号化・復号 / 圧縮) × バッチサイズ (1 MiB … 4 GiB)
× 実行場所 (CPU 単一コア / CPU 16スレッド / GPU) × データがすでに VRAM に存在するか否か。

**何を測定するか** (**3段は個別に報告しなければならず、1つの「GPU は N 倍高速」に統合しては意味をなさない**)：

| 区間 | 計測条件 |
|---|---|
| **転送**：ホスト → VRAM | GB/s、固定オーバーヘッド含む |
| **計算**：カーネル自体 | GB/s |
| **転送戻し**：VRAM → ホスト | GB/s (scrub は判定結果1点のみ返却、EC 再構築は全再構築データを返却、両者には巨大な差異) |

**判定基準**：

1. **エンドツーエンド純収支**：`CPU 16スレッド所要時間 ÷ (転送 + 計算 + 転送戻し) 所要時間`。
   **1 未満は負の収支**であり、そのセルは直ちに否決。
2. **バッチサイズに伴う収支曲線がどこで 1 を超えるか**——そのバッチサイズが GPU 有効化の閾値となり、
   明示的に計算可能でなければならない (`.claude/rules/fs-design.md` ハード要件 1)。
3. **転送戻し量の影響**：scrub は1つの判定のみ返却、EC 再構築はバッチデータ全体を返却。
   両者の曲線形状は完全に異なると予想され、**個別に報告しなければならず、1つの数値で総括してはならない**。

**何をもって失敗とするか**：
- GPU 計算段自体が CPU 16スレッドより速くない場合、**転送段を検証するまでもなく**、当該タスクは直ちに否決。
- 各バッチサイズにおける純収支がすべて ±10% 以内に収まる場合、PCIe 帯域幅で固定されていないか確認し、
  **その種のタスクがオフロードに適さないことを示す正当な結果として、ありのまま記録する**。
- ⚠️ **陽性対照**：GPU に極めて適していることが判明しているタスク (巨大行列乗算など) を同一パイプラインで実行し、
  顕著な高速化を示す必要がある。測定されない場合 ⇒ 環境または harness の欠陥であり、**ラウンド全体を無効化**——
  「高速化なし」をタスクの結論として記録してはならない。

**実機** (2026-08-28 実測確認)：NVIDIA RTX 5090 (32 GB) + RTX 5060 Ti (16 GB)、ドライバ 595.84。
⚠️ **2枚の GPU カードの型番が異なるため、ベンチマーク実行時はどちらを使用するか固定し計測条件に記録すること。**

**前提条件**：なし。ただし CUDA ツールチェーンが必要であり、`.claude/scripts/env.sh` は現時点でそれを検査していない。
