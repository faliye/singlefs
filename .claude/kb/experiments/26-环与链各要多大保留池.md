## E26 环与链各要多大保留池 —— 已跑（2026-08-29）

**还 [checks-owed.md](../checks-owed.md) C30（链式保留池量化未验）。**
[decisions.md](../decisions.md) D23（journal 的角色与格式）判「取定长环」时用过一条量化——
链式下保留池要从 `ckpt_cost` 涨到 `ckpt_cost + 一个 checkpoint 窗口内的 journal 块`。
**那条是算出来的，没验过。** E26（环与链各要多大保留池）把它做成可执行模型并逐档扫描。

### 结论：卡死恰好在预测的那一档归零，两条臂各自对上

容量 10 万块、2 万次操作、每 100 次一个 checkpoint、`ckpt_cost = 64`、每次操作 1 块
⇒ 一个窗口的 journal 块 = 100。起始占用 99%。

| reserve | 环的 checkpoint 卡死 | 链的 checkpoint 卡死 |
|---|---|---|
| 0 / 32 | 95 | 120 |
| **64** | **0** | 120 |
| 100 / 128 | 0 | 120 |
| **164** | 0 | **0** |
| 256 / 512 | 0 | 0 |

⇒ **环在 `reserve = 64` 归零**（= `ckpt_cost`）；
**链在 `reserve = 164` 归零**（= `ckpt_cost + 窗口 journal 块 = 64 + 100`）。
逐位对上 D23（journal 的角色与格式）算出来的那个式子。

**阴性对照**：起始占用 95%（自由空间 5000 块）时**两条臂全不卡，任何 reserve 都不卡**
⇒ 效应确实来自空间紧张，不是建模伪影。

### 一条对 E19（defer 窗口下的假性 ENOSPC）结论的收窄

E19（defer 窗口下的假性 ENOSPC）写过「保留池对普通分配是纯税」。
**那句话有一个隐含前提：保留池已经大到不卡死。前提之外它的符号是反的。**

| 区间 | reserve | 普通分配被拒次数 |
|---|---|---|
| 卡死区间 | 0 | **9340** |
| 不卡死区间 | 64 | 756 |
| 不卡死区间 | 512 | 1204 |

卡死之后空间根本不回收，拒绝数被卡死支配 ⇒ **小保留池反而拒绝得更多**。
这一条是E26（环与链各要多大保留池）的测试第一版写错时当场暴露的（原断言是「保留池越大拒绝越多」，
拿 0 与 512 比，结果反了）。两个区间现在各有一条钉死的测试。

### 口径与已知局限

- 纯计数模型，无设备、无文件系统。**必须有每窗口的净泄漏**（模型取 8 块），
  否则 checkpoint 把消耗的空间全数还回去、free 永远回到起点，实验测不到任何东西——
  首版就是这样，六个测试里三个红。泄漏本身是真实的：
  D16（发布语义）已定「checkpoint 内的释放在发布前不得进入可分配集合」，
  加上 D22（单元原子性怎么合成）的根环 K 代扣住。
- **没有建模假性 ENOSPC**，只建模了 checkpoint 卡死与普通分配被拒。
  两者的分治见 E19（defer 窗口下的假性 ENOSPC）。
- 代码 `research/e7-index-bench/src/bin/e26_journal_reserve.rs`（`cargo run --release --bin e26_journal_reserve`），
  原始输出 `research/results/e26-journal-reserve-2026-08-29.out`。三轮字节一致。

**工程质量**：7 个单测，**7 条变异全部被抓**，三轮字节一致。
