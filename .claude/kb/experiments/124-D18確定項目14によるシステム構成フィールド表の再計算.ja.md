## E124 D18 確定項目 14 によるシステム構成フィールド表の再計算 —— 実施済（2026-09-09、純算術、12 単体テスト / 14 ミューテーション全捕捉）：**nonce 水位は 8 バイトではなく 12 バイトを要し、E115 (システム構成フィールド表の完全性とバイト予算) の 4 マスの数値はそれぞれ +4；合成アームは新水位下でも 512 上で 4 マスすべてに収まる；デバイス表が Code 3 コンテナを採用する場合スロット内の `devs` の 4 バイトは省略可能であり、水位の 4 バイトをちょうど相殺する**

[中文](124-系统配置字段表按已定项14重算.md) · [English](124-system-config-field-table-recomputed-per-d18-settled-item-14.en.md) · **日本語**

**答える対象は D22 (ユニット原子性の合成手法) 確定項目 9（システム構成のフィールド表）** の 2026-09-08 レビューで残された勘定である。同段落は「D18（ブロックに含める情報） 14 条すべて確定」の後に逐字的にこう記述している：
「**確定項目 14（nonce 記号は完全な 96 ビット nonce でありユニット平文ヘッダに存在）がブロッキング条項 ② のマスの入力を変更した** ——
E115 (システム構成フィールド表の完全性とバイト予算) が D9（暗号化） の 3 項目に採用したのは最小利用可能仮定値であり、これに従って再計算する必要がある。」

**さらに E115 (システム構成フィールド表の完全性とバイト予算) が問わなかった 1 点を追加**：その 31 項目の必須項目のうち第 30 項目
「デバイス数 `devs`」の出典は逐字的に「D22（ユニット原子性の合成手法） 確定項目 2『P > devs』；デバイス表をスロット外に移管した後にエントリ数が残存しない」である ——
しかしデバイス表ユニットが Code 3 パックレコードコンテナを採用する場合、コンテナヘッダ内にもともとレコード数が存在する。**その 4 バイトが省略可能か否かは、リポジトリ内で問われたことがなかった。**

### 判定基準（実施前確定、実施後変更不可）

1. **nonce 水位再計算ゲート**：D18 (ブロックに含める情報) 確定項目 14 の 96 ビット nonce に従い、I-6.5（nonce 水位単調） が要求する水位幅はいくつか？**絶対値を報告**し、E100 (システム構成の3段幾何) / E115 (システム構成フィールド表の完全性とバイト予算) で使用された 8 バイトとの差分バイト数を報告する。差分を予算に算入後、**512 / 4096 の 2 段階で「収まる / 何バイト溢れるか / 断裂状態数」をマスごとに絶対値で再報告**する。
2. **`devs` 冗長性の 2 本のアーム**：アーム甲はデバイス表ユニットに **Code 3 パックレコードコンテナ**を採用（ヘッダ内オフセット 69 にレコード数 2 バイトあり）⇒ スロット内の `devs` は省略可能；アーム乙は **Code 2 インデックスノードクラス**を採用（ヘッダ内にレコード数なし）⇒ 省略不能。**両アームそれぞれのスロットの絶対バイト数を報告**し、差分のみの報告は禁止。⚠️ **両アームとも実行必須**（`.claude/singlefs-ai-sop/rules/test-discipline.md`「陽性対照はテストされるすべてのアームに対して実行しなければならない」）。
3. **新入力下での合成アーム再計算**：デバイス表 / ツリーテーブル / マスター鍵スロット / 中央マッピングの 4 本の間接ポインタを単一の間接ディレクトリユニットに合成し、スロット内には 1 ポインタのみ残す形態について、4 マス（`wide` × `map_sep`）それぞれの絶対バイト数と断裂状態数を報告する。
4. **装置間照合**：E124 (D18 確定項目 14 によるシステム構成フィールド表の再計算) 自身のコードを用いて E115 (システム構成フィールド表の完全性とバイト予算) の `candidate_bytes` と `plus_devtable_ptr` を再計算し、2 つの数値は E115 (システム構成フィールド表の完全性とバイト予算) 成果物と逐字一致しなければならない（361 / 420）。不一致の場合は不合格と判定。これは `.claude/singlefs-ai-sop/rules/show-me-test.md`「2 つの装置が同一の量を計算する場合、それらを同一の数値に落とし込む検査を設けなければならない」の形態である。
5. **絶対値アサート**：判定基準 1/2/3 の各結論について絶対値を固定するアサートを持つこと、アーム間相互比較のみは禁止（`.claude/singlefs-ai-sop/rules/test-discipline.md`「複数アームの相互比較のみでは全アーム同時の誤りを検出できない」）。

### 失敗条件（実施前確定）

| 条件 | 発動時の判定 |

### 実測（2026-09-09、純算術、12 単体テスト / 14 ミューテーション全捕捉）

**計測条件と再実行**：コード `scripts/experiment-apparatus/e124_system_configuration_recompute.rs`、成果物 `research/results/e124-system-configuration-recompute-2026-09-09.out`（41 行、終端 `emitted=41`）、ミューテーション表 `scripts/mutation/tables/e124_system_configuration_recompute.tsv`、`scripts/experiment-apparatus/replay.sh` に配線済。
再実行：

```bash
bash scripts/experiment-apparatus/replay.sh E124     # research/results/e124-system-configuration-recompute-2026-09-09.out と 1 バイトずつ照合
```

⚠️ **純算術は決定的であり、複数回実行は隠蔽された状態が存在しないことを示すものであって、統計的安定性を示すものではない**。
根拠の強度はミューテーションテストと絶対値を固定したアサートに由来し、試行回数には由来しない。

#### 判定基準 1：nonce 水位は 12 バイトを要し、E100 / E115 で使用された 8 は 4 不足

成果物先頭 2 行の逐字記録：

```
name=watermark_gate decided_nonce_bits=96 required_bytes=12 e100_used=8 consistent=0 short_by=4
name=watermark_gate_control fed=12 consistent=1 short_by=0
```

⇒ **I-6.5（nonce 水位単調） は「記録された nonce 水位 > 全ディスクに出現した最大 nonce」を要求し、
D18 (ブロックに含める情報) 確定項目 14 以後その nonce は完全な 96 ビットである** ⇒ 水位は少なくとも 12 バイトを要する。
E100 (システム構成の3段幾何) ソース内のその行は逐字的に `("nonce_watermark", 8)` であり、64 ビットしか表現できなかった。
⚠️ **8 バイトは確定項目 14 以前には誤りではなかった** —— 当時平文ヘッダに存在したのは nonce **記号**であり、水位は記号に対する水位であった；
確定項目 14 が記号と nonce を同一の量に統合したことで、このマスの入力が変更されたのである。

⚠️ **これは「E100 / E115 のアサートの記述誤り」ではない**：両者とも水位がどれほどの幅を持つべきか述べるアサートを持っておらず、
当時の候補表をそのまま書き写しただけであった。**確定項目 14 確定時にこのマスに注意を促すものは何も存在しなかった** ——
同型の未済の検査が C178 (システム構成の必須フィールド表が手写しに依存) に記録されている。

#### 判定基準 1 の下流：E115 の 4 マスがそれぞれ +4

E115 (システム構成フィールド表の完全性とバイト予算) と同一の計測条件（スロット内に `devs` を含む、すなわち `dev_unit=code2_index`）でマスごとに再計算：

| wide | map_sep | ポインタ合成 | E115 (システム構成フィールド表の完全性とバイト予算) 逐字 | E124 (D18 確定項目 14 によるシステム構成フィールド表の再計算) 再計算 | 512 スロット |
|---|---|---|---|---|---|
| 0 | 0 | 否 | 503 | **507** | 収まる（余剰 5、元は余剰 9） |
| 0 | 1 | 否 | 562 | **566** | 溢れ 54（元は 50） |
| 1 | 0 | 否 | 532 | **536** | 溢れ 24（元は 20） |
| 1 | 1 | 否 | 591 | **595** | 溢れ 83（元は 79） |
| 0 | 任意 | **是** | 385 | **389** | 収まる |
| 1 | 任意 | **是** | 473 | **477** | 収まる |

4096 バイトスロット上では 16 マスすべてが収まり、断裂状態数は常に 0（単体テスト `negative_control_4096_always_fits` に固定、
成功メッセージは「計 16 マス検査完了」と報告）。

⇒ **E115 (システム構成フィールド表の完全性とバイト予算) の判定方向は一字一句変更なし**：合成アームは依然としてすべての計測条件において 512 バイトセクタに収まる唯一の形態である。
**変化したのは余白である**：非合成のマスは「余剰 9」から「余剰 5」へ縮小した。

#### 判定基準 2：デバイス表が Code 3 コンテナを採用する場合、スロット内の `devs` は 4 バイト節約可能

E115 (システム構成フィールド表の完全性とバイト予算) 必須項目表の第 30 項目の出典は逐字的に
「D22（ユニット原子性の合成手法） 確定項目 2『P > devs』；デバイス表をスロット外に移管した後にエントリ数が残存しない」である。
**後半部分はデバイス表ユニット自体がエントリ数を保持しない場合にのみ成立する。** D18 (ブロックに含める情報) 確定項目 11 の Code 3 パックレコードコンテナのフィールド表において、
オフセット 69 の行は逐字的に `| 69 | レコード数 | 2 | ≤ 583 |` である；Code 2 インデックスノードクラスのクラス識別セグメントにはこの項目が存在しない。

成果物の逐字記録：

```
name=devs_arm wide=0 code3=385 code2=389 saved=4 record_count_bytes=2
name=devs_arm wide=1 code3=473 code2=477 saved=4 record_count_bytes=2
```

⇒ **両アームの差は 4 バイト**であり、水位引き上げも 4 バイトである ⇒ **Code 3 アーム上では互いに相殺し合い、スロットの総バイト数は E115 の数値に戻る**
（`dev_unit=code3_packed wide=0 map_sep=0 merge_ptrs=0 total=503`、E115 (システム構成フィールド表の完全性とバイト予算) と逐字一致）。
⚠️ **これは単に「4 バイト節約できた」という小さな事象ではない**：`devs` がスロットに入るか否かは**デバイス表ユニットがどのコードを採用するかに依存する**ことを示しており、
**そのマスはリポジトリ内で未確定であった** —— E124 (D18 確定項目 14 によるシステム構成フィールド表の再計算) は失敗条件に従い両アームをそれぞれ 1 回計算するのみにとどめ、リポジトリの代わりに選定はしない。
新たな空白として立項し、[checks-owed.md](../checks-owed.md) に記録。

#### 判定基準 3：合成アーム

成果物 3 行の逐字記録：

```
name=merge_cost unit_header=68 saved_in_slot=177 paid_in_unit=68
name=merge_cost unit_header=77 saved_in_slot=177 paid_in_unit=77
name=merge_cost unit_header=86 saved_in_slot=177 paid_in_unit=86
```

スロット内で `3 × 59 = 177` 節約、新設間接段は D18 (ブロックに含める情報) 確定項目 7 の 3 段階ヘッダ計算に基づき最悪 86 を支払う ⇒ **正味 91 節約**、
E115 (システム構成フィールド表の完全性とバイト予算) と同一値。

#### 判定基準 4：装置間照合

成果物最終行の逐字記録：

```
name=e115_reconcile rows=24 candidate_bytes=361 plus_devtable_ptr=420 missing_narrow=83 missing_wide=112
```

4 つの数値は E115 (システム構成フィールド表の完全性とバイト予算) / E100 (システム構成の3段幾何) 本文と逐字一致。
⚠️ **照合は自己検証ではない**：E124 (D18 確定項目 14 によるシステム構成フィールド表の再計算) は候補表を 23 行の定数表 + 1 つの水位パラメータに分解しており、361 は**加算により得られたもの**であってハードコードではない；
いずれかの行の幅を変更すると（ミューテーション M12）直ちに不合格と判定される。

### 本実験で答えられないこと

純算術：mkfs なし、マウントなし、実デバイスなし、ファイル操作 0 箇所。
**「これらのフィールドそれぞれがどれほどの幅を持つべきか」には答えない** —— それぞれ個別の単独決定を要する；E124 (D18 確定項目 14 によるシステム構成フィールド表の再計算) は確定条項に基づき既存の仮定値を再計算するのみである。
**完全性ゲート自体が項目を見落とすか否かにも答えない** —— その必須項目表は依然として E115 (システム構成フィールド表の完全性とバイト予算) で手作業転記されたものであり、未済の検査は
[checks-owed.md](../checks-owed.md) C178 (システム構成の必須フィールド表が手写しに依存) に記録。
**デバイス表ユニットがどのコードを採用すべきかにも答えない** —— 判定基準 2 は両アームのバイト数をそれぞれ 1 回計算するのみである。
