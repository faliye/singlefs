## E7 オフラインインデックスharness —— 初回ラウンド実行済み（2026-08-27）

[中文](07-离线索引harness.md) · [English](07-离线索引harness.en.md) · **日本語**

**背景**：E1 (ノードサイズ vs 回復性) / E2 (再帰走査に対するキー配置の影響) / E4 (範囲再構築 vs 個別変更の交差点) はすべて「D8 (コアインデックス構造) の確定と checker に依存」と書かれており、D8 (コアインデックス構造) のパラメータ決定もこれらの実験を待つ形となり、
デッドロックを形成していた。打開策は1つの事実を認めることである：**インデックス構造の選定には完全なファイルシステムは不要であり**、
実ブロックデバイス上で動作可能な独立インデックスエンジンと一連のワークロードリプレイヤーがあれば足りる。

**何をするか**：VFS なし、POSIX セマンティクスなし、クラッシュリカバリなしの**インデックス harness** を作成する——
「ブロックデバイス上でツリー／KV を維持し、insert / point query / range scan / 範囲削除をサポートする」機能のみを持つ。
その上で各候補構造を実装し、同一のワークロードリプレイで比較する。

**候補構造**（[prior-art.md](../prior-art.md) 7.3 に基づく）：

| 候補 | 測定対象 |
|---|---|
| B+tree（ベースライン） | ポイント検索最適時の読み出しコスト上限 |
| ログ構造ノードの B+tree（D8 (コアインデックス構造) 現行方針） | ノード内追記 + 定期再配置の実効ゲインと再配置コスト |
| Bε-tree（内部ノードにメッセージバッファを保持） | 小規模書き込み吸収能力、ポイント検索の劣化度 |
| Bε-tree + size-tiering + フィルタ（SplinterDB 形態） | 純粋な Bε-tree に対する書き込み増幅とポイント検索の差異 |
| 表中の他の4候補のいずれか + key-value 分離（WiscKey 形態） | 大容量 value をインデックス外へ移動した後の compaction / 再配置コスト削減度と range scan 劣化度 |

**何を測定するか**：書き込み増幅、読み出し増幅、ポイント検索レイテンシ分布、range scan 帯域幅、空間増幅、CPU 使用率。
**各項目は「コールドキャッシュ」と「ホットキャッシュ」の2組に分ける**——ホットキャッシュ下ではすべての構造がほぼ同等に見えるためである。

**判定基準**：「ワークロード形態 × 構造」の表を得ること。各マスは「何を測定するか」列の6指標である。
**この表自体が成果物であり**、単一の勝者を選出する必要はない——D8 (コアインデックス構造) が求めているのは「パラメータをどう決めるか」であり、「どのツリーを選ぶか」ではない。

**ベースラインは教科書的 B+tree ではなく、D8 (コアインデックス構造) 現行方針でなければならない。**
D8 (コアインデックス構造) で確定した形態は「ログ構造ノード + write buffer フロントエンド」であり、**それ自体が小規模書き込みを吸収する機構である**。
ソート済みノードの素朴な B+tree をベースラインにすると、「バッチ処理の有無」が測定されてしまい、「メッセージバッファが write buffer に対して何をもたらすか」が測定できない。
文献中の数値はすべて素朴なベースラインに対するものである：BetrFS は ext4/btrfs/XFS/ZFS と比較し、SplinterDB は RocksDB と比較しており、
**write buffer フロントエンドを備えた対照群は一つも存在しない**——D8 (コアインデックス構造) 現行方針に対するメッセージバッファの限界効用について、既存文献は何の数値も提供していない。

**何をもって失敗とするか**（2種類に分類し、混同してはならない）：

| 現象 | 判定 | 理由 |
|---|---|---|
| 各候補があらゆるワークロードで測定ノイズ以下の差異しか示さない | **ラウンド全体を無効化**、データセットを拡大しキャッシュをクリアして再実行 | データセットが小さすぎてすべてページキャッシュに収まっている可能性が高い |
| Bε が**非バッチ対照群**（素朴なソート済みノード B+tree）に対して有意に優れていない | **実装に問題あり、ラウンド全体を無効化** | 陽性対照：効果は文献で確証されており、測定できない場合は実装の誤り（バッファ比率 0、挿入毎のフラッシュなど）である |
| Bε が **D8 (コアインデックス構造) 現行方針ベースライン** に対して優位性を持たない | **正当な結果であり、ありのまま記録する** | メッセージバッファが write buffer で得られないものを追加で獲得できなかったことを意味し、これこそ E7 (オフラインインデックスharness) が回答すべき問いである |

⚠️ **非バッチ対照群は必ず維持しなければならない**。さもなければ「優位性なし」が「結論がそうである」のか「実装が壊れている」のか区別がつかない。
両方の対照群を同時に実行して初めて、判別力と反証可能性が同時に確保される。

**write buffer フロントエンドを備えた対照群は皆無であった**。

#### 3つの厳格要件の個別判定

| 要件 | 観測結果 | 判定 |
|---|---|---|
| 1. 各アームが主張する構造を真に実装しているか | 2つのバッチアームのコア判定基準を定数（バッファ=1）に置換：logstruct_wb 0.866 → **1.502**（+73%）、betree 0.171 → **1.702**（+897%）；sorted_bplus は不変（元々バッファなし） | **合格**。構造が真に関与している |
| 2. 償却アーキテクチャの対称性 | logstruct_wb と betree は同一ノードキャッシュ、同一 checkpoint ペース（4096 操作毎）を共有。sorted_bplus は意図的にライトスルー——**非バッチ対照であり対称性要件の対象外** | **合格** |
| 3. ブロック層独立計測値 + 検証パス自体の判別力 | 5ラウンド9マスのプログラムカウンタと `/sys/block/vda/stat` が**ラウンド毎に一致**；`O_DIRECT` を外すとブロック層の読み出し値がすべてゼロになりプログラムカウンタは不変、経過時間は73倍に低下 | **合格** |

#### 2つの解析対照（第3の独立パス）

- `sorted_bplus`：1回あたり 1 書き込み + `(1 − 64/1024)` 読み出し = **1.9375**、実測 **1.9378**。
- `logstruct_wb`：512個のランダムキーが約400個の異なるリーフに到達、各リーフで1読み出し1書き込み ⇒ 約 **1.56**、実測 **1.5755**。

⚠️ **レンジの低さは決定論的見せかけではない**：5ラウンドのシードはすべて異なる（101/202/303/404/505）、
他の2アームのレンジは 0.2% と 0.9% である。`sorted_bplus` の 0.0% は操作あたり正確に1回の書き込みを行い、
読み出し回数が20万回サンプリング上のページフォールト率平均であることに起因する。

### キャッシュ／ツリー比スキャン（2026-08-27、4段階 × 5シード = 20ラウンド、すべて有効）

**更新パス io/op（中央値）**

| キャッシュページ | ツリー比 | 非バッチ対照 | D8 (コアインデックス構造) 現行方針 | Bε | **Bε / D8 (コアインデックス構造)** | D8 (コアインデックス構造) / 非バッチ |
|---|---|---|---|---|---|---|
| 16 | 2% | 1.9844 | 1.5755 | 0.6384 | **2.47×** | 1.26× |
| 64 | 6% | 1.9378 | 1.5755 | 0.4900 | **3.22×** | 1.23× |
| 264 | 25% | 1.7437 | 1.5755 | 0.3176 | **4.96×** | 1.11× |
| 1057 | **100%** | 1.0051 | **0.2515** | 0.1678 | **1.50×** | **4.00×** |

**ポイント検索 読み出し/回（中央値）**：3アームは各段階でほぼ同等（2% 段階で 1.78/1.78/1.72、
100% 段階で全アーム 0.053）、**Bε の方が僅かに劣るのではなく僅かに優れている**——理由は外挿境界の節を参照。

ブロック層とプログラムカウンタ：**60/60 マス一致**。

#### 2つの結論

**1. `Bε / D8` (コアインデックス構造) は単調ではなく、中央でピークを迎える。**
2% → 25% と 4.96× まで一貫して上昇するが、キャッシュがツリー全体を収容できるようになると **1.50× へ急減する**。
⇒ **Bε の優位性の条件は「ツリーがキャッシュに収まらないこと」である**——E12 (バッチシーケンシャル追記 vs 非バッチランダムページRMW) における D5 (スナップショット・領域台帳機構) の優位性条件
（「カウンタテーブルがキャッシュに収まらないこと」）と同型である：双方が「ランダム検索をシーケンシャル／バッチに変換する」ものであり、
それは収まりきらない場合にのみ価値を持つ。

**2. D8 (コアインデックス構造) 現行方針は 2% / 6% / 25% の3段階で io/op がビット単位で同一（1.5755）——キャッシュが全く機能していない。**
メカニズム：**write buffer がリーフ順にソートされた後、各フラッシュはリーフ空間全体にまたがるシーケンシャルスキャンとなり、
LRU は「キャッシュを超える反復的なシーケンシャルスキャン」に対してヒット率が正確に 0 になる。**

介入による実証（同一リーフの集約はそのままに、**グループの処理順序のみをシャッフル**）：

| キャッシュ段階 | ソート済みフラッシュ | グループ順シャッフル | |
|---|---|---|---|
| 25% | 157,739 読み出し | **143,251 読み出し（−9.2%）** | 順序が確かに推進要因である |
| 100% | 1,024 読み出し | **1,024 読み出し（完全同一）** | **陰性対照**：全収容時は順序無関係 |

⚠️ その 9.2% は**下限**である：シャッフルのシードはグループ数から導出され、グループ数が同じなら同一の順列となり、
フラッシュを跨いで相関が生じ効果が弱まる。**方向性と陰性対照はともに成立しており、オーダーは保守的である。**

> **ここから設計要件が得られる：write buffer をソートする場合、ノードキャッシュはスキャン耐性を持つものでなければならない
> （2Q / LRU-K など）。さもなければソートは局所性を生み出すどころか破壊してしまう。**
> これは [decisions.md](../decisions.md) D8 (コアインデックス構造) に直接影響を与えるが、D8 (コアインデックス構造) 本文は 2026-08-27 時点では
> 「write buffer でバッチ集約しソート・重複排除後に一括挿入」と記載されているのみで、**キャッシュ戦略には一切の要件を課していなかった**。

### ノードサイズスキャン（2026-08-27、3段階 × 5シード = 15ラウンド、**約 1 MB の固定メモリ予算**）

**計測条件の要点：メモリ予算が固定されているため、ノードが大きくなるほど収容できるノード数は減少する。** これこそが真のトレードオフである。

|---|---|---|---|---|---|---|
| **4 KiB** | 264 | 25% | io/op | 1.7437 | 1.5755 | **0.3176** |
| | | | バイト/回 | 7,142 | 6,453 | **1,301** |
| | | | ポイント検索読み出し/回 | 0.7766 | 0.7766 | 0.7361 |
| **16 KiB** | 66 | 6% | io/op | 1.9359 | 1.5755 | **0.3994** |
| | | | バイト/回 | 31,718 | 25,812 | **6,544** |
| | | | ポイント検索読み出し/回 | 1.2249 | 1.2249 | 1.1624 |
| **64 KiB** | 16 | 2% | io/op | 1.9844 | 1.5755 | **0.6384** |
| | | | バイト/回 | 130,050 | 103,249 | **41,841** |
| | | | ポイント検索読み出し/回 | 1.7792 | 1.7792 | 1.7175 |

ブロック層とプログラムカウンタ：**45/45 マス一致**。

#### 結論：固定メモリ予算下では、大ノードは3つの軸すべてで悪化する

I/O 回数は倍増し（Bε 0.318 → 0.638）、バイト数は **32倍**（1,301 → 41,841）、ポイント検索読み出し回数も倍増する。
メカニズム：**ノードが大きくなるほど同一メモリに収容できるノード数が減少し、ヒット率の低下が「1回あたりの読み出し増加」による回収を上回る速度で進行する。**

`logstruct_wb` の io/op は3段階で**ビット単位で完全一致（1.5755）**——同一の理由（ソート済みフラッシュ ⇒ シーケンシャルスキャン ⇒ ヒット率 0）により、
ノードサイズは接触するノード数を変えない；しかしそのバイト数は **16倍** に膨張する。

⚠️ **これは「メディアごとの階層化レイアウト」を正当化できない**：[decisions.md](../decisions.md) D8 (コアインデックス構造) 制約 1 により、ノードサイズは
mkfs 時にシステム構成に書き込まれるフォーマットパラメータとして確定している——**パラメータで十分であり、そのために別レイアウトを新設する必要はない**
（レイアウト数は D12 (対象メディア) 確定項目 1 に属し、事前の制限は設けない）。
E7 (オフラインインデックスharness) は「1回のノード読み出し」を**ノードサイズに関わらず** 1 回のデバイス I/O として計上している；
仮想マシン + ホストファイル（SSD 近似）上では**バイト数が主導的**であるため、大ノードは純損失となる。

**シーク主導側の実測も完了しており（E7 (オフラインインデックスharness)「シーク主導段階」を参照）、結論は逆ではなく同一方向である**：
「各 I/O コストが同等でサイズに無関係」という極限においても、大ノードは勝てない。
⇒ **小ノードはバイト主導とシーク主導の双方の極限で勝利しており**、メディアによってノードサイズの方向性を逆転させる必要はない。

⇒ [decisions.md](../decisions.md) D8 (コアインデックス構造) の「128K–256K を無批判に踏襲しない」方針に対して：**両端から支持が得られた**。

**さらに仮想マシンとホストの `io_per_op` はビット単位で完全一致**（同一デフォルトシード `0x51561234`）：
1.937385 / 1.575920 / 0.493670。**メディアを変え、カーネルを変えても、カウントは1ビットも違わない。**

⚠️ **時間数値は使用不可**：実機 `/boot` 下で読み取り可能な唯一のカーネルが `vmlinuz-6.17.0-lockdep` であり、
ロック検証オーバーヘッドが大きい——同一段階の仮想マシン内所要時間はホストの約 **2倍**（29.7 s 対 14.5 s）。
**カウント指標は影響を受けないが、時間指標は環境を跨いで比較してはならない。**

⚠️ **計測条件の差異を明記すること**：元ラウンドは QEMU ブロックデバイス上で実行され、シードも今回と異なる；
今回は ext4 上の通常ファイルで実行され、`O_DIRECT` は有効のままである。3アームの差はすべて 0.3% 以内。
「同日仮想マシン内での再実行：検証パスも再現」の数値は**再実行によってのみ再確認可能であり、過去アーカイブの参照では確認できない**——再実行には QEMU が必要。

**レート制限パスの赤実証**：同一の 300 回の直接読み出しについて、無制限時 0.18 s；100 IOPS 制限時 2.89 s
（≈ 300/100 = 3 s）。この手順を踏まなければ「差異が出なかった」のか「レート制限が機能していなかった」のか区別できない。

**モデルの自己証明**：経過時間と「I/O 回数 ÷ レート制限値」の整合性（中央値、N=5）

| 段階 | アーム | io/op 中央値 | 予測経過時間 | 実測中央値経過時間 | 誤差 |
|---|---|---|---|---|---|
| 4 KiB | 非バッチ対照 | 1.742435 | 87.12 s | 87.13 s | 0.01% |
| 64 KiB | 非バッチ対照 | 1.984590 | 99.23 s | 99.18 s | 0.05% |
| 4 KiB | Bε | 0.317940 | 15.90 s | 15.90 s | 0.00% |
| 64 KiB | Bε | 0.639135 | 31.96 s | 31.91 s | 0.15% |
| 4 KiB | D8 (コアインデックス構造) 現行方針 | 1.574990 | 78.75 s | 78.76 s | 0.01% |
| 64 KiB | D8 (コアインデックス構造) 現行方針 | 1.574990 | 78.75 s | 78.65 s | 0.13% |

⇒ **バイト数はこのデバイス上では全く勘案されない**：64 KiB 段階では操作毎に 130,041 バイト、4 KiB 段階では 7,137 バイトを読み出すが
（**18倍**）、経過時間は I/O 回数のみによって決定される。モデルは主張通りの挙動を忠実に果たしている。

**ブロック層検証は依然として成立**：レート制限は QEMU スタック内に `throttle` ブロックドライバを挿入しているため
（従来の `-drive` に代わり `-blockdev driver=throttle`）、I/O パスが変更されており、
ブロック層対照が有効なままであると無前提に見なすことはできない。実測で **12/12 マスがビット単位で完全一致**（2構成 × 3アーム × update/query、
プログラムカウントの reads/writes とゲスト `/sys/block` の `blk_r`/`blk_w` が完全一致）。
この検証パスは 2026-08-27 初回ラウンドで赤実証済みである——ダイレクト I/O を外すとブロック層カウントはゼロになりプログラムカウントは微動だにしなかった。

**結果**

| アーム | 4 KiB 経過時間中央値 | 64 KiB 経過時間中央値 | 大ノード | 各自のレンジ |
|---|---|---|---|---|
| 非バッチ対照 | 87.13 s | 99.18 s | **差 13.8%** | 0.06% / 0.32% |
| D8 (コアインデックス構造) 現行方針 | 78.76 s | 78.65 s | ほぼ同等（−0.14%） | 0.09% / 0.06% |
| Bε | **15.90 s** | 31.91 s | **差 100.7%** | 0.72% / 0.33% |

**レンジ ≤0.72% は不審ではなく、機構的なものである**：経過時間 = I/O 回数 ÷ レート制限値 であり、
I/O 回数は5つのシード間でわずか 0.06% しか違わない（4 KiB 非バッチ対照段階：1.742510 / 1.741970 /
1.742720 / 1.742435 / 1.741695）。**シードは確かに変動している**——5つの値は各々異なる；
単にこのワークロードの構造が確定的であり、変化するのはキーシーケンスのみである。
レンジの小ささは逆に「レート制限が確実に経過時間を主導している」ことを再確認させる。

**⇒ シーク主導の極限においても大ノードは勝てず、逆転は起きない。**

理由：独立変数は**固定メモリ予算**であり、ノードが大きくなるほど収容可能数が減少し、ミス率が上昇し、
**ノード読み出し回数がかえって増加する**——この効果が「1回で多く読み出す」利点を凌駕するためである。

### シーク主導段階が証明できないこと

- **回転ディスクの実測ではない。** モデル化デバイスである。
- **モデルにシーケンシャルマージが含まれていない。** 実機械ディスクでは隣接する小 I/O が1回のシークにマージされるが、
  QEMU の IOPS レート制限は個別に課金される ⇒ **本モデルは小ノードのコストを過大評価している**。
  過大評価されてなお小ノードが勝っているため、**この限界は結論を弱めるどころか強固にする**。
- **両端（4 KiB と 64 KiB）のみを測定し、16 KiB の中間段階を測定していない。** 単調性は未検証。

### この数値群が証明できないこと

- ⚠️ **ツリーが非常に小さい**：1024 リーフ + 32 内部 + 1 ルート = 1057 ノード（約 4.3 MB）、キャッシュ 64 ページ（**6%**）。
  実際のツリーは遥かに大きく、**キャッシュ／ツリー比こそが駆動量である**——この比率が変われば、3アームの格差も変動する。
- ⚠️ **ワークロードは既存キー空間に対するランダム更新であり、分割・統合がない**。
  分割動作は射程外であるが、BetrFS 自身が相対的に悪化するケースとして挙げているのはまさに「ノード分割・統合がクリティカルパスに乗る」場合である。
- ⚠️ **ポイント検索列が直感に反するが、これは構成に起因する**：クエリは更新と**同一の一様ランダム分布**を使用しているため、
  最近更新されたキーが高い確率でキャッシュされたルート／内部バッファに留まっており、リーフの読み出しを1回省くことができる。
  **コールドキーに対するクエリでは逆の結果となる**——これは単独で測定すべきであり、E7 (オフラインインデックスharness) では測定されていない。
- ⚠️ ノード固定 4 KiB、value 固定 8 バイトであるが、D8 (コアインデックス構造) 確定項目 2 は **16 KiB 定数** を採用している
  ⇒ **E7 (オフラインインデックスharness) の3アームはすべて、もはや本プロジェクトの値ではないノードサイズ上で実行されている。**
  16 KiB 上の再測定は E56 (メッセージバッファのゲイン vs イプシロン) を参照。
- ⚠️ **Bε アームにおいてバッファ容量とファンアウトが互いに無関係な2つの定数となっている**（`message_buffer_capacity = 200`、`FANOUT = 32`、
  内部ノードはメッセージのみを保持しピボットを保持しない） ⇒ 両者が同一のノードバイトを争奪することがなく、
  そのせめぎ合いこそが Bε の機構のすべてである。**したがって E7 (オフラインインデックスharness) のノードサイズスキャンはノードサイズとバッファ比率を同時に変更してしまっている
  （4 KiB 時 0.78、16 KiB 時 0.195、64 KiB 時 0.049）、3段階は比較不能である。**
  是正は E56 (メッセージバッファのゲイン vs イプシロン) を参照。

**計測条件**：`e7-index`、musl 静的リンク、xorshift64\*；ファンアウト 32、1024 リーフ、各リーフ 64 キー、
キー空間 65536；ノード 4 KiB、ノード毎 255 スロット；キャッシュ 64 ページ、write buffer 512 エントリ、
Bε バッファ 200 エントリ、checkpoint 4096 操作毎；毎ラウンド 20 万回更新 + 2 万回ポイント検索。
仮想マシン 2048M / 4 vCPU / 64 MiB virtio ディスク、`cache=none,aio=native`；ホスト 32 コア / 60 GiB；QEMU 8.2.2 + KVM。

### ⚠️ 解析式による対照は以前は散文の中にしか存在しなかった（2026-08-29 敵対的検証により補完）

E7 (オフラインインデックスharness) に記載されていた第3の独立検証パスは「2つの解析式と実測の一致（1.9375 vs 1.9378、約 1.56 vs 1.5755）」であったが、
**コード内にはそれを固定するアサーションが一切存在しなかった**——4つの単体テストが固定していたのはページ番号の非重複、キーマッピングの境界内収容、幾何学的自己無撞着性であり、**すべて構造的性質であった**。
⇒ 幾何定数が変更されると 1.9375 は暗黙のうちに無効化され、D11 (インデックスノード内のメッセージバッファ要否) 前提条件 2 が引用する
**3.22 倍という数値はまさにこれらの数値から算出されたものであった**。

`the_no_batching_control_arm_has_an_analytic_io_per_op_of_1_9375` を追加：
`1 + (1 − 64/1024) = 1.9375`、および `LEAF_COUNT == 1024` と `FANOUT² == LEAF_COUNT` を固定。
⚠️ **固定しているのは解析式と幾何定数であり、実測値ではない**——実測にはデバイスと仮想マシンが必要で単体テスト内では実行できず、
両者の照合は依然として再実行に頼るほかない。ミューテーション表は `scripts/mutation/tables/e7_index.tsv` に保存されている。

### E12 (バッチシーケンシャル追記 vs 非バッチランダムページRMW) から学んだ3つの厳格要件（満たさなければ実行してはならない）

E12 (バッチシーケンシャル追記 vs 非バッチランダムページRMW) の教訓は具体的であった：あるアームがある機構を実装していると主張しながら実際はスタブであり、
両アームの償却アーキテクチャが非対称であった——**結果としてあの17万倍という数値の中で、機構とバッチ処理がそれぞれどれだけ貢献したのか分解できなかった**。
E7 (オフラインインデックスharness) はこれを繰り返してはならない：

1. **各アームは主張する構造を真に実装していなければならない。**
   アームの名前が何であれ、コード内にその実体が存在しなければならない。
   ⚠️ **自己検証方法**：該当アームのコア判定基準を常に真／偽の定数に置換した場合、結果が**顕著に変化しなければならない**；
   変化がなければその構造は全く関与しておらず、**ラウンド全体が無効となる**。
   （E12 (バッチシーケンシャル追記 vs 非バッチランダムページRMW) のアーム A の判定基準をコイントスに変えても結果が同一であった——それこそがこの自己検証が赤になる形態である。）
2. **すべてのアームの償却アーキテクチャは対称でなければならない**：同一のバッチウィンドウ、同一のフラッシュタイミング、同一の発行セマンティクス。
   [decisions.md](../decisions.md) D16 (パブリッシュセマンティクス) は checkpoint を確定しており、**すべてのアームが同一の checkpoint ペースで実行される**。
   さもなければ測定されるのは「誰がバッチ化したか」であり、「誰の構造が優れているか」ではない。
3. **デバイス I/O はブロック層の独立計測値を持たなければならず**（仮想マシン内 `/sys/block/*/stat`）、プログラム内カウンタと1マスずつ照合されなければならない；
   かつ**この検証パス自体が故障注入によって判別力を持つことを証明しなければならない**（`O_DIRECT` を外すとブロック層の読み出し値がゼロにならなければならない）。
   `.claude/singlefs-ai-sop/rules/evidence-discipline.md`：検証パス自体もそれが赤になることを証明しなければならない。

### もう一つの独立変数の追加：バッファ内に冪等完全値を置くか増分を置くか

[decisions.md](../decisions.md) D11 (インデックスノード内のメッセージバッファ要否) のコスト判定基準は「バッファ内に**冪等完全値**（マージ = 後勝ち、
checker は value セマンティクスの理解不要）を置くか、**増分 Δ**（マージは value セマンティクスに依存）を置くか」に改訂された。
**これは独立変数として測定されなければならない**：同一アームにおける2つのエントリ形態下での書き込み増幅とマージコストがそれぞれいくらか。
これは D11 (インデックスノード内のメッセージバッファ要否) のコスト 1 が成立するかを決定し、その判定基準は D8 (コアインデックス構造) と D11 (インデックスノード内のメッセージバッファ要否) に跨っている。

**前提条件**：ブロックデバイス、ワークロードリプレイヤー、Rust ツールチェーン。**ファイルシステム不要、checker 不要、D8 (コアインデックス構造) の確定不要。**

**これが何を解消するか**：E1 (ノードサイズ vs 回復性) のノードサイズ、E2 (再帰走査に対するキー配置の影響) のキー配置、E4 (範囲再構築 vs 個別変更の交差点) の範囲再構築交差点、
E8 (大容量と小容量ファイルで書き込みパスを分けるべきか) の大小ファイル分流、E9 (走査局所性に対するキー符号化の影響) のフルパス vs inode インデックス——5つの実験の主要部分はすべてこの harness 上で先行実行可能であり、
「真の POSIX セマンティクスとクラッシュリカバリを必要とする」部分のみをファイルシステム構築後まで保留できる。
