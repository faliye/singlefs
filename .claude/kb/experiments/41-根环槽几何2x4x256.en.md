## E41 Root Ring Slot Geometry 2×4×256 —— Run (2026-08-30, N=5 rounds byte-identical): Tear isolation judged Red, slot width 256 < atomic width

[中文](41-根环槽几何2x4x256.md) · **English** · [日本語](41-根环槽几何2x4x256.ja.md)

**What it asks**: Can the candidate configuration in D22 (Synthesizing Unit Atomicity) settled item 2 (verbatim: "**2 regions × 4 slots × 256 bytes = 2048 bytes**") hold up.

⚠️ **Division of labor with E34 (Root Ring Slot Geometry)**: E34 (Root Ring Slot Geometry) asks about **relationship between slot width and device mapping units** (mechanistic derivation, local `io_min == physical_block_size == 512` cannot falsify, with two cloud legs owed); **E41 (Root Ring Slot Geometry 2×4×256) asks whether that specific parameter combination suffices under crash and block reuse constraints**, the modelable half.

### What to Test, Criteria, Failure Clauses

- **What to test**: Model root ring per `2 regions × 4 slots × 256 bytes`, sweep fsync rate and checkpoint interval, measuring three aspects:
  1. **Duration of one rotation circuit** (= 8 slots ÷ root publish frequency);
  2. **Block reuse delay**: I-7.4 (recent K generations of blocks not reused) requires blocks referenced by roots of the most recent K generations not be reused, with K and slot count sharing origin ⇒ duration of one circuit serves as upper bound on reuse delay;
  3. **Number of slots destroyed by a single torn write** (computed as `slot width / atomic width`, taking local 512 along with array tiers 4096 / 65536).
- **Criteria**:
  - **Geometry sufficient**: Duration of one circuit **≥** worst-case block reuse delay requirements (the one written down in D22 (Synthesizing Unit Atomicity) settled item 2 itself).
  - **Tear isolation**: Number of slots destroyed by a single write must be **1**.
    ⚠️ Local host has `physical_block_size = 512` whereas candidate slot width is 256 ⇒ **this item is expected to go red**, which is precisely what needs to be measured, not an implementation bug.
- **Positive control**: Set slot width to `max(physical_block_size, io_min)` with each slot exclusively occupying one unit; "slots destroyed by a single write" must drop to 1—otherwise the model is not computing per unit at all, invalidating the entire round.
- **Failure clauses**: If both criteria are satisfied across all parameter combinations, candidate form holds, **faithfully record**; if only tear isolation fails, conclusion is "slot width must be raised" rather than "root ring form is wrong"—**the two must never be conflated**.
- ⚠️ **Must include absolute value assertions**: "Slots destroyed by single write" is directly computed from `(slot width, unit width, start offset)`; "duration of one circuit" is directly computed from `(slot count, root publish frequency)`. Neither is allowed to be read back from tested code.

### ⚠️ An Unavoidable Premise

D22 (Synthesizing Unit Atomicity) settled item 2 concedes this item depends on "independent failure domains at disk head and tail", for which **local host provides no evidence** (ZFS 4-label design relies on the same assumption). E41 (Root Ring Slot Geometry 2×4×256) **does not verify this assumption**, calculating geometry solely under the premise that it holds.

None. Pure count model.

### Host Testing (2026-08-30)

| Quantity | Value |
|---|---|
| Candidate form | 2 regions × 4 slots × 256 bytes = **8 slots / 2048 bytes** |
| One circuit (root published per fsync) | **8 operations**; root published per checkpoint (E16 (Role of Journal: WAL vs Intent Log) measured 200 roots per 200k operations) ⇒ **8000 operations** |
| Tear: slot width 256, judging width 512 / 4096 | Destroys **2 / 16** slots |
| Positive control: slot width raised to 512 (local `physical_block_size = io_min = 512`) | Destroys **1** slot |
| But slot width 512 under 4096 judging width | Returns to **8** slots |
| **Misalignment**: 512-wide slot offset by 256 | Straddles **2** atomic units ⇒ risk slots **2** |
| **Can entire 2048-byte ring fit inside one `io_min`** | Cannot fit in 512; **can fit in 4096 and 65536** |
| Cost of raising slot width to judging width: ring total bytes | 512 tier **4096** (2× candidate), 4096 tier **32768** (16×) |

**Four conclusions**:

1. **Candidate slot width 256 rejected**: Fails to achieve isolation across both 512 and 4096 judging widths (destroys 2 / 16 slots). Expected to go red at inception; going red is **not an implementation bug**.
2. **"2 regions × 4 slots" dimension has zero coverage in E41 (Root Ring Slot Geometry 2×4×256)**: In model `REGIONS` only participates in multiplication; inputs for **region spacing and failure domains are absent**, yet they are the sole rationale for the number "2".
   ⇒ **"Configuration not overthrown" reflects absence of evidence, not a negative result.**
3. **Tear isolation was missing a requirement that "root slots align to judging width"**:
   Under [invariants/02-根环.md](../../../crates/singlefs-checker/invariants/02-根环.md) the I-7 (root ring) class lacked this clause at the time (now I-7.5 (root slots aligned to judging width), implemented, judged slot-by-slot by pool-level checker), and positive control's "drop to 1 when raised to 512" implicitly presumed it—measured to return to 2 when offset by half a slot.
4. **The mechanism that truly wipes out the entire ring in a single blow is device internal RMW, not tearing**:
   A 2048-byte ring **fits within a single 4096 or 65536 `io_min`**.
   Remedy is not raising slot width (which addresses tearing), but **separating the two regions by ≥ `io_min`**.

⚠️ **A quantity mismatch was corrected (pointed out by deduction leg in that round, verified line by line in code by main agent)**:
Judging width column included 65536 prior to correction, whereas **64 KiB is the scale of `io_min`, not `physical_block_size`**—
checked in `block/blk-settings.c` `blk_stack_limits` where `t->physical_block_size = max(t->physical_block_size,` takes max of member disks' `physical_block_size`, and in `drivers/md/raid0.c`, `raid5.c` (both set `lim.io_min = mddev->chunk_sectors << 9`).
Meanwhile D20 (Load-Bearing Surface: Unit Atomicity & Self-Containment) corollary 3 settles "self-witnessing unit atomic width = runtime detected `physical_block_size`".
⇒ Prior conclusion that "single write destroys 256 slots, wiping out all witnesses" **does not hold and was deleted**; corresponding genuine mechanism is in conclusion 4, and cost is not that "256×".

### "Is One Circuit Enough": What Cannot Be Judged Is a Non-Existent Requirement

Artifact `reuse_requirement_source=none`—no number for "worst-case block reuse delay requirement" exists in kb.
However **lower bound is written down**: I-7.3 (ring health) requires "in addition to highest generation at least one earlier generation record exists", and D22 (Synthesizing Unit Atomicity) states verbatim "K must be runtime policy (**lower bound ≥ 2**)". 8 ≥ 2.
Moreover D22 (Synthesizing Unit Atomicity) explicitly orders "**do not interpret root ring as 'can roll back K generations'**"
⇒ A requirement shaped like "must roll back N generations" should not exist per D22 (Synthesizing Unit Atomicity)'s own definition.
**What is missing is not data, but that requirement itself does not exist.**

⚠️ **A kb contradiction was discovered along the way**: Bracket note in I-7.4 (recent K generations of blocks not reused) wrote "**K = root ring depth**",
whereas D22 (Synthesizing Unit Atomicity) verbatim says "K must be runtime policy (lower bound ≥ 2), **cannot be format constant**",
explicitly noting "'root ring depth = block reuse delay' easily gets implemented as 'depth is format field, so K is format field'".
Root ring depth is format quantity (slot count) ⇒ **both statements cannot hold literally simultaneously**.
⚠️ **This contradiction was resolved on 2026-09-13**: I-7.4 (recent K generations of blocks not reused) changed "K generations" to rollback candidate set (judged valid per instance table ∧ txg ≥ F_effective), and block reuse bound was given by D16 (Publish Semantics) settled item 1 as `max(F_effective, oldest valid root in ring)` ⇒ no longer having a quantity named K defined twice differently.
In this model `cycle_ops` and `reuse_delay_ops` call the same function twice, the visible manifestation of this conflation—**criterion "one circuit ≥ requirement" is therefore a self-comparison in this model**.
