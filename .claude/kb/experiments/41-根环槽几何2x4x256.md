## E41 根环槽几何 2×4×256 —— 已跑（2026-08-30，N=5 轮字节一致）：撕裂隔离判红，槽宽 256 < 原子宽度

**它问的是**：D22（单元原子性怎么合成） 未定项 2 那个候选形态
（逐字：「**2 区域 × 4 槽 × 256 字节 = 2048 字节**」）站不站得住。

⚠️ **与 E34（根环槽几何） 的分工**：E34（根环槽几何） 问的是**槽宽与设备映射单元的关系**
（机制推导，本机 `io_min == physical_block_size == 512` 无法证伪，且两条云端腿欠着）；
**E41（根环槽几何 2×4×256）问的是那个具体参数组合在崩溃与块重用两条约束下够不够用**，是可建模的那一半。

### 要测什么、判据、失败条款

- **测什么**：按 `2 区域 × 4 槽 × 256 字节` 建模根环，扫 fsync 率与 checkpoint 间隔，量三样：
  1. **轮换一圈的时长**（= 8 槽 ÷ 发根频率）；
  2. **块重用延迟**：I-7.4（近 K 代块未被复用） 要求最近 K 代根引用的块不得重用，
     而 K 与槽数同源 ⇒ 一圈的时长就是重用延迟的上界；
  3. **一次撕裂打掉几个槽**（按 `槽宽 / 原子宽度` 算，取本机 512 与阵列常见的 4096 / 65536 三档）。
- **判据**：
  - **几何够用**：一圈的时长 **≥** 最坏块重用延迟需求（D22（单元原子性怎么合成） 未定项 2 自己写下的那条）。
  - **撕裂隔离**：一次写打掉的槽数必须为 **1**。
    ⚠️ 本机 `physical_block_size = 512` 而候选槽宽 256 ⇒ **预期这一条会红**，
    那正是要量出来的东西，不是实现 bug。
- **阳性对照**：把槽宽设成 `max(physical_block_size, io_min)` 且每槽独占一个单元，
  「一次写打掉的槽数」必须降到 1 —— 否则模型根本没在按单元算，整轮作废。
- **失败条款**：若两条判据在所有参数组合上都满足，候选形态成立，**如实记录**；
  若只有撕裂那条不满足，结论是「槽宽要抬」而不是「根环形态错」——**两者不许混为一谈**。
- ⚠️ **必须带绝对值断言**：「一次写打掉几个槽」由 `(槽宽, 单元宽, 起始偏移)` 直接算出；
  「一圈的时长」由 `(槽数, 发根频率)` 直接算出。两个都不许从被测代码读回来。

### ⚠️ 一个不能回避的前提

D22（单元原子性怎么合成） 未定项 2 自陈本项依赖「盘首与盘尾失败域独立」，而**本机没有证据**
（ZFS 的 4-label 设计吃的是同一个假设）。E41（根环槽几何 2×4×256）**不验证这个假设**，只在它成立的前提下算几何。

### 前置

无。纯计数模型。

### 实测（2026-08-30）

| 量 | 值 |
|---|---|
| 候选形态 | 2 区域 × 4 槽 × 256 字节 = **8 槽 / 2048 字节** |
| 一圈（每次 fsync 发根）| **8 次操作**；每 checkpoint 发根（E16（journal 的角色：WAL vs 意图日志） 实测 20 万次操作 200 次根）⇒ **8000 次** |
| 撕裂：槽宽 256，判定宽度 512 / 4096 | 打掉 **2 / 16** 个槽 |
| 阳性对照：槽宽抬到 512（本机 `physical_block_size = io_min = 512`）| 打掉 **1** 个 |
| 但槽宽 512 在 4096 判定宽度上 | 又变成 **8** 个 |
| **不对齐**：512 宽的槽偏移 256 | 跨 **2** 个原子单元 ⇒ 风险槽数 **2** |
| **整个 2048 字节的环装不装得进一个 `io_min`** | 512 上装不进；**4096 与 65536 上装得进** |
| 抬槽宽到判定宽度的代价：环总字节 | 512 档 **4096**（候选的 2 倍）、4096 档 **32768**（16 倍）|

**四条结论**：

1. **候选槽宽 256 否掉**：在 512 与 4096 两档判定宽度上都做不到隔离（打掉 2 / 16 个槽）。
   立项时预期它会红，红了，**不是实现 bug**。
2. **「2 区域 × 4 槽」这一维E41（根环槽几何 2×4×256）零覆盖**：模型里 `REGIONS` 只参与乘法，
   **没有区域间距、没有失败域**这两个输入，而那正是「2」这个数唯一的理由。
   ⇒ **「形态没倒」是证据缺席，不是阴性结果。**
3. **撕裂隔离还欠一条「根槽按判定宽度对齐」的要求**：
   [invariants.md](../invariants.md) 的 I-7（根环） 类里没有这一条，
   而阳性对照的「抬到 512 就降到 1」隐含了它——实测偏移半个槽之后又变回 2。
4. **真正一次抹掉全环的机制不是撕裂，是设备内部 RMW**：
   2048 字节的环**装得进一个 4096 或 65536 的 `io_min`**。
   治它的不是抬槽宽（那是治撕裂的），是**把两个区域拉开到 ≥ `io_min`**。

⚠️ **一处量的错配已改正（本轮由反推腿指出，主 agent 逐行现查确认）**：
判定宽度这一栏此前含 65536，而 **64 KiB 是 `io_min` 的量级，不是 `physical_block_size` 的量级**——
2026-08-30 现查 `block/blk-settings.c:855-856`（堆叠取成员盘 `physical_block_size` 的 max）
与 `drivers/md/raid0.c:393`、`raid5.c:7955`（都是 `lim.io_min = mddev->chunk_sectors << 9`）。
而 D20（承重面：单元的原子性与自包含） 推论三定的是「自证单元原子宽度 = 运行时探测到的 `physical_block_size`」。
⇒ 此前据此得出的「一次写打掉 256 个槽、抹掉全部见证者」**不成立，已删**；
它对应的真机制在结论 4，代价也不是那条「256 倍」。

### 「一圈够不够」：判不了的是一个不该存在的需求

产物 `reuse_requirement_source=none`——kb 里没有「最坏块重用延迟需求」这个数。
但**下界是写下来的**：I-7.3（环健康性） 要求「除代号最大者外至少还有一条更早代号的记录」，D22（单元原子性怎么合成） 逐字「K 必须是运行时策略（**下限 ≥ 2**）」。8 ≥ 2。
而 D22（单元原子性怎么合成） 同处明令「**不要把根环读成『可以回滚 K 代』**」
⇒ 一个「必须回退 N 代」形状的需求按D22（单元原子性怎么合成）自己的定义就不该存在。
**缺的不是数据，是那条需求本身不存在。**

⚠️ **顺带发现一处 kb 矛盾**：I-7.4（近 K 代块未被复用） 的括注写「**K = 根环深度**」，
而 D22（单元原子性怎么合成） 逐字「K 必须是运行时策略（下限 ≥ 2），**不能是格式常量**」，
并明写「『根环深度 = 块重用延迟』很容易被实现成『深度是格式字段，所以 K 是格式字段』」。
根环深度是格式量（槽数）⇒ **两句话不能同时按字面成立**。
本模型里 `cycle_ops` 与 `reuse_delay_ops` 是同一个函数调两次，
正是这处混同的可见形态——**判据「一圈 ≥ 需求」因此在本模型里是自比**。

### 三方论证腿况

| 腿 | 立场 | 独有产出 | 判决 |
|---|---|---|---|
| 云端 A | 正推 | 「槽宽 = 判定宽度已经买到隔离，大于它不多买安全性只多花字节」；并指出候选的 8 槽与它自己算出的需求**相等而非有余量** | 候选不成立 |
| 云端 B | 反推 | **三处越位全部命中**：① 65536 是 `io_min` 不是 `physical_block_size`；② 据此得出的「256 倍代价」是给错的药定的价；③ 撕裂那一半与 E43（扩展点字节上限） 同日、同 crate、同一个一行公式，**不构成独立校验腿**。另指出区域维零覆盖与缺对齐要求 | 全面收窄 |
| 本地 | 找反例 | 主张 K 应等于 checkpoint 间隔（1000） | 否掉 |

**主 agent 判决**：采纳反推腿三条（越位那条逐行现查内核源码确认）+ 正推腿的「等号已够」。
**本地腿的「K = checkpoint 间隔」不成立**：D22（单元原子性怎么合成） 明言不许把根环读成可回滚 K 代，
且 E19（defer 窗口下的假性 ENOSPC） 把 K 放在**代价侧**（延迟代数越大越容易假性 ENOSPC），
它给的是 K 的上界压力，不是下界需求。
