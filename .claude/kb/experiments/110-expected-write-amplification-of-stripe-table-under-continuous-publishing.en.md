## E110 Expected Write Amplification of Stripe Table Under Continuous Publishing — Run (2026-09-06, 10 unit tests / 13 mutants caught): **The knife edge in E107 (Stripe Table Write Amplification on Primary Workload) is resolved — after letting `f` evolve with the workload itself, cumulative ratio on primary workload stabilizes at 0.953, and the nearly full container endpoint accounts for only 2.74% of publishes**

[中文](110-条带表在连续发布下的期望写放大.md) · **English** · [日本語](110-連続パブリッシュ下でのストライプ表の期待書き込み増幅.ja.md)

**This answers the cell that E107 (Stripe Table Write Amplification on Primary Workload) confessed it could not answer**:
there was no model for the distribution of `f` (occupied slots in currently open container) under real workload,
while E107 (Stripe Table Write Amplification on Primary Workload) measured that at 8 leaves of primary workload Arm A was 5.0% cheaper at `f = 0` and 5.0% more expensive at `f = 582`
⇒ **conclusion rested on a knife edge, with both sides decided by an unmodeled quantity.**
E110 (Expected Write Amplification of Stripe Table Under Continuous Publishing) lets `f` evolve under continuous publishing, reporting **cumulative ratio** rather than endpoint ratio.

### Two Arms (Byte-for-Byte Same Ruler as E107 (Stripe Table Write Amplification on Primary Workload))

Arm A = `w ≥ 3` + stripe member table (including parity, entire stripe table chain constantly taking `w = 2` mirroring);
Arm C = `w` constantly 2 all-mirrored, zero stripe records written.

### Measurement Basis (Locked Before Run)

1. **Arithmetic of single publish byte-for-byte identical to E107 (Stripe Table Write Amplification on Primary Workload)** —
   Invalidation clause 2 uses its two nailed endpoints (627 200 / 692 736 / 659 968) as cross-validation; mismatch invalidates whole round.
2. **`f` evolves with workload**: member records generated by each publish accumulate into currently open container, opening new container upon reaching 583 records.
3. Two workloads: `main` (constant 8 leaves, D25 (Target Workload Priority) primary workload) and `mixed` (1 / 8 / 64 leaves rotating).
   ⚠️ Leaf count distribution of `mixed` is **modeling choice, not measured workload profile**.
4. **Deterministic model**: running same binary N times necessarily yields identical results; evidence strength comes from mutations and assertions nailing absolute values, not from round count.

### Results (2026-09-06, artifact `e110-stripe-table-steady-2026-09-06.out`, 11 lines, `emitted=11`)

| Workload | Rounds | Cumulative Ratio Arm A ÷ Arm C | Overflow Rounds | Rounds Where Arm A More Economical |
|---|---|---|---|---|
| main (constant 8 leaves) | 100 | 0.9523 | 2 | 98 |
| main | 1000 | **0.9531** | 28 | 972 |
| main | 10000 | **0.9531** | 274 | 9726 |
| mixed (1 / 8 / 64) | 1000 | **0.7816** | 65 | 658 |
| mixed | 10000 | **0.7816** | 652 | 6578 |

**Load-bearing conclusion**: Under primary workload, endpoint where container is nearly full (ratio 1.050) **accounts for only 2.74% of publishes** (274 / 10000),
with cumulative ratio stabilizing at **0.9531** — **in expectation the knife edge tilts toward Arm A, by only 4.7%**.

**Manual calculation of overflow period** (independent of model output): Primary workload produces 17 records per publish, container holds 583 records
⇒ 17 000 records total across 1000 rounds, container boundaries crossed is `floor(17000 / 583) = 29`;
**one of which fills exactly, not counting as overflow** — `gcd(17, 583) = 1` and `17 × 583 = 9911`,
before round 583 `f = 566`, `566 + 17 = 583` exactly full ⇒ actual count **28**.
⚠️ **Initial modeling estimated 29 via `17 × 1000 / 583 ≈ 29.16`, missing this exact fill**; assertion corrected to 28 after re-expanding by manual arithmetic.

**Mixed workload intuition initially guessed in reverse**: Assumed single-leaf tier (Arm A 1.651×) would **pull up** cumulative ratio; actual measurement **pulled down** to 0.7816.
When weighted by bytes, large publishes dominate — manual calculation of one 1 / 8 / 64 cycle:
Arm A `332288 + 627200 + 3084800 = 4 044 288`, Arm C `201216 + 659968 + 4329984 = 5 191 168` ⇒ 0.7791.
Single-leaf tier is indeed more expensive, but absolute byte count is too small to lift cumulative value;
that dimension has a separate assertion nailing it (single leaf 332 288 vs 201 216 = 1.651×), proving it is active in model.
⚠️ **Note that the two figures express two different things**: by **bytes** Arm A saves 22%, by **rounds** Arm A is cheaper on only 65.8% of publishes.

**Controls and invalidation clauses**: Negative control (0 rounds, 0 leaves tested on both paths) pass;
cross-validation (three endpoints byte-for-byte identical with E107 (Stripe Table Write Amplification on Primary Workload)) pass;
expected value must fall strictly between those two endpoints — `0.9503 < 0.9531 < 1.0497` pass.

**Mutations**: 13 items in `scripts/mutation/tables/e110_stripe_table_steady.tsv`, **all 13 caught**.

### What It Cannot Answer

- **Covers written bytes dimension only, not overwrite patterns**. Space efficiency per `.claude/rules/fs-design.md` "comparing who saves more does not constitute any criterion" does not enter criteria;
  failure modes dimension (genuine criterion for format branches: turning "misused" into "unmountable") is **completely unanswered**.
- Leaf count distribution of `mixed` is modeling choice, **not measured workload profile** — real workload leaf distribution is absent from repo.
- Does not answer wall clock or latency (that half is Arm B of E107 (Stripe Table Write Amplification on Primary Workload)).
- Does not answer cost of branch "do not repair `w ≥ 3` stripes during disk lock period" when encryption enabled.
- Container occupancy evolves only by "accumulate records, open new when full", **lacking retirement and reclamation** —
  "records not deleted only retired" in D2 (RAID Stripe Policy) settled item 12 over long term reduces container utilization, dimension unmodeled.
