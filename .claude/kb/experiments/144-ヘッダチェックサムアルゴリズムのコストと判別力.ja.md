## E144 ヘッダチェックサムアルゴリズムのコストと判別力 —— 実行済み（2026-09-13、計時 + 決定的な判別力、8単体テスト / 10件ミューテーション全検出）

[中文](144-头校验和算法的代价与判别力.md) · [English](144-cost-and-discriminative-power-of-header-checksum-algorithms.en.md) · **日本語**

**問うているのは C309 (32 バイトのチェックサムのアルゴリズムが未定)である**：ユニットヘッダのチェックサム、ルートレコードの自己証明チェックサム、ジャーナルレコードヘッダのチェックサム、システム構成のスロット全体のチェックサムは、いずれも32バイト幅とカバー範囲だけが確定しており、ダイジェスト関数は未確定である。
ユーザーは「暗号と関係ないなら、もっと安くてよい」と指示した——これらの箇所が防ぐのは攻撃ではなく破損なので、候補は暗号学的ダイジェストでなくてもよい。
**七つの判定基準がすべて通過**：六つの正式アーム（SHA-256、BLAKE2s、xxHash64 × 4 シード、xxHash64、CRC-64/XZ、CRC32C）は、五つの実在するヘッダ幅で、1ビット反転、2ビット全数反転、ランダムなバイト変更のいずれも見逃しゼロ；
陽性対照（8ビット加算和）は2ビット全数反転で 11 892 件を見逃し、判別力テストは差を見分けられる；コストでは CRC32C が105バイトのヘッダに 26 ns、SHA-256 が 676 ns で、**26倍**；
14個のヘッダを1回の 359 µs の fsync に折り込むと、SHA-256 は 2.6%、CRC32C は 0.1% を占める。

**再実行コマンド**（`timing` モード：判別力の半分はバイト単位で比較し、ナノ秒の値は `replay.sh` の区間アサーションで固定する——crc32c 19〜37、sha256 473〜879）：

```bash
bash scripts/experiment-apparatus/replay.sh E144
# 装置を直接実行する：
cd scripts/experiment-apparatus && cargo run --release --bin e144-header-checksum-cost
```

コード `scripts/experiment-apparatus/e144_header_checksum_cost.rs`（六つの関数はそれぞれ公開テストベクタで固定：SHA-256 と BLAKE2s は `abc`、xxHash64 は空文字列と `abc`、二つの CRC は `123456789`）、
生出力 `e144-header-checksum-cost-2026-09-13.out`（129行、末行 `emitted=129`）、実行前登録 `e144-preregistration.md`、ミューテーション表 `scripts/mutation/tables/e144_header_checksum_cost.tsv`。

### 計測条件

- 判別力の半分は決定的（固定シード）：1ビット反転はすべてのビット（チェックサムフィールド自身のビットを含む）を走査する；2ビット反転は105バイトでフィールド外の584ビットの2ビット組合せ 170 236 組を全数走査する；ランダム変更はフィールド外の1〜8バイトを各 200 000 回変更する（変更後に元と同一になれば引き直す）；
  プローブは 1 000 000 個のランダムな42バイトのプレフィックスで、三つの数を報告する：magic + バージョン + 32バイトフィールド全体で通過、フィールド全体のみで通過、有効バイトのみで通過。
- 計時は変動のある観測である：アームごと・幅ごとに7ラウンド、各ラウンド 200 000 回、最小値を採り、ラウンドごとのばらつき（万分率）を別に報告する；本機のソフトウェア実装で、SHA-256 も CRC32C もハードウェア命令を使っていない。
- ミューテーション10件を全検出：五つの関数でそれぞれ定数を一つ変更（ベクタテストが赤）、対照を本物のハッシュに差し替え（対照テストが赤）、未使用バイトをゼロ埋めしない、fsync ごとのヘッダ数を12に変更、有効バイトのみを比較するプローブをフィールド全体の比較に変更、1ビット反転がチェックサムフィールドのビットを飛ばす。

### これらの数値が示すもの

1. **ヘッダのように短い入力では、判別力は六つのアームを区別できない**：1ビット、2ビット、ランダムな1〜8バイトの三種の破損は、32ビット以上のどの関数でも見逃されない；残るのは理論上のランダムな見逃し（CRC32C と xxh64 はそれぞれ 2⁻³² と 2⁻⁶⁴、32バイトは 2⁻²⁵⁶）とコストだけである。
2. **「安く」の桁**：SHA-256 は CRC32C の26倍高いが、絶対量は fsync 1回の 2.6% 対 0.1% ——「少し安く」で買えるのは fsync 時間の2.5ポイントであり、スループットの桁ではない。
3. **CRC32C はリポジトリで既に確定した関数である**（D19 (ブロックポインタ構造と幅予算) 確定項目 2 の暗号文チェックサム、D23 (ジャーナルの役割と形式) 確定項目 11 の逆方向チェーン）：これをヘッダチェックサムに採れば第二の関数を持ち込まない；32バイトフィールドでは4バイトを使い、残り28バイトはゼロ埋めし、magic がある場合のプローブ誤認は 0 である。
4. これらの数値はユーザー決定の代わりにはならない：候補間の取捨（暗号化が有効になった後の何らかの用途に備えて暗号学的ダイジェストを残すか否か）は射程外である。

### 答えられないこと

1. 1台のみ、ソフトウェア実装で、SHA-NI も SSE4.2 の `crc32` 命令も使っていない；命令を使えば比は変わる。
2. 判別力がカバーするのは反転、ランダムなバイト変更、ランダムなプレフィックスの三種のみ；セクタ全体の古い内容や引き裂きは、ユニット全体の CRC と親ポインタのチェックサムが担う（E142 (新規プールでのファイル作成のドライラン) の読み方）ので、ここでは扱わない。
3. 「32バイトフィールドを縮めるべきか」には答えない：幅は確定した条項である。
4. 計時は変動のある観測である：N 回走らせると異なり、7ラウンドの最小値と `replay.sh` の区間アサーションに頼る。
