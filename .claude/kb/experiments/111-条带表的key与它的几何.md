## E111 条带表的 key 与它的几何 —— 已跑（2026-09-06，8 单测 / 12 条变异全抓）：**三条 key 里只有「按落点排」答得出那句承重的问话；按落点排的树高 3、占 4631 ppm，是分配记录树的 10.5 倍**

**它答的是** D2（RAID 条带策略） 已定项 14（条带表这棵逻辑树的 key 取什么）。
D2（RAID 条带策略） 已定项 12 定了**载体**（住码 3 打包记录、走容器索引、容器恒走镜像），
**没说这棵逻辑树按什么排序**；而它的三个消费者问的都是同一句
「**给一个落点，它属于哪条条带**」——分配准入（C127（钉住状态在分配记录里没有落点））、
清扫准入（C128（清扫准入对 parity 格两支都判不出））、
让渡区 A 的签发判据（D9（加密） 未定项 9 那条第 ⑦ 合取）。
⚠️ **容器索引答不了这一句**：它的 key 是 `(出生树 ID, 打包记录类型, 容器号, 容器出生代)`，
**四段里没有落点**，容器号按 C103（容器索引无落点） 是「最大号 + 1」单调分配，

### 三条臂

| 臂 | key 取什么 | 「给落点找条带」怎么答 |
|---|---|---|
| `slot` | 落点（设备身份 4 + 16 KiB 槽号 6），与 D3（空间分配） 已定项 3 的分配记录树同坐标系 | **一次点查** |
| `stripe` | 条带号（条带诞生代 8 + 条带序号 4） | **答不了**——要扫全表 |
| `none` | 不排序，只按容器身份索引（**今天的状态**） | **答不了**——要扫全部容器 |

### 口径（跑前写死）

1. 几何全部指得到已定条款：单元 32768（D4（校验和位置） 已定项 1）、节点 16384（D8（核心索引结构） 已定项 2）、
   容器头 103 与成员记录 56（D18（块里携带什么信息） 已定项 11 / E106（条带成员表的载体） 已钉）、
   落点 key 段宽 4 + 6（D19（块指针的结构与宽度预算） 已定项 4 与 D3（空间分配） 已定项 7 同坐标系）。
2. **与 E97（记账与分配记录的条目编码） 同尺**：16 TiB / 90% 填充，条目数与树高按同一套算法算，
   便于与分配记录树（483 183 820 条、树高 4、442 ppm）直接比。
3. **一格一条、含 parity 格**（D2（RAID 条带策略） 已定项 12）⇒ 条目数按**格数**算，不按单元数算。
4. `w` 扫 2 / 3 / 4。`w = 2` 全镜像、一条条带记录都不写 ⇒ 条目数恒 0，这是阴性对照。

**空间那一维仍然要摆出来看付不付得起**：按落点排的树在 `w = 3` 上占 **4631 ppm ≈ 0.46% 容量**，

### 它答不了的

- **不答这棵树自己的更新代价**：每次发布要改写多少条、COW 多少节点，那是 C103（容器索引无落点） 与
  E107（条带表对主负载的写放大） 的射程，E111（条带表的 key 与它的几何） 只算稳态几何。
