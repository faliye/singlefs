## E111 条带表的 key 与它的几何 —— 已跑（2026-09-06，9 单测 / 13 条变异全抓）：**三条 key 里只有「按落点排」答得出那句承重的问话；按落点排的树高 3、占 3087 ppm，是分配记录树的 6.98 倍，且条目数与 `w` 无关**

**它答的是** D2（RAID 条带策略） 已定项 14（条带表这棵逻辑树的 key 取什么）。
D2（RAID 条带策略） 已定项 12 定了**载体**（住码 3 打包记录、走容器索引、容器恒走镜像），
**没说这棵逻辑树按什么排序**；而它的三个消费者问的都是同一句
「**给一个落点，它属于哪条条带**」——分配准入（C127（钉住状态在分配记录里没有落点））、
清扫准入（C128（清扫准入对 parity 格两支都判不出））、
让渡区 A 的签发判据（D9（加密） 已定项 9 那条第 ⑦ 合取）。
⚠️ **容器索引答不了这一句**：它的 key 是 `(出生树 ID, 打包记录类型, 容器号, 容器出生代)`，
**四段里没有落点**，容器号按 C103（容器索引无落点） 是「最大号 + 1」单调分配，
与它装的记录覆盖哪些落点**无函数关系**。

### 三条臂

| 臂 | key 取什么 | 「给落点找条带」怎么答 |
|---|---|---|
| `slot` | 落点（设备身份 4 + 16 KiB 槽号 6），与 D3（空间分配） 已定项 3 的分配记录树同坐标系 | **一次点查** |
| `stripe` | 条带号（条带诞生代 8 + 条带序号 4） | **答不了**——要扫全表 |
| `none` | 不排序，只按容器身份索引（**今天的状态**） | **答不了**——要扫全部容器 |

### 口径（跑前写死）

1. 几何全部指得到已定条款：单元 32768（D4（校验和位置） 已定项 1）、节点 16384（D8（核心索引结构） 已定项 2）、
   容器头 103 与成员记录 56（D18（块里携带什么信息） 已定项 11 / E106（条带成员表的载体） 已钉）、
   落点 key 段宽 4 + 6（D19（块指针的结构与宽度预算） 已定项 4 与 D3（空间分配） 已定项 7 同坐标系）。
2. **与 E97（记账与分配记录的条目编码） 同尺**：16 TiB / 90% 填充，条目数与树高按同一套算法算，
   便于与分配记录树（483 183 820 条、树高 4、442 ppm）直接比。
3. **一格一条、含 parity 格**（D2（RAID 条带策略） 已定项 12）⇒ 条目数按**格数**算，不按单元数算。
   ⚠️ **90% 那笔预算是数据格与 parity 格一起花的**：一条 `w` 列的条带占 `w` 个格、其中 1 个是 parity
   ⇒ 总格数恒等于这笔预算切出来的 483 183 820 格，`w` 只改这笔预算里有多少是用户数据。
   **不许把 483 183 820 当成数据格数再往上加 parity**——那样 `w = 3` 会往 16 TiB 的盘上摆 135% 的格
   （E106（条带成员表的载体） 第一版的 126.3% 是同一个错，E111（条带表的 key 与它的几何） 第一版重犯了一次，
   见「历史版本」；现在由 `cells_never_overfill_the_pool` 挡住）。
4. `w` 扫 2 / 3 / 4。`w = 2` 全镜像、一条条带记录都不写 ⇒ 条目数恒 0，这是阴性对照。

### 结果（2026-09-06，产物 `research/results/e111-stripe-table-key-2026-09-06.out`，14 行、`emitted=14`）

| `w` | 数据格 | parity 格 | 条目数 | 按落点排的树高 | 这棵树占 |
|---|---|---|---|---|---|
| 2 | 0 | 0 | **0** | — | **0 ppm** |
| 3 | 322 122 547 | 161 061 273 | **483 183 820** | **3** | **3087 ppm** |
| 4 | 362 387 865 | 120 795 955 | **483 183 820** | **3** | **3087 ppm** |

⇒ **条目数与 `w` 无关**：90% 那笔预算切出多少格就有多少条记录，`w` 只改这些格里数据与 parity 的配比。
这一条换口径之后才看得见，第一版把 `w` 读成了条目数的自变量。

**承重的那一条不是量出来的，是三条 key 的定义直接给的**：`slot` 臂答得出那句问话，
另外两条答不出。⇒ 这一格的判据**不在空间上**（`.claude/rules/fs-design.md`「比谁省不构成任何判据」），
在「有没有一条 key 让那三个消费者问得出话」。

**空间那一维仍然要摆出来看付不付得起**：按落点排的树占 **3087 ppm ≈ 0.31% 容量**（`w = 3` 与 `w = 4` 同值），
是同尺下分配记录树（442 ppm）的 **6.98 倍**。
两条 key 的扇出确实不同（落点 key 10 字节 ⇒ 906，条带号 key 12 字节 ⇒ 815），
但在这个条目数上**树高都是 3**，所以扇出不改这个 ppm；差别全在**条目数**：
分配记录一个数据单元一条，条带表一格一条、含 parity 格。

⚠️ **这个字节数与 E106（条带成员表的载体） 的臂甲镜逐位相同**（`54 315 515 904` 字节、3087.5 ppm）——
两个实验用互不相同的算法算同一个量而落到同一个数。这个交叉校验换口径之后才出现：
旧口径下 E111（条带表的 key 与它的几何） 报 4631、E106（条带成员表的载体） 报 3087.5，两边差 1.5 倍而**谁也没去对**。

⚠️ **建档当日曾写成「它顺带纠了 E106（条带成员表的载体） 一处口径」，那句是反的，已撤回**：
E106（条带成员表的载体） 的 483 183 820 从来就是**被占用的落点总数**（含数据格、parity 格与容器），
不是数据格数——它自己第一版犯过「当成数据格数再加 parity」的错并当日修掉，
还留了 `locs <= occupied_slots()` 那条会红的断言。
错的是 E111（条带表的 key 与它的几何） 第一版，它把 E106（条带成员表的载体） 修掉的那个错重做了一遍。
⇒ **D2（RAID 条带策略） 已定项 12 正文里那一行按此回改**（4631 → 3087，与 E106（条带成员表的载体） 一致）。

**对照**：阴性对照（`w = 2` 三条臂条目数恒 0）pass；
同尺交叉校验（**总格数** 483 183 820 与 E97（记账与分配记录的条目编码） 已入库的条目数**逐位相同**）pass；
阳性对照（换 key 宽度扇出必须跟着变：906 对 815）pass；
**越界闸**（`cells_never_overfill_the_pool`：三档 `w` 摆进去的格 × 32768 都不许超过 90% 那笔预算，
并自带判别力——第一版那个 724 775 730 必须被它判红）pass。

**变异**：`research/mutations/e111_stripe_table_key.tsv` **13 条，13 条全部被抓**，基线跑前跑后全绿，
日志 `research/results/e111-mutate-2026-09-06.log`。其中 **M13（parity 加在预算之上）就是第一版那个错**——
把踩过的坑做成一条会红的变异，而不是一句提醒。
⚠️ **这是确定性模型**：证据强度来自变异与钉死绝对值的断言，不来自轮数。
**手算（逐步列出来）**：条目 483 183 820 ÷ 583 条每容器 ⇒ `583 × 828 788 = 483 183 404 < 483 183 820`
⇒ 向上取整 **828 789** 个容器；容器恒走镜像 ⇒ `828 789 × 32768 × 2 = 54 315 515 904` 字节
⇒ `÷ 16 TiB × 10⁶` = **3087 ppm**。

### 它答不了的

- **不答这棵树自己的更新代价**：每次发布要改写多少条、COW 多少节点，那是 C103（容器索引无落点） 与
  E107（条带表对主负载的写放大） 的射程，E111（条带表的 key 与它的几何） 只算稳态几何。
- **不答挂钟**，也不答那次点查在分配路径上的真实延迟。
- **不答容器索引怎么建**——`slot` 臂假定条带表这棵逻辑树自己按落点排、容器索引仍只做「容器身份 → 物理指针」，
  而**容器索引本身住哪今天全仓无落点**（C103（容器索引无落点））。
- **只在 16 TiB / 90% 这一个点上算**，不是扫出来的曲线；`w` 只扫 2 / 3 / 4 三档。
- `stripe` 臂的 key 段宽（诞生代 8 + 序号 4）是**建模选择**，仓里没有一条条款定过它。

## 历史版本

### 2026-09-06（其二）：口径改回「90% 是一笔共享预算」，条目数 724 775 730 → 483 183 820

- **改前**：`cells()` 把 `16 TiB × 90% ÷ 32768 = 483 183 820` 当成**数据格数**，再往上加
  `parity = 数据格 / (w−1)`，`w = 3` 得 724 775 730 个 32 KiB 格。
  **那是 16 TiB 盘的 135%**——建档时没有任何断言看着这一维。
- **改后**：那笔 90% 预算由数据格与 parity 格**一起**花，一条 `w` 列的条带占 `w` 个格、1 个是 parity
  ⇒ 总格数（= 条目数）恒 483 183 820，与 `w` 无关；`w` 只改其中数据与 parity 的配比。
- **连带改动的结论数**：条目数 724 775 730 / 644 245 094 → **483 183 820（两档同值）**；
  ppm 4631 / 4116 → **3087（两档同值）**；对分配记录树的倍数 10.5 → **6.98**；
  `stripe` 臂的树高 4 → **3**（两条 key 在这个条目数上同高，扇出差别不再改树高）。
- **承重结论一个字不改**：三条 key 里只有 `slot` 答得出「给一个落点它属于哪条条带」，
  而那一条从来不是量出来的，是三条 key 的定义直接给的。
- **发现经过**：核 E106（条带成员表的载体） 与 E111（条带表的 key 与它的几何） 对同一个量报的两个数
  为什么差 1.5 倍。E106（条带成员表的载体） 的正文与源码都写明 483 183 820 是**被占用的落点总数**，
  且它自己第一版犯过同一个错（126.3%）、当日修掉并留了 `locs <= occupied_slots()` 那条会红的断言。
  ⇒ 建档当日写下的「E111（条带表的 key 与它的几何） 顺带纠了 E106（条带成员表的载体） 一处口径」方向是反的，已撤回。
- **这个坑现在有会红的形态**：新增单测 `cells_never_overfill_the_pool`（三档 `w` 都不许摆超 90% 预算，
  并自带判别力——第一版那个 724 775 730 必须判红）与变异 M13（parity 加在预算之上）。
  单测 8 → **9**，变异 12 → **13**，13 条全抓。
- ⚠️ **两个实验对同一个量的交叉断言仍然欠着**：这次是靠人去对才发现的，
  没有任何检查在 E106（条带成员表的载体） 与 E111（条带表的 key 与它的几何） 之间比过那个字节数。
  账记 [checks-owed.md](../checks-owed.md) C155（跨实验同量无交叉断言）。
