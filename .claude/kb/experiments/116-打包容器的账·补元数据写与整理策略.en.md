## E116 (Packed Container Balance: Metadata Writes and Compaction Strategy) — Executed (2026-09-07, pure arithmetic; 2026-10-04 header 311 -> 487 re-run: artifact, 20 unit tests, and 19 mutation table entries produced for both before and after, post-modification 19/19 caught)
[中文](116-打包容器的账·补元数据写与整理策略.md) · **English** · [日本語](116-打包容器的账·补元数据写与整理策略.ja.md)

Answers whether the payoff of D27 (small-data packing container) is "positive or negative", and separates the two ledgers that E114 (Overall Accounting of Small Data Packed Containers) conflated.

### Why It Exists

The write ledger of E114 (Overall Accounting of Small Data Packed Containers) only counted data units; whereas the 2026-09-07 second round of argumentation directly subtracted **one-time written bytes** from **permanently reclaimed space** to conclude that "net payoff is negative"—the two quantities have different units and no exchange rate in between.
E116 (Packed Container Balance: Metadata Writes and Compaction Strategy) splits this into three ledgers, each reported independently, providing the only metric that puts both onto the identical scale.

| Ledger | Unit | What It Asks |
|---|---|---|
| Steady-state occupancy | Bytes, resident | How much disk space the identical batch of live objects permanently occupies |
| One-time relocation writes | Bytes, one-off | How much write volume is needed to move into container (container + central mapping + allocation record + journal, all four counted) |
| **Payback ratio** | Dimensionless | One-time relocation writes / permanently reclaimed space. **How many bytes must be written to permanently reclaim 1 byte** |

### Four Arms

| Arm | Compaction Strategy |
|---|---|
| `pad` | No packing (current practice) |
| `bg_key` | Background compaction proceeds along central mapping key order => sequential hit on mapping leaves |
| `bg_fill` | Background compaction proceeds along container fill order, batch size `b` => random scatter across mapping leaves |
| `bg_ideal` | Metadata writes recorded as 0 (**payoff upper bound control, not a candidate**) |

### Conclusion 1: Structural Lower Bound of Payback Ratio is `w / (cap - 1)`, Independent of Implementation

`bg_ideal` falls squarely onto this closed-form expression cell-by-cell (pinned by assertion `ideal_payback_is_w_over_cap_minus_one`).
=> **D27 (small-data packing container) breaks even if and only if `cap > w + 1`.** First edition `w` = 2 => requires `cap >= 4`.

### One Modeling Error (Fixed Same Day), and Two Pre-Registered Formulas Refuted

**Allocation records were computed by placement as two per unit; D3 (space allocation) settled item 7 verbatim states "one record per unit, with additional span segment".**
Pointed out by measurement basis reviewer, main agent verified verbatim, immediately corrected and re-ran; payback ratios of three tiers dropped ~2% each, 8 KiB tier 1.0164 -> **1.0142, still > 1**, conclusion direction unchanged; after journal record header was calculated at 95 that tier was 1.0150, at 277 it was 1.0233, at 307 (D23 (Role and Format of Journal) settled item 4 plus fsid 8 and MAC 16, settled item 15 new root segment expanded from 182 to 188) it was 1.0247, at 311 (2026-09-24, settled item 4 plus intra-publish sequence number 4) it was 1.0249, at 487 (2026-10-04, settled item 15 new root segment 188 -> 364) it was **1.0330, still > 1**—conclusion direction unchanged every time.

### Two Pre-Registered Formulas Refuted, Three Numbers Retained in Source Code

1. **At `b` = 1 payback ratio registered as 1.058893, currently measured as 2.104781.** The registered value came from second round calculating only central mapping ledger,
   whereas fill order scatters allocation records as well (101 725 mutations scattered across 113 leaves), plus journal.
   Direction and magnitude of refutation remained steady through subsequent constant changes: first version measured 3.127186 (allocation records computed by placement, modeling error, fixed same day);
   after changing to D3 (space allocation) settled item 7 verbatim "one record per unit" it became 2.092080 (journal header 78);
   at header 95 it was 2.092608, at header 277 it was 2.098260, at header 307 it was 2.099192, at header 311 (2026-09-24) it was 2.099316, at header 487 (2026-10-04) it was **2.104781**. All seven numbers are kept in harness's `payback_fill_b1_absolute`.
2. **"`b` = N converges to key order" refuted**: The central mapping tree indeed converges (modifying 100 000 entries, `b` = 100 000 => 1 batch),
   but allocation records modifying 101 725 entries > `b` => still requires 2 batches, each hitting all 113 leaves.
   **"Batching all at once" is not the identical `b` across the two trees.**

### Mutation `M14` is a Real Blind Spot, Neither Equivalent Nor Sample-Insensitive

M14 changes "probability of all slots dead `d^cap`" to `d`, and in round one **not a single test failed**—
because dead slot assertion `death_uniform_never_worse` is a relative comparison (`pack <= pad`),
which remains true after changing to `d`. Per `.claude/rules/mutation-sampling.md` tripartite division: changing any sample point fails to catch it,
because **no assertion pinned that absolute value** => real blind spot. Caught immediately after adding `death_uniform_absolute`, 16/16 blind spot free.

### What It Cannot Answer

Pure arithmetic ledger: **no implementation, no I/O, no crash-point replay**. Does not answer wall clock, does not answer cache, does not answer concurrency.
**Reclamation latency not modeled** (fully dead containers assumed released immediately).
Does not answer "whether this payoff qualifies for entry into format"—that question is answered by `.claude/rules/fs-design.md` format branch criteria, not by numbers.
Workload defined internally by E116 (Packed Container Balance: Metadata Writes and Compaction Strategy), outside the domain of D25 (Target Workload Priority).
