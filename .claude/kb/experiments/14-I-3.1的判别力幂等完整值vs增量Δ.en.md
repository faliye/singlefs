## E14 Discriminative Power of I-3.1: Idempotent Full Value vs Incremental Delta — Run (2026-08-27, 5 Seeds Fully Consistent)

[中文](14-I-3.1的判别力幂等完整值vs增量Δ.md) · **English** · [日本語](14-I-3.1的判别力幂等完整值vs增量Δ.ja.md)

**Conclusion**: `I-3.1` (Allocated Accounting Reconciles) (incremental accounting vs traversal recalculation) **has zero discriminative power against incremental delta forms**—
none of the four injected classes of semantic bugs were caught, while all four **computed incorrect accounts**.
The same four classes of injection on idempotent full value forms: all three true bug classes were caught, and the fourth was fundamentally not a bug.
**Therefore Cost 1 of D11 (Message Buffers in Index Nodes) holds**: under incremental delta forms, discriminative power of I-3.1 (Allocated Accounting Reconciles) does not merely degrade; it drops to zero.

**Measurement Basis**: Pure logic experiment, no devices, no VMs, no file system. 20,000 operations / 512 keys /
batch size 64 / 5 seeds (11 22 33 44 55), all 5 seeds yielded fully consistent conclusions (satisfying both sides of
`test-discipline`: "verdicts of pass require all passing, verdicts of fail require all failing").
Re-run: `cargo run --release --bin e14-discrimination`, code `scripts/experiments/e14_discrimination.rs`.
Raw output `e14-discrimination-2026-08-29.out` (2026-08-29 re-run, cell-by-cell identical to E14 (Discriminative Power of I-3.1: Idempotent Full Value vs Incremental Delta) figures).

### Mechanism: Why Incremental Delta Side Cannot Even Catch "Dropping a Single Message"

**The premise for a checker to independently recalculate is the existence of authoritative content that bypassed accumulation logic.**

- Idempotent full value form: authoritative state is content (key → value). Accounts are its cache.
  Checker traverses content to sum, **sharing nothing** with runtime code that "incrementally maintains on buffer entry"—
  two paths are independent, so any semantic error on flush side causes them to diverge.
- Incremental delta form: **accounts themselves are authoritative content**, with nothing else to traverse.
  Checker's sole recalculation method is replaying the exact same persisted delta log using the exact same accumulation function.
  If log drops an entry, both sides drop it; if sign inverts, both sides invert—**it is comparing against itself**.
  This matches the form of `this_cpu_add(e->v[gc][i], a.v->d[i]);` in bcachefs `disk_accounting.h`:
  `this_cpu_add(e->v[gc][i], a.v->d[i])`, where runtime and GC rebuild differ only by a single subscript.

### Critical Modeling Point (Failure to Model This Yields No Measurements Upon Re-run)

**Runtime accounting must be maintained incrementally when entries enter buffer, and tree must update upon flush merge—two distinct moments, two distinct code paths.**
This directly reflects [fs-design.md](../../rules/fs-design.md) "accounting is a byproduct of transactions".
If accounts are derived from merge results, I-3.1 (Allocated Accounting Reconciles) degenerates into an identity, all four injections produce 0/5 on both forms,
and the entire experiment measures nothing.

### What E14 (Discriminative Power of I-3.1: Idempotent Full Value vs Incremental Delta) Cannot Prove

- **Does not cover crashes.** Zero crash points or replays throughout; only addresses "whether I-3.1 (Allocated Accounting Reconciles) catches semantic write bugs under steady state".
- **Does not cover gains side of D11 (Message Buffers in Index Nodes).** Gains are 1.50×–4.96× of E7 (Offline Index Harness), not measured here at all.
- **The four injected classes are not exhaustive.** They represent four classes of "semantic write bugs", not "all possible bugs".
  Detection rates of 3/3 and 0/4 apply only to these four classes; extrapolating to other bug classes requires separate arguments.
