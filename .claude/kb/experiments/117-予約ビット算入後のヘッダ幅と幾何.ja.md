## E117 予約ビット算入後のヘッダ幅と幾何 —— 実施済（2026-09-07、純算術、12 単体テスト / 12 ミューテーション全捕捉）

[中文](117-预留位算进去之后的头宽与几何.md) · [English](117-header-width-and-geometry-after-factoring-in-reserved-bits.en.md) · **日本語**

**問うているのは**：D18 (ブロックに含める情報) 確定項目 7 のフィールド表が算出したデータユニットヘッダ 105 バイトに対し、
**同節の「v1 で nonce 記号と MAC のフィールド枠を予約」という文にある 2 つの枠が表外にあった点である**。
それらを算入した後に 3 種のユニットのヘッダ幅がそれぞれどうなり、下流の幾何がどれだけ変化するか。

**答えているのは** C193 (暗号化有効時のユニットヘッダサイズが全リポジトリで未計算)であり、また
D18 (ブロックに含める情報) 確定項目 14 の確定前にユーザーが求めた数値でもある
（ユーザー：「甲を採用するが、まずヘッダ幅を明確に計算してから確定せよ」）。

### 3 本のアーム

| アーム | 予約ビット | 内容 |
|---|---|---|
| `bare` | 0 | 2026-09-07 に 4 つの下流実験で使用された計測条件 |
| `resv12` | 12 + 16 = 28 | 確定項目 14 **アーム甲**：nonce 記号 = 完全な 96 ビット nonce、MAC フル 128 ビット |
| `resv4` | 4 + 16 = 20 | **判別力対照アーム、候補ではない** —— 記号が 4 バイトのみの場合 |

| 条項 | 使用箇所の記述 |

| D9（暗号化） 確定項目 2 | MAC フル 128 ビットで切り詰めなし ⇒ 予約 MAC 枠 16 バイト |
| D9（暗号化） 確定項目 4 | 「ポインタヘッダは論理 extent ごとに 96 ビット nonce を 1 つ保持」⇒ 完全な nonce 12 バイト |
| D18 (ブロックに含める情報) 確定項目 7 補足 | E73 (ノードキー区間のファンアウトコスト) の 3 段階下界 58 / 67 / 76 にそれぞれ書き込み順序 10 と生成連番 4 を加算し 72 / 81 / 90 となる |
| D19 (ブロックポインタ構造と幅予算) 確定項目 4 | ポインタ 59 ⇒ 内部エントリ幅 22 + 59 = 81（E73 (ノードキー区間のファンアウトコスト) 自身は 22 + 32 = 54 を使用） |

### 実施前確定の判定基準と失敗条件

1. ヘッダ幅閉形式：各クラスのヘッダ = 表内フィールド + 予約ビット、クラスごとに絶対値を固定。
2. Code 2 ファンアウト = `(16384 − ヘッダ) / エントリ幅`、エントリ幅は 54 と 81 の 2 値を採用、マスごとに絶対値を固定。
3. Code 3 コンテナあたりレコード数 = `(32768 − ヘッダ) / 140`、マスごとに絶対値を固定。
4. Code 1 正味ペイロード = `32768 − ヘッダ`、マスごとに絶対値を固定。
5. **判別力**：`resv12` と `resv4` は少なくとも 1 マスで異ならなければならない。全マス一致 ⇒ 「サンプリング点非感度」と判定（`.claude/rules/mutation-sampling.md` 第 3 類）、整数境界を跨ぐサンプリング点を探索すること、**「予約ビットは幾何に影響しない」と記録することは禁止**。
6. **陽性対照のアーム別実行**：ヘッダを強制的に 0 とした際、ファンアウト = ユニット / エントリ幅、レコード数 = 32768 / 140。
7. **陰性対照**：エントリ幅 > 利用可能バイト数 ⇒ 0 を返却。

**失敗条件**：判定基準 5 が不成立の場合に判定基準を変更することは禁止、第 3 類に従いサンプリング点を補うこと。

### 実測

| アーム | Code 1 ヘッダ | Code 3 ヘッダ | Code 1 ペイロード | Code 2 の 3 段階ヘッダ | ファンアウト（エントリ 54） | ファンアウト（エントリ 81） | Code 3 コンテナあたりレコード数 |
|---|---|---|---|---|---|---|---|
| `bare` | 105 | 107 | 32663 | 72 / 81 / 90 | 302 / 301 / 301 | 201 / 201 / 201 | 233 |
| **`resv12`（アーム甲）** | **133** | **135** | 32635 | 100 / 109 / 118 | 301 / 301 / 301 | 201 / 200 / 200 | **233** |
| `resv4` | 125 | 127 | 32643 | 92 / 101 / 110 | 301 / 301 / 301 | 201 / 201 / 200 | 233 |

⇒ **アーム甲の幾何代償はファンアウトがそれぞれ 0〜1 マス低下し、Code 3 のコンテナあたりレコード数は 1 マスも低下しない。**

### 3 つの対照の判定

| 対照 | 判定基準 | 実測 |
|---|---|---|
| 陽性（アーム別） | ヘッダが 0 のときファンアウト = 閉形式値 | 3 本のアームすべてが 303 / 202 / 234 を出力 |
| 判別力 | `resv12` と `resv4` が少なくとも 1 マスで異なる | **充足**：エントリ幅 81 の第 2 段階で、`resv12` は 200、`resv4` は 201 を出力（成果物 `cells_differing=1`） |
| 陰性 | エントリ幅 > 利用可能バイト数 | 0 |

⚠️ **判別力のマスは E73 (ノードキー区間のファンアウトコスト) 自身のエントリ幅には存在しない**：エントリ幅 54 では両アームがマスごとに一致し、
切り捨て処理がその 8 バイト差を吸収した。`.claude/rules/mutation-sampling.md` によるとこれは**サンプリング点非感度**であり、
「予約ビットが幾何に影響しない」ということではない —— 単体テスト `t10` に保管され、判別力は `t09` のマスが担保する。

### 実施前に登録された値が否と判定、記録は改ざんせず維持

判定基準 2 で実施前に登録されたのは「`bare` の 3 段階すべてが 302」であったが、**実測は 302 / 301 / 301** であった ——
第 2 段階 `(16384 − 77) / 54 = 301.05` で既に 1 マス低下している。
登録された値はメイン agent が手計算の際に第 1 段階のみ計算して外挿したものであった；**2 回目の判定修正時にも第 3 段階のみ修正し、依然として第 2 段階を計算しなかった**。
2 回とも同一の誤りに起因する：**1 つのサンプリング点を 3 つと見なしたこと**。
E73 (ノードキー区間のファンアウトコスト) 自身の記述は「3 段階の結論は一致（0 または 1 マス低下）」であり、実測と矛盾しない；
矛盾するのは E117 (予約ビット算入後のヘッダ幅と幾何) の実施前のより強い登録値である。両値ともソースコード `t03` 内に残されており、実施前の値を正値に改変することは禁止される。

### 本実験で答えられないこと

純算術、I/O なし、クラッシュポイント再生なし。「E73（ノードキー区間のファンアウトコスト） の子ポインタ幅 32 を
59 に変更すべきか」には答えない —— それは C89 (ユニットヘッダ収束の未済再計算) の勘定であり、ここでは両方の幅を提示するにとどまる。
E97 (記帳および割り当て記録のエントリ符号化)/ E98 (inodeレコードとinodeツリーの幾何)/
E103 (inodeパッキング経路1の更新コスト) の内部モデルを再計算せず、それらの荷重受け幾何数値が新ヘッダ幅の下でいくつになるかを報告するのみである。
**N ラウンド実行は隠蔽された状態が存在しないことを示すものであり、統計的安定性を示すものではない** —— 決定論的モデルである。
