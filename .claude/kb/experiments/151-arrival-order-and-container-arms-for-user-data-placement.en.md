### This is a deterministic model, not a measurement

Fixed seeds and no I/O ⇒ N runs are byte-identical. Evidence strength comes from **absolute values pinned in 27 unit tests + all 22 mutations caught**: arrival not shuffled; container holds 8; packing ignores hysteresis; incremental runs break only at the same slot; container slot enters defer early; one cell in cross-apparatus table changed; commit-endogenous blocks never released; empty-segment count never decremented; tie band changed to 10%; B uses lowest slot; fallback not counted; sweep sees only one key; request arrival does not shuffle requests; commit-endogenous fallback not accounted separately; budget parameter overridden by constant; directory hint ignores members' segments; directories grouped at twice the size; fixed-home hint forgets overflow; overflow-count parameter overridden by tail-segment count; request-order count reversed; relocation excluding `R` forgets `R`; one free slot in `R` counted as entirely empty. ### Model

Use E93's slot / defer / runs definitions; node skeleton as E127 (Whether to Store Group Identity Under Splits and Merges), but without split or merge. A single-object node holds one key, a container ≤ 7 consecutive keys; when a member is dirtied it is COW-moved out as a single object, and the two remaining pieces stay in the same slot (runs treats them as one container). Once all members move out, the slot enters defer. Runs are counted in key order. Two arrival arms: uniform permutation (reshuffle E93's ascending dirty set with the same RNG), and by request (a consecutive run of dirty keys is one request, shuffle requests using the same RNG while retaining key order within each, per D16 settled item 5's “one write request is split by unit into transactions, each doing its own number acquisition”). Besides final entirely empty clustered segments, record when the initial (S − L) / G = 32 segments are exhausted, the peak afterward, and rounds with positive readings afterward; count commit-endogenous fallback separately. Each checkpoint scans ≤ 64 keys in key order; seven consecutive single-object keys last written ≥ K ago form a container placed by bump. Each checkpoint allocates M commit-endogenous blocks from the bump segment; they enter defer next round.

### What it cannot answer

1. Counting model: no timing axis or real hardware; fixed-width objects all in the ≤ 4 KiB category.
2. Packing rules are assumptions (≤ 64 keys scanned per checkpoint, capacity 7, key order, hysteresis since last write); D27 settled item 6's “one mapping leaf per transaction” and rate limit are not modeled. Container write amplification counts one write per container, not bytes.
3. Commit-endogenous blocks occupy segments only, with no trees and no runs; lifetime is one checkpoint (allocated blocks enter defer at the start of the next). All three M levels allocate from the same bump segment and compete with user data for the same open segment. First_fit's zero fallback is a lower bound under that lifetime; real tree nodes live longer.
4.
