### 路径 1：三个边界，取错的后果确实不对称——但不是三处独立的笔误

D5（快照 / 空间记账机制）定义句原样：**块 b 被快照 S 引用 ⟺ `birth(b) ≤ S.txg < death(b)`，左闭右开。**

| 规则 | 数据丢失 | 泄漏 | 与正文一致 |
|---|---|---|---|
| `birth ≤ S < death`（正文） | 0 | 0 | **3 / 3** |
| `birth < S < death`（左边界写严） | **1** | 0 | 2 |
| `birth ≤ S ≤ death`（右边界写闭） | 0 | **2** | 1 |

**两条结论**：

1. **两种取错的失败方向确实相反**——写严左边界只造成数据丢失，写闭右边界只造成泄漏。
   D5（快照 / 空间记账机制）正文那张「后果不对称」的表得到证实。
2. ⚠️ **但「写闭右边界」同时命中两个边界，不是一个。**
   `birth ≤ S ≤ death` 在 `death == S.txg` 与 `birth == death` 两格上都判成「引用」。
   ⇒ **正文把三个边界列成三行，读起来像三处独立的笔误；实际上同一个笔误同时命中两行。**
   本实验第一版按正文那张表猜成「一次泄漏」，当场红了。已回写 D5（快照 / 空间记账机制）。

### 路径 2：deadlist 级联合并，按 birth 分桶省一半左右

量的是**检查过的条目数**，不是时间。目标快照取中位。

| deadlist 条目 | 不分桶 | 桶宽 16 | 桶宽 64 | 桶宽 256 |
|---|---|---|---|---|
| 64 | 64 | **34** | 64 | 64 |
| 256 | 256 | **136** | 130 | 256 |
| 1024 | 1024 | **544** | —— | —— |

⇒ 分桶把检查量压到约 **53%**；**桶宽等于条目数时退化成不分桶**（整桶跳不掉）。
省下的恰是「整桶都比目标老」那一半——绝对值可算：
1024 条、桶宽 64、目标在 512 ⇒ 前 8 个桶整桶跳（各付一次桶头检查）+ 其余 512 条逐条 = 520。

### 路径 4：defer 队列的持久化代价

D16（发布语义）新规则 2 要求 checkpoint 内的释放在发布前不得进入可分配集合
⇒ 本该「立即释放」的那一半也要先进 defer 队列，那是额外的持久化写。

**条目数与 I/O 次数是两个指标，不许混**：条目数只由释放数决定，
I/O 次数是条目数按打包宽度向上取整（16384 条、每块 128 条 ⇒ 128 次；每块 512 条 ⇒ 32 次）。

### 口径与已知局限

- 纯逻辑与纯计数，无设备、无事务层。
- **路径 3 完全没做**，D5（快照 / 空间记账机制）的崩溃重放风险仍是零覆盖。

  分桶的收益强依赖分布，均匀分布是最有利于分桶的那一种之一。
