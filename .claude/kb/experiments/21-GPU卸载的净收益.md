## E21 GPU 卸载的净收益 —— 三段全部已测（2026-08-28）；带宽受限那格判负收益，其余**暂缓不排期**

### 已跑的两段，以及它们单独就能判掉什么

**判据 1 是 `CPU 16 线程耗时 ÷ (传输 + 计算 + 传回) 耗时`，小于 1 就否掉那一格。**
⇒ **即使核函数耗时为零**，GPU 路径也至少要付传输。那一段就是 GPU 侧的**地板**，
而 CPU 的内存带宽是 CPU 侧的**上限**。两者一比，不必等核函数写出来就能判掉一部分。

| 路径 | 吞吐 | 性质 |
|---|---|---|
| CPU 扫描（XOR 折叠，2 GiB，5 轮取最好） | **64.91 GB/s** | 内存带宽墙，CPU 侧**上限** |
| GPU 单程（锁页 H2D，≥64 MiB） | 56.69 GB/s | 传输**地板** |
| GPU 来回（H2D + D2H 串联） | **28.5 GB/s** | 传输**地板** |

**⇒ 判据：GPU 只可能在「CPU 那一侧的实际吞吐低于 GPU 的传输地板」时赢。**

| 场景 | 传回什么 | GPU 地板 | CPU 侧要慢到什么程度 GPU 才有机会 |
|---|---|---|---|
| 全盘 scrub | 只回一个结论 | 56.7 GB/s | < 56.7 GB/s |
| 批量压缩 | 压缩后的数据（比传入小） | 40.6 GB/s（压缩比 0.5）／47.6（0.25） | < 那个数 |
| **EC 重建** | **全部重建数据** | **28.5 GB/s** | **< 28.5 GB/s** |

**用 [experiments.md](../experiments.md) E6（加密算法选型） 已测的加密吞吐代入**：有 AES-NI 时单核 4.1 GB/s，
16 核约 65 GB/s，但会撞上 64.91 GB/s 的带宽墙 ⇒ **高于所有 GPU 地板，GPU 输**；
无 AES-NI 时单核 0.28 GB/s，16 核约 4.5 GB/s ⇒ **远低于 28.5 GB/s，GPU 大幅赢**。

⇒ **本轮最有用的一条：GPU 卸载的成败取决于 CPU 那一侧有没有对应的硬件指令**，
而不取决于 GPU 多快。有指令的任务（AES-NI 的加密、CRC 指令的校验和）在这台机器上
是带宽受限的，GPU 的传输地板已经比它慢；没有指令的任务才有机会。

⚠️ **本节单独看是必要条件。** 计算段与端到端见「计算段」与「判据 1 的答案」两节。

### 计算段：不需要 nvcc 也量得到上界，而它几乎免费

scrub / EC / 压缩的内层循环都是**带宽受限**的，带宽受限核函数的天花板就是显存带宽——
而那个用现成的按位算子就能量到。量出来的是**核函数的上界**（真核函数只会更慢）。

| 段 | 吞吐 | 占端到端 |
|---|---|---|
| 计算（显存内异或折叠，读+写各一遍） | **1041.3 GB/s** | 9.7% |
| **端到端（锁页主存 → 显存 → 算，不回传）** | **50.3 GB/s** | — |
| 其中传输 | — | **90.3%** |

阳性对照：含传输必须远慢于纯计算（要求 >3×），实测 **10.3×**，通过。
⚠️ 测不出这个差别多半是**没同步**——`torch.cuda.synchronize()` 漏了的话
量到的是异步启动，数字会好看一个数量级。

⇒ **GPU 路径的成本就是传输，计算段几乎免费。**

### 判据 1 的答案：带宽受限那一格是负收益，直接否掉

E21（GPU 卸载的净收益） 判据 1 是 `CPU 16 线程耗时 ÷ (传输 + 计算 + 传回) 耗时`，**小于 1 就否掉那一格**。

| | 吞吐 | 净收益 |
|---|---|---|
| CPU（内存带宽墙） | 64.91 GB/s | — |
| GPU 端到端（单程，实测） | **50.3 GB/s** | **0.78×** |

⇒ **CPU 侧是带宽受限的那些任务（有 AES-NI 的加密、有硬件指令的校验和），
GPU 卸载是负收益，否掉。** 这不再是推理——端到端两个数都是实测的。

**⇒ 阈值也随之精确了：CPU 侧吞吐低于 50.3 GB/s（单程场景）时 GPU 才开始赢。**
代入 [experiments.md](../experiments.md) E6（加密算法选型）：有 AES-NI 时 16 核撞 64.91 的墙 ⇒ 输；
无 AES-NI 时 16 核约 4.5 GB/s ⇒ 赢，且差距在一个数量级上。

### GPU 确实在工作：三条独立证据（2026-08-28 补证）

**起因是一次合理的质疑**：人在旁边看 `nvidia-smi`，读到 5090 **11 W**，判断「卡根本没动」。
质疑成立而结论不成立——两件事都是真的：

| 时刻 | 功耗 | 占用率 | SM 频率 |
|---|---|---|---|
| 基准之间的空档 | **11.67 W** | 0% | 195 MHz |
| **持续跑 10 秒**（35 次采样） | **352 W**（峰值 353） | **100%** | **2857 MHz** |
| 刚跑完 | 74.5 W | 0% | 570 MHz |

三条独立证据，任意一条单独都够：

1. **占用率对照**：空载 2 秒中位 **0%**，满载 6 秒中位 **100%**。
2. **功耗**：11.67 W → **352 W**。
3. **物理不可能**：同一段 `bitwise_xor` 在 CPU 上 **35.6 GB/s**、GPU 上 **1037.3 GB/s**，
   **29.1×**。而本机内存带宽实测封顶 **64.91 GB/s**——CPU 造不出 1037。

⚠️ **这条教训比数字重要：一个只跑毫秒级的基准，从外面看不出它跑没跑过。**
本实验前几次测量各自只让 GPU 忙 2.06 ms（计算段）到 21.3 ms（含传输），各 5 轮，
合计不到 0.2 秒；而 `nvidia-smi` 按秒采样、功耗还有滞后
⇒ **任何时刻瞄一眼，看到的几乎必然是空载**。
这正撞上 `.claude/singlefs-ai-sop/rules/test-discipline.md`
「阴性结果要能和『代码没跑到』分开」——**要说「这条路径跑过」，就得有读数证明它真的执行了**，
而毫秒级基准本身提供不了那个读数。
⇒ **做法**：GPU 类基准要么同时采占用率/功耗，要么另跑一段足够长的持续负载作为存在性证明。
脚本 `research/scripts/e21-prove-gpu.py`。

### 还有一层压在上面：这三个场景全是盘限的

三个候选场景（scrub / EC 重建 / 批量压缩）都是**全盘 I/O 密集的后台活**。
数据要先从盘上读上来，而盘的带宽比 64.91（CPU 内存带宽）与 28.5（GPU 来回）都低得多。
⇒ **整件事若是盘限的，CPU 本来就在空转，把计算卸给 GPU 省不下任何东西**——
除非 CPU 慢到比盘还慢，而那又回到「有没有硬件指令」那一条。

⚠️ **这一层是推理，不是实测**：本工程没有阵列，盘带宽没测过。
⚠️ **还有一个逃生口没验**：GPUDirect Storage 让 NVMe 直接 DMA 进显存、
绕开主存与 PCIe 那一跳，**它会推翻「GPU 吃数据 56.69 GB/s」这个传输地板**。没测过，不许当它不存在。

### 真核函数仍然没写，但它已经不影响这一格的判决

**本机有两块卡（RTX 5090 32 GiB / RTX 5060 Ti 16 GiB，驱动 595.84），但没有 `nvcc`。**
⇒ 编不出真核函数。但带宽受限算子给出的**上界**已经显示计算段只占 9.7%，
⇒ 真核函数再慢也只会让 GPU 那一侧更差，**不会翻盘**。
⚠️ 这个推论只对**带宽受限**的核函数成立。压缩这类**算力受限**的核函数不在此列，
它的计算段可能远不止 9.7%，**那一格仍然要等工具链**。
⚠️ **E21（GPU 卸载的净收益） 此前记的「无前置」是错的**，压缩那一格的前置就是这个工具链。

⚠️ 5060 Ti 当时只剩约 1 GiB 空闲（本地推理服务占着），**本轮只用 5090**，
且脚本在空闲显存 < 3 GiB 时直接拒跑——挤爆别人的服务不值得。

### 两个阳性对照，以及第二个改了两次才对

| 对照 | 断言 | 结果 |
|---|---|---|
| GPU 传输 | 锁页内存必须明显快于可分页（可分页要多一次暂存拷贝） | **2.05×**（56.69 vs 27.63），通过 |
| CPU 扫描 | **另设一条算力受限的臂**，16 线程必须接近线性扩展 | **15.30×**，通过 |

⚠️ **CPU 那条对照写错了两次，两次都是对照本身错、不是机器错**：

1. 第一版拿**被测臂自己**当对照，要求「16 线程快 2 倍」。而 XOR 折叠是**带宽受限**的，
   单线程已经跑到 54.12 GB/s、两线程就撞墙，**它本来就不该线性扩展**。
   实测 1.16× ⇒ 一个合法结果被判成了 harness 坏了。
   **`.claude/singlefs-ai-sop/rules/test-discipline.md` 明写阳性对照要用「效应确凿存在的那个基线」**，
   而不是被测臂自己。
2. 第二版另设了算力受限臂，但让**每条**线程都做同样多次迭代 ⇒ 总工作量随线程数涨，
   那是弱扩展，完美并行时挂钟持平、比值 ≈ 1，实测 0.96 又被判成不并行。
   改成**固定总工作量、按线程均分**之后是 15.30×。

⇒ **教训：阳性对照的失败，先怀疑对照的规格，再怀疑机器。** 两次都是规格错。

### 口径与代码

GPU：`research/scripts/e21-transfer.py`（torch 2.11.0+cu130），每档先跑一轮丢弃（建 CUDA 上下文），
**每次计时前后都 `torch.cuda.synchronize()`**——不同步量到的是异步启动不是传输，数字会好看一个数量级。
N=5 取中位。
CPU：`research/e7-index-bench/src/bin/e21_cpu.rs`，`cargo run --release --bin e21-cpu -- 2048 5`，
2 GiB 缓冲、5 轮取最好值；4 个单测，3 条变异逐条证明会红
（其中一条变异暴露了单测**自己重写了一遍分块逻辑、没走生产路径**，已抽成共用函数）。
输出 `research/results/e21-cpu-2026-08-28.out`。

**背景**：[decisions.md](../decisions.md) D24（后台重活能不能卸给 GPU）。三个候选场景（批量压缩、全盘 scrub、EC 重建）
全部落在 `.claude/rules/fs-design.md` 第三格（后台、可续做、非决策路径，无戒律），
所以引入 GPU 不违反已定纪律；但**收益一个数都没有**。

**自变量**：任务（校验和 / AEAD / Reed-Solomon 编解码 / 压缩）× 批大小（1 MiB … 4 GiB）
× 执行位置（CPU 单核 / CPU 16 线程 / GPU）× 数据是否已在显存。

**测什么**（**三段必须分开报，合并成一个「GPU 快 N 倍」就没意义了**）：

| 段 | 口径 |
|---|---|
| **传输**：主机 → 显存 | GB/s，含固定开销 |
| **计算**：核函数本身 | GB/s |
| **传回**：显存 → 主机 | GB/s（scrub 只回一个结论，EC 重建要回全部重建数据，两者差别巨大） |

**判据**：

1. **端到端净收益**：`CPU 16 线程耗时 ÷ (传输 + 计算 + 传回) 耗时`。
   **小于 1 就是负收益**，那一格直接否掉。
2. **收益随批大小的曲线在哪里过 1**——那个批大小就是启用 GPU 的阈值，
   必须是显式可计算的（`.claude/rules/fs-design.md` 硬要求 1）。
3. **回传量的影响**：scrub 只回一个判定，EC 重建要回整批数据。
   两者的曲线形状预期完全不同，**要分开报，不许用一个数概括**。

**怎样才算失败**：
- 若 GPU 计算段本身都不比 CPU 16 线程快，**不必再看传输段**，该任务直接否掉。
- 若各批大小下净收益都在 ±10% 内，检查是不是被 PCIe 带宽钉死了，
  **那说明这类任务不适合卸载，是合法结果，如实记录**。
- ⚠️ **阳性对照**：拿一个已知极度适合 GPU 的任务（例如大矩阵乘）跑同一条链路，
  它必须显示出显著加速。测不出来 ⇒ 环境或 harness 有问题，**整轮作废**——
  不许把「没加速」记成任务的结论。

**本机**（2026-08-28 现查）：NVIDIA RTX 5090（32 GB）+ RTX 5060 Ti（16 GB），驱动 595.84。
⚠️ **两块卡型号不同，跑分要钉死用哪一块并记进口径。**

**前置**：无。但需要 CUDA 工具链，`research/scripts/env.sh` 尚未检查它。
