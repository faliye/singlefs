### Criteria (Hardcoded Before Run, Never Modified After)

1. **Completeness Gate**: Establish in source code a table of "fields required by settled clauses to enter system configuration", **each item carrying provenance (decision number + item number or invariant number)**, asserting that every item has a row in the field table. **Report absolute values of "N required items, M missing items", naming missing items one by one.**
2. **Byte Budget After Padding**: Pad missing fields in at their respective minimum usable widths, **reporting cell-by-cell "fits / overflows by how many bytes"** on 512 / 4096 two-tier slot widths, in absolute values.
3. **Master Key Slot Two Arms**: Inline vs going through indirect layer (system configuration stores only pointer). Both arms report byte count and tear states. ⚠️ **Both arms must be run**, running only one is forbidden —— `.claude/singlefs-ai-sop/rules/test-discipline.md` "Positive control must be run on every tested arm".
4. **Pointer Synthesis Arm**: Tree table / device table / master key slot three indirect pointers **storing one each** vs **synthesizing into one indirect directory unit, leaving only one pointer in slot**. Report absolute byte count difference between both arms, and unit header bytes required by the newly added level of indirection in synthesis arm (calculated once for each of the three header tiers 68 / 77 / 86 per D18 (Information Carried in a Block) settled item 7).
5. **Absolute Value Assertion**: Every conclusion in criteria 2/3/4 must have an assertion **pinned to absolute values**, forbidding arm-to-arm mutual comparisons alone (`.claude/singlefs-ai-sop/rules/test-discipline.md` "Comparing multiple arms only against each other cannot detect when all arms are wrong together").

#### Criteria 2 / 3 / 4: Does It Fit in 512-Byte Slot After Padding

**Three of four cells overflow** (`wide` = missing items take wide measurement basis and master key slot inlined 80; `map_sep` = central mapping tree root occupies separate pointer):

| wide | map_sep | Synthesized Pointer | Total Bytes | 512 Slot | Tear States |
|---|---|---|---|---|---|
| 0 | 0 | No | **503** | Fits (rem 9) | 0 |
| 0 | 1 | No | **562** | **Overflow 50** | 2 |
| 1 | 0 | No | **532** | **Overflow 20** | 2 |
| 1 | 1 | No | **591** | **Overflow 79** | 2 |
| 0 | Any | **Yes** | **385** | Fits | 0 |
| 1 | Any | **Yes** | **473** | Fits | 0 |

On 4096-byte slot all eight cells fit, tear states constant 0.

⇒ **Synthesis arm is the sole form fitting 512-byte sector under all measurement bases**:
Synthesizing device table / tree table / master key slot / central mapping four indirect pointers into one "indirect directory unit", leaving only one pointer in slot,
**saves 177 bytes in slot** (`3 × 59`), at the cost of one unit header for the new level of indirection ——
calculated across three header tiers 68 / 77 / 86 per D18 (Information Carried in a Block) settled item 7, **worst case 86 ⇒ net saving 91 bytes**.

⚠️ **The overflow behavior of those three cells without synthesis exhibits tear states**: spanning 2 sectors ⇒ `2² − 2 = 2` readable but inconsistent states,
identical formula to E100 (Three-Segment Geometry of System Configuration) criterion 4. **Slot rotation is not atomic on those three cells.**

#### A Measurement Basis Inconsistency Measured Along the Way

**The same question "how wide is one dev id" has two numbers in the repository**:
E62 (Root Ring Ownership: Storing Identity vs Calculating Formula) byte cost verbatim is "**4 bytes** (4 regions × 1 byte)",
whereas D19 (Block Pointer Structure & Width Budget) settled item 4 (authored later) settled device ID as **4 bytes** each.
Computed under D22 (Synthesizing Unit Atomicity) settled item 2 R = 3 and D19 (Block Pointer Structure & Width Budget) measurement basis, root ring per-region device identity requires **12 bytes**, 3 times E62 (Root Ring Ownership: Storing Identity vs Calculating Formula) number.
E115 (Completeness and Byte Budget of System Configuration Field Table) computes both tiers (narrow tier 4, wide tier 12), **without picking one for the repository** —— that requires a decision, not an experiment.

#### Widths Are All Assumed Values

The nine item widths used by criteria 2/3/4 **were none of them settled in repository**, E115 (Completeness and Byte Budget of System Configuration Field Table) took minimum usable assumed values:
worst-case occupancy 8 + F 1 = 9, root ring per-region device identity 4 or 12, `w_max` 1, `g` 1, KDF ID 2, encryption type 2,
MAC length 1, `devs` 4, master key slot 59 (pointer) or 80 (inline, estimate registered in D22 (Synthesizing Unit Atomicity) settled item 9).

### What It Cannot Answer

Pure arithmetic: no mkfs, no mount, no real device.
**Does not answer "how wide each of these fields should be"** —— that requires individual standalone decisions; E115 (Completeness and Byte Budget of System Configuration Field Table) only answers "calculated at minimum usable width, does it fit".
**Nor does it answer whether completeness gate itself omits items**: that required-items table was copied out of kb by hand,
if an item was missed in copying it will not say a single word (recorded in [checks-owed.md](../checks-owed.md), see main text).
