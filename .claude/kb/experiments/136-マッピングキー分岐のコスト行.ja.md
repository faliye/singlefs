[中文](136-映射key岔路的代价行.md) · [English](136-cost-rows-for-mapping-key-forks.en.md) · **日本語**

**問い**：D19 (ブロックポインタ構造と幅予算) 確定項目 6 の3ラウンド対抗第3ラウンド（該当セルの ⑫㈤）でユーザー判定に付す前に、分岐に4種類のコスト数値が不足していた；E136 (マッピングキー分岐のコスト行) がそれを補完する——C280 (中央マッピングにどのユニットクラスを収容するかの条項欠落) で「Code 1 のみ収容」を選択した構成、実際のヘッダ幅下での Code 2 ヘッダ増分によるファンアウト、プール規模区間別のマッピングツリー段数、Code 2 / Code 3 ノード1個の移動バイト数、および派生ツリー Code 2 ノード移動時の追加読み取りノード数。

### これは計数モデルであり、実装ではない

I/O なし、ランダム源なし ⇒ N 回実行しても必然的にバイト単位で一致；根拠強度は **15単体テスト + 24ミューテーション全検出**、および3つの装置間ゲートに由来する：
`all` 構成 × ノードヘッダ 64 の 24 行は E134 (マッピングキーフォーマットコスト：スロット基準と2新アーム) の保管成果物内でバイト単位で一致；Code 2 の3段階ヘッダのファンアウト式は D18 (ブロックに含める情報) 308 行目に登録された「ファンアウト（エントリ 54）301 / 301 / 301」「ファンアウト（エントリ 81）201 / 200 / 200」を再現；

期待値は独立した Python 算術スクリプト（登録された原始量のみを使用し、装置の数式は読まない）から導出。

### 本実験で回答できない事項

- **勝敗の判定は行わず**、「どちらが優れているか」の順序付けも行わない；その数値は D19 (ブロックポインタ構造と幅予算) 確定項目 6 のコスト行にのみ算入される。
- CPU、キャッシュ、I/O 時間は計算しない；Code 2 / Code 3 ノードがどの頻度で移動されるかは未計測であり、移動は「ノード1個移動あたり」のバイト数と読み取り回数のみを報告；K は5点をサンプリングしており、実際のワークロードにおける共有分布を代表しない。
- C163 (固定点各巡で書き込みシーケンス同一によるタイブレーク失敗) 処置のコスト（挿入しながら COW する実装の禁止）はバイト数ではないため、報告しない。
- ツリーテーブルユニットおよびルートレコードのファンアウトは3段階計測条件に含まれない：ツリーテーブル各層の正味バイト数 16284 は旧 Code 2 ヘッダ 68 に由来し、3段階ヘッダに置き換えるには分母の変更が必要となるが、ここでは任意に選定しない。
- 段数は E133 (マッピングキー各候補のフォーマットコスト) / E134 (マッピングキーフォーマットコスト：スロット基準と2新アーム) と同一定義（ノードヘッダ 64、マッピングノードヘッダ 76）；3段階定義下でのマッピングツリー閾値は成果物 `tier_fanouts` の各行にあり、1〜2セル異なるが、区間の結論は変更されない。

### ミューテーション

24項目全検出。主な項目：Code 1 のみ収容時にノードポインタが全マッピング収容の幅を踏襲、3段階ヘッダに増分を加算しない、ルートスロットを 0 と計算、COW 経路でノードを1個過剰計算、移動時に参照ツリー数を乗算しない、追加読み取りが全アームに誤適用、段数区間の反転、プール規模区間の開閉反転（「プール規模がどの区間に収まるか」の単体テストでのみ検出可能）、セル減少カウントに増分を加算しない（陽性対照単体テストでのみ検出可能：増分がエントリ境界を跨ぐ際にセル減少を必ず報告）。
⚠️ 初回実行時に単体テストが1項目赤：リーフ層バイト比率の期待値 Python スクリプトが `%.5f` で四捨五入したのに対し、装置は定義通り拡大後に切り捨てていた（1.43203 対 1.43204）——期待値セルの丸め方式を修正；定義通り再計算して4セルとも合格。
