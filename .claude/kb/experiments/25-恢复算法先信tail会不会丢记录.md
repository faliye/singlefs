## E25 恢复算法：先信 tail 会不会丢记录 —— 已跑（2026-08-29）

**这不是性能实验，是安全性实验。** 还 [checks-owed.md](../checks-owed.md) C29（恢复先信 tail 会丢数据）。
[decisions.md](../decisions.md) D23（journal 的角色与格式）新增的硬要求
「恢复必须先全环扫描全验、再择最长合法前缀，不许先信 tail 再往前走」
是从机制推出来的，此前没有任何东西验过它。

### 结论

**判红条件在注册时就写死**（`rules/test-discipline.md`：失败条款不许让结论不可证伪）：
若「先信 tail」从不漏 ⇒ 那个窗口不存在、推理错、整条作废；
若「全环扫描」也漏 ⇒「陈旧 tail 只是多做功」整条作废。

环 64 块，先写 200 条撑过一圈，checkpoint 完成但 tail **不**持久，窗口内再写 `gap` 条：

| gap | 先信 tail 漏 | 全环扫描漏 | 全环扫描**多重放** |
|---|---|---|---|
| 0 | 0 | 0 | **64** |
| 1 | 1 | 0 | 63 |
| 5 | 5 | 0 | 59 |
| 20 | 20 | 0 | 44 |
| 63 | 63 | 0 | 1 |
| **100（超过环）** | 100 | **36** | 0 |

1. **「先信 tail」漏掉的条数恰等于窗口内写入的条数**——它一条都恢复不出来。
   机制：陈旧 tail 指向的槽已经被新一圈写掉，第一条就 `jsn != expected`，断号即止。
   ⇒ **D23（journal 的角色与格式） 那条硬要求成立，而且代价是全部窗口内记录，不是「一部分」。**

2. **全环扫描不丢，但它把陈旧 tail 以来的记录全部重放一遍**（`spurious = 环槽数 − gap`）。
   这一条**不在预期内，是加「多重放」这一维时当场测出来的**：
   全环扫描只知道**陈旧的**持久 tail，于是把环里 tail 之上能找到的全重放。
   ⇒ **「陈旧 tail 只是多做功」这句话有一个前提：重放必须幂等。**
   没有幂等，它就从「多做功」变成「重复施加已生效的记录」。
   那是本工程从没定过的额外要求，已记进 D23（journal 的角色与格式）。

3. **窗口撑爆环时两条臂一起丢**（gap=100、环 64 ⇒ 全环扫描漏 36 = 100 − 64）。
   ⇒ **恢复算法救不了几何。** 环大小 ≥ 窗口是
   [checks-owed.md](../checks-owed.md) C28（环几何不变量未实现）的职责，不是恢复算法的。

### 口径与已知局限

- 纯计数模型，无设备、无事务层。记录只有 `jsn` 与 `ckpt` 两个字段，
  **没有建模校验和、撕裂、乱序**——「验证一条记录」在模型里就是「槽非空且 jsn 对得上」。
- 只建模了一个窗口（checkpoint 完成 → tail 写），**没有建模多个 checkpoint 交错**。
- `spurious` 的代价没有量化，只数了条数——重放一条已生效记录的实际后果取决于幂等性，
  而幂等性本工程未定。
- 代码 `research/e7-index-bench/src/bin/e25_recovery.rs`（`cargo run --release --bin e25_recovery`），
  原始输出 `research/results/e25-recovery-2026-08-29.out`。三轮字节一致。

### 08-29 那一轮踩的三个坑，都由测试自己抓出来

1. **首次跑就红**：`gap=100` 而环 64，全环扫描漏 36 条。不是算法问题，是窗口撑爆了环。
   ⇒ 拆成两条测试，并把「窗口撑爆环」那格写成会红的断言，
   免得以后被当成恢复算法的缺陷去改错地方。
2. **只测陈旧场景 ⇒ 下界成了死代码**。`tail_persisted` 恒为 1 时全环扫描的下界永不起作用，
   变异测试把下界整个删掉一个测试都不红。补上健康场景（tail 正常持久化）后才钉住。
3. **健康场景当场抓出模型自己的 bug**：环里最大的 jsn 低于持久 tail 时
   （刚 checkpoint 完、还没写新记录），全环扫描仍返回那一条，多重放 1 条。

**工程质量**：12 个单测，**9 条变异全部被抓**，三轮字节一致。
