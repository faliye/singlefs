## E19 deferウィンドウ下の疑似ENOSPC —— モデリング層は実行済み (2026-08-28)、実機ストレステストは未実行

[中文](19-defer窗口下的假性ENOSPC.md) · [English](19-defer窗口下的假性ENOSPC.en.md) · **日本語**

**結論**：

1. **判定条件は計算可能であり、実測でも 36/36 が的中した**：

   > **疑似ENOSPC および checkpoint ストールの発生 ⟺
   > 残り空間 ≤ checkpoint ごとの攪乱量 × (遅延世代数 + 1) + 1回の checkpoint のオーバーヘッド**

   6段階の充填率（0.90–0.999）× 6段階の遅延（1–32）の計36セルにわたり、予測と実測は**セルごとに一致**した。
   この予測は**ワークロードのパラメータのみを使用**し、テスト対象モデルのいかなるフィールドも読み取らない。

2. **90% / 95% 充填下ではすべて 0**——この問題はディスクがほぼ満杯のときにのみ存在し、定常状態ではない。

   | 充填率 | 残り空間 | 問題が発生する最小遅延 |
   |---|---|---|
   | 99% | 10000 ブロック | **16**（遅延 8 では無事） |
   | 99.5% | 5000 ブロック | **8** |
   | 99.9% | 1000 ブロック | **1**（最小遅延で問題発生） |

3. **99.9% 充填下における疑似ENOSPC率**：遅延 1 → 0.375%；遅延 8 → 3.875%；遅延 16 → **7.875%**。

4. **二つの障害モードは個別に処置すべきであり、単一の言明に統合することはできない。**

   | 障害 | 抑止手段 | 数値 |
   |---|---|---|
   | **checkpoint ストール** | **リザーブプール**、かつ `reserve ≥ ckpt_cost` で十分 | **64 ブロック**の事前確保（`ckpt_cost` に過不足なく一致）で `ckpt_stall` を **199 から 0 へ撲滅** |
   | **疑似ENOSPC** | **受入のみ**。リザーブプールはかえって悪化させる | 確保量 0 → 16384 ブロックで、疑似ENOSPC は 3150 から **7246** へ増加、各段階の増加分は過不足なく `reserve / file_blocks` |

   **メカニズム**：リザーブプールは checkpoint のために設けたフロアであり、**通常の割り当て**に対しては純粋な税となる。
   そして疑似ENOSPC の成因は「defer/K が拘束する量が残り空間を超過すること」であり、リザーブプールの射程外にある。
   ⇒ 受入規則が疑似ENOSPC を抑止する：ディスクを
   `容量 − 攪乱量 × (遅延+1) − checkpoint オーバーヘッド` を超えて充填することを禁止する。

**計測条件**：純粋な論理モデリング、デバイスなし、ファイルシステムなし。容量 100 万ブロック（4 KiB/ブロック ≈ 3.8 GiB）、
一時ファイルごとに 4 ブロック、checkpoint ウィンドウごとに 200 回の「1つ削除 ＋ 1つ作成」、200 checkpoint を実行、
1回の checkpoint 自身が 64 ブロックを書き込む。コード `scripts/experiments/e19_defer.rs`（`cargo run --release --bin e19-defer`）。
生出力 `e19-defer-2026-08-28.out`。

**2つの数値は個別に計算され、同一の公式から導出されたものではない**：
`df_free = 容量 − 生存参照`（ユーザーが見るもの）；
`allocatable = 容量 − 生存参照 − 拘束量 − リザーブプール`（アロケータが見るもの）。
「拘束量」は **checkpoint ごとの会計キュー** から計算される。

### 08-28 ラウンドで検出された自前の2つのモデリング bug

| bug | 症状 | 結果 |
|---|---|---|
| `allocatable()` が `u64` で直接減算 | 拘束量が残り空間を超過した際に**天文学的数値へアンダーフロー** | 割り当てがかえって常に成功し、表全体が偽物となった |
| リザーブプールを「容量縮小」として実装し、充填率を縮小後の容量で再計算 | 確保量を 0 から 16384 に変えても**全く差が出ない** | 発見ではなく、未実装であった |
| **ストール判定が誤ったビューを読み取り**：`allocatable_for_checkpoint()` ではなく `allocatable()`（**リザーブプールを減算済み**）と記述 | `allocatable_for_checkpoint()` がデッドコードとなり、コンパイラが `never used` を警告し続けた | **「リザーブプールでは救えない」という結論は完全にこの1行に起因していた。** 正しく配線後、`reserve=64` でストールを 199 から 0 へ撲滅 |

**2つ目の bug は結果が「整然としすぎている」ことによって露呈した**——6段階の事前確保が完全に同一の数値を出力したこと自体が、
「この独立変数が配線されていない」というシグナルであった。
**3つ目の bug は三者論証の逆推脚によって捕捉された**：コードを精読し、そのメソッドが一度も呼び出されていないことを発見した。
⚠️ 原因はインデントの不一致により `str.replace` が**サイレントに適用されなかった**にもかかわらず、読み戻し確認を怠ったことであった。

### 明記すべき判別力の欠落

`analytic_held`（数式推計）と項目ごとの会計は**セルごとに完全に一致**した（800/800 … 12800/12800）。
⚠️ **その「一致」には判別力がない**：E19 (deferウィンドウ下の疑似ENOSPC) のワークロードは完全に規則的（checkpoint ごとに正確に 200 回 × 4 ブロック）であり、
2つの経路が同一の算術を計算しているにすぎない。**判別力があるのは受入の規則である**——trouble / no-trouble という二値判定を予測し、
36セルにわたり全問的中している。`analytic_held` にも判別力を持たせるためには、ワークロードが不規則（可変長ファイル、可変レート）でなければならない。
