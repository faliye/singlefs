本ドキュメントは本来「3つの検証手段をどう着地させるか」の調査記録である：各手段がどの確定条項を消費し、どの未定項目に阻まれているか、リポジトリ内から何を再利用可能か、第1版の最小範囲をどこまでとすべきか。各節に進捗到達段階を記し、第6節には当時コード着手を阻んでいた、ユーザーのみが決定可能な論点をまとめている。

⚠️ **「推奨される着地順序」の節は推論である**。2026-09-03 に三方対抗検証を一巡（各脚の状況と判決は同一節に記載）。その他の節は都度確認した客観的事実である。

## 一、3つの検証手段の概要

| 手段 | ゲート内のステージ | 入力 | 出力 | 規範的定義 |
|---|---|---|---|---|
| **トランザクション層**（テスト対象） | 単独ステージなし。モデル差分対照、クラッシュポイント再生、QEMU 負荷の3者がいずれもこれを前提とする | mkfs パラメータ、一連の操作、1つのブロックデバイス | イメージ、および書き込み要求ストリーム（クラッシュポイント再生用） | プロジェクト `CLAUDE.md`「最初の実行可能目標は1つのトランザクションを正しくコミットすること」。構造的制約は D13（検証方針）確定事項 10 の閉鎖列挙型 `CommitStep` および D17（実装レイヤリングとサードパーティパイプライン）のウエストラインに準拠 |
| **checker** | モデル差分対照とクラッシュポイント再生の両ステージ共通の判定器。O2（独立パーサー + checker）に対応 | **単一の**イメージ | 各不変条件の 成立 / 不成立 / 不適用 | D13（検証方針）確定事項 6、D13（検証方針）確定事項 7：単項述語であり、単一イメージのみを判定し、テスト対象 crate のデシリアライズや走査コードの呼び出しを一切禁止。[invariants/README.md](../../crates/singlefs-checker/invariants/README.md) がその仕様書 |
| **クラッシュポイント再生** | 「クラッシュポイント再生」ステージ | 書き込み要求ストリーム（バリアを含む）+ クラッシュ前イメージ | 各クラッシュ状態における「リカバリ → checker → レコード照合器」の結果 | `.claude/singlefs-ai-sop/rules/test-discipline.md`「クラッシュ一貫性はクラッシュポイント再生でのみ検証可能」。レイヤリングと枝刈りは D13（検証方針）確定事項 9「クラッシュポイント再生のレイヤリング手法」に準拠 |

モデル差分対照（O1（HashMap 理想ファイルシステムによるメモリモデル差分対照）および D13（検証方針）確定事項 3 の RefFS）はユーザーが名指しした3手段には含まれないが、第4の前提チェーンを成す：イメージ判定に checker を要し、テスト対象としてトランザクション層を要する。
O3（独立仕様実行器）（別言語を用い、decisions と invariants の文面のみから再導出した仕様実行器）も3手段には含まれず、D13（検証方針）確定事項 6 の3つのオラクルのうちコードから最も遠い位置にあり、着地順序の最終ステップに配置される。
レコード照合器（引数 `(pre_crash_image, record_stream, post_crash_image)`、D13（検証方針）確定事項 7 で意図的に番号未付与）も3手段には含まれないが、クラッシュポイント再生における第2の判定器となる——これがなければ、「ルートは存在するがレコードが欠落している」7分類の状態（E77（パブリッシュの永続化順序））は checker の単一イメージ判定基準から間接的にしか検出できない。

## 二、依存順序：何が何を阻んでいるか

```
フォーマットバイトの4箇所の空白 ──▶ mkfs + トランザクション層 ──▶ 書き込み要求ストリーム ──▶ クラッシュポイント再生
                                └─▶ checker ────────────────────────────────────────────────────────┘
```

## 三、各手段の第1版のスコープ

### トランザクション層第1版：mkfs、1トランザクション、1パブリッシュ、1リカバリ

新プール新規作成ファイルの定義は [layout/01-first-txn.md](layout/01-first-txn.md) に記載：mkfs 後に1つの小ファイルを書き込んで1回パブリッシュする。ディレクトリ、スナップショット、reflink、暗号化（D9（暗号化）確定事項 10）、圧縮は含まない。第1版が実装するのは純 SSD レイアウト（D12（対象メディア）確定事項 5）、ディスク2台（D2（RAID 条帯ポリシー）確定事項 9）、シリアルコミット（D13（検証方針）確定事項 2）である。

逐字的に遵守すべき確定条項：

| 手順 | 条項 |
|---|---|
| mkfs | システム構成はディスクあたり1部、更新は ≥2 スロットローテーションを経由。journal リングは2ディスクでミラーリング。第0世代ルートを全ルートリング領域に種まき（D22 確定事項 8）。ルートリング R=3、素数ステップ配置、スロット幅 = 検出された `physical_block_size`（D22 確定事項 2） |
| 割り当て | 配置箇所ごとの述語（D3 確定事項 1）、独立 keyspace の btree（D3 確定事項 3）。コミット内生ブロックはクラスタ化セグメントから割り当て（D3 確定事項 5）。参入読み取り値 = パブリッシュ済み − 飛行中承認済み（D28（マウント時コミット量）確定事項 2） |
| ユニット書き込み | データユニットはヘッダー込みで厳格に 32 KiB（D4 確定事項 5 / 確定事項 7）。ユニットヘッダーは 105 バイトのフィールドテーブル（`format-const: DATA_UNIT_HEADER_BYTES`、D18 確定事項 7）。パディングは厳格に 0 かつチェックサム対象（I-2.3（パディングバイトはゼロかつチェックサム対象）） |
| ポインタ書き込み | ポインタヘッダー 50 + 位置エントリ 14 × 2 レプリカ + 誕生識別（ポインタコード 1：書き込みシーケンス 10、計 88。ポインタコード 2 / 3：インスタンスコード 4 + 誕生シーケンス 4、計 86。D19 確定事項 4 / 7 / 8）。チェックサムは親ポインタ内にインライン化（D4 確定事項 1） |

| パブリッシュ | 永続化順序は厳格に「ユニット/ノード → バリア → journal レコード → バリア → ルートスロット（FUA）」（D16 確定事項 7）。パブリッシュごとに checkpoint_txg + 1（D16 確定事項 6）。ルートレコード 457 バイト、厳格にツリーテーブルユニット間接層を経由（D22 確定事項 7） |
| リカバリ | 全ルートスロット候補を個別に検証した上で最新を選択、同値はインスタンスコードで判定（D22 確定事項 7）。全リング走査、tail の先行信頼を禁止（D23 確定事項 3）。プレフィックス5基準（厳格な jsn 連続性、`(instance_code, checkpoint_txg)` がルート水位超、コミットマーク完備、適用前に指名ユニットを個別検証（指名ユニットの両コピーを検証後に適用）、適用の単位は1パブリッシュ全体（全体適用か全体不適用か））（D23 確定事項 14。第5基準は D16 確定事項 4 に由来） |

**構造上のハード要件**：共有トランザクション状態遷移マシンと閉鎖列挙型 `CommitStep`、網羅的 `match`、ワイルドカードアームの禁止（D13 確定事項 10）。コミットパスおよび参入パス内にメディア判定記号を持ち込んではならない（C19）。ブロックデバイスインターフェースは「書き込み、バリア、FUA 書き込み」のみを公開し、「メディアの種別」を公開してはならない。

⚠️ **第1版で明示的に見送る事項**：並列コミット（D13 確定事項 2 に「交差点を通過後に並列化を開始」と明記）、zoned レイアウト（D22 未定事項 6 未回答）、非有界操作の意図ログ（D8 確定事項 5 の一括削除パス。新プール新規作成ファイルでは不要）、defer ウィンドウ（D16 確定事項 1 で状態数カウント方式へ変更済み：ロールバック候補セットは直近4つの退避可能状態を保持し、8秒の時間窓ではない。新プール新規作成ファイルには解放がなく不要。「上書き・解放・ロールバック・再利用」マイルストーンで実装、`allocator.rs` の `reclaim_released_up_to`）。

**2つの走査方向**：走査（traversal）方向はルートスロットからツリーを下降し、スキャン（scan）方向は D18 確定事項 9 のステップでディスク全体を線形走査し、105 バイトのユニットヘッダーでブロックを回収する（E86 のプローブ、E88 の回収ルール。当時の 91 バイトヘッダーで治具を実行）。両者は同一の不変条件を1回ずつ判定し、共有するのはフォーマット解析コードのみである（D13 確定事項 12「衝突1」の妥協案）。I-1.2（ヘッダー書き込みシーケンスパブリッシュ済み）はスキャン方向が走査方向から独立した判定基準であり、断片化トランザクションのゴミを生きたユニットから選別する唯一の判定基準である。

**判定幅は独自に検出する必要があり、ハーネスや実装から取得してはならない**：I-7.5（ルートスロットの判定幅アライメント）および I-8.2（レコードヘッダーのアトミックユニット非またぎ）の判定基準はマウント時に検出された `physical_block_size` であり、イメージ内には存在しない。checker がベアデバイスを直接読み取る際（O2 の基準）、独自に検出し、mkfs 時にシステム構成に記録された値と照合すべきである（D22 確定事項 2「マウント時のデバイスごと再計算照合」の checker 側形態。スロット幅はシステム構成フィールドテーブルに入らない——D22 2026-09-10 ユーザー決定「スロット幅 = マウント時に検出された physical_block_size」、checker は自己検出値と実際のスロット幅を照合しフィールドは読まない）。ファイルをデバイスとして用いる場合検出不能となるため、checker はジオメトリを「引数由来」として報告し検出値として扱ってはならない（推論脚の指摘）。

**独立性はハードな制約であり、スタイルの問題ではない**：checker は単独の crate であり実装 crate に依存しない。実装の課金やチェックサムコードのリンクを禁止する（D17 負債表第5項、C12）。checker と実装の間で共有が許されるのは KB から生成された定数モジュール1部のみである（D13 確定事項 5、「未確定事項」第2問）。`singlefs-checker` は `singlefs-format` のみに依存する。

**自ら赤（エラー）になることを証明しなければならない**：実装済みの各不変条件に対し、それをちょうどトリガーするように改変した不良イメージを最低1部用意し、`scripts/mutation/tables/` と同型の変異テーブルとして構築しゲートで再実行する（C13 が要求するのはまさにこれである：実行されすべて緑だが実際には機能していない状態は、未実行と見分けがつかない）。C88 の二重ルートイメージ、C47 の半スロットオフセットイメージが本コーパスの最初の2件である。

### クラッシュポイント再生第1版：ユーザー空間記録、全量列挙、3つの判定器

**記録はカーネル内ではなくユーザー空間で行う。** 実装は Rust ライブラリであり、すべての I/O は同一のブロックデバイス抽象を経由する。その抽象にレコーダーを被せることで、バリアおよび FUA タグが付与された完全な書き込み要求ストリームを取得できる。`dm-log-writes` は C6（実ブロック層の FLUSH / FUA セマンティクスが想定通りかどうかの検証）に充てる。本ホストおよび VM カーネルはいずれも本モジュールを具備している（「環境確認」参照）。

**列挙は E77 のモデルに準拠**（断片化サブセットは列挙せず、D13 確定事項 4 で確定済み。⚠️ 断片化状態は「未永続化」に合算してカウントするが、それら断片化バイトパターンは実際にイメージとして生成し checker のスキャン方向に供給しなければならない——ヘッダーは着地したがペイロードが未着地の状態こそ I-1.2 が捕捉対象とするものであり、「合算カウント」を「イメージ非生成」と誤読してはならない）：バリアが書き込みストリームをセグメントに分割し、クラッシュ状態 = 先行セグメント群の完全永続化 + 現セグメントの任意サブセットの永続化 + 後続セグメント群の完全未永続化となる。D16 確定事項 7 の2つのバリアとルートスロット FUA が1パブリッシュを3セグメントに分割し、新プール新規作成ファイルをデバイスごとに記録しセグメント内任意完全書き込みサブセットをとると、状態数は 16,777,260 となる（`crash_enumeration_new_pool_file_creation_stream.rs` の `FULL_STATES`。書き込みごとに2状態のみをとると 16,777,240。ゲート checker-tier-crash-point-replay の `--full` は release 下で全状態を実行）。**クラッシュポイント再生はサンプリングを行わず、全量列挙する**。E77 からは列挙器 `crash_states`、リカバリモデル `recover`、および**リカバリコードを共有しない**監査コード `audit` の3ブロックを直接流用可能である。

**記録はプール単位ではなくデバイス単位で行う**：第1版の2ディスク構成において全書き込みは w ≥ 2 であり（D2 確定事項 6）、journal リングは2ディスクでミラーリングされる（D22 確定事項 8）。各ユニットとレコードは個別に永続化可能な2回の物理書き込みであり、バリアも2回のデバイス FLUSH となる。したがって E77 の 72 / 79 / 513 / 1024 という数値をハーネスの状態数アサーションとしてそのまま流用することはできず、ハーネス独自の書き込みストリームに基づき閉形式を再計算する必要がある（推論脚の指摘）。

**各クラッシュ状態で実行される3つの検証**：実装自身のリカバリ → checker（単項判定）→ レコード照合器（二項判定：クラッシュ前イメージ、レコードストリーム、クラッシュ後イメージを対照）。3者は独立しており、1つでも欠ければ見落とされるエラー分類が生じる。現在3者すべて接続済みである：リカバリ + オラクル、プールレベル checker（`crates/singlefs-checker` の `walk::check_pool_image`、92条、`IMPLEMENTED_INVARIANTS` の長さ。初期29条：第1版23条 + I-3.8、I-7.4、I-4.8、I-3.9、I-9.14、I-5.4）、レコード照合器（`crates/singlefs-checker-tier` の `crash::check_records`）。クラッシュポイント再生の全量はゲート checker-tier-crash-point-replay に配置。

⚠️ **クラッシュポイント再生の負荷を「新プール新規作成ファイル」単独にしてはならない**（2026-09-14 時点はこれのみであった）：mkfs 後にファイルを1つ書いて1回パブリッシュするだけではデータ側のブロック解放がゼロであり、C22 および C80 の用例が捕捉対象を持たない（対抗検証でローカル脚と正推脚が指摘）。固定負荷には上書き、解放、ロールバック、再利用を含める必要がある。同一ファイルへの上書きにより1回の解放、1回の遅延再利用、1回の課金変更が発生する。さらに C42 は「クラッシュ → リカバリ → 少量の追記 → 再クラッシュ」を要求する。したがって固定スクリプトはリカバリを挟む3回のパブリッシュ（mkfs、パブリッシュ A（ファイル書き込み）、パブリッシュ B（上書き）、B の各クラッシュポイントでリカバリ、パブリッシュ C（短）、C の各クラッシュポイントでリカバリ）となる。2026-09-17 以降、固定スクリプトストリームはパブリッシュ E（F 引き上げ後の再利用）まで進行している（ゲート checker-tier-crash-point-replay 全量）。「クラッシュ → リカバリ → 追記 → 再クラッシュ」および残留レコードの反例は未導入（`.claude/kb/milestone/02-second-txn.md` ステップ0、収口表22・23行目を参照）。
**ベースイメージの事前配置機能が必要**（推論脚の指摘）：レコーダーは今回の実行の書き込みのみを記録するため、リング内の「先行タイムラインの残留」は自然発生しない。ハーネス側で残留レコードをベースイメージに植え込む機能が必要となる。
バリアと空パブリッシュ関連の用例は mkfs と空パブリッシュのみで実行可能だが、解放・再利用・残留の3分類はパブリッシュ B および C を待つ必要がある。**C314 の2スロットはさらに管理者ロールバックを1回要求する**：パブリッシュ C 後に A のルートへロールバックしパブリッシュ D を実行。第①スロットはロールバックパブリッシュのクラッシュポイントを列挙し、第②スロットは D 後に障害の組み合わせでロールバックインスタンスのルートを読み取り不能化する。したがって固定スクリプトは mkfs、A、B、C、A へのロールバック、D となる（2026-09-13 に C314 確定時に登録）。固定スクリプトはその後 F 引き上げを経て再利用するパブリッシュ E へ進む（`.claude/kb/milestone/02-second-txn.md` ステップ0）。

**再生では回答できず QEMU 層に委ねられる事項**：C6（実 FLUSH / FUA）、C26（実機バリア数カウント）、C16 および D20 推論3第3問が要求する断片化注入——`dm-flakey` では断片化を作れず、ユーザー空間レコーダーは `physical_block_size` 粒度で作れるもののそれはモデルであってデバイスではない。
2026-09-14 より VM 層の最初の被測定対象が稼働（ゲート checker-tier-qemu-device-streams）：新プール新規作成ファイルを2基の実 virtio ディスク上で実行し、デバイス側ログ（QEMU blklogwrites）とプログラム記録ストリームを逐項照合し、バリア漏れとページキャッシュ経由の2対照をいずれも赤と判定。C6 の VM 層側（デバイス側ログからクラッシュ状態を再構築してレコード照合器を実行する。`crates/singlefs-checker-tier/src/device_log.rs` は現在記録ストリームとの逐項照合のみ）および C16 の断片化注入は依然として未済である。

両者は混同されがちだが、防ぐエラーの種類が根本的に異なる：成果物のハッシュ計算は**その成果物自身が変化した時**にのみ発報し、もう一方が何を書いているかは一切検査しない。判定基準は明快である——**このゲートはどの2つの成果物を比較しているのか？それを言えなければ、それは単なる変更検出器である。** 本プロジェクトで初めてこれを用いたのは D15 確定事項 3 での `spec_hash` の算出元定義であり、根拠と範囲は同条文に準拠する。

⚠️ これらのモデルは**機構を証明するものであり、実装を証明するものではない**。`crates/` に導入後は各ブロックごとに単体テストと変異テーブルを再整備する必要があり、`research/` 側のコードは陽性対照としてのみ機能する。

4. **却下された提案部分**：ステップ3・4の元の完了基準「5つの自己証明用例がすべて赤になる」は充足不能（2件は字面通りでは赤にならず、2件は単一パブリッシュ上で捕捉対象を持たない）。それをトリガー可能な各パブリッシュに個別に紐付ける形に変更。
