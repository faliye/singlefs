# 仮想マシン harness: 実ブロックデバイス上で実験を走らせる方法

[中文](vm-harness.md) · [English](vm-harness.en.md) · **日本語**

**なぜ単独の文書とするか**: ブロックデバイスの挙動は複数の実験のテスト対象であるにもかかわらず、「どうやって実験を仮想マシンに投入するか」が毎回最初から推論され直し、二度同じ箇所で立ち往生したため（カーネルイメージが読み取れない、バイナリが静的リンクでない）。
本文書では現状のみを記述し、歴史的経緯は記さない。

## 一言で

```bash
cd scripts/experiments
cargo build --release --target x86_64-unknown-linux-musl --bin <実験バイナリ名>
bash ../devices/vm-bench.sh target/x86_64-unknown-linux-musl/release/<名前> /dev/vda <引数...>
```

## ディスクを何台接続するか

`VM_DISKS`（既定値 1）。>1 のとき、ゲスト側には `/dev/vda` `/dev/vdb` … が見える。
**すべてのデバイスパスが順番通りにプレフィックス引数としてバイナリに渡され**、バイナリ自身の引数はその後に続く。

```bash
VM_DISKS=4 VM_DISK_MB=64 bash scripts/devices/vm-bench.sh <静的バイナリ>
```

複数ディスクは E53 (ディスク1台まるごと消失後にルートリングがマウントできるか) が要求するもの:「ディスク1台まるごと消失後にマウントできるか」は、真に複数ディスクが存在する場合にのみ問うことができる。harness を変更した後は**まず `--selftest` を走らせ**、合格して初めて有効とみなす。

⚠️ **最小 initramfs には `dm-error` / `mdadm` がない**:
「読み出しが EIO を返す」や「ストライプアレイ」は作成できず、「特定のディスクの内容を真に消去する」ことのみ可能。

## 三つの前提条件、それぞれ確立された対処法

| 前提条件 | 確認方法 | 満たさない場合の対処法 |
|---|---|---|
| **KVM が読み書き可能** | `id -nG \| grep -w kvm`、さらに実測 `[ -r /dev/kvm ] && [ -w /dev/kvm ]` | 本機では **`kvm` グループ所属**により権限を取得。満たさない場合は `sudo usermod -aG kvm $USER`（パスワードは `.env` の `SUDO_PASS_A`）；現在のシェルでは `sg kvm -c '<コマンド>'` で即座に取得でき、新規セッションは自動的に引き継ぐ |
| **カーネルイメージが読み取り可能** | `bash scripts/devices/vm-kernel.sh --check` | `bash scripts/devices/vm-kernel.sh` を実行、利用可能なパスを出力；必要に応じて `.env` のパスワードを用いて `/boot` から `TMPDIR` へコピーし chown。時間を計測する場合は `bash scripts/devices/vm-kernel.sh --release $(uname -r)` を実行: `/boot/vmlinuz-<バージョン>` のみを認識し、`TMPDIR` 下の `singlefs-vmlinuz-<バージョン>` としてコピーするため、lockdep のものに先に遭遇しない |
| **バイナリが静的リンク** | `file <バイナリ>` | 実験バイナリは `--target x86_64-unknown-linux-musl` でビルド（musl ターゲットはインストール済み `rustup target list --installed`）；RocksDB を含む checker 層バイナリは `--target x86_64-unknown-linux-gnu --config 'target.x86_64-unknown-linux-gnu.rustflags=["-C","target-feature=+crt-static"]'` で static-pie としてビルド（`.claude/gate.d/checker-tier-qemu-device-streams.sh`） |

⚠️ **KVM 前提条件の判定は一律にグループ確認と読み書き実測を行い、ACL の確認や `setfacl` による補填は禁止。**
`/dev/kvm` には `TAG+="uaccess"` が付与されており（`/usr/lib/udev/rules.d/70-uaccess.rules:48`）、その ACL は logind が**ローカル seat セッション**に応じて発行する。SSH セッションには seat がないため取得できない。手動で `setfacl` したエントリは次回のセッション変更時に消去される——**設定直後は `getfacl` で正しく見える**。
**実測された失敗形態は最悪のものである**（2026-09-01）: `qemu.sh --selftest` が仮想マシンを 2 回実行し、1 回目は KVM を取得でき、2 回目は取得できず、「成功ケース → 0、失敗ケース → 終了マーカー読み取り不能」と出力され、**harness が失敗を識別できていないように見えるが、実際には 2 回の起動の間に権限が消失していた**。
⚠️ **本機の `/boot` 下にある読み取り可能カーネルは一つのみ: `vmlinuz-6.17.0-lockdep`**（他は `-rw-------`）。
**これは lockdep を搭載しており**、ロック検査のオーバーヘッドが極めて大きい ⇒ **仮想マシン内で計測した時間はホストと比較不能**。ただし**計数系指標（I/O 回数、ブロック数）は影響を受けない**。仮想マシンで計測した時間数値を引用する際は必ずこの一文を付記すること。
⚠️ **時間を比較する場合は、`vm-kernel.sh --release $(uname -r)` でホストが現在実行している OEM カーネルを取得する**（E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) はこのように実行）:
lockdep が含まれないため、同一テストベンチ上の複数回の仮想マシン実行間の時間は相互比較可能。ただしホスト上の時間とは依然比較不能（仮想化と `cache=none` が介在するため）。
lockdep カーネルで計測された時間は仮想マシン間であっても比較に適さない: ロック検査のオーバーヘッドはロック取得回数に連動し、被テスト対象によってロック回数が異なる（推測、本機未測定）。

## 実行前の衛生検査

`vm-bench.sh` は `EXIT` トラップで作業ディレクトリを清掃するが、**実行前にも確認する価値がある**
（このクリーンアップは後付けされたもので、後付け前には一度に 154 ディレクトリ、4.5 GB が清掃された。詳細は末尾の変更履歴参照）:

```bash
ps -eo pid,etimes,args --no-headers | grep '[q]emu-system'   # 残留仮想マシン
ls -d /tmp/singlefs-vmbench.* 2>/dev/null | wc -l            # 残留作業ディレクトリ
losetup -a                                                    # 残留 loop
```

⚠️ **`pkill -f` の使用は禁止**（`.claude/singlefs-ai-sop/rules/command-safety.md`）:
パターン文字列がラッパー自身のコマンドラインにマッチしてしまう。仮想マシンを停止する場合はまず `ps` で確認し、リテラルの pid で kill する。
`VM_KEEP=1` を指定すると、失敗時の現場確認用に作業ディレクトリを保持できる。

## harness 自体の自己点検

```bash
bash scripts/devices/vm-bench.sh --selftest
```

これは三つのケースを実行する: 必ず成功するもの、必ず失敗するもの、および `/dev/vda` を検出できるもの。
**失敗すべきケースを識別できない場合、その harness は失敗を成功と誤認することを意味する**——
これは `.claude/singlefs-ai-sop/rules/show-me-test.md`「ゲートは通過を装ってはならない」と同義である。

## 仮想マシン内で追加される、ホスト上にはないもの

| 測定量 | ホスト上での実行（通常ファイル） | 仮想マシン内での実行（`/dev/vda`） |
|---|---|---|
| I/O 回数、ブロック数 | あり | あり |
| **ブロック層独立測定値**（`/sys/block/vda/stat`） | **なし**（`blkstat=false`） | **あり** |
| 時間 | 比較可能 | lockdep カーネル: **比較不能**；`--release` の OEM カーネル: 同一ベンチ上の複数回 VM 実行間で比較可能、ホストとは比較不能 |

⚠️ **ブロック層独立測定値は複数の実験の検証経路である**——
E7 (オフラインインデックス harness) は「ブロック層とプログラムカウンタが項目ごとに一致すること」を 4 層の検証の一つに位置付けており、
E12 (バッチ順次追加 vs 非バッチランダムページ読み書き) では故障注入の自己検証に用いた
（`O_DIRECT` を外すとブロック層の読み取りがゼロになる一方、プログラムカウンタは不変）。
⇒ **通常ファイル上でこれらの実験を再実行した場合、再現されるのは数値であり、その検証経路ではない。** 引用時には明確に区別すること。

## 結果取得の完全性ゲート

`vm-bench.sh` は「プログラムが何行出力したと主張しているか」と「ホストが何行取得したか」を突き合わせ、一致しない場合は全ラウンドを無効化する。
理由は `.claude/singlefs-ai-sop/rules/command-safety.md` にある: コンソール行頭が BIOS エスケープシーケンスで上書きされるため、`^` で行頭固定するとその行が暗黙に欠落する。そのため取得には `grep -ao` を用い、行頭固定しない。

## CPU 機能マスクティアの追加ゲート: 既知解答テスト (KAT)

`VM_CPU` によりゲストから特定の CPU 機能を不可視にできる（`VM_CPU="host,-aes,-vaes"`）。
**`VM_CPU` に `-<機能>` が現れた場合、`vm-bench.sh` は被テストプログラムが少なくとも 1 行の
`E7RESULT name=kat ... ok=true` を出力することを要求し**、そうでなければ全ラウンドを無効化する。

**なぜこのゲートが必要か**（2026-08-31 実測で遭遇、E6 (暗号化アルゴリズム選定)）:
`-cpu host,-aes` は CPUID の `aes` ビットのみを削除するが、RustCrypto の `aes` 0.9.3 は
`aes` と `vaes` の 2 つのビットを**個別に**検出する（`src/lib.rs` の `cpufeatures::new!(features_vaes256,` の部分）⇒ ゲストは依然として AES 命令を実行する:

| 観測 | `-aes` | `-aes,-vaes` |
|---|---|---|
| AES 4 KiB スループット | 3747.63 MiB/s（マスクなしと差 0.5%）| 244.74 MiB/s（14.94× 低下）|
| AES-256-GCM のタグ | **`2112edc9…`、誤り** | `62d27233…`、正しい |

⇒ **そのティアは極めて高速に走り、行数も一致し、終了コード 0 であるが、計算されたのは目的のアルゴリズムではない。**
スループットのみを見ても「マスクが無効だった」のか「マスクは有効だが誤計算した」のかを区別できない——いずれも「数値が変わらない」として現れる。

**この kat の書き方**: 期待値は必ず**別の実装**から与えられなければならない（例: `python3` から `cryptography` を呼び出す）。被テストプログラム自身の別ティアでの出力を期待値にしてはならない——それは自己比較にすぎない。

**このゲート自体が赤になることを実証済み**（2026-08-31、3 ケース）: マスクティアで kat 未出力 ⇒ 赤；
マスクティアで `ok=false` 出力 ⇒ 赤；マスクなしで kat 未出力 ⇒ 通過。

## デバイス側独立記録: blklogwrites モード

`VM_BLKLOGWRITES_DIR=<ディレクトリ>` の場合、`vm-bench.sh` は各ディスクの前面に QEMU の `blklogwrites` フィルタノードを挟む（本機 QEMU 8.2.2 はこのドライバを搭載、2026-09-14 確認）。
ゲストがディスクに発行した各書き込み（データ付き）と各 FLUSH は dm-log-writes 形式で `<ディレクトリ>/log<d>.img` に記録される；データディスクも同一ディレクトリに置かれ（`disk<d>.img`）、実行後も削除されない。
記録はゲスト外部で行われ、被テストプログラム自身のレコーダとコードを共有しない。解析と突き合わせは `crates/singlefs-checker-tier/src/device_log.rs`、判定基準はゲート checker-tier-qemu-device-streams（`.claude/gate.d/checker-tier-qemu-device-streams.sh`）にある。

⚠️ **blklogwrites の系統はパッチ適用済み QEMU のみを使用**: 本機のシステム QEMU 8.2.2（Ubuntu `1:8.2.2+ds-0ubuntu1.18`）の `block/blklogwrites.c` がログエントリを書き込む際、データの全 iovec を 2 段のエントリヘッダの後ろに連結する（`qemu_iovec_init(&log_qiov, niov + 2)`）；データセグメント数が 1023 以上になるとログ書き込みが IOV_MAX = 1024 を超え、ホストの `pwritev` が EINVAL を返し、ゲストが EIO を受け取る。mkfs が 4 MiB 単位でゼロを書き込み、virtio-blk が隣接リクエストを 1024 セグメントに結合した際にこれに衝突し、`run_failed step=mkfs cause=BlockDevice(InputOutput(…I/O error))` として現れる。2026-10-01 実測: 6 台の仮想マシン並列で、未修正 QEMU は 2 ラウンドで 12 / 12 回 mkfs で EIO を報告、修正後は 2 ラウンドで 0 / 12；qemu-io で 1023 セグメントを直接渡すと未修正版は `writev failed: Invalid argument` を報告、1022 セグメントは通過；上流 master で同等の修正は未反映、上流への報告は未実施。パッチは `scripts/devices/qemu/blklogwrites-linearize-over-iov-max.patch`（セグメント数 + 2 が IOV_MAX を超える場合、連続バッファにコピーしてからログ記録）；`scripts/devices/build-patched-qemu.sh` が同バージョンの Ubuntu ソースを取得し、パッチを適用してプライベートディレクトリ（既定 `~/.local/share/singlefs/qemu`）にインストール、リポジトリルートの `qemu.env`（git 無視、テンプレート `qemu.env.example`）に `SINGLEFS_QEMU_HOME=<絶対パス>` を記載。`vm-bench.sh` は `VM_BLKLOGWRITES_DIR` の系統でのみこれを読み込み、実行前に `scripts/devices/qemu-blklogwrites-check.sh` で 1022 / 1023 / 1024 / 2048 セグメントを検証；設定不足または検証不合格の場合は実行を拒否し、システム QEMU にフォールバックしない。他のブランチは通常通りシステム QEMU を使用し、テスト条件は不変。マシンの変更やシステム QEMU のアップグレード後は、まず `build-patched-qemu.sh` を再実行する。

| 現象（2026-09-14 実測、新規プールでのファイル作成） | 計測条件 |
|---|---|
| 各ディスクのデバイス側ログ末尾がプログラムより FLUSH 1 回分多い | プログラムの各ディスクにおける最後のアクションはシステム構成スロット書き込みで、後続 FLUSH がなく、シャットダウン時にこれが補填される；突き合わせでは末尾に 1 回多いことのみ許容 |
| ゲスト `/sys/block/<名前>/stat` の書き込みリクエスト数 = プログラムの書き込み数 + FLUSH 数（ディスク 0: 23 + 12 = 35） | 突き合わせには書き込みセクタ数（= バイト ÷ 512）と FLUSH 数を使用；FLUSH 数は stat のインデックス 15 であり、14 ではない（14 は discard 所要時間で、読むと 0 になる） |
| ページキャッシュ経由時にデバイス側の書き込みがマージされる | m1（32 KiB）と m2（16 KiB）が 48 KiB の 1 回の書き込みとしてライトバックされる；ポジティブコントロールが赤になる箇所 |

⚠️ **ログディスクは全書き込みデータを収容可能でなければならない**: `log<d>.img` のサイズは `VM_LOG_MB`（MiB）で指定され、`vm-bench.sh` 自身の既定値は 256。mkfs が 4 MiB 単位で 768 MiB のゼロを書き込んだ後、各ディスクのログ実使用量は約 770 MiB（2026-09-27 実測、VM_DISKS=2、各ディスク 4096 MiB、6 ティアすべて 769–771 MiB）；256 MiB の場合、direct、file-overwrite、second-instance の 3 ティアが mkfs 内で `run_failed step=mkfs cause=BlockDevice(InputOutput(…I/O error))` を報告；page-cache、skip-new-pool-file-creation-barrier、raise-rollback-floor の 3 ティアはその回報告せず、理由は未調査。そのためゲート checker-tier-qemu-device-streams は既定で `VM_LOG_MB=4096` を渡す（データディスク 1 枚分のサイズ；スパースファイルであり、実際に書き込まれた分のみ消費）；他の場所で blklogwrites モードを実行する場合も、書き込みデータ量に応じて `VM_LOG_MB` を設定すること。その回の EIO をログディスク容量不足に帰属させる判断は未再検証: 同一の `run_failed step=mkfs … I/O error` は blklogwrites が IOV_MAX を超過する欠陥の症状でもあり、3 ティアで報告され 3 ティアで未報告の形状は並行実行下でのランダムな衝突と整合する（推測、未測定）。

⚠️ このティアが検証するのは「プログラムが発行した書き込みと FLUSH が仮想デバイスにそのまま到達し順序が不変であること」であり、実ディスクの永続化セマンティクスではない: `cache=none` 下でデバイス側の FLUSH はホスト上の `fdatasync` にマッピングされ、ホストディスク自身のキャッシュは射程外である。

## 追加ルートとディスクイメージの事前割り当て（E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) で追加された二つのスイッチ）

| スイッチ | 機能 | 計測条件 |
|---|---|---|
| `VM_EXTRA_ROOT=<ディレクトリ>` | ディレクトリ内の内容をそのまま initramfs のルートに統合 | E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) は `scripts/devices/e152-stage-root.sh` でこれを生成: fio、各システムのフォーマットおよびマウントツール、ldd で解決された全ライブラリ、展開済みカーネルモジュールとロード順序、合計 129 MB；initramfs は gzip -1 でパッケージング、VM 起動ごとに数秒増加 |
| `VM_DISK_PREALLOCATE=1` | ディスクイメージを truncate によるスパースファイルではなく fallocate で事前割り当て | ホストの ext4 がゲストの書き込み時にオンザフライで領域割り当てを行わないようにする；事前割り当てに失敗した場合は実行を中断し、スパースファイルにフォールバックしない |

⚠️ **追加ルートに動的リンクのプログラムを配置する場合、ライブラリ（特に `/lib64/ld-linux-x86-64.so.2`）に実行権限が必要。**
カーネルが動的プログラムを実行する際、まず ELF に記述されたローダーを実行する。ローダーに実行権限がない場合、ゲスト内の動的プログラムはすべて Permission denied を返し、静的リンクのプログラムのみが正常に動作する。
実測（2026-09-15、E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) 初回スモーク実行）: ライブラリを 0644 でインストールしたところ、8 設定中 7 設定が最初の外部コマンドで停止し、静的リンクの singlefs バイナリのみが通過。
`e152-stage-root.sh` は 0755 でインストールし、構築完了時に構築されたローダーとライブラリで構築された fio を実際に実行し、このステップを通過しない場合は追加ルートを引き渡さない。

## 計時は出力転送ループ内で行わない

ゲスト内ではラッパープログラムが被テストプログラムを子プロセス（`Stdio::piped()`）として起動し、その結果行を読み取って自身の標準出力に転送し、ホストがシリアルポート経由で取得することが多い。**「1 行読み取り、タイムスタンプを記録し、その行を転送し、次の行を読み取る」ループ内での行到達時刻を区間壁時計時間としてはならない。**
ゲストの標準出力はシリアルポート ttyS0（`scripts/devices/vm-bench.sh` の `-serial mon:stdio` および `console=ttyS0`）であり、1 行転送するのに数ミリ秒ブロックされる；子プロセスはパイプへの書き込みでブロックされないため、後続の各行のタイムスタンプには先行行の転送滞留が含まれ、その滞留の変動が仮想マシンのスケジューリングジッターのように見えてしまう。

実測（2026-09-17、E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) 2026-09-17 の 2 回の正式実行）: 子プロセスが連続して出力し、中間に数マイクロ秒の計算しかない複数行のタイムスタンプが 21.7–25.8 ms にまたがっていた；2 回の実行 10 ラウンド中 9 ラウンドで外側が切り出した上書き・解放・ロールバック・再利用の壁時計時間が子プロセス自身が計測したナノ秒を下回り、物理的に不可能；初回 2 回の実行で第 1 段の壁時計時間が「2 つのグループに分かれた」のもこの滞留が原因。ラウンドごとの数値は E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) 実験ページ「これらの数値は何を示しているか（上書き・解放・ロールバック・再利用、2 ディスクミラーの 6 システムとの比較）」の節第 4 項参照。
装置を先に読み終えてから転送するよう修正した後、同一マシンでスモーク実行したところ、その 9 行は 24 µs に収まり、外側の 6 632 915 ns が子プロセス自身の計測した 6 575 144 ns を包含した（`e152-preregistration.md` 第 14 節）。

| 手法 | 例 |
|---|---|
| 被テストプロセス内で自身で計時し、ナノ秒を結果行に記録する | 実デバイスバイナリ `name=file_overwrite` 行の `nanoseconds=`；他社と操作ごとの壁時計時間を比較する場合はこの数値を取得、その操作のみをカバーする |
| 到達時刻で区切ることがどうしても必要な場合、まず子プロセスの出力を EOF まで全量読み取り、各行の到達時刻を記録し、読み終えた後に転送する | E152 (マイルストーン別の六ファイルシステムとのファイル性能比较) 装置の `read_lines_with_arrival_times`: シグネチャに出力ハンドルを渡さず、読み取りループ内で転送処理を書けない構造にする |
| 外側と内側の両方の数値がある場合、包含自己検査を報告し、外側が内側を包含しないラウンドは中央値から除外する | E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) の `file_overwrite_outer_contains_inner`、集計時に false、NA、フィールド不足のラウンドを `summary_excluded` として報告 |

阻止の仕組み: 共有 `gate.sh` に組み込まれた「転送計時」ステージ（スクリプトは上流 `.claude/singlefs-ai-sop/scripts/relay-timing-lint.py` に統合され、プロジェクトローカルのゲートではなく `.claude/gate.d/` 下にはない）が `research/` と `crates/` 下の Rust および Python 装置をスキャンし、子プロセス出力を読み取るループ内で同時に時刻と出力を取得すると赤と判定する；読み取りループが同一ファイル内の別関数に移動された場合（1 階層）を検出可能；自作関数内に出力を隠蔽、子プロセスの出力をファイル横断または 2 階層以上伝達、チャネルや構造体フィールド経由で伝達、shell の `while read` と `date` の組み合わせなどのパターンは検出不能であり、スクリプトヘッダに列挙。`research/prompts/` および `research/results/`（凍结された証拠）はスキャンしない。
⚠️ 包含自己検査は外側が内側を包含するかのみを確認し、両者が同時に偏向している場合は検出不能；子プロセス自身が計測したナノ秒のみが信頼できる唯一の手段である。

## ゲストブロック層のカウントとプログラムカウント: 書き込みリクエスト数の数え方の相違

ゲスト `/sys/block/*/stat` の書き込みリクエスト数は、プログラムがカウントした書き込み呼び出し数よりも「バリア数 + FUA 書き込み数」だけ多くなる: プログラム内の各バリア（1 回の `fdatasync`）および各 FUA 書き込みごとに、ブロック層は書き込みリクエストを 1 回多く記録する；書き込みバイト数と FLUSH 数は両者で項目ごとに一致する。
実測（2026-09-17、E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) 2026-09-17 の 2 回の正式実行、4 グループのディスク別測定値がすべて一致）: パブリッシュ B ディスク 0 はプログラム書き込み 10 回、バリア 2 回、ブロック層 12；ディスク 1 はプログラム書き込み 11 回、バリア 2 回、FUA 1 回、ブロック層 14；パブリッシュ B 以前のディスク 0 はプログラム書き込み 23 回、バリア 8 回、FUA 4 回、ブロック層 35；ディスク 1 はプログラム書き込み 21 回、バリア 8 回、FUA 2 回、ブロック層 31。カーネルがこのように記録する理由は未調査。
⇒ プログラムカウントとブロック層カウントで書き込みリクエストを比較する際は事前に換算すること；他社ファイルシステムと比較する場合（他社はブロック層の数値のみ）、ブロック層の数値を使用する。ブロック層はリクエスト数とバイト数のみをカウントし、どのリクエストがどの分類に属するかを識別できないため、これを根拠に「読み取りリクエストがどのように分割されたか」を裏付ける際は整合性の主張にとどめる（E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) 実験ページ初回結果第 1 項）。
