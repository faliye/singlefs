## 三　GPU 打包搬迁

- **原话**：用户 2026-10-20：「里程碑4 我们将做gpu gc。 因此讨论在里程碑7 打包搬迁能否使用gpu实现。在里程碑7中列入这一项，并且参照里程碑4的多分支处理机制 预留可以扩展的其他接口和字段。」
- **仓里已有的**（2026-10-20 现查）：后台任务的 GPU 开关、选卡、显存上限、出错不降级、两份 GPU 核比对的复核定在 D26（后台整理与放置回收） 已定项 13，一组参数管全部后台任务（用户 2026-10-20 定，原话在变更史）；里程碑四七·1 在量 GC 一批搬迁的挂钟（E185（GC一批搬迁的挂钟拆分），问题单 `research/prompts/m4-gpugc-measure-forks.md` 四行都开着），七·2 的控制接口还没设计。D24（后台重活能不能卸给 GPU） 已定项 2 的三条硬约束管任何卸给 GPU 的活；打包搬迁不在 D24（后台重活能不能卸给 GPU） 的三个候选里，归 D26（后台整理与放置回收） 已定项 13 管。master 上没有打包容器的代码（`crates/` 里 `grep -rln 'PackingContainer\|packing_container'` 零命中；`crates/singlefs-core/src/unit.rs` 只有码 1、2、3）；产品代码里没有 GPU 依赖（`wgpu` 只在 `crates/singlefs-checker-tier/Cargo.toml`）。D27（小数据打包容器） 已定项 6 定一次事务一片映射叶、代价被映射写主导；已定项 13 的 36 档同时开着的容器合计 1.15 MiB；E21（GPU 卸载的净收益） 量到传输地板要 ≥ 64 MiB 的批，所以 GPU 模式要跨很多片映射叶攒批。
- **能不能上 GPU**（主 agent 的判断，推的，没量过）：能，形态与 GPU 垃圾回收相同——GPU 只算，映射叶 COW 与事务发布留在 CPU，仍是一个事务层（`.claude/rules/fs-design.md`「一个事务层，所有结构共用」）。一批打包搬迁拆成几段：

| 段 | 做什么 | 上不上 GPU（推的） |
|---|---|---|
| 核源 | 读源对象、核源单元的校验和 | 能：带宽受限，与 GC 核源单元同形；E21（GPU 卸载的净收益） 对纯扫描量到挂钟净收益 0.78×，按 D26（后台整理与放置回收） 已定项 13 第 7 条省下的主机 CPU 时间算才可能划算 |
| 投档 | 按对象大小投进 36 档之一、定槽号 | 能，但算量小，单放它省不下什么 |
| 拼容器 | 补齐到槽宽、拼容器字节、算整容器校验和（MAC 只在加密开启时有执行路径，D27（小数据打包容器） 已定项 7） | 能：拼好的字节要传回来写盘，走「来回」那一档传输地板 |
| 改映射与发布 | 沿 key 序 COW 映射叶、走事务发布 | 不上：树操作与发布是事务层，一批之内不换后端 |
| 重新加密 | 加密开启后搬一个对象要重算 AAD 下的密文（C240（搬运时重新加密的代价没算过）） | 留口：加密不进第一个可运行版本（D9（加密） 已定项 10），这一段只在接口里留一个任务种类 |

- **参照里程碑四的多分支机制，留哪些口**：

| 里程碑四七·3 的机制 | 打包搬迁怎么接 | 留的扩展口 |
|---|---|---|
| 计算后端 `background_compute`（`cpu` / `gpu`，默认 `cpu`） | 共用这一个参数：开了 `gpu`，打包与 GC 一起走 GPU，不另设打包的参数 | 后端写成封闭枚举、穷举 `match`，不写通配臂；加一种后端只加一个成员，编译器逼每一处补上 |
| 选卡 `background_gpu_devices`、显存上限 `background_gpu_memory_limit` | 共用：一张卡的上限是全部后台任务合占的上限，打包与 GC 怎么在上限之内分，三·2 定 | 参数只有一组、不按任务分设；任务种类是封闭枚举（GC 搬迁、打包搬迁；以后 D24（后台重活能不能卸给 GPU） 的 scrub、纠删码重建、批量压缩，加密开启后的重新加密），哪些种类有 GPU 路径由枚举的穷举 `match` 说了算，加一种任务只加一个成员 |
| 挂着切换、下一批生效、一批之内不换 | 同：一次切全部后台任务，每种任务各在自己的下一批生效 | 控制接口只有一个开关，不按任务种类寻址 |
| GPU 用不上报错、不降级 | 同：正在算的那一批放弃，打包巡回停下报错 | 无 |
| 两份独立的 GPU 核各算一次比对（一张卡也能跑），确认的交 CPU 改位图，连续不确定的交 CPU 判；GPU 与 CPU 两份实现 | 同（D26（后台整理与放置回收） 已定项 13 第 8 条、D24（后台重活能不能卸给 GPU） 已定项 2 第 3 条） | CPU 参照与 GPU 路径按任务种类各一对，对拍按种类各进快档 |
| 分支能被测试强制进入、运行时看得出走了哪条 | 同（`.claude/rules/fs-design.md` 五条硬要求） | 观测计数按「任务种类 × 后端」记 |

  留口只到三处：任务种类与后端两个枚举、控制接口、内存里的观测计数；挂载参数只有 D26（后台整理与放置回收） 已定项 13 那一组，不为打包加。盘上一个比特都不加：打包意图、容器头都不记走的哪个后端（D24（后台重活能不能卸给 GPU） 已定项 2 第 1 条；D26（后台整理与放置回收） 已定项 13 第 1 条）。不写占位代码：扩展口落在枚举与参数的形态上，代码只写 GC 与打包两种任务、`cpu` 与 `gpu` 两种后端（`.claude/singlefs-ai-sop/rules/code-discipline.md`「用不到的代码删掉」；里程碑四「优化项：不在出口，进入条件已登记」一节同一做法）。

|---|---|---|---|---|
| 三·1 | 量：在里程碑五落地的打包路径上量一批打包搬迁的挂钟，按核源、投档、拼容器、改映射与发布四段拆成读写 I/O 与 CPU 各几成；量法沿用 E185（GC一批搬迁的挂钟拆分） 的装置与口径，写重跑登记，不另立量法 | D27（小数据打包容器） 已定项 6；D24（后台重活能不能卸给 GPU） 已定项 3 的判据形式；C202（打包巡回的空转开销与迟滞 K 都没有数） | 断言钉绝对值；一批的映射叶数翻倍挂钟跟着涨（判别力自证） | 里程碑五的打包路径在 master；里程碑四七·1 |
