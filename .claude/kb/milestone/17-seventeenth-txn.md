# 里程碑「格式冻结」：作业点、验收与次序

**中文** · [English](17-seventeenth-txn.en.md) · [日本語](17-seventeenth-txn.ja.md)

**口径**：规划文件，2026-10-12 提前建档，是草案。用户定了七到十，问「你可能漏了的 你觉得怎么排里程碑比较好」，主 agent 建议把十一到十五接在后面，原则是动盘上格式的都排在格式冻结之前、冻结排在对外之前（`records/2026-10-11-里程碑五打包与决策进度列.md` 第七节）；用户同日要求「写在 /home/fy5090/code/singlefs/.claude/kb/milestone 中吧 提前写上」，再定这个次序：「这个可以 做的时候还要调整」。**它不要求正确**：每项开工前回来改。冻结之后 FUSE 挂载（[12-twelfth-txn.md](12-twelfth-txn.md)）才交给外部用户。前提是里程碑三到十六的出口全部达成；前面的里程碑收口时少了哪一样，这份文件按缺的那一样重排。

**读法**：每项三格——「仓里已有的」写这一项在仓里压着哪些条款、欠账、代码（2026-10-12 现查的，带出处）；「作业点」一张表：编号、做什么、压着的条款与欠账、验收（每条先证会红）、依赖；「开工前要先定的」列还没定、开工前要走三方或问用户的问题。凡写「推的」的是主 agent 没量过的判断。作业点的编号写成「项·点」（一·1、二·3），只在这份文件里用。欠账号都是建档那天还开着的，开工前逐条现查。

**冻结之后规矩变了**：`.claude/rules/format-evolution.md` 写「一旦有外部用户，本文作废，改为严格兼容——那时直接改本文，并把推翻依据写进决策变更史」。冻结一个组件之后改它的字节要走 incompat 位（D15（格式冻结政策） 已定项 4 那张表）。**不加新事务种类**。
