**計測条件**：計画文書、2026-09-10 作成、当日の判断に基づき記述。**正確であることは要求されない**：想定される詳細は決定および実際の実装に伴い段階的に修正される；各ステップの着工前に戻って改訂し、改訂後は本文を直接修正し、経緯は git に委ねる。ステップはユーザーが 2026-09-10 に提示した 6 項目に沿い、前段階に足場を 1 ステップ、後段階にクラッシュポイント再生を 1 ステップ追加。目標はプロジェクトの `CLAUDE.md` に記載された最初の実行可能目標「1 トランザクションを正しくコミットする」である。

**読み方**：各ステップ 3 段落。「構想」はそのステップ完了後にディスク上およびメモリ内に何が増えるか；「想定される詳細」内で**想定**と記されたものは、リポジトリ内で未確定でありコード記述時に一旦採用するもので、確定後に変更される；「受入基準」はそのステップ完了後に他者へ実演可能であるべき項目であり、各項目とも事前に赤になることを証明しなければならない。末尾の 1 行「遭遇する決定点」は番号のみを列挙し展開しない。

**マイルストーンはステップ 7 まで**とし、出口はステップ 7 の受入である。ディレクトリ、スナップショット、暗号化、圧縮、zoned、並行コミット、第三者パイプラインは対象外とする。

**バイト表および決定インデックスとの連動**：各ステップには [layout/01-first-txn.md](../layout/01-first-txn.md) の各節を指す「書き出されるバイト列」行が 1 行あり、幅、値、配置先はその表に準拠し、ここでは重複転記しない；[decisions.md](../decisions.md) において「新規プールでのファイル作成のバイト列を変更：はい」と判定された未定項目は、すべていずれかのステップの「遭遇する決定点」に含まれなければならない。両者ともゲートステージ「新規プールでのファイル作成の 3 文書の相互連動」により赤判定される。

## ステップ 0　足場

**着工日（2026-09-14）の現状**：ルート `Cargo.toml` workspace（`research/` 除外）+ 4 crate（本日の workspace メンバーは 8 つ、ルート `Cargo.toml` の `members` に準拠）：`crates/singlefs-format`（フォーマット定数、`format-const:` 注および `// placeholder:` プレースホルダー付き）、`crates/singlefs-core`（アドレス newtype、ブロックデバイストレイトおよびファイルバックエンド）、`crates/singlefs-harness`（レコーダーおよびストリーム件数ゲート）、`crates/singlefs-checker`（骨格：幅判定の「プローブ済み／宣言済み」2 状態）。ゲートに「フォーマット定数ファイル内のプレースホルダー」ステージが追加され（`.claude/gate.d/doc-registries.sh` の format-const-placeholders スロット、fixtures 内にサンプル）、code-source-discipline の format-constants スロットの定数同期が `crates/` に拡張。受入 3 項目：レコーダー件数ゲートの自己証明（`stream_count_gate_rejects_a_stream_that_lost_one_write`）、2 種のアドレス型の混用によるコンパイルエラー（`address` モジュールの `compile_fail` doctest）、プレースホルダー計数ゲート——すべて存在。テストイメージのデフォルトは 4 GiB（`TEST_IMAGE_DEFAULT_BYTES`、C323 (イメージサイズに関する条項がリポジトリ内に存在しない) のプレースホルダー）、ユーザーは 2026-09-14 に仮想ディスクを 200–500 GB に拡張可能と発言。

**構想**：1 つの `crates/` workspace、3 つの crate：中核（トランザクション層）、checker、harness。N 個のイメージファイルに接続する 1 つのブロックデバイス抽象；その外側をラップし、各書き込み要求とバリアをストリームとして記録するレコーダー。新規プールでのファイル作成で書き出すすべての幅を収めた 1 つのフォーマット定数ファイル、プレースホルダー定数にはプレースホルダーマークと項目番号を付与。

**想定される詳細**：
- デバイス抽象は読み出し、書き込み、バリア、FUA 書き込み、`physical_block_size` のプローブの 5 動作のみを公開し、媒体の実体を公開しない。
- イメージファイルはデフォルトで 2 つ、`${TMPDIR:-/tmp}` に配置、サイズは **4 GiB** を想定（D23 (ジャーナルの役割と形式) 確定項目 19 ③「リング ≤ デバイス容量 ÷ 4」と規定、1 GiB ではデフォルトの 768 MiB リングを収容不能）。**想定**：`physical_block_size` はパラメータとして指定、デフォルト 512（[layout/01-first-txn.md](../layout/01-first-txn.md) 0 節と同一計測条件；4096 は第 2 層としてステップ 7 で別途実行）。
- レコーダーの記録項目：デバイス番号、オフセット、長さ、コンテンツハッシュ、バリアか否か、FUA か否か。ストリームはファイルに永続化し、ステップ 7 で使用。
- アドレスはすべて newtype：デバイス番号、デバイス内 16 KiB スロット番号、世代番号 `txg`、`jsn`、ツリー ID、inode 番号。
- 定数ファイル内の各定数に 1 行のコメント：値の由来項目、プレースホルダーか否か。

**受入基準**：
- レコーダーの自己証明：書き込みを 1 件落とすモックデバイスを入力し、件数比較で赤判定。
- 2 種のアドレス型を混用したコードがコンパイルエラー（compile-fail テスト 1 つ）。
- ゲートにステージ追加：定数ファイル内の残存プレースホルダー数を数え、各プレースホルダーが項目番号を指していることを確認、指せない場合は赤判定。

**書き出されるバイト列**：なし（このステップでは新規のディスク上バイト列は書き出さない）。

**遭遇する決定点**：フォーマット決定なし；エンジニアリング規約は [verification-build.md](../verification-build.md)「保留中の提案」第 5 問を参照。

## ステップ 1　mkfs

**現状（2026-09-14 着工、受入 5 項目すべて合格）**：`crates/singlefs-core` の `make_filesystem` が 2 台のデバイスを受け取り、バイト表 0 の m1–m4 に従ってインスタンステーブルユニット第 0 スライス（スロット 50176）、ツリーテーブルユニット第 0 版（スロット 50178）、3 領域それぞれのスロット 0 の第 0 世代ルートレコード（FUA）、各ディスク 2 スロットの世代番号 1 のシステム構成スロットを書き出す；幾何範囲外（リング > 容量 / 4、ルートリングまたはユニット領域のディスク終端超過、領域帰属が存在しないディスクを指す）はバイト列を書き出す前に拒否。`bytes` / `checksum` / `pointer` / `unit` / `system_configuration` / `root_record` / `root_ring` の 7 モジュールにエンコードされ、各オフセットは `assert_position` によりフィールド表に固定；checker（`crates/singlefs-checker`）はビット単位 CRC-32C および 3 種のスロット／ユニットのパースを独立実装し、実装とは定数モジュールのみを共有。受入（`crates/singlefs-harness/tests/mkfs_bytes_judged_by_the_checker.rs`）：同一パラメータでの 2 回の mkfs はバイト単位で完全一致；3 領域のスロット 0 は同一の第 0 世代ルートをデコードし、1 スロット 1 バイト破損時はそのスロットのみを判定；各ディスク 2 スロットのチェックサム合格かつ世代番号 1、1 スロット破損時は他方を選択；ルートレコードの 2 本のポインタが指すユニットヘッダの自己検査合格かつ位置エントリ内のユニット全体チェックサムが一致；記録ストリームのセグメントシーケンス `4+1+1+1+4`、種別文字列は 8 節の mkfs 行と完全に一致、13 回の操作。イメージ準備（ジャーナルリングとルートリング領域の完全ゼロクリア）は `make_filesystem` 内で明示的に `write_zeroes_at` により 0 を書き込み、スパースイメージと実デバイスで同一経路を通る。

## ステップ 2　データユニットを 1 つ割り当て、小ファイルのデータを書き込む

**現状（2026-09-14 着工、受入 3 項目すべて合格）**：`crates/singlefs-core` の `allocator` モジュール——ディスクごとにユニット領域空きマップ 1 枚（割り当て済みビット、セグメントごと使用スロット数、空き run 数の 3 種を増分保守、実行時ディスクスキャンなし）、ユーザーデータ配置先ポリシー（開始点最小、偶数スロット、両スロット空き、オープンセグメント外）、コミット内生ブロックはオープンセグメントからバンプ（コンテナは 32768 アライメント層）、割り当てレコード 20 バイトエンコード（当時はポリシー関数再計算比較カウントを含み新規プールでのファイル作成では恒常的に 0；2026-09-25 に C515 (ポリシー不一致カウントが恒常的に0、計測条件未変更) に伴い削除）；`unit::build_data_unit` はバイト表 2 に従いコード 1 を書き込み（ヘッダ 105 + 予約 29、ペイロードは 134 以降、ペイロード CRC は [105, 32768) をカバー）；`pointer::DataPointer` 88 バイト。受入（`crates/singlefs-harness/tests/data_unit_allocation_and_write.rs`）：3000 バイトのファイルを両ディスクの t1@50180 に書き込み、読み戻し時のヘッダ自己検査合格、ペイロード CRC 正当、先頭 3000 バイトはファイル内容と一致し以降は全 0；ペイロード／パディング領域／ヘッダの任意 1 バイト破損で赤判定、flags 非 0 は拒否；メモリ内に正確に 2 件の割り当てレコード、スロット番号は記録ストリーム内の 2 回の書き込みオフセット ÷ 16384 と一致；会計増分：割り当て済み 5 スロット、空き run 2 セグメント。

**想定される詳細**：
