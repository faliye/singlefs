## IV. Cold Reads and RefFS Without Expansion by Size

- **Existing in repo** (checked on 2026-10-22): after a legal extension to a large size within the K12 limit (the limit on N is that ⌈N ÷ payload⌉ × payload does not overflow u64, `research/prompts/m4-trunc-r1-main-verification.md` K12; for example 2⁴⁰ bytes, which still occupy only a few units on disk), the core layer's cold walk `walk_to_file` and cold recovery `recover` hand over the whole content as one vector with the hole padded with 0 up to the size (`content_padded_with_the_hole_up_to_the_size` in `crates/singlefs-core/src/recovery.rs`), and the reference implementation RefFS applies a truncation as a whole-content `resize` (the truncation site `truncated.resize(` in `crates/singlefs-reference-filesystem/src/lib.rs`), and the process aborts. The core layer's `mount.rs` and `mounted_session.rs` call neither `recover(&` nor `walk_to_file(` anywhere; the callers of cold reads are in the checker tier, the harness tier and `recovery.rs` itself, so the mount path is not affected. The truncation target of a random history is at most the current size plus 4 payloads (`new_size_in_bytes` in `crates/singlefs-harness/src/history.rs`), so the three-way differential never hits a large extension. The user settled on 2026-10-22 that this version does not change and the work goes into this optimization milestone, verbatim: "这个没必要管就按照现在的方式读。 之后会优化 没有必要现在优化。 肯定不可能现在这种方式冷读", "现在这个样子冷读肯定是不行的 放到后面的优化里程碑里面" (judgment `research/prompts/m4-validate-code-r1-main-verification.md` Section 4 row 2 and the section "用户定案"). Owed check: C878 (cold read and RefFS allocate memory for the whole size).
