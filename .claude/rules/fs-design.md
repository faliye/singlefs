# 设计纪律

具体的设计决策记在 `.claude/kb/decisions.md`。本文只写**跨决策生效的纪律**。

**这是 singlefs 的项目本地规则**，不在共享 SOP 里——文件系统的设计纪律只有本工程需要。
共享规则在 `.claude/singlefs-ai-sop/rules/`。

## 从事务开始，不从功能开始

写路径的硬核是 COW 提交机制，一切骑在它上面。任何新功能都是「一种新的事务」。
**没有事务层的功能实现一律不收。**

推论：第一个可运行目标不是「能创建文件」，是「能正确提交一个事务」——
哪怕它只能分配块、写入、提交，没有目录、没有树、性能烂到底。

## 记账是事务的副产品，不是事后的遍历

**线划在「谁消费这个数」，不划在「用什么机制算出来」。**

| 消费者 | 允不允许遍历 | 为什么 |
|---|---|---|
| **运行时决策路径**（分配、ENOSPC 准入、defer 窗口、生命周期判定） | **不许**，且代价不许随盘容量增长 | 不是慢，是**在被问到的那一刻没有答案**。准入控制要「进门前先算最坏情况」，而「释放空间这个操作本身不需要申请空间」也压在同一个数上 |
| **checker / 审计** | **必须**遍历 | 若运行时也用遍历算，checker 的遍历与运行时就是**同一次计算**，对照关系当场归零 |
| **后台、可续做、非决策路径**（销毁快照、整理、scrub） | **无戒律** | 它们走「写意图 → 分批 → 可续做」，不参与任何即时判定 |

**空间统计 / 配额 / 快照用量落在第一格**：必须在事务提交时增量维护出来。

⚠️ **被禁止的不是「遍历」，是两件事**：
「在需要答案的那一刻还没有答案」，以及「审计与被审计用同一段代码」。
第二条不依赖任何关于性能的假设——它要求的恰恰是**运行时与 checker 必须用不同的算法**。

⚠️ **别拿第一格的禁令去否第三格的设计。** 本工程已经在第二、三格豁免过三次：
checker 的全盘遍历、无界删除的意图分批、代际增量 scrub。
**一条被三次豁免的规则，它的判据就不在它字面写的那个量上。**

## 元数据块必须自描述

任何一个块单独捡起来，都要能回答「我是谁、我属于谁、我是第几代」。
这是「全盘扫描重建」在物理上可能的前提，**只能在格式层拿到，事后加不进去**。

## feature bit 分三档，且预留空位

`incompat`（不认识不许挂）/ `compat_ro`（不认识只读挂）/ `compat`（不认识随便）。

## 不同地址空间必须是不同的 Rust 类型

逻辑地址、物理地址、设备内偏移、代号、inode 号——一律 newtype，**混用必须编译不过**。

这是把一整类运行期 bug 变成编译期错误，是选 Rust 的主要理由之一。
`u64` 到处传是现有实现里真实存在的一类 bug 来源。

## 一个事务层，所有结构共用

不许为某个路径（如 fsync）开第二套事务机制。
为 fsync 单开一套日志树是常见做法，也是常见的独立 bug 源。

**它约束的是「结构」，不是「字节完全相同的落盘代码」。** 精确形态：
**一个共享的事务抽象状态机 + 一个封闭的提交步骤枚举**，
「这一步具体怎么落盘」按结构等价类分派。介质各自一条实现管道是允许的；
**绕开状态机的第二条发布路径不允许**。见 [decisions.md](../kb/decisions.md) D17 与 D13。

**推论：提交协议归本工程独占，不是可以外包的部分。**
一条第三方管道要引入新的结构性提交步骤，必须往本仓的共享枚举发 diff，
不许在自己的黑盒里发明——否则那一整类崩溃点从来没有被任何人枚举过，
而「我们保证入口和数据接口一致」这句话就是空的。

**不主动划这条线的后果有现役演示**（2026-08-27 现查 Linux 6.17 源码树）：
btrfs 的 zoned 支持不是一个 `zoned.c` 模块，`btrfs_is_zoned` 散在 20 个文件 **93 处**，
其中 **5 处在 `tree-log.c`**（事务日志路径）、**6 处在 `space-info.c`**（ENOSPC 准入）。
⇒ **介质分支不划线就会自己渗进本文件第一格与事务层**，而那正是本节明令不许多样化的地方。
**强解耦不是可选项，是防渗透的手段。**

# 不追求万能方案：分支是可以的，但要还对债

性能、安全性、设备约束三者常常没有单一最优解。
**与其硬造一个万能方案，不如显式分支**——不同规模、不同介质、不同安全要求走不同实现。

## 为什么现在可以比过去分得更细

过去的文件系统偏爱单一方案，很大程度上不是因为问题本身要求简单，
而是因为**一个维护者要把整套东西装进脑子里**：记忆负担、逐条梳理、
N 条路径之间保持一致、改一处要同步改哪几处——这些是人的瓶颈。

这部分成本现在确实被解除了：逻辑梳理与一致性维护是机器的强项。
**所以本工程不预设「越简单越好」，允许按情况细分。**

这是 `.claude/singlefs-ai-sop/rules/machine-first.md` 那条判据在设计层面的具体形态——
「设计要统一、概念要少」原本的理由是维护者要装得下，那条理由已经不成立了。

## 但有四样成本没有被解除

1. **验证是组合的，不是线性的。**
   崩溃一致性不按分支算，按**交互**算：操作跑到一半条件变了、恢复时走了另一条分支，
   要验的就是叉积。这个不因为代码由谁写而变小，只因为**分支之间是否互相隔离**而变小。
   → **只在操作期间不会变的输入上分支。** 设备类型稳定，可以；
   「当前填充率」会在操作中途越过阈值，那是危险的分支变量。

2. **格式上的分支是永久的。**
   代码分支可以删，**磁盘布局分支不能**——以后每个读者都要永远支持所有历史布局。
   → **行为上放开分支，格式上吝啬分支。**

3. **门禁的范围必须可判定——挂钟本身不是约束。**
   单次改动只碰一条分支时，只需重跑那一条，代价与分支总数无关；
   语料总量再大也不构成成本，因为等结果是异步的。
   **真正的约束是「这次 diff 到底碰了哪几条」判不判得出来**：
   判得出 ⇒ 只跑受影响的那些，O(1)；判不出 ⇒ 只能全跑，那时挂钟才变成问题。
   ⚠️ **「我只动了一条」是需要被证明的断言，不是事实**——btrfs 的 `btrfs_is_zoned`
   散到 93 处，正是一次次「我只是加个 zoned 支持」累积出来的。
   落点：[checks-owed.md](../kb/checks-owed.md) C8（范围判定）与 C19（腰线渗透）。

4. **罕见分支会腐坏。**
   千分之一才走到的分支，它的 bug 只在生产里出现——除非测试能**强制**进入它。

## 五条硬要求

1. **切换判据必须显式、可计算、写下来。**
   不许是「凭感觉」，也不许是埋在代码里的魔数。判据说不清楚 = 这个分支还没想清楚。
2. **每条分支必须能被测试强制进入。**
   留一个只供测试使用的开关，能无视判据直接走指定分支。
   **进不去就等于没测**——靠碰运气覆盖到的分支，等于没有覆盖。
3. **每条分支单独验，包括崩溃点重放。**
   「另一条分支测过了」不算——分支的意义就是行为不同，那崩溃语义也可能不同。
4. **分支必须可观测**：运行时能看出走了哪一条。
   **走错分支是性能悬崖，而悬崖是不报错的**——没有观测手段就永远发现不了。
5. **分支变量不许在操作中途改变。** 见上面第 1 条。

**反过来：判据写不出来时，先只做一条，而且先做慢而正确的那条。**
快路径是优化，慢路径是底线；先有底线，再谈优化。

## 这两条教条在格式层的形态

`singlefs-ai-sop/rules/machine-first.md` 的两条推论——**穷举的显式分支**、
**用类型让非法状态无法表示**——对代码无脑成立，代码示例见那一篇。
**格式层同样成立，但判据不同**，因为格式分支删不掉。这一节写清怎么判，省得每次重新争。

### 格式层的「让非法状态无法表示」，形态是 incompat feature bit

```rust
// ✗ 一套布局 + 参数：拿错假设是一次静默误读
struct SuperBlock { node_size: u32, /* ... */ }
// 读者按 sb.node_size 算偏移。若某个版本改了「node_size 含不含块头」的口径，
// 旧读者照样算得出一个偏移、照样读出「看起来合法」的字节 —— 不报错，而数据是错的。
```

```rust
// ✓ 布局身份进 incompat 位：不认识就挂不上，没有第三种结局
const INCOMPAT_LAYOUT_ROTATIONAL: u64 = 1 << 0;
const INCOMPAT_LAYOUT_SSD:        u64 = 1 << 1;
const INCOMPAT_LAYOUT_ZONED:      u64 = 1 << 2;

const SUPPORTED_INCOMPAT: u64 =
    INCOMPAT_LAYOUT_ROTATIONAL | INCOMPAT_LAYOUT_SSD | INCOMPAT_LAYOUT_ZONED;

fn mount(sb: &SuperBlock) -> Result<Fs, MountError> {
    let unknown = sb.incompat & !SUPPORTED_INCOMPAT;
    if unknown != 0 {
        // 拒绝挂载，而不是「尽力而为地猜」
        return Err(MountError::UnknownIncompat(unknown));
    }
    // ...
}
```

**差别不在写法漂不漂亮，在失败模式**：
参数化布局的失败模式是**静默误读**，incompat 位的失败模式是**拒绝挂载**。
后者正是教条二在格式层的形态——**用格式让「拿错布局去读」这个非法状态无法表示。**

### 由此得到格式分支的判据

> **一条格式分支值不值得，看它能不能把「用错了」变成「挂不上」。**

| 能 | 值得。它买到的是「误用不可能发生」，代价（永久支持这套布局）换到了对等的东西 |
|---|---|
| **不能** | **不值得。** 它只是多了一套要永远维护的布局、多一份 checker、多一遍崩溃点重放，**没买到任何安全性** |

这条判据把「格式上吝啬分支」从一句态度变成了可判的东西：
吝啬的对象不是分支数量，是**买不到失败模式改善的那些分支**。

⚠️ **判据里不许出现「这样更快」。** 更快是收益，不是安全性；
拿性能去换永久的格式债，要单独立决策、单独给数字，不能挂在这条判据下面过。

### 一个已经成立的实例，和一个不成立的

| 实例 | 判定 |
|---|---|
| **D12 的介质分层布局** | **成立**。不认识某套布局的读者会被 incompat 位挡在挂载之外，而不是拿错假设读出看起来合法的字节 |
| **D9 预留的「每个写的算法类型字段」** | **成立**，且它是本工程最干净的一个：老数据按各自字段解，遇到不认识的算法类型只能显式失败，不会静默按错算法校验 |
| **「持久 / 临时」分轨** | **不成立**（见 [decisions.md](../kb/decisions.md) D14）。轨道会被 `linkat` / `fsync` / 快照从操作范围之外翻转，翻转之后**盘上的位仍然是合法的**——它挡不住任何东西，因此买不到失败模式的改善 |

## 索引结构可以多样，事务层不许多样

不同数据的访问模式差异巨大（反向索引写多读少、目录项点查、extent 范围查询），
按访问模式选结构是允许的、甚至是推荐的。**唯一不许多样化的是事务层。**
