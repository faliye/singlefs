# 设计纪律

具体的设计决策记在 `.claude/kb/decisions.md`。本文只写**跨决策生效的纪律**。

**这是 singlefs 的项目本地规则**，不在共享 SOP 里——文件系统的设计纪律只有本工程需要。
共享规则在 `.claude/singlefs-ai-sop/rules/`。

## 从事务开始，不从功能开始

写路径的硬核是 COW 提交机制，一切骑在它上面。任何新功能都是「一种新的事务」。
**没有事务层的功能实现一律不收。**

推论：第一个可运行目标不是「能创建文件」，是「能正确提交一个事务」——
哪怕它只能分配块、写入、提交，没有目录、没有树、性能烂到底。

## 记账是事务的副产品，不是事后的遍历

空间统计 / 配额 / 快照用量，必须在**事务提交时增量维护**出来。
任何需要「事后扫一遍才能算出来」的记账设计，一律否决。

checker 可以遍历——**它的职责就是用遍历验证增量记账有没有出错**。
这一对照关系是验证记账正确性的核心手段，别把两者混为一谈。

## 元数据块必须自描述

任何一个块单独捡起来，都要能回答「我是谁、我属于谁、我是第几代」。
这是「全盘扫描重建」在物理上可能的前提，**只能在格式层拿到，事后加不进去**。

## feature bit 分三档，且预留空位

`incompat`（不认识不许挂）/ `compat_ro`（不认识只读挂）/ `compat`（不认识随便）。

## 不同地址空间必须是不同的 Rust 类型

逻辑地址、物理地址、设备内偏移、代号、inode 号——一律 newtype，**混用必须编译不过**。

这是把一整类运行期 bug 变成编译期错误，是选 Rust 的主要理由之一。
`u64` 到处传是现有实现里真实存在的一类 bug 来源。

## 一个事务层，所有结构共用

不许为某个路径（如 fsync）开第二套事务机制。
为 fsync 单开一套日志树是常见做法，也是常见的独立 bug 源。

# 不追求万能方案：分支是可以的，但要还对债

性能、安全性、设备约束三者常常没有单一最优解。
**与其硬造一个万能方案，不如显式分支**——不同规模、不同介质、不同安全要求走不同实现。

## 为什么现在可以比过去分得更细

过去的文件系统偏爱单一方案，很大程度上不是因为问题本身要求简单，
而是因为**一个维护者要把整套东西装进脑子里**：记忆负担、逐条梳理、
N 条路径之间保持一致、改一处要同步改哪几处——这些是人的瓶颈。

这部分成本现在确实被解除了：逻辑梳理与一致性维护是机器的强项。
**所以本工程不预设「越简单越好」，允许按情况细分。**

这是 `.claude/singlefs-ai-sop/rules/machine-first.md` 那条判据在设计层面的具体形态——
「设计要统一、概念要少」原本的理由是维护者要装得下，那条理由已经不成立了。

## 但有四样成本没有被解除

1. **验证是组合的，不是线性的。**
   崩溃一致性不按分支算，按**交互**算：操作跑到一半条件变了、恢复时走了另一条分支，
   要验的就是叉积。这个不因为代码由谁写而变小，只因为**分支之间是否互相隔离**而变小。
   → **只在操作期间不会变的输入上分支。** 设备类型稳定，可以；
   「当前填充率」会在操作中途越过阈值，那是危险的分支变量。

2. **格式上的分支是永久的。**
   代码分支可以删，**磁盘布局分支不能**——以后每个读者都要永远支持所有历史布局。
   → **行为上放开分支，格式上吝啬分支。**

3. **门禁的挂钟时间是真的。**
   分支 × 崩溃点是机器时间，但门禁要跑八小时的话，人就不会在提交前跑它——
   而「本地先跑一遍、与远端同判」是整套设计的支点。**门禁运行时长本身是设计约束。**

4. **罕见分支会腐坏。**
   千分之一才走到的分支，它的 bug 只在生产里出现——除非测试能**强制**进入它。

## 五条硬要求

1. **切换判据必须显式、可计算、写下来。**
   不许是「凭感觉」，也不许是埋在代码里的魔数。判据说不清楚 = 这个分支还没想清楚。
2. **每条分支必须能被测试强制进入。**
   留一个只供测试使用的开关，能无视判据直接走指定分支。
   **进不去就等于没测**——靠碰运气覆盖到的分支，等于没有覆盖。
3. **每条分支单独验，包括崩溃点重放。**
   「另一条分支测过了」不算——分支的意义就是行为不同，那崩溃语义也可能不同。
4. **分支必须可观测**：运行时能看出走了哪一条。
   **走错分支是性能悬崖，而悬崖是不报错的**——没有观测手段就永远发现不了。
5. **分支变量不许在操作中途改变。** 见上面第 1 条。

**反过来：判据写不出来时，先只做一条，而且先做慢而正确的那条。**
快路径是优化，慢路径是底线；先有底线，再谈优化。

## 索引结构可以多样，事务层不许多样

不同数据的访问模式差异巨大（反向索引写多读少、目录项点查、extent 范围查询），
按访问模式选结构是允许的、甚至是推荐的。**唯一不许多样化的是事务层。**
