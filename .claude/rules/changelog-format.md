# kb 历史怎么组织

**这是 singlefs 的项目本地规则**，不在共享 SOP 里——共享的 `kb-discipline.md` 只要求每份 kb 文件以
「## 历史版本」收尾、正文只写现状；这份定的是那一节内部怎么排，以及 `decisions-history.md`、
`experiments-history.md` 这两份登记表怎么组织。共享规则在 `.claude/singlefs-ai-sop/rules/`。

## 一份 kb 文件自己的「历史版本」节：按日期分组，日期只写一次

「## 历史版本」下面，同一天只有一条改动时，标题写成 `### YYYY-MM-DD` 或
`### YYYY-MM-DD：一句话摘要`，不强行拆出子标题——日期只出现一次，这条就已经满足。

同一天出现第二条改动时，把这一天的全部改动（含已经写在那儿的那一条）收进一个
`### YYYY-MM-DD` 标题下面，各自占一个 `#### ` 子标题，不在子标题里重复日期。

子标题写这条改动的一句话摘要。加 `（其一）`、`（其二）`……的判据不是摘要的字面撞没撞，
是**这条改动能不能靠一个更短的引用词区分**：子标题带着「已定项 N」「未定项 N」「E<n>」这类
点名词时，同一个点名词在同一个日期块里第二次出现就加编号（不同点名词各自不加，哪怕摘要碰巧很像）；
子标题没有这类点名词、只是一句自由文字时，同一个日期块里出现第二条就都加编号。
按写入次序编号。日期块按日期倒序排（新的在最上面），块内的子标题按写入次序排（先写的在上面）。

`decisions-history.md`、`experiments-history.md` 不适用「只有一条可以不拆」这条放宽（组织形态
见「`decisions-history.md`：按决策分组，一节一份完整历史」与「`experiments-history.md`：按实验
分组，同一套规则」两节）：那两份文件里子标题本身就是要点名的信息（哪个分项、哪个实验），永远单独占一行。

## `decisions-history.md`：按决策分组，一节一份完整历史

每条决策一个 `## D<n>（简称）` 节，节内是这条决策的全部历史，按「一份 kb 文件自己的「历史版本」节」
那一节的规则组织（日期分组，子标题写「已定项 N」或别的改动摘要）。**没有单独的按月原文文件**：
条目直接写进 `decisions-history.md` 对应决策的节里，不再往 `decisions-history/<年-月>.md` 分流。

一条改动点名了几条决策，就在几节里各写一份、内容相同。`decisions-history.md` 里不许有挂不上
任何 `## D<n>（` 节的日期条目——一条改动进不了任何决策的节，说明它不该记在这份文件里（记不属于
任何决策的过程性事项，去 `records/` 或别处，不写进这份决策变更史）。

`## D<n>（简称）` 节顶上（标题下第一行非空行）写一行现状：
`**现状**：<decisions.md 索引表那一行的「状态」格>。<「结论（简报）」格>`，历史条目排在这句下面。

## `experiments-history.md`：按实验分组，同一套规则

每个实验一个 `## E<n>（简称）` 节，节内历史按「一份 kb 文件自己的「历史版本」节」那条规则组织。
一条改动点名了几个实验，就在几节里各写一份。节顶上同样写一行现状，取自 `experiments.md`
索引表同一条实验的「状态」「结论（简报）」两格，写法与 `decisions-history.md` 那一行相同。

## 并发写入时的编号

`（其N）` 是先到先得的公共资源：取号前先查同一个分组（同一份文件的同一个日期块，或
`decisions-history.md`／`experiments-history.md` 里同一节同一个日期块）下已经用到的最大号，
取下一个没被占的号，不改别人已提交的那条。

## 门禁管哪一半

判「有没有按这份规则组织」的是门禁 doc-decisions（`.claude/gate.d/doc-decisions.sh`）的三格：
`entry-added`（决策正文改了，`decisions-history.md` 要有新增条目）、`shape`（日期与序号分属
`### ` / `#### ` 两层、两份变更史的日期块住在自己的 `## D<n>（` / `## E<n>（` 节、同一节里日期不
重复——后两条只判 `decisions-history.md`、`experiments-history.md`，一份 kb 文件自己文末的
「## 历史版本」不受「必须挂在 `## D<n>（` / `## E<n>（` 下面」这条约束，那一节本身就是它的分组）、
`status-sync`（两份变更史每节顶上的现状行与索引表一致）。具体判据以那份脚本的文件头为准。

**它管不了的**：摘要写得对不对、一条改动该点名的决策或实验有没有点全——这几样靠人。
