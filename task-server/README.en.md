# task-server

[中文](README.md) · **English** · [日本語](README.ja.md)

For resources still held after an abnormal exit, remote cleanup receipts and diagnostic logs, see [Task cleanup and GPU phase logs](cleanup-protocol.md).

The unified task server of singlefs: every task that runs project code (light, heavy, CPU, GPU) is started through it and goes into one queue, where the server schedules by resources and fairness rules with no extra delay: when the head of the queue does not fit, a task behind it that fits may start first (cutting in), and a task submitted two hours ago or more moves to the front; the rules are in "## Scheduling". Tasks are submitted only by the main agent (with the client `task-server/task`, which people use too); sub-agents only use `status` and `log` to read outcomes; picking the host, setting the memory budget, deciding whether a GPU is needed and which card to use are all decided by the server, and submission does not accept any of these.

The server is the only process that reads and writes the database: FastAPI on uvicorn, running as the user-level systemd service `singlefs-task-server.service`, listening only on a unix socket (`${XDG_RUNTIME_DIR}/singlefs-task-server/server.sock`, directory 700; the full path is at most 107 bytes, and beyond that the server, the client and `control` all exit 78, naming the path, its byte count and the limit), never on TCP. The database is embedded SQLite (WAL) under `~/.local/state/singlefs/task-server/`, and every row carries an HMAC check column. Memory acceptance is judged in one place only, the server: a task starts only when it fits, and one that does not fit stays queued in the database; a started task is still wrapped in `scripts/hosts/run-with-memory-cap.sh` (this host, with the "accepted by task-server" switch set, doing only the kernel-level backstop of the per-task cap and the slice total cap) or `scripts/hosts/multi-host-run.sh --peer` (second host).

| File | What it does |
|---|---|
| `task` | Client: `submit [--cwd <directory>] -- <command…>`, `wait <number>`, `status [<number>] [--json]`, `cancel <number>`, `log <number>`, `clean <number>`; usage and exit codes are in the file header |
| `control` | Install and check: `install [--dry-run]`, `check` (the server's `/health` reports only three things: the database cannot be written; the dispatcher judged the head of the queue startable yet failed to start it for three rounds in a row, while heads it judged not startable — waiting for a card, for the load, for an alternation group — are not reported; the progress watch: a host fits the smallest queued task by the formula yet started nothing for 10 minutes, which catches the dispatcher judging wrong), `start`, `stop`, `clear-queue` (with the server stopped, empties the task and attempt tables in the database after backing it up; resource records are kept), `pin-cap <command…>` / `unpin-cap <command…>` (through the server, pins or unpins a command's memory cap; exits 0 only after reading it back), `pause [--reason <one sentence>] [--allow-session <session id>]` / `resume` (pause and release the queue: while paused the server still accepts submissions but starts nothing new, except tasks of the allowed session, see "## Pause and resume") |

| `task_server_lib.py` | The shared part: paths, dependencies, the error-type and exit-code table, retries, resource records, build directories, sharding, the environment-variable list, identity; the whole self-test `--selftest` and the breakage switch table are in its file header |
| `task_server_selftest.py` | The self-test cells (started by the previous row) |
| `singlefs-task-server.service.in` | User-level unit template |

There is no configuration file of its own: scheduling resources are read from the multi-host configuration `multi-host.env` at the repository root (template `multi-host.env.example`); the socket, database, logs, signing key and build directories use the fixed defaults written in the "paths" section of the `task_server_lib.py` file header. Required: fastapi, uvicorn, `multi-host.env` (with `NFS_SHARED_ROOTS`, `SHARED_DATA_ROOT` and `HOSTS` in it, written as in "Which keys in the multi-host configuration" under "## NFS share"), the NFS share set up (see "## NFS share"), and a reachable server.

## Scheduling

Hosts are picked by balancing free room: a task that needs no card picks, among the hosts it can be sent to, one where it fits; when more than one fits, it picks the one whose remaining room after placing it is the larger share of that host's total cap, and this host on a tie; a retry after hitting the cap is not pinned to a host. Shards go to the second host first as the plan says, and are not moved by balancing as long as they fit there; the plan, the shards and the merge are not pinned to a host, and a plan that writes `pin` makes the whole task `shard-plan-refused` (shards are not pinned; the server picks the host). The second host runs in the same shared tree: the repository, the shared data root holding the work root `~/.local/share/singlefs/work/`, and the session transcript directory are mounted on both hosts at the same absolute paths over NFS (`NFS_SHARED_ROOTS` in the multi-host configuration, see "NFS share" below), so a run sent to the second host is started directly by `scripts/hosts/multi-host-run.sh --peer` in the task's working directory at the same absolute path, with no tree copied, nothing sent or fetched back and no path rewritten, and the files it writes are readable on both hosts; the build directory is created afresh for that run by `multi-host-run.sh` on the second host's local disk (`builds/<label>/target` under the second host's entry in the multi-host configuration's `BUILD_ROOT_BY_HOST`, under no shared root) and deleted when the command ends or is stopped (for a command that compiles it is kept for the requeue after hitting the cap, see "Starting peaks" below); the server does not set it and only records where it is (shown by `task status`); `task clean` does not touch it. Whether a task goes to the second host depends only on whether the second host is usable right now and on free room; the three kinds that could not be sent there are refused at submission ("## How to submit" below). There is no list of commands kept to one host (the user: "I say it once more: [runs only on this host] is not acceptable. Fix it as soon as possible and let the errors show"): a command naming any directory or entry can be sent to either host, and free room decides which; one that goes red on the second host stays red and is fixed in the script, the server does not shield it. Tools that change the main work tree (`hook-swap.py`, `apply-writer-patch.py`, `stage-mine.py`, those under `scripts/kb/`, `merge-and-verify` without `--skip-apply`) and commands with `--write` can be sent to the second host (they change the same tree); outcomes that would otherwise be retried, such as hitting the cap, are still not retried for them but handed back to the session that submitted them; so the tools in the parentheses get enough on the first attempt: the cap is at least "(highest of the last 5 runs of the same key + highest of the last 5 runs of the key of the verification command given by `hook-swap.py`'s `--verify`) × 1.5", with no 4G floor (task 8367 was given only 857M by the same-key window, hit it, and was left half swapped). The plan directory and each shard's artifact directory of a sharded task live under `task-server-shards/` in the shared work root, read and written by both hosts at the same absolute paths. The server does not check the merge lock: while the main work tree is being merged, tasks are queued and started as usual. At most 4 tasks start on the second host in one pass (starting too many at once gets ssh connections reset), and once that is reached another pass runs 2 seconds later; the outcome of a run on the second host follows the end line that `multi-host-run.sh` writes into the log for that command (`MULTI_HOST_RUN_STEP step=peer-command event=end … exit=<code>`): with that line the outcome follows the command's own exit code, and a command that itself exits 255 is recorded as `command-failed` and not requeued; only an exit of 255 without that line means the second host failed to run it (unreachable, ssh reset), recorded as `peer-run-failed` and requeued unchanged, at most 2 times. When the head of the queue does not fit, tasks behind it that do fit start first (cutting in); tasks younger than two hours alternate per host between whole tasks and fragment groups: the line is 85% of the host's usable cap (its total cap minus that host's margin right now), a task booked at or above it is a whole task and the rest are fragments; fragments fill one group in queue order, and when the next one would take the group past the line while a whole task waits, the group is sealed and takes no more fragments, the whole task starts as soon as it fits (it does not wait for the host to empty), and after it the next fragment group follows; waiting reasons from the alternation contain "在等这台腾空" (waiting for this host to free up). A whole task waits for one host only and seals only that host: it keeps waiting on the host already sealed for it in an earlier pass, otherwise on the host closest to fitting it right now (its booking minus what that host has left by "configured total cap − margin − sum of the caps of running attempts" is smallest); the other host keeps starting fragments. A host is sealed only if the whole task fits it: when the predicted peak itself is above the largest cap that host can give right now, the host could not start it even when empty, so it is not sealed for it; when it fits no host, nothing is sealed and the queue sends it back as `memory-cap-at-maximum` the moment it judges it. A whole task that needs cards counts only hosts with enough free cards for it, so a host whose cards are taken is not sealed for it. `/health` judges whether the head fits by the same check as placement (memory, build-directory disk, the CPU gate, the number of cards). A group's account is how much fragment booking the group has taken in: finished fragments still count (the group seals when it reaches the line and only then does the whole task get its turn; if finished ones were subtracted, fragments arriving one after another would keep the group from ever sealing), and fragments gap-filled while it is sealed are not added; the sealing sentence also gives how many of the group's fragments are still running and their booking, which drops as they finish. Gap filling while a group is sealed: the share that stays free on that host beside the head whole task is "configured total cap − margin − the head's booking − sum of the caps of attempts gap-filled beside the whole that are running" (fragments started before the seal are not subtracted: the whole task waits for them to finish anyway); a fragment that fits in it starts without looking at durations (this is how a small task with no estimated duration starts when both hosts are sealed, task 8370); one that would take part of what the head needs starts only if its estimated duration is no longer than the longest remaining time among the attempts running on that host (the blocking time), and one with no estimated duration stays sealed; a head whole task booked at the whole usable cap of that host leaves that share at 0. Estimated duration: for `scripts/crash/crash-point-replay.sh`, `.claude/gate.d/formal-verification.sh` and `.claude/gate.d/crates-mutation-replay.sh` given `--item` and not sharded, the service first runs an estimate child task (the same entry with `--list-items --with-keys`, reading one line per item, `ITEM_PLAN item=<item> to_judge=<entries to judge afresh> reusable=<entries to reuse>`), and the task joins the queue only once that child has an outcome; after every run the service reads one line per item from the log, `ITEM_DONE item=<item> seconds=<seconds> judged=<entries judged> reused=<entries reused> exit=<code>`, and records per item "seconds per entry judged afresh" and "seconds per entry reused" (in the service's own database, not in prune-server); the estimated duration is the sum over the items of counts times rates, and there is none if any item lacks a rate; a task whose estimate failed queues with no estimated duration. For other commands the estimated duration is the duration of the latest run under the same command key (the key memory records use: paths and items folded word by word, `--check` cell names kept) in which the command itself ran to its exit (exit 0 and the command's own non-zero exit both count; signal kills and outcomes the service judged or interrupted — cap hits, timeouts, stalls, squeeze-outs, cancellations, two-hour bounces — do not); the plan, shard and merge steps of a sharded task work the same way (each step takes the latest successful run of its own command key, each shard one per shard number; the plan step does not give the items of each shard, so an estimate per item is not possible for a shard). After the estimated duration, `task status <id>` says whether the figure came from the command, from the items, or that there is no record. A task submitted two hours ago or more moves to the front and is judged first; a whole task that old still counts as a whole task and seals a group for itself while not being held back by the alternation, and a host sealed for such a task takes no gap filling at all and waits to empty for it (user: 「一个任务都排了两个小时了 还要有任务插队 明显不合理」); when it does not fit, it neither holds back the tasks behind it nor keeps a share, and the tasks behind it that fit start in queue order. Queued tasks never hold room. GPU tasks pick cards in the order given in the multi-host configuration (the rule is in the "GPU" section of the `task_server.py` file header); a card's host label is that host's address in the multi-host configuration's `HOSTS`, each entry `<address>:<card index>:<quota>` (for example `192.0.2.1:0:32G`; the address may be IPv6, so the entry is split at the last two colons), a label that is not in `HOSTS` is a broken configuration, the server finds its own host through `HOSTS`, and the command gets the entry unchanged in `GPU_CARDS_BY_PRIORITY`; a cargo run with a card feature (`gpu`, `tests-on-a-real-gpu`, also as `<package>/<name>`, and `--all-features`) needs a card only when it is `test`, `run` or `bench`, which run the compiled code, without `--no-run`; `clippy`, `check`, `build`, `doc` and `--no-run` only compile, and need no card and no quiescing. A script that needs a card only for some arguments declares them in its first 60 lines with a line `# task-server-gpu-arguments: <word> [<word>…]`: started by bash or python3, it needs a card when its first non-option argument is one of those words (`*` means any argument); the form is in the `task_server_lib.py` header, section "GPU". Both hosts go through the same logic (booking, fitting, stall and CPU, peaks, caps, build directories, host picking and free disk, with the same 50G disk floor on both); what differs per host is only how it is reached, measured and started (`Machine` in `task_server.py`). When an attempt ends normally and grandchild processes of the command are still in its unit, the server stops them and says so in the outcome note; when a run of more than 30 minutes fails and the script does not declare that it can resume with `# task-server-resumable: <word>…` in its header, the outcome note says "ran N minutes, not resumable: a resubmission starts from scratch" (in Chinese).

Each attempt's command is wrapped in `scripts/hosts/capped.sh <default heavy threads per host>`, and the thread count is always that number and is not accepted at submission; a task that needs a card is always wrapped once more, outermost, in `scripts/crash/gpu-quiesce-run.sh --`. The memory wrapper, `capped.sh`, the quiesce wrapper and `multi-host-run.sh --peer` accept only the layer the server wraps directly: the server sets an admission mark for each layer (its value is `<task number>.<attempt number>`), that layer reads it and does not pass it to the command, and a script inside the task that wraps one more layer is refused on the spot; the way out is to delete that layer and read the memory, threads and card from `TASK_SERVER_MEMORY_CAP_BYTES`, `SINGLEFS_THREAD_CAP` and `GPU_CARDS_BY_PRIORITY` that the server passes; a cargo run that compiles also gets its own `CARGO_TARGET_DIR` outside the repository, which the server removes once the task has an outcome (with `SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1` set at submission it is kept, the last line of `wait` carries `build=<directory>`, and the submitting session removes it with `task clean <number>`); a cancelled task has it removed together with the scene in the same cancel (the cancel under "## 提交写法" below). The budget follows only the server's own attempt records (the largest peak of the last few successful runs × 1.5; the memory wrapper's peak table is not read; the command key first drops an `env` prefix of variables that do not change how the command runs, such as the multi-host configuration path and `LANG`); a command with no record starts at 4G (one that has only failed starts no lower than the peak of that failed run × 1.5), a command with a record has its cap and booking set from the record × 1.5 and is not raised to 4G (a pinned cap is left as it is), and a task is requeued × 1.5 after hitting the cap (the requeued cap is not raised to 4G either); when × 1.5 would reach that host's total cap it is not requeued: it moves to another host with a larger total cap if there is one, and otherwise is recorded as `memory-cap-at-maximum` and returned to the submitting session, where `next=` and the message to the session name the host, the cap reached and the peak, and suggest checking this run's scope (the items named, the test targets), its sharding and how many run at once, and resubmitting it smaller or sharded; quotas, build families and sibling shards read only attempt records whose peak measurement basis column says 「进程内存」 (process memory), and older records without that column (page cache included) are not read; the room left on a host counts only memory used by processes (`anon` plus `shmem`), not the page cache or kernel memory charged to the slice; nothing is judged during a 10-minute grace after start; after that, a task whose log has not grown for 10 minutes and whose CPU has also barely risen in that time (on average under 1% of one core) is stopped by the server and recorded as `stalled`, and unreadable CPU does not count as not rising; a task whose log and CPU have both not grown for 10 minutes while every poll in that time found some process in state D (uninterruptible IO wait: on this host the server reads the state field of `/proc/<pid>/stat` for the attempt's processes, on the second host it reads the `MULTI_HOST_RUN_PEER_IO_WAIT poll=<poll> blocked=<processes in state D> read=<yes|no>` line that `multi-host-run.sh` prints every poll, a line that does not count as log growth) is waiting on IO: it is not recorded as `stalled` and not stopped, and if any poll found no process in state D or could not read the states the original rule applies (tasks 8608, 8609, 8611 and 8619 were stopped as stalled while waiting on the NFS this host exports); a task that needs a card and whose attempt was given one, whose log and CPU have both not grown for 10 minutes while every poll in that time found a compute process of this attempt on its card (on this host the server checks whether the compute processes listed by `nvidia-smi -i <index>` include a descendant of this attempt, on the second host and when it cannot be measured it counts as present) and some poll in that time read a nonzero utilization on the card (on this host the same `nvidia-smi -i <index>` reads `utilization.gpu`; on the second host and when it cannot be read the compute process alone counts, and the basis says the utilization could not be read) is computing on the GPU: it is likewise not recorded as `stalled` and not stopped; a task whose compute process stays on the card holding memory while every poll reads a utilization of 0 has an idle card, and the original rule applies, so it is stopped and recorded as `stalled` (task 9341 held 14129 MiB on its card at 0% utilization while its last test cases did not move for half an hour); for such an idle card the "CPU barely moved" threshold rises to the command's own CPU averaging under 1 core over the window (a CPU-side polling wait is stopped, and the note gives three readings: how long the log has been still, the card utilization and the command's own CPU; 1 core or more is computing on the CPU and keeps running); if any poll found no compute process of it on the card, or the attempt was given no card, the original rule applies (tasks 8519 and 8520, two single GPU differential tests given a card on this host, were stopped as stalled while the GPU was computing; the user decided that a GPU task is 「不自己终止，告诉负责的对话 自己检查」, not ended by the server but reported to the responsible session to check); a task that has run past 5 times its recorded duration and whose log has not grown for 10 minutes is stopped and recorded as `stalled` without looking at the CPU (an endless loop is stopped too), and a task with no recorded duration is not judged by this rule; `stalled` is not retried and is returned to the submitting session; a task whose process memory (`anon` plus `shmem`, the same measurement basis as the room left above; page cache that fills the cap is reclaimed by the kernel and kills nothing, so it does not count), current or peak, had reached 98% of its cap at the moment it was judged stuck is stuck at the cap: it is stopped the same way but recorded as `memory-cap-hit` and requeued × 1.5 (a pinned cap is returned as `memory-cap-at-maximum`), with the note "顶在上限上卡住" (stuck at the cap); how long it has run, the recorded duration and the cores in use are written only into `task status`. The recorded memory peak counts only process memory on both hosts: every poll reads `anon` plus `shmem` from `memory.stat` of the memory wrapper's scope and keeps the largest seen (task 8853, building the verification package, used under 1G in its processes while page cache pushed the scope's `memory.peak` to the 50176M cap); only a command shorter than one poll, never sampled, falls back to the `memory.peak` the wrapper reads on exit. The memory peak of the second host's layer is recorded into that attempt from the `MULTI_HOST_RUN_PEER_MEMORY_PEAK bytes=<bytes>` line that `multi-host-run.sh` writes, and feeds the budget the same way as on this host; a run without that line is recorded as not measured. The disk taken by the build directory is also recorded per command as a peak (on this host by measuring the build directory the server gave, on the second host from `MULTI_HOST_RUN_PEER_BUILD_PEAK bytes=<bytes>`); before a task is sent to a host, that host's free disk minus what running attempts' build directories will still grow must hold this command's build-directory peak plus a 50G floor, otherwise the task stays queued and its waiting reason names "编译目录占盘" (build-directory disk). A command that itself exits 75 (prune-server unavailable) is recorded as `prune-server-unavailable`, `wait` exits 75 and it is not requeued; the server runs `python3 prune-server/control check` once and writes an alert when it fails, without starting or stopping prune-server. A command written as `python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <path>] -- <original command>` has its command key and its registry row taken from the original command after `--` (the `--server-binary` path is not part of the key), and the key is prefixed with `〈task-server 临时 prune-server〉`: the same scope runs one more prune-server, so it does not share a record with the unwrapped command; the wrapper itself still runs as written.

Admission books the cap: running attempts and new ones are booked at their cap (clamped to that host's total cap minus that host's margin right now), so the caps of the tasks running on a host never add up to more than that host's slice total minus that host's margin right now; the part not yet grown into is counted as "cap − the memory it cannot reclaim right now"; both hosts go through the same code: the usage is measured per attempt's scope by the same read of that host's margin (the same ssh for the second host; a scope is matched to its attempt by `TASK_SERVER_ATTEMPT_LABEL` in the environment of its processes, set on both hosts), an attempt whose scope is missing from that report is booked at its whole cap, not 0, and the memory wrapper on the second host keeps no booking of its own. The margin is the memory in that host's `singlefs-heavy.slice` right now that cannot be reclaimed and belongs to no running task (charged to the slice itself and found in no child cgroup; how it is measured is in the header of `scripts/hosts/memory_peaks_lib.py`, "余量"); every read of the two hosts' free room measures it on each host separately and rounds it up to a whole GiB (1.01G and 1.1G count as 2G, 2.1G as 3G, 0.7G as 1G, an exact whole number stays as it is); it is not a constant and is not in the configuration. A host whose margin cannot be measured gets nothing that pass, and the queue reason names the host and why; when no host the task can go to can be measured, it is not started and records `run-condition-unmet` (`wait` exits 78), with no fallback to a fixed number. Each attempt hands its cap (bytes, decimal) to the command in the environment variable `TASK_SERVER_MEMORY_CAP_BYTES`, on this host and on the second host alike. `python3 task-server/control pin-cap <command…>` pins a command's cap (`unpin-cap <command…>` removes it; written through the server, so it works while the server runs): a pinned command's cap and booking are the entry for the host it is sent to in the multi-host configuration's `SLICE_MEMORY_CAP_BY_HOST` minus that host's margin right now (space-separated `<address>=<value>`, the entry is that host's slice total, taken exactly as written; read afresh every time, never stored as a literal number; when an entry is not larger than that host's margin, `pin-cap` refuses on the spot and the way out is to raise that entry), learned peaks do not override it, hitting the cap does not grow it but records `memory-cap-at-maximum`, and `task status` says the cap is pinned; a pinned command whose configured `SLICE_MEMORY_CAP_BY_HOST` cannot be read (missing, malformed, one host left out, an address not in `HOSTS`, or the file unreadable) is not started and records `run-condition-unmet` (`wait` exits 78), and the reason line of `wait` names why it cannot be read and the way out (fix the configuration or `unpin-cap`). A suspected stall is only reported: after the grace, when the whole unit's CPU has averaged under 1% of one core for 10 minutes (for a task with a card, also no compute load of its own on its card in that time; unmeasurable counts as load), whether or not the log grows, the server does not stop it: `task status` writes "suspected stall" with the evidence, an alert is recorded, and `wait` prints one line `TASK_SERVER_SUSPECT task=<number> …` and exits 231; the task keeps running, and starting `wait` again keeps waiting (one report per stretch; the stretch ends when the CPU rises again). An attempt whose log has not grown for 10 minutes and whose memory right now is at least 98% of its cap is stopped even while its CPU rises (spinning in reclaim is not computing; task 7723 ran like this against a 6144M cap for 37775 seconds), recorded as `memory-cap-hit` and requeued at 1.5 times the cap; both hosts are judged by the same code, this host reading the outer scope's `memory.current` and the second host reading the `MULTI_HOST_RUN_PEER_MEMORY` line that `multi-host-run.sh` prints every round (that line, like `MULTI_HOST_RUN_PEER_CPU`, does not count as the log growing). Gates under `.claude/gate.d/` can be sent to the second host (it runs this same shared tree); a task with a verdict library whose row in the registry `.claude/gate.d/verdict-library-scripts.tsv` does not yet say prune-server in the third column is refused at submission ("## How to submit" below). `python3 scripts/experiment-apparatus/device-code-key.py run … --feature <value>` with a feature value containing gpu needs a card too. `/health` only probes a database write and the queue thread's heartbeat; whether the head fits but has not started is worked out by the queue thread on every pass and `/health` only reads it.

Two-hour bounce: except for the commit-time gates, a task whose attempts have been running for 120 minutes in total (queueing does not count; an attempt that hit its memory cap and was retried one size up resets the clock, so counting starts again from the attempt after the latest cap hit, however many there were; each shard counts on its own), is stopped by the service with outcome `over-two-hours` (`wait` exits 242). The message to the session gives the command, the scope declaration, the total and per-attempt durations and the last log lines, and asks it to check two things: is the scope right (name the scope — `--item`, fewer `--check` cells, named test targets; give a patch directory; or let the service shard; whole runs wait for commit time), and does this task really need that long. If not, change the scope and `task submit` as usual; if so, run the full line from the message, `task-server/task requeue <number> --long-run-confirmed --items <N> --tasks <M> --why '<why it needs that long and why the scope is what it is>'`: only the submitting session, only for a number whose outcome is `over-two-hours`; the two numbers are checked the same way as `task confirm` (a mismatch exits 3 and prints the service's confirmation sheet); `--why` needs at least 12 characters once whitespace is removed; a number can be requeued once. Once checked, the original command and scope declaration enter the tail of the queue as a new task (its position is the requeue moment), flagged "long run confirmed": it is no longer bounced at two hours, every other rule still applies, and `task status`, the list, messages and the log head print a line 「长跑已确认（原号 <n>）：<why>」. The original number is not requeued on its own. The only exemption is a commit-time gate: one of the six commit-time gates (`crash-point-replay`, qemu-device-streams, lkmm, crates-mutation-replay, formal-verification, broad-mutation) or `scripts/gate/gate-staged.sh`, without `--check` or `--item`, whose scope declaration's 为什么 says 提交前; gates with `--check`, `merge-and-verify`, entry scripts and experiments are not exempt.

Whole-package tests need a confirmation flag: `cargo test` that names no `--test`, no `--bin` and no `--lib` with a test name, or carries `--lib --tests` or `--workspace`; `.claude/gate.d/crash-point-replay.sh --check` naming all three cells crash-case-replay, feature-gated-tests and product-gpu-real-card-tests; `scripts/gate/merge-and-verify.sh` without a patch directory — these are whole-package tests and are refused at submit time (exit 3, anomaly table `whole-package-unconfirmed`) unless submitted with `task submit --whole-package-confirmed <confirmation file>`; commit-time gates are exempt. The confirmation file holds the three confirmations of `.claude/agent-common.md` 「日常开发的测试不跑整个包」 (① the files and functions changed, ② the test targets and functions that reach them, with the grep hits, ③ why naming ② is not enough), lives under a shared root and is given as an absolute path; the service checks only its form (readable, all three sections present, each at least 12 characters without whitespace) and refuses with exit 3 naming the missing section otherwise. Once accepted, `task status`, the list, messages and the log head print a line 「整包已确认：<file>」; the flag does not exempt the task from the two-hour bounce, and a requeue after a bounce carries both flags.

Memory breakdown at a cap hit: the memory wrapper on either host, when it judges that a command hit its own cap (exit 250), prints a line `RUN_WITH_MEMORY_CAP_OOM_STAT anon=… file=… file_dirty=… file_writeback=… shmem=… oom_kill=…` into the log (`scripts/hosts/run-with-memory-cap.sh` header 「撞上限那一刻的内存明细」); the service turns it into a sentence in that attempt's outcome note and in the message to the session, saying whether the bulk was the process's own memory (anon) or page cache (file, including dirty pages not yet written back); it only records, the judgement is unchanged.

## NFS share

**Why it is needed.** The principle the user set: “All scripts must run on multiple hosts. The results they produce must be readable from every host. If that cannot be done, either copy the resources or share the files.” NFS is the share-the-files route: this host exports some directories, the second host mounts them at the same absolute paths, so a result written on one host is read directly on the other, and a path a task refers to points at the same thing on both. On 2026-11-01 the user also set: “The NFS configuration must be written in the task-server readme. Do not leave anything out. This part must also be a checked item. Without NFS, do not start. Require the user to configure it. The configuration comes from the multi-host configuration file; no extra configuration file is allowed.” So the server does not set up NFS for the user: the configuration is a single key in the multi-host configuration `multi-host.env`, and the server does not start until it is set up.

**Which roots are shared.** Three: the repository itself (the root of the main work tree: the second host runs in this live tree, no tree is copied), the shared data root `~/.local/share/singlefs` (the work root and shard artifacts live under it) and the session transcript directory `~/.claude/projects`; each taken as this host's absolute path and mounted on the second host at the same absolute path (the second host's home directory may be another one; the mount points follow this host's paths).

**Export on this host.** Install `nfs-kernel-server` on this host, write one line per shared root in `/etc/exports`, exported only to the second host's address on the direct wired segment (the real address is a private value and is written only in that file on this host), then make the export take effect and enable it at boot:

```bash
# /etc/exports, one line per root
<root> <second host's address on the direct wired segment>(rw,sync,no_subtree_check)
sudo exportfs -ra
sudo systemctl enable --now nfs-server
```

**Mount on the second host.** Install `nfs-common` on the second host, create the directories at the same absolute paths as on this host, change the owner of the parent directory to the same uid as on this host, write one line per root in `/etc/fstab`, then have systemd reload and mount:

```bash
# /etc/fstab, one line per root
<this host's address on the direct wired segment>:<root> <root> nfs4 rw,hard,nofail,_netdev,x-systemd.automount,x-systemd.mount-timeout=30 0 0
sudo mkdir -p <root>
sudo systemctl daemon-reload
ls <root>                     # entering it triggers the automount
```

**Recovering by itself after this host reboots.** The fstab line carries `x-systemd.automount` and not `x-systemd.idle-timeout`. `x-systemd.automount` makes systemd put an automount point (an `.automount` unit) on the root, which does not fail together with the NFS mount itself: while this host reboots and the export is gone the mount unit may become `failed`, and the next time a process enters the root systemd starts the mount again, so once this host's `nfs-server` is back it mounts again without anyone running `reset-failed` and `start`. Without `x-systemd.idle-timeout` the mount stays once mounted and is not dropped when idle. `hard` (the NFS default) makes processes reading and writing during this host's reboot wait instead of failing. The server's mount check does not use `mountpoint -q` (an idle automount point is only an autofs placeholder there and `mountpoint -q` still exits 0); it runs `stat -f -c %T -- <root>/.` on the second host, which enters the directory and so triggers the mount, and passes only when it reads `nfs`. Once mounted, `git -C <repository root> rev-parse HEAD` on the second host reads the same commit as on this host: that is the repository root working.

**uid.** The user's uid and gid must be the same on both hosts; if they differ, add `all_squash,anonuid=<the user's uid on this host>,anongid=<the user's gid on this host>` inside the parentheses of the export entry, so that files the second host writes land owned by this host's user.

**Which keys in the multi-host configuration.** In `multi-host.env` at the repository root write three keys. First, `NFS_SHARED_ROOTS=<absolute path>[:<absolute path>…]`, the roots exported and mounted above (the repository itself, i.e. the root of the main work tree; the shared data root `~/.local/share/singlefs`, which holds the work root; the session transcript directory `~/.claude/projects`; each written as this host's absolute path): separated by colons, at least one segment, each segment starting with `/`, not ending with `/`, and containing no whitespace; write it even when `ENABLE_ACROSS_MACHINES` is 0. The template is `multi-host.env.example`, and no extra configuration file is added. The multi-host configuration check `scripts/crash/crash-point-replay-shard-configuration-check.sh` checks the form and, on this host, also checks that each segment is an existing directory; one that does not fit exits 1 and names which segment. Second, `SHARED_DATA_ROOT=<absolute path>`: the shared data root (the work root is under it), this host's absolute path, inside one segment of `NFS_SHARED_ROOTS`; the server takes it through `.claude/hooks/lib_work_root.py` (or `SINGLEFS_DATA_ROOT` when that is set in its environment), and `control install`, `start` and `check` look only at this line: missing or outside the shared roots exits 78 with the way out naming this line to add to `multi-host.env`; no default is filled in. Third, `HOSTS=<this host's IP> <second host's IP>`: each host's address on the wired direct link, separated by spaces; which one is this host is told from this host's interface addresses (`ip -o addr show`), the second host is the other one, ssh connects to it directly, and the user name comes from each host's `~/.ssh/config`. The second host's address is taken only through the shared helper `scripts/hosts/multi_host_addresses.py`, which gives an address only after the whole multi-host configuration passes its check: a missing key, a key the check does not know, or a malformed line yields no address, so the server does not start and `control start` exits 78. Values that differ between the hosts go into the three per-host keys `CARGO_BIN_DIRECTORY_BY_HOST`, `BUILD_ROOT_BY_HOST` and `SLICE_MEMORY_CAP_BY_HOST`: the value is space-separated `<address>=<value>` entries, each split at its first `=`, with exactly one entry for every host in `HOSTS` and every address in `HOSTS`; whoever needs a host's value takes the entry for that host's address. The server reads `SLICE_MEMORY_CAP_BY_HOST` (pinned caps) and treats a missing host or an address not in `HOSTS` as a malformed configuration. Each shard gets, through `TASK_SERVER_SHARD_HOST`, the `HOSTS` address of the host it runs on.

**What the server checks when it starts.** Four items; if any one fails the server does not start, exits 78, names the item and points to "## NFS share":

- configuration: `NFS_SHARED_ROOTS` is present and each segment is a directory on this host; `HOSTS` tells this host and the second host apart (the next two items reach the second host through it);
- export: every segment has an export line in `/var/lib/nfs/etab` on this host;
- mount: `stat -f -c %T -- <root>/.` reads `nfs` for every segment on the second host (entering it triggers the automount); one ssh timeout to the second host counts as "slow" first and is rechecked once 5 seconds later: a recheck that answers only leaves a line 「第二台慢（超时、复查通了）」 in the service log, with no message and the second host still dispatched to, and only a failed recheck fails the item ("cannot reach the second host");
- read and write: a probe file is written in each direction and the other side can read it (written on this host and read on the second host, written on the second host and read on this host).

`task-server/control check` checks the four items afresh each time (it prints its own result and does not change the server's `/health`); the `nfs` field of `/health` reports the same four items, but its "read and write" item (the probe in both directions) is the result of the probe made when the server came up and is not redone afterwards; after the server is up it rechecks only the first three, every minute, and when one starts failing it sends a message straight to every session with a task queued or running (see "## Messages to the session").

**When one fails.**

- Configuration fails: add the key or fix its form as in "Which key in the multi-host configuration", and create the directory first if it does not exist.
- Export fails: add the missing line to `/etc/exports` and run `sudo exportfs -ra`; if the NFS server is not running, run `sudo systemctl enable --now nfs-server`.
- Mount fails: on the second host add or fix the `/etc/fstab` line as written above and run `sudo systemctl daemon-reload`; if the mount unit has become `failed`, run `sudo systemctl reset-failed "$(systemd-escape -p --suffix=mount <root>)"` and then `ls <root>` to trigger the mount; if it will not mount, first check that the direct wired segment is up and that the client address exported to on this host is the second host's.
- Read and write fails: most likely the uid and gid differ between the two hosts, or the export entry lacks `rw`; follow the "uid" paragraph.

**How to check.** Three things, each run on the host its comment names:

```bash
stat -f -c %T -- <root>/.                   # run on the second host: printing nfs means the root is mounted
cat /var/lib/nfs/etab                       # run on this host: every root has an export line, and the client is the second host
echo probe > <root>/nfs-check-by-hand       # run on this host: written on this host
cat <root>/nfs-check-by-hand                # run on the second host: the second host reads probe
echo probe > <root>/nfs-check-peer          # run on the second host: written on the second host
cat <root>/nfs-check-peer                   # run on this host: this host reads probe
rm <root>/nfs-check-by-hand <root>/nfs-check-peer   # delete both files when done
```

## How to submit

```bash
task-server/task submit -- <command…>              # prints the task number and the confirmation sheet; the task awaits confirmation and is not queued yet; whitelisted variables in the environment such as SINGLEFS_RUN_SCOPE are carried; refused on the spot when the session's inbox address cannot be read
task-server/task submit --whole-package-confirmed <confirmation file> -- <command…>  # a whole-package test with the file of three confirmations ("Whole-package tests need a confirmation flag" above); without it the submit is refused
task-server/task requeue <number> --long-run-confirmed --items <N> --tasks <M> --why '<…>'  # confirm a task bounced at two hours really needs that long: the original command re-enters at the queue tail flagged long run confirmed ("Two-hour bounce" above)
task-server/task confirm <number> --items <N> --tasks <M>  # confirm after checking the scope against the sheet: queued only when both numbers equal what the server counts right now (placed by submission time); a mismatch exits 3 and prints the server's sheet
task-server/task wait <number>                      # fetch the outcome: exits on completion, last line TASK_SERVER_RESULT …, the exit code is the task's; a task that carries the session's inbox address need not be waited on to wake you (see "## Messages to the session")
task-server/task status [<number>]                  # this session's tasks awaiting confirmation, queued, running, and finished-but-unclaimed; given a number, a task awaiting confirmation gets the sheet computed now; queued ones carry "waiting: …", running ones how long they have run and how long the log has not grown
task-server/task cancel <number>                    # only the submitting session; once the stop is read back, the same cancel removes this task's build directory and scene and prints how many it removed and their sizes before and after
task-server/task log <number>                       # the log of the last attempt (last 200 lines; --all the whole log; --attempt <which> that attempt; exits 4 if the task or attempt is absent)
task-server/task clean <number>                     # removes the build directory and the failure scene a finished task left (only the submitting session, only once it has an outcome; without SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1 the build directory is already gone at the outcome and the scene goes one hour after wait collects the outcome; multi-host-run.sh removes the second host's build directory of its run itself; a cancelled task does not need it)
```

Confirming a submission: a task accepted by `task submit` first awaits confirmation (`awaiting-confirmation`): it is not queued, no subtask is created and no attempt starts. Standard output then carries the confirmation sheet the server returns: the whole command, the four segments of `SINGLEFS_RUN_SCOPE` as written, the number of items N the server reads from the command (each `--item`, each cell of `--check`, each named `--test`, `--bin`, `--lib` and each test name after `--exact`; when none is named it says 「整包、不指定范围」), the number M of this session's tasks queued or running right now with the numbers of those that share the command key or name an overlapping item, the predicted memory, the expected duration and where they come from, and the anomalies already visible at submission (a budget above or close to a whole host, parallelism set by the given cap, each with its suggested change), ending with the line `TASK_SERVER confirm-needed task=<number> items=<N> tasks=<M> timeout=<seconds>`. Once the scope checks out, write `task-server/task confirm <number> --items <N> --tasks <M>`: the task is queued only when both numbers equal what the server counts right now, and it keeps the number it got at submission, which fixes its place; a mismatch exits 3 and prints the sheet as the server counts it now (the numbers change when another task of the same session starts or finishes in between). A sharded parent is confirmed once; its subtasks are created by the server and need no confirmation. A task not confirmed within 30 minutes is cancelled by the server (outcome `cancelled`, the note starting 「没确认，已取消」) and the outcome is sent to the session. Only the submitting session can confirm; subagents submit no tasks and confirm none.

Cancelled tasks leave nothing behind (the user: "取消的任务要自己删掉产物 不要残留", "这个加入流程中 让task server去做"): once `task cancel` reads back that the unit has stopped, the server removes, in the same cancel, the build directory and the scene directory of every attempt of this task (for a sharded or estimated task, its children's too), even with `SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1` set; for an attempt sent to the second host, the second host's local `builds/<label>/` and the process id, exit code and output files under `runs/` are removed by step ⑥ of `multi-host-run.sh`, which the server recognises from the line it writes into that attempt's log, "⑥ 删了第二台这一趟的本地目录 …（回读不在了）"; without that line, a cleanup receipt still at `not-started` and no line in the log that is only written after that run's local directory exists mean it was never created, which does not count as left behind; one left over from an earlier attempt is removed with `--remove-build-directory`. The sizes before and after are printed one by one in the output of `cancel` and written into the log of the task's last attempt (the copy on the second host's local disk cannot be measured from the server's side, and that is written as such); something counts as removed only once reading it back shows it gone, and anything not removed is named one by one and `cancel` exits 5.

Warning at submission (the user: "绕过的 那个要做成提醒 谁做错了严厉警告"): the task is accepted and runs as usual, and the server warns on the spot, in the submit reply (the client prints it to standard error), in the log header of every attempt of the task and in `status`. The first line is "✗ 严厉警告：会话 <number> 交的任务 <number> 绕过了服务给的编译目录，取仓根 target/ 下的二进制（…）…" (stern warning: the task submitted by session <number> bypasses the build directory the server gave and takes a binary under the repository root's target/), and the second line is "→ 怎么办：…". It judges: a word of the command that falls under the repository root's `target/`, or, in this repository's script that the command starts in command position, a path literal pointing at the repository root's `target/` (preceded by a repository-root variable, `$(dirname …)/../..` or `$(git rev-parse --show-toplevel)`, followed by `target/release/` or `target/debug/`; a bare one also counts when started at the repository root). The build directory the server gave, a `CARGO_TARGET_DIR` the caller gave, `target/` under scratch and temporary directories, comments, the break-switch branch and the selftest branch (started with `--selftest`, or a function body whose name contains selftest or ends with cells) do not count. The rule is in ② "提交时警告" ① of the header of `task_server.py`. The other kind (② in the same part): when the submitting session has tasks whose outcome has not reached it for 30 minutes (the server's message did not get through and no `wait` fetched it), the task is still accepted and run, and the same three places get two lines, first "✗ 严厉警告：会话 <id> 有 <N> 条任务跑完了没人取（<id>、…）：…", then "→ 怎么办：task-server/task wait <id> 取走（…）…"; tasks with no session (submitted by hand) are not judged.

`wait` itself reports eight situations that need handling (the user chose "task wait reports them itself" in the dialog): first, a task queued too long, after `QUEUE_ATTENTION_MINUTES` (30 minutes) in the queue; second, a task running `OVERRUN_ATTENTION_FACTOR` (3) times the recorded duration, which the server never stops while the log is still growing, so this is what calls a human; third, a card replacement, where quiesce found a card broken and the server requeued the task on another card (the final outcome may be `succeeded`); fourth, quiesce not finished (`cleanup-pending`), where the command has exited but the read-back still finds leftovers and the server keeps the resource booking; fifth, a sharded parent that cannot advance (`shard-advance-failed`); sixth, a log that has not grown for long while the server keeps the task running (`quiet-log-busy`), after `QUIET_ATTENTION_MINUTES` (30 minutes) without growth while the server keeps it running because the CPU rises or cannot be read, reported whether or not there is a recorded duration; a task kept running because it waits on IO or has a compute process on its card does not get this one, `io-wait` and `gpu-busy-quiet` report it; seventh, a task waiting on IO that the server keeps running (`io-wait`), when every poll while the log has not grown has found some process in state D for `IO_WAIT_ATTENTION_MINUTES` (30 minutes) in a row, with the latest count of processes in state D and this host's current some avg60 from `/proc/pressure/io` in the basis; eighth, a task with a compute process on its card that the server keeps running (`gpu-busy-quiet`), when the attempt was given a card and every poll while its log and CPU have not grown has found a compute process of this attempt on that card, with a nonzero or unreadable utilization in each window, for `GPU_BUSY_QUIET_ATTENTION_MINUTES` (30 minutes) in a row, with the card's key and its utilization in the basis (or that the utilization could not be read); a window in which the utilization reads 0 every time stops the task as stalled instead of reporting this. A ninth kind is reported only for a task that already has an outcome: a command that writes the main working tree (`apply-writer-patch.py`, `hook-swap.py`, `stage-mine.py`, `merge-and-verify.sh` without `--skip-apply`) that ended by hitting its cap, being squeezed out, running short of GPU memory, a failed second-host run, reaching the maximum, cancellation, being stopped as stalled, losing its launcher or being killed by a signal (`workspace-write-interrupted`) may have written only half, and `next=` names the files or patch directory to check (user: 「这个问题很严重 因为可能会导致补丁没有正常写入」); for `apply-writer-patch.py` with an outcome file `apply-outcome.tsv` the server judges by its `--read-outcome`, and a patch applied in full or rolled back is not reported, nor is one run with `--dry-run`. Three more kinds (twelve in all; user: 「既然加了给对应对话发消息的功能 就就该把异常和修改意见交给对应的对话」) only remind, the task keeps its place in the queue or keeps running, the basis gives the measured numbers and `next=` the suggested change: the tenth is a budget close to a whole host (`oversized-budget`), when the queue judges that the task's booking on some host is at least that host's whole-task line (85% of its usable cap) and no more than the usable cap, with each host's booking, usable cap and where the booking comes from (how many recorded peaks, the build family, a pinned cap) in the basis; a pinned cap is reported too, and the suggestion is to check the scope, the sharding and how many run at once; a task booked above the usable cap of every host it can be sent to does not wait in the queue forever: the queue sends it back as `memory-cap-at-maximum` the moment it judges it, without starting it; the eleventh is a long run with idle cores (`long-run-idle-cores`), when an attempt has run for an hour and its average number of cores in use so far is below a quarter of the threads it was given (task 8856 used 8.881 cores on average out of 31 threads), reported once per attempt, with the suggestion to check whether the script runs serially and whether too many items were named; the twelfth is parallelism set by the given cap (`fills-any-cap`), when the last three completed runs of the same command key each peaked at least at 90% of their caps (attempts that hit the cap do not count: the peak of such an attempt sits at the cap anyway, and climbing the caps one step at a time is not parallelism set by the cap), with the suggestion 「这条命令按给的上限开并行，核实」. How each kind (together with the submission refusals, the submission warnings, every outcome, a suspected stall and an unclaimed outcome) is judged, what action it takes, its suggested change and what happens when nobody handles it follow only its row in the anomaly table in the header of `task_server_lib.py`: the head of `next=` is that row's suggested change, naming what to check for that kind (for example `io-wait` checks that host's disk and NFS and `/proc/pressure/io`; `cleanup-pending` checks the command lines left behind and whether the script exits without waiting for its children), followed by this occurrence's numbers. The server records these for the task (and its subtasks, for a sharded one) as "needs handling" reminders. A `task wait <number>` that is waiting for the task prints one line `TASK_SERVER_ATTENTION task=<number> type=needs-attention kind=<kind> tier=<tier> basis=<the numbers it rests on> why=<reason> next=<way out>` on reading a new reminder, then exits 230: the task is still queued or running and the server did not touch it; handle it as `next=` says and start `wait` again to keep waiting. For a task that already has an outcome (a card replacement that succeeded) the line is printed before `TASK_SERVER_REASON` and the exit code stays the task's. The same reminder of the same kind for the same task at the same tier wakes the caller only once, so restarting `wait` does not repeat it; it fires again only when the tier crosses the next step (twice, four times the threshold, and so on). The tiers already reported are stored in the server's database, so after a restart the server reads them back and does not report the same tier again; a task queued too long whose waiting reason has not been judged yet (the server has just restarted and this round has not reached it) is not reported in that round, only in the round that judges the reason. The server also sends these reminders straight to the submitting session (see "## Messages to the session"), keeping one account with `wait`: what was sent is not reported by `wait` again, and what `wait` reported is not sent. Server health is not `wait`'s business: the server watches itself and sends messages the same way.

Do not wrap commands or pass resource arguments: `run-with-memory-cap.sh <cap>`, `host-dispatch.py … --`, `multi-host-run.sh … --`, `nice`, `timeout`, `capped.sh`, `two-logs.sh`, `gpu-quiesce-run.sh` and the scripts' own `--memory`, `--memory-cap`, `--threads`, `--peer`, `--local-only`, `SINGLEFS_THREAD_CAP`: the server does these, and writing them is refused on the spot, naming which one to remove. Environment variables outside the whitelist are refused on the spot and named; a command that really needs one is written as `task-server/task submit -- env <name>=<value> <command…>`. Retired variables (`SINGLEFS_HEAVY_TESTS`, `GATE_MUTATION_START_OVER`) are refused on the spot whether set in the environment or written in the command (a `name=value` after `env` or in front of the command); the refusal names it and gives the way out; the list is `RETIRED_VARIABLES` in `task_server_lib.py`.

Three kinds that could not be sent to the second host are refused at submission (user: 「改成提交时当场拒（推荐）：不再悄悄改派本机：碰到这三种就在提交时报错、点名是哪个路径或哪一族、出路写怎么改，任务不跑。」): `task submit` exits 3 and prints the sentence and the way out; the task is not queued and does not run. First, an absolute path in the working directory or the command (only whole shell words count: a word that starts with `/`, the value of `name=absolute path` or `--option=absolute path`, and each shell word of a `bash -c` script once the script is split into shell words; a `/` in the middle of any other word, such as 「（接的是 /）」 inside an argument value, does not count) that lies under no segment of the multi-host configuration's `NFS_SHARED_ROOTS`: the sentence names that path and the way out is to move it under one of the segments; system paths that are the same on both hosts such as `/dev/null`, `/usr/` and `/bin/` do not count; a path under `/tmp` is refused the same way, and the sentence adds that a reboot clears `/tmp`. Second, a `SINGLEFS_DATA_ROOT` or `SINGLEFS_WORK_ROOT` handed to the command that is not under a shared root: the sentence names the variable and its value, and the way out is to set up the multi-host configuration. Third, a command that points at a row with a verdict library in the registry `.claude/gate.d/verdict-library-scripts.tsv` whose third column does not yet say `prune-server`: the sentence names that family, and the way out is to move that family onto prune-server and turn the third column into `prune-server`; a registry that cannot be read or is malformed is refused the same way.

The temporary prune-server wrapper (`python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <path>] -- <original command>`) is only for script self-tests (user: 「旧脚本不兼容 我再说一次 如果错了让 对方重新提交」): when the original command unwrapped from it contains a cargo that compiles, or needs a card (recognized the same way the service decides the build directory and the card), it is refused at submission in the same form as above: `task submit` exits 3 and prints the sentence (naming whether it compiles or needs a card) and the way out (submit again without the wrapper); the task is not queued and does not run. Unwrapping is only for judging; an accepted command still runs whole, wrapper included; the build directory, the card and the GPU quiesce are given only for the outer command, and the service does not unwrap to accommodate it. A wrapper without `--server-binary` (and without `PRUNE_SERVER_BINARY` in the assignments before the command or in the task environment) has to compile prune-server itself in the build directory the service gives, so the service counts the outer command as one that compiles: both hosts are given a build directory; with `--server-binary` nothing is compiled and none is given. The `cargo test` of the verification crate runs against the real service and is not wrapped this way.

A whole-workspace build that names no package is refused at submission (user: 「8105打回 让他重新写重新确认范围」; task 8105, `cargo build --offline --all-targets` without `-p`, was predicted at 49.0 GiB and the second host sealed its group and drained for it): a compiling cargo started directly at command position in the submitted command (`build`, `check`, `clippy`, `test`, `run`, `bench`, `doc` and their one-letter aliases; `bash -c` and `cd` are followed) is refused when it carries `--workspace` / `--all`; one without `-p` / `--package` is refused when cargo's manifest lookup (the first `Cargo.toml` from the starting directory upward) lands on a virtual manifest (only `[workspace]`, no `[package]`, as the repository root's is), and equally when the starting directory cannot be told or the manifest cannot be read. `task submit` exits 3 and prints the sentence (which cargo, started in which directory, under which manifest) and the way out: name the package to build, `-p <package>` (the verification crate is `-p singlefs-verification`); whole-repository runs go through `scripts/gate/merge-and-verify.sh` or the gate at commit time. One that lands on a package's own manifest (packages that are their own workspace such as `scripts/experiment-apparatus/` and `prune-server/`, or started inside a member's directory) builds only that package and is accepted; cargo started inside entry scripts and gates is not judged (the service only looks at the submitted command); `cargo fmt`, `metadata`, `tree` and `clean` do not compile and are not judged.

## Messages to the session

The user: 「不是你通知 而是 task-server 通知发起的对话」「包括报错 长时间没有响应 都可以这样通知」. `task submit` runs in the session's Bash, reads `CLAUDE_CODE_MESSAGING_SOCKET` (the session's inbox socket) and `CLAUDE_CODE_MESSAGING_TOKEN` (the session token) from the environment and hands them to the server with the task; the server keeps them on the task, and the token goes into no log, no `status` and no reply of `/tasks/<id>`. When they cannot be read the submission is refused on the spot (exit 3), and the way out is to submit from the Bash of a Claude Code session (subagents submit no tasks). The inbox socket is not the one recorded at submission: before each message the server reads the session registry (`~/.claude/sessions/*.json`, one file per process, reading only `sessionId`, `messagingSocketPath` and `pid`) by the session id recorded on the task and takes the `messagingSocketPath` of the latest-started file whose session id matches and whose process is still alive; the token is the one given at submission. A session restarted with a new socket gets the message on the new one; when none is found (the session is closed) the server writes the alert described under "cannot be sent" below.

The server sends one message to that socket on each of these:

- The task has an outcome (every kind for which `wait` prints `TASK_SERVER_RESULT`): sent once; once it is sent the server records it as collected (as if `wait` had fetched it), and nothing is sent when the session already fetched it with `wait`.
- A reminder that needs handling (the twelve kinds under "## How to submit") or a suspected stall: the same kind of reminder for the same task at the same tier is sent once, on the same account as `wait`. The kinds judged by time go up one tier and are sent again each time the time doubles; the kinds whose tier does not grow with time (`oversized-budget`, `fills-any-cap`, `long-run-idle-cores`, `cleanup-pending`, `card-replaced`, `shard-advance-failed`) are sent once more when they are still there 30 minutes after their tier was sent, and again each time that doubles; the first line says 「没处置、第 <回> 回再推」 and the body adds what was sent before and what is still missing now.
- An unclaimed outcome: when the outcome of a parent task has not reached the submitting session after 30 minutes (the message with the outcome did not arrive and no `wait` was started), it is sent again, and again each time that doubles, with the first line 「task-server：任务 <号> 结局还没人取（…）」; once sent it is recorded as collected.
- A task not confirmed within 30 minutes and cancelled by the server: sent as its outcome, with 「没确认，已取消」 in the body.
- Server health: the database cannot be written, the dispatcher judged the head startable but kept failing to start it, the progress watch found room but nothing started, the server's unit is down, the first three NFS items fail, the second host has been unusable for 180 seconds. It goes to every session with a task queued or running; the same thing goes to the same session once, and again only after it got well and broke again. When the server itself is down it cannot send: `task wait` exits with an error after 60 seconds without a connection, and `task submit` reports on the spot.

The first line of the body is "task-server：任务 <id> <outcome or reminder kind>…" or "task-server：服务健康 <which one>"; after it come the reason, the way out and the log as `wait` prints them, and last the line `wait` prints, verbatim: facts and ways out only. If it cannot be sent (the socket is gone, the connection fails, the session is closed) the server does not retry forever: it writes one `inbox-unreachable` alert into its log and the alert records, appends a line starting with `TASK_SERVER_INBOX` to the log of the task's latest attempt, and the task goes on. When the receiving session is idle Claude Code starts a new turn with the message; a session that skips permission prompts holds it until the user approves.

`task wait` stays: it still fetches outcomes and reminders, but a session no longer needs to start it to be woken. `task-server/control watch` is gone (it exits 2 with the way out); to check server health once by hand use `control check`.

Line format: first the line `{"type":"auth","token":"<session token>"}`, then the line `{"type":"user","message":{"role":"user","content":"<body>"}}`; both are ready before connecting and written in one go (Claude Code closes a connection that has not sent a complete line within 30 seconds). Source: the inbox socket and the auth line are in the Claude Code docs, https://code.claude.com/docs/en/cross-session-messaging.md, section "The session's inbox socket"; the docs page does not give the user line, which is taken from the example in the line "[uds-messaging] Inject messages" of the Claude Code binary's own debug log. Since the docs page does not give the line format, recheck it after upgrading Claude Code.

## Declarations in source headers

The server reads a few declaration lines in the first 60 lines of a source file to tell what a command needs; callers still write no card and no budget. The session that owns the entry script or the package adds the declaration; the server only reads it:

| Where | How it is written | What the server does with it |
|---|---|---|
| entry script | `# task-server-gpu-arguments: <argument>…` (`*` is any argument) | needs a card, and the server wraps the GPU quiesce, when the first non-option argument is one of them |
| entry script | `# task-server-gpu-cards: <count>` | when it needs cards, it needs this many on the same host (see "How many cards" below) |
| `.rs` source (the source of the same name as a compiled binary; the sources of the packages a `cargo test` / `run` / `bench` names with `-p`) | `// task-server-gpu-cards: <count>` | same as above |
| entry script | `# task-server-cargo-family: <cargo arguments>…` (for example `-p singlefs-verification --release --features gpu`) | which package, profile and features the cargo it starts builds: when the command has no record under its own key, the server starts from the recent build-phase peaks of the same build family (see "Starting peaks" below) |
| entry script | `# task-server-cargo-family: -p $3`, `# task-server-cargo-family: -p $--crate --release` | when the package to build comes from the command's arguments: `$<n>` is the n-th word after the script (counted from 1; an option and its value count as one word each), `$<option name>` is that option's value (`--crate value` and `--crate=value` are both read, nothing after `--`); at submission the server fills these in from the command and then puts it in a family, and a command where one of them cannot be filled (no such word, an empty value or one starting with `-`) gets no family and starts at 4G. Example: `scripts/mutation/prove-red.sh --copy <copy> <crate> <mutation names…>` declares `-p $3`, so runs with different mutation names fall into the same family by `<crate>` |
| entry script | `# task-server-shards: <argument>…`, `# task-server-resumable: <argument>…` | sharding and resuming (the "分片" and "续跑" parts of the `task_server_lib.py` header) |

How many cards: the real-card test the user set is 「你需要测试的是 一张卡1gb 2张卡 三张卡 每张卡都能用来分片gc。没有卡报错。 有卡但是失败 报错加cpu兜底」. For a declared count, the server goes through the cards in the multi-host configuration's priority order, picks the first host whose free cards add up to that many and which also has room in memory, and gives the first that many free cards of that host to the task as one group: `GPU_CARDS_BY_PRIORITY` carries those entries joined by spaces, the quiesce covers the whole group, and all of them count as taken while it runs. When no host among the cards the multi-host configuration names has that many, the outcome is `never-fits` (exit 241); a count that is not a positive integer gives `run-condition-unmet`, and the note names which file wrote what. Which `.rs` sources are read: with `--test <name>`, `tests/<name>.rs`; with only `--lib`, `src/lib.rs`; otherwise `src/lib.rs`, `src/main.rs` and the files under `src/bin/` and `tests/`; when several declare a count the largest wins, and none means one card. Example: with `// task-server-gpu-cards: 3` in the first lines of `crates/singlefs-background-gpu/tests/<target>.rs`, `cargo test --release -p singlefs-background-gpu --features tests-on-a-real-gpu --tests` is given three cards on the same host.

Starting peaks (from the attempt records in the server's own database, the "资源记录" part of the `task_server_lib.py` header):
- Build family: a cargo that compiles is put in a family by its packages, profile (`--release`) and features; an entry script that declares `task-server-cargo-family` is put in the family it declares. When the command has not completed once under its own key, and at every requeue after hitting the cap, it starts from the largest build-phase peak of the last 5 attempts of the same family (other command keys count too) × 1.5, used only when that is above the cap it would otherwise get (the same window as the sibling shards and as starting at the highest of the recent runs). The build-phase peak is the largest process memory (`anon` plus `shmem`) sampled before the line in which cargo prints 「Finished … target(s) in …」: on this host `attempt_runner.py` samples it, on the second host `multi-host-run.sh` takes it from its per-poll readings and prints a line `MULTI_HOST_RUN_PEER_BUILD_PHASE_PEAK bytes=<bytes>`, the same measure on both hosts; without that line (the build failed, or it is not cargo) the field is empty and nothing is lent. The peak of the whole run and the cap of an attempt that hit it serve only the same command key: the commands of a family build the same thing but need different memory when running their tests, and lending the whole run would book a single test target at the largest command of the family (task 9279, one `--exact` with a peak of 9.47 GiB alone, borrowed 42.20 GiB from a whole GPU-comparison target of the same family). When the later builds are all small, the large one leaves the window and the start comes down; a command with records of its own follows them.
- Peaks shared within one plan: the first attempt of a shard takes the peak of the plan step and of its sibling shards' ended attempts, the 5 most recent by end time (for one that hit its cap, that attempt's cap) × 1.5, and only ever raises, never pushing below 4G.
- Starting at the highest of the recent runs: the first attempt of a new submission and every requeue after hitting the cap are raised to the highest of the last 5 the server has on record for this key (caps it hit and peaks of runs that completed) × 1.5, and a requeue also looks at the build family and the sibling shards (also only the last 5); it goes both up and down: a cap just hit inside the window is seen at once, an older one that left the window no longer counts, and when the later runs are all small the start comes down with them. A command with no record at all still starts at 4G, and one with real peak records is not raised to the 4G floor.
- On a requeue after hitting the cap, the previous attempt's build directory is kept, and a requeued attempt that is still on the same host keeps using it (inferred: cargo reuses the crates it has already built by fingerprint; how much this saves has not been measured); when the requeue moves to the other host, the previous one is removed as that attempt starts. Both hosts go through the same logic: on this host through `CARGO_TARGET_DIR`; an attempt on the second host carries `--keep-build-directory`, `multi-host-run.sh` keeps `builds/<label>/` after the run, the requeued attempt carries `--reuse-build-directory <previous label>` to keep using it, and the server removes it with `multi-host-run.sh --remove-build-directory <label>` when the task moves host or has an outcome.

## Pause and resume

Jobs such as swapping the prune-server binary or clearing old rows in the verdict library need a window in which no other session's task is running, and the job itself often has to submit commands through `task submit`. `control stop` cannot give that: while the server is stopped nobody can submit, and a `task wait` that is already running exits 78 after 60 seconds. Use pause instead, and let the session that does the job through (its tasks still start while paused):

```bash
python3 task-server/control pause --reason "clear old verdict rows" --allow-session <the session doing the job>   # pause: other sessions' tasks do not start; the allowed session's tasks are queued and started as usual; submissions are still accepted, status / wait / log / cancel still answer
python3 task-server/control check                                                                                   # repeat until it prints "…、放行会话 <id>、在跑 N 个、别的会话在跑 0 个" (… allowed session <id>, N running, 0 running in other sessions)
# ...do the job that needs the window (the session doing the job submits its commands with task submit)...
python3 task-server/control resume                                                                                  # release: queued tasks start as usual, the allowance is cleared with it
```

- The id of the session doing the job: run `python3 task-server/task status` in that session and take the id from the first line, "会话 <id>：…" (it is the session the server recorded when the task was submitted, the same field `status` shows for every task). What is allowed is a session, not one command: tasks of that session that were already queued, submitted later, children of sharded tasks, estimate children and retries that went back to the queue all start as usual; tasks of other sessions, and hand-submitted tasks that have no session, stay queued and unstarted. A queued task of the allowed session shows what it is really waiting for in `status`; a queued task of another session shows "在等：服务暂停中（原因：…）".
- `pause --allow-session <another session>` on an already paused server exits 0 and switches the allowed session (reason and start time unchanged); a `pause` without `--allow-session` leaves the allowance alone; `resume` clears the allowance with the pause. For a window in which no task at all is running: `pause` without `--allow-session` and wait until `control check` reports 0 running.
- While paused the scheduler starts no new attempt (except for the allowed session's): backfill, children of sharded tasks, estimate children and retries that went back to the queue are all held. Running attempts run to their outcome (the outcome is still written and a retry still goes back to the queue, but is not started). `pause` and attempt start share one lock, so when `pause` exits 0 an attempt that was being started is already recorded and the running count of `control check` cannot be joined by another.
- The paused state, with the allowed session, is stored in the server's database (signed: a changed allowed session in the database counts as failing verification and allows nobody) and survives a server restart, allowance included, until `resume`; `pause` on an already paused server exits 0 and keeps the original reason and start time.
- `control check` prints one more line, "暂停中（原因：…，起于…）、在跑 N 个"; with a session allowed it reads "…、放行会话 <id>、在跑 N 个、别的会话在跑 M 个" (M is the running tasks that are not the allowed session's); it still exits 0 without judging "the dispatcher judged the head startable but did not start it" or watching progress; `/health` carries `paused` and `pause` (with `allow_session` and `other_running`) and `ok` is unchanged; a queued task's `status` shows "在等：服务暂停中（原因：…）".
- While paused the server keeps watching its own health (the database is writable, the unit is up, NFS, the second host) and still sends a message to every session with a task queued or running when something goes wrong.
- Only the user who runs the server may send `pause` and `resume`, checked like submit and cancel: the server compares the caller's uid with its own.
- Always `resume` when the job is done; a paused server looks healthy (`check` exits 0), so queued tasks would wait forever if you forget.

## Self-test

`python3 task-server/task_server_lib.py --selftest`: each cell runs a real uvicorn on a temporary socket, with the memory wrapper, the second host, quiesce and the systemctl used by `control` replaced by fake scripts and the attempt's scope by a fake directory; it does not compile, does not connect to the second host and does not use cards. It runs entirely in a simulated world, so the main agent starts it directly without queueing through the server (the hook list `MAIN_AGENT_TOOLS_RUN_DIRECTLY` in `.claude/hooks/lib_project_code_runs.py`); `TASK_SERVER_SELFTEST_CELLS=<cell,…>` runs only the named cells. The cells run in parallel as many at a time as the registered default of heavy-work threads per host (`scripts/hosts/heavy_threads.py`, read at the time); when that cannot be read (the registration file is missing or broken, or `SINGLEFS_THREAD_CAP` is not a positive integer) the whole run fails and does not fall back to the core count. The table of breakage switches `TASK_SERVER_BREAK=<item>` is in the `task_server_lib.py` file header.
