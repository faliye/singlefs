# task-server

[中文](README.md) · **English** · [日本語](README.ja.md)

For resources still held after an abnormal exit, remote cleanup receipts and diagnostic logs, see [Task cleanup and GPU phase logs](cleanup-protocol.md).

The unified task server of singlefs: every task that runs project code (light, heavy, CPU, GPU) is started through it, in one queue, in arrival order, with no extra delay. Tasks are submitted only by the main agent (with the client `task-server/task`, which people use too); sub-agents only use `status` and `log` to read outcomes; picking the host, setting the memory budget, deciding whether a GPU is needed and which card to use are all decided by the server, and submission does not accept any of these.

The server is the only process that reads and writes the database: FastAPI on uvicorn, running as the user-level systemd service `singlefs-task-server.service`, listening only on a unix socket (`${XDG_RUNTIME_DIR}/singlefs-task-server/server.sock`, directory 700; the full path is at most 107 bytes, and beyond that the server, the client and `control` all exit 78, naming the path, its byte count and the limit), never on TCP. The database is embedded SQLite (WAL) under `~/.local/state/singlefs/task-server/`, and every row carries an HMAC check column. Memory acceptance is judged in one place only, the server: a task starts only when it fits, and one that does not fit stays queued in the database; a started task is still wrapped in `scripts/hosts/run-with-memory-cap.sh` (this host, with the "accepted by task-server" switch set, doing only the kernel-level backstop of the per-task cap and the slice total cap) or `scripts/hosts/multi-host-run.sh --peer` (second host).

| File | What it does |
|---|---|
| `task` | Client: `submit [--cwd <directory>] -- <command…>`, `wait <number>`, `status [<number>] [--json]`, `cancel <number>`, `log <number>`, `clean <number>`; usage and exit codes are in the file header |
| `control` | Install and check: `install [--dry-run]`, `check` (the server's `/health` reports only three things: the database cannot be written; the dispatcher judged the head of the queue startable yet failed to start it for three rounds in a row, while heads it judged not startable — waiting for a card, for the load, for an alternation group — are not reported; the progress watch: a host fits the smallest queued task by the formula yet started nothing for 10 minutes, which catches the dispatcher judging wrong), `start`, `stop`, `watch`, `clear-queue` (with the server stopped, empties the task and attempt tables in the database after backing it up; resource records are kept), `pin-cap <command…>` / `unpin-cap <command…>` (through the server, pins or unpins a command's memory cap; exits 0 only after reading it back), `pause [--reason <one sentence>] [--allow-session <session id>]` / `resume` (pause and release the queue: while paused the server still accepts submissions but starts nothing new, except tasks of the allowed session, see "## Pause and resume") |
| `task_server.py` | The server (`serve`): API, queueing, acceptance, starting units, reconciliation, retries, sharding, resource records; the rules are in the file header |
| `attempt_runner.py` | Starts the command inside each attempt's unit and records the exit code and resources (the memory peak is the larger of what the periodic sampling saw and what the memory wrapper read on exit); the service removes the build directory once the task has an outcome |
| `task_server_lib.py` | The shared part: paths, dependencies, the error-type and exit-code table, retries, resource records, build directories, sharding, the environment-variable list, identity; the whole self-test `--selftest` and the breakage switch table are in its file header |
| `task_server_selftest.py` | The self-test cells (started by the previous row) |
| `singlefs-task-server.service.in` | User-level unit template |

There is no configuration file of its own: scheduling resources are read from the multi-host configuration `multi-host.env` at the repository root (template `multi-host.env.example`); the socket, database, logs, signing key and build directories use the fixed defaults written in the "paths" section of the `task_server_lib.py` file header. Required: fastapi, uvicorn, `multi-host.env` (with `NFS_SHARED_ROOTS`, `SHARED_DATA_ROOT` and `HOSTS` in it, written as in "Which keys in the multi-host configuration" under "## NFS share"), the NFS share set up (see "## NFS share"), and a reachable server.

Hosts are picked by balancing free room: a task that needs no card picks, among the hosts it can be sent to, one where it fits; when more than one fits, it picks the one whose remaining room after placing it is the larger share of that host's total cap, and this host on a tie; a retry after hitting the cap is not pinned to a host. Shards go to the second host first as the plan says, and are not moved by balancing as long as they fit there; the plan, the shards and the merge are not pinned to a host, and a plan that writes `pin` makes the whole task `shard-plan-refused` (shards are not pinned; the server picks the host). The second host runs in the same shared tree: the repository, the shared data root holding the work root `~/.local/share/singlefs/work/`, and the session transcript directory are mounted on both hosts at the same absolute paths over NFS (`NFS_SHARED_ROOTS` in the multi-host configuration, see "NFS share" below), so a run sent to the second host is started directly by `scripts/hosts/multi-host-run.sh --peer` in the task's working directory at the same absolute path, with no tree copied, nothing sent or fetched back and no path rewritten, and the files it writes are readable on both hosts; the build directory is created afresh for that run by `multi-host-run.sh` on the second host's local disk (`builds/<label>/target` under the second host's entry in the multi-host configuration's `BUILD_ROOT_BY_HOST`, under no shared root) and deleted when the command ends or is stopped (for a command that compiles it is kept for the requeue after hitting the cap, see "Starting peaks" below); the server does not set it and only records where it is (shown by `task status`); `task clean` does not touch it. Whether a task goes to the second host depends only on whether the second host is usable right now and on free room; the three kinds that could not be sent there are refused at submission ("## How to submit" below). There is no list of commands kept to one host (the user: "I say it once more: [runs only on this host] is not acceptable. Fix it as soon as possible and let the errors show"): a command naming any directory or entry can be sent to either host, and free room decides which; one that goes red on the second host stays red and is fixed in the script, the server does not shield it. Tools that change the main work tree (`hook-swap.py`, `apply-writer-patch.py`, `stage-mine.py`, those under `scripts/kb/`, `merge-and-verify` without `--skip-apply`) and commands with `--write` can be sent to the second host (they change the same tree); outcomes that would otherwise be retried, such as hitting the cap, are still not retried for them but handed back to the session that submitted them. The plan directory and each shard's artifact directory of a sharded task live under `task-server-shards/` in the shared work root, read and written by both hosts at the same absolute paths. The server does not check the merge lock: while the main work tree is being merged, tasks are queued and started as usual. At most 4 tasks start on the second host in one pass (starting too many at once gets ssh connections reset), and once that is reached another pass runs 2 seconds later; the outcome of a run on the second host follows the end line that `multi-host-run.sh` writes into the log for that command (`MULTI_HOST_RUN_STEP step=peer-command event=end … exit=<code>`): with that line the outcome follows the command's own exit code, and a command that itself exits 255 is recorded as `command-failed` and not requeued; only an exit of 255 without that line means the second host failed to run it (unreachable, ssh reset), recorded as `peer-run-failed` and requeued unchanged, at most 2 times. When the head of the queue does not fit, tasks behind it that do fit start first (cutting in); tasks younger than two hours alternate per host between whole tasks and fragment groups: the line is 85% of the host's usable cap (its total cap minus that host's margin right now), a task booked at or above it is a whole task and the rest are fragments; fragments fill one group in queue order, and when the next one would take the group past the line while a whole task waits, the group is sealed and takes no more fragments, the whole task starts as soon as it fits (it does not wait for the host to empty), and after it the next fragment group follows; waiting reasons from the alternation contain "在等这台腾空" (waiting for this host to free up). A whole task waits for one host only and seals only that host: it keeps waiting on the host already sealed for it in an earlier pass, otherwise on the host closest to fitting it right now (its booking minus what that host has left by "configured total cap − margin − sum of the caps of running attempts" is smallest); the other host keeps starting fragments. A whole task that needs cards counts only hosts with enough free cards for it, so a host whose cards are taken is not sealed for it. `/health` judges whether the head fits by the same check as placement (memory, build-directory disk, the CPU gate, the number of cards). Gap filling while a group is sealed: a fragment that would still fit on that host after the head whole task starts, by "configured total cap − margin − sum of the caps of running attempts", starts without looking at durations; one that would take part of what the head needs starts only if its estimated duration is no longer than the longest remaining time among the attempts running on that host (the blocking time), and one with no estimated duration stays sealed. Estimated duration: for `scripts/crash/crash-point-replay.sh`, `.claude/gate.d/formal-verification.sh` and `.claude/gate.d/crates-mutation-replay.sh` given `--item` and not sharded, the service first runs an estimate child task (the same entry with `--list-items --with-keys`, reading one line per item, `ITEM_PLAN item=<item> to_judge=<entries to judge afresh> reusable=<entries to reuse>`), and the task joins the queue only once that child has an outcome; after every run the service reads one line per item from the log, `ITEM_DONE item=<item> seconds=<seconds> judged=<entries judged> reused=<entries reused> exit=<code>`, and records per item "seconds per entry judged afresh" and "seconds per entry reused" (in the service's own database, not in prune-server); the estimated duration is the sum over the items of counts times rates, and there is none if any item lacks a rate; a task whose estimate failed queues with no estimated duration. For other commands the estimated duration is the duration of the latest successful run under the same command key (the key memory records use: paths and items folded word by word, `--check` cell names kept); the plan, shard and merge steps of a sharded task work the same way (each step takes the latest successful run of its own command key, each shard one per shard number; the plan step does not give the items of each shard, so an estimate per item is not possible for a shard). After the estimated duration, `task status <id>` says whether the figure came from the command, from the items, or that there is no record. A task submitted two hours ago or more moves to the front, is judged first and is not subject to the alternation; when it does not fit, it neither holds back the tasks behind it nor keeps a share, and the tasks behind it that fit start in queue order. Queued tasks never hold room. GPU tasks pick cards in the order given in the multi-host configuration (the rule is in the "GPU" section of the `task_server.py` file header); a card's host label is that host's address in the multi-host configuration's `HOSTS`, each entry `<address>:<card index>:<quota>` (for example `192.0.2.1:0:32G`; the address may be IPv6, so the entry is split at the last two colons), a label that is not in `HOSTS` is a broken configuration, the server finds its own host through `HOSTS`, and the command gets the entry unchanged in `GPU_CARDS_BY_PRIORITY`; a cargo run with a card feature (`gpu`, `tests-on-a-real-gpu`, also as `<package>/<name>`, and `--all-features`) needs a card only when it is `test`, `run` or `bench`, which run the compiled code, without `--no-run`; `clippy`, `check`, `build`, `doc` and `--no-run` only compile, and need no card and no quiescing. A script that needs a card only for some arguments declares them in its first 60 lines with a line `# task-server-gpu-arguments: <word> [<word>…]`: started by bash or python3, it needs a card when its first non-option argument is one of those words (`*` means any argument); the form is in the `task_server_lib.py` header, section "GPU". Both hosts go through the same logic (booking, fitting, stall and CPU, peaks, caps, build directories, host picking and free disk, with the same 50G disk floor on both); what differs per host is only how it is reached, measured and started (`Machine` in `task_server.py`). When an attempt ends normally and grandchild processes of the command are still in its unit, the server stops them and says so in the outcome note; when a run of more than 30 minutes fails and the script does not declare that it can resume with `# task-server-resumable: <word>…` in its header, the outcome note says "ran N minutes, not resumable: a resubmission starts from scratch" (in Chinese).

Each attempt's command is wrapped in `scripts/hosts/capped.sh <default heavy threads per host>`, and the thread count is always that number and is not accepted at submission; a task that needs a card is always wrapped once more, outermost, in `scripts/crash/gpu-quiesce-run.sh --`. The memory wrapper, `capped.sh`, the quiesce wrapper and `multi-host-run.sh --peer` accept only the layer the server wraps directly: the server sets an admission mark for each layer (its value is `<task number>.<attempt number>`), that layer reads it and does not pass it to the command, and a script inside the task that wraps one more layer is refused on the spot; the way out is to delete that layer and read the memory, threads and card from `TASK_SERVER_MEMORY_CAP_BYTES`, `SINGLEFS_THREAD_CAP` and `GPU_CARDS_BY_PRIORITY` that the server passes; a cargo run that compiles also gets its own `CARGO_TARGET_DIR` outside the repository, which is kept after the run, the last line of `wait` carries `build=<directory>`, and the submitting session removes it with `task clean <number>`. The budget follows only the server's own attempt records (the largest peak of the last few successful runs × 1.5; the memory wrapper's peak table is not read; the command key first drops an `env` prefix of variables that do not change how the command runs, such as the multi-host configuration path and `LANG`); a command with no record starts at 4G (one that has only failed starts no lower than the peak of that failed run × 1.5), and every task's cap and booking are at least 4G (a smaller cap worked out from the record is raised to 4G; a pinned cap is left as it is) and is requeued × 1.5 after hitting the cap; when × 1.5 would reach that host's total cap it is not requeued: it moves to another host with a larger total cap if there is one, and otherwise is recorded as `memory-cap-at-maximum` and returned to the submitting session; the room left on a host counts only memory used by processes (`anon` plus `shmem`), not the page cache or kernel memory charged to the slice; nothing is judged during a 10-minute grace after start; after that, a task whose log has not grown for 10 minutes and whose CPU has also barely risen in that time (on average under 1% of one core) is stopped by the server and recorded as `stalled`, and unreadable CPU does not count as not rising; a task that has run past 5 times its recorded duration and whose log has not grown for 10 minutes is stopped and recorded as `stalled` without looking at the CPU (an endless loop is stopped too), and a task with no recorded duration is not judged by this rule; `stalled` is not retried and is returned to the submitting session; a task whose memory peak had reached 98% of its cap at the moment it was judged stuck is stuck at the cap: it is stopped the same way but recorded as `memory-cap-hit` and requeued × 1.5 (a pinned cap is returned as `memory-cap-at-maximum`), with the note "顶在上限上卡住" (stuck at the cap); how long it has run, the recorded duration and the cores in use are written only into `task status`. The memory peak of the second host's layer is recorded into that attempt from the `MULTI_HOST_RUN_PEER_MEMORY_PEAK bytes=<bytes>` line that `multi-host-run.sh` writes, and feeds the budget the same way as on this host; a run without that line is recorded as not measured. The disk taken by the build directory is also recorded per command as a peak (on this host by measuring the build directory the server gave, on the second host from `MULTI_HOST_RUN_PEER_BUILD_PEAK bytes=<bytes>`); before a task is sent to a host, that host's free disk minus what running attempts' build directories will still grow must hold this command's build-directory peak plus a 50G floor, otherwise the task stays queued and its waiting reason names "编译目录占盘" (build-directory disk). A command that itself exits 75 (prune-server unavailable) is recorded as `prune-server-unavailable`, `wait` exits 75 and it is not requeued; the server runs `python3 prune-server/control check` once and writes an alert when it fails, without starting or stopping prune-server. A command written as `python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <path>] -- <original command>` has its command key and its registry row taken from the original command after `--` (the `--server-binary` path is not part of the key), and the key is prefixed with `〈task-server 临时 prune-server〉`: the same scope runs one more prune-server, so it does not share a record with the unwrapped command; the wrapper itself still runs as written.

Admission books the cap: running attempts and new ones are booked at their cap (clamped to that host's total cap minus that host's margin right now), so the caps of the tasks running on a host never add up to more than that host's slice total minus that host's margin right now; the part not yet grown into is counted as "cap − the memory it cannot reclaim right now"; both hosts go through the same code: the usage is measured per attempt's scope by the same read of that host's margin (the same ssh for the second host; a scope is matched to its attempt by `TASK_SERVER_ATTEMPT_LABEL` in the environment of its processes, set on both hosts), an attempt whose scope is missing from that report is booked at its whole cap, not 0, and the memory wrapper on the second host keeps no booking of its own. The margin is the memory in that host's `singlefs-heavy.slice` right now that cannot be reclaimed and belongs to no running task (charged to the slice itself and found in no child cgroup; how it is measured is in the header of `scripts/hosts/memory_peaks_lib.py`, "余量"); every read of the two hosts' free room measures it on each host separately and rounds it up to a whole GiB (1.01G and 1.1G count as 2G, 2.1G as 3G, 0.7G as 1G, an exact whole number stays as it is); it is not a constant and is not in the configuration. A host whose margin cannot be measured gets nothing that pass, and the queue reason names the host and why; when no host the task can go to can be measured, it is not started and records `run-condition-unmet` (`wait` exits 78), with no fallback to a fixed number. Each attempt hands its cap (bytes, decimal) to the command in the environment variable `TASK_SERVER_MEMORY_CAP_BYTES`, on this host and on the second host alike. `python3 task-server/control pin-cap <command…>` pins a command's cap (`unpin-cap <command…>` removes it; written through the server, so it works while the server runs): a pinned command's cap and booking are the entry for the host it is sent to in the multi-host configuration's `SLICE_MEMORY_CAP_BY_HOST` minus that host's margin right now (space-separated `<address>=<value>`, the entry is that host's slice total, taken exactly as written; read afresh every time, never stored as a literal number; when an entry is not larger than that host's margin, `pin-cap` refuses on the spot and the way out is to raise that entry), learned peaks do not override it, hitting the cap does not grow it but records `memory-cap-at-maximum`, and `task status` says the cap is pinned; a pinned command whose configured `SLICE_MEMORY_CAP_BY_HOST` cannot be read (missing, malformed, one host left out, an address not in `HOSTS`, or the file unreadable) is not started and records `run-condition-unmet` (`wait` exits 78), and the reason line of `wait` names why it cannot be read and the way out (fix the configuration or `unpin-cap`). A suspected stall is only reported: after the grace, when the whole unit's CPU has averaged under 1% of one core for 10 minutes (for a task with a card, also no compute load of its own on its card in that time; unmeasurable counts as load), whether or not the log grows, the server does not stop it: `task status` writes "suspected stall" with the evidence, an alert is recorded, and `wait` prints one line `TASK_SERVER_SUSPECT task=<number> …` and exits 231; the task keeps running, and starting `wait` again keeps waiting (one report per stretch; the stretch ends when the CPU rises again). Gates under `.claude/gate.d/` can be sent to the second host (it runs this same shared tree); a task with a verdict library whose row in the registry `.claude/gate.d/verdict-library-scripts.tsv` does not yet say prune-server in the third column is refused at submission ("## How to submit" below). `python3 scripts/experiment-apparatus/device-code-key.py run … --feature <value>` with a feature value containing gpu needs a card too. `/health` only probes a database write and the queue thread's heartbeat; whether the head fits but has not started is worked out by the queue thread on every pass and `/health` only reads it.

## NFS share

**Why it is needed.** The principle the user set: “All scripts must run on multiple hosts. The results they produce must be readable from every host. If that cannot be done, either copy the resources or share the files.” NFS is the share-the-files route: this host exports some directories, the second host mounts them at the same absolute paths, so a result written on one host is read directly on the other, and a path a task refers to points at the same thing on both. On 2026-11-01 the user also set: “The NFS configuration must be written in the task-server readme. Do not leave anything out. This part must also be a checked item. Without NFS, do not start. Require the user to configure it. The configuration comes from the multi-host configuration file; no extra configuration file is allowed.” So the server does not set up NFS for the user: the configuration is a single key in the multi-host configuration `multi-host.env`, and the server does not start until it is set up.

**Which roots are shared.** Three: the repository itself (the root of the main work tree: the second host runs in this live tree, no tree is copied), the shared data root `~/.local/share/singlefs` (the work root and shard artifacts live under it) and the session transcript directory `~/.claude/projects`; each taken as this host's absolute path and mounted on the second host at the same absolute path (the second host's home directory may be another one; the mount points follow this host's paths).

**Export on this host.** Install `nfs-kernel-server` on this host, write one line per shared root in `/etc/exports`, exported only to the second host's address on the direct wired segment (the real address is a private value and is written only in that file on this host), then make the export take effect and enable it at boot:

```bash
# /etc/exports, one line per root
<root> <second host's address on the direct wired segment>(rw,sync,no_subtree_check)
sudo exportfs -ra
sudo systemctl enable --now nfs-server
```

**Mount on the second host.** Install `nfs-common` on the second host, create the directories at the same absolute paths as on this host, change the owner of the parent directory to the same uid as on this host, write one line per root in `/etc/fstab`, then have systemd reload and mount:

```bash
# /etc/fstab, one line per root
<this host's address on the direct wired segment>:<root> <root> nfs4 rw,hard,nofail,_netdev,x-systemd.automount,x-systemd.mount-timeout=30 0 0
sudo mkdir -p <root>
sudo systemctl daemon-reload
ls <root>                     # entering it triggers the automount
```

**Recovering by itself after this host reboots.** The fstab line carries `x-systemd.automount` and not `x-systemd.idle-timeout`. `x-systemd.automount` makes systemd put an automount point (an `.automount` unit) on the root, which does not fail together with the NFS mount itself: while this host reboots and the export is gone the mount unit may become `failed`, and the next time a process enters the root systemd starts the mount again, so once this host's `nfs-server` is back it mounts again without anyone running `reset-failed` and `start`. Without `x-systemd.idle-timeout` the mount stays once mounted and is not dropped when idle. `hard` (the NFS default) makes processes reading and writing during this host's reboot wait instead of failing. The server's mount check does not use `mountpoint -q` (an idle automount point is only an autofs placeholder there and `mountpoint -q` still exits 0); it runs `stat -f -c %T -- <root>/.` on the second host, which enters the directory and so triggers the mount, and passes only when it reads `nfs`. Once mounted, `git -C <repository root> rev-parse HEAD` on the second host reads the same commit as on this host: that is the repository root working.

**uid.** The user's uid and gid must be the same on both hosts; if they differ, add `all_squash,anonuid=<the user's uid on this host>,anongid=<the user's gid on this host>` inside the parentheses of the export entry, so that files the second host writes land owned by this host's user.

**Which keys in the multi-host configuration.** In `multi-host.env` at the repository root write three keys. First, `NFS_SHARED_ROOTS=<absolute path>[:<absolute path>…]`, the roots exported and mounted above (the repository itself, i.e. the root of the main work tree; the shared data root `~/.local/share/singlefs`, which holds the work root; the session transcript directory `~/.claude/projects`; each written as this host's absolute path): separated by colons, at least one segment, each segment starting with `/`, not ending with `/`, and containing no whitespace; write it even when `ENABLE_ACROSS_MACHINES` is 0. The template is `multi-host.env.example`, and no extra configuration file is added. The multi-host configuration check `scripts/crash/crash-point-replay-shard-configuration-check.sh` checks the form and, on this host, also checks that each segment is an existing directory; one that does not fit exits 1 and names which segment. Second, `SHARED_DATA_ROOT=<absolute path>`: the shared data root (the work root is under it), this host's absolute path, inside one segment of `NFS_SHARED_ROOTS`; the server takes it through `.claude/hooks/lib_work_root.py` (or `SINGLEFS_DATA_ROOT` when that is set in its environment), and `control install`, `start` and `check` look only at this line: missing or outside the shared roots exits 78 with the way out naming this line to add to `multi-host.env`; no default is filled in. Third, `HOSTS=<this host's IP> <second host's IP>`: each host's address on the wired direct link, separated by spaces; which one is this host is told from this host's interface addresses (`ip -o addr show`), the second host is the other one, ssh connects to it directly, and the user name comes from each host's `~/.ssh/config`. The second host's address is taken only through the shared helper `scripts/hosts/multi_host_addresses.py`, which gives an address only after the whole multi-host configuration passes its check: a missing key, a key the check does not know, or a malformed line yields no address, so the server does not start and `control start` exits 78. Values that differ between the hosts go into the three per-host keys `CARGO_BIN_DIRECTORY_BY_HOST`, `BUILD_ROOT_BY_HOST` and `SLICE_MEMORY_CAP_BY_HOST`: the value is space-separated `<address>=<value>` entries, each split at its first `=`, with exactly one entry for every host in `HOSTS` and every address in `HOSTS`; whoever needs a host's value takes the entry for that host's address. The server reads `SLICE_MEMORY_CAP_BY_HOST` (pinned caps) and treats a missing host or an address not in `HOSTS` as a malformed configuration. Each shard gets, through `TASK_SERVER_SHARD_HOST`, the `HOSTS` address of the host it runs on.

**What the server checks when it starts.** Four items; if any one fails the server does not start, exits 78, names the item and points to "## NFS share":

- configuration: `NFS_SHARED_ROOTS` is present and each segment is a directory on this host; `HOSTS` tells this host and the second host apart (the next two items reach the second host through it);
- export: every segment has an export line in `/var/lib/nfs/etab` on this host;
- mount: `stat -f -c %T -- <root>/.` reads `nfs` for every segment on the second host (entering it triggers the automount);
- read and write: a probe file is written in each direction and the other side can read it (written on this host and read on the second host, written on the second host and read on this host).

`task-server/control check`, the `nfs` field of `/health` and `task-server/control watch` check the same four items: if one of them starts failing after the server is up, it shows in these three places too.

**When one fails.**

- Configuration fails: add the key or fix its form as in "Which key in the multi-host configuration", and create the directory first if it does not exist.
- Export fails: add the missing line to `/etc/exports` and run `sudo exportfs -ra`; if the NFS server is not running, run `sudo systemctl enable --now nfs-server`.
- Mount fails: on the second host add or fix the `/etc/fstab` line as written above and run `sudo systemctl daemon-reload`; if the mount unit has become `failed`, run `sudo systemctl reset-failed "$(systemd-escape -p --suffix=mount <root>)"` and then `ls <root>` to trigger the mount; if it will not mount, first check that the direct wired segment is up and that the client address exported to on this host is the second host's.
- Read and write fails: most likely the uid and gid differ between the two hosts, or the export entry lacks `rw`; follow the "uid" paragraph.

**How to check.** Three things, each run on the host its comment names:

```bash
stat -f -c %T -- <root>/.                   # run on the second host: printing nfs means the root is mounted
cat /var/lib/nfs/etab                       # run on this host: every root has an export line, and the client is the second host
echo probe > <root>/nfs-check-by-hand       # run on this host: written on this host
cat <root>/nfs-check-by-hand                # run on the second host: the second host reads probe
echo probe > <root>/nfs-check-peer          # run on the second host: written on the second host
cat <root>/nfs-check-peer                   # run on this host: this host reads probe
rm <root>/nfs-check-by-hand <root>/nfs-check-peer   # delete both files when done
```

## How to submit

```bash
task-server/task submit -- <command…>              # prints the task number; whitelisted variables in the environment such as SINGLEFS_RUN_SCOPE are carried
task-server/task wait <number>                      # start it with run_in_background; it exits on completion, last line TASK_SERVER_RESULT …, the exit code is the task's
task-server/task status [<number>]                  # this session's queued, running, and finished-but-unclaimed tasks; queued ones carry "waiting: …", running ones how long they have run and how long the log has not grown
task-server/task cancel <number>                    # only the submitting session
task-server/task log <number>                       # the log of the last attempt (last 200 lines; --all the whole log; --attempt <which> that attempt; exits 4 if the task or attempt is absent)
task-server/task clean <number>                     # removes the build directory and the failure scene this task left (only the submitting session, only once it has an outcome; without SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1 the build directory is already gone at the outcome and the scene goes one hour after wait collects the outcome; multi-host-run.sh removes the second host's build directory of its run itself)
```

`wait` itself reports five situations that need handling (the user chose "task wait reports them itself" in the dialog): first, a task queued too long, after `QUEUE_ATTENTION_MINUTES` (30 minutes) in the queue; second, a task running `OVERRUN_ATTENTION_FACTOR` (3) times the recorded duration, which the server never stops while the log is still growing, so this is what calls a human; third, a card replacement, where quiesce found a card broken and the server requeued the task on another card (the final outcome may be `succeeded`); fourth, quiesce not finished (`cleanup-pending`), where the command has exited but the read-back still finds leftovers and the server keeps the resource booking; fifth, a sharded parent that cannot advance (`shard-advance-failed`). A sixth kind is reported only for a task that already has an outcome: a command that writes the main working tree (`apply-writer-patch.py`, `hook-swap.py`, `stage-mine.py`, `merge-and-verify.sh` without `--skip-apply`) that ended by hitting its cap, being squeezed out, running short of GPU memory, a failed second-host run, reaching the maximum, cancellation, being stopped as stalled, losing its launcher or being killed by a signal (`workspace-write-interrupted`) may have written only half, and `next=` names the files or patch directory to check (user: 「这个问题很严重 因为可能会导致补丁没有正常写入」); for `apply-writer-patch.py` with an outcome file `apply-outcome.tsv` the server judges by its `--read-outcome`, and a patch applied in full or rolled back is not reported, nor is one run with `--dry-run`. The server records these for the task (and its subtasks, for a sharded one) as "needs handling" reminders. A `task wait <number>` that is waiting for the task prints one line `TASK_SERVER_ATTENTION task=<number> type=needs-attention kind=<kind> tier=<tier> basis=<the numbers it rests on> why=<reason> next=<way out>` on reading a new reminder, then exits 230: the task is still queued or running and the server did not touch it; handle it as `next=` says and start `wait` again to keep waiting. For a task that already has an outcome (a card replacement that succeeded) the line is printed before `TASK_SERVER_REASON` and the exit code stays the task's. The same reminder of the same kind for the same task at the same tier wakes the caller only once, so restarting `wait` does not repeat it; it fires again only when the tier crosses the next step (twice, four times the threshold, and so on). Reminders are kept in the server's memory, so they are reported once more after a restart. Server health is not `wait`'s business: the main agent starts `python3 task-server/control watch` with `run_in_background`, and when it exits something needs handling.

Do not wrap commands or pass resource arguments: `run-with-memory-cap.sh <cap>`, `host-dispatch.py … --`, `multi-host-run.sh … --`, `nice`, `timeout`, `capped.sh`, `two-logs.sh`, `gpu-quiesce-run.sh` and the scripts' own `--memory`, `--memory-cap`, `--threads`, `--peer`, `--local-only`, `SINGLEFS_THREAD_CAP`: the server does these, and writing them is refused on the spot, naming which one to remove. Environment variables outside the whitelist are refused on the spot and named; a command that really needs one is written as `task-server/task submit -- env <name>=<value> <command…>`. Retired variables (`SINGLEFS_HEAVY_TESTS`, `GATE_MUTATION_START_OVER`) are refused on the spot whether set in the environment or written in the command (a `name=value` after `env` or in front of the command); the refusal names it and gives the way out; the list is `RETIRED_VARIABLES` in `task_server_lib.py`.

Three kinds that could not be sent to the second host are refused at submission (user: 「改成提交时当场拒（推荐）：不再悄悄改派本机：碰到这三种就在提交时报错、点名是哪个路径或哪一族、出路写怎么改，任务不跑。」): `task submit` exits 3 and prints the sentence and the way out; the task is not queued and does not run. First, an absolute path in the working directory or the command (a whole word, the value of `name=absolute path`, each one inside one word such as `bash -c`) that lies under no segment of the multi-host configuration's `NFS_SHARED_ROOTS`: the sentence names that path and the way out is to move it under one of the segments; system paths that are the same on both hosts such as `/dev/null`, `/usr/` and `/bin/` do not count; a path under `/tmp` is refused the same way, and the sentence adds that a reboot clears `/tmp`. Second, a `SINGLEFS_DATA_ROOT` or `SINGLEFS_WORK_ROOT` handed to the command that is not under a shared root: the sentence names the variable and its value, and the way out is to set up the multi-host configuration. Third, a command that points at a row with a verdict library in the registry `.claude/gate.d/verdict-library-scripts.tsv` whose third column does not yet say `prune-server`: the sentence names that family, and the way out is to move that family onto prune-server and turn the third column into `prune-server`; a registry that cannot be read or is malformed is refused the same way.

The temporary prune-server wrapper (`python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <path>] -- <original command>`) is only for script self-tests (user: 「旧脚本不兼容 我再说一次 如果错了让 对方重新提交」): when the original command unwrapped from it contains a cargo that compiles, or needs a card (recognized the same way the service decides the build directory and the card), it is refused at submission in the same form as above: `task submit` exits 3 and prints the sentence (naming whether it compiles or needs a card) and the way out (submit again without the wrapper); the task is not queued and does not run. Unwrapping is only for judging; an accepted command still runs whole, wrapper included; the build directory, the card and the GPU quiesce are given only for the outer command, and the service does not unwrap to accommodate it. A wrapper without `--server-binary` (and without `PRUNE_SERVER_BINARY` in the assignments before the command or in the task environment) has to compile prune-server itself in the build directory the service gives, so the service counts the outer command as one that compiles: both hosts are given a build directory; with `--server-binary` nothing is compiled and none is given. The `cargo test` of the checker tier runs against the real service and is not wrapped this way.

## Declarations in source headers

The server reads a few declaration lines in the first 60 lines of a source file to tell what a command needs; callers still write no card and no budget. The session that owns the entry script or the package adds the declaration; the server only reads it:

| Where | How it is written | What the server does with it |
|---|---|---|
| entry script | `# task-server-gpu-arguments: <argument>…` (`*` is any argument) | needs a card, and the server wraps the GPU quiesce, when the first non-option argument is one of them |
| entry script | `# task-server-gpu-cards: <count>` | when it needs cards, it needs this many on the same host (see "How many cards" below) |
| `.rs` source (the source of the same name as a compiled binary; the sources of the packages a `cargo test` / `run` / `bench` names with `-p`) | `// task-server-gpu-cards: <count>` | same as above |
| entry script | `# task-server-cargo-family: <cargo arguments>…` (for example `-p singlefs-verification --release --features gpu`) | which package, profile and features the cargo it starts builds: when the command has no record under its own key, the server starts from the peak of the same build family (see "Starting peaks" below) |
| entry script | `# task-server-shards: <argument>…`, `# task-server-resumable: <argument>…` | sharding and resuming (the "分片" and "续跑" parts of the `task_server_lib.py` header) |

How many cards: the real-card test the user set is 「你需要测试的是 一张卡1gb 2张卡 三张卡 每张卡都能用来分片gc。没有卡报错。 有卡但是失败 报错加cpu兜底」. For a declared count, the server goes through the cards in the multi-host configuration's priority order, picks the first host whose free cards add up to that many and which also has room in memory, and gives the first that many free cards of that host to the task as one group: `GPU_CARDS_BY_PRIORITY` carries those entries joined by spaces, the quiesce covers the whole group, and all of them count as taken while it runs. When no host among the cards the multi-host configuration names has that many, the outcome is `never-fits` (exit 241); a count that is not a positive integer gives `run-condition-unmet`, and the note names which file wrote what. Which `.rs` sources are read: with `--test <name>`, `tests/<name>.rs`; with only `--lib`, `src/lib.rs`; otherwise `src/lib.rs`, `src/main.rs` and the files under `src/bin/` and `tests/`; when several declare a count the largest wins, and none means one card. Example: with `// task-server-gpu-cards: 3` in the first lines of `crates/singlefs-background-gpu/tests/<target>.rs`, `cargo test --release -p singlefs-background-gpu --features tests-on-a-real-gpu --tests` is given three cards on the same host.

Starting peaks (from the attempt records in the server's own database, the "资源记录" part of the `task_server_lib.py` header):
- Build family: a cargo that compiles is put in a family by its packages, profile (`--release`) and features; an entry script that declares `task-server-cargo-family` is put in the family it declares. When the command has not completed once under its own key, it starts from the largest peak of the last 5 successful runs of the same family × 1.5, used only when that is above 4G; a command with records of its own follows them.
- Peaks shared within one plan: the first attempt of a shard takes the peak of the plan step and of its sibling shards' ended attempts, the 5 most recent by end time (for one that hit its cap, that attempt's cap) × 1.5, and only ever raises, never pushing below 4G.
- Starting at the highest of the recent runs: the first attempt of a new submission and every requeue after hitting the cap are raised to the highest of the last 5 the server has on record for this key (caps it hit and peaks of runs that completed) × 1.5, and a requeue also looks at the build family and the sibling shards (also only the last 5); it goes both up and down: a cap just hit inside the window is seen at once, an older one that left the window no longer counts, and when the later runs are all small the start comes down with them. A command with no record at all still starts at 4G, and one with real peak records is not raised to the 4G floor.
- On a requeue after hitting the cap, the previous attempt's build directory is kept, and a requeued attempt that is still on the same host keeps using it (inferred: cargo reuses the crates it has already built by fingerprint; how much this saves has not been measured); when the requeue moves to the other host, the previous one is removed as that attempt starts. Both hosts go through the same logic: on this host through `CARGO_TARGET_DIR`; an attempt on the second host carries `--keep-build-directory`, `multi-host-run.sh` keeps `builds/<label>/` after the run, the requeued attempt carries `--reuse-build-directory <previous label>` to keep using it, and the server removes it with `multi-host-run.sh --remove-build-directory <label>` when the task moves host or has an outcome.

## Pause and resume

Jobs such as swapping the prune-server binary or clearing old rows in the verdict library need a window in which no other session's task is running, and the job itself often has to submit commands through `task submit`. `control stop` cannot give that: while the server is stopped nobody can submit, and a `task wait` that is already running exits 78 after 60 seconds. Use pause instead, and let the session that does the job through (its tasks still start while paused):

```bash
python3 task-server/control pause --reason "clear old verdict rows" --allow-session <the session doing the job>   # pause: other sessions' tasks do not start; the allowed session's tasks are queued and started as usual; submissions are still accepted, status / wait / log / cancel still answer
python3 task-server/control check                                                                                   # repeat until it prints "…、放行会话 <id>、在跑 N 个、别的会话在跑 0 个" (… allowed session <id>, N running, 0 running in other sessions)
# ...do the job that needs the window (the session doing the job submits its commands with task submit)...
python3 task-server/control resume                                                                                  # release: queued tasks start as usual, the allowance is cleared with it
```

- The id of the session doing the job: run `python3 task-server/task status` in that session and take the id from the first line, "会话 <id>：…" (it is the session the server recorded when the task was submitted, the same field `status` shows for every task). What is allowed is a session, not one command: tasks of that session that were already queued, submitted later, children of sharded tasks, estimate children and retries that went back to the queue all start as usual; tasks of other sessions, and hand-submitted tasks that have no session, stay queued and unstarted. A queued task of the allowed session shows what it is really waiting for in `status`; a queued task of another session shows "在等：服务暂停中（原因：…）".
- `pause --allow-session <another session>` on an already paused server exits 0 and switches the allowed session (reason and start time unchanged); a `pause` without `--allow-session` leaves the allowance alone; `resume` clears the allowance with the pause. For a window in which no task at all is running: `pause` without `--allow-session` and wait until `control check` reports 0 running.
- While paused the scheduler starts no new attempt (except for the allowed session's): backfill, children of sharded tasks, estimate children and retries that went back to the queue are all held. Running attempts run to their outcome (the outcome is still written and a retry still goes back to the queue, but is not started). `pause` and attempt start share one lock, so when `pause` exits 0 an attempt that was being started is already recorded and the running count of `control check` cannot be joined by another.
- The paused state, with the allowed session, is stored in the server's database (signed: a changed allowed session in the database counts as failing verification and allows nobody) and survives a server restart, allowance included, until `resume`; `pause` on an already paused server exits 0 and keeps the original reason and start time.
- `control check` prints one more line, "暂停中（原因：…，起于…）、在跑 N 个"; with a session allowed it reads "…、放行会话 <id>、在跑 N 个、别的会话在跑 M 个" (M is the running tasks that are not the allowed session's); it still exits 0 without judging "the dispatcher judged the head startable but did not start it" or watching progress; `/health` carries `paused` and `pause` (with `allow_session` and `other_running`) and `ok` is unchanged; a queued task's `status` shows "在等：服务暂停中（原因：…）".
- While paused `control watch` keeps watching whether the server answers, the database is writable, the unit is up, NFS and the second host.
- Only the user who runs the server may send `pause` and `resume`, checked like submit and cancel: the server compares the caller's uid with its own.
- Always `resume` when the job is done; a paused server looks healthy (`check` exits 0), so queued tasks would wait forever if you forget.
