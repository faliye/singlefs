# task-server

[中文](README.md) · **English** · [日本語](README.ja.md)

For resources still held after an abnormal exit, remote cleanup receipts and diagnostic logs, see [Task cleanup and GPU phase logs](cleanup-protocol.md).

The unified task server of singlefs: every task that runs project code (light, heavy) is started through it and goes into one queue, where the server schedules by resources and fairness rules with no extra delay: when the head of the queue does not fit, a task behind it that fits may start first (cutting in), and a task submitted two hours ago or more moves to the front; the rules are in "## Scheduling". Tasks are submitted only by the main agent (with the client `task-server/task`, which people use too); sub-agents only use `status` and `log` to read outcomes; picking the host and setting the memory budget are decided by the server, and submission does not accept either. The server schedules only CPU and memory; it does not assign, lease or quiesce cards: the cards belong to the GPU batch verification server (`gpu-verification-server/`), see "## Cards".

The server is the only process that reads and writes the database: FastAPI on uvicorn, running as the user-level systemd service `singlefs-task-server.service`, listening only on a unix socket (`${XDG_RUNTIME_DIR}/singlefs-task-server/server.sock`, directory 700; the full path is at most 107 bytes, and beyond that the server, the client and `control` all exit 78, naming the path, its byte count and the limit), never on TCP. The database is embedded SQLite (WAL) under `~/.local/state/singlefs/task-server/`, and every row carries an HMAC check column. Memory acceptance is judged in one place only, the server: a task starts only when it fits, and one that does not fit stays queued in the database; a started task is still wrapped in `scripts/hosts/run-with-memory-cap.sh` (this host, with the "accepted by task-server" switch set, doing only the kernel-level backstop of the per-task cap and the slice total cap) or `scripts/hosts/multi-host-run.sh --peer` (second host).

There is no configuration file of its own: scheduling resources are read from the multi-host configuration `multi-host.env` at the repository root (template `multi-host.env.example`); the socket, database, logs, signing key and build directories use the fixed defaults written in the "paths" section of the `task_server_lib.py` file header. Required: fastapi, uvicorn, `multi-host.env` (with `NFS_SHARED_ROOTS`, `SHARED_DATA_ROOT` and `HOSTS` in it, written as in "Which keys in the multi-host configuration" under "## NFS share"), the NFS share set up (see "## NFS share"), and a reachable server.

## Scheduling

Hosts are picked by balancing free room: a task picks, among the hosts it can be sent to, one where it fits; when more than one fits, it picks the one whose remaining room after placing it is the larger share of that host's total cap, and this host on a tie; a retry after hitting the cap is not pinned to a host. Shards go to the second host first as the plan says, and are not moved by balancing as long as they fit there; the plan, the shards and the merge are not pinned to a host, and a plan that writes `pin` makes the whole task `shard-plan-refused` (shards are not pinned; the server picks the host). The second host runs in the same shared tree: the repository, the shared data root holding the work root `~/.local/share/singlefs/work/`, and the session transcript directory are mounted on both hosts at the same absolute paths over NFS (`NFS_SHARED_ROOTS` in the multi-host configuration, see "NFS share" below), so a run sent to the second host is started directly by `scripts/hosts/multi-host-run.sh --peer` in the task's working directory at the same absolute path, with no tree copied, nothing sent or fetched back and no path rewritten, and the files it writes are readable on both hosts; the build directory is one of this tree's pool on the second host ("## Build directories" below): a new one is created by `multi-host-run.sh` on the second host's local disk (`builds/<label>/target` under the second host's entry in the multi-host configuration's `BUILD_ROOT_BY_HOST`, under no shared root) and kept after the run with `--keep-build-directory`, and one already in the pool is reused with `--reuse-build-directory <label>`; the server does not set `CARGO_TARGET_DIR` and only records where it is (shown by `task status`); `task clean` does not touch it. Whether a task goes to the second host depends only on whether the second host is usable right now and on free room; the three kinds that could not be sent there are refused at submission ("## How to submit" below). There is no list of commands kept to one host (the user: "I say it once more: [runs only on this host] is not acceptable. Fix it as soon as possible and let the errors show"): a command naming any directory or entry can be sent to either host, and free room decides which; one that goes red on the second host stays red and is fixed in the script, the server does not shield it. The post-merge verification `scripts/gate/merge-and-verify.sh` applies patches and verifies only on a snapshot it copies itself and writes not one byte of the main work tree (its header, 「快照（不拿锁）」), so it does not count as changing the main work tree, and hitting the cap gets the usual larger cap and requeue. Tools that change the main work tree (`hook-swap.py`, `apply-writer-patch.py`, `stage-mine.py`, those under `scripts/kb/`) and commands with `--write` can be sent to the second host (they change the same tree); outcomes that would otherwise be retried, such as hitting the cap, are still not retried for them but handed back to the session that submitted them; so the tools in the parentheses get enough on the first attempt: the cap is at least "(highest of the last 5 runs of the same key + highest of the last 5 runs of the key of the verification command given by `hook-swap.py`'s `--verify`) × 1.5", with no 4G floor (one swap was given only 857M by the same-key window, hit it, and was left half swapped). The plan directory and each shard's artifact directory of a sharded task live under `task-server-shards/` in the shared work root, read and written by both hosts at the same absolute paths. The test binaries the plan step puts under the plan directory (`test-binaries/`) are removed by the server when the parent task gets an outcome (success, failure and cancellation alike) and on `task clean <parent number>`; the rest of the plan directory stays. If the real path of that subdirectory is not inside this task's own plan directory (a symbolic link pointing elsewhere, say), the server leaves it and prints a line in its log; how many files and how many bytes were removed goes into the operation log. The server does not check the merge lock: while the main work tree is being merged, tasks are queued and started as usual. At most 4 tasks start on the second host in one pass (starting too many at once gets ssh connections reset), and once that is reached another pass runs 2 seconds later; every ssh the server starts itself (NFS recheck, free-room probe, process check, progress readings) reuses connections: it carries `ControlMaster=auto`, `ControlPath=<server state directory>/ssh/%C` (one per host) and `ControlPersist=300`, host names come only from the multi-host configuration, and the master connections are closed one by one when the server stops (the ssh that attempts start through `multi-host-run.sh` is not part of this layer); the outcome of a run on the second host follows the end line that `multi-host-run.sh` writes into the log for that command (`MULTI_HOST_RUN_STEP step=peer-command event=end … exit=<code>`): with that line the outcome follows the command's own exit code, and a command that itself exits 255 is recorded as `command-failed` and not requeued; only an exit of 255 without that line means the second host failed to run it (unreachable, ssh reset), recorded as `peer-run-failed` and requeued unchanged, at most 2 times. Queue order follows only two rules: (1) a task that has waited out the aged limit (two hours) and still cannot start holds back every task behind it: until it starts none of them starts, and their queue reason says 「排在任务 N 后面：它已排满时限」; (2) while an earlier task has not started, a later one may start first only if it has a last run duration (how long the same command key took the last time it really ran to its end: a record, not an estimate) and that duration is no longer than the longest remaining time among the tasks running on that host (remaining = that task's last run duration minus the time it has run; when no running task has a computable remaining time, a task with a last run duration may start first); a task with no last run duration does not cut in, and its queue reason says 「不插队」. The service does not estimate durations: memory caps come from records and grow 1.5 times after a hit; an item that really runs four hours is stopped and returned, and one that runs two hours gets a reminder to split it (the commit gates submitted with `--full-gate` are exempt from both). Queued tasks never hold room. Both hosts go through the same logic (booking, fitting, stall and CPU, peaks, caps, build directories, host picking and free disk, with the same 50G disk floor on both); what differs per host is only how it is reached, measured and started (`Machine` in `task_server.py`). When an attempt ends normally and grandchild processes of the command are still in its unit, the server stops them and says so in the outcome note; when a run of more than 30 minutes fails and the script does not declare that it can resume with `# task-server-resumable: <word>…` in its header, the outcome note says "ran N minutes, not resumable: a resubmission starts from scratch" (in Chinese).

Each attempt's command is wrapped in `scripts/hosts/capped.sh <default heavy threads per host>`, and the thread count is always that number and is not accepted at submission; no quiesce wrapper goes around it (tasks hold no cards, see "## Cards"). The memory wrapper, `capped.sh` and `multi-host-run.sh --peer` accept only the layer the server wraps directly: the server sets an admission mark for each layer (its value is `<task number>.<attempt number>`), that layer reads it and does not pass it to the command, and a script inside the task that wraps one more layer is refused on the spot; the way out is to delete that layer and read the memory and threads from `TASK_SERVER_MEMORY_CAP_BYTES` and `SINGLEFS_THREAD_CAP` that the server passes; the card-choice variables in the server's own environment (`GPU_CARDS_BY_PRIORITY`, `CUDA_VISIBLE_DEVICES`) are not passed to the command; a cargo run that compiles also gets a `CARGO_TARGET_DIR` outside the repository: one of this tree's pool on this host, so tasks submitted later on the same tree keep building incrementally, and it is removed only when the tree is deleted ("## Build directories" below); the last line of `wait` carries no `build=`, and a cancelled task has only its own scene removed (the cancel under "## 提交写法" below). The budget follows only the server's own attempt records (the largest peak of the last few successful runs × 1.5; the memory wrapper's peak table is not read; the command key first drops an `env` prefix of variables that do not change how the command runs, such as the multi-host configuration path and `LANG`); a command with no record starts at 4G (one that has only failed starts no lower than the peak of that failed run × 1.5), a command with a record has its cap and booking set from the record × 1.5 and is not raised to 4G (a pinned cap is left as it is), and a task is requeued × 1.5 after hitting the cap (the requeued cap is not raised to 4G either); when × 1.5 would reach that host's total cap it is not requeued: it moves to another host with a larger total cap if there is one, and otherwise is recorded as `memory-cap-at-maximum` and returned to the submitting session, where `next=` and the message to the session name the host, the cap reached and the peak, and suggest checking this run's scope (the items named, the test targets), its sharding and how many run at once, and resubmitting it smaller or sharded; quotas read only attempt records whose peak measurement basis column says 「进程内存」 (process memory), and older records without that column (page cache included) are not read; the room left on a host counts only memory used by processes (`anon` plus `shmem`), not the page cache or kernel memory charged to the slice; nothing is judged during a 10-minute grace after start; after that, a task whose log has not grown for 10 minutes and whose CPU has also barely risen in that time (on average under 1% of one core) is stopped by the server and recorded as `stalled`, and unreadable CPU does not count as not rising; a task whose log and CPU have both not grown for 10 minutes while every poll in that time found some process in state D (uninterruptible IO wait: on this host the server reads the state field of `/proc/<pid>/stat` for the attempt's processes, on the second host it reads the `MULTI_HOST_RUN_PEER_IO_WAIT poll=<poll> blocked=<processes in state D> read=<yes|no>` line that `multi-host-run.sh` prints every poll, a line that does not count as log growth) is waiting on IO: it is not recorded as `stalled` and not stopped, and if any poll found no process in state D or could not read the states the original rule applies (four tasks were stopped as stalled while waiting on the NFS this host exports); a task that has run past 5 times its recorded duration and whose log has not grown for 10 minutes is stopped and recorded as `stalled` without looking at the CPU (an endless loop is stopped too), and a task with no recorded duration is not judged by this rule; the recorded duration only counts completed runs whose work is comparable to this one, at least 3 of them (a shard only counts runs with the same shard count), and with fewer this rule is not applied; an attempt whose process memory or peak grew by at least 64 MiB within a window is making progress and is not stopped even past 5 times; the heartbeat lines a command prints at a fixed interval (`TASK_SERVER_HEARTBEAT <text>`) do not count as log growth, so a command that prints only heartbeat lines with the CPU idle is still judged stalled after a full window, while one that mixes in real output is not stopped; when a command is ended by a signal (its attempt unit received a stop signal, or its exit code is 128 + the signal number), the reason line names the signal and says whether the service sent a stop signal this time and from which step; `stalled` is not retried and is returned to the submitting session; a task whose process memory (`anon` plus `shmem`, the same measurement basis as the room left above; page cache that fills the cap is reclaimed by the kernel and kills nothing, so it does not count), current or peak, had reached 98% of its cap at the moment it was judged stuck is stuck at the cap: it is stopped the same way but recorded as `memory-cap-hit` and requeued × 1.5 (a pinned cap is returned as `memory-cap-at-maximum`), with the note "顶在上限上卡住" (stuck at the cap); how long it has run, the recorded duration and the cores in use are written only into `task status`. The recorded memory peak counts only process memory on both hosts: every poll reads `anon` plus `shmem` from `memory.stat` of the memory wrapper's scope and keeps the largest seen (a run building the verification package used under 1G in its processes while page cache pushed the scope's `memory.peak` to the 50176M cap); only a command shorter than one poll, never sampled, falls back to the `memory.peak` the wrapper reads on exit. The memory peak of the second host's layer is recorded into that attempt from the `MULTI_HOST_RUN_PEER_MEMORY_PEAK bytes=<bytes>` line that `multi-host-run.sh` writes, and feeds the budget the same way as on this host; a run without that line is recorded as not measured. The disk taken by the build directory is also recorded per command as a peak (on this host by measuring the build directory the server gave, on the second host from `MULTI_HOST_RUN_PEER_BUILD_PEAK bytes=<bytes>`); before a task is sent to a host, that host's free disk minus what running attempts' build directories will still grow must hold this command's build-directory peak plus a 50G floor, otherwise the task stays queued and its waiting reason names "编译目录占盘" (build-directory disk). A command that itself exits 75 (prune-server unavailable) is recorded as `prune-server-unavailable`, `wait` exits 75 and it is not requeued; the server runs `python3 prune-server/control check` once and writes an alert when it fails, without starting or stopping prune-server. A command written as `python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <path>] -- <original command>` has its command key and its registry row taken from the original command after `--` (the `--server-binary` path is not part of the key), and the key is prefixed with `〈task-server 临时 prune-server〉`: the same scope runs one more prune-server, so it does not share a record with the unwrapped command; the wrapper itself still runs as written.

Admission booking: a new attempt is booked at its cap (clamped to that host's total cap minus that host's margin right now); a running attempt is booked only at the memory its scope in the report cannot reclaim right now (no fixed margin added, no number estimated in advance), no more than its cap (one whose scope is not in the report yet is booked at its whole cap), and each keeps its own cap (memory.max), so only the one that exceeds it is killed; each host's formula is the total cap minus the margin minus the sum of what the running attempts are booked at (the bookings never exceed the total cap; the sum of the running caps does not enter the formula); each attempt's cap comes only from the records of its own command key: with no record it starts at 4096M and is retried × 1.5 after hitting the cap, and records of other keys or of sibling shards of the same run are not borrowed; slice backstop: while the host's measured slice room is below 4 GiB no new task is started there in that pass, with the queue reason saying the measured room is short; when memory does not fit, the queue reason says what each of the two numbers is — how much the books can still take (total cap, margin, and the running bookings) and how much the slice can still hold as measured — and names the two running tasks with the largest bookings on that host with their booking and actual use; the CPU gate takes the larger of the load and the threads of the attempts running there, adds the threads of the task being placed, and places it only if that stays within the core count × 3.4375 (the line is 110 on a 32-core host); a running attempt that has run for 120 seconds and for which the service has measured a full segment counts the cores in use of its most recent full segment: the service reads the cumulative CPU every round, two readings 120 seconds or more apart give one segment's cores in use, and the attempt takes the most recent segment (rounded up, at least 1, at most the registered threads), so when a task finishes a busy stretch and goes idle its booking drops with it; the peak-segment cores, the largest over all segments, are used only for the core record written at the end and for the small-task slots; because cores in use are pushed down when the host is packed (several tasks that each want 31 cores share one host and each gets only seven to ten), the service also reads the attempt's runnable threads every round (on this host the per-attempt layer counts the threads in state R in the process tree when it samples; on the second host `multi-host-run.sh` prints one `MULTI_HOST_RUN_PEER_THREADS` line per round), and the running branch counts min(registered threads, max(cores in use of the most recent segment, the runnable count read most recently)); a round whose reading is missing uses cores in use only. One that has run for 120 seconds but for which the service has not yet measured a full segment (just restarted) counts the cumulative CPU so far divided by the seconds run (the cumulative figure is kept by the cgroup and survives a restart). One that has not yet run 120 seconds, or that cannot be measured, is counted the same way as the task being placed: the largest CPU-gate threads (`cpu_gate_threads`, recorded when an attempt ends as min(registered threads, max(peak-segment cores, largest runnable count)); older attempts without that field are not read) over the last 5 runs of its command key that ran to the end (rounded up, at least 1, at most 31), or the registered threads for now when there is no record or no command key (measured once a full segment is measured); a task over the line that needs no more than 2 cores still starts on a small-task slot ("要核数少的名额"), with at most 4 attempts per host running on such slots at once; when they are all taken it queues and the reason says "要核数少的名额 4 个已用满"; an attempt started on a slot records `cpu_small_slot` and its start line and `task status` say so, and the slots are counted from the running attempts in the database, so a restarted service still sees them; an attempt that has run for 120 seconds and whose peak-segment cores exceed 2 no longer holds a slot (one that cannot be measured, or has no full segment yet, still does); a host whose core count or load cannot be read gets nothing in that pass; the second host's headroom is read on a timer by a background thread of the service (with time limits, and not retried for a while after a failed read), placement only takes its latest reading, and a stuck second host does not hold up placement on this host; both hosts go through the same code: the usage is measured per attempt's scope by the same read of that host's margin (the same ssh for the second host; a scope is matched to its attempt by `TASK_SERVER_ATTEMPT_LABEL` in the environment of its processes, set on both hosts), an attempt whose scope is missing from that report is booked at its whole cap, not 0, and the memory wrapper on the second host keeps no booking of its own. The margin is the memory in that host's `singlefs-heavy.slice` right now that cannot be reclaimed and belongs to no running task (charged to the slice itself and found in no child cgroup; how it is measured is in the header of `scripts/hosts/memory_peaks_lib.py`, "余量"); every read of the two hosts' free room measures it on each host separately and rounds it up to a whole GiB (1.01G and 1.1G count as 2G, 2.1G as 3G, 0.7G as 1G, an exact whole number stays as it is); it is not a constant and is not in the configuration. A host whose margin cannot be measured gets nothing that pass, and the queue reason names the host and why; when no host the task can go to can be measured, it is not started and records `run-condition-unmet` (`wait` exits 78), with no fallback to a fixed number. Each attempt hands its cap (bytes, decimal) to the command in the environment variable `TASK_SERVER_MEMORY_CAP_BYTES`, on this host and on the second host alike. `python3 task-server/control pin-cap <command…>` pins a command's cap (`unpin-cap <command…>` removes it; written through the server, so it works while the server runs): a pinned command's cap and booking are the entry for the host it is sent to in the multi-host configuration's `SLICE_MEMORY_CAP_BY_HOST` minus that host's margin right now (space-separated `<address>=<value>`, the entry is that host's slice total, taken exactly as written; read afresh every time, never stored as a literal number; when an entry is not larger than that host's margin, `pin-cap` refuses on the spot and the way out is to raise that entry), learned peaks do not override it, hitting the cap does not grow it but records `memory-cap-at-maximum`, and `task status` says the cap is pinned; a pinned command whose configured `SLICE_MEMORY_CAP_BY_HOST` cannot be read (missing, malformed, one host left out, an address not in `HOSTS`, or the file unreadable) is not started and records `run-condition-unmet` (`wait` exits 78), and the reason line of `wait` names why it cannot be read and the way out (fix the configuration or `unpin-cap`). A suspected stall is only reported: after the grace, when the whole unit's CPU has averaged under 1% of one core for 10 minutes, whether or not the log grows, the server does not stop it: `task status` writes "suspected stall" with the evidence, an alert is recorded, and `wait` prints one line `TASK_SERVER_SUSPECT task=<number> …` and exits 231; the task keeps running, and starting `wait` again keeps waiting (one report per stretch; the stretch ends when the CPU rises again). An attempt whose log has not grown for 10 minutes and whose memory right now is at least 98% of its cap is stopped even while its CPU rises (spinning in reclaim is not computing; task 7723 ran like this against a 6144M cap for 37775 seconds), recorded as `memory-cap-hit` and requeued at 1.5 times the cap; both hosts are judged by the same code, this host reading the outer scope's `memory.current` and the second host reading the `MULTI_HOST_RUN_PEER_MEMORY` line that `multi-host-run.sh` prints every round (that line, like `MULTI_HOST_RUN_PEER_CPU`, does not count as the log growing). Gates under `.claude/gate.d/` can be sent to the second host (it runs this same shared tree); a task with a verdict library whose row in the registry `.claude/gate.d/verdict-library-scripts.tsv` does not yet say prune-server in the third column is refused at submission ("## How to submit" below). `/health` only probes a database write and the queue thread's heartbeat; whether the head fits but has not started is worked out by the queue thread on every pass and `/health` only reads it.

Two-hour reminder: except for the commit-time gates, when a task's attempts have been running for 120 minutes in total (queueing does not count; an attempt that hit its memory cap and was retried one size up resets the clock, so counting starts again from the attempt after the latest cap hit, however many there were; each shard counts on its own), the service neither stops nor changes the task; it records the reminder that needs handling `long-run-unconfirmed`. The message to the session gives the command, the scope declaration, the total and per-attempt durations and the last log lines, and asks it to check two things: is the scope right (name the scope — `--item`, fewer `--check` cells, named test targets; give a patch directory; or let the service shard; whole runs wait for commit time), and does this task really need that long. If the scope is wrong, `task-server/task cancel <number>`, fix the scope and resubmit; if the scope is right and the task really needs that long, confirm with the full line from the message, `task-server/task confirm <number> --why '<why it needs that long and why the scope is what it is>'`: `--why` needs at least 12 characters once whitespace is removed, only the submitting session may confirm, and only a running task past two hours can be confirmed (anything else exits 3). A confirmed task is flagged, `task status`, the list, messages and the log head print a line 「长跑已确认：<why>」, there are no further reminders, and every other rule still applies. An unconfirmed task is reminded again after 30 minutes and at each doubling after that, and keeps running. A task with no session (manual `--manual`) gets no message; the reminder goes to the task log and the 「长跑待确认」 line of `status`, and it can be confirmed the same way. The only tasks not reminded are commit-time gates submitted with `--full-gate`: one of the six commit-time gates (`crash-point-replay`, qemu-device-streams, lkmm, crates-mutation-replay, formal-verification, broad-mutation), the full crash amplification (`scripts/crash/crash-amplification.sh`) or `scripts/gate/gate-staged.sh`, without `--check` or `--item`, and not a query-only form either (`--selftest`, `--list`, `--list-items`, `--help` and the like, `query_only_entry` in `task_server_lib.py`); gates with `--check`, `merge-and-verify`, entry scripts and experiments are reminded.

Four-hour hard limit (anomaly table `over-four-hours`, action: bounce, exit 229): everything except `--full-gate` is judged, and neither `--why` nor 「长跑已确认」 gets past it. Time is added up as in the previous paragraph (queueing does not count; a memory cap hit that was retried resets the clock); at 14400 seconds the service stops this attempt, does not requeue, records the outcome `over-four-hours` and sends it to the session that submitted it; tasks already running when the service restarts are judged the same way. The way out is to split the item that ran too long as `.claude/rules/long-run-split.md` "how to do it" says (shrinking the domain or naming fewer items is not a split), then resubmit with `task-server/task submit`. Sharded tasks: the plan, each shard and the merge each count their own attempts, and the whole has no wall clock of its own (time spent while shards are queued one after another counts against nobody). A shard that reaches the limit is stopped alone and gets this outcome; its siblings stay queued and keep running, and once all have finished the whole ends with that shard's outcome, with no merge. A command that modifies the main workspace is stopped too, and `workspace-write-interrupted` asks the session to check what it left.

Submitting by hand: outside a Claude Code session, write `task-server/task submit --manual -- <command…>`. The inbox address is not read, the task is recorded with no session, the service pushes neither outcomes nor reminders, and the outcome is fetched with `task-server/task wait <id>`; for a task judged long, confirmation works as usual. The service reads the session from the process tree: `--manual` inside a session is refused (`manual-from-session`), and so is no session without `--manual` (`sessionless-unmarked`); an inbox address in the environment does not count.

Whole-package tests need a confirmation flag: `cargo test` that names no `--test`, no `--bin` and no `--lib` with a test name, or carries `--lib --tests` or `--workspace`; `.claude/gate.d/crash-point-replay.sh` whose `--check` names feature-gated-tests, product-gpu-real-card-tests, or crash-case-replay without `--crash-cases-only` (any one cell or several count; `--check crash-case-replay --crash-cases-only --item crash-case:<name>` judges only the named crash enumeration cases and does not count); `scripts/gate/merge-and-verify.sh` without a patch directory or with `--all-packages` — these are whole-package tests. Unscoped runs need the same flag (commit-time gates have their own `--full-gate` rule, below): the six commit-time gates and `gate-staged.sh` without `--check` or `--item`, `scripts/crash/crash-point-replay.sh` and `scripts/crash/crash-amplification.sh` without `--item`, and `scripts/experiment-apparatus/replay.sh` without an experiment number (the table is `UNSCOPED_RUN_ENTRIES` in `task_server_lib.py`); unscoped runs belong to commit time, and running one outside it needs the user's go-ahead first. Both kinds are refused at submit time (exit 3, anomaly table `whole-package-unconfirmed`) unless submitted with `task submit --whole-package-confirmed <confirmation file>`; commit-time gates (the six gates, the full crash amplification and `gate-staged.sh`, without `--check` or `--item`) skip the confirmation flag: they are submitted with `--full-gate`, and one without it is refused on the spot (exit 3), which the confirmation flag cannot stand in for. Every submit-time refusal is judged in one place, the service's `submit_refusal`; when the service starts it rechecks queued and awaiting tasks against the same list, and a task that fails is recorded as `resubmit-required` and pushed to the session that submitted it. The confirmation file holds the three confirmations of `.claude/agent-common.md` 「日常开发的测试不跑整个包」 (① the files and functions changed, ② the test targets and functions that reach them, with the grep hits, ③ why naming ② is not enough), lives under a shared root and is given as an absolute path; the service checks only its form (readable, all three sections present, each at least 12 characters without whitespace) and refuses with exit 3 naming the missing section otherwise. Once accepted, `task status`, the list, messages and the log head print a line 「整包已确认：<file>」; the flag does not exempt the task from the two-hour reminder.

Starting tests and verification must name what to run (anomaly table `unnamed-run`, refused at submit time, exit 3): for the submitted command and every command in command position inside `bash -c`, `cargo test` must carry `--exact` and full test names after `--` (`cargo test -p <package> --test <target> -- <full test name> --exact`; naming only a `--test` target or giving only a filter word does not count); `scripts/gate/merge-and-verify.sh`, `scripts/crash/crash-point-replay.sh` and `scripts/crash/crash-amplification.sh` must carry `--item`; `scripts/mutation/prove-red.sh` must name mutations after `--copy <copy> <crate>`; a gate stage under `.claude/gate.d/` must carry `--item`, or use `--check` only on cells that start no tests (the cells that start tests are listed by hand in `TEST_STARTING_GATE_CELLS` in `task_server_lib.py`, and naming one of them needs `--item`; the cell-name tables in the stage file headers do not mark which cell starts tests, so the list cannot be read from them, and the self-test test-starting-cells-listed checks that every cell name in the list is in that stage's cell-name table); gate `crash-point-replay.sh` with `--item` also needs `--check` to leave out the cells that run the whole verification crate: naming crash enumeration cases is written `--check crash-case-replay --crash-cases-only --item crash-case:<case name>`, and without `--check` it still runs all nine cells and is refused; naming only `feature-gated:<file name>` without `--check` runs only the feature-gated-tests cell and builds only the named files, and is accepted. Query-only forms (`--list`, `--list-items`, `--selftest`, `--no-run`, `-- --list`) are not judged; nor is a submission with `--full-gate` (the commit-time run) or `--whole-package-confirmed` (a whole-package confirmation file whose form has been checked). The refusal says which kind went unnamed and writes out this command in its named form. The criterion lives in one place (`unnamed_run_problem` in `task_server_lib.py`); the scope-declaration hook `.claude/hooks/run-scope-guard.sh` calls the same function before the command runs to judge what goes through `task submit`, and when the service starts it rechecks queued tasks against the same criterion.

Memory breakdown at the highest moment (task 10279 peaked at 45.46 GiB while the wrapper's reading of memory.stat at exit showed anon 311296: the process had been killed and the memory released): while the command runs, each round reads the scope's memory.current and, when it is above the highest so far, saves the anon, file, file_dirty, file_writeback and shmem of memory.stat (`attempt_runner.py` here, a per-round `MULTI_HOST_RUN_PEER_MEMORY_STAT` line from `multi-host-run.sh` for the second host); on a cap hit the service turns it into a sentence in that attempt's outcome note and in the message to the session, saying it is the highest moment and whether the bulk was the process's own memory (anon) or page cache (file, including dirty pages not yet written back); it only records, the judgement is unchanged. Both hosts use the same peak: the larger of the per-round process memory and the value the memory wrapper hands over at exit (page cache excluded, sampled every 0.1 seconds); on the second host a missing exit value is recorded as not measured and stays out of quotas (the task 10045 family recorded the shell's 18 MiB on every second-host run while this host measured 556 MiB). A task bounced after repeated cap hits (`memory-cap-at-maximum`, or `memory-cap-hit` after 16 retries) whose outcome attempts end with at least two cap hits in a row also carries `loop_leak=` in the `wait` reason line, and the outcome message to the session puts 「检查代码有没有逻辑循环或内存泄漏：…」 on a line of its own: the two kinds to look for (logic loops: infinite loops, unbounded recursion, adding to the same collection over and over, rereading everything every round; memory leaks: caches or tables that only grow, reading a large file or the whole result into memory at once, large objects never released), and the basis: the cap and peak of every attempt in turn, whether each peak is larger than the one before, whether every attempt reached 98% of its cap, and the memory breakdown at the moment of the last cap hit (heap or page cache). A task that hit the cap only once, or was bounced at queue time without ever starting, does not carry it.

Ordering of a whole-task cancel: when a sharded task is cancelled as a whole, after stopping the units of its running children the service waits until each of them has an outcome in the database (the same wait as for a non-sharded cancel); only then does it record `cancelled` for the whole task, remove the artifacts and reply that it stopped; children that do not settle in time get a 500 that names them. An attempt that has ended in the database is never written back as running from a copy read earlier. The pre-launch recheck judges the host it re-reads the same way the queue pass does (disk floor, build-directory disk use, the second host's NFS mount), and the result replaces that host in this pass's resource view. Stopping for a stall stops only the attempt that was judged; a retry started in the meantime is not affected. Recovery of the second host's cleanup (`multi-host-run.sh --recover-cleanup`) runs at most once at a time per attempt.

Queue reasons are written per host: what a queued task is waiting for (`waiting: …` in `task status`, which is also the basis of the queued-too-long reminder) is one sentence per host, starting with the host name, and the sentence names what blocks that host: memory, build directory disk use, a full build directory pool, the CPU gate (including that host's core count or load being unreadable), disk pressure (for tasks that compile: that host's `/proc/pressure/io` full avg300 is above `TASK_SERVER_IO_PRESSURE_LIMIT` in the multi-host configuration; without that key nothing is judged, and each host is read on its own), the slice backstop (that host's measured slice room below 4 GiB or too small for this task's predicted peak), the pinned cap, or the host being unavailable right now; a sentence that gives only numbers and leaves the reader to work out which one blocks does not count. The note of a task returned as a whole (`never-fits`, `run-condition-unmet`) likewise carries the host name for each host.

The grounds for handling are read from the database: the grounds that reminders, confirmations, "run anyway" and returns rely on (which kind was reported, up to which reminder threshold, whether it was confirmed, whether "run anyway" was recorded) are written into the service's database and judged from that copy; the service process keeps in memory only what this pass computes and what can be recomputed from the database and fresh readings after the service is replaced. When the service stops and starts again, queued and running tasks are recognized from the database: the same threshold is not reported again, confirmed tasks and tasks recorded as "run anyway" are not pushed again, and `confirm --why` still accepts reminders that were already reported. The scheduler's own judgements (how many times a stray process outside tasks was reported, how many rounds a shard plan failed to advance) are persisted the same way: one row per item named `restart-surviving:<name>` in the database meta table, signed; the service reads them back on start, does not adopt a copy whose signature fails, records `record-tampered` and starts from empty.

**Refinements to booking and judging.**

- A running attempt's memory booking: for its first 2 minutes it is booked at its full cap (how high it will climb has not been measured yet), and after that at the scope's actual usage read this round (no more than the cap): after a compile spike falls back, the booking follows it down.
- Booking audit: every minute the service compares, per host, "the sum of the memory bookings of the running attempts" with the audit baseline (the sum of what the scopes cannot give back); when the bookings are at least 3 times the baseline and exceed it by 8 GiB or more for 3 rounds in a row it judges "booking drift" (what is left over comes only from the attempts whose scope is missing from the report and that are booked at their whole cap), lists for every attempt how much it books, how much it really holds and whether the booking is taken from the measured use, the cap the measured use has reached, or the whole cap for a missing scope, writes it into the `booking_drift` field of `/health` and the output of `control check`, and pushes it to the sessions of the queued tasks it blocks (once on the spot, then once more each time the duration doubles). It only reports; it stops no task.
- Submission trace: for every submission the service prints one line "提交进出" to its log when it replies: when it was received, whether it was accepted or refused, and how many seconds after receipt each step finished (entering a worker thread, the submission refusals, the session, the task itself, the database write, the submission warnings, the confirmation sheet, the reply); a step that alone takes 5 seconds or more gets one more line on the spot. When `task submit` gives up after waiting 30 seconds for the reply and exits 78, these lines show which step was slow.
- A stopped unit frees its booking first: from the moment the readback shows the unit stopped (`is-active` not running and `cgroup.procs` empty; an unreadable state does not count as stopped) the attempt no longer counts in the CPU and memory booking of running attempts, while the wrap-up (deleting directories, taking the peak, recording the outcome) is finished as before.
- The CPU load in a queueing reason is written as "load N (of which M threads waiting on IO)"; the gate judges as before.
- The `fills-any-cap` reminder does not count runs whose cap was set from the recorded peaks (the attempt's `prediction` field is `record`).
- Whole-machine memory line: when both the share of available memory and the share of free swap on a host are below 12% (earlyoom kills processes only when both are below 10%), no new task is dispatched to that host in this round and the queue reason gives both shares; only new dispatch is held, running tasks are not stopped.
- Killed by a TERM or KILL the service did not send (earlyoom, kernel OOM): when the command exits non-zero, the service sent no stop signal for this attempt, and the earlyoom or kernel log of that host in the same period names a process id from this attempt's process tree, the outcome is `killed-externally` (exit 228) and it is requeued under the same cap at most 2 times; the service cannot get process ids on the second host, so `scripts/hosts/multi-host-run.sh` records the process ids of the run's process tree on the second host, and when the command exits non-zero it reads that host's earlyoom and kernel logs and, if one of the ids is named, prints one line `MULTI_HOST_RUN_PEER_EXTERNAL_KILL source=<earlyoom|kernel> pid=<id> line=<log line>`; the service reads that line, records `killed-externally` and requeues under the same cap as for the local host; without the line the outcome stays `command-failed`. A kernel line reading "Memory cgroup out of memory" (some memory cgroup reached its own limit, for example a small cgroup the command itself set up for a process to hit; not the whole machine running short) does not count as external on either host: on the second host `multi-host-run.sh` skips such a line and does not print `MULTI_HOST_RUN_PEER_EXTERNAL_KILL` for it (it looks on for another line), the service also tells the two kinds apart by the content of `line=`, and the attempt is judged the usual way (the command's own non-zero exit, or a cap hit when this attempt's own scope hit its cap).
- `python3 task-server/control bookings`: read-only, lists per host and per running attempt the cap, current usage, the amount booked and why, with the host's total, the amount still fitting by the formula (total × 1.5 minus the margin minus the summed bookings) and the measured slice room on the last line (reads the `booking_ledger` field of `/health`, does not contact the second host).
- `python3 task-server/control key-stats [--since <time>] [--dump <file>]`: read-only (the database is opened read-only, so it works while the service runs). The statistics take only ended attempts that have a command key and whose peak metric is the current one (the same test the cap setting uses), and the first line gives the row counts before and after filtering; alternation and "hit the cap, latest task succeeded" are counted by task (the attempts of one task fold into one, marked by the outcome of its first attempt), and alternation by attempt is reported on a separate line. `--since` takes only attempts started at or after that time (epoch seconds, or `YYYY-MM-DD` for the start of that day, with dates as `time.gmtime` counts them). `--dump <file>` writes the ended attempts as jsonl, one per line (columns `id`, `task_id`, `number`, `command_key`, `command`, `started_at`, `ended_at`, `outcome`, `exit_code`, `memory_cap`, `memory_peak`, `peak_metric`, `stalled_at_cap`, `prediction`, `shard_count`, `host`, `item_plan`, null when absent); the file is created exclusively, and an existing file is refused with exit 2.
- When the CPU gate counts threads for a new task from the recorded cores of its history, runs where the command itself exited non-zero but ran to the end also count (stopped, cap-hit and signal-killed runs do not).
- `task-server/task promote <number>` (a hook pops up a dialog for the user to confirm before that client command runs): only the session that submitted the task may do it, and the task must be queued or be a sharded parent whose shards have been confirmed; a promoted task goes first, is not counted against the aged limit, does not hold back the tasks behind it when it cannot start (those behind it are not judged by the cutting-in rule), and skips the CPU gate (it starts once its memory fits); a sharded parent is promoted together with the subtasks queued right now, and the plan, shards and merge created later are promoted too; a pass runs right after the change.
- When a session is let through during a pause, the queue positions of queued tasks are computed over the whole queue, and the queued tasks of other sessions keep their positions.
- When the second host's free disk is below the floor, a task whose record is larger than this host and that only the second host can hold stays queued until that disk frees up, and is not judged `never-fits`.
- When a database write transaction fails (disk full, IO error, busy), it is rolled back before the error is reported, the connection is not left inside the write transaction, and other threads can still write.
- While the second host is in the cool-down after its last failed read, cleanup, the process check, build directory removal and the idle pass do not connect to it and handle it as "unreachable" on the spot; when the server stops, it also waits for the second host's free-room probe thread to exit.
- When the command cannot start (the first argv entry does not exist or is not executable), it is recorded as the command itself exiting 127 or 126, not as `launcher-lost`; after the command exits, the server's layer takes one more CPU and thread sample.

## NFS share

**Why it is needed.** The principle: “All scripts must run on multiple hosts. The results they produce must be readable from every host. If that cannot be done, either copy the resources or share the files.” NFS is the share-the-files route: this host exports some directories, the second host mounts them at the same absolute paths, so a result written on one host is read directly on the other, and a path a task refers to points at the same thing on both. The NFS configuration is written in this README and is also a checked item when the server starts. So the server does not set up NFS for the user: the configuration is a single key in the multi-host configuration `multi-host.env`, and the server does not start until it is set up.

**Which roots are shared.** Three: the repository itself (the root of the main work tree: the second host runs in this live tree, no tree is copied), the shared data root `~/.local/share/singlefs` (the work root and shard artifacts live under it) and the session transcript directory `~/.claude/projects`; each taken as this host's absolute path and mounted on the second host at the same absolute path (the second host's home directory may be another one; the mount points follow this host's paths).

**Export on this host.** Install `nfs-kernel-server` on this host, write one line per shared root in `/etc/exports`, exported only to the second host's address on the direct wired segment (the real address is a private value and is written only in that file on this host), then make the export take effect and enable it at boot:

```bash
# /etc/exports, one line per root
<root> <second host's address on the direct wired segment>(rw,sync,no_subtree_check)
sudo exportfs -ra
sudo systemctl enable --now nfs-server
```

**Mount on the second host.** Install `nfs-common` on the second host, create the directories at the same absolute paths as on this host, change the owner of the parent directory to the same uid as on this host, write one line per root in `/etc/fstab`, then have systemd reload and mount:

```bash
# /etc/fstab, one line per root
<this host's address on the direct wired segment>:<root> <root> nfs4 rw,hard,nofail,_netdev,x-systemd.automount,x-systemd.mount-timeout=30 0 0
sudo mkdir -p <root>
sudo systemctl daemon-reload
ls <root>                     # entering it triggers the automount
```

**Recovering by itself after this host reboots.** The fstab line carries `x-systemd.automount` and not `x-systemd.idle-timeout`. `x-systemd.automount` makes systemd put an automount point (an `.automount` unit) on the root, which does not fail together with the NFS mount itself: while this host reboots and the export is gone the mount unit may become `failed`, and the next time a process enters the root systemd starts the mount again, so once this host's `nfs-server` is back it mounts again without anyone running `reset-failed` and `start`. Without `x-systemd.idle-timeout` the mount stays once mounted and is not dropped when idle. `hard` (the NFS default) makes processes reading and writing during this host's reboot wait instead of failing. The server's mount check does not use `mountpoint -q` (an idle automount point is only an autofs placeholder there and `mountpoint -q` still exits 0); it runs `stat -f -c %T -- <root>/.` on the second host, which enters the directory and so triggers the mount, and passes only when it reads `nfs`. Once mounted, `git -C <repository root> rev-parse HEAD` on the second host reads the same commit as on this host: that is the repository root working.

**uid.** The user's uid and gid must be the same on both hosts; if they differ, add `all_squash,anonuid=<the user's uid on this host>,anongid=<the user's gid on this host>` inside the parentheses of the export entry, so that files the second host writes land owned by this host's user.

**Which keys in the multi-host configuration.** In `multi-host.env` at the repository root write three keys. First, `NFS_SHARED_ROOTS=<absolute path>[:<absolute path>…]`, the roots exported and mounted above (the repository itself, i.e. the root of the main work tree; the shared data root `~/.local/share/singlefs`, which holds the work root; the session transcript directory `~/.claude/projects`; each written as this host's absolute path): separated by colons, at least one segment, each segment starting with `/`, not ending with `/`, and containing no whitespace; write it even when `ENABLE_ACROSS_MACHINES` is 0. The template is `multi-host.env.example`, and no extra configuration file is added. The multi-host configuration check `scripts/crash/crash-point-replay-shard-configuration-check.sh` checks the form and, on this host, also checks that each segment is an existing directory; one that does not fit exits 1 and names which segment. Second, `SHARED_DATA_ROOT=<absolute path>`: the shared data root (the work root is under it), this host's absolute path, inside one segment of `NFS_SHARED_ROOTS`; the server takes it through `.claude/hooks/lib_work_root.py` (or `SINGLEFS_DATA_ROOT` when that is set in its environment), and `control install`, `start` and `check` look only at this line: missing or outside the shared roots exits 78 with the way out naming this line to add to `multi-host.env`; no default is filled in. Third, `HOSTS=<this host's IP> <second host's IP>`: each host's address on the wired direct link, separated by spaces; which one is this host is told from this host's interface addresses (`ip -o addr show`), the second host is the other one, ssh connects to it directly, and the user name comes from each host's `~/.ssh/config`. The second host's address is taken only through the shared helper `scripts/hosts/multi_host_addresses.py`, which gives an address only after the whole multi-host configuration passes its check: a missing key, a key the check does not know, or a malformed line yields no address, so the server does not start and `control start` exits 78. Values that differ between the hosts go into the three per-host keys `CARGO_BIN_DIRECTORY_BY_HOST`, `BUILD_ROOT_BY_HOST` and `SLICE_MEMORY_CAP_BY_HOST`: the value is space-separated `<address>=<value>` entries, each split at its first `=`, with exactly one entry for every host in `HOSTS` and every address in `HOSTS`; whoever needs a host's value takes the entry for that host's address. The server reads `SLICE_MEMORY_CAP_BY_HOST` (pinned caps) and treats a missing host or an address not in `HOSTS` as a malformed configuration. Each shard gets, through `TASK_SERVER_SHARD_HOST`, the `HOSTS` address of the host it runs on.

**What the server checks when it starts.** Four items; if any one fails the server does not start, exits 78, names the item and points to "## NFS share":

- configuration: `NFS_SHARED_ROOTS` is present and each segment is a directory on this host; `HOSTS` tells this host and the second host apart (the next two items reach the second host through it);
- export: every segment has an export line in `/var/lib/nfs/etab` on this host;
- mount: `stat -f -c %T -- <root>/.` reads `nfs` for every segment on the second host (entering it triggers the automount); one ssh timeout to the second host counts as "slow" first and enters a two-minute recheck period, rechecked every 5 seconds: a recheck that answers only records "slow" in the service log and in the `nfs` field of `/health` (`slow_last`), with no message and the second host still dispatched to, and only a recheck period that ends with no answer fails the item ("cannot reach the second host") and sends the message;
- read and write: a probe file is written in each direction and the other side can read it (written on this host and read on the second host, written on the second host and read on this host).

`task-server/control check` by default reads the latest result in the `nfs` field of the server's `/health` (its output says how long ago that was judged) and answers within seconds; `control check --probe [--limit <seconds>]` checks the four items afresh, printing a line when each item starts and when it ends, with a total time of at most `--limit` (60 seconds by default), and at the deadline it prints which item it is stuck on and exits 1; the `nfs` field of `/health` reports the same four items, but its "read and write" item (the probe in both directions) is the result of the probe made when the server came up and is not redone afterwards; after the server is up it rechecks only the first three, every minute, and when one starts failing it sends a message straight to every session with a task queued or running (see "## Messages to the session").

**When one fails.**

- Configuration fails: add the key or fix its form as in "Which key in the multi-host configuration", and create the directory first if it does not exist.
- Export fails: add the missing line to `/etc/exports` and run `sudo exportfs -ra`; if the NFS server is not running, run `sudo systemctl enable --now nfs-server`.
- Mount fails: on the second host add or fix the `/etc/fstab` line as written above and run `sudo systemctl daemon-reload`; if the mount unit has become `failed`, run `sudo systemctl reset-failed "$(systemd-escape -p --suffix=mount <root>)"` and then `ls <root>` to trigger the mount; if it will not mount, first check that the direct wired segment is up and that the client address exported to on this host is the second host's.
- Read and write fails: most likely the uid and gid differ between the two hosts, or the export entry lacks `rw`; follow the "uid" paragraph.

**How to check.** Three things, each run on the host its comment names:

```bash
stat -f -c %T -- <root>/.                   # run on the second host: printing nfs means the root is mounted
cat /var/lib/nfs/etab                       # run on this host: every root has an export line, and the client is the second host
echo probe > <root>/nfs-check-by-hand       # run on this host: written on this host
cat <root>/nfs-check-by-hand                # run on the second host: the second host reads probe
echo probe > <root>/nfs-check-peer          # run on the second host: written on the second host
cat <root>/nfs-check-peer                   # run on this host: this host reads probe
rm <root>/nfs-check-by-hand <root>/nfs-check-peer   # delete both files when done
```

## How to submit

```bash
task-server/task submit -- <command…>              # prints the task number; a task judged long also gets the confirmation sheet and awaits confirmation without being queued, any other task is queued at once and prints one line 「直接进队：…」 (queued directly: why it is not a long task); whitelisted variables in the environment such as SINGLEFS_RUN_SCOPE are carried; refused on the spot when the session's inbox address cannot be read
task-server/task submit --whole-package-confirmed <confirmation file> -- <command…>  # a whole-package test with the file of three confirmations ("Whole-package tests need a confirmation flag" above); without it the submit is refused
task-server/task confirm <number> --why '<…>'       # after checking the scope and duration from the two-hour reminder: the task really needs that long; no further reminders ("Two-hour reminder" above); it does not get past the four-hour hard limit ("Four-hour hard limit" above); a task with an open oversized-budget or fills-any-cap reminder whose scope was checked and really needs that much uses it too to record "run anyway" (regardless of the two-hour mark; after a service swap the kinds already reported still count), and that kind is not pushed again
task-server/task confirm <number> --items <N> --tasks <M>  # for a task judged long, confirm after checking the scope against the sheet: queued only when both numbers equal what the server counts right now (placed by submission time); a mismatch exits 3 and prints the server's sheet; a task that was queued directly is still recognised: the reply is 「已在队里，不用确认」 (already queued, no confirmation needed), exit 0, the two numbers are not checked
task-server/task wait <number>                      # fetch the outcome: exits on completion, last line TASK_SERVER_RESULT …, the exit code is the task's; a task that carries the session's inbox address need not be waited on to wake you (see "## Messages to the session")
task-server/task status [<number>]                  # this session's tasks awaiting confirmation, queued, running, and finished-but-unclaimed; given a number, a task awaiting confirmation gets the sheet computed now; queued ones carry "waiting: …", running ones how long they have run and how long the log has not grown
task-server/task cancel <number>                    # only the submitting session; once the stop is read back, the same cancel removes this task's scene and prints how many it removed and their sizes before and after (a build directory in the local pool goes back to it and is not removed; a run sent to the second host and stopped midway has its build directory removed with it by `multi-host-run.sh`)
task-server/task log <number>                       # the log of the last attempt (last 200 lines; --all the whole log; --attempt <which> that attempt; exits 4 if the task or attempt is absent)
task-server/task clean <number>                     # removes a finished task's own failure scene (only the submitting session, only once it has an outcome; without SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1 the scene goes one hour after wait collects the outcome; the build directory belongs to the tree's pool and is not removed; a cancelled task does not need it)
```

Confirming a submission, long tasks only: of the tasks `task submit` accepts, only those the server judges long at submission first await confirmation (`awaiting-confirmation`): not queued, no subtask created, no attempt started. Four rules, tried in order, the first that matches counts: ① the longest of the last 5 completed runs recorded in the library under the same command key is over 1800 seconds; ② a whole run with no scope narrowing: the scope declaration kind is `whole`, or the command carries `--full-gate` or `--whole-package-confirmed`; ③ the service will split it into shards; ④ the command key has no duration record and the command is a compiling `cargo test` or a gate run item by item (it names `--item`). Everything else is queued directly with no confirmation sheet: the control commands and scripts of the three services, `scripts/gate/hook-swap.py`, single gate cells (`--check`), `--selftest` of any script, small `.sh` and Python scripts, and any command whose recorded durations are all within 1800 seconds; the submit output carries one line `直接进队：<why it is not a long task>`, and `task confirm` still recognises such a task: the reply is 「已在队里，不用确认」, exit 0. For a task judged long, standard output then carries the confirmation sheet the server returns: the whole command, the reason it was judged long (which key recorded how long, or a whole run, or shards, or compiling with no record), the four segments of `SINGLEFS_RUN_SCOPE` as written, the number of items N the server reads from the command (each `--item`, each cell of `--check`, each named `--test`, `--bin`, `--lib` and each test name after `--exact`; when none is named, whole-package tests, gates and entries without a selecting argument and other cargo commands say 「整包、不指定范围」 (whole package, unscoped run), and anything else says 「范围由脚本里面定，服务算不出」 (the script decides the scope; the service cannot count it)), the crash cases and domain (the number of `crash-case:` items named in the command and the value of `--crash-expand-up-to`; `merge-and-verify.sh` and `crash-point-replay.sh` with neither in the command say 「范围由脚本里面定，服务算不出」), the number M of this session's tasks queued or running right now with the numbers of those that share the command key or name an overlapping item, the predicted memory and where it comes from, and the anomalies already visible at submission (a budget close to a whole host, parallelism set by the given cap, each with its suggested change), ending with the line `TASK_SERVER confirm-needed task=<number> items=<N> tasks=<M> timeout=<seconds>`. Once the scope checks out, write `task-server/task confirm <number> --items <N> --tasks <M>`: the task is queued only when both numbers equal what the server counts right now, and it keeps the number it got at submission, which fixes its place; a mismatch exits 3 and prints the sheet as the server counts it now (the numbers change when another task of the same session starts or finishes in between). A sharded parent is confirmed once; its subtasks are created by the server and need no confirmation. A task not confirmed within 30 minutes is cancelled by the server (outcome `cancelled`, the note starting 「没确认，已取消」) and the outcome is sent to the session. Only the submitting session can confirm; subagents submit no tasks and confirm none.

Cancelled tasks leave nothing behind (the user: "取消的任务要自己删掉产物 不要残留", "这个加入流程中 让task server去做"): once `task cancel` reads back that the unit has stopped, the server removes, in the same cancel, the scene directory of every attempt of this task (for a sharded task, its children's too), even with `SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1` set (the build directory belongs to the tree's pool and goes back to it, not removed); for an attempt sent to the second host, the second host's local `builds/<label>/` and the process id, exit code and output files under `runs/` are removed by step ⑥ of `multi-host-run.sh`, which the server recognises from the line it writes into that attempt's log, "⑥ 删了第二台这一趟的本地目录 …（回读不在了）"; without that line, a cleanup receipt still at `not-started` and no line in the log that is only written after that run's local directory exists mean it was never created, which does not count as left behind; when that run reused a directory of the pool, `multi-host-run.sh` removes it as well because the command never reached an exit code, and the server drops it from the pool when it settles the attempt. The sizes before and after are printed one by one in the output of `cancel` and written into the log of the task's last attempt (the copy on the second host's local disk cannot be measured from the server's side, and that is written as such); something counts as removed only once reading it back shows it gone, and anything not removed is named one by one and `cancel` exits 5.

Warning at submission (the user: "绕过的 那个要做成提醒 谁做错了严厉警告"): the task is accepted and runs as usual, and the server warns on the spot, in the submit reply (the client prints it to standard error), in the log header of every attempt of the task and in `status`. The first line is "✗ 严厉警告：会话 <number> 交的任务 <number> 绕过了服务给的编译目录，取仓根 target/ 下的二进制（…）…" (stern warning: the task submitted by session <number> bypasses the build directory the server gave and takes a binary under the repository root's target/), and the second line is "→ 怎么办：…". It judges: a word of the command that falls under the repository root's `target/`, or, in this repository's script that the command starts in command position, a path literal pointing at the repository root's `target/` (preceded by a repository-root variable, `$(dirname …)/../..` or `$(git rev-parse --show-toplevel)`, followed by `target/release/` or `target/debug/`; a bare one also counts when started at the repository root). The build directory the server gave, a `CARGO_TARGET_DIR` the caller gave, `target/` under scratch and temporary directories, comments, the break-switch branch and the selftest branch (started with `--selftest`, or a function body whose name contains selftest or ends with cells) do not count. The rule is in ② "提交时警告" ① of the header of `task_server.py`. The other kind (② in the same part): when the submitting session has tasks whose outcome has not reached it for 30 minutes (the server's message did not get through and no `wait` fetched it), the task is still accepted and run, and the same three places get two lines, first "✗ 严厉警告：会话 <id> 有 <N> 条任务跑完了没人取（<id>、…）：…", then "→ 怎么办：task-server/task wait <id> 取走（…）…"; tasks with no session (submitted by hand) are not judged.

`wait` itself reports the reminders that need handling, eighteen kinds in all (`ATTENTION_KINDS` in `task_server_lib.py`): a task queued too long (`queued-too-long`), after `QUEUE_ATTENTION_MINUTES` (30 minutes) in the queue; cleanup not finished (`cleanup-pending`), where the command has exited but the read-back still finds processes or cannot read (this host's unit and scope, the second host's cleanup receipt) and the server keeps the resource booking; a sharded parent that cannot advance (`shard-advance-failed`); a log that has not grown for long while the server keeps the task running (`quiet-log-busy`), after `QUIET_ATTENTION_MINUTES` (30 minutes) without growth while the server keeps it running because the CPU rises or cannot be read; a task whose log is flat but that is making progress is not reported: once the log has been flat for 10 minutes, the server reads every 5 minutes the files that the processes in this run's process tree have open for writing (the top-level log does not count; on both hosts; on the second host the same code runs over the same ssh channel), and a growing written file (such as a test process saving its output to `record.log` in the run directory) counts as progress; how long the log has been flat is counted from the latest reading that saw progress, and the running-progress line also says which file is growing; a task kept running because it waits on IO does not get this one, `io-wait` reports it; a task waiting on IO that the server keeps running (`io-wait`), when every poll while the log has not grown has found some process in state D for `IO_WAIT_ATTENTION_MINUTES` (30 minutes) in a row, with the latest count of processes in state D and this host's current some avg60 from `/proc/pressure/io` in the basis; a host that cannot read the unit state of a running attempt (`unit-unreadable`), after 60 seconds in a row of reconciliation without a reading and again each time that doubles, with its basis and way out under "Unit state unreadable" below; a task that ran past two hours without confirmation (`long-run-unconfirmed`), judged and confirmed as described in the "Two-hour reminder" paragraph above. Five more kinds are reported only for a task that already has an outcome: a command that writes the main working tree (`apply-writer-patch.py`, `hook-swap.py`, `stage-mine.py`) that ended by hitting its cap, being squeezed out, a failed second-host run, reaching the maximum, cancellation, being stopped as stalled, losing its launcher or being killed by a signal (`workspace-write-interrupted`) may have written only half, and `next=` names the files or patch directory to check (user: 「这个问题很严重 因为可能会导致补丁没有正常写入」); for `apply-writer-patch.py` with an outcome file `apply-outcome.tsv` the server judges by its `--read-outcome`, and a patch applied in full or rolled back is not reported, nor is one run with `--dry-run`; `hook-swap.py` is judged the same way by its `--read-outcome` (given its own `--root` and `--scratch`): a swap that finished or was rolled back is not reported, nor is an unfinished outcome that belongs to another hook swap in the same command (the reverse spec its output names lies under that swap's `--scratch`); the patch directory of a wrapped `apply-writer-patch.py` is worked out from the `cd` commands and assignments recognizable in that command, and a whole string with a `cd` inside a brace group or a heredoc body, or the one command in the string that carries its own `env -C`, counts as not worked out and is reported as possibly half-written; a hook swap (`scripts/gate/hook-swap.py` without `--feed-only`) that exits 7 (an earlier swap was left unfinished, so this one is refused and writes nothing) is reported to the blocked session (`workspace-write-blocked`, sent once); the same command exiting 9 (the earlier swap has not written its completion and the process that started it is still on this host, so another swap is refused and not one byte is written) or exiting 10 (the same `--scratch` is held by another swap, or a real swap of this repository is held by another swap, so no tree was built and no file was written; the service tells the two apart from the refusal in the last attempt's log and, when it recognizes neither, says either may apply) is reported to the blocked session (`previous-swap-running`, sent once), and the way out is to wait until that swap writes its completion (for exit 10, until it ends) and then submit the same command again unchanged, or, for exit 10 caused by a held scratch directory, to give a different `--scratch` when one of the two swaps is a `--dry-run` (this command itself, or the swap holding the directory) (a dry run does not hold the repository and a real swap holds it first, so two real swaps stay blocked by the repository even with different scratch directories; when the repository is held, a different scratch directory does not help); a task that ends with a run time over 7200 seconds and is not in `.claude/long-run-split-exempt` is reported as `long-run-split` (sent once, pointing to `.claude/rules/long-run-split.md`); a task whose last attempt's log has a line carrying the `NOT_RUN_NO_GPU_ADAPTER` marker (a case "not run this time": the judging stage did not execute and the case returned with a placeholder outcome while the test process still reports ok; the marker is a whole word, every occurrence in a line is recognized and counts as one case: preceded by the start of the line, whitespace or any other non-identifier character (only ASCII letters, digits and underscore count as identifier characters) and followed by whitespace (a tab included) or the end of the line, with ANSI colour codes removed first; a longer or shorter word does not count (the boundary and the cutting of a line into one piece per occurrence are imported from the gate library `scripts/gate/lib_libtest_result_lines.py`; only the name `NOT_RUN_NO_GPU_ADAPTER` is recognized here, other `NOT_RUN_` names only cut a line into pieces), and the case named is the one in that occurrence's own `test=` field, so two cases whose output was squeezed onto one line are counted once each; when the tests run without `--nocapture`, what passing tests print is swallowed by the test framework and never reaches the log, so the service cannot read this line and raises nothing: no reminder does not mean every case ran; a sharded task is judged shard by shard, a cancelled one is not judged) is reported as `gpu-cases-not-run` (sent once), and the outcome note gains a paragraph "N cases of this run were not run this time" naming each one (at most 8, the rest only as a count), with the way out saying these cases do not count as passed and that a conclusion needs a resubmission with the gpu feature or the conclusion of the GPU batch verification server; the exit code and the outcome kind follow the command, and a command that exits 0 is still a success; the marker lines are recognized in the pass in which the server already reads the log, with no second read. Five more kinds (user: 「既然加了给对应对话发消息的功能 就就该把异常和修改意见交给对应的对话」) only remind, the task keeps its place in the queue or keeps running, the basis gives the measured numbers and `next=` the suggested change: a budget close to a whole host (`oversized-budget`), when the queue judges that the task's booking on some host is at least that host's whole-task line (85% of its usable cap) and no more than the usable cap, with each host's booking, usable cap and where the booking comes from (how many recorded peaks, the default for no record, a pinned cap) in the basis; a pinned cap is reported too, and the suggestion is to check the scope, the sharding and how many run at once; the predicted peak, the cap and the booking are all cut to the usable cap of the host being judged (a pinned cap, a record, the default for no record and a retry after a cap hit alike), so a record larger than a whole host is never judged as never fitting: a host that can hold it gets it, and when no host can, it starts at the cut amount and is sent back as `memory-cap-at-maximum` only when it still hits the cap at the maximum; a long run with idle cores (`long-run-idle-cores`), when an attempt has run for 600 seconds and its average number of cores in use so far is below 24/31 of the threads it was given (below 24 cores for 31 threads); it is reported once per attempt and not sent again, the basis says 「给 31 线程、平均只用 x 核」, with the suggestion to check whether the resources are used sensibly, whether the script can run in parallel or in slices, and whether too many items were named; parallelism set by the given cap (`fills-any-cap`), when the last three completed runs of the same command key each peaked at least at 90% of their caps (attempts that hit the cap do not count: the peak of such an attempt sits at the cap anyway, and climbing the caps one step at a time is not parallelism set by the cap), with the suggestion 「这条命令按给的上限开并行，核实」; repeated cap hits while still being requeued (`repeated-cap-hits`), when the last three attempts of the same task all hit the memory cap and the service is still requeueing it at 1.5 times the cap; it is reported once per task (a fourth hit does not report again), the `wait` line also carries `loop_leak=` and the message to the session puts the 「检查代码有没有逻辑循环或内存泄漏：…」 paragraph on a line of its own (the second half of the 「Memory breakdown at a cap hit」 paragraph above), with the suggestion to check the code against that paragraph kind by kind: cancel and fix the code if there is a loop or a leak, leave it alone if the job really is that large; a thread total far over the registered count (`threads-over-registered`), when an attempt's total thread count is over twice its registered threads for three rounds in a row, its runnable threads are over the registered count as well, and the one process with the most threads is itself over twice the registered count, with the thread counts, the runnable count, the registered count and that process's name in the basis; a compiler or linker that starts many sleeping threads does not count, it is reported once per attempt and the task keeps running. How each kind (together with the submission refusals, the submission warnings, every outcome, a suspected stall and an unclaimed outcome) is judged, what action it takes, its suggested change and what happens when nobody handles it follow only its row in the anomaly table in the header of `task_server_lib.py`: the head of `next=` is that row's suggested change, naming what to check for that kind (for example `io-wait` checks that host's disk and NFS and `/proc/pressure/io`; `cleanup-pending` checks the command lines left behind and whether the script exits without waiting for its children), followed by this occurrence's numbers. The server records these for the task (and its subtasks, for a sharded one) as "needs handling" reminders. A `task wait <number>` that is waiting for the task prints one line `TASK_SERVER_ATTENTION task=<number> type=needs-attention kind=<kind> [reminded_after_seconds=<seconds>] basis=<the numbers it rests on> why=<reason> next=<way out>` on reading a new reminder (a `why=` longer than 300 characters is cut to that length and ends in "…"; the full text is in the "原因：" line of the message the server sends to the session), then exits 230: the task is still queued or running and the server did not touch it; handle it as `next=` says and start `wait` again to keep waiting. For a task that already has an outcome (such as a main-working-tree write that did not end normally) the line is printed before `TASK_SERVER_REASON` and the exit code stays the task's. The same reminder of the same kind for the same task wakes the caller only once per reminder threshold, so restarting `wait` does not repeat it; it fires again only at the next threshold (twice, four times the starting one, and so on), and the kinds judged by time write `reminded_after_seconds=<the threshold reached this time, in seconds>` after `kind=`. The thresholds already reported are stored in the server's database, so after a restart the server reads them back and does not report the same threshold again; a task queued too long whose waiting reason has not been judged yet (the server has just restarted and this round has not reached it) is not reported in that round, only in the round that judges the reason. One more kind, `booking-beyond-idle-machine` (cannot start on any host): when the queue judges that a command does not fit on any host right now and would still not fit even after every task the server runs on that host has finished and released its memory (typically a booking at the usable cap, or a pinned cap), it only reminds and keeps the task queued; the basis says, host by host, what is still missing after that release, and the suggestion is to check why the cap sits at a whole host (for a pinned cap, look at the pinned value and the multi-host configuration, and unpin it if that much is not needed); it is sent once. The booking of such a task is usually also at or above the whole-host line (`oversized-budget`), but the task cannot start and "run it as is" is no way out, so while this kind is open `oversized-budget` is not reported for it as well (nor for a queued task the queue pass has not yet judged for "cannot start on any host", so a notice found at submission never goes out ahead of this kind); it is reported once the task can start. Such a task does not count as "queued ahead and not yet started" and does not block the tasks behind it even after the aging limit; it starts by itself once the machine's free memory is enough. The server also sends these reminders straight to the submitting session (see "## Messages to the session"), keeping one account with `wait`: what was sent is not reported by `wait` again, and what `wait` reported is not sent. Server health is not `wait`'s business: the server watches itself and sends messages the same way.

Do not wrap commands or pass resource arguments: `run-with-memory-cap.sh <cap>`, `host-dispatch.py … --`, `multi-host-run.sh … --`, `nice`, `timeout`, `capped.sh`, `two-logs.sh`, `gpu-quiesce-run.sh` and the scripts' own `--memory`, `--memory-cap`, `--threads`, `--peer`, `--local-only`, `SINGLEFS_THREAD_CAP`: the server does these, and writing them is refused on the spot, naming which one to remove. Environment variables outside the whitelist are refused on the spot and named; a command that really needs one is written as `task-server/task submit -- env <name>=<value> <command…>`. Retired variables (`SINGLEFS_HEAVY_TESTS`, `GATE_MUTATION_START_OVER`) are refused on the spot whether set in the environment or written in the command (a `name=value` after `env` or in front of the command); the refusal names it and gives the way out; the list is `RETIRED_VARIABLES` in `task_server_lib.py`.

Three kinds that could not be sent to the second host are refused at submission (user: 「改成提交时当场拒（推荐）：不再悄悄改派本机：碰到这三种就在提交时报错、点名是哪个路径或哪一族、出路写怎么改，任务不跑。」): `task submit` exits 3 and prints the sentence and the way out; the task is not queued and does not run. First, an absolute path in the working directory or the command (only whole shell words count: a word that starts with `/`, the value of `name=absolute path` or `--option=absolute path`, and each shell word of a `bash -c` script once the script is split into shell words; a `/` in the middle of any other word, such as 「（接的是 /）」 inside an argument value, does not count) that lies under no segment of the multi-host configuration's `NFS_SHARED_ROOTS`: the sentence names that path and the way out is to move it under one of the segments; system paths that are the same on both hosts such as `/dev/null`, `/usr/` and `/bin/` do not count; a path under `/tmp` is refused the same way, and the sentence adds that a reboot clears `/tmp`. Second, a `SINGLEFS_DATA_ROOT` or `SINGLEFS_WORK_ROOT` handed to the command that is not under a shared root: the sentence names the variable and its value, and the way out is to set up the multi-host configuration. Third, a command that points at a row with a verdict library in the registry `.claude/gate.d/verdict-library-scripts.tsv` whose third column does not yet say `prune-server`: the sentence names that family, and the way out is to move that family onto prune-server and turn the third column into `prune-server`; a registry that cannot be read or is malformed is refused the same way.

The temporary prune-server wrapper (`python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <path>] -- <original command>`) is only for script self-tests: when the original command unwrapped from it contains a cargo that compiles (recognized the same way the service decides the build directory), it is refused at submission in the same form as above: `task submit` exits 3 and prints the sentence (naming the original command) and the way out (submit again without the wrapper); the task is not queued and does not run. Unwrapping is only for judging; an accepted command still runs whole, wrapper included; the build directory is given only for the outer command, and the service does not unwrap to accommodate it. A wrapper without `--server-binary` (and without `PRUNE_SERVER_BINARY` in the assignments before the command or in the task environment) has to compile prune-server itself in the build directory the service gives, so the service counts the outer command as one that compiles: both hosts are given a build directory; with `--server-binary` nothing is compiled and none is given. The `cargo test` of the verification crate runs against the real service and is not wrapped this way.

A whole-workspace build that names no package is refused at submission (user: 「8105打回 让他重新写重新确认范围」; task 8105, `cargo build --offline --all-targets` without `-p`, was predicted at 49.0 GiB): a compiling cargo started directly at command position in the submitted command (`build`, `check`, `clippy`, `test`, `run`, `bench`, `doc` and their one-letter aliases; `bash -c` and `cd` are followed) is refused when it carries `--workspace` / `--all`; one without `-p` / `--package` is refused when cargo's manifest lookup (the first `Cargo.toml` from the starting directory upward) lands on a virtual manifest (only `[workspace]`, no `[package]`, as the repository root's is), and equally when the starting directory cannot be told or the manifest cannot be read. `task submit` exits 3 and prints the sentence (which cargo, started in which directory, under which manifest) and the way out: name the package to build, `-p <package>` (the verification crate is `-p singlefs-verification`); whole-repository runs go through `scripts/gate/merge-and-verify.sh` or the gate at commit time. One that lands on a package's own manifest (packages that are their own workspace such as `scripts/experiment-apparatus/` and `prune-server/`, or started inside a member's directory) builds only that package and is accepted; cargo started inside entry scripts and gates is not judged (the service only looks at the submitted command); `cargo fmt`, `metadata`, `tree` and `clean` do not compile and are not judged.

## Messages to the session

The user: 「不是你通知 而是 task-server 通知发起的对话」「包括报错 长时间没有响应 都可以这样通知」. `task submit` runs in the session's Bash, reads `CLAUDE_CODE_MESSAGING_SOCKET` (the session's inbox socket) and `CLAUDE_CODE_MESSAGING_TOKEN` (the session token) from the environment and hands them to the server with the task; the server keeps them on the task, and the token goes into no log, no `status` and no reply of `/tasks/<id>`. When they cannot be read the submission is refused on the spot (exit 3), and the way out is to submit from the Bash of a Claude Code session (subagents submit no tasks). The inbox socket is not the one recorded at submission: before each message the server reads the session registry (`~/.claude/sessions/*.json`, one file per process, reading only `sessionId`, `messagingSocketPath` and `pid`) by the session id recorded on the task and takes the `messagingSocketPath` of the latest-started file whose session id matches and whose process is still alive; the token is the one given at submission. A session restarted with a new socket gets the message on the new one; when none is found (the session is closed) the server writes the alert described under "cannot be sent" below.

The server sends one message to that socket on each of these:

- The task has an outcome (every kind for which `wait` prints `TASK_SERVER_RESULT`): sent once; once it is sent the server records it as collected (as if `wait` had fetched it), and nothing is sent when the session already fetched it with `wait`.
- A reminder that needs handling (the eighteen kinds of `ATTENTION_KINDS` in the `task_server_lib.py` header) or a suspected stall: the same kind of reminder for the same task is sent once per threshold, on the same account as `wait`; that account is kept in the database (reminders that need handling on the task row; the segment of a suspected stall that was reported, the sessions each service-health problem was sent to and the threshold each booking drift was pushed to in the saved-across-restart records), so after a restart the same one is not sent again. When an outcome comes in with a recorded run time over 7200 seconds and the item is not in `.claude/long-run-split-exempt`, one `long-run-split` is sent (judged by the shard's or the whole task's run time), pointing to `.claude/rules/long-run-split.md`; when the hook swap exits 7 (blocked by an unfinished earlier swap), one `workspace-write-blocked` is sent to the blocked session. When an attempt's total thread count is over twice its registered threads for three rounds in a row and its runnable threads are over the registered count as well, one `threads-over-registered` is sent (the basis gives the thread counts, the registered count and the name of the process with the most threads; the task keeps running and is not stopped; a compiler or linker that starts many sleeping threads does not count). The kinds judged by time are sent again each time the time doubles; the kinds whose threshold does not grow with time (`oversized-budget`, `fills-any-cap`, `long-run-unconfirmed`, `cleanup-pending`, `shard-advance-failed`) are sent once more when they are still there 30 minutes after they were sent, and again each time that doubles; the first line says 「没处置、第 <回> 回再推」 and the body adds what was sent before and what is still missing now.
- An unclaimed outcome: when the outcome of a parent task has not reached the submitting session after 30 minutes (the message with the outcome did not arrive and no `wait` was started), it is sent again, and again each time that doubles, with the first line 「task-server：结局（任务已结束，这条结局还没人取）任务 <号> <中文名>（<种类>，退 <码>；第 <回> 回，上一回在 <日期>）」; once sent it is recorded as collected.
- A task not confirmed within 30 minutes and cancelled by the server: sent as its outcome, with 「没确认，已取消」 in the body.
- Runaway process outside tasks: both hosts are scanned every 5 minutes; a process outside the task slice with at least 30 minutes of accumulated CPU at half or more of its elapsed time is reported only to the session it belongs to, again every 30 minutes while it stays; a local process whose session is known and that is still there after two reports is stopped by pid and that session is told; when the originating session cannot be identified (on the second host, or after that session exited) it is terminated at once and only goes into the alerts; session processes and their ancestors, systemd units and system services, sshd and the editor are never touched.
- Server health: the database cannot be written, the dispatcher judged the head startable but kept failing to start it, the progress watch found room but nothing started, the server's unit is down, the first three NFS items fail, the second host has been unusable for 180 seconds, and when GPU is enabled, GPU server card failures and unjudgeable blocks (read at most once a minute via `python3 gpu-verification-server/control cards-failed`). It goes to every session with a task queued or running; the same thing goes to the same session once, and again only after it got well and broke again. GPU server card failures are keyed by host, server process, and card, with the next step asking the user to reset that card; unjudgeable blocks are grouped by host and stream (family plus stream-key prefix) without the process ID, the body reports how many blocks in that stream are currently unjudgeable and the leading block numbers, and the next step follows each block line's `claim=`: `released` or `not-held` means the claim was released and the other host will try, `kept` means the claim was not released and waits for the claim lease to expire, and unreadable or unrecognized values report "unrecognized GPU server card-failure line" without guessing. When an item is not seen in the current read, two cases are not treated as recovered: unjudgeable streams (the GPU server retries once after restart, and the same stream failing again is not re-sent) and a host with a failed card that has not had a successful read since `task-server` started (`cards-failed` reports `unreadable` or `unreachable`). Each alert item is written once in the alert record and is not rewritten after a `task-server` restart. When the server itself is down it cannot send: `task wait` exits with an error after 60 seconds without a connection, and `task submit` reports on the spot.

The first line of the body gives the class and the task's state right now, so the first line alone tells them apart: "task-server：结局（任务已结束）任务 <id> <Chinese name>（<kind>，退 <code>；第 1 回）", "task-server：提醒（任务还在排 / 还在跑，不是结局）任务 <id> <Chinese name>（<kind>；第 <n> 回，上一回在 <date>）", "task-server：疑似卡住（任务还在跑、服务没停它）任务 <id> 疑似卡住（suspected-stall，第 <segment> 段；第 1 回）", or "task-server：服务健康 <which one>"; every kind carries a Chinese name with the English kind name in parentheses, and a repeated message says which time it is and the date of the previous one. After it come the basis, the reason and the way out as `wait` prints them, with the lines of confirmation marks (such as the confirmed long run) after the basis and the way out, then the log, and last the line `wait` prints, verbatim: facts and ways out only. If it cannot be sent (the socket is gone, the connection fails, the session is closed) the server does not retry forever: it writes one `inbox-unreachable` alert into its log and the alert records, appends a line starting with `TASK_SERVER_INBOX` to the log of the task's latest attempt, and the task goes on. When the receiving session is idle Claude Code starts a new turn with the message; a session that skips permission prompts holds it until the user approves.

`task wait` stays: it still fetches outcomes and reminders, but a session no longer needs to start it to be woken. `task-server/control watch` is gone (it exits 2 with the way out); to check server health once by hand use `control check`.

Line format: first the line `{"type":"auth","token":"<session token>"}`, then the line `{"type":"user","message":{"role":"user","content":"<body>"}}`; both are ready before connecting and written in one go (Claude Code closes a connection that has not sent a complete line within 30 seconds). Source: the inbox socket and the auth line are in the Claude Code docs, https://code.claude.com/docs/en/cross-session-messaging.md, section "The session's inbox socket"; the docs page does not give the user line, which is taken from the example in the line "[uds-messaging] Inject messages" of the Claude Code binary's own debug log. Since the docs page does not give the line format, recheck it after upgrading Claude Code.

## Declarations in source headers

The server reads a few declaration lines in the first 60 lines of a source file to tell what a command needs; callers still write no budget. The session that owns the entry script or the package adds the declaration; the server only reads it:

| Where | How it is written | What the server does with it |
|---|---|---|
| entry script | `# task-server-shards: <argument>…`, `# task-server-resumable: <argument>…` | sharding and resuming (the "分片" and "续跑" parts of the `task_server_lib.py` header) |
| entry script | `# task-server-compiles: yes` | compiles: a gate entry whose cargo cannot be seen at the command level still gets a build directory as a compiling task (`CARGO_TARGET_DIR` on both hosts, one of the same tree's pool; a sharded plan, shards and merge follow the parent); any other word is bounced. A bare `--selftest`, or `--list-items` / `--help` / `-h`, does not count |

Card declarations (`# task-server-card-lease:`, `# task-server-gpu-cards:`, `# task-server-gpu-arguments:`) are not recognised: when the submitted command, or any command in command position inside `bash -c`, starts a script whose first 60 lines carry one of them, the submission is refused on the spot (`task submit` exits 3, anomaly-table row `card-declaration`); the note starts with 「卡归 GPU 批处理验证服务，任务不领卡」 (cards belong to the GPU batch verification server, tasks do not take cards), names the script and the declarations it carries, and the way out is to delete that line, turn the card-needing part into writing pending rows to the verdict library for the GPU server to judge (see "## Cards"), and submit again. The rule is `card_declaration_problem` in `task_server_lib.py`.

Memory quota (from the attempt records in the server's own database, the "资源记录" part of the `task_server_lib.py` header; this is the only rule, scripts and callers do not report memory and entry headers carry no memory declaration):
- When the database has completed attempts under the same command key (the same kind of command), the cap and the booking are the largest of the last 5 (the measured peak of a run that completed, the cap of one that hit it), not multiplied by 1.5; records of the parent task or of sibling shards of the same run are not borrowed (a shard's key carries its shard number but not the shard count: when the count changes the same shard number lands on the same key, but sizing reads only the records of runs with the same shard count). A key (with its shard count) that has no record of its own is sized like a command with no record; records of other keys are not borrowed. Options that only choose the range do not enter the key: `--item`, `--only`, `--skip`, `--exact`, `--fingerprint-of`, `--crash-expand-up-to` with their values, the test-name filters of `cargo test`, and the environment variables that name cells or items (`*_SELFTEST_CELLS`, `GATE_MUTATION_ROW_SELECTION`) are all dropped, so the same entry shares one record whether or not it names items and whichever it names; the `--item` named by two gate cells, code-tooling's break-switch-replay and crash-point-replay's crash-case-replay, still gets one key per item (`scripts/hosts/memory_peaks_lib.py` header "key" ③). The command word of a gate or entry script of this repository (those under `.claude/gate.d/`, `scripts/` and `.claude/scripts/`) enters the key as its path relative to the repository: written as an absolute path (the same file in the main work tree, a snapshot or a repository copy) or as a relative path, it lands on the same key (`repository_script_word` in `task_server_lib.py`); words in the command that do not start with `-` (the repository root and the like) enter the key after the options, so the root written before or after the options lands on the same key (`selection_class_words`). The key of the plan step of a sharded task also drops the assignment of the domain-shrinking variable `SINGLEFS_CRASH_AMPLIFICATION_EXPAND_UP_TO` (the shrink depth only changes how many crash states each shard judges; the plan step only builds and splits), while the shard keys still carry it. Scripts never report how much memory they need, and the service does not read such lines. `cargo test` with the same package, features and profile shares one key: the key keeps only the package (`-p`), the features (`--features`, `--all-features`, `--no-default-features`) and the profile (`--release`, `--profile`); the named test target (`--test`, `--lib`, `--bin`, `--example`, `--bench`) and the test filter after `--` are left out, so commands naming different targets start from the same record. The peaks measured by runs that were cancelled, that failed by themselves, or that were stopped as stalled or at four hours only count as a floor: they raise the start only when larger than the largest in the window, and with an empty window only when larger than 4G; smaller ones never lower it (the next run does not hit the low steps again). It goes both up and down: a cap just hit inside the window is seen at once, an older one that left the window no longer counts, and when the later runs are all small the start comes down with them. Without a completed attempt under this key it starts at 4G and is requeued × 1.5 after hitting the cap (4096M → 6144M → 9216M …), and a "how much I need" line printed by the command itself is never accepted. A command with real peak records is not raised to 4G; it only has a floor of 1 GiB: the recorded peak counts process memory only (`anon` plus `shmem`) while the cap also has to hold the page cache that reading files brings in, so neither a starting cap nor a requeued cap is below 1 GiB, and the booking follows that cap (a task running one python3 script that read a single file with a 5 MiB peak exited 250 at caps of 3M, 5M and 8M); a record above the floor is followed as it is; a pinned cap is not subject to the floor and stays as pinned even below it; the floor never exceeds the largest cap that host can give.
- On a requeue after hitting the cap, the requeued attempt first takes the build directory this task's previous attempt used on the same host and keeps building in it ("## Build directories" below); when the requeue moves to the other host, the previous one stays in the pool of the host it was on. Both hosts go through the same logic: on this host through `CARGO_TARGET_DIR`; on the second host with `--reuse-build-directory <that one's label>`.

## Build directories

Build directories are given per "which tree × which host" (the "编译目录" part of the `task_server_lib.py` header):
- The tree is the first level, going up from the task's `--cwd` after symbolic links are resolved, that has a `.git` (a repository copy is a git worktree, each one its own tree). Compiling tasks submitted one after another on the same tree on the same host keep using this tree's pool of build directories on that host, and cargo rebuilds only what changed by fingerprint; different trees each get their own pool and never share one (the two times different trees shared a build directory and copies kept old modification times so that cargo judged nothing needed rebuilding, sections fifty-two and sixty-nine of `records/2026-09-16-subagent拆分提案.md`).
- At most 3 per tree per host (`BUILD_POOL_SLOTS_PER_TREE` in `task_server.py`, set together with the build directory disk check): an attempt takes a free one and returns it when it is done; it first takes the one this task's previous attempt used on the same host, then the most recently used free one, and opens a new one only while the pool is not full; when all are taken and the pool is full the task waits, with the queue reason naming the full build directory pool. A newly opened one still has to pass the build directory disk check; when a directory of the pool is reused, that check subtracts the disk it already takes (recorded from the measured peak when each attempt settles) from this command's build directory disk peak.
- This host's are under `TASK_SERVER_BUILD_DIRECTORY`, named `tree-<first 8 hex digits of the sha256 of the tree path>-<6 random hex digits>` with no task number or attempt label (a directory in the pool is reused by later tasks, so a name carrying the number of the task that opened it would make `ps` show the wrong task); the second host's under `builds/` beneath its entry in the multi-host configuration's `BUILD_ROOT_BY_HOST` (kept by `multi-host-run.sh --keep-build-directory`, reused with `--reuse-build-directory`); the pools of the two hosts are independent.
- Removal: 「服务build之后必须删除历史」「自己用完自己删」 is counted per tree — when the tree (the first directory at or above `--cwd`, after resolving symbolic links, that has `.git`, or the resolved `--cwd` itself when none has) is deleted its whole pool goes with it. The server sweeps once when it starts and again in the background every 10 minutes; one with a process holding a file in it is not removed, an alert `build-directory-left` is written, and the next sweep tries again. Recording an outcome, `task clean` and a cancel do not remove the build directories in the local pool (a run sent to the second host that fails or is stopped midway has its build directory removed with it). The same sweep also removes directories under the local build root that are in no pool and are named `task-<library label>-<number>-<attempt>` (named after the attempt label); one with a process holding a file in it is not removed, an alert `build-directory-left` is written, and the next sweep tries again.
- A caller-supplied `CARGO_TARGET_DIR` outside the repository is used as given, not removed and not put in a pool; one pointing into the repository is refused at submission.

## Pause and resume

Jobs such as swapping the prune-server binary or clearing old rows in the verdict library need a window in which no other session's task is running, and the job itself often has to submit commands through `task submit`. `control stop` cannot give that: while the server is stopped nobody can submit, and a `task wait` that is already running exits 78 after 60 seconds. Use pause instead, and let the session that does the job through (its tasks still start while paused):

```bash
python3 task-server/control pause --reason "clear old verdict rows" --allow-session <the session doing the job>   # pause: other sessions' tasks do not start; the allowed session's tasks are queued and started as usual; submissions are still accepted, status / wait / log / cancel still answer
python3 task-server/control check                                                                                   # repeat until it prints "…、放行会话 <id>、在跑 N 个、别的会话在跑 0 个" (… allowed session <id>, N running, 0 running in other sessions)
# ...do the job that needs the window (the session doing the job submits its commands with task submit)...
python3 task-server/control resume                                                                                  # release: queued tasks start as usual, the allowance is cleared with it
```

- The id of the session doing the job: run `python3 task-server/task status` in that session and take the id from the first line, "会话 <id>：…" (it is the session the server recorded when the task was submitted, the same field `status` shows for every task). What is allowed is a session, not one command: tasks of that session that were already queued, submitted later, children of sharded tasks and retries that went back to the queue all start as usual; tasks of other sessions, and hand-submitted tasks that have no session, stay queued and unstarted. A queued task of the allowed session shows what it is really waiting for in `status`; a queued task of another session shows "在等：服务暂停中（原因：…）".
- `pause --allow-session <another session>` on an already paused server exits 0 and switches the allowed session (reason and start time unchanged); a `pause` without `--allow-session` leaves the allowance alone; `resume` clears the allowance with the pause. For a window in which no task at all is running: `pause` without `--allow-session` and wait until `control check` reports 0 running.
- While paused the scheduler starts no new attempt (except for the allowed session's): children of sharded tasks and retries that went back to the queue are all held. Running attempts run to their outcome (the outcome is still written and a retry still goes back to the queue, but is not started). `pause` and attempt start share one lock, so when `pause` exits 0 an attempt that was being started is already recorded and the running count of `control check` cannot be joined by another.
- The paused state, with the allowed session, is stored in the server's database (signed: a changed allowed session in the database counts as failing verification and allows nobody) and survives a server restart, allowance included, until `resume`; `pause` on an already paused server exits 0 and keeps the original reason and start time.
- `control check` prints one more line, "暂停中（原因：…，起于…）、在跑 N 个"; with a session allowed it reads "…、放行会话 <id>、在跑 N 个、别的会话在跑 M 个" (M is the running tasks that are not the allowed session's); it still exits 0 without judging "the dispatcher judged the head startable but did not start it" or watching progress; `/health` carries `paused` and `pause` (with `allow_session` and `other_running`) and `ok` is unchanged; a queued task's `status` shows "在等：服务暂停中（原因：…）".
- While paused the server keeps watching its own health (the database is writable, the unit is up, NFS, the second host) and still sends a message to every session with a task queued or running when something goes wrong.
- Only the user who runs the server may send `pause` and `resume`, checked like submit and cancel: the server compares the caller's uid with its own.
- Always `resume` when the job is done; a paused server looks healthy (`check` exits 0), so queued tasks would wait forever if you forget.

## Unit state unreadable

When reconciliation cannot read an attempt's unit state (`systemctl --user show` cannot start, times out or prints no `ActiveState`), the server cannot tell whether the unit is still there. An attempt that left `result.json` is settled by its exit code; one that did not is not killed, not settled and gets no outcome: the attempt stays `running`, there is no deadline after which it is settled, and the server checks without systemd whether the attempt still has processes: on this host, whether the runner process number recorded in the `started` marker is still in `/proc`, and whether `cgroup.procs` is empty for the unit's cgroup, for the cgroup named in the `scope` file that `attempt_runner` writes, and for memory-wrapper scopes whose processes carry this attempt's label; for an attempt sent to the second host whose cleanup receipt is still `pending`, the same code runs on the second host over the same ssh channel and reads the `runs/<label>.pid` and `runs/<label>.scope` that `multi-host-run.sh` records. Only when every cgroup reads as empty (a cgroup directory already removed counts as empty) and none of the recorded process numbers is alive, for a 10-second grace, is the attempt settled as having left no result and recorded as `launcher-lost`; if anything cannot be checked (a cgroup cannot be read, the `started` marker is missing, the cleanup receipt cannot be read, the second host cannot be reached), the server keeps waiting.

While the unit state stays unreadable: after 60 seconds in a row the session that submitted the task gets a `unit-unreadable` message (a reminder that needs handling; its basis names the host the attempt runs on, the unit whose state this host cannot read, and the process numbers and cgroups found), then again each time the time doubles, never twice for the same threshold; `/health` reports unhealthy, with `problem` naming the attempts whose unit state this host cannot read and the `unit_unreadable` field listing each one (processes still present, all gone, cannot be checked, first check not finished), and `control check` exits 78 on it. Once this host's user-level systemd is fixed the server judges as usual. The rules are under ① "读不到单元状态" in the `task_server.py` header.

## Cards

Cards belong to the GPU batch verification server (`gpu-verification-server/`, "卡只归 GPU 服务，任务不拿卡" in `.claude/rules/verification.md`): it opens the cards named in the multi-host configuration and keeps holding them, and quiescing before opening, checking the cards and judging all belong to it. This server schedules only CPU and memory: it does not tell from a command or script name who needs a card, and it does not assign, lease, quiesce or reclaim cards; placement looks only at memory, the CPU gate and build-directory disk use. The command it starts is not wrapped in a quiesce wrapper, and the card-choice variables in the server's own environment (`CARD_CHOICE_VARIABLES` in `task_server_lib.py`: `GPU_CARDS_BY_PRIORITY`, `CUDA_VISIBLE_DEVICES`) are not passed to the attempt. An entry whose header carries a card declaration is refused at submission ("## Declarations in source headers" above). The two servers connect only through the verdict library (the RocksDB of prune-server): tasks only record, write pending rows to the verdict library and read the conclusions. The rule is under "卡" in the `task_server.py` header.

## Self-test

`python3 task-server/task_server_lib.py --selftest`: each cell runs a real uvicorn on a temporary socket, with the memory wrapper, the second host and the systemctl used by `control` replaced by fake scripts and the attempt's scope by a fake directory; it does not compile, does not connect to the second host and does not use cards. It runs entirely in a simulated world, so the main agent starts it directly without queueing through the server (the hook list `MAIN_AGENT_TOOLS_RUN_DIRECTLY` in `.claude/hooks/lib_project_code_runs.py`); `TASK_SERVER_SELFTEST_CELLS=<cell,…>` runs only the named cells. The cells run in parallel as many at a time as the registered default of heavy-work threads per host (`scripts/hosts/heavy_threads.py`, read at the time); when that cannot be read (the registration file is missing or broken, or `SINGLEFS_THREAD_CAP` is not a positive integer) the whole run fails and does not fall back to the core count. The table of breakage switches `TASK_SERVER_BREAK=<item>` is in the `task_server_lib.py` file header.

Attempt units started by a self-test (and by its switch runs) stop with the outer task ("套在外层单元里的服务" under ③ in the `task_server.py` header): when the server runs in a self-test, or itself runs inside an attempt, it finds its own user-level unit from `/proc/self/cgroup` and starts every attempt unit with `BindsTo=` and `After=` that unit; once the outer task stops (cancelled, stopped as stalled, cap hit) systemd stops those attempt units right away instead of waiting for them to time out. Both hosts go through the same code. The real server (its own service unit) does not add them: attempt units must keep running across a server restart.
