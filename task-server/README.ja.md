# task-server

[中文](README.md) · [English](README.en.md) · **日本語**

異常終了後に残る資源の占有、リモートの後始末の受領確認と診断ログは[タスクの後始末と GPU フェーズのログ](cleanup-protocol.md)を参照。

singlefs の統一タスクサーバ：プロジェクトのコードを走らせるタスク（軽い・重い・CPU・GPU）はすべてこれを経由して起動し、一つのキューで到着順に並び、別途の遅延は置かない。タスクを投入するのはメイン agent だけ（クライアント `task-server/task`、人も同じくこれを使う）で、サブ agent は `status`、`log` で結果を見るだけ。どのマシンに載せるか、メモリ枠、GPU が要るか、どのカードを割り当てるかはすべてサーバが決め、投入時にはこれらを受け付けない。

データベースを読み書きするプロセスはサーバだけ：uvicorn 上の FastAPI を、ユーザーレベルの systemd サービス `singlefs-task-server.service` として動かし、unix socket（`${XDG_RUNTIME_DIR}/singlefs-task-server/server.sock`、ディレクトリ 700。フルパスは 107 バイト以内で、超えるとサーバ・クライアント・`control` のいずれも 78 で終了し、そのパスとバイト数と上限を示す）だけを開き、TCP は開かない。データベースは組み込みの SQLite（WAL）で `~/.local/state/singlefs/task-server/` に置き、各行に HMAC の検証列を持つ。メモリの受入はサーバの一か所だけで判定する：収まるときだけ起動し、収まらないものはデータベースに並んだまま待つ。起動するタスクは引き続き `scripts/hosts/run-with-memory-cap.sh`（このマシン。「task-server が受入済み」のスイッチを立て、タスクごとの上限と slice の総上限のカーネル層での歯止めだけを行う）または `scripts/hosts/multi-host-run.sh --peer`（二台目）で包む。

| ファイル | 役割 |
|---|---|
| `task` | クライアント：`submit [--cwd <ディレクトリ>] -- <コマンド…>`、`wait <番号>`、`status [<番号>] [--json]`、`cancel <番号>`、`log <番号>`、`clean <番号>`。使い方と終了コードはファイル冒頭 |
| `control` | 導入と確認：`install [--dry-run]`、`check`（サーバの `/health` が報告するのは三つだけ：データベースに書けない、振り分け（ディスパッチ）が先頭を起動できると判定したのに三ラウンド続けて起動できなかった（起動できないと判定したもの——カード待ち、負荷待ち、交替のグループ待ちなど——は報告しない）、進み具合の確認：あるマシンが式で待機中の最小のタスクを収められるのに 10 分間一件も起動していない（振り分け自身の判定誤りを拾う））、`start`、`stop`、`watch`、`clear-queue`（サーバ停止中にデータベースを退避してからタスクと試行の二つの表を空にする。資源記録は残す）、`pin-cap <コマンド…>` / `unpin-cap <コマンド…>`（サーバ経由でコマンドのメモリ上限を固定値にする・外す。読み戻して確かめてから 0 で終わる）、`pause [--reason <一文>] [--allow-session <セッション番号>]` / `resume`（キューの一時停止と再開。停止中も投入は受け付けるが、通したセッションのもの以外は起動しない。「## 一時停止と再開」） |
| `task_server.py` | サーバ（`serve`）：API、キュー、受入、ユニットの起動、突き合わせ、再試行、分割、資源記録。判定規則はファイル冒頭 |
| `attempt_runner.py` | 各試行のユニットの中でコマンドを起動し、終了コードと資源を記録する（メモリのピークは周期採取の値とメモリラッパーが終了時に読んだ値の大きい方）。ビルドディレクトリはタスクの結果が出たらサービスが消す |
| `task_server_lib.py` | 共用部分：パス、依存、エラー種別と終了コードの表、再試行、資源記録、ビルドディレクトリ、分割、環境変数の一覧、身元。全体の自己検証 `--selftest` と破壊スイッチの表はファイル冒頭 |
| `task_server_selftest.py` | 自己検証の各セル（前の行から起動される） |
| `singlefs-task-server.service.in` | ユーザーレベルのユニットのテンプレート |

独自の設定ファイルはない：スケジューリングの資源はリポジトリ直下のマルチホスト設定 `multi-host.env`（テンプレート `multi-host.env.example`）から読む。socket、データベース、ログ、署名鍵、ビルドディレクトリは `task_server_lib.py` 冒頭の「パス」に書いた固定の既定値を使う。必須：fastapi、uvicorn、`multi-host.env`（中に `NFS_SHARED_ROOTS`、`SHARED_DATA_ROOT`、`HOSTS` があること。書き方は「## NFS 共有」の「マルチホスト設定のどのキーか」）、NFS 共有の設定が済んでいること（「## NFS 共有」を参照）、サーバに繋がること。

マシンの選択は空きの均衡による：カードの要らないタスクは送れるマシンの中から収まるものを選び、収まるマシンが複数あるときは載せた後の残りがそのマシンの総上限に占める割合の大きい方を選び、同じならこのマシンを選ぶ。上限に当たった後の再投入は特定のマシンに固定しない。分割の各片は計画どおりまず二台目に行き、収まる限り均衡で載せ替えない。計画、各片、統合はどれもマシンに固定しない。計画に `pin` を書いたものは全体を `shard-plan-refused` と記録する（片はマシンに固定しない。どのマシンかはサーバが選ぶ）。二台目は同じ共有ツリーで走る：リポジトリ、作業ルート `~/.local/share/singlefs/work/` のある共有データルート、セッション記録ディレクトリを NFS で二台とも同じ絶対パスにマウントし（マルチホスト設定の `NFS_SHARED_ROOTS`、下の「NFS 共有」の節）、二台目に送る回は `scripts/hosts/multi-host-run.sh --peer` がタスクの作業ディレクトリ、同じ絶対パスでそのまま起こす。ツリーを複製せず、送らず、取り戻さず、パスも書き換えず、書き出したファイルは二台とも読める。ビルドディレクトリは `multi-host-run.sh` が二台目のローカルディスクにその回だけ新しく作り（マルチホスト設定の `BUILD_ROOT_BY_HOST` のうち二台目の項の下の `builds/<ラベル>/target`、どの共有ルートの下でもない）、コマンドが終わっても止められても先に消す（コンパイルするコマンドが上限に当たって並べ直すときは次の回のために残す。下の「ピークの出発点」）。サーバは設けず、どこにあるかだけ記録する（`task status` で見える）。`task clean` は扱わない。二台目に送るかどうかは、二台目がいま使えるかと空きだけで決まる。二台目に送れない三種類は投入のときに断る（下の「## 投入の書き方」）。一台だけに送るコマンドの名簿はない（ユーザー：「【このマシンだけで走る】は受け入れられない、と改めて言う。早く直して、誤りを表に出せ」）：どのディレクトリ、どの入口を指すコマンドも二台のどちらにも送れ、どちらかは空きで決まる。二台目で赤になったものは赤のままにし、スクリプトの側で直す。サーバはそれをかばわない。メインの作業ツリーを変えるツール（`hook-swap.py`、`apply-writer-patch.py`、`stage-mine.py`、`scripts/kb/` の下のもの、`--skip-apply` なしの `merge-and-verify`）と `--write` 付きのものは二台目に送れる（変えるのは同じツリー）。上限に当たるなど本来は再投入する結末は従来どおり再投入せず、投入したセッションに返す。分割の計画ディレクトリと各片の成果物ディレクトリは共有の作業ルートの下の `task-server-shards/` にあり、二台が同じ絶対パスで読み書きする。サービスはマージロックを確かめない：メインのワークツリーをマージしている間も普段どおり並べ、起動する。一回の割り当てで二台目に起動するのは最大 4 件（一度に起動しすぎると ssh の接続がリセットされる）で、上限に達したら 2 秒後にもう一回割り当てる。二台目の結末は `multi-host-run.sh` がログに書くそのコマンドの終了行（`MULTI_HOST_RUN_STEP step=peer-command event=end … exit=<コード>`）で決める：この行があればコマンド自身の終了コードで決め、コマンド自身が 255 で終わったものは `command-failed` と記録して再投入しない。この行がなく 255 で終わったものだけが二台目で走らなかったもの（繋がらない、ssh がリセットされた）で、`peer-run-failed` と記録してそのまま再投入し、最大 2 回まで。先頭が収まらないときは、収まる後続を先に起動する（割り込み）。投入から二時間に満たないものはマシンごとに一枚物と小物の組を交互に起動する：マシンの使える上限（総上限からそのマシンの今の余裕を引いたもの）の 85% を境とし、記帳がそれ以上のものが一枚物、ほかは小物で、小物はキューの順に一組に詰め、次の一件で境を超えるときに一枚物が待っていれば組を締めて小物を載せず、一枚物は収まり次第起動し（マシンが空くのを待たない）、一枚物の後は次の小物の組に戻る。交互で止めた待ち理由には「在等这台腾空」（このマシンの空きを待っている）が入る。一枚物は一台だけで空きを待ち、その一台だけ組を締める：前の回でそのために締めたマシンがあればそこで待ち続け、なければ今いちばん収まりに近いマシン（その記帳から、そのマシンの「設定の総上限 − 余裕 − 走っている試行の上限の和」の残りを引いた値が最小）を選ぶ。もう一台は小物をそのまま起動する。カードの要る一枚物は、要る枚数の空きカードがそろうマシンだけを数え、カードがふさがっているマシンはそのために締めない。`/health` が先頭の収まりを判定するのは配置と同じ判定（メモリ、ビルドディレクトリのディスク、CPU の関門、カードの枚数）。組を締めている間の隙間埋め：先頭の一枚物が起動した後も「設定の総上限 − 余裕 − 走っている試行の上限の和」でそのマシンにまだ収まる小物は、所要時間を見ずに起動する。先頭の要る分に食い込む小物は、見込み所要時間がそのマシンで走っている試行の残り時間の最長（ふさいでいる時間）以下のときだけ起動し、見込み所要時間のないものは締めたまま待つ。見込み所要時間：`scripts/crash/crash-point-replay.sh`、`.claude/gate.d/formal-verification.sh`、`.claude/gate.d/crates-mutation-replay.sh` に `--item` を付けて分割しないものは、サーバがまず見積もりの子タスク（同じ入口に `--list-items --with-keys` を付けたもの。項目ごとに一行 `ITEM_PLAN item=<項目名> to_judge=<新たに判定する件数> reusable=<再利用できる件数>` を読む）を走らせ、その結末が出てからキューに入れる。走るたびにログの項目ごとの一行 `ITEM_DONE item=<項目名> seconds=<秒> judged=<判定した件数> reused=<再利用した件数> exit=<コード>` から、項目ごとに「新たに判定する一件あたりの秒数」と「再利用する一件あたりの秒数」をサーバ自身のデータベースに記録する（prune-server には入れない）。見込み所要時間は各項目の件数 × 秒数の和で、どれか一項目でも秒数がなければ見込み所要時間はない。見積もりが失敗したものは見込み所要時間なしで並ぶ。ほかのコマンドの見込み所要時間は、同じコマンドキー（メモリの記録と同じキー：パスと項目は語ごとに畳み、`--check` のセル名は残す）の直近の成功した実行の所要時間。分割したタスクの計画・各片・統合の三段階も同じ（各段階が自分のコマンドキーの直近の成功した実行を取り、各片は片番号ごとに一つ。計画の段階が片ごとの項目を出さないので、片の項目別の見積もりはできない）。`task status <番号>` は見込み所要時間の後ろに、その数がコマンドによるものか、項目によるものか、記録なしかを書く。投入から二時間を過ぎたものは先頭に上がって先に判定し、交互の対象にしない。収まらないときも後続を止めず、枠も取り置かず、収まる後続はキューの順に起動する。待ちタスクは枠を取り置かない。GPU タスクはマルチホスト設定に書いたカードの順に選ぶ（判定規則は `task_server.py` 冒頭の「GPU」）。カードのホスト名札はマルチホスト設定の `HOSTS` にあるそのホストのアドレスで書き、各項目は `<アドレス>:<カード番号>:<割当量>`（例 `192.0.2.1:0:32G`。アドレスは IPv6 でもよく、右から二か所で切る）、名札が `HOSTS` にない項目は設定の誤りとし、サーバーは `HOSTS` で自分のホストを見分け、コマンドには `GPU_CARDS_BY_PRIORITY` に項目をそのまま渡す。カードを使うフィーチャ（`gpu`、`tests-on-a-real-gpu`、`<パッケージ>/<名前>` の形と `--all-features` も）付きの cargo でカードが要るのは、コンパイルしたコードを走らせる `test`、`run`、`bench` で `--no-run` を付けないものだけで、`clippy`、`check`、`build`、`doc` と `--no-run` はコンパイルだけなのでカードも整地も要らない。引数によってだけカードが要るスクリプトは、先頭 60 行の中に `# task-server-gpu-arguments: <語> [<語>…]` の一行を書く：bash か python3 で起動され、最初のオプションでない引数がそのどれかならカードが要る（`*` はどの引数でも要る）。書き方は `task_server_lib.py` の先頭「GPU」。二台は同じ一段の判定を通る（記帳、収まるかどうか、停滞と CPU、ピーク、上限、ビルドディレクトリ、マシン選び、ディスクの空き。ディスクの下限は二台とも 50G）。マシンごとに違うのは、そのマシンへの届き方、測り方、起動の仕方だけ（`task_server.py` の `Machine`）。試行が普通に終わった後、ユニットにコマンドの孫プロセスが残っていれば、サービスが止めて結果の説明に書く。30 分を超えて走って失敗し、スクリプトが先頭に `# task-server-resumable: <語>…` で再開を宣言していなければ、結果の説明に「N 分走った、再開できない：出し直すと最初から走る」（中国語）と書く。

各試行のコマンドは `scripts/hosts/capped.sh <マシンごとの既定の重い作業のスレッド数>` で包み、スレッド数は常にこの数で、投入時には受け付けない。カードの要るタスクは必ず最も外側でさらに `scripts/crash/gpu-quiesce-run.sh --` で包む。メモリラッパー、`capped.sh`、クリアラッパーと `multi-host-run.sh --peer` はサーバが直接包んだ層だけを受け付ける：サーバは各層に受け付けの印（値は `<タスク番号>.<何回目>`）を設定し、その層はそれを読み取ってコマンドには渡さない。タスクの中のスクリプトがもう一層包むとその場で拒否し、出口はその層を消して、メモリ、スレッド、カードはサーバが渡す `TASK_SERVER_MEMORY_CAP_BYTES`、`SINGLEFS_THREAD_CAP`、`GPU_CARDS_BY_PRIORITY` を読むこと。コンパイルする cargo には、その回専用のリポジトリ外の `CARGO_TARGET_DIR` を別に与え、走り終えても残し、`wait` の最終行に `build=<ディレクトリ>` を付け、投入したセッションが `task clean <番号>` で消す。枠はサーバ自身のデータベースの試行記録だけに従う（直近数回の成功した実行のピークの最大値 × 1.5。メモリラッパーのピーク表は読まない。コマンドキーは先に `env` とマルチホスト設定のパス、`LANG` のような走り方を変えない変数のプレフィックスを外す）。記録のないコマンドはまず 4G で記帳し（失敗した回しかないものはその回のピーク × 1.5 を下回らない）、どのタスクも上限と記帳は 4G を下回らない（記録から出した上限が小さくても 4G を取る。固定値は除く）、上限に当たったら 1.5 倍にして再投入する。1.5 倍にするとそのマシンの総上限に届くものは再投入せず、総上限のより大きい別のマシンがあればそちらに移し、なければ `memory-cap-at-maximum` と記録して投入したセッションに差し戻す。マシンの残りを数えるときはプロセスが使うメモリ（`anon` と `shmem`）だけを数え、ページキャッシュと slice に付いたカーネルのメモリは数えない。起動後の 10 分間の猶予中は判定しない。その後、ログが 10 分間伸びず、その間 CPU もほとんど伸びていない（平均で一コアの 1% 未満）ものはサーバが止めて `stalled` と記録し、CPU が読めないことは伸びていないとは見なさない。記録された所要時間の 5 倍を超えて走り、ログも 10 分間伸びていないものは CPU を見ずに止めて `stalled` と記録し（無限ループも止める）、所要時間の記録がないものにはこの規則を当てない。`stalled` は再試行せず、投入したセッションに差し戻す。止まったと判定した時点でその回のメモリのピークが上限の 98% に達していたものは上限に張り付いて止まったもので、同じく止めるが `memory-cap-hit` と記録して 1.5 倍で再投入し（固定値のものは `memory-cap-at-maximum` で差し戻す）、説明に「顶在上限上卡住」（上限に張り付いて止まった）と書く。どれだけ走ったか、記録された所要時間、使用中のコア数は `task status` にだけ書く。二台目の層のメモリのピークは `multi-host-run.sh` が書く `MULTI_HOST_RUN_PEER_MEMORY_PEAK bytes=<バイト数>` からその試行に記録し、このマシンと同じく枠の決定に入れる。この行がないものは測れなかったと記録する。ビルドディレクトリのディスク占有もコマンドごとにピークを記録し（このマシンではサーバが与えたビルドディレクトリを測り、二台目では `MULTI_HOST_RUN_PEER_BUILD_PEAK bytes=<バイト数>` から）、あるマシンに送る前に、そのマシンのディスクの空きから走っている試行のビルドディレクトリがまだ伸びる分を引いたものに、このコマンドのビルドディレクトリのピークと 50G の下限が収まらなければキューに残し、待ち理由に「编译目录占盘」（ビルドディレクトリのディスク占有）と書く。コマンド自身が 75 で終わったもの（prune-server が使えない）は `prune-server-unavailable` と記録し、`wait` は 75 で終わり、再投入しない。サーバは `python3 prune-server/control check` を一度走らせ、通らなければアラートを書く。prune-server を起動も停止もしない。`python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <パス>] -- <元のコマンド>` と書いたコマンドは、コマンドキーと登録表の行を `--` の後の元のコマンドで決め（`--server-binary` のパスはキーに入れない）、コマンドキーの前に「〈task-server 临时 prune-server〉」を付ける：同じ scope で prune-server が一つ多く走るので、包まないコマンドと記録を共有しない。ラッパー自体はそのまま全体を実行する。

受け入れは上限で記帳する：走っている試行も新しく起こす試行も上限で記帳し（そのマシンの総上限からそのマシンの今の余裕を引いた値で頭打ち）、マシンごとに走っているタスクの上限の和がその slice の総上限からそのマシンの今の余裕を引いた値を超えないようにする。まだ伸びきっていない分は「上限 − 今回収できない使用量」で数える。二台とも同じ一段を通り、使用量はそのマシンの余裕を読むその一回（二台目は同じ ssh）で試行ごとの scope について測って持ち帰り（scope は中のプロセスの環境にある `TASK_SERVER_ATTEMPT_LABEL` で試行に対応づける。二台とも渡す）、その報告にその試行の scope がなければ上限をまるごと記帳し、0 にはしない。二台目の側のメモリラッパーは別に記帳しない。余裕はそのマシンの `singlefs-heavy.slice` に今ある、回収できず、どの走っているタスクにも属さない分（slice 自身に記帳され、どの子 cgroup にもないもの。測り方は `scripts/hosts/memory_peaks_lib.py` のファイル頭「余量」）で、二台の空きを読むたびにマシンごとに測り、1 GiB 単位で切り上げる（1.01G・1.1G は 2G、2.1G は 3G、0.7G は 1G、ちょうど整数なら繰り上げない）。定数ではなく、設定にも書かない。余裕を測れないマシンにはその回は送らず、待ちの理由にどのマシンか・なぜかを書く。送れるマシンがどれも測れないものは起動せず `run-condition-unmet`（`wait` は 78 で終わる）と記録し、固定の数には戻さない。各試行はその回の上限（バイト、十進）を環境変数 `TASK_SERVER_MEMORY_CAP_BYTES` でコマンドに渡す。このマシンでも二台目でも渡す。`python3 task-server/control pin-cap <コマンド…>` でコマンドの上限を固定する（`unpin-cap <コマンド…>` で外す。サーバ経由でデータベースに書くので、サーバが動いていても使える）。固定したコマンドの上限と記帳はマルチホスト設定の `SLICE_MEMORY_CAP_BY_HOST` のうち送り先のマシンの項からそのマシンの今の余裕を引いた値（`<アドレス>=<値>` を空白で区切る。項はそのマシンの slice の総上限で、書いたとおりの値。毎回読み直し、数字そのものは記録しない。項がそのマシンの余裕より大きくなければ `pin-cap` はその場で断り、出口はその項を大きくすること）で、学んだピークに置き換えられず、上限に当たっても大きくせず `memory-cap-at-maximum` と記録し、`task status` に固定値であることを書く。固定したのに設定の `SLICE_MEMORY_CAP_BY_HOST` が読めない（ない、書き方が違う、一台抜けている、`HOSTS` にないアドレスがある、ファイルが読めない）ものは起動せず `run-condition-unmet`（`wait` は 78 で終わる）と記録し、`wait` の理由行に読めない原因と出口（設定を直すか `unpin-cap`）を書く。止まった疑いは知らせるだけ：猶予の後、ユニット全体の CPU が 10 分間平均で一コアの 1% 未満（カードの要るものはその間そのカードに自分の計算負荷もないこと。測れないときは負荷ありと見なす）なら、ログが伸びていてもいなくても、サーバは止めない。`task status` に「止まった疑い」と根拠を書き、警告を一件記録し、`wait` は `TASK_SERVER_SUSPECT task=<番号> …` の一行を出して 231 で終わる。タスクは走り続け、`wait` をもう一度起こせば待ち続ける（同じ一続きは一度だけ知らせ、CPU がまた伸びたらその一続きは終わり）。`.claude/gate.d/` を指すゲートは二台目に送れる（走るのは同じ共有ツリー）。判定ライブラリを持ち、登録表 `.claude/gate.d/verdict-library-scripts.tsv` のその行の三列目がまだ prune-server でないものは、投入のときに断る（下の「## 投入の書き方」）。`python3 scripts/experiment-apparatus/device-code-key.py run … --feature <値>` で特性の値に gpu を含むものもカードが要る。`/health` はデータベースの書き込みの試しとキュースレッドの鼓動だけを見る。先頭が収まるのに起きていないかはキュースレッドが毎回の排列で求めて残し、`/health` はそれを読むだけ。

## NFS 共有

**なぜ必要か。** ユーザーが定めた原則：「所有的脚本必须多机跑。抛出的结果需要多机都能读取。如果不行，要么复制资源，要么共享文件。」（すべてのスクリプトは複数のマシンで走らせること。出した結果は複数のマシンから読めること。それができないなら、資源を複製するか、ファイルを共有すること。）NFS はファイルを共有する側の道：このマシンがいくつかのディレクトリをエクスポートし、二台目が同じ絶対パスにマウントするので、一方が書き出した結果をもう一方がそのまま読め、タスクが指すパスも二台で同じものを指す。ユーザーは 2026-11-01 にさらに定めた：「NFS 的配置要写在 task-server 的 readme 中。不要遗漏了。这部分也要作为检测项目。没有 nfs 不启动。要求用户配置。配置相关来自多机配置的配置文件中 不允许增加额外的配置文件。」（NFS の設定は task-server の readme に書くこと。書き漏らさないこと。この部分も検査項目にすること。NFS がなければ起動しない。ユーザーに設定を求めること。設定に関わるものはマルチホスト設定のファイルから取り、別の設定ファイルを増やしてはならない。）そのためサーバはユーザーの代わりに NFS を設定せず、設定はマルチホスト設定 `multi-host.env` の一つのキーだけで、整っていなければサーバは起動しない。

**共有する区切り。** 三つ：リポジトリそのもの（メインの作業ツリーのルート。二台目はこの生きたツリーで走り、ツリーを複製しない）、共有データルート `~/.local/share/singlefs`（作業ルートと分割の成果物がその下にある）、セッション記録ディレクトリ `~/.claude/projects`。どれもこのマシンでの絶対パスを取り、二台目の同じ絶対パスにマウントする（二台目のホームディレクトリは別でもよく、マウント先はこのマシンのパスに合わせて作る）。

**このマシンでのエクスポート。** このマシンに `nfs-kernel-server` を入れ、共有するルートごとに `/etc/exports` に一行ずつ書き、二台目の有線直結セグメントのアドレスにだけエクスポートする（実際のアドレスは非公開の値で、このマシンのこのファイルにだけ書く）。続けてエクスポートを有効にし、起動時に自動で立ち上げる：

```bash
# /etc/exports、ルートごとに一行
<ルート> <二台目の有線直結セグメントのアドレス>(rw,sync,no_subtree_check)
sudo exportfs -ra
sudo systemctl enable --now nfs-server
```

**二台目でのマウント。** 二台目に `nfs-common` を入れ、このマシンと同じ絶対パスにディレクトリを作り、親ディレクトリの所有者をこのマシンと同じ uid にし、ルートごとに `/etc/fstab` に一行ずつ書いてから、systemd に読み直させてマウントする：

```bash
# /etc/fstab、ルートごとに一行
<このマシンの有線直結セグメントのアドレス>:<ルート> <ルート> nfs4 rw,hard,nofail,_netdev,x-systemd.automount,x-systemd.mount-timeout=30 0 0
sudo mkdir -p <ルート>
sudo systemctl daemon-reload
ls <ルート>                     # 入ると自動マウントが働く
```

**このマシンの再起動の後に自分で戻る。** fstab の行に `x-systemd.automount` を書き、`x-systemd.idle-timeout` は書かない。`x-systemd.automount` で systemd はこのルートに自動マウントポイント（`.automount` ユニット）を置き、これは NFS のマウントそのものの成否と一緒に駄目にならない：このマシンが再起動してエクスポートがない間にマウントのユニットが `failed` になっても、次にどれかのプロセスがこのルートに入ると systemd がもう一度マウントを起こすので、このマシンの `nfs-server` が戻れば `reset-failed`、`start` を人が打たなくてもまたマウントされる。`x-systemd.idle-timeout` を書かないので、一度マウントしたら使われていなくても外さない。`hard`（NFS の既定）はこのマシンの再起動の間に読み書きしているプロセスを失敗させず待たせる。サーバのマウントの判定は `mountpoint -q` を見ない（使われていない自動マウントポイントはそこに autofs の仮置きがあるだけで、`mountpoint -q` はそれでも 0 で終わる）。二台目で `stat -f -c %T -- <ルート>/.` を走らせ、ディレクトリに入ってマウントを働かせ、`nfs` が読めたときだけ通す。マウントした後、二台目で `git -C <リポジトリのルート> rev-parse HEAD` がこのマシンと同じコミットを読めれば、リポジトリの区切りは通じている。

**uid。** 二台でユーザーの uid と gid を同じにする。違うときは、エクスポート項目の括弧の中に `all_squash,anonuid=<このマシンでのユーザーの uid>,anongid=<このマシンでのユーザーの gid>` を加え、二台目が書き込んだファイルがこのマシンのこのユーザーのものになるようにする。

**マルチホスト設定のどのキーか。** リポジトリ直下の `multi-host.env` に三つのキーを書く。一つ目は `NFS_SHARED_ROOTS=<絶対パス>[:<絶対パス>…]` を書く。上でエクスポートとマウントをしたルートそのもの（リポジトリそのもの＝メインの作業ツリーのルート、作業ルートを含む共有データルート `~/.local/share/singlefs`、セッション記録ディレクトリ `~/.claude/projects`。どれもこのマシンでの絶対パスで書く）で、コロン区切り、一区切り以上、各区切りは `/` で始まり、`/` で終わらず、空白を含まない。`ENABLE_ACROSS_MACHINES` が 0 でも書く。テンプレートは `multi-host.env.example` で、別の設定ファイルは設けない。マルチホスト設定の判定 `scripts/crash/crash-point-replay-shard-configuration-check.sh` が書き方を判定し、このマシンではさらに各区切りが既存のディレクトリであることも判定する。合わないものは 1 で終了し、何番目の区切りかを示す。二つ目は `SHARED_DATA_ROOT=<絶対パス>`：共有データルート（作業ルートはその下）で、このマシンでの絶対パス、`NFS_SHARED_ROOTS` のどれかの区切りの下にあること。サーバは `.claude/hooks/lib_work_root.py` でこれを取り（環境に `SINGLEFS_DATA_ROOT` があれば環境に従う）、`control install`、`start`、`check` はこの行だけを見る。書いていない、共有ルートの外にあるときは 78 で終了し、`multi-host.env` にこの行を足すよう出口に書く。既定値は補わない。三つ目は `HOSTS=<このマシンの IP> <二台目の IP>`：各マシンの有線直結の区間のアドレスを空白で区切る。どれが自分かはこのマシンのネットワークインターフェースのアドレス（`ip -o addr show`）で見分け、二台目はもう一方で、ssh はそこへ直接つなぐ。ユーザー名は各マシンの `~/.ssh/config` に任せる。二台目のアドレスは共用の取り方 `scripts/hosts/multi_host_addresses.py` だけを通して取り、それはマルチホスト設定をまるごと判定に通してからアドレスを返す：キーが欠けている、判定が知らないキーがある、壊れた行があると取れず、サーバは起動せず、`control start` は 78 で終了する。二台で値が違うものはマシンごとの三つのキー `CARGO_BIN_DIRECTORY_BY_HOST`、`BUILD_ROOT_BY_HOST`、`SLICE_MEMORY_CAP_BY_HOST` に書く：値は空白で区切った `<アドレス>=<値>` で、各項は最初の `=` で切り、`HOSTS` の各マシンにちょうど一項、アドレスはどれも `HOSTS` にあるものとし、あるマシンの値が要るときはそのマシンのアドレスの項を取る。サーバが読むのは `SLICE_MEMORY_CAP_BY_HOST`（固定値）で、一台抜けている、`HOSTS` にないアドレスがあると設定が壊れていると判定する。分割の各片は `TASK_SERVER_SHARD_HOST` で自分が動くマシンの `HOSTS` のアドレスを受け取る。

**サーバ起動時に何を判定するか。** 四項目で、どれか一つでも通らなければサーバは起動せず、78 で終了し、どの項目かを示して「## NFS 共有」を指す：

- 設定：`NFS_SHARED_ROOTS` があり、各区切りがこのマシン上のディレクトリである。`HOSTS` でこのマシンと二台目を見分けられる（次の二項目はそれで二台目につなぐ）；
- エクスポート：このマシンの `/var/lib/nfs/etab` に各区切りのエクスポート行がある；
- マウント：二台目で各区切りの `stat -f -c %T -- <ルート>/.` が `nfs` を読む（入ると自動マウントが働く）；
- 読み書き：両方向に探針ファイルを一つずつ書き、相手が読める（このマシンで書いて二台目で読み、二台目で書いてこのマシンで読む）。

`task-server/control check`、`/health` の `nfs` 欄、`task-server/control watch` も同じ四項目を判定する：サーバが起動した後でどれかが通らなくなったときも、この三か所で見える。

**通らないとき。**

- 設定が通らない：「マルチホスト設定のどのキーか」のとおりキーを補うか書き方を直し、ディレクトリがなければ先に作る。
- エクスポートが通らない：`/etc/exports` に足りない行を補い、`sudo exportfs -ra`。NFS サーバが動いていなければ `sudo systemctl enable --now nfs-server`。
- マウントが通らない：二台目で上の書き方のとおり `/etc/fstab` の行を補うか直し、`sudo systemctl daemon-reload`。マウントのユニットが `failed` になっていれば `sudo systemctl reset-failed "$(systemd-escape -p --suffix=mount <ルート>)"`、それから `ls <ルート>` でマウントを働かせる。マウントできないときは、まず有線直結セグメントが通じているか、このマシンでエクスポート先にしたクライアントのアドレスが二台目のものかを確かめる。
- 読み書きが通らない：多くは二台の uid、gid が合っていないか、エクスポート項目に `rw` がない。「uid」の段のとおりにする。

**確かめ方。** 三つ。それぞれコメントに書いたマシンで実行する：

```bash
stat -f -c %T -- <ルート>/.                   # 二台目で実行：nfs と出ればこのルートはマウントされている
cat /var/lib/nfs/etab                          # このマシンで実行：各ルートにエクスポート行があり、クライアントは二台目
echo probe > <ルート>/nfs-check-by-hand        # このマシンで実行：このマシンで書く
cat <ルート>/nfs-check-by-hand                 # 二台目で実行：二台目で probe が読める
echo probe > <ルート>/nfs-check-peer           # 二台目で実行：二台目で書く
cat <ルート>/nfs-check-peer                    # このマシンで実行：このマシンで probe が読める
rm <ルート>/nfs-check-by-hand <ルート>/nfs-check-peer   # 確かめ終えたら二つのファイルを消す
```

## 投入の書き方

```bash
task-server/task submit -- <コマンド…>              # タスク番号を表示する。環境中の SINGLEFS_RUN_SCOPE のようなホワイトリストの変数はそのまま持っていく
task-server/task wait <番号>                        # run_in_background で起動し、完了時に終了、最終行 TASK_SERVER_RESULT …、終了コードはタスクのもの
task-server/task status [<番号>]                     # このセッションの待ち・実行中・完了して未受領のもの。待ちには「待ち：…」、実行中にはどれだけ走ったか、ログがどれだけ伸びていないかを付ける
task-server/task cancel <番号>                       # 投入したセッションだけ
task-server/task log <番号>                          # 最後の試行のログ（最後の 200 行。--all で全体。--attempt <何回目> でその回。タスクかその回がなければ 4 で終了）
task-server/task clean <番号>                        # このタスクが残したビルドディレクトリと失敗時の現場を消す（投入したセッションだけ、結果が出てから。SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1 を付けていなければビルドディレクトリは結果が出た時点で消え、現場は wait が結果を受け取ってから一時間後に消える。二台目のその回のビルドディレクトリは multi-host-run.sh が自分で消す）
```

`wait` はタスクが対処を要する五つの場合を自分で知らせる（ユーザーがダイアログで「task wait 自己报」を選んだ）。一つ目は並んだまま長すぎる場合で、キューに `QUEUE_ATTENTION_MINUTES`（30 分）並んだとき。二つ目は記録された所要時間の `OVERRUN_ATTENTION_FACTOR`（3）倍まで走った場合で、ログが伸びている間サービスは止めないので、人を呼ぶのはこの一件だけである。三つ目はカード交換での再投入で、静止化がカードの故障を判定し、サービスが別のカードで並べ直した場合（結末は `succeeded` になりうる）。四つ目は静止化が終わっていない場合（`cleanup-pending`）で、コマンドは終了したが読み戻しがまだ片づいておらず、サービスは資源の占有を保持している。五つ目は分割した親タスクが進まない場合（`shard-advance-failed`）。六つ目は結末があるタスクにだけ出す：主作業ツリーを書き換えるコマンド（`apply-writer-patch.py`、`hook-swap.py`、`stage-mine.py`、`--skip-apply` なしの `merge-and-verify.sh`）が、上限超過、押し出し、GPU メモリ不足、二台目で走れなかった、上限の頭打ち、取り消し、停滞での停止、起動元を見失った、シグナルで殺された、のいずれかで終わった場合（`workspace-write-interrupted`）で、半分だけ書いた可能性があり、`next=` で確かめるファイルかパッチディレクトリを挙げる（ユーザー：「这个问题很严重 因为可能会导致补丁没有正常写入」）。`apply-writer-patch.py` で結末ファイル `apply-outcome.tsv` があるものは、サービスがその `--read-outcome` で判定し、全部当たったもの・戻したものは知らせず、`--dry-run` 付きも知らせない。サービスはこのタスク（分割したものは子タスクも含む）のこれらを「対処が要る」通知として記録し、そのタスクを待っている `task wait <番号>` は新しい通知を読むと一行 `TASK_SERVER_ATTENTION task=<番号> type=needs-attention kind=<種類> tier=<段> basis=<根拠の数> why=<理由> next=<出口>` を出して 230 で終了する。タスクは並んだまま、または走ったままで、サービスは手を触れていない。`next=` に従って対処し、`wait` を起動し直して待ち続ける。すでに結末があるタスク（カード交換で成功したもの）では、この行は `TASK_SERVER_REASON` の前に出て、終了コードはタスクのままである。同じタスクの同じ種類の通知は同じ段では一度しか起こさず、`wait` を起動し直しても繰り返さない。段が次の段（しきい値の二倍、四倍……）をまたいだときにだけ再び起こす。通知はサービスのメモリにあるので、サービスの再起動後にもう一度出る。サービスの健全性は `wait` の担当ではない。メイン agent が `run_in_background` で `python3 task-server/control watch` を起動して見張らせ、それが終了したら対処する。

コマンドを包まず、資源の引数も書かない：`run-with-memory-cap.sh <上限>`、`host-dispatch.py … --`、`multi-host-run.sh … --`、`nice`、`timeout`、`capped.sh`、`two-logs.sh`、`gpu-quiesce-run.sh` とスクリプト自身の `--memory`、`--memory-cap`、`--threads`、`--peer`、`--local-only`、`SINGLEFS_THREAD_CAP`：これらはサーバが行い、書けばその場で拒否してどれを外すかを示す。ホワイトリスト外の環境変数はその場で拒否して名前を示す。本当に必要なコマンドは `task-server/task submit -- env <名前>=<値> <コマンド…>` と書く。退役した変数（`SINGLEFS_HEAVY_TESTS`、`GATE_MUTATION_START_OVER`）は、環境に設定しても、コマンドに書いても（`env` の後とコマンドの前の `名前=値`）その場で拒否し、拒否の説明で名前を示して出口を書く。一覧は `task_server_lib.py` の `RETIRED_VARIABLES`。

二台目に送れない三種類は投入のときにその場で断る（ユーザー：「改成提交时当场拒（推荐）：不再悄悄改派本机：碰到这三种就在提交时报错、点名是哪个路径或哪一族、出路写怎么改，任务不跑。」）：`task submit` は 3 で終了し、その一文と出口を出し、タスクは並ばず走らない。一つ目は、作業ディレクトリとコマンドの中の絶対パス（語全体、`名前=絶対パス` の値、`bash -c` のように一語に書いた中の一つずつ）に、マルチホスト設定の `NFS_SHARED_ROOTS` のどの区切りの下にもないものがある場合で、そのパスを挙げ、出口はどれかの区切りの下に移すこと。`/dev/null`、`/usr/`、`/bin/` のように二台で同じシステムのパスは数えない。`/tmp` の下のものも同じく断り、その一文に再起動で `/tmp` が消えることを添える。二つ目は、コマンドに渡す `SINGLEFS_DATA_ROOT`、`SINGLEFS_WORK_ROOT` に共有ルートの下にないものがある場合で、変数と値を挙げ、出口はマルチホスト設定を整えること。三つ目は、コマンドが登録表 `.claude/gate.d/verdict-library-scripts.tsv` の判定ライブラリを持つ行を指し、その行の三列目がまだ `prune-server` でない場合で、その系統を挙げ、出口はその系統を prune-server につなぎ、三列目を `prune-server` に書き換えること。登録表が読めない、壊れているものも同じく断る。

一時 prune-server のラッパー（`python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <パス>] -- <元のコマンド>`）はスクリプトの自己検証専用である（ユーザー：「旧脚本不兼容 我再说一次 如果错了让 对方重新提交」）。そこから剥がした元のコマンドにコンパイルする cargo がある、またはカードが要る（見分け方はサービスがビルドディレクトリとカードを決めるときと同じ）なら、投入のときに上と同じ形でその場で断る：`task submit` は 3 で終了し、その一文（コンパイルするのかカードが要るのかを挙げる）と出口（ラッパーを外して投入し直す）を出し、タスクは並ばず走らない。剥がすのは判定のためだけで、受け付けたものはラッパーごとそのまま走る。ビルドディレクトリ、カード、GPU の静止化は外側のコマンドにだけ与え、サービスはラッパーを剥がして合わせることはしない。`--server-binary` を付けないラッパー（コマンドの前の代入にもタスクの環境にも `PRUNE_SERVER_BINARY` がない場合）は、サービスが与えたビルドディレクトリの中で prune-server 自身をコンパイルするので、サービスは外側のこのコマンドをコンパイルするものとして扱う。本機に送っても二台目に送ってもビルドディレクトリを与え、`--server-binary` 付きのものはコンパイルせず、与えない。checker 層の `cargo test` は本物のサービスに対して走らせ、このラッパーはかぶせない。

## ソースのファイル頭の宣言

サービスはソースファイルの先頭 60 行にある宣言の行から、コマンドが何を要るかを見分ける。呼び出し側はこれまでどおりカードも額も書かない。宣言はその入口スクリプトかパッケージを受け持つセッションが加え、サービスは読むだけである：

| 書く場所 | 書き方 | サービスの使い方 |
|---|---|---|
| 入口スクリプト | `# task-server-gpu-arguments: <引数>…`（`*` はどの引数でも） | 最初の非オプション引数がそのどれかならカードが要り、サービスが静止化をかぶせる |
| 入口スクリプト | `# task-server-gpu-cards: <枚数>` | カードが要るとき同じ一台のこの枚数が要る（下の「何枚のカード」） |
| `.rs` ソース（コンパイルしたバイナリと同名のソース。`cargo test` / `run` / `bench` が `-p` で名指したパッケージのソース） | `// task-server-gpu-cards: <枚数>` | 同上 |
| 入口スクリプト | `# task-server-cargo-family: <cargo の引数>…`（例 `-p singlefs-verification --release --features gpu`） | 中で起こす cargo がどのパッケージ、どのプロファイル、どの機能をビルドするか。このコマンドが自分のキーで記録を持たないとき、同じビルド系統で走りきったピークから始める（下の「ピークの出発点」） |
| 入口スクリプト | `# task-server-shards: <引数>…`、`# task-server-resumable: <引数>…` | 分割と再開（`task_server_lib.py` のファイル頭「分片」「续跑」） |

何枚のカード：ユーザーが決めた実カードの試し方は「你需要测试的是 一张卡1gb 2张卡 三张卡 每张卡都能用来分片gc。没有卡报错。 有卡但是失败 报错加cpu兜底」である。枚数を宣言したものは、サービスがマルチホスト設定のカードの優先順に見て、空きカードがその枚数そろい、メモリにも収まる最初の一台を選び、その台の空きカードのうち前からその枚数をひとまとめに渡す：`GPU_CARDS_BY_PRIORITY` にはその項目を空白でつないだ一続きを渡し、静止化はまとめて行い、走っている間はどれも使用中と数える。マルチホスト設定が挙げたカードでどの台もその枚数がそろわないものは結末を `never-fits`（241 で終了）とし、枚数が正の整数でないものは `run-condition-unmet` とし、どのファイルに何と書いてあったかを説明に挙げる。読む `.rs` ソース：`--test <名前>` を付けたものは `tests/<名前>.rs`、`--lib` だけのものは `src/lib.rs`、それ以外は `src/lib.rs`、`src/main.rs` と `src/bin/`、`tests/` の下のもの。いくつかに書いてあれば最大を取り、どれにもなければ一枚。例：`crates/singlefs-background-gpu/tests/<ターゲット>.rs` の先頭の数行に `// task-server-gpu-cards: 3` と書けば、`cargo test --release -p singlefs-background-gpu --features tests-on-a-real-gpu --tests` に同じ一台の三枚を渡す。

ピークの出発点（サービス自身のデータベースにある試行の記録。`task_server_lib.py` のファイル頭「资源记录」）：
- ビルド系統：コンパイルする cargo はパッケージ、プロファイル（`--release`）、機能で系統に分け、`task-server-cargo-family` を宣言した入口は宣言どおりの系統に入れる。自分のキーで一度も走りきっていないとき、同じ系統で直近 5 回走りきった試行の最大ピーク × 1.5 から始め、4G より大きいときだけ取り替える。自分の記録があるものは自分の記録に従う。
- 同じ計画でのピークの共有：分割の一片の最初の試行は、同じ計画の計画ステップと兄弟片の終わった試行のうち終了時刻の新しい 5 件のピーク（上限に当たったものはその回の上限）× 1.5 を取り、上げるだけで 4G より下には押し下げない。
- 直近の最高から始める：新しく投入したものの最初の試行と、上限に当たった後の毎回の並べ直しは、このキーでサービスが記録している直近 5 回のうち最高の一回（当たった上限、走りきった試行のピーク）× 1.5 まで上げ、並べ直した回はビルド系統と兄弟片も見る（同じく直近 5 回だけ）。上がりも下がりもする：窓の中で当たったばかりの段はすぐ見え、古いものは窓を出れば数えず、その後の数回がどれも小さければ起点も下がる。記録が一つもないものは従来どおり 4G から、実際のピークの記録があるものは 4G に引き上げない。
- 上限に当たって並べ直したとき、前の回のビルドディレクトリは消さず、並べ直した回がまた同じ台ならそれを使い続ける（推測：cargo は指紋でビルド済みのクレートを使い回す。どれだけ省けるかは測っていない）。別の台に移った回では、その回が始まるときに前の回のものを消す。二台は同じ一段を通る：本機は `CARGO_TARGET_DIR` で指し、二台目の試行は `--keep-build-directory` を付けて `multi-host-run.sh` が走り終わった後も `builds/<ラベル>/` を残し、並べ直した回は `--reuse-build-directory <前の回のラベル>` でそれを使い続け、台を移るか結末が出たらサービスが `multi-host-run.sh --remove-build-directory <ラベル>` で消す。

## 一時停止と再開

prune-server のバイナリ入れ替えや判定ライブラリの古い行の削除のように、ほかのセッションのタスクが一つも動いていない時間帯が要る作業は、自分も `task submit` でコマンドを投入することが多い。`control stop` は使えない。サーバ停止中は誰も投入できず、すでに `task wait` している側も 60 秒で 78 を返して終わる。代わりに一時停止を使い、作業するセッションを通す（そのセッションのタスクは停止中でも通常どおり起動する）。

```bash
python3 task-server/control pause --reason "判定ライブラリの古い行を消す" --allow-session <作業するセッション>   # 一時停止：ほかのセッションのタスクは起動しない。通したセッションのタスクは通常どおり並び起動する。投入は受け付け、status / wait / log / cancel は応答する
python3 task-server/control check                                                                              # 「…、放行会话 <番号>、在跑 N 个、别的会话在跑 0 个」（通したセッション・実行 N 件・ほかのセッションの実行 0 件）と出るまで繰り返す
# …時間帯が要る作業（作業するセッションが task submit でコマンドを投入する）…
python3 task-server/control resume                                                                             # 再開：待っていたものは通常どおり起動し、通したセッションの指定も一緒に消える
```

- 作業するセッションの番号：そのセッションで `python3 task-server/task status` を実行し、先頭行「会话 <番号>：…」の番号を使う（タスク投入時にサーバが記録したセッションで、`status` が各タスクに出すセッションと同じ欄）。通すのは一つのコマンドではなくセッションである：そのセッションがすでに待たせているもの、あとから投入するもの、分割タスクの子、見積もり用の子、上限超過で待ち行列へ戻った再試行はすべて通常どおり起動する。ほかのセッションのものと、セッションを持たない手動投入のものは待ったままで起動しない。通したセッションの待機中タスクの `status` は本当に待っている理由を出し、ほかのセッションの待機中タスクは「在等：服务暂停中（原因：…）」と出る。
- すでに停止中のサーバへ `pause --allow-session <別のセッション>` を送ると 0 で終わり、通すセッションを替える（理由と開始時刻は変えない）。`--allow-session` を付けない `pause` は通す指定に触れない。`resume` は通す指定も一緒に消す。タスクが一つも動いていない時間帯が要るなら、`--allow-session` なしで `pause` し、`control check` が実行 0 件と報告するまで待つ。
- 停止中、スケジューラは新しい試行を一つも起動しない（通したセッションのものを除く）。空きへの割り込み、分割タスクの子、見積もり用の子、上限超過で待ち行列へ戻った再試行はすべて保留される。実行中のものは結果が出るまで走る（結果は書かれ、再試行は待ち行列へ戻るが起動はしない）。`pause` と試行の起動は一つのロックを共有するので、`pause` が 0 で終わった時点で起動中だった一件は記録済みで、`control check` の実行中件数にあとから割り込む試行はない。
- 一時停止の状態は、通したセッションも含めてサーバのデータベースに保存され（署名付き。データベース内の通したセッションを書き換えると検証に通らないものとして扱い、誰も通さない）、サーバを再起動しても通す指定ごと `resume` まで続く。すでに停止中のサーバへの `pause` は 0 で終わり、元の理由と開始時刻を変えない。
- `control check` は「暂停中（原因：…，起于…）、在跑 N 个」の一行を加えて出す。セッションを通しているときは「…、放行会话 <番号>、在跑 N 个、别的会话在跑 M 个」となる（M は実行中のうち通したセッションのものでない件数）。終了コードは 0 のまま、「振り分けが先頭を起動できると判定したのに起動できていない」も進み具合も判定しない。`/health` は `paused` と `pause`（`allow_session` と `other_running` を含む）を返し、`ok` は変わらない。待機中タスクの `status` には「在等：服务暂停中（原因：…）」と出る。
- 停止中も `control watch` は、サーバの応答、データベースへの書き込み、ユニット、NFS、第二のホストを見続ける。
- `pause` と `resume` を送れるのはサーバを起動したユーザだけで、投入や取消と同じ判定（呼び出し側の uid がサーバ自身の uid か）を使う。
- 作業が終わったら必ず `resume` する。停止中のサーバは健全に見える（`check` は 0）ので、忘れると待機中のタスクはずっと待つ。

## 自己検証

`python3 task-server/task_server_lib.py --selftest`：各セルが本物の uvicorn を一時 socket 上に立て、メモリラッパー、二台目、静止化、`control` が使う systemctl を偽のスクリプトに、試行の scope を偽のディレクトリに置き換える。コンパイルせず、二台目に繋がず、カードも使わない。すべて模擬の世界で走るので、メイン agent がサーバのキューを通さず直接起動する（フックの一覧 `.claude/hooks/lib_project_code_runs.py` の `MAIN_AGENT_TOOLS_RUN_DIRECTLY`）。`TASK_SERVER_SELFTEST_CELLS=<セル,…>` で指名したセルだけを走らせる。破壊スイッチ `TASK_SERVER_BREAK=<項目>` の表は `task_server_lib.py` 冒頭にある。
