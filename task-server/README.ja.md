# task-server

[中文](README.md) · [English](README.en.md) · **日本語**

異常終了後に残る資源の占有、リモートの後始末の受領確認と診断ログは[タスクの後始末と GPU フェーズのログ](cleanup-protocol.md)を参照。

singlefs の統一タスクサーバ：プロジェクトのコードを走らせるタスク（軽い・重い）はすべてこれを経由して起動し、一つのキューに入り、サーバが資源と公平の規則でスケジュールし、別途の遅延は置かない：先頭が収まらないときは収まる後続を先に起動でき（割り込み）、投入から二時間を過ぎたものは先頭に上がる。規則は「## スケジューリング」。タスクを投入するのはメイン agent だけ（クライアント `task-server/task`、人も同じくこれを使う）で、サブ agent は `status`、`log` で結果を見るだけ。どのマシンに載せるか、メモリ枠はサーバが決め、投入時にはこれらを受け付けない。サーバが配分するのは CPU とメモリだけで、カードの割り当て・貸し出し・静止化はしない：カードは GPU バッチ検証サービス（`gpu-verification-server/`）のもので、「## カード」を参照。

データベースを読み書きするプロセスはサーバだけ：uvicorn 上の FastAPI を、ユーザーレベルの systemd サービス `singlefs-task-server.service` として動かし、unix socket（`${XDG_RUNTIME_DIR}/singlefs-task-server/server.sock`、ディレクトリ 700。フルパスは 107 バイト以内で、超えるとサーバ・クライアント・`control` のいずれも 78 で終了し、そのパスとバイト数と上限を示す）だけを開き、TCP は開かない。データベースは組み込みの SQLite（WAL）で `~/.local/state/singlefs/task-server/` に置き、各行に HMAC の検証列を持つ。メモリの受入はサーバの一か所だけで判定する：収まるときだけ起動し、収まらないものはデータベースに並んだまま待つ。起動するタスクは引き続き `scripts/hosts/run-with-memory-cap.sh`（このマシン。「task-server が受入済み」のスイッチを立て、タスクごとの上限と slice の総上限のカーネル層での歯止めだけを行う）または `scripts/hosts/multi-host-run.sh --peer`（二台目）で包む。

## スケジューリング

マシンの選択は空きの均衡による：タスクは送れるマシンの中から収まるものを選び、収まるマシンが複数あるときは載せた後の残りがそのマシンの総上限に占める割合の大きい方を選び、同じならこのマシンを選ぶ。上限に当たった後の再投入は特定のマシンに固定しない。分割の各片は計画どおりまず二台目に行き、収まる限り均衡で載せ替えない。計画、各片、統合はどれもマシンに固定しない。計画に `pin` を書いたものは全体を `shard-plan-refused` と記録する（片はマシンに固定しない。どのマシンかはサーバが選ぶ）。二台目は同じ共有ツリーで走る：リポジトリ、作業ルート `~/.local/share/singlefs/work/` のある共有データルート、セッション記録ディレクトリを NFS で二台とも同じ絶対パスにマウントし（マルチホスト設定の `NFS_SHARED_ROOTS`、下の「NFS 共有」の節）、二台目に送る回は `scripts/hosts/multi-host-run.sh --peer` がタスクの作業ディレクトリ、同じ絶対パスでそのまま起こす。ツリーを複製せず、送らず、取り戻さず、パスも書き換えず、書き出したファイルは二台とも読める。ビルドディレクトリはこの木の二台目での組の一つ（下の「## ビルドディレクトリ」）：新しく開くものは `multi-host-run.sh` が二台目のローカルディスクに作り（マルチホスト設定の `BUILD_ROOT_BY_HOST` のうち二台目の項の下の `builds/<ラベル>/target`、どの共有ルートの下でもない）、`--keep-build-directory` で走り終わった後も残し、組にすでにあるものは `--reuse-build-directory <ラベル>` で続けて使う。サーバは `CARGO_TARGET_DIR` を設けず、どこにあるかだけ記録する（`task status` で見える）。`task clean` は扱わない。二台目に送るかどうかは、二台目がいま使えるかと空きだけで決まる。二台目に送れない三種類は投入のときに断る（下の「## 投入の書き方」）。一台だけに送るコマンドの名簿はない（ユーザー：「【このマシンだけで走る】は受け入れられない、と改めて言う。早く直して、誤りを表に出せ」）：どのディレクトリ、どの入口を指すコマンドも二台のどちらにも送れ、どちらかは空きで決まる。二台目で赤になったものは赤のままにし、スクリプトの側で直す。サーバはそれをかばわない。マージ後検証 `scripts/gate/merge-and-verify.sh` は自分で複製したスナップショットの上でだけパッチを当てて検証し、メインの作業ツリーには一バイトも書かない（そのファイル頭「快照（不拿锁）」）ので、メインの作業ツリーを変えるものには数えず、上限に当たれば普段どおり上限を広げて並べ直す。メインの作業ツリーを変えるツール（`hook-swap.py`、`apply-writer-patch.py`、`stage-mine.py`、`scripts/kb/` の下のもの）と `--write` 付きのものは二台目に送れる（変えるのは同じツリー）。上限に当たるなど本来は再投入する結末は従来どおり再投入せず、投入したセッションに返す。そのため括弧の中のツールは初回から十分に与える：上限は「（同じキーの直近 5 回の最高 + `hook-swap.py` の `--verify` が与える検証コマンドのキーの直近 5 回の最高）× 1.5」を下回らない（4G の底は設けない。ある入れ替えは同じキーの窓だけで 857M しか与えられず、当たって、入れ替えが途中で止まった）。分割の計画ディレクトリと各片の成果物ディレクトリは共有の作業ルートの下の `task-server-shards/` にあり、二台が同じ絶対パスで読み書きする。計画の段が計画ディレクトリの下に置くテストバイナリ（`test-binaries/`）は、親タスクに結末が出たとき（成功、失敗、取り消しのどれでも）と `task clean <親タスクの番号>` のときにサービスが消し、計画ディレクトリのほかのファイルは残す。そのサブディレクトリの実パスがこのタスク自身の計画ディレクトリの下にないもの（よそを指すシンボリックリンクなど）は消さず、サービスのログに一行出す。消したファイルの数と大きさは操作ログに書く。サービスはマージロックを確かめない：メインのワークツリーをマージしている間も普段どおり並べ、起動する。一回の割り当てで二台目に起動するのは最大 4 件（一度に起動しすぎると ssh の接続がリセットされる）で、上限に達したら 2 秒後にもう一回割り当てる。サービスが自分で起こす ssh（NFS の再確認、余裕の探査、プロセスの確認、進み具合の読み取り）はすべて接続を再利用する：`ControlMaster=auto`、`ControlPath=<サービスの状態ディレクトリ>/ssh/%C`（マシンごとに一つ）、`ControlPersist=300` を付け、ホスト名はマルチホスト設定からだけ取り、サービスを止めるときにマスター接続を一つずつ閉じる（試行が `multi-host-run.sh` 経由で起こす ssh はこの層に含まない）。二台目の結末は `multi-host-run.sh` がログに書くそのコマンドの終了行（`MULTI_HOST_RUN_STEP step=peer-command event=end … exit=<コード>`）で決める：この行があればコマンド自身の終了コードで決め、コマンド自身が 255 で終わったものは `command-failed` と記録して再投入しない。この行がなく 255 で終わったものだけが二台目で走らなかったもの（繋がらない、ssh がリセットされた）で、`peer-run-failed` と記録してそのまま再投入し、最大 2 回まで。キューの順序は二つの規則だけに従う：① 待ち時間の上限（二時間）を超えてもまだ起動できないタスクは、その後ろに並ぶすべてのタスクを止める。それが起動するまで後ろは一件も起動せず、待ち理由には「排在任务 N 后面：它已排满时限」と書く。② 前にまだ起動していないタスクがあるとき、後ろのタスクが先に起動できるのは次の場合だけ：前回の実行時間（同じコマンドキーが前回実際に最後まで走ってかかった時間。記録であって見積もりではない）があり、その時間がそのマシンで走っているタスクの残り時間のうち最も長いものを超えないこと（残り = そのタスクの前回の実行時間から走った時間を引いたもの。走っているどのタスクも残り時間を出せないときは、前回の実行時間があるものは先に起動してよい）。前回の実行時間がないものは割り込まず、待ち理由には「不插队」と書く。サービスは所要時間を見積もらない：メモリの上限は記録から決め、上限に当たれば 1.5 倍にする。一項目が実際に四時間走れば止めて差し戻し、二時間走れば分割を勧める通知を送る（`--full-gate` で投入したコミットゲートはどちらの対象にもならない）。待ちタスクは枠を取り置かない。二台は同じ一段の判定を通る（記帳、収まるかどうか、停滞と CPU、ピーク、上限、ビルドディレクトリ、マシン選び、ディスクの空き。ディスクの下限は二台とも 50G）。マシンごとに違うのは、そのマシンへの届き方、測り方、起動の仕方だけ（`task_server.py` の `Machine`）。試行が普通に終わった後、ユニットにコマンドの孫プロセスが残っていれば、サービスが止めて結果の説明に書く。30 分を超えて走って失敗し、スクリプトが先頭に `# task-server-resumable: <語>…` で再開を宣言していなければ、結果の説明に「N 分走った、再開できない：出し直すと最初から走る」（中国語）と書く。

各試行のコマンドは `scripts/hosts/capped.sh <マシンごとの既定の重い作業のスレッド数>` で包み、スレッド数は常にこの数で、投入時には受け付けない。外側に静止化のラッパーは包まない（タスクはカードを持たない。「## カード」を参照）。メモリラッパー、`capped.sh` と `multi-host-run.sh --peer` はサーバが直接包んだ層だけを受け付ける：サーバは各層に受け付けの印（値は `<タスク番号>.<何回目>`）を設定し、その層はそれを読み取ってコマンドには渡さない。タスクの中のスクリプトがもう一層包むとその場で拒否し、出口はその層を消して、メモリ、スレッドはサーバが渡す `TASK_SERVER_MEMORY_CAP_BYTES`、`SINGLEFS_THREAD_CAP` を読むこと。サーバ自身の環境にあるカード選択の変数（`GPU_CARDS_BY_PRIORITY`、`CUDA_VISIBLE_DEVICES`）はコマンドに渡さない。コンパイルする cargo には、リポジトリ外の `CARGO_TARGET_DIR` を別に与える：この木のこの台での組の一つで、同じ木に後から投入したタスクは続けて増分ビルドし、木が消されたときにだけ消す（下の「## 受け入れの記帳：新しく起こす試行は上限で記帳する（そのマシンの総上限からそのマシンの今の余裕を引いた値で頭打ち）。走っている試行は報告にあるその scope の今回収できない使用量だけで記帳し（固定の余裕は足さず、前もって見積もった数は見ない）、自分の上限を超えない（報告にまだその scope 倍してやり直し、ほかのキーや同じ回の兄弟片の記録は借りない。slice の下支え：そのマシンの slice の実測の余地が 4 GiB に満たない間はその回は新しいタスクを起こさず、待ちの理由には実測の余地が足りないと書く。メモリが収まらないときの待ちの理由には二つの数がそれぞれ何か——帳簿にあとどれだけ記帳できるか（総上限、余裕、走っている記帳の和）と slice テストと検証を起こすときは名指しが要る（異常表 `unnamed-run`、投入時に拒む、3 で終了）：投入したコマンドと `bash -c` の中でコマンド位置にある一つ一つについて、`cargo test` は `--` のあとに `--exact` とテストの完全名を付ける（`cargo test -p <パッケージ> --test <ターゲット> -- <テストの完全名> --exact`。`--test` のターゲットだけを名指す、絞り込みの語だけを渡すものは数えない）。`scripts/gate/merge-and-verify.sh`、`scripts/crash/crash-point-replay.sh`、`scripts/crash/crash-amplification.sh` は `--item` を付ける。`scripts/mutation/prove-red.sh` は `--copy <コピー> <crate>` のあとにミューテーション名を書く。`.claude/gate.d/` のゲート段階は `--item` を付けるか、`--check` でテストを起こさないセルだけを名指す（テストを起こすセルは `task_server_lib.py` の `TEST_STARTING_GATE_CELLS` に手で並べてあり、そのどれかを名指すなら `--item` が要る。各段階のファイル頭のセル名表はどのセルがテストを起こすかを書いていないので、そこからは読み取れない。自己検証 test-starting-cells-listed が、表のセル名がどれもその段階のセル名表にあることを確かめる）。ゲート `crash-point-replay.sh` は `--item` を付けたうえで、`--check` で検証クレート全体を走らせるセルを外す必要がある：クラッシュ列挙ケースを名指すなら `--check crash-case-replay --crash-cases-only --item crash-case:<ケース名>` と書き、`--check` がなければ従来どおり九セルを走らせるので拒む。`feature-gated:<ファイル名>` だけを名指して `--check` を付けないものは feature-gated-tests セルだけを走らせ、名指したファイルだけをビルドするので受け付ける。問い合わせだけの書き方（`--list`、`--list-items`、`--selftest`、`--no-run`、`-- --list`）は判定しない。`--full-gate`（コミット時の一回）か `--whole-package-confirmed`（形式を確かめ済みのパッケージ全体の確認ファイルを渡すもの）を付けたものも判定しない。拒否の説明にはどの種類が名指されていないかを書き、このコマンドを名指した形に書き直して示す。判定基準は一か所だけ（`task_server_lib.py` の `unnamed_run_problem`）で、範囲宣言フック `.claude/hooks/run-scope-guard.sh` はコマンドの実行前に同じ関数を呼んで `task submit` で投入されるものを判定し、サーバが起動したときに並んでいるタスクを同じ基準で判定し直す。

メモリが最も高かった瞬間の内訳（タスク 10279 はピーク 45.46 GiB なのに、ラッパーが終了時に読んだ memory.stat は anon 311296 だった：プロセスが殺されメモリが解放された後だから）：走っている間、毎回 scope の memory.current を読み、それまでの最高を超えたら memory.stat の anon、file、file_dirty、file_writeback、shmem を保存する（本機は `attempt_runner.py`、二台目は `multi-host-run.sh` が毎回 `MULTI_HOST_RUN_PEER_MEMORY_STAT` の一行を出す）。上限に当たった試行では、サービスがそれを一文にして結末説明とセッションへのメッセージに写し、メモリが最も高かった瞬間であること、大半がプロセス自身のメモリ（anon）かページキャッシュ（file、まだ書き戻していないダーティページを含む）かを書く。記録するだけで判定は変えない。ピークは二台とも同じ定義：毎回採ったプロセスのメモリと、メモリラッパーが終了時に渡す値（ページキャッシュを除き 0.1 秒ごとに採る）の大きいほう。二台目で後者が読めないものは未計測として割り当てに入れない（タスク 10045 の系列は二台目で毎回シェルの 18 MiB だけを記録し、本機の計測は 556 MiB だった）。上限に続けて当たってから差し戻したタスク（`memory-cap-at-maximum`、または 16 回当たりきった `memory-cap-hit`）で、結末の試行の末尾が二回以上続けて上限に当たっているものは、`wait` の理由の行に `loop_leak=` も付け、セッションへの結末メッセージは「检查代码有没有逻辑循环或内存泄漏：…」を別の行に書く。確かめる二種類（論理ループ：無限ループ、際限のない再帰、同じ集合に何度も足す、毎回全量を読み直す。メモリリーク：増えるだけで減らないキャッシュや表、大きなファイルや全量の結果を丸ごとメモリに読む、使い終わっても解放しない大きなオブジェクト）と根拠（各回の上限と峰値を順に、峰値が回ごとに大きくなっているか、毎回上限の 98% に達しているか、最後に上限に当たった瞬間のメモリ内訳で大半がヒープかページキャッシュか）を書く。一度しか当たっていないもの、キューの時点で記帳が上限を超え一度も起動していないものには付けない。

丸ごとの取り消しの順序：分片のタスクを丸ごと取り消すときは、走っている子タスクのユニットを止めたあと、それぞれがデータベースで結末を持つまで待ち（分片しない取り消しと同じ待ち方）、そろってから全体に `cancelled` を記録し、成果物を消し、止めたと返す。時間内にそろわない子タスクは 500 で名指しする。データベースで終わった試行を、先に読んだ写しから走行中に書き戻すことはない。起動前の再確認は読み直した台を待ち行列の一巡と同じく判定し（ディスクの下限、ビルドディレクトリの占有、二台目の NFS マウント）、結果をこの一巡の残量に反映する。停滞で止めるのは判定したその試行だけで、その間に再投入された次の試行には及ばない。同じ試行の二台目のクリーンアップ回復（`multi-host-run.sh --recover-cleanup`）は同時に一つしか起こさない。

待ち理由はマシンごとに書く：待っているタスクが何を待っているか（`task status` の「待ち：…」。待ちすぎの通知の根拠もこれ）は、マシンごとに一文ずつ、文頭にマシン名を置き、そのマシンを止めているのがどれかを名指す：メモリ、ビルドディレクトリのディスク占有、ビルドディレクトリの組が満杯、CPU の関門（そのマシンのコア数か負荷が読めないことも含む）、ディスク圧力（コンパイルするタスクについて、そのマシンの `/proc/pressure/io` の full avg300 が多機配置の `TASK_SERVER_IO_PRESSURE_LIMIT` を超えている。このキーがなければ判定せず、二台はそれぞれ自分の値を読む）、slice の下支え（そのマシンの slice の実測の余地が 4 GiB に満たない）、固定値、またはそのマシンが今使えないこと。数だけを書いて、どれが止めているかを読む人に推させるものは名指したことにならない。丸ごと差し戻すもの（`never-fits`、`run-condition-unmet`）の説明も同じくマシンごとにマシン名を付ける。

処置の根拠はデータベースから読む：通知・確認・「そのまま走らせる」・差し戻しといった処置が使う根拠（どの種類を報告したか、どの通知しきい値まで報告したか、確認したか、「そのまま走らせる」と記録したか）はサービスのデータベースに書き、判定はデータベースのその記録に従う。サービスのプロセスのメモリには、この回に計算したもの、サービスを入れ替えた後にデータベースと読み直した数から計算し直せるものだけを置く。サービスを止めて起こし直しても、待ちと実行中のタスクはデータベースに従って引き続き認める：同じしきい値は二度と報告せず、確認済みのものと「そのまま走らせる」と記録済みのものは再び送らず、`confirm --why` は報告済みの通知をそのまま受け付ける。スケジューラ自身の判断（タスク外の空回りプロセスを何回報告したか、分割計画が進まなかった回数）も同じくデータベースに書く：データベースの meta 表に一つにつき一行 `restart-surviving:<名前>`、署名付き。サービスは起動時に読み戻し、署名が合わないものは認めず `record-tampered` を記録して空から始める。

**帳簿と判定の細かい見直し。**

- 走っている試行のメモリ記帳：起動から 2 分たたないうちは上限をまるごと記帳し（どこまで伸びるかまだ測れていない）、たったあとはこの回に読んだ scope の実際の使用量で記帳する（上限まで）。コンパイルのピークが下がれば、記帳もそれに合わせて下がる。
- 記帳の突き合わせ：サービスは毎分、マシンごとに「走っている試行のメモリ記帳の和」と突き合わせの基準（各 scope の回収できない使用量の和）を比べる。記帳の和が基準の 3 倍以上で 8 GiB 以上多い状態が 3 回続いたら「記帳のずれ」と判定し（残るのは報告に scope がなく上限をまるごと記帳した試行だけ）、試行ごとにいくら記帳し実際にいくら使っているか、記帳が今の実測・実測が届いた上限・scope がなく上限まるごとのどれから来たかを並べ、`/health` の `booking_drift` 欄と `control check` の出力に書き、それに止められて並んでいるタスクのセッションへ通知する（同じことはその場で一度、その後は継続時間が倍になるごとにもう一度）。報告するだけで、タスクは止めない。
- 投入の出入りログ：サービスは投入を一件受けるたびに、返事をするときサービスのログに「提交进出」の一行を出す：受け取った時刻、受け付けたか断ったか、ワーカースレッドに入る・投入時の拒否判定・セッション・タスクの認定・データベースへの書き込み・投入時の警告・確認票・返事の各段が受け取ってから何秒で終わったか。一段だけで 5 秒以上かかったものはその場でもう一行出す。`task submit` が返事を 30 秒待って 78 で終わったときは、これらの行でどの段が遅かったかを見る。
- ユニットが止まったら先に記帳を外す：読み戻しでユニットの停止（`is-active` が実行中でなく `cgroup.procs` が空。状態が読めない場合は停止と見なさない）を確認した時点から、その試行は CPU とメモリの走行中の記帳に入れない。後片付け（ディレクトリ削除、ピーク取得、結果の記録）は従来どおり最後までやる。
- 待ち理由の CPU 負荷は「負荷 N（うち IO 待ちのスレッド M）」と書く。関門の判定は変えない。
- リマインダ `fills-any-cap` は、上限が記録のピークから決まった回（試行の `prediction` 欄が `record`）を数えない。
- マシン全体のメモリ線：ある一台で、マシン全体の利用可能メモリの割合と swap の空きの割合がどちらも 12% を下回ったとき（earlyoom は両方が 10% を下回って初めてプロセスを殺す）、この周回ではその一台に新しいタスクを送らず、待ち理由に二つの割合を書く。止めるのは新規の割り当てだけで、実行中のものは止めない。
- サービスが送ったものではない TERM または KILL で殺された場合（earlyoom、カーネル OOM）：コマンドが 0 以外で終了し、この試行でサービスが停止シグナルを送っておらず、その一台の同じ時間帯の earlyoom またはカーネルログがこの試行のプロセスツリー内のプロセス番号を名指ししているとき、結果を `killed-externally`（終了コード 228）とし、同じ上限で最大 2 回まで再投入する。二台目のプロセス番号はサービス側では取得できないため、`scripts/hosts/multi-host-run.sh` が二台目側でこの実行のプロセスツリーのプロセス番号を記録し、コマンドが 0 以外で終了したら二台目の earlyoom とカーネルログを読み、その番号のどれかが名指しされていれば `MULTI_HOST_RUN_PEER_EXTERNAL_KILL source=<earlyoom|kernel> pid=<番号> line=<ログの原文>` を一行出す。サービスはこの行を読み、本機と同じく `killed-externally` と記録して同じ上限で再投入する。この行がなければ `command-failed` とする。カーネルの行が「Memory cgroup out of memory」のもの（あるメモリ cgroup が自分の上限に達した。たとえばコマンド自身が作った小さなメモリ cgroup でプロセスを上限に当てたもので、マシン全体のメモリ不足ではない）は二台とも外部とは数えない。二台目では `multi-host-run.sh` がそういう行を飛ばして `MULTI_HOST_RUN_PEER_EXTERNAL_KILL` を出さず（次の行を探し続ける）、サービス側も `line=` の中身で分け、通常の判定に戻す（コマンド自身の 0 以外の終了、またはこの試行自身の scope が上限に当たったなら上限到達）。
- `python3 task-server/control bookings`：読み取り専用で、マシンごと・実行中の試行ごとに上限、現在の使用量、計上した量とその理由を並べ、最終行にそのマシンの合計と計算式（総額 × 1.5 から余裕と記帳の合計を引く）でなお収まる量、slice に実測でなお入る量を書く（`/health` の `booking_ledger` 欄を読み、二台目には接続しない）。
- `python3 task-server/control key-stats [--since <時刻>] [--dump <ファイル>]`：読み取り専用（データベースを読み取り専用で開くので、サービスが走っていても使える）。統計は終わった試行のうち、コマンドキーがあり、ピークの測り方が今の版のもの（枠を決めるときと同じ判定）だけを取り、最初の行に絞り込みの前と後の行数を書く。交替と「上限に当たり、最新のタスクは成功」はタスク単位で数え（一つのタスクの何回かの試行は一つにまとめ、最初の試行の結果を取る）、試行単位の交替は別の行で報告する。`--since` はその時刻以降に起動した試行だけを取る（epoch 秒、または `YYYY-MM-DD` でその日の始まり。日付は `time.gmtime` で数える）。`--dump <ファイル>` は終わった試行を一行一つの jsonl に書き出す（列は `id`、`task_id`、`number`、`command_key`、`command`、`started_at`、`ended_at`、`outcome`、`exit_code`、`memory_cap`、`memory_peak`、`peak_metric`、`stalled_at_cap`、`prediction`、`shard_count`、`host`、`item_plan`、ないものは null）。ファイルは排他的に新規作成し、すでにあれば拒否して 2 で終わる。
- CPU ゲートが新しいタスクのスレッド数を履歴の記録済みコア数から数えるとき、コマンド自身が 0 以外で終了したが最後まで走った回も数える（停止された回、上限に当たった回、シグナルで殺された回は数えない）。
- `task-server/task promote <番号>`（このクライアントコマンドは実行前にフックがダイアログを出して利用者の確認を求める）：投入したセッションだけが使え、タスクは待っているものか、分割が確認済みの親タスクでなければならない。繰り上げたタスクは先頭に並び、待ち時間の上限に数えず、起動できなくても後ろを止めず（後ろのものは割り込みの規則で判定しない）、CPU ゲートを通さない（メモリが収まれば起動する）。分割の親タスクは今待っている子タスクと一緒に繰り上がり、あとで作る計画・各片・マージも同じく繰り上がる。変更したらその場で一回割り当てる。
- 一時停止中にあるセッションを通すとき、待っているタスクの順位はキュー全体で数え、ほかのセッションの待っているタスクの順位は失われない。
- 二台目のディスクの余裕が下限を切っているとき、記録が本機より大きく二台目にしか収まらないタスクは、そのディスクが空くまで並んで待ち、`never-fits` とは判定しない。
- データベースの書き込みトランザクションでエラーが出たとき（ディスク満杯、IO エラー、ビジー）は、先にロールバックしてから報告し、接続を書き込みトランザクションの中に残さず、ほかのスレッドは引き続き書き込める。
- 二台目が前回読めず、まだクールダウン中の間は、後始末・プロセスの確認・ビルドディレクトリの削除・空回りの各所はつなぎに行かず、その場で「つながらない」として扱う。サービスを止めるときは二台目の余裕の探査スレッドが終わるのも待つ。
- コマンドが起動できない（argv の先頭が存在しない、実行権限がない）ときは、コマンド自身が 127 か 126 で終了したと記録し、`launcher-lost` とは記録しない。コマンドが終了したあと、サービスの層で CPU とスレッドをもう一度採取する。

## NFS 共有

**なぜ必要か。** 原則：「所有的脚本必须多机跑。抛出的结果需要多机都能读取。如果不行，要么复制资源，要么共享文件。」（すべてのスクリプトは複数のマシンで走らせること。出した結果は複数のマシンから読めること。それができないなら、資源を複製するか、ファイルを共有すること。）NFS はファイルを共有する側の道：このマシンがいくつかのディレクトリをエクスポートし、二台目が同じ絶対パスにマウントするので、一方が書き出した結果をもう一方がそのまま読め、タスクが指すパスも二台で同じものを指す。NFS の設定はこの README に書き、サーバ起動時の検査項目にもなっている。そのためサーバはユーザーの代わりに NFS を設定せず、設定はマルチホスト設定 `multi-host.env` の一つのキーだけで、整っていなければサーバは起動しない。

**共有する区切り。** 三つ：リポジトリそのもの（メインの作業ツリーのルート。二台目はこの生きたツリーで走り、ツリーを複製しない）、共有データルート `~/.local/share/singlefs`（作業ルートと分割の成果物がその下にある）、セッション記録ディレクトリ `~/.claude/projects`。どれもこのマシンでの絶対パスを取り、二台目の同じ絶対パスにマウントする（二台目のホームディレクトリは別でもよく、マウント先はこのマシンのパスに合わせて作る）。

**このマシンでのエクスポート。** このマシンに `nfs-kernel-server` を入れ、共有するルートごとに `/etc/exports` に一行ずつ書き、二台目の有線直結セグメントのアドレスにだけエクスポートする（実際のアドレスは非公開の値で、このマシンのこのファイルにだけ書く）。続けてエクスポートを有効にし、起動時に自動で立ち上げる：

```bash
# /etc/exports、ルートごとに一行
<ルート> <二台目の有線直結セグメントのアドレス>(rw,sync,no_subtree_check)
sudo exportfs -ra
sudo systemctl enable --now nfs-server
```

**二台目でのマウント。** 二台目に `nfs-common` を入れ、このマシンと同じ絶対パスにディレクトリを作り、親ディレクトリの所有者をこのマシンと同じ uid にし、ルートごとに `/etc/fstab` に一行ずつ書いてから、systemd に読み直させてマウントする：

```bash
# /etc/fstab、ルートごとに一行
<このマシンの有線直結セグメントのアドレス>:<ルート> <ルート> nfs4 rw,hard,nofail,_netdev,x-systemd.automount,x-systemd.mount-timeout=30 0 0
sudo mkdir -p <ルート>
sudo systemctl daemon-reload
ls <ルート>                     # 入ると自動マウントが働く
```

**このマシンの再起動の後に自分で戻る。** fstab の行に `x-systemd.automount` を書き、`x-systemd.idle-timeout` は書かない。`x-systemd.automount` で systemd はこのルートに自動マウントポイント（`.automount` ユニット）を置き、これは NFS のマウントそのものの成否と一緒に駄目にならない：このマシンが再起動してエクスポートがない間にマウントのユニットが `failed` になっても、次にどれかのプロセスがこのルートに入ると systemd がもう一度マウントを起こすので、このマシンの `nfs-server` が戻れば `reset-failed`、`start` を人が打たなくてもまたマウントされる。`x-systemd.idle-timeout` を書かないので、一度マウントしたら使われていなくても外さない。`hard`（NFS の既定）はこのマシンの再起動の間に読み書きしているプロセスを失敗させず待たせる。サーバのマウントの判定は `mountpoint -q` を見ない（使われていない自動マウントポイントはそこに autofs の仮置きがあるだけで、`mountpoint -q` はそれでも 0 で終わる）。二台目で `stat -f -c %T -- <ルート>/.` を走らせ、ディレクトリに入ってマウントを働かせ、`nfs` が読めたときだけ通す。マウントした後、二台目で `git -C <リポジトリのルート> rev-parse HEAD` がこのマシンと同じコミットを読めれば、リポジトリの区切りは通じている。

**uid。** 二台でユーザーの uid と gid を同じにする。違うときは、エクスポート項目の括弧の中に `all_squash,anonuid=<このマシンでのユーザーの uid>,anongid=<このマシンでのユーザーの gid>` を加え、二台目が書き込んだファイルがこのマシンのこのユーザーのものになるようにする。

**マルチホスト設定のどのキーか。** リポジトリ直下の `multi-host.env` に三つのキーを書く。一つ目は `NFS_SHARED_ROOTS=<絶対パス>[:<絶対パス>…]` を書く。上でエクスポートとマウントをしたルートそのもの（リポジトリそのもの＝メインの作業ツリーのルート、作業ルートを含む共有データルート `~/.local/share/singlefs`、セッション記録ディレクトリ `~/.claude/projects`。どれもこのマシンでの絶対パスで書く）で、コロン区切り、一区切り以上、各区切りは `/` で始まり、`/` で終わらず、空白を含まない。`ENABLE_ACROSS_MACHINES` が 0 でも書く。テンプレートは `multi-host.env.example` で、別の設定ファイルは設けない。マルチホスト設定の判定 `scripts/crash/crash-point-replay-shard-configuration-check.sh` が書き方を判定し、このマシンではさらに各区切りが既存のディレクトリであることも判定する。合わないものは 1 で終了し、何番目の区切りかを示す。二つ目は `SHARED_DATA_ROOT=<絶対パス>`：共有データルート（作業ルートはその下）で、このマシンでの絶対パス、`NFS_SHARED_ROOTS` のどれかの区切りの下にあること。サーバは `.claude/hooks/lib_work_root.py` でこれを取り（環境に `SINGLEFS_DATA_ROOT` があれば環境に従う）、`control install`、`start`、`check` はこの行だけを見る。書いていない、共有ルートの外にあるときは 78 で終了し、`multi-host.env` にこの行を足すよう出口に書く。既定値は補わない。三つ目は `HOSTS=<このマシンの IP> <二台目の IP>`：各マシンの有線直結の区間のアドレスを空白で区切る。どれが自分かはこのマシンのネットワークインターフェースのアドレス（`ip -o addr show`）で見分け、二台目はもう一方で、ssh はそこへ直接つなぐ。ユーザー名は各マシンの `~/.ssh/config` に任せる。二台目のアドレスは共用の取り方 `scripts/hosts/multi_host_addresses.py` だけを通して取り、それはマルチホスト設定をまるごと判定に通してからアドレスを返す：キーが欠けている、判定が知らないキーがある、壊れた行があると取れず、サーバは起動せず、`control start` は 78 で終了する。二台で値が違うものはマシンごとの三つのキー `CARGO_BIN_DIRECTORY_BY_HOST`、`BUILD_ROOT_BY_HOST`、`SLICE_MEMORY_CAP_BY_HOST` に書く：値は空白で区切った `<アドレス>=<値>` で、各項は最初の `=` で切り、`HOSTS` の各マシンにちょうど一項、アドレスはどれも `HOSTS` にあるものとし、あるマシンの値が要るときはそのマシンのアドレスの項を取る。サーバが読むのは `SLICE_MEMORY_CAP_BY_HOST`（固定値）で、一台抜けている、`HOSTS` にないアドレスがあると設定が壊れていると判定する。分割の各片は `TASK_SERVER_SHARD_HOST` で自分が動くマシンの `HOSTS` のアドレスを受け取る。

**サーバ起動時に何を判定するか。** 四項目で、どれか一つでも通らなければサーバは起動せず、78 で終了し、どの項目かを示して「## NFS 共有」を指す：

- 設定：`NFS_SHARED_ROOTS` があり、各区切りがこのマシン上のディレクトリである。`HOSTS` でこのマシンと二台目を見分けられる（次の二項目はそれで二台目につなぐ）；
- エクスポート：このマシンの `/var/lib/nfs/etab` に各区切りのエクスポート行がある；
- マウント：二台目で各区切りの `stat -f -c %T -- <ルート>/.` が `nfs` を読む（入ると自動マウントが働く）。二台目への ssh が一度時間切れになったらまず「遅い」として 2 分間の確かめ直しの期間に入り、5 秒ごとに確かめ直す。どの回かで返ればサービスのログと `/health` の `nfs` 欄（`slow_last`）に「遅い」と記録するだけで、通知せず二台目にも割り当て続ける。期間が終わっても通らないときだけ不合格（「二台目につながらない」）としてメッセージを送る；
- 読み書き：両方向に探針ファイルを一つずつ書き、相手が読める（このマシンで書いて二台目で読み、二台目で書いてこのマシンで読む）。

`task-server/control check` は既定ではサーバの `/health` の `nfs` 欄にある最新の結論を読み（出力にいつ判定したものかを書く）、数秒で結論を出す。`control check --probe [--limit <秒>]` はこの四項目をその場で判定し、各項目の開始と終了に一行ずつ出力し、合計時間は `--limit`（既定 60 秒）まで、時間切れになればどの項目で止まっているかを出力して 1 で終了する。`/health` の `nfs` 欄も同じ四項目を報告するが、「読み書き」の項目（両方向の探針）はサーバが起動したときの一回の探針の結論で、その後はやり直さない。サーバが起動した後は前の三項目だけを毎分確かめ直し、通らなくなったものはタスクが並んでいる・走っているセッションへサービスが直接メッセージを送る（「## セッションへのメッセージ」）。

**通らないとき。**

- 設定が通らない：「マルチホスト設定のどのキーか」のとおりキーを補うか書き方を直し、ディレクトリがなければ先に作る。
- エクスポートが通らない：`/etc/exports` に足りない行を補い、`sudo exportfs -ra`。NFS サーバが動いていなければ `sudo systemctl enable --now nfs-server`。
- マウントが通らない：二台目で上の書き方のとおり `/etc/fstab` の行を補うか直し、`sudo systemctl daemon-reload`。マウントのユニットが `failed` になっていれば `sudo systemctl reset-failed "$(systemd-escape -p --suffix=mount <ルート>)"`、それから `ls <ルート>` でマウントを働かせる。マウントできないときは、まず有線直結セグメントが通じているか、このマシンでエクスポート先にしたクライアントのアドレスが二台目のものかを確かめる。
- 読み書きが通らない：多くは二台の uid、gid が合っていないか、エクスポート項目に `rw` がない。「uid」の段のとおりにする。

**確かめ方。** 三つ。それぞれコメントに書いたマシンで実行する：

```bash
stat -f -c %T -- <ルート>/.                   # 二台目で実行：nfs と出ればこのルートはマウントされている
cat /var/lib/nfs/etab                          # このマシンで実行：各ルートにエクスポート行があり、クライアントは二台目
echo probe > <ルート>/nfs-check-by-hand        # このマシンで実行：このマシンで書く
cat <ルート>/nfs-check-by-hand                 # 二台目で実行：二台目で probe が読める
echo probe > <ルート>/nfs-check-peer           # 二台目で実行：二台目で書く
cat <ルート>/nfs-check-peer                    # このマシンで実行：このマシンで probe が読める
rm <ルート>/nfs-check-by-hand <ルート>/nfs-check-peer   # 確かめ終えたら二つのファイルを消す
```

## 投入の書き方

```bash
task-server/task submit -- <コマンド…>              # タスク番号を表示する。長いタスクと判定したものだけ確認票も出して確認待ちにし、列には入れない。それ以外はすぐ列に入れ、「直接进队：…」（長いタスクではない理由）の一行を出す。環境中の SINGLEFS_RUN_SCOPE のようなホワイトリストの変数はそのまま持っていく。セッションの受信先が読めなければその場で拒む
task-server/task submit --whole-package-confirmed <確認ファイル> -- <コマンド…>  # パッケージ全体のテストに三度の確認を書いたファイルを付ける（上の「パッケージ全体のテストには確認の印が要る」）。付けなければその場で拒む
task-server/task confirm <番号> --why '<…>'          # 二時間の通知で範囲と所要時間を確かめ、本当にそれだけ要ると確認する。以後は通知しない（上の「二時間の通知」）。四時間の上限は通らない（上の「四時間の上限」）。oversized-budget、fills-any-cap の通知が開いているタスクで範囲を確かめ本当にそれだけ要るときも、これで「そのまま走らせる」と記録する（二時間の線は見ない。サービスを入れ替えた後も報告済みの種類は認める）。記録した種類は再送しない
task-server/task confirm <番号> --items <N> --tasks <M>  # 長いタスクと判定されたものは、確認票で範囲を確かめてから確認する：二つの数がどちらもサービスが今数えたものと同じときだけ列に入る（投入時刻で位置が決まる）。合わなければ 3 で終わり、サービスの確認票を出す。すぐ列に入れたタスクにはこれまでどおり応じ、「已在队里，不用确认」（すでに列にあり、確認は要らない）と答えて 0 で終わり、二つの数は照合しない
task-server/task wait <番号>                        # 結末を取る：完了時に終了、最終行 TASK_SERVER_RESULT …、終了コードはタスクのもの。セッションの受信先を記録したタスクは起こされるために起動しなくてよい（「## セッションへのメッセージ」）
task-server/task status [<番号>]                     # このセッションの確認待ち・待ち・実行中・完了して未受領のもの。番号を与えた確認待ちのタスクには今計算した確認票を出す。待ちには「待ち：…」、実行中にはどれだけ走ったか、ログがどれだけ伸びていないかを付ける
task-server/task cancel <番号>                       # 投入したセッションだけ。止まったことを読み戻したら、同じ取り消しの中でこのタスクの現場を消し、何個消したか、消す前と後の大きさを出す（本機の組のビルドディレクトリは組に戻し、消さない。二台目に送られ途中で止められたその回は `multi-host-run.sh` がビルドディレクトリごと消す）
task-server/task log <番号>                          # 最後の試行のログ（最後の 200 行。--all で全体。--attempt <何回目> でその回。タスクかその回がなければ 4 で終了）

も付け、セッションへのメッセージは「检查代码有没有逻辑循环或内存泄漏：…」の段落を別の行に書く（上の「上限に当たった瞬間のメモリ内訳」の段落の後半と同じもの）。提案はその段落に沿って種類ごとにコードを確かめることで、ループやリークがあれば取り消してコードを直してから投入し直し、規模がもともとそれだけ大きいなら放っておく。スレッド総数が登録数を大きく超えた場合（`threads-over-registered`）は、ある試行のスレッド総数が三回続けて登録スレッド数の二倍を超え、そのうち実行可能なものも登録数を超え、スレッドが最も多い一つのプロセス自身も登録数の二倍を超えたときで、根拠にスレッド数、実行可能な数、登録数、スレッドが最も多いプロセス名を書く。眠っているスレッドを大量に起こすだけのコンパイラやリンカは数えず、試行ごとに一度だけ知らせ、タスクはそのまま走らせる。各種類（投入時の拒否、投入時の警告、各結末、停滞の疑い、未受領の結末も含む）の判定、動作、提案、誰も対処しないときどうするかは、`task_server_lib.py` のファイル頭「异常表」のその行だけに従う：`next=` の先頭はその行の提案で、その種類で確かめるものを名指しする（例：`io-wait` はそのマシンのディスクと NFS、`/proc/pressure/io` を確かめる。`cleanup-pending` は残ったプロセスのコマンド行と、スクリプトが子プロセスを待たずに終わっていないかを確かめる）。その後に今回の具体的な数が続く。サービスはこのタスク（分割したものは子タスクも含む）のこれらを「対処が要る」通知として記録し、そのタスクを待っている `task wait <番号>` は新しい通知を読むと一行 `TASK_SERVER_ATTENTION task=<番号> type=needs-attention kind=<種類> [reminded_after_seconds=<秒>] basis=<根拠の数> why=<理由> next=<出口>` を出して 230 で終了する（`why=` が 300 文字を超えるときはその長さで切って末尾に「…」を付け、全文はサービスがセッションに送る通知の「原因：」の行にある）。タスクは並んだまま、または走ったままで、サービスは手を触れていない。`next=` に従って対処し、`wait` を起動し直して待ち続ける。すでに結末があるタスク（主作業ツリーの書き換えが正常に終わらなかったものなど）では、この行は `TASK_SERVER_REASON` の前に出て、終了コードはタスクのままである。同じタスクの同じ種類の通知は一つの通知しきい値につき一度しか起こさず、`wait` を起動し直しても繰り返さない。次のしきい値（起点の二倍、四倍……）に達したときにだけ再び起こし、時間で判定する種類は `kind=` の後に `reminded_after_seconds=<今回達したしきい値、秒>` を書く。知らせたしきい値はサービスのデータベースに記録するので、サービスを再起動してもデータベースから読み戻し、同じしきい値はもう出さない。キューに長く待っているものは、待ち理由がまだ判定されていない回（サービスが再起動したばかりで、この回がまだそれに届いていない）には出さず、理由が判定された回に出す。もう一種類 `booking-beyond-idle-machine`（どのマシンでも起動できない）がある。キューが、あるコマンドは今どのマシンにも収まらず、しかもそのマシンでサービスが走らせているタスクがすべて終わってメモリを返しても、マシン全体の空きが必要量に届かないと判定したとき（記帳が使える上限に張り付いている場合や、上限を固定した場合に多い）、知らせるだけでタスクは並べたままにする。根拠にはマシンごとに、返した後でもまだ何が足りないかを書き、提案は上限が一台分に張り付いている理由の確認（固定した上限なら固定値と多機配置を見て、そこまで要らなければ固定を外す）である。一度だけ送る。このタスクの記帳は通常、一台分の線（`oversized-budget`）にも届くが、起動できず「そのまま走らせる」という出口が使えないので、この種類が開いている間は `oversized-budget` をあわせては出さず（キューの一巡が「どのマシンでも起動できない」をまだ判定していない待機中のタスクにも出さない：投入時に見つかった分がこの種類より先に出ることはない）、起動できるようになってから出す。このタスクは「前に並んでいてまだ起動していないもの」に数えず、並べておける時間を過ぎても後ろのタスクを止めない。マシン全体の空きが必要量に戻れば自分で起動する。これらの通知はサービスが投入したセッションへも直接メッセージで送る（「## セッションへのメッセージ」）。記帳は `wait` と同じもので、送ったものは `wait` がもう出さず、`wait` が出したものは送らない。サービスの健全性は `wait` の担当ではない。サービスが自分で見張り、同じようにメッセージを送る。

コマンドを包まず、資源の引数も書かない：`run-with-memory-cap.sh <上限>`、`host-dispatch.py … --`、`multi-host-run.sh … --`、`nice`、`timeout`、`capped.sh`、`two-logs.sh`、`gpu-quiesce-run.sh` とスクリプト自身の `--memory`、`--memory-cap`、`--threads`、`--peer`、`--local-only`、`SINGLEFS_THREAD_CAP`：これらはサーバが行い、書けばその場で拒否してどれを外すかを示す。ホワイトリスト外の環境変数はその場で拒否して名前を示す。本当に必要なコマンドは `task-server/task submit -- env <名前>=<値> <コマンド…>` と書く。退役した変数（`SINGLEFS_HEAVY_TESTS`、`GATE_MUTATION_START_OVER`）は、環境に設定しても、コマンドに書いても（`env` の後とコマンドの前の `名前=値`）その場で拒否し、拒否の説明で名前を示して出口を書く。一覧は `task_server_lib.py` の `RETIRED_VARIABLES`。

二台目に送れない三種類は投入のときにその場で断る（ユーザー：「改成提交时当场拒（推荐）：不再悄悄改派本机：碰到这三种就在提交时报错、点名是哪个路径或哪一族、出路写怎么改，任务不跑。」）：`task submit` は 3 で終了し、その一文と出口を出し、タスクは並ばず走らない。一つ目は、作業ディレクトリとコマンドの中の絶対パス（シェルの語全体だけを見る：`/` で始まる語全体、`名前=絶対パス` と `--オプション=絶対パス` の値、`bash -c` のスクリプトの語をシェルの語に切った一つずつ。ほかの語の途中に挟まった `/`（引数の値の「（接的是 /）」など）は数えない）に、マルチホスト設定の `NFS_SHARED_ROOTS` のどの区切りの下にもないものがある場合で、そのパスを挙げ、出口はどれかの区切りの下に移すこと。`/dev/null`、`/usr/`、`/bin/` のように二台で同じシステムのパスは数えない。`/tmp` の下のものも同じく断り、その一文に再起動で `/tmp` が消えることを添える。二つ目は、コマンドに渡す `SINGLEFS_DATA_ROOT`、`SINGLEFS_WORK_ROOT` に共有ルートの下にないものがある場合で、変数と値を挙げ、出口はマルチホスト設定を整えること。三つ目は、コマンドが登録表 `.claude/gate.d/verdict-library-scripts.tsv` の判定ライブラリを持つ行を指し、その行の三列目がまだ `prune-server` でない場合で、その系統を挙げ、出口はその系統を prune-server につなぎ、三列目を `prune-server` に書き換えること。登録表が読めない、壊れているものも同じく断る。

一時 prune-server のラッパー（`python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <パス>] -- <元のコマンド>`）はスクリプトの自己検証専用である。そこから剥がした元のコマンドにコンパイルする cargo がある、（見分け方はサービスがビルドディレクトリを決めるときと同じ）なら、投入のときに上と同じ形でその場で断る：`task submit` は 3 で終了し、その一文（元のコマンドを挙げる）と出口（ラッパーを外して投入し直す）を出し、タスクは並ばず走らない。剥がすのは判定のためだけで、受け付けたものはラッパーごとそのまま走る。ビルドディレクトリは外側のコマンドにだけ与え、サービスはラッパーを剥がして合わせることはしない。`--server-binary` を付けないラッパー（コマンドの前の代入にもタスクの環境にも `PRUNE_SERVER_BINARY` がない場合）は、サービスが与えたビルドディレクトリの中で prune-server 自身をコンパイルするので、サービスは外側のこのコマンドをコンパイルするものとして扱う。本機に送っても二台目に送ってもビルドディレクトリを与え、`--server-binary` 付きのものはコンパイルせず、与えない。検証クレートの `cargo test` は本物のサービスに対して走らせ、このラッパーはかぶせない。

パッケージを名指ししないワークスペース全体のビルドは投入のときにその場で断る（ユーザー：「8105打回 让他重新写重新确认范围」。タスク 8105 は `-p` なしの `cargo build --offline --all-targets` で予測 49.0 GiB）。投入されたコマンドのコマンド位置で直接起動されるコンパイルする cargo（`build`、`check`、`clippy`、`test`、`run`、`bench`、`doc` とその一文字の別名。`bash -c` と `cd` はたどる）は、`--workspace` / `--all` があれば断る。`-p` / `--package` がなく、cargo のマニフェストの探し方（起動したディレクトリから上へ最初の `Cargo.toml`）で仮想マニフェスト（`[workspace]` だけで `[package]` がない。リポジトリのルートのものがそれ）に当たるものも断り、起動したディレクトリが分からない、マニフェストが読めないものも同じく断る。`task submit` は 3 で終了し、その一文（どの cargo を、どのディレクトリで、どのマニフェストで起動したか）と出口を出す：ビルドするパッケージを名指しする（`-p <パッケージ>`、検証クレートは `-p singlefs-verification`）。リポジトリ全体を走らせるものは `scripts/gate/merge-and-verify.sh` かコミット時のゲートを通す。パッケージ自身のマニフェストに当たるもの（`scripts/experiment-apparatus/`、`prune-server/` のようにそれ自体がワークスペースのパッケージ、またはメンバーのディレクトリの中で起動したもの）はそのパッケージだけをビルドするので受け付ける。エントリスクリプトやゲートの中で起動する cargo は判定しない（サービスは投入されたコマンドだけを見る）。`cargo fmt`、`metadata`、`tree`、`clean` はコンパイルしないので判定しない。

## セッションへのメッセージ

ユーザー：「不是你通知 而是 task-server 通知发起的对话」「包括报错 长时间没有响应 都可以这样通知」。`task submit` はセッションの Bash で走り、環境の `CLAUDE_CODE_MESSAGING_SOCKET`（セッションの受信 socket）と `CLAUDE_CODE_MESSAGING_TOKEN`（セッションのトークン）を読んでタスクと一緒にサービスへ渡す。サービスはタスクに記録し、トークンはログにも `status` にも `/tasks/<番号>` の返答にも出さない。読めないときはその場で拒み（終了コード 3）、出口は Claude Code セッションの Bash から投入すること（サブエージェントはタスクを投入しない）。受信 socket は投入時のものを使わない：送る前に毎回、サービスはタスクに記録したセッション番号でセッション登録（`~/.claude/sessions/*.json`、プロセスごとに一つ。読むのは `sessionId`、`messagingSocketPath`、`pid` だけ）を読み、セッション番号が同じでプロセスがまだ生きているもののうち最後に起動した一つの `messagingSocketPath` を取る。トークンは投入時に持ってきたもの。セッションが再起動して socket が変わったものは新しい方へ送り、見つからないもの（セッションが閉じた）は下の「送れない」のとおり警告を書く。

サービスは次の場合にその socket へメッセージを一通送る：

- タスクに結末が出た（`wait` が `TASK_SERVER_RESULT` を出すすべての種類）：一度だけ送る。送れたらサービスは取られたものとして記録する（`wait` が取ったのと同じ）。セッションがすでに `wait` で取ったものは送らない。
- 対処が要る通知（`task_server_lib.py` ファイル頭 `ATTENTION_KINDS` の十八種類）と停滞の疑い：同じタスクの同じ種類の通知は同じしきい値では一度だけ送り、記帳は `wait` と同じものを使う。この記帳はすべてデータベースにある（対処が要る通知はタスク行、報告済みの停滞の疑いの区間・サービス健全性をどのセッションに送ったか・記帳ずれをどのしきい値まで通知したかは再起動をまたいで残る記録）ため、サービスを再起動しても同じものは送り直さない。結末が出た時にサービスの記録した所要時間が 7200 秒を超え、`.claude/long-run-split-exempt` にもない項目には `long-run-split` を一度送る（片または全体の所要時間で判定）。出口は `.claude/rules/long-run-split.md`。フック入れ替えが 7 で終了した（前回の入れ替えが完了していないため止められた）場合は、止められたセッションに `workspace-write-blocked` を一度送る。ある試行のスレッド総数が三回続けて登録スレッド数の二倍を超え、そのうち実行可能なものも登録数を超えたときは `threads-over-registered` を一度送る（根拠にスレッド数、登録数、スレッドが最も多いプロセス名を書く。タスクはそのまま走らせて止めない。眠っているスレッドを大量に起こすだけのコンパイラやリンカは数えない）。時間で判定する種類は時間が倍になるごとに送り直す。しきい値が時間で上がらない種類（`oversized-budget`、`fills-any-cap`、`long-run-unconfirmed`、`cleanup-pending`、`shard-advance-failed`）は、送ってから 30 分たってもまだ残っていればもう一度送り、その後は倍になるごとに送る。一行目に「没处置、第 <回> 回再推」と書き、本文に前に何を送ったか、今何が足りないかを書く。
- 未受領の結末：親タスクの結末が 30 分たっても投入したセッションに届いていない（結末のメッセージが届かず、`wait` も起動していない）ものはもう一度送り、その後は倍になるごとに送る。一行目は「task-server：结局（任务已结束，这条结局还没人取）任务 <号> <中文名>（<種類>，退 <コード>；第 <回> 回，上一回在 <日付>）」で、送れたら受領済みとして記録する。
- 投入して 30 分確認されずサービスが取り消したもの：結末として送り、本文に「没确认，已取消」を含む。
- タスク外プロセスの空回り：二台を 5 分ごとに調べ、タスク slice の外にあり、累計 CPU が 30 分以上で経過時間の半分以上を占めるプロセスを、それが属するセッションだけに知らせる。残っていれば 30 分ごとにまた知らせる。属するセッションが分かるローカルのプロセスは二回知らせても残っていればサービスがプロセス番号で止めてそのセッションに伝える。発起セッションが分からないもの（第二台のもの、発起セッションが終了したもの）はすぐに終了させ、警告に書くだけとする。セッションプロセスとその祖先、systemd ユニットとシステムサービス、sshd、エディタには触らない。
- サービスの健全性：データベースに書けない、振り分けが先頭を起動できると判定したのに起動できないまま、進み具合の確認で収められるのに起動していない、サービスのユニットがない、NFS 共有の前の三項目が通らない、第二のホストが 180 秒使えない。GPU を有効にしている場合は GPU サービスのカード故障と判定できないブロックも加える（毎分多くても一度 `python3 gpu-verification-server/control cards-failed` を読む）。タスクが並んでいる・走っているすべてのセッションへ送り、同じものは同じセッションへ一度だけ、直ってからまた壊れたときにまた送る。GPU サービスのカード故障はホスト・サービスプロセス・カードの単位で一件とし、次の手順はそのカードのリセットをユーザーに依頼する。判定できないブロックはプロセス番号を含めずホストとストリーム（族とストリームキー先頭）ごとにまとめ、本文にそのストリームで現在判定できないブロック数と先頭数件のブロック番号を書き、次の手順は各行の `claim=` に従う：`released`・`not-held` は占有を解放済みで別のホストが試み、`kept` は未解放で占有期限の経過を待ち、取得できないか判別できない値は推測せず「GPU サービスのカード故障行を判別できない」と報じる。今回の読み取りで見えなかった項目のうち、判定できないストリーム（GPU サービス再起動後に一度再試行し、同じストリームが再び判定できなくても再送しない）と、カード故障のあったホストでタスクサービス起動後に一度も読み取りが成功していないもの（`cards-failed` が `unreadable`・`unreachable` と返す場合）の二種類は回復扱いとしない。警報記録には同じ項目を一度だけ書き、タスクサービスの再起動後も書き直さない。サービス自体が落ちているときは送れない：`task wait` は 60 秒続けてつながらなければエラーで終わり、`task submit` はつながらなければその場で報告する。

本文の一行目は種類とタスクの今の状態を先に書き、一行目だけで見分けられる。「task-server：结局（任务已结束）任务 <番号> <中文名>（<種類>，退 <コード>；第 1 回）」、「task-server：提醒（任务还在排 / 还在跑，不是结局）任务 <番号> <中文名>（<種類>；第 <回> 回，上一回在 <日付>）」、「task-server：疑似卡住（任务还在跑、服务没停它）任务 <番号> 疑似卡住（suspected-stall，第 <区間> 段；第 1 回）」、または「task-server：服务健康 <どれ>」。どの種類にも中国語名を付け、英語の種類名は括弧の中に置く。送り直しは何回目かと前回の日付を書く。その後に `wait` が出す行どおり根拠・理由・出口を書き、「长跑已确认」のような確認印の行は根拠と出口の後に置き、続いてログ、最後に `wait` のその行をそのまま置く。事実と出口だけを書く。送れない（socket がない、つながらない、セッションが閉じた）ときは送り直し続けない。サービスのログと警告記録に `inbox-unreachable` を一件書き、そのタスクの最後の試行のログに `TASK_SERVER_INBOX` で始まる一行を足し、タスクはそのまま続く。受け手が空いていれば Claude Code はこのメッセージで新しいターンを始める。権限確認を飛ばすセッションでは、ユーザーが承認するまで保留される。

`task wait` は残す：結末と通知はこれまでどおり取れるが、起こされるために起動する必要はもうない。`task-server/control watch` は削除した（2 で終了し、出口の一文を出す）。サービスの健全性を手で一度確かめるには `control check` を使う。

行の書き方：まず一行 `{"type":"auth","token":"<セッションのトークン>"}`、次に一行 `{"type":"user","message":{"role":"user","content":"<本文>"}}`。二行は接続前に用意して一度に書く（Claude Code は 30 秒以内に一行そろわない接続を閉じる）。出典：受信 socket と認証行は Claude Code の文書 https://code.claude.com/docs/en/cross-session-messaging.md の「The session's inbox socket」節。user の行の書き方は文書に書かれておらず、Claude Code のバイナリ自身のデバッグログの「[uds-messaging] Inject messages」の一文にある例から取った。文書に行の書式がないので、Claude Code を更新したら確かめ直すこと。

## ソースのファイル頭の宣言

サービスはソースファイルの先頭 60 行にある宣言の行から、コマンドが何を要るかを見分ける。呼び出し側はこれまでどおり額を書かない。宣言はその入口スクリプトかパッケージを受け持つセッションが加え、サービスは読むだけである：

| 書く場所 | 書き方 | サービスの使い方 |
|---|---|---|
| 入口スクリプト | `# task-server-shards: <引数>…`、`# task-server-resumable: <引数>…` | 分割と再開（`task_server_lib.py` のファイル頭「分片」「续跑」） |
| 入口スクリプト | `# task-server-compiles: yes` | ビルドする：コマンドの層で cargo が見えないゲートの入口もビルドするものとしてビルドディレクトリを渡す（二台とも `CARGO_TARGET_DIR`、同じ木の組の一つ。分割の計画・各片・合併は親タスクに従う）。別の語を書いたものは差し戻す。`--selftest` だけのもの、`--list-items` / `--help` / `-h` 付きのものは数えない |

カードを借りる・要るという宣言（`# task-server-card-lease:`、`# task-server-gpu-cards:`、`# task-server-gpu-arguments:`）はサービスが認めない：投入したコマンドと `bash -c` の中のコマンドの位置にある各コマンドが起動するスクリプトの先頭 60 行にそのどれかが書いてあれば、投入時にその場で断る（`task submit` は 3 で終了、異常表 `card-declaration`）。説明の頭の一文は「卡归 GPU 批处理验证服务，任务不领卡」（カードは GPU バッチ検証サービスのもので、タスクはカードを借りない）で、そのスクリプトと書いてあった宣言を挙げ、出口はその行を消し、カードの要る部分を判定ライブラリに判定待ちの行を書いて GPU サービスに判定させる形に改め（「## カード」を参照）、投入し直すこと。判定は `task_server_lib.py` の `card_declaration_problem`。

メモリの割り当て（サービス自身のデータベースにある試行の記録。`task_server_lib.py` のファイル頭「资源记录」。決め方はこの一つだけで、スクリプトも呼び出し側もメモリ量を申告せず、入口のファイル頭にもメモリの宣言はない）：
- 同じコマンドキー（同じ種類のコマンド）で走りきった試行がデータベースにあれば、直近 5 回の最大（走りきった試行は測ったピーク、上限に当たった試行はその回の上限）を取り、上限も記帳もそれに等しく、1.5 倍しない。親タスクと同じ回の兄弟片の記録は借りない（分割の片のキーは片番号だけで片数を含まない。片数が変わっても同じ片番号は同じキーに載るが、上限を決めるときは片数が同じ回の記録だけを読む）。このキー（片数込み）自身に記録がないときは記録のないコマンドと同じに決め、ほかのキーの記録は借りない。範囲を選ぶだけのオプションはキーに入れない：`--item`、`--only`、`--skip`、`--exact`、`--fingerprint-of`、`--crash-expand-up-to` とその値、`cargo test` のテスト名の絞り込み、セルや項目を名指す環境変数（`*_SELFTEST_CELLS`、`GATE_MUTATION_ROW_SELECTION`）はすべて外し、同じ入口は項目を名指すかどうか、どれを名指すかにかかわらず一つの記録を共有する。ゲート code-tooling の break-switch-replay と crash-point-replay の crash-case-replay の二つのセルが名指す `--item` は従来どおり項目ごとに一つのキー（`scripts/hosts/memory_peaks_lib.py` のファイル冒頭「键」③）。このリポジトリのゲートと入口スクリプト（`.claude/gate.d/`、`scripts/`、`.claude/scripts/` の下のもの）のコマンド語は、リポジトリ内の相対パスでキーに入る：絶対パス（メインの作業ツリー、スナップショット、リポジトリの複製にある同じファイル）で書いても相対パスで書いても同じキーになる（`task_server_lib.py` の `repository_script_word`）。コマンドの中で `-` で始まらない語（リポジトリのルートなど）はオプションのあとに並べてキーに入り、ルートをオプションの前に書いても後に書いても同じキーになる（`selection_class_words`）。分割タスクの計画段階のキーは、範囲縮小の変数 `SINGLEFS_CRASH_AMPLIFICATION_EXPAND_UP_TO` の代入も外す（縮小の深さは各分割がいくつのクラッシュ状態を判定するかだけを変え、計画段階はビルドと分割しかしない）。各分割のキーは引き続きそれを含む。スクリプトは自分の必要なメモリを決して報告せず、サービスもそうした行を読まない。`cargo test` は同じパッケージ・同じ特性・同じプロファイルなら一つのキーにまとめる：キーにはパッケージ（`-p`）、特性（`--features`、`--all-features`、`--no-default-features`）、プロファイル（`--release`、`--profile`）だけを残し、名指したテストターゲット（`--test`、`--lib`、`--bin`、`--example`、`--bench`）と `--` の後のテストの絞り込みは入れない。違うターゲットを名指したコマンドも同じ記録から始める。取り消された回、コマンド自身が 0 以外で終わった回、止まったと判定されたか四時間で止められた回のピークは下限としてだけ数える：窓の中の最大より大きいときだけ引き上げ、窓が空なら 4G より大きいときだけそれで始め、小さいものは引き下げない（次の回は当たったことのある低い段からやり直さない）。上がりも下がりもする：窓の中で当たったばかりの段はすぐ見え、古いものは窓を出れば数えず、その後の数回がどれも小さければ起点も下がる。このキーで走りきった試行がなければ 4G から始め、上限に当たったら 1.5 倍して並べ直す（4096M → 6144M → 9216M …）。コマンド自身が出す「どれだけ要るか」の行は一切認めない。実際のピークの記録があるものは 4G に引き上げず、1 GiB の下限だけを設ける：記録のピークはプロセスのメモリ（`anon` と `shmem`）だけを数えるが、上限はファイルを読んで入るページキャッシュも収めなければならない。そのため最初の上限も並べ直しの上限も 1 GiB を下回らず、記帳もその上限で行う（あるタスクはファイルを一つ読むだけの python3 スクリプトで、ピーク 5 MiB、上限 3M・5M・8M のいずれも 250 で終わった）。下限より大きい記録は記録に従い、固定した上限はこの下限の対象外で下限より低くても固定値のまま、下限がそのマシンの与えられる最大の上限を超えることはない。
- 上限に当たって並べ直したとき、並べ直した回はこのタスクの前の回が同じ台で使ったビルドディレクトリをまず取り、そこで続けてビルドする（下の「## ビルドディレクトリ」）。別の台に移った回では、前の回のものは元の台の組にそのまま残る。二台は同じ一段を通る：本機は `CARGO_TARGET_DIR` で指し、二台目は `--reuse-build-directory <そのもののラベル>` を付ける。

## ビルドディレクトリ

ビルドディレクトリは「どの木 × どの台」ごとに与える（`task_server_lib.py` のファイル頭「编译目录」）：
- 木は、タスクの `--cwd` をシンボリックリンクを解いてから上へたどり、最初に `.git` がある階層（リポジトリの複製は git の作業木で、それぞれが一本の木）。同じ木で同じ台に続けて投入したビルドするタスクは、この木のその台での組のビルドディレクトリを続けて使い、cargo は指紋で変わったものだけを再ビルドする。違う木はそれぞれ自分の組を持ち、一つを共用することはない（違う木がビルドディレクトリを共用し、コピーが古い更新時刻を保ったため cargo が再ビルド不要と判定した二回、`records/2026-09-16-subagent拆分提案.md` の第五十二節と第六十九節）。
- 一つの木につき一台あたり最大 3 個（`task_server.py` の `BUILD_POOL_SLOTS_PER_TREE`。ビルドディレクトリのディスク占有の判定と一緒に決める）：一つの試行は空いているものを一つ取り、終わったら返す。まずこのタスクの前の回が同じ台で使ったもの、次に空いている中で最近使ったものを取り、組が満杯でないときだけ新しく開く。全部ふさがっていて満杯なら待ち、待ち理由にビルドディレクトリの組が満杯だと名指す。新しく開くものもビルドディレクトリのディスク占有の判定を通る。組のものを続けて使うときは、その判定はこのコマンドのディスク占有のピークから、それがすでに占めている分（試行の後始末ごとに測ったピークで記録する）を差し引く。
- 本機のものは `TASK_SERVER_BUILD_DIRECTORY` の下で、名前は `tree-<ツリーのパスの sha256 の先頭 8 桁>-<ランダムな 16 進 6 桁>`（タスク番号も試行ラベルも含めない。組の中のディレクトリは後のタスクが続けて使うので、開いたタスクの番号が付いていると `ps` で別のタスクと取り違える）、二台目のものはマルチホスト設定の `BUILD_ROOT_BY_HOST` のうち自分の項の下の `builds/`（`multi-host-run.sh --keep-build-directory` で残し、`--reuse-build-directory` で続けて使う）。二台の組は互いに関係しない。
- 削除：「服务build之后必须删除历史」「自己用完自己删」は木ごとに数える——木（`--cwd` のシンボリックリンクを解いてから上へ最初に `.git` がある階層、どこにもなければ解いた後の `--cwd` そのもの）が消されたらその組を丸ごと消す。サーバは起動時に一度掃き、その後は 10 分ごとに裏でもう一度掃く。中のファイルを開いているプロセスがあるものは消さず、警告 `build-directory-left` を書き、次の掃除でまた試す。結末の記録、`task clean`、取り消しでは本機の組のビルドディレクトリを消さない（二台目に送られ途中で失敗した、または止められたその回はビルドディレクトリごと消される）。同じ掃除で、本機のビルド根の下でどの組にも入っておらず名前が `task-<ライブラリのラベル>-<番号>-<回>`（試行のラベルで名付けたもの）のディレクトリも消す（中のファイルを開いているプロセスがあるものは消さず、警告 `build-directory-left` を書き、次の掃除でまた試す）。
- 呼び出し側が自分でリポジトリ外の `CARGO_TARGET_DIR` を与えたものはそのまま使い、消さず、組に入れない。リポジトリの中を指すものは投入時に断る。

## 一時停止と再開

prune-server のバイナリ入れ替えや判定ライブラリの古い行の削除のように、ほかのセッションのタスクが一つも動いていない時間帯が要る作業は、自分も `task submit` でコマンドを投入することが多い。`control stop` は使えない。サーバ停止中は誰も投入できず、すでに `task wait` している側も 60 秒で 78 を返して終わる。代わりに一時停止を使い、作業するセッションを通す（そのセッションのタスクは停止中でも通常どおり起動する）。

```bash
python3 task-server/control pause --reason "判定ライブラリの古い行を消す" --allow-session <作業するセッション>   # 一時停止：ほかのセッションのタスクは起動しない。通したセッションのタスクは通常どおり並び起動する。投入は受け付け、status / wait / log / cancel は応答する
python3 task-server/control check                                                                              # 「…、放行会话 <番号>、在跑 N 个、别的会话在跑 0 个」（通したセッション・実行 N 件・ほかのセッションの実行 0 件）と出るまで繰り返す
# …時間帯が要る作業（作業するセッションが task submit でコマンドを投入する）…
python3 task-server/control resume                                                                             # 再開：待っていたものは通常どおり起動し、通したセッションの指定も一緒に消える
```

- 作業するセッションの番号：そのセッションで `python3 task-server/task status` を実行し、先頭行「会话 <番号>：…」の番号を使う（タスク投入時にサーバが記録したセッションで、`status` が各タスクに出すセッションと同じ欄）。通すのは一つのコマンドではなくセッションである：そのセッションがすでに待たせているもの、あとから投入するもの、分割タスクの子、上限超過で待ち行列へ戻った再試行はすべて通常どおり起動する。ほかのセッションのものと、セッションを持たない手動投入のものは待ったままで起動しない。通したセッションの待機中タスクの `status` は本当に待っている理由を出し、ほかのセッションの待機中タスクは「在等：服务暂停中（原因：…）」と出る。
- すでに停止中のサーバへ `pause --allow-session <別のセッション>` を送ると 0 で終わり、通すセッションを替える（理由と開始時刻は変えない）。`--allow-session` を付けない `pause` は通す指定に触れない。`resume` は通す指定も一緒に消す。タスクが一つも動いていない時間帯が要るなら、`--allow-session` なしで `pause` し、`control check` が実行 0 件と報告するまで待つ。
- 停止中、スケジューラは新しい試行を一つも起動しない（通したセッションのものを除く）。分割タスクの子、上限超過で待ち行列へ戻った再試行はすべて保留される。実行中のものは結果が出るまで走る（結果は書かれ、再試行は待ち行列へ戻るが起動はしない）。`pause` と試行の起動は一つのロックを共有するので、`pause` が 0 で終わった時点で起動中だった一件は記録済みで、`control check` の実行中件数にあとから割り込む試行はない。
- 一時停止の状態は、通したセッションも含めてサーバのデータベースに保存され（署名付き。データベース内の通したセッションを書き換えると検証に通らないものとして扱い、誰も通さない）、サーバを再起動しても通す指定ごと `resume` まで続く。すでに停止中のサーバへの `pause` は 0 で終わり、元の理由と開始時刻を変えない。
- `control check` は「暂停中（原因：…，起于…）、在跑 N 个」の一行を加えて出す。セッションを通しているときは「…、放行会话 <番号>、在跑 N 个、别的会话在跑 M 个」となる（M は実行中のうち通したセッションのものでない件数）。終了コードは 0 のまま、「振り分けが先頭を起動できると判定したのに起動できていない」も進み具合も判定しない。`/health` は `paused` と `pause`（`allow_session` と `other_running` を含む）を返し、`ok` は変わらない。待機中タスクの `status` には「在等：服务暂停中（原因：…）」と出る。
- 停止中もサービスは自分の健全性（データベースへの書き込み、ユニット、NFS、第二のホスト）を見続け、問題があればタスクが並んでいる・走っているセッションへメッセージを送る。
- `pause` と `resume` を送れるのはサーバを起動したユーザだけで、投入や取消と同じ判定（呼び出し側の uid がサーバ自身の uid か）を使う。
- 作業が終わったら必ず `resume` する。停止中のサーバは健全に見える（`check` は 0）ので、忘れると待機中のタスクはずっと待つ。

## ユニットの状態が読めないとき

突き合わせで試行のユニットの状態が読めない（`systemctl --user show` が起動できない、タイムアウトする、`ActiveState` を出さない）と、ユニットがあるかどうか判定できない。`result.json` を残した試行はその終了コードで締める。残していない試行は kill せず、締めず、結果も記録しない。試行は `running` のままで、時間切れで締めることもない。代わりに systemd を通さずにこの試行にまだプロセスがあるかを確かめる：このホストでは、起動マーカー `started` に記録した runner のプロセス番号が `/proc` にまだあるか、ユニットの cgroup、`attempt_runner` が書く `scope` ファイルが指す cgroup、この試行のラベルを環境に持つプロセスのいるメモリラッパーの scope の `cgroup.procs` が空かどうか。二台目に振った試行でクリーンアップの受領ファイルがまだ `pending` のものは、同じ ssh の経路で二台目でも同じコードを走らせ、`multi-host-run.sh` が記録した `runs/<ラベル>.pid` と `runs/<ラベル>.scope` を読む。cgroup がすべて読めて空（ディレクトリがもう消えていても空と数える）、記録したプロセス番号がどれも生きていない状態が 10 秒の猶予のあいだ続いたときだけ、結果を残さなかった試行として `launcher-lost` を記録する。一つでも確かめられない（cgroup が読めない、起動マーカーがない、受領ファイルが読めない、二台目に繋がらない）ときは待ち続ける。

読めない間は、続けて 60 秒経つとタスクを投入したセッションに `unit-unreadable`（対処が要る通知。根拠には試行がどのホストで走っているか、このホストが状態を読めないユニット、確かめたプロセス番号と cgroup を書く）を送り、時間が倍になるごとに送り直す。同じしきい値では二度送らない。`/health` は不健全を返し、`problem` にこのホストがユニットの状態を読めない試行を書き、`unit_unreadable` 欄に一件ずつ（プロセスがまだある、すべてない、確かめられない、初回の確認がまだ）並べる。`control check` はそれで 78 を返す。このホストのユーザーレベルの systemd が直れば通常どおり判定する。判定方法は `task_server.py` のファイル頭 ①「读不到单元状态」。

## カード

カードは GPU バッチ検証サービス（`gpu-verification-server/`、`.claude/rules/verification.md`「卡只归 GPU 服务，任务不拿卡」）のもの：マルチホスト設定に従ってカードを開いてずっと持ち、開く前の静止化、カードの確認と判定もそちらが受け持つ。このサービスが配分するのは CPU とメモリだけ：コマンドやスクリプトの名前から誰がカードを要るかを見分けず、カードの割り当て・貸し出し・静止化・回収はしない。振り分けはメモリ、CPU の関門、ビルドディレクトリのディスク占有だけを見る。起動するコマンドの外側に静止化のラッパーは包まず、サービス自身の環境にあるカード選択の変数（`task_server_lib.py` の `CARD_CHOICE_VARIABLES`：`GPU_CARDS_BY_PRIORITY`、`CUDA_VISIBLE_DEVICES`）は試行に渡さない。ファイル頭にカードの宣言を書いた入口は投入時に断る（上の「## ソースのファイル頭の宣言」）。二つのサービスは判定ライブラリ（prune-server の RocksDB）だけでつながる：タスクは記録を走らせ、判定ライブラリに判定待ちの行を書き、結論を読むだけ。判定は `task_server.py` のファイル頭「卡」。

## 自己検証

`python3 task-server/task_server_lib.py --selftest`：各セルが本物の uvicorn を一時 socket 上に立て、メモリラッパー、二台目、`control` が使う systemctl を偽のスクリプトに、試行の scope を偽のディレクトリに置き換える。コンパイルせず、二台目に繋がず、カードも使わない。すべて模擬の世界で走るので、メイン agent がサーバのキューを通さず直接起動する（フックの一覧 `.claude/hooks/lib_project_code_runs.py` の `MAIN_AGENT_TOOLS_RUN_DIRECTLY`）。`TASK_SERVER_SELFTEST_CELLS=<セル,…>` で指名したセルだけを走らせる。セルを並列に走らせる数は、ホストごとの重い作業の既定スレッド数の登録値（`scripts/hosts/heavy_threads.py` をその場で読む）で、読めない（登録ファイルがない・壊れている、`SINGLEFS_THREAD_CAP` が正の整数でない）ときは全体を赤にし、コア数には戻さない。破壊スイッチ `TASK_SERVER_BREAK=<項目>` の表は `task_server_lib.py` 冒頭にある。

自己検証（とスイッチの回）が起こした試行ユニットは外側と一緒に止まる（`task_server.py` のファイル頭 ③「套在外层单元里的服务」）：サービスが自己検証の中で、あるいはそれ自身が一つの試行の中で動いているときは、`/proc/self/cgroup` から自分のいるユーザーレベルのユニットを見つけ、試行ユニットを起こすたびに `BindsTo=` と `After=` にそのユニットを付ける。外側のタスクが止まると（取り消し、止まったと判定して停止、上限に当たった）、systemd はそれらの試行ユニットをその場で止め、自分のタイムアウトを待たない。二台とも同じ一段を通る。本物のサービス（独立したサービスユニット）は付けない：試行ユニットはサービスの再起動をまたいで走り続けなければならない。
