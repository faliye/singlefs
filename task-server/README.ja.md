# task-server

[中文](README.md) · [English](README.en.md) · **日本語**

異常終了後に残る資源の占有、リモートの後始末の受領確認と診断ログは[タスクの後始末と GPU フェーズのログ](cleanup-protocol.md)を参照。

singlefs の統一タスクサーバ：プロジェクトのコードを走らせるタスク（軽い・重い・CPU・GPU）はすべてこれを経由して起動し、一つのキューに入り、サーバが資源と公平の規則でスケジュールし、別途の遅延は置かない：先頭が収まらないときは収まる後続を先に起動でき（割り込み）、投入から二時間を過ぎたものは先頭に上がる。規則は「## スケジューリング」。タスクを投入するのはメイン agent だけ（クライアント `task-server/task`、人も同じくこれを使う）で、サブ agent は `status`、`log` で結果を見るだけ。どのマシンに載せるか、メモリ枠、GPU が要るか、どのカードを割り当てるかはすべてサーバが決め、投入時にはこれらを受け付けない。

データベースを読み書きするプロセスはサーバだけ：uvicorn 上の FastAPI を、ユーザーレベルの systemd サービス `singlefs-task-server.service` として動かし、unix socket（`${XDG_RUNTIME_DIR}/singlefs-task-server/server.sock`、ディレクトリ 700。フルパスは 107 バイト以内で、超えるとサーバ・クライアント・`control` のいずれも 78 で終了し、そのパスとバイト数と上限を示す）だけを開き、TCP は開かない。データベースは組み込みの SQLite（WAL）で `~/.local/state/singlefs/task-server/` に置き、各行に HMAC の検証列を持つ。メモリの受入はサーバの一か所だけで判定する：収まるときだけ起動し、収まらないものはデータベースに並んだまま待つ。起動するタスクは引き続き `scripts/hosts/run-with-memory-cap.sh`（このマシン。「task-server が受入済み」のスイッチを立て、タスクごとの上限と slice の総上限のカーネル層での歯止めだけを行う）または `scripts/hosts/multi-host-run.sh --peer`（二台目）で包む。

| ファイル | 役割 |
|---|---|
| `task` | クライアント：`submit [--cwd <ディレクトリ>] -- <コマンド…>`、`wait <番号>`、`status [<番号>] [--json]`、`cancel <番号>`、`log <番号>`、`clean <番号>`。使い方と終了コードはファイル冒頭 |
| `control` | 導入と確認：`install [--dry-run]`、`check`（サーバの `/health` が報告するのは三つだけ：データベースに書けない、振り分け（ディスパッチ）が先頭を起動できると判定したのに三ラウンド続けて起動できなかった（起動できないと判定したもの——カード待ち、負荷待ち、交替のグループ待ちなど——は報告しない）、進み具合の確認：あるマシンが式で待機中の最小のタスクを収められるのに 10 分間一件も起動していない（振り分け自身の判定誤りを拾う））、`start`、`stop`、`clear-queue`（サーバ停止中にデータベースを退避してからタスクと試行の二つの表を空にする。資源記録は残す）、`pin-cap <コマンド…>` / `unpin-cap <コマンド…>`（サーバ経由でコマンドのメモリ上限を固定値にする・外す。読み戻して確かめてから 0 で終わる）、`pause [--reason <一文>] [--allow-session <セッション番号>]` / `resume`（キューの一時停止と再開。停止中も投入は受け付けるが、通したセッションのもの以外は起動しない。「## 一時停止と再開」） |
| `task_server.py` | サーバ（`serve`）：API、キュー、受入、ユニットの起動、突き合わせ、再試行、分割、資源記録。判定規則はファイル冒頭 |
| `attempt_runner.py` | 各試行のユニットの中でコマンドを起動し、終了コードと資源を記録する（メモリのピークは周期採取の値とメモリラッパーが終了時に読んだ値の大きい方）。ビルドディレクトリはタスクの結果が出たらサービスが消す |
| `task_server_lib.py` | 共用部分：パス、依存、エラー種別と終了コードの表、再試行、資源記録、ビルドディレクトリ、分割、環境変数の一覧、身元。全体の自己検証 `--selftest` と破壊スイッチの表はファイル冒頭 |
| `task_server_selftest.py` | 自己検証の各セル（前の行から起動される） |
| `singlefs-task-server.service.in` | ユーザーレベルのユニットのテンプレート |

独自の設定ファイルはない：スケジューリングの資源はリポジトリ直下のマルチホスト設定 `multi-host.env`（テンプレート `multi-host.env.example`）から読む。socket、データベース、ログ、署名鍵、ビルドディレクトリは `task_server_lib.py` 冒頭の「パス」に書いた固定の既定値を使う。必須：fastapi、uvicorn、`multi-host.env`（中に `NFS_SHARED_ROOTS`、`SHARED_DATA_ROOT`、`HOSTS` があること。書き方は「## NFS 共有」の「マルチホスト設定のどのキーか」）、NFS 共有の設定が済んでいること（「## NFS 共有」を参照）、サーバに繋がること。

## スケジューリング

マシンの選択は空きの均衡による：カードの要らないタスクは送れるマシンの中から収まるものを選び、収まるマシンが複数あるときは載せた後の残りがそのマシンの総上限に占める割合の大きい方を選び、同じならこのマシンを選ぶ。上限に当たった後の再投入は特定のマシンに固定しない。分割の各片は計画どおりまず二台目に行き、収まる限り均衡で載せ替えない。計画、各片、統合はどれもマシンに固定しない。計画に `pin` を書いたものは全体を `shard-plan-refused` と記録する（片はマシンに固定しない。どのマシンかはサーバが選ぶ）。二台目は同じ共有ツリーで走る：リポジトリ、作業ルート `~/.local/share/singlefs/work/` のある共有データルート、セッション記録ディレクトリを NFS で二台とも同じ絶対パスにマウントし（マルチホスト設定の `NFS_SHARED_ROOTS`、下の「NFS 共有」の節）、二台目に送る回は `scripts/hosts/multi-host-run.sh --peer` がタスクの作業ディレクトリ、同じ絶対パスでそのまま起こす。ツリーを複製せず、送らず、取り戻さず、パスも書き換えず、書き出したファイルは二台とも読める。ビルドディレクトリは `multi-host-run.sh` が二台目のローカルディスクにその回だけ新しく作り（マルチホスト設定の `BUILD_ROOT_BY_HOST` のうち二台目の項の下の `builds/<ラベル>/target`、どの共有ルートの下でもない）、コマンドが終わっても止められても先に消す（コンパイルするコマンドが上限に当たって並べ直すときは次の回のために残す。下の「ピークの出発点」）。サーバは設けず、どこにあるかだけ記録する（`task status` で見える）。`task clean` は扱わない。二台目に送るかどうかは、二台目がいま使えるかと空きだけで決まる。二台目に送れない三種類は投入のときに断る（下の「## 投入の書き方」）。一台だけに送るコマンドの名簿はない（ユーザー：「【このマシンだけで走る】は受け入れられない、と改めて言う。早く直して、誤りを表に出せ」）：どのディレクトリ、どの入口を指すコマンドも二台のどちらにも送れ、どちらかは空きで決まる。二台目で赤になったものは赤のままにし、スクリプトの側で直す。サーバはそれをかばわない。メインの作業ツリーを変えるツール（`hook-swap.py`、`apply-writer-patch.py`、`stage-mine.py`、`scripts/kb/` の下のもの、`--skip-apply` なしの `merge-and-verify`）と `--write` 付きのものは二台目に送れる（変えるのは同じツリー）。上限に当たるなど本来は再投入する結末は従来どおり再投入せず、投入したセッションに返す。そのため括弧の中のツールは初回から十分に与える：上限は「（同じキーの直近 5 回の最高 + `hook-swap.py` の `--verify` が与える検証コマンドのキーの直近 5 回の最高）× 1.5」を下回らない（4G の底は設けない。タスク 8367 は同じキーの窓だけで 857M しか与えられず、当たって、入れ替えが途中で止まった）。分割の計画ディレクトリと各片の成果物ディレクトリは共有の作業ルートの下の `task-server-shards/` にあり、二台が同じ絶対パスで読み書きする。サービスはマージロックを確かめない：メインのワークツリーをマージしている間も普段どおり並べ、起動する。一回の割り当てで二台目に起動するのは最大 4 件（一度に起動しすぎると ssh の接続がリセットされる）で、上限に達したら 2 秒後にもう一回割り当てる。二台目の結末は `multi-host-run.sh` がログに書くそのコマンドの終了行（`MULTI_HOST_RUN_STEP step=peer-command event=end … exit=<コード>`）で決める：この行があればコマンド自身の終了コードで決め、コマンド自身が 255 で終わったものは `command-failed` と記録して再投入しない。この行がなく 255 で終わったものだけが二台目で走らなかったもの（繋がらない、ssh がリセットされた）で、`peer-run-failed` と記録してそのまま再投入し、最大 2 回まで。先頭が収まらないときは、収まる後続を先に起動する（割り込み）。投入から二時間に満たないものはマシンごとに一枚物と小物の組を交互に起動する：マシンの使える上限（総上限からそのマシンの今の余裕を引いたもの）の 85% を境とし、記帳がそれ以上のものが一枚物、ほかは小物で、小物はキューの順に一組に詰め、次の一件で境を超えるときに一枚物が待っていれば組を締めて小物を載せず、一枚物は収まり次第起動し（マシンが空くのを待たない）、一枚物の後は次の小物の組に戻る。交互で止めた待ち理由には「在等这台腾空」（このマシンの空きを待っている）が入る。一枚物は一台だけで空きを待ち、その一台だけ組を締める：前の回でそのために締めたマシンがあればそこで待ち続け、なければ今いちばん収まりに近いマシン（その記帳から、そのマシンの「設定の総上限 − 余裕 − 走っている試行の上限の和」の残りを引いた値が最小）を選ぶ。もう一台は小物をそのまま起動する。組を締めるのはその一枚物が収まるマシンだけ：予測ピークそのものがそのマシンの今出せる最大の上限より大きければ、空いても起動できないので、そのために締めない。どのマシンにも収まらなければどこも締めず、列はそれを判定した時点で `memory-cap-at-maximum` として差し戻す。カードの要る一枚物は、要る枚数の空きカードがそろうマシンだけを数え、カードがふさがっているマシンはそのために締めない。`/health` が先頭の収まりを判定するのは配置と同じ判定（メモリ、ビルドディレクトリのディスク、CPU の関門、カードの枚数）。組の勘定はその組に入れた小物の計上の合計である。走り終えたものも数えたままにする（境に届いたら締め、そこで初めて一枚物の番が来る。走り終えたものを引くと、小物が次々に来て組がいつまでも締まらない）。締めている間に隙間で起動したものは加えない。締めたことを書く一文には、その組の小物のうちまだ走っている本数とその計上も書き、走り終えればその分減る。組を締めている間の隙間埋め：先頭の一枚物の横でそのマシンにそのまま空いている分は「設定の総上限 − 余裕 − 先頭の計上 − 一枚物の横に隙間で入れて走っている試行の上限の和」である（締める前に起動した小物は引かない。一枚物はもともとそれらが走り終えるのを待つ）。そこに収まる小物は所要時間を見ずに起動する（二台とも締めているときに見込み所要時間のない小さなタスクはこれで起動する。タスク 8370）。先頭の要る分に食い込む小物は、見込み所要時間がそのマシンで走っている試行の残り時間の最長（ふさいでいる時間）以下のときだけ起動し、見込み所要時間のないものは締めたまま待つ。先頭の一枚物がそのマシンの使える上限いっぱいに計上していれば、その分は 0 である。見込み所要時間：`scripts/crash/crash-point-replay.sh`、`.claude/gate.d/formal-verification.sh`、`.claude/gate.d/crates-mutation-replay.sh` に `--item` を付けて分割しないものは、サーバがまず見積もりの子タスク（同じ入口に `--list-items --with-keys` を付けたもの。項目ごとに一行 `ITEM_PLAN item=<項目名> to_judge=<新たに判定する件数> reusable=<再利用できる件数>` を読む）を走らせ、その結末が出てからキューに入れる。走るたびにログの項目ごとの一行 `ITEM_DONE item=<項目名> seconds=<秒> judged=<判定した件数> reused=<再利用した件数> exit=<コード>` から、項目ごとに「新たに判定する一件あたりの秒数」と「再利用する一件あたりの秒数」をサーバ自身のデータベースに記録する（prune-server には入れない）。見込み所要時間は各項目の件数 × 秒数の和で、どれか一項目でも秒数がなければ見込み所要時間はない。見積もりが失敗したものは見込み所要時間なしで並ぶ。ほかのコマンドの見込み所要時間は、同じコマンドキー（メモリの記録と同じキー：パスと項目は語ごとに畳み、`--check` のセル名は残す）で、コマンド自身が終了まで走った直近の実行の所要時間（終了コード 0 もコマンド自身の 0 以外の終了も数える。シグナルで殺されたもの、上限到達・時間切れ・停滞停止・押し出し・取り消し・二時間打ち切りのようにサービスが判定したり中断したりした結末は数えない）。分割したタスクの計画・各片・統合の三段階も同じ（各段階が自分のコマンドキーの直近の成功した実行を取り、各片は片番号ごとに一つ。計画の段階が片ごとの項目を出さないので、片の項目別の見積もりはできない）。`task status <番号>` は見込み所要時間の後ろに、その数がコマンドによるものか、項目によるものか、記録なしかを書く。投入から二時間を過ぎたものは先頭に上がって先に判定する。二時間を過ぎた一枚物もそのまま一枚物として組を締めさせ、それ自身は交互に止められない。そういう一枚物のために組を締めたマシンでは隙間埋めを一件もせず、空くのを待って起動する（ユーザー：「一个任务都排了两个小时了 还要有任务插队 明显不合理」）。収まらないときも後続を止めず、枠も取り置かず、収まる後続はキューの順に起動する。待ちタスクは枠を取り置かない。GPU タスクはマルチホスト設定に書いたカードの順に選ぶ（判定規則は `task_server.py` 冒頭の「GPU」）。カードのホスト名札はマルチホスト設定の `HOSTS` にあるそのホストのアドレスで書き、各項目は `<アドレス>:<カード番号>:<割当量>`（例 `192.0.2.1:0:32G`。アドレスは IPv6 でもよく、右から二か所で切る）、名札が `HOSTS` にない項目は設定の誤りとし、サーバーは `HOSTS` で自分のホストを見分け、コマンドには `GPU_CARDS_BY_PRIORITY` に項目をそのまま渡す。カードを使うフィーチャ（`gpu`、`tests-on-a-real-gpu`、`<パッケージ>/<名前>` の形と `--all-features` も）付きの cargo でカードが要るのは、コンパイルしたコードを走らせる `test`、`run`、`bench` で `--no-run` を付けないものだけで、`clippy`、`check`、`build`、`doc` と `--no-run` はコンパイルだけなのでカードも整地も要らない。引数によってだけカードが要るスクリプトは、先頭 60 行の中に `# task-server-gpu-arguments: <語> [<語>…]` の一行を書く：bash か python3 で起動され、最初のオプションでない引数がそのどれかならカードが要る（`*` はどの引数でも要る）。書き方は `task_server_lib.py` の先頭「GPU」。二台は同じ一段の判定を通る（記帳、収まるかどうか、停滞と CPU、ピーク、上限、ビルドディレクトリ、マシン選び、ディスクの空き。ディスクの下限は二台とも 50G）。マシンごとに違うのは、そのマシンへの届き方、測り方、起動の仕方だけ（`task_server.py` の `Machine`）。試行が普通に終わった後、ユニットにコマンドの孫プロセスが残っていれば、サービスが止めて結果の説明に書く。30 分を超えて走って失敗し、スクリプトが先頭に `# task-server-resumable: <語>…` で再開を宣言していなければ、結果の説明に「N 分走った、再開できない：出し直すと最初から走る」（中国語）と書く。

各試行のコマンドは `scripts/hosts/capped.sh <マシンごとの既定の重い作業のスレッド数>` で包み、スレッド数は常にこの数で、投入時には受け付けない。カードの要るタスクは必ず最も外側でさらに `scripts/crash/gpu-quiesce-run.sh --` で包む。メモリラッパー、`capped.sh`、クリアラッパーと `multi-host-run.sh --peer` はサーバが直接包んだ層だけを受け付ける：サーバは各層に受け付けの印（値は `<タスク番号>.<何回目>`）を設定し、その層はそれを読み取ってコマンドには渡さない。タスクの中のスクリプトがもう一層包むとその場で拒否し、出口はその層を消して、メモリ、スレッド、カードはサーバが渡す `TASK_SERVER_MEMORY_CAP_BYTES`、`SINGLEFS_THREAD_CAP`、`GPU_CARDS_BY_PRIORITY` を読むこと。コンパイルする cargo には、その回専用のリポジトリ外の `CARGO_TARGET_DIR` を別に与え、結果が出たらサーバが消す（投入時に `SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1` を設定したものは残し、`wait` の最終行に `build=<ディレクトリ>` を付け、投入したセッションが `task clean <番号>` で消す）。取り消したものは同じ取り消しの中で現場ごと消す（後の「## 提交写法」の取り消し）。枠はサーバ自身のデータベースの試行記録だけに従う（直近数回の成功した実行のピークの最大値 × 1.5。メモリラッパーのピーク表は読まない。コマンドキーは先に `env` とマルチホスト設定のパス、`LANG` のような走り方を変えない変数のプレフィックスを外す）。記録のないコマンドはまず 4G で記帳し（失敗した回しかないものはその回のピーク × 1.5 を下回らない）、記録のあるコマンドは上限と記帳を記録 × 1.5 で決め、4G に引き上げない（固定値は従来どおり）。上限に当たったら 1.5 倍にして再投入する（再投入の回も 4G に引き上げない）。1.5 倍にするとそのマシンの総上限に届くものは再投入せず、総上限のより大きい別のマシンがあればそちらに移し、なければ `memory-cap-at-maximum` と記録して投入したセッションに差し戻す（`next=` とセッションへのメッセージには、どのマシンで当たったか、どこまで上げたか、峰値がいくらかを書き、今回の範囲（指定した項目、テスト対象）・分割・同時に起動する数を確かめ、小さくするか分割して投入し直すよう提案する。割り当て、ビルドの系統、兄弟の分片は、峰値の計測条件の欄が「进程内存」（プロセスのメモリ）の試行記録だけを読み、その欄がない古い記録（ページキャッシュを含む）は読まない）。マシンの残りを数えるときはプロセスが使うメモリ（`anon` 分間伸びず、その間どの回にも状態 D（割り込み不可の IO 待ち）のプロセスがあったもの（本機ではその試行のプロセスごとに `/proc/<番号>/stat` の状態を読み、二台目では `multi-host-run.sh` が毎回出す `MULTI_HOST_RUN_PEER_IO_WAIT poll=<回> blocked=<状態 D のプロセス数> read=<yes|no>` の行を読む。この行はログの伸びに数えない）は IO を待っているので、`stalled` と記録せず止めない。状態 D のプロセスがない回や読めない回が一度でもあれば元の判定に従う（タスク 8608、8609、8611、8619 は二台目で本機が輸出する NFS を待っている間に停滞として止められた）。カードの要るタスクでその試行にカードが割り当てられたもののうち、ログも CPU も 10 分間伸びず、その間どの回にもそのカードにこの試行の計算プロセスがあったもの（本機では `nvidia-smi -i <番号>` の計算プロセスにこの試行の子孫プロセスがあるかを読み、二台目と測れないときはあるものと見なす）で、その間にカードの利用率が一度でも 0 でなかったもの（本機では同じ `nvidia-smi -i <番号>` で `utilization.gpu` を読む。二台目と読めないときは計算プロセスがあることだけで数え、根拠に「利用率读不到」と書く）は GPU で計算しているので、同じく `stalled` と記録せず止めない。計算プロセスがカードにずっとあってメモリを占めていても、利用率がどの回も 0 のものはカードが働いていないので、元の判定どおり止めて `stalled` と記録する（タスク 9341 はカードに 14129 MiB 自己检查」（自分では終わらせず、担当のセッションに知らせて自分で確かめさせる）と決めた）。記録された所要時間の 5 倍を超えて走り、ログも 10 分間伸びていないものは CPU を見ずに止めて `stalled` と記録し（無限ループも止める）、所要時間の記録がないものにはこの規則を当てない。`stalled` は再試行せず、投入したセッションに差し戻す。止まったと判定した時点でその回のプロセスが使うメモリ（`anon` と `shmem`。上の残りと同じ計測条件で、上限まで満ちたページキャッシュはカーネルが回収しプロセスを殺さないので数えない）の現在値かピークが上限の 98% に達していたものは上限に張り付いて止まったもので、同じく止めるが `memory-cap-hit` と記録して 1.5 `multi-host-run.sh` が書く `MULTI_HOST_RUN_PEER_MEMORY_PEAK bytes=<バイト数>` からその試行に記録し、このマシンと同じく枠の決定に入れる。この行がないものは測れなかったと記録する。ビルドディレクトリのディスク占有もコマンドごとにピークを記録し（このマシンではサーバが与えたビルドディレクトリを測り、二台目では `MULTI_HOST_RUN_PEER_BUILD_PEAK bytes=<バイト数>` から）、あるマシンに送る前に、そのマシンのディスクの空きから走っている試行のビルドディレクトリがまだ伸びる分を引いたものに、このコマンドのビルドディレクトリのピークと 50G の下限が収まらなければキューに残し、待ち理由に「编译目录占盘」（ビルドディレクトリのディスク占有）と書く。コマンド自身が 75 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <パス>] -- <元のコマンド>` と書いたコマンドは、コマンドキーと登録表の行を `--` の後の元のコマンドで決め（`--server-binary` 受け入れは上限で記帳する：走っている試行も新しく起こす試行も上限で記帳し（そのマシンの総上限からそのマシンの今の余裕を引いた値で頭打ち）、マシンごとに走っているタスクの上限の和がその slice の総上限からそのマシンの今の余裕を引いた値を超えないようにする。まだ伸びきっていない分は「上限 − GiB 単位で切り上げる（1.01G・1.1G は 2G、2.1G は 3G、0.7G は 1G、ちょうど整数なら繰り上げない）。定数ではなく、設定にも書かない。余裕を測れないマシンにはその回は送らず、待ちの理由にどのマシンか・なぜかを書く。送れるマシンがどれも測れないものは起動せず `run-condition-unmet`（`wait` は 78 で外す。サーバ経由でデータベースに書くので、サーバが動いていても使える）。固定したコマンドの上限と記帳はマルチホスト設定の `SLICE_MEMORY_CAP_BY_HOST` のうち送り先のマシンの項からそのマシンの今の余裕を引いた値（`<アドレス>=<値>` を空白で区切る。項はそのマシンの slice の総上限で、書いたとおりの値。毎回読み直し、数字そのものは記録しない。項がそのマシンの余裕より大きくなければ `pin-cap` はその場で断り、出口はその項を大きくすること）で、学んだピークに置き換えられず、上限に当たっても大きくせず `memory-cap-at-maximum` と記録し、`task status` に固定値であることを書く。固定したのに設定の `SLICE_MEMORY_CAP_BY_HOST` が読めない（ない、書き方が違う、一台抜けている、`HOSTS` にないアドレスがある、ファイルが読めない）ものは起動せず `run-condition-unmet`（`wait` は 78 で終わる）と記録し、`wait` の理由行に読めない原因と出口（設定を直すか `unpin-cap`）を書く。止まった疑いは知らせるだけ：猶予の後、ユニット全体の CPU が 10 分間平均で一コアの 1% 未満（カードの要るものはその間そのカードに自分の計算負荷もないこと。測れないときは負荷ありと見なす）なら、ログが伸びていてもいなくても、サーバは止めない。`task status` に「止まった疑い」と根拠を書き、警告を一件記録し、`wait` は `TASK_SERVER_SUSPECT task=<番号> …` の一行を出して 231 で終わる。タスクは走り続け、`wait` をもう一度起こせば待ち続ける（同じ一続きは一度だけ知らせ、CPU がまた伸びたらその一続きは終わり）。ログが 10 分伸びず、いまのメモリがその試行の上限の 98% 以上のものは、CPU が伸びていても止める（回収の中で空回りしているのは計算ではない。タスク 7723 は 6144M の上限に張りついたまま 37775 秒こうして走った）。`memory-cap-hit` と記録し、上限を 1.5 倍にして並べ直す。二台とも同じ判定で、このマシンは外側の scope の `memory.current` を読み、二台目は `multi-host-run.sh` が毎回出す `MULTI_HOST_RUN_PEER_MEMORY` の一行を読む（この行は `MULTI_HOST_RUN_PEER_CPU` と同じくログが伸びたとは数えない）。`.claude/gate.d/` を指すゲートは二台目に送れる（走るのは同じ共有ツリー）。判定ライブラリを持ち、登録表 `.claude/gate.d/verdict-library-scripts.tsv` のその行の三列目がまだ prune-server でないものは、投入のときに断る（下の「## 二時間打ち切り：コミット時のゲートを除き、各試行が走っていた時間を足し合わせて（待ち時間は数えない。メモリ上限に当たって一段大きい上限でやり直したときは時間をゼロに戻し、最後に上限に当たった後の試行から数え直す。何回当たっても同じ。分割した各片はそれぞれ数える）120 分になったタスクは、サービスが止めて結末を `over-two-hours`（`wait` は 242 で終了）と記録する。セッションへのメッセージにはコマンド、範囲宣言、合計と各試行の所要時間、ログ末尾の数行を書き、二つを確かめるよう求める：範囲は正しいか（範囲を名指す：`--item`、`--check` のセルを減らす、テストターゲットを名指す。パッチディレクトリを渡す。サービスに分割させる。全体の実行はコミット時に回す）、本当にそれだけ走らせる必要があるか。違っていれば範囲を直していつもどおり `task submit` する。正しければメッセージにある一行 `task-server/task requeue <番号> --long-run-confirmed --items <N> --tasks <M> --why '<なぜそれだけ走らせるのか、なぜその範囲か>'` を実行する：投入したセッションだけ、結末が `over-two-hours` の番号だけ。二つの数は `task confirm` と同じやり方で確かめ（合わなければ 3 で終了し、サービスが計算した確認票を出す）、`--why` は空白を除いて 12 字以上、一つの番号は一回だけ。確かめが通れば、元のコマンドと元の範囲宣言で新しいタスクとして待ち行列の末尾に入り（位置は requeue した時点）、「長跑已確認」の印が付く。二時間では打ち切らず、ほかの判定はそのまま。`task status`、一覧、メッセージ、ログ頭に「长跑已确认（原号 <n>）：<why>」の一行を出す。元の番号は自動では並び直さない。免除はコミット時のゲートだけ：コミット時の六つのゲート（`crash-point-replay`、qemu-device-streams、lkmm、crates-mutation-replay、formal-verification、broad-mutation）か `scripts/gate/gate-staged.sh` で、`--check` も `--item` も付けず、範囲宣言の「为什么」に「提交前」と書いたもの。`--check` 付きのゲート、`merge-and-verify`、入口スクリプト、実験は免除しない。

パッケージ全体のテストには確認の印が要る：`--test`、`--bin`、テスト名付きの `--lib` を名指さない `cargo test`、`--lib --tests` か `--workspace` 付きの `cargo test`、crash-case-replay・feature-gated-tests・product-gpu-real-card-tests の三セルを全部名指した `.claude/gate.d/crash-point-replay.sh --check`、パッチディレクトリを渡さない `scripts/gate/merge-and-verify.sh`——これらはパッケージ全体のテストで、`task submit --whole-package-confirmed <確認ファイル>` を付けずに投入するとその場で拒む（3 で終了、異常表 `whole-package-unconfirmed`）。コミット時のゲートは免除する。確認ファイルには `.claude/agent-common.md`「日常开发的测试不跑整个包」の三度の確認（①変えたファイルと関数、②それらに届くテストターゲットと関数および grep の当たり、③なぜ②を名指すだけでは足りないか）を書き、共有ルートの下に置いて絶対パスで渡す。サービスは形式だけを判定し（読める、三段がそろう、各段が空白を除いて 12 字以上）、合わなければ 3 で終了して欠けた段を名指す。通れば受け付け、`task status`、一覧、メッセージ、ログ頭に「整包已确认：<ファイル>」の一行を出す。この印があっても二時間打ち切りは受け、打ち切り後の requeue で入る新しいタスクは二つの印を両方持つ。

上限に当たった瞬間のメモリ内訳：二台のメモリラッパーは、コマンドが自分の上限に当たった（250 で終了）と判定した瞬間に `RUN_WITH_MEMORY_CAP_OOM_STAT anon=… file=… file_dirty=… file_writeback=… shmem=… oom_kill=…` の一行をログに出す（`scripts/hosts/run-with-memory-cap.sh` ファイル頭「撞上限那一刻的内存明细」）。サービスはそれを一文にしてその試行の結末説明とセッションへのメッセージに写し、大半がプロセス自身のメモリ（anon）かページキャッシュ（file、まだ書き戻していないダーティページを含む）かを書く。記録するだけで判定は変えない。

## NFS 共有

**なぜ必要か。** ユーザーが定めた原則：「所有的脚本必须多机跑。抛出的结果需要多机都能读取。如果不行，要么复制资源，要么共享文件。」（すべてのスクリプトは複数のマシンで走らせること。出した結果は複数のマシンから読めること。それができないなら、資源を複製するか、ファイルを共有すること。）NFS はファイルを共有する側の道：このマシンがいくつかのディレクトリをエクスポートし、二台目が同じ絶対パスにマウントするので、一方が書き出した結果をもう一方がそのまま読め、タスクが指すパスも二台で同じものを指す。ユーザーは 2026-11-01 にさらに定めた：「NFS 的配置要写在 task-server 的 readme 中。不要遗漏了。这部分也要作为检测项目。没有 nfs 不启动。要求用户配置。配置相关来自多机配置的配置文件中 不允许增加额外的配置文件。」（NFS の設定は task-server の readme に書くこと。書き漏らさないこと。この部分も検査項目にすること。NFS がなければ起動しない。ユーザーに設定を求めること。設定に関わるものはマルチホスト設定のファイルから取り、別の設定ファイルを増やしてはならない。）そのためサーバはユーザーの代わりに NFS を設定せず、設定はマルチホスト設定 `multi-host.env` の一つのキーだけで、整っていなければサーバは起動しない。

**共有する区切り。** 三つ：リポジトリそのもの（メインの作業ツリーのルート。二台目はこの生きたツリーで走り、ツリーを複製しない）、共有データルート `~/.local/share/singlefs`（作業ルートと分割の成果物がその下にある）、セッション記録ディレクトリ `~/.claude/projects`。どれもこのマシンでの絶対パスを取り、二台目の同じ絶対パスにマウントする（二台目のホームディレクトリは別でもよく、マウント先はこのマシンのパスに合わせて作る）。

**このマシンでのエクスポート。** このマシンに `nfs-kernel-server` を入れ、共有するルートごとに `/etc/exports` に一行ずつ書き、二台目の有線直結セグメントのアドレスにだけエクスポートする（実際のアドレスは非公開の値で、このマシンのこのファイルにだけ書く）。続けてエクスポートを有効にし、起動時に自動で立ち上げる：

```bash
# /etc/exports、ルートごとに一行
<ルート> <二台目の有線直結セグメントのアドレス>(rw,sync,no_subtree_check)
sudo exportfs -ra
sudo systemctl enable --now nfs-server
```

**二台目でのマウント。** 二台目に `nfs-common` を入れ、このマシンと同じ絶対パスにディレクトリを作り、親ディレクトリの所有者をこのマシンと同じ uid にし、ルートごとに `/etc/fstab` に一行ずつ書いてから、systemd に読み直させてマウントする：

```bash
# /etc/fstab、ルートごとに一行
<このマシンの有線直結セグメントのアドレス>:<ルート> <ルート> nfs4 rw,hard,nofail,_netdev,x-systemd.automount,x-systemd.mount-timeout=30 0 0
sudo mkdir -p <ルート>
sudo systemctl daemon-reload
ls <ルート>                     # 入ると自動マウントが働く
```

**このマシンの再起動の後に自分で戻る。** fstab の行に `x-systemd.automount` を書き、`x-systemd.idle-timeout` は書かない。`x-systemd.automount` で systemd はこのルートに自動マウントポイント（`.automount` ユニット）を置き、これは NFS のマウントそのものの成否と一緒に駄目にならない：このマシンが再起動してエクスポートがない間にマウントのユニットが `failed` になっても、次にどれかのプロセスがこのルートに入ると systemd がもう一度マウントを起こすので、このマシンの `nfs-server` が戻れば `reset-failed`、`start` を人が打たなくてもまたマウントされる。`x-systemd.idle-timeout` を書かないので、一度マウントしたら使われていなくても外さない。`hard`（NFS の既定）はこのマシンの再起動の間に読み書きしているプロセスを失敗させず待たせる。サーバのマウントの判定は `mountpoint -q` を見ない（使われていない自動マウントポイントはそこに autofs の仮置きがあるだけで、`mountpoint -q` はそれでも 0 で終わる）。二台目で `stat -f -c %T -- <ルート>/.` を走らせ、ディレクトリに入ってマウントを働かせ、`nfs` が読めたときだけ通す。マウントした後、二台目で `git -C <リポジトリのルート> rev-parse HEAD` がこのマシンと同じコミットを読めれば、リポジトリの区切りは通じている。

**uid。** 二台でユーザーの uid と gid を同じにする。違うときは、エクスポート項目の括弧の中に `all_squash,anonuid=<このマシンでのユーザーの uid>,anongid=<このマシンでのユーザーの gid>` を加え、二台目が書き込んだファイルがこのマシンのこのユーザーのものになるようにする。

**マルチホスト設定のどのキーか。** リポジトリ直下の `multi-host.env` に三つのキーを書く。一つ目は `NFS_SHARED_ROOTS=<絶対パス>[:<絶対パス>…]` を書く。上でエクスポートとマウントをしたルートそのもの（リポジトリそのもの＝メインの作業ツリーのルート、作業ルートを含む共有データルート `~/.local/share/singlefs`、セッション記録ディレクトリ `~/.claude/projects`。どれもこのマシンでの絶対パスで書く）で、コロン区切り、一区切り以上、各区切りは `/` で始まり、`/` で終わらず、空白を含まない。`ENABLE_ACROSS_MACHINES` が 0 でも書く。テンプレートは `multi-host.env.example` で、別の設定ファイルは設けない。マルチホスト設定の判定 `scripts/crash/crash-point-replay-shard-configuration-check.sh` が書き方を判定し、このマシンではさらに各区切りが既存のディレクトリであることも判定する。合わないものは 1 で終了し、何番目の区切りかを示す。二つ目は `SHARED_DATA_ROOT=<絶対パス>`：共有データルート（作業ルートはその下）で、このマシンでの絶対パス、`NFS_SHARED_ROOTS` のどれかの区切りの下にあること。サーバは `.claude/hooks/lib_work_root.py` でこれを取り（環境に `SINGLEFS_DATA_ROOT` があれば環境に従う）、`control install`、`start`、`check` はこの行だけを見る。書いていない、共有ルートの外にあるときは 78 で終了し、`multi-host.env` にこの行を足すよう出口に書く。既定値は補わない。三つ目は `HOSTS=<このマシンの IP> <二台目の IP>`：各マシンの有線直結の区間のアドレスを空白で区切る。どれが自分かはこのマシンのネットワークインターフェースのアドレス（`ip -o addr show`）で見分け、二台目はもう一方で、ssh はそこへ直接つなぐ。ユーザー名は各マシンの `~/.ssh/config` に任せる。二台目のアドレスは共用の取り方 `scripts/hosts/multi_host_addresses.py` だけを通して取り、それはマルチホスト設定をまるごと判定に通してからアドレスを返す：キーが欠けている、判定が知らないキーがある、壊れた行があると取れず、サーバは起動せず、`control start` は 78 で終了する。二台で値が違うものはマシンごとの三つのキー `CARGO_BIN_DIRECTORY_BY_HOST`、`BUILD_ROOT_BY_HOST`、`SLICE_MEMORY_CAP_BY_HOST` に書く：値は空白で区切った `<アドレス>=<値>` で、各項は最初の `=` で切り、`HOSTS` の各マシンにちょうど一項、アドレスはどれも `HOSTS` にあるものとし、あるマシンの値が要るときはそのマシンのアドレスの項を取る。サーバが読むのは `SLICE_MEMORY_CAP_BY_HOST`（固定値）で、一台抜けている、`HOSTS` にないアドレスがあると設定が壊れていると判定する。分割の各片は `TASK_SERVER_SHARD_HOST` で自分が動くマシンの `HOSTS` のアドレスを受け取る。

**サーバ起動時に何を判定するか。** 四項目で、どれか一つでも通らなければサーバは起動せず、78 で終了し、どの項目かを示して「## NFS 共有」を指す：

- 設定：`NFS_SHARED_ROOTS` があり、各区切りがこのマシン上のディレクトリである。`HOSTS` でこのマシンと二台目を見分けられる（次の二項目はそれで二台目につなぐ）；
- エクスポート：このマシンの `/var/lib/nfs/etab` に各区切りのエクスポート行がある；
- マウント：二台目で各区切りの `stat -f -c %T -- <ルート>/.` が `nfs` を読む（入ると自動マウントが働く）。二台目への ssh が一度時間切れになったらまず「遅い」として 5 秒後に一度だけ確かめ直し、確かめ直しが返ればサービスのログに「第二台慢（超时、复查通了）」の一行を残すだけで、通知せず二台目にも割り当て続ける。確かめ直しも通らないときだけ不合格（「二台目につながらない」）；
- 読み書き：両方向に探針ファイルを一つずつ書き、相手が読める（このマシンで書いて二台目で読み、二台目で書いてこのマシンで読む）。

`task-server/control check` は毎回この四項目をその場で判定する（結論は自分で出し、サーバの `/health` は変えない）。`/health` の `nfs` 欄も同じ四項目を報告するが、「読み書き」の項目（両方向の探針）はサーバが起動したときの一回の探針の結論で、その後はやり直さない。サーバが起動した後は前の三項目だけを毎分確かめ直し、通らなくなったものはタスクが並んでいる・走っているセッションへサービスが直接メッセージを送る（「## セッションへのメッセージ」）。

**通らないとき。**

- 設定が通らない：「マルチホスト設定のどのキーか」のとおりキーを補うか書き方を直し、ディレクトリがなければ先に作る。
- エクスポートが通らない：`/etc/exports` に足りない行を補い、`sudo exportfs -ra`。NFS サーバが動いていなければ `sudo systemctl enable --now nfs-server`。
- マウントが通らない：二台目で上の書き方のとおり `/etc/fstab` の行を補うか直し、`sudo systemctl daemon-reload`。マウントのユニットが `failed` になっていれば `sudo systemctl reset-failed "$(systemd-escape -p --suffix=mount <ルート>)"`、それから `ls <ルート>` でマウントを働かせる。マウントできないときは、まず有線直結セグメントが通じているか、このマシンでエクスポート先にしたクライアントのアドレスが二台目のものかを確かめる。
- 読み書きが通らない：多くは二台の uid、gid が合っていないか、エクスポート項目に `rw` がない。「uid」の段のとおりにする。

**確かめ方。** 三つ。それぞれコメントに書いたマシンで実行する：

```bash
stat -f -c %T -- <ルート>/.                   # 二台目で実行：nfs と出ればこのルートはマウントされている
cat /var/lib/nfs/etab                          # このマシンで実行：各ルートにエクスポート行があり、クライアントは二台目
echo probe > <ルート>/nfs-check-by-hand        # このマシンで実行：このマシンで書く
cat <ルート>/nfs-check-by-hand                 # 二台目で実行：二台目で probe が読める
echo probe > <ルート>/nfs-check-peer           # 二台目で実行：二台目で書く
cat <ルート>/nfs-check-peer                    # このマシンで実行：このマシンで probe が読める
rm <ルート>/nfs-check-by-hand <ルート>/nfs-check-peer   # 確かめ終えたら二つのファイルを消す
```

## 投入の書き方

```bash
task-server/task submit -- <コマンド…>              # タスク番号と確認票を表示する。タスクは確認待ちで、まだ列に入らない。環境中の SINGLEFS_RUN_SCOPE のようなホワイトリストの変数はそのまま持っていく。セッションの受信先が読めなければその場で拒む
task-server/task submit --whole-package-confirmed <確認ファイル> -- <コマンド…>  # パッケージ全体のテストに三度の確認を書いたファイルを付ける（上の「パッケージ全体のテストには確認の印が要る」）。付けなければその場で拒む
task-server/task requeue <番号> --long-run-confirmed --items <N> --tasks <M> --why '<…>'  # 二時間で打ち切られたタスクが本当にそれだけ要ると確認する：元のコマンドが待ち行列の末尾に入り長跑已確認の印が付く（上の「二時間打ち切り」）
task-server/task confirm <番号> --items <N> --tasks <M>  # 確認票で範囲を確かめてから確認する：二つの数がどちらもサービスが今数えたものと同じときだけ列に入る（投入時刻で位置が決まる）。合わなければ 3 で終わり、サービスの確認票を出す
task-server/task wait <番号>                        # 結末を取る：完了時に終了、最終行 TASK_SERVER_RESULT …、終了コードはタスクのもの。セッションの受信先を記録したタスクは起こされるために起動しなくてよい（「## セッションへのメッセージ」）
task-server/task status [<番号>]                     # このセッションの確認待ち・待ち・実行中・完了して未受領のもの。番号を与えた確認待ちのタスクには今計算した確認票を出す。待ちには「待ち：…」、実行中にはどれだけ走ったか、ログがどれだけ伸びていないかを付ける
task-server/task cancel <番号>                       # 投入したセッションだけ。止まったことを読み戻したら、同じ取り消しの中でこのタスクのビルドディレクトリと現場を消し、何個消したか、消す前と後の大きさを出す
task-server/task log <番号>                          # 最後の試行のログ（最後の 200 行。--all で全体。--attempt <何回目> でその回。タスクかその回がなければ 4 で終了）
task-server/task clean <番号>                        # このタスクが残したビルドディレクトリと失敗時の現場を消す（投入したセッションだけ、結果が出てから。SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1 を付けていなければビルドディレクトリは結果が出た時点で消え、現場は wait が結果を受け取ってから一時間後に消える。二台目のその回のビルドディレクトリは multi-host-run.sh が自分で消す。取り消したものには使わない）
```

投入の確認：`task submit` が受け付けたタスクはまず確認待ち（`awaiting-confirmation`）になり、列に入らず、子タスクも作らず、試行も起こさない。標準出力にはサービスが返す確認票が続く：コマンド全体、`SINGLEFS_RUN_SCOPE` の四つの区切りの原文、サービスがコマンドから読み取った項目数 N（`--item`、`--check` の一つ一つのセル、名指しした `--test`、`--bin`、`--lib` と `--exact` の後のテスト名をそれぞれ数える。一つも名指ししていなければ「整包、不指定范围」と書く）、このセッションが今待ち・実行中のタスク数 M とそのうちコマンドキーが同じものか名指しした項目が重なるものの番号、予測メモリと予想所要時間とその出所、投入の時点で分かる異常（全体を超えるか全体に近い予算、与えた上限で並列度を決めているもの。それぞれその種類の提案つき）、最終行は `TASK_SERVER confirm-needed task=<番号> items=<N> tasks=<M> timeout=<秒>`。範囲が正しければ `task-server/task confirm <番号> --items <N> --tasks <M>` と書く：二つの数がどちらもサービスが今計算したものと同じときだけ列に入り、番号は投入時のもので、それで位置が決まる。合わなければ 3 で終わり、サービスが今数えた確認票を出す（その間に同じセッションの別のタスクが起動・終了すると数は変わる）。分割の親タスクは一度確認すれば、子タスクはサービスが作り、確認は要らない。30 分確認されないタスクはサービスが取り消し（結末 `cancelled`、説明は「没确认，已取消」で始まる）、結末としてセッションへ送る。確認できるのは投入したセッションだけで、サブエージェントはタスクを投入せず、確認もしない。

取り消したタスクは何も残さない（ユーザー：「取消的任务要自己删掉产物 不要残留」「这个加入流程中 让task server去做」）：`task cancel` がユニットの停止を読み戻したら、サーバは同じ取り消しの中で、このタスク（分割と見積もりのものは子タスクも）の各試行のビルドディレクトリと現場ディレクトリを消す（`SINGLEFS_KEEP_TEST_TEMPORARY_FILES=1` を設定したものも消す）。二台目に送った回は、二台目のローカルの `builds/<ラベル>/` と `runs/` の下のプロセス番号、終了コード、出力の三つのファイルを `multi-host-run.sh` の ⑥ が消し、サーバはその試行のログに書かれた「⑥ 删了第二台这一趟的本地目录 …（回读不在了）」で消えたと認める。その行がなくても、後始末の受領確認がまだ `not-started` で、その回のローカルディレクトリを作った後にしか書かれない行もログにないなら、まだ作られていないので消せなかったとはしない。前の回に残ったものは `--remove-build-directory` で消す。消す前と後の大きさは一つずつ `cancel` の出力に出し、そのタスクの最後の試行のログに書く（二台目のローカルディスク上のものはサーバ側から測れないので、そう書く）。読み戻して無くなっていて初めて消したとし、消せなかったものは一つずつ名指しして `cancel` は 5 で終わる。

投入時の警告（ユーザー：「绕过的 那个要做成提醒 谁做错了严厉警告」）：受け付けてそのまま走らせ、サーバはその場で警告を出し、投入の返答（クライアントが標準エラーに出す）、そのタスクの各試行のログの先頭と `status` に入れる。一行目は「✗ 严厉警告：会话 <番号> 交的任务 <番号> 绕过了服务给的编译目录，取仓根 target/ 下的二进制（…）…」（厳重警告：セッション <番号> の投入したタスク <番号> はサーバが与えたビルドディレクトリを迂回し、リポジトリ根の target/ の下のバイナリを取っている）、二行目は「→ 怎么办：…」。判定するのは、コマンドの語がリポジトリ根の `target/` の下に落ちるもの、またはコマンドの位置で起動されるこのリポジトリのスクリプトの本文に、リポジトリ根の `target/` を指すパスの字面があるもの（前にリポジトリ根の変数、`$(dirname …)/../..`、`$(git rev-parse --show-toplevel)` が付き、後に `target/release/`、`target/debug/` が続く。リポジトリ根で起動したものは裸の書き方も認める）。サーバが与えたビルドディレクトリ、呼び出し側が与えた `CARGO_TARGET_DIR`、下書きと一時ディレクトリの下の `target/`、コメント、壊しスイッチの枝と自己検証の枝（`--selftest` で起動したもの、名前に selftest を含むか cells で終わる関数の本体）は数えない。判定は `task_server.py` の冒頭 ②「提交时警告」① にある。もう一つ（同じ節の ②）：投入したセッションに、結末が 30 分たってもそのセッションへ渡っていないタスク（サービスのメッセージが届かず、`wait` でも取っていない）があるときも、受け付けてそのまま走らせ、同じ三か所に二行を出す。一行目「✗ 严厉警告：会话 <番号> 有 <N> 条任务跑完了没人取（<番号>、…）：…」、二行目「→ 怎么办：task-server/task wait <番号> 取走（…）…」。セッションのない手作業のタスクは判定しない。

`wait` はタスクが対処を要する八つの場合を自分で知らせる（ユーザーがダイアログで「task wait 自己报」を選んだ）。一つ目は並んだまま長すぎる場合で、キューに `QUEUE_ATTENTION_MINUTES`（30 分）並んだとき。二つ目は記録された所要時間の `OVERRUN_ATTENTION_FACTOR`（3）倍まで走った場合で、ログが伸びている間サービスは止めないので、人を呼ぶのはこの一件だけである。三つ目はカード交換での再投入で、静止化がカードの故障を判定し、サービスが別のカードで並べ直した場合（結末は `succeeded` になりうる）。四つ目は静止化が終わっていない場合（`cleanup-pending`）で、コマンドは終了したが読み戻しがまだ片づいておらず、サービスは資源の占有を保持している。五つ目は分割した親タスクが進まない場合（`shard-advance-failed`）。六つ目はログが長く伸びないのにサービスが止めていない場合（`quiet-log-busy`）で、CPU が伸びているか読めないためにサービスが止めないまま `QUIET_ATTENTION_MINUTES`（30 分）ログが伸びなかったとき、記録された所要時間があってもなくても知らせる。IO 待ちやカード上の計算プロセスのために止めていないものにはこれを出さず、`io-wait`、`gpu-busy-quiet` で知らせる。七つ目は IO 待ちなのにサービスが止めていない場合（`io-wait`）で、ログが伸びない各回にずっと状態 D のプロセスがあり、それが `IO_WAIT_ATTENTION_MINUTES`（30 分）続いたとき、根拠に直近の回の状態 D のプロセス数と本機のいまの `/proc/pressure/io` の some avg60 を書く。八つ目はカードにその計算プロセスがあるのにサービスが止めていない場合（`gpu-busy-quiet`）で、試行にカードが割り当てられ、ログも CPU も伸びない各回にずっとそのカードにこの試行の計算プロセスがあり、各窓でカードの利用率が一度は 0 でないか読めず、それが `GPU_BUSY_QUIET_ATTENTION_MINUTES`（30 分）続いたとき、根拠にカードのキーとカードの利用率（読めないときは「利用率读不到」）を書く。一つの窓で利用率がずっと 0 のものはこれを出さず、停滞として止める。九つ目は結末があるタスクにだけ出す：主作業ツリーを書き換えるコマンド（`apply-writer-patch.py`、`hook-swap.py`、`stage-mine.py`、`--skip-apply` なしの `merge-and-verify.sh`）が、上限超過、押し出し、GPU メモリ不足、二台目で走れなかった、上限の頭打ち、取り消し、停滞での停止、起動元を見失った、シグナルで殺された、のいずれかで終わった場合（`workspace-write-interrupted`）で、半分だけ書いた可能性があり、`next=` で確かめるファイルかパッチディレクトリを挙げる（ユーザー：「这个问题很严重 因为可能会导致补丁没有正常写入」）。`apply-writer-patch.py` で結末ファイル `apply-outcome.tsv` があるものは、サービスがその `--read-outcome` で判定し、全部当たったもの・戻したものは知らせず、`--dry-run` 付きも知らせない。さらに三種類ある（全部で十二種類。ユーザー：「既然加了给对应对话发消息的功能 就就该把异常和修改意见交给对应的对话」）。どれも知らせるだけで、タスクはそのまま並び、そのまま走り、根拠には測った数を、`next=` には直し方の提案を書く。十番目は予算がマシン一台分に迫る場合（`oversized-budget`）で、キューがそのタスクのあるマシンでの記帳がそのマシンの一枚物の境（使える上限の 85%）以上で使える上限以下だと判定したとき、根拠に各マシンの記帳、使える上限、記帳の出所（記録した峰値が何回分か、ビルドの系統、固定値）を書く。上限を固定したものも知らせ、提案は範囲・分割・同時に起動する数の確認である。送れるどのマシンの使える上限よりも記帳が大きいものはキューで待ち続けず、キューが判定したその時に `memory-cap-at-maximum` で差し戻し、一度も起動しない。十一番目は長く走るのにコアが使われていない場合（`long-run-idle-cores`）で、試行が一時間走り、今までの平均使用コア数が与えたスレッド数の四分の一に満たないとき（タスク 8856 は 31 スレッドで平均 8.881 コアしか使わなかった）、試行ごとに一度だけ知らせ、提案はスクリプトが直列に走っていないか、範囲を指定しすぎていないかの確認である。十二番目は与えた上限で並列度を決めている場合（`fills-any-cap`）で、同じコマンドキーの直近三回の走りきった試行の峰値がどれも各回の上限の 90% 以上のとき（上限に当たった試行は数えない：当たった回の峰値はもともと上限に張り付いており、上限を一段ずつ上っていくのは上限で並列度を決めているのではない）、提案は「这条命令按给的上限开并行，核实」。各種類（投入時の拒否、投入時の警告、各結末、停滞の疑い、未受領の結末も含む）の判定、動作、提案、誰も対処しないときどうするかは、`task_server_lib.py` のファイル頭「异常表」のその行だけに従う：`next=` の先頭はその行の提案で、その種類で確かめるものを名指しする（例：`io-wait` はそのマシンのディスクと NFS、`/proc/pressure/io` を確かめる。`cleanup-pending` は残ったプロセスのコマンド行と、スクリプトが子プロセスを待たずに終わっていないかを確かめる）。その後に今回の具体的な数が続く。サービスはこのタスク（分割したものは子タスクも含む）のこれらを「対処が要る」通知として記録し、そのタスクを待っている `task wait <番号>` は新しい通知を読むと一行 `TASK_SERVER_ATTENTION task=<番号> type=needs-attention kind=<種類> tier=<段> basis=<根拠の数> why=<理由> next=<出口>` を出して 230 で終了する。タスクは並んだまま、または走ったままで、サービスは手を触れていない。`next=` に従って対処し、`wait` を起動し直して待ち続ける。すでに結末があるタスク（カード交換で成功したもの）では、この行は `TASK_SERVER_REASON` の前に出て、終了コードはタスクのままである。同じタスクの同じ種類の通知は同じ段では一度しか起こさず、`wait` を起動し直しても繰り返さない。段が次の段（しきい値の二倍、四倍……）をまたいだときにだけ再び起こす。知らせた段はサービスのデータベースに記録するので、サービスを再起動してもデータベースから読み戻し、同じ段はもう出さない。キューに長く待っているものは、待ち理由がまだ判定されていない回（サービスが再起動したばかりで、この回がまだそれに届いていない）には出さず、理由が判定された回に出す。これらの通知はサービスが投入したセッションへも直接メッセージで送る（「## セッションへのメッセージ」）。記帳は `wait` と同じもので、送ったものは `wait` がもう出さず、`wait` が出したものは送らない。サービスの健全性は `wait` の担当ではない。サービスが自分で見張り、同じようにメッセージを送る。

コマンドを包まず、資源の引数も書かない：`run-with-memory-cap.sh <上限>`、`host-dispatch.py … --`、`multi-host-run.sh … --`、`nice`、`timeout`、`capped.sh`、`two-logs.sh`、`gpu-quiesce-run.sh` とスクリプト自身の `--memory`、`--memory-cap`、`--threads`、`--peer`、`--local-only`、`SINGLEFS_THREAD_CAP`：これらはサーバが行い、書けばその場で拒否してどれを外すかを示す。ホワイトリスト外の環境変数はその場で拒否して名前を示す。本当に必要なコマンドは `task-server/task submit -- env <名前>=<値> <コマンド…>` と書く。退役した変数（`SINGLEFS_HEAVY_TESTS`、`GATE_MUTATION_START_OVER`）は、環境に設定しても、コマンドに書いても（`env` の後とコマンドの前の `名前=値`）その場で拒否し、拒否の説明で名前を示して出口を書く。一覧は `task_server_lib.py` の `RETIRED_VARIABLES`。

二台目に送れない三種類は投入のときにその場で断る（ユーザー：「改成提交时当场拒（推荐）：不再悄悄改派本机：碰到这三种就在提交时报错、点名是哪个路径或哪一族、出路写怎么改，任务不跑。」）：`task submit` は 3 で終了し、その一文と出口を出し、タスクは並ばず走らない。一つ目は、作業ディレクトリとコマンドの中の絶対パス（シェルの語全体だけを見る：`/` で始まる語全体、`名前=絶対パス` と `--オプション=絶対パス` の値、`bash -c` のスクリプトの語をシェルの語に切った一つずつ。ほかの語の途中に挟まった `/`（引数の値の「（接的是 /）」など）は数えない）に、マルチホスト設定の `NFS_SHARED_ROOTS` のどの区切りの下にもないものがある場合で、そのパスを挙げ、出口はどれかの区切りの下に移すこと。`/dev/null`、`/usr/`、`/bin/` のように二台で同じシステムのパスは数えない。`/tmp` の下のものも同じく断り、その一文に再起動で `/tmp` が消えることを添える。二つ目は、コマンドに渡す `SINGLEFS_DATA_ROOT`、`SINGLEFS_WORK_ROOT` に共有ルートの下にないものがある場合で、変数と値を挙げ、出口はマルチホスト設定を整えること。三つ目は、コマンドが登録表 `.claude/gate.d/verdict-library-scripts.tsv` の判定ライブラリを持つ行を指し、その行の三列目がまだ `prune-server` でない場合で、その系統を挙げ、出口はその系統を prune-server につなぎ、三列目を `prune-server` に書き換えること。登録表が読めない、壊れているものも同じく断る。

一時 prune-server のラッパー（`python3 scripts/prune-server/prune_server_client_selftest.py --with-temporary-service [--server-binary <パス>] -- <元のコマンド>`）はスクリプトの自己検証専用である（ユーザー：「旧脚本不兼容 我再说一次 如果错了让 对方重新提交」）。そこから剥がした元のコマンドにコンパイルする cargo がある、またはカードが要る（見分け方はサービスがビルドディレクトリとカードを決めるときと同じ）なら、投入のときに上と同じ形でその場で断る：`task submit` は 3 で終了し、その一文（コンパイルするのかカードが要るのかを挙げる）と出口（ラッパーを外して投入し直す）を出し、タスクは並ばず走らない。剥がすのは判定のためだけで、受け付けたものはラッパーごとそのまま走る。ビルドディレクトリ、カード、GPU の静止化は外側のコマンドにだけ与え、サービスはラッパーを剥がして合わせることはしない。`--server-binary` を付けないラッパー（コマンドの前の代入にもタスクの環境にも `PRUNE_SERVER_BINARY` がない場合）は、サービスが与えたビルドディレクトリの中で prune-server 自身をコンパイルするので、サービスは外側のこのコマンドをコンパイルするものとして扱う。本機に送っても二台目に送ってもビルドディレクトリを与え、`--server-binary` 付きのものはコンパイルせず、与えない。検証クレートの `cargo test` は本物のサービスに対して走らせ、このラッパーはかぶせない。

パッケージを名指ししないワークスペース全体のビルドは投入のときにその場で断る（ユーザー：「8105打回 让他重新写重新确认范围」。タスク 8105 は `-p` なしの `cargo build --offline --all-targets` で予測 49.0 GiB、二台目がそのためにグループを封じて空けた）。投入されたコマンドのコマンド位置で直接起動されるコンパイルする cargo（`build`、`check`、`clippy`、`test`、`run`、`bench`、`doc` とその一文字の別名。`bash -c` と `cd` はたどる）は、`--workspace` / `--all` があれば断る。`-p` / `--package` がなく、cargo のマニフェストの探し方（起動したディレクトリから上へ最初の `Cargo.toml`）で仮想マニフェスト（`[workspace]` だけで `[package]` がない。リポジトリのルートのものがそれ）に当たるものも断り、起動したディレクトリが分からない、マニフェストが読めないものも同じく断る。`task submit` は 3 で終了し、その一文（どの cargo を、どのディレクトリで、どのマニフェストで起動したか）と出口を出す：ビルドするパッケージを名指しする（`-p <パッケージ>`、検証クレートは `-p singlefs-verification`）。リポジトリ全体を走らせるものは `scripts/gate/merge-and-verify.sh` かコミット時のゲートを通す。パッケージ自身のマニフェストに当たるもの（`scripts/experiment-apparatus/`、`prune-server/` のようにそれ自体がワークスペースのパッケージ、またはメンバーのディレクトリの中で起動したもの）はそのパッケージだけをビルドするので受け付ける。エントリスクリプトやゲートの中で起動する cargo は判定しない（サービスは投入されたコマンドだけを見る）。`cargo fmt`、`metadata`、`tree`、`clean` はコンパイルしないので判定しない。

## セッションへのメッセージ

ユーザー：「不是你通知 而是 task-server 通知发起的对话」「包括报错 长时间没有响应 都可以这样通知」。`task submit` はセッションの Bash で走り、環境の `CLAUDE_CODE_MESSAGING_SOCKET`（セッションの受信 socket）と `CLAUDE_CODE_MESSAGING_TOKEN`（セッションのトークン）を読んでタスクと一緒にサービスへ渡す。サービスはタスクに記録し、トークンはログにも `status` にも `/tasks/<番号>` の返答にも出さない。読めないときはその場で拒み（終了コード 3）、出口は Claude Code セッションの Bash から投入すること（サブエージェントはタスクを投入しない）。受信 socket は投入時のものを使わない：送る前に毎回、サービスはタスクに記録したセッション番号でセッション登録（`~/.claude/sessions/*.json`、プロセスごとに一つ。読むのは `sessionId`、`messagingSocketPath`、`pid` だけ）を読み、セッション番号が同じでプロセスがまだ生きているもののうち最後に起動した一つの `messagingSocketPath` を取る。トークンは投入時に持ってきたもの。セッションが再起動して socket が変わったものは新しい方へ送り、見つからないもの（セッションが閉じた）は下の「送れない」のとおり警告を書く。

サービスは次の場合にその socket へメッセージを一通送る：

- タスクに結末が出た（`wait` が `TASK_SERVER_RESULT` を出すすべての種類）：一度だけ送る。送れたらサービスは取られたものとして記録する（`wait` が取ったのと同じ）。セッションがすでに `wait` で取ったものは送らない。
- 対処が要る通知（上の「## 投入の書き方」の十二種類）と停滞の疑い：同じタスクの同じ種類の通知は同じ段では一度だけ送り、記帳は `wait` と同じものを使う。時間で判定する種類は時間が倍になるごとに一段上げて送り直す。段が時間で上がらない種類（`oversized-budget`、`fills-any-cap`、`long-run-idle-cores`、`cleanup-pending`、`card-replaced`、`shard-advance-failed`）は、その段を送ってから 30 分たってもまだ残っていればもう一度送り、その後は倍になるごとに送る。一行目に「没处置、第 <回> 回再推」と書き、本文に前に何を送ったか、今何が足りないかを書く。
- 未受領の結末：親タスクの結末が 30 分たっても投入したセッションに届いていない（結末のメッセージが届かず、`wait` も起動していない）ものはもう一度送り、その後は倍になるごとに送る。一行目は「task-server：任务 <号> 结局还没人取（…）」で、送れたら受領済みとして記録する。
- 投入して 30 分確認されずサービスが取り消したもの：結末として送り、本文に「没确认，已取消」を含む。
- サービスの健全性：データベースに書けない、振り分けが先頭を起動できると判定したのに起動できないまま、進み具合の確認で収められるのに起動していない、サービスのユニットがない、NFS 共有の前の三項目が通らない、第二のホストが 180 秒使えない。タスクが並んでいる・走っているすべてのセッションへ送り、同じものは同じセッションへ一度だけ、直ってからまた壊れたときにまた送る。サービス自体が落ちているときは送れない：`task wait` は 60 秒続けてつながらなければエラーで終わり、`task submit` はつながらなければその場で報告する。

本文の一行目は「task-server：任务 <番号> <結末または通知の種類>…」か「task-server：服务健康 <どれ>」で、その後に `wait` が出す行どおり理由・出口・ログを書き、最後に `wait` のその行をそのまま置く。事実と出口だけを書く。送れない（socket がない、つながらない、セッションが閉じた）ときは送り直し続けない。サービスのログと警告記録に `inbox-unreachable` を一件書き、そのタスクの最後の試行のログに `TASK_SERVER_INBOX` で始まる一行を足し、タスクはそのまま続く。受け手が空いていれば Claude Code はこのメッセージで新しいターンを始める。権限確認を飛ばすセッションでは、ユーザーが承認するまで保留される。

`task wait` は残す：結末と通知はこれまでどおり取れるが、起こされるために起動する必要はもうない。`task-server/control watch` は削除した（2 で終了し、出口の一文を出す）。サービスの健全性を手で一度確かめるには `control check` を使う。

行の書き方：まず一行 `{"type":"auth","token":"<セッションのトークン>"}`、次に一行 `{"type":"user","message":{"role":"user","content":"<本文>"}}`。二行は接続前に用意して一度に書く（Claude Code は 30 秒以内に一行そろわない接続を閉じる）。出典：受信 socket と認証行は Claude Code の文書 https://code.claude.com/docs/en/cross-session-messaging.md の「The session's inbox socket」節。user の行の書き方は文書に書かれておらず、Claude Code のバイナリ自身のデバッグログの「[uds-messaging] Inject messages」の一文にある例から取った。文書に行の書式がないので、Claude Code を更新したら確かめ直すこと。

## ソースのファイル頭の宣言

サービスはソースファイルの先頭 60 行にある宣言の行から、コマンドが何を要るかを見分ける。呼び出し側はこれまでどおりカードも額も書かない。宣言はその入口スクリプトかパッケージを受け持つセッションが加え、サービスは読むだけである：

| 書く場所 | 書き方 | サービスの使い方 |
|---|---|---|
| 入口スクリプト | `# task-server-gpu-arguments: <引数>…`（`*` はどの引数でも） | 最初の非オプション引数がそのどれかならカードが要り、サービスが静止化をかぶせる |
| 入口スクリプト | `# task-server-gpu-cards: <枚数>` | カードが要るとき同じ一台のこの枚数が要る（下の「何枚のカード」） |
| `.rs` ソース（コンパイルしたバイナリと同名のソース。`cargo test` / `run` / `bench` が `-p` で名指したパッケージのソース） | `// task-server-gpu-cards: <枚数>` | 同上 |
| 入口スクリプト | `# task-server-cargo-family: <cargo の引数>…`（例 `-p singlefs-verification --release --features gpu`） | 中で起こす cargo がどのパッケージ、どのプロファイル、どの機能をビルドするか。このコマンドが自分のキーで記録を持たないとき、同じビルド系統の直近のビルド段ピークから始める（下の「ピークの出発点」） |
| 入口スクリプト | `# task-server-cargo-family: -p $3`、`# task-server-cargo-family: -p $--crate --release` | どのパッケージをビルドするかがコマンドの引数で決まるとき：`$<n>` はスクリプトの後ろの n 番目の語（1 から数え、オプションとその値はそれぞれ一語）、`$<オプション名>` はそのオプションの値（`--crate 値` と `--crate=値` のどちらも読み、`--` の後ろは読まない）。提出時にこのコマンドから埋めてから系統に入れ、一つでも埋まらない（その語がない、値が空か `-` で始まる）コマンドは系統に入れず 4G から始める。例：`scripts/mutation/prove-red.sh --copy <コピー> <crate> <変異名…>` は `-p $3` と書き、変異名の違う実行は `<crate>` で同じ系統に入る |
| 入口スクリプト | `# task-server-shards: <引数>…`、`# task-server-resumable: <引数>…` | 分割と再開（`task_server_lib.py` のファイル頭「分片」「续跑」） |

何枚のカード：ユーザーが決めた実カードの試し方は「你需要测试的是 一张卡1gb 2张卡 三张卡 每张卡都能用来分片gc。没有卡报错。 有卡但是失败 报错加cpu兜底」である。枚数を宣言したものは、サービスがマルチホスト設定のカードの優先順に見て、空きカードがその枚数そろい、メモリにも収まる最初の一台を選び、その台の空きカードのうち前からその枚数をひとまとめに渡す：`GPU_CARDS_BY_PRIORITY` にはその項目を空白でつないだ一続きを渡し、静止化はまとめて行い、走っている間はどれも使用中と数える。マルチホスト設定が挙げたカードでどの台もその枚数がそろわないものは結末を `never-fits`（241 で終了）とし、枚数が正の整数でないものは `run-condition-unmet` とし、どのファイルに何と書いてあったかを説明に挙げる。読む `.rs` ソース：`--test <名前>` を付けたものは `tests/<名前>.rs`、`--lib` だけのものは `src/lib.rs`、それ以外は `src/lib.rs`、`src/main.rs` と `src/bin/`、`tests/` の下のもの。いくつかに書いてあれば最大を取り、どれにもなければ一枚。例：`crates/singlefs-background-gpu/tests/<ターゲット>.rs` の先頭の数行に `// task-server-gpu-cards: 3` と書けば、`cargo test --release -p singlefs-background-gpu --features tests-on-a-real-gpu --tests` に同じ一台の三枚を渡す。

ピークの出発点（サービス自身のデータベースにある試行の記録。`task_server_lib.py` のファイル頭「资源记录」）：
- ビルド系統：コンパイルする cargo はパッケージ、プロファイル（`--release`）、機能で系統に分け、`task-server-cargo-family` を宣言した入口は宣言どおりの系統に入れる。自分のキーで一度も走りきっていないとき、および上限に当たった後の毎回の並べ直しは、同じ系統（ほかのコマンドキーの試行も数える）の直近 5 回のビルド段ピークの最大 × 1.5 から始め、元の上限より大きいときだけ取り替える（兄弟片、直近の最高から始めるのと同じ窓）。ビルド段ピークは、ログに cargo が「Finished … target(s) in …」の行を出す前に回ごとに採ったプロセスメモリ（`anon` と `shmem`）の最大：このマシンでは `attempt_runner.py` が採り、二台目では `multi-host-run.sh` が回ごとの読みから採って一行 `MULTI_HOST_RUN_PEER_BUILD_PHASE_PEAK bytes=<バイト>` を出す。両台で同じ量。その行がない（ビルドが通らない、cargo でない）ものはこの欄が空で、貸さない。試行全体のピークと上限に当たった試行の上限は同じコマンドキー自身にだけ使う：系統の各コマンドは同じものをビルドするが、テストを走らせる段で要るメモリはそれぞれ違い、全体を貸すと単体テストの一ターゲットを系統でいちばん大きいコマンドで記帳してしまう（タスク 9279 は `--exact` 一つで単独のピーク 9.47 GiB なのに、同じ系統の GPU 照合のターゲット全体の 42.20 GiB を借りた）。その後のビルドがどれも小さければ大きい回は窓を出て起点も下がる。自分の記録があるものは自分の記録に従う。
- 同じ計画でのピークの共有：分割の一片の最初の試行は、同じ計画の計画ステップと兄弟片の終わった試行のうち終了時刻の新しい 5 件のピーク（上限に当たったものはその回の上限）× 1.5 を取り、上げるだけで 4G より下には押し下げない。
- 直近の最高から始める：新しく投入したものの最初の試行と、上限に当たった後の毎回の並べ直しは、このキーでサービスが記録している直近 5 回のうち最高の一回（当たった上限、走りきった試行のピーク）× 1.5 まで上げ、並べ直した回はビルド系統と兄弟片も見る（同じく直近 5 回だけ）。上がりも下がりもする：窓の中で当たったばかりの段はすぐ見え、古いものは窓を出れば数えず、その後の数回がどれも小さければ起点も下がる。記録が一つもないものは従来どおり 4G から、実際のピークの記録があるものは 4G に引き上げない。
- 上限に当たって並べ直したとき、前の回のビルドディレクトリは消さず、並べ直した回がまた同じ台ならそれを使い続ける（推測：cargo は指紋でビルド済みのクレートを使い回す。どれだけ省けるかは測っていない）。別の台に移った回では、その回が始まるときに前の回のものを消す。二台は同じ一段を通る：本機は `CARGO_TARGET_DIR` で指し、二台目の試行は `--keep-build-directory` を付けて `multi-host-run.sh` が走り終わった後も `builds/<ラベル>/` を残し、並べ直した回は `--reuse-build-directory <前の回のラベル>` でそれを使い続け、台を移るか結末が出たらサービスが `multi-host-run.sh --remove-build-directory <ラベル>` で消す。

## 一時停止と再開

prune-server のバイナリ入れ替えや判定ライブラリの古い行の削除のように、ほかのセッションのタスクが一つも動いていない時間帯が要る作業は、自分も `task submit` でコマンドを投入することが多い。`control stop` は使えない。サーバ停止中は誰も投入できず、すでに `task wait` している側も 60 秒で 78 を返して終わる。代わりに一時停止を使い、作業するセッションを通す（そのセッションのタスクは停止中でも通常どおり起動する）。

```bash
python3 task-server/control pause --reason "判定ライブラリの古い行を消す" --allow-session <作業するセッション>   # 一時停止：ほかのセッションのタスクは起動しない。通したセッションのタスクは通常どおり並び起動する。投入は受け付け、status / wait / log / cancel は応答する
python3 task-server/control check                                                                              # 「…、放行会话 <番号>、在跑 N 个、别的会话在跑 0 个」（通したセッション・実行 N 件・ほかのセッションの実行 0 件）と出るまで繰り返す
# …時間帯が要る作業（作業するセッションが task submit でコマンドを投入する）…
python3 task-server/control resume                                                                             # 再開：待っていたものは通常どおり起動し、通したセッションの指定も一緒に消える
```

- 作業するセッションの番号：そのセッションで `python3 task-server/task status` を実行し、先頭行「会话 <番号>：…」の番号を使う（タスク投入時にサーバが記録したセッションで、`status` が各タスクに出すセッションと同じ欄）。通すのは一つのコマンドではなくセッションである：そのセッションがすでに待たせているもの、あとから投入するもの、分割タスクの子、見積もり用の子、上限超過で待ち行列へ戻った再試行はすべて通常どおり起動する。ほかのセッションのものと、セッションを持たない手動投入のものは待ったままで起動しない。通したセッションの待機中タスクの `status` は本当に待っている理由を出し、ほかのセッションの待機中タスクは「在等：服务暂停中（原因：…）」と出る。
- すでに停止中のサーバへ `pause --allow-session <別のセッション>` を送ると 0 で終わり、通すセッションを替える（理由と開始時刻は変えない）。`--allow-session` を付けない `pause` は通す指定に触れない。`resume` は通す指定も一緒に消す。タスクが一つも動いていない時間帯が要るなら、`--allow-session` なしで `pause` し、`control check` が実行 0 件と報告するまで待つ。
- 停止中、スケジューラは新しい試行を一つも起動しない（通したセッションのものを除く）。空きへの割り込み、分割タスクの子、見積もり用の子、上限超過で待ち行列へ戻った再試行はすべて保留される。実行中のものは結果が出るまで走る（結果は書かれ、再試行は待ち行列へ戻るが起動はしない）。`pause` と試行の起動は一つのロックを共有するので、`pause` が 0 で終わった時点で起動中だった一件は記録済みで、`control check` の実行中件数にあとから割り込む試行はない。
- 一時停止の状態は、通したセッションも含めてサーバのデータベースに保存され（署名付き。データベース内の通したセッションを書き換えると検証に通らないものとして扱い、誰も通さない）、サーバを再起動しても通す指定ごと `resume` まで続く。すでに停止中のサーバへの `pause` は 0 で終わり、元の理由と開始時刻を変えない。
- `control check` は「暂停中（原因：…，起于…）、在跑 N 个」の一行を加えて出す。セッションを通しているときは「…、放行会话 <番号>、在跑 N 个、别的会话在跑 M 个」となる（M は実行中のうち通したセッションのものでない件数）。終了コードは 0 のまま、「振り分けが先頭を起動できると判定したのに起動できていない」も進み具合も判定しない。`/health` は `paused` と `pause`（`allow_session` と `other_running` を含む）を返し、`ok` は変わらない。待機中タスクの `status` には「在等：服务暂停中（原因：…）」と出る。
- 停止中もサービスは自分の健全性（データベースへの書き込み、ユニット、NFS、第二のホスト）を見続け、問題があればタスクが並んでいる・走っているセッションへメッセージを送る。
- `pause` と `resume` を送れるのはサーバを起動したユーザだけで、投入や取消と同じ判定（呼び出し側の uid がサーバ自身の uid か）を使う。
- 作業が終わったら必ず `resume` する。停止中のサーバは健全に見える（`check` は 0）ので、忘れると待機中のタスクはずっと待つ。

## 自己検証

`python3 task-server/task_server_lib.py --selftest`：各セルが本物の uvicorn を一時 socket 上に立て、メモリラッパー、二台目、静止化、`control` が使う systemctl を偽のスクリプトに、試行の scope を偽のディレクトリに置き換える。コンパイルせず、二台目に繋がず、カードも使わない。すべて模擬の世界で走るので、メイン agent がサーバのキューを通さず直接起動する（フックの一覧 `.claude/hooks/lib_project_code_runs.py` の `MAIN_AGENT_TOOLS_RUN_DIRECTLY`）。`TASK_SERVER_SELFTEST_CELLS=<セル,…>` で指名したセルだけを走らせる。セルを並列に走らせる数は、ホストごとの重い作業の既定スレッド数の登録値（`scripts/hosts/heavy_threads.py` をその場で読む）で、読めない（登録ファイルがない・壊れている、`SINGLEFS_THREAD_CAP` が正の整数でない）ときは全体を赤にし、コア数には戻さない。破壊スイッチ `TASK_SERVER_BREAK=<項目>` の表は `task_server_lib.py` 冒頭にある。
