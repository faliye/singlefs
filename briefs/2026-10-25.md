## 当前状态（2026-10-25）

**项目处于里程碑「共享与回收」（[`.claude/kb/milestone/04-fourth-txn.md`](../.claude/kb/milestone/04-fourth-txn.md)）：只读快照机制、截断与文件大小变更、只读索引扫描重建及 CPU 垃圾回收路径均已有核心代码实现；Verus 形式化验证完成了 GC 搬迁保持读值与恒等变换的性质证明（`crates/singlefs-replay-prefix` 内 78 verified）；新增 GPU 垃圾回收设计与实现路径，并基于 E185 实验装置完成 CPU GC 与 GPU GC 的对比测试；同时承接并推进了里程碑三遗留的 51 笔及 8 笔未合入门禁检查等深层欠账。**
当前里程碑是「共享与回收」（[`.claude/kb/milestone/04-fourth-txn.md`](../.claude/kb/milestone/04-fourth-txn.md)）；
这一版仍不能挂到系统里用：没有 FUSE，没有内核模块，没有目录与 POSIX 接口。**别拿它存任何数据。**

这份简报系统梳理里程碑四的核心进展、GPU 垃圾回收机制、CPU 与 GPU 垃圾回收的对照实验实测数据，以及承接自里程碑三的工程挑战与当前边界。

### 核心功能进展

里程碑四围绕多头共享与存储回收构建了一系列核心文件系统事务机制：

- 只读快照：实现只读快照的创建与销毁（`publish_create_snapshot` 与 `publish_snapshot_destruction_intent`）；引入 deadlist 记账树，快照存在时覆盖写与删除所释放的旧块进入 deadlist 而不立即释放，待快照销毁时再级联回收；活快照列表实现可枚举遍历。
- 截断与大小变更：实现单文件 truncate 至指定字节大小（`publish_size_change`），复用（reuse）删除意图与分批回收机制；快照引用的截断尾部块同样进入 deadlist；当前真实改变大小支持首个文件（inode 1），其他活 inode 仅接受等长请求。
- 扫描重建：只读扫描重建模块（`crates/singlefs-checker/src/rebuild.rs`）实现从物理单元反向扫描出中央映射、extent 和 inode 内存结构，并与现行运行时索引树逐项对拍比对零差异；池级 checker 判定的已实现不变量扩展至 108 条。
- 自建 CPU 垃圾回收：实现基于段候选选择与存活块识别的整理规划器、基于 `logged_ops` 的整理意图记录、分批搬迁发布（`publish_relocation_batch`）以及发布后的底层 discard 流程。
- GC 形式化验证：在 Verus 中建立纯函数整理模型，完成一批搬迁保持读取值（`compaction_plan_proofs.rs`）与恒等变换推论的形式化证明，登记 78 个 verified。

### GPU 垃圾回收

用户定案将 GPU 垃圾回收（D26（后台整理与放置回收） 已定项 13）纳入里程碑四出口 8，作为后台计算加速机制：

- 挂载参数体系：引入 `background_compute=gpu`（默认 `cpu`）、`background_gpu_devices` 与 `background_gpu_memory_limit` 挂载参数，实现一套参数统一管理后台整理计算资源。
- 动态切换与刚性报错：支持运行中动态切换计算路径并在下一批生效；若 GPU 设备不可用或运行出错，严格向调用方返回错误，禁止静默回退降级至 CPU 路径，确保行为可预期。
- 前台写入让路：施加 GC 写入带宽上限控制，整理写流量占比严格限制在顺序写带宽的 1.6% 以下，彻底避免后台搬迁冲刷争抢前台 fsync 磁盘带宽。
- 聚合批次必要性：GPU 内核启动与主机设备间通信存在极高的固定开销底噪（φ 达 91.2% 至 99.8%）；单批搬迁提交在所有配置下均跑输 CPU，GPU 垃圾回收必须采用多批聚合形态（`merge_batches`）将数百至数千批任务合并提交以摊薄延迟。
- 身份查找优化：结合 VII·6 优化按身份查映射条目，消除随池容量线性增长的内存查找瓶颈。

### CPU GC 与 GPU GC 对比测试（E185）

基于入库实验装置 E185（GC一批搬迁的挂钟拆分），在 RTX 5090（卡 0）与 RTX 4090（卡 1）上系统测试了不同池容量（P = 1024 与 8192 单元）、存活比例（f = 0.25 与 0.75）及候选段数 K 下的 CPU 与 GPU 性能特征。

CPU 垃圾回收的挂钟耗时拆分测试（E185 第二段 stage-split）表明，CPU 计算开销高度集中于版本重读与映射查找：

| 阶段 / 任务 | 挂钟耗时占比 | 说明 |
|---|---|---|
| 甲·校验和计算（CRC32C） | < 2.05% | 搬迁单元数据校验，单批耗时极低 |
| 乙·区域扫描与映射反查增量 | < 0.66% | 解包单元头与映射过滤增量 |
| 丙·候选段打分与选择 | < 2.89% | 评估各段回收价值的计算开销 |
| 其余·版本重读与内存发布克隆 | > 94.40% | 读现行版本、按单元克隆与树结构更新占据 CPU 绝对大头 |

规模扩展比率 ρ（CPU 耗时 / 盘 I/O 等待耗时，E185 第一段 wall-clock）实测数据揭示了不同池规模下的瓶颈特征：

| 池大小 (P) | CPU / 盘 I/O 耗时比 (ρ) | 瓶颈判定 |
|---|---|---|
| 1024 单元（小池） | 1.22 ～ 1.49 | 计算与 I/O 耗时相当（`both`），均占显著比例 |
| 8192 单元（大池） | 8.44 ～ 9.85 | CPU 计算耗时绝对主导（`cpu`），计算卸载需求随规模剧增 |

GPU 垃圾回收提交形态与收益对比（E185 第三段与对比分析脚本 `e185_r1_compare.py`）得出以下定案结论：

| 提交形态 | 聚合批数范围 | 判定结论 |
|---|---|---|
| 单批次即时提交（`one_batch_per_submission`） | 1 批 | 72 组测试全输（`gpu_loses`），固定调度开销吃满算力 |
| 多批次聚合提交（`merge_batches`） | 125 ～ 5993 批 | 卡 0（RTX 5090）在 120 个对比点中 64 点实现盈利或持平 |

实测中整理写带宽对顺序写带宽的最大比值仅为 0.015977（约 1.6%），证明在合理批聚合调度下，GPU 垃圾回收能有效分担大规模池下的 CPU 计算压力，且完全不干扰前台写入延迟。

### 承接里程碑三欠账与收尾难点

里程碑三在执行后期引入了基于 Verus 的形式化证明核与基于 GPU WGSL 判器的百亿态崩溃放量系统。这两项高强度验证体系消耗了绝大部分研发人力与整机算力，导致里程碑三在收口退出时遗留了大量未完成的工作：

- 算法优化搁置：段 4 规划的容量线性代价优化（二·6 C567）与旋钮登记扫值（六·4）完全未开。
- 门禁分级悬空：常规层与大负载层门禁分级 C409 未能闭环，延期移交。
- 海量欠账转移：51 笔底层欠账（包括删除墓碑判据、崩溃点重放判别力、形式化门禁样本等）转入里程碑四项八，另有 8 笔未合入门禁检查转入项九。

上述巨量遗留欠账对里程碑四的收尾带来了显著困难：工作区既要开发复杂的快照与 GC 事务，又要承接底层修复；多次引发全仓编译锁冲突、显存配额超限与重型门禁运行超时，严重拖慢了里程碑四的收口闭环进度。

### 验证、checker 与代码规模

截至当前，代码库各层验证体系规模如下：

- 池级 checker 不变量：代码清单 `IMPLEMENTED_INVARIANTS` 登记并实现 108 条不变量，GPU 判器内核已同步覆盖全部 108 条。
- 形式化证明：`crates/singlefs-replay-prefix` 内 78 个 verified 全部通过，必红世界严格证红。
- 门禁与用例：门禁框架覆盖 17 道；`#[test]` 规模达 3900 余条，崩溃枚举用例持续覆盖数十亿个崩溃状态。

### 当前产品边界与未开工项

当前实现仍具有明确的工程原型边界：

- 默认产品 GC 路径因生产环境批大小尚未最终定案，在签署意图前停机；测试开关可推进内部搬迁流程，不等于生产自愈 GC 已经全自动可用。
- 截断与大小变更目前仅支持首文件（inode 1）实际改变长度，其余活 inode 仅接受等长请求。
- 系统挂载入口（FUSE / 内核模块）、目录树体系、POSIX 完整文件接口、加密与压缩仍未提供。
- 别拿它存任何数据，磁盘格式在外部正式发布前仍可能推倒重来。
