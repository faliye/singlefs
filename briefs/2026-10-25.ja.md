## 現在の状態（2026-10-25）

**プロジェクトはマイルストーン「共有と回収」（[`.claude/kb/milestone/04-fourth-txn.md`](../.claude/kb/milestone/04-fourth-txn.md)）にあります：読み取り専用スナップショット機構、切り詰めとファイルサイズ変更、読み取り専用インデックススキャン再構築、および CPU ガベージコレクション経路のコアコード実装が揃いました；Verus 形式検証により、GC 移動が読み出し値を保持し恒等変換を構成する性質証明を完了しました（`crates/singlefs-replay-prefix` 内で 78 verified）；GPU ガベージコレクションの設計と実行経路を新たに追加し、E185 実験装置に基づいて CPU GC と GPU GC の比較テストを実施しました；同時に、マイルストーン3から引き継いだ 51 件の深層の未済の検査と 8 件の未マージゲート検査を継承して推進しました。**
現在のマイルストーンは「共有と回収」（[`.claude/kb/milestone/04-fourth-txn.md`](../.claude/kb/milestone/04-fourth-txn.md)）；
この版もまだシステムにマウントして使うことはできません：FUSE もカーネルモジュールもなく、ディレクトリも POSIX インターフェースもありません。**いかなるデータもこれに保存しないでください。**

本ブリーフでは、マイルストーン4のコア進捗、GPU ガベージコレクション機構、CPU と GPU ガベージコレクションの対照実験実測データ、およびマイルストーン3から引き継いだ工学的課題と現在の境界を体系的に整理します。

### コア機能の進捗

マイルストーン4では、複数ヘッドの共有とストレージ回収を中心に一連のコアファイルシステムトランザクション機構を構築しました：

- 読み取り専用スナップショット：読み取り専用スナップショットの作成と破棄（`publish_create_snapshot` および `publish_snapshot_destruction_intent`）を実装しました；deadlist 記帳ツリーを導入し、スナップショットが存在する際の上書きと削除によって解放された古いブロックを即時解放せず deadlist に記録し、スナップショット破棄時にカスケード回収します；生存スナップショット一覧の列挙可能な走査を実現しました。
- 切り詰めとサイズ変更：単一ファイルを指定バイト長へ切り詰める処理（`publish_size_change`）を実装し、削除インテントとバッチ回収機構を再利用しました；スナップショットが参照する切り詰めの末尾ブロックも同様に deadlist に入ります；実際の長さ変更は現在最初のファイル（inode 1）のみをサポートし、他の生存 inode は同長要求のみを受け入れます。
- スキャン再構築：読み取り専用スキャン再構築モジュール（`crates/singlefs-checker/src/rebuild.rs`）は、物理ユニットから中央マッピング、extent、および inode メモリ構造を逆走査して復元し、実行時の現行インデックスツリーと項目ごとに突き合わせて差異 0 を検証します；プールレベル checker が判定する実装済み不変条件は 108 条に拡大しました。
- 自作 CPU ガベージコレクション：セグメント候補の選択と生存ブロックの識別に基づく整理プランナー、`logged_ops` に基づく整理インテントレコード、バッチ移動パブリッシュ（`publish_relocation_batch`）、およびパブリッシュ後の低層 discard フローを実装しました。
- GC 形式検証：Verus 内で純粋関数整理モデルを確立し、バッチ移動が読み出し値を保持する証明（`compaction_plan_proofs.rs`）と恒等変換の系を形式検証し、78 件の verified を登録しました。

### GPU ガベージコレクション

ユーザー決定により、バックグラウンド計算加速機構として GPU ガベージコレクション（D26（バックグラウンド整理と配置回収） 確定項目 13）をマイルストーン4出口 8 に組み入れました：

- マウントパラメータ体系：`background_compute=gpu`（デフォルト `cpu`）、`background_gpu_devices`、`background_gpu_memory_limit` のマウントパラメータを導入し、一組のパラメータでバックグラウンド整理の計算資源を統合管理します。
- 動的切り替えと厳格なエラー通知：実行中に計算経路を動的に切り替えて次のバッチから有効化することをサポートします；GPU デバイスが利用不能であるか実行時エラーが発生した場合、呼び出し元へ厳格にエラーを返し、CPU 経路への無言のフォールバック・縮退を禁止して、動作の予測可能性を保証します。
- フォアグラウンド書き込みへの譲歩：GC 書き込み帯域幅の上限制御を適用し、整理書き込みトラフィックの割合をシーケンシャル書き込み帯域幅の 1.6% 以下に厳格に制限して、バックグラウンド移動のフラッシュがフォアグラウンド fsync のディスク帯域幅を奪い合う事態を徹底的に防止します。
- バッチ集約の必要性：GPU カーネル起動とホスト・デバイス間通信には極めて高い固定オーバーヘッドの下限が存在します（φ は 91.2% ～ 99.8% に達する）；単一バッチの移動投入はすべての構成で CPU に劣後するため、GPU ガベージコレクションでは数百から数千バッチのタスクをまとめて投入する複数バッチ集約形態（`merge_batches`）を採用してレイテンシを償却することが必須となります。
- 身元検索の最適化：VII·6 と連携して身元によるマッピングエントリ検索を最適化し、プール容量に線形比例して増大するメモリ検索ボトルネックを解消します。

### CPU GC と GPU GC の比較テスト（E185）

コミットされた実験装置 E185（GC-一バッチ分の移動の壁時計分解）に基づき、RTX 5090（カード 0）および RTX 4090（カード 1）上で、異なるプール容量（P = 1024 および 8192 ユニット）、生存割合（f = 0.25 および 0.75）、候補セグメント数 K における CPU と GPU の性能特性を系統的にテストしました。

CPU ガベージコレクションの壁時計所要時間分解テスト（E185 第二段 stage-split）は、CPU 計算コストがバージョンの再読み込みとマッピング検索に高度に集中していることを示しています：

| ステージ／タスク | 壁時計所要時間の割合 | 説明 |
|---|---|---|
| 甲・チェックサム計算（CRC32C） | < 2.05% | 移動ユニットデータの検証であり、単一バッチの所要時間は極めて軽微 |
| 乙・領域スキャンとマッピング逆引き増分 | < 0.66% | ユニットヘッダのアンパックとマッピングフィルタリングの増分 |
| 丙・候補セグメントのスコアリングと選択 | < 2.89% | 各セグメントの回収価値を評価する計算コスト |
| 残余・版の再読み込みとメモリ内パブリッシュの複製 | > 94.40% | 現行バージョンの読み込み、ユニット単位の複製、ツリー更新が CPU の圧倒的大部分を占める |

規模拡張比率 ρ（CPU 所要時間／ディスク I/O 待機時間、E185 第一段 wall-clock）の実測データは、異なるプール規模におけるボトルネックの特性を明らかにしています：

| プールサイズ (P) | CPU／ディスク I/O 所要時間比 (ρ) | ボトルネック判定 |
|---|---|---|
| 1024 ユニット（小プール） | 1.22 ～ 1.49 | 計算と I/O の所要時間が拮抗（`both`）し、双方が顕著な割合を占める |
| 8192 ユニット（大プール） | 8.44 ～ 9.85 | CPU 計算時間が圧倒的に主導（`cpu`）し、規模拡大に伴い計算オフロード需要が急増する |

GPU ガベージコレクションの投入形態と利益の比較（E185 第三段および比較分析スクリプト `e185_r1_compare.py`）により、以下の定案結論が得られました：

| 投入形態 | 集約バッチ数範囲 | 判定結論 |
|---|---|---|
| 単一バッチ即時投入（`one_batch_per_submission`） | 1 バッチ | 72 組のテストすべてで敗北（`gpu_loses`）、固定ディスパッチオーバーヘッドが能力を消費 |
| 複数バッチ集約投入（`merge_batches`） | 125 ～ 5993 バッチ | カード 0（RTX 5090）は 120 比較ポイント中 64 ポイントで利益または同等性能を達成 |

実測において、整理書き込み帯域幅のシーケンシャル書き込み帯域幅に対する最大比率はわずか 0.015977（約 1.6%）であり、適切なバッチ集約スケジューリングの下で、GPU ガベージコレクションは大容量プールにおける CPU 計算負荷を効果的に分散し、フォアグラウンド書き込みレイテンシを一切阻害しないことが実証されました。

### マイルストーン3の未払い継承と収束の難点

マイルストーン3の実施後期において、Verus に基づく形式証明核と GPU WGSL 判定器に基づく百億状態クラッシュ増幅システムが導入されました。これら二つの高強度な検証体系は開発リソースと計算資源の大半を消費したため、マイルストーン3の完了退出時に大量の未完了作業が残されることになりました：

- アルゴリズム最適化の棚上げ：セクション4で計画されていた容量線形コスト最適化（二·6 C567）およびノブ登録とスイープ（六·4）は完全に未着手となりました。
- ゲート段階分けの未解決：通常層と大負荷層のゲート段階分け C409 は閉環できず、延期移管されました。
- 膨大な未払いの移管：51 件の低層の未済の検査（削除墓石の判定基準、クラッシュポイント再生の判別力、形式検証ゲートサンプル等を含む）がマイルストーン4セクション8に移管され、さらに 8 件の未マージゲート検査がセクション9に移管されました。

上記の巨額の残存未済の検査は、マイルストーン4の収束作業に著しい困難をもたらしました：作業ツリーでは複雑なスナップショットと GC トランザクションの開発と同時に、引き継いだ低層の改修を行わねばならず、全リポジトリのコンパイルロック競合、GPU メモリ割り当て超過、ヘビー層ゲート実行タイムアウトが頻発し、マイルストーン4の収束進捗を著しく圧迫しました。

### 検証、checker とコード規模

現時点におけるコードベース各層の検証体系の規模は以下の通りです：

- プールレベル checker 不変条件：コード一覧 `IMPLEMENTED_INVARIANTS` に 108 条の不変条件が登録・実装され、GPU 判定器カーネルも全 108 条を同期してカバーしています。
- 形式証明：`crates/singlefs-replay-prefix` 内の 78 件の verified がすべて合格し、必ず赤になる世界も厳格に赤を証明しています。
- ゲートとテストケース：ゲートフレームワークは 17 本をカバー；`#[test]` 規模は 3900 件を超え、クラッシュ列挙ケースは数十億のクラッシュ状態を継続的に網羅しています。

### 現在のプロダクト境界と未着手項目

現在の実装には依然として明確なエンジニアリングプロトタイプの境界が存在します：

- デフォルトのプロダクト GC 経路は、本番環境でのバッチサイズが最終確定していないためインテントの署名前で停止します；テストスイッチによる内部移動プロセスの進行は、本番用自動修復 GC が完全自動で利用可能であることを意味しません。
- 切り詰めとサイズ変更は、現在最初のファイル（inode 1）のみが実際に長さを変更でき、他の生存 inode は同長要求のみを受け入れます。
- システムマウントエントリ（FUSE／カーネルモジュール）、ディレクトリツリー体系、完全な POSIX ファイルインターフェース、暗号化、圧縮は依然として未提供です。
- いかなるデータもこれに保存しないでください。ディスクフォーマットは外部正式リリース前に全面的に再構築される可能性があります。
