### 判定は関数ユニットキーで再利用する

D13 (検証ルート) 確定項目 17 は、判定を再利用する単位は関数だと決めた: 各判定のキーは、それが依存する関数ユニットのコメントを除いた指紋、クロージャが実際に参照する cfg アトムとその真偽、ツールチェーン、解決した依存の版、判定自身の内容入力だけからなる。コミットやツリーで計算した変更範囲、ファイル全体の指紋、手書きの版定数、パス、名前、行番号、資源上限はキーに入らない。クロージャを集めきれないものはキーを拒み、走らせはするが保存しない。キーを変えて旧ライブラリを無効にすることはコストに数えず、互換の移行は書かない。

- 新しいクレート `crates/singlefs-unit-graph`（関数ユニットグラフ）: Rust と WGSL のソースを項目ごとにユニットに切り、コメントを除いた指紋を取り、入口からクロージャを集め、再利用キーを計算する。`std` だけを使い、テスト基盤側に属し、製品コードではない。判定器グループのユニットキーは `crates/singlefs-checker-tier/build.rs` がこれを通して計算し、バイナリに埋め込む。ゲート code-tooling の function-units-two-implementations-agree セルは、これと `scripts/gate/lib_function_units.py` の二つの実装が切り出すユニットがユニットごとに同一であることを判定する（2026-10-16 の測定: 27874 ユニット、8 入口）。
- checker 層のクイック層はテスト関数ごとに再利用する: 二回の実行とも各テスト関数が一つの判定で、キーはそのユニットクロージャに cfg アトムの真偽、release プロファイル、ツールチェーン、依存の版を加えたもの。キーが一致する関数は `--exact --skip` で飛ばし、拒まれたものはそのまま走る。2026-10-18 の後ろ 8 件の実行（`~/.local/share/singlefs/work/fix-2026-10-18/crash-point-replay-full.log`）: フィーチャーなしの回はコンパイルできたテスト関数 1163、今回判定 1155、再利用 0、拒否 8。`gpu,verdict-store` フィーチャー付きの回は 1032、今回判定 1024、再利用 0、拒否 8。再利用 0 なのは関数ごとの判定ライブラリがこの回に初めて埋まったから。拒否 8 件は実行時にパスを組み立てるテストで、クロージャを集めきれない。
- クラッシュ列挙ケースはブロックごとに再利用する: ケースが終わると `CRASH_CASE_BLOCKS blocks= reused= fresh= red= refused=` の一行を出す。クイック層は各ケースを `SINGLEFS_CRASH_CASE_BLOCKS_QUERY=1` を付けて起動し、ブロックキーを計算してライブラリを照会するだけで一ブロックも判定しない。全ブロックに同じキーの判定があるときだけ覆われたと数える。
- クラッシュ判定ライブラリ `~/.local/share/singlefs/crash-amplification/crash-state-verdicts` は今日 7.0G（`du`、測定）。ブロックキーは内容だけで決まるので、どの機械が判定したかに関わらず再利用される: 二台がブロックを半分ずつ取り、二台目の結論はローカルのライブラリにマージする。

### オブザーバーの二段と重複除去

クラッシュポイントに付けるオブザーバー（書き込み可能マウントのオブザーバーと状態ごとの計数オブザーバー）は二段で動く: 記録段は CPU で状態ごとにリカバリして観察し結果をライブラリに書き、判定段はライブラリから読むだけで、イメージは GPU で判定する。

- 重複除去はリカバリ報告のバケット分けと読み出し集合の証人による（ユーザーが 2026-10-16 に決めた）: 記録段はまず `recover` を呼び、リカバリ報告の要約でバケットに分け、バケットの最初の状態だけ実際に走らせ、記録デバイスが読んだ区間とその区間のバイト要約を証人として記録する。後の状態は証人と一致すれば再利用する。読み出し集合はグループごとに一度だけ、証人は一行ずつ保存し、索引は読み出し集合でグループ化する。ケース 6 の unlink ストリーム（2026-10-17 の測定）: 索引を直す前は 23 番目のクラッシュポイントで 5 分ごとに約 13 万状態しか記録できず、直した後は一区間で 301 秒に 799 万状態（約毎秒 2.7 万、推定で約 80 倍）。1184 の証人は 8 の読み出し集合グループにしか分かれなかった。
- 記録段は二台に分け持たせる（2026-10-16 にドライバを変更）: 各機械が自分のライブラリに記録し、今日は二台目の結論だけを取り戻し、記録したブロックはローカルのライブラリにマージしない（次の節を参照）。進捗行は壁時計で 300 秒ごとに出す。
- 重複除去の方式名はオブザーバーの版キーに入る（定数 `OBSERVER_DEDUPLICATION_SCHEME`）。キーに残る手書きの版文字列はこれ一つ。ユーザーは 2026-10-18 に、もう上げないこと、マイルストーン四の締めで削除して保存法のコードをキーに入れることを決めた。

### GPU 判定器: メモリ台帳と判定表の容量

- 同じカード上の複数の判定器は GPU メモリで待ち行列に入る（第五ラウンド、2026-10-16）: 以前は c561 σ 項目が表ごとに判定器を作り、それぞれカード全体の割り当て量で作業領域を開いていたので、31 スレッドが一度にカードに乗ると 5090 で「wgpu error: Out of Memory」に当たった。今は要求幅を作業バッファ一つにし、同じカードの判定器は順に待つ。
- 判定表の容量: 列挙書き込みの上限 `MAXIMUM_ENUMERATED_WRITES` は 2048 から 8192 に、配置先あたりの書き込み数の上限 `MAXIMUM_WRITES_PER_LOCATION` は 64 から 256 に上げた（組み合わせマスクは u64 四語になり、WGSL の配列は Rust の定数から生成する）。与えられた状態の経路では、決して着地しない書き込みに断裂イメージを付け足さなくなった。きっかけはケース 12 のランダム履歴 63 区間が判定表を作れなかったこと（割り当てレコードの壁へ向かう 32 区間は一区間あたり記録書き込み 4436 から 5265、配置先 (0,0) は書き込み 88 から 111）。エンジンはそのとき CPU 判定器に退避し、ケースのアサーションが止めた。カーネルは約 0.3% 大きくなり、固定した三つのカーネルサイズもそれに合わせて変えた。
- ライブラリの単体テスト三件は判定経路を CPU に決め打ちしていて、ゲートの「GPU を構成したら CPU に退避しない」の判定法と衝突した。今は複数マシン構成から経路を取り、gpu フィーチャー付きの回にだけコンパイルされ、探針のストリームは mkfs 済みの二台ディスクのプールに配置先の先頭へ着地する書き込みを使うものに変えた（GPU 判定表はシステム構成を読めるベースを要する）。

### この結果を「検証済みで赤はない」と読んではならない

- **ケース 1 はこれより前に一度赤になり、根本原因は見つかっていない。** 2026-10-18 の三回目の起動で、新規プールでのファイル作成のストリームのローカル分が 101 で終了した: `块 0 在库里没有 allocation_generation_read_sets 的结论（观察者那一路没写库）`。記録段はこのオブザーバーに欠けていた 52 ブロックを記録し、108 ブロックはキーで記録済みと数えたのに、判定段はブロック 0 の結論を読めなかった。同じ日の後に同じツリーでの単独実行は緑（上の表の行）で、二回の間にライブラリに増えたのはその回に記録したブロックと二台目の分から取り込んだ結論だけ。補充の記録と判定段の結論の読み出しの間の順序か帰属の問題（推定）で、マイルストーン四で空のライブラリ上で再現する。
- **ケース 6 は最終のツリーで走らせ直していない。** 2026-10-17 の緑は証人の保存法を変える前のツリーで判定したもので、判定はキーにより今日のツリーで再利用される（イメージ判定のキーもオブザーバーの結論のキーも変わっていない）。走らせ直さなかったのは、今日のドライバでは二台目が自分の分を毎回記録し直す（前回は約 9 時間）ので、今夜には収まらないから。
- **ケース 12 はテストとしては緑、ゲートでは赤。** 22 の赤いブロックはケースが故障注入の設計で認める想定内の赤で、クイック層のライブラリ照会「赤があれば赤」では、その赤がケースの認めるものかどうかを判別できない。ユーザーは 2026-10-18 に甲を決めた: 登録表にこのケースの印を付け、印のあるケースはクイック層でもフル実行と同じように cargo test を起動し終了コードで判定する。変更は進行中で、それが終わってからコミットのゲートに緑が出る。同じケースには、単独実行で判定したのにライブラリ照会で判定が見つからないブロックが 63 ある（推定: 記録経路と照会経路がその 63 表に異なるブロックキーを計算する）。マイルストーン四で調べる。
- 二台目が記録したオブザーバーのブロックは今日はローカルのライブラリにマージされず、毎回記録し直し、止めて再起動すると捨てられる（前回は約 7 時間を失った）。二台の分担は起動時に重みで固定され、走行中にブロックを移せない。判定段の一回のディスパッチの時間は状態数にほとんど比例せず、5090 の計算力は使い切れていない。ユーザーは 2026-10-18 に、ローカルがブロックを配る中央リース、二台目のライブラリをローカルにマージ、判定段は GPU ノードごとにタスクをリースすると決めた。いずれもコミットの後。
- フィーチャーなしの clippy は dead_code を一つ報告する（`crash_amplification.rs` の `gpu_judge_units_fingerprint_of_this_process` はフィーチャーなしでは呼び手がない）。`check.sh` は `--all-features` しか走らせないので、ゲートには見えない。
- この版のコードに対する広域ミューテーションの結論はコミット時にだけ出る。GPU 判定器が正しいかどうかは CPU 判定器と状態ごとに一致することでしか示しておらず、突き合わせたのはクイック層の小さな入力だけ。
- クイック層では lib の区間に今回未実行の行か CPU で判定した行が一つあるだけで区間全体がライブラリに記録されず、次の回は 1000 件を超えるテストを走らせ直す。
