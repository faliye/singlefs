## Current status (2026-09-14)

**Code writing has started.** Steps 0–7 of the milestone "new-pool file creation" ([`.claude/kb/milestone/01-first-txn.md`](../.claude/kb/milestone/01-first-txn.md)) are written:
mkfs on two disks, write a 3000-byte file, commit once, drop everything in the process, and read it back after a cold start.

It cannot yet be mounted into the system: there is no FUSE, no kernel module, and no directories, snapshots, deletion or overwrite. **Do not store any data in it.**
The disk format is still soft and may be torn down and redone at any time before the first external user appears ([`.claude/rules/format-evolution.md`](../.claude/rules/format-evolution.md)).

### Crash-point replay of new-pool file creation: 262165 crash states, zero violations

From after mkfs to the end of the commit there are 33 writes and 6 barriers (including taking the instance number and two warm-up empty publishes).
Cutting the write-request stream into segments at the barriers, with any subset of writes inside a segment persisted and the rest not, gives **262165** crash states, **all enumerated, none sampled**.
For every state, the crash images of both disks are really generated in memory (unpersisted locations hold the old bytes), recovery is run on them, and three things are judged:

| What is judged | Result |
|---|---|
| Reading the file after recovery: if it is read, it must be byte-for-byte correct; once the root is persisted, falling back to the pre-commit state is not allowed; the walk must not fail | Zero violations (the file reads back in 7 states and does not exist yet in 262158) |
| An independently implemented checker (sharing only the format constants with the recovery code) judges the 23 invariants of the first version on the image | Zero violations |
| Record checker: the root is on disk while the journal record is absent; recovery claims to have reached the new state while a unit is absent | Zero violations |

These checks **do go red**: with the root persisted, removing each of the 8 units one at a time goes red all 8 times; removing the barrier between the journal record and the root makes the record checker go red.
Gate checker-tier-crash-point-replay repeats the full run in release mode every time, and goes red if the state count or any counter disagrees with the committed artifact.

The same transaction is also run for real on two virtio disks in QEMU (gate number 55): every write and every FLUSH recorded independently outside the guest on the device side
is identical, item by item, to the stream the program recorded itself; the two controls, dropping one barrier and going through the page cache, both go red.

### This result cannot be read as "it never breaks on power loss"

All it can say is: for **new-pool file creation**, under **the crash model below**, by **the checks implemented so far**, there is not a single violation. It does not cover any of the following:

| Not covered | Why |
|---|---|
| Writes other than new-pool file creation | The workload is number acquisition after mkfs, two empty publishes and one commit with data; not a single block is ever released. Overwrite, reuse after release, multiple mounts and administrator rollback are not in crash-point replay yet ([`.claude/kb/verification-build.md`](../.claude/kb/verification-build.md) 「崩溃点重放 的负载不能只是『新池新建文件』」) |
| Disks that do not honor FLUSH / FUA | The crash model assumes every write before a barrier is persisted ([D13 (Verification Route) settled item 4](../.claude/kb/decisions/13-验证路线.md)). The QEMU level checks that the order the program issues really reaches the virtual device; whether a physical disk's write cache keeps its promise is not in it |
| A torn write that happens to fool the checksum | The model treats every half-torn write as "not persisted" and relies on the 32-bit CRC32C to recognize it; the collision probability is knowingly accepted |
| Invariants the checker does not implement yet | Of the 66 invariants in use in [`crates/singlefs-checker/invariants/README.md`](../crates/singlefs-checker/invariants/README.md), the checker judges 23; the rest have nothing to judge until overwrite, release, rollback and reuse, snapshots or encryption exist |
| Corruption other than crashes (bit flips, misdirected writes) | Not what crash-point replay targets. Recovery only has one set of hand-corrupted probes: if one copy is bad it reads the other, if both are bad it reports unreadable, and it never returns bad data |
| Functional correctness | Random differential testing against an ideal model in memory does not exist yet |
