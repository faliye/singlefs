This brief systematically summarizes the new capabilities, verification systems, and test deliverables achieved in Milestone 3, and thoroughly explains the substantial volume of owed checks left behind due to the heavy resource consumption of formal verification and crash amplification, as well as the significant difficulties these owed checks imposed on wrapping up Milestone 4.

### New core capabilities

Milestone 3 centered on single-file deletion transactions and repeated copy-on-write (COW) progression, landing the following core file system mechanisms:

- Single-file deletion transaction: implemented the single-file unlink workflow (deletion by inode number), employing a two-phase transaction—first publishing deletion intents (`publish_unlink_intent`), followed by background transactions executing batched reclamation of physical units (`publish_unlink_step`), equipped with automatic resumption capabilities upon mount recovery.
- `deleted_inodes` tree and tombstone mechanism: introduced the `deleted_inodes` tree to track objects in intermediate deletion states; established a tombstone mechanism based on the retirement tree (`retirement_tree`), maintaining rigorous accounting during leaf container merges and borrows (`remove_record_from_leaf_containers`), introducing Opt2 watermark retrieval and inode number watermark step rows.
- On-disk format specification: all new fields, intent carriers, and retirement entries involved in deletion transactions were strictly registered in `.claude/kb/layout/03-third-txn.md`.
- Multi-COW read/write consistency: introduced core-tier write entry points by inode number (`UserChange::OverwriteOfAnInode`, `UserChange::SequentialWriteOfAnInode`), constructing multi-COW streams encompassing multi-file interleaved overwrites and large multi-unit writes.
- Instance table sweep: implemented the instance table sweeper (`crates/singlefs-core/src/instance_table_sweep.rs`), attached to the tail of writable mounts, resolving the long-term expansion defect where instance table rows only grew without deletion.

### Verification systems and test deliverables

Milestone 3 conducted deep frontier exploration in verification engineering, constructing a three-tier defense architecture comprising formal methods, model checking, and large-scale hardware acceleration:

- Verus formal verification: established a pure functional recovery replay kernel in `crates/singlefs-replay-prefix`, formally verifying the correctness and monotonicity deductions of prefix truncation, root selection, and ring scan, registering and passing 78 verified items; combined with E165 (Bounded Exhaustive Recovery Replay and Mutation Kill Bound) bounded model enumeration to build strict must-red counterexample suites.
- Independent specification executor and semantic model: implemented the Python-based independent specification executor O3 (E170), and constructed an in-memory reference file system RefFS (`crates/singlefs-reference-filesystem`) based on POSIX semantics, conducting differential testing against the core model.
- GPU crash amplification judge: developed high-performance parallel judges based on WebGPU / WGSL (`crash_judge_checker.wgsl` and `crash_judge_checker_scan.wgsl`), compiling pool-level checker invariants into GPU compute shaders and multiplying judging throughput manifold.
- Two-stage observers and read-set witness deduplication: restructured observers into a two-stage architecture featuring a CPU recording stage and a GPU judging stage, introducing an efficient deduplication algorithm based on recovery-report bucketing and read-set witnesses that elevated recording rates from 130,000 states per 5 minutes to 27,000 states per second.
- Test scale and full run deliverables: gate suite expanded to 17 gates and 131 cells; mutation table `mutations.tsv` reached 3955 rows; implemented invariants in the pool-level checker reached 108; all 14 full run crash enumeration case items were verified across multi-host environments, covering 5,149,586,107 crash states (approx. 5.15 billion) with 0 violations.

### Handover owed checks and obstacles to Milestone 4

Although Milestone 3 achieved critical deliverables in deletion transactions and verification breadth, the introduction of formal verification and the construction of the multi-billion-state crash amplification system heavily consumed engineering personnel capacity and hardware compute resources. To ensure lemma proofs succeeded and the 5.15-billion-state verification system remained stable, development capacity was heavily skewed toward verification infrastructure, resulting in numerous core engineering tasks planned for Milestone 3 remaining uncompleted:

- Algorithmic and performance optimizations completely shelved: capacity-linear cost optimizations planned for Section 4 (II·6 C567, addressing allocation and publish costs growing linearly with pool capacity) and system-wide knob registration/sweeping (VI·4) were completely unstarted, forcing the postponement of the entire section.
- Gate staging left unresolved: gate staging C409 differentiating the regular tier and large workload tier failed to achieve closure and adjudication, lingering at the question definition stage.
- Massive low-level owed checks transferred: at Milestone 3 closeout, 51 owed checks (Section 8)—encompassing deletion tombstone criteria vacancies, crash-point replay discriminative power supplements, and formal gate sample completeness—along with 8 unmerged gate checks (Section 9), could not be cleared within Milestone 3 and were packaged wholesale into Milestone 4.

This severe transfer of engineering debt created extreme difficulties and obstacles for wrapping up Milestone 4 "sharing and reclamation":

- Severe scope inflation: Milestone 4 was originally scoped around read-only snapshots, truncation, scan rebuilds, and CPU/GPU garbage collection, but was compelled to additionally shoulder and stabilize dozens of low-level defects transferred from Milestone 3.
- Resource contention and blocking: fixing and validating inherited owed checks frequently triggered whole-workspace recompilations, contending with Milestone 4 development for cargo compilation locks and multi-core CPU capacity; GPU VRAM quotas repeatedly approached exhaustion when simultaneously supporting multi-billion-state verification and GC measurements.
- Protracted gate closeout: execution durations for heavy tier gates and full run backlog acceptances surged dramatically, causing Milestone 4 to enter prolonged cycles of debt digestion and environmental stabilization even after delivering its primary feature set.
