### Verdicts reused by function-unit keys

D13 (verification route) settled item 17 decided that the unit of verdict reuse is the function: the key of every verdict consists only of the comment-stripped fingerprints of the function units it depends on, the cfg atoms the closure really references with their truth values, the toolchain, the resolved dependency versions and the verdict's own content inputs; change ranges computed per commit or per tree, whole-file fingerprints, hand-written version constants, paths, names, line numbers and resource caps never enter the key; a closure that cannot be collected refuses the key, runs anyway and is not stored; invalidating the old library by changing the key is not counted as a cost, and no compatibility migration is written.

- New crate `crates/singlefs-unit-graph` (function-unit graph): it cuts Rust and WGSL source into units item by item, fingerprints them with comments stripped, collects the closure from an entry point and computes the reuse key, using only `std`; it belongs to the test infrastructure side, not to product code. The unit keys of the judge groups are computed through it by `crates/singlefs-checker-tier/build.rs` and compiled into the binary. The function-units-two-implementations-agree cell of gate code-tooling judges that it and `scripts/gate/lib_function_units.py` cut out unit-for-unit identical units (measured 2026-10-16: 27874 units, 8 entry points).
- The checker tier's quick tier reuses per test function: in both trips every test function is one verdict, keyed by its unit closure plus the cfg atom truth values, the release profile, the toolchain and the dependency versions; functions whose key matches are skipped with `--exact --skip`, refused ones run anyway. The run of the last 8 cases on 2026-10-18 (`~/.local/share/singlefs/work/fix-2026-10-18/crash-point-replay-full.log`): the trip without features compiled 1163 test functions, 1155 judged now, 0 reused, 8 refused; the trip with the `gpu,verdict-store` features compiled 1032, 1024 judged now, 0 reused, 8 refused. Reuse is 0 because the per-function verdict library was first filled in this run; the 8 refused are tests that assemble paths at run time, so their closure cannot be collected.
- Crash enumeration cases reuse per block: when a case finishes it prints one line `CRASH_CASE_BLOCKS blocks= reused= fresh= red= refused=`; the quick tier starts every case with `SINGLEFS_CRASH_CASE_BLOCKS_QUERY=1`, which only computes block keys and queries the library without judging a single block, and a case counts as covered only when every block has a verdict under the same key.
- The crash verdict library `~/.local/share/singlefs/crash-amplification/crash-state-verdicts` is 7.0G today (`du`, measured); block keys depend on content only, so a verdict is reused whichever host judged it: the two hosts each take half of the blocks, and the second host's conclusions are merged into the local library.

### Observers in two stages, with deduplication

Observers attached to crash points (the writable-mount observer and the per-state counting observers) now run in two stages: the recording stage recovers and observes state by state on the CPU and writes the results into the library, the judging stage only reads from the library, and the images are judged on the GPU.

- Deduplication is by recovery-report bucketing plus read-set witnesses (decided by the user on 2026-10-16): the recording stage calls `recover` first, buckets by the digest of the recovery report, really runs the first state of a bucket, and the recording device notes the segments read and their byte digests as a witness; later states that match a witness are reused. Read sets are stored once per group, witnesses one row each, and the index is grouped by read set. On the unlink stream of case 6 (measured 2026-10-17): before the index fix, at the 23rd crash point only about 130 thousand states were recorded every 5 minutes; after it one segment recorded 7.99 million states in 301 seconds (about 27 thousand per second, inferred about 80 times faster); 1184 witnesses fell into only 8 read-set groups.
- The recording stage is split across the two hosts by share (driver changed 2026-10-16): each host records into its own library, and today only the second host's conclusions are fetched back, not its recorded blocks (see the next section). A progress line is printed every 300 seconds by wall clock.
- The name of the deduplication scheme is part of the observer version key (constant `OBSERVER_DEDUPLICATION_SCHEME`), the only hand-written version string left in any key; the user decided on 2026-10-18 that it is no longer bumped and is removed at the wrap-up of milestone four, letting the storage code enter the key instead.

### GPU judge: memory ledger and judge-table capacity

- Several judges on one card now queue on GPU memory (fifth round, 2026-10-16): before, the c561 σ item created one judge per table, each opening a scratch area sized to the whole card's quota, and 31 threads landing on the card at once hit "wgpu error: Out of Memory" on the 5090; now the request width is one scratch buffer and judges on the same card queue.
- Judge-table capacity: the enumerated-writes limit `MAXIMUM_ENUMERATED_WRITES` went from 2048 to 8192 and the writes-per-placement limit `MAXIMUM_WRITES_PER_LOCATION` from 64 to 256 (the combination mask became four u64 words, and the WGSL arrays are generated from the Rust constants); the given-states path no longer appends torn images for writes that never land. The cause was that 63 random history segments of case 12 could not be built into judge tables (the 32 segments toward the allocation record wall had 4436 to 5265 recorded writes each, and placement (0,0) had 88 to 111 writes); the engine then fell back to the CPU judge and the case's assertion caught it. The kernels grew by about 0.3%, and the three pinned kernel sizes changed accordingly.
- Three library unit tests hard-coded the CPU as their judge route and collided with the gate's rule "a configured GPU does not fall back to the CPU"; they now take the route from the multi-host configuration and are compiled only into the trip with the gpu feature, and their probe flow became a two-disk pool after mkfs with writes landing on placement starts (the GPU judge tables need a base whose system configuration can be read).

### This result cannot be read as "verified, nothing red"

- **Case 1 went red once before, and the root cause is not found.** In the third start of 2026-10-18 the local share of the new-pool file creation stream exited 101: `块 0 在库里没有 allocation_generation_read_sets 的结论（观察者那一路没写库）`: the recording stage recorded the 52 blocks this observer was missing, 108 counted as recorded by key, yet the judging stage could not read the conclusion of block 0. Later the same day a single run on the same tree went green (the row in the table above), and between the two runs the library only gained the blocks recorded in that run and the conclusions imported from the second host's share; it is an ordering or ownership problem between the top-up recording and the judging stage's reading of conclusions (inferred), to be reproduced on an empty library in milestone four.
- **Case 6 was not rerun on the final tree.** Its green of 2026-10-17 was judged on the tree before the witness storage change, and the verdicts are reused by key on today's tree (neither the image-judgement key nor the observer-conclusion key changed); it was not rerun because today's driver makes the second host re-record its share on every run (about 9 hours last time), which does not fit in tonight.
- **Case 12 is green as a test and red at the gate.** The 22 red blocks are expected red that the case accepts by its fault-injection design, and the quick tier's library query, "any red is red", cannot tell whether a red block is one the case accepts; the user decided 甲 on 2026-10-18: the registry marks this case, and for marked cases the quick tier starts cargo test as the full run does and judges by exit code. The change is in progress, and only after it does the commit gate have a green. The same case also has 63 blocks whose verdicts the library query cannot find although the single run judged them (inferred: the recording path and the query path compute different block keys for those 63 tables), to be investigated in milestone four.
- The second host's recorded observer blocks are not merged into the local library today; they are re-recorded on every run and discarded when a run is stopped and restarted (about 7 hours lost last time); the split between the two hosts is fixed by weight at start and blocks cannot move while running; the time of one dispatch in the judging stage hardly grows with the number of states, so the 5090's compute is not used up. The user decided on 2026-10-18: central block leasing with the local host handing out blocks, the second host's library merged into the local library, and the judging stage leasing tasks per GPU node; all after the commit.
- Clippy without features reports one dead_code (`gpu_judge_units_fingerprint_of_this_process` in `crash_amplification.rs` has no caller without features); `check.sh` only runs `--all-features`, so the gate does not see it.
- The broad-mutation conclusions for this version of the code are produced only at commit; whether the GPU judge is right is proven only by being identical to the CPU judge state by state, and the differential has only covered the small inputs in the quick tier.
- In the quick tier, one line reporting not run this time or one CPU-judged line in the lib section keeps the whole section out of the library, and the next trip reruns its more than 1000 tests.
- Before the commit, to pass the nine gates that are not heavy, about 40 names (vague names and names carrying an ordinal) and a few constant spellings were changed in the checker tier, the harness tier, the function unit graph and ten experiment fixtures: only a compile check (three packages with and without features, the ten fixtures) and rustfmt were run, not the tests; these changes alter the unit keys of many verdicts, and per the user's decision the six gates of the heavy tier were not rerun on the final tree before the commit.
