### Six gates at commit, two things on user request, a light tier and a heavy tier

Every commit runs six heavy gates: checker-tier-crash-point-replay (quick tier), checker-tier-qemu-device-streams, checker-tier-lkmm, checker-tier-crates-mutation-replay, checker-tier-formal-verification and checker-tier-broad-mutation, with `SINGLEFS_HEAVY_TESTS=commit` on the command; all six are registered in `.claude/gate.d/stage-inputs.tsv`, and if their inputs have not changed the previous verdict is reused. The full run of crash-point replay (`--full`) and the full run of crash amplification happen only on user request. Every GPU run quiesces first and does not restore afterwards ([`.claude/rules/verification.md`](../.claude/rules/verification.md)).

On 2026-10-10 the user decided on two tiers (`.claude/kb/verification-build.md` 「八、崩溃点重放：崩溃放量的流程与用户定的两档」): crash-point replay, formal verification and the crates mutation table are each split into a light tier and a heavy tier. The light tier is run by the implementation writer and by post-merge verification; it is the core part plus items named by the change, without pruning. The heavy tier is the overall gate at commit, with three ways of running (pruning, item by item, full run), and nothing is committed while it is red. The light tier must be a subset of the heavy tier and stays until the transaction features are complete.

The same day it was decided to merge crash-point replay and crash amplification into one set. Today the repository already has the merged table `.claude/gate.d/crash-point-replay-items.tsv` (13 items, one stream per item, merging the 13 `crash-case:` rows and the 8 amplification items deduplicated by stream) and the entry point `scripts/crash/crash-point-replay.sh`; the three light-tier commands run with `--quick` as described in `verification.md` 「两档：轻型与重型」. Behind it the two original drivers are still called; until the new entry point is wired into the commit run, commits still run the quick tier and the full run as before.

### Formal verification: Verus verifies the core that takes the recovery replay prefix

The new crate `crates/singlefs-replay-prefix` is the pure-function core that takes the journal prefix for recovery replay; it depends only on `vstd`, and `singlefs-core` depends on it, so what Verus verifies is exactly the copy compiled into the product and called by the recovery path. Gate checker-tier-formal-verification has six cells: four verify this crate (toolchain pinning, `--no-cheating` proof, vacuity, must-red worlds; `.claude/gate.d/verus-pins.tsv` registers 56 verified, Verus release `0.2026.09.20.aef82ed`); the other two judge that the red-example pin table of E165 (Bounded Exhaustive Recovery Replay and Mutation Kill Bound), `.claude/gate.d/e165-pinned-red-examples.tsv` (360 rows), is complete and that every row replays on the implementation of the tree being judged.

### Mutation: the crates mutation table and broad mutation

### RefFS: the semantic reference file system

The new crate `crates/singlefs-reference-filesystem` (RefFS) walks POSIX operations in memory only, and judges whether what recovery reads back after a crash falls inside the allowed set; its only dependency is `std`, and it imports neither the implementation, the pool-level checker nor the two tiers, as judged by the checker-implementation-disjoint cell of gate checker-independence-and-sync. Both the harness tier and the checker tier call it.

Judged now plus reused is 5,201,290,115 states, 0 violations. Running again against the library right afterwards, all 8 items reused 5,201,290,115 states with 0 judged now, which is the evidence that resume works. Three points need careful reading:

- **The red of position-addressed-trees is not a violation.** The stream `ExtentLowerSegmentGrowsToTwoLevels` has segment write counts [322, 290, 1, 2], a whole domain of 2^322 + 2^290 + 3 states, which expansion 30 cannot cover; only 10 states were judged (each of the two long segments landing whole and not landing at all). The other four streams total 553,664,562 states in closed form, differing from the judged-now count only by the 40 base states the crash points carry, so they are exhaustive. The entry point goes red by the rule "at full depth every row must be exhaustive=true". Verdict J10 of the third round of the crash enumeration merge decided to register by segment, judge registered segments on the union of the 甲二 domain (in-place writes take any subset, COW writes only all or nothing) and expansion 6, and report skipped amounts with segment numbers and write counts: the engine side is implemented, the entry point side is not wired in, and the registry has no segment registered yet (C790). Which segments to register is for the user to decide.
- **The observer (J4) was not inlined in this run.** The writable-mount observer mounts once on the CPU and runs the pool-level checker once for every state; even after removing the full journal ring scan it takes about 19.5 ms per state per thread (measured with 8 threads), while the GPU judges a state in about 4 µs; the 20753 blocks of the multi-record publish item would take about 5 days on two hosts (inferred). On 2026-10-12 the user decided the observer becomes a class of its own and is not inlined in this round: the test module reads `SINGLEFS_CRASH_AMPLIFICATION_OBSERVERS=deferred`, and the entry point records those two items as not-run. The full-run case of the crash-point replay deletion stream attaches the same observer directly to every state, and was not named in this run (C789).
- **In the σ item, 1 ignore point, 869,269,834 states, is not judged per the registry**; it is preset in the case. The entry point added up the same number reported by each of the three two-host driver lines, so the ITEM and TOTAL lines say 3 points and 2,607,809,502 states (C791).

This run also caught and fixed one place in product code: the slice form of `PoolReader` (`&[(DeviceIdentity, Device)]`) had no hint for the journal record slots, so every recovery in a writable mount scanned the whole of both 768 MiB rings, and 330 ms of the observer's 345 ms per state went to the ring scan. The fix adds `journal_record_offsets_hint` to `BlockDevice` with a default that returns `None`; the slice read path forwards the disk's answer, the sparse memory disk answers from the sectors written, and the recording disk and the fault injection disk pass it through. The new test `crates/singlefs-harness/tests/sparse_block_device_journal_hint_matches_the_full_ring_scan.rs` has three cases (the hint and the full ring scan find the same slots after mkfs, after warm-up, and after the first file; the slice read path passes it through; the fault injection disk passes it through); `crates/mutations.tsv` gained three rows (hint returns the empty set, slice does not pass it, fault injection disk does not pass it, each proven red), and the light-tier registry gained one row. `recovery.rs` is in the code closure of the GPU judge, so the judge version changed from `gpu_judge:7fa0adbf10708a36` to `f0b9512b88d5bbfe`; conclusions in the library from before are not reused under the new version, and each item was judged again.

Two pitfalls at the script layer, both hit for the first time in this run: the worktree is built from HEAD plus the staged tree and does not carry the `.claude/singlefs-ai-sop/` copy ignored by `.gitignore`, so the static check before the crash-point replay gate starts could not import `preflight` (`gate.sh --staged` copies it when building the tree; the full-run script did not); the `cargo test … --exact <case>` assembled by the two-host driver through the shared library did not carry `--include-ignored`, and since every crash-point replay full-run case is marked ignore, not a single recording stage ran, it exited 0, and the gate went red; the two-host path of crash-point replay had never run green before this.
