### Core functional progress

Milestone 4 establishes a series of core file system transaction mechanisms centered on multi-head sharing and storage reclamation:

- Read-only snapshots: implemented the creation and destruction of read-only snapshots (`publish_create_snapshot` and `publish_snapshot_destruction_intent`); introduced the deadlist accounting tree, where old blocks freed by overwrites and deletions while snapshots exist enter the deadlist rather than being immediately released, cascading into reclamation only upon snapshot destruction; live snapshot lists support enumerable traversal.
- Truncation and size modification: implemented single-file truncation to specified byte lengths (`publish_size_change`), reusing (reuse) deletion intents and batched reclamation mechanisms; trailing blocks truncated under snapshots similarly enter the deadlist; actual length modification is currently supported for the initial file (inode 1), while other live inodes accept only equal-length requests.
- Scan rebuild: the read-only scan rebuild module (`crates/singlefs-checker/src/rebuild.rs`) scans physical units to reconstruct in-memory central mapping, extent, and inode structures, verifying zero divergence via differential comparison against runtime index trees; implemented invariants judged by the pool-level checker have expanded to 108.
- Built-in CPU garbage collection: implemented a compaction planner based on segment candidate selection and live block identification, compaction intent records residing in `logged_ops`, relocation batch publishing (`publish_relocation_batch`), and post-publish underlying discard workflows.
- GC formal verification: established a pure functional compaction model in Verus, formally verifying that batch relocation preserves read values (`compaction_plan_proofs.rs`) and identity transformation corollaries, recording 78 verified items.

### GPU garbage collection

Per user settlement, GPU garbage collection (D26 (background compaction and placement reclamation) settled item 13) has been incorporated into Milestone 4 Exit 8 as a background compute acceleration mechanism:

- Mount parameter framework: introduced `background_compute=gpu` (default `cpu`), `background_gpu_devices`, and `background_gpu_memory_limit` mount parameters, establishing a unified parameter suite to manage background compaction computing resources.
- Dynamic switching and strict error escalation: supports dynamic switching of compute paths during execution, taking effect on the subsequent batch; if GPU devices are unavailable or encounter execution failures, errors are strictly returned to callers without silent fallback degradation to CPU paths, guaranteeing predictable behavior.
- Foreground write yield: enforces a GC write bandwidth ceiling, strictly capping compaction write throughput below 1.6% of sequential write bandwidth to eliminate background migration interference with foreground fsync disk bandwidth.
- Necessity of batch aggregation: GPU kernel launches and host-device communication exhibit high fixed overhead floors (φ reaching 91.2% to 99.8%); single-batch migration submissions lose to CPU across all configurations, making multi-batch aggregation forms (`merge_batches`) combining hundreds to thousands of batches essential to amortize invocation latency.
- Identity lookup optimization: coupled with VII·6 optimizations for looking up mapping entries by identity, eliminating memory search bottlenecks that scale linearly with pool capacity.

### Comparison test of CPU GC and GPU GC (E185)

Utilizing the committed experimental apparatus E185 (wall-clock breakdown of a batch of GC migrations), CPU and GPU performance characteristics were systematically evaluated on an RTX 5090 (Card 0) and an RTX 4090 (Card 1) across varying pool capacities (P = 1024 and 8192 units), live fractions (f = 0.25 and 0.75), and candidate segment counts K.

Wall-clock breakdown measurements of CPU garbage collection (E185 stage 2, stage-split) demonstrate that CPU compute costs are overwhelmingly concentrated in version re-reading and mapping lookups:

| Stage / Task | Share of Wall-Clock Time | Description |
|---|---|---|
| A · Checksum computation (CRC32C) | < 2.05% | Data verification for relocated units, incurring minimal single-batch overhead |
| B · Region scan and mapping inverse lookup increments | < 0.66% | Unpacking unit headers and mapping filter increments |
| C · Candidate segment scoring and selection | < 2.89% | Computational cost of evaluating reclamation value across segments |
| Remaining · Version re-reading and in-memory publish cloning | > 94.40% | Reading current versions, per-unit cloning, and tree updates dominate CPU execution |

Scaling ratio ρ (CPU time / disk I/O wait time, E185 stage 1, wall-clock) empirical measurements reveal bottleneck transitions across pool sizes:

| Pool Size (P) | Ratio of CPU to Disk I/O Time (ρ) | Bottleneck Verdict |
|---|---|---|
| 1024 units (small pool) | 1.22 ~ 1.49 | Compute and I/O durations are comparable (`both`), each claiming substantial shares |
| 8192 units (large pool) | 8.44 ~ 9.85 | CPU compute heavily dominates (`cpu`), with compute offloading demand surging at scale |

GPU garbage collection submission forms and profitability comparisons (E185 stage 3 and comparison analysis script `e185_r1_compare.py`) yield the following settled conclusions:

| Submission Form | Aggregated Batches Range | Verdict Conclusion |
|---|---|---|
| Immediate single-batch submission (`one_batch_per_submission`) | 1 batch | Loses across all 72 test groups (`gpu_loses`), fixed dispatch latency consuming compute capacity |
| Multi-batch aggregation submission (`merge_batches`) | 125 ~ 5993 batches | Card 0 (RTX 5090) achieves profitable or neutral performance across 64 of 120 comparison points |

Empirical measurements confirm that the maximum ratio of compaction write bandwidth to sequential write bandwidth is 0.015977 (approx. 1.6%), verifying that under disciplined batch aggregation, GPU garbage collection effectively alleviates CPU compute pressure in large pools without disrupting foreground write latency.

### Inheriting Milestone 3 debt and wrap-up difficulties

During the late stages of Milestone 3, formal verification proof kernels based on Verus and a multi-billion-state crash amplification system based on GPU WGSL judges were introduced. These high-intensity verification architectures absorbed the vast majority of engineering personnel and hardware compute capacity, leaving substantial unfinished work at Milestone 3 closeout:

- Deferred algorithmic optimizations: Section 4 optimizations regarding capacity-linear costs (II·6 C567) and knob registration/sweeping (VI·4) remained completely unstarted.
- Unresolved gate staging: gate staging C409 differentiating the regular tier and large workload tier remained open and was postponed.
- Substantial debt transfers: 51 low-level owed checks (encompassing deletion tombstone predicates, crash-point replay discriminative power, and formal gate samples) transferred into Milestone 4 Section 8, with an additional 8 unmerged gate checks moving to Section 9.

This inherited owed check volume imposed significant obstacles on Milestone 4 wrap-up: the workspace was compelled to simultaneously construct complex snapshot and GC transactions while stabilizing inherited low-level defects; this triggered frequent workspace compile lock contention, GPU memory quota exhaustion, and heavy tier gate timeouts, substantially complicating the closeout of Milestone 4.
