## Current status (2026-09-28, updated 2026-09-29 and 2026-09-30)

**Crash amplification is wired into the code, and the whole judge has moved onto GPUs: everything the CPU judge judges (root selection and both recovery passes, the seven oracle classes, the two criteria of the record checker, and all 49 invariants of the pool-level checker) is also judged by GPU kernels,
identical to the CPU judge state by state. After quiescing, with two hosts and five GPU cards and an expansion limit of 28 enumerated in full, the seven items total 2.616 billion states with zero violations (the stream through E then unmount alone is 1 662 648 564 states), in one run of 7 hours 37 minutes.**
Steps 0–5 of the milestone "overwrite, release, rollback and reuse" ([`.claude/kb/milestone/02-second-txn.md`](../.claude/kb/milestone/02-second-txn.md)) are all in the code.
This version still cannot be mounted into the system: no FUSE, no kernel module, no directories, snapshots or deletion. **Do not store any data in it.**

### Crash amplification: record first and verify later, reuse by block, merge two hosts

A crash point is tied to a fork in the test code, with the identity `<path in repo>::<crash point name>::<reuse key>`, where the reuse key = SHA-256(write table with barriers, final value of the parent image); the judging-method version is an attribute of the verdict row:
when the judging method changes, old rows are kept as history and this version judges from scratch. A path `<flow>.<cycle>.<step>/…` is only an index (`acquire_instance_and_warm_up.system_configuration_slot.1/…/publish_overwrite.data_unit+index_node+packed_records.1`);
the block key contains only the identity: renaming does not invalidate a verdict, and the common prefix of several streams is verified only once in the library. Verdicts go into RocksDB; the two hosts each write their own library, merged into one after the run, and recorded blocks minus verified blocks is what is still owed.

On 2026-09-28, four ways of running were made to work end to end with the CPU judge:

| Way of running | Domain | Result |
|---|---|---|
| Single CPU, two-host CPU, single-host CPU+GPU, two-host CPU+multi-GPU | Fixed script through D, expansion limit 18: 393 338 states | All four: 0 red, empty reconciliation |
| Two-host CPU, 31 threads on each host | Fixed script through D, whole domain (all 36 segments expanded): **51 773 558 states** | **0 red**; this host 4108 states/s, the second host 4320 states/s, about 100 minutes each |
| Same library, same code, run again | Same as above | Both hosts `states_checked_here=0`: nothing already verified is rerun |

"Whole domain" means every proper subset of every barrier segment is enumerated (`exhaustive=true`), with no sampling; pruning comes only from the ignores and expansion limit preset in the test code, and segments where no pruning is switched on do not lose a single state.

### Three-stage pipeline: judge, verify, compare state by state

① The judge judges every state and writes the verdict into the KV store; at the same time, the facts needed for verification (class and checksum of each unit write, fields and pointers of each root, units and roots in the baseline, three-state writes, the state range of each segment) are written into the KV store per stream.
② Verification from the facts: another GPU kernel verifies a whole block (65 536 states) in one dispatch, or a CPU reference implementation verifies with the same criteria; the two are equal state by state.
③ The verification table and the verdict table are compared state by state: verification red ⇒ the judge must be red, and not a single disagreement is allowed.

Criteria covered by stage ②: the latest persisted root verifies itself, where its four pointers land (the position entry checksum matches a unit that is on disk), and the two checksums of that unit itself.
The very first differential run hit a wrong criterion ("any persisted unit with a bad checksum is red": in a crash state, half-written units not referenced by the root naturally do not match, and the pool-level checker does not judge them); it was fixed.

### GPU judge: three kernels, one table, state-by-state differential

All placements of a stream and their byte versions under every persistence combination are first laid out as tables on the CPU (`crash_judge_tables`) and uploaded to the card whole; each state gets one GPU thread that decodes the persisted set from its index and looks up the version of every placement,
then decodes the system configuration, roots, journal, index nodes, packed records and data units from the bytes in GPU memory. The judging follows recovery in `singlefs-core` and the pool-level checker in `singlefs-checker`, each written separately (WGSL, no shared code).

| Kernel | What it judges | Compared with the CPU |
|---|---|---|
| `crash_judge_recovery.wgsl` | Choose the system configuration, root selection, ring scan, replay the prefix (back links, sequence numbers, commit markers, verify every named unit), walk to the first file; one pass with and one without the journal; the seven oracle classes; the two record checker criteria | Red bits, the root landed on, and the outcome class of both passes are identical state by state |
| `crash_judge_checker.wgsl` (walk kernel) | First batch: system configuration, root ring, the four journal ones and I-7.7; second batch: the 29 walk invariants (instance table chain, tree table, inode tree, allocation record tree, extent upper and lower segments, multi-level code-2 tree, central mapping entries, rollback candidate set, versions applied from records, abandoned roots) | The violation bits of the 49 invariants are identical bit by bit |
| `crash_judge_checker_scan.wgsl` (scan kernel) | Third batch: I-1.8, I-3.9, I-9.14, I-5.4, I-3.10, I-7.9, I-3.1 / I-5.2 / I-3.11 (including the quarantine exemption and the defer below F) | Same as above |

Differential case `crash_judge_gpu_agrees_with_the_cpu_judge_on_every_state`: 6 existing streams (new-pool file creation, corrupted tree table, journal commit marker 2, record flag 3, slot distance 512, fixed script through rollback D)
plus 11 must-red streams (inode record blocks, birth generation of a data unit object, generation of an allocation record, two overlapping allocation records, accounting value, tree table order, birth txg of a mapping key, instance table row, two differing copies of a data unit, tree table birth txg across roots, release generation out of range:
each red on its designated invariant), expansion limit 16, 525 365 states identical state by state. The must-red streams rely on `corrupt_units_and_reseal_up_to_the_root`: after changing one field it reseals both checksums of the unit, then replaces every position entry pointing at it (tree nodes, root records, journal named items) with the new whole-unit CRC,
reseals each changed structure and propagates the back links, so the only corruption left is that field itself. σ (the misaligned-reuse history) has its own differential: it writes slot 0 of the system configuration 34 times, so the combination mask of one placement in the judge's tables needs the upper 32 bits; 65 548 states identical state by state.

The first run of the must-red streams caught two holes that comparing red bits alone could not see, both fixed: the walk kernel kept overwriting the accounting row during the candidate-root passes (the CPU copies the accounting away after walking the latest root); the "with journal" pass of the recovery kernel never called `scan_journal`,
so both recovery passes landed on the same root: in states where the record had landed but the root had not, the CPU landed on the new version and read the file while the GPU landed on the old version with no file, and the oracle was green on both sides. The differential was therefore tightened to also compare the root landed on and the outcome.

### Pipeline: if GPUs are configured the GPU judges, and if it cannot, it is an error

With `ENABLE_GPU=1`, stage ① has the GPU judge judge every block, stage ② has another kernel verify from the fact tables, and stage ③ compares with the verdict blocks state by state. There is no sampling and no fallback:
failing to build the tables, a state the GPU cannot judge, a card named in the configuration being unusable, or two hosts being configured and the second host failing to run are all errors that exit, without falling back to the CPU judge, using one card fewer, or switching to one host.

GPU cards are used by the priority in the private configuration: on the same host the card ranked first is filled first (one dispatch carries as many states as fit in its memory quota), and only what does not fit goes to the next card.
The full run (`scripts/crash/crash-amplification.sh`) quiesces at startup (stopping the inference and speech services on both hosts) and gives whole cards to crash amplification, restoring on exit.

At any one time a card computes the states of one dispatch; each state's scratch area is 0.94 MiB. Once a dispatch carries enough states, the time per state shoots up, while memory is still far from full
(fixed script through rollback, expansion 16, middle of the stream):

| Card | Fastest step | One more buffer (2 170 states) | Memory full |
|---|---|---|---|
| 5090 | 21 700, 1.56 µs per state | 2.99 µs | 31 291, 86.4 µs |
| 5060 Ti | 6 510, 5.92 µs | 37.3 µs | 14 072, 276.6 µs |

So the number of states per dispatch is not computed from memory but measured on the card: the same range of states is dispatched one buffer larger each step, stopping when a state is 25% slower than the best step or one dispatch exceeds 0.25 seconds, and taking the fastest step;
it is remeasured every 512 dispatches (the knee moves with how heavy the states are), and steps past the knee are not tried again. When one dispatch runs on the card too long, the driver reports a context-switch timeout and kills the channel (kernel log Xid 109),
and the program never gets its result: if one dispatch exceeds 0.5 seconds, the next is halved, and waiting for the card is capped at 120 seconds before it is an error.

a stream that had been red once showed green on the next run (each stream's wrap-up only looked at the red judged in that run); the second host rebuilt dependencies from scratch every run. The account is in section three of `records/2026-09-28-里程碑三崩溃放量剪枝与GPU调度.md`.

### This result cannot be read as "it never breaks on power loss"

- The correctness of the GPU judge is proven only by being identical to the CPU judge state by state; if both are wrong in the same place, the differential cannot catch it. The must-red streams with corrupted fields only cover the red paths of 11 invariants; the other 38 were only compared on healthy streams.
  The differential compared 17 streams, 525 365 states at expansion limit 16, and 65 548 states on σ; larger domains were not compared (in the full run, stage ② has another kernel verify from the fact tables and stage ③ compares state by state, which is a different full-run verification covering only its own criteria).
- Of the crash enumeration streams in the registry, the ones wired into amplification are the seven items in the full-run table; crash injection samples random history runs and has no fixed sequence of points, and does not enter the pipeline (light test).
- Every table in the kernels has a capacity (64 writes per placement, 2048 references, 1024 data unit objects, 1024 instance table rows, 2048 allocation records, 4096 defers, and so on): states that exceed it cannot be judged by the GPU, and the pipeline exits with an error naming the state and the reason codes of both kernels; raise the kernel capacity and run again.
- Kernel cold compile: the driver's compiler expands every call site into a copy of the callee. The walk kernel originally had six call sites for "walk one root", which after expansion was more than three times the size of the other two kernels; cold compile on this host took 523 seconds, and the second host (driver version 580) could not finish within 48G of memory. After changing to one call site, about 18 seconds on this host and 94 seconds and 3.4 GiB on the second host. Before compiling a kernel, its expanded size is measured, and over 400 thousand expressions is refused (the three kernels are 220 to 270 thousand). The driver's on-disk cache (`__GL_SHADER_DISK_CACHE`, enabled by `usable_gpu_cards`) uses one shared application name, so each host cold-compiles each kernel version once.
- The judging-method closure only collects the files that the two judges reach by module reference (the core write-path files referenced by `recovery` are in it: collected at file granularity, not cut finer); the pipeline, dispatch, storage, identity, progress modules, the GPU verifier and the test files that set the points are not in it, and changing them does not invalidate verdicts. The library lives under `~/.local/share/singlefs/crash-amplification/`; placing it in a directory cleared at boot such as `/tmp` is refused, and rerunning the same command resumes.
- The quick tier of the checker tier (library and integration tests) has 3 red, the inline tests of experiment fixtures e158 and e161 have 10 red, and 5 anchors of the crates mutation table do not match the source: all are pinned values not rechecked after the end of milestone two changed the write path; they are already on HEAD and not fixed yet.
- Large-scale fault injection has 2 new findings: after the device swallows one write in the starting segment, the model says the writable mount should succeed, while the implementation refuses with "rereading once still cannot read a newer state"; recorded as an owed check, not decided.
