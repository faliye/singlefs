## 三、 第二问审核：转入 GPU 后，CPU 是否释放？

分「操作系统物理进程占核」与「`task-server` 调度器 CPU 闸账面记账」两个层面核查：

### 1. 物理进程层面：进入纯 GPU 判段时物理 CPU 已释放（单格 1～2 核）
- 在 `broad-mutation.py:3338-3343`（串行跑预编译二进制）、`.claude/gate.d/crash-point-replay.sh:3398`（直接起二进制跑 `--stage judge`）、`crates-mutation-rows.py:5534`（等普通 worker 全部收齐后一次只派 1 格）、`replay.sh:5174-5216`（串行跑 `REPLAY_GPU_ROWS`）中，CPU 阶段的多线程 `cargo` 编译池与多进程 worker 池均已停下，进程树在 GPU 阶段实际只用 1～2 个物理核喂卡与等卡完成。
- 物理层面的两处例外：
  1. `crates-mutation-rows.py` 在 `card_ready` 阶段各格之间会还卡并拉起单格 `cargo test ... --no-run` 编译（此时不持卡，但会短暂重新用满 `CARGO_BUILD_JOBS` 核）。
  2. `scripts/crash/crash-point-replay.sh:3834-3846` 在一片内依次串行跑 `run_test_functions`、`run_enumeration_part`、`run_pipeline_part` 三段，每段各自经历一次「CPU 编译/录制 → 领卡跑 GPU → 还卡」，因此物理 CPU 是三波「满核 → 1 核 → 满核 → 1 核」往复，而非整片只做一次 CPU 到 GPU 的单向切换。

### 2. `task-server` 调度器 CPU 闸（账面核数）层面：不是当场释放，存在 3 处滞后与边界问题

`task-server` 的 CPU 闸在 `task-server/task_server.py:10653-10655` 中按 `occupied = max(load, threads)`（本台实时负载与服务在跑尝试的账面线程数 `running_threads` 取大）判定新任务能否进场。在跑尝试的账面核数由 `running_threads`（第 10733-10762 行）与 `measured_running_cores`（第 10764-10786 行）计算：

```python
if attempt.get("card_lease"):
    _, samples = self.note_running_sample(
        self.running_cpu_samples, attempt.get("id"), now, usage,
        CPU_RECENT_WINDOW_SECONDS, earlier_reading, keep_anchor=True
    )
    if (elapsed > CPU_RECENT_WINDOW_SECONDS and samples
            and now - samples[0][0] >= CPU_RECENT_WINDOW_SECONDS
            and samples[0][1] <= usage and self.card_taken(attempt)
            and not lib.broken("cpu-running-whole-average", self.environment)):
        return min(
            max(registered, 1),
            max(1, math.ceil((usage - samples[0][1]) / 1e6 / (now - samples[0][0]))),
        )
```

核查发现以下 **3 个导致转入 GPU 后账面 CPU 未能及时（或未能）释放的机制问题**：

#### 问题 ①：600 秒（10 分钟）滑动窗口滞后——领卡瞬间账面核数丝毫不降
- `CPU_RECENT_WINDOW_SECONDS = 600`（`task-server/task_server.py:1058`）。
- 服务在任务起跑后一路往 `self.running_cpu_samples[attempt_id]` 追加 `(now, usage)` 读数，保留 600 秒前的锚点 `samples[0]`；**在调用 `lease_take`（`task-server/task_server.py:8461-8549`）领到卡的那一刻，服务并没有清空或重置 `running_cpu_samples` 的窗口起点**。
- 结果：当任务刚结束 31 核满跑的 CPU 阶段、调用 `lease take` 转入只占 1 核的 GPU 阶段时，`[samples[0][0], now]` 这 600 秒窗口里装的**全部是刚刚过去的那 10 分钟满核 CPU 阶段读数**。
- 因此，在转入 GPU 的瞬间，`(usage - samples[0][1]) / 1e6 / (now - samples[0][0])` 算出来的依然是 ~31 核；此后随时间推移线性缓慢下降，必须等进入 GPU 阶段满 **600 秒（10 分钟）** 后，CPU 阶段的读数完全滑出窗口，账面核数才会真正降到 1～2 核。（在自测 `task-server/task_server_selftest.py:17697-17702` 的 `cell_cpu_gate_lease_taken_lets_cpu_task_start` 中，自测也是把时钟额外拨过整整一个 `window` 即 600 秒后，才测得账面核数降为 1 核。）

#### 问题 ②：起跑未满 600 秒就转入 GPU 的任务，在满 600 秒前退回「历史峰值段核数」，完全不释放
- `measured_running_cores` 第 10774 行的前置条件写了 `elapsed > CPU_RECENT_WINDOW_SECONDS and samples and now - samples[0][0] >= CPU_RECENT_WINDOW_SECONDS`。
- 如果一个按需领卡的任务（或分片的一片）CPU 阶段只跑了例如 180 秒（满核 31 核）就已经调用 `lease take` 转入 GPU 阶段：在 `elapsed` 从 180 秒走到 600 秒的这 **420 秒 GPU 运行期内**，第 10774 行条件不成立，代码直接落入第 10782 行的 `self.note_peak_segment(attempt, now, usage)`。
- 而 `note_peak_segment`（第 10788-10799 行）取的是 `max(cores, self.running_peak_cores.get(attempt_id, 0.0))`——即**这一次尝试开跑以来所有 120 秒段的最高峰值核数**（31 核）！这意味着只要总运行时长还没满 600 秒，即便早已转入 GPU 且物理只占 1 核，账面也一直按历史最高峰值 31 核记账。

#### 问题 ③：`card_taken` 一旦领过一次卡即永久为真，对多波次任务无「还卡回 CPU」与「再次领卡」的区分
- `card_taken`（`task-server/task_server.py:10816-10822`）定义为：
  `bool(lease["cards"]) or float(lease["held_seconds"] or 0) > 0 or lease["held_since"] is not None`。
- 一旦尝试领过一次卡并归还（`held_seconds > 0`），`card_taken` 在该次尝试剩余生命周期内永久为 `True`。
- 对于在一个尝试内经历多次「CPU → GPU → 还卡 → CPU → GPU」的任务（如 `gate.sh` 顺序跑多道门禁、`scripts/crash/crash-point-replay.sh` 跑三段、`crates-mutation-rows.py` 多格要卡变异交替编译），既不会在每次 `lease take` 时重置 CPU 采样起点，也不会在 `lease return` 后区分是否仍在持卡阶段。

## 四、 待决策修复清单汇总

| 序号 | 位置 | 问题简述 | 建议改法 |
