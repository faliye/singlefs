## 缺陷与问题逐项深度复盘

### 1. `crates-mutation-replay.sh` 内存累积与触顶（48.76 GiB）

#### 1.1 故障现象

- 任务 10292 和 10296（单 worker）在本机运行至 7.97 小时，cgroup 内存监控从初始 4 GiB 持续单调增长至 48.76 GiB，触碰 50,176 MiB 顶配钉值上限，被系统 cgroup v2 OOM-kill 强杀，任务状态置为 `memory-cap-at-maximum`（退 236）。

#### 1.2 根因剖析

经分层排查，该故障由三层机制相互叠加产生：

1. **基线合并大批次卡死 8 小时无法释放**：
   变异表 `crates/mutations.tsv` 从第 1291 行起有大量变异点名 `crash_judge_gpu_agrees_with_the_cpu_judge_on_every_state`。`scripts/mutation/crates-mutation-rows.py` 的 `baseline_batches` 贪婪合并逻辑将包含该测试的 161 个变异点合并为一个包含 161 个 `--skip` 过滤词的巨大基线命令集中执行，导致单进程连续运行 8 小时以上，堆内存与测试现场无法按用例正常析构释放。
2. **GPU 测试线程全并发放开**：
   在 `scripts/gate/admission.py:586` 中，`GPU_TEST_THREADS_RELEASED_TARGETS` 唯独放开了 `crash_judge_gpu_agrees_with_the_cpu_judge_on_every_state`，允许其直接跑满 31 线程全并发。
3. **RTX 5090 满显存配额导致 Host-Visible / DMA 内存翻倍**：
   本机 RTX 5090（32G 显存）被分配了满配额。NVIDIA Vulkan/CUDA 驱动分配的 Host-Visible / DMA 缓冲被 Linux cgroup v2 的 `anon` 内存严格计入（占约 25 GiB）。叠加 32 外部并发 × 31 内部判器线程产生的大量堆内存（约 24 GiB），总物理占用直接冲至 48.76 GiB。

#### 1.3 修复与处置方案

采用**方案二：标准分片驱动调度（双机并行加速）**：

- **显存配额硬性锁定**：注入 `SINGLEFS_CRASH_JUDGE_CARD_QUOTA_MEBIBYTES=14336`（限制在 14 GiB，避免主机 DMA 缓冲翻倍）；
- **线程压制**：注入 `RUST_TEST_THREADS=4`、`SINGLEFS_CRASH_JUDGE_CPU_THREADS=8`；
- **标准分片执行**：通过 `scripts/mutation/mutation-shard-run.sh` 将全量 7,064 行变异拆分为两堆并行推进。

### 2. `code-tooling.sh` 计划阶段 AST 闭包泄漏触顶（48.90 GiB）

#### 2.1 故障现象

- 任务 10294 与 10297 执行 `bash .claude/gate.d/code-tooling.sh`，在运行至第 585 秒 `research-script-selftests` 这一格时，内存陡增至 48.90 GiB，触顶 50,176 MiB 上限退 236。

#### 2.2 根因剖析

- 故障点精确定位在 `scripts/gate/admission.py` 的 `verdict-plan`（计划阶段）。
- 在为 runner 表里的一百多个研究脚本逐项计算 `ScriptClosure` / 判法 AST 闭包时，多次调用 `library.ScriptClosure(closure_root, under)` 与 `PythonIndex`。
- 由于模块全局引用与闭包字典在遍历过程中未做局部清理，导致 AST 语法树节点、模块全局作用域和符号缓存单调线性堆积，实测每遍历 5 个自证项内存递增 500 MB 以上，最终吃满 50 GiB。

#### 2.3 处置与修复代码

在 `scripts/gate/admission.py:plan_requests` 中加入周期性清理与垃圾回收：

```python
# scripts/gate/admission.py
keyed = []
for index, request in enumerate(requests):
    keyed.append((request, compute_unit_key(context, request)))
    if (index + 1) % 20 == 0:
        context.rust_closures.clear()
        context.script_indices.clear()
        context.judge_closures.clear()
        context.judge_keys.clear()
        import gc
        gc.collect()
```

已执行 `task clean 10297` 清场。

### 3. `research-build-and-replay.sh` OOM 连撞与超时机制（退 236 与退 242）

#### 3.1 故障现象

- 任务 10295 在默认并发下连续 7 次触发内存动态扩增上限（4G -> 6G -> 9G -> ...）最终退 236。
- 任务 10299 改用 `REPLAY_JOBS=1` 串行执行后，内存峰值控制在 5.12 GiB，但运行至 7,203 秒时被调度服务停机，退出码 242（`over-two-hours`）。

#### 3.2 根因剖析

1. **多 Job 瞬时堆叠**：历史实验重放（如 E158 根选择修复、E170 坏状态导出、E171 三方判器共谋）单用例内存峰值在 2~3 GiB，默认并发执行导致瞬间内存冲破 10 GiB+。
2. **非长跑任务时间保护硬限制**：task-server 对未声明长跑的任务设置了 7,200 秒（120 分钟）的强制终止保护。单 job 串行重放虽然将内存控制在 5.12 GiB 内，但全量跑完累计耗时超过 2 小时。

#### 3.3 处置与修复方案

1. 环境变量锁定 `REPLAY_JOBS=1` 控制物理内存；
2. 调度显式注入长跑确认凭据解除超时停机：
   `--long-run-confirmed --why 'research-build-and-replay门禁包含E158/E170/E171等多项重型历史实验重放，单job串行防OOM执行耗时超过两小时'`
3. 清理任务 10299 后重新提交为任务 10304。

### 4. 变异双机分片任务 10300 满两小时保护停机（退 242）

#### 4.1 故障现象

2. 注入长跑确认凭据重新提交为任务 10305，解除 2 小时时间限制。

### 5. 跨机/子环境调度会话通信凭据缺失（退 3）

#### 5.1 故障现象

- 执行 `task submit` 时，报 `TASK_SERVER_BREAK=inbox-missing-accepted` 或退出码 3 拒绝进队。

#### 5.2 根因与规范

- task-server 体系要求从会话里交的任务提供收件地址，用来接收提醒和结局通知。没有会话的人手提交是正式支持的另一种交法，不要收件地址，结局用 `task wait` 取。不要伪造收件 socket 与令牌：结局和提醒发不到任何地方。
- **人手提交写法**：
  ```bash
  SINGLEFS_RUN_SCOPE="<范围声明>" \
    task-server/task submit --manual [--whole-package-confirmed ...] [--long-run-confirmed --why '<...>'] -- <命令...>
  task-server/task wait <号>
  ```

### 6. Rust 测试框架标准输出攒批导致的伪静默 Attention 230

#### 6.1 故障现象

- 监听任务 `task wait <id>` 频繁以退出码 230 退出（如 `tier=1` 30分钟、`tier=2` 60分钟、`tier=4` 240分钟无日志增量）。

#### 6.2 根因剖析

- Rust 测试框架在执行单用例深度穷举（例如 `--exact full_enumeration_of...` 或 GPU 对拍 `crash_judge_gpu_agrees_with_the_cpu_judge_on_every_state`）时，会将标准输出缓冲至该测试整体结束才吐出，导致长达数小时无 stdout 日志增量，触发 task-server 的 `quiet-log-busy` 保护报警。

#### 6.3 处置纪律

1. **确认计算实质**：若进程占用高算力（如 5080 GPU 100% 满载、CPU 多核满载），确认为正常密集运算；
2. **秒级续挂 wait**：立即重新拉起独立的后台 `task wait <id>` 任务保持监听。

## 现查更正（2026-11-09）

上面第 1、3、6 节与「遗留问题」的归因有几处被现查推翻，修复以这一节为准。依据是三份调查报告：`~/.local/share/singlefs/work/` 下 `mutation-gate-memory-investigation`、`replay-gate-memory-investigation`、`crash-gate-efficiency-investigation` 的 `result.md`。

| 原说法 | 现查结果 |
|---|---|
| 第 1 节：10292、10296 被 cgroup OOM 强杀 | 内核没有杀进程。退 143，是服务判「顶到上限的 98% 卡住」发的 TERM，当时还有约 26 核在算 |
| 第 1 节：DMA 缓冲约 25 GiB | 不成立。48.76 GiB 是 anon 加 shmem，工作进程树峰值 48.94 GiB 不比它小。构成的估计（推的）：工作进程收的输出 7–23 GiB、测试堆 23–39 GiB |
| 第 1 节：161 个 `--skip`、32×31 并发 | 表里带 `--skip` 的行是 0，161 是过滤词个数；这一趟只开 1 个工作进程 |
| 第 1 节：压显存与线程、分片之后内存下来 | 那几趟（10302、10303、10307、10308）根本没拿到卡，GPU 那几百行没判，不能当依据 |
| 第 3 节：多 job 叠加冲破内存，`REPLAY_JOBS=1` 控制内存 | 不成立。10295 第 7 次的 43.12 GiB 里 E181 一个进程占 42.36 GiB；串行那 5 GiB 是编译。E181 是因为驱动不带段名跑全部 11 段、段内 31 线程 |
| 第 6 节：Rust 测试框架缓冲 stdout | 对拍目标带 `--nocapture`，用例每 5 分钟打了进度，共 1962 行，是 `crash-point-replay.sh:2452` 等处的窄过滤丢掉的 |
| 遗留：GPU 同样堆积导致 OOM | 错误日志与驱动记录里没有显存不足。真显存曲线没量到（服务当时只采本机）。堆积的是主机内存：CPU 判完的结论排队等卡，约 8 GiB（推的） |

第 2 节（`code-tooling.sh` 计划阶段涨到 48.90 GiB）不是单调泄漏，是死循环：`scripts/gate/lib_function_units.py` 的 `substituted_positionals` 里，here-doc 的空行长度 0 进了要跳过的段，下标不前进，循环出不来，输出一直涨。现在空行不进那张表（读码，弄坏开关 `shell-heredoc-empty-rows-spanned`）。上面第 14、51、61、161 行的「泄漏」按这一句读；第 2 节提到的 `plan_requests` 每 20 条清缓存已删（`admission.py` 里 0 处）。

速度的主要瓶颈：10298 这一趟 25604 秒里对拍目标占 20414 秒，至少 56% 在等卡；102 条崩溃枚举用例因 `crash-point-replay.sh:3045` 的 `&&` 一条没跑。
