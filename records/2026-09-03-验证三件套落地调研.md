## 一、问的是什么

`gate.sh` 每次都打印三条未实现阶段：模型对拍、崩溃点重放、QEMU 真实负载。
用户要的是「开始调研实现 checker / 事务层 / 崩溃点重放」。三样在仓里都是零代码
（现查：`crates/` 不存在、根 `Cargo.toml` 不存在，`research/` 下 90 多个二进制全是模型）。

调研先回答四个问题，再给一个落地顺序：

1. 每一样要消费哪些已定条款——逐条对到分项号，能对上的才算「可以照着写」。
2. 被哪些未定项挡着——[first-txn-layout.md](../.claude/kb/first-txn-layout.md) 里判「改字节：是」的四条，
   加上五处只定形态没定宽度的。
3. 仓里现成能抬走什么——E77 的枚举器与独立审计、E78 的四条恢复算法、E42 的前缀枚举、
   E85 / E88 的单元头与认领规则、E44 的 O_DIRECT 设备代码、变异表与复跑脚本。
4. 环境够不够——cargo 1.98、QEMU 8.2.2 + KVM、herd7 7.58 都在；
   宿主与虚机内核都带 `dm-log-writes` / `dm-flakey` 模块，但虚机 initramfs 现在不装模块。

答案全在 [verification-build.md](../.claude/kb/verification-build.md)。

## 三、三方对抗

对「推荐的落地顺序」与三样的第一版范围（背景材料 `research/prompts/_verification-build-background.md`，
16 条现查事实 + 6 条提案）发了三条腿，立场各不相同：

| 腿 | 立场 | 提示 | 输出 |
|---|---|---|---|
| 云端 Sonnet | 正推：只从已定事实推出三样各自的最小第一版与顺序，再与提案比 | `research/prompts/verification-build-forward-sonnet.md` | `research/prompts/verification-build-forward-sonnet-output.md` |
| 云端 Opus | 反推：假设提案是错的，找自证用例抓不到的具体失败 | `research/prompts/verification-build-reverse-opus.md` | `research/prompts/verification-build-reverse-opus-output.md` |
| 本地 Qwen | 找反例：构造能同时骗过三个判决器的坏实现 | `research/prompts/verification-build-local-counterexample.md` | `research/results/verification-build-local.out`（字词损坏闸判绿，退出码 0） |

判决写在 [verification-build.md](../.claude/kb/verification-build.md)「三方对抗」一节，摘要如下：

- **反推腿带回一个实测，主 agent 复跑后逐格相同**：跑 E77 原样，只摘根槽前的屏障（b_ur 臂）数据违例 0 / 79、
  记录洞 7；已定的两道屏障下关掉验证与不关都是 0 / 72。所以 C76 的两条自证用例按字面**不会红**——
  第一条只有记录核对器判得红，第二条要配一个改坏的点名单元。两处都改了（checks-owed 其四）。
- **I-7.3 在每一份刚 mkfs 的镜像上都红**：D22 已定项 8（2026-09-02）把第 0 代种进全部区域，
  而 I-7.3（2026-08-28）要求「除代号最大者外至少还有一条更早代号」。加了 mkfs 初始态的例外，
  并记下种子在被覆盖完之前会遮住轮换 bug（invariants.md 2026-09-03）。
- **层 0 的负载不能只是第一个事务**：本地腿与正推腿各自指出释放路径在第一个事务里不触发，
  反推腿指出 C42 要三次发布夹一次恢复、且基镜像要能预置残留记录。落地顺序照此改。
- **撕裂子集不必枚举**：三条腿对「有父指针的单元撕裂态并进未持久」一致；核对 D22 已定三与 D23 已定项 13 后，
  自证单元同样有整单元校验和，所以 D13 分项 4 的候选答案收窄成「只枚举整写子集，未持久位置取旧内容并真的生成镜像」。
  仍是推论，等用户定。
- **正推腿补了三处提案漏项**：O3 全然缺席、C77 / C29 不在自证表、超级块槽没排进解析器那一步。都补进了顺序表。
- **两处 kb 口径问题报给用户**（在对方正在改的文件里，没动）：journal 记录头 78 / 91 / 95 三处说法且 format-const 只登记了 3 个常量；
  五元组 33 字节没有分字段宽度。

## 三之二、共享边界与运行载体：当天晚些的第二轮三方对抗

用户说「按照实验定下来」之后，D13 分项 4 当场定案；接着把落地顺序第 0 步里剩下的两问
（checker 与实现允许共享什么、第一版的运行载体）也发了一轮三方对抗，背景材料
`research/prompts/_checker-sharing-vehicle-background.md`（12 条现查事实 + 2 条提案）。

| 腿 | 判定性产出 |
|---|---|
| 正推（云端 Sonnet） | 从 D13、D17 债表第 5 项与 C12 推出「常量在例外内、解析 / 校验和 / 遍历 / 记账禁止」，newtype 那格已定条款留空、提案取了更严的一边；补两条骑手：录制钩子要挂在块设备接口而不是操作 API（一次发布内部的中间崩溃点否则整个吞掉），库要落在 `crates/` 下才受 Show me test 管 |
| 反推（**Sonnet 代跑**，见下） | 现查本机内核 6.17 的 `block/bdev.c`：`sb_set_blocksize` 对大于 `PAGE_SIZE` 的块要求 `FS_LBS` 加 `CONFIG_TRANSPARENT_HUGEPAGE`，而单元 32768、节点 16384 都大于本机 4096 ⇒ 内核模块那条路要先付这笔账（主 agent 逐行复核原文）。另指出推迟内核模块的依据不该记成 D7（是否进 Linux 主线），因为那条只管往主线投不投 |
| 本地（找反例） | 三条反例里两条都落在同一处：kb 里写错的那个值（`JOURNAL_HDR` 78）让两边一起错而全绿；它同时指出手抄两份也抓不住这一条 |

⚠️ **反推腿是替代腿**：原定的 Opus 连续三次被服务端过载打断、一个字都没写出来，
按 `.claude/rules/three-way-inference.md`「缺席必须显式报告」记在这里与决策变更史（其十二）。
换 Sonnet 补跑，输出文件名带 `substitute` 字样。

**判决**：两条都定了（D13 已定项 5、D17 已定项 5，变更史其十二）。三腿一致指向的那个盲区
——共享一份生成常量抓不住「kb 里就写错的值」，而手抄两份同样抓不住——**不是共享造成的**，
所以不改共享规则，另立 **C94（登记的格式常量与后来的定案对不上）**：门禁要比对登记值与同一份正文里
那些已定增量之和，并要求 first-txn-layout 表里每个已定宽度都有登记标记（现在全仓只登记了 3 个）。
