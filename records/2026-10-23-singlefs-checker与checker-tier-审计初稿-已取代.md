## 结论

**当前 checker 存在可以让损坏镜像零违例通过的漏检，不能仅凭测试全绿、CPU/GPU 对拍一致、Verus 通过就认定恢复验证闭环成立。**

最直接的反例是：从真实 mkfs、暖机、文件发布形成的镜像出发，把 txg=1 根的树表指针出生 txg 改为 999，重封根槽校验和，并同步 journal 的新根段和反向链。池级 `check_pool_image` 返回：

```text
CONFIRMED end-to-end 1 txg1 root pointers claim birth=999; I-1.2=Holds; all violated=[]
```

这不是单纯的代码风格疑点，也不是通过破坏校验和绕开解析的测试。损坏的是指针与被引用单元的身份关系，checker 应当检查它，却因为跨根复用访问缓存而跳过。

## F01：访问缓存跳过了“新引用”必须重新检查的约束

**位置：** [walk.rs:1985](../crates/singlefs-checker/src/walk.rs) 的 `read_index_node`，关键早退在约 2016 行；出生身份检查随后才发生，树 ID 检查在约 2050 行。跨根复用同一个 Walk 的调用位于约 18295、18428 行。

`read_index_node` 读回单元、验证位置条目后，先把物理落点插入 `visited_units`。已经访问过就直接返回 `WalkedByAnEarlierVersion`，不会再执行：

- 当前指针的出生 txg、实例、尾段与单元头是否相符；
- 当前调用者要求的树 ID 与单元头是否相符；
- 当前树的 schema/key 解释等后续检查。

复用单元的内容可以缓存，但“指针 A 指向这个单元是否合法”和“指针 B 指向这个单元是否合法”是两个检查。A 合法不推出 B 合法。现在缓存键仅是落点，无法为 B 的指针字段、预期树和父节点约束作保。

### 完整镜像反例

公开探针调用既有 `common::build_pool`，先确认原镜像没有违例；再修改 txg=1 根里的树表指针出生 txg 为 999，根槽重新计算 CRC，并调用既有辅助函数把改后的根同步进对应 journal 新根段、修复反向链。

该镜像保留更早的根，它们也引用相同的树表节点。节点从其他根先被访问，损坏引用再走到它时触发缓存早退。结果 `I-1.2=Holds`，全部不变量的 `Violated` 列表为空。

局部对照还验证了两种情况：

```text
缓存命中：I-1.2 违例数 0；全新 Walk：违例数 1。
缓存命中：I-1.3 违例数 0；全新 Walk：违例数 1。
```

第二种把同一节点的预期树 ID 从 7 改成 8。它证明同一个早退位置不只影响一个字段。完整镜像反例针对出生身份；未另外构造树 ID 情况的完整镜像。

**影响：** checker 对所有候选根的验证存在次序依赖；扫描重建等后续检查在本次完整镜像上没有补住。即使 GPU 完全跟随 CPU 这个行为，两路一致也只是共同漏检。

**建议：** 缓存“节点字节及解析结果”和“已经展开的后代集合”，每次跟随引用仍执行身份、预期树、schema、父子层级/区间等引用相关检查。失败节点与成功展开节点也应有不同缓存状态。

**验收：** 保留本报告完整镜像反例，要求 `I-1.2` 报红；同节点多指针、多根、快照共享、父层级不同、schema 不同分别验证。改变根遍历顺序不能改变是否发现相同损坏。

## F02：journal 扫描的保留规则与恢复不一致

**位置：** [walk.rs:9584](../crates/singlefs-checker/src/walk.rs) 的 `scanned_journal_records_of_device`，约 9603 行 `records.insert(record.counter, ...)`；随后约 9696 行 `records_as_the_recovery_reads_them` 才构造 `(instance, counter)` 键。

**恢复对照：** `crates/singlefs-core/src/recovery.rs:4943` 的 `scan_journal`，调用经过形式化验证的 `first_copy_of_each_record_key`，按 `(instance, counter)` **先到保留**。

checker 在逐盘扫描阶段使用 `BTreeMap<u64, ...>`，同一 counter 的后一个记录会覆盖前一个。之后再加实例号已无法恢复被覆盖的数据。

反例在同一盘两个环槽放置都能通过自证和字段解析的记录：相同实例、相同 counter=1，分别携带 txg=10 和 txg=20。它们不是正常写者应产生的布局，但属于坏盘/错误写者审计必须有明确行为的输入。

```text
checker 逐盘扫描：保留 txg=20。
实际 core::scan_journal：保留 txg=10。
```

同一 counter、不同实例的变体还会在 checker 逐盘阶段丢掉一条记录，而 core 可以保留两条。既有“两块盘同 counter 不同实例”的单测只覆盖跨盘拼表，不能覆盖同一盘预先覆盖的问题。

**影响：** checker 用来判断恢复前缀、反向链和发布规则的记录集合，可能不是恢复实际使用的集合；被覆盖的坏记录也可能逃掉逐记录检查。这里没有证明正常合法流一定能产生该冲突，也不把错误布局当作合法格式。

**建议：** 分开保存“所有自证记录及物理位置”和“恢复实际采用的记录视图”。前者用于格式和冲突检查，后者独立实现 `(instance,counter)` 先到保留。对记录物理槽与 counter 的对应关系做显式判定，避免只在注释里假定它成立。

**验收：** 同盘重复键、同盘不同实例、跨盘冲突副本、候选顺序变化都做成校验和自洽的用例；checker 预测的前缀与实际 core 恢复使用的记录逐条相同。

## F03：txg 高 32 位在对拍与持久结论里被抹掉

**位置：** [crash_judge_conclusions.rs:367](../crates/singlefs-checker-tier/src/crash_judge_conclusions.rs) 的 `LandedRootWords`、381 行 `landed_root_words_of`、68 行恢复字编码、85 行 `recovery_passes_differ`。GPU 输出对应在 `crash_judge_recovery.wgsl:1533` 附近，只写 `effective_txg.x`。

恢复的 `CheckpointTxg` 是 u64，但结论只记录 `checkpoint_txg_low: u32`。公开探针构造两份合法类型的报告：

```text
实例 1，txg = 7
实例 1，txg = 4294967303 = 2^32 + 7
```

保持其他字段相同后，两份 `CrossCheckWords` 完全相等，`recovery_passes_differ` 返回 false。

**影响：** 不同恢复版本可以被对拍认作相同；`journal_differing_states` 会漏记对应差异；缓存恢复字无法还原完整版本。给定状态判器 trait 的默认兼容入口也按低 32 位检查显式声明版本（`crash_given_states.rs:269` 附近），具有相同别名问题。

这是合法 u64 域内的信息损失，不需要真的顺序执行 2^32 次发布才能测试；边界构造即可验证。当前小 txg 流通常碰不到它，不代表格式保证覆盖正确。

**建议：** 根身份显式保存 `has_root`、实例号、txg 高低两字；恢复字、GPU 输出、缓存格式、比较函数一起更新。区分“没有根”和数值哨兵，不继续依赖全 1 的组合。

**验收：** 至少覆盖 `2^32-1`、`2^32`、`2^32+7` 和高位不同低位相同的两个根；要求比较不等、差异计数增加、缓存往返完整保留 u64。

## F04：撕裂态的旧字节与当前持久集合无关，漏掉可达状态

**位置：** [crash.rs:2347](../crates/singlefs-checker-tier/src/crash.rs) 的 `WritesWithTornImages::of`。约 2371 行先把这次写之前的所有写完整施加到 `image_before_the_write`，再固定生成这一写的唯一撕裂镜像。生成函数在 2309 行。

同一段允许每次写分别选择未持久、撕裂、完全持久。但撕裂字节按“此前全部写都持久”的历史预先计算。这两种假设在同段重叠覆写时不相容。

### 九态反例

使用一个 4096 字节范围：

```text
基线：全部 0x11
W0：同一范围写全部 0x22
W1：同一范围写全部 0x33
W0、W1 位于同一段，都可撕裂。
```

按扇区原子性，一种明确可达的结果是：W0 没有持久，W1 前四个扇区持久，后四个扇区保留基线：

```text
0x33 × 2048 | 0x11 × 2048
```

探针通过实际 `crash_state_enumeration_tables`、`extract_flow_facts` 和 `CrashImage` 枚举全部九态，**没有一个状态得到上述字节**。W1 的预制撕裂像后半段固定为 0x22；甚至在 W0 的原写及撕裂写均未选择时，也携带来自 W0 的 0x22。

这说明九态闭式和 CPU/GPU 拆编号都相同，并不证明枚举到的镜像覆盖物理状态。两路共享了同一份旧字节模型，会共同漏掉它。

### 撕裂粒度也需要明确

`torn_image_of_in_place_overwrite` 在“第一个不同字节至最后一个不同字节”的中点切开，不向 512 字节扇区对齐。探针让新旧只在同一扇区的偏移 10 和 20 有差异，生成结果同时不是该扇区的完整新值或完整旧值。这与既有测试文档中的“崩溃点重放撕裂粒度就是扇区”不一致。

如果第三态只是代表“新旧都不能通过校验”的抽象值，非物理字节本身未必造成结论不健全；但必须证明这个代表对全部判器观察等价。当前代码还处理 discard、范围清零、逐扇区缺席检查，不能仅凭整槽校验和通常拒绝损坏就外推全部观察等价。

**影响与边界：** 已确认通用枚举器对上述输入漏掉字节状态；尚未证明当前所有登记的真实文件系统流中，哪一条一定会形成这个同段重叠覆写。报告不把这个合成反例说成已复现业务恢复失败。

**建议：** 在小范围内建立独立的逐扇区持久模型，对每个状态按实际已持久前写生成旧字节；或者明确限定输入域并在入口拒绝同段重叠覆写。若保留三态抽象，需要给出对恢复、记录核对器、checker 全部观察的等价性条件。

**验收：** 本反例的物理状态必须被表示，或被有证明的等价类覆盖；至少加入同段两次覆写、覆写与 discard、部分范围重叠、两次均撕裂的比较。态数公式核对不能替代镜像集合核对。

## F05：缓存往返后的结论不再是原来的 CrossCheckWords

**位置：** [crash_judge_conclusions.rs:1066](../crates/singlefs-checker-tier/src/crash_judge_conclusions.rs) 的 `cross_check_words_of_a_stored_given_state`，约 1120 行把 `pool_checker_judged_bits` 固定为 0，把 `scan_rebuild_outcome` 固定为 NOT_REACHED。实际读取路径在 `crash_amplification.rs:15502` 附近。

公开探针让 I-1.13 成立，先得到对拍字，再按实际红项和恢复字存储表示还原：

```text
判到位：4951760157141521099596496896（1 << 92） → 0
扫描重建结局：0（成立） → 4294967295（NOT_REACHED）
```

红项和根身份低位保持一致，但还原后的逐状态结论不等于现判的逐状态结论。若对同一状态比较完整对拍字，会得到依赖缓存命中的不一致；若再从还原出的状态重算覆盖计数，会把原来已判断的状态算作没判断。

**需要准确区分：** 当前引擎还另存块级 `count_vector`，读取时也把它返回。因此本反例没有证明现有顶层块汇总必然计错。问题在于返回的统一 `CrossCheckWords` 类型已经丢失逐状态语义，块级总数也无法恢复每个状态的具体判到位和理由。已有注释承认了这种有损还原，仍应在接口上约束它的用途。

**建议：** 保存逐状态判到位与扫描重建结局；或者返回独立的“缓存摘要”类型，让无法恢复的字段成为显式未知值，禁止拿它直接做完整逐状态对拍和重计数。

**验收：** 对 Holds、Violated、NotApplicable、PartiallyJudged 和各扫描重建理由做现判→存储→还原测试；完整类型要求字段相等，摘要类型则必须显式拒绝完整比较/重计数。

## F06：不同恢复不变量失败在对拍中被合并

**位置：** [crash_judge_conclusions.rs:295](../crates/singlefs-checker-tier/src/crash_judge_conclusions.rs) 的 `gpu_failure_point_code`，以及约 397 行 `outcome_and_failure_point_of`。

目前失败点按 `RecoveryFailure` 的 enum 成员编码，不保留其中的不变量名或稳定的语义子原因。例如：

```text
InvariantViolated { invariant: "I-1.2", ... }
InvariantViolated { invariant: "I-1.3", ... }
```

两者都得到同一个 `GPU_FAILURE_POINT_INVARIANT_VIOLATED`。公开探针已断言两码相同。`UnitMalformed` 的不同失败环节、`UnitUnreadable` 的不同槽等也会被合并。

**影响：** 两个实现如果在不同检查处拒绝同一输入，仍可能被判定恢复失败点相同。池级 checker 位图检查的是镜像上的不变量，不是各恢复实现究竟执行了哪个拒绝条件，不能保证自动补齐这个信息损失。

这不表示凡是“同类错误”都必须逐字比较诊断文本；但至少 I-1.2 与 I-1.3 这种不同语义拒绝不能因为共用 enum 成员而被宣称是相同失败点。

**建议：** 编码稳定的拒绝原因标识：不变量编号、解析阶段和必要的对象标识；将易变的人类诊断文本留在比较外。明确对拍契约究竟要求“成功/失败相同”还是“语义拒绝位置相同”。

**验收：** 不同不变量的两个失败必须比较不等；同一语义失败仅诊断措辞变化应保持相等。

## G01：给定状态表没有内容 oracle，不能独立证明恢复内容正确

**位置：** `crash_given_states.rs:341` 的 `judge_a_given_state_on_the_cpu`；结论构造在 `crash_judge_conclusions.rs:971`。GPU 给定状态路径在 `crash_amplification.rs:15620` 附近，期望版本表为空，之后去掉 oracle 位。

该路径运行两遍恢复、池级 checker 和记录核对器，但不提供期望内容版本表。`CrossCheckWords` 也没有读回内容或内容摘要。

公开探针让根身份相同、两次都报 `FileRead`，读回内容分别为 `[1]` 和 `[99]`；给定状态的对拍字完全相同。

**边界：** 有版本表的普通崩溃枚举另有内容 oracle，其他调用者也可能另外检查内容。因此不能据此声称所有恢复测试都不检查内容。能确认的是：给定状态判定组件本身，以及仅比较它返回字的对拍，不足以排除静默错读。

建议给表增加独立生成的期望文件视图/允许集合，至少输出完整内容摘要和文件身份；把“结构一致”“两路内容一致”“内容属于允许版本”分成三项验证。仅新增两路内容摘要对比仍不足以排除两路共同读错。

## G02：形式化证明通过，但没有覆盖整个恢复链路

本次核实了实际运行，不是只相信登记表：整个形式化核 **78 verified、0 errors**。未发现据此可直接认定的证明失败或 `admit` 绕过。问题是证明结论必须按它的输入、前提和状态模型解释。

### 取前缀核接入了产品，但其外侧仍是可信边界

`singlefs-replay-prefix/src/lib.rs:3547` 的 `replay_core` 确实被 `core/recovery.rs:5199` 调用。core 在约 5143 行通过运行时断言检查键序与计数器的两项前提；这一点是有落实的，不应说成全部前提无人检查。

但原始字节解析、系统配置选择、候选根过滤、读盘回调、点名单元验证、NewRootSource 到新根九字段的拼接、实际树遍历和可写挂载写盘不在这次核证明内部。F01 和 F02 正好发生在这类边界附近，所以核全绿并不与反例矛盾。

### 幂等证明的状态比磁盘状态窄

约 787 行的记录级幂等与 848 行的不动点性质主要描述 `RootSource` 和 applied 记录集合；不动点还以前提约束 txg 顺序、读者回答稳定、候选不超在飞上限。它不等于证明可写挂载写出的系统配置轮换、实例表、释放记录、删除续作等磁盘副作用重跑后逐字节不变。

应分别验：纯函数前缀不动点、只读恢复输出不动点、可写挂载的磁盘状态不动点/观察等价；第三项还应在第一次恢复写入中再崩溃，然后重启验证。

### 单调推论依赖关键写侧前提

约 2845 行 `corollary_the_landed_version_does_not_go_back` 的 requires 已要求：较大状态选根不早于较小状态；较小状态施加过记录时，较大状态选根至少覆盖其落点，或者两次核输入完全相同。证明核没有从扇区持久集合包含关系自动推出这些写侧事实。

因此它证明的是“这些前提成立时，核结果不后退”，不是“所有更大持久集合上的完整恢复必然不后退”。建议为前提建立独立可执行检查和小世界枚举，覆盖 FUA、屏障、根槽覆盖、回退、掉盘与读故障；对不适用的故障模型明确排除。

### 整理核没有直接成为产品实现

`singlefs-replay-prefix/src/compaction_plan_proofs.rs` 的选段与计划核，产品 `singlefs-core::compaction_plan` 不直接调用；当前通过该模块 cfg(test) 下的转换和小输入对拍连接。这个边界源码已经写明。需要继续防止把“抽取核证明通过”写成“产品选段、搬迁发布、目的地分配及崩溃恢复已端到端证明”。

建议逐项维护“性质—模型—前提—产品入口—胶水验证—反例”的映射，并对实际胶水新增字段/分支实施变化检查。证明条数相同不保证仍证明了同样的工程性质。

## G03：GPU 判表与被测实现共享了校验计算

**位置：** `crash_judge_tables.rs:17` 引用 `singlefs_core::checksum::{crc32_castagnoli, wide_checksum_field_holds}`；约 1355 行 `version_checks` 把系统配置、根、journal、单元的 CRC 和校验成立位计算后放入判表。该文件还引用 core 的环位置计算等函数。

CPU 池级 checker 自写 CRC 和解析，与 core 的 crate 依赖隔离是真实存在的。但 GPU 判器不是对所有输入字节都独立计算一遍校验：它消费了录入段用 core 算好的部分事实。

**风险：** 被测实现的校验计算和 GPU 输入预处理可能同源犯错；只看 GPU 恢复与 core 一致，不能排除这类失误。完整独立 CPU checker 对拍可以帮助发现它，但必须确认实际跑了、输入没有在共同预处理阶段被丢掉、结论也没有被压缩掉差异。

这是架构上的共因边界，不是本次发现 CRC 算错，也不是说全部 CPU/GPU 对拍失效。建议判表校验事实用 checker 的独立实现生成，或分别保留两份校验结果并核对；保留独立原始字节参考路径，针对坏长度、校验覆盖范围、错误指针及重复 journal 记录做变异测试。

## G04：复用豁免不能证明“这次复用合法”

**位置：** `crash.rs:284` 的 `reuse_is_not_proven_illegal_by_the_reclaim_predicate`，调用位于约 223 行的逐扇区缺席判断。

它不读取实际释放记录和真实释放代，而使用“原发布 txg+1”作释放代下界，使用全部前写中的最大 F、环内根的界作宽松判据。源码已明确说明：它只在证得出不合法时拒绝，实际释放代更晚等情况可能漏过；跨崩溃接缝后，原历史没有发生的后缀还可能进入这个宽松界。

因此变量 `explained_by_a_persisted_legal_later_write` 的“legal”强于它真正证明的内容。实际语义更接近“有后写，且这个粗界没有证明它非法”。

报告不把这项已登记的近似假装成新发现，也没有额外复现一个穿过全部其他判器的非法复用。需要控制的是信任范围：记录核对器通过不等于回收谓词完整成立。

建议在选定的小世界和可疑状态上增加独立精确参考：从发生过且持久的历史、真实分配/释放记录和有效时间线计算合法复用集合；与宽松判据对照，记录每次豁免的原因和使用的界。精确参考不应继续复用同一近似函数。

1. **先修 F01。** 已有完整镜像零违例反例，直接影响 checker 作为独立裁判的可靠性。把引用检查从展开缓存中拆出，固定当前反例及跨根次序对照。
