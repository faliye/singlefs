# 崩溃判器与测试流的效率优化：项目、过程与读数

这份记录只管效率优化这一条线：量到了什么、哪些说法撤回过、做了哪些改法、各自验到哪、还开着什么。调度上的来往（派了谁、任务号、哪一批）在 `records/2026-11-13-全量提交门禁前收尾调度.md` 里，这里只在要出处的地方引任务号与报告路径。数一律标来源；写「推的」的没量过。

## 一、起因与用户定案

起因：崩溃放量加崩溃枚举用例每次提交要判一百亿态以上，慢流在卡上每秒只判一千多态；一次合入后验证里对拍目标跑了四小时没完。

用户定案（原话，按先后）：

- 「你应该优先优化，和尽快优化」「然后告知我优化后的影响」。
- 「你不能为了优化测一个数据跑4个小时。全量的验证在这里没有什么意义」——此后量法一律取小样本：不超过一块 65536 态，或缩过域，或只录不判。
- 「你最好还是不要推 我认为这是需要核实的」。
- 「所有的流都要把日志加上」「都要进行审查和优化」「0.05也要优化」「几百亿状态下的 0.05 还是比较长的时间」。
- 「等卡的这个问题，目前看起来除非能增加卡，不然没法解决。这个以后就不要提了，因此还是要从 cpu调度和算法上优化」。
- 「我们目前测试这部分不是几次，是千万次亿词，哪怕是1毫秒在这种量级累加出来效果都很惊人。更不要说一个算法优化了。比如更快的读取和写入rocksdb」。
- 任务服务的 CPU 闸（32 核的台负载上限 110）要不要动：「先量再定」。
- 「积压交替验证 是一个比较好的方法。这样我们一张卡可以让多个任务使用」「要考虑反向拿任务 就是 gpu自己领任务 或者判定器自己分发任务」「比如有五张卡 五张卡 每张卡能读多少batchsize。当cpu算到一定的数量 就分批次发给各个gpu 这样， 脉冲进行」「等于是无状态的服务。 这样效率应该就起来了」「这和 gc 差不多是一个道理 一个水位线，然后发一波任务」「还有坚持最开始那个策略， cpu和gpu要隔离。cpu数据装入rocksdb gpu server从rocksdb中读出来。如果这个策略非常消耗时间，我考虑redis。因为我们本来就有redis」。
- 「要详细记录优化的项目和过程 这部分很有意义」。

### 3.7 内核改过之后第一次上卡建管线（`~/.local/share/singlefs/work/batch38-pipeline-build-time/`）

现象：带改过的内核的任务停在 `phase=judge_resources_begin` 十分钟上下，卡利用率 0%，CPU 一到三核。

四条只建管线、不判的量法（5090，驱动 `NVIDIA 595.99.02`，本机空着时量）：

| 情形 | 11 条管线合计挂钟 |
|---|---|
| 驱动缓存全空、五组并行（18440） | 182.6 秒 |
| 驱动缓存全空、十一条线程（18443） | 180.5 秒 |
| 只有走读内核变（18442） | 157.8 秒 |
| 缓存全命中（18441） | 1.9 秒 |

冷编时逐条：走读 182.5 秒（展开后 370463 个表达式）、恢复 90.6 秒（288999）、分配代扫描 70.8 秒（277387）、引用与快照 41.0 秒（191118）、扫描重建 12.9 秒（69417），其余不到 9 秒。

读法：

- 时间花在驱动把着色器编成机器码；缓存命中就不付。缓存在每台的 `$HOME/.cache/singlefs/singlefs-gpu-shader-cache/GLCache`，不在共享根，按卡分区。
- 整趟挂钟等于走读一条的用时，多开线程不省；用时随表达式数涨得比线性快。
- 驱动缓存按每条管线各自的内容认，改哪个内核只冷编哪个。
- 本机负载一百上下时同一步是 600 秒上下：调查员采样一条编译线程，在 CPU 上跑 122.3 秒、在就绪队列里等 272.7 秒。任务服务的 CPU 闸让 32 核的台负载到 110（`task-server/task_server.py:994`）。
- 走读内核的表达式数离钉的上限 400000 只剩 3 万左右。

## 四、撤回与更正过的说法

| 说过的 | 实际 | 怎么发现的 |
|---|---|---|
| 慢流约 4600 态每秒 | 60 态每秒（那时每批 128 态） | 记账行是每 128 态一行，数行数算错了 |
| 「走读占六成」 | 慢流上走读只占等卡时间的 0.137，最大的是记账分片与分配代扫描 | 按总等卡时间重算；之前只比每次提交的秒数，没乘次数 |
| 「跨候选根按记录去重」能省 11–23 倍 | 内核里单元与 I-3.10 已经在一个态的各候选根之间只判一次；拿掉整个记录循环只省 0.05 秒 | 实现员读内核（`crash_judge_checker.wgsl:5638`、`crash_judge_checker_scan.wgsl:1492`），变体量法核了 |
| 「110 个在途写里 102 个落在环版本单元的槽上」 | 比的版本集合含被录的那四次发布自己，对每条单元写恒真；量得出的是 102 条里 90 条落在起点镜像已写过的槽上 | 算法审核复核探针的比法 |
| 对拍四小时跑不完是因为「一个函数里循环 32 条流」 | 32 条流本来是 32 条独立用例；原因是合入后验证没把崩溃域上限交给对拍读的那个变量，每条流在全量域上判 900 万到 1300 万态 | 实现员核日志与源码 |
| 「16G 卡约 540 态每秒」 | 没有出处：出自一条被取消的任务的进度行 | 速度表的事务员在日志里找不到 |
| 走读记录循环那份补丁省「约 5%」、不重读 inode 树那份省「约两成」（第一次说） | 那次拿的是另一段块的旧读数，不是同块同卡；后来用同卡同块同宽度的三条互为对照重新得出 2%–3% 与约两成 | 改前对照落在另一张卡上，才发现不可比 |
| CPU 一侧四份补丁「不换判器组键」 | 91 组里换了 56 组 | 编键表比出来的；实现员是照入口表读的，没编 |

## 五、做过的改法与现状

### 5.1 合入后验证把崩溃域上限同时交给对拍目标

`scripts/gate/merge-and-verify.sh`：缩域时 `SINGLEFS_CRASH_AMPLIFICATION_EXPAND_UP_TO` 与 `SINGLEFS_CRASH_JUDGE_EXPAND_UP_TO` 一起往下传。自证过（18385，查了 121 种），新弄坏开关红在点名的 11 行。崩溃点重放入口 `scripts/crash/crash-point-replay.sh` 同形改了，改到的两格自证过。合入后验证整趟要多久还没重量。

### 5.2 每条流每一趟的用时汇总行

- GPU 判器：行首 `CRASH_AMPLIFICATION_GPU_PASS`，每张卡每趟一行（提交次数、等卡秒数之和、最长一次、每次提交态数的中位数、占比）。补丁在 `~/.local/share/singlefs/work/batch35-per-pass-summary-line/patch/`。测试 209 条过，证红 5 行全抓。换两组判器键（GPU 判器、观察者结论拼块）。
- 分项驱动与两台分片驱动把这种行转打进任务日志：改在主工作区，自证都过。
- 还没罩到：给定状态表、观察者交回的盘、排计划的试判、对拍那两个函数的派活。

### 5.3 GPU 判器内核三处（`~/.local/share/singlefs/work/batch35-judge-pass-optimization/`）

| 补丁 | 做了什么 | 量到的（同卡同块同宽度互为对照，5060 Ti、每次提交 1602 态） |
|---|---|---|
| 同一版不重读 inode 树 | 墓碑与谱系那一遍里同一条根指针读全过就不再重读 | 分配代扫描 0.9066→0.7227（约两成） |
| 走读记录循环少读 | 不回头读前一条记录的号、出生代只读一次、保留字节按字读 | 走读 0.3290→0.3177（2%–3%） |
| 记账分片接着做 | 后面的片不整轮重算权重 | 5080 上整块 622→629 态每秒，这一趟每次 0.0638→0.0618 秒 |
| 三份合起来 | — | 整块 458→491 态每秒（458 已含走读那一份） |

写段检查：新用例（三种记账分片切法下结论字逐字相同、与 CPU 逐态相同）过，clippy、build 过，证红 4 行全抓。展开钉值要跟着改。弱处：没有「被优化掉的那部分起作用时照样判红」的用例；不重读那份的缓存键改错在这条流上测不出。

### 5.4 CPU 一侧与判定库读写（`~/.local/share/singlefs/work/batch37-cpu-side-and-library-io-2/`）

| 补丁 | 做了什么 |
|---|---|
| 解结论字挪出卡线程 | 卡线程只留找判不了的状态那一遍，结论字交写库线程解 |
| 判定库读写 | 镜像判定存一块新块的往返 5 次降到 2 次；去两处整块拷贝；观察者判段的读合批、不再读回刚存的那一份 |
| 几个观察者只恢复一次 | 录入段按块走，一个态恢复一次交给各观察者 |
| 叠加表增量 | 改动表分前缀与自己那一截、相邻态共用前缀；见证摘要没做增量（它是当键存库的 SHA-256） |

写段检查：编译、clippy、测试（不带 gpu 特性 230 条、带 244 条）、证红 11 行全过。量到的：观察者录入一块 65536 态，改后 2.2 秒（18457，第 36002 块）；可比的改前只有带计时探针的那一次 5.13 秒（第 35000 块）——约 2.3 倍，不是同块同条件。

卡住的两件：

- 换了 56 组判器组键（观察者代码 52 组、镜像判定、给定状态、观察者结论拼块、CPU 事实核对各 1 组）。照现在合进去，判定要重判、观察者要重录。正在查是哪几个函数单元带进去的、能不能挪出闭包。
- 三处行为变了，要过代码轮：存块那一刻没有一步拦并发写；判段不再读回；多线程下同一把键库里记哪个代表态随调度变（判定不变而存的字节不定）。

## 八、这一轮量法上守的几条

- 一条量法不超过一块 65536 态；能只录不判、只建管线不判的就不上判定。
- 变体内核只取用时，判定不当数；它的键与产品不同，不盖产品的判定。
- 同一块在同一把键下判过一遍就进库，第二趟整块复用、量不到：改前改后要么取没判过的块，要么让键不同。
- 比两个读数先核是不是同一张卡、同一宽度、同一块；不是的写明，不拿来算百分比。
- 性能实验在本机跑的时候不往本机交别的活（E152 那一次第 1 轮有三次虚机被本机的编译搅了）。
- 「不换判器组键」这类话要编键表核，不照入口表读。
- 实现员的补丁点名测试时，把 `crash_identity::` 里判器闭包那几条一并点上：四份 CPU 一侧补丁的两趟测试只点了改到的两个模块，那条在补丁树上是红的测试没跑到。
