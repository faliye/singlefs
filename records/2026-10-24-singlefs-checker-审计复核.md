## C01：缓存命中错误地免除了新引用的检查

位置：[walk.rs:1985](../crates/singlefs-checker/src/walk.rs) 的 `read_index_node`，关键顺序在约 2016 行：先按落点查询 `visited_units` 并早退，随后才检查当前指针的出生身份、预期树 ID。跨候选根复用 Walk 的调用在约 18424 行。

同一节点的解析结果和后代展开可以复用，但一条新指针的出生字段、调用者预期的树 ID 仍需检查。节点先被合法引用，不能证明后来的另一条引用也合法。

### 排除了哪些反解释

| 可能的反解释 | 本轮对照 |
| --- | --- |
| 改坏的根低于回退下界、根本没有进入检查范围 | 记录实际候选集，包含 `(实例1, txg1)`；另记录坏指针实际执行到了读节点处 |
| 指针和单元本来就相符，字段偏移写错了 | 独立解析指针和被指节点：原出生 txg=0，单元出生 txg=0，改后指针出生 txg=999 |
| 只是根校验和失效，检查被提前挡住 | 重封校验和并断言根解析成功；journal 新根段和反向链同步重封 |
| 只有私有函数的人工调用才会触发 | 使用既有 mkfs→暖机→文件发布夹具，运行公开池级入口 `check_pool_image` |
| 不加缓存时也不应该报这个字段 | 全新 Walk 的局部对照能报红；只在临时副本补检查后，同一完整镜像恰好报 `I-1.2` |
| 对照修改把所有镜像都判红 | 原镜像及恢复输入在三轮中都为零违例 |
| 测到的是同一根里不合法的重复引用，而不是跨版本共享 | 局部用例显式调用 `begin_walking_a_version` 后再引用；完整镜像来自候选根间共享树表 |

### 完整镜像实测

```text
candidate_roots=[(0,0),(1,3),(1,1),(1,2)]
root_txg=1 original_pointer_birth=0 actual_node_birth=0 mutated_pointer_birth=999
pointer_birth=999 cache_hit=true
```

| 运行 | 损坏镜像 I-1.2 | 损坏镜像全部违例 | 合法原镜像 |
| --- | --- | --- | --- |
| 原版第一轮 | Holds | 空 | 空 |
| 临时补引用检查 | Violated | 仅 I-1.2 | 空 |
| 再次原版 | Holds | 空 | 空 |

局部树 ID 对照也一致：同一个树 ID=7 的节点，被新版本按树 ID=8 引用时，原版缓存命中违例数 0，全新 Walk 违例数 1；临时补检查后缓存命中也为 1。

**确认范围：** 完整镜像零违例反例对应出生 txg；树 ID 对应局部函数对照，没有另称它也已得到完整镜像零违例反例。其他 schema、层级等约束存在相似早退边界，但本轮未逐一复现，不能直接计作新增缺陷。

### 修复建议与验收

把缓存分为“节点内容/解析缓存”和“后代展开缓存”。每条引用仍检查指针身份、预期树及父子关系。缓存成功解析和失败解析的状态应分开。

最少验收应保留上述三组控制：合法镜像、坏引用、恢复输入；增加候选根顺序与快照共享的变化。不能仅凭新的缓存命中次数或某一个不变量被额外评估，认定修复完成。

## C02：journal 扫描的键与冲突选择不匹配实际恢复

位置：[walk.rs:9584](../crates/singlefs-checker/src/walk.rs) 的 `scanned_journal_records_of_device`，约 9603 行按 `counter` 使用 `insert`；后到记录覆盖先到记录。`records_as_the_recovery_reads_them` 稍后才加入实例号，已无法恢复被覆盖的内容。

实际恢复位置：[recovery.rs:4943](../crates/singlefs-core/src/recovery.rs) 的 `scan_journal`，按 `(instance,counter)` 先到保留；选择核 `first_copy_of_each_record_key` 已接入形式化证明。

### 本轮采用的相同输入

从真实池取得已解析的系统配置与几何，保留原系统配置，在各盘清空 journal 环，再在盘 0 的两个实际环槽写入冲突记录。两条记录都先经 checker 和 core 的记录解析器断言接受。checker 与 core 接收的是**同一个 MemoryPool**。

| 两条记录及排列 | checker 逐盘保留结果 | core 实际扫描结果 |
| --- | --- | --- |
| `(实例1,counter1,txg10)` 后接 `(实例1,counter1,txg20)` | txg20 | txg10 |
| 上述记录反向排列 | txg10 | txg20 |
| `(实例1,counter1,txg10)` 后接 `(实例2,counter1,txg20)` | 仅实例2 | 实例1和实例2都保留 |
| 上述记录反向排列 | 仅实例1 | 实例1和实例2都保留 |

四种排列在三轮中均重复成立。由此排除了“恰好是某一个 txg 的解析差异”和“仅仅两套夹具不一致”。

### 影响边界

这是**冲突、损坏或错误写者输入上的一致性缺陷**。两条相同 counter 记录同时占据不同环槽，不符合正常写者的记录位置规则。报告不再将它扩大为“正常发布流一定会遇到的恢复错误”。

但 checker 后续将这些记录视为恢复会读取的集合，并据此判断前缀、反向链等性质。只在更晚的合并阶段采用 `(instance,counter)` 不能解决前一阶段已经丢数据的问题。坏盘审计也不能把尚未检查的布局前提直接当真。

### 修复建议与验收

分别维护：所有自证记录及物理位置、恢复实际采用的记录视图。前者用于发现布局与冲突，后者须与真实恢复的先到保留一致。若选择对冲突布局直接判红，也必须在丢弃记录前显式检查，不能继续悄悄生成另一份“恢复视图”。

验收应覆盖同盘同键、同盘同 counter 不同实例、两种排列、跨盘副本冲突及正常唯一记录。初稿的合成几何探针只作历史证据，本轮结论以同一真实镜像对照为准。
