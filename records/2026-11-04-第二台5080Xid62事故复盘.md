# 第二台 RTX 5080 反复 Xid 62 事故复盘（2026-11-04）

## 结论

- **根因**：第二台 RTX 5080（PCI 总线号 1 那一张）从 P8 深度空闲被叫醒时，卡内管功耗与频率的 PMU 停机（内核 Xid 62，GSP 报「PMU has halted」，随后 Xid 154 要求重置）。触发的负载是 GPU 判器的快档测试：测试之间卡空闲十几秒降到 P8，下一条测试一往卡上建资源就出事。与 NVIDIA/open-gpu-kernel-modules #1307 同一签名（「GSP task watchdog … partition 4#0, task 3」），是驱动固件那一侧的毛病，触发在我们的负载样子上。外部报告没在本项目验证。
- **处置**：第二台系统单元 `nvidia-5080-min-clock.service`，按 PCI 总线号把 5080 核心频率下限锁在 800 MHz（上限 3105），空闲停在 P5、不进 P8，开机自起。用户定（「我觉得 800就可以了」「看起来就是锁频的问题」）。
- **现状**：5080 已恢复、锁着频，已放回服务的两行卡表。锁频之后高频叫醒 13 次没有 Xid、没进 P8（检查只跑了约 4 分钟，卡放回服务后停掉；不是对照试验，用户定不跑对照）。

## 经过

- **11-02 到 11-03**：五次 Xid 62。用户判断「不是驱动问题 切换驱动依旧出现」「触发原因是我们的代码，任务切换交接时候触发了这个问题」，先放着，见 `records/2026-11-03-积压跑法分片与GPU判器吞吐.md`「事件」一节的 Xid 62 那几条。
- **11-04 第一次崩**：合入后验证任务 5939 在 0 号卡上跑时出事，`nvidia-smi` 读成 `[N/A]`，恢复动作「GPU Reset Required」。
- **重置**：`nvidia-smi --gpu-reset -i 0` 两次都回「Not Supported」（第二次停了 `nvidia-persistenced`、没有客户端也一样）；只把卡从 PCI 总线摘下扫回，GSP 起不来（「unexpected WPR2 already up, cannot proceed with booting GSP」），卡还从 `nvidia-smi` 里消失、另两张卡的编号前移。改成解绑驱动、写 sysfs 的 `reset`、再摘下扫回才恢复。
- **找根**：用户定「你来解决 5080 必须要解决了」，摘出服务卡表单独测，授权第二台上的操作与绕过重型测试闸直接起测试。对照、复现与遥测见「证据」。
- **处置与放回**：锁频、装开机单元；管 task-server 的会话（0a）换上「清场只查分到的卡」那一批之后，回读锁频单元在跑，把 5080 放回卡表。

| 是不是派活太长（Xid 109） | 每次 Xid 62 前 30 分钟 5080 有没有 109 | 一条都没有；109 都在崩之后 |

## 恢复卡的命令

在第二台上以 root 执行（照这个次序做成两次；`nvidia-smi --gpu-reset` 在这张卡上回「Not Supported」，不用它）。`0000:01:00.0` 是 5080 的显卡功能，`0000:01:00.1` 是它的声卡功能。

```bash
d=/sys/bus/pci/devices/0000:01:00.0
# 1. 先留现场：AER 状态寄存器（重置会清掉）
lspci -s 01:00.0 -vv | grep -iE 'UESta|CESta|DevSta|LnkSta'
# 2. 卡上不能有人开着：只剩 nvidia-persistenced 才往下做；别的进程（别的卡上的 GPU 测试也会开着 /dev/nvidia0）等它退出
fuser -v /dev/nvidia0
systemctl stop nvidia-persistenced
# 3. 解绑声卡与显卡功能
echo 0000:01:00.1 > /sys/bus/pci/drivers/snd_hda_intel/unbind
echo 0000:01:00.0 > /sys/bus/pci/drivers/nvidia/unbind
# 4. PCI 层重置（只摘下扫回、不做这一步，GSP 起不来：「unexpected WPR2 already up」）
echo 1 > $d/reset
# 5. 两个功能都摘下、扫回，驱动重新认卡
echo 1 > /sys/bus/pci/devices/0000:01:00.1/remove
echo 1 > $d/remove
sleep 2
echo 1 > /sys/bus/pci/rescan
# 6. 起回 persistenced、重新锁频（重置会清掉锁）
systemctl start nvidia-persistenced
systemctl restart nvidia-5080-min-clock
# 7. 回读：恢复动作是 None、三张卡编号同原来、5080 空闲不在 P8、内核没有新的 RmInitAdapter 失败
nvidia-smi -i 00000000:01:00.0 -q | grep -i 'recovery action'
nvidia-smi --query-gpu=index,name,pci.bus_id,pstate,clocks.sm --format=csv,noheader
journalctl -k --since '-2min' | grep -E 'RmInitAdapter|bad state'
```

第 3 步解绑显卡功能时，卡上还有进程开着会卡住；所以第 2 步必须先确认 `fuser` 只剩 `nvidia-persistenced`。第 4 步写 `reset_method` 指定 `bus` 时内核回「Invalid argument」，照默认的方式（FLR）重置就成。

## 做得不好的

1. **头两天把它当「芯片问题、慢慢查」放着**，没有当场留现场：没有遥测、没有出事那一刻的测试时刻，六次都只剩内核日志。
2. **头一个结论下窄了**：只查了 0 号卡上的任务就说「不是频繁换任务」，用户指出「门禁任务从昨天跑到今天都没有这个问题，今天晚上的小任务就触发了」之后才分开「服务层换任务」与「卡上负载的样子」。
3. **先后提了三个没量过的假设**（任务被杀、PCIe 链路、频繁换任务），各花了一轮才排除；前两个本可以先查已有的日志（6 次里只有 1 次是撞内存上限被杀）。
4. **头一版复现太慢**：逐条单独起、一轮约 25 分钟，用户叫停后才改成只跑出事最快的那一个目标（6 分钟复现）。
5. **一张坏卡拖垮全台**：服务清场查全部卡，任一张坏就全起不来，还把好卡记坏；我交的积压跑法因此整件失败。
6. **重置办法没有现成的**：10-30 那次是用户手工重置的，办法没留，这次又摸索了一遍。
