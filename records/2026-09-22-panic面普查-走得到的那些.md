# 走得到的那些：什么样的盘上内容会走到它

**判据**：盘上读到的字节是攻击者可控的、或者设备返回了错误时，这一处会不会 panic。
下面每一段写清**什么样的盘上内容**会走到它、**经哪条调用链**、**panic 落在哪个子表达式**。
逐处判定在 `full-list.md`，跨文件前提在 `full-list.md` 开头与 `partial.md`。

⚠️ 行号按 `/tmp/claude-1000/panic-survey/snap/`（2026-09-22 05:52 UTC 的工作树快照，sha256 在 `snap.sha256`）。
这一轮做到一半时另一个会话在改 `crates/singlefs-core/`，`raw.tsv`（05:22）里 `records.rs` / `transaction.rs` / `recovery.rs` / `mount.rs` / `write_accounting.rs` 五份的行号已经过期。

## 一句话总账

**21 处走得到，全部来自同一条根因的两个分身**：

| 根因 | 落在哪 |
|---|---|
| **盘上自述的宽度 / 数量没有下界判，就拿去按字段表的固定偏移切** | R1–R4（core 的条目解析器）、R12（checker 的区域数）、R13（checker 走读主干） |
| **盘上读来的结构值不经判定就喂进写侧断言与位图** | R5（两盘同槽）、R6–R11（分配器与记账行） |

**core 侧 15 处，checker 侧 6 处。** core 的读路径普遍把结构判做成了 `Err`（`unit.rs` 的三个 `parse_*`、`recovery.rs` 整份都很干净），
漏的是**条目这一层**：单元头判得很严，单元里**条目的宽度**只判了 `entry_width ≥ key_width`，之后就按 24 / 27 / 55 / 100 / 112 / 120 这些固定偏移去切。

## R1 extent 条目短于 112 字节 ⇒ `parse_extent_record` 越界

- **位置**：`records.rs:355`（`bytes[..24]`），以及同一函数下一行 `DataPointer::read_from(&mut ByteReader::at(bytes, 24))` 打到的 `bytes.rs:72`
- **盘上怎么造**：把 extent 树根那个码 2 节点的 `key_width`（偏移 51）写成 ≤ 8、`entry_width`（偏移 84+2k）写成 8、`entry_count` 写成 1、声明长度写成 8，两道校验和照新内容重算。`parse_index_node` 全部通过（`entry_width < key_width` 不成立、`entry_count × entry_width == declared_length` 成立、条目区装得下），交出一条 8 字节的条目。
- **调用链**：`mount_writable` → `rebuild_previous_version` → `recovery.rs:589` `parse_extent_record(extent_node.entries.first()…)`，以及 `recovery.rs:1364` 的同一处。
- **panic**：`bytes[..24]` 的切片越界。长度落在 24..112 时则是 `bytes.rs:72` 的 `take` 越界。

## R2 映射条目短于 55 字节 ⇒ `parse_mapping_entry` 越界

- **位置**：`records.rs:363`（`bytes[..27]`），以及 `records.rs:364` 的 `ByteReader::at(bytes, key.len())` 打到的 `bytes.rs:72`
- **盘上怎么造**：同 R1，改的是映射树根节点的 `entry_width`（判据只要 ≥ `key_width`，而映射 key 宽 27，55 这个数没有任何东西在看）。
- **调用链**：`recovery.rs:661`、`recovery.rs:1377`、`transaction.rs:1000`（`mapping_locations_for_key`，释放判定那条路）。

## R3 inode 内部条目短于 120 字节 ⇒ `parse_inode_internal_entry` 越界

- **位置**：`bytes.rs:72`（这个函数自己没有 `[..]` 切片，全靠 `reader.get_*`）
- **盘上怎么造**：inode 树根节点的 `entry_width` 写成 8..119。
- **调用链**：`recovery.rs:607`（`rebuild_version` 里逐片叶容器那个循环）、`recovery.rs:1304`（`walk_to_file`）。快照里 `transaction.rs` 已经不再 import 这个函数，`carried_file_version_units`（`transaction.rs:1990`）现在走别的路。

## R4 分配记录 / 记账条目短于 20 / 34 字节 ⇒ `AllocationRecord::parse` / `AccountingEntry::parse` 越界

- **位置**：`bytes.rs:72`；两个 `parse` 分别在 `allocator.rs:70` 与 `records.rs:169`，**都没有一句长度判**
- **盘上怎么造**：分配记录树 / 记账树根节点的 `entry_width` 写成 10..19 / 22..33（要 ≥ key 宽 10 / 22）。
- **调用链**：`recovery.rs:649`、`recovery.rs:655`（`rebuild_version` 里那两个 `.map(...)`）；另有 `recovery.rs:465`、`1254`、`1286`。

> R1–R4 的共同修法只有一处：`parse_index_node` / `parse_packed_unit` 交出条目之前，或者各条目解析器入口，按「这棵树的条目该有多宽」判一次。
> **checker 那一侧已经有现成的做法**：`walk.rs:929/939/949` 的 `node.entry_width >= extent_leaf_record_bytes()` 那几道，以及 `judge_packed_container` 的 `registered_record_width(record_type) == Some(width)`。

## R5 根记录 / 映射条目里两条位置条目的槽号不等 ⇒ 「两盘同槽」断言

- **位置**：`mount.rs:467`（`format_time_allocator` 里的 `placement_of`）、`transaction.rs:957`（`placements_to_release_via_mapping`）
- **盘上怎么造**：把根记录里 `instance_table` 或 `tree_table` 指针的两条位置条目写成不同的槽号，诞生 txg 保持 0（过 `VersionWithoutFileNotWrittenByMakeFilesystem` 那道判），整槽校验和重算。`RootRecord::parse_slot` 只判 magic / 整槽校验和 / fsid / flags，**不判两条位置条目**。
- **panic**：`assert_eq!(pointer.locations[0].slot, pointer.locations[1].slot, "两盘同槽（D2 已定项 10）")`
- **同族但没走到**：`pointer.rs:108` / `149` 的 I-2.5 升序断言。core 的读路径同样不判升序（只有 checker 的 `image.rs:293` 判），而携带式发布会把盘上读来的指针原样写回 `RootRecord::to_slot` / `TreeTableEntry::to_bytes`。本轮没把这条链的每一步坐实到一次具体的写，所以 `full-list.md` 里仍记 走不到；**它是下一轮第一个该复核的**。

## R6 分配记录的槽号落在单元区之外、或跨度越过单元区末尾

- **位置**：`allocator.rs:236`（`DeviceFreeMap::index` 里的 `slot.0 - UNIT_AREA_START_SLOT`）、`allocator.rs:375`（`assert!(end <= self.allocated.len())`）
- **盘上怎么造**：分配记录树里放一条 `slot < 50176`（`UNIT_AREA_START_SLOT`）的记录，或者 `slot` 靠近单元区末尾而 `span_slots` 写到 0x7FFF。
- **调用链**：`mount_writable` → `rebuilt_allocator`（`mount.rs:390`）→ `PoolAllocator::rebuild_from_records`（`allocator.rs:601`）→ `mark_allocated`（613）。
- **panic**：槽号偏小时落在 `index` 的减法上（`Cargo.toml:17` 的 `overflow-checks = true`，`expect` 那一句轮不到跑）；跨度过大时落在 375 那条断言上。
- **`is_free`（`allocator.rs:240`）自己判了上下界**，`mark_released` / `isolate` / `hold_until_floor_takes_effect` / `mark_reclaimed` / `mark_allocated` 五个入口一个都没判。

## R7 被抛弃根那棵账里的槽号 ⇒ `isolate` 的跨度断言

- **位置**：`allocator.rs:282`（`isolate`，`allocator.rs:279`）
- **调用链**：`mount.rs:364` `allocator.isolate_abandoned(record.device, record.slot, span)`，记录来自 `allocation_records_under_root(devices, root)`，一条判都没经过。

## R8 两条分配记录罩住同一个槽

- **位置**：`allocator.rs:376`（`assert!(self.allocated[start..end].iter().all(|taken| !*taken), "跨度里有已分配的槽")`）
- **盘上怎么造**：分配记录树里放两条 `(device, slot)` 相交的记录。
- **这一条代码自己写着会 panic**：`allocator.rs:500` 那段注释——「留着它，下一次可写挂载重建分配器时两条记录罩住同一个槽，重建在 `mark_allocated` 的断言上 panic」。
- **拦得住它的判据已经写好了，只是没接在这条路上**：`recovery.rs:1100` 的 `allocation_records_are_one_per_device` 正好判这一条，而它**只在 `walk_to_file`（1154）里调**；挂载走的 `rebuild_version`（541）一次都不调。

## R9 分配记录的设备身份不在池里

- **位置**：`allocator.rs:611`（`.expect("分配记录的盘在池里：走读逐盘核过")`）、`allocator.rs:942`（`.expect("被抛弃根的分配记录的盘在池里：走读逐盘核过")`）
- **盘上怎么造**：把一条分配记录的设备身份 4 字节写成池里没有的号。
- **两句 `expect` 的理由都写着「走读逐盘核过」**，而走读就是 `walk_to_file` 那条路——挂载不走它（同 R8）。

## R10 两块盘的分配记录树不对称 ⇒ 释放时另一块盘没有记录

- **位置**：`allocator.rs:703`（`.expect("释放的落点要有分配记录")`）、`704`（`assert!(!record.is_released)`）、`705`（跨度不符的 `assert_eq!`）
- **机理**：释放前的校验 `placements_to_release_via_mapping`（`transaction.rs:962`）**只核 `locations[0].device` 那一块盘**的记录在册、未释放、跨度相符；而 `PoolAllocator::release`（`allocator.rs:697`）对**每块盘**都要求有一条对得上的记录。
- **盘上怎么造**：盘 0 的分配记录树里有 `(slot, span, 未释放)`，盘 1 的没有，或者已释放，或者跨度不同。

## R11 记账树里没有 inode 号水位那一行

- **位置**：`transaction.rs:846`（`.expect("每次发布都写 inode 号水位那一行（D5 已定项 8 的池级三行之一）")`）
- **盘上怎么造**：把记账树根里 `statistic == 12`（`STATISTIC_INODE_WATERMARK`）那条记录换成别的 statistic。条数不变，所以 `walk_to_file` 的「记账条目数 = 3 + 6 × 盘数」也照样过；而 `rebuild_version` 连条数都不数。
- **调用链**：挂载重建之后的第一次发布（写行 / 暖机 / 写文件都要取水位）。
- **`grep -rn STATISTIC_INODE_WATERMARK crates/singlefs-core/src/` 只有 4 处命中，没有一处是读路径上的判定。**

## R12 系统配置里的区域数 > 3 ⇒ checker 下标一个长 3 的数组

- **位置**：`image.rs:206`（`geometry.region_devices[usize::try_from(region).expect("区域号")]`）
- **盘上怎么造**：系统配置槽偏移 361 那一字节（`regions`）写成 4..255，整槽校验和重算。`check_system_configuration_slot` 判 magic / 校验和 / incompat 位，**不判这个字节**。
- **panic**：`region_devices` 的类型就是 `[u32; 3]`（`image.rs:115`），`geometry_of` 只读 379 / 383 / 387 三个（`image.rs:132`），`region` 取到 3 就越界。
- **同一个量在同一个 crate 里另一处夹过**：`walk.rs:1907` 的 `&geometry.region_devices[..regions.min(3)]`。`image.rs:206` 少了这个 `.min(3)`。
- **同一行还有第二个问题（射程之外）**：`region * geometry.prime_step * geometry.chunk_bytes`（`image.rs:209`）三个因子全是盘上读来的 u64，`overflow-checks = true` 下会溢出 panic。

## R13 checker 走读主干按固定偏移切条目，而条目宽度是盘上自述的

- **位置**：`walk.rs:273`（映射条目 `entry[27..55]`）、`307` 与 `320`（树表条目 `entry[14..100]`）、`357`（inode 内部条目 `entry[34..120]`）、`511`（extent 记录 `record[24..112]`）
- **盘上怎么造**：与 R1–R4 同一招——把对应那棵树根节点的 `entry_width` 写成刚好 ≥ key 宽、但小于字段表宽度。各 key 宽：映射 27、树表 8、inode 8、extent 24。
- **`index_node_view` 只判 `entry_width < key_width`（`lib.rs:333`）**，`check_index_node_keys` 只判 `schema.width() == view.key_width`（`lib.rs:423`）；两道都够不着「条目要装得下整条记录」。
- **同一个文件里的另一条走读一道守卫都不缺**：`walk.rs:893`（`entry.len() < tree_table_entry_bytes()`）、`929` / `939` / `949`（`node.entry_width >= …`）、`1203`、`1290`。**守卫是现成的，只是没铺到 `walk_root` 这一支上。**
- **后果比 core 那边更直接**：checker 是判据的可执行形式，它 panic 意味着「一个畸形镜像让 checker 自己倒下」，而不是判红。

# 缺口：本轮判了「走不到」，但撑着它的不是一道检查

这几处今天不会炸，靠的是一条**没有写下来、也没有检查盯着**的契约或算术余量。它们不算走得到，但下一轮改动很容易把它们变成走得到。

| 位置 | 今天靠什么不炸 | 什么改动会让它炸 |
|---|---|---|
| `lib.rs:268`（`check_unit` 的 `unit[51]`） | 函数自己的守卫是 `unit.len() < 42`，比用法窄 10 字节；救它的是三个 `read` 实现都 `vec![0u8; length]` 之后整份返回（`recovery.rs:82`、`crash.rs:42`、`crash.rs:270`） | 任何一个 `ImageReader` / `PoolReader` 实现在越界时返回短 Vec 而不是 `None` |
| `walk.rs:104/106/111/115/130`（`judge_unit_header`） | 同上，而且这个函数**一句长度判都没有** | 同上 |
| `walk.rs:574/577/580/582`（扫描方向读单元头） | 同上 | 同上 |
| `inode_tree.rs:88`（`INODE_LEAF_RECORDS - records.len()`） | 233 这个上界正好等于「32632 ÷ 140 向下取整」，一条不多 | 改 `INODE_RECORD_BYTES` 或 `PACKED_UNIT_HEADER_BYTES` 而不重算 `INODE_LEAF_RECORDS` |
| `pointer.rs:108/149`（I-2.5 升序断言） | core 的读路径不判升序，而携带式发布会把盘上读来的指针写回去；本轮没把「哪一次写会拿到一条降序的盘上指针」坐实 | 见 R5 末尾——这是下一轮第一个该复核的 |
