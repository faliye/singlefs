## 判决：今天定不了。承重的是自举那一面。

**攻击腿七条命中里最硬的三条**（主 agent 逐条核过原文）：

1. **容器的 MAC 与 nonce 在候选的 value 里没有位置（格式级）。**
   D18 已定项 11 逐字：容器索引是「打包单元物理指针（**与 MAC**）的唯一持有者」；
   而别的树引用容器用的是 26 字节身份引用，里面**没有指针头部**；
   MAC 128 位 + nonce 96 位恒定占位在指针头部 31 里（D19 已定项 3），
   位置条目 14 只有「密文校验和 4」。D9 已定项 4 逐字「nonce 每 extent 存，**不现算**」
   ⇒ 加密后解不开。修法要按标签分两种 value ⇒ **「零新结构」当场作废**。
2. **自举会重演，收敛在「中央映射自己的节点」那一层，而那一层零条款。**
   D2 已定项 12 逐字「容器整条链恒走 `w = 2` 镜像」，而 E107 的 163 840 定额把「容器索引 3 层」
   算在「整条链」里 ⇒ 换成中央映射就是给一棵大得多的树整体换 `w`；
   只镜像覆盖码 3 那段 key 的子树又撞 `.claude/rules/fs-design.md` 硬要求 5
   「分支变量不许在操作中途改变」——哪个节点覆盖那段随分裂移动。
3. **折进标签字节是被 key 碰撞逼出来的，不是排序偏好。**
   类型 1 容器号树内单调从 1 起、类型 2 容器号 = inode 号也从 1 起，
   而 first-txn-layout 逐字写着第一个事务的 inode 叶是「容器号 = 1、出生代 = 1」
   ⇒ 不把类型放进 key 就有**真碰撞**。代价：扩展空间从第二级登记表的 65 531 掉到标签里的 7，**缩 9361 倍**。

**正推腿给的可核实的数**（主 agent 复核）：单元类登记表已登记 **7 个码**（256 余 249）；
打包记录类型已登记 **4 种 + 1 无效**。折进标签要 3 个新值，**算术上绰绰有余**——所以第 3 条命中打的不是空间，是扩展性。

**候选自己文本不一致**：类型 2 已由 D8 已定项 6 定成「就是 inode 树的内部节点」、
类型 4 已由 D18 已定项 11 定成「根记录直接持有」⇒ 候选的全称提法要收窄到
「类型 1、类型 3、以及条带表那个待登记的新类型」。

**面四通过、不欠新账**：码 3 头那四个命名字段齐全（出生树 ID 43 / 打包记录类型 51 /
容器号 53 / 容器出生代 61），扫描重建读得出容器身份。
⚠️ **找反例腿第 3 条说「头里缺容器出生代」是错的**，主 agent 逐字核表坐实。

## 这一轮学到的

- **候选说「零新结构」的时候要先问它 value 装不装得下**。这条候选栽在 MAC 与 nonce 上，
  而那两样在别处（指针头部 31）有位置、在中央映射的 value（位置条目 14）里没有。
- **「折进一个字节」这种收口，代价不在字节数上，在值域**：算术上 249 个空位绰绰有余，
  真代价是把扩展空间从 65 531 缩到 7。
- **找反例腿三条里有一条是编的**（说码 3 头缺容器出生代），逐字核表当场否掉。
  这正是「腿给的每条命中都要主 agent 现查」那条纪律要拦的。
