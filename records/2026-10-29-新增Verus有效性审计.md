# 新增 Verus 有效性审计

用户要求检查已添加的 Verus 是否有效、能否发现错误。本轮重点审计前几轮新增的 `file_range_proofs.rs`、`partial_write_proofs.rs` 及其 core 包装；同时验证完整 replay-prefix crate。没有把其它会话新增的 core 证明算作本轮已经逐项审计的对象。

## 已完成的正向验证

本机正式门禁因内存资源预约排队满 3600 秒，包装退 252。这是未运行，不是证明失败，也不计作通过。随后将固定副本和同一份 Verus 发布包转到配置中的第二台，在原有内存包装下执行。

- 工具链核对通过：Verus `0.2026.09.20.aef82ed`、发布包 SHA-256、六个 Cargo 包的版本/出处/源码指纹，以及 Verus Rust 1.98.1 与产品 Rust 1.98.0 均与登记一致。
- `proof` 整格通过：135 个验证条目，合计 **150 verified、0 errors**，`--rlimit 10`。135 与 150 分别是条目数和证明义务数，不混用。
- 产品构建与 Verus 构建的 **98 个产品 MIR 条目整段逐字相同**；没有发生路径别名规整。这覆盖 replay-prefix 的编译对应关系，不覆盖 core 包装或全部产品路径。
- 七份核没有禁止标记，没有额外可信声明、cfg 分叉或证明区域外的 trait 实现。vstd 按固定版本整体信任。该结果没有形式化证明 Verus、Z3、Rust 编译器自身无缺陷。
- 普通 Rust 回归：core **370 passed**，replay-prefix **25 passed**，共 395 项。

门禁的判法单元指纹因已有 `memory_peaks_lib.py` 的 `globals-lookup` 拒算，全部现判、没有复用旧结论；这没有跳过实际验证。

## 规格与数学推导复核

1. 单元计数：非零 size 满足 `size - 1 = q × capacity + r`、`0 <= r < capacity`，因此 `q × capacity < size <= (q + 1) × capacity`；返回 `q + 1` 同时满足足够覆盖和最小性。零大小单独处理，顺序写的零大小返回一个单元。不能只把除法表达式和实现相同当作正确性的依据。
2. 写交集：起点取两个起点的最大值，终点取两个终点的最小值；起点小于终点时返回正长度及两个相对偏移，否则没有共同字节。后置条件用逐字节等价表达恰好覆盖交集，两侧减法在相应分支不会下溢。
3. 尾部分批：目标取 desired 与 existing 的最小值；最终批恰好到目标，非最终批减少正的 batch。分区引理同时约束进度、并集和不重叠。
4. 部分写：五类结果由旧/新单元、是否相交、是否整块覆盖划分。两个引理把端点比较连接到“存在共同字节”与“每个单元字节都被写”的语义；写后单元数取原数与所需数的最大值，保留已有后缀。

规格中的乘加按数学整数解释。`unit_containing_byte` 证明字节落在数学区间内，**没有证明区间末端能装进 u64**；core 实际换算还要检查这一点。

## 故障注入与缺口

静态覆盖检查发现上述两个模块有三个引理缺少独立必红变异。本轮在 `crates/singlefs-replay-prefix/verus-must-red-worlds.tsv` 补三行：

- `tail-partition-needs-positive-batch`：去掉 batch > 0。反例 existing=1、desired=0、batch=0、next=0，严格进度不成立。
- `adjacent-partition-needs-seam-inside-range`：只保留 left <= right。反例 left=0、seam=2、right=1、写区间 [0,3)、byte=1，合并区间与两段并集不等。
- `partial-touch-needs-nonempty-write`：允许 ws=we。反例 ws=we=1、us=0、ue=2，端点相交判定为真但共同字节不存在。

这三行连同已有 31 行，共 **34 个变异全部被真实 Verus 拒绝**，证明错误落点均与登记的 landing 相同，原文均唯一命中；没有 rlimit 用尽的项。三行新增变异各报一条证明错误，与登记的 proof_errors=1 一致；整组没有错误条数漂移。新增两个模块的静态负例覆盖缺口已清除。

完整仓库的静态覆盖检查仍报告另外九处缺口：unlink_proofs 的五个引理，core/block_device 的两个 invariant 块，core/bytes 的 copy_bytes_into 和 core/checksum 的 crc32_castagnoli。这是负例覆盖缺口，不等于这九处证明或实现已被证伪；本轮没有宣称整个仓库门禁全绿。

## 证明抓不到的调用层错误

在独立副本把 core 枚举转换中的 `OldReadBack => OldUnitReadBack` 故意改成 `OldReadBack => OldUnitCoveredWhole`：

- replay-prefix Verus 仍然 **150 verified、0 errors**；
- 现有 core 测试 `partial_write_read_decisions_match_overwritten_bytes_at_unit_boundaries` 从通过变为失败（退出 101，读回标记 false/true 不等）。

这证明当前纯核证明不能替代未验证包装层的测试，不能由证明数量推得整条写入路径无 bug。变异仅作用于临时副本并已还原，正式源码没有该错误。

另外用两个临时 Rust 探针复现 API 边界：

1. `PartialWriteOfAFile::new(0, 0, FileOffsetInBytes(u64::MAX - 1), NonZeroU64::MIN)` 构造成功，但对最后写入单元调用 bytes_written_into 时，单元末端加法在 debug 构建溢出。实际 transaction 在计划使用前检查按整单元取整后的长度，该例被拒绝；未发现正常事务路径可触发这个 panic。
2. 构造 offset=0、length=1 的计划后，把公开 offset 改成两个单元容量，缓存的 end 仍为 1，可破坏写区间一致性。当前事务路径使用未改写的构造结果。公开字段的不变量没有被类型系统或本轮 Verus 证明强制维护。

以上是未验证 API 的约束缺口，不能报告成已确认的产品数据损坏。本轮没有更改这些 API 的行为。
