# GC 形式化与 core 改动严格复核

开始于标题那一天，2026-10-25 完成复核。依据用户要求：“仔细审核你改动，尤其是涉及 core 相关的。需要反复的论证”，并“格外严格的确认新增代码合理且没有问题”。

本轮审查 [GC 扩展](2026-10-24-GC实现与旧读者及崩溃协议形式化扩展.md) 引入的产品接核与新增证明。采用同一审查者的三个视角：逐项语义推导、构造反例、证明边界核对；不是三位独立审查者的评审。**通过这些检查不能保证代码绝对没有问题，也不能将条件模型提升为产品端到端证明。**

结论：在本轮核对范围内，没有发现接核改变选段、批计划或回收比较结果的反例；发现并处理了不必要的 key 克隆、证明输入无法由输出测试充分观察的缺口和边界说明不足。新增直接输入检查及九个必错变异均实际验证。性能和完整实现精化的剩余限制见下文。

## 第一轮：从改动前实现逐项推导

### 选段

1. 活槽统计仍只取目标设备的未释放记录，逐槽累计；扫描仍先按设备过滤，同一起点取第一份。构造核输入前的代码未改变这些判据。
2. 每个输入下标与段起点一一对应且顺序递增。核的“最小 live_slots，同分最早下标”与旧的 `(greedy_score(live_slots), start_slot)` 最小值相同。
3. 排除这次挂载打开的段、活意图段、含 pin 的段、扫描拒绝的段；未扫描仍是候选，扫描后无可搬项不再是候选。这五类条件逐一核对。
4. 核返回的合法下标通过同一槽号公式还原。Chosen/ScanBeforeChoosing/NoEligibleSegment 三种结果与旧分支对应。
5. pin 区间是 `[start, end)`；尾部不足整段不进入输入。新增边界用例直接给定期望结果，另与旧算法核对。
6. 计算地址时既有的乘法、加法及设备几何前提没有被正式证明。转换未新增不同的数学公式，但额外向量会增加资源消耗；不能用纯结果等价论证 OOM 行为相同。

### 计划

1. K 仍来自 `NonZeroUsize`；全输入 key 互异检查先于转换与取前 K 项，不因批上限而漏掉后面的重复 key。
2. 转换不重排/过滤记录，分类与源槽逐条对应；计划核返回输入下标，产品从原扫描取完整 Placement 和真实 key，跨度不从简化核结构重造。
3. key 身份表按完整字节的相等关系分配 ID：相等 key 复用身份，不等 key 获得不同身份。`BTreeMap<&[u8], u64>` 比较字节内容，不比较借用地址；输入不可变，借用不逃出转换函数。
4. 参考算法仍是 filter 可搬项后 take(K)，空计划再区分扫描是否为空。独立参考不调用产品转换函数或计划核。
5. `plan_batch_skipping_the_units_this_publish_rewrites_anyway` 的原有特殊分支没有变化：只剩本来就重写的节点时可以返回全部节点，不能误套普通计划的 K 项上限。

### 回收

`CheckpointTxg` 是派生 Ord 的单字段 u64 newtype。将其 `<=` 比较交给核，保留全宽、released 条件和等于 floor 的边界；未改变计算 floor、按设备处理、去重、位图和隔离保护的代码。新增测试覆盖 0、1、32 位边界及 u64 最大值，全部 released/floor/generation 组合共 72 格。

**不能反推**比较核正确就说明回收策略完整正确。核不计算 floor；算术引理要求 `floor <= reader_txg < generation`，两项不等式及版本到地址引用的连接都必须由调用方另证。

### 独立参考是否真保留旧实现

以最初接核 diff 记录的改动前 Git blob `808c4691593740bbd76bf81d2940c79ad930e083` 为固定基线，冻结两段函数体词法单元，再机器比较：

- choose_region 的旧函数体与 reference_choose_region 逐 token 相同，仅忽略注释和空白。
- plan_batch 的旧函数体与参考体，仅将参数表达式 `batch.units()` 展开为传入的 `batch_units`，其余 token 相同。

首次尝试使用暂存区作基线被检查拒绝：暂存区已包含后续接核修改，不能代表改动前。没有据此改参考算法或放宽判据；改用原 diff 的固定 blob 后通过。失败输入与日志也保留在证据目录，避免把可变暂存区误当可靠历史。

## 第二轮：主动寻找测试看不到的错误

发现三类需要补强的地方：

| 发现 | 处理 |
| --- | --- |
| 原新增计划转换复制了所有可搬 key，除了输出 K 项外又增加一遍 key 字节分配 | 改用借用切片作为身份表键，保持内容比较，去掉额外字节克隆；仍保留向量和树节点开销 |
| ID 和源槽等字段主要参与规格，最终计划结果正确不代表证明输入正确 | 提取私有 `compaction_kernel_allocations`，直接检查输入条目数量、源槽、全部 key 对的相等关系；测试重复 key 的转换只是核对表示关系，产品仍在调用前拒绝重复 |
| 既有枚举没有覆盖重复扫描优先级、尾段、pin 端点、特殊 key、完整 Placement 和大 K | 新增有明确期望的边界用例；对特殊 key 和非升序源位置的人工输入检查不重排及完整保留，不能把这些测试解释为盘面输入合法性证明 |

九个新变异已登记到 `crates/mutations.tsv`，全部在指定测试上失败，原始基线全部通过：

1. key 身份只看首字节，错误合并共同前缀。
2. 重复 key 分配新身份，破坏相等关系。
3. 源槽转换偏移一槽。
4. 同段重复扫描改取最后一份。
5. 把不足整段的尾部算作完整段。
6. pin 区间误改为包含段末。
7. 返回 Placement 时把 span 强制改成 1。
8. 撤掉全输入重复 key 拒绝，让 K 之外的重复项漏过。
9. 回收比较从 `<=` 误改成 `<`。

这些反例分别检查表示、选择和产品返回值；不是仅把预期值复制成实现的镜像测试。有限用例和九个反例也不构成所有输入或所有可能错误的穷尽证明。

## 第三轮：逐条核对形式化结论是否被夸大

新增 [src/README.md](../crates/singlefs-replay-prefix/src/README.md)，并在 [gc_crash_proofs.rs](../crates/singlefs-replay-prefix/src/gc_crash_proofs.rs) 中为状态、步骤、六个规格函数和每条证明补充解释。核对后必须保留以下边界：

- 所有读者匹配同一个 logical，连 key 域也相同。“旧读者”仅指搬迁前物理地址的读者，不是任意历史逻辑快照。
- disk 把地址视作抽象数据单元，没有设备编号和多槽 span。`Write` 可表达无人引用地址上的任意坏字节，不证明设备写原子性。
- Checkpoint 和 Crash 的原子保存/恢复语义由 gc_next 定义。幂等定理检查该定义的后果，不是从真实根环和 journal 解析推出恢复结果。
- Relocate 要求完整字节已持久且相等；这不是实际 CRC 检测正确性证明，也没有证明校验和无碰撞。
- Relocate 不要求目的新鲜、不同于源或保证进展，可以是无操作搬迁。证明读取保持不等于空间守恒、分配互斥或 GC 终止。
- `gc_slot_is_unreferenced` 保护当前根、持久根和每个读者，但没有证明 allocator 的 floor 判据自动蕴涵这个地址条件。
- 非空见证的函数体逐步检查搬迁与读者释放；其 ensures 只暴露初始非空状态存在，不能充当返回完整执行历史的契约。
- 只有回收比较函数在 gc_crash_proofs 中被产品直接调用；其余规格和引理不是产品的实际发布/恢复执行代码。

此前报告中的“完整步骤分类”应理解为**所定义七个抽象步骤的逐类证明**，不是已经覆盖真实 GC 或文件系统全部事件。本轮明确纠正这一容易被误解的说法。

## 未消除的风险与范围

没有实测性能分布或大池内存上界。选段额外构造输入向量；计划虽然不再复制所有 key 字节，仍有转换向量和借用 key 的 BTreeMap。不能声称接核没有资源代价。

没有完成设备屏障/FUA、根与 journal 解析、真实恢复择根、双盘、隔离、不同逻辑版本及错误重试的端到端精化。未运行全工作区门禁或全量设备崩溃枚举。本轮没有提交。
