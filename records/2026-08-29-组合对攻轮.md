### 4. 根环的候选几何直接违反 D2（RAID 条带策略） 已定的两条硬要求

| 出处 | 逐字 |
|---|---|
| D22（单元原子性怎么合成） 未定项 2 | 「一个候选形态（**2 区域 × 4 槽 × 256 字节 = 2048 字节**）已提出，未验证」 |
| D20（承重面：单元的原子性与自包含） 已定 | 自证单元（根槽、journal 记录头）的原子宽度「**等于运行时探测到的 `physical_block_size`**，不许硬编码」 |
| D2（RAID 条带策略） 已定硬要求 1 | 「**不发出小于设备物理映射单元的写**。在 Linux 上这个量是 `io_min`，不是 `physical_block_size`」 |
| D2（RAID 条带策略） 已定硬要求 2 | 「**不让两个生命周期不同的对象共享同一个物理映射单元**」 |

**两处撞车，一处不需要任何特殊设备**：

1. **本机现查 `/sys/block/nvme0n1/queue/physical_block_size = 512`**，
   而候选槽宽是 **256 字节** ⇒ **两个槽挤在同一个原子单元里**。
   按 D22（单元原子性怎么合成） 自己的分析（整单元校验和之下多条挤一个原子单元
   「除第一条外都判不了撕裂」），**写一个槽可能撕裂邻槽**。
   而根环存在的全部理由就是「一次撕裂不许抹掉唯一见证者」。
2. **整个根环 2048 字节可以落进单个 `io_min` 单元**。
   `io_min` 与 `physical_block_size` 是两个量（D2（RAID 条带策略） 自己强调过），
   而 Linux 的稳定 ABI 文档逐字写着 minimum_io_size
   「For RAID arrays it is often the **stripe chunk size**」
   （本机 `fs-refs/linux-6.17/Documentation/ABI/stable/sysfs-block`，2026-08-29 现查）
   ⇒ 阵列上 `io_min` 轻易是 64 KiB ⇒ **8 个根槽全在一个映射单元里**
   ⇒ 一次掉电诱发的设备内部 RMW 可以**打掉整个根环**。
   这正是 D2（RAID 条带策略） 硬要求 2 要禁的形态，而根槽是本工程生命周期最长的对象之一。

⇒ **建议**：D22（单元原子性怎么合成） 未定项 2 定槽几何时，槽宽取
`max(physical_block_size, io_min)` 并且**每槽独占一个 io_min 单元**；
两个「区域」的分离判据也要按 `io_min` 而不是按字节数写。
（内核代码里 `physical_block_size ≤ io_min` 恒成立，D2（RAID 条带策略） 已记，
所以「槽宽 ≥ io_min」自动满足 D20（承重面：单元的原子性与自包含） 那条原子宽度要求。）
⚠️ 本机 `io_min == physical_block_size == 512`，**这条在本机无法用故障注入证伪**，
与 D2（RAID 条带策略） 那两条硬要求同样是机制推导。

**三方论证：只跑了本地腿（2026-08-29，字词损坏检查通过）。**
提示 `research/prompts/e34-rootring-geometry-local.md`，
输出 `research/results/e34-rootring-local.out`。立场是「找反例」。

- **两半都判成立**，机制描述与本节一致。
- **它独立给出的最小更正与本节相同**：槽宽 ≥ `io_min`，且每槽完整落在自己的 `io_min` 单元内、互不重叠。
- **它举的反例**：`io_min` 恰为 256 字节的设备上不违规。⚠️ 这个反例**在 Linux 上取不到**——
  `io_min` 的下界是逻辑块大小，而本机逻辑块就是 512。**记为无效反例。**
- ⚠️ **一处分歧，判它错**：本地腿说 D20（承重面：单元的原子性与自包含）

  ——**方向与 D2（RAID 条带策略） 当初纠正的那次相反，说明这个坑两边都好踩。**
  ⇒ D20（承重面：单元的原子性与自包含） 那条**不改**，本节的更正是**加一条写侧要求**，不是替换它。

**这条还有一笔没算的账**：D21（权威态与派生态的分界） 的逐字节表把
「位置条目 ×2（dev 1 + 物理偏移 6 + 密文校验和 4）= 22 字节」算在**单元元数据 108 字节**里。
若位置条目必须整段住在明文映射层，那 22 字节要**在明文层再付一遍**，
而明文映射层的每条目宽度**从没进过任何一张成本表**。

### 8. D8（核心索引结构） 的 key 布局在 D6（快照实现模型） 定案之后已经不完整

D8（核心索引结构） 已定项 3（2026-08-26）：`key = (locality_id, inode, offset)`——**三段，没有快照维**。D6（快照实现模型） 定案（2026-08-29）取多可写头 ⇒ 同一个 `(inode, offset)`
必须能同时存在多个可写头版本 ⇒ **key 必须带快照维**。**D8（核心索引结构） 至今没改。**

**它已经在支撑一个下游判断**：D9（加密） 已定项 4 写着
「前置也已经满足了——D8（核心索引结构） 已定项 3 早在 2026-08-26 就定下
key = `(locality_id, inode, offset)`……⇒ 这个理由不再成立，本项现在可以定」。
⇒ **那个「前置已满足」建立在一个已经被 D6（快照实现模型） 抽掉的 key 布局上。**

⚠️ 门禁两个未定项阶段都抓不到这个形状：它们扫的是**未定项**被别处定了，
而这里是**已定项**被别处的定案挖空。与 C41（已定小节的前提也会陈旧）同型，
但 C41 记的是「已定小节里的**前提**」，这里是「**已定的结论本身**不再完整」。

### 9. 「快照前缀」与「快照 ID 进 key 低位」互斥，而 D6（快照实现模型） 引用了前者给自己减负

D8（核心索引结构） 的布局规则逐字：「**同一快照的 key 带同一 snapshot 前缀** → 删快照有机会变成范围操作」。D6（快照实现模型） 的候选逐字：「bcachefs 的「**快照 ID 进 key 低位**」」。

**前缀与低位是同一段排序权的两种互斥用法**：
快照 ID 在高位 ⇒ 同一快照的 key 连续、而同一对象的多个快照版本散开；
快照 ID 在低位 ⇒ 同一对象的多版本连续、而同一快照的 key 散开。

而 D6（快照实现模型） 在给自己减负时**引用的正是 D8（核心索引结构） 那句前缀规则**：
「另见 D8（核心索引结构） 已定的布局规则：『同一快照的 key 带同一 snapshot 前缀 →
删快照**有机会变成范围操作**』」。
⇒ **D6（快照实现模型） 用一条与自己候选形态互斥的布局，去对冲自己那条「删快照要遍历」的代价。**

⚠️ 还有一层：D6（快照实现模型） 自己的九条判据里，条件 1 已经把
「快照 ID 进 key 低位」这个**唯一列出的候选形态**判为「目前给不出 O(1) 局部可判定的归属谓词」。
⇒ **D6（快照实现模型） 已定的是一个方向（多可写头），不是一个机制**——
而 E26（三种记账模型的查找代价与精度） 量出来的 O(N) 代价是按某个机制算的。

## 三、一条产品层的链条，不是缺陷，但值得摆出来

把三条已定决策接起来读：

1. **D25（目标负载优先级） 已定**：目标负载取**粗粒度**（seq，一次 fsync 带 8 叶、1 条共享脊柱），
   数据库 / 虚拟机镜像那类（rand / multistream）是**次**。
2. **D10（随机写 / 碎片化的真答案） 已定**：取候选 C 交给设备，
   依据正是「候选 A / B 的收益**在粗粒度下被摊薄**」。
3. **D10（随机写 / 碎片化的真答案） 自陈**：「在不支持 FDP / ZNS 的设备上，
