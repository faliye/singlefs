## 六、为什么停不下来

### 目的在哪几处掉了

| 环节 | 手上有的 | 缺的 |
|---|---|---|
| 第三轮判决 | 8 条岔路，每条带「要量的代价」 | 「这个数怎样会改变选择」「量到哪算够」 |
| 派设计员 | 6 个量、4 条臂、7 种历史、崩溃与坏镜像 | 一个字没提岔路，还明令不读第三轮判决 |
| 登记 | 问题加全部设计纪律 | 只能按「每条纪律都做到」写成 1341 / 1097 行 |
| 登记的停机条款 | S1–S4 | 全是「结论还有没有效」，没有「问题已经能回答就停」 |
| 执行员交回 | 单测、变异、产物、没做什么 | 「这一段之后哪条岔路能判」 |
| 实验状态 | 已跑、部分已跑…… | 「够判定了，其余不跑」这个合法结局 |
| 问用户续不续 | 「两个实验全部补齐」 | 选项问的是缺口补不补，不是定岔路还缺不缺这些数 |

用户后来说「如果需要，一直执行下去没有问题」。那句话在叫停之后才说，不是原因；它的立场也对。缺的是判断「需要」的那一环。

### 三处结构性缺口

1. **目的和答案放在同一份文件里。** 「设计时不看已有结论」防的是先有结论再建模型，但岔路表和结论都在判决里，挡掉结论就连目的一起挡掉了。
2. **只有「做少了」的检测器，没有「够了」的出口。** 门禁 86 号、「部分已跑」、停机条款、核查员都在查做少了；停下来看起来永远像欠账。当天为了堵「没跑完写已跑」，给设计员与执行员各加了第 3b 步，把「太大」变成了「分段做完」，没有变成「够判就停」。
3. **拆成子 agent 时，「嫌大就砍」这项没写下来的职责没有落进任何定义。** 以前登记与装置是同一个人写，写装置时会砍；现在设计员定范围不付代价，执行员付代价而为防事后建模不许改范围，主 agent 能砍但没有触发点。

三方论证那边是同一个形状：每一轮的改法生出下一轮要攻的新候选；当天补的「第三轮之后停」是轮数上限，也不是「问题判完就停」。

### 过程里另外暴露的

- **子 agent 没有人盯。** E154 第四段执行员 23:25 把 87 号复跑重定向进日志、却把 `echo "exit=$?"` 打到标准输出，23:35 起用 `until grep -q "^exit="` 等一行永远不会出现的字；它还用了规则禁止的 `pgrep -f`。主 agent 在它空转约四分钟后查进度才发现。
- **执行员的报告要主 agent 重数。** E153 第三段挑着报「突出发现」、第五段把 Q6b 的族名单写错并给不存在的 0 编了原因；实验页同一句也错，两处已改。
