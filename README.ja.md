**ゼロから設計したコピーオンライト（COW）ファイルシステム。Rust で実装。**

## なぜもう一つ作るのか

私は多くのファイルシステムのコードを読んできて、どれも優れていると思う。けれど、苦しい時代を過ごしてきたせいで、どれも贅沢が足りず、結合が強すぎて、こんなに豊かな時代になっても楽ができない。

だから私たちは楽をすることにした。singlefs は醜くてもいいし、ストレージを無駄にしてもいいし、肥大した実装の分岐をたくさん並べて持っていてもいい。

何年も後に誰かが singlefs のコードを評するとき、「一山のクソだ」ではなく「何本ものクソだ」と言ってほしい。

実装上、一か所を変えると多くの分岐を一緒に変えなければならないかもしれない。でも構わない。もう一本、違う分岐を気軽に足せばいい。たとえそれが一味違う臭さでも。

うん、まだ検証中だけど、たぶんいけると思う。
waaagh!

singlefs がフォーマットとアーキテクチャから取り組む設計上の問題と、採用した方向。設計目標であり、実装範囲は「現状」に記す。

| 痛点 | 根本原因 | このプロジェクトの選択 |
|---|---|---|
| ばかげた ENOSPC（空きがあるのに書けない、ファイルを消しても容量不足と言われる） | 二段階の割り当てと硬直した chunk の分類 | data/metadata を分けず、全体で一つのアロケータ |
| RAID5/6 の write hole | 固定幅のストライプは読み込み・変更・書き込みが要る | ストライプ幅を可変にし、読み込み・変更・書き込みを一切しない |
| クォータの集計が遅くて間違う | 集計が事後の走査で、しかも逆引きインデックスを辿る | 集計はトランザクションの副産物で、コミット時に増分で維持する |
| 逆引きインデックスが複雑さのブラックホールになった | 後から生えてきたもので、設計されたものではない | 初日からフォーマットに組み込む |
| 誰も修復ツールを走らせる勇気がない | 再構築可能性が設計目標ではなかった | メタデータブロックを自己記述にし、checker をフォーマットと一緒に進化させる |

決定とその根拠は [`.claude/kb/decisions.md`](.claude/kb/decisions.md)、落とし穴の一覧は [`.claude/kb/pitfalls.md`](.claude/kb/pitfalls.md) にある。

### 容量とオーバーヘッドのデータ

既存の実験には実測と算術モデルがあり、値はそれぞれの計測条件（デバイス、負荷、フォーマット）に限る。現行の完全なファイルシステムのスループット、遅延、汎用性能の約束ではない。対比表には全結果と履歴バージョンの制限を記している。

- 容量上限：E152 (マイルストーン別の六ファイルシステムとのファイル性能比較) の一台あたり 16 GiB の構成では、ユニット領域は一台の容量の 95.2%、ミラー化したプールの上限は二台合計の 47.6%。ツリーと会計がさらに空間を使うため実際の使用可能量はこれより少ない。単一ディスク mkfs 対応を示すものではない。対比は [`scripts/experiment-apparatus/perf-by-milestone.md`](scripts/experiment-apparatus/perf-by-milestone.md)。
- 小ファイル：データユニットのディスク占有量は固定 32 KiB。現在は 105 バイトのヘッダと 29 バイトの予約領域を除き、ペイロード上限は 32634 バイト。未使用部をゼロ埋めし、各ユニットが個別に空間を使う（E66 (パディング後に小ファイルがどう配置されるか)。実装は[データユニット構築](crates/singlefs-core/src/unit.rs)）。 D27 (小データパッキングコンテナ) は確定済みだが未実装。E120 (等比のサイズクラス表で公比をどう決めるか) の 11.1% は選択したクラス表のパディング浪費上限であり、現行実装やコンテナ全体の費用の実測ではない。
- 割り当てレコードツリー：32 KiB の配置先、充填率 90% の算術モデルで容量の約 0.055%（E74 (割り当てレコードのエントリ数と整理コスト)）。このツリーだけの値で、他のインデックス、journal、スナップショット、予約空間は含まない。

## 現状

現在のマイルストーンは「共有と回収」（[マイルストーン四](.claude/kb/milestone/04-fourth-txn.md)）。読み書き可能な二台構成のファイルシステムライブラリ原型は存在するが、コア機構の存在は全受入条件の達成を意味しない。前段階の引き継ぎは[マイルストーン三](.claude/kb/milestone/03-third-txn.md)にある。

| 能力 | 実装済み | 現在の制限 |
|---|---|---|
| フォーマットとマウント | 二台のディスクでの mkfs、書き込み可能マウント、クローズ後の再マウント、コールドスタート読み取り | mkfs は現在ちょうど二台を要求する。任意台数、RAID5/6、ホット追加は提供済みではない |
| ファイルと内容の読み書き | 一回のパブリッシュで複数ファイルを作成。inode 番号で書き、バイトオフセットで読み戻す | ディレクトリはない。上書きと順次書き込みはどちらも全内容を先頭から置換し、任意オフセットの部分書き込み入口はない |
| 削除と再利用 | 削除のインテントを先にパブリッシュしバッチ回収。ロールバック下限を越えた配置先を再利用 | 先頭ファイルの削除完了後に新規作成した inode にはデータを書けない。削除前から存在する他ファイルは引き続き書ける |
| 切り詰めと伸長 | 縮小はインテント発行後にバッチ回収。伸長と同サイズ要求はそれぞれ一回のパブリッシュ | 実際のサイズ変更は inode 1 のみ。他の生存 inode は同サイズ要求のみ受け付ける |
| 読み取り専用スナップショット | 作成・削除。参照を残す旧ブロックは deadlist に入る | 同時に最大 10 個。提供済み読み取りインターフェースは先頭ファイルのみ。書き込み可能スナップショットとクローンはない |
| ロールバックとリカバリ | マウント中の管理者ロールバック、journal 再生、リカバリ後のインテント継続 | 対応するライブラリ呼び出しとテスト負荷で検証。完全な POSIX 使用経路はない |
| トランザクションのパブリッシュ | ユーザー変更は同期パブリッシュ。一つの要求に複数のユニット単位トランザクションを含められる | 時間・ダーティバイトによる自動 checkpoint、要求間バッチ化、マウント時閾値設定は未接続 |
| 整理と回収 | インテント、領域スキャン、移動、パブリッシュ後 discard の内部経路はある | バッチサイズ未定のため既定の製品経路はインテント発行前に停止。テストスイッチで進めても自動バックグラウンド GC の提供にはならない |
| インデックスのスキャン再構築 | checker は中央マッピング、extent、inode の表をメモリへスキャン再構築して比較できる | 全ツリーを再構築し修復をディスクへ書き戻す汎用ツールはない。livelist と疎なサイドテーブルのエントリ書き手も未実装 |

システムへのマウント入口（FUSE / カーネルモジュール）、ディレクトリと POSIX インターフェース、暗号化、圧縮、小オブジェクトのパッキングは未提供。GPU 判定器はテスト用で、製品 GPU GC は未実装。設計表の可変幅ストライプ、自動整理、再構築可能性は目標であり、現在の製品能力を示すものではない。

**どんなデータもこれに保存しないこと。** ディスクフォーマットはまだ柔らかく、最初の外部ユーザーが現れるまでは作り直される可能性がある（[フォーマット進化規則](.claude/rules/format-evolution.md)）。後続のコード作業と受入条件はマイルストーン四末尾の待最適化項目に登録してある。

ライブラリの実際の使い方は[複数 inode 内容書き込みテスト](crates/singlefs-harness/tests/writes_by_inode_number_of_several_files.rs)と[切り詰めインテント・バッチテスト](crates/singlefs-harness/tests/truncation_intent_batches_and_final_batch.rs)を入口にする。開発例であり、日常使用向けのファイルシステムコマンドではない。

### 検証機構と根拠の範囲

検証表は既存の機構と入口を示すものであり、現在の作業ツリーが全ゲートに合格したという意味ではない：

| 検証 | 何を判定するか | ゲート |
|---|---|---|
| クラッシュポイント再生 | 書き込み要求のストリームを各ディスクのバリアで区切り、区間内のあらゆる永続化状態を列挙し、状態ごとにイメージを作ってリカバリとプールレベル checker を走らせる | checker-tier-crash-point-replay。フル実行はユーザーの要求時のみ |
| クラッシュ増幅 | 同じ列挙を数十億状態まで広げる。ストリームをまず判定ライブラリに記録し、ライブラリから読み戻して判定する。判定器は GPU 上で動き、二台構成で分割する | `scripts/crash/crash-amplification.sh`。ユーザーの要求時に走らせる |
| プールレベル checker | コード一覧 `IMPLEMENTED_INVARIANTS` は 108 項目。イメージと前提条件で適用範囲を判定し、全イメージで 108 項目すべてを完全に判定するという意味ではない | 上の二行から呼ばれる |
| モデル突き合わせ | ランダムな操作列を、メモリ上にだけ住む理想モデルと一歩ずつ比べる | harness-model-differential-and-scenarios |
| QEMU 実デバイス | 二つの virtio ディスク上で固定の負荷を走らせ、デバイス側で記録した書き込みと FLUSH をプログラムが記録したストリームと項目ごとに比べる。クラッシュ注入はない | checker-tier-qemu-device-streams |
| メモリ順序 | herd7 が `litmus/` 以下の各 Never を判定する。それぞれにバリアを外した対照がある | checker-tier-lkmm |
| 形式検証 | Verus は製品で使う復旧プレフィックス取得・ルート選択・リング走査の純関数核を検証する。別途整理計画・抽象モデルの証明はあるが、core の移動実行とクラッシュは対象外で、ファイルシステム全体の証明ではない | checker-tier-formal-verification |
| ミューテーション | crates のミューテーション表は一行ごとに一か所を壊し、指名したテストが赤にならなければならない。広域ミューテーション（cargo-mutants）はすべての変異に結論があり、生き残りが一つもないことを求める | checker-tier-crates-mutation-replay、checker-tier-broad-mutation |

checker の結果は「成立」「不成立」「不適用」「部分未判定」の四種で、後二者は完全な成立を意味しない。違反数や GPU 違反ビットがゼロでも、全適用条項を完全に判定したことにはならない。

対象限定監査の記録：2026-10-23 の作業ツリー監査は harness の 6 テスト対象を実行し、60 件成功、0 件失敗。複数 inode 書き込み、スナップショット、切り詰めフィールド・バッチ、内部整理動作を扱った。全ワークスペース、GPU、Verus、QEMU、全域クラッシュ検証は再実行しておらず、全体の受入証拠にはしない。コマンド、制限、ログは[コード先行監査報告](records/2026-10-23-代码先行的工程进度与决策核对.md)にある。

過去のフル実行記録（現在の作業ツリーのフル検証結論ではない）： 2026-10-16 から 2026-10-18 のフル実行はクラッシュ列挙ケース 14 件を覆い、ログに状態数のある 12 件の合計は 5,149,586,107 のクラッシュ状態（約 51.5 億）で、すべての状態に同じキーの判定があり違反 0。判定はクラッシュ判定ライブラリに保存され関数ユニットキーで再利用され、判定器は二台の GPU で走る。ケース 6 は最終のツリーで走らせ直しておらず、ケース 12 のクイック層の判定法は最終日に変えた。六本の重いゲートは 2026-10-15 に一回走った: herd7 と QEMU（仮想マシン 6 回、検査 123 項目）は緑、形式検証とミューテーション表はライト層（ミューテーション 172 行のうち 2 行が赤にならない）、広域ミューテーションには当時の版のコードに対する結論はなかった。各テストの数、計測条件、欠落は [2026-10-18 のブリーフ](briefs/2026-10-18.md)の「テストデータのまとめ」を参照。

**ゲートが全部緑でも、それはモデル層でのクラッシュ整合性の根拠にすぎず**、「検証済み」ではない。各項目がどこまで走ったか、どれが今回未実行と記録されたか、まだ何を覆っていないかは、[最新のブリーフ（2026-10-25）](briefs/2026-10-25.md)（過去のブリーフは [`briefs/`](briefs/)）を見ること。

## システム構成

マウントは各ディスクのオフセット 0 と 4096 にある二つの 4096 バイトスロットから**システム構成**を読む。定義された構造は 489 バイトで、二つのスロットを交互に使う。システム構成 → ルートリング → ルートレコード → ツリーテーブル → インデックスツリー → データユニットの読み取り連鎖に必要な幾何と同一性を供給する。スロットの冗長性は、全コピー喪失後の構成の自動復元を提供するものではない。

フォーマット上のフィールドは四分類。予約フィールドがあるだけで、全設定入口や再構築機構が実装済みとはしない：

| フォーマット分類 | バイト数 | 現在の実装範囲 |
|---|---:|---|
| 不変構成 | 389 | フォーマット、レイアウト、幾何の同一性。一部だけが mkfs パラメータであり、全フィールドを調整できるわけではない |
| 可変構成 | 4 | インデックスノードサイズ。現在は 16 KiB 定数で実装し、サイズ変更と再構築を行う汎用製品入口はない |
| 実行時構成 | 36 | 時間、ダーティバイト、整理水位フィールドは既定値を使用。マウント時設定経路と対応する自動トリガーはない |
| 実行時の量 | 60 | ファイルシステムが管理する世代、水位などの状態。対応するパブリッシュで更新し、ユーザーは直接設定しない |

自己記述ユニットはスキャンと照合を支えるが、現在の読み取り専用再構築は一部のインデックス表をメモリに得るもので、全メタデータを修復してディスクへ書き戻すものではない。完全なフィールドと互換条件は[バイトレイアウト表](.claude/kb/layout/01-first-txn.md)にある。

## コントリビューターガバナンス（Contributor Governance）

> **Implementation That Favors the AI, Review That Favors the Human（実装は AI に優しく、レビューは人に優しく）.**
>
> **Make every submitted patch review-worthy（すべての提出をレビューに値するものにする）.**
>
> **Contribution throughput may be unbounded; acceptance throughput is evidence-bound（投稿のスループットは無制限でよいが、受入のスループットは根拠に縛られる）.**

ゲートは誰かを締め出すためにあるのではない。すべての提出を、人が時間を割いて見る価値のある線まで引き上げるためにある。機械的な部分はスクリプトに任せ、人の注意は人にしか判断できないところに使う。

**受入基準は自動化された検証である。** このプロジェクトは提出者を出自で区別しない。区別は一つだけで、根拠を伴う提出と、伴わない提出である。根拠の基準は誰にとっても同じ物差しで、送る前にゲートを一度走らせれば、自分がどこに立っているか分かる。

> 開示: このプロジェクトのコード、ドキュメント、ゲートスクリプトは人と AI の協働で作られており、今後もずっとそうである。これは私たち自身のやり方の説明であって、提出者を分類するものではない。

## 貢献

三つの必須要件:

1. **`crates/*/src/` を変えたら必ずテストを付ける。** 例外はなく、「次のパッチで足す」もない。
2. **新しいテストはまず赤になることを示す**: テスト対象のコードを壊し、テストが失敗することを確かめ、元に戻す。どう確かめたかをコミットメッセージに書く。赤になることを示せないテストは書かなかったのと同じ。
3. **未実装の検証は合格のふりをしない。** ゲートはまだ組み込まれていない段階を明示的に列挙する。緑は実装済みの部分が通ったことしか意味しない。

```bash
SINGLEFS_RUN_SCOPE='种类=target; 跑什么=多inode内容写测试; 范围=1 个测试目标; 为什么=验证README的库级使用入口' \
bash scripts/hosts/capped.sh default \
bash scripts/hosts/run-with-memory-cap.sh 12G \
bash scripts/hosts/run-build-directory.sh \
cargo test -p singlefs-harness --test writes_by_inode_number_of_several_files

bash scripts/crash/crash-point-replay.sh --list-items
```

この例は harness の一対象だけを実行する。12G はメモリ上限の例で、スレッド数はプロジェクト登録値を使い、スクリプトが一時ビルドディレクトリを削除する。`--list-items` は登録用例を列挙するだけで検証は実行しない。他の対象は変更範囲で選ぶ。コミット前フルゲートの資源前提、範囲宣言、実行法は[コミット手順](.claude/skills/gate/staged-gate.md)にある。

checker 層（クラッシュ列挙ケース、QEMU、herd7、ミューテーション表、形式検証、広域ミューテーション）は既定ではコミット時にだけ走り、コマンドに `SINGLEFS_HEAVY_TESTS=commit` を付ける。クラッシュポイント再生のフル実行とクラッシュ増幅のフル実行はユーザーの要求時にだけ走る。何がヘビー層に数えられるか、ライト層とヘビー層をどう分けるかは [`.claude/rules/verification.md`](.claude/rules/verification.md) にある。

前提: herd7 には `opam install herdtools7` が要り、`SINGLEFS_KERNEL_TREE=` で `tools/memory-model` を持つ Linux のソースツリーを指す。QEMU の段階には KVM と、blklogwrites のパッチを当てた QEMU が要る（`scripts/devices/build-patched-qemu.sh` でビルドしてプライベートなディレクトリに入れ、[`qemu.env.example`](qemu.env.example) に従ってリポジトリのルートに `qemu.env` を書く）。欠けていれば走るのを拒み、システムの QEMU には戻らない。仮想マシン装置の前提は [`.claude/kb/vm-harness.md`](.claude/kb/vm-harness.md) にある。

### 複数マシンと GPU（任意）

リポジトリのルートにあるテンプレート [`multi-host.env.example`](multi-host.env.example) に従って、手元に `multi-host.env`（git では無視される）を書く。二台構成での分割、GPU 判定器、GPU カードの優先順と割り当て量、静止化のコマンドがすべてそこにあり、各キーの説明はテンプレートにある。書き終えたら `bash scripts/crash/crash-point-replay-shard-configuration-check.sh` で一度判定する。GPU を使うときは必ず先に静止化し、終わっても元に戻さない（`scripts/crash/gpu-quiesce-run.sh`）。結果がファイルになる作業を二台目に移すには `bash scripts/hosts/multi-host-run.sh --peer -- <コマンド>`。各スクリプトの置き場所は [`scripts/README.md`](scripts/README.md) にある。

ゲートスクリプトとルールは singlefs-ai-sop がまとめて配布しており、参加者は全員同じ一式を走らせる。

## 始め方

ルールとゲートは独立したリポジトリ singlefs-ai-sop にある。同じ仕様に中国語、英語、日本語の三つのリポジトリがあり（[`singlefs-ai-sop-zh`](https://github.com/faliye/singlefs-ai-sop-zh)、[`-en`](https://github.com/faliye/singlefs-ai-sop-en)、`-ja`）、対外的には `-en` が正である。このプロジェクトが使うのは `-zh`。プロジェクト内のものは**コピー**で、上流の `.git` と `CLAUDE.md` は含まない:

```bash
git clone https://github.com/faliye/singlefs.git
git clone https://github.com/faliye/singlefs-ai-sop-zh.git
cd singlefs
rsync -a --exclude '.git' --exclude CLAUDE.md ../singlefs-ai-sop-zh/ .claude/singlefs-ai-sop/
diff -rq --exclude=.git --exclude=CLAUDE.md ../singlefs-ai-sop-zh .claude/singlefs-ai-sop   # 何も出力されなければコピーは完全
bash .claude/singlefs-ai-sop/install.sh     # バージョンスタンプ .singlefs-ai-sop-version を更新する
bash scripts/crash/crash-point-replay.sh --list-items
```

上流がリリースしたら、同じ `rsync` でもう一度コピーし、`install.sh` をもう一度走らせる。**ルールの変更は上流リポジトリで行う**。`.claude/singlefs-ai-sop/` をその場で書き換えてはならない。
